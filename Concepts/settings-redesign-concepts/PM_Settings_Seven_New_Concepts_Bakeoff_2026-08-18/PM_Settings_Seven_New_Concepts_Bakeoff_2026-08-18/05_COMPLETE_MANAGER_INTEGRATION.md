# Complete Manager Integration and Coverage

## New rule: every concept is complete

The prior collective-coverage rule is superseded. Every concept 05–11 must expose and demonstrate all non-deferred manager families itself.

`shared_grammar` is not an accepted coverage status. Allowed statuses are:

```text
demonstrated
deferred_named_owner
missing
```

`missing` is a failure. `deferred_named_owner` is allowed only for a genuinely separate owner module and requires a reachable insertion destination, owner name, return contract, and no fabricated backend.

## Manager integration contract

Every manager must be reachable through its owning domain and universal search; no manager may exist only behind an obscure overflow action. Every manager remains inside the same Settings shell and uses the concept's own visual/navigation grammar. It must retain Project context, breadcrumb, search, Back, Close, theme, responsive behavior, and origin return.

A manager may use domain-appropriate archetypes:

```text
preference document
resource roster + detail sheet
inventory/catalog
setup or repair sequence
read-only health projection
diagnostic/log drawer
preview/confirmation transaction
```

Do not flatten all of them into identical setting rows. Do not launch a visually unrelated manager application.

## Shared implementation versus shared visual renderer

Allowed to share across concepts:

- actual inventory and normalized demo records;
- headless search index;
- stable IDs and route objects;
- state store and persistence simulator;
- command/receipt simulator;
- icon library;
- headless manager semantics;
- performance/test harness.

Must be concept-native:

- Home composition;
- domain navigation;
- manager shell and resource layout;
- search dropdown presentation;
- exact-result reveal;
- narrow-width navigation;
- motion and spatial transitions;
- density and typography.

No iframe, redirect, import of another concept's visible manager renderer, or link to another concept page counts as implementation.

## Provider manager density

The default provider view answers a small set of human questions first: connected state, selected account/product, available models, usage-end behavior, routing/fallback, setup/repair. Credentials, installations, model catalogs, limits, logs, and diagnostics may be coordinated subpages. Do not present a giant wall containing every provider setting at once.
