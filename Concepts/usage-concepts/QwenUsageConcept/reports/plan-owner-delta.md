## Notes

1. **Settings registry — false certification retracted on 2026-08-18.** As shipped on 2026-08-11 this row carried the disposition "demonstrated (consumer contract)", which this file's own status key defines as "U11 now shows the state end-to-end in the concept". It certified as proven the one thing that was disproven. Measured by the independent audit on 2026-08-17: the Usage quick-controls sheet mutated and persisted five Settings-owned policies to localStorage — warn before running low, automatic account/provider switching, continuation product, continuation "then" action, extra paid usage, and the monthly spending limit — while the command log gained zero entries, so zero commands were dispatched and zero deep links were taken. The evidence is `PM_Usage_Independent_Audit_2026-08-17/audit-evidence/probes/axis1-ownership-probe-results.json` (five persisted `u11:settings` writes, cmdLog delta 0). Audit findings: A01-01 (blocker, the sheet itself), A01-03 (blocker, this register and two others certifying the opposite of measured behaviour), A10-08 (minor, 27 of the 30 settings-directed controls in the UI never reach a deep link). Repair of the sheet is a separate change: this row stays retracted until a harness measures the repaired sheet, and only that measurement can restore a disposition here.

2. **Five owner paths retracted on 2026-08-18 — they were never files.** As shipped on 2026-08-11, five rows of this table named `Plans/` documents that do not exist and never existed. The verbatim paths, preserved: `Plans/Goal_Runtime.md` (row 9), `Plans/Free_Models.md` (row 7), `Plans/Notifications.md` (row 20), `Plans/Server_Project_Sync.md` (row 18), `Plans/Storage_events.md` (row 21). Re-confirmed 2026-08-18: `test -e` returns MISSING for all five and `git log --all --diff-filter=A -- Plans/<file>` returns 0 commits for each, so none was deleted — none was ever created. Packet §06 lists these as **subject areas** ("Goal Runtime", "Free Models/catalogs", "Notifications", "Server/Project Sync", "Storage/events"), never as filenames; this file converted the labels into file paths and never checked them. A deferral to a nonexistent owner is an open hole, not a handoff. The corrected owners are in the table above, each verified. Audit finding: A11-01 (major).

3. **Row-count reconciliation, 2026-08-18.** This table shipped with 19 rows against `impact-register.json`'s 10 entries and packet §06's 20 owner subjects — three different lists (audit A11-13, sub-item 3). Two edits reconcile them. First, "Planning Wizard / PRD Builder" was one merged row; the packet lists them as two subjects, so the merge is split, and the split exposed that the merged row's "demonstrated" disposition rested entirely on a Planning Wizard run — PRD Builder is now honestly marked **not demonstrated**. Second, the packet's "Provider adapters" subject had been silently replaced by a CLI-bridged-providers row; Provider adapters is restored as row 5 and CLI-bridged providers is retained as row 6, because `Plans/CLI_Bridged_Providers.md` is a real owner the concept genuinely exercises. 20 packet subjects plus that one added subject is 21 rows, and `impact-register.json` now carries the same 21.

4. **What this file is not.** Every "demonstrated" disposition here means the concept renders or holds the state described. It does not mean a harness asserted it: `reports/demo-fixture-report.json` records, per fixture, whether the evidence is a rendered-DOM check or an in-memory data assertion, and most are the latter. Nothing in this file should be read as a verification result. The full audit is at `Concepts/usage-concepts/PM_Usage_Independent_Audit_2026-08-17/`.

5. **Row 19 re-verified on 2026-08-18 (second pass).** The correction above was checked rather than taken on trust, by reading `ops-1` out of a booted page (`window.U11.operational`) rather than out of the source file. Three results. (a) The fields the row claims are all present, but they are not peers: `consent`, `installation`, `provenance` and `arch` are nested inside `acquisition` — `consent` and `source` one level down, `provenance` and `arch` two levels down inside `acquisition.installation` — and the row's original flat list read as if all nine sat on `ops-1` itself. The row now states the nesting. (b) `affectedConnections` is absent, confirmed by a deep key walk over the whole record and by `JSON.stringify(ops-1)` containing no occurrence of the string "affected" at any depth. The retracted claim is retracted correctly. (c) What reaches the reader has moved since the audit and only halfway: `outcome` now renders, both as the label "Outcome" (present in all 13 rooms) and as the value — "Rolled back" in prose and a "ROLLED BACK" badge in the Ledger and Attention rooms. `failureClass` still does not: the label "Failure class" and the value `verify_failed` in any casing are absent from all 13 rooms and from the ue-609 inspector, checked against `document.body.innerText` and `document.documentElement.outerHTML` together. So the highest-precedence subject on this table is demonstrated on data it carries, demonstrated in the UI for the outcome, and undemonstrated in the UI for the failure class. Audit finding A08-01.
