## GUI / widget / context sections

Owner of this section: GUI-surfaces research agent (Context Lens popup, context ring, More Details/Context Detail, widgets, themes, motion, command IDs, DRY, Slint). Companion sections (e.g. usage-semantics) are owned by other agents and appear separately below/above.

### Top 3 GUI gaps/conflicts (highest impact)

**G1 — Duplicate widget-add command IDs (`cmd.widget.add` vs `cmd.dashboard.add_widget`).**
Two canonical families both register widget add. `cmd.widget.add {page, widget_id}` is in UI_Command_Catalog §2 (L375) with "no persisted domain event (UI layout state update)" and surfaces "Dashboard, Usage page, Orchestrator widget tabs". Separately, `cmd.dashboard.add_widget {project_id, dashboard_id, widget_id, layout_slot,…}` is registered (UI_Command_Catalog Fable closure addendum shard 017 L55; Wiring_Matrix.production.json L6943) and emits the persisted event `dashboard.widget_added`; FinalGUISpec L27735 explicitly repairs the Add-Widget flow to "dispatch cmd.dashboard.add_widget through catalog.dashboard_add_widget". The two disagree on payload shape and on whether a domain event is persisted. The `cmd.widget.*` row also lists "Orchestrator widget tabs" as a surface, which contradicts the Widget_System Progress-only hostability rule (WS-010: only `widget-orchestrator-progress` is widget-composed; "Orchestrator widget tabs" is stale). **Action:** prototypes should treat `cmd.dashboard.add_widget`/`cmd.dashboard.catalog` as the production entrypoints and `cmd.widget.*` as the UI-layout-state primitive set; flag for owner reconciliation (UI_Command_Catalog owns IDs per DRY_Rules §2.1).

**G2 — Widget "focus mode" + S/M/L/XL size presets have no canonical command/contract.**
The prototype kebab "focus / S/M/L/XL / close" (Concepts/usage-concepts/BUILD_PLAN.md L52–53) is a build-plan contract only. Canonical Plans define: free `col_span`/`row_span` resize via `cmd.widget.resize` (UCC L377), and `cmd.widget.configure` for presentation config (UCC L378) — but there is **no `cmd.widget.focus`, no focus-mode definition, and no S/M/L/XL preset table** anywhere in canonical Plans. S/M/L/XL must be implemented as presets over col_span/row_span; "focus mode" is unowned. **Action:** either map focus→an existing surface affordance or register it; do not let each concept invent its own.

**G4 — No canonical command ID for a reduced-motion toggle.**
Reduced motion is a **setting** (`reduce-animations` drives application reduced-motion, FinalGUISpec L29698; `prefers-reduced-motion` honored L2120) with strong canonical behavior (instant show/hide under reduced motion: ACD-439 L24070; F3-473 L31262–31274). But there is **no `cmd.theme.set_reduced_motion` / `cmd.accessibility.*` command ID** in UI_Command_Catalog. The prototype's "manual MOTION toggle AND prefers-reduced-motion" (Rebuild Plan L26) has no canonical command to dispatch. **Action:** prototype may toggle the setting locally, but a canonical command ID is missing and should be registered if the toggle persists.

### Additional GUI gaps / conflicts

**G3 — Widget sizing contract ambiguity (presets vs free grid-span).** Canonical = free grid-snapping `col_span`/`row_span` (FinalGUISpec §C.1 L18–24; `cmd.widget.resize`). Prototype = "free resize with coarse-grid snap only on pointer-up, FLIP no-flash" + S/M/L/XL presets (Rebuild Plan L53). The snap-timing (continuous vs pointer-up) and the preset ladder are not canonicalized. Reconcile snap behavior before implementation.

**G5 — "No left status edge-bars" / "no-colored-edge-strip" is stricter than canon.** Prototype build plan (Rebuild Plan L28) bans left status edge-bars on usage widgets. Canonical Plans use left-edge accent stripes/bars for **selection**: activity-bar "3px left-edge accent stripe" (FinalGUISpec L615; shard 010 L106) and chat-rail left accent bars (ACD-444 L24346–24347). Not a true conflict if the prototype rule is scoped to *status* strips on cards (vs *selection* indicators), but the scoping is unstated — record as a reconciliation note.

**G6 — "No user-facing underscore" has no canonical Plans prose.** Rebuild Plan L27 ("humanize at the view layer via R.human") is prototype-only. Canonical only governs machine IDs (underscores allowed in command segments: Wiring_Matrix.schema L76; Wiring_Matrix.md L152). If the no-underscore UI rule must hold in Slint, it needs a canonical home (FinalGUISpec/Glossary).

**G7 — Detailed motion tokens (cubic-beziers/durations) are not canonical.** The full easing/duration table (entrance/exit/interactive/scale-in/pulse/count-up/stagger) lives only in Rebuild Plan L59–75, which itself defers a "future spec motion annex" (L124–125). Canonical motion = the sprout family (~300ms open / ~220ms close, overshoot, reduced-motion-instant: ACD-439) + the F3-473 web→Slint map. Prototype-specific beziers are non-binding until promoted.

**G8 — "Context Lens popup" naming conflation.** Prototype/handoff language calls the usage popup the "Context Lens popup". Canonically the popup carrying Usage/Tokens/Cost/Compact Now/More Details is the **context ring status module** (ACD-441/ACD-434; usage-feature UF-011), distinct from the **Context Lens** mute/focus/subcompact control (F3-306; `cmd.chat.context_lens.*`). They share the ACD-442 sprout chrome. The build plan's "Context-Lens popover = the one standard popup" (Rebuild Plan L24) refers to the shared chrome contract, not the control. Risk: wiring the wrong command family to the usage popup.

**G9 — More-Details density ("calm editorial", "show N messages") is build-plan prose, not canonical.** The stacked-bar + collapsible by-role legend + three cost figures + "show N" + Raw-at-bottom layout (Rebuild Plan L16–19) is a locked build decision; canonical IA is Curated{Overview,Breakdown,Messages}/Raw with expandable per-message rows (assistant-chat-design §12.0 shard 018 L34–40; UF-012). "show N messages" has no canonical command — it is a local collapse over canonical per-message expansion + the `cmd.chat.open_thread_context_details` deep-link.

**G10 — Settings "scrollbar on every scroller" is prototype guidance.** Canonical only defines the `scrollbar-width` theme token (Retro 12px styled / Basic 8px system-like; FinalGUISpec §6.2 shard 013 L58). The "apply the Settings scrollbar treatment to every scroller" rule (Rebuild Plan L25) has no separate canonical statement.

## Usage semantics sections (token / quota / cost / projection)

Owner of this section: usage-semantics research agent (token buckets & counting_semantics, "used tokens", quota windows/reset/cooldown, burn/run-out, projection provenance, cost model, no-double-count, missing-vs-zero, non-authoritative-quota providers). Companion GUI section appears above. All citations re-verified against the live corpus 2026-07-30. Full prose + citations: `plans-usage-synthesis.md`; proof-of-reading: `plans-source-ledger.json`.

### Top 3 usage-semantics gaps/conflicts (highest impact)

**U1 — "burn rate" / "run-out" (forecast exhaustion) has NO canonical definition in `Plans/**`.**
The prototypes' secondary Cost section wants burn + run-out (Concepts/usage-concepts/BUILD_PLAN.md L79, L130), but those terms appear ONLY as (a) build-plan/demo-realism prose (Claude-Code-Usage-Monitor "burn, P90/custom limit, run-out", computation-only), (b) the `spend_rate_exceeded` anomaly class (UF-083 `usage-feature.md:6016`), and (c) UF-065's pre-execution high-cost "cost forecast and warning semantics" (`:4362`, `:897`) — which is action disclosure, NOT quota forecasting. The only canonical numeric rate is the anomaly formula `current_window_cost / max(median_previous_7_windows_cost, 1)`, threshold `3.0`, confidence `min(1.0, observed_samples/7.0)` (`:5811`). The only canonical hook for a forecast is the window model: `fixed_reset` has a reset boundary, `rolling` a sliding lookback (`:602-603`), but **no formula, and no insufficient-history/zero-burn/reset-before-exhaustion handling is specified**. **Action:** any prototype burn/run-out MUST be a clearly-labeled derived GUI projection over the canonical window model + `provider_total`, fail-closed to `unknown` when history is insufficient, and must NEVER render a fabricated countdown (UF-085 `:5711`, UF-087 `:5441`). Recommend promoting a canonical burn/run-out definition before implementation.

**U2 — No literal rule forbidding synthesizing a WEEKLY reset from a 5-HOUR reset; `window_kind` has no per-provider value (except MiniMax).**
Canonical `window_kind = rolling | fixed_reset | billing_cycle | session_only | unknown` (`usage-feature.md:597`; UF-041 `:3080`). "5-hour"/"weekly"/"monthly" are **`window_label`/duration values, not kinds** — yet the rebuild plan frames "5h short window (7d weekly)" (L12). The anti-synthesis rule is only IMPLIED by: Alibaba 5h/weekly/monthly windows must be **preserved separately, not flattened** (`:358`); avoid one generic 5h/7d column (UF-041 `:3120`); no fabricated countdowns from probes (UF-085 `:5711`, UF-087 `:5441`); and 5h vs 7d being separate fields with separate `resets_at` (MA-063 `Multi-Account.md:915`). The rebuild plan itself flags "no explicit `window_kind` per provider except MiniMax; Ollama/local unnamed" (L117). **Action:** treat each window as carrying its OWN reset evidence; never derive one window's reset from another's; render `Unknown reset` when a window has no authoritative `resets_at` (`:352`). Recommend an explicit "one reset per window; no cross-window reset synthesis" rule.

**U3 — "three cost projections (API-billed / plan-included / combined)" and "add-on/overage bucket (own used + reset)" are BUILD-PLAN framings, not canonical vocabulary — and a second cost model is explicitly banned.**
Canonical cost authority is SINGLE: `cost_microdollars` (integer u64) and/or provider minor units + currency; `cost_usd` is display-only (Contracts_V0.md:2192-2196 / shard `contracts_v0/015:14-19`; `usage-feature.md:523-524`; UF-085 `:5619`). The rebuild plan's three-way Cost split is "GUI projections over the single UsageRecord cost authority (UF-087), not a second cost model" (L20-22), and "purchased extra usage = its own add-on/overage bucket (own used + reset)" (L23) is a build decision. Canonical Plans only have: overage as **policy/entitlement states** (`paid_overage_disallowed`, `paid-overage policy` — `usage-feature.md:254-255`; UF-077 `:5226`) and the hard rule that **plan-backed vs API-billed buckets must NOT merge** (Codex `:233`; MA-023 `Multi-Account.md:2291`). UF-064 bans feature-local cost views (`:4295-4353`). **Action:** prototype's API-billed/plan-included/combined and add-on bucket must be presentation projections over UF-085 `cost_microdollars` + `cost_status`/`source_class` (e.g. `pricing_estimated` vs `provider_reported`) + `entitlement_class` — never a parallel cost store. The add-on "own used + reset" needs a canonical owner if it is to persist.

### Additional usage-semantics gaps / conflicts

**U4 — `value_state` has no single canonical closed enum; two overlapping lists exist.** UF-074 (`usage-feature.md:5041`) lists `missing, unavailable, unsupported, blocked, stale, estimated, provider-reported, zero`; F3-418 (`FinalGUISpec.md:27751`) and UF-087 (`:5435`) add `disabled, not_exposed, hidden_byok, hidden_subscription, streaming_partial, failed, adjusted`. Reconcile into one closed enum (and give it a Glossary home — see U6).

**U5 — `source_authority` is carried everywhere but has NO spelled-out closed enum** in the usage docs. `source_class` (UF-085 `:5619`) and `source_confidence = high|medium|low|unknown` (UF-074 `:5041`) are closed; `source_authority` is referenced alongside them (UF-085/UF-087/F3-418/CV-316) with values like "authoritative vs derived" implied but never enumerated. Risk: prototypes inventing authority labels.

**U6 — Glossary is missing the provenance vocabulary.** Rebuild plan L119 records that the Glossary lacks `settlement_status / source_class / value_state / source_confidence / cost_status`. These enums live in usage-feature/Contracts/FinalGUISpec but have no Glossary SSOT entry. (Related: rebuild plan L120 notes `UF-034 merges freshness+health (should be two enums)` — but FinalGUISpec L2495 ALREADY splits `projection_freshness = current|refreshing|stale` from `projection_health = healthy|degraded|unavailable`, so UF-034's merged framing is stale and should be retired, not mirrored.)

**U7 — `cache ⊆ input` is not explicit in Prompt_Pipeline.** Rebuild plan L120 records this. `counting_semantics` (the inclusive/exclusive authority) lives in usage-feature (UF-085/UF-086) and Contracts (shard 015), but the Prompt_Pipeline owner doc does not restate it; consumers reading only Prompt_Pipeline could miss the no-double-count rule.

**U8 — `widget.budget_donuts` is in the canonical default Usage layout, but the rebuild plan says to kill it.** Canonical default layout includes `widget.budget_donuts` ("Donut charts for budget consumption per platform", `usage-feature.md:797`, config at `:819`); rebuild plan L84 says "kill the wrong-metric 'budget' donuts (u5/u6/u8)". Direct conflict between the canonical widget catalog and the prototype plan — needs an owner adjudication (and a canonical replacement metric if budget donuts are retired).

**U9 — daily-summary rollup has no storage owner; Antigravity honesty rules are scattered.** Rebuild plan L121 records "daily-summaries rollup has no storage owner" (compaction into daily summary records is described at `usage-feature.md:619` but not owned in storage-plan), and L116 records Antigravity honesty rules scattered across CLI_Bridged_Providers (`:1441`) and usage-feature (`:281-346`). Both are reconciliation/owner-routing gaps, not prototype blockers.
