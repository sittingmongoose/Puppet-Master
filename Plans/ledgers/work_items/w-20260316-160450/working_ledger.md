    - input: `header?: string`, `text: string`, `options?: string[]`
    - output: `answer: string`
  - but the already-locked product UX and existing workflow docs now imply a richer contract:
    - Interview/clarification flows already use structured question UI
    - `Contracts_V0.md` already carries `question_ids[]` in `requirements.clarification_requested`
    - `FinalGUISpec.md` already models question counts, inline question forms, and wizard/thread resume behavior
- New high-signal gap:
  - `Permissions_System.md` currently does **not** list `question` in the permission-key table or default-permission table at all, even though `Tools.md` gives it a permission key.
- Final recommendation:
  - canonically support two modes:
    - `single_question`
    - `questionnaire`
  - keep legacy single-question callers working as sugar over the richer envelope
  - recommended minimum input envelope:
    - `mode: "single_question" | "questionnaire"`
    - `header?`
    - `prompt?`
    - `questions: Array<QuestionItem>`
  - `QuestionItem` minimum fields:
    - `question_id`
    - `question`
    - `description?`
    - `options?`
    - `required?` (default true)
    - `multi_select?` (default false)
    - `allow_freeform?` / `allow_other?` (default true)
    - `placeholder?`
    - `default_values?`
  - recommended output envelope:
    - `status: "answered" | "submitted" | "dismissed" | "timed_out" | "unavailable"`
    - `answers: Array<{ question_id, values: string[], source?: "option" | "other" | "freeform" }>`
    - optional backward-compat `answer_text?` for true single-question callers
- Behavioral rules:
  - multi-question flows are first-class, not an edge case
  - users may answer in any order
  - required questions block final submit
  - draft answers auto-save until submit or dismiss
  - dismiss is an explicit state, not a fake submission or rejection
  - headless / HITL-unavailable paths return `status = "unavailable"` rather than fabricated answers
  - subagents/brainstorming should not spam users with independent question flows; coordinated top-level Q&A remains the product rule
- Permission recommendation:
  - add `question` to `Permissions_System.md`
  - recommended default: interactive-surface-friendly / effectively `allow` when HITL is available, with runtime returning `unavailable` when the surface cannot present questions
  - this keeps the tool aligned with clarifying-question-first product behavior rather than treating normal user questioning as a gated side effect
- Storage / event recommendation:
  - bounded structured questionnaire drafts should persist thread-scoped answer data only
  - do not persist arbitrary widget/UI state
  - existing clarification events with `question_ids[]` remain compatible and should be treated as evidence that multi-question identity is already canonical on the workflow side
