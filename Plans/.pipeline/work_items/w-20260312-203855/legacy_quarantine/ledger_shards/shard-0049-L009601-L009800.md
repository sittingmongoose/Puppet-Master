L009678: ### Key findings
L009679: - The canonical field family is already mostly clear:
L009680:   - `node.blocked` / `node.unblocked`
L009681:   - `blocked_reason_code`
L009682:   - `blocked_sequence`

L009684:   - `node.prerequisite_resolved`
L009685:   - `wake_reason = approval_resolved | clarification_resolved | auth_recovered | startup_recovered | ...`
L009686: - The missing piece is ownership semantics, not field naming:
L009687:   - no doc clearly says who mints `blocked_sequence`
L009688:   - no doc clearly says when a new blocked episode starts versus an existing one being updated
L009689:   - `request_id` still competes with `blocked_sequence` in HITL/storage examples
L009690:   - startup recovery wakeups are named but not tied to a concrete blocked-episode restoration rule
L009691:
L009692: ### Recommended owner decision
L009693: - `blocked_sequence` should be owned by the runtime scheduler/executor layer, not by UI/HITL/chat/storage.
L009694: - Scope:
L009695:   - monotonic per `{ run_id, node_id }`
L009696:   - starts at `1`
L009697:   - increments only when the node transitions from non-blocked to a new blocked episode
L009698: - A blocked episode is the canonical unit for:
L009699:   - approval waiting
L009700:   - clarification waiting
L009701:   - auth/prerequisite waiting
L009702:   - permission/FileSafe/external-side-effect block
L009703:   - worktree conflict / dirty-worktree block
L009704: - Updating metadata for the same unresolved blocked prerequisite must retain the same `blocked_sequence`.
L009705: - A new `blocked_sequence` is minted only when:
L009706:   - the prior blocked episode was resolved/unblocked and a later distinct blocked condition occurs, or
L009707:   - the blocked reason changes in a way that creates a genuinely new recovery episode rather than additional detail on the same episode
L009708:
L009709: ### Recommended HITL/request bridge
L009710: - `blocked_sequence` should be canonical; `request_id` should become a child/compatibility handle for approval-specific UX/history.
L009711: - Practical rule:
L009712:   - `waiting_approval` blocked episode exists first-class in runtime/state
L009713:   - if the blocked reason needs an approval prompt surface, the system may also mint a stable `request_id`
L009714:   - that `request_id` maps 1:1 to the underlying `{ run_id, node_id, blocked_sequence }`
L009715: - `request_id` must never be the only durable key for recovery/mutation decisions.
L009716: - Approval commands should route by blocked episode identity; any retained `request_id` is lookup metadata, not the canonical recovery target.
L009717:
L009718: ### Recommended startup-recovery handshake
L009719: - On restart, the runtime restores current unresolved blocked episodes from canonical blocked/runtime records/projections.
L009720: - The scheduler then emits a scheduler pass with `wake_reason = startup_recovered`.
L009721: - That startup-recovery pass does not mint new blocked episodes by itself; it rehydrates existing unresolved episodes and reevaluates runnable work.
L009722: - If restart determines an in-flight attempt cannot resume, that attempt transitions to `stale_historical`; if a blocked prerequisite still exists, the existing unresolved blocked episode remains the actionable state.
L009723: - If restart discovers a previously persisted blocked episode is no longer valid because the prerequisite was already satisfied externally, the recovery cycle should resolve/unblock that episode explicitly rather than silently dropping it.
