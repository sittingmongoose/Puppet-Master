L005475: ### Key findings
L005476: - The earlier general escalation ladder still fits:
L005477:   - `info`
L005478:   - `warning`
L005479:   - `attention_required`
L005480:   - `blocked`
L005481:   - `system_notification`
L005482: - The current docs already give strong pieces of the behavior:
L005483:   - blocked and attention-required stay distinct
L005484:   - wizard-blocked cards outrank wizard-attention-required
L005485:   - thread badges preserve highest severity and blocked counts
L005486:   - usage warnings support thresholds, quiet periods, and clear actions
L005487:   - all-nodes-blocked can escalate by elapsed time
L005488: - What was still missing was the interaction policy:
L005489:   - how concern state influences escalation
L005490:   - how blocked-owner influences message routing
L005491:   - how stale/degraded trust should suppress or qualify notifications
L005492:
L005493: ### Concern interaction direction
L005494: - Strong recommendation:
L005495:   - concern severity alone should not drive escalation
L005496:   - escalation should be based on concern severity + execution impact + persistence + ownership
L005497: - Good working rule:
L005498:   - advisory concern with no execution effect
L005499:     - usually `info` or `warning`
L005500:   - concern tied to weak integration but not yet completion-blocking
L005501:     - `warning` or `attention_required`
L005502:   - concern that blocks seam completion, promotion, or recovery
L005503:     - `blocked`
L005504: - `acknowledged` concerns should reduce repeat in-app surfacing, but they must not mask an active blocked state if the underlying condition still blocks progress.
L005505:
L005506: ### Blocked-owner interaction direction
L005507: - Blocked owner now looks like one of the most important routing dimensions.
L005508: - Recommended rule:
L005509:   - blocked owner influences both destination surface and notification style
L005510: - Examples:
L005511:   - `User`
L005512:     - eligible for thread/chat prompt, Dashboard/Progress CtA, and possibly system notification
L005513:   - `Package Overseer` / `Seam Overseer` / `Corroboration`
L005514:     - usually operational surfaces first, with user escalation only if persistence or decision need crosses threshold
L005515:   - `Runtime` / `Recovery` / `Graph Patch`
L005516:     - often Progress/History/Node Graph first; user notification only when action or trust decision is actually needed
L005517:   - `External Resource`
L005518:     - likely warning/banner first, system notification only if it stalls meaningful progress long enough
L005519:
L005520: ### Projection-trust interaction direction
L005521: - This seam changed materially after the projection-trust work.
L005522: - Important rule:
L005523:   - stale or degraded projections must not generate overconfident notifications
L005524: - Recommended behavior:
L005525:   - if a summary surface is `stale`
L005526:     - local in-app indicators may still show, but wording should disclose possible staleness
L005527:   - if a surface is `degraded`
L005528:     - avoid strong notification claims that rely on incomplete projections
L005529:     - prefer notifications rooted in canonical events/blocked records rather than derived rollups
L005530: - Example:
L005531:   - a degraded concern rollup should not emit a fresh “3 new concerns” system notification unless canonical records support it
L005532:   - a canonical blocked event can still drive notification even if some projection surfaces are degraded
L005533:
L005534: ### Routing / surface direction
L005535: - Good emerging routing model:
L005536:   - `History`
L005537:     - canonical chronology of everything
L005538:   - `Progress` / `Dashboard`
L005539:     - active operational attention and grouped counts
L005540:   - `thread/chat`
L005541:     - direct user-action path when the blocked owner or flow genuinely needs user input
L005542:   - `system notification`
L005543:     - sparse summon layer for high-value action-needed states
L005544: - This means many concern changes should remain in-app only unless:
L005545:   - owner is effectively the user
L005546:   - blocked persistence crosses threshold
L005547:   - new actionable path becomes available
L005548:
L005549: ### Resurfacing direction
L005550: - The earlier “don’t spam on every heartbeat” rule still stands, but now it needs sharper triggers.
L005551: - Good resurfacing triggers:
L005552:   - severity increase
L005553:   - blocked owner change
L005554:   - concern changes from advisory to execution-impacting
L005555:   - blocked duration threshold crossed
L005556:   - trust state improves enough that previously suppressed actions become available
L005557:   - trust state degrades enough that prior assumptions are no longer safe
L005558: - Poor resurfacing trigger:
L005559:   - unchanged scheduler ticks or repeated identical stale summaries
L005560:
L005561: ### Usage / pressure interaction direction
L005562: - Usage warnings are the clearest existing example of quiet-window behavior.
L005563: - Recommended generalization:
L005564:   - pressure/threshold warnings may use quiet periods
L005565:   - blocked states and canonical action-needed episodes may not quietly disappear behind the same suppression rule
L005566: - This is especially important when usage/account pressure turns into a real blocked execution condition.
L005567:
L005568: ### Copy / severity interaction
L005569: - Because projection trust now matters, some notification copy needs qualification.
L005570: - Good copy patterns:
L005571:   - `Warning: provider pressure high`
L005572:   - `Blocked: waiting on user approval`
L005573:   - `View may be stale; refresh before acting`
L005574:   - `Projection degraded; showing canonical history only`
L005575: - Bad pattern:
L005576:   - a strong imperative or resolved-sounding notification driven from an untrusted summary projection
L005577:
L005578: ### Contradictions / gaps surfaced
L005579: - Current docs define many notification pieces, but not enough of the interaction policy between concern state, blocked ownership, and projection trust.
L005580: - Without this interaction layer, the UI could:
L005581:   - over-notify on advisory concerns
L005582:   - misroute blocked episodes to the wrong surface
L005583:   - emit confident alerts from degraded projections
L005584: - The quiet/dismiss model is much clearer for usage warnings than for general operational warnings.
L005585:
L005586: ### Candidate fixes to carry forward
L005587: - Define notification routing using:
L005588:   - severity
L005589:   - execution impact
L005590:   - blocked owner
L005591:   - persistence
L005592:   - projection trust
L005593: - Keep concern acknowledgment as a noise-control mechanism, not a blocked-state suppressor.
L005594: - Allow quiet windows for advisory/pressure warnings, not for canonical blocked episodes that still require action.
L005595: - Require degraded/stale disclosure or canonical revalidation before strong notification claims are emitted from projection-heavy surfaces.
L005596:
L005597: ### Do-not-forget details
L005598: - blocked owner is not just descriptive; it should help decide where and how the user is notified
L005599: - projection trust should affect notification confidence, not only action gating
L005600: - acknowledged concerns can reduce noise, but they must not create fake health when the runtime is still blocked
