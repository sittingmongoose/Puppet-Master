L006413: ### Key findings
L006414: - Existing docs already imply three distinct action classes, even though they do not name them centrally:
L006415:   - low-risk presentation actions may use no confirmation plus short undo windows
L006416:   - durable state transitions often require explicit confirmation or explicit rationale
L006417:   - destructive or topology-changing actions use stronger gating and are not true undo
L006418: - `Widget_System.md` is useful mainly as a negative precedent here:
L006419:   - widget removal is intentionally lightweight and reversible via a short local undo window
L006420:   - concern actions should NOT inherit that policy because concerns are canonical operational/governance records rather than ephemeral layout state
L006421: - `FinalGUISpec.md` reinforces the right asymmetry:
L006422:   - delete / rollback / repository creation / permission preset replacement all use confirmations because they create durable or side-effectful changes
L006423:   - annotation flow distinguishes runtime-progressed state (`addressed`) from user-controlled semantic closure (`resolved`)
L006424:   - dismissible banners are presentation-noise controls, not durable issue-state transitions
L006425: - That creates a cleaner concern action split:
L006426:   - `acknowledge` is closest to noise-control / ownership-signaling
L006427:   - `dismiss` is a durable semantic judgment and must not look like closing a toast
L006428:   - `resolve` is not one generic operation; it needs `resolution_kind`
L006429:   - `merge` / `split` / `supersede` are structural lineage edits, not ordinary state toggles
L006430: - The safest cross-cutting rule is:
L006431:   - concern actions never hard-delete canonical concern history in normal operation
L006432:   - concern "undo" should generally be implemented as compensating follow-up records (`reopened`, reverse-merge lineage, successor concern, etc.), not history erasure

L006442: ### Contradictions / gaps surfaced
L006443: - There is still no canonical concern action matrix spanning:
L006444:   - confirmation level
L006445:   - rationale requirements
L006446:   - who may perform the action
L006447:   - reversibility model
L006448:   - lineage side effects
L006449: - Existing UI docs have many local confirmation examples, but nothing yet defines how durable concern actions should differ from:
L006450:   - dismissing a banner
L006451:   - removing a widget
L006452:   - resolving an annotation
L006453:   - deleting a file / run / skill
L006454: - Concern lifecycle is now fairly clear, but lifecycle alone is not enough:
L006455:   - `dismissed` without required rationale will look too much like a convenience close
L006456:   - `resolved` without required `resolution_kind` will collapse meaningful semantic differences
L006457:   - `merge` / `split` / `supersede` without dedicated action policy will create silent lineage ambiguity
L006458: - There is still no explicit rule for whether runtime/overseer actors may directly perform concern-state transitions versus only propose them through linked records.
L006459:   - This matters because `acknowledged` is plausibly actor-driven
L006460:   - but `dismissed`, manual `accepted_risk`, and some lineage edits likely need tighter authority
L006461:
L006462: ### Candidate fixes to carry forward
L006463: - Add a canonical concern action policy table with at least:
L006464:   - `action`
L006465:   - `allowed_actor_kinds`
L006466:   - `confirmation_level`
L006467:   - `rationale_required`
L006468:   - `resulting_status_or_lineage`
L006469:   - `reversibility`
L006470:   - `audit_fields`
L006471: - Recommended default policy:
L006472:   - `acknowledge`: confirmation `none`; rationale optional; reversibility `compensating_action_only` via explicit return to `active`
L006473:   - `resolve` from a linked canonical fix/recovery/patch outcome: confirmation `none` or `light`; rationale optional if the linked record is sufficient; reversibility `compensating_action_only` via `reopened`
L006474:   - `resolve` without linked canonical evidence, including `accepted_risk`: confirmation `strong`; rationale required; reversibility `compensating_action_only`
L006475:   - `dismiss`: confirmation `strong`; rationale required; reversibility `compensating_action_only` via explicit `reopened`
L006476:   - `reopen`: confirmation `none` or `light`; rationale optional but recommended when reopening a dismissed concern; reversibility `compensating_action_only`
L006477:   - `merge` / `split` / `supersede`: confirmation `strong`; rationale required; reversibility `compensating_action_only` through new lineage records, never silent history rewrite
L006478: - Reserve `hard_gate` for exceptional concern-affecting operations only:
L006479:   - admin repair
L006480:   - privacy/redaction paths
L006481:   - cross-run or cross-scope lineage rewrites that could materially change audit interpretation
L006482: - Treat "quiet" or temporary suppression as UI-notification behavior, not concern dismissal.
L006483:   - concern dismissal changes concern meaning/state
L006484:   - quieting only changes resurfacing behavior
L006485: - Treat `acknowledged` as escalation/noise control and ownership visibility, not semantic closure and not blocker removal by itself
L006486:
L006487: ### Do-not-forget details
L006488: - concern operations should likely be available from multiple surfaces (`Progress`, `Seams`, `Evidence`, `History`, `Ledger`, graph inspector), so the same action policy must survive different UI densities
L006489: - narrow surfaces must not compress `dismissed` and `resolved` into one generic "closed" action
L006490: - the audit trail should preserve who acknowledged/dismissed/resolved/reopened and why, even when the visible current state looks simple
L006491: - if a concern is currently tied to active blocked status, acknowledgment alone must not clear the block
L006492: - structural concern actions (`merge`, `split`, `supersede`) likely need guided flows rather than one-click menus because they change search/history/ledger interpretation
