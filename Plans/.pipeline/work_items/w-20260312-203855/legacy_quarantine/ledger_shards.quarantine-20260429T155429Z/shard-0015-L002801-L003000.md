L002801:   - higher-level objects like promotions, concerns, graph patches, recovery records, and lane/worktree lifecycle states are not yet using one shared semantic vocabulary
L002802: - There are several similar-but-different concepts in play:
L002803:   - `historical`
L002804:   - `stale_historical`
L002805:   - `superseded`
L002806:   - `revoked`
L002807:   - `reopened`
L002808:   - `archived`
L002809:   - `deleted` / `removed`
L002810: - These should not collapse into a generic "old" state.
L002811:
L002812: ### Recommended semantic split
L002813: - Strong recommendation:
L002814:   - separate `time status`, `replacement status`, and `validity status`
L002815: - Working interpretation:
L002816:   - `historical`
L002817:     - no longer current/live, but still part of valid history
L002818:   - `stale_historical`
L002819:     - historical and specifically not resumable/reusable as live execution state
L002820:   - `superseded`
L002821:     - replaced by a newer canonical successor for the same semantic slot
L002822:   - `revoked`
L002823:     - previously accepted/active decision or state was explicitly withdrawn
L002824:   - `reopened`
L002825:     - an object previously treated as settled/completed became active again
L002826:   - `archived`
L002827:     - hidden from default operational surfaces but retained and queryable
L002828:   - `removed`
L002829:     - live backing object is gone, but history may remain
L002830:
L002831: ### Important distinction examples
L002832: - `historical` vs `superseded`
L002833:   - every superseded object is historical
L002834:   - not every historical object is superseded
L002835: - `superseded` vs `revoked`
L002836:   - `superseded` = replaced by newer truth
L002837:   - `revoked` = prior acceptance/approval/promotion was invalidated or withdrawn
L002838: - `archived` vs `historical`
L002839:   - `historical` is record/time truth
L002840:   - `archived` is visibility/operational-surface policy
L002841: - `removed` vs `revoked`
L002842:   - `removed` is backing-object or storage-presence state
L002843:   - `revoked` is semantic validity state
L002844:
L002845: ### Candidate application by object family
L002846: - attempts
L002847:   - already have `stale_historical`
L002848:   - should also expose when an attempt is superseded by later remediation/graph generation
L002849: - promotions
L002850:   - need explicit distinction between:
L002851:     - current accepted promotion
L002852:     - historical prior promotion
L002853:     - revoked promotion
L002854:     - superseded promotion if replaced by a later accepted promotion
L002855: - concerns
L002856:   - lifecycle already includes `active`, `acknowledged`, `resolved`, `dismissed`
L002857:   - still needs historical semantics:
L002858:     - merged/split/superseded concern records
L002859:     - resolved-but-historical concern lineage
L002860: - graph patches
L002861:   - old path/generation is historical
L002862:   - invalidated prior path may be superseded by newer generation
L002863:   - the patch request/decision record itself may later be historical without being revoked
L002864: - recovery records
L002865:   - restore attempts and recovery episodes need current vs historical semantics
L002866:   - failed or abandoned recovery attempts should remain visible without masquerading as current recovery truth
L002867: - lane/worktree records
L002868:   - backing worktree may be removed
L002869:   - lane may still be historical
L002870:   - archival policy should be separate from semantic validity
L002871:

L002890: - Attempts have a clearer historical contract than other major record families.
L002891: - There is not yet one shared semantic glossary for `historical` / `superseded` / `revoked` / `reopened` / `archived` / `removed`.
L002892: - Deletion/archive language in storage docs risks bleeding into semantic validity language if not separated carefully.
L002893: - Orchestrator/UI docs currently refer to some of these ideas conceptually, but not yet as one consistent cross-record system.

L002912: ## Research Progress - 2026-03-16 - Project-Level Run Relationship Clarification
L002913:
L002914: ### Confirmed clarification
L002915: - Multiple Orchestrator runs within the same project may be completely unrelated.
L002916: - Example:
L002917:   - run A adds one feature
L002918:   - run B later adds a different feature
L002919:   - both are in the same project/repo
L002920:   - neither should imply lineage or semantic succession relative to the other unless an explicit relationship exists
L002921:
L002922: ### Implications
L002923: - `historical run` must not imply:
L002924:   - predecessor/successor relationship
L002925:   - continuation of the same orchestration thread
L002926:   - supersession by a newer project run
L002927:   - shared seam/package/node identity
L002928: - `historical` at the run level should mean only:
L002929:   - not the currently focused live run
L002930:   - or older in time than another selected/current run
L002931: - Relationship must be explicit, not inferred from same-project membership.
L002932:
L002933: ### Recommended run-semantics split
L002934: - Distinguish:
L002935:   - `historical run`
L002936:   - `related run`
L002937:   - `derived run`
L002938:   - `retry/recovery run` or continuation lineage if such a concept exists later
L002939: - Working interpretation:
L002940:   - `historical run` = any non-active/non-focused run retained for the project
L002941:   - `related run` = explicitly linked by user/system relationship metadata
L002942:   - `derived run` = intentionally spawned from or based on another run's outputs/graph/contracts
L002943: - Default rule:
L002944:   - same project does not mean related
L002945:   - same repo does not mean related
L002946:   - temporal order does not mean related
L002947:
L002948: ### UI direction
L002949: - History should default to chronological project run history, not lineage history.
L002950: - If there is no explicit relationship, runs should appear as separate entries only.
L002951: - If explicit relationships are introduced later, the UI may add:
L002952:   - `derived from run ...`
L002953:   - `retry of run ...`
L002954:   - `continuation of run ...`
L002955:   - `shares feature seam with run ...`
L002956: - But those must be explicit metadata, not inferred by heuristics.
L002957:
L002958: ### Search / routing implication
L002959: - Search results should preserve run identity exactly and avoid collapsing similarly named seams/packages/nodes across unrelated runs.
L002960: - Cross-run navigation should switch focus to the selected run, not imply that the selected object is part of the currently focused run's lineage.
L002961:
L002962: ### Historical semantics refinement
L002963: - At the run level:
L002964:   - `historical` is mostly a focus/time classification
L002965:   - not a semantic replacement classification
L002966: - `superseded`, `revoked`, `reopened`, etc. should apply only where real object lineage/validity relationships exist, not to arbitrary project runs.
L002967:
L002968: ### Candidate fixes to carry forward
L002969: - Keep project run history chronological-first.
L002970: - Add explicit run-relationship metadata if the product later wants cross-run derivation/continuation concepts.
L002971: - Avoid UI copy like `superseded by newer run` unless there is an explicit relationship proving that.
