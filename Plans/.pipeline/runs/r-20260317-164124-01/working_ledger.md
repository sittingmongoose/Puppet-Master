## Candidate Fixes / Design Directions
- Treat this seam as four linked contracts:
  - message action row
  - message info popover
  - context-detail editor tab
  - cost/context normalization for that tab
- Message action row:
  - hover/focus-revealed
  - left cluster = icon actions
  - right cluster = compact summary
  - compact row labels use normalized user-facing values:
    - `Ask`
    - `Agent`
    - `Plan`
    - `Deep Plan`
- Canonical message actions:
  - `Copy` = universal copy action on every message
  - `Edit` = restore most recent user message into composer for modification
  - `Resend` = replay the most recent user message and discard later generated history/work after that point
- Info popover exact curated field list:
  - `Mode`
  - `Provider`
  - `Model`
  - `Effort`
  - `Persona`
  - `Worker`
  - `Tokens`
  - `Context`
- Info popover label rules:
  - `Mode` uses normalized user-facing values: `Ask | Agent | Plan | Deep Plan`
  - `Worker` uses `Agent` or `Subagent`
  - `Tokens` shows compact total plus breakdown when expanded
  - `Context` shows used/limit and percent when known
  - assistant compact row shows duration/thinking time
  - user compact row shows timestamp
  - version and `current` / `frozen` do not appear in chat-facing copy
- Context circle interaction should now be split explicitly:
  - `hover`:
    - open a lightweight module
    - show `Usage`, `Tokens`, estimated `Cost`
    - bottom action: `More Details`
  - `click`:
    - surface `Compact Now`
    - `Compact Now` triggers compaction immediately
- Deep Plan canonical modeling:
  - `Deep Plan` should survive normalization as its own first-class mode/workflow identity
  - do not collapse it into plain `plan`
  - if shared lower-level planning mechanics need representation, put them in a subordinate behavior/profile field
- Context-detail editor-tab contract:
  - one context-detail tab per thread
  - stable tab key should be thread-scoped
  - clicking `More Details` focuses the existing tab if already open
  - tab live-updates as thread data changes
- Recommended context-detail information architecture:
  - top-level header summary
  - top-level view toggle:
    - `Curated`
    - `Raw`
- `Curated` view structure:
  - `Overview`
  - `Breakdown`
  - `Messages`
- `Overview` should show:
  - thread/session title
  - message counts
  - headline provider/model/mode/persona summary
  - effort / worker summary where relevant
  - headline tokens/context/cost metrics
- `Breakdown` should show:
  - context usage bar
  - token buckets
  - grouped breakdowns by role / tools / provider/model when available
- `Messages` should show:
  - one expandable row per message
  - compact row fields:
    - role
    - worker type
    - mode
    - model
    - time/duration
    - total tokens
    - cost
  - expanded message fields:
    - provider
    - model
    - effort
    - persona
    - token breakdown
    - context usage
    - cost
    - relevant requested/effective deltas only when material
    - notable tool/part summary
- `Raw` view should show:
  - accordion list of messages
  - full serialized payload per message when expanded
  - tool-part payloads
  - provider metadata blobs
  - path/runtime data needed for debugging
- Agent vs subagent visual treatment:
  - same base card family
  - subagent variant uses subtle alternate accent and/or border
  - optional distinct active animation while running
  - no dramatic layout fork
- Cost recommendation for this seam:
  - use the OpenCode-style formula as PM’s estimated-cost baseline
  - store both raw provider-reported buckets and normalized buckets
  - use provider-sensitive cache normalization heuristics initially
  - use model pricing tiers such as over-200k variants when available
  - label chat/detail cost as `Estimated Cost` unless PM has provider-authoritative cost semantics
  - raw/log views should preserve the normalization path and raw bucket values for audit/debugging
- Overall recommendation:
  - use OpenCode as behavior/information reference
  - do not copy its raw-JSON-first default presentation
  - do not copy its cost logic blindly without PM-specific disclosure and audit fields
- Compaction recommendation:
  - compaction should be directly available from the context circle click path
  - compaction should not require opening the detail pane
  - hover remains for lightweight status and navigation; click becomes the maintenance-action entrypoint
