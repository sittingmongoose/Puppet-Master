--- MEDIUM SEVERITY (5) ---

FIDELITY-01  severity: medium
  where: Plans/storage-plan.md — build lifecycle section (~line 404-405)
         Plans/Tools.md — performance targets (line 417)
  ledger obligation: Build threads use `thread-priority` crate at ThreadPriority::Min on
    all platforms, plus QOS_CLASS_UTILITY on macOS Apple Silicon via
    pthread_set_qos_class_self_np, to prevent editor starvation.
  current state: storage-plan.md says "one active build slot per project" and "supersede
    via CancellationToken" but never names the crate, the priority level, or the macOS
    QoS class. Build is described as "background" without priority contract.
  recovery: Add to storage-plan.md build-pipeline section: "Build threads use
    `thread-priority` crate (`ThreadPriority::Min` on all platforms; additionally
    `QOS_CLASS_UTILITY` on macOS Apple Silicon) to prevent editor starvation."
  sources: FID-B04, FID-D01

FIDELITY-02  severity: medium
  where: Plans/storage-plan.md — build lifecycle section
         Plans/Tools.md — no mention
  ledger obligation: Multi-project build resource model: per-project build slot, shared
    common thread pool across projects, FIFO queuing when pool is saturated.
  current state: "one active build slot per project" is stated but no shared thread pool
    or FIFO queuing policy for cross-project resource contention is documented anywhere.
  recovery: Add to storage-plan.md build lifecycle: "Projects share a common build thread
    pool. When the pool is saturated, pending builds queue FIFO."
  sources: FID-B03

FIDELITY-03  severity: medium
  where: Plans/storage-plan.md — binary file contracts subsection
  ledger obligation: All binary index files (file_map.bin, lookup.bin, postings.bin) use
    little-endian byte order with no inter-field padding.
  current state: storage-plan.md defines magic bytes, header fields, and field sizes but
    never specifies byte order or padding rules. An implementer could use big-endian or
    add alignment padding.
  recovery: Add one rule: "All binary index files use little-endian byte order with no
    inter-field padding."
  sources: FID-B01

FIDELITY-04  severity: medium
  where: Plans/GitHub_Integration.md §C.3 + Plans/storage-plan.md (security)
  ledger obligation: ALL inbound paths (from .gitmodules, dirty-staging notifications,
    remote file-change events, file watcher) must be canonicalized and validated with
    starts_with(project_root) or starts_with(cache_root) before filesystem use.
  current state: GitHub_Integration.md rejects ".." in submodule paths. FinalGUISpec.md
    mentions symlink canonicalization. But the GENERAL security rule covering dirty-staging
    and remote-watcher paths is never stated. A malicious remote path in a dirty
    notification could write outside cache_root.
  recovery: Add explicit security rule to GitHub_Integration.md §C.3 or storage-plan.md
    dirty-layer section: "All paths received from remote file-change notifications,
    dirty-staging writes, or file watcher events are canonicalized and validated with
    starts_with(project_root/cache_root) before filesystem use."
  sources: FID-C01, FID-D04

FIDELITY-05  severity: medium
  where: Plans/Tools.md — performance targets (line 417)
  ledger obligation: Peak RSS contribution typically <500 MB even for large repos.
    Only lookup table is mmap'd; postings are streamed.
  current state: Tools.md lists query latency, build times, incremental memory spike
    (1.5x), and SSD baseline. Steady-state RSS cap is absent. Without this, implementers
    have no memory budget for the mmap strategy.
  recovery: Add: "Steady-state memory: peak RSS contribution typically <500 MB (only
    lookup table is mmap'd; postings are streamed via offset). Incremental rebuilds
    spike to ~1.5x index size temporarily."
  sources: FID-C03
