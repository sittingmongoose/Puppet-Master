## 9. Persistence and storage

<a id="PERSISTENCE"></a>

Permission configuration has Everywhere, Computer, Project and Persona owner homes plus the ephemeral session layer. PS-144 defines sole writers, read-only mirrors, origin metadata and atomic revision admission; runtime effective config is a projection.

ContractRef: PolicyRule:Decision_Policy.md§2, ContractName:Plans/Personas.md#STORAGE-LAYOUT

| Layer | Location | Format | Lifetime |
|-------|----------|--------|----------|
| **Everywhere** | Settings-home writer; read-only `~/.config/puppet-master/permissions.toml` projection | Owner rule record / TOML compatibility | Until explicit edit/revoke |
| **Computer** | Owning Server/Execution Host app rule family, tagged Computer key | Owner rule record | Until explicit edit/revoke |
| **Project** | `<project_root>/.puppet-master/permissions.toml` | TOML | Until explicit edit/revoke |
| **Persona** | Existing library profiles at `~/.config/puppet-master/permission-profiles/<profile_id>.toml` and declared whole Project versions | Owner profile record / TOML | Until explicit edit/revoke |
| **Session** | In-memory approval cache under exact scope key | Runtime | Current run/session; cleared on restart |

Durable approvals use `cmd.permissions.create_project_rule`, `cmd.permissions.create_computer_rule` or the existing `cmd.permissions.create_global_rule` spelling normalized to Everywhere. The person selects the exact level/key and pattern; paths never go Everywhere. Persist rule_id, tool_pattern, action, scope_key, created_at, created_by_thread_id and issuer/origin/version/acceptance/revision metadata at the sole owner under CAS. rule_id remains the stable revoke/update key. rule_id is an RFC 9562 UUID in its lowercase hyphenated form (`^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$`): a create request carries a newly generated one or null, in which case the owner generates it (this applies to `cmd.permissions.create_project_rule` and the global spelling, whose request is `Plans/automation_authority_contracts.schema.json#/$defs/permission_rule_command_request_v2`); `cmd.permissions.create_computer_rule` is wired to `computer_rule_create_request` (the `computer_rule_request` shape), which has no `rule_id` field, so for a computer rule the owner always generates the rule_id and returns it in `computer_rule_create_result.rule_id`; the owner refuses a create whose rule_id already names a rule it holds, live or revoked; rule_id is never derived from tool_pattern, scope or level, never changes for the life of the rule, and is never reused after revoke or delete. The UUID form binds creates only: a rule created before it keeps its original rule_id (for example `rule-a`) as its stable key, the owner never rewrites that key to a UUID, and `cmd.permissions.update_rule`, `reorder_rule`, `delete_rule` and `revoke` accept any existing rule_id of 1 to 256 characters unchanged (`permission_rule_command_request_v2`; a `created` result always carries the UUID). User-config and simpler TOML views are projections, never second writers. PS-144 owns selected-rule/profile copy contributions and destination revalidation.

### 9.1 TOML format

Permission config files use the following TOML structure:

```toml
# Simple per-tool permissions
[tools]
read = "allow"
edit = "ask"
bash = "ask"
webfetch = "allow"

# Granular rules (object syntax)


[tools.bash]
"*" = "ask"
"git *" = "allow"
"npm *" = "allow"
"rm *" = "deny"

[tools.read]
"*" = "allow"
"*.env" = "deny"
"*.env.*" = "deny"
"*.env.example" = "allow"

# Special guards
[guards]
doom_loop = "ask"
external_directory = "ask"
external_publish_side_effect = "ask"

# External directory allowlist
[guards.external_directory]
allowlist = [
  "~/.cargo/**",
  "/usr/local/include/**",
]

# Doom loop threshold override
[guards.doom_loop]
threshold = 3
```

### 9.2 Config key in redb

The resolved permission set for the active session (merged from all layers) is also persisted to redb as part of `config:v1` under the key `tool_permissions` for compatibility with the existing config schema defined in `Plans/Tools.md` §10.1 (chapter `Implementation plan: permissions (spec for implementers)`, subsection `10.1 Config schema`; Tools.md numbers `## 10.` twice, so the heading name decides, per its Section 10 Numbering Supersession). The TOML files are the durable source of truth; the redb key is a projection.
