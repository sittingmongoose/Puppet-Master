L00002906	### W.2 Thread-to-worktree binding data model
L00002907	
L00002908	Thread-to-worktree binding is durable, explicit, and identity-bearing.
L00002909	
L00002910	**New redb key family:**
L00002911	- Key: `thread_state:{thread_id}:worktree_binding`
L00002912	- Value (JSON):
L00002913	```json
L00002914	{
L00002915	  "worktree_id": "wt-abc123",
L00002916	  "branch_name": "assistant/fix-auth-bug",
L00002917	  "worktree_path": ".puppet-master/worktrees/thread-a1b2c3d4",
L00002918	  "bound_at_utc": "2026-03-26T02:45:00Z",
L00002919	  "binding_origin": "manual | auto_create",
L00002920	  "temp_branch_name": "assistant/thread-a1b2c3d4"
L00002921	}
L00002922	```
L00002923	`temp_branch_name` tracks the original temporary branch name assigned before title generation. For UI display, always use `branch_name`; `temp_branch_name` is internal bookkeeping only. Assistant thread worktree filesystem paths are generated as `.puppet-master/worktrees/thread-{short_id}` from the bound thread id and append numeric suffixes such as `thread-{short_id}-2` when that directory already exists; `worktree_id` remains the stable record identity and MUST NOT make `wt-*` the filesystem path model.
L00002924	
L00002925	**Inverse lookup (for 1:1 enforcement):**
L00002926	- Key: `worktree_binding_reverse:{worktree_id}`
L00002927	- Value: `thread_id`
L00002928	- Used to quickly check whether a worktree is already bound to another thread.
L00002929	
L00002930	**Binding rebuild logic:** Projectors replay `chat.thread_worktree_bound` and `chat.thread_worktree_unbound` events in sequence order to reconstruct current binding state. The last event for a given `thread_id` determines whether a binding exists and which `worktree_id` it references.
L00002931	
L00002932	**Worktree record extension (existing `worktree_record.v1`):**
L00002933	- Add optional field: `owner_thread_id?` alongside existing `owner_run_id?` and `owner_node_id?`.
L00002934	- Owner semantics: exactly one of `owner_thread_id`, `owner_run_id/owner_node_id`, or neither (manual) is set.
L00002935	
L00002936	**Startup revalidation:** After PM startup rehydrates thread state from redb/seglog, the next focus of a thread with `thread_state:{thread_id}:worktree_binding` lazily verifies that the recorded path exists and appears in `git worktree list`. If the path is missing, PM auto-unbinds by deleting the binding and reverse lookup, emits `chat.thread_worktree_unbound` with `reason=path_missing`, and notifies the user; it does not silently re-create the missing worktree.
L00002937	
L00002938	**Worktree-aware same-file identity rules:**
L00002939	- The canonical file identity for thread-bound chat, debug, Source Control, and GitHub pivots is `{ repo_id, worktree_id, relative_path }`; path alone is not sufficient.
L00002940	- The same relative path in two worktrees is treated as two different open subjects unless a compare session explicitly binds them together.
L00002941	- Thread-scoped opens default to the thread's bound `worktree_id`. If the thread has no bound worktree, the UI may fall back to the currently selected worktree but must label that fallback explicitly.
L00002942	- Historical cards, receipts, and debug evidence remain pinned to the captured `worktree_id` even if the thread later rebinds to a different worktree.
L00002943	- Merge-back, compare, and PR creation flows may intentionally bridge the bound worktree to a base branch, but they must preserve both identities rather than collapsing them into one generic path.
L00002944	- At turn-start, Chat populates and freezes `execution_unit_context.worktree_id` plus `working_directory` for the whole turn; safe points include worktree snapshot fields `worktree_id`, `worktree_path`, `branch_name`, and `HEAD_sha`.
L00002945	- Project switch marks the worktree binding inactive rather than unbound; the button stays disabled until switch-back, then reactivates against the same binding.
L00002946	
L00002947	**1:1 enforcement:** One worktree per thread, one thread per worktree. If a user tries to bind a worktree already bound to another thread, the action is blocked with an explicit error and a deep link to the owning thread when available.
L00002948	
L00002949	**Mode-worktree invariant:** Worktree binding is thread-level state, orthogonal to Ask, Agent, Debug, Plan, and Deep Plan mode. Mode transitions never rebind, unbind, or change the frozen `working_directory` for an in-flight turn; the next turn observes the same bound worktree unless the user explicitly changes the binding.

L00003144	#### W.8.3 Merge execution
L00003145	
L00003146	**Critical:** Merge executes in the main repo working tree, NOT inside the worktree. This is consistent with WorktreeGitImprovement.md `merge_worktree()` operating from the main repo context: the worktree branch is merged INTO the target branch in the main repo. Exception: Rebase is a two-phase operation: step 1 (`git rebase` / `git rebase {target}`) runs in the worktree, and step 3 (`git merge --ff-only`) runs in the main repo.
L00003147	
L00003148	ContractRef: ContractName:Plans/WorktreeGitImprovement.md, ContractName:Plans/Contracts_V0.md
L00003149	
L00003150	**Exclusive merge lock:** `.git/pm-merge.lock` (main repo). Acquired BEFORE guard checks for atomicity. Guards fail → lock released immediately. Lock held → ALL merge buttons project-wide disabled.
L00003151	
L00003152	Worktree command when-clause conditions are UI pre-checks only; Merge uses a two-phase check in which `.git/pm-merge.lock` is acquired first, then dirty/conflict/active-run/detached-HEAD guards are re-checked atomically before mutation.
L00003153	
L00003154	The lock lives under the main repo `.git/` directory; acquiring `.git/pm-merge.lock` is the FIRST merge-execution step and makes the guard-check plus execution atomic.
L00003155	
L00003156	This guard-to-lock atomicity includes the detached HEAD guard: after the lock is held, PM re-reads the worktree HEAD state before merge, rebase, PR, or pre-merge test mutation proceeds.
L00003157	
L00003158	The UI pre-check `/disabling` state is advisory only: all pre-checks are re-checked atomically AFTER lock acquisition. For Rebase, the lock covers the ENTIRE sequence from worktree rebase through tests to main repo ff-merge.
L00003159	
L00003160	**Lock file format:** `{ "pid": <int>, "started_utc": "<ISO8601>", "worktree_id": "<string>", "strategy": "<string>" }`
L00003161	
L00003162	**Stale lock recovery:** On startup (lazy), if PID dead or lock older than 5 minutes → auto-remove. The stale lock is auto-removed before new merge execution proceeds. Toast: "Stale merge lock cleaned up."
L00003163	
L00003164	**Execution steps (when pre-merge test disabled):**
L00003165	- **Squash:** `git checkout {target}` → `git merge --squash {branch}` → `git commit -m "{message}"`
L00003166	- **Merge:** `git checkout {target}` → `git merge --no-ff {branch} -m "{message}"`
L00003167	- **Rebase:** (in worktree) `git rebase {target}` → (in main repo) `git checkout {target}` → `git merge --ff-only {branch}`
L00003168	
L00003169	Canonical command templates may use `{worktree_branch}` for the same source branch: `git merge --squash {worktree_branch}`, `git merge --no-ff {worktree_branch} -m "{message}"`, and `git merge --ff-only {worktree_branch}`.
L00003170	
L00003171	**Auto-fetch:** Before any merge strategy, the backend runs `git fetch origin {target_branch}` in the main repo so the local target is up-to-date. If fetch fails because there is no remote or the user is offline, merge proceeds with local state and shows an advisory toast.
L00003172	
L00003173	**Rebase is non-interactive only.** The dialog runs plain `git rebase` / `git rebase {target}`; interactive `git rebase -i`, `-i`, pick/squash/fixup, and `/squash/fixup` workflows are terminal-only.
L00003174	
L00003175	**Commit authorship:** User's git identity (`user.name`/`user.email`). No AI co-author injection.
L00003176	
L00003177	**Git hooks:** NOT bypassed. Hook failure = merge failure with Retry/Cancel. Standard commit hooks run at their normal Git trigger points during the merge/commit step after any pre-merge test passes; `pre-merge-commit` runs during `git merge --no-ff` commit and gets the same treatment as pre-commit failure. For `prepare-commit-msg`, PM's provided commit message is the initial value; hooks may append/modify it before the commit is finalized. If hooks modify files, for example auto-formatting in a pre-commit hook, the test gate tests the PRE-hook state; hooks run after test pass as part of the commit pipeline, not the test pipeline.
