L00001831	### End-of-phase / end-of-task / end-of-subtask verification
L00001832	
L00001833	When the orchestrator **completes** a Phase, Task, or Subtask (e.g. all iterations or sub-items done, acceptance criteria about to be checked), run:
L00001834	
L00001835	1. **Wiring check again (did we wire what we built?):** Re-run the same wiring/readiness questions as at start, but in "completion" context: for the work just done at this tier, are all new or touched config/settings properly wired (GUI ↔ backend ↔ execution)? This catches cases where work during the tier introduced a new setting or UI that was not yet connected.
L00001836	2. **Acceptance criteria (existing):** Run the existing verification gate (e.g. criteria from PRD, command/file/regex checks). This remains the "did we meet the spec?" check.
L00001837	3. **Quality verification (new):** Beyond acceptance criteria, **review the code (or artifacts) produced at this tier** to ensure the work was done well -- not just "does it pass the gate?" but "is it maintainable, correct, and aligned with project standards?" Both of the following are **required** (no human review; agent-driven only):
L00001838	   - **Structured code review by reviewer subagent (required, not optional):** Run a dedicated reviewer subagent (e.g. `code-reviewer`) at end-of-phase/task/subtask. It inspects the diff or artifacts and outputs pass/fail + feedback. There is no path that skips this. Do **not** use human review.
L00001839	   - **Quality criteria in the gate (required as well):** Extend the verification gate for this tier to include automated quality items (e.g. "no new clippy warnings," "new code has tests," "no TODOs without tickets").
L00001840	4. **Document packaging verification (new):** End-of-run verification MUST enforce `Plans/Document_Packaging_Policy.md` for any Markdown/text artifact under `.puppet-master/**` produced during the run that reached packaging triggers.
L00001841	
L00001842	ContractRef: ContractName:Plans/Document_Packaging_Policy.md, Gate:GATE-014

L00001844	**Quality Gate: Fail vs Warn Rules (Resolved):**
L00001845	
L00001846	| Check | Severity | Action |
L00001847	|-------|----------|--------|
L00001848	| Linter errors (error-level) | Critical | **Fail** — block tier completion |
L00001849	| Linter warnings (warn-level) | Advisory | **Warn** — log, do not block |
L00001850	| Formatter violations | Advisory | **Warn** — log, do not block |
L00001851	| Test failures | Critical | **Fail** — block tier completion |
L00001852	| Test coverage delta < 0% | Advisory | **Warn** — log, do not block |
L00001853	| Build errors | Critical | **Fail** — block tier completion |
L00001854	| Type check errors | Critical | **Fail** — block tier completion |

L00001857	Config: `quality.gate.{check_name}.action` — override per check (`"fail"` or `"warn"`).

L00001859	**BeforeTierEnd verification responsibilities:**
L00001860	
L00001861	- **Collect tier artifacts:** Collect all artifacts produced during this tier (code changes, documents, test results, etc.)
L00001862	- **Compute diff:** Compute git diff for changed files in this tier (if applicable)
L00001863	- **Load tier context:** Load tier context and execution history for this tier
L00001864	- **Prepare verification context:** Build verification context with artifacts, diff, tier context, and config
L00001865	
L00001866	**DuringTierEnd verification responsibilities:**
L00001867	
L00001868	- **Re-run wiring check:** Re-run wiring/readiness check for completed tier (check if new config/settings were introduced and are properly wired)
L00001869	- **Run acceptance criteria:** Run existing verification gate (PRD criteria, command/file/regex checks)
L00001870	- **Run quality verification:**
L00001871	  - **Code review by reviewer subagent:** Invoke reviewer subagent (e.g., `code-reviewer`) to review diff/artifacts
L00001872	  - **Quality gate criteria:** Run automated quality checks (linters, formatters, test coverage, security scanners)
L00001873	- **Run Document Set verification:** For large Markdown/text artifacts produced in the run, execute full Document Set audit checks (A/B/C) and fail tier completion on any packaging verification breach.
L00001874	- **Collect verification results:** Collect all verification results (wiring, acceptance, quality)
L00001875	- **Determine tier status:** Determine if tier should be marked "complete", "incomplete" (rework), or "complete with warnings"
L00001876	
L00001877	**AfterTierEnd verification responsibilities:**
L00001878	
L00001879	- **Persist verification results:** Append the verification result to the canonical runtime verification/receipt event family and project it into redb-backed verification read models. The legacy `.puppet-master/state/verification-{node_id}-end.json` path is retired source-lineage and may exist only as an explicit debug/export mirror generated from canonical storage.
L00001880	- **Update tier status:** Update tier status in PRD/state based on verification results
L00001881	- **Generate feedback:** If verification failed, generate feedback for agent/user (what failed, which file/criterion, suggested fix)
L00001882	- **Handle failures:** If quality fails, either mark tier as "incomplete" (rework) or "complete with warnings" (log and proceed) per policy

L00002446	### 2. Structured Handoff Report Validation
L00002447	
L00002448	**Concept:** Enforce a standardized output format for subagent invocations. Every subagent must produce a structured handoff report with required fields. If output is malformed, block and request one retry (fail-safe after retry).
L00002449	
L00002450	**BeforeHandoffValidation responsibilities:**
L00002451	
L00002452	- **Detect output format:** Detect if subagent output is structured (JSON) or unstructured (text)
L00002453	- **Load validation schema:** Load validation schema for `SubagentOutput` format
L00002454	- **Prepare validation context:** Build validation context with expected fields and format requirements
L00002455	
L00002456	**DuringHandoffValidation responsibilities:**
L00002457	
L00002458	- **Parse structured output:** Attempt to parse output as structured `SubagentOutput` JSON
L00002459	- **Validate required fields:** Validate that all required fields are present (`task_report` is required)
L00002460	- **Validate field types:** Validate that field types match schema (string, array, enum, etc.)
L00002461	- **Validate findings format:** Validate that findings array contains valid `Finding` objects with required fields
L00002462	- **Extract from text (fallback):** If JSON parsing fails, attempt to extract structured data from text output
L00002463	- **Request retry if malformed:** If output is malformed and retry not yet attempted, request one retry with format instruction
L00002464	
L00002465	**AfterHandoffValidation responsibilities:**
L00002466	
L00002467	- **Persist validation results:** Append the handoff-validation result to the canonical runtime verification/receipt event family and project it into redb-backed handoff validation read models. The legacy `.puppet-master/state/handoff-validation-{node_id}.json` path is retired source-lineage and may exist only as an explicit debug/export mirror generated from canonical storage.
L00002468	- **Update tier context:** Update tier context with validated `SubagentOutput` (task_report, downstream_context, findings)
L00002469	- **Handle validation failures:** If validation fails after retry, proceed with partial output but mark tier as "complete with warnings"

L00003219	### 4. Cross-Run Knowledge Continuity
L00003220	
L00003221	**Concept:** Persist architectural decisions, established patterns, tech choices, and lessons learned across runs through canonical runtime storage, planning artifacts, and handoff bundles. When a new run starts, load prior context from those canonical sources to maintain continuity.
L00003222	
L00003223	**What to persist:**
L00003224	
L00003225	- **Architectural decisions:** Tech stack choices, design patterns, framework selections.
L00003226	- **Established patterns:** Code organization, naming conventions, testing strategies.
L00003227	- **Tech choices:** Dependency versions, tool configurations, environment setup.
L00003228	- **Pitfalls encountered:** Known issues, workarounds, anti-patterns to avoid.
L00003229	
L00003230	**Canonical storage posture:**
L00003231	
L00003232	- orchestration continuity is derived from seglog/redb-backed runtime state, stored plan outputs, and normalized handoff bundles.
L00003233	- `.puppet-master/memory/*` is not the canonical continuity source for orchestrator child runs.
L00003234	- continuity records should be queryable and attributable without requiring a memory-manager sidecar file hierarchy.
L00003235	
L00003236	**When to persist:** At phase completion, especially after planning/architecture work, extract durable decisions and patterns from canonical outputs and store them through the same runtime/project persistence path used for other orchestrator artifacts.
L00003237	
L00003238	**When to load:** At run start, before Phase 1 begins, assemble continuity context from canonical persisted decisions, stored outputs, and handoff projections. The same continuity inputs may inform child selection (for example, a prior Rust decision may bias toward a Rust-focused child Persona), but they do not create subagent-specific durable memory.
L00003239	
L00003240	**Platform-specific implementation:** Platform-agnostic. All platforms benefit from canonical continuity inputs injected into prompts, but the continuity source remains runtime storage and structured artifacts rather than memory files.

L00003304	### 8. Structured Handoff Contract Enforcement at Runtime
L00003305	
L00003306	**Concept:** Enforce the structured handoff format (Task Report + Downstream Context + Findings) at runtime via AfterTier hook validation, not just in prompts. This ensures reliability even if prompts are modified.
L00003307	
L00003308	**Enforcement:**
L00003309	
L00003310	- **AfterTier hook:** Calls `validate_subagent_output()` (see #2 above).
L00003311	- **On validation failure:** Block response, request one retry with format instruction.
L00003312	- **After retry:** If still malformed, proceed with partial output (fail-safe) but mark tier as "complete with warnings."
L00003313	
L00003314	**Documentation:** Document the contract in AGENTS.md and in subagent prompt templates. State that subagents **must** produce structured output; runtime validation enforces it.
L00003315	
L00003316	**Platform-specific implementation:**
L00003317	
L00003318	- **Cursor/Codex/Claude/Gemini:** Parse JSON output; validate required fields (`task_report`, `downstream_context`, `findings`).
L00003319	- **Copilot:** Parse text output; extract structured sections via regex or pattern matching; validate presence.
L00003320	
L00003321	Provider capability rule: provider-doc findings are capability evidence, not a blanket bypass for local validation. For schema-critical handoffs, provider-native schema enforcement is preferred where available: Anthropic provider-doc guidance directs schema-critical workflows to **Structured Outputs** for guaranteed JSON schema conformance, and Gemini provider-doc guidance supports schema-bound structured output and SDK schema helpers. Across providers and `/transports`, PM still runs local validation and records downgrade behavior because transport support and adherence vary; unsupported or weak transports fall back to locally validated structured output or partial-output warnings.
L00003322	
L00003323	**Integration with existing plan:** This complements the existing "required reviewer subagent" requirement. The reviewer must produce structured output; runtime validation ensures it.

L00003764	
L00003765	When multiple agents/subagents run concurrently (parallel subtasks, different tiers, or same tier with multiple subagents), they need **coordination** to avoid conflicts, understand what others are working on, and not "freak out" when code changes around them.

L00003771	#### Canonical active-agent coordination records and projections
L00003772	
L00003773	Canonical durable coordination truth is the `EventRecord` stream plus redb projections owned by `Plans/storage-plan.md` and registered in `Plans/Contracts_V0.md`. `AgentCoordinator` is an append/projection consumer, not a JSON file store.
L00003774	
L00003775	Canonical seglog record families:
L00003776	- `coordination.agent_registered` records agent registration before execution.
L00003777	- `coordination.agent_status_updated` records lifecycle/status changes such as queued, running, awaiting_parent, blocked, complete, failed, or cancelled.
L00003778	- `coordination.agent_operation_updated` records the current operation summary, progress note, and operation refs.
L00003779	- `coordination.agent_file_ownership_updated` records file activity claims for coordination warnings; it is not a FileSafe lock or durable exclusive lease.
L00003780	- `coordination.agent_unregistered` records normal completion or explicit unregister.
L00003781	- `coordination.agent_crashed` records crash/heartbeat expiry resolution.
L00003782	- `coordination.agent_aborted` records parent/user/runtime abort resolution.
L00003783	- `coordination.debug_mirror_exported` records optional mirror export attempts and outcomes.
L00003784	
L00003785	Canonical redb projections:
L00003786	- `coordination_agent_projection.v1:{project_id}:{agent_id}` for the latest agent lifecycle, status, runtime/platform identity, worktree binding, operation ref, and last applied coordination sequence.
L00003787	- `coordination_file_projection.v1:{project_id}:{path_hash}:{agent_id}` for current file-activity claims and conflict-warning inputs.
L00003788	- `coordination_operation_projection.v1:{project_id}:{agent_id}:{operation_id}` for operation progress, current operation text, and related source refs.
L00003789	- `coordination_snapshot_projection.v1:{project_id}:{projection_scope}` for the prompt-injection/read-model snapshot consumed by schedulers and agents.
L00003790	- `projector.checkpoint.coordination:{project_id}` for the projector checkpoint that proves which seglog range the read model has consumed.
L00003791	
L00003792	Concurrency and atomicity rules:
L00003793	- Up to 32 active agents across multiple worktrees update coordination by calling the PM-owned coordination append API; they do not read-modify-write canonical state files.
L00003794	- A coordination mutation is admitted only as one append/CAS boundary: the writer checks the current `agent_revision` or `last_applied_event_id`, appends one EventRecord with an idempotency key, and the projector advances the redb projection plus checkpoint in one redb transaction.
L00003795	- Lost updates are prevented by CAS on `agent_revision`/`last_applied_event_id`. A stale update returns a coordination conflict diagnostic; the caller reloads the projection and emits a new event instead of overwriting the old projection.
L00003796	- Canonical scheduling, conflict prevention, prompt injection, and execution decisions read only the redb projections whose checkpoint covers the required seglog sequence. They never read `active-agents.json`, `agent-messages.json`, verification JSON, or handoff JSON as authority.
L00003797	- Mirror writers run after canonical projection commits. If a mirror write fails, lags, or is corrupt, PM emits diagnostics and regenerates the mirror from seglog/redb; canonical scheduling and execution continue from projections only.
