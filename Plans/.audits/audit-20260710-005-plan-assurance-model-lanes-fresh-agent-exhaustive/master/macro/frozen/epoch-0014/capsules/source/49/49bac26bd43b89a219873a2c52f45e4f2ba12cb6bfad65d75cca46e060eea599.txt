L00001553	### 2.5 Analytics scan jobs
L00001554	
L00001555	**Trigger:** Periodic (e.g. every 5 minutes) or on-demand (e.g. when Usage view is opened). Can run in a background task or a separate thread; must not block the main UI. On-demand refresh should leave the previously written rollups visible until the new scan completes.
L00001556	
L00001557	**Scan range:** Last N hours (e.g. at least 7d for `tool_usage.7d`) or since last scan checkpoint. Read from seglog (or JSONL mirror) in order; filter by event type (`usage.event`, `run.completed`, `tool.invoked`). Canonical tool-usage windows for MVP are `5h`, `24h`, and `7d`; `1h` remains optional.
L00001558	
L00001559	**Compute:** For 5h/7d: aggregate `usage.event` by platform, sum tokens (or request count) in sliding 5h and 7d windows. For tool latency: collect `tool.invoked` latencies, compute percentiles (p50, p95). For error rates: count run failures / total runs in window. For **tool usage** (Usage tool widget, Plans/Tools.md §8.4): aggregate `tool.invoked` by `tool_name` over the window -- count, p50/p95 ms, error_count (count only events where `success = false`). `tool.denied` events and FileSafe blocks do **not** contribute to `tool_usage.{window}` because the widget reflects executed calls only.
L00001560	
L00001561	**Write:** Store results in redb under `rollups` namespace (e.g. `usage_5h.{platform}`, `usage_7d.{platform}`, `tool_latency.{window}`, **`tool_usage.{window}`**, `tool_usage_meta.{window}`). Usage view and tool usage widget read from these keys; no direct seglog read for dashboard.
L00001562	
L00001563	**Checkpoint:** Store "last scanned up to seq X" or "last scanned timestamp" in redb so the next run doesn't rescan from the beginning. Idempotent: recomputing the same window and writing the same keys is safe.

L00001835	## 5. Gaps and how we address them
L00001836	
L00001837	
L00001838	The remaining persistence gaps for the rewrite shell are addressed by explicit owner-aligned state instead of feature-local ad hoc blobs.
L00001839	
L00001840	### 5.1 Unsaved editor recovery is required, not optional
L00001841	
L00001842	Unsaved editor recovery is a live shared-buffer storage contract, not implementation-order housekeeping. The `/checklist` may track delivery work, but it must not downgrade recover-unsaved to `/later`: recovery begins when the first dirty buffer state is captured, `/ends` only after save, discard, or explicit recovery resolution, and multi-view `/editor` surfaces share the same recovery record, `/restore` target, and `/redo` lineage rather than creating per-view recovery branches.
L00001843	
L00001844	
L00001845	Rules:
L00001846	- recover-unsaved is required MVP behavior for local and remote-backed buffers
L00001847	- recovery snapshots store local buffer state, capture metadata, host/path identity, and write availability at capture time
L00001848	- remote-backed recovery banners must say `Recovered local edits — remote destination not yet synchronized`
L00001849	- save success is only claimed after the effective destination confirms the write
L00001850	
L00001851	Implementation spec:
L00001852	- key: `editor_state.v1:{project_id}:{file_path_hash}`
L00001853	- stores: cursor position, scroll offset, selection ranges, undo stack reference, and unsaved changes flag
L00001854	- recovery trigger: on session restore, reload each open editor's state before restoring focus
L00001855	- conflict handling: if the file changed on disk since the last save, show a diff and let the user choose how to resolve the mismatch
L00001856	
L00001857	ContractRef: ContractName:Plans/FileManager.md, ContractName:Plans/GitHub_Integration.md, ContractName:Plans/FinalGUISpec.md

L00001861

L00001864	Required stored distinctions:
L00001865	- requested vs effective browser runtime/capabilities
L00001866	- requested vs effective LSP enablement and attached-server set
L00001867	- freshness vs health vs write availability for remote-backed projections
L00001868	- restore outcome for historical Search, LSP, browser, and editor recovery surfaces
L00001869	
L00001870	Implementation spec:
L00001871	- key patterns: `{resource_type}_requested.v1:{scope}:{id}` and `{resource_type}_effective.v1:{scope}:{id}`
L00001872	- requested state is what the user or system asked for; effective state is what actually applies after resolution

L00001906	### 5.4 Host-aware LSP persistence and restart behavior
L00001907	Rules:
L00001908	- LSP lifecycle and restart budgets are persisted by host-aware session key
L00001909	- restart/reconnect preserves enough state to disclose whether a projection is current, refreshing, stale, degraded, or unavailable
L00001910	- remote-mode projects never restore into a silent local fallback path
L00001911	- On crash, `/transport` loss, or `/sync-loss` restart, PM recreates the host-aware LSP session and replays all currently attached documents for that session/root in deterministic URI order.
L00001912	- Automatic restart uses the persisted restart budget and backoff state; after the bounded crash budget is exhausted, the session remains `Degraded` until user retry, and a user-initiated restart resets the budget/backoff counters.
L00001913	- Each host-aware LSP session keeps a bounded protocol/state trace buffer for operational/debug inspection only, not canonical app history; the surfaced trace fields include session key, root, current state, last error, restart attempt/backoff, and a recent protocol trace reveal action.
L00001914	
L00001915	Implementation spec:
L00001916	- key: `lsp_server_state.v1:{host_id}:{server_id}:{root_hash}`
L00001917	- stores: server config, capabilities snapshot, last known status, and restart count
L00001918	- recovery path: on session restore, restart LSP servers using the persisted config
L00001919	- persisted restart counts survive reconnects so budget enforcement and degraded-state disclosure remain stable after restart

L00001923	## 6. Potential problems and solutions
L00001924	
L00001925	| Problem | Solution |
L00001926	|---------|----------|
L00001927	| **seglog corruption or partial write** | Append-only with flush and last-complete-record recovery. CRC32 per record is mandatory; validate on every read; corrupt record -> skip + recovery event. |
L00001928	| **redb corruption** | Restore from backup or rebuild projections from canonical seglog. |
L00001929	| **Projector falls behind** | Buffer events in bounded batches and checkpoint only after a successful commit. |
L00001930	| **Analytics scan blocks UI** | Run analytics scans in the background; UI shows last committed rollup plus freshness state. |
L00001931	| **Disk full / storage I/O** | Surface a user-facing error, stop unsafe writes, and retry only per storage I/O policy. |
L00001932	| **Migration failure** | Leave previous version intact; do not open a half-migrated store. |
L00001933	| **Multiple app instances** | Acquire exclusive flock on the active durable-store `lock-path` / `pm.lock` derived from the selected logical storage root or safe-local fallback before any writes. If the lock is held, enter `/read-only` viewer mode and notify the user. |
L00001934	
L00001935	ContractRef: ContractName:Plans/Architecture_Invariants.md, ContractName:Plans/Executor_Protocol.md, ContractName:Plans/storage-plan.md
L00001936	
L00001937	| Problem | Solution |
L00001938	|---------|----------|
L00001939	| **Checkpoint lost** | Rebuild from seglog / last retained segment. |
L00001940	| **API contract (caller handling errors)** | `append()` / redb write operations return structured `Result`; no silent swallow. |
L00001941	| **Projector panic or crash** | Do not advance checkpoint; restart from last good checkpoint. |
L00001942	| **File record LRU eviction** | Cap in-memory file records at 10,000 entries and rebuild lazily on access. |
L00001943	| **Boot-time janitor** | After active durable-store lock acquisition, sweep stale `.tmp.*` artifacts, validate lock freshness, and emit a `storage.boot_recovery` event if cleanup was required. |
L00001944	| **DB / redb shutdown hygiene** | Close the DB handle in the shutdown sequence before process exit. |
L00001945	
L00001946	ContractRef: ContractName:Plans/Architecture_Invariants.md, ContractName:Plans/Executor_Protocol.md, ContractName:Plans/FileSafe.md

L00001962	### 8.1 Phased implementation order
L00001963	
L00001964	- **Phase 1 -- seglog foundation**
L00001965	  Build first: app data root resolution, directory creation (`storage/seglog`, `storage/redb`, `storage/jsonl`, `storage/tantivy`), and seglog writer only (envelope format, seq, flush, optional rotation by size/day). No projectors, no redb.
L00001966	  **Exit criterion:** We can append events and read them back (by tailing or reading the segment file).
L00001967	
L00001968	- **Phase 2 -- redb and schema**
L00001969	  Build: redb open under app data root, schema (namespaces/tables per §2.3: settings, sessions, runs, checkpoints, editor, rollups, review_rules), key patterns, and a migrations runner (version in meta, run migrations on open).
L00001970	  **Exit criterion:** We can read/write settings and checkpoints (e.g. put/get in `settings` and `checkpoints` namespaces).
L00001971	
L00001972	- **Phase 3 -- projector: seglog → JSONL mirror**
L00001973	  Build: single projector that tails seglog from a checkpoint, appends to the JSONL mirror (same envelope format), and persists its checkpoint in redb (`checkpoints` namespace).
L00001974	  **Exit criterion:** Tail seglog, write mirror, resume from checkpoint after restart (no duplicate mirror lines, checkpoint advances).
L00001975	
L00001976	- **Phase 4 -- projector: seglog → Tantivy (chat index)**
L00001977	  Build: projector (or second projector) that reads seglog from checkpoint, indexes `chat.message` (and optionally `chat.thread_created`) into a Tantivy chat index (fields: thread_id, content, role, ts, message_id), and persists its checkpoint in redb.
L00001978	  **Exit criterion:** Events are indexed and search returns results (e.g. by content or thread_id).
L00001979	
L00001980	- **Phase 5 -- analytics scan and rollups**
L00001981	  Build: analytics scan job (periodic or on-demand) that scans seglog (or JSONL mirror) over a time range, computes 5h/7d usage rollups, tool latency, and tool_usage (per-tool count, p50/p95, error_count per Plans/Tools.md §8.4), writes to redb `rollups` namespace, and stores a scan checkpoint.
L00001982	  **Exit criterion:** 5h/7d and tool rollups are written to redb and the UI (or a test reader) can read them.
L00001983	
L00001984	- **Phase 6 -- wire chat, editor, and Usage**
L00001985	  Build: wire chat persistence (thread list and thread content to seglog; read from redb + seglog/snapshots per assistant-chat-design), editor state to redb `editor` namespace (FileManager.md §2.9), Usage/dashboard reading rollups from redb and triggering analytics scan (usage-feature.md); emit `usage.event` with `thread_id` and `run.completed` with optional usage snapshot.
L00001986	  **Exit criterion:** Full flow works: create thread, send message, events in seglog; projectors update mirror and index; Usage view shows rollups; editor state persists.
L00001987	
L00001988	**Dependencies:** seglog writer before any projector; redb open + schema + migrations (including `checkpoints` and `rollups` namespaces) before projectors and analytics scan; projectors must not start until redb is open and checkpoints namespace exists; analytics scan must not run until rollups namespace (and scan checkpoint key) exists. Projectors may start once the seglog writer is initialized (current segment may be empty). When checkpoint is missing and seglog is empty, projector starts from position 0 and has nothing to process; when checkpoint is missing and seglog has data, projector starts from the beginning of the first segment.

L00002000	### 8.3 Startup and shutdown
L00002001	
L00002002	**Startup order:**
L00002003	1. Resolve the app data root (environment override optional).
L00002004	2. Probe the selected storage root for durable-store safety, including `unsafe-filesystem` / NFS posture, and establish any required safe local fallback before durable stores are opened.
L00002005	3. Derive the active durable-store root and its `lock-path`, then acquire exclusive `pm.lock` ownership before any writer opens durable state. If the lock is already held, PM enters `/read-only` viewer mode and stops before writer startup.
L00002006	4. Create `storage/seglog`, `storage/redb`, `storage/jsonl`, `storage/tantivy` if missing.
L00002007	5. Open redb and run migrations.
L00002008	6. Open the seglog writer.
L00002009	7. Start projectors that tail seglog and write JSONL/Tantivy/checkpoints.
L00002010	8. Start optional analytics schedulers and per-project index services.
L00002011	
L00002012	If durable-store fallback is active, PM routes lock files, durable DB state, and session snapshot metadata to the safe local fallback while preserving the selected logical storage root for lineage and user-visible diagnostics.
L00002013	
L00002014	ContractRef: ContractName:Plans/FileSafe.md, ContractName:Plans/Executor_Protocol.md, ContractName:Plans/Architecture_Invariants.md
L00002015	
L00002016	**Regex-index startup recovery:** After a project context is known and before the first indexed `grep` or Search-panel regex query for that project:
L00002017	1. Scan the relevant `regex_index/` directory.
L00002018	2. Pick the highest valid `gen-{N}/` candidate.
L00002019	3. Validate `index_meta.json`, per-file xxh3 checksums, and `lookup.bin` sizing / offsets before mmap.
L00002020	4. For Git-backed caches, verify `anchor_sha` is still reachable (`git cat-file -t {anchor_sha}`). Unreachable anchors invalidate the snapshot and trigger rebuild from current HEAD.
L00002021	5. If a valid snapshot exists, create `IndexSnapshot`, mmap `lookup.bin`, and mark the project `ready`.
L00002022	6. If no valid snapshot exists, mark the project `no_index` and transparently serve raw ripgrep until the background full build completes.
L00002023	7. On checksum or metadata mismatch, delete the corrupt generation directory and trigger a full rebuild; fall back to raw ripgrep until the rebuilt snapshot is ready. Delete orphaned or partial generations opportunistically during this recovery path.

L00002028	1. Signal projectors to stop and flush outputs.
L00002029	2. Cancel in-flight regex builds and wait briefly for partial-generation cleanup.
L00002030	3. Flush and close the seglog writer.
L00002031	4. Close redb.
L00002032	5. Release the active durable-store lock after the final writer flush completes.
L00002033	6. Leave the last valid regex snapshot and any reusable remote cache state in place; ordinary shutdown does not evict caches.

L00002043	### 8.4 First run / empty state
L00002044	
L00002045	
L00002046	- **Dirs:** If app data root exists but `storage/*` dirs are missing, create them (§2.1).
L00002047	- **Seglog:** If `storage/seglog/` is empty, writer creates the first segment on first append; projectors reading checkpoint "none" start from offset 0 and see no events until the first append.
L00002048	- **redb:** On first open, if no `schema_version` (or missing `meta` namespace), run initial migration that creates all namespaces and sets `schema_version` to 1. redb is created on first open if the file does not exist (standard redb behavior).
L00002049	- **Projectors:** When checkpoint is missing, treat as "start from beginning of seglog" (first segment, offset 0); when seglog is empty, no work.
L00002050	**Analytics Scan When Checkpoint Missing (Resolved):**
L00002051	
L00002052	When the analytics scan checkpoint is missing (first run or after reset):
L00002053	- Scan from **seq 0** (beginning of seglog).
L00002054	- Rationale: ensures no data is missed. The seglog is append-only, so a full scan is safe and idempotent.
L00002055	- For large seglogs, the scan is paginated: process **1000 events per batch**, yielding between batches to avoid blocking the event loop.
L00002056	- After the scan completes, write the checkpoint to redb (`analytics:scan_checkpoint` → last processed seq).
L00002057	- Subsequent runs resume from the checkpoint.
L00002058	- Config: `analytics.scan_batch_size`, default `1000`.
