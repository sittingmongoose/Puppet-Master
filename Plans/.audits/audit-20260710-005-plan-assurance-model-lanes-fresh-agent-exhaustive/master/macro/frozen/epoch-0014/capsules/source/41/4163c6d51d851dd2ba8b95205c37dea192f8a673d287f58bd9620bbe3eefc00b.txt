L00000102	## 1. Definitions
L00000103	
L00000104	<a id="DEF-USER-COMMAND"></a>
L00000105	### 1.1 User Command (preset)
L00000106	
L00000107	
L00000108	A **User Command** is a user-authored or catalog-installed command preset stored as a Markdown file with YAML frontmatter. When invoked, the template body is resolved (placeholders expanded, file includes loaded, shell output injected) and submitted as a prompt to the active chat thread or run. User Commands are the user-facing automation surface — they let users package repeatable prompt workflows without writing code.
L00000109	
L00000110	<a id="DEF-UICOMMAND-DISTINCTION"></a>
L00000111	### 1.2 UICommand (internal dispatch) — distinction
L00000112	
L00000113	
L00000114	A **UICommand** (`Plans/Contracts_V0.md#7-uicommand`, `Plans/UI_Command_Catalog.md`) is an internal UI dispatch identifier (e.g., `cmd.chat.model`, `cmd.lsp.goto_definition`). UICommands are stable IDs that bind UI elements to handlers. They are **not** user-authored; they are developer-defined, code-registered, and wiring-matrix-verified.
L00000115	
L00000116	User Commands and UICommands are orthogonal:
L00000117	- User Commands are **content presets** (prompt templates).
L00000118	- UICommands are **internal dispatch actions** (UI handler bindings).
L00000119	
L00000120	A User Command's invocation through the chat slash-command surface or command palette ultimately dispatches a UICommand (`cmd.chat.run_user_command`) to trigger execution, but the User Command itself is not a UICommand.
L00000121	
L00000122	ContractRef: ContractName:Plans/Contracts_V0.md#7-uicommand, ContractName:Plans/UI_Command_Catalog.md
L00000123	
L00000124	### 1.3 Invocation surfaces
L00000125	
L00000126	Project-scoped universal search, left-panel content search, and file-manager search remain product/search surfaces, not User Commands. The command palette may expose runnable commands as one category inside project-local `/symbols/commands/other` search, but implementation-readiness seams such as desktop to `/file-manager` `/drop`, diff heat maps or scrollbar change markers, ignored-file dimming or `/hiding`, generated-vs-workspace-file distinctions, and `/open/save/export` behavior are owned by the file/editor/search/GUI specs named in `Plans/00-plans-index.md`.
L00000127	
L00000128	File tree actions and editor/file operations use canonical UICommands, not user-authored command presets. `Plans/FileManager.md` owns tree context-menu and action semantics; `Plans/UI_Command_Catalog.md` owns `cmd.file.*` and `cmd.chat.add_file_reference`; this document only owns whether a user-authored command can invoke or appear beside those actions without rebinding their IDs.
L00000129	
L00000130	`Commands_System` / `Commands_System.md` owns this user-authored slash and `/palette` boundary only. Internal `UICommand` modeling, registration, route arguments, and command-catalog migration remain separate from user command presets even when the same palette displays both categories.

L00000144	## 2. Storage and discovery
L00000145	
L00000146	<a id="STORAGE-LAYOUT"></a>
L00000147	
L00000148	User Command files are stored in a deterministic two-tier layout. Project-local commands override global commands by name.
L00000149	
L00000150	ContractRef: PolicyRule:Decision_Policy.md§2
L00000151	
L00000152	### 2.1 Project-local
L00000153	
L00000154	```
L00000155	<project_root>/.puppet-master/commands/<name>.md
L00000156	```
L00000157	
L00000158	Scoped to the project workspace root. Available only when that project is active.
L00000159	
L00000160	### 2.2 Global
L00000161	
L00000162	```
L00000163	~/.config/puppet-master/commands/<name>.md
L00000164	```
L00000165	
L00000166	Available across all projects. Overridden by a project-local command with the same name.
L00000167	
L00000168	### 2.3 Resolution order
L00000169	
L00000170	
L00000171	When resolving a command by name:
L00000172	1. Check `.puppet-master/commands/<name>.md` in the active project root.
L00000173	2. If not found, check `~/.config/puppet-master/commands/<name>.md`.
L00000174	3. If not found, the command is unresolved. The invocation surface MUST display an error: "Unknown command: \<name\>".
L00000175	
L00000176	### 2.4 Name collision rules
L00000177	
L00000178	
L00000179	### 2.4.1 Reserved namespace retirements
L00000180	
L00000181	Reserved built-ins and their families cannot be overridden by provider, skill, or extension naming.
L00000182	
L00000183	ContractRef: ContractName:Plans/UI_Command_Catalog.md, ContractName:Plans/assistant-chat-design.md
L00000184	
L00000185	Collision rules:
L00000186	- `/web` reserves the family namespace for `/web search`, `/web fetch`, `/web extract`, `/web research`, `/web crawl`, and `/web map`
L00000187	- `override_builtin: true` is `/forbid` for reserved Assistant Chat built-ins; if it survives for extension design, it is limited to `non-core` command namespaces and cannot override `/web`, `/skill`, `/cancel`, `/clear`, `/stop`, or other canonical chat commands.
L00000188	- `/web` commands are network `/external-read` operations, not `/shell` mutation commands. Approval/help copy routes URL-host scoped `For Session` examples for `/web extract`, `/web crawl`, `/web map`, and the `/crawl/map` follow-on family through `Plans/Permissions_System.md`, while `/web search` and `/web research` use `tool-wide` session grants only for that web tool.
L00000189	- `/worktree` is reserved and cannot be re-bound by a custom command
L00000190	- `/skill` is part of the reserved built-in slash-command set and remains a built-in helper surface for skill discovery or invocation; it cannot be rebound by User Commands or `override_builtin`
L00000191	- `/plugins` remains a plugin-management/navigation surface, not a User Command namespace that a project command may redefine
L00000192	- natural-language and slash dispatch share the same underlying dispatcher, so collision handling is consistent across both entry points
L00000193	- Slash, palette, natural-language, agent-initiated, subagent, Goal Runtime, PRD Builder, and Planning Wizard web/browser intents normalize to the active `cmd.chat.web.*` command IDs and PM WebOperation / BrowserAction dispatcher; `/web` slash forms are entrypoints only, not the capability boundary. Command dispatch records `invocation_source`, optional `agent_reason`, and source IDs before the tool call; URL-reading phrases route to `cmd.chat.web.fetch` / `webfetch`, while visual, dynamic-page, iframe, console, network, screenshot, or PDF evidence requests attach BrowserAction/Site Reader requirements to the same command dispatch.
L00000194	
L00000195	Reserved-name validation is a command-system boundary shared with chat-design, chat-overlay, and command-catalog consumers. The runtime rejects command files, palette entries, or plugin/skill projections that collide with the reserved-name set before they can emit a canonical-event, and `/mode` must be disambiguated by owner context so chat-overlay display mode, runtime run mode, and User Command frontmatter do not share an untyped payload slot. GPT-era registry audits do not create new event names by observation: `chat.thread.created` and `chat.thread_created` cannot both be active names for the same event, and `chat.message.submitted` is not valid support for `cmd.chat.run_user_command` until the event registry owns that name.
L00000196	
L00000197	Ask `/Plan` behavior for command-triggered tools follows `Plans/Run_Modes.md` (`/Run_Modes.md`) and `Plans/Permissions_System.md`: Plan remains read-only for project mutation, but information-gathering `/tool` families such as web search, fetch, extract, research, crawl, and map are ask-gated or policy-denied by explicit permission rows rather than blanket auto-denied as if they were shell/file mutation.
L00000198	
L00000199	### 2.5 Name validation
L00000200	
L00000201	**Name regex:** `^[a-z][a-z0-9_-]{0,48}[a-z0-9]$`
L00000202	- Starts with a lowercase letter.
L00000203	- Contains only lowercase letters, digits, hyphens, and underscores.
L00000204	- Ends with a lowercase letter or digit.

L00000211	## 3. Command schema
L00000212	
L00000213	<a id="COMMAND-SCHEMA"></a>
L00000214	
L00000215	A User Command file (`<name>.md`) consists of YAML frontmatter followed by a Markdown template body.
L00000216	
L00000217	ContractRef: PolicyRule:Decision_Policy.md§2, ContractName:Plans/DRY_Rules.md
L00000218	
L00000219	### 3.1 YAML frontmatter
L00000220	
L00000221	```yaml
L00000222	---
L00000223	description: "Run the project's test suite and report results"
L00000224	persona: "rust-engineer"
L00000225	mode: "regular"
L00000226	model: "anthropic/claude-sonnet-4"
L00000227	subtask: false
L00000228	permissions_profile_override: null
L00000229	override_builtin: false
L00000230	---
L00000231	```
L00000232	
L00000233	### 3.2 Field definitions
L00000234	
L00000235	| Field | Required | Type | Meaning |
L00000236	|---|---|---|---|
L00000237	| `name` | Required | `string` | Invocation name. Must pass validation and MUST NOT collide with reserved Assistant Chat built-ins or reserved git/GitHub prefixes. |
L00000238	| `description` | Required | `string` | Short user-facing description. |
L00000239	| `arguments` | Optional | `array<object>` | Positional argument schema for validation/help. |
L00000240	| `persona_override` | Optional | `string` | Requested Persona override for the command execution context. |
L00000241	| `mode_override` | Optional | `string` | Requested runtime mode override when allowed by the owning surface. |
L00000242	| `model_override` | Optional | `string` | Requested model override. |
L00000243	| `permissions_profile_override` | Optional | `string` | Permissions profile override, subject to the central permission system. |
L00000244	| `override_builtin` | Optional | `boolean` | Reserved for future non-chat extension points. It MUST NOT override canonical Assistant Chat built-ins or reserved git/GitHub prefixes. |
L00000245	
L00000246	ContractRef: ContractName:Plans/assistant-chat-design.md, ContractName:Plans/Permissions_System.md, ContractName:Plans/Prompt_Pipeline.md
L00000247	
L00000248	### 3.3 Template body
L00000249	
L00000250	The Markdown body following the frontmatter is the prompt template. It supports three dynamic features: placeholders, file includes, and shell output injection.
L00000251	
L00000252	<a id="TEMPLATE-PLACEHOLDERS"></a>
L00000253	#### 3.3.1 Placeholders
L00000254	
L00000255	| Placeholder | Meaning |
L00000256	|-------------|---------|
L00000257	| `$ARGUMENTS` | All remaining text after the command name. |
L00000258	| `$1`, `$2`, ... `$N` | Positional arguments, space-separated from the invocation text. |
L00000259	
L00000260	Placeholder extraction: At load time, the template is scanned for `$ARGUMENTS` and `$N` patterns. The extracted list is stored as `hints` for autocomplete display.
L00000261	
L00000262	Unresolved placeholders (no value provided) are replaced with empty string.
L00000263	
L00000264	<a id="TEMPLATE-FILE-INCLUDE"></a>
L00000265	#### 3.3.2 File includes (`@path`)
L00000266	
L00000267	The pattern `@path/to/file` in the template body causes the referenced file's contents to be included at that position during template resolution. Directory references (`@path/to/dir`) include a listing of the directory contents.
L00000268	
L00000269	**Permission guard:** File inclusion is checked against the `read` permission key (`Plans/Permissions_System.md` §5). If the active permission resolves to `deny` for the referenced path, the include is blocked and an error message is substituted. If `ask`, the approval UI is shown.
L00000270	
L00000271	ContractRef: ContractName:Plans/Permissions_System.md#5-tool-permission-keys
L00000272	
L00000273	<a id="TEMPLATE-SHELL-INJECTION"></a>
L00000274	#### 3.3.3 Shell output injection (`` !`command` ``)
L00000275	
L00000276	
L00000277	The pattern `` !`shell-command` `` in the template body executes the shell command and injects its stdout at that position during template resolution.
L00000278	
L00000279	**Permission guard:** Shell injection is checked against the `bash` permission key (`Plans/Permissions_System.md` §5). If the active permission resolves to `deny`, the injection is blocked and an error message is substituted. If `ask`, the approval UI is shown and the user's response (`deny`/`once`/`for session`/`always`) is respected per `Plans/Permissions_System.md` §6.
L00000280	
L00000281	ContractRef: ContractName:Plans/Permissions_System.md#5-tool-permission-keys, ContractName:Plans/Permissions_System.md#ASK-FLOW

L00000285	## 4. Execution semantics
L00000286	
L00000287	
L00000288	<a id="EXECUTION"></a>
L00000289	
L00000290	### 4.1 Working directory
L00000291	
L00000292	The active working directory for command execution resolves as follows:
L00000293	
L00000294	1. If the active context has a bound worktree (`is_worktree` is true in execution context), use the **worktree root path**
L00000295	2. Otherwise, use the **active project root**
L00000296	
L00000297	This applies to all command execution contexts: Assistant Chat (all modes), Orchestrator DAE, terminal sessions, and file operations.
L00000298	
L00000299	When a thread with a bound worktree is active in Assistant Chat, all `cmd.chat.*` commands execute against the worktree root. When no worktree is bound, they execute against the project root.
L00000300	
L00000301	ContractRef: ContractName:Plans/Executor_Protocol.md, ContractName:Plans/assistant-chat-design.md, ContractName:Plans/Run_Modes.md
L00000302	
L00000303	Assistant worktree commands share the orchestrator worktree directory family but use thread-derived names. Existing orchestrator worktrees keep `.puppet-master/worktrees/{tier_id}` style directory names; Assistant thread worktrees use `.puppet-master/worktrees/thread-{short_id}`, where `short_id` is derived from the bound `thread_id`. If `thread-{short_id}` already exists, command handling appends a numeric suffix such as `thread-{short_id}-2` instead of silently reusing a stale directory.
L00000304	
L00000305	For worktree-bound threads, edit and file cards display paths relative to the resolved `working_directory`; for example, `src/main.rs (+12 −3)` is shown relative to the worktree root and opens by resolving that relative path under `working_directory`, with no special path rewriting layer. Terminal commands opened from the same thread set terminal `cwd` to the worktree path, not the main project root, and persist that worktree path as `cwd_snapshot` on the `terminal_session_record`.
L00000306	
L00000307	ContractRef: ContractName:Plans/assistant-chat-design.md, ContractName:Plans/WorktreeGitImprovement.md, ContractName:Plans/storage-plan.md
L00000308	
L00000309	### 4.2 Subtask execution
L00000310	
L00000311	command-subtask behavior is not a lighter-weight exception to the canonical child-run contract. When `subtask: true` is set, the command launches a canonical child run through the same delegated-run contract used everywhere else.
L00000312	
L00000313	ContractRef: ContractName:Plans/Tools.md, ContractName:Plans/Prompt_Pipeline.md, ContractName:Plans/storage-plan.md
L00000314	
L00000315	`subtask: true` is not a lighter-weight interpretation of a normal prompt submission. It creates a child-session / `/delegation` boundary with required parent-child lineage, storage, `/permission/capability`, and runtime evidence.
L00000316	
L00000317	Required behavior:
L00000318	- resolve requested and effective Persona/runtime/model/effort state using the same pipeline as any other child run.
L00000319	- classify the child dependency as `required` or `/optional`; `required` is the safer default for command subtasks unless the command explicitly declares advisory behavior.
L00000320	- inherit and then narrow the parent permission ceiling and compatible capability universe, including child capability narrowing before dispatch.
L00000321	- record the parent-child linkage in canonical event and storage records.
L00000322	- do not silently fallback when the command explicitly requested a runtime surface that is unavailable or incompatible; this is the command-level `no-silent-fallback` rule.
L00000323	- record the requested-vs-effective (`/effective`) provider `/runtime` surface when policy, availability, compatibility, or account binding changes the launched child.
L00000324	- borrow provider child-session/delegation patterns where useful, but never require provider-native `session-tree` semantics on direct providers. PM canonical child-run identity remains the SSOT even when the provider has no native session tree.
L00000325	- source-code evidence such as OpenCode `task.ts` is upstream evidence only; PM enforces its own `provider-family` / TOS guard for native subagent routing instead of assuming upstream task launch behavior is sufficient.
L00000326	- permission resolution for command-launched child work defers to `Plans/Permissions_System.md` (`/Permissions_System.md`) for lane, package, `/package/account-bounded`, account-bounded approval scope, and multi-lane orchestrator runs; Commands may request or display the selected approval scope, but must not synthesize a weaker command-local policy.
L00000327	- generalized projection freshness uses storage and owner vocabulary: `storage-plan.md` and `storage-plan` reserve `trust_tier` for Preview and `/browser` semantics, so Commands uses projection-freshness and `/degraded` state for stale command projections rather than reusing `trust_tier` as a generic trust/degraded label.
L00000328	
L00000329	ContractRef: ContractName:Plans/Models_System.md, ContractName:Plans/Permissions_System.md, ContractName:Plans/Contracts_V0.md
L00000330	### 4.3 Persona selection
L00000331	
L00000332	Command subtasks follow the canonical child Persona resolution order.
L00000333	
L00000334	ContractRef: ContractName:Plans/Personas.md, ContractName:Plans/Tools.md, ContractName:Plans/Run_Modes.md
L00000335	
L00000336	Rules:
L00000337	- explicit command Persona override wins.
L00000338	- otherwise the command-provided task or child type resolves Persona through the normal child Persona pipeline.
L00000339	- parent Persona is at most a weak hint.
L00000340	- child Persona does not silently copy the parent Persona.
L00000341	### 4.4 Mode and model overrides
L00000342	
L00000343	Provider, model, account, Persona, and worker-policy overrides, including the `/model/account/worker-policy` family, use the same requested/effective display grammar: command UI shows the requested override, effective result, inheritance source, and policy remap reason instead of deriving it from ad hoc color, disappearance, or current-settings winner state.
L00000344	
L00000345	
L00000346	Command overrides are explicit child requests, not bypasses around the runtime model.
L00000347	
L00000348	ContractRef: ContractName:Plans/Models_System.md, ContractName:Plans/Run_Modes.md, ContractName:Plans/CLI_Bridged_Providers.md
L00000349	
L00000350	Rules:
L00000351	- command mode overrides are capped by parent mode authority.
L00000352	- command model/runtime surface overrides become explicit child requests.
L00000353	- explicit requests do not silently fallback.
L00000354	- requested versus effective runtime/model/effort fields remain visible when remaps occur because of compatibility or policy.
L00000355	
L00000356	### 4.5 Current Working Set
L00000357	
L00000358	Command cards, command-launched child runs, and command-produced blocks remain in the current `working-set` while they are the latest active result in the current branch of work, directly support the next intended action, participate in unresolved comparison `/approval/question/validation` state, or are explicitly focused or `/pinned` by the user. They leave the working set when a newer result supersedes the same purpose, the finding has been carried forward, or execution clearly moves to a different branch of work.
L00000359	
L00000360	### 4.6 Template resolution order
L00000361	
L00000362	Template resolution proceeds in this order:
L00000363	1. Parse YAML frontmatter; extract field values.
L00000364	2. Extract placeholder hints (`$ARGUMENTS`, `$1`, `$2`, ...) from body.
L00000365	3. Substitute placeholders with invocation arguments.
L00000366	4. Resolve `@path` file includes (permission-checked).
L00000367	5. Resolve `` !`command` `` shell injections (permission-checked).
L00000368	6. The fully resolved body is the prompt submitted to the run.
L00000369	
L00000370	ContractRef: ContractName:Plans/Commands_System.md#EXECUTION

L00000374	## 5. Permissions integration
L00000375	
L00000376	<a id="PERMISSIONS"></a>
L00000377	
L00000378	### 5.1 Shell injection permission check
L00000379	
L00000380	Shell injection (`` !`command` ``) is evaluated against the `bash` permission key using the resolution algorithm in `Plans/Permissions_System.md` §8. The shell command string is the invocation context for granular pattern matching.
L00000381	
L00000382	If the resolution yields `ask`, the approval UI is shown with the full shell command displayed. The user's response follows `Plans/Permissions_System.md` §6 semantics:
L00000383	- `once`: Execute this injection only.
L00000384	- `for session`: Insert a session-scoped allow rule for the command pattern.
L00000385	- `always`: Create the durable allow defined by `Plans/Permissions_System.md` §6.
L00000386	- `deny`: Block this injection for the current blocked episode.
L00000387	
L00000388	Command permission prompts inherit parallel actor scoping. HITL/tool and `/tool` approval semantics normalize onto one blocked-episode model with explicit scope keying, field-family cleanup, and durable provenance. When resolving command-launched work, template file inclusion, or shell injection, the invocation must pass `actor/lane/run/account` and `/lane/run/account` scope so `session-scoped` `always` approvals, `reject-cascade` rules, and doom-loop `three consecutive times` counters are evaluated per actor/lane/run/account instead of across unrelated interleaved concurrent execution. If that context is under-specified, the command must present the blocked-overlay/HITL route instead of pretending a global approval or denial is safe. The legacy headless `ask -> deny unless HITL at current tier boundary` phrase is tier-era shorthand and resolves to normal blocked-overlay routing.
L00000389	
L00000390	The same permission algorithm owns `ask/plan` and `external_publish_side_effect` semantics. A command that would publish externally, mutate durable state, or ask the user to approve a plan must resolve both concepts through one canonical approval calculation, not through separate command-template text.
L00000391	
L00000392	ContractRef: ContractName:Plans/Permissions_System.md#ASK-FLOW, ContractName:Plans/Permissions_System.md#RESOLUTION
L00000393	
L00000394	### 5.2 File inclusion permission check
L00000395	
L00000396	File inclusion (`@path`) is evaluated against the `read` permission key. The file path is the invocation context. Same `ask` flow semantics apply.
L00000397	
L00000398	ContractRef: ContractName:Plans/Permissions_System.md#5-tool-permission-keys
L00000399	
L00000400	### 5.3 `permissions_profile_override`
L00000401	
L00000402	If a command specifies `permissions_profile_override`, the named profile is loaded from `~/.config/puppet-master/permission-profiles/<profile_id>.toml` and applied as an additional precedence layer between Persona overrides and project-level rules (effectively replacing the Persona's profile for this command's run).
L00000403	
L00000404	ContractRef: ContractName:Plans/Permissions_System.md#PRECEDENCE-LAYERS

L00000615	## 8. OpenCode baseline and Puppet Master deltas
L00000616	
L00000617	OpenCode command material is external reference input used for ALIGNED/RECONCILED/ADOPTED/REFERENCE categorization only; it does not override Puppet Master command names, dispatch rules, storage paths, or reserved slash-command policy.
L00000618	
L00000619	
L00000620	<a id="BASELINE-DELTAS"></a>
L00000621	
L00000622	Per `Plans/OpenCode_Deep_Extraction.md` §7D and §9D:
L00000623	
L00000624	### 8.1 Baseline
L00000625	
L00000626	OpenCode loads commands from four sources: built-in commands (`init`, `review`), config-defined commands, MCP prompts (converted to commands), and skills (registered as commands if no name collision). Discovery paths: `.opencode/commands/<name>.md` (project) and `~/.config/opencode/commands/<name>.md` (global). Template features: `$ARGUMENTS`, `$1`/`$2` positional args, `` !`shell` `` injection, `@file` inclusion. `subtask: true` runs as a subagent task. `model` override uses `provider_id/model_id` format. Custom commands can override built-in commands by name; when a user-defined command has the same name as a built-in command, the user-defined version takes precedence.
L00000627	
L00000628	### 8.2 Puppet Master deltas
L00000629	
L00000630	1. **Discovery paths:** Puppet Master uses `.puppet-master/commands/<name>.md` (project) and `~/.config/puppet-master/commands/<name>.md` (global) instead of `.opencode/` paths.
L00000631	2. **Persona integration:** OpenCode commands specify `agent` (agent name). Puppet Master commands specify `persona` (Persona ID per `Plans/Personas.md`), which is a higher-level role definition decoupled from provider-native agent concepts.
L00000632	3. **Permissions profile override:** OpenCode commands have no per-command permissions override. Puppet Master adds `permissions_profile_override` for fine-grained control.
L00000633	4. **No built-in commands:** OpenCode bundles `init` and `review` as built-in commands. Puppet Master does not bundle built-in User Commands; equivalent functionality is provided through reserved slash commands (`Plans/assistant-chat-design.md` §5) and Orchestrator actions.
L00000634	5. **MCP prompt integration:** OpenCode auto-converts MCP prompts to commands. Puppet Master treats MCP prompts as a separate mechanism; they are not auto-registered as User Commands.
L00000635	6. **GUI management:** OpenCode has no GUI for command management. Puppet Master provides a full Commands settings screen (§6).
L00000636	7. **Built-in command override policy:** OpenCode allows custom commands to freely override built-in commands by name. Puppet Master does not allow User Commands to override canonical reserved Assistant Chat slash commands. The `override_builtin` field is reserved for future non-chat extension points and MUST NOT be used to bypass reserved chat-command or reserved git/GitHub prefix rules.
L00000637	8. **Provider and capability identity limits:** OpenCode final-pass evidence from `OpenCode_Deep_Extraction.md`, `OpenCode_Coverage_Matrix.md`, `Provider_OpenCode`, and `Provider_OpenCode.md` remains external reference input for command behavior only. Puppet Master still requires its own SSE filter discriminator, stable mapping of OpenCode session IDs into provider-native identity fields, requested `/auth` versus `/effective` account identity parity, and command ID registration before adopting OpenCode-specific behavior. Capability discovery such as `capabilities.get` is a live provider/runtime contract, not a command-local cache; `Media_Generation_and_Capabilities.md`, `Media_Generation_and_Capabilities`, `Contracts_V0.md`, and `Contracts_V0` own the frozen orchestrator capability snapshot and event-registration boundaries.
L00000638	
L00000639	ContractRef: ContractName:Plans/OpenCode_Deep_Extraction.md
