L00000079	## 2. CLI-bridged execution strategies
L00000080	
L00000081	Two mutually exclusive execution semantics apply when Puppet Master invokes a CLI-bridged provider (see `Plans/CLI_Bridged_Providers.md` for the Provider facade contract).
L00000082	
L00000083	ContractRef: ContractName:Plans/CLI_Bridged_Providers.md, ContractName:Plans/Architecture_Invariants.md#INV-009
L00000084	
L00000085	<a id="STRATEGY-HTE"></a>
L00000086	### 2.1 HTE — Hosted Tool Execution
L00000087	- The provider CLI acts as a **plan/reasoner only**. It produces no file edits and executes no shell commands.
L00000088	- Puppet Master asks for a structured plan or reasoning output, executes **all** actions itself via Puppet Master tools (subject to the permission model in `Plans/Tools.md`), and feeds results back to the provider.
L00000089	- HTE is a **host-owned action loop**: the provider may request the next hosted action or return a final answer, but Puppet Master executes every real tool call itself under the permission + FileSafe stack and feeds the structured result back into the next provider turn.
L00000090	- When `execution_strategy = "hte"`, the adapter MUST place the provider in the most restrictive available **no-tools / no-side-effect** posture for that provider, even when the higher-level runtime mode is `regular`.
L00000091	- The legacy `/plan/regular` shorthand maps to the canonical ask/plan/regular default: HTE is used for `ask`, `plan`, and `regular` unless `regular` explicitly selects DAE and provider policy allows it.
L00000092	- Any tool-call observation from the provider stream during HTE is a kill condition (see §5.2).
L00000093	
L00000094	<a id="STRATEGY-DAE"></a>
L00000095	### 2.2 DAE — Delegated Agent Execution
L00000096	
L00000097	#### 2.2.1 DAE worktree context
L00000098	
L00000099	When a DAE executes inside a worktree (orchestrator-owned or assistant-owned), the execution context carries the worktree identity:
L00000100	- `working_directory` is set to the worktree root path
L00000101	- `worktree_id`, `worktree_branch`, and `is_worktree` fields are present in the execution context
L00000102	- File operations, git operations, terminal sessions, and LSP root identity all resolve to the worktree path
L00000103	
L00000104	This applies regardless of whether the DAE was triggered by Orchestrator or by Assistant Chat.
L00000105	
L00000106	ContractRef: ContractName:Plans/Executor_Protocol.md, ContractName:Plans/assistant-chat-design.md
L00000107	
L00000108	- The provider CLI **executes tools itself** (file edits, shell commands, etc.).
L00000109	- Puppet Master spawns the CLI in a jailed workspace, ingests the `stream-json` normalized event stream, and enforces policy via guards, reconciliation, and kill-switches.
L00000110	- DAE uses an **ephemeral Puppet Master-managed jail** (prefer a dedicated worktree; otherwise an equivalent isolated workspace) and the provider sees only jail paths.
L00000111	- The canonical workspace MUST NOT be directly writable during DAE. Host-side reconciliation applies the verified jail diff back only after scans and FileSafe checks succeed.
L00000112	- Providers that cannot offer deterministic pre-spawn restriction / tool-policy injection MUST advertise `dae_allowed = false` and cannot be selected for DAE.
L00000113	- The **actual jail diff** is authoritative for mutation accounting; provider-reported tool/file activity is advisory correlation data only.
L00000114	- Child/subagent runs inherit the parent selected strategy unless a higher-level SSOT explicitly narrows it.
L00000115	- Workspace isolation is per-subagent: HTE child/subagent turns inherit the parent write-scope because PM executes tools, while DAE child/subagent turns run in their own jail and reconcile back only after scans and FileSafe checks succeed.
L00000116	- End-of-run scans are mandatory (see §5.2).
L00000117	- FileSafe guards (`Plans/FileSafe.md`) apply to all DAE-originated mutations.

L00000122

L00000124	
L00000125	Given the same inputs, the same strategy MUST be selected.
L00000126

L00000132	
L00000133	| Surface state | Effective overlay | Normalized runtime mode | Notes |
L00000134	|---|---|---|---|

L00000136	| `Plan` | `plan` | `plan` | Read-only planning posture. |
L00000137	| `Deep Plan` | `deep_plan` | `plan` | Read-only planning posture with deeper overlay identity. |

L00000146	| Mode | `writes_allowed` | Strategy | Selection rule |
L00000147	|---|---|---|---|
L00000148	| `ask` | `false` | HTE | Always HTE; no opt-out. |
L00000149	| `plan` | `false` | HTE | Always HTE; no opt-out. |

L00000151	| `yolo` | `true` | DAE | DAE with mandatory guardrails + scans. |

L00000153	**Resolution algorithm:**
L00000154	
L00000155	1. Read normalized runtime `mode` from the run envelope.
L00000156	2. If `mode ∈ {ask, plan}` -> strategy = HTE. Return.
L00000157	3. If `mode == yolo` -> strategy = DAE. Return.
L00000158	4. If `mode == regular`:
L00000159	   a. If run config contains `cli_bridged_strategy: "dae"` and the active provider policy flag `dae_allowed == true` -> strategy = DAE. Return.
L00000160	   b. Otherwise -> strategy = HTE. Return.
L00000161	
L00000162	ContractRef: ContractName:Plans/CLI_Bridged_Providers.md, ContractName:Plans/Run_Modes.md, ContractName:Plans/Tools.md

L00000165	- `effective_mode_overlay = debug` with `mode ∈ {ask, plan}` is an invalid automated-debug combination and MUST be normalized before run spawn; the runtime must not execute a Debug investigation in read-only posture
L00000166	- `Debug Mode + regular + HTE` is the recommended default runtime/execution model for Debug investigations
L00000167	- `Debug Mode + yolo` is an advanced opt-in only and MUST NOT become the default Debug posture
L00000168	- a visible `Debug` picker is a workflow overlay plus target/evidence package, not a brand-new runtime mode; it must normalize into `ask | plan | regular | yolo` rather than adding another runtime enum

L00000170	- the default Debug posture is `mode = regular` with HTE unless the user explicitly requests a DAE-capable posture and provider policy allows it
L00000171	- `yolo` still requires DAE; if the provider policy snapshot does not allow DAE, the run MUST fail before provider spawn with `stop_reason = "yolo_requires_dae_provider"`; it MUST NOT silently downgrade to HTE

L00000188	
L00000189	Three-level concurrency limits apply globally across all run strategies and MUST NOT be overridden by Persona or overlay configuration alone.
L00000190

L00000193	| Cap | Default | Scope | Kill / behavior |
L00000194	|---|---|---|---|
L00000195	| `max_concurrent_crews_per_platform` | 4 | Per provider platform | New crew spawn requests queue until a slot is free. |
L00000196	| `max_concurrent_agents_per_crew` | 8 | Per active crew context | Reviewer or worker spawns queue rather than widening the limit. |
L00000197	| `max_total_active_agents` | 32 | Entire run | Global cap across all crews and direct child agents. |

L00000204	
L00000205	Budget limits are enforced by the run supervisor regardless of strategy. They are frozen into the run envelope and survive pause/resume for the same `run_id`.

L00000209	ContractRef: ContractName:Plans/Executor_Protocol.md, ContractName:Plans/Contracts_V0.md

L00000211	| Budget key | Default | Applies to | Meaning |
L00000212	|---|---|---|---|
L00000213	| `max_nesting_depth` | 4 | All modes | Maximum orchestrator -> crew -> agent -> child nesting depth before `kill.recursion_depth`. |
L00000214	| `max_total_spawned_agents` | 99 | All modes | Hard cap on total spawned agents before `kill.agent_count`. |
L00000215	| `max_tool_rounds` | 200 | All modes | Same-level tool-call round ceiling per agent before `kill.tool_round_limit`. |
L00000216	| `max_wall_ms` | 1200000 | All modes | Maximum wall-clock duration for the run. |
L00000217	| `max_estimated_tokens` | 80000 | All modes | Estimated token ceiling for the run budget. |
L00000218	| `max_same_shell_failure` | 3 | DAE / host-managed shell surfaces | Consecutive failures of the same canonical shell fingerprint before stop. |
L00000219	| `max_write_thrashing` | 5 writes / 10 min | DAE / hosted mutation paths | Same normalized file identity rewritten too often in a sliding window. |
L00000220	| `max_retryable_errors` | 3 | All modes | Ceiling on retryable provider/executor failures before run termination. |

L00000234	## 5. Kill conditions and enforcement
L00000235	
L00000236	<a id="KILL-CONDITIONS"></a>
L00000237	
L00000238	A kill condition triggers immediate run termination with outcome `done.failed` and a machine-readable reason code.
L00000239	
L00000240	Run outcome naming follows a two-family reason-code contract: `kill.*` names pre-dispatch or `/active-kill` supervisor triggers, while `done.*` names terminal outcomes recorded after shutdown, usage, or recovery finalization.
L00000241	
L00000242	ContractRef: ContractName:Plans/FileSafe.md, ContractName:Plans/CLI_Bridged_Providers.md
L00000243	
L00000244	### 5.1 Universal kill conditions (all strategies)
L00000245	
L00000246	Universal termination conditions resolve to canonical stop reasons before the run is finalized.
L00000247	
L00000248	ContractRef: ContractName:Plans/Executor_Protocol.md, ContractName:Plans/Permissions_System.md, ContractName:Plans/Contracts_V0.md
L00000249	
L00000250	| Condition | Trigger | Default threshold | Configurable | Terminal stop reason |
L00000251	|---|---|---|---|---|
L00000252	| `kill.recursion_depth` | Nesting depth exceeds `max_nesting_depth` | 4 | Yes | `kill.recursion_depth` |
L00000253	| `kill.agent_count` | Total spawned agents exceed `max_total_spawned_agents` | 99 | Yes | `kill.agent_count` |
L00000254	| `kill.tool_round_limit` | Tool-call rounds exceed `max_tool_rounds` | 200 | Yes | `kill.tool_round_limit` |
L00000255	| `done.task_timeout` | Individual task exhausts `task_timeout_ms` or inherited remaining budget and the grace-period shutdown path completes | Per envelope | Yes | `done.task_timeout` |
L00000256	| `kill.budget_exceeded` | Pre-request estimate exceeds the remaining run or session budget before dispatch | Per run/session budget | Yes | `kill.budget_exceeded` |
L00000257	| `stop.identical_failure` | Same `(tool_name, args_hash, error_message)` triple observed twice consecutively | exact-match | No | `stop.identical_failure` |
L00000258	| `stop.user_cancel` | User explicitly cancels the run | - | No | `stop.user_cancel` plus `done.cancelled` outcome |
L00000259	| `kill.hte_tool_observed` | Provider-originated tool call appears during HTE | 0 observed | No | `kill.hte_tool_observed` |
L00000260	
L00000261	Rules:
L00000262	- `done.task_timeout` is the canonical terminal stop reason for elapsed-budget exhaustion after graceful teardown. Internal supervisor bookkeeping may classify the pre-terminal trigger as timeout exhaustion, but consumers MUST persist and inspect `done.task_timeout`; `kill.task_timeout` is retired as a consumer-facing terminal alias.
L00000263	ContractRef: ContractName:Plans/orchestrator-subagent-integration.md, ContractName:Plans/Contracts_V0.md, ContractName:Plans/Executor_Protocol.md
L00000264	- `kill.budget_exceeded` remains pre-dispatch only. Post-response budget-overrun cases use terminal `done.budget_exceeded` after usage has been durably recorded and MUST NOT be folded back into the pre-dispatch row above.
L00000265	ContractRef: ContractName:Plans/usage-feature.md, ContractName:Plans/storage-plan.md, ContractName:Plans/Contracts_V0.md
L00000266	
L00000267	#### Exact-match doom-loop guard
L00000268	
L00000269	The doom-loop guard is exact-match only. PM MUST compare the same `(tool_name, serialized_args_hash, error_message)` triple at the same nesting level across consecutive attempts. Fuzzy matching, substring matching, and `looks similar` heuristics are prohibited for this terminal stop condition.
L00000270	
L00000271	Broader retry suppression for substantially equivalent failures is owned by `Plans/Tools.md` and does not rename or replace this exact-match stop condition.
L00000272	
L00000273	ContractRef: ContractName:Plans/Executor_Protocol.md, ContractName:Plans/Architecture_Invariants.md, ContractName:Plans/Tools.md

L00000275	#### Signal handling and process lifecycle
L00000276	
L00000277	PM entrypoints MUST establish the canonical shutdown root with `signal.NotifyContext` or an equivalent once-owned signal fan-out before provider, MCP, terminal, or LSP helpers are started.
L00000278	
L00000279	ContractRef: ContractName:Plans/Executor_Protocol.md, ContractName:Plans/Contracts_V0.md, ContractName:Plans/storage-plan.md
L00000280	
L00000281	`SIGTERM` and `SIGINT` request graceful shutdown. `SIGHUP` triggers config reload, not shutdown. Every managed provider, MCP, terminal, and LSP subprocess MUST run in its own process group (`setsid` on Unix; `CREATE_NEW_PROCESS_GROUP` on Windows) so signal delivery stays scoped to the `/process-group` rather than individual PIDs.
L00000282	
L00000283	Windows MCP subsystem shutdown uses `CREATE_NEW_PROCESS_GROUP`; graceful cancellation sends `CTRL_BREAK_EVENT`, waits 3 seconds, then uses `TerminateProcess` for the still-live child process group. Windows paths that may exceed ordinary path length limits are normalized with the `\\?\` long-path prefix before process launch or teardown bookkeeping.
L00000284	
L00000285	This lifecycle section replaces over-summarized process-shutdown wording by naming the entrypoint signal root, process-group rule, platform-specific teardown sequence, and orphaned-process RAM leak prevention rationale.
L00000286	
L00000287	Grace periods:
L00000288	- provider processes: 5 seconds, then force terminate
L00000289	- MCP and LSP subprocesses: 3 seconds, then force terminate
L00000290	- shutdown entrypoints MUST be guarded by an idempotent `Once`-style primitive; re-entrant shutdown is a safe no-op
L00000291	
L00000292	ContractRef: ContractName:Plans/storage-plan.md, ContractName:Plans/LSPSupport.md, ContractName:Plans/Executor_Protocol.md
L00000293	
L00000294	Shutdown durability rules:
L00000295	- before force termination or final outcome emission, PM flushes buffered normalized events and seglog writers
L00000296	- if durability flush fails, PM emits a structured diagnostic and the terminal outcome escalates to `done.crashed` rather than claiming a clean shutdown
L00000297	- user-driven or parent-driven cancellation produces `done.cancelled`, not `done.failed`, even if force termination is needed after the grace window
L00000298	
L00000299	ContractRef: ContractName:Plans/storage-plan.md, ContractName:Plans/Architecture_Invariants.md, ContractName:Plans/Contracts_V0.md
L00000300	
L00000301	Startup recovery:
L00000302	- if PM starts and finds an unfinished run with no canonical terminal `done` event, it performs crash recovery against the last durable seglog state
L00000303	- recovered crash cases synthesize terminal metadata with `done.crashed` and `stop_reason = crash_recovered`
L00000304	- PM MUST NOT silently drop an incomplete run or rewrite it as `done.failed` without the crash marker
L00000305	
L00000306	ContractRef: ContractName:Plans/Contracts_V0.md, ContractName:Plans/storage-plan.md, ContractName:Plans/Architecture_Invariants.md
L00000307	
L00000308	##### Resource disposal and health monitoring
L00000309	
L00000310	Runtime teardown is an owned lifecycle contract, not best-effort cleanup:
L00000311	- PM closes DB handles, MCP sessions, terminal shells, temporary files, and owned subprocess groups in a deterministic teardown order
L00000312	- a failed teardown step emits a structured diagnostic; PM MUST NOT silently reuse poisoned process state or abandoned shell/session state

L00000337	| Condition | Reason code | Description |
L00000338	|-----------|-------------|-------------|
L00000339	| Repeated shell failure | `kill.shell_failure` | Same canonical shell command fails `max_same_shell_failure` consecutive times. |
L00000340	| Write thrashing | `kill.write_thrash` | Same file written more than `max_write_thrashing` times within 10 minutes. |
L00000341	
L00000342	`kill.shell_failure` counting contract:
L00000343	- a shell failure increments the streak only when an actually executed canonical shell tool invocation ends with `tool_result.ok == false`, non-zero exit, timeout, or signal termination
L00000344	- permission denials, FileSafe blocks, validation failures, missing execution due to policy, and synthesized reconciler closures do **not** count as shell failures
L00000345	- the canonical shell fingerprint is `(tool_name, normalized_command, normalized_cwd)` after adapter normalization, including removal of provider wrapper boilerplate such as an outer `bash -lc` added by Puppet Master
L00000346	- user-interface-only terminal actions such as reveal, pin, rename, clear-scrollback, or pane movement do **not** count as executed shell invocations
L00000347	- explicit terminal restart or explicit session replacement resets shell-failure continuity because a new `terminal_session_id` is created
L00000348	- success of the same fingerprint resets the streak to zero; a different executed fingerprint also resets the previous fingerprint's streak
L00000349	- Compatibility labels are canonicalized here: `shell-fingerprint` means the canonical shell fingerprint, `terminal-normalized` means the terminal normalized `done` and `/audit` outcome family, and `/replace/stop` covers explicit session replacement, restart, or user/parent stop paths.

L00000351	ContractRef: ContractName:Plans/Tools.md, ContractName:Plans/storage-plan.md, ContractName:Plans/UI_Command_Catalog.md
L00000352	
L00000353	`kill.write_thrash` counting contract:
L00000354	- file identity is the normalized project-relative real path of the mutated jail path after symlink / `.` / `..` collapse
L00000355	- a qualifying write is an actual content-changing create / overwrite / append / rename-destination / delete observed from the authoritative jail diff or equivalent live mutation metadata
L00000356	- denied, blocked, no-diff, rollback, and Puppet-Master-owned post-processing writes do **not** count
L00000357	- the window is a **sliding** 10-minute window using the run supervisor's monotonic clock; a kill occurs immediately when a new qualifying write would make the count exceed the configured ceiling for that file

L00000359	ContractRef: ContractName:Plans/FileSafe.md, ContractName:Plans/CLI_Bridged_Providers.md, ContractName:Plans/storage-plan.md

L00000373	## 6. Run outcome taxonomy
L00000374	
L00000375	Every run terminates with exactly one canonical coarse outcome value.
L00000376	
L00000377	ContractRef: ContractName:Plans/Contracts_V0.md#EventRecord, PolicyRule:Decision_Policy.md§2
L00000378	
L00000379	| Outcome | Meaning |
L00000380	|---------|---------|
L00000381	| `done.ok` | Run completed successfully; all objectives met. |
L00000382	| `done.failed` | Run terminated due to a handled error, kill condition, or post-run scan failure. |
L00000383	| `done.deferred` | Run paused; work remains but requires external input such as HITL approval. |
L00000384	| `done.rotated` | Run terminated and a follow-up run was spawned for continuation. |
L00000385	| `done.gutter` | Run terminated without meaningful progress; provider produced no actionable output. |
L00000386	| `done.cancelled` | Run was explicitly cancelled by the user, parent, or canonical timeout or stop path. |
L00000387	| `done.crashed` | PM or a managed runtime crashed or lost durability before clean terminal finalization. |
L00000388	
L00000389	ContractRef: ContractName:Plans/Tools.md, ContractName:Plans/storage-plan.md
L00000390	
L00000391	Rules:
L00000392	- the outcome MUST be recorded in the terminal `done` event of the normalized provider stream and persisted via `EventRecord` to seglog
L00000393	- normalized `done.payload.status` remains a coarse transport-facing status (`success | cancelled | failed`), while `done.payload.outcome` carries the canonical taxonomy above
L00000394	- `done.cancelled` is for explicit cancellation semantics; `done.failed` is not a catch-all for stop paths that were intentionally requested
L00000395	- `done.crashed` is reserved for crash or durability-loss scenarios, including startup crash recovery
L00000396	- user-driven terminal restart or replacement mints a new runtime identity instead of mutating the prior run outcome in place
L00000397	- clearing scrollback or revealing an existing terminal session does not mint a new run outcome

L00000399	ContractRef: ContractName:Plans/UI_Command_Catalog.md, ContractName:Plans/Section15_MVP_Promoted_Features_Spec.md, ContractName:Plans/storage-plan.md

L00000670	## Runtime Mode Interaction with Blocked Recovery Consolidation Addendum (2026-03-09)
L00000671	
L00000672	This section defines deferred / Waiting Run Mode Semantics.
L00000673	
L00000674	### Run-level state
L00000675	- A run remains active if any node is runnable.
L00000676	- If no node is runnable and blocked/backoff/prerequisite-waiting work exists, the run is deferred/waiting rather than terminal.
L00000677	- Terminal completion requires no runnable, no blocked, no backoff, and no unresolved prerequisite work.
L00000678	
L00000679	### Headless blocked discovery
L00000680	When `headless_ask_denied` blocks work in a non-interactive mode:
L00000681	- emit a blocked notice with `blocked_reason_code: headless_ask_denied`
L00000682	- surface blocked node count in CLI/log status summaries
L00000683	- surface a dashboard badge if a UI session is attached
L00000684	- include the exact permission or approval that could not be presented interactively
L00000685	- return `status: "unavailable"` with `reason: "headless"` to tool and operation-card consumers when no interactive presenter exists
L00000686	- do not offer GUI-only recovery actions such as `Open in Terminal` from a headless context; provide resume guidance, permission-preset adjustment, interactive mode change, fallback strategy when policy allows it, or an orchestrator-facing blockage
L00000687	
L00000688	### Safe-point applicability
L00000689	Run modes do not redefine `mutation_capable`. They only determine whether mutation-capable attempts may occur and therefore whether safe points are relevant in that mode.
L00000690	## Headless Blocked Discovery and Mutation Classifier Alignment Addendum
L00000691	
L00000692	### Headless `headless_ask_denied` discovery
L00000693	
L00000694	When `headless_ask_denied` blocks a node in a headless or non-interactive run mode:
L00000695	
L00000696	1. A `blocked_notice` event is emitted to the event bus with `blocked_reason_code: headless_ask_denied`.

L00000698	3. If the run has a connected UI session, a dashboard notification badge appears.
L00000699	4. The blocked notice includes the specific permission or approval that was needed and could not be presented interactively.
L00000700	
L00000701	Recovery: the user must either (a) change the run mode to interactive and resume, (b) adjust permission presets to pre-approve the needed action, or (c) abort the blocked node.
