L00000038

L00000044	### Three-axis settings model
L00000045	
L00000046	Settings resolution is always described on three axes:
L00000047	- `source`: where a candidate value came from (`manual_override`, `persona_preference`, `surface_default`, `scope_policy`, `config_default`, `provider_default`).
L00000048	- `request`: the value explicitly requested for this run or child run.
L00000049	- `execution`: the value actually handed to the selected provider/runtime after capability checks, worktree assignment, and policy gating.
L00000050	
L00000051	The display grammar MUST preserve the distinction between requested and effective values for provider, model, variant, effort, auth mode, and account identity.
L00000052	
L00000053	### Deterministic precedence by scope
L00000054	
L00000055	The canonical precedence chain is:
L00000056	1. explicit run-envelope override
L00000057	2. scoped owner policy for the active execution unit (`run`, `seam`, `package`, `node`, `overseer`, or delegated subagent)
L00000058	3. Persona preference
L00000059	4. surface or stage default
L00000060	5. project or global config default
L00000061	6. last-used state where the surface explicitly permits it
L00000062	7. provider default
L00000063	
L00000064	Rules:
L00000065	- the same inputs and availability set MUST produce the same effective result
L00000066	- scope-specific policy MAY narrow or pin provider/model choices, but it MUST still emit requested versus effective values
L00000067	- parallel-node worktree assignment participates in precedence when a worktree owner constrains the allowed provider/model surface for that node
L00000068	- ownership transitions between overseer and delegated-subagent levels MUST emit a fresh resolver record instead of silently inheriting stale effective state

L00000244	## 2. Model and runtime selection priority
L00000245	<a id="SELECTION-PRIORITY"></a>
L00000246	
L00000247	Model and runtime selection remains deterministic and follows the same requested/effective runtime pipeline used elsewhere.
L00000248	
L00000249	| Priority | Source | Description |
L00000250	|---|---|---|
L00000251	| 1 | explicit override | run envelope, manual picker, tier override, or surface-level override |
L00000252	| 2 | Persona runtime preferences | per-Persona defaults for provider entry, model, variant, and supported controls |
L00000253	| 3 | surface defaults | Chat, Interview, Builder, Orchestrator, or profile defaults |
L00000254	| 4 | project/global defaults | configuration defaults including preferred runtime family or model |
L00000255	| 5 | last used | previous user choice when still valid |
L00000256	| 6 | internal/provider fallback | provider/runtime default chosen after capability filtering |
L00000257	
L00000258	ContractRef: PolicyRule:Decision_Policy.md§3, ContractName:Plans/Prompt_Pipeline.md, ContractName:Plans/FinalGUISpec.md
L00000259	
L00000260	Selection rules:
L00000261	- the runtime first resolves the concrete provider entry/runtime surface, then the effective model within that surface.
L00000262	- `provider_family_id` may influence pooling or fallback, but it does not replace the concrete provider entry selection.
L00000263	- if the runtime internally reroutes to another effective model or model variant, that deviation is captured as runtime evidence; it does not rewrite the frozen requested selection.
L00000264	- model availability and capability checks must consider the concrete runtime surface, not just the vendor model namespace.
L00000265	- Retired Gemini CLI deterministic selection precedence (`--model`, `GEMINI_MODEL`, `settings.json` `model.name`, local model router, provider default, and `general.plan.modelRouting`) is retained only as source-lineage. Active CLI-runtime selection in this lane belongs to Antigravity CLI (`agy`, `agy models`, `--model`) and must record requested/effective model evidence without treating Gemini CLI as an active provider.
L00000266	
L00000267	Fallback resolution emits a `fallback_chain[]` in the requested/effective model snapshot. L00000708	### 6.1 Definition
L00000709	
L00000710	A **Variant** is a named model preset that the user can quickly switch between. Variants provide a fast way to cycle through models without editing config.
L00000711	
L00000712	### 6.2 Built-in variants
L00000713	
L00000714	Puppet Master ships with a set of built-in variants based on available providers:
L00000715	
L00000716	| Variant name | Target model | Description |
L00000717	|-------------|-------------|-------------|
L00000718	| `default` | Per selection priority (§2) | The system-selected model. Always available. |
L00000719	| `fast` | Smallest/cheapest available model | Optimized for speed and cost. |
L00000720	| `powerful` | Largest/most capable available model | Optimized for quality. |
L00000721	
L00000722	Built-in variants are resolved dynamically based on available providers at runtime. If a variant's target model is unavailable, the variant falls back to the `default` variant.

L00000780	
L00000781

L00001098

L00001102	- `1` = terse, code-only, minimal explanation,
L00001103	- `2` = concise with light explanation,
L00001104	- `3` = balanced default,
L00001105	- `4` = detailed and explanatory,
L00001106	- `5` = verbose, teaching-oriented, high-context explanation.
L00001107

L00001112	1. user preference setting,
L00001113	2. mode overlay,
L00001114	3. explicit per-thread override.

L00001117	- plan mode → `4`
L00001118	- ask mode → `3`
L00001119	- agent mode → `2`

L00001123	- `talkativeness` maps to system-prompt instructions that control response length, amount of explanation, and expected detail level,
L00001124	- some model families follow terse instructions more reliably than others, so PM MAY adjust the instruction mapping per model family while preserving the same user-visible scale.
L00001125	
L00001126	`talkativeness` is a Persona instruction-layer control rather than a transport sampling knob.
L00001127	
L00001128	Canonical implications:
L00001129	- `persona_talkativeness` does **not** require its own transport matrix row.

L00001281	## Runtime Retry / Fallback Ownership Addendum (2026-03-09)
L00001282	
L00001283	Model fallback and runtime retry are separate concerns.
L00001284	
L00001285	### Ownership split
L00001286	- model selection decides requested/effective provider/model before execution begins
L00001287	- runtime policy decides whether an attempt is retried, remediated, blocked, or escalated after a classified outcome
L00001288	- providers and adapters may not invent model-local retry loops that bypass runtime policy
L00001289	
L00001290	### Required attempt snapshots
L00001291	
L00001292	
L00001293	Each attempt MUST retain requested and effective model/provider identifiers so users can later explain why a blocked or failed attempt ran under a specific effective configuration.
L00001294	
L00001295	### Fallback rule
L00001296	Model fallback may change the effective model only through the shared model-selection contract, never as an implicit side effect of provider transient handling inside an already-running attempt.
L00001297	## Requested/Effective Model and Retry Ownership Canonical Alignment (2026-03-09)
L00001298	
L00001299	Requested/effective model resolution remains separate from runtime retry policy.
L00001300	
L00001301	Rules:

L00001345	## Provider/model selection policy and audit addendum
L00001346	
L00001347	This addendum elaborates how the canonical provider/model precedence owner section is surfaced through user-facing policy, capability gating, and audit trail details.
L00001348	
L00001349	### Persona, execution-unit, and scope policy inputs
L00001350	
L00001351	
L00001352	1. **Persona axis**: Users select a Persona (e.g., "Code Analyzer", "Documentation Writer") which carries default preferences for model, provider, and mutation_policy.
L00001353	2. **Execution Unit Type axis**: Different execution unit types (run, node, delegated_subagent) can have scoped policies (e.g., "use GPT-4 for run-level analysis, but Claude for node-level code generation").
L00001354	3. **Scope axis**: Settings can be scoped to worktree, project, or global level; settings at a tighter scope override broader scopes.
L00001355	
L00001356	### Precedence chain for provider/model selection
L00001357	
L00001358	When a unit needs to select a provider and model, resolve in this order:
L00001359	
L00001360	1. **Explicit run-envelope override**: If the run was launched with `--provider=X --model=Y`, use those.
L00001361	2. **Scoped owner policy**: If the active execution_unit_type has a policy (e.g., "node-type uses Copilot"), apply it.
L00001362	3. **Persona preference**: Use the active Persona's default model and provider.
L00001363	4. **Surface or stage default**: If the UI surface or execution stage has a default (e.g., "code review prefers GPT-4"), use it.
L00001364	5. **Project or global config default**: Fallback to project-wide or global settings.
L00001365	6. **Last-used state**: If permitted by settings, use the model/provider from the previous run of the same type.
L00001366	7. **Provider default**: Use the provider's canonical default model.
L00001367	
L00001368	### Settings resolution and override semantics
L00001369	
L00001370	
L00001371	- **Conservative policy**: Use only settings tier 1 (explicit override) or tier 3+ (canonical defaults); do not apply stage defaults or persona preferences.
L00001372	- **Standard policy** (default): Use tiers 1-5 (explicit override through project defaults); respect all configuration.
L00001373	- **Aggressive policy**: Use all tiers 1-7; auto-select the cheapest or fastest model if multiple are available and equally suitable.
L00001374	
L00001375	### Provider capability and cost gating
L00001376	
L00001377	- **Capability check**: Before selecting a provider, verify it supports the required model and inference parameters (context length, output length, reasoning mode, etc.).
L00001378	- **Multi-account capability check**: Provider capability modeling MUST include multi-account-related behavior before any provider/account pool can be selected or switched. Required capability facts include `supports_multi_account`, signal sources/confidence, cooldown/retry-budget support, reset countdown support, and provider-specific limits that change account pressure interpretation or rotation safety.
L00001379	- **Cost gating**: If a model exceeds the active Persona's cost budget, skip it and move to the next in the precedence chain.
L00001380	- **Fallback**: If all preferred models exceed budget or are unavailable, emit a concern (not a silent failure) and suggest cheaper alternatives or escalation.
L00001381	
L00001382	Clamp/substitution decisions use the `clamp/substitution` reason-code family when the requested provider, model, effort, capability, instruction projection, or skill projection cannot be applied exactly.
L00001383	
L00001384	Required `clamp/substitution` reason codes:
L00001385	- `model_unavailable`
L00001386	- `model_routed_by_provider`
L00001387	- `model_substituted`
L00001388	- `effort_unsupported`
L00001389	- `effort_clamped`
L00001390	- `auth_family_capability_clamped`
L00001391	- `capability_unknown`
L00001392	- `instruction_projection_partial`
L00001393	- `skill_projection_partial`
L00001394	
L00001395	Rules:
L00001396	- `model_unavailable` and `model_routed_by_provider` distinguish PM inability to select a requested model from provider-side rerouting after PM dispatch.
L00001397	- `model_substituted`, `effort_clamped`, and `auth_family_capability_clamped` are explicit `/substitution` evidence for requested/effective differences caused by model fallback, narrowed effort, or auth-family capability limits.
L00001398	- `effort_unsupported` and `effort_clamped` distinguish unsupported effort controls from accepted-but-narrowed effort controls.
L00001399	- `capability_unknown`, `instruction_projection_partial`, and `skill_projection_partial` remain inspectable so the UI does not present a fully honored model/capability/instruction state when PM only has partial or unknown evidence.
