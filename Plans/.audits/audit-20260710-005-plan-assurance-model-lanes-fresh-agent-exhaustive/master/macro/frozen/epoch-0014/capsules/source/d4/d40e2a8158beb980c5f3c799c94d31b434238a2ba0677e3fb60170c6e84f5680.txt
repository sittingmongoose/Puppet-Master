L00000014	## 1. Purpose
L00000015	
L00000016	Define the integration contract for **OpenCode** as a **server-bridged provider** in Puppet Master. Unlike CLI-bridged providers (Cursor, Claude Code), OpenCode uses a **local HTTP server** with an OpenAPI 3.1 REST API and SSE event stream. Codex, Copilot, and Gemini follow direct-provider auth/calls rather than this server-bridged transport.
L00000017	
L00000018	**Key distinction (locked):** OpenCode is **server-bridged only**. Puppet Master MUST communicate via HTTP REST + SSE through the unified Provider facade; it MUST NOT run OpenCode as a CLI-bridged runtime transport. If OpenCode is enabled, this transport is not optional.
L00000019	
L00000020	### 1.1 Transport + auth taxonomy (normative)
L00000021	
L00000022	- **Transport taxonomy (SSOT):** `Plans/Contracts_V0.md` (§2.1 Provider transport taxonomy) and the Provider routing policy in `Plans/CLI_Bridged_Providers.md`.
L00000023	- **OpenCode (this plan):**
L00000024	  - **Transport class:** server-bridged (`ProviderTransport = ServerBridge`; request envelope `transport = "http"`; streaming via SSE).
L00000025	  - **Auth realms (split):**
L00000026	    - **Server auth realm:** `server_credentials` (HTTP basic auth to the OpenCode server).
L00000027	    - **Provider auth realm:** provider-native auth for upstream AI providers, managed inside OpenCode and exposed via `/provider/auth` + callback endpoints.

L00000099	## 4. Architecture Overview
L00000100	
L00000101	### 4.1 OpenCode Server Model
L00000102	
L00000103	OpenCode uses a **client/server architecture**:
L00000104	
L00000105	1. The user runs `opencode serve` (or the TUI, which starts a server internally).
L00000106	2. The server exposes an **OpenAPI 3.1** HTTP API on `http://<hostname>:<port>` (default: `http://127.0.0.1:4096`), and serves interactive API docs at `/doc`.
L00000107	3. Clients interact via REST endpoints and an SSE event stream.
L00000108	4. OpenCode is **provider-agnostic**: it supports Anthropic, OpenAI, Google, Azure, AWS Bedrock, OpenRouter, XAI, Mistral, Groq, DeepInfra, Venice, ZAI, Alibaba-compatible transports, and more — all configured through its own config.
L00000109	
L00000110	**Puppet Master connects to OpenCode as a client**, sending prompts and receiving responses through the HTTP API.
L00000111	
L00000112	**Runtime boundary (scope clarification):** Puppet Master does not use SDK launch flows for OpenCode runtime transport. CLI path input is launcher/discovery fallback only; run transport remains HTTP/SSE.
L00000113	
L00000114	### 4.2 Transport: HTTP + SSE (Server-Bridged)
L00000115	
L00000116	| Aspect | CLI-Bridged (existing) | Server-Bridged (OpenCode) |
L00000117	|--------|----------------------|--------------------------|
L00000118	| **Communication** | Spawn subprocess, parse stdout/stderr | HTTP REST requests + SSE event stream |
L00000119	| **Lifecycle** | Process per run (fresh spawn) | Session per run (HTTP session lifecycle) |
L00000120	| **Model discovery** | CLI command (`agent models`, etc.) | `GET /provider` API endpoint |
L00000121	| **Auth detection** | Preflight CLI check + exit codes | `GET /global/health` + HTTP status codes |
L00000122	| **Event stream** | JSONL on stdout | SSE on `GET /event` or synchronous response |
L00000123	| **Tool calls** | Embedded in JSONL stream | Embedded in message response parts |
L00000124	
L00000125	### 4.3 Why Server-Bridged (not CLI)
L00000126	
L00000127	OpenCode's CLI (`opencode`) can launch a TUI/server and also supports non-interactive execution via `opencode run`. Puppet Master still standardizes this provider on the HTTP server API for runtime calls so health/auth checks, model discovery, and event normalization stay transport-consistent with the unified Provider contract. This matches OpenCode's client/server architecture where multiple clients (TUI, IDE plugins, and external integrations) talk to the same server.

L00000131	## 5. Connection Contract
L00000132	
L00000133	### 5.1 Server Discovery and Connection
L00000134	OpenCode connection is profile-driven.
L00000135	
L00000136	Each OpenCode row in PM is a `Server Profile` with one of two modes:
L00000137	- `Managed Server`
L00000138	- `Attach to Existing Server`
L00000139	
L00000140	This profile model replaces the older single-instance connection assumption. PM may track multiple OpenCode server profiles at once, and every request freezes the chosen `connection_profile_id` before execution.
L00000141	
L00000142	Profile roots may be represented as `/profiles/<connection_profile_id>/` or a concrete provider-root `.../profiles/<connection_profile_id>/`; each profile is a per-unit runtime surface with PM sidecar state under `pm/state.json`, `pm/logs/`, `pm/projections/`, and `pm/backups/`.
L00000143	
L00000144	ContractRef: ContractName:Plans/Multi-Account.md, ContractName:Plans/Contracts_V0.md, ContractName:Plans/storage-plan.md
L00000145	
L00000146	Required profile fields:
L00000147	- `connection_profile_id`
L00000148	- `label`
L00000149	- `profile_mode`
L00000150	- endpoint summary (`host`, `port`, or explicit base URL)
L00000151	- `endpoint`
L00000152	- `server_auth_ref`
L00000153	- `config_root`
L00000154	- `enabled`
L00000155	- `priority`
L00000156	- `discovered_upstream_provider_ids[]`
L00000157	- optional credential refs for HTTP auth
L00000158	- health state
L00000159	- discovery state
L00000160	- last discovery snapshot metadata
L00000161	- PM ownership mode
L00000162	
L00000163	Connection rules:
L00000164	- `Managed Server` means PM owns launch command, environment/config selection, reconnect attempts, and shutdown behavior.
L00000165	- `Attach to Existing Server` means PM owns endpoint/auth configuration and health/discovery polling only.
L00000166	- all runtime calls remain HTTP/SSE server-bridge calls regardless of whether PM launched the process.
L00000167	- profile selection freezes into `connection_profile_id` in the requested/effective runtime snapshot before execution.
L00000168	- The `managed-vs-attached` split is part of the OpenCode `/transport` contract: PM supports one-or-many OpenCode server-profile and `/config` profiles instead of a single global connection record.
L00000169	- For `Managed Server`, PM may launch OpenCode with a PM-selected `OPENCODE_CONFIG_DIR` and owns the `long-lived` MCP configuration state in the provider-profile config root where the provider requires local config files; run start may perform only a lightweight `last-mile` worktree-specific sync rather than a full install/`/setup` on every call.
L00000170	- For `Attach to Existing Server`, the selected endpoint is an `attached-server`. PM reflects server-side MCP and tool configuration as `External / Not Managed` unless the OpenCode server API exposes a deliberate PM-managed `/config` path.
L00000171	
L00000172	ContractRef: ContractName:Plans/CLI_Bridged_Providers.md, ContractName:Plans/Prompt_Pipeline.md, ContractName:Plans/FinalGUISpec.md
L00000173	### 5.2 Health Check
L00000174	Health and discovery are separate states.
L00000175	
L00000176	PM must evaluate OpenCode profiles in this order:
L00000177	1. connection / launch state
L00000178	2. health check result
L00000179	3. discovery refresh result
L00000180	
L00000181	ContractRef: ContractName:Plans/FinalGUISpec.md, ContractName:Plans/storage-plan.md, ContractName:Plans/usage-feature.md
L00000182	
L00000183	Canonical profile states:
L00000184	- `Configured`
L00000185	- `Launching` or `Connecting`
L00000186	- `Connected`
L00000187	- `Discovering`
L00000188	- `Ready`
L00000189	- `Connected (stale discovery)`
L00000190	- `Connected (discovery failed)`
L00000191	- `Disconnected`
L00000192	- `Launch failed`
L00000193	
L00000194	Rules:
L00000195	- a profile is not fully `Ready` until health succeeds and discovery completes.
L00000196	- if health succeeds but discovery fails, the profile remains connected but degraded.
L00000197	- if a previously ready profile disconnects, PM preserves the last-known discovery snapshot and marks it stale rather than blanking the provider/model surface.
L00000198	- attached profiles may be healthy while still `ExternalNotManaged` for some management affordances.
L00000199	- discovery state covers provider, model, and auth refresh together. GUI/status projections may label that grouped readiness as `/models/auth` or `/discovery/auth`; if a cached discovery snapshot is reused after a failed refresh, the row must keep explicit `/stale` labeling alongside the last-known provider/model/auth facts.
L00000200	- Upstream auth exposed by OpenCode is labeled `Connected in OpenCode`; it is not converted into a PM-owned account row. When a profile is disconnected or unhealthy, PM preserves last-known `/providers`, models, and auth facts with explicit `stale-state` labeling rather than blanking the upstream surface.
L00000201	
L00000202	ContractRef: ContractName:Plans/Contracts_V0.md, ContractName:Plans/Multi-Account.md, ContractName:Plans/CLI_Bridged_Providers.md

L00000228	
L00000229	OpenCode is a server-bridged adapter over the PM child-run model.
L00000230	
L00000231	ContractRef: ContractName:Plans/CLI_Bridged_Providers.md, ContractName:Plans/Tools.md, ContractName:Plans/storage-plan.md

L00000233	Mapping rules:
L00000234	- PM `thread_id`, `run_id`, `parent_run_id`, and `child_run_id` remain canonical PM lineage fields.
L00000235	- The server-bridged OpenCode projection mirrors the expanded correlation `/identity` bundle from `ProviderRequestEnvelope`, including run/thread/parent/child lineage, attempt identity, execution role, requested/effective runtime/provider/model/account descriptors, permission/tool-policy snapshot refs, working-directory or worktree identity, prompt parts, retry/approval context, normalized output/correlation ids, and provider-native session ids as additive metadata only.

L00000237	- PM must not rewrite `thread_id` into an OpenCode session id.
L00000238	- PM preserves requested versus effective runtime/model/effort state even when OpenCode internally uses agent/session configuration.
L00000239	- PM records the runtime platform as `opencode` while model IDs preserve upstream provider namespaces such as `anthropic/...`; the transport host and upstream provider identity must remain distinct in requested/effective runtime disclosure.

L00000244	- OpenCode's aggregator/bridge role covers upstream vendors PM may not support natively; on app `boot-refresh`, PM refreshes OpenCode provider/model discovery in the background, keeps last-known connected upstream models visible until refresh finishes, and reports progress or per-provider failure in the shell `/status-bar` without blocking runtime selection.

L00000585	### 13.3 Cancellation and abort contract
L00000586	
L00000587	Cancellation is a first-class provider control and is distinct from ordinary request failure.
L00000588	
L00000589	Rules:
L00000590	- canceling an in-flight request means Puppet Master sends a provider-specific cancellation action for the active OpenCode transport, such as closing the HTTP stream, canceling the SSE subscription, or triggering an abort signal on the request handle
L00000591	- if partial output tokens have already been received, those tokens are retained and the normalized response is marked `completion_reason: cancelled`
L00000592	- timeout and cancel are distinct: timeout is automatic after `request_timeout_ms`, while cancel is a user-initiated action
L00000593	- after cancellation, the provider connection is returned to the connection pool when healthy, or closed and discarded when the transport is suspected to be corrupted
L00000594	- PM MUST emit `provider.request_cancelled { provider_id, request_id, tokens_received, reason: "user" | "timeout" | "budget" | "error" }`
L00000595	
L00000596	ContractRef: ContractName:Plans/Contracts_V0.md, ContractName:Plans/Executor_Protocol.md, ContractName:Plans/storage-plan.md
L00000597	
L00000598	### 13.4 Concurrency model
L00000599	
L00000600	OpenCode request dispatch is queue-backed and provider-account scoped.
L00000601	
L00000602	Rules:
L00000603	- default mode is sequential: one active request at a time per provider account
L00000604	- parallel mode is allowed only when explicitly enabled, such as subagent execution or other orchestrator-controlled fan-out flows
L00000605	- concurrency limit is configurable per provider account; default = `1`; upper bound is provider-specific and MUST respect upstream rate-limit constraints
L00000606	- when the concurrency limit is reached, new requests enter a FIFO queue
L00000607	- queued requests time out after `queue_timeout_ms` (default `30000ms`) if they have not started execution
L00000608	- different accounts for the same provider have independent concurrency limits and independent queues
L00000609	- PM MUST emit `provider.request_queued { provider_id, request_id, queue_position, queue_depth }` whenever a request is queued instead of starting immediately
L00000610	
L00000611	ContractRef: ContractName:Plans/Multi-Account.md, ContractName:Plans/Executor_Protocol.md, ContractName:Plans/Contracts_V0.md
L00000612	
L00000613	### 13.5 Streaming error recovery
L00000614	
L00000615	Streaming recovery preserves already-received output while keeping retry ownership aligned with PM runtime policy.
L00000616	
L00000617	Rules:
L00000618	- if the connection breaks mid-stream, PM MUST:
L00000619	  1. retain all tokens received so far
L00000620	  2. mark the partial response as `completion_reason: stream_error`
L00000621	  3. attempt reconnect when `auto_retry_stream: true` (default)
L00000622	  4. include `partial_response` context in the retry so the model can continue when the provider supports continuation from partial output
L00000623	- provider support for continuation from partial output is not universal; when unsupported, PM preserves the partial output and surfaces the stream error without fabricating a seamless continuation
L00000624	
L00000625	Rate-limit handling:
L00000626	- on HTTP `429`, read `Retry-After` when present; otherwise use exponential backoff `1s → 2s → 4s`
L00000627	- maximum rate-limit retries = `3`
L00000628	- after the retry limit is exceeded, fail the attempt with `failure_class: rate_limited`
L00000629	
L00000630	Token/budget handling:
L00000631	- if the model hits its output token limit during streaming, the response ends normally with `completion_reason: length`
L00000632	- if PM budget enforcement triggers mid-stream, PM terminates the stream, keeps the partial response, and marks `completion_reason: budget_exceeded`
L00000633	
L00000634	ContractRef: ContractName:Plans/Executor_Protocol.md, ContractName:Plans/Contracts_V0.md, ContractName:Plans/storage-plan.md

L00000683	## OpenCode Runtime Retry / Blocked-State / Packet Canonical Alignment (2026-03-09)
L00000684	
L00000685	
L00000686	OpenCode-specific runtime behavior must remain aligned with the canonical runtime scheduler, retry taxonomy, safe-point contract, remediation lineage, runtime packet, and usage pipeline.
L00000687	
L00000688	### Required OpenCode runtime fields
L00000689	
L00000690	Each OpenCode-backed attempt MUST preserve the shared runtime identity and correlation bundle:
L00000691	- `run_id`
L00000692	- `thread_id`
L00000693	- `node_id`
L00000694	- `attempt_id`
L00000695	- `retry_count` when present
L00000696	- requested/effective model identifiers
L00000697	- requested/effective permission snapshot identifiers when relevant
L00000698	- `replan_generation`
L00000699	- `mutation_capable`
L00000700	- `safe_point_id?`
L00000701	- `remediation_root_id?`
L00000702	- `remediation_parent_attempt_id?`
L00000703	- `remediation_generation?`
L00000704	
L00000705	If a field is not transmitted directly to an OpenCode HTTP endpoint, the adapter MUST still preserve it in local correlation state and attach it to normalized provider events, storage records, and retry/recovery decisions.
L00000706	
L00000707	### Required rules
L00000708	- preserve canonical runtime identity (`run_id`, `thread_id`, `node_id`, `attempt_id`, generation, snapshot ids, safe point, and remediation lineage) across the request/stream lifecycle
L00000709	- OpenCode transport reconnect logic may reconnect only to observe an existing attempt; it MUST NOT silently resubmit prompts, reset attempt identity, or invent provider-local fallback loops
L00000710	- once a prompt/request has been accepted for execution, any retry decision MUST round-trip through the canonical runtime scheduler and failure taxonomy
L00000711	- OpenCode-specific auth, transient, structured-output, and tool-denial signals MUST normalize into canonical `blocked_reason_code` / `failure_class` values before orchestration or UI consumes them
L00000712	- prerequisite resolution after auth or permission recovery MUST surface a canonical scheduler wake and create a new attempt snapshot rather than mutating the blocked attempt in place
L00000713	- a `safe_point_id` created before a mutation-capable OpenCode attempt remains attached across the entire request/stream lifecycle
L00000714	- recovery restores that rerun work use a new `attempt_id` while preserving lineage references to the restored parent context
L00000715	- replan invalidation MUST be checked before rerunning a blocked or retried OpenCode attempt; stale attempts from an older `replan_generation` must not resume silently
L00000716	- any OpenCode-local retry wording is superseded by canonical runtime retry ownership
L00000717	
L00000718	### Canonical failure and blocked mapping
L00000719	
L00000720	OpenCode-specific signals MUST collapse into the shared runtime taxonomy before they reach orchestration or UI layers.
L00000721	
L00000722	| OpenCode / server condition | Canonical runtime classification | Required behavior |
L00000723	|---|---|---|
L00000724	| `401` / invalid server credentials / server auth expiry for the OpenCode server realm | `blocked_reason_code = auth_expired` (server realm) | Surface blocked recovery; require credential refresh before explicit retry |
L00000725	| Upstream provider auth challenge or expired provider session reported by OpenCode | `blocked_reason_code = auth_expired` (provider realm) | Preserve blocked node/thread state and wait for auth recovery |
L00000726	| Timeout, connection refused, transient SSE disconnect after submission, HTTP 5xx, provider outage, or rate limiting | `failure_class = provider_transient` | Runtime retry/backoff policy applies; no OpenCode-local retry policy may override it |
L00000727	| Malformed structured output, missing required JSON shape, or incomplete normalized tool payload | `failure_class = structured_output_invalid` | Route into structured-output remediation / retry policy |
L00000728	| Tool-policy refusal, permission denial, FileSafe denial, or external side-effect approval block surfaced through OpenCode-mediated work | Preserve the already-determined canonical runtime class (`permission_denied`, `filesafe_blocked`, `external_side_effect_blocked`, etc.) | The adapter MUST NOT collapse these to generic `error` or `provider_failed` |
L00000729	
L00000730	### Capability and usage alignment
L00000731	
L00000732	OpenCode capability reporting MUST stay consistent with the shared provider contract.
L00000733	
L00000734	Required declarations:
L00000735	- transport class = server-bridged HTTP/SSE
L00000736	- supports streaming normalized events
L00000737	- supports tool use only through the canonical tool-policy snapshot
L00000738	- uses split auth realms (server credentials vs upstream provider auth)
L00000739	- performs no hidden runtime retries
L00000740	
L00000741	If OpenCode or the selected upstream model does not support a requested runtime control, Puppet Master MUST record the control as unsupported/skipped in effective runtime state rather than silently ignoring it.
L00000742	
L00000743	**Usage and Ledger alignment:** OpenCode server returns message-level usage; the adapter maps it to normalized usage (same shape as `usage.event`). Persistence and Ledger/Usage consumption follow `Plans/storage-plan.md` and `Plans/usage-feature.md`. For implementers, the OpenCode product pipeline (`Session.getUsage`, processor finish-step) is the reference for how message metadata becomes stored usage; terminology should not drift.
