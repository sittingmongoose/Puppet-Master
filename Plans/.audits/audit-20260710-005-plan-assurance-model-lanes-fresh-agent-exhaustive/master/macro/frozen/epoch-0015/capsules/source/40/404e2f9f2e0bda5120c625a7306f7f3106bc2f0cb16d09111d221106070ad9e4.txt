L00002726

L00002730	- a FileSafe block becomes `blocked_reason_code = filesafe_blocked`

L00002733	### 2. Recovery options
L00002734	
L00002735	When FileSafe allows user recovery, runtime/UI surfaces must expose exact options.
L00002736	- Align `tool.denied` emission with the normalized `filesafe_blocked` outcome taxonomy so guard events and terminal outcomes tell the same story.
L00002737	- Blocked-state payloads use `blocked_reason_code`, ordered `allowed_action_ids[]`, `blocked_sequence`, `preserved-local-work`, prerequisite metadata, and `detail_ref?`; deprecated field names such as `allowed_actions[]` and `blocked_reason` must not appear in new canonical schemas.
L00002738	- Graph-local `Retry/Replan/Reopen/Approve/Deny` and `/Replan/Reopen/Approve/Deny` labels normalize to canonical `cmd.runtime` / `cmd.runtime.*` recovery commands before display or persistence.

L00002805	Shared runtime action IDs remain the canonical recovery families. L00002814	### Restore override
L00002815	`filesafe_blocked` is not retryable by default.
L00002816	
L00002817	If a mutation-capable attempt performed local changes before the FileSafe block was finalized, the blocked projection MUST expose:
L00002818	- `preserved_local_work = true`
L00002819	- `requires_safe_point_restore = true`
L00002820	
L00002821	When `requires_safe_point_restore = true`, the only legal rerun path is `restore_safe_point_then_retry`.

L00002823	### Persistence
L00002824	A FileSafe block is a persistent blocked runtime episode until resolved or superseded.
L00002825	
L00002826	Context-shaping and handoff rule:
L00002827	- FileSafe does not define alternate child continuity or alternate memory behavior.
L00002828	- any rerun or restore after FileSafe denial uses canonical handoff reconstruction.
