L00000038	## 1. Definitions
L00000039	
L00000040	<a id="DEF-PLUGIN"></a>
L00000041	### 1.1 Plugin
L00000042	
L00000043	A **Plugin** is a self-contained extension module that hooks into the Puppet Master lifecycle via a defined set of events. A plugin is loaded once at session start (or when first discovered) and remains active for the session duration. Plugins MAY register custom tools, modify prompts, intercept tool execution, and inject context during compaction.
L00000044	
L00000045	<a id="DEF-HOOK"></a>
L00000046	### 1.2 Hook
L00000047	
L00000048	A **Hook** is a named callback registered by a plugin for a specific lifecycle event. When the event fires, all registered hooks are invoked in deterministic order (§3.3). A hook receives a typed context object and returns a result that may continue, modify, or block the pipeline.
L00000049	
L00000050	ContractRef: ContractName:Plans/Glossary.md, ContractName:Plans/Tools.md

L00000054	## 2. Discovery and storage
L00000055	
L00000056	<a id="DISCOVERY"></a>
L00000057	
L00000058	### 2.1 Discovery paths
L00000059	
L00000060	Plugins are discovered from three sources in strict order:
L00000061	
L00000062	| Priority | Source | Path / Config |
L00000063	|----------|--------|---------------|
L00000064	| 1 (first) | **Internal plugins** | Compiled into the Puppet Master binary (e.g., auth adapters). Not user-editable. |
L00000065	| 2 | **Project-local** | `.puppet-master/plugins/<plugin_id>/` in the active project root. |
L00000066	| 3 | **Global** | `~/.config/puppet-master/plugins/<plugin_id>/` |
L00000067	| 4 (last) | **Config package list** | `config.plugins[]` — package specifiers or `file://` local paths. |
L00000068	
L00000069	ContractRef: PolicyRule:Decision_Policy.md§2
L00000070	
L00000071	### 2.2 Plugin manifest
L00000072	
L00000073	Each plugin directory MUST contain a `plugin.json` manifest:
L00000074	
L00000075	```json
L00000076	{
L00000077	  "id": "my-plugin",
L00000078	  "name": "My Plugin",
L00000079	  "version": "0.1.0",
L00000080	  "description": "Short description of what this plugin does.",
L00000081	  "hooks": ["tool.execute.before", "tool.execute.after"],
L00000082	  "tools": ["my-custom-tool"],
L00000083	  "entry": "plugin.wasm"
L00000084	}
L00000085	```
L00000086	
L00000087	| Field | Required | Type | Description |
L00000088	|-------|----------|------|-------------|
L00000089	| `id` | **Required** | `string` | Unique plugin ID. Regex: `^[a-z][a-z0-9-]{1,48}[a-z0-9]$`. MUST match directory name. |
L00000090	| `name` | **Required** | `string` | Human-readable display name. Max 100 characters. |
L00000091	| `version` | **Required** | `string` | Semver version string. |
L00000092	| `description` | **Required** | `string` | Max 500 characters. |
L00000093	| `hooks` | Recommended | `string[]` | List of hook event names this plugin subscribes to (from §4). |
L00000094	| `tools` | Optional | `string[]` | List of custom tool names this plugin registers (§6). |
L00000095	| `entry` | **Required** | `string` | Relative path to the plugin entry point (WASM module, subprocess-based entry, or dynamic library). JavaScript/TypeScript/Bun entries are OpenCode compatibility evidence only and are not a Puppet Master runtime dependency. |
L00000096	
L00000097	ContractRef: ContractName:Plans/Plugins_System.md#DISCOVERY
L00000098	
L00000099	### 2.3 Deduplication
L00000100	
L00000101	If the same `id` appears in multiple sources, the **first-discovered instance wins** (by priority order in §2.1). Later duplicates are skipped and a warning is logged.

L00000105	## 3. Load order and execution model
L00000106	
L00000107	### 3.1 Auto-load prohibition
L00000108	
L00000109	PM MUST NOT auto-load executable plugin code from config without explicit user approval. This is the plugin no-auto-load executable-code rule.
L00000110	
L00000111	ContractRef: ContractName:Plans/Permissions_System.md, ContractName:Plans/Architecture_Invariants.md
L00000112	
L00000113	Required behavior:
L00000114	- first-time plugin load shows source, declared hooks, requested capabilities, and trust implications
L00000115	- approval is version/hash-sensitive; source change requires new approval
L00000116	- config-only discovery does not imply execution approval
L00000117	
L00000118	ContractRef: ContractName:Plans/FinalGUISpec.md, ContractName:Plans/storage-plan.md
L00000119	
L00000120	### 3.2 Deterministic load order
L00000121	
L00000122	Plugins are loaded in strict priority order (§2.1). Within a single source (e.g., project-local), plugins are loaded in lexicographic order by `id`.
L00000123	
L00000124	Rule: Given the same set of plugins on disk and in config, the load order MUST be identical across runs.
L00000125	
L00000126	ContractRef: PolicyRule:Decision_Policy.md§3
L00000127	
L00000128	### 3.2 Plugin lifecycle
L00000129	
L00000130	1. **Discover:** Walk discovery paths (§2.1); collect valid manifests.
L00000131	2. **Validate:** Parse `plugin.json`; reject plugins with invalid manifests (log warning, skip).
L00000132	3. **Initialize:** Load the entry module; pass a `PluginContext` object (§3.4). The plugin registers hooks and custom tools.
L00000133	4. **Active:** Hooks are invoked throughout the session.
L00000134	5. **Teardown:** On session end, a `session.end` event fires; plugins perform cleanup. Puppet Master then unloads plugins.
L00000135	
L00000136	### 3.3 Hook execution order
L00000137	
L00000138	<a id="HOOK-EXECUTION-ORDER"></a>
L00000139	
L00000140	When an event fires, all registered hooks for that event are invoked in **plugin load order** (§3.1). Within a single plugin, if multiple handlers exist for the same event, they execute in registration order.
L00000141	
L00000142	Rule: Hook execution order MUST be deterministic. Internal plugins execute first, then project-local, then global, then config-sourced.
L00000143	
L00000144	ContractRef: ContractName:Plans/Plugins_System.md#LOAD-ORDER
L00000145	
L00000146	### 3.4 Plugin context object
L00000147	
L00000148	<a id="PLUGIN-CONTEXT"></a>
L00000149	
L00000150	When a plugin is initialized, it receives a `PluginContext`:
L00000151	
L00000152	```
L00000153	PluginContext {
L00000154	  project_root: Option<PathBuf>,       // Active project root (None if no project)
L00000155	  global_config_dir: PathBuf,          // ~/.config/puppet-master/
L00000156	  plugin_data_dir: PathBuf,            // Per-plugin persistent storage dir
L00000157	  register_hook: fn(event, handler),   // Register a hook callback
L00000158	  register_tool: fn(tool_def),         // Register a custom tool (§6)
L00000159	  log: fn(level, message),             // Structured log emitter (§8)
L00000160	}
L00000161	```
L00000162	
L00000163	The `PluginContext` is the sole API surface for plugins. Plugins MUST NOT access Puppet Master internals outside this interface.
L00000164	
L00000165	ContractRef: ContractName:Plans/OpenCode_Deep_Extraction.md
L00000166

L00000169	## 4. Hook events
L00000170	
L00000171	<a id="HOOK-EVENTS"></a>
L00000172	
L00000173	The following hook events are defined. Each event specifies its input shape and the allowed return actions.
L00000174	
L00000175	Rule: Every hook event MUST be listed in this table. New events require an update to this document.
L00000176	
L00000177	ContractRef: PolicyRule:Decision_Policy.md§2, ContractName:Plans/Tools.md
L00000178	
L00000179	### 4.1 Tool execution hooks
L00000180	
L00000181	#### 4.1.1 Hook re-check invariant
L00000182	
L00000183	If a plugin hook modifies tool arguments, the modified arguments MUST be re-run through permission and validation checks before dispatch. Hooks may not widen permissions after the original check has passed.
L00000184	
L00000185	ContractRef: ContractName:Plans/Permissions_System.md, ContractName:Plans/Architecture_Invariants.md
L00000186	
L00000187	Required sequence:
L00000188	1. evaluate permission/validation on original arguments
L00000189	2. run arg-touching hook
L00000190	3. re-run permission/validation on modified arguments
L00000191	4. dispatch only if the re-check passes
L00000192	
L00000193	ContractRef: ContractName:Plans/Tools.md, ContractName:Plans/Executor_Protocol.md
L00000194	
L00000195	Plugins that declare arg-touching hooks require a higher-trust approval posture (signed or explicitly `/approved` elevated approval) than read-only hooks.
L00000196	
L00000197	ContractRef: ContractName:Plans/Architecture_Invariants.md, ContractName:Plans/FinalGUISpec.md
L00000198	
L00000199	#### 4.1.2 Signed verification for arg-touching hooks
L00000200	
L00000201	Plugins that declare arg-touching hooks MUST be signed or explicitly approved at a higher trust level than read-only hooks. This is because arg-touching hooks can be used to inject malicious arguments after permission checks.
L00000202	
L00000203	ContractRef: ContractName:Plans/Permissions_System.md, ContractName:Plans/Architecture_Invariants.md
L00000204	
L00000205	
L00000206	<a id="HOOK-TOOL-EXECUTE"></a>
L00000207	
L00000208	#### `tool.execute.before`
L00000209	
L00000210	| Field | Value |
L00000211	|-------|-------|
L00000212	| **Fires** | Before a tool invocation is executed (after permission check passes). |
L00000213	| **Input** | `{ tool_name: String, args: Value, invocation_id: String }` |
L00000214	| **Returns** | `Continue` (proceed), `Continue(modified_args)` (proceed with changed args), or `Block(reason)` (abort tool call with reason). |
L00000215	
L00000216	#### `tool.execute.after`
L00000217	
L00000218	
L00000219	| Field | Value |
L00000220	|-------|-------|
L00000221	| **Fires** | After a tool invocation completes (success or error). |
L00000222	| **Input** | `{ tool_name: String, args: Value, result: ToolResult, invocation_id: String, duration_ms: u64 }` |
L00000223	| **Returns** | `Continue` (pass result through), or `Continue(modified_result)` (return modified result to the agent). |
L00000224	
L00000225	ContractRef: ContractName:Plans/Tools.md, ContractName:Plans/Contracts_V0.md#EventRecord
L00000226	
L00000227	### 4.2 Permission hooks

L00000229	<a id="HOOK-PERMISSION"></a>

L00000232	
L00000233	| Field | Value |
L00000234	|-------|-------|
L00000235	| **Fires** | When the permission engine resolves a tool invocation to `ask` (before presenting to user). |
L00000236	| **Input** | `{ tool_name: String, args: Value, resolved_action: "ask" }` |
L00000237	| **Returns** | `Continue` (present ask UI), `Allow` (auto-approve), or `Deny(reason)`. |
L00000238	
L00000239	Rule: Plugin overrides of permission decisions MUST be logged to the event ledger as `plugin.permission.override` events.

L00000321	## 5. Hook return semantics
L00000322	
L00000323	<a id="HOOK-RETURNS"></a>
L00000324	
L00000325	All hooks return one of the following actions:
L00000326	
L00000327	| Action | Meaning |
L00000328	|--------|---------|
L00000329	| `Continue` | Proceed with the pipeline unchanged. |
L00000330	| `Continue(modified)` | Proceed with the modified payload. The next hook in the chain receives the modified version. |
L00000331	| `Block(reason)` | Abort the pipeline. Only applicable to `tool.execute.before`. The reason is returned to the agent as an error. |
L00000332	| `Allow` | Auto-approve (only for `permission.ask`). |
L00000333	| `Deny(reason)` | Auto-deny (only for `permission.ask`). |
L00000334	| `InjectContext(items)` | Append context items (only for `session.compacting`). |
L00000335	| `ReplacePrompt(prompt)` | Replace compaction prompt (only for `session.compacting`). |
L00000336	
L00000337	Rule: If a hook raises an unhandled error (panic, timeout), it is treated as `Continue` and a warning is logged. Default hook timeout: 5 seconds (configurable via `config.plugins.hook_timeout_ms`, default `5000`).
L00000338	
L00000339	ContractRef: PolicyRule:Decision_Policy.md§2

L00000343	## 6. Custom tool registration
L00000344	
L00000345	<a id="CUSTOM-TOOLS"></a>
L00000346	
L00000347	### 6.1 Registration
L00000348	
L00000349	Plugins MAY register custom tools via `PluginContext.register_tool(tool_def)`. The `tool_def` includes:
L00000350	
L00000351	```
L00000352	ToolDefinition {
L00000353	  name: String,                        // Tool name (validated per Plans/Tools.md §3)
L00000354	  description: String,                 // Tool description shown to agents
L00000355	  input_schema: Value,                 // JSON Schema for tool input
L00000356	  execute: fn(args: Value) -> Result<ToolResult>,  // Execution handler
L00000357	}
L00000358	```
L00000359	
L00000360	### 6.2 Name collision behavior
L00000361	
L00000362	<a id="TOOL-COLLISION"></a>
L00000363	
L00000364	Rule: When a plugin registers a tool whose name collides with a built-in tool, the **built-in tool takes precedence** by default. The plugin tool is registered under a namespaced alias: `<plugin_id>.<tool_name>` (e.g., `my-plugin.read`).
L00000365	
L00000366	A config flag `config.plugins.allow_tool_override` (default `false`) MAY be set to `true` to allow plugin tools to override built-in tools. When enabled, plugin tools registered later in load order override earlier ones.
L00000367	
L00000368	ContractRef: ContractName:Plans/Tools.md
L00000369	
L00000370	### 6.3 Central registry routing
L00000371	
L00000372	All plugin-registered tools are added to the central tool registry (`Plans/Tools.md`). They are subject to the same permission policy engine (`Plans/Permissions_System.md`). Unknown tools default to `ask` permission.
L00000373	
L00000374	ContractRef: ContractName:Plans/Tools.md, ContractName:Plans/Permissions_System.md#DEFAULTS
L00000375	
L00000376	### 6.4 Core-surface /extensibility and host-policy boundaries
L00000377	
L00000378	Plugin-added subviews/cards/actions (`/cards/actions`) may extend core surfaces, but they MUST NOT replace reserved surface IDs, panel routes, command-family meaning, or deep-link target meaning. Plugin-added navigation into core surfaces must use the canonical context payloads owned by the target surface.
L00000379	
L00000380	Plugin-added tools, hooks, MCP bridges, and other `/extensibility` capabilities that contact external hosts, registry hosts, or Kubernetes clusters must declare contacted domains/hosts before execution. They inherit `registry_hosts[]`, `k8s_host_policy`, `/network/trust`, proxy, and permission policy checks before dispatch; policy denial uses canonical host-policy blocked reasons and ordered `allowed_action_ids[]`, not plugin-private recovery semantics.
L00000381	
L00000382	Hooks must not silently rewrite protected routing fields, including remote host/base URL, registry host, kube context, namespace, or receipt identity keys. If a plugin hook changes any protected routing field, the modified invocation is revalidated through the permission engine and may be blocked with canonical `/denied` outcomes.
L00000383	
L00000384	ContractRef: ContractName:Plans/Permissions_System.md, ContractName:Plans/Containers_Registry_and_Unraid.md, ContractName:Plans/UI_Command_Catalog.md
L00000385

L00000415	
L00000416	### 7.4 Child-run plugin and MCP inheritance
L00000417	
L00000418	Plugin and MCP effects for child runs are inherited as an effective compatible subset, not as a blind copy of the parent environment.

L00000420	ContractRef: ContractName:Plans/Permissions_System.md, ContractName:Plans/Tools.md, ContractName:Plans/Models_System.md

L00000422	Rules:
L00000423	- child-visible plugin behavior exists only when the child runtime path supports it and the parent effectively allowed it.
L00000424	- plugin behavior must not function as a backdoor that widens child permissions or tool authority.
L00000425	- MCP availability follows the same parent-ceiling and compatibility-subset rule.
L00000426	- requested versus effective dropped capability details should remain visible for debugging.

L00000434	```
L00000435	
L00000436	When a Persona is active, any plugin whose `id` appears in `disabled_plugins` is skipped during hook dispatch (not unloaded, just silenced).

L00000442	## 8. Structured plugin logging
L00000443	
L00000444	<a id="PLUGIN-LOGGING"></a>
L00000445	
L00000446	All plugin activity is logged to the Puppet Master event ledger (`Plans/Contracts_V0.md#EventRecord`).
L00000447	
L00000448	### 8.1 Event types
L00000449	
L00000450	| Event type | When emitted |
L00000451	|------------|-------------|
L00000452	| `plugin.loaded` | Plugin successfully initialized. |
L00000453	| `plugin.load_failed` | Plugin failed to load (invalid manifest, entry error). |
L00000454	| `plugin.hook.invoked` | A hook was called (includes plugin_id, event name, duration_ms). |
L00000455	| `plugin.hook.error` | A hook raised an error or timed out. |
L00000456	| `plugin.hook.blocked` | A hook returned `Block` (includes reason). |
L00000457	| `plugin.permission.override` | A plugin overrode a permission decision (§4.2). |

L00000517	## 10. OpenCode baseline and Puppet Master deltas
L00000518	
L00000519	<a id="BASELINE-DELTAS"></a>
L00000520	
L00000521	Per `Plans/OpenCode_Deep_Extraction.md` §7G and §9G:
L00000522	
L00000523	### 10.1 Baseline
L00000524	
L00000525	OpenCode plugins are JavaScript/TypeScript modules loaded via `import()`. Plugin sources: internal (compiled), built-in npm packages, and config-specified packages/paths. Plugins receive a `PluginInput` with SDK client, project metadata, and Bun shell. The `Hooks` interface defines ~15 named hooks including `tool.execute.before/after`, `permission.ask`, `experimental.session.compacting`, `chat.message`, `chat.params`, `shell.env`, and system/message transforms. Custom tools are registered via the `tool` property; plugin tools override built-ins on name collision.
L00000526	
L00000527	### 10.2 Puppet Master deltas
L00000528	
L00000529	1. **Plugin runtime:** OpenCode uses JS `import()` with Bun. Puppet Master uses a platform-agnostic plugin API (WASM modules, subprocess-based, or dynamic libraries — entry format defined by `plugin.json` `entry` field). No JavaScript runtime dependency.
L00000530	2. **Tool collision policy:** OpenCode allows plugin tools to override built-ins by default. Puppet Master defaults to **namespaced aliasing** (built-in wins); override requires explicit opt-in via `allow_tool_override`.
L00000531	3. **Compaction hook naming and semantics:** OpenCode uses `experimental.session.compacting` as the hook key. Puppet Master canonicalizes this as `session.compacting` (dropping the `experimental.` prefix). For backward compatibility, plugins subscribing to `experimental.session.compacting` are mapped to the canonical `session.compacting` hook at registration time as an alias. Puppet Master additionally formalizes the return semantics with `InjectContext` vs `ReplacePrompt` return types and first-wins conflict resolution for `ReplacePrompt`.
L00000532	4. **Deterministic load order:** OpenCode deduplicates by function identity. Puppet Master defines strict priority-ordered discovery with lexicographic tiebreaking and documents the order for reproducibility.
L00000533	5. **Structured logging:** OpenCode plugin errors are logged but not structured. Puppet Master emits typed ledger events (`plugin.loaded`, `plugin.hook.invoked`, etc.) for auditability.
L00000534	6. **Per-Persona overrides:** OpenCode has no per-agent plugin controls. Puppet Master allows Personas to disable specific plugins via `disabled_plugins`.
L00000535	7. **CLI-backed provider plugin capability evidence:** When the `claude` local binary is used as a CLI-bridged provider, PM records native agents, effort selection, model selection, fallback model support, MCP, plugins, settings injection, and headless JSON/stream-json output as observed provider-protocol capability evidence; plugin support remains capability-scoped and does not imply every provider account can load PM plugins.
L00000536
