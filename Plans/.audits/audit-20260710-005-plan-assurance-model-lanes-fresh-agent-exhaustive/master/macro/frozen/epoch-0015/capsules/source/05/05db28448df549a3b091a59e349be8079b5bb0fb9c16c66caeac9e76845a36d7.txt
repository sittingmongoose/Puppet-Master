L00000102	### P0 fail-closed security resolution (2026-07-07)
L00000103	
L00000104	This section is the active FileSafe security decision for FABLE `fable-20260706-p0-filesafe-fail-open-and-allowlist-security`. Earlier examples that appear to disable guards, match approved commands by prefix, treat empty allowlists as warn-only, or make `PUPPET_MASTER_ALLOW_DESTRUCTIVE=1` sufficient authority are retired source-lineage only unless this section explicitly restates them as live behavior.
L00000105	
L00000106	Canonical requirements:
L00000107	- FileSafe, BashGuard, FileGuard, and SecurityFilter initialization failures fail closed. The affected startup/runtime path blocks guarded command execution, file mutation, and sensitive-file access until the diagnostic is resolved.
L00000108	- Disabled guard states are valid only for explicit, authenticated, auditable operator configuration that narrows or intentionally suspends one named guard for a scoped run/project/worktree duration. Initialization failure must never create a disabled guard.
L00000109	- Approved command matching is exact after normalization. Normalization trims leading/trailing whitespace, collapses internal ASCII whitespace runs to one space, preserves token order and shell metacharacters, and does not split or concatenate authorization across command segments.
L00000110	- Command identity is the whole normalized segment that would be dispatched after policy expansion and before spawn. For multi-line or chained invocations using newline, `&&`, `;`, `||`, or `|`, each dispatch segment is normalized and checked independently; the invocation is allowed only if every segment is independently allowed and none is blocked. An approval for `git status` does not approve `git status && rm -rf /`.
L00000111	- Prefix, substring, `starts_with`, shell-fragment, fuzzy, prompt-expanded, and concatenated-command approval are forbidden. Mismatches emit `filesafe.command_denied` with `denial_code = approved_command_identity_mismatch`.
L00000112	- Missing or empty command/path allowlists fail closed whenever the corresponding guard is enabled. `strict_mode=false` can soften non-authoritative advisory reporting only after a safe enforcement baseline is present; it cannot permit writes, reads, or commands when the authoritative allowlist, baseline, root, or guard input is absent.
L00000113	- `PUPPET_MASTER_ALLOW_DESTRUCTIVE=1` is only a request signal. It is not sufficient authority by itself. A destructive override requires an authenticated operator grant with auth realm, operator identity, reason, scope, duration/expiry, project/run/worktree binding, and an emitted security event and receipt before any destructive command can run.
L00000114	- Prompt/free-text command or path extraction is never the sole enforcement boundary. Structured tool arguments, final command segments, and resolved path scopes remain mandatory checks.
L00000115	- Source-lineage snippets that preserve old fail-open, prefix-match, or disabled-fallback examples must be explicitly fenced as retired/noncanonical and must include a copy-prevention note saying they are not implementation guidance.

L00000134	## 1. Architecture Overview
L00000135	
L00000136	### 1.1 Three-Layer Defense
L00000137	
L00000138	| Layer | Type | When It Fires | Reliability |
L00000139	|-------|------|---------------|-------------|
L00000140	| **Pre-execution guard** | Rust module | Before every Bash/command call | Deterministic (regex match) |
L00000141	| **Agent prompt rules** | Behavioral guidance | When agent reads instructions | Probabilistic (model compliance) |
L00000142	| **Post-execution audit** | Event log check | After command execution | Deterministic but reactive |
L00000143	
L00000144	**Layer 1 is the fix.** It blocks destructive commands before they execute, regardless of what the model decides to do.
L00000145	
L00000146	### 1.1A Runtime and GUI configuration boundary
L00000147	
L00000148	FileSafe GUI configuration recomputes predicted requested/effective state for effective-runtime interactions when the user changes provider/account/model/threshold/effort settings, preserving the `/account/model/threshold/effort` context instead of showing stale state.
L00000149	
L00000150	Configuration rendering keeps `inherit/override`, `requested/effective`, and provider `honored/skipped/clamped` states visually distinct; `/override`, `/effective`, and `/skipped/clamped` labels must not be collapsed into one toggle state.
L00000151	
L00000152	Runtime snapshots may include `/model/auth/account` credentials, but FileSafe also records non-provider operational identities when write-scope, prompt-safety, or recovery behavior depends on the account, instruction bundle, runtime binding, lane, or policy layer that sits beside those credentials.
L00000153	
L00000154	Model and provider enforcement is lane-aware: e.g., a Security Lane may require a specific model from `Plans/Models_System.md` (`/Models_System.md`) before FileSafe allows execution.
L00000155	
L00000156	Identity normalization for `provider_account_id` is cross-doc; FileSafe consumes the shared identity contract instead of minting local provider/account IDs for guard logs or runtime snapshots.
L00000157	
L00000158	Execution correlation must not drift back to tier-era labels: `tier_id` is human-readable grouping metadata only, and treating it as a canonical execution key is surface-drift.
L00000159	
L00000160	Worktree strategy is resolved by `Plans/WorktreeGitImprovement.md`: source labels such as `chain-wizard-flexibility` / `chain-wizard-flexibility.md`, explicit `no-worktrees`, and per-subtask worktrees cannot override FileSafe's guard-visible isolation contract.
L00000161	
L00000162	FileSafe write scope is multi-node and role-specific: sharded node scopes under `puppet-master/project/plan_graph/` and `/project/plan_graph/` map by `/Task/Subtask/Iteration`, active node/work package, and allowed-file metadata rather than one monolithic `puppet-master` plan file.
L00000163	
L00000164	Agent-Config shell ownership remains in `Plans/FinalGUISpec.md`, but FileSafe configuration must carry the fuller `/account/instruction/runtime` contract when write-scope or prompt-safety decisions depend on account, instruction bundle, or runtime binding.
L00000165	
L00000166	provider-specific divergence requires an explicit `Manual Override` toggle before FileSafe allows behavior that departs from the shared state model. provider-specific GUI wording/flows are reconciliation cleanup against the now-frozen account/runtime model, not a reason to fork FileSafe policy.

L00000482	// FileSafe pattern-loading helper example
L00000483	
L00000484	use regex::Regex;
L00000485	use std::fs;
L00000486	use std::path::Path;
L00000487	use anyhow::{Context, Result};
L00000488	
L00000489	// DRY:FN:load_patterns — Load destructive command patterns from file
L00000490	/// Load destructive command patterns from file
L00000491	///
L00000492	/// # File Format
L00000493	///
L00000494	/// - One regex pattern per line
L00000495	/// - Lines starting with `#` are comments (ignored)
L00000496	/// - Empty lines are ignored
L00000497	/// - Patterns are case-insensitive (automatically prefixed with `(?i)`)
L00000498	/// - Patterns match against the full command string
L00000499	///
L00000500	/// # Examples
L00000501	///
L00000502	/// ```
L00000503	/// # PHP / Laravel
L00000504	/// artisan\s+migrate:(fresh|reset|refresh)
L00000505	/// artisan\s+db:(wipe|seed\s+--force)
L00000506	/// ```
L00000507	///
L00000508	/// # Errors
L00000509	///
L00000510	/// - Returns error if file cannot be read
L00000511	/// - Returns error if any pattern is invalid regex
L00000512	/// - Invalid patterns stop loading (fail-fast)
L00000513	pub fn load_patterns(pattern_file: &Path) -> Result<Vec<Regex>> {
L00000514	    let content = fs::read_to_string(pattern_file)
L00000515	        .with_context(|| format!("Failed to read pattern file: {}", pattern_file.display()))?;
L00000516	    
L00000517	    let mut patterns = Vec::new();
L00000518	    let mut line_number = 0;
L00000519	    
L00000520	    for line in content.lines() {
L00000521	        line_number += 1;
L00000522	        let line = line.trim();
L00000523	        
L00000524	        // Skip comments and empty lines
L00000525	        if line.is_empty() || line.starts_with('#') {
L00000526	            continue;
L00000527	        }
L00000528	        
L00000529	        // Compile regex (case-insensitive)
L00000530	        // Note: Some patterns may already include (?i), but adding it again is safe (no-op)
L00000531	        let pattern = if line.starts_with("(?i)") {
L00000532	            line.to_string()
L00000533	        } else {
L00000534	            format!("(?i){}", line)
L00000535	        };
L00000536	        
L00000537	        match Regex::new(&pattern) {
L00000538	            Ok(regex) => patterns.push(regex),
L00000539	            Err(e) => {
L00000540	                return Err(anyhow!(
L00000541	                    "Invalid regex pattern at line {} in {}: {}\nPattern: {}",
L00000542	                    line_number,
L00000543	                    pattern_file.display(),
L00000544	                    e,
L00000545	                    line
L00000546	                ));
L00000547	            }
L00000548	        }
L00000549	    }
L00000550	    
L00000551	    if patterns.is_empty() {
L00000552	        warn!("No patterns loaded from {}", pattern_file.display());
L00000553	    } else {
L00000554	        info!("Loaded {} patterns from {}", patterns.len(), pattern_file.display());
L00000555	    }
L00000556	    
L00000557	    Ok(patterns)
L00000558	}
L00000559	
L00000560	// DRY:FN:load_patterns_with_merge — Load patterns from multiple files and merge
L00000561	/// Load patterns from multiple files and merge them
L00000562	///
L00000563	/// # Arguments
L00000564	///
L00000565	/// * `default_file` - Default/bundled pattern file (required)
L00000566	/// * `local_file` - Project-specific pattern file (optional)
L00000567	///
L00000568	/// # Behavior
L00000569	///
L00000570	/// - Loads default patterns first
L00000571	/// - If local file exists, loads and appends local patterns
L00000572	/// - Duplicate patterns are kept (no deduplication)
L00000573	/// - Returns combined vector
L00000574	pub fn load_patterns_with_merge(
L00000575	    default_file: &Path,
L00000576	    local_file: Option<&Path>,
L00000577	) -> Result<Vec<Regex>> {
L00000578	    let mut patterns = load_patterns(default_file)?;
L00000579	    
L00000580	    if let Some(local) = local_file {
L00000581	        if local.exists() {
L00000582	            let local_patterns = load_patterns(local)
L00000583	                .context("Failed to load local patterns")?;
L00000584	            patterns.extend(local_patterns);
L00000585	            info!("Merged {} local patterns", local_patterns.len());
L00000586	        }
L00000587	    }
L00000588	    
L00000589	    Ok(patterns)
L00000590	}

L00000910	- Non-JSON `codex exec` exposes `session id`, selected model `/provider/effort`, and a final `tokens used` summary; FileSafe may record those values as execution metadata but must not treat them as authorization by themselves.
L00000911	- provider-specific proxy/plugin patterns may support session-stickiness and quota-aware selection, but `/plugin` projection remains subordinate to FileSafe's PM-owned command/path checks.
L00000912	- `provider_usage_source_kind?` and `provider_signal_confidence?` may annotate provider-discovery evidence quality only as compatibility/evidence-signal aliases. They normalize to `source_class`, `source_confidence`, and `source_authority` before UsageRecord persistence, accounting, GUI display, rollups, or runtime-artifact projection, and they must not become FileSafe permission authority, accounting authority, live overlay policy, or full projection details in every runtime snapshot.
L00000913	
L00000914	**Strategy:** 
L00000915	1. Check **compiled prompt** (after context compilation) at platform runner level
L00000916	2. Check **command string** (final CLI command) at BaseRunner level
L00000917	3. Check **context files** (security filter) at platform runner level
L00000918	4. Check **file paths** (write scope + security filter) at BaseRunner level
L00000919	
L00000920	This provides defense-in-depth: multiple checks at different stages of execution.

L00001379	## 10a. FileSafe and Assistant YOLO mode
L00001380	
L00001381	**Context:** In Assistant chat (see **Plans/assistant-chat-design.md** §3), **YOLO mode** means the agent runs with maximum permissions: no permission prompts. The user accepts full automation for that session; the agent can execute, edit, and run tools without asking.
L00001382	
L00001383	**Implication for FileSafe:** When YOLO is on, there is **no human approval step** before tool execution. FileSafe is therefore the **primary protection layer** for Assistant chat in YOLO mode. If FileSafe is disabled or relaxed while YOLO is on, destructive commands and out-of-scope writes can run with no further gate.
L00001384	
L00001385	**Requirements:**
L00001386	
L00001387	1. **Same FileSafe config for Assistant:** Assistant chat (and thus YOLO runs) must use the same FileSafe settings as the rest of the app (Command blocklist, Write scope, Security filter). No separate "Assistant-only" bypass unless explicitly configured.
L00001388	2. **Recommend FileSafe on when YOLO is on:** When the user enables YOLO for a chat, the GUI should recommend (or warn) that FileSafe remain enabled. Options: show a one-time hint ("FileSafe protects you when YOLO is on"), or a small indicator that FileSafe is active when YOLO is selected.
L00001389	3. **Configurable and visible:** FileSafe toggles must be easy to find and turn on/off (see §13.4 and §15.5). A user who turns on YOLO should be able to confirm FileSafe state without digging through multiple screens.
L00001390	4. **Optional: per-context override:** If product requirements later allow "relax FileSafe for this chat only" (e.g. power users), that must be an explicit, clearly labeled setting--not the default when YOLO is on.
L00001391	
L00001392	**Summary:** YOLO mode and FileSafe are complementary: YOLO removes approval prompts; FileSafe enforces hard limits (destructive commands, write scope, sensitive files). FileSafe settings must be configurable in the GUI and easy to turn on or off, and when Assistant runs in YOLO mode, FileSafe should be the main line of defense.

L00001405	#### 11.1.1 Realpath-before-scope-check invariant
L00001406	
L00001407	All file paths submitted to FileSafe write-scope or security-filter checks MUST be resolved through `realpath()` before any scope comparison.
L00001408	
L00001409	ContractRef: ContractName:Plans/Permissions_System.md, ContractName:Plans/Architecture_Invariants.md

L00001411	Required behavior:

L00001415	- non-existent target paths for create operations resolve by canonicalizing the nearest existing parent directory with `realpath()`, then appending exactly one normalized final path segment; if the parent is missing, crosses a symlink boundary, fails permission checks, or case/collision checks are ambiguous, deny access
L00001416	- never fall back to comparing the unresolved path against `allowed_files`
L00001417	- re-run canonicalization and scope/security comparison immediately before mutation, open, spawn, or promote; any drift between initial check and pre-dispatch/pre-rename recheck is a TOCTOU failure and emits `filesafe.path_denied` with `denial_code = path_toc_tou_recheck_failed`

L00001426

L00001434	- if backup creation or backup-metadata persistence fails, the mutation fails closed before the target path is modified

L00001448	
L00001449	All mutable FileSafe rewrite paths (plan apply, patch apply, safe auto-fix, context file rewrite, and verification-driven rewrite) MUST follow the same optimistic-concurrency / CAS contract.

L00001482	#### 11.1.3 Case folding and file-record lifecycle
L00001483	
L00001484	FileSafe and permission matching MUST use the same filesystem-awareness for case sensitivity; this closes the OC-FILE-201/202 symlink-scope pair together with the case-fold comparison contract.
L00001485	
L00001486	ContractRef: ContractName:Plans/Permissions_System.md, ContractName:Plans/Executor_Protocol.md
L00001487	
L00001488	Case-sensitivity detection contract:
L00001489	- At project/worktree root initialization, PM probes case sensitivity by creating a temporary probe file (e.g., `.pm_case_probe`) and checking whether the filesystem distinguishes it from `.PM_CASE_PROBE`.
L00001490	- If the probe succeeds (both names resolve to the same inode), the filesystem is case-insensitive.
L00001491	- If the probe cannot be created (read-only filesystem, permission error, or other I/O failure), PM defaults to case-sensitive mode (the stricter assumption).
L00001492	- The detected case-sensitivity flag is cached per project root and reused for all FileSafe and permission path comparisons within that project session.
L00001493	
L00001494	ContractRef: ContractName:Plans/storage-plan.md, ContractName:Plans/Architecture_Invariants.md
L00001495	
L00001496	Normalization rules:
L00001497	- On case-insensitive filesystems: apply Unicode NFC normalization followed by locale-independent lowercasing before path comparison.
L00001498	- On case-sensitive filesystems: compare paths byte-for-byte after NFC normalization only.
L00001499	- The normalization method MUST be identical in FileSafe write-scope checks and Permissions_System path-pattern matching. Divergence between the two is a security defect.
L00001500	- Symlink handling always compares the final canonical real path and the canonical real allowed root, never the lexical alias used in the request.
L00001501	- Non-existent create targets compare the canonical existing parent path plus the normalized final segment and must be rechecked after temp-file creation and immediately before rename/promote.
L00001502	- Case-fold behavior must reject ambiguous sibling collisions, including two directory entries that normalize to the same comparison key on a case-insensitive or Unicode-normalized filesystem.
L00001503	
L00001504	ContractRef: ContractName:Plans/Permissions_System.md, ContractName:Plans/Tools.md
L00001505	
L00001506	In-memory file records are bounded by an LRU cap of 10,000 entries. Eviction rebuilds from canonical event state on next access; it does not silently lose guard correctness.

L00001591	### 11.3 Prompt Content Checking & Context Compilation
L00001592	
L00001593	**Problem:** Agents may include destructive commands in their prompts, not just CLI args. Additionally, context files may contain destructive commands that get compiled into the final prompt.

L00001600	4. **Final Prompt:** The compiled prompt (with context) is sent to platform CLI

L00001612	        prompt.to_string()
L00001613	    } else {

L00001615	    }
L00001616	}
L00001617
