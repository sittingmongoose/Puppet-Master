L00004752	**Gap #28: File locking and concurrent writes**
L00004753	
L00004754	**Issue:** Legacy/source-lineage mirror writers that directly update `active-agents.json` can race, corrupt JSON, or lose updates. Canonical coordination avoids this class by prohibiting read-modify-write on files and admitting updates only through seglog append plus redb projection CAS.
L00004755	
L00004756	**Mitigation:**
L00004757	- **Canonical append/CAS:** Each update appends one coordination EventRecord with an idempotency key and expected agent revision; stale expected revisions fail with a conflict diagnostic.
L00004758	- **Projection transaction:** The coordination projector writes all affected redb rows and the checkpoint in one transaction. It does not advance the checkpoint on partial failure.
L00004759	- **Mirror-only atomic writes:** Optional mirrors use same-directory temp files, fsync, and rename. Mirror failure is a debug/export failure, not a canonical coordination failure.
L00004760	- **No fail-open scheduling:** Lock timeout, mirror write failure, or mirror corruption must never authorize scheduling or execution from stale mirror data.

L00004984	**Gap #31: File operation extraction reliability**
L00004985	
L00004986	**Issue:** Extracting file operations from agent output is unreliable. Agents may mention files they don't edit, or edit files they don't mention. Platform hooks may not fire for all file operations.
L00004987	
L00004988	**Mitigation:**
L00004989	- **Multi-source extraction:** Combine multiple sources: (1) agent output parsing (regex for file paths), (2) platform hooks (`PreToolUse`/`PostToolUse`), (3) provider stream/tool events from CLI output adapters, (4) git diff detection (compare worktree before/after).

L00004991	- **Validation:** After agent completes, validate claimed files against actual git diff. If mismatch, log warning and update coordination state.
L00004992	- **Best-effort updates:** If file extraction fails, still register agent with empty `files_being_edited` list. Coordination context will still show agent is active, just without file details.

L00005054	**Gap #32: Coordination state size limits and performance**
L00005055	
L00005056	**Issue:** If many agents run simultaneously, coordination projections and prompt-injection snapshots can become large. The supported v1 bound is up to 32 active agents across worktrees; above that, admission policy must queue or throttle new child runs.
L00005057

L00005059	- **Size limits:** Limit coordination state to max 100 active agents. If exceeded, prune oldest agents (by `started_at`).

L00005124	**Gap #33: Conflict resolution and file locking**
L00005125	
L00005126	**Issue:** If two agents want to edit the same file, coordination context warns them, but there's no automatic conflict resolution. Agents may ignore warnings or both proceed, causing merge conflicts.

L00005422	### Parallel Execution Configuration
L00005423	
L00005424	**Concurrency caps rationale:** Per-platform concurrency limits exist for two reasons:
L00005425	
L00005426	1. **Provider rate limits:** Each platform (Cursor, Codex, Claude Code, Gemini, Copilot) enforces rate limits on concurrent requests. Exceeding them causes throttling, errors, or temporary bans.
L00005427	2. **Dev-machine load:** Agent processes consume CPU, disk I/O, and memory on the machine hosting the project folder. Running too many concurrent processes degrades the user's development environment.
L00005428	
L00005429	**Source of caps:** The canonical concurrency limits are defined in the `Canonical crew-cap and availability rules` `executionLimits` anchor above. The plan graph defines only dependency structure (`depends_on`, plus blocking edges such as `blockers`/`unblocks` where applicable); max concurrent is an execution/config concern. See `Plans/Crosswalk.md` §3.7 for the ownership table.
L00005430	
L00005431	**Crew limits vs agent limits:** These are separate concepts:
L00005432	- **Per-platform agent cap:** limits individual concurrent agent/subagent processes per platform. This is what hits rate limits and machine load.
L00005433	- **Crew cap** (`maxConcurrentCrewsPerPlatform`): limits concurrent crew groups per platform. A crew is a logical group of subagents working together.
L00005434	
L00005435	Both limits apply: a crew spawn must not exceed either the crew cap or the per-platform agent cap. See the `Canonical crew-cap and availability rules` `executionLimits` anchor for canonical values.

L00005657	## Autonomous QA Loop Pattern Integration
L00005658	
L00005659	### Overview
L00005660	
L00005661	The [autonomous QA loop pattern](https://gist.github.com/gsemet/1ef024fc426cfc75f946302033a69812) provides a proven orchestrator pattern for autonomous task execution with quality gates. While designed for VS Code Copilot, its concepts can enhance our orchestrator subagent integration.
L00005662	
L00005663	### Key Concepts from Autonomous QA Loop
L00005664	
L00005665	1. **Orchestrator/Subagent Separation**: Orchestrator manages loop, subagents implement tasks
L00005666	2. **Three-Tier QA System**: Preflight → Task Inspector → Phase Inspector
L00005667	3. **Progress Tracking**: Visual status symbols (⬜ 🔄 ✅ 🔴) with detailed tracking
L00005668	4. **Task Prioritization**: Incomplete tasks (🔴) prioritized over new tasks
L00005669	5. **Phase-Aware Execution**: Only work on current phase, don't jump ahead
L00005670	6. **Pause Mechanism**: `PAUSE.md` file to safely halt execution
L00005671	7. **Commit Strategy**: Amend commits for rework, conventional commits for new work
L00005672
