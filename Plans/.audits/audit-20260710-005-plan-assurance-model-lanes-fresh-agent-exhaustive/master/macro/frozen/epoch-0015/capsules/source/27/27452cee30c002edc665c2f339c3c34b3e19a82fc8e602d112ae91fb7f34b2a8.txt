L00000102	### 2.0.1 Worktree path guard rules
L00000103	
L00000104	Worktree path resolution MUST apply the fail-closed symlink policy from `Plans/Permissions_System.md` §1.1 and `Plans/Architecture_Invariants.md` INV-017.
L00000105	
L00000106	Search/index paths that interact with worktrees or remote caches are canonicalized before use and validated with `starts_with(project_root)` or `starts_with(cache_root)`. This includes paths derived from `.gitmodules`/gitmodules, dirty staging notifications, remote file-change notifications, and file watcher events; submodule paths containing `..` are rejected with a logged warning before affecting a project tree or remote `cache_root`. Index-build walks and ripgrep verification default to `--no-follow` / `no-follow`; a "Follow symlinks" indexing setting is OFF by default, and when enabled PM still canonicalizes the resolved target and reapplies `starts_with(project_root)` before indexing or verifying it.

L00000108	ContractRef: ContractName:Plans/Permissions_System.md, ContractName:Plans/FileSafe.md

L00000110	Required:
L00000111	- All file paths computed relative to a worktree root MUST be normalized via `realpath()` before any scope check or file guard comparison.
L00000112	- If `realpath()` fails on a worktree-relative path, the operation MUST be denied.
L00000113	- The `working_directory` passed to FileSafe `check_file_write` MUST be the real path of the worktree root, not a symlinked alias.

L00000117	### 2.0A Assistant worktree command and ownership rules
L00000118	
L00000119	- Compare buttons for assistant/worktree rows open committed branch-to-branch review only: worktree branch HEAD against base branch HEAD through `cmd.git.open_diff`, with `compare_origin` set to the base branch ref (e.g. `main`).
L00000120	- `cmd.chat.worktree.create` and `cmd.chat.worktree.remove` delegate to `WorktreeManager`; worktree creation/removal is user/system-initiated infrastructure, not agent-tool-gated, and agents do not run raw `bash` `git worktree add` or removal commands.
L00000121	- Git-aware tools such as `git status` auto-scope to the worktree through process `cwd`.
L00000122	- Branch rename follows `chat.thread_title_generated`; merge and PR command when-clause checks require the worktree not be on detached HEAD.
L00000123	- Branch existence checks use `git rev-parse --verify refs/heads/{branch}` before create; existing branch reuse uses `git worktree add <path> <branch>`.
L00000124	- Detached transitions refresh `worktree_projection.v1`; Source Control rows for orch-owned worktrees show `Open Lane` instead of `Open Thread`.
L00000125	- `Permissions_System.md` remains unaffected by this worktree creation/removal contract because worktree creation and removal are routed through Source Control and `WorktreeManager`.
L00000126	
L00000127	
L00000128	### 2.1 Base branch for worktree creation
L00000129	
L00000130	- **Gap:** Worktrees are created with `git worktree add -b <branch> <path>` from **current HEAD** of the main repo. There is no checkout of `config.branching.base_branch` first.
L00000131	- **Impact:** If the main repo is on a feature branch, new worktrees are created from that branch instead of `main` (or configured base).
L00000132	- **Fix:**
L00000133	  - Before creating worktrees for a parallel group, ensure the main repo is on `config.branching.base_branch` (e.g. `git checkout base_branch` or at least validate and warn).
L00000134	  - Optionally: create worktrees from a specific ref, e.g. `git worktree add -b <branch> <path> <base_branch>` (supported in recent Git).
L00000135	
L00000136	### 2.2 active_worktrees lost on restart
L00000137	
L00000138	- **Gap:** `active_worktrees` is in-memory only. After restart it is empty; real worktrees may still exist under `.puppet-master/worktrees/`, but `get_node_worktree(node_id)` returns `None`, so iterations use the main repo path.
L00000139	- **Fix (choose one or combine):**
L00000140	  - **Option A:** On orchestrator init (or when loading a run), repopulate `active_worktrees` from `worktree_manager.list_worktrees()` for paths under `worktree_base`.
L00000141	  - **Option B:** When resolving working directory for a node, if `active_worktrees` has no entry, fall back to `worktree_manager.get_worktree_path(node_id)` and verify the path exists and is a valid worktree (e.g. in `list_worktrees()`); if so, use it and optionally re-register.
L00000142	
L00000143	### 2.3 Merge conflicts: worktree kept but re-run can destroy it
L00000144	
L00000145	
L00000146	- **Gap:** On merge conflict, `cleanup_subtask_worktree` returns without removing the worktree but removes the node from `active_worktrees`. Re-running the same subtask calls `create_subtask_worktree` → `create_worktree` → "if path exists remove_worktree", so the conflicting worktree is removed and the conflict state is lost.
L00000147	- **Fix:**
L00000148	  - On conflict, either: (1) surface the worktree path to the user (e.g. toast or status) and avoid reusing that node_id for a new worktree until the user resolves or discards, or (2) document clearly that re-running will replace the worktree and lose unmerged state.
L00000149	  - Optionally: add a "Resolve worktree conflicts" action that lists worktrees with merge conflicts and offers to open in editor or remove after confirmation.
L00000150	
L00000151	### 2.4 Node ID and branch name sanitization
L00000152	
L00000153	- **Gap:** Worktree path is `worktree_base.join(node_id)` with no sanitization; branch name is `format!("subtask/{}", subtask_id.replace('.', "-"))` with no other sanitization. Risky for path traversal or invalid refs.
L00000154	- **Fix:**
L00000155	  - Sanitize `node_id` for use as a single path component (strip or replace `..`, path separators, and other unsafe characters) before `join`.
L00000156	  - Sanitize branch name for git refs (e.g. reuse or mirror `BranchStrategyManager::sanitize_id` or a shared helper; disallow spaces and other invalid ref characters).
L00000157	
L00000158	### 2.5 Branch already exists when recreating worktree
L00000159	
L00000160	
L00000161	- **Gap:** If the branch (e.g. `subtask/ST-001-001-001`) already exists (e.g. after incomplete cleanup), `git worktree add -b <branch> <path>` fails with "fatal: A branch named '...' already exists."
L00000162	- **Fix:**
L00000163	  - Before `worktree add -b`, check if the branch exists (e.g. `git rev-parse --verify refs/heads/<branch>`). If it exists, use `git worktree add <path> <branch>` (no `-b`) to create the worktree from the existing branch, or explicitly delete the branch if it is safe (e.g. no other worktree uses it).
L00000164	
L00000165	### 2.6 Detached HEAD worktrees
L00000166	
L00000167	- **Gap:** `list_worktrees` only sets `branch` when it sees a `branch refs/heads/...` line. Detached HEAD worktrees yield empty `branch`; `merge_worktree` would then call `git merge ""`.
L00000168	- **Fix:** When parsing porcelain output, treat missing branch as "detached". In `merge_worktree`, if source_branch is empty, skip merge or merge by commit hash and document behavior.

L00000170	### 2.8 Lane/worktree lifecycle, storage families, and historical vocabulary
L00000171	
L00000172	
L00000173	#### Lane and worktree lifecycle
L00000174	- Lanes own worktrees through explicit allocation and handshake.
L00000175	- Worktrees are allocated at lane start and reclaimed at lane end (implicit or explicit).
L00000176	- Storage families define data layout and cleanup rules; worktrees may span multiple storage families.
L00000177	
L00000178	#### Source Control to Orchestrator handshake
L00000179	- When a lane requests a worktree, Source Control MUST confirm allocation, provide the worktree path, and publish any applicable storage metadata.
L00000180	- Orchestrator records the handshake in the ledger so restart and recovery can reuse the same worktree.
L00000181	- Stale worktrees (allocated but not reclaimed) are eligible for cleanup via storage housekeeping.
L00000182	
L00000183	#### Provider/model precedence and worktree allocation strategy
L00000184	- Worktree allocation strategy is determined by lane policy, not by individual nodes.
L00000185	- Multiple providers may offer worktree allocation; the lane selects a primary provider and routes all allocations through that provider.
L00000186	- Fallback providers are secondary; they are used only if the primary provider is unavailable.
L00000187	### Source Control to Orchestrator handshake
L00000188	Source Control is the concrete repo/worktree operator, while Orchestrator remains the lane-pool operational truth.
L00000189	
L00000190	Required row fields:
L00000191	- owning package reference
L00000192	- `lane_id`
L00000193	- `run_id`
L00000194	- `worktree_id`
L00000195	- lifecycle state
L00000196	- blocked/recovery state
L00000197	
L00000198	Rules:
L00000199	- worktree rows MUST show owning package, lane, and run references together with lifecycle and blocked/recovery state
L00000200	- Source Control actions operate on concrete repositories and worktrees but MUST report results back through canonical lane/worktree records
L00000201	- Orchestrator decisions about reuse, cleanup, retry, and recovery consume the same lane/worktree records rather than side files
L00000202	
L00000203	### Provider/model precedence and worktree allocation strategy
L00000204	Provider/model selection and worktree allocation are one ownership surface because allocation follows the effective execution scope.
L00000205	
L00000206	Precedence order:
L00000207	- delegated subagent
L00000208	- overseer
L00000209	- node
L00000210	- work package
L00000211	- seam
L00000212	- run
L00000213	
L00000214	Allocation rules:
L00000215	- parallel nodes receive distinct worktree allocations unless they explicitly reuse an existing clean allocation owned by the same effective scope
L00000216	- contamination, dirty-state, conflict-state, blocked recovery, or lineage mismatch disqualify reuse and force a new allocation or explicit repair
L00000217	- cleanup only occurs after lineage-safe completion or archival and MUST preserve the historical record of the lane/worktree pair
L00000218	- run-completion cleanup waits for the owning cleanup grace period before deletion; the cleanup worker records `grace_period_ms`, performs a file-lock check, and refuses deletion while active locks, safe-point refs, terminal/editor sessions, or blocked recovery lineage still reference the worktree
L00000219	- `worktree.deleted` may be emitted only after the grace-period and file-lock checks pass; `worktree.created` records the allocation path, branch, lane/run/package lineage, and source-control owner before a node begins work in that tree
L00000220	- ownership transitions between scopes MUST update the effective provider/model choice together with the lane/worktree assignment record
L00000221	
L00000222	#### Runtime lineage transfer and restore targeting
L00000223	- Worktree ownership transfer requires an explicit runtime lineage event; replan must either rebind explicitly to new attempt lineage or allocate new worktree lineage, never silently inherit prior ownership.
L00000224	- Manual prune/remove stays forbidden while the worktree is `active` or `blocked_preserved` unless the explicit override policy permits it and records the override.
L00000225	- Restore and retry payloads, including `cmd.runtime.restore_safe_point_then_retry`, carry exact SCM targeting: `repo_id`, `worktree_id`, and `baseline_target`.
L00000226	- `baseline_target` is a closed candidate enum for restore/retry targeting: `safe_point`, `historical_commit`, and `worktree_head`.
L00000227	- Retry and `/fresh-attempt` commands must support the same SCM targeting and reuse policy; runtime rejects restore/retry when the targeted worktree or baseline cannot be validated instead of substituting another worktree.
L00000228	- Legacy `git_panel/*` and `git_panel` state is one-time migration input into `source_control.project_state.{project_id}` only. Settings-owned policy such as `branching.base_branch` remains canonical settings policy, followed by canonical Source Control project state, with legacy `git_panel/*` consulted only when the canonical key is absent; no new build writes both legacy and canonical keys.

L00000230	#### Worktree identity, active context, and copy contracts
L00000231	
L00000232	Source Control owns the live SCM truth for current repo/worktree state, while Health is a read-only diagnostic and `/validation` mirror unless a repair utility deep-links back into Source Control. Worktree projection keys use `project_id/repo_id/worktree_id`; the compact `/repo_id/worktree_id` display is allowed only as a label over canonical IDs. `repo_id` is stable per project repo root, `worktree_id` is stable per concrete worktree instance, `worktree_path` is display/navigation state, and a `/recovered` or recreated path gets a new durable instance marker rather than inheriting stale identity. Every `multi-worktree` and multi-active-worktree view reads these IDs from durable-storage state before rendering live SCM affordances.
L00000233	
L00000234	Remote-mode and `/SSH` projects still use the same canonical IDs. L00000235

L00000270	## 3. Git Improvements
L00000271	
L00000272	### 3.0 Git subprocess integrity invariant
L00000273	
L00000274	#### 3.0.1 Exit-code classification and recovery
L00000275	
L00000276	Git subprocess exit codes are classified into three recovery categories:
L00000277	
L00000278	ContractRef: ContractName:Plans/Executor_Protocol.md, ContractName:Plans/FileSafe.md
L00000279	
L00000280	| Exit Scenario | Classification | Recovery Action |
L00000281	|---|---|---|
L00000282	| Exit 0 | success | proceed normally |
L00000283	| Exit 1 with `nothing to commit` on stdout | informational | proceed (not an error for commit operations) |
L00000284	| Exit 1 (generic failure) | fatal | fail the operation with structured error; do not retry |
L00000285	| Exit 128 + signal (e.g., SIGKILL, SIGTERM) | fatal | fail immediately (`/fail-immediately`); report the signal in the error |
L00000286	| Exit 128 (ambiguous) | fatal | fail the operation; log full stderr for diagnosis |
L00000287	| Lock contention (`index.lock` exists) | retryable | retry once after 500ms backoff; fail on second attempt |
L00000288	| Network timeout (fetch/push/clone) | retryable | retry with exponential backoff (max 3 attempts, base 1s) |
L00000289	| Authentication failure (exit 128 with auth error on stderr) | fatal | fail immediately; surface credential refresh guidance |
L00000290	| Disk full / permission denied | fatal | fail immediately; surface the OS-level error |
L00000291	
L00000292	ContractRef: ContractName:Plans/storage-plan.md, ContractName:Plans/Run_Modes.md
L00000293	
L00000294	Rules:
L00000295	- Retryable scenarios MUST use bounded retry with backoff. Maximum 3 retry attempts for network operations; maximum 1 retry for lock contention.
L00000296	- Fatal scenarios MUST NOT be retried or skipped (`skip-silently-never`). The operation fails with a structured error that includes the git command, exit code, and stderr content.
L00000297	- The `nothing to commit` case is the only exit-1 scenario that is not treated as a hard error. All other non-zero exits follow the hard-error rule from §3.0.
L00000298	
L00000299	ContractRef: ContractName:Plans/Executor_Protocol.md, ContractName:Plans/Architecture_Invariants.md
L00000300	
L00000301	Every git subprocess that mutates or validates PM-managed state MUST treat a non-zero exit status as a hard error.
L00000302	
L00000303	ContractRef: ContractName:Plans/FileSafe.md, ContractName:Plans/Executor_Protocol.md
L00000304	
L00000305	The pre-write and post-stage git checks are session-scoped to the active PM-managed worktree. FileSafe snapshots and recoverable backups must align with `FileSafe.md#11.1.2a` and this hard-error rule rather than masking a failed `git status --porcelain` or git mutation subprocess.

L00000310	- distinguish `nothing to commit` from generic failure, but do not treat genuine git command failure as informational noise

L00000557	### 7.2 Doctor: project path context
L00000558	
L00000559	- Doctor checks implement `async fn run(&self) -> CheckResult` with **no parameters**. They have no built-in "project path" or "working directory."
L00000560	- **GitRepoCheck** and **GitConfiguredCheck** "use project path when available" can be implemented by **resolving project root inside `run()`**: e.g. call `config_discovery::discover_config_path(None)` (or with a hint if the app can pass it), then take the parent directory as project root; run `git rev-parse --git-dir` or `git config user.name` with `current_dir(project_root)`. If no config is found, fall back to current behavior (CWD or HOME). This matches the pattern used in the orchestrator-subagent plan for the Gemini plan-mode Doctor check.
L00000561	- **App → Doctor:** When the app runs Doctor (e.g. from the Doctor view), it could pass a "config hint" (e.g. `current_project.path`) so `discover_config_path(Some(hint))` finds the project's config. That would require extending the Doctor run API to accept an optional hint (e.g. `run_all(hint: Option<&Path>)`) and threading it into checks that need it. Alternatively, keep discovery inside each check with `discover_config_path(None)` so the "project" is whatever directory would be used when no project is selected (cwd, default workspace, etc.).
L00000562	
L00000563	### 7.3 Backend run does not use current project
L00000564	
L00000565	- **Current behavior:** `spawn_orchestrator_backend` calls `ConfigManager::discover()` with **no hint**. The wizard and start-chain use `ConfigManager::discover_with_hint(config_hint)` with `current_project.path`. So the **orchestrator run** (Dashboard "Run") never receives the current project path; it uses whatever `discover_config_path(None)` finds.
L00000566	- **Implication:** For "recovery when project is known" and "Doctor use project path," if the user selects a project in the UI but the run is started from the same app, the run still uses discover-with-no-hint. To make "current project" meaningful for the run, the run command must pass a hint (e.g. extend start message with `config_hint: Option<PathBuf>`). **Call site to change:** In `app.rs::spawn_orchestrator_backend`, replace `ConfigManager::discover()` with `ConfigManager::discover_with_hint(config_hint)`; pass `current_project.path` from Dashboard when starting a run. The plan should explicitly call out: "When starting a run from the Dashboard, pass `current_project.path` as config hint so the run and recovery use the selected project."
L00000567	
L00000568	### 7.4 Merge conflicts: persisting "conflict worktrees"
L00000569	
L00000570	- To "avoid reusing that node_id for a new worktree until the user resolves," the app must remember which node_ids have unresolved merge conflicts. Options: (1) a small state file under `.puppet-master/` (e.g. `worktree-conflicts.json` listing node_ids), updated when a merge fails and cleared when the user runs "Recover worktrees" or resolves manually; (2) in-memory only (lost on restart, so re-run would still overwrite after restart). The plan should specify which approach or mark as "optional: in-memory set for the session only" to avoid scope creep.

L00000765	## Worktree Lane Allocation and Source Control Reconciliation
L00000766	
L00000767	`Plans/WorktreeGitImprovement.md`, `Plans/orchestrator-subagent-integration.md`, and `Plans/Crosswalk.md` converge on `/worktree` and `/worktrees` ownership, but the worktree owner must make the allocation strategy concrete. The old run/tier/subtask, branch-per-run, subtask-per-worktree, wizard-centric, /iteration-scoped, and /seam-aware SCM assumptions are compatibility context only until they map to package-based lane pools, shared Source Control visibility, and per hosted side-effect effective-account recording.
L00000768	
L00000769	Source Control is the primary operational surface for worktree inventory and actions, and Orchestrator consumes worktree identity, blocked state, and lineage. `dirty_worktree` and `worktree_conflict` route back to Source Control with the correct worktree in scope; historical runs preserve historical worktree references after prune `/remove`. L00000770
