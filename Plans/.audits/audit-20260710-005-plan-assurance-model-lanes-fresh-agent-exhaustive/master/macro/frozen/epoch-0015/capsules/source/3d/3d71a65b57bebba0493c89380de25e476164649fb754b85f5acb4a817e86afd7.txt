L00000089	## 1. Definitions and scope
L00000090	### 1.1 Path normalization invariants
L00000091	
L00000092	Before any permission match, path comparison, or scope check, paths MUST be normalized in this order:
L00000093	1. Expand `~` and `$HOME` to the real home-directory path.
L00000094	2. Resolve an absolute path and eliminate `.` / `..` components.
L00000095	3. Resolve symlinks with `realpath()`; this is the symlink-root canonicalization step.
L00000096	4. Match only against the normalized canonical path.
L00000097	
L00000098	ContractRef: ContractName:Plans/FileSafe.md, ContractName:Plans/Executor_Protocol.md
L00000099	
L00000100	Required behavior:
L00000101	- `realpath()` failure is fail-closed. Broken symlink, permission error, or missing target means deny.
L00000102	- PM MUST NOT compare against an unresolved path as fallback.
L00000103	- Unexpanded `~` in a runtime path comparison is always a bug.
L00000104	
L00000105	ContractRef: ContractName:Plans/FileSafe.md, ContractName:Plans/Architecture_Invariants.md

L00000171	## 2. Permission actions
L00000172	
L00000173	<a id="PERM-ACTIONS"></a>
L00000174	
L00000175	Exactly three permission actions exist. Every tool invocation resolves to exactly one action.
L00000176	
L00000177	ContractRef: PolicyRule:Decision_Policy.md§2
L00000178	
L00000179	### 2.1 `allow`
L00000180	
L00000181	The tool invocation proceeds without user approval. FileSafe guards (`Plans/FileSafe.md`) still apply after permission resolution.
L00000182	
L00000183	### 2.2 `ask`
L00000184	
L00000185	The tool invocation is paused pending user approval. The user is presented with the invocation details and MUST choose one of the canonical resolution options: `deny`, `once`, `for session`, or `always` (see §6). If no user is available (headless/Orchestrator run), `ask` maps to `deny` unless a HITL/approval gate is active for the current blocked episode or package/seam decision point and can surface the ordered `allowed_action_ids[]` through the shared approval scope (`Plans/human-in-the-loop.md`).
L00000186	
L00000187	### 2.3 `deny`
L00000188	
L00000189	The tool invocation is blocked. The policy engine emits a `tool.denied` event (`Plans/Contracts_V0.md#EventRecord`) and returns an error to the agent. The tool is not executed.
L00000190	
L00000191	### 2.4 Deterministic precedence across layers
L00000192	
L00000193	Permission rules are evaluated in a strict layer precedence. The first layer that produces a defined rule for the invocation wins; higher-precedence layers shadow lower layers on a per-rule basis, but they do NOT replace the entire lower ruleset.
L00000194	
L00000195	ContractRef: ContractName:Plans/Run_Modes.md, ContractName:Plans/Personas.md#PERSONA-INJECTION, PolicyRule:Decision_Policy.md§2
L00000196	
L00000197	| Priority | Layer | Source | Description |
L00000198	|---|---|---|---|
L00000199	| 1 | Mode override | `Plans/Run_Modes.md` | `ask` / `plan` clamp mutating capability; `yolo` applies only where policy allows. |
L00000200	| 2 | Parent/run ceiling | runtime envelope | Parent execution ceiling and inherited restriction patterns. |
L00000201	| 3 | Session cache | runtime | Prior explicit approvals scoped to the session. |
L00000202	| 4 | Persona overrides | `Plans/Personas.md` | Named permission profile for the active Persona. |
L00000203	| 5 | Project-level | `.puppet-master/permissions.toml` | Project-local rules. |
L00000204	| 6 | Global-level | user config | User-wide rules. |
L00000205	| 7 | Defaults | this document | Hardcoded fallback table. |
L00000206	
L00000207	ContractRef: ContractName:Plans/Run_Modes.md, ContractName:Plans/Tools.md
L00000208	
L00000209	Child inheritance rules:
L00000210	- Child runs inherit both action ceilings and restrictive argument-pattern rules from the parent chain.
L00000211	- Inheritance is additive-downward and merge-not-replace: a child may narrow authority, but MUST NOT widen or replace away inherited restrictions.
L00000212	- The permission chain is evaluated as Parent Agent -> Parent Session -> Child Session -> Child Agent, then project/global/default layers.
L00000213	
L00000214	ContractRef: ContractName:Plans/orchestrator-subagent-integration.md, ContractName:Plans/Executor_Protocol.md
L00000215	
L00000216	When multiple rules for the same permission key are simultaneously applicable, the most specific scope wins before falling back to the broader layer order in §2.4. Scope specificity is:
L00000217	
L00000218	`lane:{lane_id}` > `seam:{seam_id}` > `package:{package_id}` > project > global
L00000219	
L00000220	Role-scoped account policy overrides use the same precedence chain. A rule may carry `allowed_roles`, `disallowed_roles`, `cooldown_policy_override`, and `switch_threshold_override`; these fields narrow which execution roles may use the account/pool and how cooldown or threshold switching applies, but they do not widen the parent/run permission ceiling.
L00000221	
L00000222	Scope meanings:
L00000223	- `package:{package_id}` applies only while execution is inside the identified package. A package scope inherits from the enclosing project scope unless explicitly overridden.
L00000224	- `seam:{seam_id}` applies only at the named seam boundary, including cross-package transitions and other explicitly modeled boundary crossings.
L00000225	- `lane:{lane_id}` applies only within the identified execution lane and is the narrowest durable scope in the standard precedence model.
L00000226	
L00000227	This specificity order applies anywhere scoped permission material is evaluated, including session-cache approvals, durable project/global rules, and inherited parent/run ceilings. Ties within the same scope still use the layer order in §2.4 and last-match-wins behavior inside the selected ruleset (§3.1).
L00000228	
L00000229	ContractRef: Plans/FinalGUISpec.md#10.8 Human-in-the-loop approvals, Plans/Tools.md#10.7A Web-operation approval summary rules

L00000281	## 3. Granular rules
L00000282	
L00000283	<a id="GRANULAR-RULES"></a>
L00000284	
L00000285	A permission rule MAY be a simple action string (`"allow"`, `"ask"`, `"deny"`) or an object containing pattern-based sub-rules that match against invocation context (e.g., file path for `read`/`edit`, command string for `bash`, URL for `webfetch`).
L00000286	
L00000287	ContractRef: ContractName:Plans/OpenCode_Deep_Extraction.md, PolicyRule:Decision_Policy.md§2
L00000288	
L00000289	### 3.1 Wildcard syntax and matching
L00000290	<a id="WILDCARD-SYNTAX"></a>
L00000291	
L00000292	Pattern matching uses the following syntax:
L00000293	
L00000294	| Token | Meaning |
L00000295	|-------|---------|
L00000296	| `*` | Matches zero or more characters |
L00000297	| `?` | Matches exactly one character |
L00000298	
L00000299	**Special case:** A pattern ending with ` *` (space + wildcard) makes the trailing portion optional. Example: `"git *"` matches both `"git"` and `"git status"`.
L00000300	
L00000301	Tool-family prefix wildcards are valid for MCP/server-provided tools as well as built-ins. Enabling or disabling `github_*` affects every matched tool from the `github` server family, while more specific rules still win according to the precedence and last-match rules below.
L00000302	
L00000303	**Ordering:** Within a single ruleset (object syntax), rules are evaluated in definition order; the last matching rule wins. This allows broad patterns followed by narrow exceptions.
L00000304	
L00000305	```toml
L00000306	[bash]
L00000307	"*" = "ask"
L00000308	"git *" = "allow"
L00000309	"rm *" = "deny"
L00000310	```

L00000392	### 3.4 Pattern suggestion contract ("always" approval)
L00000393	
L00000394	<a id="PATTERN-SUGGESTION"></a>
L00000395	
L00000396	When a user responds `always` to an `ask` prompt (§6.2), the system derives a suggested approval scope from the invocation context and presents the user with scope-bound approval choices instead of silently minting a session-wide allow. Pattern suggestions are still derived from tool-specific context:
L00000397	
L00000398	- **bash:** The command prefix (first word + space + `*`). Example: invocation `git commit -m "fix"` → pattern `"git *"`.
L00000399	- **edit/read/glob/grep:** The directory prefix (`<dir>/**`). Example: invocation path `src/auth/login.rs` → pattern `"src/auth/**"`.
L00000400	- **websearch/webresearch:** Wildcard discovery scope (`*`) or query/task-category scope when the advanced matcher is implemented, because the URL set is not known before discovery. The wildcard is tool-scoped and never grants unrelated network, file, shell, or mutation authority.
L00000401	- **webfetch/webextract/webcrawl/webmap:** The normalized target origin and scope. Single-target reads and extraction use the concrete URL origin (`https://<domain>/*`); bounded crawl/map rules use the approved root origin plus an explicit crawl-scope discriminator, never a naked wildcard.
L00000402	- Web approval pre-population is deterministic: `websearch` and `webresearch` pre-populate `*`; `webfetch` and `webextract` pre-populate `https://<actual-host>/*` derived from the URL; `webcrawl` and `webmap` pre-populate `https://<actual-root-host>/*` derived from `root_url`. The `/suggest` value is a user-editable pre-population convenience, not a lock.
L00000403	
L00000404	The suggested pattern is displayed to the user during approval confirmation. The user MAY edit the pattern before a durable project/global rule is created, but the canonical approval anchor remains `approval_scope_key` plus blocked-episode identity rather than a UI session id.

L00000669	## 8. Resolution algorithm
L00000670	
L00000671	### 8.0 Composition with precedence layers
L00000672	
L00000673	The resolution algorithm composes the strict layer precedence from §2.4 with the dispatch checks in this section. The flow is:
L00000674	1. Build the invocation context from the tool name, normalized arguments, target paths/hosts, runtime mode, parent/run ceiling, session state, Persona, project/global/default rules, and capability snapshot.
L00000675	2. Apply the mode layer from §2.4 as the first permission candidate: `ask` and `plan` clamp mutating tools to `deny`; `yolo` clamps tool permissions to `allow` where provider/runtime policy permits. Later non-bypassable guards and capability checks may still return blocked/denied outcomes, but they do not rewrite the recorded mode-layer decision.
L00000676	3. Resolve the effective rule for each permission key through §2.4 layer order plus scope specificity, with inherited parent/run ceilings, role-scoped account policy, and session-cache approvals narrowing authority but never widening it.
L00000677	4. Run non-bypassable guards and capability gates, including full-string banned-command checks, external-directory checks, domain-sensitive remote-side-effect checks, executable trust checks, host/network policy, and capability availability.
L00000678	5. Persist requested/effective permission evidence, including `requested_permission_state`, `effective_permission_state`, `downgrade_reason`, `approval_scope_key`, `permission_snapshot_id?`, `blocked_reason_code`, and ordered `allowed_action_ids[]` when applicable.
L00000679	6. If an approved hook mutates arguments or execution context, re-run §2.4 rule resolution and all applicable guards on the modified invocation before dispatch.
L00000680	7. Dispatch only when the final effective decision is `allow` and all guards pass; `ask`, `deny`, blocked, unavailable, or capability-failed outcomes emit audit evidence and do not call the underlying tool.

L00000682	ContractRef: ContractName:Plans/Run_Modes.md, ContractName:Plans/Tools.md, ContractName:Plans/Executor_Protocol.md, ContractName:Plans/Contracts_V0.md

L00000684	### 8.1 Banned-command full-string check
L00000685	
L00000686	Banned-command evaluation MUST scan the full command string, not just the first token. The scan includes shell metacharacters and substitution forms such as `;`, `&&`, `||`, `|`, `$()`, and backticks.
L00000687	
L00000688	ContractRef: ContractName:Plans/FileSafe.md, ContractName:Plans/Tools.md
L00000689	
L00000690	A command that passes a first-token allowlist but contains a banned destructive sequence in its arguments is still denied. First-token-only checking is prohibited.
L00000691	
L00000692	ContractRef: ContractName:Plans/Executor_Protocol.md, ContractName:Plans/Architecture_Invariants.md
L00000693	
L00000694	### 8.2 Hook re-check and execution-path invariance
L00000695	
L00000696	Resolution happens before dispatch and again after any arg-touching hook mutation. The dispatch layer MUST NOT call the underlying tool implementation until both checks pass on the final argument set.
L00000697	
L00000698	ContractRef: ContractName:Plans/Plugins_System.md, ContractName:Plans/Tools.md
L00000699	
L00000700	Required order:
L00000701	1. Normalize request context and candidate paths.
L00000702	2. Evaluate `policy.may_execute_tool()` on the original invocation.
L00000703	3. Run arg-touching hooks, if any.
L00000704	4. Re-run permission checks on the modified invocation.
L00000705	5. Dispatch only if the re-check passes.
L00000706	
L00000707	ContractRef: ContractName:Plans/Executor_Protocol.md, ContractName:Plans/Architecture_Invariants.md
L00000708	
L00000709	### 8.3 Shell environment isolation routing
L00000710	
L00000711	Environment isolation for shell/session processes is jointly owned by `Plans/orchestrator-subagent-integration.md` and `Plans/Tools.md`. The permission layer consumes that invariant when evaluating agent/crew execution context, but does not define shell lifecycle behavior itself.

L00000713	ContractRef: ContractName:Plans/orchestrator-subagent-integration.md, ContractName:Plans/Tools.md
L00000714	
L00000715	Cleanup-sensitive approval and retention checks are permission-visible. If active-run ownership, unresolved blocked recovery, required safe-point restore, unresolved conflict inspection, or newer lineage dependency still exists, the target remains `retained`, `suspect`, or `restoring`, not cleanup_eligible; approval cards must not offer destructive cleanup as if age alone made it safe.

L00000717	## 9. Persistence and storage
L00000718	
L00000719	<a id="PERSISTENCE"></a>
L00000720	
L00000721	Permission configuration is stored at three durable layers plus one ephemeral layer.
L00000722	
L00000723	ContractRef: PolicyRule:Decision_Policy.md§2, ContractName:Plans/Personas.md#STORAGE-LAYOUT
L00000724	
L00000725	| Layer | Location | Format | Lifetime |
L00000726	|-------|----------|--------|----------|
L00000727	| **Global** | `~/.config/puppet-master/permissions.toml` | TOML | Until user edits/deletes |
L00000728	| **Project** | `<project_root>/.puppet-master/permissions.toml` | TOML | Until user edits/deletes |
L00000729	| **Persona** | Named profiles referenced by `default_permissions_profile` in `PERSONA.md` frontmatter; stored alongside global permissions config at `~/.config/puppet-master/permission-profiles/<profile_id>.toml` | TOML | Until user edits/deletes |
L00000730	| **Session** | In-memory session cache | Runtime | Current session only; cleared on restart |
L00000731	
L00000732	Durable approvals created through `create_project_rule` or `create_global_rule` are persisted in their owning config layer as metadata-bearing records with the logical fields `{ rule_id, tool_pattern, action, scope_key?, created_at, created_by_thread_id }`. `rule_id` is a stable UUID generated at rule creation and is the canonical revocation/update key; `tool_pattern` is not unique and MUST NOT be used as the durable identity. File-level TOML projections MAY additionally expose these rules in the simpler per-tool tables shown below, but the stored rule identity and audit metadata remain part of the canonical durable record.
L00000733	
L00000734	### 9.1 TOML format
L00000735	
L00000736	Permission config files use the following TOML structure:
L00000737	
L00000738	```toml

L00000740	[tools]
L00000741	read = "allow"
L00000742	edit = "ask"
L00000743	bash = "ask"
L00000744	webfetch = "allow"

L00000747	
L00000748	
L00000749	[tools.bash]
L00000750	"*" = "ask"
L00000751	"git *" = "allow"

L00000755	[tools.read]
L00000756	"*" = "allow"
L00000757	"*.env" = "deny"
L00000758	"*.env.*" = "deny"

L00000763	doom_loop = "ask"

L00000942	## 10A. Security model
L00000943	
L00000944	### 10A.1 Trust boundaries and threat model
L00000945	
L00000946	The permissions system spans four explicit trust boundaries:
L00000947	
L00000948	1. user intent and explicit approval surfaces
L00000949	2. Puppet Master runtime policy, projection, and audit machinery
L00000950	3. tool execution backends
L00000951	4. external services reached by tools
L00000952	
L00000953	Threat model summary:
L00000954	- **Prompt injection:** model output or external content attempts to smuggle tool names, arguments, or approval intents that the runtime did not independently authorize.
L00000955	- **Privilege escalation:** the model or a child run requests broader permissions than its current ceiling, scope, or durable grants allow.
L00000956	- **Data exfiltration:** tools attempt to send project/user data to unauthorized files, hosts, domains, or remote services.
L00000957	
L00000958	### 10A.2 Capability gates and sandbox boundaries
L00000959	
L00000960	Permissions are necessary but not sufficient. A tool is executable only when it is both capability-registered and permission-allowed; unregistered tools remain non-runnable even if a rule says `allow`.
L00000961	
L00000962	Sandbox/capability boundary rules:
L00000963	- `bash` executes in the user's environment and is not sandboxed beyond normal OS-level user permissions.
L00000964	- file-oriented tools are scoped to the active project root and configured working roots unless explicit policy broadens that access.
L00000965	- web-oriented tools must respect configured domain allowlists and web-operation scope keys in addition to normal permission decisions.
L00000966	
L00000967	### 10A.3 Audit trail
L00000968	
L00000969	Every permission outcome that matters operationally — grant, deny, or prompt — MUST be written to seglog. The audit record MUST include at least `tool_pattern`, `decision`, `scope`, and `requesting_context`, enabling later review of durable-rule creation, inherited narrowing, and denied/externalized execution attempts.

L00001049	## 12A. DockerHub / Unraid remote-side-effect guard addendum
L00001050	
L00001051	This addendum extends §§4, 5, and 7 for DockerHub publication and managed Unraid template-repo flows.
L00001052	
L00001053	### 12A.1 `external_publish_side_effect`
L00001054	
L00001055	`external_publish_side_effect` is a special guard for remote side effects that change publication visibility, remote repository state, or remote distribution state.
L00001056	
L00001057	Covered operations include:
L00001058	
L00001059	- DockerHub repository creation
L00001060	- DockerHub image push when initiated by an agent/autonomous flow rather than a direct user click
L00001061	- creation of a managed remote template repo
L00001062	- remote push of the managed Unraid template repo
L00001063	
L00001064	### 12A.2 Behavior
L00001065	
L00001066	- `push_policy = after_build` does not satisfy the “exact remote side effect requested” rule by itself. A Build click remains approval for local build only; the later auto-dispatched image push still requires `external_publish_side_effect` evaluation at the time it is about to run.
L00001067	- The same rule applies to follow-on managed template-repo creation and push steps: they are never implicitly approved by earlier local-only actions or by the existence of enabled defaults.
L00001068	
L00001069	- Default action: `ask`
L00001070	- This guard is **non-bypassable**
L00001071	- `yolo` mode MUST NOT auto-allow this guard
L00001072	- Session-scoped `always` approvals MUST NOT suppress this guard globally
L00001073	- A direct user click on the exact publish/create/push button counts as approval for **that one requested side effect only**
L00001074	- Follow-on side effects still require their own approval when they were not part of the same direct user action
L00001075	
L00001076	Example:
L00001077	- Clicking **Push image** may approve the image push itself
L00001078	- It does **not** auto-approve creating a missing DockerHub repo if the repo does not already exist
L00001079	- It does **not** auto-approve pushing the managed Unraid template repo unless that was the exact user action requested
L00001080	
L00001081	### 12A.3 Failure behavior
L00001082	
L00001083	When the guard is rejected:
L00001084	
L00001085	- local build results remain intact
L00001086	- local template generation/editing remains intact
L00001087	- remote side effects do not execute
L00001088	- the agent/runtime MUST surface a corrected error describing which remote step was blocked
L00001089	
L00001090	### 12A.4 Canonical key/default additions
L00001091
