L00000942	## 10A. Security model
L00000943	
L00000944	### 10A.1 Trust boundaries and threat model
L00000945	
L00000946	The permissions system spans four explicit trust boundaries:
L00000947	
L00000948	1. user intent and explicit approval surfaces
L00000949	2. Puppet Master runtime policy, projection, and audit machinery
L00000950	3. tool execution backends
L00000951	4. external services reached by tools
L00000952	
L00000953	Threat model summary:
L00000954	- **Prompt injection:** model output or external content attempts to smuggle tool names, arguments, or approval intents that the runtime did not independently authorize.
L00000955	- **Privilege escalation:** the model or a child run requests broader permissions than its current ceiling, scope, or durable grants allow.
L00000956	- **Data exfiltration:** tools attempt to send project/user data to unauthorized files, hosts, domains, or remote services.
L00000957	
L00000958	### 10A.2 Capability gates and sandbox boundaries
L00000959	
L00000960	Permissions are necessary but not sufficient. A tool is executable only when it is both capability-registered and permission-allowed; unregistered tools remain non-runnable even if a rule says `allow`.
L00000961	
L00000962	Sandbox/capability boundary rules:
L00000963	- `bash` executes in the user's environment and is not sandboxed beyond normal OS-level user permissions.
L00000964	- file-oriented tools are scoped to the active project root and configured working roots unless explicit policy broadens that access.
L00000965	- web-oriented tools must respect configured domain allowlists and web-operation scope keys in addition to normal permission decisions.
L00000966	
L00000967	### 10A.3 Audit trail
L00000968	
L00000969	Every permission outcome that matters operationally — grant, deny, or prompt — MUST be written to seglog. The audit record MUST include at least `tool_pattern`, `decision`, `scope`, and `requesting_context`, enabling later review of durable-rule creation, inherited narrowing, and denied/externalized execution attempts.

L00001054	
L00001055	`external_publish_side_effect` is a special guard for remote side effects that change publication visibility, remote repository state, or remote distribution state.

L00001062	- remote push of the managed Unraid template repo

L00001064	### 12A.2 Behavior
L00001065	
L00001066	- `push_policy = after_build` does not satisfy the “exact remote side effect requested” rule by itself. A Build click remains approval for local build only; the later auto-dispatched image push still requires `external_publish_side_effect` evaluation at the time it is about to run.
L00001067	- The same rule applies to follow-on managed template-repo creation and push steps: they are never implicitly approved by earlier local-only actions or by the existence of enabled defaults.
L00001068	
L00001069	- Default action: `ask`

L00001071	- `yolo` mode MUST NOT auto-allow this guard
L00001072	- Session-scoped `always` approvals MUST NOT suppress this guard globally
L00001073	- A direct user click on the exact publish/create/push button counts as approval for **that one requested side effect only**
L00001074	- Follow-on side effects still require their own approval when they were not part of the same direct user action
L00001075	
L00001076	Example:
L00001077	- Clicking **Push image** may approve the image push itself
L00001078	- It does **not** auto-approve creating a missing DockerHub repo if the repo does not already exist
L00001079	- It does **not** auto-approve pushing the managed Unraid template repo unless that was the exact user action requested
