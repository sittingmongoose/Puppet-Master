L00000030	## 2. Hostability and data contracts
L00000031	Widgets consume stable projections and canonical records. They do not define page semantics.
L00000032	
L00000033	Rules:
L00000034	- widget config changes presentation, local filtering, and layout only
L00000035	- widget-level filters inherit page/project/focused-run context and do not invent independent run scope
L00000036	- Route vocabulary is cross-cutting, not page-local; widget reconciliation starts from owner docs before surface docs so widgets consume the route/open contract instead of recreating route terms locally.
L00000037	- `tab-level` filters live in tab scope, `widget-level` filters are safe subfilters, and `page-native` actions stay with route/open or page owner docs; `/package` hostability consumes package/seam projections without turning widgets into page owners.
L00000038	- a widget action routes through canonical commands and route/open contracts rather than bypassing them
L00000039	- widget surfaces consume cross-cutting `/state` and `/runtime` owner contracts rather than reopening already-locked seams: SSH retry-budget/reconnect behavior is owned by GitHub Integration, and stale cross-references must point to the owning contract before widget drill-downs are implementation-ready
L00000040	- Widget_System consumes, but does not own, the FinalGUISpec anchors `#### 7.4.4 Settings (Unified) panel specification`, `#### 7.4.7 Agent-Config panel specification`, and `## 15. Promoted widget catalog (web tools, planning, question, operation cards)`: those anchors own provider class/settings disclosure, web/plan/question/approval widget ownership, and the inline visual/web-tool rendering split.
L00000041	- Widget hostability treats `/settings/widget`, `/plan/question/approval`, and `/web-tool` as routed GUI consumer paths over FinalGUISpec and UI command owners; Widget_System owns only whether those widgets can be hosted by Dashboard, Usage, or Orchestrator `Progress`, plus layout and projection inheritance.
L00000042	- Stale or incomplete widget summaries are `/retire` or `/incomplete` instead of being reintroduced as live catalog entries; the older source shorthand `### 15.1` through `### 15.9` is source-lineage only, with active promoted widget sections resolved by named FinalGUISpec headings rather than by minting a missing `### 15.9` section.
L00000043	- Legacy Orchestrator widget inputs such as `/Tiers`, `Orch/Tiers`, `widget.tier_tree`, `PuppetMasterEvent`, `PuppetMasterEvent::TierChanged`, and `TierChanged` are compatibility evidence only. Live hostability does not restore `Dashboard, Usage, Orchestrator widget tabs`; non-Progress Orchestrator surfaces use native views, while `Progress` may host widgets over canonical projections.
L00000044	- Layout migration SSOT keeps `dashboard_layout:v1` only as an import source or rollback backup; canonical Dashboard writes go to `widget_layout:v1:dashboard`, and the legacy `dashboard_layout` / `dashboard_layout:v1` keys are not updated or retained as peer layout state after migration completes. Retired Orchestrator layout namespaces `widget_layout:v1:orchestrator:tiers`, `widget_layout:v1:orchestrator:evidence`, `widget_layout:v1:orchestrator:history`, and `widget_layout:v1:orchestrator:ledger` remain compatibility-only import evidence, not live widget layout targets.
L00000045	- `Plans/GUI_Rebuild_Requirements_Checklist.md` / `/GUI_Rebuild_Requirements_Checklist.md` is a follower, not a source. Any `PASS` for `/open`, cross-cutting widget coverage, or `Tiers` is valid only after current owner docs pass the Progress-only, route/open, and runtime-recovery model.
L00000046	- `Plans/Widget_System.md` / `/Widget_System.md` removal remains lightweight and locally undoable, but canonical concern actions and `/governance` records do not inherit Widget_System / `Widget_System.md` removal policy.
L00000047	- Settings scope follows this hierarchy: `App / Global` owns broad product defaults and `/catalogs/capabilities`; `Project` owns primary execution policy; `Seam` carries meaningful feature-level overrides; `Package` carries local `/recovery` overrides; `Node` is rare and targeted; `Actor / Role` covers cross-cutting `/account/persona/worker` policy; `Runtime only` is computed truth, not user configuration.

Widget_System consumes `Orchestrator_Page` / `Orchestrator_Page.md` for the active `Progress`, `Plan Compile`, `Seams`, `Node Graph`, `Evidence`, `History`, `Ledger` page model and does not treat `Tiers` as a live widget tab.

L00000050	- Performance and fallback rules cover `Plan Compile`, `Seams`, `Node Graph`, `Evidence`, `History`, `Ledger`, Progress widgets, and cross-tab inspectors. A projection-derived inspector falls back to `Ledger` / `History` or an exact record view via `detail_ref`.

L00000085	## 4. Orchestrator Progress widget scope and catalog linkage
L00000086	
L00000087	
L00000088	### Progress-only widget hostability
L00000089	
L00000090	Only the Orchestrator `Progress` surface is widget-composed. `Plan Compile`, `Seams`, `Node Graph`, `Evidence`, `History`, and `Ledger` remain native views, and no other Orchestrator tab may opt into widget composition.
L00000091	
L00000092	Tier-first widget catalog assumptions are compatibility-only; Widget_System hostability follows the Orchestrator Progress-only rule and must not broaden widgetization across native Orchestrator tabs.
L00000093	
L00000094	The Orchestrator UI composes exactly one consumer widget: the `Progress` widget with ID `widget-orchestrator-progress`. This widget occupies a dedicated layout space within the Orchestrator UI and receives orchestrator-native runtime events, progress markers, and node-level state.
L00000095	
L00000096	`orchestrator:progress` persists in its own layout namespace and does not share layout keys with Dashboard or Usage. Layout resets, imports, and overrides for Dashboard or Usage do not rewrite Orchestrator Progress placement.
L00000097	
L00000098	### Catalog source and drill linkage
L00000099	
L00000100	The Progress widget ID (`widget-orchestrator-progress`) is defined in the current promoted widget catalog in `Plans/FinalGUISpec.md` Appendix C (§ C.2, § C.4). Widget_System consumes that named catalog source directly and does not invent an independent catalog or additional widget cards.
L00000101	
L00000102	The full 13-widget Progress catalog and default drill targets are:
L00000103	1. `progress.run-overview` → Execution unit tree scoped to `focused_run_id`
L00000104	2. `progress.current-task` → Node inspector for the active execution unit
L00000105	3. `progress.lane-health` → Lane row filtered to the selected lane or worktree
L00000106	4. `progress.node-throughput` → Dense node list filtered to slow or blocked nodes
L00000107	5. `progress.blocked-concerns` → Concern lane filtered to `blocked` or `attention_required`
L00000108	6. `progress.approval-queue` → Concern inspector showing pending approvals
L00000109	7. `progress.recovery-status` → Recovery timeline for the selected concern or blocked episode
L00000110	8. `progress.artifact-receipts` → Artifact browser filtered to receipt-linked runtime artifacts
L00000111	9. `progress.worktree-state` → Source Control worktree row with lane, package, and run refs
L00000112	10. `progress.account-pressure` → Historical `account_pressure_episode` list
L00000113	11. `progress.account-switches` → Historical `account_switch_event` list
L00000114	12. `progress.escalation-stack` → Project attention view focused on the shared escalation ladder
L00000115	13. `progress.attention-summary` → `project_attention_item.primary_route_payload` list
L00000116	
L00000117	Drill-through and linkage semantics (`progress` → node, `progress` → lane, `progress` → evidence) are owned by the Orchestrator UI and by the FinalGUISpec consumer contract, not by Widget_System hostability rules.
L00000118	
L00000119	Transferred Progress labels and taxonomy:
L00000120	- State labels: `queued`, `running`, `attention_required`, `blocked`, `recovering`, `degraded`, `complete`
L00000121	- Action labels: `Inspect`, `Focus run`, `Open evidence`, `Request approval`, `Acknowledge`, `Dismiss`, `Resolve`, `Retry recovery`
L00000122	- Alert taxonomy: `advisory`, `attention_required`, `blocked`, `escalated`, `degraded_projection`
L00000123	- Event taxonomy: `run_started`, `node_started`, `node_completed`, `concern_opened`, `approval_requested`, `approval_decided`, `recovery_started`, `recovery_completed`, `artifact_published`, `account_switched`
L00000124	- Condition-aging policy: advisory warnings may quiet after one stable refresh window; `attention_required` resurfaces on meaningful change or persistence; `blocked` and `escalated` never auto-quiet
