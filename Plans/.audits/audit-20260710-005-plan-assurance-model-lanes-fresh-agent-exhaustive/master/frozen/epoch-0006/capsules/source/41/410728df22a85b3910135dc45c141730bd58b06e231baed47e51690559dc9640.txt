L00001906	### 5.4 Host-aware LSP persistence and restart behavior
L00001907	Rules:
L00001908	- LSP lifecycle and restart budgets are persisted by host-aware session key
L00001909	- restart/reconnect preserves enough state to disclose whether a projection is current, refreshing, stale, degraded, or unavailable
L00001910	- remote-mode projects never restore into a silent local fallback path
L00001911	- On crash, `/transport` loss, or `/sync-loss` restart, PM recreates the host-aware LSP session and replays all currently attached documents for that session/root in deterministic URI order.
L00001912	- Automatic restart uses the persisted restart budget and backoff state; after the bounded crash budget is exhausted, the session remains `Degraded` until user retry, and a user-initiated restart resets the budget/backoff counters.
L00001913	- Each host-aware LSP session keeps a bounded protocol/state trace buffer for operational/debug inspection only, not canonical app history; the surfaced trace fields include session key, root, current state, last error, restart attempt/backoff, and a recent protocol trace reveal action.
L00001914	
L00001915	Implementation spec:
L00001916	- key: `lsp_server_state.v1:{host_id}:{server_id}:{root_hash}`
L00001917	- stores: server config, capabilities snapshot, last known status, and restart count
L00001918	- recovery path: on session restore, restart LSP servers using the persisted config
L00001919	- persisted restart counts survive reconnects so budget enforcement and degraded-state disclosure remain stable after restart

L00001923	## 6. Potential problems and solutions
L00001924	
L00001925	| Problem | Solution |
L00001926	|---------|----------|
L00001927	| **seglog corruption or partial write** | Append-only with flush and last-complete-record recovery. CRC32 per record is mandatory; validate on every read; corrupt record -> skip + recovery event. |
L00001928	| **redb corruption** | Restore from backup or rebuild projections from canonical seglog. |
L00001929	| **Projector falls behind** | Buffer events in bounded batches and checkpoint only after a successful commit. |
L00001930	| **Analytics scan blocks UI** | Run analytics scans in the background; UI shows last committed rollup plus freshness state. |
L00001931	| **Disk full / storage I/O** | Surface a user-facing error, stop unsafe writes, and retry only per storage I/O policy. |
L00001932	| **Migration failure** | Leave previous version intact; do not open a half-migrated store. |
L00001933	| **Multiple app instances** | Acquire exclusive flock on the active durable-store `lock-path` / `pm.lock` derived from the selected logical storage root or safe-local fallback before any writes. If the lock is held, enter `/read-only` viewer mode and notify the user. |

L00001962	### 8.1 Phased implementation order
L00001963	
L00001964	- **Phase 1 -- seglog foundation**
L00001965	  Build first: app data root resolution, directory creation (`storage/seglog`, `storage/redb`, `storage/jsonl`, `storage/tantivy`), and seglog writer only (envelope format, seq, flush, optional rotation by size/day). No projectors, no redb.
L00001966	  **Exit criterion:** We can append events and read them back (by tailing or reading the segment file).
L00001967	
L00001968	- **Phase 2 -- redb and schema**
L00001969	  Build: redb open under app data root, schema (namespaces/tables per §2.3: settings, sessions, runs, checkpoints, editor, rollups, review_rules), key patterns, and a migrations runner (version in meta, run migrations on open).
L00001970	  **Exit criterion:** We can read/write settings and checkpoints (e.g. put/get in `settings` and `checkpoints` namespaces).
L00001971	
L00001972	- **Phase 3 -- projector: seglog → JSONL mirror**
L00001973	  Build: single projector that tails seglog from a checkpoint, appends to the JSONL mirror (same envelope format), and persists its checkpoint in redb (`checkpoints` namespace).
L00001974	  **Exit criterion:** Tail seglog, write mirror, resume from checkpoint after restart (no duplicate mirror lines, checkpoint advances).
L00001975	
L00001976	- **Phase 4 -- projector: seglog → Tantivy (chat index)**
L00001977	  Build: projector (or second projector) that reads seglog from checkpoint, indexes `chat.message` (and optionally `chat.thread_created`) into a Tantivy chat index (fields: thread_id, content, role, ts, message_id), and persists its checkpoint in redb.
L00001978	  **Exit criterion:** Events are indexed and search returns results (e.g. by content or thread_id).
L00001979	
L00001980	- **Phase 5 -- analytics scan and rollups**
L00001981	  Build: analytics scan job (periodic or on-demand) that scans seglog (or JSONL mirror) over a time range, computes 5h/7d usage rollups, tool latency, and tool_usage (per-tool count, p50/p95, error_count per Plans/Tools.md §8.4), writes to redb `rollups` namespace, and stores a scan checkpoint.
L00001982	  **Exit criterion:** 5h/7d and tool rollups are written to redb and the UI (or a test reader) can read them.
L00001983	
L00001984	- **Phase 6 -- wire chat, editor, and Usage**
L00001985	  Build: wire chat persistence (thread list and thread content to seglog; read from redb + seglog/snapshots per assistant-chat-design), editor state to redb `editor` namespace (FileManager.md §2.9), Usage/dashboard reading rollups from redb and triggering analytics scan (usage-feature.md); emit `usage.event` with `thread_id` and `run.completed` with optional usage snapshot.
L00001986	  **Exit criterion:** Full flow works: create thread, send message, events in seglog; projectors update mirror and index; Usage view shows rollups; editor state persists.
L00001987	
L00001988	**Dependencies:** seglog writer before any projector; redb open + schema + migrations (including `checkpoints` and `rollups` namespaces) before projectors and analytics scan; projectors must not start until redb is open and checkpoints namespace exists; analytics scan must not run until rollups namespace (and scan checkpoint key) exists. Projectors may start once the seglog writer is initialized (current segment may be empty). When checkpoint is missing and seglog is empty, projector starts from position 0 and has nothing to process; when checkpoint is missing and seglog has data, projector starts from the beginning of the first segment.
