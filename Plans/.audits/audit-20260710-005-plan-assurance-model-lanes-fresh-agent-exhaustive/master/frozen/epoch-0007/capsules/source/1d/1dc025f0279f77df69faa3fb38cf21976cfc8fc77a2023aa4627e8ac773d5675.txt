L00001379	## 10a. FileSafe and Assistant YOLO mode
L00001380	
L00001381	**Context:** In Assistant chat (see **Plans/assistant-chat-design.md** §3), **YOLO mode** means the agent runs with maximum permissions: no permission prompts. The user accepts full automation for that session; the agent can execute, edit, and run tools without asking.
L00001382	
L00001383	**Implication for FileSafe:** When YOLO is on, there is **no human approval step** before tool execution. FileSafe is therefore the **primary protection layer** for Assistant chat in YOLO mode. If FileSafe is disabled or relaxed while YOLO is on, destructive commands and out-of-scope writes can run with no further gate.
L00001384	
L00001385	**Requirements:**
L00001386	
L00001387	1. **Same FileSafe config for Assistant:** Assistant chat (and thus YOLO runs) must use the same FileSafe settings as the rest of the app (Command blocklist, Write scope, Security filter). No separate "Assistant-only" bypass unless explicitly configured.
L00001388	2. **Recommend FileSafe on when YOLO is on:** When the user enables YOLO for a chat, the GUI should recommend (or warn) that FileSafe remain enabled. Options: show a one-time hint ("FileSafe protects you when YOLO is on"), or a small indicator that FileSafe is active when YOLO is selected.
L00001389	3. **Configurable and visible:** FileSafe toggles must be easy to find and turn on/off (see §13.4 and §15.5). A user who turns on YOLO should be able to confirm FileSafe state without digging through multiple screens.
L00001390	4. **Optional: per-context override:** If product requirements later allow "relax FileSafe for this chat only" (e.g. power users), that must be an explicit, clearly labeled setting--not the default when YOLO is on.
L00001391	
L00001392	**Summary:** YOLO mode and FileSafe are complementary: YOLO removes approval prompts; FileSafe enforces hard limits (destructive commands, write scope, sensitive files). FileSafe settings must be configurable in the GUI and easy to turn on or off, and when Assistant runs in YOLO mode, FileSafe should be the main line of defense.

L00001483	
L00001484	FileSafe and permission matching MUST use the same filesystem-awareness for case sensitivity; this closes the OC-FILE-201/202 symlink-scope pair together with the case-fold comparison contract.
L00001485

L00001488	Case-sensitivity detection contract:
L00001489	- At project/worktree root initialization, PM probes case sensitivity by creating a temporary probe file (e.g., `.pm_case_probe`) and checking whether the filesystem distinguishes it from `.PM_CASE_PROBE`.
L00001490	- If the probe succeeds (both names resolve to the same inode), the filesystem is case-insensitive.
L00001491	- If the probe cannot be created (read-only filesystem, permission error, or other I/O failure), PM defaults to case-sensitive mode (the stricter assumption).
L00001492	- The detected case-sensitivity flag is cached per project root and reused for all FileSafe and permission path comparisons within that project session.

L00001496	Normalization rules:
L00001497	- On case-insensitive filesystems: apply Unicode NFC normalization followed by locale-independent lowercasing before path comparison.
L00001498	- On case-sensitive filesystems: compare paths byte-for-byte after NFC normalization only.
L00001499	- The normalization method MUST be identical in FileSafe write-scope checks and Permissions_System path-pattern matching. Divergence between the two is a security defect.
L00001500	- Symlink handling always compares the final canonical real path and the canonical real allowed root, never the lexical alias used in the request.
L00001501	- Non-existent create targets compare the canonical existing parent path plus the normalized final segment and must be rechecked after temp-file creation and immediately before rename/promote.
L00001502	- Case-fold behavior must reject ambiguous sibling collisions, including two directory entries that normalize to the same comparison key on a case-insensitive or Unicode-normalized filesystem.
