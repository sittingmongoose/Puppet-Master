L00000251	
L00000252	The compaction-immune set is partitioned into two tiers with distinct truncation rules:
L00000253	
L00000254	**Untouchable set** (never truncated under any circumstances):
L00000255	- system prompt
L00000256	- persona instructions
L00000257	- active tool schemas

L00000264	- current and recent reasoning blocks required for correct continuation

L00000277	### 2.1 Context assembly and cache preservation
L00000278	
L00000279	Prompt assembly preserves cache-friendly stable prefixes. PM keeps role-specific context compilation, compaction-aware re-reads, and once-per-phase skill bundling so repeated turns do not re-inject the same bulky context unnecessarily.
L00000280	
L00000281	ContractRef: ContractName:Plans/FileSafe.md, ContractName:Plans/Tools.md
L00000282	
L00000283	Provider-specific / per-provider cache strategy is explicit:
L00000284	- **Anthropic:** ephemeral/cache-control marker strategy. PM emits `cache_control: { type: "ephemeral" }` on eligible message blocks. Anthropic's server-side cache handles TTL and invalidation transparently; PM does not manage Anthropic cache state.
L00000285	- **Google/Gemini family:** provider-native `cachedContent` strategy. PM creates a `cachedContent` resource via the Gemini Caching API with a configurable TTL (default: 5 minutes). The returned `cachedContent` resource name is passed in subsequent `generateContent` requests via the `cachedContent` field. PM tracks the resource TTL and proactively refreshes cached content before expiry when the underlying context has not changed. Token savings are calculated as the difference between the full context token count and `cachedContentTokenCount` reported in provider usage metadata. When `cache_with_oauth` is `false` for the active Gemini surface, cache-marker emission is suppressed entirely.
L00000286	- **OpenAI family:** metadata or adapter-controlled cache-hint strategy. PM sets cache-hint headers or metadata per OpenAI conventions. Server-side cache behavior is provider-managed; PM does not track cache state for OpenAI surfaces.
L00000287	- **Unsupported surfaces:** disable cache-marker emission and fall back safely. No cache-related fields are emitted in the request.
L00000288	
L00000289	ContractRef: ContractName:Plans/Models_System.md, ContractName:Plans/CLI_Bridged_Providers.md
L00000290	
L00000291	Reasoning-block payloads MUST be preserved through replay and compaction. PM MUST first prefer provider-compatible replay or conversion of reasoning/assistant state; lossy summarization is allowed only when the target surface cannot accept the original form, and the summary MUST remain explicit about being synthesized from prior reasoning.
L00000292	
L00000293	`/reasoning` blocks are `/replay`-safe state: PM preserves or converts them before compaction, treats provider-native `reasoning_tokens` as raw mapper input, and normalizes that value into the UF-085 JSON-safe `reasoning` bucket (display/semantic alias `reasoning/thoughts`) with explicit `counting_semantics`. Raw `reasoning_tokens` may remain in redacted provider payload refs or compatibility metadata, but it is not an independent active `UsageEvent` accounting field and MUST NOT be added to `output_total` when provider semantics say output is already inclusive. PM MUST NOT silently strip thinking/reasoning content merely because an adapter lacks a native replay field.
L00000294	
L00000295	Out-of-order reasoning-block delivery through LiteLLM/Bedrock-style proxies is tolerated by the replay state machine: PM buffers or reorders provider-compatible reasoning state instead of crashing or collapsing it into lossy summary by default.
L00000296	
L00000297	ContractRef: ContractName:Plans/usage-feature.md, ContractName:Plans/Contracts_V0.md, ContractName:Plans/Architecture_Invariants.md
L00000298	
L00000299	Context-compression references such as Xeditor `_context_updates` are implementation references only. PM preserves the referenced behavior as incremental per-tool-call tool-result compression evaluated at every tool-call boundary rather than whole-session compaction; summaries retain causal replay metadata and canonical tool/result lineage.
L00000300	
L00000301	OpenCode replay evidence from `message-v2` / `message-v2.ts` is a compatibility hazard, not PM canon: synthetic compaction text such as "What did we do so far?" must be tagged as synthetic continuation or compaction metadata and must not replay as a user-authored instruction.
L00000302	
L00000303	Historical assistant serialization rules:
L00000304	- historical turns serialize the final user-visible assistant answer plus any tool/result or lineage metadata needed for causal replay
L00000305	- transient progress/status chatter, partial streaming fragments, and superseded intermediate assistant states are omitted unless they remain unresolved or are explicitly pinned
L00000306	- message boundaries remain explicit across user, assistant, system, and synthetic-continue turns so replay cannot merge stale assistant progress into a new request; the compatibility marker `/assistant/system/synthetic` resolves to these boundary markers only
L00000307	
L00000308	ContractRef: ContractName:Plans/storage-plan.md, ContractName:Plans/Contracts_V0.md, ContractName:Plans/Run_Modes.md

L00000310	#### 2.1.1 Synthetic-continue state machine and loop prevention
L00000311	
L00000312	Synthetic continue is the bounded fallback used when a provider stops because of length or context pressure but PM still has an incomplete answer that should continue within the same run segment.
L00000313	
L00000314	ContractRef: ContractName:Plans/Run_Modes.md, ContractName:Plans/storage-plan.md
L00000315	
L00000316	Eligibility rules:
L00000317	- only `regular` and `yolo` runs may auto-inject synthetic continue
L00000318	- PM considers synthetic continue only after normal compaction and cache-preserving reassembly have already run
L00000319	- synthetic continue is prohibited once a terminal `done` outcome, explicit user cancellation, HITL pause, or parent-mediated defer decision exists
L00000320	
L00000321	ContractRef: ContractName:Plans/Executor_Protocol.md, ContractName:Plans/assistant-chat-design.md
L00000322	
L00000323	State tracked per run segment:
L00000324	- `synthetic_continue_count`
L00000325	- `last_assistant_tail_hash`
L00000326	- `last_continue_prompt_hash`
L00000327	- `last_continue_reason`
L00000328	
L00000329	ContractRef: ContractName:Plans/storage-plan.md, ContractName:Plans/Contracts_V0.md
L00000330	
L00000331	State machine:
L00000332	1. **Idle** -> default state while no continuation is needed.
L00000333	2. **Eligible** -> provider stopped for `length` or equivalent incomplete-output condition and PM still needs continuation.
L00000334	3. **ContinueInjected** -> PM injects one canonical continuation turn using the prior assistant tail and current run lineage.
L00000335	4. **ContinueObserved** -> provider emits new assistant content after the synthetic continue.
L00000336	5. **Suppressed** -> PM blocks further synthetic continue because /loop-prevention rules fired.
L00000337	
L00000338	ContractRef: ContractName:Plans/Contracts_V0.md, ContractName:Plans/Run_Modes.md
L00000339	
L00000340	Loop-prevention rules:
L00000341	- automatic synthetic continue is capped at 2 attempts per run segment
L00000342	- PM MUST compare the latest assistant tail hash against `last_assistant_tail_hash`; if the tail is unchanged after a synthetic continue, PM suppresses further auto-continue
L00000343	- PM suppresses further auto-continue if the provider returns effectively empty continuation output or repeats the same continuation prompt hash without net new content
L00000344	- suppression emits `diag.synthetic_continue_loop_prevented` with the reason and leaves the run to normal failure or rotation handling instead of silently retrying forever
L00000345	
L00000346	Task-based checkpoint markers in seglog preserve prompt/session recovery points for long sessions; this recovery lesson keeps checkpoint recovery separate from synthetic-continue injection.
L00000347	
L00000348	ContractRef: ContractName:Plans/Architecture_Invariants.md, ContractName:Plans/Executor_Protocol.md

L00000387	## 3. Rotation (follow-up run spawning)
L00000388	
L00000389	<a id="ROTATION"></a>
L00000390	
L00000391	Rotation is the act of terminating a run and spawning a follow-up run (typically due to overflow/compaction constraints) while preserving continuity.
L00000392	
L00000393	
L00000394	Rotation decision boundary (canonical):
L00000395	- Deterministic compaction/pruning is attempted first against the **final assembled payload**. Rotation is considered only if the payload still cannot fit after compaction.
L00000396	- `ask` and `plan` are **rotation-ineligible**. If the payload still does not fit after deterministic compaction, the run terminates under the normal failure/budget taxonomy rather than spawning a follow-up run.
L00000397	- `regular` and `yolo` are **rotation-eligible**. A rotated follow-up run MUST inherit `thread_id`, `mode`, `strategy`, effective Persona/runtime state, and a narrowed-or-equal tool-policy snapshot.
L00000398	
L00000399	Rule: When rotation occurs, the run outcome MUST be `done.rotated` per `Plans/Run_Modes.md`.
