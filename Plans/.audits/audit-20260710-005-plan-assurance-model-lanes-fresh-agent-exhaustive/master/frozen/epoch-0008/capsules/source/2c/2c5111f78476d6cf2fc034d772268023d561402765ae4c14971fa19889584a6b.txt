L00000585	### 13.3 Cancellation and abort contract
L00000586	
L00000587	Cancellation is a first-class provider control and is distinct from ordinary request failure.
L00000588	
L00000589	Rules:
L00000590	- canceling an in-flight request means Puppet Master sends a provider-specific cancellation action for the active OpenCode transport, such as closing the HTTP stream, canceling the SSE subscription, or triggering an abort signal on the request handle
L00000591	- if partial output tokens have already been received, those tokens are retained and the normalized response is marked `completion_reason: cancelled`
L00000592	- timeout and cancel are distinct: timeout is automatic after `request_timeout_ms`, while cancel is a user-initiated action
L00000593	- after cancellation, the provider connection is returned to the connection pool when healthy, or closed and discarded when the transport is suspected to be corrupted
L00000594	- PM MUST emit `provider.request_cancelled { provider_id, request_id, tokens_received, reason: "user" | "timeout" | "budget" | "error" }`
L00000595	
L00000596	ContractRef: ContractName:Plans/Contracts_V0.md, ContractName:Plans/Executor_Protocol.md, ContractName:Plans/storage-plan.md
L00000597	
L00000598	### 13.4 Concurrency model
L00000599	
L00000600	OpenCode request dispatch is queue-backed and provider-account scoped.
L00000601	
L00000602	Rules:
L00000603	- default mode is sequential: one active request at a time per provider account
L00000604	- parallel mode is allowed only when explicitly enabled, such as subagent execution or other orchestrator-controlled fan-out flows
L00000605	- concurrency limit is configurable per provider account; default = `1`; upper bound is provider-specific and MUST respect upstream rate-limit constraints
L00000606	- when the concurrency limit is reached, new requests enter a FIFO queue
L00000607	- queued requests time out after `queue_timeout_ms` (default `30000ms`) if they have not started execution
L00000608	- different accounts for the same provider have independent concurrency limits and independent queues
L00000609	- PM MUST emit `provider.request_queued { provider_id, request_id, queue_position, queue_depth }` whenever a request is queued instead of starting immediately
L00000610	
L00000611	ContractRef: ContractName:Plans/Multi-Account.md, ContractName:Plans/Executor_Protocol.md, ContractName:Plans/Contracts_V0.md
L00000612	
L00000613	### 13.5 Streaming error recovery
L00000614	
L00000615	Streaming recovery preserves already-received output while keeping retry ownership aligned with PM runtime policy.
L00000616	
L00000617	Rules:
L00000618	- if the connection breaks mid-stream, PM MUST:
L00000619	  1. retain all tokens received so far
L00000620	  2. mark the partial response as `completion_reason: stream_error`
L00000621	  3. attempt reconnect when `auto_retry_stream: true` (default)
L00000622	  4. include `partial_response` context in the retry so the model can continue when the provider supports continuation from partial output
L00000623	- provider support for continuation from partial output is not universal; when unsupported, PM preserves the partial output and surfaces the stream error without fabricating a seamless continuation
L00000624	
L00000625	Rate-limit handling:
L00000626	- on HTTP `429`, read `Retry-After` when present; otherwise use exponential backoff `1s → 2s → 4s`
L00000627	- maximum rate-limit retries = `3`
L00000628	- after the retry limit is exceeded, fail the attempt with `failure_class: rate_limited`
L00000629	
L00000630	Token/budget handling:
L00000631	- if the model hits its output token limit during streaming, the response ends normally with `completion_reason: length`
L00000632	- if PM budget enforcement triggers mid-stream, PM terminates the stream, keeps the partial response, and marks `completion_reason: budget_exceeded`
L00000633

L00000707	### Required rules

L00000709	- OpenCode transport reconnect logic may reconnect only to observe an existing attempt; it MUST NOT silently resubmit prompts, reset attempt identity, or invent provider-local fallback loops
L00000710	- once a prompt/request has been accepted for execution, any retry decision MUST round-trip through the canonical runtime scheduler and failure taxonomy
L00000711	- OpenCode-specific auth, transient, structured-output, and tool-denial signals MUST normalize into canonical `blocked_reason_code` / `failure_class` values before orchestration or UI consumes them
L00000712	- prerequisite resolution after auth or permission recovery MUST surface a canonical scheduler wake and create a new attempt snapshot rather than mutating the blocked attempt in place
L00000713	- a `safe_point_id` created before a mutation-capable OpenCode attempt remains attached across the entire request/stream lifecycle
L00000714	- recovery restores that rerun work use a new `attempt_id` while preserving lineage references to the restored parent context
L00000715	- replan invalidation MUST be checked before rerunning a blocked or retried OpenCode attempt; stale attempts from an older `replan_generation` must not resume silently
