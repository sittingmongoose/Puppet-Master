### Where to work
- Never work on `main` in the shared checkout `/mnt/Cursor/PuppetMaster`. It is for landing only.
- Make your own worktree and branch from the current `main`, on the VM's local disk under `~/pm-worktrees/`, never on the mount. The mount is a network share: every `git status`, checkout and regeneration in a worktree there walks the tree over NFS and slows every other agent, and the periodic scans that the Codex app-server and the Claude desktop server run against an open checkout do the same. A sparse worktree is under 1 GB and the VM disk has room. The first line is still required even on local disk: the worktree's git directory lives inside the shared checkout's `.git` on the mount, which assigns it to another owner.
  ```
  git config --global --add safe.directory ~/pm-worktrees/<name>-<date>
  git -C /mnt/Cursor/PuppetMaster fetch origin
  git -C /mnt/Cursor/PuppetMaster worktree add --no-checkout -b <kind>/<name>-<date> ~/pm-worktrees/<name>-<date> origin/main
  cd ~/pm-worktrees/<name>-<date> && git sparse-checkout set Plans scripts reports Concepts && git checkout <kind>/<name>-<date>
  ```
  Drop directories you do not need from the sparse set. Branch kinds: `research/`, `audit/`, `concept/`, `plans/`, `fix/`. The object store and your worktree's index stay with the shared checkout on the mount; only your working tree is local. That removes the per-file scan over NFS, which is what made git slow, but it does not make every git operation local.
- Open your thread, IDE or Codex session in your worktree, not in the shared checkout, so the harness scans hit local disk.
- Worktrees that already exist on the mount under `/mnt/Cursor/PuppetMaster-research/` may finish the branch they are on; create no new ones there.
- In T3 Code, the Puppet Master project is a full local clone of this repository on each machine (`~/src/PuppetMaster` on the VM and the Mac, `C:\Users\sitti\src\PuppetMaster` on Windows), and T3 creates each thread's worktree and branch from it on local disk; that replaces the `~/pm-worktrees` recipe above for T3 threads. Fetch `origin/main` before you branch, push your branch after every landing-sized step, and land exactly as "How to land on main" says, from the shared checkout.

### How to commit and push
- Commit only the paths you changed, with a message that says what they are. Never `git add -A` or `git add .`. Never commit another thread's edits.
- Push your branch after every landing-sized step. Unpushed work does not exist.
- If you edited a `Plans/*.md` document, regenerate its derived files and commit them with the edit: `python3 scripts/pm-shard-plans.py --generate --config Plans/sharding_config.json` then `python3 scripts/pm-plan-index.py generate`. Regeneration is deterministic; if files for documents you did not edit change, stop and report.
- Governance reseals (`Plans/Spec_Lock.json`, `Plans/.evidence/**`, readiness artifacts) are never part of ordinary work. There is no standing Plans agent: a reseal is its own task, done only by an agent Jared assigns to that reseal, following the latest `reports/governance-reseal-*/reseal-record.md`, and a landing that leaves governance staleness reports a reseal request to Jared instead of resealing. A reseal's scope includes the one required row in `Plans/auto_decisions.jsonl`, the `refresh-batch-hashes` and `refresh-final-summary` pair on migration run `pds-20260611-002-atomize-planunits`, the run the aggregate checks validate (`pm-plans-verify.py` `DEFAULT_PLAN_MIGRATION_RUN`), and the currentness edition written in place after a backup; the landing agent refreshes the run named in `current_run.json` with `snapshot-current` in a full local worktree at the new `main` after a landing that changes `Plans/`.

### How to compile a ledger
- Compiling a ledger into owner prose is one task; its schema, fixture and gate companions are a second task. Do the prose first and nothing else, then the companions.
- Between the two, run the compile witness: `python3 scripts/pm-ledger-compile-witness.py Plans/ledgers/v2/<ledger_id> --base origin/main`. It is a static text check with no model in it: every unit a findings record claims to repair must be a compile target and must actually differ from the base revision, every exact token of a compiled atom must appear in an owner unit's prose and in that unit's `preserved_exact_tokens`, and every registered token must occur in its own unit's text. Run it before the compile review, not after.
- A compile is ready to land when the deterministic checks pass and one blind form-driven review has run, with a cycle cap of two. Whatever is still open after the second cycle is written down as an open ledger question rather than argued further.

### How to land on main
- Before the fetch for a landing, run `mkdir /mnt/Cursor/PuppetMaster-Evidence/scratch/landing-lock/held`; success means you hold the landing lock, so write your agent name, branch and UTC time to `held/holder.txt`, hold it through the fast-forward, the checks, the push of `main` and the worktree removal, and release it with `rm -r` of that directory; if `mkdir` fails, read `holder.txt` and clear the directory only if its latest time is more than 90 minutes old, otherwise wait five minutes and retry. A holder whose landing runs long (a check in the shared checkout, a follow-up) rewrites the time in `holder.txt` at least every 25 minutes, so the 90 minutes count from its latest time; rewrite it atomically by writing a temp file in `held/` and renaming it over `holder.txt` (`python3 -c` with `os.replace`), never with `>` or `open(..., 'w')` on `holder.txt` itself, because an instant of an empty file makes `verify` and `batch-check` refuse a holder they cannot read. On the remote-host route the check itself runs BEFORE you take the lock; take it for `verify`, the fast-forward, the push, the follow-up and the worktree removal. This is the one lock procedure for every lander, whichever route its checks take; `reports/landing-checks/README.md` follows it and adds no other lock. Branch pushes need no lock, and `main` is never pushed without holding it.
- `git fetch origin`, then `git rebase origin/main` on your branch. For Plans edits, re-read every passage you cite against the current text before applying; a passage that changed since your snapshot is re-adjudicated, not merged blind. Never hand-merge `_shards` or `.plan_index`; regenerate them.
- In the shared checkout, if `git status` shows uncommitted changes in any file your branch touches, stop and hand the branch over. Otherwise `git merge --ff-only --no-overwrite-ignore <branch>` (if it refuses because an ignored file is in the way, stop and hand the branch over with that path; never delete or move the file to make room), run `python3 scripts/pm-shard-plans.py --check --config Plans/sharding_config.json`, and push `main`. A fast-forward of the shared checkout's `main` is pushed in the same step or reset back immediately with `git reset --keep origin/main`, never left ahead of `origin` while checks or repairs run elsewhere; never use `--hard` in the shared checkout, because it would discard other threads' uncommitted work.
- The shard check reads the working tree, not `HEAD`, so another thread's uncommitted work in the shared checkout can fail your landing. Run the check in your own worktree before you land, so a failure at landing can only be someone else's. If every failure names files your branch does not touch, confirm `HEAD` is consistent (`git cat-file -e HEAD:<named shard>` succeeds and `git show HEAD:<its manifest>` references it), push `main` anyway, and report the failing files to Jared. Never fix or commit another thread's files to make the check pass. If any failure names a file your branch touches, stop and fix it on your branch first.
- **Checks on a remote host (from 2026-11-22; Jared approved moving landing checks off the VM).** Instead of running the landing check on the VM, a lander may run it on a chosen idle host with `python3 -B "$PM_LAND_SCRIPT" check <branch> --on <host>`, where `PM_LAND_SCRIPT` is the absolute path of a trusted copy of `scripts/pm-land.py` as `reports/landing-checks/README.md` says (the shared checkout may not have the script before its first landing), (default `nas1`, the measured fastest host until a new measurement changes it; if it is busy or down, use another configured host, or run the check in the shared checkout as the next bullet says) and then, under the landing lock, run `python3 -B "$PM_LAND_SCRIPT" verify --receipt <path> --commit <full SHA> --base <full origin/main SHA>` in the shared checkout twice: immediately before the fast-forward and again immediately before pushing `main`, always passing `--commit` and `--base`. `verify` exiting 0 confirms only that the receipt is for exactly this commit and these inputs; it prints the recorded checker exit, and that exit decides the landing exactly as the bullets below say (2 or 3 stops it, even though `check` and `verify` themselves exit 0). `verify` binds the exact checked commit, tree, full `origin/main` base, full ignored-input inventory (paths and SHA-256), report SHA-256 and recorded checker exit, and refuses, naming the paths, any dirty shared checkout (any staged change, any modified or deleted tracked file, or any hidden index flag), an ignored-input file that differs or is missing, an untracked file the checks read, and an ignored file at a path the branch newly tracks. `check` removes its temporary remote worktree only after a completed check (`exit_code` 0, 1 or 2) whose job and process tree (the systemd unit cgroup, or every descendant proven ended under `setsid`) have ended; failed runs (including checker exit 3) and runs with live or unverified processes keep the remote copy and report its path. Landers keep doing the lock, fast-forward, shard check, push and worktree removal by hand; every other rule in this section (exit codes, baseline, staleness and follow-up) is unchanged.
- **Land in batches (from 2026-11-23; Jared approved the change on 2026-11-06).** Several landings may share one snapshot and baseline follow-up instead of one each. A batch is one continuous hold of the landing lock. Open it by writing `batch-start: <full SHA of origin/main before the batch's first landing>` into `held/holder.txt`, and add one line `batch-landing: <branch> <main SHA it pushed> <the record.json its check printed>` for each landing as it lands. Every landing check inside the batch is measured against the batch-start instead of `origin/main`: on the remote-host route, `python3 -B "$PM_LAND_SCRIPT" check <branch> --on nas1 --base <batch-start>` before you take the lock, which also asks that check for its row report, and under the lock `python3 -B "$PM_LAND_SCRIPT" verify --receipt <path> --commit <full SHA> --batch-start <batch-start>`. `verify` in batch mode accepts a receipt whose base is the batch-start only while `holder.txt` still names that open batch and every commit `origin/main` has landed since the batch-start is covered by its `batch-landing` rows, which climb from the batch-start to the current `main` (a row names one landing, however many commits it pushed); the receipt stays bound to its commit, tree, ignored inputs, check report and row report by SHA-256, and a batch-start is a full SHA, never a moving name. A landing on `main` that the holder does not list makes both commands refuse with "repair the holder, then rerun": the rows, not the commit count, decide what has landed. A plain `verify --base <the current main>` is refused while `holder.txt` names an open batch whose `batch-start` is behind `origin/main`: a landing inside the batch is verified with `--batch-start`, and nothing else lands until the batch closes. `verify` prints `PUBLISH_LEASE=<the origin/main it pinned>`; lease the hand push on exactly that value, never on a reread of `origin/main`. The batch's closing follow-up is verified with `python3 -B "$PM_LAND_SCRIPT" verify --receipt <path> --commit <full SHA> --batch-close` (no `--base`): `holder.txt` must still open the batch, `origin/main` must be its last `batch-landing` row, and the commit must include the refreshed `reports/landing-checks/baseline.json` and may change only `Plans/.plan_migration/**` and that baseline. So the check judges the whole batch as one branch: every path any landing in the batch touched counts as the branch's, the baseline's currency is measured against `batch-start`, and the exit codes mean exactly what they mean for one landing. The follow-up's own check uses `--base origin/main`. **The strict rule, for the second and later landing:** `python3 -B "$PM_LAND_SCRIPT" batch-check --receipt <this member's record.json>` compares this member's report with the one before it, read from the holder's last row and re-hashed against its receipt, and this member may stay only when the two reports are identical in every subcheck total, every bucket count, every row key wherever both row reports print every row, and every subcheck's known or sampled status. The one allowed difference is governance staleness in buckets that name a file this member's own branch touched, printed in full in its report; a subcheck that is a permanent sample, which the producer positively identifies as one whose validator writes no complete export, is compared on its total only, and its total must be unchanged. Anything else means this landing is judged alone: a rise, a fall, a gone or new row, a changed key, a count not fully known, a status change, or a mapping the tool cannot read, and `batch-check` names the first difference. The first landing of a batch is judged exactly as a single landing is today. `verify --batch-start` runs that same judgment itself under the lock, against the same pinned predecessor it publishes on and with this member's existing receipt; an earlier `batch-check` result is never enough, because a handoff can change which member the receipt is. The lock passes from one lander to the next inside a batch only by pm-mail between the two, with `holder.txt` rewritten atomically (a temp file renamed over it, as the lock bullet says), keeping the same `batch-start`, every `batch-landing` row and `batch-first-push` line, and the current UTC time; nobody outside the batch lands until it closes, and the 90-minute rule above counts from the latest time in `holder.txt`. Whoever clears a `holder.txt` that names a `batch-start` closes that batch first, with its follow-up at the current `main`, before landing anything of their own. Don't open a batch when the baseline is within two hours of being seven days older than `origin/main` (the check measures that from `batch-start`, so a batch opened there judges every member alone), and never refresh the snapshot or baseline in the middle of a batch: the refreshed baseline's commit is not an ancestor of `batch-start`, so pre-existing failures would stop counting as pre-existing for the rest of the batch. Record the batch's first push of `main` as `batch-first-push: <YYYY-MM-DDTHH:MM:SSZ>` in `holder.txt`; without it the tool reads the first landing's commit time, and a branch committed long before it was pushed then reads as past the two hours at once. A batch takes at most four landings and two hours from that first push, and its holder's latest time must be under 90 minutes old: `batch-check` and `verify --batch-start` refuse a landing past any of those, and that landing is judged alone. A landing that needs a reseal or an exemption Jared granted is never part of a batch: close the open batch first and land it alone. A landing check that stops a landing inside a batch is a stop like any other: don't push it, close the batch with its follow-up at the current `main`, then rebase it on the new `origin/main` and judge it alone. A batch with a hand landing in it closes at the next landing: a hand landing leaves no report to compare with. Put a batch's Plans landings first: the first canon edit after non-Plans landings adds whole-snapshot rows that no earlier report holds. The batch closes with one follow-up (the `Plans/` follow-up bullet below) at its final `main`, done by whoever holds the lock then; a batch that touched no `Plans/` path needs none. Then release the lock. `python3 -B "$PM_LAND_SCRIPT" batch-status` prints the open batch, its landings and the limits, writing nothing.
- On the shared-checkout route, run the landing check after the fast-forward and the shard check and before you push `main`; on the remote-host route it runs on the remote copy BEFORE the fast-forward, as the bullet above says. Its recorded exit decides, even when its JSON shows zero blockers. The command: `python3 scripts/pm-landing-check.py --base origin/main`. It has to run before the push: it measures your branch by what `git diff --name-only origin/main..HEAD` names, and once `main` is pushed that list is empty. It runs the same three read-only repository-wide checks (`pm-plans-verify.py run-gates`, `pm-plans-verify.py audit-governance`, and `pm-plan-migration.py validate` against the run named in `Plans/.plan_migration/current_run.json`) and reports only two things: failures that are new since the recorded baseline `reports/landing-checks/baseline.json`, and failures that name a path from `git diff --name-only origin/main..HEAD`, less `Plans/_shards` and `Plans/.plan_index`, whose failures are matched on the units of the documents your branch changed rather than on their own regenerated paths. A per-plan seal no longer runs these checks, so landing is where they run, and they still cost about ten minutes; what changed is that you no longer read several thousand pre-existing failures to find the few that are yours. It exits 0 when it has nothing to report and every subcheck finished, 1 when nothing it reports stops the landing (governance staleness on files your branch edited, pre-existing failures whose baseline count has not risen, failures that are new but name none of your files, or a subcheck that timed out), and 2 when it reports something that does stop it: a failure on your branch's files that is neither staleness nor pre-existing, a bucket that grew whose error kind is not staleness, or a rise in a truncated subcheck other than the readiness growth counter and a run-gates copy judged by its complete audit-governance copy. A failure counts as pre-existing only while the baseline is current, its commit an ancestor of `origin/main` and no more than 7 days older than it; otherwise the report's first lines say the baseline is stale and must be re-recorded before the next landing, never to pass the one at hand, and such a failure on your files stops the landing. A subcheck that timed out is an infrastructure result, never a failure of yours: the run was not fully verified, so it lifts exit 0 to 1 and changes no other exit code.
- The two aggregate checks print only the first 50 (run-gates) or 100 (audit-governance) failures of each subcheck, so the failures past that cap are never keyed and the match against your branch's paths runs over the printed sample, not over every failure. Such a subcheck is compared by its total only, because which rows it prints can change with nothing added or removed; a rise in that total stops the landing, since nothing can say whether what was added names a file of yours. There are two exceptions. The readiness validator's total is the readiness growth counter, and its rise is staleness, which does not stop the landing, when at least one stale row it printed is new or grew and names a file your branch touches, and no printed row that is not staleness is new or grew. The run-gates copy of a validator is judged by its audit-governance copy instead of by its own total when that copy, run at the same version in the same landing check, reports the same total, printed every failure now and when the baseline was recorded, and lists every row the run-gates copy printed. The check prints which subchecks are truncated, how many failures that leaves unkeyed, and which run-gates copies it judged by their audit-governance copy, and why. A subcheck whose validator writes a complete export is keyed from that export when the export's total matches the printed total, and is then not truncated; the check prints which subchecks were keyed this way.
- `Plans/_shards/**` and `Plans/.plan_index/**` do not count as files your branch touched. Regeneration rewrites them whole, so they name every unit in the repository rather than the ones you edited. A failure recorded against them is matched instead on the `plan_unit_id` in its own record, against the units owned by the documents you actually changed.
- What to do with what it reports. A failure that names a file your branch touches and is neither governance staleness nor pre-existing stops the landing: fix it on your branch. A pre-existing failure was on `main` before your branch and does not stop the landing; where its content changed on your files, compare it with the baseline's rows, since the same count can hide one failure fixed and another added. Governance staleness for documents your branch edited (Spec Lock `stale_hash`, stale owner or artifact evidence hashes, a stale readiness report, the stale plan-migration snapshot) is the expected consequence of editing canon before the next reseal; it does not stop the landing and is reported to Jared as a reseal request. A failure that is new but names no file your branch touches does not stop the landing either: push `main` and report it to Jared, exactly as the shard-check rule above reads. A subcheck that timed out does not stop it by itself, but rerun that subcheck on its own and judge what it reports by these rules before you push `main`. Never fix or commit another thread's files to make a check pass.
- Run it on a whole tree. The check refuses a sparse worktree with exit 3, because the three checks read the whole repository and every file outside a sparse cone reads as missing: a dry run on a worktree without `Concepts` and `tests` produced three blocking items and 76 new failures that were all the absent cone and none of them about the branch. Use the shared checkout at landing, or `git sparse-checkout disable` first; `--allow-sparse` overrides it for a deliberate partial run.
- When a landing changes any `Plans/` path, after its landing check and first push of `main`, the landing agent keeps the landing lock and refreshes the current plan-migration snapshot and baseline in a full local worktree at that new `main`: run `python3 scripts/pm-plan-migration.py snapshot-current` first, then `python3 scripts/pm-landing-check.py --record-baseline`. `snapshot-current` removes snapshot runs older than the one it replaces, and git history keeps those bytes, so nothing is copied to the evidence share. Commit the new run, that removal and the baseline together as one separate follow-up commit, fast-forward and push `main`, remove the worktree, then release the lock. At a batch's close, this follow-up is verified with `--batch-close` instead of `--base`, as the batch rule above says. A landing with no `Plans/` paths refreshes neither artifact. This snapshot and baseline refresh is separate from a governance reseal. Never refresh the baseline to make a landing pass: that excuses exactly the failure it was meant to show. `reports/landing-checks/README.md` says what the baseline holds and what a full checkout has to contain.
- When the branch is on `main`, remove the worktree from the clone that owns it (the shared checkout for `~/pm-worktrees`, the thread's own clone for a T3 worktree): `git -C <owning clone> worktree remove <path>`, then `git -C <owning clone> branch -d <branch>` once `git merge-base --is-ancestor <branch> origin/main` succeeds.
