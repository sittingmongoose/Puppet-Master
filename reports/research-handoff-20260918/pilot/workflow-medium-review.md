# Focused workflow review — 2026-09-08

Read-only review of `pilot_v2.py`, `research_shared_v2.py`, README and the three specified smoke receipts. Inspected the shared helper's directly delegated Store/fetch/repository/read functions to assess provenance. No models, Goals, campaigns, or run changes were made. Protocol files remain frozen. Findings below describe a future revision or explicit manual review checks, not edits authorized by this report.

## Prioritized findings and smallest fixes

1. **P1 — Batch delivery can silently skip individual leads.** `finish()` assigns the same phase job to every requested ID (pilot lines 122–126); `ready()` accepts any nonempty notes file (131–133). A reconciliation or comparison covering only one of twenty assigned IDs marks all twenty delivered. The stage label's semantic-quality disclaimer does not cure a missing deliverable: subsequent campaigns skip those omitted IDs. A timed-out or failed job with partial notes has the same effect. Smallest fix: retain the Markdown workflow, but require a minimal per-ID outcome marker and validate the requested-ID set before advancing each lead. Preserve partial notes and runtime status; leave absent IDs explicitly pending. Human assessment of evidence remains separate. The 205-lead smoke demonstrates input batching, not output-ID conservation.

2. **P1 — Later studies do not invalidate earlier review.** A zero/short deep-study budget can compare leads with pending studies, as intended. A subsequent `campaign()` studies those leads, updates their implementation/history job pointers, then skips reconciliation and comparison because old reports still satisfy `ready()` (183–203). The displayed comparison can therefore predate the evidence it appears to summarize. Smallest fix: record the upstream job IDs/content hashes used by each review and treat downstream results as stale when those inputs change. Preserve earlier reports. A manual fallback is to label these results explicitly stale and require refreshed review before any proposal/repair is promoted.

3. **P2 — Intake retains files but does not carry every unresolved direction.** Discovery `notes.md` is ingested only when no nonempty `leads/*.md` exists (57–62). The discovery prompt explicitly requests coverage and unresolved directions there; mixed output can leave useful directions outside the lead queue. Study notes can likewise contain independent follow-ups without creating the requested lead files. Origin notes are linked through `sources.md`, but their unresolved directions are not guaranteed a tracked disposition. Smallest fix: retain a separate unresolved-intake entry for aggregate notes, or have a bounded extraction/reviewer pass account for their remaining directions. Avoid falsely splitting coverage prose into established findings. Existing fallback smokes do not test mixed output.

4. **P2 — Crash/resume lacks an attachment recovery step.** Discovery is considered attempted merely because `jobs/` exists (149, 185). A crash after job directory creation or after execution but before `finish()` can leave a run with no attached leads; the next campaign skips discovery and exits with an empty queue. Interrupted study jobs similarly become orphan artifacts and can be repeated. `ingest` recovers lead files but does not restore the phase association to parent leads. Smallest fix: on resume, reconcile job specs/outcomes with run pointers, attach finished artifacts idempotently, and label interrupted attempts. Require an actual discovery delivery receipt, not directory existence. Keep retries as new jobs; do not overwrite history. The current runner exposes no explicit overall completion status, but an empty status after interruption can easily be misread as successful completion.

5. **P2 — Cached displayed text and repository working trees are not integrity-bound to their claimed sources.** URL hits verify `raw` against its hash, but reuse `text.txt` without validating its derivation/hash (`research_shared_v2.py` 35–40). The base Store hashes raw bytes while persisting that unchecked text. Repository reads/searches use a shared writable working tree while citing `HEAD`; `rev-parse HEAD` does not prove read files match the commit. An accidental or agent write could thus contaminate another job's source evidence without matching commit truth. Smallest fix: hash/verify cached extracted text as well; read tracked repository content from the pinned commit or verify a clean checkout and make cached acquisitions read-only to participants. No evidence of actual contamination was found in the reviewed receipts.

6. **P2 — “All leads enter later review” is a pass-level intention, not a guaranteed terminal property.** Reconciliation failures without notes prevent comparison; new leads ingested during reconciliation are outside its initial snapshot, and new leads from comparison also wait for another campaign. They remain in run state, so this is visible deferral rather than deletion. Record explicit pending reconciliation/comparison counts and reasons at campaign end. Also, 30,000 characters is a soft batch target: a single oversized lead/report passes through whole (170–181). Flag oversized handoffs for bounded splitting or a manual review; do not silently truncate them.

## Bounds, cache separation, and acceptable limits

- No unbounded scheduler model loop is evident in this version. Deep-study admission checks a monotonic deadline; a no-notes study breaks that loop; later review uses finite snapshots. `advance` also has an admission deadline. Per-job adapter timeouts are requested, but adapter process-tree cleanup was outside this review and is not established by these files.
- The campaign is **not wall-clock bounded by `--research-seconds`**: initial discovery, already admitted studies, and every subsequent review batch are outside that budget. This is accurately described in the README. Large lead volume means large review cost. A separate explicit review admission budget with visible pending IDs is the smallest option if a hard operational bound becomes necessary; do not add silent count truncation.
- Shared acquisition does not automatically share research conclusions. Each helper invocation reserves and writes its own request, raw/text artifacts and receipt in the job-local evidence directory; upstream report links are constructed only from the same run. Cached URL receipts retain acquisition timestamps. First-acquisition pinning is an acceptable pilot policy, and means freshness/order limitations must remain disclosed.
- Isolation is by prompt and path convention, not a filesystem security boundary. Participants have shell tools and can reach absolute cache/protocol paths; these files do not establish enforcement against reading sibling arms or evaluator material. Thus claim “no conclusions are deliberately supplied through the helper,” not proven adversarial cross-arm isolation. Ordinary separate workspaces plus an audit of suspicious out-of-scope reads is adequate for a bounded cooperative pilot; stronger benchmark claims need restricted access.
- The smoke receipts support intake retention/idempotence, input-batch membership, pending-deep visibility, and successful cache reuse. They do not prove per-ID report completeness, retry recovery, immutable extracted evidence, proposal quality, or semantic coverage. The 309 readable files/five unavailable fixtures and one run per configuration are appropriately disclosed limits, not reasons to invent broad coverage claims.

## Minimal decision handling

No production approval framework is needed. For each genuinely new feature or material choice, produce a concrete proposal entry with lead IDs, primary evidence, proposed behavior, owner/consumer locations, dependencies, alternatives/tradeoffs, acceptance checks, and a clear `pending user decision` state. Separate an existing-contract repair from a product choice; ambiguous cases remain proposals. Show the reviewable entries to the user before asking for decisions. Record the explicit decision and its exact scope; rejection/deferment remains a visible lead disposition.

Only after an authorized decision should a separate manual step patch real owner/consumer Plans, verify the changes, and record the actual patch/evidence as landed. A report or decision row is insufficient. Keep synthetic fixture changes separate from real canon. The two already-authorized September corrections do not authorize future feature choices. The current comparison prompt already expresses this boundary; the missing minimum is an explicit, reviewable decision artifact and the output/staleness checks above, not an approval UI.
