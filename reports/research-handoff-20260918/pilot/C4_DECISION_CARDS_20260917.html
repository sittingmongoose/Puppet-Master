Jujutsu research, continuation 4. Two decisions for Jared, 17 September 2026

The two product choices left over from the six-arm run

Thirteen corrections from the six arms are landing under the standing repair authorization. Two things the arms found are not corrections, because canon makes no false promise about them today. They are choices, and they are yours. Each records as a Decision Log entry.

1. Conflict and merge editors on Jujutsu workspaces: build a safe save-back, or scope them read-only?

The question

When a user opens a diff or merge editor on a Jujutsu workspace, should Puppet Master own a typed contract for saving the result back into the working copy, or should those surfaces be read-only or built-in-editor-only on Jujutsu workspaces, with a stated reason when a control is disabled?

Why it came up

Four arms reached the same territory from different directions. The plans already own every principle a well-known class of editor bugs violates: a save that turns a file the editor never saw into a deletion, an empty file confused with a deleted one, a tool that writes the working copy directly and is then described as atomic. But the surface where that class lives has no owner, no command and no schema. The Jujutsu command inventory has no conflict-editing command. The only merge-editor command rows belong to the Git adapter. And the command that opens a merge editor is gated on an availability flag that appears once in the whole corpus and is defined nowhere.

Two earlier decisions bear on this. In the Jujutsu answers you declined an external diff editor and a third-party diff library, and in the terminal decisions you chose to own the engine code rather than rely on other people's. Continuation 3 declined the arbitrary conflict editor surface for the same reasons. So the open question is narrower than it looks: not whether to add external editors, but what the built-in surfaces promise on Jujutsu workspaces.

What you get

If you build the contract: a per-file save entry typed as text, deleted, missing, binary, unsupported with a reason, symlink with target, or mode change, so a scan fact can never become a write instruction; every save bound to the repository, workspace, expected native revision and conflict identity; a preflight before the first write; application through the FileSafe ledger so a failure on one file rolls the whole save back or fences it; and any external tool run over an isolated copy whose result is imported rather than written in place.

If you scope the surfaces: diff open, merge-editor open and the Git external-merge-tool preference are read-only or built-in-editor-only on Jujutsu workspaces, the availability flag gets a definition, and a disabled control says why. Nothing new is promised.

What it costs

The contract is a new owned surface across Source Control, FileSafe and Jujutsu Integration: PlanUnits, schema, fixtures and a test matrix, and it re-opens the external-tool question you closed unless it is limited to the built-in editor. Scoping costs a handful of acceptance criteria and a reason code, and leaves the built-in editor as the only writer until its own save path is designed.

Options
  1. Scope the surfaces read-only or built-in-editor-only on Jujutsu workspaces, define the availability flag, and give disabled controls a typed reason. Revisit the save-back contract when the built-in editor's save path is designed.
  2. Build the typed save-back contract now, limited to the built-in editor.
  3. Build the typed save-back contract now, including isolated-tree import for external tools.
  4. Nothing new.
Recommendation
Option 1. It keeps the surfaces truthful immediately, follows the three decisions you have already made about owning the code and not shipping external editors, and defers the expensive part to the point where the built-in editor's design can carry it. Option 2 becomes the natural follow-up then.
Your answer
Option 1, taken as recommended on 17 September 2026 ("Do you recommendations for the choices"). Records as DL-056.

2. Bookmark controls: name the exact remote and action every time?

The question

Should every Jujutsu bookmark control and confirmation say, in ordinary words, exactly which remotes it will touch and what it will do to each, rather than presenting a combined or synced bookmark as one thing?

Why it came up

The Muse arm found that nowhere in the plans is there a vocabulary for a bookmark's state across remotes: synced, unsynced, tracked on one remote and not another, combined. The dangerous cases, such as untracking a bookmark on every remote when the user meant one, are already unrepresentable in the command schema, which binds track and untrack to a single remote identity. So the gap is not a broken promise. It is what the controls and confirmations tell the user, which is a product surface.

What you get

Confirmations that disclose the affected remotes before dispatch. Untrack on a combined bookmark confirms every remote by name, untrack on one unsynced remote confirms that remote. Rename on a tracking bookmark discloses that it untracks first. Delete-local and forget-remote never share one control. Push and fetch say all-remotes or one-remote. Pseudo-remotes and non-fetchable remotes are not shown as ordinary remotes. Unsynced, untracked or absent references are never folded silently into a combined chip.

What it costs

A bookmark-state vocabulary in the Source Control owner and confirmation copy in the command catalog. There is no forget-remote command in the frozen Jujutsu inventory, so the forget-remote label stays out unless that command is added later, which would be a separate capability decision.

Options
  1. Accept as a disclosure requirement on the owner: the vocabulary and the confirmation rules above, no new commands.
  2. Accept with changes you name.
  3. Decline; keep the current combined presentation.
Recommendation
Option 1. It costs copy and a vocabulary, adds no command, and the cases it guards against are exactly the ones users cannot undo.
Your answer
Option 1, taken as recommended on 17 September 2026. Records as DL-057.
