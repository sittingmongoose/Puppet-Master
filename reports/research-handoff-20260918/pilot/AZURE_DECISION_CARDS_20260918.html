Azure DevOps Integration research, 17 to 18 September 2026. Seven decisions for Jared

What the Azure DevOps research left for you to decide

Two full research arms on the Azure DevOps Integration plan produced 26 verified corrections, which land under the standing repair authorization. Seven things they found are not corrections, because the plans make no false promise about them yet. They are choices about what Puppet Master will do, and each records as a Decision Log entry.

1. Reading branch policies

The question

Nothing in the 43-command forge set reads the branch policies that guard a branch on Azure DevOps; the plans only promise policy information on a pull request. Should the promise be narrowed to what the plans already say, or should a read of branch policies be added?

Why it came up

Both arms found the gap and disagreed on what to do about it. Azure exposes branch policies separately from pull requests, and a user looking at a branch has no way to learn what will block a merge until they open one.

What you get

Narrowing keeps the plans truthful with no new surface. Adding the read gives the branch view the same gate information the pull request view has, before a pull request exists.

What it costs

The read is a new command with its own contract, fixtures and a provider-neutral shape, since GitHub and GitLab expose the equivalent differently.

Options
  1. Narrow the promise to pull requests now; consider the branch read later.
  2. Add the branch-policy read as a new command.
Recommendation
Option 1. Truthful now, and the read can be added when the policies region in decision 4 exists to display it.

2. What a vote is attached to

The question

No Azure DevOps vote carries a revision identity. Read literally, the plans' rule that an approval is bound to a revision makes every Azure approval stale at first observation. Should approvals be bound to the revision observed when Puppet Master read them, labelled as observed by Puppet Master, or treated as never attributable to a revision?

Why it came up

Azure records a reviewer's vote on the pull request, not on a specific iteration. Both arms found that the plans' staleness rule cannot be met by the provider as it is.

What you get

Observation-time binding gives users a usable staleness signal with an honest label. Never-attributable is strictly truthful but makes the two vote criteria in the Azure plan unmeetable and shows every approval as unbound.

What it costs

Observation-time binding needs a stored observation revision per vote and copy that says Puppet Master observed it. Never-attributable needs the two criteria rewritten.

Options
  1. Bind to the observed revision, labelled as observed by Puppet Master.
  2. Treat Azure votes as never attributable to a revision.
Recommendation
Option 1. It is what a careful human reviewer does with the same information, and the label keeps it honest.

3. Status checks and policy evaluations

The question

On Azure, a status check is both an API surface and a policy type. Showing statuses only loses the requirement level; showing policy evaluations only misses statuses no policy watches; showing both naively shows one check twice in two states. Which should the checks view show?

Why it came up

The checks command as planned asks Azure for something it cannot return, and once that is repaired the display still has to pick a source. The arms note this may not be implementable until a join key between the two exists.

What you get

A checks view that agrees with what Azure will actually enforce, or one that is complete but ambiguous about enforcement.

What it costs

A joined view needs a documented key between a status and the policy that watches it, which Azure does not publish directly; the research could not confirm one exists.

Options
  1. Evaluations as the primary list, with unwatched statuses shown separately as informational.
  2. Statuses only, with the requirement level left out.
  3. Both, joined, once a key is established; until then, option 1.
Recommendation
Option 3, which is option 1 now with the join as the stated end state. Undecided is better than decided wrongly, and this keeps enforcement visible today.

4. Where policies live in the interface

The question

The Azure plan promises policies and checks, but the two consumer owners, Source Control and the final interface specification, name only "current checks". Should there be one gate list whose rows carry their source and an enforcement column, or a new provider-neutral policies region that amends both consumer owners?

Why it came up

Without a decision, the Azure promise has nowhere to render. Decisions 1 and 3 both need the answer.

What you get

One gate list is the smaller change and keeps checks where users already look. A policies region is clearer for providers with rich policy models but adds a surface to two owners.

What it costs

One list: a source column and an enforcement column, with fixtures. A region: new units in two consumer owners and the interface specification.

Options
  1. One gate list with a source and an enforcement column.
  2. A new provider-neutral policies region amending both consumer owners.
Recommendation
Option 1. It keeps one place for "what blocks this merge" and carries enforcement explicitly.

5. A merge strategy field

The question

The merge command has no strategy field, and on Azure the omission silently selects no-fast-forward. The correction being landed states that in prose. Should the command gain a typed merge-strategy field so the choice is explicit?

Why it came up

The research found that omission reads as safety and is not; the provider makes a choice on the user's behalf.

What you get

An explicit, provider-neutral strategy the user sees before merging.

What it costs

A field on a closed command shape, a provider mapping for each forge, fixtures, and confirmation copy.

Options
  1. Add the typed strategy field, defaulting to the provider's default and always shown.
  2. Leave the command as is, with the prose statement only.
Recommendation
Option 1. A merge is the one action users cannot undo cheaply; the strategy should never be implicit.

6. Re-running a policy evaluation

The question

Azure lets a user requeue a policy evaluation. Puppet Master has no command for it. Add one?

Why it came up

When a build policy fails for a transient reason, the only recovery on Azure is to requeue; without the command the user leaves Puppet Master to do it.

What you get

Recovery without leaving the workbench.

What it costs

A new command in the frozen forge set with permissions, a receipt and fixtures, and no equivalent on some providers, so it must degrade truthfully.

Options
  1. Add a requeue command, disabled with a typed reason where the provider has no equivalent.
  2. Do not add it; link out.
Recommendation
Option 1, after decision 3 settles what an evaluation is in the interface; it is small and it closes a real gap.

7. A vote and reviewer carrier

The question

The Azure plan's two vote criteria promised things no contract shape could carry; the correction being landed amends those criteria. Should a vote, approval and reviewer carrier be added to the review contracts so the promise can return?

Why it came up

Every forge exposes votes or approvals, and Puppet Master's review view has no typed place for them.

What you get

Reviewer state in the review view, provider-neutral, with decision 2's binding rule applied.

What it costs

A new record family in the forge contracts with fixtures per provider and the interface rows to show it.

Options
  1. Add the carrier, provider-neutral, with decision 2's binding.
  2. Leave votes out of the review view.
Recommendation
Option 1. A review view without reviewer state is incomplete on every provider, not only Azure.
