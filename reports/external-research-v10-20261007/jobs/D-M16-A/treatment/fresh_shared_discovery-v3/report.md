## Shared substrate (identity / freshness; reuse invalidation)
Every captured store keys tiles flatly by (tile source, z, x, y): MBTiles `tiles(map_zoom_level,map_column,map_row)` [MBT S Tiles]; leaflet.offline by resolved URL [LO-TM:97]; osmdroid by tilesource+index [OSQ:128]; libshumate by cache_key [SHU:378]. Freshness is not part of that identity: it comes from explicit max-age/s-maxage or heuristics [R9111 §4.2, §5.2.2.1], with validators (ETag/Last-Modified) [R9110 §8.8] enabling revalidation [R9110 §13]. Automatic reuse invalidation [R9111 §4.4] fires on non-GET methods or explicit directives — a GET-only tile viewer gets almost none, so source/version changes must re-key identities manually. Tiles are small; that shapes both topics below.

## Topic 1 — resumable tile acquisition / refresh under intermittent links
**Acquisition (accepted with conditions; bulk rejected).** All captured clients acquire per tile: downloadTile→saveTile keyed by URL [LO-TM:84,97]; osmdroid saveFile(stream) [OSQ:128]; libshumate store_tile_async [SHU:957]. Resumability across interruptions comes from skip-existing (hasTile [LO-TM:206]) plus per-tile retry, not byte-range: no captured client uses RFC 9110 §14 ranges for tiles (negative lead; small tiles make per-tile granularity the natural resume unit). Bound: OSMF policy names bulk downloading ("scraping") and offline mass use as prohibited [OSMP], so acquisition must stay viewport/session-bounded; ControlSaveTiles saving a computed viewport list per action [LO-CS:139] is that bounded pattern. Unresolved: acquisition-queue persistence across app restarts — held in memory only in captured code.
**Refresh (accepted mechanism; applicability unresolved).** Conditional GET with If-None-Match/If-Modified-Since against stored validators [R9110 §13.1.2–13.1.3] revalidates without re-download; OSMF documents cache headers and conditional requests [OSMP]. Scheduling follows stored freshness (max-age) with viewer-owned grace/retry. Uncertainty: whether a given tile source actually emits validators/max-age is source-specific and unverified here — the policy page is not a header probe. Intermittent links: connectivity gating exists [OSN:33] but captured code ships no backoff/hysteresis; retry policy is the viewer's.

## Topic 2 — stale-tile display / retention when a newer version exists
**Display (accepted serve-stale; blocking refresh rejected).** Stored-first display with no staleness check [LO-TL:20] can show arbitrarily old tiles — negative finding. RFC 5861 stale-while-revalidate bounds the alternative: serve the stale tile once, refresh in background within a declared window [R5861 §3]; stale-if-error extends it as offline fallback [R5861 §4] (optional lead shared with topic 1). Display therefore needs an age/freshness read beside the blob; libshumate mark_up_to_date [SHU:543] is the recorded freshness-update counterpart.
**Retention (accepted bounded purge; unbounded rejected).** Captured bounded patterns: size_limit + async purge [SHU:378,728]; per-tile expires column with startup cleanup and purgeCache [OSQ:53,56,102,213]. MBTiles 1.3 has no freshness/retention fields [MBT] — a viewer adding retention defines its own schema (unresolved: expiry authority — server header vs heuristic vs both). Unbounded keep-everything contradicts the small-device context of every captured implementation.

## Topic comparison and discriminating checks
The topics share the substrate (identity + freshness) but consume it differently: acquisition/refresh spends freshness to decide network work (skip or validate); display/retention spends it to decide what users see and what is evicted. A shared freshness record serves both; the two policies stay independent decisions. Proposed checks (proposed, not executed): (1) probe candidate tile endpoints for ETag/Last-Modified/Cache-Control — absent headers degrade refresh to time-based re-download and make stale-display windows pure heuristics; (2) measure tile size distribution — if p95 is far below range-request payoff, byte-range resume is confirmed unnecessary; (3) kill/restart mid-acquisition — skip-existing should complete without duplicates; (4) serve stale with a revalidate window = max-age — observe staleness bounded vs unbounded. Checks 1–2 test the shared substrate per topic; 3 is topic-1-specific; 4 is topic-2-specific.

## Material findings (eight, distinct)
1. HTTP caching is the shared substrate: freshness lifetime [R9111 §4.2] + validators [R9110 §8.8] drive both refresh and stale-display decisions.
2. Resumable acquisition is per-tile skip-existing + retry [LO-TM:206], not byte-range; no captured tile client uses RFC 9110 §14 for small tiles.
3. Acquisition must be bounded — bulk scraping is prohibited by OSMF policy [OSMP]; per-view/session limits required.
4. Captured connectivity gating has no backoff/hysteresis [OSN]; intermittent-link retry policy is viewer-owned (uncertainty).
5. Refresh mechanism: conditional revalidation [R9110 §13]; OSMF expects cache-aware conditional clients [OSMP]; per-source header emission unverified (uncertainty).
6. Stored-first display without a staleness check goes unboundedly stale [LO-TL:20]; serve-stale-then-revalidate [R5861 §3] bounds it.
7. Bounded retention exists in captured code — size-limit purge [SHU] and expiry purge [OSQ] — but MBTiles 1.3 carries neither; schema is viewer-owned.
8. Shared identity is a (source,z,x,y) flat key; automatic reuse invalidation [R9111 §4.4] does not fire for GET-only viewers, so source/version changes must re-key.

## Uncertainties preserved (topic-specific)
Topic 1: per-source validator/max-age emission unverified; queue persistence across restarts unaddressed; backoff design open. Topic 2: expiry authority unresolved; RFC 5861 revalidate windows are informational, not normative; eviction order differs (libshumate rank/size vs osmdroid expiry). Shared substrate evidence does not by itself settle either topic's policy — preserved per obligation 4.

## Disposition ledger
Accepted: bounded per-tile acquisition with skip-existing resume (T1); conditional revalidation (T1 refresh); serve-stale + background revalidate (T2 display); size/expiry-bounded retention (T2). Amended: stored-first display pattern amended with a staleness age-check before serving. Rejected: bulk/mirror acquisition; blocking refresh on the display path; unbounded retention; byte-range resume as default. Unresolved: per-source header support; queue persistence; expiry authority; eviction order; revalidate-window normativity.
