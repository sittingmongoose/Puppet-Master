## 1. O1 — Open discovery findings

The discovery starts from the archive’s local workflow: select recordings from removable media, preserve originals, inspect them, optionally make listening copies, and document the work. It is bounded evidence for this plan slice, not a survey of local ingest applications, audio components, or the wider project.

- **Archivematica is a workflow analogy, not a scope-matched application recommendation.** Its transfer documentation describes file identifiers, checksums, supplied-checksum verification, and original-order records; its ingest workflow has normalization decision points. Its manual-normalization documentation relates originals and derivatives and supports event detail, while its documented workflow assumes a one-to-one filename relationship. These examples support explicit source/derivative links and visible workflow states. This local desk does not need Archivematica’s wider pipeline or automation. The one-to-one filename assumption also means its workflow should not be copied as the path policy for this desk. [S14, S15]
- **BWF MetaEdit is a focused BWF/WAVE metadata product.** Its documentation describes technical-metadata tables, structural warnings, selectable validation rules, and CSV/XML export; it also documents commands that edit and save embedded metadata. The useful analogy is to show observed embedded values, validation warnings, and archivist corrections separately. Inspection in this desk must not silently edit source files. These sources do not establish equivalent behavior for FLAC or MP3 and do not select a general metadata parser. [S09, S11, S13]
- **Audio-data integrity and whole-file fixity answer different questions.** BWF MetaEdit’s embedded MD5 can cover the audio-data chunk while excluding metadata chunks. It can be supplementary evidence about the stream, but it cannot replace a whole-file digest for an untouched original or package member. [S12]
- **Archival-master preferences do not select a listening-copy recipe.** The Library of Congress describes BWF/LPCM preferences for archival masters and discusses uncompressed audio, sampling rate, word length, and channel context. That does not settle compatibility, codec, channel handling, quality, or file-size choices for these interview access copies, and does not justify transforming an already-digital source. Keep those choices explicit and unresolved until the product decision is made. [S09, S10]
- **BagIt is a concrete package-format candidate, not a demonstrated requirement.** RFC 8493 treats payload as opaque bytes, defines manifest and tag-manifest roles, and defines a valid bag as complete with every manifest checksum successfully verified. Payload-Oxum is an incomplete-bag shortcut, not a substitute for checksum validation. BagIt permits fetch.txt and deferred payload, but this desk’s proposed offline, complete-local-package policy rejects that option. For BagIt creation, RFC 8493 says tools should support SHA-256 and SHA-512 and should enable SHA-512 by default. [S01]

These findings support staged copying, read-only inspection, explicit derivative choices, and observable package validation. They do not establish that BagIt is needed, that any named product is an application dependency, or that a parser, decoder, encoder, playback engine, or desktop workflow has been selected.

## 2. O2 — Pinned implementation and governing context

The inspected component is Library of Congress bagit-python v1.9.0 at tag commit 861ddacb339d5b92659f0187a402f501d841abbe. The exact pinned bagit.py and test.py bytes are [S02] and [S03]; the release record is [S04].

At this commit, Bag.validate defaults to fast=False and completeness_only=False. It checks structure and fetch information, then content. The content path checks Payload-Oxum when present, can return early for fast=True, checks manifest completeness, can return early for completeness_only=True, and otherwise compares manifest hashes with the files. Therefore, a full-integrity reopen must use neither fast=True nor completeness_only=True. Oxum match, manifest completeness alone, and a fast check do not prove checksum equality. The pinned test test_validate_flipped_bit changes bytes without changing file size: ordinary validation catches the checksum mismatch, while fast and completeness-only modes do not. These are inspected source and test claims; no upstream test was executed for this revision. [S01, S02, S03]

Do not call bagit-python v1.9.0’s make_bag() on removable originals. Its implementation changes into the selected directory, moves its children into a temporary location, renames that location to data/, requires write access, and writes BagIt-Version 0.97. It is therefore not the proposed BagIt 1.0 package writer and can change source-directory layout. [S02, S04]

The v1.9.0 _encode_filename() replaces CR and LF but does not percent-encode a literal percent sign. RFC 8493 requires percent-encoding percent, CR, and LF in manifest paths. Issue #157 gives the corresponding percent-sequence example and was still open in the captured record. This evidence rules out this pinned writer for the proposed BagIt 1.0 use when exact filenames, including percent signs, must be preserved. The rejection is scoped to this version and behavior; it is not a claim that BagIt is unusable or that this library cannot validate every package. [S01, S02, S18]

The release’s fetch validator accepts a file: URI without a network location after the change associated with issue #153 and PR #154. This is relevant implementation history only. It does not change the desk’s product policy to reject fetch.txt and remote/deferred payload. The linked conformance-suite PR #14 remained open in the captured review record, so do not describe its proposed fixture as a merged regression test. [S02, S04, S05, S06, S17]

## 6. O6 — Complete proposed replacement plan

### P1 — Batch capture

The desk accepts an archivist-selected batch of at most 100 WAV/BWF, FLAC, and MP3 files from removable storage. It creates a local accession staging area and does not change source file bytes or embedded metadata. Before copying, it records the selected source path in a lossless, platform-tagged representation and detects unreadable files, traversal-like inputs, duplicate destinations, target case-fold or normalization collisions, reserved/unsupported names, and paths that cannot be represented on the target platform. A conflict or unrepresentable path blocks silent promotion and requires a visible archivist decision. Never overwrite a prior original or silently rename a source. Any package-path mapping must be deterministic, reversible, displayed to the archivist, and stored with the exact source-path record.

Each copy attempt uses a unique temporary destination outside the completed-original namespace. While reading the source, the application hashes the byte stream it actually observes and records its byte count and attempt status. It writes those bytes to the temporary destination, checks for read/write errors, closes and flushes the destination using the platform-supported durability operation, then reads back the completed destination and checks its full-byte count and digest against the observed stream. Before promotion, it attempts a second source read and compares that count/digest to the first observed stream to detect source change during copying. A mismatch, disconnect, read error, write error, failed flush, or unavailable required verification leaves the item incomplete or explicitly verification-limited; it is not reported as a verified accession original.

Only after required comparisons succeed may the temporary destination be atomically promoted to the accession path. The record states exactly which source stream was observed, whether the second source pass was available and matched, what destination readback and flush checks succeeded, the digest algorithm, and the resulting assurance. Matching hashes attest to the observed bytes and readback; they alone do not prove persistence after power loss. If the platform cannot confirm the required flush or directory-entry durability, report that limitation instead of claiming it. After disconnect, write failure, or restart, retain any partial bytes only as attempt-specific recovery material; rehash them before use, never trust a prior “complete” flag, and either resume after the source is reselected and checks pass or start a new attempt. No partial file is presented as an original. These are proposed contracts; recovery, atomicity, and durability behavior have not been tested.

### P2 — Inspection and notes

For each verified staged original, display duration, channel count/layout when known, sample rate, encoding/codec, bit depth where meaningful, embedded metadata, warnings, and whole-file fixity. Show the parser name/version and distinguish “not present,” “not supported or understood,” “malformed,” and “read failed.” Provide waveform and listening review for spot checks. No transcript or speech recognition is in scope.

Store parser output as an immutable observation record. Store archivist notes or corrections separately with field, observed value, corrected value, author, and time. Inspection and correction entry never rewrites the original. Optional BWF-specific rule sets may show visible opt-in review warnings; they do not automatically edit metadata, decide rights, or establish correctness for FLAC or MP3. Parser, waveform, and playback mechanisms remain open product choices.

### P3 — Listening derivatives

The archivist explicitly requests a listening copy, chooses a named profile/settings, sees the intended transformation and expected output properties, and confirms before execution. The product must decide whether that preview is only a settings/property preview or also an audible preview generated from a temporary copy; label the behavior and do not imply that one meaning is already selected. There is no default codec, quality level, channel operation, or preservation recipe in this proposal.

Every derivative has a stable link to its source item and records profile/settings, codec/container, sample rate, channel operation, bitrate or sample format where applicable, encoder name/version, parameters, output path, attempt, and result. Show queued, running, completed, cancelled, and failed distinctly. Write output to an attempt-specific temporary path. Partial bytes never count as a completed derivative and are never allowed to overwrite a source or prior derivative. Product owners must choose whether failed partial output is retained or removed and what restart/retry behavior is visible; either behavior must remain auditable and must create a new attempt.

### P4 — Accession package and reopen validation

Package only completed, sufficiently verified staging data. Retain originals and derivative references, observations, provenance, fixity, settings, tool/version, and copy/transformation dispositions. Record source-to-derivative identity and every storage-path mapping. The proposed package is a complete local directory with a versioned manifest, observations, and provenance; no remote or deferred payload is permitted.

**Format choice remains conditional.** Before selecting BagIt 1.0, product owners must establish an actual interoperability consumer and a path policy that can be represented safely across supported filesystems. If those conditions are met, use RFC 8493 BagIt 1.0 with complete payload/tag manifests and SHA-512 enabled by default. Add SHA-256 only when a compatibility need is established; if SHA-256 alone is chosen, record the reason and validate that profile. Keep the copy digest separate from this package-manifest default and record its algorithm. A custom versioned directory manifest remains the alternative if local completeness/provenance is sufficient and BagIt interoperability is not required; the trade-off is less interoperability with BagIt consumers.

Reject fetch.txt and remote/deferred payload as a product policy even though the format permits them. On reopen, perform full checksum validation of every manifested payload and tag file with neither fast nor completeness-only mode. Report missing expected manifest paths, unlisted payload paths, manifest checksum mismatches, malformed/duplicate entries, and tag-file discrepancies separately. Do not describe a missing path plus an extra path as a proved rename; an optional UI suggestion may pair them as a heuristic while preserving each raw finding. Payload-Oxum may be used only as an early incomplete-package signal. Embedded BWF audio-data MD5 may be shown separately but never replaces whole-file fixity. BagIt validation does not prove audio decodability, listening quality, correct metadata, or durable storage after a later power loss.

Do not use bagit-python v1.9.0 make_bag() on originals or treat it as the BagIt 1.0 writer. Its 0.97 output and percent-path behavior fail the proposed version/path requirements. Before implementation, either select a different pinned writer that passes the exact path/version/platform acceptance cases, build a small writer and verify it against an external conformance test suite, or choose the custom versioned manifest and explicitly accept the interoperability trade-off. No writer is selected or validated here.

### P5 — Components and environment

The application remains local and offline on Windows and Linux, never uploads interview audio, and does not edit source metadata during inspection. Keep metadata inspection, decoding/playback, transformation, and package writing as separate decisions. Before selecting a component, document pinned version/build, formats and malformed-input behavior, licensing/distribution constraints, source mutation behavior, network behavior, and platform coverage. BagIt remains a conditional format choice; bagit-python v1.9.0 remains code/validator evidence only. BWF MetaEdit is an optional BWF-specific validation analogy, not an automatic metadata editor or general audio parser. No parser, decoder, encoder, playback engine, or conversion library has been selected or validated.

### P6 — Synthetic acceptance plan

Run only after implementation, with generated media and synthetic metadata. No case below was run for this research.

1. **Copy and recovery:** verify observed-source stream and destination readback counts/digests; confirm source immutability; inject disconnect, source mutation during copy, read error, destination write error, flush error, and restart with partial temporary bytes. Confirm failed states never become completed originals, restart rehashes, retry does not overwrite, and unavailable flush/durability evidence is labeled.
2. **Paths:** test duplicate names in separate directories, target case-fold and Unicode-normalization collisions, reserved/unsupported names, traversal-like paths, Unicode, literal percent, and CR/LF where supported. Confirm the application either preserves a path or displays a deterministic reversible mapping; never silently rename or discard. For BagIt, verify percent encoding of percent, CR, and LF against the selected writer/conformance checks.
3. **Inspection:** use synthetic WAV/BWF, FLAC, and MP3 examples with known/unknown fields, malformed headers/tags, parser warnings, unusual channel layouts, absent technical fields, and mismatched embedded values. Verify observed metadata and corrections stay separate and the original hash does not change.
4. **Derivative:** use synthetic mono, stereo, multichannel, and unusual-layout samples for each profile later selected. Check properties against confirmed settings, distinguish settings preview from any audible preview, and inject interruption/failure/cancellation. Verify status, partial-file policy, retry behavior, and source immutability. These cases do not prove subjective quality.
5. **Package and reopen:** reopen a valid package, then separately delete an expected path, add an unlisted path, rename a path, change bytes without changing size, alter manifest/tag files, omit or duplicate entries, and test every selected checksum profile. Confirm reports distinguish missing, unlisted, and checksum-different paths without asserting semantic rename. If BagIt is chosen, include SHA-512 default, any SHA-256 compatibility profile, and literal-percent path cases. Reject fetch.txt/remote holes and reopen offline.
6. **Validator lifecycle:** if parallel validation is selected, test Pool-construction failure and pool.map() failure after construction on Windows and Linux. Confirm errors cannot be reported as success and workers are closed/joined or otherwise cleaned up. The pinned constructor-error test is evidence for that one case only. If parallelism is not required, compare the simpler single-process path without presuming a performance result.
7. **Scope:** generate batches of 1 and 100 synthetic files and check item states and progress. Set any performance threshold only as a separate product acceptance decision; no speed or quality result is claimed here.

## 7. Alternatives, rejected leads, and remaining decisions

- **Fixity:** Reject Payload-Oxum-only validity and embedded BWF audio-data MD5 as sole accession/package fixity. Use full-byte digests for source-copy comparisons and package members. Keep the copy digest and BagIt manifest algorithm decisions separate; SHA-512 is the BagIt creation default recommendation, while the source-copy digest remains a separately recorded product/implementation choice. - **Metadata:** Reject automatic embedded metadata normalization during inspection. Preserve parser observations and archivist corrections separately. BWF rules are optional BWF-only cues, not a general requirement across the accepted formats. [S11–S13]

- **Fetch and URI support:** Reject fetch.txt/deferred payload for the offline complete-local product. Retain file-URI validator support only as bounded upstream history, not as a product requirement. [S01, S05–S07, S17]
- **Unresolved:** whether BagIt interoperability is required; package path/version policy; copy digest and source-stability guarantee; achievable flush/durability evidence on each filesystem; parser and format-identification coverage; decoder, encoder, and playback components and licenses; derivative compatibility/quality/channel choices; settings versus audible preview; failed partial retention and retry semantics; and whether 100 files need parallel validation.
