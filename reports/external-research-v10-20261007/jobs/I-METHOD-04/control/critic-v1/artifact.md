## Overall disposition

The proposal is a coherent, useful research deliverable and its P1–P6 comparison is substantially complete. Preserve its byte-oriented ingest, per-item state, explicit derivative preview, offline constraints, candidate separation, BagIt/PREMIS distinction, and proposed-versus-executed validation labels. Do not carry its current metadata-edit and MP3 defaults into a final plan unchanged: each conflicts with stated preservation/format requirements for some cases. Add durable recovery and a few exact interoperability cases before treating the acceptance proposal as complete.

The researcher appropriately calls this a proposal, leaves shipping versions and several product choices open, and does not claim an application build or validation. My fresh independent checks confirm the important versioned claims below. Two source-backed corrections matter:

1. The pinned FFmpeg n7.1.1 libmp3lame wrapper exposes mono/stereo layouts and nine listed rates (8,000 through 48,000 Hz, not arbitrary rates). Therefore “preserving channels and sample rate by default” cannot apply to every accepted source while MP3 is the output. A multichannel source or an unsupported rate needs an explicit reject, alternate-format, downmix, or resampling choice before conversion. Do not let a preview or FFmpeg negotiation silently make it.
2. A “copied package item” that is subsequently edited is no longer the byte-identical ingest original. BWF MetaEdit v20.05 opens and saves against the same stored filename. Protecting the removable-drive source does not protect the only package copy. Keep the ingest original immutable; use sidecar corrections or a separately identified metadata-enriched rendition derived from it, with before/after full-file hashes and an event record. Resolve this before deciding where package manifests are created.

## Material to preserve

- **P1:** Copy, do not move or edit, removable-drive sources; compare full-file hashes and byte counts; stage per item; make failure/cancellation visible; keep original relative-path information and a reversible collision mapping.
- **P2:** Separate parsed observations from notes/corrections; treat absent or invalid fields cautiously; keep spot listening distinct from transcription or full listening review.
- **P3:** Keep explicit opt-in and preview. The FFmpeg documentation supports the warning about automatic stream selection (including selection by channel count) and default metadata copying. Explicit stream and metadata mapping is warranted. The proposed bitrate/downmix/tag choices remain product decisions.
- **P4:** BagIt is a credible filesystem packaging candidate, and PREMIS is correctly described as inspiration rather than conformance. BagIt validates paths and bytes; it does not define the semantics of oral-history events.
- **P5:** Keep offline Windows/Linux operation, no uploads or runtime downloads, and no metadata edits merely for display. Treat all inspected versions as research snapshots rather than shipping commitments.
- **P6:** Keep synthetic interruption, malformed metadata, unusual layouts, conversion, and fixity checks. The draft distinguishes these proposals from executed application tests.

## Consequential source verification and limits

### BWF MetaEdit code, governing definition, caller, and issue

I independently opened the immutable v20.05 source snapshot at commit `43e603dc93108f7075ad91fa83c5802f18ef2ae2`. In `Source/Riff/Riff_Handler.cpp`, `Riff_Handler::Open` stores the supplied path in `Chunks->Global->File_Name` (lines 147–175); `Riff_Handler::Save` locks its handler, reopens that stored file, writes, and reopens the same filename for validation (269–315, 341–396). The public `Open`, `Save`, `Get`, and `Set` methods wrap internal helpers with the handler CriticalSection. The governing `CriticalSectionLocker` definition enters the section on construction and leaves on destruction. The supplied GUI/Core evidence traces Save All through the threaded Core worker and per-file handler save. This supports the narrow claim that the fix serializes access to per-handler state on these paths. It does not make the tool an ingest engine, a full-file fixity mechanism, or a safe editor for the preservation original. See the linked v20.05 source, header, locker definition, and callers in [C01](sources/bwf-release-riff-handler.cpp), [C02](sources/bwf-release-critical-section.h), [C03](sources/bwf-release-Source-Common-Core-cpp), [C04](sources/bwf-release-Source-GUI-Qt-GUI_Main_Menu-cpp), and [C05](sources/bwf-release-gui-main-perfile.cpp).

The issue evidence is represented accurately but should retain its caveats. Issue #71 reports intermittent failure while applying CSV metadata changes to 10,020 WAVs; its reporter says the trigger was uncertain and later reports success with two changed variables (logging and Google Sheets). PR #112 adds per-handler locking and is explicitly linked to #71; a reporter says a supplied snapshot appeared to fix the problem. Release v20.05 lists the large-save crash fix and the inspected release commit contains the patch. This is useful manual regression evidence plus release applicability, not a controlled reproduction or automated regression test. The issue’s bulk metadata edit is materially different from this product’s 100-file ingest/derivative limit. Preserve that limited inference; do not use it as throughput or reliability proof. Evidence: [C06](sources/bwf-issue-71.html), [C07](sources/bwf-pr-112.html), [C08](sources/bwf-fix-112.patch), [C09](sources/bwf-release-20.05.html), [C10](sources/bwf-release-history-gui.txt).

### FFmpeg and BagIt behavior

I independently checked the pinned FFmpeg n7.1.1 source at commit `db69d06eeeab4f46da15030a80d539efb4503ca8`. `libavcodec/libmp3lame.c` lists supported rates and only mono/stereo layouts (lines 311–334); initialization passes the chosen channel count and sample rate to LAME (94–105). This is a direct implementation condition the researcher’s documentation-only FFmpeg review did not make explicit. Add this source and its condition to the final evidence. It makes MP3 compatibility a real constraint, while leaving the appropriate user-facing fallback a product choice. The same pinned manual supports the automatic stream and metadata-mapping observations; FFprobe’s JSON output supports a candidate technical probe, not a guarantee that every desired field is present or semantically reliable. See [C11](sources/ffmpeg-7.1.1-libmp3lame.c), [C12](sources/ffmpeg-7.1.1-commit-cli-doc.texi), and [C13](sources/ffmpeg-7.1.1-commit-ffprobe-doc.texi).

RFC 8493 supports BagIt’s payload and tag manifests, SHA-256 support, and the claim that a complete BagIt 1.0 payload must list each payload file in every manifest. It also says new-bag tools should enable SHA-512 by default. Thus SHA-256 is allowed and may be retained for the separate source/copy fixity check, but the final should either choose SHA-512 for the BagIt default or state why it deliberately uses SHA-256. The RFC requires path handling to stay inside the bag and specifically calls for tests of traversal/drive-letter namespaces; it also calls out case and Unicode normalization collisions. The draft’s traversal and case tests are good; add a decomposed/composed Unicode collision pair and verify source-path identity survives cross-filesystem mapping. BagIt manifests are corruption checks, not active-attack protection or event semantics. See [C14](sources/bagit-rfc8493.html).

The researcher’s PREMIS distinction and narrow FADGI/BWF scope are sound as stated. The LoC source says BWF MetaEdit’s embedded MD5 concerns the WAV audio data, not whole-file RIFF fixity; keep a separate package checksum. The FADGI v3 source is specific to embedded Broadcast WAVE fields and does not prescribe universal rules for FLAC, MP3, or full accession notes. See [C15](sources/premis-v3.0.pdf), [C16](sources/loc-bwf-metaedit-overview.html), [C17](sources/bwf-fadgi-guideline-v3.pdf), and [C18](sources/loc-bwf-fdd000356.html).
