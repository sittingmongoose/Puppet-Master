# D-M15-A — Transfer resume and representation identity: bounded mechanism recommendation
Arm: treatment `fresh_transport_scout-v3` (fresh transport scout; complementary scope; no sibling input read). Sources: open discovery, frozen at capture — `sources/index.json` (5 SHA-256-pinned entries: RFC 9110 HTML, tus 1.0.0, AWS S3 CreateMultipartUpload page, rename(2), open(2); man-pages 6.19, RFC June 2022). No downloaded code was executed; all validation below is proposed.

## Bounded recommendation (no full sync service)
Bind each pending transfer to one identity — a strong content hash (e.g. SHA-256) of the local bytes, computed at enqueue and stored in the transfer record. Enforce it at two gates. *Local gate:* before every resume attempt (not only the first), re-read the attachment path, re-hash, compare; equal → resume; unequal → discard the old session and start a fresh transfer of the new bytes. *Transport gate:* resume byte-range GETs only with `If-Range` carrying a strong ETag, and uploads only under protocols whose server-side validator changes with content. Bound retries (attempt count and byte-progress floor) with full-restart fallback. Scope: transfer-session mechanics and local identity only; no sync engine, conflict UI, or storage redesign is recommended. Conditions and uncertainty follow per finding.

## Material findings (8)
**F1 — Byte-range resume is safe only behind a strong validator.** RFC 9110: `If-Range` "instructs the recipient to ignore the Range header field if the validator doesn't match, resulting in transfer of the new selected representation instead of a 412." So a resumed GET under content replacement degrades to a clean full re-transfer, never a mixed 206. Requires the server to mint strong ETags. [rfc9110.html, §13.1.5/§14] Disposition: accepted.

**F2 — tus-style offset resume is session-bound and content-blind.** Captured protocol: "Given the offset, the Client uses the PATCH method to resume the upload … Upload-Offset: 70." The offset is positional state in a server session keyed by URL; the core 1.0.0 protocol carries no representation identity, so a mid-transfer replacement is invisible to it. Usable for this app only when amended with the local hash gate of F6. [tus-resumable-upload-1.0.0.html] Disposition: amended (adopt resume mechanics, add identity gate).

**F3 — Part-based upload (S3 multipart) gives per-part identity, not a public whole-object identity.** Upload is split into numbered parts, each with its own ETag, and completion presents the part list — a commit-style protocol needing up-front session creation. The composite ETag's hash semantics are not publicly specified, so it cannot serve as an app-level content identity outside the S3 protocol. [s3-api-createmultipartupload.html] Disposition: unresolved (identity semantics outside S3's own protocol).

**F4 — Atomic local replacement changes path→content binding instantly.** rename(2): "If newpath already exists, it will be atomically replaced, so that there is no point at which another process attempting to access newpath will find it missing." An in-flight transfer holding an open descriptor keeps reading the old inode consistently (standard POSIX behavior implied by atomicity; the captured excerpt does not state fd-continuation explicitly — uncertainty). But atomicity protects only in-flight reads: it guarantees nothing about the *next* open, so identity must be re-verified at each resume. [man7-rename-2.html] Disposition: accepted with recorded uncertainty.

**F5 — In-place replacement defeats any transfer-side repair.** If the app replaces content by truncating/rewriting (`O_TRUNC`-style open) instead of rename, a concurrent reader observes a truncated or mixed file; no transport mechanism can repair a corrupted local read side. The recommendation is therefore conditional on replace-via-rename; if in-place writes exist, identity gating detects the change (hash mismatch) but cannot salvage an already-corrupted partial. [man7-open-2.html] Disposition: accepted.

**F6 — Reconciliation: one identity key, two enforcement points.** The overlap of the two sides is resolved by a single binding key — the strong content hash stored with the transfer record — enforced locally (F4/F5: re-hash before every resume) and in transport (F1: strong-validator conditional resume). Neither gate alone suffices: position-only resume (F2) silently mixes replaced bytes; identity checks without atomic local writes still corrupt via F5. For tus-family sessions the local gate is the *only* identity check that exists. [all five sources] Disposition: accepted.

**F7 — Rejected identity candidates.** (a) mtime+size: not collision-safe — replacements can preserve both, and RFC 9110 treats Last-Modified as inherently weaker (dates "go back in time" after clock correction or backup restore); false resume and false abort both possible. (b) Weak ETags (`W/`) in the transport gate: weak validators assert semantic equivalence; a replaced photo is not equivalent, so only strong validators are usable. (c) Path/filename as identity: rename(2) shows the same path atomically denotes different content over time. [rfc9110.html; man7-rename-2.html] Disposition: rejected (all three).

**F8 — Retries must be bounded, with byte-progress and attempt floors.** Rural flaps make resume loops that lack an attempt/progress bound non-terminating; the retained pattern is a small bound (e.g. N attempts, require ≥ some bytes progress per attempt) and fallback to full restart under F1's validator semantics, so a bounded failure still yields correct bytes. Exact constants are app-tunable, not source-derived (uncertainty). [rfc9110.html; tus-resumable-upload-1.0.0.html] Disposition: accepted with open parameterization.

## Retained conditions, uncertainty, and open leads
Conditions: recommendation assumes HTTP-family transfer (Range/tus/multipart shaped); server control over ETag strength is the pivotal condition (U1). Replace-via-rename vs in-place write is unknown for this app (U2) and decides whether F5 corruption is live. fd-continuation after rename is asserted from POSIX semantics, not an explicit captured sentence (U3). S3 composite ETag semantics unpublished (U4). Re-hash cost per resume on rural devices is an untested assumption, bounded by photo sizes (U5). Open lead: tus checksum extension as a cheaper partial gate (per-chunk rather than whole-file) — not investigated in depth; also HTTP conditional upload (If-Match on PUT) as the mirror of F1, noted not scoped. No executed validation: V-proposals below were designed but not run (no code execution permitted).

## Validation — proposed vs executed
Proposed V1 (replace-then-resume, discriminating): enqueue a large transfer, replace the file twice — once via rename, once in-place — then force a resume. Identity-gated resume restarts cleanly in both cases; position-only resume (tus bare, or Range without If-Range) produces a mixed file for at least one arm. Proposed V2 (server-side replacement between attempts): drop the connection mid-transfer, replace server-side, resume; observe mixed 206 vs clean restart to discriminate strong-If-Range deployments from weak ones. Executed: none — both require a live transfer stack, which this scout did not build.
