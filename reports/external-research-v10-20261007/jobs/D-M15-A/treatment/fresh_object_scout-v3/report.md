# D-M15-A — Fresh object scout: transfer resume × representation identity (treatment arm)

Scope: independent open-discovery scout over transport-side resume and local-object replacement/lifecycle. Sources selected and captured during work (`sources/index.json`, sha256-bound, captured 2026-10-07). No sibling/control input used. Six source identities: RFC 9110 (HTTP Semantics, June 2022); tus resumable-upload core v1.0.0 (2016-03-24, captured from master); AWS S3 UploadPart API reference (API 2006-03-01); rename(2) Linux man page; SQLite "Atomic Commit In SQLite" (page dated 2026-04-21); Pro Git 2nd ed. §10.2 Git Objects.

## Material findings (8)

**F1 (transport).** HTTP itself supplies byte-resume primitives — Range requests, Content-Range, Partial PUT, multipart/byteranges (RFC 9110 §14) — and blesses automatic retry of idempotent requests after connection failure (§9.2.2), with Retry-After (§10.2.3) as a delay hint. Negative lead: no retry-count bound exists anywhere in the RFC; boundedness is entirely client policy. Condition: only the `bytes` range unit is standardized.

**F2 (transport).** A dedicated resumable-upload protocol (tus 1.0.0) makes the resume point explicit: HEAD returns `Upload-Offset`; PATCH must restate an offset exactly equal to the server's, else 409 Conflict without modification; the client SHOULD send remaining bytes in one PATCH but MAY split. Negative leads, retained: the core spec mandates no chunk size (common "untrusted network" attributions are absent from the captured text) and specifies no mechanism for replacing an existing upload resource. The offset is an opaque byte count — content-blind.

**F3 (transport).** S3 multipart uploads number parts 1–10,000 and define same-number re-upload as overwrite ("the previously uploaded part is overwritten"). This is existence proof that transport-side identity cannot detect substitution: replacing a part silently succeeds, and the API page states no retry bound (SDK policy, not API — negative lead). Orphan parts accrue storage until Complete or Abort.

**F4 (local-object).** Content-addressed identity (Git model: SHA-1 of `blob <size>\0` + content) makes identity derive from bytes: changed content yields a new object while the old persists — "Your object database now contains both versions." Consequence: replacement is detectable and decidable by hash comparison, not by name. Negative lead: this chapter does not cover GC of unreachable objects (deferred to its §10.7), so orphan lifecycle is open; SHA-1 collision posture unverified in the capture.

**F5 (local-object).** POSIX rename(2) gives atomic replacement — "there is no point at which another process attempting to access newpath will find it missing" — and a failed rename leaves an instance of newpath in place. Negative leads: no durability statement at all (atomic swap ≠ durable swap; crash after rename without fsync may lose data), EBUSY is optional, and the BUGS section disclaims rename atomicity on NFS.

**F6 (local-object).** SQLite's atomic commit is the canonical discipline for incomplete local writes: original content is journaled before modification, the journal flush is "critical" for power-loss survival, a "hot journal" means the file is inconsistent and must be rolled back, and the commit instant is journal deletion. Negative leads carried over: fsync is "broken on some versions of Windows and Linux" with "nothing that SQLite can do" — an unrecoverable risk on rural power/storage — and readers are protected by exclusive locking, which has no analogue in a plain staged-file upload.

**F7 (reconciliation).** The two sides fail complementarily, so their mechanisms must be joined, not concatenated. Offset resume (F2) detects stream-position drift but not replacement; per-part overwrite (F3) proves a server accepts substitution silently; hash identity (F4) detects replacement but knows nothing of wire progress; rename+fsync (F5+F6) publishes locally but says nothing about the wire. The join: key the transfer session on (content-hash, size) computed from the final file, and precondition every resume request on that hash. Offset mismatch → refuse (409-analog); hash mismatch → the local object was replaced, so abort the old session and start a new one — never resume bytes across versions. Resuming across a replacement without this check concatenates two photos into one attachment; with it, resume-vs-restart is a cheap hash comparison against an already-open file.

**F8 (lifecycle overlap).** Orphaning is a two-sided lifecycle risk with one cleanup duty. Remotely, incomplete multipart sessions bill until Complete/Abort; locally, temp/staged files and un-GC'd content-addressed objects persist. Therefore bounded retries must be paired with bounded abandonment: a retry cap that transitions the session to terminal state and triggers abort (termination extension / AbortMultipartUpload) plus temp-file removal. Otherwise "bounded retries" only bounds attempts, not residue.

## Bounded recommendation

Content-hash-keyed resumable sessions: (1) locally, compute SHA-256 of the final file; stage chunks in a temp file; (2) publish via fsync-then-rename — amended from raw rename(2) semantics, which alone lack the durability guarantee; (3) transport side, use byte-range or tus-style offset resume, every request preconditioned with the session's content hash (If-Match-style, RFC 9110 §13.1.1); (4) retries bounded, e.g. 5 attempts with exponential backoff + jitter, honoring Retry-After; on exhaustion, park or abort; (5) on replacement (hash mismatch), abort + cleanup per F8. No sync service is proposed — this is one upload path's mechanism, conditioned on: single-writer per attachment, server support for a precondition header (or client-side verification if it must be transport-opaque), and filesystems where rename is atomic (not NFS per F5).

## Validation: proposed vs actually executed

Executed here: source capture and binding only (six raw captures sha256-verified; every quoted locator grep-checked against captured bytes). Proposed, not executed: fault-injection comparison of (a) offset-only resume vs (b) hash-preconditioned resume under (i) connection kill at random offsets, (ii) file replacement mid-transfer, (iii) power loss during staged write. Discriminators: (1) zero mixed-content objects ever land (end-to-end hash on receipt) — offset-only resume is expected to fail this; (2) bytes re-sent per interruption; (3) orphan count remote+local with and without abort-on-replace; (4) torn published files after power loss.

## Dispositions

Accepted: offset-equality precondition (F2); per-part overwrite as evidence of content-blind transport identity (F3); content-hash session key + join (F7); abort-on-replace cleanup (F8); staged-write journal discipline (F6). Amended: rename(2) publish — amended with fsync (F5+F6); RFC 9110 auto-retry — amended to bounded backoff with jitter, since the RFC sets no bound (F1). Rejected: offset-only resume as sufficient under replacement; same-part-number overwrite as a versioning mechanism; unbounded retry loops. Unresolved: chunk-size guidance on untrusted networks (absent from tus core; wider tus guidance unverified); S3 SDK retry bounds (not in captured page); real-world deployment breadth of Partial PUT; SHA-1 collision posture of Git-style identity; whether the server must expose precondition support or the client verifies alone.

Uncertainty: tus text captured from `master` (drift vs the 1.0.0 tag unverified); S3 page is vendor-primary HTML (JS-augmented portions possible); RFC 9110 §13–15 wording confirmed by grep on raw text after the initial read truncated past §6.4.
