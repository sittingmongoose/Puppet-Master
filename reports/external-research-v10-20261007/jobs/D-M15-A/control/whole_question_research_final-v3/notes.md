## First useful finding (transport side: resume + bounded retries) — saved 2026-10-07T20:40Z approx

**F1 (candidate, transport/resume):** For unreliable links, resumable transfer is achievable two ways with materially different adoption costs: (a) generic HTTP byte-range resume — client re-requests `Range: bytes=<offset>-`, discovers support via `Accept-Ranges`, and uses `If-Range` (RFC 9110 §13.1.5) so that "if the validator doesn't match… [the server] transfer[s] the new selected representation instead of a 412" — i.e. the transport layer already contains the hook where "someone replaced the file mid-resume" converts into a clean restart rather than corruption; (b) a purpose-built resumable-upload protocol (tus v1.0.0): POST creates the upload with `Upload-Length`, `HEAD` returns the authoritative `Upload-Offset`, `PATCH` (application/offset+octet-stream) appends at that offset — resume becomes an offset probe, not a range negotiation. Conditional: (a) works only if the server keeps supporting ranges for the whole representation and the validator is strong (If-Range with a weak validator is invalid); (b) requires deploying/operating the tus protocol on the server. Uncertainty retained: we captured the protocol specs, not per-server support data — whether the target backend honors `Accept-Ranges`/`If-Range` for stored photo objects is unknown until probed.

**F2 (candidate, bounded retries):** Retry needs both a trigger class and a bound. curl's documented behavior names the transient class explicitly (timeout, HTTP 408/429/500/502/503/504/522/524) and bounds retries by count with exponential backoff (first wait 1s, then doubling) and by wall-clock via `--retry-max-time`; other errors are not retried unless forced (`--retry-all-errors`). Servers declare their own pacing hint through `Retry-After` (RFC 9110 §10.2.3). Composability evidence: `-C -` (continue at auto-detected offset) composes with `--retry`, so "bounded retry + resume" is an established, documented client pattern rather than a custom design. Negative lead: retry classification is client-policy, not protocol — curl treats 429 as transient while a naive client might retry on any failure; an app on rural links will see non-transient failures (connection reset mid-body) that no listed status code names, so the bound must also cover "transport-level failure without a response", which the documented trigger class only reaches via "timeout".

**F3 (negative lead, server-side write path):** HTTP offers no dependable standard server-side partial write: RFC 9110 §14.5 "Partial PUT" says such support "is inconsistent and depends on private agreements with user agents". So a range-resume design cannot assume the server accepts resumable appends; resumption via 206/Range is a read-side mechanism, and upload resume needs either full re-PUT, an app protocol (tus-style PATCH at offset), or the in-progress IETF draft (draft-ietf-httpbis-resumable-upload-13, non-normative, may change). This is the main fork for the recommendation and the interaction with local-object identity (ticket 3).

## Open uncertainties / retained
- Unknown whether target server stack supports Accept-Ranges/If-Range or tus; no per-server capture.
- draft -13 is work-in-progress (explicitly Active Internet-Draft) — cannot be relied on as normative.
- curl's "transient" list is one tool's policy; mobile/webview HTTP stacks differ (not captured).
- If-Range requires strong validators — interaction with how the app computes local identity is deferred to the local-object slice.

# Local-object / lifecycle slice (independent investigation)

Captured 2026-10-07T20:41Z: man7 rename(2), man7 unlink(2), W3C File API WD 2026-09-12, Pro Git 2nd ed. §10.2 (see `sources/index.json` rows 4-7). Write-side identity precondition anchor reuses already-captured RFC 9110 §13.1.1 If-Match.

**F4 (candidate, representation identity mechanism):** The identity of a local attachment should be content-derived, not path-derived. Git's design is the canonical public model: "Git is a content-addressable filesystem… insert any kind of content… Git will hand you back a unique key", the key being "the SHA-1 hash — a checksum of the content you're storing plus a header". Under content identity, replacing the photo simply mints a new object name; a transfer already in flight for the old name remains well-defined — there is no "same file" ambiguity to arbitrate. Conditions: digest must be computed over the stable bytes being transferred (post-snapshot), and the object store must retain the old object until its transfer completes or is abandoned. Negative lead/uncertainty: SHA-1 is Git's legacy choice for its own reasons; the app should choose a modern digest (e.g. SHA-256), and digest choice is app-private — nothing captured says server-side ETags will agree with the local digest, so identity agreement across the boundary must not be assumed.

**F5 (candidate, local lifecycle atomicity):** On POSIX-like systems the replace event itself is already safe against an in-flight transfer: rename(2) — "If newpath already exists, it will be atomically replaced, so that there is no point at which another process attempting to access newpath will find it missing" — and "Open file descriptors for oldpath are also unaffected"; likewise unlink(2): a deleted-but-open file "will remain in existence until the last file descriptor referring to it is closed". So if the transfer reads through an open handle of the old bytes, a user replacement neither truncates nor mutates the in-flight read stream; the old object persists until the transfer releases it. Negative lead: this is Linux/POSIX-man-page evidence — Windows share-mode semantics (whether a replacement can even open a file with a live reader) are NOT captured and differ; web-platform stacks behave differently again (see F6). Platform coverage is a real uncertainty.

**F6 (candidate, platform snapshot semantics):** Where the stack is web-like, the platform already fixes read-of-replaced-file semantics: W3C File API (WD 2026-09-12) gives every Blob "snapshot state, which must be initially set to the state of the underlying storage", with further normative snapshot rules for File — i.e. reads reflect the bytes as of snapshot time, not later local mutations. Condition: the snapshot must be taken when the transfer starts (or at first read), else "snapshot of what" is ambiguous. Uncertainty: WD status, not a finished Recommendation; and the spec governs Blob reads, not the app's upload queue bookkeeping.

**Bridge to transport side (for reconciliation):** RFC 9110 §13.1.1 If-Match (already captured) is the write-side counterpart of content identity: a PUT guarded by If-Match fails with 412 when the representation changed under it. So the same concept — strong, content-derived validator — exists on both sides: local (digest of bytes; F4) and transport (ETag/If-Range §13.1.5, If-Match §13.1.1). The interaction risk is not "two mechanisms to invent" but one identity convention split across a boundary; whether server ETags are strong and content-derived is server-dependent (retained uncertainty, unresolved until a target server is chosen).
