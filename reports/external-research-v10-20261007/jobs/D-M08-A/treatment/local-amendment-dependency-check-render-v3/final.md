# D-M08-A: Safe resumable-download recommendation

This is a bounded recommendation for a desktop client that saves partial GET bytes and later requests a range. It addresses the supplied critique item by item; it is not a full application plan.

1. **AMENDED — Bind bytes to the selected representation.** Store the effective target URI, contiguous byte count, strong validator, content coding, and request fields that may select the response (especially fields named by Vary). A strong ETag does not establish identity across different resources. Vary: * means the client cannot decide locally whether the saved response applies to a later request. If target, coding, or selection context changed, resume only if the same selected representation can still be established; otherwise start a full GET. ([RFC 9110 §§3.2, 8.8.1, 12.5.5](https://www.rfc-editor.org/rfc/rfc9110.txt))

2. **AMENDED; REJECTED — Unconditional overwrite on failed If-Range.** Request Range: bytes=N- for N saved contiguous octets. Prefer the saved strong ETag in If-Range. A date is allowed only when there is no entity tag and the client can establish that Last-Modified is strong. A weak tag is never valid there. A false If-Range condition makes the server ignore Range rather than return 412, but does not guarantee a successful 200 in every exchange. Replace the old file only after a complete successful full GET 200 has been received and validated; stage and atomically commit that replacement. A redirect, error, interrupted body, or other response must not be appended or treated as the full representation. After a redirect, bind any new request to the new effective target. ([RFC 9110 §§8.8.2.2, 13.1.5, 14.2, 15.3.1](https://www.rfc-editor.org/rfc/rfc9110.txt))

3. **ACCEPTED with fail-closed detail — Validate 206.** Inspect status, Content-Type, and Content-Range. For a supported single-part byte response, require a valid interval starting at N and a body octet count equal to last-pos minus first-pos plus one. That length equation is a local integrity check derived from the RFC's inclusive byte positions. For a known total, require last-pos to be smaller than the total and check agreement with a compatible saved total; these are validity and local consistency checks. An unknown total marked with * is allowed. Combine only when the same target and strong validator are established. Reject invalid or unknown range units and unsupported multipart responses; never guess that a partial 206 supplied the entire requested suffix. ([RFC 9110 §§14.1.2, 14.4, 15.3.7–15.3.7.3](https://www.rfc-editor.org/rfc/rfc9110.txt))

4. **ACCEPTED with qualification — Handle 416 separately.** Never append a 416 body. If present, Content-Range: bytes */N reports the current selected representation length; the server should send it, but its absence is permitted. The length does not prove that local prefix bytes are current. A 416 can also reject excessive or overlapping ranges. Servers may ignore Range and return 200, so handle that as a separate full-response path. ([RFC 9110 §§14.2, 14.4, 15.5.17](https://www.rfc-editor.org/rfc/rfc9110.txt))

5. **ACCEPTED — Keep coding and lengths consistent.** Byte ranges address the coded representation data. Store and resume in one consistent byte form; do not join transparently decoded bytes to a coded prefix. For 206, Content-Length describes that message's content, usually not the full representation; Content-Range describes its interval and may provide the total. Requesting Accept-Encoding: identity or disabling automatic decompression is optional advice, not a guarantee about the server or library. Check the actual response and bytes exposed to the writer. ([RFC 9110 §§8.4, 8.6, 14.1.2, 15.3.7](https://www.rfc-editor.org/rfc/rfc9110.txt))

6. **AMENDED — Refresh metadata with combined bytes.** Keep the validator, target, coding, and selection metadata attached to the bytes they describe. RFC 9110 §15.3.7.3 defines precedence: an incomplete 200 supplies the combined fields; if a 206 is combined with a stored 200, use the most recent 200 fields; with only 206 responses, use the most recent response as the base and replace matching fields with newly supplied fields other than Content-Range. RFC 9111 §3.4 requires caches that combine partial content to update stored fields from the new response. If this sidecar is not an HTTP cache, define its narrower refresh policy explicitly and never silently retain a stale validator, coding, selector, or length. Re-evaluate downstream append decisions whenever identity inputs change. ([RFC 9110 §15.3.7.3](https://www.rfc-editor.org/rfc/rfc9110.txt), [RFC 9111 §3.4](https://www.rfc-editor.org/rfc/rfc9111.txt))

7. **ACCEPTED — Proposed checks, not test results.** Test unchanged-representation resume; changed ETag followed by full-200 replacement; weak-tag refusal; a qualifying strong Last-Modified date; a shorter resource and 416 with and without Content-Range; failed If-Range followed by a non-200; partial, malformed, wrong-offset, and body-length-mismatched 206; unsupported multipart and unknown range units; changed Vary or coding; and metadata refresh after combination. Test gzip with the exact library path, including its automatic-decompression setting. These checks are proposed and were not executed for this recommendation.

8. **UNRESOLVED — Library byte exposure.** The chosen HTTP library is unspecified. The RFCs define the coded representation and range semantics, but do not establish whether this client's response API transparently decompresses or which byte form it exposes. Before implementation, test the exact writer path and record response coding, decoding configuration, and observed bytes. Until then, byte-form compatibility remains an implementation uncertainty.
