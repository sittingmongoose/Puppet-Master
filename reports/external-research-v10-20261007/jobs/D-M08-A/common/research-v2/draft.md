# Legitimate test input — untrusted candidate preliminary proposal

**Scope.** This is preliminary. No candidate-authored critique or amended upstream identity claims were supplied in the mapped inputs, so I cannot claim to resolve critique findings or adjudicate such amendments. The proposal addresses the supplied download-resume question.

1. **Bind the partial file to one selected representation.** Persist the target URI, the request fields that select the response (especially those named by `Vary`), `Content-Encoding`, and its validator. Prefer a strong ETag. HTTP defines a strong validator to change when GET-visible representation data changes, but the same validator can occur on different resources; keep the URI and selection context too. (`httpsem` §§8.8.1, 12.5.5.)

2. **Make a conditional single-range GET.** For a saved prefix of N octets, request `Range: bytes=N-` with `If-Range` carrying the saved strong ETag. Never send a weak ETag in `If-Range`; use a Last-Modified date only when there is no ETag and the date qualifies as a strong validator. Keep selection headers stable across attempts. Range is defined for GET, and a server may ignore it. (`httpsem` §§13.1.5, 14.1.2, 14.2.)

3. **Append only a verified 206 segment.** Accept a supported single-part `206` only when `Content-Range` is valid, uses `bytes`, starts exactly at the saved byte count, and the received body covers precisely its inclusive start-to-end span. If total length is known, require end < total. Reject gaps, overlap, malformed ranges, changed validators, or multipart bodies unless multipart handling is implemented. If the response supplies only part of the requested suffix, continue at the next byte under the same representation condition. `Content-Length` delimits/counts this response's enclosed data; use `Content-Range` for the full representation length. (`httpsem` §§8.6, 14.4, 15.3.7.1, 15.3.7.3.)

4. **Treat status codes as different file operations.** A `200` on resume means the server ignored Range or If-Range did not match and the full selected representation was sent: truncate/replace the prefix, never append it. On `416`, `Content-Range: bytes */length` reports the current selected representation length, not that the saved bytes are its prefix; restart with a full GET rather than declaring success from matching lengths alone. (`httpsem` §§13.1.5, 15.5.17.)

5. **Preserve the ranged byte form.** Byte offsets address the encoded representation data when a content coding is applied. Record `Content-Encoding`, keep the same `Accept-Encoding` selection, and disable transparent decompression while writing ranged bytes (or otherwise define offsets over the exact stored form). Mixing decoded local bytes with encoded range offsets corrupts the file. (`httpsem` §§8.4, 12.5.5, 14.1.2.)

6. **Keep partial data provisional.** Combine segments only when they share a strong validator. An HTTP cache may store incomplete content only as incomplete and may combine partial content only with a common strong validator; an application should not treat a partial file as a complete response. (`httpsem` §15.3.7.3; `httpcache` §§3.3–3.4.) ETags are server assertions, not cryptographic integrity proofs; optional advice: verify a separately published digest after completion. That integrity advice goes beyond these two RFC rules.

**Proposed checks (not run):** unchanged strong ETag returns matching 206 and completes; changed ETag returns 200 and replaces; ignored Range returns 200 and replaces; 416 with equal, shorter, or longer reported length does not falsely certify the partial file; malformed/wrong-offset/multipart 206 is rejected; weak ETag and non-strong Last-Modified are not used in If-Range; gzip or automatic decompression cannot shift offsets; a changed `Vary` selection starts a new partial state. Verify byte-for-byte output and no stale tail after replacement.
