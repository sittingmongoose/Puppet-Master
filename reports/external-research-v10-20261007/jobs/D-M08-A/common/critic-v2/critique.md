# Legitimate test input — candidate critique, not evaluator truth

**Reviewed input:** the mapped preliminary proposal at `research-v2/draft.md`. This is a source-grounded critique of that untrusted candidate text; it is not evaluator truth. Source identifiers and frozen hashes are listed below.

## Findings

1. **Critique findings and amended identity claims — unresolved (brief obligations 1 and 5).** The mapped draft says no candidate-authored critique or amended upstream identity claims were supplied, and the map/manifest provides none. Accept that disclosure; do not infer findings or amendments. The proposal therefore cannot demonstrate that it resolved critique findings or checked consequences of amended identity claims. Finalize only after those inputs are supplied, or explicitly retain both obligations as unresolved. (Input map; D-M08-A brief §§1, 5.)

2. **Representation identity — accept with an important condition (obligation 2).** Keep the target URI and request selection context; a strong validator changes when GET-visible representation data changes, but the same strong validator can identify different resources, so it is not a global identity key (RFC 9110 §§8.8.1, 12.5.5). Preserve the values of the fields named by `Vary` and the content coding. Add explicit handling for `Vary: *`: the client cannot decide that a stored response is appropriate for a later request without forwarding it to the origin, so do not resume from that partial state on local identity matching alone (§12.5.5). If the response supplies no `Vary`, avoid treating that as proof of global identity.

3. **Conditional range request — accept, clarify response validation (obligation 2).** `Range: bytes=N-` with `If-Range` carrying the saved strong ETag is appropriate. A weak entity-tag is forbidden in `If-Range`; a date is allowed only when there is no entity-tag for the representation and the date is a strong validator (RFC 9110 §13.1.5). Keep the selection headers stable. If a 206 omits the validator, do not treat omission itself as a changed validator: a 206 to an `If-Range` request can omit non-required representation fields because the client already has the prior response (§15.3.7). If a validator is present and conflicts, reject the segment. A server may ignore Range; a 200 is the full selected representation and must replace/truncate the old prefix, not append (§§14.2, 15.3.7).

4. **206 integrity and continuation — accept.** Require a supported single-part 206, a valid byte `Content-Range`, exact next offset, and a body whose actual octet count equals the inclusive range span. A numeric complete length must exceed the last position; `*` is valid when length is unknown (§14.4). A 206 can satisfy only part of the requested suffix, so continue from the next verified byte; reject malformed, overlapping, gapped, or unsupported multipart data (§15.3.7.1–.2). `Content-Length` on 206 counts this response’s content, not the full representation; verify received bytes against `Content-Range` rather than using that header as the full-file length (§15.3.7).

5. **416 and completion — accept as a conservative safe policy (obligation 3).** For byte ranges, `Content-Range: bytes */length` reports the current selected representation length, not proof that the saved bytes are its prefix (RFC 9110 §§14.4, 15.5.17). Restarting rather than declaring completion from equal lengths alone is safe, though potentially redundant. Keep this as policy, not an RFC mandate; any optimization would need a previously verified contiguous prefix and established matching representation identity.

6. **Encoding, provisional state, and advice — accept with scope caveats (obligations 4 and 6).** Byte offsets apply to encoded representation bytes when Content-Encoding is present, so storing decoded bytes while resuming with encoded offsets is unsafe; bind Accept-Encoding/content coding or disable transparent decompression (§§8.4, 14.1.2). Keep partial data provisional and preserve the proposed byte-for-byte, replacement, status, malformed-range, validator, and decompression checks. Label them proposed/not run. RFC 9111 §§3.3–3.4 describe cache storage/combination rules; cite them as supporting analogy, not as direct application requirements for every desktop client. The optional post-download digest is sensible integrity advice beyond these RFC rules; an ETag is a validator, not a cryptographic digest. Test actual client-library decompression and server behavior because RFC semantics do not guarantee a particular library’s handling.
