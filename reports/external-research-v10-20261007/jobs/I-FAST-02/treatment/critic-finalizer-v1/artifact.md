## Proposed replacement plan

### P1 — Inputs and provenance

1. Import volunteer CSV readings for exactly two private local location IDs and one approved public CO-OPS station dataset for the selected month. Keep original CSV and downloaded response bytes unchanged; record paths, byte hashes generated by the host/application, retrieval time, source URL, request parameters, and parser version.
2. For CO-OPS requests preserve station ID, product, begin/end dates, datum, units, time zone, interval, output format, API response/errors, and metadata snapshot. Distinguish predictions, observed water_level, verified hourly_height, and modeled ofs_water_level; only predictions are the primary comparison reference. NOAA says water_level may be preliminary or verified, datum is mandatory for water-level products, and interval/retention limits differ by product [S01].
3. Prefer a UTC request/time basis and canonical internal height unit after explicit validation, while retaining source timestamp text, source time zone, source unit, and source height unchanged. Do not infer missing CSV time zones, units, datum, sign conventions, instrument zero, or sensor-method identity.
4. Import a station metadata snapshot (station details, tide-prediction classification/reference/offsets where applicable, datums and superseded datums, sensors/notices, retrieval date). NOAA's metadata service exposes these as separate resources, including station installation/removal details and sensors/outage messages [S02]. Snapshot the metadata used for this run; do not rewrite old runs when NOAA updates it.
5. Represent each volunteer location's measurement setup as an epoch. A move, gauge-zero/reference change, sensor replacement, recording-method change, unit change, or material timing change starts a new epoch unless reviewers document a justified conversion. Retain source-row IDs so each plotted point and comparison traces to input rows.
6. Keep volunteer labels anonymous in the notebook and exports by default. Do not require publication of coordinates or exact location details. If a private local map is needed, it is opt-in and excluded from ordinary exports.

### P2 — Comparability and interpretation

1. Retain the plan rule: store raw and interpreted values separately, let reviewers choose only supported interpretations, and allow comparison to remain unresolved [frozen plan §P2]. Each interpretation records author, time, evidence, conversion formula/parameters, and competing interpretations.
2. Normalize timestamps only when the source convention is known. Preserve raw time text and declared zone/offset; convert unambiguous time to UTC for ordering. Ambiguous/nonexistent local times at daylight-saving transitions, rounded/date-only times, and unknown zones stay unresolved until a reviewer supplies a documented rule. NOAA accepts GMT, fixed local standard time (no DST), and local time adjusted for DST [S01]; these conventions are not interchangeable.
3. Convert units only when the input unit is stated or otherwise evidenced. A datum is a vertical reference, not a unit conversion. NOAA lists STND as a reference unique to each station, MLLW as U.S. coastal chart datum, and says subordinate-station predictions require MLLW [S01]. Equal datum labels do not prove a volunteer local reference is tied to NOAA's datum.
4. Permit an absolute residual only when both series are demonstrably expressed on a common vertical reference, with mapping evidence and validity interval recorded. If a local gauge has only an arbitrary or changed zero, retain separate raw/relative series and mark the absolute comparison unresolved; do not silently zero-center, calibrate, or apply a station offset.
5. Show public reference-station ID, name, type, geographic context, prediction interval, datum, units, time convention, and relevant update/metadata snapshot next to the series. A single public station does not establish local equivalence at both volunteer locations.

### P3 — Analysis and display

1. Show the selected month for locations A and B separately, with raw observations, interpreted series if resolved, NOAA predictions, visible input gaps, and volunteer setup-epoch boundaries. Keep NOAA observed levels, if imported, visually and semantically distinct from astronomical predictions.
2. Define residual sign before computation; recommended convention is volunteer interpreted level minus NOAA predicted level. For every matched point expose both timestamps, signed time offset, location/epoch, source row, prediction station, and residual. Label results as descriptive differences for this selected series, month, and rule—not prediction accuracy, calibration, navigation advice, or surge guidance.
3. Default to an equality join on normalized timestamps. Do not use an unconfigured `merge_asof` call for exact-only matching: pandas defaults to backward direction with no tolerance, which can select any earlier right-side row. Offer reviewer-selected backward, forward or nearest matching only as a separate alternative, with a finite positive tolerance chosen from volunteer time precision and prediction interval. Record direction/tolerance, expose both timestamps and signed offset, and leave unmatched rows missing. In pandas 3.0.6, nearest ties choose the backward row and there is no tie-rule parameter; explicitly adopt and test that behavior, resolve ties in a wrapper, or leave a tie unresolved. Do not use unconstrained nearest matches, silent forward/backward filling, or interpolation. If a reviewer needs interpolation, treat it as separate optional analysis with formula, bracketing-data requirement, provenance and tests; `merge_asof` itself only selects rows. A zero tolerance is accepted by pandas but is not the approximate-match product policy.
4. NOAA supports several prediction intervals for harmonic stations but only high/low predictions for subordinate stations [S01, S03]. Use time-series residuals only where the chosen station/product yields a suitable interval. For subordinate/high-low-only output, offer a clearly labeled event-level high/low comparison or mark a dense residual unavailable; do not synthesize a continuous series.
5. Retain simple descriptive summaries only for a declared comparison and show sample count, unmatched/gap count, time-offset range, and selected coverage alongside any residual summary. Median, mean/bias, MAE or RMS may be offered as descriptive statistics, never a universal accuracy score. NOAA says prediction error varies by station and weather/runoff; its published example uses station-specific, one-year prediction-minus-observation RMS, so it is not a threshold for this two-site one-month volunteer sample [S04, S05].
6. Candidate event annotations are optional, manually reviewed context only. A NOAA citizen-science water-level application described in 2018 used photos and GPS-tagged reports of elevated water/impacts for communication; it is an event-reporting analogue, not evidence that photo/GPS reports are standardized continuous gauge values or that the app remains available today [S06].

### P5 — Components and operating boundary

1. Recommend a local notebook/dataframe workflow using pandas for CSV handling and time-key alignment. Use an equality join for the default exact-timestamp rule. The pinned pandas 3.0.6 public `merge_asof` definition requires ascending time-key order, supports grouping, exact-match control, direction and tolerance; `_AsOfMerge` validates matching key types/tolerance and dispatches to compiled join logic that returns row indexers. Its defaults are backward direction, exact keys allowed and no tolerance, so it is not an exact-only default. Nearest matching selects the closer timestamp; the pinned Cython implementation chooses backward on an exact-distance tie, with no public tie override [S09–S11]. This joins rows; it does not estimate a water level between predictions.
2. Pin implementation pandas release and Python interpreter together before build. The source evidence is pinned to pandas 3.0.6, released September 17, 2026; upstream says pandas 3.0 supports Python 3.11 and higher [S15]. If local runtime is older or uses another pandas line, recheck contract, regression test, and implementation at that release. This is not a claim the application was built.
3. Put NOAA acquisition behind a small import step that saves response bytes and metadata, then let the notebook run locally/offline. NOAA API supports CSV/JSON/XML; Tide Predictions also exposes downloadable data and request URLs for independent inspection [S01, S03]. Apply limits to the correct product: the API states six-minute measured water-level data is limited to one month per request, while tide predictions permit up to one year for non-high/low intervals and 10 years for high/low [S01]. Do not impose the measured-data one-month cap on prediction intervals. At run time, check the chosen station/product/interval, exact date range, response limits and any needed nonoverlapping chunks against the current service documentation and preserve the response/errors [S01, S03].
4. Keep plotting library undecided until offline export and interaction needs are demonstrated. Static and interactive plots are alternatives; neither was selected or code-audited here. The notebook remains local and does not require uploading volunteer data or publishing location details [frozen plan §P5].
