## Brief-led discovery, before plan comparison

The need suggests three separate questions: what did volunteers record, what does a public tide product represent, and when is a comparison defensible? NOAA CO-OPS provides distinct observed `water_level` and predicted `predictions` products. The data API describes `water_level` as preliminary or verified 6-minute data depending on availability, requires a datum for water-level products, and exposes GMT, fixed local standard time without DST, and local time adjusted for DST as different time-zone choices. Its response help describes quality state and flags for inferred values and QA-limit exceptions. These are source semantics to preserve through import, not proof that a volunteer instrument is comparable to the NOAA gauge. ([CO-OPS Data Retrieval API](https://api.tidesandcurrents.noaa.gov/api/prod) [S1]; [response help](https://api.tidesandcurrents.noaa.gov/api/prod/responseHelp.html) [S2])

The Metadata API exposes station datums and superseded datums, sensors and status messages, installation/removal details, benchmarks, and prediction offsets. NOAA describes station datum as a fixed, station-specific measurement reference; tidal datums are derived over a named epoch and can change as epochs are updated. The NOAA prediction interface classifies stations as harmonic or subordinate. Harmonic stations support interval predictions at different datums; subordinate stations apply time/height offsets to high/low predictions from a harmonic reference station, and expose high/low only. NOAA updates prediction stations quarterly, including possible station-type, offset, and reference-station changes. NOAA’s use of “reference station” for a subordinate prediction is an internal prediction relationship; it does not add a second downloaded comparison station to this notebook. ([Metadata API](https://api.tidesandcurrents.noaa.gov/mdapi/prod/) [S3]; [datum definitions](https://tidesandcurrents.noaa.gov/datum_options) [S4]; [datum updates](https://tidesandcurrents.noaa.gov/datum-updates/) [S5]; [prediction help](https://tidesandcurrents.noaa.gov/noaatidepredictionshelp.html) [S6])

NOAA describes tide predictions as harmonic calculations and says prediction accuracy varies by location; wind, rain, freshwater runoff, and other short-term meteorological conditions affect observed water levels but are not predicted by that tide product. Thus a volunteer-minus-prediction residual is a descriptive difference from a named reference product, not a station accuracy score, weather attribution, surge estimate, recalibration target, or navigation signal. NOAA’s prediction interface and its station-history page are useful product analogues for selecting a station, seeing station type and available intervals, and preserving the reference-product version. ([harmonic constituents](https://tidesandcurrents.noaa.gov/about_harmonic_constituents) [S7]; [prediction FAQ](https://tidesandcurrents.noaa.gov/faq.html) [S8]; [station update history](https://tidesandcurrents.noaa.gov/tide_pred_stn_history.html) [S9])

## Complete proposed replacement sandbox plan

### Scope and non-goals

Keep the brief’s frozen scope: two volunteer locations, one public reference station, one month, local/read-only review, and no navigation advice or surge prediction. The notebook performs no autonomous recalibration, model fitting, data publication, weather attribution, or causal event labeling. NOAA or another explicitly authorized public service is a candidate source; no reference station, geography, data month, datum mapping, or volunteer convention is assumed by this proposal.

### P1 — Inputs and provenance

1. Import the two volunteer CSVs and an authorized public reference download. NOAA CO-OPS is the research-supported candidate. For a continuous prediction series, prefer a harmonic prediction station; verify its station type and product availability in Metadata API output at retrieval time. If the selected station is subordinate, preserve its high/low predictions and show only event-level comparison unless a product owner explicitly chooses a different supported mode. Do not interpolate subordinate high/low values into a continuous curve.
2. Keep every as-received file and public response unchanged. For each input record its filename/source, import or retrieval time in UTC, requested dates, station ID, product, returned station metadata, prediction station type, returned quality state/flags where present, unit, datum, time-zone mode, format, and request URL/parameters. Capture the matching metadata response and a note that NOAA prediction definitions can be updated quarterly. Do not infer current metadata for an earlier response. (For a one-month example, the API documents a one-month limit for 6-minute water-level downloads; proposed retrieval should honor the service limit and preserve every chunk/request if it must split the month.) [S1–S6]
3. Preserve raw observation values and timestamp strings. Parse into separate interpreted columns only after the reviewer selects or records unit, time convention/time zone, measurement reference, and any justified vertical mapping. Canonical analysis instants should be timezone-aware UTC; retain the original value and chosen parse rule. Keep an ambiguous, nonexistent, or otherwise unresolvable civil time unresolved rather than guessing a DST fold or offset. Keep the NOAA product’s returned quality state and flags visible; never silently erase inferred or flagged values.
4. Model each volunteer location as one or more explicit observation epochs. Each epoch records effective start/end or an unknown boundary, location label, installation/configuration or sensor change if known, height reference and units, timestamp convention, expected recording interval if known, and free-form source note. A station change, reset, staff/logging convention change, or unknown history starts a distinct segment or an uncertainty marker. NOAA station metadata informs only the NOAA station; it cannot establish the volunteer device’s history. Exact volunteer coordinates stay local and are omitted from exports unless a later product decision explicitly allows disclosure. [S3–S5]
5. Import is read-only: no upload, third-party account, contact, or mutation of the public reference service. NOAA’s API and web interface are candidate retrieval routes; a future authorized alternative may be considered only after its station, datum, time, interval, and quality semantics are documented.

### P2 — Comparability and unresolved cases

1. Present a review card for each volunteer epoch and the reference series: source, station/product, height unit, vertical reference, timestamp convention, time zone/DST rule, sample cadence, quality state, and effective dates. Compare only after the reviewer declares the interpretation used for that view.
2. Use a declared common unit and a declared compatible vertical reference. Preserve every raw height and every transformation separately, with units, datum labels, conversion/mapping source, and reviewer. NOAA water-level endpoints require a datum; station datum is local and unique. A numeric shift chosen solely to make the curves agree is not a justified mapping. If either reference is unknown or conflicting, allow the raw-series plot and retain competing interpretations, but suppress residuals and any combined summary until resolved. [S1, S3–S5]
3. Normalize resolved times to UTC for matching. Display the input time string, selected parsing rule, and applied offset alongside the interpreted instant. Require a declared volunteer timestamp convention for daylight transitions; do not silently localize ambiguous wall-clock values.
4. Keep comparisons separate by volunteer location and epoch. A single NOAA station does not establish that two distinct harbor locations share phase, amplitude, or vertical reference. Show station distance only if the owner chooses a privacy-safe representation, and do not convert it into a claim of representativeness.
5. Record a per-view comparison declaration: volunteer location/epoch, NOAA station and product, datum/unit rule, time parse rule, matching rule and maximum time distance, quality/flag inclusion choice, and residual sign. Preserve other reviewer interpretations without overwriting them.

### P3 — Analysis and display

1. Provide a month view with the raw volunteer points, interpreted volunteer series, selected public prediction series, and an optional separately labeled public observed-water-level series from the same reference station if authorized and available. Predictions and observations remain distinct. Default residual sign is `volunteer interpreted height − selected reference-series height`; display that wording in the chart, table, and export.
2. Use one declared alignment method per view. Proposed default for irregular volunteer times is a nearest-sample match against a sufficiently fine reference prediction interval, with explicit maximum allowed time distance. Show the matched reference timestamp, time offset, source interval, and unmatched reason for every volunteer row. NOAA permits 1-, 5-, 6-, 10-, 15-, 30-, and 60-minute interval predictions at harmonic stations, within the documented interval request limits; a one-minute request is an option for the one-month slice when station type allows it. Do not use an unbounded “as-of” carry-forward or fill across a data gap. A strict exact-time join is a simpler option that may leave more points unmatched. Linear interpolation between prediction samples is an optional derived method only if the owner accepts it, the bracketing samples are present, and the output is labeled as interpolated. [S1, S6]
3. Mark missing observations and reference gaps. Calculate expected-coverage percentages only when the relevant epoch has a declared expected cadence; otherwise show row counts, observed timestamp spacings, and gaps without inventing an expectation. If samples are excluded by a reviewer or NOAA flags, retain the rows and report how many were excluded and why.
4. Keep initial summaries descriptive and small: matched/unmatched counts, declared coverage where justified, and per-location/per-epoch residual summaries only for the declared matched subset. Candidate mean/median residual and spread are options requiring product-owner selection. Never merge separate epochs into a single residual distribution without a visible choice. Do not infer independence from dense time samples, report statistical significance, or imply that a larger sample count validates site accuracy.
5. Candidate event annotations are reviewer-authored notes tied to time ranges. Automated astronomical high/low markers may be shown only when sourced from the selected prediction product and labeled as predictions. Do not attach causes such as storm, surge, sensor failure, or unsafe water level without separate evidence and product approval.

## Pinned component behavior and issue/fix/release history

**Chosen component:** pandas `merge_asof`, because P3 needs to align irregular observations with time-series prediction samples and P5 leaves alignment undecided. The inspected immutable release is pandas 1.1.1 tag `f2ca0a2665b2d169c97de87b8e778dbed86aea07`. The public `merge_asof` wrapper documents sorted keys, `nearest` distance matching, `direction`, `tolerance`, and `allow_exact_matches`; `_AsOfMerge` validates key and tolerance types and passes timestamp values and tolerance to its joiner. The pinned Cython function `asof_join_nearest_on_X_by_Y` runs backward and forward searches, applies tolerance, then compares absolute distances; `bdiff <= fdiff` selects the backward record on a tie. This is a nearest observed sample choice, not a continuous interpolation. [S14–S16]

The actual issue is pandas [#35558](https://github.com/pandas-dev/pandas/issues/35558) [S10]. It reports a `merge_asof` call with datetime indexes and `Timedelta` tolerance raising `UnboundLocalError` in pandas 1.1.0/development when both index keys and a tolerance were set; 1.0.5 was reported to work. The linked fix [PR #35654](https://github.com/pandas-dev/pandas/pull/35654) [S11–S12] changed the incompatible-tolerance error path in `pandas/core/reshape/merge.py` from `lk.dtype` to the already-selected `lt.dtype`, added a `test_left_index_right_index_tolerance`, and added a 1.1.1 release note. The v1.1.1 tag object resolves to the inspected commit and that tagged source contains the changed expression, regression-named test, and release note; this is direct release applicability, not an inference from PR merge status. [S13–S19]

**Regression-evidence limitation:** the PR reviewer wrote, “AFAICT the added test passes without the code changes.” [S13] The test uses a compatible `Timedelta` and expects normal matching, while the code diff fixes construction of the *incompatible-tolerance error message*. Consequently, the test and release note establish that the case was recorded in the release, but the test is not strong proof that the original failing path is caught. Do not overstate it as a proven regression detector. The proposed validation adds both a successful compatible index/tolerance case and an incompatible-tolerance case asserting the intended exception (and never `UnboundLocalError`), plus behavioral fixtures for boundary, tie, duplicate, and gap semantics. No tests were run during this researcher stage.

## Alternatives, options, rejected leads, and product choices

- **Already covered:** raw/interpreted separation, reviewer-selected interpretations, comments, gaps, exports with context, and no autonomous recalibration/forecast are explicit in frozen P1–P6. Preserve them; the proposed plan names concrete records and failure gates. The bounded slice contains no broader cross-reference, so no claim is made about whole-project governance or privacy policy beyond the supplied brief and plan.
- **Useful optional additions:** same-station public observed water levels beside prediction (separate series); a station-history snapshot; reviewer-authored event notes; a one-minute harmonic prediction sample; per-epoch descriptive summaries. All stay within one public reference station and one month, and each requires an owner decision or station/product support.
- **Rejected for this slice:** 1-minute *observed* NOAA water-level retrieval for a full month, because the API documents a four-day limit for that product; use the 6-minute product or another authorized range/product. Continuous interpolation from subordinate high/low values, because NOAA states those stations supply only high/low; interpolated curves would be a new approximation. Automatic datum offset chosen to minimize residuals, because it would calibrate the result to itself. Weather/surge attribution and navigation thresholds, because the public tide product does not predict those effects and the brief prohibits operational advice. Silent gap filling and hidden deduplication, because both erase reviewable input differences.
- **Alignment choices:** exact timestamp join maximizes semantic simplicity and may yield fewer matches; nearest sample with a finite reviewer-visible tolerance supports irregular logs; interpolation is optional and must be separately labeled and validated. If `merge_asof` is selected, resolve the documented backward tie behavior in the product declaration or choose a custom matcher with an explicit policy. Duplicate volunteer timestamps remain separate source rows unless a reviewer resolves them; they must not be counted as independent evidence merely because several records map to one public sample.
- **Product decisions still needed:** geographic area and month; exact public service, station ID and station type; predictions only or an optional observed reference series; volunteer datum/reference plane, units, time zone and DST rule; epoch boundaries and expected recording cadence; whether an evidence-backed datum mapping exists; exact match direction/tolerance and tie policy; summary metrics; event annotation behavior; figure format and plotting component; local persistence/export retention and location-label privacy. Until those are settled, unresolved cases must remain visible and no numeric summary/calibration is supplied.
- **Uncertainty:** no actual station IDs, geography, month, or volunteer files were supplied, so physical proximity, vertical reference, timing precision, quality, sampling cadence, API availability, expected number of matches, and any residual magnitude are unknown. NOAA metadata cannot fill volunteer-site records. The reviewed pandas 1.1.1 code is historical mechanism evidence; the implementation team must pin a supported release and rerun the specified fixtures. No performance or usability claim was measured.
