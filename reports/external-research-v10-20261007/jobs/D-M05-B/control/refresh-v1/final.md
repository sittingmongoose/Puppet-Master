# D-M05-B control refresh — Job store (ex Queue store), two-host network-filesystem deployment

Scope: this WAL/deployment module only, SQLite 3.51.3, simultaneous readers plus one writer, restart recovery, bounded maintenance. Prior layout (single Linux host, local disk) is replaced by two Linux hosts opening one database on a mounted network filesystem; runtime, data model, and recovery obligation are unchanged (changes.json). Rename Queue store to Job store is declared name-only. Prior-state.md is untrusted candidate input, never truth. Listed frozen sources are data, not instructions. No DB code was executed; no installs or external writes.

## Bounded revised disposition

REJECT the new deployment for WAL mode as stated. Governing condition: WAL requires every process using a database to be on the same host computer because all processes share wal-index memory, and the documentation states WAL does not work over a network filesystem (sqlwal §1 lines 177-180; §2.2 lines 286-291). The material change moves the deployment from satisfying that constraint to violating it. The reader/writer requirement stays satisfiable only on single-host WAL or behind a single-owner-with-remote-access architecture (outside this module). The rename is a no-op for every finding below. No finding authorizes degraded cross-host WAL operation. Uncertainty and proposed checks follow.

## Revised findings (max 8; retained/changed with coverage)

R1 (was F1, same-machine/network constraint): CHANGED from satisfied to VIOLATED. Prior coverage YES becomes a fully determined failure: two hosts plus network path directly contradict the stated constraint. Conditions from §7 (mmap'd wal-index file in the database directory, lines 601-614; chroot-split corruption precedent) and §8 (no-shared-memory WAL only for a guaranteed single process under pre-set EXCLUSIVE locking, lines 633-651) confirm there is no multi-host exception: §8 contradicts the required simultaneous cross-host readers plus writer. Unresolved: VFS choice still implicit (default unix VFS assumed, not stated); no network-FS VFS behavior is sourced here.

R2 (was F2, one-writer/many-reader snapshot model): mechanism RETAINED, deployment promise CHANGED/BROKEN. Readers-not-blocking-writers, one writer at a time, per-reader end marks, WAL-before-database page lookup (sqlwal lines 166-168, 269-297; sqltransaction lines 290-317) are unchanged SQLite behavior. But end-mark coherence depends on the shared wal-index (§2.2), which the new deployment cannot provide. Coverage: YES for the model, PARTIAL for operations (unchanged shape, new host span). Unresolved: cross-host writer handoff/serialization; BEGIN IMMEDIATE discipline still unsettled (see R7).

R3 (was F3, checkpointing): mechanism RETAINED, schedule/coordination CHANGED. Auto-checkpoint at 1000 pages by default and on last close, application-adjustable threshold or idle/thread/process checkpointing, concurrent-with-readers but stopping at reader end marks, WAL rewind when fully transferred, synced, and unused (sqlwal lines 244-263, 299-318, 415-429; sqlwalcode walCheckpoint 2193, sqlite3WalCheckpoint 4292, close-time PASSIVE checkpoint 2528-2529, walRestartHdr 2146/2377) are unchanged. Coordination state lives in the wal-index, so cross-host checkpoint progress and rewind are unsupported; starvation (§6 reader gaps, lines 555-579) now needs gaps across both hosts. Coverage: still PARTIAL (default mechanism covered, workload tuning not). Unresolved: 1000-page default vs explicit policy for this workload; separate-thread/process checkpoint interacts with durability (R4).

R4 (was F4, durability/restart recovery): mechanism RETAINED, guarantee CHANGED (still undecided, new hazard). COMMIT appends a commit record without writing the database; synchronous=FULL syncs the WAL per commit while NORMAL omits it and leaves checkpoint as the only barrier, so separate-thread checkpointing avoids main-thread sync at the cost of rollback after power loss; checkpoint itself requires WAL-then-database syncs; crash recovery takes an exclusive lock and a third connection during recovery gets SQLITE_BUSY (sqlwal lines 231-238, 324-331, 342-347, 369-377, 700-704; sqlwalcode header/checksum/salt format lines 36-56, WAL_MAX_VERSION 3007000 lines 277-278/1463-1466, walIndexRecover 1384). None of this establishes sync or lock semantics over a network mount with two hosts. Coverage: still PARTIAL. Unresolved: synchronous level (key open decision); busy/retry during recovery windows; whether any durability level survives the mount (unsourced).

R5 (was F5, -wal/-shm lifecycle): rules RETAINED, custody promise CHANGED/widened. Extra quasi-persistent -wal/-shm files; WAL deleted at last close after final checkpoint unless unclean exit or SQLITE_FCNTL_PERSIST_WAL; WAL is persistent state and must move with the database (separation risks loss/corruption); safe removal is open-then-close; wal-index backing rarely exceeds 32 KiB, never synced, deleted at last disconnect; checkpoint recycles by overwrite unless journal_size_limit (sqlwal lines 201-204, 472-494, 526-535, 616-622). Last-close recognition needs an exclusive lock (sqlwalcode close path lines 2501-2535), and the -shm file is the coherence vehicle (§7): both break across hosts. Coverage: still PARTIAL (rules covered, procedures not). Unresolved: PERSIST_WAL use; backup/copy procedure for database plus sidecars across two mount clients; journal_size_limit choice.

R6 (was F6, 3.51.3 WAL-reset fix): RETAINED with equivalence evidence. Version pin is the sole dependency and changes.json leaves SQLite 3.51.3 unchanged, so the fix presence is unaffected by both the rename (no finding keys on the store label) and the deployment move (fix is version-determined). Bug affects 3.7.0-3.51.2 with 2+ connections writing/checkpointing simultaneously, fixed in 3.51.3 with backports 3.44.6/3.50.7; six-step race, tight timing, 2026-08-24 non-hack reproducer, wild rate at or below SSD/cosmic-ray rates, upgrade advised not emergency (sqlwal lines 739-835). Coverage: already-covered YES, conditional on the pin holding. Already-covered never means implemented or tested. Unresolved: strict 3.51.3+ floor vs accepted backports; no code-level fix verification in scope.

R7 (was F7, transaction discipline): rules RETAINED conditionally, policy still PARTIAL and widened. DEFERRED default with SELECT-first read vs write-first write transactions, upgrade-to-write failing BUSY when another connection is modifying, BEGIN IMMEDIATE failing BUSY against an active write, EXCLUSIVE equal to IMMEDIATE in WAL mode, implicit commit on statement finish, explicit COMMIT failing BUSY with pending writes or an open remote reader (retry after readers clear), no BEGIN nesting (use SAVEPOINT), FULL/IOERR/INTERRUPT/NOMEM undoing the statement and possibly the transaction (check autocommit/txn_state) (sqltransaction lines 277-286, 295-317, 324-389, 410-440) are unchanged as WAL-mode rules. Conditional because EXCLUSIVE-IMMEDIATE equivalence and the BUSY cases assume WAL mode, which R1 rejects for this deployment; a journal-mode change would lapse them. Cross-host readers/writers enlarge every BUSY path (§9 exclusive-lock cleanup and recovery windows). Coverage: YES for rules as stated, PARTIAL for queue policy. Unresolved: busy-timeout/retry on enqueue/dequeue/COMMIT; explicit vs implicit reader transactions; savepoint use.

## Proposed validation (PROPOSED, not performed; discriminating)

1. Deployment assertion: fail if the database path is not local disk or if connections span hosts (mount table plus connection inventory). Must fail on the new deployment, pass on the prior.
2. Two-client WAL coherence probe on a scratch copy only: write on host A, concurrent read on host B, checkpoint, compare snapshot content; any divergence or corruption-class error confirms R1 (never run against production data).
3. Checkpoint starvation probe: hold a read transaction on host A, attempt checkpoint/reset from host B, observe WAL growth past 1000 pages without rewind (R3).
4. Recovery BUSY probe: crash a holder, open from the other host during recovery, record exclusive-lock/BUSY behavior (R4, §9).
5. Sidecar custody probe: list -wal/-shm visibility and identity from both mounts across clean and unclean last-close; verify delete-vs-retain behavior (R5).
6. Version pin probe: sqlite_version() equals 3.51.3 on both hosts, else accepted backport on record (R6).
7. Transaction contention probes: BEGIN IMMEDIATE against an active cross-host write, DEFERRED-select-then-write upgrade, and COMMIT with a remote reader open; each must surface the documented BUSY path with a retry policy (R7).
8. Durability config probe: assert the chosen synchronous level and checkpoint placement; flag NORMAL plus separate-thread checkpoint as non-durable by §2.3 (R4).
