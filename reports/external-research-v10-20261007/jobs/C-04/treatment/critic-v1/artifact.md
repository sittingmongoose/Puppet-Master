# Small ensemble score desk: final research and planning proposal

**Assignment:** C-04/treatment/critic-v1. This is a proposal for the hypothetical ensemble in the brief, not an existing product or validated music workflow. The exact input map, frozen inputs and captured-source identities are recorded in [source-map.json](./source-map.json). Each bracketed source ID below resolves there; captures are in [sources/](./sources/).

## Recommendation

Start with a page-first rehearsal library that preserves each authorized original and every replacement as an immutable, provenance-linked revision. Musicians should always be able to open the received page. Accept a supplied MusicXML or MEI file as a separate representation; offer scan-to-notation only as an optional, human-reviewed aid. Keep personal marks separate from director-published ensemble notes.

For the first collaboration path, publish versioned portable rehearsal packets that members download before rehearsal and return through an explicit import/review step. This gives the group offline use without a permanent commercial account or continuously available host. The packet is a copy: later withdrawal can stop new publication, but cannot recall copies already downloaded.

Use two kinds of anchors where available, each with a clear scope:

- A page-region mark targets one exact page rendition and its revision. Its coordinates use the rendition's declared source coordinate frame.
- A symbolic passage reference targets an exact notation-file revision and its part. Any MusicXML event ID or measure label is context for that document; a librarian-created rehearsal-passage ID may link manually confirmed references across parts.

A part, edition or page replacement creates a new revision. Old marks remain visible on the revision they describe. New mappings stay **needs review** until a person reconnects them. Never infer score equivalence or move a note silently.

## Open discovery and useful alternatives

Discovery began from the ensemble's broad user problem, before opening PLAN.md: a volunteer needs to intake authorized paper and digital parts, navigate them in rehearsal, share director notes, retain personal pencil marks, work offline, and hand off a portable packet. Open searches led to page/image annotation standards, score OMR, notation interchange and rendering, and scholarly score-to-facsimile models. Those mechanisms were selected for relevance; no component or defect list was assumed in advance.

| Mechanism | What it helps with | Main cost or boundary | Proposed use |
|---|---|---|---|
| **Page-first facsimile/PDF** | Keeps the view tied to the page musicians actually received; works for scans, photos, and notation files rendered or exported to pages | A region is tied to a particular page asset; replacement, crop, rotation, or re-render requires an explicit remap | **Core.** Preserve the source and annotate a frozen page rendition. |
| **Structured notation first** | Can navigate symbols, parts and passages after a MusicXML/MEI file is available; notation may reflow without changing its musical content | Supplied files differ; OMR can misread; IDs and printed measure labels do not establish identity across files; renderer layout differs from the supplied page | **Optional companion.** Accept supplied notation and keep reviewed OMR output as a separate representation. |
| **Automatic OMR versus supplied/manual structure** | A local OMR program can create a starting transcription; supplied editable files need no image recognition | Correctness varies with score type and version; correction time and package/license maintenance are real; cloud conversion adds account, privacy and connectivity costs | Keep page-only use complete. Try local OMR only for eligible printed scores and require review against the source. |
| **Portable snapshots versus live collaborative sync** | Snapshots support predownload, room-without-network use, and explicit publication | Members must return changes; the librarian resolves conflicting edits; there is no automatic real-time view of everyone’s work | **V1.** Publish an immutable base revision and import member changes explicitly. Consider live sync only if the group demonstrates need and chooses hosting, identity, access, backup and conflict rules. |

Web Annotation provides a useful outside-score analogy: an annotation has a body and target, selectors can describe a segment in more than one way, and an SVG selector is sized relative to its source resource. The model does not prescribe transport or sync [WA01]. IIIF Presentation 3.0’s Manifest/Canvas/AnnotationPage structure is a possible archive/interchange model, not a local permission or offline-sync solution [IIIF01]. MEI’s facsimile / surface / zone pattern is a music-specific later lead for linking a score encoding with page regions; its declared coordinate frame still needs to be respected [MEI01].

## Pinned component evidence and applicability

### Audiveris: optional local OMR

The reviewed code is **Audiveris 5.11.0**, tag 5.11.0, commit 9e1e55cd2746037d059345881c53e6a6754bffbd [A01–A06, A10]. The project describes an OMR engine plus interactive correction editor; its handbook limits the engine to common Western printed notation and common symbols, excludes handwritten scores, and says verification/correction remains necessary [A01–A02]. The export guide distinguishes a resumable .omr project from .mxl: MusicXML output is lossy, so retaining both the original and editable OMR project is useful when the group chooses this path [A03].

Implementation inspection adds a further reliability condition. In Book.export, transcription failure returns false; after per-score export exceptions are caught and logged, the method returns true after the loop [A04, lines 588–637]. A success return therefore does not prove every output file is complete or reopenable. Import/review should verify that expected output exists, parses, and can be reopened; the original must remain usable if any stage fails.

Issue #971 reports one batch export failure on Audiveris 5.11.0 build 9e1e55...: all selected sheets reached PAGE, but export failed while reloading a RunTable, followed by a failing recovery attempt [A07]. The captured issue page showed Open. In the pinned code, afterUnmarshal delegates to afterMarshal, whose loop reads sequences.length without a null check [A05, lines 329–360]. This makes the reported stack plausible for this code; it does not establish frequency, the reporter’s proposed root cause, or behavior on every score. I did not reproduce the report or retrieve its linked score.

A separate version history example is bounded the same way. Issue #920 reports a bass-clef pitch difference between 5.10.1 and 5.9.0 [A09]; the 5.10.2 release notes state a rounding-error fix for #920 [A08]. The captured issue page showed Open. I found no independently run regression test for that case; treat the release note as the project’s stated fix, not a quality guarantee for later versions.

**Disposition:** research Audiveris locally only if input coverage, volunteer correction effort, target platforms and its AGPL-3.0 distribution implications fit [A02, A10]. Preserve the source, .omr project and generated MusicXML separately. Keep results marked unreviewed until a person compares them against the correct page revision. Do not treat a processing milestone, a positive return value, or the presence of MusicXML as verified content.

### MusicXML identity, timing and coordinates

MusicXML 4.0’s score-part ID links a document’s part-list entry to its part data; it is a file-local part identifier, not the ensemble’s lasting part identity [MX02]. A measure’s required number is a token that may be non-numeric; text can affect display, and an optional ID is unique to that document. The specification expects measure numbers to correspond across parts when their left barlines coincide, but non-controlling measures explicitly permit a different left barline. Those rules do not establish identity after re-export, re-pagination, replacement, or across unlike part files [MX01]. A note’s optional ID is also document-unique when present, not a cross-file identifier [MX03]. Treat measure numbers as human context and file IDs as revision-scoped locators; cross-part links need a person-confirmed mapping.

The timing unit matters. divisions gives the count per quarter note; duration is a positive number expressed in those division units, selected to represent tuplets and rhythmic values [MX04–MX05]. Do not store a raw duration integer as seconds or a universal tick count. If a notation anchor needs an offset, store a normalized musical position with the exact notation revision and enough divisions context to resolve it. MusicXML “tenths” are tenths of interline staff space and are scaled through score scaling; they are not CSS pixels or PDF points [MX06]. Likewise, do not reuse a renderer’s current screen coordinates as source-page coordinates.

### Rendering alternatives

**OpenSheetMusicDisplay (OSMD) 2.2.0**, released 2026-10-02 and pinned to peeled commit b416d38707b87d6ed0a56c5bd8309124ad99172d, is a TypeScript MusicXML renderer for browser and Node environments. Its API accepts XML content and separates load() from render() [O01–O02, O06]. Its README says it is a renderer rather than a full score editor and documents unsupported or partially supported MusicXML features [O01]. It is BSD-3-Clause at this pin [O04–O05].

The 2.2.0 change history and a specific patch show how hit-testing depends on layout geometry. Several fixes adjust nearest-note selection for TAB rests, neighboring voices, note-head centers and grace notes [O03]. Commit b24777e changes the hit-test and adds a test in GetNearestVoiceEntry_Test.ts for a clicked TAB rest that should not be selected [O07]. This is useful implementation history for a future click-to-navigate interaction. It also shows why a transient click location or renderer graphical object is not an annotation identity. The test file was inspected, not run here.

**Verovio 6.3.0**, pinned to peeled commit 425dd7b6ba26edcecbe345c10b15586d095743d9 [V05], is a portable C++20 library with JavaScript, Python, Java, Swift and Go bindings. Its README describes MEI engraving to SVG and converters including MusicXML [V01]. The header declares RenderToSVG(pageNo) with 1-based page numbering, GetPageWithElement(xmlId) based on current layout, and MEI access; it labels its editor methods experimental [V02]. The README and COPYING.LESSER specify LGPL v3 [V01, V04]. **This corrects the predecessor’s GPLv3 claim for Verovio.** The source tree’s top-level COPYING alone is not an adequate license summary [V03]; use the project’s README and LGPL file, and have the chosen distribution reviewed before bundling.

OSMD favors a TypeScript/browser route with direct MusicXML loading; Verovio offers a C++/multi-binding engraving route with strong MEI support and MusicXML conversion. Both can be evaluated for the actual authorized files. Neither is selected here: the viewer host and accessibility needs are not supplied, feature coverage differs, and either renderer’s reflowed page is a representation rather than the uploaded page. OSMD’s BSD-3-Clause, Verovio’s LGPLv3, and Audiveris’s AGPLv3 are maintenance/distribution inputs; this proposal makes no legal conclusion.

## Complete minimum workflow

1. **Create identities and provenance at intake.** Create separate local IDs for work, edition, part, source asset and source revision. Keep the exact authorized upload read-only and record a SHA-256, supplied title/instrument labels, uploader, intake time, permission/provenance statement, librarian corrections and publication status. Byte-identical re-imports may be detected by hash; equal hashes establish equal bytes only. Similar titles, arrangements, transpositions, publishers or instrument names do not establish equivalent editions or parts. Replacements become new revisions instead of overwriting prior ones.
2. **Keep page use independent of interpretation.** Accept authorized page images, PDFs and supplied notation. Show a page preview before optional conversion. Record every derivative’s source revision, tool/version/options, output hash, page mapping, errors and status: not attempted, processing, failed, unreviewed, reviewed against source, or rejected. Status applies to a named output revision; a new input or output invalidates its old review. For Audiveris, preserve .omr alongside MusicXML. Failed conversion leaves the previous page-only item available.
3. **Keep annotations scoped and understandable.** A page note stores (edition_id, part_id, part_revision_id, page_rendition_revision_id) plus a region selector in that rendition’s declared coordinate frame. Record its dimensions, orientation/crop transform and content hash. Export a simple SVG region selector relative to the source rendition, following the Web Annotation pattern where useful [WA01]. Use renderer coordinates only to place the current overlay. Give each note author, created/edited revision, visibility, body, and base publication revision. Maintain personal and shared note stores separately.
4. **Link parts by explicit rehearsal passages.** A shared rehearsal passage gets a group-local ID and a readable label. The director or librarian maps it to one selector per part, with the part’s own page and, if dependable, an optional notation locator. Keep the printed measure label for musicians; never assume equal measures, page numbers, transposition, or notation IDs across two parts. If no valid mapping exists, label that part unresolved and keep the note accessible from the list for a human to fix.
5. **Publish and rehearse offline.** The librarian maintains the latest published library revision; the director selects works/passages and explicitly publishes shared notes and ordered rehearsal items. Members download the relevant authorized parts before rehearsal. A versioned ZIP packet should include a manifest with work/edition/part/revision IDs, source and derivative hashes, page order, interpretation/review state, included shared note IDs/targets, rehearsal order, export time and format version. Include the page/PDF view and structured files only when authorized and selected. Generate a printable packet with visible edition/part identity and shared notes; include a machine-readable sidecar. Exclude private marks unless the owner deliberately exports them.
6. **Import, resolve, recover and delete deliberately.** Offline member edits carry the packet’s basePublishedRevisionId, author, scope and annotation IDs. Independent new annotations can be added. Edits to the same shared annotation remain two visible candidates with their base revisions until the director resolves them; never silently take last-write-wins or combine two geometries. Keep the last good library/packet while imports, rendering and export are staged; validate manifests and file hashes before publication; report failed or incomplete conversion and allow retry from the original.

Access and retention must be explicit even in a modest tool. Librarians own canonical identity/provenance corrections and source replacement; the director controls ensemble-note publication and rehearsal packets; members read the selected packet and keep private marks. Roles may be combined by agreement, but private-to-shared is a visible publish action. If there is no authenticated host, packet distribution remains a human-controlled operation; the application must not imply server-side enforcement that does not exist. A permission statement records what the librarian supplied, not proof of ownership or a license determination.

Before implementation, members must decide what deletion covers: active original, derived pages and notation, personal annotations, shared annotations, queued offline edits, backups and already downloaded packets. A deletion flow should remove controlled active copies and prevent stale imports from re-adding deleted items with a minimal tombstone; set a finite backup retention period and say what the tombstone retains. A packet or offline cache already handed out cannot be remotely recalled. If later multi-device hosting is desired, authentication, authorization enforcement, transport/storage protection, recovery and backup expiry are blocking design decisions, not implied by the annotation format.

## Observable validation proposal

All checks below are **proposed**, require a small sample the ensemble has permission to process, and have not been executed here.

- **Intake and identity:** Import one authorized scan, one phone photo, one PDF and one supplied notation file. Reopen each. Confirm edition/part/source revision and permission statement remain visible; the original bytes/hash do not change; byte-identical import is detectable; changed bytes create a new revision. Confirm a title match never silently merges edition or part identity.
- **Interpretation and review:** For at least one clean printed page and one difficult/phone image, record per-page OMR outcome, reviewer and output hash. Compare every accepted passage with its source page. A failed, skipped or uninspected page must never say reviewed against source. Reopen the .omr project and compare the MusicXML export; record observed losses without extrapolating an accuracy rate from this small set.
- **Coordinate and replacement behavior:** Draw a region at two zoom levels and after supported rotation/resize. It must remain over the same point in the exact stored rendition. Replace or crop a page and confirm the old target stays readable on the old revision while the replacement displays needs review; no automatic relocation occurs.
- **Different parts:** Use two authorized parts with different pagination and at least one nonmatching or absent measure label. Have a director link one rehearsal passage to each. Confirm the packet shows each musician the correct edition/part/page, the labels remain as context, and a missing link stays unresolved.
- **Offline privacy and conflict:** Download a published packet, disconnect the network, open the selected pages and add a private mark. Reopen offline; verify the private mark is usable and absent from a director’s packet. Make disjoint new notes and two edits to the same shared note in separate copies. Import them; new IDs survive, the conflicting note preserves both candidates, and a person chooses the resolution.
- **Handoff and recovery:** Reopen a packet on a clean device without network. Check all hashes, required files, page order, notation/review status, edition/part labels and note privacy. Interrupt import/export and retry; the original and last good packet remain openable and the failed artifact is visibly incomplete.
- **Access, withdrawal and deletion:** Exercise each role and each publication boundary. Remove a source, derivative, personal mark and shared note in turn; verify active controlled copies, queued edits, stale-import tombstones and backups follow the written retention policy. Record that an already distributed packet remains outside the application’s recall control.
- **Cross-version locator check:** Use a notation file with IDs and one without them. Confirm any ID is interpreted only within that file hash; change/re-export the file and confirm an old ID or measure label does not bind automatically. Resolve timing using that file’s divisions context, not a screen coordinate or seconds.

## Decisions, optional leads and uncertainty

**Decide for the minimum:** page-first core; immutable source/part revisions; supplied provenance; optional reviewed structured interpretation; separate private/shared annotations; per-part human-linked rehearsal passages; librarian-published snapshots; offline packet; explicit delete/retention policy; no automatic migration when a page or part changes.

**Keep optional:** MEI facsimile alignment for groups with archive-style source/notation links; assisted cross-part passage suggestions with human confirmation; live sync or a CRDT only after member coordination need is shown; a local OMR tool only after authorized sample coverage and license/platform review. Consider import/export standards as bridges rather than required internal schemas.

**Still unresolved:** the actual devices and UI host, representative editions and notation variants, the group’s permission records, whether volunteer correction cost is acceptable, which renderer and license obligations fit distribution, whether anyone operates a shared server, authentication needs, backup duration, and what to do when an offline packet returns after its part has been withdrawn. No supplied score corpus or rights documentation answers these questions. Public issue reports describe particular cases; they are not incidence data.
