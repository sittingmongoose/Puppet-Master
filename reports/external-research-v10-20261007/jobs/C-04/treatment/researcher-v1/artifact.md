# Small ensemble score desk: research proposal

**Assignment:** C-04/treatment/researcher-v1. This is a planning proposal for the hypothetical brief, not a description of an existing ensemble or a validated music-processing system. Frozen input hashes and public-source identities/captures are recorded in [source-map.json](./source-map.json). Bracketed IDs below resolve to its source records.

## Recommendation

Build the first useful workflow around **authorized source files and immutable score revisions**. Keep a PDF or page image as the reference musicians can compare with the paper part. Add a structured MusicXML/MEI view when the member supplied one, and make scan-to-notation conversion an optional, separately reviewed aid. Attach every mark to a specific part revision and page rendition; add a semantic notation anchor only when the source actually contains a usable one. Never silently move a mark when a page, part, edition, or notation file changes.

Use an offline rehearsal packet with an explicit publish/import step as the first collaboration mechanism. This preserves access in a room without connectivity and avoids making a permanent commercial account a condition of use. Treat live sync as a later option, gated on the group selecting a host, account, conflict, and retention model. This is an inference from the small-group scope and connectivity requirements, not a guarantee supplied by a component.

## Open discovery and alternatives

The brief's broad problem led to four useful mechanism families before I read the frozen plan: page-image/PDF annotation; optical music recognition (OMR) to symbolic notation; notation interchange/rendering; and archival facsimile links between symbols and page regions. W3C Web Annotation offers an outside-the-score analogy for platform-neutral body/target/selectors [S16]; the MEI facsimile model links musical content to source surfaces/zones [S17–S18]. They suggest a dual-anchor model, but neither standard supplies this product's permission, sync, or review workflow.

| Mechanism | Value | Cost or failure mode | Proposal |
|---|---|---|---|
| Page-first: retain the exact PDF/image and place regions on that revision | Works for scans, photos, printed parts, and handwriting; lets a musician check against the received page | A replacement or re-render changes the target; a page coordinate cannot by itself identify a passage across differently paginated parts | **Core.** Make a page region revision-bound; label it visibly with edition/part and page. |
| Structured-first: represent a passage as part + measure/event + musical-time offset and render notation | Can navigate notation that reflows; can support links to corresponding points when a person supplies the mapping | OMR may misread; measure labels can vary or be absent; IDs generally do not promise identity across separately edited files; a renderer's page layout differs from the source | **Optional.** Use only with a named notation-file revision and a verified anchor; keep the source page available. |
| Automatic OMR versus manual/digital intake | Local OMR can reduce transcription work; manual page notes and supplied MusicXML need no recognition claims | OMR and export errors are observable risks; manual structure costs volunteer time; cloud conversion can impose account, privacy, and connectivity dependencies | Make local OMR opt-in. Accept supplied MusicXML/MEI directly. Keep page-only operation complete. Do not make a cloud service a prerequisite. |
| One central live collaborative library versus versioned portable packets | Central sync is convenient and can serialize publication | Requires a continuously available host/service, identity and authorization, conflict rules, backups, and connectivity; real-time merge is extra complexity | Start with a librarian-owned published snapshot plus local member packet. Import submissions explicitly and retain conflicting revisions. Revisit a central host only when the group requests it. |

Two rendering candidates illustrate a real trade-off. OpenSheetMusicDisplay (OSMD) 2.2.0 is a TypeScript MusicXML renderer (`load`/`render`) built for browser/Node environments [S09–S12]. Its 2026-10-02 release identifies commit `b416d38707b87d6ed0a56c5bd8309124ad99172d` and includes substantial hit-testing/rendering fixes [S10]; a current hit result is still not a durable annotation identity. Verovio 6.3.0 is a C++ toolkit that can render SVG pages and query an element's page/attributes by `xml:id`; its page number is 1-based and the page lookup follows current layout [S13–S15]. Its public header marks editing methods experimental, so the proposal uses it only as a possible renderer/query engine, not as the annotation editor. OSMD's BSD-3-Clause versus Verovio's GPLv3 and Audiveris's AGPLv3 also mean that “free” is not a complete distribution/licensing decision [S04, S12, S15]. Verify the selected target platforms, supported content, and redistribution model before choosing or bundling one. Neither renderer reproduces a submitted scan as the authoritative page.

## Evidence, semantics, and applicability

### OMR implementation and release history

Audiveris is a useful local candidate because its own project describes an OMR engine paired with an interactive correction editor, an XML-based `.omr` project, and export to a subset of MusicXML 4.0. Its documentation says perfect recognition is out of reach in many cases [S01]. The reviewed release is **5.11.0**, pinned to `9e1e55cd2746037d059345881c53e6a6754bffbd` [S02–S05]. In that code, `Book.export` first calls transcription and then writes movement/opus MusicXML [S03, `Book.java:572–635`]. `RunTable.afterUnmarshal` calls `afterMarshal`; the latter dereferences `sequences.length` [S02, `RunTable.java:329–360`].

At the same exact 5.11.0 commit, open issue #971 reports a case where every sheet reached PAGE but the persisted structure reload/export failed, with an additional failing recovery path [S06]. The code path makes the reported `null` dereference plausible. **This was not reproduced here**; the issue is a reporter's case, not proof that every score or every installation fails. Its status was Open when captured. Treat it as a concrete applicability risk and require an end-to-end score-set check before relying on conversion.

There is also a traced release example: issue #920 reports different exported F-clef pitches in 5.10.1 versus 5.9; release 5.10.2 says it fixes #920's rounding error [S07–S08]. The issue itself still displayed Open in the captured view, despite the release note. This shows a version-specific export regression and a release-note fix, not a general quality rate or assurance that later versions have no related defects. The inspected 5.11.0 issue remains separate from that fixed case.

Audiveris is therefore a **research candidate**, not a selected dependency or a correctness oracle. Prefer a workflow that records the source hash, tool/build version, output hash, and a per-part/page review status. Preserve both the source and editable OMR project/output. Mark “reviewed” only after a person compares the relevant interpreted output to the page; keep unread/rejected pages explicit. Because the code is AGPL-3.0 [S04], distribution or server-side use requires a deliberate license review; no legal conclusion is offered here.

### Score identifiers, time, and page coordinates

MusicXML 4.0 distinguishes a measure's `number` token from an optional document-unique `id`. Measure numbers may be non-numeric, displayed `text` may differ, a measure's number can be non-unique within a part, and `non-controlling` measures may not line up at the left barline with other parts [S19]. Thus a printed “m. 12” is useful human context but is not a durable cross-part or cross-version key. A document ID can distinguish an element in that one document; the format does not promise the same ID after re-export or file replacement. Preserve a file hash/revision with any such ID.

MusicXML timing uses `<divisions>` per quarter note; `<duration>` is in those division units, and divisions must accommodate tuplets [S20–S21]. Store the notation file version and divisions context with any timing offset; do not treat those integers as seconds, pixels, or a universally fixed tick rate. MusicXML “tenths” are tenths of interline staff space, scaled through `<scaling>`, not screen pixels or PDF points [S22]. Do not reuse renderer coordinates as source-page coordinates.

The MEI Guidelines' `facsimile`/`surface`/`zone` structures support a written page image and links from encoded events/measures via IDs and `facs`; surface coordinates are relative to the abstract surface and need not equal a selected graphic's pixel dimensions [S17–S18]. This is a strong archival analogy and an optional later interchange path when a source arrives with MEI. It does not make a scanned score automatically aligned to MEI, and it is more structured than the minimum rehearsal workflow needs.

W3C Web Annotation recommends selectors that identify a segment and allows multiple selectors for the same segment; its SVG selector's dimensions are relative to the source resource [S16, §§4.2, 4.2.7]. This supports a portable sidecar pattern (source revision + selector + note), including an image-region fallback beside a semantic target. The Data Model is not a transport/sync protocol and does not define music notation identity, ensemble roles, or migration; those remain product decisions [S16, §1.1].

### Minimum useful workflow and portable data

1. **Intake.** Librarian imports allowed scans, phone photos, PDF, MusicXML, or MEI; selects/creates work → edition → part; confirms supplied labels and permission statement; preserves exact bytes and checksum. Exact duplicate hashes may be grouped; semantic equivalence is never inferred from filename.
2. **Preview/review.** Make a page image view first. Optional conversion creates a separate representation with provenance and `not_attempted / queued / failed / needs_review / reviewed / rejected` status. “Reviewed” names reviewer, date, and representation hash. A conversion failure leaves page-only use intact and provides retry/remove-original guidance.
3. **Annotate/map.** Musicians add private page marks and text notes. The director drafts shared passage notes. Each page-specific mark points to a part revision and source-page rendition. A shared rehearsal passage can map to different part pages/measure anchors only through reviewed per-part links. Old annotations stay readable on their original revision.
4. **Publish and rehearse.** Director publishes an immutable selection. Create a portable `.zip` bundle with a versioned `manifest.json` listing work/edition/part/revision IDs, source/output hashes, permission statement, page order, shared note IDs/revisions/targets, chosen rehearsal items, tool versions, and export time; include only selected files and published annotations. Generate a print-friendly PDF with shared notes visibly rendered and a clear edition/part label; include the machine-readable sidecar so future tools can recover selectors. Never flatten private marks into a shared PDF. A musician can open the packet offline.
5. **Return/recover/delete.** Members may submit new private or proposed shared-note revisions as a packet or pending change file. Import validates base/revision IDs and retains conflicts. Keep previous published revisions until explicit retention cleanup. Provide per-item deletion and explain which files, packet copies, local devices, and backups it affects. If an import or render is incomplete, keep the last usable revision, show an actionable failed/needs-review state, and permit retry without replacing the original.

This packet format is a proposed app-specific envelope, not an existing interoperability standard. The optional sidecar can borrow Web Annotation concepts for page selectors and MEI references for notation/facsimile links; an export test must verify what another program can actually read. For a small volunteer group, explicit snapshots and conflict copies cost an extra handoff step but avoid requiring a continuously hosted paid account or promising untested concurrent merging.

## Observable validation proposal (not executed)

These are future checks for a legitimate, permission-cleared sample set. Define the set with the ensemble before use. Do not upload members' scores to an external conversion service during testing.

- **Intake/provenance:** import one scanned image, one phone photograph, a PDF with mixed orientation, a supplied MusicXML and a supplied MEI file. Compare original bytes/hash before and after; reopen each item's source, edition, part, and permission fields; confirm a same-hash re-import does not create a false new revision while a changed byte hash does.
- **OMR failure/review:** on simple/complex print and a skewed photograph, record per-page completion/failure and compare every interpreted page to the original. A page that fails or is not inspected must never display “reviewed.” Record observed omissions/extra symbols as examples; do not claim a general recognition rate from this small sample. Include export/reopen failures such as the risk in [S06].
- **Page selector:** draw regions on the same fixed rendition at two zoom levels, rotations supported by the viewer, and one resize; verify the mark overlays the same source region. Change the rendition profile and replace/crop/insert a page; require the old target to remain inspectable and the new target to be `needs_review`, never auto-moved.
- **Part/passage mapping:** use two allowed parts with different pagination and at least one differing or missing measure label. Ask a director to link a rehearsal passage to both. Confirm each member lands on the correct part/page and the group passage does not pretend the labels or pages are identical.
- **Semantic selector:** on notation files with/without IDs and with different `divisions`, verify stored IDs remain scoped to the exact file hash and musical offsets resolve using that file's divisions. Re-export the score and confirm old IDs do not silently bind to a different symbol; require re-review when the ID is absent/changed.
- **Offline/publication/conflict:** disconnect network after packet creation; open page, shared notes, ordered rehearsal items, and add a private mark. Confirm private content is absent from the director's packet. Create two offline edits to the same shared note, import both, and verify both survive with an explicit resolution prompt; verify independent notes merge without rewriting originals.
- **Export/access/deletion/recovery:** reopen bundle on a clean device without network; check manifest, filenames, hashes, page order, edition/part identity, and rendered print labels. Attempt deletion for each content category; verify documented behavior for a known managed copy, an offline copy, and a retained backup. Interrupt a conversion/export and retry; verify last good revision and source bytes remain readable.

## Decisions, optional leads, and limits

**Decide now:** page-first core; immutable source revisions; explicit identity/provenance; optional reviewed notation; dual but revision-scoped anchors; director publication; portable offline packet; no automatic cross-edition/part/page migration; no cloud/account dependency in v1. **Defer:** renderer selection until host platform and accessibility requirements are known; embedding versus separately installed Audiveris/Verovio until distribution/license policy is known; real-time sync and user authentication until there is a chosen hosted/shared-server model; exact backup duration until members approve a retention policy.

Optional future work is a curated MEI bridge for source/page/symbol alignment when volunteers need archive-grade linking; assisted but human-confirmed inter-part passage mapping; and authenticated synchronization of immutable packets. Each stays optional until a measured rehearsal task justifies its maintenance cost.

**Uncertainty and remaining objections:** No score files, representative workload, platform matrix, rights evidence, or device/account model were supplied. No OMR or rendering accuracy test was run; no tool behavior should be generalized beyond inspected docs/code and cited issue/release history. MusicXML/MEI IDs can aid a single representation but do not prove cross-version identity. A generated view may differ from printed layout. The exact portable manifest schema, annotation merge UX, authentication topology, retention durations, and how to treat a member's removed-but-offline packet need product decisions before implementation. Public issue reports are evidence of reported cases, not confirmation of frequency or maintainers' diagnosis. The study did not audit every issue or score feature in the selected projects.

## Claim check and critical review

- **Checked:** frozen input hashes match the input map; B-P1–B-P7 were each compared against the frozen section IDs. All source IDs in the source map point to captured bytes with calculated SHA-256 and exact access time.
- **Checked:** Audiveris 5.11.0 commit, `Book.export` flow, `RunTable` marshal callbacks, issue #971 status/reported version, and #920 release-note history were compared at their recorded pinned sources. The hypothesized crash mechanism remains an inference; the issue report was not reproduced.
- **Checked:** MusicXML `number`/`id`, division timing, MusicXML tenths, MEI surface-zone frames, W3C selector/frame semantics, and Verovio page indexing/editor stability were traced to exact reference/API entries and cited above.
- **Repaired:** do not rely on user-entered measure labels or renderer output coordinates as durable identities; page annotations are bound to an exact revision; interpretation stays optional and unreviewed until human check; publication separates private notes; export/deletion claims are bounded to copies actually controlled.
- **Unresolved objections:** whether the host uses a browser/native viewer; which exact pages/formats the ensemble needs; whether preserving/editing a structured file is worth license/maintenance burden; how roles authenticate in a shared server; retention windows; and how imports handle an offline member's stale copy. These are explicit gates, not scientific facts.
