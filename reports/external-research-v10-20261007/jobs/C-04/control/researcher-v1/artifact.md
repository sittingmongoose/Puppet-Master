# C-04/control/researcher-v1 — research and planning proposal

## Recommendation

Use a **facsimile-first, versioned library** for the first useful workflow. Preserve each authorized upload exactly as received and treat previews, OCR/OMR, notation files, and rendered notation as identifiable derivatives. Let members read and mark published material offline. Use representation-specific anchors and explicit librarian-reviewed links across parts. Add structured navigation only for passages a musician has checked against the source. Do not require OMR to make a packet or an annotation usable.

For the initial group workflow, use versioned packet exchange: a director publishes a read-only rehearsal snapshot; players download it, annotate locally, and can explicitly submit shared notes against the snapshot they used. A librarian resolves conflicting edits into a new published revision. This has no permanent account or network dependency, and the packet stays useful in a room with poor connectivity. It is deliberately a small-group workflow, not live collaborative editing. A self-hosted server can be a later option if volunteers prove that packet exchange is too cumbersome.

The brief itself excludes score marketplaces, acquiring copyrighted catalogs, composition, replacing engraving tools, and live performance assessment. The proposal keeps those boundaries and does not presume a score collection or validated recognizer exists.

## Discovery and competing mechanisms

I began from the user's workflow and constraints, before inspecting the frozen plan: preserve varied inputs, help people find passages, retain distinct private and shared marks, handle different part pagination, and work offline with portable handoff. Public primary discovery located an OMR editor (Audiveris), a standard interchange format (MusicXML), a notation renderer/importer (Verovio), a PDF viewer/coordinate API (PDF.js), the music-encoding alternative MEI, and the W3C Web Annotation selector model. These are different layers; none by itself supplies the complete library, rights, identity, collaboration, or deletion policy.

| Mechanism | What it buys | Main cost or failure boundary | Proposal |
|---|---|---|---|
| **Page/facsimile first**: notes point to a specific original file version and page region | Works for PDFs, photos, scans, and printed packets without recognizing the notes; members see the exact notation they rehearsed | A crop, replacement, rotation, or new pagination can make a saved region wrong; a page coordinate cannot align two parts by itself | Make this the dependable MVP anchor. A changed asset makes its anchors stale pending review |
| **Symbolic/semantic first**: OMR produces MusicXML; notes point to source-specific part/measure/staff/beat/event | Can support measure navigation and potentially link passages across different page layouts after correspondence review | Recognition and export can be wrong or lossy; measure labels and element IDs are not cross-edition identities; renderer reflow is not the source page | Optional, human-checked derivative; never replace the page source or silently migrate an anchor |
| **Facsimile-linked encoding**: MEI represents notation and connects score elements to image surfaces/zones | More expressive for editorially linking a score transcription with source images | Requires encoding and conversion expertise plus explicit coordinate transforms; more than a small volunteer group needs for intake | Keep as a future lead if reviewed passages and facsimiles become a curatorial priority |

A second consequential choice is collaboration. Exchanging versioned bundles fits intermittent connectivity and is easy to archive, but updates are asynchronous and need a librarian review. A continuously available hosted service reduces manual exchange but adds account, hosting, access-control, backup, and connectivity duties. A self-hosted LAN service avoids a permanent vendor account but is unavailable when the LAN/server is absent and still needs offline conflict handling. A shared folder or peer-sync tool is a possible transport, not a collaboration model: it does not itself decide which edition is current, separate private from shared notes, review conflicts, or recall downloaded copies. Start with explicit bundles; revisit only if the pilot shows a real burden.

## Component and data evidence

**Audiveris / OMR.** The pinned 5.11.0 handbook says the target is printed Common Western Music Notation, handwritten scores are unsupported, only common symbols are supported, and recognition still needs quick human verification/correction. It documents the AGPL-3.0 license. Its export guide distinguishes editable/restartable `.omr` work from `.mxl`: `.omr` can regenerate MusicXML, while MusicXML export is lossy and cannot reconstruct all OMR data ([AUD-01](sources/audiveris-handbook-5.11.0.md), overview; [AUD-02](sources/audiveris-export-5.11.0.md), “Saving” and “.omr files vs. .mxl files”). Treat `.omr` as an optional work file, not the library's sole source; keep it only when the group chooses the storage and license burden.

At commit `9e1e55cd2746037d059345881c53e6a6754bffbd` (release 5.11.0), `PartwiseBuilder` emits parts with IDs from Audiveris logical-part IDs and measure numbers from score IDs, with other measure-number forms used for repeat copies ([AUD-03](sources/audiveris-PartwiseBuilder-5.11.0.java), lines 550–631, 1981–1986, 2217–2223). These are useful within an export; the code does not establish stable IDs between uploads or editions.

A relevant history trace is specific and bounded. Issue #920 reports a bass-clef pitch offset in MusicXML from 5.10.1 where the reporter did not observe it in 5.9 ([AUD-04](sources/audiveris-issue-920.html), report/environment). Release 5.10.2 identifies the #920 fix as an F-clef pitch-rounding error; the pinned 5.10.1→5.10.2 patch changes `ClefInter` pitch/bounds behavior ([AUD-05](sources/audiveris-release-5.10.2.html); [AUD-06](sources/audiveris-5.10.1-to-5.10.2.patch), patch 24/30). The captured patch contains no dedicated regression-test file for this fix. It supports “this particular bug was fixed in 5.10.2,” not general recognition accuracy.

Release 5.11.0 is the current release observed in this capture ([AUD-08](sources/audiveris-release-5.11.0.html), release tag/commit). Issue #971 is a still-open user report against exact build `9e1e55cd2746037d059345881c53e6a6754bffbd`: in one multi-sheet batch, all sheets reportedly reached PAGE but export produced no MusicXML after a saved-structure reload/recovery exception ([AUD-07](sources/audiveris-issue-971.html), “Summary,” “Environment,” and “Minimal reproducer”). I did not fetch the score or independently reproduce the report. Its exact scope is not proof that all books fail; it is a reason to exercise multi-page save/reload/export before choosing a batch workflow. No issue title is treated as evidence beyond its stated version and report.

**MusicXML, Verovio, and MEI.** The MusicXML 4.0 schema is the pinned `v4.0` tag at `799e2defb2ece0ae7bafe08dcbcac25b2c631d53` ([MXL-01](sources/musicxml-4.0-musicxml.xsd), `measure-attributes` and `part-attributes`, lines 2383–2410). It says `measure@number` is a required token, may be non-numeric, and may be non-unique within a part; `measure@text` may be a different printed label. Partwise numbers coordinate parts at shared barlines, not editions or separate exports. `part@id` is an ID reference to that file's own part list. The same schema defines `<divisions>` as divisions per quarter note (line 2822): if a checked locator stores beat position, express it as an exact rational quarter-note offset and retain the source divisions value, never as elapsed seconds ([MXL-01](sources/musicxml-4.0-musicxml.xsd), lines 2820–2822). Thus store the source-file hash and interpretation ID around any measure/event locator; do not use a measure number or MusicXML part ID as a library-wide identity.

Verovio 6.3.0 (commit `425dd7b6ba26edcecbe345c10b15586d095743d9`) describes itself as an MEI engraver that can import/render MusicXML and output SVG; it is LGPL-licensed ([VRV-01](sources/verovio-6.3.0-README.md), lines 11–29). Its importer code keeps the source measure number as a label, also tracks measures by sequence index, and when numbers repeat prefers the matching index ([VRV-02](sources/verovio-6.3.0-iomusxml.cpp), lines 193–209, 358–402, 1815–1883). That is implementation evidence for one renderer, not a format guarantee. Its pinned 6.3.0 changelog includes continued MusicXML importer changes, reinforcing that rendered output is version-sensitive ([VRV-03](sources/verovio-6.3.0-CHANGELOG.md), 6.3.0 entry; [VRV-04](sources/verovio-release-6.3.0.html)). Verovio can be evaluated as an optional notation view for reviewed structure; it is not an OMR engine and should not silently stand in for the uploaded page.

MEI 5.1 offers a richer alternative: a `surface` is a rectangular writing-space that can have one or more graphics, and a `zone` denotes an area; `@facs` can point from an encoded element to a surface or zone ([MEI-01](sources/mei-v5.1-surface.html); [MEI-02](sources/mei-v5.1-zone.html); [MEI-03](sources/mei-v5.1-att-facsimile.html)). The MEI 5.1 guidelines specify that a zone's coordinates are relative to its parent surface and need not be the same frame as the dimensions of a particular graphic (Guidelines §12.1, listing 438, p. 387; [MEI-04](sources/mei-v5.1-guidelines.pdf)). That is useful for curated score/facsimile links but would require explicit transforms. Do not copy those values into PDF.js or image coordinates without conversion.

**PDF.js and annotation analogy.** PDF.js 6.3.289 at commit `1c8020a7d4e43668ac287a3ecf9a8dbea17e4c56` has a `PageViewport` transform parameterized by the page view box, `userUnit`, scale, rotation, and offsets; `convertToPdfPoint` reverses the viewport transform ([PDF-01](sources/pdfjs-6.3.289-page_viewport.js), lines 47–73, 186–212). Its example documents the PDF bottom-left versus canvas top-left convention and page viewports at 72 DPI ([PDF-02](sources/pdfjs-6.3.289-examples.md), “Rendering the Page”). Save anchors in a documented source-page frame and use that API boundary, not CSS pixels or device DPI. PDF.js `AnnotationStorage` is an in-memory map with serialization for the API; it is not an ensemble's independent, role-aware sidecar store ([PDF-03](sources/pdfjs-6.3.289-annotation_storage.js), lines 26–42, 114–136, 168–200). A maintainer discussion says applications must manage separate persistence themselves ([PDF-05](sources/pdfjs-discussion-17649.html), maintainer answer). An open PDF.js report describes a 4/3 DPI/viewport-coordinate mismatch on 5.4.530 ([PDF-04](sources/pdfjs-issue-20604.html), version/reproduction); that report does not establish the same bug in 6.3.289. It justifies explicit rotation, crop, zoom, high-DPI and pointer-to-source regression checks on the selected build. The studied 6.3.289 release and source are pinned in [PDF-06](sources/pdfjs-release-6.3.289.html).

As a cross-domain analogy, W3C Web Annotation defines typed target selectors and representation state. It warns that position selectors are brittle when the target changes and recommends identifying the desired representation; quote selectors can also expose text that should not be copied from restricted works ([WEB-01](sources/w3c-web-annotation-model.html), §§4.2.4–4.3). Adopt the separation of body, target, selector, and representation version as a design idea, not the full JSON-LD protocol.

### Minimum record and workflow

1. **Intake:** librarian imports only a score the ensemble says it is allowed to use. Create an asset/version record with exact bytes/hash, filename, media type, page count/labels, received-by/time, source note, and permission statement/provenance. Present likely duplicates as candidates for a person to decide; never merge by title alone.
2. **Prepare:** preserve the original file. Create a preview derivative with generator/version and hash. If the material is printed CWMN and a responsible volunteer opts in, run OMR as an isolated, optional job. Keep its source hash, exact version/options, native project if useful, MusicXML derivative, and per-page failure/warning state. A failure leaves the source readable. Keep status `unreviewed` until scoped manual checking.
3. **Link parts:** librarian assigns each part to a specific edition and version. Record the part's submitted label/instrument/transposition text as observed, plus corrected display labels and who corrected them. Don't assert that similarly named parts or two editions are equivalent.
4. **Annotate:** a personal mark is private to its owner. A director note is ensemble-visible only after explicit publication. Each note has immutable ID, body, creator, audience, time, publication revision, status, source-version target(s), and edit/supersession links. A passage label is useful text, not a key. If a verified interpretation is available, attach its source-specific structural locator in addition to (not instead of) the visible-page locator.
5. **Map differently paginated parts:** author one shared note with a readable textual location; attach a separate page/structure target for each part only after a musician or librarian checks it. Show part label and source version beside each link. Never infer that “measure 20” in one upload equals “measure 20” in another. A missing/uncertain map remains readable as text and is not clickable on the wrong page.
6. **Publish and rehearse offline:** the director creates an immutable ordered snapshot. The member opens it without a network, reads selected parts, and retains private marks locally. “Submit shared note” is an explicit action that includes author and base snapshot. The librarian reviews a returned bundle and publishes a new snapshot. If the same note was independently edited, retain both changes and ask for resolution.
7. **Export:** ship a self-describing ZIP with `manifest.json`, selected authorized source pages, optional checked rendering, shared notes only, hashes, edition/part labels, and a plain README. Reopen and checksum the packet on a device with no connection. The packet must explain a note even if the app or symbolic renderer is unavailable. Do not flatten personal marks into a director's PDF.

### Retention, access, and recovery

Use three roles for the pilot: librarian can ingest/edit identity/provenance; director can curate and publish shared rehearsal notes; members can read published packets, keep personal marks, and submit explicit shared additions. If a person can be both librarian and director, grant both roles explicitly. Keep the uploaded-source permission as an attributed declaration, not an ownership verdict. Limit exported contents to selected material and chosen shared notes.

Set a written retention choice before intake: retain the source and its required derivative while active; on removal, stop future publication, remove active source/derivative/preview copies and caches, and retain only a minimal non-content tombstone needed to explain that a referenced item was removed. Set a finite backup expiry and test that expired backups are actually removed. Let a member export or delete their personal marks. Document that copies already downloaded to devices may persist and cannot be technically recalled by an offline app.

Keep assets as ordinary files and a small portable manifest/index, not a single irreplaceable database blob. Back up originals, manifests, note events, and mapping/review metadata together; store no credential or permanent vendor account in a packet. Recovery should restore to a separate directory, recompute hashes, and confirm that note ownership, version labels, stale anchors, and shared/private boundaries remain intact. For conversion failures, preserve originals, retain logs/version/options, set a retryable failed status, and avoid creating a reviewed state. A rebuild of any derivative is a new derived version, not an overwrite.

## Optional leads, uncertainty, and validation proposal

Optional after a working paper/PDF packet: Verovio as a locally packaged second view for passages with checked MusicXML; MEI if volunteers demonstrate a need for authored notation-to-facsimile zones; a small self-hosted sync service if manual submissions fail the pilot. Before distributing any bundled component, review its exact license and packaging implications. Audiveris is AGPL-3.0 and Verovio LGPL; this research does not make a legal compatibility determination.

No recognition accuracy, coordinate migration, cross-part correspondence quality, offline conflict behavior, storage burden, rights status, license compatibility, or old-copy removal behavior is validated here. No ensemble score was supplied or processed. The recent issue reports are primary project history but remain reports, not independent reproduction. Current release pages can change; keep the cited builds pinned for any pilot.

**Proposed checks for a later authorized pilot (none executed here):**

- Use a small group-approved set spanning PDF, phone photo, digital document, and editable notation; note each permission basis. Verify original-byte hash and page inventory on ingest/export/restore.
- Include at least one rotated/cropped PDF and raster photo. Place region marks at known staff corners/measure centers; test zoom, 90°/180° rotation, crop box, window resize, and high-DPI display. Compare mapped source coordinates on reopening; fail if an anchor shifts outside the marked source region. Run on the selected PDF.js build because issue #20604 is version-specific.
- For optional OMR, independently verify selected notes/rests, rhythm, accidentals, clefs, parts, measure sequence, and printed labels against the source. Track which areas a reviewer checked. Exercise multi-page save, close/reopen, re-export, and one known failure/cancel case. Keep a mismatch report; never infer acceptance from successful export alone.
- Reflow one verified MusicXML passage in Verovio and compare the musical target, while showing that its rendered pagination may differ from the original. Test duplicated/non-numeric/pickup measure labels and an absent optional event ID. Confirm stale or ambiguous targets do not produce a wrong click.
- Give two musicians different part pagination. Ask each to find the same director note from the packet, then record whether each part target was explicitly verified. Test replacing one page and one full part: old notes remain visible as stale; no automatic migration occurs.
- Work disconnected, create private marks and explicit shared submissions from one base snapshot, then submit simultaneous edits to one shared note. Confirm no private mark appears in the return packet, both edits survive conflict detection, and the librarian can publish a resolved next revision.
- Export and reopen a rehearsal ZIP entirely offline. Verify checksums, edition/part identity, selected pages, note readability, permission metadata, and exclusion of personal marks. Exercise deletion, cache cleanup, backup expiry, restore, and a withdrawal notice; confirm the packet explains that old offline copies persist.
