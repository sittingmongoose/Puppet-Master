# C-04/control/reviser-v1 — final research and planning proposal

## Decision

For this hypothetical small ensemble, plan a **facsimile-first, versioned library with portable rehearsal snapshots and explicit returned-note review**. Keep the original authorized scan, photo, PDF, digital score document, or notation export identifiable while retained. Let people rehearse from a self-describing packet without a network. Keep interpretation and rendering as optional derivatives; a note or packet must remain useful when no notation conversion is available.

Start with a small record model and a librarian-led workflow. Do not build a general sync engine, an elaborate event ledger, or a cross-edition music identity service for the first pilot. Preserve the safety properties that matter: source/version identity, review scope, private/shared separation, explicit publication, non-silent conflict handling, readable export, and a deletion/backup policy. Add structural notation links or replication only if the pilot shows a concrete need and a maintainer is willing to own them.

This is a proposal for the brief’s hypothetical ensemble, not a description of an existing ensemble, collection, implementation, or test result. I did not change canonical Plans, create WorkNodes, or build software.

## Open discovery and useful mechanisms

I began with open discovery from the user-level brief—authorized mixed-format scores, edition/part identity, checked passage help, distinct private and director markings, different pagination, poor connectivity, and portable handoff—before reading the frozen plan. Broad public discovery surfaced page-first readers, group-packet workflows, notation import/export, OMR, linked facsimiles, and offline replication. I then selected public primary sources for implementation and data semantics. Product marketing claims were not used as evidence of technical guarantees.

| Mechanism | Where it helps | Cost or limit | Decision |
|---|---|---|---|
| **Facsimile-first page regions and human labels** | Supports scans, photos and PDFs without recognizing notation; the musician sees the page actually rehearsed. | A region is tied to one exact source version and page. Crop, replacement, orientation or re-pagination can make it stale. It cannot align different parts by itself. | MVP anchor. Keep the old target and ask for review after source change. PDF.js is a candidate PDF rendering/coordinate component, not the library or note store ([REV-PDF-01](sources/pdfjs-6.3.289-page_viewport.js), [REV-PDF-03](sources/pdfjs-6.3.289-annotation_storage.js)). |
| **OMR → MusicXML → notation rendering** | Can provide optional measure navigation or another view for suitable printed notation and an editable score file. | OMR can be wrong and export can be lossy; symbol/part/measure labels are file-local. Rendered pagination may differ from the source. It adds a volunteer review and license burden. | Optional and off by default. Audiveris 5.11.0 is a pilot candidate only for suitable printed Common Western Music Notation; Verovio 6.3.0 is a candidate renderer for existing/checked MusicXML, not an OMR engine ([REV-AUD-01](sources/audiveris-handbook-5.11.0.md), [REV-AUD-02](sources/audiveris-export-5.11.0.md), [REV-VRV-01](sources/verovio-6.3.0-README.md)). |
| **Facsimile-linked notation such as MEI** | Offers an authored structure for linking encoded events to a surface and marked image region. | Needs curated encoding, stable document-local IDs and an explicit surface-to-image coordinate transform. It is too much to require at intake. | Keep as an optional future research path for a group that wants scholarly/curatorial links ([REV-MEI-01](sources/mei-v5.1-surface.html), [REV-MEI-02](sources/mei-v5.1-zone.html), [REV-MEI-03](sources/mei-v5.1-att-facsimile.html)). |
| **Published packet and returned additions** | Has a clear revision, works with no network/account, and can open in ordinary readers. | Asynchronous; the librarian must inspect competing submissions. A disconnected copy cannot be recalled. | Start here. Use a folder or ZIP with a manifest and explicit base-revision references. |
| **Offline local database with later replication** | Could reduce manual bundle transfer and retry synchronization after reconnection. | Requires a maintained endpoint, access design, replica lifecycle, conflict UX, backup and deletion rules. Conflict resolution still belongs to the application. | Later option only. PouchDB 9.0.0 documentation describes retryable live replication and conflicts, but this review did not inspect a pinned PouchDB implementation; it is not a component recommendation ([REV-PDB-01](sources/pouchdb-replication.html), [REV-PDB-02](sources/pouchdb-conflicts.html), release context [REV-PDB-03](sources/pouchdb-release-9.0.0.html)). |
| **Hosted or LAN service** | Can centralize publication and reduce manual return handling; a LAN server may avoid a permanent vendor account. | Needs connectivity at the right time plus account/service operation, access controls, backups, deletion and conflict policies. A LAN is unavailable when its server is absent. | Do not make it an MVP dependency. Reconsider only if bundle exchange fails the pilot. |

The cross-domain W3C Web Annotation model is a useful analogy: keep annotation body, target, selector and representation state separate. It warns that positional selectors can be brittle when a resource changes. Adopt that separation as a design idea, not its full JSON-LD protocol ([REV-WA-01](sources/w3c-web-annotation-model.html), §§3–4). A title, a measure label, or a pixel coordinate alone is not a durable cross-edition identity.

## Pinned implementation and data evidence

### Audiveris and the bounded issue history

At the pinned Audiveris 5.11.0 commit `9e1e55cd2746037d059345881c53e6a6754bffbd`, the handbook describes an interactive OMR editor for printed Common Western Music Notation, says handwritten scores are unsupported and only common symbols are supported, and says users need to verify/correct output. It identifies AGPL-3.0 licensing. The export guide distinguishes reloadable `.omr` project data from lossy `.mxl`/MusicXML export; MusicXML cannot recreate all OMR work. This supports a source-preserving, opt-in job and a license/packaging review, not a recognition-quality promise ([REV-AUD-01](sources/audiveris-handbook-5.11.0.md), lines 43–69; [REV-AUD-02](sources/audiveris-export-5.11.0.md), lines 9–59; release pin [REV-AUD-04](sources/audiveris-release-5.11.0.html)).

The pinned `PartwiseBuilder` creates a MusicXML part ID from an Audiveris logical-part ID and writes measure labels from score IDs, including special forms for repeat copies. These are useful within that export; the code establishes no stable ID across another upload, edition, or export ([REV-AUD-03](sources/audiveris-PartwiseBuilder-5.11.0.java), lines 550–632, 1981–1986, 2217–2223).

I checked two distinct history points. Issue #920 is a reporter’s F-clef pitch-offset report against 5.10.1 compared with 5.9. The 5.10.2 release notes identify the specific fix as F-clef pitch rounding, and the pinned 5.10.1→5.10.2 patch changes `ClefInter`/clef code. No dedicated regression-test path appears in that comparison range; that is a range-limited observation, not proof that no test exists elsewhere. This trace shows a specific defect was repaired, not general OMR accuracy ([REV-AUD-06](sources/audiveris-issue-920.html), [REV-AUD-07](sources/audiveris-release-5.10.2.html), [REV-AUD-08](sources/audiveris-5.10.1-to-5.10.2.patch)).

Issue #971 remains an open, un-reproduced report at the captured time against the exact 5.11.0 build. It describes one seven-sheet batch where sheets reached PAGE but save/reload during export failed and no MusicXML was produced. I independently checked the pinned code: `RunTable.afterUnmarshal` calls `afterMarshal`, whose `sequences.length` access has no null guard; the reported `FileSystemAlreadyExistsException` is also consistent with `ZipFileSystem.open` requesting a new ZIP filesystem. This makes the report relevant to the optional multi-page workflow, but it does **not** establish prevalence, prove the reporter’s full causal account, or show an independent reproduction. The linked score was not downloaded or used. Do not treat batch export as dependable until the exact chosen build passes a permission-cleared save/close/reopen/re-export and failure-recovery pilot ([REV-AUD-05](sources/audiveris-issue-971.html); code [REV-AUD-09](sources/audiveris-RunTable-5.11.0.java), lines 329–360; [REV-AUD-10](sources/audiveris-ZipFileSystem-5.11.0.java), lines 91–113; [REV-AUD-11](sources/audiveris-Book-5.11.0.java), lines 1837–1858).

### MusicXML, Verovio and MEI

The pinned MusicXML 4.0 schema says `measure@number` is required but may be nonnumeric and non-unique in a part. In partwise files, numbers **should** match across parts only when measures share a left barline; `non-controlling` measures can have a different barline, and `measure@text` can differ from the machine-oriented number. A part ID is an ID reference within that document’s own part list. `divisions` means subdivisions per quarter note, not seconds or a cross-file beat scale. Therefore keep labels for readers, and never use a MusicXML part ID or measure number as a library-wide or cross-edition identity. If a checked structural locator later needs time within a measure, store an exact rational quarter-note offset alongside the source and interpretation identity; do not persist raw `divisions` as if its unit were universal ([REV-MXL-01](sources/musicxml-4.0-musicxml.xsd), lines 2383–2410, 2820–2822).

Verovio 6.3.0 (commit `425dd7b6ba26edcecbe345c10b15586d095743d9`) advertises MusicXML import/rendering to SVG and LGPL licensing. In this pinned importer, measures are tracked by sequence index as well as label; where labels repeat, it prefers a matching sequence index. This implementation detail reinforces that labels alone are ambiguous. It does not prove that a rendered view preserves every input feature or aligns with source pages. Keep Verovio optional for checked MusicXML and compare its output on the exact ensemble files before selecting it ([REV-VRV-01](sources/verovio-6.3.0-README.md), lines 11–29; [REV-VRV-02](sources/verovio-6.3.0-iomusxml.cpp), lines 193–211, 358–402, 1815–1883; release [REV-VRV-03](sources/verovio-release-6.3.0.html)).

MEI 5.1 defines `surface` as a coordinate space that can group graphics, `zone` as an area of interest, and `@facs` as a link to facsimile structures. This is a richer future option for curated links, not a drop-in coordinate format for PDF.js or photos; its own parent surface and graphic mapping must be preserved and tested. No MEI file was authored or rendered here ([REV-MEI-01](sources/mei-v5.1-surface.html), [REV-MEI-02](sources/mei-v5.1-zone.html), [REV-MEI-03](sources/mei-v5.1-att-facsimile.html)).

### PDF coordinates and annotation storage

PDF.js 6.3.289 at commit `1c8020a7d4e43668ac287a3ecf9a8dbea17e4c56` constructs a `PageViewport` transform using `viewBox`, `userUnit`, scale, rotation and offsets. It provides both `convertToViewportPoint` and the inverse `convertToPdfPoint`. Its code accepts quarter-turn rotations (0/90/180/270) and rejects other rotation values for this viewport API. Persist geometry in the source PDF page frame, bound to the exact asset version/page and needed page-box/unit/orientation metadata; convert current pointer coordinates through the API. Do not store CSS pixels, screen DPI, zoom, or window offsets as durable coordinates. Raster photos need a separate source-pixel frame with original dimensions and recorded orientation transform ([REV-PDF-01](sources/pdfjs-6.3.289-page_viewport.js), lines 54–110, 185–213; rendering example [REV-PDF-02](sources/pdfjs-6.3.289-examples.md); release [REV-PDF-04](sources/pdfjs-release-6.3.289.html)).

PDF.js `AnnotationStorage` is an in-memory map whose values can be serialized for PDF.js APIs. It is not a role-aware ensemble sidecar, a durable library store, a backup policy, or an access-control system. Store rehearsal notes separately with explicit source and audience identity ([REV-PDF-03](sources/pdfjs-6.3.289-annotation_storage.js), lines 29–36, 176–215). I found no primary issue/fix that clearly applies to this exact 6.3.289 coordinate path. An older-version report is not evidence of the same defect in this pin; coordinate behavior remains a proposed validation item, not a tested guarantee.

### Offline replication alternative

PouchDB’s 9.0.0-era guides describe local/remote replication, `live: true` with retry and pause/resume events, immediate 409 conflicts, and eventual conflicts whose deterministic default winner does not resolve note meaning. The app must expose/resolve conflicting revisions or choose a deliberate merge policy. The guides also warn that destroying a replicated database can repopulate it; deleting replicated content requires deleting the relevant records and designing replica/backup handling. These docs make replication a plausible later mechanism, but this reviser did not inspect PouchDB source at a pinned commit or validate its cross-platform behavior. The critic’s concern is therefore accepted: do not recommend it as the selected component. If later chosen, pin and review code, test conflict/deletion behavior, and design authorization first ([REV-PDB-01](sources/pouchdb-replication.html), lines 68–97, 127–143; [REV-PDB-02](sources/pouchdb-conflicts.html), lines 12–32, 53–105; release metadata [REV-PDB-03](sources/pouchdb-release-9.0.0.html)).

## Integrated minimum workflow and proposed records

1. **Intake only authorized material.** The librarian enters work, edition and part labels as supplied, confirms the part’s edition, and records submitter, received time, source note, media type, page inventory and an attributed permission assertion. Create local opaque IDs; keep observed and corrected labels distinct. Store the exact bytes and SHA-256 while retained. Hash equality supports a byte-duplicate suggestion, not authorship or permission. Similar title is not a merge rule.
2. **Prepare a useful page view.** Keep the source asset and version available while retained. For PDF/image inputs, use a reader or a tested PDF/image viewer. For editable notation, preserve the original and include an authorized readable PDF when available; evaluate a local Verovio build for MusicXML only as a later candidate. Record each derivative’s source hash, generator/version/options, output hash, page map and state. If rendering or OMR fails/cancels, keep the source accessible, show a retryable error and never call the result checked.
3. **Use small review states.** Suggested states: `not attempted`, `processing`, `needs review`, `checked (scoped)`, `failed`, and `stale`. `checked` records exactly which passage/pages, source and interpretation version, who checked them and when. A spot check does not bless the whole score. Keep the original page beside any structured view.
4. **Anchor annotations to the representation used.** A minimal note record needs note ID, body, creator/member ID, private/shared visibility, created time, base publication revision when shared, and zero or more typed targets. A PDF target stores asset-version ID, page index, source-frame geometry and page view metadata; an image target stores original dimensions and orientation transform. Page and printed measure text remain explanatory labels. If a structured target is later enabled, store derivative/interpretation ID, document-local part ID, sequence position, printed label and (only if needed) an exact rational beat offset. MusicXML `divisions` is per quarter note; do not treat its raw integer as seconds or a global unit. Do not infer equivalence across two files.
5. **Link parts by review, not numbering.** A director writes one readable note and can add a distinct target for each part only after a player or librarian checks that target in the exact source version. Different pagination is represented by multiple targets for one note, not a presumed common measure. Keep an unresolved target visibly unresolved.
6. **Publish and return a bounded snapshot.** The director publishes an ordered read-only revision. A member opens selected parts offline and keeps personal markings locally. “Submit shared note” is explicit and creates a return record tied to the packet revision; private marks are excluded. If two returns touch one shared note, preserve both and ask the librarian to publish a resolution/new revision. A local file copy is not revocable; update notices can request deletion but cannot prove it.
7. **Export and restore without the app.** Deliver a folder or ZIP containing a plain README, manifest, selected authorized source pages/files, hashes, work/edition/part and revision IDs, shared notes, target coordinates and stale/checked legend, plus an optional checked PDF overlay/renderer output. Keep clean originals separate from derived marked views. Verify the packet opens in ordinary readers without a network. Restore backups to a separate location and compare hashes, identities, visibility and stale status before replacing an active library.
8. **Withdraw and delete by policy.** Before intake, state who may request removal, what is removed from the live library and caches, backup expiry date, how members can export/delete personal notes, and how to handle withdrawal. Stop future publication and delete active source/derivative copies under that schedule. Retain only the smallest non-content removal record needed to prevent accidental republishing, then expire it as policy allows. Explain that old offline packets may remain. If replication is introduced later, test deletion propagation across every replica and backup; deleting a database/container alone may restore replicated material.

## Reviser resolution of material critique points

- **Scope and maintainer load:** accepted. Use the researcher’s safety properties but take the critic’s staging correction: no full event log, semantic locator registry, or tombstone/backup subsystem for the MVP. Keep only version IDs, explicit note submissions and the minimum retention/deletion policy needed before importing real files.
- **Audiveris evidence:** repaired with fresh source captures and pinned implementation checks. Issue #971 is applicable to one exact 5.11.0 build and relevant to a batch workflow, while remaining a user report without independent reproduction. The code makes the reported failure path plausible; validation is still required. The issue #920 → 5.10.2 release/patch trace is a narrow history example, not a quality claim.
- **MusicXML semantics:** tightened the researcher wording to the schema’s “should match” only for measures sharing a left barline, and retained its non-controlling, duplicate, nonnumeric and printed-text distinctions. No cross-file correspondence is assumed.
- **PouchDB:** keep as an architecture alternative only. Its docs explain conflict and deletion behavior, but I did not inspect pinned source code. No PouchDB component is chosen; source pinning, API/platform tests and license/operations review remain prerequisites.
- **MEI and Verovio:** recaptured their primary documentation/code at pinned 5.1 and 6.3.0 sources. Preserve them as optional opportunities; no editor, renderer or transform was run, and no migration compatibility is claimed.
- **Rights, identity, access:** keep hashes as byte identity/integrity only. A librarian’s permission statement is provenance, not verification. Offline role labels do not prevent file copying. No legal rights determination or secure-access guarantee is made.
- **PDF.js:** independently checked the pinned API and storage implementation. Store source-frame coordinates and keep note persistence outside `AnnotationStorage`. No 5.x coordinate bug is inferred to exist in 6.3.289.

## Conditions, optional leads and open uncertainty

Use only score files the ensemble is authorized to handle; no private score set was supplied, downloaded or processed. No copyright catalog, marketplace, composition, engraving replacement, or live performance scoring is in scope. Before distributing/bundling a component, review the exact build and its license/packaging requirements; Audiveris documents AGPL-3.0 and Verovio LGPL, and this proposal does not decide compatibility. Keep public components/local files and portable outputs ahead of a permanent commercial account, but do not promise that a free component is free of maintenance or license obligations.

Optional after the basic packet works: (a) a pinned Verovio view for existing checked MusicXML; (b) Audiveris for a rights-cleared printed-score OMR pilot; (c) MEI for authored notation-to-facsimile zones; (d) local-first replication or a small hosted/LAN service if return packets create demonstrated labor; (e) a richer search/index or optical metadata extraction. Each is conditional and should have a named maintainer, limited input set, exact version, storage/deletion implications and a measured pilot before it becomes routine.

Open questions: what formats the group can actually open on its rehearsal devices; whether they need a PDF preview for every editable file; acceptable per-device storage and backup expiry; who adjudicates shared-note edits; whether roles must be technically enforced; whether group member identities can be named in return files; and what permission evidence/withdrawal terms the librarian can reliably record. No source supports OMR accuracy on phone photos, cross-part passage alignment, anchor migration, access enforcement in copied bundles, deletion of old offline files, renderer fidelity, or volunteer workload. Those remain pilot questions, not decisions hidden inside the schema.

## Observable validation proposal (none of these checks executed)

Use only a small set whose source and permissions are recorded explicitly by the ensemble or test author. Do not use the issue reporter’s score unless its rights are independently established. Record all checks against exact tool builds and source hashes.

- **Intake/identity:** import a scan/PDF, oriented photo, digital score document and one editable notation export. Compare original-byte hashes and page inventory after export/restore. Give two same-title editions; pass only if they remain separate until a librarian confirms identity. A hash or title match alone must not assert permission.
- **Coordinate recovery:** on PDFs with non-default page boxes and 0/90/180/270 rotation, draw a known region and save in source PDF coordinates via PDF.js. Reopen at different zooms, viewport sizes and device scaling; inverse/forward transform should return within 2 viewport pixels at the recorded display transform and remain over the original marked staff region. Test photos separately using recorded original pixel dimensions and orientation; fail on a region that silently drifts after EXIF/display rotation.
- **Review scope and anchors:** mark only one passage checked and verify other passages remain `needs review`. Replace a page and then a whole part; old targets must remain attached to the old hashes and visibly stale. No replacement may auto-present an old region as current. Different part pagination must be handled with separate verified targets or readable text, never a guessed click.
- **Structured notation:** only if optional OMR/renderer is enabled, use suitable permission-cleared printed CWMN, compare a predeclared sample of notes/rests, rhythm, accidentals, clefs, parts and labels against the source, and record exactly what was checked. Exercise multi-page save, close/reopen, re-export, cancel and failure recovery on the chosen Audiveris build. For existing MusicXML, exercise nonnumeric, duplicate and pickup labels, repeated structures and reflow in the exact Verovio version; compare musical content, not page layout. Successful conversion alone is not acceptance.
- **Offline notes/conflicts/privacy:** download one published revision, disconnect, add personal marks and an explicit shared return, then create simultaneous changes to the same shared note. Pass only if both returns remain inspectable, each shows its base revision, and publication requires a visible librarian decision. Reopen the exported packet and assert personal marks are absent unless a separate explicit sharing action was made.
- **Handoff/recovery/deletion:** open packet PDF and README with no account, app or connection; verify manifest IDs, checksums, selected pages, note readability, stale-target legend and no private data. Restore a backup elsewhere and verify identities and note visibility. Exercise withdrawal and expiry: future packets exclude removed files, active caches are cleared by the stated policy, backup deletion occurs on schedule, and the UI/README says old offline copies cannot be recalled. If replication is ever chosen, verify deletion cannot be undone by a surviving replica.
