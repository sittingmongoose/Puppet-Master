## Research findings from open discovery

### Existing products and mechanisms

- **OpenEnergyMonitor / emonCMS** is a close local-monitoring analogue. Its feeds page documents fixed-interval feeds and variable-interval timestamped feeds; missing fixed-feed values remain null and appear as graph gaps. It also exposes CSV import/export. The home-energy app presents recent power and historical daily kWh views. These mechanisms support retaining explicit interval semantics and showing coverage/gaps. [S01](https://docs.openenergymonitor.org/emoncms/feeds.html) [S03](https://docs.openenergymonitor.org/applications/home-energy.html)
- The same product offers `Log to feed (Join)` to bridge missing values with a straight line and accumulators that bridge gaps and remove resets. That can make a graph easier to read, but it changes evidence. Given P3’s “no estimated value silently becomes a measured value,” this should not be the default import or comparison policy. If a later product choice permits a correction, preserve raw records and mark the derived series and rule visibly. [S02](https://docs.openenergymonitor.org/emoncms/daily-kwh.html)
- **Home Assistant’s Energy dashboard** is an adjacent dashboard model that consumes integrated sensors/statistics with declared units and state classes; it is not a drop-in raw-CSV review workflow. Its long-term statistics aggregate by state class, and its documented `total_increasing` reset rule treats decreases over 10% as resets. Its FAQ also warns that summing resettable sensors can create a false transient and inflate saved totals; it recommends keeping those sources separate. These are useful failure cues, not rules to copy for unknown meter exports. [S04](https://www.home-assistant.io/docs/energy/) [S05](https://www.home-assistant.io/docs/configuration/long-term-statistics/) [S06](https://www.home-assistant.io/docs/energy/faq/)
- **Polars** is a Rust-compatible alternative for CSV data frames and lazy scans. Its guide shows both eager `CsvReader` and lazy `LazyCsvReader`; its time-series guide documents date parsing/schema inference. It is an optional aggregation engine if later profiling justifies it. Here the files cover three meters and one year, but the export interval and actual row counts are unspecified, so there is no evidence yet that a dataframe/query engine is needed. If selected, retain original bytes and perform preview/interpretation before inference or aggregation. [S07](https://docs.pola.rs/user-guide/io/csv/) [S08](https://docs.pola.rs/user-guide/transformations/time-series/parsing/)

### Consequential component: Rust `csv` crate

The current published Rust `csv` version observed in the crates.io registry was **1.4.0**, published 2025-10-17. The signed annotated tag `1.4.0` resolves to immutable commit `4a3997e91d668ea1d8595bdef15625a77cf2308a`; the tag response reported signature verification as valid. I inspected that exact commit’s `src/reader.rs`, `src/error.rs`, `csv-core/src/reader.rs`, and manifests. [S09](https://crates.io/api/v1/crates/csv) [S10](https://api.github.com/repos/BurntSushi/rust-csv/git/tags/2dc6e06cf8a9f199542f1fa5ba35b1b072280e3a) [S11](https://api.github.com/repos/BurntSushi/rust-csv/commits/4a3997e91d668ea1d8595bdef15625a77cf2308a) [S12](https://raw.githubusercontent.com/BurntSushi/rust-csv/4a3997e91d668ea1d8595bdef15625a77cf2308a/src/reader.rs) [S13](https://raw.githubusercontent.com/BurntSushi/rust-csv/4a3997e91d668ea1d8595bdef15625a77cf2308a/src/error.rs) [S14](https://raw.githubusercontent.com/BurntSushi/rust-csv/4a3997e91d668ea1d8595bdef15625a77cf2308a/Cargo.toml) [S15](https://raw.githubusercontent.com/BurntSushi/rust-csv/4a3997e91d668ea1d8595bdef15625a77cf2308a/csv-core/src/reader.rs) [S16](https://raw.githubusercontent.com/BurntSushi/rust-csv/4a3997e91d668ea1d8595bdef15625a77cf2308a/csv-core/Cargo.toml)

- In `src/reader.rs`, `ReaderBuilder::default` sets `has_headers=true` and `flexible=false` (lines 40–48). `ReaderBuilder::flexible` documents that disabling flexibility returns an error when record field counts differ; enabling it turns that check off (lines 230–310). The public `Reader::read_record` path feeds records to `ReaderState::add_record` (lines 1530 onward); `add_record` compares the current field count to the first expected count and returns `ErrorKind::UnequalLengths` with the record position, expected width, and actual width (lines 1882–1900). `ErrorKind::UnequalLengths` exposes that position and both widths in `src/error.rs` (lines 69–80).
- Release tests in `src/reader.rs` cover an unequal-width row failing with its byte/line/record location (`read_record_unequal_fails`, lines 2321–2345), the same input being returned when flexibility is enabled (`read_record_unequal_ok`, lines 2347–2368), and continuing after a shape error (`read_record_unequal_continue`, lines 2370–2398). This supports a preview that preserves and flags irregular rows. It does not establish that those rows are semantically usable.
- The application should explicitly choose a header and row-shape policy. For a review-first importer, either keep the parser strict and collect positioned shape errors while continuing, or use `flexible(true)` only to expose every raw row and then validate every width against the selected header/mapping in application code. In either case, mismatched rows remain review findings and cannot silently enter measured totals. Avoid direct struct deserialization before a user-selected column interpretation; `csv` splits and decodes records but does not determine meter identity, timestamp meaning, unit, interval-vs-counter semantics, or energy validity.

## Proposed replacement sandbox plan

### Goal and bounds

Build a local dashboard for one community-centre building from CSV exports for three meters covering one year. Help operators understand when energy is used, compare periods, and review inconsistent exports. Keep original P1–P6 obligations. No billing certification, tariff conclusion, automated control, equipment-purchase advice, or verified-savings claim.

### P1 — Ingestion and interpretation preview

Import CSV bytes as immutable evidence. For each batch, record the selected meter, source-file identity, import time, original header/cells, parser findings, and a versioned interpretation. In preview let the operator select or confirm the meter, timestamp column and format, timezone/offset, interval-label convention (start/end or cumulative reading instant), value column, unit, value kind (interval energy, average/instantaneous power, or cumulative counter), and interval duration where applicable. Show raw and interpreted values together. Preserve every source row and its parser position, including malformed-width or unparseable rows; mark the reason for review rather than dropping or coercing it. Require explicit confirmation before the mapping contributes to summaries. Keep alternative mappings as competing interpretations.

### P2 — Local evidence store and review history

Keep source files and raw row values immutable. Store parsed candidates, selected mapping/version, meter identity, derived time interval/instant, review flags, user resolution, and provenance back to the source file and row. Compare repeated exports for exact duplicates and overlapping meter/time ranges only after a timestamp interpretation exists. Present both source records and their origin; preserve the operator’s keep/exclude/resolve decision as a review record. Do not automatically overwrite, deduplicate into a single “true” row, or infer counter rollover limits.

### P3 — Calculations and dashboard

Provide daily and monthly totals, time-of-day profiles, and user-selected period comparisons. Derive interval-energy totals only from rows explicitly mapped as interval energy with compatible units. Convert power to energy only when the value is known to be an interval average and the interval duration/time interpretation is known; label the method. For cumulative readings, derive differences only between ordered readings under the same interpretation. A decrease/reset/rollover candidate is a review flag; do not apply a generic reset threshold or infer a rollover maximum. Missing and excluded readings remain visible as gaps and are not interpolated by default.

Show the selected calendar/timezone, exact comparison boundaries, units, interpretation version, expected/valid/missing/excluded coverage, and unresolved review counts. When the timezone is known, aggregate by that building-local calendar while retaining the original timestamp and unambiguous instant; daylight-saving transitions can produce a repeated local clock label or a nonexistent one. In `chrono-tz` 0.10.4, `TimeZone::offset_from_local_datetime` returns `Ambiguous` for overlapping local spans and `None` for gaps, which supports keeping those cases distinct rather than coercing them. [S25](https://docs.rs/chrono-tz/latest/src/chrono_tz/timezone_impl.rs.html) Preserve an offset if supplied. If a local timestamp is ambiguous or nonexistent and the file does not disambiguate it, keep it unresolved until the operator selects an interpretation; do not silently shift or merge it. Do not choose a comparability cutoff absent a product decision; make coverage visible and let the user decide.

### P4 — Alternative interpretations and operator context

Allow saved competing import/measurement interpretations and period comparisons between them. Allow optional dated annotations such as closure periods. Keep narrative annotations separate from measurements and present descriptive differences without attributing cause. Keep savings verification, billing, tariffs, equipment recommendations, and automated control outside the product boundary.

### P5 — Components and privacy

Candidate ingestion component: Rust `csv` 1.4.0 at commit `4a3997e91d668ea1d8595bdef15625a77cf2308a`, with the row-width and position behavior documented above. Keep parsing separate from energy semantics. The application must validate row width, timestamp, numeric value, units, meter, interval/counter type, duplicates, and overlaps after preview. Polars remains an optional candidate for derived aggregation if profiling warrants it; no chart or local-storage library is selected by this research. Run without a network service or account connection. Keep exports account-identifier-free by default, and include identifiers only in an explicitly selected review package.

### P6 — Period comparison export and proposed validation

Export a comparison with meter and import identities, exact selected period/timezone, coverage and missing/excluded counts, selected mapping versions, unit/value kind, review resolutions, method for derived totals, and unresolved uncertainty. Default omit account identifiers. Preserve enough provenance to reproduce the displayed comparison from the retained inputs.

**Proposed checks (not executed):**

1. Import a small CSV with a header, quoted delimiter, and a ragged row. Confirm the preview retains raw cells, identifies the row/width error, and never counts it as a valid measurement. Confirm later valid rows remain reviewable.
2. Re-import identical bytes and an overlapping export. Confirm both source identities remain visible, duplicate/overlap flags are stable, and resolving one source changes a comparison deterministically without rewriting inputs.
3. Use synthetic interval-energy values with an explicit unit conversion and known sum; use a separate average-power sample with known duration. Confirm totals only appear under the declared value kind and conversion. Changing the mapping changes the interpretation version and forces reproducible recalculation.
4. Use a cumulative series with increasing readings, a drop, and an unknown rollover limit. Confirm the drop is flagged, no negative consumption or guessed rollover is silently created, and an operator resolution is recorded before a derived value is included.
5. Use a synthetic timezone fixture with a spring-forward gap and fall-back repeated wall-clock label. Confirm source labels/offsets remain visible, valid offset-bearing times map to distinct instants, and unresolvable naive times are flagged rather than shifted or collapsed. This fixture validates behavior, not the building’s timezone.
6. Remove one interval and mark one suspect interval excluded. Confirm charts and exports show the gap, exclusion reason, coverage and totals calculated from only reviewed included data; no line-join or imputation occurs.
7. Export the same comparison twice from unchanged inputs and decisions. Confirm the manifest, interpretation, provenance, period boundaries, and aggregates are reproducible; confirm account identifiers are absent by default.
8. If comment parsing is enabled for a confirmed file profile, add comments between rows and at EOF without a trailing newline. Confirm comment handling does not swallow a data row; until that test passes against the chosen parser version, leave comment handling disabled for that profile.

### Alternatives, optional work, and unresolved decisions

- Choose an explicit raw-record parser plus app validation for MVP; consider Polars only after representative file-size and interaction profiling shows that an aggregation engine materially helps. The actual export interval and row counts are unknown.
- Support comment-prefixed metadata only if real exports require it. Keep this setting profile-specific because the chosen parser has the open EOF-comment issue described above.
- The exact timezone and whether exports encode offsets, local wall times, interval starts, interval ends, or cumulative reading times are unknown until representative public-safe examples are available from the user. Preserve alternatives rather than deciding now.
- Meter-specific reset and rollover behavior, interval durations, expected coverage denominators, treatment of overlapping-but-not-identical readings, and any comparability thresholds remain product decisions. A generic 10% reset rule is explicitly not adopted from Home Assistant.
- The storage engine, chart library, detailed review-package format, event vocabulary, and whether review packages may include identifiers remain open.
- Source research was limited to public documentation/code, not actual building exports. No full-project cross-reference was available in the supplied plan slice.
