# D-M11-A final: tar filter/error/compat policy for 3.14.0 Linux ingest (bounded)

Scope binding: CPython **3.14.0** on Linux, `tarfile.extract`/`extractall` on untrusted tar archives. Released `tarfile.py` bytes govern; PEP/prose are secondary. Frozen 2026-10-07 bytes verified (all 8 SHA-256 match manifest; see Sources).

Policy: extract with explicit **`filter='data'`**, default **`errorlevel=1`**, into a **fresh empty directory**; on `FilterError` abort and wipe the destination; layer sandbox-owned name/count/size caps plus OS resource limits on top. Never leave `filter` implicit in portable code; never treat the pre-filter warning as describing filtered 3.14 paths.

## Findings (7)

1. Old concern, lineage, 3.14.0 default. Pre-filter `extractall` honored archive metadata as-is; docs warned against untrusted extraction without inspection, but the check was unspecified and routinely skipped/wrong (PEP 706 Motivation cites e.g. CVE-2007-4559). PEP 706 (Final, 3.12) added keyword-only `filter`, named filters `fully_trusted`/`tar`/`data`, `TarFile.extraction_filter`, `FilterError` subclasses, `TarInfo.replace`. Lineage: issue #102950 "Implement PEP 706" → PR #102953 merged 2023-04-24 (`af530469…da414`) → transition 3.12–3.13 (omitted filter warned `DeprecationWarning`, used `fully_trusted`) → issue #121999 "Fully implement PEP 706: change default to 'data'" closed 2024-07-26. Released default in `tarnew.py:2370-2374` (`_get_filter_function` returns `data_filter` when arg and attribute are `None`, no warning) vs `tarold.py:2217-2226` (3.12.3 warns + returns `fully_trusted_filter`). Confirmed by `tardocnew.rst:650` ("will use `data` by default"), `:742-754` `test_extractall_default_filter` (mocks assert `data_filter` called, others not).

2. Omitted vs explicit filter; errorlevel binding. Omitted (`filter=None`, `extraction_filter=None`) = `data` on 3.14.0 but `fully_trusted`+warning on 3.12.3: portable code must pass `filter` explicitly. Explicit string resolves via `_NAMED_FILTERS` (`tarnew.py:864-869`); unknown → `ValueError`; callable used directly; `extraction_filter` accepts only `None`/callable, string → `TypeError` (`tarnew.py:2375-2386`). `FilterError` (carries `tarinfo`) is fatal: `errorlevel=1` (default, `tarnew.py:1710`) raises/aborts; `0` logs at debug and skips the member; `2` also raises non-fatal `ExtractError` (`_handle_fatal_error`/`_handle_nonfatal_error`, `tarnew.py:2531-2548`). 3.14.0 also treats filter-raised `UnicodeEncodeError` as fatal. Custom filters: `FilterError` = fatal, `ExtractError` = non-fatal. Any abort can leave **partial extraction**; caller must clean up.

3. File/link/path domains; destination assumptions. `tar` domain (all members): strip leading `/`+`os.sep`, refuse surviving absolute names (`AbsolutePathError`, incl. `C:/` forms), refuse realpath-after-join escapes (`OutsideDestinationError`, symlink-following), mask mode `& 0o755`. `data` adds: refuse absolute and outside-destination links for **both** symlinks and hardlinks (`AbsoluteLinkError`, `LinkOutsideDestinationError`; 3.14.0 `normpath` on `linkname`); refuse special files (`SpecialFileError`; only reg/hardlink/dir/symlink pass); reg/hardlink modes forced `u+rw`, `g/o-x` dropped when `u-x`; dir/symlink mode→`None` (skip chmod); `uid/gid/uname/gname`→`None` (skip chown). Containment: `realpath(dest, ALLOW_MISSING)` + `commonpath`; symlink targets resolve against `dest/dirname(name)`, hardlinks against `dest/linkname`; filter runs **just before each member** against live disk, and 3.14.0 re-applies it at directory-attribute fixup. Entry-point defaults differ (`extractall(path=".")` vs `extract(member, path="")`). Condition: extract into a new empty dir so pre-existing links cannot redirect the check.

4. Residual limits (security + resource exhaustion). `data` is **not** a license to skip inspection: 3.14 docs retain the warning that predefined filters do not prevent denial-of-service. Unbounded in-filter: member count, total bytes, single-file size, name/symlink length; repeated members overwrite (later wins); races with concurrent writers; case-insensitive shadowing; control chars/confusables/foreign separators; executable extensions, extensionless and Windows device names; inside-destination symlinks still permitted. Complements required: fresh `mkdtemp` dest, external disk/memory/CPU limits, allow-listed names/extensions, caps on count/total/individual size, abort-and-wipe on any `FilterError`.

5. No projection of the old warning. The CVE/pre-filter warning describes **unfiltered extraction** (`fully_trusted`, pre-3.12 behavior, `--filter`-less CLI) through **write paths** `extract`/`extractall` (and tarball `shutil.unpack_archive`). It does not describe: `data`/`tar`-filtered 3.14 extraction; read-only `extractfile` (no `filter` param; returns file object for reg/link, else `None`; `tarnew.py:2549+`), `getmember(s)`, `list`, `is_tarfile`; `TarFile.add`'s separate `filter`; zip handling (`zipfile` gained no filter here; passing `filter` for zip fails); backports (default `fully_trusted` **without** the warning). 3.14-only `LinkFallbackError` (link→copy fallback rejected via `makelink_with_filter`) is likewise outside the old vocabulary.

6. Conditional compatibility policy (fail-closed). Pin sandbox to 3.14.0 behavior: `extractall(filter='data')` (or `filter=tarfile.data_filter`), `errorlevel=1`; catch `FilterError`/`OSError`, discard dest on failure. Portable code: feature-detect `hasattr(tarfile,'data_filter')`, never version-compare (backports exist); absent → fail closed, or warn-and-continue only on explicit caller opt-in to `fully_trusted`; never assign a string to `extraction_filter`. Implement caps/allow-lists by wrapping `data_filter` in a stateful custom filter, not by reimplementing containment. Never set global `TarFile.extraction_filter` from library code (top-level app/`site` only, wrapped in `staticmethod` per docs).

7. Regression checks — proposed, version-discriminating (not executed). Per-release fixtures asserting: omitted filter → `data` on 3.14 / warns+`fully_trusted` on 3.12.3; `..`-escape, absolute path, absolute/outside symlink, outside hardlink, fifo/device refused under `data` but (isolated) honored under explicit `fully_trusted`; `tar` allows inside-links yet blocks escapes; mode/owner sanitization values; 3.14 `linkname` normpath; unknown-name `ValueError`; string-`extraction_filter` `TypeError`; `errorlevel=0` skip-vs-`1` abort; pre-created-symlink dest case; CLI `--filter` passthrough; tarball `shutil.unpack_archive` default. Each records the release under test and fails closed when `data_filter` is absent.

Conditions / uncertainty / negative leads. Conditions: Linux 3.14.0 bytes as hashed; dest exists and attacker-inert at start; single-threaded extraction; no concurrent mutation. Uncertainty: issue/PR JSON = bodies/meta only (no comment threads); 3.14 `shutil` companion diff not in corpus (referenced by #121999 checklist only); redistributors may alter defaults (PEP 706 permits). Negative leads: builtin filters never return `None` (skip is custom-only); no `errorlevel` semantic change 3.12.3→3.14.0 beyond added `UnicodeEncodeError` fatal path and dir-fixup refilter; no evidence `extractfile` writes to disk. Opportunity (optional): `StatefulFilter` context manager (count/bytes/name rules around `data_filter`) per docs example.
