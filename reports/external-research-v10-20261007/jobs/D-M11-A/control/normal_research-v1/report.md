# D-M11-A: tar extraction filter/error/compat policy for a 3.14.0 Linux ingest sandbox

Scope: CPython **3.14.0**, Linux, untrusted tar archives via `tarfile.extract` / `extractall`. Released implementation files govern; PEP/prose are secondary. All hashes below verified against the frozen manifest on 2026-10-07.

Recommendation: extract with an **explicit `filter='data'`**, default `errorlevel=1`, into a **fresh empty directory**, abort-and-clean-up on `FilterError`, and layer sandbox-owned resource/name checks on top. Do not rely on the omitted-filter default for cross-version safety, and do not treat the pre-filter warning as describing filtered 3.14 paths.

## Findings (7)

1. Old concern, lineage, and the 3.14.0 default. The pre-filter concern is that `extractall` honored archive metadata as-is; docs warned never to extract untrusted archives without inspection, but the check was unspecified and often skipped or wrong, yielding issues such as CVE-2007-4559 (PEP 706 Motivation/Security Implications). PEP 706 (Final, Python-Version 3.12) added keyword-only `filter` to `extract`/`extractall`, named filters `fully_trusted`/`tar`/`data`, `TarFile.extraction_filter`, `FilterError` subclasses, and `TarInfo.replace`. Tracking issue python/cpython#102950 → PR #102953 (merged 2023-04-24, merge SHA `af53046…da414`). Transition: 3.12–3.13 omitted filter warned `DeprecationWarning` and used `fully_trusted`; issue #121999 (closed 2024-07-26) changed 3.14 to `data`, removed the warning, updated docs/tests/shutil. In 3.14.0 `tarnew.py:_get_filter_function` returns `data_filter` when both argument and attribute are `None`; 3.12.3 `tarold.py` warns and returns `fully_trusted_filter`. Doc `tardocnew.rst` (`filter` versionchanged 3.12/3.14, Extraction filters) and `tartest.py:test_extractall_default_filter` (mocks assert `data_filter` called, others not) confirm the released default.

2. Omitted vs explicit filter, and errorlevel binding. Omitted (`filter=None`, `extraction_filter=None`) means `data` on 3.14.0 but `fully_trusted`+warning on 3.12.3: never leave it implicit in portable code. Explicit string resolves via `_NAMED_FILTERS`; unknown names raise `ValueError`; callables are used directly; `extraction_filter` accepts only `None`/callable and raises `TypeError` for strings. `FilterError` (with `tarinfo` member) is **fatal**: with `errorlevel=1` (default) it aborts extraction, with `0` it is logged (at `debug>0`) and the member skipped, with `2` non-fatal `ExtractError` is also raised (`_handle_fatal_error`, `_handle_nonfatal_error`, `_get_extract_tarinfo`, doc `TarFile.errorlevel`/Filter errors). 3.14.0 also treats `UnicodeEncodeError` from the filter as fatal. Custom filters should raise `FilterError` for fatal and `ExtractError` for non-fatal refusals. Any abort may leave a **partial extraction**; cleanup is the caller's duty.

3. File/link/path domains and destination assumptions. `tar` domain (all members): strip leading `/`+`os.sep`, refuse surviving absolute names (`AbsolutePathError`, e.g. `C:/foo`), refuse members whose realpath-after-join escapes the destination (`OutsideDestinationError`, symlink-following), mask mode with `& 0o755`. `data` adds: refuse absolute-link and outside-destination links for **both** symlinks and hardlinks (`AbsoluteLinkError`, `LinkOutsideDestinationError`), with 3.14.0 `normpath` normalization of `linkname`; refuse special files (`SpecialFileError`: only reg/hardlink/dir/symlink pass); reg/hardlink modes forced `u+rw` with `g/o-x` dropped when `u-x`; dir/symlink mode→`None` (skip chmod); `uid/gid/uname/gname`→`None` (skip chown). Destination is `realpath(dest, ALLOW_MISSING)` + `commonpath` containment; symlink targets resolve against `dest/dirname(name)`, hardlinks against `dest/linkname`; the filter runs **just before each member** against live disk state, and 3.14.0 re-applies it at directory-attribute fixup. Defaults differ by entry point: `extractall(path=".")` vs `extract(member, path="")`. Sandbox condition: extract into a new empty dir so pre-existing links cannot redirect the containment check.

4. Residual limits: security and resource exhaustion. Even `filter='data'` is explicitly **not** a license to skip inspection: predefined filters do not prevent denial-of-service, and the warning persists in 3.14 docs. Unbounded in-filter: file count, total bytes, single-file size, filename/symlink length; repeated members overwrite (later wins); live-directory races during extraction; case-insensitive shadowing; control characters/confusables/foreign separators; executable extensions and extensionless/Windows device names; symlinks still permitted when inside-destination (disallow them by policy if unneeded). Required complements: fresh `mkdtemp` destination, external OS-level disk/memory/CPU limits, allow-listed names/extensions, caps on count/total/individual size, and abort-and-wipe on any `FilterError`.

5. Do not project the old warning onto every current path. The CVE/pre-filter warning describes **unfiltered extraction** (`fully_trusted`, pre-3.12 behavior, old `--filter`-less CLI) through the **write paths** `extract`/`extractall` (and `shutil.unpack_archive` for tarballs). It does not describe: `data`/`tar`-filtered 3.14 extraction; read-only paths `extractfile` (no `filter` parameter; returns a file object for reg/link, `None` otherwise), `getmember(s)`, `list`, `is_tarfile`; `TarFile.add`'s separate `filter`; zip handling (`zipfile` gained no filter in this PEP; passing `filter` for zip fails); or backports (which default to `fully_trusted` **without** the deprecation warning). The 3.14-only `LinkFallbackError` (link→file-copy fallback rejected by the filter via `makelink_with_filter`) is also outside the old warning's vocabulary.

6. Compatibility policy (conditional, fail-closed). Pin the sandbox to 3.14.0 behavior by passing `filter='data'` explicitly and keeping `errorlevel=1`; catch `FilterError`/`OSError`, discard the destination on failure. For portable code, feature-detect with `hasattr(tarfile, 'data_filter')`, never version-compare (backports exist): fail closed with `extractall(filter=tarfile.data_filter)`; warn-and-continue only when the caller explicitly accepts `fully_trusted`; never assign a string to `extraction_filter`. Wrap `data_filter` in a custom stateful filter for caps/allow-lists rather than reimplementing containment. Do not set a global `TarFile.extraction_filter` from library code (top-level app/`site` only, wrapped in `staticmethod`).

7. Regression checks (proposed, discriminating by version). Proposed only — see Execution note. Per-release fixtures asserting: omitted filter resolves to `data` on 3.14 / warns+`fully_trusted` on 3.12.3; `..`-escape, absolute path, absolute symlink, outside symlink, outside hardlink, and fifo/device members refused under `data` but (fixture-isolated) honored under explicit `fully_trusted`; `tar` allows inside-links but still blocks escapes; mode/owner sanitization values; `linkname` normpath on 3.14; `ValueError` on unknown names; `TypeError` on string `extraction_filter`; `errorlevel=0` skips-and-continues vs `1` aborts; destination pre-created-symlink case; CLI `--filter` passthrough; `shutil.unpack_archive` tar default. Each check records the release under test and fails closed when `data_filter` is absent.

Conditions/uncertainty/negative leads. Conditions: Linux 3.14.0 `tarfile.py`/`tarfile.rst` bytes as hashed; destination exists and is attacker-inert at start; single-threaded extraction; no concurrent mutation. Uncertainty: issue/PR JSON captures carry bodies only (no comment threads); `shutil` 3.14 companion diff was not in the frozen corpus (only referenced by #121999 checklist); redistributor patches may alter defaults (PEP 706 allows it). Negative leads: no `None`-return from builtin filters (skip is custom-filter-only); no `errorlevel` change between 3.12.3 and 3.14.0 semantics beyond the added `UnicodeEncodeError` fatal path and directory-fixup refilter; no evidence that `extractfile` writes to disk. Optional opportunity: a small `StatefulFilter` context manager (count/bytes/name rules around `data_filter`) per the docs example.
