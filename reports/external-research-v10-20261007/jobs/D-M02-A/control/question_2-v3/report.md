# Q2 — When request variation blocks reuse

## Recommendation and scope

For this single-user GET reader, keep each stored response’s target URI, method, original request values for its `Vary` fields, current response directives, and validators together. Reuse only after the RFC 9111 checks below. A changed `Accept-Language` blocks unvalidated reuse when that stored response names it in `Vary`; a changed request field not named there does not automatically change the HTTP cache key. Do not add `Authorization` as a `Vary` field by default. If the product can switch principals while retaining one local cache, isolate or purge entries on principal change as an application security measure; HTTP’s private-cache model presumes one user.

## Dispositions

**Accepted — ordinary reuse and stale constraints (limited Q1 cross-condition).** URI and method must match; the stored response’s selecting request fields must match; unvalidated reuse is barred by response `no-cache`; and the response must be fresh, permitted stale, or successfully validated. Stale service is also barred by `must-revalidate`, applicable `s-maxage`/`proxy-revalidate`, or `no-cache`, and otherwise requires disconnection or explicit client/origin permission. Thus a Vary mismatch requires origin validation before reuse; it is not permission to serve the mismatching variant directly. [RFC 9111 §§4, 4.1, 4.2.4, 5.2.2.]

**Accepted — `Vary` determines request-field matching.** `Vary: Accept-Language` means compare that field with the value on the request that stored this response. Matching may normalize only transformations allowed by syntax or known to preserve field semantics; absent matches only absent. `Vary: *` never matches by field comparison and therefore cannot authorize an unvalidated hit. RFC 9110 says an origin should send `Vary` when it wants selective reuse, but may elide it when the performance cost outweighs the content-selection distinction. Therefore, if an origin actually varies language but omits `Vary`, this client cannot infer that from HTTP metadata. Its behavior is unresolved without an origin contract or endpoint observation. [RFC 9111 §4.1; RFC 9110 §12.5.5.]

**Amended — “every Accept-Language change must miss.”** The normative condition is narrower: a changed language value prevents unvalidated reuse only when the stored response’s `Vary` selects `Accept-Language` (or another rule requires validation). If the field is absent from `Vary`, HTTP does not expand the key for it. A cache may keep multiple responses; if several match, RFC 9111 gives preference-ranking guidance and otherwise chooses the most recent. [RFC 9111 §4.1.]

**Amended — Authorization and cache scope.** A private cache may store responses to authenticated requests subject to the ordinary storage, key, freshness, and reuse rules. The shared-cache prohibition is different: a shared cache must not use a response to a request containing `Authorization` unless response `must-revalidate`, `public`, or `s-maxage` permits shared storage/reuse and the cache obeys that directive. `private` alone does not grant that permission. RFC 9110 says `Authorization` need not be listed in `Vary` because reuse for a different user is prohibited by Authorization’s cache rules; that does not create a principal-specific cache key for an app that departs from the single-user premise. [RFC 9111 §3.5; RFC 9110 §§11.6.2, 12.5.5.]

**Rejected — treating `no-cache`, `no-store`, and `private` as synonyms.** Request `no-cache` is an advisory preference for successful validation before using a stored response; request directives need not be implemented. Response `no-cache` is stronger: do not satisfy another request without successful validation (qualified field names allow reuse only with those fields excluded or successfully revalidated; support is often limited). Request `no-store` bars storing that request and its response in private and shared caches, but does not purge an old entry; response `no-store` bars storing or reusing that response in either cache type (subject to `must-understand`’s specified exception). Unqualified response `private` bars shared storage but permits private storage; its field-qualified form restricts listed fields in a shared cache. None of these directives adds a request field to the cache key. [RFC 9111 §§5.2.1, 5.2.2.]

**Accepted — 304 updates do not erase the selection rules.** A cache first forms the 304 update candidates from responses that could have been chosen for the request under the existing URI/method/`Vary` rules, then applies the validator-matching rules. A 304 with a nonmatching strong validator cannot update those stored responses. For a validly identified response, fields supplied by the 304 update/replace stored fields under §3.2 (with that section’s exceptions, including `Content-Length` and fields on which the cache depends). Consequently, supplied `Vary` or `Cache-Control` can change the stored metadata; that updated `Vary` and directive set governs later reuse. A 304 is not a general license to ignore the old selection key or the new response restrictions. [RFC 9111 §§3.2, 4.3.4.]

**Unresolved — endpoint and account behavior.** The RFCs cannot establish whether this origin actually varies on `Accept-Language` when it omits `Vary`, whether its `Vary` list is complete, or whether this application can switch authenticated principals while retaining entries. Resolve the first two with an origin contract or controlled endpoint observation; resolve the third from product behavior. Until then, the local cache’s principal boundary is an application assumption, not a fact established by these sources.

## Proposed boundary fixtures (not executed)

1. Seed English and French responses with `Vary: Accept-Language`; test same value, different value, absent versus empty, repeated lines/allowed whitespace, and `Vary: *`. Assert only a match can hit without validation.
2. Change `Vary` on a validating 304. Assert candidate selection uses the old stored key and a matching validator; then assert later lookups obey the updated field set. Include 304 updates adding response `no-cache` or `no-store` and confirm later reuse follows the updated directive.
3. Send an authenticated request through private and shared-cache configurations. Test absent permission, each of `public`, `must-revalidate`, and `s-maxage`, then test local cache behavior when the app switches principals.
4. Exercise request/response `no-cache` and `no-store`, response `private` with and without field names, and stale entries with/without `must-revalidate` or explicit `max-stale` permission.
