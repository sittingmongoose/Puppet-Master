# D-M02-A / control / join-v3 — joined research report

## Recommendation

For the specified single-user GET reader, reuse a stored response only after checking storage eligibility, target URI and method, the stored response’s current directives, its Vary-selected request fields, and freshness or successful validation. Treat the cache as private only while entries remain confined to one user. RFC requirements do not establish this origin’s language-selection behavior or the application’s account-switch behavior.

## Findings

1. **Accepted — Q1 and Q2 selection conditions.** A response must be storable under RFC 9111 §3. A reusable response must match the target URI and a method that permits reuse. Without validation, each field named in the response’s Vary must match the corresponding field on the request that originally selected the stored response; only syntax-safe whitespace changes, same-name field combination, or normalization known to preserve semantics count as matches. Missing matches only missing. Vary: * never matches for unvalidated reuse. A mismatch requires a suitable origin response before that representation can satisfy the request. If Vary omits Accept-Language, HTTP does not let this client infer that the origin nevertheless selected by language. [RFC 9111 §§3, 4, 4.1](https://www.rfc-editor.org/rfc/rfc9111.html#section-4.1); [RFC 9110 §12.5.5](https://www.rfc-editor.org/rfc/rfc9110.html#section-12.5.5)

2. **Amended — freshness differs by cache type.** For a shared cache, freshness lifetime is s-maxage when present, otherwise max-age, otherwise Expires minus Date (using receipt time if Date is absent); for a private cache, use max-age, then Expires, then eligible heuristic freshness. Heuristics are unavailable when explicit expiry exists and require an eligible status or explicit cacheability. A response is fresh only when lifetime is strictly greater than current age. Current age accounts for Age/Date, response delay, and resident time. When a response cannot be reused, validate it if possible: a cache MUST send relevant stored entity tags, and SHOULD send Last-Modified for a non-range request validating one stored response that has that value. A 304 can freshen only eligible stored candidates under finding 5; a full response satisfies the request and may be stored subject to §3. [RFC 9111 §§4.2.1–4.2.3, 4.3](https://www.rfc-editor.org/rfc/rfc9111.html#section-4.2)

3. **Amended — stale and Authorization rules are conditional.** Stale reuse is not a general offline fallback: it is allowed only while disconnected or when the client/origin explicitly permits it, and is prohibited by response no-cache, must-revalidate, and applicable shared-cache s-maxage or proxy-revalidate. Request max-stale can express client permission, but request directives are advisory. Under §3.5, a shared cache cannot use a response to an Authorization request to satisfy a later request unless the response has public, must-revalidate, or s-maxage and the cache follows that directive. A private cache is not subject to that §3.5 prohibition, but ordinary storage, key, and reuse conditions still apply. HTTP says Authorization need not be listed in Vary to prevent reuse across users; it does not isolate an app cache that changes principals. [RFC 9111 §§3.5, 4.2.4, 5.2.1, 5.2.2.2, 5.2.2.9–10](https://www.rfc-editor.org/rfc/rfc9111.html#section-3.5); [RFC 9110 §§11.6.2, 12.5.5](https://www.rfc-editor.org/rfc/rfc9110.html#section-11.6.2)

4. **Rejected — no-cache, no-store, and private are interchangeable.** Request no-cache is an advisory preference for successful validation before using a stored response; unqualified response no-cache requires successful validation before reuse, even when fresh. Qualified response no-cache controls the named fields. Request no-store MUST NOT store that request or its response, but the RFC says it does not govern an already-stored response used to satisfy the request. Response no-store bars storing the immediate request/response and using that response again, subject to the defined must-understand exception. Unqualified response private bars shared storage while allowing a private cache to store subject to ordinary constraints; qualified private restricts named fields in a shared cache. None of these directives is a reliable privacy guarantee. [RFC 9111 §§5.2.1, 5.2.2.3–7](https://www.rfc-editor.org/rfc/rfc9111.html#section-5.2.2.4)

5. **Accepted — a 304 preserves both old selection and new policy.** The cache first forms the update set from stored responses that could have been chosen for the validated request, except that they need not already be fresh or otherwise serveable; validator matching then identifies what may be updated. Matching strong validators select corresponding candidates; if none match, the 304 MUST NOT update a stored response. Without strong validators, a matching weak validator selects the most recent match; without validators, update only when the set contains exactly one candidate and it also has no validator. Update supplied fields under §3.2 and its exceptions. When a 304 omits fields that a corresponding 200 would send, HTTP requires Vary and, for caching, Cache-Control and Expires when applicable. Changed Vary and directives govern later reuse; the 304 is not a license to bypass either the old candidate-selection rules or the new policy. [RFC 9111 §§3.2, 4.3.1, 4.3.4](https://www.rfc-editor.org/rfc/rfc9111.html#section-4.3.4); [RFC 9110 §15.4.5](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.4.5)

6. **Unresolved — origin and application facts.** The source corpus cannot establish whether this origin actually varies content by Accept-Language when Vary is absent, whether its Vary metadata is complete, or whether this app can switch users while retaining entries. An origin SHOULD send Vary when it wants selective reuse by language, but may elide it when the performance cost outweighs the content-selection distinction. Treat principal isolation as an application condition; do not infer origin behavior from the RFCs.

7. **Proposed checks and executed evidence.** Proposed, not run: (a) age just below, equal to, and above max-age, plus shared s-maxage precedence; (b) English/French Accept-Language, absent versus present fields, only permitted normalization, and Vary: *; (c) private/shared authenticated requests with no exception, public, must-revalidate, and s-maxage, alongside request-versus-response no-cache/no-store, qualified private, stale max-stale versus must-revalidate, and principal switching; (d) 304 candidate sets with matching/mismatching strong tags, weak tags, and no validator, changing Vary and Cache-Control, then checking subsequent lookup. Executed: SHA-256 for both frozen RFC text files matched sources.json; SHA-256 for both predecessor reports matched the authorized map. No endpoint request, implementation test, or proposed fixture was run.
