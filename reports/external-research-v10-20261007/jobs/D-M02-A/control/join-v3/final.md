# D-M02-A — Joined recommendation

For the single-user GET reader, reuse a stored response only after checking that it is storable, the target URI and method match, the response’s current directives allow reuse, its Vary-selected request fields match, and it is fresh or successfully validated. Treat the cache as private only while entries remain confined to one user.

1. **Accepted — Q1/Q2 selection.** Without validation, a stored response’s nominated Vary fields must match the values on the request that selected it. Only allowed whitespace changes, same-name field combination, and normalization known to preserve semantics count; absent matches only absent. Vary: * never matches for unvalidated reuse. A mismatch needs an origin response before that representation can satisfy the request. If Vary omits Accept-Language, HTTP does not reveal whether the origin nevertheless selected by language. [RFC 9111 §§3, 4, 4.1](https://www.rfc-editor.org/rfc/rfc9111.html#section-4.1); [RFC 9110 §12.5.5](https://www.rfc-editor.org/rfc/rfc9110.html#section-12.5.5)

2. **Amended — freshness, validation, and stale use.** Shared caches use s-maxage, then max-age, then Expires minus Date; private caches use max-age, then Expires, then eligible heuristic freshness. Use receipt time when Date is absent. Heuristics require no explicit expiry and an eligible status or explicit cacheability. Fresh means freshness lifetime is strictly greater than current age, which accounts for Age/Date, response delay, and resident time. Validate a non-serveable candidate when possible: send relevant stored entity tags, and SHOULD send Last-Modified for a non-range request validating one stored response that has it. Stale reuse is allowed only while disconnected or explicitly permitted by the client/origin, and is barred by response no-cache or must-revalidate and by applicable shared-cache s-maxage or proxy-revalidate. Request directives, including max-stale and no-cache, are advisory. [RFC 9111 §§4.2.1–4.2.4, 4.3, 5.2.1](https://www.rfc-editor.org/rfc/rfc9111.html#section-4.2)

3. **Amended — Authorization scope.** A shared cache cannot use a response to an Authorization request for a later request unless response public, must-revalidate, or s-maxage permits shared use and the cache follows that directive. A private cache is not subject to that shared-cache prohibition, though ordinary storage and reuse rules remain. Authorization need not be in Vary to prevent HTTP reuse across users; an app that can change principals must isolate or clear its own cache. [RFC 9111 §3.5](https://www.rfc-editor.org/rfc/rfc9111.html#section-3.5); [RFC 9110 §11.6.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-11.6.2)

4. **Rejected — conflating directives.** Request no-cache merely prefers successful validation; unqualified response no-cache requires it before reuse, even while fresh. Qualified response no-cache controls its listed fields. Request no-store MUST NOT store the request or response but does not govern an already-stored response used to answer it. Response no-store bars storing the immediate exchange and reusing that response, subject to the must-understand exception. Unqualified response private prevents shared storage but permits private storage subject to ordinary constraints; qualified private restricts named fields in shared storage. None is a reliable privacy guarantee. [RFC 9111 §§5.2.1, 5.2.2.3–7](https://www.rfc-editor.org/rfc/rfc9111.html#section-5.2.2.4)

5. **Accepted — conditions after 304.** First form the stored-response set that could have been chosen for the validated request under the existing URI, method, and Vary rules; then apply validator matching. Matching strong validators identify candidates; if none match, the 304 MUST NOT update a stored response. Without strong validators, a matching weak validator selects the most recent match; with no validator, update only if exactly one candidate exists and it also lacks a validator. Update fields under RFC 9111 §3.2. When a corresponding 200 would include them, RFC 9110 requires 304 to include Vary, Cache-Control, and Expires. Updated Vary and directives govern later reuse; they do not erase candidate-selection rules or authorize bypassing new restrictions. [RFC 9111 §§3.2, 4.3.4](https://www.rfc-editor.org/rfc/rfc9111.html#section-4.3.4); [RFC 9110 §15.4.5](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.4.5)

6. **Unresolved — actual origin and account behavior.** The RFCs cannot establish whether this origin varies by Accept-Language when Vary is absent, whether its Vary metadata is complete, or whether the app changes principals while retaining entries. An origin SHOULD send Vary when it wants selective reuse by language, but may elide it when performance costs outweigh the distinction. Resolve actual behavior with an origin contract or controlled endpoint observation; confirm principal-switch behavior from the application. These conditions are outside the supplied evidence.

7. **Proposed checks; none executed.** Test age just below/equal/above max-age and shared s-maxage precedence; English/French, absent/present, permitted normalization, and Vary: *; private/shared authenticated requests with each Authorization exception and request-versus-response no-cache/no-store, qualified private, and stale max-stale versus must-revalidate; and 304 strong/weak/no-validator candidate matching followed by changed Vary/Cache-Control and new lookups. These are proposals only. Executed checks were limited to SHA-256 verification: both supplied RFC text files matched sources.json and both predecessor reports matched the authorized hashes. No endpoint, implementation, or fixture test was run.
