# D-M02-A / control / question_2-v2 — bounded research report

## Recommendation

Treat reuse as a conjunction of independent gates: target URI and method eligibility, request-field matching under the stored response's current `Vary`, cache directives, and freshness or successful validation. A matching language preference never overrides no-store, no-cache, authorization, or stale rules. No origin implementation or policy was supplied, so the RFCs determine the protocol conditions but cannot establish whether this reader's origin actually varies its content by language or identity.

## Findings and obligation dispositions

1. **Freshness, validation, stale reuse — accepted with conditions.** A response is fresh only while current age is below its freshness lifetime. Use shared `s-maxage` first for shared caches, otherwise `max-age`, then `Expires`; heuristic freshness is possible only for eligible responses without explicit freshness. A cache may validate a stored response it cannot serve, commonly with validators. Stale service is barred by response `no-cache`, `must-revalidate`, or applicable shared `s-maxage` / `proxy-revalidate`; otherwise it is allowed only when disconnected or expressly permitted by the client, origin, extension, or applicable out-of-band contract. A request `no-cache` expresses a client preference for validation, not the response directive's MUST. [RFC 9111 §§4, 4.2–4.3](https://www.rfc-editor.org/rfc/rfc9111.txt)

2. **Vary and cache-key matching — accepted, with the language boundary made explicit.** A stored response naming `Vary: Accept-Language` cannot be reused without successful validation unless the incoming field matches the original request field after only permitted syntax cleanup or normalization known to preserve semantics. Absence matches only absence; do not infer that `en`, `en-GB`, or a missing field are interchangeable. `Vary: *` never matches for unvalidated reuse. If no stored response matches, forward the request. The stored response must also match the target URI and be usable for the method. The origin SHOULD send Vary when it wants selective reuse of language-negotiated responses; RFC 9110 notes it can elide Vary when it accepts the caching tradeoff, so an omitted Vary cannot reveal an origin's hidden language dependency. [RFC 9111 §§4, 4.1](https://www.rfc-editor.org/rfc/rfc9111.txt); [RFC 9110 §12.5.5](https://www.rfc-editor.org/rfc/rfc9110.txt)

3. **Authorization — shared and private rules differ.** A shared cache cannot store/use an Authorization response for later requests unless an applicable response directive explicitly permits shared caching; RFC 9111 identifies `must-revalidate`, `public`, and `s-maxage`, subject to their requirements. `private` does not grant shared use and its unqualified form prohibits shared storage. A private cache may store an authenticated response subject to ordinary constraints. Authorization need not be named in Vary because HTTP already restricts cross-user reuse in shared caches. The RFCs do not specify this single-user reader's account-switching or local cache-partitioning design; if one private cache can serve multiple principals, partitioning by principal is a separate safety recommendation, not an inferred RFC mandate. [RFC 9111 §§3, 3.5, 5.2.2.2, 5.2.2.7, 5.2.2.9–10](https://www.rfc-editor.org/rfc/rfc9111.txt); [RFC 9110 §11.6.2](https://www.rfc-editor.org/rfc/rfc9110.txt)

4. **no-cache, no-store, private — amended as distinct controls.** Request `no-cache` asks for validation; response `no-cache` without a field list MUST be validated successfully before reuse, even if otherwise fresh. Qualified response `no-cache` restricts listed fields, though implementations often treat it as unqualified. Request `no-store` prohibits storing that request and its response in both cache types, but does not clear an already stored response if the request is served from cache. Response `no-store` prohibits storing either message and using that response for another request. `private` controls shared versus private storage; it is not a confidentiality guarantee. [RFC 9111 §§5.2.1.4–5, 5.2.2.4–7](https://www.rfc-editor.org/rfc/rfc9111.txt)

5. **304 cross-question conditions — accepted with the original gates preserved.** A 304 identifies stored candidates that could have been chosen for the request (the ordinary eligibility requirements except freshness/validation), then validator rules select which entries can be updated. It updates supplied stored header fields, replacing existing values. RFC 9110 requires a 304 to include Vary, Cache-Control, and Expires when they would have appeared on the corresponding 200. Apply any supplied new Vary/directive values to the stored entry; a successful validation permits the current reuse, but does not waive current Authorization rules or the Vary check for later requests. Recompute freshness from the refreshed metadata. A full response instead replaces the candidate for the request. [RFC 9111 §§3.2, 4.3.3–4](https://www.rfc-editor.org/rfc/rfc9111.txt); [RFC 9110 §15.4.5](https://www.rfc-editor.org/rfc/rfc9110.txt)

6. **Claim dispositions and discriminating checks.** Accepted: reuse requires all applicable gates above. Amended: “same URI and fresh is enough” must also account for method, Vary, directives, and authorization. Rejected: `private` or `no-store` alone guarantees privacy; the RFC explicitly says no-store is not a sufficient privacy mechanism and private only limits storage location. Unresolved: actual origin variation, cache directives, validators, and account behavior are absent from the corpus.

   **Proposed, not executed:** (a) warm `Vary: Accept-Language` entries for `en` and `fr`; check exact match, missing-versus-present, and a semantically equivalent normalized field, and ensure the other language forwards/validates; (b) ensure `Vary: *` never serves without validation; (c) try an Authorization response through private and shared caches with no grant, then with `public`, `must-revalidate`, `s-maxage`, and `private`; (d) matrix request versus response `no-cache`, `no-store`, and `private`, including stale and disconnected cases; (e) validate an entry with 304 carrying changed Cache-Control/Vary and confirm updated fields govern future hits, while a full 200 replaces it. Add an account-switch fixture if the reader supports multiple principals.
