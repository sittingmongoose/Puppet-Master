# D-M02-A / control / question_1-v3 — Q1 recommendation

**Scope.** The reader stores GET responses. Treat its cache as private only while it is confined to one user; apply the shared-cache rules to any intermediary. A stored response is a candidate only for the same target URI and a method that permits reuse. The request that populated it, its response metadata, and the current request are needed to decide more. ([RFC 9111 §§2, 4](https://www.rfc-editor.org/rfc/rfc9111.html#section-4))

## Findings

1. **Q1 — fresh reuse, validation, stale.** Check the stored response's own policy and age after selecting a candidate under findings 2–3. For a shared cache, freshness lifetime is `s-maxage`, then `max-age`, then `Expires − Date` (or receipt time if Date is absent); otherwise a heuristic is permitted only when no explicit expiration exists and the response is eligible for heuristic freshness. Reuse without validation only while `freshness_lifetime > current_age`; calculate age using Age/Date, response delay, and resident time. A response with response `no-cache` always needs successful validation, even while fresh. When a candidate cannot be served, validate it if possible: send stored entity tags; Last-Modified is recommended in the specified single-response case. A 304 can freshen the stored representation under finding 5; a full response replaces it. ([RFC 9111 §§3, 4, 4.2–4.3.3](https://www.rfc-editor.org/rfc/rfc9111.html#section-4.2))

   Stale is not a general offline fallback. A cache may serve stale only when disconnected or when client/origin permission explicitly allows it, and never against response `no-cache`, `must-revalidate`, or applicable shared-cache `s-maxage`/`proxy-revalidate`. Request `max-stale` can permit it if the cache honors that advisory request directive; `must-revalidate` still blocks it. Request `max-age`, `min-fresh`, and `no-cache` are also preferences, not mandatory cache behavior. ([RFC 9111 §§4.2.4, 5.2.1, 5.2.2.2, 5.2.2.8, 5.2.2.10](https://www.rfc-editor.org/rfc/rfc9111.html#section-4.2.4))

2. **Q2 — Vary and matching.** The minimum key is method plus target URI. Each response's `Vary` nominates additional request fields; if it says `Vary: Accept-Language`, reuse without revalidation requires the current Accept-Language to match the value on the request that populated that representation. Matching permits only syntax-safe whitespace changes, combining same-name field lines, and normalization known to preserve that field's semantics. An absent field matches only another absent field. `Vary: *` never matches for unvalidated reuse. A miss must go to the origin (possibly with validators). The origin SHOULD send Vary when it wants selective reuse by language, but may omit it; absent Vary therefore leaves actual language-selection behavior unknown. Each 200 response can carry a different Vary policy. ([RFC 9111 §4.1](https://www.rfc-editor.org/rfc/rfc9111.html#section-4.1); [RFC 9110 §12.5.5](https://www.rfc-editor.org/rfc/rfc9110.html#section-12.5.5))

3. **Authorization — private/shared distinction.** In this single-user reader, a private cache may store an authenticated GET when ordinary storage and reuse rules allow; credentials have user-agent scope and the effect of `private` for that request. Keep the cache isolated if the app can change users. A shared cache MUST NOT store/reuse an Authorization response unless its Cache-Control explicitly allows shared caching via `public`, `must-revalidate`, or `s-maxage`, and the cache follows that directive. This exception does not erase Vary, freshness, validation, or other storage constraints: `public` explicitly marks a response cacheable; `s-maxage` supplies shared freshness and requires revalidation when stale; `must-revalidate` requires revalidation when stale but supplies no freshness lifetime by itself. RFC 9110 says Authorization need not be named in Vary because its field definition already restricts reuse across users; Vary is not a substitute for the shared-cache exception. ([RFC 9111 §§3, 3.5, 5.2.2.2, 5.2.2.9–10](https://www.rfc-editor.org/rfc/rfc9111.html#section-3.5); [RFC 9110 §§11.6.2, 12.5.5](https://www.rfc-editor.org/rfc/rfc9110.html#section-11.6.2))

4. **Do not conflate directives.** Request `no-cache` asks for successful validation; response `no-cache` mandates it (qualified response form can restrict named fields). Request `no-store` forbids storing that request and its response; response `no-store` forbids storing the immediate request/response and reusing that response. A request `no-store` does not govern an already-stored response used to satisfy it. Neither form is a reliable privacy guarantee. Response `private` bars a shared cache from storing the whole response; a private cache may store it, including when it would not otherwise be heuristically cacheable. Qualified `private="Field"` limits those fields and can allow the shared cache to store the remainder, subject to other rules. ([RFC 9111 §§5.2.1.4–5, 5.2.2.4–7](https://www.rfc-editor.org/rfc/rfc9111.html#section-5.2.2.4))

5. **304 — carry conditions forward.** A 304 is metadata for a previously stored body, not an arbitrary same-URI hit. First consider only responses that could have been chosen for this request (including URI, method, and the old Vary conditions); then apply validator matching. A 304 with strong validators updates candidates with a matching strong validator, and updates none if there is no match. Without strong validators, a matching weak validator selects the most recent match; with no validator, update only when there is exactly one candidate and it also has no validator. Update the identified response's fields from the 304, replacing fields provided and preserving other stored fields under the update rules. RFC 9110 requires a 304 to include Vary, Cache-Control, and Expires when they would be sent on the corresponding 200. Apply changed Vary/Cache-Control before future selection: re-check the new key and directives; `Vary: *` prevents later unvalidated reuse, while new `no-cache` or `no-store` must not be bypassed. If changed Vary cannot be safely associated with the validated request's field values, decline reuse until a full response can be safely keyed; the RFC specifies matching/update rules but not index-migration mechanics. ([RFC 9111 §§3.2, 4.3.4](https://www.rfc-editor.org/rfc/rfc9111.html#section-4.3.4); [RFC 9110 §15.4.5](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.4.5))

6. **Dispositions and proposed boundary fixtures.** **Accepted:** fresh, key-matching responses may satisfy GET without origin contact. **Amended:** stale reuse is conditional and subordinate to explicit prohibitions; a 304 refreshes only validator-identified candidates. **Rejected:** `no-cache`, `no-store`, and `private` are synonyms, or Vary alone protects Authorization. **Unresolved:** the actual origin's language-selection behavior, emitted Cache-Control/Vary/validators, and intended sharing policy are not specified by the brief.

   Proposed (not executed) fixtures: (a) age just below/equal/above max-age, and shared s-maxage overriding max-age; (b) Accept-Language match, mismatch, absent-versus-present, legal normalization, and `Vary: *`; (c) two language variants with changed Vary and a 304 changing Vary/Cache-Control, checking future lookup follows updated metadata; (d) authenticated responses to private versus shared caches, testing no exception, `public`, `must-revalidate`, and `s-maxage`; (e) request versus response no-cache/no-store and qualified private; (f) stale with max-stale versus must-revalidate/disconnection; (g) 304 with matching/mismatching strong tag, weak tag, and no validator. RFC 9111 §4.2's strict `lifetime > age` formula makes equality a useful boundary case; test it explicitly against the deployed cache.
