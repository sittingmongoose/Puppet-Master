# D-M02-A / control / question_1-v2 — Q1 disposition

## Governing rule

A private cache may reuse a stored response only for the same target URI and an allowed method, when all selecting request fields named by the stored response’s Vary match the original request (including absence matching only absence), the response is not barred by no-cache unless successfully validated, and it is fresh, permitted stale, or successfully validated. When used without validation, emit Age from current_age. [RFC 9111 §§4, 4.1, 4.2.3](https://www.rfc-editor.org/rfc/rfc9111.html#section-4)

Freshness lifetime uses the first applicable rule: shared-cache s-maxage; max-age; Expires minus Date (or receipt time if Date is absent); otherwise eligible heuristic freshness. Current age must account for Age, Date, response delay, and resident time. Heuristics are allowed only without explicit expiration and for heuristically cacheable or explicitly cacheable responses. Conflicting directives use the most restrictive; invalid freshness should be treated stale. [RFC 9111 §§4.2.1–4.2.3](https://www.rfc-editor.org/rfc/rfc9111.html#section-4.2)

If a response is stale or otherwise not reusable, validate it when possible: use If-None-Match with an available entity tag; it takes precedence over If-Modified-Since. A 304 permits updating and reusing a matching stored response; a full response replaces it for the request. Stale service is allowed only while disconnected or when explicitly permitted by the client/origin (for example max-stale or a supported stale extension/out-of-band contract), and only absent a prohibition. Unqualified response no-cache and must-revalidate prohibit stale reuse; must-revalidate still bars stale use during disconnection. The qualified no-cache form restricts named fields and can permit reuse if those fields are excluded or successfully updated; implementations often handle it as unqualified. [RFC 9111 §§4.2.4, 4.3.1–4.3.4](https://www.rfc-editor.org/rfc/rfc9111.html#section-4.3)

## Shared conditions carried into Q1

- **Authorization:** this is a private cache, so Authorization alone does not prohibit storage; normal cacheability and directive rules still apply. A shared cache must not store/use a response to an Authorization request unless Cache-Control explicitly allows shared storage; RFC 9111 names must-revalidate, public, and s-maxage, subject to each directive’s conditions. A local implementation that can switch accounts should partition by account/credential context; that is a product safeguard, not an HTTP cache-key requirement. [RFC 9111 §§3, 3.5](https://www.rfc-editor.org/rfc/rfc9111.html#section-3.5)
- **Directive distinctions:** request no-cache means the client prefers successful validation before a stored response is used; unqualified response no-cache requires successful validation before reuse, while qualified no-cache is limited to its named fields. Request no-store forbids storing that request or its response, but if it is satisfied from cache it does not itself invalidate the already stored response. Response no-store forbids storing and using the response. Unqualified private bars shared storage but permits private-cache storage; qualified private allows shared storage only after removing its named fields, subject to other constraints. Thus no-cache, no-store, and private are not interchangeable. [RFC 9111 §§5.2.1.4–5.2.1.5, 5.2.2.4–5.2.2.7](https://www.rfc-editor.org/rfc/rfc9111.html#section-5.2)
- **Accept-Language / Vary:** if a stored response says Vary: Accept-Language, reuse without revalidation requires a semantic match to the original request value; absent matches only absent. Vary: * never matches. Authorization need not be listed in Vary to prevent cross-user reuse under HTTP’s shared-cache rules. [RFC 9111 §4.1](https://www.rfc-editor.org/rfc/rfc9111.html#section-4.1); [RFC 9110 §12.5.5](https://www.rfc-editor.org/rfc/rfc9110.html#section-12.5.5)
- **After 304:** RFC 9110 requires a 304 to include Vary and applicable cache metadata (including Cache-Control/Expires) that a corresponding 200 would send. RFC 9111 selects eligible stored responses, matches validators, and updates their fields from the 304, replacing existing values subject to its stated exceptions. Recompute freshness and obey newly returned directives; a 304 does not waive Vary matching for future reuse. The RFC does not spell out a re-key algorithm when Vary itself changes on 304. Conservative implementation inference: retain selecting-request context, apply the updated Vary before later reuse, and do not serve another request from the entry if its updated match cannot be established. [RFC 9110 §15.4.5](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.4.5); [RFC 9111 §§3.2, 4.1, 4.3.4](https://www.rfc-editor.org/rfc/rfc9111.html#section-4.3.4)
