# D-M02-A — bounded recommendation

**Disposition ledger.** **Accepted:** reuse depends on ordinary cache eligibility, request/response selection, and the freshness/validation gate below. **Amended:** “fresh means reusable” is incomplete; freshness cannot cure a URI, method, Vary, no-cache, or storage-rule failure. **Rejected:** Authorization does not need to be added to Vary. **Unresolved:** these RFCs cannot establish whether a particular origin emits complete Vary and cache metadata or what language it selects when they are absent.

1. **Q1 — eligibility and freshness.** For a stored GET, first require matching target URI, a method usable for this request, and all Vary selectors to match. A stored response with response no-cache needs successful validation. It must also be storable under RFC 9111 §3: among other conditions, no response no-store, and a cacheability basis such as explicit freshness, public/private as applicable, an allowed extension, or a heuristically cacheable status. Fresh means current_age is strictly less than freshness_lifetime (RFC 9111 §§3, 4, 4.2). A private cache uses max-age, then Expires minus Date, then eligible heuristic freshness; s-maxage overrides only for shared caches. Do not infer freshness from status alone where §4.2.2 disallows heuristics.

2. **Q1 — validation and stale.** If no eligible fresh entry can be used, validate a selectable stored entry, normally with its ETag in If-None-Match and, when appropriate, Last-Modified in If-Modified-Since (RFC 9111 §4.3.1; RFC 9110 §13). A 304 permits updating and reusing the stored representation; a full response must satisfy the current request and may be stored subject to cache constraints. Stale is not a normal fallback: it may be served only when disconnected or explicitly permitted by client/origin, and never against a prohibiting response directive. In particular, response no-cache and must-revalidate prohibit stale use; s-maxage and proxy-revalidate impose the shared-cache restriction. max-stale can permit stale if honored, but request directives are advisory (RFC 9111 §§4.2.4, 5.2.1, 5.2.2).

3. **Q2 — Vary and key matching.** The URI/method key is expanded per stored response’s Vary. For Vary: Accept-Language, reuse without validation requires the presented Accept-Language field to match the original request field under RFC 9111 §4.1’s limited whitespace, field-line combination, and specification-defined semantic-normalization rules. Absence matches only absence; do not substitute “same likely language” for a match. Vary: * never matches without validation. A mismatch means this entry cannot satisfy the request without successful revalidation; forward it for validation or obtain another response. RFC 9110 §12.5.5 says Vary identifies selection inputs and recommends it when language preference affected a cacheable representation, but permits omission when the origin accepts the caching tradeoff.

4. **Authorization — private versus shared.** “Private cache” means dedicated to one user; it is not the Cache-Control private directive (RFC 9111 §1). A private cache can store an authorized GET when the general storage/cacheability rules permit. A shared cache must not store or reuse a response to an Authorization request unless the response has an allowing directive: must-revalidate, public, or s-maxage, subject to that directive’s constraints (RFC 9111 §§3, 3.5). Keep authenticated entries within the single-user/account boundary. RFC 9110 §12.5.5 says Authorization need not be named in Vary because reuse for a different user is prohibited; Vary is not a substitute for enforcing that boundary.

5. **Directive distinctions.** Request no-cache asks that a stored response not be used without successful origin validation, but request directives are advisory; implement it for this reader’s refresh semantics. Response no-cache permits storage but requires successful validation before reuse; its qualified field-name form restricts those fields, though RFC 9111 notes support is uncommon. Request no-store forbids storing the request or its response in either cache; it does not erase an already-stored response if this request was satisfied from cache. Response no-store forbids storing the request/response and using that response for another request, in both private and shared caches. Unqualified response private bars shared storage while permitting a private cache to store even a response that otherwise would not be heuristically cacheable, subject to other constraints; private="fields" bars a shared cache from storing those fields but can permit the remainder. Neither private form means “confidential” or “never cache locally” (RFC 9111 §§5.2.1.4–5, 5.2.2.4–7).

6. **304 cross-question rule and checks.** A 304 does not replace the body with an empty representation. First restrict update candidates to responses that could have served the validation request under URI, method, and Vary rules; then select by validators (strong validator match first; weak-validator or no-validator cases as §4.3.4 specifies). Update the identified stored headers from the 304. RFC 9110 §15.4.5 requires Content-Location, Date, ETag, Vary, Cache-Control, and Expires when they would have appeared in the 200. Re-evaluate the updated entry’s Vary, freshness, and no-cache/no-store rules before later reuse: a changed Vary can change which requests match, while changed freshness directives can alter validation timing (RFC 9111 §§3.2, 4.3.4).
