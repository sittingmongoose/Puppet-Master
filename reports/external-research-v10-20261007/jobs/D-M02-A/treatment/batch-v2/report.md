# D-M02-A treatment - bounded cache recommendation

**Scope.** One private, single-user GET cache; requests can carry Authorization and Accept-Language. This is a normative reading of RFC 9111/9110, not an executed cache implementation. No draft claims were supplied for adjudication.

1. **Q1 - freshness and validation (accepted, with conditions).** Reuse only a stored response for the same target URI and an allowed method when its Vary selectors match, it is not barred by response no-cache, and it is fresh, permitted stale, or successfully validated. Fresh means freshness lifetime exceeds current age. Compute lifetime in order: shared-cache s-maxage, max-age, Expires minus Date (or receipt time when Date is absent), then a permitted heuristic only when there is no explicit expiration and the response is cacheable. Current age accounts for upstream Age, transit, and residence time. A stale/unusable entry normally triggers validation: send a stored entity tag in If-None-Match when available; a 304 can freshen an eligible stored response, while a full response replaces it. [RFC 9111 Sections 3, 4, 4.2-4.3.4](https://www.rfc-editor.org/rfc/rfc9111.txt)

2. **Q1 - stale reuse (amended).** Staleness alone is not permission to serve. RFC 9111 allows stale generation only when disconnected or explicitly permitted by the client, origin, extension, or an out-of-band contract. A response no-cache or must-revalidate blocks stale use; applicable shared-cache s-maxage and proxy-revalidate also block it. must-revalidate requires successful origin validation even while disconnected. Treat max-stale as a client allowance only where the cache implements that advisory request directive, and never as overriding a response prohibition. [RFC 9111 Sections 4.2.4, 5.2.1.2, 5.2.2.2, 5.2.2.8, 5.2.2.10](https://www.rfc-editor.org/rfc/rfc9111.txt)

3. **Q2 - Vary and key matching (accepted).** Match URI/method plus every request field named by the stored response's Vary. Accept-Language must participate when the origin selects content by language: en and fr variants cannot share an unvalidated hit. Matching permits only syntax-safe whitespace changes, combining same-name field lines, and normalization known to preserve semantics; an absent field matches only another absent field. Vary: * never matches. A mismatch prevents reuse without origin validation. If the origin omits Vary, the RFC key has no language selector; the cache cannot infer that the origin varied correctly. RFC 9110 says an origin should send Vary when it wants selective reuse, including language negotiation. [RFC 9111 Section 4.1](https://www.rfc-editor.org/rfc/rfc9111.txt); [RFC 9110 Section 12.5.5](https://www.rfc-editor.org/rfc/rfc9110.txt)

4. **Authorization - private/shared distinction (accepted; identity isolation retained as an application invariant).** Authorization does not itself bar a private cache from storing an otherwise storable response. A shared cache must not reuse a response to an Authorization request unless Cache-Control contains public, s-maxage, or must-revalidate, and it obeys that directive. In particular, stale reuse remains barred where required. RFC 9110 says Authorization need not be added to Vary because reuse for a different user is prohibited by Authorization semantics. For this single-user cache, keep entries scoped to the same authenticated principal; clear or partition them if the account changes. Do not treat Vary: Authorization as a substitute for that isolation. [RFC 9111 Sections 3, 3.5](https://www.rfc-editor.org/rfc/rfc9111.txt); [RFC 9110 Sections 11.6.2, 12.5.5](https://www.rfc-editor.org/rfc/rfc9110.txt)

5. **Cache-Control - directives are not interchangeable (rejected: "no-cache means no-store").** Request no-cache is an advisory preference for successful validation before reuse; caches need not implement request directives. Response no-cache is mandatory: do not reuse that response for another request without successful validation (qualified field-name form applies to those fields, though it is often treated as unqualified). Request no-store prohibits storing that request or its response, but does not erase an already stored response used to satisfy it. Response no-store prohibits storing the immediate request/response and using that response for another request. Unqualified private forbids shared storage and permits private storage subject to other rules; qualified private lets a shared cache omit named fields and possibly store the remainder. private controls storage scope; it does not ensure secrecy. [RFC 9111 Sections 5.2.1, 5.2.1.4-5.2.1.5, 5.2.2.4-5.2.2.7](https://www.rfc-editor.org/rfc/rfc9111.txt)

6. **304 cross-conditions and uncertainty (accepted update rule; conservative policy for underspecified edges).** A 304 updates only stored responses that could have been selected for that request, then filters by validators: matching strong validators take priority; weak validators select the most recent corresponding response; without a validator, update is allowed only for the sole eligible stored response that also lacks one. Apply 304 fields under the header-update rules. If freshness directives conflict, honor the most restrictive rule (for example, no-cache overrides max-age). Then re-run the complete reuse gate against the resulting Cache-Control, Vary, principal, age, and stale constraints. A 304 is not permission to broaden a language variant or bypass no-cache/no-store. The RFC does not give a bespoke migration rule for a 304 that changes Vary so the cache lacks a safe selector snapshot, nor explicit cleanup steps for an already stored body when 304 carries no-store. Proposed fail-closed policy: invalidate that entry and fetch a full response whenever its new scope cannot be proved safe; verify the no-store case against the intended cache behavior before release. [RFC 9111 Sections 3.2, 4, 4.3.1-4.3.4, 5.2.2.4-5.2.2.5](https://www.rfc-editor.org/rfc/rfc9111.txt)

**Same-author cross-condition pass.** Apply controls conjunctively: URI/method/Vary/principal match; no-store/no-cache and freshness/stale rules; shared Authorization permission; then 304 freshening by eligible variant and validator. A 304 bypasses no gate; recalculate with updated metadata. Ambiguous variant scope fails closed.

**Disposition summary.** Accepted: the RFC freshness, variant, Authorization, and 304 rules above. Amended: "fresh means reusable" requires all URI, method, selector, directive, and principal checks. Rejected: equating no-cache with no-store, assuming Authorization must be in Vary, or treating a successful 304 as a general reuse grant. Unresolved: whether the origin consistently varies by Accept-Language and how it changes Vary/Cache-Control across 304s; these are server behaviors, not inferable from the RFC alone.

**Discriminating checks proposed, not executed.** (a) Store en with Vary: Accept-Language; try fr, absent, and en, then repeat with Vary: *. (b) Compare private and shared caches for an Authorization response with no enabling directive, each of public/s-maxage/must-revalidate, and no-store; attempt stale shared reuse while disconnected. (c) Validate an en variant with 304s that change max-age, Vary, and no-store; verify the next fr request cannot inherit the en body and that no-store is handled fail-closed. **Executed witness:** SHA-256 verification of the two frozen source files only; no HTTP fixtures or cache code were executed.
