# I-METHOD-03 — revised MVP plan: transit transfer information kiosk

**Status:** Complete proposed replacement for inherited P1–P6 and O1–O6. This is a plan and evidence review, not an implementation, feed evaluation, test report, or performance result. It carries forward the supported discoveries and records the actual critic-v1 objections and their dispositions.

## Decision summary

Propose a read-only service for 20 selected stops and one curator-configured transfer across two agencies. Use one selected GTFS Schedule feed per agency. Overlay only fresh, feed-scoped, unambiguous GTFS Realtime TripUpdates for the exact trip instance and stop event; otherwise show the schedule and why the estimate is unavailable. Compute only the configured connection. Do not use VehiclePositions as predictions, add a general journey planner, or promise a wait, boarding, accessible route, successful transfer, or dispatch response.

The specification contract is pinned to the supplied google/transit commit 3c9e7b904b5035349622f03e11851e25c16d1d99: its GTFS Schedule reference, GTFS Realtime reference, protobuf definition, and best-practice capture. This pin is the design basis, not a claim that an unknown local feed implements it. The proposed architecture is a small product-owned parser, matcher, calculator, and view. No parser library, programming language, framework, device, or browser release has been selected or evaluated. The internal interface and data contract below are bound; those implementation choices remain open.

## Bound contract and defaults

| Concern | Proposed first-release contract |
|---|---|
| Schedule and Realtime specification | Use the supplied pinned references and protobuf at commit 3c9e7b904b5035349622f03e11851e25c16d1d99. Recheck the selected feed versions against this contract before coding. |
| Feed and trip identity | Namespace every identifier by selected feed/agency. A trip key is feed_id, trip_id, and start_date; include start_time whenever needed to identify a frequency-based instance. A missing, ambiguous, cross-feed, or unsupported match suppresses that overlay. |
| Feed incrementality | In the pinned proto, omitted FeedHeader.incrementality defaults to FULL_DATASET; accept it as a complete snapshot. Reject explicit DIFFERENTIAL as unsupported and unspecified. Never merge it into retained state. Absence of an entity from a new full snapshot removes it from the current snapshot. |
| Relationship defaults | The pinned TripDescriptor enum begins with SCHEDULED at value 0; its omitted relationship therefore uses that protobuf default. The StopTimeUpdate reference also defines omitted schedule_relationship as SCHEDULED. Support the scheduled overlay path and explicit CANCELED/DELETED handling below. Other relationships are unavailable in this release. |
| Time types | Schedule HH:MM:SS is service-day time in the agency timezone; it may exceed 24:00:00 and follows the supplied standard’s noon-minus-12-hours convention on daylight-saving transition days. Parse to a timezone-aware instant, then compare cross-agency event instants as signed integer Unix seconds. Realtime absolute event times and header/trip timestamps are Unix seconds. Delays and walking/minimum-transfer durations are integer seconds. Do not treat an omitted or unknown value as zero. |
| TripUpdate freshness | Record fetch time, optional FeedHeader.timestamp, and optional TripUpdate.timestamp separately. Use the TripUpdate’s own timestamp for estimate freshness; it must be present and have age from 0 through 90 seconds inclusive. Missing, future, stale, or invalid per-trip timestamps make that trip’s estimate unknown and restore schedule-only display. The 90-second limit is a proposed consumer policy based on producer guidance, not a specification guarantee or measured local reliability. |
| Header timestamp | FeedHeader.timestamp is optional in the pinned schema. Its absence is not a specification violation and never proves a trip estimate is current. If a valid per-trip timestamp exists, an estimate may still be used while the UI says header time is unknown. Record decreasing header times as a feed-time anomaly, not a reason by itself to discard an otherwise fresh per-trip timestamp; producer guidance notes load-balanced instances can return the same content with differing header times. |
| Alert freshness and time | The supplied proto makes FeedHeader.timestamp optional and provides no separate Alert update timestamp. A rider-facing current alert therefore requires a present, nonfuture header timestamp no older than the proposed 10-minute limit, a matching selector, and an applicable communication window. This conservative rule does not prove that an individual alert changed recently. |
| Transfer threshold | For type 2, require min_transfer_time. Define the single required duration as max(reviewed_walk_seconds + explicit_buffer_seconds, min_transfer_time_seconds). Both inputs mean a total minimum connection duration; do not add them. For other allowed transfer types use reviewed walk plus explicit buffer. Reject a type-2 record with its required minimum missing. |
| Result API | Proposed pure internal operation: evaluate_connection(ConnectionInput, now_unix_seconds) -> ConnectionResult. ConnectionInput carries feed-scoped trip keys, service dates, stop sequences, schedule/estimate event instants, mapping version, integer-second walk/buffer/minimum values, and freshness provenance. ConnectionResult is one of SCHEDULE_ONLY, REAL_TIME_ESTIMATE, TRANSFER_FORBIDDEN, EXPECTED_TO_WAIT, or UNKNOWN, with source labels and arithmetic. This is a plan contract, not an existing library API. |

## Proposed replacement plan

### P1 — source intake, version binding, and activation

A curator selects one public Schedule archive per agency and, if published, its TripUpdates and Service Alerts endpoints. Record feed identity separately from publisher entity IDs. Do not join agencies because stop IDs or trip IDs happen to match. Compare Schedule feed_info.feed_version and Realtime FeedHeader.feed_version only when both are present: equal values are a match, unequal values suppress the affected overlay, and a missing value is unknown rather than a match. The fields are optional/recommended in the supplied references.

Validate and parse a candidate Schedule archive before activation. Promote a complete candidate atomically, retain the previous valid snapshot for rollback, and record URL, fetch time, publisher version metadata when present, archive digest, parser/validator identity, and import result. Schedule and Realtime versions remain distinct. Realtime failure must not roll back or replace the active Schedule snapshot.

Use HTTPS, conditional requests when supported, publisher-approved polling limits, and backoff after errors. Keep fetch time separate from producer timestamps. The supplied best practices recommend feed refresh at least every 30 seconds, TripUpdates no older than 90 seconds, and Service Alerts no older than 10 minutes; these are producer recommendations, not evidence about the selected agencies. Do not impose a 30-second polling interval until actual publisher terms and limits are known.

Accept absent incrementality as FULL_DATASET under the pinned proto default. Reject DIFFERENTIAL; do not apply its entities to a prior snapshot. Invalid protobuf, wrong feed identity/version, missing required feed structure, a future timestamp, or an ambiguous mapping makes affected Realtime data unavailable. A missing FeedHeader.timestamp is optional-schema behavior: retain fetch time, mark header freshness unknown, and make per-trip decisions from TripUpdate.timestamp as specified above.

### P2 — rider view and alert/cancellation behavior

Show scheduled departures for the selected 20 stops and the one configured transfer. Label every event as **scheduled** or **real-time estimate** and show agency/feed, applicable source timestamp, and age. A TripUpdate without an exact, fresh prediction for the selected event does not mean “on time.” Mark stale, cached, unknown, and unavailable states with text and icon as well as color.

For a matched scheduled TripUpdate, use a direct StopTimeUpdate for the selected stop sequence. If both StopTimeEvent.time and delay are present, use absolute time because the pinned proto says it takes precedence. If time is absent and event delay is present, add the signed integer-second delay to the corresponding Schedule event. Do not infer an event time from VehiclePosition, an ambiguous stop ID, omitted uncertainty, or a missing event value. StopTimeUpdate uncertainty absent means unknown; explicit zero remains distinct and is not presented as a statistical confidence guarantee. A repeated stop ID requires stop_sequence. A selected NO_DATA or SKIPPED stop does not produce a transfer estimate. Unsupported relationships or conflicting event data return to schedule-only/unknown.

A fresh, matched CANCELED TripUpdate may be shown as canceled. DELETED is experimental in the pinned schema and means the trip should not be shown as canceled to riders; suppress that trip from the rider list and preserve the raw disposition in volunteer evidence. If cancellation identity or per-trip freshness is unknown, do not assert a current cancellation.

For alerts, use the pinned current fields precisely. A rider-facing notice must have at least one nonempty informed_entity selector matching a configured agency, route, trip, or stop/station. All fields inside one selector must match together (logical AND); separate selectors are alternatives. TripDescriptor.route_id is not a route-wide Alert selector; use EntitySelector.route_id. Use communication_period as the user-facing communication window and impact_period, when present, as the service-impact window. Treat a window as start-inclusive and end-exclusive for this application contract and test both boundaries. If communication_period is absent, follow the consumer-choice allowance by retaining the alert for volunteer review as “communication time unspecified,” but do not claim a current rider warning. If impact_period is absent or does not include now, do not say service is currently affected; a communication-window notice may still be labeled with impact timing unknown or upcoming. active_period is deprecated in the pinned proto and is not the controlling first-release display field. Alerts without a matching selector, expired communication time, or fresh feed-header evidence do not become current rider warnings.

On a tablet connection failure, retain the last valid Schedule snapshot and cached view with the last successful fetch time. Mark it **cached** and Realtime stale/unavailable; never present cached estimates as current. The interface should be keyboard and screen-reader operable. This does not imply vehicle, station, path, or service accessibility data.

### P3 — transfer interpretation

A curator creates an explicit, reviewed arriving-stop/departing-stop mapping for the one cross-agency connection, with version, walk duration in integer seconds, separate explicit buffer seconds, and the source or method used for each. Geographic proximity or equal stop IDs alone is insufficient. If the mapping is absent, invalid, or stale, show “connection not configured.”

For each leg, choose a fresh matched TripUpdate estimate only under P2’s identity and freshness contract; otherwise use the Schedule event and label it schedule-only. Keep arrival/departure event instants and sources visible. Compute available transfer seconds as departure instant minus arrival instant. Type 3 forbids the connection. Type 2 requires a present nonnegative min_transfer_time from the applicable Schedule rule and compares against the single max formula in the contract. Types 0 and 1 use reviewed walk plus buffer; type 1 may be labeled “agency-declared timed transfer; vehicle expected to wait,” never as a guarantee. Reject missing type-2 minimums instead of asking the external validator to catch them. Do not infer type-4/type-5 linked or in-seat transfers across agencies; the supplied Schedule reference says linked trips use the same vehicle.

Expose the short arithmetic explanation: arriving event and source, departing event and source, available seconds, required seconds, mapping version, and any Schedule transfer rule. Do not label a connection “safe,” “likely,” or guaranteed; there is no local outcome data or validated model. Preserve timepoint=0 as approximate when supplied. In the pinned Schedule reference, omitted timepoint is treated as exact; do not invent a confidence score from omission.

### P4 — volunteer review and history

Provide a separate read-only volunteer evidence view. For each displayed result retain enough data to replay its meaning: Schedule and Realtime feed IDs/versions, fetch time, producer timestamp and field level, trip/date/stop_sequence, alert and selector/time window if used, mapping and walking-rule versions, freshness decision, result-contract version, and transfer arithmetic. Store evaluation time so later snapshots do not rewrite an earlier result. Retain source records needed for replay rather than only a screenshot.

Keep seven days as the proposed retention period. Public history shows a compact result/source-age summary; detailed source records are limited to the volunteer view and deleted after seven days. Do not collect rider identities, accounts, precise kiosk interaction history, or analytics identifiers for this read-only MVP. Access policy and retention of vehicle identifiers remain unresolved product/privacy choices and must be confirmed against selected feeds and local expectations before retaining those fields.

### P5 — components, refresh, and offline behavior

Choose a small product-owned GTFS reader, deterministic transfer calculator, and web view as the architecture boundary. The input/output API and data types above are the binding plan contract. No named parser or runtime version is selected, inspected, or claimed fit; implementation selection remains explicitly open. Do not adopt OpenTripPlanner for this fixed single-transfer view. OTP v2.10.0 documentation/release is a comparison point and a credible future option if the product grows to many origins, destinations, routes, modes, and routing semantics. The inspected OTP VehiclePosition matcher is not the TripUpdate calculator and does not establish it is validated.

MobilityData’s GTFS Validator is a candidate Schedule preflight only. The inherited capture observed v8.0.1 as latest (published 2026-05-12). Issue #2174 asks for a missing-required-field rule after min_transfer_time became required for transfer_type 2. The issue was not reproduced, validator code was not audited, and no defect in v8.0.1 is established. Implement and test the type-2 minimum rule in this product regardless of validator output.

Keep network polling and archive parsing off the rider request path. Component library, language/runtime, device/browser, agency endpoints, terms, and local feed behavior remain open; no performance fit is inferred from documentation.

### P6 — proposed acceptance evidence, not executed

Before implementation, freeze the two actual Schedule/Realtime feed pairs, feed identities/version fields, selected stops, stop-pair mapping, agency timezones, publisher limits, and reference tablet/browser/network. The following are proposals only; this reviser ran no application, validator, feed, build, or performance tests.

1. **Schedule intake and snapshots:** valid candidate activates atomically; malformed or wrong-feed candidates preserve the previous valid Schedule. Schedule and Realtime version mismatch suppresses overlays. Missing feed_version is unknown. Verify absent incrementality is FULL_DATASET, explicit DIFFERENTIAL is rejected, and an entity missing from the next full snapshot disappears.
2. **Trip identity and applicability:** identical trip IDs in different feeds never cross-match. Exercise missing/ambiguous trip IDs, start_date collision, required start_time/start_date for frequency instances, repeated stop IDs with sequence, unknown calendar date, and unsupported schedule relationships. A frequency exact_times=0 / UNSCHEDULED case is unavailable unless actual feed selection and a later product decision add it.
3. **TripUpdate freshness:** test per-trip age at 0, 90, and 91 seconds; missing, malformed, future, and stale TripUpdate.timestamp; absent header with fresh per-trip time; stale header with fresh per-trip time; decreasing header values from out-of-sync feed instances; and fetch time shown separately. Only per-trip timestamp controls estimate age. Header absence is not a required-field error.
4. **Stop event behavior:** direct selected StopTimeUpdate with absolute time, delay-only, both time and delay (time wins), missing values, NO_DATA, SKIPPED, malformed/duplicate/out-of-order sequence, and uncertainty omitted versus zero. Verify the exact matching feed/trip/event changes and unsupported or ambiguous data returns to schedule-only/unknown.
5. **Alerts and cancellation:** matching/nonmatching informed_entity selectors, AND across fields in one selector, alternate selectors, route-wide EntitySelector.route_id, communication and impact start/end boundaries, expired item still present, absent communication period, absent impact period, stale/missing/future alert-feed timestamp, CANCELED, and experimental DELETED. Distinguish “communicated now” from “service affected now.”
6. **Transfer rules:** type 0, 1, 2, and 3; missing type-2 min_transfer_time rejection; walk-plus-buffer below/equal/above type-2 minimum to exercise max; mapping version change; missing/ambiguous mapping; too-short transfer; type-1 copy without a wait promise; and type 4/5 not inferred across agencies.
7. **Service dates and clocks:** calendar exceptions, agency-specific timezones, times after 24:00, DST spring-forward/fall-back, cross-agency instant comparison, overnight trips, and a service-date collision. Compare with hand-calculated fixtures using the pinned time convention.
8. **Review, cache, privacy, and retention:** reconstruct a result from captured inputs and versions; compare source/mapping changes; label cached data after disconnect; expire the seven-day records; verify no rider identifiers enter evidence/logs; review vehicle-ID access/retention before enabling it.
9. **Performance:** on the named reference tablet/browser, use both selected agencies’ actual snapshots, 20 stops, and one transfer; record p50/p95/p99, payload size, and network state. The inherited proposed warm update target is p95 ≤1 second after ingestion; keep it a proposal until measured. Set a cold-load target only after device/network constraints are known.

## Remaining choices, uncertainty, and execution limits

The inherited brief-derived record names no actual city, agencies, feed URLs, actual stop pairs, local walking times, network limits, operating timezones, device/browser, or feed quality. Selected feeds may omit comparable feed_version, TripUpdate.timestamp, or Alert communication/impact periods; no local applicability can be claimed. The proposed 90-second/10-minute thresholds, zero tolerance for future timestamps, alert behavior, walking/buffer values, seven-day retention, p95 target, and internal API need owner confirmation against selected feeds, device, publisher limits, privacy expectations, and local clock behavior. Zero tolerance for a future timestamp is deliberately conservative and is not a GTFS requirement. No cold-load target is set.

The inherited research did not download or test a local feed, run the Validator, execute OTP or application tests, build an app, benchmark a device, or prove a transfer can be made. This reviser performed no public-source request, web search, git resolution, feed request, validator run, build, or test. It read only the allowed input map, the named predecessor artifacts/maps, and captures named in those maps. Captures copied under this job’s sources/ retain upstream IDs and provenance in source-map.json; local paths are linked there. Source IDs in this document resolve through that map.

No application was built and no transit advice was validated. Schedule-only output remains available when Realtime is absent, stale, malformed, mismatched, unsupported, or not attributable. The product must never call it “on time.”


## Consolidated retain, already-covered, reject, and uncertain dispositions

- **Retain:** the two-agency/20-stop/single-transfer scope; schedule-only fallback; feed-scoped matching; reviewed stop-pair mapping; explicit source/version evidence; seven-day proposal; no rider identity; no accessibility, occupancy, success-probability, boarding, dispatch, or wait guarantee; and the proposed validation suite.
- **Already covered in the inherited draft, now made binding:** separate fetch and publisher timestamps, versioned evidence/replay, missing-update-as-unknown, service-day/timezone care, cache labeling, and the absence of executed tests. Critic C1 is still accepted because the inherited draft incorrectly called FeedHeader.timestamp required and did not bind freshness to TripUpdate.timestamp.
- **Reject:** merging DIFFERENTIAL into prior state; treating missing TripUpdate as on-time; joining agencies by coincident IDs; using VehiclePositions as predictions; treating OTP VehiclePosition history as TripUpdate validation; counting both transfer minimums by addition; cross-agency in-seat inference; and making current rider alerts from unmatched, stale, or time-unknown data.
- **Uncertain or owner-dependent:** actual feed availability and terms, local feed quality and version declarations, missing timestamp frequency, alert period coverage, stop mapping and measured walk/buffer, local timezone/device/network, concrete parser/runtime choice, privacy policy for vehicle IDs, and whether the proposed thresholds and performance target fit this installation. These stay open until the actual feeds and deployment constraints are known.
