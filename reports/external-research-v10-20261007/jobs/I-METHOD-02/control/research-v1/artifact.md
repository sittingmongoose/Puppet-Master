### Research findings

#### Standards and analogous products (O1)

- IIIF Presentation API 3.0 models a compound object as a Manifest containing ordered Canvases. A Canvas is a view with its own URI and dimensions; painting Annotations attach images to it, and separate non-painting Annotation Pages can hold annotations about it. The Canvas and SpecificResource/Selector model gives the desk a durable view anchor instead of relying on array position. Presentation API 3.0 defines rights as an informative rights/license URI and requiredStatement as text clients must display when using or displaying a resource. See S1, §§5.2, 5.3, 5.5-5.6.
- IIIF Image API 3.0 provides a stable image-service identifier and an info.json document containing dimensions, tile capabilities, and optional rights. Image API requests can ask the partner service for regions and sizes; requesting a crop is still a request to the partner service and must not become a copied package asset by accident. CORS and authentication are explicit service concerns. See S2, §§2.2, 4, 5.1-5.6, 7.1.
- The W3C Web Annotation Data Model represents a note as an Annotation with a body and target. A SpecificResource can combine a source with a Selector. Its FragmentSelector covers rectangular media fragments; its SvgSelector covers non-rectangular areas such as polygons. This supports standards-shaped exchange while the institutional desk keeps review status and revision lineage as explicit application metadata. See S3, §§3.2, 4.2.1, 4.2.7.
- The IIIF Cookbook's multiple-view recipe directly addresses one object represented by multiple Canvases. Mirador is the closest existing product analogue: its official feature page describes comparison workspaces, IIIF v2/v3 support, W3C annotation display, annotation creation via a plugin, and workspace import/export. Those features are useful for a fit check, but the public page does not establish the brief's rights-controlled review package, institutional revision conflicts, or local-upload policy. See S4 and S26.
- Universal Viewer is a useful read-oriented alternative when the main requirement is an embeddable IIIF viewer; its official page describes opening a IIIF Manifest and OpenSeadragon image zoom. It is not evidence of a review-packet or revision-conflict workflow. Annotorious is a promising region-editing alternative: its current guide describes image annotation and OpenSeadragon/IIIF integration. I inspected the guide, not its implementation or a pinned package release, so adopting it remains a prototype option rather than a source-verified recommendation. See S27 and S6.
- RightsStatements.org's No Copyright—Contractual Restrictions statement demonstrates why a rights URI cannot be treated as a permission switch: the statement describes contractual use limits, says other permissions may be needed, and says the statement itself is not a license. A package should retain and show the provider's rights URI, required attribution text, and link, while the institution separately defines what export is allowed. See S28, together with S1 and S2.

#### Consequential component, pinned code, and mechanism (O2)

Candidate: OpenSeadragon 6.1.1, pinned to commit 201d47833e3f10e9fa55159cd4203630521926b8. The release API reports publication on 2026-09-09; the v6.1.1 source and regression-test files were independently fetched from that exact commit. This is a conditional viewer choice, not a final component lock. See S8-S17.

The captured IIIFTileSource constructor normalizes v2 @id and v3 id into its internal image identifier, requires an image identifier plus width and height, and derives tiling from Image API metadata (src/iiiftilesource.js, lines 65-203). Its getTileUrl constructs partner Image API region/size URLs from the service identifier and image pyramid (lines 460-520). Viewer source resolution calls the tile-source type/configuration path when opening an object (src/viewer.js, lines 2106-2184). This is evidence for using OpenSeadragon to render an Image API service after a separate Presentation Manifest parser has selected a Canvas and its image service. It is not evidence that OpenSeadragon itself parses a Presentation Manifest.

The code has two coordinate systems that matter to annotation persistence. Viewer.addOverlay documents its location as viewport-relative and notes that overlays are removed on close/page change unless preservation is enabled (src/viewer.js, lines 2600-2615; teardown at 967-982). A screen/viewport location changes with pan, zoom, rotation, resizing, and page changes; it is not stored annotation geometry. TiledImage.imageToViewportCoordinates, viewportToImageCoordinates, and rectangle helpers convert between image pixels and viewer coordinates (src/tiledimage.js, lines 589-720), and upstream round-trip assertions are present at test/modules/tiledimage.js, lines 54-68. Persist geometry in a stable Canvas coordinate frame and convert only for rendering. If Canvas dimensions differ from the painting image's dimensions, apply the explicit Canvas-to-image scale before calling OpenSeadragon image-pixel helpers.

The viewer's sequence mode presents a list of tile sources as one active page (Viewer.open, lines 774-805; goToPage, lines 2572-2597). The brief also requires comparing two views. Prefer two independently identified view panes for comparison, or prove an alternative in a prototype; do not use sequence index as identity or assume overlays survive page switching. OpenSeadragon's sequence example confirms the array/sequence model (S5).

#### Real issue → fix → regression → release (O3)

OpenSeadragon issue #2962 reported that a valid IIIF v2 info.json with sizes: [] crashed OpenSeadragon 6.1.0 while constructing IIIFTileSource. The report includes a reproducible service response, a standalone constructor example, the stack location, and a comparison showing 5.0.1 worked while 6.0.0, 6.0.2, and 6.1.0 failed. It traces the regression to the size-list refactor in commit ae500afb/#2710, first released in 6.0.0. See S18.
PR #2963 fixed the constructor guard from testing only that sizes exists to testing that it exists and is non-empty. It added the infoJson2level1EmptySizes fixture and the QUnit test “IIIFTileSource ignores an empty sizes array,” which asserts the source constructs without a level-size list or legacy pyramid and produces the same max level, tile width, and tile URL as the no-sizes case. The PR merged as d5efe646122631cba1afb66fb778a4d0f7351315 on 2026-08-31. See S19-S20.
The v6.1.1 release is dated 2026-09-09. At its pinned commit, the captured constructor contains the non-empty guard and the captured test/modules/iiif.js contains the named regression test at lines 299-310. That closes the observed issue-to-fix-to-regression-test-to-shipped-version chain for the tested case. This researcher did not run the test. The upstream issue's matrix is reporter-supplied release comparison, not an independent run in this stage. This evidence supports selecting 6.1.1 as the starting candidate and requires retaining the empty-sizes regression fixture in the desk's own compatibility suite; it does not prove all partner services work.

A secondary upstream history item, issue #1861 / PR #1865, records disappearing per-page overlays in sequence mode and a merged visibility fix. The changed-files response shows only src/overlay.js changed and no test file, so I treat it as a manual bug/fix history signal, not automated regression or release evidence. It reinforces the decision to keep durable annotations in the application's own model rather than treating viewer overlays as saved notes. See S23-S25 and the current viewer/overlay code in S12-S13.

### Proposed replacement sandbox plan

#### P1 — Sources and view identity

The desk accepts local images and curator-supplied IIIF resources without taking ownership of partner imagery. Normalize each input into an object record and one or more view records. A Presentation Manifest input yields stable Manifest and Canvas URIs, Canvas dimensions, painting image-service ID, provider attribution, rights URI, and requiredStatement text. A direct Image API info document yields its canonical image-service ID and dimensions; attach it to a desk-owned stable view ID. A local upload receives a desk-owned view ID and a content fingerprint computed locally.

Support Presentation API 2.1 and 3.0 and Image API 2.x and 3.0 in the MVP if the partner inventory confirms both; otherwise publish the supported subset and a clear unsupported-version error. Map versions into one internal object/view representation. Never identify a view by its current array index. A session may hold up to fifty objects; open the selected view and a bounded thumbnail/list representation lazily rather than requesting all full-resolution views at once.

#### P2 — Inspection and annotation model

Use a deep-zoom viewer for remote Image API services and a separately tested local-file path. Compare two views in separate panes by default, with each pane bound to its own view identity. Annotation geometry is stored in the source Canvas coordinate frame: top-left origin, unrotated, finite values inside Canvas width and height. If Canvas and painting image dimensions differ, define the scale transform and round-trip it in tests.

Export rectangle targets as Web Annotation SpecificResources with FragmentSelector values xywh=x,y,w,h; export polygons with SvgSelector values whose SVG viewBox is 0 0 canvasWidth canvasHeight. Sanitize imported SVG and text; render markup as data, never executable HTML. Each annotation has a unique stable ID, author, created/modified times, text body, source/view target, selector and review status. Review status is application metadata, not a claim of Web Annotation standard semantics. No visual recognition is included.

Use OpenSeadragon 6.1.1 only as a current deep-zoom candidate. It opens Image API tile sources after a separate Manifest adapter chooses the Canvas. Reopen notes from the desk's durable model and redraw them through pixel-to-viewport conversion. Do not store OSD overlays, viewport locations, sequence positions, or transient selection as canonical note data.

#### P3 — Review package and rights behavior

Define one versioned package document with package ID/version, object/view records, annotation records, source metadata snapshot, rights/attribution snapshot, package revision lineage, and per-view open status. A ZIP package may contain this document and only explicitly selected institution-owned thumbnails. Partner image bytes, partner service crops, and partner-derived thumbnails are excluded by default. If institutional policy authorizes any exception, require a named permission/policy and explicit curator opt-in before export; no rights URI alone activates the exception.

On reopen, attempt only the supplied source reference. Show which object/view a note targets even when the source is unavailable. Distinguish unreachable, denied/authentication required, unsupported, metadata-changed, and not-verifiable states. Keep the prior rights text and fresh source metadata side by side when they differ. If identity cannot be verified from a stable provider identifier/version signal, say so; do not promise pixel-change detection from URL or dimensions alone.

#### P4 — Storage and revisions

Keep the small institutional service and independent-review exchange; defer live simultaneous editing. Persist package revision ID, parent/base revision ID, author, timestamp, and import origin. On import, recognize an unchanged duplicate; when revisions share a base but differ, preserve both and present annotation-level conflicts to a curator. Never silently overwrite a note or resolve conflict by timestamp alone. The institutional owner must choose authentication, access roles, retention, backup, merge UI, and export/audit policy before implementation.

#### P5 — Components and usability

Prototype three paths: OpenSeadragon 6.1.1 plus a small Manifest adapter and app-owned annotation model; Mirador configured with a review-package/revision integration; and, if useful, OpenSeadragon with Annotorious as the drawing UI and an adapter into the same app-owned annotation model. Do not lock a parser, annotation plug-in, or image-upload conversion path until representative partner manifests and local files pass the same fixture suite.

The MVP must support keyboard navigation between objects/views, zoom and pan, visible focus and predictable return from dialogs, a keyboard-operable rectangle workflow, polygon editing with a documented accessible fallback, readable rights/attribution text, and non-color review status. Cap concurrent full-resolution requests and load adjacent object thumbnails only when needed. Local-file MIME types, maximum file sizes, TIFF/RAW handling, and any browser-side tiling/conversion limit are explicit product decisions.

#### P6 — Acceptance

All acceptance items below are proposals; none was executed during research. See the validation proposals below.

### Product choices, options, and rejected leads

**Recommended starting path:** use OpenSeadragon 6.1.1 for deep zoom only, with a distinct IIIF Presentation adapter and a canonical Web Annotation-shaped note model. Before component lock, compare one representative v2 manifest, one v3 manifest, one direct v2 service with sizes: [], one v3 service, one local high-resolution image, and a two-pane comparison in each candidate path.

**Alternatives:** Mirador may reduce viewer and manifest work if its annotation plugin and workspace handling can be integrated with the institutional package and conflict service. Universal Viewer can anchor a read-only/embedded workflow but the cited page does not establish region authoring or review exchange. Annotorious may reduce drawing work, but its pinned code, package compatibility, exported selectors, keyboard authoring, and behavior with current OSD have not been checked. A custom SVG overlay is a smaller drawing surface but still needs accessible editing, import/export, sanitization, identity and revision handling.

**Rejected as default behaviors:** copying or proxying partner pixels into a review packet; deriving permission to export from the mere presence of a rights URI; treating an Image API service URL as a Presentation Manifest; storing a note against a view's array index; storing zoom-dependent viewport coordinates as geometry; treating the viewer overlay as durable annotation storage; or silently discarding notes when a source is unavailable. These either conflict with the brief or are contradicted by the captured standard/component responsibilities.

**Decisions still needed from the museum:** minimum Presentation/Image API versions based on partner inventory; supported local image types and size/performance ceiling; whether authorized local originals can ever travel in a package; who may approve local thumbnails or other derivatives; exact review-status vocabulary; user identity and retention policy; and whether staff prefer a Mirador-centered integration or a narrower custom desk.

### Remaining uncertainty and limits

Partner manifests and image services vary in API version, metadata quality, CORS, authentication and stability; this stage inspected public standards and upstream code but no actual partner sample. Some manifests may scale a painting into a Canvas whose dimensions differ from the image service; the adapter's transform needs real fixtures. SvgSelector interoperability and accessible polygon editing need cross-client checks. Browser support and memory for large local files are unverified. Rights metadata may be incomplete or contractually constrained; the museum must set the export rule. The package schema, institutional service and merge interaction are proposals, not an implemented or deployed system.
