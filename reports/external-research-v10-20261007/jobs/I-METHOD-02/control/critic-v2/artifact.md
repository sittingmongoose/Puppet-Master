## Overall disposition

Retain the research proposal’s core direction and all six frozen plan areas. Its strongest decisions are keeping partner pixels out of portable packages by default; separating library behavior from museum policy; preserving notes and original targets when sources fail or change; treating geometry, rights, revision conflicts, keyboard access, and low bandwidth as product requirements; and separating proposed acceptance checks from executed research.

Two corrections must carry into finalization:

1. Treat Annotorious 3.9.4 as a **context-bound image annotation adapter**, not as a package mechanism that independently preserves every W3C target. In the pinned W3C parser, the non-array branch reads the misspelled property **rest.targret**. Static inspection shows the internal target is rebuilt without the input SpecificResource source/type. The serializer accepts a caller-supplied source string. This can work when import first resolves each annotation to its exact view, provides that view ID to the adapter, and retains original annotation JSON; the adapter alone cannot guarantee multi-view target identity.
2. Correct the research artifact’s O3 statement about Annotorious issue #603. The issue is now closed as completed, after a reporter confirmed the fix. Commit **61148bfe2300a55e0c5ce7f20bd5538de7ca0e1b** is in the history leading to the exact 3.9.4 GitHead; the pinned package contains a 512-character guard and numeric coordinate pattern. The separate PR #604 is closed without a merge commit, so do not call it merged or count its branch-only tests as shipped. Keep bounded-input and malformed-selector checks as defense-in-depth, but do not label #603 unresolved for 3.9.4.

The central remaining implementation condition is to resolve a source/view’s annotation target and coordinate frame before editing or importing. A Presentation Canvas, Image API service, image body, and local upload are not interchangeable identifiers. Finalization should state the model for service-only links and museum-owned uploads and retain raw target JSON for lossless round trips.

## O1 — discovery from the user need

The IIIF Presentation and Image APIs, W3C Web Annotation Model, and Cookbook region/polygon recipes are well-chosen primary sources. The region recipe supports selecting a region of a resource while retaining the original image, but it is a painting/display recipe and explains Canvas and resource dimensions can differ. It does not show that OpenSeadragon image-pixel coordinates can be written directly as a Canvas-target annotation. The polygon recipe is more directly applicable: it warns that SVG rendering varies and explains that a selector targeting the whole Canvas differs from SVG mapped to a subregion; a subregion must target the Canvas bounding rectangle and may require different X/Y scaling. Keep the draft’s identity-transform rule only for validated matching dimensions; add the bounding-rectangle rule to polygon fixtures.

The rights properties identify informative rights assertions and can support display, but do not replace the museum’s permission decision. The proposed source/view-level rights snapshot and refusal to export partner pixels are supported and should remain. Finalization should define who can authorize a locally owned derivative thumbnail and record that authorization with the asset.

Mirador is a useful alternative to prototype, but its cited project page is unversioned and cannot establish exact-version keyboard, polygon, package, or rights behavior. Treat Universal Viewer, TIFY, and Curation Viewer as discovery leads only; ecosystem presence is not feature-parity evidence. Preserve bounded alternatives found in the Cookbook: a non-painting annotation on the full resource is directly relevant to curator notes; Content State may be a viewing-state option if the selected viewer supports it; copy-and-crop is a poor default under the no-republication/no-partner-copy constraint. None changes frozen scope without a product decision.

## O2 — pinned code and governing context

**OpenSeadragon 6.0.2.** The independently fetched tag ref and annotated tag object resolve to commit **7842cd92e6799d97c18227a79cb69af4f706b023**; the tag reports unsigned. Captured release-commit overlay.js, viewer.js, iiiftilesource.js, and overlay tests establish the pin. Viewer.close, Viewer.open, and Viewer.addOverlay show how transient viewer overlays are cleared/recreated and that close may happen during sequence page changes. The method documentation calls addOverlay locations viewport-relative, while Overlay constructor documentation calls its location “on the image”; keep the distinction explicit and do not use either overlay API as the persistent annotation coordinate contract. The sequence warning is useful but is not annotation-persistence evidence.

**Annotorious 3.9.4.** Both exact package tarballs were independently fetched and their SHA-512 hashes match version metadata’s dist.integrity. Metadata reports GitHead **3fbefb2cb4646c11e2d0d0b9fb4977fe028186a4**; the OSD adapter peer range includes OSD 4, 5, and 6. In the adapter source map, createOSDAnnotator defaults drawing off; SVGDrawingLayer converts viewer-local points to OSD image coordinates and records a new annotation ID, user, and creation time. viewerOffsetPointToImageXY handles OSD flip and rotation. These paths establish image-space drawing, not arbitrary IIIF painting transforms or accessible keyboard drawing.

The core W3C adapter serializes a SpecificResource using a caller-supplied source string; ordinary non-rotated rectangles become pixel FragmentSelectors and other supported shapes use SVG selectors. Its import path rebuilds the internal target and has the rest.targret typo above. A multi-view importer must retain original target/source and selector, resolve the exact view, then provide that ID to the adapter or use a separately validated parser. Do not assume one global source value can round-trip a package containing many Canvases.

The pinned SVG serializer emits a polygon element by default and has an optional Mirador-safe path mode; the source comments describe viewer-specific support. This is an interoperability risk, not evidence that either form fails. Keep the independent-viewer gate and lossless retention for selectors the viewer cannot render. The 512-character limit and numeric coordinate pattern in the pinned FragmentSelector parser support mitigations for reported #603 inputs; inspect exact input behavior and retain limits rather than infer general parser safety.
