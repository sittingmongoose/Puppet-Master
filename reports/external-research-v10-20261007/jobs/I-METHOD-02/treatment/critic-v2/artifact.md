## O1 — Discovery from the museum’s need

The draft correctly starts from stable view identity, detailed inspection, portable notes, rights limits, and reopening after source failure. Preserve the IIIF Presentation 3 Manifest/Canvas structure, W3C Web Annotation selectors, IIIF Image API, rights and authorization distinctions, and the multiple-Canvas lead. The official Presentation 3 specification says a Manifest’s ordered Canvases represent views; a Canvas has an HTTP(S) identity and provides a frame of reference. It also says a present requiredStatement must be rendered, while rights is an informative assertion that may or may not be rendered. The rights recipe likewise distinguishes a requiredStatement from a rights URI. See [Presentation 3](https://iiif.io/api/presentation/3.0/) and its [rights recipe](https://iiif.io/api/cookbook/recipe/0008-rights/), captured as sources/iiif-presentation3.html and sources/iiif-rights-recipe.html.

The product comparison is useful but incomplete. Mirador 4 is a serious alternative because its current project page advertises comparison workspaces, zoom and pan, IIIF Presentation and Image v2/v3, authentication, and annotation creation through a plugin. Those features could reduce custom manifest navigation and two-pane work; they do not establish that its plugin and state model meet this desk’s revision and portable-package rules. Keep it as a real alternative and test its annotation persistence path before selecting. [Mirador](https://projectmirador.org/), captured as sources/mirador-home.html.

Add Universal Viewer as a bounded optional lead, not as a presumed replacement. Its project page advertises IIIF Manifest display, OpenSeadragon zoom, embedding/configuration, and IIIF Auth support. The reviewed page does not establish polygon authoring, side-by-side review, or this package/revision workflow. It is therefore a candidate for comparison only where viewing and access control matter. [Universal Viewer](https://universalviewer.io/), captured as sources/universalviewer-home.html.

Keep Tropy as an inspection analogy and reject it only as a full browser/shared-review solution: its selections and notes are useful, but its product model is desktop-oriented. Do not reject Annotorious globally on issue #599. The issue remains open and reports a narrow production Webpack failure for Annotorious 3.7.13 onward, with 3.7.19 broken and 3.7.4 working in the reporter’s Next 16, React 19, OpenSeadragon 5.0.1 setup. That is a conditional integration risk, not evidence against every release or the proposed OSD 6.1.1. Preserve it as an alternative requiring an exact production-build test if considered. ## O2 — Pinned code and governing behavior

The proposed OpenSeadragon v6.1.1 pin is verified as tag v6.1.1 resolving through tag object 96bdae63fc78de7cfb0721480b4e0560e0ce6b96 to full commit 201d47833e3f10e9fa55159cd4203630521926b8. Captures: sources/osd-tag-ref-v6.1.1.json, sources/osd-tag-object-v6.1.1.json, sources/osd-v6.1.1-release.json, and sources/osd-latest-release.json.

Independent inspection of the pinned code confirms these claims:

- src/iiiftilesource.js, IIIFTileSource.supports and configure, recognizes Image API 1.x, 2.x, and 3.x info data and normalizes it. This is image-service handling, not Presentation Manifest parsing. The proposed Manifest adapter remains necessary.
- src/viewer.js, Viewer.addOverlay, accepts an HTML overlay and redraws it. Its documentation calls the supplied location viewport-relative.
- src/overlay.js, Overlay.drawHTML and _getOverlayPositionAndSize, handles position, size, rotation, flip, and content direction for an HTML overlay. It does not supply polygon editing, a Web Annotation record model, or the desk’s workflow.
- src/viewport.js explicitly warns that its image/viewport conversions are inaccurate with multiple images and directs callers to the specific TiledImage conversions. A separate viewer per comparison pane is a defensible simplification; persist neither viewport positions nor unqualified image-pixel coordinates.

These boundaries support OSD as an image-viewer candidate, not as a complete annotation component. Make the app-owned annotation layer explicit: use TiledImage conversions for pointer/image mapping, render and edit polygon geometry in an app-owned SVG layer, and test that layer through resize, crop/clip, rotation, flip, and source replacement. Do not imply that addOverlay’s rectangle-like location is the serialized region geometry.

Pinned captures are sources/osd-v6.1.1-iiiftilesource.js, sources/osd-v6.1.1-viewer.js, sources/osd-v6.1.1-overlay.js, sources/osd-v6.1.1-viewport.js, and sources/osd-v6.1.1-openseadragon.js. The actual v6.1.1 code URLs contain the full commit SHA.
