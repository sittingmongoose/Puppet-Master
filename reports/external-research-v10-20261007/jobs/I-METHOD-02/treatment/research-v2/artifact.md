## O1 — Discovery from the user need

The museum needs to identify a particular view, inspect small regions at high zoom, exchange notes without copying partner pixels, and let another curator reopen the packet. The following primary sources were selected from that need before comparing P1–P6.

- **IIIF Presentation API 3.0** models a compound object as a Manifest with ordered Canvases representing views. Canvases provide the coordinate frame and may refer to images and annotation pages; non-painting annotations are separate from the image-painting annotations. This supports identifying a front/back or detail view by Canvas URI instead of by an array index. The Presentation API’s Annotation and Canvas structure also gives the desk a stable export target. [IIIF Presentation API 3.0](https://iiif.io/api/presentation/3.0/), especially Manifest, Canvas, Annotation Page and Annotation; captured as `iiif-presentation3` in `source-map.json`.
- **W3C Web Annotation** has a `FragmentSelector` for media fragments and an `SvgSelector` for non-rectangular areas, including polygons. A selector belongs to a `SpecificResource` target. Rectangles can use a `xywh` fragment; polygons can use SVG coordinates relative to the image. This is a better exchange format than an undocumented viewport-pixel record, provided the desk fixes the coordinate frame and preserves the source URI. [W3C Web Annotation Data Model](https://www.w3.org/TR/annotation-model/), Specific Resources and Selectors; captured as `web-annotation-model`.
- **IIIF Image API 3.0** supplies standard region and size requests for an image service. **OpenSeadragon’s IIIF tile source** recognizes Image API context versions 1, 2 and 3 and normalizes them; it does not parse the Presentation Manifest that groups object views. The desk therefore still needs a Manifest-to-view adapter. [IIIF Image API 3.0](https://iiif.io/api/image/3.0/); pinned OSD source is captured as `osd-v6.1.1-iiiftilesource`.
- **Rights metadata is not permission enforcement.** IIIF `rights` is an informative license/rights assertion and may not be visible. `requiredStatement` is a separate statement that a client must render, although it can be initially hidden if the means of revealing it is obvious. Neither property authorizes the museum to republish an image. The Authorization Flow API describes provider-controlled access for restricted resources, but its authentication mechanism is outside the spec and may involve another institution’s system. [IIIF rights recipe](https://iiif.io/api/cookbook/recipe/0008-rights/), [Presentation API 3.0](https://iiif.io/api/presentation/3.0/), and [Authorization Flow API 2.0](https://iiif.io/api/auth/2.0/); captured as `iiif-rights-recipe`, `iiif-presentation3`, and `iiif-auth2`.
- **Mirador 4** is the closest full product alternative found: the IIIF guide describes a current, open-source multi-window viewer for zooming, comparison and annotation, with broader Presentation API 3 support than earlier versions. It may reduce viewer and manifest-navigation work. The museum still needs to establish whether its annotation plugin and persistence model can satisfy this desk’s package, rights and revision requirements. [IIIF guide to using resources](https://iiif.io/get-started/explainers/using_iiif_resources/) and [Mirador](https://projectmirador.org/); captured as `iiif-using-resources` and `mirador-home`.
- **Tropy** is a useful inspection analogy, not a browser-desk candidate. Its desktop product groups photos into items, supports tags and notes, and lets a user create image selections with attached metadata and notes. Its documentation says it is a personal-computer application rather than an online presentation platform. [Tropy basics](https://docs.tropy.org/) and [Tropy selections](https://docs.tropy.org/in-the-item-view/selections); captured as `tropy-basics` and `tropy-selections`.
- **Annotorious** is a plausible region-drawing alternative. Its open issue #599 reports a specific production Webpack drawing-mode failure in versions 3.7.13 onward, with 3.7.19 reported broken and 3.7.4 reported working in the reporter’s Next.js/OSD setup. The issue was open when retrieved. It is a concrete reason to require production-build verification and exact dependency pins before adopting it; it is not proof that all builds or all versions fail. [Annotorious issue #599](https://github.com/annotorious/annotorious/issues/599); captured as `annotorious-regression-599`.

A further useful lead is the IIIF recipe for opening multiple Canvases. The desk should treat views as distinct Canvases and let the curator choose which two to compare; a view is not safely identified by a transient UI slot. [IIIF multiple-Canvas recipe](https://iiif.io/api/cookbook/recipe/0540-link-for-opening-multiple-canvases/); captured as `iiif-multicanvas-recipe`.

## O2 — Pinned component code and governing behavior

**Recommended viewer component:** OpenSeadragon **v6.1.1**, full commit `201d47833e3f10e9fa55159cd4203630521926b8`. GitHub’s v6.1.1 tag ref and tag object were captured to resolve that immutable commit; the helper’s `--commit` field is only a caller label and does not itself bind code identity. The actual code URLs below include the full commit SHA. The v6.1.1 release was published 2026-09-09. Its source, tag metadata, release notes and demo are captured under `sources/` and indexed in `source-map.json`.

- `src/iiiftilesource.js`, `IIIFTileSource.supports` and `configure` (around lines 205–306 of the captured source) recognize Image API contexts 1–3 and normalize Image API `info.json`. This governs the direct IIIF image-service link path. It does not parse Presentation API manifests or decide which Canvas/body to show.
- `src/viewer.js`, `Viewer.addOverlay` (around lines 2600–2645) is the caller that accepts an overlay and redraws it. Its API documentation calls `location` viewport-relative. `src/overlay.js`, `Overlay`/`drawHTML`/`_getOverlayPositionAndSize` (around lines 80–104 and 253–345) governs how the overlay is positioned, sized, rotated and flipped. A `Rect` location is convenient syntax for an overlay rectangle; it does not by itself define the serialized annotation coordinate system.
- `src/viewport.js`, `Viewport.imageToViewportRectangle` and `viewportToImageCoordinates` (around lines 1370–1545) convert between image pixels and viewer coordinates. The source warns that `Viewport` coordinate conversion is inaccurate with multiple images and directs callers to the specific `TiledImage` conversion methods. This supports one active image per comparison pane and source-pixel coordinates stored independently of pan/zoom.
- `src/openseadragon.js` documents `overlayPreserveContentDirection`, which controls whether text remains readable when the viewport is flipped. The same behavior appears in the pinned overlay source.

**Implementation consequence:** use two independent OSD viewers for the two comparison panes, each with one selected source. Persist region geometry in the selected image/Canvas coordinate frame; convert pointer positions through that pane’s `TiledImage` methods. Do not persist viewport coordinates. Test both resize and flip/rotation handling before accepting the component. OSD supplies image display, zoom and overlay mechanics, not annotation editing, status workflow, package revisioning, or a Presentation Manifest parser.

## O3 — Issue, fix, regression evidence and release applicability

OSD issue [#1614](https://github.com/openseadragon/openseadragon/issues/1614) reports that after flipping the image, a `viewer.addOverlay()` overlay did not flip with it and moved in the opposite horizontal direction. The issue comments record that the issue remained reproducible on OSD 3.0.0 in December 2021. In July 2024, PR [#2546](https://github.com/openseadragon/openseadragon/pull/2546) merged the fix: correct overlay position on flip, invert scale/rotation as needed, and add an option that preserves content direction for readable text. Its changed files include `src/overlay.js`, `src/viewer.js`, `src/openseadragon.js`, and `test/demo/overlay.html`; the demo was extended to exercise overlay behavior while flipped/rotated.

Release applicability is explicit: [OSD v5.0.0 release notes](https://github.com/openseadragon/openseadragon/releases/tag/v5.0.0), published 2024-08-14, list the #2546 overlay fix and content-direction option. The selected v6.1.1 source still contains the flip positioning and direction-preservation behavior. The history establishes a real defect, reported behavior, merged fix, demo witness and a release containing that fix. It does **not** establish that the original defect was a regression introduced by a specific version, and the PR added a demo rather than an automated regression test. The acceptance plan below therefore still requires automated geometry coverage; the released fix must not be mistaken for proof that the museum’s full annotation flow works.

The additional Annotorious issue #599 is a more explicit version regression report, but had no fix/release evidence at retrieval. It supports treating that integration as an alternative requiring its own production-build test, not as an adopted fix.

## O6 — Complete proposed replacement plan and validation artifact

### P1 — Sources and identity

The desk opens curator-selected local image uploads and user-supplied IIIF Presentation or Image API links. Support a defined Presentation 2.1/3.0 subset: ordered Manifests/Canvases and one selected painting image service per view. A Manifest with multiple Canvases creates multiple named views; the curator chooses a view for each pane. Fetch remote links directly in the curator’s browser; do not proxy them. Unsupported structures, malformed manifests, CORS failure, missing service data and denied access produce an explanation and preserve the source URI. For restricted providers, decide whether to implement IIIF Authorization Flow 2.0; otherwise show the denied state. Do not silently substitute a different image or view.

An object has a stable local object ID; each view has a stable local view ID plus the original Manifest, Canvas and image/service identifiers. Local uploads record a generated ID, filename, MIME type, dimensions and local content hash. Remote sources record provider, URI, observed Canvas/service identifiers and dimensions, rights metadata and last-observed time; do not download a remote source to hash it. Whether Presentation 2.1 must be supported is a release decision informed by representative partner manifests before implementation freeze.

### P2 — Inspection and annotation

Use OSD v6.1.1 in two separate panes for comparison. Load image-service tiles lazily and keep one active image per pane. Rectangles and polygons are annotations owned by the desk, not image edits. Each annotation records an ID, object/view IDs, original Canvas/source URI, source-coordinate geometry, text, curator identity/label, create/update timestamps and review status. Store rectangle coordinates in the defined pixel coordinate space; store polygons as ordered points in that same space. Serialize standards-facing targets as Web Annotation `SpecificResource` targets: rectangle `FragmentSelector` (`xywh`) and polygon `SvgSelector`. Any conversion from an image service’s pixel dimensions to the Canvas dimensions must be explicit and tested; reject or flag unhandled multi-image/offset Canvas cases instead of guessing.

No visual recognition runs in the MVP. Provide a keyboard path for selecting and editing a region, including a numeric rectangle entry path and keyboard-created polygon vertices; pointer drawing alone does not satisfy P5.

### P3 — Review exchange and rights

Export an application-owned portable ZIP containing a versioned `review.json`, object/view identifiers, annotation data, revision lineage, rights/source observations and optional allowlisted local thumbnails. Never bundle or persist partner image bytes, partner crops or screenshots. A curator may include a thumbnail only for a local asset the institution has marked owned/cleared. A missing local source can be reattached by matching an explicit local hash or curator confirmation; do not match on filename alone.

On reopen, report each view as available, unavailable, changed/possibly changed, or access denied. Keep annotations visible in the review list and linked to their original source even if the image cannot load. Compare stable URIs/IDs and dimensions when available. State the limit: replacement at the same URI with unchanged dimensions cannot reliably be detected without a provider version signal or permission to verify content. Display provider, `rights`, and `requiredStatement` at the object/view level. Treat `rights` as metadata and never as automatic republication permission.

### P4 — Service and revisions

The institutional service stores package metadata and annotation/revision records, not partner image bytes. The browser obtains partner images directly from provider services; it does not proxy or persist them. Save local source bytes to institutional storage only if the institution separately chooses that policy and marks the asset as owned/cleared; it is not a default of this plan. Save each annotation/review change as a revision with a parent revision ID. Importing the same package with divergent descendants creates a conflict view with both versions and field/geometry differences. The curator chooses an outcome; the service preserves the prior versions. Live simultaneous editing is deferred.

### P5 — Components, usability and performance

Pin OpenSeadragon v6.1.1 to commit `201d47833e3f10e9fa55159cd4203630521926b8`. Use its Image API tile source for image services. Implement an app-owned, versioned Manifest adapter limited to the supported Presentation 2.1/3.0 subset; unsupported cases remain explicit. Keep application annotation records in Web Annotation-compatible JSON-LD and retain desk-only review fields as named extensions. Mirador 4 can replace the viewer/Manifest adapter if curators need broader IIIF navigation, but must pass package, revision, rights and workflow acceptance before selection.

Keep the full keyboard/focus path, visible selection/status, readable rights statement, and resize/reduced-bandwidth behavior in the MVP. Open only the selected two views at full resolution; lazy-load the rest. No server-side thumbnail generation from a partner source. Establish the target browsers, realistic network profile and acceptable load-time threshold with curators before sign-off; this research makes no speed claim.

### P6 — Proposed acceptance witnesses

1. Parse representative v2.1 and v3.0 Manifests with front/back and detail Canvases. Verify stable Canvas/source IDs, order and rights statements. Include an unsupported/multiple-painting-body case and verify the desk asks for a selection or explains its limit.
2. Open a local image and an Image API 2/3 service. Compare two views, resize both panes, zoom, pan, rotate and flip. Round-trip rectangle and polygon geometry through create, save, close and reopen, measuring against known source-coordinate points. Test the exact OSD v6.1.1 code path, including the #2546 flip case.
3. Exercise unavailable, CORS-blocked, changed-ID, changed-dimension and denied sources. Verify the packet keeps all annotation data and labels the source state without substituting a view. Include a same-URI/same-dimension replacement case and verify the UI does not claim certainty.
4. Export and reopen a package with an allowed local thumbnail and a partner view. Inspect its contents to confirm it contains no partner image bytes, crops or screenshots. Verify rights metadata and required statements remain attached to the correct view and export does not treat a license assertion as authorization.
5. Import two independently revised copies of the same package. Verify divergence is presented as a conflict with both revisions preserved, and that user resolution is explicit.
6. Complete inspection, rectangle and polygon creation/editing, source selection and export using keyboard only. Check focus order, visible focus, accessible names/status announcements and that rights statements are discoverable.
7. Run a 50-object low-bandwidth session: thumbnails and text first, only two full-resolution views at a time, no eager loading of all partner images. Curators set the acceptable latency threshold before the run.

All seven items are **proposed checks**, not executed checks. No application was built or validated in this role.

## Alternatives, product decisions and uncertainty

- **Recommended:** OSD v6.1.1 plus the narrow app-owned Manifest adapter and Web Annotation record shape. It gives a pinned, inspectable Image API viewer and a direct overlay/coordinate layer. The museum still owns the two-pane workflow, annotation editing, parser, package and conflict rules.
- **Alternative:** Mirador 4. It covers multi-window comparison, Presentation navigation and annotations more broadly, and may reduce custom viewer work. Decide after a curator workflow prototype whether its extension and annotation persistence model can preserve this desk’s package/revision model. Do not infer product fit from its feature list alone.
- **Alternative with a warning:** Annotorious can supply rectangle/polygon drawing around OSD, but issue #599 reports a production-bundle regression in later 3.7.x builds. Pinning 3.7.4 is only a reported workaround, not an independent compatibility result for OSD 6.1.1. If considered, test its exact pins in the target production bundler and verify its exported selectors against the chosen Web Annotation format.
- **Analogy only:** Tropy’s nested photo selections and notes are useful for curator inspection, but its local desktop workflow does not meet the browser/shared-review requirement.

Product choices still needed: whether partner inventory requires Presentation 2.1 in the first release; whether restricted IIIF Authorization Flow is supported or denied sources remain view-only failures; institutional login versus curator-entered attribution; the institution’s policy for storing owned local uploads; which local thumbnails curators may include; representative supported Manifest structures; and browser/network acceptance thresholds. These choices do not change the constraints against republishing partner pixels.

Uncertainty: CORS and provider access vary by institution; same-URI content replacement may be undetectable; the proposed narrow parser needs sample manifests; the OSD issue fix is released but its PR did not add an automated regression test; OSD alone does not supply polygon editing or review persistence; and candidate criticism has not run.
