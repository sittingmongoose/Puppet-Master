## O1 — Discovery from the museum’s need

The bounded need is to identify the intended view of an object, inspect small regions at high zoom, exchange review notes without copying partner pixels, and let another curator reopen the review packet. Discovery had already been completed in the research role; this revision adds no broad search or discovery stage.

The supported standards mechanisms are:

- **IIIF Presentation 3.0:** a Manifest describes a compound object; its ordered Canvases represent views. A Canvas has a stable HTTP(S) URI and assembles content through painting annotations. The supplied specification says rendered content must be scaled into the Canvas space. Non-painting annotations are separate from the Canvas painting annotations. This supports storing Manifest and Canvas identity rather than a transient pane number.
- **IIIF Presentation 2.1.1:** the captured older specification uses a different JSON shape, including @id/@type, Sequences, Canvases, painting annotations, and otherContent. It must have its own versioned input adapter. Support for 2.1.1 in the first release is a curator and partner-inventory decision, not an interoperability fact established by this research.
- **W3C Web Annotation and Media Fragments:** SpecificResource provides a source plus selector; FragmentSelector can use the Media Fragments syntax and declare its syntax through conformsTo; SvgSelector can describe a non-rectangular area such as a polygon. The proposed exported review annotations target a Canvas in one declared coordinate frame. Legacy IIIF 2.1.1 annotations are parsed as legacy input and normalized; that input format is not conflated with the desk’s W3C-compatible output.
- **IIIF Image API and OpenSeadragon:** Image API supplies region and size requests. The pinned OpenSeadragon IIIF tile source recognizes Image API contexts 1 through 3; it does not parse Presentation Manifests or select a Canvas. A separate Manifest adapter remains necessary.
- **Rights and access:** the supplied IIIF rights material distinguishes the informative rights assertion from requiredStatement, which must be rendered when the resource is displayed or used. Rights metadata does not itself grant republication permission. Authorization Flow 2.0 describes provider-controlled access, while implementation and identity arrangements remain provider-dependent.
- **Product options:** the supplied Mirador 4 homepage advertises an open-source, multi-window viewer with zoom, comparison, annotation, and a plugin framework. It does not establish this desk’s package, revision, exact Presentation/Image API version, or authentication fit. The supplied Universal Viewer homepage supports a narrower lead: Manifest viewing, OpenSeadragon zoom using IIIF Image API, embedding, and IIIF Auth. It does not establish polygon authoring, side-by-side review, or this desk’s persistence model.
- **Inspection analogies and conditional integrations:** Tropy’s supplied selection documentation supports photo-item selections and notes as an inspection analogy; that evidence does not establish a browser/shared-review solution. Annotorious issue #599 is a specific open report about production Webpack drawing-mode behavior for reported 3.7.13-and-later builds, with 3.7.19 broken and 3.7.4 working in the reporter’s Next.js 16, React 19, OpenSeadragon 5.0.1 setup. It is a conditional risk for that environment, not proof that all Annotorious builds fail or that it applies to OpenSeadragon 6.1.1.
- **Multi-Canvas lead:** the IIIF cookbook’s multiple-Canvas recipe supports treating each view as a distinct Canvas and letting a curator select views for comparison. UI order is not a durable identity.

The researcher’s report says discovery preceded plan comparison. Its supplied captures do not independently establish that chronology, so this remains a reported process fact rather than a verified source claim. The critic’s map mentions Recogito in a search record, but the admitted primary-source captures do not support a product disposition; it remains unadjudicated.

## O6 — Full proposed replacement plan

### P1 — Sources, identity, and access

The desk opens curator-selected local image uploads and curator-supplied IIIF Presentation or Image API links. Support up to 50 objects, each with multiple views. Treat a Manifest as the object-level source and each Canvas URI as a view identity; never use a list position, pane number, or label as the persisted identity.

Propose a fixture-backed, versioned adapter for Presentation 2.1.1 and 3.0 over an explicitly bounded subset: ordered Manifests/Canvases and a supported painting image/service association. Each Canvas provides its label, dimensions, source annotation/body identifiers, and rights/access statements. Make v2.1.1 first-release support conditional on representative partner inventory; implement separate syntax paths for v2.1.1 and 3.0 rather than one parser that guesses. For multiple, offset, or ambiguous painting bodies, require an explicit supported selection or show the unsupported state; do not silently choose or remap an image. Record unsupported structures as open limitations until exact fixtures and curator needs settle them.

Each object has a stable desk ID, Manifest URI, provider, and last-observed time. Each view has a stable desk ID, Canvas URI, original image/service URI, source protocol/version where known, Canvas dimensions, image/service dimensions, rights assertion, requiredStatement, and any explicit version signal. Local uploads have a generated ID, filename, MIME type, dimensions, and local content hash. Remote partner images are fetched directly from their provider by the curator’s browser; no server-side proxy, remote-byte persistence, or remote hashing is part of this plan.

A malformed or unsupported Manifest, missing image service, CORS denial, unavailable source, and unauthorized source produce a visible state that retains the original URI and annotations. Decide whether restricted providers require IIIF Authorization Flow 2.0 in the first release. If not implemented, report access denied without substituting a different Canvas. Display requiredStatement when the resource is displayed or used; treat rights as metadata, not permission to republish.

### P2 — Comparison, geometry, and review annotations

Use two independent OpenSeadragon 6.1.1 viewers for side-by-side comparison, with one active selected image per pane. Load only those selected views at full resolution. Use the pinned IIIF Image API tile-source for image service data, while the app-owned Presentation adapter chooses the Canvas/view.

Use the Canvas as the canonical stored and exported coordinate frame. Image-service pixels, Canvas coordinates, and viewport/display coordinates are distinct. Derive a versioned mapping from a supported painting annotation’s image/body placement and source dimensions into the Canvas dimensions. Persist the mapping inputs/version with the source observation so the geometry can be reconstructed deterministically. Convert pointer positions through the image-specific TiledImage conversion methods identified by the pinned Viewport source, then map into Canvas coordinates. Do not serialize viewport positions. If the placement or selector cannot be interpreted unambiguously, mark the view unsupported for region editing and preserve its source link rather than guessing.

Render desk geometry in an app-owned SVG layer. Keep it separate from OSD’s viewport-relative HTML overlays. An annotation includes an annotation ID, object/view/Canvas IDs and URIs, selector geometry, source/mapping version, note text, curator identity or label, creation/update times, and review status. Rectangles and polygons are notes about a region; they do not alter source images. There is no visual recognition in the MVP.

For exchange, model the target as a Web Annotation SpecificResource whose source is the selected Canvas. Emit rectangles as a FragmentSelector using xywh in the declared Canvas frame and a conformsTo link to Media Fragments. Emit polygons as an SvgSelector whose geometry uses the same Canvas frame. Preserve the canonical geometry independently of display zoom, pane size, flip, or rotation. Keep version-specific Presentation 2.1.1 Open Annotation input parsing separate from this W3C-compatible output form.

Provide keyboard operation for selecting a view, creating/editing a region, entering rectangle coordinates numerically, creating polygon vertices, editing notes/status, and exporting. Pointer-only drawing does not satisfy the plan. Visible focus, accessible names, status announcements, and rights discoverability are acceptance requirements.

### P3 — Review package, rights, and source changes

Export a versioned application-owned ZIP with review.json, package/revision lineage, object/view/Manifest/Canvas/image-service identifiers, source observations, rights metadata, annotation records, review state, and optional allowlisted thumbnails. Never include partner image bytes, partner crops, or screenshots. Include a thumbnail only for a local image explicitly marked institution-owned/cleared. Local upload retention and storage require a separate institutional decision; neither local nor remote bytes are silently added to the review service.

On reopen, report each source as available, unavailable, possibly changed, or access denied. Keep notes and annotations visible and attached to their original Canvas/source even if the image cannot load. A local missing source may be reattached by matching an explicit local hash or curator confirmation, never filename alone.

Compare provider IDs, Manifest/Canvas/image URIs, dimensions, and any provider version signal. A URI or dimension change may be reported as changed; an unchanged URI and dimensions without a version/content signal are only “not detected as changed,” not proof that pixels are unchanged. Do not fetch/hash remote image bytes to resolve this uncertainty. Keep rights and requiredStatement attached to the correct object/view. Whether annotation text, metadata, and partner URIs may be exported is an institutional policy decision before release.

### P4 — Institutional storage and revisions

The institutional service stores package metadata, annotation/review records, and their revisions; partner image bytes are not proxied or stored. Local upload retention can be enabled only under a separate institutional policy for owned/cleared assets.

Assign package and revision IDs with parent revision IDs. Store each annotation and review-state change as a revision with author attribution. Importing divergent descendants creates a conflict view that retains both histories and displays field and geometry differences. A curator explicitly chooses or edits a resolution; the service preserves previous versions. No silent last-write-wins and no live simultaneous editing.

Before implementation freeze, decide whether attribution comes from institutional login or a curator-entered label, and define how authorship and imported revision ancestry are represented.

### P5 — Components, alternatives, usability, and performance

Carry OpenSeadragon v6.1.1 at commit 201d47833e3f10e9fa55159cd4203630521926b8 as the provisional image-viewer candidate. Its captured tag object points to that commit, but its tag is unsigned and its release is not marked immutable. The pinned source and release notes support image-service/overlay review; they do not establish signed release provenance or complete application compatibility.

Keep an app-owned, versioned Presentation adapter for the subset selected in P1. Keep application annotation records W3C-compatible, with desk-only review/status fields represented as named extensions. The app owns Canvas mapping, polygon drawing/editing, keyboard workflow, persistence, rights behavior, package format, and conflict resolution.

Keep Mirador 4 as a serious full-viewer alternative. Its admitted homepage advertises multi-window viewing, zoom, compare, annotate, and plugin extensibility. Before selection, compare it with the OSD-plus-adapter option using the same Canvas-mapping, package, revision-conflict, rights, accessibility, and source-failure witnesses. Exact Presentation/Image API version and authentication support are not established by the admitted homepage capture and need direct verification before making those claims.

Keep Universal Viewer as a narrower viewing/access alternative because its supplied homepage advertises Manifest viewing, OpenSeadragon zoom via IIIF Image API, embedding, and IIIF Auth. Require the same package, review, region-editing, and revision checks before treating it as a fit. Keep Annotorious as a conditional region-drawing option only; if considered, pin exact packages and verify its exact production-bundler integration and exported selectors. Its issue #599 is a warning for the reported environment, not a universal compatibility conclusion. Tropy remains an inspection analogy, not an implementation selection for this browser/shared-review workflow. Recogito remains unadjudicated due lack of admitted primary evidence.

Keep keyboard/focus operation, visible selection/status, requiredStatement discoverability, resize behavior, reduced-bandwidth behavior, and lazy loading in the MVP. Load only two full-resolution views at once. Curators must choose supported browsers, a realistic network profile, and the acceptable latency threshold before the 50-object low-bandwidth witness. This plan makes no speed claim.

### P6 — Proposed acceptance witnesses

All witnesses below are proposals, not executed checks.

1. **Manifest and identity:** Parse representative Presentation 2.1.1 and 3.0 Manifests for front/back/detail views. Verify stable Manifest/Canvas/service IDs, ordering, labels, rights, and requiredStatement. Include missing service data, invalid structures, alternate bodies, multiple painting bodies, offset placements, and unsupported selectors. Verify the adapter reports unsupported inputs without substituting a view.
2. **Canvas mapping and geometry:** Use local images and Image API 2/3 services with Canvas dimensions both equal to and different from source pixel dimensions. Include Canvas-size recipe style scaling, offsets, crop/clip, and multiple-body cases. Draw rectangles and polygons; round-trip through save/reopen and verify against known Canvas-coordinate points after resize, zoom, pan, rotation, and flip. Test the exact pinned OSD TiledImage conversion path and the app-owned SVG layer.
3. **OSD service and overlay cases:** Include an Image API info response with an empty sizes array, as named in the v6.1.1 release notes. Add an automated geometry regression witness for flip/rotation and readable overlay content associated with the #2546 fix. The historical PR demo is not the automated witness.
4. **Source failure and change:** Exercise unavailable, CORS-blocked, unauthorized, changed-Canvas-ID, changed-image-ID, changed dimensions, same-URI/same-dimensions replacement, and stable-Canvas/replaced-image scenarios. Verify honest state labels, no false certainty, no view substitution, and annotation retention. Exercise Authorization Flow only if selected for the release.
5. **Package and rights:** Export and reopen a partner view plus an allowed local thumbnail. Inspect the ZIP to ensure it contains no partner bytes, crops, or screenshots. Verify source identifiers, rights/requiredStatement, notes, revision lineage, and the institution’s export policy for annotations/metadata/URIs.
6. **Revision conflict:** Import two independently revised descendants of one package. Show both histories and field/geometry differences; require explicit curator resolution and preserve previous versions and attribution.
7. **Keyboard and low bandwidth:** Complete view choice, region creation/editing, status update, and export with keyboard only; verify focus, names, visible state, announcements, and rights discoverability. Run the agreed 50-object low-bandwidth profile with only two full-resolution views at once. Curators set the browser/network profile and latency threshold before running it.

No application build, application test suite, or interoperability test was run in the research, critic, or reviser roles. The seven witnesses are not results.
