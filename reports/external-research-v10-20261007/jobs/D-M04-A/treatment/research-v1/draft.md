# D-M04-A treatment research — bounded recommendation

## Recommendation

1. **Choose the write mode by whether the event will write.** For the single writer’s ordinary event-buffer write path, use a short explicit `BEGIN IMMEDIATE` → validate/apply database changes → `COMMIT` transaction. It requests the writer slot at the beginning, so contention is found before doing the write unit’s work. SQLite still permits only one simultaneous writer; WAL does not change that. Keep the transaction limited to database work, and do not sleep, call services, or await user work while it holds the writer slot. [S1, §2.1–2.2, lines 288–357; S2, lines 293–299]

2. **Deferred is reasonable when a transaction may stay read-only; its upgrade is a different failure point.** `BEGIN DEFERRED` does not acquire a transaction until first access. A first `SELECT` starts a read snapshot; a later write upgrades it if possible and otherwise can return `SQLITE_BUSY`. In WAL, if another writer has committed since that snapshot, SQLite 3.51.3’s `sqlite3WalBeginWriteTransaction` returns `SQLITE_BUSY_SNAPSHOT` and starts no write transaction. Do not retry that write against the same snapshot: roll back, re-read, and replay the entire logical unit only if it has no non-database side effects and is safe to repeat. [S1, lines 322–357; S4, lines 3681–3747]

3. **Treat WAL as a concurrency improvement, not a no-contention promise.** Verify the opened database’s actual mode with `PRAGMA main.journal_mode`; setting the pragma returns the resulting mode, and may return the original mode when a change fails. The local-disk, same-host case fits WAL’s shared-memory requirement. WAL lets readers and a writer generally proceed together, but still has one writer and can return `SQLITE_BUSY` in documented exceptional cases such as recovery or last-connection cleanup. Long readers can also prevent checkpoint completion and let the WAL grow even while writes proceed. [S3, lines 1208–1287; S2, lines 160–205, 293–318, 555–579, 672–711]

4. **Keep retries an application policy with a wall-clock bound.** A conservative starting policy to measure, not a SQLite guarantee: use one 100 ms busy timeout per connection, at most four lock-acquisition/commit calls, pauses capped at 25/50/100 ms with jitter, and a 1 s monotonic contention deadline (whichever limit comes first). Count time spent inside SQLite calls against the deadline; do not issue a call unless its configured wait fits the remaining budget. On exhausted `SQLITE_BUSY`, return a retryable failure/requeue signal rather than waiting indefinitely. `PRAGMA busy_timeout` installs the connection’s single busy handler and can overwrite a handler already installed, so choose one handler strategy deliberately. [S3, lines 576–588]

5. **Retry the operation that is safe to retry, and clean up before reuse.** If `BEGIN IMMEDIATE` returns busy, no write unit began: back off within the envelope and retry BEGIN. If COMMIT returns the documented reader-related `SQLITE_BUSY`, the transaction remains active; retry COMMIT on that same transaction, not the body. If its deadline expires, roll it back and report failure. For a deferred upgrade failure or a body error, explicitly roll back any still-active transaction, close/reset/finalize outstanding statements/cursors, then restart from fresh reads only when the operation is idempotent. Do not assume every error auto-rolls back. [S1, lines 378–395; S1, lines 330–342; S4, lines 3681–3747]

6. **Useful alternative and discriminating checks (proposed only).** Keep DEFERRED for conditional paths that often remain read-only; it avoids reserving the sole writer slot for those paths, at the cost of a possible failed upgrade and full restart. Compare it with IMMEDIATE using the same event workload on SQLite 3.51.3 and a local database: hold writer A while B begins, measure B’s bounded wait and verify no partial insert; then test DEFERRED by having B read, A commit, and B attempt its write, verifying rollback plus a fresh read/replay and exactly one row via a stable event ID. In WAL mode, hold a long reader while writing and observe that writer commits can continue while checkpoint progress/WAL size stalls, then release the reader and verify progress resumes. Repeat with WAL unavailable/disabled to check the fallback path and actual-mode detection. These checks are proposals, not run results.

**Conditions and uncertainty.** Confirm the SQLite library actually is 3.51.3 and inspect the binding’s handling of primary/extended busy codes; the mapped sources establish WAL’s `SQLITE_BUSY_SNAPSHOT` path but do not specify every language binding’s error mapping. The timeout/attempt values above are initial operational limits to tune against measured queue latency and event size. Never retry a failed external side effect as though SQLite made it atomic.
