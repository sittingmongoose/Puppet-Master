# D-M04-A treatment recommendation

Use a short explicit `BEGIN IMMEDIATE` transaction for an event-buffer path that will write: acquire the writer position before doing the database work, then validate/apply and commit. Keep network calls, sleeps, and unrelated work outside the transaction. Use `BEGIN DEFERRED` for paths that may remain read-only, so they do not reserve the single writer slot unnecessarily. SQLite supports only one simultaneous writer. [sqltransaction, §§2.1–2.2, raw lines 288–357; sqlwal 293–297]

A deferred transaction does not begin database access until first use. If its first access is a SELECT, it holds a read snapshot; a later write must promote that transaction. In WAL mode, if another connection has committed since the snapshot, SQLite 3.51.3’s WAL code returns `SQLITE_BUSY_SNAPSHOT` and starts no write transaction. Do not retry the write against that same snapshot. Reset/finalize outstanding statements, roll back, re-read, and replay the whole logical unit only if it is safe and idempotent and has no external side effects. [sqltransaction 330–342; sqlwalcode 3681–3737; supplemental sqlresultcodes 915–935]

Treat WAL as conditional. On the opened database, query `PRAGMA main.journal_mode`; when setting a mode, use the returned mode because SQLite returns the original mode if it could not change it. WAL permits readers and a writer to proceed concurrently but still allows only one writer. It requires all processes accessing the database to be on the same host. Long readers can prevent checkpoint completion and allow the WAL to grow. WAL mode can still produce BUSY during recovery, exclusive-lock situations, or last-connection cleanup. If WAL is not active, follow the actual journal mode’s behavior; rollback-mode readers can make COMMIT return BUSY. [sqlpragma 1214–1224; sqlwal 166–180, 293–318, 555–579, 672–705; sqltransaction 378–389]

Keep retry behavior in the application. As an initial policy to measure, configure one 100 ms busy timeout per connection, allow at most four total lock-acquisition/COMMIT calls, use pauses capped at 25/50/100 ms with jitter, and enforce a 1 s monotonic deadline. Count time inside SQLite calls; do not start a call unless its configured wait fits the remaining budget. Return a retryable/requeue result when the budget expires. `PRAGMA busy_timeout` sets the connection’s single busy handler and can replace an existing handler. These values are not SQLite guarantees. [sqlpragma 576–588]

Classify failures by phase. If `BEGIN IMMEDIATE` is BUSY, the write body has not started; retry acquisition within the budget. If a reader-related COMMIT is BUSY and the transaction remains active, retry COMMIT on that transaction rather than rerunning the body. The mapped transaction manual documents that behavior, but the supplemental live result-code page says a successful BEGIN IMMEDIATE prevents later BUSY through COMMIT; its broad wording is not pinned to 3.51.3. Resolve that scope against the deployed build and actual journal mode. `SQLITE_LOCKED` is different: it signals a same-connection or shared-cache conflict, not ordinary contention from a separate connection. Release/reset/finalize the conflicting cursor or statement, resolve the conflict, and classify again; do not feed LOCKED into the BUSY retry loop. Confirm whether the binding exposes extended result codes such as BUSY_SNAPSHOT. [sqltransaction 378–389; supplemental sqlresultcodes 171–184, 399–453]

After a body error or failed deferred promotion, clean up before reuse: reset/finalize outstanding statements, explicitly roll back if a transaction is still active, and discard/reopen the connection if its state cannot be established. Never assume every error automatically rolls back. Retry a whole unit only from fresh reads and only when replay is safe. [sqltransaction 330–342, 378–395]

**Alternative and proposed discriminating checks (not run).** Keep DEFERRED for paths that usually stay read-only. Compare it with IMMEDIATE on SQLite 3.51.3 using a local database: hold writer A while B begins and verify bounded acquisition/no partial insert; then let B read, let A commit, and verify B’s attempted promotion fails, rolls back, rereads, and leaves exactly one row for a stable event ID. Repeat a long-reader/checkpoint case in WAL and confirm writer commits proceed while checkpoint progress stalls, then resumes after the reader closes. Run the same contention case with WAL unavailable/disabled and query the actual mode. This will discriminate the COMMIT-BUSY documentation tension and the fallback behavior.

**Conditions.** Confirm the deployed library is 3.51.3, actual journal mode, process placement, and binding error-code mapping. The retry envelope is a starting application policy to tune against measured queue latency and event size; SQLite documents locking outcomes, not this retry schedule. Do not retry external side effects as if they were atomic.
