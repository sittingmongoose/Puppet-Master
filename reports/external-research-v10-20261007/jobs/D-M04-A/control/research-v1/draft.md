# D-M04-A bounded research draft

## Recommendation and material findings

1. **Verify the journal mode before relying on WAL behavior.** Query `PRAGMA main.journal_mode` on the database connection and proceed with this WAL-specific policy only when the returned mode is `wal`; if the requested change did not take, SQLite returns the original mode. The brief’s local-disk, one-writer setup fits WAL’s same-host shared-memory requirement. WAL lets readers and a writer proceed concurrently, but it still permits only one writer at a time. [PRAGMA documentation, §journal_mode](https://www.sqlite.org/pragma.html) (capture lines 1208–1227); [WAL documentation, advantages and concurrency](https://www.sqlite.org/wal.html) (lines 166–169, 267–300).

2. **Use `BEGIN IMMEDIATE` for a unit known to write.** It requests the single-writer slot at the start, before the application does work that would need to be discarded on an acquisition conflict; it can return `SQLITE_BUSY` while another writer is active. Keep the transaction short and avoid network calls, user waits, or unrelated work while holding it. Reserve `BEGIN DEFERRED` for read-only work or cases where a write is genuinely optional: deferred does not acquire a transaction until first access, and a first SELECT starts a read transaction. [Transactions, §2.2](https://www.sqlite.org/lang_transaction.html) (lines 322–353); [WAL source tag 3.51.3](https://raw.githubusercontent.com/sqlite/sqlite/version-3.51.3/src/wal.c) (lines 3690–3734).

3. **Treat read-to-write upgrade as a restart boundary.** A deferred read transaction keeps its historical snapshot. If another connection commits after that snapshot and before the upgrade, the write can fail; the 3.51.3 WAL implementation returns `SQLITE_BUSY_SNAPSHOT` when it obtains the writer lock but detects that the WAL index header changed since the read began. Waiting and retrying only the failed statement inside that stale transaction cannot refresh the snapshot. Roll back, then retry the complete logical transaction from a new read snapshot, subject to the application safety rule in finding 4. [Transactions, §§2.1–2.2](https://www.sqlite.org/lang_transaction.html) (lines 293–307, 332–342); [wal.c](https://raw.githubusercontent.com/sqlite/sqlite/version-3.51.3/src/wal.c) (lines 3690–3734).

4. **Keep retry policy in the application and bound it.** SQLite serializes writers and reports conflicts; it does not promise the caller’s whole operation will eventually succeed. Set one request-level deadline and attempt cap, use bounded backoff with jitter for transient writer-acquisition `SQLITE_BUSY`, and stop when the deadline is reached. Retry a whole transaction only when its database effects are atomic and repeating the logical operation is safe; move external side effects after commit or make them independently idempotent. The connection has only one busy handler: `PRAGMA busy_timeout` sets it and may overwrite a previously installed handler, so choose a single timeout/handler arrangement and do not count both mechanisms as independent guarantees. [WAL documentation, §9](https://www.sqlite.org/wal.html) (lines 672–706); [PRAGMA busy_timeout](https://www.sqlite.org/pragma.html) (lines 576–588).

5. **Clean up according to the failure point.** If `BEGIN IMMEDIATE` fails, do not run the transaction body. If a deferred upgrade fails, roll back before restarting from a new snapshot. For other errors, check whether the transaction is still active and explicitly roll it back before reusing the connection; SQLite documents that manual transactions normally persist until COMMIT/ROLLBACK, with specified exceptions. A busy COMMIT is different from a failed body: the transaction documentation says that in its documented busy case the transaction remains active and COMMIT may be retried after the reader clears—retry COMMIT, not the body. If state or rollback is uncertain, retire the connection rather than leak an open transaction. BEGIN transactions do not nest; use SAVEPOINT/ROLLBACK TO/RELEASE for a genuine nested unit. [Transactions, §§2 and 2.3](https://www.sqlite.org/lang_transaction.html) (lines 248–288, 378–386).

6. **WAL reduces, but does not remove, contention; long readers have a separate cost.** WAL’s documented `SQLITE_BUSY` cases include exclusive locking mode, last-connection cleanup, and recovery after the last connection crashed; applications should be prepared for them. Separately, a long-running reader can stop a checkpoint at its end mark, delaying checkpoint progress and allowing the WAL to grow. Close cursors and end read transactions promptly; monitor checkpoint progress/WAL size if readers are long-lived. The mapped sources do not establish a retry rule for `SQLITE_LOCKED`; preserve the exact primary and extended result code and diagnose that path instead of automatically treating every “busy/locked” result alike. [WAL documentation, §§2.2 and 9](https://www.sqlite.org/wal.html) (lines 267–321, 672–706).

## Useful alternative

For a workload with many competing write requests, serialize write intents through one bounded application queue and keep database write transactions short. This trades some queue latency/head-of-line blocking for fewer simultaneous database contenders. For workloads where most deferred transactions remain read-only, retaining DEFERRED avoids reserving the writer slot unnecessarily; any read transaction that later needs a write must still be prepared to roll back and restart after an upgrade/snapshot conflict.

## Proposed discriminating checks (not run)

- With WAL confirmed and two independent connections, hold a deferred read snapshot on A; let B write and commit; then attempt A’s write. Record primary and extended result codes, prove that restarting A’s whole transaction sees B’s commit, and compare with a competing `BEGIN IMMEDIATE` that fails before its body runs.
- Hold A’s long read while B writes and checkpoints. Verify checkpoint progress stops at A’s end mark, resumes after A ends, and capture WAL size and latency. This distinguishes write-lock contention from checkpoint starvation.
- Configure the connection’s busy handler/timeout once, induce writer contention, and measure total wall time against the application deadline. Exercise a `SQLITE_LOCKED` path separately and verify it is logged/classified rather than silently entering the `SQLITE_BUSY` retry loop.
- Inject a transaction-body error after a write; verify rollback leaves no partial database change and the connection can begin a fresh unit. If COMMIT returns busy in the supported mode, verify transaction state and retry only COMMIT.

## Conditions and uncertainty

This is a recommendation for the brief’s local-disk, one-writer, long-lived-reader workload and SQLite 3.51.3 implementation. WAL requires the participating processes to be on the same host; do not carry this policy to a network filesystem. The transaction, WAL, and PRAGMA pages are capture-pinned public documentation, not immutable 3.51.3 documentation. Implementation-specific snapshot evidence is limited to the version-3.51.3 `wal.c` capture. The proposed checks are design proposals, not executed results. Cold acquisition read the supplied local bytes (network_requests=0); this does not measure or claim Internet download savings.
