# D-M04-A bounded recommendation

## Recommendation

**Confirm the active journal mode before applying WAL assumptions.** Query `PRAGMA main.journal_mode`; use the WAL-specific expectations below only when it returns `wal`. If a requested mode change fails, SQLite returns the original mode, so do not assume a requested switch took effect. WAL requires all participating processes to use the database on the same host. ([PRAGMA capture, lines 1208–1227](https://www.sqlite.org/pragma.html); [WAL capture, lines 160–177](https://www.sqlite.org/wal.html))

For a transaction known to write, prefer **`BEGIN IMMEDIATE`**. It starts a write transaction up front and can return `SQLITE_BUSY` if another writer is active. Keep the transaction short; do unrelated or externally visible work outside it. Use **`BEGIN DEFERRED`** for read-only work or when writing is truly optional. DEFERRED starts on first database access: if that access is a SELECT, the connection holds a read snapshot, and a later write must upgrade it. SQLite allows multiple readers but only one writer. ([Transaction capture, §§2.1–2.2, lines 293–352](https://www.sqlite.org/lang_transaction.html); [WAL capture, lines 296–303](https://www.sqlite.org/wal.html))

**Treat reader-to-writer upgrade as a restart boundary when the snapshot is stale.** In WAL mode, the 3.51.3 implementation returns `SQLITE_BUSY_SNAPSHOT` if it obtains the writer lock but finds that another connection changed the WAL-index header after this read snapshot began. Retrying the failed write inside that old transaction cannot refresh its view: roll back, then replay the complete database-only transaction from a new snapshot if the logical operation is safe to repeat. A plain `SQLITE_BUSY` while another writer holds the single writer slot is a distinct acquisition conflict; do not label every busy result a stale-snapshot error. ([Transaction capture, lines 293–307 and 332–352](https://www.sqlite.org/lang_transaction.html); [SQLite 3.51.3 `wal.c`, lines 3688–3734](https://raw.githubusercontent.com/sqlite/sqlite/version-3.51.3/src/wal.c))

Keep retries in the **application policy**: set one request deadline and attempt cap, and use bounded backoff (with jitter if useful) for transient writer-acquisition conflicts. Fit any SQLite busy timeout within that same request budget. Each connection has one busy handler; setting `PRAGMA busy_timeout` may replace an existing handler. SQLite serializes writers and reports conflicts; it does not guarantee the caller's whole operation will eventually succeed. Retry the full logical operation only if its database effects are atomic and replay is safe. Move external side effects after commit or make them idempotent. ([PRAGMA capture, lines 576–588](https://www.sqlite.org/pragma.html))

WAL lets readers and a writer proceed concurrently, but it does not remove all `SQLITE_BUSY` cases. The WAL documentation lists exclusive locking mode, last-connection cleanup, and recovery after a crash. A long reader can also hold an end mark that stops a checkpoint from advancing; that delays checkpoint progress and may let the WAL grow, even though the reader normally does not block the writer. End read transactions and cursors promptly; monitor checkpoint progress and WAL size for long-lived readers. The mapped sources do not establish a retry rule for `SQLITE_LOCKED`: preserve the exact result codes when exposed by the binding and diagnose that condition separately instead of sending every “busy/locked” result through one retry loop. ([WAL capture, lines 266–312 and 681–706](https://www.sqlite.org/wal.html); [Transaction capture, lines 355–369](https://www.sqlite.org/lang_transaction.html))

## Failure cleanup and alternative

If `BEGIN IMMEDIATE` fails, do not run the body. Manual transactions normally persist until COMMIT or ROLLBACK, but some errors may roll back automatically; inspect transaction state (for example, with `sqlite3_get_autocommit()` or `sqlite3_txn_state()`) and roll back before reusing an active connection. Retire it if cleanup or state is uncertain. If COMMIT returns `SQLITE_BUSY` and the transaction remains active, retry COMMIT only; never replay the body. The transaction page documents a reader-blocked COMMIT case, but WAL readers normally do not block writers, so do not assume that is the cause in WAL mode. Use SAVEPOINT/ROLLBACK TO/RELEASE for nested work; BEGIN transactions do not nest. ([Transaction capture, §§2, 2.3, and 3, lines 248–288 and 378–438](https://www.sqlite.org/lang_transaction.html); [WAL capture, lines 166–169 and 296–303](https://www.sqlite.org/wal.html))

One useful alternative for many competing writes is a **bounded application write queue**. It serializes write intents before they contend inside SQLite, trading some queue latency and head-of-line blocking for fewer simultaneous writer attempts. Keep DEFERRED for work that is likely to remain read-only; any later write still needs the upgrade/restart handling above.

## Proposed discriminating checks — not run

- With WAL confirmed, hold a DEFERRED read snapshot on connection A; let B write and commit; then attempt A's write. Capture the primary/extended result, roll back A, and confirm a fresh transaction sees B's commit. Compare with a competing IMMEDIATE begin and verify its body did not run when acquisition failed.
- Hold A's long read while B writes and checkpoints. Record checkpoint progress and WAL size, then end A's read and observe whether progress resumes. This separates writer-lock contention from checkpoint delay.
- Induce writer contention and compare total time with the application deadline and configured busy handler. Separately induce a `SQLITE_LOCKED` path and verify it is classified by its exact code. These are proposed checks, not executed witnesses.

## Conditions and uncertainty

This recommendation assumes the brief's local-disk, single-host workload and SQLite 3.51.3. The transaction, WAL, and PRAGMA sources are mutable documentation captures dated 2026-10-07; their full hashes, source identities, and read ranges are in `sources.json`. The version-tagged `wal.c` capture supports the implementation-specific `SQLITE_BUSY_SNAPSHOT` statement. The loaded library version was not independently checked, and the mapped sources do not settle a `SQLITE_LOCKED` retry policy. Cold acquisition read the supplied frozen local bytes (`network_requests=0)); this is not an Internet-download measurement or savings claim.
