# C-01 — Community telescope notebook: research and planning proposal

**Status:** planning proposal for the hypothetical club in the frozen brief. It proposes a bounded first workflow; it does not claim a product exists, validate astronomy data, select a deployment host, or establish that every camera format can be previewed. Source IDs below resolve to captured bytes and access metadata in `source-map.json`.

## Recommendation

Plan a small, club-controlled web review service with a local intake queue for field notes and removable-media files. Keep publication and the shared record centrally authoritative. Let volunteers prepare a session and assemble an import while offline; upload later with a resumable transfer; review metadata and previews before making selected items club-visible. Preserve each upload and processing result as a separate version. This fits the stated “offline entry, later collaborative review” need with less operational work than peer-to-peer multi-writer synchronization.

Use internal UUIDs for sessions, import batches, assets, asset versions, annotations, and members. Use SHA-256 to identify the bytes of each file version and to check transfer integrity. A digest can suggest identical bytes; it cannot establish that two files represent the same observation. Preserve duplicate-looking imports as separate records until a member confirms their relationship. Preserve original filenames and paths as submitted metadata, never as record keys.

A session record holds its planned target label and member-supplied notes as claims. An import batch holds an ordered list of per-file items and status. A file version holds digest, byte length, detected media type and detection method, source filename/path, ingest actor/time, and raw metadata. Keep parsed metadata beside the original value with its source, parser/version, parse status, precision, and applicable unit/time-scale. Leave values opaque where the source does not establish units or interpretation. FITS 4.0 defines time keywords and advises explicit time scale; `DATE-OBS` normally refers to the observation start, while comments and other time scales can change interpretation. `TIMESYS` supplies time-scale context and defaults to UTC when absent in the defined cases ([S17], FITS §§4.4.2, 8.3, 9.2). Keep the exact header text and flag ambiguous or unsupported values for review. A parsed value remains supplied data, not a scientific validation.

Represent processing as a provenance graph: an original version may have zero or more derived versions, each with parent asset/version, tool and version, transformation parameters, operator, and time. Generate previews only through a format adapter with an explicit support matrix. Start with a small set of common display formats; retain other originals and show a useful “preview unavailable” state until a decoder/conversion path is selected and validated. A FITS stretch, rotation, crop, or color mapping is a derived interpretation. Record it and retain the input bytes. Bound converter CPU, memory, and output size.

### Ingest and recovery

Use a local spool that retains source files and a simple manifest until the server confirms receipt. Create a batch and file-item IDs before transfer. Show per-file states such as `copied`, `hashing`, `queued`, `uploading`, `paused`, `transferred`, `integrity-check`, `needs-review`, `preview-ready`, `published`, and `failed`; include a human-readable cause and a retry action. An interrupted copy or upload stays resumable. Keep removable media intact until the club copy is verified.

The tus 1.0.0 protocol defines `Upload-Offset` and `Upload-Length` in bytes. A client can ask the current offset with `HEAD`, resume using `PATCH`, and must handle `409 Conflict` when its offset is stale ([S01], §§Headers, HEAD, PATCH). The `tusd` reference server v2.10.1 (release 2026-09-16, commit `388a27cb81c33b2349e0308b5e97e23797e86fd9`) implements offset checks and limits in `PatchFile`; its create path also validates maximum size ([S02], lines 334–345, 734–829, 892–980, 1430–1444; [S38]). The protocol resumes bytes; it does not decide whether an application record is complete or verify that the intended source file was selected. After transfer, recompute the full file digest on the server, compare it with the local manifest, commit object and metadata state atomically, and only then mark the item ready for review. Treat lost responses idempotently by batch/item ID.

Implementation history is relevant. tusd issue #1320 reports a request-header race with asynchronous hook processing against v2.8.0; PR #1337 cloned the header and added race/isolation tests, then merged in January 2026 ([S07], [S08]). The captured v2.10.1 code includes that clone and the tests ([S04], [S05]). Issue #1386 reported a maximum-size bypass through an opt-in IETF draft path. PR #1397 and the v2.10.1 release record the fix ([S09], [S24], [S38]); keep the experimental draft disabled for this first design, set application-side size limits, and verify the chosen tus server/storage adapter. v2.10.1 also lists a deferred-length S3 truncation fix; this is a reason to test the exact adapter and upload mode. No upload test was run for this assignment.

### Annotation, identity, visibility, and editing

Treat each preview as an immutable derived asset with its own version ID and digest. Attach a region to that exact preview version, with a declared coordinate frame: `xywh=pixel:x,y,w,h` in the selected preview’s pixel dimensions, origin at its upper-left, x increasing rightward and y downward. Keep the preview file or a reproducible derivative record available with the annotation. The Web Annotation model supports a target resource plus a selector; Media Fragments defines pixel and percentage `xywh` forms ([S13], §4.2; [S14], §6.1.2). Pixel coordinates avoid percent-to-pixel rounding for a fixed preview. Store author, created time, revision, text, and edit history. If a new process creates another preview, keep old annotations on the old target and mark them “review against new version”; never silently move a region. Offer explicit member-confirmed remapping later if the club has validated an image-registration workflow. Do not assign sky coordinates or infer scientific classifications in the first scope.

Use invite-only club identities and coordinator/member roles. Draft session notes and unpublished imports default to private to their owner. A publication action explicitly chooses the records and images made club-visible. Apply access checks to records, previews, original downloads, and exports; protect local pending drafts on shared devices; keep raw storage paths private. Keep the club-visible packet separate from a member’s private working copy.

Use a server-issued revision token for mutable session fields. A client update includes the revision it read; a stale write returns a conflict while preserving both the server version and the local draft for review. HTTP `If-Match` with strong entity tags is a standard conditional-update mechanism; a failed precondition yields `412 Precondition Failed` ([S20], §13.1.1). Independent comments append as separate records. Edits to the same note or annotation create a new revision and use a three-way compare or an explicit member choice. The activity view should say who changed what and when. This gives predictable recovery without silently replacing a concurrent edit.

### Withdraw, erase, and handoff

Define two coordinator actions. **Withdraw** immediately removes club access and prevents new exports. **Erase** deletes hosted originals, derivatives, previews, annotations, and local pending copies within a declared retention process; record only a minimal non-sensitive deletion tombstone if the club needs an audit trail. The policy must state how backups expire and what happens to already downloaded packets: the service cannot recall copies members have already received. The retention interval and who may authorize erasure remain club decisions because the brief supplies no duration or ownership rule.

Export a selected-session snapshot as a directory package with `README`, a versioned `manifest.json`, selected original and derived files, annotation/revision JSON, and provenance links. Use stable IDs and relative paths; include the exact preview bytes targeted by each region. Wrap payload files in BagIt 1.0 with a SHA-256 manifest and verify the manifest after export/import. BagIt specifies payload layout and checksum validation, while explicitly leaving payload meaning to the application ([S15], §§1, 2.1.3, 2.4, 3). Add the app manifest for observation/session meaning and annotation targets. RO-Crate 1.3 is an optional richer JSON-LD provenance profile if members later need an ecosystem-readable graph ([S16], current specification sections “Provenance of entities” and “Data Entities”). The astronomy-specific OpenAstronomyLog 2.1 ecosystem is another optional mapping: the public Observation Manager listing reports OAL 2.1 compatibility, FITS support, and HTML export ([S18], [S19]). Audit the actual schema before claiming it can represent versions, annotations, access state, or this full provenance graph. The public feature list is a discovery lead, not an implementation audit.

## Mechanism comparison and decision

| Mechanism | Fit to this brief | Benefits | Costs and limits | Decision |
|---|---|---|---|---|
| Central record with local intake queue, resumable upload, immutable file versions, and revision-checked edits | Offline session entry and later shared review; one place to manage membership, visibility, and packet export | Simple publication boundary; retries and integrity checks are observable; one current club record; fewer peer-sync and backup responsibilities | Remote review depends on a reachable club-controlled host; an administrator owns backups, access, and retention; drafts on disconnected devices are not immediately shared | **Choose for the minimum workflow**, subject to a hosting/maintenance decision. A single club-managed host and disk-backed storage minimize service lock-in; no account or purchase is selected here. |
| Local-first multi-writer records using Yjs shared types, local persistence, and a sync provider | Strong offline access and concurrent editing across disconnected clients | Updates are documented as commutative, associative, and idempotent; Yjs is network-agnostic and can merge supported shared types ([S35], [S36]) | A provider, local persistence, access control, blob replication, revocation, backup, and deletion semantics remain application work. Concurrent text convergence does not make application records or annotation targets semantically correct; replicated copies complicate erasure. | **Defer.** Revisit if offline collaboration itself becomes the main requirement. If evaluated, pin a stable release and test the exact schema/provider. |
| Portable packet as the primary exchange model | Move selected sessions between members or systems without a permanent commercial account | BagIt checks transfer integrity; a JSON manifest can explain IDs, versions, sources, and annotation frames | Manual import/export and conflict handling are awkward for regular collaborative edits; packages do not provide shared identity or revocation | **Keep as an exit/handoff path**, not the live collaboration database. |

Yjs provides a useful history check for the deferred option. v13.6.29 had a deep-observer `currentTarget`/`path` regression (issue #768). The maintainer closed it with v13.6.33 on 2026-09-23; that release changes when the observer target is set and adds `testDeepEventPathsWithMultipleDeepObservers` ([S12], [S23], [S26], [S29], [S33], [S37], [S39], [S40]). The exact stable tag targets commit `9ea3a4fb57b814292ce18dfd13c4f422e44e6c5c`, with fix commit `713a2895e78d13dd6cc257fdd4d46dbdec6d4fa7`. This test addresses event-path behavior; it does not establish suitability for this app’s note, image, permission, or deletion model.

## Observable validation proposal (not executed)

1. **Identity and metadata:** import two byte-identical files under different names and two different files for one session. Confirm stable records, exact hashes, no automatic observation merge, and a reviewable raw-versus-parsed metadata display. Include FITS with `DATE-OBS` and `TIMESYS` variations plus missing/ambiguous values; verify the stored time-scale and “needs review” behavior.
2. **Ingest recovery:** interrupt a local copy and a large upload at known byte offsets; restart the app and process; verify the source remains intact, tus `HEAD` reports the saved offset, stale offsets return a conflict, retries do not duplicate records, and the server digest matches before review status appears. Test chosen disk/object adapter, size limits, and lost responses.
3. **Preview provenance and regions:** run supported files through the declared preview pipeline; verify original bytes are unchanged and preview records include tool/version/parameters. Place rectangles at edges and interior points; round-trip `xywh` against the exact preview dimensions. Reprocess a file and confirm old annotations remain on the old preview and show a review-needed state.
4. **Concurrency and access:** two members edit one session note from the same base revision; confirm one update succeeds, the stale update is retained as a draft, and a visible compare/merge resolves it without data loss. Confirm independent comments both remain. Attempt direct preview, original, and export access as an unauthorized member; confirm drafts stay private and only explicitly selected items publish.
5. **Withdraw, erase, and export:** withdraw a shared item and verify new reads/exports are denied. Exercise the declared erasure and backup-expiry policy, documenting already downloaded packet limits. Export a selected session, verify BagIt checksums offline, reopen the manifest, and confirm each annotation resolves to the included preview version and each derivative points to its parent.

## Optional leads, unresolved decisions, and limits

- Measure actual file sizes, supported capture formats, device operating systems, and connectivity before selecting quotas, preview libraries, or hosting. No representative club files or performance run were available.
- Choose a club-controlled host and backup owner before inviting users. Remote collaboration needs network reachability; this research did not compare host prices or buy a service.
- Set a retention duration and erasure authority with members before importing private material. The brief does not establish ownership or legal requirements.
- Consider OAL 2.1 import/export for conventional observing-log fields; consider RO-Crate 1.3 only if collaborators need a richer exchange graph. Keep a plain JSON manifest readable without either standard.
- Consider a local-first CRDT only after testing user-visible semantics, persistence, identity/revocation, large binary handling, restore, and deletion on the exact selected versions. Yjs code/docs prove its update model, not end-to-end app behavior.
- No image decoder, FITS transformation, host, database, account, retention duration, astronomy ground-truth source, application code, or WorkNode was selected or tested. Public product listings and standards do not establish that the club’s actual files are valid or scientifically accurate.

## Claim review and unresolved objections

**Checked:** the frozen brief and PLAN bytes match their input-map SHA-256 values; source capture hashes are in `source-map.json`; source pins and release records were checked against public tag/release metadata. tus offsets and lengths are byte counts. FITS time semantics are bounded by the header/time-scale context. Web Annotation/Media Fragments identify resource and selector roles. BagIt verifies manifest checksums. The v13.6.33 Yjs fix and regression test address the cited deep-event path case.

**Repaired during research:** an initial interim inspection saw tusd v2.9.2 and Yjs v13.6.32. Current release API/tag checks identified tusd v2.10.1 and Yjs v13.6.33 instead. Final version conclusions use the latter releases; the older captures are marked superseded in the map.

**Unresolved:** no independent runtime reproductions were run; no file-format matrix, storage adapter, hosting target, retention interval, conflict interface, or private-draft threat model was validated. The Yjs regression is fixed in v13.6.33, but that alone does not support selecting Yjs for this workflow. The existing Observation Manager/OAL listing was used as a discovery analogy; its full code and schema were not audited. Proposed validation above remains outstanding.
