# C-01/control/reviser-v1 — integrated research and planning proposal

**Status:** Final research/planning proposal for the hypothetical club in the frozen brief. This recommends a bounded workflow and conditional architecture; it does not establish the truth of observations or metadata, validate a decoder, choose a host, or report a product test. Public-source IDs below resolve to fresh captures and exact locators in source-map.json.

## Recommendation and decision gate

Plan a **private local intake queue plus a club-controlled review service with explicit publication**, but make the host/operator decision a gate, not an assumed fact. This supports session entry away from connectivity and later shared review. It does not offer shared review while offline. Before selecting it, the club must identify a volunteer willing to operate a reachable service, accounts, storage, backups, updates, access rules, and deletion. No costs, hosting arrangement, or available connectivity were supplied, so affordability and maintainability are unverified.

If the club declines that operating burden, run a packet-based pilot: prepare a session and local files, then hand selected packets between members for review. This avoids a permanent service, but cannot provide a single current shared record, immediate revocation, or easy concurrent editing. Defer live collaboration until the club chooses an operator or revises its requirements.

For the service option, preserve uploaded originals, make each preview or processed rendition a separate immutable version, keep private drafts until an explicit publish action, and export selected sessions as portable packages. Treat all observation fields and member annotations as claims. Do not add telescope control, precision reduction, inferred sky coordinates, event prediction, or public social networking.

## Open discovery and mechanism comparison

Discovery began from the user brief’s need to collect mixed session files, enter notes with weak connectivity, annotate images with other members, and carry data between devices. I searched public astronomy format/provenance sources, local photo-catalogue patterns, offline collaborative data, and replicated-document conflict behavior before comparing the frozen plan.

| Mechanism | Useful fit | Costs and boundary | Disposition |
|---|---|---|---|
| **Central review record plus private local queue and delayed upload** | One explicit club publication boundary; a coordinator can control membership, future access, recovery, and packet export. A local queue can retain work until reconnection. | Requires an operator and reachable host. The server must implement identity, authorization, metadata/provenance, visible conflict handling, storage limits, backups, and erasure. The queue is not shared review while disconnected. | **Preferred conditionally** if the club accepts a named operator and verifies device, file-size, and connectivity needs. Prefer a portable, self-hostable deployment if operationally feasible; no service or account is selected. |
| **Local-first multi-writer records using a CRDT, such as Yjs** | Each member can edit a local copy; document updates can later merge independent of delivery order. Yjs documents state updates are commutative, associative, and idempotent (S12). | A CRDT merges supported document operations; it does not decide whether files show the same observation, whether a region still applies after image processing, who may read copied data, or how binaries and revoked data are replicated. A sync provider, local persistence, publication rules, and deletion policy remain necessary. | **Defer** unless shared offline editing is a core requirement. If reconsidered, evaluate the exact provider, schema, persistence, authorization, and release together. |
| **Replicated JSON documents using CouchDB-style revision trees** | Database replicas can exchange changes after offline edits. Concurrent revisions can remain as leaf conflicts rather than being physically discarded. | A normal document read returns a deterministic winner without surfacing all conflicting leaves; callers must ask for conflicts, fetch leaves, and merge or present them. The Tropy project is a useful analogy outside direct astronomy competitors: its documentation describes a local desktop photo catalogue with metadata templates, notes, and export, while explicitly distinguishing it from a web application (S21). That supports the usefulness of a low-administration local catalogue pattern, not its suitability for FITS data or the club’s multi-member review. The IVOA Provenance Data Model is an optional astronomy-specific mapping lead if a real interoperability need emerges (S02); do not adopt a standards-shaped schema before the club’s actual data and export partners are known.

## Proposed records and ingest workflow

Use separate stable identifiers for **session**, **planned target label**, **import batch**, **asset**, **asset version**, **derived preview**, **annotation**, **member**, and **publication event**. Preserve submitted filenames and relative paths as descriptive input, never as database keys. SHA-256 plus byte length identifies a byte sequence and helps compare transfers; it does not establish observation identity, source authenticity, authorship, correctness, or safe deduplication. Keep identical-byte and renamed files as distinct import records until a member decides their relationship.

For each immutable version, retain original bytes and record digest, size, submitted name/path, ingest actor/time, detection result, and any parse status. Store raw supplied metadata separately from parsed interpretations. An interpreted field should carry source location, parser and version, status, precision, unit, and time scale where established. Preserve values as opaque strings when their units or interpretation are unknown. A parser succeeding is not a scientific validation.

FITS Standard v4.0 defines FITS structure and time-related keywords, including DATE-OBS and TIMESYS within the standard’s FITS scope (S01). Preserve raw header values beside parsed ones; do not apply FITS semantics to JPEG, RAW, or other unsupported inputs, infer a missing time scale, or assert that a supplied time or target is correct. Collect representative club files before fixing a supported format, metadata, size, or preview matrix. Preserve unsupported files and show “preview unavailable” until a decoder/conversion path is separately validated.

Create a local batch manifest and IDs before copying. Keep removable media intact until a complete club copy has been checked. Give each file a visible state such as copied, hashing, queued, uploading, paused, transferred, integrity-check, needs-review, preview-ready, published, or failed, plus cause and retry action. Retry by batch/item ID so a lost response does not create a duplicate record. Mark an item reviewable only after full transfer, a server-side digest comparison with the local manifest, and durable recording of metadata and object location. Recovery must account for disk-full, interrupted copy, interrupted transfer, process restart, and an object write that succeeded while the application response was lost.

The tus 1.0.0 protocol defines upload offsets and lengths in bytes; HEAD discovers the current offset, PATCH continues, and an offset mismatch is a conflict (S06). The pinned tusd v2.10.1 implementation at commit 388a27cb81c33b2349e0308b5e97e23797e86fd9 checks upload length and offset and applies MaxSize checks on create and body writes (S10, handler implementation at lines 334–345, 481–491, and 892–923). Issue #1386 reports a size-limit bypass only when the experimental IETF draft protocol is enabled; the issue says that mode is opt-in, and PR #1397 adds the limit check to that path with a regression test. Release v2.10.1 includes the fix (S07–S09). Therefore, keep the experimental path disabled in this proposal and test the exact selected server, mode, and storage adapter before relying on it. tusd’s per-upload limit is not a total club quota, authentication, authorization, transaction boundary, or proof that the chosen source file was uploaded. No upload or storage adapter was run here.

## Preview provenance and member annotation

Represent each processed image as a distinct derived asset version with parent version, tool/version, parameters, operator, time, and status. Preserve original bytes unchanged. Bound CPU, memory, output size, and accepted formats before any converter is selected.

A note/comment targets a stable session or asset/version. A rectangular selection targets an **immutable preview version**, not “whatever is displayed now.” Store the target preview ID and digest, its pixel dimensions, and a rectangle in the rendition frame as **xywh=pixel:x,y,width,height**. W3C Media Fragments defines pixel xywh as four integers with x=0,y=0 at the top-left of the image; percentage coordinates are a separate form (S04). W3C Web Annotation supplies a target plus selector model (S03). These standards define a representation, not correct behavior of the future UI. Convert user selection from displayed CSS coordinates into the exact selected preview’s pixel frame, with orientation/crop/rotation recorded. Do not mix viewport pixels, source sensor pixels, FITS WCS coordinates, and displayed-preview pixels. Do not assign sky coordinates in this scope.

Keep authorship, created time, edit revision, text, and history. When a new preview is produced, leave old regions on their original preview and show “review against new version.” Do not silently transform or remap them. A member may create a new annotation or explicitly confirm a remap only after a separately validated registration process.

## Identity, visibility, edits, and deletion

Use invite-only club identities and coordinator/member roles as a proposal, subject to the club deciding how accounts are created, removed, and recovered. Draft notes and unsubmitted imports default private to their owner. Publishing is an explicit event selecting session records, previews, and source files for club visibility. Enforce authorization on listing, metadata, originals, previews, derivatives, annotations, download links, and exports. Do not expose storage paths. Decide whether members share devices and how local queues are protected, logged out, and erased. No identity provider is selected.

For the central option, give mutable session fields a server revision token or strong ETag. A client submits the revision it read; reject a stale update and retain the submitting draft for comparison. RFC 9110 defines If-Match conditional request semantics and 412 Precondition Failed (S20). That rejects a stale write; it is not a three-way merge. Show both versions and require an explicit member choice or compare/merge action. Store independent comments as separate append-only records; editing a comment or annotation creates a new revision with actor and time.

For CouchDB-style replication, the 3.5 documentation explains that conflict leaves can coexist and that basic GET exposes the deterministic winner without necessarily revealing other leaves; clients must request and inspect conflicts before resolution (S19). The pinned 3.5.0 couch_db.erl code distinguishes all revision leaves and only returns conflict metadata when that option is requested (S24, lines 1823–1867 and 1926–1942). This reinforces that database convergence does not guarantee that volunteers see every edit. The code/docs were inspected, but no CouchDB-specific issue/fix history or runtime test was audited; keep this option deferred and reopen that diligence if it becomes a candidate.

Define two separate coordinator actions:

- **Withdraw:** immediately deny future club reads and prevent new exports.
- **Erase:** remove hosted originals, derivatives, previews, annotation history, and local pending copies under a declared retention process; document how primary and backup copies expire. Keep only a minimal non-sensitive deletion marker if an audit need exists.

Choose the retention interval, authorization to erase, backup expiry, and process for local pending copies before importing real member data. Neither server deletion nor membership revocation recalls a packet already downloaded by a member. State that limit and include only the selected material in each export.

## Portable handoff

Export a selected snapshot as a directory or archive with a human-readable README, versioned application manifest, stable IDs and relative paths, selected original and derived bytes, submitted and parsed metadata with provenance, annotation revisions, exact preview targets/dimensions, publication/privacy selection, and a SHA-256 payload manifest. Include payload checksums and verify the package offline after export and after re-import. BagIt v1.0 defines a payload directory and checksum manifests, and expressly leaves payload meaning to the application (S05). The application manifest must therefore explain the links and status; a valid checksum does not prove a correct observation or a safe disclosure.

## Observable validation proposal — not executed

1. **Club and format discovery:** survey member devices, operating systems, connectivity at the site, removable media, file sizes, and representative images/notes. Produce a support matrix. Confirm that unsupported files remain intact and are clearly unavailable for preview. Compare host/operator workload and cost with packet-only handoff before selecting deployment.
2. **Identity and metadata:** import identical bytes under different names, renamed duplicates, and distinct processed versions from one session. Confirm distinct stable records, accurate byte hashes, no automatic observation merge, and a reviewable raw-versus-parsed metadata display. Include supported FITS samples with missing/ambiguous DATE-OBS or TIMESYS; confirm source attribution and review status without claiming astronomical correctness.
3. **Ingest interruption:** interrupt local copy and network upload at known byte offsets; restart the client/service; retry after a lost response and stale offset; simulate disk-full and failed object persistence. Confirm source-media bytes remain unchanged, retry is idempotent, the resume offset is byte-accurate, stale offset is surfaced, server digest matches before review, and the actual size/quota controls work with the selected adapter and mode.
4. **Preview/annotation:** for each supported image type, verify original bytes are unchanged and preview provenance records tool/version/parameters. Place rectangles at corners and interior points; test viewport scaling, orientation, crop/rotation, and resize. Confirm saved coordinates round-trip against exact preview pixels and old regions remain attached to old preview versions after reprocessing.
5. **Conflict and access:** two members edit one note from the same revision while disconnected, then reconnect. Confirm no silent lost edit, both drafts remain inspectable, independent comments remain separate, and publication is explicit. Test lists, metadata, sources, previews, derivatives, annotations, and exports as owners, other members, coordinators, revoked members, and unauthenticated clients. Confirm private drafts never leak via indirect paths.
6. **Withdrawal, erasure, and handoff:** withdraw and erase private and published items; confirm future reads/exports are denied, primary copies and backups expire under policy, local queues are handled, and the documented limit on downloaded copies is accurate. Export a selected packet, validate payload hashes offline, re-import it, and confirm IDs, provenance, annotation targets, visibility selection, and included files.

## Evidence and execution boundary

Fresh captures were saved under sources/ and indexed with URL, UTC access time, exact release/commit where pinned, locator, response status, byte count, and SHA-256. I manually inspected the captured specifications, source files, issue/release pages, and patches; extracted relevant FITS standard text for static reading; and inspected the Yjs regression test and tusd fix test in the patch. These checks validate source retrieval and my reading of specified behavior only. No test suite, product build, upload, storage adapter, image conversion, UI, server, hosting account, or astronomy ground truth was run or selected. The source map records failed alternate capture URLs explicitly; none is used for an evidence claim.

The unresolved decisions are the service operator/host, operating cost, member/device access, identity lifecycle, retention period, backup expiry, erasure authority, representative file support, exact preview pipeline, total quota, and whether shared offline editing is worth distributed-sync complexity. Keep these conditions attached to the proposal until the club decides them.
