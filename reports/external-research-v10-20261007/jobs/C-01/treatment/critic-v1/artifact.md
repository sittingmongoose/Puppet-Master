## Evidence review, semantics, and critic repairs

### Image annotation and coordinates

The W3C Web Annotation Data Model supplies a way to express a body, target resource, attribution/lifecycle properties, and selectors; it includes `FragmentSelector` and `SvgSelector`. It is a representation model, not a service, access-control system, offline synchronization protocol, or guarantee that a selector continues to indicate the same content after the target changes. W3C Media Fragments defines image `xywh` with `x,y,width,height`; its pixel form refers to intrinsic image pixels with `(0,0)` at the image's top-left, and the standard also permits percentages. ([S01](https://www.w3.org/TR/2017/REC-annotation-model-20170223/) §§3.3, 4.2.1, 4.2.7, 4.3; [S02](https://www.w3.org/TR/2012/REC-media-frags-20120925/) §§4.2.2, 6.1.2, 7.1.)

**Proposed correction to A-P4:** store the rectangle against an immutable rendition ID and digest, dimensions, orientation/transform description, and explicit coordinate convention. The default can be integer `xywh=pixel:` coordinates in the displayed rendition, with top-left origin. A replacement, crop, stretch, rotation, or new processing version receives a new target; retain the old annotation and mark the new target “review required” until a person re-anchors it. Do not claim celestial meaning. A later WCS feature would need its own format/context-aware interpretation and expert validation.

I independently inspected OpenSeadragon v6.0.2 code, pinned to commit `7842cd92e6799d97c18227a79cb69af4f706b023` ([S12](https://github.com/openseadragon/openseadragon/commit/7842cd92e6799d97c18227a79cb69af4f706b023)). `Viewport.viewportToImageCoordinates` warns that it is inaccurate with multiple images and recommends `TiledImage.viewportToImageCoordinates`; it also has a single-image clipping caveat. The `TiledImage` methods convert through that image's coordinate frame and rotation. Their optional `current` argument matters: `true` uses the currently drawn location, while the default `false` uses the target location. Therefore, if a pointer is mapped while an image is animating, use the specific displayed `TiledImage` and current-state conversion, or wait until it settles; do not use a viewer-global conversion or treat screen/viewport coordinates as image pixels. ([S14](https://github.com/openseadragon/openseadragon/blob/7842cd92e6799d97c18227a79cb69af4f706b023/src/viewport.js), lines 1360–1394; [S15](https://github.com/openseadragon/openseadragon/blob/7842cd92e6799d97c18227a79cb69af4f706b023/src/tiledimage.js), lines 578–623.) This is API evidence, not a claim that our application would use this viewer or that an annotation UI has been tested.

The relevant history is narrow and traceable. Issue #2873 reports wrong `event.item` values and intermittent misplaced/missing images when multiple `addTiledImage` callbacks are drained in a batch; the reporter provides a reproduction and reports a difference between v6 and v5.0.1. PR #2874 changes `processReadyItems` to pass the queued `tiledImage` as `{item: tiledImage}`; the v6.0.1 release entry lists the multi-image fix, and the inspected v6.0.2 `src/viewer.js` contains the callback form. ([S16](https://github.com/openseadragon/openseadragon/issues/2873), [S17](https://github.com/openseadragon/openseadragon/pull/2874), [S21](https://github.com/openseadragon/openseadragon/pull/2874.diff), [S18](https://github.com/openseadragon/openseadragon/releases/tag/v6.0.1), [S13](https://github.com/openseadragon/openseadragon/blob/7842cd92e6799d97c18227a79cb69af4f706b023/src/viewer.js), lines 1947–1958.) ### Astronomy files and observation time

FITS is a standard for astronomical data products, not a promise that every member file will be FITS, contain one image, have usable WCS, or be interpreted correctly by a generic browser. FITS v4.0 states that the first image pixel has coordinates `(1.0, 1.0, ...)`; the W3C media-fragment pixel selector uses top-left `(0,0)`. These are different frames. If a future viewer connects them, define and test a conversion rather than copying FITS WCS numbers directly into a web selector. The FITS WCS material also distinguishes approved standard conventions from local/non-standard conventions. ([S03](https://fits.gsfc.nasa.gov/standard40/fits_standard40aa-le.pdf) §§8.2, 8.2.1; [S04](https://fits.gsfc.nasa.gov/fits_wcs.html).)

**Critic repair to the earlier time conclusion:** preservation of raw strings and uncertainty was right, but FITS v4 supplies more specific defaults that must be stated. For a four-digit-year `DATE-OBS`, the standard says the default interpretation is UTC for dates from 1972-01-01 and UT before; it says the value is expressed in the HDU's principal time system/scale, assumes it refers to the start of the observation unless another meaning is explained, and recommends explicit scale where ambiguity is possible. FITS datetime syntax disallows timezone designators. `TIMESYS` defaults to UTC when absent in the global context, while time-axis/table contexts may specify an overriding scale. These rules apply only when the input is actually being interpreted under FITS v4 and the relevant HDU/keyword context supports that reading; they do not convert a member-entered local time or arbitrary filename into UTC. Preserve exact supplied/header text and comments, its origin and HDU/field, parser and version, interpreted scale and the rule used (explicit, FITS default, convention, or unresolved). Keep the observer's local wall time separate from import time and the normalized value. Do not invent timezone, target truth, or timestamp precision. ([S03](https://fits.gsfc.nasa.gov/standard40/fits_standard40aa-le.pdf) §§4.4.2.2, 9.1.1, 9.2.1–9.2.2.)

### File integrity, sync, and handoff

Nextcloud documentation is useful to bound the file-sync option, not to promise the club's deployment behavior. Server 35 documentation describes chunked upload assembly and constraints, sharing configuration, and version history that may be aged out and limited to a fraction of current free space. Its File Drop documentation says unauthenticated upload is not chunked. The conflict manual is pinned to documentation commit `2de94819a621e1d5876e6afde1f47203b613b96e`, but not to a desktop-client release: it describes retaining the remote file plus a local conflicted copy, normally not uploaded, for human resolution. A future choice needs exact server and client versions and policy testing; no code or deployment was inspected here.

For a selected-session packet, I recommend a human-readable README and versioned manifest, with stable IDs and relative paths, and per-file SHA-256. Consider using the IETF BagIt 1.0 layout for package integrity: it defines opaque payload files and checksum manifests whose validation checks bytes against listed hashes. BagIt does not define astronomy metadata, application object relationships, permissions, or scientific correctness, so include the notebook's own versioned session/asset/annotation manifest. ([S05](https://www.rfc-editor.org/rfc/rfc8493.html) §§2–3.)

## Proposed minimum records and workflow

- **Separate identity from content:** stable IDs for planned session, actual session, ingest packet/attempt, asset instance, immutable asset version, note revision, member, and annotation. Preserve original filename, size, supplied type, digest, supplier, receipt time, and original metadata. A digest identifies bytes, not an observing event: if matching bytes arrive under a different name or session, show the relationship and ask to attach, skip, or create another instance.
- **Represent derivatives without overwriting:** each processed image or preview is a new version with a parent link, dimensions, digest, supplier, known tool/version/parameters, and declared transforms. Unknown provenance remains unknown. Never overwrite the submitted original or assert that supplied metadata or a derived image is scientifically correct.
- **Make intake resumable and visible:** issue a packet/attempt ID and per-file state; stage chunks or a local packet; verify complete length and digest; then register metadata and relationships atomically. A repeated submission is idempotent by packet/attempt key. Content matches are duplicate hints, not automatic merges. Show interrupted, unsupported-preview, needs-review, failed, and ready states. Keep an incomplete session out of published packets until an authorized person accepts it. Define temporary-part cleanup, file-size/storage limits, and a recoverable path before launch.
- **Use explicit identity and access:** give each member an account/identity in the service, but do not prescribe an identity provider until hosting is known. Private drafts belong to their author and named coordinators; club visibility begins with an explicit publish action. Enforce the same authorization on originals, derivatives, thumbnails, comments, and downloads—not only on visible controls. Review capture-site metadata, member names, and free text before export. A public/unlisted link is not a private-draft rule.
- **Keep edits understandable:** comments are separate authored records. For a shared editable note, submit an expected revision ID; accept one current revision, preserve a stale submission as a visible conflict candidate with its base revision/author/time, and let the author or coordinator reconcile it. Do not use last-write-wins. Keep publication and annotation history according to a club-approved retention policy. These are proposed app rules, not behaviors established by W3C or Nextcloud.
- **Separate visibility, deletion, backup, and packet copies:** withdrawal should revoke notebook access and remove the item from new exports promptly. Deletion should name which live originals, derivatives, previews, upload parts, and annotation content are purged, when backups expire, and whether a minimal tombstone is permitted. A 30-day recovery period is one policy option to discuss, not an evidence-based default. A previously downloaded packet cannot be recalled; tell recipients and record the withdrawal. Require a restore drill before relying on the service.
- **Make handoff work offline:** export selected records, originals, chosen derivatives, annotations, and provenance in a portable directory/ZIP with a README, schema version, relative paths, stable parent links, per-file checksums, access/rights notes, incomplete-entry warnings, and a snapshot of exactly what was exported. The validator should catch malformed manifests, checksum failures, missing parents, and annotation targets absent from the packet. Keep credentials, machine paths, and the live database out. Preserve unknown fields on import/export where feasible.
