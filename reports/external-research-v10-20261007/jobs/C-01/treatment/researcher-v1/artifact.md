# Community telescope notebook — research and planning proposal

Assignment: `C-01/treatment/researcher-v1`  
Inputs: the hypothetical case brief and read-only frozen plan identified in the stage input map.  
Status: proposal only. No product, WorkNodes, canonical plans, accounts, issues, or pull requests were created.

## Recommendation

Plan a small, club-controlled review service with one authoritative catalog and asset store, plus a portable offline intake packet that members can fill and upload later. The service owns identities, visibility, versions, annotation history, and import status. It should store original bytes unchanged and add preview renditions as separate derived assets. It should use per-record revision checks and append-only comments instead of silently choosing the most recent offline edit.

Keep the deployment deliberately small: one supported host and one application writer; use an ordinary transactional catalog and a club-controlled file store. Do not sync a live database file among volunteers. Keep the database engine, image decoder, and exact viewer conditional on a short pilot with real club files. A local database is a reasonable first candidate only when it remains on the service host; move to a separate database only if measured concurrency, backup, or operations require it. Use an existing Nextcloud installation as a file handoff option only if the club already has a capable operator. Its generic sync/version features do not supply the notebook's object model, annotation identity, or semantic conflict resolution.

Make the operator condition explicit: before deploying a service, name one person who will patch it, monitor storage, and perform a restore. If no member can own that work, start with portable session packets and a coordinator-mediated review queue rather than introduce a permanent commercial account or an unmaintained server. This still supports disconnected session entry and later shared review, while placing the choice to host a continuously available service behind a real maintenance check.

## Documented behavior and implementation review

### Annotations and coordinate frames

The 2017 W3C Web Annotation Data Model provides a representation for an annotation body, target resource, author/lifecycle information, and selectors. Its `FragmentSelector` can name a media fragment; its `SvgSelector` can represent a rectangular or non-rectangular shape. The model is an exchange/data model, not a storage service, group permission system, offline synchronization engine, or promise that selectors survive a changed image representation. See [S01 §§3.3, 4.2.1, 4.2.7, 4.3](https://www.w3.org/TR/2017/REC-annotation-model-20170223/).

W3C Media Fragments `xywh` defines x, y, width, height in intrinsic image pixels, with `(0,0)` at the top left; it also permits percentages. This gives a useful portable convention for a rectangle on a particular rendition ([S02 §§4.2.2, 6.1.2, 7.1](https://www.w3.org/TR/2012/REC-media-frags-20120925/)). It does not mean that a rectangle identifies the same celestial object in a crop, rotation, stretch, stack, or replacement image. Preserve the rendition identity and dimensions with the selector, and mark it for review when the target changes.

OpenSeadragon is a candidate only for high-resolution preview zoom and pan. I inspected its public v6.0.2 code at commit `7842cd92e6799d97c18227a79cb69af4f706b023`, rather than infer API behavior from a similarly named issue. The code distinguishes viewport and image coordinates; `Viewport.viewportToImageCoordinates` is explicitly warned as inaccurate in a multi-image world, where the corresponding `TiledImage` conversion should be used. The `TiledImage` conversion path applies its rotation when converting between coordinate frames ([S08, `src/viewport.js:1360–1394`](https://github.com/openseadragon/openseadragon/blob/7842cd92e6799d97c18227a79cb69af4f706b023/src/viewport.js); [S09, `src/tiledimage.js:578–623`](https://github.com/openseadragon/openseadragon/blob/7842cd92e6799d97c18227a79cb69af4f706b023/src/tiledimage.js)).

Relevant release history: issue #2873 reported wrong callback items and intermittent missing/misplaced images during concurrent `addTiledImage` calls in v6; the report included a reproduction harness. PR #2874 passed the queue's own tiled image to its callback and merged on 2026-02-20; v6.0.1 release notes list the fix. The inspected v6.0.2 `processReadyItems` code still passes `{ item: tiledImage }` ([S11–S12](https://github.com/openseadragon/openseadragon/pull/2874), [S10](https://github.com/openseadragon/openseadragon/releases/tag/v6.0.1), [S07, `src/viewer.js:1954–1957`](https://github.com/openseadragon/openseadragon/blob/7842cd92e6799d97c18227a79cb69af4f706b023/src/viewer.js#L1954-L1957)). This is implementation evidence for that callback fix, not proof that every viewer path is correct.

A separate v6.0.2 issue #2925 remained open at the time of capture. Its reporter described intermittent blank rendering after dynamically adding a tile image from a slow IIIF server; using the Canvas drawer reportedly avoided it. That report has no demonstrated applicability to a single already-prepared local preview, but it is relevant if the pilot dynamically adds remote or slow tiles. Avoid that pattern in the initial interface or test it on the actual deployment; do not present the issue as a confirmed defect in the proposed workflow ([S13](https://github.com/openseadragon/openseadragon/issues/2925)). A simple `<img>` preview may be enough if the club's images do not need deep zoom.

**Proposal/inference:** annotate in the unzoomed pixel coordinates of the exact displayed preview, after converting browser coordinates through the selected image's API. Save integer `x,y,width,height`, dimensions, orientation/transform identifier, rendition ID, and the rendition SHA-256. The origin is top-left; reject or flag out-of-bounds regions. Keep the annotation's asset-version target immutable. If a new rendition is made, show the old annotation on its old target and label it “review required” on the new version; never silently scale or project it. If a future workflow needs sky coordinates, make that a separate, expert-validated feature using the particular input's valid WCS. Ordinary viewer coordinates are not WCS.

### Astronomy-file and time semantics

The NASA/IAU FITS Standard v4.0 is the applicable standard reference captured here. Its WCS section states that coordinate metadata relates world coordinates to image pixels; the standard's first pixel coordinate is `(1.0, 1.0, …)` for the described FITS coordinate frame, unlike the top-left zero-based image-pixel convention above. The standard also describes explicit time scales: `TIMESYS` has a specified default in its global context, but relevant time-axis metadata may override it. Its date/time syntax does not use a timezone designator. Do not equate a FITS coordinate, a browser pixel, a filename timestamp, and an observer-entered local time ([S04 §§8.2.1, 9.2.1](https://fits.gsfc.nasa.gov/standard40/fits_standard40aa-le.pdf); see also the FITS version reference [S03](https://fits.gsfc.nasa.gov/fits_standard.html) and NASA WCS overview [S05](https://fits.gsfc.nasa.gov/fits_wcs.html)).

**Proposal:** keep original FITS or other submitted bytes unchanged. Preserve the submitted header/metadata as evidence, and represent any extracted fields as values with their source file/header key and parser version. A time record should keep the exact entered/header value, its source, any known offset/time scale, and an explicit “unknown” state where absent; do not convert an unzoned text value to UTC. The pilot should collect representative files before deciding which formats can produce previews or which fields can be interpreted. An image preview is for review, not scientific reduction, and no import should assert that the supplied time, target, equipment, or coordinates are correct.

The standard reference is not evidence that each member's files conform to FITS v4 or have a usable WCS. The NASA solar-coordinate note S21 is informative for the one-based indexing convention but includes solar-image examples; do not reuse its domain-specific transformations for this club.

### Shared files, conflicts, versioning, and local-catalog analogies

Nextcloud Server 35 documentation describes user/group shares and administrator-controlled public links. Its WebDAV chunking documentation recommends chunking v2 and documents server assembly and request constraints. The large-upload guide notes that the default upload limit is 512 MB and that web server, PHP, timeouts, temporary storage, and object-storage configuration affect large transfers ([S17](https://docs.nextcloud.com/server/stable/admin_manual/configuration_files/file_sharing_configuration.html), [S18](https://docs.nextcloud.com/server/stable/developer_manual/client_apis/WebDAV/chunking.html), [S19](https://docs.nextcloud.com/server/stable/admin_manual/configuration_files/big_file_upload_configuration.html)). This makes it a plausible self-hosted carrier, but not a configuration-free service. The server manual is version 35; a patch version and the club's environment were not selected or tested.

The Nextcloud desktop conflict manual captured at documentation commit `2de94819a621e1d5876e6afde1f47203b613b96e` says that simultaneous local and remote edits can leave the remote base file plus a local “conflicted copy” requiring a person to compare and merge. By default, the local conflict copy is not uploaded. This is useful preservation behavior, but it is not a member-aware merge of note fields and does not itself make the local edit visible to the group ([S15](https://github.com/nextcloud/documentation/blob/2de94819a621e1d5876e6afde1f47203b613b96e/user_manual/desktop/conflicts.rst)). The manual source is not pinned to a specific client release; this behavior must be checked against the precise client version selected for deployment.

Nextcloud Server 35 file versions are restore points, not immutable archives: the documented schedule prunes old versions, uses at most 50% of a user's available free space, and lets named versions escape automatic expiration. Therefore a club must not rely on default version history to meet its retention or deletion policy ([S16](https://docs.nextcloud.com/server/stable/user_manual/en/files/version_control.html)).

Tropy's public documentation gives a useful outside-domain analogy for grouping photos, entering structured metadata, adding tags/notes, and exporting a project as JSON-LD. It explicitly describes a personal-computer product rather than an online shared presentation system. Its format list is a starting point for image-handling expectations, not a compatibility claim for FITS or this project ([S20](https://docs.tropy.org/)). AstroLog's public page describes an open-source astrophotography logging project; it puts manual logging, equipment management, and backup in its stated v1.0 roadmap, with assisted extraction and community features later. It is worth revisiting after release/source/license inspection, but those roadmap statements do not establish current group collaboration or fit this club's scope ([S24](https://astro-log.app/)).

## Proposed records and workflow

### Stable identity and provenance

Use separate identifiers for a planned session, an actual session, an ingest packet/attempt, a media asset instance, an immutable asset version, a note revision, and each annotation. A digest such as SHA-256 identifies bytes; it does **not** identify an observing event. The same bytes can appear under different filenames, sessions, or submitted relationships. Treat a matching digest as a duplicate hint and show the member the existing asset and session context before deciding whether to attach, skip, or register another instance.

Keep original filename, byte size, detected format, digest, who supplied it, when the catalog received it, and any submitted observation metadata. Record session time separately from import time. If an image is processed or corrected, register a new derivative version with a parent asset/version link, supplier, software/tool and version where known, stated transformations/parameters, dimensions, and digest. Label unknown provenance as unknown; never substitute inferred processing details. Store member-supplied target labels and capture details as claims with provenance, not verified facts.

### Offline intake and recoverable import

A session packet should be readable without the notebook service: a versioned manifest plus the selected files, relative names, explicit notes, IDs, and optionally already-known checksums. Offline entry creates a local draft/outbox; after reconnection, upload parts resumably and report each file's state. The server should verify the completed bytes and digest, then atomically register the asset/version and its relationships. Repeating the same packet or upload token must not create an accidental second import; an explicit user action can attach already-known bytes to another session.

Suggested visible states: `draft`, `queued`, `uploading`, `interrupted`, `received`, `verifying`, `ready`, `unsupported-preview`, `needs-review`, `failed`, and `withdrawn`. Keep partial sessions visibly incomplete and out of club-published exports until a member/coordinator explicitly accepts a partial import. Retrying an interrupted transfer should resume or restart only the incomplete file; it must not silently rewrite an original or overwrite a derivative. Define abandoned temporary-part cleanup, available storage, maximum file size, and the user's recovery path before launch. If offline browser storage is used, it is a cache until a durable packet export succeeds; test browser closure, quota exhaustion, and device loss.

### Review, annotations, identity, and access

Use one club identity per member and roles only as needed: member, coordinator, and administrator. Private drafts are visible only to their author and an explicitly authorized coordinator. Publication is a distinct action that changes access and places the item in the club review list. Do not use an unlisted/public link as the privacy mechanism. Enforce the same permission on original bytes, thumbnails, renditions, packet downloads, and export endpoints; hiding a button is insufficient. Consider capture-site EXIF, member names, and free-text notes potentially sensitive; make export inclusion deliberate.

Keep annotations as authored records with author ID, creation time, visibility, body, target asset-version ID/digest, selector, and revision/status. Comments can be independent append-only records, so members can comment concurrently. Give a shared editable note an expected revision ID: one submission can advance it; a submission based on a stale revision is preserved as a conflict candidate and shown alongside the current text. Ask the author or coordinator to reconcile it explicitly. Keep all accepted and rejected revisions in the catalog history according to the adopted retention policy. This gives predictable behavior without claiming automatic semantic merging.

When a processed image supersedes a preview, keep earlier annotation links intact and flag the new version for review. A human may create a new annotation/re-anchor action linked to the old one; do not edit the old selector in place. Keep annotations descriptive and member-attributed. Do not auto-convert comments into classifications or use them as scientific ground truth.

### Retention, deletion, recovery, and export

Separate “withdraw from club view” from “delete stored material.” Withdrawal should immediately revoke notebook access and exclude the item from new exports while preserving an authorized recovery copy. Proposed pilot default, pending club approval: a 30-day recoverable deletion window, then purge the original, derivatives, thumbnails, temporary uploads, and personal annotation content from live storage; expire backup copies on a stated, bounded rotation. Record a minimal tombstone only if the club's policy permits it. The administrator must test the actual backup and restore procedure. A downloaded/exported packet cannot be recalled by the server; name packet recipients and communicate withdrawal instead of promising universal deletion.

Export a selected-session packet as a ZIP or directory with a human-readable README, schema version, manifest, selected session fields, original and chosen derived files, annotations, identity/parent links, provenance, visibility/rights notes, and per-file SHA-256 checksums. Use relative paths and stable IDs, not a live database, credentials, account URLs, or machine-specific absolute paths. Provide a validator that checks manifest syntax, hashes, missing parents, and annotation targets; keep a snapshot of exactly which versions were exported. The format should preserve unknown fields on round trip where possible and include a clear note that the contents and supplied astronomy metadata are not scientifically validated.

## Decisions, optional leads, and open conditions

**Recommended now:** define the portable record model and workflows above; pilot one offline intake packet, one authorized upload, one published review, one annotation, one revision conflict, one export, and one restore. Keep the export schema and file relationships independent of the live application. Use explicit member approval for publication and for re-anchoring a region.

**Condition before service deployment:** identify the operator, hosting boundary, backup destination, patch process, and restore procedure. If the club chooses a hosted Nextcloud server, pin supported server and desktop-client releases together, then test access, file-drop policy, chunk retries, version pruning, and conflict visibility. If the club has no maintainer, choose the packet/coordinator fallback instead of assuming an unmanaged public or home service will be reliable.

**Decisions to resolve with actual member files and policies:**

- Which formats and largest expected files need in-app preview; which can be stored and downloaded but marked `unsupported-preview`?
- Is a record's session time an observer-entered local civil time, an explicit offset timestamp, or an astronomy time-scale value? Which fields are required, and who can correct them?
- Does the group need annotation display on a derivative only, or a validated mapping between a derivative and a specific original/WCS? Default recommendation: derivative-local only.
- When matching bytes arrive under different names or sessions, should the app suggest attachment to an existing asset, preserve a second asset instance, or both?
- Who may publish, edit a shared note, withdraw, delete, export, and restore? Which exported metadata may identify people or capture locations?
- Approve or change the proposed 30-day recoverable-delete window and state an actual backup-expiry bound before production use.

**Optional later work:** compare related renditions side by side; show an annotation's previous target next to a replacement; use more expressive SVG selectors; import astronomy metadata with a documented parser only after format/WCS/time validation; add a member-controlled field allowlist for exports. Deep zoom with OpenSeadragon is conditional on representative file sizes and display need. AstroLog is a later competitor lead only: its current public roadmap places community features after its stated manual-log v1.0 phase; no code, release artifact, or license version was evaluated here (S24). Tropy is an analogy for metadata and JSON-LD export, not a selected shared notebook (S20).

**Uncertainty:** no actual telescope files, display sizes, observing-time conventions, host topology, budget, member roster, retention policy, or operator availability were supplied. Consequently, this proposal does not choose a supported decoder, database engine, authentication library, or hosting provider; it does not claim astronomical correctness, exact costs, or validated metadata extraction. The implementation histories reviewed apply only to the pinned OpenSeadragon component and its cited issues. Nextcloud facts are versioned documentation, not evidence from a club deployment.
