## Recommendation

Plan a small club-owned review service as the authority for member identity, publication, access, and shared revisions. Give a member a printable or downloadable session draft that works offline and can be brought back as an import package. Make the package private until an explicit submit or publish action. Members can review together after ingest; simultaneous edits to one shared note use a base-revision check and an explicit compare-and-resolve flow.

This supports the brief’s low-connectivity entry and later collaboration without promising multi-writer live sync while every device is disconnected. It does require an operator and a second person who can restore the service. If the club cannot own those responsibilities, choose serialized packet exchange and accept that shared review will happen later. No permanent commercial account is required.

Keep original bytes unchanged. Model the planned session, actual session, logical asset, exact file bytes, rendition, annotation, and annotation revision as separate related records. A digest identifies identical bytes, not a repeated observation or scientific identity. Every processed image is a new rendition with a link to its inputs and a record of who supplied it and any known tool, version, settings, and description. Submitted metadata remains visible beside any parsed or normalized values.

Do not assume any viewer can display every supplied file. Begin with a versioned, tested support profile and preserve an unsupported original for download. FITS 4.0 allows multiple HDUs and arrays beyond a simple two-dimensional image, and its DATE-OBS meaning depends on the HDU time system; keep raw values, source HDU, and uncertainty rather than silently converting them. [S05]

## Discovery, mechanisms, and evidence boundaries

I began from the brief’s user-level workflow before reading PLAN.md: a planned session, files and notes carried home, a later processed image or correction, interrupted ingest, private drafts, joint image review, and a selected handoff packet. The initial public-primary discovery pass covered image annotation and region conventions, offline replication and concurrent edits, astronomy metadata, and archival handoff. It surfaced three useful mechanisms and analogies:

| Mechanism | Strength for this workflow | Cost or boundary | Disposition |
|---|---|---|---|
| One shared authority with offline draft packages and conditional revision writes | Straightforward private/published states, access control, one place to inspect ingest state and withdraw shared records | Requires a service operator; offline edits do not become shared until submitted; stale drafts need a deliberate compare/resolve screen | Recommend as the minimum collaborative service, conditional on named service and backup owners |
| Local-first peer replication or CRDT documents | Each member can edit while disconnected and exchange changes later. CouchDB documents describe retained divergent revisions and deterministic winner selection; Automerge exposes all property conflicts in a pinned implementation. [S07–S14] | Deterministic convergence does not choose the club’s intended wording, approval, or visibility. Replication, authentication, revocation, retention, and conflict presentation remain application work | Defer until concurrent offline editing is a demonstrated need |
| BagIt package exchange, with astronomy-specific OAL as an optional adapter | Portable transfer, manifests for byte-integrity checking, and a possible mapping to existing observing logs. [S04, S16–S18] | A packet is not shared state or an access policy. A valid bag proves listed checksums, not completeness of the scientific record, provenance assertions, or scientific correctness. OAL 2.1’s inspected schema is old and has no demonstrated compatibility with member files | Use a BagIt directory as an exchange layer; evaluate OAL only if members already have relevant exports |

A synchronized folder containing a live database is not the same as packet exchange. SQLite’s WAL documentation says all database processes must be on one host and that WAL does not work over a network filesystem. It also says transactions across attached databases are not atomic as a set. If SQLite is evaluated later, keep its database and WAL files on the service host; do not have laptops or removable media open or sync the live database. This research does not select SQLite or pin a runtime release. [S06]

The W3C Web Annotation Data Model provides a portable body/target/selector shape and lifecycle fields, but it does not prescribe transport or access control; its external-resource metadata is described as a hint, not authoritative identity. Media Fragments defines rectangular xywh selectors with integer x, y, width, and height; pixel is the default, (0,0) is top-left, and percent coordinates are relative to the original media dimensions. The selector still needs an exact target representation and dimensions. [S01–S02]

Evidence labels: **documented** means a standard or official documentation statement; **implementation evidence** means pinned source or tests inspected; **inference** means a product consequence proposed from that evidence; **unvalidated proposal** means it needs representative files or a prototype.

## Pinned implementation and history

**Automerge alternative, inspected at @automerge/automerge 3.5.0.** The official release tag points to commit 4d2a8f6bfecfb7f1e4fca126e6d2122ac526f903 and was published 2026-09-16. In implementation.ts the API documentation says a concurrent property write has an arbitrary but deterministic displayed winner; getConflicts delegates to conflictAt. conflicts.ts calls the underlying getAll operation and returns competing values indexed by operation ID. The 3.5.0 tests cover competing map/list values, conflict inspection, and editing conflict values in a change callback. These tests were read, not run. The release added author metadata as an opaque hex value and fixed list insertion, patch/rich-text, and performance issues. An opaque actor/author field is not authenticated club membership. [S09–S14]

Issue 889 reports that a redundant same-value assignment was not represented in getConflicts, with its reproduction naming version 2.1.11. My fresh GitHub API record reports closed_at 2026-09-10, and the rendered page displays Closed; the API record has no pull-request link. A web search result still showed “Open”; I treat that as a stale index result. A comments API request was rate-limited, and no release note or source change tying the closure to a fix was established. Therefore the issue does not establish a defect in 3.5.0, nor that it was fixed there. The release tests and code are equivalent implementation-history evidence for the advertised conflict behavior; the issue’s closure reason and cross-version fix path remain unresolved. [S10–S15, S19]

**CouchDB replication, documentation-only comparison.** The captured stable documentation identifies the CouchDB 3.5 documentation. It describes same-node stale revision writes as 409 conflicts, while independent offline replicas can retain concurrent leaf revisions; the deterministic winner is only a display choice, and applications must inspect and resolve conflicts. This is a useful alternative mechanism, not a selected component or a code audit; no exact CouchDB package build or issue/fix history was investigated. [S07–S08]

**Astronomy and exchange analogies.** FITS Standard 4.0 was published 2016-07-22 and updated 2017-12-01. It says DATE-OBS is expressed in the HDU’s principal time system/scale, other scales are permitted, explicit scale is recommended, and the value is assumed to be the observation start unless clarified. FITS arrays and extensions also make a universal “simple preview” assumption unsafe. This is format semantics, not proof that member values are correct. [S05]

The OpenAstronomyLog archive inspected at commit 59cc9dd4ecbd7569d90f86b0313e0430578f18fb (commit dated 2020-12-09) contains an OAL 2.1 schema whose XSD revision is 2011-08-08. It has session and observation times plus optional image references, so it is a useful import/export analogy. It does not supply the notebook’s full immutable rendition lineage, collaborative annotation history, or access policy. I did not verify current repository head or compatibility with actual club data. [S16–S18]

**HTTP conditional-edit semantics.** RFC 9110 requires strong entity-tag comparison for If-Match and says a false precondition must not apply the requested method. A 412 response is allowed; the RFC also allows a 2xx response when the same state-changing action is known to have already succeeded. For the proposed notebook, use a strong base revision and return a stale-edit response for a genuinely changed representation; only treat an exact retry as already applied when its operation identity is known. The standard does not keep a client’s rejected draft or resolve its meaning; the app must preserve and compare it. [S03]

## Critic review of the prior proposal

I retain its useful direction: one shared review authority plus portable offline drafts, immutable originals, separate logical and byte identities, explicit rendition lineage, durable annotation targets, explicit publication, and a checksum-verified handoff. The exact frozen plan already contains the essential scope and explicitly marks its mechanisms unvalidated; those are preserved in the section-by-section dispositions.

I changed or qualified several conclusions after checking fresh evidence. The prior artifact called issue 889 open; the fresh API record reports it closed and the rendered capture displays Closed, while a search index still shows Open. Its closure reason and any fix reaching v3.5.0 remain unproven. The prior validation text expected a stale If-Match update to fail; refine it to distinguish a changed representation from a retry known to have already succeeded, for which RFC 9110 permits 2xx. The prior proposal suggested a BagIt directory or ZIP; RFC 8493 distinguishes BagIt from serialized archival formats including ZIP, so this proposal uses a directory and leaves any wrapper format to a separate profile. It also proposed a transaction that publishes staged files without explaining that database and external blob-store commits are not atomic together; this proposal requires a recoverable journal instead. Finally, the OAL archive proves the inspected schema/commit dates, not current upstream status or compatibility with member exports.

The main remaining objections are operational rather than scientific: no one has yet accepted responsibility for a host and restore, no real file set establishes the preview profile, and no user study shows whether offline same-note concurrency is necessary. Keep those as explicit decision gates rather than treating the proposed architecture as selected fact.

## Integrated proposed workflow and data rules

1. **Prepare and record.** A coordinator creates a stable planned-session ID and a human title. A member’s offline draft retains that ID, claimed observing interval, target label, notes, and local capture time. Distinguish device-claimed time from server receipt time and show the draft as device/package-only until submission.
2. **Ingest and recover.** Assign a durable import ID and record per-file state, byte count, digest, source filename, staging path, and error. Stage files first, verify the copied bytes, then publish the metadata pointer. Database and filesystem commits are not one atomic transaction: use a recoverable import journal and idempotent retry, and show incomplete states after a crash. Do not mark an import complete while any required file is missing or unverified.
3. **Keep identity and provenance separate.** Give sessions, logical assets, exact byte blobs, renditions, annotations, and revisions stable IDs. Hashes support byte integrity and storage deduplication only. Preserve duplicate or renamed import records if their provenance differs. Record who submitted a file, when it was received, its original name, and known transformation inputs, operator, tool/version, and settings. Do not certify image contents, observation fields, or transformations as scientifically correct.
4. **Preserve submitted metadata.** Store supplied headers and notes as received alongside separately parsed values, units, source file/HDU, parse status, and any normalization method. For FITS DATE-OBS preserve the supplied value and HDU scale; do not infer UTC if absent or ambiguous. A target label is descriptive text. Sky-coordinate annotations and WCS remapping are out of the initial profile.
5. **Bound preview behavior.** Declare the supported image/metadata profile and viewer version. For unsupported, malformed, multi-HDU, or dimensional files, preserve the original and mark preview unavailable or incomplete. A generated preview is a distinct derived representation with source ID, digest, dimensions, renderer/version, orientation, stretch, and any crop. It is not scientific reduction.
6. **Anchor collaboration to exact versions.** Keep comments and regions as separately identified, attributed, revisioned annotations. Anchor each rectangle to a stable rendition ID and digest, declared dimensions, coordinate unit, and canonical image origin. Convert display-canvas coordinates through the actual scale/orientation/crop transform before saving; never save canvas CSS pixels as if they were original-file pixels. A W3C Web Annotation projection may aid export, but it does not itself define the app’s display transform, authentication, version history, or transport. When a processed rendition arrives, old annotations remain on the prior rendition. Migration to a new rendition is an explicit, reviewed action; do not imply that visual similarity or WCS registration has been validated.
7. **Make edits and visibility explicit.** Use authenticated member identities and coordinator roles. Keep private drafts private at the service and blob layer, not merely hidden in the interface. Enforce access for both metadata and original/derived bytes. Submit edits with a strong base revision. If the shared record has changed, retain the rejected local draft, show both versions, and require an explicit resolved revision. Never use arrival time as an automatic merge rule. Record publication as an explicit event.
8. **Specify withdrawal, deletion, and recovery.** Decide retention, backup, and account-removal policy before live use. “Withdraw” hides a record from future club search and exports; “delete” purges selected source bytes, derived previews, annotations, indexes, and caches according to the stated policy. Report pending cleanup and completion. State that prior exports and recipient copies cannot be recalled. Back up metadata and blobs as a consistent set; rehearse restore and verify every restored digest and link before relying on the service.
9. **Export a selected packet.** Use an on-disk BagIt v1.0 directory with a payload manifest and an explicit notebook profile/version. Include only selected sessions and approved originals, chosen renditions, annotations, provenance links, and a README describing omissions. Use a supported checksum algorithm selected by the profile. BagIt distinguishes a complete bag from a valid one whose listed checksums verify; it is not a scientific validator or access-control system. The inspected RFC distinguishes BagIt from serialized archival formats such as ZIP, so do not label a ZIP file itself “RFC 8493 BagIt” without a separately specified and tested wrapper. Keep private drafts out unless selected. Re-import must verify the manifest and show missing or altered files.

## Observable validation proposal

All checks below are **proposed acceptance checks, not executed checks**.

1. **Offline draft and publication:** disconnect a member device; create a draft for a planned session, close/reopen it, and confirm its notes and attachments persist in the package. Submit online and verify the planned ID and claimed time are retained, server receipt time is separate, and nothing is club-visible before explicit publication.
2. **Format and metadata profile:** use representative member-selected files, including missing or malformed metadata, one multi-HDU FITS, and one unsupported dimension. Confirm source bytes are unchanged, raw headers remain available, unknown fields stay unknown, time scale/HDU are visible, and unsupported preview never blocks original access.
3. **Interrupted ingest:** interrupt imports before copy, mid-file, after blob write, and before metadata publication. Restart; verify journal state, retry idempotency, digest recheck, clear per-file recovery, and that no partial import appears complete. Deliberately alter one byte and confirm publication is blocked.
4. **Identity and lineage:** import identical bytes with different names and as two separately submitted records. Confirm storage may deduplicate bytes without collapsing provenance. Add a processed image and confirm it receives a new rendition identity with an explicit input link and processing details.
5. **Region geometry:** use an asymmetric image with marked corners and center. Test x/y order, top-left origin, pixel and percent mapping, orientation, crop, scale, zoom, and resize. Replace the rendition with a different size/crop; confirm prior rectangles stay with the prior digest and the new rendition requests human review.
6. **Concurrent edits and access:** have two members edit from one base revision. Confirm a stale update is rejected, its draft survives, both values can be compared, and a resolved revision has a named author. Verify private metadata and direct image/derivative URLs remain inaccessible to another member before publication and after reload.
7. **Withdrawal, deletion, backup, restore:** withdraw a record and confirm it is absent from new searches and exports. Exercise deletion against originals, derived images, caches, indexes, and scheduled backups; show pending and completed states. Restore a consistent backup and verify all digests and links. Confirm the UI explains that earlier exported copies remain with recipients.
8. **Packet transfer:** export a selected session as a BagIt directory, copy it to a separate device, inspect it without the app, and validate all manifests. Remove or alter a payload file and confirm validation fails. Confirm profile version and omissions are visible and private drafts are absent unless selected.
