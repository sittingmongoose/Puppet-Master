# Community telescope notebook: independent planning proposal

**Assignment:** C-02/treatment/researcher-v1. This is a research proposal for the hypothetical brief in the mapped input set; it is not product code or canon. The exact brief and frozen plan hashes are recorded in `source-map.json`. The plan is treated as an unvalidated proposal, not an answer key.

## Recommendation

Plan a small, self-hosted club workspace with one authoritative review service and its database and image store on the same club-managed host. Members use a browser on the club network or an intentionally configured private connection; no permanent commercial account or public social layer is required. Make the online service the authority for club-visible records, publication, access, and deletion decisions.

For field use, prepare an **offline session draft package** that can be saved to removable storage. It carries the planned session ID and a local notes form, remains private until a member submits it, and is later ingested into the review workspace. This gives the group an explicit offline handoff without trying to make every copy of a shared database a live multi-writer replica. If the club cannot assign an operator and backup owner for a host, the viable fallback is packet-based, serialized review; the group should accept that trade-off instead of promising always-on collaboration.

Keep the original file bytes immutable. Separate a logical asset ID from a hash of the bytes, and represent every conversion or processing output as a new, linked rendition/asset. Anchor an annotation to an exact image representation and its dimensions. On concurrent note edits, require an explicit revision precondition and preserve a stale draft for comparison; do not silently choose whichever upload arrived last.

## Mechanisms and trade-offs

| Mechanism | What it gives this club | Costs and failure modes | Decision |
|---|---|---|---|
| **One self-hosted authority; local offline draft packages; explicit revision checks** | Central member identity, private/public state, predictable publication, one ingest journal, and one place to withdraw a record. Offline session notes can be carried home and submitted later. A strong `If-Match` precondition is specified to prevent applying a stale edit; the server can return `412 Precondition Failed` when its current representation no longer matches. [S12] | Someone must own the host, restore practice, and access policy. The HTTP precondition itself does not save a rejected draft or resolve a semantic conflict; the application must retain the draft, show the two versions, and require an explicit resolution. Offline edits to a shared note are not instantly shared. | **Recommend for the minimum workflow.** The brief asks for later collaboration and visibility control, not simultaneous editing of one record by devices that remain disconnected. |
| **Local-first collaborative documents (Automerge-style CRDT)** | Local copies can be edited offline and later synchronized; concurrent operations converge. In pinned JavaScript `@automerge/automerge` v3.5.0, `getConflicts` exposes competing property values keyed by operation IDs; tests cover concurrent object replacement and conflict reads. [S17–S22] | Convergence is not member-level meaning. The documented ordinary property read picks a deterministic operation-ID winner, not the chronologically latest edit; the other values need explicit conflict UI. Actor/author metadata is not authenticated identity (v3.5.0 release describes author metadata as opaque hex). Networking, storage, who may share a document, revocation, retention, and deletion still need application policy. The official project article says its public sync server is for experimentation and recommends running one's own for production. [S16–S24] | **Defer.** Revisit only if several members must edit the same notes while disconnected and the group accepts the extra sync and authorization design. No CRDT component is selected. |
| **Portable exchange package (BagIt); optional OAL import/export** | BagIt packages opaque payload files with manifests; a receiver can verify the listed bytes after copying. OAL 2.1 offers an astronomy-specific exchange shape for observations, including session and image references. [S13, S25–S29] | A package is a handoff, not live shared state, role enforcement, edit merging, or a deletion mechanism. BagIt validity proves manifest checksums, not scientific correctness or metadata truth. OAL 2.1's schema revision is 2011 and the repository's last push is 2020-12; current club-tool compatibility is unknown. The inspected XSD has image references and observation `begin` but is not a complete immutable-asset, annotation-history, and provenance model. | **Use BagIt for selected-session export and offline transfer.** Keep OAL as an optional compatibility adapter after testing actual member exports; do not make it the canonical internal model. |

A synchronized folder containing the live database is a tempting fourth route, but it is not the same as exchanging a package. SQLite's own WAL documentation says all processes accessing a WAL database must be on one host and WAL does not work on a network filesystem; the WAL and SHM files are part of the operational database state. [S14, S15] If SQLite is chosen, run the service and database together on local storage and let remote clients call the service. Do not open a shared database file from member laptops or sync a live WAL database through removable media. The database engine and its release remain unselected; pin and validate them when the host environment and write load are known.

## Proposed minimum workflow and data rules

1. **Prepare.** A coordinator creates a planned session record with a stable internal ID and a human-readable title. A printable/downloadable session draft includes that ID. A member may record an actual session, rough interval, target label, and free notes offline. The UI labels an unsent draft “on this device/package only.”
2. **Ingest safely.** Import writes to a staging area with a durable import ID and visible per-file state. Check file length and a strong digest while copying; recheck before commit. An interrupted import can resume by rechecking already-staged bytes. Only after the payload and metadata pass checks does one transaction publish the import record. Failures show which file failed and whether retry or replacement is needed. Retrying the same package is idempotent at the import level, but a repeated digest is only a duplicate-bytes signal, not proof of the same observation.
3. **Keep identity and provenance separate.** Give a session, each logical asset record, each rendition, each annotation, and each revision a stable opaque ID. Record SHA-256 (or a selected stronger digest) for byte integrity and deduplication, while preserving the submitted filename, importer, import time, and original package identity. A matching hash may reuse stored bytes, but does not collapse two provenance records or tell us whether a renamed file or repeated exposure is the same event. A processed image is a new asset with `derived_from` links and recorded tool/version, parameters, and operator-supplied description; it never replaces the original.
4. **Preserve source metadata and units.** Store submitted text/headers unchanged alongside any normalized field and its source. Represent observation time as a raw supplied value plus an optional normalized value, its timezone/time scale, interval interpretation, and provenance. FITS v4.0 says `DATE-OBS` normally means an observation start, but permits time scales other than UTC and recommends explicit scale; preserve the source value and do not invent a scale where it is absent. [S01] A target label is descriptive input, not a solved coordinate. If coordinates are later accepted, store declared frame, axis order, units, and origin explicitly and keep them distinct from user prose. Nothing here certifies that metadata or image content is scientifically correct.
5. **Limit preview promises.** Preserve any supplied file type as bytes and report whether this version of the viewer can display it. Start with a tested allowlist of common raster images and a deliberately bounded FITS profile. FITS is a structured file with a primary HDU and possible extensions and dimensions, not a promise that every file is a simple 2-D web image. [S01] If a format cannot be displayed safely, show the original as downloadable and invite a separately supplied preview. Any generated preview records its source asset, renderer/version, options (including stretch/orientation), dimensions, and status; identify it as a display rendition, not a scientific reduction.
6. **Anchor comments and regions to a stable target.** Represent a comment as its own revisioned annotation and a marked rectangle as an annotation with a target asset/rendition ID and exact display representation. A W3C Web Annotation-compatible projection is a good portable starting point for bodies, targets, creator/time, and a `FragmentSelector` that names the fragment specification. [S10] For a rectangle, use Media Fragments `xywh` with a declared unit, dimensions, and top-left origin; pixel is the default and percent is relative to the original media dimensions. [S11] Store the rendition ID/hash and width/height beside the selector, so it is never misread against a later preview. When a processed image arrives, retain the old target and show its annotations as belonging to the prior version. Migration to a new rendition is a new, reviewable action; never silently move rectangles or imply registration between images. A later WCS-based migration is optional and requires validated transforms.
7. **Make visibility and edits explicit.** Use coordinator-managed club members and roles, with owner-private drafts and an explicit publish action. Enforce access in the service for both record metadata and image bytes, not only in the interface. For an edit, carry the base revision/strong entity tag. RFC 9110 requires strong comparison for `If-Match` and identifies it as a lost-update precondition. [S12] On mismatch, reject the write, keep the draft locally, and offer to save it as a separate pending revision with its base revision. The user compares both versions and authors a resolved revision; the app does not label a server arrival time as “latest.” Annotations remain separately attributed contributions. Do not turn comments into automated scientific classifications.
8. **Define withdrawal, deletion, and recovery.** Before real use, the club chooses retention and backup rules. “Withdraw from club view” hides an item from search and future packets; “delete” removes the source bytes, generated previews, annotations, indexes, and caches according to the policy. The product must show which backups and exported copies cannot be recalled. A coordinator-visible deletion job should report pending cleanup and completion evidence. Maintain a consistent backup of metadata plus blob storage and run a restore rehearsal before relying on the workspace; validate every restored file against its digest. A deletion policy cannot promise erasure from packets already handed to another member.
9. **Export and hand off.** Export only selected sessions and explicitly approved assets/annotations. A BagIt v1.0 directory or ZIP includes `bagit.txt`, a payload manifest (use SHA-512 for newly created packages), `data/` with originals, chosen renditions, an export metadata file, annotation JSON-LD, provenance links, and a short README naming schema/profile versions and known omissions. RFC 8493 defines a valid bag as a complete bag whose listed checksums verify; it treats payload contents as opaque bytes. [S13] The receiving view rechecks the manifest and displays incomplete/missing items. Keep private drafts out unless explicitly selected. A packet can be copied offline, retained, or re-imported; later revocation cannot reach that copy.

## Pinned component/code and history findings

### FITS/WCS and region-coordinate risk

**Documented behavior.** The NASA/IAU FITS Standard 4.0 defines headers, data units, and extensions; it says `DATE-OBS` should be read with the HDU's time system/time scale and generally refers to the start of observation. [S01] Astropy 8.0.1 documentation says integer pixel values fall at pixel centers; its high-level API uses zero-based coordinates, with the first pixel spanning `-0.5` to `+0.5`, while low-level calls accept origin 0 or 1. It distinguishes pixel order `(x,y)` from array order `(row,column)`. [S02]

**Implementation evidence.** I inspected Astropy v8.0.1, signed release/tag commit `7c5a9c124ce84c76992016e89631566ad398aff7` (released 2026-07-08): `astropy/wcs/utils.py` contains `skycoord_to_pixel(..., origin=0, mode="all")` and `pixel_to_skycoord(..., origin=0, mode="all")`; `test_utils.py` includes a generic `test_skycoord_to_pixel_swapped`. [S03–S05] The helper implementation selects longitude/latitude axes and calls low-level world-to-pixel conversions; the documented default `origin=0` is therefore part of the API contract, not a default to hide in an app.

**Pertinent history and boundary.** Astropy issues #4976 (opened 2016) and #10468 (opened 2020) report a reversed `CTYPE1='DEC--TAN'`, `CTYPE2='RA---TAN'` WCS and a wrong coordinate-to-pixel/cutout result; #10468 reports Astropy 4.0 and includes a specific `Cutout2D` reproduction. Both issues were open in the captured state. [S06, S07] PR #20473 proposed new regression tests for latitude-before-longitude and a `native_pixel_order` API; its patch is useful evidence of the axis-order edge case, but that PR was closed on 2026-10-02 without merge and targeted milestone v8.1.0. Its patch is not code in pinned v8.0.1. [S08, S09] I did not run the code against a club file or establish that these reports affect every current WCS file. The plan should therefore avoid world-coordinate annotation mapping in its first profile. If later needed, pin a released Astropy build and test both `CTYPE` orders, origin 0/1, `(x,y)` vs `(row,column)`, image display flip, and pixel-to-world round trip against asymmetric fixture points.

### Local-first conflict mechanism

**Documented behavior.** The Automerge conflict guide describes a default deterministic winner for a conflicting property and a `getConflicts` route to inspect all operation values; its ordering is based on internal operation IDs, not wall-clock time. [S16] That is enough to compare a CRDT with a server revision precondition, but not to claim that an app's meaning of “last edited” or “approved” is handled automatically.

**Implementation evidence.** At `@automerge/automerge` 3.5.0, commit `4d2a8f6bfecfb7f1e4fca126e6d2122ac526f903`, `implementation.ts` exports `getConflicts` and delegates to the pinned conflict projection, which reads all conflicting values; `conflicts.ts` maps those values by operation ID. The pinned test creates independent edits to the same `user` property, merges them, and reads the conflicts; it also checks that values read outside a change callback cannot mutate the document. The tests were read, not executed. [S17–S22]

**Release/history limit.** The v3.5.0 release adds change-author metadata described as opaque hex, not a club identity or authentication credential. [S17, S22] Open issue #889 reports that assigning a property its already-current value is treated as no change and consequently does not add a conflict in the reporter's scenario. I did not reproduce it on v3.5.0, so it is a caution with unresolved version applicability, not a claim that v3.5.0 is broken. [S23] The official Automerge Repo article describes local storage and sync adapters and says its public sync server is experimental; a club deployment would need its own operational and access design. [S24] This is why the CRDT path remains a future comparison, not the MVP choice.

## Open decisions, optional leads, and uncertainty

Resolve these before an implementation brief: who owns the host and restore process; whether private drafts are device-local or may be coordinator-visible; expected network/access mode; representative formats, file sizes, and FITS HDUs/dimensions; retention duration and deletion/backups; whether members need concurrent offline edits to the same note; and whether existing members actually exchange OAL 2.1. No specific database, web framework, preview renderer, authentication product, or annotation library is selected here.

Optional leads are (a) a validated, read-only FITS preview path with explicit stretch/orientation metadata; (b) WCS coordinate overlays only after pinning and testing the axis/origin behavior above; and (c) OAL 2.1 import/export for clubs that already have matching data. None expands the initial scope into scientific image reduction. The schema and sample-file compatibility are not proven by these sources.

Other unresolved limits: no actual capture files, storage volumes, host hardware, member accounts, or retention decisions were supplied; no sample image was tested; no device-clock reliability was established for offline timestamps; the ability to migrate rectangles across reprocessing is intentionally unresolved; the Automerge issue's effect on v3.5.0 is unverified; and there is no claim that BagIt checks prove provenance claims or scientific correctness.

## Observable validation proposal

These are **proposed acceptance checks, not checks run in this research assignment**.

1. **Offline draft and handoff:** disconnect a test device, open a prepared session draft, add time/target/notes, export its package, restart the app, and confirm the exported text/attachments remain available. Reconnect and submit it. Confirm it is private until an explicit publish event and retains the original planned-session ID.
2. **Metadata and format profile:** ingest a representative member-selected file set covering the declared supported formats, missing metadata, malformed metadata, one multi-extension FITS, and one unsupported dimensionality. Confirm originals are byte-identical, unknown fields stay unknown, time scale/units are visible, and unsupported preview does not destroy or rewrite a file.
3. **Identity and ingest recovery:** import identical bytes under changed filenames and distinct logical records; confirm byte storage may deduplicate but provenance remains separate. Interrupt a multi-file import at several points, restart, resume, and verify no partial import is marked published. Corrupt one byte and confirm the digest error blocks commit with a clear retry action.
4. **Rendition and annotation coordinates:** use an asymmetric image with marked corner/center rectangles and known dimensions. Verify top-left origin, x/y order, pixel/percent conversion, image flip, and zoom/resizing. Replace the preview with a differently sized/cropped derivative; confirm the original annotation remains on the original rendition and the new view asks for review rather than silently relocating it. If WCS is later enabled, add fixtures with `RA,DEC` and `DEC,RA` axis order and origins 0 and 1; compare expected coordinates and round trips.
5. **Concurrent revisions and visibility:** have two member sessions edit the same base revision and separate revisions. Confirm the stale `If-Match` update is rejected, the original stays visible, both drafts are retained, and a user can resolve them into a new revision. Check that owner-private drafts and their direct image URLs remain inaccessible to another member until publication, including after reload.
6. **Withdrawal, deletion, and restore:** withdraw a record and confirm it disappears from new member searches/exports; run hard deletion per the chosen retention policy and inspect source bytes, preview cache, index, and backup handling. Confirm the UI states that exported copies cannot be recalled. Restore a consistent database-plus-blob backup and verify all restored digests and links.
7. **Packet integrity:** create a selected-session BagIt export, move/copy it to another device, validate all manifest hashes, remove or alter one payload file and confirm validation fails, then inspect the packet without the original application. Verify private drafts are absent unless selected.
