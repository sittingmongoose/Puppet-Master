## Recommended direction

Plan a **single-club, self-hosted web service with offline private drafts and an explicit submit/sync queue**. Keep the club’s shared server authoritative. Store source files and derivatives as immutable files in club-controlled storage; store records, access decisions, revisions, and provenance in a small service-owned metadata database. Keep the database engine and authentication implementation open until the club names its host/operator and reviews its threat model; do not make a managed commercial account a prerequisite.

For edits, give each note/annotation a server revision and use an HTTP conditional update (`ETag` plus strong `If-Match`). RFC 9110 specifies that a failed `If-Match` condition must prevent the state-changing method; 412 is an allowed failure response, and the mechanism is expressly intended to prevent lost updates. Preserve the rejected draft and show both versions for a person to reconcile. Treat comments as append-only items where practical, so independent comments do not conflict. This gives predictable behavior without pretending that offline edits can be merged safely by timestamps. [S15](https://www.rfc-editor.org/rfc/rfc9110.html)

Use a browser-local draft/outbox for session entry and annotations while disconnected, but show a persistent unsent state and provide a local export/recovery action. The WHATWG Storage Standard permits user agents under storage pressure to clear `best-effort` storage buckets; a browser database is not the only copy of an unsent observation. Request persistent storage where supported, explain when it is unavailable or declined, and keep source files on removable media until the server acknowledges and verifies them. [S25](https://storage.spec.whatwg.org/)

**Important deployment boundary:** public/private access must be enforced by the server on every record and binary request. A hidden button or unguessable ID is not authorization. A self-hosted service avoids a permanent vendor account but still needs a named operator, updates, backups, account recovery, transport security, and a documented recovery path.

## Data, image, and annotation model

### Ingest and provenance

FITS is a self-describing astronomy interchange format with Header/Data Units, image extensions, tables, and arrays that can be one-, two-, or higher-dimensional. It is not equivalent to “a picture with a few fields.” Preserve each original byte stream unchanged, including files that cannot be previewed. Record detected format, byte length, SHA-256, original relative path and filename, import batch, submitter, receipt time, and validation/preview status. A content hash identifies exact bytes only: equal hashes permit blob deduplication, but do not prove that two files represent the same observing event, that a rename is a new observation, or that supplied metadata is correct. [S01](https://fits.gsfc.nasa.gov/standard40/fits_standard40aa-le.pdf), [S02](https://fits.gsfc.nasa.gov/fits_primer.html)

Separate `session`, `observation/event`, `ingest batch`, `file/blob`, `image plane`, `derivative`, and `annotation` IDs. A derivative record should identify its source asset(s), producing tool and version, parameters/settings, author or service, creation time, output hash, chosen HDU/plane, dimensions, and any crop/scale/rotation/flip mapping. Link a processed image to its parent without replacing the original. Keep raw header values and provenance next to any normalized fields, with parser identity, rule/version, and “unparsed/ambiguous” status; never silently promote a header field into a verified fact. This is a compact application of PROV-O’s Entity/Activity/Agent and `wasDerivedFrom` / `wasGeneratedBy` relationships, not a requirement to implement RDF. [S06](https://www.w3.org/TR/prov-o/)

For a repeat import, verify file length and hash before linking to an existing blob. Keep a separate import/observation record even if the exact bytes already exist. Upload to a staging area, record per-file progress and errors, and publish the file into the catalog only after the complete byte count and hash match. Make finalization idempotent so retry after a disconnect creates neither a second observation nor a partial “complete” file. Preserve failed items with a resumable status and a clear retry/export action.

### Time and display semantics

FITS v4 specifies that `DATE-OBS` refers to the start of an observation unless comments explain otherwise; it is expressed in the HDU’s principal time system/scale, and explicit scale is recommended. FITS v4 defines `TIMESYS` for time-related keywords and says UTC is assumed when it is absent. ISO-looking text alone does not identify every scale or validate the clock. Preserve the submitted keyword/comment and scale; expose a normalized candidate only with its exact source and parsing status. For non-FITS sources, keep the user-entered value and its stated zone/scale separate. [S01](https://fits.gsfc.nasa.gov/standard40/fits_standard40aa-le.pdf)

FITS HDUs can hold cubes, tables, and data not suitable for a simple 2-D preview. Preview only a supported selected image plane/HDU, record the selection and display stretch, and show an explicit “original retained; preview unavailable” state for unsupported or malformed content. Do not alter the original or imply that a display stretch, supplied target label, time, or annotation is scientifically correct.

Astropy v8.0.1 documents a consequential coordinate distinction: high-level WCS pixel methods use zero-based Cartesian `(x, y)` coordinates, with the first pixel centered at `(0,0)` and spanning `-0.5…+0.5`; low-level methods accept an origin of 0 or 1; methods named `pixel` and `array` use different axis orders. The pinned implementation’s `array_index_to_world` reverses index order before calling `pixel_to_world`, and the pinned tests exercise high-level conversion behavior. Thus no code should mix FITS 1-based coordinates, NumPy `(row,column)`, and display `(x,y)` without an explicit conversion. Astropy is an optional WCS/metadata library candidate, not a verified detector or metadata validator; its own docs note that a WCS transformation can be absent or limited by the header. [S03](https://docs.astropy.org/en/v8.0.1/wcs/index.html), [S22](https://github.com/astropy/astropy/blob/7c5a9c124ce84c76992016e89631566ad398aff7/astropy/wcs/wcsapi/high_level_api.py), [S23](https://github.com/astropy/astropy/blob/7c5a9c124ce84c76992016e89631566ad398aff7/astropy/wcs/wcsapi/tests/test_high_level_api.py)

### Durable annotations

Replace A-P4’s “position on the currently displayed preview” as the durable anchor. Store each region/comment against an immutable asset/derivative ID, exact dimensions, HDU and selected plane, plus an explicit coordinate convention and transform to the display preview. A workable first proposal is 0-based image pixel coordinates (`x` right, `y` down), with integer positions denoting pixel centers as in Astropy’s high-level WCS API; persist fractional positions if the UI permits them. Serialize rectangles with a declared `xywh` convention and bounds checks. Tests must establish how displayed zoom, stretch, crop, rotation, mirroring, and pixel centers map back before this schema is accepted.

The W3C Web Annotation model gives a portable shape for a text body and a target-specific selector; its selector model points at a segment and names the fragment specification. IIIF Image API 3.0 separately defines image regions in pixels or percentages, with the upper-left image origin and dimensions tied to the full image. Borrow those explicit target/selector ideas, but keep a small JSON subset unless interoperability with a IIIF server is an actual need. [S04](https://www.w3.org/TR/annotation-model/), [S17](https://www.w3.org/TR/selectors-states/), [S05](https://iiif.io/api/image/3.0/)

When an image is replaced or reprocessed, keep the old asset and its annotations available and mark the anchors as tied to that older version. Show them as stale against the new derivative, request human confirmation/re-anchoring, and record the re-anchor event. Do not silently remap a region using WCS or image similarity. Add polygon/sky-coordinate anchors only as optional later work after representative data validates their conventions. Comments stay ordinary member text, never automatic scientific classifications.

## Identity, sharing, deletion, recovery, and export

Keep private drafts local until submit. On the server, distinguish private draft, submitted-for-review, and club-visible states. Members may contribute to club-visible discussions according to an explicit per-record permission; coordinators manage member access, asset publication/withdrawal, and deletion requests. Store author ID and server receipt time separately from client edit time. Apply ACL checks to metadata, previews, original files, derivatives, exports, and direct download URLs. PouchDB/CouchDB 3.5’s documented database `members` role can read and write all ordinary documents in its database, which is why direct use of one shared database is not enough for the proposed private/public boundary. [S14](https://docs.couchdb.org/en/stable/api/database/security.html)

For the recommended API design, a note has immutable revisions or an append-only edit history. A client submits its `If-Match` revision; if another member has changed it, preserve the stale draft and show a comparison/resolve action. No “last submitted wins” rule is safe for overlapping edits. Deleting an annotation or asset should first withdraw it from normal access, then follow a club-approved retention and purge rule across blobs, database references, backups, and exports. A withdrawal from the service cannot recall copies already downloaded into a member’s packet; state that at export and withdrawal time. Keep the policy open until the club chooses retention periods and who may authorize purge.

For handoff, adopt a BagIt 1.0-compatible folder/ZIP with `data/`, a UTF-8 JSON manifest describing selected records and provenance, and `manifest-sha256.txt` for every payload file. RFC 8493 requires a payload manifest to list every payload exactly once with a checksum and path relative to the bag. Include originals, chosen derivatives, selected annotation history, schemas/readme, and raw plus normalized metadata. Exclude private drafts, credentials, internal tokens, and unrelated member data by default; an explicit selection controls what is included. Receiver validation should check safe relative paths, checksum and manifest completeness, then report missing or unsupported content. Hash validation proves package-byte integrity, not scientific truth, archive longevity, or the identity of whoever created the packet. [S16](https://www.rfc-editor.org/rfc/rfc8493.txt)

## Proposed validation and optional leads

These are acceptance checks to run in a later authorized test phase; none was run here.

1. **Format/metadata fixture set:** FITS primary image, image extension, cube, table-only file, common JPEG/PNG, malformed FITS, and missing/ambiguous headers. Verify byte-for-byte original preservation, cataloged format/HDU/plane, explicit unavailable-preview status, no data overwrite, and raw vs normalized metadata. Include `DATE-OBS` with `TIMESYS=UTC`, `TT`, `TDB`, no `TIMESYS`, and conflicting comments; verify stored raw text and recorded parser output without asserting clock truth.
2. **Ingest interruption:** disconnect after some chunks, resume, repeat the exact file, rename identical bytes, and import the same bytes for a distinct session. Verify incomplete content is not published, length/hash checks gate completion, retries are idempotent, the blob can be deduplicated while import/session records remain distinct, and error messages identify recovery steps.
3. **Annotation geometry:** use known synthetic pixel grids and varied dimensions; test each rectangle corner and pixel center through resize, crop, 90° rotation, mirror, and preview stretch. Verify location on the exact image plane, FITS/WCS axis-order conversion where enabled, boundary clipping, and stale marking/review after a new derivative. No telescope truth labels are needed.
4. **Offline/revision/access:** create a private draft offline, reconnect, submit and verify scope; make two edits from the same revision and verify one conditional write succeeds while the other is retained and shown for human resolution. Verify separate comments remain separate. Test direct metadata, preview, original, derivative, and export URLs for anonymous, ordinary member, coordinator, revoked member, and private-draft cases.
5. **Retention and recovery:** simulate interrupted server write, restart, backup restore, local browser data removal, denied persistence request, withdrawal, and purge. Verify UI distinguishes local-only, queued, verified, published, failed, withdrawn, and purged states; verify backup/purge behavior and disclose that already-exported packets remain outside server control.
6. **Export round trip:** export a selected session, verify every payload path/hash and manifest entry, inspect offline without a login, re-import into an empty test library, and confirm originals, chosen derivatives, annotations, provenance, and incomplete flags retain their identities. Verify private drafts and other sessions are absent by default.

Optional leads, not first-release requirements: Astropy WCS readouts after header suitability checks; a IIIF-compatible image service if remote region/tile delivery becomes useful; BagIt profile validation and digital signatures if packet authenticity later matters; multi-plane/cube visualization; polygon or sky-coordinate annotations only after pixel transforms and WCS input cases pass. No item turns member metadata into verified science.
