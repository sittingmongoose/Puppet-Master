## Assessment and recommendation

The researcher proposal has a strong, coherent core: preserve imported originals, separate file identity from observing-event identity, record derivative lineage, treat offline work as pending until acknowledged, make edit conflicts visible, keep annotations tied to an exact image version, and export a checksum-checked portable packet. These recommendations preserve the brief's negative constraints and most of A-P1–A-P7.

Keep the **server-authoritative revision model as the preferred collaboration behavior**, conditional on the club naming an operator and accepting that publication/review waits for connectivity. An offline draft/outbox may queue small notes and annotations, but should not be the sole copy of irreplaceable image bytes. Preserve the removable-media source until the server has verified the complete upload and the member has a recovery/export route. Do not yet select a database, authentication stack, web framework or image-processing pipeline. If the club cannot operate a server, the useful fallback is a portable file archive with immutable originals, explicit JSON annotation sidecars and file synchronization; the club must accept that sync conflict copies need human reconciliation and that folder sync does not provide per-record access control. A multi-master browser database is a credible third option only if the club values peer/device replication enough to take on its conflict, storage and authorization work.

The proposal is not ready to adopt unchanged. Its principal repair is to distinguish annotation geometry conventions: Astropy's WCS pixel coordinates identify pixel centers, while a rectangle's `xywh`/IIIF-style region describes an extent from an image origin. The proposal must name the mapping between them instead of saying integer rectangle positions are pixel centers. W3C Web Annotation supplies a portable annotation/selector model; it does not supply an annotation transport service or a FITS/WCS coordinate contract. Other evidence-backed repairs and limits follow.

## Independent source assessment and corrected claims

- **Conditional updates are a protocol primitive, not a complete conflict product.** RFC 9110 §13.1.1 requires strong entity-tag comparison for `If-Match` and requires the server to evaluate the precondition before performing the method; 412 is the defined precondition-failed response. This can prevent a lost update only if the service creates a strong tag for the relevant note/annotation revision and compares it atomically with the write. The RFC does not implement the revision store, preserve an offline rejected draft, or specify a user-facing merge. Keep the proposal, and add those application requirements plus a test for stale writes. [C03](https://www.rfc-editor.org/rfc/rfc9110.txt)
- **Browser persistence is fallible.** The Storage Standard permits best-effort buckets to be cleared under storage pressure and describes persistent-storage requests; a request is not a cross-browser durability guarantee. Keep the proposed unsent/queued state and recovery/export action, but do not imply that it protects source files or guarantees durable offline drafts. Retain the source copy until full server-side length/hash verification. [C04](https://storage.spec.whatwg.org/)
- **Image-region coordinates need two explicit spaces.** IIIF Image API 3.0 defines a region as `x,y,w,h` measured from the image's upper-left pixel origin, and specifies region → size → rotation → quality → format order. Astropy v8.0.1's high-level WCS API is zero-based Cartesian `(x,y)` with the first pixel center at `(0,0)`; array indices use a different axis order. These documented conventions are related but not interchangeable. Define a single UI/display transform and persist either bounds in a declared pixel-edge coordinate space or a documented center-based point model; convert explicitly when sending WCS coordinates. Test pixel-center and rectangle-edge cases, resize/crop/rotation/mirror, and HDU/plane selection. Pin every anchor to an immutable asset/derivative and dimensions. [C02](https://iiif.io/api/image/3.0/), [C13](https://github.com/astropy/astropy/blob/7c5a9c124ce84c76992016e89631566ad398aff7/astropy/wcs/wcsapi/high_level_api.py), [C14](https://github.com/astropy/astropy/blob/7c5a9c124ce84c76992016e89631566ad398aff7/astropy/wcs/wcsapi/tests/test_high_level_api.py)
- **Annotation standards do not establish this product's coordinate or transport behavior.** W3C Web Annotation models bodies, targets, selectors and resource states, and recommends selectors that identify a segment. It expressly leaves transport to a separate protocol. Use a small, documented subset or JSON sidecars; do not claim conformance alone makes FITS annotations portable or keeps anchors stable after image processing. [C01](https://www.w3.org/TR/2017/REC-annotation-model-20170223/)
- **FITS metadata must retain exceptions and provenance.** FITS Standard 4.0 says `DATE-OBS` ordinarily denotes observation start unless its comment gives another interpretation; the time scale is the HDU's principal scale, and explicit scale is recommended. FITS defines `TIMESYS` with UTC as its default, but the standard has legacy two-digit-year cases with no default start/middle/end interpretation. Preserve raw keyword, comment, HDU and source file; label normalization as a parser result, not truth. The proposal's broad UTC statement should carry those boundaries. Do not infer completeness or correctness of submitted metadata. [C06](https://fits.gsfc.nasa.gov/standard40/fits_standard40aa-le.pdf)
- **Portable package checks prove byte integrity only.** BagIt 1.0 gives a useful payload-manifest/checksum convention; checksum success says nothing about scientific correctness, creator identity, future availability, or downloaded copies being recalled. Keep the proposed packet and disclose withdrawal limits. [C05](https://www.rfc-editor.org/rfc/rfc8493.txt)
- **SQLite is suitable only in the topology its storage semantics support.** WAL allows readers while a writer is active, but still permits one writer at a time and relies on shared memory; it is not a database file to place in a folder synchronized among members or use as a remote shared store. A service may use a local database behind its API after concurrency, backup and recovery design; this is not a component selection. [C07](https://sqlite.org/wal.html)
- **File synchronization preserves versions, not collaborative meaning.** Syncthing's file-versioning documentation archives superseded/deleted files according to configuration. This is a recovery aid; it does not merge the meaning of two note edits, implement privacy roles or decide which version should be visible. It supports the portable-file alternative only with a human conflict workflow. [C08](https://docs.syncthing.net/v1.25.0/users/versioning)

## Competing mechanisms and trade-offs

| Mechanism | Fit and benefits | Costs / conditions | Disposition |
|---|---|---|---|
| **Server-authoritative service + client outbox + revision-conditional writes** | One club-visible record state; centralized publication, account revocation and checks on metadata and every binary route; stale edits can be rejected and retained. Works for low-connectivity entry followed by online review. | Requires a named operator, reachable service for shared review, update/backup/account-recovery work, atomic compare-and-write, and durable handling of queued work. A browser outbox is not a trusted archive. | **Preferred collaboration model, conditional** on operator and connectivity decision; do not select stack or database yet. |
| **Portable file archive + JSON/Web Annotation-shaped sidecars + folder sync/export** | Directly portable, can be inspected and backed up with ordinary files, suitable for capture away from the network and avoids a permanent vendor account. Syncthing versioning can retain replaced/deleted versions. | Whole-file conflicts need human triage; access is commonly folder/device scoped rather than per record; sync can multiply large files and does not ensure semantic merge. A local SQLite index must be disposable/derived, not a WAL database shared through sync. | Keep as the operational fallback or companion archive. Require a conflict/review procedure and never claim folder sync supplies application ACLs. |
| **PouchDB/CouchDB-style multi-master replication** | Replicates offline changes and checkpoints between peers/server; pinned PouchDB 9.0.0 code and tests show revision-difference replication and explicit divergent-revision/conflict retrieval. | Replication does not merge domain meaning. Conflicts remain to resolve; large attachments/browser quotas and real member privacy remain separate concerns. The code/test evidence is not a usability or multi-gigabyte guarantee. | Credible optional path if device-to-device replication is a demonstrated requirement; defer for minimum workflow. |

Do not equate the third option with either automatic conflict resolution or private per-record authorization. PouchDB issue #8298 reports intermittent browser-to-CouchDB synchronization failure for a particular Angular/service-worker/Chrome/IndexedDB setup; it is labeled stale, says it could not be reliably reproduced, and this inspection found no release-specific fix or applicability evidence. Do not use it to claim PouchDB 9 is broken or fixed for this workflow. Equivalent implementation-history evidence is the pinned replication code plus its integration tests and 9.0.0 release notes; these show implementation and regression coverage, but leave browser/version coverage, large-image transfer, current security/release status, and this product's auth topology unverified. [C09](https://github.com/apache/pouchdb/blob/194c0754bb482824c3cb07d6432c7b95707d0a72/packages/node_modules/pouchdb-replication/src/replicate.js), [C10](https://github.com/apache/pouchdb/blob/194c0754bb482824c3cb07d6432c7b95707d0a72/tests/integration/test.conflicts.js), [C11](https://github.com/apache/pouchdb/issues/8298), [C12](https://github.com/apache/pouchdb/releases/tag/9.0.0)

## Integrated proposed workflow

1. **Identity and ingest.** Give a club, session, planned observation/event, ingest attempt, source file/blob, image HDU/plane, derivative and annotation distinct stable identities where they are useful; keep the entity boundary for “observation/event” open until members decide whether one session can contain multiple observations. Preserve original relative path/name, byte count, cryptographic hash, submitting member, receipt time, supplied metadata and import batch. Equal hashes establish equal bytes only; preserve separate event/import records if needed. Copy, do not rewrite or move the only original. Stage uploads and expose per-file progress/errors; finalize idempotently only after length/hash verification. Repeated/interrupted imports must resume safely, avoid publishing partial files, and leave a visible recovery/export path.
2. **Metadata and preview.** Retain raw metadata with source file/HDU, parser/version and parse status; keep normalized time/target values alongside it as unverified candidates. A FITS file may contain multiple HDUs, cubes, tables or data that cannot be shown as one ordinary picture. Preview only a supported selected HDU/plane and record that selection, dimensions and display transform/stretch. If unsupported/malformed, preserve the bytes and report “preview unavailable”; do not imply astronomy truth or silently rewrite FITS. Astropy/WCS can be an optional readout after suitability checks, not a validator.
3. **Derivatives and annotations.** Keep each processed image as a new immutable derivative with source IDs/hashes, tool/version, settings, author/service, time, selected plane, dimensions and crop/scale/rotate/flip mapping. Anchor a comment/region to the exact version and plane it annotates; preserve it when another derivative appears, mark its status stale against the new image and require a person to re-review/re-anchor. Do not move coordinates automatically through WCS or image similarity. Use a documented geometry schema that distinguishes pixel centers from rectangle edges and display coordinates, stores bounds/dimensions and defines coordinate origin and axis directions. Start with rectangles and text only; polygons/sky coordinates are optional after fixture validation. Comments remain member-authored text, not automatic classifications.
4. **Identity, collaboration and access.** Preserve member/coordinator roles and private draft vs submitted vs club-visible states from A-P5. On a server route, authorize every metadata, preview, original, derivative, export and direct-download request, and test revoked/private cases. For edits, issue a strong per-record revision tag and atomically reject stale writes; keep the rejected local draft, show both revisions and let a person resolve. Independent comments can be separate append-only records. Record author identity and server receipt separately from client edit time. Do not silently choose a winner by arrival time. Decide account recovery, member revocation and who can publish before deployment. For file sync, describe its weaker folder/device privacy and human conflict process.
5. **Retention, withdrawal, recovery.** Separate working source media, club originals, derivatives, database records, service backups and packets already exported. Define who can withdraw/purge and the retention window before implementation; withdrawal from the service cannot recall copied packets and purge must address backups per the selected policy. Name the operator and verify backup/restore and account recovery. Distinguish queued, verified, published, failed, withdrawn and purged states to members. Do not turn storage persistence requests or sync versioning into a backup promise.
6. **Handoff.** Export a user-selected packet that can be inspected offline without a live service/account. Use a BagIt-compatible structure with payload checksums, an application manifest/schema, originals, selected derivatives, selected annotation/history, provenance and incomplete-entry markers. Exclude drafts, credentials, internal tokens and unrelated member data by default. Provide a receiver check for safe relative paths, checksum and manifest completeness; report missing/unsupported items. State that hash checks establish package-byte integrity, not scientific validity or authorship, and exported copies are outside future service withdrawal.
