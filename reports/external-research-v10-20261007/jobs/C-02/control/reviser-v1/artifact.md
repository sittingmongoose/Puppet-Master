## Recommendation and alternatives

Start with a **single-club service that owns published state**, with a modest web review interface and a local draft/outbox for low-connectivity entry. Store original and derived image bytes as separate immutable files in club-controlled storage; keep metadata, permissions, revisions and provenance in a service-owned catalog. Leave the web framework, database, account system, image decoder and hosting choice open until a club member agrees to operate, back up and restore the service. This direction avoids a required permanent commercial account and supports a clear publish boundary; it still has real hosting and operator costs.

Use a durable submit protocol: stage uploads, report per-file state, resume interrupted transfers, and publish only after length and SHA-256 verification. Keep the camera/removable-media original until the server confirms verification and the contributor has a recovery/export path. Save offline notes in an explicit local queue and offer a downloadable session packet; browser storage is a convenience, not the only copy. The club shares and reviews records after reconnection, rather than silently merging disconnected whole-record edits.

| Mechanism | Benefits for this brief | Trade-offs and decision |
|---|---|---|
| **Server-authoritative API with local outbox and conditional writes** | One visible published state, central member revocation and access checks, works with offline drafts followed by later review. RFC 9110 gives a lost-update primitive: strong `If-Match` comparison must be evaluated before the state-changing method; a false condition fails (normally 412). [HTTP01](https://www.rfc-editor.org/rfc/rfc9110.txt) | The app must atomically compare and write, preserve rejected drafts, present a human resolution flow, and maintain backups/accounts. Shared review waits for connectivity. **Preferred direction**, conditional on a named operator and acceptance of these duties. No web stack or database is selected. |
| **PouchDB/CouchDB-style multi-master replication** | Each device can make offline changes and later replicate; PouchDB supports retry/checkpoints and CouchDB replicates divergent revisions. The deterministic displayed winner does not merge the losing edit: the application must find and resolve conflicts. [PDB03](https://raw.githubusercontent.com/pouchdb/pouchdb/194c0754bb482824c3cb07d6432c7b95707d0a72/docs/_guides/replication.md), [CDB01](https://docs.couchdb.org/en/stable/replication/conflicts.html) | More recovery and conflict UI, browser-storage and large-file sizing work, plus a separate permission design. CouchDB database membership is database-scoped, not a private-draft-per-record mechanism by itself. [CDB02](https://docs.couchdb.org/en/stable/api/database/security.html) Keep as an optional path only if device-to-device sync becomes a demonstrated need; do not treat “sync” as semantic merge or privacy. |
| **Portable directory/packet with JSON sidecars and optional folder sync** | Most directly inspectable and moveable; useful at the telescope site and as a fallback if no one can operate a service. BagIt provides a payload manifest/checksum pattern. [BAG01](https://www.rfc-editor.org/rfc/rfc8493.txt) | Whole-file conflicts need people to compare versions. Folder sync does not understand note meaning or provide per-record authorization; versioning can aid recovery but is not a semantic merge. [SYNC01](https://docs.syncthing.net/v1.25.0/users/versioning) Keep as the offline handoff and service-free fallback, with an explicit conflict procedure. Do not sync a live SQLite WAL database among members; WAL depends on same-host shared memory and still has one writer. [SQL01](https://sqlite.org/wal.html) |

The third-party standards are analogies and exchange options, not preselected services: W3C Web Annotation models a body, target and selector [WA01](https://www.w3.org/TR/2017/REC-annotation-model-20170223/); Media Fragments and IIIF define image-region syntax and processing conventions [MF01](https://www.w3.org/TR/media-frags/), [IIIF01](https://iiif.io/api/image/3.0/); BagIt packages payload and checksum manifests. None defines this club’s FITS/WCS geometry, application transport, authorization or merge policy.

## Proposed minimum workflow and data decisions

### Session, identity, ingest and provenance

Give the club, planned observation, session, ingest attempt, submitted file, image plane, derivative, note and annotation separate stable IDs where they represent separate things. Keep the distinction between an observing “event” and a session open until members say whether one session can include several observations. Use a cryptographic digest for byte identity only: equal hashes can deduplicate storage, but do not prove that two files represent the same observation, that a rename is a new event, or that supplied metadata is true.

For every import record the original relative path and filename, byte count, SHA-256, submitter, client time as supplied, server receipt time, import batch, detected format and validation/preview status. Preserve the submitted bytes unchanged. Stage each upload; show pending, uploading, verified, published, failed and withdrawn states; make retry/finalization idempotent. A retry after interruption must not create a second completed import or expose partial bytes. Keep raw header/sidecar values beside any normalized candidate, with parser name/version and parse status. Do not silently promote parsed metadata into verified astronomy facts.

### Formats, time and preview boundaries

FITS is a structured interchange file with HDUs and arrays of one or more axes, not necessarily one ordinary 2-D picture. Its array indexing starts at 1 and axis order can differ from the display’s `(x,y)` and a programming library’s `(row,column)` convention. [FITS01](https://fits.gsfc.nasa.gov/standard40/fits_standard40aa-le.pdf), [FITS02](https://fits.gsfc.nasa.gov/fits_primer.html) Preserve unsupported or malformed files and show “preview unavailable”; for a supported preview, record the selected HDU, plane, dimensions, stretch and display transform. Do not make FITS the only accepted format: treat actual member files as a later validation input.

FITS 4.0 defines `DATE-OBS` as the observation start by default unless the comment explains otherwise, and says its scale is the HDU’s principal time system/scale; explicit scale is recommended. Its time defaults depend on the date representation, and `TIMESYS` has a defined default in its own context. Preserve the original keyword, comment, HDU and raw value; show normalization only as a parser result with source/scale and ambiguity status. For non-FITS inputs preserve the member’s value and stated zone/scale separately. [FITS01](https://fits.gsfc.nasa.gov/standard40/fits_standard40aa-le.pdf) The service must not claim it validates a clock, target, image, or observing metadata.

### Annotation geometry: explicit local convention

**Repair to the researcher proposal and critique:** “integer rectangle positions are pixel centers” is ambiguous and is withdrawn. Astropy v8.0.1 documents high-level WCS pixels as zero-based Cartesian coordinates whose first pixel center is `(0,0)` and whose pixel spans `-0.5…+0.5`; array-index methods use a different order and the pinned implementation reverses indices before `pixel_to_world`. [AST05](https://docs.astropy.org/en/v8.0.1/wcs/index.html), [AST01](https://github.com/astropy/astropy/blob/7c5a9c124ce84c76992016e89631566ad398aff7/astropy/wcs/wcsapi/high_level_api.py), [AST06](https://github.com/astropy/astropy/blob/7c5a9c124ce84c76992016e89631566ad398aff7/astropy/wcs/wcsapi/low_level_api.py), [AST02](https://github.com/astropy/astropy/blob/7c5a9c124ce84c76992016e89631566ad398aff7/astropy/wcs/wcsapi/tests/test_high_level_api.py). W3C `xywh` and IIIF region coordinates describe regions from an upper-left image origin; they do not establish a FITS/WCS contract. [MF01](https://www.w3.org/TR/media-frags/), [IIIF01](https://iiif.io/api/image/3.0/)

Proposal for a small application-owned schema, subject to synthetic-grid validation:

- Target an immutable asset/derivative ID and exact dimensions. For FITS also store the zero-based HDU ordinal, selected plane’s zero-based array indices and declared axis mapping; retain `EXTNAME`/`EXTVER` when present.
- Store rectangles in `image-plane-pixel-edges-v1`: origin `(0,0)` at the top-left boundary; x increases right, y down; extent is `[0,width] × [0,height]`. A sample at array `(row,column)` occupies `[column,column+1) × [row,row+1)` and its center is `(column+0.5,row+0.5)`. Store finite bounds and reject out-of-range geometry.
- Record the affine transform from the displayed preview to that plane (including crop, scale, rotation and mirror) and invert it before saving. Stretch changes appearance, not geometry. For optional Astropy high-level WCS conversion, map an edge-space center `(x,y)` to zero-based pixel-center coordinates `(x−0.5,y−0.5)` and map `(row,column)` to `(x,y)` explicitly. Do not hand-convert FITS WCS fields outside a tested library path.
- Keep text and region anchored to the exact image version they describe. When a replacement/processed derivative arrives, retain old annotations and mark them stale against the new image; require member re-review/re-anchor and record that action. Do not auto-remap through WCS or image similarity.

This schema is an unvalidated proposal, not an assertion that a W3C or IIIF selector has identical half-open edge semantics. The first version may keep the geometry in a documented JSON sidecar, using a W3C-shaped body/target envelope only where useful; claim interoperability only after round-trip fixtures prove it.

### Collaboration, visibility, access and recovery

Keep A-P5’s member/coordinator distinction and explicit private draft, submitted-for-review and club-visible states. A note or editable annotation should carry a revision. Use a strong ETag and atomic `If-Match` on writes; on a stale revision, reject without overwriting, retain the local draft, display both versions and let a person resolve. Independent comments can be separate append-only records. RFC 9110 specifies the conditional request behavior, not this application’s revision store, UI, draft durability or merge policy. [HTTP01](https://www.rfc-editor.org/rfc/rfc9110.txt)

Browser storage can be evicted under storage pressure even though persistent-storage requests exist. [STORE01](https://storage.spec.whatwg.org/) Request persistence where supported, show whether it was granted, and offer a local packet/export; do not promise it is durable. Keep original files on member media until verified server receipt. Show when records are local-only, queued, rejected, verified or published, and give recovery instructions after storage loss.

Authorize every metadata, preview, original, derivative, export and download route; hidden controls or unguessable IDs are not authorization. Define who may invite/revoke members, publish drafts, withdraw material, restore accounts and export private data. Keep author ID, client edit time and server receipt time distinct. The role matrix and account-recovery mechanism remain unresolved until the operator and members are identified.

### Retention, withdrawal and portable handoff

Before deployment, choose retention periods, backup retention and who may authorize deletion. A withdrawal should remove material from ordinary service access; purge must cover metadata, source/derived blobs and backups according to that policy. A packet already downloaded by a member cannot be recalled by the service. Avoid promising deletion from others’ copies.

For selected-session handoff, export an offline-inspectable folder/ZIP with a BagIt-compatible payload manifest and SHA-256 checksums, a versioned JSON manifest/schema, originals, selected derivatives, provenance, chosen annotation history and incomplete-entry markers. Exclude private drafts, credentials, tokens and unselected sessions by default. A receiver should check safe relative paths, required manifest entries and checksums, then report missing/unsupported files. A checksum proves package-byte integrity, not authorship, scientific validity or long-term availability. [BAG01](https://www.rfc-editor.org/rfc/rfc8493.txt)

## Decisions, optional leads and unresolved conditions

**Decisions now:** recommend service-authoritative publication with a local outbox if an operator accepts hosting/backup/recovery duties; preserve media until acknowledged; keep records and image assets versioned and separately identified; use human conflict resolution; anchor regions to a specific immutable image plane with the explicit proposed coordinate schema; export checksummed portable packets. Do not select a database, authentication system, commercial host, image server or image-analysis pipeline now.

**Optional later leads:** PouchDB/CouchDB if true peer/device replication is wanted; a folder-only BagIt workflow if no operator exists; Astropy for read-only WCS display after test fixtures; IIIF region/tile delivery if large-image review needs it; polygon/sky-coordinate annotations only after the pixel model is verified. None is mandatory for the initial workflow.

**Open conditions:** who will operate and restore the service; likely image sizes/formats and what members need offline; whether private drafts need backup; what counts as one observation/event; permission to publish, withdraw and purge; retention and backup periods; acceptable conflict-review burden; account recovery; and whether packet receivers require authenticity signatures rather than corruption checks. These need club evidence, not researcher invention.
