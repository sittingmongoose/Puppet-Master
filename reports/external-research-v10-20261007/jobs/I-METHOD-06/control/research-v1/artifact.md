## Proposed replacement plan text

### 1. Authority and bounded product meaning

`Plans/Backup_Restore_System.md` remains the sole product owner for Project Backup, Full Server Backup, repositories and destination attempts, manifests, verification, test restore, retention, receipts, restore modes, and readiness. This story implements only one Project and two destinations. Internal recovery points, Settings transfer, Project Move, Duplicate With History, and Full Server Backup stay distinct products. Storage retains physical persistence and internal recovery; Settings retains configuration transfer; Project Sync retains Move authority transfer; credential and security owners retain custody and portability decisions. A research observation about an engine does not change those owners or imply runtime readiness.

A “copy” is a committed, independently addressable Project repository snapshot. The capture has one immutable `capture_set_id` and one manifest digest; each destination attempt records its own `repository_id`, immutable `snapshot_id`, upload/commit state, verification receipts, failure evidence, and retry identity. Two repository IDs establish separate repository authority. They do not alone establish separate disaster or compromise fate. Before the UI or a receipt calls the pair “independent,” record the pair’s material failure domains: administrator/account and credential authority, provider/control plane, region/site, network path, and online/offline or tested immutable protection. If important domains are shared or unknown, report “two copies; independence limited/unknown” and name the correlation. Do not silently infer independent protection from two paths, buckets, credentials, or successful uploads.

CISA recommends offline encrypted backups and regular availability/integrity testing; its ransomware guidance explains that reachable backups can be attacked with production systems. This supports recording a failure-domain choice and offering one protected/offline destination where the chosen adapter can prove it. It does not certify any destination family or dictate a universal provider. Exact family selection and Object Lock/immutability claims remain downstream release and security evidence. [CISA #StopRansomware Guide](https://www.cisa.gov/resources-tools/resources/stopransomware-guide) [S17]

### 2. Capture one coherent Project generation

The Server-owned `BackupCoordinator` captures through one version-pinned `BackupEngineAdapter`; the engine is not a second coordinator or canonical PM store. Storage supplies a `CaptureBarrierService` that flushes/closes the seglog boundary, exports non-rebuildable redb consistently, pins replay watermarks and CAS manifests, and identifies rebuildable Tantivy and declared projections. Freeze an immutable staging generation only after those owner receipts agree. Release the application barrier before network upload. Never copy open database/log files opportunistically or hold the barrier through a remote transfer.

The manifest binds the capture set to exact Project identity and source Host/Environment; app, storage, engine, and protocol versions/compatibility; the consistency vector and exact included generation references; every included relative path/object, family, size, and digest; exclusions and reasons; source-code inclusion and Git/Jujutsu closure; and destination-specific snapshot references as they become known. Keep saved files, durable recoverable editor buffers, dirty/uncommitted source, Git/JJ operation state, and unavailable process-only memory distinct. Do not manufacture a commit or JJ operation; do not claim process-only memory was backed up. Derived indexes are declared for rebuild and are never portable authority. A required unavailable source waits or yields a visibly partial result; it cannot replace the last complete recovery point.

The engine issue reviewed here makes this boundary concrete. Restic 0.18.1 issue #5667 showed an inaccessible malformed Windows source path could lead to a saved empty snapshot. The merged #21852 fix changed `filterExisting` to skip all `Lstat` errors, abort when none remain, and added `TestFilterExistingUnreadable`; release v0.19.1 explicitly lists both issue and PR. At the pinned v0.19.1 source, `runBackup` returns before opening the repository for no sources. With a mix of accessible and inaccessible roots it can still save a snapshot, then return `ErrInvalidSourceData`; therefore “snapshot ID emitted” is not capture completeness or success. PM must preserve that partial/error outcome per destination. This engine-level path filter still does not make a live Project generation consistent; the PM capture barrier remains required. [Restic issue #5667](https://github.com/restic/restic/issues/5667), [merged fix #21852](https://github.com/restic/restic/pull/21852), [v0.19.1 release](https://github.com/restic/restic/releases/tag/v0.19.1), [pinned source `cmd_backup.go`](https://github.com/restic/restic/blob/6aa3a516ce654808a1f28f9fa21e9b7c8e6e90bf/cmd/restic/cmd_backup.go), [pinned regression test](https://github.com/restic/restic/blob/6aa3a516ce654808a1f28f9fa21e9b7c8e6e90bf/cmd/restic/cmd_backup_test.go) [S01–S05]

### 3. Two destination attempts and truthful run state

Build the two attempts from the same frozen capture generation, using separate Project repository bindings and the admitted Restic adapter. The bounded default proposal is one separately reported engine operation per destination from that staging generation, so a failed first repository does not become the hidden read source for the second. Restic `copy` from one repository to another remains an option when product owners accept its dependency and cost: its documentation says different encryption keys require reading and uploading the snapshots, with additional bandwidth/cost and possible deduplication loss. It must still produce and verify a separate destination receipt. Rclone `copy` may be considered a bounded transport only after the adapter proves atomic publication, integrity, identity, and resumable partial-write behavior; raw file-copy output is not a PM snapshot receipt. Never use `rclone sync` against a live Project Vault: its documented behavior makes the destination match the source and can delete destination-only objects. [Restic repository-copy docs](https://restic.readthedocs.io/en/v0.19.1/045_working_with_repos.html), [rclone copy](https://rclone.org/commands/rclone_copy/), [rclone sync](https://rclone.org/commands/rclone_sync/) [S08, S14, S15]

Each destination has its own attempt state, lock, retention/prune authority, snapshot identity, error, and evidence. One destination failure cannot erase, downgrade, or turn the other green. In this two-copy flow, both committed destinations are required for the “two copies committed” terminal; one success and one failure is `partial`, with per-destination states retained and a retry scoped only to the failed attempt. Cancellation and restart follow the durable phase journal; missing journal or destination evidence never becomes success. A committed but structurally unverified copy, structurally verified copy, full-data-checked copy, and Restore-as-New-drilled copy remain different axes. Required versus best-effort verification governs terminal handling only; it never selects a verification depth.

### 4. Verification choices and evidence claims

Every verify dispatch names one immutable `backup_id` and `snapshot_id`, an explicit direct depth or current owner-resolved verification plan, and a typed admission for that exact target, scope, permission/currentness, cost class, and expiry. Producers present a depth/plan choice on every route. The owner revalidates the admission and never retargets `latest`, adopts a superseded plan, or silently narrows the request. The receipt keeps requested depth and performed scope; a pass requires them to match. A full read that was canceled or stopped early stays failed with its failure evidence. Only `cmd.backup.test_restore` can produce an isolated restore-drill receipt.

The evidence vocabulary is:

1. **Captured:** owner barrier and coverage manifest identify the immutable Project generation and exclusions.
2. **Committed:** this destination’s immutable snapshot/commit ID and manifest association are durable. It says nothing about later readability.
3. **Structural:** engine repository/index/snapshot/tree/reference checks pass for the admitted target. This does not read every stored data pack or prove application restore.
4. **Sampled data:** the exact admitted subset, algorithm/selection, and actually read packs/files are recorded. It gives partial data-read evidence and is never called full verification. For Restic, `--read-data-subset` selects data packs; a percentage is a random subset and is not a guarantee that repeated runs eventually cover all packs. A partition schedule may claim complete coverage only when all partitions cover a fixed, identified pack inventory.
5. **Full data:** all admitted data packs for the selected snapshot/repository scope are read by the pinned engine. Restic `check` defaults to structural consistency; `--read-data` reads all packs, while `--read-data-subset` reads a specified subset. This is a repository-format/data-read result, not proof that PM can import the Project or that required external credentials exist. Record bytes/pack scope, engine version, destination, snapshot ID, time, and errors.
6. **Restore as New drill:** the exact immutable snapshot is imported through PM into an isolated recovery target, gets a fresh Project ID with all identity-bearing references rewritten, passes staged and post-restore checks, and opens with expected durable content after declared derived indexes rebuild. This is the strongest proposed evidence that the snapshot can be recovered. Keep its environment, build/protocol versions, target recovery prerequisite, source snapshot, checks, and failures in its own receipt. Passing one copy does not confer a drill result on the other.

Kopia documents the same useful distinction: ordinary `snapshot verify` checks restore metadata/blob availability but stops short of downloading, decrypting, and decompressing the data; its 100% file-verification option reads and decodes all selected files; Kopia calls a restore the gold-standard validity check. This is an alternative mechanism, not evidence that a Restic adapter behaves identically. Its current documentation describes a 1% randomized daily sample as an operational compromise, not a deterministic full-coverage receipt. Borg 1.4.5 offers `borg check --verify-data` to read/decrypt/decompress all archive data, at significant cost; `--repair` is separate, read-only is the default, and repair can lose data. None of these engine checks proves PM identity rewrite, compatibility, or app-level readiness. [Restic check docs](https://restic.readthedocs.io/en/v0.19.1/045_working_with_repos.html#checking-integrity-and-consistency), [Kopia consistency docs](https://kopia.io/docs/advanced/consistency/), [Kopia verify CLI](https://kopia.io/docs/reference/command-line/common/snapshot-verify/), [Borg 1.4.5 check](https://borgbackup.readthedocs.io/en/1.4.5/usage/check.html) [S06–S13]

### 5. Restore as New in an isolated recovery environment

The recovery operator selects a specific `snapshot_id` from a specific destination, not `latest`; validates the destination/Kit trust and capability; authenticates and unlocks through protected Recovery Key submission; loads the encrypted manifest; reviews exact coverage, compatibility, excluded secrets, cost/retrieval constraints, and missing source/auth readiness; then produces a `RestorePreviewReceipt` and obtains approval. Preview/browse content stays untrusted and cannot execute or escape its sandbox.

Run Restore as New against a disposable, isolated recovery Server/workspace with a fresh namespace and no automatic source-network, agent, hook, macro, credential, or external-service access. Preserve the normal BRS-023 pre-staging target recovery prerequisite even for this drill. If an empty disposable target cannot produce the ordinary verified target receipt, the owner must specify evidence that satisfies that prerequisite; do not silently waive it. Stage into quarantine; verify staged hashes, schema/storage compatibility, path/identity mappings, and Project-ID non-collision; rewrite every identity-bearing reference; rebuild derived indexes from restored canonical bytes; post-verify actual load/read/use; report external reattachment and sign-in separately from data recovery. Activate only inside the isolated new Project through atomic or journaled recoverable boundaries. A refusal or failure leaves the live Project untouched. Test from each destination independently. A successful two-destination recovery claim requires a passing drill from both; otherwise show exactly which copy was not tested or failed.

Every mutating restore preserves the normal verified recovery-point requirement or the narrowly scoped BRS-023 alternative: verified unavailability plus current, explicit human consent bound to this restore/mode/target/preview/approval/idempotency. Consent neither creates a recovery point nor creates rollback capability. Browse, compare, verify, download, extract, and archive retrieval remain separate non-mutating operations. Existing `in_place`, `selective`, and `server_full` modes and Settings strategy stay retained by reference; this proposal adds no new mode and does not expand the Full Server implementation design.

NIST SP 800-34 Rev. 1 recommends testing system recovery on an alternate platform from backup media and documenting outcomes/lessons learned. Applied here, the drill should capture an after-action record with source snapshot and destination, compatibility/build identity, exact expected checks and results, actual missing dependencies, and corrective actions. NIST guidance supports this exercise shape; it does not certify Puppet Master or replace app-specific acceptance. [NIST SP 800-34 Rev. 1, §3.5.1](https://nvlpubs.nist.gov/nistpubs/legacy/sp/nistspecialpublication800-34r1.pdf) [S18]

### 6. Completion, readiness, and recovery claims

The operation record exposes independent capture completeness, each destination commit, integrity depth, and isolated restore-test state. “Two copies committed” requires two committed destination snapshots from the same capture set. “Integrity checked” states exactly structural, sampled, or full-data scope per snapshot. “Recovered successfully” requires the separately executed Restore-as-New drill and its post-restore checks. “Ready” additionally follows the retained owner’s source, credential, and compatibility classifications; a static plan, manifest, hash list, engine exit status, receipt schema, or concept UI is not runtime or recovery proof. Never inherit verification/drill evidence across snapshots or destinations. Never run repair automatically as part of verification.

## Alternatives, optional opportunities, and rejected leads

- **Restic `check` depth:** suitable candidate because it offers a structural default, full pack reading, and explicit subsets. It must not produce a PM restore-drill claim. Its per-repository tests do not prove the PM app can reconstruct this Project.
- **Kopia:** useful verification vocabulary and optional full-file reader. Current docs say default snapshot verify stops before downloading/decrypting/decompressing data. Issue #3605 reports Kopia 0.15.0 returning code 0 after ENOSPC during full verify; the captured issue was still open with no linked PR. This is a historical caution, not evidence that current Kopia remains defective. Before adopting it, verify current released source, regression tests, and error/exit behavior. [Kopia issue #3605](https://github.com/kopia/kopia/issues/3605) [S10–S12]
- **Borg:** useful alternative for full encrypted content verification, but not a reason to replace the retained Restic candidate; its check still is not PM activation and `--repair` must remain a distinct, explicitly authorized, potentially lossy operation. [S13]
- **Restic `copy`:** supported cross-repository alternative with explicit read/upload bandwidth and deduplication tradeoffs. Use only if owners accept that one destination attempt reads from the other repo; it does not merge authority and is not a second coordinator. [S08]
- **rclone:** plain `copy` is less destructive than `sync` but neither defines capture consistency, committed snapshot identity, per-destination evidence, or a safe PM completion receipt. `sync` is rejected for a live Vault because destination-only content may be deleted. [S14–S15]
- **Optional opportunity:** an offline/immutable destination and scheduled full-data verification or Restore-as-New cadence can improve recovery evidence. The cadence, extra storage/egress, permissions, and any Object Lock assertion are choices for product/security/release owners; no cadence or cloud price is asserted here.

## Concrete validation proposals

These are proposed checks for a later authorized implementation sandbox; none ran here.

1. **Input/source completeness:** all source roots accessible yields a complete immutable capture; all roots inaccessible yields no snapshot/commit; one required root inaccessible with others available returns explicit partial/error, never green. Exercise malformed Windows paths, ENOTDIR, permission denial, offline source, disappearing source, and failure during read. Keep an engine-emitted snapshot ID when present but do not count it as a complete capture.
2. **Barrier and generation:** inject Project mutation, redb transaction, seglog append, replay watermark movement, CAS update, Project move/removal, and editor-buffer changes at each capture barrier boundary. Verify exact recorded generations; ensure network upload starts only after immutable staging and barrier release; verify no live database file was copied.
3. **Two destination outcomes:** in temporary repositories, succeed both, fail destination A before upload, fail B mid-write, lose a destination after commit, and kill the process before/after commit marker. Verify each attempt retains its own snapshot/error/evidence; one success plus one failure is partial; retrying B cannot rewrite or erase A’s last verified snapshot. Validate the declared failure-domain summary against actual test credentials/accounts/locations before testing any independence badge.
4. **Verification depth:** for each immutable snapshot test structural, sampled, and full-data admission. Corrupt a manifest/tree/reference and a data pack separately. Confirm structural scope does not claim full data; subset output records actual packs/sampling; all deterministic partitions apply to a fixed inventory; full-data cancellation and resource failure stay failed; requested/performed mismatch and stale admission fail; no automatic repair or silent target switch occurs.
5. **Restore as New:** drill separately from each destination in a fresh isolated target with a new Project ID. Check collision rejection, all identity-bearing references rewritten, FileSafe path/Unicode/traversal/case conflicts, excluded secrets, missing source/auth states, schema/storage compatibility, full file/content read, derived index rebuild, app open/read invariants, and post-restore receipt. Inject crash at quarantine, staging, activation, and receipt publication; prove live Project untouched and rollback only when a real recovery point exists. Validate the BRS-023 prerequisite for an empty target before calling the drill complete.
6. **Evidence/readiness:** test schema-positive and negative fixtures, all receipt joins, retention holds and per-destination state; separately run fresh backup–restore–restart drills before any readiness claim. Report unavailable lanes `not_run` with named risk. Static schema/validator success never advances runtime readiness.

## Remaining choices and uncertainty

1. Define the minimum destination failure-domain differences needed for “independent” and whether both attempts are mandatory before the user can call the bounded flow complete.
2. Choose concrete destination families and whether one must be offline/immutable; capability and security evidence is adapter-specific and absent here.
3. Decide whether a separately uploaded pair from immutable staging or Restic `copy` is the preferred product behavior after measuring bandwidth, egress, recovery independence, and retry cost.
4. Pin the implementation Restic release only after platform, tool provenance, license/SBOM, security, protocol, and update/rollback gates. v0.19.1 is the examined release, not an unconditional product lock.
5. Set verification admission costs, sampled cadence, full-data cadence, and Restore-as-New drill cadence with real workload and destination cost data. Random sampling has no deterministic proof of complete coverage.
6. Specify a valid BRS-023 target recovery receipt for a fresh, empty isolated test environment; no bypass is proposed.
7. Resolve actual identity/reference rewrite coverage and expected app-level restoration invariants with the Project/Storage owners. The frozen slice does not include the cross-referenced owners’ full implementation contracts, so this proposal does not claim whole-project coverage.
8. O5 remains pending the prospective fresh critic. Any new objection after that review remains open rather than being silently dismissed.
