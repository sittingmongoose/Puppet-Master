# Small ensemble score desk — research and planning proposal

**Assignment:** C-03/control/researcher-v1, independent research arm.  
**Inputs:** the held-out brief at `cases/C-03/BRIEF.md` (SHA-256 `2ef73187a614d42d74b8043b977d2f3ce3dbaee61123e5d92e0f81e1c73f40d4`) and frozen proposal at `cases/C-03/PLAN.md` (SHA-256 `7c61a4d148cd8ab135b4e077fb3566daa5ce566cbe176f6f8e3cbe103aaf10a9`), as named by the supplied input map. Public-source identities, URLs, capture times, versions/commits, locators, byte counts and SHA-256 values are in [`source-map.json`](source-map.json); captured bytes are under [`sources/`](sources/).

## Recommendation

Keep the minimum product page-first and revision-aware. Preserve each authorized PDF, image, or notation file as an immutable input; let the librarian establish explicit work, edition, part, contributor and rights records; and let musicians mark the exact page image they received. Accept MusicXML as an optional authored input when supplied. Treat optical music recognition (OMR) as an optional, versioned derivative that is always unchecked until a person reviews a specified result against its source.

Use a page-region anchor as the dependable location, with an optional structured-score locator as a secondary clue. Do not claim that measure numbers, generated MusicXML, or similarly titled uploads establish equivalence between parts or editions. Keep personal markings in a private lane and shared rehearsal notes in a director-published lane. For the first useful workflow, use explicit publication revisions and queued suggestions rather than a multi-writer CRDT: only the director publishes shared notes, while members can read offline and keep private marks offline. This keeps the permission and merge story inspectable. Reconsider automatic concurrent merge only if pilot use shows a real need.

This is a proposal, not a selected implementation or a validated music-processing pipeline.

## Discovery, mechanisms, and evidence

The brief calls for mixed inputs and useful passage references under imperfect connectivity. Open discovery therefore began with the intake and representation problem: compare already-structured notation with image-first intake; compare image geometry with logical measure references; and check collaboration approaches that keep work available offline. The standards and implementation sources below were selected from those needs before using the frozen plan to identify specific amendments.

### Score intake and representation

| Mechanism | Benefits for this group | Costs and conditions | Decision |
|---|---|---|---|
| **Authored structured notation first** (for example, supplied `.mxl`/MusicXML, possibly rendered by a notation application) | Structured parts/measures can support navigation and may avoid recognition work. MusicXML 4.0 organizes scores as parts and measures, and supports partwise and timewise organization [S10](sources/musicxml-structure-tutorial-4.0.html). | It does not cover paper, photos, or many PDFs. Measures have file-local identifiers and display labels can differ from the `number` value; numbers need not be numeric, and `non-controlling="yes"` allows part barlines not to coincide [S09](sources/musicxml-measure-partwise-4.0.html). Conversion/re-engraving can change layout and identifiers. | Accept when members already have it; do not require it or treat it as the source of truth for the page they rehearse from. Preserve the uploaded file and identify any rendered derivative. |
| **Page-image first** (retain PDF/photo/scan, view and annotate the source page) | Covers every requested intake class and provides a stable, human-visible reference even when recognition fails. It allows the librarian to identify the exact edition and part before publication. | Visual marks alone do not supply semantic note search; region references do not automatically survive replacing a page or reflowing a notation file. A renderer and coordinate transform still need selection and testing. | Use as the dependable minimum. Anchor marks to an immutable page-preview asset, not a screen coordinate or a guessed measure match. |
| **Page image plus optional OMR** | Can generate a structured derivative from a scan and may help the librarian navigate or locate passages. Audiveris 5.11.0’s pinned README describes its exporter as writing a *subset* of OMR data to MusicXML 4.0 [S01](sources/audiveris-readme-5.11.0.md). The maintainers’ current handbook says `.omr` preserves OMR data that MusicXML cannot and describes MusicXML export as lossy [S19](sources/audiveris-export-handbook.html); that handbook is living and not pinned to 5.11.0, so confirm the detail on the candidate build. | Output is not a verified transcription. The export can lose OMR-specific information, and a passed processing stage is not proof that symbols or an export are correct. Audiveris is AGPL-3.0 [S02](sources/audiveris-license-5.11.0.txt); distribution/linkage choices need license review. Its 5.11.0 release includes a fix for some imperfect scans [S05](sources/audiveris-release-5.11.0.html), while a separate 5.11.0 export failure report remains open [S08](sources/audiveris-issue-971.html). | Defer from the core workflow. Pilot only with authorized material, explicit review, pinned build/settings, and the observable checks below. Never replace or hide the original. |

These mechanisms solve different inputs rather than compete for one universal format. The recommended model is therefore dual: immutable page/source files are the human reference; a supplied or generated structured representation is linked as a derived alternative with its own version and review state. Do not regenerate a score rendering and silently relink page marks.

### Pinned implementation and release history: Audiveris

The audited release is **Audiveris 5.11.0**, tag commit `9e1e55cd2746037d059345881c53e6a6754bffbd` (released 2026-07-11) [S05](sources/audiveris-release-5.11.0.html). This is the latest release identified by the official release endpoint during this research, not a claim about later releases.

The code at that exact commit was inspected, not executed. In `RunTable.java`, `afterUnmarshal` calls `afterMarshal(null)`, whose loop reads `sequences.length` without a null check [S16](sources/audiveris-RunTable-5.11.0.java). In `ZipFileSystem.java`, `open` calls `FileSystems.newFileSystem(uri, env, null)` [S17](sources/audiveris-ZipFileSystem-5.11.0.java). These implementation details are consistent with the failure route described by open issue #971: a null `sequences` during persisted-sheet reload, followed by a failure to reopen an already-open ZIP filesystem. The issue names build `9e1e55cd2746037d059345881c53e6a6754bffbd`, gives a multi-page reproducer, and was still open when checked on 2026-10-07 [S08](sources/audiveris-issue-971.html). This is maintainer-tracker evidence plus source consistency, **not an independently reproduced defect**. The issue links to a score on IMSLP; that score was not downloaded or used.

A separate fixed path shows why release pins matter. Issue #953 reports two null-pointer failures that abort batch export for imperfect/skewed scans [S18](sources/audiveris-issue-953.html). PR #954 changed `StaffBarlineInter.getBounds()` to allow a missing bounding rectangle and added guards plus debug logging when `MeasureStack.getXOffset()` lacks geometry [S06](sources/audiveris-pr-954.html), [S07](sources/audiveris-pr-954.patch). The exact 5.11.0 code contains those changes [S03](sources/audiveris-StaffBarlineInter-5.11.0.java), [S04](sources/audiveris-MeasureStack-5.11.0.java); the release notes list the imperfect-scan export fix [S05]. The PR describes manual checks against a 5.10.2 release build, but changes only two implementation files and adds no automated regression test. The release note establishes that the fix shipped, not that all imperfect scans now export. Issue #971 is an applicable counterexample to any broader guarantee.

Official handbook pages describe `-batch`, `-export`, `-save` and an output-directory option [S20](sources/audiveris-cli-handbook.html), but the handbook is not pinned to this release. If the pilot uses those commands, first verify command syntax and behavior against 5.11.0 itself. Do not make the tool a service or library dependency before resolving AGPL distribution implications and the unresolved 5.11.0 failure report.

### Annotation location mechanisms

Two useful location mechanisms were compared:

1. **Visual target:** page identity plus a rectangular or drawn region in a known image coordinate frame. This works for a scan even when no note-level representation exists, but it attaches only to that exact page representation.
2. **Logical target:** part and measure/event identity from a structured score. This can help after a layout change within the same file, but the MusicXML measure identifier is unique only within the document; displayed `text` may differ from `number`; implicit and non-controlling measures weaken simple cross-part matching [S09]. A logical label is not a general cross-edition identity.

The Web Annotation Data Model is a useful analogy, not a complete score schema: it separates an annotation from its target and offers `SvgSelector` for a geometric region, while `TextQuoteSelector` is explicitly for normalized text with surrounding quote context [S11](sources/web-annotation-model.html). Notation symbols on an image are not ordinary selectable text. Media Fragments `xywh` defines rectangular `x,y,width,height` selection with a top-left origin and pixel or percentage units [S12](sources/media-fragments.html). This proposal adopts an explicit raster frame rather than PDF-native points because no PDF renderer or page-transform API has been selected.

**Proposed anchor record:** `source_asset_id`; `page_preview_sha256`; `page_index0` (zero-based source page); `preview_width_px` and `preview_height_px`; and a positive pixel rectangle `(x,y,width,height)` in the unrotated, orientation-normalized page preview, with zero-based top-left origin and half-open bounds `[x,x+width) × [y,y+height)`. Save the renderer/version and orientation/crop transform with the preview. The half-open bound convention is a product proposal, not a property claimed by Media Fragments. UI page labels may be one-based, but serialized indexes must name their base. Pencil-like marks should be sidecar vector strokes (ordered points in the same page frame and style/width, with pen metadata optional); text and region notes use the same target frame. Do not run handwriting recognition. An optional logical hint can contain `structured_file_sha256`, `part_id`, measure `id` when present, `number` and `text` as labels, plus any parser-specific event key. It is a search/re-attachment clue, never automatic evidence that a different part or edition is equivalent.

A changed preview hash means the old visual anchor is stale. Preserve the old target and note, mark it “needs reattachment,” and let a person accept or reject a suggested correspondence. Never silently move a mark to a similarly numbered measure or new page. This gives readable behavior when pagination differs: keep part-specific visual anchors, and allow the librarian to attach a clearly shared rehearsal instruction to separate anchors with a human-confirmed relation.

### Collaboration, offline use, and provenance

A shared CRDT (for example, the options described in Yjs offline persistence and Automerge conflict documentation) can keep local changes available and synchronize later. Yjs describes `y-indexeddb` local persistence as a distinct provider alongside a network provider [S14](sources/yjs-offline-docs.txt). Automerge documents automatic merge for many concurrent changes, but for concurrent writes to the same property it deterministically chooses a winner and exposes conflicts for application handling [S15](sources/automerge-conflicts-docs.html). These are **living documentation pages, not pinned code audits**; neither library is selected here. CRDT does not decide whether an annotation is personal or shared, who may publish it, what deletion means for offline replicas, or whether two concurrent edits mean the same musical instruction.

For the first workflow, use a simple revision protocol: director-published shared notes are immutable publication revisions; members download an identified revision and can read it offline; personal marks are private records keyed to the user and page; and any member suggestion for a shared note is a separate pending record carrying the revision it was based on. If the director publishes meanwhile, show the base as stale and require review. If two devices edit the same private note, keep both as a conflict or ask the user to choose; do not overwrite silently. This is cheaper to explain than merging live multi-author shared state and fits the brief’s single publisher. Revisit CRDT only if concurrent shared editing becomes a demonstrated requirement, after choosing and pinning an implementation and transport.

Model provenance in a small domain record rather than requiring RDF: source asset, uploader/contributor, supplied title and edition notes, rights/provenance note, import time, transformations/engine version/settings, outputs and hashes, and human review status/actor/time. This follows the useful distinction in PROV-O between entities, activities and agents and its `wasDerivedFrom` relation [S13](sources/prov-o.html); it is a design analogy, not a claim that PROV-O certifies rights. A content hash identifies bytes, not a work or permission. The librarian records authorization evidence; the software must not infer rights from file presence.

## Complete minimum workflow proposal

1. **Intake and identity.** Permit an authorized librarian to add a work, an edition, and its parts. Give each a stable local opaque ID; store supplied title, composer/arranger, publisher/edition statement, year/catalog labels and instrument/part names separately from those IDs. Each upload is a new immutable asset/version, with uploader, timestamp, byte size/hash, source type, supplied provenance/permission note, and any correction history. A matching hash may identify identical bytes but must not auto-merge distinct edition, contributor or rights records. Keep PDF/photo originals; accept an existing MusicXML/MXL file as an additional source. Validate a small documented set of formats/limits and surface parse failures without deleting the input.
2. **Render and optional interpretation.** Render a read-only page preview linked to the original page and fixed renderer settings. Show page count/index and the preview identity. Any OMR output is a separate derivative with input digest, engine name/version/commit, settings, generated-output digest and status (`unreviewed`, `reviewed`, `rejected`, or `stale`). Review state names exactly which page/source/output was checked, who checked it and when; replacement, rerun, or changed source makes it unreviewed/stale. Permit “reviewed with known errors”; never imply perfect transcription.
3. **Part and edition links.** Let a librarian explicitly link each part file to an edition and correct supplied labels before publication. Keep ambiguous equivalence unresolved; do not auto-match by title, measure number, page count or similar hash. Replacements create a new version rather than overwrite.
4. **Annotations.** Store annotation body, author, created/modified times, visibility, publication revision, and target anchor. Keep each musician’s marks private by default. Director notes become shared only after an explicit publish action. Where two parts paginate differently, create separate confirmed visual anchors under one shared rehearsal-note ID; do not pretend they occupy the same page. A replacement does not erase old marks: show them against their old source and ask for manual reattachment to a new source.
5. **Rehearsal and offline review.** Let the director select an ordered rehearsal list and publish the exact edition, part and note revision. A member may pre-download assigned published parts and read them offline. Show the packet/library revision and last-sync time, and mark edits/suggestions as pending. Offline personal edits remain private and queue until connection returns; pending shared suggestions remain unpublished until the director reviews them. Do not imply the downloaded view is current.
6. **Access, retention and deletion.** Use distinct librarian, director and member permissions (one person may hold more than one role): librarian manages intake/identity/rights and replacement; director manages rehearsal lists and shared publication; member reads assigned published material and writes their own private marks/suggestions. Enforce visibility on read, sync and export paths. Decide retention before importing a real collection: how long originals, derivatives, private/shared annotations, audit history and backups remain; how a user exports/deletes personal marks; and how a rights withdrawal is propagated. Deletion should create a sync tombstone until replicas have had a chance to process it, with a documented purge/backup window. Explain plainly that a file or packet already downloaded or printed cannot be remotely recalled. Protect local caches using available platform controls and provide a visible clear-local-copy action; offline access necessarily retains a local copy.
7. **Handoff/export.** Make a self-describing portable packet for the selected rehearsal: permitted part files or print-ready renditions, a UTF-8 manifest, and sidecar notes/anchors. Include work/edition/part local IDs and labels, source hashes, selected publication revision, selected note IDs/authors, generated time, OMR review status, rights/provenance text supplied by the librarian, and a short explanation of coordinate/page indexing. Default to excluding personal marks. If flattened shared-note printing is offered, create a derivative and retain the manifest/sidecar; never put a private layer in a shared export implicitly. Open the packet without a permanent commercial-account dependency. Export remains subject to supplied rights/permission.

## Proposed observable validation (none executed here)

Use only a small set with documented permission: one born-digital PDF, a clean scan, a skewed phone photo, an existing structured notation file, and two differently paginated/revised parts. Keep the source files private to that validation and do not use an example score without explicit permission.

- **Ingest/provenance:** after import and preview generation, compare original bytes/hash with intake; verify each source, preview and OMR export is separately identified and linked to the uploader, permission note, tool version/settings and output hash. Identical bytes with different declared provenance must not collapse identities.
- **Representation/recognition:** compare optional OMR output to the page and known authorized notation, record symbol/measure errors by page, verify unreviewed/rejected/stale states, and confirm a re-run invalidates review. For Audiveris, run only a pinned release in an isolated authorized trial; include the PR #954 imperfect-scan path and a multi-page case related to open issue #971. Compare a control build if its version/licensing and setup are approved. This proposal does not claim #971 has been reproduced or fixed.
- **Anchors/transforms:** place regions near page corners and staff lines, zoom/pan, reopen at several viewport scales, and confirm the same pixels map to the same saved page frame. Exercise rotation/crop normalization and verify index base in the exported packet. A preview hash change must mark the old target stale.
- **Cross-part/edition behavior:** use parts with different pagination, nonnumeric/display measure labels, and an explicit part with non-controlling measures; confirm that measure text alone never silently relinks annotations. A librarian-confirmed shared note should show its distinct target on each part.
- **Replacement/recovery:** replace one page and one part; confirm the old file/notes remain accessible under prior revision, the new target begins unreviewed, and no mark disappears or moves without explicit reattachment. Simulate a failed OMR parse/export and interrupted upload; retry should preserve the original and report which derivative is missing.
- **Offline/collaboration/access:** pre-download a published revision, disable connectivity, view it, make personal marks and queue a suggestion; reconnect after the director publishes a newer revision. Verify no personal mark is visible to another member or in a default packet; show the conflict as pending against its base revision. Verify unauthorized part IDs cannot be opened through both UI and export paths.
- **Retention/deletion/handoff:** exercise clear-local-copy, account/role removal, personal-mark deletion and rights withdrawal with an offline device and a backup window. Verify tombstones propagate and the UI warns that copies already downloaded/printed cannot be recalled. Export and open a packet in a clean environment without an account; inspect manifest identities, note visibility, source hashes, permission text, review state and region coordinates. Confirm optional flattening contains only selected shared notes.

Acceptance thresholds (such as OMR accuracy sufficient for a use case, cache expiration and recovery time) remain open product decisions and should be set with volunteer users and their actual authorized files. A successful import/render/export is not a musical correctness result.

## Optional opportunities and unresolved conditions

- Later compare a second notation-rendering/import component and a non-OMR mapping approach on licensed material. The current research does not establish a renderer, database, sync service, file-annotation library or portable package standard for the product.
- If rehearsal navigation by note/beat becomes valuable, prototype linking page regions to MusicXML event positions and investigate MEI as an additional structured format. Treat every mapping as source-file-specific until a person verifies it against the page and part.
- If simultaneous shared editing proves necessary, run a separate pinned-code and transport/security comparison of CRDT versus revisioned server merge. The captured Yjs/Automerge pages are discovery leads only; they do not establish current release behavior or a sufficient access-control/deletion design.
- The proposed packet includes score assets only when the librarian has recorded permission to distribute them to the named recipients. Rights, duration, backups, who can delete a shared note, and treatment of withdrawn works require the ensemble’s policy. No policy can revoke a printed or already copied file.
- The audited Audiveris issue is open and user-reported. Its source path is consistent with the report but has not been run or independently reproduced; no private or linked score was accessed. The proposed coordinate record has not been implemented against a renderer. The source-map’s living documentation is explicitly marked unpinned.
