# Small ensemble score desk — independent research and planning proposal

**Assignment:** C-03/treatment/critic-v1  
**Evidence date:** 2026-10-07 UTC  
**Admitted input:** the hypothetical user-level brief and frozen prospective plan, with byte hashes recorded in `source-map.json`.  
**Status:** planning proposal only. No product implementation, score transcription, WorkNodes, canonical Plans/main edits, or score corpus was created or used.

## Recommendation

Start with an image-first library and a librarian-maintained cue map. Preserve the exact authorized files musicians brought in—scans, photos, PDFs, or editable notation—as immutable source versions. Give the work, edition, part, asset version, cue, annotation, and published packet distinct local IDs. Record byte hashes and supplied provenance, while treating those hashes as evidence of byte identity only: a hash cannot establish that two files are the same edition or that the group has permission to share either one.

A musician must be able to rehearse from an ordinary PDF or image without network access or the application. Shared cues should point separately to each part's own page and visible landmark. A human-entered measure label remains helpful for discussion, but it is descriptive; do not infer equivalence across different editions or differently paginated parts from matching labels.

Keep original pages authoritative. Accept supplied MusicXML as an additional representation, and consider a renderer such as OpenSheetMusicDisplay only after the exact file flavor and visible content pass a small import review. Keep OMR outside the required path. If a future trial is justified, run it on eligible files, preserve the original, label every result unreviewed, expose the review status and originating tool/version, and require a named person to check the resulting passage against the source before it is shared as reviewed.

For this small group, publish numbered portable rehearsal bundles and accept separate, opt-in contribution bundles for later review. A librarian reviews changes and publishes the next release. Keep personal marks private by default and outside both shared packets and contribution bundles unless the musician explicitly selects them. This supports poor connectivity and avoids requiring a permanent commercial account; it does require a deliberate human merge step. Defer continuous synchronization until the group demonstrates that bundle handoff is too cumbersome.

## Discovery and options

I began from the brief's user problem—mixed authorized source files, edition and part identity, usable marks across different pagination, offline rehearsal, and later shared review—and searched public primary sources before examining the frozen plan for gaps. The initial sweep covered image-region annotation, symbolic music interchange and rendering, OMR, offline handoff, and collaborative publication. The useful distinction is not “paper versus digital”: it is whether a note is anchored to a particular page representation or to a checked symbolic representation.

| Mechanism | What it gives the ensemble | Main costs and failure modes | Disposition |
|---|---|---|---|
| Immutable page assets plus a region selector | A direct visual reference for scans, photos, PDFs after a defined page rendering, and any notation that cannot be parsed. Musicians see the exact page they will rehearse from. | A page region says nothing by itself about where another part reaches the same music; the librarian must map cues per part. Coordinate transforms and replacement pages need explicit handling. | Required first workflow. |
| Reviewed symbolic notation, such as supplied MusicXML | Structured parts, measures, note events, and opportunities for navigation or later semantic linking. A source may already be editable without OCR. | It may not preserve the supplied engraving or page turns, not every tag is supported by every renderer, and identifiers/labels are representation-specific. It cannot be treated as a verified musical reading without review. | Accept as optional alongside the original; only use semantic locators after validation. |
| OMR conversion from score image to notation | Can create a structured starting point where no editable notation was supplied. Audiveris offers an editor and a subset MusicXML exporter; HOMR offers a model-led image-to-MusicXML pipeline. | Recognition and export can fail or omit content. Correction workload is unknown for this group's repertoire. Dependencies, model weights, licenses, release practices, and input limits add maintenance work. | Optional research lead, never a prerequisite for intake, annotation, or a packet. |
| Human-authored cue map without event transcription | A librarian can create a handful of common rehearsal landmarks and link each one to the correct place in each part. | Requires manual care and review; it does not create a machine-readable full score. | Preferred cross-part alignment for the first useful workflow. |

The W3C Web Annotation Data Model is a useful analogy for a body (the note), target (the page or score asset), and selector (the chosen region). Its SVG selector describes a shape relative to its source resource, while position-only selectors can become brittle when the resource changes; a state can help identify the intended representation. Adopt these ideas selectively. Do not claim full W3C conformance unless a defined profile is implemented and validated. [S01]

### Component evidence and applicability

**Audiveris 5.11.0.** The pinned repository describes an integrated OMR engine and correction editor and exports a subset of its internal data as MusicXML 4.0. Its `ScoreExporter` builds a `ScorePartwise` object and marshals either plain XML or compressed MXL. `PartwiseBuilder` walks Audiveris score measures, assigns score-local measure labels, and marks an implicit measure; it creates MusicXML structure, not stable ensemble-wide work/edition/part identities. This code path supports treating exported notation as a derived, versioned representation rather than replacing the supplied file. [S04–S07]

The release history is mixed. Audiveris PR #954 merged two null-safety guards into `development` on 2026-06-21. The author reported manually rerunning photographed multi-meter parts on 5.10.2 after each guard changed a batch-export abort into MusicXML output. The guards return `null` for missing barline bounds and return `0` when measure geometry is missing, with debug logging added after review. The PR's public changed-file view lists two Java files and zero completed checks; it does not show an automated regression fixture. Release 5.11.0 includes the imperfect-scan export fix. The evidence supports a crash-recovery improvement, not accurate recognition or successful export for every score. [S04, S08, S09]

A separate issue filed against 5.11.0 reports that a seven-page book can reach the PAGE stage but produce no MusicXML during export because reloading a sheet structure throws an NPE and its recovery path fails. The report says pages 3–9 fail together while page 9 alone succeeds. At capture, the issue remained open, without a linked fix/PR or later release in the inspected release listing. This is a reporter's reproducible claim, not a failure reproduced here; the example score was not downloaded. It is nevertheless consequential for a proposed OMR path because a completed recognition stage is not evidence that the export will exist. [S04, S10]

**HOMR v0.7.0.** This is a competing model-led lead, not a selected dependency. Its pinned `main.py` preprocesses a raster image, runs segmentation and symbol recognition, and writes MusicXML; its `pyproject.toml` declares Python and ONNX Runtime dependencies, AGPL-3.0, and project version `0.1.0` even though the captured repository release tag is `v0.7.0`. The README advertises PDF input, but the pinned entry point calls `cv2.imread` and raises an unsupported-format error unless it gets an image; PDF support would require a separately designed rasterization step. The README also describes predicted `imgpos` coordinates as rough rather than pixel-exact and conflicts internally: its limitations paragraph says dynamics/articulation and related symbols are neglected, while its technical overview later claims those predictions. The entry point initializes weight handling before processing; offline use therefore needs a verified, pre-provisioned model-weight plan. These boundaries make HOMR worth comparing only if the group has photos that make a permitted trial valuable. No HOMR issue/fix/regression history was assessed, and no model was installed or run. [S18–S21]

**OpenSheetMusicDisplay (OSMD) 1.9.6.** The pinned code accepts a string, `Document`, or `Blob`; the implementation handles XML and MXL paths, then requires a `score-partwise` root and rejects other MusicXML document forms. `render()` lays out a loaded sheet into a renderer. The pinned README calls OSMD a renderer, not an interactive notation editor, and lists MusicXML limitations. Its 1.9.6 changelog includes fixes around cursor/repetition behavior, PDF/SVG output, and grace-note positioning, plus measure-number CSS support. Thus it is a plausible optional renderer for a compatible MusicXML file, not an OMR engine, source PDF renderer, annotation store, or guarantee that a conversion matches the supplied engraving. No score file was loaded here. [S14–S17]

### Representation semantics that govern the proposal

MusicXML 4.0 is a W3C Music Notation Community Group Final Report, explicitly not a W3C Standard or Standards Track document. In its partwise form, `<measure number>` is a required token intended to identify that measure and to relate parts sharing the same left barline. It need not be numeric; pickup and other implicit measures can have special numbering; the optional `text` attribute can display a different measure label; measure-numbering instructions use `text` for display when present and otherwise use `number`. [S24] The optional measure `id` is unique only within that document. These semantics are useful inside a particular file, but they do not establish an identity across distinct editions or separately exported part files. [S02]

`<divisions>` gives the number of units per quarter note used by note durations; those divisions may account for tuplets and are not a count of seconds or pixels. If a future checked notation path adds event locators, bind each locator to the exact notation asset version and define how musical offsets are interpreted; do not compare raw duration integers from different files as if they shared units. [S03]

## Proposed integrated workflow and data

### Intake, identity, and provenance

1. The librarian creates a work record and an edition record, then attaches one or more part records. These are local IDs, not inferred from titles or filenames. Keep titles, composer/arranger, publisher, editor, instrument, transposition, and printed labels as supplied descriptive claims that a librarian may correct while preserving the original claim.
2. Each admitted file becomes an immutable `asset_version_id` with original bytes, SHA-256, byte count, detected format, page count/order where applicable, submission source, received date, and the edition/part the librarian assigned it to. A hash proves only byte identity. A replacement creates a new version and a `replaces` relation; never overwrite the old file.
3. Record authorization as a librarian-attested status, source/permission note, permitted audience/distribution, attribution, and any end date or restrictions. Unknown authorization remains unknown and blocks packet publication. Possession of a file is not a rights determination. The brief supplies no real score or permission record, so no rights policy was validated here.
4. Any preview, converted notation, or OMR result becomes a derived record pointing to the exact input hash and naming the tool/version/configuration, run date, and state (`unreviewed`, `reviewed`, or `rejected`). Store the result separately. Only a named reviewer can mark it reviewed, and that status says it was checked against its source—not that it is error-free.

### Passage, personal, and shared annotation

- A page mark targets an immutable page representation. For image assets, use a documented region selector relative to that full-resolution, orientation-normalized image. For a PDF, record the source PDF version, 1-based page, page rotation/CropBox facts, and the ID/hash of the exact page rendering used for the mark. Do not store zoomed-window pixels as durable coordinates. The PDF viewer and coordinate transform are unselected, so PDF coordinate conversion remains a validation item, not an established implementation fact.
- A `cue_id` is a human-maintained rehearsal point. It carries a label and one locator per relevant part: edition/part/asset version, page, visible measure text if any, region or passage hint, and a short landmark. A director note targets the cue and may also include a part-specific locator. If two parts paginate differently, the player follows their own locator. If the librarian cannot confidently map a cue, mark it unresolved instead of manufacturing equivalence.
- A musician's marks default to a local private scope. Shared notes are separate records created or published by the director/librarian. A musician must explicitly opt a private note into a submission bundle; the import preview shows exactly which notes and assets will be shared.
- Replacing a page or part never moves an annotation automatically. Preserve the old target and display it as belonging to the old version. A human may create a new re-anchored annotation that links back to its predecessor and records reviewer/time. If the same annotation was edited in two offline copies, preserve both proposals and ask the librarian to select, combine, or defer them; do not select by timestamp alone.

### Offline collaboration, publication, and handoff

The first collaboration model is explicit, immutable releases plus opt-in return bundles. The director prepares an ordered cue list. The librarian stages a release with authorized parts and published shared notes. Each member downloads it before rehearsal, can use the files offline, and keeps personal annotations separate. After rehearsal, a member may export selected suggestions tied to the exact release and asset-version IDs. The librarian previews and merges submissions into a new release; earlier releases remain identifiable until their retention rule expires.

A live shared service could make cross-device review faster and support centralized access management, but would add hosting, identity, authorization, security, backup, deletion-propagation, and offline-conflict duties. A replicated database or CRDT can help move/merge edits, but neither on its own selects the correct edition target, decides whether a personal mark is publishable, or revokes already-exported files. Reconsider a service only if actual usage demonstrates that bundles are inadequate and the group accepts its ongoing administrator and access model. These are architecture trade-offs, not claims that a particular sync API was tested.

A published ZIP should include a plain README, versioned `manifest.json`, ordinary PDFs/images and source notation permitted for that release, and machine-readable cue and published-annotation data. The manifest should name release ID/parent release, edition and part IDs, source file hashes, order, attribution and distribution restrictions, published note IDs, schema version, and file checksums. Members should be able to open the pages and read cue/annotation text without the app. Personal marks are omitted by default. A checksum detects accidental change; it does not encrypt, authorize, authenticate, or remotely revoke the copy. A standard package format such as BagIt can be considered later if interoperability justifies its additional format rules; no package standard was selected or implemented.

### Access, retention, deletion, errors, and recovery

Use three understandable capabilities for the initial workflow: librarian (intake, identity, rights, mapping, review, and publication), director (rehearsal list and shared-note drafts/publication when delegated), and member (read the published release, maintain private marks, submit opted-in notes). This is an intended workflow boundary, not cryptographic enforcement for a copied file. Do not put member email addresses or account secrets in portable manifests.

Before use, the ensemble must choose a retention period for active sources, derived files, private notes, contributions, and backups. The proposal is to retain each source version only while it remains authorized and needed for current/archived releases, delete the active asset and derivatives when no longer needed or permission is withdrawn, and make backup expiration explicit. The duration and any archival exception remain unresolved because no group policy was supplied. A local deletion can remove the item from that device; a new published release can omit a shared item; neither can recall a packet already copied by a member. Explain that limitation and any recipient notice process plainly. Do not promise deletion from backups or recipients until those mechanisms exist and are tested.

Imports should be staged and validated before changing the library. Verify checksums and schema version; detect duplicate submissions, stale releases, unknown part/edition IDs, malformed files, unsupported formats, and conflicting edits. Show an error with the affected file and a recovery action. An interrupted import/export must not publish a half-release. Keep a previous release available so a damaged new package can be withdrawn and republished from a known-good source set.

### Repaired claims and unresolved objections

- **Confirmed with narrower meaning:** the Audiveris 5.11.0 imperfect-scan patch exists and is in the release. Its geometry fallback can keep processing from aborting, but returning `0` is not proof that the recovered offset is correct. The new proposal treats it only as crash recovery. [S04, S08, S09]
- **Added material counterevidence:** the open 5.11.0 export issue means successful recognition-stage progress does not establish successful MusicXML delivery. We do not claim the reported failure is universal or reproduced. [S10]
- **Corrected input applicability:** HOMR's README advertises PDFs, but the pinned entrypoint expects an image readable by OpenCV and raises an unsupported-format error otherwise. PDF intake would need an additional, validated rasterization step. README output coverage is internally inconsistent, and the package metadata version differs from the captured release tag. HOMR is therefore a lead, not a selected component. [S18–S21]
- **Narrowed renderer claim:** OSMD is a renderer with a partwise MusicXML loader, not an editor, converter from scans, or general document rendering system. It must be exercised against actual authorized notation before selection. [S15–S17]
- **Preserved and refined plan coverage:** keep the original-file, human-review, role/publication, offline, and manifest intentions already in B-P1–B-P7. Add stable local identity and source-version links; use cue-specific per-part mapping; define opt-in personal-note handoff and explicit conflict review; clarify coordinate, deletion, and permission limits.

Still unresolved: which file formats the group actually uses; allowed redistribution/attribution; retention and backup duration; target operating systems; whether PDF page-region coordinates merit more effort than the printed page cue; whether any OMR result is worth volunteer correction time; which renderer preserves needed markings; who may publish; and whether future account-based sync is acceptable. Resolve these with the ensemble, not by assuming a software feature settles them.

## Observable validation proposal (not run)

1. **Intake and rights gate:** use a small, permissioned varied set of raster, PDF, and editable notation files. Re-import identical bytes and a changed replacement. Confirm separate source versions, hashes, part assignments, authorization states, and a blocked packet for unknown/withdrawn authorization. No public or private score set was used in this research.
2. **OMR value and failure review:** only if the librarian has eligible authorized printed pages, compare one clean scan and one phone image. Record whether the candidate accepts them, process failure, correction count/time, missing/changed symbols, export availability, and reviewer decision. Keep the original visible and output explicitly unreviewed. Compare Audiveris and HOMR only after their install/weight and licensing/distribution conditions are resolved; do not use note count as accuracy ground truth. Do not use the HOMR web demo or download weights for this proposal.
3. **Renderer and format:** feed known authorized partwise and timewise MusicXML, plus an MXL if in scope, to the exact pinned renderer. Observe accepted/rejected input, parse errors, visible markings, page/measure mapping, and differences from the original. Confirm an export/reopen retains the manifest and expected content. If timewise or unsupported tags are required, OSMD 1.9.6 is not applicable as-is.
4. **Coordinates:** place a region on a page with known orientation, rotation, and crop; reopen at a different zoom/window size and verify it overlays the same ink. Replace the page and confirm the old annotation stays bound to the old version. Test PDF CropBox/rotation with the selected viewer before fixing a coordinate schema.
5. **Cross-part cues and collaboration:** create one cue whose two parts use different pagination and labels. Confirm the shared note is intelligible at both specific locators and unresolved links are visible. Take the release offline, add private notes, export a selected contribution, import it twice, then submit two different edits to one annotation and a stale release. Confirm idempotent handling, private-by-default behavior, conflict presentation, and librarian publication only into a new release.
6. **Handoff, recovery, access, and deletion:** open the ZIP without the app, read README/manifest, check hashes, then alter/remove one file and confirm validation catches it. Interrupt a staged import and confirm no partial release appears. Check member/director/librarian capabilities and publication preview. Remove an active source/annotation and verify the stated derivative and backup policy; separately show that an already-copied packet remains with its recipient.
