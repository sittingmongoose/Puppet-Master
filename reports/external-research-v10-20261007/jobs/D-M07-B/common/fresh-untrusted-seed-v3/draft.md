Preliminary proposal: importing user-entered longitude/latitude via pyproj 3.6.1 (PROJ 9.3.0 assumed by brief), EPSG:4326 → EPSG:3857

P1. Order contract. Build one Transformer with Transformer.from_crs("EPSG:4326", "EPSG:3857", always_xy=True) so every call takes (lon, lat). Without always_xy, the authority axis order for EPSG:4326 is (lat, lon), and the shipped documentation warns axis order "may be swapped" when the first axis points north (projdoc, Transformer warning). The docstring example from_crs("EPSG:4326","EPSG:3857").transform(33, 98) returning easting≈10909310, northing≈3895303 confirms default-mode inputs are read as (lat, lon) (projcode, transform() example). Uncertainty: whether the upstream UI truly guarantees lon,lat per record. Proposed check: assert the source axis order via the CRS class, as projdoc recommends.

P2. Unit contract. transform() defaults radians=False: geographic input in degrees, output in the target CRS's linear unit — metres for EPSG:3857 (projcode, transform()/itransform radians parameter). Uncertainty: callers feeding radian data must set radians=True explicitly; no auto-detection is documented.

P3. Silent invalid input. With the default errcheck=False, a failed transform returns inf instead of raising (projcode, transform()/itransform errcheck docs). Poles and swapped coordinates are exactly the inputs that fail, so errors can propagate invisibly. Proposal: use errcheck=True on the interactive path, or check results with math.isfinite before use. Uncertainty: whether specific out-of-range inputs (e.g., latitude 98) raise, return inf, or extrapolate is not stated in the corpus; probe on the target environment.

P4. Pole boundary. Web Mercator diverges at the poles; neither projdoc nor projcode states EPSG:3857's usable latitude cutoff (projcode's transform()/itransform docs cover error returns, not latitude limits), so treat ±90° and near-pole inputs as unverified. Proposed check: probe transform(0, y) for y = 85, 89.9, 89.999, 90 and record value/inf/exception per case. Lead: if high latitudes are expected, gate inputs by the documented area of use rather than by an assumed cutoff (this lead uses general knowledge beyond the corpus and is marked as such).

P5. Applicability. Transformers expose area_of_use, and TransformerGroup orders candidate operations by area overlap and lists unavailable_operations for missing grids (projcode, Transformer.area_of_use; TransformerGroup docs). Proposal: read the selected transformer's area_of_use, record it, and treat out-of-region transforms as suspect — PROJ may fall back to a ballpark operation. Uncertainty: EPSG:3857's exact area polygon is not in the corpus; extract it at runtime.

P6. Optional batch opportunity (assessed separately). For bulk import, itransform streams points lazily in 64-point buffers, accepts a switch flag for systematically swapped tuples, raises ValueError on empty input, and restricts tuples to 2–4 coordinates (projcode, itransform implementation); transform() also accepts arrays. Threading caveat: Transformer keeps per-thread state (TransformerLocal), while transformers from TransformerGroup are documented not thread-safe (projcode). Uncertainty: no performance measured here; proposed check is a 10k-point timing comparison itransform vs array transform.

P7. Environmental dependency (kept visible). Behavior depends on the installed PROJ runtime and data: version-gated options exist (force_over requires PROJ 9+, only_best PROJ 9.2+, get_last_used_operation PROJ 9.1+), and grid/network availability shapes results (is_network_enabled; TransformerGroup.download_grids) (projcode). The frozen corpus holds pyproj 3.6.1 sources but not the PROJ binary or data; PROJ 9.3.0 is the brief's assumption and is unverified. Proposed check: log proj_version_str and the data directory at startup before relying on any gated option.

P8. Validation preservation. Perform the import only through supported documented interfaces — Transformer.from_crs, errcheck, area_of_use, and the CRS-class axis check named in projdoc — and avoid the deprecated module functions transform()/itransform(), which emit FutureWarning (projcode). Keep the order contract user-facing: detect and reject or explicitly normalize swapped coordinates instead of silently coercing them. Uncertainty: where swap detection best belongs (import path vs upstream UI) is a design choice the corpus does not settle, and the corpus gives no removal timeline for the deprecated functions, so the avoidance rule may need revisiting in later pyproj releases.
