# R1 evidence — RFC 8493 (BagIt V1.0), reviser independent re-read

Provenance: https://www.rfc-editor.org/rfc/rfc8493.html (Informational, Oct 2018).
Retrieved: 2026-10-07T18:45:28Z (HTTP 200, 63600 bytes; matches S1/C2 byte counts).
Range: S1.3, S2.1–S2.4, S3, S5.1–S5.4, S6.1.2, Payload-Oxum.

Independent observations (exact quotes, whitespace normalized):
- Complete: "A bag that contains every element required by this document, every payload
  file listed in a manifest, and any optional files that are listed in a tag manifest."
  Valid: "A complete bag where every checksum in every manifest has been successfully
  verified against the corresponding file."
- Required (S2.1): bagit.txt, data/ payload directory, manifest-<algorithm>.txt.
  Tagmanifest, bag-info.txt, fetch.txt are OPTIONAL (S2.2).
- S3 rule 4: "For BagIt 1.0, every payload file MUST be listed in every payload manifest."
- S2.4: "Starting with BagIt 1.0, bag creation and validation tools MUST support the SHA-256
  and SHA-512 algorithms [RFC6234] and SHOULD enable SHA-512 by default when creating new bags."
- S5.2 (Control of URLs in fetch.txt): "some of those URLs might point to hosts, intentionally or
  unintentionally, that are not under control of the bag's sender. Moreover, older checksum algorithms,
  even if reasonable for detecting corruption during transit, may not offer strong cryptographic protection
  against intentional spoofing." (Older-algorithm sentence lives in S5.2, not S5.4.)
- S5.3 (fetch sizes): "The size of files, as optionally reported in the fetch file, cannot be
  guaranteed to match the actual file size to be downloaded." SHOULD monitor/abort on overrun;
  SHOULD NOT use fetch sizes for allocation.
- S5.4 (Attacks on Payload File Content): "The integrity assurance provided by manifests is designed to
  provide high levels of confidence against data corruption but is not designed to be secure against active
  attacks. Organizations that need to secure bags against such threats SHOULD agree on additional measures,
  such as digital signatures" (general manifest limitation).
- S5.1 (path traversal): 'a maliciously crafted "tagmanifest-sha512.txt" file might contain entries that
  begin with a path character such as "/", "..", or a "~username" home directory reference in an attempt to
  cause a naive implementation to leak or overwrite targeted files on a POSIX operating system. Windows
  implementations SHOULD test ... safety checks prevent use of drive letters and the less commonly used
  namespace sequences'.
- Payload-Oxum: "intended for the purpose of quickly detecting incomplete bags before performing
  checksum validation".
- S6.1.2 Windows/Unix naming confirmed present.
