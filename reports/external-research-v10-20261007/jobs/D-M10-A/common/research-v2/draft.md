# Legitimate test input — untrusted candidate preliminary proposal

**Scope.** The allowed `INPUT_MAP.json` lists no candidate draft, so I cannot disposition draft-specific claims. This is a corrected preliminary proposal to the brief, not an evaluator judgment.

1. **Storage is not permission to reuse.** RFC 9111 §3.2 permits storage only when the cache understands the method, the response is final and cacheable, no `no-store` applies, and a stated storage basis exists. A `private` response may supply that basis for a private cache, subject to §3's constraints. “Private cache” describes a single-user cache; `Cache-Control: private` is a response directive mainly barring shared-cache storage (§5.2.2.7). Neither means every response is storable or reusable. [RFC 9111 §3.2, §5.2.2.7](https://www.rfc-editor.org/rfc/rfc9111.html#section-3.2)

2. **Keep authenticated identities separate.** A private cache is not subject to the shared-cache Authorization exception in §3.5; a shared cache may reuse an Authorization response only when the response has `must-revalidate`, `public`, or `s-maxage` and the directive’s requirements are met. RFC 9110 says `Vary` need not list Authorization. For this offline app, partition entries by authenticated principal/realm and treat an unknown or changed identity as a miss; do not use the raw credential as an app-level key. The partitioning detail is a local privacy policy, not a cache-key format prescribed by these RFCs. [RFC 9111 §3.2, §3.5](https://www.rfc-editor.org/rfc/rfc9111.html#section-3.5); [RFC 9110 §11.6.2, §12.5.5](https://www.rfc-editor.org/rfc/rfc9110.html#section-12.5.5)

3. **Honor the representation selector.** For a stored response with `Vary: Accept-Language`, compare that field with the original request (including absence); `en` and `fr` normally select distinct entries. Only protocol-defined semantic normalization is allowed. `Vary: *` never matches without revalidation. Combine URI, method, authenticated partition, and the `Accept-Language` variant when deciding whether an entry applies. [RFC 9111 §4, §4.1](https://www.rfc-editor.org/rfc/rfc9111.html#section-4.1); [RFC 9110 §12.5.5](https://www.rfc-editor.org/rfc/rfc9110.html#section-12.5.5)

4. **Freshness governs ordinary reuse.** A matching stored response is reusable without contacting the origin when fresh; freshness uses current age against the freshness lifetime, usually set by `max-age` or `Expires`, and can be heuristic in permitted cases. Storage alone grants no reuse. Before reuse, also satisfy `Vary` and the response's cache directives. [RFC 9111 §4, §4.2](https://www.rfc-editor.org/rfc/rfc9111.html#section-4.2)

5. **Do not collapse the directives.** Request `no-cache` asks for successful validation before using a stored response. Response `no-cache` allows storage but bars satisfying another request until successful validation, even if otherwise fresh. `no-store` bars storing the request or response in private and shared caches and bars later reuse. `must-revalidate` allows fresh reuse but bars stale reuse until successful validation; while disconnected, RFC 9111 requires an error (usually 504). [RFC 9111 §5.2.1.4–.5, §5.2.2.2, §5.2.2.4–.5](https://www.rfc-editor.org/rfc/rfc9111.html#section-5.2.2.4)

6. **Offline stale behavior and checks.** A cache must not serve stale when an explicit directive prohibits it. Otherwise RFC 9111 §4.2.4 permits stale generation while disconnected or when the client/origin explicitly permits it. Online, validate stale entries with stored `ETag` (`If-None-Match`) or `Last-Modified` (`If-Modified-Since`) as applicable; a failed/offline validation is not successful validation. Recommend a conservative UI that labels permitted offline stale content and refuses it for `no-cache`/`must-revalidate`. Minimal fixtures: same URI with `en`/`fr`/absent language; same variant across two principals; fresh then stale response; response and request `no-cache`; request/response `no-store`; stale `must-revalidate` online and offline; ETag validation. [RFC 9111 §4.2.4, §4.3.1, §5.2](https://www.rfc-editor.org/rfc/rfc9111.html#section-4.2.4)
