# Critique of the untrusted proposal

The proposal was read before checking its evidence. The core model is strong; no central claim needs wholesale rejection. The corrections below matter because the draft phrases some directive rules too broadly and the requested recommendation needs to preserve protocol conditions.

1. **Storage — amend.** The §3 storage checklist is substantially accurate, including final status, understood methods, cacheability signals, and private-cache treatment. Add the §5.2.2.3 exception: a cache implementing `must-understand` SHOULD ignore `no-store` when it understands and implements that status code's caching requirements. The draft's unconditional “no-store is absent” condition misses this exception.
2. **Authorization — accept with qualification.** Shared-cache use of an Authorization response requires `must-revalidate`, `public`, or `s-maxage`, with that directive obeyed (§3.5). RFC 9110 says Authorization need not appear in `Vary` because cross-user reuse is prohibited by default; qualify that with the explicit shared-cache permissions. Account partitioning in a private app cache is a prudent product rule, not a keying scheme specified by these RFCs.
3. **Vary — accept and clarify.** The normalization, absent-field, and `Vary: *` statements track §4.1. A nonmatching entry is not an unvalidated hit; the cache cannot satisfy the request from it, though it may forward a validation request and receive a full response selected for the current request.
4. **Freshness/reuse — accept, clarify conditions.** Use `current_age < freshness_lifetime`; freshness uses shared `s-maxage`, then `max-age`, then `Expires` relative to `Date`, then permitted heuristics. Heuristics require no explicit expiry and an eligible status or explicitly cacheable response. `no-cache` needs a qualified/unqualified distinction.
5. **Validation — accept with precision.** ETag and Last-Modified validation and the 304/full-response distinction are right in outline. A 304 updates only eligible stored response(s), filtered by validator matching; it is not a new representation. A validating 5xx can be forwarded or treated as failure, with stale fallback still subject to §4.2.4.
6. **Directives — amend.** Unqualified response `no-cache` requires successful validation before reuse; `no-cache="field"` can permit reuse if listed fields are omitted or successfully revalidated. Response `no-store` forbids storage and reuse, subject to `must-understand`. Request directives are advisory under §5.2.1; if honored, request `no-store` governs that exchange and does not delete an already stored response. `must-revalidate`, shared `s-maxage`, and shared `proxy-revalidate` block stale reuse; response `no-cache` also blocks stale reuse.
7. **Fixtures — accept, expand.** The draft's fixtures are useful proposals. Add request and qualified response directive cases, `must-understand`/`no-store`, shared Authorization exceptions, Vary mismatch and wildcard, exact freshness boundary, 304 metadata/validator filtering, and validation-5xx stale behavior. None of these fixtures was executed in this review.
8. **Unresolved product choices.** RFCs do not choose per-account cache partitioning, retention duration, revocation/erasure behavior, offline presentation, or whether to support particular stale extensions. Keep these as product decisions rather than standards claims.

Disposition: **accepted** — the core storage/reuse distinction, default Authorization restriction, Vary matching, freshness/validator model, and RFC-versus-product uncertainty. **Amended** — the scope and conditions above. **Rejected** — none of the proposal's central claims. **Unresolved** — the product choices in item 8.

Source basis: the exact listed RFC 9111 June 2022 and RFC 9110 June 2022 captures. Their SHA-256 values matched the input map and source manifest. This is a text review; no implementation, test fixture, or downloaded code was run.
