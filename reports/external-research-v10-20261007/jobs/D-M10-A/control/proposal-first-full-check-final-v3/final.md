# Corrected bounded recommendation: authenticated private offline cache

**Decision:** Accept the proposal's main storage/reuse model, with the amendments below. The controlling sources are [RFC 9111 §§3, 3.5, 4.1–4.3.5, 5.2.1–5.2.2](https://www.rfc-editor.org/rfc/rfc9111.html) and [RFC 9110 §§11.6.2, 12.5.5](https://www.rfc-editor.org/rfc/rfc9110.html). Both exact June 2022 captures listed in the input map were hash-verified.

1. **Storage is separate from reuse.** A cache may store only if it understands the request method; the response is final; it understands the status code when it is 206/304 or `must-understand` is present; shared-cache restrictions are met; and a cacheability signal applies (`public`, `private` for a private cache, `Expires`, `max-age`, shared `s-maxage`, a permitting extension, or a heuristically cacheable status). Response `no-cache` permits storage. Response `no-store` prohibits storage and later reuse, except that a cache implementing `must-understand` SHOULD ignore `no-store` when it understands and implements the status code's caching requirements. An unqualified `private` permits private-cache storage, subject to §3, even without heuristic cacheability. [RFC 9111 §§3, 5.2.2.3, 5.2.2.5, 5.2.2.7]

2. **Authorization boundary.** A private cache can store an authenticated response when the storage conditions are met; `Authorization` alone does not bar private storage. A shared cache cannot use such a response for another request unless it has `Cache-Control: must-revalidate`, `public`, or `s-maxage` and obeys that directive. `public` permits shared caching; `must-revalidate` and `s-maxage` permit it subject to stale revalidation rules. RFC 9110 says Authorization need not be listed in `Vary` because cross-user reuse is prohibited by default; read that with RFC 9111's explicit shared-cache exceptions. For an app that supports account switching, partition entries by account and never cross-serve them as a product safety rule; the RFCs do not define that account key. [RFC 9111 §3.5; RFC 9110 §§11.6.2, 12.5.5]

3. **Variant match before unvalidated reuse.** The target URI/method and other cache constraints must permit reuse. With `Vary: Accept-Language`, the later request's nominated field must match the original under §4.1's permitted normalization. Absent matches only absent; `Vary: *` never matches. A different language preference is not a fresh unvalidated hit merely because the URI matches. A nonmatching entry cannot satisfy the request directly; a cache may forward a validation request, and the origin can return a full response for the current request. [RFC 9111 §4.1; RFC 9110 §12.5.5]

4. **Freshness and reuse.** Reuse requires an eligible method/target and matching variant, plus freshness or a valid stale/validation path. A response is fresh only when `current_age < freshness_lifetime`; equality is stale. Lifetime precedence is shared `s-maxage`, `max-age`, `Expires` minus `Date` (or receipt time if Date is absent), then permitted heuristics. Heuristics require no explicit expiry and a heuristically cacheable status or an explicitly cacheable response. A response `no-cache` constraint must also be satisfied. [RFC 9111 §§4, 4.2–4.2.3]

5. **Validation is conditional and variant-sensitive.** When no stored response can be used directly, an online cache can forward a conditional request. It MUST send stored entity tags when present; it SHOULD send Last-Modified for a single stored response outside a range request. A 304 has no new representation: it updates only eligible stored response(s), filtered by validator matching, after which the stored representation may satisfy the request. A full response supplies the representation and may be stored if §3 permits. On validation 5xx, the cache can forward the error or treat the server as unavailable; stale fallback remains subject to §4.2.4. [RFC 9111 §§4.3.1, 4.3.3–4.3.4]

6. **Directive effects.** Unqualified response `no-cache` allows storage but requires successful origin validation before each reuse. Qualified `no-cache="field-name"` can allow reuse if those fields are excluded from the later response or successfully revalidated. Response `no-store` bars storing or reusing that response, subject to the `must-understand` case in finding 1. `must-revalidate` bars stale reuse, including while disconnected. A cache may serve stale only when disconnected or explicitly permitted by the client/origin (such as `max-stale` or an applicable extension) or an out-of-band contract; never when barred by response `no-cache`, `must-revalidate`, or shared-cache `s-maxage`/`proxy-revalidate`. Request directives are advisory: if honored, request `no-cache` asks for successful validation, while request `no-store` governs that exchange and does not erase an already stored response. `no-store` is not a sufficient privacy guarantee. [RFC 9111 §§4.2.4, 5.2.1, 5.2.2.2–5.2.2.10]

7. **Proposed checks (not executed).** Use an authenticated `200 GET` with `private, max-age=60`, `Vary: Accept-Language`, and ETag. Check same-account/same-language fresh reuse; account switch; absent/different language and `Vary: *`; normalization; age just below, equal to, and above 60 seconds; online 304 with matching and nonmatching validators plus metadata update; and full-response replacement. Add response unqualified/qualified `no-cache`, response `no-store`, understood/ununderstood `must-understand`, request `no-store` with an existing entry, and offline stale cases with/without `must-revalidate`. Separately test shared Authorization with no exception and each of `public`, `must-revalidate`, and `s-maxage`; check `proxy-revalidate`/`s-maxage` stale behavior and 5xx fallback. These are recommended fixtures only; no code or tests were run.

8. **Disposition and uncertainty.** **Accepted:** the draft's core distinction among storage, reuse, validation, Authorization, Vary, and its account/retention/UX uncertainty. **Amended:** the `must-understand` exception, default-versus-explicit Authorization sharing, qualified `no-cache`, exact freshness and 304 conditions, and advisory request directives. **Rejected:** none of its central claims. **Unresolved:** account-key design, offline UX, retention/erasure policy, and which stale extensions the product will support; RFCs do not decide these.
