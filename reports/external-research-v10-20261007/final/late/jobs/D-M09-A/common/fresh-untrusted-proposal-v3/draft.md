# Preliminary proposal: incremental online backup of a live SQLite 3.51.3 writer

Bounded question (preserved): an incremental online backup of a live SQLite 3.51.3 database with a concurrent writer, across the seam joining API/locking behavior to retry, progress, destination replacement, and cleanup. Sources: S1 = https://www.sqlite.org/backup.html (capture 2026-10-07, sha256 306b6cca…e04); S2 = https://www.sqlite.org/c3ref/backup_finish.html (capture 2026-10-07, sha256 3beb8d98…25b); S3 = sqlite version-3.51.3 src/backup.c (sha256 ee4cbfc7…ef7). Preliminary; uncertainty stated per proposition.

**P1 — Loop shape.** Call init() once, step(N) repeatedly with small N (the S1 example uses 5 pages), sleep between steps, then finish() once. The source read-lock is held only inside each step call [S2], so writers proceed between steps; step(-1) holds it for the whole copy [S1 §3]. Uncertainty: the 250 ms delay in S1 is illustrative; pacing is workload-specific (lead: log restart frequency to tune it).

**P2 — Retry classification.** Treat only SQLITE_BUSY and SQLITE_LOCKED as retryable; READONLY, NOMEM, and SQLITE_IOERR_* are fatal — abandon via finish() [S2; S3 isFatalError()]. LOCKED occurs when the source connection is in use for writing when step is called; BUSY when a lock wait fails or the source btree is mid write-transaction [S2; S3]. Register a busy timeout on both connections [S1 §2.2] and bound application retries. Uncertainty: whether the two BUSY origins need different backoff is not settled in-corpus.

**P3 — Restart seam.** An external write to the source (other connection or process) invalidates copied pages and the next step restarts from page 1 [S2; S3 sqlite3BackupRestart]. A write through the same source handle is instead merged into the destination for already-copied pages [S3 backupUpdate]. Frequent external writes can prevent completion entirely [S1 §3.1]. Proposal: route writer traffic through the backup's source handle during the window where feasible, else measure restarts and completion rate. Uncertainty: S1 says external writes "usually" restart the backup at the next step; the exact pager trigger is outside this corpus.

**P4 — Progress is stale by design.** remaining()/pagecount() return values latched by the previous step, not a live read, and are not threadsafe against concurrent step calls [S1 §3.2; S2; S3]. Report completion = (pagecount − remaining) / pagecount as advisory only. Uncertainty: staleness is bounded by one step interval, not further quantified here.

**P5 — Destination exclusivity.** Between init() and finish() the destination connection must not be used by any thread; SQLite does not check, and misuse may malfunction or deadlock; in shared-cache mode no process connection may touch the destination file [S2]. The first step opens the destination write transaction, held until finish or DONE [S2; S3]; init() fails if the destination already has a transaction open [S2; S3 checkReadTransaction]. Proposal: dedicate the destination connection to the backup. Uncertainty: cross-VFS behavior untested here.

**P6 — Completion and abandonment cleanup.** On DONE the destination commit completes inside step; the file is truncated to the copied size (source bytes at matched page sizes) and the schema cookie is bumped, invalidating cached schemas [S3]. finish() before DONE rolls back the destination transaction, preserving pre-backup contents [S2; S3]. finish() returns the first prior step error, except BUSY/LOCKED, which it does not remember [S2]. Uncertainty: S1's overview calls the result the source "as it was when the copying commenced" while §3.1 promises a consistent, up-to-date snapshot at completion; reconcile by relying on consistency, with snapshot vintage depending on which writes went through the source handle.

**P7 — Page-size and WAL preconditions.** The first step attempts to set the destination page size to the source's [S3 setDestPgsz]; a WAL or memdb destination whose page size then differs fails SQLITE_READONLY (fatal), as does a read-only destination [S2; S3]. Proposal: match page sizes at destination creation; verify journal mode. Uncertainty: only the WAL/memdb mismatch is code-confirmed here; other mismatches are handled silently in-corpus.

**P8 — Error reporting locus.** Backup errors are attached to the destination connection; read sqlite3_errcode()/errmsg() on the destination handle after finish(), as S1's examples do [S1 §2.1; S2]. Uncertainty: extended-IOERR discrimination is documented but untested here.

Optional lead beyond corpus: back up to a scratch destination and rename into place after success, since the destination stays locked for the whole run; engineering practice, not a source claim.
