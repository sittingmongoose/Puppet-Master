**Overall verdict.** The proposal's core is source-supported: loop shape (S1 L399–411; S2 L236–242); retry classification, S3's isFatalError (L217–219) generalizing S2 L219–234; destination exclusivity and quiescence (S2 L178–180, L301–315); DONE-time truncation, cookie bump, rollback (S3 L417–541, L599–606); page-size/WAL READONLY triggers (S2 L210–217; S3 L375–383); destination-handle error locus (S1 L294–310). Two claims need added conditions; one prose/code tension is unresolved in-corpus.

**Findings.**

1. **finish() after BUSY — doc/code tension (material, unresolved).** S2 L272–274: a step return of BUSY/LOCKED "does not affect the return value of sqlite3_backup_finish()". S3 stores each step's rc unconditionally (L558) and finish returns p->rc unless DONE (L603), also writing it to the destination handle (L604–606). Strict code reading: finish immediately after BUSY returns SQLITE_BUSY; the prose holds only because an intervening step overwrites the stored BUSY (entry rc=BUSY is non-fatal, so the body re-runs — S3 L329–330). S1's canonical loop (L405–408) exits only on DONE/fatal, so it never exposes the case. Also imprecise: finish semantics are last-error, sticky-if-fatal (a fatal entry rc freezes p->rc by skipping the body), so the proposal's "first prior step error" and S2's "during any prior step" (L268–270) overstate the memory. Test T1.
2. **Same-handle merge conditions omitted (material).** The merge claim is unconditional in the proposal; S1 L456–465 requires a file-based (non-in-memory) source, same process, same handle, and S1 L473–478: for an in-memory source even same-handle writes restart the whole backup. S2's summary (L245–250), also cited, omits these conditions. The merge covers only already-copied pages (iPage < iNext, S3 L661–685); a failed merge stores a sticky error (S3 L677–682) that terminates the backup on the next step — unhandled by the proposal.
3. **Progress latches per successful step and reads optimistically across restarts (material).** Counters update only when a step ends SQLITE_OK (DONE is assigned inside that block, after the latch — S3 L402–409); BUSY/LOCKED steps leave older values while S1's example still calls the progress callback after them (L400–407). Before the first successful step both are 0 (zero-allocated in init, S3 L176): the documented formula (S1 L489–497) divides by zero and remaining()=0 falsely reads complete. After an external-write restart only iNext resets (S3 L701–707): the report can claim near-complete while the true remaining work is the whole copy. Staleness is bounded in successful-step count, not wall time (S2 L285–291).
4. **"Writers proceed between steps" has an unstated precondition (material).** The source read transaction is opened per step and closed at step end only if that step opened it (S3 L350–353, L548–553). An application-held source read transaction across steps keeps the shared lock up and blocks writers.
5. **Busy-handler citation overreaches (minor).** "Both connections [S1 §2.2]" — S1 L324–335 recommends the handler only for the file-backed connection pFile; no corpus text advises it on the live source handle. Keep the advice, cite as extrapolation. The BUSY-origin split is correct: LOCKED when the source handle is in use at call time (S2 L226–228); BUSY on file-lock failure (S2 L219–225) or source mid write-transaction (S3 L340–344).
6. **setDestPgsz failure swallowed except NOMEM (minor).** S3 L361 treats only SQLITE_NOMEM from the first-step page-size attempt as an error; other failures are ignored, only the WAL/memdb mismatch check (L375–383) can then fail READONLY, and rollback-journal destinations proceed via span-copy and ratio truncation (L449–457, L522, L530). Match page sizes at destination creation; silence, not success, is the fallback.
7. **No resume; destination shippable only after DONE (material).** Corpus "restart" is internal to one live backup object (S3 L701–707); interrupted work is never resumed — a new attempt is a fresh init from page 1 (S2 L150–160). finish before DONE rolls back, preserving pre-backup contents (S2 L255–263; S3 L600), so the destination is clean for retry; only a step that returned SQLITE_DONE leaves a shippable file. Crash-mid-backup recovery is standard journal rollback outside this corpus (inference, marked). SQLITE_IOERR_NOMEM collapses to primary NOMEM before storage (S3 L555–557), so extended-IOERR discrimination does not survive finish.
8. **Silent storms; add a deadline (material).** Restart storms (S1 L480–482) and destination-BUSY storms increment no user-visible counter. Bounded retries and completion-rate measurement are right; add a wall-clock deadline, abandoning via finish; for pathological writers consider the in-corpus alternatives, VACUUM INTO and sqlite3_rsync (S1 L196–208; S2 L324–332). The scratch-destination-and-rename lead stays engineering practice with outside-corpus caveats: WAL sidecars, open handles.

**Reconciliation (from sources, not votes).** S1's overview "bit-wise identical copy … as it was when the copying commenced" (L184–187) versus §3.1 "consistent and up-to-date snapshot" (L468–471) resolves through restart/merge semantics (S2 L242–250; S3 L661–707): external writes restart the copy, so the completed backup reflects the source at/after the last restart — "as of commencement" holds only for a quiescent source — and same-handle merges make it strictly newer. Rely on consistency; snapshot vintage depends on which writes went through the source handle. The finish/BUSY tension (finding 1) is the one disagreement the frozen bytes cannot resolve; recorded with a test, not voted.

**Corrected recommendation.** init once; small step increments; no application transactions on the source connection while the loop runs (4); retry only BUSY/LOCKED, bounded, busy timeout at least on the file-backed connection (5); abandon fatal errors via finish; route writer traffic through the backup's source handle where feasible, under finding-2 conditions; report progress only after a successful step, guarded by pagecount>0, as advisory (3); dedicate the destination connection; ship only after DONE (7); wall-clock deadline then abandon via finish (8); create the destination at the source page size and verify journal mode (6).

**Proposed tests.** T1 (1): on 3.51.3, hold a conflicting destination-file lock, drive step→BUSY, finish; record finish's return and sqlite3_errcode(dest) — prose predicts SQLITE_OK, strict code reading SQLITE_BUSY. T2 (2,3): write externally mid-backup; confirm the next step restarts and counters hold pre-restart values until it completes; repeat with an in-memory source. T3 (4): hold a source read transaction across steps; confirm writers block between steps. T4 (3): query counters before any step; confirm 0/0 and formula division-by-zero. T5 (8): continuous external writes; confirm the deadline path abandons via finish with destination contents preserved.

**Uncertainty.** Every finding cites the frozen bytes at the lines given; finding 1 is unresolved in-corpus; crash recovery and rename-with-WAL caveats are marked outside-corpus inferences. All P1–P8 citations trace to real text at their cited locations; no fabricated sources found.
