## A. Retry / destination / cleanup (draft P1, P2, P5–P8)

**Verdicts.** P1 loop shape — CORRECT: init once (140–210), step loop (314–566), finish once (571–619); source read-lock opened and closed inside each step (350–353, 548–553); `nPage<0` copies all (390); the 250 ms sleep is example code. P2 retry classification — MOSTLY CORRECT: `isFatalError` (217–219) makes all fatal but OK/BUSY/LOCKED; NOMEM fatal (361–363, 555–557); trigger attribution wrong, see A-1. P5 destination exclusivity — CORRECT (A-3). P6 completion/abandonment — MOSTLY CORRECT (A-2, A-4). P7 page-size/WAL preconditions — CORRECT (A-4). P8 error locus — CORRECT (A-2).

**A-1 retry.** S2 says step returns SQLITE_LOCKED when "the source database connection is being used to write to the source database"; captured 3.51.3 returns SQLITE_BUSY for exactly that state (source btree in `TRANS_WRITE`, 337–344). No statement in the captured file produces LOCKED (only 218, 679), so LOCKED must arise outside the corpus (candidates 350–351, 367, 394). The draft cites [S2; S3] as if they agree; they do not. Per the governing rule: plan on BUSY for same-handle writes in this release, keep LOCKED retryable (218), flag the mismatch — irreconcilable in-corpus. The draft's busy-timeout "on both connections" over-extends S1 §2.2 (destination file connection only); the source side is inference, though BeginTrans (350–351) can hit BUSY under rollback-mode contention.

**A-2 finish() semantics.** S2: BUSY/LOCKED from step "does not affect the return value of sqlite3_backup_finish()". Code: each step stores its rc (558); finish returns `p->rc` unless DONE (603) and stamps it on the destination handle (604–605) — so finish immediately after a BUSY/LOCKED step returns that code. The draft's "first prior step error, except BUSY/LOCKED" is imprecise both ways: fatal errors persist (330 short-circuit, 558 re-store), and a last-step BUSY/LOCKED is returned. P8 confirmed (605; init errors into `pDestDb` at 90, 101, 126, 167–169, 178), with a caveat: finish sets code only (`sqlite3Error`, not `ErrorWithMsg`), so errmsg() may be empty — key retries on errcode().

**A-3 destination lifecycle.** Confirmed: init rejects one handle for both sides (166–170) and any open destination transaction (124–130, 191–193, "destination database is in use"); first step sets destination page size (361–363) and opens the destination write transaction held until DONE or finish (365–371, `bDestLocked`); every thread must stay off the destination handle, SQLite does not check, misuse may malfunction or deadlock (156–162; S2); shared-cache: no process connection may touch the destination file (S2). Edge the draft missed: `sqlite3BackupRestart` (701–707) resets only `iNext` — a restart never re-validates destination state.

**A-4 cleanup and preconditions.** Confirmed: DONE commits inside step (535–539); schema cookie `iDestSchema+1` (423) plus schema reset (426–428); WAL set-version (429–431); truncate to copied extent (447–458; 470–523; 530) — the draft's "source bytes at matched page sizes" is exact. finish before DONE rolls back, preserving prior contents (599–600; S2). WAL/memdb page-size mismatch and read-only destination fail SQLITE_READONLY, fatal (374–383; 366–368; 217–219). Caveat: non-NOMEM `setDestPgsz` results are discarded (361) — silent mismatch possible for non-WAL destinations (absorbed by 233–276, 447–458); reachability outside the corpus. The draft's reconciliation of S1's overview ("as it was when the copying commenced") with §3.1 ("consistent and up-to-date snapshot") is accepted: same-handle writes merge (661–685), external writes restart (701–707) — completion is consistent, vintage varies with write routing.

**Checks.** PC-A1: probe same-handle write then step; record the code actually returned, BUSY vs LOCKED (pins A-1). PC-A2: force one BUSY step, call finish() immediately; assert observed finish return and errcode(dest) (pins A-2). PC-A3: negative test — read the destination handle between steps, shared-cache and not; "it worked" is luck. PC-A4: finish mid-copy, byte-compare destination to pre-backup (contents and size); full run → cookie changed, size matches truncate math.

## B. Interrupted / restarted backup and progress seam (draft P3, P4)

**Verdicts.** P3 restart semantics — CORRECT: external write → `sqlite3BackupRestart` resets `iNext=1` for every backup attached to that source pager (701–707; attach 302–309), next step re-copies from page 1; S1 §3.1's "usually" and its starvation warning match; the pager-internal trigger is correctly flagged outside the corpus. Same-handle write merges at write time for already-copied pages (`iPage<iNext`, 669–682). P4 progress — MOSTLY CORRECT: remaining()/pagecount() are latched fields (625–647), not live reads; S1 §3.2 ("values stored by the previous call … do not actually inspect the source database file") and S2 ("only updated by sqlite3_backup_step()") agree; not thread-safe against concurrent step/finish (60–65).

**B-1 naming.** `bRestart` occurs nowhere in the captured corpus (0 hits, S1–S3). The mechanism is `sqlite3BackupRestart` plus `iNext=1` (701–707); the calling trigger is outside this corpus. Claims keyed to a `bRestart` variable are not corpus-grounded.

**B-2 progress meaning.** (a) Counters latch only in steps ending OK/DONE (402–406); BUSY/LOCKED steps leave the last values — no regression, but no stall signal. (b) After init, before the first successful step, both fields are 0 (176): the completion formula divides by zero there. (c) After a restart the next OK step latches `nRemaining≈pagecount` — progress is non-monotonic; a restart hits all backups chained on the pager (703–706).

**B-3 merge cost.** Each same-handle write to a copied page synchronously copies into the destination under its mutex (669–682): routing trades restarts for per-write cost — measure both, as the draft proposes. Merges stop after a fatal error (669); in-memory sources restart regardless of handle (S1 §3.1).

**B-4 interruption and re-entry.** The destination transaction persists across steps and restarts (365–371); restart never rolls it back. A second init on the same destination fails while any earlier backup object is unfinished (124–130, 191–193): re-entry requires finish() first (rollback 599–600). One source may feed several destinations (204, 306–307); an external-write restart invalidates all at once. Crash recovery is pager-internal, outside the corpus.

**Checks.** PC-B1: mid-backup external write, then step; assert remaining() jumps toward pagecount() (non-monotonicity observed). PC-B2: source-handle write mid-backup; new value present at DONE, no counter reset. PC-B3: second init while unfinished → NULL + "destination database is in use"; after finish → succeeds. PC-B4: external write per sleep window; require an abort bound (wall time or restart count) — completion is not guaranteed (S1 §3.1).

**Uncertainty summary:** the BUSY/LOCKED trigger and finish-after-BUSY behavior are S2/S3 tensions resolvable only by PC-A1/PC-A2 on live 3.51.3; LOCKED origins, non-NOMEM `setDestPgsz` failures, the external-write detection point, and crash recovery lie outside the corpus; pacing (N, sleep interval) is workload-specific.
