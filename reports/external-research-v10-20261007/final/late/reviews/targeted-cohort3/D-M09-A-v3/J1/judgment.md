## 2. Consequential claims and governing conditions

**F1 / P1 — supported loop, missing source-transaction condition (D2).** S2:150–160 supports init/step/finish and exactly one finish per successful init. S1:392–411 supports the illustrative five-page/250-ms loop; S2:199 supports negative N copying the remaining pages. However, S3:350–353 opens a source read transaction only if `sqlite3BtreeTxnState(p->pSrc)` is NONE. Only that path sets `bCloseTrans`; S3:548–553 closes it only when that flag is set. If the source handle already has a read transaction, backup reuses it and does not release it after each step. Thus final:9's unconditional “read-lock lives only inside each step” and resulting writer-access assurance need a condition absent from the recommendation. In rollback-journal mode that retained read lock can block another writer's commit; concurrent access also requires the threadsafe configuration stated at S2:295–299. The per-call handle mutex is a separate matter.

**F2 / P2 — classification and busy-handler bypass substantially supported.** S3:217–219 treats exact OK/BUSY/LOCKED as nonfatal; READONLY/NOMEM/IOERR errors are fatal. S3:329–344 and 350–351 establish the source-Btree write-transaction BUSY branch before any attempted source read transaction, supporting the bypass of the busy handler on that branch. Application retries remain necessary. S1:325–335 registers the timeout on `pFile`, which can be source or destination in that example (S1:247–248); marking “both connections” as an engineering extension is appropriate. The final does not preserve the predecessor's source-write→LOCKED assertion as release truth: the supplied code's direct branch returns BUSY. Retry classification should not silently generalize from exact constants to every extended member of a result-code family: A2:3647–3649 can return `SQLITE_LOCKED_SHAREDCACHE`, while S3's predicate compares exact values. Workload-specific backoff remains unestablished; no optimal timing was demonstrated.

**F3 / P6 — genuine doc/code correction, weakened completion meaning (D1).** S2:272–274 says transient BUSY/LOCKED do not affect finish. S3:558 actually stores the step's return, and S3:603–605 returns/stores that value unless it is DONE. A subsequent successful step can overwrite BUSY; abandonment immediately after BUSY returns BUSY. Fatal returns latch through S3:329–330; the correction is supported by released code. Finish rolls back any still-open destination transaction and destroys the object (S3:599–615), so a new init is required for a new operation.

But `claim-review.md:55` says such a result is not a **fatal** failure; `final.md:13` says it is “not failure.” An abandoned copy is incomplete, even if the old destination remains usable and the problem is retryable. Conversely, after an incomplete step returning OK, finish can return OK while rolling the copy back: S3:402–409, 558, 599–603 and S2:265–267 show this directly. Finish success therefore cannot establish copy completion. The final's governing loop and condition 3 never explicitly preserve DONE as the completion criterion. This is a material cleanup/outcome ambiguity, not evidence of corruption on ordinary cancellation.

**F4 / P3 — supported, justified correction.** S2:244–250 and S3:701–707 support detected external change restarting copying at page 1, while S3:669–681 updates an already-copied page through the source pager when the operation has no fatal error. S1:460–478 expressly gives the non-in-memory/same-handle exception and in-memory restart behavior. Additional release inspection confirms the ordinary in-memory case: A1:1979–1983 and 6484–6493 lead an in-memory commit to the restart callback. Final F4 corrects a missing predecessor condition; frequent restarts preventing completion are supported at S1:480–481. “Route writer traffic through the source handle where feasible” is an optional operational suggestion, conditional on appropriate connection serialization and transaction boundaries, not a demonstrated performance result. Detecting every pager trigger was not necessary to validate this stated mechanism; a universal no-restart promise for same-handle file writes would be too strong (A1:3129–3137 covers a WAL rollback restart).

**F5 — consistency retained, vintage formulation overgeneralized (D2).** S1:184–186's commencement wording conflicts with its own S1:468–471 and update/restart mechanism. The final correctly declines to promise an init-time snapshot for an ordinary incremental backup whose read transactions are renewed. Same-handle updates and detected external changes can incorporate later committed state; writes after the final acquired snapshot are not thereby included. However, a source read transaction may have started before init and remain active across the entire copy, as S3:350–353/548–553 shows. A5:269–280 explains the unchanged WAL reader end mark. Such a backup can be consistent yet reflect a snapshot older than the claimed “window from last restart to last step” (`final.md:17`). The asserted last-step lock release also does not occur for that pre-existing transaction. The interpretation needs that condition, not a rejection of consistency itself.

**F6 / P5/P8 — supported restrictions and reporting, acquisition nuance.** S2:301–315 supports destination-handle exclusion and process-wide exclusion of the destination shared cache/file. S2:178–187 and S3:124–130/191–200 support init failure on an already-open destination transaction and destination error reporting. S3:366–371 acquires the destination write transaction only after earlier prerequisites succeed; a source-write BUSY before this leaves it unacquired. A later failing step may already have acquired it, so cleanup is needed on every exit, not only after a step that returned OK. S3:604–605 and S1:296–310 support reading the destination error after finish. The final retains these important operating restrictions. It could state more explicitly that source and destination handles must differ (S2:174–176; S3:166–170), though a dedicated destination normally implements this.

**F7 / P4 — correct latched values, incorrect refresh condition (D3).** S1:499–505 and S3:625–646 support cached rather than live counts. S2:317–322 supports the concurrent-step warning. But S3:402–404 updates counts while local `rc` is OK, **before** S3:405–406 changes the return to DONE, and before destination commit work at S3:417–539 can instead fail. Thus final:21 and governing condition 6's “refresh only on OK steps” misread an internal branch as a returned status. A terminal DONE step refreshes the counters; even a later commit IOERR can coexist with newly refreshed counts. A BUSY returned before the copy block normally leaves them unchanged, which remains useful supported advice. The ratio also requires `pagecount > 0`: init zeroes the object (S3:176), and a zero-page source stores pagecount zero before the empty-destination handling (S3:388, 402–404, 418–420). “Advisory” does not supply a denominator guard or prove completion when remaining is zero. Repeated BUSY returns can leave counts older than a single step interval; the final properly lists that bound as unresolved instead of proving it.

**F8 / P7 — page-size checks supported; replacement lead fails separately (D4).** S3:112–115 and 361–363 establish an attempt to set destination page size and propagation of NOMEM from that attempt. The actual WAL/memory mismatch check follows at S3:373–383; read-only destination is documented at S2:210–216 and implemented at A2:3621–3624. Matching page sizes and compatible journal mode is useful preventive advice. Do not read “other mismatches change silently” as proof that the attempted setter always succeeds: A2:3082–3095 can reject a fixed size and S3:233–275/449–457 handles different copy-page sizes. Eventual destination format replacement and successful immediate setter adjustment are distinct. This qualification does not invalidate the matching-size recommendation.

The final's unresolved exact detection trigger, different backoffs, cross-VFS behavior, and extended-IOERR discrimination remain appropriately unverified. Source review supplies mechanism evidence, not dynamic validation of all configurations.
