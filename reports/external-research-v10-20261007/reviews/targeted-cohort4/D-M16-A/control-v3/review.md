## Six material findings

### F01: 304 payload reuse is turned into an incorrect shared-state no-op (high)

Candidate lines 9, 13, 17, 28, 37, 60. Primary evidence: E03, E04, E07, E09.

The cross-topic revalidation event and its published test oracle conflate unchanged content with unchanged freshness/retention state.

**Source facts:** A suitable 304 freshens a stored response and updates provided headers. Freshness age is measured from generation/validation. The RFC does not mandate an application rollback slot.

**Materiality and inference:** Both topics read the shared freshness state; stale eligibility or validators can change with no payload. The local keep-one-until-next-successful-revalidation rule also contradicts retention untouched on a successful 304. The proposed fixture would approve this inconsistency. Leaving pixels/body unchanged is valid; metadata and any dependent state are not generally a no-op. Pruning follows the candidate’s chosen rule, not an invented HTTP retention mandate.

**Limit:** The earlier refresh disposition correctly says 304 freshens, and “display” could narrowly mean pixels. The finding concerns the unqualified no-op for both consumers, the explicit retention contradiction, and the missing metadata fixture; it does not claim every 304 must repaint.

**Discriminating check, proposed:** A matched 304 with changed Date/Cache-Control/Expires and an existing rollback slot must reuse content, update eligible metadata/age, recompute display eligibility, and apply whichever successful-validation pruning rule is actually selected.

### F02: Blanket offline fallback loses HTTP-cache versus application-history conditions and an age bound (high)

Candidate lines 11, 13, 25, 36, 44, 48, 60. Primary evidence: E02, E05, E07, E08, E23.

The accepted bounded stale policy cites disconnected cache permission as an unconditional offline display permission and treats extension absence/status as client control over directive semantics.

**Source facts:** RFC 9111 forbids disconnected stale cache reuse under applicable explicit prohibitions. RFC 5861 carries seconds windows and directive scope. RFC 9111 §6 separately allows applications/history to redisplay already retrieved data beyond HTTP freshness. HTTP cache storage eligibility still exists despite absence of numeric retention quotas.

**Materiality and inference:** “Whenever offline” supplies no expiry branch and conflicts with rejecting unbounded stale use. A marker and named policy constants do not define which store is a conforming cache, what permissions apply, or when old pixels stop being displayed. A permitted local archival/history view is a legitimate option. The defect is failing to name that contract and retaining a false blanket standards justification, not a universal ban on offline display.

**Limit:** Because §6 permits distinct application redisplay, cache MUST rules cannot automatically be imposed on every rendered image. The reviewer explicitly preserves this option and does not force one UI policy or window value.

**Discriminating check, proposed:** Separate ordinary HTTP-cache reuse from an authorized user-visible history view. Test no-cache/must-revalidate/no-store, presence/absence and expiry of SWR/SIE permission, corrected Age, offline age-cap expiry, and the chosen history exception.

### F03: Provider policy is reduced to rates/identity while offline exclusion and seven-day fallback are omitted (high)

Candidate lines 7, 13, 24, 27, 60. Primary evidence: E14, E15, E16.

The source-specific acquisition disposition omits the provider eligibility gate for this offline bundle/region use case and generalizes a conditional caching floor.

**Source facts:** OSMF Standard raster service prohibits offline/prefetch/bulk acquisition beyond actively viewed tiles; it points offline users to self-hosting or explicitly permissive providers. Seven days is a fallback only when cache headers cannot be read. Permitted normal cached revisits are distinct.

**Materiality and inference:** A small, slow or quota-bounded offline download remains prohibited at that endpoint. Applying seven days unconditionally also loses server-header freshness conditions. These are governing conditions of the chosen primary policy. For this acquisition feature the OSMF endpoint must be excluded or the feature restricted to the policy’s permitted interactive/cache-revisit use. Other providers may permit offline bundles under their own terms.

**Limit:** The final declares no selected live provider. This is a missing conditional source/provider disposition, not proof that an actual forbidden download occurred and not rejection of the generic offline viewer.

**Discriminating check, proposed:** An offline-area request using tile.openstreetmap.org must fail the provider-permission gate. An explicitly permissive/self-hosted provider remains an option. Readable Cache-Control/Expires follow their rules; only header-unreadable OSM caching takes the seven-day fallback.

### F04: Resume support probes omit the representation binding needed for safe cross-version byte resume (high)

Candidate lines 7, 23, 36, 60. Primary evidence: E09, E10, E11.

Range capability is used as the enablement gate for resumability without the governing strong-validator, encoded-range and response-branch conditions.

**Source facts:** Accept-Ranges is advisory; servers may return 200 despite it. Partial pieces may only be combined with the same strong validator. If-Range must not use a weak ETag; Content-Range and content coding/length matter. 416 is an error/length signal, not successful resume.

**Materiality and inference:** The topic explicitly shares changing tile versions. Resuming an old prefix against a newer suffix can corrupt the tile even if 206 support was demonstrated. The suggested 206/416-only oracle misses valid 200 fallback and representation changes. The 10–40 KB rationale has no captured measurement. Whole-tile retry with completed-tile/region checkpointing remains a sound conservative option. An optional byte-resume route must retain representation binding; no full application plan or numerical optimization threshold is required.

**Limit:** The candidate correctly disables default per-tile Range and leaves live support unresolved. This finding targets the conditions under which its proposed optional branch would be promoted, not a demand to implement Range now.

**Discriminating check, proposed:** Drop a transfer, change origin version, then request the remainder. Strong If-Range/representation binding must select safe full replacement or compatible partial data; validate Content-Range/coding/length and include 200, 206 and 416 cases. Keep checkpointed whole-tile acquisition distinct from an unsupported bundle API.

### F05: Status-only rules broaden SIE and overstate 404 removal (high)

Candidate lines 11, 25, 32, 39, 44, 48. Primary evidence: E05, E08, E13, E20.

The bundle maps all non-404/410 failures to SIE while mapping any 404 to definitive removal and leaving already-defined RFC error scope as an unknown.

**Source facts:** RFC 5861’s defined error situations yield 500/502/503/504 and have a staleness bound. RFC 9110 says 404 may be temporary or undisclosed, while 410 indicates likely permanence. Mapbox documents 404 while a tileset is unpublished/processing.

**Materiality and inference:** The default can continue display for unrelated authorization/request failures and terminate an otherwise useful cached tile on temporary 404. Its status fixture locks in these wrong classifications; “SIE scope unresolved” obscures a condition already in the captured source. A conservative local stop-on-404 policy is permitted as a choice, and a broader local archival fallback may be chosen separately. Neither should be presented as RFC-defined removal or SIE behavior. Permanent deletion/retention requires a declared local/provider contract.

**Limit:** The disposition uses the word definitive, which can be a provider-specific qualification. The cross-topic test and broader non-404/410 rule omit that qualifier; no provider evidence making every 404 definitive was supplied.

**Discriminating check, proposed:** Distinguish 500/502/503/504, network failure, 401/403, 429, temporary/processing 404 and a provider-confirmed removal/410. Assert the chosen independent display, retry and retention responses plus SIE age/permission bounds.

### F06: A MediaWiki parser-cache TTL is attributed to mod_tile expiry (medium)

Candidate lines 13, 56, 60. Primary evidence: E17, E21.

Keyword presence is promoted into a tile-specific numeric precedent despite a different subject and authority layer.

**Source facts:** The captured rendering-wiki HTML places Cache expiry:86400 and Reduced expiry:false inside the NewPP parser-cache report; its other 86400 occurrence is parser-cache metadata. The page contains no mod_tile name. The mod_tile README supplies configurable expiry heuristics but no one-day value.

**Materiality and inference:** The sole asserted numeric tile precedent for retention is absent. This is a consequential source-attribution error even though the final also says quotas are unresolved and the precedent is nonnormative. Hashes and grep counts cannot establish this semantic claim. 86400 seconds equals one day, but the fact concerns caching the wiki page. The correct bounded negative is that these captured documents supply no tile one-day retention precedent.

**Limit:** No chosen quota directly derives from the number. Severity is therefore medium rather than claiming a demonstrated shipped quota failure.

**Discriminating check, proposed:** Bind each numeric value to its surrounding authored/configuration subject and authority. The parser comment and metadata must be rejected as tile-policy evidence; any later actual mod_tile config capture needs its own version and locator.
