## Material defects and governing conditions

**D1 — Regeneration is confused with integrity verification (high; correctness/usefulness).** Final lines 214–216 prescribe “regenerate-then-validate, never validate-then-trust”; F1 lines 43–45 correctly discusses regeneration after authorized changes, but the later categorical rule lacks that restriction. Primary counterevidence: RFC 8493 §§1.3/3 define validation against recorded checksums (P01, extracted lines 462–475); bagit.py lines 451–460 deliberately defaults `manifests=False` to avoid creating a new baseline for corrupted payloads, and lines 515–519/1275–1299 regenerate tag checksums from current bytes (P02). Pinned tests demonstrate changed tag contents fail against the existing reference and that explicitly replacing the checksum makes them pass (P28, lines 383–402). **Static inference:** regenerating a tag manifest before assessing existing tags blesses a damaged tag or payload manifest into the new baseline. Legitimate authorized updates need regeneration; that does not make regeneration an integrity test. This is not a claim that an executed check was falsely reported.

**D2 — External-directory promotion is not a crash-safe transaction (high; completeness/usefulness).** Final F4 lines 65–74 says flip the row to complete inside SQLite and atomically move into the store; line 264 says stage+verify+flip addresses recovery. Primary counterevidence: SQLite §5 coordinates attached *database* files using its journal machinery, not arbitrary directory renames (P03, extracted lines 538–644). The Linux fsync documentation explicitly distinguishes file durability from a required directory fsync (P24, extracted lines 36–39). **Static inference:** commit-before-rename permits a complete row without a promoted bag; rename-before-commit permits a promoted bag with rolled-back metadata. A pre-promotion fsync does not describe post-rename directory durability. The final only tells restart to re-verify quarantine/incomplete rows and never auto-promote; it does not cover both persistent states or final-store orphans. This is an incomplete proposed recovery protocol, not a reproduced implementation bug.

**D3 — Catalog visibility does not establish byte access control (high; completeness/usefulness; narrower source attribution error).** F7 lines 93–103 and §9 line 267 treat catalog layers/auto-add guards as covering sensitive originals; V5 lines 243–245 proposes that direct media URLs become unreachable. The mixed-visibility quote itself is accurate. Primary counterevidence: an Omeka maintainer explains that known filesystem filenames are accessible and that permission-enforcing storage needs an additional delivery mechanism (P20, July 8 response; [primary discussion](https://forum.omeka.org/t/media-privacy-and-direct-file-urls/29696/3)). Omeka S v4.2.1, resolved to commit `7e428a3296a399e21a6a6418578175ad8c7edf60`, defaults to `/files`, creates direct URLs, and exempts existing files from PHP routing (P38 lines 20–33; P31 lines 72–75; P39 lines 5–10). The Access module's own instructions require server rewrites to prevent direct access (P21, extracted lines 115–118). This is conditional counterevidence about a supported analogue, **not a claim that the unspecified future custom catalog must use default Omeka storage**. The final lacks the delivery/storage condition needed for its coverage claim, including what happens after a previously public original is restricted. Site membership auto-add settings also do not themselves change item public/private visibility (P04, extracted lines 171–173 versus 320–324); calling them auto-publication conflates two states. A proposed test is useful but does not close the design gap.

**D4 — Fast success is aggregate-count success, not per-file presence (medium; correctness).** F2 lines 47–53 calls the tier a “presence/size sweep” and says log “presence-only”; §3 lines 152–153 describes Payload-Oxum presence/size. Primary counterevidence: `_validate_oxum` sums total bytes/count; `fast=True` returns before `_validate_completeness` (P02 lines 778–795, 797–837). The project's pinned `test_validate_completeness` renames an expected file and asserts fast success while completeness fails (P28 lines 119–130). The candidate correctly warns it skips checksums. Its remaining presence wording can still falsely imply expected paths were verified; missing/replaced files can cancel in the aggregate. Weekly full validation mitigates the detection delay but does not strengthen the nightly observation.

**D5 — “Cannot copy corruption” exceeds the proposed checks (medium; correctness/usefulness).** F5 lines 76–79 permits “completeness + spot fixity” before copy while naming the mechanism a replica that cannot copy corruption. Primary counterevidence: RFC §3 requires all recorded checksums for validity (P01 lines 471–475); pinned same-length-bit-change tests pass completeness/fast but fail full validation (P28 lines 100–111). **Static inference:** an unsampled same-size damaged file can be copied. Full verification afterward can detect it against an unchanged trusted manifest; versioned snapshots can retain a good older version. Those mitigations do not establish the absolute heading, nor specify rejection/retention/known-good selection of a failed new replica. No claim is made that versioning necessarily overwrites an older copy.

**D6 — Cloud versioning is not immutability (medium; correctness/breadth; optional alternative).** M-e lines 144–147 says cloud object storage “with versioning” provides “cheap immutability,” expressly under a synthesis label. Primary counterevidence: AWS documents permanent deletion of a selected version and noncurrent-version expiry (P35, extracted lines 8–18 and 29–43); Object Lock is an additional retention/legal-hold mechanism with mode and permission conditions (P25, extracted lines 6–38 and 109–121). No provider was selected, so these are a primary counterexample to the generic guarantee, not an assumption that the archive uses S3. Encryption does not prevent authorized deletion. The optional status reduces immediate implementation impact but leaves the alternative comparison inaccurate; “cheap” also lacks cost evidence.

**D7 — Failed-storage recovery is absent despite a complete-coverage claim (high; completeness).** The brief explicitly requires recovery from failed storage. Final lines 264 and 273–274 claim recovery addressed and no plan clause unaddressed; F5 and V3 describe copying and refusing overwrite, not restoring. Primary evidence: brief.md lines 3–5 and plan.md line 3 are the governing requirements; SQLite's own backup guidance explains the database/journal/WAL consistency conditions (P23 §1.2–1.3). No section specifies reconstituting originals plus their database, dedup back-references, provenance and rights, or validating a restore after losing disk 1. This is an observed omission in a fully read artifact, not a failed runtime test.

**D8 — An introduction-only absence check is generalized to the entire retrieved documentation (medium; correctness/breadth).** Final F9 lines 115–117 claims the retrieved Archivematica ranges contain no normalization/format-policy/PREMIS/BagIt coverage. Critique C-1/C-2 and C6 source note reach that conclusion from intro-page term counts; dispositions C-1 repeats it. Primary counterevidence: the independently retrieved **same declared S6 documentation root**, Archivematica 1.18 (P07), lists BagIt transfers at extracted line 76, describes SIP→AIP/DIP at lines 102–103, lists PREMIS rights and normalization at 106–107, and describes editing format policies for normalization/characterization/validation at 144–146, with PREMIS at 163. The intro alone lacks those terms, but the three-page declared source set does not. These brief index descriptions do not establish normalization event logging, a specific affordable policy, or BagIt interoperability details; deleting an over-specific claim can still be warranted. The defect is the incorrect negative source claim and the resulting dismissal of pertinent leads already in the frozen source set. It is inherited from, and preserved by, the required critique rather than erased by this review.

Additional limits, kept separate from material defects: bagit-python's creator writes **BagIt 0.97**, not 1.0 (P02 lines 242–245; P28 lines 482–485), although final F1/§7 adopts the 1.0 every-manifest rule. A deliberate compatibility choice is possible, but not stated. The below-bag dedup mechanism is not physically selected; M-c simultaneously defers a content-addressed store. Bare content addressing does not by itself schedule verification. RFC filename interoperability is a reasonable premise for richer metadata but does not directly establish volunteer naming/search failure. The Omeka Items page actually discusses linked resources/templates outside the candidate's narrowly declared excerpts; the final honestly declines to claim that behavior, so this is lost discovery breadth, not a false positive. Equal byte counts do not prove equal bytes; the supplied “identical upstream content” notes overstate their identity evidence. Independent SHA-256 identities here apply to this review's captures, not retroactively to discarded candidate captures. Pinned code's string-prefix path containment check also does not justify a general symlink/contributed-path safety guarantee; V8 only covers named textual path cases.
