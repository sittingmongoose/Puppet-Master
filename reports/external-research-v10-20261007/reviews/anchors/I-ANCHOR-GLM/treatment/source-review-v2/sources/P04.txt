283: There are four fundamental top-level roles in the framework:
284: - Root role
285: - Targets role

292: All roles can use one or more keys and require a threshold of signatures of
293: the role's keys in order to trust a given metadata file.

295: ### Root role ### {#root}
296: 
297: The root role delegates trust to specific keys trusted for all other
298: top-level roles used in the system.
299: 
300: The client-side of the framework MUST ship with trusted root keys for each
301: configured repository.
302: 
303: The root role's private keys MUST be kept very secure and thus should be
304: kept offline.  If less than a threshold of Root keys are compromised, the
305: repository should revoke trust on the compromised keys.  This can be
306: accomplished with a normal rotation of root keys, covered in section
307: [[#key-management-and-migration]]. If a threshold of root keys is compromised,
308: the Root keys should be updated out-of-band, however, the threshold should
309: be chosen so that this is extremely unlikely.  In the unfortunate event that
310: a threshold of keys are compromised, it is safest to assume that attackers
311: have installed malware and taken over affected machines.  For this reason,
312: making it difficult for attackers to compromise all of the offline keys is
313: important because safely recovering from it is nearly impossible.

507: Implementers of TUF may use any data format for metadata files as long as
508: all fields in this specification are included and TUF clients are able to
509: interpret them without ambiguity. Implementers should choose a data format
510: that allows for canonicalization, or one that will decode data
511: deterministically by default so that signatures can be accurately verified.
512: The chosen data format should be documented in the POUF of the implementation.
513: The examples in this document use a subset of the JSON object format, with
514: floating-point numbers omitted.  When calculating the digest of an
515: object, we use the "canonical JSON" subdialect as described at [Canonical JSON](
516: https://web.archive.org/web/20251209150702/http://wiki.laptop.org/go/Canonical_JSON).

1294: ## Record fixed update start time ## {#fix-time}
1295: 
1296: Record the time at which the update began as the fixed update start time.
1297: Time is fixed at the beginning of the update workflow to allow
1298: an application using TUF to effectively pause time, in order to ensure that
1299: metadata which has a valid expiration time at the beginning of an update
1300: does not fail an expiration check later in the update workflow.

1302: ## Load trusted root metadata ## {#load-trusted-root}
1303: 
1304: Load the trusted root metadata file.  We assume that a good,
1305: trusted copy of this file was shipped with the package manager or software
1306: updater using an out-of-band process.  Note that the expiration of the
1307: trusted root metadata file does not matter, because we will attempt to update
1308: it in the next step.
1309: 
1310: ## Update the root role ## {#update-root}
1311: 
1312: 1. Since it may now be signed using entirely different keys, the client MUST
1313:   somehow be able to establish a trusted line of continuity to the latest set
1314:   of keys (see [[#key-management-and-migration]]).  To do so, the client MUST
1315:   download intermediate root metadata files, until the latest available one is
1316:   reached.
1317: 
1318: 2. Let N denote the version number of the trusted root metadata
1319:   file.
1320: 
1321: 3. **Try downloading version N+1 of the root metadata file**, up to
1322:   some W number of bytes (because the size is unknown). The value for W is set
1323:   by the authors of the application using TUF. For example, W may be tens of
1324:   kilobytes. The filename used to download the root metadata file is of the
1325:   fixed form VERSION_NUMBER.FILENAME.EXT (e.g., 42.root.json). If this file is
1326:   not available, or we have downloaded more than Y number of root metadata
1327:   files (because the exact number is as yet unknown), then go to step 5.3.10.
1328:   The value for Y is set by the authors of the application using TUF. For
1329:   example, Y may be 2^10.
1330: 
1331: 4. **Check for an arbitrary software attack.** Version N+1 of the root
1332:   metadata file MUST have been signed by: (1) a <a>THRESHOLD</a> of keys
1333:   specified in the trusted root metadata file (version N), and (2) a
1334:   <a>THRESHOLD</a> of keys specified in the new root metadata file being
1335:   validated (version N+1).  When computing the <a>THRESHOLD</a> each
1336:   <a>KEY</a> MUST only contribute one <a>SIGNATURE</a>. That is, each
1337:   <a>SIGNATURE</a> which is counted towards the <a>THRESHOLD</a> MUST have
1338:   a unique <a for="root">KEYID</a>. Even if a <a for="root">KEYID</a> is listed
1339:   more than once in the "signatures" list a client MUST NOT count more than one
1340:   verified <a>SIGNATURE</a> from that <a for="root">KEYID</a> towards the
1341:   <a>THRESHOLD</a>.
1342:   If version N+1 is not signed as required, discard it, abort the update cycle,
1343:   and report the signature failure.  On the next update cycle, begin at step
1344:   [[#update-root]] and version N of the root metadata file.
1345: 
1346: 5. **Check for a rollback attack.** The version number of the new root
1347:   metadata (version N+1) MUST be exactly the version in the trusted root
1348:   metadata (version N) incremented by one, that is precisely N+1.
1349:   If the version of the new root metadata file is not N+1, discard it,
1350:   abort the update cycle, and report the rollback attack.
1351: 
1352: 6. Note that the expiration of the new (intermediate) root metadata
1353:   file does not matter yet, because we will check for it in step 5.3.10.
1354: 
1355: 7. **Set the trusted root metadata file** to the new root metadata
1356:   file.

1359:   non-volatile storage as FILENAME.EXT (e.g. root.json).
