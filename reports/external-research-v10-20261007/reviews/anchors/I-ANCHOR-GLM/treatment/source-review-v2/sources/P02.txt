435: 4.2. Prefix Indexes
436: By default, FTS5 maintains a single index recording the location of each
437: token instance within the document set. This means that querying for complete
438: tokens is fast, as it requires a single lookup, but querying for a prefix
439: token can be slow, as it requires a range scan. For example, to query for
440: the prefix token "abc*" requires a range scan of all tokens greater than
441: or equal to "abc" and less than "abd".
442: A prefix index is a separate index that records the location of all
443: instances of prefix tokens of a certain length in characters used to speed
444: up queries for prefix tokens. For example, optimizing a query for prefix
445: token "abc*" requires a prefix index of three-character prefixes.
446: To add prefix indexes to an FTS5 table, the "prefix" option is set to
447: either a single positive integer or a text value containing a white-space
448: separated list of one or more positive integer values. A prefix index is

579: 4.3.4. The Trigram Tokenizer
580: The trigram tokenizer extends FTS5 to support substring
581: matching in general, instead of the usual token matching. When using the
582: trigram tokenizer, a query or phrase token may match any sequence of characters
583: within a row, not just a complete token. For example:
584: CREATE VIRTUAL TABLE tri USING fts5(a, tokenize="trigram");
607: If an FTS5 trigram tokenizer is created with the case_sensitive option set to 1,
608: it may only index GLOB queries, not LIKE.
609: Notes:
610: Substrings consisting of fewer than 3 unicode characters do not match any
611: rows when used with a full-text query. If a LIKE or GLOB pattern does not
612: contain at least one sequence of non-wildcard unicode characters, FTS5
613: falls back to a linear scan of the entire table.
614: If the FTS5 table is created with the detail=none or detail=column option
615: specified, full-text queries may not contain any tokens longer than 3
616: unicode characters. LIKE and GLOB pattern matching may be slightly slower,
617: but still works. If the index is to be used only for LIKE and/or GLOB
618: pattern matching, these options are worth experimenting with to reduce
619: the index size.
620: The index cannot be used to optimize LIKE patterns if the LIKE operator
621: has an ESCAPE clause.
