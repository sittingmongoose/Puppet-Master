L474: FTS5 features four built-in tokenizer modules, described in subsequent
L475: sections:
L476: The unicode61 tokenizer, based on the Unicode 6.1 standard. This

L490: characters assigned to a
L491: general category beginning with "L" or "N" (letters and numbers,
L492: specifically) or to category "Co" ("other, private use") are considered tokens.
L493: All other characters are separators.

L546: 4.3.2. Ascii Tokenizer
L547: The Ascii tokenizer is similar to the Unicode61 tokenizer, except that:
L548: All non-ASCII characters (those with codepoints greater than 127) are
L549: always considered token characters. If any non-ASCII characters are specified
L550: as part of the separators option, they are ignored.
L551: Case-folding is only performed for ASCII characters. So while "A" and
L552: "a" are considered to be equivalent, "Ã" and "ã" are distinct.
L553: The remove_diacritics option is not supported.
L554: For example:
L555: -- Create an FTS5 table that uses the ascii tokenizer, but does not
L556: -- consider numeric characters to be part of tokens.
L557: CREATE VIRTUAL TABLE ft USING fts5(a, b,
L558: tokenize = "ascii separators '0123456789'"
L559: );

L579: 4.3.4. The Trigram Tokenizer
L580: The trigram tokenizer extends FTS5 to support substring
L581: matching in general, instead of the usual token matching. When using the
L582: trigram tokenizer, a query or phrase token may match any sequence of characters
L583: within a row, not just a complete token. For example:
L584: CREATE VIRTUAL TABLE tri USING fts5(a, tokenize="trigram");
L585: INSERT INTO tri VALUES('abcdefghij KLMNOPQRST uvwxyz');
L586: -- The following queries all match the single row in the table
L587: SELECT * FROM tri('cdefg');
L588: SELECT * FROM tri('cdefg AND pqr');
L589: SELECT * FROM tri('"hij klm" NOT stuv');
L590: The trigram tokenizer supports the following options:
L591: Option Usage
L592: case_sensitive
L593: This value may be set to 1 or 0 (the default). If it is set to 1,
L594: then matching is case sensitive. Otherwise, if this option is set to
L595: 0, matching is case insensitive.
L596: remove_diacritics
L597: This value may also be set to 1 or 0 (the default). It may only
L598: be set to 1 if the case_sensitive options is set to 0 - setting both
L599: options to 1 is an error. If this option is set, then diacritics are
L600: removed from the text before matching (e.g. so that "á" matches "a").
L601: -- A case-sensitive trigram index
L602: CREATE VIRTUAL TABLE tri USING fts5(a, tokenize="trigram case_sensitive 1");
L603: Unless the remove_diacritics option is set, FTS5 tables that use the trigram
L604: tokenizer also support indexed GLOB and LIKE pattern matching. For example:
L605: SELECT * FROM tri WHERE a LIKE '%cdefg%';
L606: SELECT * FROM tri WHERE a GLOB '*ij klm*xyz';
L607: If an FTS5 trigram tokenizer is created with the case_sensitive option set to 1,
L608: it may only index GLOB queries, not LIKE.
L609: Notes:
L610: Substrings consisting of fewer than 3 unicode characters do not match any
L611: rows when used with a full-text query. If a LIKE or GLOB pattern does not
L612: contain at least one sequence of non-wildcard unicode characters, FTS5
L613: falls back to a linear scan of the entire table.
L614: If the FTS5 table is created with the detail=none or detail=column option
L615: specified, full-text queries may not contain any tokens longer than 3

L921: 4.8. The Locale Option
L922: This option is only useful to applications that implement
L923: custom tokenizers. If an fts5 table is created
L924: with the "locale=1" option specified, then the fts5_locale() SQL function may
L925: be used to associate a locale value (e.g. "th_TH" or "en_US") with strings
L926: passed to FTS5. FTS5 itself does not use locale values, but makes them
L927: available to the tokenizer implementation whenever the string is tokenized.
L928: The tokenizer may then adjust its behavior based on the locale.
L929: -- The following statement creates an fts5 table with locale support.
L930: -- The "tokenizer=..." option below must be replaced with a real tokenizer
L931: -- specification for a tokenizer that supports locales.
L932: CREATE VIRTUAL TABLE ft USING fts5(a, b, locale=1, tokenizer=...);
L934: -- column "a" uses locale "th_TH", the value written to column "b" uses the
L935: -- tokenizer's default locale
L936: INSERT INTO ft(a, b) VALUES(
L937: fts5_locale('th_TH', 'Tokenize this in Thai locale'),
L938: 'Tokenize this in the default locale.'
L939: );
L940: -- The "en_US" locale is used to tokenize the query terms in the
L941: --following query.
L942: SELECT * FROM ft( fts5_locale('en_US', 'query terms') );
L943: Attempting to pass an fts5_locale() string to an fts5 table that was not
L944: created with the locale=1 option is an error.
L945: When an fts5_locale() string is stored in a normal content table (i.e. not a
L946: contentless or external content table), the attached locale is stored along
L947: with it. If the string is tokenized by FTS5 again, for example because its
L948: row is being deleted or as part of an auxiliary function evaluation, the
L949: attached locale is again passed to the tokenizer implementation.
L950: In order to support locales, an FTS5 external-content table may use an SQL
L951: view that returns fts5_locale() values as the content table. For example:
L952: -- Each row of this table contains a string and its locale.
L953: CREATE TABLE t1(val, locale);
L954: INSERT INTO t1 VALUES('a text value', 'en_US');
L955: -- A view to combine the string and locale from table t1.
L956: CREATE VIEW v1 AS SELECT rowid, fts5_locale(val, locale) AS val FROM t1;
L957: -- An FTS5 table to read locale-enabled strings from view v1.
L958: CREATE VIRTUAL TABLE ft USING fts5(val, locale=1, content=v1, tokenize=...);
L959: If an fts5_locale() value is written to an UNINDEXED column of an fts5
L960: table, the locale value is discarded and the string stored by itself.
L961: The fts5_get_locale() function may be used to retreive
L962: the locale of a value stored in an FTS5 table.
