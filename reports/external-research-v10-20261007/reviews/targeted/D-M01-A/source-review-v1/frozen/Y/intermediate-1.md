# D-M01-A research-stage draft: incremental SQLite snapshot

## Recommendation
Use SQLite’s Online Backup API for the nightly snapshot, conditionally: it is a sound bounded mechanism when the job can finish within its window and the destination is isolated. It does not promise prompt completion under uninterrupted writes from another source connection; those writes can restart the copy, potentially forever. Use a private staging destination and publish it as the nightly snapshot only after the API reports completion and validation passes. Retain the previous known-good snapshot on any failure. The exact publication/retention mechanism is an application choice, not established by these captures.

No predecessor draft or claims were supplied. Statuses below apply to this research recommendation, not to an external candidate.

**Rejected claims:** “finish returns `SQLITE_OK` proves completion, progress counts prove snapshot validity, or unlimited retries ensure success.” The captured source contracts contradict these assumptions.

## Findings and obligation dispositions

1. **Connection roles and legal use — accepted.** Call `sqlite3_backup_init(dest, "main", source, "main")`: the destination connection/file is the database being replaced; the source connection is the live note index. They must be different handles. The destination must have no open read or write transaction at init; from successful init until finish, do not use the destination connection through any other API (and avoid other connections to its shared cache). Complete exactly one `sqlite3_backup_finish()` for each successful init. The source may continue to be used when calls are properly serialized/thread-safe; do not call `backup_step` while the source handle is in a write transaction.

2. **Consistency under writes — amended.** The API holds a source read lock only during each step, so short batches let the writer run between calls. Completion yields a consistent database snapshot. Writes through the same file-backed source connection update pages already copied; writes through another connection/process normally restart the backup on the next step. Repeated restarts can prevent completion. For this single-host app, prefer coordinating small backup steps on the existing writer connection between its transactions, serialized on that handle, if architecture permits. If the backup must use a separate read connection, measure restart behavior under the real write rate and fail by a deadline rather than implying an exact start-time snapshot. The docs describe same-handle writes as automatically reflected and other-connection writes as restart-causing; they do not provide a timestamp API identifying the snapshot cut.

3. **Completion, contention, and terminal failure — amended.** `SQLITE_OK` means a step succeeded but may leave pages; only observing `SQLITE_DONE` means the API completed. `SQLITE_BUSY` and `SQLITE_LOCKED` from step are retryable: retry the same handle later. The captured API docs describe `LOCKED` when the source connection is being used to write, while the 3.51.3 code explicitly returns `BUSY` when its source b-tree is already in a write transaction (code lines 337–342). Handle the actual returned code, log the extended code/error, and treat recurring contention as a scheduling problem. Proposed bounded policy: copy 64 pages per step; pace successful steps briefly to yield to the writer; retry BUSY/LOCKED with 100 ms exponential backoff capped at 1 s, stopping at 10 contention returns or a 5-minute total job deadline, whichever comes first. These limits are starting values, not SQLite requirements; tune them against database size and the nightly window. Treat other step errors (including READONLY, NOMEM, and IOERR variants) as terminal; do not retry the same operation indefinitely.

4. **Cleanup and finish — accepted.** On `SQLITE_DONE`, call finish, require its result to be `SQLITE_OK`, close the destination, validate, then publish. On timeout/contention exhaustion or any terminal step error, call finish once to release resources, close handles, and discard the private partial staging artifact; do not publish it. Finish rolls back an unfinished destination transaction, but its `SQLITE_OK` alone does **not** prove that the copy completed: it may return OK when no step error occurred even if the caller abandoned the operation. Track whether `SQLITE_DONE` was observed independently.

5. **Destination transaction and page-size restrictions — accepted.** The destination is write-locked for the operation. It must be writable and not concurrently accessed. If it is in WAL mode, source and destination page sizes must match or step can return `SQLITE_READONLY`; the 3.51.3 source enforces this (lines 373–383). Prefer creating/configuring the staging database with a matching page size and verify its journal mode before init. A rollback-journal file destination can have its page size changed by backup, but matching sizes avoids this branch and is safer for a nightly routine.

6. **Progress counts — amended.** `backup_remaining()` and `backup_pagecount()` report values from the most recent step, not live inspection; source changes may make them stale until the next step, and restarts can make percentage jump. Use them only for best-effort telemetry (`pagecount==0` needs a separate display case), never as completion, consistency, or validity proof. `SQLITE_DONE` is the completion signal.

7. **Minimal discriminating validation; uncertainty and leads — unresolved where noted.** Proposed (not executed): test a representative copy while the writer inserts/updates/deletes between steps, once with a serialized same-handle writer and once via a second source connection; require the completed destination to pass `PRAGMA integrity_check` and workload-specific row/foreign-key invariants, and record duration/restarts. Separately force destination contention, an active source write transaction, an injected disk/IO failure, and a WAL page-size mismatch; verify retry versus terminal classification, that incomplete staging is never published, and that the prior snapshot remains usable. No database was opened and no runtime test was run for this research stage. Main unresolved dependency: whether the application can schedule steps on the writer handle between transactions. If not, test whether its actual update rate permits completion within five minutes; raise no cap without an explicit nightly budget. `VACUUM INTO` is documented as an alternative, but these captures do not establish its concurrency/latency tradeoffs here, so retain it as a lead for a separately tested comparison. `sqlite3_rsync` is also listed by SQLite but is not a fit for this local-only destination unless remote replication later becomes a requirement.
