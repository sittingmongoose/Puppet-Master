# D-M01-A control — stage criticism

**Stage result:** critique only; this does not finalize the recommendation. The predecessor draft is largely sound. Retain its conditional recommendation, with one material correction about sqlite3_backup_finish() in the selected release.

## Obligation dispositions

1. **Connection roles and legal usage — accept, clarify the operational boundary.** The draft correctly gives D as destination and S as source, requires distinct connection handles, notes destination transaction-at-init failure, and calls finish once per successful init. Keep the destination handle unavailable to all other API calls from init through finish; with shared cache, isolate the destination file from same-process connections too. A dedicated source handle is prudent, not a general API requirement: concurrent source-handle use depends on a threadsafe SQLite build.

2. **Consistency under writes — accept with amendment.** “Consistent and up-to-date snapshot” is not a snapshot frozen at the scheduled start time. A write through another source connection/process can make the next step restart copying from the beginning; writes through the same file-based source handle update already-copied pages. Repeated restarts can prevent completion. The draft says this, but should make the consequence of its dedicated-source-handle recommendation explicit: if the live writer uses another handle, its commits take the restart path. Proposed check: commit between partial steps via both the backup source handle and a second writer handle; verify completed-copy integrity and transactional invariants, and measure restart/runtime behavior.

3. **Completion, retry, terminal failure, cleanup — amend one material code claim.** DONE is the completion signal; OK means continue; BUSY/LOCKED can be retried on the same backup handle; other step errors are terminal for this run. Keep bounded elapsed-time and retry limits as proposed policy, not SQLite guarantees. However, the draft says BUSY/LOCKED do not affect finish’s return. That matches the captured API prose but conflicts with the supplied SQLite 3.51.3 implementation: backup_step stores its result in p->rc (line 558), and backup_finish returns SQLITE_OK only when p->rc == SQLITE_DONE, otherwise p->rc (lines 602–605). Amend the statement to distinguish docs from the version-pinned code; log both codes, and count success only after a step returned DONE and finish returned OK (the draft’s actual success rule is safe). The implementation also returns immediate BUSY when the source pager is already in a write transaction (lines 337–342); a busy timeout does not turn that branch into a wait, so explicit backoff/deadline must handle it. Proposed checks: transient lock contention clears and succeeds on retry; persistent contention reaches the deadline; cleanup occurs after finish/close and only removes the run-unique staging file and sidecars; the previous good snapshot remains untouched.

4. **Destination transaction/page-size constraints — accept, keep runtime condition.** The draft correctly covers destination transaction-at-init, writable disk staging, and the WAL page-size mismatch that yields READONLY. “Default rollback-journal mode” is a proposal that must be verified on the opened destination; retain the runtime journal-mode/page-size check. Exercise a pre-existing destination transaction and WAL/source page-size mismatch.

5. **Progress counts — accept.** These counts describe the last step’s view and may lag source-size changes until the next step. They are estimates, not completion evidence. The draft’s DONE requirement is right. Keep reads serialized against concurrent step/finish calls; the API warns concurrent counter access with stepping can return invalid values.

6. **Validation and alternative — accept as proposed, not executed.** The draft proposes integrity/invariant checks, contention and deadline cases, destination restrictions, reopen/validate, and atomic publication while preserving the prior snapshot. Tighten pass criteria in implementation, but no test was executed in this research stage. Retain VACUUM INTO only as an alternative when a vacuumed copy is desired; comparative contention/performance was not established.

## Remaining conditions and evidence

Unresolved deployment facts: whether writer and backup use the same source handle, whether long transactions or sustained churn occur, destination journal mode/page size, and whether the deployed 3.51.3 build is threadsafe as assumed for concurrent-handle use. These affect scheduling and performance, not the conditional API-suitability conclusion. Resolve them with target-build checks before adopting timings as operational limits.
