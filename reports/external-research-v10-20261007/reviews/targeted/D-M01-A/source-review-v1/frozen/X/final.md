# D-M01-A — bounded recommendation

**Recommendation — accepted with conditions.** SQLite’s Online Backup API is suitable as a nightly snapshot mechanism for this single-host, local-disk database if a run writes to a private, unique staging file and the deployed SQLite 3.51.3 build is checked against the policy below. Publish only after a step explicitly returns `SQLITE_DONE`, `sqlite3_backup_finish()` returns `SQLITE_OK`, the connections close, and the staged copy passes reopen and integrity checks. A failed or unfinished run must leave the last known-good snapshot untouched.

1. **Connections and legal use — accepted, clarified.** Call `sqlite3_backup_init(D,"main",S,"main")`: D is writable destination and S is source; they must be different connection handles. D must have no open read or read-write transaction at init. Call finish exactly once after each successful init, including on abandonment. From init through finish, do not pass D to any other API; with shared cache, do not access the destination file through another same-process connection either. A dedicated S handle is prudent for a single backup coordinator. Concurrent use of S from other threads is permitted only when this SQLite build is compiled and configured for threadsafe connections. [API]

2. **Writes during the copy — accepted with amendment.** Each step holds a source read lock only for that call, so writes may proceed between steps. A completed copy is consistent and up to date, but is not promised to represent the exact scheduled-start instant. A write from another connection/process usually restarts the copy; a write through the same file-backed S handle updates copied pages. Thus, using a dedicated backup S while the live writer uses another handle takes the restart path. Repeated restarts can prevent completion. In the pinned implementation, a step returns `SQLITE_BUSY` immediately if S’s pager is already in a write transaction; a busy timeout alone does not wait through that branch. [Online Backup API] [API] [3.51.3 code]

3. **Results, retry, and cleanup — accepted with a material correction.** On init failure (NULL), record D’s error and fail setup. For steps, `SQLITE_OK` means continue, `SQLITE_DONE` alone means complete, and `SQLITE_BUSY`/`SQLITE_LOCKED` may be retried later on the same handle. Treat other step errors as terminal for this run. Proposed bounded policy—not a SQLite guarantee: step 128 pages at a time; use a 250 ms busy timeout and about 100 ms backoff between partial steps/retries; abandon after 60 seconds overall or 8 consecutive BUSY/LOCKED results, whichever comes first. Tune these limits from target-build measurements. After success or abandonment, finish once, log every step result plus finish’s result, close both handles, then remove only this run’s unique staging file and its SQLite sidecars. If cleanup fails, report it and do not reuse that staging path. A later run uses a fresh path; retain the last good snapshot.

   The API prose says finish can return `SQLITE_OK` even when no step completed and says BUSY/LOCKED do not affect finish’s result. The supplied 3.51.3 code instead returns the last stored step result unless it is DONE, mapping DONE to OK: an incomplete last `SQLITE_OK` still yields OK, while a last BUSY/LOCKED is preserved. So finish alone is never completion evidence; require a recorded DONE and finish OK. [API] [3.51.3 code]

4. **Destination restrictions — accepted, runtime-checked.** Use a writable disk staging database, not an in-memory destination, and do not open a destination transaction before init. SQLite normally sets a disk destination’s page size during backup. A destination in WAL mode with a page size different from the source can make step fail with `SQLITE_READONLY`; keep staging out of WAL or establish a matching page size. Read back journal mode and page size on the actual target before relying on either assumption. [API] [3.51.3 code]

5. **Progress — accepted.** `sqlite3_backup_remaining()` and `sqlite3_backup_pagecount()` report the previous step’s view; changes to source size are not reflected until another step. They are estimates, not proof of a stable total, completion, or a point-in-time snapshot. Read them through the same serialized backup owner, not concurrently with step/finish. Use the step result for completion. [Online Backup API] [API]

6. **Validation and retained alternative — proposed, not executed.** On the deployed 3.51.3 build: (a) step a multi-page database while committing known transactions through both S and a second writer handle; then reopen the copy, run `PRAGMA integrity_check`, and verify transaction-level markers/invariants; measure restarts and duration; (b) induce transient BUSY/LOCKED that clears and sustained contention that reaches the deadline, checking same-handle retry, finish logging, owned-file cleanup, and preservation of the prior snapshot; (c) test destination transaction-at-init and WAL/page-size mismatch and verify no failed candidate is published. These are proposed checks; no database/runtime test was executed here. Reopen and validate before same-filesystem atomic publication. Retain **VACUUM INTO** as an optional lead if a vacuumed/compacted copy is wanted; comparative contention and timing were not established. [Online Backup API]

**Unresolved deployment facts:** whether S is shared with the writer, writer transaction duration and churn, SQLite threadsafe configuration, destination journal mode/page size, and whether a 60-second window is operationally adequate. Confirm these before adopting the proposed limits; sustained external writes may repeatedly restart a dedicated-handle backup.
