# D-M02-B control — Q1 recommendation

**Scope.** This answers how to read a small crop and preserve its grid, plus the requested Q2 distinction. Sources are the frozen Rasterio 1.3.10 and GDAL 3.9.0 public materials listed below and text-only inspection of tagged Rasterio 1.3.10 implementation files. No downloaded code was executed; proposed fixtures below were not run.

## Recommendation and obligation dispositions

For a pixel-aligned, in-bounds crop, construct an integer `Window(col_off, row_off, width, height)`, read it with `src.read(..., window=w)`, and keep `src.window_transform(w)` with the returned array. If writing a cropped raster, set its width/height to the crop array’s columns/rows and its transform to that window transform. Rasterio windows are in pixel offsets and sizes; `window_transform` shifts the affine origin to the crop while retaining pixel vectors, including rotation/skew. This is the Q1 disposition. [Rasterio windowed reads](https://raw.githubusercontent.com/rasterio/rasterio/1.3.10/docs/topics/windowed-rw.rst) [tagged transform implementation, `windows.py` lines 83–98, 343–362](https://raw.githubusercontent.com/rasterio/rasterio/1.3.10/rasterio/windows.py)

| Brief obligation | Disposition |
|---|---|
| 1. Pixel window and transform | **Accepted:** use `Window(col_off,row_off,width,height)` and `src.window_transform(w)` for the same effective window used to read. For a simple crop, keep it integer and in bounds. If clipping or fractional offsets are required, first settle the effective window; the 1.3.10 read path crops non-boundless windows and rounds window lengths when allocating the natural output shape, so blindly transforming a different requested window can misregister the result. [`_io.pyx` lines 580–598](https://raw.githubusercontent.com/rasterio/rasterio/1.3.10/rasterio/_io.pyx) |
| 2. Smaller output array | **Accepted with a transform update:** `read(window=w, out_shape=(out_h,out_w), resampling=...)` resamples the crop. Start with `t = src.window_transform(w)` and use `t_out = t * Affine.scale(w.width/out_w, w.height/out_h)` (or the returned array’s actual dimensions). This preserves the crop’s outer extent while changing cell size. The same scale is applied in both axes even for rotated/skewed grids. [Rasterio resampling example](https://raw.githubusercontent.com/rasterio/rasterio/1.3.10/docs/topics/resampling.rst) [`_io.pyx` read path](https://raw.githubusercontent.com/rasterio/rasterio/1.3.10/rasterio/_io.pyx) |
| 3. Logical pixels vs physical I/O | A 1×1 logical window does not promise 1×1 physical I/O: Rasterio reads one or more dataset chunks/blocks; an unchunked source may require the whole dataset. Inspect `src.block_shapes` per band (and `block_windows`) on the actual file. Unknown block layout, compression, driver, cache and storage path prevent a byte-cost estimate from this brief. [Rasterio blocks and read behavior](https://raw.githubusercontent.com/rasterio/rasterio/1.3.10/docs/topics/windowed-rw.rst) |
| 4. Crop vs resampled coordinates | **Accepted:** cropping translates the origin and keeps the original pixel vectors; resampling scales the vectors so output pixels cover the same crop extent. Pixel centers therefore move to a new grid. GDAL’s pixel/line coordinates use the upper-left pixel corner as (0,0), with its center at (0.5,0.5); compare world coordinates at corners and centers, not just array dimensions. [GDAL geotransforms](https://raw.githubusercontent.com/OSGeo/gdal/v3.9.0/doc/source/tutorials/geotransforms_tut.rst) |
| 5. Categorical vs continuous | **Amended:** nearest is the documented default and preserves sampled class values, but it is not a universal aggregation rule. For categorical data, use nearest when retaining a representative source label; consider mode only when majority aggregation is the intended meaning. For continuous data, bilinear/cubic are reasonable interpolation choices; average is a candidate for downsampling when a local mean is the desired statistic. No method is universally “correct”; nodata handling and scientific meaning govern. [Rasterio resampling guidance](https://raw.githubusercontent.com/rasterio/rasterio/1.3.10/docs/topics/resampling.rst) [1.3.10 `Resampling` definitions, `enums.py` lines 48–107](https://raw.githubusercontent.com/rasterio/rasterio/1.3.10/rasterio/enums.py) |
| 6. Fixtures and uncertainty | **Unresolved inputs:** actual block layout, whether data are categorical or continuous, class labels, nodata policy, and intended target scale are unspecified. Proposed checks (not executed): (a) synthetic array with unique values and a known affine including rotation/skew; read an integer crop and compare values plus crop corner/center coordinates to the matching parent pixels; (b) read that crop to a smaller shape, assert the output transform has the same outer extent and new pixel-center locations; (c) class-ID and continuous-plane fixtures, checking nearest/mode labels versus bilinear/cubic/average behavior against the chosen semantics; (d) tiled and strip-organized GeoTIFF fixtures with aligned, misaligned and 1×1 windows, inspect each band’s `block_shapes`, and measure physical I/O only with driver/storage instrumentation if that performance claim matters. |

**Claim dispositions.** No predecessor artifacts or draft claims were supplied. In this recommendation: **accepted** — a crop needs its own window transform; **amended** — smaller `out_shape` also requires a correspondingly scaled transform; **rejected** — logical requested pixel count is a proxy for physical bytes read; **unresolved** — block cost and the right aggregation method without layout and data semantics.
