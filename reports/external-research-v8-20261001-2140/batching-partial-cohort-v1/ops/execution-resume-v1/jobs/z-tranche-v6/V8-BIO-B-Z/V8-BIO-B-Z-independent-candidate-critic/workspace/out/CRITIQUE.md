## 2. Supported corrections and counterexamples

- **C1 [CORRECTION] — "the spec permits 2–5 levels" (PROPOSAL § B1) is unsupported.** S1 bounds *dimensionality*, not level count: "The length of 'axes' must be between 2 and 5" and the layout note "the number of dimensions is variable between 2 and 5". Nothing in S1 bounds the number of `datasets` entries; the layout explicitly shows levels `0…n` with arbitrary names. Counterexample: a 0.4 file with three or six resolution levels is spec-conformant, so the prototype's two-level gate must be presented as a **product rule** (per the brief's "exactly two resolutions"), not as spec conformance — otherwise a conformant file would be visibly rejected with a wrong reason string. The gate itself stays [CHOICE]; only its attribution changes.
- **C2 [CORRECTION, minor] — vizarr release check.** Observed: `…/releases/latest` → 302 → `/releases` (200, empty index), not a literal 404. The substantive claim (no published releases) is corroborated; the proposal's HTTP detail should be restated.
- **C3 [CORRECTION, minor] — README quote force.** The actual sentence is "Support for other Zarr arrays is **supported but not as well tested**." The proposal's elision "is not as well tested" drops the source's own acknowledgment that generic Zarr *works*; preserve the full sentence so the vizarr weakness is not overstated.
- **C4 [ADDITION] — `path`-form transforms are 0.4-legal and unhandled.** S1's trafo table permits `translation`/`scale` values as `"path":str` (binary data in-container). The proposal's resolver reads list-of-floats only. Its B2 fallback ("unparseable → withhold calibration with reason") degrades safely, so this is not a failure, but a legal file would be classified "invalid metadata" rather than "supported but unreadable transform form". Add a path-form fixture or a lead; also ensure the F10 invalid-scale state and the path-form state are visibly distinct.

## 3. Witness recipe check (own values; hand reasoning; nothing executed)

- **Values:** 2048→512 is a factor 4; per the verified PR #590 formula, level-1 `scale = [4,4]`, `translation = [4/2 − 1/2, …] = [1.5, 1.5]`. By hand: Interpretation A gives level-1 pixel 0 → 0×4 + 1.5 = **1.5 µm**; Interpretation B gives **0 µm**; the aggregation argument `(0+1+2+3)/4 = 1.5` matches A. **[SRC-CHK]** the formula matches the S4 diff exactly (including `scale0 = [1.0]*ndim`).
- **Discrimination:** the example does discriminate its stated assumption — "display the declared per-level physical frame" vs "assume levels share the level-0 origin" — with a 1.5 µm/axis separation, which is precisely the #403 failure class. **[INFER] caveat:** the aggregation tie-breaker presupposes a pixel-anchor convention (level-0 pixel *k* centered at index×scale), which S1 does not itself fix; the proposal correctly presents this as an argument and marks everything UNEXECUTED. Keep that labeling in the final proposal.
- **Tolerance interaction [INFER, concrete counterexample]:** B3 precondition 3's ½-coarse-pixel tolerance equals 2 µm in F1 — *larger* than the 1.5 µm #590 centering offset. That is fine for its stated use (image-vs-label per-level transform comparison), but if the same tolerance is ever reused as a cross-level origin-continuity check, it would tolerate exactly the scale-only error the witness exposes: a scale-only level-1 origin differing from the label's translated origin by 1.5 µm would pass a 2 µm check. The final stage should state which comparison the tolerance belongs to.
