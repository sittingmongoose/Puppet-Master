1. **napari version pin vs. captured docs (`locked_data_level`).** The multiscale-level-lock behavior cited from `napari/docs@main` (`docs/howtos/layers/image.md`, captured 2026-10-03) must be confirmed present in the exact napari wheel pinned for the prototype (release v0.9.2 published 2026-09-29; release notes show active multiscale work, e.g. #9495). *Consequence:* manual level switching and test V3 depend on it; fallback is programmatic level forcing via the layer's multiscale API of the pinned version. *Next:* check the pinned wheel's changelog/source for `locked_data_level` before implementation.

2. **Cursor world-coordinate readout surface.** The proposal relies on napari composing `scale`+`translate`+`units` into world coordinates (documented in `docs/guides/units.md`), but the exact public accessor for "cursor position in world coordinates" for an embedded viewer was not pinned to a versioned locator in this stage. *Consequence:* B2's readout implementation choice (subscribe to mouse events + `world_transform` vs. reuse the status bar) is open. *Next:* resolve against the pinned napari API docs.

3. **Group-level (multiscales-level) `coordinateTransformations` handling in napari.** NGFF 0.4 allows transforms at the multiscales level, "applied after" per-dataset transforms (spec §multiscales). Whether the chosen reader/viewer path applies them automatically was not verified. *Consequence:* files using group-level transforms would misrender silently if unhandled. *Next:* implement the composition in our own interpretation layer (already planned) and add a fixture; do not rely on the viewer.

4. **ome-zarr-py release containing the PR #590 fix.** The translation-generating `generate_coordinate_transformations` is on `master` (captured 2026-10-03), but the numbered release that first ships it was not identified in this stage. *Consequence:* the "supported correction" is only effective above that release; below it, scale-only defaults reappear. *Next:* pin the release (or the commit `db3d40e…` build) in requirements and note it in the About box.

5. **Pixel-center vs. index-origin convention.** NGFF 0.4 maps data coordinates to physical coordinates but does not state whether index *i* denotes the pixel's center or edge. The fixture V1 expected value uses one convention. *Consequence:* half-pixel disagreement in physical readouts for the scientist. *Next:* explicit product decision + tooltip; keep the convention in one code path.
