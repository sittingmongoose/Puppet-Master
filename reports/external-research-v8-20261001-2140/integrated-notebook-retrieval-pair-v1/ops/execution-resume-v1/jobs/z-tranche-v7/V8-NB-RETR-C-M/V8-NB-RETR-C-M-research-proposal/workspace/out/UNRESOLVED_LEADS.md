Remaining consequential dependencies/uncertainty only (per task scope). Each lead names what is unresolved, why it is consequential, and the next verification step. None of these are resolvable from the sources already captured in this case.

1. **Upstream behavior drift in nbformat's public `validate()` default path.** On `main` (captured 2026-10-03, sha256 prefix `3db1fe48de10…`), `validate()` delegates to `_validate()` with `repair_duplicate_cell_ids=True` default, so the public default path still repairs missing/duplicate cell ids (with `MissingIDFieldWarning`/`DuplicateCellId` warnings), while the 5.5.0 changelog states the direction is fail-not-fix and PR #447 removed the opt-out kwargs. Consequential because our read-only capture pipeline depends on non-mutation. Next step: pin a specific nbformat release at implementation time and empirically re-verify which path the pinned version's `validate()` takes; the prototype design (deep-copy + `isvalid()`-style checks + mutation guard T9) is correct under either behavior.

2. **nbdime version pinning vs. captured `main` sources.** The captured diffing sources are branch `main` and post-date the latest numbered release `v4.0.4` (2026-02-10). The `threshold: 0.3` similarity default, `set_text_similarity_options`, and `compare_cell_by_ids` predicate may differ in the pinned release wheel. Consequential because §4.2/§4.3 thresholds are parameterized against these defaults. Next step: read the pinned wheel's `nbdime/diffing/generic.py` and `notebooks.py` before freezing prototype thresholds.

3. **Similarity-metric equivalence for rename inference.** git's documented "extent of changes" score with a 50% default (gitdiffcore.adoc) is a different function from the `difflib.SequenceMatcher` ratio the prototype would use; borrowing the 50% number is a labeled product choice, not an equivalence. Consequential because a systematically miscalibrated threshold would mislabel renames on long-line text files. Discriminating test T6 covers the ambiguity case, but quantitative calibration on the fixture corpus stays open until the proposed test suite actually runs (unexecuted in this stage).

Low risk, but if the exact first-shipping release matters later, verify against the `v5.11.0` tag tree.
