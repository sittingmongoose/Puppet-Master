## 3. Q2 — lane separation, identity regimes, renames/untracked/limits: verified; one fixture-design counterexample

**Notebook lanes — [SRC-VERIFIED]/[CHOICE] with a completeness gap (C4).** The five-lane model is consistent with S3/S4 as far as it goes, but the proposal's enumeration of `set_notebook_diff_targets` paths omits `/cells/*/attachments` and `/cells/*/outputs/*/metadata` (the latter is consistent with its "output metadata as its own sub-lane" statement; the former is a real nbdime lane with a dedicated differ, `diff_attachments`). The v4.5 schema allows `attachments` on raw/markdown cells. Dropping the attachments lane is a defensible prototype scope choice (the brief's N2 requires source/outputs/metadata separation, not attachments), but it is currently implicit — it should be stated as a choice/limitation, not left as if the five lanes were nbdime's full target set. Also worth stating: `set_notebook_diff_targets` defaults are all-True (`details=True`), so nothing is ignored unless the prototype actively configures it; the "deliberate skipping" lives inside the similarity predicates, not the target configuration.

- nbdime id predicate matching only when both cells have ids and they are equal — verified (S3).
- The two-regime matcher, refuse-and-expose behavior on duplicate ids, no-capture-repair stance, 0.5 similarity thresholds as tunable knobs, and unresolved-identity reporting are coherent [INF]/[CHOICE], correctly not presented as source-mandated. **Files, renames, untracked, limits (§4.3) — mostly verified; one cited correction (C1).**
- "Observed difference is primary" (hash comparison), rename-as-inference with exact-hash first and thresholded similarity second, untracked = present-but-unmanifested reported as found at comparison time, and the capture-limit unknowns are coherent [INF]/[CHOICE] and consistent with the brief's N3.
- The metric non-equivalence warning (git's "extent of changes" ≠ `difflib` ratio; 50% borrowed as a labeled number, not an equivalence) is honest and matches S11's wording ("extent of changes" algorithm).
- **C1 [SRC-CORRECTION] — the §4.3(3) ambiguity example and test T6 cannot exercise the stated path as written.** The proposal's example is "two byte-identical files in A, only one in B" with the expectation that "all candidates are listed and identity stays unresolved" (T6 likewise: "candidate pairs listed, identity unresolved"). Under the proposal's own algorithm, candidate pairings are formed between *disappeared* and *appeared* paths. In that fixture the appeared set is empty (B merely lacks one of the two identical files), so there is nothing to pair with: the report is a plain deletion of one path (trivially ambiguous which, but the contents are identical, so nothing observable hinges on it and no candidate list is produced). The ambiguity code path is unreachable with this fixture, so T6 as specified **does not discriminate** exposure-based pairing from git-style auto best-match — both behaviors produce the same output on it. Concrete counterexample that does discriminate: A = {`a.txt`, `b.txt`} byte-identical; B = {`c.txt`} with `c.txt` byte-identical to them. Then disappeared = {`a.txt`, `b.txt`}, appeared = {`c.txt`}, and both `a→c` and `b→c` are exact-content candidates: exposure must list both and leave identity unresolved, while a git-style best-match/auto-resolve would silently pick one — exactly the divergence the proposal claims to test. (Equivalently: one disappeared, two identical appeared files.) The final correction stage should fix §4.3(3)'s example and T6's fixture accordingly.
