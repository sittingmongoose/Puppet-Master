## Q1. Two compared components and the version-specific behavior that supports a minimal approach

### Component A: nbdime (jupyter/nbdime)

- **[S]** Identity/scope: "Tools for diffing and merging of Jupyter notebooks." Repository `https://github.com/jupyter/nbdime` (default branch `main`); latest release tag **v4.0.4**, `published_at` 2026-02-10T15:02:16Z (GitHub API `releases/latest`, sha256 `8bc19b50…`).
- **[S]** Version-specific behavior — cell-id support is recent and optional: changelog entries under 4.0.0rc0 and 4.0.0, "Enhancements made — Add support for using cell ID in diffing and merging [#639]" (`CHANGELOG.md` @ `main`, sha256 `1d3c90cd…`). **[I]** That id-based diffing did not exist before 4.0.0 is inferred from the addition being a changelog *enhancement*; no pre-4.0 source was captured.
- **[S]** Matching model: `nbdime/diffing/notebooks.py` @ `main` (sha256 `9f9739fe…`), `notebook_predicates["/cells"] = [compare_cell_approximate, compare_cell_moderate, compare_cell_strict, compare_cell_by_ids]` under the comment "# Predicates to compare cells in order of low-to-high precedence". Docstrings fix the multilevel iteration roles: `compare_cell_strict` — "first multilevel diff iteration"; `compare_cell_moderate` — "second multilevel diff iteration"; `compare_cell_approximate` — "third and last multilevel diff iteration". `compare_cell_by_ids` — docstring "Compare cells x,y strictly using cell IDs", comment "# Only consider equal if both have IDs and they match", body `return 'id' in x and 'id' in y and x['id'] == y['id']` — i.e. id-matching applies **only when both cells carry ids and they are equal**; otherwise the content heuristics decide. The heuristic comparators exclude identity-relevant metadata (per-function comments quoted in §1/C4).
- **[S]** Change-classification surfaces: `set_notebook_diff_targets(sources=True, outputs=True, attachments=True, metadata=True, identifier=True, details=True)` maps to distinct diff paths `/cells/*/source`, `/cells/*/outputs`, `/cells/*/attachments`, `/metadata`, `/cells/*/id`, `/cells/*/metadata`, `/cells/*/outputs/*/metadata`, with `execution_count` handled under "details" (ignore-keys on `/cells/*` and `/cells/*/outputs/*`). `/cells/*/id` is an atomic path (`atomic_paths={"/cells/*/id": True}`), so an id change is a replace, not a patch. `/cells` and `/cells/*/outputs` are diffed with `diff_sequence_multilevel`.
- **[S]** **Hard condition**: module docstring — "All diff tools here currently assumes the notebooks have already been converted to the same format version, currently v4 at time of writing. Up- and down-conversion is handled by nbformat." `diff_notebooks` docstring repeats: "The notebooks are expected in the format of nbformat's version 4." nbdime does not itself gate on `nbformat_minor`; cross-minor-version semantics are delegated away.
- **[S]** Rename precedent: `diff_attachments` comments — "2: An attachment is renamed (key change)" / "Currently, #2 is handled as two ops (an add and a remove)". Even inside a notebook-aware differ, a rename is *observed* as add+remove and *not* inferred.

### Component B: nbformat (jupyter/nbformat)

- **[S]** Identity/scope: "Reference implementation of the Jupyter Notebook format" (default branch `main`; the license field in the captured PR #282 base-repo payload is BSD-3-Clause). Latest release tag **v5.11.1**, `published_at` 2026-08-17T08:10:55Z (GitHub API `releases/latest`, sha256 `4e7c7592…`).
- **[S]** Version-conditioned cell identity: the v4.5 schema (sha256 `523e3578…`) defines `cell_id` as a string with `pattern: "^[a-zA-Z0-9-_]+$"`, `minLength: 1`, `maxLength: 64`, and **requires** `id` on every cell kind (`raw_cell`, `markdown_cell`, `code_cell` required lists all include `id`). The v4.4 schema (sha256 `dddf3bff…`) contains **no `id` property and no `cell_id` definition at all**; its cell definitions use `additionalProperties: false`, so under a strict 4.4 reading an `id` key would be invalid. Changelog (sha256 `414e10d3…`): 5.1.0 "Implemented CellIds from JEP-62"; 5.1.1 "Changes convert.upgrade to upgrade minor 4.x versions to 4.5".
- **[S]** Uniqueness is an *additional check*, not a schema property: the v4.5 schema's `metadata_name` description states uniqueness "cannot be checked by the json schema and must be established by an additional check" (stated for *names*; there is no `uniqueItems` constraint on `cells` either). In code, uniqueness is enforced by the validator: `_normalize` walks `seen_ids` and, with repair disabled, raises `ValidationError("Non-unique cell id '<id>' detected.")` (`validator.py` @ main, sha256 `3db1fe48…`); `test_non_unique_cell_ids` in `tests/test_validator.py` @ main (sha256 `1d5990ad…`) exercises exactly that and repeats the call "try again to verify that we didn't modify the content".
- **[S]** Normative validation posture — normative statement vs current mechanism (corrected per C2/C3). Normative force: nbformat CHANGELOG 5.5.0 section, verbatim at main: "`validate()` is a function that is core to the security model of Jupyter. Callers rely on it not mutating its argument or trying to fix the notebook passed to it." … "The auto-fixing arguments are therefore deprecated and will be removed in a future release; validation will fail instead of silently modifying an invalid notebook." … "Use `normalize()` explicitly when a notebook from an external source needs to be repaired before validation. It returns a normalized copy …" … "normalization is a compatibility tool, not a substitute for fixing the producer." Current mechanism: the kwargs were removed in 5.11.0 ("Remove deprecated kwargs from `validate()` function [#447]"; refactor #439 "Refactor validation to separate deprecated kwarg handling"), **but repair-on-validate is still the default behavior path** — `validate()` → `_validate(...)` with keyword-only default `repair_duplicate_cell_ids=True` → `_normalize`, whose docstring admits it "does currently mutate `nbdict`", "for historical reasons", while `validate()` uses it. Non-mutation is asserted only in `isvalid()`; `iter_validate`'s Notes still carry the aspiration in future tense: "To fix: For security reasons, this function should *never* mutate its `nbdict` argument…". `normalize()` takes a deepcopy and returns `(changes, deep-copied normalized)` — copy-in/copy-out by construction.
- **[S]** Warning-vs-error condition for missing ids: for `(version, version_minor) >= (4, 5)`, a cell without `id` triggers `MissingIDFieldWarning` ("Cell is missing an id field, this will become a hard error in future nbformat versions. You may want to use `normalize()` … (available since nbformat 5.1.4). Previous versions of nbformat are fixing this issue transparently, and will stop doing so in the future."), and repair happens only when `repair_duplicate_cell_ids` is true (`_normalize`, sha256 `3db1fe48…`). In `nbformat/warnings.py` @ main (sha256 `bcd6aa3e…`), `MissingIDFieldWarning` and `DuplicateCellId` are `FutureWarning` subclasses whose docstrings say "This will be turned into an error at later point." and "We subclass FutureWarning as we will change the behavior in the future." `test_should_warn` (parametrized over both validator backends) exercises the warning path.

### Comparison and what supports a minimal approach (N5 comparison)

| Dimension | nbdime | nbformat |
|---|---|---|
| Core competence | heuristic cell diff/merge + presentation (CLI/GUI/Lab) | authoritative per-minor-version schemas, validation, normalize/upgrade |
| Cell identity | id-first predicate (since 4.0.0) + strict/moderate/approximate content fallbacks | defines when ids must exist ((4,5) threshold), their syntax; uniqueness via validator, not schema |
| Cross-minor input | explicitly out of scope (expects same v4 version; delegates conversion to nbformat) | in scope: version detection, validation, upgrade, normalize |
| Weight | heavy: TS/GUI/merge machinery beyond this prototype | light: library suitable as a format gate |
| Read-path safety at current main | n/a (diff operates on supplied dicts) | **[S]** `reads()`/`validate()` repair ≥(4,5) notebooks in memory; only `isvalid()` guarantees non-mutation |

- **[I]** The minimal approach is *not* "pick nbdime or nbformat" but a split: **nbformat's schemas as the version/format reference with `isvalid()` (on deep copies) as the validation gate; a small purpose-built two-snapshot differ modeled on nbdime's predicate design** (id-equality highest precedence, then progressively relaxed content comparisons; metadata/execution_count excluded from identity). Per C2 the prototype parses snapshot JSON itself and never passes snapshot dicts through `nbformat.reads()`/`validate()`.
- **[I]** Justification from source conditions: nbdime's own docstrings exclude our cross-minor case (one snapshot may declare 4.4, the other 4.5), while nbformat supplies exactly the version-conditioned rules (id presence, syntax, uniqueness-as-extra-check) our matcher must branch on.
- **[P]** Concrete tradeoff accepted: reimplementing matching risks diverging from nbdime's battle-tested heuristics. Mitigation: mirror nbdime's predicate ordering, cap the heuristic stack at two levels (exact-equality, then a difflib-style ratio fallback), and — where both snapshots declare ≥ (4,5) with unique ids — treat id-equality as *authoritative* (matching `compare_cell_by_ids`), confining heuristic risk to pre-4.5 snapshots. Embedding all of nbdime to obtain one predicate function is rejected as disproportionate for an offline prototype **[P]**; re-implement-not-embed also avoids acting on nbdime's unresolved license terms (GitHub API reports `Other`/`NOASSERTION` per the critique stage's capture; not re-verified this stage — see leads).

## Q2 / N2. Notebook change observations and cell identity

### Separating source, outputs, metadata

- **[S]** A v4 **code** cell is a record with `id` (4.5+), `cell_type`, `metadata`, `source`, `outputs`, `execution_count` (v4.5 schema, `code_cell` required list and property map, `additionalProperties: false`). **`attachments` is a property of `raw_cell` and `markdown_cell` only** (both v4.4 and v4.5 schemas) — corrected per C1; nbformat CHANGELOG 4.1.0: "adding support for attachments **on markdown and raw cells**". The notebook root has `metadata`. nbdime diffs each of these through a distinct path (`notebook_differs` map) and can include/exclude each via `set_notebook_diff_targets` — evidence that per-field classification is the established granularity.
- **[P]** The prototype's per-matched-cell-pair observation record: `{cell_kind, matched_by, source_changed, outputs_changed, metadata_changed, attachments_changed (raw/markdown only), execution_count_changed, id_changed, position_moved, schema_anomaly}`. `schema_anomaly` reports condition violations such as an `attachments` key on a code cell or an id violating the 4.5 pattern. Defaults follow nbdime: `execution_count` and output/attachment *metadata* are reported but never affect identity or a "same work" judgment.
- **[S]** Output comparison precedent: `compare_output_approximate` — "# Deliberately skipping metadata and execution count here" — compares `output_type` plus kind-specific data (`stream` name/text, `error` ename/evalue/tracebacks, mime-bundle `data` for `display_data`/`execute_result`) and plays safe on unknown keys; `compare_output_strict` differs only in strictness, still "# NB! Ignoring metadata and execution count".
- **[T]** Discriminating fixture (proposed, unexecuted): two 4.5 snapshots whose only difference is (a) a one-character source edit, (b) a re-run producing different `outputs` with identical `source`, (c) `execution_count` only, (d) a `metadata.tags` change. Expected: exactly one of the four flags set per case; (c) sets only `execution_count_changed`.

### Cell identity / matching under differing version or identifier conditions

- **[S]** Conditions from nbformat: ids are *required* only at `nbformat_minor ≥ 5` (v4.5 required lists; v4.4 has no id); id syntax `^[a-zA-Z0-9-_]+$`, length 1–64; uniqueness enforced by validator logic, not the JSON Schema.
- **[S]** Conditions from nbdime: id-matching applies only when **both** cells carry ids and they are equal (`compare_cell_by_ids`); otherwise content heuristics decide alignment in multilevel iterations (strict first, moderate second, approximate "third and last"); id-changes are atomic replaces (`atomic_paths`).
- **[P]** Prototype matching algorithm, version-gated:
  1. Read each snapshot's declared `(nbformat, nbformat_minor)` from the stored bytes with a plain JSON parser; **report both declared versions** (N1). If major ≠ 4 or the file is not JSON, the notebook is marked unsupported-for-cell-analysis (file-level comparison only). A declared 4.x with missing `nbformat_minor` is unsupported for cell analysis **[S]-supported**: `test_notebook_invalid_without_min_version` @ main shows nbformat itself rejects such a notebook.
  2. If both snapshots declare ≥ (4,5): match by `id`. Duplicate ids **within a snapshot** → those cells go to an `ambiguous` bucket with the duplicate ids listed; the prototype never silently repairs ids (direct application of the nbformat #243/#282 lesson, below, and of the C2 finding that library read paths *do* repair). A same-id pair spanning the snapshots is one logical cell even if positions differ → reorder is reported as `position_moved`, not delete+add.
  3. If either side declares < 4.5 (or ids are absent/duplicated/invalid): fall back to nbdime-style ordered heuristics on `(cell_type, source)` — exact match first, then similarity — restricted to the *unmatched* residue. Every fallback-matched pair is labeled `matched_by: "content-heuristic"` and presented as provisional. If a fallback region contains cells with identical `(cell_type, source)`, the pairing within that region is reported as ambiguous rather than guessed.
  4. Cross-version pairs (e.g., 4.4 ↔ 4.5): same rules, plus the version mismatch itself is surfaced as a first-class observation. **No upgrade/downgrade is performed before comparison** **[I]**: upgrading side A to 4.5 would fabricate ids (nbformat `upgrade` targets 4.5 per changelog 5.1.1), destroying exactly the identity information the comparison is supposed to expose. If the user explicitly requests a normalized view, run nbformat `normalize()` on a **deep copy** only and label the output as derived (basis: `normalize()` deep-copies its input and returns the copy, sha256 `3db1fe48…`; normative posture: 5.5.0 changelog, quoted above).
- **[T]** Discriminating fixtures (proposed, unexecuted; these recipes are the self-derived witnesses for the matching rules): (a) 4.4 ↔ 4.4 identical sources, cells reordered, **pairwise-distinct `(cell_type, source)`** → all pairs `matched_by: content-heuristic` (exact), every cell `position_moved`, zero content changes (corrected per critique §6); (a′) same but with one duplicated content pair → ambiguous-pairing report instead of a guessed pairing; (b) 4.5 ↔ 4.5 with one duplicated id → pair reported ambiguous, remainder still id-matched; (c) 4.5 ↔ 4.5 same id, source edited, position swapped → `id` match + `source_changed` + `position_moved`; (d) id present with invalid characters under a declared 4.5 → cell flagged `schema_anomaly` (4.5 `cell_id` pattern; cf. `test_invalid_cell_id` @ main) and excluded from id-matching; (e) code cell carrying an `attachments` key under declared ≥4.5 → `schema_anomaly`, per C1.

### File renames, untracked files, limits of captured states (N3)

- **[S]** Observed-vs-inferred precedent: nbdime records an attachment rename as an add + a remove op (`diff_attachments` comments) — rename is not a primitive the differ emits. Git-style similarity detection is *not* cited here because no primary source for it was captured in this case; the design below rests on the nbdime precedent plus the product rule.
- **[P]** Each snapshot stores a manifest: `{path, sha256, bytes, tracked_flag}` for every regular file captured, plus the notebook's declared `(nbformat, nbformat_minor)`. Comparison emits, per path: `unchanged`, `edited` (same path, different hash), `deleted` (path in A only), `added` (path in B only).
- **[P]** Rename is an **inference layer**, never an observed op: a delete of `p` + add of `q` is labeled `rename-inferred (exact)` iff `sha256(p) == sha256(q)`; otherwise it stays delete+add with an optional similarity annotation, and the UI exposes the raw add/delete facts alongside any inference. The equivalence rule (exact content equality) is a **product choice**; with only two text files, false-pairing risk is small but the label remains explicitly "inferred".
- **[P]** Untracked file: the capture records the repository's tracked/untracked status *as declared by repository metadata at capture time* and snapshots the content either way. A file untracked in both snapshots is compared like any file but badged `untracked`; tracked↔untracked transitions are reported as observed status changes. A file *not present in a snapshot's manifest* is **unknown** for that state — it cannot be compared and (N4) cannot be recovered.
- **[P]** Limits made explicit in the report: unsaved editor buffers are out of scope (brief); capture data absent for a path ⇒ content unknown, never guessed; similarity annotations are heuristics, not facts; outputs reflect whatever was saved — no re-execution ever occurs.

## Q3 / N5 (part 2). Real issue → fix → test chain

**Failure (issue).** nbformat issue **#243 "Merciful validation"** (GitHub API `issues/243`, sha256 `882be9f7…`): created 2022-01-20T19:21:15Z, **state open**, related to #235. Body, verbatim: "Right now, if you have a validation error for non-unique cells, you will get a validation error informing you that a cell had a duplicate cell_id, and also the notebook that you passed in will be modified with *only* the first instance of a non-unique cell." The concrete harm is documented in PR #282's description: notebook trust signatures were computed before `validate()`, which then mutated the notebook — "the signature is computed before validate, and validate mutate the notebook, leading to the signature not matching" — a saved, trusted notebook re-opened as untrusted.

**Fix.** PR **#282 "Start separating normalisation from validation logic"** (GitHub API `pulls/282`, sha256 `e32bac08…`): created 2022-06-08T07:46:20Z, merged 2022-08-16T08:17:46Z, milestone **5.5.0**, merge commit `1b5c8393c28284d792bfe34c4068e0817bb18cc1`, head `fc45fed51440b6f2d38578171777a83adafed2f5`, `changed_files` 7, `additions` 630, `deletions` 102. The PR body states the principle: "really `validate()` _should not mutate the notebook ever_. Validate is in part used for security." Verified from the PR-era code and surviving structure: new `nbformat/warnings.py` (`MissingIDFieldWarning`, `DuplicateCellId`, both `FutureWarning` subclasses, sha256 `bcd6aa3e…`); `_normalize` gated on `(version, version_minor) >= (4, 5)` — missing id ⇒ warning + repair only if asked; duplicate id ⇒ `ValidationError` when repair is disabled; `isvalid()` deep-copies its input and asserts non-mutation in a `finally` block; `normalize()` copy-in/copy-out. Released per CHANGELOG 5.5.0 (sha256 `414e10d3…`), quoted under Q1. **C2-attributed precision:** the fix landed non-mutation in `isvalid()`/`normalize()` and the then-read path, while `_validate`'s pre-existing positional repair default became the keyword-only default `True` — so plain `validate()` (and therefore today's `nbformat.reads()`) still repairs ≥(4,5) notebooks in memory; the 5.11.0 kwargs removal (#447) removed the knobs without changing that default.

**Scoped engineering lesson.** **[I]** Observation/validation code over external inputs must (1) never mutate its input — and, per C2, must not *assume* a library function is non-mutating: at current nbformat main only `isvalid()` guarantees it, while `validate()`/`reads()` repair in memory; separate read-only validation from an explicit, labeled normalization step on a copy; (2) version-gate every identity assumption (the (4,5) threshold exists precisely because id semantics changed); (3) treat ambiguous identifiers (duplicates) as reportable state, not something to repair silently; (4) make non-mutation itself a tested property (deep-copy equality, run-twice idempotence), because mutation bugs surface as *distant* failures (trust/signature mismatch), not at the mutation site.

**Adoption in the prototype.** **[P]** The comparison engine runs on frozen snapshot bytes parsed with the prototype's own JSON parser; every read is pure. nbformat is used, pinned (currently v5.11.1), only via `isvalid()` on deep copies (or not at all beyond schema reference); `nbformat.reads()`/`validate()` are never applied to snapshot data; `normalize()` may run only on a deep copy, only on explicit user action, and its output is labeled derived. Duplicate ids and missing ids are findings, not defects to fix.

## N1. Capture/input contract and read-only comparison

- **[P]** Contract per snapshot: notebook file bytes (JSON object; the snapshot records the **declared** `nbformat` and `nbformat_minor` as read from the bytes); two ordinary text files with `{path, sha256, bytes}`; manifest including the repository's declared tracked/untracked flag per path; capture timestamp. Snapshots are immutable once taken.
- **[P]** Unsupported inputs are detected and reported, not crashed on: non-JSON notebook, `nbformat` major ≠ 4, missing `nbformat_minor`, undeclared cells array. Notebook *cell-level* analysis is skipped for unsupported notebooks; file-level comparison continues. (Cell-level conditions that follow from the version — ids present/absent/required — are handled per Q2.)
- **[C]** Corrected rule for absent capture data (grounding adjusted per C2): comparison reports `unknown` for any dimension without captured bytes; the prototype never substitutes defaults and never repairs inputs during comparison. Grounding: the 5.5.0 changelog normative statement (callers rely on `validate()` not mutating or fixing its argument) **plus the verified current mechanism** — repair-on-validate is still the default path (`_validate` default `repair_duplicate_cell_ids=True`; `reads()` calls plain `validate()`), so the only non-mutating library entry is `isvalid()`, and the safest posture is self-parsing. Unsaved changes are unknowable by construction (offline saved-state tool; unsaved buffers excluded by the brief).
- **[I]** Comparison itself is a pure function over the two manifests + bytes: same inputs ⇒ same report; no writes anywhere under the original workspace or snapshot store (enforced by the recovery design in N4, which writes only under a fresh destination).

## N4. Recovery into a new destination

- **[P]** Recovery takes an **explicitly selected** snapshot and a destination path, and copies exactly the snapshot's captured files (bytes verified against stored sha256 before write). The original workspace and both snapshots are never written, reset, checked out over, or merged into (brief requirement; matches the read-only posture above).
- **[P]** Refusal/error states, each with a distinct message: (1) destination exists and is not an empty directory → refuse before any write; (2) a manifest entry whose stored bytes are missing or hash-mismatched → integrity error, abort before completing (partial-copy policy **[P]**: write to a temporary directory inside the destination parent, then atomic-rename into place, so a failed recovery leaves no partial destination); (3) destination name collides with a required subdirectory layout → refuse; (4) uncaptured content (file absent from the selected snapshot) is reported as *not recoverable* — the tool never promises it.
- **[P]** Untracked files: recovered iff present in the selected snapshot, badged `untracked` in the recovery summary. Renames: recovered under the **snapshot's own path names** — recovery reproduces the captured state, not the inferred rename interpretation (inference is a reporting-layer concept only; this keeps recovery byte-faithful).
