# UNRESOLVED LEADS — V8-BIO-COND-C-Z research proposal

Only consequential dependencies/uncertainties are listed. Each names what is unresolved, why it matters (which obligation), and the concrete next probe. None blocks the proposal; all would be resolved by execution-stage probes, not by more desk research.

1. **Reader boundary: what ome-zarr-py 0.19.2 actually exposes for per-level transforms** (affects B2, B5-2). PyPI metadata and issue history were captured, but this stage did not inspect the 0.19.2 source. Since PR #582 (merged 2026-07-01) the reader normalizes legacy 0.1–0.3 metadata to an internal 0.6 model; whether a 0.4 store's per-level `coordinateTransformations` — and any multiscales-level transforms — survive that normalization unchanged into the widget-visible metadata is unverified. Probe: load fixture F1 with `ome-zarr==0.19.2`, dump the parsed multiscale metadata, compare with the on-disk `.zattrs` (execution receipt required).
2. **Multiscales-level `coordinateTransformations` support in the chosen stack** (affects B2/F8). Ecosystem evidence says support is incomplete: ome-zarr-py #172 open since 2022-03-02 (writer side), vizarr #261 reads `datasets[0]` only. Our proposal implements level-level transforms reader-side as a product choice; if the pinned napari/ome-zarr pair already handles them, the F8 fixture may pass for the wrong reason (double application). Probe: F8 plus a negative control where our layer is disabled.
3. **Negative/axis-flip scales** (affects B2 contract only if producers write them). Observed upstream divergence: vizarr #297 (negative scale not rendered flipped; closed without captured fix). Napari's behavior with negative scale entries is unverified in this stage. NGFF 0.4 does not explicitly forbid negative scale values. Probe: extend F1 with a negative x-scale and assert the signed readout.
4. **Nearest-neighbor sampling when label and image scales differ** (affects B3/V-2). The upstream test added in napari PR #6596 covers a uniform-scale 3D case; no captured evidence covers categorical sampling under *differing* label/image per-level scales, which is exactly our V-2 case. The proposed fix (enforce sampling at node construction, port the exact-color test to 2D and to mismatched scales) is designed but UNEXECUTED.
5. **Multiple `multiscales` entries in one group** (affects B1 contract message only). §3.4 permits several named multiscale entries; this prototype deliberately reads `multiscales[0]` and surfaces a notice. Whether real-world single-dataset inputs ever carry more than one entry is unexamined; if the execution stage finds them, the refusal message should list entry names (spec: user chooses by name, first is fallback — informative example text).

Not leads (resolved in PROPOSAL.md with locators): mandatory per-level scale (§3.4), optional translation and its required order (§3.4), axis-name non-normativity (§3.1), the image/label dataset-count MUST and absence of any stronger alignment guarantee (§3.7/§2.1), the napari issue→fix→test chain (§3), and component versions/behaviors (§1, §9).
