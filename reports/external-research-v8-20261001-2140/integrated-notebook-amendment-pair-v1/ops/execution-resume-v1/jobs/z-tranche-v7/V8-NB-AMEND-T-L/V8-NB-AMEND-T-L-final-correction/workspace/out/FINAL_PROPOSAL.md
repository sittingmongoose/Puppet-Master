## 2. Q1 — Which two existing components offer useful precedents, and what version-specific behavior supports a minimal approach?

**Component 1: `jupyter/nbdime` v4.0.4 (notebook-aware structural diffing).**
- nbdime computes diffs over nbformat dicts with a *multilevel sequence diff* for `/cells`: `notebook_predicates["/cells"]` is an ordered list of comparison predicates "in order of low-to-high precedence": `[compare_cell_approximate, compare_cell_moderate, compare_cell_strict, compare_cell_by_ids]` [SRC-1]. The multilevel engine consumes this ordered predicate list (`diff_sequence_multilevel` → `compute_snakes_multilevel(a, b, compares)`) [SRC-2]. **[CORRECTION, critique note 5 — hedge shrunk]** The v4.0.4 docstrings state the iteration order directly: `compare_cell_strict` is used "in the **first** multilevel diff iteration", `compare_cell_moderate` "in the **second**", `compare_cell_approximate` "in the **third and last**" [SRC-1]; PR #639's body corroborates ("in the first comparison pass (strict) the existing cells that all had IDs are first matched to each other, and only in the next passes are the cells that gained IDs in the current change compared with their old ID-less versions") [C2]. Combined with the "low-to-high precedence" list order, this supports the highest-precedence-first reading — including `compare_cell_by_ids` running first. Only the internal mechanics of `compute_snakes_multilevel` (`snakes.py`, uncaptured) remain unverified: pass-order statements here are docstring/PR-description-level, not code-level (lead 1).
- Version-specific behavior that matters: since PR #639 (merged 2023-11-01T12:17:51Z, "Fixes #553") [C2], `compare_cell_by_ids(x, y)` — docstring "Compare cells x,y strictly using cell IDs", body `'id' in x and 'id' in y and x['id'] == y['id']` — is the **highest-precedence** `/cells` predicate [SRC-1, C2]. The `/cells/*/id` path is declared **atomic** (`atomic_paths={"/cells/*/id": True}`), so a changed id is a single replace op, never an inner patch [SRC-1]. `set_notebook_diff_targets(sources=True, outputs=True, attachments=True, metadata=True, identifier=True, details=True)` exposes per-field inclusion/ignoring, including `/cells/*/id`, `/metadata`, `/cells/*/outputs`, and `execution_count` as "details" [SRC-1].
- nbdime's own boundary condition: "All diff tools here currently assumes the notebooks have already been converted to the same format version, currently v4 at time of writing. Up- and down-conversion is handled by nbformat." [SRC-1, module docstring]. So nbdime itself treats declared version as an input precondition, not something the differ verifies.
- Shipped validation style: `nbdime/tests/test_notebook_diff.py` at v4.0.4 asserts diff/patch roundtrips, e.g. `patch_notebook(a, diff_notebooks(a, b)) == nbformat.from_dict(b)` over "any pair of notebooks in the test suite" (`test_diff_and_patch_notebooks(any_nb_pair)`) [SRC-3].

**Component 2: git's rename/copy detection (diffcore), docs at v2.43.0 (file-level precedent).**
- `-M[<n>]`/`--find-renames[=<n>]`: "If `n` is specified, it is a threshold on the similarity index (i.e. amount of addition/deletions compared to the file's size). For example, `-M90%` means Git should consider a delete/add pair to be a rename if **more than** 90% of the file hasn't changed." Without a `%` sign the number reads as a fraction with a decimal point before it (`-M5` = 0.5 = `-M50%`). "To limit detection to exact renames, use `-M100%`. **The default similarity index is 50%.**" [SRC-10] — note the strict "more than": the boundary is *excluded* under git's documented rule; see §3.3 for how this prototype states its own boundary.
- Rename/copy detection is a *generated view*, not stored data: `--diff-filter` notes "copied and renamed entries cannot appear if detection for those types is disabled" [SRC-10]. Status letters `A|C|D|M|R|T|U|X|B` are the reporting vocabulary [SRC-10].
- Cost/limits are explicit: the exhaustive fallback comparing "all remaining unpaired destinations to all relevant sources" is **O(N²)** and is bounded by `-l<num>` (defaults to `diff.renameLimit`; "a value of 0 is treated as unlimited") [SRC-10]. `-B` interplay: with `-M`, a totally-rewritten file can also be a rename source, with `n` "(defaults to 50%)" and `m` "(defaults to 60%)" [SRC-10]. `--no-renames` turns detection off "even when the configuration file gives the default to do so" [SRC-10] — this capture does not itself state the on-by-default value, so no claim is made about it (lead 4).
- `--[no-]rename-empty`: "Whether to use empty blobs as rename source" [SRC-10] — cited as evidence that even exact-content edge cases (empty files) are explicit policy, which §3.3's formula mirrors.

**Substrate: `jupyter/nbformat` v5.11.1 (format + validation semantics).** See §3 and §4 for the v4.5 cell-id constraints and the repair-by-default semantics; first-listed tag v5.11.1 as of 2026-10-03 [SRC-11].

**Why this supports a minimal approach** [INFER]: nbdime demonstrates that a small, ordered predicate ladder over the notebook's JSON structure — not a line-diff of serialized JSON — is sufficient to separate source/output/metadata/identity changes, and its approximate heuristics show where such ladders can silently misalign (§3.1). git shows the file-level vocabulary: report renames as a threshold-based *inference* over delete/add pairs, with an exact-content fast path, a bounded candidate set, and an explicitly documented boundary rule. Both ideas are small enough to reimplement locally (~300–500 lines) for a two-snapshot, one-notebook prototype; neither project needs to be imported wholesale [CHOICE].

## 3. Q2 — Separating source/output/metadata changes; cell identity when version/identifier conditions differ; files: renames, untracked, capture limits

### 3.1 Notebook change model (per-field lattice)

Observe each cell as fields that mirror nbdime's diff paths and ignore-switches [SRC-1]: `source`, `outputs` (code cells; per output: `output_type`, `name`/`text`, `ename`/`evalue`/`traceback`, `data` mimebundle, output `metadata`), `execution_count`, cell `metadata`, `id`, `attachments`. Notebook root `metadata` is a separate field. **[INFER]** nbdime's own comparators deliberately ignore `metadata` and `execution_count` when deciding *cell equality* ("NB! Ignoring metadata and execution count" in `compare_cell_moderate`/`compare_cell_strict`; `compare_cell_approximate` also ignores outputs — "NB! Ignoring metadata, execution_count, outputs") [SRC-1] — that is correct for alignment but wrong if silent; this prototype adopts the *separation* but every ignored field still produces its own observation entry. **[CHOICE]** Rule: "no change" is exact equality only; similarity is used exclusively for *alignment suggestions* and is always labeled with its pass and score in the report.

**[INFER]** A specific nbdime hazard supports the exact-equality rule. `compare_text_approximate` at v4.0.4: (i) first, a fast cutoff `if bool(x) != bool(y): return False` — exactly-one-side-empty pairs return `False` **without comparison** (**[CORRECTION, critique note 4]** this exception was omitted from the frozen proposal; verified in `bc9c5c5ad149…`); (ii) then, if both strings are shorter than `shortlen = 10`, it returns `True` *without comparing them* ("Allow aligning short strings without comparison"); (iii) otherwise it applies a 0.7 similarity threshold. Even `compare_text_strict` accepts ≥0.95 similarity as "strict" [SRC-1]. A reporting tool reusing these heuristics could under-report edits in tiny cells. nbdime can afford this because it patches rather than reports; a comparison prototype cannot.

### 3.2 Cell identity and matching ladder (absent / duplicate ids; reordering)

Normative identity conditions first:
- nbformat **4.5+** schema requires `id` on every cell (raw/markdown/code `required` arrays include `"id"`), with `/definitions/cell_id`: `pattern: "^[a-zA-Z0-9-_]+$"`, `minLength: 1`, `maxLength: 64`; root `nbformat` is fixed to major 4 (min 4/max 4) and the 4.5 schema sets `nbformat_minor` minimum 5 [SRC-7].
- JEP 62: the id is a **unique cell identifier within the notebook** ("the JEP proposes a unique cell identifier"); "Uniqueness across notebooks is not a goal"; the id "stays the same once created" (Q6: "Correct. It stays the same once created.") even when content changes; splitting a cell gives one part a new id; paste must regenerate on collision; older formats are auto-filled (e.g. `uuid.uuid4().hex[:8]`); and — a direct consequence the JEP names — "Notebooks with the same source code can be generated with different cell ids, meaning they are not byte equal" [SRC-9].
- Uniqueness is **not** enforced by the JSON schema itself: the schema pattern is per-instance, and nbformat's own `metadata_name` description notes the analogous limitation — "This criterion cannot be checked by the json schema and must be established by an additional check" [SRC-7]. In code, the check lives in `nbformat/validator.py::_normalize` [SRC-8].
- nbformat's validator **repairs by default**, and the public API offers no non-repairing validate: **[CORRECTION, critique note 3 — API precision]** at v5.11.1, public `validate()` has **no** `repair_duplicate_cell_ids` parameter and always reaches `_validate(...)` whose keyword-only `repair_duplicate_cell_ids` defaults to `True` (`_validate`'s docstring: "the public `validate` always uses the defaults"); public `normalize()` likewise calls `_normalize(..., True, ...)` (repair on) and returns a modified deep copy. A missing id (declared ≥ 4.5) triggers `MissingIDFieldWarning` + `generate_corpus_id()`; a duplicate id is *replaced* with a `DuplicateCellId` warning "Non-unique cell id … detected. Corrected to …". Repair-disabled behavior exists only in private `_validate(...)` and inside `isvalid()`, which hardcodes `repair_duplicate_cell_ids=False`, suppresses `MissingIDFieldWarning`, deep-copies the input, asserts non-mutation, and returns a bare boolean — its docstring points to `validate()` "to see the individual errors", which repairs [SRC-8].

**No-repair observation path [CORRECTION, critique note 3 — re-specified]:** a comparison tool must observe an *unmodified* representation of the captured notebook. The prototype: (i) **primary path** — parses the raw dict and reimplements the two identity checks directly on it (missing id when declared (major, minor) ≥ (4, 5); duplicate ids via a seen-ids scan), mirroring `_normalize`'s check semantics at v5.11.1 [SRC-8] and producing detailed diagnostics without any repair; (ii) optionally calls `nbformat.isvalid(deepcopy(nb))` as a secondary boolean cross-check, with its limits stated (no diagnostics, `MissingIDFieldWarning` suppressed, input asserted unmutated); (iii) **never** calls public `validate()` or `normalize()` on an observation copy, because both repair by default [SRC-8]. F-series no-repair checks (F5) assert against path (i).

Prototype matching ladder for cells of two snapshots A and B **[CHOICE, modeled on S1/C2]**, each match recorded with the pass that produced it. Matching is **one-to-one per pass**: if a candidate would pair an already-matched cell, or more than one candidate competes for the same cell at the same pass, the competing candidates are reported as **unresolved-identity candidates** and none is auto-applied.

1. **Pass P1 — id match** (nbdime's `compare_cell_by_ids` semantics: equal only if both have ids and they match [SRC-1, C2]): equal ids ⇒ same cell. Condition: this pass applies only to id values that are **unique within each state** (the JEP's uniqueness invariant [SRC-9]; duplicates verified by our own check per S8 semantics). If either state has duplicate ids, those ids are excluded from P1 entirely.
2. **Pass P2 — exact source match** **[CORRECTION, A1 — replaces the frozen P2]**: `cell_type` equal and `source` exactly equal. `outputs`, cell `metadata`, `execution_count`, and `id` are deliberately **not compared at this pass**; any differences in those fields are recorded as per-field change entries on the matched pair. Every cell_type-equal, source-identical pair matches at P2. *(Frozen text required "equal outputs list content" for code cells, which pushed source-identical/outputs-differing pairs down to P3 and mislabeled an *observed* equality as an *inferred* alignment; `compare_cell_strict` includes output comparison because nbdime patches rather than reports [SRC-1] — a precondition a reporting tool must not inherit.)*
3. **Pass P3 — near-match suggestion**: `cell_type` equal, source **not** exactly equal (else P2 already matched), and source similarity ≥ 0.95 (the "strict" bar nbdime uses [SRC-1]; similarity computed by the pinned §3.3 formula over the cell `source` lines). P3 candidates are **reported as inferred alignments**, never silently merged.

Derived observations: cells matched by P1 with changed position ⇒ **reorder**; matched cells differing in `source`/`outputs`/`metadata`/`execution_count` ⇒ per-field change entries (under corrected P2, a P2-matched pair can legitimately carry outputs/metadata/execution_count change entries); a cell whose id changed while P2/P3 content matches ⇒ report "content-matched pair with **id change**" (justified: ids are stable once created [SRC-9], so an id change is itself an observation); unmatched ⇒ add/remove.

Version/identifier conditions, preserved:
- Declared `nbformat_minor` < 5 in a snapshot: ids may be legitimately absent [SRC-7/S9]; matching falls through to P2/P3 for those cells, and the report states that identity was unavailable.
- Declared ≥ 5 but an id is absent or malformed: schema/validator violation — reported from the *unrepaired* dict via the primary observation path [SRC-7, SRC-8]; the cell still flows through P2/P3 (nbdime's rule that a cell without an ID is never id-equal to a cell with an ID [C2, SRC-1] is exactly the behavior needed here).
- Duplicate ids in a state: never silently repaired (contrast nbformat `validate()`'s default repair [SRC-8]); the duplicated ids are excluded from P1 and any P2/P3 ambiguity is reported as **unresolved identity** rather than a forced pairing.

### 3.3 Files: edits, rename, untracked

- Manifest model: each snapshot carries `manifest: {path → {sha256, bytes, tracked?}}` (the `tracked` key is our optional capture-contract extension; see §6 step 1). Per path: present-in-both + same hash ⇒ unchanged; different hash ⇒ **edited**; only-in-A ⇒ **removed**; only-in-B ⇒ **added**. [CHOICE]
- **Similarity metric (pinned — [CORRECTION, critique note 2]).** For two texts, let `L1`, `L2` be their line sequences (`str.splitlines()`; notebook/cell `source` lists are joined with `""` before splitting). Similarity = `difflib.SequenceMatcher(None, L1, L2, autojunk=False).ratio()` — i.e. `2·M/(len(L1)+len(L2))` where M is the total size of matched blocks; `autojunk=False` keeps small-file behavior deterministic. Edge cases: both empty ⇒ 1.0 (exact-hash equality short-circuits to 100% before the ratio runs); exactly one empty ⇒ 0.0. **[CHOICE]** — no similarity arithmetic has been executed in any stage of this case; the metric is specified so that F7 outcomes are computable once executed [TEST-P].
- **Rename as inference, never an observation**: following git's model [SRC-10], a (removed r, added a) pair is reported as a *rename candidate* only when similarity(r, a) ≥ τ, with τ default **50%** (git's default similarity index) and τ = 100% shown as "exact" (hash-equal); otherwise the pair stays delete + add. **Boundary disclosure [CORRECTION, critique note 1]:** git's documented rule is strict — "`-M90%` means Git should consider a delete/add pair to be a rename if **more than** 90% of the file hasn't changed" [SRC-10] — so at exactly 50% git would report delete+add, while this prototype's "≥ τ" rule reports a rename candidate. Keeping "≥" is a deliberate, labeled **[CHOICE]** (boundary-inclusive suggestion is the more helpful default for a two-file recovery tool, and every report shows the score and rule version); it is stated here so the operator difference from the cited convention is explicit, not silent. **[INFER]** git computes renames at diff time from A/D pairs (renames "cannot appear if detection … is disabled" [SRC-10]); this prototype copies that reporting convention but **not** git's internal similarity algorithm — our metric is the pinned, documented line ratio above, and the report shows the score and rule version, so the inference stays inspectable and revisable. The JEP's byte-inequality point for identical notebook sources [SRC-9] is the same lesson one level down: content-identity and document-identity are different predicates.
- **Untracked**: tracking status is *not* observable from two saved states alone; it must come from the capture. **[CHOICE]** If the manifest records `tracked: false`, the file is reported "untracked at capture time" and is otherwise an ordinary captured file; if the manifest does not record a `tracked` key, the report says "not present in baseline manifest; tracking status unknown". This preserves the observed-vs-inferred separation instead of guessing.
- Naming: report letters follow git's `--diff-filter` vocabulary (`M`, `A`, `D`, `R` with similarity, plus our `U?` unknown-tracking marker) for familiarity [SRC-10, CHOICE].

### 3.4 Limits of the captured states (what comparison cannot know)

- Only saved states exist in the model: unsaved editor buffers are outside every snapshot, so any change that was never saved is unknowable, and the report must say so rather than infer from file mtimes. [CHOICE, from brief]
- If a manifest entry or notebook bytes are missing from a snapshot, comparisons over that content are *unknown*, not "empty". Declared version vs actual content mismatches (e.g. declared 4.5 with missing ids) are reported as validation observations, never auto-corrected (§3.2). [SRC-7/8 grounding]
- Cross-version snapshots: nbdime itself assumes both notebooks are already in the same format version and delegates conversion to nbformat [SRC-1]. **[CHOICE]** This prototype does **not** up/down-convert (originals and captures are read-only; recovery must return captured bytes). Cross-minor comparisons are flagged "declared versions differ"; structural matching still runs, with per-cell identity conditions applied per state as in §3.2.

## 6. Component comparison, recommendation, and revised plan (N5)

**Comparison of the two components** (independently discovered, §2):

| Dimension | nbdime v4.0.4 | git diffcore rename detection (docs v2.43.0) |
|---|---|---|
| Level | notebook JSON structure (cells, outputs, metadata, ids) | file/blob level (paths, contents) |
| Identity model | ordered predicate ladder; id-equality at highest precedence, exact→approximate content below; pass order documented at docstring level (§2) [SRC-1, C2] | none at file level; identity is a similarity *inference* over delete/add pairs with a strict documented boundary [SRC-10] |
| Version conditions | assumes both inputs already same format version; conversion delegated to nbformat [SRC-1] | no format conditions; documented O(N²) fallback bounded by `-l`/`diff.renameLimit` [SRC-10] |
| Boundedness | per-notebook, small n; approximate heuristics are fast but report-hazardous (§3.1) | exact-content fast path + threshold; candidate-set cap [SRC-10] |
| Gap for this prototype | heavyweight CLI/web surface; heuristic equality unsuitable as a report predicate as-is | no notebook structure; no id concept |
