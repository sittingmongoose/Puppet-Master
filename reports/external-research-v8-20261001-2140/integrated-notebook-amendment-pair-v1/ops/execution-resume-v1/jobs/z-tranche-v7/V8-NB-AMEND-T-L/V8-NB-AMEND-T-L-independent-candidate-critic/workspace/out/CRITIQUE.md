## 3. Warranted amendments (three, highest-consequence first)

### A1 — Fix the P2 pass definition: source-identical/outputs-differing pairs are mislabeled as "inferred" alignments (N2, Q2)

- **Affected passages:** `PROPOSAL.md` §3.2, Pass P2 (line 72): "**Pass P2 — exact content match**: `cell_type` equal and `source` exactly equal (and, for code cells, equal outputs list content)." together with §3.1's rule (line 57): "similarity is used exclusively for *alignment suggestions*" and N2's F6 expectation (line 118): "F6 (outputs-only change and execution_count-only change produce exactly the field-specific entries)".
- **Defect [INFER from the proposal's own rules]:** For code cells without usable P1 matches (absent/malformed ids, or ids excluded because duplicated — exactly the states N2 targets), a pair with byte-identical `source` and differing `outputs` fails P2 (outputs clause), then matches P3 (similarity 1.0 ≥ 0.95) and is therefore reported as a "near-match suggestion … never silently merged" / "inferred alignment". That is the wrong normative force: the source equality is *observed*, not inferred; no similarity suggestion is needed; and F6's own expectation of "exactly the field-specific entries" is violated by the extra, wrong provenance class. The proposal's fixture F6 therefore does not discriminate its stated assumption as written.
- **Concrete replacement:** Redefine P2 as: "cell_type equal and `source` exactly equal — outputs, metadata, `execution_count`, and `id` are deliberately not compared at this pass; any differences in those fields are recorded as per-field change entries on the matched pair. (Every cell_type-equal, source-identical pair matches at P2.)" This keeps the nbdime-faithful *field separation* while moving outputs from a match precondition to a post-match observation, matching §3.1's "every ignored field still produces its own observation entry".
- **Support:** the proposal's own §3.1 rule and P3 definition (internal consistency); contrast `compare_cell_strict` @ `notebooks.py` v4.0.4 (capture `bc9c5c5ad149…`), which includes strict output comparison because nbdime *patches* rather than *reports* — the mislabel hazard is specific to a reporting tool. [SRC] facts above; the change itself is [CORRECTION]/[CHOICE].
- **Discriminating check [TEST-P]:** extend F6 with an id-less code-cell variant: identical source, outputs differ ⇒ expected exactly one P2 match plus exactly one outputs change entry; under the current text the same fixture yields a P3 "inferred alignment" provenance, which is the failure signal.

### A2 — N4 recovery: add case-collision and path-escape refusals before any write

- **Affected passage:** `PROPOSAL.md` §5 N4 (line 125): "Name collisions cannot arise *within* one snapshot (the manifest is keyed by path) and recovery never merges anything into the original workspace …"
- **Defect [INFER]:** The no-collision inference holds only for exact-string, case-sensitive path comparison on the destination filesystem — an assumption the proposal never states. Counterexample: a snapshot legally capturing both `README.txt` and `readme.txt` (distinct keys) written to a default-formatted macOS (APFS case-insensitive) or Windows (NTFS) destination overwrites or errors with no defined behavior. Relatedly, nothing in §N4 rejects manifest paths containing `..` components or absolute paths, which escape the destination directory. Brief N4 explicitly requires handling of "name collisions"; the current spec covers only a subset.
- **Concrete replacement (add to §N4):** "Before any write, recovery validates the selected manifest: (a) every destination path is relative, normalized, and contained within the destination root — otherwise refuse with the offending entries; (b) no two entries collide under the destination filesystem's name comparison, with case-insensitive collision detection mandatory — otherwise refuse before any write with the collision list. Where the destination filesystem cannot be interrogated, assume case-insensitive." Existing fail-closed and audit-log behavior is unchanged.
- **Support:** [INFER]/[CHOICE] from filesystem semantics; no upstream source is implicated or contradicted; consistent with the proposal's own fail-closed defaults and the brief's N4 wording (`inputs/BRIEF.md` line 18).
- **Discriminating check [TEST-P]:** new fixture F8g — selected snapshot manifest contains `README.txt`, `readme.txt`, and `sub/../x.txt` ⇒ refusal with zero writes, listing both the case-collision pair and the escaping path; current text passes this fixture silently (partial/overwriting copy), which is the failure signal.

## 4. Additional consequential notes and unresolved obligations (explicit, not defect-filling)

1. **τ boundary semantics differ from the cited git convention [SRC/CHOICE].** The proposal sets the rename threshold as "similarity ≥ τ, τ default 50% (git's default similarity index)" and F7b expects `≥50% ⇒ R` (lines 85, 122). git's doc defines the rule *strictly*: `-M90%` means "a rename if **more than** 90% of the file hasn't changed" (`diff-options.txt@v2.43.0`, capture `c7b3566f63b7…`). A pair at exactly 50% is `R` under the proposal and not-a-rename under git's rule. The proposal may choose ≥ (it is a [CHOICE]), but §3.3 presents τ as git's convention while silently switching the comparison operator; the corrected proposal should state the boundary explicitly and add a F7 fixture at exactly-50% similarity.
2. **Rename similarity formula unspecified (sharpens lead 5).** §3.3 promises "a documented, simple line-based ratio" but never names it, so `R (inferred, score)` values and F7a–c outcomes are unreproducible until specified (e.g., difflib line ratio vs. symmetric line-set overlap). The correction stage should pin the formula; no similarity arithmetic has been executed in either stage.
3. **nbformat public-API precision for the no-repair observation path [SRC].** At v5.11.1 (`validator.py`, capture `3db1fe48de10…`), public `validate()` has **no** `repair_duplicate_cell_ids` parameter — it always reaches `_validate(..., repair_duplicate_cell_ids=True)`. Repair-disabled behavior exists only on private `_validate(...)` and inside `isvalid()`, which hardcodes `repair_duplicate_cell_ids=False`, suppresses `MissingIDFieldWarning`, returns a bare boolean (no error details), deep-copies the input, and asserts non-mutation. So §3.2/§6's "validate a deep copy with repair disabled" is realizable only as `isvalid(deepcopy(nb))` (boolean verdict, no diagnostics) or by reimplementing the missing-id/duplicate-id checks; the corrected proposal should state which path produces its detailed observations, and F-series no-repair checks should assert against that chosen path.
4. **Condition preservation in §3.1 [SRC].** `compare_text_approximate` has an earlier fast cutoff — `if bool(x) != bool(y): return False` (exactly one side empty) — before the short-string rule (`notebooks.py@v4.0.4`, capture `bc9c5c5ad149…`). The proposal's "returns `True` for any two strings shorter than 10 characters without comparing them" should add this exception. The hazard's substance is unchanged.
5. **Lead 1 is partially upgradeable from already-captured evidence [SRC].** The v4.0.4 docstrings state the multilevel iteration order directly: `compare_cell_strict` "in the first multilevel diff iteration", `compare_cell_moderate` "in the second", `compare_cell_approximate` "in the third and last". Combined with the "low-to-high precedence" list ordering, this supports application of the highest-precedence predicate (incl. `compare_cell_by_ids`) first, i.e., the proposal's "highest-precedence id-equality" reading. `snakes.py` remains uncaptured, so the hedge should shrink, not disappear.
