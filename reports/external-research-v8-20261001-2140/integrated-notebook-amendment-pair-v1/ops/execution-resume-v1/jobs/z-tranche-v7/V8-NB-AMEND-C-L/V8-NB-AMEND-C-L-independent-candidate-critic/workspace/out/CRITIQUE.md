## 3. Corrections and counterexamples

**C1 — [supported correction, must land in the final revision] The Q3 fix chain mis-attributes the 5.2.0 change to PR #236, which the source record shows was never merged.** §4 states: "Fix chain: PR #236 'Start working on mutation issues in validate.' … Released as: nbformat **5.2.0** 'Only fix cell ID validation issues if asked' (S2)". Evidence: the direct issues-API record for #236 (fetched 2026-10-03T03:31:47Z, sha `66c9810b…`) shows `state: "closed"`, `closed_at: 2022-06-08T07:40:31Z`, and **`pull_request.merged_at: null`** — a PR closed *without* merge. The captured changelog's 5.2.0 section is old-style and **unattributed** (no PR links), so S2 cannot connect the entry to #236 either, and no other captured source does. The proposal's S6 register cites issue-*search* result bodies (which do not carry `merged_at`), which plausibly explains how this was missed. Required fix: restate the chain as #235 (issue, 2021-11-16) → 5.2.0 changelog entry (unattributed in S2) → warning text / `normalize()` since 5.1.4 (#359 quote) → 5.5.0 deprecation with the security-model rationale → 5.11.0 "Remove deprecated kwargs" (PR #447); cite #236 only as the recorded "Step 1 toward #235", closed unmerged 2022-06-08. Q3 remains satisfiable — the issue→fix→test chain survives on S2+S3+S6 without the #236→release link — but as written §4 asserts a release fact its own register does not support and the direct record contradicts.

**C2 — [normative-force correction] The `unrecognized_cell`/`unrecognized_output` claims overstate S1.** §2.1 says the definitions "preserve cells/outputs from future minor revisions [S-fact, S1]" and §3.3(e) tags "unrecognized cells/outputs must not crash comparison" as **[S-req]** because "S1 defines unrecognized_cell/unrecognized_output precisely so they can be represented". Evidence (S1, byte-identical): the definitions exist with descriptions "Unrecognized cell/output from a future minor-revision to the notebook format", **but** `definitions.cell` `oneOf` lists only `raw_cell`/`markdown_cell`/`code_cell`, and `definitions.output` `oneOf` lists only the four known output types. The `unrecognized_*` definitions are referenced by neither `oneOf`, so a cell with a future `cell_type` does **not** validate against the captured v4.5 schema; forward tolerance is instead behaviorally evidenced by S3 `test_future` (future *declared minor* with extra keys passes at its own version, fails forced at 4.3). Required fix: reclassify §3.3(e)'s "[S-req]" as a prototype requirement [CH] supported by [INF] from S3 `test_future`; note explicitly that "defined in the schema" ≠ "admitted by the schema's cell/output branches". Add the validator's future-minor relaxation path to the open leads.

**C3 — [internal-consistency correction with counterexample] `execution_count` is not an output; folding it into `outputs.changed` breaks the proposal's own separation guarantee and makes F3 non-discriminating.** §3.2 defines `outputs.changed(cell_ref, detail, old, new)` "(including execution_count-only changes …)", and F3 is "outputs-only change (incl. execution_count bump)". Evidence: S1's `code_cell.required` is `["id","cell_type","metadata","source","outputs","execution_count"]` — `execution_count` is a **sibling** of `outputs`, not a member; S1 additionally gives `execute_result` outputs their own separate `execution_count` field, so "cell counter" and "result counter" are distinct fields that one op name would conflate. Counterexample: a cell whose outputs are byte-identical with `execution_count` 3→4 would be reported as `outputs.changed`; a consumer filtering "outputs changed" is told something false, and the §3.2 guarantee "an edit to source alone never marks outputs/metadata changed" fails by symmetry for a sibling required field. The nbdime precedent itself (S7 index, verbatim) classes execution counters as "generated values", not outputs. Required fix: a distinct observation kind (e.g., `execution_count.changed`, noise-classified by default [CH], noise source = S7), and split F3 into F3a (outputs content change, counter held fixed) and F3b (counter-only). As written, F3 cannot fail — it cannot distinguish the stated assumption (noise classification) from an ordinary output change.

**C4 — [validation-coverage gap vs N5] The §3.1 input refusals have no fixture.** §3.1 specifies refusal of major ≠ 4 (S1 `maximum: 4`), v4-without-`nbformat_minor` (S3 `test_notebook_invalid_without_min_version`), and non-notebook JSON; §6 step 1 requires refusing them; but F1–F12 exercises none of them. N5 requires "discriminating validation covering N1–N4", so the proposal's own fixture set leaves N1's unsupported-input reporting untested. Required fix: add refusal fixtures (major=3; v4 missing minor — mirroring S4's `no_min_version.ipynb`, 252 B; non-notebook JSON), each asserting the specific refusal.

**C5 — [coverage gaps, three instances]** (i) §3.1's invalid-id rule (pattern/length failure → demote to identity-by-position, citing S3 `test_invalid_cell_id`) has no fixture; S4's `invalid_cell_id.ipynb` (766 B) is cited in §1/§3.1 but never used by F1–F12 (F6/F7 cover missing/duplicate, not malformed). (ii) §5's untracked-without-content outcome ("listed as unrecoverable") has no fixture — F10 covers only content-present untracked. (iii) §3.1's comparison-side rule "if a snapshot did not record a file's content … we report `content-missing`, never infer it" has no fixture; F11's missing blob covers only the recovery-side refusal.

**C6 — [overstatement vs cited source; classification] §2.2's table row "nbdime — File (non-notebook) diff/rename/recovery: None (notebook-only tool)" is stronger than its citation.** S7 `diffing.html` (byte-identical) documents the diff format for "mappings (dicts) or sequences (lists or strings)" and is addressed to library users — the diff representation and primitives are generic, so "file diff: None" is not supported by S7 as an S-fact. What S7/S8 do support: no rename detection, no workspace/manifest concept, no copy-into-new-directory recovery, and notebook-focused tooling. Required fix: narrow the claim to rename/recovery/manifest absence, mark the cell [INF]. The §2.2 recommendation is unaffected, because the decisive gaps (rename detection, recovery) are real.

**C7 — [citation-scope precision] §3.3(b) merges an inference into an S-req quote.** The tag "[S-req + exception, S1]" covers two clauses: "the schema cannot enforce uniqueness across oneOf branches" and "cell-level `name` uniqueness is explicitly outside schema-checkable power". S1's explicit statement ("This criterion cannot be checked by the json schema…") lives in `definitions/misc/metadata_name` and is about cell **metadata.name**; the `cell_id` definition (pattern, minLength/maxLength) carries **no** uniqueness claim anywhere in S1. Schema-level non-enforceability of id uniqueness is a legitimate [INF] — behaviorally supported by S3, where duplicate ids are caught only by Python-side `_validate(repair_duplicate_cell_ids=False)`, not by schema validation. Required fix: split the labels (name clause = S-req quote; id clause = INF). The design conclusion (report duplicates, never silently repair) is unchanged and sound.

(ii) S7 `index.html` re-capture differs byte-wise from the register (dynamic RTD wrapper); every quoted substantive string is identical, no claim affected. (iii) S6's register hashes correspond to issue-search bodies; the per-issue records verified here differ byte-wise as expected across endpoints.
