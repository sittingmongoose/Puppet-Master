I1-1 — Separate the current deliverable from acquisition and revision history
Source evidence
tools/delivery.py:412-454, especially lines 448-453, always appends Auditable history and then the complete investigator revision_history to the rendered report. NEXT_TRIAL.md defines that report as the maintained arm's designated final. prompts/evaluator-i1.txt requires the final judgments to be locked before reading upstream acquisition records.
The maintained prompt explicitly asks the agent to preserve previous whole records in revision_history. The control prompt also asks for removed/replaced material in an appendix of its report. Thus the correction belongs to both arms, not just the maintained one.
Reproduction
Probe P1 supplies valid current findings plus a historical sentinel that is absent from every current part. render(assemble(draft)) places that sentinel in the designated final report. This proves the first evaluation view includes historical acquisition material. It does not show that an evaluator has actually misgraded anything, and it is not a reference-key leak. I1 has not run.
Why it matters
“Do not give history credit” is not the same as “history has not been seen yet.” The proposed staged evaluation cannot honestly claim upstream was withheld if previous acquired records are already included in the first report. Repeating current records and history also makes a larger evaluator input without adding new current findings.
Bounded correction
Before any paid dispatch:
1. Define a current-only report projection for I1. It contains every current substantive finding part, including uncertainty and UNEXECUTED proposed validation, plus necessary source provenance. Do not delete material because it is uncertain.
2. Preserve original/raw JSON, superseded records, snapshots, and change reasons separately in an audit/history artifact. The existing full rendering may remain available there. No audit history is destroyed.
3. Change the control prompt's appendix instruction to save historical material separately as well. Freeze the new control/maintained prompts before inference. This is not post-hoc cleanup of a result.
4. The first evaluator view contains the fixed case/key plus the two current reports; raw acquisition/history is disclosed only after final-report judgments are saved and fixed. Reuse the same two reviewer assignments and existing file-copy/access workflow; no new evaluator model stage is needed. If the implementation can enforce only a prompt boundary, disclose that limitation rather than claim filesystem-level isolation.
5. Add a synthetic regression: a marker present only in a superseded record is absent from the first-view report/package and present in the history artifact. A current uncertain finding and a validation proposal must still be in the current report.
6. Re-freeze only the affected new files and proposed trial identities. Preserve all historical R1/R1b files and scores.
Acquisition/preservation measurement clarification (same amendment)
State exactly which records form each arm's acquisition inventory. Do not use only final draft.json as both the maintained arm's acquisition denominator and its rendered result: that would test copying of the last state, not preservation across research.
After final judgments lock, use the control's observation records and preserved revisions, and the maintained arm's chronological snapshots/revision records/current records, with native write traces where already available. Trace source-supported substance to its earliest recorded occurrence and disposition. Separate legitimate correction or supersession from accidental loss; a title-only lead is not a complete acquired finding. Report two separate results:

V-FOLLOWON-1 — Absence lint blocks ordinary missing-input conditions and proposed tests
Not executed by I1. Fix before a later paid flash-verifier integration; do not expand I1 to test it.
tools/delivery.py:29-39 matches standalone missing, unsupported, and similar terms. Lines 231-242 apply this trigger to a kept part's text, not just explicit source-absence assertions. Lines 291-297 clear current content for the whole finding when any part has a defect.
Against otherwise valid synthetic draft and keep decisions:
- P2 condition: If a required file is missing, show an error and leave the input unchanged.
- P3 validation proposal: Supply an unsupported codec and check that its name appears in the error.
Both require a structured absence packet and make the whole finding UNRESOLVED. Neither sentence asserts that evidence is absent from the corpus. These are synthetic reproductions of deterministic behavior, not model runs.
The code/schema disclose that the heuristic may overflag. Nevertheless, these are normal in-domain conditions and tests, not obscure adversarial wording. A broad keyword trigger must not become a mandatory demand for irrelevant corpus searching.
Later correction: distinguish source-absence assertions from conditional missing-data behavior, unsupported-input handling, quoted negative examples, and unexecuted proposals. A heuristic can flag likely source-absence prose; it cannot determine truth, prove exhaustive search, or require every negative word to carry an absence packet. Preserve honest unresolved disputes. Do not create a universal natural-language classifier or hardcode the OME answer key.
Documented design consideration, not a new blocker
Probe P4 confirms the documented rule: an unresolved action on any part makes the whole finding unresolved. Keeping a typed uncertainty is a different operation that preserves the question as a question. This is not an undisclosed parser defect. The future verifier should be tested on this distinction, particularly where an optional unresolved question is not a precondition of a supported fact. Do not fix this by detaching essential conditions from their claims or default-confirming anything.
