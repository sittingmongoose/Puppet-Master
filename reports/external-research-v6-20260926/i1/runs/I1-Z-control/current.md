# Slide Scout / OME-Zarr 0.5 — current research report (draft v1)

Case: `ome-zarr-thin`. Plan: `case/plan/Viewer.md` (frozen thin snapshot, lines cited as "Plan Ln"). Corpus: the 125 manifest-listed `case/sources/S001..S125.txt` fixed-source captures only; no live sources were fetched and no sources outside the corpus were read. Evidence quality note: several small handles are search-aid or error placeholders, not source content (O-024); GitHub issue titles are leads/allegations, not established behavior; README support claims are product assertions, not verified facts. All validation proposals below are **unexecuted**.

## 1. Format obligations that bind Slide Scout (NGFF 0.5)

**F-1. 0.5 runs on Zarr v3 with unrestricted Zarr features.** OME-Zarr 0.5 is defined on Zarr v3 (`zarr.json` for groups and arrays; attributes under a namespaced `ome` key), and "All features of the Zarr format including codecs, chunk grids, chunk key encodings, data types and storage transformers may be used… unless explicitly disallowed" — none observed disallowed (S003 lines 67–77, O-001). Constraint: Slide Scout needs a real Zarr v3 storage layer (sharding, codecs, chunk key encodings), not a bespoke reader of flat chunk files. Consequence of ignoring: unopenable or silently wrong reads of flagship datasets. Validation (unexecuted): open S055-style sharded+blosc array in the chosen storage stack and byte-compare a decoded chunk against a reference implementation.

**F-2. Version string lives at `attributes.ome.version` and MUST be consistent within a hierarchy** (S003 lines 152–165, O-002). Reference readers instead detect version from inner `version` fields left over from 0.4 or by storage generation (O-012, O-031, O-045). Constraint: version detection should read `ome.version`, with storage-generation probing as fallback. Consequence: copying reference heuristics misclassifies hybrid/legacy filesets. Disposition: **correction** to the implicit Plan assumption that "0.5" is self-identifying (Plan Ln 5).

**F-3. Axes obligations are name-only MUSTs; type and unit are SHOULD.** `axes` entries MUST have unique `name`; `type` and `unit` are SHOULD (custom type strings are legal); axes length MUST equal array dimensionality; each level array's `zarr.json` MUST carry `dimension_names` matching the axes names (S003 lines 166–174, O-003; real instance S054/S055, O-020/O-021). Constraint: calibrated display needs defined fallbacks for missing units and custom types; `dimension_names` vs axes mismatch is a detectable, explainable malformation (Plan Ln 7 feedback duty). Disposition: **covered** in spirit by Plan Ln 5 ("dimensions, units and coordinates") but the fallback behavior is a **product_choice**.

**F-4. Transform model: dataset-level scale (exactly one) + at most one translation after it, then optional group-level transforms applied after** (S003 lines 294–319, O-004). Real filesets carry per-level centering translations (O-013) and the IDR catalog deliberately includes dataset-level and multiscales-level translation samples (S010 lines 976–992, O-023). napari's feature matrix shows group-level scale/translation were unsupported in the tested napari (O-032) and a user report shows default readers silently ignoring transforms (O-026). Constraint: Slide Scout must compose [dataset transforms → group transforms] in order, per level, and never drop group-level entries. Consequence of missing this: silently wrong calibration — the failure the brief explicitly targets. Validation (unexecuted): render S010's 13457537/13457539-style translation pairs and verify overlay alignment numerically. Disposition: **covered** by Plan Ln 11 ("calibrated coordinate display") but the composition rule is a correctness detail the Plan does not state.

**F-5. Multiscales lists may have multiple entries; reader guidance is "user can choose by name, fallback first"** (S003 lines 388–397, O-005). ome-zarr-py reads only entry [0] (O-015); in the OME feature matrix no tested viewer supported more (O-032, bounded to its 2025-era vintage per O-043). Disposition: **optional_capability** / **product_choice**: implement list handling and a chooser, or document first-entry-only.

**F-6. `omero` display metadata is transitional and optional, but constrains channel color (6-hex) and window {min,max,start,end} when present** (S003 lines 398–430, O-006; schema is weaker than prose — window keys required only if a window object exists, and per-channel color/window not required at all by image.schema, O-010). napari/ome-zarr-py use `active`, `label`, `color`, `rdefs.model` (greyscale forces white), window start/end as contrast limits, with explicit degradation when windows are absent (O-015, O-016). Constraint: channel visibility controls and default T/Z need omero when present, defined defaults when not; schema-valid files can still violate prose (missing color/window). Disposition: **product_choice** for defaults; **correction** to any plan that treats schema-validity as display-readiness. AGAVE initially loaded no extra metadata at all for 0.5 (O-031) — the cost of skipping this is visible: no channel colors/names.

**F-7. Labels: integer dtypes only; labels group MUST list members; label image MUST implement multiscales with the SAME number of scale levels as the source; `image-label` is SHOULD; rgba per label-value is MAY** (S003 lines 431–514, O-007). napari hides labels by default, requires colors to show anything, and squeezes channel axes on label layers; units must stay consistent across layers or napari hides the scale bar (O-016, O-018). Constraint: overlay alignment must match level counts and reconcile channel axes; a colormap fallback is needed for color-less labels; overlay layers must carry unit metadata or calibrated display silently degrades. Disposition: Plan Ln 5/Ln 11 **cover** overlays, but three sub-behaviors are **product_choice** (default visibility, fallback colormap, mismatch handling).

**F-8. HCS plate/well and bioformats2raw collections are normative discovery surfaces the thin Plan never names.** Plate: `columns`/`rows`/`wells`/`version` MUST, acquisitions MAY, `rowIndex`/`columnIndex` 0-based, well paths constrained; well: `images` MUST (S003 lines 118–129, 515–560, 740–808, O-008). b2r: `bioformats2raw.layout: 3` transitional, optional `OME/series` + OME-XML, numbered groups by default; readers SHOULD NOT default to only the first image (S003 lines 175–275, O-009). napari discovers b2r children via OME-XML Image IDs rather than `series` (O-019); ome-zarr-py builds stitched plate/well grids with zero-filled missing tiles (O-015). bioformats2raw output hierarchies are user-configurable via `--scale-format-string` (S033, O-035), so hard-coded numbered paths break on real conversions. Constraint: discovery = plate traversal + b2r cascade (series → numbered groups → OME-XML) + plain multiscales groups. Disposition: **correction** — Plan Ln 5 "lists the images it finds" is under-specified without these two collection forms.

## 2. Spec-vs-practice contradictions (kept visible)

**F-9. A flagship-produced 0.5 plate omits the spec-MUST `plate.version`** (S056, ome2024-ngff-challenge idr0090, O-022 vs S003 line 550). Constraint: never hard-fail discovery on a missing `plate.version`; surface as an anomaly. Validation (unexecuted): run S056's fileset through ome-ngff-validator and record whether it flags (validator exists per S031, O-029). Disposition: **unresolved** as a spec-practice conflict; behavior requirement is clear (tolerate + explain).

**F-10. 0.5 label images cannot be reliably distinguished from ordinary images.** 0.4 required `image-label` on label groups; 0.5 downgraded it to SHOULD ("every valid image group is also a valid image-label group"); OME issue #339 (open since 2025-09-19) asks for a fix (S035 lines 5037–5113, O-042). Concrete instance: the IDR 0.5 label fileset has no `image-label` key at all (S054, O-020). Constraint: overlay discovery must be `labels`-group-first, `image-label`-second, with a manual assignment affordance. Disposition: **unresolved** spec gap; product behavior **product_choice**.

**F-11. image.schema is weaker than the normative prose** (O-010): channel `color`/`window` not required per channel in schema though prose MUSTs them; scale-array length equality not expressible. Constraint: do not use schema validation as a display-readiness gate. Disposition: **correction** to any validation-first design.

**F-12. zarr v3 disables the v2 `compressor` option** ("compressor cannot be used for arrays with zarr_format 3. Use bytes-to-bytes codecs instead", PR #413 trace, S013/O-039); real 0.5 arrays use `sharding_indexed` + blosc/zstd + crc32c (S055, O-021); b2r's 0.5 codec menu is null/blosc/gzip/zstd (S033, O-035); napari's ecosystem split on zarr v2/v3 caused import-level breakage for users (S011, O-026). Constraint: Slide Scout's storage stack must be v3-native with the codec set {null, blosc (all cnames/shuffles), gzip, zstd, sharding_indexed, crc32c, bytes, transpose} — the union of producer menus (S033/O-035) and the reference implementations (S085/O-045: tensorstore ships exactly blosc, bytes, crc32c, gzip, sharding_indexed, transpose, zstd). Disposition: **correction** — Plan Ln 9 "interoperate with real tools" has a concrete codec floor the Plan never states.

## 3. What reference reader implementations reveal

**F-13. Version detection is storage-first everywhere.** ome-zarr-py: probe attrs, unwrap `ome`, detect from leftover version keys, default to newest (O-012/O-014). AGAVE: "if we find a zarrv3 zarr.json file, then I am assuming a OME-NGFF 0.5 json file… Anything outside this assumption will error out" (S094/S082, O-031); its diff probes zarr.json first then `.zattrs` (S098, O-045). Consequence: prior art conflates storage generation with format version. Slide Scout opportunity: read `ome.version` first (F-2). Disposition: **product_choice** with a recommended direction.

**F-14. Lenient vs strict parsing.** napari accepts rotation/affine/sequence transforms that 0.5 does not define, and already carries 0.6 `coordinateSystems`/`scene` handling (S048, O-017); ome-zarr-py v0.19.0 had to become "more permissive with version 0.5" to accept real SpatialData filesets (S052, O-038). Constraint: unknown-but-parseable constructs should degrade with explanation, not crash (Plan Ln 7). Disposition: **product_choice** (strictness policy), with 0.6 items as **optional_capability** watch items only (RFC 5 is version 0.6.dev3, "first-class support for spatial and coordinate transformations… coordinate systems… scenes", S051 lines 216–248, O-038 context).

**F-15. Reference UI precedents worth copying or rejecting.** napari: labels hidden by default; no colors ⇒ nothing shown; channel axis split into layers; per-axis units kept with None placeholders to preserve the scale bar (O-016, O-018). ome-zarr-py/napari: plates stitched into one almost-square image with zero-filled missing wells (O-015) — invisible fabrication; vizarr shows only the lowest plate resolution and opens wells in new windows (O-032). AGAVE HELP documents a 16-bit-only, GPU-memory-bound, 4-channel-cap origin and a 100 MB tensorstore cache cap (O-044, O-045). Disposition: each is a **product_choice** for Slide Scout; the zero-fill precedent should be rejected in favor of explicit "empty well" marks (consequence: honesty about absent data).

**F-16. Discovery-by-legacy-pattern silently excludes 0.5.** ome-zarr-py's BioFile Finder integration scanned the local filesystem "looking for zarr images (only .zattrs for now - can add zarr v3 support as a follow-up)" (S023, O-046). Constraint: Slide Scout local discovery must probe `zarr.json` and `.zattrs`/`.zgroup`. Disposition: **correction** to any folder-scan design implied but unstated in Plan Ln 5.

## 4. Requirements the thin Plan misses (compatibility, navigation, display)

**F-17. Collection discovery breadth** — plate + b2r + labels + multi-series (F-8, F-10, F-16). The IDR corpus that defines "representative" spans 0.1–0.5, plates with up to 384 wells/329 fields, labels, b2r collections, and >100k-pixel images (S010, O-023). Disposition: **correction** (scope) with an **unresolved** product question: does "OME-Zarr 0.5" exclude the 0.4 filesets users actually have? (Plan Ln 3 vs Ln 9; brief line 3.)

**F-18. Responsiveness requirements beyond pixel reads.** vizarr's plate issue: row×col metadata requests before any pixels (1,970 requests for one IDR plate) (S050, O-041); napari "crashes on zooming" on plates and Z-downsampled pyramids; vizarr fails Z-downsampled pyramids and non-2 downsampling; neuroglancer fails big-endian `>u1` (O-032, vintage-bounded per O-043); vizarr #60: wrong chunk at low resolutions ⇒ 404 + hang (O-041). Constraint: batch/reuse array metadata during discovery; clamp chunk indices per level; support Z-downsampled pyramids, non-2 scale factors, and big-endian dtypes. Plan Ln 7 covers background reads + cancellation but not these. Disposition: **correction** to Plan Ln 11's acceptance list (add these rows). AGAVE's failure stream (GPU memory leaks, caching, load-time downsampling) shows desktop memory discipline is the recurring desktop pain (O-044).

**F-19. Sharding is the 0.5 flagship storage mode, not an edge case.** IDR/challenge 0.5 outputs are sharded (O-021, O-036); ome-zarr-py shipped sharding only in v0.16.0 (O-038); an open ome-zarr-py issue shows auto-sharded writes crashing the writer (S044, O-049), and `shards: "auto"` string specs are entering producer APIs. AGAVE has zero "shard" search hits in the captured open-issue search (S102, O-047 — weak negative evidence, bounded). Disposition: **correction** to the Plan's implicit storage assumptions; validation proposal in §7.

**F-20. Failure explanations need detail the reference readers lack.** ome-zarr-py's `parse_url` collapses missing-vs-unopenable to `None` (O-014); AGAVE PR #220's assumption "error[s] out in some way" without validation (O-031); vizarr #307 alleges chunk tiling corruption on challenge-resaved 0.5 data (open, single-reporter — allegation only, O-025). Constraint: Slide Scout's "explain which image or data could not be displayed" (Plan Ln 7) should classify: missing node / unreadable zarr.json / unsupported codec / version mismatch / transform mismatch. Disposition: **covered** (Plan Ln 7) with **correction** in depth; validation proposal in §7.

## 5. Opportunities and simpler alternatives

**F-21. Library options exist; building storage from scratch is avoidable.** ome-zarr-py #407 surveys nine OME-Zarr libraries across metadata/validation/arrays/graph-traversal/CLI dimensions, including ome-zarr-models (OME's validation-focused models), ngff-zarr, and ngio (S029 lines 139–204, O-048). AGAVE delegates storage to tensorstore (O-045); napari-ome-zarr 0.8.0 went zarr-v3-native by dropping ome-zarr (O-037). ome-zarr-py's own timeline (0.12.0 read/write 0.5 → 0.16.0 sharding → 0.19.x permissiveness, O-038) shows the Python stack matured through 2025 — recent enough that installed tools lag (O-026). Disposition: **optional_capability**/**product_choice**: select and pin a storage library; also **correction** to any assumption that "the OME Python stack" is uniformly 0.5-capable.

**F-22. Cheap wins beyond surveyed viewers.** Multi-entry multiscales (F-5): no tested viewer supported it (O-032, vintage-bounded). Missing `plate.version` tolerance (F-9): flagship data violates the MUST. Honest empty-well marks (F-15). Each is small and differentiating. Disposition: **optional_capability** items for explicit review per Plan Ln 9.
