# D4 label-source omission adjudication

J8's reported acceptance of registered nested labels when `image-label` or `source` is wholly absent is **not a proven factual error**. Its core is defensible; default propagation and recovery remain interpretation/policy issues. Do not extend that finding to treating `source: {}` identically, or to ignoring an explicit conflicting source. This adjudication concerns the reported wording only, not J8's complete artifact or derivative acceptance.

Evidence checked 2026-09-09. Independent evaluator; no participation in native jobs.

**Normative authority.** [OME-NGFF 0.5 §2.6, “labels” metadata](https://ngff.openmicroscopy.org/0.5/) uses SHOULD for `image-label`, MAY for `source`, and MAY for `source.image`; supplied values must have the prescribed types. It states: “The default value is `../../`”. The Conformance section makes descriptive assertions normative too, except explicitly informative material. Thus this default is not merely an illustrative implementation preference. Section 2.6 permits intermediate groups without metadata and describes registration under the enclosing image's `labels` group. Section 1.1 illustrates `original/0` registration.

The most direct reading applies the declared default when a present source object lacks `image`. The text does not specify whether to synthesize missing enclosing objects, a conflict-precedence algorithm, or mandatory whole-label rejection after a source-resolution failure. SHOULD is a recommendation with possible exceptions, not an unconditional presence requirement. These limits preclude both universal default insertion and universal acceptance/rejection claims based solely on omission.

**Versioned schema evidence.** The official [`label.schema`, lines 7–26 and 79–88](https://github.com/ome/ngff/blob/8cbba216e37407bd2d4bd5c7128ab13bd0a6404e/schemas/label.schema#L7) requires `ome.image-label` and `ome.version`; it does not require `source` or `source.image`, and contains no `default`. Its source validation checks object/string shape, not path resolution. [`strict_label.schema`](https://github.com/ome/ngff/blob/8cbba216e37407bd2d4bd5c7128ab13bd0a6404e/schemas/strict_label.schema) additionally requires colors. Consequently, the label schema's `image-label` presence rule is stronger than the prose recommendation. Report which validator/profile is applied; schema failure here does not establish a universal reader-rejection rule. The official [`ome_zarr.schema`](https://github.com/ome/ngff/blob/8cbba216e37407bd2d4bd5c7128ab13bd0a6404e/schemas/ome_zarr.schema) is an `anyOf` across schemas, further limiting conclusions drawn from the label branch alone.

**Implementation evidence, not normative authority.** The model project's v1.6 release pins to `7c297d90e70e9251620d33775e56c49e7acd0185`. Its [`v05/image_label.py`, line 19](https://github.com/ome-zarr-models/ome-zarr-models-py/blob/7c297d90e70e9251620d33775e56c49e7acd0185/src/ome_zarr_models/v05/image_label.py#L19) declares absent `image_label` as `None`. Its [`common/image_label_types.py`, lines 32–39 and 62–65](https://github.com/ome-zarr-models/ome-zarr-models-py/blob/7c297d90e70e9251620d33775e56c49e7acd0185/src/ome_zarr_models/common/image_label_types.py#L32) declares missing `source` as `None`, but `Source.image` as `default="../../"`. The v0.5 module [imports those shared types](https://github.com/ome-zarr-models/ome-zarr-models-py/blob/7c297d90e70e9251620d33775e56c49e7acd0185/src/ome_zarr_models/v05/image_label_types.py#L4). This corroborates distinct omission handling. It does not prove association discovery or image-target validity: the shared source class explicitly leaves target validation as a TODO. This implementation cannot settle normative ambiguity by itself.

**Separate acceptance expectations.** Assume all unrelated image, label-array, coordinate and registration requirements are satisfied. Let image `A` be `/A`, registry `R` be `/A/labels`, and label group `L` be `/A/labels/original/0`, listed as `original/0` at `R`.

| Input at L | Metadata/schema observation | Conservative viewer expectation proposed here |
|---|---|---|
| `image-label` absent | Dedicated label schema fails presence check; v1.6 model keeps `None`. | Allow registered association to A under a documented omission policy; record missing recommended metadata. Do not claim a source object was stored or universally defaulted. |
| `image-label` present, `source` absent | Dedicated label schema allows omission; model keeps `source=None`. | Allow the same registered association policy. Keep this distinct from an empty source object. |
| `source: {}` | Dedicated label schema accepts; model supplies `image="../../"`. | Evaluate that default: it reaches R, not A. Diagnose unresolved/invalid effective source. Do not count this fixture as an unqualified successful source association. Any registry-based display recovery is a separate explicit policy. |
| `source.image="../../"` | Schema accepts the string but cannot validate its target. | It reaches R. Reject this source association to A; never silently reinterpret it as three parent steps. Whole-store rejection is unnecessary. |
| `source.image="../../.."` | Schema accepts the string. | It reaches A. Accept the source association after target and remaining compatibility checks. |
| Another explicit path | String validation alone is insufficient. | Resolve from L and check the actual image target. Diagnose any disagreement with registration; do not silently override the explicit value. |

At a direct label group `/A/labels/seg`, two parent steps instead reach A. Registered nested paths themselves are not defects. No number of intermediate groups changes the literal meaning of an explicit relative path.

Suggested plan wording: “Discover associated labels through the image's labels registry, retaining nested paths. Preserve whether `image-label`, `source`, and `source.image` were supplied. Permit absent enclosing metadata through documented registry association handling. For a present source object with omitted image, evaluate `../../`; resolve supplied paths literally from the label image group. Check target identity and compatibility. Report source failures or conflicts without silently correcting paths; define any display fallback separately.”

**Verification and remaining limits.** Executed Draft 2020-12 validation against the fetched official label/version schemas: absent `image-label` failed; absent `source`, empty `source`, and both explicit relative strings passed; `source:null` failed. None of these six validations mutated the inputs. These were metadata-shape checks, not full store fixtures. Model behavior was established by source inspection, not executing the model package. No live reader was tested. A maintainer clarification would still be needed to establish universal propagation through absent enclosing objects or reader recovery/precedence rules. The v1.6 model distinction supports narrowing J8, not scoring an unspecified `source:{}` fixture as equivalent to absent source.
