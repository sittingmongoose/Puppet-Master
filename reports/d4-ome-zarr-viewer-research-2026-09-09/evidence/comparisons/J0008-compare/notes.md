### R1 — Recognize and enumerate the fileset hierarchy, preserving image and array paths

**Classification: concrete repair. Owner:** Viewer.md:5 (“opens a local OME-Zarr 0.5 fileset and lists the images it finds”), constrained by :9. **Consumers:** image chooser and channel/plane canvas in :5; discovery/interoperability acceptance in :11. There is no requirement for a plate-shaped UI: a list of well/image paths can satisfy the existing chooser.

**Evidence:** AGAVE dispatch uses a `.zarr` extension or a local directory path containing “zarr” (S00021:36–65); its Zarr opener counts entries in the supplied group's `multiscales` list and does not enumerate a collection hierarchy (S00008:200–231,360–425). OME-Zarr 0.5 instead places metadata under `attributes.ome`, requires a version consistent within the hierarchy, and distinguishes image groups, resolution arrays, collections, plates, wells and labels (S00005:149–174,175–275,431–474,515–560,740–752). BFF #508 fixes application classification for paths inside `.zarr`/`.n5` containers; it does not rewrite the selected path to the container root (S00031 patch, S00035 comments, S00036–S00037).

**Concrete replacement/addition to line 5:**

> Inspect local Zarr metadata rather than requiring a filename substring. Validate Zarr node kind/format independently from `attributes.ome.version`; distinguish a supported OME-Zarr 0.5 image/organization, another version, a generic Zarr group and malformed metadata. For a selected image group, use its multiscales metadata. For a plate, follow `plate.wells[].path` and each well's `well.images[].path`. For a transitional `bioformats2raw.layout` collection, give plate metadata precedence; otherwise read `attributes.ome.series` from `OME/zarr.json`, resolving its image-group paths in the collection's root namespace. If that layout has no series or plate metadata, use its consecutively numbered image groups beginning at 0. For other local hierarchies, discover candidate image groups by bounded, cancellable metadata traversal and validate their OME image metadata; do not apply the numbered-collection convention to arbitrary Zarr groups or treat every array as an image. List all discovered source images with stable group paths, retaining usable siblings when one image fails. Resolve every `datasets[].path` relative to its image group in metadata order; never construct a level path from an integer index. Keep associated labels as overlays for their source images. Preserve a supplied image-group subpath rather than replacing it with the enclosing `.zarr` root.

The numeric `bioformats2raw.layout: 3` used by the spec's JSON examples is a required positive fixture. Prose quotes “3”; a string-only parser is unsupported by those examples. Acceptance of a string variant needs schema/producer evidence; this report does not assert that the string is conforming. A generic root is not itself an OME image, but may contain valid OME image groups: do not reject those merely because the root lacks `multiscales` or the transitional marker. Local traversal can inspect child metadata without decoding image chunks (Zarr core's listable-hierarchy guidance, S00066:982–1006). Only a completed discovery with no recognized images justifies a no-images explanation; an interrupted or unreadable scan must say discovery is incomplete. This is a proposed way to satisfy the Plan's existing image-listing intent, not a claim that OME 0.5 mandates arbitrary recursive directory crawling or defines every custom collection convention.

**Acceptance checks:**

1. Open the same single-image hierarchy from a directory named `sample.zarr` and from a renamed directory with no “zarr” substring; image identity, dimensions and navigation agree. Open a nested image group whose name contains dots and preserve its exact relative path; a trailing directory separator changes no identity.
2. A collection with `OME/zarr.json: attributes.ome.series = ["images/b", "images/a"]` lists both source images in declared order, without looking under `OME/images/` or confusing their pyramid arrays for images. A fixture with `bioformats2raw.layout: 3`, no series and no plate finds numbered groups 0 and 1. A generic group with unrelated numbered arrays is not silently treated as this layout; a generic parent containing valid OME image groups at `images/a` and `images/b` discovers both by metadata. Cancelling or losing permission during that scan yields an incomplete-discovery state, not a false empty-fileset result.
3. A sparse plate containing two wells and two images per well lists four source images using plate/well metadata. A deliberately inconsistent series list does not override plate precedence. A broken image is identified by path and leaves valid images selectable.
4. High-to-low dataset paths `full`, `pyramid/half`, `pyramid/quarter` are opened exactly as declared. Pan/zoom selects the corresponding arrays rather than paths `0`, `1`, `2`; base-image and overlay level paths may differ.
5. A generic v3 group, an array passed where an image group is needed, a v2/OME-0.4 store, missing OME namespace, inconsistent OME versions, and invalid JSON receive distinguishable explanations. In-scope valid image groups do not fail merely because their enclosing collection lacks root `multiscales`. Any array-to-parent convenience navigation is optional, not assumed.

### R2 — Carry axis semantics and complete calibration through every selected view

**Classification: concrete repair. Owner:** Viewer.md:5 dimensions/units/coordinates, time/plane controls and pyramid choice. **Consumers:** details panel, canvas and aligned overlays in :5; “calibrated coordinate display” in :11.

**Evidence:** OME-Zarr defines arbitrary unique axis names, array `dimension_names` matching those names, typed ordering and rank 2–5 (S00005:81,166–174,299–307). Dataset transforms require one scale and at most one translation after it; optional multiscale transforms apply afterward (S00005:276–315). AGAVE reads only dataset transform `[0].scale`, takes the first spatial unit, and locates T/C/Z/Y/X by conventional names (S00008:234–259,319–350,400–416,562–581; S00015:340–393). Centisecond is allowed by the spec but AGAVE abbreviates it to `cs` and its seconds converter falls through unchanged (S00015:221–268). These are code-level gaps; they were not reproduced on screen.

**Concrete replacement/addition to lines 5 and 11:**

> Derive dimensions, control indices and slicing from the axis metadata and matching array dimension names, preserving each axis's name, type, order and unit. Treat absent time/channel/third-spatial dimensions as absent controls or singleton internal dimensions, never as a reason to demand TCZYX input. Compose each selected level's dataset transforms, then its multiscale transforms, in specified order, and use the same mapping in coordinate details, viewport placement and overlays. For per-axis scale/translation lists, the mapping is `p = s_global * (s_dataset * i + t_dataset) + t_global`, with identity for an omitted global list. Keep array index coordinates distinct from physical coordinates. Preserve heterogeneous units per axis or convert values numerically to a common compatible unit before spatial comparison; changing a unit label alone is insufficient. Missing or unsupported calibration must be shown as unknown/index-space or specifically unsupported, never silently assigned a physical origin or unit.

Arbitrary spatial names do not themselves identify anatomical orientation. Preserve their declared identity/order and avoid guessing that a name implies X/Y/Z. Where an axis-to-canvas mapping is ambiguous, explain the limitation; a user-configurable orientation/mapping editor would be an additional choice. Valid scale/translation values stored through a transform `path` are allowed by §2.3; resolve them read-only if supported, or explicitly report that representation as unsupported rather than substituting identity. The exact supported-representation boundary belongs in the compatibility decision in R5.

**Acceptance checks:**

1. Positive fixtures cover YX, TYX, CYX, TCYX, ZYX, TZYX, CZYX and TCZYX, with distinct time/channel/plane values and non-square dimensions. Selection must return the reference slice. Include valid custom names (e.g. `row`, `column`, `depth`) and matching `dimension_names`; a mismatch is invalid metadata, not permission to silently permute values.
2. An X-axis example with `i=4`, dataset scale 2 and translation 10, global scale 3 and translation −5 yields **49** physical units. With the next level's scale 4 and index 2, the same physical point remains 49. Verify numerical details and overlay position across zoom, not just a scale bar.
3. An axis in nanometers and another in micrometers retain correct aspect/calibration; 1000 nm and 1 µm are the same physical length. Time scale 2 centiseconds at index 25 gives 50 cs or 0.5 seconds when converted. No HH:MM:SS overlay is required to test the underlying values.
4. Valid scale-followed-by-translation and multiscale-level transforms are positive tests. Translation-first, missing scale, duplicate scale and wrong vector lengths are **negative** metadata tests. Do not label translation-first a conforming 0.5 incompatibility.
5. Missing units remain unspecified; controls may still operate in index space. Unsupported axis types/transform representations get specific feedback while other images remain usable. Any supported transform-path fixture produces the same mapping as its inline equivalent.

### R3 — Associate and align labels while preserving discrete integer identity

**Classification: concrete repair. Owner:** Viewer.md:5 “optional overlays for associated label images.” **Consumers:** selected image's overlay canvas in :5 and “aligned label overlays” in :11; read-only/session-local policy in :9. “Optional” permits turning an overlay off; it does not make a displayed, misassociated overlay correct.

**Evidence:** `labels` is nested inside its image alongside resolution arrays; `labels/zarr.json: attributes.ome.labels` lists paths relative to that labels group, including intermediate groups. Label pixels use integer types through signed/unsigned 64-bit. A label's multiscales metadata is required, its number of levels must equal the source's, `image-label` is a SHOULD and `source` is optional (S00005:102–117,431–474). AGAVE's opener does not traverse those relations (S00008); rendering an integer volume with interpolation off is not associated-label support. Its 16-bit intensity buffer is also an unsafe model for label identity (S00009:19–48).

**Concrete replacement/addition to line 5:**

> Discover the selected image's label groups from their metadata paths. Use nesting and any valid `image-label.source.image` reference to establish the source relationship without requiring the optional source field. Resolve source paths relative to the label image; do not blindly apply `../../` across deeper intermediate groups. Validate compatibility of the label's dimensions, axes, levels and physical mapping with the selected source before displaying an overlay. Select each image's and label's actual dataset paths and map their coordinates into the same physical space. Preserve raw integer label IDs through lookup/color assignment, using discrete sampling without interpolating, normalizing or narrowing IDs. If association or alignment cannot be established, keep the source image usable and explain why that overlay is unavailable.

**Acceptance checks:**

1. Discover an ordinary `labels/cells` image and a nested `labels/original/0` image from the label list; neither needs a filename ending `.zarr`. Absence of optional `image-label` or `source` does not by itself cause rejection when nesting establishes the relationship. Conflicting or unresolvable explicit source references do not silently attach to the selected image.
2. A label with a singleton irrelevant dimension overlays correctly; a real spatial/temporal mismatch is explained. The spec's same-level-count requirement is validated; non-numeric level paths are independently resolved. Translation/scale fixtures put a labeled landmark at the same physical position at multiple zoom levels and selected planes/times.
3. Label values 1, 65537 and 16777217 remain distinct; a supported uint64 path also preserves adjacent IDs above 2^53. Test signed labels as supported. Equality/color lookup cannot pass through an inexact floating-point representation or a uint16 intensity remap. For an unsupported integer representation, report it rather than merging IDs.
4. Zooming never produces intermediate label IDs. Toggling overlays changes only session display state. Malformed label metadata or a failed label chunk leaves the base image and other overlays/choices usable. Metadata-provided label colors are a normative SHOULD; any fallback palette/opacity policy is explicitly recorded, not mistaken for a segmentation-analysis feature.

### R4 — Make background reading, cancellation and failure containment observable

**Classification: concrete repair. Owners:** Viewer.md:7 responsiveness/cancellation/errors, and :5 automatic pyramid selection. **Consumers:** every pan/zoom, channel/time/plane or image change in :5; large-data/no-crash acceptance in :11.

**Evidence:** AGAVE allocates the selected volume plus a temporary native-dtype channel buffer, uses a 100,000,000-byte TensorStore cache, and synchronously reads selected channels (S00008:474–524,542–639). GUI open has an explicit async/chunk/cancel TODO and blocking call; the timeline also calls synchronously (S00022:826–838; S00023:73–117). TensorStore is chunked; AGAVE's application model is not evidence of bounded, out-of-core interactive viewing. TensorStore Read may leave a target partly written on error (S00016:638–645); unchecked Future/Result `.value()` can terminate the process (S00008:562–596; S00032–S00034).

**Concrete replacement/addition to lines 7 and 11:**

> Perform metadata discovery and data decode away from the interaction thread. For the current image, level, viewport, time, plane, visible channels and enabled overlays, schedule the chunks/regions needed for that view. Do not make a full-resolution volume or whole time series a prerequisite for first display. On a view change, cancel obsolete queued and in-flight work through the reader's supported mechanism and stop scheduling further obsolete reads. Tag results with the view identity so a late success, partial buffer or error cannot overwrite the current canvas, coordinates or control state. Bound queued work, decoded buffers and any caches together, release obsolete allocations, and report unsupported or over-budget requests without blocking navigation. Check parse/open/slice/read/decode results before publishing data; contain an image/level/overlay failure to the affected item and retain selection of valid siblings.

Cancellation does not imply that an already-running disk operation is instantaneously abortable. Where the backend cannot stop one operation, its remaining work and memory must stay bounded and its stale result must be discarded. This qualification preserves the cancellation requirement; merely moving an unbounded full-volume load to a worker does not satisfy it. No particular cache size, backend or disk-cache product feature is adopted here.

**Acceptance checks:**

1. On a large local fixture exceeding available RAM at full resolution, open a coarse view and navigate while metadata and reads are deliberately delayed. Input handling and selecting another image continue before those reads finish. Trace requested regions/levels to show first display does not require the whole volume/time series. Record machine, dataset, cache state, event-loop delays, peak process/decoded/GPU memory where applicable, and first/useful-view latency; do not invent a passing latency threshold from AGAVE's 100 MB cache setting.
2. Delay request A, select B, complete B, then deliver A's success, failure and partial-result variants. Only B may update pixels, dimensions, coordinates and controls. Exercise image changes plus rapid pan, zoom, channel, plane and time changes. Cancellation must remove obsolete queued requests; completed/stale work must not accumulate across repeated cycles.
3. Inject invalid metadata, an unavailable image, permission-denied reads, corrupt compressed chunks, shard-index/checksum errors, unsupported codec/dtype and a backend read failure. Feedback identifies the affected image and level/region or overlay, distinguishes unsupported from corrupt/unavailable, and permits another valid item. Partially filled buffers must not masquerade as completed data.
4. Check time/control state after a failed new selection: the UI must not label old pixels with the newly requested time/plane. Distinguish any retained previous view or incomplete region visibly. Opening a good item after each failure succeeds without restarting the process.
5. Hash the local fixture tree before and after discovery, viewing, display changes, cancellation and failures. No source metadata/chunk mutation or cache sidecar is created inside it. Session display changes do not get written to `omero` or label metadata.

Include a positive sparse/fill-value case separately from read failures: uninitialized array regions use the declared fill value, not an invented zero or a generic corruption error (Zarr core, S00062:385–396). An absent chunk representing fill and an I/O error such as permission denial are different outcomes. The retrieved core page identifies itself as **3.1** (S00056:56–60); this citation supports the fill-value distinction, not a claim that every 3.1 extension is covered by the pinned reader or required by the initial 0.5 acceptance corpus.

### R5 — Replace “representative filesets” with a traceable interoperability matrix

**Classification: concrete repair. Owner:** Viewer.md:9 “interoperate with filesets from real OME-Zarr 0.5 tools.” **Consumers:** all controls/details/overlays in :5 and acceptance in :11. A public sample index alone cannot satisfy this consumer.

**Evidence:** AGAVE PR #220 reports a “very barebones first try” that “seems to load basically all” conversion-challenge samples, assumes `zarr.json` means OME 0.5, and supplies no pass/fail inventory (S00011). The challenge's top CSV indexes five CSV sources, not five datasets (S00042). One acquired omero-zarr image is OME 0.5 CZYX with paths 0/1/2 and channel metadata (S00019); its first array is uint16, shape `[2,236,275,271]`, regular grid and `sharding_indexed` with bytes + blosc(zstd, shuffle), index bytes + crc32c (S00020). TensorStore's pin documents those codec names (S00013:19–62), which does not prove the complete configuration's pixels decode correctly.

**Concrete replacement/addition to line 11:**

> Maintain a fixture manifest mapping each interoperability claim to producer/version, exact source and metadata/chunk hashes, permitted local-use provenance, metadata features, expected image paths/dimensions/axes/calibration, selected reference pixel regions and expected control/overlay outcomes. Include local copies of real-producer single images, collections/plates and associated labels, supplemented by small controlled edge/error fixtures. Record reader/backend versions and explicit pass/fail/unsupported results. A successful canvas alone does not prove correct slice, dtype, origin or label alignment. Exercise sharded and unsharded Zarr v3, actual codec chains, fill values, ranks, units and transforms; do not substitute a synthetic-only suite for real-producer interoperability.

The verified sample is a concrete seed, **not a completed local fixture or passing runtime test**. Its shard spans the full first-array shape while inner chunks are `[1,1,275,271]`; this is useful for checking whether a plane request reads appropriate shard ranges without requiring a whole-shard decoded allocation. License, pixel references and local mirroring remain to be established before calling it a reusable regression fixture. The report fetched metadata only.

**Acceptance checks:**

1. The manifest has evidence for a real 0.5 single-image producer, a real collection/plate producer and real associated labels; each unresolved row stays explicitly unverified. The omero-zarr seed covers CZYX, the given sharding/blosc/zstd/crc32c combination, anisotropic spacing and optional display metadata. Supplement it with R1–R4's paths, ranks, transforms, units, dtypes and error cases; do not infer collection or label coverage from a filename containing `_labels`.
2. Compare reference decoded values separately from display mapping: uint8/uint16, signed int32 including negative values, finite float32, constant float, NaN/Inf policy, and every supported label integer type. AGAVE's int32 path reaches a converter that interprets all 32-bit data as float (S00008:588–604; S00015:288–299; S00009:30–48). Slide Scout must dispatch by actual dtype/signedness and keep display normalization separate from source-value/label semantics. Raw quantitative measurement/export is not added to the product.
3. Publish the supported codec/dtype/axis/transform representation matrix and actionable unsupported feedback. Unfamiliar extensions cannot silently decode as a familiar codec or default calibration. Any decision to narrow promised interoperability to a subset of otherwise valid real-producer 0.5 filesets requires review under :9; this report does not preapprove AGAVE's dtype whitelist or claim every Zarr extension is supported.
4. Run the manifest on the actual application and supported deployment environments before declaring implementation acceptance. Save expected versus actual results, fixture hashes and backend pin. Remote sample acquisition for a developer's local test corpus does not add remote storage to the viewer's user-facing scope.

### Optional proposals — none approved or incorporated into Plans

All proposals below are governed by **Viewer.md:9, “Additional capability choices require explicit review.”** Their potential consumers are named separately so existing requirements are not mistaken for approval of a particular implementation or interface.

#### P1 — Compare a native TensorStore reader before choosing the application stack

**Classification: product proposal requiring approval.** Potential consumers: local hierarchy opener, background loader, canvas and calibrated details (Viewer.md:5,7), with interoperability acceptance (:11). The Plan does not name a language, toolkit, backend or supported OS matrix.

**Reviewable proposal:** approve a bounded comparison prototype of a C++ read adapter using TensorStore for **local, read-only** arrays, plus a minimal Qt canvas/controller. The adapter takes image-group identity, actual dataset path, typed axis selections and viewport bounds; it returns typed decoded regions, calibration, request identity and structured failures. Keep OME discovery and transforms above the array driver, because TensorStore's Zarr driver does not provide that product contract by itself. Exercise R1–R5's same fixtures and instrument process memory, queued work, cancellation, first-view latency, correctness, build time and packaged size. Compare against the team's alternative reader stack before production selection. Reproduce AGAVE's v0.1.78 as a reference, but select a production version only after a documented change/fix review and rerun; this proposal does not nominate the old pin as current best.

**Benefit:** AGAVE demonstrates a shipped native desktop reader path without a Python/dask array-loading dependency; its release v1.8.0 announces 0.5 support (S00027:1–3; S00049). Its FetchContent pin and TensorStore's enumerated v3 codecs make a reproducible starting point (S00010:32–50; S00013:19–62; S00045). A native adapter may suit desktop packaging and typed region reads, but performance gains remain hypotheses.

**Dependencies:** target OS/toolchain decision; Qt and other redistribution/license review; actual backend release/fix inclusion; codecs/axis/dtype/transform coverage; asynchronous lifetime and cancellation design; local fixture provenance. AGAVE's README lists Qt, CMake, Python build tooling, Perl/NASM and native dependencies (S00027:19–119). A build can use Python even though the read path is native. #395 supplies a real macOS generated-header build report, not a diagnosed universal Qt/TensorStore defect (S00060).

**Tradeoffs/alternatives:** C++ packaging and build maintenance versus potential runtime integration benefits; direct native buffers versus careful ownership/error handling; a pinned dependency's reproducibility versus missing later fixes. A Python/Qt approach remains unevaluated here. Reusing AGAVE's whole-volume conversion or four-channel rendering cap would undermine this Plan's thin, responsive plane browser and is not part of the proposal. Prototype approval and production stack/pin approval are separate decisions.

**Decision evidence:** identical expected-pixel/calibration/label results across candidate adapters; no-crash failure results; measured cancellation/memory/navigation on the intended platforms; build/packaging report and explicit limitations. A successful compile or a codec-name match alone is insufficient.

#### P2 — Initialize channel display and starting view from validated omero metadata

**Classification: product proposal requiring approval.** Existing consumers: channel visibility and time/plane controls (Viewer.md:5); session-local display settings (:9); channel/plane acceptance (:11). The Plan does not specify initial colors, intensity windows, initial time/plane or threshold persistence across time.

**Reviewable proposal:** on first open of an image in a session, use valid `omero.channels` colors/windows, optional active flags/labels, and in-range `rdefs.defaultT/defaultZ` to seed the display and starting selections. Use stable indexed channel labels when optional labels are absent. Treat absent or malformed optional display metadata as a fallback-display condition; do not fail a valid image solely because a label is absent. Validate channel count, six-digit colors, finite ordered window bounds and selector ranges. As a proposed default, use a fixed deterministic channel palette and the implementation's documented finite-data display range when metadata is unavailable; the chosen range policy must handle constant/nonfinite data without division by zero or undefined casts. Preserve the user's overrides while navigating that image during the session; do not silently reset visibility or absolute window values at every timepoint. No source writes or cross-session persistence.

**Benefit:** real datasets carry useful defaults that reduce setup and avoid arbitrary initial views. The acquired omero-zarr seed includes LaminB1/Dapi channel colors and windows plus default Z=118 (S00019:77–113). Omero is an optional transitional convention with required color/window fields when present, not a separate unspecified “0.5 display standard” (S00005:398–430). AGAVE reads channel labels only in its Zarr opener (S00008:183–197).

**Dependencies:** agreed fallback intensity/range and compositing policy, validation of optional metadata, channel identity across time, UI indication of metadata defaults versus user settings, fixtures with missing labels/metadata and invalid defaults. If extra color/LUT/window editors are wanted, that interface is a further explicit choice; the existing visibility checkboxes do not authorize copying AGAVE's entire transfer-function editor.

**Tradeoffs/alternatives:** producer defaults improve familiar rendering but may be stale, saturated or hide channels; a fixed initial display is easier to predict but needs more manual work. Preserving absolute windows supports visual comparison over time; per-timepoint percentile recomputation can reveal changing contrast but changes the appearance of the same intensity. AGAVE's histogram/remap behavior (S00023:102–116) is precedent, not a mandate. Review the proposed preservation/default policy before adoption.

**Acceptance if approved:** load the verified channel metadata, missing-omero and valid-omero-without-label fixtures; assert exact initial channel settings and starting indices or documented fallbacks. Change settings, time and plane, then revisit the image in the same session; retain overrides. Verify zero writes and deterministic new-session initialization. This report does not claim P2 is already required by line 5.

#### P3 — Add a supported automation API only if its value exceeds internal test hooks

**Classification: product proposal requiring approval.** Potential consumer: representative-file and error/cancellation acceptance (Viewer.md:11). No external API, server or Python client is currently required. Automated UI/read tests can be implemented internally without exposing a product service.

**Reviewable proposal:** if scripted end-user or cross-process testing is needed, expose an explicitly enabled local automation adapter for open/list/select/read-status operations. Use stable request IDs; exact image and dataset paths or a checked index-to-path mapping; matching extents/calibration for the selected ROI/level; bounded success, failure, cancellation and disconnect responses. Prefer an internal or local IPC transport for the initial use case. If a WebSocket is selected, bind to loopback by default, define local-client authorization and lifecycle, and require separate review for remote exposure. Do not copy a no-timeout response queue or a command-type number as a per-request identity.

**Benefit:** reproducible selection/error tests and scripted workflows. AGAVE's `load_data_and_get_info` accepts path/scene/level/time/channels/ROI and returns metadata (S00040:954–995), showing a useful test surface.

**Dependencies:** public API scope/versioning, request and buffer lifetimes, deterministic failure propagation, local process permissions, cleanup, and whether screenshots/render export would cross the excluded export boundary. No export endpoint is proposed here. AGAVE sends binary commands and JSON metadata replies; its Python client allows a different URL from the localhost default (S00039:151–205; S00040:990–995; S00029:204–221). Its server listens on Any in NonSecureMode (S00029:69–101). The client has no application timeout on its receive queue and server failures can return without metadata (S00030:34–53,72–90; S00038:655–684).

**Tradeoffs/alternatives:** an external protocol improves reuse but adds compatibility/lifecycle and access-control work; internal test hooks can satisfy the Plan with less product surface. AGAVE server `std::to_string(level)` diverges from GUI resolution through the actual dataset path (S00038:662; S00052:282–298); a naive copied API could fail valid non-numeric paths. Its returned nested dimensions come from `loadDimensions()` choosing the last level while top-level extents come from the loaded ROI (S00008:433–440; S00038:679–741), so success metadata is not automatically a reliable reference oracle.

**Acceptance if approved:** success, bad path, unsupported dtype/codec, non-numeric resolution paths, selected-level/ROI dimensions, concurrent/cancelled requests, delayed responses and disconnects all yield bounded, matched outcomes. Assert that disabled/local-only configuration does not expose an unintended listener. Live AGAVE server behavior and deployment protections were not tested here.

#### P4 — Consider advanced loading controls or time-series preload only after measuring the automatic viewer

**Classification: product proposal requiring approval; recommended to defer pending R4 measurements.** Potential consumers: image loading and time selection (Viewer.md:5,7). Automatic level selection already exists in the Plan; a mandatory manual load dialog would change that behavior.

**Reviewable proposal A:** offer an optional advanced panel for an explicit resolution override, XYZ load-region restriction and an estimate of decoded/process/GPU memory where relevant. Keep automatic viewport-level selection as the default, let the user return to it, and make scope restrictions clear so “hidden channel” is not confused with “not loaded.” AGAVE's guide describes low-resolution-first ROI selection and a GPU estimate, with highest-resolution/all-channels defaults and reload needed for excluded channels (S00014:94–128).

**Benefit/dependencies/tradeoffs:** expert users can constrain expensive data or inspect a consistent resolution; implementation needs valid region/level metadata, memory estimation, a readable override state and tests for coordinate/label consistency. Estimates can be wrong, dialog friction slows browsing, and requiring a reload to reveal a channel conflicts with a smooth visibility control. R4's automatic chunk/plane reads may make these controls unnecessary. If approved, acceptance checks override/reset behavior, exact region coordinates and independently estimated versus observed memory; no AGAVE four-channel limit is imported.

**Reviewable proposal B:** add opt-in, cancellable preloading of selected timepoints with an explicit memory/disk quota and eviction policy. Any cache is outside the source fileset; define identity/invalidation and deletion. #323 requests whole-series caching because repeated stepping is slow (S00059); it does not establish shipped coverage or the best policy for Slide Scout.

**Benefit/dependencies/tradeoffs:** lower repeated-step latency costs RAM/disk, duplicate data, invalidation logic and potentially competing I/O. Compare a bounded neighbor-time cache and no-preload baseline before whole-series preload; never make preload a prerequisite for navigation. If approved, verify measured latency improvement, hard quota/eviction behavior, cancellation and no source changes on the same fixture. Choosing persistent disk storage or controls is additional scope; an internal bounded cache needed to fulfill responsiveness can remain an implementation detail.
