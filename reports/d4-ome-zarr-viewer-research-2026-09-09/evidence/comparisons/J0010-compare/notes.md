## L-9916d9541a47 — Storage performance and responsiveness
Disposition: concrete repair

**Owner and consumer.** Viewer.md:7 already requires background large reads, cancellation after view changes and explained failures. Viewer.md:5 supplies the current level/channel/time/plane/view selection; :11 consumes responsiveness and noncrashing failure behavior. Merely moving a whole-volume allocation to a worker can still exhaust memory or let an obsolete request replace the current display. The missing requirements concern selection-limited work, completion identity, memory bounds and meaningful acceptance evidence.

**Primary storage evidence.** The [sharding specification](https://zarr-specs.readthedocs.io/en/latest/v3/codecs/sharding-indexed/) (S00024, lines 144–206, 232–256) defines one outer-grid chunk as a shard with independently encoded inner chunks, an offset/length index, fill sentinels and an index at the beginning or end (end by default). Range reads can fetch the index and selected inner-chunk bytes. The [Zarr performance guide](https://zarr.readthedocs.io/en/latest/user-guide/performance/) (S00025, 168–206, 293–342) distinguishes read-unit chunk shape from write-unit shard shape and discusses interacting I/O/thread/Dask concurrency. [LocalStore `_get`](https://github.com/zarr-developers/zarr-python/blob/main/src/zarr/storage/_local.py) (S00026, 30–44) reads the whole file only when no byte range is requested; explicit range/offset/suffix requests seek and read part of it. These are mechanisms, not a latency guarantee.

The actual [6001240 intensity array](https://livingobjects.ebi.ac.uk/idr/zarr/v0.5/idr0062A/6001240_labels.zarr/0/zarr.json) (S00017) is CZYX uint16, shape `[2,236,275,271]`, outer shard `[1,10,512,512]`, inner chunks `[1,1,256,256]`, inner bytes(little-endian)+Blosc(zstd, shuffle), index bytes+crc32c. One full XY plane of one channel intersects four inner chunks. The shard index has 40 slots and is `40*16+4 = 644` bytes with these index codecs. These are calculations from metadata/spec, not observed reads. Its [actual label array](https://livingobjects.ebi.ac.uk/idr/zarr/v0.5/idr0062A/6001240_labels.zarr/labels/0/0/zarr.json) (S00019) instead has int8, no sharding, chunks `[1,59,69,136]` and bytes+zstd. The older “uint16 labels with 256³ inner chunks” conflates two different arrays.

**Historical reports do not establish a present format regression.** [zarr-python #1343 comments](https://github.com/zarr-developers/zarr-python/issues/1343#issuecomment-2422543196) (S00027; also comment 2422542961) reran the original ancient sharding example with 3.0.0b0 and reported the slow-read problem gone in October 2024. [#2710](https://github.com/zarr-developers/zarr-python/issues/2710) (S00057) begins with a writing comparison in 3.0.0; a later [June 2025 read report](https://github.com/zarr-developers/zarr-python/issues/2710#issuecomment-2949706320) (S00052) says 3.0.8 unchunked Xarray load was faster while Dask-scheduled load was slower in that environment, with codec/configuration context. [ome-zarr-py #640](https://github.com/ome/ome-zarr-py/issues/640) (S00055) is an auto-sharding writer/rechunking failure, not evidence that readers or explicit sharding fail. The [zarr-benchmark README](https://github.com/zarr-developers/zarr-benchmark/blob/main/README.md) (S00056, 8–18) says planning stage and “does not run yet,” despite a usage section. Preserve it as a design reference, not a verified runnable harness. [ome-zarr-py #232](https://github.com/ome/ome-zarr-py/issues/232) (S00098) reports an 8× conversion-memory increase during pyramid writing; napari #139's dated dependency/scale report is retained as a contextual lead. Neither is a local reader measurement.

Reject the parent's unconditional “LocalStore reads whole chunk files,” “one decode per plane,” “v3 is slower” and “pyramid level is the primary bottleneck” conclusions. The plane/ROI can intersect many XY tiles, chunks spanning unused Z/T/C positions, or sparse fill; codec chain, read coalescing and cache state affect real I/O. Do not infer the producer of sharded data from one writer bug. bioformats2raw's own shard options also contradict a challenge-only producer assumption.

**Concrete replacement behavior for :7.** Represent each request by fileset/image/multiscales entry/level/axis selection/ROI and a view generation. Choose the existing level appropriate for the physical view, and request only the needed spatial region, channels and selected planes/timepoints, subject to unavoidable codec/chunk granularity. On an oversized request, use an available suitable coarser view or explain the resource failure; do not silently alter the requested image identity or write a rechunked store.

On view changes cancel work no longer needed, stop scheduling its further reads and use backend cancellation where supported. Discard obsolete completions even if an in-flight file read or decode cannot be interrupted. Publish pixels, coordinate metadata and displayed selection consistently for the same generation; an old image must not be labeled as the new slider state. Keep only explicitly identified prior content or loading/unavailable regions while replacement data is pending. Handle asynchronous status failures and discard partially written output. Distinguish legitimate missing-chunk fill from missing metadata, unavailable images, invalid indexes, checksum/decode failure and user cancellation. A corrupt chunk must not silently become a scientific zero tile.

Primary [AGAVE FileReaderZarr](https://github.com/allen-cell-animated/agave/blob/9e7b47f7e64f56a5f7cffb317e72486aeb7ebfe3/renderlib/io/FileReaderZarr.cpp) (S00028, 583–606) reads uint8/int32/uint16/float32 and then calls [convertChannelData](https://github.com/allen-cell-animated/agave/blob/9e7b47f7e64f56a5f7cffb317e72486aeb7ebfe3/renderlib/io/ConvertChannelData.cpp) (S00047, 19–49). The latter treats every 32-bit source as float, ignoring the dtype distinction. [VolumeDimensions](https://github.com/allen-cell-animated/agave/blob/9e7b47f7e64f56a5f7cffb317e72486aeb7ebfe3/renderlib/VolumeDimensions.cpp) (S00084, 288–299) confirms int32 is 32-bit/sampleFormat=2 while float32 is 32-bit/sampleFormat=3. These are numeric fixture needs, not reproduced corruption in Slide Scout or a universal defect in TensorStore.

**Replacement behavior for :5/:9:** dispatch conversions by actual dtype and signedness, not bit width alone. Preserve source numeric meaning up to a deliberate display transfer function. Keep transfer settings stable through level/time changes within the session unless the user chooses otherwise; any fallback normalization must handle constant and nonfinite data deterministically. Never run segmentation IDs through an intensity normalization or lossy floating-point identity path. Do not imply that adding a raw-intensity readout UI is already scoped; exact source values are needed for internal correctness tests regardless of what the details panel displays.

Use registration/context to determine label intent, not just dtype or filename.

**Label repair and acceptance:** retain exact signed/64-bit IDs through decode, color lookup and metadata association; use sparse identity mappings so an enormous ID does not imply a palette allocation proportional to the maximum value. Opening must not scan all full-resolution pixels to discover every unique label. Test explicit RGBA alpha (128 means 128/255 when normalized), absent colors, singleton C/T label dimensions and missing optional metadata. Use categorical sampling that cannot invent intermediate label IDs; nearest-neighbor is the proposed rendering rule, with boundary appearance reviewed as part of display policy. Do not silently hide a registered valid label solely because image-label is absent. Exact pixel correctness and sparse-ID scalability have not been runtime measured.

**Display/property proposals requiring approval:** recommend labels available but initially hidden, explicit metadata colors when present, and deterministic fallback colors when absent; make zero/background treatment deliberate. Benefit: overlays are discoverable without obscuring the image; dependencies: categorical renderer, exact ID mapping and visibility state; tradeoff: hidden defaults reduce immediate visibility and fallback colors may lack scientific meaning. A virtualized label-property table would expose the heterogeneous properties already present, but is additional UI beyond :5: benefit is contextual inspection, dependencies are exact ID joins and bounded table loading, tradeoffs are clutter/memory and no inference of clinical meaning. The real [source-image group](https://livingobjects.ebi.ac.uk/idr/zarr/v0.5/idr0062A/6001240_labels.zarr/zarr.json) (S00011), [labels container](https://livingobjects.ebi.ac.uk/idr/zarr/v0.5/idr0062A/6001240_labels.zarr/labels/zarr.json) (S00016) and [label-image group](https://livingobjects.ebi.ac.uk/idr/zarr/v0.5/idr0062A/6001240_labels.zarr/labels/0/zarr.json) (S00018) directly demonstrate the three different roles. The label array is int8 (S00019); the intensity array is uint16 (S00017).

The parent prose's root-level series, image-level labels list, sibling-outside-image labels directory, mandatory `image-label`, and mandatory `.zarr` suffix for every image are incorrect. Series belongs to the OME subgroup; labels belongs inside the source image, beside its resolution arrays. Image-label is SHOULD, optional source.image defaults to `../../`, and arbitrary nested image names are shown in the spec. The numeric example `bioformats2raw.layout: 3` is valid evidence; quoted prose “3” must not become a string-only parser rule. Consecutive numbering is scoped to the transitional bf2raw layout without plate/series, not all Zarr groups. Reader awareness of multiple images is SHOULD and choosing an image is MAY; the Plan's own image-list promise supplies the product reason to enumerate collections. Multiple entries in one `multiscales` list are a distinct case for which the spec explicitly shows first-entry fallback (388–397).

**Concrete replacement discovery behavior for :5.**

1. Inspect the selected local directory's node type, storage version and namespaced OME version/role; support extensionless image and collection directories. Classify image, bf2raw collection, plate, well and labels-container metadata separately. A resolution array or labels container is not an additional intensity image. Unknown versions and non-OME wrappers receive an explanation; unrestricted folder indexing is a separate proposal below the aggregate parent.
2. For bf2raw layout, plate metadata takes precedence. Otherwise resolve `OME/zarr.json.attributes.ome.series` paths relative to the collection, preserving list order and using XML only for supplemental identity/name information. If there is no series list or plate, support the documented consecutive `0`, `1`, … fallback even when optional XML is absent. Do not manufacture group paths from XML Image-ID suffixes. Invalid/missing declared links remain visible as failures rather than disappearing from a complete-looking list. Nonconforming sparse/custom layouts without a usable map need explicit diagnosis, not a claim of complete discovery.
3. For plates, follow actual `plate.wells` paths and verify rowIndex/columnIndex/path agreement. For each well, use all `well.images` entries with their acquisition IDs, instead of assuming field `0` or a representative well describes every image. Preserve sparse wells and distinguish unlisted wells from listed paths that fail. Keep plate/well/acquisition/field identity available in the existing image list; no spatial mosaic is implied.
4. For an image, follow the ordered `multiscales[*].datasets[*].path` values as array paths and retain multiscales identity separately from level identity. Read the source image's nested `labels/zarr.json.attributes.ome.labels` paths relative to that labels group, including intermediate groups. Registered integer label images remain discoverable when optional `image-label`, colors/properties or source.image are absent. Resolve explicit source.image relative to the label image; honor the specified default when omitted, and report a missing/ambiguous association without overlaying against an invented parent. An isolated integer image does not by itself establish segmentation intent.
5. Check source/label axis correspondence, integer dtype, per-level calibration and required level count before asserting an aligned overlay. Singleton label dimensions may correspond to irrelevant source dimensions, as in the real two-channel image/one-channel labels. Apply each grid's own calibration; do not force equal channel counts or reuse intensity-array chunks. Labels can be unavailable while the source image and other items remain browseable. Errors identify the image/label and offending link or metadata role. No source metadata is repaired in place.

**Consumer acceptance for :11.** Fixtures must cover a plain extensionless 0.5 image; a mapped nonnumeric/nested bf2raw series list with XML IDs that differ from paths; no-XML numbered fallback; a root with both layout and plate keys (plate wins); sparse wells, a non-`0` field and multiple acquisitions; arbitrary level paths such as `s0`; a nested label path; and labels lacking optional `image-label`/source/colors. The fetched 6001240 specimen must yield one source image with an associated label `0`, never a spurious image entry for the `labels` container. Test broken array/series/label links, duplicate or inconsistent row/column metadata, mismatched dimension_names and floating-point labels. Good sibling images stay selectable and failures are explained. Test valid overlays with label C=1/source C=2 and equal level counts; wrong levels or unverifiable geometry must not look aligned. Metadata-only recognition is not evidence that pixels decode.

**Reader precedents and limits.** Pinned [napari reader](https://github.com/ome/napari-ome-zarr/blob/1638ac76f312562d140410259367a091b542d780/napari_ome_zarr/ome_zarr_reader.py) (S00038, 178–202, 267–283, 341–365, 572–578) provides useful role dispatch, but its checked path uses the first multiscales/first transform, XML Image-ID suffixes for bf2raw and requires optional image-label. These are source-level fixture candidates, not runtime failure observations. Pinned [vizarr ome.ts](https://github.com/hms-dbmi/vizarr/blob/be7ccc260e848a2829873c8746f32b4f43599435/src/ome.ts) (S00034, 321–347) unwraps attrs for a label image but reads `attrs.labels` directly from its container, unlike the actual 0.5 `attrs.ome.labels`; Zarrita attribute behavior and an end-to-end fixture remain necessary before declaring an observed vizarr defect. [AGAVE FileReaderZarr.cpp](https://github.com/allen-cell-animated/agave/blob/9e7b47f7e64f56a5f7cffb317e72486aeb7ebfe3/renderlib/io/FileReaderZarr.cpp) (S00028, 224–231, 361–425) supports scene selection through multiscales entries; it is not evidence that every current viewer only opens the first. That image-group reader does not provide this plate/series/labels traversal.

**Unresolved standard conflict.** The real [190129 plate](https://livingobjects.ebi.ac.uk/idr/share/ome2024-ngff-challenge/idr0090/190129.zarr/zarr.json) (S00015) has name `190129`, contrary to older prose, but no nested plate.version. The spec prose requires it (550–551); the [plate schema](https://ngff.openmicroscopy.org/0.5/schemas/plate.schema) (S00036 raw JSON) and spec examples do not. Preserve the normative requirement and the incompatibility together. Proposal for review: allow otherwise well-defined plate navigation with an explicit compatibility warning for this specific omission, without claiming full conformance; strict rejection remains an alternative. Benefit: real-tool interoperability; dependencies: semantic diagnostics and a bounded exception rule; tradeoff: leniency can hide malformed data if warnings are lost. The schema alone cannot approve this policy.

**Other UI proposals requiring approval.** A named multiscales-entry chooser would prevent hidden alternative representations: benefit is access beyond the documented fallback; dependencies are separate entry/level identity and reset of per-image state; tradeoff is added choice and potentially incompatible geometries. A plate grid or well-field mosaic could speed HCS browsing, but needs independent thumbnail scheduling, acquisition choices and clear separation between a display grid and measured physical positions; it costs memory and can mislead about registration. The repaired list-based discovery needs neither mosaic construction nor a public remote service. Initial label visibility, fallback palette and background-label treatment remain explicit display-policy proposals under the aggregate parent.

## L-580ffdee048c — TensorStore backend and version choice
Disposition: product proposal requiring approval

**Owner and consumer.** Viewer.md:9 owns 0.5 real-tool interoperability and review of material capability choices; :5 consumes decoded arrays plus NGFF axes/calibration, :7 consumes responsive cancellation/error behavior, and :11 verifies these outputs. The complete Plan chooses no language, toolkit or array backend. TensorStore is a viable candidate; adopting it or copying AGAVE's version is not already approved.

**Versioned primary evidence.** [AGAVE renderlib/io/CMakeLists.txt](https://github.com/allen-cell-animated/agave/blob/9e7b47f7e64f56a5f7cffb317e72486aeb7ebfe3/renderlib/io/CMakeLists.txt) (S00041, 32–44) pins **v0.1.78** and tarball SHA256 `f59667a32357b8cc0c752429927ad97654f6a67c7d3d62b9efea902c6798d473`. The [tagged codec directory](https://github.com/google/tensorstore/tree/v0.1.78/tensorstore/driver/zarr3/codec) (S00043) and [compared revision fe8acc091512fd58e98aeea9b842865d85e61ed6](https://github.com/google/tensorstore/tree/fe8acc091512fd58e98aeea9b842865d85e61ed6/tensorstore/driver/zarr3/codec) (S00045) both contain bytes, blosc, crc32c, gzip, zstd, transpose and sharding_indexed; the latter adds a crc32c test. This maps the S00017 image and S00019 label chains to candidate implementations. It is not a successful decode, proof of integrity checking at every layer, or “all standard codec” coverage.

A concrete post-pin change is [0ad6ce118cce4af052a8ab246da577554c0a72e0](https://github.com/google/tensorstore/commit/0ad6ce118cce4af052a8ab246da577554c0a72e0) (S00033, 3 August 2026): it fixes Read/Write/GetStorageStatistics output permutation for transpose combined with sharding and adds a 3D cyclic-permutation read/write test using order `[1,2,0]`. The pin predates this fix. It does not implicate the real S00017 chain, which contains no transpose. [Tagged metadata.cc](https://github.com/google/tensorstore/blob/v0.1.78/tensorstore/driver/zarr3/metadata.cc) (S00042) versus [the compared newer file](https://github.com/google/tensorstore/blob/fe8acc091512fd58e98aeea9b842865d85e61ed6/tensorstore/driver/zarr3/metadata.cc) (S00040) also demonstrates expanded structured/raw-byte dtype and fill handling. This is a bounded version comparison, not an exhaustive changelog/cancellation audit or a recommendation to ship an untested HEAD.

**Rank hypothesis corrected.** The pinned [Read contract](https://github.com/google/tensorstore/blob/v0.1.78/tensorstore/tensorstore.h#L638) (S00029, 638–673) explicitly aligns/broadcasts source to target through AlignDomainTo. [alignment.h](https://github.com/google/tensorstore/blob/v0.1.78/tensorstore/index_space/alignment.h#L79) (S00030, 79–124) right-aligns dimensions if either side is unlabeled and allows unmatched singleton source dimensions/extra target dimensions. AGAVE retains selected T/C axes at length one and uses `[1,1,Z,Y,X]` as target (S00028, 543–596). Canonical YX, ZYX, CZYX, TZYX, TCYX and TCZYX selections can therefore broadcast; “rank below five necessarily fails” is rejected. That source reasoning does not validate arbitrary NGFF axis names/order, custom axes or out-of-bounds selections. Metadata-driven axis meaning belongs in the application, not a literal TCZYX assumption.

**Backend boundaries that the application must own.**

- Tagged metadata accepts omitted dimension_names and only assigns unique names as domain labels (S00042, 398–417, 598–611). NGFF nevertheless requires names matching axes; array-open success is not NGFF validation. The parser supports a regular chunk grid, permits an empty storage_transformers list but rejects nonempty ones (423–442), and rejects unknown top-level extension fields unless marked must_understand:false (309–323). Ordinary user attributes are different. These concrete restrictions disprove universal v3 support without requiring every extension in the initial viewer.
- Read yields a future/status and may leave the destination partially written on failure (S00029, 643–645, 672–673). [Result::value](https://github.com/google/tensorstore/blob/v0.1.78/tensorstore/util/result.h#L434) (S00031, 434–457) terminates the process on error; [Future](https://github.com/google/tensorstore/blob/v0.1.78/tensorstore/util/future.h) (S00032) routes value through result().value(). AGAVE's unchecked Read(...).value() calls (S00028, 585–596) therefore have a conditional termination path, not automatic exception recovery. No crash was reproduced here.
- Read supports progress callbacks and batching (S00029, 650–656). Cancellation is cooperative when futures/ready callbacks no longer need a result, with producer cancellation hooks (S00032, 229–238, 326–340, 582–586); it is not guaranteed immediate interruption of I/O/decompression. Buffer lifetime and discarded stale completions must be managed above the backend.
- Tagged [file_key_value_store.cc](https://github.com/google/tensorstore/blob/v0.1.78/tensorstore/kvstore/file/file_key_value_store.cc) (S00044, 396–405, 450–487) supports byte-range reads, optional mmap and range coalescing (max_extra_read_bytes=255). “Native local reader must read whole shard” is unsupported. AGAVE's 100,000,000-byte cache pool (S00028, 484–493) does not include its selected-volume destination/native temporary allocations (510–524) or all GPU/staging memory.
- For the optional legacy direction, pinned [v2 schema](https://github.com/google/tensorstore/blob/v0.1.78/tensorstore/driver/zarr/schema.yml) (S00062) identifies `zarr2`/`zarr` and dot/slash dimension_separator; [driver.cc](https://github.com/google/tensorstore/blob/v0.1.78/tensorstore/driver/zarr/driver.cc) (S00061) opens `.zarray` metadata. An absent `.zmetadata` is not a v2 failure. A consolidated-only store and arbitrary packed kvstore need separate verification; there is no demonstrated v2 sharding_indexed or documented “consolidated” driver switch here. Legacy 0.4 reading remains a review choice, not required by :9's 0.5 boundary.

**Reviewable backend proposal.** Evaluate a release-pinned TensorStore version containing the demonstrated transpose/sharding correction behind a read-only array adapter, alongside a version-pinned zarr-python stack or another independently verified v3 reader. Keep discovery, NGFF validation, transforms, selection identity, label semantics and display conversion outside backend-specific code. The adapter should return typed arrays/status/progress, accept declared string paths and bounded selections, use explicit read/open modes, and integrate with the generation/cancellation contract under L-9916d9541a47. Do not adopt AGAVE's unchecked value calls, fixed literal-axis logic or whole-selected-volume policy as requirements.

Benefit of TensorStore: native selective/range reading and asynchronous primitives with the observed codecs already represented. Dependencies: native build/package distribution for the chosen platforms, codec linkage, lifecycle integration and pixel-conformance fixtures. Tradeoffs: C++ build/update burden and application-side NGFF work versus Python ecosystem reuse and its runtime/dependency/threading complexity. A zarr-python alternative must account for actual package floors (ome-zarr-py requires Python >=3.12 at S00054; napari plugin >=3.11 at S00059) and cannot inherit every advertised release feature through an older reader API. No platform, dependency or backend commitment is made by this report.

**Acceptance before selection.** Check both sharded uint16 intensity and unsharded int8 labels, including selected numeric pixels, CRC corruption and fill chunks. Use a cyclic transpose+sharding 3D fixture to discriminate the old pin from a fixed candidate; equal codec names are insufficient. Exercise rank 2–5, arbitrary valid axis names, singleton axes, custom-axis diagnosis and out-of-range selections; compare exact dtype values, not only successful Open. Check required NGFF dimension_names/axes equality even when the backend accepts the array. Inject asynchronous decode failure and cancellation and verify no process termination, partially valid frame or use-after-free; confirm bounded retained memory, real byte-range behavior and source-tree immutability. Measure cold/warm UI workloads on the same hardware/corpus using the performance gate above. Unknown codec/grid/transformer/dtype must have explicit unsupported feedback.

Still uncertain: decoded pixels and cancellation behavior for the chosen packaged version, target-platform build maturity, consolidated-only support, actual memory/latency and coverage beyond the bounded inspected changes. These are retained next-evidence requirements, not reasons to discard the native-backend lead or claim it already passes acceptance.
