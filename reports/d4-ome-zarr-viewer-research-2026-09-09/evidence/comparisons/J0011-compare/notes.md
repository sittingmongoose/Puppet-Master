### D1 — Recognize nodes and discover the images in a fileset

**Comparison.** Owner: `Viewer.md:5`, “opens a local OME-Zarr 0.5 fileset and lists the images it finds.” Consumers: image selection and associated overlays in the same line, recovery at line 7, image-discovery acceptance at line 11. The intent already covers multiple images. The missing contract is how fileset, image group, pyramid array and labels container differ; a flat list is sufficient, so a full plate dashboard is not required by this repair.

**Evidence.** NGFF 0.5 §2 (S00003:149–156) puts metadata and version in `attributes.ome`, with a consistent metadata version throughout the hierarchy. §2.2.3 (261–275) specifies plate precedence, `OME/series`, and the consecutively numbered image fallback, and says readers SHOULD make multiple images known. §2.4 (298–307,388–397) distinguishes entries of one multiscales list from their resolution datasets. §2.6 (431–474) defines labels discovery and source association. AGAVE's `loadNumScenes` counts one selected group's `multiscales` entries (S00006:223–231); its reader opens paths from that group but does not implement this fileset hierarchy discovery (360–425). Sampled JAX `3722.zarr` is a `bioformats2raw.layout:3` root (S00021), and IDR `190129.zarr` is a plate (S00022). These are concrete layouts, not hypothetical directory naming conventions.

**Concrete replacement behavior for the line-5 open/discovery contract.** Inspect local `zarr.json` as node metadata; validate Zarr format/node type separately from the OME namespace and metadata version. A generic Zarr v3 node is not automatically OME-Zarr 0.5. Keep the chosen fileset and selected image-group path distinct. For a direct image, expose its multiscales alternatives and named/relative resolution paths. For a collection, follow plate/well image references when plate metadata is present; otherwise use declared `OME/series` or the specified numbered-image fallback for a bf2raw collection. Resolve each dataset path relative to its image group. Discover label images through the associated labels list, including intermediate groups; do not list the labels container as a pixel image. Preserve image identity and enough relative path/well/field context to distinguish otherwise identical names. Discovery must remain bounded/cancellable; a broken reference must identify the item and leave other discovered images selectable.

**Acceptance checks.** A local image root, two-image bf2raw collection with explicit series, numbered fallback, and plate with multiple wells/fields produce the expected choices and stable identities. A plate plus bf2raw metadata follows the plate hierarchy. Distinguish multiple multiscales entries from their resolution levels and separate image groups. Use arbitrary nonnumeric dataset paths, nested labels paths, duplicate display names, an unavailable referenced image, and a generic v3 group with no OME image metadata. Assert no silent first-image-only result, no attempted volume read of the collection root, and no metadata/data writes. The locator checks under L-09ceb3cfac5e also apply.

### D2 — Axis semantics and complete calibration

**Comparison.** Owner: dimensions/units/coordinates and time/plane/level controls at `Viewer.md:5`. Consumers: the details panel, selected canvas position and label overlay in line 5; calibrated-coordinate and aligned-overlay acceptance at line 11. “Shows units and coordinates” does not establish their mapping across levels, crop offsets or time.

**Evidence and conflict resolution.** NGFF §2.1/2.4 requires unique axis names, correspondence to array dimensions, matching array `dimension_names`, and type order; names themselves are arbitrary (S00003:168–174,299–307). Three spatial axes SHOULD be zyx in the stated anisotropic case, not a universal MUST for literal axis names. Transform lists apply in order (293), dataset transforms require exactly one scale and permit one translation **after** scale, and optional image-level transforms apply afterward (308–315). AGAVE instead uppercases names, slices by T/C/Z and assumed Y/X indices, reads only `dataset.coordinateTransformations[0].scale`, and chooses a single spatial unit (S00006:234–351,400–415,562–580). Its time conversion supports a subset and defaults unrecognized time units to seconds (S00044:246–268). Thus valid translations, enclosing transforms and per-axis units are supported correctness concerns. The older “valid translation-first 0.5 store loses calibration” example is rejected: that ordering is nonconforming.

**Concrete replacement behavior.** Bind controls and slices to validated metadata dimension indices, preserving names, types, shape and units per axis. Absent T/C/Z dimensions must not shift another axis's meaning. Preserve the actual displayed-plane mapping in the details panel; never silently relabel arbitrary axes as conventional letters. For data index vector `p`, compose dataset and multiscales transforms in their specified order: with scales/translations at both levels, `q = S_m(S_d p + T_d) + T_m`. A cropped read uses the index in the original array, including the crop origin. Compute coordinates and overlay registration through this same mapping at every pyramid level. Retain physical units independently for each axis; convert only recognized compatible units. Missing units mean calibration is unspecified, not micrometers or seconds. Malformed transform lengths/order or mismatched dimension names require an explicit diagnostic, not silent zero origins or reordered transforms. Custom axis semantics that cannot be interpreted remain an identified capability limit; arbitrary spelling of valid supported axis types is not itself an error.

**Acceptance checks.** Use index `(2,3)`, dataset scale `(2,4)`, translation `(10,-6)`, image scale `(3,0.5)` and translation `(1,8)`; displayed metadata-space coordinate must be `(43,11)`. The same physical position reached at another resolution or through a crop must agree. Check mixed spatial units, nonzero time translation, `kilosecond`, missing units, arbitrary axis names, legal different spatial ordering, and matching/mismatching `dimension_names`. Use conventional YX, TYX, CYX, TCYX, ZYX, TZYX, CZYX and TCZYX fixtures and compare actual selected values/coordinates, not shape alone. Reject translation-first as a negative conformance fixture. General custom-axis/orientation UI is a separate optional product choice, not implied by these checks.

**Rank conflict resolved against the backend contract.** AGAVE does allocate `{1,1,Z,Y,X}` after length-one T/C slicing (S00006:562–596), but TensorStore `Read` aligns/broadcasts to its target (S00037:638–645). Default alignment is `all` (S00039:50–51); an unlabeled target right-aligns dimensions and permits unmatched singleton source dimensions (S00038:79–124). The conventional lower-rank cases are therefore alignable. Reject “fixed target rank necessarily fails on rank <5.” End-to-end AGAVE pixel correctness and arbitrary-axis behavior remain unverified, which is why the fixtures above still matter.

### D3 — Preserve numeric types and label meaning

**Comparison.** Owner: channel viewing and associated label overlays at `Viewer.md:5`. Consumers: aligned overlays and channel/plane acceptance at line 11; unchanged source/session-local display at line 9. Source immutability alone does not prevent an in-memory type conversion from corrupting scientific meaning. No explicit supported-dtype matrix is present.

**Evidence.** AGAVE accepts `int32` alongside uint8/uint16/float32 (S00006:585–600), but calls a bit-width conversion that explicitly assumes all 32-bit input is floating point and reinterprets it as float (S00054:30–48). This is a source-supported int32 type-confusion defect. Float32 is min/max remapped to uint16; constant ranges and non-finite values have no explicit guard in that function, but their runtime outcomes were not measured. NGFF labels are integer arrays, including signed and 64-bit types (S00003:438–439); label-value keys must retain integer identity, source paths are relative, and provided RGBA colors SHOULD be used (461–474). The actual IDR label array declares int8, absent from AGAVE's whitelist (S00029).

**Concrete replacement behavior.** For every supported dtype, decode according to complete dtype and byte-order metadata, not bit width alone. Preserve signedness and value identity through the data pipeline; keep display mapping separate from scientific samples and label IDs. Preserve large integer labels through lookup without converting IDs through a lossy floating-point representation. Render labels categorically (nearest-neighbor sampling or an equivalent method that cannot invent intermediate IDs), register through image/label transforms and source associations, and respect compatible singleton dimensions. Validate label/image level-count and shape compatibility; do not silently line up different pyramids by list index. An unsupported dtype or invalid label association is an item-specific diagnostic while the source image remains usable. Define safe finite display normalization for supported constant/non-finite float input; no division-by-zero path or invented calibrated intensity claim. A raw pixel-value inspector is not required by the existing details-panel promise.

**Acceptance checks.** For each declared supported type, compare decoded known samples against an independent expected-value oracle. Include negative int32 values (never float-reinterpreted), uint16 above 255, float32 constant/negative/non-finite cases, and signed integer labels. Exercise distinguishable label IDs above the exact range of the renderer's float type if those integer types are supported; otherwise verify the declared unsupported result. Check zero labels with explicit nontransparent RGBA (the spec does not universally reserve zero as transparent), nested source paths, singleton C, label edges under zoom, and mismatched level counts. Verify original file hashes and that channel/window adjustments change only session display state.

**Material support/display choice — product proposal requiring approval.** Establish an explicit initial support matrix before claiming general interoperability: recommended candidate image types uint8/uint16/int8/int16/uint32/int32/float32/float64, with all eight NGFF integer label types represented by exact IDs; extensions and other types explicitly classified. This breadth is a proposal, not an approved Plan requirement or a claim about a chosen backend. Benefit: avoids silently inheriting AGAVE's narrow whitelist. Dependencies: decoder support, renderer conversion/lookup design, independent fixtures and resource measurements. Tradeoff: wider dtypes increase conversion, large-ID and test complexity; a narrower release would knowingly exclude valid filesets and must be reviewed rather than presented as full coverage.

Omero colors/windows/active flags and default T/Z are a related **product proposal requiring approval**: initialize valid session display from supported optional metadata, use documented fallbacks when absent/malformed, and retain explicit user overrides across navigation. Benefit: reproducible channel interpretation and useful first view. Dependencies: numeric/display separation, range validation and precedence rules. Tradeoffs: malformed real-world metadata, surprising writer defaults and more display-state complexity; compare this with simple deterministic session defaults. NGFF §2.5 specifies required fields *when optional omero is present* (S00003:398–430), not a universal reader obligation to implement all OMERO rendering modes. AGAVE's reader consumes labels only (S00006:160–198). Using supplied label RGBA follows a separate reader SHOULD in §2.6; honoring it is recommended for the existing overlay capability, without adding a label-property browser or histogram editor.

### D4 — View-scoped reads, level selection and cancellation

**Comparison.** Automatic available-level selection and channel/time/plane controls are already owned by `Viewer.md:5`; background reads, navigation responsiveness and cancellation are explicit at line 7. Consumers are the canvas/controls and line-11 large-data acceptance. No feature proposal is needed to honor those existing promises. What is missing is request identity, read granularity, stale-result handling and bounded resource behavior.

**Evidence.** AGAVE reads a whole selected XYZ region at one time for each selected channel (S00006:474–604); documented load settings provide level, ROI, initial time, channel exclusions and a GPU estimate (S00042:98–128). The timeline calls the reader synchronously (S00043:78–116), and the docs warn of whole-volume loading on slider release (S00042:723–739), consistent with open #84/#323 (S00045/S00046). TensorStore exposes futures, progress and batches (S00037:638–705); #228 explains that immediately awaiting `.value()` serializes independent reads and that aggregation is not guaranteed merely by launching futures (S00036). Thus AGAVE's behavior is an application pattern, not an unavoidable backend limitation. “No caching” is false: there is a 100 MB TensorStore context (S00006:485) and a path-keyed preloaded-image map (S00060:15,68–95).

**Concrete replacement behavior.** Perform metadata discovery/open and image reads off the interaction thread. Select available pyramid arrays from metadata and the current view, preserving physical position across a level change. Schedule bounded regions/planes/chunks needed by the latest view and channel/time selection; compressed chunk/shard granularity may require extra bytes, but a small view must not mandate decoding the whole volume or all times. Include fileset, image/multiscales identity, level, region, channel/time/plane and metadata generation in request/cache identity. On selection change, cancel queued obsolete work, propagate cancellation to active operations where supported, stop additional obsolete work at the next cancellable boundary and prevent late completions from replacing the newer view. Keep buffers alive until asynchronous consumers finish, then release them. Bound in-flight buffers, decoded cache and display/GPU allocations as well as backend cache; choose documented budgets from measurements rather than treating AGAVE's 100 MB cache as a total memory bound. Reader handles are read-only, and all cache/display changes remain outside source files.

**Acceptance checks.** With delayed local reads, request A then B and allow A to complete last: only B may update canvas, coordinates, controls or error state. Cancel while reading and during metadata discovery; observe UI event handling and verify no further obsolete requests are submitted after cancellation is observed. Navigate channel/time/plane/level rapidly and return to a view with a different ROI to detect incorrect cache reuse. A synthetic huge shape at fixed viewport must not cause allocations proportional to the complete volume. Document peak CPU/GPU/in-flight memory and input-event/cancellation latency against agreed test-hardware limits; the Plan has no numeric thresholds, so specific values require review, not invention here. Read a store mounted read-only and compare a before/after hash manifest. A low-resolution preview or batched reads are implementation options; full-series preload/playback and a persistent disk cache are separate product proposals discussed under L-eff66a7b89e1.

### D5 — Recoverable, correctly classified read failures

**Comparison.** The owner at `Viewer.md:7` already requires failures to identify the image/data and allow another selection; line 11 consumes it as understandable feedback rather than a crash. Repair the stages and state guarantees, not the overall error-UX goal.

**Evidence.** AGAVE checks many metadata/open results (S00006:102–127,389–391,495–499), but transform/read `.value()` calls are unchecked (564–596). Pinned TensorStore `Future::value()` delegates to `result().value()` (S00051:861–889), whose non-OK contract terminates the process (S00052:434–462). This is a supported failing-path consequence, not a claim that every AGAVE open failure crashes. `Read` may partially write its target on error (S00037:643–645). Zarr core fill semantics and the sharding missing-inner-chunk sentinel distinguish intentionally unstored fill data from I/O/corruption (S00041:385–392; S00047:190–195).

**Concrete replacement behavior.** Check parse, open, transform and asynchronous read outcomes before publishing data. Attach the selected image/array/level and stage to diagnostics: unsupported OME version/node/type/codec, malformed metadata/coordinates, unavailable local object, or actual read/index/decompression/checksum failure. Never publish a partly written target as a successful image; retain an explicitly identified previous view or show the selected region as unavailable while leaving navigation active. Honor declared fill values for absent chunks and missing inner chunks; do not replace checksum/decode errors with fill or call normal sparse storage corrupt. Ignore stale errors from cancelled requests just as stale pixels are ignored. No uncaught exception/process termination from malformed external data.

**Acceptance checks.** Distinguish generic v3 metadata from unsupported OME version; malformed JSON from a missing array; valid absent chunk/shard and inner-chunk sentinel from corrupted bytes/index/checksum; and unsupported codecs from unreadable paths. Inject a failure after part of a target is written and verify no successful frame is published. One failing image/level/label must leave alternate items selectable; cancellation must not display a misleading corruption error. Acceptance should examine diagnostic context and recovery, not assert one implementation's exact message string.

### D6 — Backend/codec/toolchain compatibility

**Comparison.** `Viewer.md:9` owns interoperability with real 0.5 tools; line 11 consumes it through representative fixtures. No language, UI toolkit, TensorStore dependency or codec profile has been selected in the Plan. NGFF permits Zarr features and extensions (S00003:68–72), so supporting several codecs does not justify a claim to read every possible 0.5 fileset.

**Disposition within the aggregate: product proposal requiring approval for the backend; concrete repair for truthful compatibility evidence.** Record the actual reader/backend revision, compiler/platform, declared dtype/grid/key/codec support and tested chains with every compatibility result. Detect an unsupported required encoding before rendering instead of silently guessing. Validate existing arrays in read-only mode. Upgrades must rerun affected fixtures; absence of open issue reports and tracker closure counts are not acceptance evidence.

**Reviewable backend proposal.** Evaluate TensorStore behind a local-reader boundary as one candidate; do not adopt AGAVE's pin, Qt stack or volume renderer automatically. Benefit: an existing C++ implementation of Zarr3, sharding, codec composition and asynchronous read APIs. Dependencies: approved language/platform choice, reproducible dependency pin/hash, packaging/compiler feasibility, error/cancellation integration and the corpus below. Tradeoffs: build size/time and dependency maintenance; source/API support may exceed actual tested combinations; unknown extensions still need explicit outcomes. Compare a newer reviewed TensorStore revision with v0.1.78 as a reference and with the project's eventual alternative decoder on the same local fixtures. A limited read-only spike producing correctness, memory, latency and build results is the decision artifact. No implementation or dependency change is approved by this report.

**Evidence.** Current AGAVE CMake FetchContent pins v0.1.78 with a SHA256 (S00058:32–44), while the #220 merge and v1.8.0 pin v0.1.71 (S00049/S00050:35–38). Its March 2025 “basically all” statement (S00048) therefore cannot establish v0.1.78's exact tested corpus. Pinned TensorStore schema documents regular grids, bytes, transpose, sharding_indexed, crc32c, gzip, blosc and zstd (S00040). These are supported chain candidates, not successful runtime decodes here. Optional consolidated metadata exists in Zarr v3 (S00041:550 onward); the older contrary claim is rejected. The pinned v2 schema/binding documents `metadata_key` (default `.zarray`), not the handoff's asserted `consolidated` option (S00133:105–114; S00134:143–154); that claimed switch is not adopted as an implementation requirement. Whether to consume consolidation as an optimization is deferred until the chosen backend and fixtures justify it.

**Acceptance checks for any chosen backend.** Exercise actual dtype/codec chains, default and v2-style chunk keys, regular unsharded arrays and sharding with edge shards, both index positions and checksums; verify native sample values against an independent oracle. Test unsupported required extensions with useful feedback, compiler/platform build reproducibility, read-only opening, partial errors and lower-rank array alignment. Do not require Slide Scout to write arrays or add remote drivers to reproduce unrelated backend creation/network issues.

### D7 — Shard indexes, read amplification and resource limits

**Comparison.** Owner: responsive large-data/background reads at `Viewer.md:7`, with automatic levels in line 5. Consumer: line-11 large-dataset interaction check. The Plan's “large dataset” alone does not select a workload that reveals shard-index cache churn or amplification when reading a plane. This is an independent performance-acceptance repair even if pixels decode correctly.

**Evidence.** TensorStore #178's maintainer describes 1,531 roughly 10 MB indexes, requiring over 15 GB to retain the working set, with repeated index reads otherwise; the reporter improves on non-network storage but remains limited on the HPC mount (S00034, comments 2248991802 and 2253287777). It is a workload explanation, not a closed bug universally fixed by an upgrade. A local filesystem path can be a network mount without adding remote-storage APIs to the product. Zarr sharding permits individually accessed inner chunks (S00047:74–95), so large shards do not necessarily mean all shard bytes are read. Sample JAX shards are `[1,3,1,32768,32768]` with `[1,3,1,1024,1024]` inner chunks (S00026); the IDR time series uses `[10,4,25,507,507]` versus `[1,1,1,507,507]` (S00031). They stress different locality and cross-channel/time costs.

**Concrete replacement behavior/acceptance.** Extend line-11 large-data acceptance to cold/warm pan, zoom, plane, channel and time jumps across shard boundaries on documented local disk and, when available, a filesystem mount. Record bytes read versus selected decoded/displayed bytes, index/cache hits and misses, total memory (not just one cache), in-flight request count, first useful frame, UI latency and cancellation latency. At a fixed viewport, compare increasing dataset extent and distinct shard working sets; enforce the agreed memory/queue bounds and correct latest-view results. Include both index locations, edge chunks and corrupt index handling. These measurements choose cache budgets, demand reads, bounded prefetch or batching; they do not authorize whole-volume/time-series caching or rewriting/rechunking the read-only source. Numeric performance targets and optional mount support guarantees remain review decisions, with limitations reported per tested environment.
