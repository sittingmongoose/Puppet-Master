# SQLite WAL route qualification

**Scope.** This is a source-grounded qualification of SQLite’s documented WAL behavior, not a measurement of a particular application build or filesystem. No target binary/runtime was supplied, so deployment applicability remains unverified.

**Concurrency.** WAL lets readers and a writer proceed concurrently: each read transaction holds a stable snapshot, while writers append commits to the WAL. There is still only one writer at a time. All database processes must be on the same host; WAL’s shared wal-index makes network filesystems unsupported. Checkpointing copies WAL pages back to the database. A long-running reader can hold an older end mark and prevent a checkpoint from advancing past it or resetting the WAL. PASSIVE checkpoints make available progress without waiting; FULL waits for readers/writers at the required boundary. The default auto-checkpoint threshold is 1,000 pages, but build and runtime settings can change it. [SQLite WAL documentation](https://www.sqlite.org/wal.html)

**Durability.** A commit is recorded in the WAL; it need not wait for checkpointing. The WAL sidecar is part of persistent database state and must travel with the database when copied or moved. In WAL mode, synchronous=NORMAL preserves consistency but a just-committed transaction may roll back after an OS crash or power loss; synchronous=FULL adds a WAL sync after each commit for stronger power-loss durability. NORMAL still syncs at checkpoints. Thus “checkpointed” and “durable at commit” are distinct properties, and the effective synchronous setting must be inspected rather than inferred from WAL mode or a presumed build default. [PRAGMA synchronous and wal_checkpoint documentation](https://www.sqlite.org/pragma.html#pragma_synchronous) [Compile-time options](https://www.sqlite.org/compile.html#default_wal_synchronous)

**Current applicability.** The official WAL page, accessed 2026-10-09 and last updated 2026-08-25, reports a rare WAL-reset corruption race affecting SQLite 3.7.0 through 3.51.2 when multiple connections to one database race writes and checkpoints. It says the fix is in 3.51.3 and later, with backports to 3.50.7 and 3.44.6; the 3.51.3 release record also identifies the fix. Check the deployed library’s version/source ID before relying on WAL. A simple concurrency check is not a reproducer for this narrowly timed race. [WAL-reset details](https://www.sqlite.org/wal.html#walresetbug) [SQLite 3.51.3 release record](https://www.sqlite.org/releaselog/3_51_3.html)

**Source-backed validation proposal.** On the target SQLite build and a local filesystem, record sqlite_version(), sqlite_source_id(), PRAGMA journal_mode, synchronous, wal_autocheckpoint, and compile options. With two connections, hold an explicit read transaction and snapshot on connection A; commit an update on B; verify B succeeds while A still sees its original snapshot and a newly started reader sees the update. Disable auto-checkpointing on the isolated writer connection, add writes after A’s end mark, and record the three values returned by PRAGMA wal_checkpoint(PASSIVE). Then end A’s transaction and issue PRAGMA wal_checkpoint(FULL) with a bounded busy timeout; expect completion with no frames left pending. This validates snapshot concurrency and checkpoint progress, not power-loss durability or the rare reset race. If power-loss durability is a product requirement, separately run controlled storage fault injection against the actual VFS/device and require the configured FULL path; an application-process crash is not equivalent.
