# SQLite WAL: concurrency, durability, and current applicability

## Concurrency

SQLite's write-ahead log mode, available since version 3.7.0 (2010-07-21), replaces the rollback journal: original pages stay in the database file and each commit appends to a separate `-wal` file (https://www.sqlite.org/wal.html §1–2). A reader fixes an "end mark" — the position of the last valid commit when it starts — and sees one point in time for its whole transaction. Writers only append to the WAL, so readers do not block the writer and the writer does not block readers; but because there is only one WAL file, there can be only one writer at a time. The no-blocking claim is "mostly true": SQLITE_BUSY can still occur against connections held in exclusive locking mode (Chrome and Firefox do this), during last-connection cleanup, and during crash recovery (wal.html §9).

## Durability and checkpoint conditions

Durability is governed by `PRAGMA synchronous`. In WAL mode, synchronous=FULL syncs the WAL on every commit and is "atomic, consistent, isolated, and durable (ACID)"; synchronous=NORMAL omits the commit-time fsync, so recent transactions "might rollback following a power failure or hard reset" while WAL remains corruption-safe at NORMAL; EXTRA is no different from FULL in WAL mode (https://www.sqlite.org/pragma.html, PRAGMA synchronous; wal.html §2.3). A checkpoint must sync the WAL before copying frames into the database and sync the database before resetting the WAL. By default an automatic PASSIVE checkpoint runs when the WAL reaches 1000 pages (`PRAGMA wal_autocheckpoint`; zero disables it) or when the last connection closes. A checkpoint can only run to completion and reset the WAL when no other connection is using it; with continuously overlapping readers it starves and the WAL grows without bound. RESTART or TRUNCATE checkpoints force completion but may block readers (wal.html §2.2, §3.1–3.2, §6; pragma.html, PRAGMA wal_checkpoint).

## Current applicability

WAL is "significantly faster in most scenarios" with fewer fsync calls. Constraints: all processes must be on one host because the wal-index needs shared memory, so network filesystems are out (EXCLUSIVE locking mode allows single-process WAL without shared memory since 3.7.4); read-only WAL databases are openable only since 3.22.0 (2018-01-22); transactions above roughly 100 MB favor rollback mode; pre-3.7.0 clients cannot open WAL databases at all. Newer caveat: the WAL-reset bug, found 2026-03-03, could corrupt multi-connection WAL databases in versions 3.7.0 through 3.51.2; it is fixed in 3.51.3 (2026-03-13) with backports in 3.44.6 and 3.50.7. The current release, 3.54.0 (2026-10-09) per https://www.sqlite.org/index.html, includes the fix, so WAL remains broadly applicable today for same-host workloads on current or patched releases; unpatched pins in 3.7.0–3.51.2 should be treated as exposed.

## Source-backed validation proposal

Demonstrate the reader-blocks-checkpoint-reset condition: create a WAL database; hold a long read transaction open on connection A; commit writes from connection B past the 1000-page autocheckpoint threshold; then `PRAGMA wal_checkpoint(TRUNCATE)` from B should report busy with the `-wal` file not shrinking while A is open, and should complete with truncation once A closes. Expected from wal.html §2.2 ("a long-running read transaction can prevent a checkpointer from making progress") and §6 ("A checkpoint is only able to run to completion, and reset the WAL file, if there are no other database connections using the WAL file").
