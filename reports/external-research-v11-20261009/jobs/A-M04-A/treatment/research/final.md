# Final — maker-inventory recommendation and exact thin-plan comparison

**Case:** S04, maker-inventory. **Research stage:** ER11 A-M04-A/treatment/research. **This complete revision follows the frozen discovery** in `discovery.md`; it does not change that record. This is a small-product design recommendation, not a vendor audit, deployment, implementation, or production assurance claim.

## Recommendation in brief

Keep a shared calendar as the member/staff view, but make confirmed reservations a server-accepted, resource-aware record whose commit atomically rejects an overlapping active reservation. Keep physical tool custody, dated reservations, consumable amounts, repair availability, and site transfers as distinct facts. Make the server/database the single authority when online. On a disconnected device, permit cached browsing and queued/pending requests; only show global confirmation after an authoritative commit. If the organization requires checkout to continue while Wi-Fi is down, define a deliberate per-site offline-authority or exclusive-stock policy and reconcile idempotent events with explicit conflicts. Timestamps alone cannot arbitrate what two disconnected people were each allowed to take or reserve.

For the stated small scope, the simplest design to reason about appears to be a central application with one transactional store and staff-facing CSV staging, subject to confirming the actual network failure boundary and hosting skills. This is a conditional design inference, not a measured comparison of deployment cost or risk. PostgreSQL has an official range-overlap exclusion mechanism if the team can operate it; another single-authority transactional store can work if its tested write transaction protects the complete read-check-write invariant. A CouchDB-style offline-first replicated design is a real alternative only if working independently offline is more important than instant cross-site exclusive confirmations, and the product explicitly handles reservation conflicts. The brief does not establish a database, language, budget, hosting preference beyond “avoid complex hosting,” scale, offline promise, or mandatory booking workflow. Do not commit to a vendor or distribution topology until these are answered.

## Product and mechanism findings

1. **Closest lending-library workflow: MyTurn.** Its vendor page lists check-in/out, barcode scanning using common USB/Bluetooth scanners, multi-location inventory/transfer, reminders, and reservations. A public PG&E program using a MyTurn-hosted catalog asks for a reservation, then staff approve and acknowledge it; that program cites two days of lead time and staffed handoff appointments. This supplies a useful alternative to immediate self-service confirmation. These sources do not demonstrate overlap enforcement, offline behavior, repair/consumables coverage, migration fidelity, or contract/pricing. Treat the PG&E lead time as that program’s policy, not a universal software default. (S01–S02)
2. **Makerspace machine/member workflow: Fabman.** The vendor describes online bookings for machines/rooms/desks together with membership, training/access privileges, machine integration, and optional billing for bookings/use; its stable 1.2.10 API index includes a Booking resource. This is a useful comparator if training/eligibility and equipment access are first-order. The inspected sources do not prove reservation concurrency, offline booking, inventory import, consumable counts, hosting details, or cost. (S03)
3. **Custody lifecycle: Snipe-IT.** Unique asset tags and check-in/out model a current assignee/location: its guide states a checked-out item cannot be checked out to another person before return. Status labels distinguish deployable, undeployable, archived, and pending, while accessories/components/consumables have different behavior. Useful for asset tags, staff checkout, repairs/condition, and migration; not evidence of future calendar intervals. Snipe-IT’s importer has valuable explicit limits: custom fields must already exist and match names exactly; its older history importer requires existing assets/users, matches by asset tag/name, expects three headers, ignores extra fields, and expects ascending history dates. This is a warning against a blind generic overwrite importer. (S04–S05)
4. **Quantity/parts tracking: InvenTree.** It describes stock as quantity per physical location, with `in stock`, `allocated`, and `available = in stock - allocated`; allocation is for orders/builds/other commitments and inventory is decremented on consumption. Its Pint-backed units accept compatible conversions and configurable custom units; symbols are case-sensitive and common dimensionless piece units are built in. Stock history and permissions are separate facilities. This maps to consumables, stocktakes, transfer/traceability, and role-controlled adjustment, but does not establish time-slot reservation behavior. (S06)
5. **One-writer transactional enforcement: PostgreSQL.** Version 18 documentation shows `EXCLUDE USING GIST` with a `tsrange` overlap operator to reject conflicting intervals; an example adds resource equality via `btree_gist`. This can enforce the no-overlap rule at storage commit, unlike a calendar display or a pre-write availability query alone. The application still needs correct active-state predicates, cancellation/edit handling, scope by asset/site, response on conflict, idempotency, timezone normalization, and a deliberate half-open/closed endpoint and buffer policy. Using PostgreSQL adds an operated database to maintain; the feature’s existence is not itself a production verification. (S08)
6. **Offline-first replication alternative: CouchDB.** Official 3.5 docs describe incremental replica sync so sites/devices can continue with local copies while disconnected. Divergent document edits are kept as conflict branches, and application logic must merge/resolve them. Conflict preservation is valuable for audit/reconciliation but does not enforce that two distinct offline reservation documents for the same tool do not overlap. A product must mark such reservations provisional, impose exclusive site/quota/lease authority, or otherwise require an online authority for confirmation. (S09)

## Core product model and operational policy

A minimal domain model should give separately addressable, durable concepts rather than reusing one mutable status or number for unrelated workflows:

- **Reusable equipment:** stable ID/barcode, name/category, home/current site and location, current availability condition, expected service interval if useful, and any access/training eligibility. Never use the display name as identity.
- **Reservation:** equipment or a bounded-capacity resource, member, requested start/end, state (at least requested/pending, confirmed, cancelled/expired), creation/update actor and time, and decision record. Decide whether a reservation attaches to an individual serialized tool or a count in a pool. Only confirmed, live records block another confirmation. A reservation is not a checkout.
- **Checkout/return:** actual custody, who handed out/received it, expected and actual return, state/condition at handoff, and late or lost follow-up. Do not imply possession from a future reservation. Check-in is an event; if damaged, a separate repair/unavailable record follows.
- **Repair/maintenance:** structured reason/type, opened/closed time, reporter/owner, unavailable/restricted state, and repair actions/cost/parts if wanted; retain a free-text note for context. A work order is optional at this small scope, but “broken” should not be just a note that leaves an item bookable.
- **Consumables:** per-site part/stock location, base unit, quantity/precision, count adjustment/receipt/usage events, and optional reservation/allocation rules. Use integral “each” for counted items where appropriate; allow defined compatible fractional units only where the physical item justifies it. InvenTree shows the power and setup complexity of general-purpose units. Keep quantity commit atomic; no accepted deduction may drive count below the policy limit.
- **Site transfer:** dispatch/in-transit and receipt (actor, time, source/destination, quantity/item), rather than changing the site silently. Cross-site booking scope depends on this transfer state.
- **Audit/provenance:** append an operational event for reservation, checkout, return, repair, stocktake, adjustment, transfer, import, and conflict resolution with event ID, actor (possibly explicitly unknown for old data), time/source, target, old/new state or delta+unit, and reason where useful. Corrections should be explainable; retention, delete rights, and restore expectations need user policy.

Treat [start,end) as a reasonable proposed interval convention: a reservation ending at 12:00 and the next starting at 12:00 do not collide before any policy buffer. That boundary is an example only and must be decided with pickup/return/cleaning reality. Include preparation/cleaning time in the occupied window if a tool cannot be used by the next member immediately. Decide behavior on overdue return or a repair report that overlaps an existing future reservation (notify staff and affected member, block new booking, rebook/approve; do not silently delete either history).

## Retained alternatives, conditions, decisions, and uncertainty

- **Reservation policy alternatives:** member request followed by staff approval (PG&E example); immediate confirmation for low-risk tools subject to atomic server check; a hybrid by tool/training/safety category. Staff approval can make operational review explicit but creates a queue and delays; self-service is faster but needs clear eligibility and conflict handling. The brief alone cannot choose.
- **Data/hosting alternatives:** one small central instance/store minimizes distributed consistency work but can be unreachable from a disconnected site; a wired on-site server/AP may keep local users working while the internet is down but must be tested against the actual outage; two synchronized site databases improve local continuity but make shared-resource decisions harder; fully offline replicated data preserves local writes at the cost of conflict/UI/support complexity. PostgreSQL range constraints are evidence for one authoritative SQL design; CouchDB replication documents a different availability tradeoff. The client/server placement, backup owner, upgrade responsibility, and recovery objective remain decisions.
- **Cross-site policy alternatives:** block cross-site reservations while unavailable; partition every shared/high-demand tool into exclusive site ownership; reserve transfers until receipt; or add an explicit lease protocol and its expiry/fencing/clock rules. Do not imply any approach gives both unrestricted offline writes and immediate global exclusive knowledge.
- **History alternatives:** minimum useful operational log versus detailed immutable audit and long retention; optionally import historical loans where data quality allows versus only importing current inventory. The old files, legal obligations, staff effort, and retention policy are not supplied. Imported facts may be uncertain; preserve uncertainty and original row references.
- **Unsettled user questions:** (1) What precisely fails when Wi-Fi drops—member handset-to-AP, site internet, or intersite connectivity? (2) Must a reservation be confirmed offline, or is a pending request/checkout journal enough? (3) Are any tools shared between sites and how do they transfer? (4) Which bookings require staff approval/training? (5) Which consumables are fractional and what is their base unit? (6) What source columns and unique identifiers exist in old sheets, and must past loans be imported? (7) Who hosts/backups/updates the system and what budget/IT capacity exists? (8) Which audit history must be retained and who can correct it?
- **Evidence limits:** vendor pages establish described features, not real-world reliability or contracts. Public software docs evolve; InvenTree docs reviewed are moving `stable/latest` pages (and are labeled that way in S06), while its concurrency evidence is pinned to code/release identifiers in S07. None of the inspected product sources proves this specific makerspace’s user experience, security posture, data export, or current price. The database examples have not been implemented or run in the target app.

## Proposed validation set (not executed)

1. **Same-tool overlap race:** two independent sessions submit identical/overlapping active intervals at once. Exactly one confirmation must commit; the losing user sees a comprehensible conflict and retry path. Test touching endpoints per chosen convention, buffer, edit, cancel/rebook, and repair-block interactions.
2. **Consumable concurrent decrement:** with quantity `q`, launch two concurrent adjustments whose sum exceeds `q`; accepted total remains within the selected lower bound, every accepted operation has one event ID and exactly one audit delta. Repeat at both sites after any transfer.
3. **Offline boundary/reconnect:** disconnect the actual link specified by the user, submit bookings/checkouts at both sites, verify displayed state is accurately pending/local-only/global-confirmed. Reconnect, retry duplicate operation IDs, inspect merged data and all conflicts, confirm no silent overwrite and no false confirmed overlap. Include out-of-order device timestamps and clock skew.
4. **Reservation and custody state transitions:** request/approve/deny/cancel/expire, checkout/return/overdue, repair block/close, future booking affected by return/damage, and dispatch/receipt transfer. Check actor/site/time history and member/staff permissions on every step.
5. **CSV dry run and migration:** old-sheet fixtures with renamed columns, duplicate/missing names and IDs, duplicate barcode, BOM/encoding/quoted commas, date locale ambiguity, unknown users/sites/statuses, mixed/case-mismatched units, decimals/negatives, partial history, rerun/idempotency. Compare before/after inventory by site; no unexpected overwrite, duplicate, or irreversible action; rejected/ambiguous records are reviewable.
6. **Audit and recovery:** verify append/correction semantics and retention/export rules; restore a backup in a clean environment and reconcile item counts, reservations, custody, maintenance, and imported source references.
