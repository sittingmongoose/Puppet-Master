# Critique — maker-inventory research draft

**Assignment:** ER11 A-M04-A/treatment/critic  
**Inputs:** exact input map, original S04 brief, complete own-arm research draft and discovery, source map, frozen revealed plan, and declared primary-source root.  
**Scope:** independent review and targeted amendments to a complete, self-contained final. No candidate runtime or upstream test was executed.

## Material findings and amendments

1. **Add a reservation-only product path, with a current security qualification.** The draft compares lending-library, makerspace, asset-lifecycle, and parts-inventory products, but omits a dedicated resource scheduler. LibreBooking is an open-source resource-scheduling candidate: its README lists multi-resource booking, waitlists, role-based access, quotas/credits, reports, and calendar integration. It is not evidence of a complete makerspace inventory system. The same mutable README, read on 2026-10-09, announces a planned high-impact security release for 2026-10-13 and says details will wait until release; its prior notice warns that versions before 7.0.0 had an administrator-takeover vulnerability. This is significant enough to include as a screening alternative and to defer any trial/deployment pending a fresh security check. Its README lists PHP, Apache, and MySQL/MariaDB deployment prerequisites, which may conflict with “avoid complex hosting.” The release page identifies v7.0.0 as released 2026-10-06 at short commit 422b4b0. I did not infer whether that release is affected by the newly announced issue. (S10)

2. **Tighten the PostgreSQL time-model caveat.** The range-overlap recommendation is supported, but the documented example uses tsrange, whose subtype is timestamp without time zone. The example combining a resource key with range overlap first installs btree_gist. PostgreSQL 18 documents tstzrange for timestamp-with-time-zone values and exclusion predicates for subsets of rows. The final now says to choose and test an explicit instant/site-time representation, notes extension setup, and keeps active-state predicates as an implementation detail. This matters for two sites, daylight-saving boundaries, pooled inventory, and status transitions. It does not invalidate the database mechanism. (S08)

3. **Narrow the P2 rejection.** “Updated by each client” could mean clients initiate safe writes through a server-side transaction, not necessarily that they execute an unsafe read-modify-write themselves. The evidence supports rejecting stale, unconstrained read-modify-write. It does not prove that every client-originated update is unsafe. The revised disposition requires one authoritative transaction or constrained database operation, permission checks, an atomic lower-bound check, audit/event recording, and idempotency; it leaves the API/database boundary to the user’s hosting and security choice. (S06–S08)

4. **Keep the implementation recommendation conditional.** A small central store is a reasonable inference from the brief’s avoidance of complex hosting and need for consistent reservations, but no source establishes that it is the lowest-risk choice for this organization. The revised final labels it a leading hypothesis and adds a scenario-based fit check against integrated products and combined tools. No vendor, pricing, security, support, export, or hosting comparison was performed deeply enough to choose a product. (S01–S10)

## Minor findings and retained cautions

- **P1:** Keep a calendar as a view/request interface, but do not rely on its display as a concurrency safeguard. The original distinction is sound. LibreBooking strengthens the case for screening a scheduling product, while leaving fit and security unproven.
- **P3:** Timestamp-only reconciliation is not a conflict policy. The draft correctly treats disconnected global confirmation as a user decision and preserves provisional writes, site-exclusive scopes, or online authority as alternatives. CouchDB docs support replication with application-specific conflict resolution; they do not prove an asset-booking implementation.
- **P4:** Stable identifiers, review, and ambiguity handling are supported by Snipe-IT’s importer example. Hashes, rollback/compensation, immutable event audit, and full source-row provenance are useful safeguards, but should be scoped to migration risk and user policy rather than treated as demands imposed by Snipe-IT.
- **P5:** Typed maintenance/unavailable state plus free text is proportionate. Snipe-IT status labels demonstrate assignability state, not a maker-specific maintenance/work-order workflow. The draft preserves that limitation.
- **P6 and validations:** Race testing is more discriminating than normal-flow smoke tests, and the upstream InvenTree issue chain gives a relevant inventory example. All checks remain proposals. Gate offline, fractional-unit, historical-import, restore, and other tests on chosen product policies.
- **Discovery/evidence:** MyTurn and Fabman evidence is vendor-authored and supports only described features. Snipe-IT, InvenTree, PostgreSQL, and CouchDB primary evidence was re-opened independently and is summarized in the critic source map. The PG&E-hosted public page returned HTTP 403 on this review pass; the predecessor map records the earlier observation, so it remains only a scoped example, not a universal product default. Mutable documentation remains labeled mutable.
