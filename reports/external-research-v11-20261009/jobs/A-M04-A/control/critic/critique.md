# ER11 critic — maker-inventory (S04)

## Scope and verdict

I reviewed the complete control-arm predecessor `research/draft.md`, `discovery.md`, `revealed-plan.md`, `source-map.json`, and all four bounded evidence notes under `research/sources/`, against the exact brief. I then independently opened the public primary sources indexed in `source-map.json`. I did not inspect campaign/history, evaluator, or counterpart material, and did not run an application or test.

The draft is strong on the core consistency distinction: a calendar is not a concurrency guard; timestamp reconciliation is not a reservation policy; quantity stock is distinct from uniquely tagged tools; and proposed checks are clearly labeled unexecuted. Its six P dispositions mostly stand. One material competitor characterization is stale against a release that was already current when the predecessor’s source map was captured: Snipe-IT v8.8.0 now documents dated reservation requests and a unified reservations calendar. That feature must enter the comparison, but the release notes alone do not prove an overlap-prevention guarantee. The offline-checkout recommendation also needs a tighter physical-custody condition, and the database constraint must be scoped to booking states that actually hold equipment.

## Material findings

### M1 — Update the Snipe-IT comparison using v8.8.0

The draft says Snipe-IT “is not a complete borrowing calendar,” and characterizes its check-out as current custody rather than future date-range booking (`draft.md`, Product and architecture findings). The narrower caution is sound, but the account is incomplete: the draft’s own source map pins Snipe-IT v8.8.0, released 2026-09-30, and says that release notes were consulted. The official v8.8.0 notes add a `/calendar` containing reservations and a Requestables Overhaul whose requests can have start/end dates, appear on the calendar, and link to fulfillment. The official requestables page also says assets and asset models can be requestable. See [SNIPE-88-RELEASE-CRITIC] and [SNIPE-REQUESTABLES-CRITIC].

**Required amendment:** describe Snipe-IT as having at least date-window request/calendar functionality in v8.8.0, then leave open whether requests block an asset, how overlapping requests are approved or rejected, whether conflicts are enforced under concurrent writes, and what location/role rules apply. Do not elevate it to a proven reservation system: the release notes do not answer those questions. Add a focused proposed evaluation using two overlapping requests for one asset, adjacent requests, requests for distinct assets, role visibility, fulfillment/cancellation, and two site locations. This also corrects the predecessor source map’s summary of SN-RELEASE, which records only PHP and importer facts despite the reservation features being in the same release.

### M2 — Make offline checkout contingent on verified local custody

P3 is correctly rejected as written: a timestamp sort cannot establish which disconnected claim should win. The local-first evidence describes branch conflicts and arbitrary deterministic winners, not a business-valid winner ([POUCH-CONFLICTS-CRITIC], [COUCH-35-CONFLICTS-CRITIC]). However, the suggested exception—“offline checkout may be recorded as a local action against an item already assigned to that site”—is under-specified. A site assignment can be stale during a partition, after an in-flight transfer, or after an earlier offline checkout; a cached “assigned here” value alone does not prove the physical tool is present, serviceable, and not already in another member’s custody.

**Required amendment:** distinguish a new future reservation from a physical checkout event. If offline checkout is allowed, condition it on staff verifying the tool’s physical presence and custody at that site, and define how the system handles a stale transfer/checkout state and duplicate replay. Otherwise queue the event as unconfirmed for reconciliation. Keep global availability and new firm reservations unconfirmed until the authority accepts them, unless the owner chooses site-exclusive pools or another explicit partition policy. Add those stale-transfer and duplicate-checkout cases to the outage validation. The user must still choose whether either site may promise a firm booking while disconnected.

### M3 — Define exactly which reservation states the database invariant protects

The recommendation to use an authoritative relational constraint is supported. PostgreSQL 18 documents range exclusion constraints using `&&`; combining tool identity equality with range overlap requires the relevant GiST operator class (the example uses `btree_gist`). Its two-argument range constructor defaults to `[)`, while timestamp ranges are continuous and range text can specify other bounds ([PG18-RANGE-CRITIC]). The draft correctly proposes adjacent-interval tests, but the recommendation and test should say that only confirmed/booked holds block another hold. If a draft or tentative offline request is stored in the same table and participates in an unconditional constraint, it may reject requests that are supposed to remain tentative; canceled/expired rows and authorized overrides likewise need defined semantics.

**Required amendment:** name the authoritative database as a decision still to be selected, require valid nonempty intervals with a single enforced bound convention, and define which statuses enter the no-overlap invariant and how any privileged override is recorded. Keep the limit explicit: this prevents concurrent conflicts only at the reachable authority; it cannot confirm a global booking at a disconnected site. Extend the proposed tests to cover draft/tentative, confirmed, canceled, and override transitions as well as overlapping and adjacent intervals.

### M4 — Repair status must address bookings that already exist

P5 correctly rejects free-text-only maintenance because the brief asks for repair status. The proposed rule that a tool in repair is unavailable for booking/check-out covers new actions, but not a repair report made after future bookings have already been confirmed. The draft’s repair lifecycle test checks that the tool is unavailable during repair, yet never tests what happens to those existing reservations.

**Required amendment:** preserve the owner decision on authority/notifications, but define the required system response when a repair interval overlaps an existing hold: surface affected bookings, prevent an invalid checkout, and give staff a recorded cancel/reassign/contact path. Add an existing-booking-then-repair test. Do not silently delete or leave a confirmed reservation appearing available to staff while the item is known unsafe.

## O1–O6 review and retained strengths

- **O1 — Discovery:** Cheqroom, Snipe-IT, InvenTree, replicated local-first data, and a central relational authority are materially different references. The competitor set is useful, but Snipe-IT’s new request windows make its role broader than an asset-register-only comparator. Do not infer that its beta mobile app or sync adapters imply offline reservation guarantees.
- **O2 — Primary behavior, defaults, limits:** The PostgreSQL example and its `btree_gist` requirement are grounded; PouchDB/CouchDB conflict behavior is described with appropriate caveats; Snipe-IT import limitations and InvenTree units/history/import flow are useful. `latest`/`stable` InvenTree pages and Cheqroom’s migrated help articles are appropriately flagged as mutable or inaccessible. Preserve those caveats and version-pin before implementation. The current source map should add the omitted Snipe-IT calendar/request details.
- **O3 — Evolution chain:** The InvenTree #12478 issue/fix/release chain is relevant to a check-then-write race and is not overstated as proof of this product. My independent PR-page access confirmed the reported two-success/five-unit race and merge on 2026-07-28. The browser blocked the diff URL during this pass; the inherited `INV-ALLOC-PR` evidence note reports the inspected lock/revalidation patch, cross-transaction test, and `select_for_update` backend guard. Keep that provenance distinction; do not say I independently re-read the patch here.
- **O4 — Per-clause comparison:** All six exact clauses receive a meaningful disposition. No P2/P4 correction is contradicted by the reviewed evidence. P1 and P6 rightly distinguish baseline coverage from optional view/enhanced tests. P3 is a valid rejection of timestamp-only arbitration, not a rejection of all offline work.
- **O5 — Conditions and alternatives:** The owner decisions on firm offline promises, hosting, item identity/quantity pools, legacy history, and retention are appropriate. Keep both a small shared service and pre-partitioned site pools as conditional options. Do not make a local-first PWA sound operationally free: it still needs sync, conflict support, backups, and an accountable authority. No costs or product-plan entitlements were established.
- **O6 — Validation:** The six proposed validations distinguish race safety, partition behavior, import ambiguity, stock/custody history, authorization, and actual acceptance; their “not executed” status is honest. Add the M1 and M4 cases. The issue/fix regression test is evidence for why to test, not an executed makerspace test.

## Minor findings and editorial corrections

1. The recommendation says “append-only activity history” broadly, while its test and data model include correction/retirement but do not state whether corrections are compensating events or direct edits. Keep append-only as an intended audit design only if corrections and retention are specified; the brief does not itself require indefinite retention.
2. “An atomic transaction/compare-and-update or append a stock event and derive/materialize the balance” gives alternatives but should make the invariant common to both: concurrent decrements cannot go negative or be lost, and operation retries cannot double-apply. The unique operation ID appears later and should be tied back to this rule.
3. InvenTree issue #12478 concerns order allocations for quantity stock, not timed equipment reservations. The draft correctly calls it an analogue; retain that boundary wherever it informs P1/P2.
4. The plan of using one service is a conditional recommendation, not proof of a simple hosting burden. The user’s “avoid complex hosting” constraint remains unresolved until service operations, backup/restore, and second-site connectivity are compared against a managed product option.
