# ER11 revised research — A-M10-A / treatment / S10 data-import

**Status:** complete research-stage final, revised against the exact revealed plan and the mapped independent critique. This is a product research proposal, not an implementation selection, benchmark, or assurance result.

## Scope and recommendation

The brief is a desktop import assistant for nonprofit analysts handling large CSV files, occasional Excel workbooks, inconsistent dates and identifiers, inference preview, original-string preservation, understandable rejects, and repeatable monthly transformations. The proposal stays within that small product scope. It does not promise universal format coverage or production performance.

Build the import design around separate stages: preserve the selected source and its digest; parse CSV structure or workbook cells; show type inference as a proposal; apply only reviewed conversions and transformations; record issues and output lineage; save the accepted, ordered recipe; and compare each monthly input with the recipe's expected schema. Keep source values and normalized values separately addressable. An inference result must never silently overwrite an identifier or original value.

The strongest current prototype candidate for the stated Rust desktop direction is Rust csv 1.4.0 plus Calamine 0.36.1, with explicit adapters and a source-aware issue model. This is a shortlist candidate, not a demonstrated winner. DuckDB, Arrow CSV, Polars, OpenRefine, and Power Query each offer materially different capabilities that may fit particular workflows. The brief does not define the laptop resource envelope, workbook formats, privacy policy, locales, or null vocabulary, so those decisions and performance comparisons remain open. [S01–S12; C01–C14]

## O2 — consequential behavior, defaults, types, limits, and applicability

### CSV parsing, inference, and source fidelity

A CSV parser returns fields and records after interpreting delimiters, quotes, and line breaks; that representation is not the original byte stream. Keep an immutable reference to the source file and its digest. If the user needs a controlled copy, document it as a source copy and verify its digest. Show the decoded field, inferred type, and converted value as distinct things. Preserve identifiers as text unless the user approves a numeric meaning. [S06; C04; C12; R03; R05]

For Rust csv 1.4.0, make the dialect and header choice visible. Its defaults include headers enabled and strict equal field counts; its default does not trim fields. A record-start parser position is not a cell coordinate or a fine-grained byte range. If exact field position is not established, label location as record-start or unknown. For invalid UTF-8, use a byte-oriented route or report a decoding error; do not fabricate decoded text. A malformed quoted record can also make later record boundaries uncertain. [S06; C04; R03]

DuckDB documents 20,480 sampled rows by default, with sample placement affected by file seekability and compression. A sample can miss a rare late identifier/date. Treat inference as preview, show sample mode and coverage, surface conflicting examples, and distinguish it from full-file validation and user-approved conversion. Power Query and Polars document other sampling defaults (first 200 and 100 respectively); Arrow examples include a 100-row or full scan choice. These values describe tools, not evidence that any sample is adequate for this nonprofit dataset. Keep 1,000 as a possible configurable preview only if product usability and performance support it; never make that prefix the sole type authority. [S01; S07; S10; C01; C06; C07; C13]

Header detection, dialect, null interpretation, and type inference are separate choices. DuckDB’s docs describe header-inference limitations when all columns become VARCHAR. Ask users to confirm uncertain header/dialect results. Distinguish an empty field, a configured null token, a short record with absent fields, a worksheet blank, and a missing worksheet coordinate. A machine locale may be a visible preselection, but it must not silently determine conversion. [S01–S04; C01–C03]

### Dates, workbook cells, and formulas

The locale example in Power Query documentation shows that day/month values may fail or change meaning under another regional format; an explicit per-conversion locale is available. Make date format and locale explicit at the column or operation level, display a discriminating sample, preserve the input value, and save the accepted choice in the recipe. Ask when a value remains ambiguous or unsupported. A date-only value does not carry a timezone; do not invent one. [S10; C06]

A workbook cell is not always a rendered string. Preserve the source workbook, sheet and cell coordinate, underlying cell kind, available number format, formula text, and cached value as separate evidence. A numeric cell displayed with leading zeroes differs from a text cell containing those zeroes. Calamine distinguishes several value kinds and exposes the XLSX date epoch, but its API shape is not a guarantee of rendered-text fidelity or low total memory. A cached formula value is not proof that the formula was freshly recalculated. Make formula, cache, and supported date behavior visible and test them. [S08–S09; C05; R04]

DuckDB XLSX import demonstrates why these are product choices: range and empty-row behavior are configurable, empty cells can be typed as VARCHAR, and an ignore-errors option can convert cast failures to NULL. Do not adopt such defaults invisibly. The initial set of workbook formats, formula/cache behavior, blank-cell semantics, and any resource limits require product decisions. [S04; C03]

### Rejects, locations, and counts

Keep both an in-app issue ledger and a downloadable error CSV. The ledger is for review and resolution; the CSV preserves the exact P4 deliverable and supports the analyst’s existing workflow. Use stable fields for run/source identity, input hash, logical record identity, issue category, column where known, parser/rule message, resolution, and location precision. Location fields should be nullable and accompanied by a precision label such as record start, verified byte span, or unknown. Distinguish structural parse failures from typed conversion failures. Make raw offending values or entire failed rows a deliberate privacy choice, with clear export disclosure; the original file remains authoritative for exact bytes. DuckDB’s opt-in rejects table illustrates that diagnostics can include line/byte positions, column, error type, source line, and message, while also showing that collection behavior is tool-specific. [S03; S06; C02; C04; R02; R03]

For row reconciliation, define the first denominator as logical data records recognized after the selected dialect and header rule—not physical lines. RFC 4180 permits quoted fields to contain line breaks and describes optional header presence, while also noting CSV implementation variation. A blank physical line or header line is counted separately, not as a data record. Each recoverable logical input record receives exactly one initial disposition: accepted, rejected, or intentionally skipped. If the parser cannot recover a logical boundary, count the affected source byte span or physical-line range separately with an unrecoverable/unknown status; do not invent a record count. [C12; R05]

At each named filter or deduplication step, report before/after counts and the number removed by that step. Preserve lineage from each output row to stable input record IDs. Equal counts do not prove values are correct, so add identity, duplicate, and selected-value checks. The brief’s count comparison remains important, but counts need a defined unit and cannot stand alone. [S03; S11; C12]

### Recipe reuse and resource behavior

Store a versioned, ordered recipe with operations, parameters, column mapping, locale/date rules, null rules, header/sheet/range choices, and the accepted schema. Keep recipe identity separate from each monthly input hash. Before applying it, detect missing, added, duplicate, reordered, or changed columns and pause when meaning may have changed. [S11]

Pin parser/library, transformation implementation, and locale/date-data versions in every run manifest. Do not silently replay a recipe under changed semantics. Proposed compatibility behavior: use the exact old engine when it remains available; otherwise present a visible migration diff and require approval before replay. Keep a golden fixture across upgrades. The user/product must decide whether old engines are bundled/retained and how long they remain runnable. OpenRefine’s reusable operation-history JSON is precedent for replay, not evidence that a new product’s recipes are portable or deterministic. [S11–S12; C10; C14]

For modest-memory laptops, separately measure process RSS, temporary disk, latency, cancellation, and recovery on the lowest supported target. DuckDB documents that its configured memory limit applies to its buffer manager; it does not establish a total application RSS bound. OpenRefine memory descriptions in the inherited sources are from different generations and cannot be compared without pinning builds. The minimum RAM/storage, file-size envelope, and whether temporary disk is allowed remain user decisions. [S05; S12]

### Source drift note

The inherited DuckDB observation records a maximum CSV line size of 2,097,152 bytes. A direct read of the DuckDB 1.5-current rolling page on 2026-10-09 displays 2,000,000 bytes. Both observations are retained under their original IDs; the rolling URL is not a fixed release source, so this review cannot say when or why the displayed value changed. Do not repeat either number as a product limit. Parameterize any test to the pinned engine version, and resolve the exact value against a fixed release only if it affects the eventual product choice. [S02; C02; R01]

## O3 — relevant issue, fix, regression, and release/evolution chains

**Workbook-date chain:** OpenRefine issue #1908 reports Excel dates imported as text in 3.1 compared with 2.8. Maintainer discussion attributes the regression to Java 8 date-type changes while the Excel importer still supplied the old type. PR #2909 changed the importer to OpenRefine’s OffsetDateTime type and added date tests; it merged on 2020-07-09. The issue was assigned to 3.5, and tag 3.5.0 was released on 2020-11-07. This is evidence for versioned adapter regression fixtures, not proof for every workbook epoch, formula, format, or timezone. [S13–S15; C08–C10]

**CSV quote-option chain:** OpenRefine issue #7042 reports that disabling quote processing behaved differently in 3.8 than in 3.7. PR #7703 adds a case confirmed to fail before the fix, disables quote handling in parser configuration when the option is off, and merged into master on 2026-03-13 as commit c32deb2. The PR carries milestone 3.10.2; this review did not verify a 3.10.2 release and does not claim one. Keep a versioned quote/delimiter compatibility fixture. [S16; C11; R07–R08]

Both chains are bounded upstream examples. They justify adapter-specific regression tests during future implementation; they do not validate this proposed assistant or its libraries.

## O5 — retained alternatives, constraints, disagreement, and uncertainty

Preserve source bytes separately from parsed CSV strings and separately again from normalized output. For workbooks preserve the original file and keep cell kind, coordinate, number format, formula, and cache information distinct where the adapter exposes them. Do not equate a cell’s displayed form with its stored value. Keep a visible review step for inference and identifier conversion. [S06; S08–S09; C04–C05]

Keep multiple implementation routes open until fixtures and the laptop envelope exist. Rust csv plus Calamine is a plausible language-aligned prototype; DuckDB may be useful for SQL staging and diagnostic comparison; Arrow or Polars may suit typed batch processing. OpenRefine and Power Query are analyst workflow competitors and UX references, not proposed Rust dependencies. No performance, package size, support matrix, or licensing comparison has been measured here.

Keep issue review and downloadable error CSV as separate but connected experiences. The exact error export schema and whether values/full rows are included require a privacy decision. Source files, rejects, archives, and error messages may contain sensitive nonprofit or personal data. OpenRefine’s archive warning is an example of why project history and a clean replay recipe should be separate exports. [S03; S11; C14; R02; R06]

The brief does not decide: minimum RAM/storage and temporary-disk use; file-size/row/cell envelope; supported workbook formats; formula/cache policy; locales and accepted date formats; null tokens and empty-string behavior; malformed-file recovery; whether filtered/deduplicated records are supported; source-copy retention; or old-engine retention. These remain explicit user/product decisions. Do not promote library defaults into these policies.

Important uncertainty remains: a 1,000-row sample may miss late or rare values; no sample size is proven adequate; CSV implementations vary; parser recovery after malformed quoting is adapter-specific; Calamine streaming does not give a whole-process memory bound; workbook cached values may be stale; OpenRefine documentation covers different generations; the DuckDB line-size value is on a rolling page; and the issue chains cover only their stated regressions. Each should be resolved by pinned versions, representative fixtures, and measurement when implementation begins.
