# ER11 critic — A-M10-A / treatment / S10 data-import

**Stage result:** independent critique of the complete treatment research draft after the declared plan reveal. **Overall judgment:** the draft is a coherent, evidence-backed small-scope proposal and correctly refuses to present tests as executed. It is suitable as a research-stage draft after the material corrections below. It is not an implementation selection or proof of performance.

**Materials read:** this stage's `assignment.md` and exact `input-map.json`; the declared S10 `brief.md`; all four declared predecessor files (`draft.md`, `discovery.md`, `source-map.json`, `revealed-plan.md`); and the declared predecessor `sources/index.md` and `sources/observations.md`. I did not inspect a parent, counterpart, evaluator, campaign/history material, or unrelated files. New research was limited to public primary documentation, released source, RFC text, and upstream issue/PR/release records. No nested agents were used.

## Findings that should change the draft

### Material

**M1 — P4 should retain the promised CSV output.** The draft upgrades the plan's “Keep failed rows in an error CSV” into an in-app issue ledger and demotes CSV to an optional export. The ledger is a useful correction to the *information model* (record/cell location, structural versus cast error, source value, rule, resolution), but making the named output optional weakens an explicit plan clause without evidence that the user wants it removed. Preserve both: an in-app, source-linked issue ledger and a downloadable error CSV with stable columns and source/run identifiers. Let users choose whether to include sensitive offending values, and document that the source file remains authoritative for exact bytes. This is a **partial correction plus enhancement**, not a reason to reject the output. Privacy is a design condition, not grounds to silently drop the export. [O4; P4; brief “understand rejected rows”; S03, S11; C02, C14]

**M2 — P6's proposed reconciliation categories need disjoint definitions.** The draft says reconcile input records as accepted + rejected + “explicitly skipped/header/blank/excluded” records. These labels can overlap, and a header or physical blank line is not necessarily a data record. CSV logical records can contain embedded line breaks, so physical lines are not a safe row-count unit. Define the denominator as *logical data records after dialect/header parsing*, keep header/blank physical lines and parser-unrecoverable byte spans in separate counters, and make each logical input record land in exactly one initial disposition (accepted, rejected, or intentionally skipped). Thereafter report separate counts for named filter/dedup steps and preserve lineage from output rows to input record IDs. Count equality alone cannot validate content. This sharpens a sound P6 correction and is more precise than the present V4/V6 coverage. [P6; O2/O6; C12 RFC 4180 §§2, 3; S03; C04]

**M3 — Do not promise a precise issue location the parser cannot provide.** Rust `csv` 1.4.0 supports byte records and positions, but its reader position is observable at record starts; its source comments say finer-grained positions are unsupported. String records also require valid UTF-8. The proposed issue ledger should therefore distinguish a reliable logical record start, a parser-provided position, a best-effort byte span, and an unknown location. Retain the original file by immutable reference/hash (or a controlled source copy) and never claim a malformed quoted record has a recoverable cell coordinate when the parser cannot establish one. For invalid UTF-8, use a byte-oriented path or report the decoding failure without fabricating decoded text. The draft already says “best offset” and distinguishes bytes from fields; this finding makes that limitation operational and should be reflected in V1/V4 and the P4 schema. [O2/O6; S06; C04; C12]

**M4 — Calamine's XLSX iterator is streaming, but does not establish a low-RAM import.** The 0.36.1 `XlsxCellReader` docs confirm XML-stream iteration and formula/cache access. The constructor also receives shared-string and cell-format slices, and all `next_*` methods consume the same stream, so only one streaming mode may be used per reader. This supports the draft's caveat that iteration does not bound whole-process memory, but the cause and API constraint should be explicit. V5/V7 should include large shared-string and style tables, sparse sheet dimensions, formula metadata mode, and peak RSS/temp storage; do not infer workbook-level memory bounds from the iterator name. [O1/O2/O6; S08/S09; C05]

**M5 — Recipe replay needs compatibility behavior, not just versioned storage.** The draft is right to separate a reusable recipe from a monthly input hash and to pause on schema drift. It should also say what happens when a parser/library, locale database, date-format parser, or transformation implementation changes: pin the execution versions in each run; define whether old recipes replay under the old engine, migrate with a visible diff, or pause for approval; and keep a golden fixture across upgrades. OpenRefine's exported operations JSON shows that operation replay is a useful product precedent; it does not establish that a new assistant's operations are portable, deterministic, or semantically stable. Existing “library versions” in the run manifest partially covers this; the missing piece is recipe compatibility policy. [P5; O2/O6; S11/S12; C14]

### Minor factual/traceability correction

**m1 — DuckDB max-line value differs between inherited notes and the current page.** The predecessor observation/draft records a default of 2,097,152 bytes. A fresh read of the DuckDB 1.5-current overview table gives 2,000,000 bytes. Because the URL is rolling and the map does not pin a documentation commit, this is an unresolved observation discrepancy, not proof of when or why the value changed. Do not carry either number as a product limit; the conclusion that a parser-specific line cap must be visible remains correct. Label the exact source/version and resolve against a fixed release before repeating the number. [S02; C02]

## Discovery, alternatives, and evidence quality

The selected Rust `csv` + Calamine combination is a plausible prototype for this Rust desktop brief, not a demonstrated winner. The draft labels it as a candidate and correctly leaves performance to measurement. Arrow offers typed batches (default 1,024 records per batch and a supplied schema); DuckDB offers richer CSV detection, rejected-scan diagnostics, SQL staging and XLSX import; OpenRefine is a local cleanup/replay competitor; Power Query supplies inference and locale UX precedent. These alternatives materially differ, and no source indicates any one meets the laptop envelope. Preserve the comparison as a shortlist; select only after comparing supported workbook formats, raw-value fidelity, recoverable rejects, package/deployment size, update/licensing constraints, and identical fixture performance. [S01–S12; C01–C10]

The discovery's Polars note said “API search only” without its own source-map ID. I independently checked the versioned `polars-io` 0.55.2 API: schema inference defaults to 100 rows, `None` means a full scan documented as very slow, and `low_memory` trades performance for reduced memory. That verifies the capability claim, not a hard memory bound or recommendation. The critic source map adds a new ID; upstream S01–S16 are preserved unchanged. [C07]

The O3 OpenRefine #1908 chain is sound: the issue records a 3.1 Excel date regression relative to 2.8; maintainer discussion attributes it to the Java 8 date-type migration with the Excel importer left on the old type; PR #2909 switches to `OffsetDateTime` and adds date tests, merges July 9, 2020; the issue/release record places the fix in 3.5, released November 7, 2020. This is one bounded adapter regression, not evidence for every workbook epoch/formula/time-zone case. [S13–S15; C08/C09]

A second, more CSV-specific evolution lead is now verified: OpenRefine #7042 records changed quote-option behavior between 3.7 and 3.8; PR #7703 adds a failing-before regression test and fixes parser configuration, merged into `master` March 13, 2026, with milestone 3.10.2. The inspected record does **not** prove a 3.10.2 release shipped; do not state that. The draft's short note is accurate but understates the completed chain. Keep V1's quotes/delimiters case and make a versioned compatibility fixture from it. [S16; C11]

One current DuckDB header behavior is worth retaining as a caution: when every column is inferred as `VARCHAR`, current docs say header detection cannot distinguish the header from data and assumes a header unless overridden. This supports explicit header review and `all-text` mode; it does not establish that DuckDB is suitable as the product parser. [S01; C01]

## Minor findings and remaining decisions

- The brief does not select RAM/storage thresholds, file sizes, accepted spreadsheet formats, formula policy, locale set, null tokens, malformed-file policy, or intentional filters. Retain these as user decisions; do not invent them.
- P1's correction is supported as a rejection of *sole reliance* on 1,000 rows, not as proof that full-file scanning is always the right preview default. Make the speed/coverage tradeoff visible.
- V4's “max-line boundary” should be parameterized by the parser and its pinned version; DuckDB's cap is not a product standard.
- Issue-ledger/error-export retention, source copies and project archives may contain personal data. Define disclosure/retention controls with the product's data handling, while keeping rejection explanations useful.
- The OpenRefine memory comparison spans different documentation generations; no memory number should be treated as a current head-to-head benchmark. The manual documents exportable operation history and warns that project archives preserve prior data/history; this supports the privacy concern but does not prove a reusable recipe is safe or version-stable. [C14]
