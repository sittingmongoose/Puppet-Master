## Brief constraints preserved

This is a small shellfish farm with 12 harvest crews, 2 packing sheds, a broad coastal inlet, bed assignments, pickup windows, and packing-line capacity. Crews currently record harvest quantities and lot labels on waterproof cards. Initial-system budget is $14,000. Some work occurs under weak mobile coverage. Buyers need reliable lot-level handoffs but may not see crew phone numbers or internal quality notes. Weather, buyer demand, and locally issued closures can change operations. The farm wants its authorized notices represented without software deciding whether harvest is permitted. Crew languages vary; the shed uses a shared touchscreen with gloves. Managers need to see lots waiting for handoff, packed, or held for review, and correct transcriptions without deleting who changed them. One species and one shed are candidates for the first pilot. Decisions still open: who can release a held lot, which outside notice links to a bed, and whether buyers need direct access or paper suffices.

The brief supplies no jurisdiction, shellfish species, existing devices/network, current record format beyond waterproof cards, standard measurement unit, scale accuracy, notice authority, buyer format, legal applicability, budget allocation, or release-role decision. These remain unknown, not assumptions to fill silently.

## Findings for the brief's full scope

### 1. Three distinct ways to start

**A. Keep a paper-first, digitize only the handoff board.** Continue pre-numbered waterproof harvest cards and lot labels. Add a shed board or narrow shared screen for three visibly distinct states (waiting for handoff, packed, held for review) and record each handoff/correction as a dated amendment that refers to the original card. A printed, allowlisted lot docket is the default buyer interface. This minimizes connectivity dependence and preserves a familiar field workflow, but paper-to-screen reconciliation and late transcription still need a named owner and backlog. This is a low-change operational option, not a guarantee of lower total cost.

**B. Adapt an offline form workflow.** ODK Collect plus a Central server is a practical configurable prototype for field capture; Collect is the offline-capable client recommended by the docs for enumerator work, while the current ODK Web Forms are not offline-capable. Audit forms can record old/new answers, a required edit reason, an entered user identity, and an audit log; Central's docs say editing creates a new submission version. This could test harvest capture, amount/unit, lot label, bed, pickup/packing expectations, and corrections with a small set of crews. It does not itself solve cross-shed capacity scheduling, status transitions, buyer-specific read views, approval authority, or trustworthy identity on a shared device. An identity prompt accepting any nonblank string is not authentication. It needs a fit test before choosing it as the production system. [S02–S04]

**C. Build a narrow, offline-first event workflow.** A small app can treat lot history as append-only events (harvest recorded, packed, held, correction added, handoff signed) and derive the manager's current status view from them. Use unique pre-issued lot labels during offline work, stable event IDs, queued sync, and explicit duplicate/conflict review; never silently accept last-writer-wins for material quantity, bed, hold, release, or handoff changes. Keep card photo/scan or paper-card reference as a fallback. A one-species/one-shed pilot is credible scope; adding 12 crews, two sheds, spatial notice logic, buyer accounts, barcode inventory, and integrations together is not a justified starting scope. GS1 EPCIS/CBV is a useful optional event vocabulary/export model if buyer interoperability later warrants it, not a mandate to build a full EPCIS service. [S08]

ABALOBI MONITOR is a useful adjacent product to demo because its official material describes multilingual, offline-compatible catch landing entry, dashboards, and user/configuration support for small-scale fisheries. It is the closest unfamiliar product found for remote crew data collection. It has no evidence of farm bed-to-shed capacity allocation, held-lot release roles, buyer-safe projections, or the specific shellfish workflow; product claims about free use do not settle setup/support/customization cost. Use it as workflow inspiration and a fit interview, not as a presumptive purchase. farmOS Field Kit demonstrates assigned farm activities and offline edits synced later, but its v1 guide itself describes a proof-of-concept no longer receiving major feature updates; it is an aging reference, not a default recommendation. [S01, S10]

### 2. Record shape, status, units, and correction semantics

Give each harvest lot a permanent human-readable farm identifier (pre-issue ranges/cards before disconnected work so crews cannot independently invent colliding IDs). A record should link that lot to the source card, species (pilot-controlled list), crew or operator (minimum needed), bed ID, actual harvest time as reported, quantity, explicit unit, device-captured time, system receipt/sync time, and event origin. Keep planned pickup/packing capacity separate from actual harvest and handoff events.

Represent event time and record time separately: time a crew says an event happened can differ from the later time the event reached the server. Offline device clocks are not an independent authority; flag corrections to event time and show sync time rather than presenting either as proof of a permitted harvest. Capture and retain the original source card or its reference.

For count lots, use a whole count; for mass or volume, use a positive decimal plus an explicit fixed unit selected with managers and the buyers. GS1's quantity model distinguishes a positive integer for fixed-measure/countable items (with unit omitted) from a positive non-integer physical amount plus a UOM for variable measure; its UOMs use 2- or 3-character UN/CEFACT codes. The standard is useful as an export contract; do not assume the farm's scale or buyers already use that schema. ODK's integer field rejects decimals and caps at nine digits; its decimal field accepts decimals but caps the text at 15 characters. Check these constraints against actual weights/counts before adopting an ODK form. [S04, S08]

The system should never erase a saved harvest, change, or hold. A correction appends: lot ID, field amended, prior value, replacement value, reason, correcting person, event time, recorded time, and source reference. Current lot state can be reconstructed from events; a visible history and source-card pointer make transcription fixes reviewable. Form audit logs can help, but they are a best-effort mechanism rather than a substitute for an explicit correction event. A 2023 ODK report describes lost changed-answer audit events after deferred validation in a field-list workflow; treat that narrow old report as a regression case if those UI patterns are used, not as a claim about current versions. [S02, S07, S08]

Keep transitions explicit: harvest recorded → waiting for handoff → packed → handoff recorded, with “held for review” as a blocking condition that persists until a person authorized by the farm releases it. Hold reason/category may be recorded privately. A closure notice should be a source fact (issuing authority, original title/URI or preserved copy, issued/observed time, effective interval if stated, text as stated, human bed-link decision and confidence), not a machine-calculated permission. When notice-to-bed assignment is ambiguous, put the bed/lot into review and let an authorized person decide. Never equate “no notice found” with “harvest permitted.”

### 3. Data access, buyer handoff, and shared touchscreen

First release should keep internal/private data in a separate operational record from the buyer-visible projection. Default to a printed lot record that contains only agreed items such as lot ID, species, harvest date/time if required, bed/area descriptor if agreed, quantity plus unit, packing/handoff events, and the farm's chosen notice reference. Exclude crew personal numbers and internal quality notes. Do not claim a link, form, or export is buyer-safe unless tested against a field-by-field allowlist. ODK Public Access Links are documented as data-collection links that let holders submit to a form; that is not evidence of a buyer read-only trace page. Direct buyer access remains a user choice that requires a separate role, revocation, and field-visibility decision. [S03]

For glove use, prioritize large high-contrast touch targets, three status actions with words and icons, no color-only meaning, short bilingual labels, unit presets, numeric keypad, visible save/queued/synced state, and a clear way to find/scan a pre-issued lot. A shared shed device must identify the active worker for consequential edits; consider per-action operator selection/credential confirmation for release/handoff rather than assuming a continuously logged-in named account is the person wearing gloves now. Keep crew phone numbers out of ordinary buyer views and avoid GPS by default. Usability proposals need real glove, language, noise, wet-screen, and interruption testing; no source reviewed proves a specific UI already meets these conditions.

### 4. Offline and sync behavior

A field record must save locally without network, retain an unsent queue across app restarts, make “saved here” distinct from “received centrally,” retry idempotently, surface rejected/conflicting events, and show the eventual server-confirmed receipt. Pilot disconnected entry, closing/reopening the app, clock skew, duplicate taps, later form/schema version, and two devices recording adjacent or same lots. The ODK issue/fix chain is concrete evidence that offline edits and sync reconciliation can have subtle owner/access/hash edges: issue #6768 described stale local entities; PR #6910 selected a client integrity check when the hash was unchanged and reports regression checks across access modes, deletion/update patterns, and Android versions. This supports explicit failure-injection validation, not rejection of ODK as a whole. [S05, S06]

The 12 crews can record independently while disconnected, but shed line capacity and pickups are shared resources. Offline scheduling can create oversubscription if each device sees old capacity. For pilot, centralize assignment and capacity edits at the shed or reserve a bounded slot once crews sync; display stale schedule age, avoid making disconnected screens look authoritative, and send collisions to a human. Do not let offline crew entry silently release a hold or overbook a packing line.

### 5. Cost and scope conditions

The $14,000 initial budget is a constraint, not a price target with known line items. The brief gives no labor rates, existing hardware/server, hosting, support, translation vendor, label stock/scanner costs, integrations, or training costs. Do not attach unsupported dollar estimates to ODK, ABALOBI, farmOS, or custom work. Make any vendor/build comparison include discovery, devices, hosting, sync, import, support, multilingual review, printing/labels, training, security/access, backups/restore, and contingency. Stage a fixed-scope pilot/prototype so a bid can demonstrate actual offline retry, buyer-safe print, audit correction, and held-release policy before committing to the rest of the budget. Stop or rescope if those core behaviors do not fit the cap.

Do not use the FDA rule page as a design certification: applicability depends on listed food and case-specific exemptions/activities. The current FDA page itself has an update mismatch: its top section describes non-enforcement before July 20, 2028 while a lower section still says Jan 20, 2026. Jurisdiction is unknown; ask for species and market/regulatory context, check current official notice and qualified advice. Irrespective of that determination, the product can capture harvest/packing/shipping facts and preserve source references without inferring permission. [S09]

## Initial validation proposals (not executed)

1. Paper and digital parallel run for one species/one shed with a preissued lot range; reconcile 100% of lot labels, quantity/unit, bed, and handoff against cards at end of day, including one correction. Pass if every test lot has one stable ID and no untraceable overwritten values.
2. Weak-network/offline matrix across at least two crew devices and one shed touchscreen: airplane mode, app restart, duplicate submit, reconnect, retry, altered record version, and server delay. Verify local persistence, idempotency, conflict/queue signaling, final event history, and visible sync receipt. Inject stale capacity data; confirm overbooking is blocked/reviewed.
3. Audit and authority cases: mis-key quantity, wrong bed, wrong time, late notice, notice map uncertainty, hold, attempted handoff while held, unauthorized release attempt, authorized release (only after role decision), and delete/recreate attempt. Compare displayed state to appended source events; software must not compute an open/closed legal permission result.
4. Shared-touch test with actual gloves and each pilot language: find assigned lot, enter amount/unit, save offline, find queue, correct an error, and complete handoff. Observe mis-taps, time, required help, language comprehension, and lock/sign-out leakage; revise based on failures.
5. Buyer projection test: print/export a real sample and attempt to discover crew phone numbers, internal notes, or unrelated lots. Confirm only approved fields and selected identifiers appear. If direct buyer access is later chosen, test authentication, revocation, shared link forwarding, field allowlist, and offline/printed fallback separately.
6. Recovery/capacity/backup: restore from backup in a clean test environment, reconstruct one lot's history and buyer receipt; exercise both sheds' future case only if included in pilot; measure line capacity in stated units/time from an authorized source. This is proposed work, not completed verification.
