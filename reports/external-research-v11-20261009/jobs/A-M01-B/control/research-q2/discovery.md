# research-q2 discovery — S07 documentation-portal (q2: products / workflow / usability / options + validation)

Scope: internal documentation portal for 60-person engineering group, three codebases, multilingual notes, frequent releases. Search must return the relevant released version, cite exact passages, and help maintainers see contradictions without silently rewriting documentation. Research existing products/mechanisms, code/doc linkage, retrieval conditions, migration/export options.

Method M01 control q2. Focus: competing products, workflow/usability/options, meaningful validation. Preserve cross-topic implementation dependencies for join with q1 (architecture/data/storage/transport). This discovery was written from the brief alone, before plan reveal. No plan file was read.

## 1. Product / approach landscape (O1)

Studied from primary docs (see source-map.json, sources/index.md). Unfamiliar-useful emphasis beyond a thin static-site default:

- Backstage TechDocs: docs-as-code portal. Authors write Markdown in `docs/` beside code with `mkdocs.yml` using `techdocs-core`; CI generates and publishes to storage; portal renders inside Backstage catalog entity (`backstage.io/techdocs-ref`). Strength: one discovery surface for services, per-service ownership. Limitation observed: no first-class multi-version/preview in core; versioning is a community addon (WIP) tied to feature request backstage/backstage#16711. Consequence: released-version scoping must be designed outside core TechDocs or via addon + storage layout.
- Antora: modular static generator for AsciiDoc, aggregates versioned content repositories via a playbook into component versions. Versions are first-class (branches/tags as version sources, `antora.yml` name/version/display_version/prerelease, sorting, facets, distributed component versions, stable resource IDs/xrefs across versions). Strength for three codebases + frequent releases: each repo/tag becomes a component version with stable cross-version links. Cost: AsciiDoc-first, not Markdown-first; multilingual is not its headline path.
- Starlight (Astro): modern Markdown/MDX docs with built-in i18n routing, fallback content, RTL support, and default Pagefind offline search with no configuration. Versioning is not first-class like Docusaurus; versions are modeled as content sections or community plugins. Strength: multilingual + offline search out of box, low maintenance. Gap: released-version semantics must be imposed by content layout + search scoping.
- Docusaurus v3.10.2: snapshot versioning (`docs/` = next/unreleased, `docusaurus docs:version <ver>` freezes to `versioned_docs/version-<ver>/`, `versions.json`, `lastVersion` controls default). i18n by filesystem (`i18n/<locale>/...`), per-locale build/deploy, Crowdin/Git workflows. Search: official Algolia DocSearch (hosted, weekly crawl, free for public dev docs; firewall/private needs run-your-own), plus community Typesense/local-search options. Strength: version + locale + search in one system. Costs: build time and contributor complexity grow with versions; maintainers warn not to version prematurely.
- MkDocs Material + mike: `mike deploy --push --update-aliases <ver> latest`, `mike set-default`, `versions.json` on `gh-pages`, Material `extra.version: provider: mike` renders selector, alias redirect, stay-on-page switching, version warning banner. Strength: simple branch-published version dirs, good version UX. Implies branch publishing (gh-pages), not Actions-artifact path; search scoping across versions must be handled (per-version index or filter).
- Sphinx + gettext + sphinx-intl + Weblate/Transifex: established POT/PO translation flow (`locale_dirs`, `gettext_compact`, `sphinx-intl update`), team translation services, multiple builders (HTML, PDF/LaTeX). Strength: rigorous multilingual + print/PDF export + cross-references/domains. Cost: reStructuredText-first (Markdown via MyST is secondary), heavier authoring.
- Search backends as products, not just plugins:
  - Pagefind: fully static post-build indexer. Runs after static build, emits bundle to `pagefind/` (default output subdir), no server component. Control via `data-pagefind-*` attributes, `root_selector` default `html`, `exclude_selectors`, filters/metadata, multilingual segmentation with extended binary for CJK (`pagefind_extended`), `Intl.Segmenter` for CJK queries, `force-language`. Strength: zero infra, low bandwidth, offline-friendly, good default for Starlight. Limits: index is per build output; multi-version scoping requires per-version bundle + selector or custom filter design; large sites create many chunks.
  - Typesense (self-hosted): query (`q`, `query_by`) + `filter_by` on facet/numeric fields, `sort_by`, pagination `page`/`per_page` (default 10), highlight snippet with `<mark>`, typo tolerance params. Version/locale/codebase scoping is a filter expression (e.g. `version:=v2 AND locale:=en`). Requires facet fields in schema; filter changes are query-time.
  - Meilisearch v1.54.3 (self-hosted): `filterableAttributes` must be set before filtering; updating it rebuilds index (cost proportional to dataset); `sortableAttributes`; facet search requires filterable; tenant tokens can scope results. Same version-filter pattern as Typesense, but schema change cost is explicit.
  - Algolia DocSearch: hosted crawl + front-end query, `contextualSearch` option for version context in Docusaurus. Inapplicable as hosted free tier for private-behind-firewall internal portal; run-your-own or local/Typesense alternative needed.
- Contradiction/quality aids (no silent rewrite):
  - Vale (Go CLI): code-like prose linting, not grammar correction. YAML extension system (`substitution`, `swap`, `message`, `level: error`, `ignorecase`), `.vale.ini` core keys (`StylesPath`, `Packages`, `MinAlertLevel: suggestion|warning|error`, `IgnoredScopes/SkippedScopes`, `[formats]` map), `vale sync` installs packages, `vale ls-config` resolves effective config. CI gate fails on error. v3.22+ supports filename/glob format maps. Use: terminology consistency, banned rewrites, flag contradictions for human queue. Explicitly does not rewrite docs.
  - Complementary: dead-link fail build (`mkdocs build --strict`, Docusaurus build), version-aware diff reports (what changed between released versions, which passages conflict), explicit contradiction queue UI. LLM rewrite is rejected by brief constraint; LLM may only propose cited candidates for human accept.
- Code/doc linkage: colocated `docs/` + entity catalog (Backstage) + stable permalinks (release tag + file path + anchor) + API extractors (TypeDoc-class) rendered as Markdown + “change the source” links to live tag. Citations must carry version + locale + path + excerpt hash, not just URL.
- Migration/export options: keep Markdown/MDX or AsciiDoc/rST as source of truth; static HTML bundle per release; PDF via Sphinx/LaTeX or browser print; offline search bundle (Pagefind) or index snapshot (Typesense/Meilisearch); Pandoc-class conversion for import/export. Export must preserve anchors and version labels so citations survive migration.

## 2. Consequential behavior, defaults, limits, applicability (O2)

- Pagefind: post-build only; `--site <PATH>` required, `--serve` is preview-only shortcut. Defaults: `output_subdir=pagefind`, `root_selector=html`. Filters/metadata outside root selector are not detected. `exclude_selectors` accepts one selector via CLI/env (comma-joined) but lists via config file. Applicability: internal static portal with infrequent index service ops; for three codebases × N versions × M locales, plan per-version/per-locale bundle layout and selector that loads the matching index so a result never leads to another version. CJK notes require extended build + language config; verify with target locales.
- Docusaurus versioning: snapshot is explicit CLI; after cut, `docs/` becomes next. `versions.json` + `versioned_docs/` + `versioned_sidebars/` are the frozen state. Default released version via `docs.lastVersion`. Only version on doc-breaking releases; cap retained versions (e.g. last three minors per major) to bound build time. Versioned + localized multiplies (`i18n/<locale>/docusaurus-plugin-content-docs/version-<ver>/`); default guidance observed: localize current only unless demand proves otherwise; deploy locales independently. Search applicability: use per-version index or `contextualSearch`/filter so browsing v1 returns v1; canonical duplication across versions is a known unresolved default (see O3), so version scoping cannot rely on SEO canonical.
- MkDocs+mike: `mike deploy <ver> latest --update-aliases --push`, `mike set-default`. Material reads `versions.json`. Alias types: redirect (static-host friendly) vs symlink/copy. Stay-on-page and warning banner are UX conditions for “relevant released version.” Applicability: simplest version UX for Markdown teams already on MkDocs; needs gh-pages branch publishing and PR-preview discipline (preview deploys must not pollute `latest`/default).
- Starlight: `locales` + `defaultLocale` in integration config; content under `src/content/docs/<locale>/` or root locale; fallback serves default-locale page with badge when translation missing; UI strings via `src/content/i18n/` + translation schema extension. Search default Pagefind; hide via frontmatter/page exclude or `data-pagefind-ignore`; alternatives via Algolia/Typesense plugins. Applicability: best multilingual-static default; versioning must be added by layout/plugin + search scoping.
- Typesense: `q` + `query_by` + `filter_by` (e.g. `num_employees:>100`, string equality `field:=value`, multi `field:=[a,b]`, range `field:>=min`), `sort_by`, `per_page` default 10. Highlight returns `field/snippet/matched_tokens`. Facet/filter fields must exist in records; scope internal search by indexed `version`, `locale`, `codebase`, `release_tag` attributes. Applicability: self-hosted, firewall-friendly, exact-passage snippets for citations.
- Meilisearch: filtering requires advance `filterableAttributes` (mandatory, not search-time); update triggers full re-index; same for `sortableAttributes`; facet search only on filterable, prefix-only, no numeric facet search (convert to string). Scope by `version/locale/codebase` filterable attrs. Tenant tokens for future multi-tenant scoping. Applicability: same as Typesense with explicit reindex cost on schema change — declare filterable set at index creation.
- Vale: `.vale.ini` shape: global keys above first header, `[formats]` map, other sections are globs. Unknown keys warn, misplaced core/section keys error naming the key. `MinAlertLevel` enum gates output; `--minAlertLevel` flag overrides. `[*.{md,mdx}] BasedOnStyles`, per-rule `=NO` off switches. `vale sync` required after clone/worktree (gitignored styles). Applicability: terminology + contradiction-pattern rules as CI errors, style suggestions as warnings; JSON output (`vale --output=JSON`) feeds contradiction queue; never auto-applies fixes in portal path.
- Sphinx i18n: gettext-based since v1.1; `sphinx-build -b gettext` emits POT, `sphinx-intl update -p _build/gettext -l <lang>` updates PO, translators edit PO, build per locale. `locale_dirs`, `gettext_compact`, `gettext_uuid` govern catalogs. Weblate/Transifex for team flow. Applicability: when rigorous translation memory + PDF + cross-refs outweigh Markdown simplicity; migration cost from Markdown notes is real.
- Antora versioning: content sources declare branches/tags/refs; playbook aggregates; `antora.yml` per component version; prerelease/display_version/sorting/facets; resource IDs (`component:module:page`) give stable xrefs across versions. Applicability: three codebases as three components, each tag a version; best version-link stability; AsciiDoc lock-in is the tradeoff.

## 3. Issue / fix / regression / release evidence (O3)

- Backstage backstage/backstage#16711 “TechDocs preview” (+ versioning): core lacks PR preview and multi-version display; community `backstage-plugin-techdocs-addon-versioning` claims to solve it but self-describes as work in progress, not production-ready. Consequence: do not promise released-version search + preview from core TechDocs alone; plan addon or separate versioned static portal behind catalog links. Status observed via issue page + addon README.
- Docusaurus cross-version search/canonical: long-standing behavior where version snapshots duplicate pages; automatic cross-version canonical was requested and closed as wontfix as out of core scope (secondary report corroborated by versioning docs structure). Mitigations observed in the wild: per-version local-search index (each version loads its own index; result never crosses versions), `contextualSearch: true` for Algolia, version caps. Also: a stale frozen `versioned_docs/version-*` can fail the whole site build while current builds fine — version snapshots are independent failure domains. Consequence: version-scoped search must be explicit, not assumed.
- Pagefind multilingual evolution: CHANGELOG/Releases show v1.0.x hotfixes restoring default-on multilingual segmentation and `pagefind_extended` binary for CJK; later CJK query segmentation via `Intl.Segmenter`, `force-language`, custom index language. Consequence: CJK locales need extended build + verification; do not assume default binary covers target languages.
- Vale evolution: `.vale.ini` filename/glob `[formats]` requires v3.22.0+; older installs silently(?) mis-scope those files — pin minimum Vale version in CI and document it. `vale sync` missing-styles failure names a missing path, not “not set up” — onboarding runbook must include sync step.
- Absent/inapplicable: no usage/billing observations (null); no silent-rewrite mechanism endorsed — absence is intentional per brief. No runtime witness executed (no qualified sandbox available); see validation section.

## 4. Cross-topic dependencies preserved for q1 join

- Version store layout ↔ URL/routing ↔ search scope: whether versions are directories (`/v2/...`), snapshots (`/docs/v2/...`), or components, the search layer must receive the same `version` key the router displays. Per-version static bundle and filtered service index are two implementations of one contract: displayed version = searched version.
- Release cut ↔ index build: static post-build index (Pagefind) runs after each version build; service index (Typesense/Meilisearch) needs document batch with `version/locale/codebase/release_tag` + filterable schema fixed upfront (Meilisearch reindex cost). Frequent releases favor automated tag→build→index pipeline with idempotent version keys.
- Locale fallback ↔ search fallback ↔ citation label: if page falls back to English, search excerpt and citation must label the fallback locale, not masquerade as translated. Index per locale + fallback badge is one coherent design.
- Code linkage stability: citations need tag-pinned code links; `main` links rot. Release pipeline should emit a manifest (doc version → code tags) that search/citation rendering consumes.
- Storage/transport (q1) owns: artifact store, index hosting, cache, auth; q2 owns: version/locale selector UX, scoped query construction, citation rendering, contradiction queue, export UX. Contract between them is the version-locale-codebase key set + passage locator format.

## 5. Workflow / usability / options synthesis (q2 focus)

- Authoring: Markdown/MDX default (lowest friction for 60 engineers), AsciiDoc only if Antora version-link value outweighs retraining, rST only if Sphinx PDF/gettext value dominates. Colocate docs with code (`docs/` per repo), preview per PR, Vale + link check as required gates, human merge.
- Release: tag code → freeze docs snapshot (Docusaurus version / mike deploy / Antora tag version / Starlight layout version) → build versioned site → build/scope search index → update `latest`/default alias → publish manifest. Keep `next` visibly distinct from released; never serve `next` as default search scope.
- Search UX: selector for version + locale + codebase, defaulting to relevant released version (latest stable for that codebase, not global latest); results show version/locale badges, exact passage excerpt with `<mark>`-style highlight, link to anchored passage; “other versions say otherwise” hint when same page differs across versions (contradiction surfacing, not rewriting).
- Contradiction queue: Vale errors + link failures + cross-version diffs feed a maintainer inbox grouped by page/version/locale; each item shows competing passages side by side with citations; actions are edit/accept/retire, never auto-fix. Multilingual contradictions show source vs translation with fallback labels.
- Migration/export: source stays portable (Markdown or AsciiDoc); export offers versioned HTML bundle, PDF for release notes/compliance, offline search bundle or index snapshot, and manifest. Import path via Pandoc-class conversion + anchor preservation check. Retire unsupported versions on a schedule to bound search/build cost.
- Options retained (not collapsed): (a) Docusaurus + per-version local/Typesense search; (b) MkDocs Material + mike + per-version index; (c) Starlight + Pagefind + layout versioning; (d) Antora for AsciiDoc multi-repo versioning; (e) Sphinx for gettext/PDF rigor; (f) Backstage TechDocs as discovery shell over any versioned static backend. Hosted Algolia only if public/firewall allows; otherwise self-hosted.

## 6. Validation: executed vs proposed (O6)

Executed: public primary-source reads via web_fetch during 2026-10-09T18:25–18:27Z (see source-map observed operations). No runtime, no witness, no sandbox execution — no qualified sandbox was available, and assignment forbids arbitrary execution. No usage/billing observed (null).

Proposed discriminating validations (for build/test stage):
- V1 Released-version scoping: seed v1 + v2 with deliberately different passages; assert queries from v1 UI return v1 excerpts and links, never v2, for each backend option. Discriminates per-version index vs filter correctness.
- V2 Exact-passage citation: assert every result carries version + locale + path + anchor + excerpt hash and the anchor resolves to the quoted passage in the built HTML. Fails on drift/rewrites.
- V3 Locale fallback honesty: request untranslated page in locale X; assert fallback badge + English excerpt labeled as fallback in both page and search. Discriminates routing vs index mismatch.
- V4 Contradiction visibility without rewrite: introduce controlled terminology conflict and cross-version fact difference; assert queue shows both passages with citations and no source file was auto-modified. Vale error rate vs false-positive rate reported.
- V5 Release-cut rehearsal: tag a test release, run tag→snapshot→build→index→alias pipeline twice (idempotence), assert `latest` points correctly, old links still resolve or redirect, search scope updates. Discriminates alias/redirect vs copy designs.
- V6 Export round-trip: export a version to HTML bundle + PDF + offline index; assert anchors/version labels/citations survive and offline search answers the V1 probe. Discriminates backend lock-in.
- V7 CJK/extended search (if locales need it): assert CJK queries segment and return excerpts under extended build; fails on default binary. Discriminates Pagefind build choice.
- V8 Usability walkthroughs: maintainer triages 10-item contradiction queue; author previews PR docs; reader finds released answer in ≤3 clicks with visible version badge. Qualitative but discriminating across portal options.

## 7. Uncertainty and open inputs

- Target locales (especially CJK?) decide Pagefind extended vs default and Sphinx-gettext vs filesystem-i18n weight.
- Firewall/public status decides Algolia-hosted viability vs self-hosted Typesense/Meilisearch/Pagefind.
- Source format preference (Markdown vs AsciiDoc vs rST) decides Antora/Sphinx vs Docusaurus/Material/Starlight.
- Version retention policy (how many releases searchable) bounds build/index cost and retires stale contradictions.
- Backstage presence: if the org already runs Backstage, TechDocs-as-shell is strong; otherwise a standalone versioned portal is simpler than adopting Backstage for docs alone.
