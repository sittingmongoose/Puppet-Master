## Material findings (must fix; each would change the build if ignored)

### M1 — P1 availability equation omits counted/multi-unit tools
- Challenge (CQ1/CQ7): the draft's atomic safeguard is `EXCLUDE USING gist (tool_id WITH =, tstzrange(...) WITH &&)`. This is correct for unique tools but makerspaces hold multiples (draft itself cites "Angle Grinder" ×3 under P4). Three identical grinders need count semantics (at most N overlapping confirms per model), which a per-`tool_id` exclusion cannot express; per-unit rows need a unit-assignment policy (any-unit vs named-unit booking).
- Evidence: predecessor S02/S11 excerpts cover only single-resource exclusion; S09 YaleSTC chain is about equipment counts ("availability falls below zero", "negative equipment availability") — i.e., the cited authority itself counts units, but the draft's equation ("which reservation states count, over which interval") never says what happens when quantity > 1. Independently confirmed C01: exclusion compares row pairs; counting requires a different construct (partial unique indexes per unit, serializable ledger-winner, or advisory-lock counting).
- Demand: extend the equation with a quantity rule (unique-unit vs counted-model), a unit-assignment policy, and one P-V6 matrix row plus one P-V1 counted-case (N+1 parallel attempts against N units → exactly N confirm).
- Uncertainty: low on the gap (text objectively absent); the fix shape is a design choice, not dictated by evidence.

### M2 — No offline authentication/identity story (P3/D2 gap)
- Challenge (CQ8): P3 permits offline checkout at both sites during Wi-Fi outages, and P-V2 tests offline checkout + reserve. Nothing says HOW an offline member/staff identity is established: cached credentials, member PIN, trust-and-reconcile, staff-only offline mode? Actor identity is load-bearing elsewhere (ledger actor in P2, repair actor in P5, conflict "both versions + timestamps + actors" in P-V2) but has no offline acquisition mechanism.
- Evidence: predecessor Q3/P3 evidence covers transport (S03/S04/C02), arbitration policy, and PWA shell — none covers identity. Absence verified by full-text inspection of draft + discovery. This is a genuine omission, not a user decision yet recorded (D2 covers scarce-tool partition behavior, not identity).
- Demand: add user decision D7 (offline identity: cached-auth vs PIN vs staff-only vs trust-on-reconnect, with revocation window) and extend P-V2 with an identity case (revoked/lapsed member checks out offline → on reconnect the intent is flagged, not silently honored).
- Uncertainty: medium — the right choice depends on unobserved staff practice; the demand is for an explicit decision + test, not a specific mechanism.

### M3 — No membership lifecycle model (brief: "members reserve tools")
- Challenge (CQ9): the draft models reservation intents, actors, and availability policy (D1) but never models membership itself: join/renew/lapse/revoke, and what each state does to existing reservations and availability. Predecessor's own S14 evidence notes MyTurn members "sign-up or renew their memberships" — the observed baseline has membership state, but the draft drops it. Consequences leak into D1 (do a lapsed member's future reservations still block? are they auto-cancelled?) and M2 (offline checkout by a lapsed member).
- Evidence: full-text inspection — "member" appears only as actor/requester; no membership states, no lifecycle, no retention rule. Brief obligation "members reserve tools" makes this in-scope, not gold-plating.
- Demand: add a minimal membership state rule (active/lapsed/revoked + effect on new vs existing reservations) as a user decision with a default (recommend: lapsed blocks new reservations, existing reservations stand until staff review), and one P-V6 matrix row.
- Uncertainty: medium — default is a recommendation; staff must confirm. Critic demand for SOME rule is strong; demand for the specific default is weak (validly overridable).

### M4 — P-V1 and P-V5 lack per-architecture pass criteria (validation applicability)
- Challenge (CQ6/CQ10): P-V1's pass ("exactly one confirms absent app pre-check (exclusion/serializable), else a documented race window + staff-visible arbitration") is written for alternative D (Postgres) but alternatives A (SQLite single-writer: serialization makes the test trivially pass — it discriminates nothing), B (CouchDB multi-master: two offline confirms are BOTH expected, arbitration is the pass condition), and C (PowerSync: sync-rule visibility + server arbitration) each need different pass criteria. P-V5 ("single binary + Litestream→S3 or equivalent") similarly assumes A; restore/re-sync drills for B (replication catch-up), C (re-sync from Postgres), and E (SaaS export) are different procedures, and "or equivalent" does not specify them.
- Evidence: alternatives A–E are retained in the draft (p. 72–73 of draft); P-V1/P-V6 text addresses only the Postgres/exclusion case. O6 requires "meaningful discriminating validations" — a validation that cannot be executed as written against three of five retained alternatives is not yet meaningful.
- Demand: parameterize P-V1 and P-V5 with one pass criterion per retained architecture (or scope each to named alternatives and mark the rest TBD). P-V2/P-V3/P-V4/P-V6 are architecture-agnostic as written — no change needed.
- Uncertainty: low — this is a completeness defect in the draft's own terms.
