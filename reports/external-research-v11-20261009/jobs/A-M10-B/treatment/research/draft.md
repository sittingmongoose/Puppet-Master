## Per-P disposition (every exact clause)

### P1: “Use a shared calendar for reservations.” → CORRECTION + OPTIONAL ENHANCEMENT + USER DECISION
- Verdict: do NOT use a shared calendar as the reservation system of record. A calendar stores events; it does not define or enforce reservation availability. Correction replaces it with: one availability equation + atomic confirmation + availability display derived from that equation, with a calendar VIEW as an optional enhancement.
- Why (evidence): lending availability is a family of decisions, not one check — YaleSTC Reservations regressed repeatedly across catalog vs calendar vs validation, requests vs approved reservations vs checked-out vs overdue vs renewal, date-vs-datetime boundaries, and display floors (PR #934/#932 fixed catalog/validation then found a renewal bug; PR #985/#982 floored negative display at zero; issue #1449 showed PR #1220 silently dropped checked-out items from the availability equation; PR #625 encoded overdue policy as availability math; PR #1580 made “requests block availability” a global option). A shared calendar answers none of these; each would become an emergent bug. Double-booking safety additionally requires atomic enforcement: with Postgres, an exclusion constraint (`EXCLUDE USING gist (tool_id WITH =, tstzrange(starts_at, ends_at) WITH &&)`, `btree_gist`, `'[)'` bounds, partial `WHERE` on active statuses) so concurrent overlapping confirms cannot both commit; without Postgres, a serialized confirm transaction or ledger-winner design with an explicitly documented race window. Application pre-checks alone double-book under concurrency.
- Already-covered fragment: none — discovery never endorsed calendar-as-record.
- Optional enhancement: calendar VIEW of confirmed reservations (Snipe-IT itself added calendar view as a new feature), plus one-way sync to external calendars if staff ask. View ≠ record.
- User decision D1: availability policy — do unapproved requests block availability? Do overdue items block tomorrow? May admins override hard validations (YaleSTC #1131 shows the override question is real)? Date or datetime granularity?
- Rejected: shared-calendar-as-truth (Google/Outlook/CalDAV as reservation store).

### P2: “Keep stock quantities in a database row updated by each client.” → CORRECTION
- Verdict: rejected as stated. Quantity must be DERIVED from a ledger of stock movements per location, never a single row that every client overwrites. Correction: append-only movement log (receive, checkout, return, consume, adjust, scrap) with actor + timestamp + note; current quantity = sum per item per location; writes carry idempotency keys so offline retries do not double-apply; math floors at zero for display while preserving the true ledger underneath.
- Why (evidence): client-updated quantity rows lose updates under concurrency (two sites/phones read 5, each writes 4, truth is 3 but row says 4); they go negative without policy; they erase history (who consumed the last spool?); they cannot represent two sites, rooms, or bins. InvenTree’s transferable fragments are cascading locations (site → room → shelf/bin) and serialized items with per-item test/commissioning records; Snipe-IT’s are the asset-vs-consumable split and per-item complete history; Grocy’s are batch/expiry tracking for the consumable tail. None of them stores truth as one client-written number.
- Conditions: asset tags stay string-typed (never numeric-coerce); consumables get reorder points + low-stock events; serialized lendables get per-unit history; adjustments require reason + actor.
- Optional enhancement: barcode scanning for decrement/issue (Grocy/Snipe-IT pattern), shippable after the ledger.
- Uncertain: exact reorder points and count cadence (no data on this makerspace’s consumption rates) — keep configurable, default to manual reorder flags.

### P3: “Permit offline checkout and reconcile by timestamp.” → ALREADY-COVERED (permit offline) + CORRECTION: REJECTED reconciliation (replace with explicit arbitration)
- Verdict: split. “Permit offline checkout” is already-covered and correct — both sites must keep checking out/in during Wi-Fi outages. “Reconcile by timestamp” (last-write-wins) is rejected and replaced with explicit conflict arbitration: every offline intent is queued with actor + device + timestamps + idempotency key; on reconnect the system applies non-conflicting intents, and surfaces every genuine conflict (same scarce tool double-claimed, quantity driven below zero, repair-state vs checkout race) with BOTH versions visible for staff resolution. No silent winner.
- Why (evidence): PouchDB/CouchDB prove offline-first multi-master sync works (browser PouchDB ↔ CouchDB, AP, eventually consistent, revision tree keeps ALL conflicting branches), but the deterministic winner every node agrees on is a database choice, NOT evidence of fairness or newness — presenting it as the outcome is a design error. Conflicts come in two kinds: immediate 409s on stale `_rev` (including live-replication races mid-edit, always handle; upsert-retry only for true deltas like counters) and eventual conflicts from offline edits on two replicas. Sync transport keeps improving (PouchDB 9.0 Delta Sync cut field bandwidth by up to ~50%), yet no release auto-arbitrates scarce-resource claims — by design it never will. PowerSync likewise moves transport to local-SQLite↔Postgres with server sync rules but leaves arbitration to the app. Timestamp order additionally fails on clock skew across two sites and phones.
- PWA shell required in all architectures: service worker (scriptable proxy + asset caching) + local store (IndexedDB/OPFS SQLite) + visible outbox + background sync. The shell governs “works with no network”; arbitration governs “two sites agree.”
- User decision D2: partition behavior for SCARCE tools — queue-and-confirm (accept offline reservation intents, confirm/staff-arbitrate on reconnect) vs refuse-offline-reserve (offline checkout of on-shelf items allowed, new reservations for scarce tools require connectivity)? Evidence cannot settle this; staff must.
- Rejected: last-write-wins / reconcile-by-timestamp; silent CRDT auto-merge for reservations (cr-sqlite-class auto-merge cannot satisfy detect-and-alert, and is unmaintained); treating sync as arbitration.

### P4: “CSV import overwrites matching names.” → CORRECTION (rejected as stated; replaced with staged keyed import)
- Verdict: rejected as stated on both halves: names are not keys, and overwrite is not an import strategy. Correction: staged import keyed on stable IDs (asset tag / SKU, string-typed), with upload → detect + preview first N rows with issues highlighted → column mapping with remembered per-source synonyms → dry-run validation with per-row errors → commit with report + undo window. Never direct-to-production.
- Why (evidence): PapaParse with `header:true` maps rows onto header keys and reports short rows as `FieldMismatch` in `parsed.errors` while `parsed.data` still carries the row with missing keys unset — viewers reading `parsed.data` alone draw silent empty cells (the exact bug fixed in observed commit 36f7dc5 “read the file a spreadsheet wrote”). Real sheets break naive importers with BOM/encodings (Excel dialects; `encoding` config; `utf-8-sig` vs `utf-8`), semicolon delimiters, ragged rows, duplicate headers (two `email` columns — dict parsing silently keeps one), embedded line breaks/quotes, header synonyms (“Tool” vs “tool name” vs “Item”), date/number formats, and missing markers (`N/A`, `NULL`, blank). Matching on names additionally collides on near-duplicates (“Angle Grinder” ×3), renames, whitespace/case, and merged sheets. Overwrite then destroys the production row it collided with.
- Conditions: detect delimiter/encoding/header-row with staff overrides; remember mappings per source sheet; type rules per column (IDs/quantities/dates); dry-run mandatory; commit report lists created/updated/quarantined rows; quarantine (not silent skip, not blind overwrite) for ambiguous matches.
- Optional enhancement: scheduled re-import / export-for-reports; supplier BOM-format uploads (InvenTree pattern) only if manufacturing scope ever arrives (currently out of scope).
- Uncertain: this makerspace’s actual sheet dialects (no corpus observed) — the staged loop is designed to absorb unknown dialects without developer help.

### P5: “Tool maintenance is a free-text note.” → CORRECTION (note retained as a field inside a repair CASE)
- Verdict: free text alone is rejected as the maintenance MODEL; retained only as the note field within a repair case. Correction: repair is a state machine with history — e.g., ready → flagged → in-repair → ready/archived — where every transition records actor + timestamp + note + optional parts used + optional photo. Each tool page shows its full timeline; a global feed shows recent repair/checkout activity.
- Why (evidence): Snipe-IT’s per-asset complete history + recent-activity snapshot and InvenTree’s serialized-item test/commissioning records show the transferable pattern: current state is always answerable (“is the table saw usable now?”) AND the story is answerable (“who had it when the guard broke? what changed since?”). A single free-text note answers neither reliably: it cannot gate reservations (flagged tools stay bookable), cannot show who/when, cannot track parts consumed, and is overwritten by the next note. Repair state must also feed availability (flagged/in-repair tools are unreservable by policy, with the policy itself a user decision).
- Conditions: flagging available to members (report issue from reservation, MyTurn-pattern “review and report issues”) with staff triage; in-repair transition restricted to staff; archived reason required (lost/stolen/broken).
- Optional enhancement: maintenance kits/checklists per tool class; due-date reminders; parts-from-consumables linkage.
- Uncertain: compliance/immutability needs (no regulatory evidence) — no tamper-proof claims; ordinary authenticated history suffices unless staff say otherwise.

### P6: “Test normal reservation and check-in flows.” → ALREADY-COVERED (keep) + CORRECTION (expand to discriminating validations)
- Verdict: normal-flow tests stay, but they are necessary, not sufficient — every YaleSTC regression passed normal flows. Correction adds the six discriminating validations below (P-V1…P-V6); each would change the plan if it failed.
- Executed checks (read-only; no runtime/sandbox; honest scope): E1 fetched primary docs (Postgres constraints, PouchDB replication/conflicts, PapaParse docs, Snipe-IT features, PowerSync overview, InvenTree index, Circulate repo) and converged exclusion syntax across 5+ snippets; E2 search-observed 6 YaleSTC availability records + PapaParse encoding issues to establish regression families; E3 cross-checked single-binary/Litestream roles across 3+ snippets (backup ≠ multi-writer); E4 verified discovery froze before plan reveal. No witness ran with side effects; no proposals are presented as executed.
- Proposed validations (discriminating; scoped to this small product, not unlimited production guarantees):
  - P-V1 concurrency: N parallel overlapping reservation attempts; pass = exactly one confirms absent app pre-check (exclusion/serializable), else a documented race window + staff-visible arbitration. Discriminates Postgres-exclusion vs app-only vs queue-and-confirm.
  - P-V2 partition: site B offline; checkout + reserve on both sites; reconnect; pass = zero silent loss, every conflict surfaces both versions + timestamps + actors, staff picks winner. Discriminates transport-only vs arbitration-complete.
  - P-V3 hostile CSV: BOM + semicolons + ragged rows + duplicate headers + Excel encoding + embedded newlines; pass = per-row errors shown, zero silent coercion, mapping remembered, dry-run before commit. Discriminates complete (`errors`+`meta` honored) vs `data`-only importers.
  - P-V4 repair-story query: “who had tool X when flag Y was raised, and what changed since?”; pass = answerable from timeline + activity feed without DB diving. Discriminates ledger-complete vs current-state-only.
  - P-V5 cold-start/restore: fresh operator restores candidate stack (single binary + Litestream→S3 or equivalent) to a known point within documented steps/time. Discriminates simple-claimed vs simple-demonstrated.
  - P-V6 availability matrix: requests block? overdue blocks tomorrow? checked-out counts? renewal inclusivity? cancelled/denied excluded? admin override?; pass = ONE equation implemented identically in constraint + validation + display with a test per cell. Discriminates specified vs emergent availability.

## Retained findings (what to build)

- Domain synthesis (no single observed product covers it): lendable ASSETS (unique, reservable, repairable, per-asset history) + CONSUMABLE stock (quantities by cascading location, reorder points, batch/expiry where relevant) + REPAIR cases (state machine + history) + RESERVATION intents (request → confirm → checkout → return/overdue). Borrow: Snipe-IT’s asset/accessory/consumable/component split + status ladder + history; InvenTree’s cascading locations + serialization; Grocy’s batch/expiry tail; Circulate/Yale’s lending lifecycle (holds/requests, loans, renewals, overdue).
- Availability equation first: state which reservation states count, over which interval, with which inclusivity (`[)`), whether requests block, how overdue/renewal/cancel count, and override policy — then implement identically in DB constraint + app validation + display. Without this equation every fix moves the bug (O3 Chain 1).
- Offline: PWA shell + local intent queue (idempotency keys, visible outbox) in ALL architectures; arbitration queue for genuine conflicts; never silent winners, never timestamp reconciliation.
- Audit: per-item full ledger (who/what/old→new/when/note) + global recent activity; repair transitions included; actor identity threaded through every write path (or trigger + session actor).
- Extensions first: REST API covering every action (kiosks/printers/scripts); outbound webhook events (checkout/checkin/overdue/low-stock/repair-flagged) with one chat target initially; CSV staged import + export. Future seams named, not built: SSO/LDAP, locker/PIN hardware, multi-tenancy, MDM adapters.
- CSV: staged keyed import per P4 correction; string-typed IDs; quarantine + report + undo.

## Alternatives retained (genuine trade-off, no forced consensus)

- A. Single-node simple core + offline-tolerant clients (RECOMMENDED default for “avoid complex hosting”): one host (either site or tiny VPS) running a single-binary backend (PocketBase-class: one Go binary, embedded SQLite, auth/realtime/storage/admin/REST, ~15–20MB, <30MB RAM, `./pocketbase serve`) or equivalent; PWA queue with idempotent apply; Litestream WAL→S3 for backup/PITR. Least ops. Limit: single-writer; partition behavior per user decision D2.
- B. Multi-master documents (CouchDB + PouchDB): both sites fully writable offline; revision-tree conflicts surfaced to staff. Most offline-capable; departs from relational modeling; needs the same arbitration layer; deterministic winner never shown as fair.
- C. Synced relational (PowerSync + Postgres): local SQLite UX, server Postgres truth, YAML sync rules per-user visibility, real-time. Keeps SQL; most operational surface.
- D. Single Postgres + PWA queue (variant of A with stronger guarantees): exclusion constraints for double-booking + queued intents; higher hosting cost than SQLite.
- E. Buy, don’t build: MyTurn (130+ lending libraries; browse/reserve/review/memberships) or Lend Engine (locker/PIN, API) — the baseline members will compare against. Retained as legitimate if custom build cost exceeds budget.
- Rejected with reason: shared-calendar-as-record; single-quantity-row; timestamp/LWW reconcile; name-matched overwrite import; free-text-only maintenance; silent CRDT auto-merge for scarce tools; Koha/OpenRoom (domain mismatch); PartKeepr (dormant); BOM/build depth (out of scope); Litestream-as-sync (it is backup, not multi-writer).
