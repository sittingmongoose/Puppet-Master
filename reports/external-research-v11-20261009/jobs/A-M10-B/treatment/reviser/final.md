## Per-P disposition (every exact clause)

### P1: "Use a shared calendar for reservations." → CORRECTION + OPTIONAL ENHANCEMENT + USER DECISION

- Verdict: do NOT use a shared calendar as the reservation system of record. A calendar stores events; it does not define or enforce reservation availability. Correction replaces it with: one availability equation (EXTENDED per M1 with a quantity rule below) + atomic confirmation + availability display derived from that equation, with a calendar VIEW as an optional enhancement.
- Why (evidence): lending availability is a family of decisions, not one check — YaleSTC Reservations regressed repeatedly across catalog vs calendar vs validation, requests vs approved reservations vs checked-out vs overdue vs renewal, date-vs-datetime boundaries, and display floors (PR #934/#932 fixed catalog/validation then found a renewal bug; PR #985/#982 floored negative display at zero; issue #1449 showed PR #1220 silently dropped checked-out items from the availability equation; PR #625 encoded overdue policy as availability math; PR #1580 made "requests block availability" a global option). A shared calendar answers none of these; each would become an emergent bug. Double-booking safety additionally requires atomic enforcement: with Postgres, an exclusion constraint (`EXCLUDE USING gist (tool_id WITH =, tstzrange(starts_at, ends_at) WITH &&)`, `btree_gist`, `'[)'` bounds, partial `WHERE` on active statuses) so concurrent overlapping confirms cannot both commit; without Postgres, a serialized confirm transaction or ledger-winner design with an explicitly documented race window. Application pre-checks alone double-book under concurrency (two transactions both pass an overlap check, both insert — the check-then-insert race).
- M1 quantity extension (ACCEPTED, new in this final): the per-`tool_id` exclusion above is correct ONLY for unique tools. Makerspaces hold multiples (this draft itself cites "Angle Grinder" x3). Three identical grinders need count semantics (at most N overlapping confirms per model), which a per-resource exclusion cannot express — exclusion compares row pairs (if any two rows are compared on the specified columns with the specified operators, at least one comparison must fail), so it can forbid pairs but cannot count triples. The equation therefore carries a quantity rule: (a) unique-unit tools use per-unit exclusion (or per-unit rows + exclusion); (b) counted-model tools use a counting guard — one of: per-unit rows with a unit-assignment policy (any-unit auto-assign vs named-unit booking) plus per-unit exclusion; or a serializable ledger-winner transaction that counts overlapping confirms and commits at most N; or an advisory-lock counted section. The choice is a design decision recorded at build time; the equation states which rule applies per tool class, and the P-V6 matrix carries one quantity row while P-V1 carries one counted case (N+1 parallel attempts against N units → exactly N confirm). The cited YaleSTC authority itself counts units ("availability falls below zero", "negative equipment availability"), so the draft's equation was incomplete without this rule; the disposition (correction) is unchanged, the equation is now complete.
- Timezone condition (m6, new): store tz-aware ranges, display site-local, evaluate boundaries in site tz. This is unconditional for any range-based design; date-vs-datetime granularity remains a D1 user decision.
- Already-covered fragment: none — discovery never endorsed calendar-as-record.
- Optional enhancement: calendar VIEW of confirmed reservations (Snipe-IT itself added calendar view as a new feature), plus one-way sync to external calendars if staff ask. View ≠ record.
- User decisions: D1 availability policy — do unapproved requests block availability? Do overdue items block tomorrow? May admins override hard validations (YaleSTC #1131 shows the override question is real)? Date or datetime granularity? PLUS D1-quantity (M1): per tool class, unique-unit vs counted-model, and for counted models any-unit vs named-unit assignment. PLUS D8 membership interaction (M3): do a lapsed/revoked member's existing reservations still block availability, or are they auto-cancelled/held for review?
- Rejected: shared-calendar-as-truth (Google/Outlook/CalDAV as reservation store).
- Uncertain: exact tool-class quantity list (which tools are unique vs counted) — keep per-tool-class configurable; default unique unless staff mark counted.
- Build-citation note (m1): the room-booking `tstzrange` overlap shape is converged across 5+ independent secondaries and the fetched Postgres primary confirms exclusion existence, GiST enforcement, and pairwise semantics (circles example); pin one stable-version Postgres page carrying a range-overlap example before citing as build authority. The finding stands.

### P2: "Keep stock quantities in a database row updated by each client." → CORRECTION

- Verdict: rejected as stated. Quantity must be DERIVED from a ledger of stock movements per location, never a single row that every client overwrites. Correction: append-only movement log (receive, checkout, return, consume, adjust, scrap) with actor + timestamp + note; current quantity = sum per item per location; writes carry idempotency keys so offline retries do not double-apply; math floors at zero for display while preserving the true ledger underneath.
- Why (evidence): client-updated quantity rows lose updates under concurrency (two sites/phones read 5, each writes 4, truth is 3 but row says 4); they go negative without policy; they erase history (who consumed the last spool?); they cannot represent two sites, rooms, or bins. InvenTree's transferable fragments are cascading locations (site → room → shelf/bin) and serialized items with per-item test/commissioning records; Snipe-IT's are the asset-vs-consumable split and per-item complete history; Grocy's are batch/expiry tracking for the consumable tail. None of them stores truth as one client-written number. The floor-at-zero-display/true-ledger split mirrors the YaleSTC floor finding (catalog/calendar floored at zero while math preserved the negative).
- Idempotency scope (m12, new): default shape is client-generated UUID per intent, deduplicated server-side; the scope (per device? per member? server-issued for kiosk flows?) and deduplication window are fixed at design time. This final does not invent the window; the build records it.
- Conditions: asset tags stay string-typed (never numeric-coerce); consumables get reorder points + low-stock events; serialized lendables get per-unit history; adjustments require reason + actor.
- Optional enhancement: barcode scanning for decrement/issue (Grocy/Snipe-IT pattern), shippable after the ledger.
- Uncertain: exact reorder points and count cadence (no data on this makerspace's consumption rates) — keep configurable, default to manual reorder flags.

### P3: "Permit offline checkout and reconcile by timestamp." → ALREADY-COVERED (permit offline) + CORRECTION: REJECTED reconciliation (replace with explicit arbitration)

- Verdict: split. "Permit offline checkout" is already-covered and correct — both sites must keep checking out/in during Wi-Fi outages. "Reconcile by timestamp" (last-write-wins) is rejected and replaced with explicit conflict arbitration: every offline intent is queued with actor + device + timestamps + idempotency key; on reconnect the system applies non-conflicting intents, and surfaces every genuine conflict (same scarce tool double-claimed, quantity driven below zero, repair-state vs checkout race) with BOTH versions visible for staff resolution. No silent winner.
- Why (evidence): PouchDB/CouchDB prove offline-first multi-master sync works (browser PouchDB ↔ CouchDB, AP, eventually consistent, revision tree keeps ALL conflicting branches), but the deterministic winner every node agrees on is a database choice, NOT evidence of fairness or newness — presenting it as the outcome is a design error. Conflicts come in two kinds: immediate 409s on stale revision (including live-replication races mid-edit, always handle; upsert-retry only for true deltas like counters) and eventual conflicts from offline edits on two replicas. Sync transport keeps improving (PouchDB 9.0 Delta Sync cut field bandwidth by up to ~50%), yet no release auto-arbitrates scarce-resource claims — by design it never will. PowerSync likewise moves transport to local-SQLite↔Postgres with server sync rules but leaves arbitration to the app (see m3 inference note below). Timestamp order additionally fails on clock skew across two sites and phones.
- PWA shell required in all architectures: service worker (scriptable proxy + asset caching) + local store (IndexedDB/OPFS SQLite) + visible outbox + background sync. The shell governs "works with no network"; arbitration governs "two sites agree."
- Offline identity (M2, new): the draft assumed an offline actor but never said how identity is established offline. Added as user decision D7: cached-auth vs member PIN vs staff-only-offline vs trust-on-reconnect, with a revocation window. Actor identity is load-bearing (ledger actor in P2, repair actor in P5, conflict "both versions + timestamps + actors" in P-V2); the mechanism is a staff choice, and P-V2 carries an identity case (revoked/lapsed member checks out offline → on reconnect the intent is flagged for review, not silently honored). See also M3 membership lifecycle.
- User decision D2 (retained): partition behavior for SCARCE tools — queue-and-confirm (accept offline reservation intents, confirm/staff-arbitrate on reconnect) vs refuse-offline-reserve (offline checkout of on-shelf items allowed, new reservations for scarce tools require connectivity)? Evidence cannot settle this; staff must.
- CouchDB operating limit (m7, new, alternative B only): compaction drops conflict bodies while keeping lineage, bounded by the revision-retention limit — losing branches remain resolvable only within that bound. Record the retention/compaction policy for B at build time.
- Outbox/conflict window (m11, new): the visible outbox and arbitration queue require a bounded retention + overflow policy (what happens to un-arbitrated intents after N days? storage cap?). No evidence bounds it, so this final does not invent numbers; the build records the bound.
- Rejected: last-write-wins / reconcile-by-timestamp; silent CRDT auto-merge for reservations (auto-merge cannot satisfy detect-and-alert — this rejection stands on the primary-doc design reason that conflict resolution is the application's job, WITHOUT relying on any maintenance claim per m2); treating sync as arbitration.
- Design-reason downgrades (m2/m3, accepted): the cr-sqlite maintenance note ("unmaintained since late 2024") rested on one secondary snippet and is NOT cited as governing — the rejection stands on design alone. The PowerSync-arbitration statement is marked as reasonable inference from sync-rules-as-visibility evidence, not as a directly observed arbitration doc — the transport-vs-arbitration conclusion stands.

### P4: "CSV import overwrites matching names." → CORRECTION (rejected as stated; replaced with staged keyed import)

- Verdict: rejected as stated on both halves: names are not keys, and overwrite is not an import strategy. Correction: staged import keyed on stable IDs (asset tag / SKU, string-typed), with upload → detect + preview first N rows with issues highlighted → column mapping with remembered per-source synonyms → dry-run validation with per-row errors → commit with report + undo window. Never direct-to-production.
- Why (evidence): PapaParse with `header:true` maps rows onto header keys and reports short rows as `FieldMismatch` in `parsed.errors` while `parsed.data` still carries the row with missing keys unset — viewers reading `parsed.data` alone draw silent empty cells (the exact bug fixed in observed commit 36f7dc5 "read the file a spreadsheet wrote"; the governing data/errors/meta triple with `FieldMismatch` type and `TooFewFields`/`TooManyFields` codes is confirmed on primary docs independently of that snippet per m5). Real sheets break naive importers with BOM/encodings (Excel dialects; `encoding` config; `utf-8-sig` vs `utf-8`), semicolon delimiters, ragged rows, duplicate headers (two `email` columns — dict parsing silently keeps one), embedded line breaks/quotes, header synonyms ("Tool" vs "tool name" vs "Item"), date/number formats, and missing markers (`N/A`, `NULL`, blank). Matching on names additionally collides on near-duplicates ("Angle Grinder" x3), renames, whitespace/case, and merged sheets. Overwrite then destroys the production row it collided with.
- Conditions: detect delimiter/encoding/header-row with staff overrides; remember mappings per source sheet; type rules per column (IDs/quantities/dates); dry-run mandatory; commit report lists created/updated/quarantined rows; quarantine (not silent skip, not blind overwrite) for ambiguous matches.
- Export condition (m8, new): export-for-reports uses explicit unparse settings (record delimiter, newline, quoting — observed defaults include `newline: "\r\n"`); round-trip through the staged importer must not surprise. One condition line; prevents a silent format regression.
- Optional enhancement: scheduled re-import / export-for-reports; supplier BOM-format uploads (InvenTree pattern) only if manufacturing scope ever arrives (currently out of scope).
- Uncertain: this makerspace's actual sheet dialects (no corpus observed) — the staged loop is designed to absorb unknown dialects without developer help.
- Provenance note (m5): commit 36f7dc5 is snippet-level (message + body, no diff fetch, honestly disclosed) and is cited as illustration only; the import rule (honor `errors`+`meta`, never `data` alone) stands on primary docs.

### P5: "Tool maintenance is a free-text note." → CORRECTION (note retained as a field inside a repair CASE)

- Verdict: free text alone is rejected as the maintenance MODEL; retained only as the note field within a repair case. Correction: repair is a state machine with history — e.g., ready → flagged → in-repair → ready/archived — where every transition records actor + timestamp + note + optional parts used + optional photo. Each tool page shows its full timeline; a global feed shows recent repair/checkout activity.
- Why (evidence): Snipe-IT's per-asset complete history + recent-activity snapshot and InvenTree's serialized-item test/commissioning records show the transferable pattern: current state is always answerable ("is the table saw usable now?") AND the story is answerable ("who had it when the guard broke? what changed since?"). A single free-text note answers neither reliably: it cannot gate reservations (flagged tools stay bookable), cannot show who/when, cannot track parts consumed, and is overwritten by the next note. Repair state must also feed availability (flagged/in-repair tools are unreservable by policy, with the policy itself a user decision).
- Conditions: flagging available to members (report issue from reservation, MyTurn-pattern "review and report issues") with staff triage; in-repair transition restricted to staff; archived reason required (lost/stolen/broken).
- Optional enhancement: maintenance kits/checklists per tool class; due-date reminders; parts-from-consumables linkage. Member-facing due-date/overdue reminders (m10, new) are a named future seam: staff-side webhook events ship first; member nudges (due-soon, overdue notice) follow the MyTurn-class baseline when staff confirm the channel.
- Uncertain: compliance/immutability needs (no regulatory evidence) — no tamper-proof claims; ordinary authenticated history suffices unless staff say otherwise.
