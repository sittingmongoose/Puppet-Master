## 0. What the brief demands (from the brief alone)

Desktop workbench for librarians: import, clean, compare small metadata collections. Four governing constraints, verbatim in spirit from the brief:

1. Third-party transformation extensions must be *useful without unrestricted host access* (the sandbox problem).
2. *Reproducible preview* — a transformation must be inspectable before commit and reproducible afterward.
3. *Undo* — reversible work.
4. *Offline export* and *future extension version upgrades*.

Obligations: O1 unfamiliar tools/approaches; O2 consequential primary-source behavior, defaults, limits, applicability; O3 an issue/fix/release evolution chain; O4 per-P comparison (only possible after reveal); O5 one coherent self-contained final retaining alternatives and uncertainty; O6 discriminating validations, executed work separated from proposals.

## 1. O1 — Landscape: real products and materially different approaches

**Domain-native tools (the librarians' world):**

- **OpenRefine** (SRC-03, SRC-06, SRC-12) — the de-facto open tool for cleaning messy metadata; Facet/cluster/GREL workflow; operation-log history; extension system. It is the closest existing product to this brief and the single richest comparable.
- **MarcEdit** (SRC-08) — MARC-centric manipulation tool for catalogers (7.8, .NET 10 LTS, 2026-07-05); macOS via Wine, Linux via mono, Windows installers incl. no-admin user-only; automation through a COM library (`MARCEngine75`) for "VBScripts or applications" and plugins (AI plugin "in development", OCLC Connexion plugin). Shows the real domain constraints: legacy MARC formats, JSON-LD interop pressure, Windows-first packaging, and a *host-scripted* (COM) extension model rather than a sandboxed one.

**Materially different extension-isolation architectures (the design space for the brief's core constraint):**

1. **In-process, no isolation** — OpenRefine extensions (SRC-03): Butterfly modules; server-side commands are Java classes instantiated from `controller.js` via Rhino's `Packages.` bridge; jars in `MOD-INF/lib` are "automatically loaded by Butterfly". The documentation states **no sandbox, no permission model, no isolation guarantees anywhere** — extensions are trusted JVM code. This is exactly what the brief forbids; it is retained as the negative baseline and as a *usable shape* (its registry of extension points — operations, GREL functions, importers/exporters, overlay models — is good API design independent of its trust model).
2. **Capability-gated embedded runtime** — Deno (SRC-01): all sensitive I/O denied by default; scoped grants (`--allow-net=example.com`, `--allow-read=./data`), `--deny-*` overrides, `NotCapable` errors, runtime `Deno.permissions` query/request/revoke. Applicability for a desktop host: run each extension in a zero-permission Deno Web Worker and expose *brokered host functions* instead of flags.
3. **In-process JS engine with explicit ceilings** — QuickJS (SRC-09): `JS_SetMemoryLimit()`, `JS_SetMaxStackSize()`, `JS_SetInterruptHandler()` (timeout). No ambient-authority model — safety comes from what the embedder *doesn't* expose. Cheapest isolation tier; weakest guarantee tier.
4. **WASM sandbox with capability imports** — Wasmtime (SRC-02) and Extism (SRC-10) on top of it: linear-memory isolation, no ambient authority, guard pages/regions, ANSI-escape filtering on terminal output; Extism adds polyglot PDKs (Rust/JS/Python/Go/…), runtime limiters/timers, and "host-controlled HTTP without WASI". Extism's docs-site concepts page 404'd this pass, so its manifest capability fields remain **unverified** (SRC-10 drift note).
5. **Two-context capability split** — Figma (SRC-04): main-thread sandbox that can touch the document but has no browser APIs (`fetch`, `setTimeout`, DOM), plus a UI iframe with browser APIs but no document access; message passing between them; **manifest-declared network allowlist enforced as CSP errors**; cooperative cancel + forced `closePlugin()` lifecycle.
6. **No code at all** — declarative transformation: JSONata (SRC-07), a "lightweight query and transformation language for JSON data" with embeddable implementations (JS primary; Java/C++/Go/Python/.NET/Rust ports at "varying version levels") and "configurable guardrails when embedding". Most librarian cleaning tasks (trimming, case/whitespace normalization, splitting, mapping vocabularies, reshaping JSON) are expressible declaratively. A GREL/JSONata-style expression tier makes *most* extensions safe by construction, shrinking the population of arbitrary-code extensions that ever need the sandbox tier.

**Synthesis (discovery-stage recommendation, subject to P-clause comparison):** a *tiered* extension model — (T0) built-in ops + declarative expressions (JSONata-like) as the default authoring tier; (T1) WASM extensions via an Extism-style framework with no filesystem/net grants by default and host-brokered I/O; (T2, optional later) worker-process runtime (Deno model) if a JS-native tier is demanded — with the Figma pattern's split applied to UI (extension UI sandboxed, manifest-declared domains, CSP-style enforcement) and the OpenRefine pattern applied to the *operation log* (below).

## 2. O2 — Consequential primary-source behavior: defaults, units, limits, applicability

- **Deno defaults (SRC-01):** deny-all I/O by default; units are *scopes on flags* (host, path, env var name); `--allow-run` and `--allow-ffi` **bypass the sandbox** ("especially dangerous": `--allow-run=deno`); `eval`/dynamic import/workers inherit privilege (so a host must not hand extensions an eval-capable surface together with grants); defense-in-depth guidance explicitly recommends Workers with reduced permissions + OS sandboxing. Applicability: process-per-extension or worker-per-extension; grants should stay at zero for transformation extensions.
- **Wasmtime guarantees and caveats (SRC-02):** bounds-checked linear memory; call stack inaccessible; type-checked control flow; "no ambient authority"; WASI FS is capability-based ("applications can only access files and directories they've been given access to"). Caveats a host must respect: 2 GB guard regions and CFI are mitigations *against possible Cranelift bugs*; Spectre mitigations are "ongoing research" (aarch64 `csdb` disabled by default for performance); ANSI escapes in guest terminal output are filtered because they had real side effects. Applicability: strongest isolation per extension; startup/compile cost and per-extension memory are the price; terminal-output filtering matters if the workbench renders extension logs.
- **QuickJS limits (SRC-09):** memory ceiling per `JSRuntime`, max stack size, interrupt-handler timeout (no dedicated CPU-budget API — timeouts are hand-built on the interrupt callback). Applicability: in-process tier for trusted-ish local expressions; **not** an authority boundary — pair with no-dangerous-bindings discipline and treat limits as availability (DoS) protection, not security.
- **OpenRefine extension surface (SRC-03):** extension points enumerated in §1; operations need static `reconstruct(Project, JSONObject)` (i.e., operations are JSON-round-trippable by design — the same property SRC-12 exploits); no security model stated. Applicability: copy the *shapes* (operation registry, expression-function registry, importer/exporter registry), reject the trust model.
- **Figma runtime split (SRC-04):** the document-facing sandbox lacks even `setTimeout`; all I/O lives in the UI iframe; manifest network allowlist produces CSP errors on violation; plugins must self-terminate or the user cancels. Applicability: UI/worker split maps cleanly onto a desktop workbench (preview pane = UI iframe analog; transform worker = document sandbox analog); manifest allowlists are a user-decidable permission UX.
- **JSONata (SRC-07):** declarative, embeddable, guardrail-configurable; ports are uneven ("varying version levels" — a port-maturity risk; the JS reference implementation is the conservative embed choice). Applicability: T0 tier; deterministic pure-function evaluation also makes preview/replay trivially reproducible.
- **OpenRefine operation log (SRC-12):** "save and re-apply the history of any project" as JSON; history doubles as audit evidence ("showing that your data cleanup didn't distort or manipulate the information in any way"); project archives carry *earlier data states* — a privacy hazard if the dataset was anonymized mid-history. Applicability: one log serves undo, reproducible preview (apply op to sample → show diff), and offline export (recipe JSON + data), with an explicit rule that exported bundles inherit the most sensitive historical state.
- **MarcEdit constraints (SRC-08):** COM automation ties scripting to Windows; macOS/Linux rely on Wine/mono/.NET runtimes. Applicability: a cautionary packaging datapoint — the workbench's extension runtime should be a bundled, self-contained engine (WASM or embedded JS), not an OS scripting bridge, if cross-platform offline behavior matters.

## 3. O3 — Issue/fix/release evolution chains (evidence retained)

1. **Wasmtime-wasi filesystem sandbox escape — GHSA-vqjp-4c8c-hfgg (2026-08-20, SRC-11).** Upstream cap-std bug (GHSA-hp8f-xmx4-4qrg): "a trailing slash could be used in specific circumstances to escape the filesystem sandbox" via symlink handling; guests could read/write arbitrary host files. Affected: "<= 24.0.12, >= 25.0.0, <= 36.0.13, >= 37.0.0, <= 46.0.2, >= 47.0.0, <= 47.0.3"; patched: "24.0.13, 36.0.14, 46.0.3, and 47.0.4" (48.0.0+ unaffected). CVSS v4 8.8; CWE-61; "no known workaround"; **not exploitable on Linux ≥ 5.6 with `openat2` `RESOLVE_BENEATH`**. Chain: dependency bug → escape in the isolation layer → four coordinated patch lines → platform-dependent exposure. Lessons: the sandbox implementation is itself attack surface; default extensions to *zero* filesystem grants so a sandbox bug has nothing to reach; pin patched runtime lines and ship host updates; defense-in-depth at the OS layer has version-dependent value. This is the strongest O3 evidence found; it is recent (two months old at access), concrete, and version-exact.
2. **Zotero 6→7→8 plugin migration (SRC-05).** "All Zotero plugins will need to be updated for Zotero 7"; XUL overlays dropped ("Most existing Zotero plugins use overlays and will need to be rewritten"); bootstrap lifecycle (`startup/shutdown/install/uninstall` + `ADDON_UPGRADE` reason + Zotero-7-only `onMainWindowLoad/Unload`); manifest compat gating (`strict_min_version`/`strict_max_version`, e.g. `"7.0.*"`); update manifest RDF→JSON with Zotero 7 unable to parse RDF (but JSON served from the old `.rdf` URL still processed); dual install.rdf+manifest.json coexistence for a migration window; new registries (`ItemTreeManager.registerColumn`, `ItemPaneManager.registerSection`, `Reader.registerEventListener`); platform breakage inventory (OS.File→IOUtils with "temporary" shims, XBL removed, .xul→.xhtml). Lessons for "future extension version upgrades": declare compat ranges in extension manifests; give extensions an explicit upgrade hook; keep shims temporary and say so; migrate update-feed formats with same-URL content negotiation.
3. **OpenRefine 3.9.4→3.9.5 and the moving extension API (SRC-06).** 3.9.4 marked pre-release: "This release failed to build correctly. Please see 3.9.5 instead" — a same-day supersession, i.e. real release hygiene under failure. Across 3.9.3→3.10.1 the extension-relevant surface demonstrably moves (new Geospatial extension, GREL additions, "custom clustering enabled for non-GREL expressions", cell renderers "3.7+" per SRC-03). Lesson: extension API drift is normal; the workbench needs a declared, versioned extension API and a compat matrix, not implied stability.

**Where evidence was absent or inapplicable (stated plainly):** no public security-issue chain for OpenRefine's own extension trust model was found this pass (absence of evidence, not evidence of absence); Extism's manifest capability fields were not verified (docs 404, SRC-10); no librarian-specific WASM plugin ecosystem benchmark exists to cite; GitHub's releases page did not display years for most OpenRefine entries, so exact release years are unverified (SRC-06). MarcEdit's plugin language/registration mechanism is not stated on its site (SRC-08) — not guessed.

## 4. Alternatives, conditions, and disagreements retained

- **Tiered model vs single mechanism:** the single-mechanism options (everything-WASM; everything-in-process-QuickJS) are simpler but fail one of the brief's two poles — WASM-only makes simple expressions heavyweight to author; QuickJS-only lacks an authority boundary. The tiered model (declarative default, WASM for code) conditions on: acceptable WASM compile/startup latency for interactive preview (untested — O6), and JSONata-port maturity for the host's implementation language.
- **Deno-worker tier (T2):** strongest JS ergonomics with real capability gating, but it pulls a whole runtime into the desktop app (packaging weight, offline update burden — cf. MarcEdit's mono/Wine story, SRC-08) and its escape valves (`--allow-run`/`--allow-ffi`) must never be granted to extension workers. Conditionally preferable only if a JS-native code tier is a hard requirement.
- **Figma-style UI split:** disagree-with-simplest-design point — putting extension UI in the same context as extension logic is tempting for a desktop app, but the split gives the manifest-declared network allowlist a natural enforcement point and keeps extension UI from touching the data file directly. Cost: message-passing plumbing and two toolchains.
- **Undo semantics:** log-of-operations (OpenRefine) vs snapshot-undo. The log wins on reproducibility and export (same artifact serves all three: preview/undo/export) but constrains extensions: every extension effect must be expressible as a replayable operation with deterministic behavior — non-deterministic or external-side-effecting extensions break the model and should be structurally impossible at T0/T1 (pure transform-in/result-out interfaces).
- **Preview semantics:** preview = run the operation against a bounded sample in the same sandbox and diff, *without* writing history; commit = append to log. Condition: sampling must be deterministic (stable row selection) or reproducibility claims weaken; undetermined this pass.

## 6. O6 — Proposed discriminating validations (none executed; no runtime available)

1. **QuickJS ceiling test:** embed QuickJS; set `JS_SetMemoryLimit` to 64 MB and an interrupt-handler timeout of 2 s; submit a memory-bomb and an infinite loop; *discriminates* whether limits hold under adversarial input vs merely polite code. Proposed.
2. **WASI zero-grant + escape simulation (lab only, patched line):** with a patched wasmtime (≥ 24.0.13 per SRC-11), run a guest given zero preopened dirs and one explicitly preopened dir; attempt path traversal patterns (trailing-slash/symlink shapes from the advisory description) against the preopened dir; *discriminates* whether the default-no-grant posture plus patched runtime resists the known escape class. Must run only in a qualified sandbox; never against host data. Proposed.
3. **Deno worker zero-permission test:** worker with no grants; attempt `fetch`, file read, `Deno.run`; assert `NotCapable` for each; then grant only a brokered host function and show net/file attempts still fail. Proposed.
4. **Operation-log round-trip:** apply a fixed op-JSON sequence to two copies of a sample dataset; byte-compare results; then truncate the log N steps (undo) and re-apply; *discriminates* log-undo correctness and reproducibility. Proposed.
5. **Preview determinism:** same preview request twice → identical sample and diff; then vary selection seed → observe whether history commits differ. Proposed.
6. **Manifest allowlist enforcement (Figma analog):** declare one allowed host for an extension UI; attempt a second; assert CSP-style block. Proposed.
