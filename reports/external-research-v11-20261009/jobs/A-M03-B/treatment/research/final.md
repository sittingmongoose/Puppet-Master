# Final — S09 plugin-workbench: external research, plan comparison, and design position

Case A-M03-B / treatment / research · 2026-10-09 · Method M03 v1 (researcher → critic-finalizer). This document is the complete, self-contained final (O5): it restates in prose everything needed to judge the conclusions; bracketed SRC-IDs merely point into the retained evidence (`source-map.json`, excerpts under `sources/`). The brief's exact obligations (O1–O6) govern coverage; §11 checks them one by one. Critique dispositions from the independent critic pass are in `criticism.md` and are incorporated here.

## 1. Scope and governing constraints (from the brief alone)

The product is a desktop workbench for librarians to **import, clean and compare small metadata collections**, where **third-party transformation extensions must be useful without gaining unrestricted host access**, and the workbench must support **reproducible preview, undo, offline export and future extension version upgrades**. Four constraints, one sentence each in the brief, each doing heavy design work:

1. *Useful but confined extensions* — the sandbox problem; the whole isolation architecture hangs on it.
2. *Reproducible preview* — a transformation must be inspectable before it commits and reproducible afterwards.
3. *Undo* — reversible work, without depending on extension cooperation.
4. *Offline export* + *future extension version upgrades* — portability today and a migration story tomorrow.

The brief also sets the investigative duties: real products and materially different approaches (O1); consequential primary-source behavior — defaults, units/types, limits, applicability (O2); at least one issue/fix/release chain, with honest absence statements (O3); comparison against every revealed plan clause with exact dispositions (O4); one self-contained coherent final retaining alternatives and uncertainty (O5); discriminating validations with executed work never conflated with proposals (O6).

## 2. Evidence base and its limits

Twelve primary public sources were fetched and retained on 2026-10-09 (access timestamps and observed operations, including three 404s and two 301 redirects, are recorded in `source-map.json`): Deno's security/permissions documentation; the Wasmtime book's security page; OpenRefine's extension-writing reference and its "Exporting your work" manual; OpenRefine's GitHub release listing (3.9.3–3.10.1); the Zotero 7 for Developers migration guide; the Figma "How plugins run" documentation; the QuickJS manual's memory/interrupt sections; the Extism README; MarcEdit's product site; JSONata's overview; and Wasmtime security advisory GHSA-vqjp-4c8c-hfgg.

Two evidentiary limits travel with every conclusion below. First, most sources are **unversioned live documentation** — the *concepts* (deny-by-default; no ambient authority; capability-scoped filesystems; manifest allowlists) are stable design inputs, but exact flags, manifest field names and version strings must be re-verified at build time. Where exact strings mattered, they are quoted verbatim from the source (the wasmtime advisory's affected/patched versions) or flagged unverified (Extism's manifest fields — the Extism docs concepts page returned 404 this pass; only the README was retrieved). Second, **no runtime was executed in this stage**: every check proposed in §10 is a proposal, and every performance-flavored question (WASM preview latency, limit magnitudes) is unanswered, not answered optimistically.

## 3. Landscape (O1): real products and materially different approaches

**The domain's own tools.** OpenRefine is the most prominent domain-adjacent open tool in the evidence gathered: a faceting/clustering workbench for messy data whose *extension system* is the closest existing analogue to this brief's — and whose trust model is the anti-goal. Its extensions are Butterfly modules; server-side commands are Java classes constructed from `controller.js` via Rhino's `Packages.` bridge, and jars dropped into `MOD-INF/lib` "will be automatically loaded by Butterfly"; the documentation describes **no sandbox, no permission model, no isolation guarantee anywhere** (SRC-03). That is unrestricted host access by construction — exactly what the brief forbids — while OpenRefine's *extension-point shapes* (registered operations, expression functions, importers/exporters, per-project overlay models) remain worth copying on their own merits. MarcEdit, the other librarian-facing product examined, is MARC-centric (7.8, built against .NET 10 LTS, released 2026-07-05), automatable through a COM library (`MARCEngine75`) for VBScripts and third-party tools, Windows-first with Wine on macOS and mono on Linux (SRC-08) — real-world proof that OS-scripting-bridge extension models carry heavy cross-platform packaging costs, and a caution for a desktop workbench choosing its extension runtime.

**Materially different isolation architectures.** Five distinct models were examined as candidates for "useful without unrestricted host access":

1. **In-process, trusted** (OpenRefine, above) — the baseline to reject.
2. **Capability-gated runtime** (Deno, SRC-01): "Deno is secure by default... no access to sensitive APIs" — file, network, environment and subprocess access all denied unless explicitly scoped (`--allow-net=example.com`, `--allow-read=./data`, `--deny-*` overrides, `NotCapable` errors, runtime `Deno.permissions` query/request/revoke). Its own docs identify the escape valves: `--allow-run` and `--allow-ffi` "effectively grant full access", and `eval`/dynamic imports/workers inherit privilege — so a safe host must hand extensions zero flags plus brokered host functions, never a shell-surfaced runtime.
3. **In-process engine with explicit ceilings** (QuickJS, SRC-09): `JS_SetMemoryLimit()` for a global allocation limit per runtime, `JS_SetMaxStackSize()`, and `JS_SetInterruptHandler()` — a callback "regularly called by the engine when it is executing code", usable "to implement an execution timeout". Feasibility of limits is proven; authority is *not* part of the engine — safety depends entirely on what the embedder declines to expose. Suitable for the expression tier, not for arbitrary third-party code.
4. **WASM sandbox with capability imports** (Wasmtime, SRC-02; Extism, SRC-10): bounds-checked linear memory, inaccessible call stack, type-checked control flow, "no ambient authority" — guests reach the world only through explicitly linked imports; WASI filesystem access is capability-based ("applications can only access files and directories they've been given access to"), with defense-in-depth (2 GB guard regions, CFI, memory zeroing, ANSI-escape filtering on terminal output) existing precisely because the sandbox implementation is itself attack surface. Extism packages this into a plugin framework: polyglot PDKs (Rust, JS, Python, Go, C/C++, .NET, Zig…), host SDKs across sixteen languages, "runtime limiters and timers", and host-controlled HTTP "without WASI" — outbound calls exist "if allowed", i.e. host-brokered.
5. **Two-context capability split** (Figma, SRC-04): plugin code "runs on the main thread in a sandbox" that can touch the document but has no browser APIs (no `fetch`, no `setTimeout`, no DOM), while a `figma.showUI()` iframe gets browser APIs but no document access; the two talk only via message passing; the plugin manifest can declare allowed network domains, and requests to others fail as CSP errors; the plugin must `closePlugin()` or the user cancels it. A proven shape for splitting data-touching logic from I/O-capable UI with user-visible permission grants.

**A sixth approach avoids the problem: no code at all.** JSONata — "a lightweight query and transformation language for JSON data" with XPath-3.1-flavored path semantics, embeddable implementations (JavaScript reference; Java, C++, Go, Python, .NET, Rust ports at "varying version levels") and "configurable guardrails when embedding" (SRC-07) — expresses normalization, splitting, vocabulary mapping and JSON reshaping declaratively. Whatever is expressible declaratively is safe by construction: deterministic, no host surface, trivially previewable.

## 4. Mechanism behavior that binds the design (O2)

- **Deny-by-default is a runtime property, not a property of processes.** A child process inherits the user's whole world; Deno's model (SRC-01) shows what a real grant system looks like (scopes, denies, catchable `NotCapable`) and where it leaks (run/ffi; eval inheritance). Consequence: P1's child-process mechanism is necessary but insufficient without an authority layer.
- **Filesystem capability layers still fail — in specific, patchable ways.** Wasmtime's WASI FS gave guests "only files and directories they've been given access to" (SRC-02) *and* shipped an escape (see §5). Consequence: default extensions to zero filesystem grants so that even a sandbox bug has nothing to reach; where a file tier is needed, hand an *opened capability* (preopened directory), never a writable path string.
- **Limit feasibility is proven; limit magnitudes are not.** Interrupt-handler timeouts, memory ceilings, stack limits (SRC-09), runtime limiters and timers (SRC-10), user-cancelable plugins (SRC-04) all exist. No evidence gathered supports specific default numbers; they are build-stage tuning targets (see C8 in `criticism.md`).
- **Operation history can be a serializable, replayable artifact.** OpenRefine exports "all the operations shown in the Undo/Redo tab" as JSON, re-appliable to another project, "useful for showing that your data cleanup didn't distort or manipulate the information in any way" — and its project archives "contain earlier data states", an explicit privacy hazard for anyone who anonymized mid-history (SRC-12). Consequence: one log can serve preview, undo, export and audit simultaneously; and every export must carry the earlier-states warning.
- **Declarative evaluation has embedder-side guardrails** (SRC-07) — the control surface for the no-code tier.
- **Extension UI and extension logic can be different trust contexts** (SRC-04) — the natural enforcement point for per-extension network allowlists and for keeping extension UI away from raw data.

## 5. Evolution chains (O3), with the absences stated

**Chain 1 — the isolation layer's own escape (strongest evidence of this pass).** Wasmtime advisory GHSA-vqjp-4c8c-hfgg (published 2026-08-20; also RustSec-2026-0269; underlying cap-std advisory GHSA-hp8f-xmx4-4qrg; CWE-61; CVSS v4 8.8 High; no CVE assigned): "Wasmtime's filesystem implementation provided in the wasmtime-wasi crate contained a bug which allowed guests to escape their filesystem sandbox and read/write external files and directories" — root cause a cap-std bug where "a trailing slash could be used in specific circumstances to escape the filesystem sandbox" during symlink handling. Affected versions, verbatim: "<= 24.0.12, >= 25.0.0, <= 36.0.13, >= 37.0.0, <= 46.0.2, >= 47.0.0, <= 47.0.3"; patched: "24.0.13, 36.0.14, 46.0.3, and 47.0.4" (48.0.0+ unaffected); "There is no known workaround for this issue"; and it was not exploitable on Linux kernels after 5.6 supporting `openat2` with `RESOLVE_BENEATH` (SRC-11). Full arc: upstream dependency bug → escape in the *sandbox itself* → coordinated patch releases across four maintained lines → platform-dependent exposure. Design lessons carried into §7: zero-by-default grants; pin patched runtime lines; the *host* needs an update path, not just extensions; OS-level mitigations have version-dependent value.

**Chain 2 — a platform's extension-migration discipline (the versioning evidence).** Zotero 7 "incorporat[ed] changes from Firefox 60 through Firefox 115" and declared "All Zotero plugins will need to be updated"; XUL overlays were dropped ("Most existing Zotero plugins use overlays and will need to be rewritten") in favor of bootstrapped plugins with `bootstrap.js` lifecycle hooks — `startup()`, `shutdown()`, `install()`, `uninstall()`, each receiving a reason constant including `ADDON_UPGRADE` — plus Zotero-7-only `onMainWindowLoad()`/`onMainWindowUnload()` window hooks; plugins declare explicit compatibility ranges (`strict_min_version`, `strict_max_version`, e.g. `"7.0.*"`) in a WebExtension-style `manifest.json`, with dual `install.rdf`+`manifest.json` coexistence during the migration window; update manifests moved RDF→JSON with Zotero 7 no longer parsing RDF but still accepting JSON served from the old `.rdf` URL; platform removals came with explicitly "temporary" shims (OS.File→IOUtils) (SRC-05). Lesson: version governance is done with *declared ranges, explicit upgrade hooks, and shimmed format migrations* — the exact opposite of silently loading whatever is newest.

**Chain 3 — release hygiene in the nearest comparable product.** OpenRefine 3.9.4 was marked pre-release: "This release failed to build correctly. Please see 3.9.5 instead" — a same-day supersession; and across 3.9.3→3.10.1 the extension-relevant surface visibly moved (new Geospatial extension, GREL additions, "custom clustering enabled for non-GREL expressions", cell renderers documented as "3.7+") (SRC-06). Lesson: extension APIs drift and even good projects ship broken releases; the workbench needs a declared, versioned extension API and a compat matrix, not implied stability.

**Honest absences.** No public security-issue chain for OpenRefine's extension trust model was found this pass (absence of evidence, not evidence of safety). No benchmark of librarian-specific WASM plugin ecosystems exists to cite. MarcEdit's site does not state its plugin languages or registration mechanism — not guessed. GitHub's releases page did not display years for most OpenRefine entries; chain order and content are verified, absolute years are not. Extism manifest capability fields remain unverified (docs 404).

## 6. Plan comparison (O4): exact per-P dispositions

The revealed plan, verbatim: *"P1: Run extension scripts as child processes. P2: Pass the dataset path and output directory as arguments. P3: A timeout limits each extension. P4: Store output as the new dataset after success. P5: Load the newest extension version automatically. P6: Test with a sample formatter."*

**P1 — "Run extension scripts as child processes." → Correction.** The mechanism is right (crash isolation; OpenRefine's in-process JVM model is the counterexample) and incomplete (a bare child process holds the user's whole authority). Carried forward: per-extension child processes **with zero ambient authority** — a capability-dropping runtime (zero-grant Deno worker/subprocess with host-brokered functions) or a WASM sandbox — plus OS sandboxing as defense in depth. First-class condition (critic point C10): extensions are **declared artifacts** — manifest with entry point, runtime/interpreter, version, checksum — never shell invocation strings; whether the plan's "scripts" meant raw executables is unresolved (§9), and if it did, this condition is the correction's most important part. Structural addition beyond the clause: a declarative expression tier as the default authoring path, so most transformations never run third-party code at all (coverage claim labeled a hypothesis, §10-v3).

**P2 — "Pass the dataset path and output directory as arguments." → Rejected as written, corrected in intent** (critic C5 sharpens the exact disposition). Rejected: string paths handed to extensions are ambient authority in both directions — they disclose where data lives and they grant whatever the path allows; the wasmtime-wasi escape (§5, chain 1) is a path-handling bug in a layer far more careful than raw arguments. Corrected intent, carried forward: **contents over stdin** (or equivalent bounded pipe) and results on stdout, no filesystem knowledge in the common case; for oversized collections, one host-created scratch directory opened once and handed as an opened capability to a runtime that enforces the boundary — never a replayable writable path. Optional capability with its own permission UX: manifest-declared per-extension network allowlists, user-approved, CSP-enforced (Figma pattern, SRC-04). Reproducibility condition: recipes record transforms and parameters, never machine-specific paths.

**P3 — "A timeout limits each extension." → Correction + optional enhancement.** Retained core: every invocation gets a wall-clock timeout. Corrected: a timeout alone is not a resource policy — memory and output size need ceilings too (feasibility: interrupt handler + `JS_SetMemoryLimit`, SRC-09; "runtime limiters and timers", SRC-10). Semantics carried forward: separate budgets for preview and commit runs (concrete defaults are explicitly build-stage tuning targets, not findings — critic C8); breach of a limit is a first-class preview result ("exceeded 2s/64MB" style, numbers illustrative only) so a buggy extension is distinguishable from a bad transform; user cancel with forced lifecycle termination (SRC-04's model). Units: seconds of wall clock per invocation; bytes of memory and output.

**P4 — "Store output as the new dataset after success." → Correction + conditions.** Direction kept; mechanism made reproducible. The operation log is authoritative: commit = validate, append a replayable operation (extension ID, pinned version, parameters), **materialize by replay, and require replay parity with the previewed diff** (critic C1 mechanizes the draft's slogan); parity failure quarantines the commit and records the extension as non-deterministic. A dataset snapshot is stored alongside for undo speed and recovery, with recorded provenance (which log positions it covers); for non-replayable extensions the snapshot is the recorded truth and exports warn that the recipe alone cannot reproduce the dataset (critic C2 resolves the source-of-truth ambiguity honestly). "Success" is defined: exit 0 + schema-valid output + replay parity. Undo = revert to a log position; no extension cooperation needed. Privacy condition retained from evidence: history carries earlier data states; exports must surface that (SRC-12).

**P5 — "Load the newest extension version automatically." → Rejected as stated; user decision retained for update-check UX.** Rejected on the brief's own axes: silent newest-version loading makes replay non-reproducible (a recorded operation's meaning changes under the project) and contradicts the migration evidence — Zotero gates with `strict_min_version`/`strict_max_version`, explicit `ADDON_UPGRADE` lifecycle, and shimmed update-format migration (SRC-05), while OpenRefine's own train shipped a broken release superseded same-day (SRC-06). Replacement: per-project **version pinning** recorded in the operation log; new operations may use newer installed versions; upgrades are explicit user actions with validation and shown compat ranges; the extension manifest carries declared compat ranges. The genuinely user-owned piece: whether the workbench *checks* for updates automatically and how it notifies — auto-check yes, auto-swap no.

**P6 — "Test with a sample formatter." → Retained + optional enhancement; partly uncertain.** A known-good sample formatter is the right end-to-end smoke test (import → preview → commit → undo → export). Enhanced: the test set must include the failure paths — limits enforced under adversarial input, zero-grant assertions, escape-shape simulation against the file tier, replay determinism, version-mismatch handling (§10). Uncertain and recorded as such: which metadata schema the sample formatter targets (MARC-family vs CSV/JSON) is a product decision the evidence cannot settle (MarcEdit shows MARC-centric gravity; OpenRefine shows the CSV/JSON world; SRC-08, SRC-03).

**Plan-coverage gap (recorded, not absorbed):** the brief's **"compare"** obligation has no P-clause at all. The operation-log architecture yields comparison naturally — replay the same recipe over two imported collections and diff — but this remains a scoping decision for the build stage (critic C7).

## 7. Integrated design position

Tiered extension model: **T0 declarative** (JSONata-like expressions with embedder guardrails) as the default authoring path — deterministic, host-free, hypothesis-labeled coverage claim; **T1 sandboxed code** (WASM via an Extism-style framework or zero-grant Deno worker) for transformations that need real code — declared artifacts, zero ambient authority, host-brokered I/O only; **T2 (conditional)** a JS-native worker tier if user demand requires it, never granted its escape valves. Cross-cutting: **operation log as the source of truth** with parity-checked replay and provenance-tracked snapshots; **two-context UI split** so extension UI holds the network allowlist and never raw data; **export bundle** = current dataset snapshot + operation-history recipe JSON (extension IDs + pinned versions) + a manifest with checksums and the workbench/extension version matrix + an explicit field recording whether history — and therefore earlier data states — is included (critic C6); **version governance** = pinning + declared compat ranges + explicit upgrade lifecycle + host-runtime update path. The bundled-runtime lesson from MarcEdit (SRC-08) argues the extension runtime should be self-contained (WASM or embedded engine), not an OS scripting bridge.

## 8. Alternatives, conditions, user decisions (retained, O5)

**Alternatives.** All-WASM (one sandbox, heavier authoring; rejected as sole tier). All-in-process QuickJS (cheapest; no authority boundary; kept only inside the expression tier). Deno-worker as the code tier (best JS ergonomics with real gating; costs a bundled desktop runtime; conditional on JS-tier demand). Snapshot-undo instead of log-undo (simpler; loses replay/export/audit; fallback for non-loggable operations only). Extension UI in-process (simpler plumbing; rejected for losing the allowlist enforcement point and the data/UI boundary).

**Conditions.** Content-over-stdin assumes practical pipe/memory limits (else capability-directory path, with patched-runtime condition). Log-undo assumes deterministic extensions (non-determinism is detected and quarantined, not assumed away — C1/C2). WASM tier interactivity assumes acceptable compile/startup latency — unmeasured. JSONata tier assumes a mature enough port (JS reference is the conservative choice). Pinning assumes the workbench ships an update mechanism so users aren't stranded on vulnerable extensions — the §5 advisory is the reminder that hosts need updates too.

**User decisions.** Auto-check for extension updates (on/off, notification style). Whether offline exports include history, with the earlier-data-states warning shown at export time. Per-extension network allowlist grants (requested in manifest, approved and revocable). Optional capability: a local, explicitly non-sandboxed console for the user's *own* scripts (MarcEdit's VBScripts audience), clearly separated from third-party extensions. Optional capability: compare-mode across two collections via recipe replay.

## 10. Executed checks vs proposed validations (separated, O6)

**Executed in this stage:** retrieval of the twelve sources (operations and timestamps recorded); the plan reveal; hash verification of discovery immutability across the reveal; JSON validation of the source map; this critique-and-finalization pass. **No runtime was executed; no sandbox was exercised; no extension ran; no benchmark measured anything.**

**Proposed (none executed):**
1. **Limit-enforcement test** (P3): memory-bomb and infinite-loop inputs against `JS_SetMemoryLimit` + interrupt-handler timeout or equivalent runtime limiters; also yields the data to set default budgets.
2. **Zero-grant + escape-shape simulation** (P1/P2): on a *patched* wasmtime line (≥ 24.0.13 per the advisory), a guest with zero preopened dirs and one preopened dir, attempting trailing-slash/symlink traversal shapes from GHSA-vqjp-4c8c-hfgg — qualified sandbox only, never against host data.
3. **Declarative-coverage classification** (T0, critic C3): classify a sample of public librarian cleaning recipes (e.g., Library Carpentry OpenRefine lessons) as declaratively expressible or not; report the fraction.
4. **Zero-permission worker assertion** (P1): `fetch`/file/`Deno.run` all `NotCapable`; brokered host function works; grants stay absent.
5. **Operation-log round-trip** (P4): same recipe JSON applied to two dataset copies, results compared byte-for-field; truncate (undo) and re-apply; replay-parity checked at commit.
6. **Preview determinism** (P4): identical preview requests → identical samples and diffs.
7. **Allowlist enforcement** (P2 optional capability): declared single host allowed; second host blocked as CSP-style error.
8. **Sample-formatter end-to-end with failure paths** (P6): happy path plus limit-exceeded, malformed output, and version-mismatch cases.
