## Brief restated (working scope)

Food bank, 180 volunteers, coordinators need predictable coverage; changing availability, recurring shifts, mobile access, accessible reminders, privacy-limited sharing, occasional imported rosters. Investigate competing products, constraints/optimizers and fairness options with implementation/version evidence.

## O1 — Products and materially different approaches discovered

Three materially different architecture families were examined with primary evidence, plus a fourth family from unverified leads:

1. **Commercial scheduling marketplace (self-signup).** VolunteerHub (S2, S3) is the direct product analogue. Primary-page quotes: volunteers "browse events, register, and manage their own schedules"; "Capacity limits prevent over-booking"; "Waitlists for full shifts" and "Fill cancellations with waitlists"; "Create recurring shifts in seconds"; "Duplicate schedules, reduce repetitive admin work"; the system "automatically sends confirmations, reminders, and follow-ups", with customizable timing and "email or optional text messages" plus manual reminders; list/calendar/map views on mobile-friendly pages; approval workflows and org-defined rules for volunteer self-cancellation; auto-grouping at registration ("Requires Orientation," "Requires Background Check"); a volunteer mobile app with on-site check-in; "Advanced Permissions" as the closest named privacy control; availability stored in the volunteer database ("contact information, skills, availability, and more"). *Useful and unfamiliar here:* waitlist-driven cancellation filling and registration-triggered group placement — both are coordinator-load reducers this brief did not name explicitly.
2. **CRM-integrated open-source extension.** CiviVolunteer (S4, S5) for CiviCRM: define "multiple volunteer projects", opportunities "with distinct roles and shifts", "manually assign volunteers to shifts", sign-up or interest-only registration, hours logging and reporting, relationship-based management ("Volunteer Manager" relationship decides who can manage). License AGPL-3.0 (with exception file). Crucially, the latest docs list **recurring opportunities only under "Future plans"** (together with skill-matching, organization links, public recognition, self-service hour logging) — i.e., recurring shift support is absent in the shipping product. Useful as the open-source, data-ownership-first alternative; its gap on recurrence is itself a design input.
3. **Constraint solver with explicit fairness metric.** Timefold (formerly OptaPlanner) quickstart `employee-scheduling` (S7). This is the strongest implementation evidence found for fairness and availability-aware optimization: hard constraints — required skill, no overlapping shifts (penalized by minute overlap), "At least 10 hours between 2 shifts" (penalized by missing break minutes: `(10 * 60) - breakLength`), max one shift per day, "Unavailable employee" (penalized by overlapping duration in minutes against `Employee::getUnavailableDates`); soft constraints — undesired/desired dates (penalized/rewarded by overlapping minutes) and `balanceEmployeeShiftAssignments`:

   ```java
   constraintFactory.forEach(Shift.class)
       .groupBy(Shift::getEmployee, ConstraintCollectors.count())
       .complement(Employee.class, e -> 0L) // Include all employees which are not assigned to any shift.
       .groupBy(ConstraintCollectors.loadBalance(...))
       .penalizeBigDecimal(HardSoftBigDecimalScore.ONE_SOFT, LoadBalance::unfairness)
   ```

   The `complement(..., e -> 0L)` line is directly relevant to the brief's "do not assume equal availability": fairness is computed over **all** employees including zero-assignment ones, so a rarely-available volunteer is not silently excluded from the fairness statistic. Score type is `HardSoftBigDecimalScore` (BigDecimal is required by `penalizeBigDecimal`/`LoadBalance`), hard/soft levels separate feasibility from preference; all time penalties are in **minutes (int)** derived from `Duration`.
4. **Solver with quota bands (alternative fairness family).** Google OR-Tools CP-SAT employee scheduling example (S10) distributes load with explicit integer bands instead of a fairness metric: `min_shifts_per_nurse = (num_shifts * num_days) // num_nurses`, and a max of min or min+1 depending on divisibility, enforced as linear constraints. Requests are a 3D binary array `shift_requests[n][d][s]`; the objective maximizes fulfilled requests (each contributes 1 — unitless counts, no weights). Coverage is `model.add_exactly_one(shifts[(n, d, s)] for n in all_nurses)` per shift and `model.add_at_most_one(shifts[(n, d, s)] for s in all_shifts)` per nurse-day.

Unverified leads (search snippets only, not fetched, not cited as evidence — retained per O5 as candidates for later primary verification): Schedly (advertises automated reminders 24h before shifts), Rosterfy (large-event volunteer workforce positioning), Better Impact / Volgistics / SignUpGenius / Zelos / Serve.love, app.timefold.ai constraint catalog ("Balance shift count", "Balance time worked"), Baeldung Timefold tutorial.

## O2 — Governing defaults, units, types, limits, applicability

- **Timefold quickstart (S7).** Score model: `HardSoftBigDecimalScore`, ONE_HARD per violating entity (or per minute where scaled), ONE_SOFT for preferences and fairness. Units: all temporal penalties in minutes. Fairness unit: `LoadBalance::unfairness` (a real-valued spread statistic over per-employee shift counts, BigDecimal-penalized). Default policy encoded: 10h minimum rest, one shift/day, unavailability hard, desire/undesire soft. Limits: none declared in the file; solver runtime limits live outside this file (not observed — recorded as absent evidence).
- **OR-Tools example (S10).** Types: booleans for assignments, 3D binary for requests. Units: objective in fulfilled-request counts; bands in integer shifts. Defaults: the requests example is run "with defaults — no `max_time_in_seconds`, `num_workers`, or other limits are set anywhere on the page"; the enumeration variant sets `linearization_level = 0` and `enumerate_all_solutions = True` and stops after 5 solutions via callback. Stated limits: none; the sample is 5 nurses × 3 shifts × 7 days, and the page notes enumerating all 5,184 schedules of the smaller example is "usually not practical" — a scale caution, not a model limit. **Applicability caveat:** the band formula implicitly assumes all nurses are available every day; with the brief's changing availability, bands must be computed per volunteer over days they are actually available (the quickstart's date-range availability model is the better template).
- **VolunteerHub (S2, S3).** Governing product defaults: capacity per event, waitlists, recurring shift creation, reminder channel = email + optional text with organization-customizable timing, self-service registration/cancellation governed by org-defined rules, permissions via "Advanced Permissions". These are product capabilities with no published algorithmic semantics (how waitlists rank, how recurrence expands) — observable behavior only.
- **CiviVolunteer (S4–S6).** Governance defaults: relationship-based permissions ("Volunteer Manager"), configurable project defaults for "manager, beneficiary, and other relationships", permissions `Edit Volunteer Project Relationships` / `Edit Volunteer Registration Profiles`. API invariant (2.2+): `VolunteerProject.create` auto-creates a flexible need; `VolunteerNeed.create` throws "would result in the creation of a second flexible need for a given project". Scale evidence: none published for 180 volunteers; absent evidence stated.

## O5 — Retained constraints, alternatives, disagreements, uncertainty

- **Original constraints carried forward:** 180 volunteers (modest scale — solver approaches are comfortably in range but band/enumeration examples at nurse scale are illustrative only); changing availability (availability must be first-class data, not an assumption); recurring shifts; predictable coordinator coverage; mobile access; accessible reminders (channel and timing configurable — accessibility beyond channel choice was not evidenced by any fetched source); privacy-limited sharing (only VolunteerHub "Advanced Permissions" and CiviVolunteer relationship permissions found as concrete mechanisms); occasional imported rosters (VolunteerHub integrations incl. Salesforce/Blackbaud/Zapier are evidence of import surface; CiviVolunteer inherits CiviCRM import tooling — neither fetched source documents a roster-CSV contract, recorded as absent).
- **Alternatives retained:** (a) fairness as a spread metric over all volunteers (Timefold `loadBalance`+`complement`) vs (b) fairness as min/max quota bands (OR-Tools) vs (c) fairness as product-level process (waitlists, rotation via duplicate schedules — VolunteerHub); (a) is the only one of the three that includes zero-shift volunteers in the statistic by construction.
- **Disagreement/tension:** quota bands are simple and auditable but break when availability differs across volunteers; a spread metric handles uneven availability only if the denominator is availability-normalized — neither fetched source normalizes fairness by availability, so a design would need to add that. This is a genuine open design point, not a settled finding.
- **Uncertainty:** VolunteerHub's algorithmic behavior (waitlist ranking, recurrence expansion, reminder default timing) is unpublished; CiviVolunteer release dates undated on the fetched pages; timefold-quickstarts has no GitHub Release objects (`releases/latest` returned none) so "2.3.0" is a tag/release-commit designation only; docs.timefold.ai fairness page 404'd on the first URL tried and was not pursued (snippet knowledge only).

## O6 — Proposed discriminating validations (proposed only; NOT executed)

No runtime/solver is available in this stage, so nothing below has been run; these are proposals. (1) Availability-normalized fairness test: build a toy instance where volunteer A is available 4× as often as B; check whether a `loadBalance`-style objective and a band objective both over-assign A, and whether dividing `unfairness` by available-shift capacity discriminates the two mechanisms. (2) Recurrence expansion audit: generate a weekly recurring shift series across a DST boundary and verify local-time stability of the expanded instances. (3) Reminder accessibility check: run a screen-reader pass over VolunteerHub's reminder emails (or any chosen template) against WCAG text-email practice — discriminating between "email/text channel exists" and "accessible". (4) Import contract test: round-trip a 180-row roster CSV with Unicode names and duplicate emails through any chosen import path and diff the volunteer table. (5) Permission probe: as a volunteer-role user, attempt to read another volunteer's contact record to test privacy-limited sharing defaults. Executed checks actually performed in this stage are limited to: fetching/verifying the sources recorded in `source-map.json` (HTTP statuses, sha256 of two retained source files, tag greps, GitHub API metadata calls).
