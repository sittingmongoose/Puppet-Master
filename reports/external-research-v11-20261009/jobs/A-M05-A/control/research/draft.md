## 1. Exact per-P dispositions (O4)

### P1 — "Index all fields with keyword search."

**Disposition: correction + user decision.** Keyword indexing is the right baseline and already-covered by discovery §3, but "all fields" is wrong in a collection with restricted material: internal curator notes, donor/rights-holder contact fields, and restriction-class markers must be excluded from the public index or the index itself becomes a disclosure channel. Correction: index a declared public-field list, never a blanket all-fields default; keep a separate internal index scope for curator search if needed. Governing defaults carry over from discovery: a FTS5 baseline has no typo tolerance or synonyms (SRC-01, verified), while Meilisearch's typo bands (0 typos ≤4 chars, 1 typo 5–8, 2 typos ≥9, first-char typo counts double, `disableOnNumbers=false` by default) materially affect accession numbers and short names (SRC-03, verified). User decision: engine choice (SQLite/Postgres FTS5 vs Meilisearch vs Typesense) — discovery retained both stacks as viable at 40k records; Typesense's exact defaults remain unverified (SRC-08).

### P2 — "Add embeddings of each entire record for semantic search."

**Disposition: optional enhancement + correction.** A semantic layer is an enhancement over the keyword baseline, not a replacement, and its value is unproven for this catalog until the validation set runs (uncertain; see §7). Correction: embedding "each entire record" wholesale dilutes signal — embed per field/section (title, object description, materials, period) plus images separately, with a record-level vector only as a weighted composite if evaluation supports it. Version condition (verified chain, SRC-02): if Postgres/pgvector is chosen, pin ≥0.8.4 — iterative index scans (needed so rights/visibility filters don't silently under-return) arrived in 0.8.0, possible HNSW vacuum index corruption was fixed in 0.8.3, and further vacuum/memory fixes in 0.8.4. At 40k records an exact scan is also viable, which de-risks the HNSW chain entirely. Alternatives retained: Typesense built-in embeddings + hybrid search in one binary (candidate, defaults unverified, SRC-08); CLIP-style image/text embeddings (candidate, no model docs retained).

### P3 — "Publish resized images with their catalog captions."

**Disposition: correction + already-covered + condition.** Discovery §4 already covers this mechanism: IIIF Image API 3.0 serves URL-derived derivatives (`{base}/{identifier}/{region}/{size}/{rotation}/{quality}.{format}`, `info.json`, fixed processing order, conformance levels 0/1/2, optional max-dimension limits — SRC-04, verified), so "publish resized images" should be implemented as IIIF-style derivative serving rather than ad-hoc pre-baked resizing; level-0 static conformance is the minimal-ops path, a dynamic server only if zoom/region demand it. Corrections: (a) captions are content too — caption text can itself be sensitive or rights-bearing, so captions ride under the same visibility rules as their objects; (b) captions double as alt text/accessibility surface, which the plan doesn't mention. Condition: the serving layer is an enforcement point — quality downgrades, watermarking or region restriction for restricted material happen per-request at this layer, not by baking restricted derivatives to disk.

### P4 — "Restricted records are removed during the nightly index job."

**Disposition: rejected.** Nightly batch removal is the wrong mechanism on four independent grounds from discovery §5: (a) exposure window — a record whose rights change to restricted mid-day stays publicly searchable up to 24 hours; (b) fragility — any index rebuild that forgets the removal filter re-publishes restricted records wholesale; (c) category error — index removal is a sync side effect, not enforcement; the requirement is server-side per-query visibility filtering that composes with keyword, facet and vector retrieval (and note the plan's own P4 direction is the *opposite* failure mode of the pgvector pre-0.8.0 filtered-scan under-return — the fix is query-time filtering done right, not batch removal); (d) curator transparency — curators need restricted records visible *to them* with a why-is-this-hidden view, which removal-from-index destroys. Replacement (verified pattern, SRC-05/SRC-06): Mukurtu-style communities/cultural-protocols visibility model — access decided per record by protocol membership at query/serve time; a nightly job may remain solely as a backstop consistency *check* that flags any public-index document lacking public visibility rights. Standardized rights surfacing via RightsStatements.org SKOS URIs (SRC-07, verified at repo level; full hierarchy unconfirmed — primary site unreachable).

### P5 — "Enrichment writes directly to source records."

**Disposition: rejected.** Direct in-place writes contradict the brief's own "curators need transparent corrections and exports": originals are the export/audit baseline, and a silent overwrite destroys provenance exactly where uneven descriptions most need accountability. Replacement from discovery §2: enrichment as attributed, reversible overlays (who/what/when produced each field), original + enriched stored side by side, curator review before any promotion; reconciliation-style batch tooling (OpenRefine + authority services — candidate, primary evidence absent, SRC-09) fits review-before-commit by design. Optional enhancement retained: model-assisted *suggested* descriptions, always as suggestions under the same overlay discipline.

### P6 — "Validate search with the curator's favorite ten queries."

**Disposition: correction + uncertain.** Ten curator-favorite queries are a biased instrument: curators are expert-vocabulary insiders, while the brief's target visitor explicitly lacks expert vocabulary; ten queries also cannot discriminate keyword vs semantic vs hybrid at the effect sizes that matter. Correction: keep curator queries as one input, but adopt the discovery §8 set as the actual instrument — golden visitor query set (30–50 staff-written visitor queries, nDCG@10 across FTS5/Meilisearch/Typesense ±vector), typo torture against the verified default bands (SRC-03), filtered vector recall test (SRC-02 chain), rights enforcement probe, IIIF conformance smoke, and a reconciliation pilot if that path is pursued. Uncertainty: no executed result exists for any of these (§7), so P2's value and the engine choice both stay formally uncertain until run.

## 3. Conditions and original constraints

Brief constraints carried intact: 40,000 records; uneven descriptions; images; changing rights; restricted cultural material; visitors without expert vocabulary; curator transparency for corrections and exports; scope is this small product, not unlimited production guarantees. Derived conditions: public-field index allowlist (P1); pgvector ≥0.8.4 pin if Postgres (P2); serving layer as rights enforcement point (P3); query-time visibility filtering everywhere, nightly job demoted to backstop check (P4); overlay-with-provenance enrichment, originals immutable (P5); server-side enforcement only, no client-side hiding (all).

## 4. Alternatives retained

Single-Postgres stack (FTS5/bm25 + pgvector, exact-scan viable at 40k) vs dedicated engine (Meilisearch or Typesense) beside a record store; Mukurtu wholesale adoption vs borrowing its protocol-based access pattern; IIIF level-0 static derivatives vs dynamic image server; reconciliation-based enrichment vs search-side synonym/typo compensation vs model-assisted suggestions — all with conditions in §1 and grades in §2.

## 5. Optional capabilities and user decisions

User decisions required: current system of record and ingest format (unknown, not public); engine choice (P1); embedding model and hosting (P2, if pursued); which restriction classes exist locally and whether source-community protocols apply (P4); authority targets for enrichment (domain-dependent); hosting budget/ops appetite. Optional capabilities retained but not required by the plan: Typesense curation (pin/hide/replace per query) for curated exhibits; TK Labels/content-warning surfacing; rights history via statement-URI re-pointing exports.
