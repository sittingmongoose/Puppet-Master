## 1. The product, in one paragraph

A local museum's 40,000 catalog records — unevenly described, image-bearing, with rights that change and some culturally restricted material — need a public discovery interface that serves visitors who do not have expert vocabulary and curators who must correct and export transparently. The revealed thin plan (P1 keyword index over all fields, P2 whole-record embeddings, P3 resized images with captions, P4 nightly removal of restricted records, P5 enrichment direct-writes, P6 validation by the curator's ten queries) is directionally reasonable and, after comparison, survives in modified form: every P disposition was adjudicated by the independent critic and **all six were upheld** — none was found to be a false correction or false rejection — with two evidence footings downgraded and one rejection made explicitly conditional. The final recommendation, refined by the critique:

- **Search (P1+P2):** keyword index plus embeddings, but *not* "all fields" and *not* "entire records." Identifiers and administrative fields get exact-match treatment (Meilisearch `disableOnNumbers`/`disableOnAttributes`, S07; Typesense `:=`, S08); embedding covers descriptive prose in chunks, because the selected encoder truncates at 256 word pieces ("By default, input text longer than 256 word pieces is truncated", S09, confirmed twice: S09 and critic spot-check C01). Hybrid fusion leaning keyword (Typesense default 0.7K/0.3S, S08) protects name and number precision. Engine choice stays a user decision among four evidenced shapes — embedded SQLite FTS5 (S01), Meilisearch (S07), Typesense (S08), or client-side MiniSearch (S06) — decided by P4's policy architecture and operating budget.
- **Images (P3):** pre-generated fixed sizes are the IIIF level0 form of "resized images" (S02) — the architecturally level-headed default; deep zoom via IIIF server + OpenSeadragon (S17) is an optional enhancement with pin-and-regression-test conditions; captions stay in the metadata layer.
- **Access (P4):** rejected as "nightly removal," replaced by tiered, event-driven propagation: public tier always available, restricted material shown to exist with gated tiers (IIIF Auth External→Kiosk→Clickthrough→Login and 302/401 mechanics, S03), rights changes applied as a same-day propagation with a reconciliation sweep — and **true removal supported as a per-class tier outcome** where counsel or communities require it.
- **Enrichment (P5):** rejected as direct writes; candidates are recorded as provenance-stamped assertions over Getty AAT (74,460 concepts, ODC-By 1.0, generic-terms-only scope, S05) and Wikidata (`wbsearchentities` limit 7/max 50, language-fallback caveat, S04), curator-approved, then applied as versioned dated statements.
- **Validation (P6):** the curator's ten queries survive as the known-item expert-probe slice — retention criteria stated: they are cheap regression probes against expert vocabulary — inside a mixed suite that adds short-word typo tests, visitor-task queries, truncation recall, rights-propagation checks, and a mobile weight probe.

## 2. Critique demands, each dispositioned

Every demand is answered in place below: material findings M1, M2, M3, M4 and M5 first, then the six minor findings (each cited in the critique as minor 1, minor 2, minor 3, minor 4, minor 5 and minor 6).

**M1 (P3's EXIF citation failed verification against retained S18) — RESOLVED by re-derivation, not retraction.** The critic was right that the retained S18 note did not carry the quote. A fresh fetch of Cantaloupe's own `CHANGES.md` (retained as **S19**, accessed 20:18 UTC) verifies it verbatim: release **5.0.1 — "Fixed several issues related to EXIF metadata parsing."** plus 5.0.3 "Improved the resiliency of the built-in EXIF reader." and 5.0 "EXIF Orientation values are always respected." The P3 correction therefore stands on primary evidence: EXIF handling in this pipeline has had real defects, so scrubbing embedded metadata (GPS, author) at derivative-generation time remains required. Root cause noted honestly: the discovery-phase releases-page fetch had surfaced the wording but the evidence note failed to retain it.

**M2 (P4 presented a design inference as an S15 fact) — CONCEDED and corrected.** The 12 RightsStatements URIs embed `/1.0/` as the *vocabulary's* version, one frozen value per statement — not a per-object assertion history (S15). The "change = new dated assertion" pattern is a museum-built design the evidence note itself recommended, and the draft cited it as if the data model provided it. Corrected statement: rights modeling = the fixed 12-statement vocabulary (pinned, CC0, labels joined from per-language JSON-LD since 2019-06-05) **plus a museum-owned assertion table** (record, statement URI, application date, actor). The P4 rejection itself does not move: the nightly-latency flaw, tiering support (S03), and TK Label conditions-imply-tiers (S16) all stand independently, as the critic confirmed.

**M3 (SQLite FTS5 release chain was asserted, not retained) — RESOLVED by re-derivation.** The discovery phase *had* fetched `changes.html` but failed to register it in the source map — the critic correctly called this unretained. Re-fetched and retained as **S20** (accessed 20:18 UTC): all seven links verified verbatim — 3.44.2's "fuzz testing only minutes after the 3.44.1 release was tagged," 3.45.1's regression "introduced in version 3.44.0 but undiscovered until after the 3.45.0 release," 3.46.1 secure-delete false positives, 3.47.0 locale tokenizers/contentless_unindexed, 3.50.2 BLOB UPDATE fix, 3.50.3 corrupted-index memory error (original typo "against against" retained), 3.51.1 fts5vocab latent bug (2023-11-24 → 2025-11-28). The pin-and-reverify condition for FTS5 is now evidenced, matching the fully-evidenced Cantaloupe (S18+S19) and OpenSeadragon (S17) chains. source-map.json carries S19/S20 as a labeled post-reveal addendum; no frozen entry was modified.

**M4 (the brief's "exports" obligation was never designed) — CONCEDED; designed here.** For the recommended thin stack, export is a first-class feature, not an afterthought: a curator-triggered export view over the catalog database (CSV/JSON-LD) with three switches — scope (whole catalog, a saved search, or a collection subset), rights filter (exclude restricted records or include metadata-only rows per the P4 tier classes), and provenance columns (enrichment assertions, correction history from the P5 assertion table, rights assertion dates). Because corrections and rights live as dated rows, exports are truthful by construction — a snapshot join, not a reconstruction. For the platform alternatives the brief comparison keeps alive: CollectiveAccess ships batch import/export (S13); Omeka S export is module-mediated (S12, unverified depth). If the museum defers the custom export view, that deferral is recorded as an explicit user decision in §4 rather than silently dropped.

**M5 (deletion lifecycle unaddressed) — CONCEDED; designed here.** Five surfaces must agree when a record is removed or downgraded: the catalog row, the FTS5 external-content index (delete via the `'delete'` command with exact stored values or "the results may be unpredictable", S01), the vector table (sqlite-vec's latest release, v0.1.9, exists precisely to fix "DELETE operations", S11 — the delete path gets a regression test on every version bump), any serialized client-side index (MiniSearch payloads ship wholesale; removal requires regeneration, not mutation, S06), and pre-generated image tiers (delisted objects' files must be pulled or ACL'd at the static host). Design: a single `removal_event` row per object (reason: rights assertion, takedown, TK label) consumed by the propagation job, which drives all five surfaces and writes completion back — the same event-driven mechanism P4's tier changes use, so removal is a tier outcome, not bespoke surgery.

**Minor 1 (S16 tally arithmetic muddled) — CONCEDED.** The evidence note's own arithmetic ("6+9+5" labeled 19; the sum is 20; six Permission names were listed) was sloppy, though the underlying uncertainty (page says 19, lists 20–21 names) was honestly carried. ## 3. The four carried questions, adjudicated

1. **Tiered access vs legal takedown:** tiering is the default shape; full removal exists as a per-class tier outcome via the M5 deletion design, so counsel can elect it without re-architecture. Whether any class requires it is a user decision (museum counsel + communities).
2. **CLIP image vectors:** blocked until dimension, text-limit, and license are verified from model config or the paper (S10 records their absence from the fetched card); adopt only if V-calibrated value justifies the indexing cost.
3. **Ten-query suite:** survives as the known-item expert-probe slice with stated criteria (Minor 3), inside the mixed suite.
4. **Engine ordering under P4:** the policy forces a *split*, not an elimination — a public index (possibly client-side/static, S06/S11-WASM) holding only unrestricted records, plus a server-side filtered index if restricted material must remain discoverable-as-existing at a lower tier (S03); legally removed classes are excluded from the public index via the M5 delete path. Final engine selection among the four shapes is a user decision gated on V1/V4/V5 results.
