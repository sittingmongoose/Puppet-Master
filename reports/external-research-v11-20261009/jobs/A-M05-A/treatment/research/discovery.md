# Discovery — S05 museum-search (block A-M05-A, arm treatment, stage research, method M05 v1 retained-investigator)

Written 2026-10-09 UTC, before any plan reveal. Sources of truth for this phase: `cases/S05/brief.md` (read once), this directory's `assignment.md` and `input-map.json`, and 18 independently chosen public primary sources (see `source-map.json`, evidence in `sources/`). The case file `plan-root-only.md` was never opened; no predecessor, campaign, evaluator, counterpart or history was read; usage/billing was unobserved and is recorded as null. Discovery is frozen as of this file plus `source-map.json`; nothing here will be rewritten after the reveal.

## 1. The product problem, restated from the brief alone

A local museum (40,000 catalog records) needs a public search interface. Records have uneven descriptions, images, rights that change over time, and some culturally restricted material. Two user groups with conflicting needs: visitors, who must reach meaningful discovery **without expert vocabulary**, and curators, who need **transparent corrections and exports**. The brief asks for tools and alternatives across five mechanism areas — metadata enrichment, semantic/keyword search, image handling, access policy — plus implementation/release conditions, with equal-weight obligations O1–O6.

The core tension: discovery quality (fuzzy, semantic, vocabulary-free) pulls toward heavy machinery, while a small museum's operating reality (no devops staff, changing rights, cultural protocols) pulls toward small, inspectable, long-lived systems. Every choice below is scored against that tension, not against maximal capability.

## 2. Keyword search: three materially different engines, three default regimes (O1, O2)

**SQLite FTS5 (S01).** An embedded index inside the catalog database itself. Governing defaults, verified: BM25 is the default rank ("column rank contains by default the same value as would be returned by executing the bm25() auxiliary function with no trailing arguments"), lower is better, and k1/b are "hard-coded at 1.2 and 0.75" — relevance tuning happens only through per-column weights (`bm25(t, 10.0, 5.0)`) and tokenizer choice. The default `unicode61` tokenizer removes diacritics from Latin characters by default, which conveniently lets "cafe" match "café" — but that is a default to be tested, not assumed (visitor behavior with accented artist names). External-content tables (`content='...'`) keep the index beside the catalog but transfer sync responsibility to the implementer ("It is still the responsibility of the user to ensure that the contents of an external content FTS5 table are kept up to date") — trigger recipes are in the doc, including the trap that triggers added after data load do not backfill (use `rebuild`). Units/limits: tokens cap at 32,768 bytes with silent truncation (no error); index size is controllable — on the doc's 1.6 GiB example corpus, `detail=none` cut the index from 743 MiB to 134 MiB. Applicability: 40k records is trivial scale for FTS5; the engine is free, file-shaped, and survives without servers.

**Meilisearch (S07).** A small standalone server. Its typoTolerance default is a JSON object: `{enabled: true, minWordSizeForTypos: {oneTypo: 5, twoTypos: 9}, disableOnWords: [], disableOnAttributes: [], disableOnNumbers: false}`. Consequential default analysis: a 4-letter collection word like "mask" or "jade" gets **zero** typo tolerance because words shorter than 5 must match exactly — precisely the short words visitors mistype. Retuning `oneTypo` (and setting `disableOnNumbers` for accession numbers, so 2001.45 never matches 2001.54) is a mandatory configuration decision, not polish. Default ranking rules run `words, typo, proximity, attributeRank, sort, wordPosition, exactness` — the presence of the newer `wordPosition` rule is itself a version-drift marker; pin releases.

**Typesense 30.2 (S08).** Typo tolerance defaults to `num_typos: 2` on all queried fields, Damerau–Levenshtein, gated by `typo_tokens_threshold` (default 1 — start typo-correcting when fewer than 1 exact result). Notably there is **no minimum word length**, so short museum words keep 2-typo tolerance where Meilisearch gives them none — a materially different default regime for the same problem. `prefix` defaults true on the last word (autocomplete-shaped). Pagination caps at 250 hits/page (`per_page` default 10). Field weights via `query_by_weights` (0–127, order matters).

**MiniSearch (S06).** The materially different deployment shape: a ~zero-dependency in-memory JS engine ("can comfortably run both in Node and in the browser"), fuzzy at relative edit distance (`fuzzy: 0.2` = "0.2 * term length"), prefix and field boosts, and an `autoSuggest` engine ranked "by the relevance of the documents that would be returned by that search." Uncertainty kept honest: the docs claim only a "modern search result ranking algorithm" — BM25 is never named, so relevance behavior is unverifiable from the primary source. Applicability: with a 40k-record index serialized into a static site, an entire search UI ships as files; memory in a mobile browser is the binding constraint (proposed validation, not executed). Caveat: everything in the index ships to the client, so client-side search cannot be the tier that hides restricted records.

## 3. Semantic search: encoders, vectors, and one file that holds everything (O1, O2)

**all-MiniLM-L6-v2 (S09)** — 384 dimensions, 22.7M parameters, Apache-2.0, trained on ~1.17B web sentence pairs. Its hard governing limit is "input text longer than 256 word pieces is truncated": uneven museum descriptions that ramble past ~256 tokens silently lose their tails at embed time. Mitigation (chunking, summary-plus-head dual vectors) is a design condition, and the Reddit-heavy training mix is a plausible domain gap for catalog prose — both unquantified until measured.

**clip-ViT-B-32 (S10)** — maps "text and images to a shared vector space" with listed uses "image search, zero-shot image classification, image clustering and image deduplication"; a multilingual variant covers "50+ languages." Honesty record: the model card fetched does not state the embedding dimension, the text-token limit, or the license — three adoption-blocking facts that must come from config files or the paper before commitment.

**sqlite-vec (S11)** — the unfamiliar-tool find of this phase: "A vector search SQLite extension that runs anywhere!", pure C, no dependencies, runs "in the browser with WASM," dual Apache-2.0/MIT, `vec0` virtual tables with metadata/partition columns and KNN via `match ... order by distance`. Combined with S01, one SQLite file can hold keyword index, vectors, rights flags, and catalog data — the whole discovery backend deployable as a single file (or even WASM in-browser). Conditions are real: it is "pre-v1, so expect breaking changes," and its latest release, v0.1.9 (2026-03-31), is literally titled "Bug fix for DELETE operations" — pin versions and wrap writes. Whether its KNN path is brute force or ANN is not stated in the README (repo contains ivf/diskann/rescore sources), so recall/latency must be measured.

**Typesense built-in vectors (S08)** — the pragmatic middle: auto-embeddings generated server-side from declared fields (`embed.from` + `model_config`, built-ins like `ts/e5-small` and `ts/all-MiniLM-L12-v2`, or custom ONNX), regenerated only when source fields change, with hybrid search fusing keyword and vector ranks as `rank_fusion_score = 0.7 * K + 0.3 * S` (keyword-leaning by default; `alpha` adjustable). Whether distant typo tolerance applies inside hybrid mode is not stated in the fetched pages — flagged for validation.

## 4. Metadata enrichment without expert vocabulary (O1, O2)

**Getty AAT (S05)** — 74,460 concept records, 503,230 terms, published under ODC-By 1.0 as "Linked Open Data (JSON, RDF, N3/Turtle, N-Triples...), XML, Relational Tables, Web Services APIs," refreshed periodically, monthly online search. Scope discipline matters: AAT carries generic terms only ("each concept is a case of many... 'cathedral' is in scope but Chartres Cathedral is not") — object-type/material/technique normalization is squarely in scope; agent and place authority needs ULAN/TGN (same license family), and subject/iconography access is a real gap (CONA exists but was not investigated here). AAT's polyhierarchy (seven facets, multiple parents) is what enables visitor browsing by material/object-type instead of curator phrasing.

**Wikidata `wbsearchentities` (S04)** — free label/alias search returning label+description in the user language; `limit` default 7, hard max 50; `language` selects the search language while `strictlanguage` disables "language fallback" — a silent widening that a monolingual museum may not expect. This is the cheapest path to autocomplete that explains itself ("Teapot — container with spout, Q191744") without any local vocabulary maintenance.

Both enrichment paths share an applicability condition: enrichment must be recorded as **assertions with provenance** (which vocabulary, which match, who/what confirmed it), because brief's "transparent corrections" obligation means curators audit the machine's suggestions, not live inside them.

## 5. Image handling: a standard pipeline vs its operational weight (O1, O2, O3)

**IIIF Image API 3.0 (S02)** — request grammar `{identifier}/{region}/{size}/{rotation}/{quality}.{format}` with fully specified failure semantics (out-of-bounds regions cropped; zero-area → 400; upscales → 400, or 501 for `^` variants), an `info.json` JSON-LD contract with required `profile` (level0/1/2) and an optional `rights` property, and optional `maxWidth/maxHeight/maxArea` caps. Level choice is the cost lever: level0 (fixed sizes only) is servable by pre-generated files with no dynamic server at all.

**Cantaloupe (S18)** — the concrete JVM IIIF server, and the strongest O3 chain found: its PDFBox dependency carried **CVE-2021-27807 and CVE-2021-27906**, fixed by "Updated the PDFBox dependency..." in **v4.1.9 and v5.0.1 released the same day (2024-05-03)**; the community then pressure-tested it — issue #634 reports a Trivy scan of a v4.1.11 docker image surfacing a large CVE surface "mostly stemming from bundled Java dependencies" — leading to further hygiene releases (v5.0.6 "Updating libraries to fix security issues"; v5.0.7 upgrading maven-assembly-plugin for CVE-2023-37460, 2025-03-13). Two operational conditions follow: a museum running a JVM image server inherits a dependency-CVE treadmill (scanning and upgrade cadence required), and the project's latest release is ~19 months old at access — velocity is part of the risk.

**OpenSeadragon (S17)** — the standard deep-zoom viewer, with the second O3 chain: v5.0.0 (Aug 2025) flipped the default renderer — "Dropped support for IE11" and the viewer "defaults to WebGL when available" — and v5.0.1 (Dec 2025) then shipped a regression cluster: "the WebGL drawer would draw the image in white" (#2620), "TiledImage.setClip would sometimes leave tiles unloaded" (#2590), images disappearing "on page zoom change or moving windows between monitors" (#2627), among others (#2570, #2582, #2600/2606, #2615, #2619). The 6.0.0 line (Feb 2026) overhauled the data pipeline, with v6.1.1 (2026-09-09) current. Adoption condition: pin ≥6.0.2 (better 6.1.1), regression-test the WebGL path on the museum's actual kiosk hardware, keep the canvas drawer selectable as fallback.

**Alternative shape (from S02+S06):** at 40k records with modest image sizes, level0-IIIF-compatible pre-generated sizes served statically + MiniSearch-style client UI is a no-dynamic-server pipeline — materially cheaper to operate, at the cost of deep zoom and server-side access control.

## 6. Access policy: changing rights and restricted cultural material (O1, O2)

**RightsStatements.org (S15)** — the fixed vocabulary for "changing rights": exactly 12 statements in three collections, each versioned in-path (`/1.0/`): In Copyright — `InC`, `InC-OW-EU` (EU Orphan Work), `InC-RUU` (Rights-holders Unlocatable or Unidentifiable), `InC-EDU` (Educational Use Permitted), `InC-NC` (Non-Commercial Use Permitted); No Copyright — `NoC-NC`, `NoC-CR` (Contractual Restrictions), `NoC-OKLR` (Other Known Legal Restrictions), `NoC-US` (United States); Other — `NKC` (No Known Copyright), `CNE` (Copyright Not Evaluated), `UND` (Undetermined). Implementation facts that shape design: the canonical data is SKOS/Turtle in a CC0 GitHub repo (pinned here at commit 93f1613, 2026-09-02), and since 2019-06-05 descriptive labels live in **language-specific JSON-LD files, not in the TTL** — display labels must be joined from those files. Data is versioned, so a rights *change* is recorded as a new dated assertion (old statement URI + new statement URI + date), which is exactly the audit trail "changing rights" needs. Availability drift observed live: rightsstatements.org itself returned **HTTP 526 (Invalid SSL certificate, Cloudflare)** on both attempts during the access window while the canonical repo served normally — a small museum should pin a copy of the vocabulary, not resolve URIs against the live site.

**IIIF Authentication 1.0 (S03)** — the restricted-material mechanism: bearer tokens delivered `{"accessToken": ..., "expiresIn": 3600}` via an iframe/postMessage dance, four interaction patterns — External, Kiosk ("no user interaction... automatically," built for gallery hardware), Clickthrough (one button), Login — a client preference order (External → Kiosk → Clickthrough → Login), and tiered access where the server 302s to a lower tier's resource or 401s. Public tier = low-res images with metadata visible; full tier behind Clickthrough/Login is a natural mapping for culturally sensitive items. The spec itself warns that third-party-cookie workflows are "now, or will soon be, obsolete in most browsers," and 2.0 is the current stable — this 1.0 fetch is a baseline, and the 2.0 delta is an open gap.

**Local Contexts TK Labels (S16)** — the non-copyright access axis: Provenance/Protocol/Permission labels ("outline traditional protocols associated with access to this material" — seasonal, gender-restricted, secret/sacred) applied by Indigenous communities, with Hub APIs for collection integration. Two honest records: adopting them is a community partnership, not a software feature (label authority sits with communities); and the page is internally inconsistent — it says "19 labels" while listing 6+9+6 names — so the canonical count needs Hub verification before schema freeze.

## 7. Platforms and whole-shape alternatives (O1)

Four implementation shapes emerged, deliberately including unfamiliar ones:

1. **Cataloging platform as backbone — CollectiveAccess (S13):** Providence (cataloging, "pre-configured with popular metadata standards," batch import/export) + Pawtucket2 (public faceted browse); actively maintained (v2.0.11, 2026-03-15). Condition: PHP stack + profile authoring; search depth inside Pawtucket2 unverified.
2. **Publishing platform as backbone — Omeka S (S12):** "next-generation web publishing platform" for cultural heritage, LOD publishing, DPLA-ready resource templates, module ecosystem, multi-site. Condition: module-mediated search (depth unverified); pairs naturally with a custom search layer if needed.
3. **Minimal-computing static exhibits — Minicomp/Wax (S14):** "longevity, low costs, and flexibility," Jekyll-based, museum collections as static exhibits. Condition: exhibit-page focus and Ruby/Jekyll toolchain bound its fit; candidate for a curated subset, not 40k-record faceted discovery.
4. **Thin custom stack (assembled from S01+S06+S11+S08):** one SQLite file (catalog + FTS5 + sqlite-vec) behind a minimal API, or Typesense (typo+vector+hybrid in one server), fronted by a static site; rights as pinned RightsStatements rows; IIIF images via pre-generated sizes or Cantaloupe. Maximum control, maximum ownership of search-quality tuning (the §2 default regimes become the museum's own configuration burden).

## 8. Issue/fix/release chains studied (O3 — explicit)

- **SQLite FTS5 (S01 evidence §6.13/§4.4.2 + release history):** version-bound format changes (secure-delete 3.42.0; contentless-delete 3.43.0; older readers fail with "invalid fts5 file format (found 5, expected 4) - run 'rebuild'"), plus a fuzzing-discovered fix in 3.44.2 "only minutes after the 3.44.1 release was tagged," a 3.45.1 fix of an integrity_check regression "introduced in version 3.44.0 but undiscovered until after the 3.45.0 release," 3.46.1 secure-delete false positives, 3.47.0 locale-aware tokenizers + contentless_unindexed, 3.50.2 BLOB UPDATE fix, 3.50.3 corrupted-index memory error, 3.51.1 fts5vocab latent bug (2023–2025). Lesson: FTS5 is stable but its edge features churn; pin and re-verify after upgrades.
- **Cantaloupe PDFBox CVEs (S18):** dependency CVEs → same-day dual-branch fixes (v4.1.9 + v5.0.1, 2024-05-03) → community scanner pressure (#634) → continued hygiene releases → v5.0.7 (2025-03-13). Lesson: the image server's supply chain is the museum's problem; scan containers and budget upgrade time.
- **OpenSeadragon WebGL flip (S17):** feature default change (5.0.0, Aug 2025) → eight-fix regression patch (5.0.1, Dec 2025, incl. white-image drawing) → pipeline overhaul (6.0.0, Feb 2026) → current 6.1.1 (Sep 2026). Lesson: viewer defaults can regress rendering on real hardware; pin, test on kiosk hardware, keep a fallback.
- **sqlite-vec (S11):** v0.1.9 "Bug fix for DELETE operations" (2026-03-31) on a pre-v1 project — deletes through `vec0` tables were recently broken. Lesson: wrap writes, pin, expect breakage between minor versions.
- Where evidence was absent, it is said so: Pawtucket2/Omeka-S search internals, MiniSearch's ranking algorithm, sqlite-vec's ANN status, Typesense hybrid typo interplay, and CLIP's dim/license were **not verifiable from fetched sources** and are carried as open items, not assumed.

## 9. Alternatives, conditions, disagreement and uncertainty register (O5 seeds)

- **Engine defaults genuinely disagree** on short words: Meilisearch (no typos < 5 chars) vs Typesense (2 typos always). This is a discriminating difference, not noise — museum vocabulary is full of 3–4-letter object words.
- **Client-side vs server-side search** (S06/S11-WASM vs S07/S08): tradeoff is restricted-material exposure + index weight vs zero-operating-cost longevity.
- **JVM IIIF server vs pre-generated sizes** (S18 vs S02-level0): capability vs a dependency-CVE treadmill and release velocity.
- **AAT-only vs AAT+Wikidata enrichment** (S05 vs S04): controlled vocabulary quality vs breadth and free autocomplete; both need provenance-recorded assertions.
- **Auth 1.0 vs 2.0** (S03): fetched spec is itself flagged obsolete-in-parts; 2.0 unread (gap).
- Unverified facts carried forward: MiniSearch ranking basis; CLIP 512-dim/77-token/license; sqlite-vec ANN status; TK label canonical count; Omeka/CollectiveAccess search depth; OpenSeadragon 5.x year attribution (inferred from sequence + two pinned dates); Typesense hybrid typo behavior.

## 10. Proposed discriminating validations (O6 — proposed only; **none were executed**; no runtime was available)

1. **Short-word typo test (S07 vs S08):** index a sample catalog in Meilisearch and Typesense with stock settings; query misspellings of 3–4-letter object words ("mask", "jade"); measure hit/no-hit. Discriminates whether Meilisearch needs `oneTypo` retuning in this domain.
2. **FTS5 diacritics/tokenizer test (S01):** build a small external-content FTS5 table over accented titles; verify default diacritic folding matches visitor behavior; test `remove_diacritics 0` variant. Discriminates tokenizer configuration.
3. **MiniLM truncation effect (S09):** embed long descriptions whole vs chunked (256-token limit); measure recall@10 on known-item queries. Discriminates chunking design.
4. **sqlite-vec recall/latency (S11):** 40k×384 vectors, KNN vs brute-force baseline; delete-then-query regression re-test after v0.1.9. Discriminates single-file backend viability.
5. **MiniSearch index weight (S06):** serialize a 40k-record index; load on a low-end mobile browser; measure memory and first-query latency. Discriminates static-site search viability.
6. **Rights vocabulary pinning drill (S15):** vendor rights-statements.ttl + label JSON-LD at a pinned commit; verify URI stability and label join; re-run against live site after the 526 outage clears. Discriminates pin-vs-live design.
7. **IIIF tiered-access walkthrough (S02+S03):** serve one restricted item with public/low tiers + Clickthrough; exercise 302/401 and token flow in OpenSeadragon. Discriminates restricted-material UX.
8. **Dependency-scan rehearsal (S18):** Trivy-style scan of the chosen image server image before adoption; count CVEs. Discriminates image-server choice.
9. **Enrichment precision sample (S05+S04):** run 200 record titles through AAT/WebID matching; curators grade suggestions. Discriminates enrichment pipeline value before committing to audit tooling.

Each of the above is a proposal; none ran in this phase. Checks that *were* executed in this phase are limited to artifact existence/JSON-validity verifications recorded in the stage directory.
