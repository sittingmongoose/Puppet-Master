- **Build-your-own local-first option.** RxDB v17.0.0 documents local writes and later sync, handler/checkpoint requirements, retry/idempotency considerations and a master-wins default conflict handler ([S09](evidence.md#s09--rxdb-local-first-replication-guide-version-1700)). - **Manual continuity path.** A numbered paper queue/manifest with per-terminal allotments, a dispatch handoff, and later reconciliation is materially different from SaaS or local-first code. It can be tested before software; the case still must decide whether an offline entry is confirmed, provisional, or waiting. It is an operational proposal, not an externally verified product claim.

## Relation and condition graph

1. **No link between terminals → no shared current inventory at the point of sale.** A local database or a product’s “offline” mode can allow local work, but it does not by itself show that the other terminal’s concurrent sale is known. For a fixed sailing capacity, global no-overbooking while terminals cannot communicate requires a policy choice:
   - a single authority can keep confirmations unique, while disconnected stations queue requests or record provisional intents;
   - preallocated, non-overlapping terminal quotas permit local confirmations up to each quota, while reducing flexibility and possibly stranding unused capacity; or
   - terminals may independently accept sales and reconcile later, which preserves service continuity but requires an explicit overflow/priority remedy and accepts a real conflict risk.
   
   This is an inference from the brief’s disconnected-terminal condition plus the documented independent replicas and application-managed conflicts in CouchDB/RxDB ([S07–S09](evidence.md#s07--apache-couchdb-eventual-consistency)). “Offline ticketing” is not sufficient evidence for whichever policy the operator chooses ([S01–S02](evidence.md#s01--pdms-compass)).

2. **Reservation → ticket → actual boarding are separate states unless the operator chooses otherwise.** The WSF reference explicitly separates a vehicle capacity reservation and ticket purchase, and does not require walk-on reservations on its named routes ([S06](evidence.md#s06--washington-state-ferries-reservation-workflow)). For this case, daily counts must distinguish reserved/held capacity from walk-on requests, tickets, and boarded passenger/vehicle counts.

3. **Vehicle “count” may be dimensional.** Oversized vehicles can consume more deck space than an ordinary vehicle. Model sailing capacity in the units used by the ferry’s real loading rule (for example, class/bay/length, if the operator confirms those rules), not just one scalar count. Keep wheelchair assistance as a private operational requirement linked to the reservation/boarding workflow, and expose only a neutral load/assist marker on any public queue view.

4. **Offline changes need provenance and a conflict path.** A cancellation, sailing move, late accessibility note, or boarding change made on one disconnected copy may race with a change from another copy. Preserve the original change event, user/terminal, local order/time, and resolution. Do not silently use a storage-layer winner as the product policy. CouchDB’s normal views surface only a winning revision, and RxDB’s documented default selects the server/master version on conflict ([S08–S09](evidence.md#s08--apache-couchdb-conflict-model)).

5. **Budget and staffing constrain the likely pilot shape.** The initial amount is $9,000; recurring cap is $1,800/year = $150/month for all included recurring costs. If all 36 staff required paid seats, this would average $50 per person/year before hosting, payment fees, support, hardware, printer media, backup, training, and integrations. This arithmetic is not a vendor price comparison. No page reviewed exposed a comparable current quote; FerryCloud’s page explicitly asks for a quote and lists CET-business-hours support for its Basic tier ([S05](evidence.md#s05--ferrycloud-pricing-page)). A managed vendor path is more plausible than an operator-maintained custom sync stack for a team without IT, but only a complete quote and owner-approved outage policy can settle that inference.

## Evidence and interpretation boundaries

Vendor pages describe supplier claims, not acceptance tests. The WSF workflow is a state/route-specific example and cannot be imported as local regulation. CouchDB/RxDB documentation explains database replication behavior, not a ferry booking implementation. The RxDB issue/fix trail concerns WebRTC sync in an order-processing test, not capacity correctness ([S10–S12](evidence.md#s10--rxdb-issue-5342)). No prices, vendor references, accessibility audit, jurisdiction-specific rules, device inventory, route capacity, or outage duration beyond “half a shift” were observed. All proposed validations in the discovery are unexecuted.

## Additional bounded architecture alternatives checked after critique

- **Managed offline cache and backend (Firestore).** Google documents cached reads/queries and queued writes; writes to the same document use last-write-wins, cached queries can be stale/incomplete, and transactions fail offline. On web, offline persistence is disabled by default; if enabled, passenger-bearing cache is not automatically cleared between sessions. These facts make Firestore a useful architecture comparison, not a solution to disconnected capacity authority. A product could keep offline actions provisional and arbitrate on reconnect, but must visibly distinguish cached freshness and protect shared-device data ([S13–S14](evidence.md#s13--cloud-firestore-offline-data)).
- **Embedded relational changesets (SQLite Session Extension).** This captures/apply changesets between databases with the same schema and compatible starting data. It is disabled by default, requires declared primary keys, does not capture virtual tables and exposes conflict callbacks. The application still needs transport, ordered replay, schema/version handling, retry/idempotency and the reservation authority rule. It is a lower-level building block rather than a sync product ([S15](evidence.md#s15--sqlite-session-extension)).
- **CouchDB upgrade issue boundary.** Issue #5879 reports 3.5.1 memory/availability problems at very large DB/shard counts and remains open/needs-triage; official 3.5.2 notes exist but the reviewed notes do not establish that they fix this issue. This deserves a release review if CouchDB is selected for implementation, but it is not evidence about this small pilot’s reliability ([S16–S17](evidence.md#s16--couchdb-issue-5879-bounded-lower-transfer-caution)).
