## Scope and method

The brief calls for a public museum search interface over about 40,000 catalog records, with uneven descriptions, images, changing rights, and some culturally restricted material. Visitors need useful discovery without expert vocabulary; curators need correction transparency and export. This report evaluates approaches for metadata enrichment, keyword/semantic discovery, image delivery and access/governance. It does not select a production stack because the catalog schema, source of truth, current policy process, hosting environment, language needs and operating capacity are not supplied.

I worked from the brief and independently explored primary project and standards sources. I extracted source-backed entity–relation–entity statements with conditions and versions, then grouped them into topical communities. No service API was called; no catalog data, executable, server or test runtime was available or used. I did not run a witness or benchmark. All checks below are proposals, not executed results. The source map records source URLs, observed revisions/versions, locators, access time and operations. Original excerpts are bounded; the complete source pages remain navigable through the index.

## Condensed recommendation for later plan comparison

Use a curator-controlled enrichment pipeline that keeps original catalog values and records authority identifiers, decisions, source, reviewer and timestamp. Do not silently overwrite collection language with a vocabulary or generated label. Establish a well-tuned lexical baseline with plain-language labels, synonyms/crosswalks and useful facets; then compare opt-in hybrid search on real queries before making embeddings the default. Separate copyright/re-use metadata from cultural protocols and technical authorization. Keep an authoritative record-level policy decision in the museum system, filter search and exports through it, and enforce it again at record, manifest, info.json, thumbnail, image-derivative and cache boundaries. Use IIIF where object viewing/interoperability justify it; static derivatives are a lower-operations option. Include culturally contextual guidance close to results, ideally through community-led Local Contexts Projects where those apply. These are evidence-grounded candidate directions, not a commitment to a named product.

## Emergent topical communities

### Community A — Curator-controlled enrichment and provenance

OpenRefine provides a reversible curation workbench rather than an automatic enrichment daemon. A curator can clean/cluster values, reconcile against Wikidata, Getty authorities or a local CSV-backed service, review candidates and export changed records. Original value and link can coexist, but workflow transformations can lose the link if only display value is copied. Preserve a stable original field plus structured enrichment data: authority URI, authority/service/version, original text, chosen candidate, reviewer/decision status, date and batch. Reconcile in measured batches because service behavior/latency differs and OpenRefine has no throttle control in the operation. The 40,000-row corpus was not benchmarked. Prefer local controlled vocabularies for local terms, sensitive descriptors or uncertain external matching. Do not overwrite community-preferred terminology or imply a match is endorsement. Evidence: [S01–S02](sources/01-enrichment.md).

**Conditions and disagreement:** entity matching may link an artist/place/concept while the institution still must decide whether a label is accurate, appropriate, public or culturally authorized. Exact-match confidence is not a governance decision. Public Getty/Wikidata services and a local authority are alternatives; neither was called or performance-tested.

### Community B — Visitor search: language access, lexical precision and semantic recall

A lexical baseline plus metadata cleanup, synonym/crosswalk expansion and browseable facets addresses exact artist names, accession numbers, titles, dates and subjects. Visitor labels can translate specialist vocabulary into common language while retaining canonical terms for curators. Search should expose why a result appears, preserve exact identifiers and support forgiving spelling without making hidden metadata public.

Hybrid retrieval is an optional extension for broad natural-language searches over sparse descriptions. Meilisearch is one candidate: its v1.6 article defines semanticRatio as a 0-to-1 blend and documents default 0.5; current documentation requires a configured embedder/template and recommends tuning on actual data. The current guide warns that semantic retrieval can produce weak matches and offers a score threshold. Embedding document templates should include only approved public discovery fields, with exclusion/refresh policy for sensitive or changing rights data. An existing local search/database implementation with text matching and controlled terms is a materially different lower-dependency alternative; hosting and operational context are unknown, so no engine is selected.

Meilisearch issue #6591 is open at this snapshot and reports that adding an empty/null searchable field can change hybrid ranking path and score for the same query/configuration. It cites version 1.52 and is a user report, not a failure reproduced here. This matters during schema evolution and when score thresholds or result explanations are used. Require representative ranking stability checks on a pinned version; compare lexical and hybrid mode on the same judged query set. A user-controlled facet is not a policy filter.

**Conditions and open dependency:** automatic embedding generation may send record text to a provider and entail model/provider terms, payload, availability and billing. The brief does not specify whether hosted processing is allowed. Local/self-hosted embeddings or keyword-only search remain options. Provider usage and billing were not observed. Evidence: [S03–S07](sources/02-search.md).

### Community C — Interoperable image viewing and cultural/rights governance

IIIF is useful when zoomable image delivery, standardized viewer interchange, multi-page/compound objects or reuse across cultural-heritage tools justify a service. Image API 3.0 standardizes parameterized requests and technical information; profiles declare actual feature level. For modest display needs, static/pre-generated resources may meet requirements with less operational complexity. Presentation API 3.0 describes human-facing manifests but is explicitly not the search index; it distinguishes requiredStatement, which must be rendered, from rights, which is informative and may not render. Use it for interoperable presentation while retaining search, policy and rights evidence in the catalog/system of record.

Cantaloupe is a Java dynamic IIIF server candidate, not a recommendation without a pinned-version review. Its historical 401 exception report and explicit 5.0.5 fix supply a concrete denial-path regression chain. The release list observed at this snapshot called v5.0.7 latest while the mutable development log had 6.0 entries; review maintenance, security issues, supported release and staff Java capacity. The issue/fix chain means deny responses must be deliberately exercised, including cache/derivative routes. No Cantaloupe software was downloaded or run.

Copyright/re-use, access authorization and cultural protocols are separate state. RightsStatements.org provides machine-readable high-level copyright/re-use descriptors; these can be inaccurate and do not replace detailed rights records or licenses. Local Contexts adds community-authored TK/BC Labels and institution-authored Notices, explicitly complementary to copyright. A Notice may be an initial disclosure while inviting community engagement; a Notice is not a substitute for a community Label. Display the applicable Label/Notice close to the content. CARE supports community authority and collective benefit as governance criteria.

A proposed policy model records separate decisions/provenance for: (1) legal copyright/re-use assertion; (2) institutional technical visibility class and effective authorization rule; (3) community protocol/Label or Notice and linked Project; (4) attribution/required statement; (5) policy owner, approval date and review/expiry status. A policy change should trigger fail-closed search index refresh, cached result/thumbnail/IIIF invalidation and an access audit. Search excerpts, facets, counts, exports, feeds, embeddings and identifiers can leak restricted information even when the full image is hidden; the museum must decide which metadata remain discoverable. This is an inference from the brief and source distinctions; no local policy model was inspected.

**Conditions and external dependency:** Local Contexts API v2 requires authorized Hub credentials and respects account/project visibility; live API/embed can reflect community updates while downloaded/static data may suit offline systems. API v2 is documented as default since February 2025. A platform integration can require field mapping, key handling and certification; a museum's own database has a distinct route. Community choice about which material to label, whether/when to apply Labels and appropriate circulation is a human governance dependency, not a feature to infer from copyright. Evidence: [S08–S21](sources/03-image.md) and [S17–S21](sources/04-rights-governance.md).

### Community D — Release, operations and change control

Pin tested software and model versions. For a dynamic image server, compare current published tags and release notes to the development branch; maintainers' build/security practices and current supported Java/runtime are operational requirements. For search, lock engine/API and embedding model, retain rollbackable index version, and rebuild from authoritative catalog after rights/rule changes. For OpenRefine enrichment, retain exported operation/decision record and authority identifiers. For Local Contexts, use a live connection only if the museum can safely manage keys and dependency; track static snapshot freshness otherwise. Sources do not establish hosting costs, provider rates, service availability, implementation effort or museum support capacity.

## Complete condition-preserving findings

1. **Useful starting search experience.** Clean field values; index title/alternate title/creator/date/place/object type/material/subject/approved description; map specialist terms to plain-language synonyms; present a few visitor-oriented facets. Preserve exact identifier search and attribution/provenance. This is a proposal; corpus-dependent relevance and accessibility remain to validate.
2. **Optional semantic discovery.** Offer it as a test mode or switch after the baseline. Use only public, approved fields in embedding templates; make semantic weight explicit; inspect weak matches and recall on visitor queries. Keep exact names and identifiers strong. Compare model/provider, hosted/self-hosted operation, data-transfer terms, language coverage and per-record/call costs before deciding. Costs and usage remain null/unobserved.
3. **Batch metadata enrichment.** Use OpenRefine for candidate-based cleanup with a review queue. Pilot on representative subsets by entity type; compare Getty ULAN/AAT/TGN, Wikidata and the museum's local authority where each fits. Preserve rejected/unmatched/ambiguous states and do not treat one authority's score as comparable to another's.
4. **Image delivery.** Determine whether static thumbnails/detail files suffice before deploying IIIF. If IIIF is needed, model profiles/manifests against catalog formats, sizes, image rights and viewer needs. Cantaloupe may be prototyped only against a pinned supported release and ops/security review; release and Java fit remain open.
5. **Access and cultural guidance.** Ask curators and affected communities to define which item records, fields, thumbnails, derivative sizes, manifests, exports and indexes are discoverable; what permission states and substitute images are appropriate; who changes rules; and how updates/revocations propagate. Keep legal rights separate from community protocol and technical access. A deny rule should cover direct URL access, cached derivative delivery, API responses, export and search side channels.
6. **Curator corrections and exports.** Each correction should expose current/original value, proposed value, authority/Label source, decision maker, timestamp, approval and rollback history. Export only records/fields the user's role may export; include stable IDs, provenance and export time. Exact schema and role set require museum decisions.

## Proposed discriminating validations — none executed

1. **Search relevance set:** curate 50–100 representative visitor queries across accession IDs, misspellings, common descriptions, unusual names, multilingual/ambiguous terms and sparse descriptions. Curators and non-expert visitors judge top-5 utility. Compare lexical baseline, synonyms/crosswalks and a hybrid configuration. Report exact-match success, recall-at-k, judged usefulness and cases where semantic broadening is wrong.
2. **Hybrid ranking stability:** with a version-pinned fixture and fixed queries/vectors, compare scores/order before and after adding a searchable field that is null on some documents. Inspect ranking details and thresholds; reproduce or rule out issue #6591 on the target version.
3. **Visibility leakage matrix:** prepare public, restricted-image/public-metadata, restricted-metadata, cultural-protocol, changed-rights and revoked-access fixtures. Exercise search snippets, counts, facets, autocomplete, detail, manifest, info.json, thumbnails, all image sizes, exports, direct URLs, cached derivatives, stale tokens and public mirrors. Assert authorized discovery, unauthorized omission/neutral substitute and purge/refresh timing.
4. **Denial status and cache regression:** for chosen image server, test missing, malformed, expired, revoked and valid authorization for info, thumbnail, tile and full-size routes. Require expected denial/redirect/substitute rather than server exception; ensure a previously authorized cached object is not served after revocation. Cantaloupe #536/5.0.5 is historical context, not evidence the test ran.
5. **IIIF profile and viewer check:** validate representative JPEG, PNG, large TIFF, multi-page and unavailable-image responses against declared profile, dimensions, crop/size behavior, CORS, requiredStatement and rights rendering; test viewer access flow over HTTPS. Compare static derivatives against dynamic server for storage, latency, quality and maintenance.
6. **Enrichment pilot:** sample by field and authority type; capture request latency/failures, ambiguous/unmatched rate, false positives after review, identifier persistence and export round-trip. Confirm authority service terms/rate limits and throttle/retry plan outside OpenRefine if required. No Getty/Wikidata query was sent here.
7. **Curator workflow:** have curators correct, reject a candidate, revert and export a filtered subset; verify original retention, provenance, role authorization, deterministic export and visible change history.
8. **Cultural governance review:** institution and community representatives review field visibility, Notices/Labels, wording, contact/attribution, owner/review date, appeal path and update latency. Validate Local Contexts display and API permissions with the institution's account type and current terms. UI tests do not substitute for community approval.

No runtime, database, museum account or qualified witness sandbox was supplied; no tests, benchmarks, API transactions or provider-usage checks were performed. These are proposals for later validation, not results.
