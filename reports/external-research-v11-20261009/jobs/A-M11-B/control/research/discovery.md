## Product problem and decision frame

The brief asks for a public discovery interface over 40,000 local-museum records with uneven descriptions and images, changing rights, and some culturally restricted material. It also calls for curator-visible corrections and exports. The user experience has two different vocabularies: visitors need plain-language discovery and exact object lookups; curators need provenance, review, and reversible edits. The scale count alone does not establish the existing catalog system, image stack, staffing, hosting, query load, language distribution, rights taxonomy, acceptable latency, model budget, or who has authority to define restricted-material rules. Tool choice and policy must remain conditional on those answers.

This is a small product brief, not a commitment to production-wide availability, legal interpretation, a model accuracy guarantee, or blanket exposure of a full catalog. No running application, catalog export, media corpus, qualified witness sandbox, access policy, or relevance judgments were provided. No runtime, security, benchmark, or curator-review check has been executed. All validation below is proposed.

## O1 — independently discovered options and materially different approaches

### Data quality and authority matching

**OpenRefine reconciliation** is a curator-oriented cleanup process, not a catalog serving engine. It can submit names/terms plus typed and property context to a reconciliation service and return ranked authority IDs with previews; its supported stable protocol is v0.2. Human review is required; candidate score semantics are per service. Start with authority-specific, small batches and preserve source fields; do not use the displayed top score as a universal confidence threshold. The “Use values as identifiers” operation assumes existing IDs and skips lookup, so use it only after validating the IDs. [S01](sources/02-curation-and-vocabulary.md#s01--openrefine-reconciliation-api), [S02](sources/02-curation-and-vocabulary.md#s02--openrefine-user-manual-reconciling)

**Getty AAT, TGN and ULAN** provide references for art/material-culture concepts, place names and artist/person names. The Getty makes them available via OpenRefine, SPARQL and linked-open-data downloads (JSON/RDF/Turtle/N-Triples); N-Triples full data is refreshed monthly and data is ODC-By 1.0, with specified attribution and contributor/source credit. Getty retired its XML web services and archived XML/relational data drawn 2026-01-30 is not refreshed. Favor maintained LOD workflows over legacy endpoints. Getty authorities are useful matches, not exhaustive museum truth, rights rules, or a substitute for local/community language. [S03](sources/02-curation-and-vocabulary.md#s03--getty-vocabularies-data--services)

Recommended curation shape: keep each original field immutable; write proposals as separate fields/rows with source authority URI, source version/date, candidate explanation/score and scoring service, transformation/model version if generated, reviewer identity/decision/date, rejection/uncertain state, and export history. Keep user-facing search aliases and curator-approved enrichments separate. Make correction and export actions idempotent, inspectable, and reversible. For uncertain matches, present candidates and evidence; do not silently replace local community terms with an external authority.

### Search approaches

Three viable designs deserve a common-data evaluation rather than a scale-based guess.

| Approach | Useful fit | Consequential defaults / costs | Conditional role |
|---|---|---|---|
| **PostgreSQL FTS + exact vectors first; pgvector ANN only if measured** | Strong baseline if PostgreSQL already stores the catalog; structured record, rights filter and provenance can remain together. GIN is PostgreSQL’s preferred FTS index. pgvector exact nearest-neighbor is default/perfect-recall. | HNSW trades recall for speed; pgvector v0.8.7 HNSW `m=16`, `ef_construction=64`, `ef_search=40`. ANN filters apply after index scan; underfill can occur. `vector` ceiling is 2,000 dims; `halfvec` 4,000. pgvector filtering issue includes a 40k-row case and shows iterative scanning is opt-in/tuning-sensitive. FTS configuration and field weights must be chosen. | Best low-complexity baseline if an existing PostgreSQL catalog is present. First measure exact FTS + exact vector and filters. Add ANN only if query latency needs it and relevant rows still meet recall/count targets. [S06](sources/01-search-and-ranking.md#s06--postgresql-18-preferred-text-search-indexes), [S07](sources/01-search-and-ranking.md#s07--pgvector-readme-at-v087), [S08–S09](sources/04-evolution-and-regressions.md#s08--s09--pgvector-filtered-ann-underfill--v080-iterative-scans--remaining-tuning) |
| **Typesense** | One purpose-built search service combines text, filters/facets and optional semantic retrieval; can use internal ONNX models, external embedding APIs or precomputed vectors. | v30.2 default hybrid weights are keyword .7/vector .3. Cosine distance range is 0–2, not a probability. Default HNSW `M=16`, `ef_construction=200`, `ef=10`; the vector index config differs from pgvector. Auto-embeddings rerun only on `embed.from` changes. Remote indexing batches default to 200 with 60s timeout/two tries; search remote timeout 30s/two tries. Model calls may send collection descriptions to a provider; internal model generation costs CPU/indexing time. | Candidate for the simplest integrated search-service proof if independent search operations are acceptable. Need test exact accession/object-ID paths and explainable match reasons; test provider/network/model/language conditions and benchmark actual 40k content. Use model versioned embedding records and rebuild plan. [S04](sources/01-search-and-ranking.md#s04--typesense-vector-search-and-embeddings-api-302) |
| **Qdrant** | Explicit multi-retriever architecture: named dense and sparse (e.g., BM25) vectors in a point, separately retrievable then fused/reranked. | Query API since 1.10; RRF defaults to `k=2`, equal per-retriever weights. RRF ignores raw score margins; fixed raw-score mixing is unsafe across scales. Candidate depth bounds which objects can win. Weighted RRF requires v1.17 per current docs and should be tuned on a separate labeled set. Multi-shard global fusion has a placement constraint. | Distinct option when evidence warrants independent vector retrieval and controlled fusion, and the team wants a vector service. It increases operational and synchronization work if the catalog remains elsewhere; no such need is established yet. [S05](sources/01-search-and-ranking.md#s05--qdrant-hybrid-and-multi-stage-queries) |

For visitor search, keep exact identifiers, accession numbers, proper nouns and title matches available in a deterministic lexical path. Add semantic retrieval as a second path for natural-language/lay-language discovery, not a replacement for exact/keyword retrieval. Give viewers plain-language query affordances: everyday category facets, sample searches, clear empty/refine state, filters and “why shown” cues such as title/description match versus related-topic suggestion. Score numbers should not be shown as confidence unless calibrated. Make terse or missing descriptions a distinct indexed state; a semantic embedding of empty text cannot create real object context. Do not invent descriptions/subject tags and present them as catalog facts.

### Images, rights and cultural protocols

IIIF Image API 3.0.0 supports interoperable region/size/rotation/quality/format requests and an `info.json` capability document. It explicitly specifies image delivery, not image management or enforcement. It can be backed by static derivatives or dynamic service. IIIF Authorization Flow 2.0.0 provides a browser-oriented challenge/token/probe pattern; a restricted image service’s `info.json` must declare its probe, all traffic and client pages must use HTTPS, and different access tiers should use distinct URIs. It supports substitutes (for example permitted lower-resolution alternatives), but the institution still has to define/implement authorization and cache policy. Do not gate only the viewer: test direct metadata, `info.json`, pixels/tiles, thumbnails, downloads, every derivative/copy/export path, cache invalidation after rights change, and all dimensions of unauthorized behavior. [S10](sources/03-images-and-access.md#s10--iiif-image-api-300), [S11](sources/03-images-and-access.md#s11--iiif-authorization-flow-api-200)

For a culturally restricted collection, **Mukurtu** offers a materially different, community/protocol-centered CMS model. Its current v4 manual requires protocols for each media asset and can sync them to the parent item or manage media independently; it explicitly describes open discoverable metadata with strict media access. Evaluate Mukurtu as a whole platform if that governance/workflow is central; the evidence does not establish migration suitability for this museum. **Local Contexts TK Labels** can identify community-specific provenance, protocols and permissions and explain conditions to visitors. They are a display/context and community-engagement layer; the museum must not treat a displayed label as a backend access check. [S12](sources/03-images-and-access.md#s12--mukurtu-v4-manual-media-access), [S13](sources/03-images-and-access.md#s13--local-contexts-traditional-knowledge-labels)

Separately model rights-in-use, public discoverability, metadata visibility, image/derivative visibility, and allowed reuse. These states can diverge. Before selecting open, member, request, seasonal, community-only, masked or suppressed tiers, the museum needs named decision-makers (including affected cultural/community authorities), practical review/change/appeal process, and a policy for records with unknown or stale rights. Pending a decision, no code path should infer public access from a missing rights value; preserve the record while defaulting the potentially restricted representation to an explicit review state. Keep an audit of who changed each access level and invalidate all derived public copies when it changes. Avoid putting restricted wording/content into embeddings, search suggestions, logs, public facets, exports or unrestricted analytics unless approved by that authority.

Cantaloupe is a relevant IIIF image-server option, but its release evidence shows why version-specific denial tests matter: 4.1 evolved authorization callbacks; v5.0.5 fixed an uncaught exception when `authorize()` returned HTTP 401. That proves a particular fix existed, not that current deployments are secure or that the server automatically enforces museum rules. Choose a pinned release only after checking its current support/security status and verifying deny/allow/cache behavior. [S14–S15](sources/04-evolution-and-regressions.md#s14--s15--cantaloupe-authdelegate-release-evolution)

## O2 — consequential behavior, defaults and scope

The decisive differences are visible in operation, not product counts: OpenRefine proposes and requires reviewer judgment; Getty delivers monthly linked authorities but retired legacy formats; Typesense combines ranks at .7/.3 by default with cosine distance, request timeouts and re-embedding triggers; Qdrant fuses bounded candidate lists by default RRF; pgvector exact search is recall-complete until ANN is introduced, where filter underfill and caps apply; IIIF separates standard delivery descriptions from server authorization; Mukurtu assigns policy at item and media asset layers. Those facts shape curator trust, public access and release validation. Detailed field/default/version evidence is indexed in [primary-source notes](sources/index.md), with exact locators in [source-map.json](source-map.json).

## O3 — issue, fix and release evolution

The best-sized analogue is pgvector issue #719 and v0.8.0: filtered approximate queries underfilled/returned no eligible rows; the 0.8.0 update introduced iterative scans and planner improvements but did not make iterative scans automatically active. The report includes a 40k-record case where choices between strict and relaxed scans materially changed time in that contributor’s setup. This is not a reproducible benchmark; it argues for measuring filter completeness and latency rather than trusting row count or default ANN. A second applicable chain is Cantaloupe 4.1 authorization callback evolution, a v5.0.5 HTTP-401 exception fix, and subsequent 5.0.6 changes. This shows denied/error response paths can regress; it does not demonstrate an actual museum-specific regression or secure policy. [S08–S09](sources/04-evolution-and-regressions.md#s08--s09--pgvector-filtered-ann-underfill--v080-iterative-scans--remaining-tuning), [S14–S15](sources/04-evolution-and-regressions.md#s14--s15--cantaloupe-authdelegate-release-evolution)

## Proposed discriminating validations (none executed)

1. **Relevance set:** construct a curator-judged set representing exact accession/object IDs, uncommon proper names, known title fragments, historical spellings, ordinary visitor descriptions, field-specific technical terms, typos, multilingual and no-description objects, broad themes, and zero-result/noise queries. Compare lexical baseline, Typesense default hybrid, a separately measured alpha, Qdrant dense+sparse RRF, and PostgreSQL exact vector where feasible. Use the same catalog snapshot, embeddings/model version, and filters. Report recall@k, MRR/nDCG@10, exact-ID success, coverage for empty-description rows, query/task completion, judged false associations and p50/p95 latency. Split tuning and evaluation queries to avoid tuning on the final set.
2. **Curator enrichment:** stratify OpenRefine samples across authority types, service, missing/ambiguous data, near-identical people, same-name places, non-match, cultural terms and known IDs. Inspect false-positive best candidates and score distributions service-by-service. Verify bulk approval/revert, original-field preservation, source attribution and export round-trip; exact IDs should be checked before applying the no-lookup ID operation.
3. **Access matrix:** create test fixtures for public, restricted, pending/unknown and approved substitute media with at least signed-out/public and permitted-member identities. Directly request catalog record/API, facets/autocomplete, image `info.json`, IIIF tile/region requests, full-size originals, thumbnails, alternate formats, manifests/annotations, search suggestions, caches/CDN and exports. Assert no restricted bytes/metadata or sensitive terms leak on every unauthorized path; verify the explicitly allowed reduced tier and rights-change invalidation. Test both a museum policy decision and exact community-designated roles, not a label-only UI.
4. **Images/operations:** run representative source formats, large dimensions, EXIF orientation, cropped/rotated/region variants, transparent/color images and corrupt files through proposed image delivery; check dimensions and rights metadata, status/errors, cache behavior, latency and accessibility of image alt/context. If image rights change, test purging all public derivatives.
5. **Scale and lifecycle:** benchmark the full 40k import/index and representative concurrent search under available hardware and network conditions; record model provider, token/request billing estimates and local/remote inference; measure reindex/update/correction propagation, batch failure/retry/idempotence, backups and export. For pgvector ANN, compare exact ground truth under every hard filter and rights predicate, measure empty/underfilled output and scan-limit hit rate at different selectivities/strictness. None of these were run here.
