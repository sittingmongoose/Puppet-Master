# Research draft — field inspections

**Case:** S01 / A-M01-A / control / research-q2  
**Plan compared:** revealed-plan.md, P1–P6  
**Research status:** Independent product/workflow discovery plus exact per-clause adjudication. Discovery was saved before reveal and remains frozen. Plan-comparison evidence added afterward is indexed in source-map.json and sources/source-notes.md.  
**Execution status:** No product runtime, test device, or qualified sandbox witness was used. Validation activities below are proposals only.

## Recommendation

The thin plan makes material decisions about platform, offline storage, synchronization, media references, authorization, and testing without defining how an inspection survives a day offline or how a coordinator returns it for correction. Keep the form-first and straightforward small-team workflow, but make the state and data transitions explicit before implementation.

The smallest credible workflow is: an inspector opens an assigned inspection, resumes a durable draft, records structured answers/location/photos offline, marks it ready, and sees the complete case package queued until all parts are acknowledged by the server. The coordinator sees only received cases with their media-completeness state, leaves a reasoned correction request, and sees the later version and activity history when it returns. Export bundles preserve the case data and linked original photos in ordinary formats. A future self-hosted deployment remains an operating choice with a named operator, backup/recovery plan, and independent export path.

Prefer one active editor per inspection in the first release: inspector owns the local draft, coordinator reviews the accepted version, and a correction request hands editing back. Reject silent last-write-wins for inspection facts. Give every inspection, submission version, and photo a stable identity; stale versions must be detected and both values retained until a person resolves them. The exact ownership, sharing, media-retention, and conflict-resolution policies remain user decisions.

| **P1: “Use a PWA and browser local storage for all offline records.”** | **Rejected as written; platform choice uncertain.** | A PWA is an optional prototype path, not established by this research as the right field client. Reject localStorage as the sole home for all offline records and photos. The HTML Standard defines localStorage as an origin-scoped key/value store using DOMString values and cautions that shared storage across browser agent clusters has no guaranteed locking. The WHATWG Storage Standard snapshot registers a 5 × 2^20 byte (5 mebibyte) recommended quota for the localStorage endpoint; this is not a universal measured cap for all browser APIs. Its broader quota is implementation-defined, buckets start best-effort, and persistent storage requires permission. Best-effort storage may be cleared under storage pressure. Those constraints do not rule out a PWA using IndexedDB or another browser file store for records and separate photo blobs, but it would still need a granted/verified persistence state, quota checks, visible storage-full handling, safe schema upgrades, and crash/reboot recovery evidence on the actual Android browser. Keep a PWA pilot optional until camera/geolocation, large attachments, sensitive offline data, one-day use, and recovery pass the same field scenario as a native client. **User decision:** native Android versus PWA, conditioned on those results and the support team’s ability to deploy updates. Sources: [HTML Standard: Web Storage](https://html.spec.whatwg.org/multipage/webstorage.html), [Storage Standard snapshot](https://storage.spec.whatwg.org/commit-snapshots/23f38d8feaf530b9787822e067a7eb6f953af322/). |
| **P2: “Upload complete inspection JSON on reconnect with last-write-wins.”** | **Split disposition: retain a versioned complete new-record submission as an option; reject last-write-wins; correct the sync contract.** | A complete JSON payload may be a reasonable first submission if it has a stable client-generated case ID and can be retried idempotently. It does not settle the independent photo upload/acknowledgement path or edits to an already accepted case. Require a server version/base revision on updates; stale submissions become visible conflicts, never silent replacements. ODK’s API is one concrete pattern: an update identifies the current version; a stale version returns HTTP 409; update XML replaces the whole record, while matching media names can be carried to the next version. QFieldCloud demonstrates why the default must be explicit: its documented default is timestamp Last Wins and an older conflicting attribute update is discarded, although history keeps it. ODK’s and QFieldCloud’s behaviors are product-specific examples, not a spec for this app. **User decision:** whether first release limits edits to one owner at a time or supports overlapping edits and how a coordinator resolves them. Sources: [ODK Central Submission Management API](https://docs.getodk.org/central-api-submission-management/#updating-submission-data), [QFieldCloud conflict behavior](https://docs.qfield.org/reference/qfieldcloud/jobs/). |
| **P3: “Store photo URLs in each form.”** | **Rejected; replace with stable attachment references and an offline media path.** | An online URL cannot identify a not-yet-uploaded camera image while the inspector is offline. Persist each photo as an attachment object with stable media ID, parent inspection/version ID, local durable file/object reference, capture metadata, and a content digest. Queue it separately and expose whether it is present locally, uploading, acknowledged, or failed. The case JSON refers to the stable media ID; the server creates an authorized URL when needed. Export a manifest that reconnects every media ID to a portable file. ODK Central’s documented CSV ZIP uses per-submission attachment folders; Mergin’s selective-sync option shows that a feature can arrive on another device while the photos remain unavailable there. Photo visibility, EXIF/location disclosure, compression, retention, and selective sync must be explicit. Sources: [ODK Central export layout](https://docs.getodk.org/central-submissions/), [Mergin selective sync](https://merginmaps.com/docs/manage/selective_sync/). |

A generic review button plus CSV alone is insufficient. Specify received/missing-media indicators, searchable queue, reviewer comments/reasons, correction return path, attributed version history, and explicit approval state. A CSV export should include a media manifest and attachments, stable IDs, field dictionary, coordinate units, version/status metadata, and filters for selected cases/media. ODK Central is a useful benchmark: its states include Received, Edited, Has Issues, Approved, Rejected; only some are automatic, and states do not trigger workflow actions. Rejected submissions remain in exports unless filtered. Its ZIP carries root/repeat tables and an attachments folder associated by submission instance ID. **Optional enhancement:** GeoJSON/GeoPackage for map-focused recipient workflows, after validating use. **User decisions:** names/transitions for states; whether rejection means exclusion or merely a flag; export and sharing audience; whether discussion/version metadata is in the public bundle. Sources: [ODK submission review states](https://docs.getodk.org/central-submissions/#submission-review-states), [ODK Central roles/form access](https://docs.getodk.org/central-projects/). |
| **P5: “Defer access control beyond individual sign-in until rollout.”** | **Rejected as written; add minimum authorization before the pilot.** | The brief includes selective sharing, inspectors and a coordinator, and inspection photos/locations. A sign-in identifies a person but does not decide which cases, photos, review actions, or exports that person may use. At minimum, model inspector, coordinator/reviewer, and administrator capabilities separately, scope inspectors to assigned inspections, prevent field users from browsing unrelated submissions, and filter exports/shares. This is a product-scope recommendation from the case’s sharing requirement, not a claim that a specific legal rule applies. The ODK example separates project roles and can assign mobile users access to selected forms, illustrating that identity and authorization scope are distinct configuration concerns. **User decision:** exact permission granularity, guest/partner workflow, roles, link versus file sharing, retention, and whether assignment-level scoping is required at initial pilot. If the team cannot decide partner access yet, ship no external-sharing path until it can be configured safely; do not rely on account sign-in alone. Source: [ODK Central project roles and form access](https://docs.getodk.org/central-projects/). |

## Retained product and workflow findings

### Alternatives and conditions

- **ODK Collect + Central: form-first open stack.** It is the closest researched Android/offline benchmark for forms with location and image responses. Central supplies role and form access, a coordinator review table, comments, missing-media warnings, edit history, filtering, and exports with linked media. It is relevant both as a lower-code pilot and as an example to compare against the custom correction workflow. Central can be managed through ODK Cloud or self-hosted. Self-hosting is free software, but the operator still needs a DNS domain, Linux/Docker administration, backup/upgrade responsibility, storage, and time. Its docs report a trial with 50 devices and 5 MB submissions, with about 1–2 submissions per second when attachments constrain throughput; that is bounded vendor evidence, not an SLA or prediction for this smaller team. Sources: [ODK Collect](https://docs.getodk.org/collect-intro/), [ODK install/self-host guidance](https://docs.getodk.org/central-install/).
- **KoboCollect + KoboToolbox: enumerator-survey workflow.** Forms must be preloaded; records can be kept as editable drafts or finalized/queued to send. Offline finalized records can be sent after reconnect, and the vendor documents manual USB transfer for devices with no internet path. Its draft/final distinction is a good training and status pattern. Evaluate correction routing and coordinator permissions in a hands-on scenario before assuming it covers the full case. Source: [KoboCollect data collection](https://support.kobotoolbox.org/data_collection_kobocollect.html).
- **QField/QFieldCloud or Mergin Maps: GIS and feature-first workflow.** This is useful if inspectors rely on parcel/building maps, spatial selection, geometry, or offline basemaps. QFieldCloud packages offline layers as GeoPackage and offers configurable conflict handling, but the documented default Last Wins can discard the older overlapping change. Mergin recommends GeoPackage for collaborative offline editing and offers selective photo sync: collaborators may see feature data while another inspector’s photos do not download to their device. A QGIS project and a map-led training workflow add work if inspection by address and form is sufficient. Sources: [QFieldCloud jobs/conflicts](https://docs.qfield.org/reference/qfieldcloud/jobs/), [Mergin supported formats](https://merginmaps.com/docs/gis/supported_formats/), [Mergin selective sync](https://merginmaps.com/docs/manage/selective_sync/).
- **ArcGIS Survey123: mature managed form stack.** It demonstrates Draft, Outbox, Sent, and optional Inbox states; an unsent Outbox record can be edited. Its current docs specify an Inbox maximum of 5,000 parent records (repeat records add more). A response exists in only one device folder at a time; a Sent/Inbox configuration can fail to pull an update made from another device. Consider it if the nonprofit already uses ArcGIS, with a test of ongoing correction and a full media export before adoption. Sources: [Survey123 offline sending](https://doc.arcgis.com/en/survey123/capture/mobile/submitsurveyresults.htm), [Survey123 existing-data editing](https://doc.arcgis.com/en/survey123/create/connect/prepareforediting.htm).
- **Fulcrum: commercial general-purpose benchmark.** It distinguishes a filtered Data Downloader from a broader Exporter. The Downloader supports several spatial/database formats and has a 10 GB and/or 100,000-media-file limit; the Exporter is faster for full history but has less filtering and limited line/polygon support. The docs support comparison of photo/GPS/history export controls, but this research did not verify pricing, offline behavior, self-hosting, terms, or nonprofit suitability. Those remain procurement questions. Source: [Fulcrum export options](https://help.fulcrumapp.com/en/articles/73547-how-to-download-or-export-data).

The right discriminator is task fit, not raw feature count: compare a form-first assigned-inspection flow with a map-first flow only if inspectors actually need map navigation. A hosted product may shorten setup; a self-hosted option may shift cost to staff operations; custom work may offer a focused offline correction journey but carries full reliability and maintenance responsibility.

### Field usability and accessibility

Use plain questions and instructions, visibly mark required versus optional evidence, and reveal only relevant follow-ups. Allow a clear “cannot capture” reason when GPS/camera is unavailable rather than making a permission failure look like a corrupt record. Preserve typed answers and lead directly to correction when validation fails. Do not convey error or required status with color only.

Android guidance calls for labeled controls, accessible full flows, and testing with platform tools such as Accessibility Scanner. WCAG 2.2 SC 3.3.1 requires automatically detected errors to identify the affected item and describe the error in text; generic first-error-only feedback can create repetitive submissions. WCAG 2.2 SC 2.5.8 describes a 24-by-24 CSS-pixel target or spacing exception for web content. Keep that CSS unit on the web coordinator surface; test Android controls with platform guidance, TalkBack, actual device sizes, and enlarged text. Sources: [Android accessible app guidance](https://developer.android.com/guide/topics/ui/accessibility/index.html), [WCAG 2.2 Error Identification](https://www.w3.org/WAI/WCAG22/Understanding/error-identification), [WCAG 2.2 Target Size Minimum](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum).

### Portability, media, and privacy

The routine exit path should produce a self-contained filtered bundle: CSV case rows, stable IDs and schema/data dictionary, original photos, and a manifest joining photo IDs/files to cases. Preserve location as numeric coordinates with explicit units/reference and accuracy/source. A map-focused format can be optional. Do not treat a vendor’s media URL, a browser URL, or a database row ID as the only copy of a photo or inspection.

Selective sharing needs an explicit audience, selected cases/fields/media, permission boundary, and retention/revocation policy. The brief does not state whether partners need image-level access, whether GPS may be disclosed, whether links are acceptable, how long media should live, or how EXIF should be handled. These decisions should be made before shipping any external-sharing workflow. A future self-hosted deployment is viable only if an operator, backup/restore process, upgrades, and support ownership are agreed.

### Relevant evolution and exact behavior

The ODK Central changelog is an applicable product evolution chain: v1.2 introduced submission edits, review states, and comments; v1.3 added per-submission diffs and audit events including export; v1.4 added CSV options, deleted-field export, form-version metadata, and a 30-day restore/purge path for deleted forms. A later release fixed submission-geodata parsing for XML content fragments. This history shows review, history, and export changed as separate features over time; it is documentation/release-history evidence, not a reproduced regression. Source: [ODK Central API changelog](https://docs.getodk.org/central-api-changelog/).

ODK API update semantics are version-specific: the update must identify the current version; stale IDs receive 409 Conflict; the update XML replaces all fields; matching attachment names are copied. QFieldCloud’s Last Wins is another product-specific default. Neither should be generalized into a universal synchronization rule. Full locators, commit/edition data, access timestamps, and observed research operations are in source-map.json.

## Discriminating validation proposals

**Executed:** no app tests, device runs, user studies, uploads, exports, or deployment checks. These checks require a qualified runtime/device setup, not supplied with the input map.

1. **Disconnected capture and recovery:** On representative Android devices, preload current forms and assigned work; go offline for a simulated shift; capture drafts, location, and representative photos; force-close/reboot during entry and during media upload. Reconnect after a temporary interruption. Require all answers/media present, no duplicate cases on retry, visible upload acknowledgements, and editable drafts. Record OS/app build, file sizes, space, completion times, and received IDs.
2. **Correction and stale-version race:** Submit a case; coordinator flags a missing detail and returns it with a reason; inspector corrects after reconnect. Separately edit the same field from both clients based on the same earlier version. Require conflict detection, preservation/attribution of both candidates, and an explicit resolution; verify a different-field edit separately. No silent lost update.
3. **Form usability and accessibility:** With representative inspectors, run the same unfamiliar inspection form on actual screen sizes. Record completion, missed required evidence, correction rate, recovery after interruption, and confusion. Exercise TalkBack order and announcements, large text, touch spacing, contrast, location/camera permission denied, and clear text errors. Compare map-first only if route/building selection is a real task.
4. **Coordinator workflow:** Give a coordinator cases in Received, missing-photo, correction-requested, resubmitted, and approved conditions. Ask them to find exceptions, write a useful correction reason, return the right case to the right inspector, verify the updated version, and export a filtered set. Measure missed cases and state confusion.
5. **Media and sharing:** Use a representative photo batch; fill storage, deny camera permission, interrupt a media transfer, and retry it without re-sending the case. Verify content digests, attachment-parent links, original-file preservation, and photo/EXIF policy. Verify that a selected export/share contains only authorized records and media; if links are chosen, test expiration and revocation.
6. **Portability and future hosting:** Export a sample batch; reconcile row counts, types, units, statuses/versions in scope, IDs, and all media joins. Open it without a vendor account. Separately restore a proposed self-host deployment from written backup steps using a clean operator/environment; record prerequisites and maintenance burden. A CSV download alone is not proof of migration.

Set quantitative acceptance thresholds with the nonprofit before a pilot; do not invent participant performance targets or describe proposals as passed checks.
