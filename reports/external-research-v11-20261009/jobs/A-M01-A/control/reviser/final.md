## Scope and conclusion

The brief is for a small housing nonprofit with twelve Android inspectors who may work without service for a day. They capture forms, photos, and location; an office coordinator reviews corrections. Deployment should stay simple, data must be exportable and migratable without vendor lock-in, forms must be accessible, sharing must be selective, and a small self-hosted deployment may be considered later.

The evidence supports prototyping a **local-first inspection workflow** with durable offline records, a durable queue, separately tracked photo files, explicit versions and correction history, server-side scope checks, and a product-owned records-plus-media export. A Kotlin Android client using Room/SQLite, persistent app-private files, and a small authenticated API with a relational source such as PostgreSQL is a **candidate baseline to prove**, not a selected product or platform. A PWA remains a valid comparison if the target Android browsers pass the same offline and recovery scenarios. ODK Central, Kobo, PowerSync, CouchDB, GIS-first products, Survey123, and Fulcrum remain conditional alternatives.

The nonprofit still needs to choose its correction and ownership workflow, role and sharing scope, retention and photo policy, GPS requirements, export/import behavior, preferred client and hosting mode, acceptable operations burden, and who will run any self-hosted service. Documentation cannot decide those product questions or demonstrate the reliability of an implementation.

## Coherent workflow and data model to prototype

An inspector should open only assigned work, start or resume a locally saved draft, capture typed answers and location, add photos, and explicitly mark the case ready. The app should distinguish local save from server receipt. A visible queue should show metadata and each attachment’s state: saved locally, waiting, uploading, acknowledged, or failed. It should retain work through process death, reboot, storage pressure, and a day without service. On reconnect it should retry safely and show the server acknowledgement.

A coordinator should see received cases and whether their expected media arrived, filter a queue, review the submitted version, and return a correction with a reason. The inspector should see that reason beside the affected answer or photo and create a new version tied to the same stable inspection. The coordinator should see the changed version and activity history before approval or further return. These state names and transitions are examples to validate with the nonprofit; the brief does not prescribe a particular state machine.

The first release could use **one active editor per inspection**: inspector edits a draft, coordinator reviews the accepted submission, and a correction request hands editing back. This lowers collaboration complexity but still needs duplicate-send protection and stale-version detection. If simultaneous edits are allowed, the app must preserve both candidates and provide a human resolution path. Whether one-editor ownership is acceptable is a user decision, not something the sources settle.

A practical model is a versioned form/template, inspection identity, typed answers, attachment metadata, and append-only submission/correction/review events. Generate stable UUIDs on device so a case, event, or photo can exist offline. Record the event ID, target case, expected base version, actor/device, device capture time, server receipt time, and delivery state. Keep device time separate from server ordering. Retain the form version used for capture so older submissions remain interpretable. Use a server version or conditional update so an offline snapshot cannot replace a newer revision silently.

For Android, Room/SQLite is a plausible structured local store with explicit schema migration history. Commit a form edit and its outbox record together. Keep the outbox state in the database rather than only in a scheduled job. Android WorkManager can schedule network-constrained retries; periodic work has a 15-minute minimum, system conditions can delay or skip a run, and default retry backoff is exponential from 30 seconds. These are scheduling defaults, not delivery-time guarantees. Keep a manual retry and truthful queue display [Q1 A01–A03].

Keep each original photo as a separate durable file or object, not a transient URL or a large field in an often-edited inspection row. Store a stable media ID, parent inspection/version, MIME type, byte length, digest, capture metadata, and local/upload state. CameraX file output completes asynchronously and can fail. Android app-private files survive ordinary process restarts but are removed on uninstall; Android’s Storage Access Framework can support explicit import/export destinations. The product must decide gallery visibility and whether images survive uninstall/account removal. Queue image bytes independently from answer data and do not show a case package as complete until its expected attachments are acknowledged [Q1 A04–A06, Q1 P06].

Keep location as structured coordinates with reference/units, reported accuracy in metres, capture time, and source such as GPS, selected map point, or manual entry. The brief does not decide whether location is mandatory or what accuracy is sufficient. The UI should explain denied permission, unavailable fix, coarse or stale accuracy, and any allowed manual fallback rather than silently blocking or fabricating a result.

These are materially different approaches, not a market ranking.

| **CouchDB document replication** | Provides HTTP document storage, checkpointed bidirectional replication, partial replicas, and retained concurrent leaf revisions. Self-hosting requires Linux/Docker administration, DNS, backups, upgrades, storage, and an operator. ## Exact P-clause adjudication

| Clause | Final disposition | Evidence-based reasoning and retained decision |
| --- | --- | --- |
| **P1 — “Use a PWA and browser local storage for all offline records.”** | **Correct the persistence recommendation; leave client choice uncertain and to the user.** | A PWA is not ruled out, but localStorage is not justified as the only durable store for all inspection data and photos. The HTML Standard describes origin-scoped string key/value storage and warns against relying on a locking mechanism across agent clusters. A pinned Storage Standard snapshot records a *recommended* localStorage quota of 5 × 2^20 bytes (5 mebibytes), not a universal measured cap for every browser or API. The same standard says actual overall storage quota is implementation-defined; local buckets start best-effort and can be cleared under storage pressure, while persistent mode requires permission. A PWA using IndexedDB or another file store could still work, but must show persistence/quota state, handle storage-full conditions and upgrades, and pass crash/reboot, camera/geolocation, large-photo, and one-day offline tests on target Android browsers. The numeric snapshot is now independently re-opened at its exact commit through the WHATWG GitHub source [Q2 WHATWG-HTML-WEBSTORAGE, WHATWG-STORAGE-SNAPSHOT; CR01; RV06]. |
| **P2 — “Upload complete inspection JSON on reconnect with last-write-wins.”** | **Split: a versioned full first submission may be an option; reject silent/general LWW and correct update/replay behavior.** | A complete payload can be a reasonable initial submission if it has a stable client-generated ID and can be replayed idempotently. It does not solve photos or edits to an accepted case. Require a current base version or expected revision for updates; stale submissions should be visible conflicts. ODK’s API is one example: an update names the current version, stale version IDs receive HTTP 409, the XML replaces the whole prior record, and matching attachment names are copied. QFieldCloud demonstrates a product-specific timestamp Last Wins default that discards the older overlapping attribute change but retains it in history. CouchDB preserves conflicting leaves but still requires application-level merge/resolution; PowerSync’s simple server-authoritative example is per-field last-update-received-wins with delete-wins. None of these product defaults decides what is correct for an inspection fact. Preserve both disputed answers and coordinator corrections until the nonprofit chooses an ownership and resolution policy [Q2 ODK-CENTRAL-API-UPDATES; Q2 QFIELDCLOUD-JOBS; Q1 C02, P05; CR02, CR04]. |
| **P3 — “Store photo URLs in each form.”** | **Reject a URL as the complete photo design; use stable attachment identity and an offline media path.** | A remote URL cannot represent a photo that is not yet uploaded and does not guarantee the content or authorization. Keep the original bytes in durable local storage, link stable media and parent IDs, track hash/size and transfer status independently, and issue authorized remote URLs only when appropriate. Include a manifest that restores the media-to-case join. A URL remains a possible post-upload locator. ODK’s CSV ZIP and Mergin selective-sync examples show why media joins and per-device visibility need explicit handling [Q1 A04–A06, P06; Q2 ODK-CENTRAL-SUBMISSIONS, MERGIN-SELECTIVE-SYNC; CR07]. |
| **P4 — “Add coordinator review and CSV export.”** | **Already covered by the brief; retain and specify the workflow and export.** | Coordinator correction review and vendor-independent export/migration are already requirements, not new features. Specify reviewer identity/reason, states/transitions, version presented, missing-media state, return path, and approval behavior. A CSV alone does not preserve template versions, typed history, files, or access scope. Export should include stable IDs, a field dictionary and coordinate units, in-scope status/version/history, original photo files, and a manifest with counts and hashes. Whether to export all assigned properties, a selected batch, or a coordinator archive, and whether GeoJSON/GeoPackage is useful, remain user decisions [Q1 A03, D01; Q2 ODK-CENTRAL-SUBMISSIONS]. |
| **P5 — “Defer access control beyond individual sign-in until rollout.”** | **Reject deferral if sharing is enabled; add minimum server authorization before any pilot that exposes shared records.** | Sign-in authenticates a person; it does not define which inspections, answers, correction actions, photos, or exports they may use. Before enabling selective sharing, the server must enforce the chosen minimum scope on record reads/writes and photo retrieval, not just filter the client’s sync. If the nonprofit has not defined partner sharing, keep that path disabled until it has. The brief requires investigation of selective sharing but does not choose a role matrix, whether per-property assignment is needed on day one, or cached-data retention after revocation. PowerSync auth-derived filters are not a substitute for upload/file endpoint authorization; CouchDB database membership is broader than a replication selector [Q1 P04–P06, C01, C03, C04; Q2 ODK-CENTRAL-PROJECT-ACCESS; CR04]. |
| **P6 — “Test by toggling network off and on.”** | **Retain as a connectivity smoke check; correct it as insufficient release validation.** | Toggling connectivity can confirm a basic indicator or reconnect path, but not one-day durability, killed-process recovery, incomplete files, idempotent retries, stale-version conflicts, authorization boundaries, accessibility, migration, or restore. The expanded checks below are proposed only; none was run. |

## Accessibility, selective sharing, privacy, and operations

Use plain questions and instructions, explicit required/optional labels, conditional follow-ups, and field-level text errors that identify what is wrong while preserving the value. Provide a meaningful “cannot capture” or manual fallback only when the product accepts it. Label Android controls and test TalkBack, large text, touch spacing, contrast, focus, and error announcements on target devices. Android platform guidance and Accessibility Scanner are useful, not proof of a working flow. WCAG 2.2 error identification requires text that identifies the item and describes an automatically detected error; its target-size criterion is 24 by 24 **CSS pixels** or an exception for web content. Do not relabel CSS pixels as Android dp [Q2 ANDROID-ACCESSIBILITY, WCAG-ERROR, WCAG-TARGET; CR10].

Selective sharing needs an audience, permitted cases/fields/media, server-enforced read/write scope, and retention/revocation behavior. Decide what coordinator and inspector roles can do, whether partners need image or GPS access, whether a link or filtered file is appropriate, how links expire, and what a disconnected device retains after reassignment or account revocation. Include photo EXIF/location policy, photo visibility, and whether unsynced data can ever be removed. A filtered portable bundle may be safer and easier to migrate than an unrestricted account or link. This is product-policy work; no legal or privacy compliance assessment was performed.

For a future self-hosted service, name the operator and require documented updates, TLS/secrets handling, database and file backups, restore rehearsal, monitoring, and storage planning. “Simple deployment” cannot be inferred without the organization’s staffing and operations capacity. Back up the database, media objects, and necessary keys together.

## Critique adjudication and source updates

The critique’s material findings were reviewed against current primary sources and affected dependencies.

1. **Survey123 existing-image behavior — accept and incorporate with a narrow scope.** The current official page states that Inbox retrieval does not download existing images and that offline workflows are unsupported for editing existing images. It also says new images are enabled by default. This limits a returned inspection that asks an inspector to edit an existing photo; it does not establish that Survey123 cannot capture new images offline. The option comparison and validation now name that scenario explicitly [CR08; RV04].
2. **CouchDB issue #5422 mutable state — accept the need to correct and timestamp the source, but amend the critic’s claim that no resolution was visible.** The critic’s 18:43–18:46 retrieval recorded a closed issue page without a visible explanation. The reviser’s later retrieval found the maintainer discussion: #5422’s 3.4.2 attachment-stub reproduction was attributed to replication not properly passing atts_since on document GET; PR #5437 was merged to main on 2025-02-21. CouchDB 3.4.3 release notes list #5437 as fixing atts_since behavior to avoid re-replicating attachment bodies on document updates. The same notes list #5347 as fixing attachment-size calculation that could prevent shards from being scheduled for compaction. Therefore the point-in-time 3.4.2 report remains valid historical evidence, while the claim that no fix was observed is superseded by a direct release-note and PR check. This is documentation evidence, not a runtime reproduction or a claim about every later build. Keep the CouchDB gate: reproduce the reported sequence on 3.4.2 if available, verify the intended release contains the fix, test an exact 3.4.3 or later target, and measure database size/compaction under the actual attachment workload [Q1 C05–C06; RV01–RV03].
3. **PowerSync Room/attachment maturity citation — accept and separate.** The q1 P06 attachment page supports the Kotlin helper’s Alpha status but not Room ORM status. The critic’s separate official Feature Status entry is retained, and the reviser independently opened the live status table: Kotlin SDK GA, Room (Kotlin) Beta, Kotlin attachment helper Alpha. These are distinct features; do not collapse them into a generic “Kotlin SDK maturity” statement [Q1 P06; CR05; RV05].
4. **ODK licensing language — accept the precision improvement.** The source supports that Central’s source code is Apache 2.0 and says bundled third-party software has its own licenses. It is not a full license audit of all components or hosting terms. Keep this as procurement diligence, not a rejection of ODK [CR11].
5. **PowerSync P05 multiple URLs — accept and preserve source identity.** Its original source ID covers both the client-write endpoint page and update-conflict page. The inherited map is preserved without mutation; this final distinguishes which claim belongs to each URL. Do not silently reassign the original ID or treat the two pages as one mutable document [Q1 P05].
6. **CouchDB C05 immutability label — accept and correct through an additive record.** The inherited C05 source ID and its historical observation remain intact. The issue’s status and comments are mutable, so RV01 adds a timestamped later observation and RV02–RV03 identify the fix chain. The inherited record is not overwritten or rebound.

## Proposed validations — none executed

No Android runtime, representative device, application/backend, user session, or qualified sandbox witness was available. The following are discriminating proposals, not results.

1. **One-day offline durability:** preload the current form/template and assigned cases; disconnect for 24 hours; capture drafts, answers, location, and photos; force-close and reboot at defined points. Pass only if acknowledged local saves reopen intact, queue states are truthful, and unsent data remains.
2. **Photo integrity and capacity:** interrupt CameraX completion and upload, fill storage, kill the app, and retry the media without resending the case. Check hashes, orphan recovery, original preservation, low-space messaging, and that unsynced files are never silently cleaned.
3. **Replay and acknowledgement:** interrupt metadata and media transfers at different boundaries, restart workers, and replay the same event ID. Pass if the server has one logical event, hashes match, and the UI reports settled state only after actual acknowledgement.
4. **Conflict and correction handoff:** from the same base, edit the same field on two devices and a different field separately; have a coordinator request a correction while one device is stale; reconnect in both orders. Pass if both same-field values and reviewer history are retained, the chosen policy is explicit, and no correction silently disappears.
5. **Authorization and revocation:** give two inspectors different assignments; alter IDs/subscription parameters, call direct APIs, guess attachment IDs, replay after revocation, and reuse file URLs. Pass if server denies every new out-of-scope operation and documentation makes offline cached-data limits clear.
6. **Export, import, and restore:** export selected cases with schemas, status/version/history in scope, original photos, manifest, counts, and hashes. Import into a clean database/app version and verify all joins and hashes. Corrupt a file or manifest and require rejection without partial replacement. Separately restore database and files from self-host backup instructions.
7. **Form and schema migration:** carry open drafts and queued events across field additions, renames/removals, and template updates. Preserve historical interpretation and prove no pending answer is lost.
8. **Accessibility across offline states:** test TalkBack order/announcements, large text, touch spacing, keyboard navigation where applicable, field-level text errors, permission denial, draft recovery, photo flow, and correction comments without a connection. Include real target Android devices and the coordinator’s web surface.
9. **Coordinator usability:** give a coordinator received, missing-photo, correction-requested, resubmitted, and approved cases. Ask them to find exceptions, write an actionable reason, return the correct case, verify the next version, and export a filtered set. Agree quantitative thresholds with the nonprofit before any study.
10. **Alternative-specific gates:** if PowerSync is shortlisted, pin the maintained service/SDK and license, prove self-host without the dashboard, test JWT scopes and modified parameters, verify synchronous/idempotent backend writes and file authorization, and include the documented v1.23.0 wildcard Sync Stream regression fixed by PR #676 in the upgrade test. If CouchDB is shortlisted, prove the Android client, inspect concurrent branches and authorization boundaries, and reproduce attachment size/compaction behavior on the exact release. For Survey123, test a returned Inbox response with existing images and an offline attempt to edit/replace a photo, then verify exactly what the coordinator receives. For ODK/Kobo, exercise the real correction loop and complete media export.
11. **Connectivity smoke check:** retain a simple offline/online toggle as one small connectivity test, not as evidence for the other cases.

Before a pilot, set quantitative acceptance thresholds with the nonprofit; do not infer them from product documentation or the exploratory 5–8-person usability suggestion in q2.
