# H01 post-reveal research disposition

**Stage:** ER11 C-01 / treatment / research. **Plan revealed after discovery freeze:** 2026-10-09 UTC. This draft uses only source IDs established in the frozen [pre-reveal discovery](discovery.md) and [source map](source-map.json); no new source inventory or external answer was added after reveal. ## Decision summary

Run a short, synthetic-data comparison of (1) a funeral-specific product demo, Passare, and (2) a modular groupware/resource-booking pilot using a version-supported Nextcloud Calendar + Calendar Resource Management pairing. These are candidates for evaluation, not selections. Passare better matches funeral case/tasks/family communication in its vendor description, but current cost, permission granularity, offline behavior, and export are unknown. Nextcloud can model several contested resources and provide a standard calendar export, but its event sharing is coarse and an open project issue documents private resource-event disclosure. A third-party private-event toggle is not a safe privacy control for linked resources. Do not enter real family data in that candidate until role-based synthetic-user checks pass.

A central office-LAN service is a promising outage design to test because most work is from one office; it remains an inference and depends on LAN, power, local server, and name resolution. A custom per-device offline-first application could queue work but needs explicit conflict and resource-arbitration behavior and appears disproportionate for this small pilot without a funded developer/maintainer. Defer LibreBooking: v7.0.0 fixed a documented critical pre-7.0.0 takeover issue, but the project's README, as consulted on Oct 9, announced a further high-impact security release for Oct 13. No first-year cost or candidate's total cost is known; require written totals under the $10,000 ceiling before procurement.

### Other explicit classifications

- **Rejected:** “Private” on the source event is sufficient to anonymize a linked Nextcloud resource booking. The issue record directly identifies the privacy gap; until verified in an exact release/configuration, do not rely on it. This rejects an implementation assumption, not the P2 requirement.
- **Optional enhancement:** neutral service keys, status/change trail, explicit resource-confirmation state, office-local outage architecture, timezone/DST checks, human-reviewed translation, and a scoped restore test strengthen the revealed plan without expanding the pilot into a public directory or complete funeral-home ERP.
- **Uncertain:** candidate-specific prices and total first-year costs; current Nextcloud Resource Management compatibility/support window beyond server 35; Passare role granularity, offline use, family edit modes, and export coverage; actual resource-event visibility in an installed Nextcloud pair; translation/accessibility conformance; local office network resilience; officiant scheduling representation; full export/restore fidelity. These require an exact version, vendor demonstration/quote, configuration, or pilot check.
- **Already covered:** all six plan clauses correspond to brief requirements or open decisions; no plan item is rejected as unnecessary. Specific proposed refinements above do not silently resolve the owner's stated choices.

## Validation plan — all proposed, none executed

1. **Exact versions and support:** identify candidate server/app versions from current supported-release information; install only a supported compatible pairing in a qualified test environment. Record build IDs, enabled apps, permissions, backup route, and configuration before evaluating behavior. The catalog's listed support-through-35 point needs current support-window verification.
2. **Sensitive-field access:** make synthetic records covering family contact, preferences, faith/cultural instructions, payment arrangements, and a neutral service identifier. Log in as each of the six staff identities mapped to owner-approved roles and a family test account. Inspect calendar titles/descriptions, resource calendars, tasks, notifications, search, mobile/DAV clients if in scope, export output, and browser/download paths. Pass only if each account sees exactly the fields allowed by its approved role. For Nextcloud, reproduce a private source event with room/vehicle resource and check the resource calendar; any protected detail exposure fails. Use no real family data until corrected and retested.
3. **Booking integrity and change:** two staff request overlapping times for one room and then one vehicle. Pass only if one confirmation wins and the second user sees a clear rejected/pending state with a responsible person to resolve it. Add staff/officiant availability, a changed service time after family arrival, and a change discussed from another time zone. Check intended local service time, timezone conversion, DST boundary, notifications, old-slot release, new-slot confirmation, and the visible handoff. Repeat with two disconnected clients; no custom offline hold counts as confirmed until authority resolves contention.
4. **WAN/local outage distinction:** disconnect only the WAN link while preserving the office LAN, then repeat the lookup, create/update, task handoff, and export flow. Restore connectivity and verify there is one authoritative version. Separately stop the local server or isolate the LAN/power and verify staff use a designated fallback without creating duplicate confirmations. Document remote-family limitations during outage.
5. **Independent export and restoration:** agree on scope and roles first. Export events, task owner/status/due date, minimal case link, and approved notes/files if required to an owner-controlled location outside the application. Inspect fields for completeness and leakage. Restore into a clean test account/system and compare record counts, times/timezones, task states, attachments/notes, and identifiers; record omissions. For Nextcloud's CLI import, explicitly choose strict validation/error flags rather than depending on command defaults. Pass only when the separate copy is usable without the source product and can be restored within the owner's acceptable time.
6. **Keyboard/discreet-use review:** the keyboard-first staff member completes search, book, update, conflict resolution, handoff, and export without mouse input. Record focus order, visible focus, keyboard traps, error/status comprehension, and any unavailable feature. Observe the daily view with real staff using synthetic entries: it should surface today's service and changes without public-directory search, high-volume event metrics, or unnecessarily loud/noisy notices. These are proposed user checks; no conformity claim is made.
7. **Language and family material:** ask which language(s) and which documents/messages need translation. Test accented/non-Latin names, date/time format, line wrapping, print/share output, and a human-reviewed translation of the selected service information. Distinguish translated UI from translated family material and from a translation of staff-only details.
8. **Written cost and access demonstration:** request vendor pricing for first-year setup, subscription, six staff, support/training, export, renewal, storage, and taxes. Ask each vendor to demonstrate the access matrix, family view/edit state, outage behavior, and exit export using the same synthetic scenario. Reject any proposal over $10,000 in first-year total unless the owner changes the ceiling.
