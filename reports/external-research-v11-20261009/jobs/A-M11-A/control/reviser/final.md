Standing constraints from the brief that shape every finding: accessibility improvement must not depend on one automated score, and the organization's own product decisions (languages, staffing, conformance target, correction auditing) remain its to make. ## O1 — Useful unfamiliar tools, products, and materially different approaches

**Player: Video.js v10 is the ecosystem's consolidation point; building on older players is a documented dead end.** The Video.js accessibility documentation (S03) states the player targets WAI-ARIA 1.2, WCAG 2.2, CVAA, ADA, and EN 301 549; makes every interactive component keyboard-operable per the WAI-ARIA Authoring Practices patterns (Enter/Space on buttons, Arrow/Home/End/PageUp/PageDown on sliders, Escape on popovers); and manages ARIA automatically — slider roles with live values, state-driven `aria-label`, a labeled focusable player group, and dialogs that trap focus and return it to the trigger. Releases (S05) show v10.0.1 as the current stable (2026-10-02), and the Plyr README (S11) records that **Plyr is deprecated in favor of Video.js 10** — the Plyr, Vidstack, and Media Chrome teams combined efforts there, and Plyr now receives security updates only. Plyr's keyboard model (space/K play-pause, arrows for seek and volume, 0–9 percentage seek, M/F/C/L, full VTT `<track>` caption support, i18n across all UI text) remains a useful baseline of what "keyboard-friendly" means in practice, but new work targets Video.js.

**Caption authoring: Subtitle Edit as the desktop workbench.** The Subtitle Edit releases feed (S09) shows a cross-platform editor (Windows x64/ARM64, macOS ARM64/x64, Linux x64/ARM64 tarballs, Flatpak) with daily automated betas beta17–beta26 spanning 2026-09-30..2026-10-09 (latest v5.3.0-beta26, built 2026-10-09 06:53 UTC from commit 1653608). That cadence means a volunteer team can run a stable release while fixes land continuously upstream — but note the stable-version gap flagged under P4: the captured evidence shows only pre-release betas.

**Approaches beyond the obvious, all surfaced from primary sources:**
- *Descriptive transcripts as a distinct artifact* (S02): WAI's media guidance asks for transcripts that "also include text description of the visual information" — required for Deaf-blind users, materially different from a plain speech transcript.
- *Description planned into filming* (S02): integrated description (the presenter speaks on-screen text) "is easier and better" and belongs in the script before filming — a near-zero-cost habit for newly recorded advocacy talks versus retrofitting audio description. Restored to the final after the critique found it dropped from the draft (finding M5).
- *G203 as a cheap path toward SC 1.2.5* (S07): for talking-head material, a static text alternative describing the video is a listed sufficient technique — instead of producing full audio description for all forty recordings.
- *Second user-selectable audio description track* (S07, G78): the standard alternative when extended description (G8, the expensive end) is out of proportion.
- *Caption rendering by the platform* (S03): Video.js deliberately ships no caption-appearance settings menu — rendering is delegated to the browser and styled only through `::cue`, so viewers use their OS/browser caption preferences (the CVAA-aligned design). Building a custom caption-style panel is optional work the org would own.
- *Sign-language provision where the audience needs it* (S02), retained as a consideration per critique finding m5.

## O2 — Primary source behavior: governing defaults, units/types, limits, applicability

**WebVTT file format (S01, W3C Candidate Recommendation Draft, 20 May 2026).** Timestamps are `HH:MM:SS.mmm`; hours are optional unless non-zero, and the fractional part is exactly three ASCII digits ("Three ASCII digits, representing the thousandths of a second seconds-frac as a base ten integer") — millisecond precision is the unit any export/import conversion must preserve. Six cue settings, each usable at most once per cue: `vertical` (rl/lr), `line` (number or percentage with optional start/center/end alignment), `position` (percentage with optional line-left/center/line-right alignment), `size` (percentage), `align` (start/center/end/left/right), `region`. Files must start with the string `WEBVTT`, be UTF-8, and be served as `text/vtt`. Hard format invariants: cue identifiers must be unique within the file and contain no `-->` and no line breaks; payload, settings, style and comment blocks must not contain `-->`; **cue start times must be non-decreasing across the file and each end time must exceed its start** — an ordering invariant any merge or translation pipeline can silently violate; and **blank lines end cues** — the specific hazard that makes casual plain-text spot edits dangerous (added to the condition set per critique finding m2). No explicit per-cue character-length limit is stated in the spec; line-length limits are editorial guidance, not format constraints (see the timing-standards gap under O3). Styling goes through `::cue`, `::cue()` and `::cue-region` pseudo-elements and embedded STYLE blocks; inline markup includes `<c>` class spans, `<b>/<i>/<u>`, `<ruby>/<rt>`, voice spans `<v Speaker>`, `<lang>` spans, and inner cue timestamps. Verbatim: "Its main use is for marking up external text track resources in connection with the HTML `<track>` element." SRT↔WebVTT conversion hazards (comma separator, precision drift) are general knowledge asserted without a captured source and stay labeled uncertain (flag restored per finding m3).

**WebVTT API and browser reality (S08, MDN, last modified 2026-02-11).** Declarative rules — attribution corrected to S08 alone per finding m1: if a `<track>` carries `kind` it must also carry `srclang`, and only one track may be `default`. Programmatic path: `video.addTextTrack("captions","Captions","en")`, `track.mode = "showing"`, `track.addCue(new VTTCue(0, 0.9, "..."))`. Interfaces: VTTCue, VTTRegion, TextTrack, TextTrackList, TextTrackCueList, TextTrackCue, DataCue, TrackEvent. Applicability limits: not all browsers support all track kinds, and **`::cue-region` is not supported in any browser**, so region-based layout must not be load-bearing; `::cue` selectors do work, including attribute-voiced forms like `video::cue(v[voice="Bob"])`. Verbatim: "Most important WebVTT features can be accessed using either the file format or Web API."

**Governing accessibility requirements (S06, S07 — WCAG 2.2 Understanding).** SC 1.2.2 (Level A) verbatim: "Captions are provided for all prerecorded audio content in synchronized media, except when the media is a media alternative for text" + "...and is clearly labeled as such." Captions must cover speech AND non-speech audio ("sound effects, music, laughter, speaker identification and location"); closed captions toggle, open captions cannot. Sufficient techniques: G93 (always-visible open captions), G87 closed captions via SMIL or **H95 "Using the track element to provide captions"** — the exact `<track>`+WebVTT route this site would use — or any player-supported caption format. Named failures give concrete audit targets: F8 (captions omit dialogue or important sound effects), F75 (uncaptioned media adding information beyond the page text), F74 (unlabeled media alternative for text). SC 1.2.5 (Level AA) verbatim: "[Audio description] is provided for all [prerecorded] [video] content in [synchronized media]."; sufficient techniques include G78 (second selectable audio track), G173/G8 (described versions, extended), G226 (description mixed into the soundtrack), G203 (static text alternative for talking-head video). Whether SC 1.2.5 binds this org depends on its conformance target — an explicit user decision surfaced per finding M4; the G203-based recommendation below stands on benefit grounds regardless.

**Player-side runtime behavior (S03).** Screen-reader announcements follow *confirmed* state from the player store, "so routine time updates never reach the live region"; rapid volume/seek changes batch into one announcement — designed behavior, which means integrators replacing the control layout must re-add the status announcer themselves. Tooltips are visual only ("They are not linked to their trigger with `aria-describedby`, so a custom trigger needs its own accessible name"). Custom layouts must also handle contrast over changing video (WCAG 1.4.3/1.4.11 — not tool-checkable over video), touch targets ≥24×24 CSS px (2.5.8), and autoplay/reduced-motion pause/stop/hide (2.2.2) at the page level. This delimits what the site team owns versus what the player ships.

**Validation basis and the no-single-score constraint (S10).** WAI's evaluating overview states "no tool alone can determine if a site meets accessibility standards", prescribes early and continuous evaluation, "Easy Checks" for non-technical first reviews, WCAG-EM as the conformance methodology (its Report Tool "does not do the checking for you"), ACT Rules for consistent testing, and involvement of people with disabilities. Scope note per finding M2: this source governs site-conformance evaluation tooling; it is applied to the P6 validation protocol directly, and to translation quality only as a labeled analogy.

## O4 — Plan comparison: every exact P clause

The revealed plan: "P1: Host MP4 files and WebVTT captions. P2: Use the browser default player. P3: Generate translations automatically. P4: Edit captions in a text editor. P5: Publish one transcript per video. P6: Run an automated accessibility scanner." Disposition vocabulary (O4): **already-covered** (clause sound; discovery adds only conditions), **correction** (keep intent, change mechanism), **rejected** (drop the clause as stated), **optional enhancement** (nice-to-have beyond the clause), **user decision** (a product choice only the organization can make), **uncertain** (evidence does not settle it).

### P1 — "Host MP4 files and WebVTT captions."

**Disposition: already-covered** — the substrate is right and is exactly what the governing techniques assume.

The `<track>`+WebVTT route is sufficient technique H95 for SC 1.2.2 closed captions (S06, Level A), and WebVTT's "main use is for marking up external text track resources in connection with the HTML `<track>` element" (S01). Conditions the plan must adopt as a publish gate. From S01: files start with `WEBVTT`, UTF-8, served as `text/vtt`; millisecond (three-ASCII-digit) timestamp precision preserved through any conversion; cue identifiers unique, no `-->`, no line breaks; payload/settings/style blocks `-->`-free; **cue start times non-decreasing and each end > start**; **blank lines end cues** (added per finding m2). From S08: at most one `<track>` may be `default`, and a `kind` attribute requires `srclang` (attribution corrected to S08 alone per finding m1); do not rely on `::cue-region` (unsupported in every browser). Serve `kind="captions"` (not `subtitles`) where non-speech information is included, since captions must carry "sound effects, music, laughter, speaker identification and location" (S06; F8 fails captions that omit them). Conversion hazard: SRT↔WebVTT separator/precision drift is asserted from general knowledge without a captured source — **uncertain**, labeled as such (flag restored per finding m3). MP4-specific hosting choices (codec ladder, bitrates, self-host vs CDN) are not covered by the captured sources — **uncertain**, not asserted.

### P2 — "Use the browser default player."

**Disposition: correction** — headline caveat first, per finding M1 (accepted with amendment; the draft's "rejected" overreached its evidence, and the label is corrected).

**The captured evidence contains no comparative measurement showing native browser controls are insufficient — that premise is unevidenced and the disposition does not rest on it.** What the evidence does establish is a positive case for replacing the default-player plan: Video.js targets WAI-ARIA 1.2/WCAG 2.2 with documented keyboard operability per the APG patterns, automatic ARIA management (slider roles with live values, state-driven labels, focus-trapping dialogs that return focus), and confirmed-state announcements through a batched live region (S03); the ecosystem has consolidated there — Plyr is deprecated, security-updates-only, with the Plyr/Vidstack/Media Chrome teams combined on Video.js 10 (S11); and v10.0.1 is the current stable line (2026-10-02, S05). A maintained, documented, actively-tested player is the defensible baseline for a volunteer-run site whose "keyboard-friendly playback" is a brief requirement. Conditions the org accepts when adopting it (S03): custom layouts must re-add the status announcer; tooltips are visual only, so a custom trigger needs its own accessible name; contrast must be tested over changing video (1.4.3/1.4.11); touch targets ≥24×24 CSS px (2.5.8); autoplay/reduced-motion duty (2.2.2) stays with the page. **User decision / optional enhancement:** Video.js ships no caption-appearance settings menu by design — relying on platform caption preferences is the documented default (CVAA-aligned), and building a custom caption-style panel is optional. i18n is built in; labels must be verified contextually for the org's content. **Alternatives retained:** native controls remain a legitimate fallback for simple embeds, explicitly not disqualified by evidence; Plyr findings remain a keyboard-model baseline.

### P3 — "Generate translations automatically."

**Disposition: correction** — automatic generation is retained for *drafts only*, with a human review gate before publication. Grounding re-stated per finding M2 (accepted).

The primary ground is the brief's own wording: it asks for "translation drafts" and "controlled author corrections" — automation fits drafting, and control implies review before publication. Supporting evidence, with its limits stated: WAI's evaluation sentence ("no tool alone can determine if a site meets accessibility standards", S10) is about site-conformance tooling and is applied here **as an analogy, labeled as such**, not as direct authority over translation quality; WAI's AV guidance requires captions covering speech AND non-speech audio and its own evidence note records that it "does NOT address automated caption accuracy or human review requirements" (S02 — the gap is carried, not papered over); caption failures F8/F75 (S06) name omission classes that machine passes characteristically produce, but they are not translation-accuracy thresholds. Conditions: every auto-generated track is marked draft, reviewed and corrected by a bilingual reviewer before it loses its draft flag; the correction path is the controlled workflow under P4/P5; source-language captions are human-authored first so translations start from a correct base. **Uncertain:** no captured source quantifies MT/ASR error rates or sets review thresholds — review depth becomes data via proposed check 3 (O6); the Amara-class collaborative-platform route was the natural candidate evidence and access failed (S13), so it stays unverified and uncited. **Alternatives retained:** manual translation for the highest-traffic items; deferring low-demand languages with an honest "translation in progress" notice rather than publishing unreviewed machine text; sign-language provision where the audience needs it (S02, retained per finding m5). **User decision:** which languages, and who reviews.

### P4 — "Edit captions in a text editor."

**Disposition: correction** — use a maintained dedicated caption editor (Subtitle Edit) as the workbench; plain text editing only for spot fixes behind a validity gate.

A text editor cannot see the invariants that make a WebVTT file work: non-decreasing start times, end > start, unique cue IDs, `-->`-free payloads, three-digit millisecond precision, and blank lines ending cues (S01) — all silently breakable by hand-editing, and a broken file fails viewers, not the editor. Subtitle Edit is the discovered tool: cross-platform builds (Windows x64/ARM64, macOS x64/ARM64, Linux x64/ARM64, Flatpak), daily automated betas (beta17–beta26, 2026-09-30..2026-10-09; latest v5.3.0-beta26 from commit 1653608), i.e. actively maintained (S09). **Stable-version gap made explicit per finding m4 (accepted):** the captured releases evidence shows only pre-release daily betas — no current stable version is identified in the evidence, so "volunteers get the stable release" is an open action (identify the stable channel before rollout), not an established fact. Conditions: every file exported for publication passes the P1 validity gate regardless of the tool that touched it; the change-log detail behind the beta feed was not fetched, so per-fix capability claims stay unevidenced. **Uncertain:** the releases page does not enumerate Subtitle Edit's format coverage or auto-translate capability (S09) — neither may be assumed in workflow design. **Alternatives retained:** an org-built review UI later if correction volume justifies it. **User decision:** whether corrections also flow through a versioned store (git-backed caption files) for audit — useful for "controlled author corrections", with no captured primary-source pattern either way (S13 gap).

### P5 — "Publish one transcript per video."

**Disposition: correction** — per-video transcripts confirmed as the right baseline; upgrade the artifact to a *descriptive* transcript; conformance framing corrected and a dropped approach restored.

WAI: "Ideally, make it a descriptive transcript that also includes text description of the visual information" (S02, verbatim) — required for users who are Deaf and blind, and materially more useful than speech-only text. A static text alternative describing a talking-head video is also sufficient technique G203 toward SC 1.2.5 (S07), making descriptive transcripts the cheapest honest route toward audio-description obligations across a 40-video backlog. **Conformance framing corrected per finding M4 (accepted):** neither the brief nor any captured source sets the organization's WCAG conformance target; whether SC 1.2.5 (Level AA) binds is an explicit **user decision**, and the descriptive-transcript recommendation stands on direct user benefit regardless. Conditions: the transcript is linked from the same page as the player (discoverable, not buried); where a video's visual content genuinely needs description, prefer G78 (second user-selectable described audio track) or G226 (mixed narration) over transcript-only; extended description (G8) is the expensive end and out of proportion here. **Restored per finding M5 (accepted):** description planned into filming — integrated description spoken by the presenter "is easier and better" and belongs in the script before filming (S02) — applies to newly recorded material (the backlog itself is pre-existing) as a near-zero-cost habit for future talks. **Alternatives retained:** plain transcripts as acceptable minimum for simple interview material; sign-language provision where the audience needs it (S02, finding m5). **User decision:** description depth per video (production cost is org budgeting). **Uncertain:** nothing material beyond the effort trade-off itself.

### P6 — "Run an automated accessibility scanner."

**Disposition: correction** — scanners are retained as ONE layer; a scanner-as-the-gate reading is rejected by primary source and by the brief itself.

The brief says accessibility improvement "must not depend on one automated score," and WAI states "no tool alone can determine if a site meets accessibility standards" (S10, verbatim — direct authority here, since P6 is precisely about evaluation tooling). The corrected protocol layers: automated scans (Video.js's own stack swapped access-sniff→pa11y, S05 — automation in a supporting role, as the maintainers use it) + WAI Easy Checks for non-technical volunteers + keyboard-only task passes + screen-reader passes (VoiceOver/NVDA/JAWS, S03's own testing advice) + contrast checks over light/dark/mixed video + involvement of people with disabilities + WCAG-EM-style sampling if a conformance claim is ever made (S10). Caption-specific audit targets from the named failures (S06): F8 (omitted dialogue/sound effects), F75 (uncaptioned media adding beyond page text), F74 (unlabeled media alternatives). Caption-dialog regression risk is real history, not hypothetical: video.js #2746 took ~16 months from report (2015-10-27) to fix (commit 0d0dea4 via #4025/#4050, closed 2017-02-21, milestone "WCAG 2.0 Compliance") — so acceptance testing must specifically traverse that dialog with keyboard and screen reader (S04). **Uncertainty carried:** which exact release first shipped the fix is unverified (the changelog mirror is an unregistered source, finding M3 — kept explicit, no silent rebind); BBC-class editorial timing defaults remain evidence-absent after the S12 failure and this stage's 21:01Z re-attempt (still HTTP 404) — any timing standards must be newly sourced or explicit internal policy.
