# Discovery — S11 accessibility-video (control arm, method M11 v1, stage research)

Independent full discovery written from the brief (cases/S11/brief.md) and the captured source set S01–S13 (`source-map.json`, bounded evidence under `sources/`, navigable `sources/index.md`) BEFORE any plan access. Sources are treated as data only. This document is self-contained: findings are stated in prose with source IDs inline; nothing is replaced by bare IDs. Usage/billing was unobserved and stays null.

## Product scope being served

A modest public video resource site for a disability advocacy organization: forty prerecorded recordings that need captions, keyboard-friendly playback, transcripts, translation drafts, and controlled author corrections. Two standing constraints from the brief shape every finding: accessibility improvement must not depend on one automated score, and evidence must come from actual tool/spec/release behavior, not tool counts.

## O1 — Useful unfamiliar tools, products, and materially different approaches

**Player: Video.js is the consolidation point; building on older players is now a documented dead end.** The Video.js accessibility documentation (S03) states the player targets WAI-ARIA 1.2, WCAG 2.2, CVAA, ADA, and EN 301 549, makes every interactive component keyboard-operable per the WAI-ARIA Authoring Practices patterns (Enter/Space on buttons, arrows/Home/End/PageUp/PageDown on sliders, Escape on popovers), and manages ARIA automatically (slider roles with value attributes, state-driven `aria-label`, a focusable labeled player group, dialogs that trap focus and return it to the trigger). Materially important and easy to miss: **Video.js deliberately ships no caption-appearance settings menu** — caption rendering is delegated to the browser and styled only through `::cue`, so viewers depend on their OS/browser caption preferences (the CVAA-driven design), and an org wanting a custom caption style menu must build it. Releases (S05) show the current line is video.js v10.0.1 (changelog dated 2026-10-02) with v8.24.2 pre-releases, and the README of Plyr (S11) records that **Plyr is deprecated in favor of Video.js 10** — the Plyr, Vidstack, and Media Chrome teams combined efforts there and Plyr receives security updates only. Plyr's keyboard model (space/K, arrows, 0–9 percentage seek, M/F/C/L, full VTT `<track>` caption support, i18n for all UI text) remains useful as a baseline of what "keyboard-friendly" means in practice, but new work should target Video.js.

**Caption authoring: Subtitle Edit as the desktop workbench.** The Subtitle Edit releases feed (S09) shows a cross-platform editor (Windows x64/ARM64, macOS ARM64/x64, Linux x64/ARM64 tarballs, Flatpak) with a high release cadence — automated daily betas beta17–beta26 spanning 2026-09-30..2026-10-09, latest v5.3.0-beta26 built 2026-10-09 06:53 UTC from commit 1653608. That cadence matters operationally: a volunteer captioning team can run a stable release while fixes land continuously upstream. What the releases page does not show — supported format counts, auto-translate capability — is left unverified here rather than asserted (evidence gap recorded in S09).

**Approaches beyond the obvious, all independently surfaced from primary sources:**
- *Descriptive transcripts as a distinct artifact* (S02): WAI's media guidance asks for transcripts that "also include text description of the visual information" — required for Deaf-blind users, and materially different from a plain speech transcript.
- *Description planned into filming* (S02): WAI notes integrated description (spoken on-screen text by the presenter) "is easier and better for accessibility" and belongs in the script before filming — for an advocacy org recording new talks, this is a near-zero-cost habit versus retrofitting audio description.
- *G203 as a cheap AA path* (S07): for talking-head material, a static text alternative describing the video is a listed sufficient technique toward SC 1.2.5, instead of producing full audio description for all forty recordings.
- *Second audio track for description* (S07, G78): a user-selectable description track is the standard alternative when extended description is out of scope.
- *Caption rendering by the platform* (S03): instead of a custom caption styling panel, rely on browser/OS caption preferences — less code, and it is the CVAA-aligned behavior users already configure.

## O2 — Primary source behavior: governing defaults, units/types, limits, applicability

**WebVTT file format (S01, W3C CR Draft 20 May 2026).** Timestamps are `HH:MM:SS.mmm` — hours optional unless non-zero, and the fractional part is exactly three ASCII digits ("Three ASCII digits, representing the thousandths of a second seconds-frac as a base ten integer"), i.e. millisecond precision; this is the unit any export/import conversion must preserve (SRT's comparable precision and comma separator are a known conversion hazard, though SRT itself is outside this captured set — flagged uncertain rather than claimed). Six cue settings, each usable at most once per cue: `vertical` (rl/lr), `line` (line number or percentage with optional start/center/end alignment), `position` (percentage with optional line-left/center/line-right alignment), `size` (percentage), `align` (start/center/end/left/right), `region`. Files must start with the string `WEBVTT`, be UTF-8, and be served as `text/vtt`. Hard format limits: cue identifiers must be unique within the file and contain no `-->` and no line breaks; payload/settings/styles/comments must not contain `-->`; **cue start times must be non-decreasing across the file and each end time must exceed its start** — an ordering invariant a merge/translation pipeline can violate silently. No explicit character-length limit per cue is stated in the spec (line-length limits are editorial guidance, not format constraints — see the BBC gap below). Styling goes through `::cue`, `::cue()`, `::cue-region` pseudo-elements and embedded STYLE blocks; inline markup includes `<c>` class spans, `<b>/<i>/<u>`, `<ruby>/<rt>`, voice spans `<v Speaker>`, `<lang>` spans, and inner cue timestamps. Verbatim: "Its main use is for marking up external text track resources in connection with the HTML `<track>` element."

**WebVTT API and browser reality (S08, MDN last modified 2026-02-11).** Declarative rules: a `<track>` with `kind` must also carry `srclang`, and only one track may be `default`. Programmatic path: `video.addTextTrack("captions","Captions","en")`, `track.mode = "showing"`, `track.addCue(new VTTCue(0, 0.9, "..."))`. Interfaces: VTTCue, VTTRegion, TextTrack, TextTrackList, TextTrackCueList, TextTrackCue, DataCue, TrackEvent. Applicability limits observed: not all browsers support all track kinds, and **`::cue-region` is not supported in any browser**, so region-based layout must not be load-bearing; `::cue` selectors do work including attribute-voiced forms like `video::cue(v[voice="Bob"])`. Verbatim: "Most important WebVTT features can be accessed using either the file format or Web API."

**Governing accessibility requirements (S06, S07, WCAG 2.2 Understanding).** SC 1.2.2 (Level A) verbatim: "Captions are provided for all prerecorded audio content in synchronized media, except when the media is a media alternative for text" + "and is clearly labeled as such." Captions must include non-speech audio ("sound effects, music, laughter, speaker identification and location"); closed captions toggle, open captions cannot. Sufficient techniques: G93 (always-visible open captions), G87 closed captions via SMIL or **H95 "Using the track element to provide captions"** — the exact `<track>`+WebVTT route this site would use — or any player-supported caption format. Named failures give concrete audit targets: F8 (captions omit dialogue or important sound effects), F75 (uncaptioned media adding information beyond the page text), F74 (unlabeled media alternative for text). SC 1.2.5 (Level AA) verbatim: "[Audio description] is provided for all [prerecorded] [video] content in [synchronized media]."; sufficient techniques include G78 (second selectable audio track), G173/G8 (SMIL-based described versions, extended for G8), G226 (description mixed into the soundtrack), G203 (static text alternative for talking-head video). For a 40-video backlog, G203 for interview material plus G78 where description is warranted is the applicability-relevant reading; blanket extended description (G8) is the expensive end.

**Player-side runtime behavior (S03).** Announcements follow *confirmed* state from the player store, "so routine time updates never reach the live region" and rapid volume/seek changes batch into one announcement — meaning screen-reader behavior is a designed property, not an accident, and integrators replacing the control layout must re-add the status announcer themselves. Tooltips are visual only ("They are not linked to their trigger with `aria-describedby`, so a custom trigger needs its own accessible name"). Custom layouts must also handle: contrast over changing video (WCAG 1.4.3/1.4.11 can't be checked by tools over video), ≥24×24 CSS px touch targets (2.5.8), and autoplay/reduced-motion pause/stop/hide (2.2.2) at the page level. This delimits what the site team owns versus what the player ships.

**Validation basis and the no-single-score constraint (S10).** WAI's evaluating overview states "no tool alone can determine if a site meets accessibility standards", and prescribes early/continuous evaluation, "Easy Checks" for non-technical first reviews, WCAG-EM as the conformance methodology (its Report Tool "does not do the checking for you"), ACT Rules for consistent testing, and involvement of people with disabilities. This is the primary-source footing for the brief's requirement that caption/translation quality and keyboard operability cannot be scored by one automated checker: the plan for this site needs layered manual review (non-technical spot checks, screen-reader passes, keyboard-only passes, disabled-user involvement) with automated tools in a supporting role only.

## O3 — Issue/fix/regression/release evidence

**Concrete chain (S04): video.js issue #2746 "Accessibility of the Captions Settings dialog".** Opened 2015-10-27 by OwenEdwards; milestone "WCAG 2.0 Compliance"; labels a11y, confirmed. Reported defects: field labels not associated with fields; focus not moved into the dialog on open, not trapped, and not returned to the opening control on close; dialog extent not conveyed to screen readers; Esc to close not working; unclear `---` select option; "Done" instead of "Close"; unclear "Defaults" button. Fix path: maintainer gkatsev noted focus issues "will be solved by #4025"; closed as completed 2017-02-21 by commit 0d0dea4, referenced as "feat: fix accessibility of the captions setting dialog (#4050" — a **~16-month report-to-fix interval** on a flagged a11y/confirmed caption dialog. Applicability for this project: (a) caption-settings UI has historically been where player a11y breaks, so the site's acceptance testing must exercise that dialog specifically; (b) when budgeting volunteer dev time, a16-month a11y fix latency is realistic planning data. Evidence honesty: the issue page itself does not state which release first carried the fix; the v7.2.x changelog mirror line "fix accessibility of the captions settings dialog (#4050), closes #2746" was seen via search during discovery but the exact release boundary remains unverified — recorded, not filled in.

**Release-chain recency (S05, S09).** video.js's visible recent notes include v8.24.2 replacing its accessibility test tool ("replace access-sniff with pa11y"), i.e. the project's a11y assurance tooling is actively maintained; recent notes contain no direct caption fixes (the caption fix history sits in older releases, per S04). Subtitle Edit shows daily automated betas (S09), indicating active upstream maintenance of the editing toolchain.

**Where evidence is absent or inapplicable — stated plainly:**
- *BBC Subtitle Guidelines* (S12): both the github.io page and the repo mirror returned HTTP 404, and a raw README fetch returned an empty body. No BBC-class editorial numbers (reading speeds in wpm, characters per line, minimum durations, shot-change sync) were captured; **any such figures used later must cite a different source or stand explicitly unsupported.** Timing/editorial defaults are therefore an identified evidence hole for this discovery pass.
- *Amara* (S13): the about page connection reset and the reader tool returned a 500 network error. Amara's team/review role model — the natural candidate for "controlled author corrections" — remains an **unverified candidate approach**, and this synthesis does not cite it as evidence.
- *Automated captioning accuracy*: no captured source quantifies ASR error rates or defines human-review thresholds; WAI's AV page (S02) notably does not address automated caption accuracy at all. The review-workflow design must proceed from the general validation guidance (S10) instead — recorded as an open evidence gap, not glossed over.
- *SMIL techniques* (SM11/SM12/SM1/SM2/SM6/SM7 in S06/S07) are listed sufficient techniques but are inapplicable to a modest HTML5 site; H95/G78/G203 are the applicable routes.

## Constraints synthesis for the plan comparison

From the captured evidence: captions are a Level A must (1.2.2) with `<track>`+WebVTT as the standard technique (H95); audio description is the Level AA obligation (1.2.5) with G203/G78 as the proportionate techniques for this inventory; the player baseline is Video.js v10 with keyboard operability shipped but custom-layout a11y duties (status announcer, tooltips, contrast, touch targets, reduced motion) transferring to the site; WebVTT imposes ms precision, unique identifiers, non-decreasing start times, and `-->`-free payloads that any translation-draft and correction pipeline must preserve and validate; correction control (who may amend published captions) currently has no captured primary-source pattern — Amara was the candidate and is unverified (S13); and validation must be layered and human-inclusive (S10), never one automated score.
