# S07 documentation-portal — research draft and plan comparison

**Stage:** ER11 A-M07-A/control, method M07, research. The independent discovery was frozen before reading the plan. The plan below was revealed by the prescribed script and is reproduced exactly for comparison.

**Original product constraints preserved:** Build an internal documentation portal for a 60-person engineering group with three codebases, multilingual notes, and frequent releases. Search must return the relevant released version, cite exact passages, and help maintainers see contradictions without silently rewriting documentation. Research existing products/mechanisms, code/doc linkage, retrieval conditions, and migration/export options. This is a small product brief, not a guarantee of unlimited production behavior.

**Research usage/billing observed:** `null` (no spend or usage meter was available or measured). The public GitBook translation page has a published price at retrieval, recorded as a feature fact in the source notes; no user-specific consumption or estimate was calculated.

## Revealed thin plan

- **P1:** “Crawl main branches nightly.”
- **P2:** “Put every chunk in one vector index.”
- **P3:** “Answer with the top five chunks and links.”
- **P4:** “Let maintainers approve suggested rewrites.”
- **P5:** “Keep old documentation pages separately.”
- **P6:** “Test by asking maintainers ten familiar questions.”

## Per-clause disposition

| Clause | Disposition | Decision and rationale |
|---|---|---|
| **P1 — Crawl main branches nightly.** | **Correction; retain main-branch preview as optional.** | A nightly crawl of main alone cannot satisfy released-version retrieval, because main may contain unreleased work and three codebases may release independently. Ingest on commit/build/release events, preserve immutable commit snapshots, and publish a release manifest that maps a product/component release to exact repo commits. Keep main as a separately labeled preview channel. A nightly reconciliation crawl can detect missed events, but must not be the source of release truth. Backstage separates per-repository generation/publication; Docusaurus's current docs are explicit that version snapshots are cut separately; Read the Docs maps versions to Git refs and defaults `latest` to the default branch ([S01](sources/evidence-notes.md#s01), [S06](sources/evidence-notes.md#s06), [S08](sources/evidence-notes.md#s08)). |
| **P2 — Put every chunk in one vector index.** | **Correction; retain one logical search surface, not an unscoped vector-only corpus.** | Use a passage registry/index with mandatory metadata filters for repo/codebase, release, source commit, language, source path, access scope, and snapshot state. A unified physical index is acceptable only if those filters are enforced before ranking and citation. Support lexical/exact-phrase and semantic retrieval as separate signals or modes; preserve original passage text and stable source identity. Do not collapse multiple releases/locales into semantically similar but unqualified chunks. Read the Docs demonstrates explicit project/version filters and also documents that one query cannot search multiple versions of the same project; GitBook documents release and language variants with locale search behavior that may exclude other language variants ([S10](sources/evidence-notes.md#s10), [S15](sources/evidence-notes.md#s15)). |
| **P3 — Answer with the top five chunks and links.** | **Correction; top five may be a display default after validation.** | Resolve release and locale first, then return source passages whose original text is exact and whose links include immutable repo revision, release, locale, page, and passage/heading anchor. Five is not a quality guarantee: show a configurable number of ranked results, with the exact passage and enough surrounding context to assess applicability. If generating a synthesis, cite each factual claim to the exact passage(s), distinguish disagreement and version conditions, and abstain or ask when evidence is missing or release context is ambiguous. Never cite an unqualified mutable main/latest URL. None of the reviewed product docs establishes this complete answer-level citation contract; Read the Docs exposes version-aware search filtering but not exact answer citations, and GitBook's result breadcrumbs identify site/variant/page group without replacing a pinned source citation ([S10](sources/evidence-notes.md#s10), [S15](sources/evidence-notes.md#s15)). |
| **P4 — Let maintainers approve suggested rewrites.** | **Optional enhancement with strict conditions; correct “rewrite” into an evidence-linked proposal.** | A maintainer-approved patch is compatible with the brief if the system only flags evidence and drafts a reviewable change request. Show the conflicting passages, release/language conditions, source owners, and a diff. Do not edit a source file during crawl, indexing, search, contradiction detection, or translation. Approval must be an explicit human action before a normal reviewed source change; a maintainer can also dismiss the finding, mark it superseded, or record that versions intentionally differ. Swimm's vendor-described small-change auto-sync is a reason to disable or gate automatic edits; GitBook auto-translation currently cannot be manually edited according to its docs, so it needs an explicit policy decision ([S14](sources/evidence-notes.md#s14), [S16](sources/evidence-notes.md#s16)). |
| **P5 — Keep old documentation pages separately.** | **Retain and strengthen; make archive discoverable and version-conditioned.** | Keep immutable snapshots for active/relevant releases, but include them in the same catalog and retrieval experience with clear “released,” “preview,” “retired,” and “superseded” labels. Bind each snapshot to exact commits and release metadata. Let users select/confirm the release; show old pages when requested, not as unmarked competitors to the current release. Define retention and redirect policy so old exact citations remain valid. Docusaurus stores copied versioned Markdown and warns about maintenance/build cost; Read the Docs can delete artifacts on deactivation and warns about active slug changes; TechDocs issue history shows demand for per-entity historical docs ([S01](sources/evidence-notes.md#s01), [S07](sources/evidence-notes.md#s07), [S08](sources/evidence-notes.md#s08)). |
| **P6 — Test by asking maintainers ten familiar questions.** | **Retain as a smoke-test seed; expand to a discriminating acceptance set.** | Ten familiar questions can reveal navigation gaps but are likely to favor known answers and do not prove version correctness, citation integrity, contradiction handling, permissions, or abstention. Build a labeled suite with expected release/commit, locale, exact supporting passage(s), answerability, and access scope. Include same-claim/same-release conflicts, intentionally different old-release instructions, missing translation, ambiguous cross-repo release, and no-answer cases. Track exact citation match, correct version/locale, retrieval recall/precision, false contradiction rate, and unauthorized disclosure. Have maintainers judge blinded result sets. This is proposed only; no such test was run. |

## Recommended shape and alternatives

**Preferred product-independent architecture:** Keep authoritative docs in the three code repositories where possible. Add a release catalog/manifest that maps user-facing release IDs to exact repository commits and approved doc snapshots. Generate an index from immutable source material, storing passages with repo, release, commit, language, path, heading/anchor, exact text, content digest, access scope, and build time. Filter by release and language before ranking. A portal shell can then organize codebase ownership; search and contradiction review share the same evidence IDs. Indexing is read-only. A correction is a Git/authoring change request with a diff.

**Conditional product choices:**

- **Backstage TechDocs shell plus a separate version-aware retrieval layer** fits an existing service catalog and gives a direct catalog-entity-to-repository-doc link. Its default configuration builds with MkDocs/Docker and local storage; the recommended CI/static route is better for shared use. The reviewed TechDocs docs/issue do not establish per-entity multi-release snapshots or exact cross-site passage citations, so add these explicitly rather than assume them ([S05](sources/evidence-notes.md#s05), [S06](sources/evidence-notes.md#s06), [S07](sources/evidence-notes.md#s07)).
- **Docusaurus** is a strong docs-as-code candidate if snapshot copies, locale trees, and static publication suit the writers. It makes current versus latest explicit and produces stable versioned files in Git. The team owns release cuts, cross-repo release mapping, localization sync, and the custom search/citation layer. Include issue #11112's narrow v3.7 numeric-version localized root-page regression in the release test suite; do not generalize it to current Docusaurus without reproduction ([S01](sources/evidence-notes.md#s01), [S02](sources/evidence-notes.md#s02), [S04](sources/evidence-notes.md#s04)).
- **Read the Docs** is a useful proof-of-concept when code tags/branches should become docs builds quickly and project/version query filters are sufficient. Explicitly set a shipped-release default, activate only versions to retain, and test multilingual project wiring. Its 100-project query ceiling is ample for three repositories, but its one-version-per-project-per-query limitation and project-per-language structure need to match the release model. The reviewed docs do not establish exact-passage citations ([S08](sources/evidence-notes.md#s08), [S09](sources/evidence-notes.md#s09), [S10](sources/evidence-notes.md#s10)).
- **GitBook** is a hosted mixed authoring/product option for central site structure over several repository folders/spaces, and its 2025 release notes describe simultaneous release and translation variants. Test search scope, branch syncing, data access, and plan availability. Keep AI import refinement disabled when preserving text; choose manual translations unless owners explicitly accept the current automatic translation workflow's restrictions. Confirm that published results and citations can point to the exact underlying commit and release needed ([S11](sources/evidence-notes.md#s11), [S12](sources/evidence-notes.md#s12), [S14](sources/evidence-notes.md#s14), [S15](sources/evidence-notes.md#s15), [S17](sources/evidence-notes.md#s17)).
- **Swimm** is best treated as an optional code-linked maintenance or onboarding supplement. Its described code anchors and PR drift check differ from a documentation portal. Verify ownership, auto-sync controls, locale/version behavior, and export before adopting; public material inspected did not settle those questions ([S16](sources/evidence-notes.md#s16)).

These are alternatives, not yet a single selection. Backstage is the strongest catalog surface if it already exists; Docusaurus/Read the Docs give Git-based release evidence; GitBook has the most directly described hosted variant navigation for language and release versions. A brief technical proof-of-concept should compare the actual three-codebase release map and exact citation behavior before choosing.

## Retained discoveries and unresolved conditions

1. **Version identity:** Decide whether the release authority is Git tags, deployment records, or an approved manifest. When three repos do not share version numbers, map a top-level release to a tuple of repo commits; otherwise require a codebase/version selection.
2. **Default scope:** Decide whether search defaults to last deployed, latest stable, or a user-selected release. Development docs may remain searchable only as a clearly labeled preview. Do not silently fall back from a missing requested version.
3. **Locale behavior:** Select language owners and decide whether translations are human-authored or automatically maintained. Define what happens when a locale is stale or lacks the requested release; label original-language fallback instead of presenting it as translated content.
4. **Cross-language search:** The current product examples differ: GitBook describes excluding other languages by default, while the brief simply says multilingual. Make the scope visible to the user and keep locale in result metadata.
5. **Contradiction definition:** A difference across release, product configuration, locale, date, or applicability may be valid. Define grouping/triage criteria and assign a content owner. No reviewed product source documents a ready-made non-writing contradiction workflow meeting the brief; this is a scoped research observation, not a claim that no such tool exists.
6. **Hosting and access:** Decide self-hosted versus hosted, repo provider, SSO/group mapping, private snippet visibility, data residency, audit requirements, retention, and budget. No provider account, plan configuration, private infrastructure, or private API was inspected.
7. **Migration and export:** Inventory formats and source history. Prefer Markdown/Git or another reversible source format; verify exact content, links, assets, redirects, anchors, code blocks, version IDs, and locale mapping before publication. Use Git Sync for bulk Markdown where relevant; ordinary UI import has much lower per-operation limits and may alter content. Swimm export remains uncertain.
8. **Citation stability:** Define whether passage anchors use line ranges, heading IDs, or content-span IDs. Store a content hash and exact source revision so a changed page cannot silently move a citation to different text.
