# S07 documentation-portal — independent discovery

**Research stage:** ER11 A-M07-A/control, method M07, evidence-on-demand. This discovery was completed from the full brief and independently selected public primary sources before the case plan was revealed. It does not incorporate a hidden plan, parent/counterpart work, evaluator material, or campaign history.

## Brief obligations and interpretation

The product is an internal documentation portal for 60 engineers across three codebases, with multilingual notes and frequent releases. Search must find the relevant *released* version, cite exact passages, and help maintainers see contradictions without silently rewriting source documentation. The brief also requires exploration of code/doc linkage, retrieval conditions, and migration/export.

The consequential design question is the identity and lifecycle of a “released version.” A codebase may have independent tags/releases; a deployed product may comprise mutually compatible releases across several repositories. A portal cannot infer which record is right from “latest” alone. Search needs a release context and exact source identity, and any system that generates or updates text needs an explicit human-controlled path.

## Product and mechanism discoveries

### 1. Backstage TechDocs: catalog-linked docs-as-code portal

TechDocs ties Markdown documentation to a Backstage catalog entity using the `backstage.io/techdocs-ref` annotation. A component/service can therefore surface its documentation from the engineering catalog; the usual input is a `docs/` tree, `mkdocs.yml`, and `docs/index.md`. It can also host standalone documentation entities. Source preparation, MkDocs generation, and publishing are separable steps. These are useful building blocks for connecting the three codebases to service ownership and catalog context ([S05](sources/evidence-notes.md#s05), [official setup guide](https://backstage.io/docs/features/techdocs/creating-and-publishing/)).

The documented initial defaults are server-side build (`builder: local`), Docker-based MkDocs (`generator.runIn: docker`), and local filesystem publishing (`publisher.type: local`). Backstage recommends CI generation and storage-backed static artifacts for the recommended setup; `builder: external` serves published artifacts read-only ([S06](sources/evidence-notes.md#s06), [official getting-started guide](https://backstage.io/docs/features/techdocs/getting-started/)). Treat the local defaults as quickstart defaults rather than a retention/scale recommendation. TechDocs is strong for catalog linkage and generated browsing; its current docs do not establish multi-repository semantic search with passage citations or a released-history selector.

A specific issue requested storing multiple TechDocs versions per entity so users could read the docs for the component release they run. It was opened June 2022 and was closed “not planned”; the proposal's storage layout is only an issue author's suggestion, not shipped behavior ([S07](sources/evidence-notes.md#s07), [issue #12259](https://github.com/backstage/backstage/issues/12259)). This is a reason to add a separately version-aware renderer/index or use another versioned site generator if TechDocs is the portal shell. Current-page and issue evidence should be rechecked before implementation because the issue is historical.

### 2. Docusaurus: repository-native version snapshots and locale trees

Docusaurus v3.10.2 distinguishes the current docs directory from the navigation's latest version. By default `docs/` is current/“next”, while a preserved version can be the latest released route. `docs:version <name>` copies all current docs into a versioned directory, captures a sidebar, and updates `versions.json`; the `lastVersion`, `includeCurrentVersion`, `onlyIncludeVersions`, labels, routes, and version banners control what readers see ([S01](sources/evidence-notes.md#s01), [versioning docs](https://docusaurus.io/docs/versioning)). This gives explicit snapshots, but a release pipeline or maintainer must deliberately cut and publish the docs snapshot. The tool documentation warns that copies increase build and maintenance complexity, suggests keeping relatively few active versions (rule of thumb under ten), and notes that patch-only releases often do not justify another duplicate docs copy.

The same v3.10.2 documentation places each locale under `i18n/<locale>/<plugin>/...`; translated Markdown/MDX remains a whole document, with JSON for UI labels and localized data files for some plugins. Locale declaration and translation/deploy workflow are explicit; automatic locale detection is a stated non-goal ([S02](sources/evidence-notes.md#s02), [i18n docs](https://docusaurus.io/docs/i18n/introduction)). This is a concrete static docs-as-code path when version snapshots and language trees fit the writers' workflow. It does not provide the cross-codebase release identity or exact-passage citation layer by itself.

**Evolution and regression evidence:** Docusaurus issue #2651 (2020) recorded the v2 i18n design work and earlier problems including combined versioning/translation build cost and localization defects; the current v3.10.2 docs show a mature filesystem workflow ([S03](sources/evidence-notes.md#s03)). However, issue #11112 reports a narrowly scoped static-build 404 for the German translation of a versioned numeric-version root `index.mdx` in Docusaurus 3.7.0. The issue was still open, marked external, and showed no linked fix when inspected. The reporter said some nearby routes worked under the development server and that adding another doc or changing the version slug changed the result ([S04](sources/evidence-notes.md#s04)). This is not evidence of a current v3.10.2 defect, and no fix was verified; it is a high-value regression case if this approach is selected.

### 3. Read the Docs: Git-ref builds with version-aware search filters

Read the Docs creates version records from repository branches/tags. Its defaults are meaningful but not equivalent to “released”: `latest` tracks the repository default branch, and if SemVer-like refs are present, `stable` tracks the greatest stable SemVer release; tags take priority over branches. Git integration builds versions on pushes. Refs are initially inactive; activating builds them, while deactivating deletes their artifacts. Root URL defaults to `latest` unless changed to another version such as `stable` ([S08](sources/evidence-notes.md#s08), [versions docs](https://docs.readthedocs.com/platform/stable/versions.html)). For a portal whose default must mean a shipped release, the rule must explicitly point to a promoted stable/deployment identity, not silently inherit the development branch. The documented deletion and rename behaviors also mean version activation, link stability, and retention require policy.

Localization is project-based: each language has a project, and translation projects are associated with a parent; URLs carry language and version, such as `/en/stable/` and `/es/stable/` ([S09](sources/evidence-notes.md#s09), [localization docs](https://docs.readthedocs.com/platform/latest/localization.html)). This can represent the three repositories and their languages, although coordinating release identities across repositories remains application policy.

Server-side search accepts project/version filters and can include subprojects. It omits versions the reader cannot access or that do not exist, supports up to 100 projects per search, and falls back to a child project's default version when the requested version is absent. It does **not** support searching multiple versions of the same project in a single query; the last version parameter wins ([S10](sources/evidence-notes.md#s10), [search syntax](https://docs.readthedocs.com/platform/latest/server-side-search/syntax.html)). For three codebases, search can be constrained by project and a release context; it still does not provide an answer-level immutable exact-passage citation protocol in the reviewed docs. Treat that as a separate layer or acceptance test.

### 4. GitBook: hosted authoring with Git sync and site variants

GitBook provides a mixed authoring approach: docs spaces can be edited in its visual editor and connected to GitHub or GitLab. A single published site can map multiple spaces/folders from repositories to sections, with initial sync either repository-to-GitBook or GitBook-to-repository. The same structure can contain language variants; current docs say each localized version is a dedicated space with a language selector ([S11](sources/evidence-notes.md#s11), [S13](sources/evidence-notes.md#s13)). A 2026 publishing guide describes public/private sites, content spaces, site structure, and audience controls ([S17](sources/evidence-notes.md#s17)). This is a different choice from purely static generation: hosted authoring and site management can be convenient, but repository permissions, data boundaries, plan features, and sync behavior must be validated against the actual environment.

GitBook's 2025 product history says its sites support language variants and release-version variants at the same time, with separate version and language selectors. Search results can include section/variant/page-group breadcrumbs, capped at three visible breadcrumbs. Its documented default search scope emphasizes the current variant plus default variants from other sections; search can be broadened, while language variants are excluded from search scope to avoid cross-language result noise ([S15](sources/evidence-notes.md#s15), [2025 updates](https://gitbook.com/docs/changelog/2025-product-updates)). These details matter for the “relevant version” requirement: a user should understand which repo, release, and locale a result belongs to, and the team must define whether search stays in the selected language or intentionally searches all languages.

Git Sync supports repository-backed bulk migration; the importer docs report a 20-page/20-file cap for individual UI imports and up to 5,000 Markdown pages for Git Sync. The product warns that format conversion may change content and states that AI refinement during importer workflows can be disabled ([S12](sources/evidence-notes.md#s12)). Use a diff and preservation check before publishing any converted notes. GitBook's automatic translation workflow can process changed pages and sync results, but its docs say translations currently cannot be edited, it is a paid feature, and changing its glossary triggers a full retranslation. The captured docs also call out stable slugs as a manual setting ([S14](sources/evidence-notes.md#s14)). Those behaviors conflict with a strict human-authored/no-silent-rewrite policy unless the team explicitly opts into automatic translation; manual language spaces are a separate option.

**Evolution and regression evidence:** the 2025 changelog both adds combined language/release variants and records a fix for published content failing to update after translations were generated. That history is directly relevant to testing that source edits, translation runs, and publication converge to the intended language/version ([S15](sources/evidence-notes.md#s15)). It documents a historical fix, not a guarantee that every sync path is correct today.

### 5. Swimm: code-coupled documentation maintenance

Swimm describes IDE links from files/functions/code blocks to related docs and a GitHub check on each pull request. The check compares docs with code changes and classifies them as current, slightly out of sync, or outdated. The vendor says small edits may be auto-applied, while substantial updates need manual approval/modification ([S16](sources/evidence-notes.md#s16), [Swimm integration article](https://swimm.io/blog/swimm-native-integrations)). This is a materially different way to maintain knowledge close to code, particularly onboarding material and code explanations, and could supplement a portal. The automatic-update path needs review before use under this brief. The inspected primary material does not establish release-specific portal retrieval, exact citations, translation, or bulk export; those are unverified capabilities, not assumed absences.

## Cross-product implications for a coherent design

A portal shell and a retrieval system are separable. A catalog shell can organize ownership and codebase entities, while a release-aware index stores and searches immutable source snapshots. Static generators can render the docs, but they do not determine cross-repository release compatibility or exact citation identity. Hosted products may combine spaces and variants, but their own search scope/defaults must be validated rather than assumed to match the organization's release semantics.

A robust minimal source record for each indexed passage should include:

- codebase/repository and immutable commit SHA;
- release identifier and the evidence that makes it released (tag, deployed-build manifest, or approved release record);
- documentation path, source format, section/heading, and a stable locator;
- source language and, where relevant, translated-from document/revision and translation freshness;
- exact passage text or span, line/character offsets, and a content digest;
- access-control scope and index build timestamp.

The released-version catalog should map product/component releases to one or more repository commits. For independently deployed codebases, avoid inventing a single shared version. A query should first use an explicit selected release/product context or ask a disambiguating question; then filter by the resolved repo commit/version and language before ranking. When a matching released snapshot is unavailable, say so and present the nearest eligible release only as a labeled alternative. Do not silently fall through to a development branch or latest translation.

For exact citations, return a link into the immutable snapshot plus the exact passage as rendered/queried. A mutable `latest` URL or generated heading anchor alone is not enough: headings can change, locales can produce different anchors, and build output can differ. Keep source revision and locale attached to the citation. Preserve the original-language passage if showing a translation, and label the translation revision/freshness instead of presenting translated text as the source quote.

Contradiction detection should produce a reviewable evidence pair, not edit the underlying docs. Candidate pairs should be grouped by same topic/entity and compared only after scoping language, codebase, release, date, and applicability conditions. Different release behavior may be intentional rather than contradictory. Show each passage, its source identity, version and conditions; give maintainers actions such as confirm compatible differences, mark superseded, or open a proposed correction. Any source change should remain a human-reviewed Git/authoring change with its own diff and release effect. None of the reviewed products documents a built-in contradiction workflow matching all these constraints; this is an inferred product need, not an exhaustive market-absence claim.

## Conditions and user decisions still needed

The brief leaves several real product choices open. They should be decided once, rather than encoded as accidental defaults:

1. What constitutes “released”: a Git tag, a deployment manifest, an approved release record, or a per-repository rule? How are cross-repo release combinations represented?
2. What is the default result context: a selected product/component release, last deployed release, or newest stable release? What is the clearly labeled development/preview view?
3. Which locales exist, who owns translations, and may translation automation create or refresh text? What is an acceptable stale-translation behavior?
4. Is search confined to the chosen language, or may it search other languages with clear result labels?
5. Which docs need to be code-linked, and do writers want IDE surfaces, a catalog portal, a visual editor, or a combination?
6. What retention and archive policy preserves old released docs and URLs, and how should retired versions appear?
7. What repository, SSO/access-control, hosting/data-residency, audit, and budget constraints apply? The research did not inspect private provider internals, accounts, plans, or tenant configuration.
8. What counts as a contradiction, who triages it, and what review evidence is required before correcting either document?

## Migration/export implications

Prefer to preserve the authoritative source repository and full Git history, even if generated HTML or a hosted site is added. Docusaurus's versioned files are Markdown in the project tree; TechDocs publishes derived static output from Markdown; Read the Docs builds from version control refs; GitBook can round-trip through Git Sync. These each offer a source-preserving path if the organization adopts repository-backed authoring. For non-Markdown legacy content, first inventory format, heading/anchor behavior, assets, code blocks, redirects, authorship, locale, version, and source access; convert to a staging branch and compare before publication. GitBook's ordinary importer is explicitly limited and may change formatting; its larger Git Sync path is preferable for Markdown volume ([S12](sources/evidence-notes.md#s12)). Swimm export/migration behavior was not established by the inspected source.

## Proposed validation, not executed

No implementation, runtime, fixture, benchmark, account, or vendor environment was available in this research scope, and no code or product tests were run. The following are proposals only:

1. **Version-resolution fixture:** create three repositories with independently numbered releases, including a coordinated product release manifest and a deliberately mismatched repo tag. Confirm that queries resolve only the manifest's commits and never substitute the development branch. Test when a component has two simultaneously deployed releases.
2. **Locale fixture:** publish one English and one translated procedure across two releases, plus a missing/stale translation. Verify selected-language filtering, fallback labeling, stable links, and no mixing of a translated page from a different release.
3. **Citation integrity:** query a known distinctive sentence; confirm every answer citation resolves to the immutable repo/commit/version/locale and that cited text exactly matches the stored passage. Change a heading, move a file, and update the page; old citations should remain resolvable or report retirement explicitly.
4. **Contradiction review:** place a deliberately conflicting instruction in same-release docs and a differing-but-correct instruction in an older release. Confirm the first produces a review item with both exact sources, while the second is marked as version-conditioned rather than a contradiction. Verify that indexing and detection never write source files.
5. **Access isolation:** create public and restricted docs and search as users with different permissions. Verify that result metadata, snippets, citations, and contradiction pairs do not disclose inaccessible text.
6. **Build/migration check:** migrate a representative corpus containing images, nested headings, code examples, redirects, and two locales. Compare text, structure, links, search indexing, version routing, and original hashes. Test the actual monthly release volume and retention count rather than extrapolating from product defaults.
7. **Product proof-of-concept:** if evaluating Docusaurus, include the S04 numeric version + localized root-page static build regression. If evaluating GitBook, verify release/language variant scope, Git sync direction/conflict handling, fixed slugs, importer behavior with AI disabled, and the documented translation update path. If evaluating TechDocs or Read the Docs, check historical version retention and the selected repo/release semantics against the issues and limits documented above.

These checks are intentionally discriminating. None has been executed in this research stage.

It does not establish vendor pricing beyond the captured translation pricing page, self-hosted/private deployment feasibility, security posture, service-level guarantees, benchmark performance, full multilingual quality, model quality, or export guarantees. Those require current vendor confirmation or a bounded prototype.
