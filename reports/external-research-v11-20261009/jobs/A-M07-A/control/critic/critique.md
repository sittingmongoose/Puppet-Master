## Overall assessment

The draft is a strong, self-contained response to the brief. Its main correction is sound: a mutable main branch, an unqualified vector corpus, a fixed result count, and a rewrite action without an explicit review path do not by themselves establish released-version correctness, citation fidelity, contradiction handling, or preservation. It keeps product choice open, gives materially different approaches, preserves unresolved release/locale/hosting policies, and labels validation as proposed rather than executed.

I found no basis to reverse the draft’s six dispositions. I recommend four material refinements: make the P1 correction about *release identity and immutable capture*, not the nightly cadence; put Read the Docs’ child-project default-version fallback into the candidate’s stated limitations; make GitBook’s search breadcrumbs omit translation variants explicit; and age-limit Swimm’s 2022 beta-era claims and GitBook importer facts whose current pages could not be re-opened. Other proposed design details are reasonable recommendations, but they should remain clearly identified as product-independent design choices rather than vendor-established behavior.

## Material findings and recommended edits

### M1 — P1 should correct the target, not require an event pipeline

“Nightly” is not inherently wrong. A nightly job can fetch a release manifest or promoted immutable tags and index those snapshots; an event-driven pipeline can also miss events or race a release. The actual failure mode is treating the moving main branch as an authoritative released snapshot without a rule that proves which commit shipped. Revise the lead sentence to: **“A nightly crawl of mutable main alone cannot guarantee released-version retrieval; capture immutable promoted refs and map each supported product/component release to the exact repository commits. Trigger or poll ingestion as operationally appropriate, with reconciliation.”** If this case’s main is protected and itself represents a release, document that condition rather than assuming development-branch semantics. This preserves the plan’s cadence as an option.

### M2 — Carry Read the Docs’ version fallback into the comparison

The captured S10 notes and fresh official search-syntax page state that subprojects:project/version uses a child project’s default version when that child lacks the requested version; the query also cannot search multiple versions of one project at once. The draft’s Read the Docs candidate paragraph mentions the latter limitation but omits the former, despite separately warning against silent fallback. That is consequential: a cross-codebase release query could return a child’s default docs that do not match the intended product release. Add an explicit fail-closed test or post-filter requiring a per-repository resolved commit/version; if the child lacks that version, return “unavailable” or a labeled alternative, never imply that its default is the requested release [S10].

### M3 — GitBook breadcrumbs under-identify locale

The fresh 2025 changelog says breadcrumbs top out at three items and intentionally omit translation variants. The draft’s P3 comparison says breadcrumbs identify site/variant/page group; that is incomplete for a multilingual portal. State that the product hides translation-variant breadcrumbs, so locale must be shown in the selected context/result metadata or an independently pinned source citation. This strengthens the existing citation-stability requirement and is especially relevant if the portal uses GitBook variants [S15].

### M4 — Keep weakly revalidated vendor claims provisional

The prior arm captured GitBook importer limits and AI-refinement behavior (S12), but my direct re-open returned an internal error; the variant guide (S13) also returned an internal error. A later direct attempt to inspect the changelog’s search-scope section timed out. I verified other GitBook pages, including Git Sync, translations, publishing, and the changelog’s combined version/language variants, but the failed requests do not refresh the inaccessible sections. The draft discloses an earlier S12 timeout; append these critic recheck outcomes in the source map and leave importer counts/AI defaults and detailed search-scope rules as dated captured evidence requiring vendor confirmation before migration or selection. Do not silently substitute a nearby URL [S12, S13, S15].

Swimm’s cited vendor article is dated June 28, 2022 and describes the service as “currently in beta” at publication. The draft does qualify the capabilities as vendor-described and asks for verification, so this is not a reason to remove the alternative. Add the date/beta caveat and avoid implying a current capability from this post alone [S16].

## Minor findings

1. **Separate requirement from implementation choice.** Exact source identity, release scoping, and not silently rewriting are requirements/inferences from the brief. A manifest schema, content hash, hybrid retrieval, pre-ranking filter placement, and a specific event pipeline are recommended designs. Label those as proposed architecture, not requirements established by the product sources.
2. **Clarify “separately” for archives.** The user’s P5 may mean separate content snapshots, separate navigation, or a different storage tier. Draft’s shared catalog with explicit release scope is a good option, but note that the physical archive and whether old material is indexed by default remain policy choices.
3. **Turn metrics into gates.** The proposed suite names appropriate metrics, but no acceptance thresholds or adjudication rule is stated. Define them with maintainers before a POC and include a negative criterion for citations that resolve but quote a different revision/span.
4. **Keep source freshness visible.** Backstage/Read the Docs pages are rolling, and the vendor sources differ in date/version. The research draft generally records that uncertainty well. Any final shortlist should re-check product version, plan entitlement, access/privacy behavior, and importer/export behavior on the actual tenant.
5. **Do not overread absence.** Statements that no reviewed product documents the complete exact-citation or contradiction workflow are properly scoped observations, not market-wide claims. Keep that scope label where the architecture summary repeats them.
