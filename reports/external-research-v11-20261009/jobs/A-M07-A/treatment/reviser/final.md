# Final research review — documentation portal for three engineering codebases

**Stage:** ER11 A-M07-A / treatment / reviser; method M07 evidence-on-demand.  
**Status:** Complete revised research recommendation, 2026-10-09. This is a product and validation proposal, not an implementation, benchmark, security assessment, or claim that proposed checks ran. The original case brief, frozen discovery, full research draft, revealed P1–P6 plan, complete critique, and both predecessor source registers were reviewed. This file preserves the material research and resolves each criticism in the context of the brief. Independent primary-source checks are indexed in [sources/index.md](sources/index.md); the complete access ledger is [source-map.json](source-map.json).

## Recommendation

Keep authored documentation in Git and build a release-aware portal from immutable, pinned source refs. Each released record should identify its codebase, repository and path, resolved full commit, repository release, any product-release tuple, locale, stable heading anchor, exact passage text and a digest. If several repositories make up one product release, require an explicit compatibility manifest mapping that release to each repository commit. Independent tags must not be combined under an invented shared release name.

Antora remains the strongest first pilot when content should remain distributed among the three repositories and the existing docs fit its component/module structure. Its component/version and origin model suits assembly from pinned repositories. Docusaurus is a meaningful alternative alongside Antora: one site can host separate docs plugin instances with independent version lifecycles, one per codebase if useful. A build would still need to stage or fetch each repository at a pinned ref and supply the release manifest; Docusaurus multi-instance does not itself coordinate Git sources or a cross-repository product release. Test build size and locale/version routing; the Docusaurus guide recommends distinct sites if each docs instance is very large. Use a central Docusaurus docs tree instead if that is already the natural authoring model. Backstage TechDocs is most attractive if the group already operates Backstage or needs its catalog and owner navigation; its reviewed docs do not establish the release-aware search, exact passage citation, or contradiction workflow required here.

For an internal-only corpus, compare a controlled Typesense 30.1 deployment with lexical search and optional vector or hybrid retrieval. Evaluate hosted DocSearch only after the company explicitly accepts sending internal docs to that service and checks access, residency, retention, deletion and procurement terms. Neither search product replaces release identity. One physical collection can be an implementation choice only if it enforces release, locale, publication-state, codebase and user-authorization filters before ranking and before revealing snippets, links or citations. Preserve source text and hashes outside embeddings. The research does not establish which search method is more relevant, private, fast or inexpensive on this team's data.

Begin with ranked passage cards that show exact excerpts and commit-pinned links. Do not generate answer prose by default until scoped retrieval and citation checks pass. If answer synthesis is later wanted, require every factual claim to cite a returned passage from the selected release and language, verify displayed quotations against stored text/digests, and return an explicit no-evidence result when the scope has no support. A contradiction feature should surface candidate pairs for human review, show both passages and their scope, and keep any suggested resolution separate from source content.

Treat source authorization as a release-blocking design decision. The brief identifies an internal group but does not say all 60 people may read every repository or note. Before a pilot, map source ACLs to user/group identity and decide whether permissions differ by repository, release, locale or document. Apply access checks before retrieval and again when a passage, citation target or generated answer is delivered. Snippets, facets/counts, caches, exports and contradiction queues must follow the same rules; revocation and deletion must propagate. This is a required design and validation question, not evidence that any named product is insecure.

## Exact P-clause dispositions

The exact revealed plan is: **P1: “Crawl main branches nightly.” P2: “Put every chunk in one vector index.” P3: “Answer with the top five chunks and links.” P4: “Let maintainers approve suggested rewrites.” P5: “Keep old documentation pages separately.” P6: “Test by asking maintainers ten familiar questions.”**

| Clause | Disposition | Final finding |
|---|---|---|
| **P1 — “Crawl main branches nightly.”** | **Narrowed correction; cadence is an operational choice.** | A mutable branch name is not a released-version identity. A nightly crawl is reasonable for a clearly labeled preview if it records the exact resolved commit and unreleased state. A scheduled job can also reconcile release snapshots. Whether release snapshots build on release events or a schedule is not established by this brief; either way, resolve immutable refs and publish a complete manifest atomically. A nightly main crawl cannot silently answer a released query. Keep a preview only as a separate, visibly unreleased scope. |
| **P2 — “Put every chunk in one vector index.”** | **Correction upheld; vector and collection choice remain uncertain.** | One physical collection is possible only if every passage keeps codebase, release tuple, full commit, locale, publication state, path, anchor and authorization context, and exact filters constrain retrieval before ranking. Chunks from unpinned branches, unauthorized repositories or drafts must not mix into a released result. Keep literal source text and digests outside or alongside embeddings. Compare lexical, vector and hybrid retrieval on one reviewed gold set; one index versus separate collections is an implementation decision. |
| **P3 — “Answer with the top five chunks and links.”** | **Correction upheld; a top-five display may remain optional.** | A fixed count and links do not prove that a result belongs to the selected release, language or exact source bytes. Return passage cards with the exact excerpt, source path, heading, codebase, release tuple, locale, commit and authorization-safe link. Show enough evidence to expose both sides of a possible conflict. Apply release, locale and permission filters before ranking. Never silently fall back to main or another locale. A top-five UI can be retained if scoped-recall and citation tests support it; synthesis is optional and must pass citation gates. |
| **P4 — “Let maintainers approve suggested rewrites.”** | **Human review is already covered; amend the write boundary.** | Approval is compatible with the brief’s ban on silent rewriting, but approval alone is not contradiction triage. First present both exact passages with version, language, ownership and scope; the maintainer classifies a real conflict versus version/context difference. A rewrite is optional. Before any content change, require explicit, attributable authorization over a proposed diff and record approver, time, source revisions, reason and audit/rollback information. The agreed write path may be a repository change or controlled application writeback; the brief does not decide which. Reject unattended, ambiguous or unaudited mutation, not every post-approval automated application of an explicitly authorized change. |
| **P5 — “Keep old documentation pages separately.”** | **Historical retention is already covered; correct the identity requirement.** | Retaining old pages supports retrieval for a released version, but folder or URL separation alone is insufficient. Preserve the immutable source ref/commit and exact snapshot or verifiable content digest; keep repository release and product-release tuple distinct. A version route, immutable archived build or content-addressed snapshot can serve this purpose; duplicate folders are not required. How long to retain records and whether every patch release needs its own copy are user decisions. |
| **P6 — “Test by asking maintainers ten familiar questions.”** | **Correction upheld; retain ten prompts as an optional smoke test.** | Familiar prompts can test basic usability but do not discriminate wrong-release leakage, missing translations, stale citations, unsupported answers or contradiction handling. Keep them if useful, and add a reviewed multilingual gold set with exact quote targets, release/locale negative cases, missing/unreleased content, source drift, code links, conflicting and scope-different statements, and no-evidence cases. Add positive/negative authorization cases for each permission class. Set relevance, citation, privacy and release-isolation thresholds before running the evaluation. |

### Disposition categories

- **Corrections:** released answers need immutable source identity and a complete release manifest; indexing needs exact release/locale/publication and authorization filters; links and a fixed top-five limit do not establish exact evidence; historical records need stable identity; evaluation needs discriminating positive and negative cases.
- **Already covered by the brief:** maintainer review before any silent rewrite is prevented; keeping historical pages acknowledges the need for past-version retrieval.
- **Optional enhancements:** commit-pinned nightly previews or scheduled reconciliation; vector/hybrid search after comparison; natural-language answers after citation gates; suggestion and resolution workflows; immutable static archives; the original ten questions as smoke coverage; a tunable top-five presentation.
- **User decisions:** whether releases are coordinated and who owns the manifest; source repository versus central docs authoring; default release and locale behavior; permission groups and identity source; hosted indexing approval; retention and patch-release granularity; contradiction owners and acceptance states; whether approved writeback is a PR or controlled application action; whether answer synthesis is wanted; evaluation thresholds.
- **Rejected:** silent or ambiguous source edits, hiding or replacing cited content automatically, using an embedding as the only record of truth, treating query text or an implicit “latest” alias as a release pin, and silently substituting another branch or language. Vector search itself, hosted search itself and explicitly authorized writeback are not rejected categorically.
- **Uncertain:** best generator/search fit for the existing repositories; whether the three projects share a release cadence; corpus relevance and multilingual ranking; useful contradiction candidate precision and reviewer effort; hosting/privacy terms, latency, cost, retention, and actual permission boundaries. No target corpus or runtime settles these.

## Release, content and citation design

### Source set and release identity

For every publication, resolve each selected tag or ref to a full commit and emit a deterministic manifest with repository URL, codebase ID, release label, commit, docs content root and locale roots. If the user selects a product release spanning repositories, resolve it through a human-owned compatibility record containing all component commits. Do not infer coordination from similar tag names or simultaneous release dates.

Use a release-triggered build or a scheduled build that reads the same immutable refs; require complete-manifest validation before publishing. A missing tag, unreadable source, unsupported format or missing locale must fail or produce an explicit partial state, never substitute current main. If a separate nightly preview is useful, pin the commit observed for that preview and label it unreleased, with its own filter scope.

Antora’s implicit latest is also unsuitable as a product-release selector. It sorts named versions before semantic versions (named versions in reverse alphabetical order and semantic versions in descending order), then selects the first sorted version that is not a prerelease. If all versions are prereleases, it selects the first prerelease; an unversioned component is always latest or latest prerelease. When a cross-component resource reference lacks a version coordinate, Antora uses latest to resolve it. Use explicit component refs or the compatibility manifest for query and citation identity. Antora’s origin ref hash is SHA-1 (and can be the marker “(worktree)” for local content); it identifies a source ref, not an exact passage digest. Retain a separate content digest.

### Passage records

Store one record per stable heading or bounded paragraph/list passage, along with full source snapshots or enough source material to rebuild the index. A record should include:

| Field | Purpose |
|---|---|
| document_id, passage_id | Stable document and passage identity; include the source revision plus a stable anchor or digest. |
| codebase_id, repo_url, path, content_root | Ownership and source navigation. |
| product_release, repo_release, full_commit_sha | Keep coordinated product release distinct from independent repository tags. |
| locale, source_locale, translation_of, translation_source_digest | State language and translation relationship/freshness. |
| heading_path, explicit_heading_id, start/end offsets | Passage navigation and deterministic extraction. |
| exact_text, document_sha256, passage_sha256 | Exact quotation and drift validation under a stated canonicalization rule. |
| publication_state, published_at, retired_at, supersedes | Release eligibility and history. |
| access_policy_id or equivalent authorization metadata | Resolve who may retrieve or view the passage; derive this from authoritative source ACLs rather than a guessed group. |
| page_url, source_permalink, code_permalink | User navigation and code linkage at immutable refs. |

A label such as “current”, “latest” or “3.2” is presentation metadata, not a substitute for the source commit or release key. If an anchor or excerpt changes, create a new passage revision. Do not rebind an old citation ID to new text. Mark a changed source stale and retain the released snapshot according to the agreed retention policy.

### Retrieval, snippets and answers

The query context should state codebase or product, selected product-release tuple (or explicit component releases), locale and whether a preview is allowed. Authenticate the user, apply release/locale/status and access filters before ranking, and recheck authorization at every content-bearing response boundary. Make the active scope visible. If a release, translation or permission is missing, explain that rather than returning another one without consent.

DocSearch can copy docsearch:language and docsearch:version metadata to each extracted record. Its version facets accept SemVer or alphanumeric tokens case-insensitively; callers must configure the fields for faceting. The documented frontend supports up to five facet controls, and heading IDs are used for anchor links. The crawler record schema version and frontend package version are separate. These are retrieval affordances, not proof that a caller applies the correct release or permission filters. Hosted indexing would expose internal text to a third party; entitlement, contractual terms, residency, access control, deletion and cost were not checked.

Typesense 30.1 requires q and query_by; query_by fields must be string or string-array schema fields. filter_by can restrict fields, and := performs full-value string equality while : is word-level partial matching. The API docs describe one-based pages, per_page default 10 and maximum 250, prefix matching defaulting on, and numerical and alphanumerical typo tolerance defaulting on. Facet strategy defaults to automatic and max_facet_values defaults to 10. Use exact filters over canonical release, locale, status and access fields; query text containing a version number is not a pin. Also test filter escaping and actual schema behavior. These API behaviors do not prove relevance, permission safety or performance for this corpus.

Display exact stored text, heading, source commit, codebase, release, locale and an authorization-safe permalink. If an answer model is later added, it may use only authorized passages returned under the selected scope; cite every factual claim and verify quotations against the stored text/digest. If there is no adequate evidence, say so. If candidate passages disagree, display both only to users authorized for both; otherwise do not leak the inaccessible passage through a title, snippet, count or generated summary.

### Code and owner links

Link documentation to code at the same pinned source revision, using explicit repository/path and an optional symbol or line anchor. Display the code release separately if it differs from the docs release. Store structured link metadata instead of extracting arbitrary URLs from passage text. Antora origin attributes expose repository/ref/path and edit information; Backstage can bind docs to catalog entities and owners. The reviewed Docusaurus evidence does not establish a built-in cross-repository code ownership map, so use a source manifest or an existing catalog integration if needed. Do not infer an old release’s owner or implementation from a current branch.

### Contradiction review and approved changes

No reviewed product source establishes native semantic contradiction detection. Treat a detector as a candidate generator, not an authority. It may find passages sharing an API/config/topic identifier but asserting incompatible defaults, units, limits or procedures. Show both exact passages with codebase, product/repository release, locale, environment, feature flag and effective date. Let owners classify a pair as confirmed conflict, version/context difference, accepted divergence, false alarm or resolved by source change. Record the decision, reviewer, time, reason and source revisions.

A different default across releases may be correct. A translation that lags its source may be stale without being a contradiction. Candidate generation could use explicit structured rules, lexical overlap or an optional model suggestion; label its basis and measure missed conflicts and false alarms. Do not promise exhaustive detection.

A proposed rewrite remains separate from source text. Before an update, show a diff and require an authorized maintainer’s explicit approval tied to the passages and revisions. Preserve before/after provenance, audit, and rollback. A normal repository patch is one valid path; controlled application writeback can also be considered if owners authorize and audit it. No edit, replacement, suppression or canonicalization is silent.

## Product and search alternatives

| Option | Choose when | Evidence and limits |
|---|---|---|
| **Antora + Typesense or DocSearch adapter** | Keep docs in the three codebases and compose pinned component versions into a site. | Strong distributed component/version and source-origin mapping. Named versions sort before semantic versions; implicit latest has all-prerelease, unversioned and unresolved-cross-reference edge cases. A shared Antora component version still needs compatible release mapping. Duplicate resource IDs fail; duplicated optional descriptor settings can be unpredictable. Validate formats, locale conventions and explicit ref selection. |
| **Docusaurus multi-instance + search adapter** | One static site is useful, while each codebase needs its own docs set and version lifecycle. | Docusaurus 3.10.2 documents distinct plugin instances, separate versioned-doc paths and per-instance version commands. CI must stage/pin the source repositories and create the compatibility manifest; plugin instances do not provide cross-repository release coordination or the required search/citation/access behavior. Measure total rebuild cost; separate sites may fit very large docs sets better. |
| **Docusaurus consolidated docs tree + search adapter** | Central Markdown authoring and one site are already preferred. | Version routes and locale builds are supported. “Current” and “latest” are separate concepts but may be aligned by configuration for a maintained release. The version CLI copies files into editable/removable folders; it is not an immutable archive guarantee. Use explicit heading IDs for translated docs. Avoid needless patch snapshots; the guide recommends keeping the actively built set small. |
| **Backstage TechDocs + added release-aware index** | Backstage already exists and catalog ownership/navigation is valuable. | Docs associate with catalog entities, and CI can generate static output and publish it to object storage. A generated etag is a change-detection value, not an exact passage hash or release identity. Release routing, access filtering, search and contradiction review remain to be designed and checked. A symlink escaping the docs source tree is rejected. |
| **Hosted DocSearch** | Managed crawling is valuable and policy expressly permits hosted indexing of internal text. | Per-record locale/version metadata, facets and heading anchors are documented. Terms, eligibility, privacy, residency, authorization, deletion and cost were not inspected. |
| **Self-hosted Typesense** | Keeping the index inside the organization is a priority and an operator is available. | Exact filters, facets and string search are documented. The 30.1 API defaults require care with technical identifiers and version-like tokens. This research does not measure multilingual relevance, operations, throughput, latency or resource cost. |

No product is selected by the brief alone. Confirm current formats, actual source topology, Backstage availability, release mapping, user ACLs, locale set, source ownership and hosting policy before migration.

## Migration and export

Keep authored Markdown or AsciiDoc plus the pinned release manifest as the authoritative, vendor-neutral source. Normalize passage records in an interchange format so another search backend can rebuild from the same refs and source snapshots. A migration should compare page inventory, locale/version routes, anchors, passage IDs, exact text, hashes, authorization metadata and links. Docusaurus can build static routes, Antora can aggregate source roots, and TechDocs documents generating and publishing static site files; none of the reviewed sources establish one-click migration between these products or native search-index export/import. Treat interchange and rebuild as an application contract to validate, not an existing product guarantee.

The change copies that sidecar when present, warns and skips when absent, and adds a CLI test. The author reports a localized-site dogfood check. The author-reported check is not independent evidence; the chain does not show what this group runs, prove translation completeness, or rule out other regressions. ## Decisions needed before implementation

1. **Release model:** Are the codebases independently released? What record maps a product release to all source commits, and who owns it?
2. **Authoring/source location:** Keep notes in each codebase, use a central docs repository or support both? Which formats and release tags exist?
3. **Preview and default release:** Is current branch content useful in a separate preview? Should released search require a selected product release or clearly expose latest-per-component?
4. **Locale:** Which locale is the default? Should a missing translation return no result, offer a labeled source-language fallback or ask for explicit scope expansion?
5. **Authorization:** What identity provider and source ACLs govern each codebase and note? Do permissions differ by user/group, release or locale? Who approves access and revocation policy?
6. **Search and hosting:** May internal docs go to a hosted crawler/index? What data residency, deletion, SSO/access, procurement or budget requirements apply?
7. **History:** How long are records searchable and citable? Can old releases move to immutable static archives? Does every patch release require a snapshot?
8. **Conflict and writeback governance:** Who owns cross-code pairs? Who may accept divergence or approve a rewrite? Is the approved path a repository change or audited application writeback, and what audit/rollback is required?
9. **Answer interface:** Are exact passage cards enough initially, or is generated prose wanted after evidence checks?
10. **Evaluation:** Who reviews gold queries and authorizes relevance, citation, privacy, release-isolation and latency thresholds?

## Proposed validations — none executed

No application runtime, target corpus, source ACL matrix or implementation was available. These are proposed checks, not results:

1. **Authorization and release isolation first.** For each permission role, test that only allowed repo/release/locale passages are returned and that snippets, facet values/counts, links, generated answers, exports and contradiction candidates reveal no unauthorized content. Revoke a user/group and remove a source record; verify all indexes, caches and exports stop returning it. Use three pinned commits, a product-release tuple, a newer main commit, a prerelease and a missing/mismatched ref. Fail closed or label an explicit partial state.
2. **Locale and citation fidelity.** Include current, stale, missing and untranslated pages. Test no silent locale fallback. Under one documented extraction/canonicalization rule, compare displayed quotes to source bytes; verify explicit anchors, commit-pinned links and digests. Mutate a source and ensure an old citation becomes stale rather than rebinding.
3. **Docusaurus versioning and instance behavior.** If selected, test both aligned and split current/latest configuration, a released frozen ref, current preview, three plugin instances with independent lifecycles, and expected locale/version routes. Test per-instance content roots and build size. Reproduce PR 10875’s existing and absent localized current.json cases on the exact package version; separately compare translation/page inventory and freshness.
4. **Antora selection and source mapping.** If selected, test named, semantic, prerelease and unversioned component values, including the all-prerelease case. Verify how unresolved cross-component references use latest; assert that search and citations use the explicitly selected ref/compatibility tuple rather than that implicit alias. Test distributed roots with duplicate IDs and optional descriptor keys.
5. **Retrieval and presentation.** On a reviewed multilingual technical set, include API identifiers, config keys, numeric defaults, exact spans, no-evidence questions and release/locale negatives. Compare lexical, vector and hybrid retrieval on the same data; predeclare recall, ranking, citation and leakage thresholds. Check Typesense’s actual schema, exact filter escaping, prefix/typo behavior and authorization boundary. Treat top-five as an interface choice and verify it does not hide needed evidence.
6. **Contradiction and approval.** Compare one same-scope incompatible pair with a version difference, environment difference and stale translation. Check both authorized passages and the candidate’s reason. Assert no source change before explicit approval, then test the selected approved write path, approver attribution, before/after provenance, audit and rollback.
7. **Export and rebuild.** Recreate the normalized passage set in another backend or static export and compare IDs, source bytes, hashes, release/locale labels, access metadata and links. This is a proposed vendor-neutral interchange contract, not a claimed native export/import feature.
