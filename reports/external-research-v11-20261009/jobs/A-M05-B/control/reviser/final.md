**Case:** S11 · **Block/arm:** A-M05-B / control · **Method:** M05 · **Stage:** reviser

## Recommendation

First establish an organization-controlled source and publication workflow. Assign each recording a stable asset ID; retain the authorized media, approved source-language captions and readable transcript, each reviewed language version, provenance, and prior published revisions. Publish WebVTT for web timed text. Keep automatic speech/translation output and requested author corrections in clearly marked unpublished drafts until a qualified human review and an authorized publication approval. Select the player and editing path after a representative pilot.

Able Player is a specialist public-player candidate because its project documentation describes keyboard and screen-reader controls, caption preferences, interactive transcripts, and a Video Transcript Sorter for reviewing/synchronizing timed text. Its tagged v5.0.0 release is the latest stable release shown in the release listing I checked; v5.1.0-beta2 is a newer pre-release. Evaluate the beta only as a pre-release, and do not infer from its release listing that PR #778 is included. Serve local WebVTT files if choosing Able Player, because its documentation describes reduced transcript/search/customization features with captions hosted only by a video platform. Test the exact deployed bundle in the selected user matrix; documentation and a feature list do not establish site accessibility. [S05, S06, R04]

For caption editing, consider Subtitle Edit v5.2.0 on a managed workstation when creating captions or making substantial timing changes; confirm that the chosen OS/build includes the needed functions. For wording corrections to already synchronized VTT, a text editor may be the more direct workflow. Compare both on representative material. Subtitle Edit documentation describes waveform/spectrogram timing, synchronization and format conversion, plus local and remote speech-to-text choices; choosing the editor alone does not ensure that recordings stay local. [S09, S10]

Keep materially different paths open: native HTML video/track plus a site transcript has a small player dependency surface but leaves transcript, navigation and workflow work to the site; Amara may suit asynchronous multilingual collaboration if its service terms, roles, retention and export fit; YouTube Studio may suit an organization already using YouTube but should not become the sole durable caption/transcript master without an explicit platform-dependence decision. These are candidates from public documentation, not installed or tested tools. Keep approved media and text portable and independently recoverable whichever runtime is selected. [S03–S05, S11, S12]

## Product, format and workflow plan

### Per-recording source of truth

Keep one stable ID for each recording and one manifest record for each media/text asset and language. Include the media URL/version or content hash; title and duration/timebase; source language and locale; track kind; file path/URL; status and revision; author, reviewer and approver; editor or engine used; source hash; review/approval date; rights/consent status and limits; known uncertainty; and publication URL. Preserve the source-language caption and transcript status, translation reviewer state, and the per-recording visual-information decision. Keep approved files exportable and portable. Retain prior published versions and the decision/provenance for corrections.

Do not conflate caption tracks with readable transcripts. For HTML, use the captions kind for source-language captions that include dialogue and meaningful non-speech audio; use subtitles for dialogue-only or translated text as appropriate. Set an accurate srclang and UI label. Choose at most one default among captions/subtitle tracks per media element and document that choice. Keep draft translations outside public track selectors. WebVTT times are playback offsets with millisecond components, not implicit video-frame numbers. Cue start times are nondecreasing; each cue ends after its own start; distinct cues may overlap. Permit valid overlap for simultaneous speakers/sounds and flag questionable cases for human review rather than banning overlap in a linter. Check against media duration and render in the selected player/browser. [S02–S04]

HTML defines a descriptions track kind for text descriptions intended for audio synthesis. That semantic model does not prove support in the target player/user-agent/assistive-technology stack. Treat it as one integration candidate and verify discoverability, activation, language, timing, and the perceived output end to end. Keep user-selectable audio-described media or an alternate described version in consideration when the text-track path is not supported or usable. Do not publish a description draft as though its markup alone resolved visual access. [R02, R03]

A natural-language transcript may be structured HTML with headings, speaker turns and timed seek links. Keep it synchronized with caption revisions. If an interactive transcript combines captions, chapters, translations or descriptions, test focus and reading order; small differences in cue times can reorder a heading and caption. [S05]

### Human-controlled production and correction gates

1. **Rights and intake.** Before upload, processing or publication, identify rights in video, audio, music, performances and underlying text; verify permission for public playback, captions, transcripts, translation, storage, contractors/tool processing and future corrections. Check participant releases, privacy and consent limits. Record expiration and permitted uses. The cited U.S. statute is only an example of a jurisdiction-specific issue; the organization’s jurisdiction and exceptions are unknown. [S15]
2. **Source-language draft.** A human may transcribe directly or use permitted ASR to produce an explicitly labelled draft. Do not label raw ASR “captions complete.” Include intelligible speech, speaker identification where needed and meaningful sound/music; match language and locale to the recording. [S02, S09, S14]
3. **Content and timing review.** An editor compares the full audio/video, corrects wording and aligns cues. Waveforms and spectrograms can help locate likely boundaries, but listening establishes the words and meaning. A second reviewer should check high-impact content such as names, numbers, advocacy terminology, quotations, speakers and sound cues. Use a style guide and treat character-per-second or line-length figures only as warning flags adopted after language and audience review, not as universal acceptance limits. [S09, S14]
4. **Translation and approval.** Create a separate track from the approved source; preserve meaning, relevant sound/speaker information and locale conventions. Require a fluent reviewer and escalation path for disputed terms; record the reviewer and approved version/date. Before using Amara or an online ASR/translation endpoint, decide access, terms, retention/deletion, export and permission to process the media. [S09–S11, S15]
5. **Publication and correction.** Publish approved files only. Provide a correction-request route; check the request against the recording and authorized text; edit a draft; review and approve; publish a new revision; retain the prior revision and decision. Confirm that updates and withdrawals reach every track, embed, search result and export. Do not silently overwrite public files. Direct external edits require a separate decision about accounts, roles, access and contributor rights.

Forty recordings alone does not establish workload or deadline. Pilot clips across duration, language and content types and estimate review time before committing a budget or release date. Public documentation does not settle actual native-control behavior, Able Player compatibility with this site’s media/CSP/layout, beta2’s inclusion of PR #778, Subtitle Edit feature parity or data-routing for the selected build, Amara service-tier rights/retention, source/contributor clearances, or what spoken and visual information each recording contains. Preserve these as questions; do not infer answers.

## Discriminating validation proposals — not executed

1. **Player comparison.** Take a representative clip with captions, a translation, a transcript, a chapter and a no-caption/no-source edge case. Compare native controls plus transcript with the exact tagged Able Player build in selected browsers, mobile/zoom conditions, keyboard and screen-reader combinations. Use production-built assets. Record focus sequence, accessible names, caption/language selection, transcript/seek tasks, fullscreen/resizing, error recovery and task failures. Include the description delivery path and confirm users can discover, activate and perceive it; test the audio-described fallback if the text-track path is unusable.
2. **Player regression fence.** Pin the candidate release and dependency lock. Test local media; YouTube/Vimeo only if selected; absent media sources; captions without transcript; documented constructor forms that the site uses; and no-caption fallbacks. Build and inspect the actual released artifact, not only demos or checked-in bundles. Issue #775 motivates this proposal because its reporter distinguishes fresh develop output from stale committed build output; this review did not reproduce the issue. Check whether the exact candidate tag contains PR #778 before making a release claim. [S06–S08, R04, R05]
3. **Caption content and reading quality.** Sample short, long, multiple-speaker, noisy/music and visually information-heavy recordings. A reviewer watches/listens to each complete sample for exact words, speaker identification, meaningful sounds, timing, readability, placement, names/terminology and transcript correspondence. Obtain intended-user feedback and use it to set house style. Review every recording before first public release.
4. **WebVTT and packaging.** Parse every track; assert encoding/header, cue syntax, nondecreasing start times, each end after its start, end within media duration, correct language/label/kind, usable asset URL/MIME/CORS and one intentional default. Permit valid overlaps but review suspicious ones. Render tracks in each selected player/browser. For SRT/TTML exchange, compare representative content and cues before/after rather than treating a successful export as proof of fidelity.
5. **Translation quality.** For every offered language, have a fluent reviewer compare target text with the approved source, including names, advocacy terms, punctuation, speaker/sound context, timing and line segmentation. Block publication until reviewer identity and the approved version are recorded.
6. **Visual access and conformance choice.** Review each complete video for important visual-only information, on-screen text and action. Record whether existing audio already conveys the important information; at an SC 1.2.3 Level A target, decide whether audio description or a qualifying full time-based media alternative is provided. At a WCAG 2.2 AA target, where important visual information is not already conveyed in audio, provide audio description; do not treat an ordinary readable transcript or a Level A media alternative alone as the AA audio-description result. Test description delivery in the selected player/browser/assistive-technology matrix and verify transcript ordering. [R01, R02]
7. **Correction and rights rehearsal.** Exercise a correction from request through triage, draft, review, approval, new-version publication, rollback/withdrawal and update propagation to search/index/embed/export. Separately confirm each asset and language derivative can be created, stored, sent to the chosen tool and published under recorded permissions.

None of these proposals was run. No automated scanner or score is a substitute for accurate content, usable controls, human review, selected-user feedback and rights/status checks.
