# Discovery — accessibility-video

**Stage:** independent discovery, frozen before case-plan reveal  
**Research date:** 2026-10-09 UTC  
**Brief:** [S11 brief](../../../../cases/S11/brief.md)  
**Evidence index:** [sources/index.md](sources/index.md) · [source-map.json](source-map.json)

## Scope and decision posture

The brief describes forty existing recordings for a modest public disability-advocacy site. It asks for captions, keyboard-friendly playback, transcripts, translation drafts, and controlled author corrections. It does not specify the hosting stack, audience jurisdictions, languages, video ownership/licensing, storage/CDN, budget, authoring staff, required conformance level, or whether a hosted-media platform is already in use. Recommendations below therefore define a practical pilot and expose the decisions that still belong to the organization; they do not promise production compliance or settle rights.

## Discovery findings

### A. A web-first player and two alternate delivery architectures

**Able Player** is a useful specialist candidate for the web site. Its current documentation describes keyboard-operable and screen-reader-labelled controls, adjustable playback, user caption preferences, WebVTT tracks, and interactive transcripts assembled from captions, chapters, and descriptions. Its Video Transcript Sorter (VTS) can inspect and adjust timed text from multiple sources together, which directly fits the brief's caption/transcript/description synchronization problem. This is more than a generic playback skin: it brings an authoring aid and user-facing accessibility features. The constraints matter: it accepts valid WebVTT for its caption tracks; tracks hosted only at YouTube/Vimeo lose Able Player's transcript generation/search and some appearance controls; locally served tracks preserve those features. Treat current docs as a capability claim to verify in the actual target browsers and assistive technologies, not as a test result for this site. [S05, S06]

Pin a released build while evaluating it. Able Player v5.0.0 is the release shown as latest in the official release page at the research date (tag `v5.0.0`, short commit `8d235f9`, released 2026-06-21). In contrast, issue #775 documents multiple failures introduced on `develop` after 5.0.0; the reporter says a freshly built development version broke YouTube embeds and 17 of 60 project demo pages, while the checked-in distribution bundle masked those regressions. The maintainer merged PR #778, commit `cd617fc`, into `develop` on 2026-09-13 and closed the issue. This is a useful regression/fix chain and a warning to test the built artifact, not just a demo or checked-in bundle. It does not establish that the fixes have shipped in a tagged release or that the same defect affects local-file playback. [S06, S07, S08]

Two materially different player approaches remain viable:

1. **Native HTML video plus `<track>` and a purpose-built transcript view.** This has the smallest player dependency surface and uses the platform text-track model. The site still owns cross-browser control behavior, transcript navigation, preference UI, error/fallback states, and its accessibility testing. It is a good option if the organization can build and maintain those pieces, or if a small pilot confirms native controls meet its audience needs. [S03, S04]
2. **Hosted embed plus provider caption editor.** YouTube Studio, for example, permits editing caption text and timestamps, duplicating an auto-caption track for correction, publishing the edited track, and downloading/re-uploading files. This lowers media operations if the organization already uses YouTube, but embeds make the platform a runtime dependency. If using Able Player around YouTube/Vimeo, keep local WebVTT copies: the player's documentation says provider-hosted captions alone disable parts of the interactive transcript, search, and caption customization. Recheck the actual platform account, embedding, consent, and export workflow before selecting it. [S05, S12]

The source brief says “public video resource site,” not “YouTube channel.” Do not make a hosted platform, its player behavior, or its caption store the only durable copy without an explicit organization decision. A platform can be a delivery option while the site keeps its canonical video/caption/transcript assets and publishes approved tracks to the embed as needed.

### B. Editing, alignment, translation, and correction workflows

**Subtitle Edit 5** is a practical desktop/editor candidate for the forty-file production workflow. Its official documentation describes a subtitle grid, video preview, waveform and spectrogram timing, whole-file and point/visual synchronization, correction/conversion across many formats, and local speech-to-text engine choices. Its waveform display can make timing review more efficient, but visual amplitude is only a cue; it does not determine correct words, speaker attribution, or the semantic importance of a sound. The speech-to-text menu supports both local and remote engines, so “using Subtitle Edit” alone does not promise that media stays on the workstation. Configure and test an explicitly local engine if confidentiality or data residency is a requirement; otherwise document the endpoint/vendor and permission before sending source recordings. [S09]

Version matters: v5.2.0 is a released stable build dated 2026-09-10; the public repository was also publishing 5.3 beta builds during this research. Subtitle Edit 5 was a major Avalonia/cross-platform rewrite from its former Windows Forms line, and its official v5.0 release notes say not every specialized v4 feature had returned. Select a version/channel intentionally, pilot the precise workflows, and keep the editor's editable masters plus exported web deliverables under controlled versioning. Do not cite rolling `main` docs as proof a feature exists in every build. [S10]

**Amara's collaborative web editor** is a materially different route if multiple reviewers/translators work asynchronously. Its help describes side-by-side creation/editing of languages, team-based transcription/translation requests, upload/export flows, and language-labelled tracks. This may help distribute translation drafts and review work without installing a desktop editor. It introduces an external account, platform, retention/terms, access control, export, and source-media handling decision; inspect the exact service tier and permissions before using recordings. The documented upload path can replace a language track and, on some team configurations, uploaded files are marked complete. Thus a “draft” state and approval boundary need to be enforced deliberately rather than inferred from upload. [S11]

**YouTube Studio** is an alternate workflow when media already lives there: editors can change text/timestamps, duplicate and edit automatic captions, then publish; a track can be downloaded, edited elsewhere, and uploaded again. It is a simple path for a platform-owned catalog, but it is not the best sole master for an independent resource site if you need portable correction history, local track control, or an accessible transcript assembled outside the platform. [S12]

A low-risk production path for a small catalog is: inventory one representative clip; generate a machine transcript only as an explicitly labelled draft if desired and rights/data policy permits; have a fluent human correct the words, speaker turns, sound cues, language, and timing while listening to the recording; have a second reviewer approve/publish; retain the master text, timed WebVTT, review record, and prior published revision. Add more languages only after the source-language pipeline and publishing state are reliable. An automatic score, model transcript, waveform, or syntax validator cannot stand in for content review with affected users.

### C. Caption, subtitle, transcript, and description semantics

For normal HTML web delivery, make **WebVTT (`.vtt`) the published timed-text format**. The HTML `track` model distinguishes `kind="captions"` from `kind="subtitles"`; captions represent speech plus the non-speech audio needed to understand the recording, while subtitles may be dialogue-only or translated text. Give each track a language via `srclang` and a meaningful UI `label`; match the actual language/locale to the content. The HTML Standard permits at most one default among caption/subtitle tracks for a media element, so choose it intentionally rather than marking every language default. A translated track is not source-language captions; do not present an unreviewed machine translation as approved. [S02, S03]

WebVTT cues carry start/end offsets; the start of each cue is no earlier than the start of the preceding cue, end must be greater than its own start, and different cues may overlap. Cue order is by start time, not a ban on overlap. This matters for simultaneous speakers, overlapping sound cues, and the VTS transcript order; an overzealous “no overlap” lint would reject some valid material. Check cue ends against media duration and context, and check alignment by playing the video. [S04]

Keep formats purpose-specific:

- **WebVTT** is the browser/web delivery and transcript-synchronization target.
- **SRT/SubRip** is a useful interchange input, but export/convert to valid WebVTT before publishing under HTML `<track>`; verify that speaker tags, line breaks, cue settings, Unicode, timestamps, and styling survive the round trip.
- **TTML/IMSC or a delivery-required broadcast profile** is appropriate only if a destination partner requires it. It is XML/profile-based and brings a distinct processor/profile question; this brief gives no broadcast distribution requirement. Subtitle Edit lists TTML and WebVTT alongside SRT as separately supported formats, but conversion support does not prove every style/semantic feature maps without loss. [S04, S09, S13]

An accessible transcript is a user-facing text resource, not merely a dump of dialogue. Publish a readable, searchable transcript adjacent to the player or a clear link if appropriate; preserve speaker identity and meaningful sound information, headings/chapters where useful, and timestamps or seek links when they improve navigation. Able Player can build an interactive transcript from timed tracks, but also documents a manual external transcript option; the manual route permits richer structure. Review timing interactions when chapters, captions, descriptions, and translations are combined, because a one-millisecond ordering difference can move a chapter heading after its first caption. [S05]

Captions and visual description solve different information gaps. WCAG 2.2 SC 1.2.2 requires captions for prerecorded synchronized audio/video at Level A (except the stated text-alternative exception); its WAI explanation says captions convey dialogue and meaningful non-speech audio such as speaker identity, sound effects, music, and laughter. SC 1.2.3 offers an audio description **or** a full time-based media alternative at Level A; SC 1.2.5 requires audio description at Level AA where important visual information is not already spoken. Review each video for visual-only content/on-screen text and record the decision; a transcript of audio does not itself describe silent visual information. These are WCAG statements, not a determination of the legal regime applicable to this organization. [S01, S02, S14]

### D. Timing, rights, and governance constraints

For each recording, preserve its exact playback timeline/timebase and test every exported cue against that playback. Use the editor's waveform/spectrogram and offset/point synchronization to find likely boundaries; listen to the recording to decide them. Watch a complete representative segment at normal speed for synchronization, reading flow, line breaks, speaker changes, music/sound cues, and whether captions obscure important imagery. Maintain one published timing convention/house style after a small user-reviewed pilot. Numeric character-per-second or line-length limits may be adopted as **review flags**, but none is established by the brief as the acceptance standard; derive/readability-test them with the intended audience and languages rather than substituting a universal number for review. DCMP's Captioning Key is a useful editorial checklist for preserving words, speaker identity, sound effects, and music; it is guidance, not a WCAG conformance score or a globally binding law. [S09, S14]

Before public release, inventory who owns or has licensed the video, audio, music, performances, and underlying text; confirm permissions cover public web display/streaming and the needed caption/transcript/translation adaptations, storage and contractor/tool processing, and future corrections. This is a rights clearance question, not a conclusion that every caption necessarily requires a separate license. As one jurisdiction-specific example, U.S. 17 U.S.C. §106 includes an owner's exclusive right to prepare derivative works, and the statutory definition expressly includes translations; the brief does not identify a governing jurisdiction, and local counsel/rights holder review must decide application. Confirm participant releases and any privacy/consent limits as well. [S15]

For author corrections, expose a bounded route: feedback/request -> triage against the source recording -> edit draft -> language/content review -> approve -> publish a new version, retaining who/when/why and the old version. Store per-video and per-language metadata such as source asset ID/hash, language/locale, format, revision, draft/approved/published/withdrawn status, author/reviewer, source or authority for disputed wording, last review date, and rights status. Drafts should not silently replace public content. Invite named/registered trusted editors for direct corrections only if the organization decides to operate accounts and access controls. A privacy-preserving public correction form may collect only enough contact information to resolve the report. The choice between internal editors, staff-mediated requests, and named external collaborators is an organization decision.

### E. Proposed validation and evidence limits

No project runtime, 40 source files, target browser matrix, or qualified accessibility test environment was supplied by the authorized input map. No code, player, video, caption file, browser, screen reader, caption validator, or real user was run in this research. The checks below are proposals only.

1. Pilot a representative file, languages, player, and release workflow with people who use captions/transcripts, including Deaf/hard-of-hearing and blind/low-vision participants as relevant and available. Revise the house style and player choice from their task feedback.
2. For each video/language, compare transcript and captions to the complete recording for words, names/pronunciation, speaker labels, meaningful non-speech sound, translation meaning, cue timing, readable presentation, and missed/extra content. A second human reviewer signs off; sample the entire recording rather than trusting a score or a partial spot check.
3. Run a WebVTT parser/validator and automated checks for file encoding/header, cue syntax, nondecreasing start times, end-after-start, cues past media duration, language/label metadata, and missing/incorrect asset references. Permit valid overlaps; flag them for review rather than failing by default. Separately render every file in the selected browser/player. Validate conversions by round-tripping representative SRT/TTML input if either is accepted.
4. Test keyboard-only player and transcript operation: focus visibility/order, play/pause/seek/volume/caption and language selection, transcript navigation/seek, preferences, close/escape behavior, no traps, and responsive zoom/small viewport. Repeat with named browser/screen-reader/OS versions from the selected audience matrix. Automated accessibility tooling helps find markup defects but does not establish WCAG conformance or content quality.
5. Review each recording for visual-only information and document whether no audio description is necessary, a transcript/time-based alternative suffices at the chosen scope, or an audio-description track/version is needed. Verify that an approved description works as speech/text with the chosen player and that it does not get confused with captions in transcript ordering.
6. Verify rights status and contributor permissions before enabling public video, transcript, translations, or submissions; confirm how withdrawn media and corrections propagate to every track/embed/export.
7. Track readiness across all 40 recordings with one row per asset and one status per required language/alternative: source/rightholder, caption draft, language review, timing/content QC, transcript/description decision, publish approval, published asset URL/version, and last recheck. Launch only when the agreed per-item requirements are complete; use no single automated accessibility score as a gate.

## Decisions and uncertainties carried forward

- Hosting (site files/CDN, YouTube/Vimeo, or other) and whether the site keeps its own immutable source/caption masters.
- Required languages and whether each translation is a draft, publication deliverable, or both; the human fluency/review capacity and terminology owner.
- Rights-holder/jurisdictions and existing contracts/releases, especially audio/music, translation, public transcript, hosted processing, and submitted corrections.
- Whether the organization wants an in-house or staff-managed editorial workflow (Subtitle Edit/local tools), hosted collaboration (Amara), or a mixed model.
- Player selection (Able Player tagged release vs native controls/custom build vs provider iframe), target browser/assistive technology support, ownership for updates, and permitted hosting/provider constraints.
- Whether the target is specifically WCAG 2.2 AA or another standard/jurisdiction and whether visual-only information requires new audio-description production.
- Accessibility support cannot be demonstrated from feature lists alone; issue/fix histories and editor documentation do not replace version-pinned pilot tests and content review.
