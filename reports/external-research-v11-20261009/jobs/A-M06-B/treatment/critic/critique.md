## Material findings

**M1 — The load-bearing #691 quarantine-skip claim rests on issue-list metadata, not the
issue, and is not re-checked against the current release.** Evidence: source-map.json S15
observed_operations = "GitHub issue-list fetch", #691 body and linked commits explicitly
unfetched (draft.md cross-cutting, own admission); S16 (#869) comes from the *same single
list fetch*. My releases fetch (21:27:53 UTC) shows active development through v1.18.0
(2026-09-26) — six years of releases since a 2019 "won't fix" were not surveyed, and the
draft's validation proposal #3 (throwaway VM) is the only thing that would catch a fix.
Challenge accepted in part: the factual assertion "the stock exit path cannot be trusted"
(S15) overstates list-metadata evidence; it should read "reported skip, body unverified,
status on current release unknown". The recommended compensating rescan-on-release stands
independently — it is sound defense-in-depth regardless of whether #691 still reproduces —
so the P3 correction survives, but its evidence citation must be weakened as above.

**M2 — The S05/S06 bagit-python default-algorithm "conflict" is treated as symmetric
unresolved evidence; it is not.** Evidence: source-map.json S05 = direct README fetch at
21:17 UTC ("SHA256 and SHA512 are generated by default") vs S06 = search-level summary at
21:13 UTC whose direct PyPI fetch FAILED at 21:16 UTC; additionally the predecessor
`research/evidence-first.md` O2.1 asserted the MD5 default as a governing finding
("bagit-python's own project page documents that manifest generation defaults to MD5") on
exactly the evidence that later failed verification — the draft nowhere records that its
own earlier stage had asserted the losing side as fact. Challenge: a failed-fetch search
snippet must not be retained co-equal with a direct primary fetch; S06 should be downgraded
to "unverified secondhand claim, superseded by S05," while keeping the genuinely open
question (which *release tag* the README describes — S05's own version field admits "exact
latest release tag UNKNOWN", i.e., mutable default-branch evidence, correctly flagged by
the draft's pin-the-release condition, which survives).

**M3 — Version conditions are anchored to stale documentation while the project is on
v1.18.0.** Evidence: source-map.json S01 pins Archivematica behavior to `/docs/1.8.1/` and
labels it "current stable docs site"; S03 is acknowledged "~1.1 era" legacy wiki
(failed-directory claim). My releases fetch (21:27:53 UTC) shows v1.18.0 released 2026-09-26
(with paired Storage Service 0.24.0); 1.8.1-era docs are ~2019 vintage. Challenge: pipeline

must be conditioned "as documented for 1.8.1; re-verify at pinned current release" — the
draft says this nowhere for S01/S03 (it does for processingMCP.xml).

**M4 — The `processingMCP.xml` quarantine default was resolvable by the same operation class

evidence-first explicitly queued it ("Pinning … queued for the discovery stage");
discovery.md still lists it unresolved; draft re-defers it to proposed validation #2. The

configured" is search-level only) is correct and the uncertainty is honestly retained; the
challenge is the missed cheap retrieval, and any final must keep this as an open validation

**M5 — The low-cost single-VM recommendation omits the governing resource floor of its own
scanner class.** Evidence: docs.clamav.net (my fetch, 21:27:53 UTC): minimum 3 GiB+ RAM,

**M6 — Metadata repair (a named brief need) is answered with governance but no repair
