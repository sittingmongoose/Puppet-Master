## P1 — "Accept ZIP uploads." — Disposition: correction (necessary but under-specified)

ZIP-only intake cannot carry the obligations the rest of the plan assumes: a bare ZIP
has no standard manifest, so P2's checksum verification has nothing to verify against,
and there is no donor-side conformance surface. Retained findings: BagIt (RFC 8493) is
the interoperable package format with per-algorithm manifests (S04); DART gives small
donors drag-and-drop BagIt packaging driven by a profile, over generic S3/BagIt
endpoints without APTrust membership (S08, S09); BitCurator covers donors who arrive
with physical media instead of packages (S10, S11).
- Conditions: accept ZIP at the edge but immediately re-bag into BagIt with SHA-256/512
  so a manifest exists from the moment of receipt; donor-side path uses a BagIt profile
  instead (conformance enforced before upload).
- Alternatives retained: (a) profile-conformant bags from donors via DART; (b)
  archive-side re-bagging of arbitrary ZIPs; (c) full Archivematica pipeline intake of
  raw transfers (S01) — more operational weight, one product does everything.
- User decision: which intake surfaces to offer donors (DART profile vs plain ZIP vs
  physical media drop-off), and whether the archive joins APTrust or runs an
  independent S3/BagIt endpoint.
- Uncertainty: ZIP central-directory corruption and odd ZIP variants (unknown edge
  coverage of chosen extraction tooling — untested, no runtime).

## P2 — "Verify SHA-256 checksums." — Disposition: correction (right algorithm, wrong scope)

SHA-256 is consistent with RFC 8493's MUST-support list and the SHOULD-default
recommendation (S04, quote retained). Two corrections: (1) the plan never says who
creates the digests — with bare ZIPs (P1) there is no donor manifest, so "verification"
degrades to self-checking the archive's own re-bag, which proves nothing about the
donor transfer; provenance still needs donor identity + custody records bound to the
transfer, per the brief's own warning and RFC 8493's lack of any identity primitive
(S04). (2) Verification must be full (digest recompute), not `--validate --fast`,
which checks only structure + payload-oxum (S05) — fast mode cannot catch a mutated
payload byte.
- Conditions: pin the bagit-python release before relying on default-algorithm
  behavior — the current README states SHA-256/512 are generated by default (S05),
  contradicting a search-level PyPI summary claiming MD5-by-default (S06); conflict
  retained, unresolved (PyPI fetch failed). Record algorithm, tool, and tool version in
  the transfer history.
- Optional enhancement: reject MD5/SHA-1 manifests on intake (legacy donors); accept
  with re-bag + note in the rejection report.
- Uncertainty: the S05/S06 default-algorithm conflict above.

## P3 — "Extract to the archive folder and update a database." — Disposition: correction (sequence violates malware/quarantine separation)

Extraction straight to the archive folder repeats the exact failure upstream declined
to fix: Archivematica #691 — quarantine release skips the "Scan for viruses"
microservice entirely, closed 2019-10-30 as "won't fix" (S15). Correct sequence:
extract into quarantine, scan there (ClamAV; scanning is mandatory and cannot be
disabled in the Archivematica pipeline — #869, S16), rescan after freshclam definition
updates, and only then move to archive storage; add a compensating rescan-on-release
if a quarantine stage is used, because the stock exit path cannot be trusted (S15).
"Update a database" is undefined: recommend a transfer-history event log using the
canonical OSS born-digital step order (receive → virus check → format ID → fixity →
sensitive-content review → extract/normalize; S11) with tool and signature-file
versions per event — this is what makes the history repeatable.
- Conditions: ClamAV definitions auto-update (freshclam) and quarantine duration > 0
  (Archivematica's shipped `processingMCP.xml` default value remains UNCONFIRMED —
  search-level indication is effectively off unless configured); clamdscan vs clamscan
  chosen consciously (speed vs always-current definitions; S02, S14).
- Alternatives retained: minimal harness (bagit-python + DROID + ClamAV + event log on
  one VM) vs Archivematica pipeline (S01) vs APTrust-style repository flow (S07).
- Optional capability: DROID/PRONOM format identification at validation to compare
  claimed extension vs identified format (S12) — feeds both rejection reports and
  metadata repair; PRONOM signature-file version must be recorded or identification is
  not reproducible (S13).

## P4 — "Let staff edit metadata after import." — Disposition: rejected as stated; correct to audited repair with role decisions

Uncontrolled post-import editing silently rewrites the record the archive just swore
to (the brief's repeatable-history requirement). Correction: metadata repair happens
with an audit trail — append-only event log entries (who, what, when, why), original
donor metadata preserved immutably alongside repaired values; DROID identification
provides the evidence for repairs (extension/format mismatches, S12).
- User decision: which staff roles may repair which fields, and whether original
  donor-supplied metadata is immutable (recommended) or editable with history.
- Optional enhancement: repair suggestions pre-computed at validation (format ID,
  missing bag-info fields) so staff confirm rather than compose.
- Uncertainty: none load-bearing beyond the role/permission design choice itself.

## P5 — "Keep original filenames." — Disposition: already-covered in substance, correct with one condition

Keep them — but as recorded evidence, not as truth: filenames are claims (extensions
can be wrong or spoofed; DROID comparison is the check, S12). Retain original paths and
names inside the bag structure and the event log; if storage normalization renames
anything, the mapping lives in the transfer history.
- Condition: filename retention rides along with P2/P3's manifest + event log so the
  original name is provably tied to the received bytes.
- Uncertainty: non-ASCII/legacy filename encodings inside donor ZIPs (untested — no
  runtime; flagged as a validation target).

## P6 — "Test with three good packages." — Disposition: rejected as sufficient; keep as smoke subset only

Three good packages test the happy path and nothing the brief actually worries about
(rejection reports, malware/quarantine, provenance). Replace with a discriminating
matrix; keep the three-good case as one cell.
- Proposed discriminating validations (NONE executed — no runtime in this stage):
  1. Pinned bagit-python release: create a bag with defaults, inspect manifests —
     discriminates S05 (SHA-256/512 default) vs S06 (MD5 default) readings; also
     validates P2's algorithm condition.
  2. Fetch shipped `processingMCP.xml` at a pinned Archivematica release — discriminates
     "quarantine off by default" vs "on with N days" (feeds P3 conditions).
  3. Throwaway Archivematica VM: transfer → quarantine → release, observe microservice
     sequence — tests whether #691's scan-skip still exists on the current release.
  4. Mutate one payload byte in a bag; run `--validate --fast` vs full validation —
     fast passes where full fails, demonstrating fast-validation is not fixity (feeds
     P2 and rejection-report categories).
  5. Malformed ZIP, missing-file bag, unexpected-file bag, checksum-mismatch bag —
     exercises the rejection-report taxonomy (ChecksumMismatch / FileMissing /
     UnexpectedFile, S05).
  6. Same file set under two PRONOM signature-file versions — demonstrates the version
     must be recorded for repeatable history (feeds P3/P5).
  7. Non-ASCII filename ZIP round-trip (feeds P5 uncertainty).
- Executed so far, exhaustively: none — documentary retrieval only (web searches; two
  page fetches: bagit-python README, archivematica/Issues list, ~21:16–21:17 UTC). No
  sandbox/witness ran; proposals above are honestly unexecuted.

## Product-level summary

The thin plan is a reasonable skeleton but fails the brief in four load-bearing places:
it has no provenance story beyond checksums (P2), no quarantine/scan sequencing (P3,
against a known upstream won't-fix gap), uncontrolled metadata editing (P4), and a
happy-path-only test story (P6). The corrections above — BagIt profiles donor-side,
full validation, quarantine-then-scan-then-release with compensating rescan, audited
metadata repair, filenames-as-evidence, and an adversarial test matrix — close those
gaps with interoperable, low-cost OSS components identified in discovery.
