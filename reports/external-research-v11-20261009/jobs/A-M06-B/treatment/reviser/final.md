## O1 — Discovered tools, products, and materially different approaches

1. **BagIt (RFC 8493 V1.0) + bagit-python (LoC)** — the interoperable interchange wrapper:
   directory layout + per-algorithm manifests (R01, R02). Mechanism retained: validate where
   the package is built, and give every receipt a manifest from the moment it arrives.
2. **DART 3 (APTrust, OSS, GUI+CLI)** — donor-side BagIt packaging driven by
   machine-checkable BagIt profiles, uploading to generic S3/BagIt endpoints without APTrust
   membership (R16). Mechanism: push conformance to the donor; staff-side rejection shrinks
   to profile violations. Exact current release number UNKNOWN (unresolved).
3. **Archivematica (Artefactual, OSS)** — full OAIS transfer→ingest pipeline with mandatory
   ClamAV scanning (R04, R05, R08, R09). Mechanism: accept raw transfers, let the pipeline
   validate; buys normalization/AIP workflow at real operational weight.
4. **BitCurator environment + Consortium workflows; CPRER 2018 module; Educopia common
   steps** — disk imaging, PII discovery, filesystem analytics for donors who arrive with
   physical media; the canonical OSS step order (image → virus check → format ID → fixity →
   sensitive content → extract) doubles as the transfer-history event model (R17, R18).
5. **DROID/PRONOM (TNA) and Siegfried** — format identification for validation and repair
   evidence (R12, R13, R14). Siegfried v1.11.9 (2026-09-27, Apache-2.0, `sf -serve` server
   mode) is this arm's only evidence-backed identifier; DROID claims remain search-level
   (its TNA page 404'd; R12).
6. **ClamAV** — the detection engine: signature-based, freshclam updates, `--move/--copy`
   quarantine mechanics; 48 h signature-propagation latency and a 3 GiB+ RAM floor are
   governing limits, not afterthoughts (R11).
7. **Audit rubric**: NDSA Levels of Digital Preservation V2.1 (March 2026) treats fixity and
   provenance as separate staged functional areas — a usable maturity rubric for a small
   archive (R19; matrix text on OSF unfetched).

Materially different architecture axes, all retained (none collapsed): donor-side profile
conformance (DART) vs staff-side pipeline validation (Archivematica) vs a composable minimal
harness (bagit-python + Siegfried/DROID + ClamAV + append-only event log on one host);
file-package intake vs media imaging intake (BitCurator). veraPDF was probed as a PDF/A
validation candidate but has no pinned release evidence — provisional only, not load-bearing
(R15).

## O2 — Primary source behavior: governing defaults, units/types, limits, applicability

- **Algorithms (governing):** BagIt 1.0 tools MUST support SHA-256 and SHA-512; SHA-512 is
  the recommended creation default; MD5/SHA-1 optional for backwards compatibility (R01).
  Units: per-file hex digests in `manifest-<alg>.txt`; `Payload-Oxum` =
  OctetCount.StreamCount.
- **Fast validation is not fixity:** bagit-python `--validate --fast` checks structure +
  payload-oxum WITHOUT recomputing digests (R02); the RFC makes full checksum validation
  REQUIRED before a bag is valid (R01). A validator that only fast-validates has not
  verified fixity — this drives both P2 and rejection-report design.
- **Default-algorithm reading (amended per adjudication M2):** the direct README fetch —
  "SHA256 and SHA512 are generated by default" — governs; the failed-fetch PyPI summary
  claiming an MD5 default is superseded secondhand material, retained only as a recorded
  version-drift question, not co-equal evidence (R02 vs R03). The open residual is which
  release tag the default-branch README describes (release tag UNKNOWN). Any production
  reliance pins the release first (proposed validation V1).
- **Checksum ≠ provenance (structural):** manifests bind bytes to digests written at
  packaging time by whoever wrote them; BagIt has no identity/custody primitive;
  bag-info.txt is "intended primarily for human use"; the format "is not designed to be
  secure against active attacks" and tamper protection needs additional measures such as
  digital signatures (R01). Provenance must ride as separate bound evidence: donor
  identity, transfer agreement, custody log.
- **Malware/quarantine limits:** ClamAV detection is signature-based with an open-world gap;
  submitted signature changes take ≥48 h to propagate, so "not detected" ≠ "clean" and a
  scan is only interpretable against its definition age (R11). clamscan (slow, always
  current) vs clamdscan (fast, daemon-cached) is a conscious operational choice (R05).
  Resource floor: minimum 3 GiB+ RAM (3–4 GiB advised for constrained environments), 1 CPU
  ≥2.0 GHz, 5 GiB disk; supported platforms are current OS lines only (R11). No version-EOL
  policy or update-cadence guarantee is stated in the fetched docs (absence recorded).
- **Archivematica governing defaults (version-conditioned per M3):** virus scanning is
  mandatory — no supported off-switch (#869 closed 2021-06-18, R08) — making ClamAV
  availability a hard dependency; scan placement and failed-directory routing are known
  from 1.8.1-era docs and ~1.1-era wiki (R04, R06) and must be re-verified at a pinned
  current release (v1.18.0 line, R09) before any behavior claim is relied on.
- **Identification reproducibility:** identification outcomes depend on the PRONOM
  signature-file version in force; utility v2 (Oct 2020) added container-signature support;
  current signature-file version UNKNOWN (R13). Tool version AND signature-file version
  must both be recorded or identification is not reproducible; DROID's current version is
  unverified (R12).

## O4 — P-clause dispositions (exact revealed plan, compared clause by clause)

> P1: Accept ZIP uploads. P2: Verify SHA-256 checksums. P3: Extract to the archive folder
> and update a database. P4: Let staff edit metadata after import. P5: Keep original
> filenames. P6: Test with three good packages.

**P1 — "Accept ZIP uploads." — correction (necessary but under-specified).**
A bare ZIP has no standard manifest, so P2 has nothing to verify against and no donor-side
conformance surface. Retained: BagIt as the package format (R01); DART profile-driven bags
from donors (R16); BitCurator for physical-media donors (R17). Conditions: accept ZIP at the
edge but immediately re-bag into BagIt with SHA-256/512 so a manifest exists from receipt;
donor-side path uses a profile so conformance is enforced before upload. Alternatives
retained: (a) donor DART+profile bags; (b) archive-side re-bagging of arbitrary ZIPs;
(c) full Archivematica intake of raw transfers (R04, R09). User decision: which intake
surfaces to offer (DART profile vs plain ZIP vs media drop-off), and whether the archive
joins APTrust or runs an independent S3/BagIt endpoint. Uncertainty: ZIP central-directory
corruption and odd ZIP variants — edge coverage of chosen extraction tooling untested
(validation V6).

**P2 — "Verify SHA-256 checksums." — correction (right algorithm, wrong scope).**
SHA-256 matches the RFC MUST list (R01). Two corrections: (1) the plan never says who
creates the digests — with bare ZIPs there is no donor manifest, so "verification" degrades
to self-checking the archive's own re-bag, which proves nothing about the donor transfer;
provenance needs donor identity + custody records bound to the transfer (R01). (2)
Verification must be full digest recompute, not `--validate --fast`, which cannot catch a
mutated payload byte (R01, R02). Conditions: pin the bagit-python release before relying on
default-algorithm behavior; README (R02) governs over the failed-fetch PyPI summary (R03) —
downgraded per M2, drift question retained; record algorithm, tool, and tool version in the
transfer history. Optional enhancement: reject MD5/SHA-1 manifests on intake (legacy
donors) — accept with re-bag + a stated note in the rejection report. Uncertainty: release
tag behind the README default (V1 resolves).

**P3 — "Extract to the archive folder and update a database." — correction (sequence
violates malware/quarantine separation).**
Extraction straight to archive storage ignores the reported quarantine-release gap (#691,
R07) and the fact that scan results depend on definition age (R11). Correct sequence:
extract into quarantine → scan (ClamAV) → rescan after freshclam updates → release to
archive storage, with a compensating rescan-on-release event regardless of #691's current
status (amended citation strength per M1). "Update a database" is undefined: recommend an
append-only transfer-history event log using the canonical OSS step order (receive → virus
check → format ID → fixity → sensitive-content review → extract; R18) with tool and
signature/definition versions per event — that is what makes history repeatable.
Conditions: freshclam automation; quarantine duration > 0 — the shipped processingMCP.xml
default remains UNRESOLVED (R10; search-level indication "effectively off unless
configured", never to be asserted); clamdscan vs clamscan chosen consciously (R05); all
Archivematica behavior claims conditioned to 1.8.1-era evidence, re-verify at pinned
v1.18.x (M3, R09). Resource condition: the host or scan lane meets ClamAV's 3 GiB+ RAM
floor — a 1–2 GB VPS cannot run it; ≥4 GiB host budget or a separate scan host (M5, R11).
Optional capability: PRONOM identification at validation to compare claimed extension vs
identified format (R12, R14) — feeds rejection reports and P4 repair; record tool and
signature-file versions (R13). Alternatives retained: minimal harness vs Archivematica
pipeline vs APTrust-style repository flow.

**P4 — "Let staff edit metadata after import." — correction + user decision (amended
vocabulary per m-4).**
Uncontrolled post-import editing silently rewrites the record the archive just swore to;
the clause is compatible with audited repair, so: correction — repair happens with an
append-only audit trail (who, what, when, why), original donor metadata preserved
immutably alongside repaired values; identification evidence for repairs comes from
extension-vs-identified-format comparison (R12, R14). User decision: which roles may repair
which fields, and whether donor metadata is immutable (recommended) or editable with
history. Optional enhancement: repair suggestions pre-computed at validation so staff
confirm rather than compose. Evidence gap (per M6, stated as a gap): no stage in this arm
retains evidence for a repair-performing tool; ExifTool/FITS-family are named only as an
optional lead requiring its own primary check — not a supported finding.

**P5 — "Keep original filenames." — already-covered in substance; correction with one
condition.**
Keep them as recorded evidence, not as truth: filenames are claims (extensions can be
wrong or spoofed; identification is the check, R12, R14). Retain original paths/names in
the bag structure and event log; if normalization renames anything, the mapping lives in
the transfer history. Condition: retention rides with P2/P3's manifest + event log so the
original name is provably tied to the received bytes (R01). Uncertainty: non-ASCII/legacy
filename encodings inside donor ZIPs — untested (V6).

**P6 — "Test with three good packages." — rejected as sufficient; retained as smoke
subset only.**
Three good packages test the happy path and none of the brief's actual worries. Replaced
by the discriminating matrix in O6; the three-good case is one cell.

## Product-level summary

The thin plan is a workable skeleton that fails the brief in four load-bearing places: no
provenance story beyond checksums (P2), no quarantine/scan sequencing (P3, against a
reported upstream won't-fix gap and 48 h signature latency), uncontrolled metadata editing
(P4), and a happy-path-only test story (P6). The revisions — BagIt manifests from the
moment of receipt, full validation, quarantine-then-scan-then-rescan-on-release with an
audited event history, filenames as recorded evidence, an adversarial test matrix, and an
explicit ≥4 GiB RAM resource floor — close those gaps with interoperable, low-cost OSS
components, while the uncertainty ledger above bounds exactly what remains unproven.
