# Research draft v1 — community-audio oral-history collection

**Candidate:** A-M08-B / treatment / S02  
**Stage:** research; complete planning recommendation with exact thin-plan crosswalk  
**Source register:** [source-map.json](source-map.json); supporting bounded evidence is indexed in [sources/README.md](sources/README.md).  
**Basis:** S02 brief, read before the plan; exact six plan clauses below, read only from the revealed plan. No campaign history, counterpart, evaluator, or plan-root-only file was read.

## Recommendation

Do not treat automatic speech recognition output as publish-ready text, make a single transcript replacement file the system of record, or treat one per-record consent switch as sufficient for interval withdrawal. Use a small, reversible pilot with explicit human review, versioned transcript/index segments, consent-aware search, and separate preservation and public access copies. Compare a self-hosted OHMS route with managed Aviary OHMS. If community-defined cultural protocols are a requirement, test Mukurtu v4 as a governance layer or candidate catalog; if a general open collection/exhibit system is preferred, test Omeka S with a synchronized oral-history component. None of the reviewed product docs proves that a single arbitrary segment inside a long recording can be withdrawn while every other channel is safe. Make that a pilot acceptance criterion.

The brief contains 2,000 one-hour recordings (2,000 hours), multilingual speakers, volunteer transcripts, staff word/speaker corrections, searchable time-linked excerpts, preservation of source audio, cost limits, consent restrictions, and whole-recording or restricted-segment withdrawal. Treat full transcription, translations, topic indexing, streaming copies and any redacted segments as derived, attributable objects linked to a stable interview ID.

## Exact plan-clause comparison (O4)

| Clause exactly as revealed | Disposition | Retained intent and necessary correction |
| --- | --- | --- |
| **P1: “Batch automatic transcription then publish text and audio.”** | **Correction** | Batch inference can help with backlog after the donor/community rights status is checked, but output begins as an explicitly marked machine draft. A trained volunteer or staff reviewer must verify words, speaker labels, language, times, and redaction before publication. Publish only the audience-approved transcript and audio derivative. Where ASR is weak or no reviewer is available, use a curated topic index or descriptive record instead of publishing invented-looking verbatim text. |
| **P2: “Keep transcript edits as one replacement text file.”** | **Rejected** | A replacement-only file loses who changed a word/speaker/time, which version was approved, the source/model and reviewer, and the ability to reverse an incorrect correction or withdrawal. Keep discrete transcript versions and structured timed segments with stable IDs, actor, timestamp, language, review state, and provenance. Permit volunteers to suggest changes; staff or community-approved reviewers approve the public version. Export files can be generated, but do not serve as the only history. |
| **P3: “Search full text with a general database search index.”** | **Correction** | Full-text search is useful and 2,000 interviews do not by themselves justify an elaborate search product. But the public index must be built from approved text only or filter results against rights at query time. The access unit must be no coarser than the restriction unit. Use segment records with interview/segment IDs, language, speaker ID, start/end time, transcript text, topic terms, and rights state. Exclude restricted text from hits, snippets, facets, autocomplete, exports, APIs and caches. OHMS is a useful time-link/viewer mechanism; it does not itself remove every restricted copy across an integrated stack. Benchmark the selected simple database/search service on representative data before sizing it. |
| **P4: “One consent flag hides the public recording.”** | **Rejected** | One flag can represent a whole-recording public/private state but cannot express independent access for metadata, audio, transcript, translation, index or restricted interval, nor distinguish temporary embargo from permanent deletion. Consent is an agreement and authority record, not only a UI toggle. Use per-record and per-derived-object/interval rights with decision owner, scope, date, permitted audiences/uses, expiration/review, and audit events. **User decision required:** when someone requests withdrawal, does the agreement require suppressing public access while retaining an authorized sealed master, or deleting the master too? Products cannot choose that legal/ethical policy. A restriction must govern audio, transcript text, topic/index terms, excerpts, captions, exports, URLs and caches. |
| **P5: “Keep WAV originals and MP3 listening copies.”** | **Already-covered, with a format correction** | The source/access separation is sound. Preserve the received bitstream when it is digital; do not transcode a compressed incoming source into a larger “master.” For new reformatting of analog material, Library of Congress guidance prefers BWF wrapping LPCM for mono/stereo archival masters and prefers WAVE with embedded metadata for digital audio; it does not prescribe a version for every context. Generate one or more distinct access derivatives only as needed. MP3 is one possible listening derivative, not a universal choice, and is not the sole preservation copy. Record IDs, derivation metadata and checksums. |
| **P6: “Validate word accuracy on a few English clips.”** | **Correction** | English clips alone cannot validate the multilingual collection, and a few clips can miss dialect, proper-name, overlap, noise, language-switching and long-form failure modes. Run a consent-cleared pilot stratified by each represented language and salient audio/dialect conditions, with competent speakers reviewing a human reference. Report WER/CER with normalization rules, missed/spurious text and names, diarization/timing errors, review minutes per hour, and disagreement by language/condition. Set acceptance thresholds with the community and reviewers; where ASR is not useful, do not force it. |

### Reconciliation classifications across the findings

- **Correction:** P1, P3 and P6 keep their useful intent but need human review, rights-aware search and multilingual validation.
- **Rejected:** P2's single replacement as the only transcript record, and P4's one-flag access model as adequate for all restrictions.
- **Already-covered:** P5's separate original and listening-copy concept, subject to preservation format/bit-preservation conditions.
- **Optional enhancement:** Aviary's hosted workflow; Mukurtu community protocols; Omeka S for catalog/exhibits; a curated timecoded topic index when full transcripts are not affordable or reliable; BagIt packages and PREMIS event/rights metadata.
- **User decisions:** final platform and hosting; spending cap and staffing; whose/community governance rules to encode; languages and translations to prioritize; privacy versus discoverability of descriptive metadata; rights/retention meaning of withdrawal; whether recordings can be sent to a remote ASR/vendor; level of transcription/indexing promised.
- **Uncertain:** current Aviary price and storage/egress/exit costs; custom-domain/theme and ownership terms; import/export fidelity; self-hosted OHMS current server support; exact interval-level access semantics in Aviary or any chosen stack; actual ASR quality by language; original file formats/sizes; transcript rights; and whether preservation copies may lawfully/ethically remain after a particular withdrawal.

## Findings and product options

### OHMS and index-first discovery

The University of Kentucky's OHMS resource page describes word-level search linked to interview moments and links the tool, account request and login. The Viewer repository offers an oral-history-specific synchronized interface. Changing its media player requires PHP/JavaScript customization, and the repository specifically directs implementers to test transcript/index search and matching playback positions. This fits time-linked excerpts and searching, but adds server integration, update and hardening responsibilities. Confirm runtime requirements against the selected current release rather than copying an old README requirement into a procurement decision. [S02, S03, S05]

OHMS makes indexing useful as a distinct approach, not merely an inferior transcript. A transcript provides word search; a human topic index provides discoverable concepts and short time-linked sections while avoiding the false promise that every spoken word was captured. The brief does not state that all 2,000 hours must receive a verbatim transcript. A user decision should set the collection's coverage promise: full transcript, index-first, or a tiered mixture.

The Viewer release history reinforces specific integration risks. Version 3.10.12 (commit 093ff83) fixes a disappearing “View Transcript” link and index-to-transcript segment navigation; v3.10.14 fixes PDF output for legacy transcripts without timecodes; v3.10.15 (commit ec922b6bd2e94bbbe537aa931e273ce99637ec7d) adds sample Apache/Nginx rules denying direct web access to cache files. These release notes are relevant evidence for navigation, legacy-data and publishing-security QA. They are not locally reproduced fixes. The pinned README says a different player entails PHP/JavaScript adaptation and alignment checks. [S03–S05]

### Aviary's hosted OHMS route

The Aviary guide describes transcript imports/creation, editing text and speakers, find/replace, start-time correction, language alternatives, time-coded segments, annotation and export. Newer Aviary-format transcripts can be edited; legacy transcripts have less complete time data and need conversion for the editor's new sync capabilities. Manual timecodes use HH:MM:SS; WebVTT uses segment times including milliseconds. Test any time conversion, import, export, corrections and language variant round trip. [S06]

Aviary offers separate statuses/permissions for resources, media, transcripts and indexes; supports permission groups and access requests; and documents uploaded media as private/encrypted at rest in Wasabi with expiring access leases. These are vendor statements. The guide documents access at index level, while an index contains segments; it does not establish an ACL for arbitrary segments within a single index or transcript. Therefore, treat whole-object privacy as present and segment-level privacy as uncertain. Use a vendor demonstration and negative tests before relying on the platform for restricted intervals. No price was retrieved. Consider it only if its service, contract, export and operations savings fit a budget approved by the user. [S07–S08]

### Mukurtu and Omeka S as materially different routes

Mukurtu v4 gives a community-defined protocol approach: every content/media object needs a protocol; open is visible to all visitors, strict requires logged-in protocol members; content can stay open while attached media uses a stricter protocol. When multiple protocols apply, “All” is stricter and the default for documented media, while “Any” allows membership in one or more selected protocols. These defaults are significant and warrant a real membership test. This may be a strong alternative if the communities represented want that cultural-governance model. It is not documented as an interval-ACL system and does not remove the need to choose a transcript editor and synchronized viewer. [S09–S10]

Omeka S is a general web-publication system with item/media metadata and sites; a public item may have private attached media. Its global editing roles and site-specific roles are distinct. Use it as an alternative catalog/exhibit layer only if the team can supply or integrate synchronized transcript/index authoring. Object-level visibility does not prove that time slices are separately permissioned. [S11]

### ASR evolution and failure modes

Whisper v20250625 supports in-language transcription and speech translation into English, and exposes word timestamps in code. Its model card describes 680,000 hours of weakly supervised data, but the distribution is uneven: about 65% English audio/English transcript, 18% non-English audio/English transcript, and 17% non-English audio/non-English transcript. It says performance correlates with language training volume, varies by language/accent/dialect, may hallucinate text absent from audio, and that speaker diarization was not robustly evaluated. The original paper finds multilingual results vary and are related to training-data volume; its reported benchmarks are not performance predictions for this collection. Thus ASR is useful as an editable draft where test results justify it, not an equal-quality engine for every language and not an automatic speaker authority. [S12–S13]

The v20250625 changelog records a torch.load hardening change, a dynamic-time-warping device fix, translation limitation documentation and timestamp improvements. That is useful evolution evidence about the codebase but not evidence that model transcript accuracy is fixed for oral history. [S14]

### Preservation and consent workflow

The Library of Congress prefers BWF wrapping LPCM for archival masters when reformatting mono/stereo analog sound and lists WAVE with embedded metadata as preferred media-independent digital audio. Keep an existing source file bit-for-bit; do not convert an already compressed recording merely to satisfy “WAV originals.” Generate streaming derivatives separately. BagIt RFC 8493 v1.0 provides a payload/data directory and checksum manifests with verifiable completeness; it supports intake and fixity, but not access control, replication or backup. PREMIS 3.0 offers Objects, Events, Rights and Agents for recording representations, transformations, fixity events, access decisions and deletion. These standards can support an auditable workflow but do not implement it themselves. [S16–S18]

Approximate one-copy PCM storage, calculated from the brief's 2,000 hours: stereo 96 kHz/24-bit is 2.0736 decimal GB/hour, about 4.15 TB total; stereo 48 kHz/24-bit is about 2.07 TB; 64 kbit/s audio is about 28.8 MB/hour or 57.6 GB total. These estimates omit containers, metadata, other derivatives, replication, backup history, filesystem overhead and growth. Actual source formats and access demand must drive sizing.

OHA guidance makes access planning and informed consent part of project design; it recommends documented consent, possible narrator review before public release and a clear process for preservation/access. Its glossary distinguishes consent from copyright and describes rolling consent. Record what was agreed, which products/derivatives it covers, whether a withdrawal removes access or deletes files, and who can authorize that decision. Do not claim a public copy can be recalled after download. This is professional guidance, not legal advice. [S15]

## Proposed architecture

- **Preservation area:** unchanged received source, stable IDs, file metadata, checksums, at least two managed copies based on institutional policy, and logged fixity/restore events. If the agreement requires erasure, record and execute that disposition instead of preserving contrary to consent.
- **Editorial area:** controlled working copy; per-language timed transcript versions; speaker/person authority IDs and optional pseudonyms; topic index segments; volunteer proposals; staff/community review; correction provenance; transcript and index export formats.
- **Public access area:** only approved item metadata, transcript/index segments, captions, and access-audio derivatives; time-linked playback uses a tested viewer; no public search material is generated from restricted text.
- **Rights control:** rights/consent object points to authority evidence, allowed uses, media/text scopes, time intervals, audience, embargo and review/expiry. Search, API, media origin, byte-range, player, captions, RSS/feed, downloads and CDN/cache purge consult the same current allowed state.
- **Withdrawal:** immediately suppress the affected public material; invalidate URLs and caches; regenerate transcript/index/stream derivatives from approved content; log event, authority, scope and outcome; retain or erase preservation objects according to the actual agreement. A restricted interval in a single long media file usually needs a separately rendered redacted access file or an authenticated segment-serving layer. The transcript and index must be redacted too. Do not represent a time-range mask in the browser as security.
- **Portability:** keep stable IDs and documented mappings; export OHMS XML where applicable, WebVTT/TXT transcripts, CSV/WebVTT indexes, and rights metadata. Test imports/exports, not just the existence of export buttons.

## Choices that require stakeholder input

1. What is the maximum recurring spend and who will operate updates, storage, bandwidth, support, and backups? Obtain an Aviary tier quote; compare self-hosted staff time plus hosting rather than software license cost alone.
2. Who may make access rules, and are Mukurtu-style cultural protocols wanted? Which groups can approve/revoke them?
3. For each consent form and withdrawal request, what can be retained, restricted, or erased? Are transcripts and descriptions subject to the same restriction as audio?
4. Which languages, dialects, translations, and transcripts are required first? How many volunteer reviewers are competent in each?
5. Does the project need public anonymous search, controlled user accounts, embargo dates, click-through conditions, or role-group access? Does an existing website/domain/accessibility standard constrain the viewer?
6. What exact source formats/channels and audio-quality levels exist? What audience volume and streaming bandwidth should be budgeted?

No product or platform test, performance benchmark, transcription, security review, storage inventory or runtime validation was executed in this research stage.

## Discriminating validation plan — proposed, not executed

1. On the same consent-cleared 30–60 minute interview, compare a human transcript, ASR draft and human topic index. Include a fluent reviewer for each sampled language plus noisy, accented, overlapping or code-switching material. Report WER/CER with normalization rules, proper-name and dialect errors, hallucinations, speaker-label and timing errors, review minutes per hour, and topic-index usefulness. This determines whether ASR should be used for that language.
2. Have staff/volunteers correct words and speaker names and adjust times in self-hosted OHMS and Aviary. Verify attribution, revision history, reviewer approval, timestamp units and export/re-import of language, punctuation, annotations and speaker IDs.
3. Restrict a known time range. Search its unique words, topics and speaker; test snippets, suggestions, API, exports, player seeking, direct URLs, range requests, captions, feeds, downloads, derived media, logs and caches as public and authorized users. Confirm the restricted interval is unavailable and permitted surrounding material remains synchronized.
4. Withdraw a whole recording and separately one interval. Verify public metadata/text/audio removal; CDN and application-cache invalidation; direct URL denial; exports/feed/API/search refresh; and a logged decision for preservation master disposition. Public downloads already copied cannot be recalled.
5. Package one test intake using BagIt, validate every payload checksum, detect a changed byte, restore a backup and record checksums/format identification/transformation/deletion with PREMIS or a minimal equivalent.
6. For Aviary, obtain a tier-specific written quote, data-processing and retention terms, exit/export sample, domain/theme/accessibility details, and a live interval restriction/removal demonstration. For OHMS, confirm release-specific runtime support, player integration, cache/XML protections, update ownership and accessibility.
