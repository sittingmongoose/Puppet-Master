37: 0037: Attack model¶
38: 0038: The attack model of Borg is that the environment of the client process
39: 0039: (e.g. borg create) is trusted and the repository (server) is not. The
40: 0040: attacker has any and all access to the repository, including interactive
41: 0041: manipulation (man-in-the-middle) for remote repositories.
42: 0042: Furthermore the client environment is assumed to be persistent across
43: 0043: attacks (practically this means that the security database cannot be
44: 0044: deleted between attacks).
45: 0045: Under these circumstances Borg guarantees that the attacker cannot
46: 0046: modify the data of any archive without the client detecting the change
47: 0047: rename, remove or add an archive without the client detecting the change
48: 0048: recover plaintext data
49: 0049: recover definite (heuristics based on access patterns are possible)
50: 0050: structural information such as the object graph (which archives
51: 0051: refer to what chunks)
52: 0052: The attacker can always impose a denial of service per definition (he could
53: 0053: forbid connections to the repository, or delete it entirely).
54: 0054: When the above attack model is extended to include multiple clients
55: 0055: independently updating the same repository, then Borg fails to provide
56: 0056: confidentiality (i.e. guarantees 3) and 4) do not apply any more).

113: 0113: Encryption¶
114: 0114: Encryption is currently based on the Encrypt-then-MAC construction,
115: 0115: which is generally seen as the most robust way to create an authenticated
116: 0116: encryption scheme from encryption and message authentication primitives.
117: 0117: Every operation (encryption, MAC / authentication, chunk ID derivation)
118: 0118: uses independent, random keys generated by os.urandom [2].
119: 0119: Borg does not support unauthenticated encryption -- only authenticated encryption
120: 0120: schemes are supported. No unauthenticated encryption schemes will be added
121: 0121: in the future.
122: 0122: Depending on the chosen mode (see borg init) different primitives are used:
123: 0123: The actual encryption is currently always AES-256 in CTR mode. The
124: 0124: counter is added in plaintext, since it is needed for decryption,
125: 0125: and is also tracked locally on the client to avoid counter reuse.
126: 0126: The authentication primitive is either HMAC-SHA-256 or BLAKE2b-256
127: 0127: in a keyed mode.
128: 0128: Both HMAC-SHA-256 and BLAKE2b have undergone extensive cryptanalysis
129: 0129: and have proven secure against known attacks. The known vulnerability
130: 0130: of SHA-256 against length extension attacks does not apply to HMAC-SHA-256.
131: 0131: The authentication primitive should be chosen based upon SHA hardware support:
132: 0132: all AMD Ryzen, Intel 10th+ generation mobile and Intel 11th+ generation
133: 0133: desktop processors, Apple M1+ and most current ARM64 architectures support
134: 0134: SHA extensions and are likely to perform best with HMAC-SHA-256.
135: 0135: 64-bit CPUs without SHA extensions are likely to perform best with BLAKE2b.
136: 0136: The primitive used for authentication is always the same primitive
137: 0137: that is used for deriving the chunk ID, but they are always
138: 0138: used with independent keys.
139: 0139: Encryption:
140: 0140: id = AUTHENTICATOR(id_key, data)
141: 0141: compressed = compress(data)
142: 0142: iv = reserve_iv()
143: 0143: encrypted = AES-256-CTR(enc_key, 8-null-bytes || iv, compressed)
144: 0144: authenticated = type-byte || AUTHENTICATOR(enc_hmac_key, encrypted) || iv || encrypted
145: 0145: Decryption:
146: 0146: # Given: input *authenticated* data, possibly a *chunk-id* to assert
147: 0147: type-byte, mac, iv, encrypted = SPLIT(authenticated)
148: 0148: ASSERT(type-byte is correct)
149: 0149: ASSERT( CONSTANT-TIME-COMPARISON( mac, AUTHENTICATOR(enc_hmac_key, encrypted) ) )
150: 0150: decrypted = AES-256-CTR(enc_key, 8-null-bytes || iv, encrypted)
151: 0151: decompressed = decompress(decrypted)
152: 0152: ASSERT( CONSTANT-TIME-COMPARISON( chunk-id, AUTHENTICATOR(id_key, decompressed) ) )
153: 0153: The client needs to track which counter values have been used, since
154: 0154: encrypting a chunk requires a starting counter value and no two chunks
155: 0155: may have overlapping counter ranges (otherwise the bitwise XOR of the
156: 0156: overlapping plaintexts is revealed).
157: 0157: The client does not directly track the counter value, because it
158: 0158: changes often (with each encrypted chunk), instead it commits a
159: 0159: “reservation” to the security database and the repository by taking
160: 0160: the current counter value and adding 4 GiB / 16 bytes (the block size)
161: 0161: to the counter. Thus the client only needs to commit a new reservation
162: 0162: every few gigabytes of encrypted data.
163: 0163: This mechanism also avoids reusing counter values in case the client
164: 0164: crashes or the connection to the repository is severed, since any
165: 0165: reservation would have been committed to both the security database
166: 0166: and the repository before any data is encrypted. Borg uses its
167: 0167: standard mechanism (SaveFile) to ensure that reservations are durable
168: 0168: (on most hardware / storage systems), therefore a crash of the
169: 0169: client’s host would not impact tracking of reservations.
170: 0170: However, this design is not infallible, and requires synchronization
171: 0171: between clients, which is handled through the repository. Therefore in
172: 0172: a multiple-client scenario a repository can trick a client into
173: 0173: reusing counter values by ignoring counter reservations and replaying
174: 0174: the manifest (which will fail if the client has seen a more recent
175: 0175: manifest or has a more recent nonce reservation). If the repository is
176: 0176: untrusted, but a trusted synchronization channel exists between
177: 0177: clients, the security database could be synchronized between them over
178: 0178: said trusted channel. This is not part of Borg’s functionality.
185: 0185: Offline key security¶
186: 0186: Borg cannot secure the key material while it is running, because the keys
187: 0187: are needed in plain to decrypt/encrypt repository objects.
188: 0188: For offline storage of the encryption keys they are encrypted with a
189: 0189: user-chosen passphrase.
190: 0190: A 256 bit key encryption key (KEK) is derived from the passphrase
191: 0191: using PBKDF2-HMAC-SHA256 with a random 256 bit salt which is then used
192: 0192: to Encrypt-and-MAC (unlike the Encrypt-then-MAC approach used
193: 0193: otherwise) a packed representation of the keys with AES-256-CTR with a
194: 0194: constant initialization vector of 0. A HMAC-SHA256 of the plaintext is
195: 0195: generated using the same KEK and is stored alongside the ciphertext,
196: 0196: which is converted to base64 in its entirety.
197: 0197: This base64 blob (commonly referred to as keyblob) is then stored in
198: 0198: the key file or in the repository config (keyfile and repokey modes
199: 0199: respectively).
200: 0200: This scheme, and specifically the use of a constant IV with the CTR
201: 0201: mode, is secure because an identical passphrase will result in a
202: 0202: different derived KEK for every key encryption due to the salt.
203: 0203: The use of Encrypt-and-MAC instead of Encrypt-then-MAC is seen as
204: 0204: uncritical (but not ideal) here, since it is combined with AES-CTR mode,
205: 0205: which is not vulnerable to padding attacks.
208: 0208: Refer to issue #747 for suggested improvements of the encryption
300: 0300: Combining encryption with compression can be insecure in some contexts (e.g. online protocols).
305: 0305: Fingerprinting¶
306: 0306: Stored chunk sizes¶
307: 0307: A borg repository does not hide the size of the chunks it stores (size
308: 0308: information is needed to operate the repository).
309: 0309: The chunks stored in the repo are the (compressed, encrypted and authenticated)
310: 0310: output of the chunker. The sizes of these stored chunks are influenced by the
311: 0311: compression, encryption and authentication.
312: 0312: buzhash chunker¶
313: 0313: The buzhash chunker chunks according to the input data, the chunker’s
314: 0314: parameters and the secret chunker seed (which all influence the chunk boundary
315: 0315: positions).
316: 0316: Small files below some specific threshold (default: 512 KiB) result in only one
317: 0317: chunk (identical content / size as the original file), bigger files result in
318: 0318: multiple chunks.
319: 0319: fixed chunker¶
320: 0320: This chunker yields fixed sized chunks, with optional support of a differently
321: 0321: sized header chunk. The last chunk is not required to have the full block size
322: 0322: and is determined by the input file size.
323: 0323: Within our attack model, an attacker possessing a specific set of files which
324: 0324: he assumes that the victim also possesses (and backups into the repository)
325: 0325: could try a brute force fingerprinting attack based on the chunk sizes in the
326: 0326: repository to prove his assumption.
327: 0327: To make this more difficult, borg has an obfuscate pseudo compressor, that
328: 0328: will take the output of the normal compression step and tries to obfuscate
329: 0329: the size of that output. Of course, it can only add to the size, not reduce
330: 0330: it. Thus, the optional usage of this mechanism comes at a cost: it will make
331: 0331: your repository larger (ranging from a few percent larger [cheap] to ridiculously
332: 0332: larger [expensive], depending on the algorithm/params you wisely choose).
333: 0333: The output of the compressed-size obfuscation step will then be encrypted and
334: 0334: authenticated, as usual. Of course, using that obfuscation would not make any
335: 0335: sense without encryption. Thus, the additional data added by the obfuscator
336: 0336: are just 0x00 bytes, which is good enough because after encryption it will
337: 0337: look like random anyway.
338: 0338: To summarize, this is making size-based fingerprinting difficult:
339: 0339: user-selectable chunker algorithm (and parametrization)
340: 0340: for the buzhash chunker: secret, random per-repo chunker seed
341: 0341: user-selectable compression algorithm (and level)
342: 0342: optional obfuscate pseudo compressor with different choices
343: 0343: of algorithm and parameters
344: 0344: Stored chunk proximity¶
345: 0345: Borg does not try to obfuscate order / proximity of files it discovers by
346: 0346: recursing through the filesystem. For performance reasons, we sort directory
347: 0347: contents in file inode order (not in file name alphabetical order), so order
348: 0348: fingerprinting is not useful for an attacker.
349: 0349: But, when new files are close to each other (when looking at recursion /
350: 0350: scanning order), the resulting chunks will be also stored close to each other
351: 0351: in the resulting repository segment file(s).
352: 0352: This might leak additional information for the chunk size fingerprinting
353: 0353: attack (see above).
