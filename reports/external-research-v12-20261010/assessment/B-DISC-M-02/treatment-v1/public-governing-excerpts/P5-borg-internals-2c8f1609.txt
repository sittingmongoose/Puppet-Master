31: 0031: Borg uses a low-level, key-value store, the Repository, and
32: 0032: implements a more complex data structure on top of it, which is made
33: 0033: up of the manifest, archives,
34: 0034: items and data Chunks.
35: 0035: Each repository can hold multiple archives, which
36: 0036: represent individual backups that contain a full archive of the files
37: 0037: specified when the backup was performed.
38: 0038: Deduplication is performed globally across all data in the repository
39: 0039: (multiple backups and even multiple hosts), both on data and file
40: 0040: metadata, using Chunks created by the chunker using the
41: 0041: Buzhash algorithm (“buzhash” chunker) or a simpler fixed block size
42: 0042: algorithm (“fixed” chunker).
43: 0043: To actually perform the repository-wide deduplication, a hash of each
44: 0044: chunk is checked against the chunks cache, which is a
45: 0045: hash table of all chunks that already exist.
46: 0046: Layers in Borg. On the very top commands are implemented, using
47: 0047: a data access layer provided by the Archive and Item classes.
48: 0048: The “key” object provides both compression and authenticated
49: 0049: encryption used by the data access layer. The “key” object represents
50: 0050: the sole trust boundary in Borg.
