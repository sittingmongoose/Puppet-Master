27: Abstract
28: This document defines HTTP fields that support integrity digests. The
29: Content-Digest field can be used for the integrity of HTTP message content. The
30: Repr-Digest field can be used for the integrity of HTTP representations.
31: Want-Content-Digest and Want-Repr-Digest can be used to indicate a sender's
32: interest and preferences for receiving the respective Integrity fields.¶
33: This document obsoletes RFC 3230 and the Digest and Want-Digest HTTP
34: fields.¶

107: 1. Introduction
108: HTTP does not define the means to protect the data integrity of content or
109: representations. When HTTP messages are transferred between endpoints, lower-layer
110: features or properties such as TCP checksums or TLS records [TLS] can provide some integrity protection. However, transport-oriented integrity provides a
111: limited utility because it is opaque to the application layer and only covers
112: the extent of a single connection. HTTP messages often travel over a chain of
113: separate connections. In between connections, there is a possibility for
114: data corruption. An HTTP integrity mechanism can provide
115: the means for endpoints, or applications using HTTP, to detect data corruption
116: and make a choice about how to act on it. An example use case is to aid
117: fault detection and diagnosis across system boundaries.¶
118: This document defines two digest integrity mechanisms for HTTP.
119: First, content integrity, which acts on conveyed content (Section 6.4 of [HTTP]).
120: Second, representation data integrity, which acts on representation data (Section 8.1 of [HTTP]). This supports advanced use cases, such as validating the
121: integrity of a resource that was reconstructed from parts retrieved using
122: multiple requests or connections.¶
123: This document obsoletes [RFC3230] and therefore the Digest and Want-Digest HTTP
124: fields; see Section 1.3.¶
125: 1.1. Document Structure
126: This document is structured as follows:¶
127: New request and response header and trailer field definitions.¶
128: Section 2 (Content-Digest),¶
129: Section 3 (Repr-Digest), and¶
130: Section 4 (Want-Content-Digest and Want-Repr-Digest).¶
131: Considerations specific to representation data integrity.¶
132: Section 3.1 (State-changing requests),¶
133: Section 3.2 (Content-Location),¶
134: Appendix A contains worked examples of representation data
135: in message exchanges, and¶
136: Appendixes B and C contain worked examples
137: of Repr-Digest and Want-Repr-Digest fields in message exchanges.¶
138: Section 5 presents hash algorithm considerations and defines
139: registration procedures for future entries.¶
140: 1.2. Concept Overview
141: The HTTP fields defined in this document can be used for HTTP integrity. Senders
142: choose a hashing algorithm and calculate a digest from an input related to the
143: HTTP message. The algorithm identifier and digest are transmitted in an HTTP
144: field. Receivers can validate the digest for integrity purposes. Hashing
145: algorithms are registered in the "Hash Algorithms for HTTP Digest Fields" registry (see
146: Section 7.2).¶
147: Selecting the data on which digests are calculated depends on the use case of the
148: HTTP messages. This document provides different fields for HTTP representation
149: data and HTTP content.¶
150: There are use cases where a simple digest of the HTTP content bytes is
151: required. The Content-Digest request and response header and trailer field is
152: defined to support digests of content (Section 6.4 of [HTTP]); see
153: Section 2.¶
154: For more advanced use cases, the Repr-Digest request and response header
155: and trailer field (Section 3) is defined. It contains a digest value
156: computed by applying a hashing algorithm to selected representation data
157: (Section 8.1 of [HTTP]).
158: Basing Repr-Digest on the selected
159: representation makes it straightforward to apply it to use cases where the
160: message content requires some sort of manipulation to be considered as
161: representation of the resource or the content conveys a partial representation of a resource,
162: such as range requests (see Section 14 of [HTTP]).¶
163: Content-Digest and Repr-Digest support hashing algorithm agility.
164: The Want-Content-Digest and Want-Repr-Digest fields allow
165: endpoints to express interest in Content-Digest and Repr-Digest, respectively, and to express algorithm preferences in either.¶
166: Content-Digest and Repr-Digest are collectively termed
167: "Integrity fields".
168: Want-Content-Digest and Want-Repr-Digest are
169: collectively termed "Integrity preference fields".¶
170: Integrity fields are tied to the Content-Encoding
171: and Content-Type header fields. Therefore, a given resource may have multiple
172: different digest values when transferred with HTTP.¶
173: Integrity fields apply to HTTP message content or HTTP representations. They do
174: not apply to HTTP messages or fields. However, they can be combined with other
175: mechanisms that protect metadata, such as digital signatures, in order to
176: protect the phases of an HTTP exchange in whole or in part. For example, HTTP
177: Message Signatures [SIGNATURES] could be used to sign Integrity fields, thus
178: providing coverage for HTTP content or representation data.¶
179: This specification does not define means for authentication, authorization, or privacy.¶
180: 1.3. Obsoleting RFC 3230
181: [RFC3230] defined the Digest and Want-Digest HTTP fields for HTTP integrity.
182: It also coined the terms "instance" and "instance manipulation" in order to
183: explain concepts, such as selected representation data (Section 8.1 of [HTTP]), that are now more universally defined and implemented as HTTP
184: semantics.¶
185: Experience has shown that implementations of [RFC3230] have interpreted the
186: meaning of "instance" inconsistently, leading to interoperability issues. The
187: most common issue relates to the mistake of calculating the digest using (what
188: we now call) message content, rather than using (what we now call)
189: representation data as was originally intended. Interestingly, time has also
190: shown that a digest of message content can be beneficial for some use cases, so
191: it is difficult to detect if non-conformance to [RFC3230] is intentional or
192: unintentional.¶
193: In order to address potential inconsistencies and ambiguity across
194: implementations of Digest and Want-Digest, this document obsoletes
195: [RFC3230]. The Integrity fields (Sections 2 and
196: 3) and Integrity preference fields (Section 4)
197: defined in this document are better aligned with current HTTP semantics and
198: have names that more clearly articulate the intended usages.¶

223: 2. The Content-Digest Field
224: The Content-Digest HTTP field can be used in requests and responses to
225: communicate digests that are calculated using a hashing algorithm applied to
226: the actual message content (see Section 6.4 of [HTTP]). It is a
227: Dictionary (see Section 3.2 of [STRUCTURED-FIELDS]),
228: where each:¶
229: key conveys the hashing algorithm (see Section 5)
230: used to compute the digest;¶
231: value is a Byte Sequence (Section 3.3.5 of [STRUCTURED-FIELDS]) that
232: conveys an encoded version of the byte output produced by the digest
233: calculation.¶
234: For example:¶
235: NOTE: '\' line wrapping per RFC 8792
236: Content-Digest: \
237: sha-512=:YMAam51Jz/jOATT6/zvHrLVgOYTGFy1d6GJiOHTohq4yP+pgk4vf2aCs\
238: yRZOtw8MjkM7iw7yZ/WkppmM44T3qg==:
239: ¶
240: The Dictionary type can be used, for example, to attach multiple digests
241: calculated using different hashing algorithms in order to support a population
242: of endpoints with different or evolving capabilities. Such an approach could
243: support transitions away from weaker algorithms (see Section 6.6).¶
244: NOTE: '\' line wrapping per RFC 8792
245: Content-Digest: \
246: sha-256=:d435Qo+nKZ+gLcUHn7GQtQ72hiBVAgqoLsZnZPiTGPk=:,\
247: sha-512=:YMAam51Jz/jOATT6/zvHrLVgOYTGFy1d6GJiOHTohq4yP+pgk4vf2aCs\
248: yRZOtw8MjkM7iw7yZ/WkppmM44T3qg==:
249: ¶
250: A recipient MAY ignore any or all digests. Application-specific behavior or
251: local policy MAY set additional constraints on the processing and validation
252: practices of the conveyed digests.
253: The security considerations cover some of the issues related to
254: ignoring digests (see Section 6.6)
255: and validating multiple digests (see Section 6.7).¶
256: A sender MAY send a digest without
257: knowing whether the recipient supports a given hashing algorithm. A sender MAY send a digest if it knows the recipient will ignore it.¶
258: Content-Digest can be sent in a trailer section.
259: In this case,
260: Content-Digest MAY be merged into the header section; see Section 6.5.1 of [HTTP].¶
261: 3. The Repr-Digest Field
262: The Repr-Digest HTTP field can be used in requests and responses to
263: communicate digests that are calculated using a hashing algorithm applied to
264: the entire selected representation data (see Section 8.1 of [HTTP]).¶
265: Representations take into account the effect of the HTTP semantics on
266: messages. For example, the content can be affected by range requests or methods, such as HEAD, while the way the content is transferred "on the wire" is
267: dependent on other transformations (e.g., transfer codings for HTTP/1.1; see
268: Section 6.1 of [HTTP/1.1]). To help illustrate HTTP representation concepts,
269: several examples are provided in Appendix A.¶
270: When a message has no representation data, it is still possible to assert that no
271: representation data was sent by computing the digest on an empty
272: string (see Section 6.3).¶
273: Repr-Digest is a Dictionary (see Section 3.2 of [STRUCTURED-FIELDS]), where each:¶
274: key conveys the hashing algorithm (see Section 5)
275: used to compute the digest;¶
276: value is a Byte Sequence that conveys an encoded version of the byte
277: output produced by the digest calculation.¶
278: For example:¶
279: NOTE: '\' line wrapping per RFC 8792
280: Repr-Digest: \
281: sha-512=:YMAam51Jz/jOATT6/zvHrLVgOYTGFy1d6GJiOHTohq4yP+pgk4vf2aCs\
282: yRZOtw8MjkM7iw7yZ/WkppmM44T3qg==:
283: ¶
284: The Dictionary type can be used to attach multiple digests
285: calculated using different hashing algorithms in order to support a population
286: of endpoints with different or evolving capabilities. Such an approach could
287: support transitions away from weaker algorithms (see Section 6.6).¶
288: NOTE: '\' line wrapping per RFC 8792
289: Repr-Digest: \
290: sha-256=:d435Qo+nKZ+gLcUHn7GQtQ72hiBVAgqoLsZnZPiTGPk=:,\
291: sha-512=:YMAam51Jz/jOATT6/zvHrLVgOYTGFy1d6GJiOHTohq4yP+pgk4vf2aCs\
292: yRZOtw8MjkM7iw7yZ/WkppmM44T3qg==:
293: ¶
294: A recipient MAY ignore any or all digests. Application-specific behavior or
295: local policy MAY set additional constraints on the processing and validation
296: practices of the conveyed digests.
297: The security considerations cover some of the issues related to
298: ignoring digests (see Section 6.6)
299: and validating multiple digests (see Section 6.7).¶
300: A sender MAY send a digest without knowing whether the recipient supports a given hashing algorithm. A sender MAY send a digest if it knows the recipient will ignore it.¶
301: Repr-Digest can be sent in a trailer section.
302: In this case,
303: Repr-Digest MAY be merged into the header section; see Section 6.5.1 of [HTTP].¶
304: 3.1. Using Repr-Digest in State-Changing Requests
305: When the representation enclosed in a state-changing request
306: does not describe the target resource,
307: the representation digest MUST be computed on the
308: representation data.
309: This is the only possible choice because representation digest requires complete
310: representation metadata (see Section 3).¶
311: In responses,¶
312: if the representation describes the status of the request,
313: Repr-Digest MUST be computed on the enclosed representation
314: (see Appendix B.8);¶
315: if there is a referenced resource, Repr-Digest
316: MUST be computed on the selected representation of
317: the referenced resource even if that is different from the target
318: resource.  This might or might not result in computing
319: Repr-Digest on the enclosed representation.¶
320: The latter case is done according to the HTTP semantics of the given
321: method, for example, using the Content-Location header field (see Section 8.7 of [HTTP]).
322: In contrast, the Location header field does not affect Repr-Digest because
323: it is not representation metadata.¶
324: For example, in PATCH requests, the representation digest
325: will be computed on the patch document
326: because the representation metadata refers to the patch document and not
327: the target resource (see Section 2 of [PATCH]).
328: In responses, instead, the representation digest will be computed on the selected
329: representation of the patched resource.¶
330: 3.2. Repr-Digest and Content-Location in Responses
331: When a state-changing method returns the Content-Location header field, the
332: enclosed representation refers to the resource identified by its value and
333: Repr-Digest is computed accordingly.
334: An example is given in Appendix B.7.¶
335: 4. Integrity Preference Fields
336: Senders can indicate their interest in Integrity fields and hashing algorithm
337: preferences using the
338: Want-Content-Digest or Want-Repr-Digest HTTP fields. These can be used in both
339: requests and responses.¶
340: Want-Content-Digest indicates that the sender would like to
341: receive (via the Content-Digest field) a content digest on messages
342: associated with the request URI and representation metadata.
343: Want-Repr-Digest indicates that the sender would like to receive
344: (via the Repr-Digest field) a representation digest on messages
345: associated with the request URI and representation metadata.¶
346: If Want-Content-Digest or Want-Repr-Digest are used in a response, it
347: indicates that the server would like the client to provide the respective
348: Integrity field on future requests.¶
349: Integrity preference fields are only a hint. The receiver of the field can
350: ignore it and send an Integrity field using any algorithm or omit the field
351: entirely; for example, see Appendix C.2. It is not
352: a protocol error if preferences are ignored. Applications that use Integrity
353: fields and Integrity preferences can define expectations or constraints that
354: operate in addition to this specification. Ignored preferences are an
355: application-specific concern.¶
356: Want-Content-Digest and Want-Repr-Digest are of type Dictionary
357: where each:¶
358: key conveys the hashing algorithm (see Section 5);¶
359: value is an Integer (Section 3.3.1 of [STRUCTURED-FIELDS])
360: that conveys an ascending, relative, weighted preference.
361: It must be in the range 0 to 10 inclusive.
362: 1 is the least preferred, 10 is the most preferred,
363: and a value of 0 means "not acceptable".¶
364: Examples:¶
365: Want-Repr-Digest: sha-256=1
366: Want-Repr-Digest: sha-512=3, sha-256=10, unixsum=0
367: Want-Content-Digest: sha-256=1
368: Want-Content-Digest: sha-512=3, sha-256=10, unixsum=0

370: 5. Hash Algorithm Considerations and Registration
371: There are a wide variety of hashing algorithms that can be used for the purposes
372: of integrity. The choice of algorithm depends on several factors such as the
373: integrity use case, implementation needs or constraints, or application design
374: and workflows.¶
375: An initial set of algorithms will be registered with IANA in the "Hash
376: Algorithms for HTTP Digest Fields" registry; see
377: Section 7.2. Additional algorithms can be registered
378: in accordance with the policies set out in this section.¶
379: Each algorithm has a status field that is intended to provide an aid to
380: implementation selection.¶
381: Algorithms with a status value of "Active" are suitable for many purposes and
382: it is RECOMMENDED that applications use these algorithms. These can be used in
383: adversarial situations where hash functions might need to provide resistance to
384: collision, first-preimage, and second-preimage attacks.
385: For adversarial situations, selection of the acceptable "Active" algorithms
386: will depend on the level of protection the circumstances demand. More
387: considerations are presented in Section 6.6.¶
388: Algorithms with a status value of "Deprecated" either provide none of these
389: properties or are known to be weak (see [NO-MD5] and [NO-SHA]). These
390: algorithms MAY be used to preserve integrity against corruption, but MUST NOT be
391: used in a potentially adversarial setting, for example, when signing Integrity
392: fields' values for authenticity.
393: Permitting the use of these algorithms can help some applications (such as
394: those that previously used [RFC3230], are migrating to this specification
395: (Appendix E), and have existing stored collections of computed digest
396: values) avoid undue operational overhead caused by recomputation using
397: other more-secure algorithms.
398: Such applications are not
399: exempt from the requirements in this section. Furthermore, applications without
400: such legacy or history ought to follow the guidance for using algorithms with
401: the status value "Active".¶
402: Discussion of algorithm agility is presented in Section 6.6.¶
403: Registration requests for the "Hash Algorithms for HTTP Digest Fields" registry
404: use the Specification Required policy (Section 4.6 of [RFC8126]). Requests
405: should use the following template:¶
406: Algorithm Key:
407: The Structured Fields key value used in
408: Content-Digest, Repr-Digest, Want-Content-Digest, or Want-Repr-Digest
409: field Dictionary member keys.¶
410: Status:
411: The status of the algorithm. The options are:¶
412: "Active":
413: Algorithms without known problems¶
414: "Provisional":
415: Unproven algorithms¶
416: "Deprecated":
417: Deprecated or insecure algorithms¶
418: Description:
419: A short description of the algorithm.¶
420: Reference(s):
421: Pointer(s) to the primary document(s) defining the Algorithm
422: Key and technical details of the algorithm.¶
423: When reviewing registration requests, the designated expert(s) should pay
424: attention to the requested status. The status value should reflect
425: standardization status and the broad opinion of relevant interest groups such as
426: the IETF or security-related Standards Development Organizations (SDOs). The "Active" status is not suitable for an
427: algorithm that is known to be weak, broken, or experimental. If a registration
428: request attempts to register such an algorithm as "Active", the designated
429: expert(s) should suggest an alternative status of "Deprecated" or "Provisional".¶
430: When reviewing registration requests, the designated expert(s) cannot use a
431: status of "Deprecated" or "Provisional" as grounds for rejection.¶
432: Requests to update or change the fields in an existing registration are
433: permitted. For example, this could allow for the transition of an algorithm
434: status from "Active" to "Deprecated" as the security environment evolves.¶
435: 6. Security Considerations
436: 6.1. HTTP Messages Are Not Protected in Full
437: This document specifies a data integrity mechanism that protects HTTP
438: representation data or content, but not HTTP header and trailer fields, from
439: certain kinds of corruption.¶
440: Integrity fields are not intended to be a general protection against malicious tampering with
441: HTTP messages.
442: In the absence of additional
443: security mechanisms, an on-path malicious actor can either remove
444: a digest value entirely or substitute it with a new digest value computed over
445: manipulated representation data or content.
446: This attack can be mitigated by combining mechanisms described in this
447: document with other approaches such
448: as Transport Layer Security (TLS) or digital signatures (for example, HTTP Message
449: Signatures [SIGNATURES]).¶
450: 6.2. End-to-End Integrity
451: Integrity fields can help detect representation data or content modification due to implementation errors,
452: undesired "transforming proxies" (see Section 7.7 of [HTTP]),
453: or other actions as the data passes across multiple hops or system boundaries.
454: Even a simple mechanism for end-to-end representation data integrity is valuable
455: because a user agent can validate that resource retrieval succeeded before handing off to an
456: HTML parser, video player, etc., for parsing.¶
457: Note that using these mechanisms alone does not provide end-to-end integrity of HTTP messages over
458: multiple hops since metadata could be manipulated at any stage. Methods to protect
459: metadata are discussed in Section 6.3.¶
460: 6.3. Usage in Signatures
461: Digital signatures are widely used together with checksums to provide the
462: certain identification of the origin of a message [FIPS186-5]. Such signatures
463: can protect one or more HTTP fields and there are additional considerations when
464: Integrity fields are included in this set.¶
465: There are no restrictions placed on the type or format of digital signature that
466: Integrity fields can be used with. One possible approach is to combine them with
467: HTTP Message Signatures [SIGNATURES].¶
468: Digests explicitly
469: depend on the "representation metadata" (e.g., the values of Content-Type,
470: Content-Encoding, etc.). A signature that protects Integrity fields but not other
471: "representation metadata" can expose the communication to tampering. For
472: example, an actor could manipulate the Content-Type field-value and cause a
473: digest validation failure at the recipient, preventing the application from
474: accessing the representation. Such an attack consumes the resources of both
475: endpoints. See also Section 3.2.¶
476: Signatures are likely to be deemed an adversarial setting when applying
477: Integrity fields; see Section 5. Repr-Digest offers an interesting
478: possibility when combined with signatures. In the scenario where there is no
479: content to send, the digest of an empty string can be included in the message
480: and, if signed, can help the recipient detect if content was added either as a result of accident or purposeful manipulation. The opposite scenario is also
481: supported; including an Integrity field for content and signing it can help a
482: recipient detect where the content was removed.¶
483: Any mangling of Integrity fields might affect signature validation. Examples of such mangling include de-duplicating digests or combining different field values (see Section 5.2 of [HTTP]).¶
484: 6.4. Usage in Trailer Fields
485: Before sending Integrity fields in a trailer section, the sender
486: should consider that intermediaries are explicitly allowed to drop any trailer
487: (see Section 6.5.2 of [HTTP]).¶
488: When Integrity fields are used in a trailer section, the field-values are received after the content.
489: Eager processing of content before the trailer section prevents digest validation, possibly leading to
490: processing of invalid data.¶
491: One of the benefits of using Integrity fields in a trailer section is that it
492: allows hashing of bytes as they are sent. However, it is possible to
493: design a hashing algorithm that requires processing of content in such a way
494: that would negate these benefits. For example, Merkle Integrity Content Encoding
495: [MICE] requires content to be processed in reverse order.
496: This means the complete data needs to be available, which means there is
497: negligible processing difference in sending an Integrity field in a header versus
498: a trailer section.¶
499: 6.5. Variations within Content-Encoding
500: Content coding mechanisms can support different encoding parameters, meaning that the same input content can produce different outputs. For example, GZIP supports multiple compression levels. Such encoding parameters are generally not communicated as representation metadata. For instance, different compression levels would all use the same "Content-Encoding: gzip" field. Other examples include where encoding relies on nonces or timestamps, such as the aes128gcm content coding defined in [RFC8188].¶
501: Since it is possible for there to be variation within content coding, the checksum conveyed by the Integrity fields cannot be used to provide a proof of integrity "at rest"
502: unless the whole content is persisted.¶
503: 6.6. Algorithm Agility
504: The security properties of hashing algorithms are not fixed.
505: Algorithm agility (see [RFC7696]) is achieved by providing implementations with flexibility
506: to choose hashing algorithms from the IANA Hash Algorithms for HTTP Digest Fields registry; see
507: Section 7.2.¶
508: Transition from weak algorithms is supported
509: by negotiation of hashing algorithm using Want-Content-Digest or Want-Repr-Digest (see Section 4)
510: or by sending multiple digests from which the receiver chooses.
511: A receiver that depends on a digest for security will be vulnerable
512: to attacks on the weakest algorithm it is willing to accept.
513: Endpoints are advised that sending multiple values consumes resources that may be wasted if the receiver ignores them (see Section 3).¶
514: While algorithm agility allows the migration to stronger algorithms,
515: it does not prevent the use of weaker algorithms.
516: Integrity fields do not provide any mitigations for downgrade or substitution
517: attacks (see Section 1 of [RFC6211]) of the hashing algorithm.
518: To protect against such attacks, endpoints could restrict their set of supported algorithms
519: to stronger ones and protect the fields' values by using TLS and/or digital signatures.¶
520: 6.7. Resource Exhaustion
521: Integrity field validation consumes computational resources.
522: In order to avoid resource exhaustion, implementations can restrict
523: validation of the algorithm types, the number of validations, or the size of content.
524: In these cases, skipping validation entirely or ignoring validation failure of a more-preferred algorithm
525: leaves the possibility of a downgrade attack (see Section 6.6).¶

945: The request Repr-Digest field-value is computed on the enclosed representation
946: (see Section 3.1), which is the JSON object {"title": "New
947: Title"} followed by an LF.¶

949: It refers to the resource identified by
950: Content-Location (see Section 6.4.2 of [HTTP]);

1041: It is a multiline JSON object followed by an LF.¶

1083: For presentation purposes, objects that fit completely within the line-length limits
1084: are presented on a single line using compact notation with no leading space.

1086: (one line per key-value pair) with two spaces of leading indentation.¶

1169: Appendix E. Migrating from RFC 3230
1170: HTTP digests are computed by applying a hashing algorithm to input data.
1171: [RFC3230] defined the input data as an "instance", a term it also defined.
1172: The concept of an instance has since been superseded by the HTTP semantic term "representation".
1173: It is understood that some implementations of [RFC3230]
1174: mistook "instance" to mean HTTP content.
1175: Using content for the Digest field is an error
1176: that leads to interoperability problems between peers that implement [RFC3230].¶
1177: [RFC3230] was only ever intended
1178: to use what HTTP now defines as selected representation data.
1179: The semantic concept of digest and representation are explained
1180: alongside the definition of the Repr-Digest field (Section 3).¶
1181: While the syntax of Digest and Repr-Digest are different,
1182: the considerations and examples this document gives for Repr-Digest
1183: apply equally to Digest because they operate on the same input data;
1184: see Sections 3.1, 6 and 6.3.¶
1185: [RFC3230] could never communicate
1186: the digest of HTTP message content in the Digest field;
1187: Content-Digest now provides that capability.¶
1188: [RFC3230] allowed algorithms to define their output encoding format for use with
1189: the Digest field. This resulted in a mix of formats such as base64, hex, or
1190: decimal. By virtue of using Structured Fields, Content-Digest, and Repr-Digest
1191: use only a single encoding format. Further explanation and examples are provided in Appendix D.¶
