358: Headers
360: The Upload-Expires response header indicates the time after which the
361: unfinished upload expires. A Server MAY wish to remove incomplete uploads after
362: a given period of time to prevent abandoned uploads from taking up extra
363: storage. The Client SHOULD use this header to determine if an upload is still
364: valid before attempting to resume the upload.
365: This header MUST be included in every PATCH response if the upload is going to
366: expire. If the expiration is known at the creation, the Upload-Expires header
367: MUST be included in the response to the initial POST request. Its value MAY
368: change over time.

371: The latter one SHOULD be used if the Server is keeping track of expired uploads.

376: Checksum
377: The Client and the Server MAY implement and use this extension to verify data
378: integrity of each PATCH request. If supported, the Server MUST add checksum
379: to the Tus-Extension header.
380: A Client MAY include the Upload-Checksum header in a PATCH request. Once the
381: entire request has been received, the Server MUST verify the uploaded chunk
382: against the provided checksum using the specified algorithm. Depending on the
383: result the Server MAY respond with one of the following status code:
384: 400 Bad Request if the checksum algorithm is not supported by the server,
385: 460 Checksum Mismatch if the checksums mismatch or
386: 204 No Content if the checksums match and the processing of the data
387: succeeded. In the first two cases the uploaded chunk MUST be discarded, and
388: the upload and its offset MUST NOT be updated.
389: The Server MUST support at least the SHA1 checksum algorithm identified by
390: sha1. The names of the checksum algorithms MUST only consist of ASCII
391: characters with the modification that uppercase characters are excluded.
392: The Tus-Checksum-Algorithm header MUST be included in the response to an
393: OPTIONS request.
394: If the hash cannot be calculated at the beginning of the upload, it MAY be
395: included as a trailer. If the Server can handle trailers, this behavior MUST be
396: announced by adding checksum-trailer to the Tus-Extension header. Trailers,
397: also known as trailing headers, are headers which are sent after the request’s
398: body has been transmitted already.
399: Headers
400: Tus-Checksum-Algorithm
401: The Tus-Checksum-Algorithm response header MUST be a comma-separated list of
402: the checksum algorithms supported by the server.
403: Upload-Checksum
404: The Upload-Checksum request header contains information about the checksum of
405: the current body payload. The header MUST consist of the name of the used
406: checksum algorithm and the Base64 encoded checksum separated by a space.
