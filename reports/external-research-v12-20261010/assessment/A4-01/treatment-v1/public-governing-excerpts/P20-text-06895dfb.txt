606: Resumable uploads of unknown size
607: The resumable upload mechanism supports transfers where the file size is not
608: known in advance. This can be useful for cases like compressing an object
609: on-the-fly while uploading, since it's difficult to predict the exact file size
610: for the compressed file at the start of a transfer. The mechanism is useful
611: either if you want to stream a transfer that can be resumed after being
612: interrupted, or if chunked transfer encoding does not work for your application.
613: For more information, see Streaming uploads.
614: Upload performance
615: Choosing session regions
616: Resumable uploads are pinned in the region where you initiate them. For
617: example, if you initiate a resumable upload in the US and give the session URI
618: to a client in Asia, the upload still goes through the US. To reduce
619: cross-region traffic and improve performance, you should keep a resumable upload
620: session in the region in which it was created.
621: If you use a Compute Engine instance to initiate a resumable upload, the
622: instance should be in the same location as the Cloud Storage bucket
623: you upload to. You can then use a geo IP service to pick the Compute Engine
624: region to which you route customer requests, which helps keep traffic
625: localized to a geo-region.
626: Uploading in chunks
627: If possible, avoid breaking a transfer into smaller chunks and instead upload
628: the entire content in a single chunk. Avoiding chunking removes added latency
629: costs and operations charges from querying the persisted offset of each chunk as
630: well as improves throughput. However, you should consider uploading in chunks
631: when:
632: Your source data is being generated dynamically and you want to limit how
633: much of it you need to buffer client-side in case the upload fails.
634: Your clients have request size limitations, as is the case for many
635: browsers.
636: If you're using the JSON or XML API and your client receives an error, they can
637: query the server for the persisted offset and resume uploading remaining
638: bytes from that offset. The Google Cloud console, Google Cloud CLI, and client
639: libraries handle this automatically on your behalf. See
640: How tools and APIs use resumable uploads for more guidance on chunking for
641: specific client libraries.
642: Considerations
643: This section is useful if you are building your own client that sends

666: Integrity checks
667: We recommend that you request an integrity check of the final uploaded object
668: to be sure that it matches the source file. You can do this by calculating the
669: MD5 digest of the source file and adding it to the Content-MD5 request
670: header.
671: Checking the integrity of the uploaded file is particularly important if you are
672: uploading a large file over a long period of time, because there is an increased
673: likelihood of the source file being modified over the course of the upload
674: operation.
675: However, you can't perform integrity checks on intermediate portions or chunks
680: cannot be overwritten, and Cloud Storage ignores attempts to do so.
