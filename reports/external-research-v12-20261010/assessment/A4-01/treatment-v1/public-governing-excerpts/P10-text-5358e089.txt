151: S3 storage
152: Tusd can store files directly on AWS S3 or other compatible services, e.g. Minio. The uploaded file is directly transferred to S3 while the user is performing the upload without storing the entire file on disk first.
153: Configuration
154: To enable this backend, you must supply the corresponding access credentials and region information using environment variables and specify the bucket name using -s3-bucket, for example:
155: $ export AWS_ACCESS_KEY_ID=xxxxx
156: $ export AWS_SECRET_ACCESS_KEY=xxxxx
157: $ export AWS_REGION=eu-west-1
158: $ tusd -s3-bucket=my-test-bucket.com
159: [tusd] 2019/09/29 21:11:23 Using 's3://my-test-bucket.com' as S3 bucket for storage.
160: ...
161: Credentials can also be loaded from a shared credentials file (~/.aws/credentials) as described in the AWS SDK for Go. You still need to declare the AWS_REGION value which isn't conventionally associated with credentials.
162: Alternative endpoints
163: If you are using an S3-compatible service other than from AWS, you must configure the correct endpoint using -s3-endpoint. Please note that this value must start with http:// or https://, for example:
164: $ tusd -s3-bucket=my-test-bucket.com -s3-endpoint https://mystoreage.example.com
165: 2024/02/20 15:33:45.474497 Using 'https://mystoreage.example.com/my-test-bucket.com' as S3 endpoint and bucket for storage.
166: ...
167: Object prefix
168: If the bucket is also used to store files from other sources than tusd, it makes sense to use a custom prefix for all object relating to tusd. This can be achieved using the -s3-object-prefix flag. For example, the following configuration will cause the objects to be put under the uploads/ prefix in the bucket:
169: $ tusd -s3-bucket=my-test-bucket.com -s3-object-prefix=uploads/
170: AWS S3 Transfer Acceleration
171: If your S3 bucket has been configured for AWS S3 Transfer Acceleration and you want to make use of that service, you can direct tusd to automatically use the designated AWS acceleration endpoint for your bucket by including the optional
172: command line flag -s3-transfer-acceleration as follows:
173: $ tusd -s3-bucket=my-test-bucket.com -s3-transfer-acceleration
174: [tusd] 2019/09/29 21:11:23 Using 's3://my-test-bucket.com' as S3 bucket for storage with AWS S3 Transfer Acceleration enabled.
175: ...
176: Permissions
177: For full functionality of the S3 backend, the user accessing the bucket must have at least the following AWS IAM policy permissions for the bucket and all of its subresources:
178: s3:AbortMultipartUpload
179: s3:DeleteObject
180: s3:GetObject
181: s3:ListMultipartUploadParts
182: s3:PutObject
183: Storage format
184: Uploads on S3 are stored using multiple objects:
185: An informational object with the .info extension holds meta information about the uploads, as described in [the section for all storage backends]({{ site.baseurl }}/storage-backends/overview/#storage-format).
186: An S3 multipart upload is used to transfer the file piece-by-piece to S3 and reassemble the original file once the upload is finished. It is removed once the upload is finished.
187: A file object will contain the uploaded file. It will only be created once the entire upload is finished.
188: A temporary object with the .part extension may be created when the upload has been paused to store some temporary data which cannot be transferred to the S3 multipart upload due to its small size. Once the upload is resumed, the temporary object will be gone.
189: By default, the objects are stored at the root of the bucket. For example the objects for the upload ID abcdef123 will be:
190: abcdef123.info: Informational object
191: abcdef123: File object
192: abcdef123.part: Temporary object
193: {: .note }
194: The file object is not visible in the S3 bucket before the upload is finished because the transferred file data is stored in the associated S3 multipart upload. Once the upload is complete, the chunks from the S3 multipart are reassembled into the file, creating the file object and removing the S3 multipart upload. In addition, the S3 multipart upload is not directly visible in the S3 bucket because it does not represent a complete object. Please don't be confused if you don't see the changes in the bucket while the file is being uploaded.
195: Metadata
196: If metadata is associated with the upload during creation, it will be added to the file object as user-defined object metadata once the upload is finished. Because the metadata on S3 objects must only contain ASCII characters, tusd will replace every non-ASCII character with a question mark. For example, "Menü" will become "Men?".
197: In addition, the metadata is also stored in the informational object, which can be used to retrieve the original metadata without any characters being replaced.
198: If the metadata contains a filetype key, its value is used to set the Content-Type header of the file object. Setting the Content-Disposition or Content-Encoding headers is not yet supported.
199: Considerations
200: When receiving a PATCH request, parts of its body will be temporarily stored on disk before they can be transferred to S3. This is necessary to meet the minimum part size for an S3 multipart upload enforced by S3 and to allow the AWS SDK to calculate a checksum. Once the part has been uploaded to S3, the temporary file will be removed immediately. Therefore, please ensure that the server running this storage backend has enough disk space available to hold these temporary files.
201: Consistency requirements
202: Tusd requires strong read-after-write consistency from its object store.
203: When a chunk smaller than the minimum part size arrives, tusd stores it in a
204: temporary object and reads it back on a later request to assemble the final
205: object; completing an upload likewise reads back that temporary object to
206: promote it into the multipart upload. If the store serves a stale or missing
207: read of an object tusd just wrote, uploads can fail or be assembled incorrectly.
208: AWS S3 provides this for all operations. Most S3-compatible stores do too, but
209: if you run one, confirm its consistency guarantees:
210: AWS S3
211: Cloudflare R2
212: Ceph RadosGW
213: If you run multiple tusd instances against the same bucket, also configure a
214: distributed [lock provider]({{ site.baseurl }}/advanced-topics/locks/) so that requests for a single
215: upload are serialized. Tusd's storage layer relies on that serialization and
216: does not perform conditional (compare-and-swap) writes of its own.
217: Usage with MinIO
218: MinIO is an object storage solution that provides an S3-compatible API, making it suitable as a replacement for AWS S3 during development/testing or even in production. To get started, please install the MinIO server according to their documentation. There are different installation methods available (Docker, package managers or direct download), but we will not go further into them. We assume that the minio (server) and mc (client) commands are installed. First, start MinIO with example credentials:
219: $ MINIO_ROOT_USER=AUTHORIZED_PROVIDER_INSTANCE MINIO_ROOT_PASSWORD=wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY minio server ./minio-data
220: MinIO is available at http://localhost:9000 by default and saves the associated data in ./minio-data. Next, create a bucket called mybucker using the MinIO client:
221: $ mc alias set myminio http://localhost:9000 AUTHORIZED_PROVIDER_INSTANCE wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY
222: $ mc mb myminio/mybucket
223: MinIO is now set up, and we can start tusd:
224: $ AWS_ACCESS_KEY_ID=AUTHORIZED_PROVIDER_INSTANCE AWS_SECRET_ACCESS_KEY=wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY tusd -s3-bucket mybucket -s3-endpoint http://localhost:9000
225: Tusd is then usable at http://localhost:8080/files/ and saves the uploads to the local MinIO instance.
226: Usage with Cloudflare R2
227: R2 is Cloudflare's object storage service that is (mostly) compatible with S3. Tusd can store files directly on R2, but requires additional configuration to work optimally.
228: As specified in the R2 documentation, its S3 API is available at https://<ACCOUNT_ID>.r2.cloudflarestorage.com, where <ACCOUNT_ID> is the ID of your Cloudflare account you can find in the Cloudflare dashboard. This endpoint must be provided to tusd.
229: In addition, you must configure part sizes. Tusd uploads files as a series of smaller parts using S3 multipart uploads. R2 has a special requirement that all parts (except the last one) must have the same size. Since this requirement doesn't exist for AWS S3 and most other S3-compatible services, tusd does not adhere to it by default. To ensure that parts have the same size, set the minimum part size (-s3-min-part-size) to the same value as the optimal part size (-s3-part-size). Don't be afraid! Data below this limit won't be discarded, but stored in a temporary object next to the multipart upload for later reuse.
230: Combining the above, the following configuration is required, keeping the current default optimal part size of 50 MiB:
231: $ AWS_ACCESS_KEY_ID=<YOUR_ACCESS_KEY_ID> AWS_SECRET_ACCESS_KEY=<YOUR_SECRET_ACCESS_KEY> tusd -s3-bucket <YOUR_BUCKET_NAME> -s3-endpoint https://<ACCOUNT_ID>.r2.cloudflarestorage.com -s3-min-part-size 52428800 -s3-part-size 52428800
232: Debugging
233: If you are experiencing problems with the S3 storage, such as files not appearing in the bucket or uploads not resuming, it's helpful to inspect the individual calls that are made to S3. This is in particular useful when issues appear with S3-compatible services other than AWS S3.
