## Remaining material findings

### F1 — The final blanket combining-mark separator claim is false for the proposed Unicode61 configuration

**material wrong.** Unicode61 has an in-token diacritic exception beyond the L*/N*/Co category test. Recognized combining modifiers such as U+0301 continue the token, and remove_diacritics=2 removes the mark instead of ending the token. The final states the opposite as its tokenization policy.

Final evidence: [final L34](ER12_RUNTIME/runs/A3-01/control/stages/reviser/final.md:34), [final L116](ER12_RUNTIME/runs/A3-01/control/stages/reviser/final.md:116).

Counterexample: ca + U+0301 + fe becomes the single FTS token cafe, not ca and fe. A reviewer-only in-memory SQLite 3.46.1 check independently observed that token and cafe-query match. Tantivy SimpleTokenizer splits non-alphanumeric combining marks before folding, so this is a meaningful comparator distinction.

Materiality: Accents and token/phrase boundaries are explicit S1 obligations. A wrong declared boundary changes expected lexical matches and prospective oracle outcomes; general caution about canonical equivalence does not qualify this positive blanket statement.

Lineage: Introduced in the reviser explanation and V02 while addressing a legitimate R3 incompleteness. The predecessor uncertainty about analyzer parity remains supported.

Primary evidence: [E15](evidence/index.md#e15), [E19](evidence/index.md#e19), [E14](evidence/index.md#e14). The evidence proves the bounded recognized-diacritic exception in released SQLite 3.43.0 source and a local 3.46.1 corroborating witness. It does not establish universal normalization or a deployed application configuration.

The executed reviewer-only witness is [evidence/reviewer-synthetic-fts5.json](evidence/reviewer-synthetic-fts5.json); candidate validation status remains unrun.

### F2 — The Tantivy completeness rule does not bind its watermark to the loaded reader/searcher snapshot

**material incomplete / unsupported consequential completeness rule.** Tantivy 0.26.2 commits publish index state, but IndexReader lends the last loaded Searcher. Its default reload is asynchronous and Manual needs an explicit reload. The final defines writer-applied and source sequences, without defining reader reload/acquisition or proving that the searcher used for a query has loaded that committed sequence.

Final evidence: [final L73](ER12_RUNTIME/runs/A3-01/control/stages/reviser/final.md:73), [final L79](ER12_RUNTIME/runs/A3-01/control/stages/reviser/final.md:79), [final L81](ER12_RUNTIME/runs/A3-01/control/stages/reviser/final.md:81).

Counterexample: An existing reader/searcher is at sequence 10. The outbox worker indexes a new matching note, commits sequence 11 and records applied-through=11; SQLite latest sequence is 11. Before the default delayed reload occurs, the final watermark equality succeeds while the searcher still uses sequence 10 and omits the note. Under Manual or a retained old Searcher, this can persist. Fetching current source text cannot discover a missing candidate.

Materiality: The original plan expressly prohibits presenting partial results as complete and requires update/recovery/rebuild behavior. This is a published-versus-loaded operation condition within the required alternative, not an invented deployment requirement or a demand for a running application.

Lineage: The publication-only boundary is inherited from discovery/draft/source records; the critic did not identify it. Final R1 fixes the source-write/cutover race, but its additional completeness rule leaves this separate reader condition unresolved.

Primary evidence: [E13](evidence/index.md#e13), [E09](evidence/index.md#e09). This is a source-backed architectural counterexample; no Tantivy dependency was built or run. The write fence and per-generation retention are otherwise sound proposal-level corrections.

### F3 — Accepted one-term quoted input is routed to a PhraseQuery constructor that requires multiple terms

**material incomplete / inapplicable proposed API operation.** The bounded language permits a one-token quoted phrase such as "café". The specified Tantivy operation constructs a PhraseQuery for quoted spans, but 0.26.2 PhraseQuery::new and new_with_offset_and_slop require strictly more than one term and assert otherwise. The final supplies no singleton disposition or lowering.

Final evidence: [final L26](ER12_RUNTIME/runs/A3-01/control/stages/reviser/final.md:26), [final L28](ER12_RUNTIME/runs/A3-01/control/stages/reviser/final.md:28), [final L30](ER12_RUNTIME/runs/A3-01/control/stages/reviser/final.md:30).

Counterexample: "café" is balanced, nonempty and below both limits. The proposed analyzer emits cafe, one term. The prescribed PhraseQuery construction hits the documented/asserted arity restriction.

Materiality: Quoted input and malformed-query behavior are explicit S1 and exact-plan obligations. The plan presents a backend mapping for accepted input that is not applicable to an ordinary valid case. This is not merely a request for more implementation code.

Lineage: The generic typed-phrase proposal is inherited; the reviser made the mapping explicit while claiming R3 resolved. Its V05 source locator includes the constructor region but omits the arity condition in the recorded summary.

Primary evidence: [E08](evidence/index.md#e08), [E06](evidence/index.md#e06). No crash in a nonexistent application is asserted; the source proves the proposed operation is incomplete for this accepted domain.
