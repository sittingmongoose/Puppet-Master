### Staged asset mirror

The tool mirrors a completed build's asset directory into a receiver staging directory using rsync 3.2.7 on both peers. The declared controls are `protected_dir=local-notes`, `publish_mode=explicit`, and `preview_required=true`. Source and destination are selected operator-visible paths, and the stage remains unpublished until the tool reports completion. Transfer completion and publication are separate events: under `publish_mode=explicit`, a successful rsync exit only marks the stage as received and intact; the stage becomes live only through a separate, explicitly triggered publish step. rsync performs no publication, and the tool must not collapse the two steps into one automatic action.

The source argument keeps its trailing slash so the directory's contents become direct children of staging. The rsync 3.2.7 manual states that a trailing slash on a source means "copy the contents of this directory" rather than "copy the directory by name," avoiding an extra directory level at the destination; dropping it would nest the tree one level too deep. Obsolete received assets are removed inside synchronization scope with recursive transfer and --delete, which deletes "extraneous files from the receiving side (ones that aren't on the sending side), but only for the directories that are being synchronized." Excluding local-notes/ protects it: excluded files "are also excluded from being deleted" unless --delete-excluded is used. The proposed --delete-excluded is therefore removed — it "turns any unqualified exclude/include rules into server-side rules that do not affect the receiver's deletions," so the destination local-notes directory would lose its protection and be treated as extraneous.

Because `preview_required=true`, the deletion preview is mandatory, not optional. The tool runs --dry-run ("perform a trial run with no changes made") with the identical --delete and filter set, listing every pending deletion for inspection before the destructive run; exclusions limit what can be deleted but never make the preview optional. A preview is an inspection, not a lock: it observes the trees at preview time, and either peer can change before execution, so the tool re-runs the identical preview immediately before the destructive run and treats that final pass as binding. As a guardrail, --max-delete caps removals; when the cap is hit, "all further deletions are skipped through the end of the transfer," rsync warns with a skipped-deletion count and exits 25, and --max-delete=0 warns about extraneous files without removing any.

--delay-updates "puts the temporary file from each updated file into a holding directory until the end of the transfer, at which time all the files are renamed into place in rapid succession," which the manual calls only "a little more atomic." Each rename is per file; no whole-tree transaction exists, and per-file behavior implies nothing about atomic publication. On cancellation or failure the run stops, partial data stays in hidden temporary state (.~tmp~ holding directories), the diagnostic is retained, and the stage is reported interrupted or failed and never published; a later run reuses or cleans the temporaries.

Three prospective checks, none yet executed: (1) source contents land as direct children of staging at the intended depth; (2) an asset removed at the source disappears from staging within scope; (3) a pre-existing destination local-notes/ survives the delete pass. Evidence still needed: an isolated fixture run against rsync 3.2.7 peers; filter behavior when local-notes exists on both peers; observed --delay-updates and --delete ordering under interruption. The supplied commands remain illustrative and unexecuted.

## Disposition of received critique

1. **Accept.** --delete-excluded defeats the exclusion-based protection: "Files that are excluded from the transfer are also excluded from being deleted unless you use the --delete-excluded option," and with --delete-excluded an unqualified rule "turns ... into server-side rules that do not affect the receiver's deletions." Fix: keep the plain exclude of local-notes/ and drop --delete-excluded. (rsync 3.2.7 manual, --delete and --delete-excluded sections.)
2. **Reject.** Restoring deleted notes "from memory" is not a primary-documented control and would delete the required preview obligation (O4, `preview_required=true`). The manual itself provides inspectable, non-destructive alternatives: --dry-run is "a trial run with no changes made," and --max-delete=0 warns about extraneous files "without removing any of them." The preview requirement stands.
3. **Accept.** Publishing immediately on rsync success violates `publish_mode=explicit` and O5's separation of transfer completion from the explicit publish step. The atomicity claim is corrected: --delay-updates makes all files "renamed into place in rapid succession," which the manual calls only "a little more atomic" — per-file renames, not a whole-directory transaction, and no atomicity is claimed from per-file behavior.
4. **Reject.** The manual is explicit that the trailing slash changes semantics — "copy the contents of this directory" as opposed to "copy the directory by name" — and O1 requires the contents at staging's top level. --delete additionally requires the whole directory as source (e.g. "dir/"), not a shell-expanded wildcard. The trailing slash stays.
5. **Accept, qualified.** Correct that the preview and the destructive run can observe different trees and that rsync documents no lock. Adopted: re-run the identical preview immediately before execution and treat the final pass as binding. Qualified because the draft did not explicitly claim a lock; this is a new control added on the critique's evidence, not a correction of a stated claim.
6. **Reject.** The manual defines --delete as deleting "extraneous files from the receiving side (ones that aren't on the sending side)," exactly matching corpus S1's verbatim excerpt. Deletions are receiver-side; the destination local-notes directory is precisely what the protection must cover, so the critique's premise is wrong.
