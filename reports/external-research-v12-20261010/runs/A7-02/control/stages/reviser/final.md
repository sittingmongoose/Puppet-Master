# Research proposal — volunteer reading-list curation

**Run:** A7-02-control · **Stage:** reviser · **Scope:** the complete brief plus the exact plan copy released to this stage. This proposal is not an implementation or a product test. **Evidence labels:** observed external behavior is what a public source or release record states; inference is this reviser’s interpretation of that evidence; local product choice is a recommendation for this group. Public source identities, exact URLs, versions/commits, locators, access UTC, observed operations, governing conditions, and applicability are indexed by stable IDs in [`sources/index.md`](sources/index.md) and [`source-map.json`](source-map.json).

## Recommendation

Run a small, local-only curator pilot around a review queue and retained bibliography ledger. Zotero is the first workflow to test for volunteer-facing curation because its documented duplicate collection and field-level merge are approachable; JabRef is a viable alternative for a Bib(La)TeX-oriented editor and exposes useful fuzzy candidates, per-field merging, and identifier-based enrichment. Do not choose a product until the group tests the required cases on a pinned release. Neither product’s ordinary merge alone meets the brief’s provenance requirement.

Represent **a citable record** separately from a **work/version relationship** and from the **submission that contributed it**. Preserve verbatim citation text and credited submitter data as immutable submission rows. Each paper/version record receives a local stable ID even with no DOI. Store bibliographic fields in a separate reviewed record, with per-field provenance: submitted value, lookup source/provider, lookup time, status (`suggested`, `accepted`, or `rejected`), and editor decision. Preserve the older value and the source attribution when the editor approves a correction. Keep a duplicate decision and a version relationship distinct: merge only two entries confirmed to describe the same citable manifestation; connect a preprint and a journal article with a reviewed relationship while retaining two records. If uncertain, keep both and flag the candidate for the next editorial review.

A practical monthly flow is:

1. Receive the citation text and submitter credit without demanding an account. Save the original text unchanged and create a submission ID.
2. Parse fields into a candidate record, keeping the raw submission alongside it. Capture any identifier or stable citation URL the submitter supplied. A missing identifier is allowed.
3. Generate duplicate suggestions from several signals. Present the evidence and conflicting fields; do not merge on normalized-title equality alone or on DOI alone. The editor can accept a same-record merge, reject it, or keep both. Save the decision, selected field values, and related submissions.
4. Offer a lookup only as a proposal. Show provider, retrieval time, matched identifier, returned fields, and any competing results. The editor chooses whether each field replaces or supplements the current reviewed value. A no-match result keeps the record and opens a manual-citation path.
5. Mark status and relationships explicitly (`preprint`, `journal article`, other type; `is-preprint-of`, `version-of`, or an unresolved candidate). Do not collapse related outputs.
6. Publish the citations and links using the group lead’s chosen style. If the pilot passes the tests below, also offer an opt-in `.ris` file containing the approved public citation list only. Never export/download article files.

These are proposed local design decisions, not features we observed in a product. Keep the editorial ledger as the record of submissions and decisions, even if Zotero or JabRef is used to help review or export it.

In particular, a DOI should be recorded and used as strong match evidence for a registered metadata record, not assumed to uniquely identify every scholarly version. A DOI-less citation remains publishable as a locally identified record. Where a stable repository ID such as an arXiv ID is known, preserve its exact form/version as submitted; otherwise the citation text and URL remain sufficient to retain and review the item. Title/creator/year similarity can suggest a duplicate, but two editions, conference/journal versions, and preprint/publication pairs can have highly similar text. Keep separate records for a known preprint and journal article and add a reviewed version edge, even if a provider proposes a connection. Crossref’s matching approach itself reports incomplete deposited links, so no discovered edge is not proof that two outputs are unrelated [S18–S19].

## Optional identifier enrichment

An account-free option exists for an approved pilot: Crossref states that public REST API access needs no signup and exposes DOI lookup plus query/search for metadata deposited by Crossref members [S13–S14](sources/index.md#s14). For a DOI already on a citation, retrieve that DOI’s Crossref record. For an incomplete citation without DOI, a broad bibliographic search can produce candidate records; retain the original citation and compare its title, creators, year, type and any venue before presenting the result. JabRef describes lookup by DOI, ISBN, and attempts to find DOI/arXiv identifiers, but explicitly notes that lookup can fail when the input is incomplete or inaccurate [S08].

Treat each response as evidence only: retain provider, request/record URL, access time, identifier, returned field values and any competing match. Do not auto-replace a submitted title, author list, year or record type. The editor decides field by field, with both prior and accepted values kept. A null result means “this provider did not supply a match,” not “the work does not exist.” **Observed:** Crossref’s API exposes records registered with Crossref members and trusted sources [S13]. **Inference:** Crossref-only lookup cannot cover every scholarly object, so a no-match cannot establish that a citation is invalid. Crossref advises caching, monitoring status and honoring rate/concurrency headers; a 429 requires backoff. A polite request includes an email in `mailto` or the agent header, while public access requires no identification; the group lead must choose whether that email disclosure and this provider are acceptable [S14–S15]. Do not use the premium/paid Metadata Plus path in the pilot.

## Versioned import/export failure and applicability

A released JabRef issue offers a useful, bounded page-range example. On 2026-02-13, an issue reporter using **JabRef 5.15 on GNU/Linux** described importing/opening a BibTeX record with `pages = {13905--13911}` and exporting it as RIS. The reported output put the full range in both `SP` and `EP`; the reporter said a single ASCII hyphen worked [S11](sources/index.md#s11). Pull request #15315 extended range parsing to Unicode en-dash/em-dash and merged to `main` on 2026-03-13 as commit `d687c08` [S12](sources/index.md#s12). Raw source at that commit splits ASCII hyphen, en dash and em dash; `FirstPage`/`LastPage` unit fixtures cover single and double ASCII hyphens, en/em dashes, and a spaced en dash [S21](sources/index.md#s21). JabRef v6.0-alpha.6, commit `6d24100`, released 2026-05-14, explicitly lists issue #15106 as fixed; the later inspected v6.0-beta.1 is a prerelease [S20](sources/index.md#s20), [S10](sources/index.md#s10).

The affected data are the RIS start/end page fields for the reported range spelling; this history does not establish that all JabRef versions, all page encodings, or all RIS fields fail. There is a useful scope nuance: the issue’s sample is BibTeX double-dash syntax, and the release note confirms the original issue ID as fixed; the PR’s tests are page-formatter unit tests rather than a complete RIS export. No end-to-end RIS export or unit test was run for this proposal. A proposed pilot must therefore use the exact pinned build and exercise double dash, single hyphen, Unicode en/em dash, and any normalization performed between BibTeX input and RIS output, with expected `SP=13905`, `EP=13911`.

## Optional public bibliography export

Retain the brief-authorized option and make it opt-in for the pilot. Offer `.ris` for common reference-manager interchange when the chosen product/version passes an import/export fixture; Zotero documents RIS import and Quick Copy/export paths [S02–S05], and JabRef’s export history demonstrates an actual RIS workflow and why version checks matter [S11–S12, S20]. The file should contain the month’s approved citations only, preserve title/creators/year and available DOI plus resolvable publisher/repository URL, and label preprint versus journal item in a field supported by the chosen mapping. Do not attach or retrieve full text. A separate rendered public bibliography can use the group lead’s style.

This file is an option, not a mandatory service or a technical capability established by this research. Interchange formats have different field coverage: Zotero cautions that export/import loses information and that RIS does not preserve collections or attachments [S04]. Thus keep the source ledger, original submission, field provenance, merge history, and typed version relations inside the curation system; do not promise that RIS round-trips them. If required public fields fail the pilot fixture, correct the mapping or offer a verified alternative format while keeping the authorized scope visible; do not exclude the option without that evidence.

## Corrections, optional improvements, retained coverage and open inputs

**Corrections to make:** reject title-string normalization as merge authority; reject automatic field replacement from a DOI; remove the proposed no-identifier exclusion; add a manual path; replace a generic import demo with a version-specific regression test; keep publisher metadata as evidence rather than presumed editorial truth. These correct the released draft’s assumptions without changing the pilot’s source or publication boundary.

**Optional improvements:** add provenance for every normalized/corrected field; record merge/reject decisions and alternatives; show the evidence used for candidate ranking; permit explicit preprint-to-journal relation suggestions; provide a no-match queue; use an optional RIS download after fixtures pass. None is a new mandatory user-facing feature except where needed to satisfy the brief’s original merge, correction and preservation obligations.

**Owner decisions still required:** (1) the group lead’s citation display/presentation style; (2) which lookup provider(s) are acceptable and whether a polite-pool contact email may be used. The bibliography editor already has authority under the brief to approve every merge/correction. Submitters already retain credit and original citation text. Those assigned roles are not reopened here.

**Already covered and retained:** the plan accurately keeps downloadable bibliography within authorized optional scope; the specified owner role and credit language; and all four negative constraints. This proposal adds evidence, explicit behavior and validation conditions to make those statements actionable.

**Rejected:** silent merge on normalized title; automatic authoritative overwrite based on DOI; treating missing DOI as exclusion/ineligibility; any action that conflates a preprint with the later journal article; optional file export without format verification; downloading or attaching full texts; creating contributor accounts; treating the interchange file as the archival provenance record.

**Uncertain and to verify before choice:** Zotero’s duplicate page was last updated 2017; current app algorithm and false-positive controls need checking on a pinned release [S01]. Zotero field mapping is also an older living document; test current exported fields [S04]. Current JabRef documentation pages are living and not all release-pinned; the 6.0 version inspected is a beta [S10]. Crossref relation/coverage completeness varies by deposit; no-match or missing relation remains inconclusive [S13, S17–S19]. RIS’s preservation of a particular preprint label or relation must be tested in the chosen producer/consumer pair; no source here establishes an end-to-end result.
