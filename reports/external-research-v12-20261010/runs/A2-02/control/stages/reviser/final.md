# Final proposal — Portable reading-room annotation workspace

Run: A2-02-control · Stage: reviser · Status: complete research proposal; no product validation was run.

## Recommendation

Plan a 100-page pilot around a separately governed annotation store that references collection materials in place. Use IIIF Presentation API 3.0 where a source already provides it. If inventory finds Presentation API 2.1.1, accept it through a read-only, version-aware adapter and set an explicit export route before records are authored. Keep the collection’s manifest, catalogue, image master, and image delivery at the collection. A viewer is a client of the pilot; it is not the identity authority or the durable annotation store.

Each annotation should identify a curator-approved page ID and the relevant versioned presentation target, normally a Manifest and Canvas URI. Store whole-Canvas notes and rectangular selectors in the Canvas coordinate space, together with Canvas dimensions and source-version evidence. Render by mapping that geometry into the currently delivered image only when the source-to-Canvas correspondence is still valid. A stable Canvas URI alone does not establish that the image content is unchanged. Where a collection publishes no reliable content-version signal, label the revision **unknown**, preserve the evidence observed at capture, and require curator review when the source changes or before an uncertain re-anchor. Never silently move a note across a crop, rotation, changed content, or changed page identity.

Compare pinned Mirador and Universal Viewer builds against the same authorized pages and records. Mirador is the stronger first candidate when multi-up comparison is central; the documented annotation-matrix result is limited to one cookbook recipe. Universal Viewer is a useful broad, embeddable viewing comparison; the same matrix does not document that recipe for UV. Neither result proves the complete authoring, storage, import, or export path. Treat Annotorious with OpenSeadragon as a separate image-annotation integration option if the viewers do not meet a required interaction. Keep all feature claims version- and scenario-specific.

Retain a downloadable transcription-only bundle as an authorized **optional** path, conditional on rights, access, transcription provenance, and the user’s authorization. It may contain selected transcription text and a small page/provenance index, but no source images. It is a proposed pilot capability, not an established viewer feature. Do not make it mandatory.

## Pilot design

### Page identity, geometry, and source revision

The collections curator owns the stable page identifier and any mapping from that identifier to collection Manifest and Canvas revisions. Keep that identifier independent of page labels, order, current image URL, and viewer state. For each annotation, retain at least:

- curator-approved page ID and any curator-approved alias/crosswalk;
- collection and catalogue references needed to return to the source;
- Manifest URI, declared Presentation API version, Canvas URI, Canvas width and height, and the relevant image or Image API service identifier;
- annotation body, selector type and value, coordinate basis, author/provenance, timestamps, and access state;
- source revision state: collection-published revision/checksum when available; observed validators and access time when available; a digest of the retrieved Manifest representation and relevant image-information description when authorized; otherwise an explicit **unknown** state.

These capture and comparison fields are a local design proposal, not a IIIF feature or a product check. Retain only the page-level evidence needed for the pilot; do not mirror collections or image masters. A digest of a Manifest or image-information response can show that the observed description changed, but it cannot prove that image pixels did not change behind an unchanged URL and unchanged metadata. A transport validator or timestamp is useful evidence when supplied, not a curator-owned page ID or a guaranteed content history. If the collection exposes no revision marker, checksum, or other reliable change record, do not infer “unchanged” from a stable URI or equal dimensions.

For a rectangular note, store a rectangle relative to the target Canvas, with its Canvas dimensions and source evidence. Transform those coordinates for display at the current image’s resolution. IIIF’s differing-dimensions recipe supports a stable Canvas space across a replacement image when the aspect ratio is consistent; it warns that inconsistent ratios produce unpredictable distortion [S7]. The W3C media-fragment form provides rectangular xywh selectors, but client support still needs testing [S4, S5]. Percent geometry may aid a same-content resize, but does not repair a crop or altered page. Preserve numeric precision and avoid automatic remapping if aspect ratio, orientation, image reference, manifest representation, or content evidence changes.

At intake and on later read-only preflight, compare the captured evidence with the currently available Manifest and image-information description when access permits. Changed identifiers, dimensions, service URLs, orientation, or retrieved-representation digest set the record to **needs review**; a missing or inaccessible source sets it to **unavailable/needs review**, not to a copied substitute. A changed image with no observable metadata change remains undetectable unless the collection supplies an authoritative version signal. Ask the curator to confirm the mapping or provide an approved crosswalk before re-anchoring. Keep the prior target and revision evidence in the annotation history so a reviewer can see what changed.

A page-level note may target the Canvas without a selector. The IIIF Cookbook warns that clients may show no visual cue for a whole-Canvas target; a full-area selector may be more widely supported [S8]. Test both representations in each pinned viewer. A transcription can be a structured text body associated with a page or region; preserve language and format where known. Keep transcription, commentary, and region association distinct in the local model and export.

### Manifest versions, external images, and data exchange

Presentation API 3.0.0 is the current stable release shown by the specification; 2.1.1 is its previous version [S1, S2]. Inventory the 100 authorized pages before selecting adapters. Prefer native v3 inputs where already supplied. If an input is v2, parse it read-only using its v2 structures, such as Sequence, Canvas, AnnotationList, Layer, resource, and on. Do not treat v2 JSON as v3 or discard structures during normalization.

For a v2-origin page, the proposed reuse choices are explicit: export a separate v2-compatible annotation sidecar/package when the intended consumer requires Presentation 2.1.1, or convert to a separately labelled v3/Web Annotation export when the receiving client accepts that representation. Set this route with the pilot team before authoring; preserve the source version and conversion record. Keep both outputs separate from the collection’s manifest and catalogue. If an input field, selector, body, layer, provenance field, or target cannot be represented in the selected output, retain the source evidence and block that export with a field-level loss report. Do not claim a lossless round trip until representative versioned fixtures pass. If no v2 consumer or input exists, do not build v2 export merely for symmetry; record the inventory result and the chosen output contract.

For v3, use AnnotationPage/Annotation structures and W3C Web Annotation selectors and text bodies as appropriate. IIIF’s v3 change log records the adoption of Web Annotation, the id/type renames, and replacement of AnnotationList/Layer with AnnotationPage/AnnotationCollection [S3]. This is a real compatibility boundary even though the change log characterizes some practical effects as limited. Make import/export version explicit. Keep an untouched source copy reference and do not overwrite a collection manifest. Maintain a separate annotation store and export package so import and export do not modify source masters or catalogues.

Remote image delivery is an external dependency, not something annotation syntax can solve. For each authorized collection, check the Manifest and Canvas references, image service/profile and advertised features, browser CORS access, authentication, rights, URL stability, and actual availability. The Image API documents distinct unauthorized, forbidden, missing, and service-unavailable responses, and recommends CORS for browser access [S6]. Report unavailable or restricted images accurately; do not fetch or copy masters to bypass access. A non-IIIF fallback is eligible only if the curator approves its page identity and the pilot records usable dimensions and coordinate basis; until tested, do not promise zoom, selectors, or cross-viewer behavior for it.

### Compatibility history and pilot consequences

The IIIF Presentation 2.1.1 to 3.0.0 transition changes annotation structures and names, so a v2/v3 mismatch can affect Canvas/page ordering, annotation lists/layers, targets, and transcription bodies on import and export [S2, S3]. Use source-version fixtures and report unsupported or lossy fields rather than describing migration as cosmetic.

A second, bounded history affects finding notes. Mirador issue #4198 reports that annotation/layer notification dots were missing in Mirador 4. PR #4201 merged the badge repair. The PR head is 056262a; its merge commit is 25c0b0e (2025-12-04). A direct GitHub compare of 25c0b0e to the v4.2.4 tag commit 73fafe9 reports the merge commit as the merge base, 354 commits ahead and zero behind; that establishes the fix commit is in the v4.2.4 history [S14–S16, S22]. Thus the prior release-inclusion claim is confirmed by commit ancestry, not by a release-note mention. It affects discovering pages with annotations, so test the badge and opening existing notes in the selected build. This source-history check does not establish the UI works in the pilot or that authoring plugins are compatible.

The Mirador 4 announcement describes breaking framework/plugin changes; the old plugin’s own README says it does not work with Mirador 4 and requires an annotation server for durable persistence [S12, S13]. Universal Viewer’s release list is mutable and includes two “DO NOT USE” tags, so use a fixed tested release rather than a floating tag [S17]. These are reasons to pin versions and test each integration, not reasons to promise or exclude a feature without the pilot check.

### Optional transcription-only bundle

Retain this as an authorized option and decide whether to offer it only after rights and access review. IIIF’s transcript recipe describes a rendering link as one way to point to a downloadable text, while distinguishing that pointer from an implemented download interface and from synchronized or Canvas-associated transcript annotations [S9]. The text-on-Canvas recipe distinguishes visible painted transcription from commentary/supplementing content and cautions that rendering varies by client [S21].

Proposed export: selected UTF-8 text, either one file per page or one concatenated file, plus a small index containing curator page ID, page label, source Manifest/Canvas URI and API version, transcription language, provenance/status (manual, OCR, or unverified where known), and encoding. Preserve line breaks and scholarly characters. Include no image bytes or collection-wide data. Offer only where the transcription and its export are permitted; honor note privacy and the owner-approved access model. Make clear if text is unverified. A rendering link may advertise the bundle if useful, but does not create the download capability. There is no evidence-based reason in the reviewed sources to remove this option; if later excluded, document the particular rights, access, or interoperability evidence.

### Owner decisions and hard boundaries

- The **collections curator** approves stable page identifiers, source-to-page mappings, and any changed-ID or changed-image crosswalk. Viewer order, labels, and current URLs do not decide this.
- The **reading-room lead** chooses whether notes are private by default and who may view, edit, export, or publish them. Recommend private-by-default for discussion, but treat it as unapproved until the lead decides. A viewer default or public Manifest is not authorization to publish scholars’ notes.
- The pilot team chooses the required v2/v3 consumer contract, annotation store, viewer/plugin, unsupported-field policy, retention/backup approach, and export rights after inventory and owner input.

Binding negative constraints: do not copy entire collections; do not alter image masters or existing descriptive catalogues; do not promise that all viewers share every annotation feature; and do not require public publication of notes. Store only pilot annotation records and the minimum source references/evidence needed. Any sharing or publication requires an explicit, authorized action under the owner-approved privacy policy.

## Alternatives and delivery sequence

1. **IIIF adapters where already available — recommended pilot route.** Use existing Manifest/Canvas data, with version-aware readers and a separate annotation model. This does not assume every collection has a compatible manifest, public service, or accessible image.
2. **Viewer-provided authoring.** Consider only after selecting a fixed viewer and compatible extension. The Mirador 3 plugin is not a Mirador 4 solution. Persistence and authorization are separate requirements.
3. **Custom OpenSeadragon/Annotorious panel.** Consider if both viewers miss a required interaction. Budget for mapping, Canvas-coordinate conversion, W3C/body/selector adapters, persistent storage, access control, and conversion tests.
4. **Non-IIIF input.** Do not automatically reject it. Include only when the curator approves a stable page reference and the pilot can preserve coordinate dimensions and rights/access; otherwise record a specific unsupported reason. Do not mirror source collections as a workaround.

Proposed sequence: (1) obtain the curator’s authorized 100-page list, stable IDs, source versions, rights and known image revisions, and the reading-room lead’s privacy decision; (2) inventory remote references, versions, Canvas dimensions, auth/CORS and observed revision signals; (3) choose the v2/v3 export contract and pin viewer/plugin builds; (4) test representative whole-page and rectangular notes, imports, edits, save/reload, exports, resize and changed-source review in both viewers; (5) test text-only output independently; (6) expand to 100 pages only after required owner decisions and representative checks pass. A failed case becomes a documented limitation or a revised design, never silent data loss or coordinate movement.
