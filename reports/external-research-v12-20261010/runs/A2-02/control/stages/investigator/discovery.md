# Independent discovery — portable reading-room annotation workspace

Run: A2-02-control; stage: investigator. This discovery was formed from the released brief alone before the exact plan was released. Sources are indexed by immutable IDs in [sources/index.md](sources/index.md) and described in [source-map.json](source-map.json). Source retrieval and documentation review are research evidence, not product validation.

## Initial recommendation and boundaries

Treat IIIF Presentation API manifests and Canvases as a strong interoperability route where a collection already exposes them, while avoiding a pilot-wide assumption that every collection has a compatible manifest, image service, CORS policy, or viewer behavior. Keep collection catalogues and image masters at their sources. Store researcher annotations in a separate reading-room store keyed to collection-curator-approved page identifiers and the source Canvas URI where available. Import and export through explicit version-aware adapters. Preserve original manifest references and API version as provenance. Do not rewrite source manifests or image resources.

For a portable rectangle, use a stable Canvas coordinate space and a selector anchored to its Canvas, with source dimensions and image/Canvas version context captured alongside it. A Canvas need not have the current image’s pixel dimensions: IIIF’s differing-dimensions recipe explains that annotations can retain their positions when a replacement image has other pixel dimensions, provided the aspect ratio remains consistent. This protects against delivery resizing; it does not solve a crop, rotation, replacement of page content, changed page identity, or a source whose geometry changed. Those cases need a version/review and curator-approved re-anchoring. Do not use sequence index or label as identity.

For the note body, use UTF-8 text and a structured Web Annotation body, with page-level or rectangular targets. Keep a readable text export separate from the image resources. Make privacy an explicit owner decision; recommend private-by-default as the product choice for discussion, without silently deriving that setting from a viewer or public IIIF behavior.

## Findings against the original obligations

### 1. Identity, region coordinates, and portability

Presentation 2.1.1 and 3.0 both model each page/view as a Canvas with a URI. In v3, a Canvas URI must have no fragment so a region can be expressed separately; the specification’s URI guidance says published identifiers should be persistent and unchanging as far as possible [S1, S2]. The collections curator therefore owns the stable page identifier. Store that identifier independently from labels, page number, manifestation order, and image URL. Also retain source collection/catalogue URI, Manifest URI, Canvas URI, API version, source Canvas dimensions, image-service identifier, and the accessed manifest revision or retrieval timestamp. Use a curator-managed alias/crosswalk only when a collection later changes an identifier; never silently bind a new Canvas to old notes.

IIIF Canvas dimensions define a coordinate space and may differ from the delivered image’s pixel dimensions. The cookbook recipe demonstrates a larger Canvas so annotations on a current smaller image remain positioned on a replacement, with an aspect-ratio constraint [S7]. Store target rectangles against the Canvas (or as normalized geometry plus the Canvas dimensions from which it was derived); translate them for rendering at the current image size. For W3C Web Annotation export, use a SpecificResource/FragmentSelector with an `xywh` value and the media-fragment conformance link [S4, S5]. Preserve the numeric geometry and its coordinate basis instead of rounding away the source values. A separate capture of source width, height, orientation, and image/Canvas revision makes later remapping reviewable. A normalized percentage/ratio is helpful for same-content rescaling, but it cannot repair a crop, changed orientation, new recto/verso image, or cataloguer’s changed page identity. For meaningful manuscript coordinates, avoid auto-rescaling until aspect ratio and correspondence are checked.

A full-page note may target a Canvas without a selector. The IIIF recipe warns a viewer may omit any visible cue for a whole-Canvas annotation; a full-area selector may be more widely supported [S8]. Include this in the pilot’s acceptance checks.

### 2. Two viewers and an analogous annotation mechanism

The IIIF viewer overview describes Mirador as a multi-up viewer for displaying and comparing images; the Universal Viewer (UV) is an embeddable viewer spanning IIIF images, audio/video, and non-IIIF 3D/PDF experiences [S11]. They are useful alternatives for different pilot priorities: Mirador’s side-by-side manuscript comparison versus UV’s broader collection presentation. The IIIF Cookbook’s per-recipe matrix is a practical warning against treating either viewer as a universal annotation contract: for its simple annotation-tagging recipe, the current matrix marks Mirador “Yes” and UV “No” [S10]. That row is a recipe-specific result, not proof that UV cannot display any annotations. Test the exact page, selector, body, and API version the pilot needs.

Separate viewer display from annotation authoring and persistence. The Mirador 3 `mirador-annotations` plugin provides rectangle, oval, polygon, and text-descriptor authoring; its live example uses local storage, and durable persistence requires an annotation server. The project’s README explicitly says this plugin does not work with Mirador 4 [S13]. Mirador 4’s launch notes list breaking framework/plugin changes and point to community Mirador 4 annotation plugins as separate integrations [S12]. Thus those editors are not a built-in, version-independent guarantee. UV is a capable content viewer, but research here did not establish it as the pilot’s authoring/export store. Treat viewer features as version- and recipe-specific.

Annotorious is a useful analogous mechanism if the reading room needs its own focused image workspace: its current OpenSeadragon guide shows loading annotations from JSON and using IIIF image sources, with coordinates relative to the image’s base resolution. It offers a W3C image-format adapter, while also documenting that its native model is simplified and does not claim the full W3C model [S19, S20]. It is a client-side annotation library, not a manuscript viewer or a persistence/identity service. A local integration would still need Canvas identity, Manifest navigation, access control, server storage, and import/export validation. This is an integration proposal, not a claim that those pieces exist natively.

### 3. Manifest/version compatibility, remote images, and export/import

For a pilot, explicitly recognize Presentation API 2.1.1 and 3.0.0 and normalize them into a local annotation model without rewriting source data. The 3.0 changelog records a major switch from Open Annotation to W3C Web Annotation: `@id`/`@type` become `id`/`type`, and `AnnotationList`/`Layer` give way to `AnnotationPage`/`AnnotationCollection` [S2, S3]. Version 2 uses structures such as `otherContent`, `AnnotationList`, `on`, and `resource`; v3 uses Canvas `items`, `AnnotationPage`, `target`, and `body`. Detect the source context/version, retain it, and serialize to an explicitly selected output version; do not assume “JSON” alone ensures compatibility.

Manifests point to remote content. In v3, an image body can reference an Image API service and an external Annotation Page can be dereferenced later [S1, S6]. A browser must still be able to retrieve the Manifest, annotation endpoint, image-information document, and requested image. The Image API recommends CORS support for image and information responses; its error model distinguishes unauthorized/forbidden/missing/service-unavailable cases, and image authentication is handled in a IIIF-aware workflow rather than solved by annotation syntax [S6]. Check CORS, authentication, URL stability, service level/features, and actual HTTP availability for each pilot collection. Do not fetch or copy masters to evade access restrictions. A plain image URL or non-IIIF manifest needs an explicitly scoped fallback; do not claim zoom, pixel selector, or cross-viewer behavior until that fallback is tested.

Keep the authoritative annotation data in a separate store/export package. A product import should validate page ID, Manifest/Canvas match, API version, selector type and bounds, body encoding, and duplicate IDs before making notes visible. An export should include stable page identifiers, source references/version, geometry and coordinate basis when present, author/timestamps and privacy rights needed for stewardship. Offer W3C/IIIF JSON for machine reuse and readable text for people, but promise only the tested profiles/viewers. No operation should update catalogues, manifests, image masters, or collection servers.

### 4. Released compatibility history and affected pilot operation

Two version histories affect concrete pilot work. First, IIIF Presentation 3.0 deliberately changed the annotation model and several structural names from 2.1.1; this is a released compatibility change, not a theoretical future issue [S3]. A naïve v2-to-v3 import/export may lose text bodies, targets, page lists, or layers. Exercise versioned fixtures and retain the source version in imports.

Second, the Mirador 3-to-4 upgrade changed React/MUI and plugin expectations; the upstream `mirador-annotations` README says it is incompatible with v4, while 4.0 launch notes describe community plugin alternatives [S12, S13]. The concrete regression chain: Mirador issue #4198 records that an annotation/layer notification dot present in M3 disappeared in M4; PR #4201 merged a fix, and Mirador v4.2.4 release notes include that fix [S14–S16]. This affects discovering which pages have existing annotations before reading or adding notes, not just theme polish. A pilot using Mirador should pin an exact tested release and regression-check page badges, opening existing annotations, drawing, saving, reload/import/export, and plugin compatibility. The fix does not establish authoring-plugin support or cross-viewer portability.

UV releases also show why a viewer should be pinned: the release page marks v4.4.3 and v4.4.1 “DO NOT USE” due to merge errors and lists v4.4.4 (commit `2b92ff6`) as the latest release observed on access [S17]. Do not adopt a floating latest tag.

### 5. Optional transcription-only download

Retain this as an authorized option, not a mandatory feature or assumed viewer capability. IIIF’s transcript guidance explicitly describes independent download as a `rendering` link, alongside Canvas-level supplementing annotations for text shown with an image and spatially synchronized annotation fragments for synchronized text [S9]. This supports an approach for scholars without a compatible viewer: produce a UTF-8 `.txt` per selected page (or one concatenated text file) plus a small JSON/CSV index carrying curator page ID, page label, source Manifest/Canvas URI and version, transcription provenance/language, and character encoding. Include no source image or collection-master copy. Preserve all newlines and scholarly transcription characters. Offer it when a transcription exists and access/rights permit; make the text’s source/status legible (manual, OCR, or unverified if known). The standards document supports the linking pattern, not this product’s ready-made export capability, which remains a local implementation proposal. No evidence justifies excluding the option.

### 6. Owner inputs and 7. Negative constraints

The collections curator must supply/approve stable page IDs and any changed-ID crosswalk; neither a viewer’s Canvas ordering nor a catalogue’s current label resolves that ownership. The reading-room lead must choose the initial privacy setting. Recommend private by default for scholar notes pending that decision and require an explicit share/publish action and authorization before any outside exposure. A public manifest, open annotation profile, or viewer default is not authorization to publish private notes.

Carry these hard constraints into implementation and review: do not copy entire collections; do not alter collection image masters; do not promise uniform annotation features across all viewers; do not make public publication mandatory. Keep the catalogue as the collections’ existing descriptive system and store only page references needed for the pilot.

### 8. Evidence/validation status

This is a planning proposal, not implementation. The source and version observations above were read from public specifications, official project documentation/repositories, releases, and issue/PR history. No product instance, collection manifest, server, account, annotation store, import/export, or browser workflow was exercised. Therefore product checks are **NOT_RUN**. The post-plan draft should include a validation table that distinguishes these executed source-review activities from proposed pilot checks (manifest/version inventory for all 100 pages; CORS/auth/image retrieval; dimensions and Canvas mapping; whole-page and rectangle display in each pinned viewer; authoring/save/reload/export/import with two versions; privacy/access-control checks; text-only bundle without images).
