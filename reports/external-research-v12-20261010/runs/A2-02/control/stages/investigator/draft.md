# Investigator proposal — Portable reading-room annotation workspace

## Recommendation and scope

Run a 100-page pilot with an annotation layer that references collection materials in place. Use each collection’s remote manifest and image service where they exist and are authorized; do not ingest whole collections or alter masters. Keep the pilot’s annotation records in a separately governed store. Each record should refer to a curator-approved stable page identifier and a versioned presentation target (for IIIF, the manifest and Canvas identifiers), and carry its body, selector, provenance, author, and access state. Treat IIIF Presentation 3 as the preferred serialization when a collection already supplies it, while inspecting actual inputs before committing to support. Add a read-only IIIF 2.1.1 adapter only if pilot inputs require it. Keep original source data untouched and report any conversion that cannot preserve a field or selector.

For a first viewer spike, prioritize Mirador because its project overview describes multi-up comparison and the IIIF cookbook matrix marks it supported for the specific “Simple Annotation — Tagging” recipe. Keep Universal Viewer as the comparison candidate because its overview describes broad, embeddable content support. Neither source proves complete annotation authoring or equivalent behavior. Pin Mirador 4.2.4 and Universal Viewer 4.4.4 for a reproducible comparison, then re-check the release pages immediately before implementation because they change. Do not promise feature parity. Mirador’s old annotation plugin is a separate Mirador 3 integration, not a Mirador 4 core feature; if it is considered, select and validate a compatible extension and persistence service. Annotorious 3.4.0 with OpenSeadragon is a useful analogous image-annotation mechanism for a custom panel, not a ready-made manuscript viewer or a source of stable page identity.

Use persistent Canvas-space targets, not viewport pixels or the current image URL, for geometry. Save the target Canvas identifier, selector, the Canvas coordinate dimensions and the source revision used to create it. A presentation Canvas may use a stable coordinate space even when the delivered image has different pixel dimensions; the cookbook’s differing-dimensions recipe supports that pattern when aspect ratio stays consistent. Render by transforming Canvas coordinates to the current display. Percent `xywh` is also standardized for media fragments, but selectors and coordinate conventions still need testing in each pinned client. A new crop, rotation, changed page content, or changed Canvas identity is not a resize: flag it for review/re-anchoring rather than silently moving the note. Use an explicit alias/history map only after the collections curator defines stable page identity.

Keep transcription, commentary, and region association distinct in storage and export. For IIIF 3 output, W3C Web Annotation provides TextualBody and selector structures; IIIF 3 uses AnnotationPage/Annotation, while IIIF 2.1.1 uses different names and structures. An adapter must account for that major-version boundary and preserve unsupported fields or report loss. Do not claim a successful round trip based only on the standards or documentation.

Retain the brief-authorized optional downloadable transcription-only bundle. Recommend offering it on explicit user request when rights/access permit and when the reader’s access to that transcription permits export. A simple UTF-8 text file plus a small page/provenance index is a candidate, containing selected transcription text and stable page references, with no image bytes and no collection-wide export. This is a proposed product option, not an existing viewer feature. IIIF’s transcript recipe distinguishes a rendering/download link from supplementing annotations and synchronized fragments; it supports investigating this option, not a claim that a viewer implements it. Do not make the option mandatory. If the owner later excludes it, record the specific rights, access, or interoperability evidence for that choice.

## Evidence and limits

The source index at [`sources/index.md`](sources/index.md) provides direct links, versions or commits, locators, access time, observed operation, applicability, and governing conditions for S1–S21. The source map is the detailed record. Standards establish data and coordinate conventions; cookbook recipes illustrate patterns and limitations. They do not establish that a selected viewer, plugin, collection manifest, image service, or deployment implements them.

The presentation change log records a major v2-to-v3 compatibility change: v3 adopted W3C Web Annotation, renamed `@id`/`@type` to `id`/`type`, and replaced `AnnotationList`/`Layer` with `AnnotationPage`/`AnnotationCollection` [S2, S3]. Calling the migration “cosmetic” is therefore not supported. A compatibility matrix and version-specific serialization are needed.

A concrete Mirador discovery regression is documented: issue #4198 reported missing annotation/layer notification badges in v4; PR #4201 merged the palette-token fix as commit `056262a`; the Mirador v4.2.4 release at commit `73fafe9` includes that fix [S14–S16]. This matters to finding annotated pages in the pilot. It does not prove authoring-plugin compatibility, note persistence, or cross-viewer parity. The Mirador 4 announcement describes breaking React/MUI/plugin changes [S12]. The `mirador-annotations` project describes rectangle/oval/polygon/text tools and local-storage demo behavior, requires an annotation server for persistence, and says that plugin does not work with Mirador 4 [S13].

The release page retrieved for Universal Viewer lists v4.4.4 at commit `2b92ff6` and explicitly marks v4.4.3 and v4.4.1 “DO NOT USE” [S17]. Treat those as release-page findings at the recorded access time, not a timeless ranking. The Annotorious release page identifies v3.4.0 at commit `0dd99c4`; its IIIF/OpenSeadragon guide loads image-relative annotations, and its data-model guide describes a native model and W3C adapter rather than full W3C-model support [S18–S20]. This makes it a candidate for a bounded integration spike; coordinate conversion and persistence are still engineering work.

IIIF Image API documentation recommends CORS for image and image-information responses and documents distinct 401, 403, 404, and 503 responses; authentication and access control are outside the API’s own content [S6]. Thus external image availability is an input dependency. Neither metadata review nor a standards-compliant manifest demonstrates that a real collection’s URL, credentials, CORS policy, rights, or service is usable by the pilot. The actual manifests and images have not been accessed or tested here.

## Alternatives and decision conditions

1. **IIIF-based presentation adapters (recommended pilot path where collections already expose IIIF).** This uses existing manifest/Canvas structure and a standards-defined annotation representation. It does not require every collection to expose the same presentation version, public image service, or usable annotation server. Do not claim that a manifest guarantees image access or that a viewer supports every selector.
2. **Viewer-provided authoring.** Test only after pinning the exact viewer and extension. Mirador 4’s breaking changes and the v3-only plugin are evidence against assuming that its core or an old plugin supplies durable authoring. A chosen plugin still needs a persistence endpoint, access controls and version-specific output.
3. **Separate OpenSeadragon/Annotorious annotation panel.** Useful if both viewers lack a needed interaction. It adds integration for mapping selected pages and image-relative coordinates into curator-approved Canvas/page identity, W3C serialization, durable storage and export. The library’s own data-model caveat means representative selector/body conversion needs explicit review.
4. **Non-IIIF images.** Do not reject a collection automatically. Route a permitted image through a custom adapter only if the pilot can assign approved page identity and coordinate metadata; otherwise mark it unsupported for the pilot with a clear reason. Do not create a collection mirror as a workaround.

## Pilot workflow proposal

1. Ask the collections curator to identify the 100 pages, their stable identifiers, available manifest/image-service URLs, presentation versions, rights, and any known image revisions. Ask the reading-room lead to decide the privacy default. These are required owner inputs, not findings inferred from product defaults.
2. Build a small, read-only inventory of those page references. For each source, identify presentation version, Canvas ID and dimensions, image service/profile, auth requirements, current response/availability, and expected export rights. Keep an explicit `unsupported`, `needs-auth`, or `unavailable` result rather than copying a source.
3. Pin viewer builds and implement only the adapter needed for these inputs. Keep the annotation store separate. Capture a whole-page text note and region transcription/comment on representative pages; preserve selector/body and provenance. Test both reading and authoring separately.
4. Run the two viewers against the same representative pages and same annotation records. Evaluate opening, multi-page comparison, locating a page with notes, rendering whole-page and region notes, edit/save/reload, and how an unavailable external image is reported. Record a feature matrix per exact viewer/plugin/build; do not generalize a recipe result.
5. Test the optional text-only bundle as an independent path. Include only authorized selected text and stable references, no image data. Verify it is readable without either viewer and that export does not publish private annotations or change source material.
6. Expand to the 100-page pilot only after the owners resolve IDs/privacy and the representative import, display, save/reload, resize, export, and access cases pass. A failed case leads to a documented limitation or revised design, not silent coordinate or data loss.

## Open owner and implementation inputs

- **Collections curator:** stable identifier format, relationship between a stable page ID and each manifest/Canvas revision, and how changed/cropped images are identified.
- **Reading-room lead:** private/public default and who may view, edit, export, or publish notes. Recommendation for discussion: private until a user explicitly shares, subject to the lead’s decision; this is not an approved setting.
- **Collections and rights contacts:** permitted external access, credentials/auth flow, CORS configuration, transcript rights, and whether selected text may leave the source system.
- **Pilot team:** whether actual inputs require v2 support; annotation-store choice; selected viewer/plugin after comparison; import/export file contract; retention, backup, error reporting, and the policy for unsupported selectors.
