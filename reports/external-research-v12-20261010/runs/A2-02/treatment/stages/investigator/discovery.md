# Independent discovery — portable reading-room annotation workspace

**Stage:** ER12 A2 / investigator, run A2-02-treatment.  
**Discovery basis:** the complete assigned brief only. The exact plan has not yet been released; this document is frozen before that release.  
**Research access:** read-only public standards, project documentation, repository histories, release notes, and issue records. No products, accounts, installs, collection images, or production systems were accessed.

## Recommended direction

Treat the collections’ manifests, catalogues, and image masters as read-only external sources. Add a reading-room annotation layer that refers to stable page resources and coordinates in a deliberately chosen IIIF Canvas coordinate space. Keep page identity under the collections curator’s authority. Preserve source provenance (provider, exact Manifest and Canvas URIs, API version, retrieval date, Canvas width/height, image/service identifiers, rights/access cues, and any superseded-to-current page mapping) beside the annotation. Store annotation records independently; do not rewrite providers’ manifests or master images.

Use IIIF Presentation API 3 Annotation Pages and W3C Web Annotations for records that need interoperability: a whole-page target can be the Canvas URI; a region uses a SpecificResource plus FragmentSelector/media-fragment xywh; text is an embedded TextualBody. Keep the authoring model to simple text and rectangular selectors for the pilot, because specifications permit richer structures but viewer support differs. Derived page transcription is naturally represented with supplementing; a marginal note can use a commenting motivation. Do not claim every viewer renders the same bodies or selectors.

## Findings against the original obligations

1. **Page identity and coordinate portability.** The IIIF Canvas is the page/view and its absolute HTTP(S) URI is its identity; a Canvas URI must not itself contain a fragment. Do not key pages by manifest position, display label, thumbnail URL, or raw image-pixel dimensions. Ask the curator to approve a stable page-ID scheme, then keep a resolvable mapping from each provider Canvas/Manifest URI and source version to that ID. Canvas width/height define the annotation coordinate space, not the display viewport or necessarily the painted image pixel dimensions. The IIIF Cookbook’s differing-size recipe explicitly uses a larger stable Canvas space while replacing the painted image. For same content/aspect ratio with changed pixel dimensions, scaling coordinates or a percentage selector can retain relative placement. Crops, rotations, changed page boundaries, or changed aspect ratio are not solved by percentages alone: record version/image provenance, mark selectors for review, and require curator-approved mapping/re-anchoring rather than silently moving scholarly notes.

2. **Two viewers and a separate annotation mechanism.** Mirador is a multi-window image viewer and can be extended for authoring; the original mirador-annotations project adds rectangle/oval/polygon tools and text but explicitly targets Mirador 3, not Mirador 4. Mirador 4 authoring therefore needs a separately versioned compatible plugin such as the community Mirador Annotation Editor (MAE) or a purpose-built integration; persistence needs a configured annotation server or is only browser-local through local storage. Universal Viewer (UV) is a realistic independent IIIF reader with broader presentation/media coverage and a more view-oriented interface. The sources reviewed do not establish it as a compatible annotation authoring/persistence system. Use it as a comparison/reading client until a pilot demonstrates the required annotation rendering. The analogous mechanism is not either viewer: it is IIIF Presentation 3 Annotation Pages + W3C Web Annotation. Standards provide a shared data model, not a promise of common editors or common backends. IIIF Content State 1.0 is a useful additional opportunity for page/region deep links and opening a view in compatible clients; it is not a note store or annotation export format.

3. **Manifest versions, remote images, and import/export without changing masters.** Keep each provider Manifest as the source authority and read its declared Presentation version; adapters may translate v2 otherContent/AnnotationList patterns and v3 Annotation Pages into one internal record view, but retain original source bytes/identifiers and never rewrite the source. V3 moved non-painting annotations/transcriptions into annotations/Annotation Pages and changed its context, so do not merely relabel v2 JSON as v3. A Canvas can paint an external image URI, optionally with an Image API service; image metadata, CORS/authentication, rights, and service features affect whether the external resource can actually be displayed or exported. Image API 3 allows static/limited service implementations and capability declarations, so test real providers rather than assume arbitrary crops/downloads. Proposed export is a selected annotation bundle containing JSON-LD/IIIF records, stable page ID, exact source Manifest/Canvas and image/version provenance, language, motivation, selector, creator/time as allowed, and any import warnings. Import must match stable page IDs, retain original target IDs, validate selectors against Canvas bounds, and quarantine missing/ambiguous/changed pages for review. Exporting annotations does not update catalogue data, master files, or the provider Manifest. A compatible viewer URL/state export is separate from annotation bundle export.

4. **Compatibility history that affects pilot work.** The Mirador 4 release is explicitly a breaking modernization (React/MUI changes and plugin/integration updates). Its older mirador-annotations plugin README says it does not work with Mirador 4 and recommends MAE. A 2023 issue documents an install-time dependency conflict for mirador-annotations@0.5.0 and mirador@3.3.0 (React peer ranges disagree), before any note can be created. MAE provides a valuable newer route, but its pinned README describes React 18/MUI 5 and Mirador 4.0.0-alpha.2, while the reviewed current Mirador release line has moved on. This is a compatibility warning, not proof of current MAE failure: select exact versions and run the proposed install/author/save/reopen/export/import smoke path before committing to it. For collection content, separately test each observed v2/v3 manifest and provider image-service behavior.

5. **Optional transcription-only bundle.** Retain this explicitly authorized option as optional. A practical proposal is a user-requested downloadable ZIP or directory with UTF-8 transcription text/TSV plus a small JSON-LD sidecar keyed by curator-owned page ID and containing exact source URIs, language, transcription purpose, and region selector when relevant. Include no image bytes or full manifest/collection copy. This is a local product proposal, not an observed viewer feature or established capability. Its inclusion should depend on verified Unicode, language, line/page grouping, licensing/access, and import/export round-trip behavior. If export cannot preserve those associations or policy forbids it, document that evidence before excluding it; no current evidence supports exclusion.

6. **Owner decisions.** The collections curator decides the stable page identifier scheme and confirms how source versions map to it. The reading-room lead decides whether annotations are private by default. Neither decision follows from a viewer’s UI/storage defaults. Keep privacy configuration explicit; avoid public static Annotation Pages unless authorized, and design any private persistence/export controls around the lead’s decision.

7. **Negative constraints.** The proposal does not require copying all collection data, altering collection masters or catalogues, claiming universal annotation-feature parity, or publicly publishing scholars’ notes. Remote references plus a separate annotation layer are sufficient for the pilot; any permitted export is selected scholarly text/annotation data, not an image-master mirror.

8. **Validation plan and status.** No executable/product checks were run; reading specifications, docs, source code and release/issue history is research evidence, not product validation. Proposed first checks are: curator/lead identity and privacy decisions; intake audit of all 100 pages across source collections; v2/v3 manifest parsing and identity/version mapping; image availability/auth/CORS/rights and dimensions; rectangular-bound checks plus same-content resolution swaps and crop/rotation drift cases; Mirador/MAE exact-version install and create/save/reopen/selective export/import; UV read/render behavior against the same sample annotations; text-only export/import preserving Unicode and page associations; and regression checks ensuring provider manifests/images are not modified. Keep every proposed check marked NOT_RUN until actually executed.
