# Independent discovery — offline note-search adapter

Run: `A3-01-treatment`; stage: investigator. This discovery was made from the finalized brief at `treatment/inputs/brief.md` alone. The concealed plan had not been released or read when this file was saved. Scope is a local adapter for 50,000 short SQLite notes, including note create/update/delete, with SQLite FTS5 and Tantivy treated as live alternatives. The editor, sync, hosted search, and application implementation are outside scope.

At research time (2026-10-10 UTC), SQLite's latest observed upstream release was 3.53.4 (2026-07-24; source ID `2026-07-24 19:02:57 bf7c7f30031888f4e796e429ab3978879485813aaca6f641c7b33e4e09459bcc`). These are evidence snapshots, not a selection of the application's dependency versions. No app binding, bundled/system SQLite choice, compiler flags, Tantivy schema/tokenizer, Rust toolchain, or target build has been selected or inspected. Pin and report the actual runtime/build before treating any capability as present. In particular, FTS5 is in SQLite's amalgamation since 3.9.0 but source-tree configuration currently disables it unless `--enable-fts5` is used; amalgamation defaults can differ. Probe the exact application connection by creating and dropping a temporary FTS5 virtual table, and record `sqlite_version()`/source ID and effective build options. A crate version alone does not prove FTS5 availability. [S01, S06, S07]

## Bounded query and normalization candidate

Define a product grammar such as `query := atom (space atom){0..15}`, where `atom` is one nonempty unquoted token or one balanced quoted phrase. Cap input at 256 Unicode scalar values and each token at 40 UTF-8 bytes; reject over-limit input, unmatched/nested quotes, empty input, and punctuation-only input with a validation message. Quotes group tokens into a phrase; outside quotes, punctuation is a separator and terms are combined with AND in any order. For example, `canoe-kayak` tokenizes to two terms; `"old desk"` requires those tokens in order and adjacent after tokenization. Do not expose `OR`, negation, field names, prefix wildcards, `NEAR`, regex, or arbitrary SQL. Decide whether to support an explicit quote escape; the simplest first contract rejects embedded delimiter quotes.

This is an application grammar, not engine grammar. Parse and normalize once into typed atoms. For FTS5, serialize only generated phrase/term AST pieces, double any engine-level embedded double quote if supported, and bind the resulting `MATCH` value; binding prevents SQL syntax injection but does not constrain FTS5's own query operators. For Tantivy, construct typed query objects or feed only generated, escaped forms to the parser. A historical Tantivy issue reports a panic for malformed `- *` input on `tantivy` 0.22.1 / `tantivy-query-grammar` 0.22.0; a linked commit is from a contributor fork and does not establish the fix in the current upstream release. This makes strict grammar tests and current-version source review necessary, not a claim that 0.26.2 is affected. [S02, S09, S10, S15]

For comparable lexical behavior, explicitly select FTS5 `unicode61 remove_diacritics 2`; for Tantivy use an explicit `SimpleTokenizer`/lowercase/folding analyzer and an explicit, tested long-token rule instead of silently relying on defaults. This is a proposal, not a cross-library equivalence claim: Unicode versions, character folding, punctuation classes, and token limits differ. No stemming, synonyms, fuzzy matching, substring search, semantic retrieval, or universal language quality is required. Treat accents as a tested policy: Latin forms such as `café`/`cafe` may fold, but test `ø`, `ß`, decomposed accents, combining marks, and non-Latin text on the actual pinned versions before promising more.

The selected collection/tag is a separate typed filter (bound SQL equality/join for FTS5; exact term/facet filter combined with the Tantivy text query). Preserve the canonical note ID for every hit. For FTS5 use `rowid` only as the join key, not the public result identity. For Tantivy store/index a stable note ID. Return `(score, note_id)` ordered with a deterministic note-ID tiebreak. Tantivy's built-in `DocAddress` tie ordering is deterministic within that index snapshot but may differ after segment merges or rebuilds, so it is not the cross-rebuild contract. BM25 scores are lexical and corpus-dependent; no semantic meaning or long-term rank stability should be promised. [S03, S04, S11, S12]

## Write, delete, recovery, and repair mechanism

**FTS5 path.** Prefer one SQLite database, an external-content FTS5 table keyed by an integer rowid that maps to the canonical note row, and insert/update/delete triggers. The update trigger deletes old token entries and inserts new values; the delete trigger uses old values. Run the initial `rebuild` after creating triggers, since triggers do not backfill old rows. Keep source-row mutation and trigger work in one database transaction; SQLite's transaction guarantees still depend on the configured journal mode, `synchronous`, VFS, filesystem, and durable-storage behavior. If WAL is selected, keep the database, `-wal`, and `-shm` lifecycle together; `synchronous=NORMAL` sacrifices durability of recent commits on power loss/hard reset, while `FULL` syncs the WAL at each commit. Probe the configured mode rather than inferring it. On a suspected mismatch, run external-content `integrity-check` with `rank=1`, then `rebuild` from canonical content in a controlled maintenance transaction. Never repair by deleting canonical note rows. [S03, S05, S16, S17]

**Tantivy path.** Keep SQLite authoritative and append a monotonically ordered change record in the same transaction as each note create/update/delete. A single local Tantivy writer consumes changes in order; an update is delete-by-stable-ID plus add the current document; a delete removes the indexed document; commit publishes operations. Acknowledge the SQLite change record only after the Tantivy commit succeeds. Replaying a record after a crash between index commit and acknowledgement must be idempotent and tested; do not advance the applied-sequence checkpoint before commit. Tantivy's `commit()` publishes/persists additions and lets indexing resume from its last successful commit after failure; reader reload on commit is delayed by default (the docs say tens of milliseconds). These are separate-index semantics, not cross-database atomicity. Check the last applied sequence at startup, replay the queue, and rebuild a new index from a consistent SQLite snapshot when the schema/version/checkpoint is invalid or drift is detected. Use an explicit handoff of the new index and retain a fallback until validation succeeds. Filter returned IDs against SQLite so stale deleted documents are suppressed; this does not detect missing documents, so sequence/checksum/count reconciliation and rebuild are still required. [S05, S08, S14, S18]

SQLite's WAL documentation describes single-database commit records in the WAL and a default 1000-page auto-checkpoint; it also says WAL requires same-host shared memory and does not work over a network filesystem. The target is a local desktop store, but journal mode and OS-specific durability should still be explicit and failure-tested. Its rollback-journal atomic-commit explanation is specifically for rollback mode and relies on VFS/filesystem assumptions; do not generalize it to every storage fault. Tantivy issue #2847 is an open report for Tantivy 0.25.0 on Windows 10/11 NTFS: concurrent `.managed.json` atomic writes from commit and background merge can yield `PermissionDenied` on Windows (the issue also describes a possible lost registration on Linux). It is not evidence that 0.26.2 has the same defect or that it fixed it; test the exact selected release on Windows. [S13, S16, S17]

## Preliminary selection criteria and unresolved questions

For the stated 50,000 short notes and existing SQLite source of truth, FTS5 is the simpler first candidate **if** the shipped Linux and Windows SQLite builds expose FTS5 and the tested lexical/query contract is enough: it keeps note and index mutations in one local database transaction and provides external-content rebuild and integrity tools. Tantivy remains a meaningful alternative if the owner needs its richer typed query/index controls or measured performance benefit and accepts a local sidecar plus outbox, lag, replay, lifecycle, and versioned index management. No performance winner was measured; this is conditional architecture reasoning, not an empirical selection. Compare actual release/build, on-device query latency/index size/write cost on a synthetic 50k fixture, exact language behavior, and recovery complexity before final choice.

Open owner decisions: (1) which SQLite binding/library is shipped and whether it is system or bundled on Linux and Windows; exact versions and FTS5 build flags; (2) one-tag vs multi-tag filter semantics, and whether tags can be renamed; (3) query limits and behavior for quotes, stopwords, short/punctuation-only terms, long tokens, accent folding and non-Latin text; (4) whether phrases are required or if all terms may be ANDed; (5) result limit, exact tie policy, and whether recency participates; (6) excerpt source (title/body), length, and whether highlights are necessary; (7) allowable stale-search window for Tantivy and which component owns queue replay; (8) WAL/rollback mode, `synchronous`, backup and local index-file lifecycle; (9) index-schema/tokenizer migration strategy and version metadata; (10) whether 50k synthetic measurements justify a separate library. Neither engine supplies semantic understanding.
