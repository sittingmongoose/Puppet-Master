# Local note-search adapter — final recommendation

Fixture ER12-A3-01-FRESH. The released brief describes a Rust desktop field-notes tool on Linux and Windows, with about 50,000 short notes already stored by stable note ID, title, body, and collection tags in SQLite. This is a complete recommendation and bounded adapter plan, not application code. The editor and sync system remain out of scope; the note database remains authoritative; personal notes stay local. It preserves every S1–S6 clause and every negative constraint in the released brief. The exact released plan is recorded in the input manifest: SHA-256 d490464e9066ef07d933d5e8fb1b91980c28695182e280fc0e0722837e7d2718.

## Recommendation

Start with SQLite FTS5 as an **external-content** index in the existing local SQLite database. Keep the note table as the only authority for note IDs, title, body, and collection relationships. The FTS table keeps searchable postings, while FTS5 obtains source text from the existing content table; this avoids a second full-body copy while retaining a source from which to rebuild. Install insert/update/delete triggers in the same database transaction domain, build the initial postings with `rebuild`, and check external-content consistency explicitly. FTS5 is conditional on the SQLite binary actually shipped on both Linux and Windows having FTS5 enabled and on a usable row-ID mapping. Its upstream manual describes the `SQLITE_ENABLE_FTS5` build path, but no target package has been inspected (S01–S04).

Keep Tantivy as the alternative if the pinned SQLite package lacks FTS5 and cannot be changed, or a future measured requirement justifies Tantivy’s separately controlled analyzer/index while the team accepts an outbox, replay, and generation-rebuild subsystem. Neither a performance winner nor a deployed capability is established. The 50,000-note scale makes FTS5 the lower-integration-cost starting point by architecture; that is a hypothesis, not a benchmark.

## Adapter contract: query, normalization, result identity and excerpt

### Bounded query language

Accept at most 256 Unicode scalar values and at most 8 emitted searchable terms across the query; each analyzed term inside a quoted phrase counts toward the cap. A syntax scanner recognizes balanced double quotes, rejects control characters, embedded quotes, unmatched quotes, empty quoted phrases, and exceeded limits with a visible input error, and preserves the text spans for analysis. Backslash escapes are not part of the public grammar. Empty input and input producing no searchable tokens (including punctuation-only input) returns a no-search state, never a match-all query.

Outside a quoted segment, each emitted term is a required clause; all clauses are conjunctive. A balanced quoted segment creates one ordered phrase whose emitted terms must be adjacent after that backend's analysis. Punctuation and Unicode whitespace separate tokens according to the selected analyzer. Punctuation inside a quoted segment is therefore a token separator, while the emitted phrase terms must still be adjacent. The word AND is ordinary note text. The public grammar has no exposed AND/OR/NOT operators, field selectors, prefix or wildcard, regex, fuzzy, proximity, range, or match-all syntax. Parse first and build a typed query or a quoted, generated FTS expression. Bind SQL values; never execute user text as SQL or give raw user input to a backend query parser.

For FTS5, use the tokenizer configured on the FTS table for both indexing and query analysis. The FTS5 API can retrieve a tokenizer implementation and tokenize text; initialize it with the table's exact tokenizer arguments, then construct the MATCH expression only from its emitted tokens and phrase spans. Quote and escape generated tokens and bind the expression as a SQL value. This keeps Boolean structure under adapter control and prevents words such as AND from becoming operators. For Tantivy, run the exact registered TextAnalyzer used by the index on each query span, then build TermQuery and BooleanQuery clauses for terms and a zero-slop PhraseQuery from the analyzer's ordered terms and positions for a phrase. Index phrase fields with positions. These are proposed integration operations, not verified application behavior.

### Tokenization and normalization policy

The FTS5 candidate configuration is unicode61 remove_diacritics 2, with no stemming, synonyms, or stop-word removal initially. The official manual says unicode61 is based on Unicode 6.1; by default spaces and punctuation are separators, and letter, number, and private-use categories are token characters. Matching is case-insensitive. Option 2 avoids the multi-diacritic composed-codepoint case that option 1 leaves unchanged. It is a bounded Latin diacritic policy, not universal transliteration or language-aware segmentation. The default category policy treats combining marks outside those token categories as separators; do not promise canonical equivalence between every composed and decomposed spelling without an agreed fixture and an actual result.

For the Tantivy 0.26.2 comparison candidate, define a field analyzer explicitly as SimpleTokenizer, LowerCaser, and AsciiFoldingFilter, with no stemming, stop words, or synonyms. The pinned docs describe SimpleTokenizer as splitting on whitespace and punctuation and describe AsciiFoldingFilter as mapping some non-Basic-Latin alphabetic, numeric, and symbolic characters to Basic Latin equivalents. This is not equivalent by definition to FTS5 unicode61. Keep analyzer parity, accent edge cases, non-Latin scripts, token-length boundaries, and punctuation behavior as validation cases. If either analyzer configuration changes later, the index is a derived-schema migration: rebuild a new search index and validate it while retaining all authoritative notes.

### Fields, collection filter and identity

Search title and body. Each unquoted term must occur in title or body; a quoted phrase must occur in order and adjacent within one field. If a collection is selected, apply it as an exact collection-key filter, separate from the lexical query. With FTS5, use an exact EXISTS/join against the authoritative collection relationship in the same SQLite database query; preserve one result per note if tags are many-to-many. If Tantivy is selected and collection keys are indexed, maintain them through the change stream described below. Note-ID type, mutability, tag cardinality, and collection-key normalization are not supplied. Resolve them from the real schema before implementation. If the public ID is not a suitable integer, use a stable integer FTS content_rowid mapping and join back to the unchanged public ID.

Return the original public note ID and fetch current title/body from SQLite for display. Proposed order is lexical score followed by canonical note ID ascending for ties. FTS5 BM25/rank sorts best-first in ascending numeric order; Tantivy BM25 similarity sorts in descending order. Tantivy's TopDocs default tie key is DocAddress, an index location rather than the public identity. For the stated 50,000-note corpus, collect all matching score/ID pairs and sort by score then ID before page slicing, or implement a note-ID-aware collector. This is a proposal, not a measured cost. Repeatable order is promised only for the same query, corpus, analyzer, ranking configuration, index generation, and component version. Corpus updates or rebuilds may change rank, and scores from the two engines are not comparable. Title weighting, recency, page size, and latency bounds remain owner decisions.

Create a proposed excerpt of at most 160 Unicode scalar values from the current authoritative SQLite title/body, centered near a verified query-term span when available. Escape text for the UI or return separate plain-text and UI-owned highlight spans. Do not treat FTS5 snippet()/highlight() output or Tantivy Snippet::to_html() as trusted HTML. If the candidate is stale, missing, deleted, or has no source occurrence after normalization, reject it or show a safe unhighlighted current-text fallback; never invent a match. Neither engine warrants a universal language-quality claim.

## Lifecycle design details

### Preferred FTS5 path

Create an external-content FTS5 virtual table on the same local SQLite file, indexing title and body and mapping `content_rowid` to the source note key. If public IDs are not stable integers, use a stable integer surrogate as the FTS row ID while leaving the public note ID unchanged. Create AFTER INSERT/UPDATE/DELETE triggers that add a new row, issue FTS5's special delete with the old row ID and old indexed values, then insert the new indexed values on update. Avoid external-FTS `REPLACE`; make the source update statement and trigger behavior explicit. Create the FTS table/triggers and backfill/rebuild before enabling search. This follows official trigger ordering and rebuild rules (S01).

Because the content table and FTS index are in one SQLite database, a source mutation plus trigger-maintained FTS change can be committed or rolled back together. This is the main consistency advantage over a separate index. It depends on an actual FTS5-enabled build and supported local storage/VFS/journal behavior; SQLite's detailed atomic-commit article is rollback-mode-specific and states filesystem assumptions, while the transaction manual documents a single writer and rollback-causing failures. Check the actual journal mode and do not transfer the rollback-mode algorithm verbatim to WAL (S02–S04).

For repair, run the external-content integrity check with rank 1. If postings are incomplete, stale, or structurally inconsistent, rebuild them from authoritative note rows and verify after commit. Rebuild never deletes/rewrites authoritative notes. Search generation is “ready” only after a successful commit and integrity check. Initial backfill is mandatory when the FTS table is created over pre-existing notes. Consider secure-delete only if the owner defines a local-file/forensic deletion guarantee: FTS5 defaults it off; enabling it slows updates/deletes and can change compatibility with older FTS5 readers, and core SQLite secure-delete may also be needed for the database file (S01).

### Tantivy alternative

Keep the Tantivy index directory under the app's local data directory. Use indexed title/body fields with the explicit analyzer above and positions; store/index a stable exact note-ID key for update/delete; and keep SQLite as the sole source of truth for displayed text. Use typed TermQuery, PhraseQuery, and BooleanQuery construction. Tantivy 0.26.2 IndexWriter additions and deletions become visible to readers after commit; commit publishes and persists pending documents. That commit cannot commit the SQLite outbox acknowledgment atomically.

If the schema stores collection membership separately and a Tantivy field is used for collection filtering, every relationship addition, removal, or key change must be included in the same SQLite transaction's durable change log as note edits. The consumer should re-read the current authoritative note and its complete current collection-key set, then replace that note's Tantivy document idempotently. A collection-key rename must enqueue every affected note or an equivalent complete collection change. Rebuild verification compares note identity/revision and the exact current collection set. An alternative is to filter against authoritative SQLite relationships at query time, but it must not take a fixed top-K Tantivy subset and then discard nonmembers if that could omit valid lower-ranked matches; it must continue collecting candidates until the requested page is complete. Prefer indexed exact collection keys only when relationship events are transactionally covered. Actual cardinality and key semantics remain unresolved until the schema is inspected.

For crash-safe generation rebuild, each generation has a durable applied-through sequence. Capture a consistent SQLite snapshot and its high-water sequence, create a new Tantivy generation from that snapshot, and replay later durable outbox entries. Retain outbox rows until every active or candidate generation that needs them has advanced past them; alternatively discard an incomplete candidate and restart from a fresh snapshot. Do not let acknowledgment by the old active generation erase events still needed by the candidate.

Close the race at cutover with a source-write fence. Let the candidate consume changes continuously while the old generation remains active. Enter the final fence only when its pending outbox backlog is below an owner-set pause budget; otherwise keep the old generation active, continue catch-up, and retry later. Start BEGIN IMMEDIATE to acquire SQLite's single-writer slot after existing writes finish; new source mutations must wait or fail/retry while the fence is held. In that transaction read the final committed outbox sequence H, drain the small remaining delta through H, commit Tantivy, and verify its durable applied-through watermark and source identity/revision/tag state through H. Then update the active-generation marker and complete-through watermark in that same SQLite transaction and commit it before releasing the fence. If the final delta exceeds the pause budget or verification fails, roll back the marker transaction, keep the old generation active, and resume catch-up. Readers use the durable active-generation marker and its watermark. A crash before marker commit leaves the old generation active; a crash after marker commit is safe because the Tantivy commit through H happened first. Keep the old generation until the marker is durable. The maximum acceptable write pause is an owner decision and has not been measured.

Every later note or collection change is again written to the outbox in its source transaction and applied to the active Tantivy generation. Before calling a result set complete, compare its applied-through watermark with the source's latest committed sequence: wait for catch-up or report an explicit updating/unavailable state. Do not label partial results complete. The write-fence, per-generation retention, watermarks, and restart rules are application recommendations inferred from the two-store boundary, not Tantivy or SQLite built-in cross-store guarantees. Their latency and failure behavior require integration validation.

## Owner decisions and rejected/uncertain points

**Owner decisions needed before implementation:** pin the actual SQLite distribution/version/build per OS; choose and persist note-ID-to-integer-row mapping if required; define exact collection key and multi-membership semantics; confirm Latin accent equivalence and user-visible malformed-query behavior; choose title/body weighting and result page bounds; decide whether secure erasure of local deleted index terms is promised; decide the permitted migration/outage experience and maximum source-write pause while rebuilding.

**Rejected for this scoped draft:** hosted search, network export, editor/sync build, user text executed as SQL, raw backend syntax exposed as the product language, semantic-search claims, deleting authoritative notes to repair the index, and unqualified assertions that a candidate feature is absent from every released version.

**Uncertain until verified:** which SQLite/Tantivy version and build ships; whether the packaged SQLite enables FTS5; exact note-ID type and collection schema; cross-platform file and mmap behavior for pinned Tantivy; measured latency/disk use; crash behavior of the exact selected journal/filesystem mode; and whether the user expects exact phrase behavior across all languages.
