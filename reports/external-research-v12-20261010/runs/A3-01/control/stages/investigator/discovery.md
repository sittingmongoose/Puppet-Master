# Investigator discovery — A3-01-control

**Brief:** `inputs/brief.md` (read before discovery). The target is a recommendation and bounded plan for one local Rust desktop search adapter over about 50,000 short SQLite-backed notes. Note IDs, titles, bodies, and collection tags already exist. The database stays authoritative. Editor and sync work are excluded. No application changes or executable validation were performed in this discovery stage.

## Initial finding and comparator

SQLite FTS5 and Tantivy are meaningful local alternatives, but solve different integration problems. FTS5 is a virtual-table module in the same SQLite database. An external-content FTS table can index existing authoritative note text by a content-row ID; triggers or equivalent same-transaction writes maintain it. This makes one-transaction create/update/delete and crash recovery the simplest candidate, conditional on shipping an SQLite build with FTS5 enabled and an ID mapping compatible with its integer `rowid`. It is not automatically available in every SQLite binary: the official build guide describes `SQLITE_ENABLE_FTS5` (or a loadable extension), and documents different canonical-source-tree versus amalgamation configure defaults. The app must inspect the SQLite actually bundled/deployed, not infer from the system installation.

Tantivy is an embedded Rust index in a separate index directory. Versioned 0.26.2 documentation exposes explicit tokenizers, positions for phrase search, Boolean/Phrase queries, and an `IndexWriter` whose additions/deletions become searchable after commit. It offers a schema/analyzer and index lifecycle controlled by the app, but cannot join its file commit atomically to the authoritative SQLite transaction. To avoid a crash-loss window, the design needs a transactionally written SQLite outbox/change journal, ordered replay, commit-before-ack, idempotent note-ID replacement, and a deterministic rebuild procedure. A 0.20.1 history item fixed a Windows mmap build issue; this historical issue is a reason for Linux and Windows build/open/reopen validation at the eventual pinned version, not a claim that 0.26.2 is broken or universally supported.

**Working recommendation, not a decision:** prototype FTS5 first because this workload is modest, local, and already lives in SQLite; keep Tantivy as a credible alternative if ranking/analyzer customization or measured performance justifies a second index and its recovery machinery. Compare on the released plan and a representative synthetic corpus before making this an owner decision. No performance, size, UX, cross-platform build, or user-note behavior measurement has been run.

## Candidate bounded search contract

- One user-facing adapter grammar, mapped to structured backend queries rather than passed through as SQL or a backend query language: up to 256 Unicode scalar values; up to 8 searchable atoms; whitespace separates atoms; unquoted atoms are terms; a balanced quoted segment is a consecutive-token phrase; all atoms are required (AND). No exposed field selectors, Boolean words/operators, prefix/wildcard, regex, fuzzy, range, proximity, or match-all syntax. The word `AND` is ordinary text. Punctuation is a separator under the chosen analyzer; punctuation-only/empty input produces a no-search state, never a match-all query. Reject unmatched/empty quotes, controls, excess length/atoms, and unsupported syntax with an inline validation result. Bind SQL values; construct/escape an FTS expression from parsed atoms, or create Tantivy typed `TermQuery` / zero-slop `PhraseQuery` / Boolean clauses. Do not execute user input as SQL or pass it raw to a permissive query parser.
- For FTS5, explicitly specify `unicode61 remove_diacritics 2`; official docs define Unicode 6.1 letter/number/private-use token classes, punctuation/separator behavior, case-insensitive matching, and explain why option 2 avoids the option-1 double-diacritic backward-compatibility corner case. This removes Latin diacritics; it is not universal transliteration or word segmentation. For Tantivy 0.26.2, an explicit `SimpleTokenizer` + `LowerCaser` + folding pipeline is available; `AsciiFoldingFilter` maps Unicode alphabetic/numeric/symbolic characters to Basic Latin equivalents where possible. That differs in scope from FTS5's Latin-diacritic rule. Keep stemming off initially. Treat cross-backend punctuation, decomposed accents, non-Latin scripts, and overlong-token behavior as compatibility tests, not presumed equivalence or universal language quality.
- Search title and body. Interpret each term atom as a required match in either field; a phrase must occur in-order and adjacent within a single field. Add the optional selected collection as an exact filter, combined with (not interpreted as full-text) the lexical query. FTS5 can filter/join using the authoritative collection relationship; Tantivy would need exact collection-key indexing or a source-side intersection. The brief does not specify whether IDs are integer, UUID/string, or whether tag membership is one-to-many. Resolve the actual schema before selecting the FTS5 `content_rowid` and filter mapping; if note ID is not a suitable integer key, use a stable integer search-row key and join to the authoritative ID.

## Data lifecycle and result contract hypotheses

- **FTS5 candidate:** external-content table on the same database; `content_rowid` maps to the existing note key (or explicit stable integer search-row key). In the source transaction, insert/update trigger deletes old indexed text and inserts new text; delete trigger removes only FTS postings. Avoid relying on `REPLACE` for external-content FTS writes (the docs say it is handled as ABORT); use tested UPDATE/UPSERT semantics. When installing triggers after existing notes, issue an explicit rebuild because trigger creation does not backfill. A periodic/on-demand external-content `integrity-check` with rank=1 detects disagreement; `rebuild` reconstructs postings from authoritative content, never deleting notes. Since both writes are in the same SQLite transaction, a failed/rolled-back note write rolls back the search change too; recovery still depends on the selected SQLite/VFS/filesystem mode. If search is missing, stale, or internally inconsistent, schedule rebuild and keep the source table untouched. Ordinary FTS deletion leaves old posting content until merges unless secure-delete is enabled; whether the product promises resistance to forensic/local-file recovery is unresolved, and secure-delete has speed and old-format compatibility implications.
- **Tantivy candidate:** store/index a stable note ID term and exact collection key; title/body use explicit text analyzers and positions; keep SQLite authoritative. Record every committed source mutation in a SQLite outbox in that source transaction. A serial consumer applies each ID in order: delete all indexed versions by ID, add the latest live source row (or leave deleted), Tantivy-commit, then acknowledge the outbox row in SQLite. Replaying after a crash between Tantivy commit and ack is logically idempotent. Rebuild a new index from a consistent SQLite snapshot, replay outbox entries since its snapshot watermark, catch up, then switch the active index generation; compare indexed IDs/revisions against source IDs. Missing/stale index documents trigger replay or full index rebuild, not source-note deletion. `IndexWriter` docs say operations are published after commit and commit returns after pending docs are published/persisted; this does not make the separate SQLite and Tantivy commits atomic.
- Return the original stable note ID and fetch title/body/collection from SQLite for current authoritative display. Proposed order: lexical score first and note ID ascending as deterministic tie-breaker; FTS5 BM25 assigns better matches numerically lower scores, while Tantivy exposes BM25 scoring and its collectors; the adapter must explicitly implement the same tie policy. Order is repeatable for a fixed query, corpus, analyzer, index generation, and component version, not a promise that corpus updates or a rebuild cannot change relevance rank. Do not imply FTS5 and Tantivy scores are numerically comparable.
- Produce a bounded excerpt (proposed 160 Unicode scalar values) from the current SQLite title/body near an actual query-term span, with explicit ellipses. Present plain text or escaped text plus UI-owned highlight spans. FTS5 `snippet`/`highlight` and Tantivy `Snippet::to_html` insert markup; neither excerpt may be blindly trusted as safe HTML or used as the authoritative content source. Poor language matching, no occurrence after normalization, deleted/missing rows, and stale-index candidates require a safe fallback or candidate rejection, not fabricated relevance.

## Required-clause coverage and open decisions

- **S1 query/tokenization:** bounded conjunctive terms plus exact phrases; explicit punctuation, Latin-accent folding, malformed/no-token behavior, and exact collection filtering above.
- **S2 comparator/consistency cost:** same-database FTS5 virtual table versus separate Tantivy index, different query/analyzer surfaces, trigger/rebuild cost versus outbox/commit/replay/generation-switch cost.
- **S3 lifecycle:** insert/update/delete, transaction/commit, crash/replay, missing/stale index repair, authoritative-note preservation above.
- **S4 identity/order/excerpt:** source note ID, fixed-state score plus ID tie-break, safe small excerpt from live source text above.
- **S5 identity/config/history:** no dependency version or app binary is selected yet. Pin the actual SQLite source ID/version and build/compile options (including FTS5 availability), or Tantivy Cargo package/version/features/schema/tokenizer and index generation. Sources document behavior, not a deployed app. Relevant history includes FTS5 contentless-delete introduced in SQLite 3.43.0 (not needed by the external-content proposal) and the cited Tantivy Windows mmap build fix at 0.20.1.
- **S6 validation:** matrix in the eventual draft must mark every row “proposed, not run” unless actual evidence is generated; no test, build, index, app, or crash simulation has run here.
- **Negatives:** no hosted service, network export, editor/sync build, raw SQL execution, semantic-search claims, destructive repair, or unsupported global absence claim is proposed.

Questions still needing an owner or schema decision: (1) Is the actual database the same local SQLite file on both target OSes, and is FTS5 available in the intended packaged binary? (2) What is note-ID type/immutability and collection-tag cardinality/key normalization? (3) Should ranking favor title, recency, or only lexical relevance, and how much cross-version stability is expected? (4) Is secure erasure from local database/index files part of the privacy promise? (5) What query UI error and result-count/latency bounds are expected? These do not justify assuming semantic search or expanding scope to editor/sync.
