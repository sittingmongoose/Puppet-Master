This is a scoped design recommendation, not application code. It preserves all S1–S6 and negative constraints in the brief.

## Recommendation

Start with SQLite FTS5 as an **external-content** index in the existing local SQLite database. Keep the note table as the only authority for note IDs, title, body, and collection relationships. The FTS table keeps searchable postings, while FTS5 obtains source text from the existing content table; this avoids a second full-body copy while retaining a source from which to rebuild. Install insert/update/delete triggers in the same database transaction domain, build the initial postings with `rebuild`, and check external-content consistency explicitly. FTS5 is conditional on the SQLite binary actually shipped on both Linux and Windows having FTS5 enabled and on a usable row-ID mapping. Its upstream manual describes the `SQLITE_ENABLE_FTS5` build path, but no target package has been inspected (S01–S04).

Keep Tantivy as the alternative if the pinned SQLite package lacks FTS5 and cannot be changed, or a future measured requirement justifies Tantivy’s separately controlled analyzer/index while the team accepts an outbox, replay, and generation-rebuild subsystem. Neither a performance winner nor a deployed capability is established. The 50,000-note scale makes FTS5 the lower-integration-cost starting point by architecture; that is a hypothesis, not a benchmark.

## Narrow query and result contract (proposal)

1. Accept at most 256 Unicode scalar values and at most 8 resulting term/phrase clauses. Plain Unicode letter/number runs are terms; whitespace and punctuation delimit terms. A balanced `"..."` groups its token sequence as an exact adjacent phrase; an embedded quote, unmatched or empty phrase, control character, or exceeded limit returns a visible input error. Empty or punctuation-only input returns an empty/no-search state, never “all notes.” Terms and phrases are conjunctive. There is no public `AND`/`OR`/`NOT`, field syntax, prefix/wildcard, regex, fuzzy, proximity, range, or match-all operator. `AND` typed as a normal word is data. The adapter parses first, then binds SQL values and builds a quoted FTS5 expression or typed Tantivy query; it never inserts user text into SQL or passes raw text to a backend parser. This avoids confusing SQL parameter binding (which alone does not define the intended FTS query language) with a bounded product grammar.
2. Initially use case-insensitive lexical matching without stemming or semantic expansion. For FTS5 set `unicode61 remove_diacritics 2`: punctuation is a separator and Latin accented forms are folded as documented; this is a bounded Latin policy, not universal transliteration or language-aware segmentation. For Tantivy, pin an explicit tokenizer/folding pipeline instead of silently accepting defaults. Its documented `AsciiFoldingFilter` maps some non-ASCII alphabetic, numeric, and symbolic characters to Basic Latin, so parity with FTS5 must be measured on agreed fixtures, including composed/decomposed accents and non-Latin scripts (S01, S06). A lexical match is not semantic understanding.
3. Search title and body. Each term must occur in title or body; each phrase must occur adjacent within one field. If a collection is selected, intersect it as an exact collection key against authoritative collection membership, not as free-text tokens. Resolve whether collection membership is one-to-many and how its keys are normalized. The brief does not say whether note IDs are integers or strings: if no suitable stable integer exists, add/use an integer FTS `content_rowid` and join back to the unchanged public note ID.
4. Return the unchanged public note ID and current title/body from SQLite. Proposed order is best lexical score, then canonical note ID ascending for ties: FTS5 BM25/rank ascending; Tantivy BM25 score descending. Tantivy's documented `TopDocs` tie-break is ascending `DocAddress`, which is not the public note identity, so collect all matching `(score, ID)` pairs on this stated 50,000-note corpus and sort by `(score, ID)` before page slicing, or implement a note-ID-aware collector. Order is repeatable only for the same query, corpus, analyzer, ranking configuration, index generation, and component version. It does not mean the rank is immune to corpus changes or numerically comparable between engines (S01, S11).
5. Generate a proposed maximum 160-scalar excerpt from current SQLite content, centered near an actual term span when available. Render as escaped text or separate UI-owned text/highlight spans; do not trust `fts5 snippet()/highlight()` markup or Tantivy `Snippet::to_html()` as safe HTML. If a candidate is missing, stale, or has no verified source occurrence, reject it or show a safe unhighlighted current-text fallback—never invent a match. Neither candidate warrants a universal language-quality claim (S01, S09).

## Lifecycle design details

### Preferred FTS5 path

Create an external-content FTS5 virtual table on the same local SQLite file, indexing title and body and mapping `content_rowid` to the source note key. If public IDs are not stable integers, use a stable integer surrogate as the FTS row ID while leaving the public note ID unchanged. Create AFTER INSERT/UPDATE/DELETE triggers that add a new row, issue FTS5's special delete with the old row ID and old indexed values, then insert the new indexed values on update. Avoid external-FTS `REPLACE`; make the source update statement and trigger behavior explicit. Create the FTS table/triggers and backfill/rebuild before enabling search. This follows official trigger ordering and rebuild rules (S01).

Because the content table and FTS index are in one SQLite database, a source mutation plus trigger-maintained FTS change can be committed or rolled back together. This is the main consistency advantage over a separate index. It depends on an actual FTS5-enabled build and supported local storage/VFS/journal behavior; SQLite's detailed atomic-commit article is rollback-mode-specific and states filesystem assumptions, while the transaction manual documents a single writer and rollback-causing failures. Check the actual journal mode and do not transfer the rollback-mode algorithm verbatim to WAL (S02–S04).

For repair, run the external-content integrity check with rank 1. If postings are incomplete, stale, or structurally inconsistent, rebuild them from authoritative note rows and verify after commit. Rebuild never deletes/rewrites authoritative notes. Search generation is “ready” only after a successful commit and integrity check. Initial backfill is mandatory when the FTS table is created over pre-existing notes. Consider secure-delete only if the owner defines a local-file/forensic deletion guarantee: FTS5 defaults it off; enabling it slows updates/deletes and can change compatibility with older FTS5 readers, and core SQLite secure-delete may also be needed for the database file (S01).

### Tantivy alternative

Keep the Tantivy index directory under the app’s local data directory. Use a schema with indexed title/body fields configured for the selected analyzer and positions, a stored/indexed exact note-ID key for delete/lookup, and an exact collection-key field if collection filtering is executed in Tantivy. Prefer fetching final display content from SQLite to avoid treating stored Tantivy text as authoritative. Use typed `TermQuery`/`PhraseQuery`/Boolean clauses; phrase fields require indexed positions (S06–S08). Tantivy `IndexWriter` add/delete operations are not searchable until commit. Its commit does not commit SQLite’s outbox acknowledgment, hence the ordered replay protocol above (S03–S04, S08).

Build a new Tantivy generation rather than clearing the live index in place during recovery: read a consistent DB snapshot and its high-water outbox sequence, bulk-index that snapshot, replay all later sequences, verify its indexed ID/revision set against source state, then atomically change the app’s active-generation marker. Keep the previous generation until the new marker is durable. Tests must prove queries never label an incomplete generation complete. This generation/outbox design is a recommendation, not a Tantivy built-in guarantee or a performed check.

## Owner decisions and rejected/uncertain points

**Owner decisions needed before implementation:** pin the actual SQLite distribution/version/build per OS; choose and persist note-ID-to-integer-row mapping if required; define exact collection key and multi-membership semantics; confirm Latin accent equivalence and user-visible malformed-query behavior; choose title/body weighting and result page bounds; decide whether secure erasure of local deleted index terms is promised; decide the permitted migration/outage experience while rebuilding.

**Rejected for this scoped draft:** hosted search, network export, editor/sync build, user text executed as SQL, raw backend syntax exposed as the product language, semantic-search claims, deleting authoritative notes to repair the index, and unqualified assertions that a candidate feature is absent from every released version.

**Uncertain until verified:** which SQLite/Tantivy version and build ships; whether the packaged SQLite enables FTS5; exact note-ID type and collection schema; cross-platform file and mmap behavior for pinned Tantivy; measured latency/disk use; crash behavior of the exact selected journal/filesystem mode; and whether the user expects exact phrase behavior across all languages. None is reported as an executed check.
