## Recommendation

For the three-depot pilot, keep a cooperative-controlled, durable crate identifier as visible text plus a simple 1D barcode, while leaving its exact namespace and syntax to the inventory steward. Keep shipment IDs, product IDs, and receipt/movement event IDs separate. A staff scan may resolve a crate or prefill an action; a staff member must explicitly choose and confirm “receive,” “return,” or another approved movement before a receipt event is recorded. Repeated scans must not silently create duplicate accepted receipt events.

Start with the existing spreadsheet or another already-available tool, preserving the current separation between crate identity and shipment. Keep a crate registry separate from an append-only event log. This is a planning choice for a small pilot, not a finding that the sheet already enforces uniqueness, concurrency, audit, or offline replay. Do not select Odoo, Snipe-IT, GS1 Digital Link, a barcode symbology, a scanner model, or an offline queue implementation without the owner inputs and validation below.

Retain the brief-authorized QR link to public crate-care instructions as an optional feature. It is not mandatory. A generic care page on a cooperative-controlled, stable HTTPS path is a simple route; the page and any redirect must expose care instructions only, not crate movements. If a redirect is used, the web owner governs it. If no stable, approved public route exists, defer the option pending that decision rather than excluding it as technically impossible.

## Suggested record model

| Record | Meaning | Key fields and relationships |
| --- | --- | --- |
| Crate | One physical reusable container for its full service life | crate_id (stable, unique across all depots), lifecycle/status, optional crate type; do not recycle its ID. |
| Shipment | One dispatch/transport record | shipment_id, origin/destination, shipment metadata; may be associated with many crates. |
| Product | A catalog item or contents type when relevant | product_id/SKU; separate from the crate and shipment. Contents can change between crate trips. |
| Receipt/movement event | One recorded occurrence | event_id, crate_id, event type, depot, actor, timestamp, optional shipment_id, outcome, and correction/reference when applicable. One crate can have many events. |

An offline queue, if approved, should assign a unique event_id before submission, retain the original event time and actor, display pending/synced/conflict state, and make replay idempotent. These are design proposals. The source review did not configure or verify any such queue.

### Offline and low-cost scanner tradeoffs

There are three different operations that should not be conflated:

1. **Decode**: a human can read printed text without any scanner. A simple 1D scanner may decode and enter the staff ID into an application field without network access. Odoo 18.0 warns that some scanners present as USB keyboards, depend on keyboard layout, and in some mobile/IoT setups may process characters separately [O06]. The exact scanner, host, language, application focus, and terminator are unknown; test them.
2. **Resolve or retrieve content**: a 2D reader or phone can decode a URL QR locally, but opening the public web page requires network access. A scanner that can read 1D may not read 2D; camera and dedicated 2D paths must be checked separately.
3. **Record and synchronize an event**: preserving a receipt event while offline is an application and owner-policy decision, not an inherent scanner behavior. Odoo's examined docs describe real-time operations; Snipe-IT v8.8.0's beta app/sync notes do not promise this crate workflow. No offline queue capability is established by the reviewed evidence.

For a minimal staff path, print a durable readable ID plus a 1D barcode encoding exactly the same ID. Do not tie the crate label to a shipment number. The relative-cost inference is that a 1D keyboard-style scanner and manual fallback generally require less scanning capability than a QR camera/2D reader; no product prices or exact device costs were researched.

## QR, redirect, care page, and label replacement

The optional QR should be separate from the staff identifier. A simple route is an ordinary QR encoding a cooperative-controlled HTTPS care-page URL. It can point to a generic public care page without encoding depot, shipment, staff, or movement data. When a printed URL must survive a page move, the web owner may preserve a stable path and redirect it to the new page. GS1's 2024 guidance describes redirects as an identity/content management handoff, recommends temporary 303 redirects in the GS1 case, and warns that some scan/short-link services collect scan time, location, device, or marketing data [G02]. Avoid an unapproved analytics service or open redirect. A direct page URL without a controlled redirect can break when the page moves.

For label replacement, recover the crate through the readable identifier or verified registry lookup, issue a replacement label with the same crate ID, and record a label-replacement event. Remove or void the damaged label. Do not create a new crate identity because the label was damaged. If a label still scans, it resolves the same crate. A public QR is not an alternate staff identity and neither a scan nor an opened page confirms that a receipt occurred.

GS1 Digital Link is an optional standards analogy, not a capability claim for this cooperative. Its QR decoding path requires conforming GS1 identifier syntax. The GS1 quick-start examples encode a GTIN and may qualify it with serial or lot information; these keys are not arbitrary internal field names [G01]. The GS1 resolver standard release 1.2.0, ratified January 2026, defines resolver-specific behavior; it does not imply different resolvers produce identical links [G03]. The GS1 standard's ]Q3 symbology identifier is relevant only when the selected decoder exposes and downstream software uses that metadata [G04, Z03–Z04]. A generic QR URL and a GS1 Digital Link are not interchangeable just because both appear inside QR symbols.

### Version and migration evidence

The strongest fit to label migration is Snipe-IT issue #19515. It reports v8.7.1 and says the old QR Code Text setting was not visible/carried into the New Label Engine, risking blank QR output after switching engines [S05]. The linked PR's code diff (commit 1e0fc8c, merged as c1d1cd1 on 2026-09-17) copies stored qr_text to label2_title on the transition from legacy to New Label Engine [S06]. Snipe-IT v8.8.0 (tag commit 2c466fa, released 2026-09-30) includes that fix; the same release adds 1D support to one Zebra label template [S04, S07]. The issue and fix are a specific settings migration and one template's output change, not evidence that all QR readers fail or that every Snipe version behaves identically. If any label engine or template changes, test saved settings, decoded payloads, human-readable identity, and scanner result on the exact output path.

Snipe's rolling Asset Tags documentation says changing configured zero-fill length does not rewrite existing tags [S01]. Avoid changing a pilot ID format after labels exist; if unavoidable, plan explicit old-to-new aliases, lookup precedence, and replacement-label reconciliation before migration.

A narrower GS1 parser history is useful only if a GS1 path is chosen. ZXing PR #1681 updated GS1 Application Identifier lengths per the 2023 spec; the change accepts increased lengths and deliberately leaves decreased/removed AIs as legacy-compatible behavior. It merged as commit 557b5fc and appears in ZXing 3.5.3 (tag commit f0f1a94) [Z01–Z02]. PR #1839 reports ZXing QRCodeMultiReader losing symbology identifier metadata, and the fix appears in 3.5.4 (tag commit f651b0a; PR commit 34588d8) [Z03–Z04]. This applies only when the cooperative uses those ZXing versions and that multi-reader metadata path. It does not establish that ZXing is selected or that the crate-care QR should use GS1.
