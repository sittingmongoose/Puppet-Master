This discovery used only the complete original brief and public primary documentation/source code. The exact-plan reveal has not yet occurred. ## Independently discovered workflows and recommendation

Two mature aggregation patterns are useful comparators. DPLA uses Content/Service Hubs that collect partner records, with a MAP-governed catalog, an API and bulk export. Its field reference preserves originalRecord and distinguishes rights about a source resource from rights asserted for a digital object. Europeana's provider flow uses EDM and an ingestion/enrichment/publication service (Metis); EDM separates the described cultural object, web resource and aggregation. These show a useful common pattern: source institution → collection/hub adapter → explicit mapping/validation → normalized catalog → public item/record links. Both products are examples, not preselected vendors. DPLA field documentation describes MAP 3.1 in its API while its separate profile page offers MAP 5.0; treat interface/profile versions independently. Europeana's public API key path now requires an account, so do not make it a pilot dependency without an owner decision. [S02–S09, S15, S17]

For five collections, recommend a network-owned scheduled-harvest catalog with a thin, versioned adapter per collection. Accept the best supported read-only feed (prefer OAI-PMH when offered; API/export where not); preserve every raw source record and immutable ingest/version metadata; then publish a searchable mapped view with links back to the collection. A live-federated query layer can be a fallback where a collection will not supply a harvest, but each request inherits source uptime, query/rate limits and heterogeneous fields, while prior statements may disappear before the network can retain them. IIIF Presentation API 3 is a strong optional object-viewer/publishing layer when already offered: it models a manifest, a displayable required statement, a rights URI, provider attribution and a dereferenceable JSON document. It is not an aggregation, search, update or deletion protocol. [S01, S05, S12]

## Rights and source neighborhood

Treat four concepts as distinct record assertions: (a) the collection-supplied rights/reuse statement and its source URI/literal; (b) a supplied copyright license URI, with its version/conditions and stated subject; (c) a public-domain assertion/mark (an assertion by the source, not an inference by the catalog); and (d) a network or collection access policy that controls viewing/download in that service. Europeana's licensing model separates metadata release (CC0 plus non-binding use guidelines) from edm:rights for previews/digital objects. The EDM definition scopes edm:rights across aggregation/web-resource structures; DPLA's API separates sourceResource.rights from object.rights. Keep metadata, original object, reproduction, preview and local access policy scopes distinct. Show the exact supplied statement and source; do not represent it as network approval or guarantee. [S03, S06, S08, S10, S11]

RightsStatements.org's 1.0 URI vocabulary offers useful machine-readable terms; CC licenses are licenses on supplied terms, CC0 is a rightsholder's public-domain dedication tool, and PDM labels a work believed to be already public domain. The vocabulary distinguishes Copyright Not Evaluated (no status inquiry) from Copyright Undetermined (an unsuccessful inquiry) and No Known Copyright (reasonable evidence of no remaining copyright, not a conclusion after no inquiry). Therefore an empty source field must remain “no statement supplied” and must not be converted to any of those URIs. Unknown, malformed, unavailable and conflicting source values need separate data states. A conflict should preserve every original value and locator, render “conflicting statements supplied” with links, and route to the collection registrar; do not choose a winner in mapping code. [S10, S11]

Build a source record neighborhood that stores source collection and persistent identifier, exact raw statement/value and field path, statement URI (if supplied), stated subject/scope, attribution text/entity and source page, source record URL, source schema/feed and mapped profile version, fetched-at time, source-reported modified time, ingest operation, and immutable prior versions. Keep normalized values alongside, never instead of, raw values. For URI crosswalks, keep the original term and the mapping URI, relation and mapping version. SKOS exactMatch is a high-confidence transitive equivalence; closeMatch is looser and non-transitive. PROV-O provides a compact model for source entity → mapping activity → derived catalog record and accountable registrar/network mapper. These are provenance aids, not evidence that a rights assertion is legally correct. [S03, S06, S12–S14]

## Update/migration findings

OAI-PMH provides incremental datestamp ranges and resumption tokens, but deletion guarantees are repository-specific: Identify reports no/transient/persistent deletion tracking. With no tracking, records can simply vanish and an incremental harvester cannot distinguish deletion from silence. Store the Identify response and use full snapshot reconciliation or an owner-approved stale-record policy when explicit tombstones are absent. For all feed types, retain source snapshots and diff by stable source ID; separate an update, explicit deletion, failed fetch and temporarily missing record. [S01]

Bounded mapping migration example: Europeana documents ESE’s flat-field migration to EDM. Its default mapping cannot always tell whether a date describes the source object or digitization, or whether a format describes the original or the digital file; the documented default makes broad assumptions and providers may replace the mapping or provide EDM directly. For the five collections, inspect each source schema and sample before mapping; require the registrar/metadata lead to decide ambiguous field scope. Never map an ambiguity into reuse permission. [S06, S07]

Bounded released aggregator example: DPLA ingestion3 commit 608ea023 (Issue 739, 2026-06-17) records a NARA deletion-handling fault: a preprocessing path had mistaken NaidsList membership rosters for deletion files. Its patch selects NAC_DESC_Deletes files and adds a zero-valid-delete gate; non-interactive execution halts, while a skip flag is an explicit exception. The pinned maintainer README says deletion records from April 2025–June 2026 may remain and leaves retroactive processing to the team. This is an observed source-code/runbook claim, not an independently reproduced production incident. The pilot should count and surface update/delete outcomes, use explicit tombstones when available, and make backfill a recorded owner choice. [S16]

## Optional visitor features, owners and constraints

Retain the supported optional reuse-help link and downloadable source-attributed metadata record in the proposal. IIIF 3 supports an informational rights URI and displayable requiredStatement; human-readable HTTPS links exist for standard statements. DPLA exposes JSON-LD and a downloadable export precedent. Recommend first showing the original statement URI/value plus its collection source and a short neutral “about this statement” link. Offer a JSON-LD/JSON metadata download only when each registrar approves source metadata exposure and the metadata lead pins the export shape/metadata-use terms; exclude image bytes and restricted fields. Keep this optional and gated; neither evidence nor the brief establishes universal source export permission. [S03, S10–S12, S17]

Owner rules: each collection registrar owns the truth, completeness, scope and correction of its supplied statement; the network metadata lead owns crosswalks, mappings, provenance schema, normalization rules and visible conflict behavior. Route legal, rights-status or policy ambiguity to those owners. Do not grant a new license, infer reuse from a visible thumbnail, scrape a restricted collection, or turn unknown into a public-domain statement.

## Method and validation boundary

Verification was grouped by governing neighborhood: one OAI-PMH pass for dates, format, tokens and deletions; one EDM/DPLA pass for entity and rights scope; one rights-vocabulary/CC pass for statement conditions; one IIIF pass for visible text, URI and record serialization; and one SKOS/PROV pass for mapping/provenance. Each condition was then resolved separately. Compared with ordinary sequential clause review, this reuses shared source bytes and avoids rereading a specification per obligation, without reducing obligation coverage or depth. No separate competent-reference artifact is an allowed discovery input, so no candidate-specific performance comparison is claimed.

Executed research checks: read the original brief; read the listed official documentation and pinned source evidence; inspected the DPLA commit through a read-only GitHub REST request. No collection feed, external product API, catalog implementation, rights choice, or legal conclusion was tested. Proposed validations (not run): per-collection schema/version and source-owner inventory; fixture ingest for supplied license, RightsStatements URI, supplied PDM, missing, malformed and conflicting values; visible text/source link review; statement-change and source-deletion simulations including OAI no/transient/persistent cases; mapping regression for ambiguous date/format; metadata download scope/attribution review; and zero/invalid delete count alert/backfill procedure. [S01–S17]
