# Planning proposal: a five-collection reuse-information catalogue

**Run:** A6-02-control · **Stage:** investigator · **Research cut-off:** 2026-10-10 UTC  
**Scope:** A pilot catalogue linking digitized objects from five museum collections. This is metadata and workflow research, not a legal determination, implementation, or product validation.

Source IDs below resolve to exact source identity, access method/time, locator, conditions, version, and applicability in [source-map.json](source-map.json). The [source index](sources/index.md) groups the public primary documentation and release/history evidence. “Observed” means what a cited public page, code, or history states. “Recommendation” is a local planning inference. No behavior described in vendor, standards, or aggregator documentation was exercised against a live product here.

## Recommendation

Plan a reversible, source-preserving pilot with one adapter and an audit trail per collection. Keep each collection’s supplied statement, exact URI/string, source record identifier and source link alongside any network mapping. Display the supplied statement and its source even when the statement is missing, disputed, changed, or unfamiliar. Route unresolved meaning to the responsible registrar and mapping questions to the network metadata lead. The catalogue records and presents source claims; it neither issues permissions nor adjudicates them.

Do not implement a reusable/not-reusable boolean or a standard permission badge on every thumbnail. Those would turn heterogeneous, sometimes descriptive statements into a new network claim, obscure uncertainty and access scope, and could imply permission from image visibility. Do not discard statement identifiers. A human-readable label is useful for people, but it is not a substitute for the stable URI and source text.

For workflow discovery, compare (a) Europeana Metis’ documented staged aggregation pattern and (b) an Omeka S collection-publishing path using CSV Import/API plus optional OAI-PMH output. Use the pinned DPLA Ingestion 3 pipeline as a third, code-backed comparator for source-specific mapping and update handling. Evidence does not establish Metis’ current availability, Omeka S as a complete five-source aggregator, or any of the three as the chosen platform. A product choice therefore remains open. The safest current product decision is to specify a shared record/provenance contract and run a bounded, non-production pilot against each collection before choosing an implementation.

A downloadable source-attributed metadata record and reuse-help link remain authorized optional scope. Retain both in the proposal, but do not promise capability or make either a release requirement until owners choose content and a target output profile is tested. A possible IIIF 3.0 pattern separates a machine-readable seeAlso record from a human-facing homepage or direct rendering; the format itself does not prove that a collection provides a suitable endpoint [S10, S14]. An Omeka S API response defaults to JSON-LD from public resources, while OAI-PMH publication depends on module configuration and has a documented deletion gap [S26, S27].

**Workflow inference:** Metis supplies the strongest cited example of a staged, provider-facing transform-and-preview process; Omeka S supplies documented collection entry/publishing mechanisms; DPLA supplies implementation and change-history evidence for aggregation. They cover different parts of the flow. No source proves that one package alone meets all pilot requirements. Compare them using identical, sanitized test fixtures and acceptance criteria: source retention, collection-specific maps, missing/conflicting status, visible provenance, update/delete reconciliation, record access vs media access, export profile, and failure reporting.

**Analogous controlled vocabulary and provenance mechanism:** SKOS gives explicit mapping relationships between concepts—exactMatch, closeMatch, broadMatch, narrowMatch, and relatedMatch. Only exactMatch is transitive; closeMatch is deliberately non-transitive [S16]. Getty AAT guidance models stable concept identifiers, terms, hierarchy, notes and source warrants rather than treating a label as the concept [S17]; Getty Linked Open Data materials show contributor/source/revision activity [S18]. W3C PROV-O can relate source entities, mapping activities, responsible agents and derived records, but does not create a log by itself [S19]. Recommendation: preserve each source value and URI; record a separate, versioned network mapping with relation type, target concept ID, mapping agent/rule, source warrant and date. Never equate a label string to a concept identifier or use a broader/close mapping as identity.

## Rights, reuse and access model

The catalogue should represent what the source says, who supplied it, what it refers to, and when it was observed. It should not make a new legal claim. Keep the following concepts distinct in schema and display:

| Information | Meaning for this pilot | Handling |
| --- | --- | --- |
| **Supplied rights statement** | A statement attached by a collection. It may describe a status or communicate a source’s position; its presence does not mean the network authored or independently confirmed it. RightsStatements.org says its statements are not licenses [S05]. For example, UND/1.0 means the provider reviewed status but could not determine it; CNE/1.0 means the provider has not evaluated it. Neither is the same as no statement or public domain [S20, S21]. | Preserve the exact URI and supplied label/text, registrar/source, scope, and retrieval/update time. Display it as supplied and visibly identify its source. Missing, unknown, unsupported, conflicting, or malformed input remains explicit; it is not replaced with a favorable default. |
| **License** | A license is an explicit instrument or grant with terms. The catalog should report an explicit source-provided license identifier and source wording without issuing one itself. Europeana’s guidance distinguishes CC licenses from RightsStatements.org descriptions and says an institution may apply a CC license only when it holds all relevant rights [S06]. | Do not infer a license from an image, thumbnail, collection membership, or a plain-text label alone. Do not normalize a source claim to a different license. Validate URI syntax and mapping while retaining the exact original. Refer scope/authority questions to the registrar. |
| **Public-domain assertion or tool** | A source may assert that a work is public domain, or use a public-domain tool. Europeana distinguishes CC0 (a dedication/waiver tool) from the Public Domain Mark, which identifies a work believed to be in the public domain; they are not interchangeable labels [S06]. | Preserve the exact source URI and wording, including its scope (underlying work vs digitized reproduction). Never infer a public-domain claim from absent rights, UND, CNE, an unsupported URI, a visible thumbnail, or a failed lookup. |
| **Local access policy** | A collection’s public/private setting, authentication, file restriction or embargo governs access to metadata or files. These controls are separate from reuse status. Omeka Access documentation explicitly separates resource visibility, file access and embargo; a resource notice may remain visible while a file is restricted [S28]. IIIF Authorization Flow is likewise an access/retrieval mechanism, not a license [S15]. | Model access policy separately, including whether it applies to metadata, a particular media file, a derivative or a manifest. Honor source access gates; never scrape restricted material. Visible metadata or a thumbnail is not a reuse decision. |

The public Europeana vocabulary is platform-specific and lists 14 accepted options [S06]. The Omeka Rights Statements module release page lists a dropdown of 11 statements and pairs selected human-readable names with linked-data URIs; its release is 1.2.1 from 2023 and is listed for Omeka S 3/4 [S24]. This release may be useful for controlled entry, but its page does not establish current statement coverage or the network’s accepted set. Omeka Value Suggest includes RightsStatements.org and Creative Commons suggestions, but users can ignore suggestions and type their own text; batch conversion may leave the structured label empty or preserve an existing label rather than importing a canonical one [S25]. These features must not be described as an enforcement or validation guarantee. Custom Vocab allows URI/label pairs, but duplicate URIs collapse to the last label and conversion may replace an original label [S29]. Preserve source values before any conversion.

### Missing and conflicting statement workflow

1. Ingest a source record without inventing a value. Record statement_status (for example, supplied, missing, malformed, unsupported, conflict, or pending review), raw value/URI, source URL and record ID, observed-at time, and applicable scope if known.
2. Continue to expose the supplied source text and source link, including when it is incomplete or unfamiliar. Present an explicit “not supplied” or “source values conflict” state instead of a default badge.
3. When two fields or sources disagree, retain both observations and their provenance. Do not choose the most permissive, newest-looking or easiest-to-map value automatically. Queue the discrepancy to that collection’s registrar; route mapping/provenance treatment to the network metadata lead. Keep the unresolved state visible until an owner decision is recorded.
4. If the source changes, append a versioned observation and reconciliation event; do not erase the prior source value. Mark whether an earlier record is superseded, retracted, unavailable or deleted only from source evidence and owner policy. A disappearance from a feed is not itself a confirmed rights change.
5. Keep rights interpretation separate from technical validation. A recognized URI can be syntactically valid while its applicability, scope or authority remains uncertain. Unrecognized and missing values are data to preserve and route, not errors to coerce into a public-domain or “not reusable” boolean.

This is a conservative workflow recommendation, not a legal rule or an executed workflow.

## Proposed record neighborhood and update contract

Each collection adapter should retain a raw source snapshot (subject to that collection’s permissions) and emit a normalized record without overwriting it. At minimum, specify and carry:

- network_record_id, collection_id, stable source_record_id, source-system and source-record URL, source collection/set, and source schema/profile/version;
- supplied statement label/text exactly as received, supplied URI exactly as received, source field/path, supplying collection/registrar, known statement version, and scope target (work, reproduction, file/media, thumbnail, manifest, record, unknown); keep raw and normalized/mapped values distinct;
- source attribution/provider and credited party separately; record whether text is a supplied visible statement, creator credit, publisher/provider label, or unresolved role;
- object/representation neighborhood where available: object URI, digital-object/media URI, IIIF manifest URI and version, isShownAt/landing page, thumbnail URI, and access/embargo status for each applicable resource. Do not let a work-level statement silently become a file-level statement or vice versa. EDM v5.2.7’s separate aggregation/WebResource scope and IIIF’s rights/required-statement fields demonstrate why these targets should be explicit [S08, S10]; their cardinalities are profile/version-specific, not universal rules;
- raw vocabulary URI/label, normalized concept ID and mapping relation, target scheme/version, mapping rule/version, mapping agent, date, source warrant and any review status. Keep source text, URI and mapping side by side; do not collapse distinct values into a copied label;
- first-seen, last-retrieved, source-modified, last-successful-sync, and mapping-change timestamps, plus the exact source version/snapshot or permitted digest. Record each ingest/transform/export activity, responsible software/person or rule and input/output entity relations (PROV-O is a candidate vocabulary, not an automatic implementation) [S19];
- per-source status and counts for created, updated, unchanged, missing, rejected, duplicate ID, conflict and deletion/tombstone observations. Retain tombstones/change events and link them to the last known source record. A failed or partial harvest must not be treated as a clean full snapshot;
- access-control metadata and local access policy in fields separate from reuse statements, including whether the restriction covers descriptive metadata, originals, derivatives, thumbnails, or manifests. Do not retrieve restricted assets to “complete” a record.

The exact output profile and retention/access policy are local decisions. They must be selected and documented before implementation. DPLA’s documented provider-specific maps and original records support adapter-level mapping and source retention as an operational pattern [S01]. Its NARA incident shows why update counts, delete validation, and explicit reprocessing decisions are needed [S02]. Omeka’s exact-match update semantics and OAI deletion TODO show that product defaults cannot substitute for an agreed source ID and reconciliation contract [S23, S26].

## URI, visible text, attribution and optional reuse-help/export

For IIIF collections, first discover which Presentation API versions are actually published. IIIF Presentation API 2.1.1 used license and attribution; 3.0.0 changed these to rights and requiredStatement, added structured provider, and changed the model/context [S09–S12]. Do not perform a blind rename: issue #1287 documents why a creator-like attribution can be different from publisher-defined rights/usage text, and the v3 specification distinguishes the machine-oriented URI from visible text. In 3.0, requiredStatement must be rendered; rights may or may not be rendered by a client [S10, S12, S13]. Preserve the original manifest and version, map only after checking semantics and allowed URI rules, and retain unmapped values in a visible/source-linked field. Do not attach a blanket statement to every thumbnail.

An optional help link should lead to a destination and wording approved by the owners; it should explain how to interpret the supplied source statement and where to ask questions, without asserting new permission. Keep it distinct from the statement URI and record provenance. A machine-readable metadata record may be linked by IIIF seeAlso; homepage is for a human-facing page and rendering for a directly consumable alternate representation such as a downloadable file [S10, S14]. Where Omeka S is selected, public API JSON-LD or configured OAI-PMH are candidate output mechanisms [S26, S27], but data fields, profile, visibility, output access, update/delete behavior, and compatibility have not been tested. Optional export must be limited to owner-approved fields and must not publish restricted metadata or media links. Proposed checks should include direct retrieval, correct content type/profile, provenance and attribution completeness, accessibility, stable URI behavior, and the target client’s ability to consume it; cross-origin behavior should be checked only where the chosen deployment requires it.

## Migration/history finding and collection-specific consequences

### IIIF Presentation API 2.1.1 to 3.0.0

The 3.0 change log is a released, backwards-incompatible migration record. license was renamed rights; attribution became requiredStatement; provider structure and the v3 context were introduced [S11]. The design issue explains that attribution was overloaded: a creator attribution can conflict with a publisher-defined rights notice [S12]. This is relevant when one of the five collections exposes IIIF, but research did not establish that any of them does.

For each collection, enumerate whether it supplies IIIF at all, manifest URI/version, supported client versions, whether rights is attached to the work/canvas/manifest or a specific media resource, and whether old manifests coexist with new ones. Build and review a collection-specific crosswalk. Preserve the raw v2 property and URI; map a recognized license to v3 rights only when its semantics and target URI are permitted. Reevaluate the old attribution value’s meaning before assigning it to requiredStatement; do not automatically copy creator credit into a rights statement or vice versa. Keep unknown values with source context for registrar review. Test whether any application hides the v3 rights URI visually and whether the required visible statement is shown. Pin source and target API versions and retain a rollback route.

Collection-level consequences remain unknown: one collection may have no IIIF; another may have v2 only; another may expose both a rights URI and a distinct visible credit; another may use custom extensions or a restricted manifest. Therefore, one successful manifest is insufficient. The five collection registrars must identify their feed/manifest versions and statement scope, and the metadata lead must own the crosswalk and provenance.

### DPLA NARA delete behavior as an update-history case

A second relevant history finding is the DPLA NARA delta-ingest issue documented at a pinned source commit. Incorrect delete file names/tags caused delete updates to be rejected; the described December 2025 and January 2026 runs processed zero deletes; a June 2026 script fix was recorded, while whether to reprocess prior cycles was left for a team decision [S02]. This shows that a code fix and a source-of-truth repair are separate decisions. It does not establish a current NARA issue, an issue in DPLA generally, or a bug in the five museum feeds.

For this pilot, validate each collection’s actual update mechanism: stable IDs; complete vs delta snapshots; semantics of omission, tombstone and explicit delete; expected and observed counts; correction/backfill procedure; and human approval threshold for destructive changes. A missing record in a partial feed or failed harvest should not delete the catalogue record. Maintain a quarantine/reconciliation report and require explicit owner policy before applying deletes. If a source exposes IIIF and also a record feed, record which source governs a rights change and how conflicting timestamps are handled.

### Suggested pilot exit criteria

Proceed to a platform decision only after all five collection owners identify their feeds, IDs, statement scope and access conditions; the metadata lead approves the profile/map/provenance contract; each adapter demonstrates source-preserving ingest and update reconciliation on a representative sanitized fixture; missing/conflicting/unknown states remain visible; no restricted media is fetched; and an agreed export demonstrates source attribution without exposing private fields. Record every exception and product/module version. A passing pilot demonstrates only the tested version and fixtures; it does not establish a legal conclusion or guarantee untested sources.
