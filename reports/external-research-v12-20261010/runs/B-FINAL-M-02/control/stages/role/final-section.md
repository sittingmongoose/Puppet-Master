# Latest-reading ingestion

Use PostgreSQL 17 at Read Committed to maintain one current row per device in a single `latest_reading` table. Define `device_id` as a non-null unique key and `observed_at` as non-null; store the reading payload in the same row. Apply the fixed settings `duplicate_policy=reject_batch`, `stale_policy=keep_newer`, and `max_batch_rows=100`. The caller assigns a batch identifier and validates the row limit before database submission.

Before issuing SQL, the caller scans the complete batch for repeated `device_id` values. If any repeat exists, reject the entire batch, report its identifier and duplicate IDs, and issue no multi-row INSERT. Do not choose one duplicate silently. PostgreSQL 17 documents `INSERT ... ON CONFLICT DO UPDATE` as deterministic: a statement cannot affect one existing row more than once, so duplicate proposed rows for the arbiter key can raise a cardinality violation ([PostgreSQL 17, INSERT, “ON CONFLICT Clause”](https://www.postgresql.org/docs/17/sql-insert.html)). The preflight enforces the requested policy and avoids relying on that database error.

For a validated batch, send one multi-row `INSERT` with `ON CONFLICT (device_id) DO UPDATE`. Set `observed_at` and the payload columns from `EXCLUDED` only when `EXCLUDED.observed_at > latest_reading.observed_at`. A previously unseen device is inserted. A conflict replaces the stored timestamp and payload only when the incoming observation is strictly newer; an older or equal timestamp leaves the stored row unchanged. This implements `stale_policy=keep_newer`, including the equal-time case. Use a timestamp type and input normalization that make the comparison meaningful.

The `device_id` unique key must be the arbiter named by the conflict target. At Read Committed, PostgreSQL handles a concurrent insert/update conflict by waiting as needed and applying the upsert to the conflicting row; the conditional comparison is evaluated against that row. Thus, among successfully committed writes for a device, an older observation cannot overwrite a newer one. The guarantee is limited to the selected conflict: unrelated constraint violations, missing privileges, trigger behavior, transaction failures, or other database errors can still prevent success. `ON CONFLICT` is not an unconditional success guarantee ([PostgreSQL 17, Transaction Isolation, §13.2.1](https://www.postgresql.org/docs/17/transaction-iso.html); [PostgreSQL 17, INSERT, “ON CONFLICT Clause”](https://www.postgresql.org/docs/17/sql-insert.html)).

Request `RETURNING device_id` to identify rows actually inserted or updated. PostgreSQL returns only successfully inserted or updated rows; a conflicting row locked but skipped because the `WHERE` condition is false is not returned ([PostgreSQL 17, INSERT, “Description” and “condition”](https://www.postgresql.org/docs/17/sql-insert.html)). Count returned IDs as changed, not all submitted IDs. With no trigger or other schema behavior suppressing writes, a successfully submitted ID absent from `RETURNING` is a stale/equal skip; confirm that assumption before reporting per-row outcomes. Do not publish success counts for a failed statement, and do not acknowledge batch success until its transaction commits. On failure, report the batch identifier and the database error; preserve enough diagnostic detail to investigate without claiming a partial successful batch.

**Prospective acceptance checks (not executed):** (1) Submit two rows with one `device_id`; verify whole-batch rejection occurs before any SQL. (2) Verify a new device inserts, a newer timestamp updates, and older/equal conflicts leave stored values unchanged and are absent from `RETURNING`. (3) Run competing upserts for one device at Read Committed and verify committed state never regresses; inject an unrelated constraint error and verify failure reporting with no success acknowledgement.

**Remaining uncertainty:** No DDL, trigger inventory, driver behavior, transaction wrapper, or database run was supplied. Validate the deployed unique key, timestamp/null handling, trigger effects, commit reporting, and concurrent error/retry policy. The checks above are proposed only; none has been executed.

## Critique dispositions

1. **Accept.** Reject duplicate keys in caller preflight. PostgreSQL 17, INSERT, “ON CONFLICT Clause,” documents the cardinality-violation restriction for repeated arbiter keys: [S1](https://www.postgresql.org/docs/17/sql-insert.html).
2. **Reject.** `last_row_wins` contradicts the frozen `duplicate_policy=reject_batch` and the caller-side rejection requirement; database convenience does not authorize changing that product rule.
3. **Accept.** A conditional conflict row locked but not updated is omitted from `RETURNING`; only inserted/updated rows are returned. PostgreSQL 17, INSERT, “Description” and “condition”: [S1](https://www.postgresql.org/docs/17/sql-insert.html).
4. **Reject.** Unconditional overwrite violates the strict-newer requirement and `stale_policy=keep_newer`; retain the timestamp predicate. PostgreSQL 17, INSERT, “condition”: [S1](https://www.postgresql.org/docs/17/sql-insert.html).
5. **Accept.** The upsert outcome is guaranteed only absent an independent error; report database failures and withhold success acknowledgement. PostgreSQL 17, INSERT, “ON CONFLICT Clause,” and Transaction Isolation, §13.2.1: [S1](https://www.postgresql.org/docs/17/sql-insert.html), [S2](https://www.postgresql.org/docs/17/transaction-iso.html).
6. **Reject.** PostgreSQL 17 supports `INSERT ... ON CONFLICT DO UPDATE` at Read Committed, including concurrent conflicts; Serializable is not required for this mechanism. The strict predicate may intentionally skip stale/equal rows. PostgreSQL 17, Transaction Isolation, §13.2.1, and INSERT, “condition”: [S2](https://www.postgresql.org/docs/17/transaction-iso.html), [S1](https://www.postgresql.org/docs/17/sql-insert.html).
