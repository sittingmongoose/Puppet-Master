### Latest-reading ingestion

The collector ingests at most 100 readings per batch into one PostgreSQL 17 table under Read Committed, keyed by device_id with observed_at. The table carries a unique NOT DEFERRABLE index on device_id used as the ON CONFLICT arbiter. Fixed settings are `duplicate_policy=reject_batch`, `stale_policy=keep_newer`, and `max_batch_rows=100`. Each batch carries a caller-generated batch identifier for diagnostics and uses a single multi-row INSERT for each accepted batch.

Before SQL, the caller validates the batch and rejects the whole batch without issuing INSERT when any check fails: more than 100 rows, any device_id repeated within the batch, or missing device_id or observed_at. It never sends intra-batch duplicate device_id values to SQL and never silently keeps one duplicate. Source statement (S1, PostgreSQL 17, INSERT / ON CONFLICT Clause): INSERT with ON CONFLICT DO UPDATE is deterministic and must not affect one existing row twice; a cardinality violation is raised otherwise, and proposed rows should not duplicate each other on arbiter attributes. Inference: pre-SQL rejection is therefore required to implement duplicate_policy=reject_batch. Full URL: https://www.postgresql.org/docs/17/sql-insert.html.

The statement is INSERT with ON CONFLICT (device_id) DO UPDATE SET observed_at = excluded.observed_at, payload = excluded.payload WHERE excluded.observed_at > readings.observed_at, requesting RETURNING device_id. Source statement (S1): the WHERE condition is evaluated after a conflict is identified; only rows where it returns true are updated, although all conflicting rows are locked. Inference: a strictly-greater comparison implements stale_policy=keep_newer. Strictly newer timestamps replace the stored row; equal or older timestamps leave the stored row unchanged. No overwrite-all path is allowed.

RETURNING reports only rows successfully inserted or updated. Source statement (S1, INSERT / RETURNING): rows locked but not updated because the ON CONFLICT DO UPDATE WHERE condition failed are not returned. Inference for accounting: the caller marks only identifiers present in RETURNING as inserted or changed, and treats submitted-but-absent identifiers as skipped-stale rather than changed. It must not mark every submitted row as changed.

Uniqueness and concurrency conditions are explicit. The device_id unique index must exist and be inferred as arbiter; DO UPDATE requires an explicit conflict_target. Source statements: S1 guarantees atomic INSERT-or-UPDATE only provided there is no independent error, even under high concurrency; S2 (PostgreSQL 17, 13.2.1 Read Committed) states that in Read Committed each proposed row either inserts or updates unless there are unrelated errors. Full URL: https://www.postgresql.org/docs/17/transaction-iso.html. Inference: concurrent updaters may cause waiting and re-evaluation against the newest row version. Unrelated check, foreign-key, not-null, permission, unique-index replacement, connection, or concurrent-schema errors can still fail the statement. No unconditional-success claim is made.

On failure the caller reports the batch identifier, the database error including SQLSTATE and message, and submitted, returned, and skipped-stale counts when known; when the statement fails entirely it emits no success counts. Prospective acceptance checks, none yet executed: (1) insert three new device_ids and require all three identifiers in RETURNING; (2) resubmit one device with strictly newer observed_at and require the update plus RETURNING presence, then resubmit with older observed_at and require no stored change plus RETURNING absence; (3) submit a batch containing an intra-batch duplicate device_id and require pre-SQL rejection with no INSERT issued. Duplicate, concurrency, and unrelated-constraint validations remain to be implemented. No database test has run.

#### Critique disposition

1. Accept. Intra-batch duplicates on the arbiter risk a deterministic-statement cardinality violation, so reject-batch must run before SQL. Source: S1, ON CONFLICT Clause, PostgreSQL 17, https://www.postgresql.org/docs/17/sql-insert.html.
2. Reject. Replacing reject_batch with last_row_wins changes an original product constraint and would send arbiter duplicates that S1 forbids. Evidence may correct facts but does not authorize changing fixed tokens or O3. Source: S1, deterministic statements, PostgreSQL 17.
3. Accept. Stale conditional updates lock the row but are not necessarily returned; only successfully inserted or updated rows are returned. Changed-row accounting must use RETURNING presence, not submission. Source: S1, INSERT / RETURNING, PostgreSQL 17.
4. Reject. Removing the strictly-newer predicate violates stale_policy=keep_newer and O4. S1 condition semantics support updating only when the predicate is true; simplification does not authorize overwriting newer stored timestamps.
5. Accept. ON CONFLICT guarantees insert-or-update only absent independent or unrelated errors. Unrelated constraints and concurrent failures can still fail the statement. Sources: S1 ON CONFLICT Clause; S2 13.2.1 Read Committed, PostgreSQL 17.
6. Reject. DO UPDATE is documented at Read Committed; S2 states Read Committed is the default and describes INSERT with ON CONFLICT DO UPDATE in Read Committed mode. No redesign around Serializable is needed, and O1 requires Read Committed.

Remaining uncertainty: exact SQLSTATE mapping for intra-batch cardinality violation versus other unique violations in this schema, contention behavior and retry needs under concurrent batches on one device_id, and unrelated-constraint failure taxonomy remain unverified. No database execution supports the checks above.
