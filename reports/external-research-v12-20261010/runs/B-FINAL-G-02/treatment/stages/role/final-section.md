### Sparse workspace onboarding

The onboarding helper creates one disposable Git 2.43 clone. Its recorded choices are `selected_dir=packages/editor`, `history_policy=full`, and `network_budget=unproven`. It applies cone-mode sparse checkout to packages/editor and presents the selected directory to the user. All commit history is retained; the clone uses no `--depth`, `--shallow-since`, or `--shallow-exclude` option.

Expected working tree. In cone mode the `set` argument is a directory list: all files under each listed directory at any depth are included, as well as files that are siblings of the listed directory or any of its ancestors (git-sparse-checkout, `set`; INTERNALS — CONE MODE HANDLING). For `selected_dir=packages/editor` the working tree therefore contains: (a) every file at any depth under `packages/editor/`; (b) every file immediately under `packages/`; and (c) every file in the toplevel directory. Parent-level and toplevel files are present by design through parent patterns; this section never claims that only `packages/editor` exists. With no directories specified, cone mode still includes toplevel files.

What each control does. Sparse checkout selects which tracked files appear in the working tree; it does not by itself filter object transfer or bound total bytes. Partial-clone blob filtering (`git clone --filter=blob:none`) requests a subset of reachable objects from the server and filters blobs until needed by Git (git-clone, `--filter`), with later on-demand fetching still possible. Shallow history (`--depth`) creates a shallow clone with history truncated to the specified number of commits (git-clone, `--depth`) and therefore violates `history_policy=full`. This helper keeps full commit history, uses sparse checkout for working-tree scoping only, claims no strict upper bound of selected-file sizes on network traffic, and records `network_budget=unproven` until measured byte-transfer evidence exists for a defined workload.

Recovery and local-change safety. Changing the selection must inspect local changes first and preserve them or stop for user action; it must not discard unstaged changes or unresolved conflicts to enforce sparsity. Merge or rebase can materialize paths outside the sparsity definition (for example to show a conflict), and a sparsify step can fail on an individual file for the same reasons; the helper then runs `git sparse-checkout reapply` after the user resolves, commits, or undoes those changes (git-sparse-checkout, `reapply`). `git sparse-checkout disable` restores the working directory to include all files (git-sparse-checkout, `disable`). Failed operations retain the exit status and chosen directories, and the helper avoids announcing a ready workspace until the command succeeds.

Prospective checks and limits. Three checks are planned and none has run; no Git command or test has run for this section and no real repository was altered: (1) list and open files under `packages/editor/`, `packages/`, and the toplevel to confirm cone inclusion; (2) run a merge-like operation that materializes an extra path, then `reapply`, and confirm the tree matches the sparsity definition; (3) run `disable` and confirm a complete checkout returns. Diagnostics capture command exit status, `sparse-checkout list`, and the file lists above. Network byte transfer and command runtime are unmeasured; the integration still needs measured byte-transfer evidence and a local-change recovery fixture before any efficiency or bound claim.

Disposition of received critique (sources: S1 https://git-scm.com/docs/git-sparse-checkout, S2 https://git-scm.com/docs/git-clone; live manuals retrieved 2026-10-10, target Git 2.43):

1. Accept. Cone mode includes files immediately under leading directories and the toplevel alongside recursive directory contents (S1, `set`; INTERNALS — CONE MODE HANDLING; CONE PATTERN SET parent patterns). The draft's only-selected-files claim is revised above.
2. Accept. Sparse checkout scopes working-tree presence (S1, DESCRIPTION) while `--filter` scopes object transfer with later fetching until needed by Git (S2, `--filter`). Neither establishes a strict byte bound without workload evidence, so the bound claim is removed and `network_budget=unproven` is kept.
3. Reject. `--depth=1` creates a shallow clone with history truncated to one commit (S2, `--depth`), which contradicts O4 and `history_policy=full` (full commit history, not merely a complete current tree). The final section omits `--depth`.
4. Reject. Merge or rebase can materialize extra paths and sparsify can fail on files with unstaged changes or conflicts, which is exactly when `reapply` is used (S1, `reapply`; EXAMPLES). O5 requires recovery, so reapply/disable are retained.
5. Accept. Removing `--depth=1` satisfies `history_policy=full` (S2, `--depth`), and recovery inspects and preserves local changes or stops instead of discarding them (S1, `reapply`). Both are reflected above.
6. Reject. A sparse index is an optional, experimental, default-off index-size and performance feature (S1, `set --sparse-index`), not a network control and not mandatory. It cannot support a claim of stopping all downloads, so it is not adopted as one.

Remaining uncertainty: version applicability rests on live manuals retrieved 2026-10-10 rather than a pinned Git 2.43 source; network byte transfer and runtime are unmeasured; no Git command or fixture has run, so cone inclusion, reapply recovery, and disable behavior are prospective until the three checks execute.
