### Sparse workspace onboarding

The helper creates exactly one disposable Git 2.43 clone for this onboarding. It records `selected_dir=packages/editor`, `history_policy=full`, and `network_budget=unproven`. In that clone, initialize cone-mode sparse checkout for `packages/editor` (for example, `git clone --sparse <repository> <disposable-dir>`, then `git -C <disposable-dir> sparse-checkout set --cone packages/editor`). This gives the user a focused working tree without changing any real repository.

Cone mode includes every tracked file under `packages/editor` at any depth, plus tracked files immediately inside each ancestor directory: the repository root and `packages/`. Thus root-level project files and files directly under `packages/` can appear alongside the selected subtree. Other sibling directories are not recursively included. If present, submodules retain their separate initialization state and are not automatically initialized or deinitialized by sparse inclusion rules. The working tree is not identical to “only the selected directory.” Git’s v2.42.0 `git-sparse-checkout` manual, “set,” “CONE MODE HANDLING,” and “CONE PATTERN SET,” describes these inclusion rules; its change history reports no manual changes from 2.42.1 through 2.51.1, covering target 2.43. [Git sparse-checkout, v2.42.0](https://git-scm.com/docs/git-sparse-checkout/2.42.0)

Sparse checkout selects working-tree paths; it does not by itself promise that other Git objects or blobs are never transferred. `git clone --filter=blob:none` is a separate partial-clone control that defers missing blobs until Git needs them. `--depth` is different again: it creates a shallow clone with history truncated to a commit depth. To honor `history_policy=full`, do not use `--depth`, `--shallow-since`, `--shallow-exclude`, or `--single-branch`. No byte-transfer cap follows from cone mode, and `network_budget=unproven` remains unmeasured. The Git 2.43.0 `git-clone` manual, “--sparse,” “--filter,” and “--depth,” distinguishes these options. [Git clone, v2.43.0](https://git-scm.com/docs/git-clone/2.43.0)

Before changing the selected directories, inspect the working tree for tracked edits, conflicts, untracked files, and ignored files in paths that may leave the cone. Preserve affected work in a verified safe copy or stop and ask the user to resolve it; never silently remove or overwrite it. Git documents that selection changes update the working directory and may delete ignored files in emptied directories. After a merge or rebase, Git may materialize out-of-cone files to show conflicts, and local changes or conflicts may prevent sparsification. Resolve, save, undo, or commit those changes first, then use `git sparse-checkout reapply` to restore the existing sparsity rules. `git sparse-checkout disable` turns off sparse checkout and restores all tracked files; inspect and protect local work before using it. If an operation fails, retain its exit status and show the command, paths, and diagnostic; do not announce readiness until the requested selection succeeds. (Git sparse-checkout v2.42.0, “reapply,” “disable,” and “set.”)

Three checks are prospective only. (1) In the disposable clone, compare materialized tracked files with the expected set: the selected subtree, root files, and files directly under `packages/`; report missing or unexpected paths and the sparse-checkout list. (2) In a disposable recovery scenario, place a local edit outside the proposed new selection and perform a merge-like operation that materializes an out-of-cone path or conflict. Confirm the helper preserves the edit or stops before changing selection; after resolving the scenario, run `reapply` and report remaining out-of-cone paths, status, and command diagnostics. (3) Run `disable` and compare the resulting tracked-file set with the complete tree, reporting missing files, conflicts, status, and exit code. None has been executed. Network bytes and runtime remain unmeasured; repository size, server behavior, later fetches, and workload can change both. The trial makes no transfer or timing guarantee.

**Remaining uncertainty:** The manuals define behavior, not this helper’s compatibility or data-safety implementation. Those claims remain prospective until the three disposable-clone checks run on the supported Git 2.43 environment.

## Critique disposition

1. **Accept.** Cone mode includes files immediately under the selected directory’s ancestors, including root-level and `packages/` files; remove the “only selected files” claim. (Git sparse-checkout v2.42.0, “set” and “CONE MODE HANDLING.”)
2. **Accept.** Sparse checkout and `--filter` control different things; neither supports a byte-transfer bound without measurement. Keep the budget explicitly unproven. (Git clone v2.43.0, “--sparse” and “--filter.”)
3. **Reject.** `--depth=1` truncates commit history. “Full history” cannot mean only a complete current tree; omit depth and keep history. (Git clone v2.43.0, “--depth.”)
4. **Reject.** Git says merge/rebase may materialize paths and conflicts or unstaged changes may prevent sparsification; `reapply` is a documented recovery after affected changes are resolved. (Git sparse-checkout v2.42.0, “reapply.”)
5. **Reject.** Removing `--depth=1` is required by `history_policy=full`; retain complete history and explain its distinction from working-tree sparsity. (Git clone v2.43.0, “--depth” and “--sparse.”)
6. **Reject.** A sparse index is an optional index-size/performance feature, not a network-transfer control; it cannot stop blob downloads. (Git sparse-checkout v2.42.0, “set”; Git clone v2.43.0, “--filter.”)
