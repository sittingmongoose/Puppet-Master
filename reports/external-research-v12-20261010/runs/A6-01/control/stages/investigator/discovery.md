# A6-01 investigator discovery

Scope: the exact original brief for a seasonal, one-route ferry board at two terminals. This discovery was made independently from the brief, before accessing the released plan. The proposal covers scheduled departures, disruption status, optional staff notices, safe stale or mismatched data behavior, and the owners' inputs.

## Findings from primary sources

### Schedule identity, service day, and time

GTFS Schedule is a zip dataset with routes, trips, stops, stop times, and date rules. A route groups displayed service; each trip has a trip_id and service_id. The service_id selects operating dates through calendar.txt and date exceptions in calendar_dates.txt. Service day is an agency-defined time period and often differs from calendar day. It may extend beyond midnight using times greater than 24:00:00. stop_times values use agency.agency_timezone, not the stop's timezone. A route, trip, service_id, stop, and timestamp therefore answer different questions and must not be substituted for one another. For this pilot, the board must resolve each trip against the right service date, date exceptions, and agency timezone before rendering a scheduled departure. [S01]

GTFS Realtime entities resolve IDs against an existing static GTFS feed. A TripDescriptor normally identifies a scheduled trip by trip_id; repeated/frequency-based trips need trip_id + start_date + start_time. start_date can also be needed for a trip that crosses midnight or is delayed into collision with the next day's trip. When trip_id is absent, route_id + direction_id + start_time + start_date is an alternative only if that combination resolves uniquely. A start_time used to identify one frequency trip is retained when the predicted departure changes; StopTimeUpdate carries the change. These are trip-instance matching rules, distinct from which service_id is active on a date and from alert applicability. [S02, S03]

The current GTFS Schedule reference was revised 2026-04-27. It recommends persistent IDs where possible, but IDs alone do not prove that a realtime entity belongs to the currently loaded schedule. feed_info.feed_version is a publisher-provided text version. A newer GTFS-RT FeedHeader has an optional feed_version that is defined to match that static version. GTFS Realtime version 2.0 is the protocol version, not the schedule revision. MobilityData recommends publishing the version in both places and keeping related IDs consistent. [S01, S02, S06, S07]

### Realtime messages, freshness, and mismatch

TripUpdates provide time changes for a trip and may describe cancellation, added or unscheduled trips, or stop-level skipped/no-data states. If a scheduled trip has no TripUpdate, the consumer must treat realtime as unavailable; the feed documentation specifically warns against concluding that it is on time. A NO_DATA stop provides no realtime timing. The board should therefore continue to display the schedule and label realtime unavailable, rather than manufacture an ETA. A supplied update can be an observed or predicted time; absent partner semantics, label it as a producer realtime update, not as a confirmed vessel position or guaranteed ETA. [S02, S03]

Service Alerts describe broader network, line, stop, or trip disruption context. The specification says delays and cancellations of individual trips should usually be communicated using TripUpdates. Alerts have active periods and informed-entity selectors; if active_period is missing, the alert remains displayable while it remains in the feed. Thus a route alert can be shown as a route/terminal disruption message, but must not be converted into a per-trip delay or cancellation. The June 2026 revision history adds communication_period and impact_period to distinguish when a notice is communicated from when service is affected; whether the partner publishes these newer optional fields is unknown. [S02, S04, S07]

GTFS Realtime best practices recommend refresh at least every 30 seconds (or when content changes), TripUpdates/VehiclePositions not older than 90 seconds, and Alerts not older than 10 minutes. A renewed header timestamp alone does not make old entity data fresh. These are recommendations for producers, not pilot execution results. Use the actual header and entity timestamps where supplied; let the owners approve the display threshold and wording. A stale feed should leave the schedule visible with its own source/version and mark realtime as stale or unavailable. [S05]

For a schedule-version mismatch, a product rule is needed because the RT schedule version field is optional. Proposed fail-closed behavior: retain the currently approved static timetable, do not apply RT entities when their explicit feed_version identifies a different schedule, and show that realtime is unavailable because versions do not align. If either side omits the version, do not claim a verified match; ask the operator and regional partner to confirm the binding and test the exact feed pair. This is an inference/product choice supported by the reference semantics, not a mandatory GTFS consumer rule. [S02, S06, S07]

### Analogous schedule-plus-event-stream mechanism

SIRI with NeTEx is a useful alternative when the regional partner already operates that ecosystem. NeTEx carries planned network/timetable data; SIRI carries realtime services. In OTP's published tutorial, SIRI-ET supplies predicted arrival/departure information for vehicle journeys and SIRI-SX supplies situation/disruption messages; both reference the Transmodel vocabulary used by NeTEx. OTP configures ET and SX separately as runtime updaters. This parallels schedule plus event/update streams but is not a promise that the ferry partner supplies SIRI, uses the same profile, or includes ferries in the relevant service. The SIRI repository identifies v2.2 as the current stable schema branch matching CEN documentation, with bug fixes only; national profiles and partner bindings still need confirmation. [S14, S15]

### Released consumer failure/fix chain and applicability

OpenTripPlanner issue #6252 described realtime lagging by up to 20 minutes under load. It named OTP 2.7.0-SNAPSHOT and National Rail GTFS with GTFS-RT; its configuration polled alerts each minute and trip updates every 27 seconds, with other polling feeds as well. The report's diagnosis was that fetching completed before graph application, so successive work accumulated and older updates remained in the queue. It did not provide a static GTFS feed_version or identify a particular timetable zip revision; this evidence is about update processing, not timetable identity. [S11]

PR #6262 linked to the issue, was merged into dev-2.x on 2025-01-09, and states that all polling updaters wait for graph update completion. The OTP 2.7.0 changelog dated 2025-03-12 includes that PR. The covered operation is poll-based updater completion/backpressure for all polling updaters; the issue does not establish which timetable revision is safe or prove that every deployment has no lag. OTP 2.10.0 is now the newer release. If Route B is considered, test the chosen released build under the pilot's actual polling/update load and record the exact schedule version and realtime feed version. The source PR lists no unit tests because it characterized the change as a performance issue. [S11-S13]

A separate, directly relevant specification evolution is the December 2024 addition of an optional GTFS-RT header feed_version matching GTFS feed_info.feed_version. It provides a schedule-pairing signal; its optional status means the pilot must not treat a missing value as a verified match. May 2025 also deprecated the ADDED relationship in favor of NEW and added REPLACEMENT; the parser/partner contract must name the producer's actual feed version and supported message types rather than assuming old examples cover current feeds. June 2026 added alert communication/impact periods. [S02, S07]

## Pilot decisions to carry forward

- Preserve the source schedule separately from each realtime message. Keep feed URL, publisher-supplied feed version, local retrieval time, header timestamp, entity update time, and validation state.
- For each displayed trip, retain route_id, trip_id, service_id, service date, terminal stop_id/sequence, scheduled time in agency timezone, and schedule version. Derive direction from the feed's stop order and owner-approved terminal mapping, not guessed direction labels.
- Display scheduled time as scheduled. Only show a distinct realtime time if a valid, fresh update matches the exact trip instance and approved schedule version. Cancellation/skip is a status, not an invented departure. If no update, stale update, missing schedule binding, or mismatch occurs, retain the schedule and state the precise realtime limitation.
- Match Alerts independently using their active period and informed entities; do not mutate trip rows from alert text.
- Treat manual notices as a separate editorial record and workflow, with explicit authorship, approval, start/end, affected scope, and withdrawal. Decide the wording and publication channel with the duty manager.
- Ask the schedule publisher for the exact GTFS zip, feed_info/feed_version, route/trip/stop IDs, calendar and calendar_dates interpretation, agency timezone, feed validity window, and change/rollback protocol.
- Ask the regional partner for the exact realtime endpoints, protocol/spec versions, TripUpdate/Alert/VehiclePosition coverage, identifier agreement, update cadence, available entity timestamps, header feed_version and behavior when schedule versions change, alert periods/selectors, outage behavior, and any national SIRI/NeTEx profile.
