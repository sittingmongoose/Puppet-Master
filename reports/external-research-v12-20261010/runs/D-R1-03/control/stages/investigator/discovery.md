## Four separate claims

1. **Bit-level continuity:** whether a particular byte sequence is unchanged between two evidenced points. A fixity match supports byte equality (subject to algorithm and trustworthy reference) only for the bytes actually hashed. A hash made now is a baseline for later checks; without a pre-migration baseline or source record, it cannot establish what happened during the earlier move.
2. **Identity of the recorded interview:** whether two files represent the same underlying interview/recording session. Byte equality is strong evidence that two files contain identical bytes, but does not establish either file is the authoritative or complete recording. A transcode changes bytes while possibly preserving interview content; names, dates, duration, or plausible content alone cannot decide identity.
3. **Completeness:** whether the extant media and transcript represent the expected interview, all sides/reels/segments, and intended beginning/end. A manifest can be complete relative to its listed payload while omitting an item absent from the expected inventory. An interior fingerprint hit or plausible duration does not establish completeness.
4. **Transcript-to-recording relationship:** which recording object or representation a transcript belongs to, including versions, segments, and timing. Filename similarity is a search clue only. A defensible link needs a stable identifier/crosswalk or documented source relationship, corroborating content/time anchors, and a recorded human decision; otherwise retain uncertainty.

## Strategy comparison

| Strategy | Can support | Cannot settle by itself / conditions |
|---|---|---|
| Read-only inventory and SHA-256/SHA-512 manifests | Current file set, paths and sizes; byte comparison against a preserved earlier manifest; missing/unlisted files relative to a defined package; later monitoring | Interview identity, transcript accuracy, consent, or completeness against an unknown expected inventory. Without a trustworthy dated source baseline, it is not historical continuity evidence. A path rename need not change bytes. Equal hashes on two paths indicate identical bytes under the selected algorithm, not two authenticated originals. BagIt treats payload bytes as opaque and names as package paths, not semantic identity. Record algorithm, tool/version, time, scope and validation result. |
| Metadata and relationship/event records | Candidate matches across renames/transcodes; format, codec, sample rate, channels, duration and embedded BWF fields; stable IDs and source/target relations; operator, tool, parameters and outcomes where logs exist | Metadata can be absent, stale, copied, rewritten or generated under a wrong clock. Tool-reported duration/format cannot show the interview is complete. PREMIS event detail/outcome are optional, so their absence does not prove no migration occurred. |
| Content-based comparison | Ranked near-identical/related audio candidates and reviewable points for possible alignment across transcodes, excerpts or renamed files | Fingerprint similarity is candidate evidence and depends on decoded content, algorithm/version and comparison window. Chromaprint explicitly is not general-purpose and trades precision/robustness for search performance. A whole-file match does not establish provenance; a partial hit does not establish completeness. Listening requires access/consent approval. |
| Bounded manual sampling | Low-cost, interpretable option for a small collection or when automated tools are unavailable: reviewers compare a declared sample of inventory rows, metadata, transcript anchors and (only if permitted) beginning/middle/end audio cues | Does not enumerate all relationships or yield a collection-wide error rate unless formally designed for that inference. Cannot reconstruct absent migration events. Record selection rules, independent reviewers, evidence viewed, disagreements and unreviewed strata. |

For renamed files, retain old/new relative paths and any independently supported stable identifier. Classify apparent copies separately as byte-identical, probable same interview/different representation, same interview/different or partial segment, distinct interview, or unresolved; do not collapse candidates. For transcodes, expect different hashes and require source/target object IDs plus a migration/normalization event before calling one a derivative. For partial files, check inventory expectations, duration/streams, content at multiple positions, and independent review. For transcript links, compare session identifiers, transcript provenance/version, and permitted time/text anchors; never link by filename alone.

## Preservation and implementation findings

- **BagIt 1.0 (S01):** defines package completeness and validity: every payload file must be listed in each manifest, and every listed checksum must verify. Payloads are opaque; paths have no meaning to BagIt. It recommends SHA-512 by default and requires BagIt 1.0 implementations to support SHA-256/SHA-512. This fits a read-only package witness, not recording identity or consent. The RFC says fixity is not protection against active attacks.
- **PREMIS 3.0 (S02):** distinguishes File, Representation, and Intellectual Entity; models structural/derivation relationships, object-linked Events, and event detail/outcome. Event date/time is mandatory and the dictionary recommends the most specific time with time zone; detail and outcome are optional. Record source/target relations and operation evidence when available; absence of optional fields is not proof nothing happened.
- **PBCore (S03):** offers media-focused instantiation relations for parts of one intellectual unit, generations, derivatives, and versions, using a related-item identifier. This can help express an audiovisual candidate but remains an assertion whose source/support must be reviewed.
- **Broadcast WAVE (S04):** may carry embedded provenance/technical clues when the extant file is actually BWF. LOC describes version history (v0/v1/v2 and supplements) and recommended use. Fields are not guaranteed to exist and do not independently establish truth, identity, or completeness.
- **Archivematica implementation (S06–S07):** 1.17.1 documentation says the workflow retains originals while normalizing to preservation/access formats under format policy, then creates AIPs with METS, PREMIS and BagIt. Thus two different files can intentionally coexist as original and derivative. 1.16.0 documentation says policies, commands and defaults can be locally changed and can evolve across releases; historic interpretation needs exact product release and local config.
- **Validator history (S08):** Archivematica issue #346 was opened in 2018 against AM 1.7.2, marked closed with 1.10.0 milestone, and reports error 110 for different paths sharing a checksum even when md5deep printed both items as passing. The public issue page does not establish the exact fix/current behavior in every release. Preserve per-file outcomes and raw logs; check duplicate-hash cases independently.
- **Audio matching history (S09–S11):** Chromaprint v1.6.1 (release commit aed8eba, 2026-07-28) includes a fix for dropped partial frames at non-frame-aligned input-buffer boundaries. Its README calls it a near-identical-audio fingerprint, not a general-purpose identity test, and describes a precision/robustness trade-off. Open issue #160 reports a Test3-specific short-input empty-fingerprint condition. Tool/algorithm version and short-window handling matter; do not treat a score as a verdict or missing output as evidence of difference.

## Reversible pilot proposal — not executed

1. Obtain authorization, consent/access rules, inventory scope, and a restricted report location before opening any interview or transcript. Use a read-only snapshot/copy, preserve observed paths and filesystem metadata, and record snapshot identity/time. Make no cleanup, rename, merge, transcode, upload, or publication.
2. Assign opaque pilot IDs. On the authorized copy, make a scoped inventory with path, size, reported file times, format result, SHA-256 or SHA-512, tool/version, UTC, operator, errors and report digest. Keep identity crosswalk restricted.
3. Compare any pre-move/source manifest with destination per item. Check same-name/different-hash and different-name/same-hash groups. Independently verify sampled entries with a second qualified implementation and preserve raw output. Label current-only inventory as a new baseline, not migration verification.
4. Characterize audio read-only: container/codec, channels, sample rate, duration, embedded metadata. If authorized and locally approved, use a pinned fingerprint tool only to nominate candidates. Exclude short fragments from negative conclusions until the exact algorithm is validated. Link transcripts via stable IDs and time/text anchors, never names alone.
5. Have a second reviewer independently assess a declared sample: include each anomaly class (renames, equal-hash duplicates, hash differences, suspected transcodes/partials, missing transcript links) plus a separately chosen random sample. Compare sampled relationship decisions to source records where available; record reviewer agreement/disagreement and method limits. For manual-only work, retain a small case ledger with evidence and rationale.
6. Record each inventory, characterization and check as a provenance event with input/output IDs, UTC/time zone, agent, tool/version, parameters, outcome, exceptions and log digest. Keep unresolved candidates with evidence, confidence basis, missing evidence and next request; do not force a duplicate/derivative classification.
