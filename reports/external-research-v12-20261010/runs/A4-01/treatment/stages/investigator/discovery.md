# Independent discovery: interrupted-upload archive accession

**Scope and status.** This is a pilot-scale planning investigation for 20 MB–40 GB film files over unreliable home connections. The archive’s provider, API subset, storage policy, and authoritative receipt point remain unknown. I used read-only public primary documentation, protocol documentation, and public release/issue history. I did not install software, access an archive account, create credentials or buckets, upload data, or validate an actual provider. The exact plan has not yet been released; this file records discovery from the brief alone.

## Early recommendation

Prefer a browser-to-object-store multipart route when the storage owner confirms the exact provider’s operations, limits, CORS behavior, checksum semantics, and cleanup policy. Keep the signing/control plane in the archive application: reserve a unique accession, authorize short-lived part requests, record upload ID and part plan, and complete only against server-validated part records. The browser reports transfer progress, not acceptance. After completion, the server must verify the final object and checksum using provider-supported semantics, then write an idempotent accession receipt. Do not treat a multipart ETag as a whole-file MD5.

Compare this with a browser-to-archive resumable server route using tus/tusd. It centralizes policy and can resume from server-reported offsets, but adds archive bandwidth, temporary disk, server capacity, distributed locking, and a storage backend that still must be compatible. A curator-authorized CLI may remain an optional fallback for very large files if the owner confirms endpoint, checksum, authentication, and support; public CLI options do not prove compatibility with this archive’s provider.

## Failure, recovery, integrity, and receipt design

1. Create a durable accession reservation with a unique idempotency key and unique destination key before issuing upload authorization. Repeated submission of the same accession should return or resume the same workflow; conflicting accession/file identity should require curator review. This is a local design inference, not a provider guarantee.
2. For direct multipart, persist upload ID, chosen part sizing, part numbers, expected file length, and server-issued authorization state. On reconnect, reconcile provider ListParts (including pagination) against the application’s plan; AWS ListParts pages at 1,000 and is for inspection, while completion must use the application’s recorded part list (S03). Re-uploading a part number replaces that part on AWS. Resume only after checking the source file identity/length and the authoritative current part state.
3. Abort stale uploads explicitly and configure lifecycle cleanup as a backstop. AWS has no default expiry for an MPU (S03); retain only as long as owner policy permits. Cleanup windows, retry windows, and storage cost exposure require the storage owner’s decision.
4. Use a declared, supported checksum algorithm from initiation onward. Verify each part where supported and verify the completed object against a full-object checksum or an independently recomputed digest using a provider-supported read/verification path. Record algorithm and scope: per-part, composite, or full-object. Never infer whole-file MD5 from multipart ETag. Provider support for checksum retrieval/validation must be proven before promising a receipt.
5. Complete, then verify the final object’s identity, size, checksum, and immutable version/generation identifier if the provider offers one. Only then issue an idempotent receipt containing accession ID, object key, provider/version identity, size, checksum algorithm/value/scope, verification result, and authoritative UTC time. The accession curator decides exactly which verification evidence makes this receipt authoritative. Progress bars, successful part PATCHes, and upload-complete UI state are insufficient.
6. For races, use unique keys and database idempotency first. AWS conditional writes add protection for supported final writes but do not reserve the MPU at creation; other S3-compatible implementations may differ (S11). A repeated completion should safely return the existing verified receipt or a clear conflict, never create a second accepted accession silently.

## Compatibility history worth testing

MinIO issue #20455 reports a concrete mismatch: with MinIO RELEASE.2024-09-13T20-26-02Z, an AWS .NET SDK PutObject carrying trailing SHA-256 returned a checksum header, while later ListObjectsV2/GetObject/GetObjectAttributes did not expose the checksum that AWS S3 exposed (S17). PR #20456 and commit f246ee7 merged a fix to persist the verified trailing checksum on 2024-09-19 (S18). I found no release tag proving which packaged MinIO release contains it; this is a code-level fix, not evidence that a deployed version has it. The observed operation was single PutObject and later retrieval, not multipart. It demonstrates why “S3-compatible” is not an operation-by-operation guarantee.

A second released chain is more directly resumability-related: tusd v2.10.1, tag commit 388a27c, released 2026-09-16, includes PR #1385 fixing silent truncation of deferred-length uploads in the S3 store (S10, S19). Keep Upload-Length known for browser-selected files when possible and test the deployed tusd tag/backend. This is evidence about that released tusd version, not the archive’s current software.

## Decision status and next evidence

**Owner decisions:** the storage owner must identify provider/product/version, supported API operations and checksum fields, consistency/CORS behavior, conditional-write semantics, lifecycle/retention and cleanup windows, and allowed endpoint/authentication pattern. The accession curator must define the evidence and exact state transition that makes a receipt authoritative, including duplicate handling. Costs remain unresolved input; quantify browser/storage egress, retained MPU parts, relay bandwidth, disk, operations, and support only after provider and traffic assumptions are supplied.

**Proposed validation, not run:** against a staging account and synthetic files only, test 20 MB, a multipart boundary, and a 40 GB sparse or generated non-film file; interrupt during a part and during completion; resume after browser reload/reselection; reconcile paginated parts; expire/abort an orphan; corrupt a part and final digest; repeat and race the same accession; test completion responses with embedded error; verify the final object checksum and receipt ordering; exercise provider CORS/signing; compare the CLI fallback on the confirmed endpoint; and test tusd’s configured release, disk limits, locking, expiry, and backend consistency. These tests require owner authorization and are not product validation performed here.

**Executed checks:** read-only review of linked public docs, protocol, release tag, issue, PR and commit context. No executable witness, install, account access, bucket/credential creation, live or synthetic upload, or local provider compatibility test was run. Those are NOT_RUN.
