# Interrupted-upload archive accession: final research proposal

**Status:** Complete planning proposal for the 20 MB–40 GB pilot; no implementation or archive-provider validation. The storage provider, version, supported API subset, retention policy, and authoritative receipt transition remain owner inputs. The investigation used public documentation and released public history. It did not access an archive account, install software, create credentials or buckets, or upload any film or test object.

## Recommendation

Keep browser-to-object-store intake as the preferred candidate, with a single-request operation for files that fit the confirmed provider’s single-request limit and multipart for larger files. Confirm the archive’s exact product/version and API behavior before choosing part sizing, checksums, signing, CORS, conditional writes, or cleanup. Keep the application in control of accession identity and upload state. Treat storage completion as an intermediate state: verify the resulting object under a curator-approved rule, then issue an idempotent accession receipt.

Compare that route with browser-to-archive resumable intake using tus and a server such as tusd. It centralizes policy and resumes from a server-reported offset, but requires archive bandwidth and capacity, temporary disk, backend consistency, and possibly distributed locking. For a distinct protocol analogy, compare Google Cloud Storage’s resumable JSON API session-URI mechanism; this is a recovery-pattern example only, not a recommendation to change the archive’s provider. Keep a curator-authorized CLI fallback as an optional path for the largest files if its exact client release, endpoint compatibility, narrow authorization, verification, and support procedure are confirmed.

## 1. Single-request and multipart operations

The revealed plan’s “5 GB limit on every upload route” is rejected. AWS documentation assigns 5 GB to a single PUT/PutObject request and separately documents a 160 GB S3 console workflow. Its multipart overview describes 5 MB–50 TB, while the quota page specifies a maximum object size of 48.8 TiB, 10,000 numbered parts, part sizes of 5 MiB–5 GiB, and no minimum size for the last part. These are AWS-specific statements about different operations; the differently expressed maxima are preserved as documented, not silently reconciled. See [AWS upload guide (S01)](https://docs.aws.amazon.com/AmazonS3/latest/userguide/upload-objects.html), [AWS multipart quotas (S02)](https://docs.aws.amazon.com/AmazonS3/latest/userguide/qfacts.html).

At a 5 MiB minimum part size, the count depends on exact bytes: decimal 40 GB (40,000,000,000 bytes) requires 7,630 parts by ceiling division; binary 40 GiB requires 8,192. Both fit AWS’s 10,000-part limit, but provider-specific bounds, chosen part size, retries, and exact file length must determine the plan. A 40 GB file exceeds AWS’s single PutObject limit, whereas a 20 MB file is below that AWS limit. Neither conclusion establishes the archive provider’s limits.

Cloudflare R2 is an illustration of operation and product variation, not a proposed archive backend: its upload guide states a 5 GiB single PUT, multipart up to 5 TiB with 10,000 parts and 5 MiB–5 GiB part sizes, equal-sized nonfinal parts, and default abort of incomplete uploads after seven days. Its separate limits page says 4.995 TiB. Preserve that documentation difference and do not borrow R2’s cleanup default for this archive. See [R2 upload guide (S12/C17)](https://developers.cloudflare.com/r2/objects/upload-objects/) and [R2 limits (S13/C18)](https://developers.cloudflare.com/r2/platform/limits/).

Checksum and completion behavior must be bound to operation and checksum type. AWS documents multipart full-object checksums for CRC64NVME, CRC32, or CRC32C; SHA-256 is available as a composite checksum, which combines part checksums rather than representing the same value as a direct whole-file SHA-256. Multipart ETag is not the whole object’s MD5. AWS’s integrity guide says that for composite or part-level multipart checksums, part numbers must be consecutive starting at 1; this condition should be carried into that checksum mode’s part plan and manifest, without generalizing it to every checksum mode or to another provider. For existing algorithms, if the checksum algorithm is omitted at CreateMultipartUpload, a completion checksum header can be accepted without being validated or stored. Specify the algorithm from initiation and record algorithm plus scope. See [AWS integrity guide (S05/C03)](https://docs.aws.amazon.com/AmazonS3/latest/userguide/checking-object-integrity-upload.html).

A direct REST client must parse the CompleteMultipartUpload response body: AWS can begin with HTTP 200 and later embed an Error. AWS SDKs handle that response behavior. Verify the selected provider and client before relying on it. See [AWS completion API (S06/C04)](https://docs.aws.amazon.com/AmazonS3/latest/API/API_CompleteMultipartUpload.html).

## 2. Two intake routes and a distinct resumable-transfer analogy

| Option | Shape and value | Constraints and applicability |
|---|---|---|
| **Route A: browser direct to object storage** | The archive application reserves the accession, signs narrowly scoped short-lived operations, and lets the browser transfer to the confirmed object endpoint. Select a single request or multipart based on exact file size and confirmed provider limits. This avoids relaying all file bytes through the archive server. | Requires confirmed API operations, CORS methods/headers and exposed ETag as needed, stable signing behavior, and a server-owned part manifest. Uppy’s current unversioned AWS S3 docs default to multipart only above 100 MiB; the threshold is configurable. Thus a 20 MB file takes the single-request path under that default, while larger files may also remain single-request until the configured threshold. That library default is separate from any service limit. Uppy Golden Retriever documents 10 MiB default IndexedDB file storage; references for larger files use temporary browser storage and may not survive a browser crash or restart, so reselecting the original file may be necessary. Pin and test the intended library release. See [Uppy S3 docs (S07/C05)](https://uppy.io/docs/aws-s3/) and [Golden Retriever docs (S08/C06)](https://uppy.io/docs/golden-retriever/). |
| **Route B: browser to archive resumable service, then object storage** | A tus 1.0 client uses HEAD to learn Upload-Offset and PATCH to continue at that offset; known Upload-Length suits a browser-selected file. A tusd service can apply archive policy before writing to the same object store. | Checksum, expiration, and termination are optional protocol extensions that a server must advertise. The checksum extension covers each PATCH body, not the complete archival object by itself. tusd v2.10.1’s S3 backend uses multipart storage, may write PATCH bodies to temporary disk, requires strong read-after-write consistency, and needs distributed locking when instances share a bucket. The final object is exposed after backend completion. Its 50 MiB optimal part-size recommendation and equal-sized nonfinal-part requirement are specifically documented for R2. This route adds relay bandwidth, disk, capacity, and operational work; it still requires a proven object-store backend. See [tus 1.0 protocol (S09/C07)](https://tus.io/protocols/resumable-upload) and [tusd v2.10.1 backend (S10/C08)](https://github.com/tus/tusd/blob/v2.10.1/docs/_storage-backends/aws-s3.md). |
| **Separate analogy: Google Cloud Storage resumable JSON API** | Google’s JSON API starts with POST Object using uploadType=resumable, returns a session URI, then accepts one or more PUT Object requests. After an error, a client can query the persisted offset and resume remaining bytes. This is a distinct session-URI recovery mechanism, included to make the “two routes and one mechanism” comparison additive. | The URI acts as a bearer capability and expires after one week; protect it and use HTTPS. A cross-origin browser must include Origin when creating the session for later CORS responses. The docs recommend final-object integrity checking and say intermediate chunks cannot be integrity-checked. This describes Google Cloud Storage only; it is an analogy, not an intake route for the archive or proof that its store supports this API. See [Google Cloud resumable uploads (R01)](https://cloud.google.com/storage/docs/resumable-uploads). |

The two actual intake routes remain Route A and Route B. The Google mechanism is separately compared to satisfy an additive reading of the brief without treating a second description of tus as a third option. The CLI below remains a separately authorized optional desktop fallback, not a mandatory third route.

## 3. Interruption, abandoned parts, checksum verification, duplicates, and receipt

Before granting upload authorization, create a durable accession reservation with a unique idempotency key and destination object key. Persist expected byte length, source/checksum plan, provider upload ID, chosen part sizing and number sequence, and application-owned part records. Replays of the same accession should resume or return the same workflow; a conflicting accession or changed source identity should be a curator-reviewed conflict. This is a local product proposal, not an S3 guarantee.

For direct multipart recovery, reconcile provider state with the application’s plan. AWS ListParts is paginated at 1,000 entries; maintain the part-number/checksum/ETag records used for completion rather than treating a listing as the completion manifest. Reusing an AWS part number replaces that part, so retry only after confirming the source and authoritative part state. Browser-side recovery may require the user to reselect a large source file. These behaviors and limits are AWS-specific and require provider confirmation. See [AWS multipart overview (S03/C12)](https://docs.aws.amazon.com/AmazonS3/latest/userguide/mpuoverview.html).

On abandonment, explicitly abort the multipart upload and configure lifecycle cleanup as a backstop after the storage owner sets retention. AWS incomplete multipart uploads do not expire by default and stored parts remain billable until completion or abort; its seven-day lifecycle example is not a default policy. Cleanup days, recovery windows, and resulting costs are owner decisions. See [AWS lifecycle examples (S04/C19)](https://docs.aws.amazon.com/AmazonS3/latest/userguide/lifecycle-configuration-examples.html).

Declare a supported checksum algorithm at initiation where required. Preserve whether a value is per-part, composite, or full-object. Verify final object identity and length plus a provider-supported checksum or an independently recomputed digest using a supported read path. Record an immutable version or generation identifier if the provider offers one. Never infer a whole-file checksum from multipart ETag.

Treat object completion as an intermediate state. The application should issue the authoritative receipt only after final-object verification passes the accession curator’s rule. The receipt proposal includes accession ID, provider and object/version identity, object key, exact size, checksum algorithm/value/scope, verification outcome, and authoritative UTC time. A progress bar, successful part responses, client “complete” state, or HTTP status alone is not acceptance.

Handle duplicate submissions first in application state: use a unique accession reservation and key, and make retries idempotent. Provider conditional writes can be a second guard where supported. AWS conditions apply to final PutObject and CompleteMultipartUpload, not CreateMultipartUpload or UploadPart; an in-progress multipart upload is not an existing object. AWS documents conflict/precondition responses for races, so retry behavior must be deliberate. Other providers may differ. See [AWS conditional writes (S11/C13)](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html).

## 4. Released compatibility history

A bounded MinIO history shows why an S3-compatible label is not an operation-by-operation guarantee. Issue #20455 reports MinIO RELEASE.2024-09-13T20-26-02Z with an AWS .NET SDK single PutObject carrying trailing SHA-256: the immediate response included the checksum, but later ListObjectsV2/GetObject/GetObjectAttributes did not expose it as AWS S3 did. PR #20456 and commit f246ee7 merged a fix on 2024-09-19 to persist the verified trailing checksum. The inspected issue and commit do not establish which packaged MinIO release contains that fix. This is a reported PutObject/retrieval mismatch and code-level fix, not a multipart result or evidence about the archive. See [MinIO issue (S17/C10)](https://github.com/minio/minio/issues/20455) and [fix commit (S18/C11)](https://github.com/minio/minio/commit/f246ee7).

A second released chain concerns the server route: tusd v2.10.1, tag commit 388a27c, released 2026-09-16, lists PR #1385 fixing silent truncation of deferred-length uploads in the S3 store. Validate the exact deployed tag and upload mode if this route is selected; the release does not show the archive uses tusd. See [tusd v2.10.1 release (S19/C09)](https://github.com/tus/tusd/releases/tag/v2.10.1).

## 5. Optional curator-authorized CLI fallback

Retain the largest-file CLI fallback as an authorized option, not a mandatory feature or established capability. AWS CLI v2 documentation provides one candidate to investigate: its S3 transfer configuration documents 8 MB multipart threshold/chunk defaults and a 5 MB minimum upload part; its checksum FAQ describes upload checksums with CRC64NVME as the default; and its cp reference exposes endpoint, profile, region, and checksum options. The cited pages identify different current AWS CLI v2 documentation releases (v2.37.6, v2.37.5, and v2.37.10), so pin the actual package before relying on combined behavior. These are client capabilities and AWS documentation, not proof of compatibility with the archive endpoint or its checksum implementation. See [CLI transfer config (S14/C14)](https://docs.aws.amazon.com/cli/latest/topic/s3-config.html), [CLI checksum FAQ (S15/C15)](https://docs.aws.amazon.com/cli/latest/topic/s3-faq.html), and [cp reference (S16/C16)](https://docs.aws.amazon.com/cli/latest/reference/s3/cp.html).

Enable this fallback only if the storage owner confirms the endpoint and required API/checksum behavior, and the curator approves a documented workflow with short-lived least-privilege authorization, safe retries, verification, and support ownership. If a specific required operation fails compatibility testing, leave the option unenabled and document that evidence; do not silently remove the authorized scope merely because it is unverified. No CLI was installed or used here.

## Independent critique dispositions

- **CI-01, part-number condition omitted — ACCEPT, with scope refinement.** The primary AWS integrity guide confirms the requirement for multipart composite or part-level checksums: part numbers start at 1 and are consecutive; nonconsecutive numbers can cause HTTP 500 at completion. The final carries this condition into that mode’s part plan. The critic’s shorthand “when using checksum mode” is broader than the governing text; this proposal does not generalize the rule to full-object mode or an unknown provider. See reviewer check RC01 and [AWS integrity guide](https://docs.aws.amazon.com/AmazonS3/latest/userguide/checking-object-integrity-upload.html).
- **CI-02, tus counted as both route and analogy — ACCEPT.** The wording can be read additively. The proposal keeps tus as the second archive intake route and adds the distinct Google Cloud Storage session-URI mechanism as a protocol analogy only. No provider switch is implied. See R01.
- **CI-03, 40 GiB versus 40 GB — ACCEPT.** The 8,192 calculation is labeled 40 GiB. For decimal 40 GB, the same 5 MiB minimum yields 7,630 parts. Exact bytes and the confirmed provider still govern sizing.
- **CI-04, 20 MB path implicit — ACCEPT.** The proposal states that current Uppy docs use multipart above 100 MiB by default, and the threshold is configurable. A 20 MB file therefore follows the single-request path under that default, if the selected provider supports that operation. The final leaves the archive threshold as an owner-confirmed client choice.
- **Critic’s overall classifications — RETAIN with the CI-01 qualification above.** No other material wrong claim or unsupported observed provider behavior was identified in the critique. The proposal labels its accession reservation, idempotency, and receipt contents as local design choices, and leaves external compatibility and cost inputs unresolved. No criticism is rejected.
