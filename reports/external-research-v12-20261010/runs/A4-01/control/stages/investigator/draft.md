# Research proposal: interrupted-upload archive accession

## Decision summary

**Recommendation.** Pilot a browser-first upload-intent flow that sends file bytes directly to the archive’s confirmed object store using per-operation, short-lived authorization and multipart upload for files whose failure cost makes whole-request restart unacceptable. Keep the application server in control of upload intent, metadata, keys, completion, verification, and receipt state; keep it out of the large-file data path. Select the multipart threshold and parallelism from synthetic-file tests under representative home-network interruptions. Keep a curator-authorized command-line fallback as an optional route for the largest files, subject to provider/version confirmation, least-privilege access, and a documented, tested command. Consider tus only if byte-offset recovery or a storage-neutral front end justifies an additional upload service.

This proposal is conditional on two explicit owner inputs: the storage owner confirms the live provider, version, operation/header subset, and retention policy; the accession curator defines when the accession receipt becomes authoritative. No storage product or retention rule is presumed, and no cost estimate is supplied.

The evidence records exact source URLs, version or commit where applicable, locator, retrieval UTC, operation, conditions/defaults/exceptions, and applicability in [source-map.json](source-map.json), with a browsable [source index](sources/index.md). Source IDs below are stable and map to those records.

## 1. Storage operations and limits

The phrase “S3-compatible” does not identify one size or checksum contract. For a bounded AWS S3 baseline, the AWS User Guide documents one SDK/REST/CLI PutObject request at up to 5 GB, while its separate console route supports up to 160 GB; the multipart API supports up to 50 TB. Multipart specifications are 48.8 TiB maximum object, 10,000 parts numbered 1–10,000, 5 MiB–5 GiB per part, with no minimum on the last part. AWS suggests considering multipart at about 100 MB. See [AWS-01](https://docs.aws.amazon.com/AmazonS3/latest/userguide/upload-objects.html) and [AWS-02](https://docs.aws.amazon.com/AmazonS3/latest/userguide/qfacts.html).

For the stated range, 20 MB is eligible for a single request on these examples; 40 GB exceeds the documented single-request limit and therefore needs multipart through AWS SDK/REST/CLI. That conclusion is about the named operation and documented product. A threshold below 20 MB might still be selected if restart cost warrants multipart overhead; it is a pilot choice, not a service requirement.

Cloudflare R2 provides a useful contrasting S3 API implementation. Its upload guide (last updated July 29, 2026) specifies 5 GiB for single PUT, 5 TiB and 10,000 parts for multipart, 5 MiB–5 GiB parts, equal sizing for all non-final parts, and a 7-day default abort for incomplete multipart uploads. Its limits are its product rules, not portable assumptions. [R2-01](https://developers.cloudflare.com/r2/objects/upload-objects/)

On AWS, the relevant multipart sequence is CreateMultipartUpload, UploadPart, and CompleteMultipartUpload, with ListParts and AbortMultipartUpload for recovery and cleanup. Initiation returns an upload ID and is where object metadata is set. Completion joins the provided part numbers/ETags in order; part numbers and ETags must be retained by the client. ListParts paginates at 1,000 and AWS cautions against using its listing as the completion manifest because unfinished parts are omitted. With additional multipart checksums, part numbers must be consecutive beginning with 1. [AWS-03](https://docs.aws.amazon.com/AmazonS3/latest/userguide/mpuoverview.html)

AWS accepts a specified full-object checksum on supported operations, computes the received object’s checksum independently, and fails completion with BadDigest when it does not match. Multipart checksum type matters: composite checksums and full-object checksums have different meanings. A multipart ETag is not necessarily the MD5 of the complete file. These are AWS behaviors to confirm against the archive provider’s exact operation/version. [AWS-03](https://docs.aws.amazon.com/AmazonS3/latest/userguide/mpuoverview.html), [AWS-04](https://docs.aws.amazon.com/AmazonS3/latest/userguide/checking-object-integrity.html)

### Browser constraints versus object-store limits

The browser does not create a larger object-size allowance: PutObject, multipart part count/size, checksum headers, completion semantics, and retention are provider/service properties. The browser path has separate requirements. The object-store endpoint must allow the application origin, the signed methods and headers, and the response headers the JavaScript needs to read. Uppy says ETag must be exposed for multipart completion and uses ListParts to resume and AbortMultipartUpload to cancel. Missing CORS headers can fail preflight before any upload begins. [UPPY-01](https://uppy.io/docs/aws-s3/)

Direct upload also depends on a still-valid signed URL and durable association between researcher, accession intent, object key, upload ID, and acknowledged parts. A progress bar or open tab is not a recovery record. Browser/device memory and local-file re-selection are client concerns; avoid whole-file buffering and verify the selected browser/library behavior for 40 GB. Cloudflare’s docs specifically note that an expired R2 presigned URL can fail without CORS headers on the response, leaving browser JavaScript unable to read the error body; this is R2-specific, but motivates testing expiry behavior for the chosen endpoint. [R2-03](https://developers.cloudflare.com/r2/buckets/cors/)

## 3. State, integrity, duplicates, and receipt

### Proposed state flow

1. **Create intent:** authenticate the researcher; reserve or validate the accession ID; record expected byte length, supplied source digest if any, object-store profile, and an immutable random staging key. Return an application upload token, not storage credentials.
2. **Transfer:** for a single request, show “uploading.” For multipart, store the upload ID and each acknowledged part’s number, ETag, and checksum. On retry, retry failed parts and reconcile from paginated ListParts. For resume, ensure the researcher can reselect the same file; a resumed upload must still match the recorded expected length and any curator-required source digest.
3. **Complete:** the server validates the part manifest and invokes CompleteMultipartUpload only once all intended parts are accounted for. Treat a completion error, 409/412, timeout, or ambiguous response as a recoverable state to reconcile, not as acceptance. Where supported, If-None-Match: * on PutObject/CompleteMultipartUpload adds a no-overwrite guard. AWS documents 412 for an existing current key and 409 cases that require a new multipart initiation; this is AWS-specific. [AWS-05](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html)
4. **Verify:** check that the completed object exists and its length matches the upload intent. Require a provider-supported full-object checksum that is validated on upload and retrievable after completion. If the provider cannot verify the required cryptographic whole-file SHA-256 on multipart completion, stream-read the completed staging object through an independent verifier and record its SHA-256. Compare with any researcher-supplied digest; do not trust the supplied value alone. Per-part checksum success and ETag alone do not prove whole-file identity.
5. **Curator decision and receipt:** persist verified object identity/digest and accession metadata. The curator’s explicit acceptance transition is authoritative. Only then issue the accession receipt. A UI can show progress, “transfer staged,” or “verification pending,” but never an authoritative accession receipt from a progress percentage or successful part calls alone.

### Abandonment and retention

AWS multipart parts remain stored and billed until completion or abort. Aborting frees existing parts, but in-flight requests can still finish, so stop part workers and verify cleanup. AWS lifecycle cleanup requires a configured AbortIncompleteMultipartUpload rule and deletes incomplete parts; it does not delete completed objects. [AWS-03](https://docs.aws.amazon.com/AmazonS3/latest/userguide/mpuoverview.html), [AWS-06](https://docs.aws.amazon.com/AmazonS3/latest/userguide/mpu-abort-incomplete-mpu-lifecycle-config.html) R2’s own docs state a 7-day automatic abort by default. [R2-01](https://developers.cloudflare.com/r2/objects/upload-objects/)

Set the exact expiry only after the storage owner approves retention. Add application cleanup for completed but unverified staging objects separately; an incomplete-MPU lifecycle rule does not remove them. Show expiry to the researcher and define what happens after expiry (start a new upload intent, retain accession metadata, and prevent accidental duplicate acceptance).

### Idempotency and duplicate accessions

Use an application idempotency key and unique accession constraint so network retries reuse the same intent/result. Keep staging keys unique per attempt and do not overwrite an accepted object. Conditional object writes are an additional storage guard only if the confirmed provider supports them; they do not make an object-store write and application database transaction atomic. On same accession plus same verified digest, return the existing accepted accession according to curator policy; on same accession with different bytes/digest, stop and request a curator decision. Filename and ETag are not deduplication keys.

### Receipt boundary

The storage owner determines whether provider-side completion/checksum calls behave as required. The accession curator determines the authoritative receipt point. Proposed minimum preconditions are: successful completion of the final object; expected length confirmed; independently validated checksum in the required strength; accession metadata durably recorded; no unresolved duplicate/collision; then curator-authorized acceptance. If storage completion succeeds but the metadata transaction fails, retry/reconcile from a durable state machine rather than issue a receipt early.

## 4. Relevant released compatibility history

A bounded example is MinIO’s checksum part-count handling. Issue #19670 reports that a multipart completion using AWS SDK for JavaScript @aws-sdk/client-s3 3.569.0 worked against AWS but failed against MinIO RELEASE.2024-05-01T01-11-10Z (commit 7926401) when the checksum had the AWS-style “-partCount” suffix. The issue reproduction says omission of the suffix worked in both. [MINIO-01](https://github.com/minio/minio/issues/19670)

PR #19680 states that it accepts the part-count suffix to improve AWS S3 compatibility, merged May 8, 2024; fix commit 0b245da modifies checksum parsing/validation. MinIO’s RELEASE.2024-05-10T01-41-38Z (commit b598402) includes #19680. This completes an issue → source fix → tagged release chain for a real CompleteMultipartUpload incompatibility. [MINIO-02](https://github.com/minio/minio/pull/19680), [MINIO-03](https://github.com/minio/minio/releases/tag/RELEASE.2024-05-10T01-41-38Z)

This is historical evidence, not a claim about every MinIO version or the archive provider. The GitHub page now identifies the minio/minio repository as archived on April 25, 2026; do not use this historical example as a recommendation to deploy that repository today. [MINIO-04](https://github.com/minio/minio)

### Correction to the frozen discovery record

After the discovery was frozen, rechecking the R2 compatibility table’s row boundaries showed an attribution error in the locked discovery.md. ## 6. What is already covered, what is optional, rejected, and uncertain

**Already covered by the brief and retained:** pilot scale; browser preference; optional desktop fallback; storage-owner confirmation and retention policy; curator receipt authority; unresolved costs; negative constraints; no-build/no-live-write research boundary.

**Optional improvements proposed:** durable upload-intent/state table; separate staging and accepted-object namespaces; upload expiry surfaced in UI; reconciliation worker for ambiguous completion; application idempotency key and conditional storage write where supported; separate cleanup of completed-but-unverified staging objects; checksum strength metadata attached to accession; memory/concurrency limits for CLI; a browser reselect/resume instruction. These add reliability detail without changing owners’ decision rights.

**Rejected draft assumptions:** one 5 GB limit across APIs/providers; ETag as the content digest; successful request/progress as proof of accession; deferred cleanup as sufficient; “S3-compatible” as proof of all AWS headers or operations; MinIO client as automatically compatible with the archive. The “single 5 GB for every upload route” statement is specifically corrected in Clause 1.

**Uncertain pending owners or tests:** actual provider/server release and endpoint; exact S3 operation/header subset; checksums available and whether whole-object SHA-256 is server-validated or needs readback; CORS and signed URL expiry semantics; lifecycle/retention behavior and days; supported max part/object sizes/count; browser/library version and safe concurrency; desktop OS and CLI package/version; allowed temporary credential mechanism; required cross-tab/workstation resume; curator duplicate policy and authoritative receipt transition; cost and staffing inputs. Uncertainty does not excuse investigation of the public facts above.
