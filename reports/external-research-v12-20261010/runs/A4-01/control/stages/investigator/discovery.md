# Investigator discovery: interrupted-upload archive accession

## Scope and status

This investigation uses only the released brief and public primary documentation, project source, and a released compatibility-fix history. It is a planning proposal for 20 MB–40 GB single-file accessions. The archive’s storage provider and supported S3 API subset remain unconfirmed; AWS S3 and Cloudflare R2 below are bounded product examples, not assumptions about the archive. Findings tagged [Observed] restate a source. [Inference] connects sources to this brief. [Choice] is a proposal for owner review. Source IDs resolve through source-map.json and sources/index.md.

No bucket, credential, account, live object, test film, downloaded code, or product service was used. No product validation was run. Every proposed check below remains NOT_RUN.

## Operation-bound size and transfer comparison (obligation 1)

| Product/operation | Documented limit or behavior | Applicability to this pilot |
| --- | --- | --- |
| AWS S3 SDK/REST/CLI PutObject (single request) | Up to 5 GB for one object. The separate S3 console upload limit is 160 GB and is not the browser-direct API contract. [AWS-01] | A 20 MB file can use one request, but interruption means retrying the single transfer; 40 GB needs multipart through these API clients. |
| AWS S3 multipart API (CreateMultipartUpload → UploadPart → CompleteMultipartUpload) | Current docs state 50 TB maximum object size (48.8 TiB); at most 10,000 numbered parts; 5 MiB–5 GiB per non-final part, with no minimum on the last part. Consider multipart at about 100 MB. ListParts returns at most 1,000 parts/page. [AWS-02, AWS-03] | All brief sizes fit the AWS documented service ceiling. At the 40 GB upper end, multipart is required. A product threshold between 20 MB and about 100 MB is a reliability/performance decision, not a service limit. |
| Cloudflare R2 S3-compatible PutObject vs multipart (bounded comparator, docs last updated 2026-07-29) | Single PUT max 5 GiB; multipart max 5 TiB/10,000 parts; 5 MiB–5 GiB each and every non-final part must have the same size. Incomplete multipart uploads abort after 7 days by default. [R2-01] | 40 GB fits R2 multipart by its own limits; R2 rules cannot be generalized to the archive’s unknown provider. Its operation matrix lists multipart operations but does not support the AWS x-amz-checksum-algorithm field on CompleteMultipartUpload; UploadPart lists Content-MD5 support. [R2-02] |

[Observed] On AWS S3, initiate the multipart upload with metadata/checksum type; retain its upload ID. UploadPart returns part ETags/checksum headers. CompleteMultipartUpload assembles parts by part number and needs the part-number/ETag list. The final multipart ETag is not necessarily an MD5 of the complete object. With a supported full-object checksum, AWS validates server-side and rejects mismatch with BadDigest. With additional checksums, part numbers must be consecutive from 1; nonconsecutive completion can return HTTP 500. [AWS-03, AWS-04]

[Inference] A reusable “S3-compatible” claim is insufficient to select either size ceilings or checksum/completion semantics. Store provider, product release, endpoint, and tested operation/header set as an explicit compatibility profile. Keep service operation limits separate from client library thresholds and server/proxy limits.

## Intake approaches and analogous resumability (obligations 2 and 5)

1. [Choice, preferred browser route] Browser-to-object-store multipart, with the application as control plane. Uppy’s current AWS S3 plugin documentation describes direct browser uploads to AWS and S3-compatible stores; its sample pins Uppy v5.2.1, uses a server signRequest endpoint, and supports PutObject for small files or Create/Upload/List/Complete/Abort multipart calls for larger ones. The endpoint should issue short-lived URLs per allowed operation/key and keep durable credentials server-side. Browser CORS must allow the application origin, methods, and signed request headers; JavaScript must be able to read ETag (and Location where needed). [UPPY-01] The browser does not change a provider’s PutObject or multipart limits. Its distinct constraints are CORS visibility, signing/URL expiry, tab/device lifecycle, persisted upload state, local-file re-selection, concurrency, and browser-specific resource limits. Avoid buffering a 40 GB object as one in-memory blob; validate the selected browser/library’s chunked path.
2. [Choice, optional desktop route] A curator-authorized command-line path using an S3-compatible transfer client such as rclone, after the provider endpoint and permissions are supplied by the storage owner. Rclone’s online S3 docs describe a configurable single-to-multipart cutoff (default 200 MiB), chunk size and concurrency, and memory use proportional to transfers × concurrency × chunk size. They also describe per-part MD5 checks and a post-upload HEAD/ETag check, while noting multipart objects do not have an ordinary whole-object MD5 ETag. [RCLONE-01] This is a candidate for a researcher with local disk and command-line ability; the brief does not mandate it. Do not imply cross-process resume from the cited docs. Keep it disabled until the curator authorizes the case and the owner approves a narrowly scoped, short-lived access path and tested command/version.
3. [Analogous mechanism, not an S3 API] tus 1.0.0 resumes by HEAD to read Upload-Offset then PATCH from that offset; its optional checksum extension verifies each PATCH body, not automatically the entire final object. Expiry/cleanup is server-advertised policy, not implied by core tus. [TUS-01] The released tusd v2.5.0 S3Store can write to AWS or compatible stores, but its implementation buffers PATCH parts to temporary disk before S3 submission; interrupted oversized parts must be resent. Its shipped defaults include 50 MiB preferred part size, 10,000 parts, 5 TiB MaxObjectSize, 20 disk-buffered parts, and 10 concurrent S3 part uploads. [TUSD-02, TUSD-03] This option introduces a service to operate and disk/endpoint compatibility requirements. Consider it only if byte-offset resumability or backend isolation matters more than direct S3 simplicity; no service has been tested here.

## Recovery, cleanup, integrity, duplicate handling, receipt (obligation 3)

[Inference] For direct multipart, create an application upload-intent record before the object upload. Keep the accession ID, intended immutable staging key, object upload ID, expected length, provider/version profile, signed-URL expiry, and each acknowledged part number/ETag/checksum. On a lost connection, retry failed parts, reconcile with paginated ListParts, and resume only while the upload remains valid. AWS warns to maintain the client’s own part ledger for completion rather than using ListParts output as the completion body; it omits unfinished parts. [AWS-03] A refreshed page or a different workstation cannot resume merely from the browser progress bar unless the server retained the intent and the researcher can reselect the same source file.

[Observed] AWS retains uploaded parts and charges their storage until a multipart upload is completed or aborted; aborting releases parts, though in-flight part uploads may still finish, so stop workers and then confirm cleanup. AWS lifecycle abort is not automatic unless configured; it removes incomplete parts after the chosen age and has no effect on completed objects. R2 documents its own 7-day default. [AWS-03, AWS-06, R2-01] [Choice] Expose a cancel action that aborts; schedule provider-supported incomplete-upload cleanup as a backstop. Set retention days only after the storage owner confirms retention policy. Treat a completed-but-unverified staging object separately; incomplete-MPU lifecycle does not delete it.

[Observed] AWS S3 independently calculates and checks its supported upload checksum; multipart checksum type matters. A composite checksum/part checksum is not necessarily a simple digest of the entire file. ETag is not a trustworthy general content hash for multipart, encryption, or compatible providers. [AWS-03, AWS-04] tus Checksum is per PATCH. Rclone’s documented multipart check uses per-part MD5 and expected ETag; it is useful transfer evidence but not proof of an independently computed archival SHA-256. [TUS-01, RCLONE-01] [Choice] Require a provider-verified checksum capability for completion. If the archive needs a cryptographic whole-file SHA-256 and the provider cannot validate that full-object checksum on multipart completion, stream-read the completed staging object through an independent verifier, compare against any researcher-supplied digest, and persist the verifier’s digest. A client-supplied digest alone is not validation. No validation from progress percentage or ETag alone.

[Choice] Make the application’s accession state authoritative, with an idempotency key and unique accession constraint; use an immutable per-attempt staging key, then promote/link only after verification. If the provider supports conditional CompleteMultipartUpload, use If-None-Match: * as an additional no-overwrite guard, not as a substitute for the database transaction. AWS supports it for PutObject and CompleteMultipartUpload; its semantics include 412 on an existing key and 409 cases requiring a fresh multipart initiation. Versioning only protects old versions, not the curator’s duplicate policy. [AWS-05] Duplicate submission with the same accession should return the existing state if the curator-approved identity/digest matches; different content should stop for a curator decision. Never deduplicate by filename alone.

[Choice] The upload UI may say “bytes sent” or “object staged”; it must not issue an authoritative accession receipt until multipart completion succeeded, the completed object’s expected length and independent checksum pass, accession metadata are committed, and the curator’s acceptance rule is satisfied. The curator—not the transport—owns the exact authoritative point. A transaction/outbox or equivalent retry-safe boundary is needed so storage success with database failure cannot issue a false receipt.

## Compatibility failure/fix history (obligation 4)

[Observed] MinIO issue #19670 records a reproducible AWS-versus-MinIO difference: with AWS SDK for JavaScript S3 client 3.569.0 and MinIO RELEASE.2024-05-01T01-11-10Z (commit 7926401), CompleteMultipartUpload accepted a SHA256 composite checksum without “-partCount” but rejected the AWS-accepted checksum formatted as {checksum}-{numberOfParts}. [MINIO-01] The linked PR #19680 says it fixes that issue, merged on May 8, 2024; commit 0b245da adds part-count parsing/validation. [MINIO-02] MinIO RELEASE.2024-05-10T01-41-38Z (commit b598402) lists PR #19680, so this is a release-bound fix, not an inferred repair. [MINIO-03] The repository page now says it was archived Apr 25, 2026; retain this as a historical compatibility case, not a present product recommendation. [MINIO-04]

[Inference] Even within one operation, checksum encoding and completion behavior can vary by implementation/version. A pilot needs a minimal conformance suite against the owner’s exact endpoint and server release before it signs URLs or accepts receipts.

## Owner decisions and unresolved inputs (obligation 6)

- Archive storage owner: confirm provider, endpoint/region, exact server release/API profile, supported operations (initiate, upload part, list/paginate, complete, abort), maximum object/part size/count, CORS/presign behavior, checksum algorithms/types at initiate/part/complete/HEAD or GetObject, conditional completion support, versioning, encryption, and lifecycle behavior. Confirm retention policy and expiry/cleanup days. No provider or retention policy is assumed.
- Accession curator: choose when an object becomes an authoritative accession, whether a supplied source hash is required, how same-accession/same-content and same-accession/different-content submissions are handled, and whether/when the CLI option is authorized.
- Cost: unresolved input. Multipart calls, checksum/readback bandwidth, temporary storage, lifecycle, and optional CLI support may affect cost, but no price estimate or budget has been invented.
- Researcher workflow: confirm whether resume must survive tab closure/workstation change and how a researcher can regain access to a particular upload intent without exposing another accession.

## Initial recommendation and validation status (obligations 7–8)

[Choice] Pilot browser-direct presigned multipart, retaining a small-file single PUT option and selecting the multipart threshold from observed pilot interruptions; use a random immutable staging key, persisted part ledger, provider-verified completion checksum, independent full-file verifier where needed, configured abandoned-upload cleanup, and delayed receipt issuance. Keep curator-authorized rclone as a conditional, documented fallback for largest files only after both owners approve its privilege and workflow. Keep tus/tusd as a measured alternative if direct browser resume proves insufficient, not as a hidden assumption.
