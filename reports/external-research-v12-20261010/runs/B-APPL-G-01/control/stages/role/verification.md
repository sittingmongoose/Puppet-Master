# B-APPL-G-01 — Redis session timeout applicability

**Case:** ER12-B-APPL-G-01-FRESH · **Role:** Applicability/exception verification

Scope is Redis Open Source 7.2: one primary with replicas, session stored as a string or hash. Conclusions concern the specified successful Redis command on the node executing it. The references are live Redis command pages; histories establish that `SET KEEPTTL` (6.0.0) and `EXPIRE GT` (7.0.0) exist in 7.2. No claim is made about an unreported client wrapper or failover durability.

1. **Supported, bounded.** On an existing hash key, `HSET` updates the hash in place and preserves its existing key-level timeout; it does not refresh or extend it. The Redis [`EXPIRE` reference](https://redis.io/docs/latest/commands/expire/) (“Refreshing expires”) names `HSET` among mutations that leave the timeout untouched. Applies to Redis OSS 7.2 and the described existing hash. If it had no timeout, it remains persistent; delete/recreate or whole-key replacement has different semantics.

2. **False.** A successful `SET` without an expiry option or `KEEPTTL` replaces the value and clears the old timeout (the `EXPIRE` reference’s example shows `TTL` becoming `-1` after `SET`). Correct wording: ordinary successful replacement makes the key persistent unless the command supplies a new expiry or `KEEPTTL`. Failed conditional `SET` (for example, unmet `NX`/`XX`) does not replace the key; explicit expiry options set a new timeout. See Redis [`SET`](https://redis.io/docs/latest/commands/set/) and [`EXPIRE`](https://redis.io/docs/latest/commands/expire/) references.

3. **Supported for the primary command, with scope limits.** Redis [`SET` reference](https://redis.io/docs/latest/commands/set/) says `KEEPTTL` retains the key TTL; its history dates the option to 6.0.0, so Redis OSS 7.2 supports it. A successful `SET key value KEEPTTL` changes the string and retains an existing timeout while its countdown continues; a persistent key stays persistent. This establishes command behavior on the executing primary, not survival across promotion: durability settings, replication state, retries, and failover trace are unknown.

4. **False.** Redis [`EXPIRE` reference](https://redis.io/docs/latest/commands/expire/) says `GT` requires a later expiry and treats a non-volatile key as having infinite TTL. Thus a finite positive duration cannot attach an expiry to a persistent key; `EXPIRE key seconds GT` is skipped (reply `0`). `GT` exists since 7.0 and applies in 7.2. Correct wording: use an unconditional positive `EXPIRE` or `NX` to add an expiry to a persistent key; `GT` may extend an existing finite expiry when the proposed deadline is later.

5. **False.** Redis [`keyspace notifications`](https://redis.io/docs/latest/develop/pubsub/keyspace-notifications/) says a non-positive `EXPIRE` deletes the key immediately and emits `del`, not `expired`. Ordinary timeout expiration emits `expired` when Redis actually deletes the key. Notifications are disabled by default; even when enabled, Pub/Sub is fire-and-forget, so a disconnected subscriber can miss events. The event names therefore require explicit notification configuration and an available subscriber.

6. **Not established.** The cited notification reference describes passive expiry on access and incremental background expiry; it gives no guarantee of an `expired` event at TTL zero and notes delay can be significant with many idle TTL keys. That is not a service p99 guarantee. The fixture supplies no benchmark, workload, host/resource profile, exact build/configuration, failover trace, or definition of “cleanup” (request rejection, key deletion, or consumer observation). Correct bounded statement: **the <25 ms p99 target is unverified**. Resolve it with measurements on the actual Redis 7.2 service under the specified replica failover and representative load, defining the start at the expiry deadline and the end as the service’s chosen cleanup outcome. No operational timing is inferred from a command reference.

## Acceptance checks (proposed; not executed)

1. Against the actual Redis OSS 7.2 primary, seed a hash and a string with positive `PTTL`. `HSET` the existing hash and assert its `PTTL` remains positive and decreases; ordinary successful `SET` without expiry/`KEEPTTL` must yield `PTTL=-1`; successful `SET ... KEEPTTL` must change the value and retain positive, decreasing `PTTL`. On a persistent control key, assert `EXPIRE key 60 GT` returns `0` and `TTL=-1`; on a volatile control key with an earlier deadline, assert a later `GT` deadline succeeds.

2. Explicitly enable key-event notifications for generic and expired events (for example `notify-keyspace-events Exg`) and subscribe before commands. Assert `EXPIRE key 0` removes the key and yields `del`, while a normally elapsed positive timeout yields `expired`. Separately run a production-representative session-cleanup measurement with replica failover; record the agreed expiry-to-cleanup interval and enough samples for p99. Pass the performance criterion only if the measured p99 is below 25 ms under the agreed conditions.
