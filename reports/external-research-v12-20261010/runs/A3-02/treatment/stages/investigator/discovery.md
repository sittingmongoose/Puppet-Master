# Investigator discovery — short browser voice memo

Run: `A3-02-treatment`; stage: `investigator`; brief: `ER12-A3-02-FRESH`. This discovery was made from the exact brief alone before the plan-release helper ran. It is scoped to a small, local-only microphone memo component for a JavaScript HTTPS page on desktop Chrome and Safari. No browser execution occurred; all validation below is proposed, not observed.

## Governing API and negotiation

Use `getUserMedia({audio: true, video: false})` only after an explicit Start action. The page needs a secure context; denial or policy/device/constraint failures must become readable error states, never silent capture or automatic retry. `MediaRecorder` is the simplest first path: attach listeners before `start`, choose a MIME type only after feature probing, catch constructor/start exceptions, and handle later `error`, `stop`, and `dataavailable` events. `isTypeSupported()` is a format-capability hint, not proof that the chosen encoder can start or finish with current resources; construction, actual start/capture, nonempty output, playback, and download are distinct gates [S01, S02]. Read the recorder's actual `mimeType` after start and use only a matching, verified extension/label. If a browser-selected default is used, record what it actually chose; do not infer a format from the browser brand.

Safari's released history makes a fixed old allow/deny list unsafe. WebKit for Safari 18.4 added WebM recording with Opus and reported ALAC/PCM audio recording; it added Ogg Opus/Vorbis on macOS Sequoia 15.4 and the listed 18.4 Apple OS releases. Safari 26.0 later announced ALAC and PCM in MediaRecorder and showed `audio/mp4; codecs=alac` as an example [S05, S06]. These release notes establish useful test candidates, not a complete MIME matrix: they do not give a precise PCM MIME string, and an earlier release note does not replace a probe on the selected Safari 26 build. Chromium source at immutable commit `19646947eb735f84c5ae91af1fe901273d67d4f7` recognizes `audio/webm` and `audio/mp4`; its source maps Opus and PCM codecs and gates AAC on `USE_PROPRIETARY_CODECS` [S08]. That is a 2025 source snapshot, not a Chrome 155 build mapping, so it generates probe candidates rather than a current release guarantee. On the research date the Chrome stable release note names desktop 155.0.8059.39/.40 (Windows/Mac) and .39 (Linux); Apple's Safari 26.0 release is build 20622.1.22 [S04, S06]. A validation report should record the actual full browser build, OS, and API results.

Candidate probe set: `audio/webm;codecs=opus`, `audio/mp4;codecs=mp4a.40.2`, `audio/mp4;codecs=alac`, and candidate PCM strings only after checking Apple's exact current documentation/runtime. Probe each exact string with `isTypeSupported`, try construction, call `start`/`stop`, and inspect actual MIME, nonempty final bytes, local playback, and download. If no exact candidate works, a no-options recorder can be considered only if its actual MIME can be honestly mapped; otherwise show `format unavailable`. Offer multiple file types only after each has passed that full path. Playback and recording support are separate.

## Lifecycle, permission, and interruption

State model to carry into the plan: `idle → requesting-permission → recording ↔ paused → finalizing → ready`, with a persistent `error` path from permission, format, device, encoder, or export failures. Start is a user action; after permission, require one live audio track and never ask for video, display capture, or system audio. Provide explicit Pause/Resume/Stop controls and reject invalid repeated operations. Track `mute`, `unmute`, and `ended`; a temporarily muted input can produce silence, while a removed device or revoked permission may end the track. Do not silently swap devices or reacquire. Show an input-interrupted message and preserve a partial memo if it finalizes into a nonempty usable file. User-driven switching should finalize/release the current track and require an explicit new Start. A track ended by this component's own `stop()` does not emit the `ended` event, so cleanup must also run on the component's own stop/reset/dispose path [S02].

Recommended privacy behavior for a hidden document: on `visibilitychange` to hidden, stop and finalize the current memo, stop the microphone tracks, and tell the user that backgrounding ended the memo; after return, allow explicit playback/download or a new Start. This is safer than leaving the microphone active in the background. The exact hidden-tab behavior and stop latency still need the proposed Chrome/Safari matrix. Enforce the five-minute target from elapsed time, not the number of `dataavailable` callbacks. `MediaRecorder.start(timeslice)` has a user-agent minimum interval and delivers queued events; the standard does not make callbacks a clock. A monotonic elapsed-time guard plus the hidden-page stop is the modest native path. If “up to five minutes” means a strict upper bound even when the page/runtime is frozen, the native timer alone cannot prove it; make that tolerance an owner decision or add sample-counted capture/post-record duration verification before making a hard-limit claim [S01, S03].

Cleanup sequence: enter `finalizing` once; request recorder stop if active or paused; stop all owned tracks promptly so permission/device use is released; keep the data listener through the final `dataavailable` and `stop` events; then assemble. Clear timers and listeners, disconnect/close any Web Audio resources, clear chunk references on reset, and revoke the playback object URL only when the playback/download view is retired. Preserve any partial chunks on a recording error long enough to assess whether a playable final blob can be salvaged; never label an empty blob as a saved memo.

## Native MediaRecorder versus AudioWorklet

**Native MediaRecorder (recommended baseline):** the browser owns encoding and container muxing. The page owns MIME selection, state/events, the bounded collection of returned encoded blobs, final assembly, playback, and local download. Pause/resume/stop and default encoding are built in. Small periodic chunks (for example a 1–2 second requested timeslice) limit per-event payload size, but the event timing is only a request. The final `dataavailable` precedes `stop`; wait for `stop` before creating the final Blob. Concatenate all nonempty blobs with the actual recorder MIME. Individual blobs may not be independently playable; the completed combination must be [S01].

**Web Audio / AudioWorklet capture and encode (alternative):** route only the microphone track through `MediaStreamAudioSourceNode` into an `AudioWorkletProcessor`; copy bounded PCM frames into a ring/transfer queue; encode off the real-time callback in a worker/library; then mux a real container and write a correct final header. AudioWorklet provides custom audio processing on the rendering thread, not an audio-file encoder or container. Processing must finish within real-time callback budgets; the current spec's default render quantum is 128 frames but is configurable, so process arrays by their actual lengths [S03]. WAV/PCM avoids lossy codec availability but yields large output: 48 kHz, mono, 16-bit PCM is about 28.8 MB for five minutes before headers/overhead (double for stereo). Float32 staging can use more. Bound queue depth and aggregate bytes; on overflow stop and report an error instead of unbounded buffering. A WebCodecs AudioEncoder path still needs support probing, worker/queue lifecycle and muxing; a WAV writer needs channel/sample-rate handling and final length metadata. Neither is a small free fallback.

A useful existing analog is `extendable-media-recorder`: its README describes a partial MediaRecorder-compatible wrapper, native recording where possible, custom audio encoders, and Web Audio PCM on other browsers; its details are a mutable repository README and no exact released commit/version was exposed in the retrieved view [S09]. Its history records a WAV/timeslice issue that closed in commit `2fe86e8`: the maintainer chose a sentinel maximum length in WAV headers for timesliced output and noted `requestData()` remained missing at that point [S10]. A separate issue report describes approximately 2× playback and 2× event spacing in that library's WAV path, but the reported library version is blank and the browser/OS fields are examples; it is not evidence of a native Chrome/Safari defect or of a verified fix [S11]. Treat these as library-specific lessons: chunks, headers, sample rate, and assembled output need direct checks.
