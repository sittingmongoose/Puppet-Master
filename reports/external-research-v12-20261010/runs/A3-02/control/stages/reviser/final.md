## Decision

Use native `MediaRecorder` for the first implementation in each tested current desktop Chrome/Safari build. Ask for only a microphone after an explicit Start click; do not upload audio. Prefer the browser's default format when the product does not require a specific output type, and read the actual output type before labeling a download. When a named format is required, negotiate at runtime and treat each layer as separate evidence: format preflight, construction/start, and completed capture/export. Fall back from a failed named MIME candidate to another preflight candidate and then to the browser default, but only before any nonempty data has been collected. If all native attempts fail, show an explicit unsupported/error state. Do not silently switch to a custom raw-audio path: Worklet capture alone is not a WAV encoder.

Do not reject Safari by browser name. WebKit documents MediaRecorder in Safari 14.1 and later format changes in 18.4/26.0 (S4–S6). Exact audio-only MIME combinations still depend on the actual browser/OS and must be checked in that runtime. Do not promise identical quality, MIME support, duration precision through system suspension, or playback in every external player.

## R1 — “Define permission, start/pause/resume/stop, track-ended, and cleanup behavior with an explicit error state.”

1. **Idle → requesting:** Start is a user gesture. Call `getUserMedia({audio:true, video:false})` or use the user's chosen `deviceId` only after a deliberate selection. Never request video/system audio. A pending permission request can remain unanswered; show “Waiting for microphone” plus Cancel. Because the pending promise is not cancellable, mark the request generation cancelled; if it later resolves, stop every returned track immediately. A denied/missing/unreadable device, blocked policy, or rejected constraint goes to `error` with a specific retry instruction and no recorder.
2. **Requesting → recording:** Confirm one live audio track and no video tracks. Attach `mute`, `unmute`, and `ended` listeners before constructing the recorder. A constructor or synchronous `start()` exception releases the stream and reports `error`. Install `error`, `start`, `pause`, `resume`, `dataavailable`, and `stop` handlers before `start(1000)`. Do not call the state `recording` until the recorder's start event/state confirms it.
3. **Pause/resume:** Pause calls `recorder.pause()` and sets the track `enabled=false`, so no microphone samples are written while paused. Record the monotonic active-time subtotal. Resume is a user gesture; first check `track.readyState === "live"`, restore `enabled=true`, call `resume()`, and continue the same memo. If the track is muted by the OS/browser, pause and show “Microphone temporarily unavailable”; `unmute` does not automatically resume. Keep a prominent component-level Recording/Paused state; do not rely on browser chrome alone to explain whether this component is gathering data.
4. **Background:** `visibilitychange` to hidden runs the pause/disable policy; returning to foreground never auto-starts capture. Require a user action to resume. This is a foreground-only policy to avoid hidden capture. A browser suspension can delay the visibility task; validate the supported browser/OS behavior and do not claim a hard wall-clock ceiling through sleep without evidence.
5. **Stop/finalize:** Stop calls `recorder.stop()` once, promptly stops the input tracks (app-controlled `track.stop()` does not fire `ended`), and waits for the final `dataavailable` and `stop` events in spec order. Append the last nonempty chunk before making the result. Use a short watchdog; if finalization does not arrive, clean up and show an incomplete-data error. A recorder `error` may be followed by partial `dataavailable` and `stop`; preserve a partial only if it has nonzero bytes and a known format, and label it partial.
6. **Track changes:** `ended` means permission was revoked/device removed/source ended. Stop/finalize, preserve any valid partial as such, release tracks, and enter an actionable error. `devicechange` refreshes device choices but does not imply a live track switched. Do not add/remove a track from a running recorder; the spec requires a recording error on track-set changes (S1–S2). Selecting another input finalizes and releases the current capture; the user explicitly starts a new capture. A single logical file across a live device switch is an owner decision requiring segment remux/re-encode or separate files.
7. **Cleanup:** On every success, cancel, error, ended track, discard, component unmount, or navigation cleanup path: stop all acquired tracks, detach listeners, clear timers, clear chunk references after Blob creation/discard, close any AudioContext and MessagePorts if a Worklet was used, and revoke the prior Blob URL when replacing/discarding. Do not retain microphone device IDs longer than needed. Error UI must say whether a partial file exists and offer retry/discard; never silently reset to idle.

## R2 — “Establish container/codec negotiation and fallback strategy, differentiating format support, successful construction, and successful capture/export.”

**Candidate set, not a support claim:** include only exact strings actually tested in a target release. Initial candidates to exercise are `audio/webm;codecs=opus`, `audio/mp4;codecs=mp4a.40.2`, `audio/mp4;codecs=alac`, and `audio/ogg;codecs=opus`, plus omitted `mimeType` for the UA default. The Safari candidates are release-bounded: WebKit documents WebM/Opus, fragmented MP4 and ALAC/PCM, plus Ogg formats on specified OS releases in Safari 18.4 (S5), and an explicit `audio/mp4; codecs=alac` example in Safari 26.0 (S6). A pinned Chromium muxer document lists WebM/Opus and MP4/Opus/AAC, but is not a Chrome release guarantee (S11). Do not show a format as available until this app verifies it.

**Runtime strategy:**

- If `MediaRecorder` is absent, report the operation unavailable in this build. Do not infer Safari or Chrome support from a UA string.
- When `MediaCapabilities.encodingInfo({type:"record", audio:{contentType, ...}})` is present and accepts the needed configuration, use it as an asynchronous preflight. The current 2026 W3C Working Draft recommends this richer query and marks the synchronous `isTypeSupported()` API deprecated; actual adoption in the selected browser must be feature-detected (S1). Where that query is missing, use `MediaRecorder.isTypeSupported(candidate)` if present. A false result skips a candidate; a true result is only permission to attempt it.
- Try each bounded named candidate once: construct inside `try/catch`, attach handlers, call `start()`, and distinguish thrown exceptions from later `error` events. If failure occurs before any nonempty chunk and the track is still live, finalize that recorder and try the next candidate. Limit retries to the finite configured list. If any nonempty data already exists, do not mix a different container/codec into that memo; finalize a partial and report the failure.
- If all named candidates fail, make one attempt without `mimeType` so the browser can choose its default. If that construction/start/capture also fails, release the stream and show an explicit unsupported/error state. No upload or unqualified format is offered. This preserves any supported native default without claiming every named codec works.
- After the `start` event, snapshot `recorder.mimeType`; reconcile with each nonempty `Blob.type`. Build one final Blob only after the terminal `stop` path. Reject zero-byte output. If the result has no trustworthy MIME type/extension mapping, show a format error instead of labeling it MP4, WebM, WAV, or Ogg by guess.
- `MediaRecorder` selects one output format for a capture. Offering two downloads of the same memo needs simultaneous recorders or local re-encoding/muxing, extra resource use, and separate validation. V1 should offer one honest output per capture; a second/lossless output is optional and needs owner approval of formats, size, and labels.

**Three success gates:** (1) the exact content-type preflight; (2) successful construction and start with no synchronous or asynchronous error; (3) nonempty completed bytes with the observed type, successful local audio preview, and a user-triggered download. A preview proves decoding in that same browser only. JavaScript can observe a download attempt, not prove that the user persisted the file. Record all three outcomes separately.

## R3 — “Compare native recording with an AudioWorklet-based mechanism, including encoding responsibility, buffering, and scope/cost implications.”

| Boundary | Native `MediaRecorder` | `AudioWorklet` path |
|---|---|---|
| Input | Permissioned microphone `MediaStream` | Same permissioned track connected through `MediaStreamAudioSourceNode` |
| Encoding/container | Browser encodes and muxes; app negotiates/selects MIME | Worklet supplies Float32 sample frames; app/library must encode and mux (e.g. PCM/WAV writer, WASM Opus encoder, or supported WebCodecs `AudioEncoder` plus muxer) |
| Data and time | Encoded Blob events; full completed event sequence forms a playable file | Sample buffers/messages; timeline should derive from sample frames and actual sample rate, not callback frequency |
| Memory/performance | Keep encoded chunks only, with a five-minute and byte ceiling; browser may still fail due resource limits | Copy into fixed ring/batched transfers; calculate bytes from actual channels/rate; handle overflow, render-thread deadlines, worker backpressure, `processorerror`, resampling and finalize/mux |
| Scope/cost | Lowest maintenance and best fit for a small existing page | Additional processor file, worker/WASM or encoder, muxer, bundler/CSP/static assets, format QA, CPU and memory risk; do not assume Worklet writes WAV |

The Web Audio 1.1 default render quantum is 128 frames but is configurable. Use actual buffer lengths/`renderQuantumSize`; never interpret call count as seconds (S3). Five minutes of 48 kHz mono Float32 samples is 57.6 MB before copies; 16-bit PCM output would be about 28.8 MB. Stereo or a higher rate multiplies this. A Worklet alternative must derive and enforce its cap from actual rate × channels × bytes/sample × duration and stop with an explicit buffer-limit error. `opus-media-recorder` v0.8.0 is an established but old analogy: its README uses WASM encoders and a Worker, has asset/bundler setup, and warns that separate WAV callback files cannot simply be concatenated (S12). It is not selected for this component.

Choose native capture unless target probes reveal a necessary feature absent from the supported native path. If a future owner chooses Worklet fallback, pin a maintained encoder/muxer and release, audit packaging, and run the same MIME/permission/resource/export matrix on that build before shipping. Until then, refuse clearly rather than silently ship an unbounded or untested recorder.

## R4 — “Explain data-chunk timing and assembly; do not treat callback frequency as a reliable clock or claim arbitrary chunks are independently playable.”

Call start(1000) only to request periodic encoded data and reduce how long one in-memory blob grows before delivery. The spec allows each interval to be at least 1,000 ms or the User Agent’s longer minimum, and a queued data event can arrive later than requested (S1). Append nonempty chunks in arrival order; do not derive elapsed time from chunk count or callback arrival intervals. Do not publish any callback Blob as a standalone download. On stop or error, wait for the terminal dataavailable event and then stop event; append the trailing nonempty chunk before making one Blob from all chunks in order. The MediaRecorder spec says individual Blobs need not be playable, while the complete concatenation must be playable. BlobEvent.timecode can aid media-timeline diagnostics but is not a wall clock or callback schedule.

**Five-minute contract and limitation:** The proposed first-version policy counts active recording time from monotonic timestamps on confirmed recording/pause/resume transitions, schedules a stop at 300,000 active milliseconds, and rechecks on each relevant event, timer, visibility return, and before resume. User pause, hidden-page pause, and a temporary muted-input pause do not accrue active time. At the threshold, stop once and finalize. This is a page-managed best-effort stop. It cannot establish a strict five-minute output maximum if JavaScript cannot run: the Chrome Page Lifecycle documentation says frozen pages suspend JavaScript timers and other freezable tasks (C2), while the MediaRecorder Working Draft describes gathering in parallel and event delivery through queued tasks (S1). Those sources do not establish whether capture continues during a particular freeze or sleep, and they do not give a Safari answer. The user has not supplied a maximum overrun tolerance or said whether “five minutes” means active captured time or wall-clock time. Those are release decisions, not conclusions to invent here. Until the owner decides them and target tests meet the chosen threshold, show the stop as a proposed active-time policy and do not claim a strict cap. If a strict cap is required, this JavaScript timer alone is not a sufficient design or validation result.

Proposed app-held encoded-blob budget is 64 MiB per memo. When the next chunk would exceed it, stop and mark the available bytes partial. Since a delayed callback may already contain an oversized browser Blob before application code sees it, this is an app-retention bound, not a guarantee about User Agent internal memory. Any custom raw PCM path needs a preallocated hard cap before capture begins.

## Optional improvements and owner decisions

Optional: microphone picker (only if input choice is needed), a verified lossless format, a second output format, OPFS-backed temporary storage, or a qualified WebCodecs/Worklet encoder. Each adds user-visible choices or implementation scope and needs its own matrix row.

Owner decisions before release: (a) retain the v1 foreground-only pause policy or deliberately authorize a visible background-recording mode; v1 pauses on hidden and never auto-resumes; (b) define whether five minutes means active captured time or wall-clock time, set a tolerated overrun, and require target evidence for that threshold; until then, the 300,000 ms active-time stop is only best effort and has no pass result; (c) accept finalize-and-restart for microphone switches versus one logical memo across devices; (d) one output format versus additional types and their size budget; (e) app-held byte limit and behavior when exceeded; (f) whether the user needs a durable local draft before clicking Download. Until decided, this plan assumes foreground-only capture, one memo/output, a proposed 64 MiB app-held cap, partial/error handling on limit, and no durable persistence or upload.

All original negative constraints are retained: no recording without user permission, no upload, no hidden/background surveillance, no system audio, no callback-count duration promise, no fabricated browser tests, no stale blanket Safari denial, and no unbounded raw PCM buffering.
