# ER12 A3-02 investigator discovery handoff

## Scope and evidence boundary

The source of discovery is the finalized synthetic brief `ER12-A3-02-FRESH` only: a small local microphone memo component for an existing HTTPS JavaScript page, current desktop Chrome and Safari, no backend/library/version pin. The plan is still concealed at this point. This handoff investigates R1–R6; it proposes a capture/export boundary rather than an app build. Sources are indexed by stable IDs in [`sources/index.md`](sources/index.md) and [`source-map.json`](source-map.json). No browser observation has been performed; historical sources below are not runtime test results.

## Mechanism and lifecycle findings

**Native MediaRecorder is the smallest baseline.** A user click starts the microphone-only request `getUserMedia({audio:true, video:false})`; there must be no request before that action and no network/audio upload path. HTTPS is assumed by the brief. A permission prompt may remain unanswered; the UI needs a cancellable “waiting” state even though JavaScript cannot cancel the underlying prompt. If a request resolves after the user cancelled the UI, stop its tracks immediately instead of starting a recorder. Handle permission denial, no input, stale/exact device selection, OS/device busy, unsupported constraints, and security policy as distinct actionable error details; never claim recording began until the stream, recorder start, and resulting data support it. Sources S1–S2.

State proposal: `idle → requesting → recording ↔ paused → finalizing → ready`, with a persistent `error` state available from every stage. Require one live audio track and no video track. Attach `mute`, `unmute`, and `ended` listeners before starting. A muted source temporarily supplies silence; to avoid silently recording an empty interval, pause and show “microphone unavailable,” and require an explicit user resume after `unmute`. A revoked permission or removed microphone ends the track: stop gathering, preserve any usable partial result as a clearly marked partial, release all tracks, and show an error with retry/discard. `track.stop()` is app cleanup and does not dispatch `ended`, so cleanup must be explicit. `MediaRecorder` may also stop automatically when all tracks end; collect its final data/error/stop sequence.

For a user's Pause action, call `recorder.pause()` and disable the track (`track.enabled=false`) so it contributes silence; update the timer from a monotonic timestamp. Resume only after a user action and after rechecking that the track remains live. On `visibilitychange` to hidden, apply the same pause+disable policy and do not auto-resume on foreground return. This avoids intentional hidden capture; test whether background/suspension on the selected supported browser delays event delivery. If the product instead requires a strict wall-clock cap through OS suspension, resolve that as an owner decision. On stop, call `recorder.stop()`, stop microphone tracks promptly, still collect trailing nonempty `dataavailable`, then wait for `stop` or a watchdog failure before building the final Blob. Clear timers/listeners and references; revoke the old playback object URL on replacement/discard/unmount. Errors from permission, constructor/start, recorder `error`, ended tracks, empty output, preview, and download must be visible, not swallowed.

Microphone selection should be explicit. `devicechange` reports a changed device set, not an automatic source switch. Refresh the picker on that event and on return to the page; do not silently choose or reacquire another mic. Do not add/remove tracks in an active recorder stream: S1 requires recording to terminate with `InvalidModificationError` when its track set changes. Baseline: a selection change finalizes the current memo, releases that stream, then asks the user to start a new capture with the selected source. Keeping one logical memo across a live source switch requires an owner choice about remux/re-encode versus separate files. Treat stop-immediately-after-track-change as a targeted regression test if a target release’s own notes identify that fix; do not generalize release-specific history.

## Format and export boundary

Do not infer the final format from the browser brand. Let the UA choose by omitting `mimeType` for the simple baseline, or, if the product must select/offer formats, test a short exact candidate list. The March 2026 MediaStream Recording Working Draft marks `isTypeSupported()` deprecated in favor of `MediaCapabilities.encodingInfo({type:"record", ...})` for richer support checks; implementation adoption is unverified, so feature-detect the async query and retain `MediaRecorder.isTypeSupported()` as a compatibility preflight where present. Treat either result only as a preflight, not proof.

Keep three steps distinct:

1. **Format candidate:** record the exact container+codec string and the preflight result, if supported. Candidates worth checking against matching builds include `audio/webm;codecs=opus`, `audio/mp4;codecs=mp4a.40.2`, Safari's vendor-documented `audio/mp4;codecs=alac`, and `audio/ogg;codecs=opus`; also try no MIME hint. S5–S6 give Safari version/OS release history; S11 is a pinned Chromium implementation document, not a Chrome release promise. The exact audio-only strings remain unverified for the assigned unpinned current desktop runtimes.
2. **Construction/start:** construct in `try/catch`, save the actual `recorder.mimeType`, install event handlers before start, then distinguish a sync `start()` exception from async error/stop. `isTypeSupported=true`, a nonthrowing constructor, or the recorder object's initial type alone is not capture success. A user-agent may still fail because the exact type/track/resource combination cannot start.
3. **Capture/preview/export:** collect nonzero `dataavailable` blobs through the final event, build one Blob with the observed MIME type, reject/label empty or error-truncated output, and preview locally with an `<audio>` element/object URL. Derive download label/extension from verified container/codec; do not call all output WAV, MP4/AAC, or WebM/Opus based on `isTypeSupported`. A preview proves this browser can decode that Blob, not that another player's decoder can. A user-triggered download is the export attempt; browser JavaScript cannot prove the user persisted the file. No upload, server encoder, or conversion belongs in this boundary.

On a permissioned short `timeslice` (e.g. 1 s), append only nonempty events, track a cumulative byte ceiling, and use all chunks only for the final Blob. The spec sets `timeslice` to a minimum or longer UA value; it is not a callback clock. Individual blobs are not necessarily standalone files, while all blobs from a completed recording must form a playable result (S1). Do not offer each callback as a download or create false duration from callback count. Use `performance.now()` active-time accounting for UI/5-minute cutoff, update on each state transition/timer/lifecycle event, and use event timecode/sample frames only as media-timeline evidence. Browser throttling can delay a timeout; background auto-pause and resume-time recheck reduce, but do not eliminate, uncertainty under OS suspension.

Bound app-held bytes (proposed configurable 64 MiB per memo); stop and show a partial/error if accumulated blobs exceed the cap. Timeslice reduces latency but does not guarantee callback cadence or cap UA-internal pending data. Do not add unconstrained PCM arrays. A 5-minute 48 kHz mono Float32 worklet buffer alone is 57.6 MB (about 54.9 MiB), before copy/encoder overhead; calculate a real cap from actual sample rate, channels, and bytes per sample, and fail before overflowing it.

## Alternative mechanisms and history

**Web Audio/AudioWorklet is a processing path, not a recording file format.** Connect the permissioned microphone track to a `MediaStreamAudioSourceNode` and `AudioWorkletNode`; process the input Float32 sample frames on the rendering thread, copy into a bounded ring/batched transfer, and feed a Worker/WASM encoder or a locally supported WebCodecs `AudioEncoder`. The Worklet does not provide a standard muxer/container/download. To produce a complete file, implementation owns channel conversion, sample-rate handling, timestamp/sample counts, encoder, container muxer/finalization, worker/worklet messaging, memory limits, CPU/deadline behavior, and output playback tests. The 1.1 spec defaults to 128 frames but permits a chosen render quantum; use buffer lengths/`renderQuantumSize`, not a hard-coded callback-count clock (S3). This approach is justified only if actual requirements demand custom DSP, a selected predictable encoding, or PCM/WAV. A mono 48 kHz 16-bit PCM WAV is about 28.8 MB for five minutes; 32-bit Float is 57.6 MB, with duplicates increasing peak memory.

An established third-party analog is `opus-media-recorder` npm 0.8.0 (S12): its README describes WebAssembly libopus/libogg/libwebm plus a dedicated Web Worker and binary paths, with Ogg/WebM/WAV formats. It demonstrates that an alternate encoder brings bundle/worker/CSP/bundler and error/format responsibilities; it is not a no-cost native polyfill. Its browser support table and last release are old and are not evidence of current Chrome/Safari support. Its WAV `dataavailable` events are complete independent WAVs, so concatenating them is specifically wrong; that is a library-specific exception to native MediaRecorder's S1 chunk rule.

Safari history makes the compatibility question concrete, not settled: Safari 14.1 added MediaRecorder with platform default encodings (S4); Safari 18.4 added WebM/Opus, fragmented MP4, lossless ALAC/PCM, and Ogg support with OS-specific scope (S5); Safari 26.0 documents ALAC/PCM and an `audio/mp4; codecs=alac` example (S6). Safari 17.4 fixed a pause/timeslice `ondataavailable` behavior (S7). WebKit issue 258567 reports empty `audio/mp4` blobs on a specific Safari 16.4/16.5.1 macOS/system-output-96-kHz setup, which the reporter fixed by switching to 48 kHz/reloading while a maintainer could not reproduce (S8). WebKit issue 243837 documents a specific iOS 15 `start/pause/requestData/stop` finalization bug and its exact 2022 commit fix (S9). These are version/setup-bounded history and motivate regression coverage; none authorizes a blanket current capability denial.

## Open implementation questions

1. What exact Chrome stable/build, macOS version, Safari build, and OS release are release targets? The phrase “current desktop” is not a reproducible support matrix.
2. Is a five-minute bound based on active captured duration or wall-clock time even through suspend? The proposed policy pauses when hidden and counts only active time; test system sleep and browser background behavior.
3. Is one browser-selected compact format sufficient, or should the UI offer a verified second/lossless type? Choose data-size budget and labels only after target-runtime probes.
4. When selected input changes mid-memo, is a partial saved memo plus a new explicit recording acceptable, or is a single logical output across device switches required? The latter adds remux/re-encode or separate-file UX.
5. What local-storage/persistence expectation applies? The brief calls for a local download and gives no durable draft store; baseline keeps one bounded in-memory Blob until download/discard.

No source-only conclusion can resolve these. The separate validation matrix should execute permission/capture/format/playback/download in target versions, and report proposed versus actually run checks distinctly.
