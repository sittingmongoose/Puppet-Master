# Research proposal: recurring rehearsal calendar distribution

Run: A4-02-control · Stage: reviser  
Status: complete research proposal based on public sources; no calendar has been built, published, imported or subscribed to. The complete source identity, exact URLs, versions/commits, locators, access UTC and applicability notes are in [`source-map.json`](source-map.json), indexed by stable IDs in [`sources/index.md`](sources/index.md).

**Evidence boundary:** “Observed” behavior below comes from the cited public standards, vendor documentation, release history and tagged source code. No orchestra feed or commercial calendar operation was tested. **Inference:** a single read-only feed is the lower-complexity pilot route than operating a calendar synchronization server; stable identifiers should make amendments easier for clients to reconcile, but this remains client-dependent. **Local recommendation:** the secretary owns one source schedule, publication waits for the manager’s room-disclosure decision, member reminders remain local, and the snapshot stays optional. These choices are proposals, not observed behavior.

## Recommendation

For a one-season pilot, maintain one authoritative rehearsal schedule under the secretary’s control and publish it as a bounded, read-only HTTPS iCalendar (`.ics`) feed. Members subscribe to its URL in the calendar client they already choose. This supports a maintained series and later amendments with less operational complexity than deploying a calendar server. Treat updates as eventually visible: delivery timing belongs to the recipient service/client, and no immediate-refresh guarantee is supported by the evidence.

Keep a separate downloadable one-season `.ics` snapshot as an optional member path. It is a one-time copy for people who cannot or do not want to subscribe, not a required feature and not a technical capability established by this research. Clearly label its season and that future edits will not reach an imported copy. Test it before offering it. The source calendar/feed and the snapshot must derive from the same approved schedule.

Use a public route only after the orchestra manager decides what room detail may be public. Google’s documented iCal URL route requires a public calendar; its support page says the public iCal address works only when the calendar is public. Do not put room detail into a public feed or snapshot until the manager approves that disclosure. If that decision is not made, publish a redacted event location or withhold that public route while the owner decides. [S02, S03]

This is a pilot-sized recommendation, not a selection of a specific hosting provider. Hosting ownership, the public/private disclosure decision, clients to support and refresh expectations remain owner inputs.

## Calendar model and update rules

### Recurring series and identity

Represent the ordinary weekly rehearsal as one finite `VEVENT` series with a persistent, globally unique `UID`, local event start/end in the venue’s time zone, a weekly `RRULE`, and a season end. The secretary creates and owns the event identity and amendments. Keep the UID through rescheduling, room changes and exports; do not recreate IDs whenever the file is regenerated. RFC 5545 defines `UID` as the persistent globally unique component identifier and `SEQUENCE` as an optional revision number starting at 0 and monotonically incrementing on significant component revisions. [S01]

Choose the venue’s actual IANA time-zone identifier only after the secretary confirms venue location and policy. Use `DTSTART;TZID=<venue-zone>:<local date-time>` and matching `DTEND` with the corresponding `VTIMEZONE`. For a local-clock rehearsal, a weekly rule in the venue zone means “the same local rehearsal time each week,” including across daylight-saving changes. A local time with no `TZID` is floating under RFC 5545 and can represent different actual instants for members in different zones. A fixed UTC rule is appropriate only if the owner means an absolute instant instead of a venue wall-clock time. A `VTIMEZONE` must cover every recurrence instance in the season. [S01]

Members who travel should see a venue-fixed event translated into the display zone currently selected by their calendar client. This is an inference from the time-zoned event model; the reviewed product pages do not promise identical traveler-display behavior. Validate a sample in each target client and state the venue zone in member-facing guidance. [S01]

### Moved or cancelled instances

For one moved instance, preserve the series UID and set an exception component’s `RECURRENCE-ID` to the original scheduled start. Set that exception’s `DTSTART`, `DTEND` and, when approved for disclosure, `LOCATION` to the moved rehearsal’s actual values. RFC 5545 specifies that when an instance moves from Friday to Thursday, the `RECURRENCE-ID` still names the original Friday. Do not encode a one-instance move as a “this and future” adjustment. [S01, §3.8.4.4]

For one cancelled occurrence, add its original scheduled start as an `EXDATE` on the master series, using the same value type and zone. RFC 5545 uses `EXDATE` to exclude a value from the recurrence set. A changed feed should remove that occurrence, but whether each service reconciles cached instances promptly is unverified; test it in the clients chosen for the pilot. [S01, §3.8.5.1]

On a season correction, keep the UID, original recurrence anchor and unaffected events stable; revise only affected series/instance fields and revision metadata; republish the full approved season. If the feed instead receives fresh unrelated IDs, clients may treat the revised events as additions rather than updates. That duplicate risk is an inference and must be checked. [S01]

Do not encode a reminder policy into shared calendar events. Members own their local reminders. The proposal omits `VALARM`; the reviewed vendor documents do not say whether local reminder customizations survive a later subscription refresh. That remains an explicit validation item.

### Import, subscription and server synchronization are not interchangeable

- **File import:** a downloaded `.ics` is copied into a calendar at import time. Microsoft says uploading the file creates a snapshot and does not refresh it when its owner changes it. Google documents `.ics` file import on a computer. Google’s warning that recurring events from **CSV** can become separate one-time entries applies to CSV import, not proof that `.ics` subscriptions fail. [S04, S05]
- **Feed subscription:** the member’s client or calendar service retains a URL and refreshes it periodically. Google’s documented “From URL” route is public-only and has no documented refresh interval in the pages reviewed. Outlook.com’s route says approximately every three hours but sometimes over 24 hours; Nextcloud’s documented default for its external iCal subscriptions is weekly. [S02, S03, S05, S09]
- **Server synchronization:** CalDAV uses a calendar-aware server and client. Where a server implements and advertises RFC 6578’s `DAV:sync-collection` report on a collection, a client can send its prior opaque token and receive changes since that state with a new token. The report is not universal across WebDAV servers and does not promise push or instantaneous updates. Authentication, account provisioning and access-control choices depend on the selected deployment. [S07, S08]

## Optional one-season downloadable snapshot

Retain this option as owner-authorized optional scope. The brief permits it; it does not establish that a working snapshot exists or that every client will import its exceptions in the same way. Google’s help documents computer-based `.ics` import; Outlook.com expressly describes a file import as a snapshot that receives no future refresh. These sources support feasibility as a standard delivery idea, not universal technical compatibility. [S04, S05]

If the owner chooses to offer it:

1. Generate a finite one-season `.ics` artifact from the same approved schedule used for the feed.
2. State its coverage dates and clearly explain “one-time import; later changes do not update this copy.”
3. Include the weekly series, moved exception and cancelled instance in a form verified against the target clients.
4. Do not attach a policy reminder or overwrite member calendars. Let the member choose where and whether to import.
5. Present snapshot and subscription as alternatives. Test importing both into a disposable test calendar for duplicates before telling members they can safely use both.
6. Apply the manager’s room-publicity decision to this file too; downloadable does not mean private.

Do not exclude the option merely because the baseline route is a feed. Exclude or defer it only if the owner declines it or the proposed compatibility check fails and no safe, accurately described representation is available. Any exclusion should name that evidence and leave the owner-authorized option visible for a later decision.

## Released history and season maintenance

A bounded history example is the Python `dateutil` recurrence parser. Issue #614 was opened on 2018-01-18 about `TZID` not being supported on `DTSTART`; PR #624 was merged on 2018-03-11; the released dateutil 2.7.0 tag (`51bda94`, 2018-03-11) records `TZID` support for `DTSTART` in `rrulestr`. The tagged source uses the TZID to look up a time zone and attach it to a local parsed start, rejecting a second conflicting time zone. This concerns that library/version only; it is not evidence of a commercial client issue or fix. The issue’s own sample combines a `TZID` parameter with a Z-suffixed UTC time, which RFC 5545 forbids. Use a local time with TZID and no `Z` in a standards-conforming fixture. [S10, S11, S12, S13, S01]

Time-zone data itself can change. The IANA release index listed tzdb 2026e (released 2026-09-29) as latest and summarized Manitoba’s move to permanent UTC−05 beginning 2026-10-31. This matters only if the orchestra venue or a relevant member display zone uses the affected rule; the brief does not give the venue or travel zones. The index does not prove that any Google, Microsoft or Apple service has already adopted that data. [S14, S15]

For season maintenance, record the chosen venue zone and the time-zone-data version used to create the feed/snapshot; review release notes before publishing a season that crosses a legal rule change; recalculate and compare affected local times; revalidate DST boundaries and the moved/cancelled exceptions in target clients. When calendars can lag, send a separate human-readable notice for urgent same-week changes. That is a reasonable response to documented variable refresh, not a tested notification service. [S01, S05, S14, S15]
