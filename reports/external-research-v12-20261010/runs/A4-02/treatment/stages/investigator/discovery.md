## Scope and evidence status

The brief describes a one-season read-only calendar, maintained by a secretary, for members using common desktop and mobile clients, including people traveling across time zones. The discovery here remains at pilot scale. It does not assume a product, a client, a calendar account, the orchestra's venue time zone, a room-visibility decision, or an existing hosting platform. Public documentation and primary standards/source history were retrieved. No account was created, no product client was operated, no member calendar or production service was accessed, and no local discriminating product check was run. Therefore, no source retrieval is reported as product validation; all validation work remains proposed/NOT_RUN.

Claim labels below distinguish **observed documentation/history** from **inference** and **proposed local choice**. Important operation boundaries are kept explicit in the compact source comparison in `source-map.json`: current help pages do not expose numeric service builds; Google Calendar API evidence is API v3, not consumer feed-import behavior; Nextcloud user-app and server-cache intervals refer to different operations.

## Initial proposal and evidence

### 1. Recurring series, moved/cancelled instances, identity, time zones

**Observed standard behavior.** RFC 5545 gives a recurrence set from `DTSTART`, `RRULE`, `RDATE`, and `EXDATE`; a `TZID`-referenced local date-time points to a `VTIMEZONE`, and the time zone definition used by a recurring component must cover all its instances. The recurring rule uses the same local time across time-zone changes. For a `TZID` `DTSTART`, `UNTIL` is a UTC date-time, an easily missed type/bound condition. A series is identified by `UID`; an instance is identified using `RECURRENCE-ID`, which is the original scheduled start even when that occurrence moves. `EXDATE` excludes a scheduled instance from the recurrence set. See [R01].

**Inference for this orchestra.** The schedule is a local event at a venue, so encode the rehearsal's venue-local wall time with a named time zone and a matching `VTIMEZONE`, not a floating time or a fixed UTC hour. This is the model that preserves, for example, a regular 19:00 local rehearsal through daylight-saving changes. A traveling member should see the same event rendered in their current local time zone; Google Calendar's help describes display in the viewer's local zone while traveling [R16]—this is documented for Google Calendar's service and still needs client-specific validation elsewhere.

**Proposed local choice.** Keep a stable `UID` for the series for the whole season. For a one-date room/time move, send an exception that retains that series `UID`, keys to the old/original `RECURRENCE-ID`, and carries the changed `DTSTART`/`DTEND` and (if public) `LOCATION`. For one canceled rehearsal, exclude that original recurrence date (e.g. through `EXDATE`) or use the source product's instance cancellation operation; select the serializer after testing target clients. Do not delete/recreate the whole series to move one rehearsal. The Google Calendar API v3 documents `originalStartTime` as immutable when an instance moves and shows cancellation by updating one instance to `status=cancelled` [R08]. The iTIP `CANCEL` method is an organizer-to-attendee message, distinct from updating a passive subscription feed [R02].

### 2. Candidate distribution products/routes and the difference between file, feed, and sync

**Google Calendar public source and URL subscription.** Current Google Help describes a public calendar as subscribable by other apps, with an iCal address available only when the calendar is public. Public calendars may be findable through search if the containing site is searchable; an owner can publish only free/busy detail, and some Workspace administrators can restrict public sharing [R05]. A member adds a public URL from a computer browser; the current Google Calendar mobile app cannot set up that subscription itself, although the calendar appears in the app after computer setup [R06]. This can be a low-setup source if the secretary already has a suitable supported calendar, but the public-visibility decision and account setup are constraints. Google does not give a subscription refresh interval on these setup pages.

**Nextcloud Calendar 35 public route.** The Nextcloud 35 user manual describes publishing a public link as read-only to external users; the public page offers both a subscription URL and an export of the whole calendar. This is a useful alternate hosted route that can avoid requiring members to have a Nextcloud account, but it requires someone to run and maintain an instance and a public link is a sharing capability [R11]. The Nextcloud 35 user manual says subscriptions refresh weekly by default, while the Nextcloud 35 admin manual says server-cached subscriptions respect a feed refresh interval or default to one day, configurable by the admin [R12]. These documents do not reconcile the default for Nextcloud's internal subscription/cache operation; preserve this as an unresolved documentation conflict rather than attributing the two defaults to different proven operations. Neither default governs Google, Outlook, Apple, or other external subscribers fetching a Nextcloud-published URL.

**Compatibility control: Outlook.com web.** Microsoft distinguishes “Subscribe from web” (a live online calendar connection) from “Upload from file” (a snapshot). The page says subscription updates may take more than 24 hours while also saying updates should happen approximately every 3 hours; that is no maximum or immediate-delivery promise. Imported `.ics` events do not refresh [R09]. Google similarly says an imported file is out of sync with its source and that CSV recurring rows may become separate one-off events [R07]. Apple documents external `.ics` subscriptions as read-only on iPhone; on Mac Calendar the user can select auto-refresh and ignore alerts while the provider controls events [R10]. These are different consumer operations and the guides do not identify exact app builds or a uniform refresh SLA.

**Server synchronization is a different route.** CalDAV and WebDAV sync use server resources, cache/state identifiers such as ETags, and (where supported) sync tokens that can report changed or removed objects [R03/R04]. This may be useful if members need a synchronized calendar account, but it introduces server/account/permission and client-compatibility questions and is more than publishing a read-only calendar URL. It must not be described as an imported file or a URL feed.

**Analogous publish/subscribe mechanism.** W3C WebSub has a publisher notify a hub; the hub delivers changes to subscribers' callback URLs after subscription verification and while a lease remains active [R13]. This is an interesting push model for a separate change-notice page, but the research found no evidence that common calendar clients use WebSub for `.ics` feeds. It is not a recommendation for this pilot's calendar channel.

### 3. Version/operation evidence and refresh bounds

The most specific recurrence/exception source is Google Calendar API **v3**: recurring events require an IANA `start.timeZone` for expansion; a moved instance retains `originalStartTime`; an instance can be retrieved and updated by its instance resource [R08]. This evidence governs that API operation, not what is imported into a member's private calendar by another product. RFC 5545 is the interop format standard, not a client conformance report [R01]. Google and Microsoft user guides document current web flows but do not give numeric software builds. Microsoft's Outlook.com page describes both static upload and URL subscription and its qualified, conflicting refresh timing language; the Google and Apple setup pages do not establish a universal numeric interval. Google's timezone help also warns that future/past events can miss DST changes and that an event created before a civil zone-rule change can show the wrong zone [R16]; treat a future DST boundary and a timezone-rule change as separate validation cases. Identify all compatibility uncertainty in the final draft and test exact clients/builds rather than carrying a provider's internal refresh default across services.

### 4. Relevant recurrence issue/fix chain and season-update consequence

Mozilla Bugzilla 1595332 reports that, in Thunderbird 68.2.1 / Lightning 68.2.0 on a remote calendar, editing one occurrence and adding a description caused the inherited location to be lost. The report and discussion locate this in recurring occurrence/proxy properties being serialized to remote calendars/ICS. The first fix attempt was backed out after recurring-event browser tests failed on the internal generation property; a later changeset was marked fixed for Thunderbird 91 and uplifted to 91.0b4 [R14]. The immutable final patch changes the proxy properties getter and adds recurring-event/recurring-exception tests that verify inherited parent properties, with `LOCATION` in the fixture [R15].

**Consequence/inference for a season update.** A room-only change to one instance is exactly the kind of small update that could be silently damaged if a client mishandles inherited series data. Include a discriminating test that changes one instance's room (and separately moves one instance in time), then confirms the updated exception, its identity and the unaffected weekly series survive save/refresh/reload. This is a historical Thunderbird regression example only; it does not imply the Google, Microsoft, Apple, or current Thunderbird products share the defect.

### 5. Supported optional scope: downloadable one-season snapshot

Retain this as a **supported option, not a mandatory feature or proven current capability**. Google supports importing an `.ics` file on a computer and makes clear that imports do not stay in sync; Microsoft Outlook.com also supports file upload and describes it as a static snapshot [R07/R09]. This supports exploring a `.ics` snapshot bounded to one season and produced from the same canonical schedule; it does not prove every mobile client can directly import it. Do not use CSV for this purpose because Google warns recurring events may flatten into one-offs [R07]. Label the season end and file generation/publication time. Tell a member who imports a replacement snapshot to replace their old season calendar rather than repeatedly overlaying copies. For Apple iPhone, the source examined supports subscribing to a URL but does not establish the direct one-season file-import path; leave that client check proposed [R10].

### 6. Ownership, rooms, reminders, and constraints

**Owner decisions preserved.** The secretary owns stable event identity and schedule amendments. The orchestra manager decides whether room details may be public. No route or public-link decision should encode rooms until that manager decision exists. Member reminders stay member-controlled; do not put mandatory `VALARM` or organization-wide reminder policy in the feed. RFC 5545 describes alarms in events; Apple Mac provides an “Ignore alerts” setting, the Google API's reminder object is for the authenticated user, and Nextcloud app reminder notes concern owners/write-sharees with third-party display depending on sync [R01/R08/R10/R11]. Client behavior is not uniform, so use a reminder-free calendar record and validate that local alerts remain untouched where the client supports local reminders.

**Negative constraints preserved.** Do not access member calendars, require members to migrate accounts, promise immediate refresh on every client, or label an imported `.ics` as a live subscription. A public link is not server synchronization. If room details cannot be public, the manager and secretary need to choose a permissioned sharing route whose sign-in requirements are acceptable without mandatory account migration.

## Initial recommendation, subject to exact-plan review

Use one secretary-maintained source calendar with a stable UID-based weekly series, named venue-local time zone and correct `VTIMEZONE`, and publish a read-only `.ics` URL if the orchestra manager permits the included details to be public. Prefer an existing service that the secretary can maintain; compare a Google public calendar route [R05/R06] with Nextcloud 35's public read-only link and download route [R11] before adopting any new host. Treat Outlook.com, Apple Calendar and Google Calendar client behavior as separate subscription operations; document observed refresh per exact release. Keep the one-season `.ics` snapshot as a conditional option produced from the same canonical schedule, with no recurring-policy `VALARM`; do not treat it as a live subscription. Retain the unresolved owner input for room visibility and require no account migration for members.
