# Independent discovery: volunteer oral-history deposit package

**Scope:** The complete assigned brief, read before plan release. This is discovery, not an implementation or product validation. It does not make any recorder/application choice mandatory. External behavior below is source-backed; workflow recommendations are local design inferences.

## Useful proposal shape

For a small society with varied recorders, begin with a portable sidecar-first deposit: copy each received recording unchanged into a deposit package; assign a stable accession/file identifier independent of its filename; record original filename, byte size, full-file SHA-256, receipt/context, rights/consent state, and descriptive metadata in a UTF-8 sidecar. Keep the raw original, a human-reviewed transcript (when approved), and any listening copy as separate files linked by stable IDs and checksums. A BagIt 1.0 directory is a promising transfer/fixity envelope: it carries arbitrary payload files and requires a manifest of checksums, while remaining semantically unaware of WAV contents [BAGIT]. This will accommodate recorders that can produce ordinary WAV without relying on their embedded-tag support. BagIt is an informational RFC; its manifests detect corruption, not active tampering, authority, or semantic completeness [BAGIT].

A second workflow can use a verified copy of the received WAV as a working derivative: staff import a one-row-per-file BWF MetaEdit CORE CSV/XML, populate only archivist-approved BEXT/INFO values, inspect the result and export the metadata record. MetaEdit supports embedded edits, structured validation and CORE CSV/XML exchange, and multi-platform CLI/GUI [METAEDIT; CORE]. Keep the original untouched and keep the approved sidecar/database authoritative. This offers metadata that travels inside BWF-aware applications and can aid discovery, but it adds tool/wrapper/field/encoding dependencies. Optional RIFF chunks can be unsupported by readers; older BWF applications can ignore fields added in later versions [EBU; FADGI]. BWF MetaEdit’s MD5 option addresses the WAVE data/audio chunk only, so it is not a substitute for a full-file package manifest [METAEDIT; BAGIT].

The meaningful alternative is ingest without embedding: allow whatever recorder supplied the WAV, preserve observed embedded fields as received, and manage all new descriptive metadata externally. It maximizes recorder compatibility and avoids metadata rewrite risk, at the cost of sidecars that can detach or become stale. If later in-file convenience is needed, add it only to a separate copy, record the event and identifiers, and validate the precise file/tool/version path. Neither workflow should require a single recording application.

## Identity, authority, versions and relationships

Use an accession/object ID and a distinct file-level ID; preserve the received filename as provenance, not identity. Record a full-file cryptographic checksum at receipt and after transfer. FADGI treats BEXT OriginatorReference as a useful unique file-level identifier and Description as a place for identifiers or pointers to externally maintained metadata, with a limit of 32 and 256 ASCII characters respectively; it cautions against revealing sensitive pathnames [FADGI; BEXT]. For an optional embedded copy, repeat only selected values approved by the collections archivist. The sidecar/catalogue remains authoritative for later descriptive corrections: MetaEdit/FADGI docs explicitly warn embedded descriptive metadata can become outdated and direct users to an identifier for newer information [LISTINFO]. This authority arrangement is a local choice, not a FADGI rule.

Record transcript history as distinct versions, not in-place correction: each UTF-8 plain-text revision has a stable ID, version/date, approval state, interviewer approval attribution, checksum, and `derived_from` link to the original recording ID/checksum; later correction points to the prior transcript revision. Preserve the original supplied transcript separately if one exists. PREMIS 3.0 recognizes structural and derivation relationships between Objects and recommends unambiguous related-object identifiers; its model supports this design without requiring that this small pilot implement PREMIS [PREMIS]. Keep received original, any BWF-tagged copy, transcript, and access audio distinct, with a recorded derivation event and the responsible tool/version and settings for each generated copy.

## Embedded fields and round-trip evidence

BWF is a RIFF/WAVE chunk format with a standardized `bext` extension; optional chunks are not supported by all applications and readers may ignore unknown chunks [EBU]. FADGI version 3 is current in the retrieved guideline index (approved 2021-04-26), covers BEXT, INFO and cue/adtl chunks, and labels particular fields strongly recommended, recommended, or optional rather than making every field mandatory [FADGI]. BEXT constraints are material: e.g. Description is ASCII and max 256 characters; OriginatorReference is ASCII and max 32; the date/time structure is limited and FADGI interprets origination times as local to the archival entity, not an unambiguous UTC datetime [FADGI; BEXT]. BWF MetaEdit's CORE CSV constraints echo ASCII field limits [CORE]. Thus do not force accents, full prose, rights/consent history or long descriptive metadata into constrained embedded fields. Keep UTF-8 text in external sidecars; decide whether transliteration or omission is appropriate only with archivist review.

A valuable optional capability: FADGI v3 defines `ltxt` Purpose value `tran` for transcription and treats `ltxt` as text associated with a range of cue points. The same recommendation specifies ASCII free text, a null terminator, and RIFF padding conditions; it is not a guaranteed plain-text transcript channel across WAV tools [FADGI]. For a portable human-reviewed transcript, a UTF-8 sidecar is safer. The embedded ltxt option could later carry short timed segments only where the target readers, code page, cue semantics and round-trip test pass. BWF MetaEdit says it does not validate XML entered in aXML/iXML/XMP chunks and has no undo for those edits; avoid them for this pilot unless a local schema and recovery path are approved [XML].

A bounded released-history example makes the encoding risk concrete. BWF MetaEdit GUI history lists Version 0.2.2 (2009-12-22) fixes for XML carriage-return encoding, escaping special characters and a platform-specific complete-file-write issue; Version 21.07 (2021-07-09) fixes for importing XML fields with `UNICODE=1`; Version 23.04 (2023-04-10) added read/write of CP437, CP850, CP858, Windows-1252, ISO-8859-1/2 fields and read/write of character encoding in the CSET chunk; Version 25.04 (2025-04-30) added ISO-8859-1 fallback when reading a core file [HISTORY]. This demonstrates that CSV/XML/chunk round-trip behavior has tool-version and encoding conditions. It does not establish that all historic or current tools read/write these encodings consistently. FADGI labels core BEXT string fields ASCII while BagIt recommends UTF-8 for tag files [FADGI; BAGIT]; do not treat one container’s text policy as the other’s. Proposed validation is to round-trip representative ASCII, accented/non-Latin, quote, CR/LF, and long values using the selected released tool version, compare extracted fields and full-file/audio hashes, and inspect unknown chunks. No such validation was executed here.

## Transcript/access option, owners and safeguards

Retain as an authorized, optional pilot path a human-reviewed plain-text transcript and accessible listening copy, subject to consent/access review and available staff time. The W3C media guidance recommends a transcript of speech and non-speech audio plus an accessible media player; W3C planning guidance lists a separate transcript for prerecorded audio-only media as WCAG Level A [W3C]. The proposal should provide an accessible page/player with keyboard-operable controls, no unexpected autoplay, volume/pause controls, a linked readable transcript, and human review of speaker labels, non-speech sounds and corrections. A separately encoded listening derivative should be generated from a verified copy, named and linked to the original, and tested for playback and accessibility; it must not replace the preservation original. For a text-only transcript, there is no need to embed it in WAV.

Explicit owners: the collections archivist decides the descriptive field model, source-of-truth policy, and which (if any) fields are copied into BWF; the interviewer approves transcript corrections and identifies uncertain speech; consent/restrictions review is an external owner input that software defaults cannot supply. Possession does not show consent. During research do not alter received originals, do not promise lossless metadata edits based only on `.wav`, do not require ASR, and do not infer consent from possession.

## Preliminary validation priorities (proposals only)

1. Define a receipt manifest and verify that a copied original matches its receipt SHA-256; verify BagIt payload and tag manifests after package transfer.
2. With approved synthetic/sample files only, confirm each recorder's actual container/codec and metadata chunks from file contents, including unknown chunks; treat extension as a hint, not proof.
3. On a duplicate, compare before/after full-file hashes, audio-data hashes, chunk inventory and metadata extraction for each selected released metadata tool and version; prove originals remain unchanged.
4. Test sidecar and BWF metadata round-trip with Unicode/legacy encodings, date uncertainty, long identifiers, commas, quotes, newlines, absent fields, and duplicate filenames.
5. Test transcript approval/version linking and access-player keyboard, screen-reader, pause/stop, volume and readable transcript behavior; obtain consent/restriction decisions outside software.

All five are proposed; no local audio/file manipulations, product tests, installations, accounts, live writes or accessibility conformance checks were run. Public source review is research evidence, not product validation.
