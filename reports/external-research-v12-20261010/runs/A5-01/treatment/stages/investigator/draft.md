# Research proposal — volunteer oral-history deposit package

**Run:** A5-01-treatment / investigator stage  
**Evidence basis:** Read-only review of public primary format documentation, preservation documentation, accessibility guidance and released tool history. Research claims are cited to the stable IDs in [`sources/index.md`](sources/index.md) and fully identified in [`source-map.json`](source-map.json). Local product validation has not been performed.  
**Released plan:** `revealed-plan.md`, released once at 2026-10-10T04:25:12.781Z after discovery was saved; release helper reported discovery SHA-256 `6e1f863f80f94caf851622885353b113f755cde02ae88eb67ba0510926c2aa80` and plan SHA-256 `b80e30c3938344528a49c1b43144af18f14b0d8ed27a2603b845042467e4e067`.

## Recommendation

Adopt a sidecar-first, immutable-original pilot. On receipt, preserve the exact volunteer-supplied WAV bytes and filename; assign stable collection and file IDs; record a full-file SHA-256, size, received name, received embedded metadata, descriptive metadata, restrictions/consent review status, and provenance in a UTF-8 sidecar/catalogue. Package the original, approved sidecars, photographs and any separately generated derivatives in a portable BagIt 1.0 directory. A payload manifest then checks every packaged file's bytes. Treat this as transfer/fixity evidence, not proof of consent, authenticity against an active attacker, semantic correctness, or long-term preservation by itself [BAGIT].

Offer a second route only when staff need in-file convenience: copy the received file, use a selected and tested BWF metadata tool on that copy, embed a small archivist-approved subset in supported BEXT/INFO fields, and retain the sidecar as the current descriptive authority. BWF MetaEdit is a realistic, cross-platform candidate for BWF files; it imports/exports a CORE CSV/XML exchange and embeds selected values [METAEDIT; CORE]. Its audio-only MD5 is not a full-file checksum [FADGI-INDEX]. This workflow needs a declared BWF/codec/tool/version profile and tests on representative files. Neither route requires volunteers to use a particular recorder application.

Retain the brief-authorized transcript/listening-copy option as an optional, supported-by-policy path, not a mandatory product feature or assumed technical capability. When consent and access review permit, create a human-reviewed UTF-8 plain-text transcript and separate listening derivative from a verified copy, obtain interviewer approval for each correction, publish with an accessible player and a direct readable transcript, and link both derivatives to the original by stable IDs and hashes. W3C WAI recommends a transcript covering speech and non-speech audio, an accessible player, and lists a separate transcript for prerecorded audio-only media at WCAG Level A [W3C; W3C-PLAN]. This is a recommendation for the pilot, not evidence that any current player or transcript passes accessibility tests.

## Workflow comparison and analogous preservation mechanism

| Workflow | Procedure | Portability and recorder compatibility | Main limitations and conditions |
|---|---|---|---|
| **A. Sidecar-first (recommended baseline)** | Leave received audio unchanged; assign IDs and capture a full-file hash; store descriptive record and links in UTF-8 CSV/JSON or catalogue; keep interviewer-approved transcript revisions and any access copy as separate files. Package these with the original in BagIt. | Works with varied recorders that can supply files; recorder need not write any descriptive metadata. Sidecars and package files are ordinary portable files. BagIt treats payload as opaque bytes and requires at least one checksum manifest listing every payload file. | Sidecar can be separated or become stale, so include stable IDs and checksums in each record/package and maintain an authoritative copy. BagIt does not interpret WAV metadata or establish owner authority/consent; manifests detect corruption but are not an active-attack security mechanism. RFC 8493 is informational, not Standards Track [BAGIT]. |
| **B. BWF-embedded subset on a working copy** | Preserve received original; duplicate it; on the duplicate use BWF MetaEdit or comparable tested software to add selected BEXT/INFO fields; import/export its CORE CSV/XML; verify output and link it as a metadata-bearing derivative. Keep sidecar authoritative. | Values may travel with a BWF-aware WAV reader and support manual discovery. Post-ingest editing avoids depending on recorder metadata-entry support. BWF MetaEdit offers GUI/CLI for multiple platforms [METAEDIT]. | Embedded chunks/fields are not uniformly supported. EBU says optional chunks are not supported by all apps and unknown chunks are ignored; older BWF readers may ignore later version fields [EBU]. ASCII limits, encoding, field limits, and possible file-write behavior need version-specific testing [FADGI; CORE; HISTORY]. The tool's MD5 covers audio data, not the entire file [FADGI-INDEX]. Never edit the received original during this research. |
| **BagIt (analogous packaging/fixity mechanism)** | Use a `data/` payload for original, sidecar, photo, transcript versions and access derivatives; use `manifest-sha256.txt` and optionally a tag manifest for package tags. Validate after transfer. | A directory-based hierarchical package for arbitrary data, independent of audio codec, recorder, database or internal WAV semantics [BAGIT]. | BagIt is a package layout and checksum mechanism, not metadata authority, audio fixity policy, access service, semantic validation, or consent workflow. UTF-8 is recommended for tag files. Add signatures or other controls if protection against active attacks is needed [BAGIT]. |

Workflow A is the starting recommendation because recorder compatibility and preservation of received bytes dominate for this pilot. Workflow B is a useful optional supplement when a selected recipient has a BWF-aware workflow; it should be enabled only after tests show the selected tool and its version preserve needed audio/chunks and handle the society's actual files. A simpler transfer package without formal BagIt is a possible local alternative, but then the society must still define its own manifest format and verification procedure. A full preservation repository or metadata standard such as PREMIS could add useful controls later; that scale is not required for this pilot.

## Findings and dispositions by exact obligation

### 1. “Compare two realistic metadata/deposit workflows and an analogous preservation mechanism with portability and recorder compatibility tradeoffs.”

**Disposition — correct the draft's proposed one-field workflow; recommend Workflow A as baseline and retain Workflow B as an optional, conditioned alternative.** The released draft says to put all metadata into one WAV comment field, link photographs by filename, and assumes metadata survives every editor. Those assumptions are unsupported. It collapses descriptive, technical, identity, restriction and provenance information into one value; does not give stable links; and cannot accommodate unbounded metadata in a fixed BEXT field. BEXT Description is ASCII and at most 256 characters and OriginatorReference at most 32, according to FADGI/EBU. EBU says some optional chunks are unsupported and unknown chunks ignored [FADGI; EBU].

**Research-backed alternatives:** Workflow A uses an immutable supplied original, stable IDs and external metadata/derivative records in a BagIt package. Workflow B uses BWF MetaEdit on a copy for selected BEXT/INFO fields, with a sidecar remaining authoritative. BagIt is the analogous preservation/transfer mechanism: its payload manifest lists each payload file once with a checksum [BAGIT]. It does not make the embedded or descriptive metadata complete or authoritative. The tradeoff is straightforward: sidecar-first accepts sidecar management in exchange for recorder/tool portability; embedded BWF increases in-file convenience where target applications support it, at the cost of field/encoding/reader/write-path compatibility tests.

**Useful discovery:** The 2021 FADGI BWF guideline adds guidance for cue, adtl, labl, note and ltxt use and BWF MetaEdit support; `ltxt` offers a purpose value `tran` for transcription, but has its own cue/time range and ASCII constraints [FADGI; FADGI-INDEX]. This is useful for optional short timed annotations, not a reason to require whole transcripts embedded in every WAV.

### 2. “Explain recording identity, embedded/sidecar metadata authority, transcript revisions and links between originals and access copies.”

**Disposition — retain BWF MetaEdit as an investigation lead, but add a concrete identity, authority, revision and lineage model.** The draft's mention of BWF MetaEdit and a sidecar-only option is already covered at a high level, but it does not settle portability or authority. `CORE` exchange is tied to filepaths and supports one record per audio file; the path alone is not an enduring identity across renaming, package moves or duplicates [CORE].

**Recommended proposal (local design choice):** Assign an accession/session ID for the interview and a distinct file ID for each received recording and photo. Preserve original filenames as receipt metadata; don't make filename uniqueness the ID. Record the full-file hash/size and package-relative path. Record field-level provenance/source and last verified time where feasible. FADGI specifically recommends OriginatorReference as an unambiguous file-level ID and Description as a limited pointer/identifier field, but those are optional embedded aids, not the master identity system [FADGI; BEXT].

The collections archivist decides which descriptive source is authoritative. Recommend the external catalogue/sidecar as the current authority and copy only selected, approved descriptive values into BWF. MediaArea's LIST-INFO help warns embedded descriptive metadata can become stale and says readers should follow identifiers to newer/better data [LISTINFO]. This is evidence for maintaining a route back to the authoritative record, not a mandate to choose one particular database.

Keep transcript versions as separate files: `transcript-v001.txt`, `transcript-v002.txt`, and so on, with UTF-8 encoding; stable transcript ID; revision date/status; interviewer approver; checksum; and links to the original recording ID/hash and prior revision. Each approved correction creates a new version; it never overwrites the preserved supplied text or previous approved version. PREMIS 3.0 describes derivation and structural object relationships, related-object identifiers and optional event links as a model for this lineage [PREMIS]. A pilot may record these relationships in a simpler table instead of implementing the full PREMIS standard.

The access copy has a distinct file ID/hash and a recorded derivation event: source original ID/hash, tool and released version, settings, creation date/operator, and target format. The transcript and access copy are sibling derivatives linked to the same source; do not imply one was generated from the other. This explicit relationship makes it possible to distinguish original, metadata-bearing copy, transcript versions and listening derivative.

### 3. “Research the conditions for optional embedded descriptive metadata without assuming every WAV tool supports the same fields or rewrite behavior.”

**Disposition — reject the draft's blanket survival assumption; keep embedding optional and condition-specific.** BWF is a RIFF/WAVE format extension. EBU Tech 3285 v2 documents fixed-size ASCII BEXT values and says applications should ignore unknown chunks; it notes optional chunks may not be supported by all applications [EBU]. FADGI v3 distinguishes strongly recommended, recommended and optional elements. Its BEXT examples include a maximum 32-character OriginatorReference and 256-character Description, and its date/time guidance has local-time semantics and limited precision [FADGI]. MediaArea's CORE CSV also specifies ASCII constraints [CORE]. Therefore, a generic `.wav` suffix does not establish a BWF variant, supported field set, character encoding, or safe rewrite behavior.

If embedded metadata is desired, first identify the actual file structure/content and supported encoding from the file and target tools. Have the archivist select a small subset and semantics; do not overload constrained fields with long descriptions, sensitive pathnames, transcript text, rights histories or consent status. Use sidecar UTF-8 for full descriptions, names, correction history and other flexible text. FADGI's `ltxt` transcript purpose is optional and ASCII; MetaEdit's current help explicitly says its aXML/iXML/XMP editor does not verify XML validity and has no undo [FADGI; XML]. These are different behaviors and conditions, not universal WAV capabilities.

Keep an immutable receipt copy. Test edits only on a duplicate. Compare full-file checksums, audio data checksums, chunk inventories and metadata extraction on both sides of the operation. BWF MetaEdit once had an optimization not to rewrite the complete file when unnecessary, and its release history also records a historical complete-file-write problem; that is evidence of conditional writer behavior, not a present-day guarantee [HISTORY]. Do not promise “lossless” writes from extension or tool intent alone.

### 4. “Investigate a relevant metadata round-trip/encoding issue or released change and explain how it affects this collection.”

**Disposition — replace the plan's current-listing assumption with the following versioned release-history evidence and a specific test implication.** The MediaArea GUI history is a mutable repository branch, so the identified releases are named versions/dates but the retrieved page did not expose a fixed commit. It records: Version 0.2.2 (2009-12-22) fixes for XML carriage-return encoding, escaping special characters and a Mac/Linux complete-file-write issue; Version 21.07 (2021-07-09) fixes for importing XML fields with `UNICODE=1`; Version 23.04 (2023-04-10) read/write support for CP437, CP850, CP858, Windows-1252, ISO-8859-1 and ISO-8859-2 fields plus CSET encoding; and Version 25.04 (2025-04-30) an ISO-8859-1 fallback when reading a CORE file [HISTORY]. Version 26.08 history and the project page listed 26.08.1 at access, but no binary was installed or run [HISTORY; METAEDIT]. These are release-history statements, not observed current product behavior.

**Effect here:** An exported/imported CSV or XML row containing an accented volunteer name, quotes, CR/LF, or non-ASCII text can behave differently by tool version and code path. The same text cannot simply be copied into BEXT fields defined as ASCII; BagIt tag-file UTF-8 policy applies to the package's tag files, not to the internal BEXT field [FADGI; EBU; BAGIT]. Preserve rich text in a UTF-8 sidecar. Before any embedded route, test actual representative values in the selected released version; check extracted round-trip text, CSET/code page, newlines, truncation, audio-data digest, full-file hash and unknown chunks. No such test has been run.

### 5. “Preserve and investigate this supported optional scope: a human-reviewed plain-text transcript and accessible listening copy alongside the preserved original. It is an authorized option, not a mandatory feature or an established technical capability; recommend conditions, retain it when supported, and explain any evidence-based exclusion.”

**Disposition — retain the option, make it conditional on consent/access, reviewer capacity and tested delivery.** Here “supported option” means the brief authorizes the society to consider it; it is not evidence of implementation or interoperability. The released draft correctly says not to remove it merely because the baseline route omits it. Its error is to omit transcript lineage and the link to the access copy.

Recommend a separate UTF-8 text transcript with speaker labels where known, non-speech cues and uncertain/heard-as notes as appropriate; every revision should show status and interviewer approval. A human-reviewed transcript does not imply ASR; ASR is not required. Do not embed it into audio unless the archivist chooses that path and target readers pass the `ltxt`/cue/code-page checks. FADGI has `Purpose=tran`, but the ltxt text is ASCII and contextually tied to cue ranges [FADGI]. W3C WAI recommends the transcript include speech and non-speech information, and its audio-only checklist identifies a transcript separate from audio; the guide also calls for an accessible media player [W3C; W3C-PLAN].

Define “accessible listening copy” locally as a separately linked playback derivative presented through an accessible player with keyboard-accessible controls, pause/stop and volume control, plus the readable transcript. A listening derivative could use a convenient format if selected recipient devices support it, but format, channels, loudness processing and preservation settings remain to be decided and tested. Link output hash, source hash, transform tool/version/settings and file IDs. Do not alter or replace the preservation original. If consent or restriction decisions disallow access, keep the original preserved under the society's approved controls but do not publish transcript or access audio; record the owner decision. If staffing or platform testing is unavailable, defer creation while retaining the option and clearly marking it NOT_RUN/NOT_CREATED, rather than asserting a technical exclusion.

### 6. “Make owner decisions explicit: The collections archivist decides descriptive-field authority; the interviewer approves transcript corrections. Consent review is an external owner input and cannot be replaced by a software default.”

**Disposition — preserve these authorities exactly; no owner decision was obtained by research.** The released draft repeats the owner roles correctly, but these are unresolved inputs, not completed approvals. The collections archivist decides the descriptive field model and the authority between catalogue/sidecar and any embedded convenience fields. The interviewer approves transcript corrections and may identify uncertainty. A separately designated consent/restriction reviewer supplies the consent/access decision; no default, possession, model output or software feature may substitute. Any public access, redaction, reuse or redistribution requires that external decision.

### 7. “Preserve negative constraints: Do not alter received originals during this research, promise lossless edits from a filename extension alone, require automatic speech recognition, or infer consent from possession of a recording.”

**Disposition — binding and complied with.** No received audio or photo was available or altered in this investigation; no code was downloaded or run, no application was installed, and no account, purchase, production access or live write was used. No losslessness claim is made; the `.wav` extension alone is insufficient to establish actual chunk/layout or write behavior [EBU; HISTORY]. No ASR dependency is proposed. Possession is not evidence of consent; external review remains open. If implementation follows, first create/verify a read-only receipt copy and test only duplicates.

Do not report research sources or future tests as executed product validation.”

**Disposition — this document supplies the proposal, and the table below separates evidence-gathering and required stage procedure from product checks.** Sources are directly linked in the source index and include applicable versions/dates and caveats in `source-map.json`. The plan's unsupported claims were corrected; the authorized transcript/access option remains; the archivist, interviewer, and consent-owner inputs remain unresolved.

## Owner inputs still required

1. **Collections archivist:** choose descriptive fields, vocabulary/identifier scheme, sidecar/catalogue authority, whether any BWF subset should be copied, which formats/chunks are within pilot acceptance, and policy for versioned descriptions.
2. **Interviewer:** define how transcript corrections/uncertainty are represented, approve every correction and revision, and confirm speaker labels/context.
3. **Consent/restriction reviewer:** decide allowed preservation, staff access, public access, redaction and reuse separately for audio, transcript, photographs and derivatives. This input cannot be synthesized from possession or software state.
4. **Society/pilot owner:** decide whether to produce an access copy for a given deposit, choose accessible delivery/codec and storage location, and accept resourcing and upkeep for the sidecar and fixity checks.
