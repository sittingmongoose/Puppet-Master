### Recommendation

Use a raw-first, append-only observation and correction ledger as the club's canonical history, then derive the public historical chart from accepted observations. Preserve each radio envelope and each uploaded CSV artifact independently of normalized rows. Keep station/sample identity, observation-time interpretation, every known receipt time, archive append time, and parser/template version traceable to the raw source. Record corrections as new, reviewed events linked to the prior row; never erase raw readings merely because they are late or later corrected.

For a low-power radio route, inventory the actual devices and server first. If the existing route is LoRaWAN, The Things Stack (TTS) is a concrete candidate; its documentation does not establish that the club uses it, that a device batches buffered samples, or that any specific device meets a battery target. Keep the documented staff-reviewed CSV backfill path as an **authorized option**, not a mandatory feature or an assumed technical capability. Both routes can feed one reviewed archive if their original route-specific evidence is retained.

PostgreSQL 18 is a reasonable small-pilot archive candidate because the proposed workflow needs relational identities, append-only provenance, and staff-reviewed imports. That is an **engineering inference**, not a product selection, benchmark, or product validation. Apache Beam event-time windows and allowed lateness provide a useful **analogy** for refreshing derived chart results after late arrivals; Beam is not a proposed pilot dependency. A time-series store such as InfluxDB 3 Core could be considered for a chart projection, but same-key overwrite behavior should not own correction history. [S08–S10, S15; R08–R09]

## Observation time, receipt time, replay, and corrections

Keep these times separate:

1. **Observation/event time:** when the station says it measured the value. Preserve the raw timestamp string, stated offset/time zone, clock-quality declaration, parser/schema version, and any justified normalized UTC value.
2. **Transport receipt time:** when the gateway, network server, or application endpoint received a radio envelope. A TTS example exposes root and nested `received_at`, gateway receive metadata, session and frame fields; the example does not promise a station sample-time field. [S04; R06]
3. **Archive append time:** when the club durably records the raw envelope or file/import.
4. **CSV upload/review time:** when an operator supplied the file and when it was reviewed/accepted. Neither is the observation time.

A gateway timestamp or TTS receipt timestamp must not be substituted for the sample time. For a multi-sample buffered payload, parse each sample's own timestamp if the actual schema supplies one. For a missing, ambiguous, or untrusted clock, preserve the original value and mark interpreted observation time unknown or uncertain; do not manufacture precision. The station steward owns station/sensor identity and clock-quality declarations. [S04–S06; R03, R06]

Use separate identifiers at the transport and application layers. A radio frame counter, session key ID, or gateway reception identifier can help explain protocol delivery and replay, but it is not necessarily a stable identity for each sample inside a payload. For LoRaWAN 1.0.4 specifically, a successful OTAA Join-Accept resets frame counters; ABP counters must not reset during the device lifetime and must survive power loss. Retransmission rules keep frame-counter behavior distinct from application-level buffered samples. These are version- and device-conditional rules; verify actual station firmware and activation before relying on them. TTS documents that a multi-gateway copy outside the deduplication window can be dropped, which likewise does not settle application replay. [S05–S06; R03, R07]

Where devices can supply a stable sample ID, use it across retries and record the session/boot generation that prevents a sequence counter reused after reboot from colliding with earlier samples. A database uniqueness rule may act on a known, non-null identity while retaining every raw received envelope. If a device has no such identity, a station/time/value fingerprint can identify **review candidates** only: equal measurements can legitimately occur, so do not silently discard them as duplicates. Archive-maintainer policy owns replay handling. [S09]

For CSV, hash and retain the exact source artifact and create an import record that links original row numbers to staged and accepted records. An exact same-file re-upload can be recognized by artifact hash/import history. A file whose contents changed is a new source artifact requiring review, not an in-place correction. Do not equate equal station/time/value rows with duplicates. Stage rows using an explicit versioned format, validate station identity, timestamp, timezone, units, and parse results, and require staff review of duplicate candidates and corrections. PostgreSQL `COPY FROM STDIN` is one possible client-streamed loader into staging; keep its fail-closed conversion default and do not use row-skipping `ON_ERROR ignore` for this review path. `COPY` and database transactions do not themselves coordinate external file preservation with database state, so the workflow must preserve the source artifact and record the acceptance event. [S08–S10; R08]

Append each observation as received, then record a correction as a new event linking the prior observation, reviewer, review time, reason, source envelope/file, and corrected values. A derived accepted view may present a corrected value while keeping both the original raw evidence and correction lineage. A late raw reading remains in history. If it changes a derived chart bucket, recompute or review the affected view rather than deleting the source record.

Apache Beam is a **delayed-event analogy**, not a selected dependency. Its guide describes watermarks as an estimate of event-time completeness and allowed lateness as a window policy that can let triggers emit further results after late data arrives. Its released `TriggerExample.java` at Beam v2.76.0 contrasts zero allowed lateness (late records dropped from that derived window) with a one-day example that permits late panes. This controls derived aggregation output, not the club's raw archive. Product choice: append raw input first; any bounded chart-refresh window may trigger recomputation, while records beyond it remain in the archive and can be included through later recomputation/review. [S11–S12; R09]

A relevant released failure/fix chain is Apache Beam issue #36470. The report says a Spanner Change Stream connector could become stuck when metadata-table partition-watermark updates were reordered, and that caching/filtering added in Beam 2.67 exacerbated it. Beam v2.69.0 release notes list the issue as fixed; the issue was later closed after that release. This is an ordering-sensitive connector example, not a defect claim about the club's radios or proposed archive. It reinforces the design choice to retain source facts independently of derived-window bookkeeping. [S13–S14; R10–R11]

## Freshness and historical-chart wording

**Product choice:** evaluate freshness from the age of the newest accepted observation whose timestamp and clock quality the station steward has declared trustworthy. If the newest candidate observation cannot be placed reliably because its time is missing, ambiguous, or clock quality is inadequate, present freshness as unknown/uncertain until the club's rule resolves it; do not use its recent receipt time to label it fresh. Show or retain newest observation time separately from last receipt time so a buffered hours-old sample received now is visibly old data.

The club editor chooses the freshness threshold, current/stale/unknown labels, empty-station behavior, and final copy. The steward supplies clock declarations; the archive maintainer determines the accepted/replayed observation view. The wording must describe historical observations and must not imply live measurement. No threshold or wording has been decided in this research stage, and no chart was exercised.
