## Executive recommendation

For ten stations, use one append-only observation and correction ledger as the canonical history, with a derived chart view ordered by validated observation time. Store raw radio envelopes and original CSV files separately from normalized samples, record station/source/time provenance on every row, and preserve corrections as new linked records. A modest PostgreSQL 18 deployment is a reasonable relational archive candidate for this pilot; this is an engineering inference from the small scale and need for reviewable lineage, not a benchmark or validated product choice. [S08–S10]

Provide two route adapters into that common archive:

1. **Low-power radio**: If the existing equipment is LoRaWAN, TTS is a concrete network-server candidate. Subscribe to the application uplink stream through MQTT or accept a configured HTTP webhook into a short, durable intake queue, then append raw envelopes before normalization. TTS’s MQTT server supports QoS 0 only; OASIS defines that mode as no acknowledgement/retry and delivery once or not at all. TTS’s optional queued webhook retries are conditional on deployment and (for TTS Cloud) Cloud Plus; default webhook handling tries once. Therefore neither route establishes exactly-once observation delivery. Keep an archive-side reconciliation/backfill path. TTS Storage Integration may help recover a recent gap if already enabled, but retention is 30 days on Cloud, 24 hours on Sandbox, configurable on Enterprise, and the integration writes in batches; it is not the club archive. [S01–S07]
2. **Optional staff-reviewed CSV backfill**: Keep the option in scope, not mandatory. For a documented format, retain the exact upload and SHA-256, identify the import and each original row, then load PostgreSQL staging from the client through CSV/STDIN. Validate headers, columns, time zone, units and parse outcomes. Surface errors rather than using COPY’s row-skipping mode. Require staff review for duplicate candidates and corrections before appending accepted observations or correction records. Enable only when the archive maintainer accepts a versioned template, reviewer procedure and replay/backfill policy. PostgreSQL’s COPY behavior informs this design but does not supply the review or lineage workflow. [S08–S10]

Apache Beam event-time windows, watermarks, allowed lateness and triggers are a useful delayed-event processing analogy, not a pilot dependency. A bounded late-update window can control when an aggregate is refreshed; it must not delete raw late readings. Append raw input first and route records older than any chosen aggregation window to retained history and recomputation/review. [S11–S12]

An optional InfluxDB 3 Core chart/analytics projection is possible only with append-only identity. Its documentation says same table/tag/time keys merge fields, with conflicting values not guaranteed to select the newest write. Avoid using same-key overwrites as the archive’s correction method. [S15]

## Recommended data and processing model

Keep these facts separate and immutable in the raw ledger:

- **Raw intake event:** source route, event/envelope ID if supplied, raw payload/file reference, SHA-256, station/device identity as received, protocol session/frame metadata, gateway metadata, receipt time at each known layer, archive append time, parser/schema version.
- **Normalized observation:** sample identity when actually supplied, declared station and sensor identity, observation timestamp as received, parsed UTC timestamp if justified, clock-quality state/uncertainty, value and unit, rainfall observation semantics if known, source intake ID/CSV row, initial disposition.
- **Review/correction event:** prior observation reference, candidate or accepted correction, who reviewed it, when, reason, linked source envelope/file, and the resulting public-view disposition. Corrections are new events; do not erase or mutate the original raw observation.
- **Derived chart/freshness view:** chart by validated observation time; separately show or derive newest observation time and latest receipt time. A value received recently can describe an older observation. The club editor chooses exact text and unknown/stale wording.

When a source has a stable sample ID, the archive can use a uniqueness rule on that specific identity while retaining every raw envelope/import record. If no stable ID exists, don’t hard-dedupe by station + timestamp + value: those readings may be legitimate equal measurements. Mark likely repeats and let the archive maintainer’s policy and staff review decide. For the exact same CSV file, compare the retained file hash and import ID to prevent blind second application; a changed file is a new input to review, not an in-place update. For a rebooted counter, require an epoch/session generation that itself survives or changes reliably. If unavailable, declare identity uncertainty rather than pretending the sequence is globally unique.

For LoRaWAN 1.0.4 specifically, the standard binds frame-counter persistence to activation/session rules: ABP counters must persist over power loss; OTAA join resets counters; frame counter retransmission rules are distinct from an application’s buffered sample identities. The actual standard and device behavior must be confirmed per station. The TTS docs add TTS-specific conditions: ABP counter reset can break an existing session; two gateways may produce copies of an uplink, but a delayed copy outside the deduplication window can be dropped. These behaviors neither guarantee all application observations arrive nor settle the archive’s policy. [S05–S06]

## Freshness and chart interpretation

Use observation time to place points on the historical timeline; use receipt time to show when the club last received input. Do not collapse them to one “latest” timestamp. An old buffered reading received today may increase “last received” without making the measurement current. The editor chooses wording such as a historical label with separate newest-sample and last-received times; this phrase is only an example, not approved copy. Define “unknown clock,” stale threshold, and empty-station behavior with the editor and steward. No output should imply live measurement, dispatch, risk rating, hazard monitoring, or safety advice.

## Released failure/history and remaining applicability

Beam’s released TriggerExample demonstrates that lateness policy changes derived results: zero allowed lateness drops late data in the example, while the one-day policy permits late panes before the window expires. It is useful for deciding refresh policy but cannot be lifted as a club retention rule. [S11–S12]

Beam issue #36470 provides a concrete failure: Spanner change-stream partition watermark estimates could move backward after metadata updates reordered; the release notes identify a fix in 2.69.0. This is a connector-specific failure, and the issue’s stated cause is not evidence that a club station will exhibit it. Its applicability is the caution that ordering/watermark bookkeeping is policy/stateful; archive raw facts independently, and verify any selected processor/version on its own merits. [S13–S14]

InfluxDB 3 Core docs warn that same table/tag/time writes with conflicting fields may not preserve the latest value. If the archive maintainer chooses a time-series store for the chart, keep raw/correction records append-only and project a deterministic accepted view; do not rely on overwrite semantics. PostgreSQL 18 documents offer CSV staging and constraints/transactions suited to a small review workflow, but no deployment choice has been tested. [S08–S10, S15]

4. **Still owner-unassigned in the brief:** declare temperature/rainfall units, rainfall accumulation semantics, sample cadence, accepted time zones, quality/range checks, and handling of samples with missing/ambiguous timestamps. Route to the appropriate owners before final schema acceptance; this draft does not invent a new authority.
