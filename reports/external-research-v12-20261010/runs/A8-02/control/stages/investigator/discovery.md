# Investigator discovery — delayed community weather-station observations

Stage: investigator, run A8-02-control. Discovery was made from the exact brief only, before reading the released plan. This is a pilot-scale planning proposal, not an implementation or validation result. All source IDs below are stable within this stage; [sources/index.md](sources/index.md) is the navigation index and source-map.json carries complete source identity and conditions.

## Recommendation

Use one append-only observation ledger and one derived historical-chart view for all ten stations. For a low-power route, treat a LoRaWAN application uplink as one transport envelope that can carry one or more station samples; capture the application-server receipt time and full transport envelope, then parse sample-level observation times and identifiers. The Things Stack (TTS) is a useful concrete candidate if the club’s gateways and devices already use LoRaWAN. Its MQTT application integration is MQTT 3.1.1 QoS 0 only, so consumer delivery may be lost; TTS Storage Integration is a bounded reconciliation aid, not the club’s archive. If HTTP webhook retries are already enabled and available in the chosen deployment, they can retry temporary endpoint failures, but default TTS webhooks are tried once and the retried feature is deployment/subscription dependent. Do not infer an end-to-end guarantee from either route. [S01–S07]

Use PostgreSQL 18 as the pilot’s canonical archive candidate because ten stations, reviewed backfills, provenance, uniqueness constraints, and correction lineage are relational and modest in scale. This is a product choice/inference, not a product trial. Preserve the received JSON or original CSV artifact and its hash, plus normalized observation rows and append-only correction/review events. A CSV file should enter a staging table with an explicit versioned template and row review, not directly overwrite canonical readings. PostgreSQL COPY supports CSV loading, matching headers, and client-streamed input; its default is to stop on conversion errors, while its optional ignore mode discards rows. Preserve that fail-closed default for the review path. [S08–S10]

A time-series alternative such as InfluxDB 3 Core can serve chart projections if its identity and correction semantics are deliberately designed, but it should not own the raw correction ledger by default: identical table/tag/time keys merge, and conflicting fields are not guaranteed to resolve to the last write. Its current guidance recommends append-only unique timestamps. [S15]

## Time, identity, replay, and corrections

Keep separate fields and meanings:
- observation/event time: when the sensor says it sampled the value; use this for historical chart placement only after preserving the original timestamp text, offset/time-zone declaration, parser/version, and the station steward’s clock-quality declaration;
- receipt time: when the network/application endpoint received a radio message, or when a CSV backfill was uploaded; TTS examples expose gateway/network/application receipt timestamps separately;
- archive time: when the club’s intake durably appended the envelope/observation.

A gateway receive timestamp or TTS received_at is not a station’s sample timestamp. For a multi-reading buffered payload, parse each sample’s timestamp; do not assign the enclosing radio frame’s one receipt timestamp as every sample’s observation time. If time is absent, ambiguous, or clock quality is poor, retain the raw representation and mark the interpreted event time unknown/estimated rather than manufacturing precision. The station steward owns station/sensor identity and clock-quality declarations. Rainfall unit and accumulation-vs-increment semantics, payload schema, accepted time zones, and quality limits remain explicit pilot inputs because the brief does not specify actual instruments.

Use distinct identities at each layer. The radio frame/session/counter is transport evidence only. LoRaWAN 1.0.4 says FCntUp increments by transmitted frame under its retransmission rules; ABP frame counters must survive power loss, whereas OTAA successful join resets counters. TTS troubleshooting also notes ABP counter-reset trouble and that multi-gateway receptions may be deduplicated in a window, with late copies outside it dropped. Applicability is conditional on the actual LoRaWAN version and device. The app’s sample ID should be device-generated and stable across replays where possible, e.g. a persistent station/sensor identity plus boot/session generation plus per-sample sequence. A rebooted sequence counter needs a new durable generation/boot ID; a frame counter is not a substitute. Where equipment cannot provide that, use a documented candidate fingerprint only to propose duplicate review, not to silently suppress records. [S04–S06]

Store each raw observation once as received, then record corrections as new events that point to the prior observation, identify reviewer, time, reason, source file/message, and corrected values. A current accepted view may exclude a superseded row for the public chart while raw rows and the correction chain remain. A late row remains in the archive regardless of how old it is; it may trigger an event-time chart or affected-bucket recomputation.

Freshness and chart order are different questions. Sort historical points by validated observation time. Retain separate last-observed and last-received values so an old buffered sample received now does not imply a current measurement. Recommend an explicit chart label that communicates “historical observations” and distinguishes newest sample time from receipt time; the club editor owns the final wording and any threshold/unknown-state wording. This is informational only, never an equipment control, live-weather assertion, or hazard warning. TTS itself distinguishes UTC event-detail times from local-browser display time, reinforcing the need for consistent timezone handling. [S04–S05]

## Delayed-event mechanism and released failure history

Apache Beam is a useful analogy, not a proposed pilot dependency. Its event-time windows use a watermark as an estimate of completeness; allowed lateness and triggers can accept later arrivals and emit additional panes. The released TriggerExample code (v2.76.0) contrasts zero allowed lateness, where late data is dropped, with one-day allowed lateness and late panes. That policy controls derived-window results, not the canonical raw archive. For this club, append first; optionally use a bounded late-update window for chart refresh efficiency, but route anything beyond that bound to retained archive/review/recomputation instead of dropping it. [S11–S12]

A relevant released time-ordering failure is Beam issue #36470. The Spanner Change Stream connector could become stuck because partition watermark updates were reordered in metadata; the issue says caching/filtering introduced in 2.67 exacerbated it. The Beam 2.69.0 release notes list the fix; the issue was closed after that release. This is evidence that even sophisticated event-time plumbing can fail around ordering/watermark state, not evidence of a bug in this club’s radio stack. The remaining device-dependent questions are the actual station protocol, frame-counter behavior across reboot/rejoin, whether readings are buffered or retransmitted, the sample timestamp source and drift, sample IDs, batch payload limits, and gateway/backhaul behavior. Verify those with inventory, released device manuals/source, and bench-only tests before relying on assumptions; do not connect to live stations. [S13–S14]

## Owner inputs and constraints

- Station steward: declare each physical station/sensor identity, relevant device/version/session details, clock source, reset behavior, and clock-quality/uncertainty.
- Archive maintainer: decide replay identity/policy, acceptable duplicate-candidate handling, CSV backfill eligibility, reviewer/audit procedure, and correction acceptance/supersession rules.
- Club editor: choose freshness and unknown/stale wording without implying live measurements; confirm chart semantics for event-time vs receipt-time disclosure.
- Unresolved beyond the assigned roles: rainfall accumulation semantics, units, sample interval, file schema, timezone conventions, freshness threshold, and pilot availability targets. Assign these before chart acceptance; do not infer from generic product documentation.

Negative constraints preserved: no live-station connection, gateway modification, guaranteed exactly-once observation claim, loss of late raw readings, weather-safety advice, production access, account, purchase, install, or write. No local implementation or executable validation was performed. Research retrieval is evidence about external products/specifications, not product validation.
