## Scope and recommendation (inference from the brief)

For ten stations, keep an append-first observation archive as the source of truth and generate the historical chart and freshness view from it. Support two controlled paths into the same archive: (A) a gateway-fed MQTT stream for stations that can deliver through a low-power radio gateway, and (B) an optional, staff-reviewed CSV backfill for buffered/outage readings. Save the original message or file and add normalized rows and corrections as new records. A database uniqueness rule may make a confirmed stable source key idempotent in a derived ingestion path; it must not erase the raw occurrence or turn timestamp/value similarity into a claim of identity. This is a pilot-scale planning choice, not a selected product or implementation.

**Alternative worth evaluating, not the archive recommendation:** InfluxDB OSS v2 offers a time-series point format and compact chart queries, but its documented point identity is measurement + tag set + timestamp. Same-key writes union fields and let the new value win ties; coarsening precision can make different observations collide. That is useful for a read projection, but it is not a row-preserving correction ledger by itself. Confirm the exact target version before relying on v2 behavior; the v2 FAQ is rolling documentation and does not establish v3 behavior. [S09]

## Time, identity, replays, and correction lineage

- Store **observation time** (as supplied by the station, preserving its original text/offset/precision) separately from **arrival time** (server receipt for MQTT; accepted import time for CSV). Do not substitute upload time for sensor observation time. Record normalized UTC only alongside the unchanged source representation and an explicit quality declaration.
- Use receipt time for the freshness calculation and observation time for the historical axis only when its quality permits; otherwise expose that uncertainty in the view. Freshness wording belongs to the club editor and should describe receipt/recorded time without saying a value is live. The archive maintainer chooses replay/backfill policy; the station steward owns identity and clock-quality declarations.
- MQTT packet identifiers are transport handshake IDs, can be reused after PUBACK, and the DUP bit concerns a packet rather than the underlying observation. The standard says a repeated application message can arrive with DUP=0 and a different packet ID. QoS therefore cannot serve as a durable observation ID or establish exactly-once sampling. Use a source event ID if the device supplies one; otherwise record station ID, any source sequence, a steward-declared boot/epoch identifier if available, raw payload, route, and arrival time. A rebooted counter without a known epoch is ambiguous; flag candidate collisions instead of discarding a row. [S01]
- For an identified transport replay, mark the occurrence/replay relationship and let the archive maintainer choose whether the chart projection suppresses a duplicate. Preserve each raw received envelope. Do not deduplicate solely on `(station, timestamp, value)`: two real readings can match, timestamps can be coarse/bad, and device counters may reset. PostgreSQL unique constraints only establish the selected key's uniqueness; by default NULL values do not compare equal, so any idempotency key must be present, stable and validated. `ON CONFLICT DO NOTHING` drops a proposed row and `DO UPDATE` changes the conflicting row; neither belongs on immutable raw evidence without an explicit, reviewed policy. [S04, S05]
- Model a correction as an appended revision/annotation pointing to the prior observation, with reason, reviewer/actor, correction time, and approval state. Keep original message/file/row and all revisions queryable. Build the chart from the latest accepted interpretation, while preserving the raw observation and its correction lineage. This is a local design inference, not a behavior guaranteed by any database product.

## Boundary and event-time analogue

The boundary is three layers: (1) the actual radio/network and gateway buffering/retransmission behavior; (2) the application’s event identity, persistence, replay, and correction policy; and (3) the historical chart’s event-time ordering, late updates, and editor-approved freshness description. MQTT 5 documents message QoS and session semantics at layer 2, while requiring an ordered, lossless underlying transport; it cannot answer how a particular radio/gateway handles outage or reboot. Device model, radio standard, firmware, gateway spool, counter semantics, clock source, broker settings and QoS are still unknown and require the steward/maintainer to identify them. [S01, S02]

Apache Beam is a useful **analogy**, not a proposed deployment: it groups by element event time, emits at watermark/trigger points, and exposes a finite allowed-lateness choice. Its v2.70.0 `Window` Javadoc says elements later than the allowed-lateness boundary are dropped and window state is then cleaned up. For this club, finite chart-window policy must never become raw-archive deletion: very late rows stay archived and can trigger a rebuild/backfill. [S06]

## Bounded released failure/fix chain

Apache Beam issue #36470 reports Spanner Change Stream reading getting stuck after a partition watermark moved backward. The issue attributes this to possible reordering of metadata-table watermark updates, exacerbated by watermark caching/filtering introduced in Beam 2.67. The Beam 2.69.0 release notes list the stuck-reading bug as fixed; the issue page also records closure after 2.69 released. The issue's final milestone displays 2.70.0, so the issue and release metadata disagree about milestone; the reviewed sources do not expose the actual code-fix commit, and no implementation detail beyond the report is claimed here. This is relevant as a released event-time progress failure and a reason to test monotonic progress/recovery, not evidence that a station gateway has this defect. [S07, S08]

## CSV backfill status and owner inputs

The supported optional CSV path is retained because the brief authorizes it and public documentation supports a concrete staging mechanism. Recommended admission conditions are: explicit station/sensor identity; timestamp meaning, timezone/precision and clock quality; schema/version and units; stable file/import ID and SHA-256; original file plus source row locator; row-level parse outcome; duplicate candidates visible to staff; correction references and reviewer decisions. The archive maintainer decides replay/backfill/dedup behavior. The station steward declares sensor identity, replacement history, counter epoch semantics and clock quality. The club editor chooses freshness language consistent with actual receipts and not implying live measurement. Missing facts are explicit owner questions, not reasons to skip research or assume a device capability.

## Negative constraints

No live-station connection, gateway modification, production access, purchases, installs or accounts were used or proposed. Do not claim guaranteed exactly-once observation delivery. Do not discard late raw readings or silently overwrite raw readings with corrections. Do not issue weather-safety advice or make the system control equipment or produce hazard warnings. This is a research/planning proposal only.
