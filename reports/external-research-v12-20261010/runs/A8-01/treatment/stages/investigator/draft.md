# Research proposal: revision-aware exhibition asset deposits

**Run:** A8-01-treatment · **Stage:** investigator  
**Evidence base:** the complete brief, read before discovery; then the exact released plan copy at `revealed-plan.md` after discovery was frozen. The released plan is treated as a fallible draft to reconcile, not as external evidence. Source IDs below resolve through [`sources/index.md`](sources/index.md) and [`source-map.json`](source-map.json).

## Recommendation

For a small pilot on ordinary local disk plus the gallery’s existing offsite copy, use a **BagIt v1.0 package per exhibition deposit state**, with one new package whenever an asset correction is approved. Preserve the old package unchanged. Do not overwrite the caption in a package already called final. Link the new package to the earlier one in a small human-readable exhibition inventory. This uses an open directory format and ordinary files; it adds no hosted preservation platform. It is a recommendation based on the stated scale, not a requirement of BagIt.

Keep **OCFL 1.1** as the alternative if the gallery expects many revisions or needs each object’s successive states represented and validated in one persistent filesystem object. OCFL is more explicit about stable object identifiers, version directories, inventories and historical state, but it also requires disciplined inventory updates and compatible validation. Neither format decides which photographs, captions, diagrams or catalogue PDFs belong in the exhibition deposit; that is the registrar’s decision.

Alongside either layout, keep a small readable asset/version register and copy/restore event log. Base the log’s fields on PREMIS’s distinction between objects, events and agents, but do not claim the spreadsheet is PREMIS-conformant. A digest confirms bytes against a stored reference; it does not establish authorship, curatorial completeness, live remote possession or backup recovery.

### Recommended identifiers and records

Keep these separate:

- `exhibition_id`: the exhibition collection (for example, `EXH-2026-04`).
- `asset_id`: a stable ID for the conceptual photograph, caption, diagram or catalogue item; never derive it solely from a filename or digest.
- `asset_version_id`: the approved state of that asset (for example, `CAP-0042-v2`), with `supersedes` pointing to `CAP-0042-v1` when corrected.
- `deposit_id`: one complete package state, plus an optional `previous_deposit_id` relationship.
- `sha512` or owner-selected `sha256`: digest of one exact file’s bytes; record the algorithm alongside the digest.
- Relative package path and user-facing filename/description: paths locate the deposited copy; do not rename the source original.

For a corrected caption, make a new deposit with the corrected caption and current approved exhibition set, retain the previous package unchanged, and update the register to connect the two states. Registrar decides whether an unchanged asset gets the same version reference in the newer deposit or a newly enumerated version record; the register must make the relationship unambiguous. The source material does not require full duplicates or a particular folder depth.

A suggested shallow BagIt payload is `data/photos/`, `data/captions/`, `data/diagrams/`, `data/catalogue/`, plus `data/inventory.csv` and `data/README.txt`. The CSV should carry exhibition ID, asset ID, version ID, role/type, descriptive label, relative filename/path, approval/status and predecessor relation. Generate the manifest after the inventory is final so that the CSV and all assets are covered. Add a tag manifest for metadata tags that should also have checksums. Use plain UTF-8 text, avoid paths differing only by case or Unicode normalization, and do not create names that collide with the target filesystem’s reserved characters or limits. These are recommendations for owner choice, not new BagIt requirements. [S01]

For the separate copy/restore log, use one row per event: event ID, event type (`deposit`, `copy`, `verify`, `restore_test`, `repair`), event time with UTC, actor/role, exhibition/deposit/asset-version identifiers as relevant, source and destination location labels, exact operation, validator and version if used, result, and a report/log reference. The log should state whether the operation merely checked recorded presence, recalculated hashes, copied bytes, or restored and opened files. A digest mismatch and a failed remote availability check are different outcomes. [S05, S06]

## Bounded copy and restore procedure

1. **Registrar release:** enumerate the intended assets and approved versions in `inventory.csv`; review that captions, diagrams, photos and catalogue PDFs are present. Assign IDs and freeze this list for the deposit. A manifest cannot fill in the curator’s intent.
2. **Package a copy:** copy selected files into the new package’s `data/` tree. Do not move originals. Create the README/index and metadata, then generate the BagIt payload manifest (recommended SHA-512) and tag manifest for tag files. Record deposit ID and prior-deposit relationship.
3. **Validate source package:** check structural completeness; compare the actual payload path set with every manifest and the register; recalculate all listed digests. Open a small representative sample of each type to catch unusable files that are byte-valid. Record validator name/version and output. A failed check blocks this deposit from being called verified.
4. **Copy to existing offsite storage:** copy the entire immutable package tree, not a partial delta or only its latest caption. At the destination, enumerate paths and run the same completeness and checksum validation. Record source/destination labels, time, result, and package manifest reference. Do not interpret recorded location or a successful source check as proof the offsite copy exists.
5. **Restore drill:** on a chosen schedule and after storage/media changes, copy one chosen package back from offsite into a new staging location. Validate its files, names, manifests and checksums there and open representative files. Record what was actually restored, the result and any exceptions. This is a proposed test; its frequency and sample selection belong to the custodian.
6. **Handle failure without blessing it:** preserve the suspect copy and reports. Reconcile against a known-good package and the registrar’s inventory. Repair by copying from a verified source into a new work copy; do not regenerate the only manifest from a possibly altered copy and then call that proof.

**Missing file:** a path listed in a manifest but absent at the destination fails BagIt completeness; list the missing relative path and stop the copy/restore acceptance. If an item expected by the registrar is absent from both the package and manifest, the checksum validator may pass; the registrar’s inventory review is the control that catches that omission.

**Changed name or path:** an unexpected rename normally yields the old manifest path missing and a new unlisted path. Compare the actual path set and Unicode-normalized/case-folded collision diagnostics as appropriate to the actual target filesystem; do not silently rewrite the manifest. If only the encoding/normalization changed and the content is otherwise matched, flag it for explicit custodian resolution and record the mapping. The BagIt RFC documents that visually identical names may compare unequal across filesystems and recommends tolerant normalization-aware validators. [S01]

**Manifest mismatch:** any digest mismatch fails integrity against the deposited reference. Do not “repair” a mismatch by recalculating the manifest over the discrepant copy; preserve both versions, obtain a known-good copy, and investigate. A missing/extra file or path mismatch is separately reported as a completeness/layout error. If no known-good copy validates, record `NOT_RECOVERED` and escalate to the custodian and registrar rather than asserting recoverability.

## Bounded released issue and local-storage consequence

The relevant example is OCFL/spec issue [#538](https://github.com/OCFL/spec/issues/538), opened 2021-04-02 and closed through #547 in the 1.1 milestone. It raised ambiguity about how historical inventories’ manifests relate to their own and earlier content directories. The [released OCFL 1.1 change log](https://ocfl.io/1.1/spec/change-log.html) documents that v1.1.0 clarified the rule so each historical inventory’s manifest references every file in that inventory’s version directory; the [release page](https://github.com/OCFL/spec/releases) identifies the subsequent 1.1.1 release (tag `1.1.1`, commit `c3f88b3`). Current 1.1 text also requires the stable object ID across versions, continuous version numbering, immutable existing version directories, and per-version inventory sidecars. [S02–S04]

This history concerns interpretation of a specification rule, not an observed implementation bug, corrupted gallery package or actual lost file. If using OCFL on ordinary disk/offsite storage, preserve all version directories and inventory files together and validate the full object at source, destination and restore. A hand-copied “current” view may discard older corrected captions and fail the preservation goal even if the newest file hashes correctly. If using BagIt, the same underlying lesson is to preserve each immutable full deposit; the OCFL clarification itself does not govern BagIt. A path-specific cross-platform risk is separately documented by RFC 8493: Unicode normalization and Windows/Unix differences can make filenames appear present while failing byte-exact manifest lookup. [S01]

## Optional human-readable exhibition inventory

**Retain as supported optional scope.** The brief authorizes the option, not a mandatory feature. BagIt’s optional `bag-info.txt` is meant for human use and arbitrary tag files are allowed, but generic BagIt processors ignore custom tag semantics. Therefore the proposal’s simple CSV is a local, human-readable inventory—not an established BagIt capability or a replacement for machine manifests. Keep it as payload so its bytes are included in the payload manifest. Provide a short README defining columns and the difference between asset/version IDs, deposit ID and digest. Test ordinary spreadsheet/text opening in the pilot. If it is too difficult to maintain, or demonstrably duplicates an authoritative registrar-held inventory with material drift risk, the registrar can exclude it and record why. No current source evidence justifies dropping it. [S01]

## Decisions and unresolved owner inputs

**Registrar decisions:** stable-ID pattern; the authoritative definition of an exhibition’s complete set; which version is current and how corrections/renames relate; who approves the human CSV; whether full snapshot bags are acceptable; when an item may be marked final.

**Custodian decisions:** SHA-512 (recommended) versus SHA-256; shallow folder/package depth; exact existing offsite destination labels and copy procedure; compatible validator and recorded release/version; validation cadence; restore-drill sample; failure escalation and retention of suspect copies.

**Inputs to resolve before a pilot:** likely bytes/file counts and correction frequency; actual local/offsite filesystem and transfer path; representative filenames including non-ASCII/long/reserved-character cases; whether an existing catalogue already provides the optional inventory; staff tools available to validate and open files; and whether the existing copy has a documented restore process. These open questions do not block answering the public specification questions and do not authorize platform replacement.
