# Independent discovery — revision-aware exhibition asset deposits

**Run:** A8-01-treatment · **Stage:** investigator · **Discovery input:** the complete brief at `inputs/brief.md`, read before external research. **Exact plan:** not available or consulted during discovery. This is the pre-release evidence base; use the exact released plan later to write dispositions in `draft.md`.

## Findings and preliminary direction

For the stated pilot, the strongest low-overhead candidate is BagIt RFC 8493 v1.0 used as one self-contained package per exhibition deposit state. It encloses ordinary files in a visible directory and a checksum manifest. It is explicitly a package/transfer layout, not a version-history system. Preserve each deposit unchanged; when a caption is corrected, issue a new deposit ID and keep the earlier one. Link both to a stable logical caption ID and record `v1 → v2` in a small exhibition inventory. For a modest gallery collection, full snapshots are easier to reason about during offsite recovery than clever incremental updates, at the cost of repeated bytes. This is an inference for the pilot, not a BagIt requirement. [S01]

OCFL 1.1 is the meaningful structured alternative. It is a filesystem-native object model with a stable object ID, continuous version directories, historical inventories, logical state, digest mappings, and immutable earlier versions. It supports an accumulated history more directly than BagIt and can live on ordinary file storage; it also imposes stricter update rules and requires a compatible validator. It is worth retaining if the gallery expects many revisions or wants reconstructable object state, but is likely over-structured for a few corrected captions. It is a standard, not a new hosted platform. [S02, S04]

Separate four identities. An **exhibition ID** names the exhibition; a persistent **asset ID** names the conceptual item (for example, one caption independent of filename); an **asset version ID** names a particular approved state; a **deposit/package ID** names the specific packaged snapshot. A cryptographic digest identifies exact bytes, not the intellectual asset or its author. A correction keeps the asset ID, gets a new version ID and byte digest, and links to its predecessor. A rename updates the recorded path while retaining the asset ID. Manifests establish exact-file integrity and manifest-relative completeness only; they cannot tell whether the registrar omitted an intended photograph, diagram, caption or catalogue. The registrar must attest to the intended set and version relationship. [S01, S02, S05]

Use two complementary records rather than stretching one checksum into proof of everything. First, place a human-readable `inventory.csv` and a short `README.txt` with the deposit, listing exhibition/asset/version IDs, role, descriptive label, relative path, correction relationship, and status. RFC 8493 allows additional tag files and defines bag metadata intended for human use, but generic clients ignore the semantics of custom tags. Make the CSV a manifested payload file if its bytes should be covered by the payload manifest. The CSV is a local product choice; BagIt does not define its column meanings or guarantee its completeness. Keep the layout shallow (`data/photos`, `data/captions`, `data/diagrams`, `data/catalogue`) and use conservative filenames in the package copy to reduce platform normalization/character-limit surprises. Do not rename or move gallery originals. [S01]

Second, keep a small readable copy/restore event log (CSV or text) with event ID/type, UTC time, actor/role, exhibition and asset/version/package IDs, source and destination location labels, observed operation, verifier/result, and notes. This is a practical PREMIS-inspired mechanism, not formal PREMIS compliance. PREMIS distinguishes objects, events and agents and places a fixity check's result/date in an event record. git-annex is a useful higher-capability discovery: content keys, `whereis`, location logs and `fsck` can help a Git-capable custodian track repository copies. Its manuals warn that `whereis` is based on last reported state rather than live remote confirmation and that fast remote checks omit checksum work; it adds software/workflow and is unnecessary under the brief's existing local/offsite-copy model. [S05, S06]

## Validation model (proposed; not executed)

At deposit, the registrar freezes the intended inventory and version links; a custodian creates the package on a copy, generates the manifest after the human index is complete, and validates the package. The custodian copies the entire immutable package to the existing offsite location, validates the destination against the same manifest, and records the result. At a scheduled interval and after media migration, restore one selected package from offsite into a separate staging directory; validate there and manually open representative photographs, captions, diagrams and catalogue PDFs. Do not count a successful local checksum as a test of offsite availability or restore usability.

- **Missing file:** report each manifest path absent as incomplete; preserve the failed copy for triage and do not overwrite a verified deposit. Re-copy from a verified peer only after checking its package ID and record the repair.
- **Changed filename/path:** compare names as well as bytes. A rename should surface the old path as missing and the new path as unlisted/extra; a normalization-only difference can be visually invisible. Treat unexplained path differences as failure pending registrar/custodian review. RFC 8493 describes Unicode normalization and Windows/Unix path interoperability risks; test any real mixed-platform path set before adopting it. [S01]
- **Manifest mismatch:** a digest mismatch is an integrity failure; a path/file-set mismatch is a completeness/layout failure. Preserve the observed report and source/destination copy labels. Do not “fix” a manifest automatically, since regenerating from a suspect copy would bless unknown changes.
- **Restore failure:** record NOT_RECOVERED, retain evidence, and investigate the existing copy chain. A correct manifest is not evidence that either backup is still available or recoverable.

## Historical release example and applicability

OCFL issue #538 (opened 2021-04-02) asked for clarity around manifests in historical inventories. It was closed through #547 in the 1.1 milestone. The released v1.1.0 change log explicitly clarified that each historical inventory's manifest must reference every file in its own version directory. The issue documents ambiguity and a wording fix; it does not report a data-loss event. The lesson for local/offsite copies is to copy and validate the complete versioned object, not only its latest/head view, and to check historical inventories with the relevant OCFL validator. It does not make BagIt's separate deposit model an OCFL object. [S02, S03, S04]

## Owner choices and boundaries carried forward

- Registrar owns intended completeness, asset IDs, correction/version relationships, and sign-off on the final human index.
- Storage custodian owns the existing offsite process, copy receipts, validation frequency, restore-test selection, and failure handling.
- Recommend SHA-512 for new BagIt payload manifests because RFC 8493 says BagIt 1.0 tools should enable it by default; retain SHA-256 as an interoperability option if the selected tools and custodian prefer it. The owner chooses after testing the actual validator; this is not a presumed mandate. [S01]
- Recommend one complete bag per exhibition deposit and shallow, role-based folders. Registrar and custodian should confirm package depth, folder names and whether full snapshots are acceptable. These are choices, not standard requirements.
- Keep the human index as a supported optional feature: retain it if the registrar can maintain a small stable CSV and staff can open it in ordinary text/spreadsheet software; exclude only if the pilot shows the index duplicates an approved authoritative catalogue or cannot be maintained, with the reason recorded. No evidence here establishes an automatic catalogue integration.
- Do not move originals, create accounts, imply hashes prove authorship or copy recoverability, or replace the current offsite copy with an untested platform. Research was read-only; no installation, account, production access, purchase, live write, package creation, restore, or product validation occurred.
