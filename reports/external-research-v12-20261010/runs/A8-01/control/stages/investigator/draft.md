## Recommendation

Pilot a direct, filesystem-readable BagIt 1.0 deposit directory for each approved exhibition deposit, with an approved human-readable `inventory.csv`, an immutable prior deposit, and a new deposit when an asset is corrected. The inventory carries the gallery's logical IDs and relationships; BagIt's payload manifest carries path and byte digest. Recommend SHA-512 for newly created manifests because RFC 8493 says BagIt 1.0 implementations must support SHA-256 and SHA-512 and should enable SHA-512 by default, but the registrar/custodian must choose and document the actual algorithm policy. Use a full per-file validation after package creation and after offsite copy, plus a bounded restore rehearsal to a clean temporary destination. A valid package is not a completeness decision, a provenance receipt, or a backup recovery guarantee.

Keep OCFL 1.1 as the serious alternative if repeated corrections, preservation of many object-level versions, or deduplicated content management justify a richer versioned-object structure. OCFL is itself a transparent filesystem/object-storage layout and does not require a hosted preservation service; it is more structurally involved than the proposed small-gallery handoff. Git-annex is an optional future aid if the gallery needs a managed view of where content is believed to be held, but the inspected `whereis` documentation says its location report does not contact remotes. It is not copy validation. None of these alternatives authorizes replacing the existing offsite copy without a successful, owner-approved pilot and restore.

The proposal keeps gallery originals in place, uses only copies in a package staging area, creates no account, and does not claim that checksums establish authorship, custody, completeness, or future recoverability. The complete evidence trail and limits are summarized below; exact source identity/conditions live in the source map.

## Evidence-backed comparison and operating model

| Approach | What it provides | Correction/version behavior | Fit and limitations here |
|---|---|---|---|
| **BagIt 1.0 directory deposit** [S01] | `bagit.txt`, `data/`, one or more payload manifests, optional tag manifests and human metadata such as `bag-info.txt`; ordinary files are directly accessible. The manifest maps file paths to checksums; completeness/validity have separate definitions. | BagIt itself is a package convention, not the gallery's asset/version registry. Preserve the earlier approved bag and issue a new package snapshot. Registrar's CSV establishes stable logical IDs, role and `supersedes` relationship. A later bag can include shared files again; this deliberately favors standalone restore over storage efficiency. | Simplest inspectable file deposit; appropriate for low volume and existing file copies. | **OCFL 1.1 versioned object layout** [S02–S03] | A stable object `id`, sequential `v1`, `v2`… directories, version states mapping digests to content paths, root inventory and digest sidecar, optional per-version inventories/logs. For a small pilot it imposes more conventions and operational checks. It is still a filesystem/object-storage layout, not a required hosted service or a claim of successful recovery. |
| **PREMIS-shaped custody/event record; optional git-annex comparison** [S09–S11] | Lightweight log of object/package ID, actor/role, UTC time, action, manifest digest, location labels, tool/version, result, exception and linked prior event. Git-annex location reports are last-known information and do not contact remotes in `whereis`. | A small CSV/text event register is more appropriate to the present scale than adding another preservation platform. ### Identity and boundaries

Use a gallery-controlled, stable logical `asset_id` independent of filename or digest; keep a `version_id` for each accepted byte state and record the version's relation to its predecessor. Example: `asset_id=CAP-042`, `version_id=2`, `supersedes=CAP-042/v1`, `reason=corrected caption`, `approved_at=...`. File paths and digests answer “which bytes at which package path?”; logical IDs and registrar relationships answer “which gallery asset/version is this, and why is it current?” A renamed path must be recorded, not silently treated as the same path or new asset based on a filename alone.

Keep four judgments separate:

1. **Integrity/fixity:** does each copied file's digest match its recorded digest, and do expected paths exist?
2. **Completeness:** did the registrar's approved inventory include every asset required for that exhibition, and does each inventory row resolve to the deposit? A self-consistent package can still omit a required row.
3. **Provenance/custody:** who prepared, approved, copied, verified or restored this version, when, from/to which recorded locations, with what result? A digest by itself proves none of these.
4. **Recoverability:** can the current custodian actually restore an approved copy to a clean destination and open representative formats? A copy receipt or hash pass does not guarantee a future recovery.

A PREMIS-inspired CSV is an analogy, not a claim of PREMIS XML conformance. The v3.0 PDF describes a digest comparison as a fixity check and records the act/date as an Event and its result as `eventOutcome`; the distinction is consistent with the gallery keeping a human-readable event ledger [S09–S10]. The current HTML semantic listing introduces five entities including Intellectual Entities, while the 2015 v3.0 PDF describes four; this proposal borrows only Event/Agent fields common to the examined material and does not rely on a PREMIS entity count.

## Bounded copy, restore and mismatch protocol

1. Registrar freezes and approves the expected exhibition inventory. Record expected item count and exceptions. Assign stable asset and version IDs; reconcile every expected row to the copy set. Do not move, rename, or otherwise modify gallery originals.
2. Copy expected files to a staging area. For any explicitly approved mapped name, preserve both original and package path in the inventory; do not normalize names in place. Detect case-only and Unicode-normalization collisions before package acceptance.
3. Create the BagIt 1.0 package from the staging copy. Put the inventory snapshot in the payload so the payload manifest covers it; create selected payload manifest and tag manifest; record package/version ID and algorithm policy. Prefer full SHA-512 validation after creation. Do not accept a Payload-Oxum-only/fast result as full integrity validation [S01].
4. On the local package, run structure/completeness plus full per-file manifest validation. Separately reconcile package paths and inventory rows. Record tool/release, exact operation, date/time, expected count, result and exceptions. A tool's reported “valid” does not establish that the inventory was complete.
5. Copy the exact package tree to the existing offsite copy. At the destination, compare the complete set of relative paths and run full per-file digest validation against the already approved reference manifest. Do not edit the reference manifest to make the copy pass. If paths changed on that destination filesystem, stop and resolve the path mapping/collision with the registrar and custodian.
6. In the bounded pilot, restore one complete selected package to a clean temporary destination using the documented copy procedure. Revalidate every listed file, reconcile the inventory, and open a representative photo, caption, diagram and catalogue PDF. Record what was sampled, elapsed time, tool/version, any failures and the successful retry. Keep this as a planned check until actually run; an isolated pass does not prove every future disaster recovery.

| Observed condition | Required behavior |
|---|---|
| Manifest-listed file absent | Fail validation; report exact path. Check the source, copy operation and destination. Do not delete the manifest row or regenerate it without owner approval. |
| A file exists under an unlisted path | Report unexpected path. If it looks like a renamed/case/Unicode-normalized path, compare stable ID, original/package path and bytes; registrar approves any mapping. Leave unresolved until manifest and inventory agree. |
| Path exists but digest differs | Mark integrity failure. Preserve both source and copy for investigation; never overwrite the source or silently rewrite the reference digest. If the registrar accepts the changed caption as new content, issue a new version and deposit, retaining the prior one. |
| Manifest, inventory and bag metadata disagree | Do not call the deposit complete. A manifest validates only the paths it enumerates; the separate registrar-owned inventory check catches omissions. If a manifest is changed, verify it against a previously trusted tag manifest/receipt or approved original package; checking a replacement manifest against itself provides no independent baseline. |
| Full copy validates but restore has not been exercised | Record “copy validation passed; restore NOT_RUN.” Do not state “recoverable” or “backup proven.” |
| Validator reports normalization conflict | Fail closed and preserve paths. Normalize only for comparison if the qualified implementation does so; detect collisions and require explicit owner resolution. Do not rewrite source filenames as an automatic repair. |

## Recommendations, optional improvements and owner decisions

### Recommended for the pilot

- Use one direct BagIt 1.0 directory package per registrar-approved exhibition deposit, retaining every accepted package unchanged. A corrected caption enters a later full snapshot with a new version ID and an explicit relationship to the earlier one.
- Add a UTF-8 `inventory.csv` snapshot with stable asset/version IDs, role, display title, payload path and version relationship. Keep a short plain text field guide where useful. The registrar signs off completeness; the custodian signs off copy/restore operations.
- Recommend SHA-512 for new BagIt manifests; record the algorithm in the bag manifest name, local policy and custody entry. Leave actual digest and future migration policy for owner confirmation.
- Qualify a specific validator release on representative copied paths before relying on it. BagIt defines format requirements; implementations have version-specific path safety, Unicode comparison and command behavior. Never describe public documentation review as a successful validator run.
- Keep the existing offsite copy and test only disposable/staged copies in the pilot.

### Supported optional improvement

Retain the human-readable exhibition inventory as authorized optional scope, with its usability, encoding, fields and reconciliation tested in the pilot. CSV is a proposed plain format, not an established capability until staff confirm that their ordinary tools open and use it. If a separate prose inventory would duplicate an authoritative catalogue, an owner-approved CSV crosswalk can supply the identifier/version/path view. Do not remove the option because BagIt or OCFL lacks a ready-made gallery screen.

### Owner inputs to resolve

1. Registrar: which existing catalogue/inventory is authoritative; required classes/counts of assets per exhibition; stable ID scheme; version/approval rules; who may approve “current”; how to record corrected captions, aliases and exhibition reuse.
2. Storage custodian: precise local/offsite paths/volume labels (no account needed), copy method, validator and pinned release, frequency/sampling of copy checks, how often to rehearse a full restore, temporary destination and incident retention procedure.
3. Joint: confirm one full snapshot bag per exhibition deposit versus per-asset packages; accept/reject duplicate storage for simpler standalone restores; choose SHA-512 as policy or another interoperable allowed choice; decide whether a custody log is signed/controlled and how its reference digest remains separate from the package copy.
4. Staff usability: confirm whether CSV plus field guide is readable and sufficient without specialist repository software, and whether existing filenames contain case/Unicode collisions requiring an explicit mapping policy.

## Already covered, rejected and uncertain

- **Already covered by the released plan and preserved:** pilot intent, ordinary local disk plus existing offsite copy, BagIt/OCFL as leads rather than winners, an authorized optional human inventory, named owner roles and binding negative constraints.
- **Rejected or corrected:** overwriting a caption in a supposedly immutable ZIP; using one whole-archive checksum as evidence that expected assets are all there; describing a future successful copy as proof of authorship/provenance/recovery; silently treating a path mismatch as a harmless rename; choosing a hosted platform or replacing offsite storage before testing.
- **Uncertain pending owner decision or pilot:** exact package depth, digest selection/upgrade policy, inventory authority and schema, naming/collision policy, tool/release to qualify, copy cadence, restore sample size and acceptable recovery procedure. No uncertainty blocks research-backed recommendation of a small BagIt pilot.
- **Evidence limit:** source issue reports and implementation history do not prove how the gallery's own storage/filesystems or a future selected tool behave. The proposed path/restore pilot is needed before any operational claim.
