# B-APPL-M-01 — Applicability and exception verification

**Scope.** Evaluated as stipulated: SQLite 3.51.3, WAL, ordinary shared-memory-capable VFS, multiple processes on one host and local disk. The proposed multi-host NFS move is a separate, unsupported configuration under WAL. The WAL page was last updated 2026-08-25; the C API and URI pages are live, unversioned references retrieved 2026-10-10. Citations below identify source sections; application to this case is an inference from the stated configuration. No workload, custom build settings, or local test results were supplied. Version exception: the WAL page reports a WAL-reset bug through 3.51.2, fixed in 3.51.3; its trigger involved separate connections with concurrent writes/checkpoints (WAL §11). The stated target is the fixed version, but the shipped binary was not inspected.

1. **False — concurrent writers.** **Source:** WAL allows readers and a writer to operate concurrently, but its single WAL file permits only one writer at a time (WAL §2.2). **Corrected wording:** “WAL permits concurrent readers and one writer; writers serialize.” This is the stated multi-process same-host setup; it does not establish simultaneous writer execution. [SQLite WAL §2.2](https://www.sqlite.org/wal.html)

2. **True, with a growth condition.** **Source:** Each read transaction holds an end mark; a checkpoint stops before overwriting pages needed by an active reader. A long transaction can stall checkpoint progress; if readers overlap continuously, checkpoints may never finish and the WAL can grow without bound (WAL §§2.2, 6). **Bound:** One reader can allow partial checkpoint progress; its eventual end lets a later checkpoint continue. Unbounded growth additionally requires writes to keep appending while completion/reset remains blocked. [SQLite WAL §§2.2, 6](https://www.sqlite.org/wal.html)

3. **False.** **Source:** WAL requires all database processes to be on the same host and does not work over a network filesystem because its shared-memory wal-index cannot be shared across hosts (WAL §§1, 2.2). **Applicability:** “SQLite is embedded” does not change this WAL constraint. The unchanged multi-host NFS design is outside the documented support boundary. [SQLite WAL §§1, 2.2](https://www.sqlite.org/wal.html)

4. **True, conditionally.** **Source:** Since SQLite 3.22.0, a read-only WAL database can be opened when both `-shm` and `-wal` exist and are readable, the containing directory permits creating them, or the connection uses `immutable` (WAL §5). SQLite 3.51.3 is newer. The WAL is part of persistent database state; separating it can lose committed transactions or corrupt the database (WAL §4). **Exception:** `immutable=1` skips locking and change detection, so use it only when the files truly cannot change; otherwise incorrect results or corruption are possible (URI filenames §3.3). A bare read-only `.db` snapshot is not shown to meet these conditions. [SQLite WAL §§4–5](https://www.sqlite.org/wal.html); [URI filenames §3.3](https://www.sqlite.org/uri.html)

5. **False.** **Source:** PASSIVE checkpoints as many frames as possible without waiting and may remain unfinished when readers or writers are active (`sqlite3_wal_checkpoint_v2`, PASSIVE mode). Even a normal completed checkpoint usually recycles/overwrites the WAL instead of truncating it (WAL §6). **Corrected wording:** A successful PASSIVE return does not guarantee a zero-byte WAL; only a successful TRUNCATE checkpoint promises truncation to zero bytes. Check the return and `pnLog`/`pnCkpt` outputs when assessing progress. [Checkpoint C interface, PASSIVE/TRUNCATE and outputs](https://www.sqlite.org/c3ref/wal_checkpoint_v2.html); [SQLite WAL §6](https://www.sqlite.org/wal.html)

6. **Unsupported by supplied evidence.** **Source:** SQLite describes WAL as faster in most scenarios, but notes read-mostly workloads can be slightly slower and that WAL size/checkpoint strategy affect performance (WAL §§1, 2.3). **Inference:** These general statements cannot establish a ≥40% reduction in this catalog’s p95 lookup latency. Missing evidence is a representative before/after benchmark on the target binary, data, host, VFS, durability settings, and reader/writer mix, with repeated p95 measurements. [SQLite WAL §§1, 2.3](https://www.sqlite.org/wal.html)

## Acceptance checks

1. **Proposed; not executed.** On the exact deployed SQLite 3.51.3 binary and VFS, confirm the runtime version and that WAL activation returns `wal` on the local same-host path; exercise two processes, one writer at a time, and a pinned long reader while recording checkpoint return code, `pnLog`, `pnCkpt`, and WAL size. Confirm progress/reset after releasing the reader. Test the shipped read-only snapshot with its actual sidecars or genuinely immutable setting. Reject a multi-host NFS WAL configuration and any snapshot that lacks a documented opening condition.
2. **Proposed; not executed.** Compare rollback-mode baseline and WAL using the same representative catalog queries/data, hardware, sync/durability settings, concurrency, and cache conditions over repeated runs. Pass the ≥40% p95 claim only if the predeclared WAL p95 is at most 60% of baseline p95; otherwise reject that performance claim. No measurement has been performed here.
