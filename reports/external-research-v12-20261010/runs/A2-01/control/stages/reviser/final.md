## Recommendation

Evaluate **ODK Collect with ODK Central first** for the 25-volunteer Android pilot. Collect documents device-side Draft, Ready to send, and Sent states and supports offline work. Central records submissions, versions and server receipt time; its CSV ZIP export carries root and repeat tables plus files grouped by submission identity. ODK Cloud is the managed hosting option; self-hosted Central needs an accountable operator and backup/restore duties. The form and permissions still need to be set up for the charity. This is a fit hypothesis based on documentation, not a tested selection. [S01](https://docs.getodk.org/collect-forms/), [S03](https://docs.getodk.org/central-forms/), [S04](https://docs.getodk.org/central-submissions/), [R02](https://docs.getodk.org/central-submissions/)

Keep **ArcGIS Survey123** as the second full product candidate if the charity already has ArcGIS Online or Enterprise, a feature-layer owner, and GIS support. Its Android field app has an offline Outbox. Layer sync and sent-record editing depend on publishing and permissions; sync and sent editing are off by default. CSV/Excel and GIS exports are available in the Survey123 website for eligible surveys, but the website cannot download surveys built from ArcGIS Server feature layers. Decide the export route only after confirming whether the charity uses hosted or ArcGIS Server layers. [S09](https://doc.arcgis.com/en/survey123/capture/field-app/submitsurveyresults.htm), [S10](https://doc.arcgis.com/en/survey123/create/connect/publishsurvey.htm), [S12](https://doc.arcgis.com/en/survey123/analyze/viewresults.htm), [R04](https://doc.arcgis.com/en/survey123/analyze/viewresults.htm)

Retain **KoboToolbox/KoboCollect** as a screened Android alternative because the released plan names it and its current docs cover offline collection and later bulk upload. Its post-submit correction workflow needs an external edit log and version checks, so it is not preferred without a demonstration that preserves the required history. [S15](https://support.kobotoolbox.org/data_collection_kobocollect.html), [S16](https://support.kobotoolbox.org/editing_deleting_data.html), [R07](https://support.kobotoolbox.org/data_collection_kobocollect.html), [R08](https://support.kobotoolbox.org/editing_deleting_data.html)

Use **CouchDB 3.5.1 replication** only as an analogy for checkpoints, stable document IDs, and retained revision branches. Its deterministic winning revision is not the data steward’s choice and must not determine this charity’s current view. It is not recommended as new infrastructure for this pilot. [S13](https://docs.couchdb.org/en/3.5.1/replication/intro.html), [S14](https://docs.couchdb.org/en/3.5.1/replication/conflicts.html)

## Coordinator-visible lifecycle

| State | Where it exists and what the coordinator may claim |
|---|---|
| **Draft — device only** | The volunteer is still entering a visit. The record is local; there is no server record or coordinator signal. |
| **Queued/offline — device only** | The form is finalized and waits in the app’s local queue. The coordinator cannot see the pending queue while the phone is disconnected. Show the queue state on the device. |
| **Sending / receipt unknown — device only until reconnection** | A send was attempted but the response is uncertain. Keep the same observation ID, form version, payload and attachment identities/bytes. Do not create a replacement record. The uncertain state is not visible to the server until a later client event arrives. |
| **Received** | After server acceptance, show server receipt time and submission identity. ODK Central defines createdAt as server receipt time. A 409 for an already-existing instanceId is a reconciliation signal: query and compare the existing record; do not mint a new observation merely because the response was lost. [R03](https://docs.getodk.org/central-api-submission-management/) |
| **Received after offline queue / apparent late arrival** | Use “after offline queue” only if a client-side queue/attempt event or delivery manifest is retained and later sent. That event is a proposed product capability to validate. Otherwise show the volunteer-reported observation time beside server receipt time and label any difference an apparent delay; do not infer connectivity or exact lateness from a phone clock. |
| **Duplicate candidate — retained for investigation** | Exact same ID with matching payload is retry reconciliation. Similar content with different IDs may be flagged using site, reported time, answers, and attachment digests. Preserve both. The field coordinator investigates and records the outcome. No candidate is merged or discarded automatically. |
| **Correction received — linked** | A correction carries its own correction/event ID and points to the original observation. Record reason, actor, reported correction time, server receipt time, changed values and any new attachment IDs. The original remains available. |
| **Current view or side-by-side view** | A display projection follows the data steward’s choice. The owner has not supplied the choice of which view to use, so it remains an explicit input. The event history remains available under either view. |

Do not promise a coordinator-visible live pending state without a reachable device. If the pilot requires queued/uncertain states in a shared coordinator screen, specify and test a client-side event/manifest that survives offline operation and is uploaded after reconnection; documentation review has not established that Collect or Survey123 sends this exact event. If no such mechanism is implemented, the coordinator view starts at server receipt.

## Proposed identity, time, photo and duplicate model

For each field visit, maintain separate identifiers and time values:

- **site_code:** a value from a coordinator-owned site list.
- **visit_id:** an immutable ID for one visit; the same site can have repeated visits.
- **observation_id:** one submitted observation/event ID. In an ODK form this may be the unique OpenRosa instanceID. Transport retries reuse it unchanged.
- **form_id and form_version:** preserve the form definition that gave the answers their meaning. Do not reinterpret old offline records using the newest form.
- **observed_time_reported:** the volunteer’s time for the ecological observation, with entered precision and time-zone/offset when known; allow estimated/unknown. Do not infer precision.
- **client timestamps:** preserve separately and mark unverified. OpenRosa timeStart/timeEnd are client metadata, not proof of accurate device time. [S02](https://docs.getodk.org/openrosa-metadata/)
- **server_received_at:** immutable server UTC receive time. It orders server intake, not the visit. [R03](https://docs.getodk.org/central-api-submission-management/)
- **correction_event_id and corrects_observation_id:** separate identity and explicit link for every correction; retain reason, actor, reported time, receipt time and changed fields.
- **attachment_id:** stable ID for each of at most three photos; link to observation or correction, form question/role, original filename, MIME type, size and preferably a digest. Retries reuse the same attachment IDs and bytes; a replacement photo gets a new ID.

Do not use a device timestamp, site plus approximate time, or filename as a primary key. A same-ID collision is resolved by checking server state and payload, not by creating a new observation. Different IDs with similar site/time/answers/photos become candidates only. Preserve all candidate records and coordinator investigation outcomes.

Do not request GPS, add geopoints from photo metadata, extract or display photo EXIF location, or use any photo-derived location. Preserve originals and do not issue remote deletion. If a privacy-safe derivative is needed for an export, generate it separately and verify that it does not expose photo location; keep the original untouched.

## Optional coordinator-reviewed legacy CSV import

Keep legacy CSV import authorized and optional. Neither the original brief nor the research establishes that the charity needs it during the pilot, and no owner has made it mandatory.

Two technical paths are worth evaluating without claiming either is already safe:

1. **ODK adapter candidate:** a staff-only importer could map approved CSV rows into version-specific ODK submission XML using the documented REST create endpoint, then upload expected attachments through the separate attachment endpoints. Preserve a source-system/legacy-row key and import-batch ID; preview field mappings and errors before any submission; generate stable, non-colliding observation IDs; reconcile an existing ID and payload before retry; never update/overwrite an existing field observation. The API docs support these building blocks, not a native CSV importer or an executed adapter. [R03](https://docs.getodk.org/central-api-submission-management/)
2. **ArcGIS feature-service candidate:** a CSV can be appended to a compatible ArcGIS Online/Enterprise feature service when the target advertises CSV in supportedAppendFormats and the capability/privilege is available. Confirm the deployment/service version, field mapping, coordinate/time handling, stable row IDs and attachment associations. Stage the import and block duplicate keys before append; do not use upsert in a way that silently updates existing observations. This is feature-service data loading, not proof of a Survey123-native legacy response importer. Do not use imageCollection append: the documented image path derives point geometry from EXIF location, contrary to the brief. [R06](https://developers.arcgis.com/rest/services-reference/enterprise/append-feature-service-layer/)
3. **Kobo:** the reviewed collection and correction sources do not explain an existing-submission CSV import route. That is unresolved evidence, not a finding that no route exists. Ask for a documented path only if Kobo becomes a serious candidate. [R07](https://support.kobotoolbox.org/data_collection_kobocollect.html), [R08](https://support.kobotoolbox.org/editing_deleting_data.html)

Before adopting any path, require a coordinator preview; frozen schema and form-version mapping; file SHA-256 and import_batch_id; stable source-row identity; row-level validation/reject reasons; explicit attachment mapping and digests; duplicate flags; rerun idempotency; read-back/reconciliation; and a no-overwrite rule. If the small pilot cannot demonstrate those controls, defer import for that batch with the precise blocker and retain the authorized option for later.

## Bounded reconnect history and applicability

ODK Collect issue #4589 (opened 2021-06-02) reports an ambiguous receipt: Central may accept a submission while the client loses the POST response. If the user then edits the local item marked failed—for example changing an end time—the XML changes, and resubmission under the same ID is rejected because the server already has that ID. The linked commit 0bc6cde filtered STATUS_SUBMISSION_FAILED out of the ordinary unsent/editable list and added a resubmission test. PR #4655 is listed in the official Collect v2021.2.0 release, dated 2021-07-27. [S06](https://github.com/getodk/collect/issues/4589), [S07](https://github.com/getodk/collect/commit/0bc6cde), [S08](https://github.com/getodk/collect/releases/tag/v2021.2.0)

This bounded history supports keeping an uncertain transport retry immutable and reconciling by stable ID. It does not establish that current Collect has the old failure, that retries across all products are exactly once, that separate IDs cannot be duplicates, or that a correction policy is automatic. The newer opt-in client_editable behavior is a distinct versioned edit path, introduced for Collect v2025.2.0/Central v2025.1.4; it does not make a failed, unacknowledged retry safe to mutate. [S01](https://docs.getodk.org/collect-forms/)
