## Recommendation

Evaluate **ODK Collect with ODK Central** as the first pilot route. It matches Android collection with intermittent connectivity, has a visible local queue, and currently documents server-side review states, versioned edits, form version identity, and exports that can package data tables with attached media. The managed ODK Cloud route can avoid assigning server maintenance to a volunteer coordinator; self-hosted Central remains an option only if the charity already has an operator. Form access still needs to be provisioned. Use a coordinator-facing workflow with an append-only correction record and explicit duplicate-candidate state; the vendor’s status labels alone do not settle the charity’s correction policy.

Keep **ArcGIS Survey123** as the second full product candidate, especially if the charity already operates ArcGIS Online/Enterprise and has a GIS coordinator. It supports an offline Outbox, but the server-side feature-layer sync option is off by default, and edit behavior depends on permissions and publishing configuration. Its export is attractive for GIS workflows; ODK’s ZIP structure is more direct for a small table-plus-photo pilot. Do not procure either route from documentation alone.

**KoboToolbox/KoboCollect** is also a real candidate from the plan shortlist, not an assumed winner. The current public docs show offline Android collection and bulk upload, but post-submit edits happen in KoboToolbox, change `_uuid`, use the latest form version in web-form edits, and can recalculate/remove values; direct raw edits cannot be undone and need an external edit log. Include Kobo in a short comparative demonstration if there is a reason to shortlist it, but do not place it in the primary two-product comparison until coordinators demonstrate preservation of correction history and versioned exports. [S15](https://support.kobotoolbox.org/data_collection_kobocollect.html), [S16](https://support.kobotoolbox.org/editing_deleting_data.html)

Use **CouchDB 3.5.1 replication** only as an analogy for restartable transport, stable document IDs, revision branches, and explicit conflict resolution. A winning revision is a database rule, not the data steward’s choice. CouchDB is not a ready survey product and is not recommended as extra infrastructure for this 25-volunteer pilot. [S13](https://docs.couchdb.org/en/3.5.1/replication/intro.html), [S14](https://docs.couchdb.org/en/3.5.1/replication/conflicts.html)

## Covered, rejected, and unresolved points

**Already covered by the complete brief (owner-supplied scope, not new research):** the 25-volunteer/intermittent-network/Android pilot; site code, observation time, structured answers and up to three photographs; offline operation; no overwriting originals; the authorized but optional coordinator-reviewed legacy CSV route; the field coordinator’s authority to accept duplicates for investigation; the steward’s authority to choose current-view versus side-by-side correction display; and all four negative constraints. **Rejected draft assumptions:** a send retry does not justify a second event ID or guarantee an automatic same-record success; device timestamps and filenames are not visit/photo identities; weekly manual deduplication is not enough to keep duplicates distinct; an unspecified “recent fix” is not evidence; documentation/release reading is not product validation; and an export-only finding does not justify excluding CSV import. Clause 1–5 rows below state the replacement behavior and evidence.

**Supported external behavior:** Collect’s local queue, ODK form/submission identifiers and versions, Central’s server-receipt timestamp and CSV/media structure, Survey123’s Outbox/publishing/export conditions, Kobo’s offline and correction behavior, and CouchDB’s checkpoints/conflict branches are linked by source ID. These claims apply only under the versions and conditions recorded for their sources; no deployed version has been observed.

**Optional improvements (not new mandatory scope):** add attachment digests and a human-readable import manifest; evaluate ODK’s opt-in client edits against a separate correction form; retain a correction reason and actor; and test an export derivative that suppresses photo GPS metadata without altering the original. The CSV-import route itself remains an authorized option, conditional on safe mapping and rerun behavior.

**Uncertain or NOT_RUN:** the charity’s current product/subscription/accounts; exact live app/server versions and role configuration; current Survey123 offline service-sync behavior for its own planned layers; correction-version visibility in actual exports; real retry behavior for a response loss during photo transfer; the device’s clock accuracy; privacy settings for exported EXIF; and existence of a safe native CSV importer. The public-document review cannot answer those operation questions.

## Proposed workflow and coordinator-visible states

| State | Meaning and transition | Coordinator view |
|---|---|---|
| **Draft (device)** | Volunteer is still entering a visit; editable locally. | No server record yet; show device-local state only. |
| **Queued / offline** | Form finalized while offline or queued after a send request. | Show visit/observation ID, last attempt and queued attachments; volunteer need not reconnect to finish the visit. |
| **Sending / receipt unknown** | A request is in flight or the connection drops before acknowledgment. | Do not create a replacement record. Retry the same ID, same observation event, same form version, exact same XML/data and attachment IDs/bytes. Query/reconcile by identity when possible. A conflict/duplicate-key reply means “check whether accepted,” not “make a new ID.” ODK Central documents 409 for an already-existing `instanceId`. [S05](https://docs.getodk.org/central-api-submission-management/) |
| **Received** | Server has acknowledged and records a server receive timestamp. | Show both `observed_time_reported` and `server_received_at`; preserve form version and attachment links. ODK calls `createdAt` the server-receipt time. [S05](https://docs.getodk.org/central-api-submission-management/) |
| **Received after offline queue / apparent late arrival** | Server receives an offline queued submission after later visits or long after the entered observation time. | Mark that the client queue was offline and arrived later; display the reported event time beside server receipt time. Do not automatically call it a chronologically later visit: phone time may be inaccurate and no “late after N hours” threshold was supplied. |
| **Duplicate candidate — retained** | Two distinct observation IDs resemble the same visit, or a repeated import key conflicts. Exact same ID is handled as retry/reconciliation; differing IDs can be compared for investigation. | Preserve both payloads and photos. Field coordinator accepts and investigates candidates. Similarity is a flag only; never merge or discard automatically. |
| **Correction received — linked** | Volunteer/coordinator records an explicit correction after a prior observation. | Store a new correction/event ID, link to original observation, capture reason/author/time, retain before/after data and any replacement photo as a new attachment. The original remains available. |
| **Current view / side-by-side view** | Steward-selected projection over the preserved observation and correction history. | Remains undecided until the data steward chooses whether the correction replaces the current view or appears beside it. No transport or similarity rule decides. |

ODK’s v2025.2 opt-in versioned edits are a candidate interaction, but they are not automatically equivalent to the proposed append-only correction event. A separate correction form is a simpler way to guarantee a distinct ID and explicit `corrects_observation_id`; compare both approaches in a nonproduction pilot. ODK metadata also documents a `deprecatedID` for a revision and Central submission versions, but server consolidation and display behavior need to be verified before relying on them for the steward’s chosen view. [S01](https://docs.getodk.org/collect-forms/), [S02](https://docs.getodk.org/openrosa-metadata/), [S04](https://docs.getodk.org/central-submissions/), [S05](https://docs.getodk.org/central-api-submission-management/)

## Identity, timestamps, photographs, duplicates

Use this proposed record identity bundle:

- `site_code`: selected from the charity’s site list or entered under coordinator validation.
- `visit_id`: generated unique value for this field visit, distinct even for repeat visits to one site.
- `observation_id`: unique submission/event ID (`instanceID` in an ODK-compatible form). Preserve unchanged through all transport retries.
- `form_id` + `form_version`: frozen with the event so its question meaning is recoverable. ODK form metadata carries identity/version and Central retains prior form versions and submission version information. [S02](https://docs.getodk.org/openrosa-metadata/), [S03](https://docs.getodk.org/central-forms/), [S05](https://docs.getodk.org/central-api-submission-management/)
- `observed_time_reported`: date/time the volunteer enters for the actual observation, with stated precision and zone/offset where known; include “estimated/unknown” rather than inventing precision.
- `client_time_metadata`: preserve separately and label unverified. OpenRosa `timeStart`/`timeEnd` are client timestamps; do not treat them as an authoritative observation time.
- `server_received_at`: immutable server-side UTC receipt timestamp. This orders receipt, not the ecological event. [S02](https://docs.getodk.org/openrosa-metadata/), [S05](https://docs.getodk.org/central-api-submission-management/)
- `attachment_id`: unique for each photo; link to event ID and photo question/role. Retain original filename, MIME type, byte count and a digest to detect identical bytes. Retry reuses the attachment identity and exact bytes; a corrected/replacement image gets a new ID and a link to the prior attachment.

Do not make `device timestamp`, `site + approximate time`, or filename a primary key. Within an exact same event ID, a second identical transport delivery is retry reconciliation. With different IDs, matching site/time/answers/file digest may form a duplicate candidate, but the field coordinator investigates it. Preserve raw attachments and do not remotely delete originals. The form requests no GPS; never parse or infer location from photo EXIF. If later exports expose GPS metadata, test a separately generated privacy-safe export derivative while leaving the volunteer’s original untouched; do not map or report the photo-derived coordinates.

## Optional coordinator-reviewed legacy CSV import

Retain the authorized option and make no claim that one of these products natively imports legacy CSV into its submission store. In the reviewed ODK API, a submission is XML and REST creation does not include its attachments; CSV export is documented. This is a limitation in evidence for a built-in path, not evidence that a separate controlled adapter is impossible. [S04](https://docs.getodk.org/central-submissions/), [S05](https://docs.getodk.org/central-api-submission-management/)

If technically supported, keep import staff-only and coordinator-reviewed. Before commit, show the mapped site, visit/event ID, form version, observation time plus its source/precision, answers, attachment references, and any duplicate candidates. Reject unknown columns or invalid rows with row-level reasons; never silently drop a row. Require a frozen import schema and mapping, input-file SHA-256, `import_batch_id`, source system and legacy row ID, attachment map/digests, and rerun-idempotency keyed by source + legacy ID. A legacy record without a stable key must receive an assigned ID in a reviewed manifest before retryable import. Existing observations are never overwritten by a CSV row. If attachments cannot be mapped, do not import them as completed observations; keep the option open and defer only that batch with a precise blocker.

## Bounded reconnect/release history and applicability

The actual example is ODK Collect issue [#4589](https://github.com/getodk/collect/issues/4589), opened 2021-06-02. The issue explains that Central can receive a submission while the client does not get the POST result; if a field collector then edits the local item recorded as failed (for example changing an end time), resubmitting under the same ID with different XML is rejected. Maintainer discussion on that issue describes this as a limbo state after uncertain network acknowledgment and scopes the fix to keeping a `STATUS_SUBMISSION_FAILED` form out of the ordinary edit list.

The source change [commit `0bc6cde`](https://github.com/getodk/collect/commit/0bc6cde) changes the unsent-instance query to exclude failed submissions and adds a resubmission test. The issue was closed by PR #4655; the official [Collect v2021.2.0 release](https://github.com/getodk/collect/releases/tag/v2021.2.0), dated 2021-07-27, lists that PR. Applicability: do not mutate a failed transport attempt under its original ID; after uncertain receipt reconcile by stable ID and preserve payload. The released change does not ensure exactly-once behavior across all clients, stop separately generated duplicates, preserve correction policy, or prove which version the charity would run. Current documented ODK edits of finalized/sent items are opt-in and separately version-tracked beginning Collect v2025.2.0 / Central v2025.1.4; this later feature is not permission to edit an unacknowledged failed retry. [S01](https://docs.getodk.org/collect-forms/), [S06](https://github.com/getodk/collect/issues/4589), [S07](https://github.com/getodk/collect/commit/0bc6cde), [S08](https://github.com/getodk/collect/releases/tag/v2021.2.0)
