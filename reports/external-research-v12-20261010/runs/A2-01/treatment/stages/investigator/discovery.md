# Independent discovery — reconnect-safe volunteer observation intake

**Run/stage:** A2-01-treatment / investigator  
**Discovery input:** the complete supplied brief only. I did not seek or read the unreleased plan. The plan-release helper has not yet been run.  
**Research window observed:** public read-only source review on 2026-10-10 UTC. Source identities, locators, versions, conditions, and applicability are recorded in source-map.json and sources/index.md.

## Initial recommendation

Run a small pilot on either **ODK Collect + Central** or **KoboCollect + KoboToolbox**, with ODK the stronger first candidate if keeping a clear received/edited/review-state history and media-complete exports are decisive; Kobo is a credible alternative if its hosted community plan, form workflow, and data-team familiarity fit better. Both provide Android offline collection after form download and support queued/late upload. Neither product alone should be assumed to implement the charity's exact correction policy. Preserve each submitted payload, introduce an explicit correction proposal linked to it, and expose the data steward's choice of current-view replacement versus side-by-side display as a recorded decision. Make network receipt, field observation, server receipt, duplicate review, and correction separate facts.

This is a research recommendation, not an implementation or product validation. No products were installed, configured, or exercised.

## Proposed record and lifecycle

Assign a random stable observation_id (UUID) when a visit record is first created offline; generate it once and keep it unchanged through save, reconnect, and retry. Record a separate visit_id if one route visit can yield multiple observations. The record carries the selected site_code, form_id, declared form_version plus a pinned schema fingerprint, answers, photo references, actor/device identifiers only to the extent authorized, and explicit timestamps. Do not use site+time+answers as a unique key: they are useful to suggest likely duplicates, not to collapse records.

Each of up to three photos should have its own stable attachment_id, parent observation_id, ordinal, original filename, media type, byte length, and content digest; bind the server-side blob key when received. Keep upload/attachment status separate from form submission status so an XML/data receipt with a missing photograph remains visible and recoverable. If the selected form platform lacks a first-class attachment identifier, a client-generated photo UUID plus digest and original submitted filename is the proposed adapter identity, not a claimed platform field.

The coordinator-facing progression is:

1. **Draft on device**: still editable; never represented as accepted server data.
2. **Finalized / queued**: immutable retry payload with stable ID and pending attachment count. Connectivity is not required to reach this state.
3. **Received, awaiting review**: server receipt timestamp and submitter known; required-media completeness shown; no content merge has occurred.
4. **Duplicate under investigation**: a person flagged a possible match. Keep it as a distinct observation. The field coordinator explicitly accepts duplicates for investigation; there is no automatic dedupe.
5. **Reviewed**: approved / needs follow-up / rejected are human review outcomes, not a side effect of delivery. Preserve who and why.
6. **Correction proposed**: new correction event with its own ID, parent observation ID, actor, timestamp, reason, changed fields, and any replacement/added attachments. It does not overwrite or erase the original payload.
7. **Correction decided**: the data steward records whether the projection treats the correction as the current view or displays both. Until that choice is made, show both and mark the correction pending. No silent merge is authorized.

A retry repeats the same finalized observation ID and exact logical content; it must not silently mint another observation or mutate submitted content. A correction receives a new correction/event ID. That split addresses both duplicate investigation and the historical same-ID/different-payload failure described below.

## Identity, time, and photo constraints

Store the controlled site code as an explicit form answer; if routes repeat a site visit, also store a visit ID and observation ID. Keep form ID and version on every observation even after a later form update. ODK/OpenRosa requires a unique instance ID, allows optional start/end, user, and device metadata, and has a deprecatedID convention for revisions; Central exposes per-version submission metadata. Kobo exposes __version__, server _id, _uuid, server _submission_time, submitter, and a stable rootUuid; its _uuid can change on edit (S04–S07, S10–S11, S19). Treat those product fields as useful platform provenance, not as replacements for a charity-owned stable observation ID and correction lineage.

The observed event time is not the sync/receipt time. ODK documents that start, end, and today depend on device time and can be wrong (S07). Store the volunteer-entered/observed time with the entered zone/offset when known, a time-quality value (known, estimated, unknown), and the server receipt time in UTC. Do not alter personal phone time settings or imply that client timestamps are server-verified. Use receipt time only to establish when the server learned of a record, not to overwrite the field observation time.

Use site code and a direct observation-time answer; do not derive precise location from photograph contents or EXIF. Do not require location permission or online presence. Do not remote-delete the volunteer's originals. Kobo's documented default keeps forms/data on-device unless a project enables delete-after-send; keep that setting off for this pilot (S09). For ODK, explicitly test/confirm the selected release's local retention settings and do not configure an automatic local purge.

## Reconnect and correction history example

ODK Collect issue #4589 (opened 2021-06-02, closed 2021-07-07 through linked #4655) documents repeated server errors when an existing submission ID was retried with changed XML while attaching media; the server required an identical XML submission file on media resubmission. The linked change made failed-to-send finalized submissions no longer editable. A user on Collect v2021.2.4 / Android 10 later reported that this prevented correcting server-rejected forms in a poor-signal field workflow, potentially losing a chance to replace photos/geopoints/barcodes in the failed submission; an ODK maintainer confirmed that the behavior change was intentional (S17–S18).

Applicability is narrow and historical: this is evidence that retries and edits under one ID can collide, and that making failed payloads immutable has a real field-work cost. It is not proof of a current 2026 regression or of how the chosen modern build handles a response lost after server receipt. The proposed design keeps finalized retry payloads stable but routes data corrections through a separately identified, linked event; the pilot must exercise interrupted uploads, server rejection, and missing-photo recovery.

## CSV legacy-import option

Retain the authorized optional scope as a coordinator-reviewed batch, not as an assumed feature. Kobo documentation distinguishes external CSV used as a lookup/preload dataset from actual respondent submissions (S14). Its separate manual recovery route is experimental and takes a ZIP of actual KoboCollect instance folders or offline web-form exports tied to an existing form—not arbitrary legacy CSV rows; the article's introductory warning says it does not prevent duplicate submissions, while its closing sentence says duplicate records are rejected. Treat that internal inconsistency as a reason to test and never rely on it as an idempotency guarantee (S13). ODK's submission/export docs establish download formats, not a built-in CSV-to-submission importer.

Recommended conditions if the owner chooses the option: accept only a declared CSV template; stage original file with SHA-256, filename, importer/version and batch ID; retain original row number and source record key; show a preview with deterministic column-to-field mapping; require a coordinator to approve; validate site, observation time/time-zone interpretation, answer codes, form-version mapping, and media references; display row-level accepted/rejected reasons; and create new IDs without pretending an ambiguous legacy key is unique. Preserve raw source values and mark unknown times/IDs as unknown. Do not infer photo location. If a CSV's site mapping, timestamps, source uniqueness, or photo-to-row mapping cannot be established, leave those rows in a reviewable quarantine/archive and do not silently create canonical observations. CSV import can be deferred or excluded if those criteria cannot be met; its exclusion would be a bounded capability/data-quality decision, not a change to the authorized scope.

## Owner inputs and useful discoveries

- Field coordinator: accept possible duplicates for investigation; define what evidence starts/ends an investigation, who can label it, and what is shown to volunteers.
- Data steward: choose whether an approved correction changes the default/current projection or is always shown alongside the original. Until answered, no current-view replacement should occur.
- Owner/team: choose product/hosting based on existing skills, location/data policy, available support budget and who owns backups; choose whether to pilot the optional legacy CSV batch; define retention/privacy for photos and any user/device identity.
- Useful built-in opportunities: ODK Central's system and user review states, activity/comments, and attachment-completeness warning; Kobo's stable rootUuid for tracking edited records; Kobo's manual recovery upload for actual app bundles (with its experimental/duplicate ambiguity); and CouchDB's explicit conflict leaves for an alternate sync design. None is a substitute for explicit product decisions.
- Preserve negative constraints: volunteers may finish and save while offline; no inference of precise place from photographs; no phone-setting change; no remote deletion of volunteers' originals; no automatic merge.
