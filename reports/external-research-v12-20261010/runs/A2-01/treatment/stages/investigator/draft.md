## Recommendation

Pilot one of two usable Android survey stacks: **ODK Collect + Central** as the leading fit if the team values explicit submission review states, per-submission activity, form-version metadata, and a ZIP export that includes media; keep **KoboCollect + KoboToolbox** as a credible hosted alternative if the team prefers Kobo's public Community Plan and its data team knows that workflow. The evidence does not establish the charity's budget, data residency, support capacity, or current staff familiarity, so the choice remains an owner decision. Pin exact app/server releases and validate before rollout. Current source pages identify ODK Collect v2026.3.5 (commit 87bf04e; released 2026-09-28) and Central v2026.3.1 (commit 7d6de62; released 2026-09-28); those release tags are not a claim that the living docs were tested against those builds (S01–S02).

Whichever product is selected, treat a visit observation as an immutable logical record with an append-only correction history. A retry resends the same finalized content under the same stable client ID. A correction is a distinct, linked event with a new event ID, actor, time, reason, changed values, and attachment references. Preserve the field coordinator's right to investigate records as duplicates and the data steward's explicit choice of how an approved correction appears. Neither latest-arrival ordering nor a deterministic conflict winner is a business decision.

## Proposed data and coordinator workflow

Give each observation a UUID when first created offline; keep it through draft saves and every transport retry. If one route visit may contain multiple independent observations, store a separate visit_id and a child observation_id for each. Store a controlled site_code, form_id, declared form_version and schema fingerprint, structured answers, submitter reference if available/authorized, and separate event times. Use a unique attachment_id for each photo, with parent observation_id, ordinal 1–3, original filename, media type, size, digest and server blob reference when received. Filenames are display metadata, not identity. A content digest can help detect a repeated file, but it must not merge distinct observations.

Display distinct states:

1. **Draft on phone** — editable and not yet a server record.
2. **Finalized / queued** — stable retry identity, immutable logical payload, and a visible count/status for each expected photo. No network connection is needed to create or keep this state.
3. **Received, awaiting review** — server receipt timestamp and submitter/provenance are visible; attachment completeness is shown separately. Do not call a data receipt complete if a required photo is missing.
4. **Possible duplicate / investigation accepted** — human flagged a likely match and the field coordinator accepted the investigation. Both records stay distinct; no auto-deduplication or merge.
5. **Reviewed** — an authorized coordinator records a review outcome, note, actor and time. Suggested states are received, needs follow-up, approved and rejected. Product labels alone do not guarantee export filtering or business rules.
6. **Correction proposed** — a new correction ID points to the original observation; proposed edits and added/replacement photos are explicit and reviewable. The old payload remains available.
7. **Correction decided** — the data steward records whether the approved correction replaces the default/current projection or appears beside the original. Before this choice, show both and mark the decision pending.

ODK Central supplies incoming Received and Edited, staff-set Has Issues/Approved/Rejected states, activity/comments, attachment warnings, and new versions for web edits. Its docs say states do not trigger actions on their own and rejected submissions remain in exports unless filtered (S04). Kobo provides a validation status and edit mechanisms, but web-form edits use the latest form logic and may recalculate/delete values; raw edits bypass form logic, cannot be undone, and should be tracked separately (S10–S11). Neither fact removes the need to make the charity's state semantics explicit.

### Conditions and local recommendation

A single online form is not acceptable: both product docs require an initial form download, then permit offline collection, with later upload or queueing (S03, S09). The volunteer can enter the observation and keep photos on-device until connectivity returns. Keep Kobo Delete after send disabled; explicitly verify ODK local-retention settings for the pinned build. Never remotely delete volunteers' original files or rely on the survey platform to manage their personal photo library.

For a bounded pilot, ODK appears the stronger coordinator-side fit because Central has named review states, activity, versioned edits, missing-media warnings and a media-inclusive export. This is a recommendation by source comparison, not proof those functions implement the owner's exact correction/duplicate policy. Kobo is a viable alternative with offline collection, server receipt/version fields and practical hosted deployment, but its raw-edit path is not undoable and web edits can change older answers after form redeployment. Pick based on team skills, server budget, data-location policy, collaboration account setup, and ownership of backups.

## Site, visit, form, attachment, time, and duplicate handling

Do not use device time as visit identity or image filename as photo identity. Use a stable generated observation UUID and, if the charity's workflow needs a visit grouping, a distinct visit UUID. Site is an explicit controlled site_code; form_id, declared form_version and schema fingerprint remain attached to the observation. Each photo has an attachment UUID and parent observation link. ODK's OpenRosa metadata requires a unique instanceID; deprecatedID may link a revision, while start/end and user/device fields are optional (S06). Kobo exposes __version__, server _id, mutable _uuid, server _submission_time and stable rootUuid (S10). Keep a charity-owned stable logical ID in addition to platform IDs.

ODK explicitly warns that start, end and today rely on device time and may be wrong (S07). Preserve volunteer-reported observation time as entered, including zone/offset if known; mark estimated or unknown times as such. Keep device-generated form start/end in separate fields and treat them as uncertain evidence. Record server received_at in UTC as sync/arrival time. Do not change phone time settings and do not convert server receipt into the observation time.

A candidate duplicate fingerprint may use site, a time window and normalized answers to sort the coordinator's review queue. It must only suggest; the brief says the field coordinator accepts duplicates for investigation, so do not reject, merge, overwrite or delete based on that fingerprint. Distinguish same observation retry (same client ID and payload) from a new same-site visit (new ID) and from a correction (new linked correction ID).

Do not infer precise location from a photo, EXIF, timestamp or filename. Do not require GPS/online access. Ask the steward to decide photo retention and whether EXIF should be preserved for other stated purposes; no automatic location extraction is proposed.

S21 adds a source-code/test finding to the storage discussion: an ODK Central public issue contains backend test code in which a revision is submitted with a new instanceID and deprecatedID; attachments are carried to the new submission definition, and an older revision's reference can keep a blob from purge after a current-version attachment is cleared. This is code/test evidence read in the issue, not a test run or a guarantee about the selected build. It means attachment version retention and storage should be checked with the pinned Central release. It does not change the negative constraint against remotely deleting volunteer originals (S21).

## Bounded failure and release history

ODK Collect #4589 was opened 2021-06-02 over repeated errors when a server already had a submission ID but a retry with changed XML tried to attach additional media. The server expected identical XML for the same ID. The issue was closed completed 2021-07-07 through linked #4655. In a public forum report, a user on Collect v2021.2.4 / Android 10 observed the resulting intentional behavior: failed finalized submissions stayed non-editable, preventing field correction after server rejection in a poor-signal workflow; a maintainer confirmed the behavior change (S17–S18).

Applicability is deliberately bounded. This illustrates why retry payload and ID must remain stable and why a correction needs a separate route, while also exposing the field cost of making a failed form immutable. It does not establish a current 2026 bug or current retry response behavior. Exercise lost acknowledgements, partial data/media receipt, rejection, resend and a new correction on the chosen releases. ODK release pages identify the current tags; no present-day release note was found that claims a general fix for every reconnect/correction case (S01–S02).

## Optional coordinator-reviewed CSV import

Retain CSV import as authorized optional scope; do not elevate it to mandatory delivery and do not represent it as a built-in capability. Kobo's CSV documentation describes a form-time lookup/preload dataset, not old observation rows as submissions (S14). Its documented manual recovery feature is an experimental ZIP of actual KoboCollect instance folders or offline web-form exports tied to a form already on the server. The same page's opening warning says duplicates are not prevented while its closing text says duplicate records are rejected; treat duplicate behavior as unverified until the exact release is tested (S13). ODK documents CSV export, not arbitrary CSV import as submission records (S04, S19).

If selected by the owner, use a review-only staging batch with: immutable source filename and SHA-256; batch ID; importer/version; original row number and source key; deterministic mapping preview; coordinator approval; row-level validation/error messages; explicit site-code and form-version mapping; a disclosed timezone interpretation; no invented source IDs; attachment-to-row verification; and a quarantine for ambiguous or invalid rows. Generate a new observation UUID unless a source key has documented uniqueness. Preserve raw values. If missing timestamps, ambiguous IDs, unsupported answer codes, or absent/unmatchable photo files cannot be resolved, leave those rows quarantined and do not silently create canonical data. Revisit or exclude the optional import only on that evidence and after owner review; do not silently narrow it now.

## Corrections, optional improvements, and owner decisions

**Required corrections to the staged assumptions:** online-only completion is incompatible with the brief and contradicted by both products' offline workflows; retry must not mean unknown new record or changed content under the same ID; device timestamp cannot establish identity; photo filename cannot guarantee stable identity; weekly export dedup cannot substitute for investigation; no source supports the “recent release resolves reconnect problems” statement; CSV import is not established by export or lookup documentation; the one-line state model must distinguish draft, queued, received, duplicate review, correction proposal and steward decision.

**Optional design improvements for the eventual product plan:** generated observation/visit IDs; schema digest; attachment UUIDs and checksums; separate photo-upload status; explicit missing-media indicator; advisory duplicate fingerprints; CSV batch digest, row numbers, mapping preview, quarantine and source lineage; a small export/restore rehearsal. These improve traceability but are not claims that either product supplies them without configuration or an adapter.

**Owner decisions still needed:** the data steward's current-view rule for accepted corrections; hosting/service budget and data location; whether optional CSV import is useful in the pilot; site-code authority; photo retention and size limits; whether user/device identifiers are needed and permitted; backup/export cadence; what a coordinator must see to accept/close a duplicate investigation. The brief already resolves duplicate authority and prohibited behavior; do not reopen those.

## Already covered, rejected, uncertain, and alternatives

- **Already covered:** user-authorized optional CSV scope and the two owner authorities are present in the released plan. Retain them rather than “discover” them as new technical features.
- **Rejected as unsupported or conflicting:** online-required workflow; device timestamp as a unique visit identity; filename as unique photo identity; manual weekly dedup as adequate policy; assumption that a recent release has fixed all reconnect failures; any hidden auto-merge; treating lookup CSV or CSV export as proof of row-import capability; removing CSV scope merely because native import was not found.
- **Alternatives:** ODK Cloud managed hosting vs ODK self-hosted Central; Kobo global vs EU server, with private Kobo servers only as a qualified option for some larger organizations; append-only correction events vs in-place update (recommend append-only and ask steward how projection works); CouchDB-style retained conflicts vs survey products (analogue, not product choice).
- **Uncertain until tested or decided:** exact latest-build retry behavior after a lost server acknowledgement; whether a product can express every proposed state without custom workflow; whether and how media IDs are exposed in a chosen export/API; exact photo count/size/file limits; Android-version compatibility; ODK local retention configuration; legacy CSV schema, import pathway, idempotency and media mapping; ODK storage impact when old submission revisions retain media; data-steward current-view policy; operational/data residency fit. Treat these as validation or owner inputs, not negative evidence.

## Research scope and disposition

This proposal stays at 25 volunteers, Android personal devices, intermittent connectivity, one site/visit observation, structured answers, up to three photographs, late receipt, correction without losing the original, and an occasional desktop path. It adds no compulsory online step, photo-derived location, phone-setting change, or remote deletion of originals. It preserves the explicitly authorized optional CSV path while separating owner permission from technical support.

The best-supported path is offline-first survey collection with stable client identity, idempotent same-payload retries, server receipt time, explicit media completeness, human duplicate investigation, and linked correction events. ODK is the conditional lead and Kobo the alternative; neither is represented as a fully validated solution. CSV import is retained for a reviewed feasibility decision. Product validation remains NOT_RUN.
