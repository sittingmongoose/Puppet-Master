# Investigator discovery — recurring room booking

Run: `A1-02-treatment` · stage: investigator · source brief: `ER12-A1-02-FRESH`.

## Scope and early recommendation

Treat this as an offline edit of one imported iCalendar object. Keep one master `VEVENT` and edit one original recurrence slot by a detached exception. The durable series identity is the imported calendar/source namespace plus the master `UID`; the occurrence key is that series identity plus a typed `RECURRENCE-ID` in the master DTSTART's value/time-zone form. A move changes the detached exception's `DTSTART`/`DTEND`, never its `RECURRENCE-ID`. A cancellation removes the slot from the generated set with master `EXDATE`; a cancelled detached record is a possible tombstone where an existing exception must remain inspectable. Do not emit an iTIP `METHOD:CANCEL` transaction for this offline snapshot-only tool. RFC 5545 gives the recurrence set and original-slot identity; RFC 5546 and providers show scheduling/API operations are different protocols (S01–S06).

A minimal data sketch is `Series(import_id, uid, master_component_raw, typed DTSTART/RRULE/TZID, source_hash)` plus `OccurrenceOverride(import_id, uid, recurrence_id_type, recurrence_id_tzid, recurrence_id_wall_or_utc, component_raw, state)`. Store ordered raw property lines/parameters for every component and preserve the original imported bytes/hash. Upsert by stable keys so an unchanged re-import is idempotent; flag duplicate UIDs, duplicate `(UID, RECURRENCE-ID)`s, unsupported rule forms, or incoming/local edit conflicts instead of arbitrarily choosing a row. Don't infer a provider object ID from an iCalendar UID or expose a provider API surface.

## Findings by obligation

- **C1 — identity:** RFC 5545 defines persistent global component `UID` and uses `UID` + `RECURRENCE-ID` (with revision `SEQUENCE`) to address an instance. For a rescheduled instance, recurrence ID remains the originally scheduled date/time; current DTSTART is the new time. Preserve value type and zone semantics, including whether the original value was local-with-TZID or UTC. Google similarly calls `originalStartTime` immutable and unique within a series even when `start` changes. Graph has API-specific `seriesMasterId`, `type`, and UTC `originalStart`; these demonstrate the same split, but IDs/UTC field shape do not transfer to ICS (S01, S03–S04).
- **C2 — cancel/move and recurrence set:** RFC 5545 makes the set from DTSTART ∪ RRULE ∪ RDATE − EXDATE, with EXDATE precedence and duplicate inclusion deduplicated; a DTSTART/RRULE mismatch makes the result undefined. For one deleted slot, EXDATE is the snapshot-level exclusion. For a moved slot, use an override keyed by the original slot. iTIP METHOD:CANCEL is an organizer-to-attendee scheduling message, not a synonym for editing an offline export. If the target already has an override, export must not leave it active beside the new exclusion; retain raw override properties in DB/tombstone and validate the selected file representation. Restrict any RANGE=THISANDFUTURE behavior and future-series edits; they exceed one-occurrence scope (S01–S02).
- **C3 — zone and DST:** Use named TZID local wall time and the matching embedded VTIMEZONE as the authority; RFC says a referenced TZID must map to a VTIMEZONE and warns missing/failing definitions cause inconsistent local interpretation. Do not store weekly time as a fixed UTC instant. RFC 5545 picks the first instant in an ambiguous fold; an explicit nonexistent DATE-TIME resolves using the pre-gap offset. Separately, a recurrence-rule-generated nonexistent local time is ignored and not counted. Proposed edit policy: show the first-fold selection explicitly; reject a new move target in a spring-forward gap with an actionable error; parse existing RFC values according to the RFC, retaining their literal and zone. Do not substitute host-local zone or silently repair unresolved/custom TZID (S01).
- **C4 — provider operations:** Google requires retrieving the instance, then updating that instance to change/cancel it; its stable `originalStartTime` survives a move. Graph lists occurrences/exceptions by range; its event resource separates `seriesMaster`, `occurrence`, `exception` and cancelled-occurrence identifiers. Graph `cancel` is organizer-only and sends attendee notification (and can target an occurrence ID); `PATCH` an occurrence modifies it but can fail if it crosses/overlaps an adjacent day-boundary condition. Transfer only conceptual identity, detached exception and separate cancellation/move operations. Do not transfer API IDs, auth/organizer rules, notifications, Graph's UTC-only `originalStart`, or its restriction as iCalendar rules. No provider calls are in scope (S03–S07).
- **C5 — unknowns/idempotence/round trip:** RFC 5545 requires unknown IANA/X-name value data to be preserved without interpretation. Retain unknown property name, ordered parameters, raw encoded value/content line and component association; do not copy opaque master fields onto an exception as if their scope were understood. Patch only the changed typed fields and preserve master and existing exception property bags. Repeat import must upsert, not append; same exact file and exported-file reimport should settle to one series and one override. Semantic round-trip is not byte identity unless raw line/fold preservation is proved. A first-party implementation history entry for Python `icalendar` 7.3.0 records that unrecognized and `X-` values were being changed by escaping on parse/serialize/jCal round trip and were fixed; another entry documents an actual TZID offset bug. These do not prove a Rust crate bug, but show why release-pinned preservation and DST tests are required (S01, S08–S11).
- **C6 — support and validation:** Supported target: one trusted `.ics` file, one weekly RRULE series in a named zone crossing DST, one occurrence move or cancel, one pre-existing exception elsewhere or at the target, and unknown properties. Unsupported inputs must remain unmodified and surface a clear unsupported/conflict outcome: other recurrence forms, multiple/unbounded semantics the chosen subset cannot safely expand, floating/UTC/mismatched zones if unsupported by the product contract, missing/ambiguous VTIMEZONE, duplicate identities, malformed or undefined DTSTART/RRULE pairs, and provider account/API operations. These are recommendations and proposed tests only; no importer, exporter, provider, or interoperability validation was executed.

## Open implementation decisions

1. Which weekly subset is accepted (e.g. interval, BYDAY, COUNT/UNTIL, RDATE/EXDATE), with parser and expander accepting the exact same grammar; reject every unsupported/unknown rule part rather than partially expand.
2. How to resolve an existing `RECURRENCE-ID` that is also in EXDATE or a cancelled detached component. Proposed canonical export is EXDATE plus no active override; retain removed exception's full raw component in the database tombstone. Validate that choice in independent consumers before calling it interoperable.
3. Whether embedded VTIMEZONE is authoritative even when its TZID resembles IANA, and how to compare it with bundled IANA tzdata. Preserve source definition; fail closed if conflict or resolver cannot prove the supported weekly DST case.
4. How repeat import treats a changed upstream file that conflicts with an edited exported file. Identical input/output should be idempotent; a changed source with same `(UID, RECURRENCE-ID)` but conflicting values must surface a conflict, not overwrite silently.
5. Choose/pin a Rust parser/expander only after checking unknown property, parameter, duplicate-line, line-fold, and timezone behavior. `caldata` 0.17.3 is an available strict Rust recurrence/parser candidate but its docs do not establish byte/opaque-property round trips. `pimalaya/ical` describes a byte-faithful syntax tree plus recurrence/time-zone modules, but the inspected repository was an unpinned `main` page, not a released commit. Neither is yet an interoperability claim (S08–S09).

## Proposed round-trip validation matrix (not run)

For each fixture below: import → show target → move/cancel → export → import exported file twice → compare occurrence keys, effective starts, master recurrence properties, and all opaque lines/parameters; assert no duplicate/phantom row. Separately parse output with two independent consumers (e.g. current Google Calendar UI import and Outlook/Graph-backed test tenant) only after authorization and a safe fixture are available; no accounts were used here.

1. Weekly 09:00 `TZID=America/New_York` series spanning spring and fall transitions: generated local hour remains 09:00; UTC offset changes correctly.
2. Move one target after DST: override keeps original RECURRENCE-ID, new DTSTART/DTEND use intended local zone; no original phantom instance.
3. Cancel ordinary slot: EXDATE excludes only that original slot; neighboring instances and master survive.
4. Existing moved exception at target + cancel; existing exception elsewhere + another move; repeated cancel/move/reimport; verify chosen tombstone/override policy and stable `UID`/RID uniqueness.
5. Fold/gap: ambiguous explicit time follows first occurrence; rule-generated nonexistent slot is skipped and not counted; newly entered nonexistent move time is refused; imported explicit gap value resolves per RFC without rewriting its lexical source.
6. Unknown `X-` and IANA properties, unknown parameters, duplicate property lines and folded lines on master and exception: preserve bytes or document tested semantic preservation; prove no property disappears or changes value/parameters.
7. Same file import twice and export reimport: one series, one occurrence override, same effective output; changed source collision yields conflict.
8. Negative fixtures: unsupported recurrence, floating/UTC/wrong-TZID input, missing/custom/conflicting VTIMEZONE, malformed identity, multiple masters with duplicate UID: no partial write/export and no silent fallback.
