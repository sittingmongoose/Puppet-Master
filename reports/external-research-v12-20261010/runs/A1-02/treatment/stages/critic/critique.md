## Overall assessment

The package preserves the assignment’s offline, single-file scope and handles C1, C2, C4, and most of C5/C6 with useful operation-level comparisons, an explicit fail-closed envelope, and a clear separation between proposed and executed validation. The two Rust-library alternatives are properly described as candidates or leads, not proven compatible. No provider/API access or implementation validation is claimed.

## Findings

### F1 — Material wrong: generated local times in a DST gap

**Locations:** discovery.md C3 and proposed matrix item 5; draft.md C3 and validation matrix row “DST fold, gap, and gap-target move”; investigator source-map.json S01 condition summary.

The package says a nonexistent local time generated by RRULE is skipped and not counted. That matches the uncorrected sentence in RFC 5545 §3.3.10, but misses RFC Editor Erratum 4271, which is Verified. The erratum removes nonexistent local time from the skip/not-count rule and directs it to §3.3.5. Under §3.3.5, a local time in a spring-forward gap is interpreted using the offset before the gap. The package therefore gives the wrong imported recurrence behavior and a wrong proposed validation expectation. Invalid calendar dates remain ignored; this finding concerns nonexistent local times only.

The recommendation to reject a newly entered move destination in a gap is explicitly a product choice and is not contradicted by this finding. The assignment’s recurring 18:30 example may not itself land in a gap, but C3 promises a general policy and the matrix expressly tests gap behavior.

**Evidence:** S01, RFC 5545 §§3.3.5, 3.3.10, 3.8.5.3; S12, RFC Editor Verified Erratum 4271. See [S01](sources/S01.md) and [S12](sources/S12.md).

### F2 — Material wrong: RFC attribution for unknown properties

**Locations:** discovery.md C5; draft.md C5 required behavior; investigator source-map.json S01 condition summary.

RFC 5545 §3.2.20 is the VALUE parameter section. Its preservation rule applies to unrecognized value-type tokens (x-name or IANA token values); it does not establish a general requirement to preserve arbitrary unknown property names, parameters, or raw content lines. RFC 5545 §§3.8.8.1–.2 separately say IANA and X-name properties may be ignored by generic consumers. The draft’s statement that RFC 5545 explicitly mandates unknown-property preservation is therefore too broad.

The behavior itself is still required by this brief’s “no silent drop of unknown properties” constraint. Keep that requirement as the product contract and separate it from the narrower RFC requirement. S10’s Python-library history remains a useful compatibility caution; it is not proof of a defect in the proposed Rust candidates.

**Evidence:** S01 §§3.2.20 and 3.8.8.1–.2; S10 v7.3.0 changelog. See [S01](sources/S01.md) and [S10](sources/S10.md).

### F3 — Material incomplete: moved-exception duration representation

**Locations:** draft.md C1 concrete moved-instance representation and C3 duration paragraph; discovery.md initial data sketch.

The concrete representation always describes a moved exception using DTSTART/DTEND. C3 correctly observes that RFC 5545 treats a recurring master with DTEND as a fixed exact duration, but a master with DURATION as a fixed nominal duration whose elapsed length can vary at a zone transition. It then says to preserve the original form “where feasible,” without defining when it is feasible or how a move across a transition maintains the intended duration. If the input uses DURATION, forcing DTEND can change its semantics.

The brief does not fix the imported event’s duration form. The adapter contract needs an explicit no-unintended-duration-change invariant and a test for moving an instance whose master uses each form.

**Evidence:** S01 §3.8.5.3; [S01](sources/S01.md).

### F4 — Material incomplete: exact RRULE UNTIL acceptance condition

**Location:** draft.md C6 proposed v1 support envelope and fail-closed list.

The draft leaves the exact weekly grammar open, which is honestly acknowledged. If UNTIL is accepted for the proposed local DTSTART with a TZID, the support contract must also enforce RFC 5545 §3.3.10’s condition that UNTIL be UTC for a DTSTART with a TZID reference. The current envelope says “optional COUNT or UNTIL only if the expander supports their counting/end semantics” but does not state this type/time-zone rule or identify invalid UNTIL forms as rejected. RFC 5545’s grammar permits either UNTIL or COUNT, not both, and COUNT includes DTSTART as the first occurrence; make these acceptance checks explicit if those forms are supported. This is an unfilled condition on a proposed supported input, not evidence that an implementation has mishandled it.

**Evidence:** S01 §3.3.10, especially UNTIL/COUNT and DTSTART rules; [S01](sources/S01.md).

### U1 — Honestly unresolved external input: canceling an existing exception

**Locations:** draft.md C2 cancel bullet and proposed validation row for canceling a previously moved override.

The draft proposes EXDATE plus removal of the active detached component, retaining its exact raw data in a local tombstone. The reviewer found no independent consumer test establishing how the selected file representation behaves when an existing override’s RECURRENCE-ID is also excluded. The draft names this as unresolved and makes cross-reader validation a prerequisite to compatibility claims. This is an external consumer-behavior question, not a material defect in the proposal as currently labeled.

**Evidence:** S01 §§3.8.4.4 and 3.8.5.1 define recurrence identity/exclusion; S02 separates iTIP cancellation messaging. Neither document proves the proposed tombstone representation’s behavior in independent readers.
