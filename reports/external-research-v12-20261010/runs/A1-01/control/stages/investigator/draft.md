# Recommendation and repairable transfer plan

Fixture: `ER12-A1-01-FRESH` · run: `A1-01-control` · stage: investigator

## Recommendation

Proceed with a **gateway-owned, provider-qualified native multipart session** as the first candidate. The gateway authenticates through the existing host identity, creates and durably journals one transfer session, allocates a unique object key, holds the provider's raw multipart upload ID, authorizes each bounded part, reconciles remote state, completes or aborts, and owns expiry/orphan cleanup. The desktop client keeps a local recovery record and uploads parts directly only with short-lived, part-scoped authorization. Keep host credentials, storage credentials, raw provider upload IDs, and signed URLs out of that record. The provider cannot be enabled because it merely calls itself “S3-compatible”; gate this route on the exact deployed vendor/build, SDK version, endpoint style, checksum mode, and HTTPS request encoding passing the validation below.

Use **16 MiB as the first part-size candidate and a hard per-request body bound**, subject to that compatibility gate. Amazon S3 documents 5 MiB–5 GiB for non-final parts and allows a smaller final part; 16 MiB therefore fits that service's rules. It yields 384 parts for 6 GiB, within its 10,000-part limit; a 20 MiB file can be 16 MiB plus a 4 MiB final part. This is arithmetic and a conservative retry/buffer choice, not a measured optimum or a promise for other vendors. A MinIO issue reports an HTTPS aws-chunked limit at 16 MiB for one specific implementation/SDK pair (S07), so part size alone is not the safety proof: the exact Rust SDK's wire encoding and the selected store must pass. Prefer a tested TLS request with explicit content length and checksum header; do not turn off integrity checks to work around a provider. Start with one active part; preserve a maximum of three only as a tunable ceiling after concurrency/race tests. No throughput claim is made.

Keep a gateway-backed resumable HTTP service using tus 1.0.0 as a viable alternative if the gateway can durably store accepted byte ranges and offsets, and direct MPU cannot be safely brokered. tus provides a clear byte-offset reconciliation protocol, but it does not itself remove the storage integration: the server must persist bytes plus offset and bridge the result to the object store. Do not add both transports in the first release. If neither route is qualified, block upload for that provider rather than guessing.

## Minimal state sketch

```text
local PREPARED (source hash/part manifest saved atomically)
  -> gateway INITIATING (idempotency key = client_upload_id)
  -> UPLOADING (authoritative remote part set; local per-part journal)
  -> FINALIZING (all expected parts reconciled; one completion intent)
  -> COMPLETED { integrity: full_match | transfer_checks_only | unverified }

UPLOADING / FINALIZING -> SOURCE_CHANGED (no new parts; no completion)
UPLOADING / FINALIZING -> ABORTING -> ABORTED | EXPIRED
uncertain response -> RECONCILING -> prior state or explicit failure; never new session silently
```

`client_upload_id` is a random value created before networking and reused for every retry of session creation. The gateway maps it, under the current authenticated principal, to a unique server session, unique generated object key, provider/profile version, raw store upload ID, expected length and SHA-256, fixed part size, expiry, and journaled part/completion state. A duplicate create with the same owner and ID returns that session; a different owner cannot adopt it. User filenames are metadata only. Do not target a reusable key: object replacement/conditional-write policy is not specified by the brief.

The local versioned JSON record stores the client ID and opaque gateway session ID, source path/length/fast file metadata, whole-file SHA-256 and per-part SHA-256 manifest, fixed part ranges, confirmed part numbers and returned opaque ETags/provider checksums, compatibility-profile ID, expiration, and local state. Do not save access tokens, storage credentials, raw provider upload IDs, or presigned URLs. Restrict local file permissions, write via temp-file/flush/atomic rename, and write acknowledged part state before advertising it locally as durable. Gateway journal plus provider `ListParts` wins over a stale local acknowledgement.

Before first creation, hash the entire source and each planned part. Before each part is sent or retried, spool at most one 16 MiB range, hash it, compare it with the saved manifest, and send the same spooled bytes. Remove the spool after the result is reconciled. Rehash the source against the whole-file digest before resuming and before completion; size/mtime/file ID are fast rejection hints, not proof, because same-size edits and timestamp-preserving replacement exist. A mismatch marks the old session `SOURCE_CHANGED`, sends no further bytes, and forbids completion. Offer a separate, explicit new upload; do not retarget the old session or silently replace its source. Full hashing on each restart/finalization is a deliberate integrity cost; the owner may consider a proven snapshot/locking method later, but may not substitute metadata-only identity without accepting weaker guarantees.

## U1 — identity, recovery record, and interruption behavior

**Disposition: accept with corrections and additions.** Use the client idempotency ID + gateway session ID + unique store key as distinct identities. The gateway retains the raw provider upload ID. The local record is a recovery journal, not authorization. Record every independently acknowledged part number and checksum/ETag, not just the largest number.

- **Process death:** after host reauthentication, load the record, verify principal/session/source, ask the gateway for current session status, and reconcile the complete remote part-number set. Amazon S3 `ListParts` returns up to 1,000 entries per request; this 6 GiB plan is at most 384 parts, but profile pagination regardless. Resume only missing parts. A part that was in flight at death is uncertain until remote reconciliation.
- **Network loss or dropped response:** the client retries with bounded backoff. For an uncertain part, first query gateway/remote state; if missing, send the same part number and the same manifest bytes. Amazon S3 documents that same-number upload replaces the prior part; use that only for the qualified adapter. Do not infer acceptance from a socket write or local “largest part” value. A lost create response repeats the same idempotency key. A lost completion response moves to `RECONCILING`; query gateway and object state before any retry. Never initialize a replacement automatically.
- **Changed local file:** rehash before resume and finalization, then verify each spooled part immediately before sending. Any mismatch means no more parts and no completion for this session. Do not delete or replace the selected local file; show the original session as source-changed and require explicit new-upload intent. Cancel/abort the old remote session after the client has stopped issuing parts.
- **Gateway credential/token expiry:** no new storage credentials go to the client. If host authentication expires, pause and request host reauthentication. If the same principal returns, gateway issues a fresh short-lived authorization for the same session/part; already acknowledged parts stay acknowledged. A different principal is denied. If an individual signed part URL expires, obtain a fresh one from the gateway and retry the same part after verifying the source range; never persist the URL.

## U2 — approach comparison and transport choice

| Property | Resumable HTTP service (tus 1.0.0) | Native multipart (qualified S3 profile) |
|---|---|---|
| Recovery unit | Byte offset on one resource. `HEAD` reports accepted offset; `PATCH` must match it and an offset mismatch is `409` without mutation. Optional checksum extension can reject a bad chunk without advancing offset. [S01](https://tus.io/protocols/resumable-upload) | Numbered independent parts. List parts after uncertain replies; retry a part without resending earlier parts. Completion orders parts by number. [S02](https://docs.aws.amazon.com/AmazonS3/latest/userguide/mpuoverview.html) |
| Data/state owner | Tus server must durably commit accepted bytes and offset together. It needs staging storage or an object-store backend. A server crash between data and offset persistence can otherwise lose or double-accept data. This atomicity is an implementation requirement inferred from the protocol contract. | Object store retains parts; gateway journals ownership/identity and reconciles with the store. No separate whole-file tus staging area is needed, but the gateway still owns idempotency, authorization, finalize/abort, and recovery. |
| Mechanism tradeoff | Stable HTTP semantics across backends; ordered byte stream and less part bookkeeping for the client. Gateway receives all bytes and must stage/relay them or implement a backend adapter; expiry/checksum/termination are optional protocol extensions that must be advertised. [S01](https://tus.io/protocols/resumable-upload) | Parts can transfer independently and a failed part alone can be retried; storage service constructs the object only on complete. It avoids a second staging copy but requires provider-specific limits, checksum types, request signing/encoding, response parsing, and orphan cleanup. Amazon S3 MPUs do not expire automatically. [S02](https://docs.aws.amazon.com/AmazonS3/latest/userguide/mpuoverview.html) |
| Failure mode | If offset and stored bytes do not share durable commit semantics, a reported offset can diverge from payload. Need service-level crash and persistence testing. | If the gateway assumes AWS behavior for an unqualified compatible store, retries/checksums/completion may fail differently. Need exact provider profile and lifecycle tests. |

**Choice:** native MPU only for a qualified endpoint because this transfer already targets object storage and parts remain there; it gives resumability without an additional tus staging object. This is conditional, not a claim that unknown storage is compatible. Gateway-backed tus is the fallback decision if its server can durably own offset and bytes with acceptable staging/relay cost. Neither user preference alone settles that architecture question.

## U3 — completion and integrity

**Disposition: reject the draft's ETag-as-file-check assumption.** ETags identify uploaded parts for Amazon S3 completion, but a multipart object's final ETag is not necessarily an MD5 of the full file. Checksum responses may be composite; Amazon S3 distinguishes `COMPOSITE` from `FULL_OBJECT`. Do not label a matching part ETag or final ETag as an independently verified byte match. [S02](https://docs.aws.amazon.com/AmazonS3/latest/userguide/mpuoverview.html) [S06](https://docs.aws.amazon.com/AmazonS3/latest/API/API_CompleteMultipartUpload.html)

Report three separate levels:

1. **Part acknowledged:** the qualified endpoint accepted a particular part and returned its part identity/checksum. Persist that result; this says nothing alone about final object visibility.
2. **Object completed:** gateway reconciled successful completion, the exact object key and expected size, and a parsed success result or authoritative status. AWS notes that completion can take minutes and return HTTP 200 with an embedded error body; parse the body and handle the error. On timeout, reconcile before retry. [S06](https://docs.aws.amazon.com/AmazonS3/latest/API/API_CompleteMultipartUpload.html)
3. **Independent byte match:** compare an endpoint-provided *full-object* checksum with a local digest computed using the same algorithm and type, after profiling that capability; if no compatible full-object checksum is offered, read the object back and compute SHA-256. A `COMPOSITE` checksum, including multipart SHA-256, is not a direct whole-file SHA-256. If neither route executes, status is `completed, integrity not independently verified` (or `transfer checks only` when part checksums were validated); do not imply equivalence.

For Amazon S3, ask for an explicit checksum mode/type during initiation and test part and full-object behavior with the exact SDK. AWS documents server-side validation when a full-object checksum is declared; its checksum matrix distinguishes full-object-capable algorithms from composite choices, so do not infer that multipart SHA-256 is a full-file SHA-256. Availability/defaults for this unspecified compatible store are unknown. If the provider returns `NoSuchUpload` after an ambiguous complete, it may mean invalid, aborted, or already completed; reconcile the unique object key and gateway journal before classifying the result. [S02](https://docs.aws.amazon.com/AmazonS3/latest/userguide/mpuoverview.html) [S06](https://docs.aws.amazon.com/AmazonS3/latest/API/API_CompleteMultipartUpload.html)

## U4 — cancellation, expiry, cleanup, retries, and owners

| Action | Owner and required behavior |
|---|---|
| Start, identity, local source validation | **Client** generates/reuses `client_upload_id`, hashes source, writes local record atomically. **Gateway** authenticates existing principal, creates one server session idempotently, allocates unique key, records intent before provider calls, and retains the raw provider upload ID. |
| Part transfer | **Client** requests a new short-lived authorization for a specific session/part, verifies/spools exact bytes, sends and records only confirmed parts; retries network ambiguity after reconciliation. **Gateway** scopes grant to principal/key/upload/part and records status. **Store** accepts/replaces that part and returns provider result. Start at concurrency 1; allow no more than 3 only after concurrent acknowledgement/reconciliation tests. |
| Token expiry | **Client/host** pauses and obtains fresh existing host authentication. **Gateway** checks the same principal and may issue a fresh per-part grant for the same session. Expiry of a grant is not session expiry. No credentials or grants are written to disk. |
| Cancel | **Client** durably records cancel intent and schedules no new part requests. **Gateway** atomically fences new grants/completion, waits for in-flight parts to settle, then aborts. It retries/reconciles abort and returns a stable terminal state. If completion already won, return `already_completed`/`too_late`; do not delete the completed object as cancel cleanup. **Store** abort removes partials on its own documented semantics. |
| Session expiry | **Gateway** owns a fixed, published deadline; proposed default is 7 days from initiation, returned in status and checked on every resume. Expiry fences new parts and invokes abort. This is a policy choice, not a tus/AWS default. **Client** reports expired and offers a separate explicit new session. |
| Orphans | **Gateway** journals `INITIATING` before `CreateMultipartUpload`, writes returned provider ID before granting part access, and sweeps incomplete rows. A crash in the remote-create/ID-persist gap can leave an MPU not yet recorded; use a unique session-key prefix, provider list/abort reconciliation, and a configured lifecycle rule as a safety net. Candidate Amazon S3 rule: abort by prefix after 14 days since initiation, after the 7-day gateway deadline. Verify rule/filter behavior; AWS's example is a configured rule, not a default, and lifecycle cannot use a tag filter for this action. If an endpoint lacks a usable sweep or lifecycle backstop, do not enable it. [S04](https://docs.aws.amazon.com/AmazonS3/latest/userguide/abort-mpu.html) [S05](https://docs.aws.amazon.com/AmazonS3/latest/userguide/lifecycle-configuration-examples.html) |
| Provider retry | **Gateway** owns bounded backoff and status reconciliation for initiate/complete/abort and cleanup; **client** owns part body retry because it reads the local file. **Store** owns durability and its API result. No retry creates a new session. |

Amazon S3 states that incomplete parts consume storage until complete/abort; an incomplete upload does not publish an object. It also documents that lifecycle can abort after a chosen number of days. These facts support explicit cleanup, but unknown providers may differ. Aborting the remote MPU is not deletion of a completed object. [S02](https://docs.aws.amazon.com/AmazonS3/latest/userguide/mpuoverview.html) [S04](https://docs.aws.amazon.com/AmazonS3/latest/userguide/abort-mpu.html) [S05](https://docs.aws.amazon.com/AmazonS3/latest/userguide/lifecycle-configuration-examples.html)

## U5 — compatibility boundary and implementation history

**Disposition: keep provider compatibility open; do not infer it from the S3 label.** The selected route requires an allowlisted tuple: vendor and server build/release; bucket/endpoint mode and addressing; pinned Rust SDK/service version; gateway signing/proxy path; HTTPS request body encoding; supported part limits; create/list-parts/complete/abort behavior; part and full-object checksum algorithms/types; and cleanup/lifecycle configuration. Store this tuple with the server session/profile version. A new tuple is disabled until its tests pass. Never disable checksums just to make a request work.

The primary implementation-history clue is MinIO issue [#21611](https://github.com/minio/minio/issues/21611): opened 2025-09-28, it names MinIO `RELEASE.2025-09-07T16-13-09Z` and AWS Go SDK service/s3 `v1.73.0+`; the reporter says checksum trailers encoded as HTTPS `STREAMING-UNSIGNED-PAYLOAD-TRAILER` fail above 16 MiB with `chunk too big`. On retrieval the issue was still Open and its repository page says archived 2026-04-25. This is a versioned community report in a first-party issue tracker, not a normative spec, confirmed fix, or result for the fictional Rust client. It supports testing the actual request encoding and provider build; it does not prove that setting multipart part size to 16 MiB alone resolves the issue. Preserve the configured checksum protection and block the profile if its supported wire form cannot pass. See [S07](https://github.com/minio/minio/issues/21611).

### Original design choices and corrections

- **Corrected:** replace “resume from the largest saved piece number” with reconciliation of the entire remote part set. At most three in flight can leave holes or uncertain acknowledgements; a maximum number cannot represent that set.
- **Corrected:** ETag is not the full-file integrity check. Keep server completion and independent byte-match as separate statuses.
- **Revised:** keep 16 MiB as a bounded first candidate, not a validated optimum. It fits Amazon S3 limits and is relevant to S07's report; exact Rust SDK/provider tests still gate it. Discovery's earlier 64 MiB sizing example was preliminary arithmetic and is superseded for this draft by the newly released 16 MiB preference plus the versioned compatibility evidence. No source makes 16 MiB universally safe.
- **Revised:** preserve at most three concurrent requests only as a cap; serial is the initial default until recovery and race behavior is proven. No benchmark justifies a chosen throughput optimum.
- **Added:** gateway idempotency/session journal, unique destination key, per-part manifest and bounded spool, full-source hash checks, explicit expiry/status, cancel fencing, cleanup sweep/backstop, same-principal token renewal, and `completed_unverified` status. These are proposed design decisions, not external standards.

### Rejected, optional, and owner decisions

- **Reject:** “largest acknowledged part number means all earlier pieces succeeded”; remote state is a set and may be noncontiguous.
- **Reject:** marking `done` merely because a completion request was sent, because HTTP returned 200, or because an ETag exists. Parse and reconcile completion; expose verification level.
- **Reject:** persistent auth/storage credentials, silent replacement with a changed file, automatic replacement session after expiry, or assuming every compatible store behaves like AWS.
- **Keep optional/out of this transfer spec:** progress/retry/cancel UI. The brief declares the existing UI outside scope; only the protocol outcomes and controls it must call are specified here. No full uploader app or authentication provider is proposed.
- **Owner decisions before implementation:** exact storage vendor/build and endpoint; whether existing gateway can persist a journal and issue narrowly scoped direct part authorization (or needs to proxy); final object-key visibility/naming requirements; acceptable full-file rehash cost on resume/finalization; exact seven-day session/14-day lifecycle policy; which provider checksum can prove full-object match; retain concurrency ceiling 3 after tests or keep serial; behavior if lifecycle/list/abort APIs are absent. Until decided and profiled, that provider path stays disabled.
