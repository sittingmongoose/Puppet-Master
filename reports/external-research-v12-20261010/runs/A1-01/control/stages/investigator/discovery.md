# Investigator discovery — ER12-A1-01

## Scope and preliminary recommendation

The assigned brief asks for one transfer and its local recovery semantics for a fictional Rust client, existing authenticated gateway, and an S3-compatible store whose exact compatibility is unknown. This is protocol research only: no production account, credentials, real upload, implementation, or validation is available. The sources below are primary protocol/service documentation and one first-party implementation issue; the proposed state machine is original design, not something those sources prescribe.

**Preliminary recommendation:** have the authenticated gateway own session creation, destination-key allocation, completion, abort, expiry, and a durable session journal; let the client upload bounded parts only under narrowly scoped, short-lived authorization. Use native multipart only behind a provider/version capability profile that has passed the proposed exact-endpoint checks. The phrase “S3-compatible” is not sufficient to enable the path. A 64 MiB part size is a candidate fixed choice: a 20 MiB file is one final part; 6 GiB is 96 parts, below Amazon S3's documented 10,000-part limit. This is a sizing calculation, not a performance finding. Start serially to keep recovery simple. If the installed gateway cannot broker native multipart safely or the provider fails the profile, do not silently fall back; decide whether to add a gateway-backed tus service or defer that provider.

## Approaches compared

- **Resumable HTTP / tus 1.0.0:** one upload URL and monotonically increasing byte offset. After a lost response, `HEAD` obtains the authoritative offset; `PATCH` must present it, with a mismatch rejected as `409` without changing the resource. The optional checksum extension verifies a PATCH body and leaves offset unchanged on mismatch. This gives a store-neutral client interface, but the server must durably couple accepted bytes and offset, retain partial data, enforce expiry/termination, and then bridge those bytes to the object store. Staging or re-uploading through the gateway can add disk, bandwidth, and a second transfer; a direct object-store backend still needs a provider-specific adapter.
- **Native multipart:** create a remote upload ID, store numbered parts independently, reconcile with list-parts after uncertain replies, and complete from the ascending part/ETag list. A failed part can be retried without restarting earlier parts. Parts live at the object store rather than a separate tus staging area, but limits, checksum modes, signatures/encoding, completion errors, and cleanup are provider behaviors that need qualification. AWS says its uploads do not expire automatically; uploaded parts remain billable until completion or abort.

## Consequential design and recovery findings (proposals)

- **Identity and journal (U1):** client creates a random `client_upload_id` before networking and reuses it as an idempotency key. Gateway binds it to the existing authenticated principal, a new server `session_id`, unique server-allocated object key, provider-profile version, expected length, part size, expiry, and provider upload ID. The local versioned recovery record contains the client/session IDs, source locator and expected length, file identity (fast metadata plus a content manifest), part ranges and SHA-256 digests, acknowledged part numbers/checksums/ETags, endpoint/profile ID, expiry, and state. Do not persist credentials, auth tokens, or signed part URLs; scope every resume request to the host's current authenticated identity. Write the local record atomically after each confirmed part. Server journal and `ListParts` are authoritative after restart.
- Before creating a session, stream-hash the selected file and record a whole-file SHA-256 plus per-part digests. Before sending or retrying a part, read that range into a bounded temporary spool, compare with its recorded digest, then send those exact bytes; this detects edits, including same-size edits, before any changed part is accepted. Remove the spool after outcome. On resume, re-check fast file metadata and each not-yet-confirmed part against the manifest. If a size/identity/digest differs, mark `source_changed`, send no more parts and never complete the old session. Require an explicit new upload; abort the old one only through the gateway. Do not silently substitute another file.
- For process death, reauthenticate, load the local record, ask the gateway for its state, and reconcile missing/uncertain acknowledgements against remote parts. For a dropped part response, query state first; otherwise retry the same part number with the same manifest digest. S3 documentation says a repeated part number replaces that part. For a dropped completion response, query gateway/object status rather than starting over. AWS specifically warns that completion may return HTTP 200 with an embedded XML error, so parse the body and record success only from a validated completion result or reconciled object state.
- **Completion and integrity (U3):** distinguish (1) part acknowledged and digest/ETag recorded; (2) remote multipart assembled and object visible, with length and final completion response recorded; (3) independent byte match. Never treat a part ETag or final ETag as whole-file MD5: AWS documents ETags as opaque and multipart checksums may be composite. Request a provider-supported full-object checksum and compare its declared type/algorithm and digest with the client SHA-256 when available. Otherwise only claim an independent byte match after reading the completed remote object back and hashing it. If neither check runs, report “completed, integrity not independently verified.”
- **Cancel, expiry and retry owners (U4):** client persists cancel intent and stops scheduling new parts; gateway makes cancel idempotent, waits for in-flight part requests to settle, aborts the provider upload, and retries cleanup/reconciles because in-flight requests can race an abort. Gateway owns fixed session expiry (candidate: seven days from initiation), returns it to the client, rejects later resumes, and exposes expired/aborted state. Configure provider lifecycle abort as a later backstop (candidate: 14 days after initiation, strictly later than the seven-day gateway deadline); if lifecycle is unavailable, gateway sweeps its own journal and aborts. Amazon S3 requires explicit abort/complete and documents lifecycle abort by key prefix and days-since-initiation. Client retries transient network calls with bounded backoff; gateway owns provider API retries, status reconciliation, and orphan cleanup; store executes each API operation. No component may auto-create a replacement session after expiry or source change.
- Use unique destination keys per server session; do not overwrite an existing object or infer a mutable filename key. If product requirements need a chosen destination key, its collision/conditional-write behavior remains an owner decision and must be profiled.

## Evidence vs original design vs open questions

**Evidence-supported behavior:** sources S01–S06 document tus offset/extension semantics and Amazon S3's multipart lifecycle, limits, checksum/ETag distinctions, abort and completion response behavior. S07 records a concrete compatibility report, not a universal rule.

**Original choices to adjudicate:** gateway ownership; idempotency and UUID identity; unique object key; local manifest/spooling; 64 MiB serial parts; seven-day fixed session expiry and 14-day lifecycle backstop; no automatic replacement; explicit `completed_unverified` status. These numbers and policy are proposals, not source defaults.

**Unresolved:** actual object-store vendor, server build/release and endpoint mode; gateway ability to hold durable state and proxy or presign scoped part requests; exact Rust SDK version and request wire encoding (including checksum header vs `aws-chunked` trailer); supported full-object SHA-256/checksum type and HEAD/readback behavior; lifecycle/abort reliability; final-key policy; whether a full-file initial scan and bounded temporary spool fit volunteer laptop constraints. S07's issue was opened 2025-09-28 against MinIO `RELEASE.2025-09-07T16-13-09Z` and AWS Go SDK service/s3 `v1.73.0+`; it reports HTTPS `aws-chunked` requests above 16 MiB rejected. The issue was still marked Open when retrieved, and the repository now shows archived on 2026-04-25. This is a version-specific warning, not proof about the fictional Rust client or every S3-compatible endpoint.
