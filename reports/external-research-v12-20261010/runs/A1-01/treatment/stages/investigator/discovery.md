# ER12 A1-01-treatment — investigator discovery (pre-plan)

## Scope and recommendation
This discovery uses only the finalized fixture brief and primary protocol, storage, and implementation-history sources below. The exact user draft has not been released or read. No code, test, production access, or real upload was run. The recommended boundary is a Tus 1.0.0 HTTP session exposed by the existing authenticated gateway, with the gateway—not the desktop client—owning the exact object-store adapter and multipart lifecycle. This keeps credentials/storage quirks out of the Rust client and gives the editor one durable byte offset. Gate launch on a conformance check against the actual storage vendor and gateway build; “S3-compatible” is not enough evidence of identical multipart/checksum behavior.

## Governing findings
- **Tus resumability (S1):** Core recovery uses `HEAD` to obtain the authoritative `Upload-Offset`, then `PATCH` with that offset. A stale offset gets `409 Conflict` without modifying the resource; a successful patch returns `204` and the new offset. Creation, expiration, checksum, and termination are extensions: the client must inspect `OPTIONS`/`Tus-Extension` and require the features it depends on. Expiration is advisory through `Upload-Expires`; a removed session should return `404` or `410`. The checksum extension validates one PATCH body, not automatically the completed file. DELETE termination asks the server to release associated resources.
- **S3 multipart mechanism (S2–S4):** AWS describes initiate → upload numbered parts → complete; retry one failed part without replacing others. The service’s documented limits are 5 MiB–5 GiB per part (last may be smaller), 10,000 parts, and 48.8 TiB per object. A 16 MiB part design would need at most 384 parts for a 6 GiB file and fits AWS limits; this is a proposed sizing choice, not validated for the unspecified vendor. Recovery state for native multipart is upload ID plus each completed part number and its returned ETag/checksum; completion submits the ordered part list. ETag is not necessarily a whole-object MD5. Incomplete parts incur storage charges until complete/abort; AWS suggests lifecycle cleanup. In-flight part requests can finish around abort, so cleanup must drain/reconcile and may need another abort.
- **Comparison:** Tus gives the client a simple sequential offset, independent of how the gateway stores bytes; the gateway adds durable session state and may itself use multipart. It does not provide parallelism unless optional concatenation is implemented. Native multipart gives independent part retries and parallelism, but pushes vendor-specific part sizing, upload ID/part bookkeeping, complete/abort, and checksum semantics into the adapter. The bounded desktop flow does not need parallelism, so hiding multipart behind the gateway is preferable.

## Recovery design choices to carry forward
Create a stable random transfer UUID and send it as an idempotency key under the existing authenticated identity; keep the gateway’s opaque session URL/ID distinct from local path, filename, and destination key. The gateway binds owner, target, declared length, source digest, and session state. Local recovery record: schema version, transfer UUID, source path and OS file identity as hints, byte length, mtime as a hint, full SHA-256 and per-16-MiB source digests, destination selection, gateway session URL, last acknowledged offset, session/expiry timestamps, and state. Write with user-private permissions and atomic replace/flush. Never store credentials. Server offset wins over cached offset after restart.

Before resume, reopen and rehash the chosen file; resume only if length and strong digest match. Check each outgoing chunk against its precomputed digest and recheck the whole source before final commit. If any check differs or the original source is unavailable, stop sending, do not substitute the new bytes, and offer to locate the matching original or explicitly cancel and start a distinct transfer. After process death or a lost response, retain the record and reconcile with `HEAD`; after a `409`, `HEAD` again rather than blindly replaying. Keep one writer per transfer.

Propose a 30-day absolute session lifetime advertised from creation in `Upload-Expires`; the exact retention period is a product/storage owner decision. After expiry, return `410`, release gateway and backend state, and offer an explicit new transfer. Client owns local bounded retry with exponential backoff and cancellation intent; gateway owns authenticated session state, idempotent create/complete/abort, expiry, and storage retries/reconciliation; backend lifecycle/sweeper is a second orphan-cleanup line with a retention longer than the gateway lifetime. Retry an operation only after querying state when its outcome is unknown.

## Completion and integrity distinctions
1. **Chunk acknowledged:** successful PATCH and returned offset mean the server processed/stored those bytes according to its protocol; they do not prove final-object creation or compare the whole file.
2. **Remote object complete:** gateway reports terminal success only after backend multipart completion and final object size/metadata checks. A completed S3 multipart ETag is opaque and is not a general full-file digest.
3. **Independently verified byte match:** compare the precomputed local full-file SHA-256 with a backend-validated full-object SHA-256 where the exact provider supports it, or read the object back through a verification path and hash it. If neither is available, report “complete, integrity not independently verified,” not “verified.” AWS S3 supports a supplied full-object checksum and rejects mismatches, but this is AWS behavior, not a promise for all compatible vendors (S2).

## History, applicability, and open questions
AWS SDK for Rust v1.69.0 (announced 2025-01-16) changed default S3 integrity behavior to add checksums on Put and validate Get; its maintainers warn third-party services may not yet support newly enabled defaults (S5). This supports the adapter boundary: pin/configure the storage client at the gateway and qualify checksum behavior against the named endpoint instead of assuming protocol compatibility. Applicability is conditional because the fictional gateway implementation and vendor are unknown. A tusd report opened 2025-09-03 against “latest” describes `InvalidPartOrder` at multipart completion for a larger AWS S3 upload and remains open at access (S6); it is a bounded report, not proof of a general tusd or S3 defect. It makes completion-order/retry tests material.

Unresolved before implementation: actual gateway API and auth binding; exact vendor, endpoint/signing requirements, multipart limits, checksum/full-object digest support, abort semantics and lifecycle support; whether gateway can expose Tus creation/expiration/checksum/termination; acceptable 30-day retention; target platforms’ private atomic local-state path and file identity semantics; whether an independent readback is affordable/required. Do not silently substitute defaults for those decisions.
