# Local-first reproducible notebook and data workspace

**Status:** research proposal for the brief and the D-V15-B applicability diagnostic. Public evidence is cited below; the evidence is not an instruction source. No repository was supplied or inspected. The issue/fix chain was discovered from public issue search during this task, so this work does not establish autonomous discovery from supplied artifacts. No full notebook application or runtime was built.

## Recommendation

Build a local project manager around ordinary folders, the standard `.ipynb` interchange format, one supported Python kernel, and an optional separate DuckDB SQL runner. Keep source data immutable and referenced by content identity. Put a versioned data contract and run manifest beside notebooks and transforms. Treat outputs from a shared interactive kernel as **unverified** until a clean replay succeeds. A clean replay should launch a fresh restricted process, record actual cell execution events, and associate each output with hashes of code, source data, contract and locked environment.

This is a product choice informed by three mechanisms: nbformat stores cells and outputs but leaves execution count nullable; nbclient replays cells in notebook order and can stop on cell errors; and DuckDB documents disk spilling for some larger-than-memory plans while explicitly describing operator limitations [S10, S12–S14]. The mechanisms are useful building blocks, not an integrated or qualified stack.

These are two independently maintained implementation precedents: Jupyter’s notebook document/client/kernel stack and DuckDB’s separate analytical engine/repository. DuckDB does not supply notebook replay, and nbclient does not supply an out-of-core relational engine. Their independence is at implementation and repository level, not proof of a tested combined product.

## Minimum workflow

| User action | Proposed behavior and persisted evidence |
|---|---|
| Create a project | Create project ID, format version, default paths, environment declaration, contract directory and run/cache directories. Do not copy data implicitly. |
| Import/identify data | Add a relative or absolute source reference, format and access mode. A full SHA-256 plus byte length is the identity for reproducibility. A quick size/mtime fingerprint is only a provisional identity and cannot produce a “current” result. Warn if referenced data is unavailable. |
| Inspect | Show file-level metadata, inferred schema and a bounded preview. Display the sampling method, sampled rows and whether parsing was partial. Label inferred types as hints until checked against a full scan or declared contract. |
| Author | Edit notebook cells, Python transforms, SQL transforms and small configuration files. Display order is notebook-array order; preserve stable cell IDs. |
| Run interactively | Keep a live kernel for exploration. Record run/session ID, kernel generation, submitted cell order and observed execution count, code hash, completion/error/interruption and output digest. Because prior state and undeclared inputs may affect a cell, label these results **unverified**. |
| Clean replay | Start a new kernel/process with the selected project revision, declared sources, locked environment and run parameters. Execute in displayed notebook order unless the user selects an explicit subset; for a subset, record actual order and mark results unverified if required predecessors were omitted. Show queued/running cell, progress, stdout/stderr and traceback. Cancellation sends interrupt, then terminates the worker after a bounded grace period; cancelled runs are not current. |
| Compare | Compare the saved run manifest with the latest clean run: changed cells, source/environment/contract hashes, output digests and bounded output previews. Digests establish byte-level equality only for canonicalized outputs. |
| Save and reopen elsewhere | Write an atomic project record/run manifest and output files; reopen from folder or portable bundle. Verify referenced-source and lock hashes. Missing data or packages yields a reproducibility gap state, not a successful replay. |
| Export | Export complete results to files with format/schema and row count where known, and include a compact manifest describing hashes, environment, execution and truncation. A notebook's visible table preview is never silently treated as the full export. |

## Data contract and larger inputs

**Product choice — schema contract.** Each imported source has a versioned contract: source format and encoding, column names and order where meaningful, logical type, required/nullable status, missing-field behavior, null-token policy, conversion rule (including timestamp format and timezone), and malformed-record policy. Record inferred schema separately from approved schema. A schema change is surfaced as a diff requiring an explicit contract update; a preview never certifies that no later row violates the contract.

**Product choice — preserve distinctions and identity.** Preserve absent fields separately from explicit nulls where the format permits; preserve raw value and parse error on conversion failure. Keep Unicode text intact. Heterogeneous values require an explicit tagged/union representation or an explicit string policy; do not silently coerce. A source-provided unique key is preferred for row identity. Otherwise use full source-content identity plus logical record ordinal, and state that the ordinal changes if the source is rewritten/reordered. For Parquet, file identity plus row ordinal only identifies a row within those exact file bytes and reader/schema interpretation. Input order is stable only when the source reader guarantees it; result ordering is guaranteed only by a declared sort with a unique tie-break key.

**Source fact and implication.** DuckDB’s pinned CSV docs say CSV lacks a schema and type detection uses sampling (default `sample_size` 20,480), while providing explicit `columns`, `all_varchar`, null controls, strict parsing, and reject storage options [S13]. The docs also say insertion order is preserved by default for CSV and can be disabled, in which case order is not guaranteed [S13]. Therefore, do not let automatic preview inference become the project's contract. Make explicit schema and null settings visible. Default to strict failure on malformed data. If the user opts into quarantine, retain raw rejected records and reasons in a separate artifact, report accepted/rejected counts, and mark downstream output incomplete; never quietly drop rows. Do not edit the original source.

**Memory and operation bounds.** The stated 5 GB-on-16 GB workstation target is an investigation target, not measured performance. Route scan/filter/projection and other supported streaming/batched transformations through bounded execution; in Python, expose batch iteration and make full materialization explicit. DuckDB documents temporary-disk spilling for larger-than-memory execution, but warns that multiple blocking operators can exhaust memory and names operators/aggregates such as `GROUP BY`, joins, sorts, windows, `list`, `string_agg` and `PIVOT` as cases needing care [S14]. Provide a configured scratch directory and disk budget. Detect unsupported plans/resource caps and fail with an actionable message or ask the user to choose a smaller input/operation; do not imply every global operation is out-of-core. Bound preview by rows and bytes, visibly mark truncation, and export full output separately.

## Execution state, provenance and invalidation

Displayed cell order, actual execution order and kernel state are different records. nbformat has an `execution_count` that may be null and output fields, but this does not record a complete execution history [S12]. nbclient's ordered replay is a suitable clean-run starting point; its error/timeout controls and sequential cell path are visible in the pinned source [S10]. Neither mechanism alone records source/environment identity or proves deterministic replay.

For every execution event, persist: run ID, notebook/cell ID and source hash, submitted order and actual start/finish order, execution count, stdout/stderr/error reference, output canonical digest, kernel generation, run mode (interactive/clean), process exit state and timestamps. Run manifest additionally records project revision, notebook hash, ordered cell hashes, source fingerprints and schemas, contract version/hash, lock hash, Python/kernel/client/engine versions, declared parameters, platform, cache inputs and output artifact hashes. Store an event log as append-only per run; atomically commit a final manifest only after output files are durable.

Visible output states are **current**, **stale**, **failed**, **unverified**, or **not run**. Only a successful clean replay whose full declared input hashes and environment/contract hashes still match can be current. A failed or cancelled run never refreshes a successful prior output; show the old result as stale/failed with its provenance. Interactive results are unverified, including after restart. Kernel restart increments generation and invalidates unverified state. If execution was interrupted or the save did not commit, leave prior saved artifacts with their old manifest and mark the attempted run incomplete.

Conservative invalidation rules:

- Editing a code cell invalidates that cell and following code-cell outputs because dependencies may be implicit in kernel state. An explicit DAG may narrow this only after dependencies are declared.
- Changing a source hash, source schema, contract, transform, runtime lock, engine version or relevant parameter invalidates every dependent result. If dependency discovery is incomplete, invalidate the whole notebook/project run.
- Changing display-only metadata need not invalidate computed values, but preserve the notebook file hash and classify the field in the policy.
- Never use mtime alone as a cache key. Cache key includes code/cell dependency hashes, full source identity, contract, environment, parameters and engine settings. Cache entries are content-addressed and written atomically; incomplete entries are ignored.

Use an exclusive per-notebook execution lock and project/environment lock. Detect external edits using the last-read file hash before writing; offer reload or save-as on conflict instead of overwriting. Save to a same-directory temporary file, flush/fsync, rename atomically, and write a commit record with checksums last. On recovery, verify the last committed generation and quarantine incomplete temp/run artifacts. These persistence mechanics are engineering choices requiring filesystem-specific validation.

## Security and support boundary

Notebook and transform code is untrusted. Run each clean replay in a separate process behind an OS-supported sandbox (container/namespace or equivalent platform boundary): read-only project/source mounts, private writable scratch, no access to home directories, host credentials or unrelated files; network disabled by default; CPU, memory, process count, wall-time, output and disk quotas. Use an allowlisted project environment prepared separately; no package installation from executing notebook code. An import blacklist is not a security boundary. Interactive kernels need the same restrictions, with user-visible limits and an explicit opt-in for any extra filesystem/network capability. This reduces convenience: notebooks that download data, read arbitrary local paths or install packages at runtime fail until the dependency/data is declared and provisioned. Sandbox strength and portability are critical dependencies to test per OS; this proposal does not assert a particular backend is already integrated.

Support one Python kernel family and a separately launched SQL engine. Do not build language kernels for this small team. SQL query results are artifacts with source hash, engine version, source identities, schema and query parameters; no implicit Python variables or kernel memory cross the boundary. A transform may exchange data only through declared file/table artifacts. Disable engine extension/network auto-install in the restricted worker unless explicitly provisioned. Credential storage and shared account profiles remain outside scope.

## Issue/fix/test chain and applicability verdict

The chain was discovered from `nbclient` issue search, not supplied by the task: issue `jupyter/nbclient#48` reports that a `CellExecutionError` from a notebook launched through IPython `%run` is displayed but does not fail the outer notebook pipeline [S01–S02]. The issue comments point to IPython PR #12301; PR metadata says it merged to IPython `master` as `c24e8af4bf631b51ddec077d13022aba00dcf30e`, on 2020-05-31, with 7.16 as milestone [S02–S03]. The diff changes `ExecutionMagics.run` to call `safe_execfile_ipy(filename, raise_exceptions=True)` and adds `TestMagicRunSimple.test_run_nb_error` [S04]. The 7.16.0 tagged source contains that call and the 7.16.0 tagged test asserts an exception for a failing notebook run through `%run`; the 7.15.0 tagged source still calls `safe_execfile_ipy(filename)` without the new flag [S06–S08]. PyPI confirms an IPython 7.16.0 release artifact was published, and its metadata records the later 7.16.3 security fix noted above [S09].

**Diagnostic result: the misleading/version-mismatched facet is assessed and present.** A plausible but incorrect reading is “nbclient fixed it” or “the merged fix applies to IPython 7.15.0.” The path is in IPython’s `%run` magic, and the tagged-source comparison shows the changed behavior in 7.16.0 but not 7.15.0. It is therefore a real version mismatch if a design/evaluation assumes the fix at 7.15.0. The test checks the direct `%run` case, not the full reported nested chain of multiple notebooks orchestrated by nbclient; that larger interaction remains uncertain. The captured PR diff and tagged source/test establish source-level behavior and release-tag applicability, not a rerun of a published wheel. This historical version is not recommended for use because the same 7.16 line needed a security fix [S09].

**Design consequence:** run notebooks through the explicitly selected clean replay client/kernel path and capture failures as run failures. Do not rely on notebook display output or `%run`-nested notebook execution to propagate status. If `%run` is allowed in interactive sessions, test propagation on every supported IPython pin and label the old nested chain as unsupported until qualified. This chain motivates precise execution status; it does not demonstrate a defect in nbclient’s ordered cell loop.

## Opportunity, alternative and limits

A useful opportunity is a local content-addressed cache keyed by source/contract/code/environment hashes. It can avoid repeat transforms, identify stale descendants and make project comparison fast; transparent cache provenance is required because a cache hit is only sound if every input is declared. A plausible alternative is to compose an external workflow/data-versioning runner around notebooks rather than maintain project-level run/invalidation logic. That may reduce orchestration code, but still needs per-cell status, sandboxing, notebook kernel support, portable source identity and recovery. It is an optional lead, not a requirement or established choice.
