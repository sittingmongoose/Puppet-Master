# Local-first notebook and data workspace: research proposal

**Research date:** 2026-10-05. This is a build plan, not a completed product or performance claim. Source facts, engineering inferences, product choices, the one executed check, and validation still proposed are labeled separately below.

## Recommendation

Build a local project coordinator around existing runtimes rather than implementing kernels or an SQL engine. Use `.ipynb` as the notebook interchange document, `nbclient` to run a clean notebook through a fresh Python kernel, and DuckDB’s Python library to scan CSV, NDJSON and Parquet files and execute optional `.sql` transforms. Keep provenance, execution events, data contracts, output status and cache lineage in a separate project manifest. Use Python as the only user kernel; expose SQL as a bounded DuckDB query/transform feature, not a second kernel family.

Candidate direct pins for the first implementation lock are CPython 3.12 (exact patch/build and platform image digest locked at release), `nbclient==0.11.0`, `nbformat==5.11.1`, and `duckdb==1.5.6`. Resolve and hash all transitive wheels and the matching `ipykernel`, `jupyter_client`, `jupyter_core`, `traitlets`, and `jupyter_server` or UI dependencies per supported platform before build. These package versions are sourced, but have not been installed or compatibility-tested here. `nbclient` 0.11.0 declares Python >=3.10 and dependencies including `jupyter-client>=7`, `jupyter-core>=5.4`, `nbformat>=5.2`, and `traitlets>=5.13`; DuckDB 1.5.6 declares Python >=3.10. An exact lock, not these lower bounds, is the environment identity [N8, D1].

Two independent implementation precedents contribute different mechanisms. Jupyter’s `nbclient` executes notebooks through managed kernels and its issue history exposes why polling kernel liveness matters when a process dies. DuckDB is a separate in-process analytical engine with file scanners, SQL, projection/filter pushdown, Parquet metadata, and bounded/streaming query paths. Neither precedent supplies the proposed project-level lineage and saved-output status model. The format, `nbformat`, is within Jupyter’s ecosystem and is treated as interchange rather than a third independent precedent [N2–N7, D2–D7].

## Evidence, inference and choices

### Notebook format and execution

**Source facts.** The notebook JSON format stores an ordered `cells` array, code source, outputs and an `execution_count` that may be an integer or null. Notebook metadata fields are optional and consumers may ignore them. A counter and saved output therefore cannot prove the order in which cells actually ran, which kernel state they saw, or that the output can be reproduced [F1]. Jupyter’s security documentation says access to a Jupyter Server permits arbitrary code execution; it documents authentication, not an OS sandbox [S1]. `nbclient` describes itself as a notebook execution library; `jupyter_client` manages kernels [N8].

**Engineering inference.** A notebook file alone cannot answer why a shared output differs. Display order, event order, kernel identity/state, source hashes and saved output need separate records. A clean replay should be an explicit transaction with a new kernel, recorded progress and a manifest.

**Product choice.** Keep `.ipynb` so analysts can exchange and edit notebooks in existing tools, but never encode the reproducibility claim only in notebook metadata. Use a sidecar execution manifest and append-only event records. Interactive execution stays exploratory: capture the cell hash, kernel ID, monotonic event sequence, start/end, outcome, inputs the coordinator observed, and output digest. Interactive output is **unverified** unless associated with a successful clean run and matching current hashes.

A clean replay starts a new kernel from the project’s selected locked environment and executes all code cells in visible order exactly once. The default first version does not cache notebook cells: Python globals, filesystem effects and hidden state make a cell dependency graph unsafe to infer. Users can still execute selected cells interactively in the current session. Clean replay reports each cell’s state, offers interrupt then worker termination on cancellation, and writes into a staging run directory. Preserve the previous completed run while a replay is running. Publish the new run only after all cells, outputs and manifest pass final hash checks. A failed or cancelled run sets its failing cell to **failed** and all possibly affected outputs to **stale**; prior bytes remain available for comparison. Kernel restart, edit, or interrupted execution can never leave the old output marked current.

Use four visible states with precise definitions: **current** means produced by the latest successful clean replay whose notebook, contract, source data and environment hashes still match; **stale** means a recorded dependency or relevant source changed, or the last run failed/interrupted after that output could have been affected; **failed** means the latest attempt for that cell failed (the last good bytes remain separately viewable as stale); **unverified** means an imported/saved output lacks matching run provenance or came from interactive state. If the coordinator cannot tell whether an input was read, show unverified and explain the missing declaration.

The clean replay guarantee is bounded: it can confirm that the declared notebook source, data identity and locked environment were replayed in a fresh kernel, with recorded event and output hashes, on the recorded supported runtime. It cannot guarantee bitwise-identical results when code uses randomness, clocks, threads, nondeterministic algorithms, undeclared files, platform-specific behavior, unpinned native libraries, or external services. Clean runs default to network off and declared project inputs only. If a user explicitly grants a capability, record it and downgrade the reproducibility claim to **environment recorded, external state not captured**. Output equality is a check, not proof that all semantic assumptions are correct.

### Source identity, schema contract and preview

**Source facts.** DuckDB’s current CSV reader can infer delimiter/header/types, but its documented CSV type-inference sample is finite (default 20,480 rows). Its JSON reader also samples for automatic type inference (default 20,480 objects); a missing JSON key becomes `NULL` in the resulting table. The Parquet reader supports schema inspection, projection/filter pushdown, and an optional per-file row number. These facilities help query larger files, but a preview or sniffed sample does not establish a full-input invariant [D2, D4, D5]. DuckDB’s CSV documentation makes `ignore_errors` and storing rejects explicit options; its rejects record file, line and byte positions. With ignore enabled malformed records can be skipped, and projection pushdown can affect which conversion errors are encountered [D3].

**Engineering inference.** Automatic inference is useful for discovery, but silent sample-based type decisions can produce different imports when later rows contain heterogeneous values. A table with nulls alone also cannot distinguish “key absent” from “key present with null.” The raw source and a versioned contract must survive normalization.

**Product choice.** The import flow records a reference to the original file(s) by normalized path/URI, size, last-modified hint, format/options, and a streaming SHA-256 content digest. Do not copy a large source by default; user can explicitly create a portable bundle with selected data. Size and mtime only accelerate a “possibly changed” prompt; content hash establishes identity. For a directory/glob record a sorted file list and each file’s content hash. Do not mutate source files.

After bounded preview, let the user confirm a versioned schema contract with field name and position/field ID, source and normalized types, required/nullable, explicit conversion, locale/encoding, date/time format and timezone policy, decimal and null-token policy, and whether source order or a business key defines row identity. Keep original text or raw-record reference for conversions where loss matters. Preserve Unicode code points as read; do not normalize strings implicitly. Convert timestamps only with explicit timezone assumptions. For NDJSON preserve key presence separately from value-nullness (for example, a presence bit per field or raw JSON record sidecar); DuckDB’s table scan alone maps both to null. A schema change such as a new optional field creates a proposed contract version and warning; missing required fields or incompatible narrowing/conversion fails until reviewed. If one field has heterogeneous values, keep it as text/JSON or require an explicit variant mapping instead of guessing a lossy type.

Assign source row identity at ingestion: stable primary key if supplied and validated; otherwise `(source-file-hash, source-record-ordinal)` for CSV/NDJSON and `(file-hash, Parquet file_row_number)` for Parquet. Keep identity through one-to-one transforms. Joins, aggregations and deduplication must declare how they construct or discard identity. A source ordinal is an audit key, not a semantic business key. Preserve raw source order only when an explicit ordinal is carried. For result order, require `ORDER BY` over a unique deterministic tie-break key to promise a stable sequence. DuckDB documents that joins, group-by, whole-table aggregates, and even `ORDER BY` do not promise original order or a stable sorting algorithm; without such a key compare results as unordered rows/multisets [D6, D7].

The preview is a clearly labeled bounded sample (initially up to 500 rows / 1 MiB, whichever comes first), with sample method, selected columns, file/row range and schema-inference scope shown. No preview result is described as a whole-dataset guarantee. Full checks such as null counts or uniqueness are explicit full scans with progress and cancel. Import errors default to fail-fast with file/record/byte location and no published normalized result. An opt-in repair flow writes a separately identified rejects artifact retaining raw malformed lines and reasons; records are never silently deleted or rewritten in place. Reject policies and count are part of the contract/run manifest. This is stricter than DuckDB’s optional skip behavior by design [D3].

### Data engine, SQL and workstation limits

Use DuckDB’s pinned Python library for common file scans, schema inspection, projections, filters and notebook SQL transforms. It is an independent engine and supports CSV, JSON, Parquet and SQL; the project version is selected as `duckdb==1.5.6`, published 2026-09-28 per PyPI. Its own project description claims larger-than-memory analytical workloads. Treat that as a vendor capability statement, not proof that every operation on a 5 GB file fits this 8-core/16 GB target [D1, D2, D4–D7].

The optional SQL workflow is `.sql` text executed in an isolated DuckDB connection in the same worker, with the same data references, environment, resource limits and run manifest as a Python transform. It is not a SQL kernel or server. Disable extension install/load and network access by default. Keep multi-statement transforms to a declared supported subset and explain transaction boundaries. Colleagues may use any SQL client on exported CSV/Parquet; a project-private DuckDB database file is a cache/output, not the source of truth. Do not promise compatibility with arbitrary external SQL engines.

For inputs around 5 GB, use file scans/column projection and streaming cursor/fetch batches; spill eligible operators into a bounded per-project scratch area. Never convert the full result into pandas or a single notebook cell implicitly. Offer a separate full materialization action with required free-space estimate and cancellation. Global sorts, high-cardinality grouping, exact distinct, unsupported readers, object sizes beyond limits or operations that cannot spill must report a resource estimate/limit and either use a separately configured larger bound or fail visibly. Large results are saved as an artifact (Parquet or CSV) while cells display at most 500 rows/1 MiB with an explicit truncation badge and export link. Caches are derived and keyed by source content hashes, contract version, transform/code hashes, exact lock hash, engine/runtime build and relevant options; invalidate descendants on change. Disable caching for undeclared side effects and notebook cells. Set worker CPU/memory/disk quotas with room for the UI and OS; the 5 GB scenario remains a target for measurement, not an achieved performance result.

### Project record, provenance, sharing and recovery

Portable project layout (illustrative):

```text
study/
  project.json                 # project ID, schema version, runtime profile
  notebooks/*.ipynb
  transforms/*.sql
  src/*.py
  data/refs.json               # external/local source references + identities
  environment/lock-*.txt       # per platform, hashes and runtime image digest
  .workspace/runs/<run-id>/    # manifest.json, events.jsonl, output artifacts
  .workspace/cache/            # disposable, lineage-keyed derived data
```

`project.json` records project ID/schema version, relative paths, runtime profile, contract versions, limits, and links to last complete run. Each execution event records run ID, cell ID, display index, observed execution sequence, code hash, kernel/process identity, start/end timestamps, status, input refs, output artifact hashes, bounded stdout/stderr and errors. A run manifest records source identities, notebook/script/SQL hashes, full environment lock and platform digest, engine and runtime versions, capability grants, contract and schema versions, execution events, output hashes, truncation flags, row counts/schema, and whether all checks completed. Exclude secrets and private account credentials. Reopen on another machine by validating the lock and data hash: if the file is missing, moved or hash differs, offer relink/recompute and keep outputs **unverified** until clean replay. A small share/export bundle can include notebook, lock, manifests, scripts, and optionally selected data/results. Otherwise ordinary folders remain the exchange mechanism.

Project input changes, lock changes, contract changes or any notebook code edit invalidate notebook clean outputs conservatively (all outputs in that notebook until replay) because Python cell dependencies are not statically reliable. A declared SQL/data transform DAG invalidates only the changed node and downstream nodes. A data reference hash change invalidates all descendants. A markdown-only edit can preserve code outputs but marks the notebook document hash changed in provenance. The UI shows saved-versus-current manifest fields and output comparisons (schema, row count, hashes, and a bounded keyed row diff); equal hashes prove byte equality only for those artifacts. Never overwrite the last successful result with partial outputs from a running or failed replay.

Use a single-writer per-project lock with lock owner, host and process metadata. For local filesystems, acquire an OS advisory lock; if lock status is ambiguous (notably a network/sync folder), open read-only or require a local working copy. Stage every save under a temporary run directory, flush files, write a checksummed manifest last, then atomically rename the completed directory and update a small current-run pointer. On startup, verify the pointer and artifact hashes; mark orphaned staging runs interrupted and retain the previous complete run. Add crash-injection tests for failures before/after manifest and rename. Folder exchange and portable bundles are minimum; concurrent editing, cloud sync conflict resolution and real-time collaboration are not.

### Execution boundary and support boundary

Notebook code is arbitrary code. Use separate worker processes for interactive and clean kernels; give each a per-run sandbox. Phase one should make the OS-enforced boundary explicit and testable on Linux: non-root worker, isolated mount namespace, project source/data read-only, dedicated scratch/output paths writable, empty/minimal environment, no host home/config mounts, no inherited credentials, network namespace off, CPU/memory/process/disk quotas, and a hard cancel/kill path. Candidate mechanisms include rootless OCI or bubblewrap plus cgroups; select only after platform tests. Do not claim an import blacklist is isolation. The UI can request a named capability (network or external path) only with explanation; record the grant and downgrade provenance. The brief excludes secrets, private data and shared account profiles. For other desktop OSes, do not represent an unsandboxed kernel as safe for untrusted notebooks; either defer untrusted execution or label and gate a trusted-project mode until an OS sandbox has been validated. Sandbox usability costs include slower starts, explicit project file grants, no package download or network calls in the run, and possible incompatibility with GPU/native access. Provision packages before execution through a trusted environment manager, outside the notebook worker.

Support CPython notebooks and project Python scripts first. Optional SQL is DuckDB SQL in the same worker with matching lineage and permissions; users needing PostgreSQL dialects, persistent server sessions, extension-provided file types, or other kernels export ordinary tables/files and use their existing client outside the workspace. Do not build a kernel per language. This matches the team’s Python-first workflow and makes the lock/provenance boundary reviewable.

## Consequential issue/fix/test chain and applicability diagnostic

The candidate-discovered failure chain is `nbclient` issue [N1] → merged PR [N3, N4] → regression test. Issue #88 reports a client waiting indefinitely after a local kernel subprocess is killed (reported against old 0.2/0.4-era versions; the report includes an OOM/container context but is not a candidate reproduction). In comments, the reporter distinguishes this from execution timeout: a timeout may kill a healthy long-running kernel. PR #90 (“Check if kernel is alive during cell execution”) merged to `master` on 2020-07-10 as `9750d9198084bd1324e679cf936f8a09ae12f057`. It adds periodic kernel-liveness polling and a self-terminating `Autokill.ipynb` regression case asserting execution raises a runtime error [N2–N4].

**Applicability result: version-mismatched historical chain found and bounded.** It would be misleading to cite merged PR #90 or its regression test as evidence that `nbclient==0.4.0` has the behavior: the exact v0.4.0 source has no liveness polling task and its test tree lacks `test_kernel_death_during_execution`; the corresponding polling code appears in v0.5.0. The selected v0.11.0 tag contains both polling and `test_kernel_death_during_execution` [N5–N7]. This supports applying the narrow local subprocess-death behavior to 0.11.0, not backporting it to 0.4.0. Test scope is a local kernel process that deliberately terminates itself and the client raises; it does not establish behavior for cgroup OOM timing, remote Jupyter Gateway kernels, full worker containment, or correct notebook results. The original issue is a user report, not a separately reproduced benchmark. The consequence is to pin a release with the code/test chain and still add our own cancellation/OOM/worker tests before claiming robust recovery.

A still-open follow-up PR [L1] describes remote Gateway `status: dead` messages being filtered during IOPub polling. Its captured patch handles that message before parent-message filtering; it was open and the files response showed no regression test. This is a useful lead, not a released fix: the proposal deliberately supports local kernels first and leaves remote Gateway execution outside scope.

## Minimum workflow coverage

1. Create a folder project; choose locked Python profile and add notebook/script/SQL files.
2. Reference/import CSV, NDJSON or Parquet without copying; hash and inspect format/schema; confirm a versioned contract.
3. View a labeled bounded preview; author a notebook or transform; run selected cells interactively in visible current-kernel state.
4. Request clean replay; monitor progress, errors and cancellation; view output statuses and compare its manifest to the prior run.
5. Save/reopen on this or another machine; validate sources and lock; relink missing sources explicitly; never call unassociated outputs current.
6. Export result tables/artifacts plus compact JSON reproducibility manifest and portable folder/bundle.

## Checks and validation status

**Executed by candidate (isolated component check only).** A pure-Python synthetic check (code/input and receipts are in `out/research/witnesses.json`) preserved source order/ordinal, Unicode, and a `value_present` bit distinguishing absent from explicit null; it rejected a string-to-number type mismatch with a row-specific error and confirmed the input object was unchanged. The runner returned exit 0 with the expected JSON output. An earlier harness attempt returned exit 1 because my assertion expected two source ordinals for three records; the input, code hash and failure are retained. This validates only the candidate-authored in-memory rule. It does not exercise DuckDB, an NDJSON parser, notebook execution, large files, hashing, filesystem recovery or the product.

**Proposed / UNEXECUTED product validation.** (1) Replay fixture notebook where cell display order differs from interactive event order; verify clean run uses fresh kernel and documented visible order, then edit an upstream cell, source hash and lock independently and assert status invalidation. (2) Kill local kernel during cell and during output polling, cancel a long cell, force OOM/resource quota, restart kernel, and ensure prior results are retained stale/failed rather than current. (3) Import synthetic CSV/NDJSON/Parquet with null, absent field, Unicode, timestamp offsets, heterogeneous values, malformed record late in file, duplicate rows and schema evolution; compare full-scan and bounded-preview claims, row identities, reject artifact and no-source-mutation. (4) On ordinary 8-core/16 GB Linux, run 5 GB CSV/NDJSON/Parquet query scenarios with projection/filter, aggregates, sorts and oversized results; record peak RSS, spill bytes, wall time, cancellation, stable ordering and failure thresholds. (5) Crash at each save phase; race two writers on local and sync/network folders; test lock recovery and no partial current pointer. (6) Validate Linux sandbox filesystem/network/resource denial with adversarial notebook fixtures; separately prove any supported macOS/Windows sandbox before extending untrusted execution. These checks are not run in this research and no 5 GB performance, full sandbox or cross-machine replay result is claimed.

## Opportunity and alternative

**Opportunity:** a provenance comparison can explain *which* of data hash, schema contract, cell source, environment lock or output artifact changed and offer one-click replay from a prior manifest. This makes a shared folder a lightweight reproducibility record without hosted service or real-time collaboration.

**Plausible alternative:** start with ordinary JupyterLab and its existing notebook UI, adding a small project CLI for data contracts, manifests and clean replay. That reduces UI build work and keeps analysts in a familiar application. It also leaves the team to reconcile Jupyter’s live kernel state and saved outputs with the external project manifest, and makes per-output current/stale feedback less integrated. Prefer the local coordinator for the initial product only if a thin viewer can preserve `.ipynb` interoperability and the team values integrated status over using stock JupyterLab.
