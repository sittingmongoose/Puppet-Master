# Local-first notebook and data workspace proposal

## Recommendation and support boundary

Build a folder-based desktop workspace around the existing Jupyter notebook format and Python kernel protocol, with `nbclient` for clean replay and embedded DuckDB as the tabular scan/SQL engine. Support Python notebooks and Python transforms, plus SQL transforms executed by DuckDB. Do not build a general kernel platform. A SQL transform is a product-owned DuckDB operation, not an arbitrary Jupyter SQL kernel. This covers the three Python analysts and gives their SQL colleague portable `.sql` files and familiar SQL without making the team maintain another kernel family.

The mechanisms come from independent projects: Jupyter's packages define notebook documents and kernel-message execution [S1–S3]; DuckDB contributes a separate in-process SQL and file-scanning engine [S8–S11]. Either mechanism remains independently useful without the other. `nbdime` is a third, complementary precedent for notebook-aware content diffs [S13]. The brief does not establish that any existing whole-product workspace meets the team's requirements.

Use `.ipynb` as the editable interchange document. Its JSON/schema format stores cells, execution counts, and outputs, but is not a record of all kernel history or proof that an output can be reproduced [S1]. Store authoritative run provenance in a sidecar manifest and event log, with a small notebook metadata link for portability. An imported notebook without a matching manifest opens normally, but its outputs start **unverified**.

The source sweep supports selecting mechanisms, not shipping them as an integrated product. Pin a compatible Python, `notebook`/`ipykernel`, `nbclient`, `jupyter_client`, DuckDB, and UI dependency set per project. The `jupyter_client` changelog records the reply fix in 8.0.2 [S7]; use 8.0.2 as a provisional compatibility floor, then lock and test a concrete compatible set. Do not infer that the floor alone fixes every notebook path. Use `pyproject.toml`, `uv.lock`, and a pinned Python version to create/sync a project environment: uv documents lock checking against project metadata and a locked mode that errors when it is outdated [S12]. A lock does not pin the operating system, native libraries, environment variables, undeclared files, or external services, so record those too and report platform differences.

## Product workflow

1. **Create a project.** Make an ordinary folder containing a small project descriptor, `pyproject.toml`, `uv.lock`, `.python-version`, `notebooks/`, `transforms/`, `artifacts/`, and `.workspace/`. The descriptor records project ID, allowed data references, schemas, limits, kernel and SQL engine identifiers, locale/timezone defaults, and output policy. Folder copying, version control, and an optional zip bundle are the sharing mechanisms. Do not include credentials. Private data is included only when an analyst explicitly chooses it for a bundle.
2. **Import and identify data.** Prefer a read-only reference to a source file. Record its relative or user-relinked path, format, size, modification metadata, and a streaming SHA-256 content digest. Size/mtime can cheaply detect likely changes, but a replay that needs a strong identity recomputes the content hash. Explicit “make portable copy” creates a separate copy; never rewrite the original. Missing path or changed content blocks replay or requests relinking and hash confirmation.
3. **Review schema and preview.** Parse CSV, newline-delimited JSON, or Parquet through DuckDB. Show a bounded preview by row count and bytes, the sample method, detected schema, and a visible “sample only; does not establish a full-file property” label. DuckDB CSV detection estimates dialect and types and allows explicit overrides [S8, S15]. Therefore inferred types are suggestions; the user confirms a schema contract before a reusable transform is treated as checked. Record header/delimiter/quote/escape/encoding, null markers, expected columns, logical and physical types, nullable/missing semantics, timestamp format/timezone, conversion rules, and schema-contract version. On later imports, report added/removed columns, type drift, nullability changes, and parse changes; invalidate affected results pending explicit acceptance.
4. **Author and run.** Open a Python notebook or edit `.py`/`.sql` transforms. A project-owned dependency graph records declared source and transform edges; notebook dependencies are conservatively implicit unless explicitly declared. Interactive runs keep a live kernel and show progress, cell start/finish, stdout/stderr, traceback and cancellation. Running an edited cell in a live kernel marks later cell outputs stale because earlier variables and side effects may be hidden state. A kernel restart, lost connection, or interruption leaves prior saved outputs visible but unverified/stale until a successful clean replay.
5. **Request clean replay.** Create a fresh kernel and run cells in notebook document order, in a clean environment matching the project lock and policy. `nbclient` exposes per-cell execution, timeouts and lifecycle/error hooks useful for the event stream [S2]. Stop at the first error by default; identify cell and traceback, allow cancellation, and keep prior committed artifacts. An explicitly chosen “continue after errors” mode may be useful for diagnosis, but cannot publish a run as a successful complete result. Stage outputs in a temporary run directory. Commit only on success by atomically replacing a small pointer to a complete immutable run directory; interrupted replay never overwrites the last committed result.
6. **Compare, save, reopen, export.** Compare the saved manifest with current source, schema, transform, code, environment, and policy fingerprints. Show changed input, changed code, old/new schema, run order and output status. Save `.ipynb` plus manifest/event log; export full data results as Parquet or CSV, with row count, schema, ordering declaration and checksum. On another machine, resolve the folder or bundle, recreate the locked environment where supported, verify data hashes, and show explicit missing-data/platform differences. A result with unmatched identity remains unverified; do not silently point at a same-named but different file.

## Data contract and large inputs

**External evidence.** DuckDB documents CSV auto-detection and explicit options [S8, S15], separate policies for malformed rows including detailed errors and explicit storage/skipping controls [S9], Python-to-SQL conversion rules [S11], and workload trade-offs that can require memory or relax insertion-order preservation [S10]. These are engine capabilities and cautions, not claims about our UI or 5 GB performance.

**Product contract.** Preserve source bytes and never silently drop a malformed record. Default parse or cast behavior is fail-fast with file, logical record number, column, rejected value (redacted where configured), and expected type. Do not turn a failed cast into NULL. An explicit quarantine action may create a separate rejects artifact with raw record and reason, count accepted/rejected rows, and mark the result partial; it never alters the source or masquerades as a complete clean run. Keep field absence distinct from explicit JSON null. Preserve original strings and Unicode; timestamp conversion requires declared format and timezone behavior, with ambiguous/nonexistent local times surfaced. Heterogeneous fields need an explicit union/variant, JSON, or string policy rather than an unreviewed coercion.

Give each input row a lineage identity: source content digest plus logical record ordinal, unless the project contract supplies a validated unique source key. Keep this identity through supported transforms; joins derive a composite lineage key or retain parent IDs. Order is unspecified for relations without a complete `ORDER BY`. A stable exported order requires ordering by a unique stable key, with lineage ID as a tie-breaker. Never infer stability from a preview, physical file order, `execution_count`, or an engine setting.

The target is an 8-core, 16 GB workstation with a 5 GB input. For scans, projections, filters, and streamable transforms, keep bounded batches and avoid loading the full file into a Python dataframe/list. Return bounded row/byte previews and spillable columnar intermediate files. Truncate large displayed outputs with an explicit row/byte count and a link to the full artifact; do not truncate the exported result without saying so. Operations requiring a global sort, exact distinct, large join, or aggregation may exceed RAM/disk limits; estimate where possible, enforce explicit spill/disk quotas, and fail with an actionable limit message rather than claim universal streaming. **This is a design target, not a verified benchmark.** Validate CSV, NDJSON, and Parquet separately, including malformed and schema-drift fixtures; measure peak RSS, temporary disk, throughput, and cancellation on 5 GB generated files, plus adversarial high-cardinality sort/join cases. Do not advertise the target until those measurements pass on the supported OS and pinned engine set.

## Kernel state, provenance, and freshness

Notebook cell-array order is display/document order. Execution counts and saved outputs are cell-local document fields; they are useful clues, not a durable event history [S1]. In a live session, the workspace records actual start/finish order, cell ID and source hash, run ID, session/kernel ID, result/error, and timestamps. The current kernel state is reported only for that live kernel and is never inferred from saved output. A fresh replay establishes a new event history and output association.

Each committed manifest contains project and notebook IDs; notebook format/version; ordered cell IDs/source hashes; run mode and run ID; actual execution sequence; input paths/format/content digests/schema contracts; transform and parameter hashes; `pyproject.toml` and lock digests; exact Python, kernel, `jupyter_client`, `nbclient`, DuckDB and OS/architecture versions; locale/timezone and engine settings; declared random seeds; sandbox policy and capabilities; per-cell status and output MIME/artifact digests; export hashes, row counts, and ordering; plus warnings for nondeterministic or external dependencies. The append-only event log holds progress and failures. Keep large outputs as immutable artifacts, not in the manifest. `.ipynb` outputs are a display copy linked by cell ID, source hash and run ID; they are not the provenance source of truth.

Use these visible statuses with text and icons (never color alone):

- **Current:** a committed successful run matches the active tracked code, schema, input, environment, policy and parameter fingerprints. This says “no tracked change since this run,” not “mathematical determinism proven.”
- **Stale:** a tracked dependency changed, or an interactive upstream cell was edited/rerun. Keep the last successful output inspectable with its old run identity.
- **Failed:** the most recent requested execution failed or was cancelled. Show the error and preserve prior output as an older run; do not display it as the failed run's result.
- **Unverified:** imported/legacy output has no matching manifest, the kernel was restarted/interrupted, or required provenance is unavailable. A clean run with deliberately granted external access can complete but carries a qualification and is not called hermetically reproducible.

Conservative invalidation is deliberate because ordinary notebook variables and side effects make static dependency inference incomplete. Any code cell edit invalidates that cell and later cells in the notebook; any live rerun does the same for following cells. Changed source hash or schema invalidates every declared descendant, and conservatively every notebook cell if the notebook has undeclared data access. Lockfile, Python/engine, OS-relevant native runtime, or execution-policy change invalidates all code outputs and caches. Changed export parameters invalidate dependent outputs. Cache only explicitly declared, side-effect-free transforms keyed by source/code/schema/parameter/environment/policy hashes; do not cache arbitrary notebook cells. A cache hit is an optimization, not a clean replay, and its source key must be visible.

## Runtime boundary, files, and recovery

Notebook code is untrusted. Run the long-lived interactive kernel and each clean replay in a supervised OS sandbox, separate from the UI/coordinator. For the initial implementation, choose a Linux backend only after verifying its namespace, filesystem, network and resource controls on supported installations. Mount the selected project inputs and runtime read-only; expose a dedicated run scratch/output directory read-write; hide user home, unrelated project siblings, credential stores, host environment secrets and other files; deny network by default; enforce CPU time, memory, process count, wall time and scratch-disk quotas; bound cell execution time; and terminate the worker on cancel (interrupt, grace period, then kill). A permission grant is narrow, visible, recorded in the manifest, and invalidates replay equivalence. The sandbox is an OS enforcement dependency that this research has not implemented or security-tested. If preflight cannot enforce the policy, disable “untrusted clean replay”; an optional user-trusted unsandboxed session must be clearly labeled as such. Import blacklists are not an isolation boundary. macOS/Windows execution is out of MVP until an equivalent backend passes the same tests.

The UI must stay responsive while a worker runs. Stream status/events with accessible text and keyboard control; support interrupt and hard cancel; preserve traceback and partial diagnostic outputs without committing them as successful. A process restart invalidates live-kernel state. Store immutable run directories and use a same-filesystem temporary write, flush, atomic rename and commit-pointer swap for manifests/results. On reopen, select the last complete committed generation and verify checksums; incomplete staging directories are recoverable diagnostics and never current results. Use an OS file lock plus owner/run metadata to prevent two writers committing to one project. If locking semantics on a network share cannot be established, allow read-only access and require one writer; do not promise concurrent shared-folder editing.

## Useful opportunity and bounded alternative

**Opportunity:** offer notebook-aware saved/current diff using an `nbdime`-like presentation: compare source by cell, outputs by MIME/data, collapse large base64 images, and suppress execution counters when only generated metadata changed [S13]. MVP can begin with a compact manifest/schema/output digest diff and link to the established tool; a polished semantic diff is optional. This directly helps answer “why did the result change?” without adding collaboration infrastructure.

**Alternative:** evaluate Polars lazy/streaming execution against DuckDB for Python-centric transform authoring [S14]. Keep DuckDB as the initial SQL interchange engine because the colleague needs SQL. Polars is a plausible substitute or optional Python library, not a guaranteed streaming path for every operator; verify supported operators, memory behavior, type semantics, ordering, and cross-platform package lock before choosing it. Real-time collaboration, hosted execution, automatic scheduling, and more language kernels remain later opportunities.

## Validation and promise boundary

**Executed by candidate:** the isolated synthetic witness catalogued in `witnesses.json` checks a tiny standard-library NDJSON contract: Unicode preservation, absent versus explicit-null fields, stable row IDs for identical bytes, strict timestamp error location, and unchanged source bytes. The receipt shows exit 0 and the actual stdout/stderr. It tests candidate-authored component code only; it does not exercise DuckDB, notebook execution, UI, sandbox enforcement, complete dataset identity, large inputs, or replay in another environment.

**Proposed / UNEXECUTED validation:** (1) implement a disposable Linux worker and demonstrate denied reads outside declared mounts, denied network, capped CPU/RAM/PIDs/disk, timeout, graceful and forced cancel, and cleanup after kernel death; threat-model filesystem races and child processes; (2) exercise two notebooks with deliberately out-of-order interactive cells, restart, edited upstream cells, changed source/schema/lock, failure and cancellation; assert status and manifest transitions; (3) use representative generated 5 GB CSV, NDJSON, and Parquet data plus malformed/schema-evolving variants; record RSS, spill, output hashes, row identities, and ordered/unordered behavior; (4) close, copy/bundle, reopen on a second clean machine, verify data relinking, lock recreation, checksums, diff, and export; (5) crash at each save phase and prove recovery selects only a complete generation; (6) run the actual `jupyter_client`/`nbclient` locked compatibility matrix, including the 8.0.2 fix path and current supported releases. These checks are not claimed to have run.

A clean replay can promise: a fresh kernel ran the recorded cells in recorded order, under the recorded declared local inputs, schema, lock, runtime, and policy; the workspace captured its events, errors, and output fingerprints. It cannot promise identical values when code is nondeterministic, accesses unpinned packages or undeclared files, observes current time/randomness, depends on external services or platform libraries, or uses a non-deterministic/global-order operation. Make those limits visible in the provenance view and export manifest.
