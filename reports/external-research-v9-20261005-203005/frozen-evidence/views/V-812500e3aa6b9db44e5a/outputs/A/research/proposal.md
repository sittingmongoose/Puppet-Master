# Proposal: a local, calibration-aware image review workspace

**Scope.** A research review/annotation tool for six people working on personal machines and exchanging closed project bundles. It is not a diagnostic product. This is a plan for an incremental implementation, not evidence that the proposed stack has been integrated or benchmarked.

## Recommendation

Build a small Qt desktop app around the napari viewer/layer model, with source readers kept behind a narrow adapter and a project-owned SQLite database for metadata, vector annotations, tiled mask data, display state, provenance and undo history. Keep image samples in their original files and open supported inputs read-only. Use tifffile’s Zarr-backed TIFF access for qualified OME-TIFF inputs and native Zarr chunk access for OME-Zarr 0.5 inputs. Export standardized integer masks as OME-Zarr labels only when the geometry and calibration are exactly representable; export vectors as a coordinate-explicit CSV table plus a machine-readable sidecar.

This is a bounded proposal, not an assertion of end-to-end behavior. Napari, tifffile and OME-NGFF are independent precedents: napari contributes a viewer coordinate chain and tested label-editing mechanisms; tifffile contributes TIFF metadata/segment reads through Zarr; OME-NGFF contributes an interchange contract. None supplies the project’s identity, transaction, annotation-scope or export-audit behavior by itself. [S1–S3]

## What the evidence says

**External facts.** OME-NGFF 0.5.2 describes images with 2–5 dimensions, names and types axes, requires the array dimension names to match, and applies listed coordinate transforms sequentially. Its multiscale image transform list is constrained to scale and translation. Its `labels` group describes integer-valued pixel annotations and permits a label dimension to match the image or be singleton when irrelevant. Its `omero` channel/window display metadata is explicitly transitional. [S1]

Tifffile 2026.9.20 documents OME-TIFF and many TIFF-like readers; it can expose TIFF segments/pages/subIFDs and pyramid levels as Zarr-backed arrays. Its examples read a region from a tiled pyramid through `return_as='zarr'`. Its memory-map example explicitly excludes compression and tiling, and its notes describe TIFF subsets and unsupported/partially supported features. This is a reader opportunity, not proof that every 3 GB TIFF stays bounded or that vendor metadata is complete. [S2]

Napari 0.8.0’s `Layer` source defines an affine transform chain (`tile2data`, `data2physical`, `physical2world`), units, axis labels, scale, translation, rotation, shear and an affine. Its cache parameter is documented as applying currently only to Dask arrays. It is a useful view model, not a project persistence format. [S3]

A consequential failure/fix chain is visible in napari’s public history. Issue #8939 reports a Dask-backed Zarr v3 label layer that opens but fails during polygon painting with `NotImplementedError: Don't yet support nd fancy indexing` in Dask. A maintainer comment points to PR #8636. That merged PR closes #8939 and refactors label painting to use boolean masks and bounding boxes so writes/replay use basic slicing on the backend. Its added tests include Dask-backed paint plus undo/redo and Zarr/TensorStore polygon paths. Napari 0.8.0 release notes include #8636 and describe painting into Zarr, Dask and TensorStore arrays. The merge commit reported by the PR is `63b1239ab53dedc4e40b934ee79fd18e4147dd83`. This establishes applicability to the released code path, not performance on our images. The tests in the diff do not establish the exact original Dask polygon gesture as a one-for-one regression test; no test suite was run for this proposal. [S4–S8]

Bio-Formats 8.5.0 documents over 140 formats, but its support table rates pixel, metadata, utility, export, multi-image and pyramid support separately. Its release includes a 53,843,906-byte `bioformats_package.jar` asset. It is a plausible compatibility alternative, but its breadth does not imply uniform metadata fidelity or bounded behavior for this app. [S9–S10]

SQLite documents atomic transactions and a WAL mode that supports same-host reader/writer concurrency but does not work over a network filesystem. It also documents the online backup API as a way to create a consistent snapshot, incrementally and with progress reporting. These are useful mechanisms, with filesystem durability assumptions and local-vs-network constraints that the app must respect. [S11–S13]

**Engineering inference.** The 3 GB target is plausible for compressed tiled TIFFs and chunked Zarr if the app requests bounded regions and caps its own caches. The cited sources do not prove the target. NGFF 0.5 is insufficient as the sole project geometry model because its multiscale transform rules do not express arbitrary rotation, shear or general affine correction. Its raster labels also do not define the app’s point/polygon scope semantics. Preserve a richer internal transform and annotation model, then gate standards exports on faithful representability.

**Product choices.** Begin with a strict format boundary and explicit imports. Keep original bytes immutable. Use one local SQLite project database to make vector edits, mask-tile edits, display settings, provenance and undo/redo transactional together. Save masks as sparse, independently compressed 2D tiles keyed by image/frame/layer/time/channel/z/y/x; absent tiles mean background. Present only current planes/regions to the viewer and update the viewer’s display from the committed project state. Do not rely on the viewer’s serialization as the project format.

## Minimum workflow and supported boundary

1. **Create project.** Create a project UUID, schema version, current revision and source/annotation tables. Use a local working copy. A shared-storage copy is a closed exchange artifact, not a simultaneously edited database.
2. **Import without rewrite.** Accept local OME-Zarr 0.5 stores and OME-TIFF/TIFF series that the pinned reader parses into a supported, unambiguous axis mapping. Open source bytes read-only. Store the raw metadata document/bytes, reader name/version, exact source path, series, dimensions, dtype, reported axes, parsed calibration and import timestamp. Record any normalization separately from the source metadata.
3. **Inspect and resolve.** Show source axes/order, type, units, extent, orientation, origin, sampling, channel/time layout, dtype and provenance. If an axis or calibration is missing, conflicting or unknown, preserve it as reported and show an explicit mapping/correction form. Require the user to choose axis role/order and physical values/units or proceed in pixel/unknown units. Store the original and correction as separate records with author/time; never overwrite instrument metadata or silently guess.
4. **Navigate and display.** Read the selected T/C/Z planes or viewport tiles lazily. Keep channel selection, order, LUT/color, contrast window, gamma, opacity, current time/slice and display-only transforms in project state. Label these as display settings; they never rewrite sample data. Show data coordinates and world coordinates together. Give cancel/progress for read, hash and conversion operations.
5. **Annotate.** Store points and polygon vertices as continuous coordinates in a named source-image sample frame; store masks as integer label values on the source grid. Bind every object to immutable source identity and frame ID. Record scope explicitly: slice, timepoint, volume, or whole acquisition, plus any channel selector. Persist style ID and a copy/version of style settings. Each completed gesture is one undoable durable transaction; persist inverse tile/geometry edits for undo/redo after reopen.
6. **Save/reopen.** A committed project database is the authority. Close and back it up through SQLite’s backup API into a temporary destination, validate schema and content checksums, then publish a versioned bundle. Reopen by schema migration in a transaction or read-only with a clear “newer project version” error; never partially mutate a project during failed migration.
7. **Export.** Export a normalized annotation table (and optional image-grid mask overlay), a small derived image and a sidecar manifest. Build outputs under temporary names, validate their checksums and metadata, then publish. Do not change the original asset.
8. **Verify.** Compare source hash before/after; compare raw samples in the derived crop with its declared source window when no resampling was chosen; verify mask IDs and annotation coordinates on reopen; show every baked/display/geometric operation in the export report.

**Supported input v1:** OME-Zarr 0.5.2 local directory/store when the array is 2–5D, axes are understood, and the installed Zarr/codecs support the encountered store; plus OME-TIFF and ordinary TIFF series through tifffile only when tested series/axis/calibration mapping is unambiguous and region access is available. Limit canonical mapping to spatial X/Y or Z/Y/X with optional one time and one channel axis. Preserve unknown axis names, but require user resolution before annotation/export. Approve only tested integer and floating dtypes/codecs in a fixture matrix. Do not claim all OME-TIFF, all TIFF-like vendor formats, proprietary containers, multi-file acquisition folders, non-affine calibration or arbitrary dimensions. A failed import leaves the project and source untouched, records the attempted path and a legible error, and offers a reader/version diagnostic or a separate explicit conversion route.

## Coordinate, identity and provenance contract

For each source series, preserve `source_axes` exactly as reported and store the explicit `array_axes` permutation. Define image-sample index coordinates as zero-based with integer values at voxel/pixel centers. For example, if array order is Z,Y,X, the stored vector is `[z,y,x]`; the app displays both `[z,y,x]` and user-oriented `[x,y,z]`. Store time/channel as discrete indices with separate physical time units where known.

Each frame has a stable `frame_id`, an invertible 4×4 double-precision matrix mapping source sample-center X,Y,Z coordinates to physical X,Y,Z and explicit units/handedness. Also store the permutation between this matrix order and array order, origin, transform provenance and the exact effective matrix. If no calibration is supplied, identify the world unit as unknown or pixel; do not label it µm. Convert a display click to source coordinates by applying the inverse of the view/display transforms and then the inverse physical mapping. Persist geometry in its source sample frame; physical values in exports are derived through the bound matrix. A resampled/cropped/reoriented derivative gets a new asset/frame ID and an operation record; annotation remapping must explicitly compose the source and target transforms.

Each source is identified by SHA-256 of exact file bytes, or a deterministic sorted path-plus-content digest for a multi-file or directory dataset. Compute this in a cancellable background step before claiming verified identity. Store path(s), size, mtime, series and digest. On reopen, a missing external path retains metadata and annotations but is visibly unavailable; relocation matches the full digest, not filename alone. A changed digest requires explicit “new source” or “relink to matching source” choice. The optional portable bundle copies the original byte-for-byte and costs storage/copy time; reference mode stays small but depends on the external source remaining available and unchanged.

## Architecture and persistence

Use a Qt shell with napari 0.8.0 for image planes, channel layers, coordinate display and existing vector-edit interactions; isolate import, calibration and persistence in app-owned services. Feed image arrays from a read-only OME-Zarr reader or tifffile’s Zarr-backed TIFF store; never call full-series `asarray()` on large sources. Use an app-owned bounded LRU cache (initial proposed budget: 1 GiB decoded/view arrays, with a smaller separately measured mask-tile cache), limited prefetch, cancellable workers and generation IDs so a late result cannot replace the currently selected slice. Napari’s own cache alone is insufficient as a policy because the cited layer doc scopes it to Dask. [S2–S3]

Store the project in SQLite: project/schema/revision; assets and raw metadata; axis mappings and frame matrices; display profiles; annotation rows and vertices; compressed sparse mask tiles; styles; operation provenance; durable undo/redo patches; export records. Store exact dtype, tile extent, codec, label-value-to-annotation mapping and checksum with mask tiles. Keep only changed tiles and the current view in memory. Store immutable source data outside the database unless the portable bundle option is selected.

Use a local WAL database for short atomic user-gesture transactions, with `synchronous=FULL` for durability unless the measured latency experiment supports another explicitly documented choice. Checkpoint at a controlled idle/close point. WAL and shared-memory side files are part of live state; never copy only the main DB file while open. For a bundle, make an online-backup snapshot, validate it, copy any selected assets, write a manifest, and publish a new version only after all parts pass checksums. A crash during one SQLite transaction should leave either its old or new committed state. A crash during bundle creation leaves the previous bundle and a removable/incomplete temporary version. SQLite documents filesystem assumptions and WAL’s same-host restriction; test the actual workstation filesystem. Do not edit WAL databases directly on the shared network storage. [S11–S13]

## Export promises

The table contains one annotation row and zero or more ordered vertex rows with project/annotation/image IDs, source digest, frame ID, geometry type, scope, T/C/Z applicability, sample-index coordinates, physical coordinates and units, style ID, label and any lossy conversion. The sidecar records source-series identity, raw-to-normalized axis mapping, matrix, operations, interpolation, writer/library version, array dtype/shape and exactly which settings were baked. CSV vectors preserve coordinates but do not render them; do not label them GeoJSON unless the output meets that standard’s coordinate contract.

An OME-NGFF 0.5.2 labels overlay is offered only for integer masks whose dimensions, scale levels and scale/translation transforms match the target image. Preserve color and label-value mapping. If an arbitrary affine cannot be represented, either perform an explicit reorientation/resampling that creates a new derived image and remapped mask, with interpolation and checksums recorded, or decline standardized overlay export and provide the project/table in its exact source frame. [S1]

A “small derived image” export offers a data crop in the original dtype and sample values where no resampling was requested, with axis/calibration metadata only when the writer can represent them. A separate rendered preview can bake channel colors and contrast into RGB, clearly labeled as display output rather than original samples. Any geometric transform/resampling is a distinct derivative operation with source and output hashes, parameters, axis/matrix changes, interpolation and software version. Tifffile’s OME-TIFF writing example supports an implementation lead, but all exact metadata-preservation claims remain to be validated. [S2]

## Opportunity, alternative and staged validation

**Opportunity.** Reusable mask annotations can be exported in OME-NGFF’s standardized integer `labels` hierarchy, enabling compatible tools to discover colors/properties and relate a mask to its image. Keep points/polygons and scope fields in the richer table because the cited labels contract is for integer pixels. Tifffile’s region-backed access may also let the group review tiled TIFF without conversion; validate instead of assuming. [S1–S2]

**Alternative.** If real instrument data fall outside the tifffile boundary, offer an opt-in Bio-Formats 8.5.0 reader or offline conversion worker that writes a separate OME-Zarr derivative, logs its reader version and all metadata changes, and never replaces the source. Its broad format list is useful, while its own per-format support ratings and Java package size argue against promising all formats in the small baseline. A narrower all-native viewer without napari is another option only if the Napari UI/packaging test fails; it would forfeit a ready coordinate/layer model and require building accessibility and interaction behavior anew.

**Proposed validation (not yet run).** On ordinary 8-core/16-GB Windows, macOS and Linux machines: measure peak RSS, decoded bytes, cache occupancy, random slice/ROI latency and cancellation on a real 3 GB tiled/compressed OME-TIFF and chunked OME-Zarr, including a 3D Z/Y/X + C/T sample. Set a proposed acceptance cap of 4 GiB application RSS and ≤1 GiB decoded/view cache, confirm no source mutation, and exercise cache eviction/cancel during reads. Inject process termination during import, each SQLite commit boundary and each export stage; reopen and verify latest committed data and previous published bundle. Move a closed bundle to another machine, relocate an external source with matching hash, and test mismatch rejection. Test marker/polygon/mask coordinates under permutation, anisotropic spacing, translation, flip and explicit resampling; compare CSV and label exports against source-frame fixtures. Test successful PNG/RGB display rendering separately from raw sample crop. Capture all outputs, versions and error/progress responsiveness. These are acceptance proposals, not component-source claims.

## Numeric witness and limitations

A candidate-authored isolated Python calculation used array-order axes Z,Y,X; index `[4,7,11]`; scale `[2,0.5,0.5]`; translation `[3,10,20]`. Sequential scale then translation gives physical Z,Y,X `[11,13.5,25.5] µm`, user X,Y,Z `[25.5,13.5,11] µm`, and the inverse recovers the input index. The check executed successfully and is recorded in `witnesses.json`. It verifies only the arithmetic convention used in this example; it does not execute NGFF, napari, a reader, an exporter or an application. The 3 GB, cross-machine, save/recovery and export assertions above remain proposed/UNEXECUTED.
