# Biomedical image review workspace: staged proposal

**Basis and scope.** This is a brief-only proposal for six researchers exchanging closed project bundles through ordinary shared storage. It does not claim autonomous discovery or full application behavior. Recommendations distinguish **Source fact**, **Engineering inference**, **Product choice**, and **Proposed validation (UNEXECUTED)**. Citations `[S#]` resolve to pinned captures and exact locators in `sources.json`.

## Recommendation

**Product choice.** Start with a Python/Qt desktop shell using napari 0.9.2 as the image-view and interactive layer component, a separately versioned Bio-Formats 8.5.0 reader adapter for only a qualified set of formats, and an application-owned project layer (manifest plus transactional SQLite metadata/annotation store). Keep the reader behind a narrow interface so an adapter can be replaced per format. Run reader calls in a worker; validate whether an out-of-process Java helper is worth its packaging and per-call overhead before selecting that deployment detail. Pin all shipped components and format policy. Do not make the project's durable state depend on transient viewer objects.

**Source fact.** napari's layer transform and units model maps data coordinates into rendered world coordinates, and its docs describe deriving scale/units from xarray coordinates [S2]. It has layer workflows for points, including visible slice and keyboard operations [S18], and its Dask tutorial gives concrete examples where a lazy-looking wrapper still reads an entire file or a reshape triggers hundreds of reads [S3]. Bio-Formats 8.5.0's `IFormatReader` API exposes region calls (`openBytes`/`openPlane`) and reports dimension order/certainty and contributing files [S6]. These are useful mechanisms, not evidence that a particular codec is bounded-memory or responsive. napari and QuPath are independently useful precedents: separately maintained codebases and GUI architectures (Python layer viewer vs Java/JavaFX pathology workflow) contribute different mechanisms. QuPath documents projects, path relocation and source-preserving display orientation [S7]; its format support is intentionally qualified and differs by image family [S8].

**Engineering inference.** Keeping viewer, reader and project responsibilities separate makes format-specific failures and coordinate conversions testable. A region API is necessary but not sufficient for bounded access: a codec can decompress an entire strip or plane internally. napari's Dask examples are a warning to test the actual access graph rather than equate delayed execution with a memory bound [S3, S6].

## Minimum user workflow

1. **Create a project.** Create an app-owned project directory with a versioned manifest, SQLite database, `derived/`, and `staging/`. Choose **reference** (leave large source in place) or **copy into bundle** (byte-preserving file copy). Never write to the input. Show this choice and storage estimate.
2. **Import and inspect.** Probe in a cancellable worker. Display reader, format, series, detected axes and order, sample type, channel count, image dimensions, calibration, orientation, contributing files, raw metadata and any inferred/uncertain values. Save an import-attempt record before expensive work. Unknown or ambiguous axes/calibration produce a visible unresolved state and a correction screen; keep the original metadata and proposed correction side by side. Do not silently guess, flatten or rewrite. A failed/partial import remains in the project as failed or needs-attention and can be retried or removed without affecting source bytes.
3. **View and navigate.** Show named axes and axis order explicitly. Select channels, time, slice/volume view, and per-channel display mapping (window/level, lookup table, gamma if later supported). Persist display settings separately from sample data. Never normalize or rewrite original samples to change display. Keep a visible `source`/`derived` indicator and show effective calibration versus original metadata.
4. **Annotate.** Enable points and polygons in a selected plane/frame, explicit 3D shapes only in a volume placement mode, and masks in a label layer. Provide reusable named styles, keyboard-operable add/select/pan/slice/time/channel navigation, undo/redo for every geometry/property edit, and a visible current coordinate/scope readout. Do not permit a 2D point tool to guess depth from the screen when the viewer is in 3D; the napari 0.4.15 repair chain shows a real 2D-layer/3D-mode interaction was handled by disabling point add mode [S10–S15].
5. **Save, close and relocate.** Commit edits in a database transaction; show dirty/saved state. Close and reopen from a closed bundle on another machine. If an external source path is missing, allow explicit relocation by matching full content fingerprint and reader series, then record the new path; a matching basename alone is insufficient. If hash differs, preserve the annotation/project and block source-dependent export until the researcher explicitly rebinds and the new binding is recorded.
6. **Export and verify.** Preview a report of included and lost information before writing an annotation table, rendered overlay, or small derived crop/resample. Stage output, validate it, then publish it as a completed export; preserve a prior good output on failure. Report coordinate origin/order/units, source identity, transform, selected channels/slice/time, whether geometry was rasterized, label-overlap policy, sample conversion, and all omitted properties. Reopen/import the output in a clean project and compare against the saved source project.

## Data and coordinate contract

**Product choice.** The project format is authoritative; the viewer layer state is an editable presentation. Every source has stable project-local `source_id`, byte length, full SHA-256 when hashing finishes, source locator(s), reader/reader version, selected series, raw metadata blob (immutable), interpreted metadata, import warnings, import options, and provenance timestamps. Multi-file readers list each contributor. Source identity is content-based plus series, not pathname-based. Hash asynchronously in bounded buffers; until complete mark identity `pending`, and do not claim a verified portable bundle.

Every axis has a name, type (`space`, `time`, `channel`, or explicitly `unknown`), position in the stored array, length, unit, and coordinate mapping. Store both raw reader axis metadata and a reviewed mapping. Canonical app order is `t,c,z,y,x`; the import adapter must explicitly map file order to it. Do not reorder raw data just to satisfy the viewer. For irregular time points store a coordinate vector; channels have stable IDs and names where known. Unknown axes block annotation/export until the user chooses a mapping or explicitly retains the input as view-only.

Spatial coordinates in the project are zero-based sample-index coordinates `(z,y,x)` (or `(y,x)`), with an explicit convention that an integer names a sample center. Store a full-precision 4×4 spatial index-to-physical affine `p = A i + b` in named physical units, plus axis permutation/flip and orientation labels. The import adapter translates source convention into this canonical convention and records the exact conversion. Keep raw metadata and effective reviewed transform separately. Display pan/zoom, window/level, slice/time/channel selection and screen-to-world transforms are view state, never baked into annotation geometry. OME-NGFF 0.4 supplies an interoperable precedent for ordered scale/translation coordinate transforms and explicit axis metadata, but its cited multiscales model is not a general arbitrary affine contract [S1 §3.3–3.4].

Each annotation has UUID, source/series ID and hash binding, geometry type, vertices/points or mask asset, stored coordinate space, coordinate order, scope (`plane_frame`, `volume`, or `acquisition`), explicit fixed time/channel/slice selectors where applicable, style ID and style snapshot, class/label, properties, author, creation/edit times, and history reference. A plane annotation contains its fixed plane and axis selectors; a volume annotation includes all three spatial indices; an acquisition-level note may have no geometry, while any acquisition-level geometry still declares its spatial domain. Masks retain label IDs, axis selectors, shape/chunk metadata and source transform. Version coordinate conventions and schema migrations; never infer 3D depth from 2D screen position. Annotation geometry remains anchored to the original source. A geometric transform/resampling creates a new derived image resource with input IDs/hashes, operation, affine, interpolation, software/version, output hash and calibration. If annotations are migrated, record an explicit separate operation and keep their original geometry recoverable.

A tiny arithmetic check was executed by the candidate against the declared scale-then-translation rule; it maps an example `(t,c,z,y,x)` index to physical coordinates and back. It verifies only this arithmetic example, not OME reader behavior, napari transforms or app serialization [W1].

## Components, limits and failure behavior

**Format boundary for v1.** Qualify OME-TIFF single-file 2D/3D fixtures first, including XY/Z plus channel/time where unambiguous, integer and floating samples, calibration, orientation and subregion reads. Add an instrument format only after representative files from each supported reader path pass the matrix below. Bio-Formats is a family of readers; its broad reader API and project documentation do not guarantee every format variant [S5, S6]. Keep the first matrix small enough for six people to reproduce. QuPath's own docs report distinct format paths and limitations, including OpenSlide's 2D 8-bit RGB boundary, which is a useful warning against a universal-support claim [S8].

An unsupported, corrupt, ambiguous or unexpectedly costly file yields a durable import warning and retains the original input, raw metadata and any already completed project work. It must never silently drop axes or substitute guessed calibration. The user can retry with an explicit reader option, map axes/calibration, keep it view-only, or cancel/remove the failed source record. The project remains openable and export of unaffected images remains available.

**Large-data target.** Use true plane/ROI access through `openBytes`/`openPlane` where the qualified reader supports it; expose bounded chunks to the viewer. Do not wrap a whole-file `imread` in a delayed task and call that bounded. Start with an LRU cache capped at 512 MiB and at most two in-flight display requests per source; show progress and check cancellation between reader calls. Cancellation latency is bounded by the current decode call only if the codec returns; disclose an unresponsive call as such. Report decode errors and progress in the UI; move work off the GUI thread. napari documents yielding worker patterns with abort/pause/resume events [S4], but that is not proof a codec can be interrupted mid-call. The stated 3 GB source and 16 GB workstation are acceptance targets, not established capability.

**Project saves and shared storage.** Store annotations, settings and operations in SQLite. For an active working copy, use short transactions and keep a recoverable previous snapshot; stage derived assets, flush/verify, then update the database reference. Use conservative rollback-journal operation for the local active project unless tested otherwise. SQLite's atomic-commit guarantees depend on filesystem, locking and fsync assumptions [S16]. Do not edit a live WAL-mode project on ordinary shared storage: SQLite documents that WAL requires all processes on one host and does not work over a network filesystem [S17]. Researchers exchange closed, versioned snapshots: copy to a `.part` location, verify hashes/database integrity, then publish a complete snapshot while retaining the previous version. Same-volume rename is a candidate commit mechanism, not a guarantee on every shared filesystem; test the group's actual storage. On reopening an incomplete snapshot, recover the last verified version and offer staged files for retry or discard.

References save disk space and keep the original untouched, but require path relocation and source identity checks. Portable bundles copy bytes and are easier to move but cost up to the source size and can be slow; offer this choice per source, never silently duplicate 3 GB in memory. Do not put the team's only active project on a network filesystem with untested locking semantics.

## Exports, accessibility and optional work

Annotation table: CSV for broad inspection plus a JSON sidecar with schema version, axis names/order, pixel-center convention, source ID/hash/series, scope/selectors, physical affine, units and style/label properties. Add GeoJSON only as an explicitly lossy interchange option: QuPath documents top-left full-resolution pixel coordinates and warns of different conventions elsewhere; ellipses become polygons, and raster labels can lose overlaps depending on export mode [S9]. Overlay PNG is a rendered view with sidecar and burned-in or separately reported display settings; it is not source samples. A label image has one class per pixel unless separate overlapping masks are exported. A derived image records crop/resample/rotation and sample conversion; preserve float/integer type when requested, and identify any lossy cast or interpolation.

Keyboard operation must cover core navigation, selection, annotation creation, undo/redo, save and cancel; every action also has a discoverable visible control. Metadata and errors use legible text, copyable details, clear unresolved status, and do not depend on color alone. Add large type/contrast/theme checks and screen-reader labels for controls during usability review.

**Later opportunities, not minimum obligations.** Add OME-NGFF/Zarr as a derived, chunked portable data option after coordinate and chunk access validation; OME-NGFF 0.4 makes axes and scale/translation explicit and is a plausible exchange route, but adds storage/metadata compatibility work [S1]. Keep useful leads open in `leads.json`: pyramidal slide support, remote/object storage, registration, automated segmentation, plugin integrations, richer measurement/statistics, and live collaboration. Each needs a separate user need and resource estimate. For mostly 2D pyramidal pathology slides, QuPath is a plausible ready-made alternative to building on napari; its projects, annotations and relocation workflow are informative, but its documented format constraints and domain focus do not cover this group's multiaxis microscopy needs [S7–S9].

## Proposed validation and release gates (all UNEXECUTED)

1. **Format/axes:** Freeze public or consented tiny fixtures from each proposed instrument. Inspect reported vs known axis order, channel/time counts, integer/float dtype, physical scale/origin/orientation and all files contributed. Exercise ambiguous/unknown axes correction and reopen; raw metadata must remain byte-for-byte available. A reader that guesses order without signaling uncertainty is view-only until resolved.
2. **Bounded reads and responsiveness:** Use an actual 3 GB representative file with a checksum before/after. Trace requested bytes/planes and peak aggregate RSS; switch slices/channels quickly, cancel during a delayed read, and record progress/error behavior. Proposed starting gates: cache <=512 MiB, no full-source-sized allocation, aggregate application/reader RSS <=6 GiB on the 16 GB test workstation, and cancellation at the first boundary after an in-progress decode returns. If a reader violates gates, exclude that format or use a verified pyramid/derived proxy; do not describe it as supported.
3. **Coordinates and annotations:** Use asymmetric calibrated synthetic data (non-square pixels, nonzero origin, axis permutation/flip) with known landmarks. Save points/polygons/masks at plane/time, volume and acquisition scopes; close/reopen on a second workstation; check displayed, stored and physical coordinates and export round trips. Test 2D placement in 3D mode and reject ambiguous depth; test affine and resampled derived data separately.
4. **Non-destructive display and transforms:** Hash source before/after window/level, channel, slice, and display changes; prove no change. Run one recorded geometric resampling and verify source hash stays fixed, output hash and affine are recorded, and annotation migration requires explicit action. Include float samples and contrast without normalization.
5. **Recovery and export:** Inject process termination during import, DB transaction, asset staging, export write and final publish. Reopen the most recent good snapshot; prove no partial export appears complete. Test network share copy/publish on the group's actual filesystem and cross-machine relocation. Compare CSV/sidecar, overlay and derived crop/resample to project state; report exact losses including overlap and coordinate conventions.
6. **Usability/accessibility:** Keyboard-only complete workflow, undo/redo after reopen, style reuse, readable metadata/error feedback, focus order, high contrast and non-color-only status. Review with researchers, including one new to the supported format.

The only executed check here is W1; all application, format, memory, durability, export and usability claims remain proposed validation rather than witnessed behavior.
