# Local calibrated annotation workspace: current proposal

**Stage:** D-V06-A, complete author rewrite from the supplied frozen proposal and captures. **Scope:** a research review tool, not a diagnostic system. This result uses supplied sources and does not claim autonomous source discovery. Source IDs resolve to pinned captures in `sources.json`; W4 is a candidate-authored isolated component check in `witnesses.json`.

## Recommendation

Build a local desktop project workspace with a small authoritative project store, read-only source access, an explicit per-image coordinate frame, and a separate view state. Start with a Python/Qt shell using napari as a replaceable image-canvas prototype; own project persistence, import decisions, coordinate conversion, provenance, and export in the application. Napari documentation describes lazy NumPy-like image layers, contrast settings that affect visualization rather than source values, multiscale levels, layer units, and shape layers [S2–S4]. These are useful architecture precedents, not evidence that a particular pinned napari release meets this brief. Before adoption, pin a release and run the validation below. If its editing or interaction model cannot meet the contract, keep the reader and project interfaces and replace the canvas.

Use tifffile as the first bounded reader for a deliberately narrow, version-pinned TIFF subset; do not treat its broad format list as our support promise [S5]. Use OME-NGFF 0.5 as a geometry vocabulary and a possible derived-image interchange format, not as the native project database [S1]. QuPath provides a separate, useful precedent for project entries, image references, relocation, and explicit export conventions [S12–S14]. These projects address different layers: NGFF specifies a data format, tifffile reads TIFF data, napari is a viewer, and QuPath documents project and export workflows.

## Evidence-backed findings and limits

- **OME-NGFF 0.5 [FACT, S1].** The pinned specification describes 2–5 dimensional arrays, named axes, and per-resolution coordinate transforms. In the multiscales mapping, scale and optional translation are applied in list order; translation follows scale. It restricts this transform vocabulary to scale and translation. This is a useful constrained interchange model, but it does not express every orientation or affine that the workspace may need. OME-Zarr 0.5 uses Zarr v3. Do not claim an arbitrary affine can be losslessly represented in NGFF 0.5 multiscales.
- **napari docs [FACT, S2–S4].** The captured docs say contrast limits affect visualization rather than the underlying image values; image layers accept lazy array-like objects; layer scale/units map data to world coordinates; shapes use vertex arrays with per-shape properties. The docs also describe limits, including costly automatic contrast on large data and constrained 3D shape editing. The docs are from a moving `main` branch captured 2026-10-05, not a release pin; implementation and performance remain to be tested.
- **tifffile [FACT, S5–S6].** The captured README describes strip/tile/page/SubIFD and pyramid access, Zarr-backed access, and memory mapping for some contiguous data. It also lists unsupported TIFF features and vendor quirks. This supports prototyping bounded reads for tested TIFF layouts only; it does not prove 3 GB latency, memory use, or support for any team's instrument files. The README capture delivered 32,768 of 32,898 bytes; cited examples and notes are within the supplied capture, but its tail was not captured.
- **QuPath [FACT, S12–S14].** Its 0.7.0 docs describe JSON project entries with reader/URI information and entry IDs, per-entry data, and per-machine project copies as a shared-drive relocation pattern. Its annotation export page says its shape exports use pixel units and an origin at the top-left of the full-resolution image, and warns this can differ from other tools. It does not specify in that statement whether integer coordinates identify sample centers or pixel edges. Therefore it supports documenting an export convention; it does **not** establish equivalence with the convention proposed below. The changelog also records real relocation, write recovery, calibration, downsample, and export-information failures across releases [S12].

### Issue → fix → regression test: tifffile #319

The issue report gives a reproducible TVIPS `PixelSizeX` change: tifffile 2026.2.20 returned `1.4208036661148071`; 2026.2.24 returned `1.4208036661148072e-09` [S7]. The subsequent changelog and release commit `503cb4eb74dd28a6acc36a0e4624ba9c2001e021` identify v2026.3.3 and “Do not convert TVIPS pixel sizes to m (#319)” [S6, S10]. This establishes a concrete report, corrective code, regression assertions, and release association. The fix commit message itself is generic; linkage is established by code comment, test, changelog, and sequence, not a pull-request record. The test uses a TVIPS fixture described in the supplied record as unavailable in the public repository. The chain supports pinning reader versions and testing calibration semantics; it does not prove all TVIPS files or all intermediate package versions behave alike. In particular, the captures establish the reported 2026.2.20 and 2026.2.24 outputs and the v2026.3.3 correction, not a complete exhaustive version matrix.

## Workflow and architecture

1. **Create/import.** Create a project with a schema version and stable project ID. Import registers an image read-only; it never rewrites the original. An import job is provisional until the reader has identified series, shape, dtype, axes, metadata, and an explicit calibration decision. Store original metadata bytes where practical alongside parsed values, parser name/version, series selection, and any user correction. A cancelled or failed import remains unresolved or is discarded; annotations and existing project state remain available.
2. **Inspect.** Show file identity, path/URI, format and reader version, dimensions, axis order, sample type, physical units, and provenance. Present competing or ambiguous metadata values side by side. Do not silently infer spatial axes or units. The user can select a supported mapping, choose pixel-only/uncalibrated work, or leave the source unresolved. Preserve the source metadata and the selected interpretation.
3. **Navigate/display.** Read visible tiles/chunks and cache them under a bounded memory budget. Channel selection, LUT, window/level, slice, time, zoom, and pan are view state, not source writes or geometric data operations. Disable automatic whole-image min/max scans by default for large images; show progress and permit cancellation.
4. **Annotate.** Store vector geometry and masks with the image identity and coordinate-frame ID. Scope is explicit: a plane annotation includes the relevant z/t indices; a volume annotation includes its time scope if any; an acquisition annotation is not silently tied to the currently displayed slice. Reusable named styles and keyboard-operable tools use a command-based undo/redo history.
5. **Save/reopen.** Save a recoverable project snapshot. On another machine, resolve reference paths by hash and explicit user relocation; never silently attach annotations to changed bytes. A project containing only references is small but requires sources to remain available. An optional portable bundle copies selected sources only after an explicit size/storage choice.
6. **Export/verify.** Export an annotation table, an overlay/label image, and a small derived image as distinct generated files with a manifest. The manifest states source identity, frame ID, coordinate convention, units, axes, any geometric operation, rendering/window settings if baked in, output dtype/shape, and known metadata loss. The user can compare the recorded source hash and operation chain and can tell which outputs contain original samples, labels, or display-mapped pixels.

**Components.** A read-only reader service provides region reads and reports progress/cancellation. A frame service owns axis mappings and pixel-index-to-physical conversion. The view controller owns presentation state. The annotation store owns vector records and tiled integer masks; the operation log records corrections and derived-image operations. The exporter writes into temporary output paths, validates the results, then publishes a complete export set and manifest. No component writes through to source files.

**First support boundary (product choice, subject to fixtures).** Accept local classic TIFF/BigTIFF and OME-TIFF with a tested set of grayscale integer and floating samples and only the compression/layout combinations present in the team's fixture suite; start with uncompressed, LZW, and Deflate where the pinned reader and codecs pass those fixtures. Admit ImageJ hyperstack TIFF only after separate axis/calibration tests. Do not advertise CZI, NDPI/BIF/whole-slide stitching, OJPEG, chroma-subsampled data, arbitrary vendor metadata, arbitrary dimensions, or all compression codecs. Unsupported, malformed, or ambiguous inputs produce a readable project record with the reason and original metadata, remain unresolved, and do not block other images in the project. New formats require sample fixtures, axis/calibration tests, and bounded-read measurements. Local OME-Zarr may be evaluated as a later reader; do not infer support from the specification alone.

## Coordinate and calibration contract

**Product choice.** One convention is authoritative: annotations use continuous **sample-index coordinates**, with index `(0,0,0)` at the center of the first stored sample. The vector coordinate order is explicitly `x,y,z`, regardless of file array order. A 2D image omits z; a volume has z. Channel and time are non-spatial axes represented by names and scoped indices, not hidden in vector order. Cursor readout shows sample-index coordinates and, when calibrated, physical coordinates with units.

Each source series has a frame record containing: ordered stored array axes and their names/types; shape and dtype; selected image/series identity; the original calibration metadata; the accepted interpretation; spatial units; and a finite 4×4 `index_xyz_center_to_world` homogeneous matrix using column vectors. It maps `[x_index,y_index,z_index,1]` to named physical `[X,Y,Z]` coordinates. The matrix convention, row/column meaning, units, and frame ID are persisted. Axis permutation, flip, origin, scale, and supported oblique orientation are represented by this matrix. A calibration or axis correction creates a new recorded frame/operation; it does not edit the source metadata. Reject singular/invalid matrices and unsupported dimensional mappings. W4 demonstrates only arithmetic for one such mapping; it is not evidence of an application implementation.

For example, a candidate frame maps index `(4,3,2)` to `(99.25,202,304) µm` under the explicit matrix exercised in W4. For a missing or disputed calibration, users may explicitly proceed in pixel-only coordinates; physical readouts and calibrated exports remain disabled until resolved. Do not call unknown calibration “1 µm per pixel.” Keep NGFF axes/scale/translation as a compatible subset; an NGFF export is permitted only if the stored mapping can be represented without loss, otherwise preserve the full matrix in a sidecar-capable format or refuse that export.

This convention corrects the seed draft's loose phrase “origin at pixel (0,0) corner.” QuPath's documented top-left/full-resolution convention is recorded as a separate external convention [S13]. An adapter must not assume the half-pixel relationship: establish it with a known marker/pixel test for each target tool/format and write the conversion into the export manifest. Until that test passes, export our stated sample-index convention and label it clearly.

## Identity, storage, and operations

A source record has stable ID, selected series, original URI/path, byte size, streaming SHA-256, observed metadata, reader/version, import policy, and status. Hashing is streamed and cancellable, but a full 3 GB identity hash costs I/O; size/mtime alone is only a relocation hint, not proof of identity. On reopen or relink, compare content hash before automatic relinking. A mismatch stays unresolved until an explicit user decision; acceptance creates a new source identity and marks attached annotations as needing review.

Store project metadata, source records, annotation records/masks, view state, and immutable operation/provenance records in a versioned project directory. Use per-user path maps for machine-specific roots and project-relative paths for deliberately bundled sources. Bundle contents are explicit; do not automatically duplicate a large external source. Projects are exchanged as snapshots through shared storage. Concurrent multi-writer editing/merge is outside v1; use a visible single-writer lock or make an opened snapshot read-only when a writer is active.

**Recovery design (choice, not yet verified).** Save to a new generation in a temporary sibling directory on the same filesystem, flush file data and directory metadata where supported, validate the generation, rename it into place, then atomically replace a small `HEAD`/commit-marker file. Retain the prior committed generation. On open, use only the generation named by a valid commit marker; if the latest marker/generation is invalid, offer the last valid generation and report recovery. This avoids treating a collection of independently replaced JSON files as one transaction. Export similarly writes all components to a staging directory and publishes the manifest only after all output files validate. The POSIX `rename(2)` documentation describes atomic replacement and `EXDEV` across filesystems, and warns that an NFS failure does not prove the rename did not happen [S15]. It does not establish equivalent behavior for the group's actual SMB/NFS setup or every desktop OS. Test on the real share; do not claim power-loss durability until tested. W3 from the frozen seed is only a local exception-before-replace component check.

A geometric transform/resampling operation creates a derived identity and records parent hash/frame, operation parameters and matrix, interpolation, software/version, output axes/shape/dtype, and output hash. It never changes original samples. Display window/level is not such an operation. Derived-image annotations attach to the derived frame or are explicitly transformed with a provenance record; no implicit carryover.

## Annotation and export contract

An annotation record includes stable annotation ID, source content ID, image/series ID, frame ID, kind (`point`, `polygon`, or mask reference), named spatial coordinates or mask geometry, scope, style ID, labels, timestamps/author, and operation history. Store coordinates and matrix coefficients as binary64 round-trip-safe JSON numbers; validate finiteness and dimension. Masks are integer-valued, tiled/chunked label data with their own frame and scope, not display screenshots. The renderer supports per-slice and volume semantics explicitly. Editing operations (create, delete, move, vertex change, style application, correction) are undoable and redoable; persist a compact snapshot plus a journal so close/reopen does not discard the intended history. Named styles contain color, line/fill, width and ordering; no color-only meaning.

CSV table export includes one row per point/vertex with annotation ID, vertex order, sample-index coordinates, optional physical coordinates and units, scope, frame/source IDs and hashes. Use a decimal representation that round-trips binary64 in the selected parser; the importer/exporter must test this rather than assume every spreadsheet preserves it. The label overlay records pixel grid, frame, label mapping, rasterization and overlap order; raster labels cannot preserve arbitrary overlapping vector objects or style detail. The small derived image states whether it is raw-value crop/resample or display-rendered pixels. PNG is suitable for a rendered preview, not a promise to preserve original integer/float samples; a typed TIFF/OME-TIFF can be considered only after tested metadata writing. Every export includes a sidecar manifest. Nothing claims that external tools honor custom microscopy coordinates from CSV/GeoJSON; interoperability needs target-specific tests. The QuPath docs themselves call out origin/unit differences and lossy ellipse-to-polygon conversion for its GeoJSON path [S13].

## Opportunity, alternative, assumptions, and validation

**Opportunity.** Exporting eligible derived rasters as OME-Zarr 0.5 could make axes, scale/translation, and label arrays consumable by compatible bioimaging tools [S1]. This is conditional on the affine being representable, Zarr writer compatibility, and round-trip fixtures; otherwise retain an explicit sidecar. It is not a v1 dependency.

**Plausible alternative.** QuPath is a credible alternative if whole-slide imaging and its project/annotation workflows become the dominant need. Its 0.7.0 documentation and changelog show useful project, relocation, and export precedents [S12–S14]; it is not assumed to cover this group's 3D/time-series annotation contract. The napari plugin route is another bounded alternative to a custom canvas; pin and validate before committing.

**Critical assumptions.** (A1) The team's selected TIFF layouts can be served through bounded reads within the 8-core/16 GB target. (A2) A 3 GB streaming content hash and page/chunk reads are acceptable in workflow time. (A3) Their calibrations can be interpreted after explicit metadata review. (A4) Save/commit-marker replacement and locking behave safely on the actual shared storage. (A5) The napari host or replacement can provide reliable keyboard operation, annotation editing, and cancellation. None is established by the supplied component documentation or W4.

**Proposed validation — all UNEXECUTED unless stated otherwise in `witnesses.json`.**

- **V1, frame/export round trip:** create 2D and 3D fixtures with nonzero origin, anisotropic spacing, axis flip/permutation, and a rotated affine. Export/reimport point and polygon indices plus physical coordinates; assert frame ID, source hash, units, matrix, scope and coordinates agree within the declared serialization tolerance. Include a known pixel marker to establish pixel-center/edge translation for each external adapter. W4 is arithmetic only and does not satisfy V1.
- **V2, real files and calibration:** collect one small fixture per supported instrument/layout; assert parsed axes and raw metadata retention, chosen value/unit/frame, and expected reader version. Include a TVIPS regression fixture where distribution terms permit; the cited tifffile fixture is not available in the public repo capture.
- **V3, bounded interaction:** on representative 3 GB tiled and multi-page inputs on the 8-core/16 GB target, record p95 viewport latency, peak RSS, cache behavior, hash time, progress, and cancel latency. Choose acceptance limits with researchers before claiming responsiveness; tifffile documentation is not a benchmark.
- **V4, recovery on actual storage:** interrupt import, save at each generation/commit-marker point, and export on local disk plus the team's shared storage; reopen and verify only a complete generation/export is accepted, the prior state is recoverable, and no source bytes changed. Exercise path relocation and a mismatching hash.
- **V5, display/data separation and annotation UX:** change contrast/LUT/channel/slice/time and verify source hash and sample values unchanged; verify geometric resample creates a recorded child identity. Test keyboard-only navigation, point/polygon/mask edits, undo/redo after reopen, visible progress/cancel, and legible metadata/errors with users.
