# Biomedical image review workspace: current proposal

**Stage:** I-05-DELIVERY-RECOVERY-R002-control-revision-a001 (revision)  
**Evidence checked:** 2026-10-06; public captures are identified in `sources.json`.  
**Purpose:** local research image review and annotation, not clinical diagnosis. This is an incremental design proposal, not a built or qualified application.

## Recommendation

Build a small Qt desktop shell around napari’s multidimensional image and annotation layers, with application-owned import, project, coordinate, identity, save/recovery and export services. Start with a narrow, explicitly tested subset of single-file OME-TIFF and local OME-NGFF 0.4/Zarr v2. Keep source pixels immutable; store annotation and display state in a small SQLite project database, and masks or derived arrays as separate immutable chunked artifacts. Researchers edit a local project copy and exchange closed, checked bundles through shared storage. Do not use napari layer metadata as the project’s scientific record.

This is a coherent candidate stack, not a demonstrated integration: napari `v0.6.5`, tifffile `2025.5.10`, Zarr Python `2.18.7`, Dask, and a locked Qt/Python environment. Zarr 2.18.7’s release metadata requires Python `>=3.11`, while napari v0.6.5 declares `>=3.10`; therefore the candidate intersection starts at Python 3.11. Neither the version metadata nor component evidence proves a resolvable, maintainable cross-platform build. Resolve the complete dependency lock and qualify it on each lab workstation OS before adoption. (S3, S4, S11, S14.)

## Evidence that changes the design

### External facts

- OME-TIFF plane order cannot be inferred from TIFF IFD/page order alone. `DimensionOrder` describes rasterization and `TiffData` can map IFDs to explicit Z/T/C positions. The adapter must use these mappings and surface inconsistencies. (S2, “DimensionOrder” and “The TiffData element”.)
- OME schema 2016-06 distinguishes `Pixels/PhysicalSizeX/Y/Z` from `Plane/PositionX/Y/Z`: the former describe pixel spacing; the latter are microscope stage positions for a channel/Z/time plane. `Pixels/TimeIncrement` is a global time spacing, while `Plane/DeltaT` is per-plane timing. The schema defines optional unit attributes and defaults (for example, pixel-size units default to µm, global/per-plane time units to seconds, and plane-position units to “reference frame”). Preserve whether a unit was explicit or supplied as a parser/schema default. These fields do not independently define one universal oriented image-to-laboratory affine. (S13, `Pixels` and `Plane` attributes.)
- OME-NGFF 0.4 specifies Zarr v2. Its multiscale image dimensions are 2–5, with 2 or 3 spatial axes and at most one time axis plus one channel or custom/null axis; axis metadata must agree with dimension order. Its multiscale coordinate transforms use scale and optional translation, with translation applied after scale; this vocabulary cannot express a general rotation or shear. Label images use integer values; the image-label `source.image` link is optional. Thus NGFF 0.4 can help exchange arrays and masks but cannot replace this project’s full coordinate, annotation and provenance contract. (S1, §§2, 3.1, 3.3–3.7.)
- Tifffile 2025.5.10 documents an `aszarr=True` route for regional TIFF access through Zarr v2 and describes reading tiles, pages/IFDs, SubIFDs and pyramid levels. The release documentation also calls out Zarr 3 incompatibility and limitations including multi-file pyramidal OME-TIFF. This supports a reader experiment, not all-TIFF support or a memory/latency guarantee. (S3, release description and requirements.)
- Napari v0.6.5’s `slice_from_axis` wraps direct Zarr arrays using Dask before slicing; `split_channels` carries metadata, including rotation, shear and affine values. That is a useful viewer-layer mechanism, not evidence that every reader/view path stays bounded or that project persistence/export is faithful. (S4, `slice_from_axis`, `split_channels`, `split_rgb`.)
- SQLite’s atomic-commit discussion depends on filesystem/VFS locking, write and flush behavior. It is not a qualification of network shares. (S12, rollback-journal and “Things that can go wrong” sections.)

### Two independent implementation precedents

1. **Napari, viewer/layer precedent.** In issue #7085, a report against `0.4.16.dev1413+ga4fa1fa0` describes “Split RGB” replacing a layer’s nontrivial transform with identity. PR #8256 explains that `split_rgb` called `stack_to_images`, which dropped affine/rotate/shear metadata, and switches the path to `split_channels`. Its regression test compares each output `affine.affine_matrix` to the original for no transform, scale, translation and `Affine(translate=[0, 4])`. The PR’s three code-bearing commits are `2b51110e65af469863697797921ff12aa668d301`, `3f994d36130e5d673ce059a1a0d66fac9cca03b0`, and `9f262998cbe464e0ec826eae691e487af752658c`; the test and implementation are present at napari tag `v0.6.5`. GitHub records merge commit `afd1bb88f296726fe98bc0a94119a51bba6870c4` on 2025-09-26 and milestone 0.6.5. The tested `Affine(...)` case wraps a translation; the test does not assert a general non-diagonal affine, rotation/shear, project save/reopen or export. The useful lesson is to test transform metadata after each view/layer operation, rather than infer preservation from the presence of an affine API. (S4–S8.)
2. **Tifffile, reader precedent.** Tifffile is a separate project and layer from napari: its 2025.5.10 release documentation describes access to TIFF tile/page/IFD data through a Zarr v2 adapter, while napari supplies a viewer’s slicing and layer behavior. The mechanisms are complementary but were not shown to be an integrated stack by these sources. Verify the exact TIFF fixtures, codecs, reads and memory use in this application. (S3, S4.)

OME-NGFF 0.4 and SQLite add independent format and storage references. Neither standard conformance nor a database transaction settles the application’s own identity, grid mapping, cross-resource durability or export semantics. (S1, S12.)

### Public failure and performance history

The #7085 → #8256 → v0.6.5 chain is stronger than an issue title or linked PR alone: the issue records the failure; the patch shows the changed code and regression test; PR metadata gives merge and milestone; the tagged implementation and test show release applicability. Its limit is the narrow RGB-split assertion described above; it does not validate this proposed app. (S5–S8.)

Napari #9515 remains an open performance report, not a completed fix chain. Its reproducer says `napari[pyqt6]==0.9.1` and `zarr>=3`, while the attached environment lists napari `0.6.1rc1.dev1` and Dask 2026.8.0. The author reports worse behavior for some multidimensional multiscale local Zarr data, especially with both T and Z. The version/configuration discrepancy and difference from this proposal’s candidate pins prevent attributing the report to napari 0.6.5 with Zarr 2.18.7. Treat it as a reason to measure read amplification, stale work and cancellation on target fixtures, not as a confirmed defect in the proposed stack. (S9–S10.)

## Architecture and initial support boundary

### Component choice

- **Desktop/viewer:** Qt shell and napari `v0.6.5` for image display, channel visibility, slice/time navigation, points, shapes and label editing. Keep the project contract in app-owned services. Napari’s tagged project metadata requires Python `>=3.10`, Dask arrays and tifffile, with Zarr optional; it does not lock Qt, codecs or all transitive dependencies. (S4, S5, S11.)
- **Image adapters:** tifffile `2025.5.10` for a tested OME-TIFF subset; Zarr Python `2.18.7` for local NGFF 0.4 stores; Dask arrays where the reader/view path is measured and supports lazy access. Zarr 2.18.7 metadata says Python `>=3.11` and lists `numcodecs`; tifffile’s documented regional TIFF route calls for Zarr 2. Pin and record the full resolved environment, including Dask, Qt binding, codecs and application version. (S3, S14.)
- **Project service:** SQLite for project/asset records, raw metadata snapshots, interpretation overrides, display settings, coordinate frames/grids, annotation geometry, styles, undo history, operation records and artifact manifests. One writer per local project.
- **Array service:** read-only source handles, cancelable asynchronous region/slice requests, bounded decoded cache and in-flight reads, plus immutable chunked masks and derived arrays outside SQLite.
- **Exporter:** stage output, write a manifest/sidecar, read it back, compare declared hashes/grid/geometry, then publish. Project services—not a viewer-layer serializer—decide whether a result is complete.

### Candidate inputs

This is the first qualification matrix, not a universal compatibility statement:

- **OME-TIFF:** local single-file inputs; one user-selected series; 2D XY or explicit ZYX spatial axes, with optional explicit time and channel axes. Parse OME-XML `TiffData` and `DimensionOrder`; accept only tested sample types and codecs and a fully understood plane map. Start without multi-file, plate/HCS, mosaics, packed color, or pyramidal OME-TIFF. BigTIFF, unusual endianness, each compression codec and pyramids need exact fixtures before inclusion.
- **OME-NGFF:** local NGFF 0.4/Zarr v2 with conformant 2–5 dimensions, unique supported axes representing 2D/3D space and optional T/C, matching array/axis order, valid transform lengths/order and compatible multiscale shapes. Validate label grid links when present; an absent `source.image` link is not proof that a label array belongs to a displayed image. Custom/null axes, plate/mosaic layouts, Zarr 3 and nonconformant metadata are outside the initial automatic boundary. A user correction is stored as a project interpretation, not silently described as conformant source metadata.
- **Samples/access:** initially qualify at least `uint8`, `uint16`, `int16` and `float32`; preserve original dtype and values. Additional dtypes/codecs become supported only after fixtures. Permit regional reads only when tile/chunk granularity and decoder buffers fit the measured budget. Reject or offer a clearly degraded, cancelable open for pathological strips/chunks after measurement.

During import show format, series/store, shape, exact axis names/order, dtype, channel metadata, raw and parser-effective units/calibration, plane mapping, tile/chunk shape, codecs, identity state and warnings. If axes/calibration are absent, contradictory or ambiguous, offer explicit correction/mapping, pixel-only work with physical coordinates unavailable, or cancel. Preserve the raw metadata snapshot and the override record separately. Never silently invent micrometres, an origin, a Z axis, channel identity, or an orientation. Unsupported or failed import leaves original bytes untouched, retains a readable import report and recoverable project state, and exposes no partly trusted image for annotation.

## Image, coordinate and annotation contract

### Axes, physical coordinates and metadata

Each image record has an ordered list of named axes, role, length, original source order and source location. Array indices always travel with their axis names. Time and channel are selections, never silently inserted into spatial coordinates. For a `t,c,z,y,x` source, array index `[t,c,z,y,x]` is distinct from spatial `index_xyz=[x,y,z]`. Coordinates are zero-based continuous sample-center coordinates: integer `i` denotes the center of sample `i`. A 2D image has X/Y only unless the user records an explicit embedding in a larger frame.

For a uniform calibrated 2D/3D grid store float64 `physical = origin + M × index`, including input/output axis names, units, frame ID, matrix order, sample-center convention and provenance. Preserve sign, axis permutation, rotation and shear where justified. When metadata supplies only spacing, one allowed explicit product interpretation is an **image-local** frame: origin at sample-center zero, positive basis along increasing named image axes, with units from the metadata. Do not call that stage/laboratory coordinates. Keep OME stage positions separately; never use `Plane.Position*` as an affine origin without a documented mapping. If source calibration is conflicting or cannot establish a mapping, leave physical coordinates unavailable until the user records an interpretation. Preserve schema defaults and whether attributes were explicit. Varying per-plane stage positions or irregular `DeltaT` remain per-plane records; do not collapse them into one uniform affine or time interval. (S2, S13.)

For OME-TIFF, resolve each plane through `TiffData`/IFD and `DimensionOrder`; report XML/TIFF shape or plane-map conflicts, the parser rule/value selected, and stop annotation until resolved. For NGFF, validate supported axis counts/order, transform vector lengths/order and multiscale shapes against 0.4; keep an explicit correction distinct from untouched metadata. (S1, S2.)

### View, derived data and annotations

Canvas/screen coordinates are transient view coordinates. Convert pointer events through the inverse current viewer transform into canonical source-grid sample coordinates before storing shapes. Persist zoom, pan, view rotation, device scale, slice/time/channel and display mapping as view state. Per-channel window/level and LUT/gamma are display-only. A documented baseline window mapping for center `L` and width `W>0` is `clip((sample-(L-W/2))/W, 0, 1)`, followed by display LUT/gamma. Store parameters and convention; changing them never writes source samples or a derived sample array.

Every annotation stores UUID, author/local identity, timestamps, type, geometry dimensionality, source asset ID and identity status/digest, immutable source `grid_id`, axis mapping/frame version, scope, style/version and optional notes/tags. Scope distinguishes a plane (including fixed slice and T/C context), time point, volume and whole acquisition. Points and polygons retain named sample coordinates; masks are integer label arrays on an explicitly identified grid with a documented label table. Reusable styles have stable IDs and versions, marker/stroke/fill/color/width, and say whether width is in screen or data units. Undo/redo is a project-owned command log for geometry, delete, scope, style and mask edits; a mask change writes an immutable chunk revision or reversible patch. Keyboard navigation covers previous/next slice/time/channel, zoom/pan, tool, save and undo/redo. Controls need labeled focus order, visible focus, non-color state cues and legible metadata/progress/errors.

A geometric operation creates a new immutable derived asset and grid; it never mutates source data. Record operation ID/type, source and derived asset/grid IDs, exact crop/resample/rotation/reflection parameters, interpolation and dtype policy, and a float64 source-grid↔derived-grid mapping. Original annotations stay anchored to their original asset/grid. A mapped copy receives a new annotation identity and operation provenance. This distinguishes annotation identity from an image transform and makes source versus derivative inspectable after reopen.

## Source identity, projects, saving and recovery

An asset ID is path-independent. Single-file identity uses streaming SHA-256. For linked external files, begin as `pending`; while pending, allow inspection but mark annotations unverified and block a “verified against source” export. Hash with a read-only handle, record file identity/size/mtime before and after, and recheck before export or relocation. A detectable change, mismatch, failed recheck or concurrent modification suspicion moves the asset to `changed/unavailable`, preserves project/annotations and blocks verified export. A read-only handle alone cannot stop another process changing bytes. Therefore a linked-source digest is a verified observation under an explicit quiescent-source contract, not proof of an immutable snapshot. For strict identity, make a portable app-owned snapshot: copy to staging, hash the copied bytes, verify/flush, publish and decode from that immutable copy. This costs disk space and time but binds the pixels used to the digest.

For a Zarr v2 tree, define a versioned manifest: enumerate every regular file (metadata and chunk payloads), use UTF-8 NFC relative paths with `/`, sort by encoded path bytes, and include each path, type, byte size and SHA-256 in a canonical manifest digest. Exclude the external root path. Reject symlinks, non-regular objects, normalized duplicate paths and case-fold collisions for portable exchange. Re-enumerate and recheck object metadata after hashing; any list/content change leaves identity pending or changed. This detects ordinary concurrent changes; only a verified portable snapshot provides a stable byte tree without the source owner’s cooperation. A relocated reference is accepted only after full digest/manifest match. Filename, size or timestamp alone is never identity proof.

A directory project contains `project.sqlite`, versioned raw metadata snapshots, optional portable source copies, and immutable `derived/` and `masks/` artifacts. References minimize disk cost but require relocation/relink; portable bundles need at least the source size plus project/derived space and copy time. Show storage mode and estimated cost. Never modify a source in place.

For local saves, use one SQLite writer, explicit transactions and a selected, versioned rollback-journal durability configuration (candidate: `journal_mode=DELETE`, `synchronous=FULL`), validated on supported local filesystems. Stage each immutable artifact in a sibling temporary location; finish writes, flush files, reread/verify hashes and sizes, publish by same-filesystem rename, flush parent-directory metadata where supported, then commit the database pointer. A rename plus SQLite transaction is not one cross-resource transaction. If a crash follows artifact publication but precedes DB commit, startup finds an unreferenced artifact. If platform flush/rename guarantees are insufficient, or a committed pointer is missing its artifact after restart, mark the revision damaged and offer the previous verified revision/backup; never silently accept partial state. Startup inventories partial stages, orphans, missing references and SQLite recovery state; cleanup only after checking all retained revisions. Back up the last good database before schema migrations.

Export to a sibling temporary file/folder, close and read it back, verify manifest, grid and declared content hashes, then publish. A failed export leaves any prior output intact and marks the temporary incomplete. Keep live editing local; do not concurrently open a live SQLite project from several workstations on an unqualified share. Close and verify a bundle before copying. Stage a copy on shared storage and publish it only after full copy/reopen verification; test the exact storage type and rename/flush semantics. The MVP has no simultaneous-edit merge.

## Minimum workflow and honest export behavior

1. Create a project and import a local source as a read-only reference or explicit portable snapshot. Inspect metadata/provenance, axes, calibration, series, dtype, tile/chunk layout and identity progress. Ambiguity offers correction, pixel-only work, or cancel; failure preserves source/project and a legible report.
2. Navigate 2D or volume data, channels and time; adjust display mapping; see original data, derived data and annotation overlays as separate states. Display changes do not change samples.
3. Add points, polygons and masks with reusable styles and visible scope/context. Support keyboard navigation and annotation undo/redo. Bind geometry to a named source grid/frame.
4. Save, close, reopen on the same or another workstation. Resolve a portable source or explicitly relink by full identity. Keep annotations readable if the source is missing, but label alignment as unavailable and block verified-against-source claims.
5. Export an annotation table, overlay and small derived image; show a field-by-field summary of preserved, transformed and omitted information; read each output back before reporting success.

The table should include annotation UUID/type/scope, source asset and digest/status, source `grid_id`, named axes and sample coordinates, slice/time/channel context, physical coordinates only when available with units/frame, style/version and operation provenance. Pair CSV with a versioned JSON manifest/sidecar; store polygons without lossy point flattening and masks with label mapping/grid and relative artifact path.

A PNG overlay is a rendered view for a specific asset/identity, derived grid, slice/time/channel, view transform, display mapping and annotation IDs. It preserves rendered pixels only; it does not by itself preserve original samples, editable geometry, calibration or the entire project. The sidecar carries those references and transforms. Never call the PNG a calibrated original image.

A small image export records source identity, source/derived grid, crop/axes/time/channel, dtype, exact operation chain and application/reader versions. If it only copies a region, preserve dtype/sample values and compare the output’s samples. If it crops, projects, rescales, resamples, casts or bakes a LUT, record exact parameters and mark the change/loss. OME/NGFF metadata may carry supported calibration, but NGFF 0.4 alone cannot carry a general rotation/shear. Keep the exact mapping in a sidecar or offer an explicitly resampled derivative with a new grid and operation record; if a recipient ignores the sidecar, label the standard-only export incomplete/lossy. (S1.)

## Proposed validation and current evidence

**Executed by candidate — W1, isolated coordinate/grid arithmetic only.** Candidate-authored standard-library Python used named axes `t,c,z,y,x`, sample indices `t=2,c=1,z=4,y=7,x=11`, a non-diagonal spatial matrix and origin, plus a declared crop/downsample map `source = [3,1,2] + diag(2,3,1) × derived`. Expected source index `[11,7,4]`, physical coordinate `[8.25,22.75,33] µm`, source index recovered from derived index `[4,2,2]`, and derived-index roundtrip `[4,2,2]`; stdout matched, stderr was empty and exit code was 0. The complete code, JSON input, receipt hashes and output are W1 in `witnesses.json`. This check validates only the stated arithmetic example; it executes no OME/NGFF parser, viewer event, source reader, SQLite project, persistence, operation service or exporter.

All other checks below are **proposed / UNEXECUTED**:

- **Import and metadata:** fixture tests for 2D, ZYX, T/C stacks and instrument examples; OME `TiffData` permutations; NGFF valid/invalid axis order, transform lengths and multiscale shapes; missing or defaulted unit attributes; nonzero/varying plane positions; global `TimeIncrement` versus irregular per-plane `DeltaT`; conflicting XML/TIFF dimensions. Compare against independent expected plane maps and keep refusal/correction cases explicit.
- **Bounded access and cancellation:** on an 8-core/16 GB machine, test representative 3 GB tiled OME-TIFF and chunked NGFF, cold/warm slices and giant-strip/chunk adversaries. Measure peak RSS, decoded cache, in-flight decoder buffers, bytes read/read amplification, p50/p95 latency, progress cadence and cancellation acknowledgment against a reference decoder. Provisional targets: cache ≤512 MiB, ≤4 concurrent reads, admit no decoded chunk above 32 MiB, warmed slice/edit p95 ≤250 ms, progress ≤250 ms, cancel acknowledgment ≤1 s. These are design targets, not observed component or application results; revise them from lab measurements.
- **Coordinates and transformations:** compare named sample centers and float64 physical mapping with independent calculations through view pan/zoom/device scaling, slice/time/channel, channel split, save/reopen and export. Exercise crop, anisotropic resampling, reflection, rotation and shear. Confirm source-bound annotations remain fixed; any mapped annotation gets a new ID/grid/operation chain.
- **Identity and recovery:** mutate/replace a linked file during and after hashing, change Zarr objects during enumeration, relocate same-name identical and changed content, interrupt portable copy and corrupt/delete objects. Inject termination before/after artifact write/flush, rename/directory flush and DB commit; reopen and verify prior revisions, pointers, orphans and incomplete exports. Repeat bundle copy/close/reopen on every actual shared-storage type. No source-change case may silently retain “verified” status.
- **Exports and editing/accessibility:** round-trip CSV+manifest, overlay, mask/label and small image. Compare samples where no pixel operation is declared; verify source and derived digests, grid/affine, time/slice/channel, mask labels, loss summaries and sidecar behavior in named receiving tools. Exercise undo/redo and mask recovery, reusable styles, keyboard-only navigation, focus order, visible focus, screen-reader labels and readable warnings/errors with researchers.

No 3 GB test, application build, full environment resolution, shared-storage qualification, end-to-end save/reopen, export roundtrip or accessibility evaluation has been executed here.

## Opportunity, alternative and unresolved decisions

**Useful opportunity (optional):** after the project model is stable, export integer masks as NGFF 0.4 image-label groups for interchange when grid and transform are representable. Keep points, polygons, undo history, arbitrary app affine and complete provenance in the project/sidecar. `source.image` is optional, so verify the actual image/label link in independent readers. (S1.)

**Plausible alternative (deferred):** if one named microscope format falls outside the strict reader subset, compare a separately qualified Bio-Formats/vendor adapter that preserves the input and emits a documented derived OME-Zarr copy with researcher-directed conversion outside the app. No Bio-Formats release, exact support matrix or integration was checked for this proposal; do not imply one. Promote an adapter only for a lab fixture with verified metadata mapping, failure recovery and downstream interoperability.

Critical decisions still depend on evidence: whether the locked Python/Qt/tifffile/Zarr/Dask/codecs environment resolves across workstation OSes; whether real microscope files fit the narrow axes/codec/chunk boundary; whether the 3 GB access and responsiveness targets are met; whether source files remain quiescent or require portable copies; which local/share filesystems honor configured journal/flush/rename behavior; and whether downstream recipients consume sidecars. Until those are measured, the architecture remains a bounded proposal. If a dependency fails, keep the project authority and data contract, narrow automatic import to passing fixtures, and make the unsupported case an explicit recoverable refusal.
