# A traceable image review workspace: coordinate and storage contract

**Research proposal — 5 October 2026.** This is a plan for a research annotation tool, not a clinical product. It was developed from the supplied brief and public primary sources; this exercise does not establish autonomous discovery beyond that scope.

## Recommendation

Build a local-first desktop shell that owns the project, provenance, annotation schema, transform history, undo/redo, and exports. Reuse napari as the interactive canvas only at an exact revision whose shape picking tests cover fractional coordinates; use tifffile's read-only Zarr view for the first bounded OME-TIFF import path, and Zarr-Python for chunked OME-Zarr access and optional mask/derived storage. Keep source pixels external by default. Do not equate an image's display mapping with a data transform.

The proposed first-stack pins are napari commit `6d386b1c2ed1c185483e06dc19ebb961679d1a7b` (the merged fix commit, for a prototype), `tifffile==2026.9.20`, `zarr==3.4.0`, `imagecodecs==2026.8.16` when compressed TIFF codecs are needed, and OME-NGFF specification 0.5.2. These are source pins to test together, not a tested application lockfile. The fix landed after the latest napari release found here: v0.9.2 was published 29 September and PR #9394 merged 2 October for the still-open 0.10.0 milestone. Ship only after a tagged release containing that fix passes the project’s own coordinate checks; otherwise the exact merge commit is a prototype-only dependency. [S02–S06]

## What the source trace changes

A docs-first review identifies useful building blocks and their intended contracts. Tifffile documents OME-TIFF series, metadata inspection, and reading a tile region through a Zarr adapter; Zarr-Python documents chunked arrays and says a slice loads the requested region into a NumPy array; OME-NGFF describes axes, scale/translation metadata, multiscales, and integer label images. These are useful facts, but they do not show that a rendered annotation remains selectable at a floating-point boundary or that a complete application meets a memory target. [S08, S10, S12]

Following the issue into the code and tests finds that boundary. napari issue #8901 reports a rectangle drawn at the expected location but impossible to select with reordered axes, scale 0.01, and translation 5.1; the report names napari 0.7.0. The reporter’s reproduction is evidence of a report, not an independently reproduced application failure. [S01]

PR #9394 explains the mechanism: shape drawing accepted a real-valued displayed slice within half a slice, while `_visible_shapes` used exact containment to decide what picking could see. A non-integer translation—or floating-point scale round-trip—could therefore draw a shape but leave it out of hit-testing. The patch changes `_visible_shapes` to use the half-slice tolerance for planar shapes and exact interval containment for dimensions the shape spans. [S02, S03]

The PR adds `test_value_with_fractional_slice_key`, `test_inside_with_fractional_slice_key`, and `test_visible_shapes_spanning_slices_are_not_widened` in `src/napari/layers/shapes/_tests/`; the first two assert picking agrees with rendering at fractional keys, and the third preserves spanning-shape boundaries. PR text reports that two tests fail without the patch and that the named upstream test suites passed; this proposal did not run napari or those suites. The PR is merged at `6d386b1c…` and references issue #8901. Its merge is after the v0.9.2 release capture, so do not attribute this fix to v0.9.2. It is listed for 0.10.0, which was not released in the captured state. [S02–S05]

**Design consequence (engineering inference):** visibility, picking, cursor coordinate readout, persisted annotation coordinates, and export must share one named coordinate mapping and test the same boundary cases. A canvas that draws an annotation is not sufficient evidence that users can later select or export it correctly.

**Limits of this chain:** it covers napari Shapes picking/render agreement for the tested planar and spanning cases. It does not prove general affine/orientation correctness, persistence round-trips, masks, TIFF reading, the 3 GB memory target, or this proposed application. The fix is an important regression precedent, not a complete coordinate system.

## Independent implementation precedents

| Precedent and pin | Mechanism worth adopting | Independence and limit |
|---|---|---|
| napari Shapes, merged source `6d386b1c…`; compare issue environment 0.7.0 and released tag 0.9.2 | Interactive multidimensional canvas and vector shapes; the issue/fix/test chain exposes the need to make display and hit-testing agree under physical transforms. | A separate viewer project from the storage/import libraries. The fix is on main after v0.9.2; the tests cover specific slice behavior, not this application or its persistence. [S01–S06] |
| tifffile 2026.9.20 | `imread(..., return_as='zarr')`, then select a region from a TIFF-backed Zarr array; inspect series shape, dtype, axes, and metadata before importing. Its README also documents that compressed segments need imagecodecs and that TIFF support has explicit limits. | An independent TIFF parser/decoder with a storage adapter, not a viewer. The documented tiled-pyramid example is a component precedent, not proof all TIFF layouts are bounded or that a 3 GB file is responsive. [S09–S10] |
| Zarr-Python 3.4.0 with OME-NGFF 0.5.2 | Chunked N-dimensional reads/writes and persistent local stores; NGFF specifies array axis names/order, scale/translation transforms, multiscales and integer label images. | A separately maintained array implementation and a separate bioimaging format specification. Zarr chunks do not themselves define app provenance or annotation semantics; NGFF 0.5 only standardizes the stated transform subset. [S07–S08, S11–S12] |

The projects contribute at different layers and are independently useful: napari supplies the canvas and vector interaction, tifffile interprets TIFF structures and can expose selected image regions, and Zarr supplies chunked array storage/access. OME-NGFF constrains one interoperable metadata/export path. These precedents are not evidence that an integrated product already satisfies this brief.

## Minimum workflow and component plan

1. **Create project.** Make a versioned project directory with a manifest, a revision journal, annotation/style records, and optional mask/derived-data directories. Keep project data separate from source images.
2. **Import without rewriting.** Initially offer local OME-TIFF/BigTIFF and OME-Zarr 0.5 only. Inspect series, shape, dtype, raw axis labels, calibration, compression/codec availability, and relevant original metadata. Ask the user to choose a series where a file contains several. Keep the opened original read-only. Do not copy the full pixel array into a second in-memory buffer.
3. **Resolve metadata visibly.** Show the source axes, axis order, units, pixel/voxel spacing, time increment, origin/translation, and any unknowns. Recognized axes may be mapped into the viewer without rewriting source order. Unknown or contradictory axes/calibration require an explicit mapping/correction; store that correction beside the untouched source metadata. Do not silently drop an axis or invent physical units.
4. **Navigate and display.** Select channels, time, and slice; save window/level, channel color/blend, and view position as display state. These controls affect only display. Make displayed original pixels visually distinct from any resampled or otherwise derived data. Keyboard navigation and an accessible metadata/error panel are minimum UI behavior.
5. **Annotate.** Provide points, polygons and masks, named reusable styles, keyboard-operable tools, and undo/redo. Persist vector annotations in a versioned app schema; persist masks as integer label arrays. Keep annotation edits independent of the image samples.
6. **Save, close, reopen elsewhere.** Commit a new project generation without modifying the source. On another workstation resolve a stable path or ask the user to relocate the image; verify source identity before reattaching annotations.
7. **Export and verify.** Export a coordinate-rich table and/or vector geometry, an optional label overlay, and a small derived OME-TIFF crop. Show a summary of source identity, output identity, axis/calibration mapping, and what metadata each export did and did not retain.

**Engineering inference:** bounded source access is plausible because tifffile documents TIFF-backed Zarr region reads and Zarr-Python documents that array slices load requested regions. Neither source establishes a whole napari render path, cache limit, peak RSS, cancellation, or 3 GB result. The viewer adapter must pass lazy array access through without `asarray()`/unbounded materialization and must be profiled before this target is claimed. [S10, S12]

**Product choices:** use the viewer as a replaceable canvas component; the project service owns identities, coordinate transforms, file I/O, and annotation serialization. Start CPU-only, with viewport tiles/chunks and a bounded decoded cache (initial proposed budget 512 MiB, at most two concurrent decodes); keep GPU use optional. A 256×256 tile of uint16 samples is 128 KiB, so 512 MiB is 4,096 such tiles before overhead. This arithmetic is a sizing illustration, not evidence of actual cache or process memory use. Tune chunk/tile shape by measured plane navigation and mask editing, not by package defaults.

## Project and coordinate contract

The manifest is app-versioned and records stable logical asset IDs separately from content hashes. For every source asset retain: original URI/path and file name; full SHA-256 and byte size; size/mtime as quick stale hints (not identity); reader and version; selected series; raw metadata and its hash; raw axis labels/order; shape, dtype, and channel/time counts; original physical calibration; and the selected canonical axis mapping. Hash in a cancellable streaming pass; record progress and verify the file did not change during the pass. A path or timestamp alone is not identity.

For the first version, canonical supported axis names are `T`, `C`, and two or three spatial axes (`Y`, `X`, optionally `Z`), with array dimensions explicitly named and ordered. Store the raw source order and a reversible permutation into canonical view order. An annotation is bound to logical `asset_id`, source SHA-256, and `coordinate_frame_id`; record its geometry type, style ID, scope, selectors, coordinate values, author/time and edit history. Slice/time annotations name their `t`/`z` selectors; volume or whole-acquisition annotations declare that scope rather than relying on omitted indices. Channel is an explicit selector or “all channels,” not an implicit spatial coordinate.

For v1, stored vector coordinates are float64 source-array index coordinates with integer voxel/pixel centers; mask samples use integer source indices. Coordinates are named by axes, not anonymous screen `(x,y)` pairs. The UI maps cursor/display coordinates through the recorded axis permutation and physical transform. The v1 physical map is explicit, axis-aligned `physical = translation + scale × index`, with unit per axis and a documented transform order; use scale then translation, as in NGFF dataset metadata. Display rotation/zoom and intensity mapping are view transforms only. Keep the original raw metadata and any user override separately. Unknown origin, oblique orientation, shear, irregular spacing or incompatible axis semantics means physical positions are marked unavailable until corrected; preserve the raw source and require an explicit supported correction before physical-coordinate export. OME-NGFF 0.5 describes identity, scale and translation; do not claim its metadata alone expresses arbitrary orientation matrices. [S08]

A geometric transform or resampling creates a new derived asset and a provenance record containing input asset ID/hash, operation and parameters, software/version, interpolation, input/output shape and dtype, output hash, and the input-to-output coordinate map. Annotation mapping across it is explicit and reviewable. Do not overwrite or mutate the source. Changing channel visibility or window/level changes only the saved display state and must leave the source hash and sample bytes unchanged.

## Support boundary, recovery and portability

**Initial supported inputs (product choice):** local OME-TIFF/BigTIFF with parseable OME metadata and a supported `T/C/Z/Y/X` mapping, and OME-Zarr 0.5 using Zarr v3. Start with types common to microscopy (`uint8/16/32`, `int8/16/32`, `float32/64`) and a small codec set exercised in fixtures; require the pinned decoder for compressed TIFF. Tifffile itself advertises many more formats, but its own notes describe unsupported TIFF features and special cases; library capability is not the application's support promise. Defer proprietary containers, RGB/sample axis `S`, unknown/custom axes, unsupported codecs, oblique/non-axis-aligned geometry, corrupt/truncated data, and untested NGFF/Zarr versions. [S08–S10]

Preflight metadata without pixel conversion. Import proceeds through `pending → validated → committed`: stage metadata and any generated assets separately; only add a usable image reference after validation. If an axis/codec/parser fails, retain the project and original metadata/error report, do not mutate the source, and allow retry after a codec or mapping choice. Cancellation removes or marks staging data recoverable; it does not damage the last committed project generation. Unknown values stay visible and are not guessed.

For local saves, write a new immutable generation into a temporary sibling directory, flush and checksum each small metadata/mask output, then atomically rename that generation and replace a small current-manifest pointer last. Keep the previous valid generation until the new one verifies. Failed exports likewise write to a temporary destination and publish only when complete. Atomic rename/fsync behavior varies on SMB/NAS and across filesystems; validate the actual shared storage. For ordinary shared-folder exchange, prefer a closed project bundle copied from a local working copy, detect a changed base generation before save, and avoid concurrent edits to one directory. Do not imply collaboration or reliable distributed locks.

Default bundle mode stores annotations, history, styles and provenance plus relative/portable source references, not 3 GB originals. A second machine first checks the path and then permits “locate image”; full hash equality is required before reusing its annotation binding. If missing or hash-mismatched, keep annotations safely detached and ask for a verified replacement or leave the image unresolved. Offer an explicit collect/copy option for smaller data or portable transfers; copying 3 GB costs disk and time but removes path dependence. Reopen behavior for a genuinely missing source is an unresolved requirement of use: the project must still open and show its metadata/annotation records with a clear unavailable-image state.

## Exports, opportunity, and alternative

A CSV table should include annotation ID/type/scope, source asset ID and SHA-256, source-frame axis names, integer selectors, float64 coordinates, physical coordinates and units when known, coordinate-frame/transform ID, style, and provenance sidecar. A vector export (e.g. GeoJSON plus sidecar) carries axis/calibration fields because plain 2D geometry cannot alone express Z/T. An OME-NGFF label overlay uses integer samples and the same declared axes/transforms; NGFF 0.5 labels cover raster labels, not this app's points and polygon objects, so retain vectors separately. A small OME-TIFF crop records crop origin and resulting coordinate map. Report exactly which original metadata was copied, normalized, omitted or regenerated; never claim that an export preserves arbitrary proprietary metadata. [S08, S10]

**Useful opportunity:** OME-NGFF 0.5 can provide a portable chunked multiscale image/label handoff to compatible bioimaging tools. After core round-trip is sound, add explicit label interoperability or a “collect into NGFF” action. Treat OME metadata `omero` display fields as useful but transitional per the spec, and do not make them authoritative for the app manifest. [S08]

**Plausible alternative:** copy/import every source into a project-owned chunked NGFF store. That makes paths and chunk layout predictable and can bundle pixels with labels, but adds conversion time and disk use, risks metadata/sample conversion, and duplicates the originals. The initial choice is references plus optional collected copies, because sources may be 3 GB and users exchange bundles on ordinary storage. The choice should be revisited if relocation failures outweigh storage and conversion cost.

## Witnesses and validation still required

The candidate executed a small isolated Python arithmetic check (W01, detailed in `witnesses.json`). It confirmed the copied half-slice predicate rejects an exact-comparison miss for `40.99999999999999` versus planar slice 41, retains exact interval handling for a spanning shape, round-trips a scale/translation example, and calculates 128 KiB for one 256×256 uint16 plane chunk. It is arithmetic over supplied values, not execution of napari, Zarr, tifffile or an app. One earlier scratch attempt exited 1 because its chunk-size expression omitted the X dimension; it is recorded as a discarded attempt and is not used as evidence.

The following proposed checks are **UNEXECUTED** and are gating work before adoption:

- On the 8-core/16 GB target, open representative 3 GB tiled and stripped OME-TIFF plus OME-Zarr with cold and warm cache; record peak RSS, bytes read, decode latency, viewport p95, and cache eviction. Confirm no second full-volume allocation and enforce the proposed cache budget; cancel during read and record cleanup/progress.
- Against the exact napari revision/release, use fixture scales and noninteger translation, reordered axes, negative scale, 2D/3D, vector/mask and spanning annotations. Assert drawn and pickable sets agree where intended, and test screen → source-index → physical → export → reopen round-trip, including the regression values in PR #9394.
- Change only window/level and channel visibility, save/reopen, and compare source SHA/sample checks; then run a crop and explicit resample and verify the original stays identical while output hashes, transformation and interpolation are recorded.
- Interrupt each save/export phase and simulate a changed/missing source on another workstation. Verify old manifest remains readable, staging is recoverable, relocation requires matching full hash, and metadata/annotations remain accessible without pixels.
- Import ambiguous axes and missing/contradictory calibration. Verify the original metadata is retained, no mapping is guessed, correction is explicit and versioned, and a rejected import leaves the rest of the project intact.
