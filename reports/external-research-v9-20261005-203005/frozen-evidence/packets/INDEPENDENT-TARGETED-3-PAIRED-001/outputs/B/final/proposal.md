# Local biomedical image review workspace: implementation proposal

**Decision in brief.** Build a local-first desktop project shell around a lazy image-reading adapter and an embedded multidimensional viewer. Keep source images immutable. Store each annotation in the project’s own named index coordinate frame, with an explicit transform to physical coordinates; treat viewer layers and CSV writers as adapters. Start with an intentionally small image support matrix and exercise it with real microscope fixtures before claiming 3 GB responsiveness. The proposal is for a research annotation tool, not a diagnostic product.

The candidate implementation pins studied here are napari **0.6.4** (tag resolves to commit `8aa6ea45b0fce8ff2a9506d75b55a93fc8ac9589`), Zarr-Python **3.1.3**, tifffile **2026.9.15** (source commit `6e0a02f10fc763abd94aee0a0ab8225b4b8860a9`), and OME-NGFF **0.5** (the captured spec page lists revisions through 0.5.2). These are research pins, not a verified compatible lockfile. Test a single environment, reader adapters, and local-storage behavior before adopting them together. See the exact source pins and capture identities in `sources.json`.

## Findings that change the plan

**External fact — chunk size and stored-object size are different.** Zarr’s sharding codec stores many independently readable inner chunks in one shard object [S5]. Zarr-Python issue #3169 reports CRC failures with `create_array(data=..., chunks=..., shards=...)` in v3.0.8 [S1]. PR #3299 separated chunk-region and shard-region iteration, and PR #3422 then changed a second array-copy path from chunk iteration to shard iteration [S2, S3]. The #3422 patch adds `test_create_array_with_data_num_gets`: with one or three shards it checks for one metadata GET plus one GET per shard, for NumPy and Zarr inputs. Release v3.1.3 includes #3422 [S4]. This is a concrete issue → code changes → regression-test → release chain.

**Limit of that chain.** The added assertion checks I/O request count, not byte-for-byte readback or the original CRC reproduction. The captured material establishes the code/test/release relationship and the storage-granularity lesson; it does not prove every sharded write is correct, memory-bounded, crash-safe, or fast on the lab’s machines. For this workspace, use a released Zarr version at or beyond the fix if writing sharded arrays, avoid treating concurrent inner-chunk tasks as independent when they update one shard, and add an application test that writes and reopens a multi-shard image/mask and compares all samples or checksums. Do not create a whole in-memory array as an import shortcut.

**External fact — displayed coordinates and persisted coordinates can differ.** Napari issue #8353 reports a 2D image with origin `(100,100)` and spacing `(2,2)`; a Points layer created from the GUI after loading that image exports values near `(50,50)` and `(57,57)`, while the reporter expected `(100,100)` and `(114,114)` [S6]. The discussion clarifies that Points data are in layer coordinates, CSV saves those points without the layer transform, and layer creation order changes the observed values. The issue remains open in the captured state; maintainers discuss a metadata-bearing writer, not a completed repair [S7]. This is not evidence that every napari export is wrong. It is a direct warning that a layer’s points, its display/world transform, and a flat table’s coordinates are separate contracts.

**Product choice from that evidence.** The application owns annotation geometry and its coordinate frame. Napari may display/edit geometry through a tested adapter, but its layer data or CSV is never the sole saved representation. Every export declares its frame and the transform used. Reopening a project reconstructs the same mapping from project metadata, independent of layer creation order.

**Independent useful precedents.** Zarr-Python is useful at the N-dimensional array/storage layer: chunked access and explicit chunk-versus-shard write granularity. tifffile is a separate TIFF reader and metadata implementation: its pinned README documents inspection of series/shape/axes without decoding pixels and TIFF-to-Zarr access for selected regions [S10]. napari is a separate interactive viewer/model with layers and transforms [S8]; its issue history exposes the persistence boundary [S6, S7]. These components solve different jobs and can be combined behind explicit adapters; their presence does not demonstrate that a complete application made from them meets this brief.

A second, narrower compatibility lesson comes from tifffile issue #334: archived Micro-Manager MMStack Summary metadata can encode nominally numeric calibration values as strings. The 2026-09-15 source change coerces pixel size, Z step and time interval to floats, with invalid values falling back to zero [S11, S12]. The captured commit changes implementation and version/changelog text but adds no automated regression test. Treat this as evidence for retaining raw metadata and testing real vendor fixtures, not as a complete issue/fix/test chain or a promise that all MMStack files are supported.

**Docs-first versus tracing.** Documentation suggests useful building blocks: OME-NGFF names axes and represents scale/translation; tifffile exposes TIFF series and lazy Zarr access; napari is a multidimensional viewer. Deliberate issue/code/test tracing found two requirements that those general capabilities do not settle: writes to sharded objects need shard-aware coordination, and layer coordinates need not be the coordinates a user expects in an export. It also found an archived TIFF calibration-string failure. Those findings change the design: keep a canonical app transform, test sharded readback rather than trusting a successful save, and make format support a fixture-backed matrix.

## Data contract and coordinate rules

The project bundle has a versioned manifest, immutable source records, one or more annotation sets, display state and a provenance log. Persist all coordinate meanings explicitly:

- Each source has a stable project ID, original URI/path, file or store identity, byte size, metadata snapshot, instrument/source notes, and import time. Preserve the original metadata verbatim, including unknown fields. A user correction is a separate recorded override; never rewrite the source to apply it.
- Store the original axis names, sizes, order, sample dtype, interpretation, and raw calibration. Map recognized axes explicitly to spatial, time, channel or other named axes. Record unknown/custom axes rather than silently squeezing, reordering or guessing them.
- Canonical annotation coordinates are zero-based **voxel-centre indices** in an explicitly named axis order. For an N-dimensional spatial image, a homogeneous matrix `A` maps the spatial index vector to physical coordinates: `p = A · [i0, …, in, 1]`. Record matrix values at full floating precision, units per physical axis, and the source/transform ID. Do not infer a world origin of zero when metadata is absent. For a 2D image, the matrix maps `(row, column)` in the chosen project order; adapter code handles conversion to the reader’s axis order.
- Keep viewer canvas coordinates, layer coordinates, source indices and physical coordinates as distinct named frames. Any view transform is transient unless saved explicitly as display state. A geometry transform or resampling creates a derived image record with parent source ID, operation parameters, software version, output identity, dtype, interpolation and output transform. It never edits the parent source in place.
- Each annotation has a stable ID, geometry type, vertices/voxel mask, bound source or derived-image ID, frame/axis order/transform ID, time and channel scope, and scope kind. A plane annotation records the fixed slice and time indices. A volumetric mask/point records full spatial indices. An acquisition-level note may have no geometry. Use 2D polygons on a named plane in the first release; use points and 3D masks for volumetric features. Make any unsupported 3D surface geometry explicit.
- Reusable styles are named project objects, not embedded color guesses. Annotation commands are undoable/redoable and refer to annotation IDs. Save command history or checkpoints so interruption does not discard edits.

OME-NGFF 0.5 is a helpful interchange/storage reference for named axes, per-level paths, and ordered identity/scale/translation coordinate transforms [S9]. It does not itself specify this workspace’s project lifecycle, editable vector-annotation persistence, arbitrary transformation history or UI. Preserve NGFF metadata on import; do not claim full NGFF or universal file support from the limited profile below.

## Proposed component shape

Use a Python desktop shell built on Qt, with napari 0.6.4 as the candidate viewing canvas, tifffile as a candidate TIFF inspector/reader, and Zarr-Python 3.1.3 for local chunked arrays/OME-Zarr and project-owned masks or derived arrays. Put a narrow adapter boundary between the project model and each library:

1. **Project manager:** versioned manifest, source identities, external-path relinking, annotation records and operation log.
2. **Reader adapters:** metadata-only inspection first; choose one recognized series; expose bounded array slices/tiles to the viewer; report axes/calibration and unsupported conditions as structured results.
3. **Display/controller:** channel visibility/blending, window/level and LUT, slice/time navigation, keyboard shortcuts, progress and cancellation. Display mapping is transient state and must not modify source samples.
4. **Annotation model:** app-owned canonical coordinates and geometry; viewer tools project/unproject screen points through a tested conversion function. Undo/redo applies to model commands.
5. **Export service:** builds a staged export from the canonical records and produces a manifest describing source, coordinate frame, display mapping, crop/resampling and hashes.

The TIFF reader docs show that series, shape, dtype and axes can be inspected before pixel decoding, and show region reads via a TIFF-backed Zarr store [S10]. Use this as a candidate path for tiled/striped formats only after measuring its actual read granularity. Memory-mapping is appropriate only when the TIFF layout permits it; compressed or awkward layouts may decode whole segments or require a different strategy. The Zarr sharding source also shows why logical chunk size alone does not state the storage I/O unit [S5]. Set a byte-bounded cache, limit concurrent decode/read tasks, coalesce accesses by storage object where necessary, and let cancellation stop queued work. Progress should identify metadata scan, decode, save or export phases. The 3 GB / 16 GB / 8-core target is an acceptance target to measure, not a conclusion from these source docs.

## Narrow initial support boundary and failure behavior

Start with two local input families:

1. OME-TIFF and selected BigTIFF/TIFF series for which the chosen reader can map axes/calibration and fetch requested regions within the measured memory budget.
2. Local OME-Zarr 0.5 stores with a tested Zarr v3-compatible profile: up to five dimensions, two or three recognized spatial axes and optional time/channel axes; supported numeric integer or floating samples; and transforms representable by the implemented scale/translation profile.

Within TIFF, support only fixture-tested combinations of tiled/striped storage, compression, sample layout and metadata. Do not promise every TIFF dialect, multi-file instrument folder or vendor extension. Initial direct import of proprietary/nonconforming formats, ambiguous series, unknown axes, incomplete or conflicting physical units, arbitrary shear/rotation, malformed metadata and giant files without a bounded region reader are unsupported until separately validated. A file extension alone is not a support decision.

For every attempted import, first create a recoverable source record and preserve raw metadata. Present detected series, axes, dtype, units, origin/spacing and uncertainties. If axes or calibration are ambiguous, let a user explicitly map axes or enter a correction and save that as an override with author/time/reason; do not alter raw metadata. If no supported interpretation is chosen, retain the project and source record, report what could not be displayed or annotated, and offer relinking or retry after a supported converter is available. A failed/partial import is marked incomplete and removable without deleting the original.

Source identity for a regular file should include path/URI, size, modification time and a streaming SHA-256. Compute the digest in cancellable background work and show “identity pending” until complete; size/time alone are weak identity. For a directory store, hash a sorted manifest of relative object names, sizes and object digests. On another machine, first try a project-relative path, then a user-selected relink; verify identity before reconnecting. Never silently accept same-name/different-content input.

## Save, recovery, portability and export

Use a directory bundle so ordinary shared storage can carry it. A compact bundle can contain `project.json`, append-only annotation/event data, small masks, optional previews and export manifests. Avoid a database server or cloud dependency in the first version. Save into a new generation/staging directory, flush data, verify manifests, then publish a small current-generation pointer with same-filesystem temporary-file rename; retain the previous committed generation. Journal edits so recovery can replay complete commands after the last checkpoint. On open, validate the current generation and offer recovery from the last complete journal entry if a write was interrupted. For an export, stage all files, validate them, then publish as a group with a final manifest/ready marker. Atomic rename and durability guarantees differ on network shares; use a local work copy or explicit “shared storage reliability not verified” behavior if locking, rename or flush semantics cannot be established. Bundle exchange is supported; simultaneous multi-writer editing and merge are out of scope.

Offer two source policies. **Reference mode** keeps large originals external and stores a verified relative/absolute locator plus identity; this saves copying space but requires relinking and access to the same data. **Portable mode** copies originals into the bundle, preserving bytes and metadata; this can approximately double disk use for a 3 GB image and makes transfer slower. Never modify originals in either mode. Derived images and masks live at new paths with operation provenance.

Minimum exports:

- Annotation table: CSV rows with annotation ID, geometry/vertex index, source ID, scope, named indices, selected T/C/Z, coordinate-frame name, physical values/units where available, and transform ID/hash. Include a JSON sidecar containing axis order, matrix, source identity, table schema version and missing-calibration status. A plain CSV alone does not preserve that context.
- Overlay: separate transparent vector or raster overlay tied to the source/transform ID; never blend it into or overwrite source data. Export a label mask separately with dimensions, dtype, axes and calibration.
- Small derived image: default to a source-dtype crop. Record crop bounds and adjusted origin, preserve sample values within the crop, and mark it as derived. Resampling, bit-depth conversion or applying a display LUT requires a distinct named operation with source/output hashes, interpolation/type/mapping details. A rendered preview may use display mapping but must be labelled as rendered pixels, not raw samples.

After export, report file list, sizes, hashes, source and transform IDs, what was cropped/resampled/rendered, and what fields the output format cannot preserve. The reviewer can reopen the project, compare values/metadata for the crop, and inspect table/overlay alignment without trusting a screenshot.

## Incremental delivery and proposed acceptance

1. **Contract and fixtures:** freeze axis/centre/coordinate conventions, error states, project schema, curated 2D/3D/T/C/integer/float TIFF and NGFF files, and malformed/ambiguous cases. Include nonzero origin, non-unit spacing, reordered axes and vendor numeric strings.
2. **Safe project/import:** create project; inspect metadata/provenance; link or copy source; preserve raw metadata; explicit axis/calibration correction; recover from a partial import.
3. **Bounded viewer:** selected channels, window/level/LUT, slice/time navigation, progress/cancel, byte-limited cache; measure tiled, compressed and chunked fixtures.
4. **Annotations:** points, plane polygons, 2D/3D masks as scoped above; reusable styles, full keyboard operability, visible coordinate readout, undo/redo and save/reopen.
5. **Portability/exports:** move a reference bundle to a second workstation and relink by identity; copy a portable bundle; export table, overlay, label and crop; verify sidecars and unchanged original bytes.
6. **Resource/recovery qualification:** on the stated workstation class, open and navigate a 3 GB test image without a second full-size resident copy; record peak RSS, cache bytes, first-display time, tile latency, cancel response and write/read checksums. Kill the app during staged save/export and verify that either the old committed generation or recovered new generation opens. Repeat shared-storage checks separately; do not infer them from local rename tests.

One small arithmetic check was executed by the candidate (receipt `exec-icoxtwr_`): with origin `(100,100)`, spacing `(2,2)` and indices `(0,0)`, `(7,7)`, the affine formula gives physical points `(100,100)`, `(114,114)` and inversion recovers both indices. It validates only this arithmetic example. It does not execute a reader, napari transform, image, project or export. The app-level validations above remain **proposed/UNEXECUTED**.

## Useful opportunity and alternative

A useful later opportunity is standardizing large vector annotations. The Allen Institute’s Zarr Vectors material describes chunked, spatially indexed point clouds, polylines, meshes and related geometry on Zarr v3; its spec page calls itself a draft “released to spark conversation,” and the Python implementation documents supported versus internal APIs [S13, S14]. This could help if annotation sets become very large or need spatial queries. Keep it as a lead: the project’s initial point/polygon/mask workload is simpler, the spec is draft, and the implementation’s format/stability must be checked before adoption. Store ordinary records in the project schema first; keep an adapter route open.

The main alternative is converting every import into a normalized, chunked OME-Zarr copy before annotation. It gives a uniform read path and can support multiscale/pyramid generation, but costs import time and extra storage, can change samples/metadata if conversion is mishandled, and adds a separate derived copy to identify and recover. For the first version, prefer read-only direct access for already supported sources and opt-in conversion only when a fixture demonstrates that direct access cannot stay bounded. Another viable UI alternative is a custom Qt canvas instead of napari; it avoids napari’s layer-model/export assumptions but shifts multidimensional rendering and annotation tools onto the small team. Defer cloud collaboration, concurrent editing, automatic segmentation and registration; none is needed to exchange recoverable project bundles.

## Assumptions and unresolved dependencies

The plan assumes local Python/Qt packaging is acceptable, source images can be opened read-only, ordinary shared storage supports eventual file exchange, and the team can provide representative, shareable test files. It does not assume the candidate libraries are mutually compatible, that all TIFF series are lazy, or that OME-Zarr metadata is complete/correct. Validate decoder dependencies and licenses, napari embedding and key bindings, physical-axis conventions, cache size, shared-storage rename/locking semantics, and the specific TIFF/NGFF compression/layout matrix before release. Preserve useful unsupported inputs and metadata while those questions are open.

The small candidate check and discovered-source history are recorded in `witnesses.json`; unresolved and optional work is itemized in `leads.json`. This proposal begins from the supplied biomedical brief and records sources discovered for this task; it is not a claim about another arm, evaluator, or independent autonomous-discovery capability.
