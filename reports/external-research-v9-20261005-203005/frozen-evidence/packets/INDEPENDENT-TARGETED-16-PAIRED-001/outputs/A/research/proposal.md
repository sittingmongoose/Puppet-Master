## Finding: separate absence, unsupported input, and missing input

The frozen lead L5 says “tifffile does not read CZI,” citing CZI’s absence from the tifffile README. That inference is **not established**. The complete README capture for tifffile 2026.9.20 lists supported TIFF-family readers but does not claim to be an exhaustive negative list; omission is not an explicit unsupported statement [S5]. The available source-code search was incomplete: the raw module capture contains only the first 524,288 of 988,932 response bytes, and GitHub’s code-search API returned HTTP 403 rate-limit [S17–S18]. No reviewed source establishes CZI support either. **Disposition:** retain CZI as outside this workspace’s proposed v1 by product choice, and leave the claim about tifffile’s complete implementation unresolved. Do not use README omission as proof.

The frozen source context also contains a 404 for `.../CHANGELOG.rst` [S13]. This is an ordinary missing-resource response for that requested path. The same repository’s root listing names `CHANGES.rst`, and the captured `CHANGES.rst` contains release history [S6, S12]. The 404 therefore says nothing about reader capability or absent release history. For the application, a nonexistent user path should likewise be reported as **missing input**, separately from a valid but unsupported image.

There is a true, narrow negative: the tifffile 2026.9.20 README explicitly says OJPEG compression, chroma subsampling without JPEG, color-space transformations, samples with differing types, and IPTC/ICC/XMP metadata are not implemented [S5]. This is evidence for those named TIFF features at that pin, not a universal statement about all image formats or other readers.

There are also source-backed positives that correct the frozen support list. The same README documents TIFF, BigTIFF, OME-TIFF, ImageJ and other TIFF-like readers, as well as tiled/page/SubIFD reads and Zarr-backed region access. It says NDPI files above 4 GB can be read and BIF files and individual tiles can be read; it explicitly says BIF stitching is not performed [S5]. Thus “NDPI unsupported” is false as a claim about tifffile 2026.9.20, and “BIF unsupported” needs the narrower wording “BIF stitching is unsupported.” A workspace may still exclude either family from v1 for validation and scope reasons. VMS is not established either way by the inspected materials.

## Proposed workspace and data contract

**CHOICE — component boundary.** Use a Python/Qt desktop shell with a reader service and a project store. For the first implementation, evaluate napari as the image canvas/layer engine; keep source resolution, import decisions, annotations, provenance, and persistence in application-owned adapters. A custom canvas is a bounded alternative if napari embedding or version pinning proves costly. This is a design proposal, not a claim that an assembled application meets the requirements.

The precedents contribute independent mechanisms. OME-NGFF 0.5 is a community data-contract precedent for named axes, units, and ordered per-level scale/translation transforms [S1]. napari documents separation of contrast-limit display mapping from sample values, lazy NumPy-like inputs, world scale/units, and n-dimensional shape behavior [S2–S4]. tifffile is a separate TIFF implementation precedent: its pinned README documents read-region mechanisms and explicit format/codec limits [S5]. QuPath is a separate project/export precedent: its project JSON records image URIs and entries, while its annotation export documentation spells out pixel coordinates and origin [S14–S15]. These are complementary layers, not interchangeable guarantees.

**Minimum workflow and storage.** Create a directory project with versioned manifests, source records, annotations, derived outputs, and deletable cache. Import sources read-only; never rewrite source bytes during import, display adjustment, or annotation. Stream a whole-file SHA-256 with progress and cancellation, retaining URI/path, byte length, reader/version, and an `identity pending` state until hashing completes. Copy large source files only after an explicit portability choice. On reopen, resolve project-relative copies first, then saved URIs/path aliases; if a relocated source’s hash differs, leave it unresolved until the user accepts a new identity. Store original metadata verbatim beside parsed/interpreted metadata and record which value the user accepted when axes or calibration conflict.

The frame record contains stored array-axis order and named axes (including time/channel), unit strings, pixel-to-world transform, and its convention. **CHOICE:** annotation pixel coordinates denote sample centers, with zero at the center of the first full-resolution sample; store coordinates and transforms as binary64. Map named spatial axes to a homogeneous matrix with a declared vector/order convention; time and channel are named non-spatial axes. Derive physical coordinates from that matrix instead of maintaining competing copies. Record every correction, reorientation, geometric transform, or resampling as an operation with source hash, parameters, software/version, and output identity. A display-only window/level, LUT, channel visibility, slice, time, pan, or zoom setting lives in view state and never changes samples. Unsupported or ambiguous calibration remains visible and unguessed; the user can correct it explicitly or keep that source unresolved.

Annotations bind to a source identity and frame version. Each record has a stable ID, point/polygon/mask geometry in source pixel coordinates, style ID, labels, and scope: one plane/time point, a volume at a time point, or the acquisition. Persist annotation edits through an undo/redo command log. Reusable styles and keyboard navigation are minimum UI behavior; metadata and errors must be legible and keyboard reachable, with text explaining source, conflict, and recovery action.

**Save, recovery, and exports.** Use immutable save generations: write and validate the next complete project state in the project filesystem, flush files, then atomically replace one small `CURRENT` pointer. Keep the previous generation until the new one reopens and validates. Exports use sibling temporary paths and publish only after close/validation. This is an engineering design, not proof of crash safety: POSIX `rename` replacement is atomic under its documented conditions, `EXDEV` applies across filesystems, and the man page warns that NFS failure does not imply the rename did not occur [S16]. Probe the group’s actual SMB/NFS/shared-storage behavior before relying on it.

Export a CSV annotation table and a small derived raster (for example TIFF/OME-TIFF or a tested NGFF output). Include an export manifest with source SHA-256, dimensions and axis mapping, pixel/world convention, units, scope, transform/resampling chain, included channels, and whether display mapping or resampling was baked into the raster. State the output sample type and every dropped feature. PNG rendered from a windowed view is a display derivative, not the original samples. A table or overlay without this manifest must not claim that it still refers to the same image. QuPath’s documented full-resolution pixel origin is useful precedent, but our center convention and any external consumer convention must be stated and checked explicitly [S15].

A portable bundle copies selected sources and project state, costs storage and transfer time, and can be large. A reference project avoids duplicate source bytes but depends on shared paths and relocation. Make this a per-source import choice and preserve content identity either way. Do not support concurrent multi-writer editing in v1.

## Bounded import/export support boundary

**CHOICE:** first support a tested subset of tiled/strip TIFF, BigTIFF, OME-TIFF, and ImageJ TIFF with declared codecs and 2–5 recognized axes; do not imply those axis or codec limits are tifffile’s maximums. Admit an OME-Zarr reader only for versioned fixtures the team has actually validated; do not treat tifffile’s TIFF-to-Zarr store as proof of general OME-Zarr compatibility. Pin tifffile and its codec/Zarr dependencies in the app and rerun calibration and boundary fixtures on every upgrade. The README’s listed capabilities are useful precedent, not a compatibility promise for every instrument or every TIFF-like format [S5–S6].

| Input or behavior | External evidence at inspected pin | Proposed v1 behavior |
|---|---|---|
| TIFF/BigTIFF/OME-TIFF and selected ImageJ files | Read support documented; tiled/page/Zarr access documented [S5] | Accept only tested container, codec, axis, and metadata combinations. |
| OJPEG TIFF | Explicitly not implemented [S5] | Reject as `unsupported feature`, retain project and source bytes. |
| CZI, VMS, or other unvalidated vendor format | This search does not establish tifffile-wide absence or support | No v1 adapter by choice; show unsupported/unrecognized distinction and preserve the project. |
| NDPI | tifffile documents read support, including >4 GB; notes performance/metadata caveats [S5] | Defer from v1 pending the group’s file fixtures; describe as app scope, not library inability. |
| BIF | tifffile can read/decode individual tiles, but does not stitch [S5] | Exclude whole-slide stitching workflows until separately implemented and validated. |
| Ambiguous axes/calibration, malformed file, missing path | Distinct conditions | Report separately; never silently guess or overwrite. |

An import attempt first checks existence/access. Missing path is `MissingInput`; a recognized valid format outside the app boundary is `UnsupportedFormat` or `UnsupportedFeature`; a recognized file that fails structural validation is `MalformedInput`; an unrecognized byte stream is `UnrecognizedInput`, not automatically proof of a known unsupported format. The failed attempt may be recorded in project history, but creates no authoritative image source or partial annotation target. Preserve the existing project and original input bytes in every failure path.

## Consequential issue → fix → regression test

The strongest calibration lesson is tifffile issue #319. The reporter compared the same TVIPS file under 2026.2.20 and 2026.2.24 and showed `PixelSizeX` changing from about 1.4208 to about 1.4208e−9 [S7]. Commit `7d9eaedd` added `test_issue_tvips_pixelsize`, asserting the file-native nanometer values and linking the issue; the test commit is the parent of fix commit `edede600` [S9–S10]. The fix comments out the nm-to-m conversion and cites issue #319 in code; the changelog update and release commit identify v2026.3.3 and “Do not convert TVIPS pixel sizes to m (#319)” [S6, S8, S10]. This is a traceable issue→test→fix→release chain, not an issue title or PR link alone.

**Applicability:** pinning the reader matters; the reported regression exists by v2026.2.24, and the named correction ships in v2026.3.3. Do not infer every intermediate build’s behavior without a version matrix. The added test uses a private test asset, and the captured history does not establish that this Goal reran the upstream suite. The workspace should retain file-native `(value, unit)` metadata, record conversion operations, and carry one fixture per instrument through its import path. Issue #54 and the 2021.1.14 changelog entry show a separate OME/ImageJ series fallback response, but no commit-to-regression-test chain was established for that case [S6, S11].

## Validation, opportunity, and alternatives

All checks below are **proposed / UNEXECUTED** in this Goal. First run a discriminator with (a) a nonexistent path, (b) a structurally valid OJPEG TIFF fixture, (c) malformed TIFF bytes, and (d) a known supported TIFF fixture. Expect four distinct statuses; the first three must leave project state and source bytes unchanged. The OJPEG fixture must be verified as a valid TIFF with the OJPEG compression tag before calling the test an unsupported-input test. No such fixture or execution receipt is supplied here. Then test a tiled region read and peak RSS/cancel latency on a 3 GB lab image; proposed initial targets are p95 tile latency below 100 ms, RSS below 4 GB, cancellation below 250 ms. Test save/export interruption on the actual shared filesystem, source hash mismatch on relocation, coordinate/export round trips, and per-instrument calibration through every pinned reader upgrade.

**Opportunity:** export derived masks or small derived images in OME-Zarr after version-specific conformance tests, using the standard axes/units vocabulary [S1]. **Plausible alternative:** embed or build a napari plugin rather than own a canvas; it reuses documented layer and lazy-access mechanisms but leaves project persistence and provenance to this team [S2–S4]. QuPath remains a useful whole-slide/project alternative if the group’s format mix changes, not a feature checklist for v1 [S14–S15].

No full application or image-format runtime test was run in this Goal. The candidate seed records W1–W3 as prior isolated checks, but their code/input are not present in this diagnostic receipt stream; this proposal does not treat those results as newly executed. CZI-wide absence, VMS support, OME-Zarr version interoperability, the 3 GB performance target, shared-storage durability, and the lab’s instrument calibration remain explicit unresolved dependencies.
