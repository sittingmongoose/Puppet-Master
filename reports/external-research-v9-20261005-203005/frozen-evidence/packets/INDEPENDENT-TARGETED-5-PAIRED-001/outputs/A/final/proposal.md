# Local biomedical image review workspace — decision proposal

**Stage:** D-V16-A-treatment-diagnostic-a001 · **Date:** 2026-10-06  
**Evidence basis:** the supplied candidate research report and public source captures; this proposal does not establish autonomous source discovery. Source IDs resolve in `sources.json`. Witnesses distinguish isolated checks from unexecuted application validation. Labels: **[FACT]** public-source fact; **[INFER]** engineering inference; **[CHOICE]** reversible product decision; **[CHECK]** executed by candidate; **[VALIDATION]** proposed, UNEXECUTED.

## Decision

**[CHOICE]** Build the first desktop increment as a napari-based application/plugin with a project-owned data model, a read-only reader service, explicit coordinate frames, and annotation persistence independent of viewer state. Use napari for layer display, lazy-array viewing and ordinary 2D drawing; own project save/reopen, annotation identity, undo/redo, frame corrections and exports in the application. Use `tifffile` behind the reader interface for the initial TIFF-family support boundary. Keep the choice conditional on an early plugin and performance spike: the cited napari documentation describes useful mechanisms, but does not prove a packaged application meets this brief.

This combines three independently useful precedents. **OME-NGFF 0.5** is a format specification for named axes, units, coordinate transforms, display-channel metadata and integer label images [FACT S1]. **napari** is a separate viewer implementation whose docs describe lazy NumPy-like arrays, multiscale layers, per-layer world transforms and shapes [FACT S2–S4]. **tifffile** is a separate reader implementation exposing data from TIFF strips, tiles, pages, SubIFDs and pyramids as arrays [FACT S5]. Their mechanisms are complementary: schema, view, and bounded source access. None establishes the behavior of this proposed application.

**[CHOICE]** Use NGFF concepts for the internal frame model and later derived-image interchange, but keep the editable project as a directory bundle with small manifests and annotation files. Do not claim every internal affine can be represented as NGFF 0.5: its multiscale coordinate transforms are scale and translation only, with transforms applied sequentially and translation after scale [FACT S1]. Export only a representable subset or write a new resampled derivative with its operation recorded.

## Source-backed lessons that change the design

### Calibration can change silently in a reader release

A useful public issue → regression assertion → fix → release chain is tifffile #319. The issue body, opened 2026-02-26, reports `PixelSizeX` as `1.4208036661148071` with tifffile 2026.2.20 and `1.4208036661148072e-09` with 2026.2.24 [FACT S6]. The regression-test commit `7d9eaedd` (2026-03-03 18:56:28Z) adds `test_issue_tvips_pixelsize`, cites #319, and asserts the file-native values. Ten minutes later, commit `edede600` (19:06:33Z; parent `7d9eaedd`) comments out the TVIPS nm-to-m division and cites the issue in code. Changelog commit `8c91499e` and release commit `503cb4eb` then identify v2026.3.3 and “Do not convert TVIPS pixel sizes to m (#319)” [FACT S7–S9, S14]. The test commit therefore precedes the code-fix commit in the captured history. The issue, code comment, test URL and release note support the linkage; this is more than an issue title or PR link.

**[INFER]** Treat imported calibration as a value-plus-unit interpretation, never as a bare number. Preserve the original metadata bytes and parser version; record any unit conversion or user correction as an operation. Pin each reader/dependency set and keep small calibration fixtures for each supported instrument. The source chain establishes public repository changes, not an execution receipt for that regression test or proof about the group’s files. The captured test names a `TVIPS_bin4.tif` fixture; this stage did not execute it.

### Axes and export conventions are contracts, not display details

**[FACT S1]** The captured NGFF report is v0.5, dated 2026-10-01, at repository revision `d9164040…`. It requires unique axis names, axis count/order to match the array, and (for multiscales) 2–5 dimensions, explicit scale per level and ordered scale/translation transforms. The `omero` channel-rendering block is transitional; label images are integer arrays [S1]. **[FACT S3]** napari uses layer scale/translation and units for data-to-world rendering, while labels and units remain different metadata. **[FACT S10]** QuPath 0.7 documents its annotation coordinates as pixels from the top-left of the full-resolution image and warns that other software may expect a different origin or units; its GeoJSON export also converts ellipses to polygons. Therefore every export below states its coordinate convention and losses rather than relying on a filename extension to imply them.

**[FACT S5]** tifffile documents tile/page/segment-oriented access and known unimplemented or vendor-specific cases. **[FACT S2]** napari documents lazy array evaluation and a multiscale path. These support choosing bounded access as the mechanism, not a claim that the 3 GB / 16 GB target is already met. In particular, codecs, metadata precedence, dependencies and application caching must be tested together.

## Minimum workflow and data contract

1. **Create/import.** Create a project before adding an image. Open source files read-only. Write an import record to a temporary project generation, then publish it only after parsing completes. Record status `ready`, `ambiguous`, `unsupported` or `interrupted`; on failure retain the project, source URI/path, available header metadata and readable error rather than discarding project state. Never rewrite the original image as an import side effect.
2. **Inspect.** Show format, reader/dependency versions, array shape and dtype, original axis order, parsed metadata, calibration values/units, provenance and source-identity status. Preserve original metadata verbatim separately from parsed/corrected metadata. If axes or units conflict, present the competing values and an explicit choice: map axes/calibration, leave calibration as pixels/unknown, or keep the source unresolved. Store the choice and its reason as a reversible correction record.
3. **Navigate/display.** Browse named spatial, time and channel axes; choose visible channels, slice/time, contrast/window, colormap and zoom. These settings belong to view state. A view contrast change only maps values to display and cannot write to the source. Any exported rendered preview is a new derivative that records baked channel/window/color settings.
4. **Annotate.** Support points and polygons on an XY plane and masks as integer/binary label data. Plane annotations name fixed `z` and `t`; volume masks span `z` at a named `t`; acquisition-level records are not accidentally restricted to the currently visible plane. By default annotations are independent of the displayed channel; a channel-specific annotation must say so. Persist reusable styles and keyboard navigation. Provide undo/redo through the project’s own command stack and persist annotation edits across reopen; do not assume viewer-layer history is a durable project log.
5. **Save/close/reopen.** The project records source identity, paths, geometry, annotations, styles, view state, operation history and export provenance. Reopen first verifies the project generation, then resolves sources by stored URI/path or a workstation path map. A relocated source relinks automatically only after whole-file SHA-256 matches. On a mismatch, keep unresolved or explicitly accept a new image identity and mark prior annotations as suspect/detached. A project that references large external files must say it is not self-contained.
6. **Export/verify.** Export a CSV annotation table and a small rendered PNG preview (or overlay); the preview is a derived view, not a copy of the source samples. Offer a type-preserving OME-TIFF crop only when it can keep sample values and calibration or records the required transform. Write all outputs to a staging path and publish only after validation. Report source and output hashes and exactly which metadata, sample values, geometry, channels, display mapping and annotation semantics were preserved or lost.

### Coordinate and identity schema

**[CHOICE]** Preserve source array axis order exactly in the source record; include an axis-name/type/unit list in that same order and a mapping from displayed `u,v` to named spatial `x,y,z`. Annotation vertices use named, zero-based full-resolution pixel-index coordinates with integer indices at pixel centers; `t` and `c` are separate selectors rather than hidden spatial dimensions. This center convention is a product rule, not a claim about all readers. A physical point is derived from the recorded frame, in one pinned convention: for axis-aligned geometry, `world_i = origin_i + scale_i * index_i`; where orientation requires it, use `world = A · [x,y,z,1]` with a documented column-vector convention, row-major matrix storage, source/target frame and units. Do not store both an unnamed affine and a scale/origin mapping as competing authorities. Use binary64 for coordinates and transforms.

A source record includes stable source ID, URI and resolved path, import policy, byte size, whole-file SHA-256, array shape/dtype, exact native metadata blob, parsed axes/frame, correction history, reader/dependency versions and verification state. An annotation record includes its ID, source hash and frame revision, kind, geometry or mask asset/hash, scope, `z/t` selectors where applicable, style ID, optional channel binding, labels and edit provenance. Store large masks as separate chunked/tiled data, not giant JSON arrays. Every geometric correction, orientation change, resample or unit conversion gets an operation ID, parameters, input hash, output hash (when a new image is created), software version and affected frame/annotation mapping. Display-only view changes never modify source pixels; an irreversible resample creates a separate derived asset.

A numerical witness illustrates why precision and order are explicit: at `104857.6` px, float32 represents `104857.6015625` (about `0.00156` px error), while this binary64 JSON round-trip is exact [CHECK W1]. For point `(2,3)`, scale `(0.5,2)` then translation `(10,20)` gives `(11,26)`; reversing the order gives `(6,46)` [CHECK W2]. These are isolated arithmetic demonstrations, not a coordinate-pipeline test of napari or this application.

### Project storage, bounded access and recovery

**[CHOICE]** Use a project directory with `project.json`, per-source metadata/provenance, per-source annotation state, immutable derived assets, a disposable cache, and numbered save generations. Keep source images external by default; an explicit “copy into bundle” choice creates a portable copy and verifies its hash. A local `locations.json` can map stable source IDs to workstation-specific paths without changing identity. A zip/bundle made of references remains dependent on those external files; a portable bundle that embeds large sources costs storage and copy time. Never imply that a references-only bundle is self-contained.

The reader exposes a `read_region(source, level, z, t, bounds)`-style API. **[INFER]** Keep a bounded LRU cache (initial design budget 512 MiB, configurable), fetch viewport tiles/chunks, limit prefetch to nearby views, and attach progress and cancellation to import/read/export jobs. The target remains a 3 GB source on an 8-core/16 GB workstation without a second whole-image memory copy. Proposed first acceptance targets are p95 viewport-tile latency below 100 ms, peak RSS below 4 GB over idle baseline, and cancellation acknowledgement below 250 ms; all are **[VALIDATION V2, UNEXECUTED]**, not claims about napari or tifffile.

For recovery, write a complete small metadata/annotation generation and validate it before atomically replacing a `CURRENT` generation pointer with a temporary file in the same directory; retain the last known-good generation and sweep abandoned staging files after inspection. `fsync` behavior and directory durability are platform-specific. Linux `rename(2)` documents atomic replacement, `EXDEV` across mount points, and an NFS case where failure does not prove the rename did not occur [FACT S12]. An isolated local check confirms the old file remains before `os.replace` and that interruption can leave an orphan temp file [CHECK W3]. It does not simulate power loss, test the actual shared storage or give a multi-file transaction guarantee. Before adopting the shared drive, test the generation protocol on the group’s OS/filesystem; on an ambiguous result, reopen and validate both generation hashes before recovery. No concurrent multi-writer editing is in v1; detect a changed project generation and refuse a blind overwrite.

Export staging is separate from authoritative project state: build under a `.partial` name, verify required files/hashes, then publish a uniquely named complete export. An interrupted export is marked incomplete and removable; it does not replace the prior export or image.

### Export contract

CSV rows carry annotation ID/type/scope, named `x_px/y_px/z_px`, `t/z` indices, frame revision and source hash. Coordinates refer to zero-based full-resolution pixel centers in the named image frame. Optional physical columns state their units and source frame. The manifest records array-axis order, screen-to-image mapping, origin convention, image shape and dtype, source URI/size/hash and verification state, annotation/image identity, units and transform history, plus the export format and losses. A rendered PNG records channels, z/t, colormap/window-level, scaling/clipping and output dtype; it does not preserve original integer/float samples, vector annotations or all vendor metadata. A mask overlay also records label values and draw/overlap order. An OME-TIFF crop is labeled derived; include axes/calibration only where representable and list omitted metadata. GeoJSON is deferred until its coordinate convention and consumer interop are tested; QuPath’s warning about pixel origin differences and ellipse conversion is directly relevant [FACT S10].

## Support boundary, failure path and alternatives

**[CHOICE] Initial read boundary:** one TIFF/BigTIFF/OME-TIFF or ImageJ hyperstack file; dimensions up to five, with only unambiguous `t,c,z,y,x` axes; tile/strip access and uncompressed, LZW or Deflate; initial regression fixtures for `uint8`, `uint16`, `int16` and `float32`. Add other dtype/codec/series combinations only after fixture coverage. Do not infer a supported combination from tifffile’s broader format list. **[FACT S5]** the reader documents many formats as readable but also states unimplemented codecs/metadata and warns about vendor quirks (for example incomplete stitching support). Defer CZI, multi-file stitching/whole-slide vendor layouts, OJPEG, unsupported compression, >5D data, unknown/custom axes and conflicting calibration until a reader-specific test set exists.

An unsupported or ambiguous file stays listed in the project with its original metadata, identity and clear reason. It cannot acquire geometry-dependent annotations until the user resolves the ambiguity or explicitly chooses pixel-only coordinates. No silent axis reorder, unit conversion, resampling or in-place repair. This is a maintainable support claim only after the exact format/dtype/codec matrix passes on representative lab files.

**[CHOICE] Alternatives:**

- A custom Qt/VisPy canvas is a fallback if a napari plugin cannot provide required packaged keyboard navigation or editing; it re-creates more viewer behavior and needs a separate spike. Do not keep both implementations in v1.
- A single SQLite/project database may simplify a one-file handoff and transactional metadata save, but has binary merge/conflict costs for six workstations. Keep the directory schema until measured annotation volume or coordination needs justify reconsideration.
- Making OME-Zarr the whole editable project would conflate image interchange with project history, paths, styles and save generations. Use its v0.5 axis/label contract for derived-image interchange first; test writing and independent re-opening before adoption [FACT S1].
- QuPath 0.7 is a plausible platform alternative if whole-slide breadth becomes central: its docs expose project references, entry IDs, summaries and explicit annotation-export coordinates [FACT S10–S11]. The present choice is a napari extension because the brief centers multidimensional microscopy review; QuPath is retained as a lead, not dismissed as a weak product.
- Copying every large source into every shared bundle is not the default. Offer it explicitly when portability outweighs storage and transfer cost.

## Critical assumptions and validation gates

**[INFER]** Main dependencies are napari plugin packaging and persistence; tifffile/codec behavior for the actual instrument files; correct axis and unit interpretation; hash cost for 3 GB files; and save semantics on the actual shared drive. Candidate research did not benchmark or build the application. Source documentation, issue history and the checks below do not resolve those dependencies.

Proposed checks, all **UNEXECUTED**:

- **V1 — lab file matrix:** exercise each supported TIFF variant, axis order, dtype and codec on representative sources; compare parsed shape, raw metadata, axes, calibration and region reads to independent fixture expectations. Regress every reader/library upgrade, including TVIPS-style value/unit checks.
- **V2 — bounded 3 GB review:** on the stated hardware measure viewport p95 latency, total and peak RSS, cache ceiling, hash duration, progress cadence and cancellation. Require the proposed thresholds above or revise the UI/cache plan openly.
- **V3 — persistence/recovery:** kill during generation save and export on each supported workstation filesystem and the actual shared storage; reopen last committed generation, verify hashes and detect `.partial`/orphan generations. Probe NFS/SMB behavior rather than extrapolating Linux local rename semantics.
- **V4 — relocation/identity:** move a reference project to a second workstation/path; confirm matching content hash relinks, changed bytes stay unresolved unless explicitly accepted, and annotation rows remain bound to the correct frame/hash.
- **V5 — export round trip:** export a known subpixel point, polygon and mask; re-import CSV/table and compare binary64 coordinates, pixel-center convention, scope, transform chain, output hashes and PNG display mapping. Confirm source-file hash is unchanged. The CSV arithmetic witness W4 is not an application export test.
- **V6 — workflow/accessibility:** close/reopen after styles, undo/redo and volume-mask edits; exercise keyboard-only navigation, point/polygon placement, mask tools, metadata inspection, errors and recovery dialogs; verify legible text feedback and no color-only state.

## Delivery-form comparison for this diagnostic

A conventional standalone report can place the whole failure history and optional ideas in its narrative, making context immediate but making the current decision harder to scan. This proposal keeps the decision and required contract in the standalone body, with exact capture/pin details in `sources.json`, check receipts in `witnesses.json`, and optional leads plus structured history in `leads.json`. That split helps separate commitments from deferred work; its risk is that a reader may skip a catalog. Inline source IDs, the #319 chain summary and explicit unresolved gates keep the decision understandable without opening one. The inventories preserve detail; they do not replace the proposal’s required meaning or citations.
