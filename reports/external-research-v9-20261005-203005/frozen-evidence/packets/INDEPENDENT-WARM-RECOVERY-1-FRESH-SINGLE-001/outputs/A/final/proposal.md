# Proposal: a reproducible local notebook and data workspace

Stage: I-06-treatment-BLIND-SOURCE-FIDELITY-R001-critic_final-a001. This is a newly authored recovery proposal based on the unchanged brief and the cited public captures. The authenticated prior final was not readable; see the companion critic report.

## Recommendation and claim labels

Build a local-first Python workspace around ordinary Jupyter notebook files, nbformat for document handling, and nbclient for clean notebook execution. Offer DuckDB as an optional in-process SQL engine for tabular workflows after format-specific adapters and compatibility are pinned. Keep the notebook document portable and the runtime provenance in a separate small project manifest and append-only run record. This combines independently useful Jupyter format/execution mechanisms with DuckDB CSV and query-engine guidance; it does not establish a pre-integrated product or compatibility between particular releases. [S1-S8]

**Documented facts** below describe cited captures and are pinned by URL, capture time and content hash in sources.json. **Design choices/inferences** are proposed architecture, not observed product behavior. The capture of current DuckDB docs identifies version 1.5; Jupyter pages identify nbformat 5.11, nbclient 0.11 and Server 2.21. These are research references, not a selected or tested dependency lock.

## Minimum workflow and project record

1. Create a folder project with notebook/script files, a small configuration file, environment lock, data references, immutable source identity records, derived outputs, execution ledger, cache and temporary space. Import identifies a file and records a content digest when the user requests the full read cost; metadata such as path, size and modification time alone is not a durable identity. Copying data is optional.
2. Inspect schema and a bounded preview. Mark previews as samples; do not use them as proof of a whole-file property. Require declared or user-confirmed field types, null/missing-field policy, timestamp parsing/time zone, heterogeneous-value policy and conversion/reject behavior. A conversion error is visible with row/byte location and source value; no malformed record is silently discarded and original bytes remain read-only.
3. Author a Python notebook or transform. Keep row identity separate from display order: for immutable text inputs a source digest plus byte offset/record position can identify an input record; for other formats require a stable key or label identity unavailable. Ordering is only guaranteed where explicitly defined, such as an ORDER BY on a unique key.
4. Support selected interactive runs with progress, cancellation and errors. Treat live-kernel outputs as provisional because notebook display order, actual execution sequence and in-memory state can differ. Record each run's notebook and cell-source digests, observed execution order, kernel/interpreter, dependency-lock digest, parameters, working directory, declared input digests/schema, start/end, status, errors and output digests. A saved notebook's code, outputs and execution counts do not by themselves prove current kernel state or reproducibility. [S1-S2]
5. Provide a clean replay in a fresh kernel/process using the recorded environment and declared inputs. Compare provenance and output hashes with the saved run. Mark output current only when the latest successful run matches code, data, parameters and declared environment; mark stale after upstream code/data/dependency changes and unverified after kernel restart, interruption or untracked effects. Arbitrary Python can read undeclared files or call external services, so without filesystem observation or a complete declaration the product cannot promise all dependencies were captured. Randomness, external services, clocks and unpinned packages remain outside the clean-replay guarantee.
6. Save with a staged temporary generation, flush and atomic rename where supported; persist output-to-run associations in a journal so reopen can select the last complete generation after interruption. On another machine, verify manifest digests and environment requirements, report unavailable paths or packages, then allow replay. Export results with a compact manifest containing source identity, schema, code/environment references, run status and output hashes. Folder exchange is the baseline; a portable bundle is a useful opportunity for one-click handoff.

## Data scale, schema and SQL boundary

DuckDB documentation says CSV dialect/type detection is sample-based: the documented default sample is 20,480 rows, `sample_size=-1` requests sampling the whole file, and non-seekable compressed input may only be sampled from the beginning. The detected type may therefore miss rare later values; allow explicit schema overrides and offer a separately labeled full validation scan when required. [S3] DuckDB's faulty-CSV documentation describes structural errors that stop scanning by default and options that can skip or capture faulty records. The product should default to visible failure/reject records and require a deliberate user choice before excluding rows. [S4]

Use bounded preview/result pages and push projection/filtering to the engine where supported. Stream/chunk or query-backed transforms when an operation permits; do not materialize a full result by default. Truncation must show that rows are omitted and distinguish a known total from an uncomputed count. Keep original data immutable and cache derived results by source digest, schema, transform code/parameters and environment lock. Invalidate matching downstream outputs when any cache-key input changes.

The 8-core/16-GB workstation and 5-GB input are investigation targets, not achieved performance. DuckDB guidance warns that large imports/exports can exhaust memory, that some allocations are not covered by its buffer manager, and that disabling insertion-order preservation may change results unless order is explicitly requested. Avoid promising all operations fit in RAM; budget process memory/temp disk, expose cancellation and controlled failure, and test scans separately from global sort/group operations. [S5,S7]

The brief's CSV, newline-delimited JSON and columnar inputs should have explicit adapters and fixture coverage. The captures reviewed here directly substantiate CSV behavior only; exact NDJSON/columnar support and version compatibility remain implementation checks. Optional DuckDB SQL runs against the same declared local data references. DuckDB's concurrency documentation describes one writer process with multiple read-only processes; serialize project writers with an application lock, detect external folder edits and offer a conflict copy. Do not advertise simultaneous multi-process writes. [S6]

## Untrusted code, support boundary and recovery

Support Python notebooks only in the initial product. Treat notebook code as arbitrary code execution: Jupyter Server's security guidance describes access to a server as access to execute arbitrary code in its environment. Authentication is access control, not process isolation. Launch kernels under a per-project OS/container boundary with read-only original-data mounts, scoped output mounts, no network by default, no secrets, explicit package-install grants, CPU/memory/disk/time quotas and process-tree termination. This constrains usability: users must request access for additional data, packages or network services. Do not rely on import blacklists. [S8]

Use local project locks and write journals; preserve previous complete outputs and recover them after an interrupted save. Show save failures and unresolved conflicts rather than silently overwriting. A plain Jupyter workflow with a separate optional SQL tool is a plausible lower-cost alternative: it retains standard notebook files but gives up integrated lineage, stale-state and result comparison. A later opportunity is a portable manifest and read-only SQL handoff for the colleague who occasionally queries tabular outputs. Real-time collaboration, hosted service, scheduling and extra language kernels remain optional.

## Consequential issue and evidence limits

DuckDB issue #25825 is an open user report of a possible silent final-row loss with explicit CSV buffer sizing. Its comments include a contributor reproduction and link PR #26195. In the captured GitHub API response that PR was open and `merged:false`; its base was `main` at the recorded SHA. The patch changes CSV boundary scanning and adds a regression-test file. This is a concrete report-to-proposed-fix-to-test chain, not evidence that the failure occurs in a released version, that the PR test passes, or that the patch shipped. No DuckDB reproduction, PR test or CI result was executed here. Verify merge/release status and run the regression matrix against the chosen release before relying on this behavior. [S9-S12]

## Validation plan — all proposed checks UNEXECUTED

- On the target 8-core/16-GB machine, profile a 5-GB CSV and columnar fixture through preview, projection/filter, conversion, group and sort. Record peak memory, temp disk, elapsed time, cancellation latency and exact operation limits; do not infer global-operation performance from a scan.
- Exercise CSV, NDJSON and columnar fixtures containing missing fields, nulls, Unicode, timestamps, heterogeneous values and malformed records. Check bounded preview labels, schema overrides, visible rejects, stable identity/order rules and source-byte hashes.
- Edit upstream code, source bytes and environment locks separately; verify dependent outputs become stale. Restart and interrupt kernels, then verify old outputs cannot remain marked current. Compare clean replay outputs and provenance with interactive runs.
- Reopen and replay a folder on a second machine; test missing dependencies and data references, two-writer locking, external edits, crash during staged save and recovery to the prior complete generation.
- Test sandbox denial of network and unauthorized paths, package-install grants, quotas and process-tree cancellation under the chosen OS/container runtime.
- Once versions are pinned, verify adapter/runtime compatibility and run the upstream CSV regression case on the chosen DuckDB release. All of these are proposed checks, not results.
