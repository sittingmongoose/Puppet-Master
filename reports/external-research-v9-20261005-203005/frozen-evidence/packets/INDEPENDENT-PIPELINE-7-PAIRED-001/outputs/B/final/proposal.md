# Local biomedical image review workspace

**Stage:** I-07-LUNA-CLOCK-FRESH-R001-treatment-critic_final-a001, independent critic and final author. No full application was built.
**Evidence labels:** **External fact** is stated by a pinned source. **Inference** is an engineering conclusion. **Choice** is the proposed design. **Validation** is UNEXECUTED unless listed as candidate-executed in `witnesses.json`. This research tool does not diagnose patients.

## Proposal

**Choice.** Build a local-first desktop workspace with a Qt shell, napari canvas behind a narrow adapter, tifffile for a tested TIFF subset, OME-NGFF 0.5/Zarr v3 for project-owned chunked image and label assets, and a versioned manifest plus SQLite for image identity, metadata interpretation, annotations, view state and operation history. Keep image chunks outside SQLite. The shell owns project/recovery semantics; the viewer owns rendering and interactions.

The reviewed pins are napari v0.5.6, tifffile v2026.9.15 and Zarr 3.3.0. They are source pins, not a compatible dependency lock. Before implementation, resolve an exact Python/Qt/NumPy/Dask/imagecodecs/tifffile/Zarr/napari set and run an integration smoke test. If the viewer stack does not resolve or meet interaction/accessibility needs, use a custom PySide/VisPy canvas with the same data contract and budget for additional viewer work. Neither route is proven to meet the 3 GB target.

## Independent precedent and critic findings

**tifffile is an independent pixel-access precedent.** Its v2026.9.15 README describes NumPy/Zarr access from TIFF strips, tiles, pages, SubIFDs and pyramidal levels and demonstrates slicing a tiled OME-TIFF via a Zarr store. This supplies a plausible bounded-read mechanism for layouts tested by the project; it is not an RSS/latency guarantee. The same README says TIFF support is a subset, names unsupported features, lists imagecodecs as needed for many compressed segments and Zarr 3.3.0 as the tested Zarr version. A large compressed strip/page, codec expansion or unsupported TIFF variant may still exceed memory or fail. [T1]

**napari is a separate interactive-viewer precedent.** Its v0.5.6 Layer source exposes named axes and units, homogeneous affine transforms and a chain from tile to data to physical to world to grid. The documented slice cache currently applies to Dask arrays. Its layer UUID lasts only for a viewer lifetime. Use these mechanisms for canvas and slicing, but own durable source identity, project persistence, annotation scope, undo, correction history and exports in the app. The two projects solve different boundaries, and the reviewed sources do not establish that their pins integrate or perform together. [N1, N2]

**OME-NGFF is the storage/interchange precedent.** Version 0.5 uses Zarr v3. Multiscale axes must match array dimension order; the profile permits 2–5 dimensions, 2 or 3 spatial axes and optional time/channel/custom axes. Per-level multiscale transformations are scale and translation only, with translation after scale. Labels provide an integer-mask convention associated with image geometry. Version 0.4 is a distinct Zarr v2 generation. Recognize versions explicitly; do not relabel v0.4 metadata as v0.5. Store a full app affine in a sidecar. If a downstream NGFF profile cannot express rotation or shear, retain the external source with a recorded view transform or resample to a separately identified derivative. The label convention does not define vector annotations, app styles, undo or provenance. [O1, O2]

**Consequential issue → fix → test → release chain.** Issue #334 reports that Micro-Manager 1.4 MMStack OME-TIFF files with string `Summary['z-step_um']` such as `'2.9033'` failed with `TypeError` in tifffile releases 2026.5.2 through 2026.9.9. In the pinned v2026.9.9 → v2026.9.15 compare, code commit `6e0a02f10fc763abd94aee0a0ab8225b4b8860a9` adds guarded `float()` parsing for `PixelSize_um`, `z-step_um` and `Interval_ms`; test commit `ed361c575930474938b5552c6745fbf2fa513cee` adds `test_read_mmstack_zstep_str`; the diff includes the change log and v2026.9.15 release commit. The regression test checks that the raw string remains, the series is `(3,2048,2048)` with `ZYX` axes, coordinates are approximately `[0,2.9033,5.8066]`, and pixels match reading without MMStack interpretation. [T2, T3]

The chain has material limits. The test has `skipif(SKIP_FILE)` and depends on a fixture; the patch is not a test-run receipt. The code falls back to `0.0` on parse `TypeError`/`ValueError`, and the MMStack Z coordinate uses `abs(zstep)`. Thus the reader's parsed coordinates can hide malformed calibration and discard signed Z direction. Preserve raw metadata and parser output separately; the app must show missing, malformed, interpreted and user-corrected calibration explicitly, and must not infer orientation from this value alone. The chain covers a concrete regression, not all MMStack files, other formats or performance. [T1, T2, T3]

**Persistence boundary.** SQLite documents transaction recovery subject to OS/filesystem/device flush assumptions. WAL requires same-host shared memory, does not work over a network filesystem, and the WAL file is part of persistent state while open. SQLite transactions do not atomically include image assets stored beside the database. Use local editing, a staged asset protocol and closed handoff bundles; test filesystem semantics directly. [D1, D2]

## Supported workflow and data contract

1. **Create and import.** Create a schema-versioned local project. Default to a read-only source reference. Offer an explicit choice to bundle untouched source bytes or make a lossless project-owned chunked copy, showing the storage estimate. Never open the original in write mode. Stage each import and do not register it as active until metadata, shape, dtype and checksums validate. Cancel leaves the prior project intact and partial assets unreferenced/recoverable.
2. **Inspect metadata.** Record source SHA-256, byte size, URI/relative-path hint, selected series, raw axes and metadata bytes/digest, reader/version, shape, dtype and raw calibration fields. Display raw declarations beside app interpretation. Distinguish missing from malformed. Preserve unsupported fields. A user correction appends a new mapping/unit/orientation with actor, time and note; never overwrite raw metadata or silently apply unit spacing.
3. **Navigate and display.** Support tested 2D and 3D spatial data, channels, time, integer and float samples. Keep the original array-axis order and map explicitly to names such as `T,C,Z,Y,X`; never infer semantics from shape. Store visible channels, per-channel window/level or intensity mapping, LUT, blend, slice and time as view state. Display settings only transform preview values. Show text labels for original, view and derived data.
4. **Annotate.** Support points, polygons and masks, reusable styles, keyboard navigation and undo/redo. Every annotation has a stable UUID, source-content ID, selected series, geometry revision, type, coordinate frame, scope, applicable time/slice/channel, author/time and style ID. Scopes are frame/slice, volume or acquisition; acquisition notes have no fabricated pixel geometry. Store vectors in float64 and masks as chunked integer labels. Persist undo commands and mask tile deltas.
5. **Save and reopen.** Keep project metadata and assets versioned. A changed/missing source remains unbound while annotations stay inspectable. Relocation requires an explicit file, full content hash, series and geometry match; never bind by filename alone. A reader upgrade that changes geometry creates a visible new interpretation, not a silent reassignment.
6. **Export and verify.** Write a coordinate table with a JSON/schema sidecar; optionally write an OME-NGFF label image, an OME-TIFF crop of original samples, and a flattened PNG overlay for review. The export dialog states preserved, changed and omitted data. Reopen each output with another reader and compare axes, values, units, coordinates and mask alignment.

**Coordinate contract.** Product choice: integer source indices refer to voxel centers. Keep storage order separately and use XYZ for spatial affine operations. Store a float64 homogeneous transform from source index `[x,y,z,1]` to a named physical frame, explicit axis permutation, units, origin, orientation/handedness and geometry revision. Time origin/step/unit and channel IDs are separate. Preserve irregular timestamps/plane positions when available; the first physical-geometry profile supports regular invertible affine grids. If geometry is unknown or irregular and not explicitly mapped, allow index-only annotation but do not claim physical coordinates. This center convention belongs to the app, not to OME-NGFF. Convert screen/tile/pyramid positions back through the recorded transform chain to full-resolution source coordinates before saving.

Any geometric transform/resampling is a distinct operation node with parent source ID, transform, target axes/origin/sampling/shape/dtype, interpolation, software/version, actor/time and output checksum. It creates a new data ID. Display window/level creates no data node. A noninvertible or unknown mapping is marked unresolved and cannot be exported as if it were equivalent to source geometry.

**Source identity and relocation.** Hash large sources in cancellable background work with progress; identity is provisional until complete. A reference can change while open. Check file identity/size/time before and after hashing and before later reads; a detected change stops annotation/export pending revalidation. These attributes are race detectors, not content identity. For stronger snapshot guarantees, copy bytes or use a project-owned lossless asset. Do not finalize export or cross-machine binding while the hash is provisional. Matching bytes alone do not authorize a changed parser interpretation.

**Save/recovery and shared storage.** Keep an editable working project on the workstation. Use SQLite short transactions and rollback-journal mode initially; choose WAL only after local behavior is tested. Write assets to unique partial paths, flush/hash/validate, promote on the same volume, sync the containing directory where supported, then commit the database pointer. Retain the last good generation. At startup check database integrity, manifest and asset hashes; ignore or offer recovery for incomplete/orphan assets. SQLite journaling does not make asset promotion atomic, so fault-inject every boundary.

For handoff, produce a closed snapshot with schema/app/reader versions, included assets or external references, and hashes. Copy under a fresh versioned name and publish a READY manifest last. If the share lacks reliable atomic rename, the receiver still rejects the bundle until READY and all hashes validate. Do not copy only the main database while WAL is open. The share is for exchange, not concurrent editing. Bundling originals is portable but duplicates large data; lossless chunked copies change container/possibly metadata normalization; references save space but depend on external files and relocation. Label reference-only bundles as non-self-contained. In-place source editing is out of scope.

**Export meaning.** CSV plus sidecar is the authoritative vector representation; include source hash, series, geometry revision, axes/order, index and physical coordinates, units/frame, scope, style and transform lineage. CSV alone may lose schema/style. NGFF labels preserve integer masks and supported image geometry; sidecar carries vectors, provenance and app affine. A direct crop may preserve original sample values and dtype if it performs no resampling/intensity mapping; shift origin and record crop bounds. Disclose omitted proprietary metadata. A PNG overlay is flattened to selected channels/time/slice and display mapping and does not preserve original numeric samples or all dimensions.

## Support and engineering targets

Start with a tested subset of single-file OME-TIFF/BigTIFF, conventional 2D TIFF, ImageJ hyperstacks with explicit axes where needed, and OME-Zarr 0.5. Require explicit series selection. Defer multi-file OME-TIFF, proprietary formats, ambiguous axes/calibration, nonlinear warps, unsupported codecs and any page/strip beyond the configured memory bound. If parsing or geometry is unsafe, preserve the project/source, show the reason and offer cancel, explicit correction, or external conversion with tool/version provenance. Do not promise universal compatibility.

For 8-core/16 GB, use bounded source reads, a byte-capped tile/chunk LRU, few decode workers, viewport priority, cancellation/stale-result tokens and progress. Never call whole-source `asarray()` in normal navigation. Proposed pilot targets are 512 MiB cache, no second full 3 GB in-memory copy, warm p95 viewport below 250 ms and visible progress/cancel for cold reads. These are UNEXECUTED targets. Tiled TIFF examples do not demonstrate them; compression expansion, one oversized page, shared-storage latency, GPU texture limits and annotation density are risks.

All required actions must be keyboard-operable: image/channel navigation, slice/time stepping, annotation mode, commit/cancel, undo/redo, save/export. Provide shortcut hints, avoid stealing keys from text fields, use legible textual errors naming file/series/axis/action, and avoid color-only state. Validate keyboard-only and screen-reader paths.

## Opportunity, alternative and validation

**Opportunity.** OME-NGFF labels offer a standards-based path to share integer masks beside multiscale images. After local save/reopen and identity are dependable, test the result in another NGFF reader. Direct tile access is another opportunity for validated TIFF layouts. Neither is assumed interoperable before tests. [O1, T1]

**Alternative.** A custom Qt/VisPy canvas avoids napari dependency drift and can control coordinate/accessibility behavior more tightly, but adds viewer, slicing and annotation work. Keep the same project contract. A reference-only TIFF reader plus table/PNG export saves storage but weakens portability. Optional later leads include Bio-Formats/BioIO/vendor adapters, OME-Zarr 0.4 conversion, remote chunk reads/shared catalog, segmentation and registration; preserve provenance and human review if considered.

**Proposed/UNEXECUTED gates:** exact dependency lock and viewer adapter smoke test; fixture matrix across 2D/3D, TCZYX, integer/float, multiple series, unknown/malformed calibration, negative Z, OME-TIFF/BigTIFF, ImageJ and NGFF v0.4/v0.5; 3 GB RSS/cache/latency/cancel benchmark on target hardware; coordinate/pyramid/resampling/table/crop/label round trips against an independent reader; hash/provisional/relocation/source-mutation checks; fault injection during import, asset promotion, database commit, export and READY publication on supported filesystems; and keyboard/screen-reader, style, undo/reopen acceptance. The small arithmetic witness in `witnesses.json` is isolated standard-library math, not application, format, storage or export evidence.

The source catalog records exact URLs, pins, locators, capture hashes and applicability. Its IDs used above are O1/O2 (OME-NGFF 0.5/0.4), T1 (tifffile README), T2/T3 (issue and fix/test/release), N1/N2 (napari Layer/release), D1/D2 (SQLite atomic commit/WAL). The issue chain supports only the cited MMStack regression. Neither precedent proves this application's behavior or the workstation targets. Supporting catalog selections are explicit adoptions of the frozen same-arm source, witness and lead catalogs; this proposal's corrections and choices are authored here.
