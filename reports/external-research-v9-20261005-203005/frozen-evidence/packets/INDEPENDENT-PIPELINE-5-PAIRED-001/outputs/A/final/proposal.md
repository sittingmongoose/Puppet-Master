# Local biomedical image review workspace: implementation proposal

**Current stage:** I-05-LUNA-CLOCK-FRESH-R001-treatment-revision-a001  
**Status:** design proposal, not an implemented or qualified application. This is a research workspace, not a diagnostic product.

## Recommendation and evidence status

Build a local desktop application around three independently useful boundaries: a read-only image source adapter, an application-owned annotation/project model, and a viewport adapter. Start with single-file OME-TIFF through `tifffile 2024.9.20` and local OME-Zarr 0.4 stores on Zarr v2; use napari Shapes `v0.5.6` for a bounded interaction spike; store project state in a local SQLite database. These are candidate pins for a fixture-backed prototype, not a validated compatible dependency lock. The package/runtime matrix, 3 GB target, filesystem durability, and every integrated UI behavior remain unverified. If the napari adapter cannot pass coordinate, persistence, keyboard, and round-trip gates, replace only the viewport with a small Qt/VisPy canvas. Keep the data contract and project model independent of either viewport.

**External facts.** OME-TIFF maps IFD planes through OME-XML `DimensionOrder` and `TiffData`; explicit mappings and UUID-linked multi-file datasets mean page number alone is not a reliable Z/T interpretation [S2]. OME-NGFF 0.4 describes 2–5 axes, named-axis order, Zarr v2 layout, per-resolution scale and optional translation, and integer image-label masks [S1]. Its transformations are limited to scale and translation for multiscales. The pinned tifffile README documents Zarr-backed selected reads, Dask access, tested Zarr 2.18.3, codec dependencies, and exclusions including multi-file pyramidal OME-TIFF [S3]. The napari Shapes implementation describes n-dimensional vector geometry, editing modes, feature data, transforms, and Dask caching [S4]. SQLite documents transaction atomicity subject to filesystem, locking, and flush assumptions; the cited atomic-commit discussion is rollback-journal focused [S9]. None of those component sources demonstrates this proposed application or its performance.

**Independent precedents.** First, OME format specifications plus tifffile contribute interoperable axis/metadata semantics and selected file-backed sample access. They address file interpretation and decoding, not annotation editing. Second, napari Shapes contributes a reusable n-dimensional vector editing and display mechanism, not a durable project model. Third, SQLite contributes transactional project-record recovery, separate from both reader and viewport. Their mechanisms and failure modes are distinct; composition still needs end-to-end qualification.

**Revision audit.** The current role manifest admits the same-arm frozen research proposal and its source, witness, and lead catalogs, but no critique artifact. No critic findings are represented as received. This proposal rechecks the affected public-source bytes and states the current retrieval limits; the frozen source catalog and lead inventory are explicitly adopted unchanged. Current fetches of the pinned NGFF page, tifffile README, and napari PR diff returned the same full-body SHA-256 values as the frozen captures. The diff was semantically inspected. GitHub API fetches for issue and release records returned HTTP 403 rate-limit responses; issue, PR metadata, release-note, and center-versus-corner issue details below therefore rely on complete same-arm captures already inventoried in the frozen source catalog [S5-S8, S11]. A newly captured release-page preview was not used to extend those claims.

## Minimum workflow

1. **Create and import.** Make a project directory containing a versioned manifest, `project.sqlite`, an `assets/` area for optional copied inputs, `derived/`, and recoverable staging directories. Default import is a read-only external reference; never open an original for writing. Offer an explicit copy-into-project choice. For copies, stream to a unique staging path, report bytes and progress, hash while copying, compare with the source, then install the verified copy and commit its database row. Install bytes before committing the row; a crash between those steps leaves an orphan that recovery can identify, while an incomplete staging copy is not a usable asset. Cancellation removes or quarantines staging data without touching source. Retain original metadata payload bytes or lossless text, parsed interpretation, reader/decoder versions, import warnings, original path/name, and any reviewed correction.
2. **Inspect.** Show availability, identity and hash status, original path, format and selected series, reader and decoder versions, original metadata beside normalized metadata, dtype, shape, array-axis order, axis names/types/units, channel labels, calibration, origin state, and unresolved warnings. Do not infer that generic TIFF page order means Z or T. For unknown or contradictory axes, preserve the raw metadata and import report, leave the series unusable until a user explicitly chooses or corrects its interpretation, preview that choice, and record who made it and when.
3. **View and navigate.** Provide visible channel selection and color, per-channel window/level and intensity mapping, slice and time controls, pixel and physical readouts, and keyboard navigation. Store these as `ViewState`; mapping, LUT, gamma, channel mix, and contrast affect rendered values only. Label original samples, display views, masks, and other derived data distinctly. Decode selected planes or chunks on workers with a bounded cache (512 MiB is an initial product setting to measure, not a component guarantee), coalesce duplicate requests, show progress for long reads or hashes, and let users cancel between I/O/decode units. A GPU may accelerate display but cannot be required for correctness. Never materialize the complete source merely to paint one view.
4. **Annotate.** Support points, 2D polygons/paths, and raster masks. Give each annotation a stable UUID, source asset identity, type, geometry, named coordinate axes, coordinate basis, transform reference, scope/selectors, style ID, author and edit timestamps, and free-text fields. Scope is explicit: a plane mark fixes the selected slice and time; a volume mark uses 3D geometry; an acquisition mark states whether time/channel selectors are a particular index or `all`. Never infer that a 2D polygon spans the stack or time series. Version reusable styles with stroke/fill/width/opacity and label defaults. Persist edit commands with before/after state for vector changes; for masks, persist changed tile/chunk patches or reversible versions rather than copying a whole mask per stroke. Commit a command and its resulting state transactionally. Keep undo/redo history after close and reopen; keyboard shortcuts must be discoverable and remappable.
5. **Save, close, and reopen elsewhere.** Commit project rows, annotations, view state, and command history in SQLite transactions. On reopen, validate schema, database integrity, asset identity, axis/transform records, and command history before enabling edits. For missing references, offer explicit relocation and compare full identity. If the candidate has different bytes, keep existing annotations bound to their former identity and require cancel, fork, or an explicit reviewed rebind; never silently retarget. Test another workstation or clean profile. Shared storage is a transfer path for closed bundles, not a live shared database or concurrent editing protocol.
6. **Export and verify.** Export an annotation table (CSV plus JSON sidecar), a transparent rendered overlay for a selected image/time/channel/slice/view, and one bounded small image crop. Write each to staging, close and reopen it with an independent reader, verify hashes and recorded semantics, then publish and register it. A failed export leaves its previous final path and committed project state intact.

## Data and coordinate contract

An image asset has an internal UUID and a content identity. For a file, identity is whole-file SHA-256 plus byte length; for a directory-backed Zarr store, use a deterministic inventory of relative keys, sizes, and per-object hashes, then hash that inventory. A hash remains `pending` until a complete cancellable pass finishes. Show this state and mark exports provisional until the full identity is checked. Paths and timestamps help locate files but never establish pixel identity. Keep a relative bundle path when copied, the original external URI/path, format/series identifiers, dtype/shape, untouched metadata payload, parsed metadata, exact axis names/order, reader/decoder pin, provenance, and calibration record. Do not treat a byte digest as scientific provenance or authenticity.

Define array-index coordinates as continuous coordinates whose integer values are sample centers; therefore index `(0,0)` is the center of the first array sample and its upper-left array corner is `(-0.5,-0.5)`. This is an application convention that needs explicit user documentation and viewer-level validation. Keep array axes named and ordered. Persist a homogeneous transform `M(world <- source_index)` with named input and output axes, units, convention, float64 coefficients, provenance, and inverse or invertibility result. A supported diagonal calibration may be written per named axis as `physical = translation + scale * index`; a general reviewed affine must retain its matrix. Never swap displayed row/column and world x/y implicitly. Channel is a selector, not a spatial coordinate; time uses its own index or time unit and never the spatial calibration. Record unknown origin as unknown, distinguish assumed local zero from measured or user-corrected origin, and do not label guessed calibration as physical truth. Reject non-finite and singular transforms.

For each image-pyramid level, preserve its exact axis order and level transform. NGFF scale/translation can represent its documented simple mappings; it cannot faithfully encode arbitrary affine or nonlinear correction [S1]. If source axes/calibration are ambiguous, preserve raw metadata and let the user select a reviewed mapping, use source-index-only annotations with physical placement explicitly unknown, or reject annotation use while retaining an import report. A correction is a separate project record and never overwrites vendor metadata. For a crop starting at source index `k`, derive the output transform by composing the source transform with the index offset; for resampling, create a new asset and record interpolation, output shape/dtype, parameters, transform, software pin, and operation UUID. The annotation remains attached to the original unless the user explicitly transforms or rebinds it.

## Components, support boundary, and failure handling

**Reader choice.** Start with local OME-Zarr 0.4/Zarr v2 and single-file OME-TIFF series whose metadata, axes, codecs, dtype, and plane mapping pass a named fixture matrix. The tifffile README shows selected access through an `aszarr` store and opening a Zarr view in read mode; it also shows writable mode and examples that write through the store [S3]. The application must enforce read-only handles (`mode='r'`), never expose write mode in the reader adapter, and never patch TIFF tags. Compressed segments may need imagecodecs. TIFF strips can require decoding a whole strip even when the viewport asks for a small rectangle; therefore bounded requests do not guarantee bounded decode cost or latency. A chunk/tile layout plus a cache is a target, not proof of 3 GB responsiveness. Do not initially accept multi-file pyramidal OME-TIFF, arbitrary vendor TIFF, unknown compression, axes outside tested permutations, unsupported sample types, or calibration that cannot be interpreted. No extension-only compatibility promise.

**Viewer choice.** Run a napari `v0.5.6` integration spike behind an adapter. Use layers to display image and annotation interactions, but let the application own source identity, scope, coordinate transforms, styles, database persistence, undo/redo, exports, and recovery. napari Shapes offers a relevant editing precedent, but does not prove our persistence or transform mapping [S4]. Disable any path that can write into an original. If canvas coordinate inversion or keyboard accessibility cannot pass the gate, keep the storage/reader contract and replace the canvas with Qt/VisPy. Dependency and packaging compatibility for the full stack remains a critical unknown.

**Rejected inputs.** Unknown codec, malformed metadata, unresolved axes, unsupported multiscale mapping, or missing files produce a visible non-destructive report with raw metadata and source identity where readable. Do not register a partially read series as usable. Offer select-series, reviewed axis/unit/origin correction with preview, retry through a qualified adapter, or cancel. Preserve the project and source bytes. Do not turn a guessed axis mapping into a silent default.

## Persistence, exchange, and recovery

Keep one local writer per working copy. Use SQLite transactions for annotation changes and undo/redo commands, with rollback-journal mode as the initial choice. SQLite documents atomic commit under assumptions about locking, filesystem writes, and flushes [S9]; that does not qualify SMB/NFS or any lab share. On startup, use SQLite recovery, integrity checks, and a verified rolling backup; present a recoverable error rather than overwriting corruption. Do not support simultaneous shared-file writers.

For copied originals, stage, hash, verify, and install data before committing the asset row. For large chunked masks or derived images, write to a temporary project-owned store, verify its manifest, then commit a reference only when complete; clean up orphans after crash recovery. For bundle exchange, close the database, create a SQLite backup/snapshot, copy it and selected verified assets into a sibling staging bundle, generate a manifest of all payload hashes, and write a completion marker only after verification. Publish using a same-filesystem rename only on filesystems the team has tested; retain the prior bundle until the new one reopens cleanly. These steps are candidate recovery options, not a universal atomicity guarantee. A crash-injection test must establish the behavior on each workstation OS and storage route.

Reference bundles are small and avoid copying multi-gigabyte sources, but depend on path relocation and full byte identity. Portable bundles copy selected originals, consume more storage and time, and need copy/hash progress. Let the user choose per source, estimate bundle size, and label missing or external dependencies prominently. Six researchers can exchange closed bundles in ordinary storage; first-version edits are local copies, with conflicting copies resolved explicitly by people.

## Export meaning

The CSV contains one row per annotation with annotation/asset UUID, source content identity, series, geometry type, named axes, coordinate basis, compact geometry, explicit selectors including `all`, units, style ID, and transform ID. Its JSON sidecar includes full transforms, axis order, origin/calibration state, data-operation lineage, and coordinate convention. CSV alone is insufficient to reconstruct calibrated geometry.

The transparent PNG overlay preserves only rasterized geometry and its alpha over one named rendered view; sidecar records selected plane/time/channel, channel combination, window/LUT/gamma, slice, opacity, rasterization and image binding. It is not a raw image, all-view representation, or lossless point/polygon record. The small crop is a new derived image containing only selected sample values and dtype if the direct crop path is validated; encoding, pixels, and metadata are not byte-identical to the original file. Any resampling changes pixels and must be a separately confirmed operation recording interpolation and output transform. State which source metadata was copied, normalized, or omitted; preserve lineage and hashes in a sidecar. NGFF `image-label` is an optional integer-mask interchange, not a replacement for points, polygons, scopes, styles, history, or the project database [S1].

## Consequential failure/fix/test chain

napari issue #6068 reports that in 3D a multiscale Labels layer could display the coarsest level while ray-based mouse sampling used unreduced coordinates and raised an out-of-range `IndexError`; the report names napari 0.4.18 [S5]. PR #6317 was merged as `e2baaa7b3ff8a0bd7d6e3c8db5ab39ff6746bb7d`, with a 0.4.19 milestone [S6]. The re-fetched full diff is byte-identical to the frozen capture (SHA-256 `c85ba6f299a485afc2351721494533d32f2aa705826c9cb694d590e11227a8b9`, current capture ID `b9851fc3dcb64708a3257e69c64fa7c7`). It sets the 3D Labels data level, divides ray endpoints by downsample factors, computes a level-specific bounding box, and adds `test_3D_multiscale_labels_in_3D` expected-value checks on synthetic repeated 2× pyramid labels [S7]. The frozen release record places the fix in napari v0.4.19 [S8].

The implementation lesson is to use one level-aware mapping for display, mouse readout, and annotation coordinates, then test returned sample values as well as visible overlay alignment. The fix test is a narrow synthetic Labels-ray case; it does not qualify anisotropic/oblique calibration, NGFF interoperability, image export, another viewer version, or the application proposed here. The separate #6320 report describes a center-versus-corner shift when changing pyramid level; no repair/test chain is established in the frozen source record [S11]. Treat sample centers, corners, scale offsets, and every export transform as release-blocking fixtures.

## Opportunities, alternatives, and later work

A useful opportunity is NGFF integer image-label export for masks after independent axis/scale validation. It provides an exchange path for label data while the JSON sidecar retains richer annotations [S1]. A plausible alternative reader is a Bio-Formats adapter for a specific instrument confirmed by the group; its v7.3.1 supported-format list is a discovery map, not proof for a lab's instrument, producer version, metadata, or codec [S10]. Evaluate exact representative files and exact reader releases before adding a format. tifffile's documented fsspec reference output is another optional experiment for referencing TIFF byte ranges; it does not change original identity, guarantee relocation, or qualify access speed [S3].

Remote chunk stores, automatic segmentation, registration, simultaneous editing, and cloud services are optional opportunities. Defer them until local identity, transforms, recovery, and export pass. Keep derived operations explicit so an eventual algorithm or shared read-only store can be added without silently changing originals.

## Proposed validation gates (all UNEXECUTED except witness W2)

1. **Reader and support matrix:** build synthetic and consented representative fixtures for 2D and named `t/c/z/y/x` axes, integer and float samples, OME-TIFF dimension-order and explicit `TiffData` cases, tiled and stripped files, each admitted codec, BigTIFF if desired, and NGFF 0.4 chunks/pyramids. Compare sample values and metadata to independent ground truth. Include malformed, missing, and unsupported files and cancellation. Do not qualify by one successful file.
2. **Bounded 3 GB access:** on the specified 8-core/16 GB target, measure source and decoded memory, cache occupancy/eviction, cold and warm viewport latency, channel/slice/time navigation, progress, hash duration, and cancellation, with GPU off and tiled/strip/compressed fixtures. Agree interaction thresholds with researchers before measuring. Confirm no complete decoded array is allocated. This is not established by tifffile examples or the arithmetic witness.
3. **Coordinate and level fidelity:** use asymmetric unique-value arrays, permuted named axes, nonzero translation, anisotropic scale, reversed orientation, several pyramid levels, selectors, and nonzero origins. Round-trip pointer → source coordinates → world → source; assert centers, corners and level mappings separately; overlay point, polygon, and masks; cover plane, volume, and all-time/all-channel scope. Include the narrow #6068 case and an explicit #6320-inspired test.
4. **Pixel immutability and operations:** hash before/after window/level, channel display, LUT, and gamma. Separately crop/resample, compare values, dtype, output transform, interpolation record and IDs; verify source bytes are unchanged and source-bound annotations move only by explicit operation.
5. **Save, recovery and portability:** inject process termination during database edits, copied import, mask staging, backup, archive creation and publication. Reopen and prove either previous committed state or fully verified new state. Test integrity check, backup restore, source relocation with equal and changed hashes, and clean-profile reopen on each workstation OS/filesystem/share. A SQLite guarantee alone is insufficient.
6. **Exports and accessibility:** independently reopen CSV/sidecar, overlay and crop. Compare source identity, coordinates, selectors, dtype, crop origin and preserved/omitted metadata. Operate import, correction, channel/time/slice navigation, annotation, style, undo/redo, save and export without pointer. Require visible focus, keyboard-operable controls, accessible labels where available, and legible actionable errors.
