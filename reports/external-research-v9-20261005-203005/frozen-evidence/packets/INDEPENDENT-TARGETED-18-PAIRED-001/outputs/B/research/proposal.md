# Proposal: local biomedical image review workspace

**Stage:** D-V12-A-control-diagnostic-a001-resource-v13-a002-BUNDLE-R001. **Evidence status:** design proposal; no application was built. `[FACT]` cites public captures in `sources.json`; `[INFERENCE]` is engineering reasoning; `[CHOICE]` is a reversible product decision; `[CHECK]` identifies an executed isolated check or an unexecuted validation plan.

## 1. Diagnostic finding and method

I selected two supplied public documents because the draft uses them to justify image access and export: tifffile’s README (S5) and QuPath 0.7.0’s annotation export page (S10). I read the full frozen captures, compared direct navigation with mechanical line maps, and matched capture IDs and SHA-256 values to `inputs/source_context/index.json`. The QuPath page is 41,941 bytes / 411 lines; ordinary reads covered lines 1–180, 181–330, and 329–411 (the last two overlap). Its exact body hash is `df12ec58ce64a72dea1596677e444ade4684b12328555ed36fda1175c341f420`, the same capture as the seed catalog. The seed had delivered only 32,768 bytes. The full page’s later warning begins at source byte 34,326, line 331: full-resolution labels for an entire whole-slide image may be impossible; downsampling, pyramids, and tile export are described instead [S10]. This changes the export plan: make region-sized derived images the default, and treat tiled export as a separate, tested operation.

The same page says a labeled image can represent only one class at a pixel; overlapping classes therefore compete, and later draw order wins. Separate binary channels can represent overlaps [S10, lines 224–230, 281–292]. A single label raster must never be presented as preserving all overlapping annotations.

The tifffile README’s full 32,898-byte / 875-line capture also matches its seed source hash, while the seed delivery stopped at 32,768 bytes. Direct reading beyond its overview narrows the reader claim: tifffile documents NDTiff, but explicitly excludes NDTiff v0/v1 series, tiling, stitching, and multiresolution pyramids; MMStack metadata may be corrupt or wrong; BIF and Trestle tiles can be decoded without stitching; and its memory-map example excludes compression and tiling [S5, lines 183–272, 565–575]. Its Zarr slice example is a small tiled OME-TIFF example, not a 3 GB benchmark or a viewer guarantee [S5, lines 759–782].

The mechanical QuPath line map is `out/scratch/qupath-export-line-map.txt` (53,606 bytes, SHA-256 `f1df07908505db35d01b208bb0063a7f98524334d97371be21303212b2ecb9ed`, source hash above). It locates lines 329–337 in the same range as the direct read. The line map is navigation evidence, not semantic evidence. The section renderer returned `JSONDecodeError` on these captured HTML/RST/Markdown inputs; I did not treat that failed aid as a source result. The TIFF line map is also recorded in `witnesses.json`. These captures and the supplied seed proposal were inputs to this diagnostic; this work does not establish autonomous source discovery.

## 2. Decision in brief

`[CHOICE]` Build the first review workflow as a napari plugin with a project and annotation layer owned by the plugin, and a narrow read-only reader service. Keep the project schema independent of napari layer serialization. Napari’s documentation separates contrast limits from pixel values, accepts lazy NumPy-like arrays, and documents scale/units and n-dimensional shape behavior [S2–S4]. This is a useful host precedent, not proof that a plugin meets the 3 GB target. Tifffile is a separate reader precedent for page/tile/chunk access [S5]; OME-NGFF 0.5 supplies an independent, normative axes/units/transform vocabulary [S1]. QuPath contributes a separate project/export precedent, including the qualifications above [S10–S11].

`[INFERENCE]` These mechanisms are independently useful: a format specification does not implement a reader, a TIFF reader does not define a viewer or project lifecycle, and a viewer’s layer model does not define portable provenance. No source alone proves full application behavior. Pin the Python, napari, tifffile, Zarr and codec versions used by each tested build; moving documentation branches are pinned here by exact capture hashes, not treated as stable APIs.

## 3. Minimum workflow and architecture

| Workflow step | Proposed behavior |
|---|---|
| Create project | Create a versioned project directory and a committed empty generation. No image bytes are embedded implicitly. |
| Import | Open source read-only. Store source URI, size, full-file SHA-256, reader/build versions, axes, parsed metadata and original metadata bytes. Stage import separately; publish only after validation. |
| Inspect | Show axis order, sample type, calibration and provenance in readable text. Show conflicting metadata families side by side. Require an explicit axis/calibration choice or mark unsupported; preserve the raw metadata. |
| Navigate/display | Use a bounded region reader on worker threads; cache decoded tiles/chunks under a fixed, configurable memory budget. Channels, LUT, window/level, slice, time, zoom and pan are view state. They never write image samples. |
| Annotate | Store points, polygons and masks with frame, image identity, style and explicit plane/volume/acquisition scope. Persist command-based undo/redo. |
| Save/reopen | Commit a new immutable project generation and atomically switch a small current-generation pointer. On another workstation, resolve an external source only after identity validation or an explicit relink. |
| Export | Write a CSV annotation table, a bounded crop/overlay, and a small derived image plus a provenance manifest. Label every rasterized, resampled or display-baked output. |

`[CHOICE]` The plugin owns source registry, annotations, view state, operation history, export manifests and recovery. The reader exposes `read_region(image_id, level, axes_selection, bounds)` and cancellation/progress; the UI requests viewport-sized data only. No GPU is required. `[INFERENCE]` A chunk cache around 512 MiB is a starting budget, not a measured optimum; the reader must refuse a segment larger than its configured decode budget rather than allocate without bound. Napari’s lazy-array documentation supports the interface pattern, not the memory claim [S2].

A project directory contains a small manifest, immutable generation metadata, per-image source/frame records, per-image annotation documents, derived outputs, a recoverable operation log, and a disposable cache. Give each project, source, annotation and generation a stable ID. Keep the original filename as a label, never as the identity. Use immutable generations so a save affecting several files is recoverable as one published state rather than a sequence of unrelated file replacements.

## 4. Data contract

**Source identity and provenance.** Store a whole-file SHA-256, byte length, original URI, optional project-relative copied path, acquisition metadata, reader/version and import timestamp. A cached size/mtime comparison may avoid unnecessary hashing, but it is only an optimization. Hash before accepting a relink and again before export; mismatch means unresolved or explicitly accepted new identity, with old annotations marked suspect. Keep exact original metadata blobs plus parsed values and any user correction as an append-only, reversible operation.

**Axes and coordinates.** Store axis names, types, order, lengths and units alongside the data. A v1 internal coordinate convention is: integer pixel/voxel coordinates name sample centres in stored array axis order; the first sample centre is index zero. Store a float64 homogeneous affine, matrix layout, column-vector convention and input/output axis order explicitly. For diagonal calibration, `world = origin_at_sample_center + direction × spacing × index`. Derived coordinates are computed from the pinned frame; do not duplicate a rounded physical coordinate as a second authority. Store per-level maps for pyramids. OME-NGFF 0.5 requires axis order to match array order and specifies scale followed by optional translation; translations follow scale and group transforms apply after dataset transforms [S1, sections `axes`, `coordinateTransformations`, `multiscales`]. Its multiscale transform subset does not express every affine orientation, so export only when representable or preserve the full transform in the workspace manifest. Do not silently drop rotation, shear, origin, handedness or anisotropic spacing.

**Annotations.** Each row records stable ID, kind, geometry axes, float64 coordinates or mask reference, source hash, frame revision, style ID, labels, creator/time and operation history. Scope is explicit: plane (`z,t`), volume (3D geometry at a `t`), or acquisition (declared axes and persistence across `z/t`). A 2D outline repeated through a volume must say so; it is not equivalent to a 3D surface. Masks have an explicit grid and integer label meaning. napari Shapes provides useful vector/style patterns but documents slice matching and 2D-only shape editing in 3D; provide volume editing by painting/editing 2D slices into a 3D mask, and do not promise free 3D polygon editing [S4]. Named styles and undo/redo are project features, not presumed viewer persistence.

**Display and transforms.** Keep channel visibility, contrast/window, LUT, selected `z/t`, zoom and pan in view state. Napari documents that contrast limits change visualization, not underlying image values [S2]; this is the intended invariant. A geometric transform, resampling, crop, channel computation or rendered preview creates a derived image with its own identity, grid, operation parameters, input hashes, tool version and output hash. Annotation mapping to it is an explicit transform with a reversible provenance link; it never silently changes the source annotation coordinates.

## 5. Bounded support and failure behavior

`[CHOICE]` V1 supports single-file grayscale TIFF/BigTIFF and single-file OME-TIFF only for tested 2D–5D `T,C,Z,Y,X` layouts, known sample types, and tested uncompressed, LZW or Deflate segments that fit the decode budget. Support tiled files and stripped files only when their decoded segment sizes meet the cap. Require explicit confirmation for absent or conflicting axes/units. Defer ImageJ hyperstacks, NDTiff/MMStack, stitched/pyramidal slide formats, RGB/sample axes, proprietary files, compressed or codec combinations without fixtures, and OME-Zarr until separately pinned and validated.

This deliberately takes a small, testable slice from tifffile’s much broader documented inventory. In particular, its general NDTiff listing cannot be read as support for NDTiff versions, stitching or pyramids it expressly marks unsupported [S5]. Its README describes an unimplemented TIFF subset and format-specific limits, not universal compatibility [S5]. A source that exceeds the byte/axis/calibration policy is retained in a source record marked `unsupported` or `ambiguous`; raw metadata remains available, annotation is blocked on that source until resolved, and the rest of the project still opens. No importer rewrites the original image.

The exact codec, tile/strip, axis and metadata policies are product choices subject to real instrument fixtures. A 3 GB file size alone is not a support classification: the largest decoded tile/strip, metadata topology and reader behavior also matter. The document’s small region-read sample does not settle those questions [S5].

## 6. Save, recovery, relocation and export

**Save/recovery.** Write every changed record into a new generation in the project filesystem, validate schema and checksums, flush files, then write and flush a temporary `CURRENT` pointer and replace it. Keep at least one earlier good generation. On open, validate `CURRENT`; if corrupt, offer the newest verified committed generation and report recovery. Failed imports remain staged or become an explicit unsupported record. Failed exports stay under a temporary name and are never mistaken for completed output. Cache files are disposable. POSIX `rename` documents atomic replacement of a name on one filesystem, `EXDEV` across mount points, and an NFS caveat where a reported failure does not prove the rename did not happen [S12]. This does not make a multi-file save transactional and does not prove SMB/NFS durability. The pointer/generation protocol is a product design to test on each supported storage system; V3 is unexecuted.

**Relocation and portability.** Default large sources to references: store original URI and a project-relative hint; keep per-workstation path mappings in a separate local preference file, not in canonical IDs. Try known paths, then ask the user to select a candidate and verify full-file hash. Never silently bind annotations to different bytes. Offer copy-into-project for selected smaller inputs or an explicit portable bundle; copying is opt-in because a 3 GB file can make exchange slow and duplicate storage. QuPath documents URI-based entries, per-entry data and per-machine project path variants for shared drives [S11]; it also warns that duplicated project files can lead to duplicate IDs if new entries are added. The proposed stable IDs and local path map avoid that specific ambiguity.

**Export contract.** CSV rows carry source hash, annotation ID/type/scope, axes, stored index coordinates, optional derived physical coordinates and units, frame ID, transform chain and style/classification. A raster manifest records source/output hashes, region, full-resolution origin, output spacing and axes, channels, interpolation, thresholding/rasterization, label order, display mapping baked in (yes/no), and operations. State that PNG is a rendered/derived view and does not preserve source intensity precision or metadata. Store numerical coordinates as round-trippable binary64 JSON numbers and test all readers; an isolated arithmetic check does not prove cross-language serialization.

Default mask export uses one binary mask per class (or channel) so overlaps remain representable. A single integer label image is optional and requires an explicit order/overlap rule; QuPath’s docs demonstrate last-drawn label wins and therefore information loss at overlaps [S10]. For large images, export the selected bounded crop as the small derived image; offer overlapped tiles or a pyramid only as a separate operation with origin mapping and boundary tests. Do not promise whole-image, full-resolution label materialization: QuPath’s full page specifically warns that it may be impossible for some large-image formats and demonstrates downsample/tile alternatives [S10, lines 329–371].

QuPath states its own shape export uses pixel units and a top-left origin at full resolution, and warns that other software may use different expectations; its GeoJSON export also changes ellipses to polygons [S10, lines 125–138]. Treat that as a useful warning, not a universal coordinate convention. V1 exports CSV and raster formats with explicit image-space metadata; defer GeoJSON until its coordinate reference and round-trip are specified and tested.

## 7. Issue → fix → regression test and applicability

A consequential calibration lesson is tifffile issue #319. The issue body reports `PixelSizeX` as `1.4208036661148071` with 2026.2.20 and `1.4208036661148072e-09` with 2026.2.24 for the linked TVIPS file [S6]. The next evidence is more than an issue title: commit `7d9eaeddc710af068f9e8c2cf30b10a7d0e5c938` adds `test_issue_tvips_pixelsize`, cites #319, and asserts the file-native values; it is the parent of fix commit `edede6002c817f056d75125ade0b20332d549cca`. That commit comments out the nm-to-m conversion and names the issue URL. Commit `8c91499e…` records the changelog entry `Do not convert TVIPS pixel sizes to m (#319)`; release commit `503cb4eb74dd28a6acc36a0e4624ba9c2001e021` identifies v2026.3.3 [S7–S9]. The parent chain and release are visible in the pinned GitHub API captures.

**Inference:** calibration must be stored as value-plus-unit, and reader upgrades need per-instrument calibration fixtures. **Limits:** issue reproduction, source fix, test diff, changelog and release establish the public history and tested expected value, not this group’s calibration correctness. The regression test refers to `tests/data/tvips/TVIPS_bin4.tif`; the supplied capture set does not prove that asset is publicly available in a clean checkout or that the test was rerun here. The test preceded the fix commit; no PR merge is evidenced in these captures. Applicability begins with v2026.3.3 for this reported tifffile path, and does not establish behavior for other readers or files.

## 8. Assumptions and validation

`[CHECK] Executed by candidate, isolated components only.` W1 uses stdlib arithmetic to distinguish scale-then-translation from the reverse and compares float32 with a binary64 JSON round trip. For pixel `[3,2]`, spacing `[0.5,2]`, origin `[10,-4]`, the intended physical result is `[11.5,0]`; the reversed order gives `[6.5,-4]`. At 104857.6 px, float32 error is about 0.0015625 px; JSON preserves the binary64 value exactly. Receipt `exec-8tot6bkb` includes code, input, stdout/stderr, exit 0 and limits. W2 tests a same-directory temp-file replacement in the isolated sandbox: a simulated exception before replace leaves the target intact and an orphan temp file; replace succeeds and hashes distinguish content. Receipt `exec-deuq9qzg`, exit 0. Neither check tests the application, a real image, power loss, cross-filesystem moves or shared storage.

`[CHECK] Proposed, UNEXECUTED:`

1. Import two representative real instrument fixtures and a synthetic 3 GB OME-TIFF. Record axes, calibration and hashes; request one viewport and distant tile; measure peak RSS, cache bound, p95 latency and cancellation. Initial goals: p95 under 100 ms at review zoom, process RSS under 4 GB, cancel under 250 ms. These are targets, not evidence [S5].
2. Round-trip index→physical→index on anisotropic X/Y/Z grids, nonzero origin, orientation and each pyramid level. Verify centre/corner and axis-order conventions using a tiny asymmetric image; reject any unsupported affine on export.
3. Kill import, save and export at each transaction boundary on local disk and the group’s actual shared storage. Reopen the prior committed generation, report recovery, and confirm no partial export is authoritative. Include SMB/NFS-specific tests before making a durability claim [S12].
4. Export a tiny fixture with overlapping classes, a crop and a downsampled image. Check that per-class masks preserve overlap, any single-label output follows its declared order, the source hash is unchanged, and an export/reimport lands on the intended full-resolution sample centres. Check that display LUT/window choices are declared as baked or not baked.
5. Move a reference-mode project between two workstations with different path prefixes; verify exact-hash relink and mismatch handling. Repeat with an explicit copied bundle.
6. Keyboard-only create/navigate/annotate/undo/redo/save/reopen/export; verify readable metadata and error paths without color-only status.

**Critical assumptions:** tifffile and its codec/Zarr dependencies can decode the team’s selected fixtures inside the memory/latency budget; shared storage honors the chosen commit protocol; import-time calibration correction is reviewable; and the team accepts v1’s narrow format boundary. All remain unverified until these checks pass.

## 9. Opportunities and alternatives

**Opportunity:** later export derived raster data and integer label arrays as OME-Zarr 0.5. The spec defines axes, units, per-level scale/translation and integer label images [S1]. This improves interoperability while keeping OME-Zarr out of the v1 critical path; its storage is Zarr v3 and needs pinned reader/writer compatibility tests.

**Plausible alternative:** use QuPath directly if the group’s work becomes mostly 2D whole-slide review. Its project-entry/reference model and documented tile, mask and shape exports are useful [S10–S11]. For current 3D/time acquisitions, start with a napari plugin and keep QuPath’s pixel-origin, overlap and full-resolution size caveats in the interop tests. If custom plugin ownership becomes too costly, retain QuPath as the platform alternative rather than copying every feature into a new canvas.

Optional leads—GPU rendering, OME-Zarr import, CZI readers, GeoJSON, registration, assistive segmentation, cloud/object storage and multi-writer collaboration—are listed separately in `leads.json`. They are not v1 obligations. The tool remains for research image review and annotation, not diagnosis.
