# Local-first notebook and data workspace — proposal

**Scope.** A small-team research workspace, not a notebook runtime implementation. Research captured 2026-10-06. Tags, PRs and documentation are described as they appeared in the captured public responses. Source IDs resolve to exact capture identities in `sources.json`.

## Recommendation

Use a portable project folder with standard `.ipynb` notebooks and explicit project/data contracts. Reuse the Jupyter Python notebook document and execution ecosystem; add a run/provenance layer beside the notebook. Use embedded DuckDB as the first tabular scan and optional SQL engine. Keep Python as the supported notebook language; do not build general kernel support. Run untrusted code only in a disposable, resource-limited OS sandbox with an explicit project-file view and network disabled by default. This is a proposed architecture, not a tested product or a validated security boundary.

Two separately useful precedents support the split. Jupyter NBFormat defines the notebook JSON shape and nbclient supplies cell execution, progress hooks, timeouts and error policy [S01–S03]. DuckDB is a separate project and contributes an embedded tabular/SQL engine with CSV, JSON and Parquet paths, type conversion behavior, and explicit fault-handling choices [S17–S23]. These projects have separate repositories and codebases; the sources establish component mechanisms, not that the combined stack works together. No repository or runtime build was prescribed or performed.

## Minimum workflow and project record

1. **Create.** Make a folder containing `project.toml`, notebooks, Python scripts, optional `.sql` transforms, `data/` references, and a hidden `.workspace/` area for manifests and rebuildable cache. Keep portable paths relative when possible. Do not silently copy or rewrite source data. Import defaults to a reference plus an identity scan; an explicit “managed copy” option may put a source copy in the project. Record the original location and copy relationship.
2. **Identify and inspect.** Select a parser from an explicit format choice or file extension, show the detected format and parse options, then present schema and a bounded preview. CSV type inference is provisional: DuckDB documents inference and explicit type controls, and separately offers faulty-row handling modes [S18–S19]. A head/seeded sample is labelled with its method and size and is never shown as proof of a whole-file property. A user can request a full schema validation scan.
3. **Author and run interactively.** Open `.ipynb` in a Jupyter editor/kernel and support selected-cell execution. Record actual execution events independently from displayed cell order. Show kernel epoch and whether the current kernel has been restarted. The current in-memory namespace is not reconstructible from cell order alone.
4. **Clean replay.** Start a fresh kernel in a fresh worker, apply the locked environment and declared project inputs, and execute the entire notebook in displayed order. The first release should not promise arbitrary clean subsets: later cells may depend on state created by skipped cells. Show per-cell start/completion, elapsed time, output/error, and a cancel action. Set a configurable cell and whole-run deadline; cancellation interrupts then terminates the worker if needed. `nbclient` documents cell execution, progress/error hooks, timeouts, and stop-on-first-error versus `allow_errors` behavior [S02]. Choose stop-on-first-error for a clean replay; any continue-on-error mode must be explicit and leave downstream outputs failed or unverified.
5. **Compare, save, reopen, export.** Compare saved and current source, environment, data, run status and outputs. Diff text/JSON tables structurally where possible and provide MIME-aware/raw output comparison for plots or rich displays. A digest is an identity check, not a semantic comparison. Save a small JSON manifest plus notebook outputs and referenced result artifacts. Reopen the ordinary folder or a portable bundle on another machine; report missing data and environment mismatches without replacing them with similarly named files. Export selected results and the manifest.

`project.toml` records a project ID, format version, relative data references and parser options, schema contracts, transform/notebook paths, environment-lock path, cache policy, and declared external resources. A data entry records format, canonical path, content identity, size, declared schema and schema-contract version. A run record records run ID, mode (interactive or clean), environment fingerprint, source fingerprints, transform/cell hashes, event sequence, completion status, output associations, and error summary. Keep full tracebacks and detailed logs separately from the small shareable manifest. Credentials and private account profiles are never included.

## Data contract and scale behavior

**Identity and mutation.** Fingerprint file bytes with streaming SHA-256; for multi-file Parquet inputs fingerprint a sorted manifest of relative names and per-file content hashes. Size and modification time can cheaply trigger a rescan but are not strong identity and cannot establish reproducibility. Hash before a run and verify afterward so a concurrently replaced source cannot be associated with the wrong output. Byte hashing is bounded in RAM but costs a complete sequential read. Do not mutate original files. A managed copy is a separate immutable input version.

**Schema and conversions.** Persist field names, source and logical types, nullability/absence policy, timestamp timezone assumption, encoding/locale where relevant, and explicit cast rules. Missing JSON properties and explicit JSON `null` are distinct contract cases. Preserve Unicode. Heterogeneous columns remain raw/variant or strings until an explicit conversion is selected. Show conversion counts and examples of rejected tokens. DuckDB documents Python/DuckDB conversion mappings, so the adapter must make those conversions visible rather than implying Python values preserve the source representation [S23]. On schema evolution, report additions, removals, renames and incompatible type changes. Default to failing on removal/incompatible conversion; allow additive fields only under a declared policy and bump the contract version when meaning changes.

Malformed rows fail the transform by default with row/file location, parser error, and counts. Never silently skip or delete. An explicit quarantine action may write raw offending records plus location and reason into a separate sidecar; report how many were quarantined and keep originals unchanged. DuckDB supports different faulty-CSV choices, including skipping and storing faulty records [S19]; the product must select its safer visible policy, not inherit a permissive parser default.

A declared business key is the row identity when present and validated. Otherwise expose a source-scoped locator (file hash plus record ordinal, or Parquet file/row-group/row ordinal), not a durable business key: rewriting a file can change ordinals. Relational query results have no implied order. A stable order requires an explicit sort and unique tie-break key; if there is no such key, say ordering is unspecified. This applies to previews, cache outputs and exported rows.

For a 5 GB input on a 16 GB workstation, the target is to parse/scan, project, filter and stream results without materializing the full table in Python. Limit notebook previews by rows and bytes; store large results as Parquet or another declared artifact and offer a bounded preview/download. A global sort, exact deduplication, full validation or global aggregation may scan/spill the whole input and needs a separate explicit cost/resource bound. DuckDB's limits documentation says the memory limit applies to its buffer manager and defaults to a share of system RAM; it is not a hard process-wide memory cap, and temporary storage needs its own quota [S22]. Thus “5 GB works” is an acceptance target, not a result established here. Pin and stage any DuckDB extensions with the environment; do not depend on a first-run network download.

## Execution state, provenance and invalidation

NBFormat code cells have source, `execution_count` and outputs, and notebooks have an ordered cells list [S01]. That document can preserve displayed order and saved outputs; it does not tell whether a saved output is fresh, which earlier cells actually ran in the current kernel, or which data/environment produced it. Keep a sidecar event journal with monotonically increasing sequence, timestamp, run ID, cell ID, kernel epoch, source/dependency fingerprints, start/end, outcome and output MIME types/digests. Associate output records with stable cell IDs; reconcile them on notebook edits and flag duplicate/missing IDs rather than relying on cell position or execution count. Store a content hash for each output and retain the previous successful output bundle until a complete clean run commits.

Use four visible output states: **current** (from a successful completed clean run whose recorded code, dependency closure, source/schema and environment fingerprints still match); **stale** (one or more known inputs changed); **failed** (the latest attempted run for the cell failed); **unverified** (legacy/imported output, interactive-only output, unknown dependency, restarted kernel, interrupted save/run, or output whose provenance cannot be confirmed). Old visible output remains visibly stale/unverified after a restart or failure; a restart never upgrades its status.

Invalidation is explicit:

- Editing a cell invalidates that cell and all statically declared descendants; unrelated cells can remain current only if their dependency declaration is complete.
- Changing a source fingerprint or schema contract invalidates every dependent transform/cell and cached artifact.
- Changing the environment lock, Python/kernel version, engine/extension pin or relevant execution configuration invalidates all run outputs.
- Kernel restart, failed/cancelled run, or interruption invalidates outputs touched by that interactive epoch/run. The last committed clean bundle is preserved but marked stale if its source no longer matches.
- Dynamic reads, environment inspection, reflection or undeclared dependencies defeat exact graph discovery. Start conservatively: notebook-level invalidation if dependency tracing is incomplete. Sandboxed file-access observation can improve the graph, but it is not a correctness proof for arbitrary code.

A cache key includes content hashes of input data, transform code, schema contract, environment lock, engine/extensions, and declared deterministic options. Cache only declared-input deterministic steps. Cache entries are immutable/checksummed and atomically published; source/schema/environment changes invalidate descendants. Do not cache computations that use unseeded randomness, clocks, network data or undeclared files. Distinguish deterministic row ordering from stable ordering as above.

A clean replay can guarantee that the application started from a fresh kernel, used the recorded locked environment and declared/fingerprinted inputs, ran cells in the declared order, and committed outputs only after successful completion. That is a provenance guarantee within the declared boundary, not a promise of byte-identical output. Nondeterministic algorithms, random seeds, locale/timezone, CPU/OS variation, unpinned packages or system libraries, external services, dynamic file reads, and hardware-dependent numerical behavior can still differ. Network should be disabled for clean replay by default; if an external resource is explicitly allowed, record endpoint/parameters and mark the run externally dependent, not hermetic. A saved `.ipynb` output without a matching manifest is unverified.

## Runtime choice, safety and recovery

Candidate component versions for a first integration branch are `nbformat 5.10.4`, `nbclient 0.11.0`, `jupyter_client 8.10.0`, `ipykernel 7.4.0`, and `duckdb 1.5.6` [S01–S05, S14, S17]. These are exact candidate versions, not a tested compatible lock; pin all transitive wheels and hashes, Python minor/build, platform, system libraries and extension artifacts before reproducibility claims. Python version, kernel dependencies (including pyzmq/libzmq and event-loop stack), supported OS targets and lock-generation process remain critical unvalidated dependencies. The live issue chain below makes `jupyter_client 8.10.0` an explicit runtime acceptance gate.

Treat notebook code as untrusted. Launch a disposable low-privilege worker in a supported OS sandbox/container: read-only runtime, no home or host environment, no credentials, no unrelated private paths, network off, read-only mounts only for declared project inputs, and a contained writable output/scratch directory. Set CPU, memory, process, file-size, wall-time and scratch quotas. Provide live progress, interrupt then terminate, and a useful error when the sandbox is unavailable. A container shares the host kernel and is not automatically a strong hostile-code boundary; do not describe it as one. An import blacklist is not isolation. Jupyter Server security documentation explicitly treats access to the server as arbitrary code execution and explains that authentication is not a code sandbox [S24]. Choose and validate a platform-specific isolation backend; if unavailable, offer inspect/preview only or an explicitly labelled unsafe local run mode. This isolation plan is proposed and was not exercised here.

Save by staging the new notebook, manifest and output artifacts under a run-specific temporary directory, checking hashes, flushing files, then atomically renaming a commit marker/pointer. Preserve the last known-good commit. On reopen, detect orphaned staging data and incomplete markers, offer discard/recover, and label affected output unverified until recovery is confirmed. Use a per-project writer lock; concurrent readers can proceed. If a lock owner dies, require an explicit stale-lock recovery and verify the project revision before writing. Treat VCS merge conflicts as conflicts, not last-writer-wins. Keep cache rebuildable and outside the source-of-truth commit. Portable bundles should preserve relative paths and manifest; external data stays external unless deliberately included, and missing references are reported.

## SQL and notebook interchange boundary

Use DuckDB for an optional SQL transform/pane over the same registered data and contract catalog. Save SQL text, parameters, referenced datasets, engine version, event and output manifest just as for Python transforms. It gives the occasional SQL user a useful path without a second general kernel. Python notebooks can use the same pinned DuckDB engine through a thin data-access adapter. Support only documented DuckDB SQL/filesystem semantics in the first release; explain unsupported extensions, remote sources and non-DuckDB dialect features. Do not embed credentials or silently access arbitrary paths. General SQL-kernel compatibility and multi-user database semantics are out of scope.

Keep `.ipynb` as the interoperable notebook document. Its standard schema is useful, but it does not settle execution runtime or provenance [S01]. Jupytext is a useful optional opportunity: its `py:percent` text representation makes inputs easier to review in Git, while a paired `.ipynb` can retain outputs; it introduces pairing/synchronization and merge-conflict cases [S25]. Offer it as an opt-in view after testing round trips, not as another required canonical file.

A plausible alternative is a Python-first columnar stack (for example, Arrow/Polars) instead of DuckDB, with SQL remaining a small optional capability or deferred. That may suit a team whose transforms are overwhelmingly Python, but it changes the SQL path, conversion boundary and streaming implementation; this alternative was not researched or benchmarked here. Another lower-risk alternative is `.ipynb` only and defer text pairing entirely. Both are bounded choices, not product requirements.

## Issue/fix/test applicability diagnostic

The candidate-discovered chain is consequential because a stalled kernel or cell breaks replay, progress and output freshness.

1. **Reported failure.** In `jupyter/nbclient#312`, the reporter gives `nbformat 5.10.4` and `nbclient 0.10.0` and describes an ipywidgets `Output` cell that can block while waiting for a reply/poll; the issue body proposes that a missing timeout is responsible [S06]. This is a report and diagnosis, not proof of the root cause. The reporter does not identify their `jupyter_client` version, OS or complete environment.
2. **Plausible but misleading local workaround.** Linked `jupyter/nbclient#311` adds a five-second timeout in nbclient, but the PR capture says `state=open`, `merged=false`, `base=main`, base SHA `a72fb94…`; the v0.10.0 tag points to that same SHA [S03, S08–S09]. The diff changes only `nbclient/client.py` and adds no regression test. A Jupyter nbclient member comments that the fix likely belongs upstream in jupyter-client [S10]. Therefore this is not an included nbclient v0.10.0 fix and must not be presented as released behavior. The added timeout could mask or alter waiting behavior; the source evidence does not establish it resolves the underlying defect.
3. **Upstream mechanism and regression test proposal.** The linked `jupyter/jupyter_client#1145` PR describes a missed wake-up after `Session.send` on an asyncio socket and adds a helper plus `test_send_wakes_pending_poll` for `send` and `send_raw`; its own description claims the regression fails before and passes after the patch [S12–S13]. The captured PR is still open/unmerged, based on SHA `978361b…`. That exact SHA is the `jupyter_client v8.10.0` tag [S14]. The pinned v8.10.0 `session.py` shadows the async socket but has no wake helper, and the pinned test file has no named regression test [S15–S16]. So the proposed upstream patch/test is **not present in that release**. This is a concrete release-applicability mismatch, not evidence that every v8.10.0 deployment reproduces the issue.

**Diagnostic result and limit.** The superficially plausible nbclient issue → PR chain is misleading as a claim of a released fix: PR #311 is open and untested in the patch, and the reporter's nbclient 0.10.0 commit matches its base. The more plausible underlying jupyter_client mechanism has a candidate regression test, but the candidate's exact base release v8.10.0 lacks both the change and test, and the PR is still open. The issue reporter's `jupyter_client` version is unknown; no candidate execution of the PR test, no release containing it, and no resolved post-fix behavior were established. Keep a failing/stalled-cell regression gate in the selected runtime matrix; do not call the bug fixed or infer that a later captured version has it fixed without checking that release's source and running the regression. A commenter reports using a blocking kernel manager as a workaround, but that is one user's report and is not a validated fallback [S07].

## Validation and delivery plan

**Executed by candidate — isolated component check only.** One authored standard-library Python check used tiny synthetic CSV text to verify that a hand-coded cache key changes when source/contract/environment fingerprints change, a hand-coded dependency graph invalidates descendants in display order while leaving an independent cell alone, and an event list preserves an interactive order that differs from display order. Exit 0; stdout and exact code/input/receipt are recorded in `witnesses.json` [W1]. It did not invoke a notebook, DuckDB, filesystem, application, issue regression or large dataset. It is not proof of application behavior, parser correctness, data quality, scale or sandboxing.

**Proposed / UNEXECUTED acceptance work.**

- Build a supported, hash-locked environment on each supported OS; verify kernel launch, clean replay, cancel/timeout, restart/error statuses, widget output, event capture and notebook round trip. Reproduce #312 where possible, run #1145's exact regression test against v8.10.0 and a build containing the proposed patch, then identify an actual released version before unblocking the runtime. Verify the full package compatibility tuple.
- Test golden CSV, NDJSON and Parquet fixtures with Unicode, missing fields versus null, timezone-aware timestamps, heterogeneous values, malformed rows, schema additions/removals, explicit casts and stable tie-break order. Assert no source mutation and no silent row loss. Test multi-file Parquet identity and change detection during a run.
- For generated 5 GB fixtures on an 8-core/16 GB target, measure peak worker RSS, scratch use and elapsed time for scans, filter/projection, chunked output, group, join and global sort. Assert bounded preview/output bytes; test configured spill and cancellation. Record hardware, data shape, version, operation and limits. No such benchmark was run here.
- Test cache hit/miss/invalidation for cell edits, transitive dependencies, data/schema hash, lock/extension changes and undeclared file access. Test kernel reset and partial failure never mark prior output current. Compare structured saved/current results, including outputs from interrupted runs.
- Run isolation tests from an adversarial notebook in a disposable test environment: path escape, access to host home/environment, subprocess/process exhaustion, network access and scratch quota. Check a second machine reopens a portable bundle with pinned environment and either verifies inputs or clearly reports missing ones. Kill the process during save and verify recovery retains the prior committed result. These tests are mandatory before claiming the execution boundary or recovery behavior.
- Check accessible progress/error announcements, keyboard operation, screen-reader status, clear stale/current labels, traceback navigation, and export with three representative analysts.

Real-time collaboration, hosted execution, automatic scheduling and broad language support remain optional opportunities. This proposal prioritizes a transparent local replay and data contract. The only executed evidence is W1; all integration, scale, compatibility, security and user validation above is proposed/unexecuted.
