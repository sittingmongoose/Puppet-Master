# Local biomedical image review workspace

**Proposal stage:** I-05-CONTROL-ARTIFACT-RECOVERY-R001-revision-a001  
**Evidence cutoff:** 2026-10-05  
**Product boundary:** local research-image inspection and annotation; not a diagnostic device, medical record or patient-care system. Six researchers edit local projects and exchange closed bundles through ordinary shared storage. This is an incremental engineering proposal, not a built or qualified application.

## Recommendation

Build a desktop project service around a small, explicit image-format boundary. Use napari **v0.6.5** for multidimensional display and point/shape/label editing; use **tifffile 2025.5.10** for a qualified single-file OME-TIFF path, its `aszarr=True` regional interface, **Zarr 2.18.7**, and a pinned Dask array dependency; read local OME-NGFF 0.4/Zarr v2 as a separate input path. Keep axes, calibration interpretation, asset identity, annotation geometry, undo/redo, operation history and exports under application control. Use a local SQLite database for small project state and immutable, chunked files for source copies, masks and derived pixels. Open external sources read-only.

Treat those versions as a **candidate baseline**, not a resolved environment. Napari's v0.6.5 project metadata declares Dask arrays and tifffile, with Zarr optional; tifffile's 2025.5.10 release documents Zarr 2.18.7 and rejects Zarr 3 for its Zarr interface. Those facts make the pins plausible together but do not resolve Qt, codecs, SQLite runtime, the full dependency graph, OS packaging or performance. A reproducible lock and fixture qualification are release gates. [S3, S8]

The initial support promise is local, single-file OME-TIFF with one selected image series and local OME-NGFF 0.4/Zarr v2 with one selected image group. Accept only a tested subset with supported arrays, codecs, axes, calibration and read-unit sizes. Keep unsupported images and their metadata intact, explain the refusal, and offer a recorded mapping, pixel-only review where meaningful, or cancel. Never silently guess a physical axis or rewrite the original. Do not advertise general TIFF, Zarr or microscopy-format compatibility.

## Source-backed findings that shape the design

### Format facts and independent implementation precedents

**External fact — NGFF 0.4.** The specification describes Zarr v2 stores, named axes, multiscale arrays and per-channel display hints. For a multiscale image it constrains dimensionality and axis roles/order, and requires dataset transforms to use one scale and optionally one later translation. This transform vocabulary is not a general rotation/shear affine. NGFF image-label groups describe integer label arrays; their link to a source image is optional. They do not define this application's vector geometry, source identity, project history or undo semantics. [S1 §§2, 3.1, 3.3–3.7]

**External fact — OME-TIFF.** OME-TIFF maps planes to IFDs using OME-XML `TiffData` and `DimensionOrder`; page order alone is not a reliable application axis map. The OME-TIFF specification also describes multi-file sets, but this proposal excludes them initially. [S2, “DimensionOrder”, “The TiffData element”, “Multi-file OME-TIFF”]

**Independent implementation precedent — reader.** Tifffile 2025.5.10 documents reading image parts through `aszarr=True` and Zarr 2, including a tiled TIFF-region example and a Dask adapter. It documents Zarr 3 incompatibility for this path and inability to read multi-file pyramidal OME-TIFF. This is reader release documentation and examples, not a test of our wrapper or a 3 GB memory/latency result. [S3, release 2025.5.10, “Requirements”, “Notes”, “Use Zarr 2 to read parts of TIFF files”]

**Independent implementation precedent — viewer/layer operations.** In napari v0.6.5, `slice_from_axis` wraps a direct Zarr array with Dask before slicing; `split_channels` passes layer metadata to channel layers. These viewer/layer mechanisms are distinct from tifffile's TIFF reader and do not make the reader/viewer a project format or establish application persistence. [S4, `slice_from_axis`, `split_channels`, `split_rgb`]

**A real failure, patch and regression test.** Napari issue #7085 reports that “Split RGB” dropped a nontrivial layer transform on `0.4.16.dev1413+ga4fa1fa0`. Maintainer discussion described inconsistent paths; the PR says `split_rgb` called `stack_to_images`, which discarded affine/rotate/shear, while a metadata-aware `split_channels` path already existed. PR #8256 changed `split_rgb` to use `split_channels` and adjusted transform argument handling. Its code-bearing commits are `2b51110e65af469863697797921ff12aa668d301`, `3f994d36130e5d673ce059a1a0d66fac9cca03b0`, and `9f262998cbe464e0ec826eae691e487af752658c`. The second adds a regression test comparing the split layers' affine matrix for no transform, scale, translation and `Affine(translate=[0,4])`. The PR merged as `afd1bb88f296726fe98bc0a94119a51bba6870c4` on 2025-09-26 for the 0.6.5 milestone, and the selected v0.6.5 tag contains both implementation and test. This chain supports a concrete lesson: a seemingly simple channel-view operation can drop spatial metadata, so test every view operation that changes layers. Its test does **not** assert general non-diagonal affine, rotation/shear, project save/reopen or exports; it is not proof of end-to-end scientific coordinate fidelity. [S4–S7]

**Performance risk report.** Napari issue #9515 is an open, configuration-specific report of over-fetching/slow interaction with n-dimensional multiscale local Zarr data. The inline reproduction asks for napari 0.9.1 and Zarr >=3, while the displayed environment reports napari `0.6.1rc1.dev1` and Dask 2026.8.0. Neither matches this proposal's candidate pins. The report and discussion justify measuring bytes read, useful bytes, stale work, latency and cancellation; they establish neither a general defect nor a repair or behavior of our candidate stack. [S9]

**Independent storage precedent.** SQLite's atomic-commit documentation describes rollback-journal recovery and its assumptions about locks, flushes and filesystem operations. It is evidence for a local transactional index, not certification of a shared filesystem or an atomic transaction spanning SQLite and separate image files. [S10 §§2–4, 9]

## Supported input boundary and safe failure

### First qualification matrix — product choice, not existing support

1. **OME-TIFF:** one local TIFF/BigTIFF container with embedded OME-XML, one researcher-selected series, one resolution level, one sample per channel, and 2D or `ZYX` spatial samples with explicitly mapped optional `C` and `T`. Require valid, unambiguous plane-to-IFD assignments, internally consistent dimensions or an explicit reviewable conflict decision, supported sample type and installed codec, and a reader layout whose largest strip/tile read unit fits the measured in-flight budget. Start by qualifying `uint8`, `uint16`, `int16` and `float32`; admit each dtype/codec/tile combination only after fixtures pass. The first release excludes multi-file sets, pyramids, packed RGB/RGBA, mosaic/HCS layouts, vendor-specific TIFF variants, unknown custom axes and unsupported compression. BigTIFF is a separate fixture gate even though tifffile documents it.
2. **OME-NGFF:** local OME-NGFF 0.4 on Zarr v2. Validate a multiscale image's 2–5 array dimensions, unique axis names, 2 or 3 `space` axes, optional single `time` and optional single `channel` axis; require the specified axis order and array dimensionality to agree. Validate level shapes/order, transform types/count/order/vector lengths, units and any label grid before display. The initial application mapping supports only spatial/time/channel roles. A custom/null axis requires an explicit mapping to a supported role or refusal. Plates, HCS, mosaics, multi-image wrapping, arbitrary custom axes, Zarr 3 and cross-array registration remain out of scope. [S1 §§2, 3.1, 3.3–3.7]
3. **Samples and chunks:** do not cast the imported samples. Each data type and codec is supported only when its exact read and display path is qualified. A giant strip/tile or chunk that defeats the memory budget is refused or made available only in a clearly marked degraded, cancelable mode after measurement. No promise covers every TIFF codec or TIFF-like vendor format. Tifffile's release notes themselves document unsupported TIFF variants and a multi-file pyramidal OME-TIFF limit. [S3]

If a parser fails or detects unsupported axes, bad transforms, broken chunks, ambiguous calibration or conflicting metadata, stop before publishing an annotatable asset. Record an import attempt, reader/version, warnings and any extracted metadata snapshot; keep the source bytes untouched. Show the detected series, shape, dtype, axes/order, sample layout, calibration fields, units, chunks/tiles and failure reason. Offer explicit options: map/correct axes or calibration and save a distinct project interpretation; continue in pixel/index coordinates with physical coordinates unavailable; or cancel. An interpretation never edits the source metadata. Corrupt/partial staging data stays unreferenced and recoverable; it must not replace an existing asset or project revision.

### OME calibration rule

**External fact.** In the OME 2016-06 schema, `Pixels/@PhysicalSizeX|Y|Z` describes optional pixel-size magnitudes, with schema-default micrometre units. `Pixels/@TimeIncrement` describes a global interval with schema-default seconds. `Plane/@PositionX|Y|Z` records plane stage positions and has schema-default “reference frame” units; `Plane/@DeltaT` records per-plane time with a seconds default. The schema documentation says TIFF structural pixel values override conflicting OME-XML values in readers. OME-TIFF `TiffData` supplies plane/IFD assignment separately. Those fields do not by themselves give a universal oriented laboratory affine. [S2; S11, OME 2016-06 schema]

**Product choice.** Retain original XML bytes, parser-effective values, literal unit strings, schema defaults and TIFF structural values separately. In the metadata panel, identify which source supplied the displayed value and whether a unit was literal or defaulted. Do not treat stage `Position*` as a global origin or turn varying `Position*`/`DeltaT` into a regular stack/time scale. A local image coordinate frame may set the center of sample index zero as its explicitly named origin; that is an application convention, not a laboratory position. A lab-frame map is available only when origin, orientation, axis directions, spacing and units are supported or the researcher records a correction. When there is no defensible mapping, preserve raw metadata and use named sample indices; physical coordinates are null/unavailable. Irregular plane positions and times remain explicit per-plane data, not a false global affine.

## Architecture and component choice

| Component | Candidate choice | Mechanism and limit |
|---|---|---|
| Desktop display/edit layer | Qt application shell embedding napari v0.6.5 | Multidimensional layers and points/shapes/labels; application services remain authoritative. v0.6.5 project metadata requires `dask[array]` and tifffile and makes Zarr optional; it declares Python >=3.10 and offers Qt extras, but no complete resolved lock. [S4, S5, S8] |
| OME-TIFF reader | tifffile 2025.5.10 + `aszarr=True` + Zarr 2.18.7 | Regional read path for tested single-file series; no blanket codec, multi-file pyramid, or memory claim. [S3] |
| NGFF reader | Zarr 2.18.7, strict OME-NGFF 0.4 metadata validator, Dask for selected/lazy reads | Accept only compliant or explicitly corrected arrays; no Zarr 3 or custom-axis promise. [S1, S3] |
| Project state | SQLite database on each researcher's local disk | Project/assets, metadata snapshots, interpretations, display state, annotations, style versions, commands, provenance, manifests and artifact pointers. Use one writer. SQLite does not store multi-GB pixels. [S10] |
| Pixel/artifact store | Read-only source references or explicit copies; immutable chunked derived arrays/masks | Async tile/slice provider, bounded decoded cache, generation IDs, cancellation and progress. Publish artifacts before database pointers. |
| Export service | Application-owned writer and manifest | Temporary bundle, readback validation, source/derived grid identity, honest loss report, then publish. |

Tifffile and napari are independently useful precedents: one exposes TIFF segment/region reads as a Zarr-2 array; the other wraps/slices arrays and manipulates display layers. Their code paths have different responsibilities, so the adapter must measure the composed path and keep a project-owned coordinate contract. SQLite supplies a third, separate persistence mechanism under its own assumptions. None of these sources proves that this exact application stack works together.

**Candidate pins:** `napari==0.6.5`, `tifffile==2025.5.10`, `zarr==2.18.7`. The selected tifffile release documents Zarr 2.18.7 as a tested requirement for opening Zarr and explicitly excludes Zarr 3 from that interface; napari 0.6.5 accepts Zarr as an optional dependency. Pin Dask, Python, Qt binding, codecs, SQLite runtime and all transitive packages only in the reproducible build qualification: the cited sources do not establish an integrated set. Record those exact versions in every project/export manifest. If the lock fails on a workstation OS, do not ship that build; retain the data model and compare a qualified Qt slice canvas/read provider against the napari adapter before changing the viewer component.

Application services:

1. **Import adapter:** detect and parse strict OME-TIFF or NGFF subsets; preserve exact source metadata and parser decisions; convert named source axes into a project axis map without reordering source identity.
2. **Project service:** versioned SQLite schema and migrations; a single local writer; durable annotation/interpretation transactions; style revisions; undo/redo commands; source/derived asset graph and provenance.
3. **Array service:** read-only handles; bounded asynchronous region requests and cache; cancellation token; visible progress; source/derived separation; immutable chunked writes.
4. **Viewer adapter:** converts screen pointer events to named continuous sample coordinates using the current view transform; supplies display state without mutating samples; treats napari layer transforms as a view adapter, not the project coordinate authority.
5. **Export service:** versioned table/sidecar, overlay and derived-image manifest; temporary output, readback checks, source-byte check and explicit complete/lossy status.

## Coordinate, grid and annotation contract

### Axes, indices and physical maps

Each imported asset retains original axis names/order, lengths, units, source metadata locations, series/group selector, sample type, shape, chunk/tile organization, parser version and interpretation revision. A separate mapping gives every axis a role (`space`, `time`, `channel`, or an explicitly corrected supported role). Array indices are always stored with the original named order; adapters never silently assume that `ZYX` data are `XYZ` coordinates.

Spatial user coordinates use zero-based continuous sample-index coordinates, where integer index `0` is the center of the first sample. The canonical project vector is `index_xyz=[x,y,z]` in named axis order; a 2D image has only X/Y unless its metadata defines a plane embedding. For an array ordered `t,c,z,y,x`, an element address `[t,c,z,y,x]` maps to spatial `[x,y,z]` plus separate time and channel selectors. The viewer displays/saves its screen, zoom, pan, rotation, device pixel ratio and slice/time selection as view state; screen pixels never become stored annotation coordinates directly.

Where a physical spatial mapping is established, store a float64 affine with explicit input/output axis names, units, coordinate-frame ID and sample-center convention:

`physical_xyz = origin_xyz + M_xyz × index_xyz`.

Store `M` and origin without decimal rounding; use the actual 2D or 3D dimension. Permit a validated signed axis permutation, scale, rotation or shear. Keep channel and time indices out of the spatial matrix. When only pixel-size magnitudes are known, an explicitly named per-image local frame can use those magnitudes and a declared local origin at sample zero; it cannot claim laboratory location or registration between images. Missing/ambiguous calibration remains null until a user records a mapping. Raw metadata and user interpretation are different immutable records.

For time, always preserve the integer index. A uniform physical time map exists only where global time-increment semantics apply and are validated. Per-plane `DeltaT` values remain a keyed per-plane table; irregular time never gets interpolated into a fictitious uniform step. Channel index/name is likewise explicit and separate from space/time.

### Source grids, derived grids and operations

An asset's raw content digest and its grid identity are separate. A grid identity includes the dataset/series selector, base-level array path, shape, named axis order/roles, sample-center convention, and the specific calibration interpretation. A derived image receives a new immutable asset ID/digest and grid ID. Every geometry-changing operation has an operation ID, input/output identities, parameter set, software/version, output dtype/shape, sampling/interpolation rule and float64 source-index-to-derived-index map. Crop, flip, reorientation, resampling, projection, cast and baked intensity mapping are separate named operations. In-place source modification is outside scope.

An annotation is anchored to a source digest, source series and grid/calibration revision. Keep its canonical geometry in source sample coordinates. A copy transferred to a derived grid receives a new annotation UUID, links back to the source annotation and operation ID, records derived-grid coordinates and retains the original unchanged. Nonlinear transforms are unsupported until the data contract and inverse/forward mapping are specified. A derived export unable to preserve the mapping must either carry the application sidecar or be identified as lossy; explicit resampling creates a new operation and derived identity.

### Annotation record and editing

Each annotation stores UUID, author/local identity, timestamps, type, source asset digest, series/grid, geometry dimensionality, named sample-index geometry, optional physical geometry/frame, explicit scope, time/slice/channel selectors, style ID/version, tags/notes and provenance. Scope is one of plane, volume, time point or whole acquisition; selectors say whether a plane's channel/time context is fixed or spans channels. Points, polygon rings and mask values have declared axis order and precision. A mask is an integer label array on an explicit grid with label-value mapping and its own immutable chunk artifact; there is no implicit resampling.

Reusable styles are named, versioned data objects with marker, stroke/fill, color and width; each width states screen-space or data-space units. Save display settings separately per asset/channel: visible channels, blend/LUT, window/level, slice, time and viewer pose. A baseline window/level with center `L` and width `W>0` maps raw value `v` to `clamp((v-(L-W/2))/W,0,1)` before the chosen display LUT/gamma. Store parameters and mapping-convention version. This is display-only state: changing it must not rewrite source or derived sample arrays.

All annotation edits flow through project-owned transactions and user-visible undo/redo commands. Commands cover add/move/delete, scope, style and mask revisions. Mask editing writes a new immutable chunk revision or a reversible patch journal; never modify original samples. Undo/redo must restore exact geometry and identifiers. Keyboard navigation covers image/channel/slice/time, tool selection, zoom/pan, save and undo/redo. Use visible focus, labeled controls, non-color-only state/scope cues, readable metadata/errors, keyboard-operable dialogs and legible progress/cancellation feedback.

## Identity, project storage and recovery

### Project directory and source identity

Use a directory project with a small `project.sqlite`, a versioned manifest and metadata-snapshot area, plus optional portable source copies and immutable `derived/` artifacts. SQLite holds project revisions, asset/import records, metadata hashes/snapshots, interpretations, display state, annotation geometry, styles, command history, operation graph, artifact manifests and references—not image arrays.

For a single file, asset content identity is a streaming SHA-256 of the original bytes. For a Zarr tree, define a versioned deterministic manifest: include every regular file (all metadata, chunks and other files); record NFC-normalized UTF-8 relative POSIX path, byte size and SHA-256; sort by UTF-8 path bytes and hash a canonical serialization. Reject symlinks, special objects, invalid paths and Unicode/case-fold collisions rather than making identity depend on host filesystem behavior. Require complete stable enumeration and a second membership check. If the tree changes or any file is unreadable during enumeration/hash, leave identity pending/invalid. Store the algorithm/version, digest, bytes, verification state and time.

A linked local file or tree is read-only through this application but may still change through another process. Show this limitation. Browsing may continue during asynchronous hashing; edits made while identity is pending are visibly provisional. A verified portable copy or filesystem snapshot is the strong route: stage it, hash and verify it, flush it, then publish it. For a linked source, require researcher confirmation that it is quiescent, compute a full digest, and recheck before verified export or relocation. Ordinary changes make the source `changed/unavailable` and block verified-against-original export while preserving annotations. A path, filename, file size or timestamp never proves identity. Without a snapshot, the app cannot prove that a linked source had no transient external write during review; the project must label that assumption instead of claiming a stronger guarantee.

The asset ID is not its path. Relocation on another machine succeeds automatically only if full digest, series selector and grid contract match. A changed source remains visible as missing/changed; its annotations remain inspectable but unverified. References save space but require a working path or explicit verified relink. Portable bundles travel more reliably but need copy time and roughly source-size extra disk space; estimate and show the required capacity before copying.

### Save sequence and crash cases

Use a single writer on a local project. Choose rollback-journal `journal_mode=DELETE` and `synchronous=FULL`, record the settings and SQLite version, and qualify them on each OS. SQLite's documented recovery depends on filesystem/VFS locking and flush semantics; its atomic-commit description is not a guarantee for a network share. [S10]

For large arrays or portable copies, write to a temporary sibling on the destination filesystem; close, read back and verify every chunk/hash; flush files; atomically rename to a new immutable name; flush its containing directory where supported; only then commit the SQLite pointer in a durable transaction. These are two resources and do not form a single atomic transaction. If directory durability cannot be established on a target, mark that storage mode unqualified. A crash before the DB transaction can leave an unreferenced published artifact; a crash during staging leaves a temporary artifact. Startup inventory must identify both, preserve the database and prior project revision, and remove nothing automatically until references are checked. A missing committed artifact marks that asset/revision unavailable; offer recovery to a verified prior revision and retain the failed DB for inspection. Before a schema migration, preserve a closed, verified project copy.

On startup, let SQLite recover its journal, run integrity/reference checks, and report last good revision and staging/orphan candidates. Do not open one live SQLite project for simultaneous editing from several workstations. Each researcher works locally, closes and verifies the project, then copies a closed bundle to shared storage; no automatic merge is promised. Test copy, rename, lock, flush and reopen on the actual share before relying on those operations.

### Bounded reads and responsiveness target

The 3 GB source and 8-core/16 GB machine are qualification targets, not evidence for a library. Use region requests and decoded chunks, not an unconditional full `asarray()`. Start with a proposed decoded cache cap of 512 MiB, at most four concurrent reads and no admitted decoded chunk above 32 MiB. Account for reader, codec and viewer buffers separately. Reject or clearly degrade a layout whose single read unit already defeats that bound. The UI issues generation-tagged requests; newer slice/channel/view state cancels or discards stale work. Keep cache updates and annotation commands independent of long reads, report progress and acknowledge cancellation. GPU is optional and not needed for correctness.

Proposed initial acceptance targets are p95 warmed slice/edit <=250 ms, progress refresh <=250 ms and cancellation acknowledgement <=1 s on the target workstation. Cold/warm access, source bytes, read amplification, RSS, cache/in-flight bytes and codec buffers must be measured against representative 3 GB tiled OME-TIFF and chunked NGFF fixtures, including a giant strip/tile. None of these results exists yet.

## Minimum workflow and export contract

1. **Create and import.** Create a project, select one or more local image sources and choose linked read-only reference or verified portable copy. Show series/group, shape, sample type, axes/order, channel/time metadata, units/calibration, chunks/codecs, source path/identity progress, metadata digest and parser/version provenance. Unsupported or ambiguous cases remain untouched; show correction, pixel-only or cancel explicitly.
2. **Inspect and navigate.** Open multiple qualified images from different instruments in one project. Navigate named channels, slice and time. Adjust visibility, window/level and LUT. Show original data, annotations and derived images as visibly different layers; display source, derivation and coordinate-frame status.
3. **Annotate.** Add points, polygons and masks. Show scope plus slice/time/channel selectors; use versioned reusable styles; support keyboard operations and undo/redo. Record the canonical geometry in sample coordinates and show physical values only when the named mapping is available.
4. **Save, close and reopen.** Save transactions and immutable artifacts, close cleanly, reopen the project and verify its database, grids and artifact references. On another machine, resolve a portable copy or explicitly relocate an external reference by full digest and series/grid identity. Keep annotations inspectable with a missing source but label their alignment/export unverified.
5. **Export and verify.** Offer an annotation table/manifest, a rendered overlay and a small derived image. Write to a temporary output bundle, read it back and verify declared fields, grids, transforms and sample hashes as applicable; publish only a complete bundle. Report copied, transformed, rendered, omitted or lossy fields in plain language.

**Annotation table.** CSV rows include feature UUID/type/scope, source asset digest and series/grid, coordinate-frame and interpretation IDs, named sample indices, optional physical values/units, time/slice/channel context, style/version and provenance. Store polygons as documented JSON geometry and masks as separate label artifact plus grid/label manifest; do not flatten them to an ambiguous point list. CSV is paired with a versioned JSON manifest because CSV alone cannot state the full contract.

**Overlay.** Export a selected image plane at its image grid with annotation styling and explicit channel/contrast/slice/time selection. The PNG preserves rendered pixels and rasterized marks only; it does not retain original samples, editable vector geometry, calibration or complete project provenance. Its sidecar names source digest, derived digest if used, grid, view/render parameters, annotation IDs and frame. A screenshot using pan/zoom/rotation must include that screen-to-grid mapping and be called a view capture, not a calibrated source image.

**Small derived image.** Record source digest, input/output grid, crop/axes/selection, sampling and interpolation, dtype, operation chain, software/reader versions and transform. A direct copy or crop that preserves sample values must be read back and hash/compare those values. Any projection, resampling, cast, intensity remap or baked LUT is a separate named operation; declare sample loss and derived identity. OME-NGFF 0.4 standard transforms do not encode an arbitrary affine, so preserve the complete matrix in the sidecar or explicitly resample into an axis-aligned representable grid as a new derived operation. If a receiving tool ignores the sidecar, identify the export as incomplete/lossy or require the explicit resampled alternative. Never silently discard rotation, reflection or shear. [S1]

For a multi-file export, use one temporary bundle directory, flush and verify each file and directory, then rename the directory on the same filesystem; place a final complete manifest/marker after readback. Failed export must leave any prior completed output intact and retain a clearly incomplete temporary for recovery/cleanup review. Hash the source before/after qualification workflows; display and annotation changes must leave it byte-identical.

## Useful opportunity, plausible alternative and deferred work

**Opportunity — NGFF labels.** After the project format is stable, export integer masks as NGFF 0.4 image-label groups where the grid is representable, with a source-image link when appropriate and an application sidecar for full identity/affine/provenance. The `source.image` link is optional in the spec; do not imply every reader will have one. Validate a prototype in independent NGFF readers before promising interchange. This extends the mask workflow without claiming labels replace editable vector annotations or undo history. [S1 §§3.6–3.7]

**Alternative — targeted conversion adapter.** If the inventory shows a high-value proprietary instrument outside the initial boundary, compare (a) a separately qualified Bio-Formats/vendor adapter that retains original bytes and records a derived OME-Zarr conversion with (b) researcher-directed conversion into the supported format before import. No Bio-Formats pin or integration is established by the current sources; choose neither until one instrument, metadata mapping, fixture and refusal/recovery path are researched. This is an alternative to widening the core reader matrix one unsupported case at a time, not universal compatibility.

Keep bundle comparison/annotation conflict review, live collaboration, cloud sync, remote storage, GPU acceleration, automatic segmentation, registration, HCS/plate and mosaic handling, pyramidal/multi-file TIFF and broader codec/sample types as separate optional leads. The six users' minimum exchange model is closed project bundles; concurrency/merge behavior changes identity and recovery requirements.

## Proposed validation gates — all UNEXECUTED except W1 and W7

The companion witness inventory includes exact procedures and scope limits. Before release:

- Resolve and lock Python, napari, Qt binding, tifffile, Zarr 2, Dask, codecs and SQLite on each workstation OS; build and reopen a common project on each.
- Create a consented lab fixture corpus with exact TIFF/NGFF metadata, codecs, chunk/tile shapes, multidimensional types, malformed cases and ambiguous axes/calibration. Include conformant NGFF arrays separately from user-corrected inputs.
- Measure the 3 GB target path and 16 GB RSS under cold/warm navigation, channel changes, editing, cancellation and adversarial tile sizes. Compare selected regions against reference reads; capture useful bytes/read amplification, codec buffers, p50/p95 latency and peak RSS.
- Check OME metadata precedence/default display, TiffData plane indexing, axes permutations allowed by the format, anisotropic spacing, local origin, explicit orientation, varying plane positions, irregular DeltaT, channel/slice/time scoping and pixel-only mode. Compare sample-center coordinates independently through view transforms and channel/layer operations.
- Mutate/replace linked file and Zarr sources during hash, after hash and before export; test interrupted portable copy and relocation. Confirm a changed source blocks verified exports without deleting annotations.
- Fault-inject artifact write, file flush, rename, directory flush and DB commit; reopen and classify staging/orphans/missing references. Repeat close-copy-reopen on each actual shared-storage type; keep live editing local unless proven safe.
- Test source-bound annotation plus a distinct derived-grid copy through crop, anisotropic resampling, reflection and rotation/shear. Read back table, overlay and derived manifest; verify exact original samples when unmodified and declared operation/loss when transformed.
- Exercise points, polygons, masks, style revisions, undo/redo, keyboard-only operation, focus order, accessible labels, non-color cues, screen-reader names and readable metadata/error/progress messages with researchers.

**Critical assumptions and consequences.** The component lock, codecs and Qt binding are unresolved; until qualified, the stack is a candidate only. Instrument inputs have not been inventoried; anything outside the matrix fails explicitly and may require a conversion path. A mutable linked source cannot prove absence of transient external writes without a snapshot/copy, so identity claims are conditional. SQLite and directory durability on the group's shared storage are unknown, so editing remains local and only closed-bundle exchange is proposed. Downstream sidecar support is unknown, so a standard-only rotated/sheared export cannot claim complete transform preservation.
