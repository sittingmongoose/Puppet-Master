# Reproducible notebook and data workspace — revised proposal

**Decision status:** bounded architecture proposal, not a built product. Source facts are marked **Evidence** and cited by source IDs in `sources.json`; design choices and forecasts are marked **Choice / inference**; executed checks and proposed work are labeled separately. Reviewed 2026-10-06. The 8-core, 16-GB, 5-GB input is an acceptance target, not a measured result.

## Recommendation and support boundary

**Choice:** make an ordinary project folder the portable record. Keep notebooks in standard `.ipynb` format, execute Python with CPython and a fresh Jupyter kernel through NBClient/Jupyter Client, use embedded DuckDB for CSV, NDJSON, Parquet and optional SQL, and keep project provenance in a versioned manifest plus append-only execution events. These are independently useful precedents: Jupyter defines notebook document and kernel protocol/execution mechanisms; DuckDB is a separate in-process analytical engine with tabular readers and SQL. Their projects and runtimes are independent; composition here is our product design, not an existing integrated reproducibility guarantee. [S1–S6]

Support Python notebooks and Python transforms first. Bind a project to a concrete interpreter build, platform/architecture, `uv.lock` with artifact hashes, notebook client/protocol versions, DuckDB build, and required native libraries. A lockfile is necessary evidence about packages, not proof that OS libraries, wheels or kernels exist on another machine. Until a qualified combination is selected, reopened results can be inspected/exported, but executable replay is marked unavailable or unverified. [S2, S3, S13]

Expose optional SQL as DuckDB SQL scripts or notebook calls using the same engine, project data contracts and lineage. It is not another general-purpose kernel: record SQL text digest, dialect and engine version. Do not promise arbitrary database-dialect compatibility or ambient external database connections. This gives the occasional SQL user a bounded path without building language kernels.

Start arbitrary untrusted execution only on qualified Linux using a separate least-privilege process boundary. Bubblewrap is a low-level mechanism whose mounts and namespaces are caller-configured, not a complete policy; explicitly test filesystem view, symlinks, sockets, network, resource controls and host configuration. No import blacklist is isolation. On unqualified macOS/Windows installs, allow editing, inspection and export but disable execution. This is a usability cost, stated in the UI. [S12]

The frozen manifest admits same-arm research proposal and three catalogs, but no critique/review artifact. I therefore independently checked the admitted proposal and relevant source chain; there are no critic-specific findings to resolve, and this missing input is not treated as evidence that critique passed. The revision preserves the supported architecture and coverage, corrects all five citation-ID shifts identified in the admitted leads, tightens the release-chain wording against new captures, and does not claim broader qualification.

## Project, import and data contract

A project folder holds `.workspace/project.json`, notebooks, Python/SQL scripts, small config, `pyproject.toml`/lock, referenced data, and committed result generations. The manifest records project/schema version, relative paths, transform and notebook IDs, explicit input references, data-contract revisions, runtime and engine/environment digests, output associations, and last committed generation. It contains no credentials or private dataset values. An optional local SQLite index is rebuildable and is never required for portable exchange. SQLite WAL has sidecar, checkpoint and same-host constraints; close/checkpoint before bundling, or use only files plus JSONL events for the simplest portable implementation. [S10, S11]

Import should reference a selected file in place where possible; copying/vendorizing is an explicit user choice. Record format, size, observed modification time, and content hash status. A full SHA-256 is strong byte identity but requires reading the whole file; a size/mtime or quick fingerprint is provisional, never proof of unchanged bytes. On clean replay or strong verification, hash the source; if it is missing, changed, or only provisionally identified, dependent results cannot be current. An absent external input on another machine opens with a missing-source status rather than being silently fetched or copied.

Schema sniffing is a suggestion to review, not a contract or full-file validation. Save a versioned explicit parser contract: format/parser version; encoding and invalid-byte policy; CSV delimiter, quote, escape, header and null tokens; NDJSON record policy; Parquet schema/partition rules; ordered fields, types, nullability, conversion and timestamp/time-zone rules. DuckDB documents CSV sniffing and option overrides, not correctness of a sample for all rows. [S4, S5]

Preserve Unicode code points without implicit normalization. Specify decimal precision/rounding and every string/numeric/timestamp conversion. Distinguish missing fields, explicit null, configured CSV null token and empty string where the format permits it; NDJSON field presence can require a sidecar before projecting to SQL NULL. A nullable additive Parquet field is allowed only by explicit schema-version policy. Incompatible type changes, missing required fields, duplicate declared keys, invalid encodings, corrupt records/pages and ambiguous timestamps stop validation for user resolution. Default behavior is fail with location, field, bounded escaped sample and reason; optional quarantine writes rejected records and reasons to a separate artifact with source identity and ordinal and reports counts. It never silently drops malformed data or edits originals. A preview is explicitly bounded/sample-only; only a full scan establishes full-input conformance.

Use source content digest plus physical record ordinal (and file/row-group/byte locator where stable) as row identity; a user-declared business key is additional only after null/uniqueness checks. Preview may preserve observed file order but labels it as source order. Query results have no order promise absent `ORDER BY`; reproducible ordering needs an order key and unique tie-breaker. Stable output order can cost memory/time: DuckDB documents insertion-order preservation controls and trade-offs, not a universal ordering guarantee. [S6]

## Notebook execution and provenance

Keep displayed cell position separate from execution event sequence, kernel session/generation, and saved result provenance. `.ipynb` fields such as `execution_count` and outputs represent document state, not a complete execution history or dependency graph. Jupyter messages can correlate requests and replies by session/parent message; NBClient can execute cells and surface lifecycle/error hooks. Neither deduces Python variable dependencies nor supplies data identity, sandbox policy, or a deterministic-replay guarantee. [S1–S3]

Interactive selected-cell execution remains available for exploration in the live kernel. Mark its outputs **unverified** unless complete provenance exists. A **clean replay** creates a fresh process/kernel from the project-bound environment, validates declared input identity/contracts, executes code cells in displayed order, records the actual sequence and events, and stops on first error by default. Record notebook/cell ID and code digest, event ID/sequence, session generation, timestamps, outcome, environment and engine digest, source/contract identities, permissions, output artifact digest and completeness. Save old successful output separately when an attempt fails.

Show four result states: **current** means completed clean replay with matching recorded code, declared dependencies, source identity, contract and environment; it means matches recorded inputs, not proof of determinism. **Stale** preserves prior result and provenance after an input changes. **Failed** means latest attempt errored, timed out or was cancelled; any earlier output remains separately stale/unverified. **Unverified** covers interactive or imported legacy output, missing provenance or incomplete replay. A kernel restart starts a new generation; interrupted/cancelled replay cannot make retained old output current.

Because Python is dynamic, conservatively invalidate the edited cell and all later code cells when an upstream cell changes. Changed source/contract stales direct consumers and descendants; undeclared file access stales the whole notebook. Environment, parser, engine or runtime digest changes stale all affected outputs, and stale all when dependency knowledge is incomplete. Only a completed clean replay restores current status. Cache only declared transformations, keyed by code, dependency/source digests, contract/parser, engine/runtime and options. Disable cache reuse for unseeded randomness, network access or hidden/unfingerprintable dependencies; cache is disposable and not provenance.

Progress includes cell, elapsed time, bounded output and accessible cancel action. Cancel kills the run process group, records cancellation, and marks incomplete outputs failed/unverified. Error status and traceback are keyboard accessible and announced to assistive technology. Compare saved/current provenance first, then offer structured table/text/image diff; numeric tolerance is an explicit display choice. Store large outputs as immutable artifacts with schema, row/byte count, digest and truncation metadata. A bounded notebook preview is visibly truncated; do not export it as complete or collect a huge scan into a Python dataframe by default.

## Scale, save, exchange and recovery

For the 5-GB goal, scan source files through DuckDB and push projections, filters and eligible aggregates into the engine; use bounded Arrow/Python batches only when interop needs them. A large sort, exact distinct, wide join or high-cardinality aggregate may need spill space or exceed limits. Make memory/temp-disk limits and unsupported operations explicit and fail helpfully. This does not promise every operator is out of core. Measure with generated 5-GB data on the stated workstation before publishing a performance claim. [S6]

Use immutable output generations: write new artifacts and event records, verify size/digest, flush where supported, then atomically replace a small current-generation manifest. Recovery keeps the last committed generation; an incomplete generation is interrupted/quarantined, never current. SQLite atomic-commit documentation describes mode-specific assumptions; WAL has separate behavior. Filesystem rename/fsync and storage hardware differ, so this is a design requiring crash-injection validation, not a universal durability guarantee. [S10, S11]

Allow one writer per project with an OS lock and compare-before-save digest. A second editor opens read-only or forks; sync-folder conflicts produce a conflict copy rather than silent overwrite. Folder exchange and a portable bundle include notebook/scripts, manifest, environment lock, selected result artifacts and a compact reproducibility manifest; data may be excluded with explicit external identity. No live WAL database is required. Open on another machine by validating lock/platform compatibility, source presence/identity and result digests; show limitations before replay/export. Credentials, private data, shared profiles, real-time collaboration, hosted execution, scheduling and broad kernel support are out of scope.

## Validation and remaining decision gates

**Executed by candidate — isolated component check:** candidate-authored standard-library Python parsed three embedded synthetic NDJSON records, asserted two accepted and one retained malformed timestamp at ordinal 3, preserved Unicode and null-versus-missing, checked an in-memory source digest and a source-sensitive cache key, then exited 0. The exact code, embedded input, stdout/stderr/exit and runner receipt scope are in `witnesses.json`. It validates only those assertions. It does not parse real files, exercise DuckDB or notebooks, prove filesystem immutability, sandbox security, large-input behavior, or full replay correctness.

**Proposed/UNEXECUTED:** (1) CSV/NDJSON/Parquet fixtures for quoting, escapes, invalid bytes, missing/null/empty, Unicode, timestamps/time zones, heterogeneous types, duplicate keys, corrupt pages and additive/incompatible schema evolution; compare parsed output and quarantine report with fixed expected results on exact supported engine builds, including PR #14464 cases. (2) On ordinary 8-core/16-GB host, measure wall time, RSS, temporary disk and cancellation for 5-GB generated input, scan/filter/projection/aggregation/join/sort and explicit spill limits. (3) Replay out-of-order interactive state, hidden globals, restart, code/source/lock changes, nondeterminism/seed, undeclared files and attempted network; check provenance, invalidation and every status. Cancel, timeout and kill mid-cell. (4) Crash-inject each artifact/manifest write boundary; test interrupted recovery, concurrent edits, stale sync copies, export/reopen on another OS. (5) Audit Linux mounts, symlinks, `/proc`, sockets, subprocesses, network namespaces, CPU/memory/PID/disk/output quotas and cancellation; qualify each OS separately. (6) Keyboard/screen-reader review of progress, cancel, errors, stale/current labels, diff and truncated output.

**Critical dependencies / bounded alternative:** supported environment pins and cross-machine native-library availability; DuckDB parser behavior for exact contracts; resource/spill capacity; atomic-save semantics on selected filesystems; and audited per-OS sandbox remain unqualified. If sandbox or environment recreation is not qualified, disable arbitrary execution and offer editing/inspection/export, or initially support declarative/SQL transforms only. A file-only manifest plus JSONL events instead of SQLite is a plausible simpler exchange path, trading lookup speed for fewer sidecar/checkpoint hazards. Useful opportunity: present DuckDB CSV sniffing as an editable import proposal that produces a committed parser/schema contract, never as full validation. [S4]
