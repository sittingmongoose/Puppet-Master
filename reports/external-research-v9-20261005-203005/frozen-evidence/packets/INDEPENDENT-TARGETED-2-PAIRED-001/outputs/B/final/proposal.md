# Local biomedical image review workspace: staged proposal

**Research scope.** This is a brief-only plan for a research annotation tool, not a clinical viewer. Public primary sources were selected live on 2026-10-05. The recommendations below distinguish external facts, engineering inferences, product choices and validation that remains to be done. No full application was built, and one isolated coordinate arithmetic check was executed (W1); that check is not evidence of any reader, viewer, persistence or export behavior.

## Recommendation and support boundary

**Product choice.** Build a local-first desktop workspace around a Qt shell and napari viewer/layer model, with a project-owned data/provenance layer and explicit export pipeline. Candidate pins for qualification are napari 0.9.2 (`595639295a153c84bcb127a9e07d801355440a35`), tifffile 2026.9.20 (`a14e516c4fa3c0c9ede980ebb3111260347dd213`), ome-zarr-py 0.20.1 (`0ac3207b12c6a5eb60b9fa4cab0b31bc2d1d35a7`), and OME-NGFF 0.5.2 (`5cdf83b6806b5e500477c7af69dae9ed2adcf77d`). These are research pins, **not a compatible, tested application lock**. Tifffile's documentation and ome-zarr-py's package metadata require a current Python/Zarr/Dask stack; assemble and lock one supported environment, then qualify the Qt/GPU combinations before committing to it [S2–S5, S12].

The first import boundary should be local, read-only TIFF/BigTIFF and OME-TIFF series with recognized 2–5 axis metadata, plus a single local OME-Zarr 0.5 image group only after read/write interoperability is qualified. Name exact sample types and codecs only after the qualification matrix. Begin with scalar integer/float data, explicit T/C/Z/Y/X mappings, and supported calibration forms. Unknown codecs, vendor-specific TIFF tags, ambiguous axes, malformed metadata, unsupported OME-Zarr versions, and unrecognized higher-level layouts must stop at preflight with a useful explanation. Do not advertise “all TIFF” or universal format compatibility. Preserve the original metadata bytes and show them with the parser's interpretation. Let the user cancel, choose an explicit axis/calibration correction recorded as project metadata, or convert through a separately reviewed workflow. If scale is unknown, allow pixel-coordinate review only after clear confirmation; do not invent physical units. Failed or cancelled import must leave the project and source intact and any incomplete staged asset identifiable for recovery/cleanup.

**External fact.** Tifffile 2026.9.20 documents TIFF/BigTIFF and OME-TIFF readers that can expose data as Zarr-backed arrays from strips, tiles, pages, SubIFDs and series, with a Dask example and explicit format/codec limitations [S5]. OME-NGFF 0.5.2 specifies Zarr v3 image axes and per-dataset coordinate transforms [S1]. ome-zarr-py 0.20.1 has writer paths and tests for NumPy/Dask data and both format versions 0.4 and 0.5 [S2–S4]. Its `FormatV05` code also has a “writing not supported yet” comment that conflicts with its writer/tests. Treat that source inconsistency as a qualification blocker, not proof of dependable v0.5 writing. None of these sources establishes that this proposed desktop stack can keep a 3 GB workload within the workstation envelope.

**Engineering inference.** A TIFF-to-Zarr/Dask route and a chunked native format are plausible ways to avoid eagerly decoding a whole file, but actual bounds depend on codec, tiling/strips, reader, cache and view access. Use a byte-budgeted tile/chunk cache with eviction, a small number of workers, background reads, cooperative cancellation, progress, and a memory-mapped path only for qualified compatible files. Do not make an in-memory second copy as an import step. GPU remains optional and should affect rendering only, never the saved coordinate meaning. Profile peak RSS, cache residency, cancellation latency and concurrent reads on representative 3 GB specimens before describing this target as met [S5; proposed checks V2–V3].

## Project and coordinate contract

Use a directory project with `project.sqlite`, immutable staged/derived assets, and a manifest. One local user owns the writable project at a time. SQLite holds image records, original metadata (or a lossless metadata blob reference), axis/frame definitions, source identities, annotations, styles, undo/redo commands, display presets, operation history, and app/schema versions. Large data stays in separate assets rather than SQLite rows.

Every image record should hold: stable project `image_id`; source `source_id`; original URI/path and selected series/group; size and streamed SHA-256; format/parser and version; byte-level original metadata; array shape and exact ordered axis descriptors (name, type, unit, direction where known); source/derived status; and frame identifiers. A path and hash alone do not identify which TIFF series or OME-Zarr group was opened, so retain that selector too. For external references, record the originally chosen path and relative handoff path if available. On reopen, resolve paths explicitly and compare size/hash/series identity; if missing or changed, request a user-selected rebind and record it. Never silently substitute an image with the same filename.

**Product choice.** Define array coordinates as continuous, zero-based sample-center coordinates in a named ordered data frame. Store the explicit `axis_order`; never infer that user-facing x/y order is array order. For every frame, store a float64 homogeneous affine (or equivalent complete transform) from array-index coordinates to named world/physical axes and units: `world = A * index + b`. Store origin, orientation, sampling, units and any correction with that frame, plus the original metadata interpretation. Axis flips/rotations and channel/time mapping must be explicit. Napari's layer model supports affine and axis/unit metadata, but its view transform is not a substitute for this project-owned contract [S13].

OME-NGFF v0.5 orders axes in metadata, requires axes to correspond to array dimensions, and defines scale followed by optional translation in each dataset coordinate transform; the transform maps data coordinates toward physical units [S1, `#axes-md`, `#trafo-md`]. The isolated witness W1 uses a small anisotropic, nonzero translation example to demonstrate why order matters; it is arithmetic only. Because this NGFF transform representation does not cover every arbitrary affine/orientation operation, retain a full project affine when needed. Either store a corresponding explicit transform record outside NGFF metadata or create a resampled derived asset as a distinct operation. Do not claim a plain NGFF scale/translation has encoded a rotation it cannot express.

Represent vector annotations with geometry type and full-precision vertices in the source data frame, associated `image_id`/frame, and a scope: plane, volume, or whole acquisition. Record fixed-axis selectors (for example, `t=4`, `z=12`), coordinate/axis order, optional computed physical vertices, units, style ID plus a style snapshot, author and timestamps. Points/polygons should retain their source-frame coordinates even as display settings change. Masks are integer label arrays with their own shape, axes, transform, source frame and label table; an NGFF label image is useful for pixel labels but is not a replacement for all vector semantics [S1, `#labels-md`]. Save channel selection, time/slice selection, colormap, window/level, opacity and active pyramid level as display state, distinctly from samples. Contrast/window changes must never rewrite original sample values.

Each geometric operation creates a new derived identity and a provenance record: parent/source hashes, operation name and version, parameters, interpolation, output dtype, transform before/after, software version and output hash. Preserve a mapping back to the source frame. Resampling, crop, orientation normalization and registration are data operations; a display-only rotate/zoom is not. Annotation export must reference the exact source/derived identity and transform used.

## Workflow and failure recovery

1. Create a project and choose reference or copy-in for each local image. Import read-only. Stage any copied or derived asset under a temporary name, validate its metadata and hash, flush it, then rename into the asset store before committing a DB row that refers to it.
2. Show provenance and metadata preflight: instrument/vendor strings as captured, series selection, axes, units, pixel/voxel sizes, dtype, compression and every ambiguity. Preserve source values verbatim; explain any proposed mapping before the user accepts it.
3. Navigate T/C/Z/Y/X axes; select visible channels, time and slice; adjust display mapping. Show current coordinate frame and active pyramid level. A multiscale view may display a coarser level, so translate annotations to the full-resolution source frame and test the mapping rather than saving view-level pixel positions [S10].
4. Annotate point, polygon and mask; select reusable styles; provide keyboard navigation and visible focused controls. Support annotation undo/redo as durable commands, with save/reopen restoring both edits and history. Keep source and derived layers visibly distinct.
5. Save transactionally. SQLite can provide atomic transactions for one database subject to its documented filesystem, locking and hardware assumptions [S14]. Group annotation and command-log updates in one transaction. Write derived files first to staging, flush, validate/hash, then rename and commit the database reference; an interruption before the DB commit can leave an unreferenced staged/orphan file for safe later cleanup, while the DB should not point to a half-written asset. Keep a recovery manifest/checkpoint and make the next open identify incomplete staging. Test crash points, disk-full and power-loss-like interruption on supported local filesystems. Do not assume a database transaction makes a separate image file atomic.
6. Close and hand off a consistent snapshot. For a live DB, use SQLite's Backup API or produce a closed/checkpointed copy; do not plain-copy a database during an active transaction. Include WAL/journal state when needed. SQLite warns that broken locking on network filesystems can corrupt data [S15]. Start with local single-writer editing and exchange closed snapshots through shared storage. Do not treat an ordinary shared folder as a safe live multiwriter database until that exact filesystem and locking behavior is verified.
7. Reopen on another machine by validating manifest/database/assets and hashes, resolving/rebinding external sources visibly, then reconstructing display and frame state. Offer a portable bundle that embeds data or a lighter handoff bundle that references it. Embedding a multi-GB source duplicates storage and transfer; references are smaller but depend on stable share paths and reachable originals. Make this trade-off explicit and never modify original image files in place.
8. Export and report what is preserved (below); validate each export before publishing it from a temporary sibling path by same-filesystem rename where supported. Atomic rename and durable flush semantics vary by filesystem, so qualify the actual target.

## Export contract

- **Annotation table:** CSV plus a JSON sidecar (or JSON table) with one geometry record per annotation, full-precision coordinates, explicit zero-based sample-center convention and `axis_order`, unit/frame, scope and selectors, style, source/derived ID and hash, relevant transform ID, and software/schema version. The table does not contain source pixels or promise that another application understands the sidecar without a defined schema.
- **Mask:** integer label image plus label table and axes/transforms in qualified OME-Zarr where possible; retain a supported TIFF option only if its mask axes/calibration round-trip is tested. A mask export preserves discrete label values and declared geometry, not editable polygon history or undo history.
- **Small derived image:** export a small lossless crop in an agreed TIFF/OME-TIFF dtype and include a sidecar with parent hash/series, crop origin, ordered axes, calibration, operation, interpolation and output hash. Verify cropped samples against source reads. Offer a rendered PNG overlay only as a separate convenience: label it as display-rendered (channels/window/colormap/opacity applied, likely 8-bit), and state that it does not preserve raw intensity, independent channels, or all calibration unless the sidecar is kept.
- **Verification summary:** include hashes and checks for table parse/coordinate round trip, mask alignment, crop pixel equality, calibration and source identity. Do not describe “export succeeded” as proof of fidelity until reopened in a second reader/viewer and compared.

## Source-backed failure lesson

Napari issue #8962 reports a hidden 4D Labels layer crashing in a 3D viewer because the slice placeholder remained 2D after the display dimensionality changed. The report traces the mismatch from `set_slice_input` through visual creation and explicitly relates it to an earlier dtype fix that had missed shape [S6]. The maintainer discussion preserves the no-fetch optimization for invisible layers and points toward updating placeholder state [S7]. PR #8968 closes the issue; its changed code refreshes the empty placeholder's rank when a hidden layer's slice input changes, and its regression test checks the placeholder rank in 3D for Image and Labels [S8–S9]. The merged fix is commit `5c700d1424ba18689b74646e813f31753421610c`, included in napari 0.7.1 [S8, S10]. The corresponding regression test is still present at the current researched napari 0.9.2 tag [S11–S12]. This is a complete issue → discussion → code fix → regression test → release/current-test chain. The source tests were inspected, not run here. It establishes a concrete state invariant and a regression-test design, not broad reliability, correct coordinates, lazy I/O, annotation persistence, or performance for this proposed app.

**Plan implication (engineering inference).** Keep lazy/no-fetch behavior, but whenever hidden layers change dimensionality ensure their placeholder shape and axis metadata stay synchronized. Add app-level regression tests across Image/Labels, hidden/visible toggles, 2D/3D, 4D inputs, and active pyramid levels. Napari is a rendering/editing component candidate, not the owner of project persistence or the full data contract.

## Opportunity, alternatives and deferred scope

**Opportunity.** Qualified local OME-Zarr 0.5 images and integer label arrays offer a useful chunked, multiscale interchange path for derived masks and imagery [S1–S4]. Treat this as a bounded, tested export opportunity, with TIFF crop plus explicit sidecar as fallback while the v0.5 writer discrepancy is resolved. OME-NGFF axes and scale/translation metadata can carry common calibration cases consistently; arbitrary transformations still require the project-level affine or explicit resampling.

**Plausible architecture alternative.** A custom Qt + VisPy canvas with the same reader/storage/project contract could provide tighter control over keyboard accessibility, annotation interactions, lazy placeholders and recovery UI. It would require the team to own substantially more rendering, layer and slicing behavior. Choose it only if a napari embedding prototype fails concrete interaction or compatibility checks; reuse the napari regression lesson either way.

**Later, not minimum obligations.** Cloud services, shared live multiuser edits, automatic segmentation, registration and vendor-wide compatibility remain deferred. A batch conversion bridge for additional proprietary formats may be evaluated after collecting the group's actual file inventory; conversion should be explicit, preserve originals and show a provenance record. Preserve these as leads, not promises [L4–L6].

## Proposed validation (not run)

The listed checks are proposed/UNEXECUTED unless marked W1 in the witness inventory. First qualify a locked build on the supported desktop OSes; then test the user-visible contract end to end.

- **Input matrix:** small golden files for tiled/strip TIFF, BigTIFF, OME-TIFF, local OME-Zarr v0.5; qualified compression codecs, integer/float dtypes, 2–5 dimensions and known/nonzero anisotropic calibration. Compare selected pixels and parsed metadata with independent tools. Test unknown axes/codecs, corrupt/truncated files, ambiguous calibration and cancellation; verify project and original remain unchanged.
- **Large data:** a representative 3 GB file on 8 cores/16 GB RAM, recording peak RSS, cache limit, worker count, first-view and navigation latency, progress, cancellation latency, pixel correctness and whether a full source-sized copy occurs. Exercise competing reads and low-memory behavior; repeat with and without optional GPU.
- **Coordinates:** sample centers, boundaries, anisotropic scales, nonzero origin, axis permutations/reflections, NGFF scale-then-translation, hidden axes, channels/time/slice scope, multiscale level switch, rotations and resampling. Compare vector/mask positions before and after save/reopen/export and verify inverse mappings where defined.
- **Persistence and handoff:** save/reopen on a second machine; kill at every staging/rename/DB-commit boundary; inject disk full and interrupted exports; verify recovery, no DB reference to partial assets, no lost undo/style state and stable hashes. Test actual shared storage locking/rename/flush semantics before supporting anything beyond closed bundles. Test missing/moved/changed external sources and explicit rebind.
- **Export and accessibility:** reimport table, masks and crop through independent readers, check crop values bit-for-bit and overlay alignment, inspect reported losses; test keyboard-only navigation, shortcuts, focus visibility, legible metadata/errors, and undo/redo behavior with researchers.

These validations are necessary before claiming the 3 GB target, broad TIFF support, crash recovery, cross-machine portability, or export fidelity.
