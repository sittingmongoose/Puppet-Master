# Incremental proposal: biomedical image review workspace

**Prepared 5 October 2026.** This is a standalone plan for the supplied research-workspace brief. Public primary sources were selected and reviewed for this stage; the task and brief themselves supplied the domain framing. It does not claim universal image compatibility or that a viewer component already provides the proposed project behavior.

## Recommendation

Build a local-first Python/Qt desktop application in small, testable layers. Evaluate napari 0.9.2 as an embedded multidimensional canvas for image, points, shapes and label layers, but keep the project model, source identity, annotation contract, import decisions, persistence, recovery and export under the workspace’s control. If embedding creates an unacceptable dependency or interaction burden, use the same contracts with a smaller Qt canvas. Napari describes multidimensional viewing and layer types that fit the navigation and editing surface, but its README and release notes do not establish the project-level guarantees this brief requires. [N1, N2]

Start with a declared, tested format subset and a bounded reader interface. Tifffile demonstrates a mechanism for returning TIFF data as Zarr and indexing tile/chunk slices; that supports a promising TIFF-family adapter, not a claim that a 3 GB image is already bounded or responsive on the target workstation. [N10] Use OME-NGFF 0.5 as a storage/interchange contract where its supported axes, transforms and integer labels fit. Its scale/translation model is not a complete internal coordinate model for all orientations or affine corrections. [N9]

The project owns durable metadata and annotations. The original source remains immutable; display adjustments are view state; geometric transforms and resampling create separately identified derived data. Store source and project files by reference by default, with an explicit verified-copy option for portable handoff. Work on a local project copy during editing and exchange closed, validated bundles over ordinary shared storage.

## Evidence, inference and choices

**External facts.** Napari 0.9.2 describes itself as a multidimensional image viewer built on Qt, VisPy and the scientific Python stack, and lists image, labels, points, vectors, shapes and surface layers. [N1, N2] Tifffile’s pinned README documents TIFF/BigTIFF and OME-TIFF reading, Zarr-backed reads, and slicing a Zarr view by page/tile dimensions. It also notes that supported compressed segments can depend on ImageCodecs and records limitations for some TIFF-like formats. [N10] OME-NGFF 0.5 defines named axes with types/units, transformation metadata, multiscales and integer-valued label images; multiscale transforms are scale and optional translation, with axes and arrays aligned by dimension. [N9]

**Engineering inference.** Keeping rendering, format decoding, project persistence and geometry identity behind separate interfaces makes each failure diagnosable. Chunked access is the right candidate for large data because it can avoid allocating a second full volume, but actual peak memory, cache behavior, codec allocation and responsiveness remain measurements to make on representative files. The small arithmetic check in [W1] sizes a hypothetical cache only; it is not such a measurement.

**Product choices.** Use a versioned folder bundle with a compact manifest, a transactional local metadata store and immutable source references. Keep masks in chunked arrays when large; keep vectors/points and edit history as structured records. Ship only formats and codec/axis combinations backed by a maintained fixture corpus. Offer import correction explicitly and preserve original metadata. These choices target reopenability and recoverability for six researchers who exchange ordinary files; they do not add real-time collaboration or cloud services.

## Independent implementation precedents and plan impact

1. **Multidimensional viewer and layer precedent — napari.** The mechanism is a viewer/layer model: data layers can represent images, labels and shapes, while the UI supports n-D navigation, display and interaction. That is useful for prototyping channel, slice/time navigation and annotations. [N1] It is independent of the storage and format precedents below because it concerns interactive presentation and editing. Treat it as a canvas candidate, not as evidence of project bundle portability, hash-based source relocation, atomic saves, specific 3 GB memory use, or faithful exports; the cited README does not promise those.

2. **Image decoding and partial-access precedent — tifffile.** The mechanism is a TIFF reader exposing array/Zarr views so code can address a slice of a tiled/chunked dataset rather than eagerly materializing every plane. The README gives a concrete Zarr slicing example and documents TIFF/BigTIFF/OME-TIFF and codec-related scope. [N10] This is independently useful even if napari is not adopted: the workspace can wrap it behind an adapter and reject unsupported encodings. The README is pinned to commit `a14e516c4fa3c0c9ede980ebb3111260347dd213` (release message v2026.9.20); only the first 32,768 bytes of its 32,898-byte capture were delivered, and the relevant read/Zarr/limitations excerpt is within that delivered portion. Do not infer performance or complete coverage from the example.

3. **Axes, coordinate and label interchange precedent — OME-NGFF 0.5.** This standard supplies a vocabulary for axes, units, multiscale arrays, sequential scale/translation transforms and integer label images. [N9] It is independent of napari’s interaction model and tifffile’s decoder: it makes metadata and array meaning more portable. Use it for compatible exports and normalized import metadata, not as the entire project format. NGFF 0.5’s described multiscale transform subset cannot encode every possible orientation/shear, and its labels are integer arrays rather than a general vector-annotation schema. Keep a richer internal affine and vector records; on export, report any mapping or omission.

These precedents divide naturally into three replaceable responsibilities: viewing/editing surface, source-array access, and interoperable metadata/storage. That boundary avoids treating any one project as proof of the complete workflow.

## A consequential public failure chain

Napari issue #9247 reports a 3D shape whose face is hidden after moving to another slice while its hover/selection outline remains visible. The report supplies a reproducible multidimensional setup and distinguishes the expected off-slice state from the stale outline. [N3] PR #9059 closes that issue. Its patch filters selected shapes against the current view and clears/refilters hover state; the associated test diff adds `test_outline_not_drawn_off_slice`, asserting that the shape is not displayed and has no outline when off-slice, alongside selection/view tests. [N4, N5] This is a concrete bug → implementation → regression-test chain, not merely an issue title or linked PR.

The merge history also matters for applicability. PR #9059 merged as `de87bdd0be61a3f63e643865553277ab22a04ac8`; PR #9399 says the earlier merge was made without updating to main and that subsequent renames broke the change. Its patch updates the renamed `_indices_view`/`_view_indices` references in code and tests, with follow-up commit `1c0f90fb55b424cc78d97a3e3acc45fd3555ccf6`. [N4, N6, N7] The v0.9.2 release points to `595639295a153c84bcb127a9e07d801355440a35`; the captured compare response from the #9059 merge to that commit reports the merge as the base and includes the follow-up commit in the release ancestry. [N2, N8] This supports saying the repair is on the v0.9.2 line, not saying that every possible rendering path is regression-free. The test evidence is code-level coverage for specific slice/selection/hover cases; it does not establish GPU, platform, time-axis, persistence or large-data behavior.

**Plan consequence.** Scope visibility by annotation scope and current axis position, and test stale hover and selection after stepping across z and time. Exercise the same record after save/reopen before geometry transforms or export. Review and rebase changes on the current base before merging; rerun regression tests after conflict resolution. The history shows why green tests on a stale base are insufficient.

## Proposed minimum architecture and data contract

### 1. Import, reader and support boundary

First release candidate: read-only OME-TIFF and a deliberately selected baseline TIFF/BigTIFF subset, plus OME-Zarr 0.5/Zarr v3 only if the implementation team can pin and test that path. Start with TIFF data through a pinned tifffile adapter; keep the reader API generic (`metadata`, `shape`, `dtype`, `read_region`, `close`, cancellation/progress). Pin exact Python and codec dependencies in the eventual lockfile; the source README reports tested dependency versions but that is not a compatibility commitment from this proposal. [N10]

Publish an explicit matrix of supported containers, compression/codec, series selection, dimensions, sample types and calibration forms. A practical initial axis matrix is tested `YX`, `ZYX`, `CYX`, `CZYX` and `TCZYX`, with channel/time/space axes identified by metadata or an explicit user mapping. Keep all dimensions by default; do not silently squeeze singleton axes or infer that an unknown dimension is a channel. Accept only combinations actually present in a small golden corpus. Other layouts, untested codecs, ambiguous multi-series files, proprietary scanner formats and unsupported pyramid/plate layouts must fail closed as an unsupported import, not partially masquerade as a valid image.

Import into a temporary project area, parse metadata and retain the original metadata blob verbatim, then commit a ready asset record only after validation. On unsupported or ambiguous input, retain an import record with source path, parser diagnostics and captured metadata where readable; keep it non-editable until the user chooses a supported axis/calibration correction or an explicit conversion. Never rewrite the source. A correction is a separate versioned user decision linked to the original metadata. If parsing itself fails, retain a failure record and let the user retry or remove that record without damage to other project data.

For large data, issue bounded region reads through worker tasks and a byte-budgeted LRU cache; initially limit concurrent decodes and avoid unbounded prefetch. Cancel queued work promptly, discard results from stale view requests, and show determinate progress when known or an honest indeterminate state otherwise. Do not promise a 3 GB image target until representative cold-cache reads, decode peak memory and navigation latency pass on the ordinary 8-core/16 GB machine. Tifffile’s example is a mechanism lead, not that validation. [N10, W1]

### 2. Coordinate, image and annotation identity

Store, per image asset: stable project-local asset UUID; original filename and URI; content length and SHA-256; acquisition/series identifier; reader and version; verbatim source metadata; parsed dimensions, dtype and channel descriptors; ordered axis list with role and unit; and a normalized index-to-physical mapping. A path or modification time is a relocation hint, not identity. Compute a full content hash in cancellable background work and mark identity `pending` until complete. On reopen, find the old path or bundle-relative asset, then verify size and full hash before binding; otherwise show the image as missing/mismatched and leave annotations available offline. Never relink by basename alone.

Represent normalized axes with stable names (`t`, `c`, `z`, `y`, `x`, plus named custom axes), explicit order, lengths, units and role. Preserve axis order exactly as read and record any user-selected axis map as a distinct correction. Use a double-precision homogeneous affine from named image-index coordinates to physical coordinates, including translation, direction/orientation and possible rotation/shear; name the coordinate order and physical units. Define this product’s integer coordinates as zero-based voxel centers and test adapter conversion against each format’s convention. NGFF 0.5 supplies scale and translation that can map simple axes; it does not settle every orientation or this product’s pixel-center policy. [N9]

Each annotation record includes its own UUID, asset UUID and source digest, coordinate-system ID, geometry type, coordinates in named image-index space, style, author/time, edit revision, and scope. Scope is one of `slice`, `timepoint`, `volume`, or `acquisition`, with explicit fixed indices for applicable non-spatial axes. Do not encode acquisition-wide scope as a wildcard that can be mistaken for a selected slice. Points/polygons remain structured vector geometry; masks are integer label arrays. Bind annotations to the source identity and transform ID. For a derived/resampled image, create a new asset UUID and record parent digest, output digest, forward/inverse mapping, algorithm/version and parameters; transfer annotations only through an explicit, recorded mapping.

Save display state separately: visible channels, per-channel window/level or lookup mapping, colormap, gamma/inversion if supported, slice/time selection and viewport. Applying a display map must never change source samples or their hash. Distinguish this state from a geometric transform/resample, which creates an identified derived asset. Make this distinction visible in the UI as **Original**, **Display adjustment**, or **Derived image**, with the operation and parent shown.

### 3. Project persistence, recovery and handoff

Use a versioned project directory: a manifest plus local SQLite metadata/edit database, structured annotation records, and optional chunked mask/derived-data stores. Keep large immutable chunks outside SQLite. Use transactions for each annotation command and save undo/redo state as commands or revisioned edits so a crash does not leave geometry and history disagreeing. Choose a SQLite release at implementation time and test it on supported local filesystems.

SQLite documents that WAL mode uses companion `-wal`/`-shm` files and requires same-host shared memory; it is unsuitable for processes sharing a live database on a network filesystem. If selected for local editing, checkpoint and close before packaging a handoff; never have two workstations edit one shared WAL database. [N11] SQLite’s atomic-commit account depends on OS/filesystem/hardware sync behavior and notes corruption risks when those assumptions fail. [N12] Therefore use a local working copy, and test the actual shared-storage path rather than presenting database transactions as a complete bundle durability guarantee.

For project-wide save/export, write a new generation to a sibling temporary directory, verify database integrity and asset/chunk checksums, write a manifest with a completion marker last, then switch a small current-generation pointer or rename within the same filesystem. Retain the previous good generation until the new generation validates. At startup, validate the manifest and recover the last complete generation; offer an explicit recovery view for incomplete temporary generations. Flush and rename behavior must be verified on the group’s filesystems; if atomic rename is not reliable, retain versioned generation directories and choose by validated manifest. Cancel removes only uncommitted temporary outputs.

Offer two handoff modes. **Reference bundle** stores the project and verified source digest/path hints, keeping the large original in shared storage; it is small and fast, but requires the source to remain available and relocation to pass the digest check. **Portable bundle** copies source bytes into the bundle, verifies the full digest, and records that path; it costs disk and copy time but travels independently. Show required space and progress, never use a hard link that could imply ownership or permit source mutation, and preserve the source as read-only in the app. If a path is lost, reopen annotations offline and prompt to locate a candidate; bind only after full identity verification.

### 4. User workflow and exports

The minimum session is: create a project; import local files; inspect source and normalized metadata/provenance; resolve unsupported axis/calibration explicitly; navigate axes and display settings; annotate; save; close; reopen on another machine; resolve reference paths by digest or use a portable bundle; export a table, overlay and small derived image; review an export manifest that states what changed and what was preserved.

Provide keyboard-operable navigation and editing, legible metadata/error details, reusable named styles, and undo/redo for annotation changes. Keep focus behavior and shortcuts discoverable; do not make mouse-only actions necessary. Show loading, cancellation and failure state near the affected image/operation.

Export a CSV table plus a versioned JSON sidecar. Include project/image UUID, source SHA-256, series, scope, fixed non-spatial indices, geometry type and exact image-index coordinates; include physical coordinates and units when calibration is valid; include axis order, coordinate convention, affine ID, style and export version. CSV alone is not the canonical representation for polygons or masks. Offer integer masks as NGFF labels when appropriate, retaining axis/transform linkage and label-ID/name/color mapping; test interoperability with a second reader. [N9]

An overlay PNG is a rendered preview of the selected slice/time/channel, crop, window and colormap. Record those view settings and the output-pixel-to-source mapping in its sidecar. State that PNG omits hidden channels, z/time planes and editable vector geometry. A small derived-image export records whether it is a lossless crop/sample copy or a projection, resampling, type conversion or intensity transform; include parent digest, operation parameters and output digest. Do not imply that a rendered preview preserves original sample values.

## Opportunities, alternatives and deferred scope

**Useful opportunity.** NGFF 0.5 integer label arrays and multiscales offer a public path for sharing mask data and pyramidal images across tools, independent of the desktop UI. Adopt that subset when round-trip tests show axes and transforms remain interpretable. Keep vector annotations and richer coordinate transforms in the project sidecar where NGFF labels are insufficient. [N9]

**Plausible alternative.** For instruments that fall outside the initial reader matrix, evaluate `bioformats2raw` as an explicit conversion worker producing OME-Zarr, while preserving the original and logging converter version and output identity. Its README documents worker and tile-size controls and warns of format/I/O sensitivity, memory risk with high worker counts, special reader behavior, and cases where temporary native-library execution or filename interpretation affects results. The repository is GPL-2.0 and the inspected commit is an untagged 0.13.0-SNAPSHOT, so packaging, license review, and a pinned conversion environment are prerequisites. The source does not prove the converter will support the group’s files or meet the 3 GB target. [N13] It is a bounded alternative for selected inputs, not a universal fallback.

Defer cloud services, live collaboration, automatic segmentation and registration. Shared bundles meet the stated six-person exchange workflow. A later opportunity is a review-only external mask or NGFF-label import, with identity and transform checks, if the group wants cross-tool annotation exchange; it should not silently become a new supported source format.

## Proposed validation and critical assumptions

Only the arithmetic/coordinate component witness [W1] was executed for this proposal. It confirms the arithmetic of one declared scale/translation example and computes a hypothetical 32 MiB tile cache. It does not execute application, file, reader, renderer, storage, export or recovery behavior. All validation below is proposed and **UNEXECUTED**; witness inventory [W2] records the planned discriminating checks.

1. Assemble a versioned corpus of known-good TIFF/BigTIFF and OME-TIFF samples spanning each advertised codec, tiling/strip layout, axis map, dtype and series case, plus NGFF 0.5 samples. Record independent metadata expectations, pixel hashes/selected values and axis transforms. Reject every unlisted combination visibly.
2. On the target 8-core/16 GB workstation, cold-open a representative 3 GB tiled source, navigate random slices, cancel reads and measure process peak memory, cache ceiling, latency and decoded pixels. Compare memory against one full decoded source and enforce a predeclared bound; test concurrent channel/time requests. Repeat with compression that exercises decode allocation. This is the evidence needed for the bounded-access target.
3. Use a tiny anisotropic `TCZYX` fixture with nonzero translation and a flipped axis; check index→physical→index round trips, voxel-center versus corner behavior, axis permutation and export in an independent reader. Include singleton/custom axes and ambiguous calibration to prove they are not silently dropped or guessed.
4. Place a 3D polygon at one z plane, move to the next plane and time point while hovered/selected, save and reopen, then verify visibility and exported coordinates. Exercise undo/redo, keyboard-only navigation and focus, reusable styles, and mask label-ID mapping.
5. Change only window/level and compare original bytes/pixel samples and source digest. Separately resample or crop, then verify a new derived identity, parent link, transform and exact operation metadata. Test PNG preview limitations against the sidecar and table values against the canonical annotation records.
6. Interrupt import, copy, save and export at multiple stages; kill/restart the process; verify the previous committed project still opens, uncommitted generations are detectable, and no manifest calls partial output complete. Test path relocation, same-name different-content rejection, full-hash confirmation and offline annotation viewing.
7. Run storage/crash and rename/checkpoint tests on the actual local and shared filesystems, including a closed bundle handoff between two workstation profiles. WAL guidance is same-host only; SQLite documentation does not guarantee this deployment’s filesystem behavior. [N11, N12]

Critical assumptions still requiring evidence: the team’s representative instrument corpus; maintainers’ capacity to pin Python/Qt/VisPy/tifffile/codec versions; exact input axis and pixel-origin semantics; local/shared filesystem durability and rename behavior; acceptable import/hash wait time and disk budget; and licensing/packaging constraints if the Java converter is used. Until validated, list unsupported format/calibration cases in the UI and preserve source metadata and diagnostic records rather than guessing.
