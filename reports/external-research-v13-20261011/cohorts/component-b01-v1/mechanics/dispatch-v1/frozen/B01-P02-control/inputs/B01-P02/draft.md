# ZIP import proposal — investigator draft

## Flow and boundaries
Read the central directory for preview, list nested folders and files, and let the user select supported content. Treat names and metadata as untrusted. The importer never launches extracted scripts. Use a new private staging directory, reject an occupied final project name, and publish only after the selected files pass validation. A failure or cancel deletes owned staging without changing existing projects. Preserve empty folders selected by the user and report skipped unsupported files explicitly.

CPython supports several ZIP compression methods; availability depends on their codec modules, and unsupported/encrypted/corrupt input can fail [S1]. Show these failures as import diagnostics rather than silently omitting a member. The draft treats all encrypted input as unsupported by product policy; this is narrower than a claim that Python cannot read any encrypted ZIP. Keep passwords out of logs. Bound member count, per-file output bytes and total actual output, not just the input archive size.

## Extraction and validation
The standard `extractall` method passes ZIP member names directly through to filesystem paths without modification; therefore it offers no protection against `..` or absolute names. Reject it entirely as a library capability and implement every path conversion ourselves. Our preview may instead use `zipfile.Path`, which should inherit the same path sanitization as standard extraction. Resolve a candidate destination, require containment beneath the staging root, and reject absolute names, drive/UNC names, parent traversal, and symlink-like entries according to a documented import policy. Use a staging tree inaccessible to other writers; the name check is not a defense against concurrent filesystem substitution on its own.

Use each `ZipInfo` object when opening content so duplicate archive names remain distinguishable. On collision after normalization, keep the first selected member and import the rest under the same path, relying on the final checksum to expose any difference. Case-insensitive Windows paths and character replacement can introduce collisions beyond exact duplicate names. The user sees canonical relative destination names before committing selection.

## Integrity and resources
Stream content with a small buffer, update per-member and total counters, check cancellation between reads, and stop at explicit output budgets. Header `file_size` is useful preview information but not a security proof. Reading through EOF is part of detecting CRC mismatch; a filename-based allowlist does not prove content type. Reject unexpected content after probing a bounded prefix, record import provenance without leaking local paths, and handle disk/permission errors. No archive may exhaust memory simply because its declared output is huge.

## Alternatives, history and validation
An earlier one-click direct extraction into an existing project was rejected because cancellation and overwrites could leave mixed state. Standard extraction into a private staging directory remains interesting if combined with prior inspection and explicit collision/resource policy. A fully custom stream importer gives stronger product controls but adds maintenance obligations. A format-specific project package with a manifest is a future alternative; it cannot replace general ZIP import in this brief. Inspection of Python docs and extraction code/tests is actual work; adversarial import tests, Windows runs and publication durability checks are proposed, not executed. Test traversal, platform collisions, duplicate names, empty folders, corrupt CRC, unsupported codecs, cancellation, disk exhaustion and no mutation of existing projects.
