# Notebook backup/export proposal — CPython 3.13.9

## Architecture and user behavior
Use SQLite's online backup through `Connection.backup` rather than copying an open main file. CPython's documented API supports concurrent access, a page batch and a progress callback [S1]. A dedicated worker creates and closes its own connections, reports progress to the GUI and writes a staged database. Editing remains enabled. Do not load the full database into memory. Never overwrite a previously published bundle; create a fresh generation directory and ask the user to choose another name if occupied.

This proposal covers a manual local backup of committed note and tag rows, their database attachment references, and the referenced external files. Stage the database, manifest, and objects in a unique hidden sibling directory on the destination filesystem. Write and verify the complete bundle before publication, then use an atomic directory rename with no-replace semantics. If the destination exists or the supported platform cannot guarantee no replacement, fail without touching it and ask for another name. Publish only complete bundles. On failure, remove only this operation's stage; if cleanup fails, leave an incomplete marker and report the failed phase and cause. Never report success for a partial backup.

Use pages=64 as an initial tuneable batch, not a timing promise. CPython 3.13.9 calls sqlite3_backup_step with that batch and sleeps only when the step returns SQLITE_BUSY or SQLITE_LOCKED; it does not sleep after every successful batch. The sleep parameter is for successive retry attempts, not a throttle, so pages do not bound elapsed time or guarantee UI yielding. Choose the batch by measuring responsiveness, write latency, and throughput on the shipped build. Keep both connections file-backed, give their page caches a fixed budget, and stream bytes with bounded buffers; pages alone is not a memory cap. [S1, S2]

The callback receives status, remaining pages, and total pages on each iteration. Show the latest values as provisional and allow the denominator or remaining count to change as writes occur. Do not promise a monotonically increasing percentage against an initial page count, a fixed rate, or an ETA. SQLite documents restarts when a different connection writes during an online backup and warns frequent restarts can prevent completion; CPython's upstream modifying-progress test also records remaining counts of 1, 1, 0 with a committed write between callbacks. The target application's exact snapshot boundary and completion behavior need workload tests. [S3, S4]

Use a thread-safe cancellation event checked by a short callback; on cancellation, raise a dedicated BackupCancelled exception. CPython 3.13.9 calls sqlite3_backup_finish when the progress callback raises and propagates the callback exception. The worker catches cancellation separately, closes both connections in a finally path, and removes only its own uniquely named staging directory. Check cancellation between bounded attachment-copy chunks too. Send progress through a worker-to-GUI queue and do not update widgets inside the callback. This is a source-backed control proposal, not an end-to-end application test. [S2, S3]

The worker opens and closes its connections in its own thread. Only committed database state is included; the application must commit changes before marking them saved and must warn if an editor still holds unsaved UI state. The design assumes CPython 3.13.9 on local disks; remote synchronization and a server database remain out of scope.

## Bundle consistency and restore
A SQLite snapshot covers database pages, not files stored outside SQLite. It does not freeze external attachments; copying a file that an editor can replace or delete can produce a bundle whose database reference and bytes come from different generations. Digests catch byte changes but do not create a cross-system snapshot. [S4]

Prefer immutable, content-addressed attachment objects with stable IDs such as SHA-256 digests. An edit writes and flushes a new object, atomically publishes it, then commits the database reference; never mutate bytes behind a published ID. Acquire a backup retention lease before starting the database backup and keep it until references in the completed copied database have been enumerated, all referenced objects copied and checked, and the manifest verified. While any lease is active, garbage collection must not unlink any old or new object. Writers can continue by publishing new immutable objects. If the current storage design cannot do this, use a brief attachment-publication lock and retain superseded versions until relevant backup leases end; do not hold a long lock over a multi-GiB copy. A process-local lock is not enough if multiple application processes can edit the workspace.

Copy references from the backup database, not from the live database. Store objects as attachments/<object-id>, copy and hash fixed-size chunks, and map copied-database references to bundle-relative IDs in a versioned manifest. If current rows contain absolute paths, rewrite only the copied database for the bundle; restore maps the relative IDs into the new workspace. A missing reference, unreadable file, or hash mismatch fails the backup and prevents publication. This retention protocol is an application design proposal; it requires race and crash testing.

Restore into a new workspace, compare digests and run SQLite integrity and application referential checks before switching the UI. Keep the original database and bundles intact on restore failure. Exclude credentials and redact local paths from diagnostics; attachment contents are private even when the database itself is small.

Before restoring, validate the manifest and reject absolute paths, parent traversal, and symlink escapes. Verify the database digest and every attachment's digest and size, confirm each database reference resolves to a listed object, run SQLite integrity and application-level reference checks, and apply only supported schema migrations in the temporary workspace. Switch the UI only after validation; never alter the source bundle or replace the live workspace on a failed restore.

Restrict bundle and staging permissions to the current user where supported. Hashes detect accidental corruption, not confidentiality or authenticity against someone who can alter both files and manifest. If backups leave the device or face malicious tampering, encrypted storage and an authenticated manifest require a separate key-management design.

## Alternatives and history
An earlier idea copied only the database file during editing. Retire it: SQLite's WAL documentation says committed content can reside in a separate WAL [S5], and online backup has a clearer database snapshot contract [S4]. A logical dump remains an optional human-readable export rather than the default binary backup: it reconstructs SQL objects and requires deliberate transaction, encoding and restore decisions [S1]. A stopped-app filesystem copy is a viable operational alternative with a complete SQLite file-set policy; it loses the requested uninterrupted editing. Do not reject WAL mode itself or claim online backup freezes all external state.

## Validation status and proposed checks
Documentation, implementation and named upstream tests have been inspected; no application backup, cancellation, durability or restore test has run. Propose concurrent note edits during backup, repeated page-count changes, callback cancellation, destination permission/disk exhaustion, occupied names and restore with attachment deletion/replacement. Measure GUI responsiveness and throughput on representative GiB bundles. Checksums detect byte mismatches, not semantic snapshot consistency or crash durability. Shipping should wait for a tested attachment-generation protocol and interruption-safe staging cleanup.

Extend the release matrix with continuous commits from a second application connection; changes to remaining and total page counts; repeated restarts; multi-GiB peak-memory measurement; attachment replacement/deletion racing garbage collection; lease release after cancellation and crash; source and destination permission errors; disk exhaustion; publication-name races; and cleanup failure. Restore valid, corrupt, incomplete, missing-object, path-traversal, and unsupported-schema bundles into a fresh workspace, verifying the old workspace remains unchanged. Exercise both WAL and rollback-journal modes and every supported OS/filesystem publication primitive. Record CPython and sqlite3.sqlite_version for each build.

No executable witness or application test was run. The available local interpreter was Python 3.14.4 with SQLite 3.46.1, not the required CPython 3.13.9 target; a local run would not validate the target binding. The CPython 3.13.9 source and upstream tests were inspected, but upstream tests were not executed.
