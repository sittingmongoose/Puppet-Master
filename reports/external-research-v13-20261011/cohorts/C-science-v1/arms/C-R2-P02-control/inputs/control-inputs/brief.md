# C-P04 — Software planning brief

A desktop publishing tool will allow separately installed converters to produce export formats from a document snapshot. Research the export-worker component, including extension discovery, capability negotiation, isolation, progress reporting, and fair resource use when several exports run together. The deliverable is an architecture recommendation grounded in primary evidence and relevant implementation history, with alternatives and a practical validation plan. We have not selected a plugin runtime or converter product.

Converters may be maintained by third parties and may crash, hang, allocate excessive memory, or emit incomplete output. Users must be able to cancel one export without corrupting its input snapshot or damaging other running exports. An export should be reported as successful only when its declared outputs are complete and can be transferred to the requested destination. A converter update must not silently change the interpretation of a saved export preset.

Investigate the trade-offs among process boundaries, runtime sandboxes, and cooperative in-process interfaces. Examine filesystem access, temporary outputs, resource limits, and error propagation using actual governing mechanisms where available. Scheduling should account for interactive editing and avoid starvation of a small export behind repeated large jobs. Explain what can be guaranteed on different host platforms and what remains conditional.

Do not install plugins into a real user's app, grant every converter broad home-directory access, assume a sandbox label enforces a memory limit, or claim cancellation after a process exit proves artifact integrity. Preserve a way to reject unsupported converter capabilities before work begins. Any executed research checks may use disposable public code or synthetic converters; distinguish them from proposed production integration and stress tests.

Complete all substantive research and planning obligations within a maximum of 60 elapsed minutes. Finish earlier when the complete output is ready. There is no minimum research duration, no requirement to consume the allowance, and no credit for waiting. The deadline includes arm-specific setup, provider queueing after admission, tools, native retries, handoffs, revision and delivery. Output quality is assessed independently of elapsed time.
