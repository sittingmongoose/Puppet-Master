**Run/stage:** C-R2-P02-control / reviser

## Recommendation

Treat each export as a host-owned transaction and an independent failure, cancellation, and accounting unit. Use a versioned declarative converter descriptor and request/response protocol. Default to one native worker process tree per export for third-party and compatibility converters. Give it a frozen document snapshot and private per-job output staging only after preflight; keep the final destination and publication step under host control. Add a WASM component path for converters built for the selected runtime and narrow host API. Limit cooperative in-process converters to trusted, owner-controlled code or an explicitly accepted compatibility case. This recommends an architecture; it selects neither a converter product nor a plugin runtime.

A subprocess isolates many crashes and gives the host a termination target, but does not by itself restrict same-user file or network authority, protect a snapshot, cap memory, or contain every descendant. The revised contract therefore requires an explicit per-platform authority boundary before claiming snapshot protection. WASI preopens with read-only permissions can provide a narrower boundary for filesystem operations routed through that context, but native processes and other host imports remain separate concerns. Until each supported host has a tested mechanism, report the limit as best effort or reject that converter mode under an owner-set policy.

The worker's completion manifest is a claim, not the source of truth for completeness. Before launch, the host must know the required output set from the user request and the versioned converter/output contract. Compare the worker manifest to that independent set, then verify staged bytes and formats. A successful exit, self-consistent manifest, digest, or completed cancellation does not alone prove semantic completeness or successful destination transfer.

Use age-aware fair-share admission with per-job accounting, global and per-converter concurrency limits, and reserved capacity for editing. State scheduler liveness conditionally: an eligible job can progress when a compatible slot and its required budgets become available under the stated arrival assumptions. A numerical wait bound is a service target to choose and measure, not a property established by aging alone. No worker-count or CPU-cap setting proves fixed editor latency.

## Original brief and scope

The brief asks for a desktop publishing tool that uses separately installed converters to export a document snapshot. Research covers extension discovery, capability negotiation, isolation, progress, and fair resource use during concurrent exports; the recommendation must use primary evidence and relevant implementation history, give alternatives and a practical validation plan, and leave both runtime and converter product unselected.

The design must account for third-party converters that crash, hang, consume excessive memory, or emit incomplete output. A user must be able to cancel one job without corrupting its input snapshot or harming sibling jobs. Success means declared outputs are complete and transferred to the requested destination. Updating a converter must not silently change a saved preset's meaning.

The comparison covers process boundaries, runtime sandboxes, cooperative in-process APIs, file authority, temporary output, resource limits, errors, platform guarantees, and conditions. It must not install a plugin into a real user's app, grant broad home-directory access, infer memory enforcement from a sandbox label, or treat process exit after cancellation as evidence of artifact integrity. Unsupported required capabilities must be rejectable before work starts. Any executed research check would be limited to disposable public code or synthetic converters and must state its actual enforcement domain. This run performed documentation research only; no converter, downloaded code, sandbox, or future host was executed or configured.

## Released provisional plan and dispositions

The following four paragraphs are the exact released plan text. Each is followed by its disposition and complete recommendation.

### Clause 1 — declaration, staging, completion manifest, and promotion

> The provisional interface lets a converter declare supported inputs, output types, and a preset schema before admission. A worker receives a read-only document snapshot and a writable temporary directory. It returns a completion manifest listing generated paths and a status code. The draft would promote those paths to the destination when the converter exits successfully; inspect whether status and a path list establish the requested completeness and transfer properties.

**Disposition: retain declarative capabilities and isolated staging; reject status-plus-worker-paths as a completion or transfer guarantee.**

- **Discovery and identity:** Read a declarative descriptor without executing the candidate. Record a stable converter ID separately from display name and publisher, exact package version and digest, protocol version, supported input/output identifiers, required and optional capabilities, preset schema version, and entry point. Search app-managed extension roots or explicitly registered user-selected locations; do not scan all of home or grant broad home-directory access. A descriptor supports discovery and preflight; it does not prove safe behavior. VS Code's extension manifest is a metadata example only. Pass the requested output format explicitly; Pandoc demonstrates why extension inference should not decide a saved export's format. [S01](sources/index.md#source-s01) [S12](sources/index.md#source-s12)
- **Capability preflight:** Compare the job's input/output requirements to descriptor declarations and a worker handshake before queue admission. Reject absent or unknown required capabilities and unsupported output types before work begins. Ignore unknown optional values only when the protocol explicitly permits it. The handshake confirms protocol compatibility, not future converter behavior.
- **Independent expected-output set:** At request/preflight time, bind the exact required output set to the job from the requested export and the versioned converter/format contract. It must define required paths, formats/media types, cardinality, and any mandatory companion files. Explicitly mark optional sidecars and the condition that permits them. The worker does not get to define completeness by omitting entries from its own manifest. At completion, compare the manifest for exact required coverage and permitted optional outputs; reject omissions, extras, duplicates, unsafe names, and malformed entries. If a format or converter cannot describe its required outputs before work, the product owner must define that contract before claiming “complete.”
- **Snapshot and filesystem authority:** Freeze a job-scoped snapshot before the worker can start, and keep the original document safe while making it. The worker should receive read-only access to the snapshot and write access only to a fresh private staging area; one job must not reach another job's snapshot or stage. This is an authority requirement, not merely a protocol promise or file-mode label. Select and configure an OS identity/ACL/sandbox boundary for each supported native-worker host, test mutation, replacement, deletion, path traversal, links, and cross-job access, and keep the final destination inaccessible to the worker. Windows Job Objects manage process groups, not file rights; Windows file access instead depends on the process token and file/directory security descriptor (S08, S15). Linux cgroups govern resource distribution and do not establish filesystem authority (S07); a read-only descriptor can constrain operations through that handle but is not by itself path confinement (S16). macOS App Sandbox file authority depends on entitlements and user grants (S10, S14). WASI preopens can scope filesystem operations and set read-only permissions for a supplied directory (S06), but only for calls through that configured context. These sources establish candidate mechanisms and their boundaries, not a selected cross-platform design.
- **Completion verification:** The host waits until the tracked worker tree is stopped or terminated, validates the manifest against the host-known set, ensures every expected staged object exists and is an allowed file, rejects traversal/unapproved links and per-file or total quota violations, checks lengths and digests, and runs an independent format validator where one exists. A digest proves byte identity, not semantic validity; zero bytes are not generically invalid. Reject absent or truncated outputs, mismatched hashes, unsupported formats, invalid structure where a validator is available, and any output set mismatch. Pandoc's release notes document an ODF expansion that could exhaust memory, a cyclic style chain that could loop, and silent content-loss fixes; these examples support defensive limits and a regression corpus but do not prove that any validator catches every defect. [S02](sources/index.md#source-s02)
- **Promotion and transfer:** Keep destination authority with the host. After successful staging verification, copy to a destination-side temporary object, verify copied bytes, then commit using the strongest operation the destination supports. A same-filesystem Linux rename may atomically replace a name; cross-filesystem rename returns `EXDEV`. Namespace atomicity does not prove semantic completeness, durability, or provider acceptance. For network/cloud/provider targets, define success using that provider's strongest documented acknowledged operation, and report the limit if rollback or atomic commit is unavailable. Do not claim Linux rename behavior as cross-platform behavior. [S11](sources/index.md#source-s11)
- **Optional hardening:** Signed package metadata, content digests, independent parsers, per-file and aggregate output quotas, and bounded logs. Signing alone is not capability or behavior proof.
- **Owner decisions:** Define per-format completeness and validators, permitted optional outputs, converter contract rules, destination success/rollback semantics, and the response when a supported host cannot enforce the requested filesystem boundary.

### Clause 2 — process boundary, timeout/memory, progress, responsiveness, cancellation

> Each converter would run in a separate process with a wall-clock timeout and a configurable memory allowance. The host would accept progress messages on a bounded channel and keep editing responsive by limiting concurrent workers. Cancellation would first request cooperation and then terminate a worker after a short grace period. The implementation must distinguish requested policy from actual enforcement, including child processes, partial files, and platform differences.

**Disposition: retain per-export process isolation as the compatibility default; make deadlines, resource enforcement, progress and terminal states explicit and platform-conditional.**

- **Worker tree and failure isolation:** Use one process tree per export by default, with per-job IDs, snapshot/stage paths, logs, limits, accounting, and state. Bound and drain stdout/stderr. Do not assume a same-user process lacks filesystem or network rights. Track descendants and close unnecessary inherited handles. Windows Job Objects can associate `CreateProcess` children by default, terminate associated processes, and permit breakaway under configured flags; nested jobs depend on Windows 8 / Server 2012 or later. Verify the actual tree and breakaway policy. [S08](sources/index.md#source-s08)
- **Timeout and cancellation:** Use an application monotonic wall-clock deadline. Send cooperative cancellation first, then after an owner-chosen grace period terminate the entire tracked tree and wait/reap it. A Windows job-time limit counts user-mode execution rather than wall time, so it is not the application deadline. Keep `cancel-requested` distinct from `cancelled`; only report cancellation after workers are stopped and that job's partial stage is removed or quarantined. If destination commit passed its defined point, resolve the race as committed/completed or committed-with-warning rather than promising rollback. LSP 3.17 is a progress/cancel protocol precedent: canceled requests still receive a response; it does not prove arbitrary work stopped. [S03](sources/index.md#source-s03) [S08](sources/index.md#source-s08) [S13](sources/index.md#source-s13)
- **Memory and other limits:** Report requested limits separately from controls actually enabled and observed. On Linux, cgroup v2 `memory.max` defaults to `max`, needs controller availability and correct hierarchy/attachment, and can be exceeded temporarily under documented circumstances; `cpu.weight` is relative distribution for eligible scheduler classes, while `cpu.max` is a bandwidth cap. On Windows, explicitly enable job/process committed-memory flags; they are not automatic, and child containment must be verified. A Windows job-time cap is not wall time. On Wasmtime, explicitly configure the per-linear-memory setting, whose default is unlimited, and separately budget host/runtime RSS, multiple memories, host calls, fuel or interruption, threads/tasks, logs, disk, and bytes. App Sandbox documentation supplies no general converter memory cap. If a supported host cannot enforce a requested cap, expose it as best-effort or refuse that mode under an owner decision; a sandbox label alone is not evidence of a memory limit. [S05](sources/index.md#source-s05) [S07](sources/index.md#source-s07) [S09](sources/index.md#source-s09) [S10](sources/index.md#source-s10) [S13](sources/index.md#source-s13)
- **Descendants and filesystem rights:** Linux children inherit their cgroup at fork, but the process tree must be placed before untrusted work can fork and the resource controller must be available. Windows child association has documented exceptions. These controls do not substitute for the filesystem boundary required in Clause 1. Exercise escape/breakaway and access attempts on every supported platform; report uncontained cases. [S07](sources/index.md#source-s07) [S08](sources/index.md#source-s08)
- **Errors:** Keep protocol replies separate from host-observed process and destination outcomes. Return stable error classes for unsupported capability, launch failure, crash/nonzero exit, timeout/cancel, resource limit, malformed protocol, output verification, and transfer/commit failure. Include phase and job ID; preserve bounded diagnostics; never let worker-supplied status override host checks. Record OS counters/notifications only where configured and observed. [S03](sources/index.md#source-s03) [S07](sources/index.md#source-s07) [S13](sources/index.md#source-s13)
- **Progress and responsiveness:** Use per-job progress tokens and a bounded message size/rate. Keep progress separate from cancel/control messages. Coalesce or drop superseded progress if the UI falls behind; never block on progress or lose a terminal result. Validate message shape, monotonic counters when present, and terminal ordering. Conversion must not run on the UI thread. A worker-count cap is necessary but insufficient: reserve interactive capacity and cap aggregate worker CPU, memory, process count, temp space, and output. Measure editing latency under contention; neither Linux CPU weights/caps nor Windows job CPU rates promise a fixed response time. [S03](sources/index.md#source-s03) [S07](sources/index.md#source-s07) [S09](sources/index.md#source-s09)
- **WASM alternative:** A WIT component can describe typed imports/exports and versioned interfaces. WASI preopens can grant job-scoped filesystem capabilities to compatible modules. Configure module memory and interruption controls explicitly; also meter host/runtime memory, host-call time, output, and disk. Pin the runtime/spec versions and supported feature set. This is an alternative for converters that can target it, not an automatic sandbox wrapper for native binaries. [S04](sources/index.md#source-s04) [S05](sources/index.md#source-s05) [S06](sources/index.md#source-s06)
- **In-process alternative:** Cooperative APIs can report progress and cancellation with low overhead, but share address space, crash fate, allocator/threads, and most host authority. A blocked/native converter cannot be safely force-stopped per export. Limit this mode to trusted first-party code or a documented owner-approved exception.
- **State model:** Keep `queued`, `preflight`, `starting`, `running`, `cancel-requested`, `verifying`, `transferring`, `succeeded`, `failed`, and `cancelled` distinct. A host records `succeeded` only after independent verification and destination commit. A cancellation request or process exit alone is not a terminal artifact-integrity result.

### Clause 3 — presets and converter-version compatibility

> Presets would store the converter identifier, version, and configuration. The draft assumes a compatible version range can safely reuse an old preset. Research capability negotiation, schema migration, and explicit user review as alternatives to silent reinterpretation.

**Disposition: retain versioned identity/configuration; reject the assumption that protocol/API compatibility implies stable preset semantics.**

Store stable converter ID and publisher, exact package version and digest, protocol version, preset schema version, canonical parameter payload, and the version that interpreted it. Preserve the original saved representation. Before admitting an updated converter, confirm it still declares every required capability. Reuse settings only under a converter-declared compatibility/migration contract tied to the schema; an API version range alone says nothing about the meaning of old parameters.

For schema change, run a versioned deterministic migration on a copy and record source/target versions and outcome. Require user review when migration is lossy, ambiguous, newly unsupported, or changes output-affecting defaults; keep the prior preset recoverable. Default to exact build/digest pinning and explicit review for a changed output-affecting build, subject to owner choice. Pandoc's release record shows format inventory and conversion behavior can change; WIT package SemVer and VS Code engine compatibility metadata do not themselves guarantee saved-preset semantics. [S02](sources/index.md#source-s02) [S04](sources/index.md#source-s04) [S12](sources/index.md#source-s12)

**Owner decisions:** Choose exact pinning and the allowed verified upgrade range; specify which schema migrations can run without a prompt, if any. Never silently reinterpret a preset.

### Clause 4 — fair admission, promotion, dispositions, and witnesses

> Recommend fair admission and promotion rules, with evidence-backed dispositions for the proposed completion protocol, cancellation path, and resource accounting. Propose witnesses for a hanging converter, excess output, failed destination transfer, concurrent small and large exports, and converter upgrades. Label any witnesses executed during research and their actual enforcement domain; do not claim tests of our future host.

**Disposition: use two-phase publication and age-aware fair-share scheduling; all witnesses below are proposed and were not run.**

- **Admission:** A central scheduler enforces global and per-converter active-job limits. Before launch, check descriptor/protocol, required capabilities, snapshot readiness and rights, destination access where safely testable, disk budget, and whether required policy is enforceable. Reject unsupported required capabilities before queueing work.
- **Fairness:** Use aging or bounded fair-share admission with per-job accounting; reserve interactive capacity. Avoid pure strict priority, which can starve exports, and pure FIFO, which can leave a small export behind repeated long jobs. Treat estimated size/runtime as a hint. Aging does not guarantee a finite wait if a job is ineligible, its required budget never becomes available, its converter quota blocks it, or arrivals consume all compatible capacity. State liveness only while the job remains eligible and a required slot/budget becomes available under declared arrival assumptions. Owners must choose a measurable wait/latency target and capacity assumptions before describing a wait bound as a service guarantee.
- **Promotion:** `private staging → stop tracked tree → compare manifest with host-known expected set → path/format/length/hash checks → destination-side temporary transfer → destination verification → supported commit → succeeded`. On failure, preserve any prior valid target when the destination supports rollback and clean/quarantine temporary data. Where atomic replacement or rollback is unavailable, disclose the weaker guarantee and use owner-approved semantics. [S11](sources/index.md#source-s11)
- **Alternatives:** Native subprocesses favor compatibility and process-level failure isolation but need OS-specific filesystem and resource authority. WASM offers explicit imports/preopens for compatible modules but still needs host limits and runtime pinning. Cooperative in-process calls are lower-overhead but share memory, crash, and cancellation fate. Recommend subprocess as interoperability baseline, WASM as an explicit alternative, and in-process only for trusted/approved converters. No converter or runtime is selected.

## Critique disposition

Critic agreement is evidence to assess, not authority. I independently rechecked governing primary documentation for WASI filesystem preopens, Linux cgroup behavior, Windows Job Object process membership, and OS file-access mechanisms. The recorded observations and limitations are in the source map. My dispositions are:

| Criticism | Disposition | Final treatment |
|---|---|---|
| 1. “Read-only” snapshot and cross-job isolation lacked an enforceable host boundary. | **Accept and amend.** | A protocol/path promise is insufficient for hostile native code. Require a configured and tested per-platform identity/ACL/sandbox/capability boundary protecting the original, snapshot, and sibling stages. Specify best-effort/refusal behavior until available. Add mutation, deletion, replacement, and cross-job access witnesses. WASI read-only preopens apply only to configured WASI calls; Job Objects/cgroups are not file-access controls. |
| 2. Worker manifest could omit a required output and remain self-consistent. | **Accept and amend.** | Host binds the expected required set from the job request and versioned format/converter contract before work. Compare exact coverage and permitted optional outputs; missing and extra entries fail. Owner defines format-specific completeness where not inferable. Add a witness whose worker omits an output from its manifest. |
| 3. “Age boost or explicit admission slot gives bounded queue progress” omitted eligibility/resource assumptions. | **Accept the objection; reject the unconditional wording.** | Aging/fair-share reduces starvation risk, but no finite bound follows if a compatible slot/budget is unavailable or the job is ineligible. State liveness only under explicit availability/arrival assumptions; treat a numerical wait bound as an owner-set and measured service target. |
| 4. S06 used an unpinned `latest` URL and exact release was unresolved. | **Accept.** | Preserve S06 unchanged; record direct current-page observations separately and continue to label the exact release behind the `latest` alias unconfirmed. Pin a versioned URL/runtime before implementation. No source ID is reassigned. |

No substantive draft claim was found materially wrong in the critic's comparisons. The main changes are specification clarifications and conditional wording, not narrower product scope. All owner decisions below remain unresolved where evidence does not select a product policy.

## Open owner decisions

1. Supported OS versions and what the app does where filesystem, process-tree, memory, or CPU enforcement is unavailable.
2. Converter trust/distribution model, signing/update channel, discovery roots, and any user-selected install policy.
3. Per-format required output sets, permitted optional companions, validators, and the precise meaning of “complete.”
4. Native-worker filesystem authority mechanism on each supported OS, including protecting the original and snapshot during creation and export.
5. Default wall timeout, cancellation grace, CPU/memory/process/temp/output budgets, and editing responsiveness target.
6. Destination contract for local, network, removable, and cloud/provider outputs: required acknowledgement, atomicity/rollback, and prior-target behavior on partial failure.
7. Exact preset/digest pinning, allowed verified update range, and which migrations require review.
8. Whether to support a WASM converter ABI and which runtime/spec versions/features to pin.
9. Whether any first-party converter may run in-process and the explicit trust and impact boundary for that exception.

Primary evidence supports the stated mechanisms and limitations, not these unresolved product/platform choices. The implementation and all proposed validations remain future work.
