# Independent discovery — C-P04 export worker

**Run/stage:** C-R2-P02-control / investigator  
**Input used:** only the released brief at inputs/brief.md. The exact plan had not been released while this file was prepared. This is discovery evidence and candidate architecture reasoning, not the final clause-by-clause draft.

## Problem framing and candidate recommendation

Treat an export as a host-owned transaction around an untrusted converter. The host owns the immutable document snapshot, preset identity, per-export job record, progress/cancel state, staging directory, resource accounting, output verification, and final destination write. A converter receives only an explicit read-only snapshot and one private output area; it does not receive the mutable document or a broad home-directory view. Each export is its own cancellation and failure domain.

The leading candidate is an out-of-process adapter with a versioned manifest and a small request/response protocol. Discover installed descriptors without running code; validate protocol version, converter identity/version, declared output formats and required capabilities; then perform a short handshake before accepting work. Reject a missing required capability before scheduling. Run one worker instance per export unless evidence later supports a safe multi-job worker. This gives the host a process tree it can terminate on timeout/cancel and isolates native crashes, while leaving OS file permissions and resource controls explicit rather than implied by “separate process.”

A WASM component/WASI runtime is a promising constrained alternative for converters that can be built for it. WIT worlds describe imports/exports and package versions; the host can expose only job-scoped filesystem capabilities. This can make the interface and file authority more explicit and portable. It is not a free whole-process resource guarantee: Wasmtime’s documented linear-memory cap is per memory and is unlimited by default unless configured. Runtime/host memory, fuel, blocking host calls, temporary disk, and external destination writes need separate policy. No product/runtime is selected.

A cooperative in-process API is the lowest-friction option for trusted, bundled code and can avoid process startup cost. It shares the app’s address space, crash fate, allocator/threads, and most of its authority. Cancellation depends on cooperative checks; an unresponsive/native converter can stall editing and cannot be safely force-stopped at a single-export boundary. It is a poor default for third-party converters.

## Discovery, identity, and preset stability

Use a declarative descriptor such as a signed or otherwise trusted package manifest under app-managed roots; an explicit user-selected install path may be added later. Do not scan all of home or execute candidates to discover their capabilities. Keep a stable converter ID distinct from display name, publisher, package version, protocol version, capability/schema version, and content digest. Bind saved presets to an exact converter build (at minimum ID + version + package digest) and a versioned parameter schema. On update, report the new build and require a declared compatible migration or user confirmation; never reinterpret old parameters silently. VS Code’s extension manifest is a useful discovery pattern (unique publisher/name, semver version, declared entry point and compatibility range), not a worker sandbox or a product recommendation. (S12)

For capability negotiation, treat the descriptor as a preflight contract and the worker handshake as confirmation. Compare required vs optional capabilities and output MIME/format identifiers before the job enters the queue. Unknown optional values can be ignored only where the protocol explicitly permits it; unknown or missing required values fail closed. A descriptor alone cannot prove a converter will honor the contract.

Pandoc is a concrete CLI reference: it lists supported formats and accepts explicit reader/writer format flags. It also infers output format from filename extension and may default to HTML for a missing/unknown output extension. The host should therefore pass the requested output format explicitly and treat the executable’s version and format list as part of the selected converter identity. Its official 3.12.1 release history (2026-10-07) adds FODT and fixes an ODF expansion that could exhaust memory, a cyclic style chain that could loop forever, and cases of silently dropped metadata/content. That is practical evidence for version-pinned presets, hostile-input limits, and release/regression testing; it does not establish Pandoc as the selected product. (S01, S02)

## Snapshot, files, and success

Create an immutable, job-scoped snapshot before queueing. The worker gets read-only access to that snapshot and write access only to a fresh private staging directory, with path traversal and symlink handling tested. Keep the destination outside the worker’s rights: after worker exit, the host validates every declared output, rejects missing/unexpected/unsafe paths and size/quota violations, checks format-specific validity where practical, and records length plus digest. A zero-length file is not universally invalid; use format validation and protocol declaration rather than a generic nonempty rule.

“Success” should mean all declared outputs passed the host’s checks and the requested destination operation completed. It must not mean merely “exit code 0,” “converter said done,” or “process exited after cancel.” A converter’s output manifest can declare relative path, format/media type, byte length and digest; the host can verify those against staged bytes. The host then transfers files. A same-filesystem rename can give atomic namespace replacement on Linux, but cross-filesystem rename fails with EXDEV; copy-based or cloud/provider destinations need a destination-side temporary write, verification, and the strongest commit operation that destination supports. Report the actual transfer outcome and its limits; local rename atomicity is not equivalent to semantic completeness, durable storage, or remote-provider acceptance. (S11)

Keep state transitions explicit: queued → starting/preflight → running → cancel-requested → cancelled, or failed, or verifying → transferring → succeeded. A cancel request is intent; do not mark cancelled until the worker/process tree has stopped and staged artifacts are discarded or quarantined. Do not touch the input snapshot or another job’s directory on cancellation. The LSP 3.17 protocol provides a useful example for separate progress tokens and cancellation requests, but explicitly requires a response even for a cancelled request; it does not promise that arbitrary work has stopped. A worker protocol must define its own acknowledgment and host escalation deadline. (S03)

## Isolation and resource policy

**Processes:** separate native crash/hang domains, stderr/exit-code boundary, and a host kill target. A process can still inherit broad same-user filesystem/network authority unless launched with restricted rights. Track descendants, close inherited handles, drain bounded stdout/stderr, use per-job temp space, enforce wall deadlines and output quotas. Windows Job Objects group and manage process trees; nested jobs are available from Windows 8 / Server 2012, and child association has breakaway exceptions. Job CPU and memory limits are opt-in configurations, not automatic. Linux cgroup v2 can set cpu.weight/cpu.max, memory.max and pids.max, but defaults are largely unbounded and controller availability/permissions/hierarchy are deployment conditions. macOS App Sandbox is entitlement-based and user-selected file access is scoped; it is not evidence of a general memory cap for an arbitrary converter helper. (S07, S08, S09, S10)

**WASM/runtime sandbox:** host-provided imports are the authority boundary. Wasmtime WASI filesystem has no guest filesystem access without preopens; each preopen can restrict operations to a supplied directory. The runtime’s per-linear-memory limit defaults to unlimited and is not the same as capping total host RSS. Configure memory, fuel/epoch interruption where supported, and host-call timeouts; still meter file count/bytes, threads/tasks, logs, and host allocations. Treat the exact runtime version and enabled features as part of deployment evidence. This is strong for portable, deliberately supported converters but does not automatically wrap native-only converter binaries. (S04, S05, S06)

**In process:** cooperative interfaces can report progress and cancellation often, but a plugin that blocks or corrupts memory can affect the editor and sibling exports. Use only for trusted first-party code or as a product owner decision with clear support limits. A sandbox label or cancellation token is not a kernel-enforced memory/CPU boundary.

## Fair scheduling and interaction

Use a central queue with global and per-converter concurrency bounds, plus independent per-job budgets. Reserve capacity for UI/editor work and use aging (or a bounded fair-share queue) so a small export cannot be perpetually bypassed by repeated large jobs. Pure strict priority can starve exports; pure FIFO can put a small job behind a long stream of heavy work. Estimate size/runtime only as a hint, and guarantee progress through an age-based boost or admission slot rather than an unreliable “smallest first” promise. A worker pool shared across jobs weakens cancellation and fault isolation; the default should preserve one job as the accounting and termination unit.

Linux cgroup CPU weight is proportional among active children under the fair-class scheduler; cpu.max is a bandwidth cap, not an interactive latency guarantee. Windows Job CPU rate is also a cap and can stop all job threads for a scheduling interval after the limit is reached. These controls can reduce background pressure, but no OS API in this evidence guarantees a fixed editor response time. Validate UX under CPU, memory, disk, and converter contention. (S07, S09)

## Platform limits and alternatives

| Approach | Strengths | Limits / conditions |
|---|---|---|
| Native subprocess per export | Crash/kill boundary; mature CLI converters; straightforward logs and protocol | Same-user rights without extra sandboxing; per-OS process-tree and resource controls; copying can be costly |
| WASM component per export | Typed imports/exports, explicit host capabilities, portable module target | Requires compatible converter build/runtime; configured WASM memory is not total process memory; host calls, disk, and runtime costs remain |
| Cooperative in-process | Low overhead, easiest access to internal document model | Shared crash/memory fate; cooperative cancellation only; unsuitable default for untrusted third parties |
| Hybrid | Native worker as compatibility path, WASM where available, trusted in-process built-ins | More than one runtime and validation path; product owner must choose support matrix and migration policy |

Platform guarantee claims must stay conditional: Linux cgroups require delegated controller availability and correct attachment of the full descendant tree; Windows Job Object flags and OS versions determine containment; macOS app sandbox authority comes from entitlements and selected-resource grants; WASM limits apply to configured module resources, not all host/runtime work; in-process plugins have no hard boundary. A portable host contract can promise state transitions, isolated staging paths, preflight rejection, and output checks. It cannot promise identical hard resource enforcement on every host without an explicit supported-platform matrix.

## Initial validation ideas (proposals only)

No code, sandbox, converter, or stress check was run during discovery. After plan alignment, validate with disposable synthetic workers and fake destinations: (1) discovery never executes candidates; (2) capability/version mismatch is rejected before a job starts; (3) preset migration is explicit and versioned; (4) worker crash, hang, descendant spawn and cancellation affect only one export; (5) snapshot remains byte-identical; (6) traversal/symlink and declared-output mismatch are rejected; (7) truncated, malformed, or digest-mismatched outputs never reach destination; (8) same-volume atomic replacement and cross-volume/provider fallback report outcomes accurately; (9) CPU/memory/process/temp quotas behave on every supported host; (10) a small job eventually runs while large jobs repeat and editor input remains responsive; (11) progress and cancellation races produce one terminal state; (12) converter upgrade/regression corpus preserves preset meaning and output contracts. Proposed production integration and stress tests remain unexecuted.
