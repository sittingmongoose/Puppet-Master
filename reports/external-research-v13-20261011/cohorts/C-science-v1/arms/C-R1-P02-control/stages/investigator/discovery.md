# Independent discovery — interview preparation workspace

## Scope and recommendation

The brief asks for a local, non-destructive preparation workspace for separate-device interview recordings, with inspection, alignment, transcripts, named excerpts, comments, portable review packages, and graceful handling of unknown metadata and unsupported media. This is product research only. No recording was read, uploaded, or processed during this research. No executable witness or implementation check was run.

Recommend a small, layered workspace with a canonical project manifest and append-only revision history; FFmpeg/ffprobe as replaceable media adapters; a source-time alignment layer; a transcript/annotation model; generated previews stored as disposable derivatives; and a package exporter that resolves every asset reference. Keep original media read-only. Do not make a single NLE project file, transcript text, container creation date, nominal frame rate, or guessed wall clock the authority for all timing.

**Candidate directions.** (1) A purpose-built offline prep tool on FFmpeg/libav plus a versioned manifest fits the brief most closely: it can preserve precise source-native time and stream selection, make only selected previews, and define the change behavior of excerpts/comments. Cost: more application work, media compatibility maintenance, accessibility, and a well-tested package format. (2) ELAN is a strong maintained candidate for manual multi-media synchronization and tiered annotation, with linked-file relocation/relink controls; it is a useful pilot/interchange option for transcript work. Its documented offset entry and time displays are in milliseconds, so do not assume its annotation clock is precise enough to be the canonical VFR frame/sample model without a compatibility experiment. (3) Kdenlive+MLT supplies an existing multitrack review/editing UI and optional proxies while project media remains referenced; use it for a fast human-factors prototype, not as the portable data model. Its project schema evolves and newer project files are explicitly not backward compatible. (4) OpenTimelineIO (OTIO) is useful for timeline interchange, rational-time clip trims, markers, media references and bundles. It does not decode media, and its file bundle exporter copies associated media into one bundle; that can duplicate a large unique original per export, so it does not satisfy modest-storage needs by itself. Treat it as an export adapter, not the canonical state store.

## Data and time model

Give every original an immutable asset ID. Retain its supplied filename, observed size, SHA-256, import time, read-only status, container/codec summary, selected stream IDs, stream metadata, and probe/tool version. Hashes are identity/integrity aids, not proof that two differently encoded files mean the same recording. Do not overwrite or “normalize” originals. Keep source paths separate from project-relative package paths. For multi-audio inputs, preserve stream index, channel count/layout, language/disposition tags when present, and an explicit selected track/channel mapping; never silently choose or downmix a track because it is stream 0.

Use integer ticks with an explicit rational time base at storage boundaries, or exact integer sample counts for audio, rather than binary floating-point seconds or a single project frame rate. Keep distinct clocks: source presentation time, decoded frame/sample position, project/review time, and optional capture wall-clock/timecode metadata. A recorded creation date, timecode, GPS field or embedded start timestamp is evidence with provenance and confidence, not presumed synchronization truth. Record a manual offset as a signed rational transform between two named asset clocks, plus method, operator, anchor observations, date, confidence/uncertainty, and revision ID. For drift, support a piecewise-linear map from multiple anchor pairs (or explicitly report that only constant offset is supported); show the residual/uncertainty instead of collapsing it into an unqualified timestamp. Always preserve the original source timestamps and offset history.

For video, the stream time base and each decoded frame’s presentation timestamp/duration govern frame identity and order; nominal/average frame rate is descriptive only when timing is variable. Packet decode order can differ from presentation order. For audio, use the selected stream’s time base and sample count/rate. At boundaries, store a half-open source interval [start, end) and separately record the requested boundary and the resolved frame/sample boundary used for display/export. This avoids inclusive-end ambiguity and allows explicit quantization reporting. A UI may show timecode and milliseconds but must show the chosen source, stream and rounding/resolution; do not imply that rounded labels are the underlying exact value. If timestamps are missing, contradictory, discontinuous, non-monotonic, or cannot be resolved to a frame/sample, mark the span unsupported/uncertain and offer a manual anchor or abstain path.

## Components and boundaries

ffprobe can inventory container format, each stream, tags, packet timing, frame timing, and timecode fields. Keep inspection separate from decoding and export. Start with bounded metadata/packet probes and do not claim a shallow probe proves complete decodability or timing correctness. Use actual decoder work only for operations that need pixels/samples (frame thumbnails, waveforms, preview playback, validation of decoded boundaries). Stream-copy can avoid re-encoding but does not promise exact cut points: FFmpeg documents seek-to-nearest-keyframe behavior for input seeks, and timestamp/fps/muxer options can shift or round output timestamps. Therefore an excerpt is a reference, not a claim that every export is frame-accurate; generated review media must state which source streams and boundary rules were used.

Generate thumbnails, waveforms and low-resolution proxies only on demand or by a declared storage policy. Key every derived item by source content hash, stream selection, source range, transform parameters, tool/version, and generator settings; make it rebuildable and safely deletable. Never edit the source to generate these. A proxy is for navigation/review, not a replacement master. Display whether a proxy is current, its approximate size, and whether the preview path may change timing or drop tracks. A “no proxy” mode and a user-set storage quota are necessary. Avoid making a full-size duplicate merely to enable review.

Keep transcript words, speaker/tier data, transcript revisions, and anchor references separate from media. A transcript correction changes text by stable annotation ID and records a revision; it is not evidence to move a timestamp. An excerpt stores its name/ID, source asset/stream, source interval, alignment revision used for cross-source display, and provenance. A comment should declare whether it anchors to immutable source time, alignment/project time, transcript annotation, or excerpt identity. When an alignment changes, compute an impact preview showing old/new cross-source placement and affected comments; preserve the prior revision and never silently move a source-time anchor. Owners must choose whether an excerpt follows an updated alignment or pins its prior alignment revision. Make the choice visible at each excerpt and show orphaned/ambiguous anchors.

## Portability and alternatives

Use a package manifest containing project schema version, stable asset IDs, safe relative paths, byte sizes, SHA-256 hashes, stream identities, transcript/alignment/revision files, excerpts/comments, and generated-derivative provenance. One original should appear once per package even when many excerpts reference it. On import, verify paths stay inside the package and validate checksums, then resolve by stable package-relative path. A changed/missing file should be reported and offered as an explicit relink candidate using checksum first and name/size/metadata only as hints; do not silently bind. Keep a package self-contained when feasible. For modest storage, offer a review-only package with one proxy per unique source plus project data and a clear “originals excluded” label, or a lightweight reference package that requires a companion originals folder. Only the first is immediately playable on another machine; the second remains dependent on the separately moved sources. BagIt supplies a standard payload/checksum envelope but no timeline semantics. OTIOZ/OTIOD packages timeline data plus associated media, but its format expects unique basenames in a flat media folder and copies media, which may be unsuitable for large files.

## Release and issue-history signals

MLT v7.30.0 release notes include a fix for incorrect AVCHD (possibly other) frame rate handling in avformat, add xml-clip for parent/child frame-rate mismatch, and fix serialization of linked in/out points. Those fixes directly warn against trusting nominal rate or undocumented project serialization. The current MLT v7.40.0 release continues to list media-path, metadata and unsupported-format fixes. Kdenlive 26.08 documentation says projects reference most original media, store proxy references, and may be upgraded with a backup; it warns that newer project documents are not backward compatible, with the v23.04 sequence change taking document version 1.04 to 1.1. OTIO v0.18.0 introduces Clip.2 multiple media references and a schema downgrade facility; v0.18.1 is a Python-wheel fix. Its issue tracker still has an open request for clarity about MediaReference.target_url format (#1990, opened 2026-01-15), a portability caveat. FFmpeg FATE documents regression tests and public sample synchronization, a suitable source for fixture candidates; its suite tests FFmpeg, not this proposed application's end-to-end semantics.

## Proposed validation (not executed)

1. Build tiny synthetic media locally: two camera-like files with known leading offsets, one VFR track with irregular frame PTS and a nonzero start, one file with two deliberately distinguishable audio streams, and an audio-only track at known sample rate. Embed absent/conflicting wall-clock tags in separate variants. Keep expected sample/frame timestamps in an independent fixture manifest. Synthetic generation is future work; no media was generated here.
2. Import read-only, hash before/after, inspect metadata and then separately decode selected boundaries. Compare source frame/sample IDs and rational timestamps to expected fixture values; verify stream selection and unsupported/uncertain state. Include packet decode/display reordering, missing PTS, duplicate/non-monotonic PTS, fractional rates, and a very long duration to catch rounding/overflow.
3. Align with one and then two manual anchor pairs; confirm offsets, uncertainty and drift are saved exactly. Change transcript text without moving anchors. Change alignment and confirm the impact preview lists affected excerpts/comments, pinned/source anchors stay stable, and chosen follow behavior is explicit and reversible.
4. Generate/delete/rebuild thumbnail, waveform and proxy under quota; verify originals' hashes remain unchanged, cached outputs are keyed to revision/settings, and no full original is generated per excerpt.
5. Export twice with multiple excerpts from one source, move the complete package to a different root/path, verify all path references and hashes resolve, and verify the unique original appears once. Test review-only and reference package labels; corrupt, duplicate-basename, missing, path-traversal and changed-hash files must fail closed or require explicit relink.
6. Add permitted public fixtures from a pinned FFmpeg FATE subset and/or public-domain/licensed media only after recording each fixture's source/license/hash. Keep a public fixture separate from the synthetic oracle and test decoder/version variability. A future integration matrix should include supported OS builds, exact FFmpeg/libav version/configuration, multi-track playback, proxy selection, export/import compatibility, and an offline run with networking unavailable.

**Checks actually run:** web research of the primary documentation/releases linked in sources/index.md; read the released brief. No software, tests, media probes, sample downloads, package creation, decoder tests, or integration checks were run. Proposed validations above remain future work.
