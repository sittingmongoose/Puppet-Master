# C-P02 — Investigator draft against the released provisional plan

## Recommendation

Revise the provisional design into an offline-first, non-destructive workspace with an app-owned, versioned asset/annotation model. Keep each original once in a read-only asset collection (or explicitly reference it in place if the owner chooses that lower-storage mode), and link interviews, stream selections, excerpts, transcript revisions, comments, and derived previews by stable IDs. Store exact source coordinates and versioned source-to-session mappings; render project positions as a view. Use ffprobe/FFmpeg for inspection, decoding and optional preview generation, OTIO for tested timeline interchange, WebVTT for timed-text exchange, and BagIt/attached RO-Crate for the optional package that includes media. Keep external-reference export available for smaller transfers. C01–C14 are the primary-source records.

This retains the useful direction of the plan but rejects using untrusted metadata as clock authority, milliseconds as stored media boundaries, automatic rewriting of approved anchors, or a digest-only claim that every media reference has been resolved.

## Offset-only vs richer alignment

An offset model is a constant translation from each source clock into the session clock. It is easy to explain and undo, works for clocks that differ only in start time, and is a reasonable default for short recordings with stable evidence. It cannot correct clock-rate error: drift grows with recording length and may make clap points near one end misleading at the other.

An affine model adds a scale/slope term. It can model stable clock-rate mismatch, but needs separated anchors to estimate it and residual checks to show that the assumption fits. Keep all source/session anchors, method, author, uncertainty and fit revision. A hand-entered slope must be labeled as such. If residuals are high or drift changes, flag “not aligned” and require manual anchors or a separately approved segmented model. Do not automatically compensate by resampling audio or changing media.

Sources such as timecode, container timestamps and BWF metadata can seed proposals, but should be independently corroborated or manually accepted. PTS is a presentation coordinate, not a shared wall clock. A WebVTT timestamp is relative to the particular media it is synchronized with. These conditions support a source-to-session mapping layer rather than a single metadata-derived clock (C01, C07–C08).

## Preview-centered vs source-based playback

| Mode | Strengths | Failure modes / limits | Recommended role |
|---|---|---|---|
| Source-based | Preserves original frame/sample cadence, stream selection and native metadata; best reference for exact boundaries and sync. | Higher decode load; seeking may be slow; unsupported codecs/containers may not play; modest devices can struggle. | Reference mode and final boundary verification where decodable. |
| Derived preview | Faster browsing and thumbnails/waveforms; can reduce repeated decode and be reused across reviews. | Can change frame cadence, timestamp origin, audio mapping/channels or quality; transcode may fail or be interrupted. | Routine browse only after source-to-preview mapping is validated; never canonicalize edits to preview time. |

A preview job should write to a temporary cache key derived from source hash + selected streams + exact recipe/build. On completion, validate decodability, expected duration/timestamps, stream map and output hash, then publish atomically as complete. On interruption or failure, keep a resumable job/error state, discard or quarantine the partial output, and keep the original untouched. Store no “ready” pointer until validation passes. On cache miss, ask whether to wait, use source playback, or mark preview unavailable. This is a proposed design; no preview job was run.

## Corrections, optional improvements, and owner decisions

**Corrections needed before implementation planning**

- Replace milliseconds-as-storage with exact rational source coordinates and display-only rounding.
- Treat embedded clock metadata as a candidate, not authority; provide manual anchors and visible uncertainty.
- Preserve original source coordinates and mapping revisions; do not silently mutate excerpts/comments when mapping changes.
- Define digest as whole-original byte identity only; preserve separate stream/range/revision references and unresolved states.
- Define transcript revision, cue lineage, and orphan behavior; prevent ID reuse.
- Make export modes explicit: link-only resolver vs package with selected originals once; identify included derivatives.
- Track preview recipe, parent hash and time mapping; never let a preview replace source truth.

**Optional improvements that fit the brief**

- Batch-select audio streams, show waveform overlays, and create local waveform/proxy caches lazily.
- Provide hash-verified relink scan inside a user-chosen directory and show path/digest/stream-summary mismatches.
- Store a human-readable manifest alongside a machine-readable versioned schema and export a BagIt/attached RO-Crate variant.
- Keep fast local reflink/hardlink optimization as an implementation detail only; it is filesystem-dependent and must not be relied on by portable packages.
- Add OTIO adapter export/import for conventional clip/range workflows after round-trip tests. Do not hand promise full semantic round-trip for uncertainty or comments unless an extension preserves it.

**Owner decisions that research cannot settle**

1. Is the managed vault allowed to copy originals once, or must it support references in place? What local storage and backup limits apply?
2. Which operating systems/filesystems and container/codec families are in scope? Required audio channel layouts/sample rates? Maximum media size/count?
3. What tolerance/residual threshold counts as “aligned”? Which anchors may be automatic, and is local waveform correlation allowed? When is piecewise drift justified?
4. Should excerpts default to source-anchored or session-anchored when they cover multiple cameras? Which behaviors require explicit approval?
5. Which transcript formats and granularity are required (paragraph/cue/word/speaker)? What should happen to comments after a cue split, merge or deletion?
6. Should link-only export be the default? Which sources may be bundled, and how much preview/cache data may be included?
7. What retention, encryption, access and deletion expectations apply to interview content? How should unsupported/corrupt inputs be reported?
