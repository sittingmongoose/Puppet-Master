# C-P04 — Final export-worker architecture recommendation

**Stage:** reviser, run C-R2-P02-treatment.  
**Basis:** original brief, frozen investigator discovery and draft, exact released plan, both independent critique packages, and a targeted recheck of the disputed primary-source claims.  
**Recommendation:** use a parent-owned coordinator and a separately supervised process for each third-party native export. Bind every job to a stable snapshot and a versioned capability contract. Constrain every writable job path; reserve aggregate resources before admission; verify actual outputs and destination transfer before reporting success. Add host controls only when their runtime availability and enforcement are verified. Keep the converter/runtime selection and host degradation policy open.

This is an architecture proposal, not a product or runtime selection. No converter, plugin, application integration, synthetic worker, sandbox, scheduler, cancellation, storage quota, or destination-transfer witness was run.

## Proposed contract and job lifecycle

The coordinator owns job state, queue order, snapshots, policy, cancellation, verification, transfer, and final status. Use explicit states such as queued, preflight, starting, running, cancelling, verifying, transferring, succeeded, failed, cancelled, timed out, and resource-limited. Serialize terminal-state races and make cancellation idempotent. Distinguish unsupported capability, preflight/start failure, crash/nonzero exit, timeout, resource-limit event, cancellation, incomplete/invalid output, destination-transfer failure, and cleanup failure. Progress is advisory and never a success signal.

### Discovery, identity, and preflight

Use data-only manifests that can be inspected without loading converter code into the editor. Bind each manifest to the exact executable/package the host verifies; a converter's self-reported digest, signature, or capability list is not authentication. The owner must choose package admission, signing, update, and trust policy.

The manifest/protocol should separately identify the stable converter ID, verified build/package digest, protocol version, supported input and output media types, option-schema version, required options/capabilities, declared output cardinality or output-set policy, and resource needs. Before making document bytes or output handles available, validate the manifest and saved preset, then run a short preflight in an empty restricted job context. Reject an unknown protocol, missing required format or option, unsupported snapshot contract, invalid settings, output shape, or unmet resource requirement before dispatch. LSP 3.17 is a pattern for initialize-time capability exchange, correlated progress, and cancellation; it is not a converter standard, and a peer can ignore cancellation or be unable to react while synchronous [S01].

Persist the verified converter identity and canonical preset values with protocol/schema and relevant dependency identity. On update, retain the exact prior build when practical or present the user with an explicit incompatibility/migration choice and preview. Never reinterpret saved options through new defaults without review. Pandoc 3.8.3 documents specific output regressions from 3.8 for SVG/WeasyPrint PDF and Typst smart quotes; those examples justify pinned builds and upgrade regression checks, but do not prove every compatible range unsafe [S12–S14]. LibreOffice separately identifies an output extension, API filter name, and parameters, so a filename extension alone is not a stable capability contract [S15].

### Snapshot, filesystem, and completion manifest

Create a stable snapshot before dispatch, record its digest, and expose it through an immutable/read-only handle or materialized read-only copy. The coordinator owns the snapshot lifetime and checks identity around the job. Give each export its own private scratch/output tree. Close inherited handles, scrub environment and credentials, deny network by default, and grant only explicit capabilities. Do not expose the user's home directory.

All converter-writable paths must remain inside the job's bounded area, including redirected temporary files, sidecars, and intermediate staging. Normalize relative output names and reject traversal, absolute paths, symlinks or other escaping references, duplicate names, undeclared files, and unexpected output cardinality. Treat the worker's declared byte count and digest as assertions, not truth. Independently enumerate the closed job output tree, open/read and hash actual bytes, compare them with the negotiated output contract, and apply a format-aware integrity check where a safe validator exists. Do not claim every format has a semantic completeness test.

The terminal manifest should be bound to the negotiated job ID and contract and describe each output's relative path, media type, byte count, digest, and required/optional status. Enforce output count and size while writing as well as at verification. A zero exit code and a valid-looking path list do not prove complete output.

### Transfer and success

Keep generated bytes private until the coordinator verifies the expected output set, reads and hashes actual files, performs any safe format checks, and transfers or commits them to the requested destination. Report success only after that destination adapter confirms its commit/transfer contract. Where possible, stage beside the target. If cross-volume or remote transfer is needed, use destination-side staging and read-back verification; report failure if transfer or commit fails. Retain or delete unpublished staging according to an explicit cleanup policy.

Linux rename replacement provides atomic pathname visibility on the same filesystem; cross-filesystem rename can fail with EXDEV, and NFS can report ambiguous retry results. Windows ReplaceFileW requires same-volume files and documents partial-failure states; its write-through flag is unsupported. Linux file fsync alone may not persist the containing directory entry. These mechanisms do not establish universal multi-file atomicity or crash durability [S16–S18]. Define atomic visibility and durability separately for each destination adapter and filesystem/service. A cancellation or process exit never proves input or artifact integrity.

## Isolation, resource enforcement, and platform limits

| Option | Benefits | Conditions and limits | Disposition |
|---|---|---|---|
| Native process plus host policy | Separate address space and a distinct lifecycle per export; compatible with ordinary native converters. | A plain subprocess under the editor's user identity is not a security boundary. Pair least privilege, constrained files/handles, scrubbed environment, and verified process-tree/resource controls. Each host's mechanisms have availability and configuration conditions. | Default architecture for third-party native converters, subject to the host enforcement/degraded-mode decision. |
| WASM/WASI runtime | Compatible guests can receive explicit preopened filesystem capabilities and configured linear-memory and instruction-fuel limits. | Wasmtime documents these controls as opt-in; memory is per WebAssembly linear memory, not whole-process RSS, and fuel is not wall-clock CPU. Native code and host calls need additional supervision. Converter/API compatibility is unknown. | Optional adapter only after a compatibility spike; retain OS process/resource supervision. No runtime is selected. |
| Cooperative in-process API | Low IPC and copy overhead; can suit a trusted first-party interface. | A crash or memory corruption can affect the editor; stuck callbacks complicate cancellation; independent private-memory reclamation and hard per-worker accounting are unavailable at this boundary. | Trusted/first-party fallback, not the third-party safety promise. |
| macOS XPC helper/broker | Apple documents XPC as IPC for helper tools and privilege isolation with a separate service process/entitlement context. A broker could accept a snapshot capability and bounded scratch access. | Current documentation describes an XPC Service bundled in an app/framework and one process per client tied to that client's lifetime. That is not by itself a per-export worker contract or proof that an arbitrary separately installed converter has its own entitlement set, descendant teardown, or CPU/memory/disk quota. A Process-launched helper from a sandboxed app inherits the app sandbox; XPC services can have different entitlements [B02–B03]. | Evaluate as a host-owned broker or helper architecture; do not count it as sufficient containment without testing the actual entitlements, access handoff, cancellation, and descendant behavior. |

On Linux, cgroup v2 controllers must be supported, exposed, enabled top-down, and delegated. Limits can be overcommitted. cpu.weight shares CPU among active eligible children; it does not reserve the editor's interactive share or order the app queue. memory.max defaults to max, may invoke OOM handling, and usage can temporarily exceed it. io.max limits device throughput, not scratch capacity. For strong descendant teardown, place the worker in its own non-root domain cgroup before untrusted code starts, prevent it from moving itself out, verify membership, use cgroup.kill only where supported for that non-threaded cgroup, and wait until the job subtree has no live process before verification [S02]. Landlock can restrict filesystem/network access only when supported and enabled; check ABI and inherited descriptors, and apply policy before untrusted code runs [S20].

On Windows, Job Objects can apply process-tree and resource controls when the process is assigned and relevant limit flags are set. CreateProcess children are normally associated, but documented creation paths and breakaway flags are exceptions. Verify membership, disable breakaway unless explicitly required, and use a job termination policy. Job memory limits account committed virtual memory, not a universal RSS cap. AppContainer is a separate least-privilege access-control layer for files, registry, network, and process access; it is not the Job Object resource budget [S03–S05, S19].

On macOS, the reviewed App Sandbox sources establish file/access entitlements and selected-file conditions, not a general per-converter hard CPU or memory quota [S09–S10]. Archived Apple guidance says an inherited child receives static rights only; a selected-file grant acquired after launch must be passed as data or a bookmark, and this archived guidance should be rechecked for supported deployment versions [S10]. Current Apple documentation distinguishes a Process-launched child that inherits the app sandbox from an XPC service with different entitlements [B02–B03]. The sources reviewed here do not establish a general descendant-kill mechanism for the proposed converter design. Specify and test the chosen per-export teardown boundary before claiming it. If a platform cannot enforce and verify the needed containment, report the control as unavailable and follow an owner-selected reject/degraded-mode policy; never silently run as though a configured limit were active.

### Scratch capacity and aggregate admission

A per-job output byte counter is useful validation but does not cap every direct write or bound aggregate scratch consumption. cgroup io.max is a rate limit, not a disk-space quota [S02]. Linux XFS documents user/project quota accounting and optional enforcement; this is an example only, contingent on filesystem and mount configuration [B01]. Use a quota-backed per-job area or a write broker that mediates all writes, redirect all temporary and sidecar paths into the bounded area, and reserve aggregate scratch capacity before admission. Verify both bytes and file-count/inode behavior on supported filesystems. If no enforceable cap covers all converter-writable paths, either reject untrusted jobs or use a weaker policy only under an explicit owner-approved degraded mode.

Per-job ceilings and a worker-count ceiling do not bound the total load when several compliant jobs share memory, CPU, I/O, process, or storage bottlenecks. The coordinator should own a shared export envelope and reserve each admitted job's maximum against it, including memory, CPU/service share, process count, scratch, and device I/O policy. Use host-enforced job ceilings where available; do not rely on converter estimates as enforceable maxima. Reserve editing headroom and define the deliberate overcommit/failure behavior. Linux cgroup limits may themselves be overcommitted, and CPU weights or io.max do not create the app's aggregate budget [S02]. Numerical budgets and the policy for hosts without enforceable controls remain owner decisions.

### Progress, cancellation, and fairness

Bound progress message sizes, rates, and channel storage. Correlate samples to the job and phase, coalesce/drop stale samples, and preserve terminal errors. Progress is advisory and never changes the job to success. Keep conversion and transfer work off the editor's interactive thread.

Admit from a bounded global queue with FIFO aging or a tested weighted-fair policy. A later large job must not indefinitely pass an older small job. Per-converter active-job caps may prevent one extension from occupying every slot. Reserve an opportunity for the oldest aged job when compatible resources become free. Separate queue delay from service time. A finite queue-wait objective requires bounded service time and actual host capacity; aging alone cannot guarantee it. Kernel CPU weights do not implement application admission or queue order [S02, S05].

For cancellation, first send an idempotent cooperative request and wait the configured grace period. Then terminate only that job through its verified OS job boundary, wait for teardown, and discard or quarantine unpublished output. Serialize races among cancel, normal exit, verification, and transfer. Record exit code/signal, structured worker error, bounded stderr, resource-limit events, teardown status, verification, transfer, and cleanup. Never begin verification while any job process can still mutate the staging tree.

## Proposed validation plan — not run

These are proposed production-design witnesses. No listed witness was executed here.

1. **Discovery and negotiation:** present supported and unsupported media, options, schemas, protocol versions, output cardinalities, missing executables, duplicate IDs, malformed handshakes, and unknown required capabilities. Verify rejection before document bytes or output handles are exposed.
2. **Snapshot and filesystem confinement:** mutate the live document during a job; attempt snapshot writes, home-directory reads, sibling-job access, inherited-handle use, traversal, symlink output, and default network access. Verify snapshot digest stability and denials under each declared host policy.
3. **Hang and descendant cancellation:** stall in preflight and conversion, ignore cooperative cancellation, fork descendants, and have a child call setsid then fork again and attempt a late staging write. After forced teardown, verify no job process can mutate output before verification; cancel one of two concurrent jobs and verify the peer and editor remain usable. Record the exact membership/teardown evidence for Linux cgroup, Windows Job Object, and the chosen macOS design. A normal-child test is insufficient.
4. **Output completeness and storage limits:** exceed output byte/count limits; omit, truncate, duplicate, add, escape, or symlink an output; exit zero with an invalid manifest. Fill quota-backed scratch, exercise sparse/large writes, create many files, kill the worker during writes, and run multiple jobs that jointly approach the scratch envelope. Verify enforcement and cleanup on each supported filesystem; no success or publication for an invalid result.
5. **Destination transfer:** test permission denial, full destination, disconnect, cross-volume copy, existing target, interrupted transfer/retry, and read-back hash. Verify success follows adapter commit and destination validation, and record atomic visibility and durability separately.
6. **Aggregate admission and fairness:** queue long and short jobs with repeated large arrivals; add several individually in-limit memory/I/O-heavy jobs and sustained arrivals while editing is active. Verify aggregate admission respects the configured envelope or documented overcommit policy; measure editing responsiveness and queue wait; confirm aging does not starve long work. Numeric thresholds require owner-set targets and bounded service.
7. **Upgrade and preset:** save a preset against an exact build/schema; change the build, defaults, dependencies, and supported options; compare golden documents. Verify the old pinned build runs or the user reviews an explicit migration before execution, with no silent reinterpretation.
8. **Host policy matrix:** inspect cgroup controllers/delegation, Landlock ABI, Windows job flags/membership and AppContainer grants, and actual macOS helper/XPC entitlements and file handoff. Trigger CPU, memory, process, file, scratch, and network denials. Record controls as active, partial, or unavailable; exercise the owner-selected reject/degraded path. Do not infer one host's enforcement from another's.

## Optional improvements

Consider signed package metadata and content-addressed converter storage under the owner-selected admission policy; resource-event telemetry and bounded stderr; per-converter queue caps; destination-side staging with read-back hashes; format-specific safe validators; and an opt-in WASI adapter after a compatibility spike. These are optional design improvements, not settled product requirements.

## Owner decisions and remaining uncertainty

Choose package admission, signing and update policy; whether third-party WASI converters are in initial scope; supported OS/kernel/filesystem versions; minimum per-job and aggregate budgets; interactive reservation; concurrency, timeout, and cancellation grace; reject versus degraded behavior when a control is unavailable; and the queue service objective. Define supported destination types and their atomic-visibility/durability contracts, multi-file output schema and safe validators, preset migration and compatibility rules, and user-visible reporting of applied limits.

The evidence does not select a converter, runtime, numeric quota, compatibility range, or host policy. The XFS quota example is configuration-dependent. The XPC documentation supports a helper-isolation option but not arbitrary dynamic converter entitlements, hard resource limits, or per-export descendant teardown. Linux cgroup control requires host support and rights; Windows Job Object claims depend on membership and breakaway configuration; the reviewed macOS sources do not establish general per-converter hard resource limits. Keep these conditions attached to any implementation or user-facing guarantee.
