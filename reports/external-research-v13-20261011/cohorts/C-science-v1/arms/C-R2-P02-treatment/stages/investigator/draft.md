## Architecture recommendation

Keep UI/document state in a parent coordinator that owns immutable job records, a job queue and destination adapters. Launch a fresh supervised worker process for each third-party export rather than sharing one long-lived process across jobs. This adds process-start/IPC cost but gives each cancellation, failure, scratch directory and resource budget a clear owner. A plain subprocess under the editor's ordinary identity is not sufficient isolation. Give it a least-privilege view of one snapshot and one scratch directory, no broad home access, no ambient credentials, and no network unless the negotiated capability and user policy require it.

Use a versioned manifest/protocol pair. Static metadata is inspected first; a preflight handshake in an empty, restricted context confirms protocol version, input formats, output types/cardinality, preset schema, option requirements and resource needs. Unsupported requirements fail before document bytes and output handles are supplied. A versioned update may add capabilities but must not silently remove a preset's meaning.

The coordinator owns the state machine:

`queued → preflight → starting → running → cancelling (optional) → verifying → transferring → succeeded`

Terminal failures should distinguish unsupported capability, start/preflight failure, crash/nonzero exit, timeout, resource-limit event, cancellation, incomplete/invalid output, destination transfer failure and cleanup failure. Keep output staging inaccessible to the destination until verification. A multi-file converter must declare the exact output set or a manifest/sidecar policy. On local filesystems, stage on the target volume and use the documented platform commit primitive; for cross-volume or remote targets, stage and read-back-verify on the destination side. Report `succeeded` only after the selected adapter confirms transfer/commit. Expose atomic visibility and crash durability as separate adapter properties, not a universal promise.

For saved presets, retain exact converter/package version and digest, protocol/schema versions and canonical settings. On upgrade, either run the pinned version or stop for explicit migration/review. The Pandoc regression history is a concrete reason to test output semantics across upgrades rather than trusting compatibility ranges [S12–S14]. LibreOffice's own CLI separates extension, API filter name and parameters; an extension alone is not a stable capability identifier [S15].

## Isolation and host enforcement comparison

| Option | Useful guarantees | Limits and conditions | Disposition |
|---|---|---|---|
| Native process + OS policy | Separate address space and independent lifecycle. Linux cgroup v2 can bound CPU/memory/PIDs/I/O and kill a cgroup tree; Landlock can restrict filesystem/network rights. Windows Job Objects can govern process trees, CPU and committed-memory limits; AppContainer can restrict file/registry/network access. macOS App Sandbox restricts resource access and XPC is Apple's preferred privilege-separation technology. | Each control is conditional: Linux controllers/LSM must be built, enabled and delegated; Landlock ABI varies and inherited handles matter. Windows breakaway and some process-creation paths can escape a job. AppContainer and Job Objects solve different problems. Apple's reviewed App Sandbox docs do not specify a general per-converter resource quota; child inheritance lacks dynamic file grants [S02–S05, S09–S10, S19–S20]. | **Default for third-party native converters**, with per-host runtime detection and explicit degraded-mode policy. |
| WASM/WASI runtime | Language/runtime portability; explicit preopened directories and permissions; configured linear-memory limits and instruction fuel can constrain compatible guests [S06–S08]. | These controls are opt-in. Current Wasmtime 49.0.2 docs say linear-memory limit defaults to unlimited and fuel defaults off; WASI defaults to no preopens. A linear-memory cap is per guest memory, not host RSS; native libraries/host calls need additional limits. ABI/runtime and converter compatibility remain unknown. | **Optional adapter only; no runtime selected.** Use process/OS supervision as another layer. |
| Cooperative in-process API | Lowest IPC and copy overhead; straightforward trusted extension APIs. | A crash or memory corruption can affect the editor; a stuck callback blocks the host; cancellation and hard per-worker accounting are not independently enforceable. | **Trusted/first-party fallback only**, not the third-party safety boundary. |

A cgroup `memory.max` is a hard pressure/containment mechanism but invokes the OOM killer and can be exceeded temporarily; it is not a graceful converter error. Windows Job memory limits count committed virtual memory and only apply when their flags are active. A timeout is a coordinator decision and needs a reliable process-tree termination mechanism. Where the platform cannot provide a requested guarantee, show that limit as unavailable or reject the job according to owner policy; do not call an advisory setting enforcement [S02–S05].

## Fair admission and promotion policy

1. Reserve UI and editing headroom; do not place export IPC, conversion or destination copy work on the editor's interactive thread.
2. Apply a host-wide export concurrency ceiling plus per-job CPU, memory, process-count, scratch-size and elapsed-time budgets where the host enforces them. Do not infer a memory cap from a sandbox label.
3. Queue by age. A later large export may not leapfrog an older short export indefinitely. Use FIFO with aging or an explicitly tested weighted-fair queue; optionally cap active workers per converter so one extension cannot occupy every slot.
4. Bound one worker's runtime and output space. A worker occupying every slot forever defeats any queue policy, so enforce a timeout where possible and report platforms where teardown limits differ.
5. Measure queue delay separately from service time. Promotion to running requires successful preflight and a resource slot; promotion to success requires output verification plus destination confirmation.

Linux/Windows CPU weights can share active CPU, but neither kernel weights nor worker-count limits define the product queue order or guarantee a finite small-job wait. cgroup CPU weights are limited to eligible scheduler classes; Windows job CPU rate behavior is version/policy-dependent. I/O controls are device-specific and destination/network latency remains separate [S02, S05]. A concrete wait SLO, reserved slot count, and overload policy need owner decisions.

## Already covered, rejected, uncertain, and optional

**Already covered by the plan and retained:** declared capabilities before admission; immutable input and isolated scratch in concept; process boundary; bounded progress; cooperative then forced cancellation; preset identity/config; and five concrete witness classes. They need the stronger success gate and actual enforcement records above.

**Rejected as unsafe assumptions:** process exit plus status/path list proves successful output; immediate promotion is safe; a configured memory number is enforced on every host; a worker process is automatically a sandbox; a compatible version range preserves preset meaning; a cancellation result proves output/input integrity; worker concurrency alone guarantees editing responsiveness or fairness; and a same-volume replacement API makes all destination transfers atomic/durable.

**Optional design improvements:** signed package metadata and content-addressed converter storage; destination-side staging plus read-back hashes; a format-specific parser/validator; resource-event telemetry and bounded stderr; an opt-in WASI adapter; per-converter queue caps. These improve traceability or policy but depend on product constraints.

**Owner decisions / uncertain evidence:** plugin admission, signing and update channel; whether WASI/native converters are supported in the first release; minimum Linux/Windows/macOS versions and fail-closed versus degraded mode; numeric resource budgets and timeout/grace periods; destination types and atomicity/durability promises; multi-file output schema and semantic validators; exact compatibility-range/migration policy; queue SLOs and interactive reserve; and which limits are user-visible. No selected converter product or runtime is supported by this evidence, and the host's actual permissions/controllers are not known.
