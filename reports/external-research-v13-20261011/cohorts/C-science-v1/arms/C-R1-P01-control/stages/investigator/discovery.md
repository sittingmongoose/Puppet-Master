# Independent discovery — C-P01 reusable results grid

**Scope boundary.** This discovery was derived from the assigned brief only. The exact plan had not been released and was not sought or read. Research covers an editable multi-column intake grid, thousands of records, keyboard and assistive technology use, record/cell identity, filtering/sorting during edits, error recovery, and rendering alternatives. No application code, public example, or synthetic fixture was run; the work to date is source review and design analysis. Source identity and bounded observations are in [`sources/index.md`](sources/index.md) and [`source-map.json`](source-map.json).

## Findings that shape the design

1. **Use an interactive grid model when users navigate and edit cells.** WAI-ARIA APG distinguishes a static table from a composite grid: a grid reduces tab stops to one managed entry point, then requires explicit in-grid focus movement. It gives arrows, Home/End and Page keys for cell navigation; Enter/F2 enters edit/widget operation and Escape restores grid navigation. Arrow keys must be given back to text editing or controls while edit mode is active. A sortable/actionable header needs keyboard access and an announced sort state. This is web guidance; a native implementation should expose an equivalent platform table/grid and focus model. See [S01](sources/index.md#s01), [S02](sources/index.md#s02), [S06](sources/index.md#s06).

2. **Record identity, view position, focus, selection, edit draft, and error are separate state.** Use an immutable unique record key from the application data and a stable field/column key; never key any of these behaviors by current row index, rendered position, or a name that can repeat. MUI and AG Grid both use stable row IDs to track selection/updates; TanStack v8 defaults to index but documents overriding it, including selected IDs that persist outside the current page. Accessibility row/column indexes are *positions* (1-based in ARIA), not record identity. If only part of a web grid is mounted, expose an accurate total count and logical positions, or an unknown count where appropriate. See [S02](sources/index.md#s02), [S11](sources/index.md#s11), [S14](sources/index.md#s14), [S20](sources/index.md#s20), [S21](sources/index.md#s21).

3. **Keep keyboard focus visibly owned and logically anchored through reordering.** Store the active location as `(record_id, column_id)` and selection as a separate set of record IDs. After a sort, locate the same record and column in the new view and move/scroll focus there. Show focus and selected state with different visual treatments and programmatic states; a focused row is not automatically the selected record when the user can select independently. Keep the row label useful when names repeat (meaningful row-header context can use a second, distinct field); do not expose an internal ID as the only human-readable label. Long/truncated display text must not erase the full accessible name; missing values need an explicit text representation. APG and MUI document the distinct managed-focus, selected, row-header, and sort semantics; the choice of disambiguating fields is a product/data-owner decision. See [S01](sources/index.md#s01), [S02](sources/index.md#s02), [S13](sources/index.md#s13), [S19](sources/index.md#s19).

4. **Make editing survive the renderer.** Put the draft and dirty-field set in a model/store keyed by `(record_id, column_id)`, outside the virtual row/cell widget lifetime. Do not commit or discard merely because a filter, sort, refresh, or virtualization change removes/recreates a row widget. If a sort moves the still-visible row, restore focus by its stable ID. If a filter hides it, retain the draft and expose a keyboard-operable unsaved-edits queue/status with “return to record” and explicit save/discard; preserve the current filters and let users return after recovery. If an external update deletes or changes the record, retain the user draft and surface a conflict/reconciliation path rather than silently overwriting or dropping it. These are proposed product behaviors, not library guarantees. MUI's persistence API illustrates that failed save may intentionally leave the cell editing, while reverting to original values exits edit mode; its focus-loss issue was traced to a filter item's changing identity and fixed with a stable ID. See [S16](sources/index.md#s16), [S17](sources/index.md#s17), [S18](sources/index.md#s18).

5. **Make validation navigable by record and field, including after filtering.** Store errors as `(record_id, field_id, code/message)` and keep a durable issue list in addition to an inline field error. A validation summary should name a human-meaningful record disambiguator and field, state the problem in text, and offer a keyboard action that reveals the row (temporarily override the filter or open a dedicated issue view), scrolls to it, and focuses the offending cell/editor. Provide next/previous issue and a return-to-results action. The error must remain identifiable when the row is not in the visible result set. WAI's WCAG explanation explicitly calls for identifying the item in error and allows summary or inline presentations. A concise polite status can report meaningful outcomes such as “18 results” or “3 records need attention”; do not announce every background row update. See [S03](sources/index.md#s03), [S04](sources/index.md#s04), [S05](sources/index.md#s05).

6. **Virtualization is a rendering choice with an accessibility contract, not a small-dataset cap.** For a web grid, WAI-ARIA supports partial DOMs through row/column count and position metadata; APG warns that an end-navigation command can reach the last loaded row, not the full dataset. AG Grid 36.2.0 advises pagination or disabling virtualization when screen readers need all cells in DOM order, at a memory/render cost. MUI X v8 documents a bounded virtual row window and says horizontal overscan needs at least one next column for arrow navigation; MUI's current accessibility docs retain a row-header cell while horizontally virtualizing its column. Windows UI Automation has a VirtualizedItem/Realize contract, while AppKit and AT-SPI expose table/row/selection concepts with different APIs. These sources show both that virtualization can be given semantics and that toolkit/AT behavior cannot be inferred from semantics alone. See [S02](sources/index.md#s02), [S06](sources/index.md#s06), [S07](sources/index.md#s07), [S08](sources/index.md#s08), [S09](sources/index.md#s09), [S10](sources/index.md#s10), [S13](sources/index.md#s13), [S15](sources/index.md#s15).

## Candidate rendering / data approaches

- **Paged semantic grid/table (recommended baseline to measure):** query, sort and filter over the full dataset, but render the current page as real accessible row/cell controls; expose total/result count and usable page navigation. Page size is a measured choice, not a maximum on total data. This can reduce tree size without pretending every row is mounted. It also simplifies sequential AT review. The tradeoff is more page transitions and a need to preserve selected IDs, focus anchors and edit drafts across pages. AG Grid explicitly offers pagination as the route to rendering all rows on a page for screen-reader review. [S10](sources/index.md#s10), [S21](sources/index.md#s21)
- **Windowed row/column rendering with full semantic navigation:** keep a viewport plus measured overscan; map logical navigation to stable IDs; expose true row/column totals/indexes or native virtualization patterns; realize/scroll an offscreen target before transferring focus. Keep row identity, focus, selection, drafts and errors independent of widgets. This offers continuous scrolling and bounded rendering but needs AT checks for offscreen discovery, last-row navigation, row headers, rapid scrolling and focus restoration. [S02](sources/index.md#s02), [S07](sources/index.md#s07), [S10](sources/index.md#s10), [S15](sources/index.md#s15)
- **Headless row model plus separately owned virtualizer:** TanStack Table separates row/sort/filter state from the scroll-index/measurement layer. This gives flexibility to build a native-specific renderer, but the application must implement focus, editor, selection, row/cell semantics and validation integration. It is a useful architecture reference, not a direct desktop component choice. [S20](sources/index.md#s20), [S21](sources/index.md#s21)
- **Load-everything nonvirtualized grid:** simplest DOM/visible-tree interpretation for truly small sets, but the brief already anticipates thousands and the vendor source warns of memory/render cost. Do not use this as the only accessibility route for a result set that then becomes too slow. A paged full-page view is a safer alternative. [S10](sources/index.md#s10)
- **Server-side query/pagination plus client-side viewport virtualization:** data retrieval and rendering are separable. If all records cannot be loaded, filtering and sorting must cover the backend result set; the current page/window is not the entire dataset. Unknown total count needs an explicit navigation/continuation model and an accurate “unknown” accessibility count where the platform supports it. [S02](sources/index.md#s02), [S20](sources/index.md#s20)

## Implementation boundaries and decisions still open

Keep the row/column model, stable record IDs, edit/validation store, focus anchor, and selection set independent from any viewport renderer. The renderer owns cell widgets, visible geometry, keyboard-to-logical-navigation mapping, and the platform accessibility tree. Persistence owns save, conflict, and external-update behavior. Validation owns field rules and issue messages, while the grid supplies a route to each issue. Do not select a web library solely from these references: AG Grid/MUI/TanStack are React/web implementations and do not prove compatibility with an unspecified native toolkit.

Owner decisions still needed after the plan is released: supported OS/toolkit; target screen-reader combinations; whether sorting/filtering can execute server-side; product identity/disambiguation fields; whether selection is independent multi-select or follows focus; save/conflict semantics; target row/column scale and performance budget; paging versus continuous-scroll default; and any legally required conformance target. For Windows, verify UIA Grid/Table/Selection plus virtual realization; for macOS verify NSAccessibility row/column/visible/selected information with VoiceOver; for Linux verify AT-SPI row count/header/selection with Orca. Measure empty/missing and duplicate names, long labels, errors hidden by filters, external updates during editing, sorting the active row, page/window transitions, and at least one high-speed scroll case.

## Failure history and evidentiary limits

MUI issue #8119 records focus being lost from a filter field when new rows arrived; the maintainer traced it to a placeholder filter item's ID changing on rerender, and PR #8603 merged a stable-ID fix (commit `474cf13`). This is a focused example that data updates can reset focus when transient UI identity is unstable; it is not proof that the same library problem persists or that it covers edits hidden by filters. [S17](sources/index.md#s17), [S18](sources/index.md#s18)

MUI issue #4124 reports sortable headers not being discoverable/announced in one JAWS/Windows screen-reader/browser check. The issue remains displayed as open in the reviewed source and contains no demonstrated linked fix; its reporter limits evidence to one combination. Treat it as a test risk, not a statement about current general behavior. Current MUI accessibility documentation describes keyboard focus/tab management and row headers but does not, in the passages reviewed, close that exact sort-announcement question. [S13](sources/index.md#s13), [S19](sources/index.md#s19)

## Validation status

**Actually performed:** reviewed the listed W3C, OS-platform, maintained-library and repository issue/PR sources at the recorded access UTC. No examples, app, device, screen reader, benchmark, or synthetic fixture were run.

**Proposed for the future console:** (a) keyboard-only end-to-end for enter grid, traverse, sort, edit, save/cancel, select/deselect, filter, navigate pages/virtual window, recover hidden draft and navigate error; (b) platform accessibility-tree inspection of names, roles, row/column headers/count/index, selection, focus, editable/readonly and error state; (c) screen-reader review with the supported AT/OS matrix for missing/duplicate/long values, sortable headers, row identity, hidden-error recovery and status throttling; (d) scripted state tests that reorder/update/filter rows while verifying drafts, selection, focus IDs and errors do not drift; (e) performance tests at agreed result sizes, column widths, row-height variance and rapid scrolling on minimum supported hardware. These are proposals, not executed checks.
