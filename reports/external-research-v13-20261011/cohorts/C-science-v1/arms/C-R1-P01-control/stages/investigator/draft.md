## Proposed design and implementation boundaries

### State model

- **Data/query layer:** canonical record IDs; stable column/field IDs; filtering, sorting, pagination/server query, current result count and revisions. View row index changes with query state and must never become identity.
- **Grid controller:** active `(record_id, field_id)`, navigation/editor mode, scroll/realize request, and page/window coordinates. The controller owns keyboard behavior. The renderer owns actual widget focus after the target is mounted.
- **Selection model:** stable record-ID set, independent from active focus. Sorting/filtering/virtualization preserve selected IDs and communicate selected count. Focus and selection have visually distinct treatments and distinct accessibility state.
- **Edit coordinator:** unsaved values and dirty fields keyed by record and field, base version, status (`editing`, `hidden by filter`, `validation failed`, `conflict`, `saved`, `discarded`). It outlives row/cell widgets. Saving and discarding are explicit; hiding a row is neither.
- **Validation/recovery model:** issues keyed by record and field; text and correction; recovery-list action; return-to-query state. A recovery list item is not a clone of a grid row.
- **Renderer/accessibility adapter:** choose native table/grid controls where possible. For web, use APG grid semantics and partial-DOM counts/indexes. For native implementations, expose the appropriate platform table/grid, row/column headers, focus, selection, scroll/realize and status APIs. The renderer must not present an index as record identity or make every background refresh a live announcement.

### Keyboard and recovery behavior

Enter the grid with one predictable Tab stop; use arrows/Home/End/Page keys for navigation and clear instructions discoverable without a pointer. Enter or F2 moves from navigation into an editor; the text field owns arrows and editing caret until commit/cancel. Escape cancels the active draft or closes an editor without silently committing. Tab/Shift+Tab behavior within editors and at grid boundaries must be consistent and tested. Every sort/filter, selection, edit, validation-summary activation, recovery, save, and discard action must be possible by keyboard. Keep visible focus and announce record/column context at useful boundaries; avoid announcing every movement if it is noisy, but test the actual AT pattern.

If a filter removes the edited record, preserve its draft and place a status/action in the recovery list. Keep the filter control focused when the user is still editing the filter; make the recovery entry reachable by ordinary Tab/keyboard navigation. “Return to record” restores the actual row through a temporary reveal or dedicated edit-recovery view and returns focus to the edited field. A validation error on a filtered-out record follows the same path, with error identity and next/previous issue controls. If an external update deletes the record, retain the draft until the user chooses a defined resolution; describe that the underlying record disappeared. Do not silently place focus in the adjacent row.

### Rendering comparison

| Approach | Strengths for this brief | Accessibility and state risks | Proposed use |
|---|---|---|---|
| Paged semantic grid/table, with full current page rendered | Predictable row order and result orientation; lower view-tree cost than mounting all records; accessible route across thousands via search/sort/page controls | More page transitions; cross-page selection/focus/draft retention must use IDs; backend sorting/filtering must cover the full result set | Baseline and fallback to measure. Page size is tuned, not a product record limit. |
| Windowed row/column grid | Bounded rendering and continuous scrolling; suitable for long lists and/or many columns | Unmounted rows may be absent to AT; logical indexes do not by themselves guarantee discovery; overscan, screen-reader headers, high-speed scroll, focus realization and last-row commands vary by implementation | Keep as the leading candidate only if it passes per-platform navigation/recovery checks; otherwise use paging as the accessible route. |
| Headless row model plus independent virtualizer | Separates filtering/sorting from viewport and lets a native toolkit own the presentation | Transfers focus, editor, semantics, selection and error integration to the application | Architectural alternative if existing native control cannot meet requirements; scope its accessibility adapter explicitly. |
| Mount every record without virtualization | Straightforward sequential DOM/tree access on genuinely modest sets | High memory and rendering cost for thousands; full mount may violate responsiveness | Do not use as the only mode at large scale; consider only within a measured page. |
| Server query/pagination plus client viewport virtualization | Handles data too large for client and separately bounds view size | Must preserve true counts/unknown-count behavior, backend search, stable IDs, page/window state and issue navigation | Compatible data-loading layer for either of the first two render strategies. |

These approaches are evidence references, not a library selection. AG Grid is a maintained, integrated web grid; MUI X is a maintained React grid with explicit focus, row-ID and editing APIs; TanStack Table is a headless model with separate virtualization. None is directly established as a fit for an unspecified native desktop toolkit. [S10–S16, S20–S21]

## Targeted validation plan (proposed, not run)

1. **Focus after deletion:** put keyboard focus in an editable cell, create a dirty draft, then deliver an external update deleting that record. Expect the draft to remain recoverable, a clear record-unavailable/conflict status, focus on a deliberate recovery/status control, and no focus or typing target silently switched to the next row. Repeat with a filter that merely hides the row; expect a distinct “hidden by filter” state and a working return action.
2. **Editing during sort:** edit a row, invoke keyboard sort on another column, and verify the same record/field remains the logical focus and retains draft text after reorder. Repeat when the edited field is itself the sort key and when a background update arrives. Verify explicit commit/cancel, sort indicator announcement, and selection persistence by record ID.
3. **Error-summary return:** cause validation errors on at least two rows, filter one out, focus the issue summary using keyboard, activate its item, and verify that the correct real row/cell is revealed and focused, the field name and message are conveyed, the draft is preserved, and the previous query can be restored after correction.
4. **Long, missing, and duplicate-looking labels:** inspect visual rendering and accessible names with long/truncated names, empty names/fields, and duplicate names. Verify full meaningful label context, explicit missing-value text, row disambiguation by approved secondary data, and no reliance on color or row index alone.
5. **Focus versus selection:** move focus across a selected row, select/deselect by keyboard, and filter/sort/page while selection persists. Verify focus and selection remain separately perceivable and exposed; range or select-all status is concise.
6. **Window semantics and navigation:** inspect table/grid accessibility tree at top/middle/end and during rapid scroll; test arrows, Page Up/Down, Home/End, first/last dataset navigation, offscreen record retrieval, row/column headers and focus restoration after rows recycle. Compare against a paged implementation using the same dataset.
7. **Performance:** on minimum supported hardware, benchmark agreed p50/p95 key-response latency, scroll frame latency, memory and query time at representative and stress-scale row/column counts with long variable-height content. Repeat with accessibility tooling active; choose row page/window size and overscan based on data, not a hard-coded tiny total record cap.

**Platform matrix to choose before acceptance:** Windows UIA with supported NVDA/JAWS versions; macOS VoiceOver with the chosen accessibility provider; Linux AT-SPI with Orca if Linux is supported. The app owner must name supported OS/toolkit/AT combinations and conformance obligations. Check native accessibility-tree contents as well as speech output; a web ARIA declaration or a successful visual check alone is not an acceptance result. [S03, S06–S09, S19]

## Unresolved owner decisions

- Supported OS/toolkit and screen-reader matrix, and legal/accessibility target.
- The data-backed record key and approved secondary fields for differentiating duplicate labels without disclosing inappropriate information.
- Selection model, including whether range/multiple selection is needed independently of focus.
- Save/validation/conflict policy and how deleted records' drafts can be resolved.
- Server-side versus client-side filtering/sorting and whether the total row count is always known.
- Target data/column sizes and latency/memory budget; page size and overscan after measuring.
- Whether continuous scroll is essential or a paged primary path is acceptable after testing with users.
