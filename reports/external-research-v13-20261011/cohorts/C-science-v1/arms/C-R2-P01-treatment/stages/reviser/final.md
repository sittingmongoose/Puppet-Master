# C-P03 — Complete research-backed import proposal

Stage: reviser, run C-R2-P01-treatment. This proposal answers the original software-planning brief and disposes every clause in the released plan. The source index is [sources/README.md](sources/README.md); identity and direct-check records are in [source-map.json](source-map.json). Existing source IDs S01–S21 retain their assigned identity. No parser or database is selected.

## Proposed outcome

Build a local import flow with four visible stages: configure a profile, stream and stage, review a complete diff, then apply the accepted choices atomically. Retain raw input and provenance throughout. Detection can suggest dialect or interpretation candidates, but a confirmed profile and explicit owner rules determine meaning. Parse and validate through EOF before accepted observations change. Preview is paged and identifies additions, replay, unchanged rows, revisions, ambiguous matches, invalid rows, omissions and conversions. The user selects whether accepted data is supplemented, revised within a named scope, or left intact. Preserve prior accepted values and lineage. A failure or cancellation before commit must not leave a partially accepted batch.

Do not rewrite the source file, upload observations, silently coerce values, treat filenames as identity, or choose a winning library in advance. Rust csv and DuckDB remain parser candidates; SQLite and DuckDB remain local storage/transaction candidates. Compare pinned builds, packaging, workload, performance, recovery and supported platforms before selection [S01](sources/README.md#s01), [S02](sources/README.md#s02), [S06](sources/README.md#s06), [S10](sources/README.md#s10), [S11](sources/README.md#s11), [S12](sources/README.md#s12).

## Profile, parsing and interpretation

CSV files do not identify their own dialect or semantics. RFC 4180 is an informational common profile, not a logger contract; W3C CSVW offers useful vocabulary for dialect, headers, types and null markers, while its empty-string default is not evidence about a particular logger [S04](sources/README.md#s04), [S05](sources/README.md#s05). Show candidate delimiter, quoting/escape, encoding, header status, column roles, date formats, null markers and unit labels, together with why each was suggested and how much input was examined. Include later-file examples in review. Users may instead select a profile without inference. A saved logger profile may prefill choices, but changes create a new profile revision bound to the import.

DuckDB documents 20,480 rows as the default type-inference sample and sample_size=-1 as reading the entire file for sampling; seekable files may be sampled at several locations, while compressed or other non-seekable input is sampled from the beginning. The documentation distinguishes sniffing from a later configured read [S06](sources/README.md#s06). Therefore neither default nor whole-file sampling validates all rows against confirmed meaning. Keep a separate EOF pass. DuckDB's documented faulty-file options include stop-on-error by default and optional skip/reject behavior, plus a finite default maximum line size; a skip path cannot silently become a complete accepted import [S07](sources/README.md#s07). Historical reports S08–S09 are regression-test prompts for specific paths and versions, not claims that current builds share those defects. Pin the exact parser build and options.

Preserve raw bytes/cell strings before decoding or converting. Rust csv provides reusable one-record reads and source positions; its StringRecord path requires UTF-8 while byte-record APIs permit retaining undecoded bytes. Header and flexible-row settings are explicit, not heuristically safe defaults [S01](sources/README.md#s01), [S02](sources/README.md#s02), [S03](sources/README.md#s03). Successful parser output alone does not establish intended meaning: a maintainer discussion describes malformed whitespace/quoting that the parser attempted to salvage [S20](sources/README.md#s20). Preserve logical record and byte locator, raw row, parser/version, dialect and error details. Because quoted cells may contain newlines, physical line number is not a reliable observation key.

Confirm per-column rules for numeric grammar as well as units: decimal and grouping separators, accepted signs/exponents, whitespace, identifier-versus-measurement role, integer range, overflow/non-finite handling, precision and rounding. Keep identifiers such as logger IDs as text absent a domain contract. Preserve the raw numeric text and show any normalized value and formula. Unit conversion is a later, separate step after both number parsing and quantity/unit mapping are confirmed. These are profile fields and owner inputs; no listed source establishes that a particular logger uses a locale or numeric convention.

Check every row through EOF for structure, decoding, configured date/number grammar, null rule and unit compatibility. A blank, configured missing marker, invalid value and numeric sentinel stay distinct. Never infer that empty, NA, N/A, -9999 or zero means missing without a column-specific rule. A contradiction invalidates the preview and points to affected records; the volunteer can revise the profile and rerun, but no fallback silently changes accepted meaning.

## Overlap, missing rows and revisions

Logger ID plus timestamp is not a universal identity: coarse clocks, repeated measurements, multiple properties/depths, clock changes and corrected metadata can collide. Row position changes when rows are reordered. OGC SensorThings provides a useful candidate vocabulary—event time, feature of interest, observed property and procedure/sensor—but is not a guarantee that a logger exposes these fields [S18](sources/README.md#s18).

Compare these approaches and show their limits:

1. **Stable event ID scoped to instrument/deployment.** Strong for a changed result only if the logger contract establishes stability and uniqueness. Missing, reused or reset IDs disqualify the key; surface collision counts.
2. **Semantic composite key.** Candidate fields include site/feature, sensor/deployment, property, event instant or interval, and applicable depth, location, method or sample context. Keep result value out so a change can be reviewed as a revision. Missing context, ambiguous time and legitimate simultaneous readings can collide.
3. **Exact-content fingerprints.** A digest of source bytes detects byte-identical file re-import; a canonical observation fingerprint can identify equal content under a documented normalization. Neither identifies a changed-value correction. Equal observations can represent distinct events, and a changed whole-file digest says nothing about which rows changed.
4. **Tolerance-based candidate search.** After explicit site, property, zone and unit mappings, rank nearby times with relevant depth/location/method context. This can surface rounded clocks or resampled rows but is not identity; close genuine readings can be false matches. Require user action.

Keep outcomes distinct: byte-identical replay, same-key/same-result, same-key/changed-result revision candidate, close-time candidate, collision/ambiguity, and new observation. Exact replay may be omitted from the active view while its import batch remains in lineage. A changed result does not automatically replace an accepted one. Let the volunteer keep both, append a proposed revision, or leave prior data intact. Any active-view replacement must name scope and target version while retaining historical rows.

A separate completeness rule is required for rows absent from a later file. **Default meaning: “not present in this file”; absence never deletes or deactivates an accepted observation.** A profile may declare an input append-only, partial/overlapping, or a complete snapshot, and a snapshot must include explicit scope such as deployment and time/interval bounds. Only a user-confirmed complete snapshot with matching declared scope may produce “no longer present” candidates. Preview lists prior rows, affected source/batch lineage and the exact scope; the user must explicitly approve an auditable active-view or revision decision. Truncation, unknown completeness or scope mismatch cannot imply removals. A same-name file with a changed digest is a new source version to diff. These are policy choices, not claims about any logger convention.

Preserve original timestamp text, format and zone. RFC 3339 full date-times carry Z or numeric offsets; a local time without offset does not identify an instant, and -00:00 denotes an unknown local offset [S19](sources/README.md#s19). Obtain a source timezone or leave wall time unresolved. A named zone may resolve to Chrono Single, Ambiguous (fold) or None (gap); do not silently select an offset [S16](sources/README.md#s16). For units, retain exact token and quantity context. UCUM 2.2 has case-sensitive symbols and conversions that may be functions; it does not establish that an unknown logger label is UCUM or that measurements share a quantity [S17](sources/README.md#s17). Only map confirmed compatible quantities, recording source/target unit, formula and mapping revision; otherwise block that interpretation from commit.

## Stage, preview, apply, cancellation and recovery

Stream logical records into local disk-backed staging while hashing the source. Store source digest, visible filename/size, parser release, dialect/encoding, profile hash, record/byte counts and stage state. Each staged row retains raw cells, locator, parse status, warnings, confirmed normalized fields only, and match candidates. Bound buffers, preview aggregation and displayed rows; page details from staging and report progress and disk use. Disk staging controls memory only if the entire path is bounded. A file larger than memory is a target to measure, not a proved performance claim.

Staged rows are not accepted observations and do not appear in normal notebook queries. Read and validate to EOF before apply. A malformed late row marks the batch invalid with no accepted-state change. Preview reports counts and paged evidence for additions, replay, unchanged rows, revision candidates, ambiguous overlap, missing rows from a claimed complete snapshot, invalid rows, configured missing markers and conversions. Show old/new raw and interpreted values, affected earlier batch, source lineage and proposed action. Recheck the source digest and database generation before apply; if either changed after preview, require a new diff and decision. Never rewrite or upload source bytes.

For SQLite, put the import-batch record, accepted versions, lineage and active-view choice promised as atomic in the same database file and one outer transaction. A staging store may be separate while its content is still unaccepted. SQLite allows one simultaneous writer; keep parsing/preview outside the write transaction and define lock/busy behavior [S12](sources/README.md#s12). Savepoint release does not commit an inner batch independently [S13](sources/README.md#s13). Avoid FAIL, IGNORE and REPLACE for accepted import rows: FAIL may retain earlier changes in the failing statement, IGNORE skips rows, and REPLACE deletes conflicting rows. Also, default ABORT backs out the failing statement but preserves prior successful statements in the still-active transaction. Therefore an apply error or cancel must be caught and the outer transaction explicitly rolled back; verify the terminal transaction state before reporting cancellation/failure [S14](sources/README.md#s14). Use explicit constraints/conflict targets and append revision events rather than overwriting history.

A COMMIT returning SQLITE_BUSY may leave the transaction active. Define a bounded retry policy or explicitly roll back, and report success, failure or cancellation only after commit or rollback is confirmed. Before opening the write transaction, compare the preview's database generation; if stale, recompute the diff and obtain any changed decision. Do not retry a stale user decision as though the preview were current [S12](sources/README.md#s12).

DuckDB remains a valid alternative with documented transactions and rollback behavior, but concurrent updates can conflict and require retry; compare on the target local desktop workload and preserve the same decision-generation rule [S10](sources/README.md#s10), [S11](sources/README.md#s11). If SQLite WAL is selected, pin a fixed SQLite build: official history says the reset defect affects WAL through 3.51.2 and is fixed in 3.51.3+, with backports 3.44.6 and 3.50.7. The reported race requires WAL, at least two connections to the same file and coincident write/checkpoint activity. This is a WAL-specific qualification, not a general SQLite minimum or a reason to reject rollback-journal mode. WAL transactions across ATTACHed databases are not atomic across the set, so keep all accepted data and provenance covered by the atomicity promise in one database file [S15](sources/README.md#s15). The official atomic-commit article specifically describes rollback-journal mode and states its storage/OS assumptions; WAL uses a different mechanism. Name and test the shipped engine build, journal mode, synchronous setting, filesystem and supported platform combination before promising crash/power-loss behavior [S21](sources/README.md#s21).

Before apply, cancellation discards or marks unaccepted staging for later cleanup and never alters accepted data. During apply, cancellation requests outer rollback and waits for confirmed terminal state. After commit, cancellation cannot erase history; a later explicit revision/compensation is needed. Restart-from-zero is the safe baseline for interrupted parsing. Optional resumable checkpoints need matching source digest, parser build, profile hash, verified record boundary and staging checksum; any mismatch restarts at byte zero. After interrupted apply, retry from verified staging only when database transaction outcome and staging integrity are known; otherwise re-parse. Expiry, quota and a recovery screen prevent stale staging from being silently imported or lost. A whole-file transaction may hold the sole writer and consume journal/WAL space; chunk commits shorten the write window but violate all-or-nothing and require an explicit owner decision.

## Lineage and user decisions

Keep at least these conceptual records (not a schema mandate):

- **Source version:** content digest, display name, size and scan time. Digest identifies bytes; filename does not.
- **Import batch:** local ID, source version, parser/library release, detected and selected settings, profile revision/hash, status, preview generation, user decision and commit/abort result.
- **Staged row:** batch, logical record/byte locator, raw row/cells, parse status, raw timestamp/value/unit, confirmed interpretation, warning and match links.
- **Observation revision/event:** prior and candidate versions, source row/batch, exact user decision and reason, and active-view status. Retain raw and normalized values and interpretation metadata.
- **Profile revision:** header mapping, encoding/dialect, numeric grammar, date/timezone rules, per-column missing markers, unit formulas and identity/completeness policy. Editing creates a new revision and rerun.

Resolve with product owners: logger families and stable-ID reuse rules; site/sensor/deployment/property and event context; append/partial/snapshot contract and snapshot scope; date formats, timezone, DST/clock reset; numeric grammar and precision; units and conversions; exact blank/sentinel markers; whether explicitly listed invalid rows may be omitted; ambiguous-match default; whether replace means only a scoped active-view switch; file/record/disk limits and performance/cancel targets; parser/database versions, encodings, durability policy and platform/filesystem support; and whether verified scan resume belongs in the first release. Safe defaults pending answers are preserve raw and prior values, do not infer missingness or conversions, and require review for unresolved matches or completeness.

Optional improvements are saved logger profiles with change warnings, preview filters for invalid/changed/overlap/missing rows, verified scan checkpoints, and a multi-file queue with a separate preview and decision per source.
