# Independent discovery — C-P03 import component

Stage: investigator, run C-R2-P01-treatment. This discovery is based only on the assigned brief and primary documentation/issues listed in source-map.json. The released plan has not been read. Accessed source pages on 2026-10-12 UTC; source-specific times and locators are in the map.

## Design space (no library selected)

A constrained Rust CSV reader and DuckDB's CSV reader are credible parser alternatives. The Rust csv 1.4.0 ReaderBuilder supports explicit dialect options; headers are on by default, and unequal record lengths error by default unless flexible parsing is enabled [S01]. Its reusable read_record/read_byte_record calls stream one record at a time, reuse the record allocation and retain a source position on success or error; StringRecord requires UTF-8, while ByteRecord handles arbitrary bytes for explicit decoding [S02]. The crate has no header heuristic: an incorrect default can consume the first data row [S01]. Maintainer guidance shows it may salvage malformed whitespace/quoting into an unintended parse rather than reject the file [S20]. Therefore parser success is not equivalent to validated interpretation. Keep the original record and location; test the chosen dialect against malformed late rows and schema invariants.

DuckDB offers a second maintained in-process parser and an analytical storage alternative. Its current sniffer tries comma, pipe, semicolon or tab, and quote/escape candidates against samples; type inference samples 20,480 rows by default, with sample_size=-1 to inspect the whole file and all_varchar to disable inference [S06]. A user can inspect the generated settings then pin them instead of relying on re-sniffing. DuckDB documents structural and cast errors, immediate failure by default, and optional skip/store-reject behavior; line length defaults to 2,097,152 bytes [S07]. Skipping rows is incompatible with a silent all-or-nothing default. Test the exact release and options selected; rolling docs and old issue reports do not establish present behavior. Reported cases include sampled type/date surprises [S08] and a 0.10.1-versus-0.10.3 CSV behavior change for a StringIO/encoding path, later closed through PR #13597 [S09]. The exact first fixed release was not established from that issue. These are regression-test prompts, not evidence that current builds have the same defects.

RFC 4180 is an informational common CSV profile, not a universal logger contract: it describes comma-separated fields, optional headers, quoting and equal-width rows, while acknowledging implementation variation [S04]. W3C CSVW metadata provides a useful profile shape for dialect, headers, column titles/types and null markers; its default null marker is empty text, and metadata can itself misinterpret columns, so any supplied/inferred profile must be visible and reviewed [S05]. Do not adopt the empty-string convention, a special token such as NA/-9999, a locale date order or an encoding for a logger without evidence or user confirmation.

## Interpretation and overlap

Keep raw bytes/cell strings before interpreting them. Offer candidates for delimiter, encoding, header, column roles, date format, unit and missing tokens; show why each was suggested and let the volunteer correct it. Bind the confirmed, versioned profile to this import. Check every row through EOF, not only a sample; report extra/missing fields, decoding failures, inconsistent date/number formats and conversion failures with logical record and byte location. Unknown extra columns remain reviewable. An empty field, an explicit missing marker and a numeric sentinel remain distinct until configured per column. Preserve raw and interpreted forms.

For timestamps with an explicit numeric offset or Z, normalize only after retaining the original text and format/profile. RFC 3339 uses a full date-time with an offset, warns that unqualified local times are not interoperable, and says numeric offsets express local time minus UTC [S19]. A naive wall time is not an instant: request a source timezone/profile or leave it unresolved. With a named zone, surface Chrono's distinct Single, Ambiguous-fold (two candidate instants) and None-gap results; never pick earliest/latest silently [S16]. Date strings such as 03/04/25 remain ambiguous until the source format is set.

Retain exact unit text and quantity context. UCUM v2.2 supplies a formal machine-readable unit code system and canonical relationships, including case-sensitive symbols and conversions that may be functions rather than multiplication by a scalar [S17]. It does not prove an unknown logger label is UCUM or that two columns measure the same quantity. Normalize only a recognized compatible quantity under a confirmed mapping; record formula, source/target units and mapping version; preserve the source value. Unknown, changed or dimensionally incompatible units are review cases, not guessed conversions.

Compare these overlap strategies explicitly:
1. A documented stable logger/event identifier scoped by sensor/deployment. It can identify a corrected row even if its value changes, but only if IDs are present, stable and not reused; otherwise it is not a key.
2. A semantic key independent of the result value: station/feature, sensor or deployment, observed property, event instant or sampling interval, and where available depth/location/method. This can identify a changed result as a revision candidate, but missing context, ambiguous time or duplicate observations can make it collide. OGC SensorThings 1.1 classifies an observation using event time, FeatureOfInterest, ObservedProperty and procedure/sensor, a useful candidate vocabulary rather than a logger guarantee [S18].
3. A normalized-content fingerprint can recognize exact repeated observations across files, but a correction changes the fingerprint and distinct real observations can have identical values/timestamps. A full-file SHA-256 identifies a byte-identical re-import only; filenames and row numbers do not identify data versions or observations.
4. Optional tolerance-based similarity (station/property plus configured time window and depth/location, comparing units only after explicit conversion) should produce ranked candidates for human review, never an automatic merge. Window width, site identity and the meaning of concurrent readings are owner decisions.

Never use the numeric result alone in an identity key. Show candidates as unchanged/replay, possible correction on an established key, exact-content candidate, possible overlap, or new/ambiguous. Keep colliding rows and previous accepted values until a user selects an action. A new file with an old name but different digest is a new source version; filename alone cannot replace history.

## Transaction, preview and lineage proposal

Use a disk-backed staging area so parsing, conversion and full-file validation are incremental and memory does not grow with row count. Compute source digest while streaming. Record parser/version and exact dialect; profile hash/version; logical record number, parser byte position, headers and raw row; raw timestamp/value/unit; normalized value/time if confirmed; source batch ID; and explicit match/revision/action links. Verify the staged source digest still matches the selected file before applying. Do not edit the source or send it to any service.

Build preview pages from staging with counts for added, byte-identical replay, same-key unchanged, revision candidates, ambiguous overlaps, invalid rows, missing markers and conversions; allow paging through row details. Preview must say whether a previous import remains, is supplemented, or which rows would be revised, including the old/new raw and interpreted values and evidence. Corrections to an interpretation create a new profile revision and rerun; they do not rewrite source text or the earlier accepted import.

Apply only after a complete EOF pass and explicit review. For SQLite, apply the accepted batch, import-batch record, lineage and active-version updates inside one outer transaction; commit only after every row and provenance record succeeds. A late parse/validation error happens before apply; an apply error or cancel rolls back the whole outer transaction. Savepoints do not independently commit when nested [S13]. SQLite permits one writer at a time, so keep parsing and preview outside the write transaction and define busy/retry behavior [S12]. Avoid INSERT OR REPLACE because it deletes conflicting rows; avoid FAIL and IGNORE because FAIL can retain earlier row changes in a failing statement and IGNORE skips violating rows [S14]. Use explicit conflict targets and append a revision event instead of overwriting accepted measurements. If using WAL, require a fixed SQLite release containing the reset-bug repair (3.51.3 or later) and test concurrency; the documented defect required two connections writing/checkpointing concurrently [S15]. DuckDB also supports ACID begin/commit/rollback and rollback of prior statements when a multi-statement batch fails [S10], but has optimistic conflicts on concurrent row updates [S11]. Compare both using actual expected batch size, query workload, embedded distribution, recovery and lineage needs before selecting.

Cancellation before apply discards/relabels only unaccepted staging. Cancellation during apply rolls back all writes; after commit, correction is a later auditable revision, not destructive deletion. Process/crash, disk-full, corrupt database and power-loss behavior need dedicated tests. If the application offers a policy to omit bad rows, each omission must be shown and separately confirmed; never call it a complete import. Long imports need byte/row progress, bounded buffers/batches, a cancel path, and visible staging disk usage. One all-or-nothing transaction may hold the sole writer longer than desired; chunk commits would break the guarantee and require an explicit product decision.

## Unresolved owner inputs and checks

Logger-specific conventions remain unknown: stable record IDs, station/sensor/deployment mapping, timestamp zone and format, interval versus instant, measurement/property vocabulary, unit labels and changes, missing markers/sentinels, encoding, dialect, comments/preambles, duplicate row legitimacy, and corrections to an existing time. Also unresolved: whether preview allows per-row omission; default outcome when an overlap is ambiguous; revision vs supplement vs explicitly scoped replacement policy; data retention/active-view meaning; maximum input size/line length, disk budget, responsiveness target, transaction/busy threshold, SQLite vs DuckDB, and supported package versions. Default safe behavior pending those decisions is preserve raw and prior accepted values, reject unresolved conversion for commit, and request a decision instead of choosing.

Proposed validations (not executed): parser contract tests for headers/no header, comma/tab/semicolon/pipe, quoted delimiter/newline, BOM/UTF-8/selected alternate encoding, unequal widths, malformed quote, and a malformed final row after valid rows; verify failed import leaves database checksum/row counts and lineage unchanged. Test conflicting explicit profile and late value type, all configured missing markers versus non-markers, date-order ambiguity, DST fold/gap, changed compatible units, incompatible/unknown units, and exact replay versus same-key changed result versus near-time readings. Test multi-file replay/reorder, same filename with changed digest, empty and truncated files, duplicate keys/identical rows. Stress bounded memory above RAM, maximum line and disk, cancellation during stage and transaction, pause/restart/re-preview against changed source and changed database generation, process interruption/crash, full disk, constraint failure, corrupt storage, WAL/checkpoint concurrency on the pinned engine, and UI progress/error location. Nothing in this assignment has been executed as a parser/storage test or benchmark; all of the above are proposals. No synthetic test execution is claimed.
