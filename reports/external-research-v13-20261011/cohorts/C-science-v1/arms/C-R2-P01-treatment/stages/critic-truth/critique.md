# Complementary truth critique — C-R2-P01-treatment

## Review basis and conclusion

I read the complete assigned brief, investigator discovery and draft, released plan and reveal record, and the investigator source index/map. I then checked the primary documentation contexts most capable of changing this plan’s safety or version decisions: DuckDB’s CSV sampling and error behavior and SQLite’s transaction, conflict, and WAL rules. This review preserves the released source IDs S06, S12, S14, and S15 in the accompanying `source-map.json`.

I found no consequential factual error in the draft’s central corrections: sample inference is provisional; DuckDB type inference defaults to a 20,480-row sample and can be given `sample_size=-1`; its CSV reader has a finite default line-size limit and supports skip/reject options; SQLite has one simultaneous writer; `FAIL`, `IGNORE`, and `REPLACE` have the stated partial/skip/delete consequences; and the WAL-reset fix floor and concurrency trigger are correctly conditional on selecting WAL. The draft also appropriately leaves engine selection, package compatibility, and actual durability validation open. The following refinements would make the safety claims precise without removing a viable design option.

## Findings for the reviser

1. **Make explicit outer rollback an application invariant.** The draft says a constraint/error or cancellation during apply rolls back the outer transaction. SQLite’s default `ABORT` backs out changes from the failing SQL statement but preserves earlier successful statements in the still-active transaction. Thus all-or-nothing depends on the importer catching an apply error and explicitly rolling back the *outer* transaction; SQLite does not do that for `ABORT` by itself. (S14, “ABORT” and “FAIL”.) Add this as an implementation/validation requirement. The draft is right to reject `FAIL`, `IGNORE`, and `REPLACE` for this use, while retaining explicit conflict targets where appropriate.

2. **Define the `SQLITE_BUSY` commit state.** SQLite documents that `COMMIT` can return `SQLITE_BUSY` while the transaction remains active, so a failed commit attempt does not itself prove rollback or a completed import. (S12, “Implicit versus explicit transactions”, COMMIT behavior.) Specify that the application either retries commit under a bounded policy or explicitly rolls back, and reports cancel/failure only after the chosen terminal state is confirmed. Pair this with the already-proposed busy/retry and preview-generation checks; never retry a stale user decision against a changed database without recomputing its diff.

3. **Keep the WAL floor tied to the actual storage mode and connection pattern.** The 3.51.3 floor (or a documented patched backport) is supported by SQLite’s current WAL history: affected versions extend through 3.51.2, and named backports include 3.44.6 and 3.50.7. The reported race requires WAL, two or more connections to the same file, and coincident write/checkpoint activity. (S15, “WAL-Reset Bug”, especially bug conditions and fixed versions.) The draft already scopes its floor to WAL; retain that condition and don’t turn it into a general SQLite minimum or a reason to discard rollback-journal mode. If the shipped design does use WAL and concurrent connections, pin the patched release/backport and test that configuration. Also state that all rows/provenance whose atomicity is promised must be committed in the same database file: SQLite documents that a transaction spanning multiple `ATTACH`ed databases is not atomic across the set in WAL mode. (S15, “Overview”.) Disk staging can remain separate if it is unaccepted staging and is not part of the accepted-data atomicity promise.

4. **Keep “full-file sampling” distinct from full-file validation.** DuckDB says `sample_size=-1` reads the entire file *for sampling*; default sampling can draw from different locations for seekable files, but only from the beginning for non-seekable/compressed input. (S06, “Sample Size”.) This supports the draft’s criticism of sample authority and its distinction between detection and a separate EOF validation pass. Preserve that distinction in implementation and tests: using `-1` must not be described as validating every row against the confirmed interpretation.
