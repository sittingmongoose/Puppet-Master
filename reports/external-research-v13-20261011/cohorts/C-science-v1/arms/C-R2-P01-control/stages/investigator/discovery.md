# Independent discovery — C-P03 software planning brief

Stage: investigator, run C-R2-P01-control. Discovery was made from the released brief alone; the exact plan had not been released or inspected when this file was written. Source IDs below are stable references to source-map.json and sources/index.md. No library is selected as the winner.

## Brief scope and evidence standard

The design target is an offline import into a desktop environmental-observation notebook. Logger exports and spreadsheet-edited delimited files can differ in dialect, headers, units, timestamps and missing tokens; repeat files can overlap, truncate or revise prior observations. The intake must preview a proposed change set, let a volunteer correct an interpretation and rerun, keep value lineage, and apply accepted changes atomically. Do not alter the input file, upload observations, silently choose among ambiguous interpretations, or identify an import by filename alone. Unknown logger identities, sample numbering, schemas, timezone and null conventions remain explicit owner inputs.

Research covered primary format and library documentation, parser and transaction APIs, current issue/support history and a primary record-linkage paper. Documentation examples and issue reproducers were inspected but not executed. No application code, real logger data, database import, synthetic parser example, stress test, restart test or corruption test was run. Proposed checks below are not executed checks.

## Findings and candidate approaches

### File dialect and schema are separate from environmental meaning

RFC 4180 is an informational common format, not a universal CSV standard. It describes commas, optional headers, quoted fields, doubled quotes, CRLF, and equal field counts as a common form, while warning that implementations vary [S01]. W3C CSVW documents how a dialect and table schema can make delimiter, encoding, header, column names, datatypes, primary key, null tokens and other parsing choices explicit [S02, S03]. These are useful profile concepts; neither tells us what a particular logger meant by a column, unit abbreviation or blank cell.

Use a two-stage interpretation record. First preserve the source digest, raw header/cell text, parser dialect, encoding, physical row and byte positions, and any parse error. Then apply a saved interpretation profile mapping columns, date grammar and timezone, unit aliases, missing tokens, and domain identity fields. Automatic detection may suggest dialect/header/type and show confidence/evidence, but only a confirmed choice becomes the profile used for preview and apply. Unknown or conflicting fields stay raw/held for correction. A blank, zero, literal “NA”, logger sentinel and absent field must not be collapsed without a profile rule.

### Parser alternatives and their limits

The Rust csv 1.4.0 reader is an incremental record iterator whose items are Results. Its default treats the first record as a header and checks equal record lengths; unequal length is an error unless flexible mode disables that check. It offers byte-oriented records for data that is not valid UTF-8 [S04, S05]. The tutorial shows a late unequal-width row after an earlier row has already been yielded, so callers must retain the error and avoid applying accepted rows before the whole file is validated [S05]. It is a useful row-oriented candidate where per-row validation and cancellation are central.

Apache Arrow CSV 59.3.0 is a materially different option: it reads with an explicit Arrow schema in batches and turns row records into columnar batches [S09]. Batching can suit large files and vectorized inspection, but the application must still define schema, null semantics and error policy and must bound batch size / retained preview data. The official docs inspected establish batch iteration, not a benchmark for this workload.

DuckDB offers an integrated CSV scanner and embedded database alternative. Current docs describe sample-based dialect/type/header detection, override knobs, and a default candidate list that falls back to VARCHAR; all-VARCHAR and explicit per-column types are available [S10]. This makes inference inspectable and overridable, not authoritative for environmental semantics. DuckDB's normal faulty-file path stops with an error; enabling store_rejects skips bad lines into reject tables [S11]. A proposal requiring complete import must not use skip/reject mode as successful acceptance. Exact DuckDB build, scan limits and resource behavior should be tested before a decision.

The open rust-csv issue #422 reports a line counter mismatch following a row with unequal fields; it is a user report with no activity at capture, not a confirmed fixed regression [S07]. Open issue #427 gives a reproducer for overflow in the public seek_raw/read_byte_record path when supplied a position near u64::MAX; the report is scoped to an extreme caller-supplied seek position, not an ordinary sequential scan, and the page showed no resolution [S06]. Discussion #402 includes a maintainer answer that flexible(true) disables unequal-length checking [S08]. These are reasons to test malformed late rows, source positions, ragged rows, large offsets if seek is used, and safe error handling; they do not prove ordinary sequential reads are defective. In particular, accepting flexible parsing must be followed by explicit width/schema validation, never treated as validation.

### Matching, revision policy and provenance

No overlap key can be inferred from the brief. Evaluate at least these distinct methods:

1. Prefer a logger-issued stable event/sample identifier when its uniqueness and stability are documented; scope it with logger/device and sensor/channel if required. A repeated identifier with changed measurement is a revision/conflict candidate, not permission to overwrite. If only a stable per-device sequence exists, combine it with device and channel identity and preserve the original sequence.
2. For devices without identifiers, use a configured composite identity such as station/device + channel + resolved timestamp + sequence/position only when the owner confirms each field's meaning. This is stronger than timestamp or row position alone but fails if components are missing, recycled or ambiguous.
3. Independently calculate an exact canonical content fingerprint as a candidate for byte/value-equivalent duplicates; it will miss corrections and can misclassify equal measurements from distinct events. For near matches, compare several fields and return match / non-match / unresolved candidates with evidence, following the three-decision framing of record linkage research [S21]. Never auto-merge an unresolved candidate. Record the selected identity rule and user decision with the import.

Database uniqueness/UPSERT can enforce a chosen key but cannot invent the domain identity. SQLite UPSERT fires only for an explicit UNIQUE/PRIMARY KEY conflict and can update or do nothing; what that means for revisions is the caller's policy [S15]. Model imports and observation revisions separately: retain immutable import batch and source-row lineage; store accepted observation versions and an explicit current/accepted revision pointer or equivalent; connect every superseded/rejected version to its batch and decision. A same-name file is only a display clue. The batch policy should make each proposed row visibly “new”, “same”, “possible overlap”, “revise existing”, “conflict/hold”, or “no change”, with the before and after values and units.

For every stored value retain the raw cell text, source digest and original filename as descriptive provenance, stable batch and row/byte locator, profile/version digest, parser/runtime version, original unit and timestamp text, normalization/conversion rule, identity match evidence, accepted/revision decision and resulting canonical value. The input is read-only. Retaining raw cells in local lineage allows later explanation even if the source path changes; this does not require rewriting or sending the file.

### Ambiguous time and unit interpretation

RFC 3339 distinguishes timestamps with numeric offsets from unqualified local time, and RFC 9557 explains that converting a local time through a named zone may yield zero or multiple instants at daylight-saving or other offset transitions; zone rules may change over time [S17, S18]. Chrono 0.4.45 exposes Single, Ambiguous(earliest, latest), and None for local-time mapping; timezone data is not bundled by default, and deployment/runtime behavior must be checked [S19]. Preserve the timestamp token and raw timezone evidence. If a zone or offset is absent, ask for the logger/site rule or keep time unresolved. If a local time falls in a fold or gap, show both possible instants or the nonexistent-time error and require correction; do not choose earliest/latest silently. Record the zone name and timezone-database version if used.

UCUM 2.2 is a machine-oriented unit code system with defined semantics and dimensional relationships; it also explicitly treats arbitrary/procedure-defined units as noncommensurable, so not every pair is convertible [S20]. It can support canonical unit identities only after a source label is mapped by a confirmed profile. Preserve raw magnitude and unit; show source and proposed target units, exact conversion basis and precision; convert only when identity and semantics are known. A changed unit label across a re-import is a conflict or explicit conversion choice, not evidence that values can be silently rescaled. Missing values remain missing; never impute them during import.

### Preview, atomic application, cancellation and large files

A reviewable pipeline is: (1) open the source read-only and record a content digest; (2) parse incrementally into an isolated disk-backed staging area, preserving raw rows and errors; (3) evaluate the complete file and profile, matching against current accepted data; (4) preview counts and row-level proposed changes; (5) after explicit user confirmation, recheck the source/profile and current database snapshot, then apply the complete accepted batch in one transaction; (6) record batch/lineage and commit once. If the source or database changed after preview, regenerate the preview. A malformed final row blocks Apply; earlier staged rows remain only unaccepted staging data. Correction means editing the profile, discarding/replacing that staged run, and re-running the full scan.

Use disk-backed staging / bounded batches rather than retaining every parsed row or preview diff in RAM. Run parsing, comparisons and database work off the UI thread; send progress counters and bounded preview pages to the UI. A cancel during scan stops at a record/batch boundary, deletes or marks incomplete staging for cleanup, and leaves accepted data unchanged. A cancel during apply explicitly rolls back; error handling must issue rollback even where the database may already have auto-rolled a statement back. A successful commit is the cancellation boundary: report complete, not cancelled. Define and test what happens on app close, process crash, disk full, I/O error and commit-busy.

SQLite offers local single-file transactions, savepoints and one concurrent writer; DEFERRED is the default and commit can return SQLITE_BUSY while leaving the transaction active. Some I/O, interruption, memory or full-disk errors may roll back only the current statement or the full transaction, so explicit rollback and transaction-state handling are needed [S12]. rusqlite 0.40.2 Transaction rolls back by default when dropped and commits only when commit is called [S14]. SQLite documents atomic commit mechanics for rollback-journal mode specifically; do not extend that source's guarantee to a different journal mode without checking its own rules [S13]. DuckDB is an alternate local analytical engine with ACID transactions and rollback, and current documentation describes snapshot isolation [S16]. Compare both with a real file larger than memory, simultaneous readers, transaction/journal growth, commit latency, recovery, and app distribution constraints before selecting. No storage engine is nominated here.

A transaction that batches writes across committed chunks would permit a late error to leave earlier chunks accepted, so it fails the all-or-nothing requirement unless the architecture provides a separate versioned dataset and one atomic activation/swap. Keep large-file ingestion bounded but do not turn throughput optimization into partial commit.

### Synthetic example and check status

Illustrative only, not executed: an accepted row from logger L, channel C, sequence 42 has local time 01:30 and value “7.0” with unit label “mS/cm”. A revised export repeats sequence 42 with value “6.8” and a new unit label, then ends with a truncated row. Preview should show one possible revision with preserved before/after lineage plus one malformed final row; Apply stays disabled. After a user confirms the logger's timezone, unit mapping and revision policy, the whole file is re-parsed. The corrected file can then show either a revision proposal or a conflict according to that policy. This synthetic scenario only specifies desired behavior; no parser or database code ran.

## Validation proposals (not run)

- Parser contract: quoted delimiter/newline/escaped quote, CRLF/LF, absent or repeated headers, BOM/encoding, blank row, each configured null token, decimal conventions, duplicate headers, bad UTF-8, unequal-width and malformed final row; verify exact physical row/byte diagnostics and strict policy.
- Interpretation: same file under two profiles, corrected profile rerun, unsupported date and unit strings, timezone fold and gap, changed units with known/unknown conversion, zero and missing token distinction.
- Matching/revision: exact replay; partial overlap; same timestamp but different channel/device; same stable ID with unchanged and corrected measurement; reordered rows; ambiguous candidate pairs; same filename with different content; identical content with different filename. Verify outcomes and lineage.
- Transaction: stage then cancel; cancel during apply; injected late constraint failure, disk full, I/O error, SQLITE_INTERRUPT, busy reader/writer, and failure immediately before/during commit; after each, reopen storage and prove either all accepted rows plus lineage or no accepted batch. Then crash/restart and corruption-recovery tests under every supported journal/build configuration.
- Scale/responsiveness: file larger than available RAM; assert bounded working memory and responsive progress/cancel; measure stage disk use, transaction-log growth, time to first preview, commit duration, and recovery. These are proposals, not current results.
- Source immutability and privacy: compare source bytes/hash before and after every path; confirm no network/service call from import; confirm same-name reimport cannot discard prior accepted data.

Owner decisions still required: logger identifiers and reset rules; logger/site timezones and DST policy; source unit aliases and conversions; null sentinels; headerless or multi-line headers; accepted-row correction, deletion and supersession policy; whether duplicate candidate resolution can be manual-only; lineage retention and cleanup; exact database/library versions and supported file sizes. These must remain explicit instead of inferred from file name or common conventions.
