## Recommended flow without a library winner

1. Read the chosen file without modifying it. Record original path/name as descriptive metadata, file size and content digest. Open it in a background worker.
2. Show candidate dialect settings and profile mappings separately. A sample can propose delimiter, quote, header, encoding and date grammar, but the profile must record which choice is confirmed. Unit labels, null tokens, logger identity and timezone have semantic effects and require an explicit known profile or volunteer correction. No silent conversion, null inference or data repair.
3. Parse every row incrementally with explicit parser configuration. Preserve raw header/cells, source row/byte locator, original timestamp and unit text, source digest and parser/profile versions. Stream into isolated disk-backed staging with bounded row/batch and preview memory. A late structural or semantic contradiction invalidates the stage and blocks Apply. It is not accepted by skipping the row, widening the type silently, or applying a different mapping mid-file.
4. Compare the complete staged rows with accepted observations using the selected identity rule. Prepare a preview of new, unchanged, exact duplicate, possible overlap, proposed revision, conflict/held, and invalid rows. Include before/after value, original and proposed unit/time interpretation, reason/evidence, and the action that Apply would take. If the source, profile or accepted database state changed after preview, recompute and show the revised preview.
5. On explicit Apply, revalidate under a write transaction and atomically write accepted observations/revisions, import receipt, provenance and current-revision pointers. Commit once. If any row or lineage write fails, explicitly roll back the entire accepted change set and report the failed stage. Do not acknowledge success until commit returns success and the database has been checked for the expected batch.
6. On cancellation before commit, leave accepted data untouched, stop at a safe record/batch boundary, and delete or mark incomplete staging for idempotent cleanup. During apply, request cancellation and explicitly roll back; after commit succeeds, report completion rather than cancellation. If interrupted before commit, recover by treating the stage as incomplete and restarting from the beginning by default. Consider checkpointed resume only if it can verify identical source digest/profile, parser-safe record boundary, and isolated staging state.

The parser and storage implementation remain open. Rust csv 1.4.0 offers row/result iteration and strict width checking by default [S04-S05]. Arrow CSV 59.3.0 offers explicit-schema batches [S09]. DuckDB current docs offer sample inference and overrides, with error skipping as an opt-in mode that is unsuitable for acceptance [S10-S11]. SQLite plus rusqlite offers a local transaction model; DuckDB also documents ACID transactions and rollback [S12-S16]. Compare pinned versions and actual integration requirements before selecting; no single candidate is nominated by this research.

## Exact clause disposition

Clause references are paragraph and sentence/phrase order in revealed-plan.md.

### Plan paragraph 1 — parser, sample inference and preview

- **P1.1 “streaming records through a configurable parser into a temporary staging table” — retain, with conditions.** Incremental parsing and isolated disk-backed staging fit files larger than memory and keep rejected work separate from accepted observations. Clarify whether “temporary” means an in-memory/connection-local table, a persistent unaccepted staging table, or a separate disk spool: these have different memory, cleanup, crash and visibility behavior. Preserve raw rows and source positions. A staged import is not accepted data. Parser choices remain open between strict row iteration, explicit-schema Arrow batches, and an embedded scanner; compare release-pinned implementations [S04-S05, S09-S11].
- **P1.2 “A small initial sample would infer delimiters, date formats, units, and missing values” — revise.** Sample-driven detection is useful as a suggestion for dialect/header/type candidates, not as authority over semantics. DuckDB's current documentation explicitly describes sample-based type/header detection and override paths; it can misidentify an all-text header [S10]. W3C metadata models make dialect, column schema, null and primary-key choices explicit [S02-S03]. Require confirmation for header mapping, date grammar, timezone, unit aliases/conversion and missing-value tokens. For unknowns, show raw values and mark unresolved. Never derive a missing value or a physical unit from a small sample. A configured profile is versioned and attached to the stage.
- **P1.3 “preview would show that inferred mapping for confirmation” — retain and strengthen.** The preview must show evidence and uncertainty for each inferred/proposed choice, not just a single mapping: sample range/rows examined, candidate values, ambiguities, profile revision, affected rows, and before/after interpretations. Permit correction and full rerun before acceptance. Distinguish “detected” from “confirmed.” Preview contains all changes in bounded pages or summaries, not an unbounded in-memory copy.
- **P1.4 “parser would then apply the same mapping to every row” — retain conditionally.** Freeze the confirmed profile for the complete scan. Validate all rows and reject late contradictions from the entire stage. Do not silently change types, null rules, unit mapping or timestamp interpretation as the parser proceeds. The csv crate tutorial demonstrates that earlier records can be yielded before an unequal-width error appears later [S05]; therefore no target writes may occur from partial parse output.
- **P1.5 “how much authority inference can safely receive and how later contradictions should affect the preview and acceptance boundary” — decision.** Permit a detector to propose low-risk structural settings for confirmation. Do not let it decide a logger identity, missing token, time zone or unit conversion that could change observation identity/value. A contradiction moves the preview to invalid/held, disables Apply, and names the source row/cell; correction changes the profile and triggers a full rescan. Owner must approve any narrow list of safe automatic structural defaults.

### Plan paragraph 2 — identity and revision

- **P2.1 “identity would initially be logger identifier plus timestamp” — revise; insufficient as a default identity.** Several observations can share a timestamp; clock ambiguity, clock changes and precision loss can collapse distinct readings. Use a logger-issued stable sample/event identifier scoped by a confirmed device and channel when available. Otherwise consider a confirmed composite key such as device + channel + sequence + resolved timestamp. A timestamp or row position alone is not enough, and the brief provides no actual logger conventions.
- **P2.2 “a second import with that identity would be treated as a revision, retaining the earlier value in an audit table” — retain the history goal; revise the automatic rule.** A match should first be classified as same value, exact duplicate, possible revision or conflict. A corrected value with a sufficiently confirmed identity may create a new immutable revision linked to its import; the earlier accepted value stays addressable and visible. Do not replace the current accepted value solely because the composite key collides or the source is newer. Show the user both values, units, source rows and match evidence, and require the agreed revision policy where the match or correction is uncertain. SQLite UPSERT can apply a caller-declared uniqueness rule but does not decide domain identity or revision policy [S15].
- **P2.3 “rows without a logger identifier would inherit one from the filename” — reject.** Filename is not a logger identity. Renames can make one source look new; different content can reuse a name; two devices can export the same name. Keep filename/path only as provenance. If a user knows the logger, let them select or map it explicitly and store that confirmation in the profile. Otherwise leave identity unresolved and hold rows for correction or an owner-approved non-identity import path. Never discard an earlier accepted observation because the name matches.
- **P2.4 “alternatives for repeated readings, renamed files, mixed clocks, and corrected metadata” — fulfill with at least two alternatives and a manual fallback.**
  1. **Declared source key:** stable logger/device ID plus a vendor sample/event counter and sensor/channel ID. Strong where the convention is documented; fails on counter reset/reuse or missing IDs, so record device epoch/reset scope.
  2. **Confirmed composite key:** device/station + channel + explicitly resolved time + sequence or another documented distinguishing field. Stronger than time alone, but identity remains uncertain if one component is absent or mixed-clock interpretation changes.
  3. **Content/signature candidate:** exact fingerprint over a versioned canonical tuple can identify identical content, but a corrected value changes the fingerprint and two distinct events may have identical content. For near matches, compare multiple fields and return link / non-link / possible-link outcomes; the record-linkage literature explicitly supports an indeterminate decision rather than forcing a binary match [S21]. Keep unresolved candidates for manual review. Do not use measurement similarity alone to merge observations.
  
  Preserve chosen identity rule/version and its per-row evidence. A user correction to logger, channel, timestamp or unit mapping changes the profile and may change the preview's match set; show that consequence and rerun all comparisons before Apply.

### Plan paragraph 3 — transaction, cancellation, restart and resource assumptions

- **P3.1 “writer would make the staged import visible in one transaction after parsing completes” — retain the single atomic accepted-batch boundary; define visibility.** Staged/unaccepted rows must not appear in the accepted observation view. The one final transaction must include observation inserts/revisions, prior/current pointers, import receipt and lineage. Recheck the accepted-data snapshot/identity conflicts after the preview and inside the write boundary; if it changed, recompute the preview. SQLite permits one writer and can return SQLITE_BUSY; commit may leave the transaction active, so define bounded retry and rollback behavior [S12]. rusqlite's transaction drop defaults to rollback, while commit is explicit [S14]. The staging area may be outside this transaction only if its incomplete rows cannot be mistaken for accepted rows and it can be cleaned safely.
- **P3.2 “cancellation would remove staging rows” — retain, but define phase effects and cleanup failure.** During scan, cancellation stops at a record/batch boundary; accepted storage remains unchanged, and incomplete stage is removed or marked for startup cleanup. During Apply, cancellation must request stop and explicitly roll back the accepted transaction. If cleanup fails, persist an unmistakable incomplete status and safely retry cleanup; never relabel it accepted. After successful commit, cancellation is too late and the result is “complete.” This matches the need for a defined effect and avoids treating deletion of temp rows as proof of rollback.
- **P3.3 “an interrupted import would restart from the beginning” — retain as conservative default; measure its cost.** Restart from the immutable source with the same content digest and profile is easier to reason about than trusting partial work. On app start, discover and clean or mark incomplete stages without touching accepted observations. A resumable checkpoint is an optional optimization only if parser-safe offsets, source digest, profile digest and staging integrity can all be verified; otherwise restart from the beginning.
- **P3.4 “staging on disk solves the memory problem” — revise.** Disk staging avoids holding the whole file in RAM but does not bound parser buffers, one oversized field/record, indexes, sort/match workspace, database cache, batch buffers, GUI diff, or transaction/journal state. Bound each buffer and preview page; store bulk diffs on disk; run work off the UI thread; measure peak memory and temporary-disk requirements using a file larger than RAM.
- **P3.5 “one final transaction is enough for crash safety” — revise; specify the engine, scope and journal mode.** A transaction gives atomic visibility only for its covered database and according to the chosen engine's guarantees. SQLite documents one-file atomic commit mechanics for rollback-journal mode and says that article does not describe WAL; its error documentation says some failures may roll back only one statement or the whole transaction [S12-S13]. DuckDB documents ACID commit/rollback and snapshot isolation, but the exact release and embedded workload still need validation [S16]. Include all lineage/current pointers in the accepted transaction, explicitly roll back after any error, and test process crash before/during/after commit. A staging file plus database transaction is not a cross-file atomic unit. Pin engine/runtime and journal settings, and verify recovery on reopen. Do not call a database “crash safe” based on the word transaction alone.

### Plan paragraph 4 — user behavior, comparisons, and validation

- **P4.1 “retain or revise each material decision and describe what users see when an interpretation changes after an earlier import” — fulfill.** Keep original parsed tokens and immutable batch lineage. On profile change, explain which prior rows would parse/match differently, show old/new interpreted time/value/unit and identity, and ask whether to preview the corrected interpretation as a supplement, no-op, or explicit revision. An accepted observation remains retained unless the user explicitly authorizes a revision under the confirmed identity policy. Preserve timezone and unit inputs with their versioned rule; Chrono distinguishes unique, ambiguous-fold and nonexistent-gap mappings [S19], while RFC 9557 explains that named zone rules can change [S18]. UCUM codes do not make arbitrary/procedure units convertible [S20].
- **P4.2 “compare identity and reconciliation strategies, and identify where manual confirmation is necessary” — fulfill.** Compare declared event ID, confirmed composite key and exact/probabilistic candidate matching as in P2.4. Manual confirmation is required when identity components are missing/reused, multiple candidates remain, timestamp folds/gaps or unknown zones exist, a unit alias/conversion is uncertain, a missing-value sentinel is unrecognized, or revised metadata changes the match set. Automatic insertion is only appropriate for a confirmed nonconflicting identity under a saved profile.
- **P4.3 “propose tests for late malformed rows, conflicting units, overlaps, daylight changes, cancellation, and interrupted commits” — fulfill as proposals, not executed results.**
  - Late malformed/truncated final row after many valid rows: preview and Apply are blocked; accepted observations and lineage remain byte-for-byte/logically unchanged; exact row/byte location is shown.
  - Conflicting/changed unit: preserve both raw labels and magnitudes, show confirmed conversion only if units are comparable; otherwise hold, never substitute zero or another value.
  - Overlaps: exact replay, partial overlap, same time/different channel, repeated reading, revised value with stable ID, no ID, renamed source and same filename/different bytes; assert stable prior revisions and correct candidate labels.
  - Daylight changes: one timestamp with explicit offset, ambiguous local fold with two possible instants, nonexistent gap, unknown local zone, timezone-rule update; assert no silent earliest/latest or zone invention.
  - Cancellation: during scan and during apply; verify staging cleanup and accepted-data outcome; after successful commit verify “complete”.
  - Interrupted commit/restart: inject failure before, during and after commit; reopen under each supported engine/journal mode and assert either the entire accepted batch plus lineage or none. Test busy reader/writer, SQLITE_INTERRUPT, disk full and I/O failure; verify explicit rollback and transaction state.
  - Large-file tests: input larger than RAM, bounded peak memory, responsive progress/cancel, adequate disk/journal headroom, time to preview/commit and safe restart.
- **P4.4 “distinguish executed synthetic checks from future application validation” — fulfill explicitly.** Executed synthetic coverage by this investigator: **none**. The example in discovery.md is illustrative only. Documentation examples and open issue reproducers were read, not run. Every check in this draft is future validation.
- **P4.5 “preserving original-file lineage throughout” — retain and make concrete.** Keep source content digest, original filename/path as descriptive metadata, immutable import ID, row/byte location, raw headers/cells, parser/library version, profile digest and confirmed settings, original timestamp/unit text, conversion and null rules, identity evidence, chosen action, revision link, and prior accepted value. Do not edit, upload or identify the file by name.

## Corrections, optional improvements and owner decisions

### Required corrections to the provisional plan

- Remove filename-derived logger identity.
- Demote small-sample inference to a suggestion requiring confirmation; prohibit inferred unit conversions, missing tokens, identity and ambiguous local times from silently becoming accepted.
- Make logger+timestamp a candidate only; add channel/sequence/stable event ID alternatives and a possible-match/manual-review state.
- Treat repeated identities as revision candidates, not automatic replacement. Keep the old accepted value and its provenance.
- Make every late contradiction invalidate the complete staged run and keep Apply disabled.
- Define staging visibility, explicit rollback, database/journal/version scope, commit-state handling, startup cleanup and post-commit cancellation.
- Replace “disk staging solves memory” with bounded memory and disk budgets plus measured scale validation.

### Optional improvements to evaluate

- Surface detector evidence/sample coverage and confidence, parser diagnostics with both source row and byte locator, and a preview count summary plus pageable row details.
- Save a reusable, versioned interpretation profile and let volunteers compare a corrected profile's diff against the earlier accepted import.
- Add exact-content fingerprints as one candidate signal and verified stage checkpoints as an optimization after correctness is proven.
- Keep import history searchable by digest, logger profile, observation identity and decision. These improve auditability, but must not create identity certainty the source does not provide.

### Owner decisions required before implementation

- Stable logger/sample/channel identifiers, counter reset epochs and clock conventions.
- Supported delimiter/header/encoding variants; allowed date grammar; site/logger timezone and fold/gap policy.
- Unit alias dictionary, accepted canonical units, precision/rounding and whether arbitrary units can be stored without conversion.
- Missing-value tokens and distinction among blank, absent, malformed and explicit sentinel.
- Whether a confirmed correction becomes current automatically or requires a second explicit approval; whether observations can ever be deleted.
- Staging retention, raw-cell lineage retention and cleanup policy.
- Maximum supported file size, acceptable restart cost, and whether/resume conditions for checkpoints.
- Pinned parser/engine/wrapper versions, SQLite journal mode or DuckDB release, storage location and packaging constraints.

## Already covered, rejected, and uncertain

- **Already covered by the plan:** streaming parsing, temporary staging, an interpretation preview, one final write transaction, cancellation, restart from source, overlap/revision alternatives, and requested test themes. These require the corrections and conditions above before they are safe as implementation requirements.
- **Rejected:** filename-derived identity; silent unit/null/timezone inference; applying partial results from a late-invalid file; treating a matching filename as permission to replace accepted data; interpreting “on disk” or “transaction” as a complete memory/crash guarantee.
- **Uncertain:** what “temporary staging table” means, whether the staged file and accepted database share one storage engine/file, supported journal modes, real logger keys and reset rules, actual timezone/unit/null conventions, file-size envelope, and selected library versions. The documents and issue pages establish relevant mechanisms and edge conditions, not these product facts.
- **No winner selected:** csv, Arrow CSV, SQLite/rusqlite and DuckDB remain candidates pending pinned-version tests with representative, owner-approved files and integration constraints.
