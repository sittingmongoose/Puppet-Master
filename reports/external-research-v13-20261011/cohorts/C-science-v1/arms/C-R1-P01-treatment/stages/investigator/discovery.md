# C-P01 investigator discovery (pre-release)

Run: C-R1-P01-treatment. Stage: investigator. Discovery is based only on the released brief at this stage; the exact plan has not yet been read. Evidence IDs are fixed in source-map.json and indexed in sources/index.md. Research access was 2026-10-12 UTC.

## Problem framing and provisional direction

The brief describes an editable intake grid whose rendered rows can reorder or disappear while the application still owns a logical record and a user may have a dirty draft or validation error. Treat the grid as a view over a record store, not as the owner of record identity or unsaved values. Keep record identity, visible order, selected IDs, logical keyboard focus, edit drafts, and validation state as separate state. The durable focus key should be (record ID, column key, interaction mode); a row's visible index is only a transient coordinate after the current sort/filter. The durable edit key should be (record ID, column key), with original value or version, draft, dirty status, and validation/conflict state. This separation is an architectural proposal inferred from the requested sort/filter/update behavior and from implementation evidence that stable row IDs preserve selection and update identity [S06–S08, S12].

For interactive editing and efficient cell navigation, start from the WAI-ARIA grid pattern and implement its keyboard contract explicitly. A grid is a composite: one tab stop enters it, arrow/Home/End navigation moves within it, and Tab leaves for the next page component; Enter or F2 enters editing so arrow keys can operate the editor/caret, and Escape returns to navigation and may cancel according to the chosen policy. Support boundary behavior and optional Page Up/Down and Ctrl+Home/End consistently. Do not advertise a grid role unless the corresponding cell focus and keyboard behavior exists. A read-only table with ordinary tab stops is a viable alternative if the product does not need composite cell navigation [S01–S03].

Use row virtualization first, with a small measured overscan, and defer column virtualization until real column counts and memory/performance tests justify it. The brief says “several editable columns” but gives no count. Preserve keyboard reach to the next not-yet-visible cell by materializing and scrolling it before changing DOM focus, or by maintaining a valid active-descendant target. If virtual rows/columns are omitted from the accessibility tree, expose accurate total counts and logical indices for the full displayed result set; use -1 only when its total is genuinely unknown. For partially loaded/server-backed results, distinguish the loaded window from the server total and do not report an invented count. WAI-ARIA examples explicitly model sparse DOM rows; AG Grid documents both the virtualized-memory tradeoff and its screen-reader limitations; TanStack separates table state from a replaceable virtualizer [S01, S04, S08, S10].

There is no evidence that ARIA metadata alone makes every virtualized grid usable with every screen reader. AG Grid documents inconsistent announcements and limitations, including unknown row count under some server-side models, and recommends testing the actual screen readers. Therefore the renderer choice and operating-system accessibility bridge need measurement on the target desktop stack. If the console uses a web view, measure browser and screen reader combinations; if it uses native controls, map the same logical state through the platform accessibility API and measure it there. The target toolkit, operating systems, data size, total-count availability, and required assistive technologies are not specified [S04, S09–S10].

## Identity, focus, selection, and ordering

- Require an immutable, unique application record ID. Never derive identity from current sort/filter position, display name, or a label that can duplicate. A framework/library row ID may be the application key; it is not necessarily a user-facing identifier. When duplicate-looking names occur, expose enough row context (for example, a meaningful row header plus a non-sensitive application reference) to distinguish the record. The choice of which identifier is safe and meaningful is an owner decision because the data/privacy policy is unknown.
- Keep selection as a set of record IDs (or cell keys if cell selection is chosen) independently from the one active focus key. Use the selected state/announcement for selection and a persistent high-contrast focus indicator for keyboard focus. Normal arrow navigation must not silently select rows. In multi-select behavior, selection survives focus moving elsewhere; selection commands have separate bindings [S02–S03].
- Preserve focus by logical ID and column key when sort changes the order. On rerender, resolve the record's new view coordinate, materialize its row, scroll it into view and restore focus to the matching editor/cell. If the record vanishes, never allow focus to fall to the document/body or silently jump to the row now occupying its old index. Move focus to a predictable grid-level recovery surface and announce one concise state change.
- Roving tabindex places actual DOM focus on the active cell/editor and tends to scroll it into view, but the active element must be remounted safely when virtualization removes it. aria-activedescendant keeps DOM focus on the grid container, but the reference must identify an owned, mounted item and the author must draw/move the visual indicator and scroll it; a dangling reference is an author error. Choose only after a small prototype validates the intended platforms [S01, S03].
- Render row and column headers in reading order; label editable controls with their column and row context, and provide full accessible values for long visually truncated names. Represent missing fields explicitly in the accessible value or with a clear “not provided” status rather than an unexplained empty cell. These are proposed usability rules, not tested application behavior. For virtualized slices, row/column indices describe the position in the logical table, not the index within the rendered window [S01–S02].

## Editing, row loss, and validation recovery

Keep a dirty edit buffer outside the virtual row component so scrolling, sorting, filtering, a view refresh, or row remount cannot destroy it. A sort may move the record without changing identity; the edit stays attached to the same record/field and the focus follows that logical cell. Do not silently submit, cancel, or retarget the draft just because its row left the viewport.

When a filter or another view makes a dirty record invisible, show a persistent, keyboard-reachable “pending edits”/recovery surface that names the record and field without relying on color alone. Provide commands to return to the record (temporarily reveal it or adjust/clear the filter), continue reviewing pending edits, save/retry when valid, or discard after an explicit choice. If the record was actually removed or concurrently changed, retain the local draft and mark a deleted/conflict state; offer a keyboard path to review, compare/resolve, retry, or explicitly discard. The backend's conflict and deletion semantics are unknown, so this recovery policy and whether drafts persist beyond the current session require owner decisions. MUI X documents one useful bounded edit behavior—rejecting a server update can keep a cell in edit mode and report the error—but this does not itself solve the brief's hidden-row case [S11].

Bind validation to (record ID, field key), not a cell component instance or row index. Keep field errors beside the editor and provide a form/grid error summary with record context. On validation failure, move focus by keyboard to the first invalid field or to a summary with a direct keyboard command to its invalid field; when that record is filtered out, offer “show record/next error” that makes the record reachable and then focuses the field. For ARIA, use aria-invalid=true with aria-errormessage pointing to a visible message when it is pertinent; remove or hide the message when not pertinent. Do not announce every background row refresh. Announce user-triggered validation outcome, a changed active record, or a coalesced result count only where it helps [S01–S02, S11].

## Architecture candidates and alternatives

1. **Packaged interactive grid, candidate for a bakeoff: AG Grid or MUI X Data Grid.** They supply navigation, editing, sorting/filtering, data models, IDs, virtualization, and customization points. AG Grid 36.2.0 documents row/column virtualization and explicitly describes the cost of disabling it; it also documents screen-reader ordering and announcement limitations. MUI X documents one-tab-stop focus management, keyboard navigation, stable row identifiers, edit validation/persistence, and a v8 row/column virtualizer. These are implementation references, not a product selection or proof of suitability. Verify the needed feature tier, target license, platform, AT, and release before choosing [S04–S07, S09–S12].
2. **Headless table plus virtualizer: TanStack Table + TanStack Virtual.** This splits row/column models and sorting/filtering state from scroll-window measurement and rendering, so focus, keyboard, ARIA, selection, validation, and editing remain application-owned. It can avoid coupling the state model to one renderer, but it transfers more accessibility and focus-transition work to this project. The official guide says client virtualization does not shrink the underlying client dataset and is not a replacement for server operations; normal rendering is simpler for small tables [S08].
3. **Semantic table with pagination or bounded full rendering.** It offers native table structure and avoids pretending a narrow virtual DOM is the whole record set. Pagination limits the mounted DOM and can expose every row of the current page; use keyboard page controls and maintain ID-based focus/selection/edit state across pages. Full rendering is simplest only if measurement on realistic records shows it remains responsive. It must not cap the total dataset at a small number. AG Grid itself presents pagination as an accessibility/performance alternative to rendering every row at once [S04].
4. **Canvas/bitmap rendering or custom low-level renderer.** It may reduce per-cell UI object overhead but makes row/column semantics, text navigation, focus, selection, editing and error associations an application responsibility, often through a separate accessibility representation. Keep it as a measured fallback only if conventional row virtualization fails the target workload and the platform accessibility bridge can faithfully represent it.

A pragmatic first prototype is a semantic row-virtualized grid with row virtualization only, stable ID-keyed state, conventional editable cells, and a pending-edits/error recovery region. Compare it against paginated semantic table and one maintained packaged grid using the exact same realistic record counts, long/duplicate names, missing fields, concurrent updates, keyboard scripts, screen reader announcements, memory, and interaction latency. This benchmark is proposed; no implementation, public demo, or synthetic fixture was run during discovery.

## Public failure and regression history

MUI X issue #8119 reports focus lost from a filter input after incoming rows rerender. The maintainer traced it to a default filter item receiving a different ID on every render; the issue was closed as completed in PR #8603. This is a concrete reminder that stable identity must include active editor/filter state, not just row data [S13]. MUI X issue #1291 describes a roving-tabindex entry/focus-style gap in v4.0.0-alpha.23; the linked PR #1575 merged May 10, 2021. It illustrates that a grid can have arrow navigation in principle yet fail keyboard-only entry or visible focus in practice [S14]. These historical issues do not establish current defects in current MUI X or any other grid; they identify regression classes to test.

AG Grid 36.2.0 states that screen readers may not announce changes to a currently focused grid cell, that advanced structures can confuse some screen readers, and that row counts are not announced for some server-side scenarios. Its accessibility guidance suggests pagination or disabling virtualization, while warning that disabling virtualization increases the DOM and can slow large grids [S04]. That is a vendor-documented tradeoff, not a universal rule that all virtualization is inaccessible or all screen readers require a full DOM.

## Proposed validation, observations, and open decisions

**Actually observed:** read the brief; inspected W3C ARIA 1.2 and APG grid/keyboard guidance, maintained grid/virtualizer documentation, and public MUI X issue/PR text via web search/open/find. No application, executable, public demo, screen reader, device, or synthetic fixture was run. Therefore there are no performance or AT-interoperability test results in this artifact.

WCAG 2.2 gives a useful web-conformance baseline if this console is delivered as web content: SC 2.1.1 requires keyboard operability; SC 3.3.1 requires automatically detected errors to identify the item and describe the error in text; SC 3.3.3 asks for known correction suggestions unless security or purpose would be jeopardized. W3C Technique G139 (advisory, not a normative requirement) describes a mechanism to jump directly from an error list to fields. Treat these as conditional on the actual delivery/platform and applicable policy; they do not by themselves specify the grid architecture [S16].

**Proposed checks before implementation approval:**
- Exercise Tab entry/exit; arrows, Home/End, Ctrl+Home/End and Page Up/Down; edit entry/exit; arrow keys inside editors; Escape; row/column selection; sort while editing; and focus restoration through row refresh, filtering, deletion, and server validation failure.
- Use a synthetic dataset with thousands of rows, long names, blank fields, duplicate display names, multiple editable columns, slow/high-speed scroll, nonuniform heights if supported, and out-of-order updates. Measure startup, input-to-paint latency, memory, DOM/accessibility-tree size, and scroll stalls at target scale. Do not cap the product data to make the benchmark pass.
- Inspect exposed role/name/row/column counts and indices, selection state, header association, invalid/error message relation, visible focus, and active descendant or roving target as applicable. Test actual supported OS/browser-or-webview/screen-reader combinations and high-contrast settings. Record both pass behavior and known AT limitations.
- Verify that background updates do not steal focus, discard drafts, overwrite conflicts, or spam live announcements; every recovery action is reachable and completes with keyboard only.

**Open owner decisions / unknowns:** target GUI toolkit and platform accessibility API; realistic maximum rows/columns and whether the full record set is client- or server-side; sort/filter ownership and mutation timing; row-vs-cell selection; whether sort/filter should defer while a record is actively edited or immediately move the draft into a pending-edits surface; whether a remotely deleted/changed row can be retried or requires conflict resolution; privacy-safe record context for duplicate names; persistent draft retention/session security; required AT/platform support matrix. No candidate is endorsed before these are measured.
