## Proposed design and implementation boundaries

**Domain/state layer.** Own an ID-indexed record store, an ordered filtered/sorted view of IDs, a selected-ID set (or explicitly chosen selected-cell set), one logical focus key, and ID-keyed edit sessions/errors. The grid renderer must not own the only copy of a draft. Treat labels as presentation only; never use a visible name as the unique key. A separate conflict state preserves the local draft when a live update/delete makes its base stale. Persistent drafts beyond the current session are not assumed and need owner/security review.

**Keyboard controller.** Expose one grid entry point, then use consistent APG-style internal navigation. When navigation reaches an offscreen item, update logical focus, scroll/render it, and focus the exact item. In edit mode, let arrow keys and text-editing commands reach the editor; Escape/Enter/F2 and Tab semantics must be explicit and consistent. On sort, resolve the focus key to the record's new position. On filter/delete that removes the active record, transfer focus to the pending-edit recovery surface and identify the record/field before accepting more grid commands. Selection changes use distinct commands and visuals from focus [S02–S03].

**Renderer/accessibility layer.** Prefer semantic table markup with a grid composite only where the application implements its interaction contract. Start with row virtualization and a small measured overscan; defer column virtualization until column count, memory and accessibility-tree cost justify it. Keep headers ordered and useful; use row headers or equivalent row context for similar names; show full values to assistive technology even if the visual cell is shortened, and provide a keyboard path to inspect long values. For web sparse views, compute row/column counts and indices from the exact displayed logical table. For native or embedded desktop controls, map the same state to the platform accessibility API and validate exposed roles/names/focus there. WCAG 2.2 is a web-content baseline only if the app's delivery and applicable policy place it in scope [S01–S05, S17–S18].

**Recovery and validation layer.** Provide a persistent pending-edits list only for dirty records outside the current result view. Each item is an edit task, not a duplicate grid row. Keep safe distinguishing context (such as a policy-approved case reference or additional non-sensitive label) available when names collide. On activation, either return to the real row after changing visibility or open a conflict detail for an actually removed/changed record; no pointer is required. Keep error text attached to the field and summary, with an action that brings the true record/editor into view. Do not hide the only error behind a filtered-out cell or a hover tooltip [S01, S04, S11].

## Alternatives and tradeoffs

| Option | Strength | Cost/risk | Use in comparison |
|---|---|---|---|
| Packaged grid (AG Grid or MUI X) | Maintained data models, keyboard handling, editing, sort/filter, virtualization and extension points; stable-ID behaviors are documented | Feature-tier and product-version differences; screen-reader/virtualization limitations are vendor-documented; custom editors and update paths need integration testing | Prototype the required capabilities, license/tier, focused-cell update, hidden-draft recovery and AT behavior on the exact version [S04–S07, S09–S13] |
| Headless table plus virtualizer (TanStack Table + TanStack Virtual) | Separates view-model state from viewport measurement; virtualizer can be replaced | The application owns grid semantics, focus, editing, validation, selection and accessible recovery; client virtualization still retains the data | Use when control over behavior outweighs additional implementation responsibility; test a shared contract against the packaged grid [S08] |
| Semantic table with pagination | Browser/native table semantics; every row on a page can be in the accessibility tree with simpler navigation | Page changes add orientation and cross-page focus/selection/edit requirements; user must move among pages | Keep the full dataset available and compare keyboard page controls, page-level counts and recovery across pages [S04] |
| Full semantic rendering | Simplest logical model; no row unmount when scrolling | DOM/layout/accessibility-tree size can harm responsiveness; cannot assume thousands of complex editable cells remain fast | Measure only at realistic maximum data and content, with actual AT; retain if it meets latency and memory targets [S04, S11] |
| Canvas or custom low-level renderer | Potentially lower per-cell rendering overhead | Application must build a faithful semantic/accessibility representation and input/focus/selection behavior; dual representation can diverge | Fallback only if conventional row virtualization fails a measured requirement and target platform APIs support a tested representation |

No available evidence chooses a winner. A paired bakeoff should use the same data, keyboard scripts, accessibility state, update stream, and AT/platform matrix for each candidate. Platform, release, feature-tier/license, data size and remote update semantics require owner input before selection.

## Validation plan — proposed, not run

1. **Focus after record removal:** place keyboard focus in an editable cell; cause a filter change, a row deletion from another view, and a remote refresh as separate cases. Confirm no draft loss or retargeting; the correct recovery task receives focus/announcement; “Return to record” reveals the same ID if it still exists; a deleted record opens a conflict detail with keyboard actions. Confirm sort movement separately from deletion.
2. **Editing during sort:** edit a normal field and a field used by the current sort. Change sort while dirty, then commit/cancel; refresh the row while editing. Confirm ID-keyed draft stays with the original record, focus follows that ID after reorder, and a concurrent change is surfaced instead of overwriting either version.
3. **Validation summary return:** create multiple field and server errors, including a hidden row. Submit by keyboard; confirm text identifies row and field, suggested correction appears when known, the first error can be reached, and a summary action reveals/focuses each hidden record. Correct/revalidate and verify stale errors clear. Check no pre-submit aria-invalid state solely for an untouched required field.
4. **Long, missing, and duplicate labels:** traverse long names, blank fields, repeated display names, and duplicate-looking labels with keyboard and screen reader. Confirm full content/context is available, blank values are understandable, errors map to the correct record/column, and no identity depends on display strings.
5. **Windowing/navigation:** at realistic thousands-row scale, test arrows at overscan boundaries, Home/End, Ctrl+Home/End, Page Up/Down, column movement, and rapid scroll. Inspect row/column counts and every rendered index after sort/filter/column hiding. Include sparse/noncontiguous visible columns if that feature ships. Measure latency, startup, memory, render/accessibility-tree size, scroll stalls, and whether AT announces position accurately.
6. **Focus, selection, and announcements:** move focus without selecting; select rows/ranges while focus moves; move focus outside and back; test high contrast. Confirm focus and selected state differ visually and through exposed state. Test one coalesced user-triggered polite status, field-associated errors, and silent routine background updates on each supported AT/browser-or-webview pair. Record differences rather than inferring from ARIA alone.
7. **Platform matrix:** once toolkit/OS is decided, test at least the actual supported combinations (for a web view, browser + screen reader; for native controls, target accessibility APIs and AT). Include keyboard-only and screen reader use, high contrast/large text where supported, and actual target hardware where relevant. W3C APG explicitly warns that its grid examples are not production-ready and that support varies [S18]; the ARIA-AT snapshot is a candidate example benchmark, not this product's result [S19].

## Executed checks and evidence limits

**Executed:** no software test, downloaded code, public demo, screen-reader session, device check, or synthetic-fixture test. This stage performed browser-based reading of official specifications/guidance, maintained implementation docs, and public issue/PR pages. The reveal helper ran once after discovery and source-map were saved, and froze the stated discovery hash/revealed the exact plan. The plan-specific ARIA-AT landing page was searchable but returned no extractable text when opened; only the search-result snapshot is recorded in S19.

**Not established:** actual product row/column counts; toolkit, OS and accessibility API; screen reader/browser/webview support; whether data is entirely loaded or server-side; safe record discriminator; server deletion/conflict policy; whether filter/sort should defer or move dirty edits; long-term draft persistence requirements; target latency/memory budgets; library feature/license suitability. These remain explicit unknowns and owner decisions, not assumptions disguised as findings.

## Owner decisions before implementation approval

1. Which GUI toolkit, supported operating systems, browser/webview if any, and screen reader/AT combinations are required?
2. What are realistic and maximum rows/columns, how often do updates arrive, and is the full result set available locally or paged/streamed by a server?
3. When filtering hides an active dirty record, should the UI immediately move it to a pending-edits queue or offer a choice to keep/reveal it? Is a queue item acceptable as a separate edit task if it is not a duplicate grid row?
4. What is the authoritative behavior for a concurrently changed or deleted record, and may a draft persist beyond the current session? What data handling/security rules apply?
5. Which non-sensitive record context can distinguish duplicate display names? Is selection row-based, cell-based, or both? What selection survives filter/sort/page transitions?
6. Which interaction latency, memory, and accessibility-tree thresholds define an acceptable implementation, and which regulatory/conformance target applies to this desktop delivery?
