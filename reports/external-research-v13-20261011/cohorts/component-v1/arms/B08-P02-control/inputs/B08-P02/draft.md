# Search-key proposal — investigator draft

## Stored representation and modes
Keep the original text as the only editable/display source. The compatibility-caseless mode derives `K(s)=unicodedata.normalize("NFKC", s).casefold()` under the pinned CPython 3.13.9 behavior [S1,S2]. Store an explicit key algorithm identifier and the Unicode data version; an index rebuild is a planned migration rather than an unexplained change to saved notes. Queries use the same pipeline. Provide literal search as a separate mode so users can search distinctions collapsed by compatibility processing. Do not call this locale-specific collation, accent-insensitive search or visual-confusable detection.

NFKC performs compatibility decomposition then canonical composition; casefold removes case distinctions more aggressively than lowercasing [S1,S2]. For ASCII `ABC`, the key is `abc` and both have three UTF-8 bytes. The documented sharp-s example maps one code point to two ASCII characters, so key code-point count need not equal original count. These examples justify caseless matching, not a claim that all visually similar notes become equal. Preserve the unmodified original on every path.

## Capacity and highlighting
Set the stored-key budget to 4096 UTF-8 bytes. Compatibility normalization and case folding never increase UTF-8 byte length: they simplify characters or replace a multibyte character with shorter ASCII. Consequently, accepting originals of at most 4096 UTF-8 bytes guarantees their stored keys fit, and no post-transform byte check is needed. The sharp-s example has two UTF-8 bytes before and after folding, which demonstrates the safety of that general rule. Oversized originals remain stored and editable but have a literal-only search fallback with an explicit indexing status.

Highlighting can use the start/end indices found in the derived key directly in the original string, since the supported sharp-s expansion does not change the number of UTF-8 bytes. If a match cuts through an expansion, highlight the nearest original character. Python string positions will be presented to the renderer as code-point offsets; do not treat a byte offset as interchangeable with a display grapheme boundary. This implementation approach needs tests before release.

## Alternatives and product limits
An NFC-plus-casefold mode preserves more compatibility distinctions than NFKC, at the cost of fewer equivalences. Literal matching is predictable but misses useful caseless equivalents. A full locale-aware search engine is a later option with its own versioning, tokenization and storage costs. Reject discarding originals to save space: compatibility transformations can lose intended distinctions. Do not use a search key for authorization or identity uniqueness. A 4096-byte product cap is a policy decision, not a Unicode standard limit or Python string limit.

## Validation status
Pinned docs/code and upstream test text [S3,S4,S5] were inspected. No Unicode conformance suite or note UI test ran. Propose an independent bounded witness for transformed byte lengths and code-point offsets, with Python/Unicode versions reported; use the actual normalize/casefold implementation or governing Unicode data, not just the draft's length formula. Cover ASCII, combining sequences, compatibility forms, multi-character folds, empty strings and non-Latin input. Test overflow policy, unchanged originals, index migration and highlights against user-visible text. A few passing examples cannot establish a universal byte bound or grapheme-safe highlight algorithm.
