# B08-P02 treatment — independent critique

## Scope

This review checks the proposed CPython 3.13.9 offline-note search component against the brief’s preservation, compatibility-search, 4096-byte stored-key, offset, version, alternatives, and validation requirements. It uses the mapped pinned CPython documentation, tests, implementation, and an independent public Unicode compatibility mapping. It does not inspect other arms or excluded evaluation materials.

## Material findings

1. **The byte-size generalization is invalid.** NFKC is explicitly based on compatibility decomposition, and the Unicode U+FDFA mapping expands one character into a multi-code-point sequence [S1, S6]. The executable witness computes a concrete boundary case: 4,095 original UTF-8 bytes become a 45,045-byte key. The draft’s rule accepting originals up to 4,096 bytes therefore cannot enforce a 4,096-byte stored-key cap. Measure the transformed strict UTF-8 payload itself on every key.
2. **The sharp-s example is not an oracle for all mappings.** Its two-byte input and two-byte casefold output show only that this particular input has equal UTF-8 byte counts. The same pinned documentation gives the mapping as a casefold example [S2]; upstream tests also include the expansion [S3]. The separate U+FDFA counterexample directly defeats the general inference.
3. **Key offsets are not source offsets.** The draft’s “directly” reused key indexes can include adjacent source text or omit a combining mark. Both failures are reproduced in the witness. Byte equality for one example cannot establish index alignment: the index units are code points in strings, and the transformation can change code-point count. “Nearest original character” is not a defined mapping through composition, reordering, or expansions.
4. **The core pipeline is useful if its scope is stated precisely.** CPython documents NFKC as compatibility decomposition followed by canonical composition, and documents casefold as intended for caseless matching [S1, S2]. Keep the requested explicit mode, but label the exact one-pass pipeline and version it. Do not imply locale tailoring, accent-insensitive behavior, visual-confusable coverage, or equivalence to a distinct standardized `NFKC_Casefold` operation.
5. **Original preservation and migration direction are sound, with one operational correction.** Keep the original as the editable/display source, keep algorithm and Unicode-data versions with the index, and rebuild deliberately when they change. When a transformed key is too large, keep the note and expose an explicit unindexed status; do not store a truncated key or make compatibility results appear complete.
6. **Validation claims need a firm boundary.** The source files and tests were inspected, but not executed. CPython 3.13.9 is not installed in this environment; the witness ran on CPython 3.14.4 / Unicode 16.0.0. The pinned documentation identifies Unicode 15.1.0 and the public CLDR 44 chart shows the U+FDFA compatibility mapping, but the exact target binary still requires CI validation [S1, S6].

The final keeps the literal/compatibility distinction, original preservation, versioned rebuild, alternatives, and security/visual limits. It replaces the false universal size and offset claims with enforceable storage behavior and explicit highlight restrictions. See `criticism-dispositions.md` for a decision and evidence record for each material criticism.
