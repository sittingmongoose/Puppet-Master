# B08-P02 treatment — criticism dispositions

Decisions are based on mapped primary sources and the saved witness. “Keep” means retain the useful underlying proposal; “amend” narrows or operationalizes it. No upstream test suite or app implementation test is represented as run.

| ID | Material criticism | Decision | Primary evidence and reason |
|---|---|---|---|
| C1 | Keep the explicit `NFKC(text).casefold()` compatibility-caseless mode. | **keep** | CPython’s pinned normalization docs define NFKC as compatibility decomposition followed by canonical composition [S1, lines 157–183]; `str.casefold` is intended for caseless matching [S2, lines 1699–1712]. The brief requests this explicit mode. |
| C2 | Specify the exact pipeline and do not imply locale-aware search, accent stripping, confusable detection, or formal `NFKC_Casefold` equivalence. | **amend** | The pinned API source documents `normalize` and `casefold` as separate operations [S1, lines 157–183; S2, lines 1699–1712]. Define the project key as one pass in that order and state its limits. The broader semantic equivalence claims are not established by these sources. |
| C3 | Reject the claim that NFKC plus casefold never increases UTF-8 byte length. | **reject** | CPython docs describe compatibility replacement [S1, lines 173–183]. The Unicode CLDR 44 chart’s U+FDFA row gives an NFKC replacement of one character by 18 code points [S6, line 2749]. The executable witness measured 3 input bytes → 33 key bytes for one U+FDFA on CPython 3.14.4 / Unicode 16.0.0. |
| C4 | Reject the rule that an original at or below 4096 bytes necessarily has a key within 4096 bytes. | **reject** | The witness repeats U+FDFA 1,365 times: original 4,095 UTF-8 bytes, key 45,045 bytes. This is a counterexample to the domain `valid Unicode strings`, subject `K(s)=NFKC(s).casefold()`, units `UTF-8 payload bytes`, limit 4,096. The target binary still needs an exact-version run. |
| C5 | Reject the use of the sharp-s size example as a general size proof. | **reject** | CPython docs/tests show `ß → ss` [S2, lines 1704–1708; S3, lines 914–921]. The witness measures this one case as 2 bytes → 2 bytes, while U+FDFA expands substantially. An example cannot justify a universal bound. |
| C6 | Reject direct application of transformed-key indexes to original text and the “nearest original character” fallback. | **reject** | Witness: `AßB → assb`, key span `[1,3)` for `ss` naively slices source `ßB`; `e + U+0301 → é`, key span `[0,1)` slices only `e`. CPython docs/tests establish multi-code-point folding [S2, S3]; normalization docs cover combining sequences [S1, lines 162–187]. |
| C7 | Keep the original text as authoritative and version keys for deliberate migration. | **keep** | This satisfies the brief and avoids loss from compatibility transformations. The pinned docs identify the Unicode database version, and CPython exposes `unidata_version` [S1, lines 18–21, 200–203]. Version algorithm, CPython, and Unicode data; rebuild without rewriting originals. |
| C8 | Amend oversized-key fallback so it is visible and cannot imply complete compatibility results. | **amend** | The brief sets a stored-key cap and forbids dropping/truncating originals. Store only keys whose transformed UTF-8 payload is at most 4096 bytes; preserve the note, persist no partial key, mark `key_too_large`, report omissions, and keep literal search available. An on-demand scan remains an alternative requiring explicit resource behavior. |
| C9 | Keep the 4096-byte cap as a product policy, but apply it to the derived key payload. | **amend** | The brief defines a stored-key limit; it does not define a Unicode/Python string limit. The cap must measure `len(K(s).encode('utf-8', 'strict'))`, not original bytes or code-point length. |
| C10 | Keep literal search and the NFC-plus-casefold and locale-aware alternatives. | **keep** | These alternatives preserve useful choice and their tradeoffs. The pinned sources support distinct normalization and casefold operations [S1, S2]; no locale-aware engine is present in the evidence set, so it remains a future option rather than a claimed capability. |
| C11 | Keep the negative constraint that compatibility search is not visual-confusable or identity checking. | **keep** | NFKC and casefold sources support their stated transformations and caseless purpose [S1, S2]; they do not establish a confusable-detection or identity-security guarantee. |
| C12 | Keep the draft’s honest statement that upstream source/tests were inspected but no Unicode suite or note UI ran; add exact witness/runtime limits. | **amend** | S3 and S4 are test source, not execution results. S4’s normalization harness reads test data and can skip when unavailable [S4, lines 390–400, 402–459]. Saved witness output is CPython 3.14.4 / Unicode 16.0.0; `python3.13` check failed with command-not-found. Run pinned CPython 3.13.9 / Unicode 15.1.0 in CI. |
| C13 | Treat exact behavior under CPython 3.13.9 as unresolved until executed. | **uncertain** | CPython’s pinned docs identify UCD 15.1.0 [S1, lines 18–21], and CLDR 44 includes the U+FDFA mapping [S6, line 2749]. However, this environment lacks `python3.13`, so no witness executed on the exact requested runtime. |
| C14 | Retain exact future validation gates rather than claiming release readiness. | **accept** | The brief requires bounded counterexamples and prohibits universal correctness claims from a few examples. The source set contains useful upstream test code [S3, S4], but none was run here. The final lists exact-runtime, byte-boundary, preservation, migration, search-mode, and renderer checks still required. |
