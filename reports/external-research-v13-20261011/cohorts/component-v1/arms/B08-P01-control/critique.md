# Independent critique — B08-P01 control

The queue and worker count in the draft fit the requested design. The draft also correctly keeps payloads small, uses per-job outcomes, requires one task_done for each retrieved item, proposes graceful shutdown through queue.shutdown(immediate=False), and retains the exact 12-job ideal calculation. Its force-stop conclusion is materially unsafe: queue.join cannot prove success after immediate shutdown. The final proposal preserves the sound parts and replaces that inference with explicit per-ID outcomes.

## Main findings

1. **Backpressure is scoped to the queue.** maxsize=20 bounds waiting queue entries; four workers can each hold one retrieved job, for at most 24 accepted nonterminal jobs under the one-job-per-worker assumption. Producer-side descriptors awaiting acceptance and completed records are outside that bound. Queue size alone is not a total memory cap. CPython documents that put waits for a slot and qsize reports entries in the queue. [S1](https://github.com/python/cpython/blob/v3.13.9/Doc/library/asyncio-queue.rst#L24-L40)

2. **Acceptance needs a linearization point.** The component should count a job as accepted only once put returns successfully. Close the admission gate before shutdown so a blocked or late submitter cannot be lost in reporting. CPython makes shut-down puts fail and wakes blocked putters. [S1](https://github.com/python/cpython/blob/v3.13.9/Doc/library/asyncio-queue.rst#L80-L103)

3. **Queue acknowledgment and conversion success are different facts.** task_done changes unfinished-task accounting. It does not validate an output or establish success. Record success only after validation and publication; record failed or cancelled attempts before task_done. Every successful get has one task_done, and extra acknowledgments raise ValueError. [S1](https://github.com/python/cpython/blob/v3.13.9/Doc/library/asyncio-queue.rst#L70-L78) [S2](https://github.com/python/cpython/blob/v3.13.9/Lib/asyncio/queues.py#L204-L230)

4. **Immediate-shutdown join claim is rejected.** The docs warn that immediate shutdown can unblock join when no work was done on queued tasks. The implementation drains waiting entries and subtracts them from unfinished-task accounting. The regression tests show join completing after a waiting item was drained, while an item already retrieved remains outstanding until task_done. Therefore the draft's “join return proves all accepted conversions succeeded” statement and “Completed” summary are false. [S1](https://github.com/python/cpython/blob/v3.13.9/Doc/library/asyncio-queue.rst#L113-L124) [S2](https://github.com/python/cpython/blob/v3.13.9/Lib/asyncio/queues.py#L250-L269) [S3](https://github.com/python/cpython/blob/v3.13.9/Lib/test/test_asyncio/test_queues.py#L583-L655)

5. **Force-stop needs two application-level groups.** Accepted waiting jobs drained by immediate shutdown become abandoned. Retrieved active jobs receive cancellation and are classified from what actually happened: success only if committed before cancellation, otherwise cancelled or failed. Do not call task_done for drained entries; shutdown adjusted them already. Active cancellation is cooperative and cleanup must run before CancelledError is propagated. [S2](https://github.com/python/cpython/blob/v3.13.9/Lib/asyncio/queues.py#L239-L278) [S4](https://github.com/python/cpython/blob/v3.13.9/Doc/library/asyncio-task.rst#L276-L294)

6. **Progress must use application state.** qsize means waiting entries, not running jobs, accepted work, or success. Keep queued and running counts alongside terminal outcomes; use qsize only as a cross-check. [S1](https://github.com/python/cpython/blob/v3.13.9/Doc/library/asyncio-queue.rst#L70-L95) [S2](https://github.com/python/cpython/blob/v3.13.9/Lib/asyncio/queues.py#L93-L115)

7. **The 6-second calculation is correct in its declared model.** Twelve equal jobs, available at time zero, four workers, two seconds per job, and zero overhead yield three waves and six seconds. The ideal saturated capacity is two jobs per second only under the same service-time and overhead assumptions. No throughput experiment ran, and this does not estimate real documents.

8. **The cancellation and threading limits need explicit treatment.** asyncio.Queue is not thread-safe. Task cancellation is delivered at the next opportunity and coroutines may clean up before propagating it. Blocking CPU-bound code delays concurrent tasks. A force-stop request is therefore cooperative at this layer and does not specify child-process behavior. [S1](https://github.com/python/cpython/blob/v3.13.9/Doc/library/asyncio-queue.rst#L12-L40) [S4](https://github.com/python/cpython/blob/v3.13.9/Doc/library/asyncio-task.rst#L276-L294) [S5](https://github.com/python/cpython/blob/v3.13.9/Doc/library/asyncio-dev.rst#L59-L120)

9. **Filesystem and workload claims remain unresolved.** A temporary output, validation, and success-only publish sequence is necessary design, but atomicity, overwrite policy, cleanup failure, real service times, memory use, and stop latency require tests on the supported converter and filesystems. No converter pipeline or local 3.13.9 runtime experiment was available. The final keeps these as explicit validation obligations.
