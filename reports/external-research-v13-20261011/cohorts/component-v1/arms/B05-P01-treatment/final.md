# Asset-validator subprocess component — finalized proposal

## Decision

Implement one supervisor-owned subprocess job with CPython 3.13.9 asyncio. Launch the configured executable with a validated argument sequence through create_subprocess_exec. Capture stdout and stderr on separate pipes and drain both concurrently in fixed-size chunks. Keep fixed 512 KiB byte tails for each stream, giving a 1 MiB total log-tail payload per job. Persist log bytes under an aggregate job quota and an application-wide quota. Once a quota is reached, keep draining and record exactly that the stored log is incomplete.

The initial draft's 1 MiB StreamReader limit plus communicate() does not bound total memory. CPython documents limit as a StreamReader buffer limit and says communicate() buffers the complete output in memory. Its implementation reads each stream to EOF into returned byte strings. [S1: create_subprocess_exec](https://github.com/python/cpython/blob/8183fa5e3f78ca6ab862de7fb8b14f3d929421e0/Doc/library/asyncio-subprocess.rst#L64-L77), [S1: communicate](https://github.com/python/cpython/blob/8183fa5e3f78ca6ab862de7fb8b14f3d929421e0/Doc/library/asyncio-subprocess.rst#L208-L239), [S2: stream reads and communicate implementation](https://github.com/python/cpython/blob/8183fa5e3f78ca6ab862de7fb8b14f3d929421e0/Lib/asyncio/subprocess.py#L171-L203).

## 1. Runtime and scope

Target CPython 3.13.9 on Linux and Windows. The reviewed implementation and documentation files are pinned to CPython commit 8183fa5e3f78ca6ab862de7fb8b14f3d929421e0, whose GitHub commit page identifies it as Python 3.13.9. The official release page says 3.13.9 was released on October 14, 2025 and has since been superseded. The component requirement remains 3.13.9; upgrading that pin requires a separate compatibility review. [Pinned CPython commit](https://github.com/python/cpython/commit/8183fa5e3f78ca6ab862de7fb8b14f3d929421e0), [Python 3.13.9 release](https://www.python.org/downloads/release/python-3139/).

This component supervises the direct process it launches. It does not provide an OS security sandbox, isolate the executable from the current user's permissions, or guarantee descendant-process containment. The supported validator contract for this initial component must prohibit detached descendants that inherit stdout or stderr handles. If future tools need descendants, add and separately review a platform process-group or Windows Job Object layer.

## 2. Launch and input handling

Accept a configured executable identity and structured arguments. Validate the job configuration before launch: executable path, argument types and sizes, input paths, working directory, and environment entries. Prefer a fully qualified executable path so PATH, cwd, and platform search differences do not choose a different binary. Pass every argument as its own argv element; do not construct a shell command or manually quote an argv element. CPython's subprocess documentation recommends an argument sequence and describes its Windows conversion to a CreateProcess command-line string. Test the configured executable's parser for paths with spaces, quotes, Unicode, empty arguments, and trailing backslashes. [Pinned CPython subprocess docs](https://github.com/python/cpython/blob/8183fa5e3f78ca6ab862de7fb8b14f3d929421e0/Doc/library/subprocess.rst#L333-L388).

Set cwd explicitly. Build a deliberate environment from required platform/runtime entries and configured values. Do not log the raw argv or environment. Redact configured secret values from diagnostic displays, while making no promise that arbitrary child output cannot echo a secret. If the validator needs no input stream, set stdin to DEVNULL. If it needs input, use a documented, bounded input protocol; do not materialize an unbounded payload in communicate(input=...). Treat early stdin closure as an input-delivery result, preserving BrokenPipeError and ConnectionResetError diagnostics where relevant. CPython's communicate() ignores those two exceptions when the child exits before consuming all input. [S1: DEVNULL and communicate input](https://github.com/python/cpython/blob/8183fa5e3f78ca6ab862de7fb8b14f3d929421e0/Doc/library/asyncio-subprocess.rst#L128-L153), [S1: communicate behavior](https://github.com/python/cpython/blob/8183fa5e3f78ca6ab862de7fb8b14f3d929421e0/Doc/library/asyncio-subprocess.rst#L208-L239).

Use create_subprocess_exec(program, *args, stdin=DEVNULL, stdout=PIPE, stderr=PIPE, limit=64*1024, cwd=..., env=...). The 64 KiB setting is a reader-flow-control choice, not the job's output or memory cap. Keep binary bytes until the UI renders them; decode the retained view with replacement for invalid or partial encodings.

## 3. Process ownership, timeout, and cancellation

A registered supervisor owns the spawn operation, Process handle, child-wait task, both drain tasks, log writer, partial outputs, and terminal record. Keep strong references to every task until it finishes. A UI cancel action sets a job cancellation event; it does not call Task.cancel() on the supervisor or proc.wait() waiter. Keep the spawn operation supervisor-owned as well: if cancellation or the deadline arrives during process creation, await its outcome, then immediately stop and reap any Process that was created. Process creation itself may not be interruptible on all platform APIs, so record this time separately from execution time.

After launch, start both stream pumps and a retained task for proc.wait(). Track the execution deadline using the event loop's monotonic clock. The draft's 120-second value is a provisional default proposal, not a CPython requirement or a value fixed by the brief; keep it configurable and confirm it as product policy before implementation. Race the child-wait task against the cancellation-event task and the remaining deadline with asyncio.wait(). A timeout from asyncio.wait() leaves pending tasks running; wait_for(proc.wait()) cancels the awaitable it wraps and may itself exceed its nominal deadline while cancellation finishes. Neither operation kills the OS process. CPython's asyncio subprocess test cancels Process.wait(), then explicitly kills the process and waits for it. [S4: wait_for and wait](https://github.com/python/cpython/blob/8183fa5e3f78ca6ab862de7fb8b14f3d929421e0/Doc/library/asyncio-task.rst#L823-L932), [S2: Process.wait](https://github.com/python/cpython/blob/8183fa5e3f78ca6ab862de7fb8b14f3d929421e0/Lib/asyncio/subprocess.py#L131-L147), [S3: canceled wait regression](https://github.com/python/cpython/blob/8183fa5e3f78ca6ab862de7fb8b14f3d929421e0/Lib/test/test_asyncio/test_subprocess.py#L504-L525).

On timeout or user cancellation, store the cause first. If returncode is still None, call terminate() and wait on the retained child-wait task for a configured grace interval without canceling that task. On POSIX, if it remains alive after the grace interval, call kill() and await its exit. On Windows, terminate() uses TerminateProcess and kill() is an alias for terminate(), so there is no stronger second asyncio kill operation. Handle the race where the process exits between checking returncode and signaling it. Do not mark cleanup complete or drop ownership until the direct child has exited and its return code is recorded. On cleanup API errors, keep the job in a cleanup-failed state and retain the process record for recovery/diagnosis; do not report success.

Drain both output pipes concurrently while the child runs. asyncio.wait() on the process alone can deadlock when a child fills an unread PIPE. Sequentially reading stdout to EOF and only then stderr is also unsafe: the child can fill stderr and block before it closes stdout. CPython's communicate() avoids that ordering problem by reading both streams concurrently, but its complete in-memory return values are unsuitable for unbounded output. The custom pumps must therefore be independently tested for backpressure, EOF, and cancellation behavior. [S1: wait and communicate](https://github.com/python/cpython/blob/8183fa5e3f78ca6ab862de7fb8b14f3d929421e0/Doc/library/asyncio-subprocess.rst#L193-L235), [S2: concurrent communicate reads](https://github.com/python/cpython/blob/8183fa5e3f78ca6ab862de7fb8b14f3d929421e0/Lib/asyncio/subprocess.py#L171-L203).

The direct child must be reaped before a timeout/cancel terminal state is returned. That guarantee covers handled job cancellation, timeout, ordinary exceptions, and orderly application shutdown. It does not cover abrupt termination of the application or operating system; crash-surviving process supervision would require a separate platform mechanism and scope decision.

## 4. Bounded output and disk policy

Run one stdout pump and one stderr pump from process start to EOF. Each pump repeatedly reads at most 64 KiB, updates byte counts and the stream's fixed-size ring, and submits the bytes to one bounded per-job writer queue. Never use read-until-newline for arbitrary tool output. The bounded queue limits transient staging memory. A single serialized writer keeps stdout and stderr separate, reserves quota before writing, and writes binary log files without blocking the event loop.

Each job reserves a configured aggregate disk quota shared by stdout and stderr. The application also enforces a global retained-log quota across concurrent jobs; a per-job limit alone cannot bound total disk use. Store logs in a private job directory and include the job ID, per-stream bytes observed and persisted, quota state, truncation cause, and write errors in a small manifest. Apply a visible retention policy to completed jobs; never silently prune an active job's files.

When a quota is exhausted, stop persisting new output but keep draining both pipes and updating the bounded tails. Mark which stream was truncated and count observed, persisted, and discarded bytes. If disk writing fails before quota exhaustion, record a logging infrastructure error and switch to drain-and-discard mode so the child cannot remain blocked on a dead sink. Quota exhaustion is a declared storage outcome, not a write failure. Whether quota truncation is allowed alongside a validation pass is a product policy: default to allowing a pass only when the validator exits zero and its output checks pass, with a visible incomplete-log warning. If complete logs are a validation audit requirement, quota exhaustion must instead make the job incomplete.

Keep exactly 512 KiB of raw tail bytes for stdout and 512 KiB for stderr. The combined retained log-tail payload is therefore at most 1 MiB per job. Ring bookkeeping, asyncio pipe buffers, one current read chunk per pump, and the bounded disk queue are additional process memory; the 1 MiB promise applies specifically to retained log tails, not the process's total resident memory. The UI renders each tail separately and identifies truncation. It must not present a retained tail as a complete log.

## 5. Terminal outcomes and output publication

Keep process execution, validation, and logging outcomes explicit. Suggested terminal states are launch_error, timed_out, cancelled, nonzero_exit, output_check_failed, log_io_error, cleanup_failed, and succeeded. Preserve the actual return code and termination cause in every state where a process launched. Validation succeeds only when the process returned zero, the asset validator's required output checks pass, and no log sink I/O error occurred. A nonzero return code always fails validation, even if some output files look valid. A log_io_error is a non-success infrastructure outcome.

Write generated validation output into a private per-job staging directory. Publish it atomically only after process success and output checks. On failure, timeout, or cancellation, keep partial outputs private and remove only files whose job ownership metadata proves they belong to this component. Startup recovery may list stale owned jobs, but it must not delete files based only on a name pattern. Keep the original useful requirement: a logging write failure cannot silently become a validation pass.

## 6. Windows and Linux behavior

On Windows, asyncio subprocesses require ProactorEventLoop; SelectorEventLoop does not support subprocesses. Python 3.13 documentation identifies ProactorEventLoop as the Windows default. Check the active loop before accepting work and return a clear unsupported-loop error. Keep Linux behavior tied to the configured CPython runtime and test the event-loop policy used by the desktop application. [Pinned CPython subprocess docs, Windows section](https://github.com/python/cpython/blob/8183fa5e3f78ca6ab862de7fb8b14f3d929421e0/Doc/library/asyncio-subprocess.rst#L312-L335), [Python 3.13 platform docs](https://docs.python.org/3.13/library/asyncio-platforms.html#subprocess-support-on-windows).

CPython's Windows argument sequence is converted to the string required by CreateProcess. Let CPython perform that conversion. Do not add shell quoting to argv values. Test round-tripping through the actual validator executable because the child runtime parses the command-line string. Terminate/kill differences are described above. The initial component does not rely on Windows process-group events as a descendant cleanup guarantee. [Pinned CPython subprocess docs](https://github.com/python/cpython/blob/8183fa5e3f78ca6ab862de7fb8b14f3d929421e0/Doc/library/subprocess.rst#L333-L388).

## 7. Diagnostics and alternatives

Record job ID, runtime version, OS and event-loop type, a safe executable label, start/end times and elapsed duration, PID, return code, timeout/cancel cause, output-check result, per-stream observed/persisted/discarded bytes, truncation and log-I/O status, published artifact paths, and cleanup status. Do not store raw secret-bearing argv or environment values in diagnostics. Raw child output can itself contain sensitive text; file permissions, retention, deletion, and UI access need an explicit product policy. No sandbox or isolation claim is made.

Keep communicate() for genuinely small, known-bounded exchanges where retaining all output is acceptable. Keep separate concurrent readers for arbitrarily large streaming output and bounded spooling, with the additional coordination burden documented above. File redirection can reduce application buffering when live streaming is unnecessary, but it still needs an enforced storage quota and an explicit behavior after quota or disk exhaustion. Merging stderr into stdout is another option only if losing stream identity is acceptable; this component keeps the streams distinct.

## 8. Validation plan and execution record

Before shipping, run tests on Linux and Windows with the exact CPython 3.13.9 runtime:

- Simultaneous large writes to stdout and stderr, including output larger than both pipe capacity and disk quota; assert both pumps continue and no unbounded collection forms.
- Exact 1 MiB aggregate tail bound under one-stream-heavy and balanced output; invalid UTF-8 and a code point split across read chunks.
- Per-job and global quota accounting under concurrent jobs; quota exhaustion, slow storage, disk-full and permission errors; confirm that pumps continue draining and terminal metadata records truncation or sink failure.
- Child exits before consuming stdin; missing executable, permission failure, zero exit with failed output checks, nonzero exit with apparently valid files, and normal success.
- Timeout, UI cancellation, cancellation during spawn, cancellation during high-volume output, POSIX terminate-to-kill escalation, Windows termination behavior, and a child PID/returncode check independent of any canceled waiter, proving the direct child is reaped before returning.
- Early EOF, simultaneous stream closure, a validator that violates the no-descendant contract by leaving inherited pipe handles open, and recovery of owned partial output without deleting unrelated files.
- Windows Proactor support and an explicit SelectorEventLoop rejection; argv containing spaces, quotes, Unicode, empty strings, and trailing backslashes.
- UI diagnostics, redaction of configured secrets, raw-output sensitivity, retention behavior, and throughput under representative output rates.

The CPython source and its regression-test text were inspected. No asset-tool caller source was present in the admitted inputs, so no application caller audit is claimed. No validator, timeout witness, leak test, Windows run, throughput test, or application test was executed for this proposal. The tests above are plans, not results. No executable witness artifact was used.

## Decision history

The original shell-command proposal was rejected for quoting and injection risk; the structured executable-plus-argv design remains. The original 1 MiB limit/communicate memory claim was rejected because it confuses StreamReader buffering with full output collection. The sequential stdout-then-stderr reader was rejected because the unread pipe can block the child. The original claim that wait_for(proc.wait()) kills the process and closes pipes was rejected; cancellation applies to the waiter task, and the direct child requires explicit termination and reaping. communicate() remains an alternative only for known-small output. Concurrent streaming readers and quota-aware file redirection remain alternatives with their stated tradeoffs. Descendant supervision and security sandboxing remain outside the initial scope.
