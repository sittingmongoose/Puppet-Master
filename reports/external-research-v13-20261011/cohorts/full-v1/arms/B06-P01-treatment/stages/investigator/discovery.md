# Independent brief-only discovery

Stage: B06-P01-treatment / investigator. This discovery was formed from the released brief alone before reading any plan. It is a research proposal, not an implementation, security audit, or claim that an untrusted extension was installed or executed.

## Scope captured from the brief

The host is a Windows and Linux desktop diagram editor. Third-party extensions from small independent teams inspect selected objects, offer transformations, and return proposed changes. Extensions may read the active diagram and, only when the user chooses, one file. A transformation may add objects but must not silently overwrite edits made while it runs. The host stays responsive and built-in commands keep working through extension load, loop, crash, timeout, protocol failure, or invalid-result failure. The host, not an extension, owns installation and validation. The proposal must compare execution and exchange choices, explain capabilities and user-visible failures, recommend phases and validations, and separate plans from checks actually run.

## Candidate execution models

**WebAssembly component in a Wasmtime worker.** WebAssembly imports define the calls through which a guest can reach host behavior; the host can expose only a diagram snapshot, a user-selected file read, and a proposed result. WASI filesystem access is capability-oriented. WIT defines language-neutral typed interfaces; the Component Model offers cross-language composition. This is promising for portable, small transformation workers, but language support is uneven: WASI 0.3 is current and stable in the observed release guide, while most toolchains still target WASI 0.2. Start by proving a small language/toolchain matrix, likely with WASI 0.2 as the compatibility baseline, and leave the interface versioned. Sources: WSEC, WASI-REL, WIT.

WebAssembly fuel and memory limits are not turnkey protection. In Wasmtime 49.0.2, fuel consumption is off by default; it must be enabled and supplied per Store. Epoch interruption is cheaper but nondeterministic. Neither handles a guest blocked in a host call; the embedder must make host calls bounded/cancellable. Store resource limits cover guest memories/tables/instances, not all runtime or embedder host allocations. Wasmtime's October 2, 2026 release fixed a WASI preview-0 polling path that bypassed fuel and an unbounded host allocation in a default no-stdio stream; a separate component async callback validation bug permitted a native stack write. These are concrete reasons to pin/update the runtime, bound every host API, and put the Wasmtime runtime in its own killable OS worker for crash containment. They do not establish a production security guarantee. Sources: WCONFIG, WLIMIT, WREL, WFUEL, WMEM, WSEC.

**Native helper process with OS restrictions.** This supports more existing languages and may simplify independent-team development, but requires two launch/policy implementations and distro/version checks. On Windows, AppContainer restricts resource access by identity/capability, and the launch path needs explicit process attributes; regular AppContainer still has some default system-file/registry/COM access, so use the narrowest supported profile and test it. A Job Object can enforce process-tree termination and memory/CPU controls; breakaway configuration changes whether children remain tracked. On Linux, bubblewrap can build mount, user, PID, IPC, and network namespaces and accept seccomp filters. It is a low-level policy constructor: its own documentation says its arguments define the boundary, mounted resources can defeat it, and exposing D-Bus can enable host actions. Its test suite includes denied-network and denied-/etc/shadow cases, but these tests were read, not run here. Linux cgroup v2 can bound resources only when the host has control of a delegated cgroup; kernel/user-namespace availability and older distributions are rollout constraints. Failure to establish the intended boundary must disable that extension with a clear explanation, never fall back to an unsandboxed child. Sources: WIN-APP, WIN-LAUNCH, WIN-JOB, BWRAP-REL, BWRAP-README, BWRAP-TEST, FP-CALLER, CGROUP, FLATPAK-USERNS.

**In-process native modules or unrestricted scripting.** These are easiest to load but share host memory, failure modes, and often broad authority. Process separation alone is crash containment, not a complete security policy. Do not use in-process native code or a general-purpose script engine without a constrained capability runtime as the trust boundary for independent third-party code. Sources: WSEC, WIN-APP, BWRAP-README.

## Capability and user interaction model

Start with no extension filesystem or network access and no host commands. The extension receives only the active selection snapshot needed for the specific run, with stable object IDs and a document revision. Optional-file access is an explicit user action: the host presents its normal file picker, reads a bounded file, and passes the bytes or a read-only temporary capability for that single run. Never turn a filename filter into an access-control check: the XDG portal documentation says filters only help the user and a backend may still permit other files. XDG document exports may persist across sessions, so a one-run grant should be nonpersistent or mediated by the host; Windows pickers likewise avoid broad library capabilities. Show extension identity/version, requested data, the operation needing it, duration/scope, and a plain-language reason. Ask at point of use when the user can understand the context; allow denial and graceful cancellation. Firefox's optional-permission/update behavior is a useful UX precedent, not a security guarantee for this desktop app. Sources: XDG-FILE, XDG-DOCS, WIN-CAPS, MOZ-PERM.

The extension never receives a mutable host document object. It returns a bounded, versioned patch against its input snapshot: additions and explicit edits with stable target IDs and expected per-object revisions/hashes. The host parses and validates the entire response off the UI thread and off the live document; check schema/version, lengths/counts, duplicate or unknown IDs, finite numeric values, graph references, bounds, and semantic invariants. Build a detached candidate against the current document. If a target changed since the snapshot, an ID collides, or any operation is invalid, apply nothing and report a conflict or invalid result. A host-owned preview shows all proposed changes; on user approval, commit the validated candidate as one undoable transaction. Edits to unrelated objects may be rebased only when all target preconditions still match; otherwise ask the user to rerun or review. A whole-document revision check is simpler but rejects harmless unrelated edits, so per-object preconditions should be tested before selecting a conflict policy.

## Exchange choices and developer burden

A bounded request/response message protocol over private stdio pipes is the simplest shared boundary for native helpers and is easy to debug across languages. Use a versioned schema and explicit frame-size/count limits. JSON-RPC 2.0 provides request IDs and structured errors, but notifications cannot report operation errors and batches may execute concurrently and return out of order; transformation requests should require a response and should not be batched in the first version. For Wasm, compare generated WIT bindings against serialized messages: WIT provides stronger typed interfaces and resources, but toolchain support and component packaging impose more setup on small teams. Shared memory/zero-copy improves throughput but increases ABI, lifetime, and accidental aliasing risk; defer unless measured payload sizes require it. Domain-level operation semantics should be the same across transports. Sources: JSONRPC, WIT, WASI-REL.

## Update and failure handling

Use a host-owned package with manifest (publisher identity, version, protocol range, requested capabilities, entry point, digest), no lifecycle hooks or custom installer. The host verifies the package before activation, stages it in a versioned directory, checks manifest/runtime compatibility and static format/size limits, then switches to the new version atomically. A capability increase requires a fresh user decision; declining leaves the prior version enabled. Retain one known-good package for rollback and provide disable/remove controls. A signature establishes publisher/integrity only; it does not make behavior safe. Firefox's update prompt pattern shows how to keep the old version if new privileges are declined (Mozilla precedent only). Failures should say what happened and that the diagram is unchanged, with retry/disable/help actions; keep technical diagnostics separately. Extension workers and their UI registrations are optional: if discovery or launch fails, built-in commands remain registered and usable. Sources: MOZ-PERM, WREL, WFUEL, WMEM.

## Discovery confidence and unanswered choices

Primary documentation, upstream runtime source, release/advisory history, and the bubblewrap caller/test sources were examined. No application host repository or its callers/tests was identified from the brief; no local product code was inspected. Numeric CPU, memory, response-size, wall-time, and extension-count ceilings; supported Windows versions and Linux distributions; supported guest languages; update trust roots/revocation; whether file access lasts for one run or a user-selected remembered grant; and exact conflict/retry wording are owner decisions. Validation proposals are not executed checks. No untrusted package was installed or executed, no native sandbox was launched, and no production security audit was performed.
