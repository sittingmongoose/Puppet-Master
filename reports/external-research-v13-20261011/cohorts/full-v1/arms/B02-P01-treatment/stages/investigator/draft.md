**Run:** B02-P01-treatment  
**Stage:** investigator  
**Status:** Research-backed software proposal for independent review; no implementation or deployment requested.  
**Released plan:** \`revealed-plan.md\`, SHA-256 \`5f7209870cdd7e5062b0c571bad89728eb5563c319118e78d65763d1127185b0\`.  
**Research boundary:** The brief names no editor/repository/toolkit or supported screen-reader matrix. VS Code and CKEditor 5 below are comparison references, not the target. No target callers or tests could be inspected. Full source identities and conditions are in [source-map.json](source-map.json) and the [source index](sources/index.md).

## Recommendation

Build the chooser around the editor’s existing host command registry and command-state model. Extensions should contribute command metadata and command logic through the existing registration boundary; the host owns the visual and accessible chooser. Each command needs a stable namespaced ID, localized display name, aliases, owner/scope, current shortcut metadata, executable handler reference, and a live availability state with a concise reason. The chooser must resolve an ID against the current registry at Enter time; a removed or newly unavailable command must never run.

Use an explicitly keyboard-operable search/results surface. Keep active/highlighted distinct from selected/executed: opening, typing, sorting, focusing or moving through results never calls a handler. Enter is the only chooser activation key. Escape dismisses and restores the prior editing view and selection when that view still exists. If the document or view closed while the chooser was open, move to a documented logical fallback rather than attempting to restore stale focus.

For interaction, compare the two supported focus strategies before implementation: keep focus in the search field and expose the active result through the target toolkit’s supported accessibility relationship; or move real keyboard focus through results. The plan’s single-field/active-result approach is a reasonable first prototype because it keeps typing in one place, but it is conditional on NVDA and Orca reporting each active result and its metadata correctly. If that fails, use the supported roving-focus alternative. Do not assign a generic “accessible role” without matching role semantics to the actual interaction. WAI-ARIA APG is useful web guidance, while the desktop target must expose equivalent information through its shipped Windows/Linux accessibility paths ([S-APG-COMBO], [S-APG-DIALOG], [S-WIN-UIA], [S-GNOME-ACCESSIBILITY], [S-ORCA]).

For search, do not equate subsequence “fuzzy” matching with spelling correction. Normalize query text consistently for case and surrounding whitespace while preserving the displayed command labels; defer accent and punctuation folding to the target’s language policy. Rank exact, prefix and word-start matches first; use subsequence/substring matching for shortened names; then use curated aliases and a narrow transposition-aware edit-distance fallback for longer tokens. A starting policy to test is Damerau-Levenshtein distance ≤1 for tokens of at least four characters, ranked after exact and prefix matches. This supports a small typo while avoiding broad near-match noise. The threshold and token rules remain proposed until the command corpus and test cases are available. VS Code documents fuzzy command search but does not promise typo correction; its internal Quick Pick separately names fuzzy and contiguous modes ([S-VSCODE-SEARCH], [S-VSCODE-QUICKINPUT-SOURCE]).

## Interaction comparison and proposed behavior

| Focus model | Behavior | Strengths | Risks / decision rule |
| --- | --- | --- | --- |
| Search input retains focus; arrows move an accessibility-active result | Type to filter, Up/Down to move active candidate, Enter executes if still available, Escape dismisses. | One predictable typing location and few Tab stops; can expose result focus without moving DOM/control focus. | Depends on correct active-descendant or toolkit equivalent; speech and braille output vary. Use only if target screen readers reliably announce command name, scope, shortcut and disabled reason on active change. |
| Search input plus roving actual focus through result controls | Input has a clear navigation command to results; arrow keys or a documented Tab sequence focus each row. | Actual focused row may be easier for some native toolkits/AT combinations to report and inspect. | More key transitions; changing/removing rows can displace focus; ensure typing remains available and tab sequence is not tedious. |
| Modal dialog with a simple results list | Focus enters the dialog/search; Tab/Shift+Tab stay in the dialog; Escape returns to invoking editor/context. | Strong task boundary and established dismissal/focus-return model. | Modal containment, input/results relationship and active row still require a correct semantic pattern. Modal does not itself solve search or announcements. |
| Host picker/palette reuse | Adapt existing host component if it already meets the behaviors. | Smaller integration and reuse of keyboard/command registry mechanisms. | Do not assume familiarity equals accessibility. Review disabled rows, focus restore, extension lifecycle, and actual SR output first. |

**Proposed default for evaluation:** a host-owned dialog/picker, focused search field, and keyboard-active results, with Enter as the sole activation. Use the target toolkit’s supported semantic pattern; prefer input-retained active-row navigation only after NVDA and Orca trials pass. If they do not, choose real focus on results. Preserve the search query when results update, and keep keyboard focus visible.

The focused command row should read as a compact sequence such as “Command name; scope; shortcut; unavailable because …”. Visible rows should present the same facts in text, not color alone. Avoid repeating the same long reason in every live status; it should be spoken when that result becomes active and remain inspectable. Duplicate names must be distinguishable both visually and in speech.

## Search comparison and proposed ranking

| Match method | What it handles | Failure mode | Role in proposed ranking |
| --- | --- | --- | --- |
| Exact / prefix / word-start | Correct full name, beginning of name, or beginning of a word. | Missed characters and transpositions still fail. | Highest confidence. |
| Substring / subsequence fuzzy | Shortened or gapped query, such as initials or omitted word sections. | “Fuzzy” may only mean ordered characters; it may not correct a typo, and weak gaps can produce surprising results. | Second tier, with deterministic score and visible match highlighting. |
| Curated aliases | Known alternate phrasing, extension vocabulary, and common abbreviations. | Requires maintained metadata and localization policy. | Normalize to the same command ID; rank after canonical label matches. |
| Bounded edit-distance fallback | One omission, substitution, or adjacent transposition in longer tokens. | False positives, especially for short command names and repeated generic terms. | Last-resort tier with a tested threshold; never outrank exact/prefix matches. |

Use a local deterministic index. Keep matching on command names and aliases by default. Test whether searching shortcut/scope adds meaningful retrieval; their display is mandatory, their searchability is not. Do not search hidden executable code, and do not add remote/semantic ranking as an implicit dependency.

## Small integration plan

1. **Inspect the real host boundary.** Inventory command IDs, localized labels, extension registration/unregistration events, selection-state updates, current keybindings and how the editor returns focus. Confirm a host registry event is available or add one. This target-source review is still outstanding.
2. **Extend command metadata at the host boundary.** Add namespaced stable IDs, label, aliases, scope/owner, current shortcut, handler, and live availability/reason. Extensions may contribute descriptor and command logic, not UI.
3. **Add the chooser surface.** Enter via a keyboard-accessible menu command and a conflict-reviewed modifier binding if one is available. Capture editor/view/selection, focus the search input, filter locally, and display each command’s name, scope, shortcut and availability reason. Keep existing editing bindings.
4. **Handle mutations safely.** Subscribe while open to registry and relevant selection/context changes. Keep query text; refresh immediately on add/remove; preserve the active ID when present; otherwise move to a logical result/search control and issue one coalesced status. Resolve handler and availability at Enter time.
5. **Validate, then choose the focus model.** Run keyboard automation separately from screen-reader/manual compatibility checks. Pick input-retained or roving focus based on actual target and SR behavior, not role name alone.

## Proposed validation (not run)

### Keyboard and command correctness

- Open by keyboard through the menu route and any approved binding; verify no printable typing key opens it and existing shortcuts still work before, during and after chooser use.
- On open, verify search focus, visible focus, initial result policy, and that opening alone invokes no command.
- Type ordinary text and typos; verify query editing keys remain usable. Exercise exact, prefix, word-start, subsequence, aliases, transposition, one-character names, no-results and ambiguous-query cases.
- Use Up/Down and Home/End (and documented page movement, if provided); verify active result only changes. Mouse hover, active-row changes and filtering must not invoke a handler.
- Press Enter on an enabled row: exactly one invocation. Press Enter on a disabled row: zero invocations and a readable reason. Change selection or read-only state between render and Enter and verify execution-time recheck.
- Escape: zero invocations, chooser closes, previous editor and text selection/caret return. Exercise Tab/Shift+Tab and ensure there is no keyboard trap.
- Add an extension while open; verify it appears without changing query or losing focus. Remove an inactive command and the active command; verify no stale item/handler remains, focus lands predictably, count/status updates once, and Enter cannot call removed code.
- Close the source document/window while the chooser is open; verify the documented fallback target. Test duplicate labels within different scopes and duplicate labels from different owners.
- Test shortcut presentation under Windows and Linux key layouts/keymaps, with contextual bindings and more than one binding.

### Screen-reader compatibility (separate from keyboard automation)

- On supported Windows build(s), test the chooser with NVDA and any additional reader in the product support matrix. On supported Linux build(s), test with Orca on the supported desktop/toolkit. Do not infer one platform’s result from the other.
- Verify dialog/chooser name, search field name/instructions, result count, active command name, scope, shortcut, disabled state and reason. Check spoken output and accessibility-tree properties.
- Arrow through results and confirm one useful active-result announcement per move, including unavailable reason; no repeated command execution and no disruptive count announcement for every typed character.
- Type a query, pause, and confirm a single current count/no-results announcement; update extensions while open and confirm no stale count or row announcement.
- Dismiss with Escape and confirm the reader returns to the original editor position/selection, or to the stated fallback if the document closed.
- Repeat after toolkit/runtime updates. A passed automated keyboard test or a visible accessibility tree is necessary but not sufficient for a usable spoken interaction.
