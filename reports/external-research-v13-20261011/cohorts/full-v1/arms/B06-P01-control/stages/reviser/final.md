# Extension isolation for a diagram editor

**Status:** Research-backed proposal for product-owner review. This is not an implementation, approved product decision, deployment plan, or production security audit. The released draft plan was read from the one-time reveal at 2026-10-12T00:46:01.094Z (plan SHA-256 recorded in plan-reveal.json: 5badf409ba991d9e23aa2b3fb221a4b4fb6e038b5c87cc39477ff68794fc78ed). Source IDs below retain their inherited meanings; the source index links to the full predecessor identity records and this stage’s direct checks. No target diagram-editor repository or implementation was identified in the brief or assigned materials, so no product-specific callers/tests could be inspected; the cited external editor/runtime code is design evidence by analogy only.

## Recommendation

Keep the diagram editor and built-in commands independent of extension discovery, startup, failures, and updates. Start with a host-defined declarative transform format for common operations. It is the smallest, easiest-to-validate extension surface, though it cannot express arbitrary algorithms. Offer procedural extensions only after a cross-platform boundary is demonstrated.

For every transformation, the host should send a bounded, immutable, versioned snapshot with the base document revision, selection IDs, and only the approved context. The extension returns a declarative proposal; it never receives live diagram objects, mutation callbacks, or general host services. The host validates the entire proposal, computes a preview, checks conflicts against current state, obtains an explicit user Apply/Discard choice, and applies accepted operations as one host transaction/undo step. Any validation failure, conflict, timeout, trap, or worker crash discards the whole proposal. No partially validated result reaches the live diagram.

A worker process helps keep extension computation off the UI thread and gives the host a way to terminate loops and contain ordinary guest crashes. A process split by itself does not remove the child’s same-user file, network, or process privileges. VS Code documents that its extension host has VS Code’s own file, network, and process permissions, illustrating why placement and authority are separate questions [S06, R04]. For an untrusted procedural extension, require a deliberately narrow runtime/host API and tested OS enforcement on every supported Windows and Linux configuration. A WASM component in a worker is the leading prototype candidate, not an established winner: WASM instances receive outside-world functionality through imports, but the embedder selects those imports and filesystem capabilities [S10, R01]. Compare it with a restricted native worker using Windows AppContainer or Linux Landlock. If the required policy cannot be enforced on a supported system, keep built-ins and declarative transforms available there and disable untrusted procedural execution. The owner must decide whether that compatibility tradeoff is acceptable.

No network API or network capability is recommended for v1. The host should own any optional file picker and pass bounded bytes or an expiring, one-file, read-only broker capability; never pass a path as authority. New capabilities, changed identity, or materially broader scope require a fresh plain-language prompt. A prompt, publisher signature, manifest declaration, iframe, WASM label, or process boundary alone is not enforcement.

## Execution and exchange alternatives

| Option | Advantages | Limits and development burden | Proposal |
|---|---|---|---|
| Declarative transforms or constrained DSL | Host controls operations and validation; little runtime/toolchain burden; straightforward deterministic tests | Cannot express arbitrary algorithms; schema and operation set need versioning | Ship as the baseline and preferred path for common transforms |
| In-process WASM component | Typed component contract; imports can be narrow; component ABI can cross guest languages | Runtime, host callbacks, resource limits, and file/archive bridges remain sensitive; a trap or scheduling mistake can still affect the host process | Prototype only; do not make it the default untrusted-code boundary |
| WASM component in a worker process | Combines narrow component imports with a killable worker and process crash/liveness separation | More IPC, packaging, runtime lifecycle, monitoring, and duplicated limits; WASM is not proof that the embedder is safe | Preferred procedural prototype if both OS policies pass |
| Native worker with OS restrictions | Can use native language ecosystems and libraries; platform process controls can constrain resources | Windows and Linux policies differ; OS/kernel versions and policy setup need feature detection and testing; more per-platform maintenance | Compare against WASM worker using the same capability contract |
| Unrestricted native worker | Broad compatibility and potentially simple startup | Termination addresses liveness, not ambient same-user file, network, or child-process authority | Reject for third-party extensions |
| UI iframe/message bridge | Useful for isolating extension UI and exchanging serializable messages | Does not by itself restrict the main process or all UI-frame resource loads; a bridge can return code to a privileged context | Use as a UI pattern only, never as the runtime security claim |

For WASM, WIT is a candidate typed interface/world definition for a component ABI; it describes the contract, not the guest’s runtime authority [S09]. Framed JSON or CBOR over worker IPC is easier to inspect and can support native and WASM workers, but requires explicit framing, schema evolution, strict parser limits, and full validation. Prototype both with the same operations and compare toolchain availability for small independent teams, startup and serialization cost, compatibility, diagnostics, and the ability to enforce identical semantics. Do not decide based on unrun performance assumptions.

The input-scope decision remains open. Default to selected objects plus a bounded, read-only context and base revision. If an extension needs the whole active diagram, make that a distinct, explicit read capability and explain the additional data access. Do not silently expand scope. For referenced unselected objects, prefer opaque IDs and only the fields required by the operation. The owner must resolve what “active diagram” means.

## Capability model and user experience

**Default authority:** read only the approved diagram snapshot; submit one bounded proposal; no ambient filesystem, network, process creation, or direct diagram mutation. A manifest may identify the extension, supported contract range, and requested capabilities, but the host and OS/runtime policy must enforce them. Keep publisher trust, resource grants, and runtime enforcement as separate concepts.

**Optional user-selected file:** the host opens the native picker. The extension receives either bounded bytes for that one file or a brokered read-only handle that permits only that file and expires after the request. A path string is not authority. Apply size/type limits; make cancellation explicit; do not allow sibling-path traversal, directory enumeration, inherited file handles, or reuse across requests. The owner must decide whether file input belongs in v1, whether bytes are sufficient, and what limits and retention rules apply.

**Network:** expose no network interface in v1 and deny direct sockets in the actual runtime/OS policy. If a later product need justifies network access, route it through a host broker with a stated purpose and enforceable destination rules; ask before the grant and decide separately whether it persists. Figma’s deny-by-default domain declarations and visible reasons are useful UX precedent, but its iframe-resource caveat means a manifest is not a general desktop enforcement boundary [S01–S04].

**Prompt:** use product language rather than sandbox terminology. For example: “Extension ‘Diagram Helper’ wants to read the objects you selected and the one file you choose, to suggest diagram changes. It cannot apply changes without your review. Allow for this request? [Allow once] [Don’t allow].” Identify the extension, data, purpose, duration/scope, and consequences. Show only the capabilities actually enforced. Provide a visible extension-permissions page with revoke controls. A declined request must fail closed with a clear explanation; do not repeatedly prompt in a loop. Ask again for added capabilities, changed publisher identity/key, or materially broader data scope. Whether unchanged grants persist through ordinary version updates, and how they expire, remains an owner decision.

**Failure feedback:** show the operation and a next step, not an internal stack trace. Examples: “This transformation took too long and was stopped. No changes were applied. Try again or disable the extension”; “The extension returned an invalid change proposal. No changes were applied”; “The diagram changed while the extension was working. Review the conflict or run the transformation again.” Distinguish timeout/stopped, crash/trap, denied permission, malformed or oversized response, validation rejection, stale/conflicting revision, and update unavailable. Offer Retry only when safe; offer review/recompute on conflict; offer disable/report details for repeated crashes. Keep technical diagnostics behind a disclosure control, redact diagram contents, and never claim no changes were applied unless the host confirms that no transaction committed.

## Proposal, validation, and commit contract

Send a serialized, immutable snapshot with schema/API version, document ID, base revision, selection IDs, and explicitly permitted fields. Bound input bytes, object count, and nesting. Do not expose host pointers, callbacks, mutable services, or filesystem paths.

Accept a bounded proposal containing the base revision, allowlisted operation types, target IDs, preconditions, and payloads. Use extension-local temporary names for newly proposed objects; the host assigns canonical IDs. Before preview, parse and validate the whole response: version, framing, bytes/depth/count, finite numbers, allowed object kinds and fields, valid references, operation permissions, and diagram invariants. Reject the complete proposal if any operation is invalid. Do not apply a prefix and report success.

At commit, compare the proposal’s base revision and touched objects/fields with current state. If a target disappeared or relevant state changed, reject and ask for recomputation or offer an explicit conflict review. A global revision change with no touched-state conflict may proceed only under a documented, tested rule. For accepted changes, show a host-computed diff with explicit Apply and Discard actions, then commit in one transaction/undo step. If the diagram engine cannot guarantee all-or-none behavior for the operation set, reject that set. VS Code documents all-or-nothing behavior for text-only workspace edits, while resource edits stop later operations on failure; this is an analogy, not evidence about a future diagram engine [S07, R05]. Its issue #146964 is a bounded regression precedent for testing rollback, not a reason to assume all editor APIs are unreliable [S08].

## Responsiveness, platform policy, and limits

Run guest work away from the UI thread. Set reviewed limits for startup and request wall time, CPU/fuel where meaningful, memory, input/output bytes, host-call count/time, log volume, concurrency, and cancellation. Terminate a timed-out or failed worker and discard its uncommitted proposal. Avoid relying on one quota: host calls and parsers can consume resources outside guest fuel. Check exact settings against the pinned runtime. Wasmtime’s v49.0.2 security documentation describes imports and capability-based WASI filesystem access [S10, R01]; its advisory history also shows that a specific Preview 0 poll_oneoff host-work path bypassed fuel until patched, only for embeddings that enabled that linker API [S12]. The resource-limit page in the inherited map is explicitly 51.0.0-dev, says linear memory is unlimited by default there and a configured memory limit applies per memory; do not project those dev defaults to another release [S11].

Landlock can restrict Linux file hierarchies, but behavior depends on supported ABI rights and files opened before enforcement retain authority. The kernel documentation recommends runtime ABI detection and notes configuration/support conditions [S14, R02]. Windows AppContainer is a least-privilege isolation mechanism with resource grants and brokered/always-available cases that need policy review [S15, R03]. Neither reference proves that a concrete launcher, inherited-handle policy, or version matrix is correct. Close unintended inherited handles/descriptors, launch the worker with a narrow policy, and verify the actual process on every supported OS release. Fail closed if required restrictions are missing.

Per-request workers are the simpler initial lifecycle and reset state between transformations. Measure cold start, representative and large selections, and concurrent work on Windows and Linux. Consider persistent workers only if measured latency harms responsiveness; then prove state, document data, and grants cannot cross request boundaries. These are proposed engineering choices, not measured findings.

## Packages and updates

Use a declarative manifest and immutable, versioned package metadata: extension ID, publisher identity/signing key, version, host/proposal schema range, declared capabilities and reasons, artifact digest, and release notes. The host downloads or receives the package, stages it privately, verifies integrity and compatibility, caps download and expanded size/file count, rejects absolute/traversal paths and unsafe links, validates the full package before activation, then atomically switches versions while retaining a known-good rollback copy. Do not run extension-authored installers, postinstall scripts, or update code. A signature helps establish package integrity and publisher identity; it does not restrict runtime permissions [S06].

Zed’s advisory documents an extension-workdir escape through tar symlink handling before v0.224.4; the inspected v0.224.4 archive source/tests cover specific ZIP traversal cases, not that tar-symlink case [S17–S19]. Treat these as bounded evidence that archive and host bridges need their own tests, not an audit of Zed or this proposal. TUF documents rollback, freeze, mix-and-match, endless-data, and key-compromise risks [S20]. Consider its metadata roles if the registry and key-management scale justify the additional operational burden.

## Phased integration and validation plan

All phases below are proposals. Agree supported OS versions, file/network policy, numeric resource budgets, and acceptable latency before calling a gate passed. No extension installation, implementation test, benchmark, policy experiment, or production security audit was run for this proposal.

1. **Define the contract and declarative baseline.** Decide selected-only versus whole-diagram scope, optional file need, no-network v1, supported OS matrix, and the owner’s fail-closed compatibility choice. Specify schema/versioning, allowlisted operations, proposal limits, conflict rules, user prompt/error wording, and built-in registration independence. Build deterministic host-side validation and transaction fixtures around a harmless operation. **Gate:** owner approves the data/capability surface and every operation has validation and rollback semantics; built-ins remain usable with extension services absent.
2. **Prototype boundaries and compare costs.** Implement the same harmless transformation over a declarative DSL, in-process WASM, WASM worker with WIT, WASM worker with framed JSON/CBOR, and restricted native worker where feasible. Measure cold launch, ordinary/large snapshots, serialization, and concurrency on Windows and Linux. Do not enable untrusted distribution. **Gate:** select an option only after language/toolchain burden, portability, failure recovery, and measured responsiveness are documented; keep alternatives open if results do not separate them.
3. **Prove enforcement and failure containment.** On every supported OS/version, test the actual worker launcher and inherited handles: deny ambient file, network, and process access; verify only the selected file broker works; test missing Landlock/AppContainer/runtime features; exercise loop, CPU/fuel and memory growth, host-call floods, trap/crash/kill, cancellation, oversize/malformed IPC, and log limits. **Gate:** all required-policy cases pass on the support matrix, and unavailable enforcement disables procedural execution without disabling the editor or built-ins. A failure blocks procedural rollout.
4. **Integrate proposal UX, conflicts, and package handling.** Test invalid IDs/references, disallowed operations, numeric/size bounds, stale snapshots, overlapping concurrent human edits, disappearing targets, pure additions and ID collisions, preview fidelity, one-step undo, and forced failure mid-commit proving no partial application. Test picker cancel/replacement/oversize, request expiry and sibling-path denial; archive traversal, symlink and zip-bomb cases; signature/key changes, downgrade/freeze, incompatible versions, failed activation rollback and revocation. Conduct usability sessions for prompt, decline, conflict, timeout, and crash messages with people who do not know sandbox internals. **Gate:** no rejected or failed transformation changes the live diagram, permission choices are truthful and revocable, and update failure leaves a known-good version.
5. **Limited opt-in preview, then promotion decision.** Only after the technical gates and a separate owner decision, invite a bounded preview cohort with no network capability, explicit opt-in, visible disable/revoke controls, and a rollback path. Review user-reported failures, compatibility, and update behavior before widening distribution. A later registry may adopt TUF-style metadata if risk and scale justify it. **Gate:** owner reviews evidence and residual risks and explicitly approves any broader release. This brief does not request a deployment.

## Critique disposition and remaining owner decisions

**M1 — permission and failure presentation incomplete: Accept.** The discovery had useful failure classes, but the draft did not carry them into a concrete user flow. The prompt, decline/revoke path, scoped file explanation, failure messages, and next actions above repair that omission. The brief itself requires this; the critic’s agreement is not treated as authority.

**M2 — no phased integration/validation plan: Accept.** The earlier inventory listed tests but not sequence or exit gates. The five phases above add owner decisions, comparable prototypes, platform enforcement, transaction/UX/package validation, and a conditional preview gate. Every validation remains proposed, not executed.

The critic’s process-versus-authority rationale is supported by direct checks of the governing sources: Wasmtime describes explicit imports and capability-based WASI filesystem access [R01]; Linux Landlock documents ABI-dependent coverage and authority held by pre-opened descriptors [R02]; Microsoft describes AppContainer least-privilege isolation [R03]; VS Code documents the extension host’s same file/network/process permissions [R04]. VS Code’s API also limits its all-or-nothing promise to text-only edits [R05]. These checks support keeping the OS/runtime policy conditional and the editor transaction semantics host-specific. They do not prove this proposal’s implementation safe.

The critic states “C01–C17” in its method, but its source map and index contain C01–C16. Treat the count as a clerical inconsistency; preserve C01–C16 meanings and invent no C17. I accept M1 and M2, but do not treat the critic’s overall “no material wrong correction” conclusion as a substitute for source review.

Unresolved owner decisions:

1. Does “active diagram” mean selected objects or the whole diagram? What minimum context may accompany the selection?
2. Is user-selected file access needed in v1? Are bytes acceptable, and what size/type/retention policy applies?
3. Is no network in v1 acceptable? What later product need would justify a broker and destination review?
4. Which Windows versions and Linux kernels must support procedural extensions? Is fail-closed disabling acceptable where controls are absent?
5. Must procedural extensions support native code, or can a WASM-only tier meet the need?
6. Do unchanged grants persist across updates? Which key/identity changes require fresh trust?
7. Are updates automatic or user-confirmed? What revocation, rollback, and retention behavior is expected?
8. What startup and large-selection latency is acceptable before persistent workers are considered?

## Validation record and residual risks

**Research performed:** reviewed the assigned brief, complete investigator discovery/draft/source map/revealed plan and plan-reveal metadata, complete critic critique/source map, and both predecessor source indexes. Directly reopened the primary references listed as R01–R05 to verify the consequential isolation and transaction claims; the operations, locators, conditions, and limits are in source-map.json.

**Not performed:** no extension was installed or executed; no code was implemented; no benchmark, automated product test, Windows/Linux sandbox experiment, or production security audit was run. All scenarios and gates above are proposed work.

Residual risks include host validation and transaction bugs, runtime or host-call vulnerabilities, missing OS controls, inherited-handle authority, policy regressions across OS versions, confused-deputy behavior in brokers, package parser/signing/key compromise, and resource exhaustion outside a single quota. A later security review must examine the concrete implementation and enforcement policy on each supported platform.
