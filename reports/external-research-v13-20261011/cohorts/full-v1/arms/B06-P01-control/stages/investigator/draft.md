# Investigator draft: third-party extensions for a diagram editor

**Status:** Research-backed proposal for owner review. This is not an approved product decision or a completed security design. Research was limited to the assigned brief and released plan. Source IDs and access notes are in source-map.json; discovery.md records the pre-release research boundary.

## Recommendation

Keep built-in commands independent of all extension services. For third-party code, use a narrow, versioned request/response contract: the host sends a bounded, immutable snapshot of selected objects and the base document revision; an extension returns a declarative proposal; the host validates the complete proposal, previews it, checks conflicts, and applies it as one transaction. The extension never receives live diagram objects or mutation callbacks.

A separate worker process is useful for timeouts, crashes, and termination, but it does not remove same-user file, network, or process access. Do not describe a plain process as a security sandbox. For untrusted third-party code, require a tested enforcement layer on Windows and Linux as well as process isolation. A practical candidate is a WASM component with a deliberately tiny import set, hosted in a worker process, with explicit memory, CPU/fuel, wall-clock, message-size, and host-call limits. Pin and patch the runtime. Compare this with native workers confined by Windows AppContainer and Linux Landlock in a prototype; both platforms must enforce the promised policy. If a supported system cannot enforce the policy, disable untrusted procedural extensions there while keeping the editor and built-ins usable. Whether that compatibility cost is acceptable is an owner decision.

Offer a declarative transform format for common operations as the lowest-risk and lowest-tooling-cost path. Keep procedural extensions optional. Figma and Zed show useful manifest and authoring patterns, but their documentation does not establish a boundary suitable for this editor. A UI iframe, a permission prompt, a package signature, or a process split alone is not proof of restricted runtime access.

## Alternatives

| Option | Benefits | Limits and conditions | Disposition |
|---|---|---|---|
| Declarative transforms or constrained DSL | Small attack surface; host controls semantics and validation; can work without extension code | Cannot express arbitrary algorithms; schema and operations need versioning | Include as the preferred built-in and simple extension path |
| In-process WASM component | Typed component contract; capability access can be limited to imports; relatively direct cross-language boundary | Runtime, host callbacks, resource limits, and archive/file bridges remain security-sensitive; a runtime failure can share the host process | Prototype only; not the default for untrusted third-party code |
| WASM component in a worker process | Adds killable worker and crash/liveness separation to the narrow import model | More IPC and runtime lifecycle work; WASM is not automatically safe; limits and imports must be explicit and tested | Preferred procedural candidate, contingent on Windows/Linux enforcement and prototype results |
| Native worker with OS restrictions | Uses platform process controls; can support native languages and libraries | AppContainer and Landlock differ; policy setup and OS/kernel support need feature detection; an ordinary child process has the parent's access | Compare as an alternative; fail closed if promised restrictions are unavailable |
| Unrestricted native worker | Easier compatibility and startup | Same-user access to files, network and child processes may remain; termination only addresses liveness | Reject for third-party extensions |
| UI iframe/message bridge | Useful UI containment and serializable messages | Does not by itself restrict main-process APIs or resources fetched by the iframe; code bridges can erase the separation | Use only as a UI pattern, never as the runtime security claim |

Figma's network manifest starts from no allowed domains and supports scoped declarations and reasons, but the documented rule does not limit resources loaded by a website in the UI iframe [S01, S02]. Its messaging examples support serialized exchanges [S03]; its resource-link documentation describes forwarding fetched code through a message and evaluating it in plugin main context [S04]. These are product-specific precedents, not guarantees for this host. VS Code documents distinct extension hosts for configuration-dependent stability/performance [S05], while its runtime-security page says extensions have VS Code's file, network, and process permissions; package signing checks integrity/source, not a restricted runtime [S06]. This supports separating host placement, publisher trust, and actual permissions.

## Data exchange and proposal application

**Input scope.** Begin with selected objects, a base revision, schema/API version, and only the minimal referenced metadata an operation needs. Do not send a live document object, host service, arbitrary callback, or filesystem path. Ask the product owner whether an extension may inspect the whole active diagram or only the selection. The safer default is selection plus bounded, read-only context. If references to unselected objects are needed, expose opaque IDs and only the minimum fields; do not silently expand to the whole document.

**Optional file.** The host owns the file picker and enforces the user's choice. Pass bounded file bytes, or a one-file, read-only broker capability that cannot be used to open sibling paths; never pass the selected path as ambient filesystem authority. Set size/type limits, make cancellation explicit, expire the capability after the request, and keep the file separate from diagram-write authority. The owner should decide whether file selection is part of the initial release and what prompt/retention behavior users expect.

**Network.** Recommend no network API or network capability in v1. A manifest can describe requested capabilities, but cannot enforce them. If a later product need requires network access, deny by default and route requests through a host broker with per-extension, purpose-specific consent and enforceable destination rules; confirm the OS/runtime layer also blocks direct sockets. Decide separately whether grants persist and how they change on package updates. Figma's domain declarations are useful permission UX evidence, not a substitute for host/OS enforcement [S01, S02].

**Contract choices.** WIT offers typed interfaces/worlds for a versioned WASM component ABI; it defines the interface, not runtime behavior [S09]. Framed JSON or CBOR over a worker IPC channel is easier to inspect and can support native workers, but requires explicit schema versioning, framing, validation, and size limits. Prototype both at the same operation set. Choose based on tooling/language support, latency, compatibility, and ability to enforce the same semantics. Do not expose live references; use immutable data plus identifiers and preconditions. Figma's serializable UI messages are a precedent only [S03].

**Patch and commit.** Return a proposal with an explicit base revision, allowlisted operation types, target IDs, preconditions, and bounded payload. Treat IDs for new objects as temporary extension-local names; the host assigns canonical IDs. Validate the entire patch before showing a preview: schema/version, count and byte limits, finite numeric values, object kinds, reference integrity, allowed fields, and operation permissions. Reject the whole proposal on any invalid operation. Never partially apply it.

On commit, compare the current document against the base revision and the proposal's touched objects/fields. If relevant state changed, reject and request recomputation or show an explicit conflict review; a global revision change with no relevant conflict can be reviewed under a documented rule. Present the resulting host-computed preview and apply through a transaction with rollback/undo. If the document engine cannot guarantee all-or-none application for an operation set, reject that set rather than report a partial success. VS Code's WorkspaceEdit API documents all-or-nothing text edits but different resource-edit behavior [S07]; issue #146964 records a create/overwrite then text-edit failure that could leave an empty file and was marked patched/verified, though the exact fix was not located [S08]. Treat these as rationale for host-specific rollback tests, not a guarantee about this diagram engine.

## Runtime, permissions, updates, and operations

**Responsiveness and resource limits.** Bound startup and request wall time, CPU/fuel where supported, memory, input/output size, host calls, and captured logs. On timeout, trap, crash, protocol error, or cap violation, terminate the worker, discard its proposal, show a recoverable error, and leave the document untouched. Wasmtime describes outside-world access through imports and capability-based WASI filesystem access, with important embedder choices [S10]. Resource controls must be explicit and verified against the exact pinned runtime; the API page inspected is 51.0.0-dev, says memory is unbounded by default and the memory-size limit is per memory, so those defaults must not be projected to another release [S11]. The 2026-10-02 Preview 0 poll_oneoff advisory documents an O(n) host-work fuel bypass for embeddings enabling that Preview 0 linker API, fixed in 49.0.2; it says P1/P2/P3 were unaffected [S12]. The v49.0.2 release entry reports fixes and a signed commit prefix [S13]. Pin a reviewed runtime, enable only needed APIs, track advisories, and update promptly.

**Platform enforcement.** Linux Landlock is unprivileged self-restriction, but rights depend on ABI and pre-opened descriptors and special /proc resources need care [S14]. Windows AppContainer can restrict file, network, and process access, with brokered resources and granular grants [S15]. These are candidate mechanisms, not evidence that a proposed policy already works. Build an explicit capability matrix for supported OS versions and test the actual launched worker and inherited handles. The host should open only brokered resources, close inherited descriptors/handles, and fail closed when a required restriction is unavailable.

**Startup mode.** Start with one worker per request as the simpler lifecycle and failure-reset model. Measure cold launch, typical and large selections, and peak parallel work on Windows and Linux. Compare persistent workers only if measured startup hurts responsiveness; if adopted, clear state between requests or isolate worker instances and ensure a worker cannot retain another document's data or grants. This is a product/performance decision after measurement, not a research finding.

**Grants.** Separate publisher trust from resource grants and from OS enforcement. Store grants against extension identity, version/API, and the specific requested capability. Recommend prompting again for any added capability, publisher identity/key change, or material scope change; never infer that a newly requested capability is already granted. Owner decision: whether unchanged grants survive routine versions, how revocation/expiry works, and whether the prompt can be remembered. A selected-file grant should be request-scoped even if other grants persist.

**Packages and updates.** Use host-controlled package processing; do not run extension-supplied installers or scripts. Verify publisher/package integrity before staging. Extract to a new private directory with strict path normalization, reject absolute/traversal paths and symlinks or links that escape the package root, cap expanded bytes/file count, then atomically activate and retain a rollback path. Zed's advisory documents an extension-workdir escape through tar symlink handling and identifies the fixed release range [S17]. Its v0.224.4 source/tests show ZIP path checks for traversal cases, while the inspected tests do not cover the tar symlink case [S18]. Its WASM host source also illustrates that preopens and inherited stdio are embedder choices [S19]. These examples motivate tests; they do not establish the new updater's safety. TUF describes rollback, freeze, mix-and-match, endless-data, key-compromise, and related update threats [S20]; adopt it only if the registry and key-management model justify the additional roles and metadata.

## Disposition of the released plan

| Released clause | Disposition | Review result |
|---|---|---|
| Run each extension in a separate process | **Correct** | Keep worker isolation for responsiveness and termination; explicitly reject the inference that process separation limits same-user OS access. Require tested OS restrictions or a tightly imported WASM runtime plus platform enforcement for untrusted code. |
| Send selected-object snapshot and document revision | **Accept with scope decision** | Use immutable, bounded snapshot plus base revision. Owner must choose selection-only versus whole-diagram inspection and approve any referenced context. |
| Extension returns a patch, not live mutation | **Accept** | Return a declarative proposal; no live host object or mutation API. |
| Validate object types, identifiers, operations before preview | **Accept and expand** | Validate all schema, limits, IDs, references, values, preconditions, and permissions before preview; reject whole proposal on any error. |
| Changed revision prompts retry or explicit review | **Refine** | Compare touched objects/fields and preconditions; on conflict, recompute or explicit review. Define any safe no-conflict continuation; do not blindly commit against changed state. |
| Built-ins do not depend on extension startup | **Accept** | Keep startup, failure, timeout, and update paths independent of built-in editor functions. |
| Manifest declares file-read/network capabilities | **Correct** | Manifest is declaration/consent metadata, not enforcement. Host broker and OS/runtime policy enforce access; deny by default. |
| Pass only selected file path | **Reject path handoff; preserve optional file input** | Host picker plus bounded bytes or a one-file read-only capability. Never grant arbitrary path traversal or general filesystem APIs. Decide whether file input ships in v1. |
| Omit network APIs in first SDK | **Accept as recommendation** | No network in v1. Revisit only for a named product need, with explicit owner approval and host/OS enforcement. |
| Process split is sufficient; OS restrictions unselected | **Reject** | Responsiveness containment and permission containment are separate. Select and verify platform restrictions before shipping third-party code. |
| Remember permission prompts locally per extension | **Refine; owner decision remains** | Separate publisher trust from capability grants; bind grants to identity/version/scope. Ask whether unchanged grants persist and define revocation/expiry. |
| Version grant inheritance and file-selector boundary unspecified | **Resolve partly; owner decision** | New/expanded capabilities or changed publisher identity require renewed consent. File access is request-scoped. Owner decides retention for unchanged permissions. |
| Timeout, patch-size limit, terminate failed workers | **Accept and expand** | Also cap memory, CPU/fuel, host calls, logs, concurrency, input bytes, and startup; discard all output after failure. |
| Measure launch overhead and large selections | **Accept** | Benchmark cold start and representative selection sizes on both OSes before committing to worker pooling. |
| Choose per-request vs persistent worker later | **Accept as open engineering choice** | Prefer per-request initially for state reset; use persistent workers only if measured latency justifies isolation and reset complexity. |
| Host unpacks known package; no custom installers | **Accept and expand** | Host verifies and safely stages packages with traversal/link/size defenses, atomic activation, and rollback; never execute installer scripts. |
| Proposed looping/malformed/stale/file/network/upgrade tests | **Accept and expand; not run** | Add import denial, memory/fuel/host-call floods, process kill, invalid references, size caps, all-or-none rollback, file-picker cancellation/limits, package traversal/symlink/zip-bomb, downgrade/freeze/revocation, and rollback cases. |
| No extensions installed and no isolation test executed | **Preserve exactly** | This review installed or ran no extension and executed no product validation or security audit. |
| Separate responsiveness from enforceable permissions and residual risks | **Accept** | State worker-process benefits separately from OS/runtime policy; list host bridge, runtime, update pipeline, OS-version, and policy gaps as residual risks until tested. |
| Provisional plan and open user-data questions | **Preserve** | Recommendations above are proposals. Product scope, permissions, compatibility, and update behavior still require owner decisions. |

## Owner decisions to carry forward

1. Should an extension see only selected objects, or the full active diagram? What minimum context may accompany a selection?
2. Is user-selected file input required for v1? If so, are bounded bytes acceptable, and what file size/type prompt should the host enforce?
3. Is a no-network v1 acceptable? If later network is needed, who approves destinations and remembered grants?
4. Which OS versions must run procedural extensions? Is disabling untrusted procedural code when enforcement is unavailable acceptable?
5. Should extensions ever run native code, or should v1 procedural extensions be WASM-only?
6. Should grants for unchanged capabilities survive an extension update? What identity changes force a fresh trust prompt?
7. Should updates be automatic or user-confirmed, and what rollback/retention period is required?
8. What startup/selection latency is acceptable before considering persistent workers?

## Validation record

**Executed during this assignment:** reviewed the primary-source material indexed as S01–S20 and prepared this proposal. The plan-reveal helper ran once and supplied the released plan. No implementation, test suite, benchmark, sandbox experiment, extension install, or security audit was run.

**Proposed before release:** Windows and Linux policy tests for blocked ambient file/network/process access; missing OS feature behavior; inherited handle closure; worker loop, crash, trap, timeout, memory/fuel/host-call floods, oversized and malformed IPC; invalid object/reference/operation; stale revision and overlapping edits; preview/commit rollback proving no partial application; optional-file cancel, size/type, expiry and sibling-path denial; archive traversal/symlink/zip-bomb, signature/key change, downgrade/freeze, incompatible update, activation rollback; built-in command behavior during worker failure. Add Windows/Linux launch and large-selection benchmarks before choosing a persistent pool. These are plans, not results.

**Residual risks:** correctness bugs in host validation or transaction rollback; runtime and host-call vulnerabilities; platform policy differences and unsupported OS versions; overly broad brokered handles; update signing/key compromise and archive parsing; resource exhaustion not captured by one quota; confused-deputy behavior in host services. A future security review must test the concrete implementation and policy on each supported platform.
