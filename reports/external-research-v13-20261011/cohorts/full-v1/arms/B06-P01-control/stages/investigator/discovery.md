# Independent discovery — extension isolation for a diagram editor

## Scope and working interpretation

This is a research-backed proposal, not an implementation. A user initiates an extension for a diagram context. It reads the active diagram, computes a transformation, and returns a proposal. The host must stay responsive and built-in commands must remain available when an extension is absent or fails. Windows and Linux are required, with host and guest languages undecided. Third-party code is potentially hostile: no ambient filesystem/network access, no custom installer, and no direct or partial writes to the live model.

The phrase “read access to the active diagram” is ambiguous against the brief’s opening emphasis on selected objects. Carry an owner decision: whether the normal scope is the selected objects or the whole diagram. Conservative default for discovery is selected objects, with an explicitly described whole-diagram read capability if a real extension requires it.

## Candidate execution models

1. **Declarative transforms or a restricted DSL.** The host parses bounded data and executes a small allowlisted operation set. This has the least runtime and easiest cross-platform testing, and supports common transforms. It does not fit arbitrary computation or extensions that need established language ecosystems. Keep it in the comparison rather than assuming arbitrary code is essential.

2. **WebAssembly Component Model guest with a narrow host API.** WIT describes typed imports/exports and contracts; guests can use only linked host functionality. The host can expose snapshots, an explicitly selected file stream/opaque handle, and proposal submission while omitting filesystem/network interfaces. Wasmtime documents memory isolation and capability-style WASI filesystem access, but the embedder chooses what to expose and must configure resource bounds. An embedded runtime is not automatically a process boundary; running it on the UI thread can still freeze the host. Current StoreLimitsBuilder documentation says linear memory is unlimited by default and its configured limit applies to each memory; that page is Wasmtime 51.0.0-dev, so verify exact behavior against a pinned shipping release before relying on values. [S09–S11]

3. **Dedicated worker process with framed JSON/CBOR IPC.** This supports more guest languages and native dependencies, and contains ordinary guest crashes. A child process without OS policy may retain the user’s filesystem and network rights, so process separation alone is not a complete security boundary. For native guests, Windows AppContainer can restrict file/network/process resources; Linux Landlock can restrict file hierarchies, with seccomp reducing allowed syscalls. Enforcement and compatibility differ by OS and kernel. Landlock’s documentation calls out ABI-dependent coverage, special-resource limitations, and the fact that descriptors opened before confinement retain their access properties. [S14–S15]

4. **WASM runtime inside a dedicated worker process.** This combines a portable component ABI with a process boundary for host responsiveness/crash containment, plus OS restrictions for defense in depth. It costs IPC, duplicated limit/monitoring work, and more packaging/debugging. It is a strong candidate for a hostile third-party threat model, but should be benchmarked against in-process WASM and a declarative tier before selection.

Figma’s manifest/UI docs show declared network domains, visible reasons, and serializable messages between plugin logic and an iframe. They also say network limits do not affect resources loaded by a rendered website; another page describes fetching script in the iframe and passing it back to the plugin main context for eval. The UI/message split is a useful data-flow pattern, not proof of a separate security boundary. [S01–S04] VS Code uses a separate Extension Host for stability/performance, while its security docs say extensions have the same permissions as VS Code, including file, network and process access. Publisher trust prompts/signatures are trust and supply-chain indicators, not least-privilege runtime controls. [S05–S06]

## Read and update contract

Give a guest an immutable, versioned snapshot with document ID/revision, selection IDs, and only fields its read capability permits. Do not hand out live model pointers or callbacks that permit direct mutation.

Return a bounded proposal: schema version, base revision, operation list, target IDs, and payloads. The host must parse and validate the entire response first: byte/depth/count caps, known object/property IDs, allowed operations, valid references and diagram invariants. At commit, compare the base revision with current state and detect overlap on every target object/field changed since the snapshot. If a write overlaps a human edit, an ID disappeared, history is unavailable, or validation fails, reject the whole proposal and report that nothing was applied. A pure-add proposal may be accepted after collision and global constraint checks. Commit accepted proposals as one host transaction/undo step; show the readable diff and explicit Apply/Discard actions first. This is a proposal, not an implemented transaction.

Do not assume an API version check guarantees safe commit. VS Code documents an all-or-nothing strategy for text-only workspace edits and abort behavior for resource operations, while its issue #146964 records a create-then-edit case that left an empty file when applyEdit returned false. The issue is closed/labeled patched in Insiders and verified; this pass did not locate its specific PR/release note. Use it as a regression-testing precedent, not proof that all editor edit APIs are unreliable. [S07–S08]

## Permission presentation and failure handling

- Start with read access to the chosen diagram scope and proposal submission. Proposal submission is not permission to edit the live model.
- Default filesystem and network access to none. The host owns the native file picker. If the user opts in, pass only that file’s bytes or one-file capability, with size/lifetime bounds. Do not expose a home-directory path, arbitrary open/read API, inherited handles, or directory walking.
- If network support is later needed, require a declared purpose and exact host allowlist, disclose it before install/use, and enforce it in the host/runtime. Figma’s none/exact-domain patterns and displayed reasons are useful UX precedent; its iframe-resource caveat limits what can be inferred from a manifest alone. [S01–S02]
- Keep permissions separately revocable. Trusting an author does not silently approve more data access. An update that requests additional capability needs a fresh plain-language prompt.

Run guest work off the UI thread or in a worker process with cancellation and CPU/time, memory, response-size, nesting, and host-call budgets. Show understandable failure states: timeout/stopped, guest crash/trap, denied permission, malformed response, validation rejected, revision conflict, or update unavailable. Include extension name, operation, next action and “No changes were applied” if commit did not occur; keep diagnostics behind a disclosure control and redact diagram contents. Built-in commands need an independent registration path so an extension loader failure cannot disable them.

## Versioning and updates

For small independent teams, prefer a declarative manifest and immutable, versioned package, not author scripts. Record extension ID/version, supported host/proposal schema range, publisher/signing identity, declared capabilities/reasons, artifact digest, and release notes. Download to a staging area; cap download and expansion size; reject absolute/traversal paths and unsafe links; validate the complete package and signature before activation; then atomically switch to the new version while retaining a known-good version for rollback. Do not run postinstall, custom installers or extension-authored update code. Capability increases require user review.

Consider a TUF-style repository if the public ecosystem grows. TUF describes rollback, freeze, fast-forward, endless-data, mix-and-match and key-compromise risks that one package signature does not address, but adds metadata roles and key-lifecycle burden. [S06, S17–S20]

Zed is a useful desktop-editor comparison. Its current authoring docs use Rust wasm32-wasip2 for procedural extensions and describe extra Rust/toolchain needs for custom code; this is portable but narrows casual guest-language choice and adds debug burden. Source at release tag v0.224.4 preopens an extension workdir with full file/dir permissions and inherits stdio, showing that WASM capability breadth is chosen by the embedder. The same tag includes archive path checks and ZIP traversal tests. Zed advisories report tar-symlink and zip-slip escapes in earlier releases, fixed from v0.224.4; the inspected archive regression test covers ZIP paths, not a tar-symlink case. Treat these as evidence for separately testing host APIs and package handling, not as a production audit of Zed or this proposal. [S16–S19]

Wasmtime’s October 2026 advisory reports a WASI Preview 0 poll_oneoff path that bypassed fuel accounting, fixed in 36.0.17, 48.0.4 and 49.0.2. It applies only to embeddings enabling the Preview 0 linker API; the advisory says P1/P2/P3 are unaffected. Pin and patch the runtime, expose only required imports/versions, and test every host call’s bound. Fuel is a defense, not a substitute for reviewing host calls or process/OS containment. [S10, S12–S13]

## Discovery questions and proposed validation

- Compare declarative/DSL, in-process WASM, WASM worker process, and native worker plus Windows/Linux sandbox. Score boundary, loop/crash response, language/toolchain burden, data-copy cost, portability/feature availability and update operations.
- Compare WIT calls with framed JSON/CBOR IPC; compare selected-object snapshot, full-diagram snapshot, opaque host handles, and serialized data. Preserve the live-mutation prohibition across all choices.
- Carry two owner questions: read scope of “active diagram,” and whether network access is entirely excluded from v1 or is an optional capability requiring approval.
- Proposed tests: infinite loop, memory growth, host-call flood, trap/panic, worker kill, oversized/malformed output, forbidden import, missing OS sandbox/kernel feature, file-picker cancel/replacement/oversize, stale snapshot, overlapping human edit, invalid object reference, atomic rollback, archive traversal/symlink/zip bomb, downgrade/freeze/revocation, update failure rollback, and built-ins after extension load failure. Run Windows/Linux smoke tests plus deterministic fake-extension tests before a public gallery. Independent security review is a future gate.
