# Draft plan: Extension isolation for a diagram editor

The draft runs each extension in a separate process and sends a serialized snapshot of selected objects plus a document revision. Extensions return a proposed patch rather than mutating the diagram directly. The host validates object types, identifiers and allowed operations before presenting a preview. A changed document revision prompts a retry or explicit review, and built-in commands do not depend on extension startup.

A manifest declares file-read and network capabilities. The first version plans to pass only a selected file path and omit network APIs from the extension SDK. It assumes this is sufficient because extensions live outside the host process; actual operating-system restrictions remain unselected. Permission prompts are per extension and remembered locally. The draft does not yet specify whether new versions inherit grants or how a file selector's permission is represented across the boundary.

The host sets a timeout, limits returned patch size and terminates failed workers. Launch overhead and repeated large selections need measurement before choosing per-request or persistent workers. Extension updates are unpacked by host code from a known package format; no custom installers run. Proposed validation includes looping workers, malformed patches, stale revisions, attempted access outside the selected file, blocked network requests and incompatible package upgrades. No extensions have been installed and no isolation test has been executed. A recommendation should separate responsiveness containment from enforceable permission guarantees and identify residual risks.

This is a provisional draft for review after the declared reveal, not an endorsed answer. Resolve material assumptions through applicable primary evidence; retain open user-data questions when they cannot be answered from sources. No future product deployment is requested.
