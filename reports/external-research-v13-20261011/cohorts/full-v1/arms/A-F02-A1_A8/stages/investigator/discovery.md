# Brief-only discovery — before exact-plan release

## Scope captured from the released brief
This proposal concerns a volunteer workflow for accepting or rejecting donated oral-history recordings, with an existing catalog but no fixed catalog API or codec. Inputs may include audio, an optional transcript, and a spreadsheet of recording IDs and permissions. Extensions are inconsistent; some files have two channels carrying different speakers; corrected transcripts can arrive after intake. Required coverage: format identification; technical metadata and duration; channels; transcript association; restart after interruption; portable catalog handoff; accessible keyboard review with textual status. Warnings must distinguish unreadable media from unsupported preview, and absent transcript from failed audio. Preserve media bytes; do not infer missing rights; do not send audio to cloud transcription; do not make a transcode prerequisite for cataloging. Batch size is normally 40 and may be 500. This is a proposal, not a collection migration. Exact plan is not yet released.

## Candidate approaches and evidence
**FFprobe / libavformat.** An input-only ffprobe job can emit selected container and stream fields as JSON, including stream errors, without creating a replacement media file. Its machine-readable output and field selection are explicit in the n8.1.1 manual [SRC-01]. FATE tests exercise JSON and other writers against a synthetic multi-stream fixture [SRC-02], useful evidence that output formatting is regression tested, not a guarantee that every museum file is supported. Support is bounded by demuxers/parsers present in the chosen build. Probing is bounded: probesize defaults to 5,000,000 bytes and analyzeduration to 5,000,000 microseconds; increasing them can expose more dispersed information at a latency cost [SRC-03]. Therefore a missing stream/field is “not reported by this probe,” not proof the source lacks it. Keep raw tool output, build identity, config, and per-field provenance. Do not treat header-derived duration as a verified listening duration.

**MediaInfo / MediaInfoLib.** This track-oriented alternative exposes channel count, positions/layout, sample rate, and sample count as distinct fields in its field definitions [SRC-05]. The v26.10 release history shows recent MP3 VBR and Opus channel-order fixes [SRC-04], so pin and record the parser release and test the museum's examples. Its history also has a real QuickTime report in which container and audio-track durations differ [SRC-06]; preserve competing duration facts/source and flag disagreement for review. CLI JSON cardinality has had a one-file-object versus multi-file-array issue and a proposed normalization PR that remained open at access [SRC-07]. A wrapper should normalize output or call one file at a time and validate schema against the selected release. It is a candidate, not a universal support claim.

**Signature identification.** Siegfried v1.11.9 identifies by PRONOM/MIME-info/LOC signatures and can produce JSON or DROID-style CSV [SRC-08]. This complements a media parser: a format identifier answers “what signature matched?”; it does not establish decodability, duration, or previewability. Its docs state that the default uses latest PRONOM signatures without a buffer limit and may scan the full file, so record the exact signature-file version/hash and measure 500-file throughput. “Unknown/ambiguous signature” must remain a format-identification status, not an unreadable-media result. Extension is only a hint.

**Narrow audio API alternative.** libsndfile 1.2.2 provides frames, sample rate, channel count, and format through SF_INFO; its read path accepts SFM_READ, while RAW input requires caller-supplied sample rate, channels, and format [SRC-09]. Its explicit supported-format matrix makes it attractive for a known PCM/WAV/AIFF/FLAC-heavy collection, but a limited decoder matrix is a poor sole intake gate when no codec is fixed and extensions are unreliable. In particular, never guess RAW parameters.

## Design hypotheses to compare after plan release
Use a local, non-destructive session. Hash originals on intake; retain source path, size, modification facts, and SHA-256. Probe a copy or read-only handle; never write metadata back to originals. Treat extension, signature identity, parser success, stream metadata, and preview availability as separate facts. Store raw and normalized duration separately with source field/tool/version; missing or conflicting values are warnings for staff, not silent normalization. Preserve the original multi-channel stream and its reported channel order/layout. Expose channel count and any known positions; label unknown channels by ordinal. Do not claim channels map to named speakers. Offer per-channel audition only where playback support can isolate the selected channel without altering the archived source; otherwise offer whole-file preview and a textual note.

Keep three outcomes independent: staff intake decision (accepted / held / rejected), media inspection state (readable / probe failed / unidentified / incomplete), and preview state (available / unsupported / not attempted). A genuinely failed read/probe should say “Media could not be read/probed”; a parser-successful file whose selected playback engine cannot play should say “Preview unavailable for this format”; neither should be encoded only by color or icon. An absent transcript is “No transcript supplied,” separate from media/audio status. If a transcript arrives later, add a versioned correction linked to the same recording ID and media hash; do not replace prior text or guess associations.

Import spreadsheet IDs as strings to preserve leading zeroes. Let staff map columns; preserve the raw cell, source row, and permission value. Join only on an exact configured recording ID. Duplicate, missing, or conflicting IDs/permissions/transcripts go to an explicit review queue. Unknown rights remain unknown and block any use/export that requires a rights decision; recording acceptance is not a rights grant. Transcript/media mismatch is not a fuzzy-match candidate. No automatic transcription or network upload.

For restart, checkpoint each recording independently with stable intake ID, source hash, tool/config version, and states such as discovered → identified → probed → linked → reviewed → exported. Commit results per item; resume completed items only when the source fingerprint and configuration still match. A changed file or correction starts a new version; a retry is idempotent and never duplicates an accepted catalog row. Keep checkpoint state outside source media. Batch throughput and crash-safety are proposals to validate, not observations from a museum collection.

For handoff, propose an open directory package with the untouched source bytes (copied byte-for-byte if recipient needs a portable bundle), versioned transcript, permissions as supplied, normalized manifest plus raw provenance, and checksums. BagIt RFC 8493 v1.0 is a fit to test: required payload manifest lists every payload file and checksum, while payload files are opaque octet streams; checksum validation is required before calling a bag valid [SRC-11]. A JSON manifest plus CSV staff view can defer catalog-specific mapping; a later adapter is only selected after catalog owner/API decision. Do not assume the catalog accepts BagIt or a particular field vocabulary.

Accessibility is a product requirement, not an implementation assumption. For a web UI, WCAG 2.2 requires keyboard operation (2.1.1), semantic name/role/value (4.1.2), and programmatically exposed status messages (4.1.3); keyboard focus must remain visible and not become trapped [SRC-10]. Map equivalent accessibility APIs if a native desktop is chosen. Include a visible, text-backed queue count, focused item identity, detailed error/reason, and non-color status; all review, association, channel-selection when available, accept/hold/reject, and export actions need keyboard paths.

## Unresolved choices and proposed validation (not executed)
No codec, target OS/UI framework, metadata schema, permission vocabulary, catalog API, transcript file standard, preview policy, or maximum audio size is specified. The plan should distinguish owner decisions from safe defaults. Do not select a parser by popularity. Proposed pilot comparison: known-good and deliberately mislabeled audio; each candidate's supported demuxer/format matrix; corrupt/truncated/empty/unrecognized inputs; duration conflicts and long/VBR recordings; dual-channel speakers with known order; duplicate IDs, leading-zero IDs, missing/conflicting rights, absent and corrected transcripts; stop/restart at every state; byte hashes before/after and against export copies; portable handoff checksum/import; keyboard-only and screen-reader status; 40- and 500-item responsiveness. No such tests or repository changes were executed during discovery.
