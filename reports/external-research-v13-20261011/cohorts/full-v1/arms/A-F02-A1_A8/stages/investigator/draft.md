## Proposal

Use a local, versioned intake session that preserves every supplied file and records a staff decision separately from technical probe and preview outcomes. Create a manifest row for each spreadsheet recording identifier before probing. Preserve the identifier and permission text as supplied, record the source file path, and make a byte-for-byte staged copy with SHA-256 verification before passing the staged copy to a read-only probe. No operation writes tags into the original. Keep the original and any correction history; do not use a converted preview as the accepted archival object.

Do not select a winning parser before the museum supplies a representative, rights-cleared test set. Put the probe behind a small adapter so FFprobe/libavformat and MediaInfoLib can be compared against the same records. An optional signature-identification step such as Siegfried/PRONOM can add a preservation format identity, but it is not a readability or preview test. A narrow decoder such as libsndfile may be suitable if the eventual collection matrix is limited, but it cannot be the sole gate while codecs and extensions are unknown. This composable design is a recommendation; the parser choice remains an owner decision.

Keep these facts distinct for every item:

| Axis | Example values | Meaning |
|---|---|---|
| Staff intake decision | Pending, Accepted, Held, Rejected | Human decision about the donation item; never inferred solely from parser or preview results. |
| File access / probe | Readable, Read error, Probe error, Unidentified, Incomplete fields | Whether bytes could be opened and which facts a particular parser reported. A format unknown to a signature tool is not itself proof of unreadability. |
| Preview | Available, Unsupported for selected player, Not attempted | Whether this configured playback path can play the staged original. It does not change acceptance by itself. |
| Transcript | Supplied, No transcript supplied, Correction received, Association needs review | Text availability and linkage, independent of audio health. |
| Permission | Supplied value, Missing/unknown, Conflicting, Needs owner review | Rights state as supplied. Unknown does not become permission by normalization or acceptance. |

A file whose read/probe actually fails should carry a textual status such as **“Could not read or probe this media file; original preserved.”** A parser-successful file that the preview engine cannot play should say **“Preview unavailable for this format; metadata was read. Preview is optional.”** An absent transcript should say **“No transcript supplied.”** Keep these as separate fields, rows, and accessible messages; do not encode them only with color, icons, a blank cell, or a generic “failed” badge. A probe can identify a container while a codec is unsupported by the chosen preview engine; conversely a parser failure can reflect an unsupported parser, damaged bytes, or access failure. Preserve the diagnostic and avoid asserting corruption unless the evidence supports it.

## Format, metadata, and alternatives

FFprobe/libavformat is a strong candidate for an open structured report: n8.1.1 documents JSON output, selected stream/container sections, and an error section; the FATE target exercises JSON against a generated multi-stream sample [SRC-01, SRC-02]. Its documented default probe limits are 5,000,000 bytes and 5 seconds. Higher limits may reveal more dispersed information but cost latency [SRC-03]. Consequently a missing field or stream is “not reported by this run,” not proof that the file contains none. The installed build also bounds actual coverage. Record executable/library version, build configuration, options, raw JSON, exit status, and diagnostics; confirm the selected build’s demuxer/codec capabilities during the pilot.

MediaInfo/MediaInfoLib exposes separate audio fields for channel count, channel positions/layout, sample rate, and sample counts [SRC-05]. Its v26.10 notes include recent MP3 headerless-VBR and Opus channel-order fixes [SRC-04], evidence that relevant edge behavior changes by release and belongs in regression fixtures. Its issue history records QuickTime files whose container and track durations differ [SRC-06]. Preserve each duration value with its source field and scope (container, stream, or derived sample count); if they disagree beyond a chosen tolerance, report the conflict and have staff review it. Do not silently select one value or call any header value verified listening time. A sample-count/rate comparison can be a secondary consistency check only when both values are present and their semantics are known. MediaInfo’s CLI JSON has also had different top-level shapes for one input versus multiple inputs; the proposed normalizing PR #2295 was still open when reviewed [SRC-07]. Use a per-file invocation or normalize and validate the JSON schema with the deployed release.

Siegfried v1.11.9 can identify signatures from PRONOM, MIME-info, and Library of Congress FDD data and write JSON/CSV/DROID output [SRC-08]. Keep it separate from the media probe: signature identity cannot establish decodability, duration, speaker mapping, or preview support. Its default uses latest PRONOM signatures without a buffer limit and may scan the whole file. Pin and record the signature database file version/hash in addition to the binary, then measure elapsed time on the museum-sized batch. An unknown or ambiguous signature should be visible, not converted into “unreadable.”

libsndfile 1.2.2 offers a compact read API exposing frames, sample rate, channel count, and format in SF_INFO. Its documentation calls out RAW as an exception: the caller must supply valid samplerate, channel, and format values [SRC-09]. That makes it a useful alternative for a known supported-format subset, not a safe general solution for this unknown-format intake. Never guess RAW parameters. The acceptance rule should be based on demonstrated parser/build coverage for the museum’s corpus, not the filename extension or a product’s general format-count claim.

For all approaches, treat the file extension as a label to compare with content, not as authority. Keep signature result (including mismatch/unknown), parser result, format/container name, audio codec, sample rate, channel count/layout, raw duration fields, normalized duration, source field, tool version, and diagnostic separately. A successful probe is not a full integrity or perceptual review. A metadata report may reflect a container header, an estimate, or a specific stream; record that provenance.

## Identifier, transcript, permission, and channel rules

Read the spreadsheet using its explicit cell types and preserve the raw identifier cell as text. Ask staff which column is the canonical recording ID and retain its source sheet/row. Do not coerce identifiers through numbers, strip leading zeroes, or silently lowercase/delete spaces. Exact equality under the staff-selected rule is the default join. The plan’s lowercase-and-remove-spaces filename-stem rule can collapse distinct identifiers and has no corpus evidence. Until staff confirms uniqueness, treat normalized filename matching only as a suggestion that requires confirmation. Show duplicate, missing, or conflicting IDs in a review queue rather than auto-linking them. A file path or transcript filename is not the identity of the donation.

A corrected transcript creates a new version linked to the same confirmed recording ID. Retain the earlier file, hash, arrival/provenance, and association as history; update the current pointer only after staff confirmation. Do not replace or delete the prior transcript. If the transcript itself has an ID mismatch, multiple possible rows, or uncertain filename normalization, hold the link for staff. Represent “No transcript supplied” as an ordinary availability state, not an audio error. For transcripts with supplied timing, preserve it as delivered. W3C WebVTT gives cues explicit start/end timestamps relative to media playback [SRC-13]; that supports synchronized display when such a timed track is already supplied. Plain text has no cue timing, so do not invent alignment, run speech recognition, or silently convert it into timed text. Whether the museum needs synchronized transcript display, and which supplied transcript formats must be accepted, remain open decisions.

Retain the permissions text verbatim and preserve its spreadsheet location. Do not infer a permission from a blank, a filename, an adjacent row, a transcript, or a staff intake acceptance. Missing, contradictory, or unmapped permission values stay unknown and block any release or use that requires that rights decision. Separate “accepted into the museum’s intake/catalog” from “authorized for public access or other reuse.” No audio is uploaded for cloud transcription; no new transcript is generated by this proposal.

Do not downmix or rewrite a two-channel original just to simplify review. Display stream count, channel count, reported layout, and channel order when known. Where layout is missing or ambiguous, label channels only by ordinal (Channel 1, Channel 2) and do not guess which speaker is on which channel. Give staff a whole-file preview when supported. Research confirms that, in a web implementation, Web Audio’s MediaElementAudioSourceNode and ChannelSplitterNode can route individual decoded channels in the live audio graph [SRC-12]. Thus isolated channel audition does not inherently require writing a converted preview file when the browser can decode the original. It does not make an unsupported codec playable. For a native client, validate equivalent routing in its chosen decoder/player. If that path is unavailable, show the channel metadata and an explicit preview limitation. An on-demand derivative can be considered only as a separately labeled convenience copy after owner approval; it never replaces the original and is not a prerequisite for cataloging.

## Restart, export, and integration

Store progress per item, not only as a final “batch complete” flag. Candidate states are: staged/hash-verified → identified → probed → transcript-linked → staff-reviewed → exported. Each record holds a stable intake UUID, exact source ID, source path, original/staged SHA-256, sizes, source-sheet row, transcript hash/revision, permission provenance, parser/signature versions and configuration, statuses, staff action, and timestamps. Store raw parser output and errors with the record. Keep this operational state outside media bytes.

A local SQLite database with a transaction per item is one feasible checkpoint; an append-only JSON journal is another. SQLite documents that write transactions do not nest, only one writer can be active, and lock contention can produce SQLITE_BUSY [SRC-14]. Keep batch writes serialized or explicitly retry transient busy conditions. In either design, a database transaction cannot atomically include copying a media file or importing a record into an unspecified catalog. For a safe retry, copy to a staging name, hash-check before marking the item complete, and reconcile partial/orphan staged files by relative path and hash on resume. The stable idempotency key should include batch ID, recording ID, and source hash. If the ID maps to different bytes later, preserve both versions and hold for staff instead of overwriting. If a transcript correction arrives, create another transcript version and preserve history. Do not emit duplicate catalog rows on re-export; the eventual catalog adapter needs an agreed upsert/idempotency contract.

For portable handoff, export a directory package with a manifest and relative references plus the actual media and transcript files needed by the recipient. References alone to the workstation’s absolute paths are not portable; a receiver cannot resolve them after the folder moves. Copy accepted originals byte-for-byte into package payload (or obtain an explicit owner decision that a non-portable pointer package is acceptable), and verify the copy hash. Give assets collision-safe generated paths rather than overwriting on duplicate basenames. Include the confirmed ID, original relative path, media hash, signature/probe facts and provenance, independent preview/transcript/permission/review statuses, transcript revision history, and staff decision. BagIt 1.0 is a candidate package convention: its data directory holds opaque payload bytes and its manifest lists each payload file with a checksum; a bag is not valid until the manifest is verified [SRC-11]. Apply its path-safety rules to imported manifest entries. BagIt does not define oral-history rights or transcript semantics, and the catalog is not known to accept it. A JSON manifest (plus a staff-facing CSV view) can form the stable interface; write a catalog-specific adapter only after the catalog owner supplies its schema/API and import semantics.

Deliver the work in stages:

1. **Field agreement:** confirm canonical ID column and cell types, permission vocabulary, transcript formats and revision practice, UI target, maximum item size, catalog ingest shape, and whether timed transcripts/channel audition are required. Preserve unknowns; do not inspect or migrate the collection as part of this proposal.
2. **Local intake pilot:** create manifest rows and byte-verifying copies; compare FFprobe and MediaInfo on a rights-cleared representative corpus. Freeze tool versions, build/config, and signature database. Keep preview optional.
3. **Review flow:** show parser/probe and player statuses separately; let volunteers inspect audio and channels when possible, link transcripts by confirmed ID, see supplied rights, and choose accept/hold/reject. Maintain a persistent decision trail.
4. **Portable export:** generate a directory handoff with relative paths, original-byte copies, transcript revisions, metadata provenance, and SHA-256 manifest. Add the actual catalog adapter only after an owner-approved dry-run contract.
5. **Validation and rollout:** run the proposed checks below before deciding whether the pilot can expand from the normal 40-item batch to 500. This stage has no implemented result.

## Accessibility and textual progress

Make every review action available from the keyboard: move through items, open details, listen/pause/seek where supported, choose a channel when available, associate or review a transcript, inspect permission text, and accept/hold/reject/export. Keep a visible focus indicator and a path out of every control; do not make color, hover, drag, or single-key shortcuts the only route. Give each control an accessible name/role/state and expose text values. These are concrete proposals based on WCAG 2.2 keyboard, focus, and name/role/value criteria [SRC-10].

Resolve the plan’s screen-reader announcement question with a low-interruption model: maintain the current item’s textual state in the interface and expose state changes programmatically without moving focus. Announce concise, polite changes (for example, “12 of 40 inspected; 2 need review”) at meaningful batch intervals and when the focused item changes. Do not generate one urgent alert per item for a 500-file batch. Keep a visible log and per-row text so volunteers can review missed announcements. In a web implementation, use the appropriate accessible status semantics and verify them with assistive technology; for a desktop implementation, use the platform’s accessibility API. W3C guidance distinguishes status messages that can be programmatically announced without focus from interactions that require focus [SRC-10]. Announcement timing and verbosity should be tested with volunteers and a screen reader rather than guessed.

### Disposition categories, already-covered points, and remaining uncertainty

- **Already covered and retained:** byte preservation, optional preview, unknown permission blocking rights-dependent release, no cloud transcription, keyboard operation, and no collection migration/deployment. The clause table preserves each of these and makes acceptance, rights, probe, preview, and transcript states explicit.
- **Corrections / rejected assumptions:** reject lowercasing/removing spaces as an automatic transcript join until uniqueness is evidenced; reject replacing the active transcript without a versioned, staff-confirmed link; reject treating references to workstation paths as a portable handoff; reject equating parser failure, unidentified format, and unsupported playback. A format extension and a “normalized” name are not verified identity.
- **Optional improvements, not brief requirements:** add PRONOM signature identity beside a media parser; use a BagIt directory to package original-byte copies and checksums if the catalog owner accepts it; use a local SQLite checkpoint or JSON journal; offer live isolated-channel preview on a decoding-capable platform; create an on-demand derivative only if separately approved; add a staff CSV view beside JSON. None is required for cataloging the original.
- **Owner decisions:** canonical ID/cell rules, permission meaning, target UI/platform, required transcript formats and synchronization, required channel audition, storage/retention limits, whether portable package copies are acceptable, and catalog adapter/upsert behavior. Do not manufacture these answers from generic documentation.
- **Evidence-backed limits and open technical uncertainty:** probe defaults can omit later/dispersed information; parser fields and duration values are format/version-dependent; signature database version must be frozen separately from Siegfried’s binary; browser channel splitting only applies after the browser decodes the original. No museum corpus was available to show actual support, duration accuracy, volume performance, or whether normalized filename IDs are unique.

## Proposed validation — not executed

Use staff-cleared representative files and synthetic malformed cases so testing does not expose collection material unnecessarily. Make results explicit: each test has expected status, parser/build/signature versions, diagnostics, byte hashes, and reviewer outcome.

| Area | Proposed cases and pass condition |
|---|---|
| Format identification | Correct extensions; renamed/mismatched extensions; no extension; signature-known; ambiguous/unknown signature; known format unsupported by chosen parser. Extension does not override content; unknown signature is not mislabeled as unreadable. |
| Readability vs preview | Valid file the probe can read but player cannot preview; actually truncated/corrupt file; unreadable path/permission error; unsupported demuxer. UI distinguishes the cause/state and keeps originals. |
| Metadata/duration | Known duration, VBR/long duration, container-vs-stream mismatch, absent duration, multiple streams, reported channels and layout. Raw facts are retained, conflicting durations are surfaced, and no unsupported precision is claimed. |
| Channel handling | Stereo with intentionally different left/right speech and known channel order; mono; multichannel with unknown layout; multiple audio streams. Confirm preview preserves original, channel labels are factual, and isolated preview (if implemented) routes only the selected channel. |
| Transcript/IDs | Exact ID match; normalized-stem collision; duplicate or missing ID; leading-zero and numeric spreadsheet cells; absent transcript; two corrections; same filename stem but different configured ID. No fuzzy join or history loss; ambiguous links require staff action. |
| Rights | Blank, known, malformed, duplicate, and conflicting permission cells. Exact input text/provenance remains; unknown values stay unknown and block only rights-dependent release/use. |
| Restart and idempotency | Interrupt before copy, during copy, after hash check, after probe, after transcript link, after staff action, and during export; resume. No source mutation, silent overwrite, duplicate decision/catalog row, or completed state with missing/hash-mismatched output. |
| Handoff | Move exported directory to another path/device; verify all relative references resolve, every payload hash validates, transcripts and required media bytes are present, and path traversal is rejected. Test catalog import only after its schema/API is known. |
| Accessibility | Keyboard-only path for all actions, visible focus and no trap; screen-reader names/status and concise queue announcements; volunteer test with screen reader. No status conveyed only by color or preview sound. |
| Scale | Compare ordinary 40-item intake with 500 items and representative large files. Measure probe, signature scan, copy, disk space, responsiveness, error recovery, and announcement noise. Do not make a throughput commitment until measured. |

## Owner decisions still open

1. Which spreadsheet column and exact cell semantics define recording identity? May IDs contain meaningful case, spaces, punctuation, or leading zeroes?
2. What permission vocabulary and which rights decisions block intake, catalog entry, public release, or later reuse?
3. Which operating system and UI framework are required, and what platform accessibility API must be supported?
4. Which transcript formats arrive; do any already contain timing; is synchronized transcript display a requirement?
5. Is per-channel audition required, or is reporting channel count/order plus whole-file preview adequate when decoding is supported?
6. What is the maximum file size/duration, storage budget for byte-for-byte staging and portable packages, and retention rule for local copies?
7. Will the receiving catalog accept a directory/BagIt package, a JSON manifest, or a later adapter? What are its upsert and idempotency rules?
8. May an operator create an optional preview derivative on demand for an otherwise unreadable preview, and if so what formats, labeling, and retention are permitted? Such a derivative is not required to catalog the original.
