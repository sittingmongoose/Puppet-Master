## Recommendation

Implement a built-in, keyboard-first command chooser over the existing command registry. Keep command execution and extension handlers in the host's current command system. Add only the metadata and runtime availability information the chooser needs; extensions should not draw or provide executable chooser UI. Show the command's localized name, visible scope, shortcut when available, and a textual availability state/reason. Hide actions that are genuinely irrelevant to the active product context only under an explicit visibility rule. A command that is relevant but currently unavailable, such as an edit that requires a selection, remains searchable and explains why it cannot run.

Start search with deterministic exact, prefix, word, and substring matches, then use a bounded typo-tolerant fallback. Rank clear matches above approximate matches. Search names, aliases, scope/category, and stable ID; expose shortcut text in rows and decide whether shortcut search belongs in the first release after testing the real inventory. Compare typo recovery and false matches using realistic commands before fixing a threshold. Preserve the query and visible localized spelling; normalize matching separately, including case and Unicode/diacritics.

For interaction, test two keyboard focus models with real screen readers: (A) keep keyboard focus in the search input while exposing the active result through the platform's equivalent of active-descendant state; (B) move actual focus into result options while browsing, with a defined return-to-search key. Use A as the first prototype because it supports continued text entry without focus hopping, but accept it only if Windows UI Automation and Linux AT-SPI checks show the active result, scope, shortcut, availability and reason reliably. If those checks fail, use B or a platform-specific adapter. A generic accessibility role alone is not evidence of success. WAI-ARIA APG documents useful web patterns, but does not promise equivalent behavior in native toolkits [S01-S07].

Opening the chooser moves focus to its search input. Arrow keys move the active result; moving/highlighting never executes. Enter is the explicit accept action. Immediately before invocation, resolve the stable ID against the current registry and re-evaluate availability. If it was removed or became unavailable, do not call the handler; remove or update the row and communicate the reason without losing focus. Escape closes without executing and restores the prior editor/view, caret, selection, and scroll position when that destination still exists. If the document/view closed while the chooser was open, restore to a documented logical neighboring destination rather than reopening stale content. Keep current command shortcuts registered independently; choose the chooser's own shortcut only after keymap conflict review on Windows and Linux.

A single concise polite status update may report a settled result count, no results, or a meaningful extension catalog change. Cancel a pending announcement when newer input supersedes it. Do not issue an assertive interruption for every keystroke or duplicate the screen reader's normal announcement of the focused result. The references support non-focus status feedback but do not establish a universal debounce interval; tune it in AT sessions [S04, S18].

## Small integration plan

1. **Inspect target seams.** Identify the existing command registry, built-in/editor action callers, extension register/dispose events, shortcut resolver, editor selection/view snapshot API, and existing accessibility adapter. The target code and callers were not named in the inputs, so this inspection is a required implementation pre-step, not a claim about source already read.
2. **Add descriptor and lifecycle adapter.** Preserve stable IDs and handler ownership. Add localized display name, aliases, scope/category, optional shortcut, current availability and a short reason. Use current registry/context events, cancellation and generation checks; remove descriptors on extension disposal.
3. **Build the chooser controller and renderer.** Reserve an audited keyboard entry binding; focus search; render distinct scope and shortcut; keep active/highlight separate from acceptance; Enter revalidates and invokes; Escape restores prior editor state. Use host-owned UI and platform-specific semantics for Windows UIA and Linux AT-SPI.
4. **Tune search and status behavior.** Rank exact, prefix, word and substring matches ahead of the typo-tolerant tier. Benchmark thresholds and duplicate/scope behavior against the actual command corpus. Debounce and cancel one polite result status; make the timing and content a result of AT sessions.
5. **Ship only after independent gates pass.** Run keyboard correctness tests and cross-platform screen-reader compatibility sessions as separate reports; resolve failures in the relevant track before proposing release.

## Alternatives compared

| Decision | Alternative | Strength | Cost / risk |
| --- | --- | --- | --- |
| Focus while browsing | Keep focus in input; expose active result | Query remains editable; natural for search-first use | Active result announcement depends on platform semantics; must verify UIA and AT-SPI |
|  | Move actual focus into options | More direct focused-item announcements and state | Returning to input takes extra navigation; may interrupt typing flow |
| Command layout | Search dialog with one-action result list | Supports large catalogue, reason and scope | Needs focus management and truthful modal behavior |
|  | Hierarchical menu | Familiar menu keys and grouping | Weak typo recovery and slower over a broad extension catalogue |
| Match strategy | Exact/prefix/word/substring | Predictable ranking and low false positives | Misspelling fails |
|  | Bounded edit distance/Bitap fallback | Recovers common typing mistakes | Threshold tuning and false positives required |
|  | TF-IDF/semantic related fallback | Finds conceptually related wording | Less transparent and beyond minimum need |
| Unavailable command | Hide whenever disabled | Shorter list | Cannot explain why a relevant action cannot run; concrete discoverability failures exist [S11-S13] |
|  | Keep relevant disabled result with reason | Discoverable and explains required state | More row metadata and requires reason source/lifecycle rules |
| Extension surface | Extension draws custom chooser row | Maximum visual flexibility | Violates brief's no executable UI-code requirement; hard to make consistent/accessibility-safe |
|  | Host renders extension command descriptors | Consistent UI, keyboard and accessibility ownership | Descriptor/reason contract must be added to host API if missing |

## Owner decisions and unresolved product data

1. **Visibility boundary:** which commands are “relevant but unavailable” and must remain visible, and which are sufficiently out of context to hide? Selection-required edits should be shown disabled with a selection reason under this proposal.
2. **Reason ownership:** for extension commands, may the host show a generic fallback, or must the extension descriptor include an optional localized reason string/key? The reason is metadata, not executable UI.
3. **Scope vocabulary:** confirm labels such as Document, Selection, Application, and extension/provider identity; target owners know the product's action model.
4. **Chooser shortcut:** select the default only after the target's Windows and Linux shortcut inventory is checked. A menu route can supplement but cannot replace a reliable keyboard entry.
5. **Search threshold and fields:** choose after measuring the actual registry and localized labels. Research cannot establish a safe edit-distance cutoff or whether shortcut text should be indexed.
6. **Focus model:** validate candidate A against NVDA/Narrator and Orca. Retain candidate B if active-result details are not consistently announced.
7. **Supported AT/platform matrix:** identify minimum Windows/Linux versions, toolkit and supported screen readers so the manual compatibility gate is repeatable.

## Findings and evidence boundaries

Already covered and retained: keyboard-only entry; explicit acceptance; Escape dismissal/restore; non-color status; visible shortcut and scope; unavailable reason; extension add/remove lifecycle; no executable chooser UI from extensions; fuzzy search alternatives; independent keyboard and AT validation.

Rejected: leaving a command row alive until the next search after its extension is removed; relying on a generic role as proof that all descriptions are exposed; relying on visual duplicate disambiguation alone; announcing each keystroke assertively; treating the VS Code/Obsidian API or WAI-ARIA patterns as target implementation facts.

Uncertain: the target host API, the actual command inventory, existing caller and test structure, scope names, current platform control tree, how quickly extension registration/disposal propagates, and screen-reader behavior in the target toolkit. These require target code or product-owner data; the brief and primary analogues cannot answer them.
