## Recommendation

Add a local provenance layer around the current document cache and notes. Keep upstream work/edition, observed URLs, captured bytes, extracted text, passage target, check events, and note-to-passage support links as separate records. The existing note remains user-authored and unchanged. A cached copy remains searchable and openable offline even when it is old, inaccessible upstream, or of uncertain origin.

A reader should be able to answer separately:

1. Which product/release/repository commit or source label was selected?
2. Which exact local representation is cached, and where did it come from?
3. Which passage in that representation was attached to this note claim?
4. What was checked upstream, when, with which validator/result, and what remains unknown?
5. Did a later local snapshot change this passage, its surrounding context, or its extracted text?

Do not collapse those answers into a single “current” badge. Neither an HTTP date nor an ETag is the source’s product release identity. A hash establishes a local byte fingerprint, not publisher identity. A matching citation link documents the selected passage; it does not establish that every sentence in the note is supported or true.

## Proposed records and relations

These fields describe a design, not an existing schema.

| Record | Key fields and behavior |
|---|---|
| Work/source | Stable local source ID; title; publisher; content kind; expected product and version/channel when known; upstream repository, commit, official release ID or version URL; source authority/reviewer assertion. Unknown fields stay unknown. |
| Locator | Original requested URL, each observed redirect and status, effective URL, canonical URL if publisher explicitly identifies one, and observation time. Keep locator aliases distinct from source and edition identity. Do not infer equivalence from a redirect alone. |
| Snapshot | Immutable local ID; original response/import bytes retained under local cache policy; byte length; media type and content encoding; capture/import UTC; SHA-256 with algorithm field; declared release/version; source of that declaration; raw object path. Never replace an older payload in place. A manual import gets a separate snapshot and an explicit “staff supplied / upstream unverified” provenance state. |
| Extraction | Snapshot ID; extractor/parser name and version; normalized extracted-text digest; page/heading/section map to raw content; Unicode normalization rules. A parser upgrade creates a new extraction record and does not silently rewrite old offsets. |
| Passage anchor | Snapshot and extraction IDs; short normalized exact quote, prefix/suffix context, code-point offsets (end-exclusive), heading/page/fragment hints and optional page image/coordinates for formats that support them. Preserve the original selector; any later candidate is separate. |
| Note link | Note ID and revision ID, ideally a claim/excerpt range, linked to the passage anchor and snapshot ID; created-by/time; relation (“supports this excerpt”, “contradicts”, “background”); reviewer and disposition. Do not attach a source only to an entire note and imply it supports everything in that note. |
| Check event | Source/locator and conditional request method; start/end UTC; request validators and their strength; response status, redirect chain, response validators, cache directives, body received/truncated, resulting snapshot/hash if any, error/rate-limit outcome, and next eligible check. Append results; do not overwrite history. |
| Review event | Candidate old/new snapshots and anchors; local text/structure diff; affected note links; user decision, actor/time and reason. A model may suggest candidate passages but cannot silently approve or rewrite a link. |

Use typed relations with evidence and direction. A byte-digest match can support “same captured bytes.” A repository commit can identify a particular immutable tree/file. Use “revision of” only when substantial content lineage is supported; “quoted from” for a copied passage; “alternate representation” when two entities present aspects of one work without claiming identical content; and “specialization of” for a time- or context-specific page within a general source. PROV-O defines these distinctions. A redirect is an observed URL event; whether it is an alias, successor, or unrelated replacement is a separate assertion. Preserve asserted, observed, and reviewed relations separately. ([W3C PROV-O](https://www.w3.org/TR/prov-o/), §§ 3.1–3.2)

For repository-backed technical documents, capture repository URL, full commit ID, path and optional line range. Git objects are content-hash named and immutable after creation, while branches move; tags are refs and are usually stable, but should not replace a full commit ID when exact identity matters. GitHub documents commit-based permanent file/line links. This works well for docs shipped with source code, but is not a universal identifier for hosted documentation. ([Git data model](https://git-scm.com/docs/gitdatamodel.html), [GitHub permanent links](https://docs.github.com/en/repositories/working-with-files/using-files/getting-permanent-links-to-files))

## Passage navigation and revisions

Use a Web Annotation inspired pair of selectors against the retained snapshot’s extracted text: normalized exact quote plus nearby prefix/suffix, and a Unicode code-point position range. Record the selector’s snapshot and extraction version. Text positions are brittle under edits. The W3C model says multiple matching exact/context selections are all matches; therefore ambiguity is a surfaced state, not a tie the system should resolve silently. Its selector model is a useful shape, but is not a revision identity mechanism. Keep stored quote/context short and local; never transmit it during network checking. ([W3C Web Annotation Data Model](https://www.w3.org/TR/annotation-model/), §§ 4.2.4–4.2.5)

On a changed candidate, compare old and new retained extracted text locally by section and passage. Report “unchanged exact passage,” “passage changed,” “possible moved passage,” “missing,” “ambiguous,” or “comparison unavailable.” Require review before changing a note link. If the exact quote is unchanged but its context or relevant normative condition changed, flag that for inspection too. Preserve a good old anchor even when a newer edition is preferred for a different query. A new version may affect some note passages and leave other links untouched; passage-level diff is a locator aid, not a semantic decision about a claim.

A real implementation example shows why “best effort” must be visible. Hypothesis issue #3705 reported that PDF.js extraction changes could make a text-position hint unreliable and a first acceptable fuzzy match land on a worse PDF passage. Merged PR #3743 changed PDF anchoring to compare candidate matches across pages with selected whitespace normalization and added tests for exact, near, whitespace-different and context-sensitive matches. The commit-specific implementation and tests are in the source index. This is PDF-specific behavior, not a universal matching rule; it supports testing ambiguity, wrong-match prevention, extraction versions and latency together. No Hypothesis test suite was executed for this research. ([issue #3705](https://github.com/hypothesis/client/issues/3705), [merged PR #3743](https://github.com/hypothesis/client/pull/3743/files))

## Identity and change-detection alternatives

| Approach | Use when | Limit / what the UI may safely say |
|---|---|---|
| Release-specific official URL, release manifest, product version or exact commit | A versioned vendor docs set, release archive, or repository document has a stable published identity. | Best fit for a deliberate older-version query. Display the selected version and its evidence; do not substitute a newer page because it is newer. A version label without a pinned object is still a publisher assertion. |
| Local raw SHA-256 and immutable payload | Every cache entry, including manual imports. | Detects byte identity/change for retained data; does not authenticate publisher, assign release, prove semantic equality or decide passage support. NIST FIPS 180-4 specifies SHA-256 as a message-digest algorithm useful for detecting changes with very high probability. ([NIST FIPS 180-4](https://nvlpubs.nist.gov/nistpubs/fips/nist.fips.180-4.pdf)) |
| HTTP ETag / If-None-Match; Last-Modified fallback | Optional low-bandwidth revalidation when origin supports it. | ETag is opaque and server-chosen. If-None-Match uses weak comparison; RFC 9110 permits weak validators for this cache-validation path even when representation data changed. Last-Modified is implicitly weak except narrow origin/date conditions. A 304 is a validator match, not universal proof of exact local bytes, source version, or anchor validity. Save validator strength and the exact response; never call a weak 304 “byte unchanged.” ([RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html), §§ 8.8, 13.1.2–.3) |
| HTTP freshness/cache directives | Decide whether an ordinary HTTP cache may reuse a response. | Freshness is cache reuse without contact and can use explicit or limited heuristic expiration; it does not force this application to refresh a result. Stale use has disconnected and directive-specific rules. Keep this separate from evidence relevance and let offline handbook search use retained copies. ([RFC 9111](https://www.rfc-editor.org/rfc/rfc9111.html), §§ 4.2–4.3) |
| Memento/web archive, including archive snapshots | Recover a prior web state or investigate a moved/disappeared public URL when an archive has coverage. | RFC 7089’s TimeGate/Accept-Datetime and Memento-Datetime provide temporal negotiation and state navigation. Archive time is not a vendor product version, and coverage/availability are not guaranteed. Show archive provenance and captured time; never substitute it silently for an official source. ([RFC 7089](https://datatracker.ietf.org/doc/rfc7089/)) |
| Software Heritage SWHID | The source is a captured software repository/artifact and archive navigation is useful. | SWHIDs can identify revisions, releases, trees, contents and paths/lines with origin/visit context. The reviewed v1.6 spec is software-specific and uses SHA-1 Git-style identifiers; it is a useful optional locator pattern, not a general web-page scheme or our new digest choice. The official docs search result was readable, but direct page retrieval returned access denied; see the source map. ([SWHID specification v1.6](https://docs.softwareheritage.org/devel/swh-model/persistent-identifiers.html)) |
| Passage selectors (quote/context and offsets) | Navigate a user to evidence inside a chosen local representation. | Useful in combination with snapshot identity; insufficient alone. Repeated text, extraction changes and normalized text can misplace a link. Any candidate match after a new snapshot needs confidence and human review. ([W3C Web Annotation](https://www.w3.org/TR/annotation-model/)) |

## Optional bounded network checks

Local query, result display, opening retained documents, selector resolution against retained snapshots, and diffing retained versions work offline. Network checking is an explicit per-user feature, separate from search. A user can request “check selected sources”; an opt-in schedule can process due records in the background. Deduplicate by normalized safe URL and host; cap work by per-run request count, per-host concurrency/rate, connect/read timeout, redirect count, response bytes and retry/backoff. Store the exact limit/result so “not checked” is not confused with “unchanged.”

Prefer conditional GET with stored ETag and/or Last-Modified where source policy permits. HTTP gives If-None-Match precedence over If-Modified-Since; a HEAD response contains no body and is metadata only, so it is only a preliminary hint, not proof about passage content. Apply HTTP redirect policy while recording each hop; do not send credentials across origins. Treat embedded credentials and sensitive query components as unsafe for unattended checks and request user repair/confirmation. Never put notes, claims, excerpts, note IDs/titles, search terms or user data in request headers, paths, bodies, logs sent upstream, or analytics. Do not send a Referer. Tell the user that a check contacts the named host and reveals request timing/IP and source URL.

Recommended states:

| Observation | Record and show | User action |
|---|---|---|
| No network request / offline / no validator | “Not checked”; show last completed check separately. Retained copy remains usable. | Optional manual check when connected. |
| Conditional response 304 | “Origin matched stored validator at [time]” plus validator type/strength and selected representation URL. Do not infer exact bytes from weak comparison or announce that all selectors are valid. Locally confirm selectors against the stored snapshot/extraction version. | No action for local anchor; refresh later if needed. |
| Full 200, same raw hash | Keep an observation; do not add an unnecessary duplicate snapshot unless response metadata or representation selection changed. Report identical downloaded bytes and timestamp; do not infer publisher authenticity from hash. | None, unless release metadata changed. |
| Full 200, different hash | Save a new immutable candidate snapshot and extraction, then run bounded local diff. Preserve old bytes and note edges. | Review only changed, missing, ambiguous, or context-sensitive note passages; attach accepted new links explicitly. |
| Redirect or canonical URL changes | Save source and destination locators, status, time and chain. Keep old locator/history and represent relation as unreviewed observation. | User/reviewer may assert alias/successor/independent resource. |
| 404/410, 401/403, 429, server error, timeout, malformed/truncated/budget stop | Record distinct outcome, time and retry policy. Never erase local copy or infer deletion/revision from a transient failure. | Retry later, inspect URL or mark no longer hosted if confirmed. |

HTTP cache freshness is independent from source version: RFC 9111 defines freshness as whether a response may be reused without validation, and permits stale handling only under specified conditions. A handbook can keep an old source available offline while clearly showing that its upstream check is unknown or old. ([RFC 9111](https://www.rfc-editor.org/rfc/rfc9111.html), §§ 4.2–4.3.4, 5.2.2.2)

## Search-result presentation and integration

For each result show the matched product/version/channel (including “version unknown”), source/release identity and evidence type, original/effective URL, local capture time and hash prefix, and upstream-check result/time. Expose separate badges/labels for “cached locally,” “checked at,” and “passage match.” Give actions to open the exact cached snapshot offline, view the exact source passage, compare old/new snapshots, inspect URL history, and select a product version. A deliberate vN query must rank/select vN evidence before other versions; newer is not equivalent to more applicable. Recency can be a visible sort, not an unqualified relevance score.

For a note excerpt show its linked claim/passage, edition and snapshot, selector status and last reviewer. A warning should say which source passage or condition changed and which note excerpt edges reference it. A retrieved page supports only the mapped passage and claim relationship; it does not certify the rest of the note. Preserve older selected editions and show new candidates separately. Do not silently “upgrade” a note citation.

Integrate as a sidecar table/index keyed to existing local document and note IDs. Keep original note bytes untouched. Backfill hashes and source metadata lazily, label unknowns as unknown, and offer review for previously imported documents. Search the few-thousand-document cache locally using an index for metadata/text and passage maps. Revalidation and diff computation run asynchronously; do not delay or disable offline search. Archive/Memento or SWHID lookup is optional and only runs after a user asks, with the archive copy labeled by archive and time.

## Owner decisions that research cannot settle

1. Which publishers/domains and document types are trusted as official for each product, and how source-specific aliases/redirects and release channels are approved?
2. Which exact release labels, support windows, prerelease channels and default filters appear in the handbook UI? Explicit user version must override “latest”; behavior when version is missing needs a product-owner choice.
3. Which file formats/extraction engines are in the first release, and how long must raw bytes, text, excerpts, redirect/check logs and imported files be retained under publisher/license policy?
4. Is scheduled revalidation enabled by default, opt-in per user, or only manual? What host allowlist, sensitive-query handling, rate/byte caps and shared-network privacy notice are acceptable?
5. What human review permissions/statuses are needed, and which changes (e.g. normative condition change vs unrelated navigation/footer) require re-review?
6. Which records are already present for existing notes/imports, whether note revisions/claim spans exist, and how to backfill them without altering notes?
7. Should Memento or Software Heritage be offered as a user-invoked secondary source, and what labels/availability caveats should accompany it?
