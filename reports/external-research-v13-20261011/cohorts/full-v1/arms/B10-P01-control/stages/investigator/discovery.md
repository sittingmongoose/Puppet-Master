# Investigator discovery — B10-P01-control

## Scope and method

This is brief-only discovery for a local technical handbook; the withheld exact plan was not consulted. I searched primary protocol/standards documentation, official project documentation, and one relevant public implementation issue/merged fix. Accessed pages and release identifiers are listed in [the source index](sources/index.md) and [source-map.json](source-map.json). I did not run external code, repository tests, a handbook crawler, or implementation checks.

## Main design finding

Keep four identities separate: (1) the logical upstream work and its alias/redirect URLs, (2) each immutable local captured representation, (3) the release/product/version or repository commit it claims to represent, and (4) a note’s claim-specific link to a passage in that captured representation. A URL is a locator, not a revision ID. A validator is an origin’s comparison token, not the product’s release identity. A content digest is a local fingerprint, not proof who published the file or which release it is. Model each capture and each check as an append-only event, with evidence and reviewer assertions distinguished.

For every cached snapshot retain the requested URL, observed redirect chain and final URL, response status, media type, content encoding, capture UTC, raw byte length and algorithm-tagged SHA-256, plus any upstream release/version, commit, ETag/strength, Last-Modified and cache directives. If extraction is supported, retain the extracted-text digest, extractor/parser version and a mapping back to raw page, heading/page, normalized text positions and quote context. Never overwrite an old snapshot after an upstream check. A manual import receives its own immutable snapshot, hash, import time/person and staff-supplied source/version fields explicitly marked as unverified.

Attach a staff note revision or explicit claim/excerpt object to a specific snapshot and passage. A Web Annotation style TextQuoteSelector (short normalized exact quote plus prefix/suffix) and a TextPositionSelector (Unicode code-point range, end-exclusive) provide complementary locators; retain the source snapshot and extractor version with them. Exact quote/context plus stable structural hints should be attempted first. If a quote has zero candidates, several plausible candidates, or only a fuzzy/low-confidence candidate, show “missing”, “ambiguous”, or “possible moved passage” and ask for review; never move the citation silently. Show the quote as support for that selected passage/claim link only. The relation does not verify all statements in the surrounding note. The W3C model explicitly warns position selectors are brittle and says multiple matching quote sequences count as all matches. (W3C-WA; HYPOTHESIS issue/fix)

Use typed, evidence-backed source relations: same bytes (digest match), revision-of only when substantial lineage is supported, alternate representation for same-work format or backup cases, and URL alias/redirect as an observed locator relationship. PROV-O distinguishes revision, quotation, specialization and alternate; preserve direction, source and confidence/reviewer. A redirect is not automatically an edition link. Keep local IDs stable; do not silently retarget an existing note when a new page appears.

## Revision identity and alternatives

| Approach | Strength | Limit and fit |
|---|---|---|
| Release/version-specific vendor URL, official release metadata, or full Git commit plus repo path | Best for deliberate product-version queries; Git objects are content-hash identified and immutable, and GitHub commit permalinks can pin a file and lines. | Prefer the user's targeted version; branches move, tags usually but not necessarily never change; repository pinning covers only repo sources. (GIT-DATAMODEL; GITHUB-PERMALINKS) |
| Local raw SHA-256 snapshot digest + retained payload | Exact local-byte comparison; works offline and for manual imports. | Identifies bytes only, not upstream authenticity, semantic version, text extraction behavior, or passage relevance. (NIST-FIPS180-4) |
| ETag conditional GET, with Last-Modified fallback | Small, cheap recheck; a matching validator can yield 304 without transferring the body. Useful as an optional status signal. | Server-generated and opaque; If-None-Match comparison is weak even when tags are present, weak tags can tolerate representation-data change; Last-Modified is implicitly weak except narrow conditions. Not a release ID or byte hash. (RFC9110) |
| Memento / web archive state | Can help recover prior page states or find URL successors when an archive supports the protocol. | Coverage, retention, and resolver uptime vary; archive datetime is not the product release date or independent proof of authority. (RFC7089) |
| Software Heritage IDs for software artifacts | Rich object types (snapshot/release/revision/directory/content) and origin/visit/path/line qualifiers make repository evidence navigable. | Specialized to archived software; reviewed v1.6 documentation uses SHA-1 Git-style hashes and cannot identify arbitrary technical web pages. (SWHID-1.6) |
| Quote/offset anchoring alone | Fast passage navigation within the chosen local representation. | Cannot identify a revision; extraction/parser changes and repeated text can create false anchors. Hypothesis’s PDF issue #3705 documented wrong early fuzzy matches and PR #3743 added across-page scoring/tests, while its PDF whitespace rule was deliberately specialized. |

## Revalidation and states

Local search should never require the network. Keep optional “check now” and opt-in background refresh behind a queue deduplicated by safe URL and host, with explicit per-run/per-host request, time, redirect, byte, concurrency, and retry/backoff limits. No check includes note text, claim, excerpt, search terms, note ID/title, or user identifiers. Do not transmit embedded credentials or sensitive query parameters; redact or ask the user to repair such URLs. Record every check as a separate event. Preserve offline cached content even when upstream is unreachable.

Prefer a conditional GET using stored validators when allowed by source policy; use a HEAD probe only as a hint because it transfers no body and a server’s behavior may not establish passage-level sameness. A 304 means the selected representation matched the validator under HTTP comparison rules; preserve validator strength and never relabel that alone as exact byte equality. A 200 with changed tag/hash means a new candidate snapshot, not a replacement for the old one. Fetch/body parsing can be size-limited; truncated, malformed, redirected, 401/403, 404/410, 429, server-error and timeout outcomes stay distinct. Record redirect chains and effective URL but ask for reviewed relation before merging identities. When validators are absent, changed, or weak, optional bounded GET plus local hash/text diff is stronger evidence; if unavailable, report “not checked/unknown.”

Separate local snapshot integrity, last upstream check, target release, and passage match in the UI. Keep query ranking version-aware: an explicit target (e.g. product vN, stable/LTS channel, full repo commit) constrains results; recency is at most a user-visible tie-breaker. Newest is not inherently most applicable. Show old source release, capture time/hash and claim-linked excerpt; allow opening its offline cached copy. New revisions appear as separate candidates with a scoped passage diff and affected-note list. The user/reviewer decides whether a particular excerpt still supports a particular claim. Never rewrite note prose automatically.

## Integration direction and validation proposals

Add a provenance sidecar/relational index around the current cache and note IDs rather than rewriting note bodies: source/work and aliases, immutable snapshot rows, request/response check events, extractor-versioned passage anchors, note-revision-to-passage edges, explicit release/commit metadata, and human review decisions. Backfill source URLs and hashes lazily; mark prior revision and manual-import origin as unknown when not evidenced. Index snapshot metadata and text locally for several thousand sources; background checking remains separate from interactive search.

Proposed validation (not executed): unit tests for strong/weak ETags, 304/200/no validator, Last-Modified precedence and invalid/absent dates, redirects, missing pages, timeouts, rate limits, body caps and offline behavior; byte-hash and extractor-upgrade tests; anchor fixtures for repeated quotes, changing context, Unicode/code-point ranges, PDF/text extraction differences, deleted/ambiguous passages and “no auto-reattach”; explicit release-target tests where a newer version ranks below a requested older version; privacy tests proving outbound requests contain only the source URL and allowed validator headers; migration tests proving original notes stay byte-for-byte untouched; and performance checks on a several-thousand-document cache for indexed local search and bounded refresh queue. These are proposals only; none were run.
