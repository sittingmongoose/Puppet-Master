# Final proposal — search provenance for a local technical handbook

**Status:** Research-backed software proposal; not an implementation or product decision. This consolidates the brief, frozen discovery, released draft plan, investigator proposal, and independent critique. It addresses the exact released clauses in order. The plan reveal records SHA-256 `acb36080380afebc5669cf45ac5ffd78c7bf760d9593263537903df66dea0957` (2,309 bytes); frozen discovery SHA-256 is `dc33b876145ade3e4e15aa280250f3ac362281a0c3294094e37420f7ebf600dc` (9,164 bytes). See [the navigable source index](sources/index.md) and [the structured source map](source-map.json).

## Proposal

Add a local provenance sidecar around the handbook’s existing cache and note identifiers. Keep distinct: (1) the logical work/source and evidence for a product release, version, channel, or repository commit; (2) observed URLs and redirects; (3) each immutable local captured representation; (4) an extraction produced from that representation; (5) a passage selector within that extraction; (6) the specific note revision or claim/excerpt linked to that passage; and (7) each network check and human review event.

The selected product version answers “which release was intended?” A local digest answers “are these retained bytes identical?” An HTTP validator answers a conditional-request question for an HTTP-selected representation. A passage selector answers “where is this excerpt in this particular extraction?” None substitutes for the others. No single “current” badge should combine them. “Newest” is not a proxy for relevance: an explicit product-version/channel/commit query constrains results, and recency is at most a visible tie-breaker after the requested version is honored.

Keep authored note bytes untouched. Keep prior snapshots and links when a new version arrives, a URL moves, or a source becomes unavailable. Local search, opening retained copies, and comparison of retained extractions work offline. Optional network checking is independent of search and never sends note, claim, excerpt, note ID/title, query, or user data to a source host.

A retrieved passage may be linked as support for a particular note claim or excerpt. That link does not establish that the rest of the note is supported or true. If a passage is changed, missing, ambiguous, or only tentatively relocated, preserve the original anchor and require a person to review any new link.

## Identity, records, and relations

These are proposed records, not an assertion about an existing handbook schema.

| Record | Proposed content and behavior |
|---|---|
| Work/source | Stable local ID, title/publisher/content kind, expected product and release/channel when evidenced, official release URL/ID or repository plus full commit and path, and who asserted source authority. Unknowns remain unknown. A version label without a pinned object remains an attributed publisher/staff assertion. |
| Locator | Original requested URL, each observed redirect/status and time, effective URL, and publisher-declared canonical URL if any. A redirect is an observation, not proof of same work, edition, alias, or successor. Retain old locators. Treat credentials and sensitive query components as unsafe for unattended checks. |
| Snapshot | Immutable local ID and retained original bytes; requested/effective URL and observed chain; status, media type, content encoding, raw byte length, capture/import UTC, algorithm-tagged SHA-256, declared release/version and its evidence, response validators and cache directives, raw object path. A manual import is a distinct snapshot with actor/time and staff-supplied fields marked “unverified / not checked.” Never overwrite an earlier payload. |
| Selected representation variant | The received Vary value plus a key for the original request method, target URI, and each safe request field Vary names, including whether a field was absent. Normalize only where that field’s specification says values are semantically equivalent. Store/replay only minimum non-sensitive values allowed by owner privacy policy; never persist credentials or private request fields. If a selector field cannot safely be retained or reproduced, do not report a comparison. Vary: * is non-matchable from request fields and cannot justify an unchanged result. |
| Extraction | Snapshot ID, extractor/parser and version, normalization rules, extracted-text digest, and mappings from section/page/heading and text positions to raw content. A parser upgrade creates a separate extraction; it does not silently change old offsets. |
| Passage anchor | Snapshot and extraction IDs; short normalized exact quote with prefix/suffix, Unicode code-point position range (end-exclusive), and optional heading/page/fragment or format-specific coordinates. Keep the original selector immutable. Any cross-snapshot or cross-extractor match is a separate candidate. |
| Note link | Note and note-revision IDs, preferably a claim/excerpt span, passage/snapshot/extraction IDs, relation (for example “supports this excerpt,” “contradicts,” or “background”), creation time/actor, and review disposition. Do not link a document to an entire note in a way that implies whole-note support. |
| Check event | Source/locator, method and target, safe variant key and Vary, sent validator and its strength/type, start/end UTC, response status/headers/redirect chain, response validators/cache directives, body received or truncated, candidate snapshot/hash if any, distinct error/rate-limit outcome, and next eligible check. Append events; do not overwrite history. |
| Review event | Candidate old/new snapshots and anchors, local section/passage/context diff, affected note links, reviewer, time, decision and reason. Software may propose candidate passages; it does not silently approve or reattach them. |

Use typed, directed relations with evidence and reviewer assertions kept separate. A matching byte digest supports “same captured bytes,” not provenance. Use “revision of” only with evidence of substantial retained content; “quoted from” for copied passage derivation; “alternate representation” for aspects/formats of one work without claiming identical content; and “specialization of” for a context- or time-specific source. PROV-O distinguishes these relation types. A redirect alone proves only an observed locator transition, not a revision or alias. ([PROV-O](https://www.w3.org/TR/prov-o/))

For repository-hosted material, retain repository URL, full commit ID, path, and optional line range. Git objects are immutable while branch references move; tags are references and are usually stable, but a full commit plus repository/path is the stronger exact locator. A GitHub commit permalink is useful for GitHub-hosted files, not a universal identifier for web documentation. ([Git data model](https://git-scm.com/docs/gitdatamodel.html), [GitHub permanent links](https://docs.github.com/en/repositories/working-with-files/using-files/getting-permanent-links-to-files))

## Passage navigation and change review

Use paired, representation-bound selectors inspired by the W3C Web Annotation model: a normalized exact quote with short prefix/suffix context, plus a code-point position range. Retain the snapshot, extraction version, and representation state with each selector. The W3C model makes position selectors brittle under edits and defines a quote selector with multiple matches as matching all of them; therefore ambiguity must be visible, not silently resolved. These selectors locate a passage in a chosen representation; they do not identify a release. ([W3C Web Annotation Data Model](https://www.w3.org/TR/annotation-model/), §§ 4.2.4–4.2.5, 4.3)

Compare retained extracted text locally, by section and passage, when a new candidate snapshot exists. Report states such as “same exact retained passage,” “changed,” “possible moved passage,” “missing,” “ambiguous,” or “comparison unavailable.” Check nearby context and relevant conditions as well as the quote: identical words under a changed normative condition can matter. A candidate passage is a locator aid, not a semantic judgment about whether a claim remains true. Require review before adding or changing a note link, and preserve valid evidence for an older selected version.

A bounded implementation example supports these cautions. Hypothesis issue #3705 described PDF.js extraction/position drift and a first acceptable fuzzy match winning before a better match on another page. Merged PR #3743 changed that PDF-specific matcher to compare across pages with selected whitespace normalization and added exact, whitespace-different, near-match, and context tests. Its code and tests were inspected in the predecessor research, but were not run here. This example motivates testing wrong-match prevention, ambiguity, extractor changes, and latency; it does not establish a universal anchor algorithm. ([issue #3705](https://github.com/hypothesis/client/issues/3705), [merged PR #3743](https://github.com/hypothesis/client/pull/3743/files), [pinned code](https://github.com/hypothesis/client/blob/904810bde556c58043672b61f0ea33748fd0e00a/src/annotator/anchoring/pdf.js), [pinned tests](https://github.com/hypothesis/client/blob/904810bde556c58043672b61f0ea33748fd0e00a/src/annotator/anchoring/test/pdf-test.js))

## Viable identity and change-detection approaches

| Approach | Good fit | Limits and safe presentation |
|---|---|---|
| Official release URL/manifest, product version, or full repository commit | Vendor releases and repository-backed docs with stable published versions. | Best for an intentional older-version query. Show evidence for the version label. A version label alone is still an assertion; do not silently replace it with latest. |
| Retained bytes plus local SHA-256 | Every snapshot, including manual imports. | Detects equality/change of the locally hashed byte sequence. Does not identify publisher, release, semantic equality, text extraction, or claim support. NIST specifies SHA-256 as a message-digest algorithm useful for detecting changes with high probability, not as an authenticity proof. ([FIPS 180-4](https://nvlpubs.nist.gov/nistpubs/fips/nist.fips.180-4.pdf)) |
| ETag with conditional GET | Optional low-transfer HTTP revalidation, when a source and safe selected variant permit it. | ETags are server-selected opaque validators. If-None-Match uses weak comparison even when tags exist, and weak comparison may match despite changed representation data. A 304 is not byte identity, a product-version ID, or selector verification. Bind every attempt to the selected variant. ([RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html), §§ 8.8, 12.5.5, 13.1.2) |
| Last-Modified / If-Modified-Since | Fallback where an ETag is absent. | The date validator is implicitly weak except narrow conditions; it is not an HTTP timestamp proving content or version. If-None-Match takes precedence when both conditions are present. Record the actual condition used. ([RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html), §§ 8.8.2, 13.1.3, 13.2.2) |
| HTTP cache freshness/directives | Ordinary HTTP cache reuse decisions. | Freshness can permit reuse without contact; stale reuse has directive/disconnection conditions. Neither is evidence that a source passage applies to a claim or that a cached version is the user’s target. Keep it separate from source-version and passage states. ([RFC 9111](https://www.rfc-editor.org/rfc/rfc9111.html), §§ 4.1–4.3.4, 5.2.2.2) |
| Memento/web archive | User-invoked recovery of an archived state or a moved/disappeared public page where covered. | TimeGate/TimeMap and Memento-Datetime enable temporal navigation where supported. Archive date is not a vendor release; availability and coverage vary. Label archive/source/time and never substitute it silently. ([RFC 7089](https://datatracker.ietf.org/doc/rfc7089/)) |
| Software Heritage SWHID | Archived software artifacts, repository docs, and archive navigation. | Can identify software object types and contextual paths/lines; specialized to archived software, not arbitrary web pages. The carried v1.6 evidence is search-index text only because direct retrieval was denied; present this as an evidence-limited optional route, not a general identifier or recommended new hash scheme. ([Software Heritage SWHID v1.6](https://docs.softwareheritage.org/devel/swh-model/persistent-identifiers.html)) |
| Quote/context and position selectors | Navigation to a passage in a selected retained representation. | Useful only alongside snapshot/extraction identity. Repeated text, extraction changes and normalization can cause failure or false candidates. No candidate after revision becomes a confirmed link without review. ([W3C Web Annotation](https://www.w3.org/TR/annotation-model/)) |

No one identifier wins in every context. Combine release evidence when available, an immutable local byte fingerprint for each capture, and a passage selector bound to that capture. Treat HTTP validators as optional freshness signals only.

## Optional bounded network checking and states

Local query, cached-copy display, selector resolution against retained snapshots, and local diffing continue offline. Offer a user-triggered “check selected sources” action and, only if owners choose, an opt-in background schedule separate from interactive search. Deduplicate by safe URL and host. Cap requests per run, per-host rate/concurrency, connect/read time, redirect count, response bytes, and retries/backoff. Record the limit and result so “not checked” differs from “unchanged.”

When permitted, prefer conditional GET with stored ETag and/or Last-Modified. Record the precondition used and its strength/type. HTTP gives If-None-Match precedence over If-Modified-Since. HEAD has no body and is metadata only; at most it is a hint, not passage evidence. Record each redirect hop and effective URL. Do not forward credentials across origins. Treat embedded credentials and sensitive query components as unsafe for unattended checking. Never send note text, claim, excerpt, note ID/title, search term, or user data in requests, headers, bodies, upstream logs, or analytics; suppress Referer. Explain that an enabled check contacts the named host and discloses the source URL, request timing, and network metadata such as IP. Only retain the minimum safe Vary selection fields needed for variant matching/reproduction; if that cannot be done, use “not checked/comparison unavailable.”

| Observation | Record and show | User action |
|---|---|---|
| Offline, not requested, unsafe/unreproducible variant | “Not checked” or “comparison unavailable”; show last completed check separately. Keep the local snapshot available. | Optional repair of URL/variant policy or later check. |
| Conditional request returns 304 | “Conditional request returned 304” for the recorded target, variant, precondition, and time; retain response chain and validator type/strength. Do not say “origin matched” unless direct-origin contact is independently evidenced. A 304 says nothing about selector validity across snapshots/extractors and is not a byte hash. | No action for a selector that still resolves in its original retained snapshot; later-version equivalence remains separate. |
| Full 200, same raw payload hash | Record the new observation and metadata/variant. State that downloaded payload bytes matched the retained digest. Do not infer publisher authenticity or release identity from the hash. | Review only if release/variant metadata or linked context changed. |
| Full 200, different payload hash | Preserve it as a new immutable candidate snapshot/extraction, then diff locally. Keep old links and payload. | Review only changed, missing, ambiguous, or context-sensitive affected links; explicitly approve any new link. |
| Redirect/canonical change | Preserve source and destination URL, status, time, chain, and representation metadata. Record observed redirect separately from reviewed alias/successor identity. | Reviewer may assert alias, successor, or independent resource using publisher evidence. |
| 401/403, 404/410, 429, server error, timeout, malformed/truncated response, budget stop | Record distinct outcome/time/retry policy. A transient failure does not delete a retained copy or prove upstream deletion/revision. A 404 alone may be temporary. | Retry, inspect, repair, or mark no longer hosted only when supported. |

HTTP cache freshness is not source-version identity. A local handbook can continue to show an old retained copy offline while its last upstream check is old, unknown, or failed.

## Search-result presentation and integration

For a result, show the user’s matched product/version/channel (including “unknown”), source/release identity and evidence type, original/effective URL, local capture time/hash prefix, representation/variant status where known, and last upstream check status/time. Keep separate labels for “cached locally,” “selected version,” “checked at,” and “passage match.” Offer actions to open the exact cached snapshot offline, open its mapped passage, compare retained snapshots, inspect URL history, and choose a version. An explicit vN query selects vN evidence before other versions; a newer version is not automatically more applicable.

For a note excerpt, show the claim/excerpt edge, linked passage and edition/snapshot, selector state, and reviewer. A warning names the changed source passage/condition and affected excerpt links. A page supports only its mapped passage relationship. Keep new snapshots as candidates and do not silently upgrade note citations.

Integrate through sidecar tables/indexes keyed to existing local document and note IDs. Lazily backfill hashes/source metadata, label unknowns, and offer review of imported records. Keep note bytes intact. Use a local index over metadata/text/passage maps for the few-thousand-document cache; run optional checking and diffing asynchronously so they do not block offline search. Memento/SWHID lookup is optional and user-invoked, with archive identity/time shown.

## Independent critique dispositions

| Critic finding | Disposition and evidence |
|---|---|
| C1 — The checker omitted Vary and the representation-selection key; safe revalidation must use the selected variant. | **Accept and amend.** Independently rechecked RFC 9110 §12.5.5 and RFC 9111 §§4.1, 4.3.1. ## Open owner and data decisions

1. Which publishers/domains and document types are official for each product, and how are release channels, aliases, redirects, and successors approved?
2. Which version labels/support channels/default filters appear? Explicit requested version must override latest; owners choose treatment of unknown versions.
3. Which file formats and extraction engines are in scope, and how long may raw bytes, extracted text, excerpts, redirects, check logs, and imported files be retained under publisher/license policy?
4. Is scheduled checking off, opt-in, or enabled? Which host allowlist, query-parameter repair, Vary metadata storage/replay, rate/byte/time limits, and privacy notice are acceptable?
5. Which people may approve passage changes, and which contextual or normative edits require re-review?
6. What note/document IDs, revision spans, import metadata, or existing check fields actually exist, and how can they be backfilled without changing note bytes?
7. Should Memento or Software Heritage be offered as a user-invoked secondary lookup, with what availability and authority caveats?
