# Draft — Background extension task admission and fairness

**Status:** independent investigator draft after the declared plan release. This is a research-backed proposal, not implementation or deployment. Discovery is frozen at the SHA-256 recorded by the one-time reveal helper. The exact plan reviewed is the released copy, revealed-plan.md. Source identities and limits are in source-map.json and sources/index.md.

## Clause-by-clause disposition of the released plan

The clause IDs below identify each sentence in revealed-plan.md in reading order. “Retain” means the direction is supported; “correct” means the sentence omits a needed behavior or overstates a guarantee; “owner decision” means sources cannot determine product policy; “optional” means useful but not necessary to meet the brief.

### P1 — Queue record, class slots, per-extension cap, UI

**P1.1 — “The draft creates host-owned queue entries with extension identity, task identifier, priority class, estimated memory and a cancellation token.” — Retain, with corrections.** Host-owned admission and durable task identity are essential to control state, queue order, cancel and publication. Store the host-verified extension identity, task/job ID, submission/input snapshot identity, attempt number, priority class, both the extension-declared estimate and host-measured estimate/confidence, wait reason, progress, lifecycle timestamps, and an opaque generation token. A cancellation token alone does not fence stale attempts or survive restart; persist a cancellation state and generation. Priority classes must be host-defined and must never depend on payment. **Owner decision:** ID format, whether duplicate submission is deduplicated, and which classes exist.

**P1.2 — “Interactive tasks have a reserved slot, while report tasks share the remaining worker capacity.” — Owner decision; the starvation risk is real.** A reserved slot can protect interactive work from a report burst, but a permanently exclusive slot may sit idle. If reports may borrow it, a non-preemptible report already using it can delay a later interactive job. Continuous interactive work can starve reports if it owns an unbounded strict-priority lane. The sources do not choose the desired tradeoff. Specify whether the slot is exclusive or borrowable, how a borrowed slot is reclaimed, and whether priority is strict, weighted, or aged. Candidate: cap interactive occupancy at one reserved worker, lend it only when idle, and interleave report starts with aging; disclose that a borrowed multi-minute report is not immediately preempted. If the product needs a hard interactive latency bound, define a runtime limit or cooperative checkpoint contract and measure it. Tokio’s FIFO semaphore is not a substitute for this host policy; large weighted requests at the head can block smaller ones [S06]. DRR is a comparison candidate, but applying a network-flow service-cost algorithm to multi-minute memory jobs is an inference [S10].

**P1.3 — “A per-extension cap prevents one submitter from occupying every slot.” — Retain, but narrow the guarantee.** A per-extension active cap limits the share of worker slots; it does not guarantee equal CPU, completion time, queue space, or memory use. Combine it with total and per-extension waiting-queue bounds, a global active limit, and an independent memory reservation gate. Count the extension that submitted a task, not the number of task IDs it creates. **Owner decision:** queue limits and active-cap defaults require expected user volume and measured workload data.

**P1.4 — “The waiting view exposes the limiting reason and allows cancellation or a temporary staff-selected priority increase.” — Retain and define.** Persist and show the actual blocker, such as global worker slots, extension turn, memory reservation, host pressure, or manual pause; scope any queue position and avoid unsupported ETA promises. A queued cancel should atomically remove eligibility and record CANCELED. The “promote one job” override should be scoped to one job, one use, and a short expiry; tell the user which peer work it jumps and record who/when/why. A separate “run despite estimate/pressure gate” override is optional and should be enabled only when an OS per-worker cap is active. Explain that it can exhaust that job’s cap, cause it to fail, and reduce application responsiveness. Do not let an override bypass the hard cap, payment restriction, or process-ownership rules. Progress/cancellation APIs such as VS Code’s withProgress and CancellationToken show a useful user-facing precedent, not a dependency or full design [S16].

### P2 — Memory admission, worker boundary, restart

**P2.1 — “Admission adds declared memory estimates and compares the total with a configurable budget.” — Correct.** Preserve the declared value as an untrusted hint. Use a separately measured class/input-size estimate and record measured peak per attempt. The scheduler should admit only when all independent gates pass: global slots, per-extension slots, and reserved memory under a configured budget that also respects current host availability and a safety reserve. Pause new starts when memory pressure crosses an owner-set threshold. Recompute reservations as actual evidence improves. Do not claim that this alone bounds actual usage.

**P2.2 — “The draft assumes extensions provide conservative estimates and has not selected an enforceable mechanism when actual usage exceeds them.” — Reject the conservative-estimate assumption; resolve the mechanism in phases.** This conflicts with the brief’s explicit warning that estimates may be inaccurate. Start with conservative admission, host observation, pressure pause, and low concurrency for unknown classes, but call this a soft guard. A hard per-task boundary requires OS support. On Windows, a Job Object can group associated processes and descendants, terminate the group, and enforce a job-wide committed-memory limit. Create/assign and verify membership before the worker can spawn children; account for breakaway, children created through Win32_Process.Create, nested-job/version behavior, and assignment failure [S01, S02]. On Linux, cgroup v2 memory.current and memory.peak account a cgroup and descendants; memory.high applies reclaim/throttle and may be breached, whereas memory.max is the hard control and may invoke an OOM kill inside that cgroup [S03]. Do not kill unrelated processes. Neither API is a security sandbox, and Windows committed bytes are not identical to Linux cgroup accounting. Linux support is conditional on cgroup v2, a controller-enabled writable delegated subtree, and one-writer ownership; systemd Delegate does not automatically enable memory [S03, S04, S05]. Do not require administrator rights or promise a hard cap where the host cannot obtain the boundary. In that fallback, disclose the missing hard limit, serialize or reduce concurrency, and pause on pressure. **Owner decision:** minimum supported Windows versions and Linux/cgroup/systemd configurations.

**P2.3 — “Host shutdown records queued jobs and stops owned workers; running jobs are marked interrupted on restart rather than claimed complete.” — Retain the distinction; correct lifecycle detail.** Queued rows remain queued after restart. Persist STARTING/RUNNING before launch; on startup mark unresolved attempts INTERRUPTED/RECOVERY_REQUIRED, advance the generation, and reconcile their exact process group before retry. Windows KILL_ON_JOB_CLOSE can stop associated members when the last handle closes, subject to the job assignment/inheritance conditions above [S01, S02]. Linux cgroup cleanup is possible only inside an owned/delegated subtree; systemd/cgroup ownership is not a global writable namespace [S03, S04]. Store a verified worker identity or unit/cgroup path and never kill by process name or stale PID alone. Retry only if the extension provides an idempotency or validated checkpoint contract; otherwise ask the user or mark NEEDS_REVIEW. If worker liveness cannot be established, do not start a duplicate automatically. Execution can be at-least-once even when publication is one-winner. **Owner decision:** shutdown wait/grace period, and which task types qualify for automatic retry.

### P3 — Output, cancel race, fairness question, constraints, validation

**P3.1 — “Report output is written to a task-specific temporary location, then published with a completion record.” — Retain and make publication atomic to readers.** Write to a private immutable attempt/generation location. Keep it visibly partial or hidden until the host validates the result manifest and commits a SUCCEEDED record pointing at it. Readers must discover completed reports through that committed record, not by scanning a shared output directory. A crash may leave an unreferenced artifact; garbage-collect only after a grace period and a reference check. SQLite can atomically commit its own row, not the filesystem artifact together with it; use state/generation fencing to bridge that boundary. The host must control or mediate publication paths if it promises that extensions cannot publish elsewhere.

**P3.2 — “Cancellation sets the token and eventually terminates an unresponsive owned worker.” — Retain; define ordering and result states.** For a running job, first commit CANCEL_REQUESTED and invalidate its generation. Then signal the cooperative token, wait a bounded grace interval, and force-stop only the owned worker tree. Mark CANCELED only after the worker is confirmed stopped; until then show cancel requested/stopping. For a queued job, move directly to CANCELED. Keep progress and artifacts separate from terminal success. A late worker may finish its old attempt, but must fail the host’s publication compare-and-set.

**P3.3 — “The plan leaves the race between cancellation and publication unspecified, as well as fairness when continuous interactive work occupies its reserved capacity.” — Correct the first now; preserve the second as an owner decision.** Serialize publication and cancel transitions in the host state store with a compare-and-set requiring (a) current generation matches, (b) state is RUNNING, and (c) validated output is present. If cancel commits first, publication fails. If success commits first, cancel reports “already complete.” This guarantees a single visible result, not exactly-once execution. For interactive/report fairness, select and document the reserved-slot/borrow/aging policy before implementation; no source can infer whether interactivity or report throughput has priority.

**P3.4 — “No payment priority or administrator requirement is planned.” — Retain as hard constraints.** Never use extension revenue/payment in admission or fairness. OS enforcement must use ordinary user rights when supported, detect unsupported configurations, and provide a clear fallback. Never terminate a process outside a verified job-specific boundary.

**P3.5 — “Proposed validation includes estimate underreporting, burst submission, long-job starvation, cancel/publish races, host restart and low-memory behavior. No load experiment has run.” — Retain and expand.** These are proposed checks only. Add extension-capped queue saturation, bogus/missing estimates, class-lane saturation, bounded-lookahead starvation, hard-cap crossing, process grandchildren/breakaway, host crash between every publication transition, cancellation while output is staged, stale worker after restart, partial report labeling, UI responsiveness and stale progress. Run on both operating systems and with low/variable memory. Measure peaks and tail behavior, not only averages. No application test, workload experiment, or platform capability test has been executed in this stage.

**P3.6 — “The proposal should compare enforceable admission and fairness policies before choosing defaults.” — Complete the comparison; retain defaults as owner choices.** Fairness and process-boundary comparisons follow. The evidence rules out treating a worker count, semaphore, or declared estimate as the whole design. It does not establish the target product’s user count, preferred fairness metric, default limits, or available OS integrations.

**P3.7 — “This is a provisional draft for review after the declared reveal, not an endorsed answer.” — Retain.** This draft is provisional and responds to the released reference plan. No deployment or product decision is authorized.

**Already covered by the released plan:** host-owned queue entries, task/extension identity, class and estimate fields, interactive/report slot split, per-extension cap, wait reason, cancel and promotion control, configurable memory budget, separate workers, interrupted-after-restart state, task-specific temporary output, eventual termination of an unresponsive owned worker, no pay/admin priority, and the initial validation scenarios.

**Rejected or corrected:** trusting that estimates are conservative; treating worker count as memory bound; treating a cancellation token as a publication fence; treating a temporary file and completion row as one atomic commit; retrying unknown/non-idempotent tasks automatically; using a semaphore as the host scheduler; assuming Linux cgroup access exists; making strict interactive priority the fairness guarantee; force-killing by name or stale PID; or allowing a user override to remove a hard worker boundary.

**Uncertain pending owner or host evidence:** the meaning and bound of fairness; reserved-slot borrowing; class weights/aging; supported OS versions and Linux manager/configuration; default slot/queue/memory limits and host safety reserve; task checkpoint/idempotency contracts; whether retries may repeat external effects; power-loss durability and actual bundled SQLite version; cancellation grace; staff/user override roles; and fallback policy where hard caps are unavailable.

## Alternatives and recommendation

| Concern | Alternative | Benefit | Cost/limit | Stage recommendation |
|---|---|---|---|---|
| Fairness | One global FIFO | Simple order | An extension burst delays all peers; blocked head can idle eligible capacity | Keep as baseline test only |
| Fairness | Strict priority with a reserved interactive slot | Predictable priority preference | May starve reports or waste capacity; borrowing a slot delays next interactive job until work finishes | Product policy decision; document slot borrowing and starvation bounds |
| Fairness | Per-extension round robin plus extension active cap | Transparent, bounded next-start share | Equal turns are not equal CPU/memory or completion time | Best simple candidate to prototype |
| Fairness | Weighted DRR by class or measured service | Expresses deliberate shares; deficit carries across turns | A network queueing algorithm is only an analogy; cost estimates are wrong and jobs are not preemptible | Compare after measuring class costs; do not assume it is the winner |
| Concurrency | Semaphore only | Cheap bound on permit count | No durable job record, tenant identity, wait reason, host memory bound, or forced stop; FIFO weighted waiter can head-block | Use only under the scheduler as a gate |
| Execution | In-process task | Lowest launch overhead | Cooperative cancellation; host and extension share crash/memory failure | Reject for untrusted or memory-heavy work unless each task is demonstrably bounded/cooperative |
| Execution | Child process without OS accounting | Killable boundary and crash separation | Same user permissions; descendants may survive unless captured; still no hard memory bound | Minimum boundary, with strict lifecycle handling |
| Execution | Windows Job Object / Linux cgroup v2 | Per-task process-tree management and OS memory accounting/limits | Different metrics and semantics; Linux delegation/controller availability conditional; Windows job setup/inheritance can fail | Preferred capability-detected adapter when available; test target OS versions |
| Execution | External broker/service | Durable/distributed work and recovery features | Adds installation, service/credentials, operations and often admin/deployment scope | Exclude from first phase unless multi-machine need is established |

**Fairness candidate:** represent each extension as a bounded FIFO queue and choose a ready extension per turn, with an active-per-extension cap. Apply an owner-approved bounded weighted rotation between interactive and report classes plus queue-age promotion. Scan a small configurable number of waiting jobs for an eligible memory/worker fit, recording each skipped reason; an aging/barrier rule prevents a large job from being skipped indefinitely. The scheduler only promises an admission opportunity. For service-time fairness, use measured occupancy and checkpointable slices or accept that long non-preemptible jobs limit the guarantee.

**Memory candidate:** keep three numbers separate: extension declaration, host’s class estimate, and runtime observed peak. For each start, reserve max(class baseline, confidence-adjusted estimate), constrained by a configurable host budget and dynamic available-memory/pressure safety margin. Compare reservation with runtime peak and label underestimates. Fit models by OS, extension/task class, input size and version; sample p50/p95/p99 and preserve cold-start fallback. Job Object committed-memory and cgroup memory.current/peak are not interchangeable, so do not pool their values. Use each OS boundary for its own task-level limit. If a boundary is absent, do not claim a strict task cap.

**Embedded queue candidate:** local SQLite offers compact transactional state and WAL reader/writer overlap for a one-host desktop queue. It has one writer, requires same-host access in WAL mode, and needs checkpoint lifecycle care [S11, S14, S15]. Pin an SQLite build with the WAL-reset fix (3.51.3 or later, or a verified backport), not a release in the affected range; validate the actual bundled build [S11, S12]. Choose FULL when a committed queue transition must survive power loss; NORMAL in WAL may roll back recent commits after power loss even though ordinary app crashes remain durable [S13]. Keep transactions short and exclude worker execution from DB transactions. External brokers remain a future alternative, not a hidden requirement.

## Corrected lifecycle contract

- **Submission:** validate host-verified extension identity, task class and input identity; persist QUEUED atomically. Enforce total/per-extension queue limits and return an actionable full-queue error.
- **Admission:** require global and per-extension slots plus memory reservation. Record why any job waits. Respect OS capability flags and current pressure. A user override cannot weaken the hard worker cap or ownership boundary.
- **Start:** commit STARTING and a fresh attempt/generation before launch; attach to the platform boundary and verify membership before allowing job code to run; then record RUNNING. If attachment fails, terminate only the just-created verified process or fail closed.
- **Progress:** accept rate-limited phase/message and optional monotonic completed/total. Persist last update; display indeterminate when the extension cannot quantify work. Progress is not evidence of checkpointability.
- **Cancel:** persist CANCEL_REQUESTED and invalidate current generation before asking the worker to stop. Escalate after a visible grace period. CANCELED and success are exclusive terminal results.
- **Publish:** stage to attempt-scoped storage; validate artifact/manifest; commit SUCCEEDED plus a pointer only if state and generation still match. The UI labels partial outputs and never presents them as a completed report.
- **Restart:** retain queued rows; reconcile interrupted process groups; invalidate previous generation; retry automatically only for a task explicitly safe to replay or resume. Otherwise present interrupted/needs-review state. Never call a task complete merely because the host shut down.
- **Audit:** retain wait/cancel/override/worker-exit/measurement/recovery reasons and policy version. Avoid storing sensitive document contents in queue telemetry; use the host’s existing document-access contract.

## Measured values and proposed validation

**Values needing measurement before defaults:** worker startup/IPC overhead; queue-to-start and interactive completion latency; elapsed time and CPU per task class/input size; per-attempt peak memory and estimate error distribution; system available memory/pressure versus task peaks; disk/report output sizes; SQLite state write/checkpoint cost and recovery time; force-stop latency; progress event volume; how long users tolerate each wait reason; and the proportion of tasks that can safely checkpoint/retry.

**Proposed, not executed:**

1. **Scheduler policy tests:** one extension submits a burst while several others submit short and long jobs; verify bounded active slots, queue limits, no revenue input, per-extension turns, class behavior, memory-block lookahead, aging and manual override effects. Compare global FIFO, strict priority, round robin, and weighted DRR over fixed and skewed service-cost sequences.
2. **Estimate/error tests:** missing, understated, overstated, stale, and adversarial declared estimates; measured class baselines; low-memory/pressure state changes; prove a concurrency count never stands in for a memory gate.
3. **Platform boundary tests:** Windows supported versions, nested/host job assignment, suspended start/assignment failure, grandchildren, breakaway flags, committed-memory cap, close-kill; Linux cgroup v2 absent/present, memory controller unavailable/enabled, no/available delegation, descendants, memory.high throttle and memory.max/OOM; prove unrelated process identities are never touched.
4. **Cancellation/publication race tests:** cancel queued/running at each state transition; cancel during report generation, after file close, before success CAS, and after success CAS; verify exactly one terminal outcome and no report visible after cancellation.
5. **Crash/restart tests:** terminate host before/after each state write and worker launch, with old worker alive, with artifact staged, and immediately before/after publish commit. Verify generation fencing, old-worker reconciliation, no duplicate unsafe side effects, queued survival, partial output visibility, and orphan cleanup.
6. **Load and UX tests:** short interactive plus multi-minute report workloads on Windows/Linux with varied memory, extension bursts, full queue, pressure transitions, worker leak, disk full, and stale progress. Measure p50/p95/p99 memory/runtime/queue wait and UI latency, wait-reason accuracy, cancellation completion, fairness by extension and class, and user comprehension of the manual override.
7. **Database checks:** crash recovery and concurrent state writes on the exact bundled SQLite release; confirm WAL version fix, one-writer busy handling, checkpointing and selected synchronous durability. No product test or performance experiment has been run here.

## Open owner decisions

1. What is the promised fairness unit: opportunity to start, worker occupancy, CPU time, or completion latency? What maximum wait counts as starvation?
2. Is the reserved interactive slot exclusive or borrowable? Can report tasks be preempted/checkpointed? Which class weights and aging limits are acceptable?
3. What are the supported OS versions and Linux cgroup/systemd environments? Is a hard per-worker cap required to run heavy jobs, or is a disclosed low-concurrency fallback acceptable?
4. What default global/per-extension active and queued limits, host memory safety reserve, estimate fallback, hard cap and pressure thresholds fit the existing application? These require measurements.
5. Which extensions promise idempotency or versioned checkpoints, and what external side effects may they perform? Is automatic retry allowed for each class?
6. Must queued/running state survive power loss or only app/OS crashes? Should the local queue use SQLite WAL, what SQLite version is bundled, and what synchronous mode is acceptable?
7. May a user promote one job? May they override a soft memory-pressure estimate gate when an OS hard worker cap exists? Which staff roles can do so, and what audit record is required?
8. How long should cancellation wait before force-stop, and how should the UI distinguish cancellation requested, stopping, canceled, interrupted, failed, partial, and complete?
