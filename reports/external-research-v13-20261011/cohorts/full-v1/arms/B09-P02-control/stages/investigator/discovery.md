# Independent discovery — before exact-plan release

**Scope.** This discovery is based on the admitted brief only. It treats the task as a research-backed proposal for a Windows/Linux desktop extension host, not an implementation. The brief names no host application, repository, runtime, framework, callers, or test suite. I therefore inspected upstream references that are plausible alternatives, including Tokio's semaphore implementation and tests, but cannot make app-specific caller/test claims. I did not execute downloaded code, run tests, or measure workloads. No load or failure validation has been run.

## Candidate queue and fairness approaches

A host-owned, persistent queue is the natural control point: extensions submit declarative jobs; the host records them and decides eligibility, active work, cancellation, state, and report publication. Separate per-extension FIFO queues allow one scheduling turn per extension rather than letting one extension's burst fill the global head. Add bounded total and per-extension queue depth, a per-extension active cap, and a global active cap. Reject overflow with an explicit reason. Use a single scheduler that emits a durable wait reason for every non-started job.

Fairness alternatives have different meanings:

- **One global FIFO** is simple and predictable, but a large burst from one extension pushes all other work back. A memory-heavy or otherwise ineligible job at the head can also block jobs that could run now.
- **Strict priority** can protect short interactive tasks, but sustained high-priority arrivals can starve batch work.
- **Per-extension round robin** is an understandable first policy and stops a single extension's queue from taking every next start. It is fairness in admission order, not equal CPU time or completion latency; several-minute non-preemptible tasks still occupy slots.
- **Deficit round robin (DRR)** can give extensions weighted turns while accounting for an estimated service cost. The original DRR paper is for packet flows and mentions other non-breakable service such as load balancing. Transfer to extension jobs is an analogy: a bad runtime or memory estimate can misprice a job, and a scheduler cannot preempt a running job unless the task supports checkpoints. Treat DRR as a candidate to prototype against simple round robin, not as a proven fit.
- A semaphore only bounds simultaneous permit holders. Tokio 1.53.2 documents FIFO waiter order and head-of-line blocking when a large acquire_many request is at the front; its implementation maintains a waiter list and its test suite exercises acquire/release and stress behavior. That is a useful primitive, not a persistent multi-tenant queue, memory bound, wait-reason API, or fairness guarantee for extensions. A 2022 Tokio issue also reports a non-cooperative task preventing another task from progressing. The host must retain control over its own scheduler loop and avoid relying on cooperative yielding for an untrusted extension.

A practical candidate is round robin over stable extension IDs, optionally weighted by host-defined class, plus small bounded lookahead past resource-blocked jobs and age promotion so a large job cannot be skipped forever. Keep interactive and batch classes distinct, but use bounded weighted turns or aging rather than strict priority. State explicitly that this improves start opportunities only. If an owner requires equal service time or bounded response time, it must add cooperative slices/checkpoints or duration limits and define the compatibility contract.

## Resource estimates and admission

Concurrency is a count of running jobs, not a memory budget. A host can reserve estimated memory and change the budget as available-memory or pressure readings change, but estimates are admission hints rather than hard guarantees. Keep the extension's declaration for diagnostics; separately measure actual per-job peak and use a conservative class estimate (for example, a measured high percentile plus headroom) keyed by task type and input-size class. Unknown or low-confidence tasks should use a conservative default and a small concurrency allowance; do not trust a self-declared value as proof of safety.

The proposed admission rule has separate gates: global worker slots, extension slots, and a memory reservation budget bounded by configured headroom and current host availability. It should leave a host safety reserve and pause new starts under pressure. A per-worker OS limit is a separate containment boundary; it does not turn estimates into an aggregate host memory guarantee. The measurements that would set the values are unknown: peak task memory, runtime, CPU, input/output bytes, startup overhead, host memory availability/pressure, queue-to-start latency, and report volume, split by OS, task class, input size, and extension. Measure Windows job committed memory and per-process/private bytes; on Linux record cgroup memory.current/memory.peak where available, not only RSS. Recalibrate after releases and keep the OS and task-class samples separate.

## Execution-boundary alternatives

- **In-process async tasks** have low startup and IPC cost, but cancellation is cooperative and a memory-bound task shares the host's failure domain. A stuck extension can make the UI unusable. A concurrency semaphore does not solve these problems.
- **One child worker process per job** adds launch/IPC costs, packaging and crash-recovery work, but gives the host a task-specific process tree to stop and account. It is the useful portable baseline to compare. A child process with the same user permissions is not a security sandbox.
- **OS-managed process groups** can improve containment and measurement with no administrator grant when the host OS exposes a usable boundary. On Windows, Job Objects group processes, normally include CreateProcess descendants, support job-wide committed-memory limits, and can terminate all members. Closing the last handle with KILL_ON_JOB_CLOSE terminates members. Exceptions include breakaway behavior, processes created through Win32_Process.Create, and assignment/lifecycle races; validate job membership before resuming the worker, and test the host when it is already inside a job. A job-memory limit is committed memory, not a promise of a universal working-set cap.
- **Linux cgroup v2** can account a process subtree: memory.current includes the cgroup and descendants, memory.peak provides a peak, memory.high throttles but may be exceeded, and memory.max is the hard control that may invoke the cgroup OOM killer. That OOM boundary is useful because it targets the cgroup rather than unrelated host work. It still is not available uniformly: controllers must be enabled, a writable subtree must be delegated, and cgroup ownership is single-writer. systemd explains that Delegate makes a subtree available but does not itself enable the memory controller. Verify capability at runtime; do not write into systemd-owned cgroups or assume every Linux desktop has a user-delegated cgroup.
- **External broker/service** can provide mature distributed queues and recovery, but would add installation, account/service, and operational requirements that the brief does not authorize. Compare it as a future option only if multi-process or multi-machine execution becomes a real requirement.

A portable design must detect resource-boundary capabilities. If a hard worker cap is unavailable, it must report that it cannot enforce a strict per-job memory limit and use conservative reservations, single/low concurrency, and host-pressure pausing; it must not imply those measures guarantee memory containment. Never kill by a broad process-name match or act on a stale PID without verifying the exact owned worker identity.

## Cancellation, progress, reports, and restart safety

Use a durable state machine such as QUEUED → STARTING → RUNNING → CANCEL_REQUESTED → CANCELED, with distinct SUCCEEDED, FAILED, and NEEDS_REVIEW/INTERRUPTED outcomes. Persist state transitions, attempt number, opaque generation/fencing token, extension ID, original inputs/snapshot, declared and measured estimates, class, progress, timestamps, wait reason, and artifact manifest. Keep the queue ledger local to the desktop profile; SQLite WAL is an embedded option with concurrent readers and one writer, only for processes on the same host (not a network share). Check its lifecycle carefully: the current SQLite history records the rare WAL-reset corruption bug through 3.51.2 and the fix in 3.51.3 and later (with listed backports). If WAL is selected, require a fixed release and test the actual bundled SQLite build. FULL versus NORMAL synchronous mode is an explicit durability/performance decision: in WAL mode NORMAL preserves consistency but recent commits can roll back after power loss; FULL adds a sync for each commit. Keep transactions short, handle SQLITE_BUSY, and checkpoint without long-lived readers. No database transaction can atomically commit arbitrary report-file writes at the same time.

For result safety, write each attempt to a private staging location, keyed by job and generation. Expose nothing as a completed report until the host has validated the artifact and committed a terminal-success row with its artifact pointer using a compare-and-set on the still-current generation and RUNNING state. Cancellation atomically changes state and generation first, then requests cooperative cancel; after a grace period the host stops only that job's process group. A late worker can only write an abandoned attempt file and cannot publish. If success commits first, a later cancel must return “already complete”; if cancel commits first, success publication must fail. Retain/garbage-collect orphan attempt directories only after a grace period and reference check. This is an application-level fencing design to validate, not a database/filesystem transaction claim.

On restart, queued rows remain queued. A row previously STARTING or RUNNING becomes a recovery candidate: find and stop the exact old worker if still alive, advance its fencing token, then retry only if the task declares idempotency or has a host-validated checkpoint contract. Otherwise mark it NEEDS_REVIEW and ask before replaying effects. A retry may execute work more than once; only publication should be one-winner. If the OS boundary cannot prove the old worker is gone, do not launch a duplicate automatically. Checkpointing is an extension contract with versioned checkpoint data and input identity, not inferred from a progress percentage.

Progress should be structured, optional, monotonic, and rate-limited: phase text plus completed/total when totals are meaningful; otherwise show indeterminate progress and last update time. Show queue position only with a scope label (e.g. within extension/class), explain the current block (“waiting for a worker slot”, “memory reservation”, “extension turn”, “host memory pressure”), and offer cancel from queued and running states. Do not promise a precise ETA when runtime estimates are weak. Record cancellation request, force-stop, exit, publication, and recovery separately. A one-job “promote” override can bypass normal fairness order and explain whose turn it skips. A “run despite estimate/pressure gate” override should be explicit, one-use, audited, expire automatically, and be available only with an OS worker cap; state that it may make this job fail at the cap and can reduce responsiveness. Neither override permits payment-based priority, kills unrelated processes, or silently raises the OS hard cap.

## Proposed integration and validation (not run)

1. Add the durable host-owned state/API and explicit submit/queue/wait/cancel/progress/terminal states; bound queued records and validate extension identity/input snapshots.
2. Add the pure scheduler and deterministic policy tests for global slot, extension turn, class/aging, memory reservation, stale estimates, overrides, and blocked-job lookahead. Compare FIFO, round robin, and DRR on burst mixes; record admission fairness separately from service/latency fairness.
3. Add one-worker-per-job execution and platform adapters. Validate Windows job assignment/descendant capture/close-kill and Linux cgroup delegation/controller/limit/OOM behavior on supported configurations. If a hard cap is absent, surface capability and the conservative fallback.
4. Add cancellation fencing and staged publication, then crash/restart recovery. Inject host termination before/after each state transition, while a worker runs, after staging and before/after success commit; verify no canceled/stale attempt becomes visible and no unrelated process is touched.
5. Add the UI wait explanations, progress, cancel, manual override, and “partial versus complete report” marker. Verify keyboard/accessibility and 20–50-job queue loads without blocking the UI.
6. Run cross-platform burst/load experiments on low, medium, and high memory devices with short and multi-minute jobs, skewed and inaccurate declarations, worker leaks, host pressure, cancellation races, full disk, and restarts. Measure p50/p95/p99 peak memory/runtime, queue wait, interactive latency, start fairness by extension, worker termination time, orphan files, DB recovery, and false/unknown wait reasons. None of these checks has been run in this research stage.

## Questions for plan comparison

Resolve owner choices about the fairness guarantee (turns versus service time), whether classes have weighted turns, which tasks can checkpoint or safely retry, default job/queue/memory caps, acceptable behavior when OS enforcement is unavailable, Linux systemd/cgroup minimum support, report durability after power loss, and whether users may override memory-pressure admission. Keep each as an owner decision until the released plan supplies the governing clause.
