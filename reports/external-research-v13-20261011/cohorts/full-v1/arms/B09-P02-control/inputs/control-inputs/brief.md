# Background extension task admission and fairness

An existing desktop analysis application allows extensions to submit background tasks for document inspection and report generation. Design its admission and scheduling component so a burst of tasks from one extension does not make the application unusable or starve other work. Some tasks are short and interactive; others consume substantial memory and run for several minutes. The host can obtain declared estimates but cannot assume they are accurate.

Research queue ownership, resource limits, cancellation, progress reporting and safe resumption after a host restart. Users should see why a task is waiting and be able to cancel a queued or running job. A report must be distinguishable from partial output, and canceled tasks must not quietly publish results afterward. Assume Windows and Linux desktop use with variable available memory. Do not equate a concurrency count with a memory bound, require administrator rights, prioritize extensions according to how much they pay, or terminate unrelated user processes. The design should support a useful manual override while explaining its consequences. Compare viable fairness and execution-boundary approaches, and specify which estimates require measurement. Propose phased integration and failure/load validation rather than a full scheduling platform or a deployment in the existing application.

Produce a research-backed software proposal, not an implementation. Explore relevant primary documentation, repository code, callers/tests, and issue-to-fix or release history where consequential. Compare feasible alternatives without assuming a winning product. Distinguish proposed validation from work actually executed. The exact draft plan is withheld during brief-only discovery and released once at the declared comparison point.

Complete all substantive research and planning obligations within a maximum of 60 elapsed minutes. Finish earlier when the complete output is ready. There is no minimum research duration, no requirement to consume the allowance, and no credit for waiting. The deadline includes arm-specific setup, provider queueing after admission, tools, native retries, handoffs, revision and delivery. Output quality is assessed independently of elapsed time.
