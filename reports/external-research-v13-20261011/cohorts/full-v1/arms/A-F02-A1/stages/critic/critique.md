# Independent critic review — A-F02-A1

**Scope:** oral-history intake and transcript handoff, run A-F02-A1. I read the complete brief, investigator discovery, draft, source map, released plan, plan-reveal record, and carried `sources/README.md` named in `input-map.json`. The SHA-256 of the released-plan copy is `5f7ff916807818307634a6a4b42dea7ed030547adae267d936cce489384d6ab2`, matching `plan-reveal.json`. I did not inspect museum media, spreadsheets, catalog records, or other candidates.

## Judgment

The proposal covers the brief well and keeps its status as a research proposal. Its main corrections to the released plan are sound: it rejects the unvalidated filename normalization join, changes “unreadable original” to a build/probe-scoped result, and rejects the assumption that catalog paths remain usable after an export directory is copied. The source matrix and limitations are generally described with appropriate conditions. I found no material factual claim in the checked draft that is contradicted by the primary sources.

There are two material incompletions to carry forward: crash recovery across a media-file rename and its separate manifest/checkpoint update is not specified; and the MediaInfo SDK candidate omits its documented default Internet contact. Neither is a demonstrated failure in an implementation, because none was built. The missing museum data, rights vocabulary, target platforms/catalog contract, and museum application repository remain external inputs rather than questions public documentation can answer.

| F03 | **Material wrong in released plan; corrected in draft** | Released-plan C12; draft “Resumable batch and portable handoff” and C12 disposition. A path that resolves on the intake workstation is not established to resolve after a directory copy. BagIt defines payload files as opaque octet streams and uses manifests for checksums; it does not give payload paths catalog semantics. PBCore offers optional duration/channel fields and an instantiation identifier, but is not a receiving-catalog API. [S15](sources/README.md#s15) [S16](sources/README.md#s16) | Correctly reject the receiving-catalog assumption. A self-contained package with relative references or a verified durable URI contract are feasible alternatives; which one works depends on the real catalog. FFmpeg’s current download page lists 9.0.2; GStreamer capability depends on installed plugins; MediaInfo is metadata-only here. Support is correctly limited to a tested release/build/feature/plugin/platform combination. [S02–S09, S13] |
