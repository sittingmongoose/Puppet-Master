# Brief-only discovery — oral-history intake and transcript handoff

**Basis:** the released research brief only. Prepared before the comparison-plan release. No museum media, spreadsheet, catalog, or collection records were available or inspected.

## Requirement map and design implications

| Brief obligation | Discovery implication |
|---|---|
| Identify formats despite inconsistent extensions; extract metadata and duration | Probe file content and reported streams, treating extension as a hint only. Keep container, codec, stream index, channel count/layout, sample rate, duration, and probe outcome as separate fields. A probe's inability to read a file means “unreadable by this probe/build,” not proof of intrinsic corruption. Duration can be absent or approximate; preserve the reported value and its source/status instead of substituting zero. |
| Preview recordings with two speakers on different channels | Preserve the full original and expose track/channel count and any declared layout. Offer staff-selectable channel audition from decoded samples, without changing the stored payload. Do not infer which person is left/right or relabel a channel unless a volunteer confirms it. Record a missing/unknown layout explicitly. |
| Associate transcripts with recording identifiers; handle later corrections | Use the spreadsheet's stable recording identifier as the join key, not a filename guess. Preserve the supplied identifier and any normalization rule; duplicate, absent, or conflicting keys go to manual review. A corrected transcript is a new linked revision with its own filename/hash/revision date and relation to the same recording; do not silently replace prior evidence. |
| Safely restart batches | Keep persistent per-item states/checkpoints and make repeated scanning idempotent. Bind state to an exact identifier plus a streaming SHA-256 of observed bytes; on restart, recheck source identity before resuming and treat changed bytes as a new version/review. Commit each item atomically, make partial-copy cleanup recoverable, and never modify/move the source. Concurrency and memory should be bounded for 40 usual and 500 maximum items. |
| Hand off portably without a fixed catalog API | Separate local intake working state from a stable export package. BagIt provides a useful packaging/fixity option: payloads are opaque bytes accompanied by checksummed manifests, but the specification does not define catalog metadata semantics. PBCore 2.1 describes media instantiations, duration, channels and identifiers; use it only if the catalog can ingest it. A versioned CSV/JSON manifest plus unchanged media remains an alternative pending catalog-owner choice. |
| Distinguish unreadable media, unsupported preview and absent transcript | Model independent statuses: probe/readability, preview capability, transcript presence/revision, permission, and staff acceptance. Example messages: “Could not read media with this intake build; check the original file” versus “Media metadata was read; preview is unavailable because this build lacks a decoder.” “No transcript supplied” is a neutral transcript state, never an audio failure. An unsupported preview does not itself imply rejection. |
| Preserve byte identity, permissions, privacy and throughput constraints | Open source files read-only; never transcode originals or require a transcode for catalog acceptance. If the handoff copies originals, byte-copy and hash-verify them. A blank/ambiguous permission remains unknown / awaiting confirmation and cannot be converted to permission to use or publish. No cloud transcription: transcript intake is file association only. |
| Keyboard and meaningful textual status | All review, acceptance/rejection, channel audition and recovery actions need keyboard paths, visible focus and status phrased in text rather than color/icon alone. Expose names, roles, values and dynamic status through the actual UI accessibility layer. WCAG 2.2 is a useful reference for keyboard operation and status messages; Slint provides FocusScope/KeyBinding and accessibility roles/labels, but real assistive-technology behavior remains target-platform validation. |

## Feasible approaches found; no winner selected

1. **FFmpeg / ffprobe, with a separate preview path.** ffprobe detects/probes supported multimedia streams and can emit JSON, including container and per-stream sections, plus an error section. That makes it a strong metadata/format candidate, not a guarantee of playback. The official download page reported FFmpeg 9.0.2 as the latest stable 9.0 release on this research date and notes that build/release branches and development differ. Pin the exact binary/build and record its enabled demuxers/decoders; ffprobe and the preview player may have different capability. This broad option adds a native dependency, distribution/licensing decisions and untrusted parser exposure. [S01–S02]
2. **GStreamer discovery and playback pipeline.** GstDiscoverer exposes duration, stream topology, channel count and channel mask; playback can report missing plugin messages. This supports an integrated design, but installed plugins and OS packaging govern what can be previewed. Its missing-plugin protocol reports missing demuxer/decoder under the same “decoder” type, and the application chooses policy. A recognized-but-not-previewable state should therefore remain distinct from failure to identify/read input. [S03–S04]
3. **Symphonia embedded in Rust, with a separate output device layer.** Version 0.6.1 is pure Rust and feature-gated. The pinned crate's Cargo.toml defaults to SIMD, metadata, ADPCM, FLAC, MKV, OGG, PCM, Vorbis and WAVE; AAC, ALAC, MP3, AIFF, CAF and ISO/MP4 are opt-in, so a “supported format” claim is only true for the exact feature set. Its own player separates probe-only, decode/verify and playback paths and notes decode errors/output failures separately. It is attractive for a controlled embedded build, but the default matrix is narrower than a general media toolkit and audio-device/platform work remains. [S05–S09]
4. **MediaInfo SDK as a metadata-oriented alternative or cross-check.** It opens files, enumerates stream kinds/numbers, and returns individual fields or formatted reports. It does not provide the preview path here, so it still needs a separate player and capability state. Its documentation notes a Windows command-line Unicode caveat; library API is the safer integration point for international filenames. [S13]

Support ends at the exact built and tested combination of container/demuxer, codec/decoder, metadata reader, stream arrangement and preview output backend. Maintain an explicit support matrix with version/build/features and test fixtures. Keep “identified and catalogable” separate from “previewable.” Never claim “all audio formats.” Symphonia 0.6.1 release notes include fixes for MP3 silent sections/tags/mono MP1, Opus-in-ISO channel information, and parser hardening after fuzz-found panics; earlier v0.5.5 release notes improved ADTS duration approximation. These are concrete reasons to pin versions and regression-test duration, channels and corrupted inputs rather than trusting a library label. [S09–S12]

## Portable record and review-flow shape

A candidate item record keeps: original collection identifier; relative source name/path and observed byte size/SHA-256; detected container, codec, stream IDs, channels/layout, sample rate and duration together with source/version and known/unknown status; independent probe, preview, transcript, permission, and human disposition states; reviewer/time/reason; associated transcript revision(s); and export-copy checksum. Avoid embedding inferred speaker names, transcript content, or permissions from filenames/metadata. Treat technical tags as untrusted descriptive metadata, not permission evidence.

Use separate terms/states for `probe unreadable`, `probe identified`, `preview available`, `preview unsupported/unavailable`, `transcript absent`, `transcript supplied/revision`, `permission unknown/confirmed/restricted`, and staff `accepted/rejected/needs review`. Persist per-item results so a retry updates/reuses the same record; source bytes changing under a stable ID requires review. SQLite transactions are one feasible local checkpoint store, but a plain append-only journal or a catalog-provided staging API may fit better after concurrency/storage decisions. [S14]

A staged path can first inventory and fingerprint without writing to sources; next allow volunteer review and channel audition; then produce a portable package/csv-json export after explicit acceptance decisions; finally adapt that export to the selected catalog. Any local preview decode may buffer/convert samples in memory for the device, but the original file remains byte-identical and no derived full-copy/transcode is required. No catalog API, deployment platforms, metadata authority, or exact permission vocabulary is fixed, so those remain owner decisions.

## Validation candidates versus work performed

**Proposed, not run:** (a) extension/content mismatch, corrupt/truncated file, valid but uninstalled decoder, unsupported container/codec, missing/incorrect duration, two discrete speech channels and absent layout; (b) sample-by-sample original SHA-256 invariance across probe/preview/restart and exact hash match for exported copies; (c) duplicate IDs, filename collisions, absent transcript, replacement transcript, duplicate/conflicting spreadsheet rows and unknown permission; (d) interrupt at each per-item boundary and restart batches at 40 and 500, checking idempotent records/no lost accepted/rejected decisions; (e) verify BagIt manifests/PBCore syntax if selected; (f) keyboard-only traversal, focus order/visibility, screen-reader status announcements, and non-color status; (g) ensure no recording bytes are sent over the network; (h) verify each format/backend on the supported target OS matrix using freely licensed fixtures.

**Executed in this stage:** web research of primary documentation, pinned upstream Symphonia source/caller/test-tool code and release/issue history; no application build, test suite, media probe, collection inspection, or accessibility run. All validation above is a proposal, not a test result.
