# Research proposal — oral-history intake and transcript handoff

**Status:** investigator draft following the one-time plan release; provisional and not an implementation, collection migration, or deployment decision. The comparison plan is the released copy, SHA-256 5f7ff916807818307634a6a4b42dea7ed030547adae267d936cce489384d6ab2. Sources are indexed in [sources/README.md](sources/README.md) and [source-map.json](source-map.json).

## Proposal

Build a local, resumable intake workflow around a durable batch manifest and explicit per-record review. Separate four things that the draft currently risks conflating: whether bytes can be read/probed by this particular build; whether a chosen playback backend can preview the decoded stream; whether a transcript is associated; and whether staff accepts the donation for the catalog or permits it to be released. A missing/unsupported preview or absent transcript is not a failed recording.

Do not choose one codec or player before the museum decides its target operating systems and allowed support envelope. Evaluate a probe adapter and a preview adapter separately, then publish the exact versions, build features/plugins and test matrix. ffprobe is a structured metadata candidate; GStreamer can discover and play but installed plugins control capability; Symphonia 0.6.1 is an embedded Rust alternative with a narrower default feature set; MediaInfo is a metadata-only reader. A second reader may be useful for discrepancy checks. All parsers receive untrusted files, so cap concurrent work and record the exact parser/build used. [S01–S13]

### Record and state model

Create a batch record and item rows before parsing media. Keep, at minimum:

- The spreadsheet donation identifier exactly as supplied, original filename/path, observed size, SHA-256 algorithm/value and hash time; do not use technical tags or filenames as authority for a missing permission or identity.
- Probe status plus the probe/build version; reported container, codec, audio stream/track IDs, channel count/layout, sample rate, any available bit depth, and duration. Store missing/unknown duration as null with a reason/source, not zero. Preserve the raw probe result or the selected fields with provenance.
- A separate preview state: not attempted, playable, unsupported by this build, output-device error, or decode error. Record the reason/capability where available.
- Transcript state and immutable revision history; permission text/source and a separate unknown/confirmed/restricted state; staff disposition, reviewer, date, and reason.
- Export-copy path and checksum once a copy is made, so later handoff can be re-verified.

Use states such as **probe not run / identified / could not read with this probe / probe error**, **preview not run / available / unsupported / device error**, **transcript not supplied / supplied / correction pending / current revision linked**, **permission unknown / confirmed / restricted**, and **needs review / accepted for catalog / rejected**. Keep these independent. “Unreadable original” overstates what one selected parser can know; show “Could not read media with this intake build” and an actionable check/retry path. For an identified container/stream with no installed decoder, show “Media was identified; preview is unavailable because this build lacks the required decoder.” The item may still be accepted if the catalog's policy permits it. Show “No transcript supplied” as its own neutral status. A staff rejection always has a reason. [S01, S03–S05, S07, S17–S22]

### Read-only media handling and identification

Open source files read-only. Hash the bytes as a stream, and never move, rewrite, rename, or transcode a source. If the managed intake directory is the accepted copy location, copy byte-for-byte to a temporary destination and atomically finalize it only after the copy hash matches the observed source hash. An interrupted/partial copy remains an incomplete item that can be safely resumed or discarded without touching the source. At restart, re-read/re-hash the source: if the bytes changed under the same supplied identifier/path, mark it changed and require review instead of inheriting old probe or permission decisions.

Treat the suffix as a hint. Probe data to identify container and streams; include codec, stream index, layout/channel count and duration source where available. Report what the current build recognized; do not label a file corrupt solely because one build lacks a demuxer or cannot decode it. A supported format is the actual container-demuxer, codec-decoder, metadata reader, channel layout and output-device combination shipped and tested. Publish that support matrix; never claim support for every audio format. Probe metadata and preview capability are not interchangeable. [S01–S09]

### Preview and channel handling

Preview is optional and must not gate cataloging. For recordings where the two channels contain different speakers, make channel selection an explicit volunteer control. When the file and backend allow it, route one decoded channel to the listening device for audition, labeling it “Channel 1” / “Channel 2” until a staff member records who is speaking. Do not presume left/right mapping, combine two speakers, or modify the archive copy. A playback graph may remap decoded samples in memory; there is no need to write a converted media file for this audition. FFmpeg documents pure channel remapping under specific one-to-one/zero-one gain conditions, which is a candidate mechanism, not proof of behavior on every input/backend. Validate channel-isolation with known fixtures and headphones on each supported OS. [S03, S07, S20]

If metadata declares a layout, retain it and show it; if it does not, say unknown and expose ordinal channels. Channel count/layout may describe technical wiring rather than speaker identity. Staff-entered speaker labels are descriptive assertions and should carry provenance. Do not require transcript/audio time alignment for intake: preserve any timestamps already supplied, but show ordinary transcript text alongside audio if it is not time-coded. Whether time-synchronized transcript preview is a catalog requirement is an owner decision.

### Transcript, ID and permission rules

Use the spreadsheet's explicit donation identifier as the authority for the recording-to-transcript association. A filename-stem match can propose a candidate, but automatic lowercasing/removal of spaces is unsafe until the museum defines that equivalence rule and confirms uniqueness. Preserve raw identifiers, source filenames and any approved normalized comparison key. Missing IDs, duplicate IDs, collisions after normalization, multiple possible files, or a correction without an identifier go to a volunteer's manual association queue. PBCore describes an instantiation identifier as an unambiguous reference; that supports unique identifiers as a modeling need, but does not prove this museum's spreadsheet already has one. [S10–S12, S16]

Treat corrected transcripts as new, immutable revisions attached to the same stable recording ID. Record original filename, hash, receipt date/source if known, revision label, and superseded/current relation. A “current transcript” pointer may change, but do not overwrite or discard prior transcript bytes. Do not invent a version sequence from filenames; an unknown/ambiguous correction requires staff review.

Preserve permission text verbatim with spreadsheet/row provenance. Unknown or conflicting permission stays unknown/restricted and blocks external release until authorized. It must never be guessed from the recording, transcript, catalog tags, or an absent value. Keep the distinction between internal catalog acceptance, restricted internal preservation, and public/released access; the museum owner must decide exactly which state the plan's word “release” means. No recordings are sent to cloud transcription, and the app should not silently invoke transcription. [S16]

### Keyboard review, status text and batch progress

The review table should be usable without a pointer: focusable rows, predictable next/previous item movement, playback and channel selection, accept/reject/review actions, and a visible focus indicator. Give controls meaningful accessible name, role and state; status text must not depend on color or an icon. Expose the same per-row statuses to the platform accessibility API.

For progress, use a persistent text summary such as “21 of 500 checked; 19 identified, 2 need review” and coalesce routine updates into polite milestones. Announce individual exceptional/blocking errors when useful, keep a browsable textual log, and do not move focus to progress. Avoid announcing every file event. W3C guidance says progress/status updates should be available without focus and should not unnecessarily interrupt; ARIA status is a polite web live-region model. Slint offers accessibility properties and focus/key scopes, but this is not evidence that a native build announces those states consistently on all screen readers. Pick announcement frequency after target-platform testing with keyboard and screen-reader users. [S17–S19, S21–S22]

### Resumable batch and portable handoff

For 40 usual / 500 maximum recordings, use bounded concurrency and streaming hashes rather than loading a batch into memory. Persist per-item state after each completed phase; retries for the same stable ID and byte hash reuse completed work, while changed bytes, duplicate IDs and changed spreadsheet rows reopen review. SQLite transactions are one option for atomic local status updates, with a defined SQLITE_BUSY/retry strategy; an append-only journal or catalog staging service is another. The catalog is not fixed, so storage choice remains open. [S14]

Do not assume a receiving catalog can resolve machine-local or temporary media paths after an export folder is copied. The portable export should carry a manifest, transcripts, unchanged media bytes (or an explicitly supported durable URI contract), stable relative identifiers, and checksums. Prefer self-contained relative paths if files are packaged. BagIt 1.0 is a viable optional package layout with payload manifests/fixity, but it intentionally gives payload files no metadata semantics. PBCore 2.1 is a possible metadata mapping for identifiers, format, duration and channel arrangement; use only if the recipient supports it and its schema/API is confirmed. A simpler versioned CSV/JSON sidecar is also feasible. Never bind the design to a made-up catalog API. [S15–S16]

## Corrections, optional improvements and owner decisions

**Corrections to the draft plan:** do not attach transcripts automatically under an unvalidated lossy normalization rule; do not label parser failure as proof the original is unreadable; do not let unsupported preview fail intake; do not assume a catalog resolves nonportable media references after a folder copy; preserve exact permission/identifier data; keep any preview remapping transient and leave source bytes untouched. These corrections follow the brief's hard constraints and the identified conditions in the primary sources.

**Optional improvements:** retain probe tool/version and raw/normalized metadata separately; record uncertainty/provenance for duration and channel layout; use SHA-256 manifests for transferred copies; offer channel audition; include a full, moveable media package (BagIt if useful); attach immutable transcript revisions; support a read-only audit log and a textual batch summary; use licensed or generated fixtures, including malformed files. These improve auditability and recovery but should be scoped with staff.

**Owner decisions still needed:**

1. Which spreadsheet column is the authoritative donation ID, and what exact case/space/punctuation canonicalization—if any—is allowed? How should duplicate identifiers be corrected?
2. What does “release” mean for unknown permission: public catalog publication, any catalog import, or both? What exact permission wording and restriction states does the museum recognize?
3. Where are accepted originals retained, and should export be self-contained or reference managed storage? What catalog import/API and media URI rules actually exist?
4. Which operating systems and packaging model must be supported? Which codecs/container combinations are required by policy or historical holdings? This decision determines the probe/preview build matrix.
5. What transcript formats/revision fields are supplied, and is timecode alignment a requirement or simply preserved when present?
6. How should volunteers name the two speakers after listening, and how frequently should batch progress be announced to screen-reader users?

## Alternatives and support boundary

| Approach | Strengths | Conditions, limits and costs |
|---|---|---|
| FFprobe + separate player | Machine-readable container/stream info and error output; can be paired with an unrelated preview backend. | Metadata success does not guarantee preview. Pin exact FFmpeg binary/build and its enabled formats. Distribution/licensing, native dependency and parser isolation need review. 9.0.2 was the latest stable 9.0 branch release on 2026-10-12. [S01–S02] |
| GStreamer Discoverer + playback | One pipeline family can expose stream topology, duration/channel data and playback missing-plugin reports. | Installed plugins/OS package choices govern capability; app-level policy must distinguish unrecognized type from missing decoder/demuxer; packaging and plugin testing are needed. [S03–S04] |
| Symphonia + output adapter | Pure Rust, modular and feature-gated; pinned player source separates probe, decode and playback. | v0.6.1 default feature set is narrower than “all formats”; each optional codec/container must be enabled deliberately. Player/device output still needs platform work. Release history includes decoder fixes and fuzz hardening; use a regression matrix. [S05–S12] |
| MediaInfo SDK + separate player | Metadata reader with per-stream inspection; can independently cross-check technical fields. | Does not solve preview; pin SDK version and use its library API for Unicode paths. [S13] |
| Handoff metadata choices | PBCore 2.1 models audiovisual instantiation identifiers, duration and channel configuration; CSV/JSON is simpler; BagIt can package opaque bytes with checksum manifests. | No catalog API or import support has been specified. BagIt is a payload package, not a descriptive catalog schema. Confirm recipient fields, path resolution and rights vocabulary first. [S15–S16] |

The supported-format statement should be a finite table: tool/library release or commit, build features/plugins, OS, container/demuxer, codec/decoder, channel layout, metadata/duration behavior, preview outcome, and fixture result. Probe success, full decode verification, and audio-device playback are different checks. A file may be identified and accepted with preview unavailable. Unknown duration/layout or absent metadata is recorded, not fabricated. Symphonia release 0.6.1 fixed several concrete stream problems; a related ADPCM issue/PR shows that codec-family names can conceal variant gaps, and maintainers have described the challenge of reproducible private-media regression checks. [S06–S12]

## Staged integration proposal

1. **Decisions and fixtures:** obtain an authorized sample of spreadsheet shape and target catalog/OS details; define ID, permission and media-retention rules. No production collection is required. Create openly licensed/generated fixtures and a desired-format list.
2. **Manifest and read-only inventory:** create batch and item rows; capture source path/name, size and SHA-256; validate required IDs/permission fields; identify duplicates/missing data without changing files. Persist checkpoints and a manual-review queue.
3. **Probe adapter:** probe content locally with a pinned build. Record container/codec/stream/channels/layout/sample rate/duration, build identifier and errors. Keep extension as a hint. Separate unreadable-by-this-build from unsupported preview; store metadata with uncertainty.
4. **Volunteer review and preview:** show the keyboard-accessible table; allow optional play and ordinal channel audition when the selected backend supports it; record speaker labels only after human confirmation. Keep transcript absent, transcript revision, and permission statuses independent.
5. **Acceptance and portable export:** record accept/reject/review with reason; retain unknown permission gates. Copy unchanged media and transcript revisions into a checksummed relative-path package or write verified durable references. Validate references/package before handoff.
6. **Catalog adapter:** after the actual catalog import contract is known, map identifiers, rights and technical metadata to the supported schema/API. Keep the local manifest versioned for rollback and audit; do not silently discard source fields.

## Validation: proposed versus executed

**Proposed validations (not run):**

- Format: rename extensions without changing bytes; test valid and malformed/truncated inputs, one supported container with unsupported decoder, multiple audio streams, metadata-only success, missing/estimated duration, and unknown channel layout. Verify the exact UI status and that unavailable preview does not mean unreadable or rejected.
- Preservation: record source SHA-256 before and after probe and preview; byte-compare accepted copy with source; interrupt copy at boundaries and verify a retry yields exactly one finalized item and unchanged original. Test same ID with changed bytes.
- Channel: use a known dual-speaker fixture; play channel 1 then 2 and confirm the other channel is absent from each audition; verify source/copy hash remains identical. Test unknown channel mask and multichannel input.
- Identity/transcripts/rights: exact match, missing ID, duplicate ID, collision after case/space normalization, same basename with different IDs, no transcript, corrected transcript, duplicate permission row, blank/conflicting permission. Check every ambiguous case reaches review and none silently gains permission.
- Restart/scale: interrupt before and after each item-state commit; rerun batches of 40 and 500; confirm idempotent checkpoints, stable ordering, bounded memory/concurrency, and preserved accept/reject decisions.
- Portability: move/copy the export directory to another path/system; resolve all relative media/transcript references; verify manifests/checksums. Validate BagIt or PBCore only if selected. Test the real receiving catalog import with a fixture.
- Accessibility/privacy: complete all actions keyboard-only; inspect focus order/visibility; test text roles/states/progress with screen readers on each selected OS; tune coalescing with users; verify no recording bytes leave the workstation.

**Executed here:** read the brief, researched and recorded primary docs, upstream Symphonia source code/caller/test utility/release and issue history, then read only the released plan. No media, museum spreadsheet or catalog data were inspected; no app, downloaded code, build, test suite, package validation, audio playback, network audit, keyboard check or screen-reader test was run. Therefore the validations above remain proposals, not results.
