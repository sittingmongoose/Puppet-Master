# Research proposal: oral-history intake and transcript handoff

**Status and scope.** This is a research proposal for the small museum described in the brief. It is not an implementation, collection migration, catalog mapping decision, or deployment. The exact released plan is recorded as SHA-256 5f7ff916807818307634a6a4b42dea7ed030547adae267d936cce489384d6ab2. The proposal preserves the brief’s full scope: inconsistent extensions; metadata and duration; recordings whose two channels may contain different speakers; explicit transcript association and later corrections; safe restart for batches of 40 usual and 500 maximum; portable catalog handoff without a fixed codec or catalog API; distinct unreadable-media, unsupported-preview, and absent-transcript messages; keyboard operation and meaningful textual status; unchanged originals; no guessed permissions; no cloud transcription; and no required transcoding before cataloging.

## Released plan text

> The draft creates a batch manifest before examining recordings. Each entry stores the donation identifier, original path, permission text supplied by staff, byte hash, and separate probe and preview statuses. Original media are copied to an intake directory without alteration, then a format-probing process reports container, channels and duration. Preview generation is optional; a successfully cataloged original need not have a playable preview.
>
> A transcript is attached when its filename stem matches the recording identifier after lowercasing and removing spaces. Later transcripts replace the current association while preserving the prior file in history. This assumes normalized stems remain unique and the spreadsheet identifier is consistently present; neither condition has been checked. Permission fields can stay unknown and block release rather than be inferred. No cloud transcription is planned.
>
> The proposed interface presents a keyboard-navigable table with text labels for accepted, needs review, unsupported preview and unreadable original. It leaves how progress announcements avoid overwhelming screen-reader users unresolved. Export is a directory with manifest, transcripts and media references; the receiving catalog is assumed to resolve those references after copying the folder. Channel-specific preview and timing alignment need investigation before deciding whether conversion is necessary. Proposed validation covers renamed extensions, interrupted batch restart, corrupt files, stereo speakers, transcript corrections and keyboard/screen-reader review. No collection files have been inspected and no validation has been executed.

There is no minimum research duration, no requirement to consume the allowance, and no credit for waiting. The deadline includes arm-specific setup, provider queueing, tools, native retries, handoffs, revision and delivery. Output quality is assessed independently of elapsed time.

## Recommendation

Build a local, resumable intake workflow around a versioned batch manifest and explicit per-record review. Keep separate states for (1) whether this intake build can read and identify the media, (2) whether its selected playback path can preview it, (3) whether a transcript is associated, (4) what permission evidence is present, and (5) whether staff accepted the record for the catalog. A failed probe by one build is not proof that the original is corrupt. An unsupported or failed preview and an absent transcript do not mean failed audio or require rejection.

Do not select a winning library or codec before the museum specifies target operating systems, packaging constraints, and required holdings. Evaluate metadata/probe and preview/output paths separately. Record each exact version, build feature set or plugin inventory, OS, stream/container/codec combination, test fixture, and outcome. “Supported” means the combinations actually shipped and tested. A successful probe, a full decode, and audible playback are different results.

## Record and review model

Create a batch manifest and one item row per supplied recording before probing. Preserve enough source information to reproduce a decision:

- Batch ID; donation identifier exactly as supplied; source path/name; observed byte size; SHA-256 algorithm, value, and observation time; and any approved normalized ID in a separate field with its rule and provenance.
- Probe status and exact tool/build version; reported container, codec, stream/track identifiers, channel count/layout, sample rate, available bit depth, duration, and the source of each field. Preserve missing or uncertain duration as unknown/null with a reason, never as an invented zero. Keep the raw diagnostic or a provenance-bearing subset.
- Independent preview status and reason: not attempted, available, unsupported by this build, decoder failure, or output-device failure. An identified file with no installed decoder may still be cataloged if the museum’s policy allows it.
- Transcript presence and immutable revisions, each with its own filename, hash, receipt date/source where known, revision label, and relation to the same recording. A current-revision pointer may change; prior transcript bytes and associations remain.
- Permission text verbatim with spreadsheet/row provenance and a separate state: unknown, confirmed, restricted, or conflicting/needs review. Do not derive permission from media, filenames, transcripts, metadata, or an empty cell.
- Staff disposition (needs review, accepted for catalog, or rejected), reviewer/date, and reason for rejection or exception. Keep catalog acceptance separate from public release or reuse permission.
- If an accepted copy is made, its relative path and verified checksum, separate from the original path and hash.

A row can therefore show “Could not read media with this intake build” or “Media identified; preview unavailable because this build lacks the required decoder” without implying the same thing. If the selected API can distinguish an inaccessible input from an unrecognized format or missing demuxer, keep that diagnostic detail; do not overstate it when the API cannot. GStreamer’s documented missing-plugin messages put missing demuxers and decoders under the same decoder type, so app wording may have to remain broader. [S01](https://ffmpeg.org/ffprobe.html) [S04](https://gstreamer.freedesktop.org/documentation/additional/design/missing-plugins.html)

Show “No transcript supplied” as a neutral transcript state. It is not an audio error. A staff rejection must have a reason. Unknown or conflicting permission remains unknown/restricted and blocks external release. The museum must decide whether internal cataloging or restricted preservation can proceed while public release is blocked.

## Read-only identification, copying, and safe restart

Open source files read-only. Hash them as a stream; do not move, rename, rewrite, or transcode them. Treat extensions as hints only. Probe content and record what the exact build reports. The observed container, codec, stream index, channels/layout, sample rate, and duration are technical evidence, not proof of transcript identity, speaker identity, or permission. The selected build may not recognize every format, and duration/layout may be absent or approximate.

If the managed intake directory is the accepted copy location, make a byte-for-byte copy to a temporary destination and verify its checksum before finalizing it. Keep temporary and final paths on the same filesystem when using rename; Rust documents that rename behavior is platform-specific and does not work across mount points. POSIX defines a conforming rename action as atomic for that one filesystem operation, but that does not make a separate manifest/database update part of the same transaction. [S23](https://doc.rust-lang.org/std/fs/fn.rename.html) [S24](https://pubs.opengroup.org/onlinepubs/9799919799/functions/rename.html)

**Recovery rule for the copy/manifest crash window (accepted F04).** Key each copy operation by the stable supplied ID plus the observed source hash; use a deterministic final destination and a unique temporary name for that key. On restart, reconcile the manifest against both temporary and finalized files:

1. Recompute and compare hashes before treating any existing file as a completed copy. Remove or replace only a verified partial temporary file; never overwrite a mismatched final file automatically.
2. If a finalized file’s hash matches the expected item hash but the manifest row is missing or stale, restore only the copy-complete checkpoint for that ID/hash. Do not infer staff acceptance, permission, transcript currency, or public-release approval from file existence.
3. If the manifest says copied but the finalized file is missing or mismatched, reopen the copy phase. Re-copy only if the source still matches the expected hash; otherwise mark changed and require staff review.
4. If source bytes differ under the same ID/path, treat them as a new source version and reopen review. For a copy pass, record the source hash before and after copying and the copied-file hash; any disagreement marks the item changed instead of finalizing it as the expected version. This detects changes visible during the pass but is not a guarantee against every concurrent-write pattern. If stronger snapshot semantics are required, select and test an OS/storage-specific mechanism.
5. Commit each item-state update transactionally. SQLite is one local option, but it allows one simultaneous writer and a write/commit can report SQLITE_BUSY; define a serialized writer or retry policy. A SQLite transaction protects its database changes, not an independent media file. This distinction is an engineering inference from the transaction and file-operation scopes, not a claim that an implementation was tested. [S14](https://www.sqlite.org/lang_transaction.html) [S25](https://www.sqlite.org/atomiccommit.html)

Inject failures at partial-copy, completed-temp, rename/finalization, and manifest-commit boundaries. Also test source changes during a pass. On every restart, preserve previously committed human decisions only when the exact ID and observed source hash still match. The 40/500-item workload needs bounded workers, streaming hashes, stable item ordering, and recovery without loading an entire batch into memory.

## Transcript association, channel audition, and accessibility

Use the spreadsheet’s explicit donation identifier only after the museum confirms which column is authoritative. Preserve the exact raw value and any approved comparison key. A filename-stem match may suggest a candidate, but automatic lowercasing and space removal is unsafe without a uniqueness check: distinct supplied values can collapse to the same normalized stem. Missing, duplicate, conflicting, or colliding IDs; multiple candidate files; and corrections lacking a stable ID go to manual association. PBCore’s instantiation identifier is modeled as an unambiguous reference, but that does not prove the museum’s sheet has a reliable unique ID. [S16](https://pbcore.org/elements/pbcoreinstantiationdocument.html)

Treat each corrected transcript as a new immutable revision attached to the same verified recording ID. Preserve old and new bytes, filenames and hashes, source/date where known, and a current/superseded relationship. Do not guess revision order from a filename or silently overwrite a prior transcript. An ambiguous correction requires review. Keep any supplied timecodes; synchronized transcript/audio preview is not required by this brief and remains an owner decision.

Preview is optional and must not gate cataloging. For a two-channel recording, offer explicit ordinal-channel audition when the decoder and output backend allow it. Label “Channel 1” and “Channel 2” unless staff records speaker names after listening. Do not presume left/right speaker identity or downmix two speakers by default. Channel remapping can happen in the playback path without writing a converted archival file; FFmpeg documents pure mappings under specific zero/one-gain and one-input-per-output conditions. This is a candidate mechanism, not proof that every input/backend works. Keep the archive copy unchanged and test channel isolation with known fixtures and headphones on each supported OS. [S03](https://gstreamer.freedesktop.org/documentation/pbutils/gstdiscoverer.html) [S07](https://raw.githubusercontent.com/pdeljanov/Symphonia/ee35874b571a35a9a6e15d3bc9a3aaf8f11fbeee/symphonia-play/src/main.rs) [S20](https://ffmpeg.org/ffmpeg-filters.html)

The review flow needs keyboard paths for row navigation, preview, channel selection, accept/reject/review, and recovery, with predictable focus order and a visible focus indicator. Give controls meaningful accessible names, roles, and states. Show text statuses rather than color/icon alone, and expose them through the selected platform accessibility API. Slint documents accessibility properties and focus scopes/key bindings, but documentation does not establish behavior on every OS/screen-reader combination. WCAG 2.2 and WAI-ARIA status-role guidance are useful behavior references for web content, not proof of native-app conformance. Use a persistent textual progress summary, such as “21 of 500 checked; 19 identified, 2 need review,” and coalesce routine announcements into polite milestones. Keep errors and the full status log reviewable without moving focus or announcing every file event. Tune the rate with screen-reader users on the selected platforms. [S17](https://www.w3.org/TR/WCAG22/) [S18](https://docs.slint.dev/latest/docs/slint/reference/common/) [S19](https://docs.slint.dev/latest/docs/slint/reference/keyboard-input/focusscope/) [S21](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html) [S22](https://www.w3.org/TR/wai-aria-1.2/#status)

## Portable handoff

Do not assume that an absolute or temporary workstation path resolves after a folder is copied. Package unchanged media and transcript revisions with a versioned manifest, stable relative identifiers, and checksums, or use a durable URI contract confirmed by the catalog owner. If the package is self-contained, BagIt is an optional fixity/structure layer; PBCore is one possible mapping if the receiving catalog accepts its schema and field meanings. A versioned CSV/JSON sidecar is also feasible. Test the actual package after moving it to another path/system and validate the actual catalog import with fixtures before committing to the mapping.

## Staged integration proposal

1. **Owner inputs and fixtures:** identify the authoritative ID column, permission/release vocabulary, source-retention policy, target operating systems, catalog import/URI contract, transcript fields, and required formats. Use authorized sample spreadsheet shape only after approval; create openly licensed or generated media fixtures.
2. **Manifest and read-only inventory:** create batch/item rows; capture exact IDs, source path/name, size, and streaming SHA-256; identify duplicate/missing keys and permission gaps without changing source files. Start manual review queues before any automatic association.
3. **Pinned probe adapter:** locally probe content using a pinned build; record version, fields, uncertainties, and diagnostics. Keep suffix as a hint and never conflate probe with preview.
4. **Volunteer review and optional preview:** implement keyboard-accessible textual status and optional play/channel audition; store speaker labels only as staff assertions with provenance. Keep transcript, rights, and catalog disposition independent.
5. **Copy recovery and export:** make byte-for-byte verified copies only where needed; use the ID/hash recovery rule above. Produce a checksummed relative-path package or verified durable references; preserve transcript revisions and permissions.
6. **Catalog adapter:** after the recipient’s actual contract is known, map IDs, rights, and technical metadata to supported fields. Keep the local manifest versioned and auditable. Do not discard source evidence or silently reinterpret rights.
