# Investigator discovery — oral-history intake

**Run:** A-F02-R0  
**Stage:** investigator  
**Basis:** the released brief only, before exact-plan release. Source IDs below resolve through [sources/index.md](sources/index.md) and `source-map.json`.

## Framing

Treat each audio asset, transcript, spreadsheet row, permission statement, and preview derivative as separately identified inputs with explicit relationships. Intake must answer four independent questions: can the bytes be read; what format/streams can the selected tools identify; can this build preview a particular stream/channel; and what rights/association information has the donor supplied? A positive answer to one does not imply the others. An original can be cataloged without a generated preview; a missing transcript is “not supplied,” not an audio error; a missing permission is “unknown/not supplied,” never an inferred grant. Keep the original byte-for-byte and calculate/retain a content checksum and provenance. Do not derive a new archival master by default.

## Discovery and technical metadata

Extensions are hints only because this collection has inconsistent suffixes. DROID/PRONOM can add a preservation-oriented format identifier from internal signatures, report an extension mismatch and export CSV, but signature coverage is incomplete and DROID does not decode audio or establish preview support (S12–S13). Pin the DROID binary and the two signature-file versions; store the identification method and signature versions with each result.

For technical probing, compare a pinned FFmpeg/ffprobe build against a pinned Symphonia feature set; GStreamer is a credible third option if its plugin deployment is already supportable. ffprobe provides machine-readable JSON, separate container and stream sections, probe errors, and tool/library version reporting (S02). Its JSON “auto” default may omit invalid or non-applicable fields, so missing duration must remain unknown, not zero (S02). Save normalized values with source field, stream index, raw probe result, tool/build version, and whether duration came from container or stream. Do not claim a duration when no usable value exists. Maintainer discussion and differing media-tool calculations show that reported duration can depend on container timestamps, padding, and decoder interpretation; keep source values and validate against known fixtures rather than treating one tool as an oracle (S09).

Use explicit stream selection for any preview/export: FFmpeg’s automatic audio choice prefers the stream with the most channels, then lower index on a tie (S03). That is unsafe for independent speakers. Expose tracks and channels separately, label unknown layouts as “channel 1/2,” and let staff assign speaker names. Never downmix or claim a speaker mapping silently. FFmpeg can split channels, but its channelsplit layout default is stereo; require a detected/confirmed layout or explicit index mapping, and keep any split audio a clearly marked derivative (S04). Probe/read failure, decoder/plugin absence, and later decode/playback failure should be distinct states. A readable original with an unsupported preview can still be reviewed, accepted/rejected, and packaged (S02, S10–S11).

## Proposed record and user flow

1. Create a batch ID and one application record per source occurrence. Keep duplicate files as separate source occurrences even if their SHA-256 hashes match; hash is identity evidence for bytes, not proof of the same historical recording. Record source path/name, size, timestamp, hash, detected-format method/result, tool versions, and per-field provenance.
2. Import the identifier/permission spreadsheet into a staging table. Preserve the exact row and source filename; validate required columns, duplicates, blanks, and conflicts before linking. Use an explicit stable recording ID when unique. No filename-only fuzzy auto-link for audio/transcripts. Allow staff to choose among candidates and show why a link is proposed. The spreadsheet schema and catalog’s ID rules are owner decisions.
3. Keep transcript state independent: not supplied; supplied and linked; unmatched; ambiguous; corrected/new revision. Store transcript checksum, input row/file, received timestamp if provided, link method, and version/supersedes relation. A correction adds a version and preserves the earlier text/asset; it never silently replaces it.
4. Keep rights as explicit supplied value + source row + scope + status (granted/denied/unknown/conflicting/not supplied). Never normalize blank to permission. Separate “accepted into custody/catalog” from “cleared for public access/use”; owner must decide whether an unknown/denied right blocks custody acceptance, while public use remains blocked absent an explicit usable grant.
5. Offer keyboard-operable review of each stream/channel and metadata; show textual states and reasons. For example: **“Original readable; preview unsupported by this build (AAC decoder unavailable).”** is separate from **“Original could not be read/probed; permission or file integrity may need review.”** A decode failure after probing is a third state. Also show **“No transcript supplied.”** Do not move focus to a status message or make color/icon its only signal. WCAG 2.2 keyboard criterion gives a testable baseline; its status-message criterion is specifically for markup, so a native client must use and test its platform accessibility API rather than treating ARIA as a native solution (S17).
6. Checkpoint each record independently in a local job database (SQLite is a feasible option, not a decision). Store stage result, input hash, tool version, and last successful boundary. SQLite transactions are atomic at transaction scope and it permits one concurrent writer; serialize checkpoint writes and keep expensive probe/decode work outside transactions (S16). On resume, rerun only incomplete/failed idempotent stages for unchanged bytes. If source bytes changed, create a new revision/review; never overwrite a completed record. Write package content into a temporary location, verify hashes, then mark the handoff complete. Crash points and real filesystem behavior still need tests.
7. Export a self-contained directory/bag containing original media, associated transcripts and optional on-demand previews, plus a documented stable-ID manifest and explicit rights/acceptance states. BagIt supplies a payload/tag structure and checksum manifests (S14); it does not define the museum’s catalog schema, rights semantics, or authenticity against active tampering. Keep preview derivatives clearly named, link them to the source hash, and never substitute them for originals. For an unknown catalog API, start with a versioned JSON/CSV manifest and mapping table; add an adapter only after the catalog owner supplies the contract. The museum should be able to inspect the package with ordinary filesystem tools.

## Proposed validation (not executed)

Use synthetic and rights-cleared fixtures only; no collection files were accessed. Include extension/content mismatches; valid, truncated, zero-byte and unreadable files; known but unsupported codecs; missing duration; one/multiple audio streams; stereo channels with distinguishable test tones; unknown/multichannel layouts; missing, ambiguous, linked and corrected transcripts; duplicate content; missing, denied and conflicting rights rows. Confirm probe and preview status remain distinct, transcript absence does not change audio state, ambiguous IDs never auto-link, and user-facing language never infers permission or speaker identity.

Before/after SHA-256 must match for every original. Inject a stop after discovery, each record commit, preview generation, manifest write and checksum pass; resume twice and check no duplicate links, partial “complete” exports or lost revisions. Revalidate BagIt manifests and independently parse exported metadata. Pin FFmpeg build/configuration, Symphonia features, DROID signatures and any GStreamer plugin set used. Exercise 40 and 500 records with representative large files, bounded concurrency, cancellation/resume, responsiveness and memory measurement; no performance claim is supported yet. Run the whole review/export flow keyboard-only, then with the supported screen reader/platform accessibility tools; inspect focus order, names, textual status, warnings, transcript absence and recovery controls. Include malformed-input/fuzz corpus cases and a pinned decoder-upgrade comparison. These are proposals only; no local code, decoder, media, UI, package validator or workload test has been run.
