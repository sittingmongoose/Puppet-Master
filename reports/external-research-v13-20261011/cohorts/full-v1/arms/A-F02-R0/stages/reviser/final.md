**Run / stage:** A-F02-R0 / reviser

The released plan SHA-256 is 5f7ff916807818307634a6a4b42dea7ed030547adae267d936cce489384d6ab2. The [source map](source-map.json) preserves the predecessor source IDs and binds the reviewed artifacts; the [source index](sources/index.md) provides navigation.

## Proposal

Use a local, non-destructive intake workflow with a durable record for each source-file occurrence. Preserve originals byte-for-byte; retain hashes, source paths, and processing provenance; store any preview as a derivative. Keep these questions independent:

1. Were the supplied bytes readable and copied intact?
2. What format, container, streams, and technical fields did a particular pinned tool identify?
3. Can this exact installed build preview a particular stream or channel?
4. Was a transcript supplied, and is its association confirmed?
5. What permission information was supplied, and what actions does its scope allow?
6. Has staff accepted, rejected, or held the item for custody, and is it separately cleared for public use?

A yes to one never implies a yes to another. An original that this build cannot preview may still be reviewed and accepted into custody. A missing transcript is “not supplied,” not an audio failure. A blank permission field is not a grant. Do not alter original bytes, guess rights or speakers, send audio to cloud transcription, or require every item to be transcoded before cataloging.

No media stack or catalog API is selected. Compare qualified local builds on the same rights-cleared fixture set and target operating systems after the museum supplies its identifier, preview-coverage, deployment, and catalog requirements.

## Records, association, and review

Create one record per source occurrence, including duplicates. A matching SHA-256 establishes byte equality when measured; it does not establish that two occurrences are the same historical recording. Retain original name/path as provenance, size, hash, supplied donor identifier, exact permission row, import time when available, and the identification/probe method and version. Keep raw tool output and normalized fields with provenance. Never normalize omitted duration to 0.

Import the identifier/permission spreadsheet into a staging view first. Preserve exact cell values and source row, validate missing columns, duplicate IDs, blanks, and conflicts, then offer explicit candidate links. No filename-only or normalized-stem fuzzy link may commit without staff confirmation. Keep the spreadsheet schema and catalog ID rules open until supplied by the museum.

Track transcript states independently: not supplied; supplied and linked; unmatched; ambiguous; corrected/new revision. Retain each text/file version, checksum, source, link history, and supersedes/current relation. Record timestamps only when supplied and keep their format and timing basis. Do not infer synchronization merely from association.

Represent permissions with supplied value, source row, scope, and explicit status. Keep custody acceptance separate from public-use clearance. A complete intake record can be held from publication. Do not convert a blank spreadsheet cell into permission or infer a speaker from channel order.

Present per-stream metadata and preview availability with actionable, non-color text and keyboard-operable controls. “Original readable; preview unsupported by this build” differs from “Could not read/probe original”; “Probe succeeded; preview decode failed” is a third state. Show “No transcript supplied” independently. Use explicit stream indexes and known channel layouts; when layout is unknown, label channels by number and let staff supply speaker names. Mark local derivatives clearly and tie them to the original hash. Do not install plugins automatically as an intake side effect.

## Safe restart design gate

The investigator identified that database atomicity does not make copied media and catalog files one transaction. The critic’s MI-01 identifies the missing part: the draft did not define recovery for partial copies, package publication before a database update, or source bytes changing during copy. I accept MI-01 and add this proposal-level protocol. It is **not implemented or validated**; the workflow is not proven safe until target filesystems and crash cases pass the proposed validation.

1. **Stable identity and state.** Give each source occurrence an immutable intake_item_id and each export a stable export_id tied to a batch and manifest version. Enforce uniqueness. Record states such as planned, copying, staged_verified, published, complete, and needs_reconciliation. “Complete” is derived only from verified bytes and package contents, not a database flag alone.
2. **Copy to an isolated attempt path.** Never copy over an original or prior accepted version. Copy to a unique same-volume staging path for that item/attempt, retaining a streamed SHA-256 and byte count. Stabilize input with a read-only snapshot or equivalent when available. Otherwise compare source identity/size and hashes before and after copying; if values differ or a stable read cannot be established, leave the item in a source-changed/review state and do not publish it. A second matching read is evidence, not a guarantee against an adversarial change-and-revert race.
3. **Verify before promotion.** Independently read back staged bytes and compare size/hash with the copy result. Only then mark staged_verified. Promote by a no-overwrite operation on the same filesystem where supported, and record which filesystem semantics are relied on. If promotion is not atomic or no-replace cannot be guaranteed on a target, use a tested alternative and do not claim atomic publication.
4. **Reconcile every restart.** On open, compare durable state with partial/staged/final paths and checksums. An incomplete partial copy is never visible as complete; quarantine/remove that attempt and recopy from a stable source rather than guessing an offset. A staged verified copy found before its database transition is rehashed and can advance idempotently under the same item ID. A final package found after publication but before the database commit is verified against its manifest and expected item IDs, then reconciled to the same export_id without duplication. If a database row says complete but the package is absent or fails verification, withdraw completion, mark needs_reconciliation, and require repair/re-export. Never overwrite a completed package; use an explicit new export version.
5. **Publish the handoff last.** Build into a unique temporary package directory on the destination filesystem. Include a manifest, required payloads, and relative references. Recheck every payload checksum, referenced path, and manifest before publishing. Use a same-filesystem no-replace rename only where that filesystem provides the required guarantee. Then persist published/complete state. Since the directory operation and database update are separate, a crash between them is resolved by the reconciliation rule; do not report completion before package read-back verification.
6. **Database limits.** If SQLite is selected, serialize checkpoint writes and keep expensive media I/O outside transactions. SQLite documents multiple simultaneous readers but one writer; an atomic database transaction applies to database changes and depends on journal mode and storage assumptions. The official transaction and commit pages do not make external package files part of that database transaction; this last statement is an application-boundary inference from the documented scope [S15–S16, C12–C13, R01–R02]. Test actual storage, rename, flush, and recovery behavior on each supported platform before relying on it.

This protocol makes interrupted states explicit and idempotent but does not claim filesystem or database durability beyond behavior qualified on target systems. A changed source becomes a new revision/review; it never silently replaces a completed item.

These tools answer different questions. A format identifier, parser, decoder, and preview path may produce different outcomes. Support ends at the features/plugins and exact configuration actually shipped. If a build cannot preview a readable original, preserve it and report that limit rather than mislabeling it unreadable. Library of Congress sound guidance informs preservation choices but is not a rule for rejecting donor originals [S18].

No winner is selected. After owner inputs arrive, compare FFmpeg and Symphonia on the same rights-cleared corpus; include GStreamer where deployment is viable. Compare per-format outcomes, multi-track/channel selection, duration provenance, errors/restart, packaging footprint, distribution constraints, and measured performance at 40 and 500 items. Do not select on codec lists alone.

## Staged integration proposal

1. **Inventory and safeguards:** create batch and occurrence IDs and manifest rows before identification/probing; stage bytes without modifying originals; hash and verify; detect duplicate or ambiguous IDs. Keep a pending hash until bytes have been read.
2. **Identify and probe:** qualify a pinned local reader/prober and optional pinned DROID/signature set. Save raw and normalized results, source field, exact versions/build/features/plugins, and structured error class. Omitted values stay unknown.
3. **Human review:** let staff inspect stream/channel evidence and preview where available, confirm transcript links, add immutable corrections, record rights and acceptance/rejection reasons, and keep custody distinct from public-use clearance.
4. **Portable handoff:** create a package with relative references and checksums, independently validate metadata and payloads, then publish through the restart protocol. Start with a documented versioned JSON/CSV manifest and mapping table. Do not connect to or mutate an unspecified catalog; add an adapter after its owner defines the contract.
