## Brief coverage map

The brief asks for (1) incremental search across multilingual text, scanned PDFs, slide exports, and optional audio transcripts; (2) result provenance (embedded text versus OCR versus supplied transcript) and a jump to a page, region, or time range where supported; (3) stable attachment identity and freshness across rename, move, replacement, partial reads, long extraction, cancellation, and error; (4) lexical and other retrieval strategies with language-aware tradeoffs; (5) bounded background work, errors, and opening original evidence without trusting snippets; and (6) an honest modest first scope plus a validation plan that separates synthetic/public checks from unavailable-corpus relevance, OCR-quality, and notebook-integration work.

## Product and implementation candidates

**Broad parser candidate: Apache Tika 4.1.0.** Its current release page says 4.1.0 is latest, requires Java 17+, and ships ZIP distributions rather than standalone runnable jars. Its supported-format guide identifies PDF parsing via PDFBox and Office/OOXML extraction via Apache POI. It can route rendered PDF pages to an OCR recognizer. Tika offers one adapter surface across document families, but brings a JVM/deployment boundary and versioned parser behavior. If evaluated, run it locally, pin the parser/config/model set, configure only local recognizers, and disable network/VLM enrichers for private attachments. An alternative is a per-format adapter set in the notebook runtime; it gives tighter control but multiplies dependencies and format-specific regression work. (S01–S03, S12)

**OCR candidate: Tesseract 5.5.3.** Its versioned manual documents text, hOCR, TSV, ALTO, PAGE XML, and searchable-PDF outputs. TSV provides each recognized word's bounding rectangle and confidence; hOCR carries word boxes and confidence. Those are coordinates for a rendered image, not proof the recognized words are right or that coordinates map to the current source version. Save render dimensions, page number, DPI, rotation/crop transform, engine/model/language versions, and raw confidence as provenance. Use OCR only when enabled/available; do not equate an OCR layer embedded in a third-party PDF with verified author text. (S04)

## Retrieval comparison

- **Local lexical ranking, recommended baseline.** SQLite FTS5 supplies phrase, prefix, column-weighted BM25 ranking, snippets, and Unicode tokenizers in the same transactional store as attachment/generation metadata. Default `unicode61` is case-insensitive under Unicode 6.1 and removes Latin-script diacritics; Porter stemming is English-specific. Trigram supports substring matching but queries shorter than three Unicode characters do not match. Preserve original extracted/display text separately from normalized/indexed text and version tokenizer settings. Start without global stemming; add language-specific analyzers only with evaluation. FTS5 external-content tables have a caller-owned synchronization contract: triggers do not backfill existing rows, stale divergence can return unintuitive hits, and update/delete order matters. Prefer generation replacement and FTS state in one SQLite transaction; avoid external-content mode unless its invariants are tested. (S06)
- **Rust-native lexical alternative: Tantivy 0.26.2.** It is an embedded search library with field-level tokenizers, configurable filters, segment indexing and explicit commit; changes become searchable at commit. It is attractive when a standalone search index is acceptable, but metadata and index then need a cross-store generation/commit protocol. Built-in defaults include punctuation/whitespace tokenization and English stemming; custom analyzers are possible, so multilingual support still needs explicit analysis choices. (S07)
- **Substring/fuzzy adjunct.** FTS5 trigram is deterministic/local for substrings and identifier fragments, with the short-query caveat above. Typo tolerance can instead use a measured edit-distance pass over lexical candidates; it is a ranking aid, not evidence identity.
- **Semantic/vector search: optional later experiment.** Embeddings may find paraphrases with few shared tokens, but need a pinned local model, added compute/storage, model-update/rebuild rules, and provenance joins for every returned chunk. Remote embedding services would upload private attachment text and are out of scope. `sqlite-vec` is an SQLite candidate, but its repository labels it pre-v1 and v0.1.9 fixed a DELETE failure for rows with long metadata values; do not make vector deletion part of the initial correctness path. Keep vectors as a separately versioned experimental index keyed by attachment version and chunk; validate replacement/delete/rebuild before exposing hits. (S08–S09)

## Freshness, replacement, and evidence model

Use a stable `attachment_id` owned by the notebook, with current path/name as mutable locator. Treat size/mtime as scan hints only; compute a content digest for each claimed version and check that bytes still match after extraction. A move/rename preserving bytes updates the locator without re-extraction. A replacement creates a new source version. Capture parser/build, config, OCR engine/model/language and tokenizer/normalization profile in an extraction revision so parser upgrades can be re-run without pretending the file changed.

Queue idempotent work by `(attachment_id, source_digest, extraction_revision)`. On change, immediately mark the old generation stale/ineligible for ordinary current results. Parse into temporary generation rows, impose per-file byte/page/pixel/time/output limits and a small global worker cap, then commit all chunks and move the active pointer atomically only if the input digest still matches. If it changed again, discard that attempt and enqueue the current version. Cancellation/failure leaves a typed state (`cancelled`, `timeout`, `unreadable`, `password_required`, `unsupported`, `OCR_unavailable`, `partial`) and no current generation for the new version. Retain old rows only for an explicit stale/unavailable view or cleanup/recovery; never include them as unqualified current hits. Deletion/tombstone removes an attachment from ordinary results immediately. Coalesce repeated edits; let note saves finish without waiting for OCR/parsing; report a compact reason, last attempt, and retry action rather than swallowing failures.

Each result chunk should carry attachment ID, exact source digest/version, extraction revision, segment ID, evidence kind (`embedded_text`, `app_ocr`, `user_transcript`), source offsets, locator kind/value, precision, and any OCR confidence. A location is a typed union (page, page+region rectangle, slide, timestamp span, or unknown), with approximate/unavailable explicit. PDF page numbers are often available, but PDF text reading order is not guaranteed by the format; coordinate targeting requires parser output that actually provides coordinates. Tesseract boxes are relative to a particular rendered page. On slides, support slide number first; do not promise a shape/region jump without a tested adapter. For audio, keep supplied transcript as its own evidence source and use timestamps only if supplied; with no transcript, leave audio unsupported in the first scope. Show source type and freshness in the result, plus “open original attachment.” Snippets aid discovery only; the original file/viewer is the evidence. (S03–S05)

## Practical initial boundary

A sensible first implementation is text-bearing PDFs and PPTX slide text, local FTS5, immutable extraction generations, exact source versioning, and page/slide locators where adapters can demonstrate them. Add optional local OCR for raster PDFs/images with explicit OCR labeling and per-page boxes only where captured. Accept user-supplied audio transcripts, not automatic transcription. Unsupported, encrypted, damaged, partial, and OCR-unavailable attachments remain visible as states but contribute no falsely current text. This boundary preserves freshness/provenance obligations while making unsupported recognition explicit.

## Issue/fix/regression evidence

Tika issue TIKA-4883 records a concrete AUTO-OCR defect: when a page's text looked poor, the parser could append OCR after the original garbage text. The issue was resolved for 4.1.0; merged PR #3145 holds extracted text until recognition, replaces only when a configured text recognizer actually produced output, and preserves extracted content if the recognizer is absent, exhausted by a page cap, times out, or errors. The PR lists both PDFParserTest and ContentEnrichersTest changes. This is a reason to test the full state machine and keep OCR and embedded-text origin visible, not assume AUTO proves quality. (S10–S11)

For the optional vector path, sqlite-vec issue #274 and release v0.1.9 show a recent deletion failure involving long metadata values and its fix. Since replacement and deletion correctness are core requirements, defer vector search until delete/rebuild behavior is tested on a pinned release. (S08–S09)

## Validation plan — proposals only

No local parser, index, or downloaded code was executed in this discovery step. The following are proposed checks, not results:

1. Create public/synthetic fixtures: text PDF, scanned PDF/image with known words, multi-page/rotated PDF, PPTX with separate slide strings, and a short audio clip with/without supplied transcript. Assert evidence labels and page/slide/time locator availability; assert regions only when the adapter emits them.
2. Simulate version transitions: index v1, replace with v2 during parse, cancel/fail the v2 job, and verify v1 is never shown as current; then complete v2 and verify one atomic swap, no old-term hit, no duplicate chunks. Repeat with rename, move, byte-identical replacement, deletion, partial read, and file mutation during extraction.
3. Exercise queue bounds/coalescing, timeout, malformed/encrypted/unsupported inputs, missing local OCR engine/language model, and retry status. Assert editing remains responsive, an actionable error is shown, and no private bytes/text leave the local process.
4. Run synthetic multilingual terms (Latin with/without diacritics, Cyrillic, CJK, Thai, mixed-script identifiers) through each selected tokenizer; record exact/phrase/substring hits and known false positives. Broader multilingual relevance with notebook content is a future evaluation, not completed validation.
5. Run index consistency/integrity checks after swaps, rollback, cancellation, deletion, and rebuild. Add a regression case for TIKA-4883's poor text plus OCR success/fallback conditions. Track parser/version/config/model pins in fixture output.
6. Recognition-quality evaluation on an authorized representative corpus and notebook end-to-end navigation are future proposals. This task has no such corpus, so no quality score or integration result is claimed.
