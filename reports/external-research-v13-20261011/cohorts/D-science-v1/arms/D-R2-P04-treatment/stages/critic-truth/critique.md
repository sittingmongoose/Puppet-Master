## Findings for the reviser

1. **Qualify cancellation and the old-generation rule by the requested version.** The draft correctly says old results become stale when bytes or extraction revision change. State the inverse too: if a retry is cancelled for the *same* digest and requested extraction revision, an already-complete generation for that exact tuple may remain current; cancellation alone does not make valid same-version data stale. Once the source digest or requested parser/config/OCR/tokenizer revision advances, a previous generation must not masquerade as current, even if the new run fails or is cancelled. Gate the active pointer on attachment existence, digest, requested revision, and job fencing. This conditional is clearer than the released plan's unconditional “leave previous index unchanged.”

2. **Preserve Tika AUTO's defaults and fallback exceptions; don't infer page provenance from configuration.** The versioned 4.1.x pages reference documents `text=AUTO` as the default, OCR threshold defaults of 10 total characters and 10 unmapped Unicode characters per page, `maxPages=-1`, 300-DPI rendering, and `maxImagePixels=100000000` (CT01). `AUTO` replaces poor extracted page text only when a configured text recognizer actually writes text; without an engine it behaves as extraction, and the extracted text is retained when the page cap is spent or the recognizer times out/fails. The 4.1.0 release-note diff corroborates that condition and the issue-to-fix path (CT03). Thus the Tika default is not itself a bounded OCR policy, and selecting `AUTO` does not prove that a given page's returned text came from OCR. The adapter must record the observed per-page outcome/source if results are to distinguish embedded extraction from app OCR. The draft points toward this; make it explicit. Tika's OCR replacement behavior is parser-specific and cannot replace the notebook's independent version/freshness state machine.

3. **Keep process isolation conditional on the actual Tika integration.** The draft's security warning is well-founded. In 4.1.x direct parser calls run on the caller thread/heap; output limits do not cap computation. Tika describes forked-JVM Pipes / `PipesForkParser` isolation and specifically calls for heap and timeout bounds; server and gRPC are not caller-authentication boundaries (CT02). If Tika remains an alternative, say isolation exists only when that path is configured and exercised; do not imply a local/network Tika service is safe merely because it is local. This does not change the draft's recommendation to keep parsing out of the UI process.

4. **Keep FTS5 claims conditional and multilingual claims modest.** The draft correctly says “if the shipped SQLite includes FTS5,” records tokenizer/version uncertainty, and proposes multilingual tests. Official FTS5 docs say the default `unicode61` tokenizer uses Unicode 6.1 categories, removes Latin diacritics by default, and tokenizes contiguous letters/numbers as runs; this is not language-aware segmentation or a multilingual relevance guarantee (CT04). The reviewer should retain the explicit CJK/Thai and mixed-script evaluation and avoid treating one successful synthetic query as broad language support. External-content FTS tables remain caller-synchronized, can return unintuitive results if divergent, and adding triggers does not backfill existing rows (CT04); the draft accurately conditions this risk and its integrity checks.

5. **PDF text order/location caveat is accurate.** PDFBox 3.0 says default text output follows content-stream order, not a guaranteed reading order; `setSortByPosition(true)` offers geometric ordering but still does not establish semantic reading order (CT05). The draft's caution and “only promise locators the adapter emits and tests” should remain. Likewise, do not convert transcript character offsets or OCR boxes into audio/source coordinates without an explicit mapping.

6. **Bounded-work coverage is conceptually sound but leaves policy values open.** One active CPU-heavy worker plus coalescing is a reasonable conservative candidate, not a fact established by the cited sources. The draft names queue, time, page, pixel, byte/output, and worker bounds, and candidly leaves queue length/fairness as owner decisions. Since the brief asks for bounded background work, the reviser should state that those bounds must be configured and tested before claiming the implementation is bounded; no numeric limits were established here. One worker alone does not bound queued work or protect against one stuck/oversized job.

## Negative/default and version check

No consequential criticism in the draft improperly removes a capability or forces a parser architecture. Tika/JVM, per-format adapters, FTS5, Tantivy, and optional vectors remain alternatives; the draft does not claim a product choice was made. Explicitly preserve these exceptions/defaults in any final synthesis: Tika AUTO can retain original extracted text on no-engine/page-cap/error/timeout; Tika's default OCR page budget is unlimited (`-1`) and its output limits do not bound work; PDFBox ordering is content-stream-based by default; FTS5 availability depends on the shipped build and unicode61's defaults are limited; and vector deletion history is a reason to test/defer, not proof that the current pinned release is still broken.
