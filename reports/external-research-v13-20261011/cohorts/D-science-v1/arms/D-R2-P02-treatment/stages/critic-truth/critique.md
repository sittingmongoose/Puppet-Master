# Complementary truth critique — D-R2-P02-treatment

**Scope:** Full frozen investigator discovery, draft, source map/index, and released design; reviewed against the brief and primary documentation. This is a critique for the reviser, not a final plan. No implementation or adversarial check was run in this stage.

## Assessment

The draft is materially well-founded and preserves the brief’s core boundaries: a selected attachment/block rather than ambient notebook access, host-owned declarative rendering as a conservative starting profile, distinct provenance for extracted text, failure-tolerant editing, and ownership-aware cleanup. Its corrections to a generic handle, markup-in-view, note-ID-only search indexing, worker timeout, ID-only cache key, process-exit cleanup, and old cached output are supported by the cited primary context. I found no basis to reverse those dispositions.

There is one material conditional gap in the Wasmtime alternative: the release/advisory record is not carried through to the no-stdio condition and its exact version ranges. Clarify it before treating the runtime comparison as implementation-ready. This does not select Wasmtime or block the architecture-neutral recommendation.

## Findings for the reviser

1. **High, conditional — distinguish runtime resource-limit generations and configure WASI output explicitly.** The draft correctly reports that GHSA-852m-cvvp-9p4w affected earlier Wasmtime branches and that patched pre-42 releases kept new limits at very large defaults; the advisory says 42.0.0+ defaults were tuned for that reported issue. But that is not a blanket bound on every host allocation. Wasmtime’s v49.0.2 release also fixed GHSA-gqmc-89g8-p25r: a WASI Preview 2 `SinkOutputStream` used when stdout/stderr were not configured allowed an unbounded host allocation in `write-zeroes`. The advisory’s affected ranges are `<36.0.17`, `37.0.0–48.0.3`, and `49.0.0–49.0.1`; patched releases are 36.0.17, 48.0.4, and 49.0.2. It says the issue only affects embeddings without configured stdout/stderr; a bounded custom `OutputStream` is a workaround. Add an explicit bounded stdout/stderr requirement for a Wasmtime/WASIp2 profile, pin and monitor the actual runtime patch, and test the no-stdio/default-stream case. Keep this claim conditional on that embedding and interface. The current draft’s byte/log/watchdog limits are useful but do not themselves establish how the runtime’s default sink is configured. [WASMTIME-NOSTDIO, WASMTIME-RES-ADVISORY, WASMTIME-RELEASE]

2. **High — preserve the filesystem advisory’s exception boundaries.** The symlink/trailing-slash escape advisory lists affected releases only through 47.0.3 and says 48.0.0+ is unaffected; on Linux after 5.6 using `openat2`/`RESOLVE_BENEATH`, this particular cap-std issue does not apply, while macOS and older Linux kernels are affected. The draft mostly states this correctly. Keep it as a specific historical regression and do not generalize either to “all WASI is unsafe” or to “newer runtime means every path boundary is safe.” Require selected OS/kernel/runtime verification and retained path/symlink regression cases. The advisory does not itself establish Windows applicability; leave that unasserted until a chosen implementation is checked. [WASMTIME-FS-ADVISORY]

3. **Medium — make the Wasmtime fuel example a time-bounded observation.** The official v49.0.2 release identifies commit `3c8a3e7`, was released 2026-10-02, and includes the `poll_oneoff` fuel-consumption fix. The release page showed v49.0.2 as “Latest” when inspected, but the draft appropriately presents it as an example rather than a selected or permanently current pin. Preserve that framing: the advisory history demonstrates version-sensitive behavior; it does not show that all WASI runtimes share the defect or that a watchdog makes a vulnerable runtime acceptable. [WASMTIME-FUEL-ADVISORY, WASMTIME-RELEASE]

4. **Medium — keep capability-removal recommendations scoped to actual access.** VS Code’s webview guidance supports restrictive resource roots, CSP and sanitization, while expressly saying resource roots are not complete protection and sanitization alone is insufficient. That is a useful precedent, not a guarantee for this notes host. Retain declarative host rendering as a recommended starting profile and keep executable/interactive rendering available for a separate, explicit design and threat-model decision; the brief asks for comparison and does not select an extension framework. Likewise, deny references that cause host resolution outside the selected attachment/run capability, but allow format-required subresources that are provably contained within the selected attachment (for example, members of that attachment’s archive) under size/depth limits. Do not turn path-traversal defense into a blanket ban on safe in-attachment content. [VSC-WEBVIEW]

5. **Medium — state exactly what worker termination proves.** Electron’s utility-process API gives the child Node integration; `env` defaults to `process.env`, its session can enable network behavior, and `child.kill()` is graceful (SIGTERM on POSIX) for that process. The API does not itself establish descendant termination or sandboxed file authority. The draft correctly treats process separation as reliability containment and calls for an OS-enforced whole-tree stop. Keep those as separate validations: child exit/reaping, descendant membership/termination, and capability denial. Do not describe a generic `kill()` as a hard stop. [ELECTRON-UTILITY, WIN-JOB, APPLE-PROCESS, APPLE-XPC]

6. **Low — cache identity and stale-search policy are appropriately conditional.** Include every input the extension can observe or that can change result meaning (including normalized configuration/permission state and host/runtime renderer/extractor identity); use immutable revisions or canonical hashes rather than assuming a revision label is sufficient. The draft already limits note/block identity to context-dependent results and allows explicit policy differences for disabled versus revoked extensions. Keep those conditions; do not force note-ID into every purely attachment-derived cache key or require deleting every benign stale result. Search provenance, visible staleness, and revocation handling remain required distinctions. [SQLITE-FTS]

## Preservation and validation status

- Keep the stated editing/save availability when rendering fails or is unavailable, version-attributed derived search records, no partial extraction publication, manifest/lease-based cleanup, and distinct upgrade/disable/uninstall/revoke states.
- Keep proposed tests labeled as proposals. The investigator reports documentation review and planning/release helper work, but no sandbox, app behavior, adversarial payload, real notebook, or cross-platform execution. That accounting is appropriately bounded; this critique also ran no implementation checks.
- The proposed nested-worker, active-content, stale-cache, uninstall, failed-extraction, and concurrent-cleanup cases cover the released plan’s explicit checks. Add a WASIp2 guest with stdout/stderr intentionally unconfigured to the conditional runtime test above.
