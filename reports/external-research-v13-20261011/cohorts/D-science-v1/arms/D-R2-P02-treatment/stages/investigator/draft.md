## Recommendation

Treat the extension as untrusted code and its inputs, messages, markup, extracted text, files, and worker behavior as untrusted data. Keep the notes editor and search state independent from preview execution. The released design has useful goals—scoped attachment input, asynchronous message passing, a separate worker, timeout/error reporting, cached results, and a preview when the extension is unavailable—but the stated boundaries are incomplete.

The lowest-risk starting contract is a bounded declarative preview schema rendered by host-owned UI, with extracted text stored as a distinct derived artifact. If rich executable extension code is required, compare WASM with an explicit host-import ABI and native workers with real OS confinement using a platform prototype. A separate process or a runtime's isolation label is not evidence of authority limits. No framework or runtime is selected here.

## Exact per-clause dispositions

| Released-plan clause | Disposition | Treatment |
| --- | --- | --- |
| Host supplies an attachment handle and block configuration | **REVISE** | Keep the scoped input concept only if the handle resolves to exactly one attachment/block, is read-only, request-scoped, and cannot enumerate notebooks or resolve arbitrary paths. Prefer sending bounded bytes plus minimal validated block configuration. Omit notebook names, roots, unrelated note content, credentials, and unnecessary metadata. Treat configuration as untrusted and validate its schema/size. A generic handle is safe only if its actual authority and lifetime are enforced by the host; a path-like reference is not itself a capability boundary. Reject indirect references too: extension-supplied relative paths, markup resource URLs, redirects, archive-member references, symlink chains, and aliases must not make the host resolve data outside the selected attachment or declared run scratch. |
| Host supplies a temporary work directory | **REVISE** | A per-run scratch area may be useful for intermediates, but it must contain no note or notebook files and must not widen filesystem access. Keep it private to that run, quota-bound, and represented in an explicit run manifest. In a WASI design, expose no directory unless needed and preopen only that scratch capability. In a native-worker design, the OS sandbox must enforce the specific read/write scope. Do not use its pathname as proof of ownership or as the sole basis for deletion. |
| Extension returns preview markup and extracted text over a message channel | **REVISE** | Retain an asynchronous typed message channel, but make the output a bounded, versioned schema and validate it before UI or search sees it. Default to host-rendered declarative components; reject scripts, event handlers, active HTML, arbitrary navigation, file URLs, remote fetches, and unbounded embedded resources. If richer active rendering is later approved, require a separate renderer origin/process with scripts, network, local-file access, preload APIs, and host bridges disabled unless narrowly justified. Apply restrictive CSP and sanitization as defense-in-depth, never as the only security boundary. |
| Embedded view displays returned markup | **REVISE** | Render only validated host-owned components by default. A message channel does not sanitize markup. A normal embedded view may still expose navigation, local resources, preload or IPC paths, and resource-exhaustion surfaces. VS Code's guidance illustrates that CSP and sanitization are needed but not sufficient [VSC-WEBVIEW]; Electron documents configuration choices that disable its renderer sandbox [ELECTRON-SANDBOX]. If interactive extension-authored execution is an owner-approved requirement, make that a separately isolated design with its own threat model and platform checks, not an implicit consequence of “preview.” |
| Index extracted text under the note ID | **REVISE** | Keep extracted text searchable, but store it as a separate preview-derived source record joined to the note/block. Include stable artifact ID, source type, extension ID and version, installed package digest, input attachment digest, API/schema version, relevant configuration/permission revision, extraction time, host extractor version, and readiness/staleness/failure status. Search results must say that the match came from extension-derived preview text and name the producer version; do not merge text into the note body or label it user-authored. An FTS row keyed only by note ID cannot preserve which source/version supplied the match. FTS external-content indexes also need an explicit synchronization/rebuild invariant [SQLITE-FTS, SQLITE-TX]. |
| A separate process runs each renderer with a timeout | **REVISE** | Keep separation and an externally enforced deadline as reliability controls; they help keep a stuck/crashed renderer away from ordinary editing. They do not alone limit files, notebooks, network, process creation, memory, or CPU. Use an asynchronous supervisor outside the worker, bound the whole invocation, validate messages, and enforce OS/runtime capabilities. Keep the main editor free to edit/save while preview work is running. Electron's utility process has Node APIs and inherited environment/session defaults unless configured [ELECTRON-UTILITY]. |
| On timeout, host kills it and displays an error card | **RETAIN WITH CONDITIONS** | Retain the timeout and clear error state. Require a hard stop of the whole worker tree/containment unit, a bounded restart/backoff policy, and a terminal run-state transition. Do not wait on a UI-critical thread. If termination is incomplete or containment cannot be verified, keep the run failed, do not publish its partial output, and do not delete files still referenced by a live reader. Error UI should say preview failed/timed out and leave the original note editable. |
| On timeout, host removes the temporary directory | **REJECT THE ASSUMPTION; REVISE THE ACTION** | Process termination does not establish that all descendants ended, that no consumer has the directory open, that its contents are not shared, or that it belongs exclusively to this invocation. Windows Job Objects have breakaway and process-tree caveats; on macOS a plain child inherits the app sandbox and a separate XPC service is needed for different entitlements [WIN-JOB, APPLE-PROCESS, APPLE-XPC]. Delete only through explicit ownership metadata after the run is terminal and no active lease/reference remains. Make reconciliation and deletion idempotent and safe after crashes. |
| Shared cache key uses input digest and extension identifier | **REJECT THE KEY AS COMPLETE; REVISE** | Input digest plus extension ID can reuse output across semantic changes. Include at least attachment/block identity, extension version and package digest, extension API/schema version, relevant configuration and permission revision, and host renderer/extractor version. Include note/block identity whenever output depends on note context or access scope; any cross-note content deduplication must preserve authorization and provenance references independently. Keep old-version cache entries separate and mark them stale; never silently relabel old output as current. |
| Extension ID is assumed to preserve preview meaning across upgrades | **REJECT** | Stable ID identifies a publisher/product lineage, not behavior or permissions. A new binary, schema, declared capability, configuration or host renderer may change extracted text and preview meaning. Version/digest transitions must trigger a new cache identity and a visible version boundary. Public Wasmtime history shows that even sandbox and fuel/resource enforcement behavior can change across releases, so runtime versions must also be recorded and maintained [WASMTIME-FS-ADVISORY, WASMTIME-RES-ADVISORY, WASMTIME-RELEASE]. |
| Disabling an extension hides new previews but retains old cache entries | **REVISE** | Do not invoke a disabled extension. Cache retention can be useful for recovery, but mark the record disabled/stale and keep its producer version, timestamp, input digest, and reason. If shown, render only an inert validated declarative artifact and label it “last preview from extension X, version Y”; never execute cached markup. Owner decision: whether disabling differs from uninstall, explicit user deletion, or security revocation, and whether those states purge, hide, or retain cache/search data. |
| Unavailable renderer shows the last preview with a badge | **REVISE** | A badge alone is insufficient unless it is persistently visible and explains stale/unavailable status and the old producer version. Prefer the last safe host-rendered declarative result when available. If cached output was active markup or cannot be validated/rendered by the current host, do not replay it; show an unavailable/error card and the original attachment fallback instead. Keep note text editable and searchable. State whether “renderer missing,” “extension disabled,” “refresh failed,” and “extension version changed” are separate user-visible causes. |
| Old extracted text remains searchable after disable/unavailability | **UNRESOLVED OWNER POLICY; RECOMMEND STALE-AWARE SEARCH** | The released plan leaves this open. Recommended baseline: keep the last successful extraction in a separately attributed derived-text record, mark it stale/unavailable, and let search surface it with a visible stale badge and exact producer version; offer a filter to exclude stale/derived hits. If the extension was explicitly revoked for security or data-handling reasons, suppress or delete its derived record according to an owner-approved revocation policy. Never quietly present it as current or note-authored. |
| Any extraction failure | **REVISE / ADD EXPLICIT FAILURE SEMANTICS** | Do not index partial output or overwrite the last good artifact with a failed run. Record a failure status and safe diagnostic. If a last good preview remains, show it only as stale with the exact version and a “refresh failed” reason. A failed run must not change note content or block save/edit/search. |
| Note open when renderer is unavailable | **REVISE / PRESERVE CORE EDITING** | Always open the note without requiring an extension. Show original note content and an attachment/custom-block fallback with type/size and open/save affordance where supported. State why the preview is unavailable and whether a last safe preview exists. Do not require installation from a marketplace; marketplace behavior is outside this plan. |

## Capability and renderer comparison

| Approach | What it can provide | Conditional limits and trade-offs |
| --- | --- | --- |
| Host-rendered declarative schema | Static rich content, search text, stable accessibility and host-controlled navigation/links/components; no extension-authored script execution. | Most direct route to keep active content out. Schema must be deliberately small, bounded and versioned; extensions needing arbitrary interactive views may not fit. This is the recommended starting profile, subject to product confirmation. |
| WASM/component module with narrow host imports | Executable transformations in a portable ABI with explicit host services; can receive only current attachment data and a narrowly scoped temporary capability. | Host imports define the actual authority. Configure instruction, epoch/wall-time, memory/table, host-call byte/allocation, handles, logs, output and concurrency limits. Wasmtime advisories demonstrate implementation defects and defaults matter: a filesystem escape was OS/kernel-dependent; WASI host allocations could exhaust resources; recent release history records a fuel bypass. Pin a supported release, follow advisories, and retain an external watchdog. This is a candidate, not a selected runtime [WASMTIME-SECURITY, WASMTIME-LIMITS, WASMTIME-STORE, WASMTIME-FS-ADVISORY, WASMTIME-RES-ADVISORY, WASMTIME-FUEL-ADVISORY]. |
| Native or Node worker with OS sandbox | Existing native parsing libraries and process-level crash isolation; OS process-tree controls can support forced stop and resource accounting. | Arbitrary code inherits capabilities unless removed. Needs real per-OS policy, narrow IPC, no broad notebook root, no unnecessary network, and process-tree controls. macOS XPC entitlements, Windows AppContainer/Job Objects and Linux namespaces/seccomp/cgroups are different deployments with version/permission constraints. More platform-specific work and ongoing testing [ELECTRON-UTILITY, APPLE-XPC, WIN-APPCONTAINER, WIN-JOB, LINUX-SECCOMP, LINUX-CGROUP]. |
| Active HTML/JavaScript in embedded view | Highest format flexibility and interactive rendering. | Largest attack surface and least compatible with the brief's no-ambient-privilege boundary. Use only after an explicit product decision, in a renderer that cannot access notes/files/network or privileged preload/bridge APIs, with restrictive CSP, strict URL/resource policy, size limits and validated messages. Sanitization alone is insufficient [VSC-WEBVIEW, ELECTRON-SANDBOX]. |

Do not equate a separate process with the authority boundary. Treat active markup as executable code. Treat WASM/WASI as a smaller capability surface only when the host exposes a deliberately narrow import set and the selected runtime is configured, patched, and tested. For every supported host platform, record which controls are active and what the application does if they cannot be established.

## Data, provenance, cache, and cleanup contract

A preview run should have an explicit record separate from note content. A proposed run/artifact identity contains:

- owning note/block and attachment digest;
- extension stable ID, semantic version and installed package digest;
- extension API and preview schema versions;
- relevant block configuration and permission revision;
- host decoder, renderer and text-extractor versions;
- run ID, start/completion time, result digest, extracted-text digest, status, and safe failure reason.

The user-facing preview should state the producer extension/version and freshness. Search documents should carry a distinct source kind such as preview-derived, stable artifact ID, note/block association, source attachment digest, producer/version, and extraction time. Search results should visibly distinguish original note text from extension output and provide an include/exclude mechanism for derived or stale sources. Update the derived record and its FTS index consistently; verify existing rows are backfilled when the index is created and that rebuild/integrity checks detect drift [SQLITE-FTS]. Database transactions can atomically change run/index metadata, but filesystem artifacts require a separate publish/reconcile protocol [SQLITE-TX, SQLITE-ATOMIC].

For cache invalidation, compare the complete identity before reuse. Attachment digest, extension package/version, schema/API, block configuration, permissions, and host renderer/extractor changes can all change meaning. Keep old entries as old entries; status changes are explicit, never a silent identity rewrite. An extension upgrade may keep the same ID while changing logic or permissions. Store extension/runtime version and source digests with each result for diagnosis.

For cleanup, create one private directory per run and a manifest/registry entry before writing temporary files. Allow atomic publish only after output validation and a successful terminal state. Track active readers, preview views, and shared references. Cleanup must require both terminal run state and no remaining ownership/lease/reference; handle cancellation, crash recovery, retries, concurrent deletion, symlink/hardlink/rename cases, and partial publication. Do not remove a shared artifact or a directory solely because a worker exited or a pathname looks temporary. A cache's pathname is not an ownership proof.

## Failure and installation state model

Proposed states: pending, running, ready, stale, failed, disabled, unavailable, cancelled, and revoked/deleted where product policy needs them.

- **Upgrade:** create a new versioned identity; old output becomes stale and retains old producer attribution. Never render old executable markup under the new version.
- **Disabled:** stop new invocations; preserve or hide old safe results according to an explicit policy. Show the old version and disabled state. Do not quietly continue using its text as current.
- **Uninstalled/unavailable renderer:** open the note normally, keep editing and search available, and offer original attachment fallback. If showing a last preview, render only previously validated declarative data and visibly label its age, producer version, and unavailability cause.
- **Failed or timed-out extraction:** publish no partial text; report the failure; preserve the last successful result separately as stale if the UI policy permits.
- **Revoked or known-compromised extension:** policy must state whether to suppress/delete cached preview and derived search text, not merely stop future execution.
- **Nested worker:** default to denying subprocess creation. If a supported extension profile permits it, the outer job/container must track and terminate the whole descendant tree and apply shared resource/temporary-data limits. A timeout on only the first PID is insufficient.

The expected failure must leave the note editable and saveable. Worker progress and status may update asynchronously without monopolizing the main thread.

1. **Capability transfer:** synthetic attachment A requests another notebook, sibling attachment, arbitrary host path, symlink, redirected or relative markup resource, archive-member reference, network URL, and undeclared capability. Verify every access is denied and the extension receives no root or generic notebook API. Verify the handle expires on completion/cancel and cannot be reused.
2. **Message/output validation:** feed active markup, event handlers, script URLs, file URLs, remote image/font requests, malformed/deep/oversized trees, oversized text, invalid Unicode, and malformed binary inputs. Verify no script or ambient host bridge runs, invalid output is rejected, limits apply before rendering/indexing, and editing remains responsive.
3. **Nested-worker timeout:** synthetic worker hangs, forks a child/grandchild, floods logs/output, allocates memory, or ignores graceful termination. Verify hard timeout, whole-tree termination, no partial publication, bounded restart/backoff, and no editing/save/search stall. Run separately on each supported OS/kernel and verify the expected sandbox/job/cgroup is active.
4. **Index provenance:** submit known synthetic original note text and extension-derived text. Verify search labels the derived hit with source type, note/block, extension/version and extraction time, never rewrites note content, and allows the user to distinguish/filter. Test duplicate text, FTS backfill/rebuild, failed extraction, artifact replacement, deletion, and stale-source filtering.
5. **Cache staleness:** vary one identity element at a time: attachment digest, extension version, installed package digest, schema/API, configuration, permission revision, host renderer/extractor, and runtime. Verify each incompatible result becomes a distinct stale entry, never silently current.
6. **Installation/lifecycle:** disable, upgrade, uninstall, make the renderer unavailable, fail extraction, revoke an extension, and reopen the same note. Verify no disabled code executes; each state is explained; original note opens and remains editable; any shown cached result is safe, stale-labelled, and attributed.
7. **Cleanup and concurrency:** race cleanup against an open preview/search reader, a second run sharing content, extension crash, cancellation, process-tree timeout, crash during publish, symlink/hardlink/rename manipulation, and restart/recovery. Verify the manifest/leases prevent deletion of live/shared data and that orphan cleanup is idempotent and confined to owned run outputs.
8. **Regression and compatibility:** if Wasmtime is chosen, pin an exact supported release, run the relevant upstream Wasmtime/WASI tests plus targeted regressions for the public path, resource exhaustion, and fuel issues; test host-import limits separately. If a native worker is chosen, assert platform sandbox and process-tree membership at runtime. If an embedded active renderer is chosen, test CSP, bridge absence and blocked local/network navigation. Test declarative and unavailable-renderer paths on all supported host platforms.

No suggested numeric quotas are asserted as findings. Owners should set thresholds from representative file sizes, extension workloads, device memory/CPU, startup/edit latency and retention expectations.

## Already covered, corrected, optional, rejected, and unresolved

**Already present in the released plan:** one attachment handle/config object; per-renderer separate process and timeout; error-card intent; temporary scratch area; input hash plus extension ID as a cache key; retaining old cache after disable; showing last preview while unavailable. These are useful starting elements but are incomplete as specified.

**Corrections required:** a handle must be object-scoped and request-scoped; temporary work must be isolated and tracked; markup must not run with ambient host privileges; extracted text needs a derived source record rather than only a note ID; cache identity must include version/config/permission/host dimensions; timeout must cover descendants; deletion requires explicit ownership and no active references; stale/unavailable output needs producer/version/reason and safe rendering.

**Rejected assumptions:** an extension ID preserves meaning across upgrades; killing one process proves all work is stopped; a temporary pathname proves exclusive cleanup ownership; an embedded view makes returned markup safe; process separation alone blocks access to other notebooks; extracted text is user-authored because it is indexed alongside a note.

**Optional improvements:** bounded retry/backoff/circuit breaker; runtime/advisory monitoring and recorded package/runtime digests; a user filter for preview-derived or stale search hits; secure diagnostic history that excludes note contents; synthetic regression corpus based on public advisories; explicit sandbox capability report per host platform.

**Unresolved owner decisions:** permitted output profiles and whether any active content is supported; target OS/kernel/runtime matrix and fallback; numeric CPU/time/memory/input/output/log/queue/temporary-space budgets; extension install/update identity and permission-change UX; whether disabled, uninstalled, or revoked differs for cache/search retention; search default inclusion, ranking, and stale-result filter; retention/deletion period; failure count/backoff policy; whether any extension may need more than the selected attachment and what consent would be required.
