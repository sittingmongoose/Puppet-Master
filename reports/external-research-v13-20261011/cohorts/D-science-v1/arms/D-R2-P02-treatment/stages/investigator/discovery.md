# Investigator discovery — D-R2-P02-treatment

Research was framed by the required brief only. The exact plan has not been released or read. These are discovery findings and candidate design constraints, not clause dispositions or a selected extension framework.

## Scope and observed evidence

The product problem is a local notes editor that gives third-party extensions one attachment or custom block to preview and extract searchable text. The extension must not acquire ambient access to other notes or notebooks; normal editing must remain available if extension work hangs, crashes, fails, or is unavailable. A preview is derived data, so it needs its own source type, provenance, version identity, and stale/failed/unavailable state.

Useful existing extension-interface references show both benefits and limits. VS Code custom editors separate a document model from a webview, support read-only previews, and explicitly expect malformed structured documents to be handled without breaking the editor [VSC-CUSTOM]. Its webview guidance calls for minimal local resource roots, restrictive CSP, and input sanitization, while warning that sanitization alone is not enough [VSC-WEBVIEW]. VS Code's extension host can be local Node, browser worker, or remote Node, but Workspace Trust explicitly does not stop a malicious extension that ignores it [VSC-HOST, VSC-TRUST]. Thus an extension host boundary can help UI stability, but is not an authorization boundary for notebook data.

Electron provides an instructive process comparison, not a framework recommendation. Its utility process is a separate child with Node.js APIs, message ports, process lifecycle events, and a child kill operation [ELECTRON-UTILITY]. Electron's Chromium sandbox is enabled for renderer processes by default since Electron 20; privileged work is brokered through IPC, but disabling sandbox or enabling Node integration changes that boundary, and the project documents limits to its ability to match Chromium's security guarantees [ELECTRON-SANDBOX]. A process split is a crash-containment tool only when the exact effective OS permissions, bridges, child processes, and resource controls are also constrained.

WASM offers a distinct model: the guest has only host imports/capabilities, and WASI directory access is explicitly preopened [WASMTIME-SECURITY, WASMTIME-WASI]. But this label is not a guarantee. Public Wasmtime advisories document (a) a full filesystem escape involving symlink/trailing-slash cases, with OS/kernel applicability, (b) guest-controlled host memory/resource exhaustion, and (c) a fuel bypass in WASI polling fixed in recent releases [WASMTIME-FS-ADVISORY, WASMTIME-RES-ADVISORY, WASMTIME-RELEASE]. Fuel is an instruction-accounting mechanism and epoch interruption is coarser/non-deterministic; memory/table limiters apply to future growth and must be configured. Independently bounded wall time, memory, input/output bytes, host-call allocations, logs, handles, and concurrency are still needed [WASMTIME-LIMITS, WASMTIME-STORE]. Do not use a stale unpatched engine or assume that fuel controls every host operation.

Cross-platform worker containment differs materially. On macOS, an ordinary child launched by a sandboxed app inherits its sandbox; a separately entitled XPC service is the documented privilege-separation route, and security-scoped file access has an explicit start/stop lifetime [APPLE-PROCESS, APPLE-XPC, APPLE-SANDBOX]. Windows AppContainer requires explicit capabilities, while Job Objects can bind children and terminate a group; breakaway settings and legacy systems can let descendants escape a job boundary [WIN-APPCONTAINER, WIN-JOB]. Linux seccomp filters syscalls, namespaces separate selected resources, and cgroup v2 controllers bound resource use; these are different controls and must be composed and checked on the supported kernel/configuration [LINUX-SECCOMP, LINUX-CGROUP]. The design needs a platform matrix and a safe fallback where its expected containment is unavailable.

## Candidate approaches (not selected)

1. **Host-rendered declarative preview schema.** Extension returns bounded data (for example, a validated tree of allow-listed text, image references, tables, and links); the app renders it with its own components. This gives the host the clearest control over scripts, navigation, styling, and accessibility, and works well for static previews/search text. It limits arbitrary interactive widgets and may require schema growth for unusual formats. If Markdown/HTML is accepted, parse and sanitize it before rendering, disable raw executable markup, restrict URLs/resources, and keep any remaining markup in an isolated renderer with no ambient bridge. CSP and sanitization are defense-in-depth, not permission controls [VSC-WEBVIEW].

2. **WASM/component ABI with explicit imports.** This offers portable executable extensions and a narrow input/output ABI. Default imports should include only the current attachment bytes and minimal block metadata; no notebook enumeration, host paths, sockets, process spawning, or unrelated storage. It still requires host-side validation, patched runtime upkeep, per-call quotas, and OS protection of the runtime itself. It may be the best prototype when richer computation is needed, but the advisories and platform/runtime support must be evaluated before selection [WASMTIME-SECURITY, WASMTIME-LIMITS, WASMTIME-FS-ADVISORY, WASMTIME-RES-ADVISORY].

3. **Separate native/Node worker under OS controls.** This can handle existing native libraries and provides a killable process boundary, but arbitrary code inherits capabilities unless explicitly reduced. Build per-platform containment: macOS XPC service entitlements rather than a plain child; Windows AppContainer plus a Job Object with breakaway checked; Linux namespaces/seccomp/cgroups as available. Disable nested process creation by default; if ever allowed, test that every descendant remains inside the same kill/resource/cleanup scope. It has the largest platform-specific implementation and validation burden [ELECTRON-UTILITY, APPLE-XPC, WIN-APPCONTAINER, WIN-JOB, LINUX-CGROUP].

A restricted webview can render approved output, but should not receive extension code or a privileged preload. Declarative model data can be painted by host code; interactive extension-authored execution needs a separately evaluated sandbox, blocked network/navigation by default, and no filesystem or notebook bridge.

## Proposed end-to-end data and behavior model

- Broker each invocation for one selected attachment/custom block. Provide opaque per-request identity, read-only bytes (or a narrow content handle), and only required block metadata. Do not provide notebook roots, generic filesystem APIs, notebook search APIs, or reusable notebook-wide grants. Each permission is an explicit host-issued capability, scoped to the current request; absent capability means denied. Any later need for note body/context should be a separate owner decision and a separate narrowly scoped grant.
- Store the extension result as a versioned derived artifact. Suggested cache identity: note/block identity; attachment digest; extension stable ID, installed package digest and version; extension API/schema version; host renderer/extractor version; relevant configuration and permission revision. Store result digest, extracted text, completion time, and status. Re-key or mark stale after attachment, extension, config, API, or host-render changes; never silently rebind old output to a new extension version.
- Keep note-authored text and preview-derived text in separate records and search source types. Index each preview text record by a stable artifact ID and retain the producing extension/version, source attachment digest, note/block link, and extraction time. Search can include derived text but must label it “preview text” with extension/version and offer a way to distinguish/filter it; never merge it into the note body or present it as user-authored. SQLite FTS5 external-content indexes require explicit synchronization with their content table; use transactional updates/rebuild or equivalent invariants [SQLITE-FTS, SQLITE-TX].
- Bound the entire pipeline: attachment bytes and decompression/parse work, wall-clock time, CPU, memory, output/text bytes, tree depth/node count, images/links, host-call payload sizes, handles, log volume, disk temporary bytes, active workers, and queued jobs. Do not invent numeric thresholds here; profile representative extensions/devices and make thresholds owner-approved. Keep decoding, extension execution, and result validation off the UI thread. Send only validated output to the UI.
- Use a supervisor with per-invocation deadline and cancel path. On timeout, terminate the worker and all descendants in its containment unit, mark the run failed/timed out, preserve editing, report that the preview failed, and apply bounded restart/backoff or disable that extension after a failure threshold. Do not wait synchronously on a UI-critical thread.
- Model states explicitly: pending, running, ready, stale, failed, disabled/unavailable, and cancelled. A ready preview shows extension name/version and refresh time. A previous safe declarative result may be shown after upgrade/disable only with a persistent stale label naming the producer version and explaining why refresh cannot occur; owner should decide whether disabled/uninstalled extensions permit even cached previews. Never rerun a disabled extension. When no renderer exists, keep the note open/editable, display its original block/attachment fallback (open/save/type/size), and explain that the extension is missing, disabled, or failed.
- Cleanup by explicit run/artifact manifest and state, not a pathname heuristic. Give each run its own private temporary directory; publish only completed output atomically; track active readers/leases and shared artifact references; delete only after the run is terminal and no consumer/reference remains. On cancellation/crash, reconcile through the manifest/registry, reject symlink/path escapes, and make cleanup idempotent. SQLite transactions can make metadata transitions atomic, but they do not by themselves make external files safe to delete [SQLITE-TX, SQLITE-ATOMIC].

## Public implementation/test and regression leads

Wasmtime documents cargo test -p wasmtime-wasi, with test programs under crates/test-programs; its guide identifies Preview 1/2 integration tests and that these programs compile/run under the harness. These are useful upstream reference paths, not checks run for this product [WASMTIME-TESTS]. Pin the actual engine and ABI release used by a prototype; at research time, Wasmtime v49.0.2 is a released tag at commit prefix 3c8a3e7, with further current fixes listed in the release [WASMTIME-RELEASE].

The filesystem escape advisory lists affected and patched Wasmtime version ranges and differentiates Linux kernels using openat2 from macOS/older Linux; the resource exhaustion advisory says multiple guest-controlled host-allocation paths were involved, and patch knobs on pre-42 branches could remain set to large defaults. A separate release entry fixes WASI poll_oneoff bypassing fuel. These findings justify patch monitoring, regression tests for paths/symlinks/hardlinks, quotas on host APIs, and independent wall-clock/process containment. They do not prove that every WASM runtime or version has the same defect [WASMTIME-FS-ADVISORY, WASMTIME-RES-ADVISORY, WASMTIME-RELEASE].

## Validation proposals and executed work

**Executed:** source discovery consisted of official documentation, runtime/project documentation, upstream test guidance, release/advisory history, and platform documents linked in sources/index.md. The prescribed native Goal activation and binding guard succeeded before source discovery. No application or adversarial test was executed. The later mandated plan-release helper is not an implementation test.

**Proposed:** test that a plug-in can read only its current attachment and cannot enumerate/open another notebook, access the host filesystem/network, or use an undeclared capability; fuzz malformed/oversized/decompression-bomb input and malformed result trees; test wall-time, CPU/memory/output/host-call/log/queue quotas; simulate hang, crash, restart, nested child, cancellation, and shutdown while editing/searching; assert the editor/search UI stays responsive. Test cache invalidation across attachment changes, extension ID/version/package digest, API/schema and config/permission changes; verify stale/failed/disabled/unavailable labels and old-version attribution. Verify preview text has distinct provenance through search, never modifies note content, and behaves correctly on duplicates/deletion. Test cleanup under shared references, active readers, open previews, concurrent cleanup, crash mid-publish, symlinks/hardlinks/renames, and install/upgrade/uninstall. Run a platform matrix on each supported OS/kernel/runtime version, including sandbox denial and whole-process-tree termination. Add public regression cases modeled on the Wasmtime advisories and use the upstream Wasmtime/WASI suites if Wasmtime is selected.

## Owner decisions to carry into planning

- Which execution profiles are supported after a prototype: declarative-only; WASM with a constrained ABI; or native worker with per-OS sandbox. Do not choose by isolation label alone.
- Whether any extension-authored HTML/JavaScript is allowed. Recommended starting point: declarative output and host rendering, no ambient bridge, no remote fetches. If richer execution is allowed, define the separate renderer origin/process and its permissions.
- Exact resource quotas and the failure threshold/backoff before extension disablement, based on representative workload/device data.
- Whether a safely inert cached preview may remain visible after extension disable/uninstall/upgrade, and retention/cleanup policy. If visible, default it to stale with old producer identity.
- Search ranking/default inclusion and user-facing filtering for derived text; regardless, provenance must remain visible.
- Supported OS/kernel versions and the fallback when strong isolation or descendant accounting is unavailable.
- Extension package identity/update/authenticity and compatibility policy; a marketplace is outside this brief.
