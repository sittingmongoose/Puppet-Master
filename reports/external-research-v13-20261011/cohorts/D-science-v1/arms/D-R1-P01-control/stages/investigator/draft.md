## Recommended component behavior

Use a persistent form with separate state for (a) the reviewer’s local decision, explanations and notes, (b) validation results for a precise snapshot, and (c) the authoritative saved resource version. A check being valid does not mean a save has committed. Client checks can give early syntax/required-field feedback, but server business rules and every write remain authoritative because browser checks are bypassable. [S01](sources/index.md#s01) [S07](sources/index.md#s07) [S08](sources/index.md#s08)

Give each editable field a local revision and dirty flag. When an asynchronous check starts, capture request ID, the relevant values and local revisions, and the server version against which the check ran. A reply may update only that matching snapshot. If the reviewer edited the decision, edited an explanatory field on which the rule depends, started a newer check, or the server version changed, mark the reply stale and do not apply its error, success, or replacement values. A cancellation request may save work but does not prove the server did not process a check.

Every detected error needs readable text next to its field and a persistent summary listing all current errors. Each summary item must lead by keyboard to the relevant existing control; inline and summary wording should agree. Programmatically associate field errors, and set invalid state only after a check has actually failed. Use text such as “Error” and a meaningful message, plus optional icon/border; never depend on color. [S01](sources/index.md#s01) [S03](sources/index.md#s03) [S04](sources/index.md#s04) The GOV.UK pattern is a useful maintained model for summary-plus-inline coverage, matching wording, and links. Its conventional summary-focus advice applies to a post-submit form response; the asynchronous portal must preserve focus if the reviewer has moved. [S10](sources/index.md#s10)

Keep a concise, non-focus-taking status channel for meaningful state changes: a discrete decision check starts, validation returns, a save starts or completes, a conflict arrives, or save outcome is unknown. Do not announce each keystroke as a save or enqueue every intermediate field response. Keep the full status/errors in the page for later review. WCAG 4.1.3 addresses messages that are statuses without focus; its supporting guidance warns that excessive live-region output can be chatty and recommends user testing. [S01](sources/index.md#s01) [S02](sources/index.md#s02) The WAI tutorial offers polite feedback patterns, but its “during typing” username sample is synchronous/local and cannot establish async freshness. [S04](sources/index.md#s04)

For focus, record whether a reviewer action still owns the response context. A background check or remote-update event never moves focus. If an explicit submit returns errors and focus remains with that submit flow, a single move to the summary is a candidate; if the reviewer has moved to another field or a newer action superseded the submit, keep focus where it is and announce a short status such as “Two errors need review.” Let the reviewer activate an error-summary link or a “Review errors” action to move intentionally. Do not autofocus every error field. The actual focus policy is an owner decision to resolve with keyboard and AT testing; WCAG requires detectable text/status but does not mandate a particular error layout. Historical reports show that summary focus and links can fail in a particular assembled page even when the message appears. [S01](sources/index.md#s01) [S10](sources/index.md#s10) [S12](sources/index.md#s12) [S14](sources/index.md#s14)

For concurrent reviewers, fetch a server revision/ETag with the resource and condition a decision write on that version using If-Match or an equivalent server-enforced compare-and-set. A failed precondition means the write must not apply; mark the decision stale, fetch the current authoritative state and show a conflict explanation with explicit choices. Do not silently replace a reviewer’s decision or any dirty explanation/notes. If the API cannot compare versions, the service owner must specify an equivalent atomic contract. [S09](sources/index.md#s09)

For saves, snapshot values and operation ID at start. A success marks only that snapshot saved; edits made after it remain dirty. A precondition failure is a conflict, not a validation success. A timeout/disconnect is “save outcome unknown,” not “saved” or a confirmed rejection: preserve the complete local draft and reconcile by operation ID/status lookup or retry the same idempotent operation only if the API guarantees that contract. After resolving, revalidate the decision against the latest resource version before allowing another write. This reconciliation/idempotency behavior is a proposed API contract, not something guaranteed by the cited sources.

## State model and ownership boundaries

| Transition | Guard and stored data | Visible and announced behavior |
|---|---|---|
| Clean → Editing | User changes decision, explanatory text or note; increment that field’s local revision and mark it dirty. | Keep edits in the form. No save announcement per character. |
| Editing → Check pending | Start only for configured local rule or meaningful decision checkpoint; store request ID, field revisions, captured values and server revision. | Retain field focus. Optionally announce one concise “Checking decision” status for this checkpoint. |
| Check pending → Current error / current valid | Reply request ID and every relevant local revision still match, and resource version is the version checked. | Apply structured errors or validity to that snapshot. Keep text and status. Use inline error associations and full summary links. |
| Any pending check → Stale reply | Any newer input/check or relevant resource version supersedes captured data. | Discard result; never clear newer errors, validate newer decision, move focus, or overwrite fields. Schedule one current check only if policy requires it. |
| Current valid → Save pending | Explicit save captures whole payload, operation ID and expected ETag. Server repeats validation and atomically checks precondition. | Show saving state and keep all fields. A validation result alone is never displayed as saved. |
| Save pending → Saved snapshot | Server confirms commit and returns new version. | Mark only unchanged captured fields clean; keep later edits dirty. Announce one completion and distinguish remaining edits. |
| Save pending → Validation error | Server rejects submitted snapshot with structured field errors. | Apply only if snapshot still current; preserve explanations/notes. Present text, summary and links; guarded focus policy above. |
| Save pending → Conflict | Server rejects If-Match/compare-and-set or an authoritative update changes a dependency. | Mark decision stale, refresh server comparison data, preserve local draft and show explicit resolution. Do not merge over a dirty field. |
| Save pending → Outcome unknown | Timeout, disconnect, route change or missing response after request may have reached server. | Keep operation ID and local draft; state “Could not confirm save” and reconcile before claiming saved or resubmitting. |
| Conflict → Rechecking / Editing | Reviewer resolves against current server state or revises decision. | Preserve text, use current resource revision, revalidate and require a new explicit save. |

For reuse, expose a small contract: stable field IDs and structured current errors in; request/snapshot metadata and resource version in; validation/save/conflict transitions out. Keep service rules and network ownership outside visual markup. Supply page language and interface direction explicitly; field-specific mixed-direction handling is a separate input policy. The frontend owns local edits, focus, request correlation, stale-response suppression, dirty flags, rendering and accessible associations. The service owns field/business validation, permissions, resource version, atomic conditional writes, structured error codes, conflict facts, and save reconciliation. A remote patch can update a field only when it is locally clean and the patch is known not to invalidate the decision; otherwise preserve the local value and mark the affected fields stale/conflicted. A decision may depend on an untouched field, so field-local “clean” status alone cannot establish validity. Product/API owners must define dependency and merge semantics.

### Maintained implementation evidence

- **Native HTML constraint validation:** the browser handles required/format checks and first-error focus with little component code. W3C’s current informative guidance notes that its messages can be generic, temporary, not magnified, and expose only the first error before another submit. It is a candidate for simple client syntax checks only when tested in the supported browser/AT combinations; it cannot validate server business rules or remote versions. [S07](sources/index.md#s07) [S18](sources/index.md#s18)
- **GOV.UK Frontend / Design System:** the maintained error-summary pattern pairs a top summary with inline field errors, matching text and links to the answer. Its documentation says to focus the summary for conventional form validation. The latest release record inspected was v6.5.1 at commit efdc06c; that release’s note did not change error-summary behavior, so it is a candidate pattern, not a validated drop-in for async focus preservation. [S10](sources/index.md#s10) [S11](sources/index.md#s11)
- **USWDS validation checklist:** this alternative shows requirements as a checklist with live pass/fail feedback. The current component page offers a v3.14.0 download while saying it will not be supported after v3.12.0 because testing found major usability/accessibility issues. Its linked studies report that 5 prototype participants did not notice a status change and 4 were confused by the checklist’s purpose, preferring inline or submit-time errors. Those are bounded prototype findings, not universal user or AT results; they are a strong reason to test before choosing a live success checklist. [S15](sources/index.md#s15) [S16](sources/index.md#s16) [S17](sources/index.md#s17)

These examples are evidence about particular patterns, versions and study prototypes. They do not establish translated quality or compatibility for the future portal. The component library remains an owner decision.

### Alternatives and trade-offs

| Strategy | Behavior | Advantages | Costs and limits |
|---|---|---|---|
| Check at decision commit / field exit, then save against same version | Send one server check for the chosen decision at an intentional checkpoint; keep controls editable; discard stale replies; save later with If-Match. | Earlier feedback; fewer doomed save attempts; can identify remote invalidation before commit. | More requests and response-order state; blur is not a safe trigger for every field; must prevent announcing every response; check-to-save race still requires server compare-and-set. |
| Check on explicit submit/save | Run local syntactic checks, send one full server validation/save attempt, and return structured errors or a committed version. | Clear user checkpoint; fewer background requests; server decision remains final. | Feedback waits for submit; error response can arrive after focus moved; must preserve draft and correlate revisions; save and validation outcome must remain distinct. |
| Remote update push/poll versus save-time comparison | Push/poll marks the loaded version stale, then fetch current facts; save-time If-Match remains the final authority either way. | Push/poll can tell an active reviewer earlier; save-time comparison is simpler. | Push/poll adds lifecycle and duplicate-notification complexity. Neither route can overwrite dirty text or replace atomic server enforcement. |

Recommendation: use an explicit decision checkpoint for rules that are useful to know early, then validate and compare versions again on save. Keep routine explanation/note editing local until explicit save unless the owner chooses a debounced draft-save policy. If draft autosave is selected, debounce requests and announce completed snapshots only; the network/API still needs unknown-outcome reconciliation.

## Proposed validation matrix

These are future checks, not checks run in this investigation.

1. **State reducer/request identity:** table-driven tests for two checks in opposite response order; edit after request; decision change then old valid reply; same field revision with a newer request; remote version change before a reply. Assert only the response whose request ID, relevant local revisions and resource version match can change current validation.
2. **Field dependency and disappearing field:** make a conditional field disappear while a response is pending; return an error for that old field. Assert the obsolete result is ignored, no hidden/detached target receives focus, and no summary link points to a nonexistent control. Add a remote update to a clean dependent field while the decision is dirty; assert the decision becomes stale and note text is preserved.
3. **Focus and keyboard:** keyboard-only submit; trigger a server error and move to a different field before it returns. Assert active element/logical keyboard position is unchanged, status is concise, every summary link can be reached with Tab and Enter, and activating one lands at the corresponding field with its label and inline error. Repeat for one and several errors, validation while focus is on a note, and an unchanged explicit-submit context.
4. **Accessible message association:** inspect accessibility tree/DOM for label, invalid state only after failure, described-by reference, summary heading/list/links and stable ID targets. Verify error remains textually understandable without color. Test announcements at each state transition for duplicates, interleaving and polite interruption; do not infer compatibility from the tree alone.
5. **Remote-write races:** two reviewers load version V; one saves V+1; second submits If-Match V. Assert server does not apply the second write, returns current conflict facts, local explanation and notes remain, and revalidation uses V+1. Race a valid check response with a 412 and with a newer update event; conflict/stale state must not be cleared by old validation.
6. **Save certainty:** save snapshot N, edit to N+1 while pending, then acknowledge N; N is clean and N+1 dirty. Simulate timeout before commit and after commit; retain operation ID and draft, display outcome unknown, reconcile/retry only under server idempotency guarantee, and never announce saved until outcome is known. Exercise navigation away and return against a changed version.
7. **Layout and content direction:** at 200% text and a 320 CSS px viewport, inspect a long translated-label fixture, multi-line summary errors, focus visibility and long unbroken identifiers; confirm information/functionality remains and ordinary form content does not need horizontal scroll. Test explicit LTR and RTL page direction with mixed-script notes, identifiers, punctuation and error links. The fixture can check layout/direction only, not translation quality.
8. **Browser/AT sessions:** after portal integration, document browser, OS, screen reader, versions, language/voice and steps. Test current and delayed errors, status ordering, keyboard position, submit summary behavior, field links, save/error/conflict/unknown messages and locale changes in representative supported combinations. Human language review and multilingual usability sessions are separate required proposals; no compatibility is claimed before they run.
