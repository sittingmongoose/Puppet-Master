# D-P01 — Software planning brief

We need a reusable review form for a multilingual service-request portal. A reviewer can enter a decision, edit several explanatory fields, and attach notes while server checks run asynchronously. Research how the form should expose pending validation, errors, save status, and changes made by another reviewer without losing keyboard position or making assistive-technology announcements overwhelming. The requested output is a sourced component plan with alternatives and a meaningful test strategy.

The same form is used with narrow layouts, zoomed text, and languages that expand labels or change reading direction. An error can arrive after the reviewer has moved to another field, and a remote update can invalidate a previously acceptable choice. Users should be able to find all errors, understand what is saved, and return to the relevant field. Discover primary guidance and maintained implementations, including useful public failure history; no UI toolkit or validation library is selected.

Investigate the relationship between client checks, server authority, focus behavior, and accessible status messages. Compare at least two strategies for presenting asynchronous validation and remote conflicts. Explain how the component represents stale responses and interrupted saves instead of treating every network reply as current. Include state transitions and ownership boundaries that another team could implement.

Do not require a pointer, use color as the only error signal, move focus on every arriving response, or announce each keystroke as a save. Do not infer translation quality or assistive-device compatibility without evidence. Preserve the user's unsaved explanation when validation or a remote change rejects a decision. Public examples and synthetic state traces may support executed checks, but future portal integration and multilingual usability testing must remain explicitly proposed.

Complete all substantive research and planning obligations within a maximum of 60 elapsed minutes. Finish earlier when the complete output is ready. There is no minimum research duration, no requirement to consume the allowance, and no credit for waiting. The deadline includes arm-specific setup, provider queueing after admission, tools, native retries, handoffs, revision and delivery. Output quality is assessed independently of elapsed time.
