# D-P06 reviser final — D-R2-P02-control

## Brief and evidence boundary

### Original brief

> A local notes application will support third-party rich-preview extensions. When a note contains an unfamiliar embedded file or custom block, an extension may produce a preview and searchable text. Research a preview-host component that keeps ordinary editing usable while handling untrusted extension code, malformed inputs, cache invalidation, and installation changes. We need an evidence-backed plan and alternatives, not a working plugin marketplace.
>
> An extension must not gain access to unrelated notebooks simply because it can render one attachment. Users should know when a preview is stale, failed, or produced by a different extension version. Extracted text needs provenance so search can distinguish a preview-derived representation from the original note content. The host should recover from a stuck renderer and clean up disposable work without deleting shared or still-needed artifacts.
>
> Discover relevant primary runtime, process, storage, and extension-interface documentation, repository paths and tests, and useful public regression history. Compare isolation and rendering approaches, including declarative output versus executable embedded content where relevant. Investigate permission scope, resource budgets, nested workers, and host-platform limitations rather than trusting an isolation label.
>
> Do not grant unrestricted notebook access, execute returned markup with ambient host privileges, infer safe cleanup only from a cache pathname, or silently treat extracted text as user-authored content. Avoid preselecting a runtime or extension framework. Include behavior for disabled or upgraded extensions and for opening a note when its renderer is unavailable. Any executed checks should use synthetic inputs or disposable public examples; proposed adversarial, integration, and cross-platform tests must remain clearly labeled.

This is a planning result, not an implementation report. It does not design a plugin marketplace or select a runtime/framework. Attachments, custom blocks, package bytes, renderer output, and messages remain untrusted. The brief's prohibitions are binding: no unrelated-notebook authority, no ambient-privilege execution of returned markup, no pathname-only cleanup inference, and no loss of derived-text provenance.

Primary-source identities and applicability are recorded in [source-map.json](source-map.json), with a navigable index in [sources/README.md](sources/README.md). Inherited IDs S-01–S-24 keep their original identity; S-25–S-28 are new, pinned repository test sources. No downloaded code was run. No product test, executable witness, sandbox witness, host, or real notebook was run. Reading upstream test source is source discovery, not test execution.

## Exact released plan

The plan is preserved verbatim below.

> The provisional host provides an extension with an attachment handle, block configuration, and a temporary work directory. The extension returns preview markup and extracted text over a message channel. The host would display the markup in an embedded view and index the text under the note ID. Research whether this boundary adequately limits capability and preserves the requested provenance, including active content and indirect file references.
>
> A separate process would run each renderer with a timeout. On timeout, the host would kill it, display an error card, and remove its temporary directory. A shared cache would use input digest and extension identifier as its key. The draft assumes process termination establishes cleanup ownership and that matching identifiers preserve preview meaning across upgrades; both assumptions need governing evidence and alternatives.
>
> Disabling an extension would hide new previews but retain old cache entries for quick restoration. Unavailable renderers would show their last preview with a badge. The plan needs to examine whether old extracted text should remain searchable and how users learn about potentially changed semantics or permissions.
>
> Give retain/revise/reject/unresolved dispositions for capability transfer, output display, indexing, isolation, cache identity, and cleanup. Compare declarative output with richer executable rendering and identify conditional guarantees. Propose checks for a hung nested worker, active markup, stale cache reuse, uninstall, failed extraction, and cleanup during concurrent use. Report any executed checks with their exact sandbox scope; no future host or real notebook is assumed tested.
>
> Complete all substantive research and planning obligations within a maximum of 60 elapsed minutes. Finish earlier when the complete output is ready. There is no minimum research duration, no requirement to consume the allowance, and no credit for waiting. The deadline includes arm-specific setup, provider queueing after admission, tools, native retries, handoffs, revision and delivery. Output quality is assessed independently of elapsed time.

## Clause-by-clause disposition

### P1 — Capability, message, display, and indexing boundary

**Revise the boundary; reject direct active-markup display as the default and reject note-ID-only indexing.** The plan already names an attachment handle, block configuration, invocation work directory, channel, preview, extracted text, embedded view, and indexing, and asks about active content and indirect references. Those components do not define their authority or validation rules.

Resolve the selected attachment/block in the host. Give the extension an opaque, read-only, short-lived capability for only that object and invocation. Bind it to note/attachment identity and digest, block identity, exact extension package identity, job ID, rights, byte allowance, and expiry. The extension cannot choose a notebook, note, path, or attachment ID as authority. A sibling or indirect reference requires another host-authorized handle. Do not pass the notebook root, database, raw path, environment, credentials, or a general host object.

Pass block configuration as bounded data validated against a versioned schema. Treat malformed encodings, huge or nested values, unexpected fields, message replay, mismatched job IDs, and returned values as hostile. The channel needs request identity, cancellation, maximum message counts/sizes, typed errors, and a versioned protocol. WIT describes imports/exports but cannot enforce the host implementation's authorization or validate all returned values [S-03].

Prefer a bounded declarative result: text, headings, tables, safe links, and media references that the host resolves through approved attachment capabilities. Validate byte counts, nesting, node count, URLs, and referenced objects, then render with host-owned UI. If required formats cannot be represented declaratively, arbitrary executable output is a separate higher-risk product decision. For web-like content, require a separate sandboxed context with opaque origin, no native bridge, restrictive CSP, and explicit denial/filtering of navigation, popups, forms, downloads, remote loads, and protocol handoff. A host-owned attachment proxy must validate every request. WHATWG conditions matter: sandboxing can give srcdoc an opaque origin; unsandboxed srcdoc can inherit the creator's origin, while allow-same-origin removes the sandboxed-origin flag [S-20, S-21]. Sanitizing HTML alone does not prove safety. Specify script, event-handler, CSS, URL, loading, focus, accessibility, and navigation behavior.

Keep extracted text in a separate derived-content record or namespace. Store source note and attachment identity/digest, block identity, extension ID and exact package/build digest, API/schema version, runtime/policy version, configuration digest, extraction time, and state. Search must label snippets as extension-derived, identify the attachment and producer, and distinguish them from authored note text. Do not merge extracted text into the note body.

Publish provenance and text only after complete successful extraction, atomically or with an equivalent versioned-pointer protocol. Do not commit partial output as current. If a write fails, preserve a last good result only with its actual stale state. SQLite is one possible mechanism: multiple readers may coexist, only one simultaneous writer is allowed, deferred write upgrades can return SQLITE_BUSY, and snapshot readers persist until transaction end [S-23]. This is an option, not a storage requirement or proof of the overall design.

### P2 — Process, timeout, scratch, and cache

**Retain process isolation and visible timeout failure as candidates; reject the cleanup and cache assumptions.** An isolated process can contain a crash, but a timeout does not enforce CPU, memory, output, descendant, or host-call limits. Rust Child::kill terminates the direct child; waiting/reaping is separate, and this API does not establish process-tree containment [S-24]. A process boundary is not a complete permission boundary.

If using an OS process, run it under platform process-group/job-object or equivalent supervision. On timeout/cancel/crash, terminate the whole invocation tree, wait/reap it, and account for orphans. Set per-invocation and aggregate wall-time, CPU, memory, output, open-file, process/thread, queue, and concurrency limits. Reserve host resources for editing/search/shutdown. Default nested workers off; if enabled, children inherit the exact same attachment-only capability and aggregate budget and cannot reset quotas.

If evaluating WebAssembly, expose only needed imports. Wasmtime illustrates why “Wasm” is not a standalone guarantee: fuel is disabled by default; an enabled store starts with zero fuel until the host sets it; epoch interruption needs an explicit deadline and traps by default. StoreLimitsBuilder limits are separate: memory size is per linear memory, and table/count limits need their own configuration [S-01, S-02]. These controls do not automatically meter host calls, allocations, I/O, process memory, or every bulk operation.

Recent Wasmtime advisories/release notes are conditional evidence, not a categorical verdict. They include Preview 0 polling that did O(n) host work outside fuel accounting (fixed in 49.0.2, with CLI/library exposure conditions); unlimited sink allocation when a WASI context left stdout/stderr unconfigured (fixed in 49.0.2); a WASI HTTP outgoing write-limit problem in 49.0.0 (fixed in 49.0.1); and a hard-link/rename permission issue requiring a particular mix of read-only and higher-rights preopens [S-05–S-09]. Deny unneeded interfaces, stdio, filesystem rights, clocks, and network. Pin a maintained runtime and promptly ship security updates. These version/API-specific examples do not show that every use is unsafe or safe.

A browser worker/web-extension model avoids Node and child-process APIs but may still create workers and use web-facing network facilities; CORS is not host authorization and virtual filesystem semantics remain relevant [S-15]. Electron utility processes run Node; env defaults to process.env, and without an explicit session they use system network context. Renderer sandbox and IPC settings must be reviewed together; Electron's webview availability is not guaranteed [S-17–S-19]. Deno permissions offer another conditional model: explicit resource permissions can narrow access, while allow-all removes the boundary; disk-backed APIs may consume disk without ordinary read/write permission [S-22]. These are options, not a runtime selection.

A timeout should cancel the job and show failed/timed-out status while the original note remains open and editable. Do not present partial output as current. Preserve a prior successful preview only with an explicit stale/unavailable state and its actual source and producer identity. Keep logs free of note contents and extension payloads.

**Reject the inference that process termination establishes cleanup ownership.** The host creates a unique per-invocation scratch root and ownership record; an extension cannot choose the parent or expand cleanup scope. Terminate/reap the full worker tree and account for readers/leases before cleanup. Use root-identity and no-follow checks; refuse or quarantine cleanup on symlinks, identity mismatch, live references, open handles, or uncertain ownership. Prefer immutable generation directories plus a host-owned atomic pointer, or explicit leases/refcounts with crash-safe reconciliation for shared blobs. Retry/quarantine failures. A pathname, extension-selected suffix, or child exit is not proof that recursive deletion is safe. Filesystem case, unlink-on-open, and atomicity/durability under concurrent writers vary by OS/filesystem [S-11]. The WASI cleanup-marker pattern applies only under each test's preopened test root; it is a fixture pattern, not product cleanup authority [S-12]. New pinned upstream path tests add concrete traversal cases but do not test concurrent shared-reader cleanup [S-27, S-28].

**Reject the cache key of input digest plus extension identifier as insufficient.** A candidate key includes stable source identity and canonical input bytes/digest; attachment and block identity; configuration digest; exact extension package/build digest and API version; renderer/runtime build; security-policy/schema version; and host-controlled locale/theme/options that affect output. Recompute current key material in the host before reuse. An identifier can remain unchanged across semantic or permission-changing upgrades. Keep result digest, provenance, generation, timestamp, and status with the key. Publish the cache pointer and search record together. Treat a cache hit as data only: disabling/removing an extension prevents new execution, and cached output cannot silently become a current execution result.

The phrase “cryptographically bound” is underspecified and is removed. The proposal is that the host recomputes the cache identity and compares it with the stored record. Any signature or tamper-authentication requirement is a separate mechanism; a cache key is not by itself a signature or trust decision.

### P3 — Disable, upgrade, unavailable renderer, and changed permissions

**Revise while leaving retention, consent, and interface choices to the owner.**

- Disable immediately prevents new jobs. Mark cached previews and extracted text disabled/stale; by default exclude stale/disabled derived text from ordinary search, or expose it only through an explicit choice with clear stale/derived labeling. Define bounded retention; do not retain indefinitely merely for quick restoration.
- An upgrade can change meaning, API behavior, or permissions. Do not label old output current under the new package identity. Before the new extension runs, surface changed requested capabilities and their effects. Neither plan nor sources establish a universal rule that every new permission must block until consent. The owner selects a permission/consent policy.
- On re-enable, verify source, configuration, package, API/runtime, and policy key material; regenerate when a relevant field differs. On uninstall, prevent execution and remove or quarantine only extension-owned derived artifacts under an explicit retention rule. Preserve original notes and attachments.
- If a renderer is unavailable, keep the note open/editable and show a clear reason. A cached preview may be shown as current only if the host verifies its key against current input, extension package, API/runtime, and policy identities. Otherwise show it only as historical/stale with producer and time, or show an unavailable card. A badge alone is inadequate if users cannot distinguish disablement, removal, upgrade, failure, or timeout.
- Keep rendering off the editor critical path, with bounded queues and cancellation. A reported VS Code Windows 1.125.0 extension-host regression blocked Search/Git for seconds to minutes; its 1.125.1 milestone does not identify a fix commit in the issue body, so it is a failure-mode example only [S-16].

### P4 — Dispositions, alternatives, and validation

The requested dispositions are: capability transfer **revise**; output display **reject active-markup default and prefer declarative output**; indexing **revise**; isolation **retain process as one candidate and revise its guarantees**; cache identity **reject the proposed two-field key**; cleanup **reject process termination as ownership proof**. These recommendations do not choose an implementation.

Declarative host-rendered output narrows authority and avoids executing returned layout/script, but may not express every required preview. A sandboxed browser context can handle web-like content with higher complexity and needs a strict origin/resource/IPC design. Wasm components can offer a typed import surface and guest resource controls, subject to host-call/runtime conditions. Restricted OS processes may suit native parsers but require platform-specific authority and descendant/resource supervision. No source establishes a single portable sandbox satisfying all needs.

#### Proposed synthetic/disposable validation — none run

1. **Hung nested worker:** use a synthetic renderer that starts a child and grandchild, then blocks. Verify the full tree is terminated/reaped, no orphan remains, budgets return, timeout status appears, and editing/search stay responsive. Repeat with each supported OS supervisor. For Wasm, test fuel/epoch exhaustion, large bulk operations, memory/table limits, host allocations/calls, and any enabled thread model.
2. **Active markup and indirect references:** return scripts, event handlers, javascript:/file: URLs, remote images/fonts, top navigation/popups/downloads, and guessed sibling/notebook paths. Assert no script or host API executes, no unauthorized file/network access occurs, and only authorized attachment-proxy requests resolve. Exercise the production embed configuration, origin, CSP, bridge, and navigation filters.
3. **Stale cache reuse:** render synthetic content and vary one key component at a time: bytes/source identity, block/config, extension artifact/version/API, host schema, runtime build, policy, and relevant display options. Verify miss/recompute or explicit historical state, derived-index invalidation, and correct labels. Include same bytes under distinct source identities if source-instance binding is required.
4. **Disable, upgrade, uninstall, unavailable renderer:** verify disabled/uninstalled extensions cannot execute, including on cache hits; changed artifacts cannot label old output current; original note/attachment survives; search follows the owner-selected stale policy; and notes remain editable without a renderer. Verify changed permission requests are surfaced and handled according to the owner's consent policy, without assuming a mandatory block-until-consent rule.
5. **Malformed/failed extraction:** use synthetic truncated, oversized, deeply nested, invalidly encoded inputs and terminate the renderer mid-stream. Verify bounds, cancellation, no partial/current index publication, accurate error/provenance, and the selected prior-result policy.
6. **Concurrent cleanup:** hold an open reader on a synthetic preview while replacement, disable, or uninstall occurs. Verify references/leases or immutable generations prevent use-after-delete, path reuse, and cross-job deletion. Inject symlink, rename, replacement, and uncertain-reference conditions; verify cleanup refuses/quarantines unsafe cases and retries safely. Run on each supported OS/filesystem because behavior differs [S-11]. Existing WASI tests are useful for root-relative path cases, not a substitute for this concurrency test [S-27, S-28].

**Executed checks:** none. This stage read primary documentation and upstream test source; it did not run tests, downloaded code, a host, or a real notebook. There is no sandbox scope to report as tested. Every numbered validation above is future work.

## Critic dispositions

The critique is assessed against the brief, exact plan, and source records; critic agreement is not authority.

- **C-01 — No concrete upstream test case was evaluated: accept and resolve the discovery gap.** At the pinned Wasmtime 49.0.2 commit, tests/all/fuel.rs contains an iloop test that sets 10,000 fuel and expects OutOfFuel from infinite loops and large bulk operations; tests/all/limits.rs exercises configured memory/table growth limits. At the pinned wasi-testsuite commit, filesystem-dotdot.rs checks that opening ../x.cleanup from a child descriptor fails NotPermitted, and filesystem-rename.rs checks traversal/absolute-path rename failures. These are concrete paths, now recorded as S-25–S-28. They improve repository/test discovery but do not establish behavior of this host, process-tree containment, active markup, or concurrent cleanup.
- **C-02 — Proposed check says new permission requests “block until consent”: accept and amend.** The brief requires users to know when semantics/permissions may change; it does not prescribe a consent gate. The plan and sources do not establish mandatory consent for every new request. Validation now requires disclosure and compliance with an owner-selected policy.
- **C-03 — “Cryptographically bound” is underspecified: accept and amend.** Replace it with host recomputation and comparison of current cache key material against the stored record. A signature or tamper-authentication requirement is separate; no protocol is claimed.
- **C-04 — Platform, formats, active content, network, budgets, retention, consent, and accessibility remain external inputs: retain uncertainty.** The brief does not decide them. Preserve them as owner decisions; do not choose a runtime, claim portability, or turn review advice into product requirements.

## Owner decisions and remaining uncertainty

The owner still needs to set supported operating systems/filesystems; extension languages and permitted attachment families; whether arbitrary active content is necessary; declarative output vocabulary and accessibility expectations; package authentication/update policy; network, worker, and filesystem grants; numeric CPU/memory/byte/process/concurrency budgets; permission notice and consent behavior; stale/history retention and search behavior; and freshness/timeout thresholds. Until implementation and those decisions exist, controls are proposals with conditional guarantees.

Evidence limitations remain visible: some vendor pages are rolling documentation; VS Code Extension Host source S-14 was only a search excerpt and its direct open timed out; the critic did not independently recheck S-04, S-05, S-13, S-14, S-18, or S-22; and the critic did not independently reconfirm the exact inherited 49.0.2 docs.rs pin for S-01/S-02. These limits bound applicability. New test source paths are pinned and inspected, not run. No runtime or framework is selected.
