# Investigator discovery — D-P06

## Scope and method

This discovery uses the released brief alone, before plan release. Attachments, custom blocks, packages, output text, preview bytes, and extension-to-host messages are untrusted. I compared declarative output, WebAssembly components, browser-rendered content, and child-process hosts without selecting a runtime or framework. Primary docs, upstream tests, and public regression records are indexed in sources/README.md; stable source IDs live in source-map.json. No code or tests were run.

## Candidate approaches

- **Declarative result plus host renderer.** An extension returns a bounded versioned data structure (typed text, headings, safe links, media references) and extracted text. The host validates the schema, byte count, nesting, URLs and references, then renders its own components. This limits arbitrary layout and scripting but minimizes markup injection and makes previews work without an executable view. VS Code documents declarative-only contributions that need no executable entry point and can run in its web extension model (S-15). This is a safe default to evaluate, not a runtime choice.

- **WebAssembly component and broker.** WIT worlds can define exactly which imports an extension needs (S-03). A custom interface could provide one opaque attachment handle and one bounded output sink; do not expose a notebook root, note-list API, database, general host object, environment or network. WebAssembly isolates guest memory, but each imported host function is an explicit authority grant and guest return values still need validation (S-03, S-04). In Wasmtime, fuel is off by default, a Store begins with zero fuel, epoch mode needs an explicit deadline, and linear-memory limits apply per memory (S-01, S-02). It is promising as one candidate, not a complete security boundary.

- **Browser renderer.** Prefer host-owned typed UI. If active content is a real requirement, keep it in a separate sandboxed frame/renderer with an opaque origin, no native bridge, restrictive CSP, no popups/forms/navigation/downloads, and a narrow validated message protocol. The HTML Standard describes srcdoc construction and sandbox-origin behavior (S-20, S-21). Electron recommends sandboxing embedded content, warns that webview is not guaranteed to remain available, and characterizes untrusted rendering as a difficult case (S-17, S-18). A sandbox label does not settle message authority or resource consumption.

- **Child process.** A separate process can isolate a crash and allow a watchdog to stop a stuck renderer. It does not automatically remove ambient authority: Electron utility processes have Node APIs, inherit process.env by default, and use the system network context without an explicit session (S-19). Any executable worker needs a clean environment, private working directory, no notebook paths or credentials, network denied by default, a narrow broker, and OS-level restrictions where available. Kill the full worker tree after a deadline; direct-child termination alone is not a sandbox (S-24). If a platform cannot provide the required boundary, disable executable plugins there and retain declarative output.

## Permission, malformed input, budgets, and nested work

Resolve each selected attachment in the host. Give the extension a short-lived, one-job capability bound to the note, attachment digest, extension ID/version/build digest, job ID and expiry. Never let the extension select a notebook or treat a guessed ID/path as authority. Validate every host call and returned value. Deny listing notes, arbitrary file paths, environment, credentials, network, subprocesses and notebook writes by default. Deno illustrates per-resource runtime permissions, but also warns that allow-all removes its sandbox and that some disk-backed APIs can consume storage without direct filesystem permission (S-22).

Cap attachment bytes, compressed and expanded size, parser depth/count, preview nodes, extracted-text bytes, output bytes, host-call count/size, concurrent jobs, per-extension totals, CPU/fuel and wall time. Keep parsing/rendering off the editor loop and kill stuck work. Fuel/epochs are only one layer: Wasmtime 49.0.2 patched a Preview 0 poll operation that did O(n) host work without fuel, a no-stdio host allocation, and an async callback stack-buffer overflow; an outgoing HTTP write-limit issue was fixed in 49.0.1 (S-05 to S-08). These are version/API-conditioned examples, not proof that current patched releases share those bugs. They show that hostcalls, process memory, output streams and update policy need separate review.

Default to no nested workers/processes. The WebAssembly threads proposal separates shared memory/atomics from thread creation and leaves spawn/join to the embedder (S-13). If the host exposes workers, count all descendants against one job-level aggregate CPU, time, memory, file, output and concurrency budget. A nested worker must inherit the exact same attachment-only capability and cannot reset the quota. Feature gates must be explicit; don't infer permissions from a runtime's isolation label.

## Cache, provenance, extension changes, and editing fallback

Proposed cache identity includes attachment content digest and stable locator; extension ID plus exact package/build digest and declared version; host API/schema version; relevant configuration/options and locale; and the parser/extractor version. Store the key beside output digests, time, status, and preview/text bytes. A pathname or timestamp alone is not freshness identity. Publish cache pointer, search record and status transactionally or with an equivalent atomic protocol. SQLite offers transactions and snapshots but allows only one simultaneous writer, so serialize/retry busy updates rather than block editing (S-23).

Keep extracted text as a separate derived search record with explicit type (preview-derived), parent note ID, attachment digest, extension ID/version/build, host API, extraction time and cache key. Label it in search and link back to the attachment. Never merge it into the authored note body or make it appear user-written. Update the cache pointer and its search record together.

On disable/remove/upgrade, stop starting work for the old installation and mark its cached results stale, disabled, or produced by version X. Compute a new key for the new package; never label the old output current. If the renderer is unavailable, keep the original note editable and show the attachment plus a clear disabled/unavailable/version-mismatch reason and compatible-renderer action. A previous preview can appear only as explicitly stale, with producing version and time. On failure/timeout preserve the note, classify the preview as failed, and do not present partial output as current.

## Disposable work and recovery

The host creates a private per-job scratch directory with unpredictable job ID, ownership manifest, quota and no extension-chosen parent. Stop the worker tree before cleanup. Delete only known descendants when a host-owned reference/lease check proves no preview, search row, open viewer or concurrent job uses them; use no-follow/root-identity checks and refuse cleanup on symlinks, open handles, mismatched identity or uncertain references. Shared content-addressed blobs need explicit references/leases and crash-safe reconciliation. A pathname or suffix does not prove ownership. The WASI testsuite removes marked temporary files only beneath each test's own preopened root; the bounded root is the lesson, not the suffix (S-12).

At timeout, record failed/timed-out status, terminate and replace the worker, preserve already-published outputs and remove only unreferenced job scratch. Keep diagnostics free of note contents and extension data. Filesystem semantics vary by platform: WASI documents differences in path case, unlink with open handles, and durability/atomicity with concurrent writers (S-11). Test the exact supported OS/filesystem combinations.

## Regression and test directions

Wasmtime's public advisories and 49.0.2 release notes show concrete failures in fuel accounting, host allocations, host output, filesystem permission composition, and component callback validation (S-05 to S-09). The hardlink advisory applied only to a specific two-preopen permission combination. Issue 13544 documents different absolute and descriptor-relative paths for overlapping WASIp1/WASIp2 preopens, but explicitly says raw capability-oriented WASI behavior is not itself a sandbox escape and the same issue does not apply to raw WASIp3 (S-10). Avoid overlapping or differently privileged preopens and review the whole capability graph.

The WASI test repository gives version-specific fixture paths and root-scoped cleanup patterns, including tests/rust/wasm32-wasip1 and tests/rust/wasm32-wasip3 (S-12). VS Code issue 321901 records a Windows 1.125.0 extension-host regression that blocked Search/Git for seconds to minutes; its milestone was 1.125.1, but the issue body names no fix commit (S-16). Treat it as a failure mode, not proof of resolution.

**Proposed validation, not executed:** use synthetic notes, fake notebooks, and disposable temp roots. Exercise malformed/oversized/recursive inputs; attempts to list/read a second notebook, guess IDs, traverse paths, use symlinks/hardlinks, read environment/network, abuse host IPC, or spawn workers; huge host-return buffers and loops; UI responsiveness under timeout/crash; upgrade/disable/removal and exact-version cache invalidation; derived-text attribution in search; cleanup after cancellation/crash with a shared live artifact, open handle, stale lease, path replacement or symlink race; and supported OS/filesystem differences. No tests/checks ran in this stage.

## Decisions still owned by the product

Preserve these for owner decision unless the released plan resolves them.
