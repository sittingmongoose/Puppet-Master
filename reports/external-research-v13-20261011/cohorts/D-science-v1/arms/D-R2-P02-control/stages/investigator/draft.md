# D-P06 investigator draft

## Scope and evidence boundary

This review covers the original brief: a local notes app uses third-party rich-preview extensions for unfamiliar embedded files and custom blocks, produces previews and searchable extracted text, and must keep note editing usable while handling untrusted extension code, malformed input, cache invalidation, install/upgrade/disable/uninstall changes, and renderer failure. It does not select a runtime or framework, assume access to a real notebook, or claim an implementation was tested. The brief's prohibitions remain binding: no unrestricted notebook access, no returned markup executed with ambient host privileges, no cleanup inferred from a cache/temp pathname alone, and no derived text presented as author-written note text. (B-00)

Evidence IDs and exact URLs, version/commit identities, locators, bounded UTC access windows, operations, governing conditions and applicability are in `source-map.json`; `sources/README.md` is the navigable index. Primary-source documents establish conditional behavior, not a security guarantee for an unbuilt host. In particular, several vendor documents are rolling docs. Wasmtime findings refer to 49.0.2/current API docs as recorded, including its 2026-10-02 release commit; WASI filesystem and testsuite references are pinned commits. The VS Code Extension Host page was only available as a search excerpt and its direct open timed out (S-14), so it is weak comparative evidence. No downloaded code was run and no executable check, product test, real-note test, or sandbox witness was run.

## Exact released-plan dispositions

### 1. “The provisional host provides an extension with an attachment handle, block configuration, and a temporary work directory. The extension returns preview markup and extracted text over a message channel. The host would display the markup in an embedded view and index the text under the note ID. Research whether this boundary adequately limits capability and preserves the requested provenance, including active content and indirect file references.”

**Disposition: revise the boundary; reject direct active-markup display and note-ID-only indexing.** An attachment handle can be a useful capability boundary only if it is a host-mediated, narrowly scoped, revocable reference with explicit rights, lifetime and byte limits. Do not expose a raw notebook path or ambient filesystem handle. The host should resolve the selected attachment/block and provide read-only access to that object; any sibling/indirect references require separately granted handles. A temporary work directory should be newly allocated per invocation, scoped to that invocation, with only the minimum read/write access and no notebook-root preopen. Filesystem capabilities are descriptor-relative in WASI 0.3.1, but traversal/symlink behavior, case folding, deletion of open files, durability and atomicity still have platform-specific conditions (S-11). Wasmtime issue 13544 documents divergent lookup with overlapping preopens; the report expressly does not establish a general sandbox escape (S-10). Avoid overlapping preopens and test the actual host/runtime combination.

Pass block configuration as bounded, schema-validated data, not as executable host state. Treat malformed and oversized blocks, deeply nested structures, invalid encodings, and extension-returned output as hostile. The message channel needs a versioned schema, message-size limits, cancellation, request identity, and explicit error states. WIT Worlds describe imports/exports as the component's external contract; they do not constrain a component's internal behavior or supply the host's security policy (S-03). The host must enforce the contract.

Prefer a declarative preview result (bounded text, links, tables, images with host-resolved attachment references, and a small typed custom-block tree) rendered by host-owned code. This sharply narrows active content and capability transfer. If product requirements demand arbitrary rich executable output, treat it as a separate higher-risk option: isolate it in a genuinely separate origin/process with no host bridge, no Node/host APIs, restrictive network and navigation policy, CSP, and tightly filtered attachment access. Sandboxed `srcdoc` may have an opaque origin, but an unsandboxed `srcdoc` can inherit the creator's origin and `allow-same-origin` lifts an important boundary (S-20, S-21). Electron's guidance supports renderer sandboxing and IPC mediation; Node integration disables sandboxing, and its WebView documentation says WebView is unsupported/not recommended and availability is not guaranteed (S-17, S-18). Sanitizing markup alone does not prove safety. Any markup path needs explicit active-content, URL, CSS/resource-loading, navigation, focus and accessibility decisions.

Index extracted text in a derived-content namespace linked to the note and source object, never as if it were note prose. Persist at least source identity/content digest, block identity, extension package digest and version, extension configuration digest, runtime/policy version, extraction timestamp, and state (current, stale, unavailable, failed). Search results should say that text is extension-derived and identify its source and extension; distinguish quoted/original note text from generated text. Commit extracted text and provenance atomically only after a complete successful extraction. SQLite permits only one simultaneous writer and snapshot readers; busy/conflict behavior must be handled without publishing partial results (S-23). A failed extraction must not silently replace a previous successful result or make partial output appear current.

**Already covered:** the plan recognizes a message boundary, an embedded view, indexing and asks about active content and indirect references. **Missing/correction:** a handle, message channel and view do not by themselves establish least privilege, origin separation, provenance or safe indexing. **Owner decision:** the allowed declarative output vocabulary and whether any arbitrary markup is a product requirement. The safer baseline is declarative host-rendered output; arbitrary active output is an explicitly opted-in exception with stricter controls.

### 2. “A separate process would run each renderer with a timeout. On timeout, the host would kill it, display an error card, and remove its temporary directory. A shared cache would use input digest and extension identifier as its key. The draft assumes process termination establishes cleanup ownership and that matching identifiers preserve preview meaning across upgrades; both assumptions need governing evidence and alternatives.”

**Disposition: retain process separation and visible timeout failure as candidate mechanisms, but revise each guarantee and reject both stated assumptions.** A timeout is necessary for responsiveness, not proof of bounded resource use. Killing a direct child does not itself terminate descendants or nested workers: Rust `Child::kill` describes killing the child process (Unix SIGKILL), not process-tree containment or a sandbox (S-24). Use platform process groups/job objects or an equivalent supervisor, terminate the full invocation tree, reap it, and check for orphans. Apply independent wall-clock, CPU, memory, output-size, open-file, process/thread-count and queue limits. Keep time reserved for the host UI and editing. Bound nested workers explicitly, preferably disable them by default; if permitted, count them against the same invocation budget. A stuck renderer must not block editing, search, or shutdown.

WebAssembly is an alternative for extensions that fit a component ABI, but “Wasm” is not itself the guarantee. Wasmtime fuel consumption is disabled by default; when enabled, a Store begins with zero fuel and the host must set it. Epoch interruption also requires an explicit deadline and trap is the default; large bulk operations can exceed a desired slice. Thread compilation and thread spawning are separate, and some component async/thread functionality is incomplete (S-01). `StoreLimitsBuilder::memory_size` is per memory and defaults to unlimited; tables/counts are separate limits (S-02). Configure and test all needed limits, pin supported versions, and add host-side limits for allocations, I/O and message/output size. Recent 49.0.2 advisories illustrate conditional gaps: Preview 0 `poll_oneoff` could do O(n) host work without fuel (CLI defaults and library opt-in differ; fixed in 49.0.2), a default WASI context without configured stdout/stderr could allow unlimited sink allocation (fixed in 49.0.2), and WASI HTTP had a write-limit check issue in 49.0.0 fixed in 49.0.1 (S-05–S-08). A hardlink/rename permission issue required a specific mix of read-only and higher-rights preopens (S-09). These are version/configuration-specific findings, not proof that all Wasmtime/WASI uses are unsafe or safe. Pin and promptly update a maintained runtime; deny unneeded WASI interfaces, stdio, HTTP, clocks and filesystem rights. The project's security policy explicitly treats guest DoS/user-controlled allocation as security concerns (S-04).

Other options have different limits. A browser worker/web extension can remove Node and child-process APIs, but browser workers may still create workers and use network-facing web facilities; CORS and virtual filesystem semantics remain relevant (S-15). Electron utility processes have Node enabled and, absent a supplied session, system network context; they are not a sandbox by virtue of being separate (S-19). Deno's explicit permission flags are useful examples, but `--allow-all` removes the boundary and some disk-backed APIs may still use disk without ordinary read/write permission (S-22). Do not choose among these until platform, extension compatibility, and a testable policy are specified.

Timeout response should be an error card that leaves the note editable. It must carry retry/disable/report state and avoid stale content being mistaken for a fresh result. A cached preview can be displayed only with a visible stale/unavailable label and only when its source and extension identity are still known; it is not an implicit success.

**Reject:** “process termination establishes cleanup ownership.” The host owns the temp directory lifecycle; a child exit does not prove descendants are gone, files are closed, or the directory is safe to remove. Give every invocation a host-created unique directory and an ownership record. Cleanup should wait for process-tree termination and active readers, use handle/identity-aware operations, avoid following symlinks, and quarantine/retry failures. Under concurrent preview reads, use leases/refcounts or immutable generation directories and atomically switch a host-owned reference; do not recursively remove a directory while a consumer may still use it. Path strings alone are not authority. Filesystem atomicity/durability and unlink-on-open behavior vary by OS/filesystem (S-11). The WASI testsuite demonstrates disposable per-test roots and cleanup markers beneath those roots as a test technique, not a product-wide cleanup guarantee (S-12).

**Reject:** extension identifier plus input digest is not enough to preserve semantics over upgrades. Use a cache key over canonical input bytes/digest, block/config digest, exact extension artifact/package digest (not a mutable display identifier), extension API/manifest version, renderer/runtime build and security-policy version. Include any host-controlled locale/theme/content settings that affect output. Revalidate source identity before returning a cached result. Upgrade, configuration or policy change invalidates/recomputes; disable/uninstall immediately prevents new execution and removes or quarantines associated derived cache/index entries according to a retention policy. If historical preview retention is desired, it must be labeled historical and cannot silently remain searchable as current.

**Already covered:** one renderer process, a timeout, error card, temp directory, and input digest appear in the plan. **Corrections:** process boundary is not resource/process-tree isolation; child kill is not cleanup; extension identifier is not immutable identity. **Alternatives:** typed host rendering, restricted component execution, or a platform process sandbox; these provide different conditional guarantees and costs. **Owner decision:** required cross-platform targets, compatibility level, permitted network/worker APIs, resource budgets, retention policy, and whether rich active markup is mandatory. No source here establishes a single portable sandbox that satisfies all of them.

### 3. “Disabling an extension would hide new previews but retain old cache entries for quick restoration. Unavailable renderers would show their last preview with a badge. The plan needs to examine whether old extracted text should remain searchable and how users learn about potentially changed semantics or permissions.”

**Disposition: revise; retain visible status, make search/retention explicit.** Disabling must prevent new extension execution and mark its existing previews and extracted text disabled/stale. Default search should exclude disabled/stale text or show it only through an explicit user choice with strong derived/stale labeling and source/extension identity. Do not retain cached values indefinitely just for quick restoration: set bounded retention and invalidate on source, config, package, runtime or permission-policy changes. On re-enable, validate all key material and regenerate if it changed. On uninstall, make the old extension result unavailable; decide whether to delete it immediately or retain a labeled historical snapshot for a defined period. Never delete the original attachment or note when cleaning extension-owned data.

An unavailable renderer may show a last preview only if it is cryptographically bound to the current input and exact extension/runtime identity; otherwise show an unavailable card. Explain whether the extension is disabled, missing, upgraded, failed or timed out, and whether the displayed result is stale. Permission changes must be surfaced before running the updated extension, including newly requested file/network/worker capabilities and effects on previously generated content. A badge alone is insufficient if it omits what changed or the source/provenance. VS Code's reported host-unresponsive regression illustrates that an extension host can affect unrelated Search/Git responsiveness, though issue #321901 does not state the eventual fix and is not evidence for this app's behavior (S-16). Keep extraction off the editing critical path, use bounded queues and cancellation, and make host availability status recoverable.

**Already covered:** hiding new previews on disable, retaining cache, last-preview fallback and a badge are explicit. **Corrections:** retaining old extracted text/search results and displaying a last preview need explicit state and identity checks. **Owner decision:** retention duration, whether disabled historical output can be searched, user consent for permission expansions, and UI details. Preserve a usable note editor when extension execution is unavailable.

### 4. “Give retain/revise/reject/unresolved dispositions for capability transfer, output display, indexing, isolation, cache identity, and cleanup. Compare declarative output with richer executable rendering and identify conditional guarantees. Propose checks for a hung nested worker, active markup, stale cache reuse, uninstall, failed extraction, and cleanup during concurrent use. Report any executed checks with their exact sandbox scope; no future host or real notebook is assumed tested.”

**Disposition: satisfy as a research and validation plan; no checks were executed.** The clause dispositions above cover all six named areas. Declarative typed output is the preferred lower-capability baseline and is suitable only if its output vocabulary supports required previews. Richer executable rendering can support arbitrary formats but increases attack surface; a browser frame is appropriate only for web-like content and only with opaque origin, no privileged bridge, strict resource policy and a host-owned attachment proxy. A sandboxed OS process or Wasm component may better fit native/parser code but needs explicit OS/runtime resource, network and filesystem policy. Conditional guarantees depend on exact platform/runtime, API set, version, configuration, host enforcement and adversarial tests; “separate process,” “Wasm,” “sandbox,” “badge,” and “digest” are not standalone proofs. (S-01–S-04, S-11, S-15, S-17–S-22, S-24)

**Proposed synthetic/disposable checks (not run):**

1. **Hung nested worker:** use a test renderer that starts a child/grandchild and blocks. After timeout, verify the whole tree is terminated/reaped, no orphan remains, resources return to budget, an error state appears, and editing/search remain responsive. Test platform supervision separately for every supported OS. For Wasm, exercise fuel and epoch exhaustion, long bulk operations, memory/table limits, host allocations and disabled/limited threading.
2. **Active markup and indirect references:** return script/event-handler markup, `javascript:` and `file:` URLs, remote images/fonts, top navigation attempts and references to unrelated attachment paths. Assert no script/host API executes, no unapproved network or file access occurs, and only approved attachment proxies resolve. Test the actual embedded runtime and its origin/bridge/CSP configuration, including sandbox changes.
3. **Stale cache reuse:** render synthetic content, then vary one field at a time: attachment bytes, block config, extension artifact/version, API version, runtime build and policy. Verify cache miss/recompute, derived-index invalidation and no current label for historical output. Test byte-identical content with different attachment identity if policy requires source-instance binding.
4. **Disable, upgrade, uninstall:** verify disabled extensions cannot execute from a cache hit, new permission requests block until consent, changed artifacts produce new cache identities, uninstall removes or quarantines only extension-owned artifacts, original notes/attachments survive, and stale search hits follow the chosen policy. Verify the user can still open/edit the note without a renderer.
5. **Failed/malformed extraction:** feed truncated, oversized, deeply nested and invalidly encoded synthetic inputs; terminate the renderer mid-stream. Confirm bounded resource use, no partial/current index commit, prior results are either retained with stale state or removed under explicit policy, provenance remains accurate, and errors are actionable.
6. **Concurrent cleanup:** hold a reader on a synthetic preview while replacement, disable or uninstall occurs. Verify generation/lease handling prevents use-after-delete and path reuse; inject symlinks and rename races; confirm cleanup cannot escape the invocation root and retries/quarantines failures. Run on each supported filesystem because unlink, case, rename and durability behavior vary (S-11).

A useful test harness can borrow the WASI testsuite pattern of isolated per-test roots and explicit cleanup markers (S-12), but these proposed tests are not the official suite and are not a claim that the host exists. No executable downloaded source was run. **Executed checks:** none. Thus no sandbox scope can honestly be reported as tested.

## Unresolved decisions and assumptions

The brief does not identify supported operating systems, extension languages, required file types, whether extensions need network, how extension packages are authenticated, resource budgets, user consent UX, output/accessibility requirements, or retention/deletion rules. The owner should decide those after choosing concrete threat and compatibility targets. Until then, guarantees are conditional and the safest default is a bounded declarative protocol, a host-owned renderer, no extension network or arbitrary markup, explicit per-object read handles, atomic derived indexing with provenance, and visible failure/stale states. This is a proposal, not an implementation report. No real notebook or future host was tested.
