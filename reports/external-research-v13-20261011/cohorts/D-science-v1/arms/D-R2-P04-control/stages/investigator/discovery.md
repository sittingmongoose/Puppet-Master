# Independent discovery — investigator stage

## Scope and recommendation

The request is an offline, incremental attachment index for notes containing multilingual text, scanned PDFs, slide exports, and short audio clips with optional transcripts. Search hits must retain the attachment version and best available page, region, or time locator, and must identify whether text came from an embedded/original text layer, OCR, or a supplied transcript. Extraction is fallible and can outlast note edits. The index therefore needs explicit version/freshness state and safe promotion of completed results.

A modest first release can use page/slide/cue chunks rather than a single flattened attachment string. Give each attachment a stable app identifier and each content revision a streaming SHA-256 fingerprint. Store the original attachment reference, version fingerprint, parser/analyzer build identifiers, extraction status, and chunks. A chunk carries modality, raw extracted text, source locator, location quality, and an extraction-run identifier. Keep normalization/index text separate from display text and retain offsets only where the extractor provides a defensible mapping. Do not make path, modified time, or OCR text the identity of the source version.

For retrieval, compare two local lexical choices. SQLite FTS5 is a strong modest default if the product already has SQLite-backed metadata: its full-text rows and attachment-version state can then be replaced in one SQLite transaction. FTS5 offers the Unicode 6.1-based unicode61 tokenizer and a trigram mode for substring search. Its defaults need explicit review: Latin diacritic folding is not universal transliteration, the Porter stemmer is for English, and trigram full-text terms shorter than three Unicode characters do not match. CJK word segmentation and relevance are not solved merely by selecting unicode61. Tantivy is a Rust-native BM25 search engine with per-field tokenizer selection, configurable/custom analyzers, and commit/rollback behavior. It is a good alternative if a separate index fits better, but metadata and search-index publication then need a generation/manifest protocol so a failed or stale job cannot mark an unpublished version current. Its open mixed-language issue and customizable tokenizer design argue for script-specific fixtures, not a blanket multilingual claim. Lindera with Tantivy is a candidate for morphological Japanese/Korean/Chinese tokenization; dictionary payload, license review, index analyzer compatibility, and dictionary upgrades become deployment/versioning obligations. Character n-grams or trigram substring search can supplement languages without spaces, with the tradeoff of broader matches and more index data. Semantic/vector retrieval is an optional later experiment: it adds local model/runtime and relevance calibration needs and cannot replace exact lexical matching or source provenance.

## Extraction candidates and limits

- Plain text and supported UTF-8 note exports can be normalized conservatively and chunked at paragraphs, preserving source offsets when the decoder permits them. Keep original Unicode text available; query normalization must match index normalization.
- For digital PDFs, lopdf 0.45.0 exposes page text and a per-page decompression limit. Use bounded per-page extraction and label the source as embedded PDF text. Page is defensible; this path does not justify inventing a region/line locator. Empty page text is not proof that the PDF is blank: scanned pages need a separate explicit OCR path.
- A local Tesseract path can rasterize only eligible pages and request TSV/hOCR output for text and OCR word/page boxes. Mark every recognized chunk as OCR-derived and never describe confidence as accuracy. Map OCR pixel boxes to displayed PDF coordinates only after exercising rotation, crop, scale, and page-origin fixtures; until then show page-only. Preserve the original PDF and offer a control to open it at the page, with region jump only when mapping is validated. Do not depend on OCRmyPDF sidecar text as the complete corpus for mixed PDFs: its documented sidecar omits pages that already have text. Existing issues show both sidecar regressions and that output-format bugs can occur, so pin a tested engine version and inspect output fixtures.
- A slide export that is a PDF follows the PDF path, with slide/page number and page-only location. For native PPTX, OOXML is a ZIP package governed by ECMA-376. A bounded reader can traverse relationships and read supported slide text runs with namespace-aware streaming XML; record slide number and shape identifier/name, not a visual rectangle unless transform math is validated. This is a useful alternative to requiring a headless office conversion dependency, but it is a deliberate format implementation, not a trivial XML grep. Initial exclusions should include unsupported embedded objects, chart/table text until tested, notes/comments unless expressly in scope, password-protected or malformed packages, and macros. Never execute package content. Cap archive entries, expanded bytes, parse time, and memory; read only expected parts and do not extract arbitrary entry paths. Office-to-PDF conversion is another option where the runtime is already qualified, but it adds an external executable and conversion/layout behavior to pin and test.
- For audio, leave transcription optional. Index a user-provided VTT/SRT transcript as supplied transcript text; VTT cue starts/ends are useful media-time locations when valid. If there is no transcript, retain searchable attachment metadata only and open the original clip from its beginning (or a known time only when supplied). Automatic speech recognition can be proposed as a later explicit opt-in and is not a completion requirement.

## Version, freshness, and jobs

On edit, rename, or replacement, resolve attachment identity separately from path. A rename with unchanged bytes can keep the same version fingerprint while refreshing the display path; replacement creates a new fingerprint. On a note edit, enqueue a bounded job with the target fingerprint and extraction-profile digest. Coalesce queued work to the newest version of each attachment; bound concurrency, per-file/expanded size, pages, wall time, and temporary storage; surface queued/running/progress/failed/cancelled/partial states and actionable stage errors. Cancellation must invalidate that job's publication token.

Write extraction output to an isolated staging generation. Before promotion, re-stat/re-hash the source or compare its current revision token and confirm the job was not cancelled and still targets the newest revision. Then atomically replace that attachment's indexed chunks and version/status in the metadata transaction (SQLite design), or commit a complete Tantivy generation and atomically advance the manifest together with metadata. Never delete the prior generation before the new parse is complete. If replacement extraction fails or is cancelled, prior chunks may be retained for recovery, but they must be marked stale against the current attachment fingerprint and hidden from normal current-result lists or visibly labeled as the previous version. Do not label them current. Tombstone/remove chunks on attachment deletion in the same publication operation; if cleanup is asynchronous, filter tombstones at query time so deleted content cannot quietly appear. Partial success records page/slide/cue coverage and missing-item reasons rather than pretending a complete extraction.

Every hit should show source name, captured version/short fingerprint, modality badge, exactness, and available page/region/time. Opening the source must resolve to the exact version where possible, verify it still matches, and then seek to a supported locator; otherwise open the attachment with an honest unknown-location message. The hit snippet is derived evidence. Keep an obvious open-original action and never present OCR as a faithful quotation from pixels.

## Alternatives and validation plan

The candidate path is: retain source bytes locally; detect format by signature plus policy (not extension alone); run bounded, offline parser adapters; normalize and chunk while preserving modality/locator; publish a complete attachment version; query lexical index first and add optional analyzer/substring lanes after fixtures. SQLite FTS5 is favored when it can share metadata transactions; Tantivy is favored when engine behavior/scale or Rust deployment considerations outweigh cross-store publication complexity. Direct PPTX parsing competes with a qualified office conversion, and page-only PDF text extraction competes with a positioned-text backend. Optional OCR should be an adapter with explicit language packs and timeouts, not a required transcription service.

Proposed executed-check candidates (none have been run in this research stage): synthetic text/PDF/PPTX/VTT fixtures for modality, version fingerprint, page/slide/time locator, OCR pixel box mapping, corrupt/password-protected inputs, ZIP expansion caps, parser timeout/cancellation, and replace/delete atomicity; public OCR fixtures for engine regression coverage. Simulate editing the note while an older extraction runs, cancel it, fail after some pages, rename without byte changes, replace bytes at the same path, and delete the attachment. Assert that no stale or deleted result is presented as current/searchable, the last good generation is recoverable but explicitly stale, and source opening never silently lands on a different version. Separately propose multilingual relevance tests over public/synthetic English, accented Latin, Arabic, CJK, and mixed-script fixtures; OCR-quality evaluation and future notebook end-to-end integration are also proposals only. Do not claim relevance, recognition quality, or implementation checks executed without an available corpus/runtime.

## Open owner decisions

1. Which containers/formats belong in v1: plain text, PDF, VTT/SRT, and whether native PPTX text is required immediately or PDF slide exports suffice?
2. Is OCR an opt-in local dependency in v1, with which language packs and supported operating systems, or a later phase?
3. Which storage/index arrangement matches the product: FTS5 in the metadata database, or Tantivy plus a generation manifest? Confirm actual embedded FTS5 availability before committing to the former.
4. Which languages get dedicated analyzers/dictionaries in v1, and who accepts dictionary payload/license and migration costs?
5. When the current attachment is unreadable, should stale previous-version hits be suppressed by default with a separate recovery view? Recommended: yes.
6. What maximum file size, expanded archive size, PDF pages, OCR time, and background concurrency fit the product's privacy/performance envelope?

No parser, search engine, OCR product, automatic transcription, private corpus, or implementation runtime was selected or tested by this discovery.
