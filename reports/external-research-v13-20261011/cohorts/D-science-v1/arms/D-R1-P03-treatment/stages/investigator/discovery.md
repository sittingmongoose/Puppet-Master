# Independent discovery — D-P03 backup and restore

## Scope and research result

The brief selects no archive format, persistence engine, or crypto package. The design therefore needs an application-owned consistency boundary and a versioned interchange contract, with format/engine choices gated on compatibility tests. The useful separation is: (1) create a consistent point-in-time workspace snapshot, (2) package and verify it, (3) explain a proposed restore without writes, and (4) apply only after explicit choices and validation. A valid container, verified extraction, and a workspace the application can open and use are distinct outcomes.

## Findings to carry into the proposal

### Capture and archive completeness

- Enumerate records, preferences, and attachment objects from one coordinated snapshot/generation. Record archive-format version, app data/schema version, generation ID/time, stable record and attachment identities, sizes, content hashes, and a complete included/excluded inventory with a reason per omission. Hash raw bytes, not names. A backup that skipped unreadable items may be retained as an incomplete diagnostic artifact, but it must not be labeled or promoted as current complete protection. Restic's documented behavior is a useful warning: it can still create a snapshot when source reads fail, while reporting the errors; the application must elevate those errors into explicit completeness state (S07).
- A file archive's CRC/header test is useful for accidental damage, not proof that all intended workspace objects were selected or that the workspace is valid. Verify each member against a manifest (size and SHA-256); when encryption is enabled, authenticate/decrypt the entire outer envelope before treating the plaintext as trusted. The CRC/SHA distinction is an inference from ZIP CRC behavior and NIST's hash-integrity specification (S04, S10).
- Write to a unique temporary file on the destination volume. Close/finalize the container, flush/sync where supported, reopen and verify all members, validate inventory totals, and only then publish it under a completed name. Cancellation, read errors, disk-full, interrupted output, failed verification, or missing members must leave the last verified archive intact and must never set a “current/complete” status. Sync guarantees and removable-media behavior require platform testing; a rename cannot cross a mount and replacement semantics vary by platform (S08).
- Candidate package choices: a conservative ZIP/ZIP64 subset (portable tooling, directory/central-directory format, CRC, common compression) or tar plus a separately selected compressor (stream-friendly, but extraction and metadata policy still need explicit rules). Keep the app manifest independent of container-specific metadata. Avoid choosing an archive library before validating duplicate-name, UTF-8, path, symlink, file-size, ZIP64, and interruption behavior. Python's documentation specifically leaves path sanitization to callers of `zipfile.Path`, and a Rust ZIP extraction advisory shows that even an API described as sanitizing paths had a symlink-order escape until a fixed release (S04, S05).

### Engine snapshot and migrations

- If SQLite is eventually selected, a raw copy of a live database file is not a safe snapshot in WAL mode: committed state can still reside in `-wal`; the official docs say the WAL is persistent state, and separating it from the database can lose committed transactions or corrupt the copy. Use SQLite's Online Backup API or `VACUUM INTO`, or quiesce/close the application and apply an explicitly tested whole-file set strategy (S01, S02). The backup API creates a point-in-time database snapshot while taking source read locks only for individual steps; `BUSY`/`LOCKED` can be retried, while I/O, no-memory, and read-only errors are fatal and require finishing/abandoning the operation (S01). Do not imply that this SQLite-specific strategy applies to an unselected engine.
- A schema number must be owned by the application and distinct from archive-format version. SQLite `PRAGMA user_version` is an app-owned integer; SQLite itself does not interpret it. Migration steps should be ordered and tested from each supported old schema on an isolated staging copy; a newer unknown schema is a preview blocker, never a guessed downgrade. SQLite documents behavioral compatibility changes to `ALTER TABLE` across 3.25.0/3.26.0 and warns that hand-editing schema can corrupt a DB, illustrating why engine version and migration history matter (S03).
- SQLite `integrity_check` checks low-level database structure and selected constraints but does not detect foreign-key violations; `foreign_key_check` is a separate check. Foreign-key enforcement has historically defaulted OFF, with compile-time override and possible future default change, so an implementation must set/check the behavior explicitly. Neither engine check proves that attachment files exist or that application-level invariants hold (S03).
- SQLite's current WAL page records a WAL-reset corruption bug found 2026-03-03, likely affecting versions 3.7.0 through 3.51.2 under a narrow condition: at least two connections in separate threads/processes open the same WAL database and write/checkpoint concurrently. SQLite says fixed in 3.51.3+, with 3.44.6 and 3.50.7 backports (S02). This is a release/applicability finding, not evidence that a backup operation itself triggers the bug; qualify the bundled engine and test concurrent access if SQLite is selected.

### Identity, relationships, and merge preview

- Treat records and attachment objects as separately identified entities. Stable record IDs and attachment IDs must survive archive round trips; attachment filenames are display metadata, not keys. Two attachment IDs with the same basename but different hashes are two different objects. Store payloads under safe generated member IDs or content-addressed names, and retain the original filename separately. A record-to-attachment reference is resolved by ID, never by basename.
- Preflight every archive member and every referenced attachment. A record whose attachment is absent remains a visible broken reference in preview and must not silently become a record with a plausible but wrong file. Inventory exclusions and missing references should be separately counted and explained.
- Preview is read-only and compares a fully verified, migrated staging representation with the live workspace. Per-record outcomes should include create, identical/no-op, update candidate, conflicting local record, unsupported/newer schema, missing attachment, filename collision with different bytes, and invalid/corrupt data. Show exact identities and relevant values, not only aggregate counts. For each conflict offer an explicit policy such as keep live, replace with archived version, or import a second entity with a new ID and remapped references; do not decide based on matching titles or filenames. The user sees the full planned effect before apply.

### Restore and atomicity

- New empty workspace: decrypt/verify, safely extract into a fresh staging directory, migrate there, validate record/reference/media invariants, then run an app-level open/read smoke check before offering promotion. Keep the current live workspace untouched until the staged replacement is verified; preserve a rollback copy during promotion.
- Existing workspace merge: prepare a candidate copy and apply preview decisions to that copy; do not mutate live files while previewing. Apply only after confirmation and a workspace quiescence/lock boundary. A database transaction does not atomically commit separately stored attachments/preferences; use a transaction journal or staged-directory swap with startup recovery, and retain the pre-restore workspace. Treat directory replacement as platform-specific and test interrupted transitions; Rust's standard rename docs distinguish Unix and Windows cases and reject cross-mount moves (S08).
- Extraction must reject absolute paths, `..`, drive/UNC paths, symlink/hardlink escapes, duplicate normalized paths, and destination paths that resolve outside staging. Default to not restoring symlinks or special files. Also enforce size/count limits and detect case-folding/normalization collisions for cross-platform archives. This is defense against archive content, including removable-media content (S04, S05).

### Encryption and whole versus incremental

- If passphrase protection is selected, encrypt the complete finalized container so filenames/manifest are not exposed, and use a maintained authenticated-encryption format/library. Age format v1.0.0 specifies passphrase wrapping with scrypt and ChaCha20-Poly1305; payload uses authenticated 64 KiB chunks and requires a valid final chunk. Its passphrase stanza must be the only recipient stanza, so passphrase-only encryption does not silently create a second recovery key path (S06). A forgotten passphrase has no provider-side recovery in this design; warn before creation, offer a generated high-entropy phrase, allow a separate owner-approved recovery design only if it is explicitly chosen/tested, and never promise recovery merely because an archive is encrypted. Test wrong password, truncation, corruption, and successful decrypt. Do not put secrets or the passphrase in logs or the manifest.
- ZIP CRC and SHA-256 manifest hashes detect member damage against the recorded values; they do not authenticate a mutable plaintext manifest against a deliberate attacker. Authenticated encryption protects the ciphertext envelope, while provenance/authenticity for an unencrypted archive would need a separately designed signature or trusted digest channel. Do not conflate either with application validity (S04, S06, S10).
- Whole-workspace self-contained archives are easiest to copy on removable media and restore independently, and give the simplest retention/verification story, at the cost of repeated storage and write time. A chain of deltas reduces bytes but adds a parent dependency, ordering, missing-base/corruption modes, and retention constraints; every required parent must travel with the selected restore point or be present in a verified local repository. Restic 0.19.1 demonstrates chunk deduplication and snapshots, but its repository is a directory with repository metadata/keys, and checking structure is distinct from `--read-data` full data verification (S07). It is a useful alternative to study, not an automatic fit: it does not supply this app's atomic logical snapshot, domain-aware conflict preview, or schema migration. Propose full self-contained snapshots for the first portable interchange; revisit incremental/content-addressed storage only after measured archive size and restore-time needs justify the added dependency graph.

## Proposed validation, not executed checks

No synthetic archive, storage, migration, or user-data checks were run during discovery. Proposed tests include: deterministic inventories and stable IDs; same-name/different-byte attachments; dangling references; excluded/unreadable members; interrupted/cancelled archive creation at each write/finalize/rename boundary; full disk and removable-device error; archive truncation, header/CRC/hash mismatch, wrong password, tampered ciphertext, and missing final authentication chunk; malicious absolute/parent/symlink/duplicate/case-colliding member names; ZIP64 and long Unicode names; supported old-to-current migrations, migration rollback/crash, and unknown future schema; SQLite online snapshot under concurrent readers/writers if applicable, with integrity and FK checks separately; new-workspace restore and existing-workspace merge preview for all conflict policies; crash at each multi-file commit step with restart recovery; and a final app-open/use check. Report each executed check and its exact fixture scope separately from this proposal.
