# Independent discovery — D-P07 recurring duty roster

**Stage:** investigator · **Run:** D-R2-P03-treatment · **Brief reviewed:** `inputs/brief.md` only, before plan release. **Exact plan:** not read at this stage.

## Findings and candidate direction

The problem is not merely merging rows. It combines disconnected edits with cross-assignment constraints, worker intent, a privileged approval, and a public version that downstream records must continue to identify. A sync engine can move and reconcile state; it cannot decide what an overlap, qualification, dependency, stale swap, or approval means for this center. Those policies need explicit owners and a server-side enforcement point.

A promising candidate to evaluate is a local SQLite database and durable ordered mutation queue paired with a server-authoritative backend. PowerSync is one maintained example: its client queues CRUD, its developer-owned backend decides how to apply/reject writes, and simple handlers commonly produce per-field last-write-wins and delete-wins semantics. Requests may be repeated, so the backend must be idempotent. This separation can fit a roster only if assignment and publication operations are validated by app logic before durable acceptance; the default merge behavior is unsafe for constrained decisions. PowerSync is not selected: center platform, preferred hosting, budget, identity system, backend and offline retention requirements are unknown. (S01–S08)

Use normalized relational records for workers, qualifications, shifts, assignment proposals, dependency rules and published snapshots if the chosen source database supports their required constraints. Record mutations as commands/events with operation UUID, actor, base draft/publication version, and intent. Keep ordinary descriptive fields separable from assignment decisions. A coordinator's unrelated changes to a note may be merged field-by-field only if the fields are actually independent and neither changes a protected business decision. Same-field edits should preserve both proposed values and identify stale bases. Never use device clocks as the decisive conflict order: clock skew can manufacture false results; sequence/version checks managed by the server are safer for critical data. (S02, S09, S11)

Treat constrained assignments as domain commands, not independent columns. An assignment/swap command should validate the relevant current schedule atomically: user is permitted to propose it; worker qualification is valid for the applicable duty and time; the worker is not double-booked under the center's overlap rule; required shifts/roles remain covered; and the referenced base version has not changed in a way that makes the request stale. On a violation, retain the proposed command and current state as a reviewable conflict; do not overwrite either version. If PostgreSQL is selected, exclusion constraints can reject interval overlap, while ordinary `CHECK` constraints cannot safely enforce cross-row rules. Multi-row rules need an appropriate exclusion/foreign-key constraint, a transactionally serialized server validator, or serializable transactions with retry after serialization failure. These are candidate implementation mechanisms, not an assumption that all domain rules are known. (S09, S11)

## Proposed data and workflow boundaries

- Keep **working draft**, **pending offline proposals**, **human-resolution conflicts**, **approval records**, and **published snapshots** distinct. A pending local edit can be visible and useful, but is labeled pending until server acceptance. Publishing is an explicit supervisor action on a specific immutable draft revision. Any later draft change creates a new revision and makes approval of the older revision ineligible for the new one.
- A proposal should carry the schedule version it was based on. A worker swap request stores that publication/version ID; if the relevant shift changed after the request, the server returns a stale-version conflict instead of silently applying the request to a different roster.
- Use server-authoritative commands with authenticated actor and explicit proposal/publish permissions. Sync filters/JWT claims can limit what records reach a client, but they do not authorize a client to publish. If PostgreSQL RLS is used, enable it for every sensitive table, define per-command policies and least-privilege roles, and test with the real app role: RLS is off by default and table owners/superusers normally bypass it. Keep supervisor approval in a server-owned append-only record tied to the exact draft revision/content hash; an offline coordinator patch cannot set or replace it. (S08, S10)
- On approval/publish, write an immutable `publication_id`/version with snapshot contents or a stable snapshot reference, `supersedes_publication_id`, approved actor/time, and a content hash. Atomically move the current-publication pointer and create notification/export outbox items referring to that version. Each request and export retains its `publication_id`; consumers can show “request concerns version …” and reproduce the same schedule later. External delivery is outside the database transaction: record attempts and provider IDs, use idempotency keys if supported, and never claim a sent notification can be recalled. Republish by sending a correction/superseding version that names the old and new IDs.
- Generate the pre-republish explanation from a deterministic diff between the current published snapshot and the proposed snapshot: added/removed/moved assignment, qualification/dependency validation outcome, resolved conflict IDs, and who/when changed it. This is explanatory evidence, not the source of approval.
- Persist draft mutations and their upload state locally in one SQLite transaction. Surface pending, accepted/synced, rejected/needs-human-review and recovery states separately. SQLite has atomic commit and WAL recovery mechanisms, but durability depends on the platform/filesystem honoring flush and locking; WAL requires processes on the same host, supports only one writer, and must not be put on a network filesystem. SQLite foreign keys are disabled by default for each connection, so explicitly enable and check them. A restore should recover accepted server state first and retain/export unresolved local-only work for user reconciliation rather than silently discarding it. Validate both `integrity_check` and `foreign_key_check`; `integrity_check` alone does not check foreign-key errors. Local backup/restore behavior and unsynced-data retention remain platform-specific requirements. (S12–S16)

## Repository callers and repair history

The official PowerSync JS monorepo includes multi-client, backend and Yjs demos and identifies package test suites (some use Playwright). Its Node demo connector is a concrete `uploadData` caller: it extracts one queued CRUD transaction, posts a batch to an app endpoint, and only completes the queued transaction after an OK response; exceptions are rethrown. Treat that as an example of the integration seam, not evidence that its demo backend implements roster rules or atomic business validation. (S03–S05)

Useful repair history makes transaction semantics a qualification item. PowerSync JS issue #48 reports a `writeTransaction()` with two inserts surfacing as two single-operation upload transactions and an undefined `transactionId`; a maintainer said it was fixed in the then-current React Native 1.2.1/Web 0.2.1 packages. The official JS/Web release history later lists the missing `transactionId` fix in Web 0.2.1. The PowerSync Kotlin changelog separately records a fix for `getNextCrudTransaction()` returning only one item (beta 31), plus connection/offline-upload timing fixes. These are historical version-specific fixes, not claims that the current client has the defect; they justify testing the exact deployed SDK and ensuring one roster swap's server-side transaction boundary is explicit. The Web release history also records a v2.4.0 OPFS WAL regression fixed in v2.4.1; current Web release observed here is v2.4.2 (2026-10-01). (S03, S06–S07)

## Proposed validation only; none executed

No downloaded code was run; no real roster, account, notification service, or deployment was touched. The following are test proposals, not results:

1. **Two-client disjoint edit:** offline coordinators change independent descriptive fields against one base version; preserve both and audit them. Then change the same field from that base; retain the losing proposal and show its current/base values. Repeat with device clocks skewed.
2. **Assignment collision:** two clients assign one worker to overlapping shifts and accept distinct swaps against the same shift while offline. Reconnect in both orders and with duplicate/retried delivery. Every server-accepted state remains valid; duplicate operation IDs do not duplicate effects; every rejected proposal stays visible with a reason and source version.
3. **Rule boundary:** missing/expired qualification, shift prerequisite changed offline, and center-defined overlap/time-zone boundary. Verify proposals remain local/pending until a server policy result; unknown center policy is explicitly configured/approved before the test becomes an acceptance criterion.
4. **Approval/publish:** unauthorized worker/coordinator publish attempts; stale approval after draft mutation; competing publish attempts. The prior approval and published snapshot are immutable; only an authorized supervisor can publish exactly the approved revision.
5. **Version consumers:** worker creates a swap against publication N, then N+1 is published. The request/export still identifies N and displays the mismatch; a correction references N and N+1. Simulate a provider timeout after database commit and duplicate delivery; records remain version-pinned and no recall is claimed.
6. **Local recovery and sync:** terminate/restart during local transaction, offline queueing, upload, server commit before client acknowledgement, and snapshot checkpoint. Reopen/retry without lost accepted edits or duplicate effects; run integrity and FK checks; demonstrate an explicit user path for unsynced proposals if local store restore is needed.
7. **SDK integration regression:** run the chosen client SDK's transaction-grouping and upload retry tests, adapting the #48 reproduction with a multi-row swap. Verify queuing/completion is not confused with server acceptance or publication.
