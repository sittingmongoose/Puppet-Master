## Clause-by-clause dispositions

### Released plan paragraph 1: records, field timestamps, post-merge rule checks

| Plan clause | Disposition | Evidence-backed finding and proposed change |
|---|---|---|
| “The draft stores shifts, assignments, and swap requests as records with stable IDs.” | **Keep, extend.** | Stable IDs support reference, retry and audit, but are not enough to represent intent. Give every offline command/request its own idempotency UUID, actor, operation kind, base publication/draft revision, affected shift/assignment IDs and lifecycle status. Represent multi-record swaps as one command with a server transaction boundary. Keep separate working draft, conflict proposal, approval and immutable published snapshot. PowerSync's queue exposes CRUD operations and per-client operation IDs; the app backend still owns how to apply them. (S01–S02) |
| “Clients would synchronize field changes and merge concurrent edits using per-field timestamps.” | **Reject as the general roster merge policy; optional only for safe descriptive fields.** | Per-field merging can preserve edits to genuinely independent fields such as a draft note, but it does not preserve the meaning of an assignment decision or prove a schedule valid. Same-field LWW discards one intent. Client timestamps can be skewed; PowerSync's own examples warn of false conflicts and recommend server-managed sequence/version checks for critical data. Adopt field patches for explicitly independent, non-protected fields only; use expected-version commands and visible conflicts for assignments, swaps, approval data and any field used by a roster rule. Keep user-entered timestamps as audit metadata, not causal authority. (S02) |
| “A rule checker would run after merge and mark overlapping assignments for coordinator review.” | **Reject the post-merge-only timing; revise to validate before server acceptance and again at publication.** | Once an invalid combined state has been written as accepted data, a later warning does not undo the interval in which it can be read, exported, approved or used. Keep offline changes as `pending`; run the authenticated server validator against the current candidate state inside the same transaction that accepts the assignment/swap; atomically reject/record an unresolved conflict if stale or invalid. Revalidate the entire publish candidate before supervisor approval/publication. PostgreSQL exclusion constraints can enforce suitable interval overlap; ordinary `CHECK` constraints cannot guarantee cross-row/table rules. Qualification validity and shift dependencies need a transactionally consistent rule check, constraints/triggers where appropriate, or serializable transactions with retry. (S01–S02, S09, S11) |
| “examine whether this preserves intent for multi-record swaps, qualifications, and dependent duties, or whether transaction and decision boundaries need a different model.” | **Different boundaries required.** | A swap that changes two assignments must be one domain command, not two separately merged field patches. Attach the request to the publication and affected assignment revisions the worker saw. Validate both sides and their qualification/dependency implications as one all-or-nothing server action. If another command changed a touched record or invariant, keep both proposals and ask for a coordinator decision/rebase. A rule checker after a row-wise merge cannot restore the discarded causal intent. (S02, S09, S11) |

### Released plan paragraph 2: approval, snapshot, offline edits

| Plan clause | Disposition | Evidence-backed finding and proposed change |
|---|---|---|
| “Approval would be a boolean on the roster plus the approving person's identifier.” | **Reject blanket boolean; revise to an immutable, version-scoped approval event.** | Store approval as a server-owned record with authenticated supervisor identity, time, exact draft revision/content hash, and status. Do not accept approval identity or state from a generic client field update. A later schedule-affecting edit produces a new revision and cannot inherit approval silently. This makes who approved what reviewable and prevents an offline coordinator edit from overwriting a supervisor's decision. Authentication/sync scoping and write authorization are separate concerns: JWT-filtered Sync Streams do not authorize a publish command; PostgreSQL RLS is off by default and table owners normally bypass it. (S08, S10) |
| “Publishing would copy the current records into a versioned snapshot” | **Keep, strengthen.** | Build a stable snapshot of the exact candidate, including a `publication_id`, monotonic or otherwise unique version, content hash, `supersedes_publication_id`, and approval reference. Make the snapshot immutable. In one server transaction, verify the supervisor has publish permission and the approval still matches the candidate, insert the snapshot, update the current-publication pointer, and add downstream outbox records. Do not publish local/offline state merely because it reconnects. (S09–S11) |
| “and send downstream consumers its version number.” | **Keep, make the version a required foreign reference in every consumer record.** | Swap requests, notification jobs, exports and delivery records should carry the immutable publication ID and, where relevant, a stable payload hash. That allows reproducing which schedule a worker saw and which data an export contained. Generate a concise diff from previous published snapshot to new snapshot before the new publish confirmation. (S01, S09–S11) |
| “Offline edits would remain local until reconnecting, at which point they would update the shared draft.” | **Revise.** | Reconnect should submit pending commands to the backend for authorization, base-version and roster-rule checks. Only accepted commands update the authoritative draft; stale/invalid ones stay visible as conflict proposals. Show local/pending separately from accepted/synced. Never auto-publish as a side effect of sync. PowerSync explicitly leaves conflict semantics to the application backend; repeat deliveries require idempotent handling. (S01–S02) |
| “The draft assumes approval can survive changes to unrelated fields; determine how approval scope and invalidation should be represented instead of accepting a blanket boolean.” | **Replace implicit survival with explicit approval scope; owner decision remains on the protected projection.** | Default to approval of the exact roster-affecting revision/hash. Any shift, assignment, swap resolution, qualification result, dependency result or publication content change requires reapproval. If the center wants metadata-only changes not to invalidate approval, define that projection and test it; do not infer from “unrelated” or implement a blanket boolean. Require an approved revision ID to equal the publication candidate ID at publish time. (S09–S11) |

### Released plan paragraph 3: worker requests, stale drafts, cancellation and notifications

| Plan clause | Disposition | Evidence-backed finding and proposed change |
|---|---|---|
| “Swap requests would refer to shift IDs and the published version the worker viewed.” | **Keep, extend.** | Store publication ID, affected shift ID(s), relevant assignment revision(s), requester, request ID, and lifecycle state. This records which roster the request concerned and supports stable re-display. Add an explicit cancellation/supersession event rather than deleting the request. (S01, S09) |
| “If the current draft differs, the coordinator could still accept the request after seeing a warning.” | **Reject warning-only acceptance.** | A warning does not rebase intent. The coordinator may explicitly rebase the proposal against the current draft after seeing affected old/current assignments and all resulting rule checks; record old and new base versions and who rebased. If an affected shift changed, if a second swap already consumed the opening, or a qualification/dependency changed, leave it unresolved until the coordinator chooses a new proposal. If only unrelated data changed, acceptance can be allowed only under an owner-approved rule defining that boundary and after server validation. (S02, S09–S11, S18) |
| “Compare this with explicit rebasing, staged proposals, or other intent-preserving approaches.” | **Prefer staged proposal plus explicit rebase.** | Preserve the worker's original proposal and base publication. A coordinator accepts it only as a newly validated command on the current draft, not as an implicit mutation of the old request. Show a diff and record the decision. This is safer than choosing LWW or treating the latest local edit as authority. A document-revision system such as CouchDB can preserve conflict leaves but still exposes a deterministic winner by default and leaves application merging to the client; it does not remove this roster-specific decision. (S02, S18–S19) |
| “how a cancelled or superseded request interacts with delayed clients” | **Add explicit terminal states and idempotent handling.** | Preserve request ID and tombstone/event for `cancelled`, `superseded`, `accepted`, `rejected`, or `needs_review`. A delayed retry of a terminal request must return its recorded terminal outcome and must not recreate the request or assign the shift. If an explicit rebase is offered, it creates a new command ID linked to the old one. Server-issued ordering/version transitions are authoritative; device clocks are not. (S01–S02, S09) |
| “and already sent notifications.” | **Add immutable notification intent and honest delivery state.** | In the publication transaction, add an outbox item keyed to publication ID, recipient and notification type. An external provider may deliver after the DB commit and may retry; record `queued/sent/failed` and provider reference with an idempotency key if supported. A sent notification cannot be recalled. If a schedule is superseded, send a correction/new notification that names the old and new publication IDs; do not rewrite the old delivery record or imply recall. If a notification is still queued, define whether it should be cancelled or replaced before dispatch. (S09–S11) |

### Released plan paragraph 4: required decision areas and evidence-backed output

| Area requested by plan | Disposition | Proposed result |
|---|---|---|
| Merge | **Answer with scoped strategies.** | Independent descriptive patches may merge when their semantics are independent. Same-field content may be retained as a conflict for review. Assignment/swap/approval operations use server-managed versions, idempotent domain commands, atomic transaction boundaries, and explicit conflict/rebase instead of timestamps or generic fieldwise merge. CRDTs such as Automerge may be evaluated for free-form notes only; their deterministic conflict resolution does not ensure roster invariants. (S01–S02, S17) |
| Rule-check timing | **Move checks before acceptance and before publication.** | Local client can show provisional feedback only. Server validates identity/permission, base version, qualification, overlap and dependency rules atomically against authoritative current state; publication repeats the checks on the exact snapshot candidate. Invalid or stale inputs remain proposals with reasons. PostgreSQL exclusion constraints and serializable transactions are conditional implementation options, not proof that the app's rules are complete. (S09–S11) |
| Approval | **Exact revision approval.** | Supervisor approval is a server-authenticated event for a defined schedule projection/version. It cannot be overwritten by coordinator sync. Publication is rejected if candidate ID/hash differs from approved ID/hash. Owner must define whether metadata-only edits affect the protected projection. (S08–S10) |
| Publication | **Immutable snapshot and atomic pointer/outbox.** | Publish immutable content and approval reference; advance current version and create notification/export work together in one database transaction. Diffs compare immutable versions. Offline reconnect never publishes on its own. (S09–S11) |
| Consumer references | **Pin all reads, requests and delivery to publication ID.** | Worker swap requests, notification payloads/delivery records, schedule exports and audit records carry a version ID. A later publication creates a correction/supersession relationship rather than changing historical content. External delivery remains separately acknowledged and non-recallable. (S01, S09–S11) |

## Alternatives and conditions

1. **PowerSync candidate:** local SQLite plus ordered CRUD upload queue and application-owned backend. Good fit to investigate for a local-first relational UI when the platform is supported and the team accepts owning server validation/conflict handling. Sync Streams are generally available in the inspected release notes; the announcement lists service v1.20+ and current SDK/Rust sync-client requirements. The exact supported platform, release family, hosting/service tier, and authorization path still need a compatibility review. Current observed JS/Web release is `@powersync/web` 2.4.2 (2026-10-01), but it is not a universal recommendation. (S01–S08)
2. **Direct local SQLite plus custom API/PostgreSQL:** more control over command/approval/publication transactions and fewer sync-engine conventions; more custom engineering for reliable queue, retries, partial sync, schema migration and monitoring. If PostgreSQL is selected, explicitly test role/RLS posture and serializable retry behavior. (S09–S16)
3. **CouchDB replication:** evaluate only if peer-to-peer document replication matters more than relational constraints. Conflicting revisions survive, yet default winners alone appear in ordinary reads/views and the app must discover and resolve leaves. Document boundaries determine which concurrent edits conflict; revision history is not the roster's published-version history. (S18–S19)
4. **Automerge/Yjs on selected text fields:** may improve merging of collaborative notes/comments. Do not use deterministic CRDT convergence as an assignment validator or approval mechanism. (S17, S01)

These are discovery candidates, not owner-approved technology choices. The case brief does not identify client platform, existing backend, hosting, identity provider, expected offline duration, data retention, or budget; no product-specific deployment recommendation is complete without those constraints.

## Existing coverage, rejected choices, uncertainty and owner decisions

**Already covered by the released plan and retained:** stable IDs; request reference to the publication the worker saw; immutable/versioned snapshot as a concept; downstream version number; the need to distinguish rule checking, approval, publication and consumer references; proposed crash, stale-approval, offline conflict, simultaneous-swap and delayed-notification tests.

**Rejected or materially corrected:** roster-wide timestamp-based field merging; checking only after merge; representing approval as a mutable boolean and approver ID; carrying approval forward across schedule-affecting changes; merging reconnecting offline edits straight into the shared draft; warning-only acceptance of a request based on a stale draft; treating notification delivery as rewindable; assuming sync checkpoint or local persistence itself validates the schedule.

**Optional improvements:** field-level merge for fields explicitly declared independent; CRDT-backed collaborative text; local optimistic display with pending label; store a deterministic diff/change summary; use PostgreSQL interval exclusion if the chosen data model supports it; encrypt/backup local data per platform after a threat/storage review; export a correction when an immutable publication is superseded.

**Owner decisions required before executable rules/acceptance tests:**

- What constitutes an overlap (time zone, daylight-saving transition, travel/buffer time, boundary equality, recurring duties)?
- Which qualifications apply to which roles/duties, their effective/expiry dates, and whether a proposed or already-published assignment can become invalid when a qualification changes?
- Are dependencies hard requirements, advisory warnings or supervisor overrides? Can the dependency graph cycle? How are coverage minima represented?
- Is a worker swap request binding to the exact publication, or may a coordinator rebase it if the affected assignment is unchanged? When does it expire? Can it be cancelled after coordinator acceptance?
- Which edits invalidate supervisor approval: all roster content, only assignment/qualification/dependency state, or another protected projection? Which roles may draft, resolve, approve, publish, export or send corrections?
- What schedule data may each worker/offline device cache, for how long, and what is the recovery process for lost/corrupt storage with unsent edits?
- Which notification channels/export formats are required, what idempotency/cancellation APIs do they support, and what corrections must be sent after publication supersession?
- Which client platform, backend database, identity provider and hosting constraints must a sync candidate satisfy?

Until those are decided, tests can demonstrate preservation and state transitions using explicit synthetic assumptions, but cannot claim center-policy acceptance.
