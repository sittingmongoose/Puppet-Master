# Independent discovery: accessible asynchronous review form

## Framing and candidate direction

The portal needs a field-level editor and a transaction boundary. Keep the review decision, each explanatory field, notes, server validation snapshot, last acknowledged save snapshot, and remote entity version as distinct state. A changed explanation stays locally owned until the server accepts the matching draft revision. Validation or concurrency rejection may invalidate the decision, but must not roll back the explanatory text or notes. The server owns eligibility and final acceptance; client checks give immediate guidance and cannot certify a choice that depends on current service data.

Two credible presentation families emerged. (1) Persistent inline errors plus a top-of-form error index with links gives local context and a way to find every current error; use one concise, polite status channel for phase changes, keep messages visible, and never steal focus when a response arrives after the reviewer has moved. Focus the summary only after an explicit submit/commit attempt if errors block that attempt, and let the reviewer activate a summary link to return. (2) A submit/blur-driven batch model can avoid transient and repetitive messages, but errors are discovered later and an asynchronously invalidated choice can otherwise remain unnoticed. Prefer a hybrid: local deterministic checks on blur/submit, remote decision validation on an intentional decision selection or commit with a debounced/cancellable request, persistent field text plus summary, and a coalesced status update for pending/result. Do not announce each keystroke or each internal save retry. W3C says status messages include waiting, progress, action results, and errors, should be exposed without focus, and cautions against excessive live-region chatter; the APG alert pattern also says alerts do not take focus, should not disappear quickly, and can become disruptive when frequent. [S01, S05]

Use native constraints for simple format/required checks where their behavior suits the service; the WCAG explanation warns that browser-native messages can be generic, transient, small at zoom, and serially expose only the first of several errors. A custom accessible component layer can render richer inline errors and server errors. React Aria is a useful maintained implementation reference: its current guide documents custom/native/realtime validation, server errors keyed by field, and says server errors clear when the field is modified. That clearing rule is an example, not a complete concurrency policy: a response must be attached to the exact submitted decision revision, and a late response for an old value must not certify or invalidate the current value. The GOV.UK Design System is a second maintained pattern: inline messages plus a persistent summary with matching wording and links to fields; its guidance focuses summary after an error-producing submission, not on each asynchronous event. These are patterns to adapt, not an assumption that this portal uses React or GOV.UK. [S02, S03, S10, S14, S15]

## State, ownership, and race handling to carry into the plan

Every client draft should have a monotonically increasing local revision. A validation request captures draft revision, decision value, and entity version; only a reply matching all three may change current validation. Abort older work where possible, but also compare response identity on arrival because cancellation does not prove that no response can arrive. On a newer local edit, mark prior validation stale/pending and do not present its success as current. On a remote invalidation or conflict, preserve local text, show which decision changed and the current server choice/version, require an explicit reviewer action to adopt or resubmit, and revalidate against the latest version.

Treat save as an explicit transaction over a snapshot, separate from background validation: idle → saving(snapshot revision, base ETag) → saved(acknowledged revision and new ETag), rejected(validation errors), conflict(precondition failed plus fresh server state), or outcome-unknown(network interruption after send). If edits occur during save, success acknowledges only the sent snapshot and leaves later edits dirty. A transport timeout is not proof that a save failed; reconcile by fetching current state or a server-supported request/idempotency key before claiming saved or retrying a non-idempotent action. HTTP If-Match uses strong entity-tag comparison to prevent lost updates; when a precondition is false, the server must not apply the operation and may return 412. The spec permits success if the same state-changing request can be determined to have already succeeded, which matters when the first reply was lost. [S09]

Separate ownership: the client owns the unsaved local draft, focused field/caret, presentation timing, and request correlation; the server owns policy validation, accepted persisted decision, current canonical version, and authoritative conflict/error response; a collaboration/event feed owns notification that some remote version exists but does not authorize overwriting local edits. Do not remount/replace active controls when showing errors or status; retain focus and textarea selection. Error-summary links are a user-directed return path. A remote event should update the server snapshot, then either mark non-dirty fields refreshed or mark dirty overlapping fields conflicted; never replace an unsaved explanation.

## Layout, language, and test direction

Keep the DOM reading/focus order meaningful and stable when inline errors or summaries are inserted. At narrow width and 200% text enlargement, let content reflow, allow long translated labels/errors to wrap, avoid fixed-width error panels, and keep focused controls visible. Use logical layout properties and document/field direction metadata for RTL; W3C Internationalization guidance says declare direction with dir and use dir=auto for user or externally supplied text whose direction is unknown. This supports correct direction mechanics, not translation quality or assistive-technology compatibility claims. [S06, S07, S08]

A future component test strategy should use deterministic synthetic traces: (a) request A for revision 4 returns after request B for revision 5 and is ignored; (b) decision becomes invalid remotely while reviewer is in a later textarea and focus/value/selection remain; (c) If-Match rejection retains all dirty text and exposes the latest canonical choice; (d) server accepts save but response is lost, so UI says outcome unknown until reconciliation; (e) edits made while save is pending remain dirty after the earlier snapshot is acknowledged. Assert state, visible text, focus identity, caret/selection, summary links, and that background events do not move focus or create one announcement per keystroke. Then propose browser keyboard/zoom/RTL layout checks, assistive-technology checks with the portal's supported matrix, and multilingual usability evaluation. No portal build, service integration, screen-reader pairing, translation review, or multilingual usability test has been run; those remain proposed.

## Public implementation failure history

React Spectrum issue #6830 reported that React 19 form-action automatic reset (RAC 1.3.1) could restore the original default value and clear server-returned validation errors. The linked fix PR #8444 merged July 7, 2025 (commit shown as effce79): it synchronizes reset state with the current defaultValue and retains action-returned server errors, while explicitly describing a best-effort distinction for programmatic resets outside user events. This is a concrete lifecycle interaction to test when framework submission/reset semantics change, not evidence that all async forms lose data. Separately, still-open report #6983 says React Aria native-mode validation did not clear/update an error until blur after correction; the report labels its reproduction version only “latest”, so treat it as a reported regression edge, not a verified behavior for a pinned release. GOV.UK's own error-summary history records moving role=alert inside the summary and removing aria-labelledby in v4.4.0 after a JAWS issue prevented the whole summary being read. [S11, S12, S13, S14]
