# Independent critique — D-P02 image derivatives

## Review basis and outcome

I reviewed the complete released brief, revealed provisional plan, investigator discovery and draft, plan-reveal record, full investigator source map, and carried source index. I independently reopened the governing format, implementation, release, and issue evidence relevant to the consequential claims. Scope remains the non-deployed component research plan. No library is selected. No image fixture, decoder, converter, metadata scanner, executable witness, malicious-input check, perceptual review, or integration test was run.

The draft covers nearly every brief obligation. The main correction is to its categorical rejection of resize-then-orient: exactly-once orientation and correct output geometry are required, while a backend may safely orient after thumbnailing when its size/crop logic accounts for the transform. The draft also needs an explicit comparison of transform paths and a concrete owner decision for which technical metadata internal review copies retain. The cited libvips truncation report has been resolved in master since the investigator's source check; release applicability remains version-specific.

## Findings

| ID | Classification | Draft locator | Evidence and assessment | Disposition for the final |
|---|---|---|---|---|
| C-01 | Material wrong / overbroad correction | P1.a, P1.c, recommended pipeline steps 3–4 | The exactly-once orientation rule is sound. The stronger rule that pixels must be manually oriented before resize is not universal. The libvips thumbnail API interprets orientation tags and can rotate the thumbnail after its shrink path; issue #1523 records the maintainer explaining that thumbnail performs this to avoid rotating a full-size raster, and the old API-combination defect was fixed. A resize-first path can be correct when the target box, crop coordinates, rounding, and final dimensions account for axis-swapping transforms. [LIBVIPS-THUMBNAIL-817](sources/index.md#libvips-thumbnail-817), [LIBVIPS-ISSUE-1523](sources/index.md#libvips-issue-1523) | Keep one logical orientation owner, normalize the geometry used by fit/crop decisions, and ensure the output has no active stale transform. Permit loader-side orientation and resize-on-load if the exact backend/version passes orientation and geometry fixtures. Treat “transform before crop/geometry” as a simple safe implementation option, not a required architecture. |
| C-02 | Material incomplete | P1.a–c; candidate approach comparison; validation matrix | The draft promotes a linear-light, premultiplied reference path but does not compare it concretely with the optimized encoded-space/shrink-on-load path. libvips documents that its normal shrink is in sRGB; its linear option may improve results but is slower because JPEG shrink-on-load cannot be used. ImageMagick likewise documents that profile/operator order and resize filter affect pixels. These are tradeoffs to measure, not a universal mandate for every thumbnail/review derivative. Alpha should remain separate from RGB profile/transfer transforms; premultiplication and a declared transparent-edge policy are appropriate. [LIBVIPS-THUMBNAIL-817](sources/index.md#libvips-thumbnail-817), [IMAGEMAGICK-OPTIONS](sources/index.md#imagemagick-options), [STD-PNG3](sources/index.md#std-png3) | In the final, compare an optimized thumbnail path with an explicit full-decode/reference path, including their profile/CMM, alpha, orientation, crop, memory, and output-profile behavior. State the visual acceptance criteria and keep paired/perceptual review proposed until run. |
| C-03 | Material incomplete, not a proven false correction | P1.a color paragraph; recommended pipeline step 2; owner decisions | The stated PNG fallback deserves context: PNG 3 treats RGB with no understood color signal as uncalibrated, device-dependent color, but says standalone viewers may choose a likely default and allow adjustment. WebP separately says sRGB should be assumed if ICCP is absent. Thus “do not silently treat an invalid profile as sRGB” is sound; a blanket rule that every untagged image is unusable is not established. Current text leaves the product fallback largely open, which is appropriate pending an owner decision. [STD-PNG3](sources/index.md#std-png3), [FORMAT-WEBP-RIFF](sources/index.md#format-webp-riff) | Keep explicit, versioned, format-specific interpretation/fallback or visible failure policy. Do not convert silently under an invented policy. Retain the owner decision for PNG untagged, WebP absent-ICCP, untagged CMYK, and malformed/incompatible profiles. |
| C-04 | Material wrong in current-state wording; underlying safety recommendation remains valid | Discovery “Design space” and “Issue and release evidence”; draft P2.c and P4.a / libvips row | The investigator map calls #5195 open, and the draft calls it an open report. On review, #5195 was closed as completed by PR #5235, merged into master on 2026-10-02. The report reproduced acceptance of a truncated JPEG by buffer/source thumbnail calls on 8.18.5 while file thumbnail refused it. The current tagged v8.18.7 release is dated 2026-09-26, before that merge; the sources reviewed do not establish which later packaged release contains the fix. The operation remains a valuable version/API-specific regression test, but its status and applicability must be stated accurately. [LIBVIPS-ISSUE-5195-RECHECK-20261012](sources/index.md#libvips-issue-5195-recheck-20261012), [LIBVIPS-PR-5235](sources/index.md#libvips-pr-5235), [LIBVIPS-RELEASE-8187](sources/index.md#libvips-release-8187) | Replace “open issue” with the dated state and release boundary. Require a truncated-input regression on the selected build and on every file/buffer/source path the component uses. Do not reject a fixed implementation solely because the historical report existed. |
| C-05 | Material incomplete; unresolved product input | P3.b; owner decisions | The brief explicitly requires selected technical metadata in internal review copies. The draft calls for an explicit allowlist and suggests moving decoder/profile/orientation facts to a private sidecar, but does not name which fields must remain in the internal image or confirm whether a sidecar satisfies the reviewers’ need. | Keep public and internal policies separate. In the final, require an owner-approved internal image allowlist (candidate fields can include normalized dimensions, orientation disposition, capture/device facts only where needed); treat the sidecar as provenance, not an automatic substitute for the requested review-copy metadata. |
| C-06 | Material incomplete | P3.a–d, recommended pipeline step 5, validation matrix | Fresh output from normalized pixels is a strong privacy-oriented recommendation and the draft correctly warns that re-encoding alone proves nothing. It should not imply that “fresh container” itself proves removal: writers may copy metadata, preserve auxiliary items, or emit unexpected chunks. Formats have materially different structures; PNG has color, text, time, Exif and animation chunks; WebP has metadata/unknown chunks and animation; AVIF is an item graph with auxiliary and derived images. [STD-PNG3](sources/index.md#std-png3), [FORMAT-WEBP-RIFF](sources/index.md#format-webp-riff), [FORMAT-AVIF-1_2_0](sources/index.md#format-avif-1_2_0) | Keep fresh construction as the leading public-export candidate, but make the claim bounded to the exact writer/build and byte-level audit. Preserve only output color signaling/alpha and approved fields. Keep per-format support and metadata coverage as owner choices; an unverified format remains unsupported. |
| C-07 | Material incomplete | Candidate approach comparison and P1.a/P1.c | The table usefully compares four maintained implementations without naming a winner. It gives less detail on the actual decode/transform approaches the brief asks to compare: loader shrink-on-load versus full-resolution decode, linear versus encoded-space resampling, CMM/profile handling, and alpha-aware filtering. Current sources support useful limits (for example, Rust image 0.25.10 has strict width/height limits but a non-strict allocation cap that some decoders may ignore; ImageMagick can spill cache to disk; progressive JPEG can raise libvips memory substantially). These details are scattered rather than compared against the same acceptance criteria. [RUST-IMAGE-02510](sources/index.md#rust-image-02510), [IMAGEMAGICK-OPTIONS](sources/index.md#imagemagick-options), [LIBVIPS-CHECKLIST](sources/index.md#libvips-checklist) | Add a compact approach comparison to the final without selecting a library. [PILLOW-SECURITY-123](sources/index.md#pillow-security-123), [IMAGEMAGICK-OPTIONS](sources/index.md#imagemagick-options), [RUST-IMAGE-02510](sources/index.md#rust-image-02510) | Keep the proposed layered caps, and distinguish estimate/check from actual isolation and enforcement. |

## Clause-by-clause disposition

- **P1.a:** Accept the intent to inspect metadata and use a declared representation; amend the fixed sequencing claim. The final requires correct logical orientation, geometry, and single-transform behavior, while allowing a tested backend to shrink before its orientation step.
- **P1.b:** Accept alpha preservation/flattening policy. Specify alpha as coverage/opacity independent of RGB color transforms, choose a named background in output color space when flattening, and validate transparent-edge behavior.
- **P1.c:** Amend “no” to “unsafe unless geometry and crop mapping account for orientation.” Compare optimized and reference paths; dimensions alone do not establish fidelity.
- **P2.a–d:** Accept and retain recipe/build identity, immutable preset revisions, dependency provenance, and the distinction between replayable settings and bit-identical output.
- **P3.a–d:** Accept allowlists and format-aware privacy review. Amend fresh-container wording so it is not treated as proof; preserve required target color interpretation; add an explicit internal-copy technical metadata decision and byte-level output audit.
- **P4.a–d:** Accept independent publication, cancellation cleanup, resource controls, explicit item status, and batch-completeness behavior. Replace estimate-only language with enforced process limits; update the #5195 status; retain every proposed test as unrun.

## Brief coverage audit

The draft preserves local/read-only original handling, selected exports, rotation and color requirements, wide-gamut and transparency concerns, broken metadata exceptions, regeneration provenance, privacy-vs-color tradeoffs, maintained alternatives without a winner, large-input resource failure, mixed-batch and cancellation behavior, no plausible partial substitute, and plain explanations for unsupported/policy exceptions. The final must keep these requirements visible and carry the unresolved accepted formats, profiles/fallbacks, sizes, metadata allowlists, budgets, cancellation policy, and regeneration promise as owner decisions.

**Executed by this critic:** reading the assigned text artifacts and web review of cited primary documentation/issues. **Not executed:** any image fixture, decoder or encoder, metadata audit, malicious-input test, perceptual comparison, or production integration check.
