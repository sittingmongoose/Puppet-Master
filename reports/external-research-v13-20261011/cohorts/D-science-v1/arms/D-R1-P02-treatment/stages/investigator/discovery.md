# Independent discovery: D-P02 image derivatives

**Basis:** the released input brief only; the exact plan had not yet been released. Research captured 2026-10-12 UTC. No image files, case fixtures, code, or executable checks were run.

## Design space

The requested component is a local, non-destructive transformation pipeline, not an upload service. Keep the original immutable and write derivatives into a separate destination. Before decode, identify a supported format from content, enforce compressed-byte and header limits, parse dimensions with checked arithmetic, and estimate decoded/intermediate memory rather than relying on compressed size. Put codec work behind process-level CPU, memory, disk and time limits. Keep accepted formats, frame/page policy, per-item status, and resource caps explicit.

There are useful competing approaches; the brief does not justify selecting one yet.

- **libvips** offers demand-driven pipelines and a file-based thumbnail operation that can exploit decoder shrink-on-load, then block shrink and Lanczos3; its thumbnail path premultiplies alpha. This can avoid full-resolution intermediate rasters. Its performance and memory benefit depends on format and loader: progressive JPEG can still require the full image in memory. The 8.17 API documents first-frame/page output by default and an explicit all-frame option. Current release evidence is v8.18.7, so behavior must be checked on that pinned release. A recent open report says fail_on=error is ignored on thumbnail_buffer and thumbnail_source even though it works on file input, allowing a plausible partial image from a truncated JPEG (LIBVIPS-ISSUE-5195). For memory buffers, issue reproduction shows passing fail_on in the loader option string is honored; that is a workaround report, not a guarantee for other codecs.
- **ImageMagick** has broad format/operator support and explicit memory, map, disk, area, width/height, time, file and thread controls. Memory/area ceilings can move pixel cache to disk rather than reject work, so predictable failure requires disk and dimension caps too. Its security policy can restrict coders and paths and is a configuration boundary; process-specific flags cannot relax policy. The ordered profile operator and resize filter also mean argument order belongs in the documented recipe (IMAGEMAGICK-OPTIONS, IMAGEMAGICK-SECURITY).
- **Pillow** has direct orientation, fit/contain/crop and ICC-transform APIs. Its EXIF transpose applies a non-identity orientation and clears the orientation field; its default rendering intent for ImageCms is perceptual, which should not be treated as an implicit product policy. Its security guidance documents pixel-bomb warning/error thresholds and recommends allowlisting formats, applying limits, sandboxing, treating warnings as errors, and keeping codecs current. This is convenient for a Python component but requires memory and process isolation.
- **Rust image 0.25.10** offers native decoders, metadata getters and orientation operations. Width/height limits are strict, while max_alloc is explicitly non-strict and some decoders may ignore it; it is not by itself a full ICC conversion policy. It is a useful Rust-native alternative if its per-codec limits, profiles, supported formats and separate CMM are proven adequate.

## Behavior that governs output

1. **Orientation:** apply the Exif transform once, before deriving output geometry or crop coordinates. All eight orientation states include mirrored cases. After baking orientation into pixels, clear/reset the stored tag so a later viewer cannot rotate again; invalid or absent orientation needs an explicit path. Pillow’s documented exif_transpose follows this pattern, and the Rust metadata API warns that retaining an applied orientation causes a second rotation. Historical bugs in Pillow YCbCr TIFF/CR2 and a libvips autorot-plus-thumbnail_image interaction show that testing only a common rotated JPEG is insufficient (PILLOW-ORIENTATION-HISTORY, LIBVIPS-ISSUE-1523). Preserve the source orientation in the provenance record, not as an active output instruction.

2. **Dimensions and scaling:** define target bounding box, aspect rule (fit versus fill-and-crop), upscaling rule, rounding, filter, and encoder quality as versioned settings. A smaller output is not evidence of accurate color or detail. The library-selected decoder shrink, resampler and order must be included in the recipe because they affect result pixels. Multi-page/animated inputs must be explicitly rejected, flattened to a named frame, or processed by a stated all-frame policy; library defaults differ.

3. **Color:** retain the source ICC/color signaling long enough to interpret samples, validate profile/sample-space compatibility, convert with an explicit CMM, output profile, rendering intent and black-point policy, and embed the target profile where the format supports it. For PNG, conflicting supported signals have defined precedence: cICP, iCCP, sRGB, then cHRM/gAMA. Untagged RGB is not guaranteed to be sRGB; untagged CMYK or invalid/unsupported profiles need a declared exception path. Wide-gamut to sRGB may require gamut mapping and can change out-of-gamut values. Pillow ImageCms defaults to perceptual intent and can reject invalid or mode-incompatible transforms. libvips issue reports describe image-specific CMYK/LAB and Apple Wide Color failures around thumbnailing/linear-light transforms; these are reasons for test coverage, not proof all inputs fail. State clearly whether review copies target sRGB, preserve a supported wide-gamut profile, or both.

4. **Alpha and scaling interaction:** keep alpha independent of ICC color conversion and do not apply RGB gamma to alpha. Filtering unassociated RGB at transparent edges can introduce fringes; compare paths that premultiply before resampling and unpremultiply after, ideally in a linear-light working space. libvips thumbnail documents automatic premultiplication. For an output format without alpha, composite against a fixed, specified background in the target color space. Preserve alpha only when the selected output format and reviewer workflow support it.

5. **Metadata modes:** do not copy arbitrary source metadata onto output. Public export should use an explicit allowlist for output-only technical/rendering fields, preserve the target ICC profile when needed to keep the visual interpretation, and remove identifying EXIF, MakerNotes, GPS, XMP/IPTC, embedded thumbnails, comments and other supported metadata blocks. Internal review output may include an explicit technical allowlist, such as orientation-normalized state, pixel dimensions and selected capture/device facts, subject to privacy policy. Do not carry stale source geometry/orientation or an embedded source thumbnail. ExifTool warns that indiscriminate deletion can remove color-space information; Pillow warns that ICC itself can carry identifying information. Thus color fidelity and privacy are separate choices, not equivalent to deleting one EXIF field. Audit duplicate namespaces and non-EXIF GPS fields; report only the tested sanitization coverage. File names, directory names and filesystem attributes are outside embedded-image metadata and need a separate export policy.

6. **Failures, batches and cancellation:** never substitute a guessed image or partial decode. Return an explicit per-item result such as success, unsupported format, corrupt/truncated, profile/policy exception, resource limit, encoder error or cancelled. Write each derivative to a unique temporary file and publish it only after successful encode and verification; the original is read-only. Record successful, failed, skipped and cancelled items in a batch manifest. Cancellation should stop scheduling pending items, signal in-flight work, clean temporary partial outputs, and preserve already-published successful items with clear statuses. A batch-wide rollback is a separate owner decision. Explain unsupported formats and profile exceptions in user-facing terms with a path to resolve them.

7. **Regeneration provenance:** retain source content hash, derivative content hash, canonical recipe/settings version, orientation disposition, source and target profile identifiers/hashes, rendering intent, alpha/background policy, dimensions/filter/crop/quality, decoder/library and transitive codec versions, CMM version, encoder version, and failure/retry status. Distinguish reproducible recipe from byte-for-byte deterministic output: codec/CMM/version changes can alter pixels or bytes even if dimensions match. Store this outside public exports and do not upload contributor files. Regeneration should reference the original by controlled local identifier/hash and must never rewrite it.

## Issue and release evidence

- Pillow’s YCbCr TIFF/CR2 orientation report and linked PR #8556 were fixed and recorded in release notes; the observed case explains why orientation pixels and metadata must both be checked (PILLOW-ORIENTATION-HISTORY).
- libvips issue #1523 reports changed interaction between autorot and thumbnail_image after 8.9.0 metadata semantics changed; tests should cover API combinations and only one stage should own orientation.
- libvips issue #5195 reports a high-severity truncated-JPEG acceptance path for buffer/source inputs in 8.18.5 and master at report time. Do not trust the declared fail_on argument on those paths without testing the exact adopted version.
- libvips issues #3159 and #4343 capture CMYK/LAB and Apple Wide Color / linear-light cases. The latter is based on a private image and an older version; it does not establish prevalence or current status. The latest release observed was 8.18.7 (24ad4d0), which does not list a thumbnail fail_on repair in its release notes.

## Owner decisions to resolve

The component owner must choose the supported formats and exact decoder builds; maximum dimensions, decoded memory estimate, CPU/disk/time caps and batch concurrency; animation/multipage behavior; thumbnail/review sizes and fit/crop/upscale/filter defaults; untagged RGB/CMYK and invalid-profile behavior; working/output color spaces and rendering intent; alpha preservation and non-alpha background; JPEG/PNG/WebP export formats and quality; public versus internal metadata allowlists; whether cancellation preserves completed files or rolls back a batch; and what level of regeneration fidelity is promised. These cannot be inferred from the brief.
