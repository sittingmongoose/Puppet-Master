# Independent discovery — D-P04 comment anchoring and reconciliation

## Scope and method

The brief asks for a source-backed component proposal, not an implemented editor. I treated comment identity and intent as an application-level layer around whichever layout collaboration engine is selected. I examined maintained primary documentation, a real whiteboard reconciliation implementation/caller, upstream issue history, and the W3C annotation interchange model. All code and issue evidence is descriptive; no downloaded code was run, no project account or document was changed, and no merge experiment was executed. The exact plan has not been released or read.

## Independent discovery from the brief

1. **Identity must outlive geometry.** Give each created shape, connector, group, thread, and region a non-recycled stable application ID. Treat coordinates, dimensions, labels, z-order, visual similarity, array position, and CRDT internal operation IDs as data about an object, not the object’s identity. A replacement gets a new ID and an explicit `replaces`/`supersedes` relation. This avoids attaching an old thread to a visually identical but newly created object. (Compare Loro TreeIDs and Automerge object/operation identities in R03, R10–R11.)
2. **Store comment intent separately from layout materialization.** A thread should name its original target ID, target kind, creation frontier/version, a local-frame or region selector, a small origin-context snapshot, and lineage/event links. Compute a current display anchor from known move/group/transform events while retaining original context. A missing target is a visible unresolved state with the last-known context; never drop the thread or silently bind it to the nearest geometry.
3. **Use explicit operation meanings.** Move/resize preserves identity. Grouping should add a group/container identity while preserving member IDs and each existing anchor’s target scope; ungrouping removes only the container. A connector has its own ID and endpoint IDs. Replacement and delete are distinct operations. If one source becomes several candidates, or a region cannot be transformed unambiguously, expose candidates and ask a reviewer.
4. **Represent deletion as an application-visible tombstone.** Capture deleted ID, deletion event/frontier and actor/time only if the retention policy permits it; retain the thread body/replies and original target snapshot separately from the visible layout. Do not auto-undelete on a concurrent stale write. An explicit undo/recover event may restore the same identity but must appear as a named operation with provenance and notice. CRDT delete/GC behavior alone does not carry the full product explanation (R07, R11).
5. **Split deterministic layout convergence from intent resolution.** Let the chosen engine converge operation sets and record technical conflicts. A comment resolver consumes those events and emits states such as `attached`, `moved`, `grouped`, `deleted-unresolved`, `replacement-candidate`, or `ambiguous`. Automatic mapping is safe only for stable-ID-preserving events with a defined transform. A winner chosen by version, operation ID, nonce, or wall clock is not proof of user intent (R10–R11, R15–R18).
6. **Treat history and tombstones as a privacy budget.** Store only the context needed to explain a thread: stable ID, origin selector/frame, causal reference, and perhaps a small rendered/vector thumbnail or content-redacted snapshot. Define duration, closure/retention policy, archive policy, compaction threshold, and what a long-offline client can still sync. Loro shallow snapshots and Automerge compaction expose real history/sync tradeoffs; Yjs documentation and its open memory report show deletion retention can be operationally material (R05, R07–R09, R12–R13).
7. **Export a self-contained, read-only review package.** Use the W3C body/target/specific-resource/selector vocabulary as an interchange shape where practical, plus app extension fields for layout version/frontier, stable target ID, original/current context, resolution status, and lineage. Include replies and unresolved threads in an appendix/side list with target preview, last-known region, and explanation; do not require the recipient to have an account or editing rights. Export redaction must be explicit because snapshots can retain sensitive geometry, names, or deleted content (R01, R05, R13).

## Approaches and comparative evidence

- **Loro** is a strong candidate to prototype if the eventual model needs frequent hierarchy moves: its maintained API exposes stable tree node IDs, move/delete events, deleted-state queries, and automatic prevention of cycles; docs explicitly note a concurrent fractional-index interleaving caveat (R02–R04). Its shallow snapshot mode makes storage/privacy tradeoffs concrete but cuts off compatibility with peers older than the retained frontier (R05). A LoroTree node ID could back a layout object ID only after version-specific tests; comment semantics remain custom.
- **Yjs** supplies a widely used shared-document model with incremental updates and optional preservation of old deleted content via `gc=false`; when GC runs it discards deleted content, and Yjs’ internal notes say deletion records do not name who or when (R06–R08). Keeping user-facing tombstones solely inside a GC-able data structure would therefore be risky. The open #741 report is a warning to test memory growth for deletion-heavy documents, not a settled benchmark or confirmed general defect (R09).
- **Automerge** offers deterministic merging, inspectable multi-value conflicts, change-history frontiers, and a Repo storage layer that safely compacts stored increments into snapshots (R10–R14). The documented map delete/concurrent-set rule can leave a key present, while same-property concurrent updates expose alternatives only through conflict inspection. This is a data convergence result, not a policy for deliberately deleted floor-plan objects or comment intent. Compaction can remove sensitive history but makes older replicas without a common ancestor incompatible.
- **Excalidraw** offers a useful nearby whiteboard example rather than a recommended dependency: current code reconciles by ID/version/versionNonce and callers pass deleted elements through restore/reconcile/update flows (R15–R16). Its issue history includes a closed import/version regression (#3795) and a separate open, unconfirmed 2026 report about remote index repair affecting versions (#11933). Both suggest tests at import/recreate and remote normalization boundaries; neither establishes current correctness for our target product (R17–R18).
- **W3C Web Annotation** provides a platform-neutral export vocabulary for comment body, target, specific segment, selectors, lifecycle, and authorship. It intentionally leaves transport/synchronization to other layers, so it is an export/schema input, not an offline merge engine (R01).

## Initial validation plan (proposed; not executed)

Construct synthetic replicas from a saved base frontier and permute delivery order, duplicate updates, and reconnect timing. Assert convergence, one stable thread ID, preserved original context, and explicit resolution state for: geometry-only move; move plus offline reply; group/ungroup; replacement with identical geometry; delete against stale edit; delete against concurrent new reply; explicit undo; ambiguous split/merge; concurrent object/connector move; and repeated import/reconciliation. Add round-trip export tests showing the full thread list, unresolved anchors, authorship/context, and redaction choice in an account-free read-only snapshot. Profile document size and memory with many historical edits/tombstones; test compaction with current and stale offline peers and verify that privacy deletion reaches replicas and archives. Keep future permission checks and usability studies separate from the proposed data/merge tests.

No executable merge experiment, permission test, export implementation, or usability study was run in this investigator discovery stage.
