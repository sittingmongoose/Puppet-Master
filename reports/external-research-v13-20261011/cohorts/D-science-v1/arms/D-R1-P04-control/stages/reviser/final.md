# Comment anchoring and offline reconciliation for floor layouts

**Deliverable:** source-backed component proposal for the original D-P04 brief and the complete released plan. This proposes application data and resolver behavior; it is not an editor implementation and does not select a collaboration library or hosted service.

**Decision summary.** Keep layout convergence and review intent as separate, linked records. Give each shape, connector, group, thread, and durable region an opaque application ID. A geometry change preserves that ID; a replacement or copy gets a new one with optional explicit lineage. Store a comment's original target and selector, creation frontier, compact origin context, and resolution history independently of the current layout. Move its display marker automatically only through a complete, deterministic transform chain on the same target. On deletion or ambiguity, retain the thread in an unresolved review list with an explanation and last-known context. A stale edit can be shown as a conflict candidate; it cannot silently make a deliberately deleted object visible. Reassignment or restoration is an explicit, attributed action. Bound detailed history with an owner-approved retention, membership, archive, compaction, and stale-client policy. A read-only export must include machine-readable thread and unresolved-anchor context; an image is supplemental.

The design follows the original brief's no-nearest-coordinate, no-silent-resurrection, and no-lost-comment constraints. It distinguishes properties a merge mechanism can provide (convergence, deterministic ordering, retained alternatives) from application policy about what a reviewer meant. The source map preserves the upstream record IDs and their conditions; [the index](sources/index.md) is navigable by ID.

## Recommended component contract

Store layout events and comment intent as separately inspectable data. A minimal anchor record should retain:

- a stable thread ID and the original target ID and kind (shape, connector, group, or selected region);
- a point/shape selector or region geometry in a declared local or board coordinate frame, plus the creation frontier/version;
- a small, policy-approved origin snapshot or summary sufficient to explain the original placement;
- explicit transform, group membership, replacement/split/merge lineage, deletion, restore, and reassignment references as applicable; and
- a current resolution state, the evidence used for a computed marker, and the alternatives/reason when no single current target is justified.

Keep replies and thread resolution separate from anchor resolution. A thread can be resolved as a discussion while its old anchor remains historical; an unresolved anchor does not delete or close the thread. Store enough provenance for the author to see “original target,” “current display position,” and “why moved or unresolved.” Do not use geometry, labels, visual hashes, array positions, z-order, timestamps, or a collaboration engine's internal operation/node ID as product identity.

### P1 — Identity, endpoints, point anchors, groups, regions, and lineage

**Persistent shape IDs — accept, with lifecycle rules.** Assign an opaque document-scoped ID at object creation and preserve it through move, resize, rotation, style edits, and membership in a group. Do not recycle it after deletion. A pasted copy or replacement gets a new ID; a deliberate restore of the original names the old ID and the restore event/provenance. This keeps object identity independent of geometry. Loro `TreeID` and Automerge object/operation identities are useful engine references, but do not replace a product-level ID ([R03](https://loro.dev/docs/api/js), [R10](https://automerge.org/docs/reference/documents/conflicts/)). The closed Excalidraw import report is a useful regression scenario: it describes a stale imported ID/version being treated as a no-op after deletion, but the issue body does not establish the exact linked fix or current behavior ([R17](https://github.com/excalidraw/excalidraw/issues/3795)). Import must be explicitly classified as restore, copy, or replace rather than inferred from appearance.

**Connector endpoints — accept.** Give each connector its own persistent ID and store source/target object IDs plus endpoint selectors in the endpoint's local frame where needed. A route can change while endpoint meaning stays the same. If an endpoint is deleted, preserve a dangling/unresolved connector record or offer a named repair action; never bind it to the nearest visible shape. An explicit `replaces` edge may expose a replacement as a candidate, but does not authorize automatic retargeting. Whether a connector should remain visible or be removed when an endpoint is deleted is an owner decision.

**Point offset within bounds — accept the stable target; amend the coordinate contract.** Persist the original target ID, anchor type/selector, and creation frontier. A normalized local point or shape-specific selector can follow a move or a declared transform on the same object. Preserve the original selector/context while deriving a separate current display marker. A scalar or pixel offset alone does not define behavior under nested transforms, rotation, nonuniform resize, flip, clipping, connector bending, or changes in local frames. Specify transform type, composition order, coordinate frames, and the frontier/version for each computed mapping. If operations conflict or the transform chain is incomplete, preserve the original target and show a conflict/unresolved state. Do not synthesize a new anchor from proximity.

**Owner decision:** for an anchor inside a resized shape, choose whether it scales proportionally, stays a fixed board distance, or follows a semantic subfeature. The data model can preserve the original choice and explain its transform; research cannot determine reviewer intent. Excalidraw's version/nonce winner is a record-reconciliation rule, not comment intent ([R15], [R16]).

**Grouping and nested transforms — accept with typed group identity and explicit composition.** A group receives its own ID and membership event; children keep their IDs. A child-targeted comment remains child-targeted and its display location is composed through the known ancestor transforms. A comment explicitly created on a group targets the group ID. Ungrouping removes or tombstones the container without rewriting child identities or moving group comments onto an arbitrary child. Keep parent/membership and transform events with causal references and a defined transform order. If a parent disappears, a group-targeted anchor may become unresolved even when a child survives. A region or comment spanning multiple descendants can yield multiple candidates; preserve it and ask the reviewer.

Loro's tree diff can report create/move/delete with parent/index context, but a subtree deletion is one event rather than a child-specific explanation; enumerate affected IDs or keep independent app-level anchor records ([R03], [R04]). Concurrent move cycle prevention and fractional-index interleaving are useful engine behaviors/caveats, not a policy for a group's comment. **Owner decision:** after ungroup, should a group comment stay on the group tombstone, fan out, or require reassignment? Do not fan out implicitly because it can duplicate intent.

**Region rectangle fallback — retain as captured context; reject as identity fallback.** Preserve the selected rectangle/polygon, coordinate frame, layout frontier, and (when appropriate) IDs intersected at creation. Prefer board-space coordinates over screen coordinates. Decide whether the region is a durable object with its own ID or a versioned spatial selection. Move it only through an explicit region move or defined transform. If new objects later occupy the old area, do not infer that the comment now targets them. A comment intended to track a set needs explicit membership/lineage; one intended to mark a floor area can retain the old selection and become stale/unresolved. W3C Web Annotation supplies a portable target/SpecificResource/selector/state vocabulary, but does not specify selector migration through a mutable collaborative layout ([R01]). **Owner decision:** fixed board area, live object-set query, or explicit region object; the choice changes the meaning of move.

**Replacement, split, merge, and delete — require explicit lineage.** A replacement gets a new ID and optional `replaces` edge; a split creates new IDs linked by `splitFrom`; a merged object links to its source IDs using `derivedFrom`. These edges explain history and may present candidates; they do not automatically move the old comment. A reviewer can reassign after seeing the original context. For the same ID, automatic placement is allowed only through a complete, declared transform chain. Replacement, split/merge, missing events, or competing transforms produce `replacement-candidate`/`ambiguous` states until a user chooses. Visually identical geometry is not identity.

### P2 — Disconnected edits, deletion, and comment-intent resolution

**Disconnected operation log — keep as an option, distinguish guarantees.** An operation log can retain actor, causal frontier, object ID, and event meaning; it still needs rules for concurrent edits, replay, ordering, duplicate delivery, stale import, and truncation. Compare these alternatives without selecting one:

1. **Operation-based/local-first CRDT.** Loro documents movable trees/lists and history; its tree API offers IDs and move/delete events, cycle prevention, and an ordering caveat. Yjs provides shared types and incremental updates; deletion-content retention depends on garbage collection. Automerge provides deterministic merging and inspectable concurrent property conflicts; its Repo layer handles persistence/compaction separately from core merge semantics ([R02–R14]). These are maintained mechanisms to evaluate for offline convergence, not complete comment-intent systems.
2. **Application event log with conditional resolution.** Keep domain events such as `ShapeCreated`, `Moved`, `Grouped`, `Replaced`, `Deleted`, `ThreadCreated`, and `AnchorReassigned`. Merge independent events; turn incompatible same-target operations into explicit conflict records. This gives the application control over provenance and intent but requires its own ordering, idempotency, conflict, and storage logic. It can sit over a CRDT or service.
3. **Record-version reconciliation.** Select a record per ID by version and a deterministic tie-breaker. This can be simpler, but same-object edits can conflict, missing records require explicit deletion semantics, repair must not masquerade as user work, and the selected winner does not prove user intent. Excalidraw is a useful comparison, not a dependency recommendation ([R15], [R16]).

For all approaches, keep sibling/z-order separate from identity and make order deterministic through an order key or explicit move operation. A record absent from one snapshot is not a delete unless the protocol says so. Test concurrent insert/move and verify index repair does not change user-edit recency. Loro's fractional-index caveat and an unconfirmed Excalidraw index-repair report make that boundary worth testing ([R03], [R18]).

**Delete and later stale edit — accept tombstone/context; reject implicit restoration.** A delete makes the object unavailable in current layout. Preserve a minimal, policy-approved tombstone (ID, deletion frontier/status, and optionally actor/time/reason) and last-known geometry or a redacted anchor summary only while allowed. Keep thread bodies and replies in independent records. If a stale or concurrent edit references the deleted ID, retain its payload as a conflict candidate and show both contexts; do not make the object visible automatically. An undo/restore is a distinct, announced event naming the restored ID, actor, and operation reversed. It may be automatic only when an explicit user-authored undo and its causality are unambiguous. A merge winner or timestamp is not evidence of intent. Concurrent thread creation plus delete should converge to a deleted object and a visible `deleted-unresolved` thread with last-known context.

This revises the plan's “restore it as a conflicted object” behavior because the brief forbids silent resurrection. Yjs's internal deletion record lacks actor/time and content is discarded when GC applies; Automerge's documented concurrent map delete/set rule can retain a concurrent set value. Those engine behaviors explain why application tombstones and intent cannot be delegated to defaults ([R07], [R11]).

**Unresolved state and reassignment — adopt.** Persist a small state vocabulary such as `attached`, `transformed`, `grouped`, `deleted-unresolved`, `replacement-candidate`, `ambiguous`, and `reassigned`. Keep all unresolved threads in a visible review list even if no current object renders. Record old/new IDs, actor, time, and frontier for reassignment. The author sees original target/context and the reason for current placement or uncertainty. Closing a discussion is not the same action as reassigning its anchor. The resolver can act automatically for an extant same-ID target with an unambiguous, identity-preserving transform; a user chooses among replacement/split/merge candidates or an incomplete/conflicting transform.

### P3 — History, privacy, stale clients, and read-only export

**Acknowledgement-based retention — reject as the complete rule; keep acknowledgements as one input.** “All participants” requires a roster, membership epoch, revocation rule, and policy for indefinitely offline or abandoned devices. Waiting for every acknowledgement can retain geometry without bound; deleting as soon as current devices acknowledge can strand a returning client with stale references. Acknowledgements can inform a safe compaction frontier, but they do not set a privacy deadline.

Define owner-approved values for membership epochs, maximum offline grace, minimum retention for unresolved review context, closed-thread retention, stale-client rebase behavior, archives/backups, and deletion/redaction propagation to replicas. After an accepted frontier, an old client should obtain the new snapshot and submit its edits as candidates against tombstones rather than replaying them as silent resurrection. Keep full history only for a justified review/undo/support period; after compaction retain only the minimal anchor summary policy allows. Treat geometry, names, authorship, screenshots, comments, deleted content, and archives as potential sensitive data.

The storage/sync/privacy costs are concrete but version-specific. Loro shallow snapshots can trim history and sensitive deleted content, with a sync cutoff for peers older than the frontier; a full archive still retains the trimmed data ([R05]). Automerge Repo storage snapshots/incrementals are distinct from history compaction; after history compaction an old replica without a common ancestor may not sync, and local compaction does not prove every archive was purged ([R12], [R13]). Yjs v13.6.33 was the latest stable release recorded in the carried map; v14 was prerelease then. The open #741 report concerns a reporter's v13.6.27 deletion-heavy workload, not a general benchmark ([R08], [R09]). Benchmark synthetic histories and include the exact pinned release before choosing a mechanism.

**Owner decisions:** retention/grace durations; roster and revoked-device behavior; whether closed threads keep a summary; which geometry/authorship is archived; who can export; and how stale offline edits are reviewed. These are privacy and product decisions, not conclusions supplied by CRDT documentation.

**Read-only external export — accept the package; reject screenshot-only sufficiency.** Export a versioned snapshot usable without an account or editing rights. Include: (a) immutable geometry and ordering at a named frontier; (b) every included thread/reply with stable IDs and permitted authorship/timestamps; (c) target kind/ID, original selector/frame, resolution state, last-known context, and explicit lineage/reassignment; (d) a human-readable list and reason for each unresolved thread, including those with no current target; (e) a screenshot/vector rendering tied to that same snapshot; and (f) schema version plus redaction metadata. A screenshot alone cannot carry replies, stable identity, the original selector, unresolved reason, or the distinction between identical-looking objects. W3C Web Annotation is a useful interchange basis, not a collaboration protocol ([R01]).

Because recipients are outside the editing group, minimize personal and floor-plan data, disclose redaction, and do not omit unresolved threads silently. **Owner decision:** which identities, replies, deleted geometry, and floor details are exportable and whether redaction is the default.

## Repository mechanisms, callers, tests, and public regression history

Excalidraw is a bounded whiteboard comparison, not a selected dependency. Its current `reconcileElements` code matches by ID, keeps a local item when it is being edited or is newer, breaks equal-version ties with the lower `versionNonce`, appends unmatched local records, orders by fractional index, then repairs invalid indices ([R15]). Its collaboration caller includes deleted scene entries in the reconciliation flow, restores remote elements with local context, reconciles, bumps versions, and applies the remote result ([R16]). These are implementation-specific record rules; they do not define thread persistence, anchor lineage, or an external export.

**Critic C1 accepted and repaired in this final.** I independently inspected Excalidraw's current `packages/excalidraw/tests/data/reconcile.test.ts` on mutable `master` (C01). The suite's helper checks expected local/remote record selection, unique output indices, result equality when local and remote inputs are swapped, and stable repeated reconciliation. Cases cover version selection, concurrent element arrays, ordering/indices, and identical IDs/version/nonces/indexes. The suite does not model comment IDs, target selectors, deleted-thread visibility, replacement intent, or anchor reassignment. This is useful upstream regression coverage and a genuine gap in the predecessor draft's required “callers/tests” discovery; it does not validate this proposed component. The file was inspected, not run.

Public reports remain reports, not verified general defects: Excalidraw #3795 is closed and links PR #3797, but the patch was not reviewed; #11933 was an open, unconfirmed reporter claim about remote index repair/version behavior; Yjs #741 is an open reporter memory report for a specified older build/workload; Loro #938 is an unverified report about redo creating a new `TreeID` ([R17], [R18], [R09], [C02]). Use them to shape reproducible regression cases, not to assert a present defect or reject a library.

## Proposed validation versus work actually performed

These are future checks, not results. Build synthetic replicas from a saved base frontier; permute delivery order, duplicates, reconnection time, and replica roles. Assert convergence separately from comment resolution. Cover:

1. Move/resize plus an offline reply; verify stable object/thread IDs, declared transform, and preserved reply.
2. Nested group/move/ungroup; verify child IDs and child-target anchors remain scoped, while group/region anchors do not silently fan out.
3. Replace with visually identical geometry; copy/import/restore as distinct operations; verify old threads stay on old lineage.
4. Split/merge with explicit lineage; verify multi-successor anchors remain candidates pending a reviewer choice.
5. Delete versus stale move/edit and delete versus concurrent new reply; verify object remains unavailable while thread/replies remain visible and candidate data is inspectable.
6. Explicit undo/restore; verify named ID, actor/provenance, causal relation, and visible notice.
7. Connector endpoint deletion/replacement; verify no nearest-object repair and exercise the owner-selected dangling/delete behavior.
8. Delayed reconnect across membership revocation and compaction; verify snapshot rebase, stale edits as candidates, and no silent resurrection.
9. Compaction/export with resolved and unresolved threads; verify every intended thread is present, image and machine-readable context name the same frontier, redaction is reflected in the delivered bundle, and archives/replicas follow policy.
10. Concurrent insertion/move, order/index repair, repeated remote apply, and idempotence for each candidate mechanism. Measure storage and memory over synthetic operation/tombstone volumes and pinned versions.

Permission/access-control checks and usability studies are separate future work; neither is proven by repository tests or by this proposal. Before implementation, pin each candidate package/commit and rerun the relevant primary-source/repository review against it.
