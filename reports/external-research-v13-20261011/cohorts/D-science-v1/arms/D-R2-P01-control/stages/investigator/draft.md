# Investigator draft — D-P05 provisional design review

Released plan SHA-256: c036fb29c9b1ffb4c0179c9919eee7484ba71bf2fbe1c9be8167bb2e25db2d00. Frozen discovery SHA-256: b9c5c944e0eadfacf8d4255d1afb290fd97b15b975dd96b2bfe0cdc2b7d27bac. Plan released at 2026-10-12T04:27:35.902Z.

## Recommendation

Do not accept the provisional design unchanged. Keep search as a discovery aid over versioned content. Store durable document-edition and passage identity outside the replaceable search chunks, apply current authorization to every retrieval/open/copy path, and present edition currency separately from relevance rank. Keep the document/records system as authority for content, publication status, version retention, and access. The brief does not select a platform. PostgreSQL FTS/pgvector and OpenSearch are maintained, self-hostable alternatives worth comparing; none should be assumed to supply durable citations, permission freshness, retention, and UI behavior as a single guarantee.

The search index may hold derived chunks, embeddings, titles, and ACL labels for retrieval. It must be treated as rebuildable and potentially stale. A citation must resolve to the exact immutable edition and passage shown to the user, or stop with an explicit unavailable/removed state after checking current authorization. If a newer edition exists, show that as a distinct fact; never change the cited target in place.

## Exact clause dispositions

| Provisional clause | Disposition | Required correction and reason |
|---|---|---|
| Chunks identified by document ID, edition number, ordinal position | **Reject ordinal as durable passage identity.** Keep source/document ID and immutable edition ID, but assign a stable passage/block ID within that edition. A retrieval chunk is a search implementation detail and can be split, merged, reordered, or regenerated; it should point to a stable passage/offset target. A heading path is display metadata because headings move. If source-native block IDs are unavailable, bind a canonicalized immutable snapshot/hash plus representation version and a quote/context or offset selector. The hash detects drift but does not locate content alone. |
| Result shows title, heading path, highlighted snippet | **Conditionally acceptable after authorization.** These fields help staff decide whether a hit is useful, but titles, headings, and snippets may themselves be restricted. Use an authorized candidate path and a current per-document/per-edition check before fetching or returning protected fields. Do not reveal denied hit counts, suggestions, titles, snippets, or timing distinctions that disclose restricted records. Show source edition and effective/publication status alongside any permitted result. |
| Citation stores those fields plus the live document URL | **Reject as immutable citation.** The live URL can change target or show only the latest edition. Store a resolver token/citation ID bound to source/document ID, immutable edition/revision ID, stable passage ID, selector fallback, content/representation hash, and the edition’s effective date/status. The pasted reference may include a human-readable title only if permitted in the destination note; omit quote/snippet text from exposed URLs and untrusted logs. A live URL may be retained as a navigation hint, never as the binding identity. |
| Edition field plus chunk position reconstructs what user saw | **Reject assumption; not demonstrated.** An edition number alone is not a content snapshot or guarantee of retention. A chunk ordinal can point elsewhere after re-extraction or boundary changes. Persist or resolve an immutable edition, stable passage identity, and selector/representation state. Capture the edition and passage displayed at copy time. A hash plus the recorded normalizer/extractor version should detect a changed representation. |
| Permission filter runs before results are displayed; index team labels refresh only when reindexed | **Insufficient and unsafe under the stated invalidation boundary.** The index label is a coarse search filter, not the authority. Reindex lag can preserve revoked access. Compose the current user/team policy into retrieval, then perform a fresh, edition-specific authorization check before content fields leave the trusted service and again when opening or copying. If permissions, identity, or ACL generation cannot be refreshed/verified, fail closed. Define a revocation SLA and a change event/epoch that invalidates all affected index documents and cached derivatives. |
| Cached snippets remain until next refresh | **Reject.** A positive snippet cache can outlive a permission change. Avoid caching sensitive snippet payloads where possible; otherwise key them by principal/entitlement epoch, document ACL generation, edition, and index generation, and synchronously invalidate or reauthorize at every use. Include browser/service-worker, application, query/result, preview, and citation caches in the threat model. A cache hit is not an access grant. Do not promise revocation of content already copied/exported to a work note or other system. |
| Initial rank combines exact terms with semantic similarity | **Accept only as an evaluated candidate, not as authority or a fixed default.** Start with a lexical baseline that preserves exact identifiers, policy numbers, quoted phrases, and titles. Compare optional local embeddings and a hybrid fusion mode on synthetic examples. Scores across lexical and vector systems use different scales; rank fusion can discard score margins. Relevance score must not imply policy authority, correctness, currency, or authorization. |
| Newer edition replaces predecessor in ordinary results; citations can request older archive | **Conditionally accept, with currency and access semantics added.** Current approved editions may be the default search view if policy owners choose that behavior. Keep the cited older edition resolvable for as long as records policy requires and current access allows. Mark older results as older, with an as-of/effective date and a link to the current edition when authorized. Authorization is per edition: a user who may see the current edition is not automatically entitled to every archived edition, and a past permission is not permanent. During reindex, show a clearly stale/previous-edition state or an updating state; do not represent the prior edition as current. |
| Removed passage redirects to latest related heading and shows a warning | **Reject automatic redirect as the citation outcome.** A related heading can have different content and policy meaning, even when similarly named. Resolve the original immutable edition/passage if retained and currently authorized. If it was deleted or retention no longer permits display, show a non-content-bearing removed/unavailable tombstone after authorization and stop. A new related passage may be offered separately as a new search result, explicitly labeled as a different passage and not an equivalent replacement. Avoid revealing tombstone metadata to someone who cannot see the document. |
| Indexing state and uncertain freshness/visibility | **Add explicit states and timestamps.** Search should identify which source revision and ACL generation were indexed and when. A missing/lagging index is not “current”; authorization uncertainty always resolves to no disclosure. Proposed state model follows below. |
| Tests for moves, withdrawal, archives, rank conflict, removals | **Propose; none were executed.** The synthetic and production scopes are separated below. |

## Supported alternatives and evidence

### Retrieval

| Candidate | Evidence and conditions | Fit for this brief |
|---|---|---|
| PostgreSQL lexical FTS with GIN | PostgreSQL 18 tokenizes and normalizes text using a selected/default language configuration; dictionaries may stem words or discard stop words. It supports title/body weights and lexical/proximity ranking. The docs explicitly describe relevance as application-specific. GIN is the inverted lookup structure; a nonzero gin_fuzzy_search_limit is a soft random subset, not a ranked truncation [S01](https://www.postgresql.org/docs/18/textsearch-controls.html), [S02](https://www.postgresql.org/docs/18/gin.html). | Strong exact-term baseline for a compact internal library when one relational source can own content, revisions, ACL rows, and search state. It does not solve semantic paraphrases by itself. Confirm language analyzers, stop words, title weights, and operator settings. |
| OpenSearch lexical BM25 | OpenSearch’s hybrid example uses keyword BM25 as one retrieval arm [S08]. Its current DLS docs warn that punctuation-bearing user identifiers can be tokenized unexpectedly when stored as text; exact keyword/custom analyzer mapping is needed for permission attributes [S09, S16](https://docs.opensearch.org/latest/security/access-control/document-level-security/). | Useful when analyzers, inverted-index scale, and independent search operations justify a separate index. Requires a maintained version, carefully mapped ACL fields, and a governed sync pipeline. |
| Dense search using pgvector or OpenSearch k-NN | pgvector v0.8.7 documents HNSW/IVFFlat, iterative scans, filtering caps, and partitioning. With approximate indexes the initial scan may be followed by filtering, so a restrictive ACL/tenant predicate can underfill; iterative scans trade additional work and ordering guarantees. OpenSearch documents in-query filter, post-filter, and exact filtered-search alternatives; a restrictive post-filter can return fewer than k, while exact filtered scoring may be costly [S04](https://github.com/pgvector/pgvector/blob/v0.8.7/README.md), [S10](https://docs.opensearch.org/3.8/vector-search/filter-search-knn/index/), [S17](https://docs.opensearch.org/latest/vector-search/filter-search-knn/index/). | Could surface paraphrases missed by lexical terms, but must be measured under team/ACL selectivity. Prefer an internally hosted model; do not transmit private documents to a managed external embedding service. Record embedding model/version and rebuild state. |
| Hybrid lexical + dense with RRF | OpenSearch says RRF was introduced in 2.19 (score normalization in 2.10). RRF uses positions and discards score margins; documentation cautions against min_score thresholds and comparing RRF values across queries. Current docs corroborate the mechanism but do not state a pinned release at access [S08](https://docs.opensearch.org/3.8/vector-search/ai-search/hybrid-search/rrf/), [S19](https://docs.opensearch.org/latest/vector-search/ai-search/hybrid-search/rrf/). | A neutral fusion baseline when raw score scales differ, not an evidence-backed winner. Compare against lexical-only and dense-only; inspect ranks by arm. A semantic hit must not hide an exact identifier match solely because its score uses a different scale. |

PostgreSQL RLS and OpenSearch DLS are implementation-level retrieval filters, not interchangeable enterprise authorization sources. PostgreSQL’s enabled RLS is default-deny without policies, but table owners normally bypass and superusers/BYPASSRLS always bypass; multiple permissive policies combine with OR [S03](https://www.postgresql.org/docs/18/ddl-rowsecurity.html). OpenSearch DLS is for read retrieval, does not constrain writes, defaults to adaptive evaluation, and has special multi-role behavior; exact role combination and field mapping matter [S09](https://docs.opensearch.org/3.8/security/access-control/document-level-security/), [S16](https://docs.opensearch.org/latest/security/access-control/document-level-security/). Elasticsearch documentation gives a candidate-specific counterexample: DLS can still permit aggregate facts about restricted documents to be inferred; its node query cache is shared by shards with conditional invalidation behavior [S14](https://www.elastic.co/docs/deploy-manage/users-roles/cluster-or-deployment-auth/controlling-access-at-document-field-level), [S15](https://www.elastic.co/docs/reference/elasticsearch/configuration-reference/node-query-cache-settings). Do not generalize that exact behavior to another engine; instead test all outward data paths, including aggregations, suggestions, error behavior, and caches, in the chosen release.

### Passage identity

Preferred: stable source-native passage/block ID scoped to an immutable edition. Keep it separate from search chunk ID so a new embedding model, chunk size, or ranking experiment cannot mutate a saved citation. If the source cannot provide stable block IDs, store an immutable normalized snapshot/revision plus representation/normalizer version, content hash, and a selector fallback. The W3C Web Annotation model provides TextQuoteSelector exact text plus prefix/suffix and TextPositionSelector offsets. It explicitly warns offsets are brittle when the representation changes and recommends representation state [S13](https://www.w3.org/TR/annotation-model/). Quote selectors may disclose content when copied, so use them only within the approved visibility/retention rules. A live URL, heading path, page number, or chunk ordinal alone is insufficient.

A useful citation resolver response has separate fields for the citation’s pinned edition and today’s current edition. Resolution order: authenticate user; resolve opaque citation ID to document+edition+passage; evaluate current access for that exact edition and destination action; if allowed, render the original passage and a distinct newer-edition notice; if removed/not retained, return an authorized tombstone; if denied/unknown, disclose no title or snippet. No automatic substitute. Store export/copy outside the revocation guarantee.

## Proposed indexing-state model

Track source revision, edition ID, index generation, ACL generation, and timestamps per document. Proposed states:

1. **queued** — source change accepted; index still points at prior complete generation.
2. **extracting** — document text and structure are being read from the approved internal source.
3. **segmenting** — stable passage IDs/selectors are being mapped; search chunks point back to them.
4. **embedding** — optional local embedding model runs; lexical indexing can proceed independently if policy allows.
5. **indexing** — new revision, metadata, and current ACL generation are written to a non-active generation.
6. **validating** — required versions, permissions metadata, passage references, and counts are checked.
7. **ready/current** — active generation includes the source revision and ACL generation shown in the record.
8. **stale/rebuilding** — newer source revision exists; show previous edition only with an explicit older/as-of label and a current access check, or show updating with no stale result.
9. **failed/blocked** — indexing or authorization synchronization failed; show non-sensitive service state to authorized users and alert operators. Fail closed for visibility where ACL currency cannot be established.
10. **withdrawn/removed** — document/passage is no longer offered as current; citations resolve to retained original content only if current policy authorizes it, otherwise an authorized tombstone.

A complete generation can be switched atomically where engine support permits. OpenSearch aliases provide one concrete atomic switch after reindex [S12](https://docs.opensearch.org/3.8/im-plugin/index-alias/), [S18](https://docs.opensearch.org/latest/im-plugin/index-alias/). Alias atomicity is not a permission transaction: a current ACL check and invalidation protocol remain necessary. If the authoritative ACL event is delayed, the UI must not hide that uncertainty behind an ordinary result card.

## Failure/release history and applicability

pgvector issue #719 reports a filtered HNSW query on v0.7.0 returning no rows where the candidate scan did not include rows matching an additional file filter; a maintainer pointed to iterative scans in v0.8.0 and suggested B-tree for highly selective filters [S06](https://github.com/pgvector/pgvector/issues/719). Version 0.8.0 added iterative scans and improved filter cost estimation. Issue #785 reports an underfilled top-100 result and latency growth with scan adjustments on 0.8.0; after asking for EXPLAIN/cardinality and suggesting B-tree/HNSW settings, the maintainer closed it without a documented code change in the issue. Closure is not evidence that the reported behavior was fixed [S07](https://github.com/pgvector/pgvector/issues/785). Version 0.8.7’s changelog records an IVFFlat build buffer-overflow fix; v0.8.3/v0.8.4 include HNSW vacuum/index repair and insert fixes [S05](https://github.com/pgvector/pgvector/blob/v0.8.7/CHANGELOG.md). These are reasons to pin versions and verify query plans, recall, build, and maintenance behavior. They do not establish which engine is best for this organization.

The OpenSearch 3.8 versioned pages used for some detailed locator evidence were marked no longer maintained at access; they are not a deployment recommendation. Current unversioned docs corroborate DLS/filter/alias/RRF mechanisms, but do not expose a release identifier at access [S16–S19]. A real implementation must select a supported release and repeat the checks there. PostgreSQL 18 docs identified 18 as current stable and 19 as development/beta [S01, S03].

## Proposed validation, not executed

No synthetic corpus, search engine, database, authorization harness, or real document set was run. The work executed here was read-only primary-source research and the plan-release helper. No relevance result or security assertion is claimed as executed.

### Small synthetic corpus checks

Construct two editions of one synthetic procedure plus a second related procedure and one withdrawn paragraph. Include a unique control ID and exact policy number, an acronym, a paraphrase with different wording, a moved heading, a changed chunk boundary, one repeated phrase, and separate team ACLs. Record expected lexical and semantic candidates manually before ranking. Compare lexical-only, dense-only, and hybrid top results for exact terms and paraphrases; note underfill and source-arm contribution. Test title/body weighting and language configuration. Treat any measured rank/score as toy-corpus behavior only.

For citation and currency, capture a result from edition 1, change the heading and rebuild edition 2 with different chunk segmentation, then resolve the pasted citation. It must still target the exact edition-1 passage and separately identify edition 2. Try an archive-enabled case, archive-retention-disabled case, and a removed passage with a superficially similar new heading. The first may display the original if currently authorized; the others must stop with a distinct unavailable/removed state, not redirect as if equivalent.

For permissions, test user A and B with overlapping and disjoint access; revoke A after indexing but before cache expiry, during an in-flight search, at citation open, and before copy. Check result lists, total counts, snippets, autocomplete, suggestions, logs, caches, archived editions, and removed-state responses. Assert no restricted title/snippet/content or distinguishable hit-count fact leaks after revocation. Force identity/ACL service failure and stale ACL generation; expected behavior is fail closed. This is still a synthetic security check and is not organizational authorization sign-off.

For rebuild state, inject delay, out-of-order update, duplicate event, extraction failure, and partial generation. Verify source revision and ACL generation labels, stale/current status, atomic cutover, operator alerting, and that one old edition is never mislabeled current. For rank conflict, create a query where exact terms and semantic similarity favor different items; display relevance only as retrieval ordering and keep publication/effective date as a separate field.

### Production/owner validation required

Real-corpus relevance, language-specific analysis, scale/latency, recall under actual group selectivity, index refresh targets, cache invalidation SLA, identity-provider consistency, archive retention, content-deletion obligations, what citation metadata may be pasted to a work note, and policy wording are **proposed owner decisions/checks**, not answered by the public sources or the synthetic corpus. Production authorization tests must use the chosen engine and deployed role/field mappings, include all read endpoints and caches, and be signed off by security/identity owners. No source in this research authorizes uploading private documents to an external embedding or search provider.

## Owner boundaries

- **Policy/content authority owner:** decides which document edition is approved/current, effective dates, whether search may include superseded drafts, and the authoritative source of status. Search rank does not determine policy authority.
- **Records/document-platform owner:** supplies immutable revision IDs or snapshots, stable passage IDs where possible, retention/deletion rules, archive availability, and tombstone semantics.
- **Identity/security owner:** defines per-user/team/edition authorization, group-combination rules, revocation SLA, ACL version/epoch source, fail-closed behavior, and acceptance tests for all result and cache paths.
- **Application/search owner:** maintains ingestion state machine, chunk-to-passage mapping, local model choice/version, query fusion, cache keys/invalidation, title/snippet minimization, and citation resolver.
- **Operations owner:** selects a supported engine/version, monitors lag/failures, validates rebuild/cutover, and sets performance/retention budgets.
- **Privacy/workflow owner:** decides which citation fields may leave the search interface and appear in a work note; no design can recall an already exported copy.

## Uncertain or unresolved

The organization has not selected its authoring/document platform, identity provider, search engine, embedding model, current-version semantics, archival duration, acceptable revocation latency, or work-note visibility boundary. These decisions affect exact retention, ACL inheritance, indexing intervals, and whether snippets/quoted text may be persisted. Resolve them with the named owners before implementation. No public implementation source substitutes for those decisions.
