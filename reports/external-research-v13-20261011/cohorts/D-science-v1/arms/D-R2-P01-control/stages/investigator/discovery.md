# Investigator discovery — D-P05 software planning brief

## Scope and research method

This discovery responds to the exact brief at inputs/brief.md. No product, search service, embedding provider, or document platform is selected. I compared maintained, self-hostable mechanisms rather than assuming one platform owns version identity, access control, indexing, and citation persistence together. The sources below are official PostgreSQL documentation, the pgvector project’s pinned v0.8.7 sources and issue history, OpenSearch 3.8 documentation, Elasticsearch documentation used as a security/cache boundary example, and the W3C Web Annotation Recommendation. Access was read-only at the recorded UTC time. I did not upload or process private documents.

## Recommendation

Treat search as an internal retrieval aid over immutable document editions, with the authoring/records system as authority for content, edition state, and access. Persist each search hit’s source ID, immutable edition/revision ID, passage ID and a locator for the exact displayed passage. Keep section path and title as display metadata, not as identity: headings can move. Store enough immutable edition text or an authorized resolvable version link to reopen the cited edition, subject to a fresh permission check. Record which edition and passage the user saw when they copy the reference. On opening, state “this cited edition” and separately show the current edition and its effective date/status. Never silently retarget the citation to the current edition.

A practical initial retrieval path is lexical search with exact identifiers, titles, headings, and procedure terms weighted above body text. PostgreSQL 18 offers an integrated FTS baseline using tsvector, language configurations, GIN, and configurable ts_rank/ts_rank_cd; its docs expressly say relevance is application-specific, and ranking functions are examples, not authority [S01, S02]. OpenSearch BM25 is a separate lexical/search-engine option. If the synthetic and later approved relevance sets show lexical misses on paraphrases, add local/on-prem embeddings and compare dense retrieval; hybrid lexical+dense is a candidate, not a default requirement. OpenSearch documents RRF from 2.19 and score normalization from 2.10. RRF avoids comparing incompatible raw score scales but discards score margins; its score is unsuitable as a universal confidence threshold or for comparison across queries [S08]. All ranking results must be described as discovery aids, never as policy authority.

Keep the source-of-truth content and identity independent from the index. An index entry should carry document ID, immutable edition ID, stable passage ID, source revision/hash, indexing generation, ACL generation, effective-from/to dates, publication status, and extractor/segmenter/embedding-model version as applicable. A transactional outbox or equivalent durable change feed should create explicit states such as queued, extracting, embedding (if used), indexing, ready, failed, and stale. Publish a fully built generation atomically when supported. OpenSearch aliases support an atomic remove/add switch after a completed reindex [S12], but this only changes the index view; it does not implement authorization freshness or citation retention. While a rebuild is underway, either serve the preceding edition clearly labeled as older/current status, or show “updating” and withhold it. In either case run the current authorization decision before releasing even a title or snippet. A failed rebuild must remain visible to operators and must not be represented as fresh.

## Retrieval options and trade-offs

| Option | Useful properties | Costs, limits, and fit |
|---|---|---|
| Lexical FTS in PostgreSQL | One self-hosted relational store can hold source/version metadata, ACL rows, content, and lexical vectors; GIN supports text lookup. Language dictionaries, phrase/query parsing, title/body weights, and ranking can be tuned [S01–S03]. Exact policy numbers, names, acronyms, and quoted phrases work naturally. | Stemming/stop words and language configuration change matches; relevance weights require evaluation. PostgreSQL ranking is not a universal probability. Simpler deployment may fit a small corpus, but large-scale search operations and rich analyzers need an owner decision. |
| Search engine lexical (OpenSearch BM25) | Mature analyzers, inverted indexes, ranking, snippets and operational scale; can remain internally hosted. OpenSearch’s own hybrid example uses keyword/BM25 plus vector results [S08]. | Separate content/index pipeline and security configuration. ACL fields must be exact keyword values, not accidentally analyzed text; 3.8 DLS docs warn analyzer tokenization of user identifiers with punctuation can undermine intended filters [S09]. |
| Dense semantic retrieval | Helps with paraphrases and meaning when wording differs; can use pgvector in PostgreSQL or OpenSearch k-NN. Exact vector search is the recall baseline; HNSW/IVF reduce work but trade recall/latency/memory. Model choice, language, versioning, and embedding refresh become new owned dependencies [S04, S10, S11]. | Weak for exact identifiers, dates, quoted language, and restrictive filters; must not silently displace lexical hits. pgvector approximate scans filter after initial scan and may underfill; iterative scans have finite caps and strict/relaxed-order trade-offs [S04]. Do not call an external inference endpoint or upload private text without explicit data approval; prefer local model inference or defer embeddings. |
| Hybrid lexical + dense | Preserve exact-term retrieval while surfacing semantic candidates. RRF is a defensible baseline if scores are incomparable; score-based normalization can retain strong score margins but needs corpus evaluation [S08]. | Fusion changes ranking and does not guarantee relevance. Result scores express ordering mechanics, not correctness, recency, authorization, or policy force. Evaluate separately for exact-term and paraphrase queries and monitor each retrieval arm. |

For pgvector 0.8.7 the README documents HNSW/IVFFlat, filtering caveats, iterative scans, and tenant partitioning. If a condition matches 10% of rows and default HNSW ef_search=40 is used, the docs estimate roughly four matches on average after filtering; iterative scan caps and memory/latency settings still matter [S04]. OpenSearch distinguishes efficient in-query filtering from post-filtering: restrictive post-filtering can return fewer than k, while exact scoring over a prefiltered subset can be expensive [S10]. So “permission filter exists” is not enough to promise top-k completeness; choose and test a strategy on selectivity and workload.

## Durable passage identity alternatives

| Strategy | What it preserves | Failure mode / use |
|---|---|---|
| Stable source-system passage/block ID under immutable edition ID (preferred when available) | Exact edition and specific block even when headings move; citation can retain an opaque stable key plus current display heading. | Needs authoring/import pipeline to preserve or deliberately remap IDs. Never rely on headings or page numbers alone. |
| Immutable snapshot ID plus canonicalized-content hash and passage offsets | Reopens the precise edition and detects drift; offsets are stable inside that immutable representation. | Offsets are brittle against normalization/extraction changes; hash is a verifier, not a location by itself. Keep extractor/normalizer version and a readable fallback locator. |
| W3C quote selector (exact text plus prefix/suffix) attached to an immutable edition target | Can relocate a passage after movement; model also supports position selectors. The W3C spec calls position selectors brittle when the resource changes and recommends state to identify the representation [S13]. | Quote text duplicates content into the reference and can itself reveal restricted information; do not put it in a public URL or unprotected log. A quote is a locator, not permission. Resolve only after reauthorization. |
| Live-document URL, heading path, page number, or offsets into the current edition alone | Convenient navigation. | Does not identify the edition/passage the user saw, can move or retarget after updates, and may leak titles or contents. Not an immutable citation. |
| Opaque citation token resolving server-side | Short pasteable reference with no exposed title/snippet; server can enforce current access and preserve version binding. | Requires durable resolver, retention policy, availability, and careful token design; token possession alone must not grant access. |

Recommended citation record: citation ID; source-system/document ID; immutable edition ID and publication/effective date; stable passage/block ID; displayed heading path as metadata; snapshot/content hash and extraction version; exact display/copy timestamp; locator strategy and fallback; and a “newer edition exists” relation/status. Include only non-sensitive or permitted human-readable text in the pasted form. On resolve, check current access first, then render the target edition and a distinct current-version notice. If the passage was removed, give an authorized, non-content-bearing tombstone such as “this cited passage is no longer available in edition X”; if policy permits, identify the archived edition or nearby retained context. Do not silently substitute a different passage or claim removal revokes already-exported copies.

## Permission changes and caches

Use the enterprise document/identity policy as the authorization source of truth; search indexes may hold candidate ACL labels but are derived and can lag. Compose ACL filtering into retrieval, then recheck current access for each candidate before retrieving or returning title, snippet, body, citation preview, autocomplete/suggestion, counts, or an open/copy action. Do not first fetch snippet fields to an untrusted client and hope to redact them. Fail closed on unknown identity, stale ACL generation, failed policy check, or inability to establish revocation freshness. Define a revocation SLA and invalidate index documents, application caches, browser/service-worker caches, and derived snippet caches against an ACL version/epoch; an unbounded positive cache cannot meet immediate revocation. Cache keys must include principal/entitlement epoch, document ACL generation, edition and index generation, or avoid caching sensitive result payloads. Keep logs and metrics free of restricted titles/snippets and avoid revealing restricted hit counts.

These are design requirements, not guarantees from any vendor. PostgreSQL row security defaults to deny when enabled with no policy, but table owners typically bypass it and superusers/BYPASSRLS always do; multiple permissive policies combine with OR [S03]. OpenSearch DLS filters read retrieval, not writes, defaults to adaptive evaluation, and DLS conditions across roles have non-obvious OR/override behavior; identifiers with punctuation need exact keyword treatment [S09]. Elasticsearch documents also warn that DLS alone can still expose aggregate facts about restricted records (e.g., terms/counts) and that cache behavior has specific exceptions [S14, S15]. Therefore keep aggregates/suggestions on the protected path and validate the chosen engine/version, roles, request shapes, caches, revocation propagation, and failure modes. These implementation examples do not prove another engine shares those behaviors.

## Index freshness and currency

Maintain a source revision/event sequence and explicit ingestion status. A change should atomically mark prior index content stale for currency while enqueueing extraction, section/passage mapping, optional embedding, ACL hydration, and indexing for the new immutable edition. Track per-document indexed revision and ACL generation. When complete, validate required fields/counts, then switch active index generation/pointer atomically where available. Do not expose the new edition as searchable until it is queryable and permission-filtered. Show “rebuilding,” “index delayed,” or “index failed” with an as-of timestamp; make any older result visibly older and link it to its actual edition. The resolver should distinguish current, superseded, withdrawn, missing, and restricted states. Current authorization overrides the fact that an old edition was once visible.

## Failure and release history

pgvector’s issue #719 records pgvector 0.7.0 returning no rows for a filtered HNSW query when nearest neighbors failed an additional file filter; a maintainer recommended upgrading to 0.8.0 for iterative scans and suggested B-tree filtering for highly selective conditions [S06]. The v0.8.0 changelog records iterative scans and improved cost estimation for filtering. A separate 0.8.0 issue #785 reports underfilled results and latency trade-offs under filters despite parameter changes; it was closed after requests for EXPLAIN/data counts and suggestions to add B-tree on the filter and adjust HNSW settings, not a documented code fix. Do not interpret “closed” as proof the behavior was fixed [S07]. Pin installed versions and add query-plan, recall, underfill, and latency checks when evaluating pgvector. v0.8.7 (2026-10-01, tag commit f37c13f) includes an IVFFlat build buffer-overflow fix; v0.8.3/v0.8.4 changelog entries include HNSW vacuum-corruption/repair and insert-vacuum fixes. These are lifecycle evidence for index build/maintenance, not proof of current behavior for this workload [S05].

OpenSearch’s pinned 3.8 docs say RRF was introduced in 2.19 and score normalization in 2.10; RRF discards score magnitude and its score should not be thresholded or compared across queries [S08]. OpenSearch 3.8 docs are marked no longer maintained at access; any implementation must be rechecked against the selected maintained release [S08–S12]. The docs distinguish filtered ANN modes and list engine/version support [S10, S11], while index aliases provide an atomic generation cutover [S12]. This is mechanism evidence, not a product selection.

## Clause coverage and validation status before plan release

This discovery covers: changing documents and multiple editions; moved headings; variable team permissions; retrieval trade-offs; durable passage identity; visible edition currency; current authorization and cache invalidation; eventual index visibility and rebuild state; removed passage behavior; ranking versus policy authority; live URL limits; private-data handling; and the irreversibility of exported copies.

No synthetic corpus, real organizational corpus, authorization harness, provider service, or search cluster was run. Therefore all relevance measurements, authorization/revocation/cache tests, latency/load tests, and organization-specific policy decisions remain **proposed**, not executed. Proposed next checks: construct a small synthetic set containing exact control IDs, paraphrases, a moved heading, two editions, one withdrawn passage, and users with intersecting/disjoint access; compare lexical-only, dense-only, and hybrid rankings; assert no result metadata/content for denied users before and after a revoke; test caches/autocomplete/counts and missing-policy fail-closed behavior; simulate rebuild delay/failure and alias/generation cutover; verify citations reopen exact edition/passages and show newer/removed states. Real-corpus relevance and policy boundary decisions require the content/records, security, identity, privacy, and policy owners.
