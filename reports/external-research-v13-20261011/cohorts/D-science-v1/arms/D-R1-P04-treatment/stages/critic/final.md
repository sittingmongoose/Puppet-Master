# D-P04 — Source-backed component proposal and exact plan disposition

**Run/stage:** D-R1-P04-treatment / independent critic-finalizer  
**Scope:** the complete D-P04 brief and only the frozen released plan in revealed-plan.md.  
**Status:** design proposal; no collaborative editor or service was changed. Source IDs and exact URLs are navigable in sources/index.md; the source map retains investigator records and separately records this stage’s checks.

## Recommendation

Model comment anchoring as a domain component beside the layout merger. Synchronization can merge geometry, hierarchy, order, and edits; it cannot by itself decide whether a person meant a thread to move to a replacement or split object. Keep original target identity and context immutable. Store current attachment as a separate, explainable resolution history.

A live object with the same incarnation key may carry its local anchor through a known move, resize, rotation, grouping, or reparenting transform. If identity or coordinate mapping is uncertain, preserve the original anchor and surface an unresolved or partial state. Never infer identity solely from proximity, label, bounds, or a matching drawing. Keep a thread available even when its target is hidden or deleted.

Loro’s Rust movable-tree API is a credible first candidate to compare for hierarchy and grouping because it supports create/move/delete operations, stable tree-node IDs across moves, and enumeration of deleted nodes [LORO-RUST-TREE-1.16.2]. That is a structural fit, not proof of comment semantics, snapshot interoperability, storage suitability, or superiority over other engines. Evaluate it alongside Automerge, Yrs/Yjs, a revisioned command sequencer, and an app-owned event/revision model before selecting a sync architecture.

## Identity, anchors, and resolution

Use an unambiguous **entity-incarnation ID** for every shape, connector, group, and review thread. The ID is immutable and never reused for a replacement or restored incarnation. This proposal uses one ID per incarnation rather than a second generation field; a logical lineage key is optional if a product query requires it. A copy or same-looking replacement receives a new ID. Optional replaces, split_from, or restores links describe lineage but do not transfer comments automatically.

A thread keeps its original target kind and ID or ID set, creation revision/frontier, an object-local point/path/region where applicable, the coordinate-frame identity/version, and only original display context permitted by the retention policy. A connector anchor names the connector incarnation and retains the endpoint incarnation IDs. A selected region retains its plan-frame geometry and selected object IDs/intersections at creation. An empty selection remains a canvas-region anchor; it does not silently become an anchor to objects that later overlap it.

On explicit restore, create a new incarnation and record a restores link plus actor, revision, and reason. An old delayed update remains pending against the old incarnation. A separate authorized resolution event may attach a thread to the restored/replacement ID; it records the old and new IDs and keeps the historical target visible. Whether the author, an editor, or a moderator may authorize that action is an owner decision.

A conceptual record should include:
- thread ID and author/reply context only as permitted by policy;
- creation revision or frontier;
- immutable original target kind and incarnation ID set;
- local point, path, or region and coordinate-frame ID/version;
- minimal original context allowed by retention policy; and
- append-only resolution events with status, revision, reason, actor, candidate IDs, and confirmer.

A live known incarnation can follow transforms automatically when the transform is defined and invertible for the anchor. A hidden/collapsed target remains reachable in review navigation. A missing endpoint, ambiguous split lineage, changed coordinate frame, concurrent move/delete, or deleted/replaced ID remains unresolved or partial until an authorized person decides. A ranked candidate may help, but coordinates alone cannot commit it.

## Merge approaches and different guarantees

| Approach | Merge and ordering capability | What it does not decide | Fit and limit to validate |
|---|---|---|---|
| **Loro movable tree plus application data** | Rust API models hierarchy, moves and delete; tree nodes retain IDs and deleted nodes can be enumerated. The maintainer documents concurrent delete/move, competing parents, cycles, ancestor deletion with descendant movement, and fractional sibling order [LORO-RUST-TREE-1.16.2; LORO-MOVABLE-TREE-ARTICLE-2024]. | Whether a thread follows a replacement, split child, or hidden descendant. A tree ID and fractional order are not a product comment policy. | First candidate to compare for groups. Test pinned Rust API, node metadata on deleted/hidden descendants, moves/cycles, snapshot round trips, and whether relative sibling order meets layer-order needs. JS loro-crdt 1.16.4 has a tree snapshot decoder fix; that is a cross-language regression signal, not evidence Rust 1.16.2 has the same defect [LORO-RELEASE-JS-1.16.4]. |
| **Automerge map/list CRDT** | Offline changes merge through a change graph; map conflicts can expose concurrent values, and list entries have operation identity. Rust crate documentation is available [AUTOMERGE-RUST-0.12; AUTOMERGE-DATA-CURRENT; AUTOMERGE-CONFLICT-CURRENT]. | Comment reassignment and deletion intent. A deterministic merged value is not a human decision. A later assignment removes alternatives from the current getConflicts() view, while full change history is a separate retention concern [AUTOMERGE-CONFLICT-CURRENT; AUTOMERGE-HISTORY-MODEL-CURRENT]. | Fine-grained entity records are a candidate schema. A concurrent map delete plus new value yields the new value, so model product tombstones explicitly [AUTOMERGE-MAP-MERGE-CURRENT]. Measure history growth and choose compaction/export policy for the workload. |
| **Yrs/Yjs shared types** | Rust/JavaScript compatible shared map, array, and text updates; state-vector sync; StickyIndex/RelativePosition follow sequence positions through insertions [YRS-STICKY-INDEX-0.28; YJS-RELATIVE-POSITION-CURRENT]. | Sequence anchors do not name shapes. Resolution may return no position for a deleted/unavailable type. Offset units and GC settings affect cross-runtime behavior and recoverability [YRS-DOC-OPTIONS-0.28; YJS-GC-INTERNALS-MAIN]. | Good for text/range subcomponents and Yjs interop; specify byte/UTF-16 behavior and test deletion, undo/redo, empty sequences, and serialization. Keep product deletion events outside engine GC. |
| **Revisioned central command sequencer** | One authority can sequence structural commands, validate cycles, and retain rejected commands for review. This can simplify ordering and server-side authority. | Offline acceptance and author intent for comment anchors. A sequencer still cannot infer that a replacement is semantically the same target. | Alternative if audit authority and invalid-move policy outweigh immediate disconnected writes. It needs membership, retry, authorization, and pending-command decisions. Not selected. |
| **Custom event log / snapshot merge** | Stores domain operations and causal bases; a reducer can represent pending delete/edit branches and project a read-only snapshot. | No built-in semantics for intent, access control, replay migration, or safe retention. | Offers domain control with higher implementation, migration, replay, storage, and compaction burden. A simpler snapshot three-way merge is another option but exposes same-object conflicts for user resolution. Not implemented or benchmarked. |

**Boundary:** first apply/merge layout operations and retain causality or alternatives required for review. Separately resolve comment intent. Preserve concurrent operations even when a renderer needs one deterministic display state. Synchronization convergence and referential intent are separate guarantees.

## Deletion, offline edits, history, and privacy

Record product deletion as an explicit event with target incarnation, causal revision, and actor/reason when policy permits. Preserve a tombstone or identity barrier so an old peer cannot make a deleted incarnation visible by replaying a stale edit. Keep delayed edits as pending input against the old incarnation. Do not discard them merely because the live layout has moved to a later checkpoint.

Before compaction, define replica identity, admission/removal/revocation, acknowledged frontiers, maximum offline periods, and the rule for updates from retired epochs. If an old update arrives after a checkpoint, quarantine it without destroying its operation data, then offer a visible rebase/merge, export, or discard decision. Never apply it as an automatic restore. Whether an expired device’s edits can be imported and who may resolve the resulting conflict remain product-owner choices.

Separate a minimal tombstone/identity barrier from sensitive history. Retain detailed geometry, labels, authors, replies, and event data only as long as permitted. Automerge documents retain full change history by default; Yjs can garbage-collect deleted content; Yrs 0.28.0 defaults skip_gc to false, meaning commits should try GC [AUTOMERGE-HISTORY-MODEL-CURRENT; YJS-GC-INTERNALS-MAIN; YRS-DOC-OPTIONS-0.28]. These engine behaviors do not define product retention or legal erasure. If policy requires erasing context, remove it from stores and exports and report that context is withheld; preserve only a permitted non-sensitive status/barrier if allowed. No storage growth or erasure behavior was measured here.

For an outside reviewer, produce a deterministic read-only projection: snapshot/revision ID, visible layout, every thread including hidden/deleted/unresolved targets, original target kind and IDs, current status and plain-language reason, and confirmed reattachment provenance. Include original/current geometry only where permitted. A screenshot is an optional visual preview, not a substitute for the semantic manifest. Do not export raw CRDT history or unrelated/private/deleted data by default; specify redaction for names, replies, author identifiers, and historical geometry. An export must not sync back into an editing session.
