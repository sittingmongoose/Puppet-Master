## Recommended proposal and state boundaries

### Backup snapshot and publication

1. Capture a logical workspace generation while writes are paused or through an immutable app snapshot. Record its generation ID. Records, attachments and preferences must all come from that same generation.
2. Build an expected manifest before copying payloads. Include archive and source app/schema versions, workspace ID, stable record/resource IDs, relationships, expected member paths, sizes and selected cryptographic digests, plus explicit exclusions and source-side missing resources. Package paths must not contain machine-specific absolute paths.
3. Write to a private temporary package. Reject duplicate paths, traversal/absolute paths, links/devices unless explicitly represented, unsupported compression, excessive member count/expanded size, and decompression resource abuse. Enforce limits while streaming; do not trust archive metadata alone.
4. Close, reopen and compare the package with the expected manifest. Verify exact set equality, lengths and digests; detect extra/missing/duplicate/corrupt members; check relationships and required preferences. CRC or container read success is weaker than a cryptographic digest and neither validates app behavior.
5. Publish a complete verified generation beside the current archive. Update “latest full/current protection” only after publication succeeds. Keep prior archives and marker intact if cancellation, source change, full disk, removable-media loss or verification failure occurs. If input attachments were already unavailable, retain their broken-reference status in the manifest but mark the package degraded; whether export fails or offers a degraded copy is an owner decision.

An unauthenticated manifest digest can detect accidental change only while the manifest is trusted. For tamper detection, authenticate the manifest or use authenticated encryption/signatures. Keep authenticity, integrity, completeness and successful extraction as distinct claims.

### Restore and merge

1. Parse the minimal outer header and enforce size limits before expensive work. If protected, decrypt/authenticate the full package into private staging. Never upload archives. Keep member names and the manifest encrypted when the user expects metadata privacy.
2. Validate format version, expected member inventory, hashes, references, source omissions and resource IDs. Report separate states: cannot parse; unsupported version; authentication failed; valid but degraded source snapshot; missing/damaged member; byte-verified package.
3. Restore into a separate candidate workspace. For an empty workspace, preserve the current workspace and open/read the candidate before switching. For newer app schema, migrate the candidate in documented steps after archive verification; log migrations and revalidate. Unknown newer schema or a failed migration stops without live changes.
4. For merge, preview stable-ID differences and ask for deliberate choices on record conflicts, deletes/updates, same-name/different-byte attachments, identity collisions, unresolved references, preferences and version conflicts. Preserve source and destination detail. Any “keep both” action gets a new identity and explicit reference rewrites. Never silently replace by filename.
5. Validate the candidate database, app-level records/references, resource bytes, migration results, and ability to open/read before changing the selected workspace. Commit by a generation switch or tested journaled transaction; retain the previous workspace until a post-commit smoke check passes. Database-only atomicity is not mixed-workspace atomicity. Cross-platform crash and durability behavior remains a verification obligation.

### Passphrase and other protection choices

- **No encryption:** easiest to open with ordinary tools and no password-loss issue, but anyone with the archive can read it.
- **Passphrase envelope:** convenient for removable storage. Password strength, offline guessing, KDF performance and long-term compatibility matter. Use an audited authenticated-encryption/KDF implementation with versioned parameters. A forgotten sole passphrase has no reset path; do not imply otherwise.
- **Recipient-key envelope:** avoids memorizing a per-archive password and can support multiple explicitly configured recipients, but users must preserve private identities and supported tools. This requires an explicit product decision; it is not a hidden recovery channel.

Wrong passphrase and modified ciphertext can produce the same authentication failure. Ask the user to check both the passphrase and file. If authentication succeeds but the inner archive fails, report inner corruption. If the outer version is parseable but unsupported, report that separately. Even encrypted packages may expose crypto/version metadata, size and timing. Encryption does not prove the source included every intended item or that the migrated app can use the restored data.

## Comparison of approaches

| Approach | Strengths | Costs/risks | Fit |
|---|---|---|---|
| Self-contained whole-workspace package | Portable on removable media; stands alone; easy to count, hash, diagnose and preview. | Larger writes; needs one coherent snapshot; app owns path safety and migration compatibility. | Recommended v1 baseline proposal. |
| Raw database copy plus resources folder | Fast and can preserve original layout. | WAL files matter; database/resources may come from different moments; poor portability and weak atomic restore; schema tied to app. | Only with documented quiescence/backup API and coordinated immutable resource generation. |
| TAR/ZIP container | Standard tools and libraries; one file is convenient. | Does not define app references, migration, complete member list, or merge semantics; path, duplicate-name, compression and limit hazards; CRC is not authenticity. | Viable container layer with a strict manifest and safe extraction; package not selected. |
| Content-addressed incremental repository | Deduplicates content and stores many snapshots efficiently. | Requires repository metadata/objects and compatible tools; full verification can be costly; change-detection rules and restore defaults matter; still needs app-aware preview/migration. | Optional later mode with full anchors and verification of required objects. |
| Direct restore into live workspace | Less staging space; superficially simpler. | Interruption can leave partial state; overwrites and deletes are hard to undo; no cross-resource transaction. | Reject as user-facing default; only consider a journaled alternative after fault testing. |
| Staged candidate/generation restore | Isolates failures and migrations; supports meaningful preview and rollback. | Requires temporary storage and a commit protocol; generation switch must be proven on supported filesystems. | Recommended restore direction. |

## Already covered, rejected, and uncertain

**Already covered:** structured record/preference export, copied attachments, manifest digests, temp extraction, preview, new-workspace and merge modes, stable record identifiers, whole-package passphrase option and the plan's requested witnesses. The brief additionally requires included/excluded inventories, incomplete backup status, missing-member detection, same-name/different-byte handling, unavailable references, future-schema migration, no upload, no live deletion before verified restore, and distinct evidence levels.

**Rejected or corrected:** archive close/readback as proof of a consistent snapshot; updating the current marker without full inventory/hash/reference verification; exporting across racing edits; attachment filenames as identity; path renaming without reference remapping; updates selected by identifier alone; one generic error for unsupported version, authentication, damage, missing members and migration; direct extraction into live workspace; implicit recovery after forgotten passphrase.

**Uncertain / owner choices:** whether source-side missing attachments abort export or permit an explicitly degraded archive; preference categories and sensitive machine-local values; merge/replacement and delete policy; stable identity/remapping rules; supported archive/schema window; full-only v1 or later incremental support; crypto package, KDF, cipher and key management; whether a user-controlled second recipient/recovery key is offered; cross-platform commit/rollback protocol; required staging space and rollback retention; definition of app-level smoke verification.
