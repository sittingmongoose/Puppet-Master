# Independent discovery — D-P03

Stage: investigator, run D-R1-P03-control. This was developed from the released user brief before reading the exact plan. The exact plan has not yet been released or inspected. No archive or storage product is selected. Research pages were accessed 2026-10-12 04:18–04:21 UTC; the source index records a UTC access timestamp for each page review. This is a proposal-stage synthesis, not an implementation result.

## Initial direction from the brief

Treat backup creation and restore as staged workflows with explicit evidence and terminal states. A portable self-contained archive is the simplest baseline to move by removable media and restore onto an empty machine. It should contain one versioned manifest plus opaque-ID-addressed record, preference, and attachment payloads. Use a stable record/attachment identity in metadata; original filenames remain display metadata, never the key used to pair or replace attachment bytes. Preserve two attachments with the same basename but different digests. A same-ID, changed-content or same-name/different-content condition should appear in preview as a conflict requiring a deliberate choice.

Capture an expected inventory from a consistent workspace view before copying payloads. The manifest should record archive/schema format, producer application/schema version, workspace identifier, item kinds and stable IDs, each expected member's relative package path, byte size and cryptographic digest, record-to-attachment references, preferences included, and every excluded or unavailable object with a reason. Compare this inventory against actual package members on verification. A clean container and matching member digests establish byte-level consistency only against that inventory; they do not prove the inventory was complete relative to the live workspace or that the application can use the data. Record source-side missing attachments separately and mark any archive with omissions/degraded input as not full protection. Do not update a “latest good/current protection” marker until export has finished, inventory and all member hashes match, and publication has succeeded. Preserve the preceding complete archive on failure or interruption.

A database snapshot is only one constituent of a workspace snapshot. If SQLite is selected, use its online backup API or an application-controlled quiescent copy; do not copy a live main database file as if it were self-contained. In WAL mode the WAL is persistent state until cleanly checkpointed/deleted; separating it from the database can lose committed transactions or corrupt the copy. Coordinate database rows, attachment files, and preferences under an application-level freeze/versioned snapshot so the archive cannot combine metadata from one point with blobs from another. SQLite transactions cover database state, not arbitrary files in the workspace. An application-level referential walk must detect missing external attachment bytes even if database integrity checks pass; SQLite foreign-key enforcement is connection-scoped and off by default unless enabled.

Package selection remains open. ZIP is broadly recognizable and libraries expose CRC/header checks, but ZIP member paths, duplicate names, compression support/version compatibility, resource limits, and extraction interruption need explicit policy. TAR is also a plausible unencrypted package container (Joplin JEX is a product example); neither container alone establishes application-level integrity. A custom manifest/container may make identity, required members, migration metadata, and integrity state explicit but adds format/version compatibility burden. A whole archive is easy to copy and independently retain; an incremental content-addressed repository such as restic offers deduplication and many snapshots but requires its metadata/object set to remain available and a separate application-aware import/preview layer. A practical alternative is to make every exported archive self-contained initially, and consider repository-style incrementals only as an optional advanced mode with full-snapshot anchors and chain verification.

## Restore and schema strategy to investigate

For a new empty workspace, validate the source archive, build a candidate workspace in a separate staging location, run migrations on the candidate only, then check application-level invariants and open/read the candidate before a short commit step. Keep the current workspace untouched through extraction, migration, relationship checks, and preview. For an existing workspace, distinguish an explicit merge from replacing/restoring a whole workspace. Preview stable-ID matches, inserts, updates, tombstones/deletes (if ever supported), same-name/different-byte resources, duplicate logical records, newer/unsupported schema versions, unavailable referenced resources, and any policy that would skip or overwrite. Prefer “keep both / remap identity” or user-selected replacement when identities/contents differ; never silently replace a file because its name matches. Unknown forward schema or failed migration should stop before live changes. A migration should be run against a staged copy and its outputs revalidated; migration is not extraction and does not become true merely because the container opened.

A proposed publication boundary is a whole-workspace generation/pointer swap after staging, so the restored database, resources and preferences become visible together. If a platform cannot provide that boundary, define a journal/rollback protocol and retain the pre-restore generation. The exact guarantees of rename/flush/power-loss behavior vary by platform, filesystem, and storage device and have not been proven here; require platform-specific crash/fault tests before claiming atomic restore. Do not run a destructive in-place extraction against the live workspace. Restic 0.19.1 is a useful counterexample: in-place restore defaults to overwrite, and docs warn that interruption can leave a partial restore.

## Evidence lessons and open questions

- ZIP `testzip()` reads every member and checks CRCs and headers, returning the first bad member. This catches certain damaged bytes, but by the method's stated contract it does not check that the archive has the app's complete expected member set, that records refer to present resources, that migrations succeed, or that restored behavior is usable. CRC is not a cryptographic authenticity guarantee. Reject duplicate package paths; validate archive member names and bound decompressed bytes/counts before writing.
- SQLite `integrity_check` is a low-level database-format/index check. It is not an app-level consistency check; references to external blob files need their own check. Online Backup API produces a consistent database snapshot despite concurrent writes, but a write-heavy source can repeatedly restart it and delay completion. Use progress/cancel reporting and preserve prior protection.
- A content-addressed incremental product gives a useful comparison, not a turnkey solution. Restic's path/metadata change detection has stated conditions; its restore defaults and interruption behavior differ from the required safe live-workspace flow. Verification must include both metadata structure and data reads, and full check may be costly. A successful extraction can still be wrong app schema or missing attachments.
- Joplin demonstrates both a JEX TAR export described as lossless and practical caveats: a 2.12.2 Android report describes non-ASCII text damaged in JEX; a 3.5.13 issue says importing JEX as “restore” can duplicate existing notes; a Windows issue shows absolute resource URLs producing broken references and omissions from JEX. A linked 2023 PR addressed a narrower WYSIWYG-to-Markdown paste path that converted absolute image paths to internal links, not every possible broken resource. These are product-specific examples, not proof that every JEX behaves this way.
- Public repair history for Joplin importer issue #12049 (3.3.3) shows files without extensions could be changed or omitted; PR #12974 merged a path-function change into `dev` on 2025-09-08 as commit `c27d542`. The PR record describes automated and manual checks, reviewer requests for importer integration coverage, earlier failing checks, and eventual 11 passing checks. This supports testing path and identity edge cases at importer level; it does not prove the application here needs Joplin's fix.
- Restic issue #2960, reported on restic 0.10.0, states SIGINT interruption can leave stored blobs/index data but no visible snapshot, with data only recoverable by a later `recover` operation. Treat “some bytes uploaded/written” and “complete usable backup published” as separate states.

## Provisional validation questions (none executed)

Proposed synthetic checks: interrupt export at each phase and verify that the previous good archive remains the current protection; remove, truncate, alter, duplicate, or add a member and verify diagnostics distinguish missing/corrupt/extra members; test malicious paths, duplicate names, very high compression ratios, size/count limits, unsupported compression, and names with Unicode, spaces, no extension, and platform-reserved characters. Exercise two different attachments with the same filename, same bytes under two names, dangling record references, unavailable source attachments, and duplicate logical records. Verify empty restore and each merge choice against an inventory of expected IDs and hashes. Migrate fixture archives from older supported schema versions into a staging workspace; refuse unknown newer versions without live writes. Inject disk-full, permission, removal, process-kill, and power-loss approximations at staging and publish boundaries on every supported OS/filesystem. Test encrypted archives with correct/wrong passphrase and ciphertext alteration, and document that forgetting the only recovery secret yields no product recovery path unless a deliberately designed user-controlled second recipient/recovery key is added. These tests are proposals; none was run in this research stage. Future migration, fault-injection, and real user-data tests remain proposed.

Open owner choices: exact inclusion/exclusion policy for machine-specific preferences and secrets; replace/merge/restore semantics and conflict defaults; supported archive and schema compatibility window; whether version 1 is self-contained only or also supports incrementals; encryption algorithm/KDF/package and any user-controlled recovery key; whether a known-missing source attachment makes export fail or emits an explicitly degraded archive; staging space and restore rollback retention; whether post-restore app-open/smoke verification is sufficient or a richer semantic validator is required. Do not resolve these by assuming a selected product.
