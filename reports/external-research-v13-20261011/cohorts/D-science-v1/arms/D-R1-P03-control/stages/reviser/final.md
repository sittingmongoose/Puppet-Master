## Proposal at a glance

Use a self-contained whole-workspace archive as the first portable-backup proposal, built from one application-consistent generation and described by an expected manifest. Treat source completeness, archive integrity, successful extraction, schema migration, referential integrity, and a usable restored workspace as separate states. Do not call an archive current full protection just because it closed or its manifest can be read. Publish and promote it only after comparing the complete expected inventory with the package, verifying member bytes and references, and successfully publishing a complete generation; retain the preceding good archive and marker on interruption or failure. A source snapshot with unavailable items is degraded and cannot be represented as complete protection.

Restore into a private staged candidate, validate and migrate there, show an item-level preview, and commit a workspace generation only after validation. Offer a clean-workspace restore and a deliberate merge mode. Stable identifiers and references matter; attachment names are labels. A same-name/different-bytes attachment or same-ID/changed-content item is a visible conflict, never an implicit replacement. Keep passphrase protection optional pending an owner choice and package review; a forgotten sole passphrase has no recovery promise. These are proposals, not implementation findings or owner decisions.

## Backup proposal: consistency, inventory, and publication

1. **Capture one logical generation.** Pause writes or request an immutable/versioned application snapshot. Bind records, attachments, and preferences to the same generation identifier. Do not infer a consistent cross-resource view from a closed archive. SQLite's Online Backup API can produce a database snapshot under its documented conditions, but does not include arbitrary files; a database generation must be coordinated with the resource/preference generation [SRC-SQL-BACKUP]. In WAL mode, a copied live database may depend on its companion WAL, so do not split those files and call the result a verified workspace snapshot [SRC-SQL-WAL].
2. **Create the expected inventory before packaging.** Record format version, producer application/schema version, workspace identity, item kinds and stable IDs, record-to-attachment references, expected package-relative member paths, sizes, and selected cryptographic digests. Record included preference categories, explicit exclusions, and source-side unavailable items with counts and reasons. Avoid machine-specific absolute paths. The inventory itself needs an application-level completeness rule; checking only the entries it already contains cannot prove it enumerated every live object.
3. **Write privately and enforce limits while streaming.** Reject duplicate package paths, absolute/traversal paths, and unsupported links or devices unless the format defines them. Set bounds on member count, expanded bytes, individual sizes, and decompression work. Do not trust uncompressed-size metadata alone. Test names with Unicode, spaces, no extension, and platform-reserved characters. If ZIP/Python is chosen, testzip() reads each member and checks CRCs/headers, but CRC is not cryptographic authenticity, the method does not compare the app's expected set, and archive path safety remains the caller's responsibility [SRC-PY-ZIP].
4. **Reopen and compare before publication.** Compare actual package paths exactly with the expected manifest; reject duplicate, extra, missing, or corrupt members. Verify byte sizes and digests, record/resource references, and required preferences. A digest is an integrity check against a trusted manifest; if an attacker can rewrite both payload and unauthenticated manifest, it is not an authenticity guarantee. Authenticate the manifest or protect the full package when tamper detection is required.
5. **Publish and promote only a complete generation.** Keep the prior archive and marker while writing, verification, and publication occur. Update the “latest full/current protection” marker only after a complete verified generation is durably published according to a platform-specific contract. A package that intentionally preserves known source omissions may be retained as degraded but must not be labeled full protection. Cancellation, source changes, disk-full, removable-media loss, and verification failure leave the prior full marker untouched. “Bytes written” and “manifest readable” are not terminal success states [SRC-RESTIC-INTERRUPT].

## Restore proposal: validation, migration, preview, and commit

1. **Parse a bounded header first.** Enforce package-size limits and identify the format/crypto version before expensive work. If encrypted, authenticate/decrypt to private staging; do not upload archives. Keep names and the manifest encrypted if the user's privacy expectation includes metadata.
2. **Report independent evidence states.** Distinguish: cannot parse; unsupported format/crypto version; unable to authenticate; valid but degraded source snapshot; byte-verified expected members; extracted candidate; supported schema; migration completed; database integrity checked; foreign-key constraints checked where applicable; external references resolved; application can open/read the candidate; and committed workspace. These are not interchangeable claims. SQLite integrity_check does not check foreign keys; use foreign_key_check separately, and separately check references to external attachment bytes [CRIT-SQLITE-PRAGMA-INTEGRITY]. If SQLite is selected, explicitly enable foreign-key enforcement on each connection where required; the documented default is OFF unless a compile-time option changes it. A foreign-key check still does not find missing external attachment files [SRC-SQL-FK, CRIT-SQLITE-PRAGMA-INTEGRITY].
3. **Restore into a separate candidate.** Verify exact members, paths, sizes, hashes, source omissions, stable IDs, and references before applying data. For a clean workspace, construct a candidate generation while retaining the current empty generation. For a newer application schema, migrate only the candidate after archive validation, log each migration, and rerun invariants. Stop on an unknown newer schema or migration failure before any live change.
4. **Preview before merge or replacement.** Show item-level additions, updates, unchanged values, identity/content conflicts, same-name/different-byte attachments, missing or unavailable references, orphans, skipped items, preferences, and any delete/replace effect. Provide the reasons and source/destination values needed to choose. Do not silently overwrite by attachment filename. A “keep both” action allocates a new ID and rewrites all affected references; any field-level record merge needs explicit semantics. Keep delete behavior an owner decision.
5. **Commit a whole candidate generation.** Prefer a tested generation/pointer switch so database, resources, and preferences become visible together. If a platform cannot provide that boundary, define a journaled commit/rollback protocol and retain the pre-restore generation. Do not delete the live workspace before candidate validation and successful open/read checks. Retain rollback through a post-commit smoke check. SQLite's documented database atomicity does not establish a mixed database/files atomic swap or crash-durability guarantee on every OS/filesystem/device [SRC-SQL-ATOMIC]. Platform-specific crash and durability tests remain required before making such a claim.

### Merge identity and references

Use stable record IDs as one input, together with content/version and relationship comparisons. Give attachments their own stable IDs and content digests; a filename is only a label. Preserve separate attachments that share a basename. Surface same-ID/changed-content, same-name/different-content, logical duplicate records, and dangling references as explicit conflicts. A path rename is not sufficient to preserve referential integrity; remap IDs and all referring records together. Do not invent automatic field-merge, deletion, or replacement semantics.

Joplin's issue #14791 is a user report about confusion between additive JEX import and replacement. Its proposed warning specifically conditions duplicate creation on enabling sync after import when the same notes already exist on another device; the report is useful as a UX example, not as a general import guarantee or a specification for this product [SRC-JOP-JEX-IMPORT-DUP]. Joplin's import/export documentation describes JEX as a TAR package and calls it lossless for notes and selected metadata; its ENEX discussion says some links lack IDs and may be reconstructed by title guesses, with ambiguity able to fail. These are Joplin format semantics, not guarantees for this product [SRC-JOP-IMPORT-EXPORT]. A Joplin Android 2.12.2/Android 10 issue reports non-ASCII corruption in JEX; its linked PR details and release status were not verified. A Windows Joplin 2.7.13 issue reports absolute resource paths and missing JEX images; the linked PR is narrow to pasting from WYSIWYG into Markdown and does not establish a universal fix. These historical reports motivate cross-platform Unicode/reference tests without implying a defect here [SRC-JOP-JEX-UNICODE, SRC-JOP-ABS-PATH, SRC-JOP-ABS-PATH-FIX]. The extensionless-file PR changed path helpers, called for an importer integration test, received review feedback about testing the import path, later added an issue-shaped fixture, and merged as c27d542 into Joplin dev on 2025-09-08 with 11 checks reported passed. The release containing it was not verified; this is repair history, not evidence of a current defect here [SRC-JOP-PATH-FIX].

## Protection choices and limits

- **No encryption:** simplest to inspect and no lost-password problem, but anyone with the archive can read it.
- **Passphrase envelope:** convenient for removable media. Password strength, offline guessing, KDF cost bounds, platform support, and long-term parameter compatibility matter. Use an audited authenticated-encryption/KDF implementation only after review. A forgotten sole passphrase has no reset path; do not imply otherwise.
- **Recipient-key envelope:** avoids memorizing a per-archive password and permits explicitly configured recipients, but the user must preserve private identities and compatible tools. Any second recipient/recovery key must be a deliberate user-controlled choice, not a hidden recovery channel.

The age v1 format is a concrete comparison: its specification describes scrypt-based passphrase wrapping and ChaCha20-Poly1305 wrapping of a random file key, and says implementations should bound the work factor [SRC-AGE-SPEC]. Its CLI illustrates passphrase and recipient/identity workflows, not a library selection or desktop key-management solution [SRC-AGE-CLI]. Whole-package encryption does not prove source completeness, successful migration, or workspace usability. Even protected packages may expose a format/crypto header, file size, and timing. Authentication failure alone may not distinguish a wrong secret from altered ciphertext; that is an inference about the available verification signal and needs cryptographic review. Use wording such as “could not authenticate; verify the passphrase and archive,” not a diagnosis of either cause.

## Strategy comparison

| Approach | Strengths | Costs and risks | Proposed fit |
|---|---|---|---|
| Self-contained whole-workspace package | Portable on removable media; independently retainable; easy to inventory, copy, and verify. | Larger writes; needs one coherent snapshot; application owns identity, path safety, compatibility, and migration. | First-version proposal. Container not selected. |
| Raw database copy plus resources folder | Can be fast and preserve native layout. | WAL state matters; database and resources can represent different moments; weak portability and mixed-resource commit behavior. | Only with a documented database snapshot/quiescence protocol and a matching immutable resource generation. |
| ZIP or TAR container | Broad tooling and a single file are convenient; JEX is a product example of a TAR package. | Does not define application references, completeness, migrations, or merge semantics; duplicate paths, extraction safety, compression limits, CRC/authenticity differences remain. | Viable container layer with a strict manifest and safe parser; no format chosen [SRC-PY-ZIP, SRC-JOP-IMPORT-EXPORT]. |
| Custom manifest/container | Can make required members, IDs, versions, and integrity state explicit. | Adds parser, format, and long-term compatibility burden; still needs cryptographic and path review. | Compare during format selection; not selected. |
| Content-addressed incremental repository | Deduplicates data and retains multiple snapshots efficiently. | Repository objects/indexes and compatible tools must remain available; full checks may read/download much more data; path change-detection assumptions matter; still needs application-aware preview/migration. | Optional later mode with full anchors and required-object chain verification [SRC-RESTIC-BACKUP, SRC-RESTIC-CHECK]. |
| Direct restore into the live workspace | Uses less staging space and appears simpler. | Interruption can expose partial changes; overwrite/delete effects are difficult to undo; no mixed-resource transaction. | Reject as the user-facing default. |
| Staged candidate/generation restore | Isolates extraction and migration failures; supports preview, validation, and rollback. | Requires temporary storage and a commit protocol whose behavior must be proven on supported platforms. | Recommended restore direction; exact mechanism remains open. |
