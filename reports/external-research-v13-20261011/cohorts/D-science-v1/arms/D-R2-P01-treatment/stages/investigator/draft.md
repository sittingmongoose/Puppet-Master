# Review draft — D-P05

## Recommendation

Revise the provisional design before implementation. Treat **retrieval relevance**, **policy authority/currentness**, **edition identity**, **passage location**, and **authorization** as separate data and decision paths. The search system returns candidates; it must not decide which policy is authoritative. A result's title, heading, snippet, count, or cached passage is itself potentially restricted data.

No engine or document platform is selected. First establish an approved private-data boundary and source-of-truth/auth contract. A practical comparison set is a local PostgreSQL full-text baseline, a maintained full-text engine such as OpenSearch or Elasticsearch, and a smaller scoped-search alternative such as Typesense. These are architecture examples, not recommendations to upload content or to treat engine ACL filters as the source of current permission. The reviewed Azure AI Search push ACL path is preview; it is not a production recommendation and would require explicit data-boundary review [S08–S09].

## Exact clause dispositions

| Plan clause | Disposition | Finding and condition |
|---|---|---|
| Chunks are identified by document ID, edition number, and ordinal position. | **Correct.** | Keep the document ID and an authoritative, stable source revision/version ID. Do not use ordinal position as a durable passage identity: adding text or changing chunk size/order can retarget that ordinal. Persist the chunker/extractor version and canonical content digest for reproducibility. Prefer author-maintained stable block IDs when the source supports them; bind them to a specific edition. Add a quote selector and position fallback for sources without stable block IDs. The W3C model defines quote and position selectors and warns that offsets are brittle and duplicate quote matches may identify multiple spans [S10]. Git’s commit:path can identify a repository blob within an edition, but only for content retained in Git [S15]. |
| Results show title, heading path, and highlighted snippet. | **Conditionally accept.** | These are useful only after permission is confirmed. Title, heading, and snippet can disclose confidential content; do not emit them as an unfiltered candidate payload. First perform current authorization, then retrieve/display permitted fields. Apply the same rule to autocomplete, counts/facets, previews, logs, error messages, cache hits, and citation resolution. |
| A citation stores those fields plus the live document URL. | **Reject as a durable citation.** | A live URL generally opens whatever edition is current later, not the edition and passage the user saw. An edition number and chunk ordinal are not enough unless the source guarantees stable version IDs and stable chunking, which the plan does not establish. Store an opaque citation ID plus source ID, exact source revision/version ID, stable block locator if available, normalized quote selector with surrounding context and position fallback, section path, canonical-text digest, extractor/chunker version, and the user-visible citation creation time. The app should resolve the exact edition with current authorization. A separate link may show a newer edition. Never use an unauthenticated temporary download URL as the durable link: Microsoft Graph documents that its version download URL needs no authentication, is short-lived, and might not be invalidated immediately after permission removal [S11]. |
| “A permission filter would run before results are displayed.” | **Insufficient; strengthen to a fail-closed authorization boundary.** | A query filter is useful defense in depth, but it is not enough when its ACL metadata is stale or when a cached snippet is returned without a new decision. Obtain the caller's current identity and permission from the authoritative identity/policy source before disclosing any result metadata or fetching a passage. If permission or freshness cannot be verified, return no title, snippet, hit count, or cached content; show only a generic access/indexing status. Azure's current documented query path appends filters when enabled, omits protected results without a user token, and returns an error rather than partial results when ACL evaluation fails [S08]. The reviewed push API says indexed access reflects the last ACL written and remains stale until re-ingestion/update [S09]. |
| The index carries team labels, refreshed when a document is reindexed. | **Reject as the sole permission source; use only as a candidate filter.** | A reindex interval is an exposure window after team membership or ACL changes. Define the authoritative permission-change event, how inherited/group changes propagate, and the maximum permitted stale interval. At serve time, validate current authorization for the exact document and edition; filter candidate IDs before returning metadata. If the authorizer is down, fail closed. OpenSearch/Elastic DLS illustrate engine-enforced read filtering, but their role semantics and query limitations need precise configuration. OpenSearch DLS applies to read retrieval rather than writes, uses adaptive evaluation by default, and combines DLS role rules with caveats; its docs warn that text analyzers can conflate identifiers and recommend keyword/custom analyzers for exact values [S05]. Elastic documents an OR-across-roles behavior where a role without DLS can widen access to all documents, and notes that restricted docs may influence global statistics/aggregates [S12]. |
| Cached snippets remain until the next refresh. | **Reject.** | A cached snippet is still restricted document content. It cannot remain servable merely because the search index has not refreshed. Permission revocation must invalidate or bypass affected result/snippet caches before display. Use push invalidation and a bounded cache TTL as backup; bind any retained cache to caller, document edition, and permission generation, and reauthorize before rendering. Do not use cache absence/presence, counts, or score changes to reveal a restricted hit. The plan's “until next refresh” behavior directly conflicts with the visibility requirement. Exported copies remain outside the app's revocation control; state that limit and do not promise to retract pasted copies. |
| Initial ranking combines exact terms with semantic similarity. | **Keep as a hypothesis, not a fixed ranking decision.** | Exact identifiers, policy names, and quoted terminology should remain easy to retrieve. Begin with a lexical baseline and compare lexical-only, semantic-only, and hybrid results on representative queries and judgments. Hybrid fusion methods such as RRF are available in maintained engines, but vendor defaults do not establish relevance for this corpus [S03–S04]. OpenSearch's own guidance says tuning needs a query set, judgments, and configuration and has no one-size-fits-all answer [S14]. Ranking is only relevance: it must never mark a result approved, current, controlling, or safe to use. Resolve those fields from the authorized policy owner/source. |
| A newer edition replaces its predecessor in ordinary results; citations may request the older edition from an archive. | **Conditionally accept with explicit edition states and retention authority.** | Normal search may prioritize only the owner-designated current edition, while authorized historical citations retain their originally cited revision. Store source revision, effective/publication date, owner-declared status, indexed revision, and index generation separately. At open, authorize the exact cited edition under the current access policy; then clearly distinguish “edition cited” from “newer edition available/current.” Do not imply that the previous edition is still valid policy. A source API's version ID is useful only while the source retains that version. Microsoft Graph says OneDrive/SharePoint version creation and finite retention depend on admin configuration and can vary by user/location; OneDrive may not preserve complete old-version metadata [S11, S17]. SharePoint's documented expiry/count trimming and retention/hold interactions show that archived editions can be permanently purged or retained under different policy [S18]. The required retention window and whether a citation may retain a protected snapshot are owner/legal decisions, not engine defaults. |
| Removed passages open the latest related heading and show a warning. | **Reject as the default citation behavior.** | This silently changes the target and may imply the new passage carries the old meaning. If the exact edition and passage remain retained and authorized, open that exact historical passage with an “older edition” label and separately link to the current owner-designated version. If deleted, purged, or inaccessible, stop with an unavailable/withdrawn state; expose even a tombstone only if its metadata is allowed. An owner may offer a separate, clearly labeled “related current passage” suggestion, never as fulfillment of the old citation. Do not resurrect deleted text or retarget by fuzzy matching. |

## Citation identity and open behavior

Recommended durable record:

- citation ID (opaque resolver token), creator and creation timestamp;
- source-system and document IDs; source revision/version ID; owner-declared edition status/effective date; canonical rendered-text digest and rendering/extractor version;
- exact selection locator: authored block ID where reliable, normalized TextQuoteSelector exact/prefix/suffix, TextPositionSelector fallback, and section/heading path as context;
- citation issuance context describing which edition the user saw, without embedding sensitive title or quote text in a shareable URL;
- current authorization and citation-resolution outcome at open time.

Store sensitive selector text in the same access-controlled domain as source content, or use an opaque citation record so the copied URL itself does not expose it. W3C TextQuoteSelector intentionally records selected text, specifies normalization/logical Unicode positions, and allows multiple matches; TextPositionSelector avoids copying quote content but is brittle after edits [S10]. The resolver should first request the exact source edition, check current access, then resolve the selector against that edition. If the quote is ambiguous or the source version has disappeared, do not guess. A confirmed exact match can highlight the passage. A newer version is a separate result with a separate citation. A hash can detect a content mismatch but cannot guarantee source authenticity, authorization, or retention.

Alternative locator strategies and trade-offs:

1. **Stable authored block IDs:** good across heading moves/reflow if editors preserve the IDs; owners need authoring conventions and must define when a changed block receives a new identity.
2. **Immutable edition ID + content digest:** strong edition disambiguation; requires the source to retain/retrieve the edition and does not identify a passage by itself.
3. **Quote plus prefix/suffix:** can re-anchor within the same edition after layout changes; duplicate text can still be ambiguous and storing quote text can disclose content.
4. **Position/ordinal/line:** compact and useful within a specific immutable rendering; moves when content or extraction changes and is not a cross-edition identity.
5. **Heading path, DOM/XPath, or fragment ID:** useful context and navigation when maintained by the source; headings/structure can move or be duplicated.
6. **Fuzzy or semantic matching:** candidate suggestion only; never silently establish that a new passage is the old one.

## Permission and cache sequence

1. Authenticate the user; resolve current groups/roles and source ACL generation.
2. Search on current and indexed ACL metadata as a defense-in-depth candidate filter. Restrict requested fields to opaque IDs until authorization succeeds.
3. For every candidate, confirm current permission at the authoritative source or an owner-approved authorization service against the exact document/edition. If the service cannot establish a current decision, fail closed.
4. Only then reveal permitted title/heading/snippet, fetch passage text, or return score/aggregate data. Include caller and authorization generation in protected cache partitioning; still reauthorize before display after any revocation signal.
5. On revocation, block access first and invalidate search, snippet, citation, and derived caches asynchronously or synchronously according to the owner-approved revocation SLO. The system can prevent future app opens; it cannot revoke already copied/exported text or screenshots.

No private document or embedding is sent to an external service under this recommendation. If owners later consider a managed service or external embedding model, that is a separate data-residency, contractual, security, and records approval—not an implementation default.

## Edition/index state model

Maintain at least: owner/source revision and status; source revision observed time; indexed revision; index generation/build status; permission generation and last successful permission sync/check time; deletion/withdrawal state; chunker/extractor/model version.

- **CURRENT:** indexed revision equals the owner-designated current revision and a fresh permission check succeeds. Return only currently authorized fields; show edition/effective date/status.
- **INDEXING / REBUILDING:** source has advanced or a new index generation is building. Do not label old hits current. A historical hit may be returned only if exact-edition access is checked now and product owners allow it; display “older edition; index updating” plus the observed source/current status. Otherwise suppress it and provide an authorized source route or generic “index updating” status.
- **PERMISSION UNKNOWN / ACL STALE:** permission sync is behind its defined bound, group expansion failed, caller token is missing, or policy service failed. Do not return titles, snippets, counts, cached hits, or citation text. Generic unavailable status only.
- **REMOVED / PURGED / WITHDRAWN:** no ordinary search hit. If still retained and currently authorized, a historical citation may open its original edition with explicit status. If not retained or not permitted, stop; tombstone/title visibility is separately authorized. A related current passage is offered only as a new, separate link.
- **INDEX FAILED:** use a previous index only under the same freshness, authorization, and historical-label rules as INDEXING. Otherwise fail closed and show generic status.

A versioned full index with an atomic alias swap can avoid a partially built index; it does not make old index contents safe after ACL changes and must not bypass per-hit permission checks [S13]. For one-document updates, write the new immutable edition/index record, verify its completion and permission metadata, and then atomically move the current pointer. Keep old content under a retention policy, not merely because it remains in a search index.

## Corrections, optional improvements, and owner decisions

**Required corrections:** replace ordinal-only passage identity; replace the live-document-only citation; prevent stale cached snippets from being served after permission changes; do not assume reindex-time team labels are current authorization; do not auto-redirect removed citations as if they were fulfilled; separate rank from authority; make indexing and ACL freshness visible and fail closed when uncertain.

**Optional improvements:** stable authored block IDs; quote and position selector fallback; source hashes and version-specific deep links; exact-identifier boosts and lexical/hybrid comparison; relevance explanation that does not disclose restricted results; versioned index and atomic publication; separate current and history search modes; owner-curated aliases/synonyms; a compact unavailable state.

**Owner decisions required before implementation:**

- Which system and role is authoritative for document editions, effective dates, “current” status, supersession, and withdrawals?
- Are old policy versions retained for citations? For how long? Can citations store an approved snapshot, or must the source platform remain the only copy? How do legal holds and deletion requests apply?
- Is authorization to historical editions governed by current ACL, historical ACL, or a more restrictive rule? Who approves group/role expansion and inherited permissions?
- What revocation freshness SLO applies to source ACL changes, identity changes, snippets, search caches, and citations? Which failures block search?
- Which fields are sensitive enough that even document title, heading, existence, counts, or an “unavailable” tombstone must be hidden?
- What private deployment boundary, language/model, embedding service, and hosting are approved? The default here is no external content upload.
- Which query types, rank trade-offs, supported languages, latency/cost bounds, relevance metrics, and source platform are in scope?

## Already covered, rejected, and uncertain

- **Already covered by the brief:** no authority from ranking; no live-only URLs as immutable citations; no private-document uploads; no promise to revoke exported copies. Preserve all four constraints.
- **Rejected:** edition number plus chunk ordinal as sufficient identity; “filter before display” as sufficient against stale ACLs/caches; leaving snippets until next reindex; silent move to a related heading; treating an archive as permanent without policy.
- **Uncertain pending owners:** actual source version identifiers/retention; current versus historical authorization; permission API and revocation latency; availability of authored stable anchors; service/data-residency requirements; which edition is authoritative and how that status changes. These are not resolved by the sources or by search rank.

## Validation proposals versus executed checks

**Executed:** no product, authorization, relevance, or synthetic-corpus checks were run. This stage is research/planning only. The sources reviewed are evidence, not validation of a proposed integration.

**Proposed synthetic checks:** create a small synthetic set with (a) two versions of one procedure and an inserted paragraph before an old ordinal; (b) a moved heading and duplicate quoted passage; (c) an exact policy identifier whose lexical rank differs from a semantic paraphrase; (d) two team ACLs, a revoked membership, and a warmed snippet cache; (e) one removed passage with a superficially related new passage; (f) source-ahead/index-rebuilding and ACL-service failure states. Check that citation opens the exact retained edition/passage, no ordinal silently retargets, rank never changes authority labels, no title/snippet/count is served after revocation, unknown authorization fails closed, no removed citation silently redirects, and state labels reflect source/index/ACL freshness. These checks would test mechanics only; they were not executed here.

**Proposed production validation:** the source/security owners must test actual identity/group resolution, inherited ACL changes, revocation and cache invalidation under realistic races, historical-version access, retention/deletion/hold behavior, and metadata side channels. Search owners must judge a representative real query set and compare lexical, semantic, and hybrid configurations with agreed relevance and latency/cost measures. Records/legal and policy owners must approve storage, citation wording, currentness, retention, and unavailable-state rules. None is complete or assumed.
