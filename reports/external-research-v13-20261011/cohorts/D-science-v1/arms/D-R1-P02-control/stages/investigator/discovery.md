## Finding

The brief calls for a deterministic derivative component behind an explicit policy boundary. A safe design inspects bounded input metadata, applies orientation once, transforms color from a known or explicitly assumed source space into a declared output space, scales/crops under a named policy, applies a role-specific metadata allowlist, writes a staged derivative without touching the original, and records provenance and status. It must report an explicit failure or unsupported state instead of substituting a preview-looking fallback.

Three maintained approaches offer different tradeoffs; this research does not rank or select them.

| Approach | Useful fit | Material conditions and risks |
|---|---|---|
| **libvips through Sharp or a direct libvips binding** | Sharp exposes header-only inspection, orientation, resize, ICC output, and pixel limits. A direct binding avoids making Node a product requirement. | Header metadata returns raw dimensions without applying EXIF orientation; Sharp's default pixel limit trusts those dimensions. Default output converts to sRGB and strips metadata; opting into all metadata can retain identifying fields. Codec support depends on the built release. Operation order and orientation behavior changed across libvips releases; pin and test the exact stack. |
| **Pillow** | Python implementation with explicit ImageOps orientation, ImageCms profile transforms, resize primitives, and a configurable decompression-bomb warning/error path. | Profile conversion, alpha handling, accepted formats, and output metadata still require application policy. Promote the bomb warning to a failed item and set a workload-specific threshold. History shows orientation changes can regress, and TIFF decode can itself consume orientation. Pin Pillow and native codecs. |
| **ImageMagick** | Broad CLI or library workflow, explicit auto-orient, ICC operations, metadata stripping, and memory/map/disk/area/time/thread/file resource controls. | Defaults are host-adjusted; set explicit policy. CLI operation order matters. Strip removes color-related metadata with descriptive metadata, so color conversion and output profile attachment must be deliberate. TIFF/JPEG orientation history includes an attempted patch and revert; verify exact releases against fixtures. |

## Pipeline proposal

1. **Keep source bytes immutable.** Never use an in-place mutating command or a destination path that aliases the source. Hash the input; stage outputs under unique temporary names. Publish only after decode, transform, encode, reopen/structural checks, and metadata policy checks succeed.
2. **Inspect before pixel decode, then distrust the header.** Record detected format, decoder/build capability, width/height, orientation-related fields, frame/page count, alpha, color/profile presence and profile identity. Use overflow-safe pixel/frame arithmetic. Header inspection aids early rejection but does not prove safe allocation or visual dimensions. Apply product pixel/frame ceilings plus worker memory, CPU/time, disk, and concurrency ceilings.
3. **Resolve orientation exactly once.** EXIF Orientation covers rotations and mirrors (1–8); the transform changes geometry, so it must precede resize/crop decisions. Emit oriented pixels and remove/reset orientation so a viewer will not apply it again. Handle malformed, conflicting, or non-EXIF orientation signals (including XMP where relevant) through a documented exception policy; do not guess. TIFF decoders may already orient pixels on load, so a second auto-orient can undo the intended result. Verify each current format/build path.
4. **Make color a declared transform.** Choose an output profile and rendering intent per output role; record source/target profile identity, transform library/version, intent, and fallback. Transform from a valid embedded profile. For absent profiles, require an owner-approved declared assumption (for example, assume sRGB for untagged RGB) or send for review; do not infer wide-gamut samples are sRGB. Surface malformed/unsupported profiles unless an approved fallback is explicit. Sharp documents default sRGB conversion plus removal of all metadata, including ICC; opt-in helpers can retain source ICC, attach a target profile, or keep all metadata. ImageMagick profile operations are ordered conversions; repeated transforms can introduce avoidable differences. Pillow exposes profile-to-profile conversion with default perceptual intent. None guarantees identical appearance on every review display.
5. **Specify scaling and alpha together.** Choose named dimensions, fit/crop/upscale rules, filter, output bit depth, JPEG quality/chroma behavior. Decode-time downsampling can reduce large-image work when supported; full decode then resize is simpler but can cost more memory. PNG stores unassociated (non-premultiplied) alpha; transparent pixels may contain arbitrary color values. This format fact motivates explicit alpha-aware resampling and transparent-edge tests, but does not prescribe a library's resampling algorithm. Preserve alpha for transparent formats. Flatten to JPEG only with a declared background and explicit ordering. Compare source-space and linear-light scaling when fidelity warrants it; the libvips issue below shows one ICC/linear path can fail for one profile, so neither path should be presumed safe without exact-version coverage.
6. **Use a role-specific metadata allowlist.** For external exports, enumerate every supported metadata/container family to remove or retain: EXIF (including orientation and GPS/personal fields), XMP, IPTC, comments, format-specific text/profile chunks, thumbnails and related records. For internal review copies, copy only owner-approved technical fields. ImageMagick strip is broader than deleting one EXIF tag and removes ICC/color signaling chunks; Sharp keepMetadata retains EXIF, ICC, XMP and IPTC as a group. Neither is a role-specific policy. Validate encoded output metadata, not just in-memory fields. Reattach the chosen output ICC after removing unrelated metadata. Deleting one field does not prove all identifiers are gone.
7. **Make per-item state and cancellation auditable.** Track stable item IDs and states such as queued, inspecting, processing, succeeded, unsupported, failed, canceled-before-start, canceled-in-flight. Each terminal state carries a user-readable reason and whether output published. Atomically publish only complete outputs; cancellation must not leave a file that looks complete. Define whether in-flight work finishes or is interrupted; clean staging data if interrupted. A batch summary reports every success and non-success. Define idempotent retries and preserve completed outputs according to owner replacement policy.
8. **Record regeneration provenance.** At minimum store source SHA-256, observed input facts, derivative role, settings/policy version or hash, decoder/codec versions and build features, transform and encoder versions, source/target ICC identifiers or hashes, intent, orientation decision, output dimensions/format, output SHA-256, and terminal status. Avoid copying contributor identity fields into the provenance record. A settings/decoder change creates a new derivative identity; originals remain available.
9. **Explain exceptional outcomes.** Unsupported format/codec, malformed header/ICC, orientation ambiguity, policy rejection, resource-limit rejection, decode/encode failure, and cancellation are distinct outcomes. Identify which input failed and why. Give next-step/retry guidance when a different format, newer decoder, different export role, or owner action is required. Never create a plausible-looking placeholder.

## History that changes risk assessment

- Pillow [#5580](https://github.com/python-pillow/Pillow/issues/5580) reported a KeyError in 8.3.0 while removing orientation from alternate EXIF data after a change intended to avoid mutating the original. Linked PR #5584 was reported released in 8.3.1. Test both output orientation and original-image immutability across EXIF representations.
- Pillow [#8554 / #8556](https://github.com/python-pillow/Pillow/pull/8556) shows YCbCr TIFF decode can already apply orientation through libtiff; Pillow merged a fix on 2025-03-29. Test decoder-applied TIFF cases as well as JPEG EXIF transpose.
- libvips [#1523](https://github.com/libvips/libvips/issues/1523) recorded different autorot plus thumbnail_image results between 8.8.4 and 8.9.0 after a metadata behavior change; the helper may rotate itself. Record exact release and operation path.
- libvips [#4343](https://github.com/libvips/libvips/issues/4343) reported an almost black linear thumbnail after a profile transform for one Apple Wide Color Sharing Profile input on 8.16.0. The fixture was not public and the profile/intent workaround was reported by the user; generality and resolution are **uncertain**, not a universal defect or confirmed fix.
- ImageMagick [#7147](https://github.com/ImageMagick/ImageMagick/issues/7147) documented orientation differences between JPEG- and LZW-compressed TIFF pages. A candidate patch reportedly regressed other pages and was reverted. Issue closure alone does not establish behavior for a current release; pin and test both compression paths.

## Validation design (proposed, not executed)

- **Orientation/decoder:** all eight EXIF orientations with asymmetric corner markers and mirror cases; missing/invalid tags; raw/already-oriented TIFF pages with JPEG and LZW compression; EXIF/XMP conflicts; assert visible geometry, no double application, and unchanged original.
- **Color/profile:** tagged sRGB, wide-gamut RGB (such as Display P3/Adobe RGB), CMYK, gray, missing ICC, malformed ICC, unsupported intent/profile; verify color-managed target values and output profile identity. Test normal and linear-light paths.
- **Alpha/scaling:** transparent edges with nonzero hidden RGB, opaque controls, semi-transparent gradients, large downscales, crop/contain/cover, no-upscale, and JPEG backgrounds. Add perceptual comparison; equal dimensions or successful encoding is not fidelity evidence.
- **Limits/failures:** at/over policy dimensions, corrupt/truncated files, extreme decoded-pixel ratios, excessive pages/frames, malformed profiles, worker memory/time/disk exhaustion, unsupported build; assert deterministic status and no published output.
- **Metadata/privacy:** seed unique values in EXIF/GPS, XMP, IPTC, comments, PNG text and ICC; check encoded outputs against each role's allowlist and confirm intended ICC preservation.
- **Batch/cancel/provenance:** mix success/unsupported/failure; cancel before start and in-flight; inject encode failure; assert only complete outputs publish, manifest explains every item, reruns are idempotent, and hashes/settings regenerate under the pinned stack.

**Checks actually executed:** none. This is desk research and planning; no fixtures, code, build, malicious-input test, perceptual review, benchmark, or production integration ran. The release helper and Goal capture are workflow mechanics, not product validation.
