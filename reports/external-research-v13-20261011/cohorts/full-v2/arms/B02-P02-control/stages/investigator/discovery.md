# Brief-only discovery — workshop booking and equipment readiness

**Scope.** This is the independent brief-only discovery for a small member booking, staff maintenance-hold, and daily readiness system. The released plan has not yet been read. The user asked for a software proposal, not implementation. No software was installed, no real workshop data was used, and none of the proposed checks below has been run.

## System shape and alternatives found

The inventory is not a room calendar. A reservation can consume several mutually constrained things over the same interval: a tool, a currently trained supervisor when the job requires one, and one shared extraction unit. Model a booking as one owner-facing request with an atomic set of allocations to named resources. Each resource needs an identity, operating/maintenance state, and applicable qualification or quantity. The browser should see only choices that can be committed together. Keep member, operator, and assigned supervisor as distinct roles.

Three deployment/product approaches merit a pilot rather than a premature winner:

1. **One local workstation running a small local-first application.** Keep the database and application on that workstation; the staff view works without the internet. SQLite is a practical low-operations candidate when all database processes are on the same host. It supports multiple readers but one writer; an explicit write transaction acquired before checking availability (for example, `BEGIN IMMEDIATE`) lets competing requests serialize and return an understandable busy/conflict outcome [S01]. WAL permits reader/writer overlap but still only one writer and does not work over a network filesystem [S02]. Therefore serve browser clients through one application process on the local workstation; do not put the SQLite file on a shared drive or let every browser/device open it. If WAL is used, specify a runtime containing the March 2026 WAL-reset fix (3.51.3 or the documented 3.50.7 / 3.44.6 backports) and keep the WAL file with its database [S02].
2. **A self-hosted LAN web application with PostgreSQL.** This supports member browsers on the building network and keeps booking writes local when the ISP is down, provided the host and LAN remain available. PostgreSQL range types express intervals, and a GiST exclusion constraint can reject overlap; pairing a resource key with the overlap operator (via `btree_gist`) gives a useful invariant for exclusive tools or people [S03]. The application should commit all resource allocations, status changes, and explanatory event records in one transaction. A LAN/server outage still requires an explicit manual fallback.
3. **Existing self-hosted schedulers as configure-and-fit candidates.** MRBS is a compact room/area-oriented PHP system with DB authentication as its default and MySQL/PostgreSQL deployment; its docs allow custom fields and private booking fields only under the documented privacy settings [S17–S18]. Its current source has an optional simultaneous-booking guard: default `$prevent_simultaneous_bookings = false`, with a separate maximum default of one when enabled [S19]. The latest NEWS snapshot identifies MRBS 1.12.2 (26 May 2026), fixes an editing-series defect under that guard (#3965), and lists security fixes (including two CVEs) [S20–S21]. MRBS may reduce ordinary calendar work, but the evidence reviewed does not establish a single all-or-nothing bundle of tool + qualified supervisor + shared extractor, nor a protected maintenance workflow; demonstrate those before treating it as a fit.
   
   LibreBooking is a richer self-hosted resource scheduler. At the v7.0.0 release commit it advertises multi-resource reservations, role-based access, resource schedules, and iCalendar integration, and requires PHP 8.2+, Apache 2.4, and MySQL 8 / MariaDB 10.6 for the documented manual deployment [S05–S06]. Its save presenter assembles one reservation series with primary and additional resources, participants, accessories, and attributes [S07]. The current code validates resource conflicts and limited accessory quantities separately [S08–S10]. Blackouts support recurrence with an explicit end date for interval-based repeats and a conflict policy; current source tests show deletion notifications and splitting/deleting an occurrence of a recurring blackout around a reservation [S11–S13]. The destructive conflict path uses a generic reason string, so the workshop must verify what staff actually see and retain; do not assume it satisfies reason-preserving dispute resolution. A current open issue reports the repeat-termination date shifted a day west of UTC; the issue’s described logic is corroborated by the current develop source, which still constructs dates with JavaScript `new Date('YYYY-MM-DD')` and local arithmetic [S15–S16]. Test time zones and recurring holds before relying on it. At the time observed, the develop README also announced a high-impact security release planned for 13 October 2026, and warns of a critical pre-7.0.0 flaw; defer any deployment decision until the new security release and supported-version posture are rechecked [S14].
   
   Neither product finding establishes an implementation defect beyond the cited source and issue; they define pilot questions. Calendar/iCalendar feeds can be read-only exports for convenience, not the enforcement authority. RFC 5545 specifies the interchange format and recurring-event rules; it is not a booking database or conflict-transaction guarantee [S04].

## Candidate operating and domain rules

Use half-open time ranges (start inclusive, end exclusive) so one booking may end exactly when the next starts; show any cleanup/buffer interval explicitly. A booking has a status such as requested/confirmed, in-use, completed, cancelled, or interrupted. A completed or cancelled booking remains in the record. A fault creates a staff-owned maintenance hold plus a fault/readiness state; a member edit cannot delete or weaken it. A daily view shows ready / held / faulted, the next reservation window, required supervisor qualification, and extractor availability, with a clear “last refreshed” time.

Represent recurring maintenance as a bounded series with explicit dates, local workshop timezone, exception dates, and per-occurrence override. A changed occurrence must say whether the edit affects this instance, this-and-future, or the full series. Store enough source information to review a generated occurrence, but materialize or verify near-term occurrences before offering availability. Keep ICS as export/import at the boundary rather than the master recurrence engine [S04, S11–S13].

On a create or update, begin one transaction, re-check every requested tool/supervisor/extractor allocation against active bookings and holds, then save all allocations together or none. For SQLite, acquire the write lock before the check and handle `SQLITE_BUSY`; for PostgreSQL, use exclusion constraints for exclusive allocations and transactional locking for any counted capacity [S01–S03]. Explain a collision by resource and time and offer a next available slot or staff contact. A page’s earlier availability snapshot is advisory; it is not proof a slot remains open.

For an accepted booking affected by a newly discovered fault, show the staff member the fault, equipment, conflicting time(s), and affected reservations. Do not silently delete an accepted booking or silently discard the hold. Provide a staff decision, contact the affected member, and append an event recording actor, timestamp, old/new resource/time/status, reason, and notification. This is a proposed minimum; retention period and whether members see names or only conflict windows remain decisions. Capture only the minimum member lookup token/display name needed to resolve a booking; no identity documents, payments, activity scoring, or broad usage history.

## Outage and adoption implications

A local workstation can serve its local screen and, while local routing works, member browsers during an internet outage. That does not cover a failed workstation, Wi‑Fi/switch, power, or LAN. Do not queue browser-side writes while disconnected: they can arrive after a competing booking and create stale/conflicting state. The operational fallback should be a dated, numbered paper hold/booking log and the last printed readiness sheet; staff enter each fallback event after recovery through the same checks and retain its original time/reason. A daily encrypted backup and a tested restore are prerequisites before live use. For a 100-person membership, either one local host with a LAN browser or one operator workstation is plausible; the number alone does not require cloud hosting.

Proposed staged adoption: map only resources, qualifications, hours, buffers, and hold/cancellation decisions; compare MRBS, LibreBooking (after its security release), and a minimal local-first build using synthetic data; run a staff-only shadow schedule; pilot one tool and one shared dependency; add bounded recurrence and interruption handling; then enable member LAN access only if support and privacy rules are agreed. Keep paper and the existing calendar authoritative until the pilot reconciles conflicts and restores successfully.

Owner decisions still open include (a) whether urgent safety maintenance immediately overrides an accepted booking and who may authorize that; (b) whether there is a safe interim state when a fault and a booking overlap; (c) which members may reserve without a member account and what minimal local identifier is acceptable; (d) required supervisor credentials and expiry; (e) buffers, cancellation/no-show and interrupted-use rules; (f) who may view booking names, event explanations, and how long history is retained; (g) whether “internet down” means ISP-only or any LAN/workstation failure; (h) who maintains backups, restores, updates, and member access.

**Proposed validation, not executed:** synthetic two-client simultaneous attempts for each constrained resource and the full bundle; confirm one complete commit at most, no partial bundle, and safe retry behavior; adjacent versus overlapping intervals; member attempts to edit a maintenance hold; blackout creation/update against accepted bookings with reason and notification; recurrence exceptions, time-zone/DST transitions, and an interrupted booking; browser retry after a LAN cut; ISP-only outage, host outage, backup restore, and paper-log reconciliation. Record which checks are proposals and which are actually run in the later draft.
