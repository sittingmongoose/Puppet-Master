# Brief-only discovery — A-F01-A1 investigator

## Scope and evidence boundary

This record was written before the exact plan was released. The brief asks for a research-backed design proposal for a desktop survey app used by three field laptops that can be disconnected for a week, with up to 50,000 observations per season. Each observation has an identifier, notes, a confidence flag, and links to separately stored photos. Offline edits can overlap, including record deletion versus another edit or photo addition. Reconnection needs an understandable recovery route. Manual file transfer must remain possible. No hosted account, automatic photo-byte upload, wall-clock-only conflict choice, or silent resurrection of a deleted observation is acceptable. App language and database are undecided.

I opened official product documentation and first-party project issue, release, and regression-test records listed by stable source IDs in source-map.json and sources/index.md. No code was downloaded or executed, no local tests were run, and no behavior was benchmarked. The exact plan remains unreleased at this point.

## Early architecture finding

Represent each user action as an immutable, idempotent edit operation with a stable operation ID, observation ID, author/device attribution, causal parent/base revision IDs, and typed payload: field patch, photo-link addition/removal, delete/tombstone, or explicit restore. Persist each operation and its derived visible state in one local database transaction. A per-device counter or random ID can establish operation identity; causal links establish what an edit had observed. Wall-clock timestamps may be displayed as approximate context, never used as universal merge order. Replaying an operation with the same ID must be harmless.

Materialize fields independently. Edits to different fields may combine; concurrent writes to the same field remain competing values in a review item. Preserve both branches until a person accepts a result. A delete is an explicit tombstone. If another laptop edits the observation or adds a photo from a base that predates the delete, retain that branch and show “deleted here; another edit/photo arrived” for review. Keep the tombstone visible until a user explicitly creates a restore action. Whether free-text notes should use append-only note entries, text merge, or whole-field review is an owner decision; no ecological policy is inferred.

Keep photo bytes in the existing separate store. An edit event refers to a stable photo/object ID, optional relative locator, media type, byte length and verified content digest. Reconnection first merges the reference event only. A separate export/import manifest can list referenced-but-missing files and let the operator choose whether to include files in a removable-media package; no automatic upload. Do not use PouchDB’s MD5 attachment digest as the proposal’s integrity contract when a stronger digest can be computed locally.

## Approaches compared

- Product-neutral operation journal plus local transaction store: best fit to the stated requirements because it can retain competing edits, express explicit tombstones, and be sent as an account-free file package. It still needs deterministic, versioned merge rules, schema evolution, safe package validation, history-retention policy, and an understandable review UI. This is a direction, not a selected storage engine.
- SQLite plus Session Extension: useful manual changeset exchange when devices share a compatible schema and starting state. SQLite documents conflict callbacks and file exchange, but sessions are disabled by default in many builds, require primary keys, and coalesce repeated writes within a session instead of preserving each as a readable audit event. Treat this as a comparison or transport primitive, not the complete journal. SQLite’s crash-test VFS is evidence for local atomicity under filesystem and flush assumptions; it does not make package exchange or photo storage atomic.
- CouchDB/PouchDB revision-tree replication: strong built-in offline/multi-master sync, local peer databases, checkpoints/retry, and explicit revision branches. A normal read returns only the deterministic winner; callers must request and fetch losing branches. Compaction discards non-leaf bodies, so durable competing-edit history needs a separate archive/retention rule. Tombstones let deletes replicate, but concurrent edit/delete still needs explicit review. Photos are revision-associated attachments; an actual replicated attachment-reference bug produced an issue, a targeted fix, and an integration regression test. External photo references reduce that coupling.
- Automerge CRDT: transport-agnostic, history-carrying documents merge independently edited properties and retain same-property losing values through a conflicts API; operation ordering uses actor/counter IDs rather than wall-clock time. However, default reads choose a deterministic value, and assigning again hides the conflict. Its documented map rule lets a concurrent set beat a delete of that key. Do not represent record deletion as removing a map key; use an explicit tombstone and test delete-versus-edit/photo behavior. Review desktop binding, storage and retention at a pinned release.
- RxDB custom replication: supports offline local work with checkpoints and an application-defined backend; its documented default conflict handler drops client/fork state in favor of the master. Viable only with a custom loss-preserving handler and backend. A hosted service is not required by the protocol, but this adds backend work and does not itself solve removable-media transfer.

## Recovery and scale

Show last durable save time/device, unsent edits, transfer status, and review items in plain language: “two notes changed offline”; “record deleted on Laptop B, edit/photo arrived from Laptop A”; “photo file is not in this transfer.” Offer choices such as keep delete, keep edit and restore explicitly, combine different fields, keep both note entries, or postpone. Record each decision as a new operation. Avoid database revision jargon.

Commit the event, current materialized view and local sequence/checkpoint atomically. After restart, replay committed operations and report the last durable state. Import must validate package identity/schema/checksums before one idempotent merge transaction; interruption should leave either the prior state or the complete batch. This is a proposal. Actual power-cut behavior depends on the selected engine, build flags, OS, filesystem and hardware flush implementation. Fifty thousand records is a sizing input, not proof of performance: benchmark realistic event retention and conflict density. Photo sizes and connection speeds remain unknown.

## Brief-only open decisions

Confirm the existing app’s transaction/storage API before choosing SQLite, an embedded CRDT, or a document replicator. Decide audit retention, author labels without accounts, whether notes remain field conflicts or become append-only entries, how deleted records appear in search/export, whether restore needs second-person review, the photo manifest/digest, and whether manual packages contain only edits or optionally selected photo files. Validation proposals, not executed checks, will be placed in the plan-aligned draft.
