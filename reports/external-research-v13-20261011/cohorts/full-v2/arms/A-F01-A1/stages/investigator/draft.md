## Recommendation

Use an append-only, storage-neutral operation journal as the authoritative edit history, with a locally materialized observation view. Store each new operation and its materialized effect in one local transaction when the existing embedded store permits it. Exchange immutable journal segments through an optional office-LAN relay and through removable-media bundles using the same import/export format. The relay is a store-and-forward convenience; it is not a leader, and its arrival order is not a merge rule. Keep photo bytes in the operator-selected separate directory. Synchronize photo-reference operations by default and offer an explicit operator choice to include photo files in a manual bundle.

This is an architecture recommendation, not a selection of SQLite, PouchDB, Automerge, RxDB, or a programming language. First inspect the existing application's storage and transaction boundary. Use causal parent IDs and field-level operations to preserve competing edits. Make deletion a durable tombstone; keep conflicting edits and photo references visible for review, and require a separate explicit restore operation before a deleted observation becomes active again. No wall-clock timestamp chooses a winner.

The visible data comprises observation ID, notes, confidence flag, and photo links. All unresolved branch data remains recoverable; a user decision creates another operation rather than erasing source branches. The brief gives no note-merging policy, retention period, photo size, connection speed, identity provider, or performance service level; those remain owner decisions or validation inputs below.

## Proposed operation and identity contract

Each operation should include:

- a stable observation ID separate from every operation ID;
- a globally unlikely-to-collide operation ID, plus an installation/device-instance ID and local sequence for traceability and gap detection;
- an optional locally assigned author label, clearly treated as display text rather than identity or uniqueness proof;
- the observed causal parent operation IDs/frontier for that observation, not just a local integer revision;
- a typed action: set a named field, add/remove a photo reference, delete/tombstone, or explicit restore;
- the field's observed base value or base operation where needed to render a three-way review;
- display timestamp, schema version, and any transfer/package ID needed for diagnosis.

An operation ID must survive retries and be reused unchanged on retransmission. Allocate identity and sequence inside the same durable transaction as the operation. Persist the device-instance ID with its local store. A fresh empty installation gets a new device-instance ID; restoring the same store preserves it. If a copied store is used as two independent laptops, require a new device-instance ID on the clone before edits. Treat a repeated ID with different payload bytes as a collision/corruption condition to quarantine and review, never as a last-writer overwrite. The exact ID encoding and author-label workflow are implementation decisions, but “local revision number + author label” alone is rejected.

Causal parents answer whether an operation was based on another operation. An arrival counter/checkpoint answers only which payloads a transport has delivered. Store arrival order may be useful for progress and retransmit diagnostics; it must not decide the visible record. A relay or import may receive operations out of order, so keep missing parents pending and recompute when their ancestors arrive.

## Local saves, recovery, and photos

For a save, durably commit the operation, updated observation view, local causal frontier, and any local transfer cursor within one transactional boundary. Display “saved” only after commit succeeds. If the current application uses a store that cannot include the operation and view in one transaction, define and review an explicit intent/segment protocol with crash recovery before implementation; do not assume two files append atomically. Keep the journal in the same embedded store as a logical append-only table when feasible. SQLite is one possible transaction engine, but SQLite Session Extension is not a substitute for this journal: its changesets assume compatible schema and starting data, require primary keys, can be build-disabled, and coalesce repeated changes made in one session [SQL-01, SQL-02]. SQLite's crash-test VFS checks that a transaction is all-or-none across simulated power failures, while its own documentation calls out filesystem, lock, flush, hardware and hot-journal assumptions [SQL-03]. The selected engine and shipped build still need target-platform validation.

Photo payloads remain outside the edit journal. Store a stable photo/object ID, verified content digest, byte length and media type in the shared reference metadata. A relative path is only a laptop-local locator and may be missing or different on another device; keep it separate from the cross-device ID. Compute the digest over the actual file and verify it when a selected file is imported. A merge of a photo-reference operation never copies or uploads bytes. An optional media bundle may include operator-selected photo files; its manifest must identify referenced files that were excluded, absent, inaccessible or failed integrity checks. Do not delete the external photo based on an edit-log conflict or compaction. A photo-link addition concurrent with record deletion remains a pending item; it cannot resurrect the record.

After an interrupted save, recovery should reopen the store and show the last complete committed state. An operation committed before shutdown must reappear exactly once; an uncommitted operation must not appear as a partial edit. Rebuild materialized state from the journal if its cache is inconsistent. Present “last saved on Laptop A; 3 edits are not yet transferred” rather than a database repair detail. If the platform cannot establish that a flush completed, report that limitation instead of claiming hard power-loss durability.

## Reconnection, removable-media exchange, and conflict handling

Use one versioned segment format for both the optional local relay and manual transfer. Each segment should carry a stable package ID, source installation ID, schema version, operation IDs and payloads, causal parents/frontier, sequence range, and an integrity manifest/checksum. Validate the package and any explicitly included photos before making a change. Import in an all-or-none local transaction, deduplicate by operation ID, record durable import status, and allow a lost acknowledgment to be retried safely. A truncated or unsupported package is rejected with a clear reason and leaves the store unchanged.

A receiver may acknowledge only after its durable import commits. A relay acknowledgment means only that the relay durably accepted the package, not that all three laptops imported it. Retain source operations and enough deduplication history for the agreed recovery horizon; do not delete a sent segment merely because it was acknowledged once. A laptop offline for a week may miss the relay's latest data and must still be able to catch up from retained operations or a verified export. Pruning and replica retirement require an explicit retention/backup policy. A received edit package with an old schema must be rejected or migrated by a declared, versioned migration, not silently reinterpreted.

Conflict decisions use causal ancestry and field overlap:

- Different fields changed from a common base may be proposed for automatic merge only where their operations commute and the field policy is known. For example, independent updates to confidence and a photo reference need not overwrite each other.
- Concurrent writes to the same field remain two values. Show the last common value, each competing edit, device/author labels, and approximate timestamps. Never silently choose by clock or by transport arrival.
- Notes remain same-field conflicts unless the group explicitly chooses an append-only note-entry model or funds a tested text merge. A generic text diff must not delete one researcher's wording.
- For delete versus edit, preserve the tombstone and the incoming edit branch. The card should say the observation was deleted on one laptop while another laptop edited it. “Keep deleted” leaves the tombstone active and archives both operations; “restore” creates a new explicit restore operation linked to the tombstone and chosen edit; “decide later” preserves the pending state. Neither the edit nor the relay can make the observation live by itself.
- For delete versus photo addition, show the photo link and file-presence status in the same pending recovery card. The group may keep the delete, explicitly restore then keep the photo link, or defer. A missing photo file does not remove its edit operation; an existing photo file is not automatically uploaded.
- A resolution adds a new operation referencing the resolved branches. Preserve the branches for the owner-approved recovery period, even when the screen no longer treats the conflict as pending.

The simple operator explanation should cover three common outcomes: “These two edits changed different fields, so both are kept”; “Both laptops changed the notes, so choose one or keep both as separate notes”; and “One laptop deleted this record while another changed it or linked a photo, so the deletion is waiting for your decision.” Explain that photos stay on their original devices unless the operator explicitly adds them to a transfer.

## Alternatives and applicability

| Approach | Supported behavior and fit | Material limit for this brief |
|---|---|---|
| Product-neutral operation journal in the app's embedded store | Preserves competing operations, explicit tombstones and removable-media exchange without a hosted identity or server. Can serve a LAN relay and a file bundle using one protocol. | Requires the app team to implement schema/versioning, causal merge, retention, import safety, and review UI. Select only after inspecting the current app. |
| SQLite transactions plus Session Extension | The Session Extension explicitly supports packaged changeset exchange between databases with compatible schemas and baseline state; callbacks can omit, abort or replace a conflicted change [SQL-01, SQL-02]. Local transactional storage is a candidate for crash-safe saves [SQL-03]. | Not an event-history design: repeated writes are coalesced; primary-key/build requirements apply; patchsets omit old values and lose conflict detection. Baseline mismatch and user-facing resolution remain the app's responsibility. |
| CouchDB/PouchDB multi-master revisions | Mature offline replication with local PouchDB peers, retry/checkpoints, tombstones and accessible conflict leaves [PDB-01, PDB-02, PDB-07, CDB-01]. Could fit if the app's language/runtime and deployment can use it. | A normal read returns a deterministic winner without showing the conflict; losing leaves require explicit reads; compaction/pruning limit body history. Deletion/edit policy still needs testing. Built-in attachments are revision-associated payloads; #8456/#8460 shows why their lifecycle needs regression coverage [PDB-03–PDB-06]. Its HTTP sync path does not itself define the requested media-transfer UX. |
| Automerge CRDT | Supports offline local changes, deterministic merge of different fields, and access to concurrent same-field values with operation IDs rather than wall-clock ordering [AM-01]. Its stored changes and compaction model are documented [AM-03]. | Default reads hide losers until queried, then a later write clears that conflict; map delete versus concurrent set yields the set value [AM-01, AM-02]. Record deletion needs an explicit tombstone wrapper and application policy. Pin and verify an appropriate desktop binding before selection [AM-04]. |
| RxDB custom replication | Offers offline client changes and checkpoint pull/push against a custom backend; no hosted account is inherent in the protocol [RX-01]. | The documented default conflict handler discards fork state and uses master. A loss-preserving custom handler, backend, local file export/import, and explicit delete policy would all be required. |

None is declared the universal winning product. Before selection, compare the existing app language, local database, transaction API, backup format, and deployment options against the above requirements. The proposed operation contract can be implemented independently of which viable adapter is chosen.

## Bounded integration sequence and exit gates

1. **Inventory and settle the contract.** Map the existing app's language/runtime, database, local transaction scope, backup/restore flow and current photo references. Decide author labels, note policy, delete/restore wording, photo digest/reference, schema migration approach and history-retention owner. Exit when an adapter can atomically persist an operation and view or a concrete recovery protocol has been reviewed. Do not choose a product before this inventory.
2. **Build the local durable journal.** Add versioned operation records, stable identity, causal frontiers, tombstones and materialized observation state. Save/reopen and backup/restore without a network. Exit when failure injection proves each edit is entirely absent or entirely recoverable after interruption.
3. **Add one transfer protocol.** Export/import validated immutable segments; then add the optional LAN relay as a store-and-forward client of that protocol. Deliver the same segment by USB/removable media. Exit when duplicates, out-of-order delivery, retry after lost acknowledgment and a week-disconnected peer preserve every operation without order-dependent output.
4. **Add recovery cards and photo manifests.** Show plain-language field conflicts, delete/edit and delete/photo review; preserve source branches and require explicit restore. Keep bytes external and make transfer inclusion explicit. Exit when every case in the conflict matrix has a predictable, reversible user choice and a clear status after restart.
5. **Pilot, size and retain.** Exercise three actual laptops with one disconnected for a week, resolve/restore a backup, and run realistic data-size and conflict-density profiles. Measure the 50,000-observation season and storage growth using observed photo metadata and event history; record photo sizes and connection speeds rather than assuming them. Exit only after the group accepts recovery, performance, retention, support and manual-transfer instructions.

## Proposed failure-oriented validation

These are validation proposals; **none were executed in this stage**.

| Failure or boundary | Exercise | Required result |
|---|---|---|
| Identity collision or lifecycle reset | Create operations from same-name authors on different devices; reinstall with restored data; create a fresh install; clone a store and edit on both clones; replay same ID with altered content. | Distinct operations remain distinct; retry deduplicates; clone gets a new installation identity; altered-payload collision is quarantined; no label or local revision silently overwrites an operation. |
| Causality versus arrival | Produce concurrent branches on three laptops and deliver in every permutation, including missing parent first and duplicate batches. | Same operation set and conflict frontier converge independent of relay arrival order; missing-parent work is pending and later applied. |
| Different and same field edits | Concurrently change confidence and notes separately; then have both change the same field from one base. | Independent fields combine only under declared policy; same-field values and common base remain available for review. |
| Delete versus edit | Delete on one laptop while another edits notes/confidence from an older base; reconnect in both directions and through the relay. | Deleted state remains visible as a tombstone/pending conflict. No ordinary edit or sync silently restores the record. Only explicit restore makes it live. |
| Delete versus new photo | Delete on one laptop while another adds a photo reference and optionally keeps the file local; import with file included and absent. | Conflict card preserves the photo operation, reports file status, and does not revive the record or upload/copy bytes implicitly. Explicit restore/link action is required. |
| Lost acknowledgment, duplicate or interrupted segment | Stop sender after receiver commit but before ack; resend; interrupt relay and import at each boundary; import from USB after network retry. | Repeated transfer is idempotent; sender can safely retry; receiver is either unchanged or has the complete batch; acknowledgement claims only durable receipt at its stated hop. |
| Corrupt, unsupported or partial manual bundle | Truncate payload/manifest, alter digest, use unknown schema, remove optional photo file, move local photo directory. | Invalid edits are rejected without partial database changes; missing photos are reported; valid operations remain importable without the files. |
| Power loss during save/restart | Inject process/system interruption before and during commit on every supported local database/platform combination; reopen copied/restored stores and verify journal/current-view consistency. | Latest committed edit is fully present exactly once; uncommitted edit is absent; recovery is readable; no message claims stronger disk durability than the tested platform provides. |
| Resolved history and retention | Resolve conflicts, compact/archive under candidate policies, then restore a backup and import a long-offline laptop's segment. | The chosen policy retains enough data to recover the promised period; after policy expiry the UI and documentation state the limit; no silent deletion of unarchived branches. |
| Scale and operator comprehension | Seed 50,000 observations plus realistic seasonal edit history and three-device conflict density; time import, search, startup, backup/restore, and let field staff perform scenario-based recovery. | Measurements establish whether the chosen store/retention and UI fit the actual group; no unsupported capacity/performance claim is made. |

## Owner decisions still open

1. Which existing app store and transaction API can persist the operation plus visible view atomically, and which language/runtime constraints apply?
2. How are local author labels chosen and shown without accounts? Are labels per person, per laptop, or both?
3. Should notes remain whole-field conflicts, become append-only note entries, or use a narrowly defined text merge?
4. When delete competes with an edit/photo, who may restore, and is a second person's approval required?
5. How long must unresolved and resolved histories remain recoverable? What backup/season-close evidence permits pruning, and how is a permanently offline or retired laptop handled?
6. What photo digest and file-ID format will be used? Are photo bytes ever included in a manual bundle by default, or only after explicit per-transfer selection?
7. Is an office-LAN relay useful, and what local network/privacy constraints apply? Manual transfer remains available regardless.
8. What startup, search, merge, backup and transfer service levels are needed at 50,000 records? Photo sizes and link rates must be measured before selecting targets.
