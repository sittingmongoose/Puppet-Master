# Brief-only discovery — B10-P02-treatment investigator

Scope boundary: this discovery starts from the assigned brief only. The comparison plan has not been opened. No application was installed, no training material was published, and no learner record was collected. This is a proposal investigation, not an implementation or a validation run.

## Early design space

Two authoring/storage patterns merit comparison. A repository of Markdown pages, diagram assets, and small structured exercise records can preserve change history and support a static build. A second volunteer can review a focused change before a release; the cost is Git familiarity and a build/release owner. A hosted block editor such as WordPress is friendlier to nontechnical authors and offers draft preview, but its WXR export is an interchange backup for WordPress sites, not a ready-to-run offline handbook. H5P adds reusable interactive activity types but a downloaded H5P package requires a compatible host; it is not itself a standalone local handbook. These are alternatives to test, not a selected product.

For a web distribution path, Material for MkDocs documents built HTML with browser-local search and a downloadable offline directory. The official offline plugin requires care: file-protocol security limits some browser behavior, its privacy plugin brings externally hosted assets into the package, and its own limitations say to disable versioning when offline mode is enabled. Docusaurus offers first-class versioned documentation, route labels and banners, but warns that maintaining multiple versions adds contributor and build complexity; its documentation also allows removal of old versions, so retention must be an explicit policy. An offline package therefore needs its archive/version scheme designed and tested separately from a default online site.

Personal progress should be a small local record keyed to an exercise identity and exact exercise revision, separated from immutable lesson/exercise content. A browser app can use IndexedDB without a server, but browser storage is origin-scoped, best-effort by default, may be cleared or evicted, and does not synchronize itself. The UI should say what persists, offer user-controlled export/import, and never transmit the progress store. A native local database is another option with stronger local transaction guarantees, at the cost of installing/updating an app. Do not promise either backup durability or cross-device continuity without proving it.

A working policy candidate is: retain status and timestamp against the exact revision that was completed; when a materially changed exercise is released, keep the old completion visibly historic and show the new revision as not completed. An owner must define what counts as material and whether an explicit, reviewed equivalence can carry status. Retired lessons should remain archived with a retirement date, label and replacement pointer; default search should favor active pages and archive lookup should clearly distinguish old matches. These are governance decisions, not platform defaults.

DOCX should be treated as an import source requiring review rather than a formatting-preserving master. Pandoc's current guide says its DOCX reader maps only styles it can convert; track-changes accept is the default and comments are ignored unless another mode is selected. Its guide shows a test fixture whose style distinctions are flattened without the styles extension. Import checks should surface tracked changes/comments, headings, lists, tables, image extraction and alternatives; no arbitrary Word layout guarantee is supported. For handouts, use a deliberately authored print output and manually inspect page breaks, links, diagrams and reading order. Printable exercise prompts can be completed on paper, but they cannot save or report the app's interactive progress.

Accessibility requirements apply to content and controls: preserve a programmatically meaningful reading order, full keyboard operation and visible focus; give instructional diagrams complete text equivalents, and keep instructional prose as text rather than rasterized text. A control's label, keyboard operation and completion feedback need assistive-technology checks. An automated checker or a platform's general accessibility claims cannot establish that each authored lesson and exercise is usable.
