# Research proposal: portable training handbook with accessible exercises

## Decision summary

Treat the released plan as a useful provisional direction, with one required correction: progress must not carry forward by default when an exercise changes. Preserve completion against the exact exercise revision completed. If a change is material, show the new revision as not completed and keep the prior completion as history. An owner must define the materiality threshold and may approve a narrowly scoped equivalence mapping, but the mapping must be explicit, reviewed, and visible to learners.

Build the proposal around canonical structured lesson content, immutable release packages, a separately stored local progress record, and distinct accessible reading and print outputs. Compare a Git-backed structured-text workflow, a hosted block editor, and an interactive-content platform before selecting tools. Material for MkDocs has a useful local-file/offline search mode but explicitly disables its versioning plugin in offline builds; Docusaurus has documented versioned pages and banners but carries version maintenance overhead. Neither should be selected until a small offline/archive prototype establishes that the complete workflow works. WordPress/H5P is more author-friendly for some volunteers but its exports need a compatible host and do not themselves make the requested offline handbook. A browser-local web app can run without an account or backend, but browser storage is best-effort and can be cleared; a native local database is a second option with installation and update costs.

This is a software proposal only. No lesson was published, no volunteer installation was performed, no learner record was processed, and no application was implemented.

## Proposed content and data boundaries

1. **Canonical lesson content.** Each lesson has a stable lesson ID, a published lesson revision, title/topic metadata, current/retired status, review date, optional replacement pointer, and structured sections. Each section uses semantic heading/paragraph/list/table/callout blocks. Diagram metadata carries an asset reference, a short alt field and a complete text-equivalent field or linked description when the diagram is complex. Avoid placing instructions only in pixels.
2. **Exercises.** Each exercise has a stable exercise ID and immutable exercise revision. A lesson revision references the exact exercise revision it presents. The local record is keyed by that exercise ID and revision. A completion record never means “completed for every future revision.”
3. **Local progress.** Store a minimal status and timestamp in a browser-origin IndexedDB database or a native SQLite database, depending on the selected deployment. Do not save free-text answers or scores by default. Do not include authoring credentials, name/email, cross-site identifiers, sync code or background upload. The network boundary should allow only intentional reading/update traffic for published content and send no progress payload. No research here verified any implementation's network behavior.
4. **Backups and changes.** Explain that browser/site data can be erased; provide a learner-initiated export file and import/restore flow if the group decides this is worth the support cost. State that export files can reveal a person's progress if shared. Validate schema migration and restore with synthetic records; never claim automatic backup or cross-device continuity.
5. **Content package lifecycle.** A published package manifest names its content revision and required application/schema version. A new package must install as an atomic version switch or leave the prior package usable if interrupted. Keep the learner store separate. Keep older content available for the agreed archive term and make archive status visible.
6. **Print and offline outputs.** Generate an offline readable version with all referenced resources included. Generate printable handouts as a separate, static output with blank write-in response areas and no hidden form state. Use the output-fidelity matrix above as the fixture checklist for headings/sequence, links, tables, alternatives, supported blocks, form behavior, and page layout. Review reading order, image alternatives, page breaks, contrast, link text, and whether essential diagrams remain understandable in monochrome. No print result should claim to have saved app progress.

## Version, retirement and progress policy

Adopt this proposed default pending owner approval:

- A revision change creates a new immutable revision record. Preserve history; do not mutate a published revision in place.
- By default, progress belongs to the exact exercise revision. On a material change, retain the old completed state with a label such as “completed on exercise revision 1”; show revision 2 as “not completed.”
- Do not decide materiality by a changed-file count or by author-only judgment. The review checklist asks whether steps, tool/part assumptions, safety warnings, expected results, or completion criteria changed.
- If a correction is genuinely non-material, an owner-designated reviewer may record an equivalence from old revision to new revision and explain why; preserve the original completion date/revision in history and show the equivalence rather than rewriting it as new work.
- A retired lesson remains in the archive with status, date, reason or replacement link if known. Default search should make the current page easy to find; the learner can explicitly include retired/historical results. Never label an archived hit “current.”
- Do not silently delete a lesson from an offline package. The owner sets the archive retention period and what to do when safety information is obsolete. An urgent correction may suppress the old page from ordinary use while retaining a clearly marked historical record if safe and legally acceptable.

## Phased adoption proposal

**Phase 0 — Policy and synthetic fixture.** Confirm the exercise materiality/equivalence rule, retired-content retention, audience devices, author skill level, data fields, and whether optional learner backup is wanted. Prepare a small synthetic set of lessons with one simple exercise, one revision that changes a task, one non-material correction, one retired page, one complex diagram, and a DOCX sample with a heading, table, image and tracked changes. This remains test data, not actual training content or learner data.

**Phase 1 — Compare authoring and package routes.** Run the fixture through a Git/structured-text route with Material offline output and through a Docusaurus version/archive route; compare a WordPress draft/preview and WXR export only if authors judge the visual editor necessary. Record volunteer effort, dependency/build support, archive/search behavior, import loss, and every output-fidelity matrix cell for HTML/offline and print/PDF. Do not publish or install for volunteers. Select a candidate only after the version/archive trade-off is demonstrated.

**Phase 2 — Test local progress boundaries.** Implement or prototype one local store only after the owner chooses browser-local or native. With synthetic status records, verify no learner identity is required, no progress request is emitted, asset updates leave progress intact, and a changed revision does not inherit completion automatically. Verify restore and update-failure behavior before describing progress as durable.

**Phase 3 — Accessibility and release rehearsal.** Have an author and an independent reviewer prepare and inspect a complete synthetic release. Complete keyboard-only, screen-reader, offline search, retired-result, diagram alternative and print/PDF checks. Fix blockers and repeat the checks. Record the exact package version and supported environment. Only after a separate authorization could the group consider real material/publication or volunteer installation; neither is part of this proposal.
