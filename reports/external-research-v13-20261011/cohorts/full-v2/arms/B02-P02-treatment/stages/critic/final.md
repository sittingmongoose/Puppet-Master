## 2. Corrected proposal

### Service shape

Use one local service as the authoritative booking ledger. A staff browser interface manages resources, faults, maintenance holds, affected bookings, cancellations, interruptions, and the daily readiness view. A member browser form can provide self-service on the workshop LAN if the owner wants members to book without staff entering requests. The application and its database remain on premises. A WAN outage is transparent only while the local host/router/Wi-Fi remain available; if the local service is unavailable, requests are provisional and no slot is confirmed.

Keep the wall calendar/spreadsheets temporarily as a shadow reference during rollout, not a second booking authority. If the pilot later moves to a shared host or different database, migrate through a reconciled export/import and preserve event IDs/reasons. Do not add live member data until the owner authorizes the pilot and its data fields.

### Domain model

- **Resource inventory:** tools, shared extraction units, and supervisors/qualified supervision capacity each have identity, location, status, booking hours, and a capacity/availability policy. Track qualifications separately from a person's general account; only qualified/on-shift staff can satisfy a required supervisor claim.
- **Reservation:** owner/member ID, job/class category only if required for scheduling, requested interval, lifecycle status, and one or more resource allocations. Store interval as an unambiguous instant with a named workshop time zone for entry/display. Recommend half-open [start,end) intervals so adjacent reservations can share a boundary before buffers. Apply buffers as explicit resource-occupancy extensions consistently in availability checks and readiness views; owners still set slot granularity and buffer amounts.
- **Allocation:** one row per scarce unit/role per reservation, with an availability guard scoped to that unit and interval. Tool, assigned supervisor, and extractor claims are created or changed as a single transaction. For quantity pools, the database must enforce capacity count, not just existence of a free row.
- **Maintenance/fault:** hold ID, affected resource, interval or finite recurrence rule/end date, reason, severity/status, creator, created time, and hold state. A fault after confirmation must mark intersecting allocations as affected and show them to staff. Member edits cannot delete or weaken the hold. Staff release/extend/resolve events keep the prior hold and reason.
- **Event history:** append an event for every material booking/hold creation, edit, cancellation, interruption, displacement, override, or resolution. Record reservation/hold ID, actor and role, UTC event time, old/new values, and the supplied reason or an explicit reason code such as member request or routine edit. Require a staff reason for safety holds, fault-driven changes, displacement, and overrides; decide with the owner whether routine member changes also require free-text detail. Preserve enough to explain who changed which date/resource and why, without logging unrelated browsing, tool-use duration, or detailed work activity.
- **Readiness:** a concise staff shift/day list and a conflict queue. Member display shows availability and the member's own reservation only; another member's name/job/fault note remains staff-only. No public history or personal analytics.

### Simultaneous requests and database choices

An availability query before submission helps people understand the schedule, but is not an enforcement boundary. The final server write must acquire the resource capacity inside a transaction and either commit every required allocation or none. Return a clear conflict response naming the unavailable resource and permissible next step. A second request for the same capacity during the first commit should lose cleanly, not create a partial reservation.

For a purpose-built system, PostgreSQL range exclusion can reject overlapping allocations for the same resource and is a strong fit for a shared LAN service (PG-RANGE). Resource claims across one booking still need a database transaction. For a one-machine/single-process pilot, SQLite is a simpler candidate if writes stay short and serialized, with explicit retry/conflict handling for `SQLITE_BUSY` (SQLITE-TXN, SQLITE-WHEN). Keep the database on the host’s local disk; client browsers call the application server and never open the database file. Avoid sharing SQLite on network filesystems (SQLITE-NET). Approximately 100 members says little about simultaneous writers, so use measured synthetic load rather than headcount alone to choose.

LibreBooking is a plausible off-the-shelf candidate for a sandboxed fit check: resource relationships can require resources together and accessories can express a shared extractor quantity. A person can be modeled as a resource in the documented model, but skill/shift-aware assignment is not established. It defaults to not double-booking a resource, but resource relationships and some usage constraints are explicitly non-admin rules, so administrative booking/override behavior needs tests (LB-ADMIN). Do not rely on a software availability check alone for concurrency: the v7.0.0 source separates the validation path from persistence, and reviewed tests are rule-level, not an interleaving/database-constraint witness (LB-AVAIL, LB-AVAIL-TEST, LB-RES-HANDLER, LB-REPO).

MRBS 1.12.2 is a credible simpler alternative for a single tool/resource calendar with repeated reservations and conflict rejection (MRBS-HOME). The pinned schema stores one room ID per reservation entry and repeat series (MRBS-SCHEMA), so it is not a demonstrated atomic compound allocator for tool + supervisor + extractor. Do not join independent MRBS reservations manually and call them one booking without a dedicated transactional extension and tests. Its 1.12.2 release contains security updates and a fix for series editing with simultaneous-booking prevention enabled, which should be kept in the evaluation record (MRBS-RELEASE, MRBS-NEWS).

LibreBooking 7.0.0 is the first version named by its current repository README as beyond the disclosed critical pre-7.0.0 admin takeover; the pinned release is dated 2026-10-06 at commit `422b4b0` (LB-README, LB-RELEASE). The README observed on 2026-10-12 also announced a further high-impact security release planned for 2026-10-13 without disclosing details. Treat this as a reason to recheck the exact release/advisory at the evaluation date, not as a claim that v7.0.0 is compromised. No candidate install was made.

### Maintenance after an accepted booking

A fault is a state change on the resource and creates an affected-booking set; it does not edit the original member booking invisibly. Until staff resolves it, readiness marks the resource unsafe/unavailable and the bookings “needs review.” Staff can move, cancel, or keep a reservation pending human contact only under the adopted displacement policy. Every move, cancellation, interruption, and hold change records the old state, new state, actor, reason or reason code, and time. A staff safety/override/displacement action requires a reason; a member cancellation cannot remove the underlying maintenance hold.

This distinction matters when comparing LibreBooking’s blackout choices. At v7.0.0 the service accepts a blackout title, resource IDs, repeat rule, and conflict resolution. Its tests show “book around” splitting the blackout interval around an existing reservation and a separate path deleting/notification for a conflicting reservation instance (LB-BLACKOUT-SVC, LB-BLACKOUT-TEST). For an actual fault, silently booking around a member’s appointment can leave the machine unavailable exactly when it is shown as occupied; silently deleting the reservation loses context. The product feature is useful, but reason retention and safe displacement need a first-class event trail/custom fit check. Do not choose “delete” or “book around” as policy by default.

### Recurrence and lifecycle

Use a finite recurring schedule with visible generated instances, an end date, and per-instance exception/cancel/edit semantics. The recurrence horizon controls what staff see in advance; it is separate from the recurrence rule’s eventual end date. The draft’s “one month ahead” is a candidate view/materialization window, not source-backed policy. Confirm the horizon with maintenance planning and retain the rule plus individual changes so later edits do not rewrite past occurrences.

For booking status, distinguish request/confirmed/in-use/completed from canceled, interrupted, and needs-review. A completed or interrupted event can release future capacity while retaining its actual end, who closed it, and a reason where safety or displacement was involved. Decide whether pending approval consumes capacity, whether no-shows release slots, who can check in/out, and whether a recurring member reservation can be canceled for one instance or the remainder of its series. LibreBooking offers recurring resources/blackouts and a skip-conflicts option, but the option silently omits conflicting future instances unless the interface explains it; its history has recurrence/DST and one-instance deletion reports on particular versions (LB-AVAIL, LB-CHANGELOG, LB-ISSUE-1535, LB-ISSUE-1536, LB-ISSUE-1416). These reports motivate tests, not claims against v7.0.0. MRBS release history likewise includes repeat-series editing and cancellation fixes (MRBS-NEWS).

### Offline use, recovery, and privacy

- **WAN down, LAN up:** continue to use the local host and local accounts. Avoid external login, CDN, email, calendar API, or payment dependencies for core booking. Email reminders are optional and may be delayed/skipped when mail is unavailable; the on-screen schedule remains authoritative.
- **Host or LAN down:** no member sees reliable current availability and no booking is confirmed. Show a clear “service unavailable / provisional request only” message if the browser can render one; otherwise use a numbered paper queue or phone/staff request procedure. On restore, staff reconcile one by one against canonical resource capacity, preserving request time and contacting members about conflicts.
- **Recovery:** keep encrypted backups off the host’s disk, have at least one restore owner, document restore order, and periodically test restoration into an isolated synthetic environment. Store database/application versions and backup time with the restore procedure. The single-machine proposal must not imply that the same machine’s backup protects against disk failure.
- **Identity/data:** avoid identity documents and payments as required by the brief. Create local accounts or staff-created roster IDs; only add contact information if the chosen notification/recovery policy needs it. No mandatory third-party hosted accounts. Keep names/reasons accessible to staff who resolve bookings, hide them from other members, minimize job details, limit export fields, and decide retention/export deletion before pilot.

## 4. Owner decisions

1. Inventory and per-tool capacity: what counts as the same resource, which tools are interchangeable, and whether any tool supports parallel work?
2. Task/class matrix: which jobs need the extractor and supervisor; who qualifies; named-person assignment vs role pool; staff on-shift limits; group-supervision cases?
3. Time policy: slot precision, setup/clean/inspection buffers, opening hours, maximum booking length, recurrence horizon, and allowed advance booking?
4. Accepted-booking semantics: does a request hold capacity while pending? Who can approve? What happens to confirmed bookings after a safety fault? Who declares urgent displacement, which order/fairness rules apply, what notice is required, and can staff override?
5. Cancellation/interruption: member cancellation window, check-in/no-show release, who marks interruption, and whether a recurring member may cancel one instance or a remainder?
6. Offline workflow: is member access expected during WAN loss only, or also local Wi-Fi/host failure? Is a provisional paper queue acceptable, who reconciles it, and what contact method works without email?
7. Privacy and history: minimum local identifier/contact fields; which staff roles may see names/reasons; what report fields are necessary; retention for reservations, fault reasons, exports, and backups?
8. Operations: one workstation or always-on LAN host; named update/backup/restore owner; separate backup destination; acceptable recovery time; local power/router resilience?
9. Adoption: which staff perform the shadow period, how conflicts with the existing wall calendar are reconciled, and what acceptance threshold enables member self-service?

Until these are answered, use explicit configurable behavior and conservative blocking; do not embed a guessed capacity, fairness, or displacement rule as unchangeable product truth.

## 5. Staged adoption proposal

1. **Define policy and inventory.** Document the tool/task/supervisor/extractor matrix, capacity, hours, buffers, cancellation and displacement authority, display/privacy, retention, offline fallback, and operator. Use no member data.
2. **Synthetic fit evaluation.** In a disposable, isolated environment, evaluate LibreBooking 7.0.0 and/or a small local-first design against the decision gates. MRBS may be evaluated if single-resource simplicity is valuable, but require a demonstrated compound allocation path. Pin releases and dependencies and recheck security notices at that time.
3. **Staff shadow mode.** Staff enter synthetic or approved pilot bookings while the existing process remains the temporary authority. Reconcile every difference daily; exercise faults, blackout, and restoration; train staff. Do not allow simultaneous independent confirmation.
4. **Staff-operated pilot.** After operational/concurrency/offline/backup gates pass, use the system as the sole authoritative schedule for a limited tool set and staff-entered member requests. Review conflicts and audit reason quality weekly.
5. **Optional member browser route.** Only after policy, privacy, access-control, device/offline, and staff-support gates pass, allow member self-service on the local network. Maintain a clear outage procedure and stop confirmations whenever the canonical service is unreachable.

These stages propose future evaluation; this task did not install or deploy a product.

## 6. Validation plan and execution record

### Proposed validation

1. **Atomic concurrency:** from separate sessions, race two members for one tool; two for one named supervisor; two for the capacity-one extractor; and overlapping bookings that claim different tools but the same supervisor/extractor. Repeat with three-resource compound claims, booking edits, and two simultaneous writes through every enabled interface/API. Assert one capacity winner, no partial allocation, a readable conflict response, and retry safety. Include adjacent half-open intervals, then repeat with configured buffers. Repeat as administrator to expose documented bypasses.
2. **Maintenance race/authorization:** race a member create/edit/cancel with a staff maintenance hold; attempt member access to edit/delete a hold by UI and direct request; create two competing holds; verify active holds remain after member changes, new reservations reject, accepted overlaps remain visible as affected, and every material change preserves actor, reason/reason code, and old/new values.
3. **Recurrence and time:** create finite daily/weekly/monthly maintenance; verify end-date enforcement, horizon rollover, DST spring/fall, one-instance skip/cancel/edit, series edit, overlapping recurring blackouts, and resource timezone display. Verify no unbounded occurrence expansion and that UI plus storage agree.
4. **Lifecycle/readiness:** cancel and interrupt bookings; check actual end/resource release, history, reason, and dashboard; fault a tool after several bookings are accepted and verify staff sees each impact, member-visible conflict, state, and safe next step. Test blackout-around/delete choices only in synthetic data.
5. **Offline/recovery:** disconnect WAN while LAN/host stay up and confirm local browser booking still commits. Separately stop LAN and host; confirm no cached display is labeled current and no booking is confirmed. Reconcile provisional requests with two colliding requests. Restore a separately stored backup into an isolated environment and compare reservations, holds, reasons, recurrence rules, and history.
6. **Privacy/accessibility/operation:** member A cannot see B’s name/job/reason, staff roles see only assigned information, exports contain only approved fields, no identity docs/payment forms exist, local app has no required cloud dependency, keyboard/mobile flows are understandable, and outage/restore guidance is readable.
