# Brief-only discovery — disconnected field-survey edit journal

## Problem framing
This is a local-first data integrity and reconciliation problem across three laptops that can be offline for seven days. The product needs stable identity, durable local edits, replayable transfer, conflict review, and an explicit policy for delete-versus-photo-add. A transport database's built-in winner is not the same thing as an operator-approved decision. Notes, confidence, site identifiers, and external photo references should remain useful when media is absent. Do not assume the selected language, database, network, media size, or hosting model.

## Feasible approaches found
- **Application-owned journal over SQLite:** make events and merge rules explicit, keep a materialized observation view, and import/export idempotent batches. SQLite transactions and WAL can support local durability. Its Session extension can encode row deltas, but is compile-time optional, is constrained to primary-key tables and compatible schemas, and coalesces repeated changes; it is not an append-only audit log or semantic conflict policy. WAL is a same-host mechanism, not a shared-network-file sync protocol. SQLite's backup API provides a consistent snapshot, whereas copying a live main database file is not a safe snapshot procedure. See S01–S06.
- **Automerge/CRDT documents:** a CRDT may merge independent field edits without a central clock. The documented property-conflict API exposes concurrent values, while ordinary property reads select a deterministic operation-ID winner; the winner must not be represented as user consent. The JavaScript release inspected was 3.4.1. Rust core/mapping support is a candidate to prototype if Rust is selected, but the Rust surface and object-lineage cases need direct validation. See S07–S13.
- **CouchDB revision-tree replication:** offers push/pull, checkpoints, tombstones, and inspectable losing revisions. Its ordinary reads still choose a deterministic winner and hide other leaf revisions unless the app asks for conflicts. Tombstones are needed for delete propagation; revision history is bounded and is not a full domain audit log. Attachments may travel with replication, so references and content must be separated to honor opt-in media transfer. A 2026 upstream fix for delete/recreate attachment revision handling is directly relevant; merged code does not establish which packaged server contains it. See S14–S20.
- **Manual exchange package:** preserves operation when there is no network and can use the same event envelope as network transport. It needs schema/version checks, checksums, duplicate suppression, and transactional cursor advancement. A raw database overwrite or a live-file copy does not merge replicas; SQLite's backup facility is for consistent snapshots, not conflict resolution. This is a transport option, not an alternative merge model.

## Candidate data and behavior contract
Use an observation UUID independent of site ID, display order, or filename; give every edit a unique event ID and originating device-instance/epoch plus monotonically increasing local sequence. Record causal parents/frontier and the affected field or operation. Never use wall-clock time to select a winner. Import by event ID, tolerate reorder/replay, and atomically persist both accepted events/materialized state and the import cursor.

Merge independent fields automatically only when the event histories establish that they do not conflict. Preserve both alternatives for concurrent edits to the same field and require an explicit resolution event that cites the alternatives. Model delete as a durable tombstone for a particular observation incarnation. A photo-add concurrent with deletion must enter review or a recoverable unlinked-media state; it must not recreate the observation implicitly. Any restore should be an explicit operation linked to the tombstone, with a deliberate choice about the photo. Which fields are immutable, how duplicate observations are recognized, and whether a restore reuses an ID or creates a linked incarnation are owner decisions.

Keep photo bytes outside the replicated observation journal by default. Store a stable attachment/reference ID and observation/incarnation ID, original external link, and—when available—content hash, byte length, MIME type, and per-device availability. Make transfer of media a separate explicit action with a manifest and hash verification. A missing or changed external file must not erase the observation. Path portability, whether to copy selected photos into managed storage, and retention of orphaned photos need product decisions.

For save durability, commit the event, materialized view, and local sequence in one database transaction. If SQLite is chosen, pin the exact build/options, use declared primary keys, choose and document synchronous policy (WAL plus FULL is the safer power-loss baseline in SQLite's documented model), and keep the WAL sidecar with the database while live. Stage a media file separately, flush and verify it, atomically publish it where the platform permits, then commit its reference; recovery must tolerate an unreferenced staged file and a referenced-but-unavailable external file. Use the SQLite Backup API for snapshots. These guarantees still depend on the filesystem and storage device honoring synchronization.

## Proposed bounded integration sequence
1. Decide deletion/photo-add, explicit restore, field-level merge, identity, and media/path semantics; write examples as truth tables.
2. Prototype the event envelope and deterministic replay with two replicas, including duplicate, reordered, and delayed events. Keep policy independent of transport.
3. Implement the local transaction/materialized view and crash-recovery markers in the selected engine; add migration/version behavior.
4. Build one idempotent import/export package with manifest, checksum, batch ID, source frontier, schema version, and optional explicitly selected media. Exercise it with removable media before network sync.
5. Add the chosen network transport as another carrier for the same package/events. Do not enable photo-byte upload by default; make transfer and acknowledgements visible.
6. Add a short review surface for conflicting field values, record deletion versus incoming photo, missing media, and explicit resolutions. Pilot on copies of real-shaped data before migration.

## Operator explanation
“Two laptops changed this observation while disconnected. Review the confidence values and the photo added after the other laptop marked the observation deleted. The incoming photo has not restored the record. Choose whether to keep the deletion, explicitly restore the observation, or retain the photo separately. No photo contents are sent unless you select transfer.” Show site and observation IDs, field, both values, originating laptop, and why review is required. Avoid database jargon, timestamps as authority, or a hidden auto-winner.

## Failure-oriented validation to plan
Test abrupt power loss at each local save, media staging/reference commit, import-batch commit, acknowledgement, and snapshot boundary; after restart, verify the event log, materialized view, cursor, and media manifest agree. Inject disk-full, read-only, checksum mismatch, missing/corrupt media, unsupported schema, old/replayed packages, device reset/clone, and one laptop absent for a full week. Run concurrent independent-field edits, same-field edits, delete plus photo-add, delete plus note edit, duplicate and reordered delivery, repeated import, explicit restore, and a second round of edits after resolution. Test backup/restore and WAL sidecar handling. Benchmark 50,000 observations with representative note lengths and indexes, but vary media sizes and connection rates because the brief supplies neither. Do not prune events needed by a week-offline replica; test any snapshot/compaction rule against acknowledged replica frontiers and retained history.

These are proposed validations, not tests performed in this stage. Research retrieved and compared primary documentation, release/source code, and issue/PR history; no application implementation, automated test, crash test, or benchmark was run. The full brief and exact plan remain controlling; this document records brief-only discovery before plan release.
