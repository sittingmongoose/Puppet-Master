# Complementary truth critique — B06-P02-treatment

**Role and scope.** Independent truth/applicability review of the frozen investigator package and released plan, limited to consequential claims, conditions, exceptions, version/history framing, preservation, and validation status. The other critic owns breadth/obligation coverage. I read the assigned brief, the complete investigator discovery and draft, source-map and source index, and the released plan/reveal record; I independently revisited the primary sources indexed below. I did not edit the investigator's artifact, execute downloaded code, run a product test, access live records, or treat a proposed check as passed.

## Disposition

No material factual correction to the proposal's core direction was found in this review. The most consequential plan correction is sound: queued work should preserve authorship but be authorized against current server policy when it arrives, and a rejection should preserve the volunteer's draft for review. The plan's transactional claim arbitration and explicit stale-state review are design requirements, not properties supplied automatically by any of the compared sync libraries.

## Findings for revision

1. **Keep per-client ordering distinct from global conflict arbitration.** PowerSync documents a per-client ordered upload log that the app backend sequentially drains; it explicitly leaves backend conflict handling to the app, says the simplest implementation is per-field last-write-wins, and requires idempotent operation handling. It mentions a per-client incrementing operation ID as one deduplication option. This supports the draft's warning against inheriting LWW for issues and its idempotent backend proposal. It does not establish a total order across two disconnected volunteers, transactional one-winner claim behavior, current-role reauthorization, or same-key/different-payload quarantine. Those remain proposed application invariants to implement and validate. The draft mostly draws this boundary correctly; retain explicit labels such as “proposed server contract” wherever the event-ID and authorization rules appear. [T01; investigator S01, S02]

2. **Automerge's conflict API is a current conflict view, not a durable audit log.** The primary reference confirms deterministic same-property resolution, preservation of the losing value in `getConflicts`, and internal ordering by operation counter then actor ID rather than wall-clock time. It also says the next assignment to that property automatically resolves the conflict and removes it from `getConflicts()`. The proposal already models append-only events separately, so no architecture change is needed; add this lifecycle caveat anywhere the alternative is summarized as retaining same-property alternatives. Keep any history needed for review in the app's own event log. [T04; investigator S10]

3. **CouchDB replication is not a business merge rule.** CouchDB 3.5 docs confirm replicated branches coexist, ordinary reads/views expose only the deterministic winner by default, and application logic must merge or surface conflicts. In single-node concurrent updates, a stale `_rev` is instead rejected with HTTP 409 and the caller must retry/re-edit. The draft accurately warns that a replication winner can hide a branch and that application reconciliation remains necessary. Preserve the distinction between replication conflict leaves and the single-node optimistic-write error; do not imply every stale write silently merges. The database security API is database-wide membership guidance, not a ready-made volunteer row/field policy. [T02, T03; investigator S05–S07]

4. **PostgreSQL supports the proposed canonical guard only when the schema expresses it.** PostgreSQL 18 documents unique-index/constraint arbitration for `ON CONFLICT`; `DO UPDATE` gives an atomic insert-or-update outcome under concurrency when its arbiter and statement conditions are satisfied. A matching partial unique index can enforce at most one active claim for the chosen row model. It does not decide which offline claimant deserves the claim, handle disconnected devices, or supply human conflict review. The proposal properly describes a database safeguard and leaves fairness/reassignment to service logic and owner policy. [T05; investigator S12]

5. **Browser durability remains conditional.** Current MDN guidance describes quota failures and eviction of best-effort origin storage under storage pressure (and additional browser-specific eviction behavior); a persistence request is not a universal guarantee. The proposal correctly treats quota/eviction, pending drafts, and foreground sync as validation/design concerns. Keep the exact target browser/platform and storage outcome open until measured; do not promise a locally queued draft is durable after eviction. [T06; investigator S13, S14]

6. **Repository history is evidence of a report, not a general defect or a verified fix.** The investigator's bounded history review explicitly labels PouchDB #8599/#9093 and PowerSync #605 as reports, and the old closed PowerSync #48 as unresolved in its closure explanation. That is the right evidentiary weight. In my re-open of #9093 I could see the reviewer's objection that the claimed integration-test file was not changed; the page excerpt did not provide a reliable current status/resolution, so I do not upgrade the investigator's time-bounded status claim. Keep version, state-at-access, reporter conditions, and absence of reproduction attached to these items. [investigator S09, S16, S19; see also T07]

## Preservation, privacy, and validation checks

- The released assumption “queued writes retain original access rights” is rejected in the proposal for a good reason. Retain original actor/authorship and the unsent content, but let the service apply current membership/action authorization. An offline device cannot learn of revocation or erase its cache until it reconnects; the proposal correctly keeps cache expiry and local purge as explicit policy/design work rather than claiming immediate remote revocation.
- The attachment lifecycle correctly treats local deletion, server-side object deletion, downloaded copies on offline phones, and backups as separate states. “Remote delete confirmed” must not be phrased as “all copies erased.” Retention and backup expiry remain owner decisions.
- Read acknowledgement is separate from issue resolution, and the draft preserves that invariant without introducing reading scores. Search privacy work correctly covers free-text contact-like data and metadata leakage through snippets/suggestions/counts/offline projections; these are proposed controls to test, not documented guarantees of a sync provider.
- The listed test matrix is consistently labeled **proposed, not executed**. I did not run the proposed checks. In particular, a partial unique index proof, authorization-after-revocation, restored-device ID behavior, photo deletion propagation, search leakage, and storage eviction remain future validation tasks.
- The stage output is a critique only. It is not the final proposal and makes no vendor selection.

## Recommended reviser deltas

1. Add the Automerge conflict-lifetime caveat and distinguish conflict inspection from durable history.
2. Keep PowerSync's ordered queue explicitly per client; describe server-side claim arbitration, deduplication semantics, and reauthorization as app contracts requiring validation.
3. Preserve all repository issue states as “at access” reports, not current bug/fix claims.
4. Retain the current caveats for database-wide CouchDB roles, PostgreSQL constraint scope, offline revocation/cache delay, attachment copies/backups, and browser eviction.
