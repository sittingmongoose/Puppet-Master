# Brief-only discovery — B06-P02-treatment / investigator

**Scope boundary.** This discovery was made from the assigned brief alone, before the comparison plan was released. I did not seek or infer the withheld plan. The research points below are evidence and proposed design directions, not an implementation decision or completed validation. Source IDs are fixed in [sources/README.md](sources/README.md) and [source-map.json](source-map.json).

## Problem and requirements

The system must carry one handover across a desk computer and phones that can be offline in the loading area. It needs to show a shift leader a readable “what changed / what still needs attention” view; let a volunteer draft edits locally; later reconcile edits and duplicate task claims; and retrieve older issues. The domain entities should distinguish handovers, tasks, location notes, equipment issues, status-transition events, task-claim attempts, per-person read acknowledgements, and optional attachment metadata. Use stable client-generated IDs so independently created notes survive reconnection without relying on synchronized clocks.

A recent handover should have a compact shift summary, a chronological “changed since last handover” list, and a separately visible unresolved-issue list with location, equipment, latest status, and next action. Each entry shows when it was authored, whether its write is saved locally / waiting to sync / accepted / needs review, and (when permitted) the author. A reader can acknowledge an individual handover item. That receipt means only “I read this note”; it does not close an issue, prove task completion, measure speed, or feed a volunteer score. The app should not rank people, expose streaks, or present aggregate reading-performance measures.

## Proposed domain reconciliation

Do not sync whole mutable task/issue snapshots with a general last-write-wins policy. Model a change as an idempotent command/event with a client operation ID, actor identity, target ID, and the state generation it was based on. The backend validates and projects accepted events into a current view. A stale offline “open/unresolved” value must never roll an issue backward after a later resolution. Resolution should be an explicit transition against the current generation; a stale resolution becomes a visible conflict/proposal for a shift leader to review. Reopening is a distinct, explicit command made after viewing the resolved state, with its own actor and reason. This is a design inference from the domain invariant, not a vendor capability claim.

Treat a task claim made without a server round-trip as **provisional**. Two phones offline can both honestly show that their volunteer asked to claim the task; neither can promise the other phone knows. On sync, preserve both attempts and arbitrate in a server transaction or surface the collision to the leader. Show the accepted claim and notify the other claimant; do not silently discard their work. A unique active-claim constraint can protect the online canonical state, while a duplicate/late command returns a specific review outcome. Do not choose a “winner” by device wall-clock timestamp. For physical work, the offline UI should also suggest the existing verbal/physical handover fallback until a claim is confirmed. These are proposals to validate.

For older-issue search, index only approved content: issue title/body with contact details excluded or redacted, equipment category, approved location, status, and date range. Filter by authorization before returning rows, snippets, suggestions, counts, or offline results. Keep volunteer contact records out of the search schema and the phone’s synchronized projection. A free-text report may still contain an accidentally typed phone number, so input guidance and server-side redaction/exception handling need validation. Role boundaries and the treatment of author names remain owner decisions.

## Sync and shared-access alternatives

| Alternative | Fit for this case | Costs and failure modes to prove |
| --- | --- | --- |
| **PowerSync-style SQLite client + relational source database** | Local SQL views and offline reads/writes with a change upload queue; the backend can decide whether a mutation is applied. This is a promising first spike if a relational operator and service owner are available. [S01, S02] | The SDK does not choose domain conflict policy: its docs describe ordered queued PUT/PATCH/DELETE operations, expect idempotent uploads, and say simple backends commonly use per-field last-write-wins. Explicitly reject stale state transitions and make claims transactional. A service/auth/database boundary, operating cost, backups and owner are still needed. Repository background-sync demo says the OS decides when a mobile task runs, so “background sync” cannot be the only delivery path. Attachment examples are in flux: one helper is deprecated and the React Native file adapter is explicitly alpha. [S03, S04, S15] |
| **PouchDB on devices + Apache CouchDB server** | A direct local/remote bidirectional replication model is purpose-built for disconnected peers and can be self-hosted. It is a plausible alternative if the organization values open-source control and can operate CouchDB. [S05, S06] | Same-document revisions can branch; ordinary reads show the deterministic winner without indicating there are hidden conflicts unless the caller asks for conflict metadata. App-level merge is still required. Database “members” broadly read/write documents rather than supplying an assumed fine-grained roles product, so validation functions and application scoping matter. The 9.0.0 release reports IndexedDB stability work, but issue/PR history includes an open IndexedDB sequence/concurrency report and an open proposed fix; treat browser storage, parallel writes, migration/pagination and attachments as spike risks, not as fixed by release wording. [S05, S07, S08, S09] |
| **Automerge / CRDT local-first documents** | Independently authored notes and list additions can merge while offline, and the underlying CRDT retains same-property alternatives for inspection. It is attractive for collaborative text or note content. [S10] | For concurrent writes to the same property, Automerge chooses a deterministic default and exposes losing values through its conflict API; this does not enforce “resolved cannot silently reopen” or exclusive task claims. Its sample repo sync server says it is unsecured and partly for demonstration, so a real deployment needs an authorized server/share policy. Keep it as a bounded prototype for free-text notes, not a substitute for domain transition rules. [S10, S11] |
| **Custom responsive client + local database/outbox + API/PostgreSQL** | Gives the clearest central rules for claims, stale transitions, search authorization and audits without buying a generic merge policy. A PostgreSQL unique/partial-unique index and atomic ON CONFLICT path can enforce canonical invariants under concurrent online requests. [S12] | The team must build durable local storage, retries, idempotency, conflict UI, filtered downloads, and device behavior. A browser PWA’s IndexedDB/cache storage is best-effort by default and background work is bounded/browser-controlled; a foreground retry/sync status is mandatory. For a phone-first app, compare a native SQLite client if browser storage persistence proves inadequate. [S13, S14] |

**Non-product constraint.** “No new commercial account for each volunteer” still leaves a need to know who authored a change and whose acknowledgement was recorded. Prefer a center-owned workspace and identity lifecycle (or a deliberate pseudonymous shift identity if the owner accepts the audit tradeoff), not personal vendor subscriptions. Do not assume a shared login satisfies attribution or privacy. Select identity provider, access rules, volunteer offboarding, and any fee-bearing operator/service only after the center decides ownership. Unknown role and retention rules stay open decisions.

## Photos and constrained data

Photos remain optional. The user can save the text handover without one. On selection, show estimated bytes and provide a small on-device resized copy; remove location/EXIF metadata by default, preview before upload, and allow cancel. Keep the attachment queued locally and visibly pending; upload only on Wi-Fi by default, or after a clear mobile-data confirmation, with per-file progress and retry after interruption. Never block saving the note on upload completion. Keep large files out of the general row-sync channel. The source records show separate attachment queues/local files/remote storage are an integration concern rather than automatic conflict handling; current sample-package stability must be checked for the chosen platform. [S03, S04]

Deletion should be an explicit authorized delete request/tombstone linked to the attachment ID. Delete the device copy promptly, stop queued retries, remove the remote object through a retryable server operation, revoke any access URL, and show “deletion pending” until the remote operation confirms. State clearly that backup expiry and legal/organizational retention cannot be promised until the owner chooses a retention window and backup-erasure process. A deleted database row or local cache cleanup alone is not proof that all stored copies have been erased. This lifecycle is a proposal, not an observed product guarantee.

## Adoption and failure-oriented validation proposals

1. **Decide ownership and policies.** Confirm service owner and support person; identity/offboarding; who may read, create, claim, resolve, reopen, and delete; approved locations/contact handling; photo consent; retention and backup deletion. Keep unresolved decisions visible in the proposal.
2. **Prototype on synthetic data.** Build a clickable or thin technical spike for one desk browser and two phones using invented handovers/issues, with a paper/whiteboard fallback. Exercise text-first use with photos disabled. No live center records or invitations during this research.
3. **Compare two paths using the same scenarios.** Run a short implementation spike for relational + queued local SQLite (PowerSync-style) and the custom API/outbox baseline; optionally add a PouchDB/CouchDB replication slice if self-hosting is a priority. Score scenario outcomes, owner burden, privacy/access fit, and deployment/account cost; don’t compare only happy-path feature lists.
4. **Only after owner approval, pilot narrowly.** First use synthetic scenarios in a tabletop; then a small, time-boxed pilot with agreed low-sensitivity data and a named leader, after role/retention decisions. Keep a paper fallback and review every conflict/failed upload before any wider use. The proposal recommends this future sequence; no real invitations or deployment were made here.

**Failure-oriented validation to propose (none executed in this stage):** (a) two phones claim one task while both offline, reconnect in either order, duplicate a retry, and confirm one canonical claim plus visible review for the other; (b) phone A holds an old open state while phone B resolves, then A reconnects, proving issue does not reopen; separately test an intentional authorized reopen; (c) read receipt leaves issue unchanged and a resolved issue can be acknowledged independently; (d) interrupt text sync before request, after server commit, and before client confirmation, then replay and verify exactly one event; (e) disconnect during large-photo upload, switch from Wi-Fi to metered data, cancel, delete offline, retry after reconnect, and inspect local file/remote object/status; (f) fill/revoke local storage and simulate browser eviction/app kill, then ensure pending drafts are disclosed and recovery/fallback is clear; (g) search for synthetic phone/email strings in titles, snippets, autocomplete, counts, and offline results under each test role; (h) test retention/delete propagation and backup expiry against the owner’s eventual written policy; (i) test 30 synthetic accounts around a shift change, with degraded network, duplicate submissions, and older-issue pagination. Record proposed checks separately from checks run.
