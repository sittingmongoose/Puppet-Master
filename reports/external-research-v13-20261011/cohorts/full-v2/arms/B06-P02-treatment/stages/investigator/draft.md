## Proposal

Build around a small, stack-independent domain model: handovers; tasks; location notes; equipment issues; append-only comments and transition events; task-claim attempts; per-person acknowledgement receipts; attachment metadata; and a current summary/search projection. Assign client-generated random IDs to events and entities. Each operation carries its actor/device, target, operation ID, creation time for display, and base version/generation when it changes state. The server deduplicates exact retries, rejects a reused operation ID with a different payload, applies access policy at receipt time, and returns an explicit result: accepted, already applied, rejected, or needs review. Device timestamps order the story visually; they do not decide business conflicts.

The most promising first comparison is relational source-of-truth plus local SQLite and an explicit queued mutation path (PowerSync or a custom outbox/API). It combines convenient local queries with room to enforce the rules below. This does **not** select PowerSync, Supabase, or any commercial service. Compare a PowerSync-backed implementation with a small custom API/outbox under the same synthetic failure scenarios; add PouchDB/CouchDB if self-hosting is a priority, and Automerge only for a bounded collaborative-note experiment. Choose only after a named operator, identity model, security boundaries, platform support, service cost, backups, and retention are understood. [S01, S02, S05, S10, S12]

### User-facing workflow

- **Start a shift:** On desk or phone, show the most recent handover, compact “what changed” entries, issues still open, owner/next action, and a clear last-sync time. Clearly label the age of offline content. Keep the active shift plus an agreed bounded set of searchable older issues locally; the set and cache lifetime need an owner decision and storage testing.
- **Read and acknowledge:** A volunteer explicitly marks a handover item read. Store an acknowledgement receipt separately from issue/task state. It only helps the next handover identify which notes were seen. Do not expose scores, response-time rankings, streaks, or an individual productivity dashboard. A read receipt must not imply the issue is resolved; resolving an issue must not imply the person read every note.
- **Write offline:** A volunteer can draft a task, location note, issue, or comment and save immediately on-device. Show whether it is local-only, queued, synced, rejected, or awaiting review. Keep the text usable without a network and photos. Sync on foreground/open and retry safely; do not promise immediate background delivery.
- **Claim work:** An offline claim is provisional: “claim requested on this device,” not a lock visible to everyone. Explain that a second disconnected phone may request the same task; retain both requests. At reconnection, one can be accepted under a server-side uniqueness rule, while the other stays visible for the leader to resolve/reassign. Do not silently lose a volunteer’s work or pick by the handset’s clock. Keep a verbal/physical fallback for work that cannot wait for network reconciliation.
- **Resolve an equipment issue:** Resolution is an explicit event against the currently visible issue generation, with actor and reason. Comments can be appended after resolution without changing its state. If a comment suggests the fault returned, flag it as a new concern for review; do not automatically reopen. Reopen requires an explicit command after showing the current resolved state. A stale offline transition is shown in a review queue and cannot restore an old “open” snapshot. A claim against a resolved issue pauses for review.
- **Search history:** Search approved issue title/body, equipment category, approved location, status, and date. Never include private phone/email/contact fields in the index or synced search projection. Apply access filters before results, snippets, suggestions, counts, or offline search. Add input guidance/redaction for contact-like strings that volunteers may type into a free-text note. Which users may see author names and historical locations is a role/privacy decision, not assumed.

## Alternatives and selection criteria

| Approach | Advantages here | Limitations / decision gate |
| --- | --- | --- |
| **Relational database + local SQLite + PowerSync or equivalent** | Offline SQL views and an ordered mutation queue are documented; the backend can apply a domain-aware policy instead of a hidden client merge. It supports a clear central search/authorization boundary. [S01, S02, S15] | PowerSync docs explicitly leave backend conflict handling to the application; simple per-field LWW is the default example, and operations may be replayed, so handlers must be idempotent. A 2025 open queue report is one reporter’s unresolved case, not proof of a general defect; an older closed transaction-grouping report does not show how it was resolved. Evaluate burst writes, replay, SDK release maturity, fees, host, auth, attachments, and operators. [S01, S16, S19] |
| **PouchDB + CouchDB replication** | Multi-master replication supports disconnected device copies and can be self-hosted. Conflict branches and tombstones are explicit and inspectable. [S05, S06] | Application must detect/resolve branches: ordinary reads hide losing revisions. Broad DB-member rights are not the same as row/field authorization. PouchDB 9.0 release claims IndexedDB stability improvements and a 25-row default find limit; a 2025 proposed concurrency patch remains open in the inspected source history and changes one JS source file, with a reviewer noting its claimed test file was not changed. Do not infer the fix shipped. Test search paging, replay, delete, and browser storage on target releases. [S05, S07, S08, S09] |
| **Automerge CRDT for collaborative notes** | Concurrent list/text edits can merge locally without a central merge round-trip; same-property alternatives remain accessible. [S10] | A deterministic field winner is still a policy choice, not a safe task/issue state machine. The public sample sync server is described as unsecured/demo; real identity, authorization, storage lifecycle and search need separate design. Test only a note-edit slice unless the team is prepared to design domain commands around it. [S10, S11] |
| **Custom API + local outbox** | Direct control over authorization, stale-state validation, claim arbitration, search filtering, attachment lifecycle and owner-managed identities. PostgreSQL unique constraints/partial indexes and atomic ON CONFLICT are useful canonical safeguards. [S12] | More code and ongoing operational ownership: client persistence, queue/retry, schema, errors, sync status, offline authorization/cache expiry, and migrations belong to the team. Browser storage can be evicted and service workers can be stopped; use an explicit foreground sync affordance and consider native SQLite if PWA persistence is not good enough. [S13, S14] |

The brief does not establish a winner among these. A short architecture spike should use the same event contract, search rules and failure matrix on two finalist implementations. Compare not only whether a demo works offline, but who administers identities, corrects failed sync, restores backups, deletes retained data, pays any service fees, and supports volunteers on low-end phones.

## Photo, retention, identity, and search policies

**Photo state model:** local draft → upload queued (after user action) → uploading with bytes/progress → remotely available → delete requested → remote delete confirmed. Error/retry and cancellation are explicit states. Keep the text event valid if the image upload fails. Persist a small attachment ID and non-sensitive metadata with the issue, while storing bytes in a separate object store. Server owns authorization and a retryable deletion operation; each device cleans its cache when the delete tombstone arrives. A physically offline phone and backups are exceptions that must be covered by chosen cache/retention policy, not hidden by UI wording. The exact retention period, archival rule, and backup-erasure guarantee are unresolved organization choices. [S03, S04, S14]

**Identity and roles:** one center-owned workspace/service is compatible with avoiding individual commercial subscriptions; each volunteer still needs a defined app identity if actions or receipts are attributable. Whether that identity is a pseudonym, named volunteer account, one-shift alias, or shared station session is not inferable from research. Define role rules for read, create, claim, resolve/reopen, search, and delete. Reauthorize queued operations at receipt time. Define offline-cache and credential expiry for a user removed while disconnected. Workshop invite codes must be single-use or individually attributable if used to bind identities; shared bearer codes do not answer this. [S02, S07, S17]

**Search:** maintain a deliberately small permitted search document or projection. Never index contact tables; scrub/mask phone/email patterns from free text before saving to search; avoid returning the original sensitive text in snippets. Server authorization must apply before query results and metadata, and offline search only sees the downloaded authorized projection. Keep an audit event for query access only if the owner policy calls for it; do not create a volunteer-monitoring feature. Search retention and historical author visibility remain open decisions. [S02, S07]

## Adoption sequence

1. **Name the owner and policy questions.** Identify a service operator and a volunteer-facing support owner. Decide roles, who may see author identity, code issuance/offboarding, offline cache/credential expiry, retention/backup erasure, photo consent and size limits, and the fallback when sync is delayed.
2. **Tabletop one shift on synthetic data.** Model two tasks, one location note, one unresolved equipment issue, a resolution, two duplicate offline claims, read receipts, and a photo. Use desk + two phones; turn off connectivity at different steps. Keep a paper copy. No real account, invitation or center data.
3. **Run an implementation spike with synthetic data.** Compare PowerSync + relational service against custom local outbox/API; include PouchDB/CouchDB if self-hosting is the deciding constraint. Record setup/operations burden, same-domain failure outcomes, install/login friction, offline storage, accessibility on older phones, and service/hosting cost. Do not select from feature claims alone.
4. **Close policy before real use.** Obtain named owner decisions for role, retention, identity, photo consent and data deletion. Then, if approved, pilot with a small group for one bounded period, low-sensitivity records only, and a named shift leader reviewing conflicts. Maintain the existing physical fallback, collect only usability/sync outcomes needed for improvement, and do not score volunteers.
5. **Expand only after review.** Check unresolved conflict and deletion cases, support workload, low-signal outcomes, and whether any volunteer still needs a paid external account. Decide whether to continue, revise, or stop before wider adoption.

## Failure-oriented validation plan — proposals, not executed checks

1. **Two offline claims:** phone A and B claim one task offline; test both reconnect orders, retries and a dropped client response after server commit. Expect at most one canonical accepted claim, both attempts retained, and explicit leader/volunteer feedback. Repeat for a resolved issue and verify claim pauses for review.
2. **No stale reopen:** A caches issue generation n as open. B resolves generation n+1. A later submits its old snapshot or comment. The current issue must remain resolved; stale transition is visible for review. A deliberate reopen must be a distinct, authorized event with current generation and reason.
3. **Receipt separation:** acknowledge an unresolved issue and verify it remains unresolved; resolve an issue and verify no volunteer receipt is fabricated. Confirm no score, ranking, streak, or speed aggregate appears.
4. **Idempotency/restore:** interrupt before upload, after server commit, and before client acknowledgement; replay. Identical operation ID/payload applies once. Same operation ID with different payload is rejected and preserved for diagnosis. Restore one backup to two test devices and verify new IDs and session/device enrollment do not collide.
5. **Revocation:** queue a write, revoke the synthetic actor while offline, and reconnect. Server rechecks permission; event is returned rejected/review-required with original authorship preserved. Test expiry/purge policy for cached sensitive data and label the unavoidable disconnected-device window.
6. **Search privacy:** seed synthetic phone/email strings in contact fields and accidental note text. Under each test role, search titles, body, suggestion list, snippets, counts, pagination and offline cache. No protected contact value should be disclosed; authorized older issues should still be findable.
7. **Photos/low data:** on Wi-Fi, mobile data and airplane mode, attach a photo only after confirmation. Interrupt/retry/cancel upload, delete while offline, reconnect one other phone that has a copy, and verify each visible status. Check no auto-download, no original GPS metadata, object deletion retry, and backup/cache expiry against the eventual policy.
8. **Local durability/platform:** kill/restart app, fill storage, deny persistence, let browser evict a synthetic cache, and test foreground/background behavior on the actual supported phone/browser versions. Pending text must be clearly disclosed and the paper fallback must remain usable. Do not rely solely on background sync; browser/OS scheduling is conditional. [S13, S14, S18]
9. **Shift scale/search:** simulate about 30 test identities around a shift change, burst repeated edits and claims, and page older issues. Confirm responsive summary, no duplicate event, no dropped operation, authorization filtering, and legible conflict messages. This validates the stated scale; it does not claim a particular database capacity result. [S08, S16, S19]
