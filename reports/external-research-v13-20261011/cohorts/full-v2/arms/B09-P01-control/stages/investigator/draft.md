## Comparison without selecting a winner

| Approach | Evidence-supported fit | Material gaps to prove |
|---|---|---|
| **Koha 26.05.04, self-hosted** | Mature circulation concepts, barcode-level items, due dates, optional notices and native bundles with per-part return scanning [K01–K04]. Best documented lending/kit workflow in this review. | Library configuration and privacy model may be more than this group needs. Damaged flag does not block circulation; override defaults to Allow; a separate not-for-loan transition may be required [K04, K09]. Claim-return is not a general immutable correction ledger [K02]. Offline workstation logs need ordered replay and use stale state [K06]. |
| **Snipe-IT 8.8.0, self-hosted** | Clear individually tagged assets, deployable/unavailable status model, importable historical asset events, backup/restore documentation [S01–S08]. | Borrower lending, removable kits, alias lookup, and immutable correction behavior are not fully established by reviewed docs. Importer locking is path-specific. Verify status on return, event retention, notification suppression, and concurrency through the actual UI/API [S02, S07–S10]. |
| **InvenTree 1.5.7, self-hosted** | Traceable stock items, event tracking, part/assembly relationships, and Docker deployment [I01–I03]. Could suit detailed parts management. | Documentation is manufacturing/stock-centered rather than a ready lending/borrower workflow. The take-stock race fix concerns inventory counting, not checkouts [I04]. Verify lending workflow or budget custom work. |
| **Small custom LAN service** | Can encode exact item, event, kit, maintenance-hold and coordinator rules; a transactional database provides suitable primitives [A02]. | Highest continuing build/patch/security/support burden; not a free shortcut. Must explicitly design permissions, migration, audit, logs, backups, recovery and outage workflow. |
| **Separate laptop databases/files** | Superficially available during coordinator outage. | Not recommended as authoritative shared inventory. SQLite WAL will not work across a network filesystem and serializes writers [A01]; independent local copies still need an explicit conflict protocol. |

Selection should follow a fit prototype rather than a score based only on feature lists. Koha deserves first testing if native lending and kit checking are decisive. Snipe-IT deserves first testing if simple asset tagging/status and operational familiarity dominate. InvenTree is a parts-traceability comparator. A custom build is justified only if the prototypes fail critical requirements and an owner accepts long-term maintenance.

**Cloud and deployment constraint:** use self-hosted services on a locally managed host/LAN; no paid cloud account is required by this path. Koha’s manual describes GNU/Linux server operation, specialist administration and no production-ready Docker container; Snipe-IT self-hosting requires a database, local configuration, dependencies and webserver. InvenTree documents a self-hosted Docker stack [K10, S11, I03]. This avoids paid cloud while leaving hardware, patching, backups and operator time to be owned and funded.

## Proposed data and transaction contract

- **Physical item:** permanent `item_id` key, printed barcode, model/type, manufacturer serial if present, aliases, location, condition, lifecycle state, and creation/retirement events. Do not derive identity from mutable name/serial.
- **Loan/event:** unique loan/event IDs; event type (checkout, return, correction, hold, release, retirement), item ID, actor, UTC timestamp, due date if set, condition/completeness, explanation, and links to earlier events. A correction appends a correcting event that references the original and states actor/reason; it never erases the original.
- **Current state:** `available`, `checked_out`, `maintenance_hold`, or `retired`. Derive or update it in the same transaction as its event. Only an authorized clearance event can release a maintenance hold. A due date never changes state.
- **Kit:** parent item plus expected child item IDs and quantities. Checkout and return scan the parent and all expected children; missing/damaged pieces put affected child and kit into a defined review state.
- **Borrower:** separate record with the minimum identity and any explicitly approved reminder channel; role-limited display; retention/anonymization policy independent of item event history.

For each checkout, the server should validate the item is available, lock/claim it, create the event, and set state in one transaction; commit before acknowledging success. A duplicate request with the same idempotency key returns the original result. A distinct concurrent request waits or fails clearly after the first commit. Use database constraints in addition to UI checks. For a damaged/partial return, save the return event and maintenance state atomically so no volunteer can observe an intermediate available state.

The LAN design serves both laptops from one coordinator. Internet loss while the LAN is reachable should not affect local transactions. For coordinator/LAN loss, the safe default is to stop accepting digital checkouts and returns. If owners need emergency lending, one paper ledger and one assigned authority can provide a controlled, auditable exception at one location; reconcile it before re-enabling checkouts. Two disconnected device logs are not the default. SQLite/WAL on a network share is ruled out [A01]. PostgreSQL locks are a primitive, not a complete transaction policy [A02].

## Validation and recovery plan — proposals, not executed checks

1. **Synthetic catalog:** 10–20 records including two drills with the same display name, two similar ladders, aliases/typos, absent or duplicate manufacturer serials, retired unit, multi-part kit and one part shared/replaced. Confirm every search result displays the physical ID and distinct attributes.
2. **Two-laptop race:** both clients read one item as available and attempt checkout together. Pass only if exactly one distinct loan is accepted, exactly one active loan remains, and the losing client sees the committed borrower/state. Retry the winner’s request with the same idempotency key and confirm no duplicate event.
3. **Return/hold:** return a damaged tool and an incomplete kit while another client refreshes/attempts checkout. Pass only if the event and hold commit together and the item cannot be loaned until an authorized release. Test every vendor override/status path, including Koha not-for-loan override disabled.
4. **Corrections/retirement:** correct a wrong return date/item/condition. Pass only if original and correction remain linked with actor, timestamp and reason. Retire and restore a unit; pass only if identity and loan history persist and restored state is explicit.
5. **Outage:** remove Internet while LAN remains, then separately make coordinator/LAN unreachable. Confirm normal operations during Internet-only loss. For authority loss, prove default fail-closed or rehearse the owner-approved single-paper-ledger path. Deliberately create conflicting provisional events in a test fixture; they must be detected and resolved before any accepted digital checkout.
6. **Migration:** export existing spreadsheets first; retain an immutable source copy and mapping manifest. Reconcile all 800 item identities, duplicate names, active loans, kits and five years of history. For ambiguous old rows, preserve them as unresolved and do not invent a physical-unit match. Compare row counts, stable IDs, event order, active-loan/status totals and sampled provenance.
7. **Recovery:** back up database, files/uploads and configuration to separate storage. Restore to an isolated host at a pinned version. Compare hashes/counts and verify active loans, event order, identities, aliases, kit membership, maintenance holds and retired-item history. Time the restore and record data loss boundary; owners set RPO/RTO and approve the result before cutover.
8. **Privacy/messages:** populate synthetic borrowers only. Inspect every role’s item/borrower views; run a staff-reviewed overdue report; verify no mail, Slack, webhook or scheduled notice leaves the test environment. Confirm retention/anonymization does not erase item history or correction explanations.

Gate each phase: policy and ownership first; synthetic fit tests second; repeatable import/restore and outage exercises third; small controlled pilot fourth; full cutover only after reconciliation and recovery sign-off. Shadow work must not create two live authorities. Keep the old lists read-only at cutover and document rollback criteria.

## Decisions still belonging to the organization

1. Loan length, renewal, holds/reservations, fines, and what “overdue” means.
2. Whether any offline lending is allowed; if yes, one authority, location, maximum duration, tracking form, custody and reconciliation rule.
3. Required borrower identifier and whether a reminder channel is collected at all; staff roles allowed to view it and retention/anonymization schedule.
4. Who may create/correct a loan or return; required correction reason/evidence; who may clear a maintenance hold.
5. Which kit pieces get their own barcode; completeness, missing-piece, replacement and damaged-part rules.
6. Archive/retirement/loss lifecycle and any exception allowing item deletion; history must remain available.
7. Hosting, patching, security, backup and restore owners; recovery targets and outage decision authority.
8. Cutover date, reconciliation tolerance, rollback owner and acceptable unresolved legacy-history rows.

These decisions cannot be settled by product documentation. The comparison sources describe product behavior and defaults, not neighborhood policy.
