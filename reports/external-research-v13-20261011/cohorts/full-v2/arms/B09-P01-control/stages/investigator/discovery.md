# Brief-only discovery — neighborhood lending inventory and returns

**Plan status:** This discovery was written from the exact brief only; the assigned plan had not yet been released or read. This is a research proposal, not a product selection or implementation.

## Findings and feasible approaches

A checkout should identify one physical unit, not just a model or name. Give every owned item a durable, organization-issued, unique barcode/ID that is never reused; keep manufacturer serial, category/model, aliases, and location as separate searchable attributes. Search should resolve aliases to the model but display the physical tag, distinguishing attributes, and current state before checkout. Koha separates a bibliographic/model-like record from individual items and supports item barcodes, but its default catalog model and terminology are library-oriented [K03]. Snipe-IT makes asset tags central and supports serials/custom fields; its asset model defines availability by assignment, deletion, and a deployable, non-archived status [S03, S07]. Neither reviewed source set establishes a complete alias workflow for near-identical household tools; test alias ranking and duplicate-name disambiguation with real catalog data.

Three candidates merit a staged comparison, without presuming a winner:

- **Koha 26.05.04** has the strongest documented lending and bundled-item workflow. A staff member checks out a patron and scans the item barcode; checkout records show due dates, while automatic check-in exists only when item types and a cron job are configured [K01, K02]. Bundles are first-class: constituent items remain separate barcoded records and are not ordinarily individually loanable; return asks staff to scan each expected piece. Missing pieces become lost and generate a claim tied to the checkout [K02]. That is a useful kit fit, but missing-part claims do not prove general append-only correction history. The normal claim-return feature similarly records a note and optional lost fee; it is not evidence of an immutable correction ledger for every loan/return [K02]. The 23.05.02 release history documents bundle-state and offline-tool defects/removal, so test the exact current release and do not infer reliability from feature presence alone [K08]. Koha’s Firefox and Windows offline tools require gathering logs from every workstation and replaying all events in order (checkout before return); local offline use can miss blocks/availability changes and is not multi-writer live consistency [K06].
- **Snipe-IT 8.8.0** is a simpler asset-custody candidate. It supports unique asset tags, item status labels, check-out/check-in notes, and statuses that make an item deployable or unavailable [S02, S03, S07]. A maintenance/undeployable state can represent a hold, but the return screen and status transition must be tested as one controlled operation; do not assume an item is held automatically on a “damaged” return. Its component model is aimed at components installed in assets, not removable loan-kit contents, so a kit may need a parent record plus explicit child IDs or a documented work-around [S02]. Built-in asset history import depends on existing tags and users and ordered history data [S04]. Snipe’s version history includes a duplicate-checkout fix and a security patch for API checkout to soft-deleted targets; pin a maintained release and include regressions in acceptance testing [S01, S09, S10]. A v8.8.0 importer locks the row before rechecking eligibility, but that evidence is importer-specific, not proof that every UI/API route is race-safe [S08].
- **InvenTree 1.5.7** provides serialized stock records, tracked events, and assembly/BOM relations with a self-hosted Docker/PostgreSQL deployment path [I01, I02, I03]. Its docs center on production stock/manufacturing rather than a volunteer borrower/return desk; treat it as a candidate for part traceability, not as a ready-made lending workflow. A 1.5.x fix for a stock-taking race was merged and assigned to the 1.5.3 milestone; this demonstrates why workflows and current release history need review, but does not validate loan checkout concurrency [I04].
- **A small custom LAN application** could directly model checkout, return, maintenance hold, correction reason, kit membership, and immutable events, but creates ongoing security, backup, support, and upgrade obligations. An authoritative server on the normally available local network is safer than two offline authorities. Use a transactional server database, atomic item-state transition, unique constraints and event append; PostgreSQL row locks can serialize competing updates [A02]. Do not put a shared SQLite/WAL database on a network file share: WAL requires same-host shared memory and allows only one writer at a time [A01].

## Workflow and policy recommendations

Keep loans and item state separate but transactionally consistent. Model each physical item as available, checked out, maintenance hold, or retired. A due date is a reminder datum, never a return event. A return event records time, volunteer, condition, kit completeness, and optional explanation; a correction appends who/when/why and the replacement interpretation while retaining the original event. Retired items stop being loanable but retain identity and history. Do not allow a “damaged” flag alone to expose an item as available. Koha’s damaged flag marks search results unavailable but does not prevent check-in or checkout. A positive not-for-loan status can block checkout, yet the override preference defaults to Allow; disable that override and test the exact return/status transition. Check-in mapping only maps a pre-existing not-for-loan status, not the damaged flag [K09, K04]. For Snipe-IT, use a non-deployable status only after checking that return and status changes cannot race or leave the item deployable [S07]. These behaviors need a two-client race test in any selected system.

A kit should have a durable kit identity, explicit expected child-item IDs, and a scan/confirmation of every removable part at return. Define missing, damaged, and partial-return rules and who may clear a hold. Koha’s native bundle behavior is the closest documented match; its “missing becomes lost” policy and skip-verification option require an owner decision and training [K02].

For aliases, maintain normalized aliases attached to the model/type record, with duplicate and typo-tolerant search only as a tested aid. Checkout must select the individual unit after search. For borrower data, first decide which name/identifier and one reminder channel are truly needed; decide access, retention, and anonymization before importing five years of personal data. No borrower messages should be automatically sent. Koha’s StoreLastBorrower default is zero, yet the manual says three last borrowers may still be shown unless checkouts are anonymized; this privacy behavior must be configured and verified, not inferred from the preference name [K04, K05]. Snipe notifications depend on channel/category settings; keep mail/notification jobs disabled until the organization explicitly adopts a policy [S05].

All three candidates can be self-hosted without a paid cloud account, but that is not zero-cost operations: someone owns patching, TLS/access control, monitoring, exports, and restore tests. Internet outage can be tolerated while the local server and LAN work. If the LAN/server fails, stop authoritative checkout/return writes unless the selected system has a tested event queue with ordering, idempotency, and conflict resolution. Do not promise live availability from isolated laptops. As a workload inference rather than a measured benchmark, 800 items is modest; the harder five-year issue is accurate migration, retention, and auditability, not assumed throughput.

## Open decisions and proposed adoption

Owners must choose loan length/renewal and overdue handling; whether holds/reservations or fines exist; required borrower identity/contact and reminder channel/purpose; who may correct events and what evidence is recorded; retention/anonymization windows; volunteer permissions; kit-completeness and damage criteria; who clears maintenance holds; retirement/loss rules; what happens during LAN/server outage; local hosting and patch responsibility; backup ownership and recovery-point/recovery-time targets. No legal or product winner is inferred.

Adopt in gates: (1) decide policy, assign owners, inventory current lists, map each physical item and historical loan to a non-reused stable ID; (2) build a clean representative fixture with duplicate names, aliases, similar models, multi-part kits, damage, retirement and five-year sample records; compare the three products and any custom option; (3) rehearse imports and two-laptop simultaneous checkout/return, LAN loss, no-message settings, correction-history preservation, and backup restoration before borrower data enters the system; (4) pilot a small labeled collection with trained volunteers and a reconciled old/new ledger; (5) expand only after sign-off and verified migration totals. For recovery, keep versioned database, uploads, and configuration backups on separate storage; restore into an isolated host; compare item/tag uniqueness, current active loans and statuses, event/history counts and ordering, aliases, kit membership, and a sample of every migration mapping. Record an export manifest, checksums/counts, and measured recovery time; owners set RPO/RTO. These are proposed validations, not checks run.
