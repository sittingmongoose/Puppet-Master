## Discovery findings and alternatives

### What the workflow needs to preserve

A shift-start screen should summarize changes since the previous handover cutoff: new work, changed tasks, added notes, open equipment problems, and explicit resolutions. It should keep unresolved issues visible across shifts and show source time/author or sync state so a reader can distinguish current server state from a locally pending change. A small handover digest is more intelligible than a raw stream of every edit.

A read acknowledgment is a separate event tied to a note and a volunteer identity. It must not change an issue's status, close a task, or create a person-by-person read count, ranking, completion rate, or performance score. The user-facing choice can simply let a volunteer mark a note as read; whether a leader may see individual acknowledgments or only their own is an organization decision.

Offline exclusive ownership cannot be guaranteed by disconnected phones that can both accept a claim. Preserve each claim as an independently identified action and mark it provisional until a connected authority reconciles it. On reconnect, retain both claimants and show a leader an explicit assignment choice. An alternative is to make offline claims provisional suggestions and confirm exclusive ownership only after server acceptance. If the organization requires a hard lock before reconnect, it must choose to disable offline claiming; a local UI cannot create distributed exclusivity. Keep claim activity and task text separate so routine notes can still be appended.

Represent issue state changes as explicit, validated transition operations with a server revision or expected prior state, unique operation ID, actor and timestamp. A stale offline “resolve,” “reopen,” or edit to status should be rejected or held for review if the server has already resolved the issue; it should never be replayed as an unconditional field replacement. A deliberate reopen is a separate visible command with actor and reason. Free-text observations may be appended as separate notes while the leader reviews state. This is an application rule, not a guarantee supplied by a sync engine.

### Feasible synchronization choices

1. **PouchDB on the phone/browser with CouchDB at the center.** PouchDB stores local data in browser IndexedDB and can sync changes to a CouchDB-compatible server for offline use [S01–S04]. CouchDB supports one-way replication and a two-way arrangement made from opposite directions. Local single-node stale-revision writes can return 409, while changes from disconnected replicas can leave multiple revisions; ordinary reads and views expose only a deterministic winner, so application code must discover and resolve conflicts [S05–S07]. This is a strong candidate where document replication and self-hosting are valued and the team is prepared to build conflict screens, authorization boundaries, indexed search and operational care. It is not safe to equate “replication succeeded” with “domain conflicts were resolved.”

2. **A server-authoritative local database with a queued upload API, exemplified by PowerSync.** The client writes locally, then sends an ordered, idempotent upload queue to an application backend; the backend owns validation and conflict policy. The uncomplicated behavior is field-level last-write-wins, but the backend can apply business rules, reject writes to completed records, or record conflicts for humans [S16–S17]. Selective Sync Streams can send only the rows and columns chosen for an authenticated subscriber, into a local SQLite database [S18]. It fits a relational backend and an explicit authority for workflow transitions. The app and backend still need to implement and monitor the rule set. PowerSync self-hosting exists, but its self-hosted dashboard is unavailable; the Open Edition service is free but source-available under FSL, whereas Cloud and the Enterprise Self-Hosted Edition are paid, and client SDKs are Apache-2.0 [S19–S20]. No volunteer account with that vendor is shown as a requirement by these sources; the app still needs an organization-chosen identity flow and the operator must check the edition's licensing and costs.

3. **A CRDT such as Automerge for collaborative local-first content.** Automerge can synchronize independent offline changes without a central server and can also be used with a server [S21]. It combines independent property and list edits; when two actors write the same property it exposes the competing values but provides a deterministic displayed winner based on operation identifiers, not wall-clock time [S22]. It may help preserve independently appended notes or structured draft changes. It does not supply task authorization, identity management, server search, retention controls, or domain-specific “resolved cannot be reopened by stale state” rules. Use it only as a component if its merge behavior is needed, not as a complete handover service.

4. **A small custom offline outbox with a conventional API and database.** The phone keeps drafts and operation IDs locally, then a service applies each operation with server-side authorization, idempotency, revision checks and explicit workflow validation. This gives the operator maximum control over claims, acknowledgments, transitions and search, but means the team owns queue durability, retries, duplicate handling, schema changes and observability. It is a valid alternative for a modest group if a maintainer can support it; the small volunteer count alone does not prove this has lower lifetime cost.

These are viable architectures, not a product decision. A later comparison should score not only initial effort but who owns conflict handling, data visibility on each phone, identity lifecycle, operational recovery, photo retention and license/hosting cost. PowerSync's optional checkpoint API is an explicit sync boundary only while a client is connected/connecting and is documented as alpha in the cited company article; do not make a pilot depend on it without rechecking its current release state [S23].

### Data, search, privacy, deletion, and local storage

Older-issue search should use a deliberately allowlisted projection: issue ID, short description, equipment/location tags, status/resolution, and dates needed for retrieval. Do not include email addresses or phone numbers in searchable documents, queries, snippets, or offline datasets. Enforce access before returning results, not just by hiding fields in the interface. CouchDB database members can read all documents in that database, so database-level membership alone cannot protect contact fields placed alongside shared handover records [S08]. An external identity service can map authenticated users and roles into CouchDB through its proxy-authentication handler, under the required trusted-secret/configuration conditions, or JWT auth; whether the center already has an identity provider is unknown [S09]. PowerSync streams can select specific columns and rows, but any synced fields are stored on the phone, so never sync private contact columns to ordinary volunteer devices by default [S18].

A normal CouchDB attachment upload is a revisioned update to its parent document; deleting an attachment also creates a document revision and requires the latest revision. Attachment transfer can therefore contend with edits to the same record [S10]. The change-feed option to inline attachments is off by default; enabling it sends base64 data, with documented overhead, so do not use that route for large photographs [S07]. A proposed UI keeps photos optional and locally staged, displays size before upload, requires an explicit upload action, defaults to Wi-Fi-only transfer with a clear cellular override, and avoids fetching photo bytes in summaries or search. On deletion, queue deletion metadata while offline, show whether removal is still pending, and propagate deletion to the server and other clients when connected. CouchDB tombstones are intentionally retained so deletes can replicate, including after compaction [S11]; that does not establish deletion from backups, old offline devices, exports or legal archives. Data retention, hard-purge authority, backup expiry and what volunteers are allowed to photograph must remain owner decisions. No universal claim of erasure should be made.

PouchDB's local browser store uses IndexedDB, but browser-managed storage may be cleared under storage pressure or by explicit user action. Chrome documents persistent-storage requests and different eviction treatment, but this is browser-specific and does not protect data from a user clearing it [S24]. A proposal should request persistent storage where supported, check quota, make unsynced local drafts conspicuous, and test the actual phone/browser combinations. It must not promise that an offline browser cache is an archival copy.

### Consequential implementation and release evidence

A recent, directly relevant CouchDB regression was reported against 3.5.2: when a document with an attachment was deleted and recreated with the same ID and attachment name before the deletion had replicated, the new attachment could fail to replace the old content on the target, particularly after a transient or continuous replication interruption [S13]. PR 6129 identified stale attachment revision positions, updated them when grafting the recreated document onto the deleted revision, and added EUnit cases for revision positions, multiple delete/recreate cycles, atts_since behavior and replication [S14–S15]. The current 3.5 release notes list that fix for recreated same-name attachments [S12]. The PR page reports 56 checks passed at merge; I inspected the code/test change but did not run its suite. This means a photo pilot should include delete/recreate + interrupted-sync regression scenarios and pin/test its chosen release; it is not evidence that every attachment or client combination is defect-free.

PouchDB's current API docs describe a default revision-history limit of 1000 and warn that a low limit can prevent it from relating an incoming revision to local history [S04]. Keep low-history configurations out of assumptions and add deletion/recreation with long-offline clients to a proposed regression matrix if PouchDB is shortlisted. I did not execute an issue reproduction.

## Proposed adoption sequence

1. Before implementation, owners define role boundaries, existing login source, searchable fields, shift cutoff, claim semantics, acknowledgment visibility, image size/cellular defaults and retention/backups. Use synthetic records and ordinary test phones.
2. Pilot recent summaries, task notes, read acknowledgments and equipment issues with a small volunteer subset for one or two weekly shifts; leave photos disabled and preserve the existing handover as fallback.
3. Exercise two disconnected phones claiming the same task, reconnect them in both orders, replay a stale edit after resolution, and confirm the leader can reconcile visibly without data loss. Train the shift leader on conflict and pending-sync indicators.
4. Add allowlisted older-issue search after access review; inspect result payloads and local storage to confirm contact fields are absent.
5. Add optional photos only after upload-size, cellular-data, privacy, deletion, retention and backup behavior have an approved owner decision. Expand toward all roughly 30 rotating volunteers only after the failure cases below pass.

This sequence is a future proposal only. No volunteers were contacted, accounts created, device enrollment, deployment, or live center records were used.

## Failure-oriented validation proposals (not executed)

- With a phone offline at the loading area, open the last available handover, draft a note and claim, close/reopen the app, then reconnect. Show local-pending versus server-accepted state; verify duplicate retries create one operation and no draft vanishes without warning.
- Two phones claim the same task while offline, then reconnect in each order. Retain both claims and show a leader reconciliation state; never choose a claimant invisibly. Test the alternate policy of offline provisional claims if exclusive assignment is required.
- Mark a note read while leaving its equipment issue unresolved. Verify the acknowledgment has no status side effect and the issue remains in the next summary; inspect that no read leaderboard or performance score exists.
- Resolve an issue on one client, then replay an older offline edit and an old resolve/reopen command from another. Verify server revision/state validation blocks silent reopen, shows the current state, and offers an explicit new reopen action only when allowed.
- Search resolved and open historical issues using location, equipment and text; attempt to inject an email/phone-like value and inspect the server response, screen, logs, and on-device synced fields. Verify authorization and field allowlisting at the API.
- Disable mobile data, stage a large photo, and ensure no photo bytes move until an approved explicit action; exercise Wi-Fi-only default, cellular override, size cap, failed/partial upload, retry, and offline deletion. After sync, test on another device and against the approved backup-retention rule rather than equating a UI delete with complete erasure.
- For CouchDB/PouchDB candidates, test revision conflicts, both replicas changing same record, attachment replacement after delete/recreate when an intermediate delete is skipped, interruption/retry, and old-client revision histories. Pin server and client versions and verify operation under the actual proxy/auth and query configuration.
- Test supported phones and browser storage under near-quota conditions, browser eviction, explicit site-data clearing, low connectivity, and shift-leader handover. Persistent-storage requests and warning behavior should be visible; local-only data can still be cleared by users.
