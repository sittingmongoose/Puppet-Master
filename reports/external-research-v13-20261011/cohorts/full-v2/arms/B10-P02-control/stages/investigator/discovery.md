# Brief-only discovery

## Problem frame
The brief describes three related products: author-maintained lessons and diagrams; an offline learner experience with topic search and personal exercise progress; and printable handouts for people who do not install the app. Keep content, client software, and learner data at distinct boundaries. Preserve historical context when lessons or exercises change, support keyboard and assistive-technology use, and keep print behavior honest about static versus interactive features. Nothing in this discovery publishes materials, installs an app, or handles real learner records.

## Feasible authoring and release shapes
1. Structured Markdown/Quarto project in version control. Quarto book projects document HTML, PDF, Word and EPUB outputs; HTML book pages can use the website full-text search. This is promising for one reviewed source producing a browsable release and handouts. Quarto search builds a local index by default, but that alone does not establish first-load or cached-offline behavior. A service worker, when used, needs a secure context and explicit cache/update behavior. A released content manifest and versioned URLs could make a downloaded handbook understandable after updates.
2. Markdown/MkDocs documentation site. MkDocs builds a static directory and its built-in search indexes page text and headings client-side. Its own offline distribution guidance warns that file:// use needs search disabled or a plugin designed for that scheme, and that themes must bundle assets instead of relying on CDNs. A hosted HTTPS PWA can instead cache the shell/content, but requires explicit offline and update tests. A plain ZIP/HTML, EPUB or PDF bundle is a separate low-install option, with less dynamic exercise functionality.
3. Word-first authoring/import. This minimizes change for authors who already draft in Word, but conversion to a constrained web/book source should be treated as import assistance, not faithful round-trip. Pandoc documents loss when the source format is more expressive than its intermediate model; DOCX custom styles can be retained as style attributes with an option, but layout/margins and complex structures are not made equivalent. An author review of imported semantic structure, links, tables, images and alt text is therefore part of the workflow.
4. Database/CMS authoring. A GUI CMS or structured form editor may reduce Git/markup burden, but adds a runtime/editor, identity and backup/update decisions. Compare it in a pilot against the volume and authors' comfort before selecting it; keep released content exportable and versioned regardless of editor.

## Data and policy implications
A browser app can keep progress in IndexedDB, scoped to that browser origin and device, without a learner account or server sync. IndexedDB is asynchronous and supports structured offline data, but it does not synchronize records. Browser storage is best-effort by default and can be cleared or evicted; the UI should describe device-local scope, offer a clear reset, and never imply durable backup. Separate static public lesson assets/cache from personal progress records. Store exercise identity plus the exact exercise revision completed, rather than a single mutable boolean. On a materially changed exercise, preserve the old record and display the new revision as not yet completed (or awaiting review); define “material” and any re-acknowledgment rule with the training owner. For a retired lesson, keep an explicit retired/replaced state, archive/version label, date and successor link. Search results should show current/retired status and version/date; policy must decide whether retired material remains searchable and how replacement precedence works.

## Accessibility, import and distribution checks to plan
Use semantic headings and DOM source order so keyboard focus and reading order remain logical; make every operation keyboard-accessible with visible focus. A complex instructional diagram needs a complete equivalent text explanation, often a short alt plus adjacent long description or table. Keep instructions in text, never only in image pixels. For print, render a fixed handout from the same authored content but do not claim it carries app state or behaves like a web exercise. Quarto documents PDF/UA tagging and figure-alt propagation but explicitly does not guarantee accessibility; generated PDFs still need validation and human review.

## Early evidence and uncertainties
Official Quarto, MkDocs, Pandoc, MDN and W3C sources support the capabilities and constraints above (see stable IDs in source-map.json and the navigable sources/index.md). Pandoc's pinned DOCX reader tests have distinct default and +styles cases. A live Quarto issue reports dashboard pages omitted from search indexes, so dashboard-format exercise pages should not be assumed searchable without a specific regression test. This does not establish a defect in ordinary handbook HTML pages. No project code, app, prototype, benchmark, offline browser session, accessibility audit, import/export sample or user interview has been run. These are evidence-supported design directions, not implementation validation or a winning product decision.

## Decisions to preserve for the released-plan comparison
Authoring UX/hosting, whether markup/Git is acceptable or a GUI CMS is needed, supported browsers/devices, local progress retention/optional manual export, the threshold for a materially changed exercise, retired-page search policy, review roles, distribution channel, release/update cadence, handout format and accessibility acceptance criteria remain owner decisions unless the exact released plan supplies an accepted constraint. Proposed validation must remain distinct from executed checks.
