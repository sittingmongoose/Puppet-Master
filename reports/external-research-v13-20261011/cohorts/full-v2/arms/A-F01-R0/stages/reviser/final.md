# Research-backed proposal — Disconnected field-survey edit journal

**Status:** Complete research-backed software proposal, not implementation. It responds to the full brief and every released-plan clause P1–P9. The one-time plan reveal is recorded in the input package. Source IDs retain their investigator or critic lineage in this stage's source-map.json; sources/index.md is the navigation page. No language, database, synchronization library, or final product is selected. The existing desktop application's repository, callers, tests, supported platforms, and build are not identified in the brief, so its integration fit remains an explicit prerequisite for later design.

## Recommendation

Keep the plan’s local-first, no-hosted-account, explicit-photo-transfer direction, but make the operation protocol and durability model precise before adding convenient merges. Prototype a single local transactional store whose durable operation journal, materialized observation state, review queue, outbox and import receipts commit together. Use stable operation IDs and causal parents, not author labels plus per-record revision numbers, as the identity/conflict foundation. Keep event history and tombstones available through an explicit retention/archival policy. Use relay arrival order only for transport; it is not a causal or conflict winner rule.

If SQLite WAL is selected, make the actual embedded SQLite release a selection gate: use 3.51.3 or later, or verify that the exact 3.50.7 or 3.44.6 backport is present. SQLite's current WAL advisory says the rare reset race affects WAL databases on versions through 3.51.2 when separate connections concurrently write or checkpoint. Include WAL-specific regression coverage for the selected build and its concurrent-connection/checkpoint path. This condition applies only to WAL; it does not disqualify SQLite or a rollback-journal configuration. Keep the durability mode and target VFS/filesystem qualification as separate gates [R01–R02, C01–C02].

The plan’s second append-only journal can remain a logical operation journal, but appending it as a second physical file beside the embedded database must not be described as atomic until a cross-file recovery protocol has been designed and fault-tested. Prefer storing the logical append-only operations in the same transactional store for the first prototype. Store photo bytes separately, pre-stage and verify them before committing a reference, and show incomplete content explicitly. Support a versioned manual operation bundle before relying on the office relay as the only recovery path.

## Proposed data model and operator behavior

A minimal operation envelope for a prototype should contain:
- operation ID (random UUID); actor/device installation ID and local sequence; operation kind and schema version;
- observation ID; changed field or relation; new value or photo reference; causal parent/head IDs known when the operator made the edit;
- local time and author label for display only, plus a source bundle/receipt identifier when imported.

The author label can change and may collide; it must not serve as the operation key. A local counter is useful for distinguishing that actor’s operations, but only with a persistent, non-cloned actor ID. A reinstall or restored copy that may continue editing needs an actor-identity rule before it can emit operations.

Maintain an explicit record tombstone operation and keep ordinary reads deleted when a delete is concurrent with an edit or photo addition. The photo event and its blob may still be reviewed; neither creates a restore. A restore is a new, attributable operation naming the tombstone or decision it overrides. Keep deletion history until every active actor has acknowledged it or an operator retires that actor and resolves any bundle it may later return with.

A review item should say in field terms what happened, not expose database internals. Example: “Needs your decision: Laptop B changed the note while Laptop A marked this record deleted. Both changes are saved. Keep deleted, restore with these edits, or compare and combine.” Show the site ID, before/current/competing value, author/device labels, time marked as reference, and whether a photo is local, transferred or missing. The chosen action should be a new history event. Make review deferrable and do not block unrelated survey work.

## Alternatives and conditions

**Embedded transactional store plus app-owned operations.** Best first architecture to validate because language/storage remain undecided and it can express field survey semantics, a manual bundle and explicit delete/photo review. SQLite documents ACID transactions and operational WAL conditions, but it is not a distributed multi-writer store. Its Session extension can create/apply row changesets only with its PK/schema/base-data conditions and callback decisions; it does not replace causal operation identity. If selected, use it as a local store and export a supported snapshot or app bundle; do not exchange live SQLite files or rely on network filesystem WAL. [S01–S06]

**CouchDB revision-tree replication.** A credible alternative if a local HTTP database service per laptop and peer management are acceptable. It retains competing revision leaves and supports push/pull/checkpoints, but app reads select a deterministic winner and the app still needs human conflict resolution. Attachment content is coupled to document revisions; protocol can stream large attachments, but the recent same-name delete/recreate issue shows that particular revision/attachment paths deserve regression testing. No hosted account is inherent in the feature, but operating this service on all laptops is a substantial product and support choice. [S10–S15]

**Automerge/local-first CRDT.** A credible alternative if retaining causal changes and convergent disconnected edits is more valuable than relational simplicity. The pinned v3.4.1 JavaScript implementation exposes save, incremental save, merge and conflict inspection, and its tests exercise retained alternatives across actors [S19–S21]. The separate mutable conflict API page was recorded as v3.5.0 by the critic, so it is not used here to identify v3.4.1 [C10–C12]. Same-map-key values still have a deterministic default presentation, and official merge rules allow a concurrent set to win over a key delete [S17, C09]. Therefore, represent domain deletion as an explicit tombstone and perform a separate operator review. The app still needs local durable persistence, relay/manual transport, attachment transfer, history-retention and user-facing policy. Verify compatibility and storage properties against the exact chosen release.

No evidence in this stage establishes that 50,000 observations or a season’s photographs fit a particular timing, disk or transfer budget. Run a representative benchmark before selecting a product or automatic transfer default. Keep data and photo sizes, expected queries, number of edits per laptop/week, storage limits and acceptable reconnect duration as explicit input variables.

## Corrected bounded integration sequence

1. **Owner constraints and protocol sketch.** Agree identity across reinstall/clone, authorship labels, which fields can auto-merge, delete-versus-edit/restore semantics, retention/privacy, active-device retirement, relay availability, expected data/photo sizes and minimum OS/filesystem targets. Keep language and store candidates open until a thin proof answers those constraints.
2. **Local durable journal.** Select a candidate store and pin its version/settings. If selecting SQLite WAL, require 3.51.3+ or the exact 3.50.7/3.44.6 fix and include the WAL concurrent-connection/checkpoint regression case. In one transaction, record the operation, actor sequence/frontier, current projection, outbox and review state. Decide the saved boundary and recovery states. Add schema/version fields from the start.
3. **Photo staging and history.** Keep bytes separate, with stable attachment IDs, digests and local paths. Implement durable stage/verify-before-reference and visible pending/missing states. Define orphan cleanup and deleted-record retention.
4. **Pure operation replay and review.** Implement field-level causal merge, duplicate suppression, missing-parent handling, preserved concurrent values, tombstones and explicit restore. Review UI shows values and provenance in plain terms. Do not add a network relay before replay is idempotent.
5. **Manual bundle.** Export/import versioned operation bundles and optionally selected blobs. Verify manifests/checksums, preflight schema/size, stage bytes, apply operations idempotently and persist receipts. Exercise restore from a copied store and from a bundle after interruption.
6. **Relay exchange.** Add the local office relay with durable receipt semantics, frontiers, retry/resume and observable partial/error status. Test two devices before three, then cover all pairwise and three-way offline edit orders.
7. **Measure and expand.** Load 50,000 representative records and realistic history, then measure indexes, startup/search, checkpoint/compaction, import/export and reconnect. Measure photo opt-in transfer on expected networks before choosing batch size or defaults. Run the delete/recreate/same-attachment-name regression and verify digest equality. Adjust only from measured constraints.

## Owner decisions still required

1. What is an author identity in the field: named person, device, or both? How are labels assigned, corrected and displayed after a device is shared?
2. Should a concurrent delete always keep the record hidden until an explicit restore, as recommended here? Who may restore it, and can restoration retain only selected fields/photos?
3. How long must raw competing edits, resolved decisions, tombstones and photo bytes remain recoverable? What archive and privacy/deletion policy governs cleanup?
4. How is a laptop lost, reinstalled, duplicated or retired, and what evidence is needed before its actor ID is retired?
5. What are the actual photo counts/sizes, expected weekly edits, free disk budget, and acceptable reconnect/import duration?
6. Must every laptop receive photo bytes, or is a reference plus explicit transfer sufficient? Which bundle medium and relay deployment are supported?
7. Which fields are safe for independent merge, and what exact note comparison/combination behavior is acceptable to the ecologists?
8. Which language/runtime, local database or sync framework best fits the existing desktop app once its platform constraints are known?

These choices remain open where the brief and primary evidence do not decide field-team policy.
