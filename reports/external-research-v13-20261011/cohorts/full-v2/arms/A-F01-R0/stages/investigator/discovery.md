# Brief-only discovery — disconnected field-survey edit journal

**Scope:** The released brief only. The exact comparison plan has not been read or inferred. Full source identity, exact URL, version, locator, access time, observations, applicability and limits are in source-map.json; sources/index.md is the bounded navigation page.

## Findings and alternatives

Separate local durability from distributed merge policy. A transaction can recover a laptop's interrupted save; it cannot decide what two week-old offline edits mean. Commit one durable operation before showing “saved.” Exchange durable operations with stable IDs, causal context and idempotent receipts. Treat the visible observation as a projection of retained history, not the only copy.

Prototype one local database per laptop with tables for observations, immutable edit operations, photo metadata, review cases, sync cursors and import receipts. SQLite is a credible storage candidate. WAL permits readers alongside a writer but only one writer, requires all processes to be on one host, has a companion WAL file and needs checkpoint management. While open, the WAL is persistent database state. NORMAL in WAL mode may lose the latest committed transactions after power loss; if “save complete” must survive power loss, qualify FULL durability with the actual filesystem/VFS. Pin the SQLite build and settings. The Session extension can create row changesets, but needs primary keys and a compatible schema and starting database. Conflicts are passed to application code for omit/replace/abort; that API is not the domain merge or a full audit journal. The Online Backup API makes a coherent snapshot for export; copying only the main database while WAL is active is unsafe.

Give each observation and photo a stable random identifier, each laptop a persistent actor ID, and every operation an idempotency ID plus actor sequence. Record causal parents or equivalent version heads: causal ancestry distinguishes a later edit made after seeing an earlier one from independent concurrent edits. Do not order competing edits by wall-clock time; keep timestamps only for human orientation. Store field-level changes so a confidence edit does not replace a note edit. Preserve concurrent note values and provenance until a person explicitly records keep/combine. For confidence, show the competing values as a simple choice.

Model deletion as an explicit durable tombstone operation with causal context, not row absence. An incoming stale snapshot, note edit, or photo addition must not clear the tombstone. When deletion competes with an edit/photo addition, retain all edits and photo metadata in history, keep the observation deleted in the ordinary list, and create a review item. The operator can keep deleted or explicitly restore, with restore recorded as a new operation that names the tombstone being overridden. Retain tombstones until every active device has acknowledged them or an operator retires a device through a documented recovery procedure; elapsed time alone cannot prove a week-offline laptop has seen a deletion.

Keep photo bytes separate from records and synchronization metadata. Store immutable photo objects by content digest and unique attachment ID, with media type/size; metadata operations only refer to IDs. Exchange metadata by default. Offer explicit/on-demand photo transfer or a clear opt-in policy; stream only selected/missing content. Stage incoming bytes, check length/digest, then make the reference visible. A missing file should read “photo not on this laptop” and remain pending. This avoids coupling a photo to the lifecycle of a deleted observation and avoids uploading all photo contents automatically.

Compare three implementation families:
1. SQLite plus an application-owned operation protocol gives portable local state, transparent schema, domain-specific conflict/deletion rules and straightforward removable bundles. It requires the team to implement causal tracking, convergence, retry and protocol versioning.
2. CouchDB supplies HTTP push/pull replication, checkpoints and revision trees; conflicting leaves are retained, but ordinary reads select one deterministic winner, so the app still needs to surface alternatives and collect human resolution. Attachments are document-revision content. It brings a database service and peer reachability into scope. A directly relevant 2026 bug: deletion and recreation with the same document ID and attachment name could leave target bytes stale if the intermediate deletion was not replicated first; issue #6126 led to the #6129 fix in CouchDB 3.5.3. Matching revision metadata therefore must not substitute for content verification.
3. A local-first CRDT such as Automerge supports edits while disconnected, change exchange and inspectable concurrent values. Its map conflict API presents a deterministic, arbitrary default and exposes the alternatives; its ordering is operation-ID based, not a wall clock. Its documented merge rules let a concurrent key assignment beat a key deletion. Therefore logical record tombstones and restore rules remain application-owned. Fine-grained updates matter; upstream implementation and tests demonstrate save/merge/conflict APIs and retained competing values. The CRDT eases convergence but does not decide ecology semantics, attachment transfer, or how review is explained.

50,000 observations is plausible for an indexed local database, but the brief omits note lengths, attachment sizes, edit rate, retention, query mix and network speed. Do not make a performance promise. Measure representative database/index size, search/startup latency, journal growth, import/compaction time, conflict-queue size and selected-photo transfer time. Partition operations per observation and bound exchange batches rather than placing a whole season into one conflict unit.

Operator explanation should avoid database terms. Example: “Needs your decision: Laptop B changed the note while Laptop A marked this record deleted. Both changes are saved. Keep deleted, restore with these edits, or compare and combine.” Show site ID, field labels, device/person attribution, local recorded time marked as reference, and photo availability. Preview the result before a choice; save the choice as a history item; allow deferring this case while other records remain usable.

## Brief obligations covered

- Storage and interrupted saves: transactional local store; stage photo bytes to durable same-volume storage, verify digest, then commit reference/event; scan for temporary/orphan blobs on recovery. SQLite recovery documentation is not a substitute for qualifying the actual filesystem.
- One-week partitions and three laptops: persist outgoing operations, exchange in bounded idempotent batches, apply and store receipt atomically, acknowledge only after commit, resume after transient failure. Support pairwise local network sync without a hosted account.
- Identity and conflicts: stable record/photo/actor/operation IDs and causal parents; preserve concurrent field values; wall time is display metadata only.
- Delete/photo overlap: tombstone controls visibility; adding a photo does not restore a record; preserve the attachment operation/reference in a review and history; restore only by explicit new operation.
- Attachments: no automatic photo upload; separate content and metadata, explicit transfer, checksums, honest missing-content state.
- Scale/unknowns: benchmark representative 50k data and photo/bandwidth cases before choosing the storage or transfer default.
- Recovery path: plain-language review queue, side-by-side values, explicit choices and audit trail.
- Manual transfer: versioned operation bundle with source device, bundle ID, operations, causal heads, schema version and digests; optionally selected blobs; preflight size/compatibility, verify and idempotently import.
- Bounded sequence: fix the operation/tombstone schema; implement crash-safe local save/history/review; prototype two-device exchange and duplicate/reordered retries; test three-device branches and tombstone acknowledgements; add manual bundles; then add optional LAN transport and measured opt-in photo transfer.
- Validation: research/source inspection only. No application prototype, benchmark, crash harness, integration test or test suite was executed. Tests below are proposals, not performed checks.

No framework is adopted in this brief-only stage. The comparison plan is still withheld pending the declared reveal.
