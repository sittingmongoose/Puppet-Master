## Recommendation

Keep the plan's core model: a durable physical-item identity, event-based loan history, one local coordinator, and explicit checks for competing checkouts. No candidate has yet been shown to provide the required reasoned, preserved corrections or alias/fuzzy search; those remain adoption gates alongside kit returns, damage holds, contact-data behavior, and restore operations. Product selection should follow a short evidence-based pilot.

For the initial pilot, both laptops should use one server on the local network. An internet outage should not stop service when that server and LAN are working. If the server/LAN is down, do not accept independent laptop checkouts as authoritative. The draft's provisional-label assumption cannot prevent a collision after an item has left. Start with checkout paused or one numbered paper queue controlled by a named volunteer, then reconcile each line against server state before resuming. Treat permitted offline checkout as an owner decision for a later, tested protocol.

A browser-based service on one LAN host can use PostgreSQL when the group can operate the service and backups. A unique item ID makes each physical unit addressable; it does not by itself prevent two active loans. In PostgreSQL, enforce one active loan per item separately, for example with a partial unique index, and have every checkout transaction lock and recheck the authoritative item state before creating the loan; handle repeated submissions idempotently. [D3–D4] A lightweight single-host service could use SQLite on the server's local storage with serialized writes, but only with a pinned, supported patched runtime. The current SQLite WAL documentation says the WAL-reset corruption bug affects WAL databases through 3.51.2 under the specific condition of separate connections/processes attempting concurrent writes or checkpoints; it is fixed in 3.51.3 and later, with some backports. Test the selected version under concurrent write/checkpoint and recovery conditions. Never open one SQLite/WAL file directly from both laptops over a network share. [D1–D2]

No candidate is a clear winner. SpaceWorks maps most directly to lending and repair holds, but the fit depends on configuration and release. Its pinned self-host guide describes a Docker-first PostgreSQL-plus-MinIO stack, separate database and object-file backups, and an optional scheduled send_return_reminders command for overdue issued or partially returned requests; a configured scheduler would send email, so a candidate pilot must leave that job unscheduled and rehearse that no message is emitted. At the pinned page, the guide says published images were not yet publicly available and gives a build-from-source overlay; verify current release/install availability. The moving modules page says issuing a reviewed request requires a box QR scan and issue photo, and return requires a photo plus remark; evidence rows and audit metadata are immutable even if a retention setting later deletes image bytes. The asset_units module is needed for per-unit tracking; without it, inventory stays quantity-tracked. The individual repair move in the pinned W1 commit also requires individual tracking, the staff_admin module, and edit permission; the commit-to-release mapping is unknown. W2 records a later fix for stale repair counts, while W3 shows the earlier individual-tracking gap. Treat these as versioned fit conditions, not guaranteed behavior of every release. [W1–W6]

Koha has explicit barcode circulation, bundle scans on return, and configurable staff logs. It is more library-oriented and may bring more administration than 800 tools need. A bundle verification can be skipped and deferred; a damaged flag alone marks an item unavailable in search but does not block checkout/check-in, so a separate restriction or maintenance workflow is needed. Its multi-computer offline process gathers and orders workstation logs, and offline checks miss some online rules. Configured long-overdue/lost handling is a status action, not evidence that a physical return was recorded. The manual's logs depend on selected preferences and do not establish reasoned correction/reversal semantics. [K1–K3]

Snipe-IT provides unique asset tags and barcode guidance, and an administrator can require notes on check-in/out. At the v8.8.0 tag, the Asset model stores an expected check-in date when supplied, stores last-checkout information and the target, then saves and emits a checkout event; this model code does not imply an automatic return or establish a reasoned correction workflow. The reviewed pages do not establish native kit completeness, maintenance-return behavior, alias search, or fuzzy disambiguation. The v8.7.2 release page does not support the carried claim that this version fixed duplicate checkout rows from a double-click: its displayed list instead includes a fix for double logging on restores. Remove that attribution. Repeated-scan and retry handling remains a reasonable general acceptance test, with no cause or fix version established here. [S1–S5]

A custom local service can represent the exact kit and correction rules but transfers software upkeep, security, upgrade and recovery duties to the group. Compare it only if a volunteer or service provider accepts that long-term responsibility.

## Identity, concurrency, and deployment comparison

| Approach | Benefits | Limits and proposed use |
|---|---|---|
| Item names, model names or serials as identity | Familiar and often already recorded. | Duplicate physical units collide; serials can be absent or illegible. Use a generated permanent item ID; retain names/serials as attributes. Koha barcode circulation and Snipe-IT unique tags support the physical-label pattern. The reviewed sources do not establish candidate alias or fuzzy-search behavior; test preferred names, aliases, similar models and disambiguation against the selected build. [K1, S1, S5] |
| Shared server with one authoritative state | Both laptops see the same availability; a transaction can serialize competing checkouts. Internet can be down while the LAN server remains reachable. | The coordinator host is a single operational dependency; name an operator and test backups and restore. This is the recommended initial deployment. |
| Independent laptop databases with provisional offline loans | Checkout can continue while disconnected. | Conflict resolution occurs after an item may already be gone, and a reminder label cannot guarantee the other volunteer sees or respects it. Do not enable in the first pilot. Koha's multi-computer offline flow itself requires logs from each workstation to be combined and ordered. [K1] |
| Self-hosted LAN application | Does not require a paid cloud account or internet round-trip to make a local transaction, if the selected software supports a self-hosted edition. | The group owns the host, patching, accounts, backup and recovery; verify licensing and any paid feature gates before choosing. SpaceWorks documents PostgreSQL and a separate MinIO object store, with both requiring backup. [W4] |
| Hosted cloud service | Can reduce local host administration and simplify remote access. | Internet instability and a possible recurring paid account conflict with the brief. Consider only if a no-required-fee tier, offline behavior, data export and data retention are verified. |
| SQLite on the LAN server vs PostgreSQL | SQLite on local server storage can serve a small application with serialized writes; PostgreSQL provides database constraints and row locks for shared transactions. | Never open one SQLite/WAL file directly from both laptops over a network share. If using WAL, pin SQLite 3.51.3 or later, or a vendor-confirmed fixed backport, then test concurrent writes/checkpoint and recovery on that runtime. PostgreSQL still needs a separate active-loan uniqueness rule plus transactional lock/recheck; an item-ID uniqueness rule alone is insufficient. Choose based on the operator's ability to back up and restore, then test the actual two-client workflow. [D1–D4] |

## Corrections to the draft, optional improvements, and owner decisions

### Corrections required to preserve the brief
- Make the unique physical-item identity durable and non-reusable; names and model names cannot identify physical copies.
- Make a returned-but-damaged unit a hard maintenance hold that cannot be checked out until an authorized repair/release event.
- Require a correction reason and preserve the corrected event/value and its replacement or reversal. The plan calls for testing corrections but does not yet state the required explanation.
- Replace independent provisional offline loans as the initial default with one controlled outage procedure. Keep a later offline-write mode open only as a tested policy choice.
- Defer borrower contact collection until the reminder policy is decided. Staff review and no automatic send are already consistent with the brief.
- Enforce single-active-loan concurrency on the authoritative server, not by warning volunteers to notice a conflict.

### Optional improvements
- Add a printed human-readable short code beside each barcode so damaged or unreadable labels can be resolved safely.
- Track condition observations separately from the authoritative available/loaned/maintenance/retired state.
- Add exportable inventory and loan-history reports to support reconciliation and recovery.
- Include a small representative pilot before the shadow session graduates to full migration; the current plan does not define a cutover gate.
- Include a written runbook for server loss, label replacement, backup restore and temporary paper transactions.

### Owner decisions that research cannot settle
- Which item types and kit parts receive their own barcode; acceptable handling of low-value interchangeable parts.
- Loan period, whether a due date is used at all, and what volunteers should do with overdue loans; due date must never close a loan.
- Who may issue, return, mark damaged, release from maintenance, correct events, retire items, or view borrower data.
- Whether reminders will ever be sent, by which channel, to which borrowers, and what minimum contact field and retention rule follows.
- Retention of loan/event history, contacts, photos and correction reasons, plus whether anonymization can be used.
- Outage behavior, the one-log custodian, temporary ID format and who approves reconciliation; later acceptance of multi-device offline writes.
- Who owns the LAN server, patching, backups and recovery; accepted recovery time (RTO) and maximum lost-data window (RPO).
- Whether mandatory photos in a candidate system are acceptable. SpaceWorks' evidence requirement is documented on a moving main-branch page rather than a release-pinned source, so verify it against a selected release. [W5]

## Validation: proposed versus executed

The following are acceptance proposals, not completed tests:

1. Load synthetic data with 800 items and five years of representative loan events, duplicate names, aliases and similar models. Confirm one unique permanent ID per unit, an exact scan match, alias lookup, and clear disambiguation. The alias/fuzzy behavior is unverified until this test passes on a selected build.
2. Submit the same item checkout concurrently from both laptops, then repeat with rapid double-scans/retries. Pass only if one active loan is created, the losing client sees the current holder/status, and retries do not create duplicate events. This is a risk-based acceptance test; the v8.7.2 Snipe-IT page does not substantiate the previously claimed double-click fix.
3. Test an internet-only outage with the LAN host reachable; both laptops should continue to see the same current state. Then isolate both clients from the host: verify checkout is blocked or the single authorized paper procedure works. Reconcile while checking for duplicate active loans and lost events.
4. Check out a parent kit, return it complete, then return it with one missing or damaged child and with a deferred verification attempt. Pass only if the kit remains unavailable until every unresolved child is accounted for and repaired/cleared by an authorized volunteer. For SpaceWorks, verify asset_units is enabled and that the selected release's individual fix action works with the needed staff module and permission; for Koha, prevent a skipped bundle check from exposing the kit as available.
5. Correct a wrong checkout and wrong return. Confirm the correction requires a reason, records actor/time, preserves the original event, updates current availability once, and is visible in history.
6. Advance a test due date without a return event; confirm it changes only overdue display/reporting. Retire an item and restore from backup; confirm its identifier, prior loans and correction chain remain.
7. Inspect borrower roles, contact fields, and notification configuration. Confirm unnecessary contact fields are not required, only authorized staff can view approved reminder data, and no email/SMS/webhook is sent. For SpaceWorks specifically, leave send_return_reminders unscheduled and confirm no scheduled or manual test path sends a message.
8. Lose the coordinator host and restore a full backup into an isolated replacement. Verify counts, IDs, active loans, kit-child manifests, repair holds, retired histories and audit events; if evidence objects exist, verify those separately. Record measured RTO/RPO and a discrepancy report before approval.
9. Before cutover, compare the cleansed inventory, active loans and five-year history against the existing lists, including a signed list of unresolved duplicates and exceptions.
