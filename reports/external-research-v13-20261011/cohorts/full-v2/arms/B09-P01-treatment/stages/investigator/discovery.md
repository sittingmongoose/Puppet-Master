# Brief-only discovery: neighborhood lending inventory and returns

## Scope and constraints
This discovery is based on the released brief only. The exact plan has not been read or sought. The requested result is a software proposal for approximately 800 physical items and five years of records, not an implementation. Required outcomes include durable identity for each physical unit, current availability, explainable loan/return corrections, two-volunteer concurrency from separate laptops, operation during internet outages where the LAN remains available, kit-part tracking, a damage hold, alias/similar-item search, minimum contact data, no paid cloud dependency, no due-date-derived returns, no history deletion on retirement, and no automated borrower messages.

## Candidate approaches; no winner assumed
1. **SpaceWorks** is a new makerspace/tool-lending product with individual asset tags and a repair-shelf operation. Its pinned code commit d3cd13cc42d1c2b823b30b57a1fcb3459601eb1a adds staff actions to move individual assets to and from a fix shelf, with tests for counts and state transitions; a later count-reconciliation fix shows availability aggregation has had defects worth guarding against. Its self-hosting guide describes a multi-service deployment and requires backup of both PostgreSQL data and MinIO objects. Current upstream module documentation says issue and return photos plus a return remark are mandatory, which may impose data and privacy overhead outside this neighborhood brief. The latest changelog section observed was 0.7.5 (2026-08-11); treat release maturity and current-version behavior as adoption gates, not as settled facts. [W1–W5]
2. **Koha 24.05** is a mature library circulation system. It checks items in and out by barcode and supports serialized bundles whose contents can be scanned on return; staff can explicitly skip verification and finish it later. Its offline workflow allows multiple computers, but the manual requires uploading all device logs, sorting transactions into a consistent order and processing them; offline validation also misses some server-side rules. Damaged status marks an item unavailable in search but does not itself prevent checkout or check-in, so a separate restriction/workflow is essential. Action logging depends on configured log preferences. These are strong circulation and history capabilities with meaningful setup and LAN-failure complexity. [K1–K3]
3. **Snipe-IT 8.8.0** is a general IT asset manager with unique asset tags and barcode labels, configurable check-in/out notes, and an accountable-person model. It can provide identity and basic loan state, but the reviewed sources do not establish a native kit return/reconciliation flow or reasoned, append-only correction model matching the brief. Release 8.7.2 fixed duplicate checkout requests on rapid double-click; verify this regression against the selected build and scanner retries. [S1–S5]
4. **A small purpose-built local web service** could model this exact workflow, but it creates an ongoing software, security, update and recovery responsibility for the group. Treat it as a comparison option, not an automatic winner.

## Coherent working proposal
Use one authoritative server on the neighborhood LAN, reached by both laptops through browser clients. Internet access should not be a runtime dependency. Each physical item gets a durable, unique printed barcode/QR ID; a shared type/model record remains separate. Keep the preferred name, aliases, category, serial or distinguishing attributes, storage location, condition, status, and retirement state. Exact-ID scans resolve one physical unit; alias and fuzzy search help volunteers choose among similar tools but never substitute for confirming the unit.

Represent a kit as a parent/container with an expected set of individually identified removable parts. Issue and return should scan the parent and required child IDs. A missing or damaged component prevents the kit/unit from returning to available state until a named volunteer resolves it. A damaged return enters a maintenance hold immediately; repair completion is an explicit actor/time/reason event. Current availability is derived only from authoritative item/loan state, never from a due date.

Store issues, returns, status changes and corrections as durable events. Corrections supersede or reverse a prior event and require a reason, actor and timestamp, preserving the original value and chain. Retiring an item marks it unavailable/retired and preserves its item and loan history. A unique item identifier and a transactional rule that allows at most one active loan per item guard against two simultaneous checkouts. PostgreSQL supports database uniqueness and row-level locks for this pattern; SQLite can work behind a single local server with short serialized writes, but its WAL mode must stay on one host and must not use a shared network database file. [D1–D4]

When the internet is unavailable but the LAN server is reachable, both laptops continue normally. If the LAN host is unreachable, stop new digital transactions or use a numbered, time-stamped paper queue owned by one volunteer, then reconcile entries against server state before resuming. Do not allow two independent laptop databases to accept writes without a tested conflict protocol. This avoids the manual merge hazards documented for multi-computer Koha offline circulation. [K1]

Keep borrower data to an internal borrower identifier/name plus only the contact field required if a reminder policy is later approved. Disable outbound email, SMS and other automatic messages while policy is undecided. Do not collect contacts just because a product requires them; verify product fields and retention before selection. Retention period for borrower contact and whether contact data may remain linked to five-year loan history are owner decisions.

## Proposed staged adoption and recovery
- **0. Decisions and cleanup:** settle item/kit definitions, identity and alias rules, loan period/due-date meaning, repair authority, correction permissions, contact/reminder policy, history retention, outage procedure, hosting owner, backup location, acceptable restore time and data-loss window.
- **1. Synthetic-data proof:** configure a candidate with duplicate names, aliases, kits, missing/damaged parts, item retirement, correction reasons and two volunteers. Exercise rapid repeated scans and simultaneous checkout attempts. Verify all outbound messaging is disabled. These are proposals; none have been run.
- **2. Small pilot:** label and import a representative 25–50 items, including multiple same-name units and several kits. Operate two laptops on the LAN across an internet outage. Reconcile counts and event history after a short pilot.
- **3. Migration:** cleanse the separate lists, assign unique durable IDs, resolve duplicates, map old loans and active loans, and create aliases and kit-child manifests. Keep the old lists read-only until reconciliation confirms all items, current loans and history. Import in batches with counts and exception sign-off.
- **4. Recovery rehearsal and expansion:** take scheduled backups before updates and at a policy-approved cadence; keep an encrypted copy separate from the host. Restore into an isolated replacement environment and verify inventory counts, unique IDs, active loans, kits, maintenance holds, retired-item histories, correction/audit events, and any retained evidence files. Record achieved restore time and recovered data window, then expand to all 800 items only when owners accept the result. SpaceWorks documents that its database and MinIO evidence files require separate backups, illustrating why restore validation must cover both. [W4]

## Organizational gaps and unresolved evidence
The group must choose a lending/due-date policy without turning overdue time into an inferred return; define who can override damaged/maintenance and correction states; decide what constitutes a kit and whether every part is individually tagged; define alias ownership and search tie-breaks; select contact fields and decide if/when reminders are sent; set retention for identity, contacts, loans, audit events and any photos; name the server/backup operator; define outage paper-log ownership and reconciliation; and set restore targets. Current-source/version uncertainty remains for SpaceWorks documentation shown on moving `main`, and product fit should be tested against released builds. The source map records exact URLs, versions/commits where captured, retrieval batch times and behavioral conditions. No product was installed; no code or test suite was run; all validation above is proposed only.
