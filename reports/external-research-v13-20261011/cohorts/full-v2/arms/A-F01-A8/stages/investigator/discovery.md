# Brief-only discovery — disconnected field-survey edit journal

**Stage:** investigator, run A-F01-A8  
**Discovery source:** the released brief at `inputs/brief.md` only. The comparison plan has not been opened, sought, or inferred.  
**Research snapshot:** 2026-10-12 UTC.  
**Disposition:** shortlist and design questions for later comparison; this is not a product selection or implementation.

## Problem frame

Three field laptops may edit the same observation during week-long offline periods. The data needs stable identity, complete competing-edit history, a plain-language recovery path after power loss during save or reconnect, and a reconnection method that also works through manual transfer. The hard prohibitions are material design constraints: no required hosted account, no automatic photo-content upload, no wall-clock winner for collisions, and no silent resurrection after a delete. The record count is bounded at about 50,000 per season, while image sizes, network speed, application language, and storage engine remain unknown.

## Candidate approaches to compare

1. **Embedded transactional store plus an application-owned change journal and merge protocol.** SQLite is a useful local-store candidate, not a conclusion. It can commit an operation and its materialized view atomically on each laptop. A separate sync layer would exchange immutable changes and keep concurrent variants. The application can set exact field, delete, attachment, and operator-review rules and can export a portable change bundle. The cost is owning and testing peer discovery, duplicate delivery, causal ancestry, merge, schema evolution, and review state; SQLite alone does not provide multi-laptop reconciliation. WAL is host-local and has checkpoint and file-copy conditions, so a live database file must not be treated as the wire protocol.

2. **CouchDB/PouchDB style multi-master document replication.** These products were designed for sync, support local PouchDB databases and HTTP peers, and preserve conflicting revision branches while exposing a deterministic visible winner. Conflict metadata must be queried and interpreted by the application; default display of the winner is not itself an operator decision. Document-level conflicts may be coarse for observation notes, confidence, site identifiers, and a concurrently added photo. Deletion uses replicated tombstone revisions, while database destruction is different and may cause replicated data to return. A PouchDB issue reports deletion propagation problems under an unusually low revision-history limit; it is an open report, not a confirmed general defect. Attachment APIs associate file bytes with documents, so byte transfer and user consent would need deliberate control. A local-only deployment or manually transferred bundle is possible in principle but still requires adapter, server, and transport choices.

3. **Automerge or another local-first CRDT.** Automerge retains a change history, merges many concurrent edits deterministically, and exposes conflicting values for a property. Different fields can merge independently; simultaneous writes to one property retain losing values in conflict metadata, but a single value remains the ordinary read result. Its map rules say a concurrent delete of a key and a set of that key resolves to the set value. The application therefore needs an explicit tombstone/conflict model to prevent a deleted observation from silently reappearing. A deletion should be an application event on an observation, not simply removal of the record map key. CRDT merge does not automatically define which differences require human review. Automerge is a Rust core with JavaScript bindings; its repository describes the Rust API as low-level and not well documented, so Rust integration is a feasibility item if the desktop language is chosen as Rust.

A plain file-sync tool or copying an open database file is not an adequate journal protocol: whole-file replacements do not encode field ancestry or delete policy, and WAL database state may include a separate persistent WAL file. Manual transfer should instead carry explicit, versioned changes (and optionally selected photo files) with integrity checks and an import receipt.

## Candidate-independent data and recovery model

- Give each observation a stable immutable ID distinct from the human site identifier. Give each laptop a durable device/actor ID. Give each edit and attachment its own globally unique ID. Use random UUIDv4-style identifiers or another reviewed collision-resistant generator; do not use a timestamp or device-local counter as a globally unique identity. Store wall time and author/device as explanatory metadata only, never as the merge ordering rule.
- Store edits as immutable operations with a change ID, observation ID, device/actor, parent/base version(s), schema version, wall-clock display time, operation kind, and field-level values or patch. Deduplicate imported operations by change ID. Keep a materialized current view for efficient search, but retain the competing change records and resolution history.
- For a first bounded merge policy, automatically combine independent fields whose ancestry proves they do not overlap. If two edits change the same scalar field, or if ancestry is unknown, retain both values and mark the observation for review. Treat a note as a whole-field conflict at first; do not invent text-edit merge semantics until a demonstrated need and a reviewable text-diff policy exist. Keep site identifier as a field, not as the row identity.
- Represent deletion as a durable tombstone operation. If a delete overlaps an edit or photo addition based on an older state, preserve both sides and place the record in review. Never make a stale edit silently cancel the tombstone. A user choice to restore or keep deleted should create a new resolution operation naming the changes it resolves.
- Keep photo bytes separate from observation/change data. Each reference should carry attachment ID, relative/local location or transfer locator, byte length, media type, and a cryptographic digest. Create and verify a temporary file, flush it, then atomically rename it before committing its photo-reference event; an interruption before the database commit can leave an orphan file, while committing first risks a dangling reference. On reconnect, exchange photo references and metadata only by default; copy bytes only through a separately visible, explicit selection. Detect missing or digest-mismatched files and show a repair choice rather than dropping the reference.
- For a SQLite candidate, put the operation append, deduplication row, updated current projection, and local outbox marker in one database transaction. Choose durability settings deliberately. WAL improves reader/writer overlap but permits only one writer at a time on that file, is not for multi-host network filesystems, uses `-wal`/`-shm` sidecars, and has checkpoint and read-transaction edge cases. Use SQLite's online backup API or a structured change export for transfer; do not copy only the main database file while a WAL database is open. Pin a supported fixed SQLite version and capture its release source ID.
- Give the operator a review queue that says in ordinary language what each laptop changed, why the app needs a choice, what it will do to the record and its photos, and how to keep either competing version or compose a result. Keep an audit trail of the selection and its source changes. Show observed device/time context without claiming that clock order proves which edit is newer.
- The manual bundle should have an explicit study/bundle ID, schema version, originating device, covered operation IDs/heads, manifest, lengths, and SHA-256 digests. Import should be idempotent, validate the whole bundle before applying it, and produce a receipt listing imported, already-known, rejected, and unresolved changes. Photo bytes should be opt-in and separately listed.

## Assumptions and open questions for comparison

The app is desktop, but operating systems, app language, local database, expected attachment count/size, backup policy, and whether the laptops ever share a local network are unspecified. No numeric sync-speed or storage estimate is justified yet. Measure representative observation and image distributions before choosing inline vs. external photo storage, transfer chunk sizes, or retention limits. Clarify whether edits to notes should remain whole-note conflicts or require character-level merge, what evidence can safely be compacted, how long tombstones/history must remain for dormant laptops, and whether group members are identified by device only or by named users. Do not purge a tombstone or losing change merely because it was imported once; a laptop may still be offline with an older branch.
