# Draft: offline field-survey journal for three laptops

**Status:** provisional investigator draft, for review. This is a design proposal, not an implementation endorsement. The brief describes three laptops, a week without connectivity, up to 50,000 observations, manual transfer, no hosted account, and no automatic upload. Attachment sizes, operating systems, storage engine, programming language, and whether any local network is available remain unknown. No product checks or tests have been run.

## Recommendation to carry forward

Treat each laptop as an independent offline author. Preserve every accepted change as an immutable, uniquely identified operation, and derive the current observation view from those operations. Use a local transactional store for the observation projection, operation journal, import receipts, and export bookkeeping. For a first prototype, evaluate SQLite as that store; do not treat SQLite's WAL as a cross-laptop journal or copy a live database file as a transfer protocol. Provide explicit, user-initiated export/import bundles as the baseline transfer path. A local relay may be evaluated later as another transport for the same bundle protocol, but the design must work when laptops do not meet on a network.

Do not make revision counters, author labels, arrival order, or wall-clock time choose a winner. Use unique change IDs and explicit causal ancestry (the change or set of changes each edit was based on). Automatically combine only edits whose fields are independent under a documented rule. Retain same-field alternatives and show them in a review queue. Represent deletion as an explicit tombstone operation; a concurrent edit or photo addition must produce a visible review case, not silently restore or erase an observation. Record the user's resolution as another operation so the alternatives and decision remain auditable.

Keep photo bytes as separate local blobs with stable photo IDs, byte lengths, media types, and SHA-256 digests. A change references the photo ID and metadata; transfer of bytes is separately visible and user initiated. A metadata-only import can show a photo as not present on this laptop. Validate bytes before attaching the reference. A crash between blob write and database commit may leave an unreferenced blob, which can be cleaned up after a scan; the reverse state (a committed reference to a missing or incomplete blob) should be detected and surfaced for repair. The precise write, flush, rename, and recovery sequence is platform dependent and remains to be tested on the selected filesystems.

If a separate journal file is required, define and failure-test a recovery protocol; atomicity between two independent resources cannot be assumed from SQLite's single-database transaction guarantee [S02]. |

A digest detects accidental mismatch but does not authenticate who supplied a file [S20]. |

Make explicit bundle export/import on removable media or a user-selected folder work first. The relay can be considered later, must require a user action, and must not upload to a hosted service automatically. A network filesystem is not an acceptable SQLite WAL sharing mechanism [S01, S07]. |
| The relay accepts operations in arrival order. | **Reject as a merge rule.** | Arrival order is a transport fact, not causal truth. Imports must be idempotent, deduplicated by change ID, and applied by operation ancestry. Independent fields can merge by policy; concurrent changes to the same field remain alternatives. Wall-clock timestamps are context only, including when clocks drift or have been reset. |
| A revision mismatch opens a card showing the old value and both edits. | **Retain and expand.** | Use a review queue for concurrent same-field edits, delete-vs-edit, and delete-vs-photo-add. Show the common base when known, both alternatives, contributing device/author labels, and the causal relationship. Offer explicit choices such as keep left, keep right, enter a merged value, or restore as a new observation. Every choice creates a resolution operation; the UI must not hide a deterministic internal winner. PouchDB and CouchDB expose revision conflicts, but ordinary reads can still show a deterministic winner unless conflict variants are explicitly requested [S08, S12, S14]. Automerge similarly retains conflicting values while defining a deterministic visible value [S16]. |
| Non-overlapping field edits are proposed for automatic merging. | **Retain conditionally.** | Merge only different fields when they descend from a known common state and the field schema declares them independent. Keep the provenance of each field. Treat a free-text note as one field and surface concurrent note edits unless a separately specified text-merge policy is adopted. Automerge documents field-level merge rules, but library behavior is not itself the product's review policy [S16, S17]. |
| Delete-versus-edit is sent to review. | **Retain and make deletion durable.** | Record delete as a tombstone operation with an observation ID and causal parents. A concurrent edit, attachment add, or edit based on a pre-delete state must not clear the tombstone by merely writing the record again. Require an explicit restore/resolution operation and show it as such. CouchDB propagates deletes as revisions/tombstones, and its replication documentation describes filters that must preserve deleted-document content when using such a filter [S09]. PouchDB's integration tests include an explicit re-put of a deleted document, while an open issue reports a low-revision-limit deletion concern; that issue is a reported risk, not verified proof of a current defect [S14, S15]. Automerge's map deletion versus concurrent set semantics are a reason to model this policy above a bare map-key delete [S17]. |
| Laptop-local revision number plus author label uniquely identifies operations. | **Reject.** | Two devices can generate the same local revision and label; labels can change, installations can be replaced, counters can reset, and transfer acknowledgments can be lost. Use globally unique change IDs plus a durable instance identity and causal references. Keep the label for humans, not identity. UUIDv7 embeds time and must not become a conflict-order rule; UUIDv4 avoids that ordering implication [S19]. |
| Acknowledgment permits discarding sent journal segments. | **Reject pending a retention protocol.** | An export is not proof that all intended recipients durably imported the data. Preserve the source event history until a defined retention/checkpoint policy is validated. If pruning is later needed, require a verified checkpoint and acknowledgments from all participating device identities, account for lost or retired laptops, and make recovery from an old backup explicit. Measure the storage cost first. Replication history can be pruned/compacted by systems such as CouchDB, so retained user-visible history must not be assumed to be permanent without an application policy [S08]. |
| Save and journal append should appear atomic. | **Retain as a requirement; revise implementation boundary.** | Within one local database transaction, either the operation, deduplication receipt, projection update, and outbox row commit together or none do. SQLite documents atomic commit under stated hardware/OS assumptions and has crash/reopen tests; these are design evidence, not evidence that this product has passed equivalent tests [S02, S05, S06]. Do not claim database-plus-photo atomicity. Use staged blob writes and validation, then commit the reference; reconcile orphan blobs after interruption. |
| The plan has not selected a database transaction or coordinated file protocol; attachment copying is an explicit action. | **Retain the open implementation choice; strengthen the attachment boundary.** | Prototype SQLite against the intended OSes and data, but keep the choice provisional. SQLite supports one writer at a time in WAL mode, and WAL is intended for processes on the same host, not machines using a shared network filesystem; preserve the `-wal` file when a WAL database is live, and use the Online Backup API or a properly closed/exported database for a coherent snapshot rather than copying only the main file [S01, S03, S07]. The Online Backup API is snapshot/backup support, not a multi-laptop merge protocol [S03]. Copy photo bytes only through explicit user action, with progress, integrity result, and missing/insufficient-space handling. |
| The plan proposes a retention setting for resolved conflicts but leaves recovery after retention open. | **Reject as an early user-facing setting; keep policy open.** | Do not invite users to discard conflict evidence before backup, restore, and old-device recovery behavior are understood. Initially keep original operations and resolution operations. Later define a tested retention/checkpoint policy, including how to reconstruct state from an older laptop backup and how to report history that has been pruned. |
| Validation would replay duplicates, interrupt saves, reconnect after competing deletion/photo addition, and restore a copied store. | **Retain; expand and mark proposed, not run.** | See “Validation plan” below. Add three-device week-long offline divergence, bundle truncation/tampering, duplicate import, lost acknowledgment, device reinstall, missing/partial photo bytes, and disk-full cases. No validation in this draft has been executed. |
| Identity and durability should be settled before convenient merge behavior. | **Retain and make the staging gate explicit.** | First settle operation identity, crash recovery, bundle receipt/idempotence, and the tombstone rule. Then add field merge behavior and conflict-review conveniences. Do not equate a library's deterministic merge with a user-approved resolution. |

## Data and transfer contract to prototype

A candidate record should have a stable `observation_id` and typed survey fields. Each accepted change should include `change_id`, `device_instance_id`, optional human label, observation ID, operation type, changed field/value or tombstone, causal parent change IDs (or the complete set of current heads), schema version, and a display timestamp. Causality and stable IDs determine duplicate recognition and concurrency; timestamps are informational. A resolution is itself a change that identifies the alternatives it resolves. An imported change must preserve its original ID and provenance.

For each laptop, use a database transaction to: validate that the operation ID has not already been applied; append the operation; update the derived observation/conflict state; record the import or local edit receipt; and update pending export state. If an operation was already imported, return an “already present” result without applying it twice. Keep the immutable operation history separate from the materialized current view conceptually, even if both occupy one SQLite file.

A user-created bundle should contain a manifest with study ID, bundle ID, schema/protocol version, exporting device ID, included change IDs and causal heads, photo IDs included or omitted, byte lengths, and SHA-256 digests. Validate the entire manifest, lengths, and digests before import. Apply changes in one database transaction and record the bundle receipt in that transaction, so retry after an interrupted transfer is safe. A missing photo should remain a visible unavailable attachment, not make its observation disappear. A partial bundle must be rejected or safely resumable; it must never be acknowledged as fully imported. SHA-256 supports byte-integrity checks but does not provide authenticity or encryption [S20]. If the group needs protection from tampering or exposure on lost media, specify signing/encryption and key recovery separately; those requirements are not supplied by the brief.

SQLite is a plausible local prototype, not a fixed choice. In WAL mode, readers and a writer can proceed concurrently but only one writer exists; long readers can delay checkpointing. WAL's shared-memory index and recovery assumptions are local-host constraints, so do not put the active database on a shared network drive [S01, S07]. SQLite's automatic checkpoint threshold and power-loss behavior should be checked against the selected library build and durability settings. The current official release observed during this investigation is SQLite 3.54.0; the documented WAL-reset fix is in 3.51.3 and later, but that is version context, not a mandate to ship the newest release without platform validation [S01, S04]. Use its Online Backup API or close/checkpoint and verify a portable database copy; never treat a raw copy of a live main database file as a reliable backup [S01, S03].

Two alternative families deserve a bounded prototype rather than a premature decision. CouchDB/PouchDB provide revision-tree replication and offline/local-to-remote patterns, with accessible conflict branches, but ordinary reads can conceal alternatives behind a deterministic winner; application code still needs conflict UI, tombstone policy, attachment policy, and evidence that selected replication mode does not move unwanted photo bytes [S08–S14]. The PouchDB release listing observed here shows 9.0.0 (June 2024) [S21]; upstream integration tests are useful behavior evidence but moving documentation/master tests are not a pinned dependency contract [S14]. Automerge retains concurrent values and can combine independent fields, but it also defines deterministic visible winners and its map deletion/set rules need an explicit application tombstone policy. The observed JS release is v3.4.1; the Rust crate/binding, target OS support, and persistence behavior still need pinning and evaluation [S16–S18]. No alternative removes the need to specify identity, user-visible review, transfer receipts, photo policy, backup, and retention.

## Review behavior

The main survey list should show which records are ready, need review, have a missing photo, or are deleted. A review item should summarize the conflict in plain language and show the shared base, competing values, device/author labels, and change ancestry where available. A timestamp can help orient a reviewer but must be labeled as device-reported context, not as a reliable ordering rule. The choices should be explicit, preserve all source changes, and create a resolution record. “Keep both” should mean creating a separately identified observation linked to the original, not allowing duplicate IDs. Resolve a delete/edit case through an explicit restore or keep-deleted choice. Avoid merging free-text notes automatically in the first version.

## Validation plan — proposed, not executed

1. **Identity and idempotence:** create changes on three isolated laptops, including after reinstall and restored backup. Confirm change IDs remain unique, imported IDs are preserved, duplicate bundles have no second effect, and identical local revision counters do not collapse distinct operations.
2. **Causal merge:** edit different fields from the same base and confirm only schema-approved independent fields combine. Edit the same field on two laptops, with skewed/reset clocks and different import orders; confirm both alternatives survive, neither timestamp nor arrival order selects the review outcome, and the resolution is another auditable operation.
3. **Delete/resurrection:** delete on one laptop while another changes a field or adds a photo from a pre-delete copy. Import in both orders and with duplicate bundles. Confirm a review appears and no operation silently clears the tombstone. Exercise explicit restore as a new resolution.
4. **Local crash durability:** inject process termination and available power-loss/fault conditions around each save stage, WAL write, checkpoint, backup, blob stage/rename, DB reference commit, bundle import, and receipt commit. Reopen on the target platform; check SQLite integrity and application-level all-or-nothing operation/projection/receipt state. Include disk-full and interrupted checkpoint/backup. SQLite's own crash tests are scenario references only [S05, S06].
5. **Manual transfer:** truncate or corrupt a bundle, omit a dependency, duplicate it, interrupt copy and retry, lose an acknowledgment, and import from an older backup. Confirm validation rejects or resumes incomplete bundles safely and never instructs a sender to prune an operation solely because it exported it.
6. **Photos and scale:** with representative and deliberately large attachment sets, check digest failure, missing bytes, duplicate blobs, removable-drive removal, selection/space warnings, and explicit metadata-only exchange. Measure create, search, edit, conflict review, export/import, backup, restore, disk use, and sync time for 50,000 observations plus measured photo-volume scenarios. Size targets cannot be set until devices, data, and interaction expectations are known.
7. **Recovery and retention:** restore each laptop from an old backup after changes have circulated; verify re-import, device retirement, conflict history, and tombstone behavior. Keep full history for the prototype. Do not expose a deletion/retention control until recovery and compaction policy is demonstrated.

These are acceptance proposals. They have not been run; there is no evidence here of product correctness, performance at 50,000 records, or safe photo transfer.

## Decisions still needed from the field team

- Which operating systems and filesystems must be supported, and can a chosen local database use reliable locking/flush semantics there?
- Do the three laptops transfer only by removable media, or may users explicitly connect them on a local network? Is any relay machine available, and who initiates a transfer?
- How are device identities assigned, labeled, backed up, replaced, and retired? Are labels personal names, team roles, or generic laptop names?
- What are typical and maximum photo count/size, retention period, per-laptop free space, and whether users need transfer of all photos or can choose subsets?
- Must bundles be encrypted or authenticated against a lost/modified USB drive? How are keys shared and recovered while offline?
- What are observation fields, valid field-level merge rules, whether a deleted observation may be restored, and whether restoring should preserve the original ID or create a linked new observation?
- How long must conflicts, deletes, and audit history remain recoverable? What happens if one laptop is lost or does not return for the next sync?
- What response times and usability expectations define acceptable review and bundle workflows?

Until these questions are answered, keep storage engine, language, relay, pruning, and automatic merge scope as prototype decisions. The plan's primary direction is sound in emphasizing identity and durability first, but the implementation must use a single, testable local commit boundary, explicit manual bundle transfer, causal conflict handling, durable tombstones, and user-visible recovery.
