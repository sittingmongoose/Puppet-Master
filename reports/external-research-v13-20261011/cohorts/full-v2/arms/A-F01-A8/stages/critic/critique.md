### SCW-01 — SQLite backup lifecycle

- **Locator/context:** “Data and transfer contract to prototype,” final SQLite paragraph. **Exact sentence:** “Use its Online Backup API or close/checkpoint and verify a portable database copy; never treat a raw copy of a live main database file as a reliable backup [S01, S03].”
- **C:** the warning covers copying only the main file while a live WAL database may have committed state in its WAL. **C*:** substitute “closed and checkpointed” for “live”; otherwise keep the sentence unchanged. **One-selector delta:** lifecycle, live → closed/checkpointed.
- **Evidence/applicability:** S01, [SQLite Write-Ahead Logging](https://www.sqlite.org/wal.html), current unversioned official docs with release context S04 (3.54.0, 2026-10-09), §§2.2, 4, accessed 2026-10-12 00:52:41Z; excerpts: “The WAL file is part of the persistent state” and separating it can lose committed transactions or corrupt the database. S03, [SQLite Backup API](https://www.sqlite.org/backup.html), unversioned official docs, §§1 and 1.1, accessed 00:52:41Z; completed backup produces a snapshot; the page distinguishes database-aware backups from other techniques.
- **Relations on same evidence E:** C **ENTAILS**: a live main-file-only copy can omit WAL state. C* **UNDETERMINED**: closure/checkpoint removes the cited WAL hazard, but these excerpts do not establish every direct file-copy failure mode or platform guarantee. The draft already says to verify the portable copy and test selected filesystems.
- **Disposition:** retain with that qualification; no replacement proposed. **Affected decision:** crash recovery and manual transfer; exact plan’s atomic-save and recovery assumptions.

### SCW-02 — CouchDB deletion filter scope

- **Locator/context:** plan disposition row “Delete-versus-edit is sent to review.” **Exact sentence:** “CouchDB propagates deletes as revisions/tombstones, and its replication documentation describes filters that must preserve deleted-document content when using such a filter [S09].”
- **C:** content-dependent replication filters encounter deleted documents without their old content and may need a deletion representation that retains filter fields. **C*:** change only the applicability condition from “when using such a filter” to “when using unfiltered replication.” **Delta:** condition, content-dependent filter → unfiltered replication.
- **Evidence/applicability:** S09, [CouchDB Replication Introduction](https://docs.couchdb.org/en/stable/replication/intro.html), CouchDB 3.5 stable docs (exact patch not exposed), §§2.1.3–2.1.5, accessed 2026-10-12 00:52:51Z and 00:53:01Z. Excerpts: deletion is “represented by a new revision” and source deletion is also applied at the target; only for filters “that depend on the document’s content” does the deleted document lack content, with a documented `_deleted:true` workaround and validation handler.
- **Relations on same evidence E:** C **ENTAILS** as a conditional caveat, though “must preserve” compresses the documented workaround. C* **UNDETERMINED**: the source describes ordinary unfiltered tombstone propagation, not a general deleted-content requirement when no content-dependent filter is used.
- **Disposition:** retain, scoped to content-dependent filters; no product rule should be inferred from the workaround. **Affected decision:** delete propagation and optional relay filtering. No supported replacement beyond this narrower statement.

### SCW-03 — Default versus conflict-aware reads

- **Locator/context:** plan disposition row “A revision mismatch opens a card showing the old value and both edits.” **Exact sentence:** “PouchDB and CouchDB expose revision conflicts, but ordinary reads can still show a deterministic winner unless conflict variants are explicitly requested [S08, S12, S14].”
- **C:** default reads can hide other concurrent leaves behind the selected winner. **C*:** change only capability modality “can” → “cannot” in “ordinary reads can still show a deterministic winner.”
- **Evidence/applicability:** S08, [CouchDB Replication and Conflict Model](https://docs.couchdb.org/en/stable/replication/conflicts.html), CouchDB 3.5 stable docs, §§2.3.1 and 2.3.4, accessed 00:52:51Z: basic GET shows only the deterministic winner; `?conflicts=true` exposes other revision IDs, then separate GETs retrieve those leaves. S12, [PouchDB Conflict Guide](https://pouchdb.com/guides/conflicts.html), moving official guide, “Eventual conflicts,” accessed 00:53:15Z: default winner plus `{conflicts:true}` returns conflict IDs.
- **Relations on same evidence E:** C **ENTAILS**. C* **CONTRADICTS**: both docs explicitly describe ordinary/default reads as returning the deterministic winner. Pouch’s guide says the CouchDB algorithm applies; this is API behavior, not a product review policy.
- **Disposition:** retain; ensure a proposed review reader explicitly retrieves branches and does not mistake the default projection for the full conflict set. **Affected decision:** review queue and the plan’s “conflict card.”

### SCW-06 — WAL reader-duration contrast

- **Locator/context:** “Data and transfer contract to prototype,” final SQLite paragraph. **Exact claim:** “In WAL mode, readers and a writer can proceed concurrently but only one writer exists; long readers can delay checkpointing.”
- **C:** a long-lived read transaction may prevent checkpoint progress. **C*:** change only duration “long” → “short.” **Delta:** quantity/duration, long → short.
- **Evidence/applicability:** S01, [SQLite Write-Ahead Logging](https://www.sqlite.org/wal.html), official docs, §§2.2 and 6, accessed 2026-10-12 00:52:41Z. Excerpts: only one writer per WAL; a checkpoint stops at a current reader’s end mark; a long-running read transaction can prevent progress until it ends; overlapping readers can prevent checkpoint completion.
- **Relations on same evidence E:** C **ENTAILS**. C* **ENTAILS** in the narrower sense of temporary delay: even a short active reader may make a checkpoint stop at its end mark until it ends. This is nondiscriminating, not evidence that short reads cause persistent checkpoint starvation.
- **Disposition:** retain, but describe persistent starvation as requiring readers that keep overlapping / fail to end. **Affected decision:** SQLite checkpoint and failure/performance validation.

## Ordinary review of brief and exact revealed plan

### Overall assessment

No **material wrong** claim was found in the reviewed packet or the primary evidence checked here. The investigator’s major plan dispositions are well supported: one local DB transaction is the atomic unit; local revision counters and labels are not global identity; arrival and wall time are not merge order; acknowledgments are not durable import proof; a relay is optional while explicit manual transfer remains the baseline; and deletion requires an application tombstone/review/resolution rule. The proposal does not silently resolve the brief’s unknown platform, connection, photo-volume, retention, or identity policy.

### Issues by required class

- **Material incomplete — operator explanation:** the brief asks for a small operator-facing explanation of what needs review. “Review behavior” specifies the information and choices a review item should display, but provides no short example explanation in plain user-facing language. This is a gap in the requested proposal detail, not a source defect. Locator: “Review behavior”; affected brief clause: operator-facing explanation.
- **Material incomplete — persistence boundary remains a prototype risk:** the draft correctly separates DB transaction atomicity from photo-file ordering and marks rename/flush/recovery platform-dependent. It proposes scans for orphans and repair for missing blobs, but no recoverable startup/reconnect procedure is yet specified. This remains an explicit validation/design obligation rather than an implementation claim. Locator: recommendation paragraph on blobs and Validation plan items 4, 6.
- **Unsupported:** none found among the consequential claims checked. Product behavior is not inferred from library behavior; PouchDB issue evidence is correctly labeled as a report.
- **Minor locator/wording:** SCW-02’s phrase “filters that must preserve deleted-document content” is compressed: the official docs describe content-dependent filters receiving a deleted revision without the old body and a workaround that uses a `_deleted:true` field plus validation. Keep the qualifier attached whenever this source is summarized.
- **Honestly unresolved external input:** supported operating systems/filesystems and durability guarantees; photo count/size and free space; transfer routes and relay availability; user/device identity lifecycle; field schema and allowed merge rules; bundle authenticity/confidentiality/key recovery; tombstone/history retention and lost-device recovery; review latency/usability targets. The draft leaves these open, as the brief requires.

### Exact-plan coverage and validation boundary

The draft addresses each released-plan clause: it rejects an uncoordinated second store; replaces revision+author identity; makes photo paths local metadata rather than identity; changes relay/arrival-order baseline to user-started portable bundles; keeps competing values visible; limits field merge to known ancestry/schema rules; makes delete review durable; rejects send-ack pruning; specifies one-DB atomic commit with staged blobs; defers retention controls; expands the proposed validation sequence; and gates convenience merging on identity/durability. No exact-plan disposition was omitted in my clause-by-clause comparison.

Attachment size, connection speed, OS, language, and engine stay open. Alternatives remain candidates, not an asserted winner. The draft distinguishes proposed acceptance tests from executed work and says no checks were run. Upstream SQLite tests are reference scenarios only; they do not validate this application. No implementation, source test, benchmark, crash test, or UI test was run in this critic stage.

The scoped evidence does not prove every platform-specific durability claim or every release’s compatibility with an undecided application.
