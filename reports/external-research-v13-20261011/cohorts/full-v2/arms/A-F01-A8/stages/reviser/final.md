# Reviser final — disconnected field-survey edit journal

**Run/stage:** A-F01-A8 / reviser  
**Research snapshot:** 2026-10-12 UTC  
**Status:** research-backed proposal; no implementation or product validation was executed.  
**Scope:** three field laptops, up to one disconnected week, approximately 50,000 observations per season, notes/confidence/site identifiers and separately stored photos, concurrent offline edits, interrupted saves/reconnects, and a manual transfer path.  
**Decision posture:** carry one local transactional store plus an application-owned causal change protocol forward as the first bounded prototype candidate. SQLite is a candidate for the local store, not a selected engine. Keep CouchDB/PouchDB and Automerge as bounded alternatives. No source-backed evidence resolves the field team's platform, data, identity, retention, security, or usability choices.

## Proposal summary

Each observation needs an immutable ID distinct from its editable site identifier. Every accepted change needs a unique change ID, durable device-instance identity, parent/head references that establish what state it was based on, schema version, operation kind, field changes or tombstone, and device-reported time for display only. A device-local revision counter may help detect stale edits but cannot identify a change or choose a winner. Store original changes and later resolutions as history; derive a current searchable view from them.

Treat the append-only operation history, deduplication/import receipt, materialized observation/conflict view, and local export bookkeeping as one logical commit. If SQLite is chosen, place these records in one database transaction where feasible. A successful save commits all of that local state; an interrupted transaction either recovers as committed or absent under the selected engine's documented platform assumptions. SQLite does not make a separate photo file atomic with that transaction. Do not use a live SQLite WAL database file as the peer-to-peer journal, share it through a network filesystem, or copy only its live main file as a backup. WAL readers and a writer can overlap, but there is one writer per database file; long readers hold a snapshot end mark that can delay checkpoint progress. Persistent checkpoint starvation requires readers to remain continuously overlapping, while a short reader may cause only a temporary pause. Select and test journal mode, durability settings, filesystem, and backup process for the actual target devices [S01–S07].

Use explicit, user-started, versioned change bundles as the baseline reconnection path. They work through removable media or a user-selected folder when no network is available. A local relay can later transport the same bundle/change protocol as an optional, user-initiated path. Neither route requires a hosted account. Identify each change and bundle independently; preserve IDs on import; deduplicate by change ID; validate the complete manifest, dependencies, lengths, and hashes before application; apply changes and record a durable import receipt together. An interrupted or repeated import must be safe to retry. Export acknowledgment alone never authorizes pruning history, because it does not prove that every intended laptop durably imported the changes.

Merge only edits to different fields when known ancestry and the field schema establish they are independent. Keep same-field concurrent values, unknown ancestry, delete-versus-edit, and delete-versus-photo-add in a review queue. Do not choose by arrival order, author label, revision count, or wall clock. Treat a note as one field initially; do not silently invent character-level merge semantics. A reviewer’s choice creates a new resolution operation that names the alternatives it resolves. A restore is explicit and recorded; the unresolved field-team choice is whether a restored observation keeps its original ID or creates a linked replacement.

Photo bytes remain local, separate blobs by default. A reference has an opaque photo ID, byte length, media type, digest, and local availability/path metadata; a path is not the photo's identity. Reconnection exchanges reference/availability metadata unless the user separately selects bytes to transfer. A digest can detect accidental byte mismatch, but does not authenticate a sender or encrypt the media [S20]. The photo-file/DB boundary needs a recovery protocol: first persist an attachment intent, then stage bytes in the managed photo root, flush and verify size/digest, atomically rename on the same filesystem where supported, then commit the visible reference/availability event in a DB transaction. On startup/reconnect, reconcile pending intents and staged/final files: verify a complete file and finish the reference commit, offer retry or discard if no complete file exists, and classify an unreferenced finalized blob as recoverable orphan. If a committed reference has missing or mismatched bytes, preserve the reference and observation, mark the attachment unavailable, and offer locate/retransfer/replace; never silently remove it. Atomic rename, file and directory flush behavior, and power-loss guarantees are platform-dependent and still require testing.

The survey list should distinguish ready, needs review, missing photo, and deleted states. A review card shows the shared base if known, both proposed values, what each laptop changed, device/author labels, the causal relationship, and photo/deletion consequences. Timestamps are device-reported context, not an ordering rule. Offer keep-left, keep-right, enter-combined-value, and explicit restore/keep-deleted choices where applicable; retain all source changes and record the resolution.

**Suggested operator text:** “Two laptops changed this observation while they were disconnected. The app kept both edits because it cannot tell which one you intended. Compare the shared starting value and each laptop’s change, then keep one or enter a combined value. Your choice will be saved, and both original edits will stay in the history.” For a delete/photo collision: “One laptop deleted this observation while another added a photo to an older copy. Nothing has been restored or removed automatically. Choose whether to keep the observation deleted or restore it; the photo will remain marked unavailable here until you choose to transfer or locate its file.” These are proposed strings; comprehension has not been tested.

## Candidate approaches and evidence limits

| Candidate | What it offers | Conditions, limits, and fit |
|---|---|---|
| Embedded transactional store plus application-owned operation history and merge protocol | Clear control over identities, tombstones, conflict review, bundle import receipts, and manual transfer. WAL is host-local and has checkpoint, sidecar, one-writer, and durability-setting considerations. Application code must own ancestry, duplicate delivery, version evolution, retention, bundle integrity, and review policy. A separate journal file would need its own cross-resource recovery protocol. |

| Automerge/local-first CRDT | Preserves causal changes, combines some independent fields, and exposes same-property conflict values. The observed JS release is v3.4.1; its Rust integration is not established by that release record. | A deterministic visible value may still be selected while competing values require an explicit conflict-aware read and user policy. A concurrent map-key deletion and set yields the set value; that rule says nothing by itself about an observation-level tombstone. Application identity, attachment handling, review, manual bundles, and release pinning remain necessary [S16–S18]. |
| Plain folder sync or copying an open database file | Easy to explain as a transport for static files. | Not a change protocol: it does not establish causal ancestry, idempotent import receipts, delete policy, or a safe live-WAL snapshot. Use explicit structured bundles or a database-aware snapshot path instead [S01, S03]. |

The SQLite official WAL page opened for this review says all WAL database processes must be on the same host because the wal-index uses shared memory, only one writer can append at a time, and a current reader's end mark can stop checkpoint progress. It distinguishes a long-running reader from persistent starvation: readers that keep overlapping with no reader gaps can prevent checkpoints from completing. The same page says the WAL file is persistent DB state and separating it from a live database can lose committed transactions or corrupt the database. The Online Backup API page says a completed backup produces a snapshot; it also says an external copy may corrupt its destination after power/OS failure while copying. Thus, the narrower live-main-file-only warning is supported; closing/checkpointing removes the particular omitted-live-WAL hazard but does not prove every direct-copy path or platform guarantee. Verify any portable copy and prefer a completed database-aware backup where appropriate [S01, S03].

CouchDB 3.5 stable documentation describes deletion as a new revision propagated to the destination. Separately, it warns that a filter **depending on document content** may receive a deleted revision without the old body; the suggested `_deleted:true` approach preserves data and attachments for filter evaluation. Do not generalize that filter caveat to ordinary unfiltered replication [S09]. CouchDB and PouchDB docs also show that ordinary/default reads can display a deterministic winner; conflict-aware options expose conflicting revision IDs, after which the application must fetch the leaves [S08, S12]. That library behavior is a reason to implement review, not a user-approved merge policy.

## Local data and transfer contract

A proposed observation has `observation_id` and typed site identifier, note, confidence, and other field data. A proposed operation has `change_id`, `device_instance_id`, optional human label, observation ID, operation kind, changed field/value or tombstone, causal parents or complete heads, schema/protocol version, and display timestamp. A resolution names the conflicting change IDs and stores the user's chosen result. Use collision-resistant random IDs such as UUIDv4 as candidates for observation, change, photo, bundle, and device-instance identity; UUID uniqueness is probabilistic, not absolute. UUIDv7 contains time and must not be used as causal proof. Device reinstalls, backups, replacement, naming, and retirement need a field-team rule; do not silently reuse a counter or assume that an author label is durable identity [S19].

For a local edit/import, a transaction should validate the change ID, append the immutable operation, update the derived view/conflict state, record import receipt (or local edit receipt), and update pending export bookkeeping. If the ID is already present, return an already-known result without applying it twice. For bundles, include study and bundle IDs, format/schema version, exporter device ID, operation IDs and required causal heads/dependencies, photo IDs included or omitted, file lengths, and SHA-256 digests. Validate the whole bundle before applying it. Import receipt and operation application should share the local transaction. Truncated, malformed, digest-mismatched, or incomplete bundles must be rejected or safely resumable, never treated as fully imported. SHA-256 is integrity checking, not authenticity/confidentiality; signed or encrypted media and offline key recovery are open requirements only if the team decides it needs them [S20].

Keep full operation and resolution history for the first prototype. Do not expose a user retention control or prune merely on export, first import, or a sender's acknowledgment. Any future checkpoint/compaction policy must define required device acknowledgments, dormant/lost laptops, backup restoration, and tombstone survival. CouchDB's compaction retains revision identifiers while discarding non-leaf bodies and can prune revision history; that is evidence that library history is not automatically a permanent user audit log [S08].

## Exact revealed plan, reproduced in full

> The draft uses a transactional embedded store for observations and a second append-only journal carrying operation identifiers, author labels, and per-record revision numbers. Photos remain in a directory selected by the operator; journal entries hold relative references and hashes. Each laptop exchanges journal segments through a relay on the office network, with removable-media bundles as a fallback. Nothing requires a hosted account.
>
> For now, the relay accepts operations in arrival order. A revision mismatch opens a conflict card showing the old value and both edits. Nonoverlapping field edits are proposed for automatic merging, while delete-versus-edit is routed to review. The draft assumes that laptop-local revision numbers plus an author label uniquely identify operations, and that acknowledgment permits discarding sent segments. Whether either assumption survives reinstall, lost acknowledgments, and interrupted transfer is unresolved. Wall-clock timestamps are display information, not a winner rule.
>
> Save and journal append should appear atomic to the application. The draft has not yet selected one database transaction or a coordinated file protocol, and attachment copying remains an explicit action. It proposes a retention setting for resolved conflicts but leaves recovery after retention open. Validation would replay duplicate segments, interrupt saves, reconnect after competing deletion and photo addition, and restore a copied store. No checks have been run. A staged proposal should settle identity and durability before adding convenient merge behavior.
>
> This is a provisional draft for review after the declared reveal, not an endorsed answer. Resolve material assumptions through applicable primary evidence; retain open user-data questions when they cannot be answered from sources. No future product deployment is requested.

## Independent adjudication of all six selected SCW records

All six frozen records were independently rechecked against governing primary pages in this stage; none was substituted or left as SCW_NOT_RUN. The source map records exact URLs, versions/commits where exposed, locators, access UTC, the operation observed, conditions, and applicability. Unversioned/moving documentation and the moving PouchDB `master` test are identified as such. The web fetch does not pin an otherwise moving page to an exact build.

1. **SCW-01 — SQLite backup lifecycle. Disposition: amend; retain the narrower warning.** The SQLite WAL page says the live `-wal` file is part of persistent DB state and separating it can lose committed transactions or corrupt the DB. That entails the selected claim for copying only a live main file without its WAL. The alternate closed/checkpointed lifecycle is **not shown false** by that evidence; the Online Backup page also warns that an external file copy may be corrupted by power/OS failure during copying. Keep the statement specific: a raw copy of a live main file alone is unsafe; after clean close/checkpoint, still verify the copy and test the platform, and prefer a completed database-aware backup for a coherent snapshot [S01, S03].
2. **SCW-02 — CouchDB deletion/filter scope. Disposition: amend for precision; accept C, retain uncertainty about C*.** CouchDB 3.5 stable docs state a deleted source document is deleted on the target because deletion is a new revision. The special content-loss issue arises for filters that depend on document contents; their workaround retains data and attachments. This supports the criticism's narrow condition, not applying that filter workaround to unfiltered replication. Phrase it as a conditional filter caveat, not a generic delete rule [S09].
3. **SCW-03 — default versus conflict-aware reads. Disposition: accept C; reject C*.** CouchDB's basic GET shows only the deterministically chosen winner without indicating other branches; `?conflicts=true` returns IDs and subsequent revision fetches retrieve variants. PouchDB's guide likewise says default replication selects a deterministic winner and `{conflicts:true}` detects alternatives. Thus C is supported and the proposed C* (`can` → `cannot`) contradicts both sources. The review UI must explicitly request and fetch branches; an ordinary read is insufficient [S08, S12].
4. **SCW-04 — low-revision-limit deletion report. Disposition: retain uncertainty; accept the scope limit.** The PouchDB issue page is still Open in the observed view. Its reporter describes CouchDB→PouchDB, a low `revs_limit` (including a `revs_limit=3` reproduction after six edits and deletion), and a reported deletion propagation failure; the page does not establish a maintainer-confirmed general defect or default-setting safety. The moving PouchDB integration test at lines 1390–1419 re-puts a previously removed document without `_rev`; that establishes API re-creation behavior, not intended observation policy or the issue's generality. Keep this as scoped risk evidence and require delete-history testing if this stack is selected; do not reject the alternative or assert a confirmed defect [S14, S15].
5. **SCW-05 — Automerge map key versus observation tombstone. Disposition: amend; accept C and retain uncertainty about C*.** The current moving merge-rules page says a concurrent delete of map key `x` and set of `x` yields the new set value. It describes nested maps/lists/simple values, not survey-record lifecycle. It therefore supports C as rationale for a higher-level policy, while C*'s substitution of an observation tombstone is neither specified nor contradicted by this library rule. State the map-key semantics exactly and separately propose an application tombstone/review operation; do not attribute that policy to Automerge [S17].
6. **SCW-06 — WAL reader-duration contrast. Disposition: amend; accept C and qualify C*.** SQLite says a reader's end mark may stop a checkpoint and a long-running read can prevent progress until it ends. It also distinguishes persistent starvation: continuously overlapping readers with no reader gaps can prevent checkpoints completing and grow the WAL. A short active reader can temporarily hold its end mark, but that does not imply persistent starvation. Preserve the “only one writer” limit and sharpen checkpoint validation to test both a long reader and a continuous-overlap/no-gap case [S01].

## Integration sequence and proposed failure-oriented validation

1. **Specify identity and event semantics.** Write the operation/bundle schemas, device lifecycle, causal parents/heads, duplicate rules, field independence table, tombstone semantics, resolution format, and history invariants. Decide whether the immutable history and current projection share one database.
2. **Prototype local persistence and recovery.** On each supported OS/filesystem, compare the candidate embedded store and relevant journal/durability settings. Inject process termination and available power-loss conditions around local transaction begin/commit, WAL write/checkpoint, database backup, pending attachment intent, staged blob write/flush/verify/rename, final reference commit, and import receipt. On reopen/startup verify that each state is either complete, safely retryable, or explicitly repairable; run engine integrity checks and application-level operation/projection/receipt assertions. Include disk-full and failed flush/rename. These checks are proposals only.
3. **Prove manual transfer before relay convenience.** Create three isolated laptops and one-week-equivalent divergence histories. Import the same bundle twice and in different orders; lose an acknowledgment; truncate/corrupt a bundle; omit a dependency; interrupt media copy and retry; restore an older backup; reinstall/retire a device. Confirm IDs survive, duplicates do not reapply, receipts are transactional, no partial bundle is acknowledged, no export alone prunes history, and all unresolved branches remain visible. Then compare an optional local relay using exactly the same semantics.
4. **Exercise merge and deletion.** From a common base, edit independent fields, same scalar fields, note text, site ID, confidence flag, and photo list on separate laptops. Skew/reset clocks and reverse import order. Verify only schema-approved independent fields combine, all same-field alternatives remain, no timestamp/arrival-order winner is used, and every choice creates a resolution event. Delete on one peer while a second edits or adds a photo from an old state; test both import orders and duplicates. Confirm no silent resurrection/erasure and explicit restore/keep-deleted works.
5. **Exercise attachment recovery and privacy.** Use representative and deliberately large files, missing/corrupt/duplicate bytes, removable media removal, no-space failures, interrupted staging/rename, crash after rename before DB commit, and missing media after a reference commit. Verify metadata-only exchange is default, byte transfer requires explicit selection, digest failures remain visible, and users can locate/retransfer/replace. Test selected replication APIs separately if CouchDB/PouchDB is prototyped to prove that they do not move photo bytes without consent.
6. **Measure scale and usability only after data are known.** Populate 50,000 observations plus measured photo-count/size distributions. Measure edit/search/list, review, export/import, backup/restore, storage, and transfer time on actual target devices; attachment sizes and link rates are currently unknown, so no numeric throughput target can be justified here. Conduct task-based review with field users: can they explain why the record is flagged, distinguish device-reported time from precedence, choose the intended branch, and recognize missing bytes?
7. **Gate history reduction and release pins.** Keep full history in the prototype. Before any compaction/retention option, test all devices returning from stale backups, a permanently lost device, tombstone retention, and audit reconstruction. Pin exact DB/library releases and adapters, record their source IDs, then repeat compatibility and recovery tests on each supported platform. The current observed context is SQLite 3.54.0 (S04), PouchDB 9.0.0 (S21), and Automerge JS v3.4.1 (S18); these observations are not a deployment mandate or a proof of Rust binding support.

**Executed validation:** none. The work performed was document/source reading and claim adjudication only. All seven steps above are proposed; do not report them as run or passed.
