# Investigator discovery — supplier spreadsheet reconciliation

## Scope and evidence boundary

This is brief-only discovery for the supplier import component. The user asks for a research-backed software proposal, no implementation, no actual supplier data import, and no production database modification. I read the assigned brief and researched public primary documentation and candidate library source only. The input map did not supply a stock-app repository path or its callers/tests, so I did not inspect local project code or claim compatibility with its current database schema. Upstream library source and issue reports were inspected; the local application integration still requires an owner-provided code path and read-only review. No case data was used.

The original brief's requirements are covered here: delimited input with inconsistent headers, decimal separators, and product codes; a preview that distinguishes new products from updates; repeated rows and reused codes after discontinuation; safe recovery after a batch stops; up to 80,000 rows; saveable mappings with drift detection; protection against duplicate quantity application on reimport; traceable invalid rows; cancel without stock changes; no ambiguous number coercion, global uniqueness assumption, formula execution, or overwriting notes from unmapped columns; local-only supplier data; comparison of feasible approaches; unavoidable staff decisions; and staged validation with defined success and partial failure. This is discovery, not the exact-plan draft. The source register is [sources/index.md](sources/index.md) and full machine-readable metadata is [source-map.json](source-map.json).

## Candidate approaches

### Parse as a streaming sequence of raw fields

For the stated delimited-text inputs, a configured Rust `csv` Reader is a small, direct fit. Its builder allows a non-comma delimiter and header setting, and its reader can yield one record at a time; it does not require inference into Rust numeric types. The examined csv 1.4.0 source has comma delimiter, header handling, and fixed record widths as defaults. Configure dialect from an explicit local supplier profile, keep fields as strings/bytes, and map column positions only after the preview confirms headers. The library is permissive in how it salvages questionable CSV, so parser success alone cannot mean data validity. If variable field counts are enabled to continue after a malformed row, compare every row with the selected header width and mark mismatches invalid; never treat the flexible option as schema validation. [SRC01](sources/index.md#src01) [SRC03](sources/index.md#src03)

Keep source codes as text (so leading zeros and punctuation survive). Normalize headers only to offer mapping suggestions; retain original labels and positions. Save a profile with supplier identity, header row, exact normalized header vector, delimiter/quote/encoding, mapped source positions, number separators, and an explicit stock-quantity operation. On a later file, compare its structure with the saved signature and show added, missing, renamed, reordered, or duplicate-normalized headers before reusing any mapping. A changed structure pauses automatic reuse; a human approves the revised mapping. An unmapped column is visible as ignored and cannot become a staff-note update.

For invalid rows, preserve the file fingerprint, profile version, byte offset, logical record index, and raw values needed for review. CSV positions expose these offsets/indices, but the upstream report for csv 1.4.0 says its line count can lag on CRLF input. Therefore show a logical data-record number and byte offset as the trace anchor; show physical line only as a convenience that must be verified for the selected parser version and dialect. [SRC02](sources/index.md#src02) [SRC04](sources/index.md#src04)

If a supplier file is not valid UTF-8, do not silently replace undecodable bytes. The crate supports byte records; either reject non-UTF-8 in the first release or offer an explicit encoding choice and strict decode. A profile records that choice. [SRC03](sources/index.md#src03) [SRC07](sources/index.md#src07)

### Compare a dataframe parser

Polars is a viable alternative if the component needs columnar transformations or aggregate analysis. Its current CSV options infer a schema from 100 rows by default and offer an option to keep going after parser errors. That is convenient for analysis but risky for reconciliation: a product code can look numeric in the first sample and contain letters/leading zeros later; an ignored row could disappear from a staff review. If selected, force identifiers and raw supplier fields to strings, turn off silent error continuation, and validate each row with source positions. For this 80k-row import, an explicit streaming record parser plus disk-backed staging is easier to reason about than loading a general dataframe, subject to the performance benchmark. [SRC08](sources/index.md#src08)

A true XLSX reader such as Calamine is a separate future path, since the brief names delimited text. Its 0.36.0 release adds streaming cell/formula-record APIs but also records a Rust MSRV increase and formula/number-format fixes. It is not evidence that workbook formulas should be evaluated. Do not add XLSX until worksheet selection, cached versus formula values, external links/macros, limits, and formula display are separately decided and tested. [SRC12](sources/index.md#src12)

### Exact quantity parsing, not guessing

Keep every cell as the original string. The supplier profile must declare the decimal mark, optional grouping mark, accepted sign/grouping syntax, and whether quantities are integer units, fractional units, or something else. Validate grouping before translating a value into canonical decimal text, then use an exact decimal parser if the stock model supports decimals. `rust_decimal::Decimal::from_str_exact` detects unrepresentable scale; it does not choose a locale. If the profile is missing or a value is ambiguous (for example, `1,234` could be 1.234 or 1,234), flag it and require a staff choice. Show raw and interpreted value side by side. Do not use floating point, locale sniffing, rounded conversion, or sampled majority as authority. [SRC06](sources/index.md#src06)

## Identity and duplicate policy

A supplier's item code is a namespaced, versioned alias, not a global product key. The durable match target should be the application's internal product ID. An exact match may be automatic only when that supplier's currently approved alias points to exactly one active internal product and the relevant mapping/profile has no unresolved drift. Keep retired alias history. If a supplier reuses an old code after a discontinued item, do not reactivate or overwrite the old product automatically: show the historical target and ask staff whether this is a new lifecycle/product or an intentional reactivation. Fuzzy description/brand/packaging similarity can produce suggestions only; never write from a suggestion without selection.

Detect duplicate source headers after the configured normalization, because a named-field deserializer can make repeated names ambiguous (the upstream csv discussion remains open). Detect repeated product-code groups inside the file before apply. Exact repeated rows may be copy errors or intentional separate lines; conflicting rows may encode distinct locations or conflict. Do not silently discard, sum, or let last row win. Group them in review, retain every source location, show whether the mapped values agree, and require an explicit duplicate policy/row decision. Compare candidate records with current active and discontinued inventory separately. [SRC05](sources/index.md#src05)

The staff must also decide which source fields are authoritative and how supplier code case/spacing/leading zero differences work. A conservative first profile preserves raw code and requires explicit normalization rules. Identical descriptions or a matching code without supplier context never prove identity.

## Preview, privacy, and application

The import should be a local staged workflow:

1. Select a local file and supplier; compute a content fingerprint; detect file type, encoding and candidate delimiter; display raw headers and a small sample. Suggestions must be confirmable.
2. Resolve header mappings and numeric conventions; compare the current header signature with the saved profile. Save the approved profile locally and version each change.
3. Stream at most the configured 80,000 logical records into local staging, retaining raw cells and source coordinates. Build a complete review set: new, update, unchanged/no-op, malformed, invalid numeric, duplicate, ambiguous match, unmapped column, and potential reimport. Cap file bytes, field sizes and preview memory as a proposed hardening item; the brief sets row count but not byte size.
4. Show searchable/filterable, paged or virtualized row differences, with source record and raw values next to normalized interpretation and current stock. New versus update is based on the selected internal target; unmapped fields never alter notes. Staff chooses the action for ambiguous rows and confirms the quantity operation (set supplier's on-hand value versus receive/add a delta).
5. Apply only after a second explicit confirmation. Cancel at any earlier point discards the staged batch and has no stock side effects. During writes, cancellation should request rollback; after commit, say it completed and offer an audited reversal workflow rather than pretending to cancel.

Use an import ledger keyed at least by supplier identity plus a digest of the exact source bytes; record profile version, selected actions, batch status and a committed marker. Check the ledger before review/apply and make an already-applied identical file a visible no-op/block. Commit the idempotency marker and all selected inventory updates in the same database transaction. Otherwise a crash between stock writes and remembering the import can make a retry duplicate them. If formats are often re-saved with different line endings/BOMs, a second normalized-content signature can raise a duplicate warning, but must not automatically block distinct revisions. The exact-once boundary is limited to the digest key and database transaction; file bytes plus a changed export can evade an exact-byte key.

The database is unspecified. First inspect its current ownership, write paths, constraints, and transaction/concurrency support with the product owner. Require inventory changes and the import ledger to be atomic in one supported transaction, and compare target row versions at apply so a long preview cannot overwrite a concurrent staff update unnoticed. SQLite provides a concrete example of all-or-none transactions, but has one concurrent writer and default DEFERRED behavior; these SQLite facts are conditional, not a claim about the target application. If the actual store cannot atomically commit both inventory changes and the idempotency record, do not enable writes until a recoverable idempotent design is approved. [SRC09](sources/index.md#src09) [SRC10](sources/index.md#src10)

For a batch that stops during apply, proposed default is: invalid/rejected rows remain outside the selected apply set; all valid rows staff chose to apply are one transaction; an error or process interruption before commit means rollback all selected stock changes and leave a retryable batch status; a successful commit means all selected rows and the applied marker are durable. Report counts of applied, unchanged, rejected, and invalid rows. This is recoverable without exposing unexplained half-applied inventory. Compare this with checkpointed per-chunk commits only if the real database cannot handle an 80k-row transaction: chunking gives faster restart but makes partial stock visible and needs per-row idempotency, durable checkpoints, resume/undo semantics and an explicit owner-approved definition of partial success. Benchmark before selecting; do not stream direct updates while previewing.

Supplier data and profiles stay on the user's machine: no uploads, remote parsing, or raw supplier values in telemetry. Decide retention for staged rows, exact-file copies, fingerprints, backups and local logs. Keep staging local and remove it on cancel/expiry under a disclosed retention policy; preserve enough state locally for a deliberate crash-recovery decision.

CSV input is text and the importer must not send it through a formula evaluator. Display formula-looking values as escaped inert text. If a future feature exports raw supplier text to CSV for spreadsheet viewing, treat that as a separate security boundary: OWASP notes spreadsheet apps may execute formula-leading cells, and mitigations can alter cell data or vary by app. Do not create an unreviewed raw CSV export. [SRC11](sources/index.md#src11)

## Decisions the product owner must make

- Which suppliers and file dialects are in the first release; header-row policy, delimiter/quote options, encodings, and whether true XLSX is out of scope.
- Which fields are required, which inventory fields a supplier may update, what “quantity” means (set-on-hand versus add/receive), supported precision and negative values.
- Supplier-code namespace and normalization (case, spaces, leading zeros), stable internal identity, history/reactivation rules for discontinued products, and whether any other identifier is authoritative.
- Duplicate policy: identical source row, same code with differing values, duplicate headers after normalization, duplicate current stock entries, and what row-level overrides are allowed.
- Decimal/group separator syntax and how to interpret ambiguous values; which encoding choices may be offered.
- What a changed mapping profile/header should do, and how long staff retain local raw staging and decision history.
- Whether the existing database can atomically apply up to 80,000 selected changes with the import ledger, how concurrent edits are detected, and whether product writes are available offline while supplier data remains local.
- Acceptable load-time/memory limits for an 80,000-row file; define thresholds before performance validation.
- If any subset commit is allowed, what the user-facing meaning of partial success/retry/undo is.

## Validation plan (proposed, not run)

1. Unit fixtures: comma, semicolon and tab delimiters; quoted delimiters and embedded newlines; BOM/UTF-8/strict alternate encoding; CRLF and LF; duplicate normalized headers; reordered/added/missing headers; short/long rows; empty fields; leading-zero and alphanumeric codes; numbers in each approved locale; ambiguous `1,234`; invalid scale; exact duplicates/conflicts; reused discontinued code; formula-like strings; unmapped note-like field.
2. Mapping tests: save a profile, reload identical structure and verify same positional mapping; change one header/order and require visible drift and confirmation; unknown columns remain ignored; no operation auto-maps into notes.
3. Identity tests: supplier A and B using the same code remain distinct; exact alias resolves one active item; discontinued/reused code requires a decision; fuzzy candidates never apply automatically; duplicate rows all retain their source location.
4. Read-only preview and cancel tests: capture pre/post stock snapshots and assert no change after cancel, parse failure, closing the window, or modified profile. Confirm no network traffic or remote file transfer in the product's environment.
5. Idempotency and recovery tests on an isolated copy/synthetic database: identical bytes and supplier after successful import are blocked/no-op even after restart; simulated failure before first write, mid-apply, at commit, and immediately after commit produces either no changes or one committed batch; retry cannot add twice. Test changed bytes separately and do not conflate with exact-file dedupe.
6. Concurrency tests: edit a stock record after preview; apply must flag conflict/re-review rather than overwrite. Test lock/busy timeout and disk-full/interruption handling for the actual database.
7. Performance test with generated synthetic 80,000-row files at realistic/worst-case field widths. Measure parse, staging, matching, preview render, and apply time/peak memory on target machines against owner-set limits.
8. Pilot rollout: first read-only previews, then one supplier/limited staff behind a disabled-by-default write gate, then broader rollout after audit of row counts, cancel behavior, repeat import, crash recovery, notes preservation and local-only data handling.

No code, production database, actual supplier file, or validation fixture was executed in this discovery. The tests above are proposals only. The exact plan is withheld until the prescribed release step.
