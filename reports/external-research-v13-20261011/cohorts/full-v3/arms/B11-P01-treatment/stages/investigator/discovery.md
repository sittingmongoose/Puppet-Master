# Investigator discovery — brief-only, pre-plan

**Stage:** B11-P01-treatment / investigator  
**Discovery is frozen before exact-plan release.** The brief describes linked references to external local files. No plan was available or consulted while writing this document.

## Scope and independent account

The record should have its own stable project-level ID and metadata; a file path is only a locator that can change. A practical initial design is to retain a user-readable original location, a path anchor (project-relative, configured base-relative, or machine-local absolute), and optional platform identity/access hints. Record states should distinguish reachable, missing, volume unavailable, permission denied, ambiguous candidate, and user-relinked. Missing references remain visible. Creating a link must be a deliberate choice distinct from importing/copying. Nothing in the brief authorizes moving, renaming, deleting, indexing, uploading, or silently copying the source.

A simple portable path model is most useful when the file and project move together: a path relative to the project root. A configured external base directory can also map the same relative subpath across computers. Absolute paths are honest machine-local locators but fail when roots change. Paths cannot by themselves identify content or distinguish a moved target from a same-named replacement. File IDs and bookmarks are useful corroborating or access hints, not a single cross-platform identity contract.

## Findings by obligation

- **Record vs location.** Store a stable reference record separately from its current locator. Keep display label, original/last-known locator, active locator, created/last-verified times, reference ID, and optional identity observations distinct. The Zotero model keeps linked-file items separate from stored copies; its implementation stores linked and base-relative forms separately (S10-S11).
- **Project move, path portability.** Resolve a project-relative path against the current project root only when the target is beneath that root or the user deliberately uses a matching project layout. For external trees, allow a user-configured base-root mapping and store the relative suffix plus the local root mapping. Otherwise keep an absolute local path and mark it machine-specific. File URIs cover several incompatible root forms and should not be treated as a universal path key (S09-S10).
- **File identity.** macOS resource IDs identify same-filesystem objects for comparison but are documented as nonpersistent across restarts (S03). Windows FILE_ID_INFO combines volume serial and a 128-bit file ID for equality of open handles on one computer (S04). Linux pairs device and inode, with inode uniqueness only within one filesystem (S06). These observations can strengthen a live check; none establishes a stable project ID across copies, filesystems, machines, or all restarts.
- **Permission and stronger platform mechanisms.** Sandboxed macOS can preserve user-granted access with security-scoped bookmarks; document-relative bookmarks can live in the project. Stale bookmark data must be replaced; inaccessible or unmountable targets fail resolution and can still expose last-known path (S01-S02). Linux XDG Documents uses persistent portal entries and permissions for sandbox access, with portal IDs under a per-user document mount; this grants access but does not solve cross-system identity (S07-S08).
- **Windows recovery alternative.** Distributed Link Tracking can locate some renamed/moved NTFS targets, but it depends on system services, file-system and domain/time conditions; tracking is lost on FAT and does not cover removable media. It is unsuitable as the required project-wide mechanism (S05).
- **Candidate replacement and control.** Search only the exact stored path first, then a user-authorized root/base or explicit folder selection. Within that bounded area, present candidate name/path/size/modified time and, if already available or explicitly requested, a content digest. A matching filename or digest is evidence, not authority to rebind: content equality is not same-file identity, and user intent decides whether changed content is acceptable. Show one candidate or an ambiguity list and commit the new locator only after a clear user confirmation. Zotero's shipped behavior searches within a configured base, uses part of the old path, and offers relink (including group relink); its release history records a macOS/Linux-to-Windows regression fix (S12-S13).
- **Removable media and failure states.** Do not equate “not reachable now” with deleted. Retain the reference when a volume is absent; offer retry and manual relink when it returns. Distinguish not found from denied access and from unavailable mount/volume where platform APIs permit it (S01-S02, S04-S08).
- **Two editor windows.** Route all reference mutations through the project persistence boundary. Use transactions plus a reference/project revision check; merge disjoint record edits and show a conflict for concurrent edits to the same reference, instead of accepting a stale window write. If SQLite is selected, it serializes writers while permitting simultaneous readers; this does not by itself decide merge policy (S14).
- **Move/export.** A project manifest can carry references and explain that external targets are not packaged. Default export copies no linked source. Offer a separate explicit “include files” operation with a visible list and outcome report if product owners want that mode. A portable relative locator is not proof that the target was included.

## Provisional direction and open facts

Prefer a small attachment-reference component behind the notebook's existing project storage: chooser/drag-drop “link existing file” action; pure locator resolver; platform access adapters; bounded candidate picker; revision-safe reference writes; and export disclosure. Do not create a general file manager, background whole-disk index, sync service, or recovery guarantee. The default core is project-relative paths where appropriate plus configured per-machine base mappings and explicit machine-local absolute paths elsewhere; macOS bookmarks and Linux portal grants supplement access where sandboxing requires them. Treat Windows IDs, Linux inode pairs, and macOS resource IDs as observations. Keep content hashing opt-in and separate from identity.

Still unresolved from this brief: actual target OS/version matrix, sandbox/package distribution model, project file/storage format, whether multiple processes as well as two windows can edit, project export/import contract, whether referenced files may be outside the project tree, required network-share behavior, preview metadata/privacy policy, and whether reference updates synchronize across devices. Do not assume these choices are settled by the research.
