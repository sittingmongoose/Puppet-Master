## Recommendation

Keep the plan's project-local reference table, stable record IDs, path-first open attempt, local-only scope, and exportable readable reference list. Change the table from a single absolute path plus mandatory first-link digest into an explicit locator model with optional observations. Use project-relative paths for files that move with the project, configured local root mappings for shared external layouts, and a clearly machine-local absolute fallback. Retain the previous/last-known path when resolution fails.

A missing locator should never trigger a silent replacement. Search only the project root and roots the user explicitly configured or selected, and only as a bounded recovery action. Use path history, file name, size, modified time, and an optional content digest to rank candidates. Show the candidates and ask the user to relink. A content digest says that bytes match; it does not prove that a candidate is the same file or the one the user intends. “Newest” is not a safe tie-breaker.

Keep file-system notifications as a short-lived refresh hint, if implemented. Events can be coalesced or dropped; watching directory roots can miss changes or require a rescan. A notification may update status or offer a repair action, but it should not silently rewrite the durable locator. Use a revision-aware persistence boundary shared by both windows, rather than letting each window replace a whole stale in-memory table. Make export state explicit: linked files are not included unless the user chooses an include-files operation and sees what will be copied.

This preserves understandable failure states and deliberate relinking without requiring a whole-disk index, privileged service, cloud account, or automatic upload. Platform APIs improve access and local matching in particular environments; they do not remove the need for the portable locator and user-confirmed recovery flow.

## Plan elements already covered, rejected, and uncertain

- **Already covered and retained:** project-local table; stable record IDs; try the exact stored path first; visible missing state and Browse action; export the table and a readable list; local-only behavior; no privileged service and no silent copying. These remain subject to the stronger status and export wording above.
- **Rejected or corrected:** absolute path as the only durable locator; mandatory first-link digest as identity; automatically selecting the newest size+digest match; current mount path as removable-volume identity; watcher-driven silent durable path rewrites; whole-table replacement from each window's stale in-memory copy; the assumption that one filesystem identity and path rule behaves alike on all OSes.
- **Uncertain and left to owners:** OS/version and sandbox matrix; project storage and process model; external-root mapping; network shares; whether and how to package optional digests or native access tokens; export-copy support; whether changed file contents count as an acceptable relink. The owner questions below make these concrete.

## Component proposal and boundaries

**Reference record.** Keep the reference record in the project-owned persistence model with a stable UUID. Suggested fields: record ID; display label; link mode; locator kind; anchor/root ID; relative suffix or native absolute path; last-known display path; optional opaque native access data by platform; optional file/volume identity observations; optional size, modified time, and digest with algorithm and observation time; status/last checked; record revision. Store observed file metadata and supported OS identity values with provenance/time, not as a replacement for the locator. On macOS, consider persisting documentIdentifier plus volumeUUIDString when available so a candidate can be corroborated across same-volume moves and restarts; these values do not locate the path, and support must be verified for the OS/volume matrix (S18-S20). Keep OS-native path data lossless; do not normalize path spelling across operating systems. A file URI is an interchange syntax for multiple root forms, not an identity (S09).

**Attach flow.** Offer separate actions for “Link existing file” and any managed/imported copy. Obtain the chosen item through the platform file chooser or drag/drop. Ask before creating a persistent reference if the user gesture is ambiguous. Save the record without copying bytes. For sandboxed platforms, capture the OS permission mechanism the user granted. On macOS, a document-relative bookmark is a plausible project-scoped option; refreshed stale bookmark data must replace the old token. On Linux, use the selected file URI and persistent portal grant where deployment requires it; the portal entry can be revoked and does not identify the file across machines (S01-S02, S07-S08).

**Open and status flow.** Resolve the stored locator, acquire its access grant, inspect current item metadata and any supported object identifier, and then open through the application boundary. If the root is offline, preserve a “volume unavailable” status and retry when it returns. If access is denied, explain the denial and offer the chooser again. If missing, retain the record and offer bounded recovery. An identity hint should only corroborate that the current open target is the same filesystem object within that API's documented scope; never assume it crosses copies, filesystems, machines, or restart boundaries where the API does not promise that (S01-S08).

**Relink flow.** Search the current project directory and user-approved roots only after a user requests repair. Rank without silently accepting. Candidate detail should include path, filename, type, size, modified time, and any supported identity/content comparison, plus a reason it was suggested. If more than one candidate remains plausible, show all candidates. The user confirms the new target. Persist the new locator and updated observations in one revision-checked change; keep the previous locator in limited history for undo or audit. Do not change the source file. Zotero's documented and shipped linked-file behavior shows one useful pattern: a configured base directory, path-aware candidate search, a user-facing relink offer, and later correction of a cross-platform path bug (S10-S13).

**Project move and export.** When a linked item is inside the project tree, a project-relative locator survives moving the whole tree with that file. For external files, a machine-specific absolute path is honest but will often fail on another machine; an owner-configured external-root mapping can make the relative suffix portable for matching layouts. A removable volume can carry a volume-relative locator and local volume hints, but volume identity is not uniform across systems, and the volume can be absent. A project export must state that links do not package originals. Optional copy-on-export is a distinct, previewed operation; report each reference as copied, missing, denied, or omitted.

**Integration boundaries.** Keep this component limited to: attach/link entry point; reference record persistence; path and grant resolver; bounded candidate discovery; missing/permission/volume status; explicit relink; open action; project export disclosure. Do not add general-purpose browsing, bulk filesystem management, global indexing, source mutation, sync, or a recovery guarantee. Use existing notebook project storage and UI routing once those contracts are known.

## Alternatives and trade-offs

| Approach | Benefit | Limitation | Recommendation |
|---|---|---|---|
| Project-relative path | Portable when project and target move together; simple and inspectable. | Does not help an outside file or a target moved separately. | Core locator for in-project targets. |
| Configured base-root plus relative suffix | Supports teams/users with the same attachment tree under different local roots; bounded discovery. | Requires matching layout and local configuration; wrong mapping can point elsewhere. | Support as an explicit option. |
| Absolute local path | Minimal schema and efficient exact open. | Brittle under project/user/drive changes; machine-specific. | Keep as fallback and last-known location, labeled local. |
| OS bookmarks/file IDs/portal grants | Can preserve access or corroborate current object on a platform. | Different APIs and scope; stale, revocable, volume/filesystem/restart constraints; poor export portability. macOS documentIdentifier plus persistent volume UUID can follow same-volume moves/restarts when supported, but does not itself locate a file (S01-S08, S18-S20). | Adapter layer; never the only cross-platform record. |
| Windows Distributed Link Tracking | Can follow some moved NTFS files and uses IDs/heuristics. | NTFS-specific; dependent on system services; not reliable for removable media or FAT; may be slow (S05). | Do not require; at most an optional Windows hint. |
| Content digest | Compares bytes and helps rank candidates. | May be costly; can become stale; identical copies match; content identity is not file identity. | Optional evidence only; never auto-relink on it. |
| Managed copy/import | Self-contained project/export and less locator failure. | Duplicates bytes and changes ownership/storage semantics. | Separate explicit feature only if an owner asks; never the default link action. |

## Owner decisions still needed

1. Supported OS versions, app packaging/sandbox entitlements, availability of macOS documentIdentifierKey/volumeUUIDStringKey on the minimum supported system and target filesystems, and whether the product needs a portable project across OS families.
2. Whether references can target outside the project tree, and how external base roots are named, configured, and exported.
3. Project storage format and whether multiple independent processes or only windows in one process can edit the same project.
4. Whether linked files may be on network filesystems; the Linux watcher documentation says remote network filesystem changes are not reported by inotify (S17).
5. Whether to store platform access tokens in the project or local user state, and whether export includes them.
6. Whether content digest is useful enough to justify first-link I/O, and whether it should be opt-in, deferred, or omitted.
7. Whether copy-on-export is supported and how the UI distinguishes inclusion of files from inclusion of reference records.
8. Whether removal is soft deletion/history or permanent record removal. Source files remain untouched either way.

## Validation plan (proposed, not run)

- Relocate a whole project tree with linked files; verify project-relative links resolve and external absolute links show machine-local/missing state without changing records.
- Rename and move a target within an approved base; move it outside the base; copy it to a second location; verify only explicit user relink updates the locator.
- Test same-name and same-size duplicates, byte-identical copies, changed content, and a newer duplicate; verify no candidate is accepted automatically and the UI explains ranking.
- Disconnect/reconnect removable storage, change mount point or drive letter, and simulate a reused mount path that now contains another volume; verify no accidental open or relink. On macOS, separately check documentIdentifier plus persistent volume UUID across same-volume moves/restart, copies, and a volume without the property.
- Revoke permissions, make a target unreadable, use a stale bookmark, and use a sandbox portal file grant; verify each error maps to a recoverable status and no original is copied.
- Exercise path names with spaces, Unicode, reserved characters, case differences, symlinks, UNC/network paths, and both relative and absolute locators on every supported OS.
- Verify watchers are optional and disposable: trigger rename, cross-directory move, volume unmount, dropped/overflow events, and network-side change; ensure reconciliation rescans and does not silently rewrite a locator.
- Open the same project in two editor windows. Edit different records and the same record; confirm disjoint changes survive, stale same-record edits surface conflict, and restart/crash during save leaves a readable current table.
- Export with links only and with explicit file inclusion; inspect manifest/list wording and per-file results. Confirm source file bytes and names remain unchanged unless the user explicitly requested a copy.
- Benchmark optional digest creation on representative large files and test a file changing during digest computation; keep digest status unknown/failed rather than claiming a stable value.
