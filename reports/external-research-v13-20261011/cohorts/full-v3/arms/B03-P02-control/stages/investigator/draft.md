## Findings, alternatives, and decision record

### Supported findings and conditions

- **Snapshot:** SQLite WAL read transactions and backup API can provide database-specific point-in-time behavior; PostgreSQL 18 Repeatable Read provides a stable transaction snapshot. These are conditional examples, not target facts. Neither proves consistency for external attachment bytes. [S01](sources/index.md#s01) [S02](sources/index.md#s02) [S03](sources/index.md#s03)
- **Reference implementation:** GitLab 19.2's pinned code has a relationship/attribute allowlist, a current-user-aware writer, per-relation batches of 100, and line-delimited relation output. Its serializer logs and skips a failed batch, a behavior that this proposal should explicitly avoid or surface as an omission/failure. The service checks permissions and coordinates structured data, uploads, repositories and archive generation. Tests express permission and field expectations, but were not run. [S09](sources/index.md#s09) [S10](sources/index.md#s10) [S11](sources/index.md#s11) [S12](sources/index.md#s12) [S14](sources/index.md#s14) [S15](sources/index.md#s15) [S16](sources/index.md#s16) [S17](sources/index.md#s17)
- **Format:** ZIP APPNOTE 6.3.10 permits data descriptors for streaming and defines ZIP64/central-directory finalization. GNU tar 1.35 documents sequential archives and PAX's greater size/name flexibility with reader-compatibility caveats. These support alternatives; neither selects the product's default. [S06](sources/index.md#s06) [S07](sources/index.md#s07)
- **Omissions and operations:** GitLab warns that its exports are not full backups and are version-dependent; its current docs list links that are not exported. A self-managed 16.5.3 issue reports a stalled ~6 GB export and missing upload-completion log, but the examined report does not establish a root cause or current fix. GitLab's 2023 direct-transfer history discusses relation batching to reduce timeouts; a 2022 MR proposed staged partials before combination but said the service was not yet used. Treat these as failure/design evidence, not target behavior. [S08](sources/index.md#s08) [S20](sources/index.md#s20) [S21](sources/index.md#s21) [S22](sources/index.md#s22)
- **Integrity and security:** SHA-256 detects changes with high probability but does not authenticate an archive whose manifest can also be edited. Future extraction must defend against traversal, symlinks and expanded-size exhaustion. [S18](sources/index.md#s18) [S19](sources/index.md#s19)

### Alternatives retained

| Approach | Benefits | Costs / conditions |
|---|---|---|
| Directory/folder bundle | Directly browsable; simple per-file verification; no packaging spool. | Many filesystem entries, destination still needs space, copy may be less convenient; completion manifest needs atomic finalization. |
| Direct ZIP64 stream | Single portable artifact; ZIP data descriptors allow sequential entry writes; avoids duplicate attachment staging. | ZIP64 support must be confirmed in supported readers; final directory is written at close; partial files need clear status and a finalized-package verification. |
| PAX tar stream, optionally compressed | Sequential output; suitable for very large blobs and long names with PAX. | User-facing reader support varies; compressed stream must finalize and inspect may require full scan. |
| Stage then package | Straightforward to inspect/retry all component files before assembly. | Highest scratch-space pressure and duplicate-byte risk; only suitable when there is an explicit staging capacity guarantee. |
| One giant JSON/CSV or base64 files | Familiar to some tools or convenient for narrow tabular reporting. | Poor for large collections, nested comments/custom types, binary attachments and bounded-memory writing; retain only as optional secondary report if separately requested. |

### Owner questions left open

1. Which source database and blob store back the tracker, and what supported snapshot/version pin guarantees a coherent task-comment-custom-field-attachment view at 50,000 tasks?
2. Is a long-lived DB snapshot acceptable, or is an immutable export snapshot/token required? What should the exporter do when that cannot be acquired?
3. Should the default output be one ZIP64 file, a PAX archive, or a folder bundle? Which desktop OS/archive readers and destination types are supported?
4. Which reference fields may be preserved when a task links to an inaccessible project, without disclosing hidden identity/content?
5. Should missing/changed attachment bytes produce a failed export or a successful archive with declared omissions? Define terminal status words and user messaging.
6. For any source dates without a zone, is there domain metadata that identifies their semantics? If not, retain the raw value as unknown-zone.
7. For a later importer, which mapped fields are authoritative and what are the conflict, duplicate and identity-mapping policies? Permission/ACL recreation stays out of scope until explicitly specified.
