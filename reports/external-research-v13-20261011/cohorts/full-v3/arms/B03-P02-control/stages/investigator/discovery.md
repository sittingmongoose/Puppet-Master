No target application repository was supplied; GitLab 19.2 is a first-party reference implementation, not the target product. No tests or downloaded code were executed.

## Contract and data model

The output should be a readable bundle with a small human-oriented `README.txt`, an explicit `manifest.json`, structured UTF-8 records (`tasks.ndjson`, `comments.ndjson`, `custom_fields.ndjson`), a binary `attachments/` area, and explicit omissions. The manifest should identify format/schema version separately from producer version; export/snapshot time; source project namespace; per-entity counts/bytes; included, excluded, and omitted relations; terminal status; and length plus SHA-256 for each data/blob member. A digest detects changes; it does not authenticate a producer.

Represent IDs as strings scoped by source instance/project and entity type, preserving immutable source IDs (or native UUIDs) across edits and repeated exports. Never derive identity from task titles or attachment names. Comments must retain their parent task reference, author attribution as permitted, and timestamp semantics. Retain custom-field definitions with type/choice metadata and each value; preserve unknown fields/types as typed raw data where safe instead of silently coercing or dropping them. Define missing versus null and whether field order matters. JSON interoperability calls for UTF-8 and unique member names; NDJSON is a useful line-stream convention, not a schema standard. [S04](sources/index.md#s04) [S09](sources/index.md#s09) [S14](sources/index.md#s14)

Use RFC 3339 with explicit offset/UTC marker for a value that is truly an instant. Preserve date-only values as dates, and named timezone separately when the field means a local schedule. A legacy timestamp with no timezone remains unqualified/unknown; do not assume UTC or transform it into a different instant. [S05](sources/index.md#s05)

## Snapshot, permissions, and omissions

Read all exported project records from one declared database snapshot, including relation membership and custom-field definitions. A sequence of paged queries or a timestamp cutoff alone does not guarantee that concurrent edits/deletes yield one coherent view. Use the target DB's supported snapshot/repeatable-read mechanism (SQLite WAL read snapshot/backup API if applicable; PostgreSQL 18 Repeatable Read if applicable), while considering long-snapshot resource costs. Database isolation does not snapshot external attachment storage: capture immutable blob/version IDs or pin object versions when the DB snapshot is taken; hash/length-check bytes while reading. If no stable byte version exists, compare observed metadata and abort or record a declared omission if it changed. [S01](sources/index.md#s01) [S02](sources/index.md#s02) [S03](sources/index.md#s03)

Do not read inaccessible linked projects. For a task link whose pointer is already visible, export only the permitted pointer and an omission record such as `target_project_inaccessible`; do not fetch target names, tasks, comments, fields, attachments, or ACLs. Similarly, an attachment record with missing/forbidden bytes must say so; never make substitute bytes. Permission tests should verify absent content, not just UI visibility. Make the owner choose whether such a declared omission yields `complete_with_declared_omissions` or makes the job fail; either way, it cannot be labeled complete-without-omissions. GitLab's current docs warn its project file export is not a full backup and omit some links; its tests show inaccessible relations are filtered. [S08](sources/index.md#s08) [S17](sources/index.md#s17)

## Packaging and bounded writes

- **Stage then package:** easy to inspect and verify as a tree, but may need a second full copy of all attachments. Do not require staging equal to export size.
- **Folder bundle:** write members directly to the chosen destination. It is human-readable and uses no packaging spool, but creates many filesystem entries and needs an atomic completion convention: flush members, write a temp manifest, then rename it to the final manifest where supported.
- **ZIP64 package:** familiar single artifact and suitable for direct sequential writes. ZIP data descriptors support streaming without known sizes; central directory/end records appear only at close, and ZIP64 handles counts/sizes/offsets beyond classic fields. Write to destination-side `.partial`, stream each attachment once while counting/hashing, close, reopen/verify, then rename to final on the same filesystem. No full attachment staging copy. A non-seekable sink cannot use rename, so needs a final completion record/trailer and consumer contract. [S06](sources/index.md#s06)
- **PAX tar stream, optionally compressed:** sequential and handles large files/long names with the right format, but reader compatibility/familiarity varies; compressed output must also finalize. [S07](sources/index.md#s07)

**Provisional choice:** define one logical contract independent of container; use a direct streaming writer by default and a selected destination (streaming removes duplicate scratch, but cannot remove the need for capacity at the final destination). Prefer ZIP64 for a single-file output only if the supported desktop reader matrix accepts ZIP64; retain folder output as an alternative if file-manager inspection is the priority. Decide expected platforms/destination behavior with the product owner. Staging every attachment before packaging is a rejected default because it doubles space pressure. CSV is useful for tabular analysis but not the canonical archive: it cannot naturally preserve typed custom data, nested comments/relations, binary files, or explicit schema behavior. One monolithic JSON with base64 attachments is also a poor default because it prevents bounded record streaming and inflates binaries.

## Completion, verification, fidelity, future import

Use terminal status values such as `complete`, `complete_with_declared_omissions`, `cancelled`, and `failed`. A complete result means every selected accessible row/blob was read at the declared snapshot; output entries are closed; record/byte counts reconcile; line records parse; references resolve or have omission entries; hashes/lengths match; and the archive end/manifest is present. Do not publish a completion marker until verification succeeds. Cancellation, disk full, process termination or failed verification leaves a conspicuous incomplete partial and does not mutate source records/files. Show per-stage progress and errors. Prefer validating the package in place; a future importer that extracts needs quarantined paths, traversal/symlink rejection, entry/expanded-size limits, and protection against archive bombs. [S18](sources/index.md#s18) [S19](sources/index.md#s19)

A round-trip fidelity table should classify each field/relation as retained exactly, normalized, omitted, unsupported, or external reference only. A bounded future importer could support a single project plus the defined task/comment/custom-field/attachment schema, map source identifiers, prevent duplicate imports, and produce a dry-run conflict report. Leave cross-project creation, live sync/deletion semantics, account/identity remapping, access-control recreation, automation, and fabricated missing data outside the first importer. Do not claim round-trip fidelity until those field-level outcomes and import conflict behavior are tested.

## Repository/code, tests, and history evidence

GitLab 19.2's pinned project allowlist explicitly enumerates relationships and included attributes [S09]. The call path authorizes the export, runs separate data/blob savers, saves the archive, reports errors and cleans work paths [S12]; a task caller provides path checks and invokes that service [S13]. Its TreeSaver passes the current user and writer [S10]. The serializer batches 100 rows, applies configured ordering and access filters, but catches a relation-batch error, logs it, skips the batch and proceeds [S11]. This is a caution: batch failures must be fatal or explicit in the manifest, never silent under an unqualified complete status. The writer stores relation arrays line by line [S14]. Tests assert root/issue/comment/relation outputs and writer parsing, and EE tests assert restricted relations are omitted [S15] [S16] [S17]. These test files were inspected but not run.

A GitLab issue reports a ~6 GB export stuck in progress in a self-managed 16.5.3 deployment and no upload-completion log; its reported cause/status is unverified [S20]. A 2022 merged MR describes exporting relations to staged temporary objects and combining a tarball, but says its new service was not yet used at that time [S21]. GitLab's 2023 history says relation batching in 16.3 reduced timeouts and allowed parallelism [S22]. Those sources motivate bounded writes, stage progress, destination/storage failure handling and cardinality-aware scale tests, not a winning architecture. GitLab's 2025/18.0 repository-backup speed fix was an O(N²) Git reference-dedup problem, not project-task export; use it only as a reminder to benchmark actual data shapes [S23].

## Proposed validation (not executed)

1. **Snapshot race:** create/update/delete tasks, comments, custom definitions and attachment references during a 50k export; prove every output corresponds to the declared point-in-time view and every attachment matches its captured immutable version. Assert no source writes.
2. **Scale and storage:** compare 50 with 50,000 tasks, large comment sets and attachments, including a file larger than configured scratch. Measure peak memory and scratch use; assert constant/bounded memory and no second full-size staging copy. Separately report insufficient final-destination capacity.
3. **Failure/cancel:** cancel during metadata and a large blob; simulate disk full, short write, changed/missing blob, denied access, process death before archive close, and a verifier mismatch. Assert no final-complete artifact, clear terminal error/progress, unchanged source records/files.
4. **Serialization:** large/duplicate IDs, duplicate/path-like/Unicode filenames, newlines/quotes/Unicode comments, unknown/null/missing custom fields, date-only/offset/naive timestamps, deterministic order, and schema compatibility.
5. **Integrity/security:** parse every line, reconcile counts/refs/omissions, verify blob size/hash, corrupt/truncate members/manifest/end record, and prove verification does not execute/extract data. For any future extraction test traversal, symlinks and decompression limits.
6. **Permission/fidelity/import:** an inaccessible linked project must yield only permitted pointer/reason and no hidden content. For a future importer, test dry-run maps/conflicts, duplicate prevention, unknown required feature handling and the named field-by-field fidelity matrix.

All six are proposed checks; none were run.
