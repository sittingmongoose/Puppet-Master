## Proposal

Define the export contract independently from the archive container. It should produce (1) a small local README and navigable static index, (2) an explicit manifest and versioned structured task, comment, custom-field, and relation records, (3) binary attachment members, and (4) explicit omissions. Human-readable files and assets must open without the network or original application. A JSON record layout should use UTF-8 and unique object member names. Per-record NDJSON/JSON Lines is one useful streaming convention; RFC 8259 does not define it or require it. Compare it with a conventional JSON document/array and select the record layout after testing real reader and importer needs. A single huge document, CSV as the canonical format, and base64-embedded attachments are not good defaults for this size and data shape. [S04](sources/index.md#s04) [S14](sources/index.md#s14)

The manifest should separate archive-schema version from producer version and declare the export/snapshot identity and time, project/source namespace, counts and byte totals, included/excluded/omitted entity and relation classes, final status, and per-member length and SHA-256. Hashes can detect later byte changes; a hash in an editable manifest does not authenticate the archive or producer. Keep the schema explicit about required and optional fields, unknown values, duplicate object keys, null versus absent, ordering, and schema-evolution behavior. [S04](sources/index.md#s04) [S18](sources/index.md#s18)

### Identity, text, dates, and custom fields

Preserve immutable source IDs (or native UUIDs) as strings with a namespace containing source instance, project, and entity type. Do not infer identity from a title, filename, byte hash, or display text. Preserve each attachment's source ID separately from its package path so two distinct attachments with identical bytes remain distinct records. A later importer can map this namespaced identity, but no import or general round-trip guarantee is made here. [S09](sources/index.md#s09)

For JSON text, use UTF-8 and reject duplicate object member names in the producer/verifier contract. Preserve source text without undocumented normalization. Represent a true instant with an explicit RFC 3339 offset or UTC marker; RFC 3339's `-00:00` means the local offset is unknown and is not the same statement as `Z` or `+00:00`. Keep date-only values as dates, and preserve a named timezone separately where a value means a local schedule. If the source has an unqualified time and supplies no semantics, retain the raw value with its zone/meaning unknown; do not invent UTC or convert it. Custom-field definitions and values should retain type, choices/configuration, and original value where safe, while distinguishing null from absent and documenting unknown, unsupported, and sensitive values. [S04](sources/index.md#s04) [S05](sources/index.md#s05)

### Snapshot, access, and omissions

Read task rows, comments, links, custom-field definitions/values, and their membership from one declared database snapshot or an equivalent immutable, versioned export snapshot. A revision marker plus identifier ordering, a timestamp cutoff, or independent page reads does not by itself make those records one coherent view. If the actual source is SQLite, its WAL read-transaction snapshot or a completed Online Backup API copy are conditional SQLite mechanisms; journal mode and transaction boundaries matter. If the actual source is PostgreSQL 18, Repeatable Read provides that database's stable transaction snapshot. These examples cannot select the target mechanism, and neither database snapshot pins bytes held in an external blob store. Discover the target database/blob-store guarantees before claiming point-in-time consistency. If a coherent snapshot cannot be acquired or maintained, fail/retry or explicitly weaken the promise; do not label independently changing reads as a point-in-time export. [S01](sources/index.md#s01) [S02](sources/index.md#s02) [S03](sources/index.md#s03)

At snapshot start, capture immutable attachment blob/version IDs or pin object versions. Stream and hash the captured versions while reading. If the source has no stable version mechanism, compare the available metadata and either fail the export or record a product-approved omission for changed/missing bytes. The brief forbids fabricated bytes. The target's long-transaction cost, snapshot API, and changed/missing-byte policy are owner/engineering decisions.

Apply the exporting user's permissions to every exported record and relation. Do not fetch an inaccessible linked project's name, tasks, comments, fields, attachments, or ACLs. A visible task link may be represented only by a pointer already available to that exporter plus an omission reason such as `target_project_inaccessible`, after the product owner approves an allowlist of safe pointer fields. Add content-level tests showing no hidden fields or bytes appear; UI filtering alone does not establish this. For missing or forbidden attachment bytes, retain the attachment record and a safe parent reference with a stable omission reason, but no placeholder file. [S08](sources/index.md#s08) [S09](sources/index.md#s09) [S17](sources/index.md#s17)

### Attachment paths, packaging, and disk limits

Treat source filenames and media types as untrusted metadata. Preserve the original display name as metadata, and use opaque, unique archive member paths keyed by stable attachment identity (or another collision-free generated identity). Do not require content-addressed paths: identical bytes can belong to separate attachments, and the cited extraction-security guidance does not mandate an exporter naming scheme. Record source attachment ID, safe display name, declared media type, size, and a streaming SHA-256. Hashes are change-detection data, not signatures. [S18](sources/index.md#s18) [S19](sources/index.md#s19)

There is no selected container. Keep the logical record contract portable across:

| Option | Advantages | Costs and conditions |
|---|---|---|
| Folder bundle | Directly browsable, easy per-file inspection, and no packaging spool. | Many filesystem entries; the final destination still needs the full output; publish a completion manifest last or atomically publish a completed sibling directory. |
| Direct ZIP64 stream | Familiar single-file artifact; ZIP data descriptors support sequential member writes; avoids an attachment-sized staging duplicate. | Confirm supported readers accept ZIP64. ZIP directory/end records appear at close, and central-directory metadata grows with member count. Close, reopen, and verify before publishing; keep failures under an unmistakable partial name. [S06](sources/index.md#s06) |
| PAX tar stream, optionally compressed | Sequential alternative for large files and long names. | Reader compatibility varies; the current reviewer and critic could not retrieve the GNU tar manual at the listed URL, so its carried format notes remain less independently verified than the ZIP facts. Confirm the exact tool/readers before choosing. [S07](sources/index.md#s07) |
| Stage then package | Components can be inspected or retried before final assembly. | Can require a second full-size copy and the most scratch space. Retain only with an explicit staging-capacity guarantee or a demonstrated need. [S21](sources/index.md#s21) |

A streaming writer is an implementation strategy, not a container choice. Prefer writing members directly to a destination-side partial artifact when the chosen format permits; this avoids a second attachment-sized spool but cannot remove the need for free space on the final destination. Preflight against the selected destination using source byte metadata plus serialization/container overhead, then monitor actual writes because compression and concurrent disk use make the estimate imperfect. Report insufficient final-destination capacity clearly. A bundle on a non-seekable sink cannot rely on rename: define a consumer-visible terminal record/trailer. In folder mode use a final manifest/marker or a completed-directory publication protocol. In every mode, consumers must treat output as incomplete until its mode-specific completion record is present. [S06](sources/index.md#s06) [S07](sources/index.md#s07)

### Completion, cancellation, and fidelity

Use explicit terminal statuses such as `complete`, `complete_with_declared_omissions`, `cancelled`, and `failed`. The owner must decide whether missing/changed bytes are a failed export or a declared-omissions result. A declared-omissions archive must never be labeled complete-without-omissions.

Only publish completion after every selected accessible row/blob has been read at the declared snapshot; records and references reconcile; omissions are explicit; data members are closed; counts, lengths, hashes and structured records verify; and the selected container has finalized. For ZIP, close to write the central directory/end records, then reopen and verify before publishing by same-filesystem rename where supported. For a folder, write into a temporary sibling and rename after verification where supported, or make the verified completion manifest the last, consumer-recognized commit record. For a stream, require a terminal completion record and define how consumers reject a missing/truncated trailer. On cancellation, disk-full, read/write error, process termination, snapshot failure, or verifier mismatch, leave a conspicuous partial/failed result and no valid completion marker. Report progress and stage-specific errors. All paths must be read-only with respect to source rows, links, metadata, and blobs. [S06](sources/index.md#s06) [S18](sources/index.md#s18)

Publish a per-field and per-relation fidelity table classifying each value as retained exactly, normalized, omitted, unsupported, or external-reference-only. Do not claim round-trip fidelity until that table and importer conflict behavior are exercised. A bounded future importer could support one project and the declared task/comment/custom-field/attachment schema, map namespaced IDs, avoid duplicates, and offer a dry-run conflict report. Keep cross-project creation, live synchronization/deletion, identity/account remapping, access-control recreation, and automation out of scope until separately specified. Verify archives in place when possible. If a future importer extracts them, quarantine the destination, reject traversal and unsafe symlinks, and bound entries, depth, and expanded bytes; treat paths, manifest, sizes, media types, schema versions, and custom values as untrusted. Unknown required schema features must fail visibly. [S09](sources/index.md#s09) [S19](sources/index.md#s19)

## Research evidence and limits

No target application repository was supplied. GitLab 19.2 at commit `fc45538465514c4777fc196641900b63470c6236` is a first-party reference implementation only: its export schema explicitly selects associations/attributes; caller and saver layers perform authorization/path checks and coordinate outputs; its serializer uses configured ordering and batches relations by 100; its NDJSON writer emits relation values line by line; and tests assert selected relation/permission outcomes. The serializer also logs and skips a failed relation batch. This is a caution, not a behavior to copy: every required batch must be retried, failed, or explicitly represented so a partial archive cannot appear complete. These repository tests were inspected in predecessor stages but were not run here. ## Decisions still needed from the product owner or engineering

1. Which database and blob/object store back the target tracker, and what supported mechanism provides one coherent task/comment/link/custom-field snapshot plus stable attachment bytes at 50,000 tasks?
2. Is a long-lived snapshot acceptable? If not, can the system create an immutable export snapshot/token? What should happen if neither can be obtained?
3. Which output containers, operating systems, archive readers, and destination types must be supported? Choose folder, ZIP64, or PAX only after a compatibility and capacity review.
4. Which visible external-link fields are safe to preserve when the linked project is inaccessible?
5. Should missing or changed attachment bytes fail the export or yield a successful archive with declared omissions? Define status names, UI wording, and retry behavior.
6. What do source date values mean when zone information is absent? If nothing establishes the meaning, preserve raw/unknown.
7. If an importer is later scoped, which mapped values are authoritative and what are identity, duplicate, conflict, permission, and unsupported-required-feature policies?

## Proposed validation plan — none of these checks were run

Before execution, define product-specific resource budgets and expected status transitions. The plan below proposes assertions; it does not report results.

1. **Snapshot race and version pinning:** export 50 and 50,000 tasks while tasks, comments, relations, custom definitions/values, and attachment references are concurrently inserted, changed, and deleted. Assert each record belongs to the declared snapshot. Mutate external blobs during reads and prove output bytes match the captured immutable versions or produce the selected explicit failure/omission.
2. **Source immutability:** record before/after source rows, relation membership, attachment/blob bytes, and relevant metadata/version IDs. Compare after successful export, cancellation at metadata/blob stages, low-space failure, read/write failure, and verifier failure. Assert the exporter has no source-side writes and no source changes.
3. **Permissions and omissions:** link to a project the exporter cannot access and deny selected attachment bytes. Inspect archive contents, not only the UI. Assert no hidden names, fields, tasks, comments, or blob bytes appear; every permitted pointer and omission reason matches the approved allowlist; no fabricated member exists.
4. **50-versus-50,000 scale and capacity:** use representative task/comment/field cardinalities and attachments, including one larger than configured scratch capacity. Measure final-destination space, temporary disk, throughput, record-batch memory, payload-buffer high-water, and per-member/container metadata. Set maximum buffer/batch budgets before testing. ZIP central-directory data has one record per entry, so total metadata grows with member count; measure that separately, cap members, or use a disk-backed index if necessary. Do not claim total memory is constant merely because blob bytes stream. Assert no second full-size attachment staging copy in the selected direct-stream mode, while separately demonstrating that the final destination has enough capacity.
5. **Cancellation and failure finalization:** cancel during metadata and a large blob; inject short writes, disk full, missing/changed blob, permission denial, process termination before archive close, and verification mismatch. For ZIP, folder, and non-seekable output, assert that only a verified result has a consumer-recognized completion marker. Every failure leaves a clearly partial/failed artifact, useful progress/error detail, unchanged source, and no success marker.
6. **Text, schema, IDs, and dates:** exercise duplicate and path-like IDs, Unicode and newline/quote text, duplicate/path-like/case-colliding filenames, null versus absent values, unknown field types, choice metadata, date-only values, offset timestamps, `-00:00`, naive timestamps, and named local schedules. Assert stable identities, valid UTF-8/JSON, unique keys, safe display metadata, and documented schema behavior.
7. **Integrity and safe verification:** parse every record, reconcile manifest counts/bytes/references/omissions, recompute member length/SHA-256, and test corruption/truncation of records, manifest, ZIP directory/end records, folder completion marker, and stream trailer. Prove verification does not execute or extract members. Distinguish a correct digest from archive authenticity.
8. **Offline and compatibility:** open README/index/data with networking disabled and without the original app. Test the chosen container against the product's supported OS/archive-reader matrix and destination types, including large ZIP64/member-count cases where applicable.
9. **Future-importer boundary:** only if a separate importer is later authorized, test dry-run identity mapping, duplicate prevention, conflicts, unknown required schema features, archive traversal/symlinks, path depth, entry-count and expanded-size limits, and quarantined extraction. Do not treat this proposal as authorization to build or run one.
