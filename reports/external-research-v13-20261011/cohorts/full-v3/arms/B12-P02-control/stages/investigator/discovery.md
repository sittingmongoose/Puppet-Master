# Independent discovery — cancelable local document-preview jobs

**Run/stage:** B12-P02-control / investigator  
**Scope source:** the released brief only. The exact plan had not been released or read when this discovery was written.  
**Research captured:** 2026-10-12 UTC. **Executable checks:** none; source review only.

## Problem framing

This is a scheduler, result-validity gate, and renderer-supervision boundary, not just a background-thread call. A render request must carry a stable document identity and revision, requested preview variant, user-visible selection generation, priority class, cancellation handle, deadline, and bounded output policy. Queue identity should coalesce equivalent work for one document/revision/variant; selecting a different document advances a monotonically increasing UI generation. A renderer result is publishable only if the view still names the same item and generation, the source revision and renderer/options key still match, the result is complete and within limits, and cancellation has not won the terminal-state race. Cancellation is a request to stop work, not proof that work has stopped. The acceptance gate remains mandatory after a cancellation request and after renderer completion.

## Scheduling, priority, and resource bounds

Use a small app-owned bounded scheduler with three semantic classes: current visible selection, near-visible prefetch, and background import previews. Dispatch current-visible work first, but do not leave imports behind an unbounded strict-priority stream. A weighted round-robin policy (for example, three visible/prefetch dispatches per background dispatch), aging of the oldest background job, and—when there are at least two slots—one slot reserved for a waiting background job are candidate guarantees. With a single slot, the weighted dispatch rule and per-job deadline provide eventual service. Values are policy parameters, not performance results. Keep one dispatcher in charge of classes; a FIFO semaphore is useful only to cap running renderers, not to implement priority. Tokio's semaphore is FIFO, including a head-of-line case for a large acquire_many request (SRC-05).

Bound active renderer count, queued job count, in-memory input/output bytes, per-render dimensions/pixels, output bytes, progress-event buffering, and cache bytes. Keep only handles/keys in the queue; do not read whole files into queued jobs. Coalesce duplicate document/revision/variant requests, promote a queued preview when it becomes visible, and replace obsolete queued visible/prefetch work. Do not drop the underlying durable import record merely because a derived preview queue is full. A starting concurrency of two is a plausible desktop default to validate, supported as a precedent by one PDF contact-sheet implementation, but is not a universal benchmark or guarantee (SRC-18).

A worker pool is an alternative to launching a process for every preview: it amortizes startup and can still be supervised if each worker handles one request at a time and the supervisor may kill/restart it. A one-process-per-job mode gives a simpler failure boundary but adds startup and memory cost. Reuse should be selected per handler based on measured startup cost, failure containment, and sandbox capabilities. Do not use an unbounded async blocking pool as the renderer budget: Tokio documents a high default thread ceiling and says started spawn_blocking tasks cannot be aborted, and runtime shutdown can wait indefinitely for them (SRC-01). Async cancellation tokens are useful for cooperative tasks, but they do not stop a native parser that ignores cancellation (SRC-02).

## Cancellation, hung work, crashes, and shutdown

Define explicit job states: accepted, queued, starting, running, cancel-requested, succeeded, cancelled, failed, timed-out, and shutdown-aborted. The supervisor owns an idempotent transition to one terminal state. Queued cancellation removes the job and releases its reservation immediately. Running cancellation first signals the handler over its job protocol; after a short bounded grace interval, terminate its process group/job object, await/reap it, discard its partial output, and release all accounting. The grace interval must be tuned from measurements; no cancellation-latency claim was tested here. A Rust Child handle alone is insufficient: std Child drop does not kill/reap the process by default; Tokio kill_on_drop also defaults false and only addresses the child, while process-tree cleanup is platform-specific (SRC-03, SRC-04).

Use monotonic wall-clock deadlines plus a no-progress watchdog for handlers that can emit heartbeats. A child exit, timeout, malformed protocol, output-limit breach, or watchdog expiry fails that job, invalidates its partial output, and lets the supervisor restart the worker with bounded backoff. Retry only failures classified as worker loss, not deterministic malformed-document errors. After repeated failures for the same handler/version, open a circuit breaker and return a typed unsupported/error placeholder rather than retrying forever. Shutdown stops admission, cancels queued work, signals active jobs, drains only until a bounded deadline, then force-terminates remaining worker trees and reaps them; it must not wait forever for a stuck parser. The UI remains asynchronous during this drain.

A child process helps contain crashes and hangs; it does not by itself sandbox a hostile parser running with the app user's authority. Prefer a per-job OS sandbox with read-only access to that document and a private bounded scratch/output directory, no network, and no inherited credentials or unrelated handles. Linux Landlock can enforce a filesystem ruleset without root when the process has no_new_privs, but supported ABI/rights vary by kernel and descriptors opened before enforcement remain outside those path restrictions (SRC-07). Windows Job Objects can account/limit/terminate process groups; child processes normally join the job unless breakaway is enabled, and nested jobs require Windows 8 / Server 2012 or later (SRC-06). AppContainer is a separate Windows isolation option introduced with Windows 8 and requires deliberate profile/capability grants (SRC-08). Apple's archived App Sandbox guidance says a plain child does not provide XPC's privilege-separation security; a child inherits only static entitlements, so an open-after-launch document needs to be passed as data or by bookmark; XPC is preferred when building a sandboxed helper (SRC-09). These are OS-specific backends, not one portable guarantee. Fail closed or expose a clearly constrained handler policy if the platform cannot establish the required sandbox; do not claim that a process boundary alone makes untrusted parsers safe. No machine-wide privileged service is required.

System thumbnail APIs are useful adapters, not the only contract. Apple Quick Look offers async best/low-quality representations and request cancellation, with format coverage influenced by platform and installed thumbnail extensions (SRC-10). Windows Shell thumbnail handlers run out of process by default in the documented model, but a registry setting can opt a handler out; its shell cache uses last-modified time and discrete sizes, so app-owned result validation and cache rules still matter (SRC-11). These APIs can serve a platform-supported fast path or fallback, but their handler/version behavior and cancellation guarantees need probing on supported OS releases. A long-lived user-level thumbnail service may be reusable on Linux, but it is optional and non-portable; do not require installing a new service.

## Cache validity and persistence boundary

Key a preview cache entry by stable document identity/content revision, normalized page/region and pixel-size request, renderer/handler identity and version, rendering options (including color mode), and cache schema version. Prefer a digest or a trustworthy app-managed content revision over a path/mtime-only key. A linked external file needs a revision policy that accounts for edits while rendering; filesystem notifications are hints, not a final acceptance check. Recheck revision immediately before publishing. For stronger guarantees on mutable external files, render from an immutable local snapshot and verify that the live content still has that revision before display.

Treat previews as derived cache data, not authoritative records. Persist only complete validated entries: write a bounded temporary artifact, validate dimensions/format/length, then atomically commit the metadata/artifact according to the chosen store's transaction semantics. SQLite's atomic-commit explanation covers rollback-journal mode, not WAL, so WAL behavior needs its own review if selected (SRC-12). On startup, discard orphaned temporaries and revalidate cache version/revision; never resume or expose a partial render. The accepted import/work queue belongs to the reference manager's existing durable import record if restart survival is required; regenerable previews can be requested again. Whether an interrupted import must resume is a product decision.

The freedesktop Thumbnail Managing Standard 0.9.0 is useful cache-history, not a sufficient correctness contract: it uses a per-user XDG cache, URI and second-resolution mtime, recommends checking size, and explicitly warns that mtime alone can collide at one-second resolution (SRC-13). Zotero's 1.1.5 contact-sheet release demonstrates a bounded image-count and approximate-byte cache, lazy near-viewport work, old-image retention until replacement decode, generation tracking, active-canvas cancellation, and a two-job cap. Its own README limits tested compatibility to Zotero 9/10 and says the tests do not establish every PDF's compatibility; those tests were not rerun for this research (SRC-18). Reuse these mechanisms selectively, not its private Zotero API assumptions.

## UI progress and integration contract

Expose a small typed interface such as `submit(Request) -> JobId`, `cancel(JobId)`, `cancel_obsolete(ViewGeneration)`, `subscribe(JobId) -> ProgressEvent`, and `shutdown(deadline) -> ShutdownReport`. A request includes document/item id, immutable source revision or file token, preview variant/options, priority class, and a deadline/limit profile. Events include the same job id and generation, state, optional completed/total units, stage label, and terminal error code. Report indeterminate progress when total work is unknown instead of inventing a percentage. Throttle or coalesce progress updates; preserve terminal events. The UI must discard progress and results for old generations, clear or replace the old document's current-preview slot on selection change, and only mark a preview current after the acceptance gate. Progress events are status hints, not authority to display output.

The renderer contract should take a read-only input capability and request parameters, emit bounded progress/results, and never write the source document. The supervisor owns cache publication, output validation, queue/fairness, cancellation, retry, and final display eligibility. Handler code should not mutate the view model or commit directly to the cache. Add explicit format support/unsupported/error outcomes and a stable renderer version in the cache key.

## Real implementation history and useful precedents

Zotero's 7.0 history is unusually close to this problem. Attachment previews were introduced in Zotero 7, with issue #238 tracking a request from 2013 until maintainers reported it added in 2025. The 7.0.4 changelog later records a preview-disappearance fix; 7.0.12 records a fix for a preview showing the wrong item during rapid attachment switching (SRC-14, SRC-20). The released v7.0.12 `attachmentPreview.js` keeps only the most recent pending task, serializes render/discard work, captures an item id, and checks after awaited work that the item is still selected before accepting it (SRC-15). This supports latest-only coalescing and a post-completion identity gate; item id alone is weaker than a document revision plus view generation. The same release's PDF worker manager uses one Web Worker and a FIFO queue with priority items inserted at the front; because priority insertion is strict, an endless priority stream can delay ordinary queued work, and the worker error listener logs but does not show a restart policy in that file (SRC-16). The separate current Zotero document-worker project builds Web Worker code for desktop and exercises shared modules in Node tests and iOS JavaScriptCore; this is a useful in-process worker architecture, not an OS-process security boundary (SRC-17).

Apple OperationQueue is another native queue model: it orders ready work by priority/readiness, caps concurrency, and lets operations cooperate with cancellation. Cancellation does not force running code to stop, and a queued cancelled operation remains until the queue starts it to mark completion; custom queues default to background QoS (SRC-19). This reinforces the need for explicit queue removal, cancellation semantics, and UI acceptance checks in an application-owned scheduler. The platform preview APIs offer progressive/low-quality content, but the product should decide whether a fast generic icon may remain visible when it is not the currently selected document; stale document content must never do so.

## Findings versus unresolved decisions

**Supported findings:** queued work can be coalesced and reprioritized; active work needs a cooperative cancel plus a force-stop boundary; native blocking tasks are not hard-cancellable; current-item checks must occur after asynchronous rendering; bounded concurrency and byte-aware caching are practical; OS process groups/sandbox features have platform/version caveats; mtime-only caching is weak; preview work and accepted imports have different persistence requirements.

**Open owner facts:** supported OS/minimum versions and packaging/signing model; actual formats and renderer licenses; whether imports are copied into immutable app storage or may be linked mutable files; whether imports must resume exactly after restart; whether system thumbnail providers are acceptable and what fallback is allowed; target visible-preview latency and memory/disk budgets; whether a generic icon is permitted while no current preview is ready; the policy if an OS sandbox is unavailable; needed progress UI and cancellation affordance.

**Validation proposed, not run:** adversarial rapid selection/edit/reopen tests with deliberately reordered completions; same-item/same-revision dedupe and promotion; stress a continuous visible stream while proving background dispatch; cancel queued and running jobs and measure kill/reap latency; inject crash, hang, malformed output and oversized input/output; deny sandbox reads/writes/network and check no credential/handle leakage; kill the app during cache commit and recover; mutate a linked file during render; exercise cache revision/renderer-version changes; verify progress ordering and stale-event rejection; test large documents and per-process resource ceilings on every supported OS. No application was built, deployed, or benchmarked here.
