# Proposal and plan review — cancelable local document-preview jobs

## Recommendation

Build an app-owned scheduler and supervisor around bounded renderer workers. Keep the UI thread out of file reads, parsing, rasterization, cache I/O, and child-process waits. Use explicit job IDs, document revisions, and per-view generations. Coalesce equivalent queued work, prioritize the current visible item, and schedule background imports with a bounded service share. Treat cancellation as a request followed by a result-acceptance gate; use cooperative cancellation first and a bounded force-stop path for parsers that hang or crash. Keep render jobs ephemeral across restart; persist imported work according to the reference manager's existing import record. Cache only complete, revision-matched results. Do not require a GPU, uploads, elevated privileges, or a newly installed machine-wide service.

A Rust implementation can expose this as a host-owned async component. On Linux, Windows, and macOS, use a per-platform process/sandbox backend where supported. A process boundary gives crash and timeout recovery but does not alone make a hostile parser safe. If the minimum supported OS cannot enforce the selected sandbox policy, an owner decision is required about whether to disable that renderer, reduce its file capabilities, or ship a different isolated helper. Sources and their conditions are indexed in sources/README.md; the full per-source identity/locator/condition record is in source-map.json.

This only guarantees queue service if running work is bounded; the no-progress/total deadline plus forced termination supplies that bound. Record attempt count and terminal cause. This is safer than two unconditional retries, which can repeatedly feed the same crashing file. See SRC-06, SRC-15, SRC-16. |

## Proposed component and integration contract

The component owns four parts:

1. **Admission and identity.** A Request contains a stable local-document/item id, a source capability (read-only handle/bookmark or app-owned immutable file), source revision, preview variant/options, priority class, UI generation, and resource/deadline profile. A result echoes JobId, document revision, render options, and generation. Requests with an identical cache/render key share work; new revisions invalidate older keys.
2. **Scheduler and resource controller.** Keep separate current-visible, prefetch, and import queues. Bound total pending descriptors, number of active renderers, memory reserved for decoded inputs/results, page/pixel dimensions, encoded output bytes, and progress buffering. Queue descriptors do not own file contents. The dispatcher applies visible preference and fair background service before asking a bounded semaphore/process pool for a slot. Do not let all CPU cores or a runtime's blocking-pool default determine renderer concurrency.
3. **Worker supervisor.** Launch a bundled, app-owned renderer with no elevation. One request at a time per worker simplifies cancellation and crash accounting. Use a small pool if startup measurements justify reuse; recycle on a crash, watchdog timeout, protocol error, memory/CPU limit, or configured age/job count. A per-request child is a stronger freshness/failure boundary but may have higher startup and memory cost. Use OS-specific process-tree termination and sandbox policies. Pass only the selected file capability, scratch/output location, and protocol handles; bound stderr and progress bytes.
4. **Result/cache gate and UI adapter.** Validate terminal status, request id, source revision, decoded output, size, dimensions, and cache schema before atomic cache publication. The UI thread receives typed events only; it never parses files or waits for a child. Before drawing, compare the completion to the current item/generation/options and cancellation state. A same-revision progressive low-quality result may be replaced by sharper output for the same current generation; a different item's image may not remain presented as its preview.

Suggested API surface, independent of the UI toolkit:

- submit(request) -> JobId
- cancel(JobId) -> CancelDisposition
- cancel_obsolete(view_id, generation)
- subscribe(JobId) -> bounded/coalesced ProgressEvent stream
- shutdown(deadline) -> ShutdownReport

Terminal outcomes are exactly one of succeeded, cancelled, failed, timed_out, or shutdown_aborted. Events carry an error category safe for the UI (unsupported format, changed source, resource limit, renderer crashed, timeout, cancellation, cache failure). Worker logs should not contain document bytes or credentials. The supervisor, not the child, owns final cache writes.

## Resource, security, and persistence policy

- **Memory/CPU/disk:** cap active jobs and worker processes independently; use a hard per-process CPU/memory/time limit where the supported OS backend can enforce it. Add format-aware page/pixel/output caps and total cache-byte/LRU limits. For very large documents, render requested pages/regions from a file handle or streamed snapshot rather than placing the whole document in memory. If a hard memory limit is absent on a supported platform, expose that as a measured risk/owner decision rather than calling the handler bounded.
- **Sandbox:** the child is an availability boundary by default. To claim hostile-parser confinement, require an OS-enforced policy. Linux can use Landlock/no_new_privs when the kernel ABI supports required rights; Windows can combine a Job Object with AppContainer/read-only paths/network denial; macOS should evaluate a bundled XPC service or correctly signed sandboxed helper and pass access to the selected local file. Never grant general home-directory read or network access by accident. A parser sandbox still cannot prove a renderer bug-free.
- **No machine-wide privileged service:** helpers ship with and are launched by the app under the current user's authority. Native Quick Look/Shell APIs are optional adapters that may invoke OS-registered handlers; their execution and cache behavior are not app-controlled enough to replace the scheduler/result gate.
- **Durability:** document/import metadata is durable according to the product's existing library/database contract. Preview queue state, progress, child identity, and partial files are volatile. Complete preview cache artifacts are optional and may be discarded/rebuilt; cache metadata must include all key/version fields. After a crash, do not mark an import complete just because a thumbnail was written.

## Alternatives and trade-offs

| Approach | Advantages | Limits / appropriate use |
|---|---|---|
| In-process async tasks plus cooperative token | Low startup cost; simple for trusted, bounded work and I/O; naturally integrated with UI event loop. | Cannot hard-stop a native parser or stuck blocking call; runtime cancellation does not kill a process. Keep for orchestration and safe code, not untrusted parsing (SRC-01, SRC-02). |
| In-process fixed CPU pool/Rayon | Bounded CPU threads and good throughput for pure CPU kernels. | Still shares address space; a panic/hang/allocator blow-up can affect the app; running task is not forcibly killed. Useful for trusted transforms after decode. |
| App-owned child worker pool | Hard process restart and timeout boundary; process count/CPU/memory policies can be platform-specific; no machine-wide service. | Startup and IPC costs; process-tree/sandbox setup differs by OS; child alone is not a sandbox. Recommended general architecture with platform enforcement. |
| One child per render | Stronger request freshness and cleanup boundary, simple discard after timeout. | More startup, memory and scheduling overhead; measure whether visible latency is acceptable. Consider for high-risk handlers. |
| Apple Quick Look / Windows Shell / Linux user thumbnail service | Reuse installed native formats, cache and platform UX; useful for generic previews/fallback. Quick Look supports cancellation and progressive representations; Windows handlers run out of process by default in the documented model. | Platform/version/provider-dependent; a handler can be installed/changed or isolation disabled; app cannot use their policies as a universal guarantee. Do not upload docs or install a new privileged service (SRC-10, SRC-11, SRC-13). |
| Shared Web Worker / embedded document worker | Separates work from UI event loop and can reuse parser code across test/runtime hosts. | Same-process failure/security boundary; worker termination discards worker state but does not itself impose file/network/OS resource limits. Good for trusted handler or UI responsiveness, not sole hostile-parser containment (SRC-16, SRC-17). |

## Open owner decisions

1. Minimum Windows/macOS/Linux versions, packaging/signing model, and acceptable per-platform sandbox backends.
2. Supported formats, bundled handler versions/licenses, whether custom or OS-installed handlers are allowed, and whether unsupported formats get a generic icon or no preview.
3. Are imported documents immutable app-owned copies, or can the library reference user-editable linked files? This determines stable revision and hashing/snapshot requirements.
4. Must an accepted import resume exactly after restart, or only remain visible in the durable import record and re-enqueue? Preview jobs themselves should not be resumed.
5. What memory, CPU, cache-disk, output-dimension, queue-size, cancel-latency, shutdown, and visible-preview targets are acceptable? The proposed two-slot cap, three-to-one scheduling ratio, and cancellation grace are not benchmarked.
6. If an OS sandbox is unavailable or cannot receive a selected file capability, should that format be disabled, shown with reduced guarantees, or handled by a different renderer?
7. Should cache be app-private or interoperate with platform caches? Is a low-quality same-document preview allowed during refresh? A previous different document must never be displayed as current.

## Proposed validation (not executed)

1. Model scheduler state transitions and test duplicate coalescing, priority promotion, queue bounds, cancellation races, one terminal transition, and background service under an endless foreground arrival stream.
2. With deterministic fake renderers, reorder completion and cancellation across rapid item changes, edits, repeated open/close, and renderer-option changes; assert the view never accepts a mismatched generation/revision and the cache never commits stale output.
3. Use format fixtures for large, malformed, truncated, encrypted, unusual-image-dimension, and unsupported documents. Verify bounded read/output/memory behavior on all supported platforms.
4. Inject worker crash before/after output, hang before progress, hang after progress, malformed IPC, runaway descendant, full disk, app shutdown, and kill during cache publish. Check retries/backoff, worker replacement, complete reap, temporary cleanup, and import/cache recovery.
5. Measure foreground latency and background completion at 1/2/4 slots under realistic import bursts; tune weighted ratio, aging, caps, and grace. Include one-slot devices and slow storage.
6. Verify no document bytes, renderer outputs, or metadata are sent over the network; test sandbox-denied home, credentials, network, and writes outside the private scratch/cache. Verify app runs without elevation and with platform sandbox present/absent.
7. Test progress event ordering, coalescing, unknown totals, and terminal status; assert no event from an older generation updates the current UI. Validate cache key changes for file revision, handler version, size, color mode, and schema.
8. If using SQLite, test the exact selected journal mode and filesystem with crash-recovery fixtures; do not infer WAL guarantees from the rollback-journal technical note.
