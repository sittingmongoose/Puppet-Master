# Independent critic review — cancelable local document-preview jobs

**Run/stage:** B12-P02-control / critic  
**Review basis:** the complete released brief, investigator discovery and draft, source-map, revealed plan, plan-reveal record, and investigator source-index README named in the input map. I independently opened the primary sources listed in the critic source map. This critiques the proposal; it is not an authoritative final design or a repair of the investigator draft.

## Overall assessment

The investigator package addresses the brief's major concerns and retains its full scope: bounded scheduling, foreground preference with background service, request and view identity, stale-result rejection, cancellation versus termination, crash/hang recovery, cache and restart validity, truthful progress, local/unprivileged operation, platform differences, alternatives, open owner facts, and future validation. Every material revealed-plan clause receives a disposition. The proposal appropriately labels the two-slot cap and fairness ratio unvalidated, and separates proposed validation from reported work.

The direction is credible, but several qualifications should be incorporated before a final is prepared. One Zotero precedent is described too strongly; coalesced work needs per-subscriber cancellation ownership; Linux network confinement and the macOS helper lifecycle need concrete fail-closed behavior; a generic Linux thumbnail service is not established by the cited sources.

## Findings

| ID / classification | Package locator | Evidence and assessment |
|---|---|---|
| C1 — **material wrong** | discovery.md, “Real implementation history”; source-map.json SRC-15 | The claim that Zotero v7.0.12 serializes preview/discard work omits a material timeout behavior. In the pinned attachmentPreview.js, _processTask races the render/discard promise against a 3-second delay, then resets processing/render flags (source lines 2050–2117). A promise that loses Promise.race is not cancelled; the task loop can admit later work while the earlier render is still active. The same file checks the selected item ID around rendering (lines 2155–2225), so the useful identity-guard precedent remains. Narrow the history claim to normal-path serialization plus latest-task coalescing and post-await item-ID checks; note that timeout bookkeeping can release without stopping underlying work. This does not invalidate the proposed acceptance gate. |
| C2 — **material incomplete** | draft.md, “Recommendation”; “Proposed component and integration contract” §1 and API surface | Equivalent requests may join one pending/in-flight render, while cancel(JobId) cancels a job. The draft does not define whether JobId belongs to shared work or one caller. If one view cancels a shared job, another still-interested subscriber could lose its result; if shared work is never cancelled, obsolete work can consume a slot. Separate render-work identity from subscriber/request identity, track interest, promote shared work when any subscriber becomes visible, and cancel the underlying render only when no valid interest remains or policy otherwise requires. Test two callers sharing work while one cancels. |
| C3 — **material incomplete** | draft.md, exact-plan row “A worker checks the flag…”; “Worker supervisor”; “Resource, security, and persistence policy” §Sandbox | The proposal correctly says a child alone is not a sandbox and treats OS backends as distinct. It does not give an enforceable timeout/kill/restart contract for the macOS XPC option. Apple's current XPC overview describes launchd starting services on demand, stopping them when idle, and restarting after a crash; that overview does not establish that cancelling an XPC connection stops a stuck render or bounds shutdown. Define the supported service type and how a hung request is forcibly ended/replaced, or mark that platform/handler unsupported until proven. Windows Job Objects also need host conditions stated: default CreateProcess children join, breakaway can escape, and nested jobs are supported starting with Windows 8 / Server 2012. Test the actual target launch environment. |
| C4 — **material incomplete** | draft.md, exact-plan row “Keep the app responsive…”; “Sandbox” bullets; discovery.md, “Cancellation, hung work, and crashes” | The general Landlock caveat is correct but too broad for the no-network requirement. Current kernel documentation describes ABI-sensitive rights: TCP network controls begin at ABI 4 and UDP controls at ABI 10. It also documents descriptor-associated access and a narrower IPC-scope caveat: a previously connected datagram socket is not constrained by later scope enforcement. State exactly which socket operations a chosen policy controls; do not treat this as a general network firewall. “Probe ABI” alone is not enough if a handler must have no network path. Name the required rights/ABI, close or avoid inherited network descriptors, and fail closed or use another backend when controls are absent. Keep deliberately passed file handles separate from unintended pre-opened handles. Add ABI- and descriptor-specific sandbox tests. |
| C5 — **unsupported** | draft.md, “Alternatives and trade-offs,” row “Apple Quick Look / Windows Shell / Linux user thumbnail service” | The cited Linux source, SRC-13, is the freedesktop thumbnail cache/metadata standard; it does not establish a generic user thumbnail service or service API. Either name and source a particular existing implementation/protocol with its version and lifecycle, or label this as an unverified Linux-specific possibility. Preserve the brief's no-new-machine-wide-service constraint. |
| C6 — **minor locator/wording** | revealed-plan.md opening paragraph; draft.md, exact-plan row “FIFO queue with two worker slots.” | The released plan says “FIFO queue” and later says visible requests are inserted at the front. Those rules are inconsistent if applied to one undivided queue. The draft's class-aware fair scheduler is a reasonable change and addresses both visible preference and starvation, but its reason “FIFO cannot express visible-item preference” overlooks the later front-insertion clause. State that the exact plan mixes FIFO-within-arrival and strict front-priority semantics; replace that combined policy with the proposed scheduler. The two-slot value remains clearly a starting proposal, not an empirical finding. |
| C7 — **material incomplete** | draft.md, exact-plan row “Failed jobs may retry twice”; “Worker supervisor”; “Open owner decisions” | The package proposes one retry for some worker failures and a per-handler circuit breaker, but neither retry count nor breaker threshold has source or measured support. The risk argument against unconditional retry is sound, yet “one retry is safer” is a design hypothesis. Define retryable failure classes, whether retries share the original total deadline/resource budget, breaker scope/threshold/reset, and whether repeated deterministic crashes disable one document or a whole handler/version. Keep defaults provisional and validate with crash fixtures. |
| C8 — **honestly unresolved external input** | draft.md, “Open owner decisions” items 1–7; discovery.md, “Findings versus unresolved decisions” | Supported OS/minimum versions, packaging/signing, format/handler set and license, immutable versus linked documents, import-restart guarantees, sandbox-absence policy, and resource/latency budgets are genuine owner facts. The draft exposes them instead of silently choosing a product. They do not require reducing brief scope; they constrain the eventual platform implementation and acceptance criteria. |

## Brief and exact-plan coverage

- **Identity and stale display:** Covered with document revision, render options, JobId, and view generation; the final UI handoff is gated and old-document pixels are cleared or replaced. Keep C2's subscriber identity separate from shared render identity.
- **Priority, fairness, and limits:** The proposal offers visible/prefetch/import classes, bounded queues and active renderers, byte/dimension/output/progress limits, and a candidate service share. These are useful policies, not validated targets. The exact plan's FIFO/front-insertion inconsistency is addressed by C6.
- **Cancellation and recovery:** Cooperative cancellation, terminal-state arbitration, bounded grace, process-tree cleanup, watchdog/deadline, typed failures, and bounded retries are covered. The platform-specific force-stop path and retry parameters still need C3/C7.
- **Cache and restart:** The draft rejects path+mtime as sufficient, includes renderer/options/schema in the key, validates before cache/display publication, and distinguishes derived previews from durable imports. Where native providers are used, capture their effective handler/version identity or constrain cache lifetime; renderer ID/version may not be obtainable from an OS-managed provider. The draft correctly leaves SQLite WAL and exact filesystem crash behavior for separate validation.
- **Progress and integration:** Typed, throttled, generation-stamped events and indeterminate progress are specified. Progress is correctly treated as a hint rather than display authority.
- **Alternatives and history:** Tokio, process workers, platform preview APIs, Apple OperationQueue, Zotero history, and Web Worker architecture are compared with platform and isolation limits. C1/C5 are the source-fit corrections identified here.
- **Local, unprivileged operation:** No GPU, upload, elevation, or newly installed machine-wide service is required by the recommendation. A process boundary alone is not called a hostile-parser sandbox. C3/C4 are needed before stronger per-platform confinement claims can be accepted.
- **Validation:** The draft labels its fairness, recovery, platform, sandbox, cache, and progress checks as proposed. Add shared-subscriber, Landlock ABI/descriptor, macOS hung-XPC, and Windows breakaway/nesting cases. Do not report future checks as run.
