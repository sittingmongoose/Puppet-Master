## Recommendation

Build a UI-independent local job coordinator around immutable requests, a bounded two-lane scheduler, handler adapters, a result validator/cache writer, and a narrow event/result contract. Keep preview generation off the UI thread. Treat visible selection as a short-lived demand lease with its own generation, separate from durable document identity. Use cooperative cancellation for handlers that can demonstrate bounded checkpoints; put expensive, fragile, or untrusted native parsers in child processes with an OS-specific supervisor and hard resource/deadline limits. Persist completed cache entries only; let the existing document/import owner reconstruct background work after restart. Numeric worker, resource, fairness, and latency targets remain owner decisions pending supported-platform and workload facts.

This design is local and per-user. It does not need a GPU, document upload, or machine-wide privileged service. Child-process separation contains many crashes, but is not itself a sandbox; access to files, devices, and networking must be constrained through per-OS user-level policy if parser threat isolation is required.

## Proposed component and integration contract

### Request identity and submission

A request contains: request_id; stable library item/document ID; source_revision; source locator supplied by the library; requested output target (selected preview, thumbnail size, page/range); render-profile/schema ID; handler ID and exact handler version; priority lane; view_target and selection_generation when UI-owned; optional import_intent_id. The durable cache key is a canonical encoding/hash of document content revision + requested render parameters + handler/build + cache schema. It does not contain only a path, mtime, or transient generation.

Submission returns one of Accepted(new ID), Joined(existing identical work), Replaced(obsolete queued work), Deferred/QueueFull, Unsupported, or ResourceRejected. Admission is bounded by pending count and estimated input/output/decoded-memory cost. Reserve room for visible demand; background batch producers submit incrementally and receive backpressure. Coalesce identical requests. A per-target latest generation supersedes stale visible work; same-document work for another page/profile remains independent.

### Scheduler and resource policy

Use independent visible and import lanes with FIFO order inside each lane and age promotion. Weighted round-robin is the default candidate because it serves both lanes during sustained load; a tunable initial 3:1 visible/import cycle may be measured, not treated as a product fact. When capacity permits, protect foreground service. When only one worker is permitted, use safe cancellation/checkpoints and an explicit no-preemption bound; do not claim that a priority reorder interrupts active decode.

Apply independent limits for: queue count and estimated queued bytes; total and per-handler active workers/processes; input bytes; decoded image pixels and dimension; estimated working memory (including intermediate buffers); encoded output bytes; temporary/cache disk quota; child CPU/wall time; no-progress duration; and retry count. Reject oversize work before allocation where possible. Account memory by decoded pixels and simultaneous buffers rather than compressed file size alone. Numeric values, low-memory mode, and whether a handler uses a child process are owner decisions informed by target devices and formats. PDF.js illustrates why to override defaults: maxImageSize is -1/no limit and stopAtErrors is false by default [S10]. GPU is optional, never required.

### Lifecycle, cancellation, and recovery

Use an explicit state machine: queued → starting → running(phase) → cancel-requested → canceled; other single terminal outcomes are succeeded, failed, timed-out, resource-rejected, unsupported, or stale-discarded. A lock/atomic transition orders cancel against commit; terminal notification happens exactly once even if cleanup itself errors. Cancel a queued request immediately. Signal cooperative tokens at checkpoints for known-cancelable handlers. For selected child handlers, request graceful stop, enforce an absolute wall deadline and no-progress watchdog, then kill the contained process tree after grace and reap/close every process handle. Do not implement an unsafe thread abort.

A result is publishable only after the handler exits successfully, the output passes format/dimension/byte checks, the source revision still matches, the request is not canceled, and cache identity matches. Cache publication is a separate atomic step. UI display is a second guard: apply only if item, request/target, profile, and current selection generation match. This prevents an old result from overwriting a newly selected document even when the old render finishes normally. PDF.js’s documented RenderTask cancellation may wait for a graphics pause and reject its promise, so treat cancellation as asynchronous until its terminal event [S09]. Its project history includes both a cancellation/loading error report with a community-fork idempotency fix [S11–S12] and a later reporter-described teardown exception that could leave a render promise pending, closed as not planned [S13]. These examples justify idempotent terminal settlement and cleanup-error injection tests, not a claim that every current PDF.js cancellation is broken.

### Cache, restart, and persistence

Keep cache in a user-local cache directory; treat it as disposable. Each committed entry represents one complete source revision and render profile, not the document path alone. Store enough self-description to validate schema, key, dimensions, and encoded format on read. Use a unique temp file beside the final object, cap writes, validate, then rename/publish. Remove temps at startup. Enforce LRU/size caps; negative-cache only deterministic unsupported/corrupt outcomes keyed to the same source/handler version, with expiry so updated files and handlers can recover.

Do not persist running/queued render jobs by default. The library/import owner retains whatever durable intent it already owns and can re-submit it after restart; the preview scheduler is idempotent. If the product must resume imports, the owner must specify durable intent, checkpoint granularity, idempotency, and changed-source handling. A single-file SQLite cache is an alternative when indexed eviction or atomic cache metadata is needed: commit blob and metadata in one transaction. If WAL is used, keep it local/same-host, allow a single writer, and manage checkpoint/sidecar lifecycle [S15–S16]. No sync database work runs on UI thread.

### Progress and UI events

Emit bounded/coalesced events with request_id, target/document ID, selection_generation if present, monotonic per-request sequence, state, phase, optional completed/total units, optional fraction, elapsed time, and terminal reason. Only emit percent when a meaningful positive total exists; otherwise phase + activity indicator. Sequence and generation allow the UI to discard reordering/late arrivals. In Slint 1.18.1, post a short closure with the immutable event through invoke_from_event_loop; do not decode, cache, wait on children, or synchronously look up thumbnails on the UI thread [S01]. GNOME’s lookup is explicitly threadsafe but performs blocking I/O, another reason to keep cache lookup off the event loop [S08].

## Evidence and alternatives

| Choice | Viable alternatives | Evidence, condition, and trade-off |
| --- | --- | --- |
| Worker execution | Fixed standard threads; Tokio async + bounded worker/semaphore; Rayon CPU pool; child per job or small child pool | Slint dispatch only requires UI handoff [S01]. Tokio blocking closures cannot be stopped after start and its limit is large by default [S02]; channel buffers are bounded FIFO [S03–S04]. Child per job gives simpler crash/deadline/resource ownership but costs startup; small pools reduce startup but require reset/recycle and can lose multiple jobs on crash. The right default depends on handler ABI, reentrancy, and cost. |
| Priority | Strict visible priority; FIFO; weighted round-robin/aging; visible reservation | Strict priority can starve imports and FIFO can bury visibility. Weighted service is a requirement-derived scheduler proposal, not a sourced claim about Slint/Tokio. Test fairness with an always-busy visible queue and sustained import feed; decide ratio and latency target with owner. |
| Cancellation | Cooperative token; async abort; process terminate; finish stale work and suppress result | Cooperative works only at handler checkpoints; Tokio async abort is yield-based and spawn_blocking abort is ineffective after start [S02]. PDF.js offers pause-aware cancel [S09]. Process termination contains work but is platform-specific. Finishing stale work can warm cache but consumes scarce resources; default is cancel obsolete visible work and suppress canceled results. |
| Fault boundary | In-process thread; OS worker thread; child process | Threads keep a shared address space. PDF.js issue #21934 is a narrow Windows Node worker_threads report, not a supported PDF.js Web Worker finding; maintainer says issue unsupported and absent in 6.x [S14]. Child process is the stronger crash boundary. Windows Job Objects manage associated descendants/limits subject to constraints [S06]; Rust Child alone manages only its direct child and requires explicit reap [S05]. |
| Cache validity | path + mtime; URI + mtime + size; full content digest; library revision + profile key | FDO 0.9.0 requires URI/mtime on global thumbs and recommends size check, but mtime has one-second precision and may collide [S07]. GNOME adds URI/mtime metadata and negative caching [S08]. Strong digest maximizes validity but can add read I/O; a library-owned source revision is cheaper if it is reliable for external changes. |
| Cache store | One atomically published file; SQLite record; OS thumbnail cache | FDO precedent uses temporary output followed by rename [S07]. SQLite can atomically commit bytes+metadata [S15], but WAL has one writer and same-machine shared-memory constraints [S16]. GNOME/FDO cache interoperability is useful for desktop icon thumbnails, but app-specific page/profile caches need richer identity than URI + modification time. |
| Restart | Requeue transient render jobs; persistent render queue; durable import intent only | Replaying active renders risks stale input and broken partial output. Persist source/import intent only if it is already part of the library’s durable contract; regenerate derived render jobs and validate cache. Numeric resume/checkpoint policy requires owner decision. |
| Progress | Page count; bytes; phases; determinate fraction; indeterminate | Page count can be truthful if the handler knows it; byte count may be unknown. PDF.js yields NaN percent without total [S10]. Report real units and phase, never fabricate percent or treat unchanged percent as definitive stall. |

### Relevant implementation history and applicability

- GNOME desktop thumbnailing demonstrates out-of-process MIME dispatch, fallback, size caps, success/failure caches, and a blocking lookup API. Its cache key begins from URI and validates last modification metadata; reuse the extension point/negative-cache idea only with stronger app cache identity [S08].
- Freedesktop’s 0.9.0 standard records a global source URI and required modification time, optional size, names cache files using the URI, uses temporary output then rename, and warns about second-resolution mtime collisions. Its portable desktop cache is not a content-integrity/security guarantee [S07].
- PDF.js API draft documents cancellation after a rendering pause, and loading progress can lack a total; its configured image size default is unlimited [S09–S10]. Pin an actual handler release and explicitly set/verify resource controls in any eventual implementation.
- PDF.js #11595 involved destroy-before-load completion in 2.3.200/2.2.228. The maintainer attributed the original symptom to Promise rejection handling; later commenters described a worker termination path, and a December 2025 community-fork commit changes a repeated termination throw to an idempotent return. The linked commit is not established as an upstream merge [S11–S12].
- PDF.js #21867 reports a teardown throw in 5.7.284 and 6.3.289 that could leave a render promise unsettled; it is marked “closed as not planned” and was not reproduced in this research [S13].
- PDF.js #21934 reports Windows Node worker_threads access violations in selected 5.x versions on one host and none in tested 6.0.227/6.3.289. Maintainers say Node worker_threads are unsupported and 6.x is fixed; do not generalize this report to standard Web Workers or all parsers [S14].

## Open owner decisions and uncertainty

1. Target operating systems/minimum versions and whether a per-user child-process sandbox is a requirement beyond crash/resource isolation.
2. Actual formats, handler versions, helper spawn trees, cancellation checkpoints, progress totals, thread safety, and handler-specific memory profiles.
3. Whether source revisions are immutable library-managed hashes or external files that can mutate outside the application.
4. Preview/cache output sizes, maximum dimensions/pixels/input bytes, total cache/disk budget, retry budget, no-progress and absolute timeouts.
5. Number of worker slots, foreground reservation, visible/import service ratio, import starvation ceiling, and latency target on minimum supported hardware.
6. Whether imports are durable in an existing owner component, whether they resume after restart, and what a user sees for unsupported/corrupt/oversize files.
7. Whether app-owned cache files or a transactional SQLite cache are preferred; no network filesystem should be assumed for a WAL database.

These uncertainties affect numeric values, platform adapters, and product behavior. They do not change the core requirements: the UI remains responsive; only the current source/profile/generation can update the selected preview; every job reaches one observable terminal state; memory, concurrency, output, and time are bounded; documents remain local; no GPU or privileged machine-wide service is assumed.

## Validation plan (proposed; not executed)

1. Scheduler/property tests: flood visible selections while imports remain queued; verify current visible jobs get service and imports are never starved beyond the selected policy; assert bounds on queue count/estimated bytes and active handler count.
2. Identity/race tests: rename or externally modify the file; switch A→B→A; change page/size/rotation/profile; finish old jobs late; verify wrong source, request generation, or handler version cannot update UI or hit a cache entry.
3. Cancellation matrix: cancel before dequeue, while opening, inside a slow page, during output validation, just before commit, after natural completion, and during shutdown; verify one terminal state, no stale display, temp cleanup, no leaked process, and correct behavior if cleanup throws.
4. Hostile/resource tests: malformed files, huge dimensions, decompression bombs, enormous page counts, child that never reports progress, child crash, disk full, output over cap, and child that starts descendants. Verify deadline/kill/reap/resource-reject outcomes on every supported OS without privileged service.
5. Restart/crash tests: terminate parent at temp write, file publication, and import reconciliation boundaries; restart; verify partial cache is ignored, complete cache is validated, imports are reissued idempotently only if their owner requires it.
6. Progress/UI tests: unknown totals, phases with no numeric fraction, rapid duplicate events, stale generation, terminal failures, and flood coalescing; assert event-loop responsiveness.
7. Performance/acceptance: measure visible p50/p95 latency, import completion/fairness, peak memory, CPU saturation, queue pressure, disk use, and shutdown time on minimum supported hardware. Set numeric pass criteria with the owner before treating any benchmark as a gate.
