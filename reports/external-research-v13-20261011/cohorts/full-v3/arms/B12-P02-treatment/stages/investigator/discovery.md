# Independent discovery — cancelable local document-preview jobs

Stage: B12-P02-treatment / investigator. Discovery is based on the brief alone; the exact plan has not been read. Source records are in source-map.json and the navigable sources/index.md. No product build, deployment, benchmark, or runtime witness was run.

## Problem decomposition

Six concerns need distinct identities and controls: (1) user-visible demand versus background import demand; (2) bounded admission and execution resources; (3) cancellation that is advisory in-process but forceable for a child; (4) whether a completed result still belongs to the current item and source revision; (5) what is durable across a process restart; and (6) honest progress/error reporting without work on the UI thread. A queue priority alone cannot solve all six.

## Mechanisms and alternatives found

GNOME’s desktop thumbnail factory is a useful implemented analogue: MIME-type registrations choose external thumbnailer programs, the caller supplies an input URI and output path, a failed helper reports a nonzero exit and a fallback may run, and success and failure caches are keyed from the input URI. The current GNOME API reference describes normal/large caps of 128/256 pixels and a negative cache. The Freedesktop Thumbnail Managing Standard (0.9.0) adds a portable local-cache pattern: canonical URI identity, metadata in the image, temporary output followed by rename, and source mtime/size verification. Its mtime is only second-resolution; it explicitly warns that mtime-only checks can reuse a wrong preview. These are useful patterns, not a complete app cache key or a security boundary. Keep handler/cache version, source revision, and render profile in this app’s key, and treat file metadata as a quick check rather than proof of bytes.

For concurrency, a fixed-size std::thread pool plus a small explicit dispatcher is the simplest runtime-independent option. Tokio’s bounded mpsc gives FIFO backpressure, but not priority lanes; its spawn_blocking pool can grow to a large configured limit and started blocking tasks cannot be aborted. If Tokio is already adopted, cap CPU work with a semaphore and keep long-running blocking handlers off spawn_blocking. Rayon is another CPU-pool option, but its standard work-stealing pool does not itself define visible-versus-import admission policy. A UI-independent worker result should return through Slint 1.18.1 invoke_from_event_loop; all widget changes remain on the event-loop thread.

To favor visible work and still serve imports, keep separate bounded/coalescing lanes (current visible request, then background import) and schedule with weighted round-robin plus age promotion. A strict priority queue can starve imports; pure FIFO lets a batch bury the selected item. Coalesce duplicate same-key work, replace obsolete queued demand, and cancel only work whose owner has declared it obsolete. Reserve or recover an execution slot for visible work when worker count permits. A guarantee depends on finite work quanta or cancellation checkpoints: a stuck non-cooperative handler can occupy a worker until its deadline/kill.

In-process cooperative cancellation is appropriate only for handlers that document checkpoints and bound their work. Tokio async abort is observed at yield points; its documentation specifically excludes aborting started spawn_blocking closures. For selected unreliable or high-cost handlers, a child process gives crash containment and an enforceable deadline. A thread is not a crash boundary: a current PDF.js issue report describes a Windows Node worker_threads crash, while the maintainer says Node worker_threads are unsupported and the cited 5.x behavior was absent in 6.x. Use that as a boundary lesson, not proof about PDF.js’s supported Web Worker or a current supported release. Rust Child::kill affects the direct child; Child drop neither kills nor waits. Windows Job Objects can manage/terminate associated descendants and apply limits, subject to breakaway/nesting conditions. Platform-specific containment and sandbox policy remain an implementation decision; a job object is process management, not by itself a parser security sandbox or a privileged service.

Resource bounds must be layered: bounded pending count/bytes, CPU concurrency, estimated decoded-memory admission, input/output byte caps, pixel/dimension caps, child-process count, wall-clock deadline, and a watchdog based on meaningful progress. PDF.js’s current draft API is a warning that library defaults are not app policy: maxImageSize defaults to -1 (no pixel limit), and stopAtErrors defaults false. Do not rely on a handler’s defaults to contain hostile or oversized input. Do not require GPU acceleration.

## Preliminary design direction for plan comparison

Give every request an immutable request ID, library item/document identity, observed source revision, page/region, target dimensions, render-profile version, and handler/version identity. Add a monotonically increasing selection generation for UI ownership. The UI accepts a result only if request ID, item, revision, and generation still match its current view; cancellation is not the stale-result guard. Re-stat or revalidate source revision before publishing. A content digest is strongest but can cost I/O on large inputs; use the library’s durable content revision when available, with explicit fallback semantics for externally modified files.

The component contract should expose submit/dedupe, reprioritize or supersede, cancel(request ID), subscribe to sequenced status/progress events, query/cache-read by complete key, shutdown(deadline), and explicit outcomes (success, canceled, stale-discarded, unsupported, failed, timed out, resource-rejected). Keep the active queue transient; persist only fully committed cache entries and the import/library state that can regenerate requests. Write to a bounded temporary output, validate dimensions/type/size, then atomically publish under the cache key. If SQLite is selected, keep cache bytes and validity metadata in one transaction, account for WAL’s single writer and same-host requirement, and treat the cache as evictable. Never resume a half-rendered job after restart.

Progress is a sequenced state stream: queued, opening, decoding, rendering, committing, cancel-requested, and one terminal state. Report determinate fractions only when the handler has a meaningful total; otherwise expose phase/elapsed and optional units, not fabricated percent. Coalesce high-rate updates, stamp each event with the request/generation, and ignore late UI events. Shutdown stops admission, cancels queued/current work, force-terminates eligible children after grace, reaps them, and returns by a bounded deadline; never wait indefinitely for in-process non-cooperative parsing.

## User-specific facts left open

Supported operating systems and minimum versions; actual formats/handlers and which expose cancellation/progress; whether import work is already durable and replayable; library item/source revision semantics for external edits; expected preview sizes and maximum decoded pixels/bytes; acceptable visible-latency, import-fairness, shutdown, memory/CPU/disk budgets; whether child sandbox primitives are available without installation; cache sharing/eviction policy; progress/error UX and whether partial previews may ever be shown. These should tune numeric caps and security scope; they do not block the component contract.

## Research executed versus proposed validation

Executed: primary documentation and implementation/history pages listed in source-map.json were opened and inspected; no application code or executable witness was run. Proposed: scheduler model tests under rapid selection and sustained imports; stale-result races across switch-away/back and source edits; cancellation before admission, during each handler phase, at commit, and during shutdown; child crash/timeout/descendant cleanup on each supported OS; oversized/decompression-bomb and malformed-file tests; cache-key/version invalidation and crash-between-write/commit tests; unknown-total and late-progress UI tests; measure responsiveness, throughput, fairness, memory peak, and shutdown latency on representative hardware. Numeric targets require owner input.
