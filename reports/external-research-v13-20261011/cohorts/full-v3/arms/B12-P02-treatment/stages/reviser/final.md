## Recommendation

Add a UI-independent local preview-job coordinator with immutable requests, bounded admission, an explicit scheduler, per-format handler adapters, a validator/cache publisher, and sequenced events. Keep decoding, child supervision, cache I/O, and waiting off the UI event loop. Use separate visible-preview and background-import lanes with coalescing, age promotion, and a weighted service policy. The visible/import ratio, worker count, queue limits, and time/resource ceilings are product decisions to measure against supported devices and actual handlers; the plan's two slots can be an initial experiment only.

Give each request a never-reused ID and a complete identity: library item ID, source revision, page/region and output profile, cache-schema/render-profile version, handler ID/build, and any UI target plus monotonically increasing selection generation. Use cancellation tokens for that one request; a newer selection supersedes only obsolete work for the same presentation target, not every job that happens to concern the same document. Cancellation is advisory until the handler reports terminal completion or a supervisor has stopped and reaped its process. Independently gate cache publication and display on current source/request identity. The source revision must describe the exact bytes consumed by the handler; a path revision at submission is insufficient. This is the principal protection against stale previews.

Start handlers in-process only when their cancellation points, failure domain, memory use, and duration are bounded and documented. Move expensive, fragile, or untrusted native parsers to per-user child processes when supported, with input/output and time limits, graceful-stop grace, forced termination of the contained process tree, and explicit reaping. A process is a crash/resource boundary, not a complete security sandbox. Do not promise parser isolation from file or network access until a supported per-OS sandbox policy is selected. The app stays local; no upload, GPU, or machine-wide privileged service is required.

Persist complete, validated cache entries as disposable derived data. Keep active render jobs transient. Let the library/import owner retain durable import intent, reconcile source revisions at startup, and reissue eligible requests. A SQLite cache is an alternative if atomic payload/metadata and indexed eviction justify it; WAL has one writer and local/same-host constraints [S15–S16]. Do not resume partial rendering or trust a saved path/mtime as proof that a result is current.

## Component contract

### Request and admission

#### Bind the revision to the bytes rendered

Use a SourceLease containing stable item identity, source revision/digest, and an immutable reader or snapshot guaranteeing the handler sees exactly those bytes. Prefer a library-owned immutable version. For mutable external files, use a supported atomic/versioned snapshot or stage a bounded sealed byte copy and hash those exact bytes; render from the snapshot, never by reopening a mutable path. Prove it is still the current revision before cache publication and display. Stat, mtime, size, and watchers are hints, not sole proof. If the exact bytes and current revision cannot be tied together, return SourceRevisionUnavailable/stale-discarded and do not cache or display the result as current. Bound snapshot I/O/disk and reject when limits are exceeded. OS snapshot support and library revision guarantees remain owner decisions.

A request carries request_id; stable library item ID; source_revision and source locator; requested page/region and output dimensions/profile; handler ID and exact handler build; cache schema; lane; optional UI target and selection_generation; and optional import_intent_id. The persistent key is a canonical versioned encoding of source identity plus every render-affecting parameter, handler/build, and cache schema. Do not put transient generation or queue priority into that key.

Submission returns Accepted, JoinedIdentical, ReplacedQueuedObsolete, Deferred/QueueFull, Unsupported, or ResourceRejected. Bound queued count and estimated bytes; active worker/process count; per-handler concurrency; input bytes; decoded dimensions/pixels and estimated working memory; output bytes; temp/cache disk; child CPU/wall time; no-progress duration; and retries. Account for decoded/intermediate buffers, not compressed size alone. Reserve admission for visible requests where possible. Reject/defer a full queue without blocking the UI. Configure parser-level limits explicitly; PDF.js draft defaults include no maxImageSize limit and stopAtErrors false [S10]. Numeric ceilings require owner input and device/format measurements.

### Scheduling and cancellation

Use FIFO within each bounded lane, with a tunable weighted cycle and import age promotion. The example 3:1 visible/import ratio is a test seed, not a guarantee. Let a newer visible request replace obsolete queued visible demand without deleting imports. Do not claim a priority reorder preempts active decoding. If only one worker can fit the memory budget, responsiveness depends on a handler checkpoint or child deadline.

The state machine is queued → starting → running(phase) → cancel-requested, with one terminal state: succeeded, canceled, failed, timed-out, resource-rejected, unsupported, or stale-discarded, SourceRevisionUnavailable, or SecurityUnavailable. Serialize cancel versus commit so exactly one terminal transition wins. Cancel queued jobs immediately. Signal cooperative tokens at documented checkpoints. For selected child handlers, send a graceful stop, enforce wall/no-progress deadlines, terminate the contained tree after grace, and always reap. Never use unsafe thread termination.

### Handler trust and isolation policy

Define a HandlerPolicy per format/version: trust classification; whether in-process work is allowed; whether a child process is required; allowed filesystem/network capabilities; resource limits; process-tree policy; required per-user sandbox; and behavior when that isolation is unavailable. Unknown handlers are not presumed trusted. A child still runs with the user's authority unless OS policy restricts it. If required isolation is unavailable, return SecurityUnavailable/Unsupported without silent unrestricted fallback. Do not add elevation or a machine-wide service. Owners must select supported OS-specific controls and user-facing behavior.

### Result/cache and UI ownership

A result reaches the cache only after successful exit, bounded/type/dimension validation, proof that the handler consumed the keyed immutable snapshot, complete key match, and ordered uncanceled commit. Store self-describing snapshot digest/capture method and key/schema/dimensions/format metadata. Use same-volume unique temp output and atomic publication where supported; evict by a configured LRU/size budget. Negative-cache only deterministic unsupported/corrupt outcomes against the same source and handler version, with expiry so updates can recover. Cache is local, per-user, and rebuildable.

Cache validity and visible ownership are separate. A valid old-selection result may warm cache; only the latest matching request/item/source/target/profile/generation may change the current view. Require a lease/snapshot tying the digest to exact consumed bytes; revalidate current revision before publication and display. For mutable external files, metadata-only rechecks are insufficient; fail closed if proof is unavailable. This prevents stale result display even if cancellation is late or ignored.

### Shutdown and restart

Stop admission, invalidate view generations, mark queued jobs canceled, signal active handlers, wait grace, kill/reap supervised children, close pipes and publish one terminal result per request, then return before the deadline. In-process handlers require bounded cancellation and a documented shutdown behavior; otherwise they cannot be promised to stop.

Do not serialize active render jobs. At start, discard temps, verify cache records, ask the library/import owner for durable outstanding intent, re-stat/revision-check sources, and submit new requests. A full content hash avoids reliance on metadata but costs a read; use the library's authoritative revision if it catches external edits. Only persist import intent in the existing owner if the owner already offers durability/idempotency. SQLite blob+metadata transactions can simplify atomic record updates [S15]; WAL supports reader/writer overlap but still one writer and depends on same-machine shared memory, so keep it on local storage [S16].

### Progress and UI integration

Emit bounded/coalesced events with request_id, target/item, selection_generation, monotonically increasing per-request sequence, state, phase, optional completed/total units, optional fraction, elapsed time, and terminal reason. Only meaningful totals produce a fraction. Unknown total means phase/activity indicator. Ignore stale sequence/generation events. Use a short UI-thread callback only to apply an already-validated result or event. Decode, supervise, wait, cache lookup, and cache writes remain off the event loop [S01, S08].

## Alternatives and relevant implementation history

- Execution: dedicated fixed threads are simple and runtime-independent; Tokio async plus a semaphore works if the app already has Tokio but started spawn_blocking closures cannot be stopped; Rayon suits CPU pools; its docs describe pool configuration and work stealing, while the conclusion that they do not define this app's visible/import lanes is an inference from the API surface [S17]. Child-per-job gives strong crash ownership and simpler hard deadlines at startup cost; a small child pool costs less startup but needs recycle/reset policy and shares failures among jobs.
- Priority: strict visible priority risks starvation; FIFO delays current view; weighted service plus age promotion is a product policy to measure. The weight cannot guarantee latency for a non-preemptible active job.
- Cache: a single immutable object/file with atomic publish is simple; SQLite transaction couples payload and metadata but adds database maintenance; OS thumbnail caches are interoperable but their URI/mtime identities may be too weak for page/profile previews [S07–S08, S15–S16].
- GNOME demonstrates MIME-based external helper dispatch, fallback, size limits, positive/negative caching, and a blocking lookup API [S08]. Borrow dispatch/fallback and negative-cache patterns; do not copy its cache key or call blocking lookup from UI.
- PDF.js RenderTask cancellation can wait for a graphics pause and rejects its promise, so cancellation is asynchronous [S09]. Draft API defaults are not containment policy [S10]. Issue #11595 has a maintainer distinction between expected promise rejection and later worker-error reports; a linked December 2025 idempotency change is in a community fork, not verified upstream [S11–S12]. Issue #21867 is a reporter-described teardown path with unsettled completion, marked closed as not planned and not independently reproduced [S13]. Issue #21934 is a reporter's Windows/Node matrix on one host: no faults in specified 6.0.227 and 6.3.289 runs. A maintainer says Node worker_threads are unsupported and the issue was already fixed in the latest release; this is not independent verification across versions/hosts and does not establish standard Web Worker behavior [S14]. These reports motivate explicit terminal settlement and handler/version-specific regression checks; they do not show all current PDF.js cancellation is broken.
- Windows Job Objects can group/manage associated processes and impose limits, but breakaway and nesting/version behavior must be handled; a job object is not a complete security sandbox [S06]. Rust Child kill/reap covers the direct child only [S05]. Other OS process-tree/sandbox adapters require target OS decisions.

## Owner decisions and unresolved facts

1. Supported operating systems/minimum versions; per-handler trust classification and per-user sandbox/capability policy; child-tree cleanup and parent-crash policy; behavior when required isolation is unavailable (recommended: fail closed).
2. Actual document formats, handler versions, spawn trees, thread safety, cancellation checkpoints, progress totals, startup cost, and memory profile.
3. Whether the library supplies immutable source-revision leases; for external files, which atomic snapshot/sealed-byte mechanism binds a strong digest to bytes read and proves currentness. Stat alone is insufficient.
4. Maximum dimensions/pixels/input/output bytes; total cache and temporary-disk budget; worker/process limits; low-memory behavior; deadlines and retry policy.
5. Foreground reservation, visible/import service ratio, import age ceiling, latency/fairness goals, and benchmark hardware.
6. Whether background imports already have a durable owner, required restart behavior, and idempotent reconciliation contract.
7. File cache versus SQLite, eviction policy, supported filesystem atomic-replace behavior, and user-facing corrupt/unsupported/oversize outcomes.

These choices tune values/platform adapters; they do not alter the invariants: responsive UI, no stale current preview, bounded resources, one terminal outcome, local documents, truthful progress, recoverable crash behavior, and no GPU/privileged service assumption.
