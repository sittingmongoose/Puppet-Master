# Brief-only discovery: incremental search for a research notebook

## Scope and evidence boundary

This discovery uses only the released brief and primary documentation, source examples, release records, and issue histories for candidate indexing approaches. The exact plan has not been released at this point and was not sought or inferred. The assignment describes an editor that already owns notes, tags, links, and note text; the concrete store, stable-ID scheme, tag schema, build packaging, platform matrix, and existing editor callers are unknown. This is a proposal for the search component, not an implementation or editor rewrite. All validation below is proposed unless explicitly marked executed.

The governing data rule is straightforward: the notebook store remains canonical. The search index contains terms/postings, a stable note key, and an indexed revision/generation marker. It does not hold a second authoritative note body or title. A result carries a stable note ID back to the current note record, and the editor opens that exact ID after checking it still exists. A path or current title is display data, never identity.

## Feasible approaches

| Approach | Fit and useful properties | Costs, conditions, and reasons to keep it in the comparison |
|---|---|---|
| SQLite FTS5 | A local embedded lexical index with SQL query and tag-filter integration. An external-content table can hold postings while reading columns from a source table; a contentless-delete table (SQLite 3.43.0+) omits indexed text and permits row deletion. FTS5 supports phrases, prefixes, NEAR, boolean operators, BM25, and configurable tokenizers. | Check the shipped SQLite build at runtime: FTS5 may be omitted. External-content consistency is the application's responsibility, and query results can look inconsistent when content and postings diverge. Contentless-delete has different read/delete/rebuild rules and has no source content from which its REBUILD command can reconstruct the index. The one-writer behavior of SQLite still applies in WAL mode. Select between same-database external content and a contentless sidecar only after the actual store/build is known. Sources S01, S02, S03, and S04. |
| Tantivy, an embedded Rust search library | A Rust-native sidecar index with index writer/reader APIs, fielded lexical search, ranking, custom analyzers, and an indexed exact-ID field. The note body can be omitted from STORED fields and loaded from the authoritative store after a hit. Commits give a published search view; a durable outbox can bridge the source store and a separate index directory. | It is a second persistence domain: edits and index commits are not one transaction. Update means delete by ID plus add the current document, then commit; Tantivy does not enforce unique IDs. Commit blocks, queued adds can block, readers reload after commit, merge/segment behavior matters, and format compatibility must be checked on upgrades. The current upstream example and API are useful, but do not establish this app's performance. Sources S08, S09, S10, S11, S12, S13, S14, and S15. |
| Source-store scan as a baseline and recovery path | Smallest correctness model and a useful oracle for search-result fixtures; no derived index can go stale. It may be acceptable as a temporary path while the index is absent or being rebuilt if measured latency is acceptable at 20,000 notes. | Do not assume it will meet interactive latency: note size, query semantics, and storage are unspecified. Its tokenization must match the selected lexical contract if it is used to compare completeness. Measure rather than declaring it too slow or fast. |
| Hosted search | Excluded by the brief's explicit prohibition on sending note text to a hosted search service. A local daemon would add process, data-copy, recovery, and packaging work without solving an identified requirement. |
| Semantic/vector retrieval | Defer. The brief makes it optional; lexical indexing is the required first capability. A local model introduces inference cost, model/runtime distribution, additional feature storage, update/rebuild work, and new retrieval behavior. Consider only if representative lexical evaluation finds a material unmet use case and local privacy/cost limits are defined. No semantic approach is recommended now. |

No candidate is selected here. If the existing canonical store is SQLite and ships FTS5 with a sufficient version, FTS5 is a compact first prototype. If the store is not SQLite, the application needs more custom analysis, or a separately rebuilt sidecar best preserves edit latency, compare Tantivy. A plain scan remains the correctness baseline and potential degraded mode.

## Proposed identity, update, and query model

Use an immutable note ID generated and stored with the note record, independent of title and filename. Keep a monotonically increasing content revision (or store change sequence). Model index coverage explicitly as engine/schema/tokenizer version, active generation ID, last applied source sequence, per-note indexed revision, pending note count, and failed note count. An index row contains only ID/revision metadata and indexed terms; note bodies/titles are not stored for later retrieval. Tag names remain in the canonical tag store; use stable tag IDs for filter semantics and render current tag names from that store.

The note mutation transaction should also append a durable outbox change keyed by note ID and revision (or a deletion tombstone). This makes a crash after a note save replayable. The single index worker coalesces repeated queued changes to the newest revision, reads a current source snapshot, applies the change idempotently, commits in bounded batches, and advances coverage only after the index commit succeeds. If the source revision changes while work is in flight, do not mark the old revision current: requeue the latest one. A delete remains represented by a tombstone until the index has removed the ID. Never drop a failure after retries; retain its error and expose a retryable degraded state. Limit workers/writers so operations for one ID cannot race or create duplicate documents.

For Tantivy, use a raw/untokenized exact stable-ID field, issue delete+add for one document revision, batch updates through a long-lived writer, commit according to a measured latency/throughput budget, and reload or wait for the configured reader policy. The 0.26.2 API says delete is visible only after commit and applies to documents from previous commits and earlier operations in the same commit; its example shows atomic reader visibility across delete+add and warns that uniqueness is not enforced. The current report about thousands of tiny segments used a new writer and a commit per database mutation, so that is a concrete anti-pattern to test against, not proof of a fixed universal threshold (S08, S11, S12, S13, S14).

For SQLite, gate the feature on the actual library's FTS5 capability and feature floor. FTS5 by default copies indexed text. External content avoids that second copy but is safe only when postings stay synchronized with the source table. Triggers are a documented option; an official SQLite bug-forum thread describes a nested second AFTER UPDATE trigger that can make the documented FTS sync trigger use already-updated OLD values. Keep trigger interactions simple and test them, or use an application outbox/worker. A downstream watcher-thread issue is specific to Tantivy 0.22.1 and index evict/reopen churn; test it only if the app repeatedly opens/closes indexes (S15). The 3.43.0 contentless-delete feature is a candidate for a separate postings-only index; it supports DELETE/UPDATE under its stated column conditions, but because no content table exists, build a fresh generation by streaming from the notebook store rather than relying on FTS5 REBUILD. Do not assume an index rebuild is harmless to editing: WAL permits readers and a writer at once, but only one writer is available, and the work of a long index write can contend with note saves (S01, S02, S03, S04, S07).

Persist saved searches as the user-visible expression plus a versioned structured query representation and stable tag IDs. Do not rewrite a saved expression when a note title changes. If a saved object means “this note,” store its immutable note ID; if it means “search for this title text,” preserve the text as the query and let current indexed note content determine matches. Keep a literal-search mode distinct from any advanced engine grammar. SQLite FTS5 supports boolean, phrase, prefix, NEAR, and column-filter syntax; binding a SQL value is not a definition of what those operators mean. Validate or escape literal input according to the product query contract, reject malformed advanced expressions clearly, and preserve the query parser/schema version so a library upgrade cannot silently reinterpret saved searches (S01, S08, S09, S10).

Apply tag filters by stable IDs, either in the canonical store or as indexed exact metadata with tag changes included in the same revision/outbox flow. Every hit should return note ID and index revision; fetch title, excerpt, tags, and body from the canonical store. Drop a hit if its note was deleted, and suppress or visibly mark it if the indexed revision no longer matches the note revision. Do not show an old indexed hit as if its snippet were current.

## Tokenization and language limits

Neither candidate's built-in default promises language coverage. FTS5's default unicode61 is based on Unicode 6.1, treats Unicode letters/numbers/private-use characters as token characters, and removes diacritics for Latin characters by default. That is not language-aware segmentation: a copied no-space script may form tokens unlike the user's intended words. A SQLite forum report documents the Polish Ł/ł case: Unicode decomposition does not map it to L/l, and a custom tokenizer was suggested. FTS5 trigram can support substring matching, but a full-text substring under three Unicode characters returns no rows; some LIKE/GLOB shapes fall back to a table scan; case-sensitive trigram only supports indexed GLOB, not LIKE. Tokens over 32,768 bytes are silently truncated. Tantivy 0.26.2's default tokenizer splits at punctuation/whitespace, lowercases, and removes tokens longer than 40 characters; en_stem is English-specific and slower. Its listed stemmer languages are not evidence that every script receives useful word-boundary segmentation. Do not claim script coverage from “Unicode” support or a language enum. Sources S01, S06, S09, S10.

Before choosing normalization, define and fixture-test at least case handling, diacritics (including Ł), Unicode normalization/combining marks, punctuation/apostrophes, long tokens/URLs, phrase and prefix behavior, and scripts represented in copied excerpts (including no-whitespace text). Index and query paths must use the same versioned analyzer. Decide whether 1–2 character search, stemming, synonym expansion, CJK/Thai segmentation, or substring search is required; otherwise label those limits and do not promise them. If an analyzer change affects indexed terms, assign a new schema/tokenizer version and rebuild; preserve saved query meaning or surface an explicit migration decision.

## Catch-up, rebuild, recovery, and user feedback

Keep serving the last known-good generation while a replacement is constructed from current canonical notes in the background. Use a build-start change sequence plus a durable change log/outbox: scan the source, replay changes after the start point, verify the candidate generation's progress and fixtures, then atomically switch the active generation pointer. Retain the old generation until the switch is durable. Keep the source scan/read transactions bounded so rebuild does not pin a database snapshot or monopolize writes. Editing remains independent of index progress; do not run a full rebuild on the UI thread.

At search time, report index state next to results, for example: “Results may be incomplete · indexed through [time/sequence] · [N] notes pending · [M] need retry.” Make the pending and failed counts discoverable in an index-status panel. Expose rebuild progress, pause/cancel if feasible, completion and last successful timestamp. On failure, keep the last good index usable but label its results as potentially incomplete; never convert an error into an empty successful search or silently discard a note. Fetch each result from the authoritative store by stable ID at click time.

On open, verify engine format, schema/tokenizer version, and persisted generation/progress. An incompatible or damaged index is a derived-data fault, not data loss: retain canonical notes, mark search degraded, offer a background rebuild, and use the previous generation or a measured scan fallback. For external-content FTS5, integrity-check without rank=1 checks FTS internals but does not compare postings to the external content table; rank=1 requests that comparison. REBUILD recreates an external-content index from its named source table but is unavailable to contentless tables. For Tantivy, version history includes incompatible index formats and explicit “reindex” requirements for older upgrades; encode index compatibility and rebuild rather than assuming any release can open any generation. Sources S01, S05, S12.

## User-visible behavior and responsiveness

Search must remain useful while catch-up runs: keep queries against the last valid generation, filter hits against current note existence/revision, and state that new or edited notes can be missing until their queued revisions are committed. Offer the status and recovery action without blocking note edits. Show exact current titles on result rows and open the exact note by stable ID. Tag filtering must operate on stable tag identity even if tag labels are renamed. Empty results, stale-suppressed results, an empty index, and an indexer error are different states.

Measure search-after-open cold and warm latency, p50/p95 query latency for common and worst-case terms, tag-filter combinations, edit-save latency, commit-to-visible lag, worker throughput/backlog age, pending/failed count, memory/CPU/disk growth, segment count/cold open cost (Tantivy), WAL/checkpoint growth (SQLite), and rebuild duration/peak disk/CPU while editing. Use a 20,000-note fixture with realistic short/long-note distribution and tag density plus churn bursts. Include rename, repeated edit during indexing, deletion during indexing, app crash between source commit/index commit/ack, index corruption, incompatible version, and rebuild interrupted before swap. Use privacy-preserving synthetic or explicitly opt-in local fixtures; the brief prohibits a private-notebook benchmark. The target responsiveness thresholds and what level of eventual staleness is acceptable are product-owner decisions, not claims this discovery can benchmark.

## Bounded integration sequence

1. Inventory the actual canonical store, stable note IDs, tag relations, SQLite library/version/build flags (if applicable), platform constraints, and note update callers. No source repository/callers were identified by the brief alone; this remains an implementation-stage obligation.
2. Agree on query semantics, saved-query format, supported scripts/search forms, stale-result wording, freshness budget, failure visibility, and measurable latency thresholds.
3. Implement a reference scan/query fixture with 20,000 synthetic notes and stable IDs. Record baseline query/edit/open/rebuild measures; run correctness cases before selecting an engine.
4. Prototype the smallest realistic FTS5 and/or Tantivy option against the current store. Compare asynchronous update and shadow rebuild with concurrent edits; select only from measured correctness, latency, resource use, build compatibility, and maintenance.
5. Add the durable revisioned outbox, single bounded worker, idempotent update/delete processing, progress/error state, and exact-ID result lookup. Keep note editing independent of index failures.
6. Add a versioned query/analyzer contract and tag-ID filters. Run multilingual fixture and rename/edit/delete/query-parser regression tests.
7. Add shadow-generation rebuild, durable catch-up replay, atomic cutover, restart/corruption recovery, and last-known-good fallback. Verify the full fault matrix before calling results complete.
8. Expose concise incomplete/error/rebuild status and retry action; tune batch/commit/debounce/checkpoint policy from the 20,000-note measurements. Do not implement semantic search or rewrite the editor in this sequence.

## Brief-clause coverage and remaining decisions

- Search text, filter by tag, follow each result to the exact note: stable ID, current-store joins, tag IDs, and result revision are proposed above.
- Repeated rename/edit/delete during indexing: immutable IDs, revisions, durable outbox/tombstones, coalescing, stale-hit suppression, and fault tests are proposed.
- Copied excerpts in different scripts: analyzer-specific limits and test fixtures are listed; no universal coverage promise is made.
- Twenty thousand entries and usefulness during indexing: compare measured candidates with an explicit pending watermark, last-good generation, and bounded background worker.
- Saved query title change: store expression/AST and version separately from titles; a “this note” target is by ID. Whether title-terms are expected to follow renames is an owner decision.
- Data store authoritative; no hosted search; no permanent filename identity; no silent index failures: each is an invariant above.
- Optional semantic search: deferred pending lexical evidence and an owner decision on local model cost.
- Compare lexical/index approaches; measurements; bounded integration: alternatives and measurement/integration sections above.

## Open product decisions

1. What note-store engine and stable immutable note ID already exist, and can note mutation plus an outbox row commit atomically?
2. What “literal search” means by default: all terms, any terms, phrase, prefix, or substring; is advanced syntax in scope?
3. Which exact scripts/languages and normalization equivalences are required for the copied excerpts?
4. Should tag filters be AND or OR when several are selected, and do saved queries pin tag IDs or resolve renamed/removed tags by another rule?
5. What stale window, saved-query migration behavior, failure UI, and rebuild cancel/pause semantics are acceptable?
6. What latency/throughput/resource targets and packaged SQLite/Tantivy versions/platforms are required?
7. Is there evidence for semantic retrieval after lexical evaluation, and what local inference/storage budget is allowed?
