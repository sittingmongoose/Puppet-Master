# Incremental search for a research notebook

A desktop research notebook already stores notes, tags and links between notes. Design its indexing component so users can search text, filter by tag and follow a result back to the exact note. Notes may be renamed, edited repeatedly or deleted while an index update is running. Some notes contain copied excerpts in different scripts, and a notebook can have twenty thousand entries. The application must remain useful while indexing catches up.

Research index layout, update scheduling, stable identity, query interpretation and recovery from a broken or outdated index. A saved query should retain its meaning after a note title changes. Explain how users learn that results may be incomplete and how an explicit rebuild avoids blocking editing. The notebook's data store is authoritative; search results must not become a competing copy of note content. Do not send note text to a hosted search service, silently omit indexing failures, treat a filename as permanent identity, or promise language coverage without investigating tokenization behavior. Semantic search is optional and must justify its costs if recommended. Compare viable lexical and indexing approaches, identify which measurements would determine responsiveness, and propose a bounded integration sequence. We need source-backed planning, not a benchmark on private notebooks or a full rewrite of the editor.

Produce a research-backed software proposal, not an implementation. Explore relevant primary documentation, repository code, callers/tests, and issue-to-fix or release history where consequential. Compare feasible alternatives without assuming a winning product. Distinguish proposed validation from work actually executed.
