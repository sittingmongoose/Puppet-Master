# Brief-only discovery: incremental search for a research notebook

**Stage:** ER13 investigator, B03-P01-control  
**Discovery cut:** before exact-plan release; the withheld plan was not read or inferred.  
**Access time:** 2026-10-12 01:09 UTC.  
**Evidence boundary:** The released brief describes a desktop notebook with tags, note links, rename/edit/delete races, excerpts in different scripts, and about 20,000 entries. No target application repository, storage schema, callers, or test suite was identified in the provided inputs. I did not inspect the unrelated Puppet Master workspace. I reviewed primary SQLite and Tantivy documentation, versioned Tantivy example/code, SQLite release/bug records, and Tantivy issue history. No private-notebook benchmark or executable code was run.

## Discovery finding

Treat search as a disposable, local derived index. The canonical notebook remains the only source of note text and current title/path. Persist a stable note identifier that survives rename and move, and return that identifier from search. When a user opens a hit, resolve it against the canonical store again; display its current title and location, and handle a deleted note as stale rather than opening an index copy. Store note text nowhere else as result content. A lexical index necessarily retains terms/postings; an external-content FTS5 index can read text from the canonical table, while a separate FTS5 sidecar can be contentless and store only postings plus an ID mapping. With Tantivy, index only searchable terms and a stable ID field; omit stored title/body fields, and fetch current content from the notebook.

There are two feasible embedded local engines and one necessary baseline:

| Approach | Where it fits | Benefits | Conditions / costs |
| --- | --- | --- | --- |
| Canonical-store scan (baseline and correctness oracle) | Any store; 20k notes is not enough information to rule it out | No persistent search state, no index rebuild drift, direct current title/body and tag filtering | Query cost grows with total indexed text and may hurt typing responsiveness; test off the UI thread and use measured thresholds. It is not a promise of adequate speed. |
| SQLite FTS5 | Strong first spike if the notebook already uses SQLite | Lexical ranking, phrases, prefixes and Boolean queries; relational tag filtering; FTS is in the same local database or a local sidecar | Confirm the shipped SQLite runtime includes FTS5. External-content mode avoids another text copy but requires same-database synchronization and consistent rowids. A worker-written sidecar can be contentless, but needs its own ID map and durable outbox. SQLite WAL permits concurrent readers and a writer, but still only one writer; same-database indexing can contend with note edits. |
| Tantivy 0.26.2 | Rust desktop application where a separate local index directory and custom tokenizer control are acceptable | Embedded library, segment-based inverted index, writer/reader commit lifecycle, customizable tokenizers; no hosted service is required by this architecture | Index is separate from the canonical store, so durable outbox/replay and rebuild lifecycle are app responsibilities. Updates are delete-plus-reinsert by term; Tantivy does not enforce unique IDs. A commit is the publication/durability boundary. Assess target OS and exact dependency version against issue history. |

A network search service is outside the permitted design because note text must not be sent to a hosted service. A separate local service process would add deployment, lifecycle and recovery cost without a need established by this brief. Semantic search is not recommended for the first release: literal terms, phrases, tags and back-links are the defined job. Local embeddings would add model/runtime size, compute, storage and a second ranking path while still requiring lexical search for exact identifiers; hosted embeddings are incompatible with the privacy constraint. Revisit only with an owner-approved use case and a measured on-device cost/quality proposal.

## Text, tokenization and query interpretation

Do not promise multilingual coverage from the word “Unicode.” SQLite FTS5 defaults to unicode61, based on Unicode 6.1: contiguous Unicode letters, numbers and private-use characters form tokens; punctuation and spaces separate them. It case-folds under Unicode 6.1 and removes diacritics from Latin-script characters by default. It does not define word-boundary morphology for every writing system. SQLite documents a rare multi-diacritic compatibility exception for remove_diacritics=1; option 2 changes it, but would still not supply general language segmentation. A 2020 SQLite forum report on Polish ł/Ł notes that default diacritic removal does not cover that character and points to a custom tokenizer. Tantivy 0.26.2’s default tokenizer splits on whitespace/punctuation, lowercases, and drops tokens longer than 40 characters; its English stemmer is slower and English-specific. A historical Tantivy CJK issue described query parser/tokenizer mismatch even with a custom segmenter. That report is a test warning, not proof that the same defect persists in 0.26.2.

Before selecting any tokenizer, build synthetic fixtures for each script the product intends to support: words with/without spaces, combining and precomposed forms, diacritics, punctuation, apostrophes/hyphens, one- and two-character terms, long tokens, copied mixed-script excerpts, and the user’s expected prefix/substring behavior. Test indexing and query tokenization together, including renames and edits. If a tokenizer cannot meet a language’s expected behavior, say so plainly or add a versioned custom/language-aware tokenizer with migration and rebuild support. SQLite’s trigram tokenizer is a separate substring tradeoff: general substrings and indexed LIKE/GLOB can help identifier or fragment search, but full-text terms shorter than three Unicode characters cannot match; patterns with no three-character literal can scan. Keep trigram as a measured optional mode, not a silent replacement for lexical word search.

Persist a small, versioned query representation instead of persisting engine-specific syntax as the product contract. For example, store the original literal text, parsed clauses, explicit match mode, selected fields, stable tag IDs and optional stable note IDs, plus parser/tokenizer schema versions. Compile it to FTS5 or Tantivy queries. Default to a clearly explained all-terms mode and make phrase/prefix syntax explicit. FTS5 and Tantivy both have their own query grammars; report parse errors visibly and never silently widen an invalid query to match everything. Bind SQL values as parameters in addition to validating the FTS query language. A saved query must not store a title string as the identity of a note or tag. A title rename leaves the saved query definition and its stable IDs unchanged; if it searches title text, its result set may naturally change when that title changes. Render the current note/tag label from the canonical store.

## Identity, updates and recovery model

Assign every note a permanent opaque ID independent of filename/title/path. Give tags stable IDs too. Keep a monotonically increasing note revision and a durable change sequence. A rename is an upsert for the same note ID; repeated edits coalesce to the latest revision; deletion persists a tombstone until the index acknowledges it. The update worker reads the current canonical note by ID rather than indexing stale text captured in a UI event. Before committing a batch, it verifies that each fetched revision is still current; if not, enqueue/re-read the newer version. Operations are idempotent by stable ID plus revision. Record a durable outbox or change log in the same transaction as the authoritative edit when the store allows it. On restart, replay from the last acknowledged sequence. Never depend on filenames as identifiers.

Use a single bounded background writer with debounce/coalescing by note ID and size/time-limited batches. Prioritize keeping edits responsive over draining an unbounded queue. Record per-note failure state, attempts, last error category and retry time; retry transient failures with capped backoff, surface permanent failures, and provide retry/rebuild actions. Do not advance the completeness watermark past an unhandled failure. Search remains available against the last good index, but the UI must label it as incomplete/stale. Show indexed/total counts, oldest pending change or lag time, last success, and failed-note count; link to details and offer retry. Each result carries stable ID and indexed revision. On open, fetch the current note; deleted or unavailable IDs are removed/retried and surfaced as stale. Tags use an exact stable-ID relation, not full-text token matching.

For SQLite FTS5 external-content mode, FTS5 reads indexed columns from a table/view in the same database; the app must keep postings consistent, typically with insert/update/delete triggers. Triggers do not backfill pre-existing rows, so the initial population requires rebuild. The official rebuild command deletes the existing FTS index before rebuilding it from the content table. This route can make a note edit and its index update atomic, but index work then shares SQLite’s single-writer path and may lengthen edit transactions. Benchmark edit latency before choosing it. For a truly asynchronous sidecar, use a contentless FTS5 table in a local index database with a stable-ID mapping and a canonical-store outbox; its text fields are unavailable on reads, and its documented rebuild command is unavailable, so build a new sidecar generation from the canonical store. Do not assume separate ATTACHed SQLite databases commit atomically as a set. For Tantivy, batch delete-by-ID plus add-current-document and commit; reload readers according to the chosen policy. Commit does block and is the publication boundary, so feed it bounded batches and acknowledge the source outbox only after a successful commit.

A user-requested rebuild is a background generation change, not an editor-wide lock. Leave the active index searchable and label its status. Build a shadow index from a consistent canonical snapshot/watermark in a separate generation, while edits continue into the durable change log. Apply all changes after the snapshot watermark to the shadow index, reach a cutover barrier, verify IDs/counts/integrity, and atomically switch the active-generation pointer. Keep the old generation until the new one is opened successfully; on failure/cancel, preserve the old index and an actionable error. Page through source notes in bounded batches and throttle CPU/I/O. If the canonical store cannot provide a consistent snapshot and ordered change sequence, that capability must be designed before promising non-blocking rebuild. After a tokenizer/schema migration, rebuild the derived index from the canonical store and retain the previous searchable generation until swap. Never reconstruct note content from the search index.

## Responsiveness measurements and proposed checks

**No performance measurements or validation checks were executed.** Once the actual store and app are identified, compare the scan baseline, FTS5 and Tantivy using deterministic synthetic data, including 20,000 notes plus larger headroom, with documented counts and body-size distributions. Proposed metrics are editor save/rename/delete p50/p95/p99 while indexing and rebuilding; search p50/p95/p99 cold and warm for common, rare, no-hit, phrase/prefix and tag-filtered queries; indexing queue age/depth and drain throughput; rebuild completion and cancel latency; CPU, memory, index size and SQLite WAL growth/checkpoint behavior. Set product budgets before deciding. Test exact-result quality for each declared script, tag intersections, stable-ID rename/move navigation, rapid edits during worker reads, delete-vs-upsert races, duplicate events, crash/restart before/after commit, corrupted/missing index, per-note failures, rebuild interruption, and saved-query load after title/tag rename and parser-version migration. Compare search result IDs to a canonical scan as a proposed oracle.

## Bounded integration sequence

1. Identify the actual note store and callers. Inventory stable IDs, edit/delete transaction points, tag schema, note sizes, supported OSes, current search behavior, and the SQLite runtime/FTS5 build if SQLite is used. This task did not identify or inspect an application repository, so no product integration fact is asserted.
2. Write acceptance budgets and representative synthetic language/query fixtures. Implement a simple scan as the correctness oracle and capture its responsiveness without using private notebooks.
3. Add a search adapter that returns stable IDs/revisions only; resolve titles, snippets and note content through the canonical store. Persist saved queries as versioned data with stable IDs.
4. Prototype FTS5 and Tantivy only if the existing store/runtime permits both; compare edit contention, query quality, update lag, rebuild and recovery against the same fixtures. Choose conditionally from evidence; the documentation alone does not settle the winner.
5. Implement the durable outbox, bounded coalescing worker, revision checks, retries, visible incomplete state and delete tombstones. Never submit note text to a hosted service.
6. Add the shadow-generation rebuild, catch-up barrier, integrity check and atomic swap. Exercise interruption/restart while editing.
7. Ship lexical text and exact tag filtering first. Reconsider custom tokenizers or semantic/local embedding support only after language evidence and an explicit owner decision.
