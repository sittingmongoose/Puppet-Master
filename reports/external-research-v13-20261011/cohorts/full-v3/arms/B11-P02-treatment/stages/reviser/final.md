# Component proposal — rehearsal cue-sheet revision and publication

## Recommendation

Use a local-first, operation-aware cue document in the Rust desktop app, with Automerge Rust 0.12.0 as the leading candidate core, a crash-safe local document store on each laptop, and a modest authenticated team relay for synchronization. Keep cue records separate from their order, give every cue and comment a stable ID, and represent reorder actions as explicit placement intents. The relay reconciles document history; it never chooses a whole sheet by wall-clock timestamp or instructs a device to replace its local replica.

This recommendation is conditional. Automerge’s versioned Rust API exposes competing values and historical reads, but the application must supply trusted author attribution, an intelligible move-resolution policy, durable stateful-sync recovery, and a separate publication boundary. Those are not delivered by choosing a CRDT. The reconnect plan below is a concrete proposed contract, not a tested implementation. If it fails the required fault-injection cases, compare Yrs 0.28.0 with an application-owned conflict log before choosing a core. See [R01–R08] and carried [S01–S17, C01–C11] in the [source index](sources/index.md) and [source map](source-map.json).

Editing, durable local saves, comments, and conflict review remain available without a network. Relay synchronization and publication refresh require a connection, but an always-online editor, enterprise account, or new chat product is not required. This is a component proposal only; no rehearsal service is built or deployed here.

## Brief scope and boundaries

The component serves a small live-event crew editing ordered cues, timing notes, role assignments, and cue-anchored discussion from laptops that may be disconnected during rehearsal. It must preserve useful independent work after reconnect, expose incompatible work for an intelligible human decision, and keep comments attached to their cue across reorder. Staff need an explicitly approved run sheet that is separate from the changing rehearsal draft and has a visible version identity.

The relay is a synchronization peer and durable recovery point, not the only copy or a chat product. Actual cue count, sheet size, rehearsal size, relay location, authentication policy, retention, and backup window remain unknown. They are measurement or owner inputs; their absence does not remove feasible mechanism research.

## Proposed data and interaction model

### Cue identity, order, comments, and assignments

Use one versioned collaboration document per sheet. Store each cue under a generated, stable `cue_id`. Its record carries timing data/notes, text, role assignments, and a deletion/tombstone state. Store order separately. Never use a visible row, cue label, time, or current position as identity. Preserve IDs across reorder and structured export/import.

A comment/message has its own `comment_id`, `cue_id`, author metadata, time, body, and optional `reply_to`. Reordering changes placement only. If a cue is deleted, retain a tombstone and keep its thread visible on a deleted-cue entry; never retarget it to the cue that inherited its old row. Restore/archive behavior is for the owner. If owners later require comments anchored to a character range inside note text, use a separately tested stable text-position mechanism; a text cursor is not a substitute for cue identity. [S02, S14]

### Reorder and placement policy — M2 accepted and specified as proposed app behavior

Do not claim that Automerge supplies a high-level atomic cue move. The versioned Rust Transaction API exposes general list insert/delete/splice operations, while its implementation groups transaction operations into a change; neither source defines the app’s concurrent move semantics. A single local user move should be committed together with its placement intent, but that local transaction does not make concurrent remote moves semantically atomic. [R03–R04, C03, S09–S10]

Represent each insertion or move as an immutable intent with a unique `move_id`, `cue_id`, source and destination neighbor IDs, the base document heads seen when the user acted, the actor, and local time. Keep every intent in history. For rendering a provisional draft:

1. Start from the order at the selected common/base heads. Process causally dependent intents in history order; use stable `move_id` ordering only to break ties between concurrent intents, so every replica can show the same provisional preview.
2. For each intent, require its cue and destination anchors to be live and internally consistent. Remove that cue from the provisional sequence before reinserting it between the requested neighbors. This keeps one visible placement per cue. A deleted/missing anchor, deleted cue, or reversed/incompatible neighbor pair is marked unresolved; keep the cue at its last valid preview location rather than guessing a new anchor.
3. Retain concurrent moves of the same cue as separate candidates. The tie-broken preview is explicitly labeled provisional, never a human-approved winner. If independently moved cues create incompatible placement constraints, detect the affected intent set, show the complete set as one order issue, and keep the last valid order for the affected cues until a human resolves it. A move-versus-delete is also an issue. Insertions into the same gap may use a stable operation-ID tie-break for convergence, with the resulting order visible for review.
4. A resolution is a new shared operation naming the exact move candidate IDs and heads it reviewed and the chosen destination/order. It changes the materialized order while retaining the original intents and decision history. Any later unseen concurrent candidate reopens the issue. Publication stays blocked while a publication-relevant order issue is open.

This provides a deterministic provisional display and a human route for same-cue moves, changed/deleted anchors, move/delete races, and incompatible multi-cue ordering. It remains application logic and must pass tests for cycles, duplicates, endpoint insertions, reverse insertion, and stale neighbors before release. The 2024 move-aware JSON CRDT paper explains why naïve concurrent moves can create duplicates or cycles and says Automerge integration was planned; it does not establish a released Automerge move API. [R04, R07–R08, C03–C06, S09–S10]

### Field, text, and conflict decisions — M1 and M4 accepted

Merge independent field edits. For a same-property conflict, query the Rust API’s full candidate set and show all values, including the operation IDs that created them. For text, emit granular insert/delete operations; do not replace a stale full note. Disjoint edits may merge. If concurrent changes overlap a timing instruction, show the common-base context and inline alternatives, then require a human to choose or edit a combined result. Concurrent replies with new IDs append independently; edits to the same existing comment use the same conflict flow. JavaScript text-guide frequency advice is not proof that the Rust/Slint adapter or a semantic overlap detector works; implement and validate those separately. [S02, S07, C02, C09, R02]

**Trusted attribution (M1).** Automerge author metadata is optional, opaque, and not authenticated crew identity. Before authoring, the app must bind a crew member’s stable author ID to a locally held, relay-issued device credential. Sign offline operation batches or an equivalent change-to-actor record with that credential. On reconnect, the relay verifies the signature and current membership before marking an author as verified; the UI displays a verified crew identity or an explicit unverified/unknown source, never a name inferred from device time or an untrusted document field. Preserve the authenticated identity-to-author mapping alongside operation history so a candidate ID can be traced to a person. If verification fails, retain the content as unverified local work and do not silently attribute or publish it. The minimal credential, revocation, and identity-retention policy is an owner/security decision. [R01–R02]

**Resolution scope (M4).** A decision records the exact candidate operation IDs and the document heads against which the reviewer decided, plus whether the person kept, edited, or explicitly rejected each candidate. It closes only that set. If an unseen concurrent write arrives, reopen the issue and block publication until it is reviewed. A later causally dependent edit is processed as a new current value; it does not erase the audit record. A deterministic CRDT winner is never an implicit human resolution. [R02, R06]

### Offline durability and reconnect recovery — M3 accepted with an explicit contract

Each laptop commits the document locally before showing “saved on this device.” Load that replica and allow edits, comments, and review while disconnected. Keep relay state distinct from local-save state.

For the chosen Automerge SyncDoc path, give each client/relay peer pair a durable session epoch, ordered frame sequence, and protocol State. Persist the serialized State and the exact generated message bytes plus sequence number in one durable outbox transaction **before sending**; do not generate a later stateful frame for that peer while an earlier frame remains unacknowledged. The receiver applies the incoming frame, updates the document and peer State, records its accepted sequence/deduplication entry, and commits those together before acknowledging. A generated reply and its updated State are likewise stored together before transmission. The sender retains and resends the identical frame on a timeout or reconnect. A duplicate already-committed sequence receives the prior acknowledgement without reapplying it to an advanced protocol State. Buffer/request retry for out-of-order frames.

The local app must atomically persist the document, peer State, and outbox; the relay must durably commit its document, per-client State, accepted-frame record, and any reply outbox before acknowledging. If either side loses the exact frame/State pairing, sees a sequence gap it cannot recover, or cannot determine whether an unpersisted message was delivered, abandon that peer epoch and reset protocol State on both ends, then handshake from the durable replicas. Never resume with one side’s stale State, replace a document, or report “synced” merely because a local frame was generated. Show “relay accepted” separately from “other device caught up.” The data store, atomic-write mechanism, retention of outbox records, and relay hosting remain implementation decisions.

This is a proposed safe envelope based on the documented protocol requirement and the Rust lost-message report, not proof that this particular relay will work. The issue report has no target crate version and does not show that every release fails; the maintainer says the stream must be reliable and state reset if a message may have been dropped. Reproduce the case against the pinned crate and exact adapter before release. [S03–S05, C08, R01, R05]

### Approval, viewing, and export

Keep draft and published records in separate storage namespaces and views. For Publish, capture a specific set of document heads; validate required fields and unresolved publication-relevant conflicts at those heads; materialize exactly that historical state; render a canonical run-sheet projection; compute its digest; and obtain an authorized approval over that revision/digest. Atomically create a new immutable record with publication ID, sheet ID, heads/revision ID, schema version, digest, approver, and approval time. If approval is retried for the same request, return the same record rather than creating a conflicting duplicate. Later draft edits never alter a record; another Publish creates a new ID. A human approval of the exact frozen projection, the authorized approver role, canonical encoding, and transactional persistence are application requirements, not CRDT features. [S02, S04, R01–R02]

Stage viewers read approved records only, not the mutable draft. Show the publication ID/time in the app and printed output. An offline viewer shows which cached record it has and its offline state. After reconnect, offer any newer approved record for an explicit switch; do not claim “latest” when offline. A read-only sync State may limit incoming document changes in one direction, but it is not an access-control list. Enforce relay permissions and publish authorization separately. [S04]

Define a versioned structured interchange format with cue IDs, order/placement intents, timing/text, role assignments, comment IDs and cue references, tombstones, schema version, and publication ID when applicable. Test imports for ID preservation and duplicate handling. A readable export can group notes, comments, and roles under cue labels while retaining stable IDs in metadata. The owners decide which comment classes are included in an approved staff sheet, which belong only to the rehearsal archive, supported formats, redaction, local cache lifetime, history retention, backup, deleted-history policy, and schema/client migration.

## Alternatives and trade-offs

- **Yrs 0.28.0:** A plausible Rust alternative with Yjs-compatible updates, documented duplicate/out-of-order update handling, and stable text anchors. Its source-map-backed documentation reports a deterministic map winner, not a complete human conflict queue; the app would still need the author, move, resolution, and publication mechanisms above. The critic’s route could not open the versioned Yrs API pages, so those API details are carried source-map findings, not independently revalidated in this reviser pass. The v0.27.3 head-insertion/StickyIndex fixes are useful regression cases, not evidence that other ordering bugs are absent. [S11–S15, C10]
- **Central edit lock or serialized editing:** Simpler if the crew can guarantee one writer at a time, but it prevents useful concurrent offline edits unless users branch locally anyway. Keep as an owner option only if actual rehearsal practice changes that requirement.
- **Manual whole-sheet branching:** Useful for explicit restore/compare or a very small team willing to reconcile manually. It still needs stable IDs, field-level conflict review, order semantics, and comment/export rules; the plan’s timestamp winner and receiver replacement would lose useful work.
- **Custom operation log:** Can encode cue moves and resolutions directly, but the component must supply causal replay, conflict handling, text collaboration, history, deduplication, recovery, and publication snapshots. It is more machinery than the first proposal warrants.
- **Plain JSON or file sharing:** Works as backup/export and may suit serialized, online editing. It does not itself provide offline concurrent merge semantics or anchored-comment preservation.

## Owner decisions and remaining unknowns

1. Which crew roles may resolve conflicts and publish? Is a coordinator assigned, and how is that person authorized?
2. Are times relative cue offsets or wall-clock values? What precision, display zone, and time validation are required?
3. Are comments cue-level only, or may they anchor to a text range? What should happen to threads on deleted, restored, or archived cues?
4. Which roles and comment categories appear in a stage-approved run sheet versus rehearsal-only exports? What redaction and export formats are required?
5. Where may the relay run, what connectivity is normally available during rehearsal, and what minimal identity or local credential scheme is acceptable?
6. What local-cache, backup, history-retention, and deletion/privacy periods are required?
7. What are actual cue/sheet counts, realistic history growth, number of simultaneous editors, backup/recovery window, and load/reconnect targets?
8. What prior formats and older-client/schema versions must import or interoperate?

No defaults are invented for these facts. Measure cue counts and workload; do not use their current unknown state to skip mechanism work.

## Validation proposals — not run

1. **Disconnected independent work:** Start two devices from common heads; disconnect; edit separate cues/fields, insert and reorder cues, add comments, close/reopen an app, then reconnect. Verify both histories survive, comments remain on the correct cue, all replicas converge, and local save status does not imply relay acceptance.
2. **Authorship and conflict attribution:** Create concurrent same-field changes from two authenticated offline devices. Verify every candidate is associated with a signature-verified member, an unknown/forged author remains visibly unverified, and author mappings survive restart and export/import.
3. **Scalar and resolution races:** Conflict on role/time, show all candidate operation IDs, resolve exactly the displayed set, then merge a third concurrent value. Verify the issue reopens, stale resolution does not suppress it, and publication remains blocked until resolved.
4. **Move semantics:** Test same-cue competing moves, independent multi-cue moves that form inconsistent/cyclic constraints, move versus delete, deleted or moved neighbor anchors, simultaneous inserts in one gap, reverse insertion, and first/last endpoints. Verify deterministic provisional display, no duplicate cue, no silent wrong anchor, complete candidate list, and publication blocking for unresolved placement.
5. **Lost frame, crash, and reconnect:** Reproduce the Rust issue’s generated-but-lost message followed by an offline conflicting edit. Crash each side before outbox commit, after outbox commit but before send, after receiver durable commit but before ack, and after ack. Verify exact-frame retry/deduplication, epoch reset after uncertain state, bounded termination, no document replacement, convergence, and preserved conflict candidates.
6. **Publication isolation and authorization:** Publish P1 at captured heads, edit the draft, and verify P1 bytes, ID, heads, and digest do not change. Confirm the approver authorized the exact frozen projection, a retry is idempotent, P2 requires a new explicit approval, unresolved conflicts block, and a viewer cannot mutate the publication.
7. **Offline viewing and interchange:** Cache P1, disconnect, verify ID and offline status, reconnect with P2 available, and require an explicit switch. Round-trip cues, order, roles, comments, tombstones, and publication references through structured import/export; inspect the readable staff export for required information and redaction.
8. **Scale and recovery:** With measured representative cue counts and realistic history, measure local save/load, document growth, relay persistence, reconnect time, frame volume, and forced-interruption recovery. Set retention and backup targets with the owners.

These are future validations. None was run in this stage.

## Criticism dispositions

| Criticism | Disposition |
|---|---|
| **M1 — Candidate authorship may be absent/untrusted.** | **Accept and amend.** Make Author metadata mandatory for locally verified work, bind it to authenticated relay membership through a signed device identity, preserve the identity mapping, and label unverifiable work. Automerge author metadata alone is not authentication. |
| **M2 — Move intents lacked a complete resolution algorithm.** | **Accept and amend.** Define causal ordering, deterministic provisional tie-break, anchor validity checks, cycle/incompatibility detection, exact candidate review, and publication blocking. This is a proposed app rule; no source establishes a shipped Automerge cue-move API. |
| **M3 — Lost-message recovery had no durable boundary.** | **Accept and amend.** Persist exact frame bytes with matching State before send; persist received document/State/dedup record before ack; replay exact frames; reset both States and start a new epoch if pairing or delivery is uncertain. Validation remains unrun. |
| **M4 — Resolution could hide a later concurrent candidate.** | **Accept and amend.** Scope each decision to exact candidate operation IDs and observed heads; a newly arrived concurrent candidate reopens the item and blocks publication. |
