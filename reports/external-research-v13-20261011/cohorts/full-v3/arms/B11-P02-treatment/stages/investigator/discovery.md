## Scope derived from the brief

A desktop rehearsal component must keep ordered cues, timing notes, role assignments, and cue-anchored discussion useful across disconnected laptop edits. Reconnect must retain useful work and identify incompatible changes for human judgment. Stable cue identity is essential so reordering cannot move a comment onto a different cue. An approved run sheet is an explicitly published version, separate from the changing rehearsal draft, and staff must see which version they have. The design may use a modest team relay but must not require an always-online editor, an enterprise account, or a chat product. Actual cue count is unknown and remains an input for later measurement, not a reason to skip mechanism research. Deliver a component proposal; do not deploy the rehearsal service.

## Initial account after the ordinary research pass

A plausible baseline is one local-first structured document per sheet, with immutable cue IDs, cue content stored separately from an ordered sequence of IDs, and comments carrying a cue ID rather than a list index. Use CRDT operations to combine independent offline edits and keep local persistence available without the relay. Add an explicit conflict review surface for same-field writes and competing cue placements. Publish a separately stored immutable projection at a captured document revision; a new publication requires a deliberate approval action. This is a research hypothesis, not a product decision, and remains subject to the exact plan.

Automerge's Rust core is a strong candidate because its Rust API exposes all competing values for a map/list property and has per-document change history. Its standard sequence semantics do not supply an atomic cue-move operation, and its Rust sync protocol has an explicit reliable in-order transport requirement. Yrs is a plausible Rust alternative with idempotent/commutative updates, missing-predecessor buffering, and persistent relative text positions; its documented map tie-break alone is not a human-facing conflict workflow. A manual branch-and-merge workflow or centralized edit lock could be simpler in other operating conditions, but a lock conflicts with disconnected concurrent editing and plain-file merging needs its own structured identity, ordering, and comment logic. See [S01–S08](sources/index.md#automerge-rust-core-and-data-model), [S11–S15](sources/index.md#yrsyjs-alternative), and [S16](sources/index.md#storage-and-network-alternatives).

## Evidence findings relevant to the original obligations

- **Stable identity and ordered cues.** Model cue entities by generated stable IDs; use a separate order structure. Never key comments or role assignments by visible row number. Automerge recommends fine-grained entity-map plus ID-list changes instead of replacing a whole nested object, and its ordinary list model does not define a first-class move [S08, S10]. Yjs also warns that an integrated shared type cannot simply be moved; this supports keeping the cue record outside the reorderable list [S15].
- **Text and notes.** Automerge provides collaborative text sequences, but the input adapter must emit editing operations. Its JavaScript guide warns that infrequent full-value diffs merge less well than frequent splice updates; this is a UI-adapter concern to verify against the native Rust API [S07]. CRDT text convergence is not the same as deciding whether a merged timing instruction is intelligible. Keep text candidates/branch context available and flag overlapping edits for review; do not silently call a deterministic character merge a human decision.
- **Comments.** The brief requires cue-level anchoring, so a comment thread can carry cue_id and remain attached when order changes. If owners later require anchoring to a character range inside note text, stable relative positions such as Yrs StickyIndex track a referenced text block through concurrent inserts; they are a refinement, not a substitute for cue identity [S14].
- **Conflict semantics and presentation.** Automerge resolves same-property concurrent assignments to one deterministic visible winner while preserving alternatives accessible through get_all; a human UI should display every candidate, author/source, and action, and record an explicit resolution [S02, S06]. The winner is not wall-clock “latest” [S06]. Automerge text and sequence operations often merge without a same-key conflict, so a component still needs overlap/placement rules and visible review markers [S07, S10].
- **Moves.** Two concurrent remove/reinsert moves of the same cue can produce duplicate placements; a paper proposes a move-aware JSON CRDT algorithm to address duplicates/cycles, but its 2024 abstract says integration into Automerge was planned, not that a released API exists. The inspected Rust 0.12.0/current list API evidence does not establish a native atomic move primitive [S09, S10]. Retain move intents with cue ID, destination neighbors, base heads, and actor; present same-cue concurrent destinations as a decision and keep publication blocked until resolved.
- **Retry and reconnect.** Automerge Rust 0.12.0 apply_changes ignores changes already applied. Its sync protocol, however, expects a reliable in-order stream and per-peer state [S01, S03, S04]. Open Rust issue #1284 shows an offline-generated but dropped message followed by a conflicting edit can leave the sync loop nonterminating; the maintainer clarifies that possible message loss requires resetting sync state [S05]. Persist each device's document before sending; use an ordered WebSocket connection; when a disconnect could have dropped an in-flight message, discard/rebuild that peer's protocol state and re-handshake (or retain the exact message/state pair). Bound the loop and do not mark an update delivered before durable relay storage. This is a proposed design rule pending fault-injection validation, not a claim that the future relay was tested.
- **Revision and publication.** Automerge Rust exposes document heads and historical reads at a specified head set [S02]. The component can capture heads, materialize the cue sheet at those heads, and atomically store an immutable published projection with a revision ID, digest, approver, and timestamp. Keep draft and published stores/views separate; ordinary rehearsal changes cannot mutate a published artifact. State::new_read_only can prevent an Automerge sync-state receiver from applying incoming changes, but is not a substitute for relay authorization or publication storage policy [S04].
- **Local storage and relay boundary.** The CRDT core is storage/network agnostic; automerge-repo is documented as JavaScript plumbing, so a native Slint component would need local persistence and a small Rust relay/sync adapter or choose another qualified transport [S03, S16]. The public Automerge demo relay is explicitly not private or production reliable; it is not a production recommendation [S16]. Automerge documents retain change history, with performance depending on the actual workload; retention, backup, deletion/privacy, and cue-count measurements remain design inputs [S08].

## Candidates and open inputs before the plan release

**Candidate A — Automerge Rust core plus a small relay.** Best fit found for native Rust and explicit conflicting-value inspection/history. Costs: own persistence/network plumbing; moves need app-level intent and review; reset/rehydrate sync state after possible frame loss; full-history storage policy and workload testing. **Candidate B — Yrs 0.28.0.** Best fit found for Yjs-compatible binary updates, duplicate/out-of-order update handling, and stable text anchors. Costs: documented deterministic map winner is not a human-readable conflict queue; app must retain alternatives and build move decisions; shared type constraints still favor separate cue entities/order. **Other alternatives** are serialized central editing, plain files with manual merge, or a custom operation log. They trade away concurrent offline edits or add significant bespoke merge logic. No candidate is locked before the exact plan review.

Unresolved user-specific facts include actual cue counts and rehearsal size, identity/authentication and publish authority, whether timing is wall-clock or relative, whether comments ever anchor to a text range, how deletion/orphaned comments should behave, which fields appear in the printed/staff run sheet, retention of deleted notes/history, relay availability/network constraints, backup expectations, and compatibility/migration requirements. These remain questions, not invented defaults.
