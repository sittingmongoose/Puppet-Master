## Product recommendation

Add a narrow project attachment-reference component. A reference is the notebook's durable record of the user's choice; its locator says where the file was last found; identity evidence describes what the OS or a content check observed. Keep those as distinct fields. The record ID identifies the notebook reference, not a file on disk. A path is a locator, not proof that the file at that path is still the intended object.

Adding a reference records the existing file and does not copy its bytes. Preserve a stable record ID and a user-facing display name. Use a project-relative locator only when a supported, platform-aware containment check establishes that the selected target resolves within the project tree. For external files, store a local absolute locator or, optionally, a user-defined root key plus a relative suffix. Named-root mapping is useful when a user keeps the same tree in a different place on another machine, but requires explicit per-machine setup. Keep the display name separate from the locator.

On macOS, a bookmark can be a useful move/rename and, when sandboxed, user-granted access aid; it needs stale-bookmark handling and balanced access calls. It is not a portable project identifier. Apple also documents that fileResourceIdentifierKey values are not persistent across system restarts. Windows file IDs can compare currently accessible files when paired with their volume serial, but are machine- and filesystem-scoped evidence. Linux inode numbers are unique only within one filesystem. Linux opaque file handles have filesystem support and stale-handle limits; opening by handle requires CAP_DAC_READ_SEARCH. These are optional, namespaced, best-effort hints. None is the cross-platform attachment ID. [S08–S13](sources/index.md#s08)

A full content digest can confirm that candidate bytes equal a previously measured snapshot; it does not show that the user intended that file object. Hashing reads the entire file and can cost I/O and time. Do not hash automatically when linking. Offer a clearly labeled local verification action or an owner-approved opt-in; record algorithm and observation time, handle concurrent modification, and explain that later edits change the result.

At open or explicit status refresh, probe the saved locator with the access scope the user granted. Report a timestamped observation, not a continuing guarantee. Distinguish at least: not checked; reachable at the saved locator; absent at a location that could be checked; volume or device offline/unavailable; access denied; path reachable but identity evidence changed; and one or more possible replacements awaiting review. A lookup only establishes current reachability. It does not prove unchanged intent.

If the saved locator cannot be used, let the user browse to a replacement or choose search roots or volumes. Search on demand, only within the project tree or roots the user explicitly selected. Show the search scope and allow cancellation and progress feedback. Candidate signals may include a supported native identity hint, relative suffix, name, file kind, size, modification time, and an optional digest. Show the evidence and its limits. Duplicate names and metadata are common; IDs can be unavailable, reused, or transient; equal content does not prove object identity. Show old and proposed locations, require an explicit user choice, and recheck the chosen target just before committing. Never bind the newest candidate automatically. Preserve the prior locator and a small revision/history record so a mistaken relink can be understood or reversed. The component helps recovery but cannot promise to find every file or infer user intent.

### Project containment, links, and portability

The critic correctly identified an underspecified boundary in the first draft. Define “inside the project” by the resolved target, not by a string-prefix test on the selected path. Before making a project-relative locator, resolve the project root and the selected filesystem target using the platform's supported path or handle APIs, then compare path components with that filesystem's rules. A symbolic link, junction, mount point, alias, or other indirection that resolves outside the project root is external, even if the selected link entry is inside the project directory. If an indirection cannot be resolved because the target is unavailable, permission is denied, a link is broken or cyclic, or the platform cannot establish containment, report containment as unknown and do not promise project-relative portability.

For a supported relative indirection whose final target remains within the project tree, preserve the selected in-tree relative path only if that representation remains valid after moving the project; otherwise store the resolved in-tree target path. The implementation must choose and document which of those semantics users get. Treat a Finder alias file as a file in its own right unless the app deliberately resolves it through an OS alias API and verifies the final target. Treat reparse-point or mounted-volume behavior the same way: resolve and verify, or classify as external/unknown. Do not silently follow an indirection across a boundary. On Windows, a final path can be obtained from an opened handle, but normalized-name queries on SMB can fail when the user lacks access to a component. On Linux, realpath resolves symbolic links when successful, but can fail for missing, inaccessible, or cyclic paths. Apple's resolvingSymlinksInPath can leave unresolvable links in the result. Those are platform-specific boundaries, not a universal algorithm. [S19–S23](sources/index.md#s19)

This policy is deliberately conservative. A user can still attach an external path or configure a named root. Project moves preserve only valid in-tree relative references and never imply that external references moved or that file bytes were packaged. If the owner wants alias following, mount-boundary traversal, or another rule, make that an explicit product choice and test it on each supported platform and filesystem.

### Storage, concurrency, and component boundaries

Persist attachment-reference mutations through the notebook's existing project-store owner. Do not assume a new table file or database format. Use atomic per-record changes and an expected revision or compare-and-swap condition. If a window's revision is stale, reject or surface the conflict, reload current state, and let the user resolve it; do not replace the whole table from an old in-memory snapshot. Notify the other open window after commit. A transaction can provide an atomic storage boundary but does not itself detect stale UI state. If SQLite is selected, WAL allows readers alongside a writer but only one writer appends at a time, and WAL requires processes on one host; do not use it for a project database on a network filesystem. [S15–S16](sources/index.md#s15)

Keep the integration narrow:

1. The attachment-reference store owns records, stable IDs, revisions, and atomic mutations.
2. A platform filesystem adapter owns path serialization/comparison, user-granted access, fresh probes, optional identity hints, volume availability, and error classification.
3. A bounded candidate finder searches only the project or user-selected roots.
4. The project window owns status, browse/relink, conflict, and confirmation interactions.
5. Export integration describes each reference and separately records whether target bytes were included.

No account, cloud service, upload, elevated service, background whole-disk index, or general file manager is needed. A watcher is not required for correctness. If an optional watcher is eventually added, it may mark records for rechecking; it must never authorize a silent rebind or replace a fresh probe.

## Alternatives and trade-offs

| Approach | Benefit | Limit | Recommended role |
| --- | --- | --- | --- |
| Absolute path | Minimal implementation; works while that path remains accessible. | Project relocation and mount/path changes can break it; the same path can later name another file. | Baseline locator for external files, always rechecked. |
| Project-relative path | A moved project can retain links when the target remains within its tree and relative structure is preserved. | Not valid for an external target; aliases, links, mounts, and path rules need containment handling. | Preferred portable locator only after the containment rule above succeeds. |
| Named root plus relative suffix | Supports users who keep a predictable tree under different machine-specific roots; Zotero demonstrates the trade-off. | Requires user setup and can be misconfigured; unsynced or moved targets remain unresolved. | Optional portability mechanism, never required. [S01–S04](sources/index.md#s01) |
| Platform bookmark or file/volume ID | Can help with user-granted access, move tracking, or same-machine comparison. | Platform-specific, may be stale, nonpersistent, reused, unsupported, or insufficient to open a file. | Optional local evidence; gracefully fall back to the locator and user-directed relink. [S08–S13](sources/index.md#s08) |
| Full content digest | Can show that bytes match a saved snapshot. | Reads all bytes; costs I/O; becomes stale after edits; equal bytes do not prove intended object. | Explicit local verification or opt-in, never sole identity or automatic rebinding rule. |
| Copy/package | Makes selected exported bytes self-contained. | Changes storage and duplication expectations; violates link-only semantics if implicit. | Separate explicit export action only. |

## Export and user control

The ordinary export should preserve stable reference IDs and a readable attachment list, and state plainly that a linked target is not included merely because its reference is present. Report per-reference inclusion, non-inclusion, or unavailability. If an owner-level export offers copy/package, it must be a distinct, explicit selection; copy only the chosen targets, mark what was packaged, and point the exported copy of those references at the packaged copies without changing the original attachment links.

Default recipient-facing metadata should include the stable record ID, display name, locator kind, and inclusion status. For a verified in-project reference, retain its project-relative locator so the reference can survive a project move; this does not say that its file bytes were included. Do not export absolute local paths, macOS bookmark/access data, access tokens, native file IDs, volume identifiers, or content digests by default. An export option that includes external paths or other local evidence requires clear disclosure and user consent. External references without exported locator details remain references only and should be described as unresolved on another machine. Owners must decide whether recipient-facing exports ever include external paths.

## Unresolved owner decisions

The brief and researched sources cannot settle these implementation facts:

1. What project persistence format and revision/locking mechanism already exist? Are the two windows in one process, separate processes, or both possible?
2. Can projects be edited on network filesystems or by multiple machines? That choice governs storage concurrency design; SQLite WAL is not a default answer for network storage.
3. Which desktop OS versions, filesystem types, removable volumes, and path-length/encoding cases must be supported? Is the macOS app sandboxed?
4. Which indirections should attachment selection follow: symbolic links, junctions, mount points, Finder aliases, and links across project boundaries? The conservative default above treats unresolved or escaping targets as external/unknown.
5. Which user-selected roots may be searched, should users name/map external roots, and what are the time, cancellation, and file-count limits?
6. Is hashing offered at all, and what file-size, I/O, privacy, consent, and recheck policy applies?
7. Should export include any external locator details? How should recipient privacy be balanced against relinking convenience?
8. Can a separate export workflow package chosen files, what happens for inaccessible targets, and how are exported-copy locators represented?

These are owner decisions, not inferred facts or blockers to the narrow proposal.

**Not executed:** no product code, downloaded code, executable witness, application, or feature scenario was run. No feature implementation was built or deployed. The checks below are proposals, not pass results.

1. **No-copy contract:** link test files and assert source bytes, path, size, and modification time do not change; verify only reference metadata is created. Separately test explicit export packaging and inclusion labels.
2. **Locator movement:** move a project while preserving in-tree relative structure; move an external file; change a removable volume mount point; verify observed state and never claim that a project move carried an external target.
3. **Containment and indirections:** exercise internal and escaping symbolic links, broken/cyclic links, Windows junctions/reparse points, mounted folders, macOS Finder aliases, inaccessible roots, and targets on a different volume. Verify only resolved in-tree targets get project-relative portability; ambiguous cases remain external/unknown. Test the chosen preserve-link-entry versus resolved-target semantics after moving a project.
4. **Identity and matching:** include duplicate names, same-size files, equal-byte copies at two paths, replacement at the old path, and edited files with stale digests. Confirm evidence is shown and no candidate is rebound without explicit user action. Exercise unavailable IDs, stale bookmark, denied access, offline volume, and unsupported filesystem behavior.
5. **Platform matrix:** on each supported OS and filesystem, cover path encodings, separators, case-sensitive and insensitive directories, Unicode names, long paths, removable volumes, and native identity availability. On macOS sandbox builds, test grant, restart, rename/move, stale bookmark refresh, and balanced start/stop access. On Windows test supported filesystems and changing drive letters/UNC paths. On Linux test target local filesystems and graceful behavior without file-handle privileges.
6. **Bounded search and optional watcher:** prove searches touch only the project or user-selected roots, can be canceled, and do not start a background disk index. If a watcher ships, add platform-specific documentation and tests for restart/startup gaps, missed events, directory rename, removable-drive removal, permission loss, and network behavior; reconcile with a fresh probe and never auto-rebind from an event.
7. **Two-window conflicts:** open one project twice; concurrently change different references; then change the same reference or delete in one window while relinking in the other. Verify stale revisions are detected, no edit disappears silently, and both windows converge after resolution. Repeat on each supported storage location.
8. **Export privacy and truthfulness:** export references that are available, absent, offline, external, and access-denied. Check stable IDs, linked-versus-packaged labels, only explicit copies, no default export of local paths/bookmarks/tokens/file IDs/volume IDs/digests, and consent disclosure for any opt-in local evidence.
