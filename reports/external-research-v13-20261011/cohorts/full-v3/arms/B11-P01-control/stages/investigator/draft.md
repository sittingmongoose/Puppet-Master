# Durable references to local project attachments — investigator draft

**Disposition key:** Retain = keep the choice with the listed boundary; Change = revise it; Reject = do not carry it into the proposal; Owner decision = implementation depends on a fact the brief does not provide. This draft responds to every sentence of the released plan and includes a complete proposal. Research and executable checks actually performed are separated from proposed validation.

## Recommendation

Build a narrow attachment-reference component around a stable project reference record, a replaceable locator, and separately recorded identity evidence. The component links the user-selected existing file without copying it. It should preserve the selected path as a locator and, where the file is actually inside the project tree, support a project-relative locator. A user-named root with a relative suffix can be an optional portability mechanism for users who keep files in a known tree. Store native filesystem identity as best-effort local evidence, not as the cross-platform ID. Make whole-file content hashing optional and explicit.

At use time, test the stored locator through the platform adapter and report a fresh, time-stamped result. If the path is absent, distinguish an offline volume and an access-denied result from an absent file. If a path exists but its current identity hints conflict with the saved hints, report a changed/replaced target. For recovery, let the user choose search roots or browse to a candidate, show every relevant match signal, and ask for explicit confirmation before rebinding. Never select the newest filename/metadata match automatically. The design can help find a replacement; it cannot promise to find every file or prove user intent from a path, digest, or OS ID.

Write reference changes through the project's existing persistence owner using atomic per-record updates and an expected revision. Synchronize open windows after commit; reject or resolve stale edits instead of replacing a whole table from an old in-memory snapshot. Keep export/reporting separate from linking: the default manifest says which references exist and whether each target was actually packaged. A separate, explicit export-level copy action may include chosen files without changing the original attachment reference. Preserve reference IDs. Treat full local paths and macOS security-scoped bookmark data as potentially private, machine-specific data; product owners must choose whether either belongs in a recipient-facing export.

The component boundary is: (1) attachment-reference store API; (2) OS filesystem adapter for selection, path representation, access scope, metadata/identity hints, availability and error classification; (3) bounded candidate finder for project files or roots chosen by the user; (4) relink/status UI; and (5) export integration that reports external references and inclusion state. It is not a general file manager, sync service, or disk index. No account, cloud service, privileged service, or silent file copy is required.

## Proposed record and status behavior

A record should have an immutable attachment-reference ID, display name, location descriptor, last-known file evidence, last-check time, and revision. A location descriptor can be one of: project-relative path; local absolute path; or user-root key plus relative path. Preserve path bytes/characters using platform-correct serialization. Do not use a file URI or display name as the only stored identity. On macOS, sandbox bookmark data should be kept in a machine/user-specific access store, not advertised as portable project data. Per-platform file IDs and volume identifiers should be namespaced by OS/filesystem and marked as best-effort observations.

The filesystem adapter should offer operations like choose existing file, probe locator, open target, collect supported identity hints, and map OS errors to a neutral status. Do not keep a file handle open as a permanent reference. A status is an observation, not a promise. Use “available at saved location” only after a current permitted probe. A path whose identity evidence changed is “needs review”; inaccessible is “access denied”; unmounted is “offline”; no candidate is “not found at checked locations.” Do not collapse these states into a red missing icon with no explanation.

A user-initiated relink flow should show the old reference, selected candidate, scope searched, match signals, and any mismatch. Preserve the old locator in a short revision/history record until the new binding is committed. Recheck the selected candidate immediately before committing so a file replaced between browsing and confirmation is not mistaken for the earlier observation. After commit, update the record revision and broadcast a project-change event so each open window reloads it.

## Alternatives and trade-offs

| Approach | Benefit | Limitation | Recommended role |
| --- | --- | --- | --- |
| Absolute path only | Very small component; works while the same path stays accessible. | Project moves and per-machine roots break it; path can later name a different file. | Baseline locator for external files, paired with a path-mode label and recheck. |
| Project-relative path or named-root-relative path | A project move or a user-selected root remap can preserve the internal folder structure. | Works only when the attachment is actually under that tree or users keep the same layout. | Preferred portable locator where its condition is met; do not silently move external files into the project. |
| OS-native bookmark/file identity | Can improve same-machine move tracking, permission persistence, and same-object checks. | Platform-specific, may be stale/ephemeral/reused/unsupported, and some APIs require elevated capability. | Optional adapter evidence; graceful fallback to paths and explicit relink. |
| Full content digest | Can confirm candidate bytes match a previous snapshot. | Reads all data; may cost time/I/O; content change breaks equality; equal bytes do not prove user intended that particular file. | Explicit local verification or opt-in, never an automatic identity or cloud key. |
| Copy or package attachment | Makes a deliberately included export self-contained. | Changes storage and duplicate-file expectations; violates link-only intent if implicit. | Separate explicit export-level operation with inclusion manifest. |

## Integration boundaries and unresolved owner facts

The component owns the attachment-reference record and status/relink operations. The notebook's project store owns persistence and conflict semantics. The OS adapter owns path format, access grant lifecycle, resource evidence, volume availability, and error classification. The project window owns refresh/conflict display. The export layer owns packaged-copy selection and disclosure. No service needs to track arbitrary filesystem locations continuously.

Before implementation, owners must identify the current project persistence format, whether two windows share one process/store and whether projects may be edited over network filesystems; supported OS and filesystem versions; whether macOS App Sandbox is enabled; expected file sizes and whether users consent to full hashing; allowed scopes for candidate search; removable-volume mapping expectations; and export privacy/copy rules. If the store is an ordinary shared file rather than a transactional database, define an interprocess lock and conflict/recovery format before implementing concurrent writes. These facts cannot be settled from the brief or upstream analogs.

## Validation plan — proposed, not run

1. **No-copy link contract:** link representative files and assert source bytes, path, size, and modification time remain unchanged; verify linking creates only reference metadata. Separately verify that explicit export copy includes only selected files and labels each inclusion in the manifest.
2. **Locator portability:** move a project containing an in-tree linked file while preserving its relative structure; verify that link resolves. Move the external file, change its parent path, and change a removable volume's mount point; verify the app reports its actual state and does not claim the project move carried external files.
3. **Identity and matching:** use duplicate filenames, same-size files, equal-byte copies at two paths, replaced files at the original path, and modified files whose digest changed. Verify that candidates show evidence and none is rebound without explicit user choice. Exercise missing, stale bookmark, permission-denied, offline, and unavailable-filesystem outcomes.
4. **Platform matrix:** on each supported OS, verify path encoding, separators, case-sensitive and case-insensitive directories, non-ASCII names, long paths, aliases/symlinks as supported, and available native-ID behavior. On macOS sandbox builds, test user grant, restart, moved/renamed target, stale bookmark refresh, and balanced start/stop access. On Windows, include supported local/removable filesystem types and changing drive letters. On Linux, include the target local filesystems and confirm any file-handle path degrades without extra capability.
5. **Candidate scope and watcher limits:** prove search touches only project or user-selected roots, remains cancellable, and does not launch a background disk index. If optional watchers ship, simulate app restart, drive removal, directory rename, and missed events; show that a fresh probe reconciles status without silent rebinding.
6. **Two-window conflict:** open one project twice. Change different references concurrently and confirm both persist. Change the same reference or delete in one window while relinking in the other; verify stale revisions are detected, neither update disappears silently, and both windows converge after conflict resolution. Repeat on every supported storage location; do not use SQLite WAL on a network filesystem.
7. **Export privacy and truthfulness:** export with available, missing, offline and external references. Confirm manifest IDs remain stable; linked targets are clearly marked not included; only explicitly chosen files are copied; recipient-facing output does not reveal local absolute paths unless a user-specific policy permits it.

No application or these feature scenarios were executed in this investigation.
