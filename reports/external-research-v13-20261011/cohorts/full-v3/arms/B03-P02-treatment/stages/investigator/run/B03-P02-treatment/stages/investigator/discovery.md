# Independent discovery — portable project archive export

## Scope and evidence basis

The brief asks for a researched proposal and validation plan for a portable, human-readable archive plus a structured representation that could support a future import of project tracker tasks, comments, dates, custom fields, and attachments. Scale spans roughly 50 to 50,000 tasks; attachment bytes can exceed temporary storage. Some links point to projects the exporter cannot access. The archive must be consistent, explain omissions, work offline to read, avoid invented attachment data and mutations, and distinguish cancellation/incomplete output. No actual export or implementation is authorized. A round-trip claim is prohibited unless retained scope is defined. Source IDs and bounded evidence are in `sources/index.md` and `source-map.json`.

## Recommended shape, subject to owner choices

Use a self-contained ZIP64 package as the default candidate: a plain-text `README.md`; a versioned `manifest.json`; a bundled JSON Schema 2020-12 dialect/schema; UTF-8 JSON Lines records for tasks, comments, custom-field definitions/values, links, and omission records; and attachment members stored under generated safe names such as `attachments/sha256/<digest>`. Put each attachment’s source display name, media type, byte count, digest, and relation in structured metadata rather than using source filenames as archive paths. This keeps the data inspectable with ordinary tools after extraction while leaving a distinct future-import contract. A package descriptor can use a small manifest/resources pattern inspired by Data Package, and per-entry SHA-256 manifests/validity checks inspired by BagIt. Bundle every schema and resource: remote references would break offline reading. ZIP is a candidate container, not a data schema; neither BagIt nor Data Package supplies tracker semantics. [S06, S11, S12, S17–S19]

Use stable source IDs as strings and qualify them with source system and entity type. Preserve source identity and relevant relation IDs; do not mint name-derived UUIDs or infer identity from display names. Define what a custom field’s identifier, key, display label, type, options, and per-task value mean, and preserve empty, null, and unknown values distinctly. Encode UTF-8 and reject duplicate JSON object keys. Represent a date-only value as a date-only value; an instant as an offset-bearing RFC 3339 timestamp; and local/future wall-clock values with their original local date/time plus zone identity when supplied. Preserve original lexical value/precision where a normalized value might lose meaning. A schema `format` annotation alone is not proof of date-time validation. [S13–S19]

## Snapshot and attachment consistency

First identify the live storage backend and source model; do not assume SQLite from the Rust/Slint implementation direction. For SQLite, choose either the Online Backup API to a temporary/private snapshot DB or one pinned read transaction. Incremental backup can bound lock time; snapshot semantics apply to the DB only. If attachments live outside it, require immutable/versioned object references or stable handles, or pin/copy each object while verifying identity and detect mutation between metadata capture and byte read. The manifest should record one `snapshot_at`/export run identity and clarify whether DB rows and blobs share a truly atomic point in time. If the backend cannot supply a coherent cross-store view, fail closed or label the precise consistency limitation; never imply a DB snapshot freezes unrelated files. [S01–S05]

Export only records and attachment bytes that the caller is allowed to read for the selected project. For a link to an inaccessible project, do not resolve it, enumerate it, or retrieve its records/bytes. Emit a link placeholder/omission with the visible relation and a reason only if the source system exposes that information under current authorization. Whether even the target opaque ID/URL is allowed in the archive is an owner/privacy decision. Never replace missing bytes with an empty file or fabricated value. Define upfront whether an attachment unavailable at snapshot time blocks the entire export or yields an explicitly partial export; absent source metadata that clearly marks a file as missing should be a hard failure by default. [S20 supports the need for explicit versioned item scope; this boundary follows the brief.]

## Completion, cancellation, and storage modes

For the streaming option, write a sibling `.partial` ZIP64 file with bounded record/blob buffers; enable ZIP64 even when today's artifact happens to be small if the product supports the specified scales. Hash bytes as they are copied. Add manifest/count/checksum information before close or use a clearly defined manifest protocol; then finish the archive (central directory/end structures), re-open/read every member, validate counts, sizes, digests, record schema and cross-references, and only then publish as the final name. Use same-filesystem no-clobber rename where supported, with platform-specific durability/atomicity checks. Before final publish, cancellation/error closes the read view and removes temporary output where possible; if cleanup fails, leave a recognizable `.incomplete` marker/name and never a valid-looking final name. Check disk capacity and reserve enough for the final bytes plus bounded metadata; streaming avoids a second full temporary payload tree but cannot avoid space for the actual output, ZIP central-directory metadata, or buffers. ZIP streaming has a tail directory, so an interrupted file is not a complete archive. [S06–S10]

Alternatives: (1) build a directory/BagIt tree then archive it—easiest to inspect/retry, but may require payload plus full archive space and extra I/O; (2) deliver an unpacked directory—avoids compression/container finalization and is directly inspectable, but creates many files and weaker single-file handoff; (3) archive a SQLite snapshot—useful for technical recovery, but is not directly human-readable and leaks implementation/schema as the import contract. Choosing among ZIP, directory package, or a formal profile is an owner decision based on required operating systems/readers, import consumers, retention and disk policy. Do not promise universal atomic rename or ZIP interoperability until the platform/target matrix is tested. [S01, S06, S11, S12]

## Package contract and limits

Manifest fields should include format/schema version and dialect; exporter and source-system versions; selected project ID; run ID and snapshot time; completion state; counts for every entity; content paths, lengths, and SHA-256; omission records/counts/reasons; and declared unsupported/omitted categories. Checksums establish accidental-corruption detection, not authenticity. Signing/encryption and key management are owner decisions (the brief does not require them). Keep output records and README self-contained; no network fetch is required to understand them. Explain that archive data does not preserve source access-control enforcement. Define major/minor compatibility, unknown optional vs required fields, custom-field evolution, and supported importer versions. A future importer should validate package version/schema before mutation and use explicit path/link/size limits. [S06, S11–S13, S17–S21]

Define “round-trip” narrowly: an identified importer version can re-create the selected, exported fields and exact listed attachment bytes under a declared normalization/omission matrix. Class each field/relation as exact, normalized, omitted/lossy, or undecided. State exclusions such as inaccessible project content, permissions/ACLs, histories, deleted items, audit/activity data, or unsupported field types only after owner/product scope confirms them. This proposal makes no universal-fidelity or backup claim. [S20 is a concrete precedent showing version/item omissions and changed attribution.]

## Owner decisions still needed

1. Which storage adapter/version and identity model are in scope, and can DB rows plus attachment versions be read from one snapshot?
2. Which platforms and built-in/external extractors/importers must interoperate, including classic/ZIP64 thresholds and filenames?
3. Is a missing/mutating attachment fatal, or can the user approve a partial archive? What is the exact meaning of “inaccessible link” and whether its target identifier may be emitted?
4. Which project records, comment history, custom-field types, timestamps, author identities, relations, and binary types are retained? Are deleted/history/ACL data in scope?
5. Do users want a single ZIP, an unpacked directory, or both? What is the disk/quota/cleanup policy and max archive size?
6. What format compatibility policy, unknown-field behavior, authenticity/signature, encryption, and future importer contract are required?

These decisions constrain an implementation and cannot be inferred from format documentation. Suggested defaults above are not approval.

## Validation proposals (not executed)

- Snapshot consistency: mutate task/comment/custom-field rows during export; verify every emitted record comes from the declared DB snapshot. Independently mutate/replace an attachment during its copy; verify stable-version pinning or detect-and-fail. Cover WAL and rollback journal if SQLite is selected.
- Scale: small and 50,000-task fixtures; more than 65,535 archive entries; a >4 GiB member if platform/test budget permits; many tiny files and large central-directory metadata. Test exact crate/lockfile version against ZIP64/Deflate.
- Offline/interoperability: disconnect network; read the README/manifest/schema/JSONL locally; validate using bundled schema only; try named built-in archive readers on supported Windows/macOS/Linux versions; include Unicode names, duplicate display names, zero-byte files, and long names.
- Integrity/failure: truncated/corrupt ZIP, altered attachment, wrong length/digest, duplicate JSON key, malformed UTF-8, unsupported required schema version, broken relation, disk full, permission failure, destination already exists, cancellation at snapshot/record/blob/finalization/verification/rename, and forced process exit. Confirm no mutation to source records, no complete-looking final file before validation, cleanup or recognizable incomplete marker, and retry safety.
- Privacy/access: two projects with one inaccessible target; assert zero reads or payload from that target, permitted link metadata policy, omission reason, and no unrelated project rows/blobs.
- Temporal semantics: date-only values around DST, explicit offsets, named zones, fractional precision, null/unknown timezone, and changing zone rules; assert no silent UTC-midnight coercion.
- Import readiness: fuzz normalized paths/symlinks/traversal/duplicates/oversized expansion; ensure importer validates before extract/write. No importer exists or was exercised here.

These are proposed acceptance checks; no product implementation, archive, offline witness, or test run was performed. The source/repository material above is research evidence, not a validation run against Puppet Master.
