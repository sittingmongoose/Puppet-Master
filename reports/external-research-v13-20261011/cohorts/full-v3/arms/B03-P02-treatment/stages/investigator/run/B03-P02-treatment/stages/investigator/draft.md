# Research-backed draft — portable project archive export

## Status and recommendation

This is a proposal and validation plan, not an implementation or approval to export records. The brief calls for an archive that is offline-readable and usable as a future structured import source, covers records and attachments, discloses omissions, preserves source state, tolerates large projects, and distinguishes incomplete output. I found no evidence that the planned per-task walk after a revision marker is a consistent snapshot. That assumption needs a source-backend-specific snapshot token/read view that covers every record; a database-only snapshot does not freeze a separate attachment store. [S01–S05]

Keep four viable package choices open until the owner selects target platforms, extraction tools, import needs, and disk policy: (1) streaming ZIP64 with a self-contained manifest/schema/JSONL/attachments, (2) staged directory then archive, (3) direct directory package with manifests, and (4) a database snapshot for technical recovery only. The first is a plausible candidate for one-file handoff but remains contingent on reader compatibility, source snapshot capability, and low-disk behavior. ZIP/BagIt/Data Package define useful container or metadata patterns, not the tracker’s field contract or a winning solution. [S06–S12]

## Package and storage alternatives

| Approach | Benefits | Costs and conditions | Current status |
|---|---|---|---|
| Streaming ZIP64 with JSONL and attachments | One-file delivery; bounded copy buffers; no duplicate uncompressed staging tree; ordinary extractors can expose local human-readable records. ZIP data descriptors permit non-seekable output. | Needs final archive capacity, tail central directory, per-entry metadata, robust cancellation/finalization; compatibility depends on ZIP64 and data-descriptor support across target readers. Pin exact library and regression test. | Candidate, not chosen. [S06–S10] |
| Staged directory then ZIP | Easy to inspect/test/retry members; simple manifest generation. | Can require source payload tree plus complete archive at once, adding disk and I/O; cleanup after cancellation must be reliable. | Alternative. |
| Direct directory/BagIt-style package | No compression; direct local browsing and manifest checks; no single archive end record; can write files incrementally. | Many-file handoff, filesystem metadata/path constraints, partial-directory cleanup, weaker single-file portability; BagIt does not define tracker semantics or authenticate against an attacker. | Alternative. [S11] |
| Data Package descriptor with bundled files | Clean resource/schema descriptor and machine-readable resource inventory. | Not itself a container; URLs are permitted by general spec, so selected profile must require bundled local files and schemas. | Schema/manifest inspiration, not a package winner. [S12] |
| SQLite snapshot DB | Useful for engineering recovery or database-native consumers. | Not directly human-readable; storage schema becomes implicit import contract; excludes external blobs unless separately bundled. | Separate recovery option, not sole requested archive. [S01–S05] |

## Proposed export state machine and manifest

1. Validate caller/project scope and destination; resolve storage/backend capabilities and chosen package profile. Capture one snapshot/version that covers all exported database entities. Pin immutable attachment version/handle or declare/verify a non-atomic boundary.
2. Write all outputs under an exclusive `.partial` location on the destination filesystem. Use read-only source access and bounded buffers. Update entry hashes, lengths, counts, and omission records as emitted. Detect read failures, version changes, short writes, quota/ENOSPC, and cancellation.
3. Produce a manifest containing format/schema versions and dialect; exporter/source versions; project/source namespace; run ID and snapshot marker; completion semantics; entity counts; package paths, sizes and SHA-256 values; omission categories/reasons/counts; and explicit unsupported scope. Bundle a readable README and schema. No untrusted source filename becomes an archive path.
4. Close source view. Finalize container including ZIP directory/end records if selected; reopen and verify archive structural readability, exact member list, manifest/member consistency, sizes/digests, local schema, references, counts, and omission status. Hashes are not a signature or authorization mechanism.
5. Publish the verified package to the final path with no-clobber same-filesystem operation where platform supports the required semantics. Do not make a completed-looking final path visible before verification. If cancel/error precedes publication, remove temporary artifacts or retain a distinct incomplete marker if cleanup fails. The source remains unchanged. Durability/fsync, atomicity, and replacement policy require platform-specific validation.

The manifest must distinguish `complete`, `complete_with_declared_omissions` (if approved), and `incomplete/failed`. A ZIP CRC is not enough for cryptographic payload fixity; add a specified digest. A digest alone does not prove who produced the archive. Whether to sign or encrypt is unresolved and not implied by the brief. [S06, S11]

## Future importer boundaries

A future importer should accept only declared format/schema versions; fail or quarantine unknown required semantics; never perform remote schema/resource lookup; validate bounded total/uncompressed sizes, member count, compression ratio, normalized relative paths, symlink/special-file metadata, duplicate/case-colliding members, digest/length, field types, cross-record references, and omission declarations before writes. The Rust ZIP advisory covers a historical affected extraction range, not all versions and not export writing; defense-in-depth checks are still required. Import authorization, conflict resolution, account mapping, permission recreation, destination transaction, and rollback/preview need separate design. [S17–S21]

## Owner decisions and unresolved assumptions

1. Name source product/backend/version and whether a stable cross-entity snapshot exists; identify how attachment versions relate to the database revision.
2. Approve the record/field/attachment inventory and whether history, deleted records, permissions, audit activity, inaccessible target IDs, and custom/unknown fields are included or omitted.
3. Select supported platforms and archive readers, one-file vs directory handoff, classic/ZIP64 requirements, max package size, temp/quota policy, and destination overwrite behavior.
4. Decide policy for bytes missing in source vs transiently unreadable: abort all-or-nothing or explicitly label user-approved partial success; define if any incomplete export is useful.
5. Define field-level date and identity semantics; whether raw source strings can be retained; whether generated stable import IDs are needed.
6. Define format/schema compatibility guarantees, unknown-field behavior, named importer target, and definition of round trip.
7. Decide signing/encryption, key management, provenance verification, and sensitivity of exported content. Neither checksums nor package encryption preserve source ACLs.
8. Define retention/cleanup/durability requirements and whether failed partials are automatically removed or retained for diagnosis.

## Validation plan — proposals only

- **Consistency:** During export, mutate task/comment/custom-field/relation data. Assert emitted rows all reflect the declared snapshot. Independently mutate/replace a blob; assert a pinned version is read or export fails/labels the approved boundary. If SQLite is selected, exercise WAL and rollback journal and the documented `read_uncommitted` exception configuration.
- **Scale and format:** Test 50 and 50,000 tasks plus realistic high comment/attachment counts; exceed classic entry-count threshold (>65,535); test one >4 GiB member if feasible and ZIP64 end records; use the exact dependency lockfile. Check short writes/central directory size and known regression path.
- **Interoperability/offline:** With network disabled, read README, JSONL, manifest and bundled schema. Validate on named versions of built-in extractors for supported Windows/macOS/Linux; test non-ASCII and duplicate display names, long names, zero-byte blobs, filename traversal characters. Record actual allowed reader matrix.
- **Integrity/completion:** Alter/truncate a member, corrupt central directory, mismatch manifest count/size/hash/schema/reference, duplicate JSON keys, malformed UTF-8, and unsupported required schema. Ensure verification blocks final publication. Distinguish ZIP structural CRC from manifest cryptographic digest.
- **Cancellation/storage:** Cancel/kill at snapshot, each entity, each attachment, directory close, archive finish, verify, and publish. Test full disk/quota/permission loss, destination collision, process restart and cleanup failure. Verify source unchanged and no complete-looking output on every pre-publish failure.
- **Privacy:** Export a project with links to accessible and inaccessible projects. Assert inaccessible content is never queried or included and the chosen identifier-redaction policy is followed. Count every omission and check no ACL claim is made.
- **Semantics/import:** Cover dates around DST, date-only, offsets, named zones, fractional precision, null/unknown types; schema minor/major and unknown field variants; future import path traversal, symlink, duplicate normalized names, ZIP bombs/expanded-size limits, and ref integrity. No importer is available in this research stage.

**Executed:** read assigned brief and released plan, researched the cited primary specs/docs/upstream code/history, and created this plan. **Not executed:** no software build, export, filesystem space simulation, archive validation, automated test, or product-side source-data access. Every validation above remains proposed.
