## Recommendation

Prototype a local-first cue-sheet component using the Rust crate Loro as the first candidate to evaluate in the project’s Rust/Slint direction. Keep the choice provisional: the Rust API documents the needed container, history/frontier, import, and export primitives, but the clearest examples of concurrent MovableList behavior and sync are JS/WASM examples. No Rust/Slint integration, persistence, adapter, usability, or load witness has been run. Pin the exact Rust crate and inspect that version’s source/release history before deciding. In particular, do not transfer a fix or behavior documented for the separate JS/WASM package loro-crdt@1.16.4 to Rust crate loro 1.16.2 [S01, S03–S06, S15].

Use stable cue IDs as entity identity, independently editable cue records, an ordered MovableList of cue IDs, and comment records keyed by comment ID and anchored by cue ID. Store per-edit intent and resolution records so a convergent display value is not mistaken for an agreed human choice. A modest relay may exchange and retain updates when laptops reconnect; local editing and durable local recovery must work without it. The design does not assume an always-online editor, enterprise account, or new chat product. Publish explicit, immutable run-sheet artifacts with visible identities, separate from the evolving rehearsal document. These behaviors require application code and policy; they are not Loro features.

## Proposed component model and conflict lifecycle

### Identity and content

- **Order:** one MovableList of CueIds. Do not copy cue text into the order structure or use array position as identity.
- **Cue entities:** records keyed by CueId with independently editable text, timing notes, role assignment(s), and explicit deletion/tombstone status. Distinct fields allow unrelated edits to coexist.
- **Comments:** records keyed by CommentId with text, author and creation metadata, agreed status/replies, and anchor_cue_id. Comments are durable shared data. “Editing now” presence is ephemeral and may be omitted from the first release.
- **Optional text ranges:** only if the owner requires them, store stable text cursors rather than integer offsets. Keep unresolved/deleted target states visible and test history-replay cost [S02, S12].
- **Intent and resolution:** persist a unique operation ID, entity/field, candidate value or before/after move anchors, author/session, observed base frontier, and a resolution ID referencing the candidates it resolves. This may live in the replicated history or a durable log atomically associated with it; in either case it is application policy, not a library promise.
- **Display:** derive cue numbers from current order. Keep conflict, local-unsent, pending-import, sync-complete, and selected-release indicators distinct.

Compare edits using causal history/frontiers, not wall-clock timestamps. If one operation causally follows another, treat it as a later intentional edit subject to ordinary product rules. If incompatible operations are concurrent, preserve every candidate and keep the field marked unresolved even if the CRDT has a deterministic displayed value. Equal candidates may be coalesced only when their meaning is identical. For cue text, initially surface all concurrent edits to the same text field with a merged-text diff and require review; later narrow review to non-overlapping stable ranges only if testing shows the conservative policy is too noisy. Concurrent inserts with distinct CueIds may merge automatically, while semantically duplicated cues remain an owner decision.

The lifecycle for entity races is:

1. **Delete versus edit:** preserve both the deletion and edited-content candidates. Show a conflict with choices to keep deletion, restore/retain the edit, or combine/repair as appropriate. Never drop the edited text merely because deletion won the deterministic view.
2. **Delete versus move:** preserve the deletion and intended move target. Ask whether to retain deletion or restore and place the cue. Do not silently hide the move or resurrect the cue.
3. **Revival versus new cue:** an explicit restore of an old CueId is different from creating a genuinely new cue with a fresh ID. Record the restore action and its decision. A new cue never inherits old comments or captures their anchors. Concurrent incompatible restore/delete operations remain reviewable.
4. **Comment creation versus cue deletion:** retain the comment and cue tombstone; show the comment in an “anchor removed” state. Re-anchor only through an attributed action that records the new cue ID. Never resolve by looking up whatever cue now occupies the old index.
5. **Duplicate/reordered delivery:** candidate operation IDs and resolution references make replays idempotent. A resolution covers only the candidate IDs it names. A later unseen incompatible candidate creates or reopens a conflict rather than being erased by an earlier resolution.

Preserve candidate operations after resolution for audit/recovery. A deterministic CRDT winner, timestamp, or hash is not human approval.

Loro Map rules can also hide one of two regular child containers independently created under the same logical key. Use stable unique entity IDs, initialize common containers consistently, and use the library’s mergeable-container mechanisms only where peers really must share a lazily created logical child [S03]. Do not assume a library container conflict is equivalent to the app’s business conflict workflow.

## Local durability, relay, retry, and recovery

The Rust Loro API says the library does not manage storage/loading/synchronization. A Loro commit groups operations and emits events/history; it has no rollback or isolation and is not a durable database transaction [S15]. The local durability boundary therefore belongs to the application.

Before acknowledging “saved,” the application must durably associate the edit’s idempotent command/operation record, resulting document state or update, and outbox entry. Use a transactional local database or a write-ahead command journal plus a replayable checkpoint. If the process crashes between applying an in-memory Loro operation and persisting a checkpoint, rebuild from the last durable checkpoint and replay journal entries by stable command ID. The exact storage format and flush semantics need implementation review and crash tests; no storage guarantee has been demonstrated here.

On reconnect, send missing incremental updates with document/schema identity, stable update identity or content hash, and version/frontier metadata. The relay authenticates the team, stores updates durably before acknowledging, deduplicates retries, and returns updates missing from the client. Import into the existing replica. If import status contains pending dependencies, fetch the missing ranges and continue to show incomplete synchronization. Do not clear the local outbox merely because a socket write succeeded. Mark an update delivered only after durable relay acknowledgement and local checkpoint advancement.

Keep periodic full snapshots and update history for recovery. Do not adopt shallow snapshots until the owner-approved retention/compaction boundary accounts for long-offline devices; the docs warn that older updates before a shallow snapshot boundary may not be importable [S04, S06]. If running a relay is unacceptable, manual update-bundle exchange is a possible alternative, but it adds staff steps and still needs authentication, replay, import, and backup policy.

Never let concurrent writers emit under the same Loro PeerID. Loro documents random defaults and warns that duplicate peer IDs can collide in operation identity; a persisted history may reuse an ID only under the library’s safe conditions and a single-writer guarantee. A copied profile, cloned process, or two active app instances must not become concurrent emitters under one ID. Test restart, restore, and duplicate-ID handling [S05, S15].

## Publication and alternatives

An approved run sheet is a separate immutable artifact, not an approval flag on the working document. Publish only a selected frontier after its conflicts are resolved. Record the exact serialized bytes and hash with release identity, schema version, source frontier, approver, and time. A later rehearsal edit creates a working revision and cannot rewrite the published bytes. If emergency override is allowed, record its actor, reason, and the conflicts it bypasses. Whether it is allowed and who may approve are owner decisions.

The stage-facing view identifies the exact selected release, caches it for offline use, and does not switch releases mid-run. Keep comments and role assignments in the export format; decide whether discussion comments are visible to stage staff. A content hash provides integrity checking, not approval authority.

| Alternative | Evidence and useful fit | Cost or limitation |
|---|---|---|
| **Automerge (Rust/JS)** | Local-first documents, history/sync, fine-grained map/list edits, and inspectable concurrent property values [S08–S10]. | Ordinary reads use a deterministic winner; conflict inspection must occur before assigning again because assignment clears the visible conflict. The reviewed Rust sync docs assume a reliable, in-order stream. The examined list API is not a dedicated move operation, so delete+insert movement needs an identity/deduplication policy. Credible Rust alternative, not rejected. |
| **Yjs** | Shared arrays/maps/text, relative text positions, and browser offline persistence through y-indexeddb [S11–S12]. | The cited persistence provider targets browser IndexedDB. A Rust desktop app needs an environment-appropriate native provider/binding. Text positions do not by themselves establish cue identity. More attractive if the component becomes web/JS-centric. |
| **ShareDB / JSON OT** | Node server/client, OT type plugins, history, and advertised offline change sync on reconnection [S13–S14]. | More server dependence. Its reconnecting-WebSocket example disables buffering while disconnected because behavior is undefined; it does not provide the durable local outbox required here. OT transformation still does not supply cue-level decision UI or publication approval. |
| **Snapshots plus app operation log** | Makes business conflicts, audit, and release approval explicit. | Custom causal merge, ordering, recovery, and migration are costly and need careful verification. Retain as a fallback if a focused CRDT prototype fails the acceptance matrix. |

Real implementation history informs risk but not adoption by itself. Loro issue #957 reported import-time lock-order panics in a particular loro-crdt@1.11.1 Node/WebRTC adapter workload; PR #958 changed operation-count access and added regression coverage. This is a reason to test the chosen Rust version and actual adapter/import/reconnect path, not evidence of a current Rust-native defect. Separately, the observed loro-crdt@1.16.4 release is a JS/WASM package and its fixes must not be attributed to Rust loro 1.16.2 without checking the Rust crate’s own history [S06–S07].

## Owner decisions and unknown facts

Resolve these before freezing product behavior:

1. Team size, number of devices/documents editing concurrently, typical and maximum sheet size, and expected cue-volume envelope.
2. Longest planned disconnection and how long relay update history must be retained for returning devices.
3. Cue-only versus text-range comments; comment editing/deletion, replies, resolution, and author metadata.
4. Whether discussion comments and role assignments are visible on the stage-facing export and which formats must round-trip.
5. Who may adjudicate conflicts and publish; whether emergency override is permitted and whether it requires a reason.
6. Whether a run pins a named release or selects the latest approved release, and how a newer release is shown during an active rehearsal.
7. Relay operator, authentication/invitation, encryption, authorization/revocation, backup, retention, and recovery responsibility.
8. How independently created semantic duplicate cues and role constraints should be handled.
9. Export/schema migration support window and how long older published releases must remain readable.

Unknown cue counts remain a sizing input; they do not remove feasible mechanism research or justify timestamp-based replacement.

## Proposed validation (not run)

1. **Durability boundary:** use the pinned Rust crate and target app storage. Crash after command-journal append, Loro operation/commit, checkpoint/update write, outbox commit, flush, relay send, relay durable store, relay acknowledgement, import, and local sync-checkpoint advancement. Reopen and replay. Confirm no success indication precedes durable local state; no acknowledged relay update is lost; replay is idempotent.
2. **Offline edits and convergence:** from a common base, use isolated replicas and distinct PeerIDs. Concurrently insert distinct cues at the same gap; move the same cue to different before/after anchors; move different cues; edit same and different text; change timing/role fields; add comments; then exchange updates duplicated, reordered, delayed, batched, and partially missing. Verify all replicas converge after the same complete update set, no nonconflicting work disappears, and pending imports remain visibly incomplete until dependencies arrive.
3. **Conflict lifecycle:** exercise delete-versus-edit, delete-versus-move, delete-versus-comment creation, concurrent restore/delete, fresh cue creation after deletion, duplicate semantic cues, and late delivery of a candidate after resolution. Verify both candidates persist, conflict status is intelligible, resolution references exact candidate IDs, a later unseen candidate reopens review, and duplicate/reordered replay does not duplicate or erase conflict decisions.
4. **Anchor integrity and export:** reorder, delete, restore, and recreate cues with comments; verify no comment silently changes target. Verify removed anchors are visible and explicit re-anchor is recorded. Round-trip exports containing comments, role assignments, and agreed metadata.
5. **Publication boundary:** publish a chosen committed frontier; continue editing, importing, and resolving conflicts; compare exact stored release bytes/hash and stage-visible release metadata. Verify ordinary publish blocking, any approved override behavior, offline cache, named-release pinning, and update prompts.
6. **Compatibility, identity, and sizing:** pin exact Rust crate and adapter; test import/export, malformed updates, supported schema migrations, backup/restore, long offline histories, duplicate PeerID prevention, maximum owner-confirmed cue/team/outage envelope, and target laptop memory/performance. Include a comparison against at least one credible alternative before treating the first prototype as selected.
7. **Usability:** ask crew members unfamiliar with the model to resolve realistic same-cue text/move/role conflicts. Confirm they can identify the cue and revision, understand keep/merge/defer choices, see unsent/pending state, and identify the exact release staff are viewing.
