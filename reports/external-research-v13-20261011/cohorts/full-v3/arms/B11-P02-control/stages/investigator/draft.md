## Recommendation

Prototype a local-first cue-sheet component with the Rust crate Loro as its first CRDT candidate, while treating adapter, data model, conflict presentation, and publication approval as application responsibilities. The current docs.rs Rust API page resolved to loro 1.16.2; the newer loro-crdt@1.16.4 release seen on GitHub is specifically the JS/WASM package. Pin and assess the exact Rust crate and its versioned release notes before adoption; do not assume the two package lines are identical [S04, S06].

Use a MovableList of stable cue IDs for order, entity maps for cue fields, and a stable cue ID in each comment record. Keep edits on each laptop fully local and durable. Synchronize incremental updates through an optional, modest team relay after reconnect. Preserve each user's edit intent alongside the convergent state so incompatible concurrent changes remain visible even when the CRDT has already selected a deterministic display value. Publish a separate immutable, named run-sheet release from an explicitly approved frontier. These are proposed behaviors, not implemented capabilities.

The mechanism choice is conditional. Loro has the strongest fit found for the Rust desktop direction because its Rust API exposes the relevant containers and version/history primitives, while its MovableList has a native move operation [S01, S04]. However, the documented concurrent move example chooses one final position deterministically; it does not ask a person to adjudicate intent. The component must add that layer [S01]. The live website examples are JS/WASM examples, so concurrency semantics, imports, persistence, and UI behavior still need direct tests using the pinned Rust crate and target app.

## Proposed document and edit model

A single sheet document should contain:

- **Cue order:** a Loro MovableList whose elements are cue IDs, never copies of cue text or positions used as identity.
- **Cue entities:** records keyed by cue ID, with independently editable text, timing note, role assignment(s), and deletion/tombstone state. Split fields so concurrent changes to different properties can coexist.
- **Comments:** records keyed by comment ID, each with author, creation metadata, content, status/replies as required, and immutable cue anchor ID. A cue reorder cannot affect the reference. Retain deleted cue entities as tombstones while comments or concurrent edits refer to them. Re-anchor only through an explicit user action.
- **Intent and resolution records:** unique edit IDs, field/entity path, proposed value or move anchors, author/session, observed base frontier, and resolution references. Record operations in the same replicated history or another durable log that is atomically associated with it.
- **Display state:** derive cue numbers from current order. Keep visible conflict, sync-pending, local-unsent, and release identity indicators separate from persisted semantic fields.

A single map field written concurrently may expose only a deterministic value in ordinary reads. Therefore, before relying on a library's conflict accessor or move winner, persist the candidate edit/operation. Loro's Map behavior can also hide a regular child container created independently under the same key; use unique entity IDs and mergeable child creation when several peers may create the same logical child [S03, S08].

For conflict classification, compare each edit's observed base frontier with the other edit's history. If one edit causally follows the other, treat the later operation as the next intentional edit. If neither saw the other and the candidate values differ, keep an unresolved conflict. Equal concurrent values can be coalesced. For concurrent moves of the same cue, store stable before/after cue IDs and show both intended placements even if MovableList has already converged to one. For cue text, a conservative initial policy is to mark same-text-field concurrent edits for review and show both branches plus the merged text; this may create review work for disjoint insertions but prevents silent acceptance of a potentially incompatible rewrite. A later design can narrow the detector to overlapping stable text ranges if owner testing shows the conservative rule too noisy.

Conflict actions should be explicit: accept candidate A, accept candidate B, enter a combined field value or move placement, or defer. A resolution record must cite the candidate IDs and actor. Preserve original candidate operations after resolution so review/audit can reconstruct the decision. Unresolved conflicts block ordinary publication. This application-level operation log, conflict detector, and interface are proposed work; none is attributed to the CRDT library.

## Local save, reconnect, relay, and recovery

1. On edit, commit to the local document and a durable local outbox before success feedback. Use a transactional database or an atomic append/snapshot scheme with verified crash recovery.
2. When connected, upload missing updates with a document ID, update identity/content hash, schema version, and relevant version-vector/frontier metadata. Relay authenticates team membership, durably stores before acknowledging, deduplicates retries, and returns changes missing from the client.
3. Import into the existing replica; retain both sides' work. If import reports pending dependencies, request missing ranges and show that sync is incomplete. Do not clear the outbox solely because a socket write succeeded.
4. After durable server acknowledgement and confirmed integration, advance the local sync checkpoint. If the connection drops, retry from the checkpoint. Duplicates are expected.
5. Persist periodic full snapshots and update history for backup/restart. Define retention, compaction, migration, backup restore, and relay outage behavior with the team. Do not adopt shallow snapshots until it is clear how old offline devices will be prevented from requiring discarded history; the docs warn that shallow snapshots limit which older/concurrent updates can be imported [S04, S06].
6. Generate a unique Loro PeerID per concurrent writer/session. Do not assign the same constant ID to two laptops or running processes; duplicate operation IDs are a corruption risk. The documented default is a random ID for each LoroDoc instance, including a reloaded copy (S05; Rust API warning in S04).

The relay can be a small team service for update persistence/exchange, not an always-online editor or chat. Its operator, authentication method, encryption at rest/in transit, authorization model, retention, backup, and threat model are unresolved. If operating a relay is unacceptable, an explicitly supported manual update-bundle exchange is an alternative, but it increases staff workflow burden and needs the same import, authentication, replay, and backup policy.

## Publication, visibility, and alternatives

Treat approved releases as separate immutable artifacts, not as a mutable “approved” boolean on the live sheet. Persist an immutable payload/manifest and its exact-byte SHA-256. Stage view shows a readable release number and hash, approval identity/time, and whether it is the release selected for this run. Rehearsal edits and relay sync never mutate that artifact. Publishing an emergency revision creates another release and an auditable selection change. A content hash detects artifact changes; it does not establish who was allowed to approve. Role authority and emergency override policy require owner decisions.

Alternative mechanisms considered:

| Mechanism | Useful evidence | Cost or limitation for this component |
|---|---|---|
| Loro Rust | Native Rust API; MovableList; text/map types; history/frontiers; incremental import/export; local-first model [S01–S06]. | No network/storage or human conflict UI. MovableList deterministically resolves concurrent move placement; app must preserve intent for a human decision. Rust crate and JS/WASM release versions must be checked separately. |
| Automerge Rust | Local-first history/sync and fine-grained maps/lists. Concurrent writes to the same property retain alternatives accessible through conflict APIs [S08–S10]. | Ordinary read chooses deterministic winner and assigning again clears the conflict; inspect before overwriting. Rust sync docs assume reliable in-order transport. No reviewed native move type; moving by delete+insert needs an identity and deduplication policy. |
| Yjs | Shared arrays/maps/text; relative positions for text comments; IndexedDB-backed offline persistence in browser deployments [S11–S12]. | Browser IndexedDB is not a Rust desktop storage adapter; native app provider/binding is additional work. Cue-level identity and move conflict presentation still need app policy. |
| ShareDB/JSON OT | Node server, OT plugins, historical versions, and advertised reconnect sync [S13–S14]. | More server dependence. Its getting-started reconnect example says closed-socket buffering has undefined behavior and disables the WebSocket queue; durable local outbox and replay must be app-owned. OT transformation still does not supply the approved-run-sheet workflow. |
| Hand-built revision log | Can make business conflicts explicit and narrowly tailored. | Custom causal merge, list movement, recovery, test matrix, and version migration are expensive and easy to get wrong. Retain as fallback if the candidate CRDT fails focused prototypes. |

Loro's project history shows both ongoing engineering and concrete edge cases. Issue #957 concerned a Node/WebRTC adapter import path on loro-crdt 1.11.1; merged PR #958 changed op-count access to avoid re-locking the operation log and added regression coverage. That is evidence to test the actual adapter/import path, not evidence of a currently broken Rust crate. The observed loro-crdt 1.16.4 JS/WASM release adds all-or-nothing failure handling and fixes around imports, diffs, unknown containers, and PeerID collisions; it must not be presented as a tested property of Rust loro 1.16.2 without checking that crate's release/code [S06–S07].

## Owner decisions and unknown facts

Resolve these before freezing product behavior:

1. How many crew members/devices and how many documents may edit concurrently? What maximum cue count and typical sheet size should guide structure/performance tests?
2. How long can a laptop stay offline, and how long must the relay retain updates for a returning device?
3. Are comments anchored only to a cue, or must they attach to a text range? Can comments be edited/deleted, resolved, or replied to?
4. Should stage staff see rehearsal comments and role assignments in a published run sheet? Which metadata must be exported?
5. Who can adjudicate conflicts and who can publish? Is emergency override allowed? Must overrides identify a reason?
6. Should a rehearsal pin a named release for its duration or follow the latest approved release? How should viewers see a newer version during an active run?
7. Who operates the relay? What accounts/invite mechanism is allowed, and what are requirements for encryption, access revocation, backup, retention, and recovery?
8. How should semantic duplicate cues created independently offline be reviewed? Which fields/roles are restricted or validated?
9. What release formats and schema migration window are needed? Does an offline device need to open older published releases indefinitely?

Unknown cue counts remain an input to sizing, not a reason to omit the mechanism design.

## Proposed validation (not run)

Build a small throwaway witness against the pinned Rust crate and target UI binding before committing to the architecture. Use independent replicas created from one agreed base and unique PeerIDs.

- Concurrent edits: insert different cues at the same gap; concurrently move the same cue to different before/after anchors; move different cues; edit different and same text fields; change one role/timing field to competing values; add comments; delete a commented cue; edit/reorder while the other replica is offline. Reconnect and deliver updates in duplicate, reverse, delayed, batched, and incomplete order.
- Invariants: all replicas converge after the complete update set; both nonconflicting edits survive; every incompatible concurrent field/move candidate is present in the conflict UI and can be resolved; no comment silently changes cue; deleted anchors remain explicit; no LWW winner is shown as approved without a decision.
- Recovery and delivery: crash at local write, outbox append, socket send, relay commit, acknowledgement, import, and local checkpoint; reopen and replay. Verify no success acknowledgement precedes durable local state and no retry loses/reorders semantic work. Simulate relay outage and missing causal dependencies.
- Publication: publish a specific frontier, continue editing and resolving new conflicts, reconnect stage viewers, and compare the exact stored artifact bytes/hash and visible release identity. Verify unresolved conflict gate, approver metadata, version selection/pinning, and explicit emergency revision.
- Compatibility and load: test the pinned Rust version, schema upgrades, backup/restore, old supported exports, malformed/duplicate updates, duplicate PeerID collision handling and application-level uniqueness checks, long offline history, and the confirmed maximum cue/team/offline envelope on target laptops. Include crash-safe filesystem/database behavior and a multi-device relay test.
- Usability: give crew unfamiliar with the model realistic same-cue and same-sheet conflicts; verify that they can identify the affected cue, compare variants, choose/merge/defer, understand which release stage staff are viewing, and see whether edits remain unsent.
