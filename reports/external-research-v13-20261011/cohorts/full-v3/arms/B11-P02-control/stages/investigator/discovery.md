# Rehearsal cue-sheet synchronization: independent discovery (pre-release)

## Source and method

The scope is the released brief only: an offline-capable desktop rehearsal component for ordered cues, timing/text, role assignments, cue comments, intelligible handling of incompatible edits, explicit approved run sheets, visible version identity, and a modest relay. No product is preselected by the brief. Primary documentation, Rust API/code documentation, package release history, and an implementation incident were reviewed. The exact tentative plan remains unreleased and unread.

## Candidate direction to compare with the released plan

Evaluate Loro's Rust crate first because it combines a native Rust API with MovableList, Map, Text, history/frontiers, and incremental import/export (S01–S06). This is a fit hypothesis, not a final choice. The library does not supply networking or app persistence; those remain component responsibilities (S04). The current docs.rs Rust API page resolved to loro 1.16.2 during this review; GitHub's newer loro-crdt@1.16.4 release is the JS/WASM package, so do not silently treat those package versions or fixes as identical (S04, S06).

Model the data around a durable random cue_id, independent of list index, displayed cue number, title, or current order. Use a MovableList<CueId> for order; maps keyed by cue_id for timing, text, and role-assignment records; and durable comment records keyed by comment_id with an immutable anchor_cue_id. Loro warns that ordinary lists combined with delete+insert to simulate moves can duplicate a logically moved item under concurrent moves; MovableList has an explicit move operation and its example converges to one placement (S01). Reordering therefore does not rewrite comment anchors. Keep a deleted cue as a tombstone while it has comments; show those comments in an “anchor removed” state and require an explicit repair/re-anchor action rather than binding by index. Generate a fresh ID for genuinely new cues. If a comment later needs a text-range anchor, persist two Loro cursors instead of offsets; unresolved/deleted targets remain visibly unresolved (S02).

## Merge policy the app must add

CRDT convergence is not the same as understanding the crew's intent. Loro's concurrent-move example deterministically selects one merged order from two different offline moves; it does not itself expose an “ask the stage manager” prompt (S01). Also, Loro Map conflict rules can hide one concurrently created regular child container under the same logical key; use unique IDs for per-cue/comment entities and ensure_mergeable_* when multiple peers may lazily create a shared child container (S03). Never show a deterministic winner as though it were human-approved.

Persist a small append-only intent record per user edit: unique operation ID, entity/field, candidate value or move target, author/session, and the Loro frontier the user had observed. On reconnect, compare same-field candidates using causal frontiers. If edits are concurrent and incompatible, retain all candidates, mark the current deterministic view as conflicted, and present a short side-by-side choice; a later resolution record names the candidates it resolves and the approved value/order. For cue text, conservatively surface concurrent edits to the same cue for review (including a merged-text diff) rather than silently assuming overlap semantics. Let character-level merge preserve non-overlapping work, but keep the review indicator until someone accepts the merge or chooses a candidate. Loro exposes frontiers and historical checkout; the conflict classification, audit records, human UI, and publish gate are app design work, not claimed as built-in capabilities (S04). Concurrent inserts at distinct cue IDs can merge automatically; duplicated or semantically repeated cues remain an owner decision.

Comments are durable shared data (author, timestamp, text, anchor cue ID, status/replies); presence such as “editing now” is ephemeral and can be omitted for the first release. Separate operational presence from comment history.

## Offline sync and recovery boundary

Each laptop edits its local persisted document without a network. A small team relay is an optional transport/storage endpoint, not an editor or chat product: clients push/pull Loro updates when available, and the relay stores versioned update blobs or snapshots with an access-controlled team/document key. Keep a durable local write-ahead outbox and mark updates delivered only after relay acknowledgement. Loro guarantees convergence when all peers receive the same updates regardless of ordering or duplication, and its import status reports missing causal dependencies; if pending is nonempty, request those ranges and do not label the replica synchronized (S03–S04). A local snapshot can be recovered and new updates exchanged after reconnect. Loro recommends periodic full snapshots for import performance; a shallow snapshot limits which earlier/concurrent updates can still be imported, so use it only with a planned retention/compaction boundary (S04, S06).

Do not reuse one Loro PeerID across concurrent writers. The docs default to a random ID per document/session; a copied profile, cloned process, or hand-assigned per-device ID without a single-writer lock can produce duplicate operation IDs (S05, S06). The relay does not make concurrent edits safe by itself and should not be treated as the conflict resolver. Authentication, membership, encryption, relay hosting/backup, offline-duration retention, and data access during rehearsals need owner/IT decisions.

## Explicit publication boundary

Represent a rehearsal document and an approved run sheet as separate identities. “Publish” takes a committed rehearsal frontier, serializes that exact state into a new immutable release record, and attaches a content hash, readable release number, approving person, and approval time. The release screen names the exact release/hash and approval metadata; staff must select which published release they are viewing. Later rehearsal operations continue on the working document and cannot mutate the release bytes. Require zero unresolved conflicts before ordinary publication; any emergency override must be explicit, attributed, and explained. A hash alone does not establish authorization; actual approver and who may publish are user-specific decisions. Loro history/frontiers aid version capture but are not an approval system (S04).

## Alternatives and real implementation lessons

- Automerge (Rust/JS) has local-first documents, history, sync, fine-grained map/list updates, and inspectable concurrent property values. Its default read is a deterministic winner; getConflicts exposes alternatives, but the conflict disappears when the field is assigned. A UI must capture and resolve it deliberately. Its Rust sync protocol assumes a reliable, in-order stream, so the app/relay must provide that transport contract (S08–S10). It is a credible Rust alternative, but the examined list API is not a dedicated move operation; moving by delete+insert needs explicit identity/deduplication policy.
- Yjs offers Y.Array/Y.Map/Y.Text, stable relative text positions useful for range comments, and offline persistence through y-indexeddb. The cited provider targets browser IndexedDB; the docs say native apps need an environment-appropriate database provider. This is attractive if the component becomes web/JS-centric, with more integration work for a Slint/Rust desktop app (S11–S12).
- ShareDB/JSON OT provides a Node server, database history, OT type plugins, reconnection/offline change-sync features. It is plausible if a server-authoritative model is desired, but its own reconnecting-WebSocket example says buffering while the socket is closed has undefined behavior and disables the socket queue. A durable local outbox, conflict/user-approval model, and relay service would still need to be designed; this is more server dependence than the brief needs (S13–S14).
- Explicit snapshots plus an append-only application operation log is a lower-library alternative that makes each conflict and approval policy visible, but requires custom merge, recovery, and ordering logic. Keep as fallback only if a small CRDT prototype fails the acceptance matrix.

The Loro issue history is relevant to implementation risk, not a claim that a current release is broken: issue #957 reports import-time lock-order panics in loro-crdt@1.11.1 under a third-party Node/WebRTC adapter and a high-replica workload; linked PR #958 addressed reentrant locking. The 1.16.4 JS/WASM release history also records transactional failure handling and peer-ID collision checks. This makes adapter-level reconnect/import/load testing and pinned-version migration tests necessary; the issue's WASM/third-party adapter environment does not establish a Rust-native defect (S06–S07).

## Checks and open facts

Research actually executed: browsed the linked primary docs, Rust API/source documentation, GitHub release/issue history; read the released brief. No code was downloaded or run, no service was deployed, and no concurrency/recovery witness was executed. The exact plan-release helper and released plan remain pending.

Proposed validation, not run: (1) two or more isolated local replicas edit while disconnected, then exchange duplicate, reordered, delayed, partial, and missing-dependency updates; all converge and pending ranges are fetched; (2) independently insert/reorder/edit the same and different cues, change role/timing scalars, add comments, and delete/revive anchors; no comment changes cue, no edit disappears, and every incompatible concurrent same-field move/text/assignment is visibly resolvable; (3) crash/reopen before and after local flush, relay send, and relay acknowledgement; (4) publish a selected frontier, continue editing, and verify release bytes/hash/identity never change; test unresolved-conflict gating and explicit override; (5) import/export/migrate supported old and new snapshots, duplicate PeerID rejection, and malformed update rollback; (6) exercise at least the team-confirmed cue-count and outage-duration envelope on target laptops, including large history and multi-peer relay load.

Owner facts still needed: expected team size, cue volume and maximum sheet size, longest planned disconnection, whether comments need text ranges or only cue anchors, who may approve/publish and whether emergency override is allowed, whether staff need shared latest publication or named release selection, retention/backup/security constraints, relay hosting responsibility, and handling of duplicated semantic cues. Unknown cue counts do not remove the feasible mechanism research above.
