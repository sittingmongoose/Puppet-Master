# Concrete monitored-cost option — not certified for the authorized strict caps

No arm launches under this proposal. The present gate denies paid admission because no frozen, independently verified cost enforcer exists. This document describes a reviewable alternative; it does not turn retrospective usage into a hard spending guarantee.

The copied Codex adapter receives `thread/tokenUsage/updated` after responses and retains `total` and `last` categories. It already creates one native Goal per job. Installed schema exposes `ThreadGoalSetParams.tokenBudget`, but its enforcement boundary and treatment of an in-flight response were not established by protocol preparation. The isolated adapter now explicitly requests `serviceTier=default` and rejects a thread that does not confirm it, before Goal activation. The copied OMP adapter records `model_usage` entries, including assistant/auxiliary usage, after native events; complete usage coverage and a provider-enforced request ceiling are not established.

A possible monitored mode would maintain one arm-wide locked journal containing observed token-category valuation, per-active-worker outstanding response headroom, incomplete/uncaptured usage, and every admission/retry/restart. Prior finished request headroom is refunded only after its receipt is validated; unknown or interrupted request liability remains reserved. Before admission require `observed_upper_usd + outstanding_headroom + new_headroom <= arm_cap`; after every usage update recompute and immediately stop admission/cancel all active native work if that inequality no longer holds. An independent watchdog must remain active during native work, not merely read receipts after campaign completion. Both arms keep the identical scheduler and policies.

Root supplied the official Astra limits (1,050,000 context, 128,000 output) from https://developers.openai.com/api/docs/models/gpt-6-astra. On the preserved September 8 basis and confirmed default service tier, the proposed maximum single-response headroom is $35.85: 1.05 million input at the maximum applicable long-context cache-write category ($25/M) plus 0.128 million output at the applicable long-context output rate ($75/M). This needs independent confirmation of category inclusivity and request context semantics. Unknown Fast tier would double applicable rates. This headroom is per upstream response, NOT per native job: a native Goal may make many responses. A fixed nonrefundable per-job reservation of $35.85 would therefore be invalid. The harness's current generic per-job reservation mechanism may only receive a proven whole-job bound; none is supplied.

The unresolved issue is the observation/cancellation race: a native server can autonomously dispatch another request before its client observes the preceding usage notification. A native Goal token budget may address this only if it enforces at the relevant request boundary and its accounting includes the same categories. Without that evidence, one extra response per active worker can remain exposed even after a threshold-triggered cancellation. Failed-request charges and uncaptured support remain separately unknown. DeepSeek also needs a supported request/Goal bound and complete usage treatment, rather than an invented token cap.

Consequently this mode would report a measured stop threshold and a documented outstanding liability window, not promise spending at most $150/$60. Using it requires the user to accept that change explicitly. The original strict-cap path remains blocked pending a supported enforcement mechanism (for example a provider-backed hard cap or a verified native per-request admission boundary). No retrospective receipts, zero-valued unknowns, or arbitrary declaration in a gate file can certify the original limit.

## Installed-runtime probe result

One authorized synthetic Astra Medium/default-tier probe set native `tokenBudget=1`. The runtime completed the first response and the alpha shell command, entered `budgetLimited`, and then generated a final summary response in the same turn. Beta and gamma were not executed. The first response used 14,217 total tokens. The final summary response used another 14,505, including 13,952 cached input tokens. Captured total usage was 28,722 tokens, while native Goal `tokensUsed` was 14,770, exactly total minus cached input. Thus this observed Goal meter omits billed cached input and still allows a paid summary after the budget limit. The default tier was confirmed; the event-reported context window was 258,400. See `budget_probe_sanitized.json` for exact source paths, SHA-256 and event lines.

This supplies concrete evidence against treating native Goal tokenBudget as a strict dollar-cap enforcer. No additional paid tests or modifications to the frozen scheduler followed this result. The monitored alternative above remains a proposal requiring an explicit change to the at-most monetary-cap requirement; it is not implemented or approved. Preserving the strict limits requires an enforcement mechanism whose request boundary and complete priced usage are supported. The tested scheduler can be reused unchanged once that separate dependency is resolved.
