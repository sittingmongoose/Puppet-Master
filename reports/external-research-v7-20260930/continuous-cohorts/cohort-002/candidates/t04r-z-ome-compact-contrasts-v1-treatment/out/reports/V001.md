## 2. Executive summary

1. An OME-Zarr 0.5 fileset is a Zarr v3 group/array hierarchy whose OME metadata lives in `zarr.json` attributes under the namespaced key `ome`, with a version string that must be consistent within a hierarchy (S003:67–72, 149–156). Image discovery must be metadata-driven; level and folder names are arbitrary (S003:91–94).
2. Multi-image `bioformats2raw.layout` collections and high-content-screening (HCS) plate/well hierarchies are format-defined ways images hide inside a fileset; a conforming reader SHOULD NOT default to opening only the first image (S003:256–275, 120–148, 530–560, 744–752). The thin plan's "lists the images it finds" needs both, and HCS is currently absent from the plan.
3. Multiresolution navigation is fixed by metadata: `datasets` paths ordered highest→lowest resolution, per-level transforms with exactly one scale, optional translation after scale, optional group-level transforms applied after per-level ones (S003:304–316). *How* to pick a pyramid level for the current view is not specified by the format — a product decision (only an informative hint exists, S003:396).
4. Correctly calibrated coordinates require composing per-level and group-level transforms in order, accepting path-referenced (not only inline) transform vectors, and degrading gracefully when axis `unit`/`type` are missing or custom (S003:276–316, 167–174).
5. Channel rendering comes from the *optional, transitional* `omero` metadata; its `channels`/`color`/`window` obligations hold only if `omero` is present; defaults for time/plane (`rdefs.defaultT/defaultZ`) appear only in informative example content (S003:398–430). Fallback rendering without `omero` is a product decision.
6. Label overlays have firm discovery/integrity rules (labels list, integer pixels, equal scale-level count) but geometry is hedged ("usually" same dimensions/transforms; dimensions "or 1"), so overlay code cannot assume 1:1 grids (S003:431–474, 106–108).
7. The capture contains no implementation/tool evidence (S003:813–814) and no live fetch is permitted, so the brief's "actual reader implementations" research is a visible unresolved area, not silently dropped (R09).
8. Nothing in this report reflects executed tests; Section 9 lists proposed, UNEXECUTED validation (R07).

## 3. Group 1 — opening a fileset, listing/selecting images, navigating multiresolution data

### A1. Container and discovery: Zarr v3 hierarchy, `ome` namespace, version consistency

**Claim (supported).** OME-Zarr 0.5 is implemented on Zarr format version 3 (S003:67–69); OME-Zarr metadata is stored in the `zarr.json` files of the hierarchy under the namespaced key `ome` in attributes, and the `ome.version` string MUST be consistent within a hierarchy (S003:149–156). Group-level attributes of an image group include `multiscales` and the transitional `omero` (S003:87–89, 295, 398–400). Any Zarr feature — codecs, chunk grids, chunk key encodings, data types, storage transformers — may be used unless explicitly disallowed (S003:70–72). The hierarchy may exist locally or behind HTTP/object storage (S003:73–77); the Slide Scout product boundary restricts it to local reading (brief; the format itself does not).

**Classification.** Established obligations.

**Limits / counterevidence (R04, R03).** Layout examples show a `.zarr`-suffixed top folder and integer level names (S003:82–94), but the normative text fixes neither: level names are explicitly arbitrary with ordering carried by `multiscales` (S003:91–94). Keying discovery on folder names would be an implementation choice, not a format rule. That a reader must tolerate the full Zarr feature surface is this report's inference from S003:70–72 — the source states the allowance; the interop failure mode for a narrower reader is inferred.

**Plan implication.** Discover images by detecting `ome.multiscales` in group `zarr.json`, validate `ome.version` consistency (S003:155–156) as an explainable-error hook, and do background reads through a Zarr-v3-capable reader (sharding/codecs); where an array uses unsupported features, explain rather than crash (plan's own goal).

### A2. Multi-image collections: transitional `bioformats2raw.layout` series, with explicit reader duties

**Claim (supported, conditional — R01).** A top-level group whose OME metadata carries `bioformats2raw.layout` MUST have the value `3` (S003:256) and implicitly describes a series of images (S003:175–181, 182–191). Under condition C = "the `OME` Zarr group exists", it MAY contain a `series` attribute; if so, `series` MUST be a list of strings (paths to image groups) whose order MUST match the `Image` element order in `OME/METADATA.ome.xml` when provided (S003:264–267). Under condition C = "no `series` attribute and no plate", separate multiscales images MUST be stored in consecutively numbered groups starting from 0, and every multiscales group MUST represent exactly one OME-XML Image in the same order (S003:268–270). If plate metadata is present alongside, the `plate` key MUST also be present and takes precedence; collections of images cannot currently be mixed with plates (S003:204–206). The companion `OME/METADATA.ome.xml` is SHOULD-grade and, when present, MUST adhere to OME-XML using `<MetadataOnly/>` (S003:257–260).

**Reader duties.** Conforming readers SHOULD make users aware that more than one image exists (SHOULD NOT default to only opening the first); MAY use `series` to determine displayable groups; MAY show all images or offer a choice; MAY ignore other groups/arrays at the root (S003:271–275).

**Classification.** Conditional obligations (MUST parts); SHOULD-graded reader duties; transitional metadata whose reading implementations may be expected (MUST) or encouraged (SHOULD) to support (S003:60–64). The concrete listing/choice UI is a product decision.

**Plan implication.** The plan's "lists the images it finds" is under-specified for series filesets: listing must surface collection members and must not silently open image 0 (S003:272). Concrete thin-plan gap.

### A3. High-content screening: plate → row → well → field is the only path to the images

**Claim (supported, conditional on HCS filesets — R01).** In an HCS dataset, three groups MUST be defined above the images: the group above the images is the well and MUST implement the well specification; the group above the well row defines a row; the group above the row is the plate and MUST implement the plate specification (S003:118–127). A well row group SHOULD NOT be present if no images exist in the row; a well group SHOULD NOT be present if no images exist in the well (S003:128–129). Plate metadata MUST contain `columns`, `rows`, `version`, and `wells`; each well entry MUST have `path` (a row name + `/` + column name, no extra leading/trailing directories), plus `rowIndex` and `columnIndex`, all 0-based and mutually consistent (S003:530–560); `field_count` and `name` are SHOULD-grade (S003:538–541); `acquisitions` is MAY, but when present each acquisition MUST have a unique integer `id` ≥ 0, with further MUST-graded value constraints (S003:518–529). Well metadata MUST contain `images` (each entry MUST have an alphanumeric, case-sensitive, duplicate-free `path`; under condition "multiple acquisitions in the plate" an `acquisition` key MUST be present and match a plate acquisition) and SHOULD contain `version` (S003:740–752).

**Classification.** Obligations on conforming filesets. Whether Slide Scout renders a plate map or flattens wells/fields into its image list is a product decision; the plan is currently silent on HCS — a gap for the brief's "find images within a fileset", because in HCS filesets images are reachable only through plate→row→well→field paths (S003:118–148).

**Limits.** The capture defines metadata structure, not UI; nothing in S003 mandates plate visualization (scoped to S003, R05).

### A4. Multiresolution layout: ordering and fallback rules are fixed; level choice is not

**Claim (supported).** Each `multiscales` dictionary MUST contain `axes` (S003:299): length 2–5 and equal to the dimensionality of the image arrays (S003:300); it MUST contain 2–3 `space` entries and MAY add one `time` and one `channel` or null/custom entry; entries MUST be ordered by type — time first, then channel/custom, then space (S003:301–302). Under condition "three spatial axes where two correspond to the image plane (yx) stacked along z", spatial axes SHOULD be ordered `zyx` (S003:303) — recommended, not guaranteed, so axis order must always be read, never assumed. It MUST contain `datasets`: each entry MUST have `path` relative to the group, and paths MUST be ordered from largest (highest resolution) to smallest (S003:304–306); every level MUST have the same dimensionality, ≤ 5, matching `axes` (S003:307). Under condition C = "only one multiscales entry", use it; otherwise the user can choose by name, with the first entry as fallback (S003:388–389). `name`, `type`, `metadata` on the multiscales dict are SHOULD-grade (S003:317–319).

**Classification.** Obligations (MUST) plus one conditional SHOULD (`zyx`).

**Product decision (format-silent).** The plan's "viewer chooses an available pyramid level appropriate for the current view" has no normative heuristic in S003; the only hint is an informative pseudocode comment, "Or perhaps choose based on chunk size" (S003:396) — informative, not a rule (R03).

**Plan implication.** Level enumeration/selection must follow `datasets` order and `coordinateTransformations`, never name sorting (S003:91–94, 305–306); multiple named multiscales need name-based user selection with first-entry fallback (S003:388–389).

## 4. Group 2 — channel/time/plane display, coordinate details, associated label overlays

### B1. Axes metadata: names are guaranteed; types and units are not

**Claim (supported).** Each axis MUST have `name`, unique across all `name` fields (S003:167–168); `type` is SHOULD-grade — SHOULD be `space`, `time` or `channel`, but MAY be any other custom string (S003:169); `unit` is SHOULD-grade — SHOULD be a UDUNITS-2 string from the capture's enumerations for space and time axes (S003:170–172); the axes length MUST equal the array dimensionality (S003:173). The `dimension_names` attribute MUST be included in the `zarr.json` of each multiscale-level array and MUST match the `axes` names (S003:174; clarified as MUST in revision 0.5.2, S003:825–827).

**Classification.** Mixed: name/dimension_names obligations; SHOULD-graded type/unit.

**Plan implication.** The details panel (dimensions, units, coordinates) can rely on axis names but must degrade gracefully when `unit` or `type` is missing or custom — show a unit only when present and label custom types as such, so the brief's "correctly calibrated coordinates" is never fabricated. Presentation defaults when `unit` is absent are a product decision.

### B2. Physical coordinates: exactly one scale per level; translation after scale; group-level transforms applied after

**Claim (supported, with conditionals — R01).** Each `datasets` entry MUST contain `coordinateTransformations` mapping data coordinates to physical coordinates for that level (S003:308); only types `translation` and `scale` are permitted there (S003:309). They MUST contain exactly one scale transformation giving pixel size in physical units or time duration; under condition C = "scaling information is not available or applicable for one of the axes", the value MUST express the scaling factor between that resolution and the first resolution for the axis, defaulting to 1.0 where there is no downsampling (S003:310). A translation MAY be present (offset from origin) and MUST be listed after scale (S003:311); scale and translation array lengths MUST equal the axes length (S003:312). The multiscales dictionary MAY add group-level `coordinateTransformations`, applied to all resolution levels after the per-level ones, under the same type/order rules — e.g., a time-axis scale shared by all levels (S003:314–316; example S003:368–374). In general, transformation lists are applied sequentially in order; each entry MUST have a `type`; translation/scale vectors may be inline float lists or binary data at a `path` in the container; `identity` is the default and typically implicit (S003:276–293).

**Classification.** Obligations (MUST parts); path-stored vectors are valid inputs a reader must accept for interoperability, though inline lists are the common form in examples — the commonality claim is inference from the examples (R03).

**Plan implication.** Calibrated readout requires composing, in order, per-level then group-level transforms per axis, including the per-level fallback factor rule and the group-level time-scale idiom (S003:310, 314–316). A thin reader accepting only inline scale arrays will fail on valid filesets using path-referenced vectors (S003:285–289). Displayed coordinates carry the axis unit only when present (B1).

### B3. Channel display: `omero` is transitional and optional; its channel/window fields are conditional obligations

**Claim (supported, conditional on `omero` presence — R01).** `omero` is transitional render metadata under the group-level key `omero` (S003:398–400). It is optional; under condition C = "`omero` present", it MUST contain `channels` (an array of dictionaries), and each channel MUST contain `color` (a string of 6 hexadecimal digits, RGB) and `window`; `window` MUST contain `min` and `max`, and MUST also contain `start` and `end` (S003:426–430). The example additionally shows `active`, `coefficient`, `family`, `inverted`, `label`, and `rdefs` with `defaultT`, `defaultZ`, `model` ("color" or "greyscale") (S003:401–423) — example content, informative, not guaranteed present (R03); the normative MUST list (S003:426–430) does not include `rdefs`, so a conformant fileset may omit `rdefs` even when `omero` is present. The capture's own wording for the window fields: `min`/`max` are "the minimum and maximum values of the window"; `start`/`end` are "the start and end values of the window" (S003:429–430); the operational reading (data range vs. initial display window, suggested by example values 0/65535 vs 0/1500, S003:411–416) is inference, not source-stated.

**Classification.** Presence optional; field obligations conditional on presence; default rendering when `omero` is absent is unspecified → product decision.

**Plan implication.** Channel visibility controls should initialize from `omero` when present (active/color/window) and fall back deterministically when absent or partial; do not assume `rdefs` exists.

### B4. Time and plane navigation: axis presence is conditional; defaults exist only in `omero` example content

**Claim (supported).** A multiscales image MAY have one `time` axis and one `channel` (or null/custom) axis in addition to 2–3 space axes, ordered before the spatial axes (S003:301–302); time units come from the UDUNITS-2 time enumeration (S003:172). Image arrays are up to 5-dimensional with the time axis before channel before spatial axes (S003:96–97). The only time/plane default hints in the capture are `rdefs.defaultT`/`defaultZ` in the informative `omero` example (S003:419–423), conditional on `omero` presence and not itself guaranteed (B3).

**Classification.** Conditional structure obligations; informative defaults.

**Plan implication.** Time-point and plane controls must be driven by the axes actually present — including custom axis types (S003:169, 301) — not by a fixed t/c/z/y/x template; when defaults are absent, the viewer needs its own deterministic initial time/plane choice (product decision).

### B5. Label overlays: firm discovery/integrity rules; styling is SHOULD/MAY; geometry is hedged

**Claim (supported).** Label images live in a `labels` group nested inside the image group (S003:437; layout S003:102–110). The `labels` group's `zarr.json` MUST contain a `labels` key whose value is an array of paths to the labeled multiscale images, and all label images SHOULD be listed (S003:441–442). Label pixels MUST be one of the eight integer types `[uint8, int8, uint16, int16, uint32, int32, uint64, int64]` (S003:438–439); intermediate groups between `labels` and the label images are allowed but MUST NOT contain metadata (S003:439–440). A label image's `zarr.json` MUST implement the multiscales specification, and its `datasets` MUST have the same number of scale levels as the original unlabeled image (S003:454–455). Layout guidance states each label dimension should be either the same as the image's corresponding dimension or 1 if irrelevant (S003:106–108; lowercase "should" in a §1.1 layout comment — normative-grade per S003:875–878 but located in layout description). The association statement says label images are produced in the same coordinate system as the corresponding image, "**usually** having the same dimensions and coordinate transformations" (S003:432–433) — a hedge, not a guarantee. Styling: the label image SHOULD contain an `image-label` object, which SHOULD contain `colors` (value MUST be a JSON array) and `version` (value MUST be a string) (S003:456–460); conforming readers SHOULD display labels using those colors (S003:461); each `colors` entry MUST contain `label-value` (integer) and MAY contain `rgba` (four integers 0–255 inclusive; fourth = alpha/opacity); additional keys are allowed (S003:461–466); `properties` and `source` are MAY-grade — `properties` entries MUST contain `label-value` and may carry arbitrary per-label key-values that need not match across entries (S003:467–471); `source` MAY include `image`, a relative path to the source image group, default `../../` (S003:472–474).

**Classification.** Discovery/integrity = obligations; display styling = SHOULD/MAY; geometry = hedged (R04: claim "overlay aligns 1:1" carries counterevidence "usually" (S003:432–433) and applicability limit "same dimension **or 1**" (S003:106–108) — both retained).

**Plan implication.** "Aligned label overlays" must not assume identical grids: render by `label-value`→rgba mapping (deterministic fallback palette when `colors` is absent — product decision), broadcast/handle size-1 axes, and locate associated labels via the `labels` list plus `source.image` (default `../../`) (S003:441–442, 472–474).

## 5. Cross-cutting findings

### X1. Normative language and JSON hygiene
RFC 2119 keywords govern (S003:56–59); lowercase occurrences remain normative because all text is normative except explicitly non-normative parts, examples and notes (S003:869–888). JSON objects MUST NOT contain comments, even though capture examples include them for clarity (S003:65–66) — a writer-side MUST; on the reader side it defines an invalid-input class that feeds the plan's "understandable feedback rather than a crash" goal (error-handling disposition is the plan's own).

### X2. Version surface and migration
The current released version is 0.5; migration scripts between numbered versions are promised; data written by editor's drafts "will not necessarily be supported" (S003:25–27). History: 0.5.0 moved OME-Zarr to Zarr v3 (S003:831–833); 0.5.1 re-added the improved `omero` description (S003:828–830); 0.5.2 clarified `dimension_names` as MUST (S003:825–827). `ome.version` MUST be consistent within a hierarchy (S003:155–156). **Unresolved (scoped to S003, R05):** the capture contains no statement about reading filesets written under 0.4.x or earlier; given the 0.5.0 Zarr-version switch, backward-compatibility of a 0.5 reader on 0.4 filesets is unknown from this capture — flagged (as inference) as an interop risk to resolve outside this scope, not a source-stated fact.

### X3. Transitional metadata policy
Transitional metadata is intended for future removal; implementations may be expected (MUST) or encouraged (SHOULD) to support *reading* it, while *writing* is usually optional (MAY) (S003:60–64). Transitional items relevant to Slide Scout: `bioformats2raw.layout` (S003:175–181; an upcoming specification will replace it) and `omero` (S003:398–400). For a read-only viewer the read side is what matters; dropping transitional read support would reduce interoperability with filesets that already exist in the wild (S003:180).

### X4. Implementations: the capture has no tool evidence
Specification §4 is a bare pointer ("See Tools.") with no listing in the capture (S003:813–814). The brief asks for research broad enough to cover actual reader implementations; within the fixed source scope this cannot be supported, and no claim in this report is based on any tool implementation. Visible unresolved area (R09) and the top undeveloped lead (Section 8).

### X5. Key spelling is exactly as specified, not normalized
Multi-word keys "should" use camelCase, but the specification notes some parts do not obey and will be updated in due course (S003:809–812); normative text uses `image-label` (S003:456), `label-value` (S003:462), `field_count` (S003:538), `maximumfieldcount` (S003:524), `rowIndex`/`columnIndex` (S003:557–558). Inference (R03): readers must match keys exactly as spelled in the normative text; case/separator normalization would be an implementation choice with interop risk, not a format rule.
