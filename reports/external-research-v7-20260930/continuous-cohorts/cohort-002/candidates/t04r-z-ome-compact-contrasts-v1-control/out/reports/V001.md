## 1. Purpose and method

This report investigates what the OME-Zarr 0.5 format obligates, permits, and leaves open, as needed by the Slide Scout thin plan (`inputs/plan/Viewer.md`): a read-only desktop viewer that opens a local OME-Zarr 0.5 fileset, lists the images it finds, navigates multiresolution data, shows channels/time points/planes, overlays label images, and displays calibrated coordinates, remaining responsive on large datasets and explaining data it cannot display.

The full product brief (`inputs/brief.md`) asks for format obligations, optional capabilities, and product decisions to be distinguished, and for reader-implementation compatibility to be researched. Per the assignment, the only admitted evidence is the S003 normative capture; the brief, plan, and task cards are treated as assignment context, never as evidence about the format. Source lines are cited as `S003 L<start>-L<end>`.

Requirement tags used below:
- **[OBLIGATION]** — a MUST/MUST NOT/SHALL-level rule on conforming writers or readers (RFC 2119 keywords per `S003 L57-L59`, `L872-L874`).
- **[RECOMMENDED]** — SHOULD-level; a strong expectation that may be justified to depart from.
- **[OPTIONAL]** — MAY-level or conditional capability.
- **[INFORMATIVE]** — example or illustration; non-normative (`S003 L877-L883`).
- **[PRODUCT DECISION]** — not fixed by the format; Slide Scout must choose.
- **[UNRESOLVED]** — cannot be settled from S003 alone.

Findings carry IDs `F###` (register in §12 and in the acquisition ledger) and consistency observations `C#` (§8).

## 2. Executive summary

1. OME-Zarr 0.5 sits on **Zarr format version 3**, and expressly allows *all* Zarr features — codecs, chunk grids, chunk key encodings, data types, storage transformers — unless explicitly disallowed (`S003 L68-L72`). A conforming reader is therefore a fairly general Zarr v3 reader; the Zarr v3 specification itself is **not** part of the admitted capture, which is a hard coverage limit (§9).
2. "Opening a fileset and listing images" means traversing a Zarr hierarchy and recognizing three layouts: plain multiscale images, bioformats2raw multi-image collections (transitional), and HCS plate/well trees. The spec requires readers to surface multiple images rather than silently opening the first (`S003 L271-L275`).
3. Physical coordinates are fully determined by per-level `scale` (exactly one, mandatory) plus optional `translation` (after scale), with possible group-level transforms applied afterwards (`S003 L308-L316`); axes carry names (mandatory) and types/units (SHOULD, UDUNITS-2) (`S003 L166-L173`).
4. Channel/time/plane display defaults come only from the **transitional, optional** `omero` metadata; only `channels[].color` and `channels[].window{min,max,start,end}` are MUST-level (`S003 L426-L430`). The viewer must degrade gracefully when it is absent.
5. Label overlays are discoverable via a mandatory `labels` key on the labels group (`S003 L441-L442`); label images must be multiscales with the same number of levels as the parent image (`S003 L454-L455`), integer-typed (`S003 L438-L439`), with SHOULD-level color rendering from `image-label.colors` (`S003 L456-L466`).
6. Several apparent spec inconsistencies were observed (§8) — e.g., plate examples omit a `version` key that the normative text says MUST be present — and the capture's Implementations section is an empty pointer ("See Tools.", `S003 L813-L814`), so the brief's "actual reader implementations" dimension cannot be evidenced from this scope.

## 3. Format identity, versioning, and conformance mechanics

- **F031 [OBLIGATION]** The capture is the OME-Zarr 0.5 Final Community Group Report dated 8 September 2026; the current released version is 0.5, and data written by editor's drafts "will not necessarily be supported" (`S003 L1-L8`, `L24-L27`). Version history: 0.5.2 (2025-01-10) clarified that `dimension_names` MUST be included; 0.5.1 re-added the improved `omero` description; 0.5.0 (2024-11-21) introduced Zarr v3 (`S003 L821-L833`). *Viewer implication:* check `attributes.ome.version` and do not assume non-0.5 material interoperates.
- **F004 [OBLIGATION]** OME-Zarr metadata lives in each `zarr.json` under the namespaced key `ome` inside `attributes`, with a string `version` attribute; **the OME-Zarr metadata version MUST be consistent within a hierarchy** (`S003 L152-L165`). *Viewer implication:* a version mismatch across a hierarchy is a detectable malformation that should be reported as "cannot display this fileset correctly", per the plan's failure-explanation requirement.
- **F029 [OBLIGATION]** JSON comments are used in some spec examples for clarity but "comments MUST NOT be included in JSON objects" (`S003 L65-L66`; example comments at `L341`, `L351`, `L361`, `L370`). *Viewer implication:* use strict JSON parsing of `zarr.json`; tolerate nothing else. [C9]
- **F030 [OBLIGATION/CONDITIONAL]** Transitional metadata is intended to be removed in future; implementations "may be expected (MUST) or encouraged (SHOULD) to support the reading of the data, but writing will usually be optional (MAY)" (`S003 L60-L64`). *Viewer implication:* a read-only viewer should expect to read transitional keys (`bioformats2raw.layout`, `omero`) because real filesets carry them.
- **[OBSERVATION, C2]** The conformance boilerplate states the RFC 2119 words "do not appear in all uppercase letters in this specification" (`S003 L875-L876`), yet the document uses uppercase MUST/SHOULD/MAY pervasively. This reads as contradictory boilerplate; the operative reading adopted here is that the uppercase keywords are normative per `L872-L874` and `L57-L59`. [UNRESOLVED as to which text governs, but immaterial in practice.]
- **F033 [OBSERVATION]** Multi-word keys should use camelCase, but the spec admits some legacy keys do not obey and "should be updated in due course" (`S003 L809-L812`). The document itself uses `bioformats2raw.layout`, `field_count`, `image-label`, `label-value`. *Viewer implication:* parse exact key spellings per section; do not normalize case.

## 4. Group 1 — Opening a fileset, listing/selecting images, multiresolution navigation

### 4.1 Storage foundation

- **F001 [OBLIGATION + inference]** "OME-Zarr is implemented using the Zarr format as defined by version 3 of the Zarr specification", and "all features of the Zarr format including codecs, chunk grids, chunk key encodings, data types and storage transformers may be used with OME-Zarr unless explicitly disallowed in this specification" (`S003 L68-L72`). No feature is explicitly disallowed anywhere in the capture. *Inference (mine, not a source statement):* Slide Scout needs a general Zarr v3 reader — sharded/chunk-key-encoding-aware, with a codec set at least covering what real writers emit — which the thin plan does not mention. *Counterpoint kept visible:* the Zarr v3 spec is outside the admitted capture, so the exact mandatory reader surface cannot be pinned down here (§9, U1).
- **F032 [OBSERVATION / scope boundary]** The hierarchy "could equally be stored on a web server to be accessed via HTTP or in object storage like S3 or GCS" (`S003 L73-L77`). The format is storage-neutral; local-filesystem-only reading is a Slide Scout product boundary, not a format property. No transfer obligation arises, but nothing in the format guarantees filesets are laid out for efficient local file access.

### 4.2 What an "image" is, and where images live

- **F002 [OBLIGATION + structure]** One OME-Zarr image is a Zarr group whose `zarr.json` group attributes include `multiscales` (and optionally `omero`); each multiscale level is a separate Zarr array ("0"…"n") of chunk files; **the array name is arbitrary, ordering is defined by the `multiscales` metadata** ("often a sequence starting at 0") (`S003 L79-L100`). *Viewer implication:* never derive level order from names or sort lexicographically.
- **F003 [OBLIGATION]** Image arrays are up to 5-dimensional, with the time axis before the channel axis, before spatial axes (`S003 L96-L97`), matching the multiscales axis-ordering MUST (`L302`). Dimensionality is variable 2–5 and axis names are arbitrary (`L81`).
- **F005 [OBLIGATION, three discovery layouts]** Images are found in a fileset in three ways:
  1. **Plain images**: sibling groups such as `123.zarr`, `456.zarr`, each carrying `multiscales` (`S003 L79-L85`).
  2. **bioformats2raw collections** (transitional, `F006`): a top-level group with `bioformats2raw.layout` (value MUST be "3", `L256`), an optional `OME` group with `series` (a list of string paths whose order MUST match the `Image` order in `OME/METADATA.ome.xml` when provided) (`L243-L253`, `L264-L267`), and — absent `series` and absent `plate` — images MUST be in **consecutively numbered groups starting from 0**, each representing exactly one OME-XML Image in order (`L268-L270`).
  3. **HCS plates**: three group levels above the images; the well group MUST implement the well specification and the plate group MUST implement the plate specification (`L118-L127`); empty well rows/wells SHOULD NOT be present (`L128-L129`); labels under a field of view are optional (`L145`). If `plate` metadata is present alongside `bioformats2raw.layout`, `plate` takes precedence, parsing follows §2.7, and "it is not possible to mix collections of images with plates at present" (`L204-L206`, `L262-L263`).
- **F009 [RECOMMENDED/MAY — directly on point for listing]** Conforming readers: SHOULD make users aware of the presence of more than one image (i.e. SHOULD NOT default to only opening the first); MAY use the `series` attribute to determine valid groups; MAY show all images or offer a choice; MAY ignore other groups or arrays under the root (`S003 L271-L275`). *Viewer implication:* Slide Scout's image-list behavior is not just a product nicety; the SHOULD-level reader obligation aligns with the brief's "find images within a fileset".
- **F010 [OBLIGATION/CONDITIONAL]** A b2raw collection SHOULD have `OME/METADATA.ome.xml` which MUST adhere to the OME-XML specification but MUST use `<MetadataOnly/>` (never `<BinData/>`, `<BinaryOnly/>`, `<TiffData/>`) (`S003 L257-L260`). *Viewer implication:* the OME-XML carries metadata only — pixel data is never in the XML; do not build display on XML pixel content, and treat the file as absent-able (SHOULD-level).
- **F012 [OBLIGATION/CONDITIONAL — HCS]** Plate dictionary MUST contain `columns`, `rows`, `wells`, `version` (string); SHOULD contain `field_count` and `name`; MAY contain `acquisitions`. Column/row names: alphanumeric, case-sensitive, unique within their list; well `path` MUST be exactly `<row>/<column>` with no extra leading/trailing directories; `rowIndex`/`columnIndex` MUST be 0-based and consistent with the path (`S003 L515-L560`). [C1: both plate examples omit the MUST-level `version` key — `L563-L640`, `L643-L739` — so real files may lack it; see §8.]
- **F013 [OBLIGATION/CONDITIONAL — HCS]** Well dictionary MUST contain `images`; each entry MUST contain `path` (alphanumeric, case-sensitive, unique within the well); when the plate has multiple acquisitions, each entry MUST contain `acquisition` (integer matching a plate acquisition id); `version` is SHOULD-presence with MUST-string-when-present (`S003 L740-L752`).

### 4.3 Multiresolution (pyramid) navigation

- **F016 [OBLIGATION]** `multiscales` is a list of dictionaries; each entry MUST contain `axes`: length 2–5 and equal to the dimensionality of the data arrays; 2 or 3 space axes; MAY add one `time` and one `channel` (or null/custom-type) axis; entry order MUST correspond to array dimension order and MUST be time → channel/custom → space; if a z axis stacks anisotropic planes, zyx ordering SHOULD be used (`S003 L294-L303`).
- **F017 [OBLIGATION]** Each entry MUST contain `datasets`, a list where each item has a `path` relative to the current group; **paths MUST be ordered from largest (highest resolution) to smallest**; all levels have the same dimension count (≤5) matching `axes` (`S003 L304-L307`). *Viewer implication:* pyramid-level selection for pan/zoom can rely on this ordering plus per-level scale (F018); arbitrary level names must not be reordered.
- **F021 [OBLIGATION + INFORMATIVE]** Multiple multiscale entries (multiple pyramids) may exist in one image group. Normative content stops at the list structure; the selection guidance — "If only one multiscale is provided, use it. Otherwise, the user can choose by name, using the first multiscale as a fallback" with pseudocode — appears in an example-style passage (`S003 L388-L397`). Per the conformance rules, examples are non-normative (`L877-L883`); treat the fallback rule as [INFORMATIVE] and the UX as a [PRODUCT DECISION]. [C7]
- **F015 [OBLIGATION]** `dimension_names` MUST be included in the `zarr.json` of each multiscale-level array and MUST match the `axes` names (`S003 L174`; MUST-clarification introduced in 0.5.2, `L825-L827`). *Viewer implication:* a cheap conformance check at open time; mismatch is reportable malformation.
- **F002/F017 [applied]** Level names are arbitrary (`L93-L94`); ordering comes from `datasets` order.

## 5. Group 2 — Channel/time/plane display, coordinates, label overlays

### 5.1 Axes, units, calibration

- **F014 [OBLIGATION + RECOMMENDED]** `axes` entries MUST contain `name` (unique across names); SHOULD contain `type` (SHOULD be `space`/`time`/`channel`, but MAY be any other custom string); SHOULD contain `unit` (SHOULD be a UDUNITS-2 string; the capture enumerates the valid space and time unit strings, `S003 L166-L173`). `axes` length MUST equal array dimensionality (`L173`). *Viewer implication:* units are not guaranteed — the details panel needs a fallback ("unit not specified") path; custom axis types are legal and need a display policy ([PRODUCT DECISION]).
- **F018 [OBLIGATION]** Each dataset's `coordinateTransformations` MUST contain exactly one `scale` giving physical pixel size (or time duration); if scaling is unavailable for an axis, the value MUST be the factor between this level and the first level, defaulting to 1.0; MAY contain exactly one `translation`, which MUST come after `scale`; scale/translation lengths MUST equal `axes` length; only `scale` and `translation` types are permitted at this position (`S003 L308-L313`).
- **F019 [OPTIONAL/OBLIGATION-when-present]** The multiscales dict MAY carry its own `coordinateTransformations` applying to all levels (e.g. a common time-unit scale); the same type/order rules apply and they are applied **after** the per-dataset transforms (`S003 L314-L316`). *Viewer implication:* correct physical coordinates = compose dataset transforms, then group transforms, in order.
- **F020 [OBLIGATION + UNRESOLVED detail]** Transformation entries MUST have a `type` of `identity` (the default, typically not explicitly written), `translation`, or `scale`; each vector may be stored inline as a float list **or as binary data at a `path` location in this container**; transformations apply sequentially in list order (`S003 L276-L293`). [UNRESOLVED U4: the capture gives no layout/dtype detail for the binary `path` variant; parsing it cannot be designed from S003 alone.]
- **F031/F004 [applied]** Calibrated coordinate display depends on the whole chain being consistent; version consistency (`L156`) and `dimension_names` (`L174`) are the cheap guards.

### 5.2 Channel / time / plane display

- **F022 [OPTIONAL, OBLIGATION-when-present; transitional]** `omero` metadata (transitional, `S003 L398-L400`) provides channel rendering info. It is optional, but if present it MUST contain `channels` (array of dictionaries); each channel MUST contain `color` (exactly 6 hex digits, RGB) and `window`, which MUST contain `min`, `max`, `start`, `end` (`S003 L426-L430`). *Viewer implication:* channel color/window defaults can be honored when present but the viewer must work without `omero` (channel table then has no format-supplied colors/ranges — [PRODUCT DECISION] fallback).
- **F023 [INFORMATIVE-only fields]** The example shows `id`, `name`, per-channel `active`, `coefficient`, `family`, `inverted`, `label`, and `rdefs.defaultT` / `rdefs.defaultZ` / `rdefs.model` ("color"/"greyscale") with a pointer to the OMERO WebGateway documentation (`S003 L401-L425`). These appear only inside the annotated example; the normative sentences do not require them, and the referenced OMERO documentation is not in the capture. Treat them as conventional-but-unguaranteed; do not rely on `defaultT`/`defaultZ` being present. [C6]
- **F019bis [OBSERVATION, C6]** The statement that the `channels` array matches the size of the `c` dimension appears only in an example comment (`S003 L403`); it is not repeated as a normative rule. [UNRESOLVED: channel-count-vs-axis-size is expected but not provable from normative text here; a mismatch-tolerant channel list is the safe reading.]
- **F016/F003 [applied]** Time-point and plane (z) selectors exist only when the axes declare `time`/extra `space` axes; axis order is fixed time → channel → space (`L302`), so UI mapping is deterministic once `axes` are read.

### 5.3 Label images and overlays

- **F024 [OBLIGATION + RECOMMENDED]** Label images live in a `labels` group nested inside the image group, sibling to the resolution arrays. The labels-group `zarr.json` MUST contain the `labels` key — a JSON array of paths to the labeled multiscale images; all label images SHOULD be listed (`S003 L441-L442`, hierarchy at `L102-L108`). Intermediate groups between `labels` and the images are allowed but MUST NOT contain metadata; names are arbitrary (`L439-L440`).
- **F025 [OBLIGATION]** Label pixels MUST be integer types: one of uint8/int8/uint16/int16/uint32/int32/uint64/int64 (`S003 L438-L439`; hierarchy comment "only integer values are supported", `L116-L117`).
- **F035 [OBSERVATION — from hierarchy comments]** Each label dimension should be either the same as the corresponding image dimension or 1 if irrelevant (`S003 L106-L108`). This appears in the §1.1 layout annotations rather than as an RFC-2119 sentence; treat as expected shape compatibility, not a proven MUST.
- **F026 [OBLIGATION]** The label image's `zarr.json` MUST implement the multiscales specification, and its `datasets` MUST have the **same number of scale levels** as the original unlabeled image (`S003 L454-L455`). *Viewer implication:* overlay alignment can be maintained per pyramid level; level-count mismatch is a reportable malformation.
- **F027 [RECOMMENDED rendering; OBLIGATION-when-present fields]** The label image metadata SHOULD contain `image-label`, which SHOULD contain `colors` (MUST be a JSON array) and `version` (MUST be a string). Conforming readers **SHOULD display labels using the specified colors**: each colors entry MUST contain `label-value` (the integer pixel value) and MAY contain `rgba` (four integers 0–255; fourth is alpha/opacity) (`S003 L456-L466`). Example display semantics: rgba `[0,0,128,128]` renders 50% blue at 50% opacity (`L513-L514`). *Viewer implication:* entries without `rgba` are legal — the viewer needs a fallback color policy ([PRODUCT DECISION]); honoring provided colors is SHOULD-level.
- **F028 [OPTIONAL]** `image-label` MAY contain `properties` (array; each entry MUST contain `label-value`; arbitrary per-label key-value pairs; entries need not share keys) and `source` (MUST be an object; MAY include `image`, a relative path to the source Zarr image group; default `../../` for the usual nesting) (`S003 L467-L474`). *Viewer implication:* `source.image` is the robust link from overlay to parent image; do not hard-code `../../`.

## 7. Applicability restrictions and transfer limits (R01, R06)

- Every HCS statement in §4.2/§5 applies **only to high-content-screening datasets** (plate/well hierarchies, `S003 L118`); it must not be read as a general-image rule.
- `omero` and `bioformats2raw.layout` are **transitional** (`S003 L37`, `L175-L181`, `L398`): an upcoming NGFF version will replace the b2raw layout (`L181`); support decisions should be revisited on format upgrades.
- The b2raw "user chooses by name / first-multiscale fallback" guidance and the multiscale-selection pseudocode are example material (`S003 L388-L397`) and must not be cited as obligations.
- The spec's storage-medium generality (HTTP/S3/GCS, `L75-L77`) does **not** transfer an obligation to support remote reading onto Slide Scout; local-only is the product boundary. Conversely, nothing in the format guarantees that a local fileset is laid out for fast local reads.
- OME-XML in b2raw filesets is MetadataOnly (`L257-L260`): no pixel data can be expected there; do not import pixel-related assumptions from the OME-TIFF context.

## 8. Counterevidence, inconsistencies, and capture anomalies (R04)

- **C1 — plate `version` MUST vs examples:** normative text says the plate dictionary MUST contain `version` (`S003 L550-L551`), but both plate examples omit it (`L563-L640`, `L643-L739`). Limits: real-world files may follow the examples; the viewer should tolerate a missing plate `version` while reporting it.
- **C2 — conformance boilerplate contradiction:** "these words do not appear in all uppercase letters in this specification" (`L875-L876`) versus pervasive uppercase keywords. Adopted reading: uppercase keywords are normative (`L872-L874`).
- **C3 — index mismatch:** the index lists "HCS, in § 2.2.3" (`L891`) while the HCS hierarchy is §1.2 (`L118`). Cosmetic; noted because it could mislead future lookups.
- **C4 — diagram artifact:** a stray "." line in the HCS hierarchy diagram (`L130`).
- **C5 — empty implementations section:** §4 Implementations is only "See Tools." (`L813-L814`). The brief asks for reader-implementation compatibility research; within this scope there is **no** implementation evidence. Strongest counterevidence to any claim that interop is "verified": it is not.
- **C6 — example-only semantics:** `rdefs` defaults and the channels↔`c`-dimension size rule exist only in annotated examples (`L401-L425`), which are non-normative (`L877-L883`).
- **C7 — pseudocode selection rule** (`L388-L397`): informative, not normative.
- **C8 — mixed requirement constructions:** "SHOULD contain a `name` key whose value MUST be a string" patterns (`L523-L529`, `L751-L752`): presence is SHOULD, value constraint is MUST-when-present. Readers must not conflate the two levels.
- **C9 — comments inside spec examples** (`L341`, `L351`, `L361`, `L370`) despite the comments ban (`L65-L66`): consistent with the ban applying to real objects, not the spec's own exposition; strict parsing still required.

## 9. Unresolved areas and coverage limits (scoped to S003; R05, R09)

- **U1 — Zarr v3 normative surface.** The Zarr v3 specification (chunk grids, codecs, chunk key encodings, storage transformers, `dimension_names` mechanics) is referenced but not admitted (`S003 L68-L72`, `L174`). Mandatory reader behavior for malformed Zarr metadata, and the minimum codec set, cannot be determined here.
- **U2 — Real-reader/tool compatibility.** No implementations content in capture (C5). Which writers/readers the viewer must interoperate with, and what they emit in practice (e.g., do real plates omit `version`, per C1?), is unresolved. A failed/absent source here cannot establish anything about tools outside the capture.
- **U3 — Binary `path` transforms.** The `path` storage option for scale/translation vectors (`L285-L289`) lacks layout/dtype detail in the capture; parsing design is blocked (relates to F020).
- **U4 — rdefs & channel-count semantics.** Normative status unresolved (C6); treat as optional conventions.
- **U5 — image-label `version` values.** The key MUST be a string (`L459-L460`) but the capture does not enumerate valid version strings.
