## Q1 — Opening, listing and selecting images; multiresolution navigation

- **F-Q1-1 (identity: fileset shape for opening).** An OME-Zarr fileset is a Zarr v3 hierarchy; one image is one group (e.g. `123.zarr`, `456.zarr`) whose group-level attributes in `zarr.json` include `"multiscales"` and `"omero"`; several images may sit side by side. The same layout may live on local disk, HTTP, or object storage. Evidence: S003:67–90 (v3 at S003:68–69; group attributes at S003:87–89; storage locality S003:73–77). Version: `capture-only:5d8b2408…`.
- **F-Q1-2 (identity: multiresolution layout).** Each resolution level is a separate Zarr array stored as a sibling directory (`0` … `n`); array names are arbitrary and ordering is defined by the `"multiscales"` metadata (often a sequence from 0). Image arrays are up to 5-dimensional with the time axis before channel before spatial axes. Evidence: S003:91–100 (ordering S003:93–94; dimension/order rule S003:96–97). Version: `capture-only:5d8b2408…`.
- **F-Q1-3 (identity: multi-image collection discovery).** Transitional `bioformats2raw.layout` marks a group that implicitly describes a series of images. Discovery logic: top-level `zarr.json` MUST have `bioformats2raw.layout` = 3; if a `"plate"` key is also present it takes precedence (collections and plates cannot be mixed); the `OME` group MAY contain `"series"`, a list of string paths to image groups whose order MUST match the `Image` elements of `OME/METADATA.ome.xml` when provided; with no series and no plate, images MUST be in consecutively numbered groups `0/`, `1/`, `2/`, … Each multiscales group represents exactly one OME-XML Image. Readers SHOULD make users aware of more than one image (SHOULD NOT default to opening only the first); MAY use `"series"` to list valid groups; MAY show all or offer a choice; MAY ignore other groups/arrays. Evidence: S003:175–206 (layout S003:183–191; value 3 S003:256; precedence S003:204–206), S003:243–253 (series key), S003:261–275 (discovery + reader obligations, esp. S003:269, 272–275). Version: `capture-only:5d8b2408…`.
- **F-Q1-4 (identity: HCS plate/well listing).** High-content screening datasets require three groups above the images: well (MUST implement well spec; its images are fields of view of the same well), well row, and plate (MUST implement plate spec). Empty rows/wells SHOULD NOT be present. The plate dictionary defines the navigable listing: `columns`, `rows`, `wells` (path = row/column name; `rowIndex`/`columnIndex` 0-based and consistent with path), `field_count`, `version`, optional `acquisitions` (unique id ≥ 0, optional name/maximumfieldcount/starttime/endtime). The well dictionary MUST contain `images`, a list of fields of view (`path`, plus `acquisition` when the plate has multiple acquisitions). Evidence: S003:118–148 (hierarchy), S003:515–560 (plate keys, esp. S003:530–537, 542–549, 550–560), S003:740–752 (well keys). Version: `capture-only:5d8b2408…`.
- **F-Q1-5 (identity: multiscales metadata governs level navigation).** Image metadata sits under the `"multiscales"` key; `"multiscales"` is a list of dictionaries. Each entry MUST contain `axes` (length 2–5, equal to array dimensionality; 2–3 space axes plus optionally one time and one channel/custom axis; ordered time → channel/custom → space; `zyx` recommended when z is the anisotropic stacking axis) and `datasets` (each with `path` relative to the group and `coordinateTransformations`; paths MUST be ordered largest/highest-resolution first). All datasets in a group share dimensionality (≤ 5) matching `axes`. `name`, `type` (downscaling method) and `metadata` are SHOULD-level. Evidence: S003:294–319 (axes rules S003:299–303; datasets/path ordering S003:304–307; optional keys S003:317–319). Version: `capture-only:5d8b2408…`.
- **F-Q1-6 (identity: selecting among named multiscales).** If only one multiscale is provided, use it; otherwise the user can choose by name, using the first multiscale as fallback (normative example pseudo-code). Evidence: S003:388–397. Version: `capture-only:5d8b2408…`.
- **F-Q1-7 (identity: 0.5 metadata namespacing and version binding).** OME-Zarr Metadata is stored in `zarr.json` files throughout the hierarchy under the namespaced key `ome` inside `attributes`; the version is a string in `ome.version` ("0.5") and MUST be consistent within a hierarchy — an opening-time validation signal. Evidence: S003:149–165 (namespacing S003:152–155; consistency S003:156). Version: `capture-only:5d8b2408…`.
- **F-Q1-8 (identity: label discoverability at open time).** A `labels` group nested in the image group is a container (not itself an image): its `zarr.json` attributes list paths to the labeled multiscale images (e.g. `{"labels": ["original/0"]}`); intermediate folders are permitted and carry no metadata; label array names are arbitrary and registered in the labels list. Evidence: S003:102–117 (hierarchy), S003:437–453 (labels key, S003:441–453). Version: `capture-only:5d8b2408…`.
- **F-Q1-9 (identity: reader must not assume Zarr features).** All Zarr v3 features — codecs, chunk grids, chunk key encodings, data types, storage transformers — may be used with OME-Zarr unless explicitly disallowed, so an opener cannot assume a particular codec or chunk layout. Evidence: S003:67–72. Version: `capture-only:5d8b2408…`.
- **F-Q1-10 (identity: transitional metadata reading duty).** Transitional metadata (e.g. `bioformats2raw.layout`, `omero`) is intended for future removal; implementations may be expected (MUST) or encouraged (SHOULD) to support reading it. Evidence: S003:60–64. Version: `capture-only:5d8b2408…`.

## Q2 — Channel/time/plane display, calibrated coordinates, label overlays

- **F-Q2-1 (identity: channel render defaults).** Transitional `"omero"` metadata holds channel rendering information. It is optional; if present it MUST contain `channels`, an array matching the c dimension size. Each channel MUST contain `color` (6 hexadecimal RGB digits) and `window`; `window` MUST contain `min`, `max`, `start`, `end`. Example channel entries also carry `active`, `coefficient`, `family`, `inverted`, `label`. `rdefs` gives `defaultT` (first timepoint to show), `defaultZ` (first Z section), and `model` (`color`/`greyscale`). Evidence: S003:398–430 (channels MUST/fields S003:426–430; rdefs S003:419–423). Version: `capture-only:5d8b2408…`.
- **F-Q2-2 (identity: axis identity, types and units for slicing/calibration).** `axes` entries: `name` MUST exist and be unique; `type` SHOULD be `space`/`time`/`channel` (custom strings allowed); `unit` SHOULD exist with UDUNITS-2 strings (enumerated lists for space and time axes). `axes` length MUST equal array dimensionality; `dimension_names` MUST be included in each level's array `zarr.json` and MUST match the axes names. Evidence: S003:166–174 (dimension_names S003:174; unit lists S003:171–172). Version: `capture-only:5d8b2408…`.
- **F-Q2-3 (identity: data→physical calibration rule).** `coordinateTransformations` map array coordinates to physical coordinates; entries apply sequentially in order; only `scale` and `translation` are allowed in multiscales contexts (identity is the default and usually implicit; vectors may be inline lists or `path` binary). Each dataset's transformations MUST include exactly one `scale` (pixel size in physical units or time duration; when scaling is unavailable for an axis, the value MUST be the factor relative to the first resolution, defaulting 1.0 with no downsampling) and MAY include exactly one `translation` (physical origin offset), which MUST come after scale. Scale and translation array lengths MUST equal the axes length. A multiscales-level `coordinateTransformations` MAY apply to all levels and is applied after the per-dataset ones (e.g. constant time unit). Evidence: S003:276–293 (types/sequential order S003:279–293), S003:308–316 (exactly-one-scale S003:310; translation-after-scale S003:311; length rule S003:312; group-level application S003:314–316). Version: `capture-only:5d8b2408…`.
- **F-Q2-4 (identity: axis order for time/plane slicing).** Axis order MUST match array dimension order and MUST be ordered by type: time first (if present), then channel or custom axis (if present), then space axes; with three spatial axes, `zyx` ordering is SHOULD when z is anisotropic. Evidence: S003:301–303 (also array-level restatement S003:96–97). Version: `capture-only:5d8b2408…`.
- **F-Q2-5 (identity: label image geometry and typing).** Label images are multiscale images with integer-only pixel types ([u]int8/16/32/64). A label image's `zarr.json` MUST implement multiscales, and its `datasets` array MUST have the same number of scale levels as the original unlabeled image. A label image sits in the same coordinate system as its source image (usually same dimensions and coordinate transformations); each label dimension is either the same as the image dimension or 1 if irrelevant. Evidence: S003:431–455 (integer types S003:438–439; level-count parity S003:454–455), S003:432–433 (coordinate system), S003:106–108 (dimension rule). Version: `capture-only:5d8b2408…`.
- **F-Q2-6 (identity: overlay colors and label metadata).** The label image's metadata SHOULD contain `image-label`, which SHOULD contain `colors` (MUST be an array; one object per unique label value; each object MUST contain integer `label-value`; MAY contain `rgba` = four integers 0–255 whose fourth component is alpha/opacity) and `version` (MUST be a string, image-label schema version). Conforming readers SHOULD display labels using these colors (worked example: rgba [0,0,128,128] renders as 50% blue at 50% opacity). `image-label` MAY also contain `properties` (per-label-value arbitrary key-value metadata; objects need not share keys) and `source` (MUST be an object; MAY include `image`: relative path to the source Zarr image group, default `../../`). Evidence: S003:456–474 (colors/rgba S003:461–466; properties/source S003:467–474), worked example S003:476–514. Version: `capture-only:5d8b2408…`.
- **F-Q2-7 (identity: end-to-end calibration example).** The spec's worked 5-D example: axes t (time, millisecond), c (channel), z/y/x (space, micrometer); level 0 scale [1,1,0.5,0.5,0.5], level 1 [1,1,1,1,1], level 2 [1,1,2,2,2]; a group-level scale [0.1,1,1,1,1] sets the time unit for all levels. This is the exact computation a coordinate readout must reproduce. Evidence: S003:320–387 (level scales S003:343, 353, 363; group scale S003:372). Version: `capture-only:5d8b2408…`.

## Plan implications (admitted plan: inputs/plan/Viewer.md)

The plan already covers: open a local OME-Zarr 0.5 fileset and list images; canvas pan/zoom; channel visibility controls; time-point/plane selection; optional label overlays; details panel with dimensions/units/coordinates; choosing an available pyramid level per view; background reads with cancellation; failure explanations; acceptance on representative filesets including a large-dataset responsiveness check. Source-derived implications and gaps:

1. **Listing must handle three shapes.** Single image group (S003:78–117), bioformats2raw series collections via `series` or numbered groups (S003:175–275), and HCS plates/wells/fields (S003:118–148, 515–560, 740–752). The plan's "lists the images it finds" should explicitly include plate/well/field navigation and the SHOULD NOT default to only the first image of a collection (S003:272).
2. **Pyramid level choice interacts with calibration.** Level ordering is defined by `datasets` path order (largest→smallest, S003:305–306) and each level carries its own physical scale; coordinate readouts must use the selected level's transforms, not level 0's (S003:308–312, worked example F-Q2-7).
3. **Named multiscale selection is a separate user choice** with first-as-fallback (S003:388–397); not mentioned in the plan.
4. **Channel controls can be initialized from `omero`** (colors, window start/end, active flags, rdefs defaultT/defaultZ/model) but it is optional — absence must not degrade display (S003:398–430); transitional reading duty at S003:60–64.
5. **Units are SHOULD-level.** Coordinates may lack units (S003:170); the details panel needs an explicit "unitless/unknown" state rather than assuming micrometers. Validate `dimension_names` against `axes` at open (S003:174).
6. **Label overlays are level-aligned by construction** (same level count as base image, S003:454–455; shared coordinate system, S003:432–433); alpha compositing per rgba 4th component (S003:463–465); integer dtype check (S003:438–439). Overlay placement should honor translation-aware physical coordinates.
7. **Cheap opening validations:** `ome.version` consistency across the hierarchy (S003:156), axes/dimensionality agreement (S003:173, 300, 307), scale/translation length equal to axes (S003:312). Failures should feed the plan's "explain what could not be displayed" behavior.
8. **Acceptance fixtures implied by the source:** series collection, sparse plate, anisotropic z (`zyx`, per-axis differing scale), minimal 2-D, labels with and without `image-label`.
