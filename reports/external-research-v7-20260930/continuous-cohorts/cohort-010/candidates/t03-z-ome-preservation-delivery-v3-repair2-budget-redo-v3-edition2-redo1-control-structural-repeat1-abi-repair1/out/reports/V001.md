## 3. What the brief requires (with line evidence)

All citations refer to inputs/brief.md.

1. **Identity and scope (line 3):** a small, read-only desktop browser for local OME-Zarr 0.5 bioimaging filesets. Read-only and local are hard constraints, not preferences.
2. **Navigation (line 3):** scientists must be able to find images within a fileset.
3. **Multiresolution inspection (line 3):** inspection by channel, time point and plane, over multiresolution images.
4. **Label overlay (line 3):** overlay of *associated* label images — associated signals optionality.
5. **Calibrated coordinates (line 3):** correctly calibrated coordinate reading.
6. **Responsiveness (line 3):** the product must remain responsive while opening large saved datasets.
7. **Explained failure (line 3):** it must clearly explain data it cannot display.
8. **Boundary and exclusions (line 5):** the current boundary is local filesystem reading; image editing, export, remote services and clinical interpretation are outside the case; source files must remain unchanged.
9. **Research mandate (line 5):** research the format and actual reader implementations broadly enough to surface compatibility, correctness, navigation and display requirements a thin initial plan may miss, and distinguish established format obligations from optional capabilities and product decisions.

## 4. Compatibility analysis (analysis plus labeled model knowledge)

The brief pins version 0.5, but real scientists hold heterogeneous data. Model knowledge (unverified here) indicates the OME-Zarr ecosystem has shipped data across several spec revisions, and that files declared as one revision frequently deviate in practice — missing pyramid levels, absent units, or nonstandard group layout. The compatibility consequence is twofold. First, version and conformance sniffing must occur at open time, before decode, so the product can route failures into explanation paths (requirement 7) instead of crashes. Second, the strictness policy is a genuine product decision the brief leaves open: refuse everything not exactly 0.5, or accept near revisions with a visible caveat. This report recommends accepting-and-labeling for close revisions, because the alternative conflicts with the navigation and inspection goals, but the decision needs an owner.

Reader choice is the other compatibility lever, and it is where the unread corpus hurts most. The brief demands research into actual reader implementations; candidate ecosystem readers known to this agent (ome-zarr-py, ngio, zarr-python as the storage layer, and web-oriented viewers such as vizarr for comparison) could not be checked against any admitted documentation, so no capability comparison is asserted here. What the brief does establish is the acceptance test any candidate must pass: chunk-level partial reads (§6), absolute non-mutation of source trees (§7), and structured error reporting (§8).

## 5. Correctness analysis

Correctly calibrated coordinates is the brief's sharpest correctness requirement. Model knowledge (unverified) says OME-Zarr carries per-axis units and per-level scale and translation transformations, and that units are frequently absent from legacy files, tempting implementers to default to micrometers. The brief's wording — *correctly* calibrated — argues the honest path: derive calibration from the file; when units are absent, display an explicit unknown-unit state rather than a plausible guess, because a wrong scale bar silently corrupts scientific judgment. The same discipline applies to label overlays (requirement 4): geometry or axis mismatches between a label image and its base are exactly the data the product must explain rather than render incorrectly.

## 6. Navigation and display analysis

Finding images within a fileset implies a scan-and-catalog layer beneath the viewer: enumerate local trees, identify image groups, expose search. Model knowledge (unverified) says such collections range from single standalone images to plate hierarchies with wells and fields, so the design must degrade gracefully to a plain list and must not assume plate semantics everywhere. Scanning must be lazy and interruptible, because filesets can be large and requirement 6 applies during opening too.

Display of multiresolution images by channel, time point and plane requires an axes-driven image model: the axis set is data-dependent, pyramid level selection should track viewport size, and reads should fetch only the requested chunk ranges. Single-resolution datasets without pyramids must render rather than fail. Responsiveness on large saved datasets then becomes a measurable budget — this report proposes, as a product decision, that first image visibility on a multi-gigabyte fileset land within a couple of seconds on ordinary desktop hardware — with the acknowledgment that the brief sets no number and the corpus could not inform one.

## 7. The integrity invariant

Source files must remain unchanged (line 5) binds every layer. Model knowledge (unverified) flags a concrete risk: some Zarr tooling writes consolidated metadata or cache artifacts into source trees, and some libraries create lock files implicitly. Any reader or indexing layer exhibiting such behavior is disqualifying or must be wrapped. Caches belong in application-owned directories. Because the invariant is absolute, it must be testable — hence the checksum harness proposed in §9.

## 8. Obligations versus product decisions

The brief itself demands this classification (line 5). Provisionally, with the obligation column flagged as model knowledge pending specification verification: format obligations include interpreting multiscale level structure, declared axes and units, coordinate transformations, associated label conventions, and plate/well metadata where present. Product decisions include the strictness policy for near-version files, default rendering when metadata is absent, search interface shape, the performance budget, and diagnostics depth. Treating a mere convention as an obligation risks rejecting valid files; every obligation item must be reconciled against the 0.5 specification text before implementation.

## 9. Proposed validation — ALL UNEXECUTED

None of the following has been run; each awaits either an admitted corpus or fixture data the bounded environment cannot currently provide.

1. **Spec reconciliation (blocked on corpus):** reconcile §8's obligation list line-by-line against the OME-Zarr 0.5 specification text.
2. **Reader bake-off (blocked on corpus and binaries):** evaluate candidate readers against the brief's acceptance tests: chunk-level reads, zero source mutation, structured errors.
3. **Integrity harness:** hash a fixture tree, browse it fully through the product, re-hash, assert byte equality.
4. **Calibration fixtures:** known physical-size fixture asserting displayed calibration matches ground truth; unit-less fixture asserting an explicit unknown-unit state.
5. **Axis matrix fixtures:** 2D through 5D datasets, with and without pyramids, asserting correct slicing of every axis combination.
6. **Label fixtures:** well-formed labels, absent labels, and mismatched geometry, asserting three distinct behaviors including the explained-failure path.
7. **Fault injection:** truncated chunk, missing metadata, unknown compressor — each must yield a distinct human-readable explanation.
8. **Performance benchmark:** open-to-first-image latency on a multi-gigabyte fileset, before and after reader selection.
9. **Boundary interaction test:** a remote URL input produces the designed local-only explanation, not an obscure error.
