## F007 Researcher background knowledge on OME-Zarr 0.5 (NOT corpus-sourced; verification UNEXECUTED)

Because no source-corpus file could be located, the following domain background comes from the researcher's general knowledge rather than from any admitted source. Every item is a hypothesis to verify against the OME-Zarr 0.5 specification and reader documentation once corpus access exists; none carries corpus evidence weight in this workspace. (1) OME-Zarr (OME-NGFF) is a chunked, multiscale image container built on Zarr; version 0.5 is associated with Zarr v3 storage including the sharding extension, while 0.1–0.4 practice used Zarr v2 with `.zarray`/`.zattrs` metadata files — a likely compatibility axis for a browser that must open arbitrary local filesets (verification UNEXECUTED). (2) Metadata groups plausibly load-bearing for the brief's duties include multiscales with per-level `coordinateTransformations`, `axes` with units (x, y, z, c, t), `omero` channel metadata (names, colors, display windows), `labels`/label-image association for overlays, and plate/well hierarchies for high-content-screening filesets (verification UNEXECUTED). (3) Established reader implementations include ome-zarr-py (Python; underlies the napari OME-Zarr plugin), ome-zarr.js (JavaScript; used by Vitessce), and ngff-zarr; support for 0.5-specific features, notably sharding, is believed to be uneven across implementations (verification UNEXECUTED). (4) Coordinate calibration in OME-Zarr is expressed via axes units plus coordinate transformations per resolution level rather than a single pixel-size field, so correctly scaled display depends on honoring the full transformation chain (verification UNEXECUTED).

## F009 Counterevidence and tensions observed in the admitted material

Three tensions qualify the requirement hypotheses. First, responsiveness versus read-only locality: the brief demands responsiveness "while opening large saved datasets" (inputs/brief.md:3) while the boundary is local read-only file access (inputs/brief.md:5); local disk latency does not match the network-optimized assumptions of existing web-oriented readers, so IO strategy (chunk-aligned access, background parsing, cancellation) is a genuine design risk rather than a settled obligation. Second, tool ambition versus "small": the brief calls Slide Scout "small" (inputs/brief.md:3) yet assigns whole-fileset discovery plus 5-D inspection plus overlay duties (inputs/brief.md:3); this tension implies scoping decisions (which fileset layouts and hierarchies to support first) are product decisions the expected thin plan was supposed to surface. Third, version pinning versus ecosystem drift: the brief pins "OME-Zarr 0.5" (inputs/brief.md:3), but local filesets in the wild may use older layouts; strict 0.5-only support would push older filesets under the "clearly explain data it cannot display" duty (inputs/brief.md:3) instead of the display duties — a genuine product-decision fork with counterevidence on both sides. No admitted source contradicts the brief itself.
