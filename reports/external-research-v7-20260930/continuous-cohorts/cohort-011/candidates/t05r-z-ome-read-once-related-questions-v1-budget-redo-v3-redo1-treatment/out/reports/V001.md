## 2. Q1 — Supported findings about the format

Each finding states the claim, its governing conditions/exceptions, and the exact location. "Inference" flags conclusions that go beyond the literal source text.

### 2.1 Storage substrate and metadata location

**F01 — OME-Zarr 0.5 is defined on Zarr v3; the whole Zarr feature surface is in scope.**
"OME-Zarr is implemented using the Zarr format as defined by the version 3 of the Zarr specification" (S003 67–69). "All features of the Zarr format including codecs, chunk grids, chunk key encodings, data types and storage transformers may be used with OME-Zarr unless explicitly disallowed in this specification" (S003 70–72). Condition: no disallow-list appears anywhere in this capture, so (inference) a reader must tolerate whatever Zarr v3 features a conforming writer chose — codecs, chunk grids, data types included — or fail with a clear explanation. Group-level attributes live in `zarr.json` (S003 87–89); chunks conform to the array's own `zarr.json` metadata (S003 99–100).

**F02 — OME-Zarr metadata is namespaced under `ome` and carries a hierarchy-consistent version string.**
The OME-Zarr metadata is stored in the various `zarr.json` files "under the namespaced key `ome` in attributes", and "The version of the OME-Zarr Metadata is denoted as a string in the version attribute within the ome namespace. The OME-Zarr Metadata version MUST be consistent within a hierarchy." (S003 149–156; example 157–165 shows `attributes.ome.version: "0.5"`). Conditions: (a) the MUST is scoped to *within a hierarchy* — different filesets may differ; (b) the layout diagram's phrasing that group attributes "include 'multiscales' and 'omero'" (S003 87–89) is a simplification — inference, but directly supported by the normative text and every example: in 0.5 the keys sit at `attributes.ome.multiscales`, `attributes.ome.omero`, etc. (e.g., S003 320–326, 476–482, 563–569). A reader that looks for a top-level `multiscales` attribute key will not find 0.5 metadata.

**F03 — Normative language mechanics.**
RFC 2119 keywords are used (in lowercase) with full force; all text is normative except explicitly non-normative sections, examples and notes (S003 869–878). JSON comments are forbidden in real objects — "comments MUST NOT be included in JSON objects" (S003 65–66) — even though several spec examples contain comments purely for clarity (e.g., S003 341, 351, 370). Inference used throughout this report: code blocks and tree diagrams in §1–2 are illustrative annotations unless the surrounding normative sentence carries a keyword; one explicit example: the multiscale-selection *sentence* at S003 388–389 is treated as governing, the pseudocode at 390–397 as illustrative (its last line, "Or perhaps choose based on chunk size.", is a non-normative comment).

### 2.2 Axes, dimensions and multiscales

**F04 — Image hierarchy: 2–5D arrays, fixed axis ordering, arbitrary level names.**
Images are Zarr groups of groups and arrays; each resolution level is a separate Zarr array (S003 78–100). "the number of dimensions is variable between 2 and 5 and … axis names are arbitrary" (S003 81). "All image arrays must be up to 5-dimensional with the axis of type time before type channel, before spatial axes" (S003 96–97). The array name is arbitrary; ordering is defined by the "multiscales" metadata, though often a sequence from 0 (S003 91–94). Multiscales axes MUST be ordered time → channel-or-custom → space (S003 301–302), with `zyx` spatial ordering a SHOULD for anisotropic z-stacks (S003 303).

**F05 — "axes" obligations, including the 0.5.2 `dimension_names` MUST.**
Each axes entry MUST contain `name`, and name values MUST be unique across all `name` fields (S003 168). `type` SHOULD be present and SHOULD be one of `space`/`time`/`channel`, but MAY be any other string (custom axis types are legal) (S003 169). `unit` SHOULD be present and SHOULD be a UDUNITS-2 string; the spec enumerates the valid space units (S003 171) and time units (S003 172). The length of `axes` MUST equal the arrays' dimensionality (S003 173). "`dimension_names` … MUST be included in the zarr.json of the Zarr array of a multiscale level and MUST match the names in the 'axes' metadata" (S003 174). Version qualification: this MUST was clarified in 0.5.2 (2025-01-10) (S003 825–827), so it is specific to the 0.5 series, not earlier versions.

**F06 — "multiscales" obligations: structure, per-level transforms, and selection.**
Each multiscales entry MUST contain `axes` (2–5 entries: 2–3 space, MAY one time, MAY one channel *or a null/custom type*, S003 299–302) and MUST contain `datasets` (S003 304). Each dataset MUST have `path` relative to the current group, and "The 'path's MUST be ordered from largest (i.e. highest resolution) to smallest" (S003 305–306). All dataset arrays share dimensionality ≤ 5 matching `axes` (S003 307). Each dataset MUST contain `coordinateTransformations` mapping data to physical coordinates; dataset-level transforms "MUST only be of type translation or scale" (S003 308–309). Conditions that govern coordinate math:
- "They MUST contain exactly one scale transformation … If scaling information is not available or applicable for one of the axes, the value MUST express the scaling factor between the current resolution and the first resolution for the given axis, defaulting to 1.0 …" (S003 310) — the scale encodes *absolute voxel size at level 0, and per-level ratios thereafter*; it also covers time durations, not just spatial pixel size (S003 310).
- One translation MAY be present; "If translation is given it MUST be listed after scale to ensure that it is given in physical coordinates" (S003 311).
- "The length of the scale and translation array MUST be the same as the length of 'axes'." (S003 312).
- The multiscales dict MAY carry its own `coordinateTransformations`, subject to the same type/order rules, "applied after" the per-dataset ones (S003 314–316) — the example uses this for a time-unit scale shared by all levels (S003 368–374).
- SHOULD-level fields: `name`, `type` (downscaling method), `metadata` (S003 317–319).
- Selection rule: "If only one multiscale is provided, use it. Otherwise, the user can choose by name, using the first multiscale as a fallback" (S003 388–389).
Multiple independent images may also exist side by side as sibling groups (S003 82–85).

**F07 — coordinateTransformations vocabulary.**
A transformation list entry MUST contain `type`; types are `identity` (default, typically not explicit), `translation`, and `scale`; vectors may be stored inline as float lists **or as binary data at a path inside the container** (`"path": str`) (S003 276–293). Transformations apply sequentially, in order (S003 293). Condition for readers: the path-form of scale/translation vectors is spec-legal, so a coordinates implementation that only accepts inline arrays is incomplete against the letter of the spec.

### 2.3 Channel display metadata

**F08 — "omero" is optional transitional render metadata; its MUSTs are conditional.**
"omero" holds channel rendering information and is explicitly **transitional** (S003 398–400) — metadata added with the intention of removing it in the future; implementations may be expected (MUST) or encouraged (SHOULD) to read transitional data, while writing is usually optional (S003 60–64). Governing conditions: "The 'omero' metadata is optional, but if present it MUST contain the field 'channels'" (S003 426); each channel MUST contain `color` (6 hex digits, RGB) (S003 427) and MUST contain `window`, which MUST contain `min`, `max`, `start`, `end` (S003 428–430). The example additionally shows `id`, `name`, `active`, `coefficient`, `family`, `inverted`, `label`, and `rdefs` (`defaultT`, `defaultZ`, `model: "color"|"greyscale"`) (S003 401–423) — these appear **only in the example**, so no MUST attaches to them in this capture; treating `rdefs` as a rendering-defaults *convention* rather than an obligation is an inference (R03). The channels array matches the c dimension size (S003 403). Version qualification: the improved omero description was re-added in 0.5.1 (S003 828–830).

### 2.4 Label images

**F09 — "labels" and "image-label" obligations and conditions.**
Label images live in a `labels` group nested in the image group (S003 437). Governing requirements: label pixels MUST be integer dtypes `[u]int{8,16,32,64}` (S003 438–439); intermediate groups between `labels` and the images are allowed but "MUST NOT contain metadata" (S003 439–440); the labels group's `zarr.json` MUST contain the `labels` key, a JSON array of paths to the labeled multiscale image(s), and "All label images SHOULD be listed" (S003 441–442); the label image's `zarr.json` MUST implement multiscales, and its `datasets` MUST have the same number of scale levels as the original unlabeled image (S003 454–455). Each label dimension must equal the corresponding image dimension or be 1 if irrelevant (S003 106–108). Display metadata: the label image SHOULD contain `image-label`, which SHOULD contain `colors` (MUST be an array if present) and `version` (MUST be a string) (S003 456–460); "Conforming readers SHOULD display labels using the colors specified" (S003 461); each color entry MUST contain `label-value` (integer) and MAY contain `rgba` — four integers 0–255, the fourth being alpha/opacity (S003 462–466); optional `properties` (array; each entry MUST contain `label-value`; arbitrary extra keys; keys need not match across entries) and `source` (MUST be an object; MAY include `image`, a relative path, default `"../../"`) (S003 467–474; example 475–514, where rgba `[0,0,128,128]` renders 50% blue at 50% opacity, S003 513–514). Consequence: when `image-label` or `colors` is absent, the spec imposes no color obligation on the reader — fallback rendering is a product decision.

### 2.5 High-content screening (plates and wells)

**F10 — HCS hierarchy and plate/well obligations.**
For HCS datasets "Three groups MUST be defined above the images": the well group MUST implement the well specification, the plate group MUST implement the plate specification (S003 118–127). Exceptions: "A well row group SHOULD NOT be present if there are no images in the well row. A well group SHOULD NOT be present if there are no images in the well." (S003 128–129) — so well/row groups may legitimately be missing, and sparse plates are explicitly supported (example S003 641–739: a 96-well plate with wells only at C/5 and D/7).
Plate dictionary obligations: `columns` MUST (list; each column MUST have `name`; alphanumeric, case-sensitive, unique; "Care SHOULD be taken to avoid collisions on case-insensitive filesystems", S003 530–537); `rows` MUST (same constraints, S003 542–549); `version` MUST (string, S003 550–551); `wells` MUST (each well MUST have `path` = row name + "/" + column name, no extra leading/trailing directories; MUST have `rowIndex` and `columnIndex`, 0-based, all three mutually consistent, S003 552–560); `field_count` SHOULD (MUST be positive integer if present, S003 538–539); `name` SHOULD (S003 540–541); `acquisitions` MAY (list; each acquisition MUST have unique integer `id` ≥ 0; SHOULD `name`, `maximumfieldcount` (positive int); MAY `description`, `starttime`/`endtime` integer epoch, S003 518–529; examples 561–583).
Well dictionary obligations: `images` MUST (list of fields of view; each MUST have `path` — alphanumeric, case-sensitive, unique in the list; "If multiple acquisitions were performed in the plate, it MUST contain an `acquisition` key … matching one of the acquisition JSON objects defined in the plate metadata"), `version` SHOULD (string) (S003 744–752; examples 753–808).

### 2.6 Multi-image collections (bioformats2raw.layout)

**F11 — Transitional "bioformats2raw.layout": discovery rules and reader duties.**
This transitional layout (added in v0.4, to be replaced by explicit metadata in a future NGFF, S003 175–181) identifies a group that implicitly describes a series of images. Governing rules: conforming groups MUST have value `"3"` for the key (S003 256); they SHOULD have `OME/METADATA.ome.xml`, which MUST adhere to OME-XML and MUST use `<MetadataOnly/>` (not BinData/BinaryOnly/TiffData) (S003 257–260). Image-location logic: if `plate` metadata is present, images MUST be at the plate-defined locations and the plate key "takes precedence"; "It is not possible to mix collections of images with plates at present." (S003 204–206, 262). The OME group MAY contain `series` (MUST be a list of strings; paths to image groups; order MUST match the OME-XML `Image` order) (S003 243–253, 264–267); if no `series` and no plate, multiscales images MUST be in consecutively numbered groups from `0` (S003 268–270). Reader duties: "Conforming readers SHOULD make users aware of the presence of more than one image (i.e. SHOULD NOT default to only opening the first image)"; MAY use `series`; MAY show all images or offer a choice; MAY ignore other groups/arrays under the root (S003 271–275).

### 2.7 Deployment and style context

**F12 — Storage medium is not restricted to local filesystem.**
The hierarchy "is represented here as it would appear locally but could equally be stored on a web server to be accessed via HTTP or in object storage like S3 or GCS" (S003 73–77). Consequence: the brief/plan restriction to local filesystem reading (inputs/brief.md line 4; inputs/plan/Viewer.md line 9) is a product boundary, not a format property.

**F13 — Key naming is mixed camelCase/legacy.**
"Multi-word keys in this specification should use the camelCase style", but "some parts of the specification don't obey this convention … they should be updated in due course" (S003 809–812). Observed mix in normative content: `rowIndex`/`columnIndex` (camelCase, S003 557–559) vs `field_count` (snake, S003 538) vs `maximumfieldcount` (flat, S003 524) vs kebab `image-label` (S003 456). Inference: parsers must match the exact literal keys as specified; no normalization should be attempted.

**F14 — Counterevidence: spec examples contradict a plate MUST.**
The plate dictionary "MUST contain a `version` key" (S003 550–551), yet **both** normative examples of plate metadata omit `version` entirely (S003 563–640 and 643–739). Examples are non-normative (S003 877–878), so the MUST stands; but (inference, preserved as counterevidence per R04) real-world writers that copied the examples may emit plates without `version`, so a reader that hard-fails on missing `version` may reject filesets that writers actually produce. This is a tolerance decision the product must make explicitly, not silently.

**F15 — Version/status framing.**
Current released version is 0.5; migration scripts are promised between numbered versions; editor's-draft data is not necessarily supported (S003 24–27). Version history: 0.5.0 introduced Zarr v3 (2024-11-21, S003 831–833), 0.5.1 re-added the improved omero description (S003 828–830), 0.5.2 clarified the `dimension_names` MUST (S003 825–827). Older releases differ materially (e.g., bioformats2raw.layout arrived in 0.4, S003 180–181; axes units/transforms in 0.4.0, S003 842).

**U01 — No reader-implementation evidence exists in the admitted corpus.**
Section 4 "Implementations" reads, in full, "See Tools." (S003 813–814). The brief asks for research into "actual reader implementations" (inputs/brief.md line 4), but the assigned scope (inputs/TASK.md lines 5) contains only the normative capture. Which real tools interoperate, and how they behave on edge cases, is **unresolved within this Goal**. Undeveloped lead: the NGFF "Tools" page (not admitted; not fetched).

**U02 — The spec is silent on three things the plan leans on.** (Negative claims scoped to S003 0.5 per R05.)
(a) No normative rule for *choosing* a pyramid level for a given view — only the largest→smallest ordering obligation (S003 306); the only chunk-size hint is a code comment inside illustrative pseudocode (S003 396). (b) No error-handling/malformed-input semantics anywhere in the capture. (c) No performance/responsiveness requirements. These are product-owned decisions informed by, not dictated by, the format.

**U03 — Enumerated values for two MUST-version strings are not given.**
Plate `version` (S003 550–551) and `image-label` `version` (S003 459–460) MUST be strings "specifying the version" of their respective schemas, but the capture does not enumerate acceptable values. Unresolved.

**U04 — Referenced external authorities were not admitted and were not inspected.**
OME-XML specification (S003 257–259), OMERO WebGateway documentation (S003 424–425), RFC 2119 (S003 896), UDUNITS-2 (S003 170), and the Tools page (S003 813–814) are referenced but outside the admitted scope; nothing is claimed about their contents.

**Rejected scope (product, not format):** image editing, export, remote services/storage, and clinical interpretation are outside this case per the brief and plan (inputs/brief.md line 4; inputs/plan/Viewer.md line 9). The format itself imposes no such restriction (F12) — these are product rejections, recorded so the report does not present them as format obligations.

**Transitional-metadata risk:** `omero` and `bioformats2raw.layout` are transitional (S003 60–64, 398–400, 175–181); both are expected to change or disappear in a future NGFF. Any product capability hard-wired to them carries a version-qualification risk that must stay visible.

## 3. Q2 — Implications for the thin viewer plan

Plan under review: inputs/plan/Viewer.md (deliberately thin). Dispositions: **adopt** (plan element is supported as-is), **extend** (works but must grow a specific obligation), **decide** (genuine product choice the plan has deferred), **limit** (explicit inapplicability/transfer limit to state).

**P01 — Image discovery must cover three layouts, with precedence. [extend]**
Plan: "opens a local OME-Zarr 0.5 fileset and lists the images it finds" (Viewer.md line 5). Evidence: discovery means at least (a) sibling image groups (S003 82–85, 268–270), (b) bioformats2raw series with optional `series` metadata and OME-XML ordering (S003 243–270), and (c) HCS plates → rows → wells → fields of view (S003 118–148, 552–560, 744–750), with plate taking precedence over bioformats2raw.layout and no mixing of collections with plates (S003 204–206). The reader SHOULD make users aware of multiple images rather than defaulting to the first (S003 272). Empty wells/rows SHOULD NOT exist, and sparse plates are legal (S003 128–129, 641–739) — the fileset browser must tolerate absent nodes.

**P02 — Channel/time/plane controls must be axes-driven, and custom axes are legal. [extend]**
Plan offers "channel visibility controls, time-point and plane selection where relevant" (Viewer.md line 5). Evidence: what "channel"/"time"/"plane" mean is defined per-fileset by `axes` (names MUST-unique, types SHOULD space/time/channel but MAY be custom strings, S003 168–169; multiscales axes MAY include "a null / custom type", S003 301) with MUST ordering time → channel/custom → space (S003 302) and dimensionality 2–5 (S003 300). The plan has no stated story for custom or null-typed axes; controls must be derived from metadata at runtime, not from fixed positions. A 2D fileset legitimately has no t/c/z — "where relevant" must be metadata-driven.

**P03 — Calibrated coordinates require composing transforms in order. [extend]**
Plan: "A details panel shows dimensions, units and coordinates" (Viewer.md line 5). Evidence: correct physical coordinates = dataset-level `coordinateTransformations` (exactly one `scale`, optional `translation` after it) followed by any multiscales-level transforms (S003 308–316), with array lengths equal to `axes` (S003 312), scale values per level being ratios-to-level-0 defaulting to 1.0 on non-downsampled axes (S003 310), units SHOULD be UDUNITS-2 strings from the enumerated lists (S003 170–172), and scale possibly encoding time durations (S003 310; example 368–374). Edge case to decide: scale/translation vectors may legally be binary blobs at a `path` (S003 285–289) — supporting or clearly rejecting path-form vectors is a product decision that must be explicit (currently: plan is silent → **decide**).

**P04 — Pyramid-level selection is a product heuristic on an ordered list; multiple multiscales need a chooser. [decide]**
Plan: "The viewer chooses an available pyramid level appropriate for the current view." (Viewer.md line 5). Evidence: levels are ordered largest→smallest by `datasets` order (S003 306); array names are arbitrary (S003 93–94); a fileset may contain several multiscales entries, in which case "the user can choose by name, using the first multiscale as a fallback" (S003 388–389). The spec offers no normative view-fitting rule (U02a) — the plan's heuristic is its own design; it must additionally handle the multi-multiscales case, which the plan does not mention.

**P05 — Label overlays: alignment is guaranteed structurally, colors are SHOULD, fallbacks are product-owned. [extend]**
Plan: "optional overlays for associated label images" (Viewer.md line 5). Evidence: label images MUST have the same number of scale levels as the parent image (S003 454–455), so level-to-level overlay registration is possible by construction; label dims may differ by 1 where irrelevant (S003 106–108), so broadcasting is required; label pixels are integer-only (S003 438–439); discovery via the `labels` key (S003 441–442, with SHOULD-complete listing at 442); readers SHOULD honor `image-label` rgba colors incl. alpha (S003 461–466); `source.image` defaults to `"../../"` (S003 472–474). If `image-label`/`colors` is absent there is no spec-sourced color — fallback coloring is a **decide** item.

**P06 — Channel rendering defaults exist only via optional transitional `omero`. [decide]**
Plan's channel visibility controls need defaults. Evidence: the only render metadata in the format is optional transitional `omero` (S003 426; transitional status 60–64, 398–400) with MUST-conditional `color` and `window` min/max/start/end (S003 427–430); `rdefs` defaults (defaultT/defaultZ/model) appear only as an example (S003 419–423, 401–418) and carry no MUST in this capture. Absent `omero`, the plan needs its own fallback (e.g., grayscale with data-driven window) — a product decision that must not be presented as format compliance, and one that carries transitional-removal risk if over-relied upon.

**P07 — Local-only reading is a declared product boundary, not a format constraint. [limit]**
Evidence: the format explicitly contemplates HTTP and S3/GCS storage (S003 73–77). The plan's local-filesystem boundary (Viewer.md line 9) is compatible but must be described as a product restriction; remote filesets are a known, spec-supported case being declined (transfer/completeness limit per R06).

**P08 — Build reading on a Zarr v3 implementation rather than hand-rolled parsing — engineering option with explicit assumptions. [decide]**
Evidence: OME-Zarr 0.5 sits on Zarr v3 with the full feature surface allowed (F01, S003 67–72, 87, 99–100). Option: adopt an existing Zarr v3 library for chunk I/O and codecs. Transfer limits (R06): this corpus contains no implementation evidence to confirm library availability, maturity, or 0.5-metadata coverage (U01); the assumption "a maintained Zarr v3 reader exists for the implementation language" is unverified here and must be validated (see V-11 below) before the option is treated as an engineering fact.

**P09 — Version interop: the plan targets 0.5 only; older filesets need a declared behavior. [decide]**
Plan: "interoperate with filesets from real OME-Zarr 0.5 tools" (Viewer.md line 9). Evidence: 0.5 = Zarr v3 (S003 831–833) + `ome`-namespaced metadata (F02) + `dimension_names` MUST (S003 174); 0.4-era filesets predate parts of this (b2raw added 0.4, S003 180–181; axes units/transforms 0.4.0, S003 842); the spec promises migration scripts between versions (S003 25–26) but none are in scope. Reading a 0.4 fileset with a 0.5-only reader is a foreseeable failure mode; the plan must decide to either reject with a clear message or support it — silence here contradicts the plan's own "understandable feedback" acceptance (Viewer.md line 11).

**P10 — Failure feedback has no format-defined semantics; the spec still shapes it. [extend]**
Plan: "Opening failures explain which image or data could not be displayed…" (Viewer.md line 7). Evidence: no error-handling semantics exist in the capture (U02b, scoped to S003). But format facts the error UX must respect: metadata may be legitimately partial (`omero` optional S003 426; `image-label` MAY-keys S003 467), wells/rows may be absent (S003 128–129), collections must not be mixed with plates (S003 206), and multi-image collections SHOULD be surfaced to the user rather than silently reduced (S003 272). Distinction required: "fileset is malformed" vs "fileset uses an optional capability the viewer declines".

**P11 — Plan acceptance checklist needs additions. [extend]**
Plan acceptance covers discovery, navigation, channel/plane controls, calibrated coordinates, aligned overlays, large-dataset responsiveness, and malformed-input feedback (Viewer.md line 11). Not yet covered by the plan, each traceable to obligations above: (1) multi-image series chooser (S003 272, 388–389); (2) HCS plate navigation incl. sparse plates (S003 641–739); (3) custom/null axis type handling (S003 169, 301); (4) missing-`omero` fallback rendering; (5) declared behavior on 0.4-era filesets (P09); (6) path-form transform vectors decision (P03); (7) missing-plate-`version` tolerance decision (F14).

**P12 — Background reads/cancellation are product commitments the format enables but does not require. [adopt, labeled]**
Evidence: the format's chunked arrays (S003 91–100) and allowed chunk grids/codecs (S003 70–72) make partial, deferred reads possible; nothing in the capture mandates async behavior or responsiveness (U02c). The plan's "Large image reads run in the background…" and "Changing the selected view cancels work…" (Viewer.md line 7) are product decisions supported by the format's mechanics, not obligations of it.

## 4. Engineering alternatives and improvement opportunities (with transfer limits)

1. **Zarr v3 library for storage I/O** (P08): assumes a maintained, spec-complete Zarr v3 reader exists for the target language; unverified in this corpus (U01). Improvement: isolate storage I/O behind an interface so the library choice is reversible.
2. **UDUNITS-2-based unit handling** for the details panel (S003 170–172): assumes a units-conversion dependency; the spec only enumerates unit *strings*, conversion is external. Limit: unit strings are SHOULD-level; unitless or unknown-unit axes must degrade gracefully.
3. **View-fitting level heuristic** (P04): e.g., choose the level whose pixel size best matches the on-screen scale. Transfer limit: purely a design option; the only format facts are ordering (S003 306) and the non-normative chunk-size remark (S003 396).
4. **Chunk-aligned tile pipeline with cancellation** (P12): map viewport → chunk indices per selected level; cancel superseded reads. Enabled by Zarr chunk semantics (S003 91–100); not required by the format.
