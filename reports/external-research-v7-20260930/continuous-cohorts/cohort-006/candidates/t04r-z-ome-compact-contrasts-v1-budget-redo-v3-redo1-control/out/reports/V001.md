## 0. Scope, method, evidence conventions

- The plan (`inputs/plan/Viewer.md`, "the Plan") is deliberately thin; this report investigates the format obligations and implementation requirements the Plan needs, per the brief (`inputs/brief.md`, "the Brief").
- **Evidence classes used below:**
  - **[EVIDENCE]** — observed directly in S003 with an exact line/section locator. Normative keywords MUST / MUST NOT / SHOULD / MAY are used exactly as S003 uses them (S003 L57–L59, RFC 2119 per L895–L896). Per S003's conformance section, examples and notes are non-normative (L877–L883).
  - **[INFERENCE]** — my interpretation drawn from evidence; not a source statement.
  - **[UNRESOLVED]** — open question not answerable from the admitted sources.
  - **[EXAMPLE-ONLY]** — observed only in a non-normative example in S003.
  - **[PRODUCT-DECISION]** — a choice the format leaves open that the Brief/Plan must decide.
- **Citation convention:** `S003 L<n>–L<m>` = `inputs/sources/S003.txt` line numbers; `§x.y` = S003 section numbers. `Plan L<n>` = `inputs/plan/Viewer.md`; `Brief L<n>` = `inputs/brief.md`. ## 1. Baseline: storage model and metadata placement

**F-B01 — OME-Zarr 0.5 is a set of conventions on Zarr v3.** [EVIDENCE]
"OME-Zarr is implemented using the Zarr format as defined by the version 3 of the Zarr specification," and "All features of the Zarr format including codecs, chunk grids, chunk key encodings, data types and storage transformers may be used with OME-Zarr unless explicitly disallowed in this specification" (S003 L67–L72; history: 0.5.0 "use Zarr v3 in OME-Zarr", L831–L833).
*Implication:* a reader cannot assume one chunk layout, one codec, or contiguous on-disk files; per-array `zarr.json` must be parsed to learn chunk shape, codecs, and encodings. The capture does not disallow any Zarr feature for image data.
*Condition:* "unless explicitly disallowed" — the disallow list within this capture is empty for image arrays.

**F-B02 — Metadata lives in `zarr.json` under the namespaced `ome` key, with a version string that MUST be hierarchy-consistent.** [EVIDENCE]
OME-Zarr Metadata is stored "under the namespaced key ome in attributes" of the various `zarr.json` files (S003 L149–L154); "The OME-Zarr Metadata version MUST be consistent within a hierarchy" (L155–L156); example `"version": "0.5"` (L157–L165).
*Implication:* the version check is a concrete validation the viewer can and should perform; a violation is a legitimate "cannot display, and here is why" case (Plan L7).

**F-B03 — Normative language is RFC 2119; examples are informative.** [EVIDENCE]
S003 L57–L59 (keywords), L867–L888 (all text normative except explicitly non-normative examples/notes). Several reader-facing behaviors appear only inside examples (e.g., the multiscale-selection pseudocode, §2.4) and therefore are guidance, not obligations. `[EXAMPLE-ONLY]` items below are marked.

**F-B04 — Transitional metadata policy.** [EVIDENCE]
Transitional metadata is added "with the intention of removing it in the future. Implementations may be expected (MUST) or encouraged (SHOULD) to support the reading of the data, but writing will usually be optional (MAY)" (S003 L60–L64). Transitional in this capture: `bioformats2raw.layout` (§2.2, L175–L181) and `omero` (§2.5, L398–L400).
*Implication:* a read-only viewer is exactly the kind of implementation the spec expects to keep supporting transitional keys; a writer would not need them. Removal risk is a version qualification that must stay attached to any claim built on these keys (rule R01).

**F-B05 — Document status and version qualifications.** [EVIDENCE]
The capture is the "Final Community Group Report, 8 September 2026" for version 0.5 (S003 L3–L4, L6); "The current released version of this specification is 0.5. Migration scripts will be provided between numbered versions. Data written with these latest changes (an "editor's draft") will not necessarily be supported." (L24–L27). Version history records 0.5.0 (Zarr v3, 2024-11-21, L831–L833), 0.5.1 (re-add improved `omero` description, L828–L830), 0.5.2 ("Clarify that the dimension_names field in axes MUST be included", L825–L827).
*Condition:* every claim in this report is scoped to OME-Zarr **0.5** as frozen in this capture. Behavior of older filesets (e.g., 0.4 Zarr-v2 layouts) is not specified inside S003 and is unresolved here (§9, U-07).

## 2. Group 1 — Opening a fileset, listing/selecting images, navigating multiresolution data

**F-G1-01 — Image anatomy: one image = one Zarr group; levels = sibling Zarr arrays; ordering comes from metadata, not names.** [EVIDENCE]
"Each image is a Zarr group"; group-level attributes include `"multiscales"` and `"omero"` (S003 L87–L89). "Each multiscale level is stored as a separate Zarr array" (L91–L92); "The name of the array is arbitrary with the ordering defined by the 'multiscales' metadata, but is often a sequence starting at 0" (L93–L94). Level `path`s are relative to the current group and "MUST be ordered from largest (i.e. highest resolution) to smallest" (L305–L306).
*Implication:* pyramid-level selection (Plan L5 "The viewer chooses an available pyramid level") must iterate `multiscales[].datasets[]` in listed order. Lexicographic directory sorting would misorder levels (e.g., "10" before "2") and is not sanctioned by the format. [INFERENCE from L93–L94 + L305–L306]

**F-G1-02 — Dimensionality is variable (2–5); axis identity comes from metadata, not file conventions.** [EVIDENCE]
"the number of dimensions is variable between 2 and 5 and … axis names are arbitrary" (S003 L81); `axes` length MUST equal the array dimensionality (L173, L300); axes MUST contain 2–3 space entries and MAY one time and MAY one channel or null/custom entry (L301); axis order MUST match array dimension order with time first, then channel/custom, then space (L96–L97 diagram note; normative restatement L301–L302).
*Implication:* nothing about an OME-Zarr fileset can be hard-coded around names like `c`, `t`, `z`; the viewer must classify axes by `type` when present. Plane/time controls are "where relevant" (Plan L5) precisely because a given image may lack time or channel axes.

**F-G1-03 — `axes` field obligations.** [EVIDENCE]
Each axis dict MUST contain `name`, unique across axes; SHOULD contain `type` (SHOULD be `space`/`time`/`channel`, MAY be other custom strings); SHOULD contain `unit` (S003 L167–L170). UDUNITS-2 unit string lists for space (L171) and time (L172) axes are given as SHOULD-level values.
*Condition:* `type` and `unit` are SHOULD, not MUST — a conforming file may omit them (drives F-G2-04 and CE-02).

**F-G1-04 — `dimension_names` MUST be present in each level array's `zarr.json` and match `axes`.** [EVIDENCE]
"The 'dimension_names' attribute MUST be included in the zarr.json of the Zarr array of a multiscale level and MUST match the names in the 'axes' metadata" (S003 L174; clarified as a MUST in 0.5.2, L825–L827).
*Implication:* the viewer can cross-check array metadata against group metadata; a mismatch is a detectable, explainable malformation.

**F-G1-05 — `multiscales` obligations (the navigation core).** [EVIDENCE]
Each multiscales dict MUST contain `axes` (S003 L299) and `datasets` (L304); each dataset MUST contain `path` (L305–L306) and `coordinateTransformations` (L308) whose transformations MUST only be translation or scale, containing exactly one scale (L309–L310); MAY contain exactly one translation, which MUST come after scale (L311); scale/translation array lengths MUST equal the axes length (L312). Rationale stated: a simple data→physical mapping compatible with the general transformation spec (L313). SHOULD-level: `name` (L317), `type` and `metadata` describing the downscaling method (L318–L319).

**F-G1-06 — Group-level `coordinateTransformations` apply to all levels, after the per-level ones.** [EVIDENCE]
Each multiscales dict MAY contain `coordinateTransformations` applied to all resolution levels; same type/order rules; "applied after them" (S003 L314–L316; example: time scaling identical across levels, L368–L374).
*Implication:* physical coordinate computation = per-dataset transformations, then group-level transformations, in order. Skipping the group-level list yields wrong time/physical coordinates. [INFERENCE from L314–L315]

**F-G1-07 — Multiple `multiscales` entries: use single; otherwise user chooses by name with first as fallback.** [EXAMPLE-ONLY, EVIDENCE of existence]
"If only one multiscale is provided, use it. Otherwise, the user can choose by name, using the first multiscale as a fallback" with pseudocode (S003 L388–L397). This guidance sits in an example context, so it is informative rather than a MUST for readers; the existence of multiple multiscales entries in one group is what the normative text establishes ("multiscales contains a list of dictionaries", L298).
*Implication / plan gap:* the Plan never mentions choosing among multiple multiscale entries in one image group; a small selection rule (default first, user-choosable by name) is a needed product decision.

**F-G1-08 — Multi-image collections: `bioformats2raw.layout` (transitional).** [EVIDENCE]
Top-level `zarr.json` must contain the `bioformats2raw.layout` key (S003 L193); conforming groups MUST have value `"3"` (L256). An `OME` group MAY exist and MAY contain a `series` attribute: `series` MUST be a list of strings (paths to image groups) whose order MUST match the `Image` element order of `OME/METADATA.ome.xml` if provided (L264–L267). If no `series` and no `plate`: multiscales images MUST be in consecutively numbered groups from `0` (L268–L269), each multiscales group representing exactly one OME-XML Image in the same order (L270). `OME/METADATA.ome.xml` SHOULD exist, MUST adhere to OME-XML, MUST use `<MetadataOnly/>` and not `<BinData/>`/`<BinaryOnly/>`/`<TiffData/>` (L257–L260).
*Conditions:* all of the discovery logic is conditional on which keys/groups are present (`plate` vs `series` vs neither) — the viewer must implement the branch tree, not one path.

**F-G1-09 — Reader obligations for collections: do not silently open only the first image.** [EVIDENCE]
"Conforming readers: SHOULD make users aware of the presence of more than one image (i.e. SHOULD NOT default to only opening the first image); MAY use the 'series' attribute …; MAY choose to show all images within the collection or offer the user a choice …; MAY ignore other groups or arrays under the root" (S003 L271–L275).
*Implication:* this directly underwrites the Brief requirement "find images within a fileset" (Brief L3) and the Plan's image list (Plan L5). The SHOULD-level awareness duty means a viewer that silently shows only image 0 of a collection is non-conforming even though the files themselves are fine.

**F-G1-10 — HCS plate hierarchy is a mandatory grouping, navigable as plate → row → column/well → field of view.** [EVIDENCE]
For HCS, "Three groups MUST be defined above the images": the group above the images is the well and MUST implement the well specification; above the well a row; above the row a plate which MUST implement the plate specification (S003 L118–L127). "All images contained in a well are fields of view of the same well" (L121–L123). A well row group SHOULD NOT be present if the row has no images; a well group SHOULD NOT be present if the well has no images (L128–L129). Field-of-view groups carry `multiscales` (+`omero`), resolution levels, and optional `labels` (L140–L146).
*Implication / plan gap:* the Plan's single "lists the images it finds" (Plan L5) silently assumes a flat list. For plate filesets, image discovery requires hierarchical traversal per the plate metadata; this is a structural plan gap, not an optional nicety.

**F-G1-11 — `plate` metadata obligations.** [EVIDENCE]
MUST: `columns` (list; each column MUST have `name`, alphanumeric, case-sensitive, unique; every physical column MUST be defined even if empty) (S003 L530–L537); `rows` (same rules) (L542–L549); `version` (string) (L550–L551); `wells` (list; each well MUST have `path` = rowName + "/" + columnName with no extra leading/trailing directories, plus 0-based `rowIndex` and `columnIndex`, all three referring to the same row/column pair) (L552–L560). SHOULD: `field_count` (positive integer, max fields per view across all wells) (L538–L539); `name` (string) (L540–L541). MAY: `acquisitions` (list; each MUST have unique integer `id` ≥ 0; SHOULD have `name`; SHOULD have `maximumfieldcount` (positive integer); MAY `description`, `starttime`/`endtime` as integer epoch timestamps) (L518–L529). Sparse plates are explicitly supported (only defined wells appear in `wells`; example of 2 wells in a 96-well plate, L641–L739).
*Local-filesystem note:* the spec's caution about case-colliding row/column names on case-insensitive filesystems (L536–L537, L548–L549) is directly relevant to Slide Scout's local-reading boundary (Brief L3).

**F-G1-12 — `well` metadata obligations.** [EVIDENCE]
The well dict MUST contain `images` (list; each entry MUST have `path` — alphanumeric, case-sensitive, unique within the list; if multiple acquisitions, an `acquisition` key MUST be present, an integer matching a plate acquisition id) (S003 L744–L750); SHOULD contain `version` (string) (L751–L752). Examples: L756–L808.

**F-G1-13 — `plate` + `bioformats2raw.layout` precedence; no mixing.** [EVIDENCE]
"If the top-level group represents a plate, the bioformats2raw.layout metadata will be present but the 'plate' key MUST also be present, takes precedence and parsing of such datasets should follow § 2.7 … It is not possible to mix collections of images with plates at present." (S003 L204–L206; also: if `plate` is present, images MUST be located at the plate-defined locations, L262; `series` SHOULD be provided for tools unaware of plate, L263).
*Implication:* a detector order is prescribed: check `plate` first; `bioformats2raw.layout` alone means a series collection. A viewer that treats a plate root as a bioformats2raw collection will misparse it.

**F-G1-14 — Zarr storage is location-agnostic in the format (local dir, HTTP, object storage).** [EVIDENCE]
The hierarchy "could equally be stored on a web server to be accessed via HTTP or in object storage like S3 or GCS" (S003 L73–L77). Slide Scout's local-only boundary (Brief L3; Plan L9) is a product restriction, not a format property; nothing in S003 assumes locality.
*Implication:* keep the storage-access layer narrow and swappable so the local boundary costs little to maintain. [INFERENCE]

## 3. Group 2 — Channel/time/plane display, coordinate details, associated label overlays

**F-G2-01 — `omero` display metadata is optional and transitional; when present its MUSTs are narrow.** [EVIDENCE]
"The 'omero' metadata is optional, but if present it MUST contain the field 'channels'" (S003 L398–L400, L426); each channel dict MUST contain `color` (string of 6 hex digits, RGB) (L427) and `window`, which MUST contain `min`/`max` and `start`/`end` (L428–L430). The rich example (L401–L423) shows `id`, `name`, `active`, `coefficient`, `family`, `inverted`, `label`, and `rdefs` (`defaultT`, `defaultZ`, `model`) — but only `channels`/`color`/`window` are normative requirements. `rdefs` (`defaultT` "First timepoint to show the user", `defaultZ` "First Z section", `model` "color"/"greyscale") is **[EXAMPLE-ONLY]**. Semantics beyond this are delegated to the OMERO WebGateway documentation (L424–L425), which is outside the admitted capture (§9, U-02).
*Implication:* channel visibility controls (Plan L5) can be pre-populated from `omero` when present; absence is conforming, so a fallback (all channels on, neutral colors) is a required design element, not polish. [INFERENCE] Channel count correspondence with the `c` dimension appears only in an example comment (L403) — treat "channels array matches the c dimension" as [EXAMPLE-ONLY]/[INFERENCE], and verify per file.

**F-G2-02 — `coordinateTransformations` vocabulary is closed: identity, translation, scale — with a `path` variant.** [EVIDENCE]
Each entry MUST contain `type`; `type` MUST be one of identity / translation / scale (S003 L279–L280); identity is the default and typically not explicit (L282–L283); translation and scale vectors are "stored either as a list of floats … or as binary data at a location in this container (path)" (L284–L289); transformations "are applied sequentially and in order" (L293).
*Implication / plan gap:* the Plan assumes plain numeric transforms implicitly. The `path` variant means a scale/translation vector can live as binary data elsewhere in the container; how to locate and decode that binary payload is not elaborated in the capture (§9, U-05). At minimum the viewer must detect the `path` variant and either support it or explain the limitation (Plan L7 failure-explanation duty).

**F-G2-03 — Physical calibration rule (the "correctly calibrated coordinates" requirement).** [EVIDENCE]
Per-dataset transformations "map the data coordinates to the physical coordinates … for this resolution level" (S003 L308). The exactly-one scale "specifies the pixel size in physical units or time duration. If scaling information is not available or applicable for one of the axes, the value MUST express the scaling factor between the current resolution and the first resolution for the given axis, defaulting to 1.0 if there is no downsampling along the axis" (L310). Translation MAY appear, MUST be listed after scale so it is "given in physical coordinates" (L311); array length MUST equal axes length (L312); group-level transformations apply after dataset-level ones (L314–L315). Worked example: 5D t/c/z/y/x with 0.5 µm voxels at level 0, 1.0/2.0 µm at coarser levels, and 0.1 ms time scaling at group level (L320–L374).
*Implication:* calibrated coordinate display (Plan L5) requires composing, per axis: dataset scale → (optional) dataset translation → group-level transformations. The time axis's physical spacing also comes from scale ("time duration", L310) — time navigation is coordinate-bearing, not just an integer index. [INFERENCE]
*Condition (R01):* when scaling information is unavailable for an axis, the value is a relative factor defaulting to 1.0 — i.e., the format itself anticipates axes with no absolute calibration.

**F-G2-04 — Units are SHOULD-level; calibration can be unit-less.** [EVIDENCE]
`unit` is SHOULD on axes (S003 L170) with SHOULD-level UDUNITS-2 value lists for space (L171) and time (L172). No MUST requires any unit to be present.
*Implication:* the Brief's "read correctly calibrated coordinates" (Brief L3) cannot always be fully honored from the file alone; the details panel must show values without inventing units, and label the absence honestly. [PRODUCT-DECISION on presentation] + [EVIDENCE on the obligation level]

**F-G2-05 — Plane ordering: `zyx` SHOULD for anisotropic 3D.** [EVIDENCE]
"If there are three spatial axes where two correspond to the image plane ('yx') and images are stacked along the other (anisotropic) axis ('z'), the spatial axes SHOULD be ordered as 'zyx'" (S003 L303).
*Implication:* plane (z) sliders (Plan L5) should be driven by the detected space axes, with `zyx` as the expected but not guaranteed order. [INFERENCE]

**F-G2-06 — Label image discovery and structural constraints.** [EVIDENCE]
Label images live in a `labels` group "nested within an image group, at the same level of the Zarr hierarchy as the resolution levels" (S003 L431–L437). The `labels` group "is not itself an image; it contains images"; label pixel types MUST be one of uint8/int8/uint16/int16/uint32/int32/uint64/int64 (L438–L439; echoed in the layout diagram, L116–L117). Intermediate groups between `labels` and label images are allowed but MUST NOT contain metadata (L439–L440); label image names are arbitrary (L440). The `labels` group's `zarr.json` MUST contain the `labels` key — a JSON array of paths to the labeled multiscale image(s); all label images SHOULD be listed (L441–L442; example L443–L453; also L104–L105). The label image itself MUST implement the multiscales specification, and its `datasets` array MUST have "the same number of entries (scale levels) as the original unlabeled image" (L454–L455).
*Conditions:* the MUST-level overlay-relevant guarantees are (a) integer pixel types, (b) multiscales compliance, (c) equal scale-level count. Dimension-size compatibility is weaker — see F-G2-08.

**F-G2-07 — `image-label` display metadata: SHOULD-level key, with colors the reader SHOULD honor.** [EVIDENCE]
The label image's `zarr.json` SHOULD contain `image-label` (S003 L456), which stores display colors, source image, and optionally arbitrary properties (L457). `image-label` SHOULD contain `colors` (whose value MUST be a JSON array) and `version` (MUST be a string) (L458–L460). "Conforming readers SHOULD display labels using the colors specified by the colors JSON array": one object per unique label; each object MUST contain integer `label-value`; MAY contain `rgba` — MUST be four integers 0–255 (R,G,B,alpha/opacity) (L461–L466; example L483–L492; rendering interpretation L513–L514). MAY contain `properties` (array; each object MUST contain integer `label-value`; arbitrary per-label key–value pairs; objects need not share keys) (L467–L471; example L493–L505) and `source` (MUST be a JSON object; MAY include `image`, a string relative path to the source Zarr image group; default `../../`) (L472–L474; example L506–L508).
*Implication:* overlay rendering should consume `image-label.colors` (SHOULD-level duty on readers), fall back to a generated palette when absent or when a label value has no `rgba` entry, and can surface `properties` as a tooltip/hover feature. [INFERENCE + PRODUCT-DECISION]

**F-G2-08 — Label↔image geometric compatibility is guaranteed only softly.** [EVIDENCE + condition]
Layout notes: "Each dimension of the label should be either the same as the corresponding dimension of the image, or 1 if that dimension of the label is irrelevant" (S003 L106–L108) — SHOULD-level, in a diagram. Semantics section: label images are "in the same coordinate system as a corresponding multiscale image (**usually** having the same dimensions and coordinate transformations)" (L433) — hedged.
*Implication:* the only hard guarantees (MUST) are integer types, multiscales compliance, and equal scale-level count (F-G2-06). Overlay alignment must therefore be computed per file from axes/transforms, handle dimensions of size 1 (broadcast), and degrade with an explanation when geometry genuinely diverges. [INFERENCE]

## 4. Cross-cutting conformance findings

**F-Q01 — Spec examples contain JSON comments; real files MUST NOT.** [EVIDENCE]
"Some of the JSON examples in this document include comments … comments MUST NOT be included in JSON objects" (S003 L65–L66). *Implication:* fixtures and parsers must not treat the spec's commented examples as literal valid JSON; a strict JSON parser is correct.

**F-Q02 — Key naming is camelCase in principle but with acknowledged exceptions; take names literally.** [EVIDENCE]
Multi-word keys "should use the camelCase style", but "some parts of the specification don't obey this convention" (S003 L809–L812). Observed instance: acquisition `maximumfieldcount` (all lowercase, L524–L525) vs plate `field_count` (snake_case, L538–L539). *Implication:* property lookups must use the exact spelled keys from §2, not a normalization scheme. [INFERENCE]

**F-Q03 — Same hierarchy rules apply regardless of discovery branch.** [EVIDENCE]
`multiscales`/`axes`/`datasets` obligations are identical for plain image groups, `series` collections, and plate fields of view (S003 L294–L316 apply wherever `multiscales` appears; plate fields of view implement "multiscales", "omero", L142).

## 7. Counterevidence, tensions and applicability limits (rule R04)

- **CE-01 — Transitional keys are both deprecated-in-intent and interop-required.** S003 intends to remove transitional metadata (L60–L64, L175–L181) while simultaneously expecting implementations to read it (L61–L62) and noting these layouts exist "in the wild" (L180–L181). For Slide Scout both facts must stay visible: implement reading of `bioformats2raw.layout` + `omero` for 0.5 interop (Plan L9), and do not build new product features on top of transitional semantics without an exit plan. [EVIDENCE + INFERENCE]
- **CE-02 — "Correctly calibrated coordinates" vs SHOULD-only units.** The Brief requires correct calibration (Brief L3), but S003 makes `unit` SHOULD (L170) and anticipates axes with no absolute scaling (L310 fallback factor defaulting 1.0). Strongest conflicting evidence retained: conforming files can be un-calibratable in absolute terms; the viewer must display factor-only or unit-less axes with an explicit caveat rather than failing. [EVIDENCE + PRODUCT-DECISION]
- **CE-03 — Overlay alignment guarantees are weaker than "aligned label overlays" suggests.** Plan acceptance says "aligned label overlays" (Plan L11); the format guarantees only equal scale-level count (L454–L455) with "usually" geometry (L433). Tests must include a dim-1 label and a mismatched-geometry label to exercise the degradation path (PV-05). [EVIDENCE + INFERENCE]
- **CE-04 — Plate vs collection parsing.** The precedence rule (L204–L206) is itself evidence that both real-world shapes occur with overlapping top-level keys; a naive key-sniffing parser has two valid-looking readings and the spec pins only one. Retained as a correctness constraint, not simplified away.
- **CE-05 — Transfer limits on external mechanisms (rule R06).** The OMERO WebGateway rendering model referenced by S003 (L424–L425) originates in a server-side rendering context; importing its semantics (e.g., `family`, `coefficient`, `inverted`, window math) into a local read-only desktop viewer is an engineering option only under the explicit assumption that those semantics are defined outside this capture and were not verified here (U-02). Likewise, the spec's multiscale-selection pseudocode (L388–L397) is informative guidance from the spec-authoring context, not an obligation; adopting it is a product choice.
