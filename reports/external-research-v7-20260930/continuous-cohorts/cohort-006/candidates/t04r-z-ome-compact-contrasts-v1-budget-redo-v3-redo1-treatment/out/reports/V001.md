## 3. Findings — Group A: opening a fileset, listing/selecting images, navigating multiresolution data

### SS-A1 — Container is Zarr v3; the full Zarr feature surface is in scope
Under the OME-Zarr 0.5 specification, an OME-Zarr fileset is implemented using the Zarr format **version 3** (S003 L67–L72; version history: "0.5.0 … use Zarr v3 in OME-Zarr" L831–L833). Condition (preserved, R01): "All features of the Zarr format including codecs, chunk grids, chunk key encodings, data types and storage transformers may be used with OME-Zarr **unless explicitly disallowed in this specification**" (L70–L72). Consequences:
- The viewer must be a Zarr v3 reader: group/array metadata lives in `zarr.json` files (shown throughout, e.g. L87–L89, L195–L197, L564–L566).
- A reader that assumes raw, uncompressed chunks or one fixed chunk-grid encoding will fail on conforming filesets; codec/shard breadth is a compatibility requirement, not a nicety.
- Applicability limit (R04/R05): the Zarr v3 normative text itself is **not** part of the capture (only referenced at L68–L69); obligations inside the Zarr spec are outside the inspected region (see §8 U1).

### SS-A2 — Metadata location and version contract
OME-Zarr 0.5 metadata is stored in the `zarr.json` files throughout the hierarchy **under the namespaced key `ome` in attributes** (S003 L149–L154), e.g. `attributes.ome.version: "0.5"` (L157–L165). The `ome` version "MUST be consistent within a hierarchy" (L155–L156) — condition: within one opened hierarchy. Image groups carry group-level attributes including `"multiscales"` and `"omero"` (L87–L89). Viewer implication: discovery means scanning candidate groups for `attributes.ome.multiscales`; a version mismatch inside an opened hierarchy is a malformed-input case that must be reported, not silently tolerated.

### SS-A3 — Dimensionality and axis order are fixed by the format
Multiscale image data is 2–5 dimensional (S003 L81, L296, L300); arrays "MUST NOT [have] more than 5 dimensions" (L307). Axes MUST be ordered by type: time first (if present), then channel or custom axis (if present), then space (L301–L302; corroborated by the layout diagram comment "axis of type time before type channel, before spatial axes", L96–L97). For anisotropic z-stacks, `zyx` spatial ordering is SHOULD (L303). Viewer implication: axis roles can be derived from `axes[].type`; "time/plane selection where relevant" is decided by axis presence, which is conditional per file (R01).

### SS-A4 — Pyramid level identity is positional, not nominal
Each multiscale level is a separate Zarr array whose **name is arbitrary**; "the ordering defined by the 'multiscales' metadata" is what matters, names are "often a sequence starting at 0" (S003 L91–L94). The `datasets[].path` list "MUST be ordered from largest (i.e. highest resolution) to smallest" (L305–L306). Viewer implication: level index = position in the `datasets` list; never sort level paths lexicographically (inference, marked: lexicographic sorting breaks at ≥10 levels, e.g. "10" before "2" — this failure mode is not discussed in S003, but follows from L93–L94 + L305–L306). Level selection policy for "the pyramid level appropriate for the current view" is a **product decision** — the spec's only selection guidance is an informative example about choosing among *named multiscale entries* ("If only one multiscale is provided, use it. Otherwise, the user can choose by name, using the first multiscale as a fallback", L388–L397), which is example text, not a MUST (R03).

### SS-A5 — Multi-image filesets: three discovery families the image list must cover
The plan sentence "opens a local OME-Zarr 0.5 fileset and lists the images it finds" requires three distinct layout families:

**SS-A5a — Plain image collection.** Sibling image groups (e.g. `123.zarr`, `456.zarr`), each a Zarr group with `multiscales` (+ optional `omero`) in `zarr.json`, each containing one array folder per resolution level (S003 L82–L94). Optionally a `labels` subgroup (L102–L117).

**SS-A5b — `bioformats2raw.layout` collections (transitional).** For multi-series conversions ("series.ome.zarr", S003 L183–L191):
- A conforming group MUST have value `"3"` for the `bioformats2raw.layout` key in the top-level `zarr.json` OME metadata (L193–L203, L256).
- Image-finding logic, conditions preserved (R01): if `"plate"` metadata is present, images MUST be located at the plate-defined locations and **plate takes precedence** — parsing follows the plate spec, and mixing image collections with plates is not possible (L204–L206, L262). If the `OME` group exists it MAY contain a `"series"` attribute, which MUST be a list of string paths whose order MUST match the `<Image>` order of `OME/METADATA.ome.xml` if provided (L264–L267). If no `series` attribute and no plate: multiscale images MUST be in consecutively numbered groups starting from 0, each representing exactly one OME-XML Image in that order (L268–L270).
- `OME/METADATA.ome.xml` SHOULD be present; it MUST adhere to OME-XML and MUST use `<MetadataOnly/>` rather than `<BinData/>`, `<BinaryOnly/>` or `<TiffData/>` (L257–L260).
- Reader obligations (conditions preserved): conforming readers "SHOULD make users aware of the presence of more than one image (i.e. SHOULD NOT default to only opening the first image)" (L272); MAY use `series` (L273); MAY show all images or offer a choice (L274); MAY ignore other groups/arrays under the root (L275). The plan's "lists the images it finds" therefore also satisfies this SHOULD, but only if discovery covers the `series`/numbered-group layouts, which the thin plan never mentions.

**SS-A5c — High-content screening (HCS) plates.** Three groups MUST be defined above the images: the well group (MUST implement the well specification), the row group, and the plate group (MUST implement the plate specification); all images in a well are fields of view of that well (S003 L119–L127). Structural MUSTs (triage detail in §6): plate `columns`, `rows`, `version`, `wells` are MUST; well `images` list is MUST; well paths are `row/column` with 0-based `rowIndex`/`columnIndex` that MUST agree with the path; column/row names alphanumeric, case-sensitive, unique; sparse plates are legal — every physical row/column MUST be defined even if empty, and empty row/well groups SHOULD NOT be present, so a 96-well grid may contain only 2 well groups (L128–L130, L530–L560, L641–L739 sparse-plate example). Well fields: `images[].path` alphanumeric, unique, plus `acquisition` when the plate has multiple acquisitions (L744–L750). Labels are optional at field level (L145).
**Gap vs plan:** the thin plan (inputs/plan/Viewer.md) describes none of the plate/well navigation; a plate fileset has its images three groups below the root, so naive "list groups with multiscales at depth ≤1" discovery would find nothing.

### SS-A6 — `dimension_names` integrity check at open time
`axes` length MUST equal the dimensionality of the image arrays (S003 L173, L300), and the `"dimension_names"` attribute MUST be included in the `zarr.json` of each multiscale array and MUST match the names in the `axes` metadata (L174; clarified as MUST in 0.5.2, L825–L827). Viewer implication: this is a cheap, decisive well-formedness check to run at open; violation = malformed input that the plan's "understandable feedback" requirement must cover.

## 4. Findings — Group B: channel/time/plane display, coordinate details, associated label overlays

### SS-B1 — Axes metadata: what is guaranteed for the details panel and axis controls
Per axis dictionary (S003 L166–L174): `name` MUST be present and names MUST be unique across axes (L168); `type` SHOULD be present and SHOULD be `space`/`time`/`channel` but **MAY be any other string** for custom axis types (L169) — condition: a viewer must not reject an image merely because an axis type is unfamiliar; `unit` SHOULD be present, SHOULD be a UDUNITS-2 string; the capture enumerates the valid space and time unit strings (L170–L172). Viewer implications: (i) the details panel can rely on names, conditionally on types, and only weakly on units (a missing unit is conforming — display fallback is a product decision); (ii) unit formatting/canonicalization (e.g. "micrometer" vs "µm") is not specified in the capture — product decision (§6).

### SS-B2 — Coordinate calibration: scale/translation composition rules
The data→physical mapping is defined per resolution level (S003 L304–L316) under the general model that a `coordinateTransformations` list is "applied sequentially and in order" (L293) with `identity` the default (L282–L283); allowed types include `translation` and `scale`, each either an inline float vector or a `path` to binary data in the container (L284–L289). Conditions, preserved:
- Each `datasets[]` entry MUST contain `coordinateTransformations` (L308) which MUST only be of type translation or scale (L309) and MUST contain **exactly one scale**; the scale "specifies the pixel size in physical units or time duration", and **under the condition** that scaling information is unavailable for an axis, that axis' value MUST express the factor between the current and first resolution, defaulting to 1.0 with no downsampling (L310).
- A translation MAY be present, exactly one, and MUST be listed **after** scale (L311).
- Scale/translation vector lengths MUST equal the axes count (L312).
- The `multiscales` dictionary MAY carry its own `coordinateTransformations`, following the same type/order rules, **applied after** the per-level ones — e.g. for a time scale shared by all levels (L314–L316).
Consequence (source-stated, not inference): the physical coordinate of a sample at level *i* = apply level-*i* transformations, then the multiscales-level transformations (L315). Open items that remain unknown (R03): whether real writers always emit absolute physical sizes vs the relative-factor fallback of L310 is not observable from the capture — this is flagged for validation (§9 V3), not asserted either way.

### SS-B3 — Channel/time/plane display defaults: `omero` is optional and transitional
Channel rendering info lives under the transitional `omero` key (S003 L398–L400). Conditions (R01): `"omero"` metadata **is optional**, but **if present** it MUST contain `channels` (array of dictionaries); each channel dictionary MUST contain `color` (6 hex digits, RGB) and `window`, and `window` MUST contain `min`/`max` and `start`/`end` (L426–L430). The example additionally shows per-channel `label`, `active`, `coefficient`, `family`, `inverted`, and `rdefs` with `defaultT`, `defaultZ`, `model: "color"|"greyscale"` (L401–L423) — but those fields appear only in the example; the normative sentence at L426 does not require them (R03: their presence in a given file is therefore **not guaranteed**; the spec also defers detail to the OMERO WebGateway documentation, L424, which is not captured — see §8 U3). Viewer implications:
- Default timepoint/plane to show, channel names, channel colors and display windows are available **only when** `omero` is present and populated; the plan's channel controls need an explicit no-`omero` fallback policy (product decision, §6).
- `omero.channels` length vs the actual `c`-axis size: the capture only says "Array matching the c dimension size" inside the example comment (L403); there is no normative MUST, and no defined behavior on mismatch — unresolved (§8 U4) and a candidate runtime sanity warning.
- Display settings staying session-local (plan) is consistent with the spec: `omero` supplies defaults/hints; nothing in S003 obliges the viewer to persist or write metadata (and the brief forbids source modification anyway).

### SS-B4 — Label overlays: discovery, constraints and display colors
Label images are integer-valued pixel-annotation images associated with a multiscale image (S003 L432–L436). Discovery and structure:
- The `labels` group is nested inside the image group, at the same level as the resolution-level arrays (L437; tree L102–L108); its `zarr.json` MUST contain a `labels` key whose value is a JSON array of paths to the labeled multiscale images; **all** label images SHOULD be listed (L441–L442). Intermediate groups between `labels` and the label images are allowed but MUST NOT contain metadata; label image names are arbitrary (L439–L440).
- Label pixels MUST be one of the integer dtypes `[uint8, int8, uint16, int16, uint32, int32, uint64, int64]` (L438–L439; also L116–L117).
- A label image's `zarr.json` MUST implement the multiscales specification, and its `datasets` MUST have **the same number of scale levels** as the original unlabeled image (L454–L455) — a violation is malformed input, relevant to the plan's failure-feedback requirement.
Display:
- The label image metadata SHOULD contain an `image-label` object, which SHOULD contain `colors` (MUST be an array) and `version` (MUST be a string) (L456–L460). Conforming readers SHOULD display labels using the specified colors (L461) — condition: only where `image-label.colors` is actually provided.
- Each colors entry MUST contain integer `label-value`; it MAY contain `rgba`, an array of four integers 0–255 (R,G,B, alpha/opacity); extra keys are allowed (L462–L466). Example: `[0,0,128,128]` renders 50% blue at 50% opacity (L475–L514). `properties` and `source` are MAY; `source.image` defaults to `"../../"` (L467–L474).
- Because `rgba` itself is optional per entry (L463), a colors entry can legally lack a color — the fallback color policy is a product decision (§6), and the SHOULD-level color obligation cannot be met for such entries without one.

### SS-B5 — Label↔image alignment limits (counterevidence preserved — R04)
Two statements in the capture bound the assumption that labels align pixel-perfectly with images:
- Label dimensions: "Each dimension of the label should be either the same as the corresponding dimension of the image, **or 1** if that dimension of the label is irrelevant" (S003 L106–L108).
- Coordinate-system identity is stated as "usually having the same dimensions and coordinate transformations" (L432–L433) — "usually", i.e. informative, not a MUST.
Consequence: overlay code must resolve the label image through its own `multiscales`/`coordinateTransformations` (which it MUST have, L454) rather than assuming index-identical geometry; a mismatch should be surfaced, not silently accepted.

"Some of the JSON examples in this document include comments. However … comments MUST NOT be included in JSON objects" (S003 L65–L66). Consequence for the viewer: real metadata files are strict JSON; a comment-bearing `zarr.json` is malformed and should produce explanatory feedback. (Also a caution for building test fixtures from the capture's examples verbatim.) No statement is made about tolerance for other JSON irregularities (e.g. BOM, trailing commas) — out of inspected scope.

### SS-C3 — Transitional metadata: reading is the duty in question
Transitional metadata (e.g. `bioformats2raw.layout`, §2.2; `omero`, §2.5) is intended to be removed in future; "Implementations may be expected (MUST) or encouraged (SHOULD) to support **the reading** of the data, but writing will usually be optional (MAY)" (S003 L60–L64). For the read-only Slide Scout this means transitional-metadata *reading* support is exactly the part that can harden into an obligation — supporting SS-A5b and SS-B3 as first-class requirements, while no writing obligations arise.

### SS-C4 — Storage-agnostic layout transfers to local disk under an assumption (R06)
The hierarchy "is represented here as it would appear locally but could equally be stored on a web server … or in object storage" (S003 L73–L77). Mechanism M (the same node hierarchy and zarr.json metadata) transfers to Slide Scout's local-filesystem case **if assumption A holds**: the local directory behaves as a valid Zarr v3 filesystem store (same node naming and chunk key encoding). Differences preserved: HTTP range-request or object-storage concerns are out of the product boundary and out of this research.

### SS-C5 — Version-history signals relevant to compatibility
The capture's history records: 0.5.0 switched OME-Zarr to Zarr v3 (S003 L831–L833); 0.5.2 clarified that `dimension_names` MUST be included (L825–L827); 0.5.1 re-added an improved `omero` description (L828–L830); earlier versions changed chunk-dimension separators and metadata layout (e.g. 0.2.0 separator "/", L849–L851; 0.3.0 added `axes`, L846–L848; 0.4.0 added axes type/units/coordinateTransformations, L840–L842). Use: these are evidence that pre-0.5-written filesets differ structurally; S003 specifies only 0.5, so interop with older filesets is unresolved within scope (§8 U6).

## 6. Obligation triage: established obligations vs optional capabilities vs product decisions

**Established format obligations (MUST-level; a conforming 0.5 fileset guarantees / requires these):**
- Zarr v3 container; metadata in `zarr.json` under the `ome` namespace; `ome.version` consistent within a hierarchy (SS-A1, SS-A2).
- Image arrays 2–5D; axes length = array dimensionality; axes ordered time→channel/custom→space; unique axis names (SS-A3, SS-B1).
- `dimension_names` present in each multiscale array's `zarr.json` and matching `axes` (SS-A6).
- `multiscales` structure: `axes`, `datasets` (MUST), per-level `coordinateTransformations` (MUST) with exactly one scale; only translation/scale; translation after scale; vector lengths = axes count; level paths ordered largest→smallest (SS-A4, SS-B2).
- `bioformats2raw.layout` value "3"; `series` = string path list ordered as OME-XML images; consecutive numbered groups when no series/plate; plate precedence over the b2raw collection (SS-A5b).
- HCS: three MUST groups (plate/row/well); plate `columns`/`rows`/`wells`/`version`; well `images`; 0-based consistent row/column/path; well `acquisition` when multiple acquisitions (SS-A5c).
- Labels: integer dtypes; `labels` key in the labels group; label image implements multiscales with equal scale-level count; `label-value` integers; `window` min/max/start/end and 6-hex `color` per channel **if** `omero` present (SS-B3, SS-B4).
- No JSON comments in metadata objects (SS-C2).

**Optional capabilities (SHOULD/MAY-level; present only under the stated condition):**
- Units on axes (SHOULD) (SS-B1); `zyx` ordering (SHOULD) (SS-A3); multiscale `name`/`type`/`metadata` (SHOULD) (SS-A4); `OME/METADATA.ome.xml` (SHOULD) (SS-A5b); plate `field_count`/`name`, acquisition `name`/`maximumfieldcount` (SHOULD) (SS-A5c); complete `labels` listing (SHOULD); `image-label` and its `colors`/`version` (SHOULD) (SS-B4); reader SHOULD surface multi-image collections (SS-A5b).
- MAY: `translation`; multiscales-level transformations; `omero` entirely; per-entry `rgba`; `properties`/`source`; plate `acquisitions`; custom axis types; reader MAYs (use `series`, show all or offer choice, ignore extraneous groups) (SS-A5b, SS-B2, SS-B3, SS-B4, SS-B1).

**Product decisions (no spec mandate found in S003):**
- Pyramid-level selection policy for the current view (SS-A4; informative example only).
- Rendering fallback when `omero` is absent (channel colors, LUT, window, default T/Z) and when `rdefs` is absent even though `omero` exists (SS-B3, §8 U3).
- Fallback label color when a `colors` entry lacks `rgba`; opacity/blend policy beyond the example's alpha semantics (SS-B4).
- Handling of unknown/custom axis types in the UI; unit display formatting; error-message copy; plate navigation UX; which multiscale entry to open first when several exist (the L388–L397 example suggests first-as-fallback — adoptable as a decision, not an obligation).

## 8. Unresolved and rejected areas (visible — R05/R09)

- **U1 — Zarr v3 internals.** Chunk grids, codecs, sharding, storage transformers, and array `zarr.json` field semantics are delegated to the Zarr v3 specification (S003 L68–L72), which is **not part of the capture**. Within inspected region S003, no chunk/codec obligations are stated; performance and codec-support requirements therefore cannot be finalized from this source. Not researchable further under the fixed source scope.
- **U2 — Reader implementations.** S003 §4 "Implementations" contains only "See Tools." (L813–L814): the capture includes **no** implementation catalog. The brief's request to research "actual reader implementations" is accordingly **unmet within scope**; this absence is scoped to S003 and does not claim that no implementations exist elsewhere. Highest-value undeveloped lead (§ Acquisition ledger).
- **U3 — `rdefs` normative status.** `defaultT`/`defaultZ`/`model` appear only in the example block (L401–L423); the normative `omero` sentence (L426–L430) requires only `channels`/`color`/`window`. Whether conforming writers reliably provide `rdefs` is unknown; the viewer must not assume it.
- **U4 — `omero.channels` length vs `c` axis.** Only an example comment ("Array matching the c dimension size", L403); no MUST, no defined mismatch behavior. Runtime mismatch handling is a product decision pending evidence.
- **U5 — Scale semantics in the wild.** S003 L310 defines the absolute-size rule and the relative-factor fallback conditionally; writer conformance is unobservable in the capture. Until validated (§9 V3), coordinate display should compute per the spec text but tolerate either regime.
- **U6 — Pre-0.5 filesets.** Version history (L821–L866) shows structural changes across 0.1–0.4, but S003 specifies only 0.5. Whether Slide Scout opens 0.4-era filesets is an open product/compat question outside this capture.
- **U7 — Display-window semantics beyond L429–L430.** The spec defers to "OMERO WebGateway documentation" (L424), which is not captured; exact min/max vs start/end rendering interpretation is adopted from L429–L430 wording only.
