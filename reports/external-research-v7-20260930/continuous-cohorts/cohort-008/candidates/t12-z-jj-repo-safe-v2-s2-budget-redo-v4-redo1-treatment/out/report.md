## Findings (7 material)

### F1. Staleness is detected by operation-log ancestry, and recovery is a first-class command
**Locators:** `cli/src/cli_util.rs:2216-2268` (`WorkingCopyFreshness`, `check_stale_working_copy`), `cli/src/cli_util.rs:1536-1643` (`snapshot_working_copy`), `cli/src/commands/workspace/update_stale.rs:42-108,110-175`, `docs/working-copy.md:94-100`, `lib/src/working_copy.rs:98-118` (`old_operation_id`, `recover`).
**Mechanism:** Every working copy records the operation id it was last updated at (`lib/src/local_working_copy.rs:1595-1597`, checkout proto write at 1751-1757). Before commands, `snapshot_working_copy` compares trees first: if `wc_commit.tree_id() == locked_wc.old_tree_id()` the copy is `Fresh` with no op-log walk (cli_util.rs:2234-2238). Otherwise it finds the closest common ancestor in the operation DAG between the working copy's operation and the loaded repo operation: ancestor == repo op → `Updated` (reload repo at the wc's operation, cli_util.rs:2256-2259); ancestor == wc op → `WorkingCopyStale` → user error "The working copy is stale … Run `jj workspace update-stale`" (cli_util.rs:1572-1582, 2260-2263); otherwise `SiblingOperation` → internal error (2264-2265). A recorded operation that no longer exists (`OpStoreError::ObjectNotFound`) is a separate error pointing at the same recovery command (1591-1598). `jj workspace update-stale` snapshots on top of the last known working-copy operation, then merges divergent operations; it refuses with "Concurrent working copy operation. Try again." if the known tree no longer matches the lock's old tree (update_stale.rs:48-51,78-96). If the operation object itself is unreadable it builds a **recovery commit** on top of the current wc commit and calls `LockedWorkingCopy::recover()` — the reset path that does not assume the previous tree exists (update_stale.rs:110-143, 145-175; lib/src/working_copy.rs:116-118; lib/src/local_working_copy.rs:1895-1907).
**Conditions/counterevidence:** the tree-equality fast path means a workspace can be op-stale yet `Fresh` if trees coincide (cli_util.rs:2234-2238) — staleness is about materialized files matching the desired commit, not op recency per se (docs/working-copy.md:96-99). `SiblingOperation` is treated as a bug indicator, not a mergeable state, at command start; the merge of sibling ops happens at repo load elsewhere (F2).
**Integration implications:** the companion must detect the stale error and either run `jj workspace update-stale` or reproduce its snapshot-then-merge sequence; after another workspace (or an agent) moves this workspace's wc commit, every command in this workspace fails until then. A GUI that only reads status should still expect this error on its first mutational command after foreign updates.

### F2. Repository concurrency is lock-free via the operation log; the git backend is the documented exception
**Locators:** `docs/technical/concurrency.md:35-38,64-127`, `lib/src/op_heads_store.rs:31-57,63-138`, `lib/src/simple_op_heads_store.rs` (present in map, **not read** — omission).
**Mechanism:** a command loads the repo at the latest operation and never sees later changes; at completion it writes its operation with the start operation as parent; "The operation cannot fail to commit (except for disk failures and such)"; the **next** command discovers and merges divergent operations by 3-way merge of view objects (conflicted bookmarks recorded, e.g. "moved from A to B or C") (concurrency.md:80-114). Op heads are zero-content files named by operation id; completing an operation adds the new file then removes old ones; "Writing the new file is what makes the operation visible" (concurrency.md:121-127). `resolve_op_heads` re-checks heads under an optional lock (explicitly "not needed for correctness"), filters ancestors, and merges remaining heads (op_heads_store.rs:52-56,63-138). Content-addressed storage makes concurrent writes safe (concurrency.md:116-119); `lib/tests/test_bad_locking.rs:103-140+` (read, not executed) simulates two machines committing concurrently and asserts both children stay visible.
**Conditions/counterevidence:** the doc itself flags known bugs: with the git backend "repository corruption is possible because the backend is not entirely lock-free" (martinvonz/jj#2193), and cross-machine rsync/NFS use is "not currently thoroughly tested", especially colocated repos (concurrency.md:51-61).
**Integration implications:** a companion running jj-lib commands from one process still competes with CLI invocations; it must implement the divergent-head merge path on load, not assume a linear op log. Colocated repos (likely default for the companion) sit exactly in the flagged weak spot.

### F3. Working-copy mutation serializes on one advisory lock; state writes are temp-file persists, but checkout itself is not resumable
**Locators:** `lib/src/local_working_copy.rs:1607-1631` (`start_mutation`), `1693-1702` (`write_proto`), `1932-1955` (`finish`), `1861-1875` (`check_out` + TODO), `660-706` (`TreeState::save`), `lib/src/lock.rs:15-21`, `lib/src/lock/unix.rs`/`lock/fallback.rs` (**not read** — omission).
**Mechanism:** `start_mutation` takes `FileLock::lock(<state_path>/working_copy.lock)` — the map/index and lock.rs:17-19 show platform split unix/fallback — then **re-reads** checkout and tree state after the lock ("Empty so we re-read the state after taking the lock", 1615-1619), capturing `old_operation_id`/`old_tree_id` (1621-1622). `finish` saves `tree_state` via `NamedTempFile` + `persist` (660-706), then rewrites the `checkout` proto the same way if the operation (or workspace name) changed (1693-1702, 1946-1952). Both persists have unresolved Windows TODOs ("Retry if persisting fails", 1699-1700, 694-695). `check_out` carries an unimplemented safety idea: "TODO: Write a 'pending_checkout' file with the new TreeId so we can continue an interrupted update" (1861-1863; also sparse variant 1917-1918 and clear-site 1953). So an interruption between file materialization and `finish` leaves disk files diverging from the recorded tree; there is no resumption record in v0.22.0.
**Conditions/counterevidence:** the lock re-read closes the classic TOCTOU for the state files, but `create_parent_dirs` documents that materialization still has TOCTOU windows against hostile concurrent checkouts (local_working_copy.rs:427-435). `FileLock::lock` semantics (block vs fail-fast, stale-lock handling) were not verifiable without reading `lock/unix.rs` — unresolved.
**Integration implications:** the companion must treat "crashed mid-checkout" as the normal case: the recorded `tree_state` is authoritative only after `finish`; the next snapshot's mtime/size comparison (F4) is what reconciles drift. Never delete `.jj` state files to "repair" (see F7/4396).

### F4. Snapshot is a parallel, mtime-filtered rescan; a crash during it is positionally safe, but it is also where observation commands can panic
**Locators:** `lib/src/local_working_copy.rs:795-906` (`TreeState::snapshot`), `909-1009+` (`visit_directory`, rayon `into_par_iter` at 939), `cli/src/cli_util.rs:1602-1641`, issues 4396 & 4508.
**Mechanism:** snapshot intersects sparse patterns with an fsmonitor matcher (817-822), walks directories with **rayon parallel iteration** (939), compares `FileState{file_type,mtime,size}` to decide re-reads (120-127, plus `placeholder()` "re-stat on next snapshot" 129-142), writes changed blobs to the store immediately (712-722) but only marks in-memory state dirty; the new tree and dirstate reach disk in `finish` (1936-1945) — `.unwrap()` on `write_tree` at 890 and `read_dir` at 936 can panic the worker. On tree change the CLI runs a transaction `tx.commit("snapshot working copy")`, rewrites the wc commit and rebases descendants (cli_util.rs:1611-1640).
**Conditions/counterevidence:** crash mid-snapshot ⇒ orphaned content-addressed objects (harmless) and unchanged `tree_state` ⇒ repeated work, no corruption — this is why observation commands are the safe surface. But issue 4396 (jj 0.21, closed not-planned) shows `jj st` panicking inside `TreeState::get_updated_tree_value` → `parse_conflict` ("must have one more adds than removes", lib/src/merge.rs:163 — region **not read**: missing link) on malformed conflict markers; and issue 4508 (open) reports many-core machines burning CPU because snapshot parallelism scales with cores.
**Integration implications:** background observation should snapshot through the library (the `SnapshotOptions` doc notes TreeState "may be long-lived … in a long-lived process", lib/src/working_copy.rs:192-194) and must survive worker panics; snapshot cost is the dominant recurring cost of observation (see F5).

### F5. Snapshot-before-every-command is the default and is slow; the documented escape hatches trade safety
**Locators:** `inputs/issues/4545.json` (body lines 70), `docs/working-copy.md:10-27`, `cli/src/cli_util.rs:1550-1555` (auto-tracking matcher, `max_new_file_size`), `lib/src/working_copy.rs:186-224` (`SnapshotOptions`, `max-new-file-size` error 161-171), `lib/src/local_working_copy.rs:761-790` (watchman query/trigger).
**Mechanism:** most commands snapshot first ("Most `jj` commands you run will commit the working-copy changes if they have changed", docs/working-copy.md:10-13); new files are auto-tracked unless ignored/`snapshot.auto-track` (docs/working-copy.md:15-27, 69-75). Issue 4545 (open) measures `jj log` 209 ms vs 58 ms with `--ignore-working-copy` on Chromium, and records why the naive skip is unsafe: `--ignore-working-copy` on `jj new` "would immediately cause a stale workspace: #4028" and it does not register the Watchman trigger (fsmonitor.rs:L210 — region **not read**: missing link).
**Conditions/counterevidence:** `--ignore-working-copy` is fine for pure readers; the hazard is mutational commands under a background-snapshot regime. Watchman/fsmonitor moves the cost out-of-band but adds an external service dependency (4545 body; local_working_copy.rs:761-790).
**Integration implications:** the companion should not shell out to `--ignore-working-copy` everywhere; either hold a long-lived library session with Watchman-style change feeds, or accept the snapshot cost and stream its progress (F6). Untracked-file policy (`max-new-file-size`, `auto-track`) must be configured deliberately or agent build artifacts get committed.

### F6. Interrupted progress delivery: the 4239 failure history is fixed in-pin by ordering; signal cleanup exists for SIGINT/SIGTERM only, and not on Windows
**Locators:** `inputs/issues/4239.json` (body line 112), public comments fetch (out/acquisition.json), `cli/src/cli_util.rs:1757-1771`, `cli/src/progress.rs:19-93,112-113,166-214`, `cli/src/cleanup_guard.rs:13-46,95-114,117-126`.
**Mechanism (failure history):** `jj rebase … | head` died of broken pipe between repo commit and working-copy update, leaving the next command stale (4239 body). Maintainer analysis: "Working-copy updates and git exports are two major sources of inconsistency"; mitigation is to reorder `update_working_copy()` after which `report_repo_changes()` runs (comments by yuja; PR #4517 by essiene; issue closed 2024-09-22). **Verified in-pin:** `finish_transaction` updates the working copy before reporting changes with the comment "so that potential errors while reporting changes (broken pipe, etc) don't leave the working copy in a stale state" (cli_util.rs:1759-1771) — the fix is present in v0.22.0.
**Mechanism (progress):** snapshot progress is a callback throttled to 30 Hz after a 250 ms delay (progress.rs:112-113,176,183-214); git fetch/push progress draws a bar and registers a `CleanupGuard` to restore the cursor (progress.rs:56-63). `CleanupGuard` callbacks run on drop **or** SIGINT/SIGTERM via a self-pipe thread; a second signal is instantly fatal (cleanup_guard.rs:102-111); the whole handler is thread-drain-then-re-raise (95-100). The non-unix `platform::init` is a no-op (117-126): **Windows gets no signal-time cleanup**, and no signal set covers SIGKILL/SIGSEGV/SIGHUP or broken pipes.
**Integration implications:** a GUI must not inherit terminal progress assumptions; use the `SnapshotProgress`/git `Progress` callbacks in-process. Recovery must not depend on cleanup guards running — the op-log/WC-state design (F1-F4) is the real safety net; guards are cosmetic.

### F7. Multi-workspace operation: per-workspace wc commits, silent skip when a workspace vanishes, rename supported, colocated workspaces are a known gap
**Locators:** `lib/src/workspace.rs:629-line file` (`Workspace`, workspace id; **only header region read, lines 1-60** — omission noted), `docs/working-copy.md:78-100`, `cli/src/cli_util.rs:1545-1549,1714-1731,1765-1768`, `lib/src/working_copy.rs:49-50,110-111`, `lib/src/local_working_copy.rs:1877-1879`, `inputs/issues/4436.json`, `inputs/issues/4342.json` (title only, from issues-index).
**Mechanism:** each workspace has its own wc commit recorded in the shared view (`wc_commit_ids` keyed by workspace id; finish_transaction iterates all workspaces and, if a workspace's wc commit became immutable (e.g. abandoned/hidden), checks out a fresh commit on top with a warning, cli_util.rs:1714-1731). A workspace deleted from the repo makes snapshot a silent no-op (1545-1549, 1765-1768). `rename_workspace` exists on the locked WC (working_copy.rs:110-111; local_working_copy.rs:1877-1879, applied in `finish` 1946-1949) — consistent with issue 4342 (FR workspace rename, closed 2024-09-17, pre-pin). Staleness across workspaces is the documented normal (docs/working-copy.md:94-100, F1). Issue 4436 (closed 2026-09-17, after capture-relevant window; 8 comments) records that non-main workspaces in a colocated repo are invisible to git tools (no `.git`), breaking e.g. Nix — open design gap through v0.22.0's era.
**Conditions/counterevidence:** `jj workspace forget` forgets repo-side state; disk files may be deleted before or after (docs/working-copy.md:90-92) — a window where a workspace exists on disk but not in the view, exactly when the silent-skip paths hit.
**Integration implications:** the companion's "several workspaces" model maps directly onto `wc_commit_ids`; it must render other-workspace staleness rather than auto-fixing it, and must not assume colocated auxiliary workspaces are git-visible.

## Transfer limits
Everything above is evidence about jj v0.22.0's CLI/library implementation. It does **not** prove a GUI companion is safe: the CLI's safety rests on process-exit ordering, advisory locks, and a user reading hints; a long-lived GUI process changes lock holding times, snapshot triggers, and failure delivery (no terminal, no signals). Each safeguard here must be re-validated in the companion's own process model before being promised to users.
