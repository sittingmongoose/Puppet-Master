### F1. A command could die after committing the repo operation but before updating the working copy, leaving a stale working copy — fixed in v0.22.0 by reordering update-before-report (#4239) — CLOSED/FIXED AT PIN

**Failure report → fix trace (complete chain):**
1. Report: `inputs/issues/4239.json` lines 11 (title), 112 (body): `jj rebase -s third -d first 2>&1 | head -n 3` then the next command fails with `Error: The working copy is stale (not updated since operation 6c9667ecda1f).` / `Hint: Run 'jj workspace update-stale'`. Reporter hypothesis: the first rebase "aborted in the middle of an operation because of a broken pipe". Closed 2024-09-22, state_reason `completed`.
2. Mechanism (pre-fix), confirmed by maintainer yuja comment read from `https://github.com/jj-vcs/jj/issues/4239/timeline` (comment 2275287126): "this particular scenario can be mitigated by reordering `update_working_copy()` and `report_repo_changes()`" (link given there to pre-fix cli_util.rs `b3ede644…` lines 1424–1430 — that parent blob is not in this corpus; **unconfirmed locally**). The reporting path writes to the terminal; when the pipe closes (`| head`), the write fails, the error propagates, and the remaining transaction tail — including the working-copy update — never runs, while the repo operation is already committed (`tx.commit` happened before both).
3. Fix commit on main: `76f40e5990db2981e7c86986c8af98f22edaccc9` "cli: reorder updating and reporting for consistency." `Fixes: #4239` (PR #4517, merged 2024-09-22T14:02:21Z). 4. Pinned implementation (v0.22.0): `inputs/repository/cli/src/cli_util.rs` (3435 lines, sha256 `689a8b64a3d0ae0b6ab74996d95813a1b2387a58d2985e25a55ddf30b0cc1c04` = PIN.json entry): `finish_transaction` lines 1699–1789; commit of the repo operation at line 1757 (`self.user_repo = ReadonlyUserRepo::new(tx.commit(description));`), then comment lines 1759–1761 ("Update working copy before reporting repo changes, so that potential errors while reporting changes (broken pipe, etc) don't leave the working copy in a stale state."), `update_working_copy` call at lines 1762–1769, `report_repo_changes` at line 1771. Supporting: `update_working_copy` method at line 1645; `report_repo_changes` at line 1805 (symbol pins from the host map, see `out/map-usage.json`).
5. Test source (not executed): `cli/tests/test_repo_change_report.rs` post-fix expectations are encoded in the fix patch (lines 98–180); the pinned test file `inputs/repository/cli/tests/test_repo_change_report.rs` (PIN sha `6614e2b5…`) contains the same reordered snapshots — presence verified via PIN; content spot-checked only through the patch.

**Conditions:** error paths that originate in *writing command output* (UI/status streams) between `tx.commit` and the working-copy update, under an external consumer that closes the pipe; repeatable per the reporter, not a concurrency race. Post-fix, an EPIPE during reporting can still abort the process after the operation is committed — the working copy is updated first, so the leftover state is only "reporting incomplete", not "stale working copy" (i.e. the fix narrows the damage; it does not make output errors transactional).
**Counterevidence/limits:** maintainer's first reaction in the timeline was "I think this is expected after failed working-copy updates" — i.e. stale-after-failed-update was considered by-design; the fix targets the *avoidable* ordering. The `demos` chain shows the workaround culture: `inputs/commit-patches/d3b0f1b97064cf0a76ce603dcf6e059fbbcf5b99.patch` lines 7–11 ("demos: redact one of the conflict outputs… I ran into https://github.com/martinvonz/jj/issues/4239") — the reporter could not shorten demo output except by discarding it entirely (patch lines 16–36).
**Integration implications (companion):** never kill or close the output stream of a running jj command mid-transaction; treat "output delivered" and "command committed" as independent events. A GUI progress panel that detaches from the child process (or a PTY that goes away) reproduces the EPIPE class. Stream progress out-of-band, or buffer/pipe-to-nowhere, and only then surface results; also expect the pre-0.22 message ordering in any pinned older bundled binary.

## Cross-cutting answers to the two question families

**QF1 (observing/changing state with concurrent edits/workspaces):** pinned jj snapshots on entry for writable commands (F3), detects cross-workspace staleness via the operation DAG (F4), guards concurrent working-copy mutations with a tree-id check ("Concurrent working copy operation. Try again.", `cli_util.rs:1052-1054`), and keeps per-workspace wc commits in the view (multi-workspace listing/rename tests in F2). Known soft spots at pin: duplicated working-copy commits when colocated Git HEAD moves concurrently (`cli_util.rs:934-942` TODO), snapshot cost/scalability (#4508, #4545), ignored-file lifecycles (#4559), and snapshot panics on corrupt conflict state (F6).

**QF2 (completion, interrupted delivery, recovery):** a jj command's *completion* is transaction commit + working-copy update + reporting (in that order at pin, `cli_util.rs:1757-1771`, F1); output failures after commit no longer strand the working copy (fixed at pin) but still strand reporting. Interruption *before* commit leaves op-heads that converge (per `docs/operation-log.md` design; docs not deeply read — see unvisited areas). Recovery tiers: `update-stale` for stale/sibling/missing-operation states (F4), `op undo/restore` for operation-level mistakes (not traced to issues), and nothing for op-store byte corruption (F4/#4423). Progress delivery: snapshot progress exists (`crate::progress::snapshot_progress`, `cli_util.rs:1602`; `cli/src/progress.rs` present at pin, not read in depth) — a companion should stream it out-of-band.

**Simpler design choices for the companion (derived, not from upstream):** (1) one serialized writer per workspace, all other views read-only with explicit operation pins (`--at-op`); (2) treat "stream closed" as fatal to the session, never to the child transaction; (3) key UI state on workspace ids + operation ids, re-validating after any command; (4) pre-flight ignore/size checks before switches (F5); (5) crash-capture every jj invocation (F6) with byte-preserving hand-off for corruption (F4 tier 3).
