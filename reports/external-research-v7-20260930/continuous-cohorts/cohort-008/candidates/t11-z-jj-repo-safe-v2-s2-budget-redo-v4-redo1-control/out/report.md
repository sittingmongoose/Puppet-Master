## Findings

### Finding 1 (family 1) — In jj, observing the working copy is itself a mutation: every ordinary command first snapshots the working copy and can create commits and new operations

- **Claim.** A companion that wants to "just look" at status/history via ordinary jj semantics will also *write*: before doing anything, most commands snapshot the working copy, may rewrite the working-copy commit, rebase descendants, and commit a new operation ("snapshot working copy").
- **Mechanism (v0.22.0).** `cli/src/cli_util.rs:897-916` — `WorkspaceCommandHelper::maybe_snapshot()` runs on the snapshot path and then imports Git refs for colocated repos. It calls `snapshot_working_copy()` (`cli/src/cli_util.rs:1536-1643`): it locks the working copy (`start_working_copy_mutation`, line 1557), checks freshness, snapshots via `LockedWorkingCopy::snapshot` with `SnapshotOptions` (`cli/src/cli_util.rs:1602-1609`; options defined in `lib/src/working_copy.rs:186-227`), and if the tree changed it rewrites the working-copy commit, rebases descendants, exports refs for colocated repos, and commits a transaction literally described as `"snapshot working copy"` (`cli/src/cli_util.rs:1611-1639`). The docs state the same behavior at the user level: "Most `jj` commands you run will commit the working-copy changes if they have changed" (`docs/working-copy.md:10-13`), and added files are implicitly tracked (`docs/working-copy.md:15-18`, controlled by `snapshot.auto-track`, 20-27).
- **What the snapshot trusts.** The default `LocalWorkingCopy` snapshot is mtime/size-based: a tracked file is "clean" only when its recorded file state equals the fresh stat **and** its mtime is older than the tree-state file's own mtime (`lib/src/local_working_copy.rs:1142-1151`, with `update_own_mtime` at 619-625 and file-state extraction at 468-509). Everything else is re-hashed and written to the store (`lib/src/local_working_copy.rs:1153-1185`). The traversal skips `.jj` and `.git` (`lib/src/local_working_copy.rs:956-958`), skips untracked ignored files (1041-1049), errors on new files over `snapshot.max-new-file-size` (1056-1064), and walks directories in parallel (`into_par_iter`, line 939). Snapshot failure modes are enumerated in `SnapshotError` (`lib/src/working_copy.rs:142-184`).
- **Cost evidence (issues).** #4545 "FR: Option to skip snapshotting-before-commands with automatic snapshots" — open at capture (`inputs/issues/4545.json:11,46`); body reports `jj log` ≈209 ms vs ≈58 ms with `--ignore-working-copy` on a colocated Chromium checkout with Watchman, and notes that naively adding `--ignore-working-copy` to mutating commands causes stale workspaces (it cites upstream #4028) and does not register the Watchman trigger (`inputs/issues/4545.json:70`). #4508 "On a machine with many cores, snapshotting large repos is very CPU-intensive" — open, labeled bug (`inputs/issues/4508.json:11,33-56,57`); body: on ~150,000 files / 24-core macOS, `jj st` took 2.28 s wall with 32.26 s sys time, vs 1.13 s / 0.49 s sys with `RAYON_NUM_THREADS=4` (`inputs/issues/4508.json:81`) — consistent with the parallel traversal at `lib/src/local_working_copy.rs:939`.
- **Conditions.** Snapshotting is skipped entirely when the command is run with `--ignore-working-copy` or `--at-op`: `may_update_working_copy = loaded_at_head && !ignore_working_copy` (`cli/src/cli_util.rs:853-854`), and mutating commands then refuse with "This command must be able to update the working copy." (`cli/src/cli_util.rs:881-895`). Docs confirm snapshotting is skipped under `--at-op` (`docs/operation-log.md:54-58`).
- **Counterevidence / limits.** Snapshotting is not unconditionally dirty: if nothing changed the tree is unchanged and only the recorded operation id advances (`cli/src/cli_util.rs:2474-2478`, free function `update_working_copy` at 2455-2481; `TreeState::snapshot` returns `is_dirty`, `lib/src/local_working_copy.rs:795-906`). A GUI that only ever runs read-only revset queries through the library (not the CLI command pipeline) would not get this exact behavior — the transfer limit is that `maybe_snapshot` is a *CLI command pipeline* behavior, not a property of the storage layer.
- **Integration implications.** (a) A background status panel must not poll by spawning ordinary mutating commands at high frequency: each poll can rewrite commits/operations and, on large repos, cost hundreds of ms to seconds (#4545, #4508). (b) Prefer read-only invocation modes (`--ignore-working-copy`/`--at-op`) for pure observation, and trigger an explicit snapshot deliberately (or after detecting quiescence). (c) If the companion embeds `jj-lib`, note that snapshot options (`base_ignores`, `fsmonitor_settings`, `progress`, `start_tracking_matcher`, `max_new_file_size`) are caller-supplied (`lib/src/working_copy.rs:186-227`), so a companion can control cost, but then owns the policy the CLI normally owns.

### Finding 2 (family 1) — The repo level is deliberately lock-free; concurrent commands are both allowed and expected, and divergence is merged by the *next* reader

- **Claim.** jj v0.22.0 does not serialize concurrent repo operations with a global lock; it records every operation in an operation log and merges divergent heads lazily. A companion running alongside a user or an agent must treat "another jj process did something concurrently" as the normal case.
- **Mechanism (v0.22.0).** Design doc: "Jujutsu takes a different approach by accepting that concurrent changes can always happen" (`docs/technical/concurrency.md:35-38`); each command loads the repo at the latest operation, cannot fail to commit its operation (barring disk failure), and it is "left for the next command to notice if there were divergent operations" (`docs/technical/concurrency.md:80-89`). Operation-log storage: op/view objects are content-addressed and "safe to write without locking"; current heads are recorded as empty files named by op id — write new, then remove old (`docs/technical/concurrency.md:116-127`). Implementation: `lib/src/op_heads_store.rs:63-138` — `resolve_op_heads()` re-reads heads under an optional lock; the lock is explicitly "not needed for correctness", only to prevent duplicated merge work (`lib/src/op_heads_store.rs:52-56, 87-89`), and merges all divergent views (via the caller-supplied resolver) into one new operation (`lib/src/op_heads_store.rs:103-137`). Repo loading merges multiple op heads with 3-way view merges, recording conflicts in the view (`docs/technical/concurrency.md:99-114`). `@`-style op resolution refuses to pick among multiple heads (`lib/src/op_walk.rs:84-101`, `MultipleOperations` at 90-97).
- **Failure histories.** #4465 "Panic in `jj op show` on 'reconcile divergent operations'" — reported on jj 0.21.0 (`inputs/issues/4465.json:112`): concurrent `jj abandon` and `jj edit` of the same change from two workspaces produced divergent operations, and `jj op show` panicked at `lib/src/default_index/revset_engine.rs:972` (`Option::unwrap()` on `None`). Status: closed 2025-06-12 (`inputs/issues/4465.json:75`), i.e. **after** v0.22.0 — treat as unresolved-at-pin unless separately verified.
- **Known gaps the docs admit.** With the Git backend, "repository corruption is possible because the backend is not entirely lock-free" (upstream issue #2193 linked) (`docs/technical/concurrency.md:51-54`); rsync/NFS/Dropbox-style concurrent use is "not currently thoroughly tested", especially colocated repos, and "might conceivably lose some bookmark pointers" though not commits (`docs/technical/concurrency.md:56-61`). The local test file simulates exactly this directory-merge concurrency in source (`lib/tests/test_bad_locking.rs:28-101` and `#[test_case]` cases from line 103) — cited as source text only, not executed.
- **Counterevidence.** Lock-free does not mean lockless everywhere: `FileLock` exists and is used for finer-grained resources (working-copy state, index, op-heads de-duplication) — `lib/src/lock.rs:15-21` with in-source concurrency tests at 32-65; and the working-copy layer *does* detect conflicting checkouts (Finding 3).
- **Integration implications.** (a) The companion must design for merge-on-next-read semantics: its displays should tolerate conflicted bookmarks/views and say so instead of assuming a single linear op history. (b) Long-lived in-process state goes stale by design — the doc warns that after loading, "the running command will not see any changes made by other processes thereafter" (`docs/technical/concurrency.md:80-83`); a companion that caches a loaded repo must re-load (as `snapshot_working_copy` does with `reload_at`, `cli/src/cli_util.rs:1562-1563`). (c) The Git-backend corruption caveat and untested distributed-FS story are transfer limits: the CLI's safety here is *documented as incomplete*, so the companion should not promise more than jj does.

### Finding 3 (family 1) — The working-copy layer is where consistency is actually enforced: state file + locks + tree/operation comparison, with explicit "concurrent checkout" detection

- **Claim.** While the repo level is lock-free, each workspace's working-copy state is guarded by a real file lock plus before/after comparisons; a companion performing change/rebase actions must go through these checks or it can clobber a concurrent checkout.
- **Mechanism (v0.22.0).** Working-copy state lives in `<workspace>/.jj/working_copy/` (state path created at init, `lib/src/workspace.rs:120-149`; type file at 146-147), and multi-workspace repos point `.jj/repo` (a file) at the shared repo directory (`lib/src/workspace.rs:549-563`; written at 345-377). `WorkingCopy::start_mutation()` "Locks the working copy and returns an instance with methods for updating the working copy files and state" (`lib/src/working_copy.rs:64-66`); `finish(operation_id)` writes the updated state (`lib/src/working_copy.rs:136-139`). `Workspace::check_out` compares the caller's expected tree with the tree recorded at lock time and returns `CheckoutError::ConcurrentCheckout` ("Another process checked out a commit while the current process was running") on mismatch (`lib/src/workspace.rs:420-449`, error text at `lib/src/working_copy.rs:256-259`). The CLI adds its own guard: `start_working_copy_mutation()` fails with `user_error("Concurrent working copy operation. Try again.")` if the repo's working-copy commit tree differs from the locked working copy's tree (`cli/src/cli_util.rs:1048-1056`). Tree-state saves are atomic-by-rename: write `NamedTempFile` in the state dir, update own mtime, `persist()` onto `tree_state` (`lib/src/local_working_copy.rs:683-704`).
- **Colocated-repo caveat (counterevidence to "safe by construction").** `import_git_head` contains an explicit TODO listing three ways duplicated working-copy commits can still be created in colocated repos (HEAD moved observed by multiple jj processes; HEAD exported but operation not committed; HEAD exported but new wc commit not checked out), noting that checking the working-copy operation id after acquiring the lock "isn't enough" (`cli/src/cli_util.rs:918-973`, comment block 934-942).
- **Integration implications.** (a) The companion's "change/rebase" actions should reuse `start_working_copy_mutation`-equivalent flows (lock → verify → mutate → finish) rather than shelling out concurrently with other jj processes' work. (b) "Try again" is an expected, recoverable outcome, not a crash: the UI should retry or surface it as such. (c) Colocated repos remain the riskiest mode even at the pin (also Finding 6); the companion should treat git-side HEAD moves as an extra invalidation trigger.

### Finding 4 (family 2) — Staleness is a first-class, user-visible state with a built-in recovery loop; a broken pipe during a mutating command used to leave exactly this state, and v0.22.0 contains the reordering mitigation

- **Claim.** "Stale working copy" (workspace A's files don't match its `@` after someone updated A's working-copy commit from elsewhere) is detected on the next command, reported with a hint, and repaired by `jj workspace update-stale`. The interrupted-progress failure history #4239 lands exactly here, and the v0.22.0 source contains the fix's mechanism.
- **Detection (v0.22.0).** `WorkingCopyFreshness` has four states: `Fresh`, `Updated(..)` (working copy moved ahead; repo must be reloaded), `WorkingCopyStale`, `SiblingOperation` (`cli/src/cli_util.rs:2214-2226`). `check_stale_working_copy()` compares the locked working copy's tree with the repo's working-copy commit tree, then computes the closest common ancestor of the working copy's operation and the repo's operation in the op DAG to classify the relationship (`cli/src/cli_util.rs:2228-2268`). `snapshot_working_copy()` turns these into behavior: `Fresh` proceeds; `Updated` reloads the repo at the working copy's operation (`cli/src/cli_util.rs:1561-1570`); `WorkingCopyStale` errors `"The working copy is stale (not updated since operation <op>)." "Run `jj workspace update-stale` to update it."` (`cli/src/cli_util.rs:1572-1582`); `SiblingOperation` is an internal error (1583-1590); a missing working-copy operation object yields `"Could not read working copy's operation."` with the update-stale hint (1591-1598). The docs define stale cross-workspace staleness and point to the same command (`docs/working-copy.md:94-100`).
- **Recovery command (v0.22.0).** `cmd_workspace_update_stale` snapshots **on top of the last known working-copy operation**, then merges the divergent operations (`cli/src/commands/workspace/update_stale.rs:48-54`, comment at 48-51); it refuses with `user_error("Concurrent working copy operation. Try again.")` when the tree changed underneath (81-83) and otherwise checks out the desired commit and finishes at the merged repo's op id (84-104). When the working copy's recorded operation is unreadable (`OpStoreError::ObjectNotFound`), `for_stale_working_copy` prints the failure and calls `create_and_check_out_recovery_commit`, which creates a child "recovery commit" and uses `LockedWorkingCopy::recover()` — the variant that does **not** assume the previous tree exists (`cli/src/commands/workspace/update_stale.rs:110-175`, esp. 163-170; `lib/src/working_copy.rs:113-118`). A real-world 2025-04 recovery transcript on #4423 shows this exact path producing `RECOVERY COMMIT FROM 'jj workspace update-stale'` after corruption cleanup (public comment by `dhardy`, 2025-04-07, on `https://api.github.com/repos/jj-vcs/jj/issues/4423/comments`; fetched during this investigation).
- **Failure history + fix.** #4239 "Broken pipe when running `jj rebase 2>&1 | head` causes stale working copy" — created 2024-08-08, closed 2024-09-22, state_reason completed (`inputs/issues/4239.json:11,46,73-75,112`): the first `jj rebase` printed its report, the pipe closed, and the *next* command failed with "The working copy is stale (not updated since operation 6c9667ecda1f)". Maintainer analysis in the official comment thread (fetched): "this particular scenario can be mitigated by reordering `update_working_copy()` and `report_repo_changes()`" (yuja, 2024-08-08), and the fix PR #4517 "just moves the call to `self.report_repo_changes(...)` after the … `may_update_working_copy` block" (essiene, 2024-09-21; yuja approved the new output order same day). The pinned v0.22.0 source contains the reordered code with the rationale in a comment: "Update working copy before reporting repo changes, so that potential errors while reporting changes (broken pipe, etc) don't leave the working copy in a stale state." (`cli/src/cli_util.rs:1699-1801`, comment+ordering at 1757-1769). Qualification: v0.22.0 postdates the issue's 2024-09-22 close and contains the reordering, so the specific #4239 repro is expected to be fixed at the pin — this is code+timeline evidence, not a runtime test (none was executed).
- **Conditions / residual risk.** The mitigation covers the `finish_transaction` reporting path of transaction-based commands. Interrupts are not globally benign: a process killed between an operation commit and the working-copy state `finish()` (e.g. `snapshot_working_copy` commits at `cli/src/cli_util.rs:1639` then finishes at 1641) can still leave the working-copy state pointing at an older operation — which is precisely the state `check_stale_working_copy` classifies and `update-stale` repairs. SIGKILL and power loss are outside any handler (Finding 7).
- **Integration implications.** (a) The companion should surface the four freshness states (especially `SiblingOperation`, which is an internal error for the CLI but an expectable situation for a long-running companion). (b) Its own output streaming must not be allowed to abort its repo writes: jj learned this the hard way (#4239); a GUI streaming command output into a panel should decouple display I/O failures from repository work entirely. (c) Offer `update-stale`-equivalent repair as a one-click recovery, and treat "Concurrent … Try again." as retryable.

### Finding 5 (family 2) — Hard crash recovery is real but manual and version-sensitive: power loss can strand empty files that make the repo unopenable, and v0.22.0 has no built-in fsck

- **Claim.** The operation-log scheme tolerates interrupted *operations* (extra heads are merged), but a hard power loss can also leave **empty/zero-length files** (op-heads, op-store objects, index segments, git objects) that make the repo fail to load with confusing internal errors; recovery in the #4423 thread was manual filesystem surgery, and the issue was still open at capture.
- **Failure history.** #4423 "hosed jj repo after hard-reboot." — created 2024-09-08, **open** at capture (updated 2026-08-25) (`inputs/issues/4423.json:11,34,39-41`); body: after a power cycle without sync, `jj 0.21 log` fails with "Internal error: Failed to load the repo / Error when reading object of type view / Is a directory (os error 21)" from a corrupted filename in `.jj/repo/op_store/views/` (`inputs/issues/4423.json:58`). The official comment thread (fetched) documents: the maintainer's manual rollback recipe over `.jj/repo/op_heads/heads/` filenames; the user's attempts producing "Concurrent modification detected, resolving automatically." followed by panics on the corrupt objects (`lib/src/operation.rs:97`, `lib/src/default_index_store.rs:245` per the tracebacks); **empty files found under `.git/objects/`** ("some of the git data wasn't written with fsync()"), later also empty `refs/jj/keep/*` and empty `.jj/repo/store/extra/*` segment files in follow-up reports (2024-09 and 2025-04/05 comments); and a successful deep-recovery route via the git store plus a final `jj workspace update-stale` recovery commit.
- **Design context (v0.22.0).** Op-head visibility is intentionally two-step — "Writing the new file is what makes the operation visible (if the old file didn't get properly deleted, then future readers will take care of that)" (`docs/technical/concurrency.md:121-127`) — which covers *ordering* crashes but not torn/zero-length writes; `resolve_op_heads` even anticipates transiently empty head sets during concurrent readdir-style updates (`lib/src/op_heads_store.rs:71-73`) but treats a persistently empty set as `OpHeadResolutionError::NoHeads` (`lib/src/op_heads_store.rs:31-35, 93-95`). At the CLI boundary, broken store reads surface as "The repository appears broken or inaccessible" internal errors (`cli/src/cli_util.rs:2162-2174`, `map_workspace_load_error`), i.e. diagnosed, not repaired. The working-copy side has one cheap user remedy visible in the thread: deleting a corrupted `.jj/working_copy/tree_state` (2025-05-27 comment) — safe because the tree state is rebuilt from disk on next snapshot (state init path `lib/src/local_working_copy.rs:595-617`), though that discards recorded file-state tracking (a full re-hash on next snapshot).
- **Counterevidence / limits.** The original report involved a repo created under jj 0.7 and inspected with 0.15/0.21; nothing in the thread shows v0.22.0 introduced or fixed the empty-file durability gap, and the issue remains open at capture — so this is recorded as an *unresolved at pin* risk, not a v0.22.0 regression. Transfer limit: these are CLI/filesystem histories on Linux ext4-class systems; a companion on other filesystems or sync modes inherits different durability behavior.
- **Integration implications.** (a) "Recover after interruption" for the companion cannot mean only `update-stale`: it needs a decision tree for load failures (working-copy-state reset vs op-head rollback vs "copy your work out via the git store"), and should refuse to auto-edit `.jj` internals — every successful recovery in the thread was expert-guided. (b) At minimum, map the observed error strings ("Failed to load the repo", "Invalid hash length", "failed to fill whole buffer", "Concurrent modification detected…") to human explanations and to a "back up `.jj` now" action. (c) The companion can offer the low-risk subset automatically: `jj workspace update-stale` (designed-for-purpose, exercised in the thread) and `--ignore-working-copy` reads for triage (`jj --ignore-working-copy op log` is the thread's first safe step, per martinvonz's 2024-09-08 comment).

### Finding 6 (family 1) — Multi-workspace mechanics are simple and mostly safe, but colocated secondary workspaces were second-class at v0.22.0 (no `.git`), and `workspace forget` doesn't touch disk

- **Claim.** Workspaces are one repo plus N working copies linked by a `.jj/repo` file; per-workspace `@` lives in the shared view. Two integration-relevant gaps at the pin: secondary workspaces in colocated repos are invisible to git tooling, and forgetting a workspace leaves its files on disk.
- **Mechanism (v0.22.0).** "You can have multiple working copies backed by a single repo… The working copy and the `.jj/` directory together is called a 'workspace'" (`docs/working-copy.md:78-88`); each workspace has its own working-copy commit recorded in the view (`docs/technical/concurrency.md:72-74` — the view contains "the working-copy commit in each workspace"; also `docs/operation-log.md:9-11`). Loading resolves `.jj/repo` either as directory or as a file containing the relative repo path (`lib/src/workspace.rs:549-563`), and adding a workspace writes that file (`lib/src/workspace.rs:345-377`). Cross-workspace modification creates staleness handled by Finding 4. `jj workspace rename` exists at the pin (`cli/src/commands/workspace/rename.rs:23-78`), matching #4342 "FR: Allow renaming of existing workspaces" (closed 2024-09-17, before the pin; `inputs/issues/4342.json:11,57,62-64`). `jj workspace forget` "make[s] the repo forget about it. The files can be deleted from disk separately (either before or after)" (`docs/working-copy.md:90-92`). In `finish_transaction`, a working-copy commit that became immutable gets a new commit created on top *per workspace*, with a warning naming the workspace (`cli/src/cli_util.rs:1714-1732`).
- **Failure/limit history.** #4436 "FR: workspaces should also be collocated in --colocate mode" — created 2024-09-11, **closed only 2026-09-17** (`inputs/issues/4436.json:11,57,62-64`): a workspace added in a colocated repo "is not recognisable as a Git repository by any git tools. It does not have a .git directory", with real damage reported (Nix silently dropping to non-git mode and copying build artifacts). Body proposes git-worktree-style integration; the requester notes libgit2/gix APIs were insufficient at the time (`inputs/issues/4436.json:81`). Status at v0.22.0 (tag date 2024-10-02): open — no fix existed at the pin.
- **Counterevidence.** Colocation of the *primary* workspace is fully supported (`lib/src/workspace.rs:209-235`, `init_colocated_git`), and colocated flows get extra sync logic (`maybe_snapshot` import ordering, `cli/src/cli_util.rs:897-916`). The gap is specific to *secondary* workspaces.
- **Integration implications.** (a) The companion can rely on workspace identity/`@`-per-workspace semantics for its UI model, including rename (already in-pin) — but must handle a forgotten workspace whose directory still exists (files present, repo no longer tracks it). (b) If the product promises "works with your git tools" in colocated projects, secondary workspaces break that promise at this pin; either create workspaces only as manually-managed git worktrees alongside, or label the limitation. (c) Agents working "elsewhere" in another workspace are exactly the cross-workspace writers Findings 3/4 guard against: the companion should expect `WorkingCopyStale` for any workspace it doesn't itself update.

### Finding 7 (family 2) — Interruption handling exists but is narrow: SIGINT/SIGTERM drop-guards only, second signal is instantly fatal, and non-unix builds have no signal cleanup at all

- **Claim.** jj's interruption story at v0.22.0 is "run cleanup callbacks on SIGINT/SIGTERM, then die by the signal". There is no SIGPIPE-style special handling (the #4239 class was fixed by *reordering writes and output*, not by handling EPIPE), no Windows signal path, and a second signal kills immediately.
- **Mechanism (v0.22.0).** `cli/src/cleanup_guard.rs` — `CleanupGuard::new(f)` registers `f` in a global table; the guard runs `f` on drop **or** on SIGINT/SIGTERM (`cli/src/cleanup_guard.rs:8-46`). Unix implementation: a signal handler writes to a socketpair; a background thread drains all live guards, then restores the default disposition and re-raises the signal (`cli/src/cleanup_guard.rs:48-115`; guard drain at 96-100). "Treat the second signal as instantly fatal" (`cli/src/cleanup_guard.rs:102-108`). Non-unix `platform::init` is a no-op, so guards only run on normal drop there (`cli/src/cleanup_guard.rs:117-126`). Progress during snapshot is a callback (`SnapshotProgress`, `lib/src/working_copy.rs:226-227`) wired to the UI in `snapshot_working_copy` (`cli/src/cli_util.rs:1602-1610`) — in-process function callbacks, not a persisted protocol. A companion embedding the library can stream it; one shelling out gets whatever the CLI prints, with the #4239 lesson that output failures must not gate repository work.
- **Conditions.** SIGKILL/power loss bypass all of this (Finding 5 covers the residue). EPIPE on status output after the v0.22.0 ordering still ends the command with an error after the working copy is updated — the update itself is preserved.
- **Counterevidence.** The transaction design already bounds damage: maintainer comment on #4239 (fetched, 2024-08-10): "many of the interrupted mutation problems are addressed by transaction in jj. Working-copy updates and git exports are two major sources of inconsistency" — matching the code where those two steps are sequenced around output (`cli/src/cli_util.rs:1748-1769`).
- **Integration implications.** (a) The companion should prefer library-embedding or `--ignore-working-copy` reads for its streaming panel, and keep any mutating action atomic from the user's perspective ("done / not done / stale-repair available"), never "half-shown". (b) If it shells out, it must not kill jj with a second signal expecting cleanup, and must not assume any cleanup on Windows or on SIGKILL. (c) Progress UX can be honest about the granularity jj gives: snapshot progress per path (callback), checkout stats summary afterwards (`CheckoutStats` fields incl. `skipped_files`, `lib/src/working_copy.rs:232-244`; printed with skip warnings at `cli/src/cli_util.rs:2362-2392`).

### Cross-cutting: conflict state is data, not an exception (supports "what remains unresolved")

Conflicts are first-class in the view and in the working copy: checking out a conflicted commit materializes conflict markers, and later snapshots **parse the markers back** into conflict objects (`docs/working-copy.md:30-41`; re-parse at snapshot via `conflicts::update_from_content`, `lib/src/local_working_copy.rs:1195-1223`). The CLI reports unresolved conflicts after working-copy updates with a recovery recipe ("start by updating to it: `jj new <change>` … then `jj resolve`/edit markers/`jj squash`") (`cli/src/cli_util.rs:1676-1684` output block; recipe text at 1931-1957; conflict listing at 2270-2360). Documented limit at the pin: no good way to resolve conflicts "between directories, files, and symlinks" (upstream issue #19 linked) and no way to see where conflict parts came from (`docs/working-copy.md:52-57`). For the companion: "what remains unresolved" can be rendered directly from conflicted paths in the tree; partial resolution via marker editing is supported by design.

## Simpler design choices the evidence supports

1. Observe with `--ignore-working-copy` (or `--at-op`) reads; snapshot explicitly on user action or quiescence (Finding 1, #4545).
2. Never let display I/O abort repository work; sequence writes before output exactly as v0.22.0 does (Findings 4, 7).
3. Make staleness a normal UI state with a repair button (`update-stale` semantics), including the recovery-commit case (Finding 4).
4. Treat load failures as "stop and guide", with `.jj` backup first; never auto-edit op-heads (Finding 5).
5. Restrict mutating actions to one writer per workspace at a time; treat "Concurrent … Try again." as retryable (Findings 2, 3).
6. Avoid promising git-tool compatibility inside secondary workspaces of colocated repos at this pin (Finding 6).
