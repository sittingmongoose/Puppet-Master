# Investigation report — Jujutsu v0.22.0 as engine reference for a workspace-aware local VCS companion

- Case: t11-z-jj-repo-safe-v2-s2 (control arm, documentation-led ad-hoc navigation)
- Pinned source: jj-vcs/jj tag `v0.22.0`, commit `67c2ae0a9e3e445f034a456b299e3f37c4dc4b93` (`inputs/PIN.json:3-5`; release dated 2024-10-02 in `inputs/repository/CHANGELOG.md:21`)
- Local corpus: unchanged original v0.22.0 logical bytes under `inputs/` (431 repository files, 68 issue bodies, 624 raw commit patches per task card); issue states/bodies captured 2026-09-30 (`inputs/issues-index.json:2-4,687-688`), which differs from release-time state
- Method: documentation- and issue-text-led; implementation/tests inspected only to confirm mechanisms. No repository, build, or test execution anywhere in this investigation. The five PNG demos in the corpus (`inputs/repository/demos/*.png`) were never visually inspected; no visual claim about them is made anywhere in this report.
- Question families addressed: (1) observing/changing repository and workspace state while edits or other workspaces exist — findings F1, F2, F3, F6, F7; (2) command completion, interrupted progress delivery, and recovery of workspace state — findings F2, F4, F5, F7.

## F1. "Observing" state is mutating: nearly every command snapshots the working copy into a new commit and operation

Statement. In v0.22.0 the working copy is auto-committed: "Most `jj` commands you run will commit the working-copy changes if they have changed. The resulting revision will replace the previous working-copy revision" (`inputs/repository/docs/working-copy.md:10-13`), and added files are implicitly tracked (`working-copy.md:15-18`). The CLI does this in `WorkspaceCommandHelper::maybe_snapshot`, gated by `may_update_working_copy = loaded_at_head && !ignore_working_copy` (`inputs/repository/cli/src/cli_util.rs:853-854, 897-916`). A changed tree produces a transaction described `"snapshot working copy"`, rewrites the working-copy commit, rebases descendants, and finishes by writing the new operation id into the working-copy state (`cli_util.rs:1611-1641`).

Mechanism. Snapshot walks the disk against recorded per-file states (`inputs/repository/lib/src/local_working_copy.rs:967-1081`), skipping `.jj`/`.git` and untracked ignored files (`local_working_copy.rs:956-957, 1041-1050`), with an fsmonitor/Watchman fast path (`local_working_copy.rs:1089-1132`) and a UI progress callback hook (`inputs/repository/lib/src/working_copy.rs:200-211, 226-227`).

Conditions and cost. Snapshot runs before commands unless `--ignore-working-copy`/`--at-op` is used (`cli_util.rs:881-895`; `--at-op` also skips snapshotting per `inputs/repository/docs/operation-log.md:54-58`). Cost is real: in a colocated Chromium checkout, `jj log` with Watchman took ~209 ms vs ~58 ms with `--ignore-working-copy` (jj-vcs/jj issue #4545, filed 2024-09-27, open at capture). On macOS with ~150,000 files and 24 cores, `jj st` took 2.28 s wall / 32.26 s system time, vs 1.13 s / 0.49 s with `RAYON_NUM_THREADS=4` (issue #4508, filed 2024-09-20, open at capture, labels bug+Mac).

Counterevidence/limits. Watchman integration and `snapshot.auto-track` (new in 0.22.0, `inputs/repository/CHANGELOG.md:66-71`) reduce but do not remove the mutation: a snapshot that finds changes still writes a commit and operation. `--ignore-working-copy` for observation is safe for reads but breaks commands that promise to update the working copy (`cli_util.rs:881-895`), and issue #4545 notes it neither updates `jj new`-checked-out state (citing #4028) nor registers the Watchman trigger — those two external links were not followed (recorded in evidence chains).

Integration implications. The companion's background status/history panel must not present `jj st`/`jj log` polling as read-only: while an agent edits files, each poll rewrites the `@` commit and appends operations, which collides with the user's own commands and costs CPU. Either observe with `--ignore-working-copy` and accept staleness, or schedule snapshotting deliberately (one owner, debounced, optionally Watchman-driven). This is a CLI-behavior fact; it does not prove a GUI polling loop inherits the same failure modes — it must be validated in the companion's own process model (see UNEXECUTED proposals).

## F2. Cross-workspace edits make a workspace "stale"; recovery is explicit, and v0.22.0 has a real recovery-commit path

Statement. With multiple workspaces sharing one repo (`inputs/repository/docs/working-copy.md:78-92`; secondary workspaces link `.jj/repo` as a file containing a relative path, `inputs/repository/lib/src/workspace.rs:549-563`), modifying workspace A's working-copy commit from workspace B makes A stale: files on disk no longer match the commit recorded as `@` (`working-copy.md:94-100`). Mutating commands then fail with "The working copy is stale (not updated since operation …)" plus the hint `Run jj workspace update-stale` (`inputs/repository/cli/src/cli_util.rs:1572-1581`).

Mechanism. Freshness is decided by comparing the working-copy state's recorded operation id (the `checkout` proto in `.jj/working_copy/`, `inputs/repository/lib/src/local_working_copy.rs:1567-1572, 1704-1718`) against the loaded repo operation, distinguishing Fresh / Updated / WorkingCopyStale / SiblingOperation at `cli_util.rs:1553-1600`; a missing working-copy operation yields "Could not read working copy's operation. Run `jj workspace update-stale` to recover." (`cli_util.rs:1591-1598`). `jj workspace update-stale` snapshots on top of the last known working-copy operation, lets divergent operations merge ("the old [wc_commit_id] wins", per the in-code comment `inputs/repository/cli/src/commands/workspace/update_stale.rs:48-51`), and if the recorded operation cannot be read at all it creates and checks out a recovery commit (`tx.commit("recovery commit")` then `locked_wc().recover(&new_commit)`, `update_stale.rs:110-143, 163-170`). A concurrent mutation while recovering errors with "Concurrent working copy operation. Try again." (`update_stale.rs:78-83`). `LockedWorkingCopy::recover` exists exactly for this "previous tree may not exist" case (`inputs/repository/lib/src/working_copy.rs:116-118`; implementation clears file state and resets, `local_working_copy.rs:1553-1557`).

Real-world validation (post-pin, qualified). In jj-vcs/jj issue #4423 (open at capture), user dhardy's 2025-04-07 comment documents a full crash-corruption recovery that ends with exactly this path: after deleting zero-length op-store/index files and re-pointing op heads, `jj workspace update-stale` printed "Created and checked out recovery commit" / "Abandoned 5 commits that are no longer reachable" and restored a working repo. Note the output strings in that comment ("RECOVERY COMMIT FROM `jj workspace update-stale`") are from a later version than v0.22.0, whose recovery-commit description is the plainer `"recovery commit"` (`update_stale.rs:131`).

Counterevidence/limits. The stale check is command-time, not push-based: nothing notifies workspace A that it went stale; the next command simply fails. `update-stale` itself snapshots first (`update_stale.rs:52-54`), so recovery of a workspace whose files are being concurrently edited can itself hit snapshot errors (F6).

Integration implications. The companion should (a) treat "stale working copy" as a first-class, expected UI state with a one-click `workspace update-stale`, (b) detect the ObjectNotFound flavor separately because it means recovery rather than refresh, and (c) never fan out parallel jj processes across workspaces without expecting these guards to trip.

## F3. Repo-level concurrency is lock-free by design; the only hard lock is per working copy

Statement. jj v0.22.0 avoids repo locks: "Jujutsu records each operation that modifies the repo in the 'operation log'" (`inputs/repository/docs/operation-log.md:6-14`), and concurrent commands never corrupt the repo — divergent operation heads are detected and merged into a new "reconcile divergent operations" operation on next load, printing "Concurrent modification detected, resolving automatically." (`docs/operation-log.md:29-44`; `inputs/repository/docs/technical/concurrency.md:64-97`; implementation `inputs/repository/lib/src/op_heads_store.rs:59-137` and `inputs/repository/cli/src/cli_util.rs:444-487`). The op-head pointer update is ordered add-then-remove so a new operation becomes visible atomically (`concurrency.md:116-127`); the optional op-heads lock exists only to avoid duplicate reconciliation work, "not needed for correctness" (`op_heads_store.rs:52-56, 87-90`).

Mechanism, and the exception. The single real mutual exclusion is the working-copy lock: `WorkingCopy::start_mutation` takes `FileLock::lock(state_path.join("working_copy.lock"))` and re-reads state after acquiring it (`inputs/repository/lib/src/local_working_copy.rs:1607-1631`); concurrent checkout of the same workspace is detected and refused (`CheckoutError::ConcurrentCheckout`, `inputs/repository/lib/src/working_copy.rs:256-259`; guard `inputs/repository/lib/src/workspace.rs:432-440`), covered by `test_concurrent_checkout` and `test_checkout_parallel` in `inputs/repository/lib/tests/test_local_working_copy_concurrent.rs:32-147` (test source read; never executed). Racy mtime edges are handled (`test_racy_checkout`, same file:149-180; `local_working_copy.rs:1148-1149`).

Conditions/counterevidence. The docs themselves qualify the model: with the Git backend, "repository corruption is possible because the backend is not entirely lock-free" (jj-vcs/jj issue #2193, cited at `concurrency.md:51-54`), and concurrent cross-machine use via rsync/NFS "is not currently thoroughly tested" (`concurrency.md:56-61`). Divergence also has rough edges at this pin: `jj op show` panicked (`Option::unwrap()` on None in the revset engine) after a two-workspace abandon-vs-edit race was reconciled (issue #4465, reported on 0.21.0; closed only 2025-06-12, i.e. after the pin — the panic path existed at v0.22.0; the fix commit was not fetched and is recorded as a missing link).

Integration implications. Parallel jj processes are safe at the repo level (last-writer merges) but serialize per workspace via `working_copy.lock`. A companion that shells out to jj while the user runs jj in the same workspace will contend on that lock, and a companion that surfaces "divergent operations" must treat reconciliation output as normal, not exceptional. The #4465 panic is a concrete reason to wrap `op show`/`op diff` inspection in error handling.

## F4. Interrupted progress delivery: broken pipes used to strand a stale working copy; fixed in v0.22.0 by reordering state updates before reporting

Statement. Issue #4239 (bug, closed 2024-09-22): `jj rebase -s third -d first 2>&1 | head -n 3` died of a broken pipe mid-command, and the next command failed with the stale-working-copy error — reproducible, "not a concurrency bug" (body `inputs/issues/4239.json:99-112`). Fixed for v0.22.0: the changelog lists "Fixing #4239 … the ordering of some messages have changed" as a breaking change (`inputs/repository/CHANGELOG.md:25-26`).

Mechanism (v0.22.0 code). `finish_transaction` now commits the repo transaction, then updates the working copy, and only then reports repo changes, with the explicit comment: "Update working copy before reporting repo changes, so that potential errors while reporting changes (broken pipe, etc) don't leave the working copy in a stale state." (`inputs/repository/cli/src/cli_util.rs:1757-1771`; report step `report_repo_changes` at 1803-1912). The fix thread matches: maintainer yuja noted the scenario was "expected after failed working-copy updates" and proposed exactly this reordering (comment 2024-08-08, fetched from `https://api.github.com/repos/jj-vcs/jj/issues/4239/comments`), contributor essiene implemented it in PR #4517 (comment 2024-09-21, same URL), and yuja added that within the transaction model "Working-copy updates and git exports are two major sources of inconsistency" (comment 2024-08-10).

Conditions. The guarantee is ordering, not durability: a hard kill (SIGKILL, power loss — F5) still interrupts anywhere; SIGINT/SIGTERM run registered `CleanupGuard` callbacks and then re-raise the default signal (`inputs/repository/cli/src/cleanup_guard.rs:13-46, 65-100`), and guards cover temp-file-style cleanup, not transaction rollback.

Integration implications. For a GUI streaming command output into a panel: closing or truncating the consumer of jj's stdout/stderr can fail writes; at v0.22.0 the repo/working-copy state is consistent *before* the human-readable report is emitted, so the companion should treat captured exit code/output as advisory and re-read state (op log + view) through jj to decide what happened. Do not infer completion from having consumed all output lines.

## F5. Crash recovery is not solved: power loss leaves zero-length op-store/index/git files, and there is no integrated repair

Statement. Issue #4423 "hosed jj repo after hard-reboot" (filed 2024-09-08, still open at capture 2026-09-30): after a power cycle without sync, every jj command failed — "Error when reading object of type view: Is a directory (os error 21)" (body `inputs/issues/4423.json:58`). The comment thread (fetched 2026-10-01 from `https://api.github.com/repos/jj-vcs/jj/issues/4423/comments`) shows the failure mode precisely: zero-length files appear under `.jj/repo/op_store/operations/`, `.jj/repo/op_heads/heads/`, `.jj/repo/index/operations/`, and `.jj/repo/store/extra/`; the reporter also found empty objects under `.git/objects/` and concluded "some of the git data wasn't written with fsync()". Manual recovery is error-prone: maintainers' steps are delete/touch op-head files by hex name (martinvonz, 2024-09-08), and mid-recovery attempts hit panics (`op_heads_store.rs:90`, `operation.rs:97`, `default_index_store.rs:245` in the reporter's 0.21/0.15 binaries) and index rebuild failures ("Failed to read non-git metadata: failed to fill whole buffer").

Mechanism and counterevidence in the pin. The design doc claims content-addressed op-store objects are "safe to write without locking" and that op-head pointer updates "ensure that transactions are atomic" (`concurrency.md:118-127`) — atomicity against concurrent readers is not durability against power loss, and #4423 is the counterexample. At v0.22.0 the working-copy `checkout` state is also read with `unwrap()` on both `fs::read` and proto decode (`local_working_copy.rs:1704-1718`), so a truncated checkout file panics instead of degrading gracefully. Mitigations that do exist at this pin: the working-copy state tree can be discarded wholesale (`rm .jj/working_copy/tree_state` fixed one reporter's snapshot failure — alberand comment, 2025-05-27), `jj workspace update-stale` reconstructs a workspace whose operation is unreadable (F2), and jj pins Git GC-protection refs under `.git/refs/jj/keep/` that recovery guides use to salvage data (dhardy/SyrupThinker comments). This is not a claim about the latest release; the issue remained open at capture.

Integration implications. The companion must assume load-time corruption is possible after OS crashes: detect "Internal error: Failed to load the repo / Failed to load an operation" as a distinct degraded mode; offer backup-before-repair; never auto-delete `.jj` internals; and drive recovery through official commands (`--at-op`, `op log`, `workspace update-stale`) rather than file surgery. A background agent writing to the repo is precisely the process that loses data here.

## F6. What is "on disk" is not what a GUI would assume: conflict markers are parsed back, ignored files are left behind, and oversized new files block every command

Statement. Three disk-level behaviors constrain any "what changed on disk / what remains unresolved" view at v0.22.0:

1. Conflicts materialize as marker text in working-copy files and are re-parsed from markers on every scan (`inputs/repository/docs/working-copy.md:30-41`). A file whose markers were hand-edited into an inconsistent form crashed snapshotting in the field — "must have one more adds than removes" (`jj_lib::merge`/`parse_conflict`) — breaking `jj st`, `jj log`, and `jj squash` for the reporter on 0.20/0.21 (issue #4396, closed not_planned 2024-09-05; whether that exact panic remains reachable at v0.22.0 was not verified — `inputs/repository/lib/src/merge.rs` was not inspected; the marker re-parsing behavior itself is documented at the pin).
2. Untracked-but-ignored files are never snapshotted (`working-copy.md:69-75`; `local_working_copy.rs:1041-1050`) and simply stay on disk across checkouts; issue #4559 (closed 2024-10-01, same day as filing, state "completed" at capture) shows the sharp edge: after switching to a revision whose `.gitignore` no longer covers a leftover 2.8 MiB crash dump, the next command failed on the then-current size guard (quote in issue). The v0.22.0 guard wording is "New file {path} of size ~{size} exceeds snapshot.max-new-file-size ({max_size})" (`inputs/repository/lib/src/working_copy.rs:161-171`), enforced at `local_working_copy.rs:1056-1064` (default ~1 MiB per the issue text; already-tracked files are always snapshotted, `working_copy.rs:205-210`). The issue's quoted wording differs from the pin's, so the report is version-qualified.
3. Checkout can silently skip files replaced by untracked/ignored files on disk — `CheckoutStats::skipped_files` exists exactly for that (`working_copy.rs:240-243`).

Integration implications. "What remains unresolved" should be derived from jj's own conflict model (tree conflicts per commit), not from grepping files for markers; "what changed on disk" must account for ignored/untracked residue that the user may believe is saved; and snapshot failures (`SnapshotError::NewFileTooLarge`, invalid paths, backend errors — `working_copy.rs:142-184`) are user-blocking conditions the GUI must surface with the configured remedy (`snapshot.max-new-file-size`, `.gitignore`), because every subsequent command re-attempts the failing snapshot.

## F7. Workspace lifecycle and the colocated-Git gap: management commands exist, but secondary workspaces are invisible to Git tooling at this pin

Statement. v0.22.0 ships `jj workspace add` (with new `--sparse-patterns=copy|full|empty`, `CHANGELOG.md:77-80`), `forget`, `root`, and — new in this release — `jj workspace rename` (`CHANGELOG.md:82`; implementation rejects empty names and untracked current workspaces, `inputs/repository/cli/src/commands/workspace/rename.rs:23-58`; fixes issue #4342, closed completed 2024-09-17). Workspace identity lives in the repo view per workspace id (`operation-log.md:9-11`), and every transaction finishes by protecting *all* workspaces' working-copy commits: if rebasing made another workspace's `@` immutable, a new commit is created on top of it with a warning naming that workspace (`cli_util.rs:1714-1732`).

Gap. In a `--colocated` repo, secondary workspaces created by `jj workspace add` have no `.git` directory, so Git-based tooling does not recognize them (issue #4436, filed 2024-09-11 with 68 +1 reactions; closed "completed" only 2026-09-17 — i.e. **not** fixed at v0.22.0). Recovery of undo context also improved in exactly this release: "`jj op undo` now reports information on the operation that has been undone" (`CHANGELOG.md:90`; issue #4431, closed completed 2024-09-15).

Integration implications. The companion should drive workspace create/rename/forget through these commands and display per-workspace `@` from the repo view rather than per-directory inference; if users also run Git tooling inside secondary workspaces, the companion must warn that colocated behavior applies only to the primary workspace at this pin. Undo/redo affordances should read `jj op log` (and can rely on `op undo`'s new reporting) instead of parsing command stdout.

## Transfer limits (CLI behavior ≠ GUI safety)

Everything above is evidence about the jj v0.22.0 CLI and library as invoked as separate processes. It does not prove the companion's GUI will behave safely: long-lived in-process use of `jj-lib` (the `TreeState` "long-lived process" caveat at `working_copy.rs:190-194`), polling loops, pipe-buffer interactions with streamed output, and multi-window multi-workspace fan-out are all outside what these sources establish. Each integration claim above is therefore a hypothesis to validate, not a property to assume.

## UNEXECUTED validation proposals

1. Stale-WC regression check: under a v0.22.0 binary, run `jj rebase … 2>&1 | head -n 3` into a conflict and confirm the next command no longer reports a stale working copy (validates F4/#4239 fix at the pin).
2. Two-workspace race: from workspace B, `jj new` on top of workspace A's `@` while A has uncommitted edits; then run commands in A; confirm stale error text and that `jj workspace update-stale` restores A with a "recovery commit"-described commit (validates F2, `update_stale.rs:131`).
3. Reconciliation robustness: reproduce the #4465 sequence (concurrent `abandon` + `edit` across two workspaces, then `jj op show @`) on v0.22.0 to confirm the panic is present at this pin (validates F3's caveat).
4. Crash simulation: kill -9 / VM power-cut during `jj commit` loops in a scratch repo, then follow the maintainers' #4423 recovery steps; record which zero-length-file locations occur and whether `workspace update-stale` suffices without manual surgery (validates F5).
5. Snapshot cost under polling: in a large repo, measure wall/system time of a GUI-like 1 Hz `jj st` loop vs `jj --ignore-working-copy log` vs Watchman-enabled, with `RAYON_NUM_THREADS` varied (validates F1 numbers #4508/#4545 in the companion's own workload).
6. Marker-fuzz: hand-corrupt conflict markers in a conflicted file and attempt `jj st` on v0.22.0 to test whether the #4396 parse_conflict panic is still reachable (closes F6.1's unresolved facet).
7. Oversized-file drill: drop a >1 MiB untracked file into a workspace and verify every command fails with `snapshot.max-new-file-size` guidance and that `--config-toml 'snapshot.max-new-file-size=…'` unblocks (validates F6.2 at the pin).
