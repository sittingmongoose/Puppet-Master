## 1. Q1 findings — governing requirements, conditions, mechanisms, failure behavior, exceptions

### 1.1 Conformance framework and document status

- **F001 [E] Conformance conventions.** Requirement keywords are RFC 2119 terms [S003 L56–59, L869–874]; requirement words may appear in lowercase [S003 L875–876] (e.g., "must" at L193 and L300), so requirement strength cannot be parsed by case alone. All text is normative except explicitly marked non-normative sections, examples and notes [S003 L877–883]. JSON comments appear in spec examples for clarity only and **MUST NOT** be included in real JSON objects [S003 L65–66] — the multiscales example itself contains `//` comments (L341, L351, L361, L370) and is therefore not valid JSON as printed. Failure behavior implication: a fileset whose metadata was copied verbatim from the spec examples is malformed.
- **F002 [E] Document status and versions.** The current released version is 0.5; migration scripts are promised between numbered versions; data written by "editor's draft" changes "will not necessarily be supported" [S003 L24–27]. Version history: 0.5.0 (2024-11-21) adopted Zarr v3 (RFC-2); 0.5.1 (2025-01-10) re-added the improved `omero` description; 0.5.2 (2025-01-10) clarified that `dimension_names` **MUST** be included [S003 L821–833]. The capture is the Final Community Group Report dated 8 September 2026 [S003 L3–4].
- **F003 [E] Storage basis.** OME-Zarr is implemented on **Zarr format version 3** [S003 L67–69]. All Zarr features — codecs, chunk grids, chunk key encodings, data types, storage transformers — **may** be used unless explicitly disallowed here [S003 L70–72]. The hierarchy may exist locally, on HTTP, or in object storage such as S3/GCS [S003 L73–77]; the format is storage-agnostic even though Slide Scout's boundary is local-only.

### 1.2 Hierarchy requirements

- **F004 [E] Image fileset layout.** Images are Zarr groups whose group-level attributes live in `zarr.json` and include "multiscales" and "omero" [S003 L87–89]. Dimensionality is variable between 2 and 5 and **axis names are arbitrary** [S003 L81]. Each multiscale level is a separate Zarr array; **array names are arbitrary**, ordering being defined by the "multiscales" metadata (often a sequence from 0) [S003 L91–94]. Image arrays **must** be up to 5-dimensional with the time axis before the channel axis before spatial axes [S003 L96–97]. Chunks follow the Zarr array specification in each array's `zarr.json` [S003 L99–100].
- **F005 [E] Labels layout.** A `labels` group nested in the image group is a container (not itself an image) listing label images for discoverability [S003 L102–105, L437–438]. Each label dimension must equal the corresponding image dimension or be 1 if irrelevant [S003 L106–108]. Intermediate folders under `labels` are permitted and currently carry no extra metadata [S003 L110, L439–440]. Label arrays support **only integer values** [S003 L112–117].
- **F006 [E] High-content screening (HCS) layout.** Three groups **MUST** be defined above the images: the well group (**MUST** implement the well specification; all images in a well are fields of view of the same well), the row group above it, and the plate group above that (**MUST** implement the plate specification) [S003 L118–127]. A well-row group **SHOULD NOT** be present if its wells hold no images; a well group **SHOULD NOT** be present if it holds no images [S003 L128–129].

### 1.3 Metadata namespace

- **F007 [E] `ome` namespace and version consistency.** OME-Zarr metadata is stored under the namespaced key `ome` in `attributes` of the various `zarr.json` files; the metadata version is a string in `ome.version`, and the version **MUST** be consistent within a hierarchy [S003 L149–156]. A fileset mixing `ome.version` values is non-conforming — a checkable failure condition.

### 1.4 Axes and coordinate mechanisms

- **F008 [E] `axes` metadata.** Each axis **MUST** have `name`, unique across all axes [S003 L168]. It **SHOULD** have `type` (one of "space", "time", "channel"), and **MAY** take other custom string values not covered by the spec yet [S003 L169]. It **SHOULD** have `unit`; the value **SHOULD** be one of the listed UDUNITS-2 strings (space and time lists enumerated at [S003 L170–172]). The length of `axes` **MUST** equal the dimensionality of the image arrays [S003 L173]. The `dimension_names` attribute **MUST** be included in the `zarr.json` of each multiscale-level Zarr array and **MUST** match the `axes` names [S003 L174; clarified as a MUST in 0.5.2, L825–827].
- **F009 [E] `coordinateTransformations` (general mechanism).** Each transformation entry **MUST** have `type`, one of: `identity` (the default, typically not explicit), `translation`, or `scale`; translation/scale vectors are stored either inline as `List[float]` or by `path` to binary data in the container [S003 L276–289]. Transformations in a list are applied **sequentially and in order** [S003 L293].
- **F010 [E] `multiscales` requirements.** Each `multiscales` dictionary **MUST** contain `axes` [S003 L299]: length 2–5 and equal to array dimensionality [S003 L300]; **MUST** contain 2 or 3 `space` entries and **MAY** add one `time` and one `channel` (or null/custom) entry [S003 L301]. Axis order **MUST** match array dimension order and **MUST** be ordered by type: time first (if present), then channel/custom, then space [S003 L302]; for 3D stacks the spatial order **SHOULD** be `zyx` [S003 L303]. Each dictionary **MUST** contain `datasets` [S003 L304]; each dataset **MUST** have `path` relative to the current group, and paths **MUST** be ordered from largest (highest resolution) to smallest [S003 L305–306]. All datasets **MUST** have the same number of dimensions, **MUST NOT** exceed 5, matching `axes` in number and order [S003 L307]. Each dataset **MUST** have `coordinateTransformations` mapping data to physical coordinates; only `translation` and `scale` types are allowed here [S003 L308–309]. There **MUST** be **exactly one scale** per dataset, giving "the pixel size in physical units or time duration"; where scaling information is unavailable for an axis, the value **MUST** express the factor between the current and first resolution for that axis, defaulting to 1.0 with no downsampling [S003 L310]. A single `translation` **MAY** be present and, if given, **MUST** come after scale so it is expressed in physical coordinates [S003 L311]. Scale and translation array lengths **MUST** equal the `axes` length [S003 L312]. The group-level `coordinateTransformations` **MAY** be present, follows the same type/order rules, and is applied **after** the per-dataset transformations — usable for a scale shared by all levels (the example applies a 0.1 ms time unit there) [S003 L314–316, L368–374]. `name`, `type` (downscaling method) and `metadata` **SHOULD** be present [S003 L317–319].
- **F011 [I] Scale-value semantics (harmonized reading).** The primary rule is that per-level scale gives the absolute pixel size in physical units [S003 L310]; the example confirms this — level 0 carries `0.5` µm, level 1 `1.0`, level 2 `2.0`, with comments naming them voxel sizes [S003 L341–363]. The relative-factor sentence at L310 is a **fallback** for axes lacking scaling information. A compliant viewer must therefore (a) treat scale as absolute physical size in the normal case, and (b) still handle a relative-factor/default-1.0 value without being able to distinguish the two cases from the data alone. **[U] Residual ambiguity:** the spec does not state how a reader can tell which regime applies for a given axis; this is unresolved on the admitted evidence and needs an explicit product decision plus tests (see F111).
- **F012 [E] Multiscale selection rule.** With one multiscale entry, use it; with several, "the user can choose by name, using the first multiscale as a fallback" [S003 L388–397 — informative pseudocode, non-normative per L877–883].

### 1.5 Transitional collection metadata (bioformats2raw)

- **F013 [E] `bioformats2raw.layout` (transitional).** Added in v0.4 to describe filesets "that already exist in the wild"; an upcoming NGFF specification will replace it with explicit metadata [S003 L180–181]. Transitional metadata may be a **MUST** for readers while writing stays **MAY** [S003 L60–64]. Conforming groups **MUST** have value "3" for the key in the top-level `zarr.json` [S003 L256]. If the top-level group is also a plate, the `plate` key **MUST** be present and takes precedence, and image collections cannot be mixed with plates at present [S003 L204–206]. The OME group **SHOULD** contain `OME/METADATA.ome.xml`, which **MUST** adhere to OME-XML and **MUST** use `<MetadataOnly/>` instead of `<BinData/>`, `<BinaryOnly/>` or `<TiffData/>` (i.e., the XML carries no pixel data) [S003 L257–260]. Image-finding logic: with `plate`, images are at the defined locations [S003 L262]; `series` **MUST** be a list of strings whose order **MUST** match the OME-XML `Image` order if provided [S003 L265–267]; with neither `series` nor `plate`, multiscales images **MUST** occupy consecutively numbered groups from 0, and every multiscales group **MUST** represent exactly one OME-XML Image in that order [S003 L268–270].
- **F014 [E] Reader duties for collections.** Conforming readers **SHOULD** make users aware that more than one image exists (**SHOULD NOT** default to opening only the first); **MAY** use the `series` attribute to determine valid groups; **MAY** show all images or offer a choice; **MAY** ignore other groups/arrays under the root [S003 L271–275]. Condition preserved: these are SHOULD/MAY duties, not MUSTs.

### 1.6 Rendering metadata

- **F015 [E] `omero` (transitional).** Optional; **if present** it **MUST** contain `channels` (array matching the c-dimension size); each channel **MUST** have `color` (6-hex-digit RGB string) and `window`, which **MUST** contain `min`, `max`, `start`, `end` [S003 L426–430]. The example also shows `id`, `name`, per-channel `active`/`coefficient`/`family`/`inverted`/`label`, and `rdefs` with `defaultT`, `defaultZ`, `model` ("color" or "greyscale") — example fields, informative [S003 L401–423]; full semantics are deferred to the OMERO WebGateway documentation [S003 L424–425], which is not in the admitted corpus (see F022).

### 1.7 Label image metadata

- **F016 [E] `labels` metadata.** Label pixels **MUST** be one of the eight integer dtypes (u)int8/16/32/64 [S003 L438–439]. Intermediate groups between `labels` and its images are allowed but **MUST NOT** contain metadata [S003 L439–440]. The labels group's `zarr.json` **MUST** contain the `labels` key: a JSON array of paths to the labeled multiscale images; all label images **SHOULD** be listed [S003 L441–442]. A label image's `zarr.json` **MUST** implement `multiscales`, and its `datasets` array **MUST** have the **same number of scale levels** as the original unlabeled image [S003 L454–455].
- **F017 [E] `image-label` metadata.** The label image **SHOULD** also carry `image-label` [S003 L456–458], which **SHOULD** contain `colors` (whose value **MUST** be an array; each object **MUST** have integer `label-value`; **MAY** have `rgba`, **MUST** be four integers 0–255, fourth = alpha) and `version` (**MUST** be a string) [S003 L458–466]. Conforming readers **SHOULD** display labels using these colors [S003 L461]. `properties` and `source` **MAY** be present; `properties` objects **MUST** have `label-value` and otherwise arbitrary, non-uniform key-value pairs [S003 L467–471]; `source` **MUST** be an object and **MAY** include `image`, a relative path to the source image group, defaulting to `../../` [S003 L472–474]. Example with two colors and properties at [S003 L476–514].

### 1.8 HCS metadata

- **F018 [E] `plate` metadata.** `acquisitions` **MAY** be present; each acquisition **MUST** have `id` (unique integer ≥ 0 within the plate) and **SHOULD** have `name` (**MUST** be a string if present) and `maximumfieldcount` (**MUST** be a positive integer if present); `description`, `starttime`, `endtime` **MAY** be present with **MUST**-level type constraints when present (integer epoch timestamps) [S003 L518–529]. `columns` and `rows` are **MUST** keys; every physical column/row **MUST** be defined even if empty; each name **MUST** be alphanumeric, case-sensitive, and non-duplicating within its list, with **SHOULD**-level care to avoid case-insensitive filesystem collisions (e.g., "Aa" vs "aA") [S003 L530–537, L542–549]. `field_count` and `name` **SHOULD** be present (positive integer / string respectively) [S003 L538–541]. `version` **MUST** be present (string) [S003 L550–551]. `wells` **MUST** be present; each well **MUST** have `path` of exactly `rowName/columnName` with no extra leading/trailing directories, plus 0-based `rowIndex` and `columnIndex`, and path and indices **MUST** agree [S003 L552–560]. **Sparse plates are explicitly supported** — the second example defines 2 wells in a 12×8 grid [S003 L641–739]; a full plate example is at [S003 L561–640].
- **F019 [E] `well` metadata.** **MUST** contain `images`, listing all fields of view; each **MUST** have `path` (alphanumeric, case-sensitive, unique within the list) [S003 L744–748]; if the plate has multiple acquisitions, each image **MUST** have an `acquisition` integer matching one of the plate's acquisition ids [S003 L748–750]. `version` **SHOULD** be present (**MUST** be a string if present) [S003 L751–752]. Note the asymmetry with plate, where `version` is a **MUST** key [S003 L550–551]. Examples at [S003 L753–808].

### 1.9 Editorial, index, and status observations

- **F020 [E] Naming-style exceptions.** Multi-word keys should be camelCase, but the spec acknowledges some keys predate the convention and "should be updated in due course" [S003 L809–812] — observable inconsistencies include `field_count`, `maximumfieldcount`, `rowIndex`/`columnIndex`, and the hyphenated `label-value`/`image-label` keys. Interop consequence [I]: readers must key off exact strings as specified, not a uniform convention.
- **F021 [E] Index/reference oddities (minor, unresolved).** The index lists "HCS, in § 2.2.3" [S003 L891] although HCS layout is defined in §1.2, and "Transitional, in § Unnumbered section" [S003 L892]; there is also a stray "." at L130. These look like conversion/formatting artifacts of the capture; they do not change any requirement but flag that the capture's cross-references cannot be trusted blindly.
- **F022 [U] Coverage limits of the corpus (unresolved areas).** The admitted source alone cannot answer: (a) which reader/writer implementations exist or how they behave — §4 says only "See Tools" [S003 L813–814]; (b) Zarr v3 mechanics (chunk grids, codecs, chunk key encoding, storage transformers, `zarr.json` array format) — deferred, not included [S003 L67–72, L99–100]; (c) OME-XML content obligations beyond `<MetadataOnly/>` [S003 L257–260]; (d) full `omero`/`rdefs` semantics [S003 L424–425]; (e) UDUNITS-2 grammar beyond the listed unit strings [S003 L170–172]; (f) any conformance test suite — none is referenced; (g) the content of the future spec replacing `bioformats2raw.layout` [S003 L180–181]. All negative statements in this report are scoped to S003 (version/hashes in §0); nothing here establishes absence in the wider corpus or ecosystem.
- **F023 [E→I] Rejected common assumptions (counterevidence kept visible).** Each of the following plausible assumptions is contradicted by cited evidence: metadata JSON may contain comments — no, **MUST NOT** [S003 L65–66]; array/folder names encode resolution order — no, names are arbitrary and `datasets` order governs [S003 L93–94, L305–306]; axis names are fixed t/c/z/y/x — no, arbitrary [S003 L81, L168–169]; plates must be fully populated — no, sparse plates are conforming and only *empty* groups are discouraged (SHOULD NOT) [S003 L128–129, L641–739]; `omero` is required — no, optional with conditional MUSTs [S003 L426]; label images may use float dtypes — no, integers only [S003 L438–439]; scale values are always absolute — ambiguous, see F011; well `version` is required like plate `version` — no, SHOULD vs MUST [S003 L550–551, L751–752].

## 2. Q2 findings — consequences for the thin plan, alternatives, improvements, validation

### 2.1 Plan implications (Viewer.md against the evidence)

- **F101 [I] Image discovery must span three layouts, and must not default to the first image.** The plan says the app "opens a local OME-Zarr 0.5 fileset and lists the images it finds" [Viewer L5]. The evidence requires that listing logic to handle: plain multiscale image groups (§1.1 [S003 L78–117]); HCS plate → row → well → field-of-view hierarchies with sparse plates (§1.2, §2.7, §2.8 [S003 L118–148, L515–808]); and bioformats2raw collections via `series`, `plate` precedence, or consecutive groups 0,1,2,… (§2.2 [S003 L175–275]), plus label listings (F016). Because readers **SHOULD NOT** default to only the first image in a collection [S003 L272], the plan's list must be surfaced prominently, not just used to auto-open the first item. Discovery should be tolerant of unrelated groups/arrays under the root, which readers **MAY** ignore [S003 L275].
- **F102 [I] The viewer must be dimension-agnostic.** 2–5 dimensions, arbitrary axis names, mandatory t→c→space ordering, and `dimension_names` in each array's `zarr.json` matching `axes` [S003 L81, L96–97, L168–174, L299–302] mean the plan's "channel visibility controls, time-point and plane selection where relevant" [Viewer L5] must be driven by parsed `axes`/`dimension_names`, never by hardcoded names like "t"/"c"/"z". Failure behavior: a mismatch between `dimension_names` and `axes` is a concrete, checkable defect to report to the user (F107).
- **F103 [I] Pyramid-level choice must come from metadata, not file names.** The plan "chooses an available pyramid level appropriate for the current view" [Viewer L5]. Evidence: level paths **MUST** be ordered high→low resolution in `datasets` [S003 L305–306]; names are arbitrary [S003 L93–94]; relative pixel sizes per level come from `coordinateTransformations` (F010/F011). Selection logic should rank levels by derived absolute size and, when several `multiscales` entries exist, follow the name-choice-with-first-fallback rule (informative) [S003 L388–397].
- **F104 [I] Calibrated coordinates need the full transformation chain.** The plan's details panel shows "dimensions, units and coordinates" [Viewer L5]. Evidence requires: per-dataset scale (exactly one; absolute physical size in the normal case, relative-factor fallback otherwise — F011), optional translation ordered after scale, and group-level transformations applied afterwards [S003 L308–316]; unit strings from the UDUNITS-2 lists [S003 L170–172]. Conditions: `unit` is only **SHOULD**, and axis `type` may be custom [S003 L169] — so the UI must degrade gracefully: show uncalibrated axes honestly rather than inventing units, and display custom types/units as-is.
- **F105 [I] Label overlays have guaranteed alignment conditions the plan can rely on — and limits.** The plan offers "optional overlays for associated label images" [Viewer L5]. Evidence: discovery via the `labels` array [S003 L441–442]; a conforming label image has the **same number of pyramid levels** as its base image [S003 L454–455] and dimensions equal or 1 per axis [S003 L106–108] — these are what make level-aligned overlay rendering sound. Overlay colors: readers **SHOULD** use `image-label.colors` rgba values [S003 L461–466]; `image-label` itself is only **SHOULD**, so a conforming fileset may omit it — the viewer needs a fallback rendering (e.g., a neutral colormap) and should say so. `source.image` defaults to `../../` [S003 L472–474]; `properties` may be shown as arbitrary per-label key-value pairs [S003 L467–471]. Counterevidence to keep visible: label images not listed in the `labels` array violate a SHOULD [S003 L442] — a scan for unlisted label-like groups is possible but is an extension beyond the spec's discovery contract.
- **F106 [I] Initial display state can come from `omero`, with required fallbacks.** The plan's channel visibility and default time/plane [Viewer L5] map to `omero` fields: channel `color` and `window` (`min`/`max`/`start`/`end` are **MUST**s when `omero` is present) and the informative `rdefs` `defaultT`/`defaultZ`/`model` [S003 L401–430]. Because `omero` is optional [S003 L426], all of this needs non-`omero` defaults (e.g., data-driven min/max windowing); `rdefs` semantics beyond the example are documented only in the unadmitted OMERO WebGateway docs (F022) — treat `defaultT`/`defaultZ` as informative hints [I], clamped to valid ranges.
- **F107 [I] The plan's failure-feedback requirement maps to a concrete, checkable MUST inventory.** The plan requires understandable feedback for malformed/unavailable input and no crashes [Viewer L7, L11]. The spec supplies the validation surface: RFC 2119 semantics including lowercase usage [S003 L56–59, L875–876]; no JSON comments [L65–66]; `ome.version` consistency [L156]; `dimension_names` presence/match [L174]; `axes` length = array dims [L173]; `datasets` ordering [L305–306]; dimensionality ≤ 5 and matching [L300, L307]; exactly one scale per dataset, translation after scale, vector lengths = axes length [L308–312]; bioformats2raw value "3", plate precedence, no mixing [L204–206, L256]; `series` string list and ordering [L265–267]; label integer dtypes [L438–439]; no metadata in intermediate label groups [L439–440]; label level-count parity [L454–455]; plate/well name, path, index, and acquisition-consistency rules [L530–560, L744–750]. A validator that reports *which* rule failed satisfies the plan's "explain which image or data could not be displayed" requirement; a crash-only reader would violate the plan, not the spec.

### 2.2 Engineering alternatives and transfer limits

- **F108 [I] Background IO, cancellation, and responsiveness are engineering options, not spec obligations.** The plan's "large image reads run in the background… changing the selected view cancels work" [Viewer L7] has **no counterpart in S003** — the spec is silent on concurrency, caching, and rendering. Transfer limits: (a) chunk-structured arrays [S003 L91–100] make partial, per-chunk loading feasible, which is the natural basis for background reads, but chunk grids/codecs/key encodings are Zarr v3 features only summarized here [S003 L70–72] and the Zarr v3 spec is not admitted — the exact chunk addressing scheme cannot be verified from this corpus; (b) the plan's local-filesystem boundary is compatible with the format (the spec explicitly shows the local appearance of the hierarchy [S003 L73–77]) while the format itself remains storage-agnostic — any future remote support is a product decision, not a format change.
- **F109 [I] Compatibility limits around versions and legacy filesets.** OME-Zarr 0.5 is Zarr v3-based [S003 L67–69, L831–833]; `bioformats2raw.layout` exists precisely because 0.4-era multi-image filesets "already exist in the wild" [S003 L180–181], and transitional reading may be a reader MUST [S003 L60–64]. The spec does not state what a *viewer* must do with non-conforming or older-version filesets: accepting pre-0.5 / Zarr v2 filesets is an unregulated product decision [U — no evidence either way in S003]. The `ome.version` consistency MUST [S003 L156] at least gives a reliable detection signal, and editor's-draft data "will not necessarily be supported" [S003 L25–27] argues for strict version checking in a viewer claiming 0.5 support.
- **F110 [I] Improvement opportunities over the thin plan (each with its evidence and limit).** (a) HCS plate grid UI with explicit sparse-plate support and per-acquisition filtering [S003 L641–739, L744–750]; (b) tolerant metadata key handling given the acknowledged naming-style exceptions (`field_count`, `maximumfieldcount`, `rowIndex`, `label-value`) — match exact spec strings, do not normalize [S003 L809–812]; (c) case-insensitive name-collision warnings for rows/columns on case-insensitive filesystems [S003 L536–537, L548–549]; (d) multi-version hierarchy detection via `ome.version` [S003 L155–156]; (e) display custom axis types and unlisted units verbatim with an "uncalibrated" marker [S003 L169–172]; (f) best-effort detection of unlisted label images, reported as a non-conformance warning rather than silently ignored [S003 L442]; (g) surface collection size ("N images") before opening, honoring F014. Each item is an option the evidence supports as *permissible and useful*; none is mandated by the spec except where a MUST/SHOULD is cited.

### 2.3 Proposed validation — ALL UNEXECUTED

- **F111 [U — explicitly NOT executed.]** No fixture, test, or conformance run was executed in this Goal; nothing below has passing status. Proposed, pending implementation:
  1. **Positive fixtures** built from the spec's own examples: 5D tczyx multiscales with group-level time scale [S003 L320–387]; 2D and 4D variants; full plate [L561–640]; sparse plate [L641–739]; multi-acquisition wells [L753–808]; labels with `image-label` colors/properties/source [L443–514]; bioformats2raw collection with `series` + `OME/METADATA.ome.xml` (MetadataOnly) [L183–253].
