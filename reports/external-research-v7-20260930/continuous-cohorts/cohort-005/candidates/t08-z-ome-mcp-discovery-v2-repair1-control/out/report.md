# Slide Scout discovery report: OME-Zarr 0.5 format obligations and reader-implementation lessons

**Date:** 2026-10-01
**Scope:** Slide Scout — a small read-only desktop browser for local OME-Zarr 0.5 bioimaging filesets. Product boundary: local filesystem reading, source files unchanged; image editing, export, remote services and clinical interpretation are out of scope.
**Method:** Discovery research using only the bounded MCP tools (`read_file`, `write_file`, `mechanical`, `public_https_get`). All sources are public HTTPS fetches logged in `out/acquisition.json`; the search/read sequence and unvisited areas are logged in `out/scheduling.json` (with immutable drafts `scheduling.draft-01.json`, `scheduling.draft-02.json`).
**Plan boundary:** This session is plan-blind: no plan, spec or answer history was admitted. "Plan implications" below are therefore generalized requirement implications for any thin initial plan, not edits to a specific admitted plan.
**Evidence hygiene:** Every external claim below carries a source ID (S#) and locator; SHA-256, size and access status are recorded per source in `out/acquisition.json`. Truncated fetches are marked. A failed search proves only that search result, not absence. All proposed validation in the final section is **UNEXECUTED**.

## 1. Independent findings

### A. Established format obligations (OME-Zarr 0.5, normative)

**FMT-01 — 0.5 is Zarr v3, not Zarr v2.** OME-Zarr 0.5 is implemented on version 3 of the Zarr specification; group/array metadata lives in `zarr.json` files, with OME metadata under `attributes.ome`, and the OME metadata `version` string MUST be consistent within a hierarchy. The 0.5.0 change entry states "Use Zarr v3 in OME-Zarr, see RFC-2". This is the single largest difference from 0.4 filesets (`.zgroup`/`.zattrs`/`.zarray`). — S1 (spec §Storage format, §OME-Zarr Metadata), S2 (version_history 0.5.0, 2024-11-21). *Obligation.*

**FMT-02 — Image layout: 2–5 dimensions, multiscale levels as sibling arrays.** An image group contains one array per resolution level (names arbitrary, typically `0`..`n`); the number of dimensions is 2–5; all image arrays MUST be at most 5-dimensional with axis order time → channel → spatial. — S1 (§Images layout). *Obligation.*

**FMT-03 — `axes` metadata obligations.** Each axes entry MUST contain a unique `name`; `type` SHOULD be `space`/`time`/`channel` (custom values MAY); `unit` SHOULD be a UDUNITS-2 string (spec lists the valid space and time unit vocabularies). The axes list length MUST equal array dimensionality, MUST contain 2–3 space axes, MAY contain one time and one channel/custom axis, MUST be ordered time → channel/custom → space, and spatial axes SHOULD be ordered `zyx` when the data is a z-stack. The `dimension_names` attribute MUST be present in each level array's `zarr.json` and MUST match the axes names (clarified as MUST in 0.5.2, 2025-01-10). — S1 (§axes, §multiscales), S2 (0.5.2), S6 (image.schema: axes array minItems 2 / maxItems 5, contains 2–3 `space` items). *Obligation.*

**FMT-04 — `multiscales` and calibration obligations.** Each multiscales entry MUST have `axes` and `datasets`; dataset `path`s MUST be ordered from highest to lowest resolution; each dataset's `coordinateTransformations` MUST contain exactly one `scale` transformation expressing physical pixel size (or, if unavailable, the ratio to the first resolution level, defaulting to 1.0) and MAY contain exactly one `translation`, which MUST come after `scale`. Group-level `coordinateTransformations` MAY apply to all levels, applied after the per-dataset transforms. `name`, `type` (downsampling method) and `metadata` are SHOULD. Where multiple multiscales entries exist, the normative guidance is: choose by name, fall back to the first entry. Scale/translation array lengths MUST equal the axes length. — S1 (§multiscales, §coordinateTransformations), S6 (image.schema: `coordinateTransformations` array minItems 1, exactly one `scale` item, items oneOf scale/translation). *Obligation (with explicit reader guidance).*

**FMT-05 — Transformation vocabulary is deliberately narrow in 0.5.** Allowed transformation types are `identity`, `translation`, `scale` only; values may be inline lists or referenced via a binary `path` in the container; transformations in a list apply sequentially in order. Rotation/affine/sequence are *not* part of 0.5 image metadata (they appear in 0.6's scene metadata and in napari-ome-zarr's scene-graph reader, see RD-09). — S1 (§coordinateTransformations), S4 (napari-ome-zarr README), S3 (version_history 0.6). *Obligation (0.5) / forward-compat note.*

**FMT-06 — `omero` rendering metadata is transitional and optional, but structured.** If present it MUST contain `channels` (one entry per channel); each channel MUST contain `color` (6 hex digits RGB) and `window` with `min`/`max`/`start`/`end`; `rdefs` carries `defaultT`, `defaultZ`, `model` (`color`|`greyscale`); the example also shows `label`, `family: "linear"`, `active`, `coefficient`, `inverted`. image.schema requires `channels` and per-channel window fields `start,min,end,max`; `label`/`family`/`color`/`active` are schema-optional. Because it is transitional, readers MUST be prepared for its absence — display defaults are then a product decision (OPT-03). — S1 (§omero), S6 (image.schema omero def). *Obligation-if-present; presence optional/transitional.*

**FMT-07 — Labels: integer-only pixel data, structural coupling to the parent image.** Label images live under an image's `labels/` group; the group's `zarr.json` MUST list label image paths (`{ "labels": [...] }`); label pixels MUST be one of `uint8/int8/uint16/int16/uint32/int32/uint64/int64`; label dimensions MUST match the parent image dimension or be `1`; intermediate groups MUST NOT contain metadata; each label image MUST itself implement multiscales, and its `datasets` list MUST have the same number of scale levels as the original unlabeled image. `image-label` metadata SHOULD be present with `colors` (each item MUST have integer `label-value`; `rgba` MAY be 4 ints 0–255 incl. alpha) and a `version` string MUST; `properties` (arbitrary per-label key/value) and `source.image` (relative path, default `../../`) are MAY. Readers SHOULD display labels using the specified colors. — S1 (§labels), S7 (label.schema: colors minItems 1 unique, `label-value` required, rgba 4×0–255; properties label-value integer; source.image string). *Obligation / SHOULD on display.*

**FMT-08 — High-content-screening (HCS) hierarchy and plate/well metadata.** Plates are `plate → row → well → field-of-view` groups; plate metadata MUST contain `columns`, `rows`, `wells`, `version`; each well entry MUST have `path` (row name + `/` + column name), 0-based `rowIndex` and `columnIndex`, all consistent; `acquisitions` is MAY with `id` (unique int ≥0) REQUIRED inside each acquisition; `field_count` and plate `name` are SHOULD. Well metadata MUST contain `images` (each with alphanumeric, unique, case-sensitive `path`; `acquisition` key MUST be present when the plate defines multiple acquisitions). Empty rows/wells SHOULD NOT be present. Row/column names MUST avoid duplicates and care is advised for case-insensitive filesystems (relevant to local reading on macOS/Windows). — S1 (§HCS layout, §plate, §well). *Obligation.*

**FMT-09 — `bioformats2raw.layout` (transitional) multi-image collections.** A top-level group with `bioformats2raw.layout: "3"` wraps a series of images: `OME/METADATA.ome.xml` (MetadataOnly) SHOULD be present; `OME` group MAY carry a `series` list of image paths ordered like the OME-XML Images; without `series`/plate, images MUST be in consecutively numbered groups from `0`. If `plate` metadata is also present it takes precedence. Conforming readers SHOULD NOT silently open only the first image; they SHOULD make users aware of multiple images and MAY offer a choice. This layout exists to describe filesets already in the wild and is slated for replacement. — S1 (§bioformats2raw). *Transitional obligation on readers.*

**FMT-10 — Machine-readable 0.5 schemas exist but under-constrain the format.** The 0.5 tree ships JSON Schema (draft 2020-12) documents with `$id` `https://ngff.openmicroscopy.org/0.5/schemas/image.schema` and `.../label.schema` plus plate/well/bf2raw/ome schemas and strict variants. Notably, the image schema encodes: `ome` required with `multiscales` + `version`; axes 2–5 items with 2–3 space axes; per-dataset transform array with exactly one `scale` (minItems 2 numbers); omero window requiring start/min/end/max. However, several normative prose rules are NOT encoded in the schema: dataset ordering (largest→smallest), translation-after-scale ordering, axis type ordering (time→channel→space), equal level counts between label and parent image, and plate `wells.path` ↔ rows/columns consistency. A validator or reader relying on schema validation alone will accept spec-invalid filesets. — S1 (§axes, §multiscales, §labels prose) vs. S6 (image.schema) + S7 (label.schema) as counter-evidence. *Obligation + validation gap.*

### B. Version ecosystem and compatibility

**COMP-01 — The brief's target version 0.5 is no longer the newest spec: 0.6 was released 2026-09-14.** The spec repository's main-branch index states "The current released version of the OME-Zarr specification is 0.6", and the 0.6 changelog entry (dated 2026-09-14) records RFC-5 adoption (transformations, coordinate systems, `scene` metadata) with multiple BREAKING CHANGE markers (unified `input`/`output` object form, removal of `inverseOf`, camelCase `inputAxes`/`outputAxes`, vector fields as normal multiscale groups). Slide Scout's 0.5 focus remains valid, but a browser that hard-assumes 0.5 will be increasingly presented with 0.6 filesets. Note a small documentation inconsistency observed: `https://ngff.openmicroscopy.org/latest/` still served a redirect to `specifications/0.5/index.html` on fetch date, while the source repo says 0.6 — treat "latest" claims per fetched source and version. — S3 (specifications/index.md; main version_history.md), S8 (`/latest/` redirect content). *Established fact; compatibility limit.*

**COMP-02 — Real-world filesets span 0.3 / 0.4 / 0.5 with different storage layers.** The compatibility matrix and reader docs exercise IDR sample data hosted at `.../idr/zarr/v0.3/...`, `/v0.4/...` and `/v0.5/...` URLs; ome-zarr-py's changelog shows multi-year 0.4 support before 0.5; the 0.4.1 release added the transitional b2raw layout "to specify filesets that already exist in the wild". A local-fileset browser should detect Zarr v2 vs v3 and the 0.x OME metadata version per hierarchy (FMT-01) and either read or clearly explain older filesets. — S9 (matrix sample URLs), S5 (ome-zarr-py changelog), S1 (b2raw transitional rationale). *Compatibility requirement.*

**COMP-03 — The ecosystem itself warns that 0.5 support is uneven.** ome-zarr-py's current documentation states: "The default version of OME-Zarr written by ome-zarr-py is v0.5, which uses zarr v3. OME-Zarr v0.5 is not yet supported by all OME-Zarr tools." ome-zarr-py also pinned `zarr < 3` in its own 0.10.2 release (November 2024) — i.e., even the reference library lagged full Zarr v3 adoption; current master uses the new OMEZarrMultiscale API over zarr v3. For Slide Scout this means the local Zarr-v3 reader is the risky component, and 0.5-written-by-2024/25-tools data must be tested against real writer quirks. — S5 (docs index; CHANGELOG 0.10.2, read_image docs). *Compatibility requirement.*

### C. Reader-implementation lessons (compatibility, correctness, navigation, display)

**RD-01 — Independent feature-matrix results, with pinned versions (April 2025 test round).** The community viewer matrix records, per feature and viewer: supported / ignored (no effect) / fails (image doesn't open) / missing (untested). Named tested versions: napari 0.5.6 with napari-ome-zarr 0.6.1 and ome-zarr 0.10.3; vizarr (current viewer, April 2025); BigDataViewer Fiji jars bigdataviewer_fiji-6.4.1, bigdataviewer-core-10.6.4, bigdataviewer-image-loaders-0.9.0, bigdataviewer-n5-1.0.2; MoBIE mobie-viewer-fiji 6.3.1 + mobie-io 4.0.3; webKnossos 24.11.0; OMERO with BioFormats ZarrReader 0.2.0; Blender 4.4.1 + Microscopy Nodes 2.2.0. Avivator, Vol-E, itk-vtk-viewer and neuroglancer were tested without named versions in the preamble. — S9 (matrix page; template source S10). *Evidence base for RD-02..RD-08.*

**RD-02 — Z-downsampled pyramids break real viewers.** For the "Z downsample" sample (IDR 9836832): Avivator and vizarr FAIL (vizarr: "expects the same number of Z-sections for each pyramid resolution", vizarr issue #60); napari is marked missing with the note "Image appears to load and display OK, but very quickly crashes on zooming etc."; Microscopy Nodes ignores it ("Z-pixel size is read without the downsampling. Can be adjusted... with the UI"); OMERO fails. BigDataViewer, MoBIE, Vol-E, itk-vtk-viewer, neuroglancer, webKnossos are marked supported. Lesson: per-level axes extents may shrink in Z as well as X/Y, and physical Z scale per level must be recomputed; naive viewers crash or mislabel calibration. — S9 (matrix row "Z downsample"). *Correctness + display requirement.*

**RD-03 — Non-2× downsampling factors break viewers.** For "multiscales downsampling not=2" (IDR 9846318): vizarr FAILS (issue #101); neuroglancer FAILS with "Error parsing 'dtype' property: Unsupported numpy data type: >u1" (big-endian arrays); most others supported. Lesson: the spec mandates exactly one scale per dataset precisely so arbitrary factors are representable; a reader must not assume factor-2 pyramids and must handle non-native-endian dtypes. — S9 (matrix row), FMT-04. *Correctness requirement.*

**RD-04 — `omero` metadata uptake is inconsistent even among established viewers.** "omero info" row: vizarr and napari apply channel names/colors/windows from `omero`; webKnossos applies it but "rdefs are not supported"; Vol-E and OMERO's own path "read channel labels from 'omero' metadata, but the colors are ignored"; several others ignore it. Lesson: honoring `omero` (channel names, colors, windows, default T/Z, model) is a differentiator and a source of "wrong defaults" complaints when ignored; rdefs handling varies. — S9 (matrix row "omero info"), FMT-06. *Display requirement / product decision on defaults.*

**RD-05 — Axes handling and legacy versions.** With v0.3 axes files, neuroglancer, webKnossos and Microscopy Nodes FAIL; with v0.4 axes, essentially all tested viewers are marked supported. Lesson: respect named axes and units rather than positional assumptions; older filesets are where positional/`c,z,y,x` assumptions bite. — S9 (matrix rows "axes (v0.3)", "axes (v0.4)"). *Compatibility + correctness.*

**RD-06 — Labels overlay support is broad but with interface caveats.** "labels" row: napari (plugin auto-loads `labels/` subgroups as label layers, initially inactive) supported; MoBIE supported but requires manually pasting `URL.zarr/labels/<name>` in the open dialog (not auto-discovered); vizarr and webKnossos supported; many other viewers mark labels ignored. Lesson: auto-discovery via the `labels/` group listing (FMT-07) is the reader-friendly path; overlay must handle integer IDs, per-label rgba incl. alpha, and properties tables. — S9 (matrix row "labels"), S4 (napari-ome-zarr README "Data support"), FMT-07. *Navigation/display requirement.*

**RD-07 — HCS plates are the weakest feature across viewers.** "HCS plate" row: vizarr "supported" but "Only the lowest resolution of a Plate is shown. Clicking a Well loads it in a new window"; webKnossos "Plate appears to load and display OK, but crashes on zooming in"; napari "missing"; itk-vtk-viewer, neuroglancer, OMERO and Microscopy Nodes fail in various cells. napari-ome-zarr's approach (grid concatenation of the first image per well) and MoBIE's separate "Open HCS Dataset" entry show two workable UX patterns. Reader-level lessons from ome-zarr-py history: missing wells must not break loading (fix 0.1.1), plate pyramids had loading bugs (fix 0.4.2), and field-of-view paths are not always `"0"` (fix 0.8.2). Lesson: plate browsing needs an explicit well/field navigation model, sparse-plate tolerance, and lazy per-well loading. — S9 (matrix row "HCS plate"), S4 (README Plates), S5 (CHANGELOG 0.1.1/0.4.2/0.8.2), FMT-08. *Navigation requirement.*

**RD-08 — bioformats2raw collections are poorly handled by many viewers.** "bioformats2raw.layout" row: napari FAILs (issue #71, historical), MoBIE and neuroglancer FAIL (neuroglancer: "Neither .zarray metadata nor OME multiscale metadata found"), OMERO fails; BigDataViewer can open the arrays via "Detect datasets" but "not as a 'multiscale' image"; vizarr redirects through the validator to per-image links; Microscopy Nodes supported. The spec itself (FMT-09) says readers SHOULD NOT default to the first image. Lesson: collection detection (`bioformats2raw.layout` + `OME/series` or numbered groups) with an image-picker is required behavior, not a nicety. — S9 (matrix row "bioformats2raw.layout"), S1 (§bf2raw reader clauses). *Navigation requirement.*

**RD-09 — Scene/coordinate-graph support exists in the plugin ecosystem ahead of (and now parallel to) 0.6.** napari-ome-zarr documents reading `Scene` groups: it builds a graph from `coordinateTransformations` (supporting `identity`, `scale`, `translation`, `rotation`, `affine`, `sequence`), picks the "top" coordinateSystem with the most input images, and reads only the first coordinateSystem per image to determine axes. This is RFC-5-style functionality; 0.6 then introduced BREAKING syntax changes (COMP-01). Slide Scout should decide whether scene/transform graphs are in scope; if yes, version-pin the syntax per fileset. — S4 (README Scenes), S3 (main version_history 0.6). *Optional capability; forward-compat.*

**RD-10 — Reference reader architecture patterns.** ome-zarr-py exposes a node-walk reader (`Reader(parse_url(...))` yields image, hidden `labels/` nodes) and a higher-level `OMEZarrMultiscale.from_ome_zarr()` that surfaces per-level dask arrays with `axes`, per-level `scale` dicts, and `axes_units`/`axes_types` — i.e., calibration is resolved per resolution level, not globally (consistent with FMT-04's inter-level scaling rule); the same API works for local filesystem paths as for URLs. vizarr demonstrates purely client-side reading (zarrita.js) with GPU rendering (Viv) but explicitly restricts itself to "2D slices of n-Dimensional Zarr arrays" with channel blending, supports a fixed dtype set (int8/16/32, uint8/16/32, float32/64), and self-describes as built for one use case with other Zarr arrays "supported but not as well tested". Lesson: the thin-plan risks are (a) treating calibration as global, (b) assuming 3D/volume, (c) unhandled dtype coverage. — S5 (read_image docs), S11 (vizarr README). *Architecture/transfer lessons.*

### D. Performance / local-fileset considerations

**PERF-01 — Multiscale level selection is the primary responsiveness lever, and it is normatively supported.** The spec's own reading guidance is to pick a named multiscale or fall back to the first; level arrays are independent, so a browser can serve the overview from a coarse level without touching full-resolution chunks (this is how matrix viewers behave on pyramids). Inference (marked as such): chunk-aligned reads against local disk should favor the same locality properties that make remote chunked reads viable. Zarr v3 also permits sharding codecs (all Zarr features "including codecs, chunk grids, chunk key encodings... may be used with OME-Zarr unless explicitly disallowed"), which changes the on-disk access pattern (one shard file contains many chunks). ome-zarr-py documents sharding in its advanced docs (page listed in docs nav; content not fetched — unvisited lead). — S1 (§multiscales python guidance, §Storage format), S5 (docs nav: advanced/sharding.html). *Performance requirement; sharding partially unverified.*

**PERF-02 — "Clearly explain data it cannot display" maps to concrete failure classes seen in the field.** Matrix "fails" notes are specific: Z-mismatched pyramids (RD-02), non-2× factors (RD-03), unsupported big-endian dtype (RD-03), b2raw root opened as an image (RD-08), plate zoom crashes (RD-07). A robust browser should classify: version/storage-layer mismatch (Zarr v2 vs v3), schema-invalid metadata, unsupported dtype/endianness, partial-pyramid inconsistencies, missing wells/fields, and absent optional metadata (no `omero` ⇒ defaults decision OPT-03). — S9 (matrix notes), FMT-01..FMT-10. *Display requirement.*

### E. Optional capabilities / explicit product decisions (not format obligations)

**OPT-01 — Volume (3D) rendering vs slice browsing.** 0.5 supports 2–5D data; several reference viewers deliberately render 2D slices only (vizarr, RD-10) while others add volume views (Vol-E, AGAVE, syGlass, WEBKNOSSOS per the tools inventory). Slice-only is spec-compliant; volume is a product choice.
**OPT-02 — Plate grid interaction depth.** Minimum: show plate layout + navigate wells/fields (napari/MoBIE patterns, RD-07). Lazy-loading and well-level multiscale rendering beyond the first field are enhancements.
**OPT-03 — Default rendering without `omero`:** compute per-channel min/max windows and a channel color palette vs. showing raw greyscale; also whether `rdefs.defaultT/defaultZ` should seed the initial timepoint/plane when `omero` IS present (the spec places no consumer MUST on rdefs).
**OPT-04 — Scene/transform-graph support (RD-09) and future 0.6 readiness (COMP-01).**
**OPT-05 — Beyond-boundary capabilities remain out of scope by the brief:** writing, export, remote services, clinical interpretation. Reading remote URLs is *not* required by the brief even though nearly all ecosystem tooling defaults to it; local-first is the differentiator.
