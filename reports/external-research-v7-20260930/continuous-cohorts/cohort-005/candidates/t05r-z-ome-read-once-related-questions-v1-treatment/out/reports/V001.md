## 1. Q1 — What the admitted evidence supports

### 1.1 Substrate, conformance framework, metadata conventions

**F-01 [OBLIGATION][CONDITION] Requirement language and normative scope.** RFC 2119 keywords govern; all text is normative except examples, notes and explicitly non-normative sections; requirement words appear in lower/upper case without loss of force. S003:L57–59, L869–888. Condition for every finding below: text inside examples (e.g., the JSON blocks at L320–387, L476–512, L561–640, L643–739, L756–784, L788–808) is illustrative unless a normative sentence states a rule.

**F-02 [OBLIGATION][MECHANISM] Zarr v3 substrate with a wide allowed-feature surface.** OME-Zarr is implemented on Zarr format version 3; "All features of the Zarr format including codecs, chunk grids, chunk key encodings, data types and storage transformers may be used with OME-Zarr unless explicitly disallowed in this specification" (L68–72). Version history: Zarr v3 adopted in 0.5.0 (2024-11-21, L831–833). Condition: the spec disallows almost nothing explicitly, so a conformant fileset may use any Zarr v3 codec/transformer — a reader supports a subset or must explain what it cannot display. [INFERENCE] The corpus does not enumerate which Zarr features real producers use (see F-31, F-32).

**F-03 [OBLIGATION] Metadata substrate and version consistency.** OME-Zarr metadata lives in the various `zarr.json` files under the namespaced `ome` key in attributes; the metadata version is a string in `ome.version` (example "0.5", L152–165); "The OME-Zarr Metadata version MUST be consistent within a hierarchy" (L155–156). [FAILURE] Inconsistent `ome.version` across a hierarchy violates the spec; detection is a reader-side validation duty (no format-defined behavior, see F-30).

**F-04 [OBLIGATION][FAILURE] JSON comments are prohibited in data.** "comments MUST NOT be included in JSON objects"; comments in the document's examples are for clarity only (L65–66). [COUNTEREVIDENCE/tension] The spec's own examples embed `//` comments (L341, L351, L361, L370; also the annotated `omero` block L401–423), so example blocks are not valid JSON as printed — copying them verbatim produces non-conformant metadata (F-33).

**F-05 [MECHANISM] Storage neutrality.** The hierarchy "is represented here as it would appear locally but could equally be stored on a web server to be accessed via HTTP or in object storage like S3 or GCS" (L73–77). Condition for Slide Scout: the format imposes no local-filesystem assumption, so a local-only reader is a product subset, not a format accommodation.

### 1.2 Hierarchy obligations

**F-06 [OBLIGATION][MECHANISM] Image fileset layout.** One image = one Zarr group; group-level attributes in `zarr.json` include "multiscales" and "omero" (L87–89). Each multiscale level is a separate Zarr array; "The name of the array is arbitrary with the ordering defined by the 'multiscales' metadata, but is often a sequence starting at 0" (L91–94). "All image arrays must be up to 5-dimensional with the axis of type time before type channel, before spatial axes" (L96–97). Chunks conform to the Zarr array specification and the array's own `zarr.json` (L99–100). Dimensionality is variable between 2 and 5 and "axis names are arbitrary" (L81). [FAILURE] Discovery or level-ordering logic that hardcodes names ("0","1","2") or axis names is unsupported by the format except in the numbered bioformats2raw collection case (F-24, L268–269).

**F-07 [OBLIGATION][CONDITION] Labels placement and pixel constraints.** A `labels` group nested in the image group holds label images; its `zarr.json` lists them, e.g. `{ "labels": [ "original/0" ] }` (L102–105). Each label dimension "should" equal the corresponding image dimension or be 1 if irrelevant (L106–108, lowercase should → normative per F-01). Intermediate folders are permitted but "currently contain no extra metadata" (L110). Label multiscales carry "only integer values" (L116–117); normatively, label pixels MUST be one of [uint8, int8, uint16, int16, uint32, int32, uint64, int64] (L438–439), and intermediate groups between `labels` and its images "MUST NOT contain metadata" (L439–440). [FAILURE] Float label data or metadata-bearing intermediate groups are non-conformant.

**F-08 [OBLIGATION][CONDITION] High-content screening (HCS) hierarchy.** For HCS datasets "Three groups MUST be defined above the images": the group above the images is the well and MUST implement the well specification; above it a row; above that a plate which MUST implement the plate specification (L119–127). A well row group SHOULD NOT be present if there are no images in the row; a well group SHOULD NOT be present if there are no images in the well (L128–129). Condition: these obligations govern HCS filesets; the spec does not state that every OME-Zarr fileset is HCS.

### 1.3 Metadata obligations (per key)

**F-09 [OBLIGATION][OPTIONAL] `axes`.** Each axis dict MUST contain `name`, unique across all names (L167–168); SHOULD contain `type`, SHOULD be "space"/"time"/"channel", MAY be another string for custom axis types (L169); SHOULD contain `unit`, the value SHOULD be one of the enumerated UDUNITS-2 strings (space units L171, time units L172). Length of `axes` MUST equal the dimensionality of the image arrays (L173). Conditions: names, types and units are only SHOULD-level except name presence/uniqueness and the length rule — a conformant file may omit units or use custom axis types.

**F-10 [OBLIGATION] `dimension_names` on arrays.** "The 'dimension_names' attribute MUST be included in the zarr.json of the Zarr array of a multiscale level and MUST match the names in the 'axes' metadata" (L174). Version qualification: this MUST was clarified in 0.5.2 (2025-01-10, L825–827). Note the locus difference: `axes` is group-level metadata; `dimension_names` is array-level — a validating reader must check both.

**F-11 [OBLIGATION][CONDITION] `multiscales` axes constraints and ordering.** Each multiscales dict MUST contain `axes` (L299); length must be 2–5 and equal to array dimensionality (L300); MUST contain 2 or 3 `space` entries, MAY contain one `time` entry, and MAY contain one additional `channel` **or** null/custom-type entry (L301 — i.e., at most five axes, with a single second non-space slot). Entry order MUST correspond to array dimension order and MUST be ordered by type: time first (if present), then channel/custom (if present), then space (L302); if there are three spatial axes (zyx stacking), spatial axes SHOULD be ordered "zyx" (L303). Image = 2–5 dimensional data with optional time/channel axes, stored as a multiple-resolution representation (L296–297). [FAILURE] Axis-order violations make physical-coordinate mapping ill-posed.

**F-12 [OBLIGATION] `datasets` (resolution levels).** Each multiscales dict MUST contain `datasets`, a list of dicts; each MUST contain `path` relative to the current zarr group; "The 'path's MUST be ordered from largest (i.e. highest resolution) to smallest" (L304–306). All dataset dicts MUST have the same number of dimensions, MUST NOT exceed 5, and number/order of dimensions MUST correspond to `axes` (L307). [MECHANISM] This ordering is what lets a viewer pick a pyramid level without inspecting shapes first.

**F-13 [OBLIGATION][CONDITION] Dataset `coordinateTransformations` (calibration core).** Each dataset MUST contain `coordinateTransformations` mapping data coordinates to physical coordinates for that level; transformations MUST only be of type translation or scale (L308–309). They "MUST contain exactly one scale transformation that specifies the pixel size in physical units or time duration"; if scaling information is unavailable or inapplicable for an axis, the value MUST express the scaling factor between the current and the first resolution for that axis, defaulting to 1.0 without downsampling (L310). It MAY contain exactly one translation, which MUST be listed after scale (so it is expressed in physical coordinates); scale/translation array lengths MUST equal the length of `axes` (L311–312). Rationale: a simple data→physical mapping compatible with the general transformation spec (L313). Conditions: the relative-factor default applies only when absolute scaling is unavailable for an axis.

**F-14 [OPTIONAL][MECHANISM] Multiscales-level `coordinateTransformations`.** A multiscales dict MAY contain group-level transformations applied to all levels, after the dataset-level ones, under the same type/order rules; e.g., to give a scale for a dimension shared by all resolutions (L314–316; example: time unit 0.1 ms at L368–374). Transformations in a list "are applied sequentially and in order" (L293). [INFERENCE] Correct physical coordinates therefore require composing dataset-level then multiscales-level transforms in list order, with `identity` as the default transform (L282–283).

**F-15 [OPTIONAL][MECHANISM][FAILURE] Transform vectors may be external binary data.** For translation and scale, the vector is "one of: `translation`/`scale`:List[float], `path`:str — stored either as a list of floats or as binary data at a location in this container"; vector length defines dimensionality (L284–292). Condition: a conformant 0.5 file may legally store its scale vector at a binary path rather than inline. [FAILURE] A reader that only accepts inline float lists will fail on conformant files unless it detects the `path` form and explains or handles it.

**F-16 [CONDITION][UNRESOLVED] Multiple multiscales entries.** "If only one multiscale is provided, use it. Otherwise, the user can choose by name, using the first multiscale as a fallback" — followed by reader pseudocode including "Or perhaps choose based on chunk size" (L388–397). [UNRESOLVED] This passage sits in the normative body but is code-shaped; its exact conformance force (normative rule vs informative guidance) is not settled by the text. Observed content: name-based user choice with first-entry fallback.

**F-17 [OPTIONAL] Multiscales descriptive fields.** `name` SHOULD be present (L317); `type` (downscaling method) SHOULD be present (L318); `metadata` about the method SHOULD be present (L319; example L375–382). All optional.

**F-18 [OPTIONAL][CONDITION] `omero` render metadata (transitional).** Transitional channel/render information under the `omero` key: `id`, `name`, `channels` (annotated in the example as "Array matching the c dimension size", L403), and `rdefs` with `defaultT`, `defaultZ`, `model` "color"/"greyscale" (L398–423). "The 'omero' metadata is optional, but if present it MUST contain the field 'channels'"; each channel dict MUST contain `color` (6 hex digits, RGB) and `window`; `window` MUST contain `min`,`max`,`start`,`end` (L426–430). Semantic reference is external: "See the OMERO WebGateway documentation" (L424–425). Transitional rule: implementations may be expected (MUST) or encouraged (SHOULD) to support **reading** transitional metadata; writing is usually optional (MAY) (L60–64). [CONDITION] All channel colors/windows/rendering defaults exist only when `omero` is present.

**F-19 [OBLIGATION][CONDITION] Labels listing and label-image parity.** The labels group's `zarr.json` MUST contain a `labels` key whose value is a JSON array of paths to the labeled multiscale image(s); all label images SHOULD be listed (L441–442). The label image's `zarr.json` MUST implement the multiscales specification, and its `datasets` array "MUST have the same number of entries (scale levels) as the original unlabeled image" (L454–455). [MECHANISM] This parity rule is what makes level-aligned overlays possible; it constrains level counts, not necessarily per-level shapes.

**F-20 [OPTIONAL][OBLIGATION] `image-label` display metadata.** The label image SHOULD contain an `image-label` object, which SHOULD contain: `colors` (MUST be a JSON array; each object MUST contain integer `label-value`; MAY contain `rgba` = four integers 0–255, fourth = alpha/opacity) and `version` (MUST be a string, the image-label schema version) (L456–466). "Conforming readers SHOULD display labels using the colors specified" (L461). `image-label` MAY contain `properties` (array; each object MUST contain `label-value`, plus arbitrary key-value pairs which need not be consistent across entries) and `source` (MUST be an object; MAY include `image`, a relative path to the source image group, default "../../") (L467–474; example L476–512; display interpretation L513–514). [UNRESOLVED] The set of valid `version` strings is not enumerated in the capture.

**F-21 [OBLIGATION] Label/image dimension correspondence (should-level).** Each label dimension should equal the corresponding image dimension or be 1 if irrelevant (L106–108). Weaker than F-19's MUST parity of level counts; overlay code should validate rather than assume identical shapes.

**F-22 [OBLIGATION][OPTIONAL] `plate` metadata.** MUST contain `columns` and `rows` (every physical row/column MUST be defined even if it has no wells; each name: string, alphanumeric only, case-sensitive, MUST NOT duplicate; care SHOULD be taken to avoid case-insensitive-filesystem collisions such as "Aa"/"aA") (L530–549); MUST contain `version` (string) (L550–551); MUST contain `wells`: each well MUST have `path` = row name + "/" + column name in that order with no extra leading/trailing directories, MUST have 0-based `rowIndex`/`columnIndex`, and path+indices MUST all refer to the same row/column pair (L552–560). SHOULD contain `field_count` ("positive integer defining the maximum number of fields per view across all wells" — the spec's phrasing, L538–539) and `name` (L540–541). MAY contain `acquisitions`: each MUST have unique integer `id` ≥ 0 within the plate; SHOULD have `name`, `maximumfieldcount` (positive integer); MAY have `description`, `starttime`/`endtime` (integer epoch timestamps) (L518–529). Examples: 2×3 plate with two acquisitions (L561–640); sparse 96-well plate with 2 wells but complete 12×8 row/column lists (L641–739).

**F-23 [OBLIGATION][CONDITION] `well` metadata.** MUST contain `images`: a list of all fields of view; each MUST have `path` (alphanumeric, case-sensitive, unique within the list) (L744–748). [CONDITION] If multiple acquisitions were performed, each image MUST contain an integer `acquisition` key matching one of the plate's acquisitions (L748–750). The well dict SHOULD contain `version` whose value MUST be a string (L751–752). Examples L753–808.

**F-24 [OBLIGATION][CONDITION] `bioformats2raw.layout` collections (transitional).** Added in v0.4 for filesets "that already exist in the wild"; "An upcoming NGFF specification will replace this layout" (L180–181). Conforming groups MUST have value "3" for the key in the top-level `zarr.json` (L256); SHOULD have `OME/METADATA.ome.xml` (see F-26); the OME group MAY contain a `series` attribute that MUST be a list of string paths whose order MUST match the order of `Image` elements in the OME-XML if provided (L265–267). Discovery logic: if `plate` metadata is present, images MUST be located at the defined plate positions; if no `series` and no plate, multiscales images MUST be stored in consecutively numbered groups starting from 0 ("0/","1/","2/",…); every multiscales group MUST represent exactly one OME-XML Image in the same order as the series index or group numbers (L261–270).

**F-25 [OBLIGATION][CONDITION] Plate precedence; no mixing.** If the top-level group is a plate, `bioformats2raw.layout` may be present but the `plate` key MUST also be present, takes precedence, and parsing should follow the plate specification; "It is not possible to mix collections of images with plates at present" (L204–206).

**F-26 [OBLIGATION][CONDITION] OME-XML sidecar.** `OME/METADATA.ome.xml` (when provided): MUST adhere to the OME-XML specification and MUST use `<MetadataOnly/>` as opposed to `<BinData/>`, `<BinaryOnly/>` or `<TiffData/>`; MAY use the minimum specification (L257–260).

**F-27 [OBLIGATION] Reader duties for multi-image collections.** Conforming readers SHOULD make users aware of the presence of more than one image (i.e., SHOULD NOT default to only opening the first); MAY use `series` to determine valid groups; MAY show all images or offer a choice (as with HCS plates); MAY ignore other groups/arrays under the root (L271–275).

**F-28 [OBLIGATION][FAILURE] Key-spelling compatibility.** Multi-word keys should use camelCase, "but some parts of the specification don't obey this convention as they were added before this was adopted, but they should be updated in due course" (L809–812). Live example: the plate acquisitions field is specified as `maximumfieldcount` (all lowercase, L524) while wells use camelCase `rowIndex`/`columnIndex` (L557–559). [FAILURE] Parsers must use each key's specified spelling exactly, and the spec itself flags future renames — key sets are version-pinned.

**F-29 [OBLIGATION] Versioning posture.** The current released version is 0.5; "Migration scripts will be provided between numbered versions. Data written with these latest changes (an 'editor's draft') will not necessarily be supported" (L25–27). Plate `version` MUST be a string (L550–551); well `version` SHOULD be present with string value (L751–752); `ome.version` MUST be consistent within a hierarchy (F-03). Version history L821–866 (0.5.2 dimension_names clarification L825–827; 0.5.0 Zarr v3 L831–833; 0.2.0 chunk dimension separator changed to "/" L849–851).

### 1.4 Mechanisms observable in the capture

- **M-1 Multiresolution storage**: per-level Zarr arrays referenced by `datasets[].path`, ordered largest→smallest (F-12); level selection is reader-side (F-16).
- **M-2 Data→physical coordinate mapping**: ordered scale/translation composition with identity default, relative-scale fallback 1.0, optional group-level transforms applied after dataset-level ones (F-13, F-14, L282–293).
- **M-3 Image discovery**: branch on plate key (precedence, F-25) → bioformats2raw.layout + series/numbered groups (F-24) → labels listing for overlays (F-19); axis/array names arbitrary (F-06).
- **M-4 Chunked random access**: arrays are folders of chunk files conforming to the array's `zarr.json` (L91–100); this is the enabling mechanism for background reads and cancellation, but chunk key encoding/codec semantics live in the Zarr v3 specification, which is not in the capture (F-32).

### 1.5 Failure behavior, exceptions, optionality

**F-30 [FAILURE][UNRESOLVED — scoped negative] No error-handling semantics are defined.** Within this capture (TOC L28–47; full text read), the spec defines no error, recovery, warning or validation-reporting behavior for non-conformant filesets. Obligations are declarative; the only localized fallbacks are: identity as default transformation (L282–283); relative scale factor default 1.0 (L310); plate-over-b2f2raw precedence (L204–205); multiscale selection fallback (L388–397, force unresolved, F-16). [INFERENCE] Everything the thin plan promises about failure explanation is a reader/product responsibility, not a format guarantee; and there is no format-sanctioned way to distinguish "invalid" from "valid but unsupported" — a viewer must define that boundary itself.

**Exceptions and conditions that must stay attached to claims** (per R01): omero and bioformats2raw.layout are transitional — read support MAY be REQUIRED, write support is usually optional (L60–64, L175–176, L398–399); units and types on axes are SHOULD (F-09); custom axis types are MAY (L169, L301); translation is MAY with order condition (F-13); multiscales-level transforms are MAY (F-14); well `acquisition` keys are conditionally MUST only with multiple acquisitions (F-23); series ordering matches OME-XML only "if provided" (L267); label listing SHOULD include all label images (L442); image-label and its subkeys are SHOULD/MAY (F-20); empty rows/wells SHOULD NOT be present while rows/columns lists MUST still be complete (F-08, F-22).

### 1.6 Counterevidence, tensions, unresolved areas

- **C-1 [COUNTEREVIDENCE] 0.5/Zarr-v3 requirement vs wild legacy data.** 0.5 mandates Zarr v3 (F-02), yet the same specification retains transitional machinery precisely because layouts "already exist in the wild" (L180–181) and transitional read expectations exist (L60–64). [INFERENCE] A viewer claiming "OME-Zarr 0.5 interop" will still plausibly encounter 0.4-era structures (v2-style data, series/METADATA.ome.xml collections); whether those are in scope is a product decision the capture cannot settle. This is the strongest internal counterevidence to a v3-only reader assumption.
- **C-2 [COUNTEREVIDENCE] Examples vs JSON rule** — F-04/F-33: data MUST NOT contain comments (L65–66) while the spec's own examples do (L341, L351, L361, L370, L401–423). Practical trap for test fixtures built by copying examples.
- **U-1 [UNRESOLVED] Reader/tooling landscape is absent from the corpus.** Section 4 "Implementations" contains only "See Tools." (L813–814). The brief asks for research on "actual reader implementations"; this cannot be satisfied from the admitted capture. Scoped claim: no reader-implementation evidence exists in this corpus (not: none exists anywhere).
- **U-2 [UNRESOLVED] Zarr v3 normative dependency not captured.** L68–72 depends on the Zarr v3 specification, but the capture's normative references list only RFC 2119 (L893–896). Codec, chunk-grid, chunk-key-encoding and storage-transformer semantics (and thus exact read granularity) are unresolved here; only the historical separator note at L849–851 touches key layout.
- **U-3 [UNRESOLVED] OMERO window/rdefs display semantics** are deferred to external OMERO WebGateway documentation (L424–425), not captured; `min/max/start/end` semantics (e.g., how start/end relate to min/max) cannot be fully derived from this corpus.
- **U-4 [UNRESOLVED] UDUNITS-2 boundary.** Valid space/time unit strings are enumerated (L171–172), but whether other UDUNITS-2-valid spellings must be accepted is not settled; the requirement itself is SHOULD-level.
- **U-5 [UNRESOLVED] image-label `version` values** not enumerated (L459–460).
- **U-6 [UNRESOLVED] Conformance force of the multiscale-selection pseudocode** (L388–397) — see F-16.
- **U-7 [UNRESOLVED] `omero.channels` length vs the channel-axis size** appears only as an example comment ("Array matching the c dimension size", L403), not in the normative sentences (L426–430); it cannot be treated as a MUST from this capture (F-34).
- **U-8 [UNRESOLVED] Capture provenance.** The alias URI is recorded, but the version tag is `capture-only:<hash>`; no live confirmation was permitted, so currency against the live site is unverified (catalog-imposed limit).
- **U-9 [UNRESOLVED] "Tools" page and migration scripts** referenced (L25–26, L813–814) are not in the corpus.

## 2. Q2 — Consequences for the supplied thin plan (same evidence, same finding IDs)

Plan under review: inputs/plan/Viewer.md (thin fixture): open local OME-Zarr 0.5 fileset, list images, pan/zoom canvas, channel visibility, time-point/plane selection "where relevant", optional label overlays, details panel (dimensions/units/coordinates), automatic pyramid-level choice, background reads with cancellation, failure explanations, interop with real 0.5 tools, local-only read-only boundary, acceptance via representative filesets.

### 2.1 Plan-element dispositions (evidence → implication → disposition)

- **P-01 "opens a local fileset and lists the images it finds"** — Evidence: F-02, F-05, F-06, F-22, F-23, F-24, F-25, F-27. Implication: "the images it finds" requires a discovery procedure with at least three branches — (a) plain image groups with `multiscales`; (b) bioformats2raw collections (value "3", optional `series`, else consecutively numbered groups from 0, plate precedence if `plate` present); (c) HCS plate → row → well → fields. Readers SHOULD surface all images rather than default to the first (F-27). Gap: the plan does not mention collections or HCS at all. Disposition: add an explicit discovery algorithm; decide product scope for HCS (at minimum detect-and-explain unsupported plates, per the brief's "clearly explain data it cannot display"). Product decision: is pre-0.5/transitional wild data in scope (C-1)?
- **P-02 Canvas, channel visibility, time/plane selection "where relevant"** — Evidence: F-06, F-11, F-18, F-34, U-3. Implication: channel/time/plane structure is knowable from `axes` (which axes exist is itself optional: time and channel are MAY, F-11), but colors, windows and initial defaults (`defaultT`, `defaultZ`, `model`) exist only if the optional transitional `omero` metadata is present (F-18); window semantics are externally defined and not captured (U-3). Disposition: keep "where relevant" tied to axes presence; define an omero-absent rendering fallback (e.g., grayscale + data-derived range) as an explicit product decision — the format does not supply one.
- **P-03 Details panel: dimensions, units, coordinates** — Evidence: F-09, F-11, F-13, F-14, F-15. Implication: dimensions come from axes/array shapes; units are SHOULD-level and may be absent or custom (F-09) — the panel needs a unitless/unknown presentation policy. "Correctly calibrated coordinates" requires implementing the composition pipeline: dataset-level transforms (exactly one scale; optional translation after scale) then multiscales-level transforms, in list order, identity default, relative-factor 1.0 fallback, lengths equal to axes count (F-13, F-14). Absolute positions need the translation offsets. Additionally, scale/translation vectors may be stored as `path` references to binary data (F-15): inline-only parsing will misread conformant files. Disposition: spec the transform pipeline; decide path-vector support (implement, or detect + explicit unsupported message).
- **P-04 "The viewer chooses an available pyramid level"** — Evidence: F-12, F-16, F-06. Implication: the format constrains only the level list and its largest→smallest order; the selection heuristic is unconstrained (the only hint — chunk-size-based choice — is an informative code comment, L396, inside the force-unresolved passage F-16). With multiple multiscales entries, name-based user choice with first-entry fallback (F-16). Level names/paths are arbitrary — never hardcode (F-06).
