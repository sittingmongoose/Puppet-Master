## 3. Group 1 — Opening a fileset, listing/selecting images, navigating multiresolution data

### 3.1 What "opening" means on disk

- **F-07 — Image open = Zarr group + per-level arrays + chunk decoding (Obligation).** An image is a Zarr group of groups/arrays; group attributes (incl. `multiscales`, `omero`) live in its `zarr.json` (S003 L87–L89). Each pyramid level is a separate Zarr array (folder of chunks) whose own `zarr.json` governs decoding (S003 L91–L100). Chunks decode "conforming to the Zarr array specification" (S003 L99–L100). Zarr v3 parsing is therefore a hard dependency of every plan feature. Plan implication: EXTEND — name the dependency and its failure surface (§7).
- **F-08 — Three fileset shapes; sniff in precedence order (Obligation).** S003 defines three top-level shapes the opener must distinguish: (1) single/multi-image plain layout (`123.zarr`, `456.zarr` image groups, S003 L82–L100); (2) HCS plate layout `plate → row → well → field-of-view images` (S003 L118–L148 plus §2.7–§2.8); (3) transitional `bioformats2raw` collection (`series.ome.zarr` with `bioformats2raw.layout`, `OME/` group, numbered image groups, S003 L175–L275). The thin plan says only "opens a local OME-Zarr 0.5 fileset and lists the images it finds" (Viewer.md L5) — the recorded plan search for `plate`/`collection`/`series`/`multiscales` finds none of these shapes named (N-05). Disposition: EXTEND (required). The opener must sniff, in order: `plate` (takes precedence where present, S003 L204–L206, L262), else `bioformats2raw.layout`, else `multiscales` (single image), and report shape ambiguity rather than guessing (§3.2–§3.3).
- **F-09 — Read-only + session-local settings (Compatible boundary).** Viewer.md L9 is compatible with the source: the recorded whole-capture searches for `writ`/`mutat`/`read-only`/`edit` find only transitional write-optionality (S003 L60–L64) and editor's-draft "data written" (L26) — no viewer write requirement and no mutation blessing (N-04). ### 3.4 Multiresolution navigation

- **F-20 — Pyramid traversal by metadata order; arbitrary names (Obligation).** `multiscales[]` MUST contain `axes` (S003 L299) and `datasets[]` (S003 L304). Each `datasets[]` entry MUST contain `path` (relative to the image group) and `coordinateTransformations` (S003 L305–L308). `datasets[].path`s MUST be ordered from largest (highest resolution) to smallest (S003 L305–L306; recorded `MUST be ordered from largest` / `largest` / `smallest` searches confirm this is the sole ordering sentence). Array folder names are otherwise arbitrary ("often a sequence starting at 0", S003 L93–L94). The viewer MUST navigate by metadata order, never by assuming `0` = full resolution or that names are numeric. All levels MUST share dimensionality (≤ 5) matching `axes` count and order (S003 L307). "Largest → smallest" has no metric in the recorded searches (N-10): implement total voxel count as an ordering sanity check and flag violations without reordering — reordering would contradict "ordering defined by the `multiscales` metadata" (S003 L93–L94).
- **F-21 — `dimension_names` validation (Obligation + known conflict).** `axes` length MUST equal array dimensionality (S003 L173); `dimension_names` MUST be present in each level's array `zarr.json` and MUST match `axes[].name` (S003 L174). The version-history one-liner "the dimension_names field in axes MUST be included" (S003 L827) conflicts with L174 (recorded `dimension_names` search confirms exactly these two occurrences); follow L174 (normative section beats history entry) and read `dimension_names` from each level's array `zarr.json`. Mismatches are malformed levels: skip-with-message or refuse the image; do not silently remap axes. Disposition: EXTEND.
- **F-22 — Pyramid name/type/metadata + "appropriate level" heuristic (Recommendation + Product decision).** SHOULD-level `multiscales[].name` (S003 L317), `type` = downscaling method (S003 L318), `metadata` dict (S003 L319; example `gaussian` + skimage params, S003 L375–L382). The plan's "chooses an available pyramid level appropriate for the current view" (Viewer.md L5) is compatible but thin: the viewer SHOULD surface `name`/`type` where choosing between pyramids or explaining quality, MUST respect metadata order rather than folder sort, and MUST apply per-level transforms (§4.3) so that "appropriate" means correctly registered, not just fast. The "appropriate" heuristic itself (viewport coverage vs bandwidth vs quality) and multi-`multiscales` choice (F-10) are product decisions. Levels whose chunks/codecs the Zarr backend cannot decode are per-level unsupported input (§7), not a whole-image crash.

## 4. Group 2 — Channel/time/plane display, coordinate details, label overlays

### 4.1 Axes: dimensionality, order, names, types

- **F-25 — Rank, composition, order, names (Obligation).** `axes` length 2–5, equal to array rank (S003 L173, L299–L300); MUST contain 2–3 `type: space` entries, MAY add one `type: time` and one `type: channel` **or** null/custom type (S003 L301; recorded `null` search confirms this is the sole null-type sentence). Image arrays "must be up to 5-dimensional with the axis of type time before type channel, before spatial axes" (S003 L96–L97). Entries MUST parallel array dimension order AND MUST be type-ordered time → channel/custom → space (S003 L302). Three spatial axes with planar `yx` + stacking `z` SHOULD order `zyx` (S003 L303). Every `axes[].name` MUST be unique (S003 L168); `dimension_names` MUST match (S003 L174). Axis names are arbitrary (S003 L81); 2-D (yx), 3-D, 4-D, and 5-D images are all conforming. The viewer MUST derive its t/c/z sliders from `axes` order + `type`, never from assumed `tczyx` positions: hide the t-slider when no `time` axis exists, hide channel controls when no `channel`/custom axis exists, and treat "plane" as the two innermost spatial axes per `axes`. The plan's "time-point and plane selection where relevant" (Viewer.md L5) is correct in spirit but must be axis-driven. Disposition: EXTEND.
- **F-26 — `type`/`unit`; no channel-unit vocabulary found in scope (Recommendation with lenient-reading rule).** `type` SHOULD be `space`/`time`/`channel`, MAY be other strings for custom axes (S003 L169); `unit` SHOULD be a UDUNITS-2 string from the enumerated space/time lists (S003 L170–L172; recorded `unit`/`UDUNITS`/`micrometer` searches confirm space list L171, time list L172, and no `Units for "channel"` sentence — N-12). The L301 "null / custom type" vs L169 strings-only wording leaves null-typed axes half-admitted; implement lenient reading (accept missing/null/unknown `type`, classify by position only to place sliders, label frankly e.g. "axis 1 (untyped)"). The viewer SHOULD honor units for calibrated display (§4.3) and MUST tolerate missing/unknown `type`/`unit` (they are SHOULD/MAY, not MUST): unknown units display literally with an "uncalibrated/unknown unit" caveat rather than erroring.

Honor `active`/`label`/`rdefs.defaultT/defaultZ/model` as best-effort initial state (initial visibility ← `active`, initial t/z ← `defaultT`/`defaultZ`, initial compositing ← `model`), but never require them. ### 4.3 Coordinates: transforms, units, and the details panel

This is the brief's "read correctly calibrated coordinates" requirement (brief L3) and the plan's "details panel shows dimensions, units and coordinates" (Viewer.md L5). The source makes it a precise computation:

- **F-29 — Transform vocabulary + per-level + global composition (Obligation).** `coordinateTransformations` is an ordered list applied sequentially (S003 L279–L293): `identity` (default, usually implicit, S003 L282–L283); `translation` (`translation: float[]` or binary `path`, S003 L284–L286); `scale` (`scale: float[]` or binary `path`, S003 L287–L289; recorded `binary` search confirms these are the sole binary-path sentences). Each `datasets[]` entry's list MUST contain only `translation`/`scale` (S003 L308–L309); MUST contain exactly one scale expressing "pixel size in physical units or time duration", or — where scaling is unavailable/inapplicable for an axis — "the scaling factor between the current resolution and the first resolution for the given axis, defaulting to 1.0 if there is no downsampling along the axis" (S003 L310); MAY contain exactly one translation = offset from origin in physical units, which MUST follow scale so it is expressed in physical coordinates (S003 L311); scale/translation vectors MUST match `axes` length (S003 L312). `multiscales[].coordinateTransformations` MAY exist, follows the same type/order rules, and is "applied … after" the per-level transforms (S003 L314–L315; recorded `applied after` search confirms the sole composition sentence) — e.g. a shared time scale (example S003 L368–L374 scales `t` by 0.1 ms uniformly, L320–L387). Physical coordinate = `global(scale∘translate) ∘ perLevel(scale∘translate)` applied to integer data indices, in listed order (S003 L293, L314–L316). The viewer MUST compose both levels; applying only per-level transforms miscalibrates every axis the global transform touches. No worked multi-axis global example beyond time was found in scope (N-25); the outer∘inner reading is the only composition consistent with "applied after".
- **F-30 — Worked calibration + details-panel content (Derived requirements).** Normative example (S003 L320–L387): 5-D `tczyx`, t-unit ms, xyz-unit µm; level 0 scale `[1,1,0.5,0.5,0.5]`, level 1 `[1,1,1,1,1]`, level 2 `[1,1,2,2,2]`; global `[0.1,1,1,1,1]`. Physical voxel at level 0: Δt = 0.1 ms, Δc dimensionless ×1, Δxyz = 0.5 µm. The details panel must show per-axis `name / type / unit / per-level scale / global scale / composed physical extent`, and the cursor readout must convert hover indices through the composed transform of the currently displayed level. Required content: dimensions (rank + per-axis array extents per level + `axes[].name`), units (per-axis `unit` or "none/unknown"), coordinates (composed physical position of cursor / view center + voxel size at current level), plus pyramid identity (`multiscales[].name/type`, level path, downscaling note). The plan names "dimensions, units and coordinates" but not the two-level composition, per-level voxel sizes, or unit caveats. Disposition: EXTEND (required for "correctly calibrated").
- **F-31 — Calibration edge cases (Ambiguities + Unsupported input).** (a) Scale-fallback reading (S003 L310): for axes without physical scaling the value is a relative factor vs level 0 (default 1.0). The viewer cannot know from the number alone whether a `1.0` is "1 physical unit" or "no downsampling" — it MUST pair every scale with its axis's `unit` presence: no `unit` ⇒ report "uncalibrated (relative scale N)" rather than inventing units. Channel axes never have meaningful physical scale; display channel index, not converted coordinates. (b) "Offset from the origin" (S003 L311) never defines the origin — the recorded `origin` search finds only the L311 sentence plus unrelated `original` substrings (N-17); treat translations as relative to the image-group frame and say so. (c) Binary-`path` scale/translation (S003 L285–L289) has no dtype/shape/endianness rule in the recorded `dtype`/`endian`/`shape` searches (all no-hit) or the `binary` read (N-18): unsupported input unless the Zarr backend resolves it; the message must name the transform and level. (d) Missing scale transform, wrong vector length, non-scale/translation types in image transforms, or translation-before-scale all violate S003 L309–L312: malformed-level handling (§3.5), never silent reinterpretation.
