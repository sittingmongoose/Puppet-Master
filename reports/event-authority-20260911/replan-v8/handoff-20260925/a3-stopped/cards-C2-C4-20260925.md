## Card C-2: what Pause and Abort Run do to a Workflow run

Card ID: `EA-A3-GOALRUN-STOPPED-MEANING-001`. Owner: Orchestrator and Executor (Workflow run lifecycle), with Goal Runtime.

**Name:** What Pause and Abort Run mean for a Workflow run.

**Question:** When a user presses Pause or Abort Run on a Workflow run, should the run be recorded as stopped (`goal_run.stopped`, reason `user_stopped`) and should the run's Goal be paused as well?

**Why:**
- The production wiring expects `goal_run.stopped` from both commands: Orchestrator > Pause and Orchestrator > Blocked run actions > Abort Run (`Plans/Wiring_Matrix.production.json` 40062-40082 and 51931-51953).
- Canon has no writer for that event. Today the only pause is Goal-level: it "sets `paused`, latches the stop epoch, and cancels no workflow-owned record", and nothing may auto-resume (`Plans/Goal_Runtime_System.md` 258).
- A stopped run is fenced but not finished. It can resume only through a new revision and an admitted `goal_run.replanned` (GRS 3468).
- The Debug investigation banner's "Cancel investigation" reuses the Abort Run command id and records the investigation `cancelled` (`Plans/Wiring_Matrix.md` 483). That is an investigation run under its own owner, not a Workflow run.

**What you get:**
- **Option 1:** both commands produce a visible, replayable "run stopped" record. The Goal shows paused, and nothing restarts on its own. The existing wiring works as written.
- **Option 2:** Pause stops only the run and the Goal stays active, so other work under the Goal can continue.

**What it costs:**
- **Option 1:** Pause and Abort look the same in the record: both end as stopped, not resumable until run resume (`goal_run.replanned`) exists. A paused Goal also blocks the Goal's other work until the user resumes it.
- **Option 2:** a new run-level fence, which canon lacks outside v8's held Replan slots. It needs its own owner contract before the stopped writer can rely on it, which adds one more contract to A3.

**Options:**
1. **Both record `goal_run.stopped` and latch the Goal's Stop (recommended).** Pause is stopped and resumable later through replan. Abort is stopped and not resumable. The Debug investigation's "Cancel investigation" keeps its own `cancelled` meaning under the investigation owner.
2. **Pause stops the run only and leaves the Goal active.** A new run-level fence is written first.
3. **Abort records cancelled instead.** This is not available now: DL-080 keeps Abort expecting stopped, and cancellation (D06) has no bound issuer (process answer Q-12).

**Recommendation:** Option 1. It keeps what the wiring and the Goal rules already say, and it needs no new fence.

**Answer:** Approved, option 1 (the recommendation). Jared, 2026-09-25, in conversation with this thread: "Recommended is good for c-2 and c-3".

## Card C-3: steps still running when Pause or Abort arrives

Card ID: `EA-A3-GOALRUN-STOPPED-INFLIGHT-001`. Owner: Executor, with Orchestrator.

**Name:** Running steps at a stop.

**Question:** If Pause or Abort Run arrives while steps are still running, what happens to them?

**Why:** A stop can be recorded only when the run is quiet. That means no step is running, and no dispatch, effect, tool call, capacity reservation or mutation fence is still open. Interrupting a running step is cancellation (D06), and D06 has no issuer (Q-12).

**What you get:**
- **Option 1:** the stop takes effect at once for new work. Running steps finish or time out under their own owners, the run is recorded stopped when quiet, and the command shows "stopping" until then.
- **Option 2:** simple and predictable: Pause is refused while anything is running.

**What it costs:**
- **Option 1:** a stop may take as long as the slowest running step. The command reports pending, and the caller retries until the run is quiet.
- **Option 2:** the user may have to press Pause several times. There is no way to stop new work from starting while a long step runs.

**Options:**
1. **Block new work at once, let running steps finish, record stopped when quiet (recommended).**
2. **Refuse Pause and Abort while anything is running.**
3. **Interrupt running steps.** Not available: it needs D06 (Q-12).

**Recommendation:** Option 1. It stops new work immediately, and it never cuts a step off halfway.

**Answer:** Approved, option 1 (the recommendation). Jared, 2026-09-25, in conversation with this thread: "Recommended is good for c-2 and c-3".

## Card C-4: which runs can record a stop

Card ID: `EA-A3-GOALRUN-STOPPED-PROFILES-001`. Owner: Executor (Workflow body owner), with this thread (A1) and Storage.

**Name:** Which Workflow runs can record a stop.

**Question:** Should the stop writer be reserved in the new v8 Workflow profile now, before A1 lands, so that every v8 run can record a stop? Or should it wait for a later v9 profile?

**Why:**
- A run can use only the writers its profile listed when it was created (EP 7523). A writer cannot be added to a profile after it is frozen.
- No existing v6 or v7 run can ever get one.
- A1 has not landed, so v8 can still carry the grammar now. The writer itself would stay unbound until the A3 stop contract lands. Process answer Q-12 prescribes this pattern for cancellation in v8.

**What you get:**
- **Option 1:** every v8 run can record `goal_run.stopped` once A3 lands, with no v9.
- **Option 2:** A1 lands as it stands, with no delay.

**What it costs:**
- **Option 1:**
  - A bounded amendment to A1's reviewed package (the v8 profile carries the stop grammar, a new D01 transition rule and a new origin kind, so its digest changes).
  - A re-review of that diff in the package and in canon, and one more packages-repo merge by you.
  - About 8 to 12 hours, with A1's landing held until then.
- **Option 2:**
  - v6, v7 and v8 runs never record stopped, and Pause stays Goal-level for them.
  - A v9 profile is needed later, and it must also carry started, cancelled and certified.

In either case, runs born before the chosen profile keep today's Goal-level pause.

**Options:**
1. **Reserve the stop writer in v8 now (A1 amendment) (recommended).**
2. **Wait for a v9 profile.**

**Recommendation:** Option 1, because A1 has not landed. After A1 lands, the only route is v9.

**Answer:** Pending. Jared asked a question on 2026-09-25: "for c-4 would there be a downside to waiting until v9? it shoulds like that would be faster". The card is re-presented with the answer (below).

### C-4 re-presented with the answer to Jared's question (2026-09-25)

**Question asked:** Is there a downside to waiting until v9? It sounds faster.

**Answer:**
- **Faster now:** yes. A1 lands as reviewed, with no amendment, no re-review and no extra packages-repo merge. That saves about 8 to 12 hours before A1 can land.
- **Probably not much slower overall.** `goal_run.blocked` needs the same thing: a writer listed in the run's profile. v8 lists none (A1 EP-127: "adds no goal_run.stopped, goal_run.blocked or goal_run.cancelled writer"). Blocked's trigger is still an open owner decision, so it cannot be reserved in v8 now. A v9 is therefore needed for blocked whichever way C-4 goes, and one v9 can carry both new writers.
- **The real downsides of waiting:**
  1. Any run created under v8 can never record `goal_run.stopped`. For those runs, Pause and Abort only pause the Goal, as today, and the wiring's expected stopped event never appears. Today this is theoretical, because nothing is built; it matters only if v8 ships as a live profile before v9.
  2. Stopped's registry and projection step (landing 2) waits for v9.
  3. v9 must carry v8's writers forward and needs its own consumer adoption, as A2 does for v8. That cost is shared with blocked.

**Updated recommendation:** Option 2 (wait for v9). A1 lands as reviewed, and one v9 carries both the stop and the blocked writers once blocked's trigger is decided. This replaces the earlier recommendation, which did not weigh that blocked needs a v9 anyway.

**Answer:** Approved, option 2 (wait for v9; the updated recommendation). Jared, 2026-09-25, in conversation with this thread: "approved".
